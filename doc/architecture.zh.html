回路与日志

有四个名字常被当成四个程序来说。它们不是。这一页画的是：真正在跑的是什么，谁往日志里写， 以及日志变了之后谁会知道。页面上的每一样东西，都出自已经存在的代码。

conductor 不是一个进程。它是回路跑一趟的代码 —— 发现、认领、工作树、代理、闸口、并入。 它在哪个进程里被调用，就在哪个进程里跑。

daemon 和 CLI 才是进程，而自 0022 起， 两者的差别比从前小了：都调用 conductor，也都在运行期间持有一个 projector。 daemon 多出来的是一把锁、一次心跳、启动时的一次修复，以及一个不断取活干的循环。

十三个包，和那支朝左的箭头

左边一列做决定。右边一列碰进程之外的东西。左边没有任何一个包叫得出右边的名字。

两个最容易混的名字，是被刻意分开的

@lingtai/env 装的是机器的环境：两个连接串、App 私钥、状态目录。 @lingtai/agent-env 装的是代理的：分层、过滤、要落进工作树的那个文件。 在 0024 之前，它们同住一个文件 —— 而这种「挨着」正是机器凭据流进子进程的那条路径的形状。现在名字直接说清了各自是谁的环境； 这才是要紧的区分，也正是它们共处一文件时看不见的那一个。

两个宿主，一条规则

每一个会往日志里追加的进程，在其运行期间都持有一个 projector。 正是这条规则，抹掉了大家一再被绊到的那处差别。

daemon 的每项常驻工作是干什么的

每条定义里有用的是后半句：它不在的时候，你会看见什么。

  • 一趟 conductor 为每个已注册的项目问 GitHub 现在有什么可跑，取一件，跑到出结论为止。一趟处理一件，或者一件也不处理。 没有它：没有活被干。这是 lingtai run 也会做的那一项。
  • projector 事件一落地就读，并推进 task_view —— 唯一的那个投影，也是看板渲染的那张表。 它是读者；它从不往日志里写。 没有它：日志完全正确，而每一块屏幕都停在它最后看到的地方。 现在每个会追加的进程都持有它，所以这已经不再是两个宿主之间的差别。
  • 取活循环 靠追加唤醒，而不是靠定时器；每次先问日志「是不是被暂停了」，然后跑一趟。 暂停本身是一个事件，所以 daemon 不在时发出的暂停，会在它回来时等着它。 没有它 —— 也就是 --no-conduct —— 你得到一个只把看板刷新、 不取活的 daemon，这正是该在已经有一趟在跑时另开的那一个。
  • 心跳 每几秒写一次 daemon_status；超过十五秒就算陈旧。刻意放在日志之外， 也是全系统唯一可变的运行态。 因为日志回答不了「还有东西活着吗」。死掉的 daemon 什么都不追加 —— 闲着的那个也一样。没有事件不等于没有 daemon，所以「活着」需要一个即使什么都没发生也会被写的存储。
  • 启动时修复 拿日志说的和世界实际有的做四项比对：投影是否跟上、有没有工作树成了孤儿、 有没有认领已经过了租期、GitHub 说的是不是日志说的。每一项在拿不到自己的输入时就空转， 而不是去猜一次全局扫描。 它把修复追加下来，而不是悄悄收拾干净：一个默默给自己擦屁股的系统 没法告诉你它一直在崩 —— 磁盘越来越干净，症状消失，然后「有东西每晚在杀 daemon」这件事 六周后以别的面目冒出来。只有 daemon 会跑它：这一趟会释放别的运行持有的认领， 而一条有人盯着的一次性命令，不该对它没被问到的活产生这种副作用。
  • 那把锁 一把会话级的 Postgres 咨询锁，lingtai:daemon。第二个 daemon 不会启动； 它会说出锁在谁手里，然后以 0 退出。 没有它：两个 daemon 抢同一件活。认领能挡下大部分，但并入通道和工作树目录挡不住。

谁改状态

四个写者、一张表、一个投影 —— 而 GitHub 站在回路的两侧，既是输入也是输出， 唯独不是「Lingtai 做过什么」的存储。

  • 只有 conductor 写「活」的事。 认领、闸口判定、并入、落地。别的都不许。
  • 看板也写。 批准、驳回、豁免都是追加。看板不是只读的 —— 它是人的决定进入日志的地方。
  • 代理经由 hook 写。 一个跑在 unix 套接字上的瘦二进制；conductor 代它追加，actor 记为 run id。
  • 投影从不往日志里写。 它们读日志，维护自己的表。会追加的投影就是历史的第二作者。
  • 投影只有一个。 task_view。一份「只有一项的清单」，唯一的作用就是让人能写出一个投影、又悄悄把它漏在清单外 —— 没有表、没有检查点、也没有会失败的检查。要加第二个，就公开地按名字加，否则它不存在。

谁通知谁

通知通道只有一条，而且是由数据库触发的，不是由任何一个进程触发的。

一件活，从头到尾

五个闸口点是固定且封闭的。每个点上跑什么由被托管仓库的 recipe 说了算；追加下来的是什么， 由 Lingtai 说了算。它不是一条直线。一次拒绝会回到 agent 那里，回到它本来就站着的 那个工作树；只有上限用尽才轮到你。

2026-09-03 发现 · 这个系统称之为「自己的 bug」的那种形状

Lingtai 自己的 recipe 在 merge 上放了一个 human: 动作 —— 每一次并入本该等一个人。它从来没跑过。两次对 main 的改动无人批准就并了进去， 在构建闸口通过之后五秒。

这个点被声明了、被 lingtai add 打印了、被记进 GatesResolved、 也画在了看板上。所有这些看起来都像是「它在工作」的证据。 配置了却没跑正是这个系统称之为自己 bug 的那种失败，而这是迄今代价最高的一例。

现在这个点和别的点一样搭一条流水线（run-once.ts 第 11 步）， 而 gate-audit.ts 对每一个闸口点做同一项比对：一件已落地的活， 它的 GatesResolved 在某个点上规划了动作，而它那次运行在该点没有留下任何判定。 能推广的是这项检查 —— 修复关掉的是一个实例，比对关掉的是一整类。 修复之前的那几次落地仍然留在日志上，所以 lingtai doctor 至今仍会点名它们； 对一份不能被改写的记录来说，这才是正确的行为。

同一种形状至今已经出现六次：一项检查存在、会报告，但看的并不是你以为它在看的那样东西。 这一页值得为这个模式来读，而不是为这些个别的 bug。

告知 GitHub：收敛，而不是重放

outbox 没有了 —— 一张表、一个投影、一个 worker、一套退避和一个死信队列， 背后只站着三次调用。取代它的东西更小也更强，差别在于它算出目标，而不是记住那次尝试。

代理拿到什么

两个文件，合并、按 recipe 过滤，以 0600 落进工作树。 conductor 恰好跑在哪个 shell 里，不是一层。

解释其余一切的那条规则

有两个问题长得很像，其实不是一回事：有哪些活存在，和 Lingtai 对它做了什么。 GitHub 回答第一个，并且是它的权威 —— 这正是发现只读标签、什么都不存的原因， 也是 GitHub 不再提供某个 issue 时它就直接不再可跑的原因。第二个由日志回答，别的都不许。

这一页记下的每一个 bug，都是那条边界被越过却没说出口的地方：一份写进投影、背后却没有事件的队列； 一条跳过了它长驻孪生兄弟所做刷新的命令；一个在一个仓库里被声明、却在两边都没被执行的闸口点； 一个因为没人注意到目标是可计算的、于是去记住尝试的 outbox。

由此还得出一条读法：行为上的断言由读 events 来定案， 不是由对代码的推理来定案。一份引了 seq 号的发现，胜过一份讲道理的。

把它写成事实，而不是留给以后被发现

还有两个接口是 promise，而且是有意的。 0026 把 runOnce、 端口和适配器都带进了 Effect：工作树、hook socket 和 agent 进程各自是一个 Scope，从前兜着「每条出口都会追加」的那个 catch-all，现在是一个具名的 defect handler，背后有测试。没有转过去的是 Runtime —— 因为 actions 要用它，而 0023 让那个包保持朴素 —— 以及 GitHubClient，因为看板、daemon 和四个命令都在用它。 两者各自是一张 ticket，只有真有东西开口要，才值得做。

admit 什么都不跑。它是五个点之一，会被解析进 GatesResolved、 也画在看板上，却没有为它搭任何流水线。这和 #58 是同一句话 —— 所以 gate-audit 把它包含在内，而不是给它开例外。

seq 不是无洞的。Postgres 序列在 INSERT 执行时取号、 在事务提交时才公开，所以在并发写者下，订阅者可能看见 seq 6 而 5 还在途中， 推进到 6 的检查点会永远跳过 5。只要 conductor 是唯一写者，它就咬不到人。 #4 必须去解决它，而不是假设它不存在。

向前兼容只做到存储为止。reducer 会忽略它不认识的事件类型， 所以旧投影能在新 conductor 下活下来。存储不会 —— 它在读的时候就抛， 所以实际上它先把这个事件拒了。目前这是刻意的，但这意味着那份宽容要等两边一致之后才真的存在。

tier: sandboxed 还没做。把整条工具链容器化本身就是一件独立的活； 第一个项目跑的是 guarded。
