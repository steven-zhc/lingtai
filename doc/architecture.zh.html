回路与日志

四个名字常被当成四个程序来说，它们不是。这一页画的是：真正在跑的是什么，谁写日志，以及日志变了谁会知道。 最后一节是一份提案，并且明确说明它是提案。

conductor 不是一个进程。它是回路跑一趟所需的代码 —— 发现、认领、工作树、agent、闸口、集成。 它运行在任何调用它的进程内部。

daemon 和 CLI 才是进程。两者都调用 conductor。daemon 在它周围还多做四件事 —— 今天所有让人意外的行为差异，都住在那道缝里。

一个库，两个宿主

daemon 不等于「conductor 在跑」。它是 conductor，加上四个常驻工作 —— 正是这四个让系统其余部分保持最新。

这几件事各自是干什么的

每条定义里有用的是后半句：它不跑的时候你会看到什么。今天它们中的大多数都缺席过。

  • conductor pass 向 GitHub 问每个已登记项目有哪些可跑，取一个，跑到出结论为止。一趟处理一个，或者一个都不处理。 没有它：没有任何活被干。这是五件事里唯一 lingtai run 也会做的一件。
  • projection follower · 投影跟随器 事件一落地就读，并推进 task_view 和 outbox —— 看板渲染所依据的表，以及 GitHub 投递所依据的表。 它只读；从不写日志。 没有它：日志完全正确，而每一块屏幕都冻在它最后看到的样子。九次运行里看板一片空白就是因为这个 —— 当时的办法是再起一个进程：lingtai daemon --no-conduct。
  • outbox deliverer · 投递器 拿 outbox 投影写下的行，真正去调 GitHub：打标签、发评论、关 issue。带退避重试；六次之后这一行判死， doctor 会点名报错。 没有它：决定永远出不了这台机器。合并发生了，日志是对的，而 GitHub 上那个 issue 依然开着、没有标签， 像是没人碰过。
  • heartbeat · 心跳 每五秒写一次 daemon_status；超过十五秒就算陈旧。刻意放在日志之外。 因为日志回答不了「还有东西活着吗」。死掉的 daemon 什么都不 append —— 闲着的也一样。 没有事件不等于没有 daemon，所以存活性需要一个「什么都没发生时也会被写」的地方。
  • reconcile 启动时把机器的实际状态与日志比对，并把差异记录下来。被中途杀掉的 daemon 会留下一个工作树， 那里还检出着一个分支，导致下一次 git 无法更新那个 ref。认领会自己过期；目录不会。 它把「删除」append 下来，而不是悄悄收拾干净 —— 因为一个默默自我清理的系统没法告诉你它一直在崩： 磁盘越来越干净，症状消失了，某个东西连着六周每晚杀掉 daemon，直到它以别的面目冒出来。
  • the lock · 那把锁 一把会话级的 Postgres 咨询锁，lingtai:daemon。第二个 daemon 不会启动，只会告诉你谁持有它。 没有它：两个 daemon 抢同一份活。认领机制能挡住大部分，但合并通道和工作树目录挡不住。

谁改变状态

四个写入者，一张表，以及一个例外 —— 一整类意外都由它解释。

  • 只有 conductor 写「活」的事。 认领、闸口结论、集成、落地。别的谁都不许写。
  • 看板也写。 approve、reject、waive 都是 append。看板不是只读的 —— 它是人的决定进入日志的入口。
  • agent 经由 hook 写。 一个挂在 unix socket 上的瘦二进制；由 conductor 代它 append，actor 是 run id。
  • 投影从不写日志。 它们读日志，维护自己的表。会 append 的投影等于历史的第二个作者。

谁通知谁

通知通道有且只有一条，而且由数据库触发，不是任何一个进程。

一个工作项，从头到尾

五个闸口位置是固定且封闭的。每个位置上跑什么，由被托管仓库的 recipe 决定；append 出来的是什么，由 Lingtai 决定。

2026-09-03 发现 · 2026-09-04 修复（#58）

Lingtai 自己的 recipe 在 merge 上放了一个 human: 动作 —— 每次合并本来都该等人点头。 它从来没有执行过。两个改动在构建闸口通过五秒之后，无人批准地合进了 main。

这个位置被声明了、被 lingtai add 打印出来、被记进 GatesResolved、还被看板渲染出来。 所有这些信号读起来都像是「它在工作」的证据。配置了却没有运行正是这个系统明确认定为自身 bug 的那种失败， 而这是迄今为止代价最大的一例。

现在这个位置会像其他位置一样构建流水线，并且 lingtai doctor 对每一个闸口位置做了 #55 当初对 end 提出的那个比对：一个已经落地的工作项，它的 GatesResolved 在某个位置计划了动作， 而它的运行在那里没有留下任何结论。能推广的是那个比对 —— 修复只关掉一个实例，比对关掉的是一整类。

八个地方。其中只有一个是权威的；其余的都可以重建、重新拉取，或者直接扔掉。

解释其余一切的那条规则

有两个问题长得很像，其实不是一回事：存在哪些活，和 Lingtai 对它做了什么。第一个由 GitHub 回答， 而且 GitHub 就是它的权威 —— 这就是为什么队列是一份缓存而不是一串事件，也是为什么 GitHub 不再列出的队列行会被直接丢掉。 第二个由日志回答，别的谁都不许答。

这一页上的每一处困惑，都是那条边界被不声不响地越过的地方：一次谁也到达不了的队列写入；一条跳过了刷新的命令 —— 而它那个长活的孪生兄弟会做这件事；一个在某个仓库里被声明、却在两边都没被执行的闸口位置。

提案 —— 十一个包，四处删除

以上所有内容都照着真实存在的代码画。这一节不是：一份提案，日期 2026-09-04，待评审。里面没有一样东西是已经建成的。

这是提案 · 不是系统

下面这些模块名来自代码之外，是对「Lingtai 应该由什么组成」的一次猜测。其中大多数已经存在，只是叫别的名字 —— 但有四处边界划错了，还有四整套机制其实根本不需要。删除的那一半，是这份提案里更大的一半。

这一节的上一稿自己造了两个词，effects 和 ports，并且保留了 outbox。两个词都删掉了。一份需要先教你它自己的词汇才能被读懂的提案，已经在它主张的那件事上失败了。

诊断：最后一块，总是住在 application 里

它已经付出的代价

看板在跑 git。apps/board/src/app/actions.ts 从 @lingtai/conductor/worktree 导入 git 和 stateDir —— 一个页面伸手到编排器里去拿一个 shell 辅助函数，因为那是它唯一存在的地方。

两个缺口叠在一起。#58 今天早上合并了。它的 close 至今还没被算出来，因为 approve 之后没有任何东西推进投影 —— 而且就算算出来了也没人投递，因为投递器在五个入口里只有两个够得到。

「有哪些投影」是在 CLI 里决定的。daemon 是被喂进去的 —— startDaemon({ projections: Object.values(PROJECTIONS) }) —— 所以「看板为什么是旧的」答案取决于你从哪个入口进来（#64）。更糟的是：一个写好了却忘了加进那份名单的投影，没有表、没有 checkpoint、也不会让任何检查失败。它和一个根本不存在的投影，从外部完全分辨不出来。

什么被删掉

四处删除

四处已经落地两处 —— outbox 在 2026-09-03（442f513），队列缓存在 2026-09-04。上面第 1–6 节画的是它们之前的系统，两样东西都还在图上。等 0022 剩下的部分落地后一起重画。

outbox —— 表、投影、投递 worker、退避重试、死信、两个事件类型，散在 conductor、daemon 和 apps/cli 三个包里。全部只为三种调用：发评论、设标签、关 issue
conductor 直接调 github，成败各 append 一条。没落地的，由 reconcile 收敛。

队列缓存 —— syncQueued、queued 行、refreshQueue
要用的时候现问 GitHub。它的主要消费者本来就在每次读之前刚刚刷新过它。

「退出前追平一次」这个特例 —— advanceBoard、catchUpProjections
每个 append 的宿主，在运行期间都持有一个 projector。一种行为，不是两种。

投影名单 —— PROJECTIONS
只剩一个投影。只有一项的名单不是名单。

outbox 这处删除留了尾巴，写在这里。它里面有两样东西不是脚手架，必须有地方落。第一样是 labelsFor —— 二十行代码，把一个工作项的状态换算成它的 issue 该带的标签：机器拿着它时是 lingtai:working，等你时是 lingtai:waiting，其余情况没有标签。这就是「GitHub 该长什么样」的全部定义，而那正是 reconcile 要用来收敛的东西，并且它是纯的。它属于 conductor，和其他关于工作项的判断放在一起。不纯的那一半留在右边：要和别人打在 issue 上的标签取并集，就得读 GitHub 的现状，所以那一步住在 github。第二样是顶替 OutboxDelivered 和 OutboxFailed 的那对事件：IssueUpdated { project, issue, change, detail } 和 IssueUpdateFailed { project, issue, change, error }，change 取 comment、labels、closed 之一。名词选 issue 而不是 outbox，因为队列马上就不存在了，而事件名不该背着一个实现细节。失败那条事件要活过所有重试机制的删除 —— 旧回路 inline 调 gh，调用失败什么都不剩，事后分不清「我们没评论过」和「评论了但没用」。留记录，不留机器。

队列这一处才是值得争论的，所以把理由写在这里。conductorPass 每一趟开头本来就已经向 GitHub 问过一次可跑集合，然后立刻从表里读回来 —— 这份缓存是同一趟 pass 内部的一个中转站。唯一因它持久化而受益的消费者是看板的 Queued 那一栏，而看板本来就是每次请求在服务端渲染的。而且正因为它被存下来了，两个入口对「要不要先刷新」产生了分歧：那就是 #57。把缓存拿掉，就没有什么可分歧的了。将来真的被速率限制咬到，缓存可以再加回来 —— 那时它会有一个理由，也会有人盯着它。

提案

十一个包，一条边界。决策在线以上，碰外部世界的一切在线以下。十一个名字里有八个已经以某种形式存在；三个是新增或抽出来的，而这三个都是某样东西不再是决策之后剩下来的。今天的包里有两个不在表上：@lingtai/runtime 并进 agent —— 它就是「启动它 · 听它说」的前半句；@lingtai/hook 原样不动 —— 它是种进工作树的编译二进制，不是库，agent 是跟它说话的那一端。

接线不该手搓。一个包声明接口、由宿主递给它一个实现，这就是依赖注入；今天的做法是把对象当参数传 —— runOnce 已经接收 client、runtime、token 和 store。这对值有效，对生命周期无效：必须有东西保证「为一趟运行打开的 projector，在运行结束时被关掉」，而且是在每一条退出路径上，包括那些提前的拒绝。今天没有任何东西保证这一点 —— 这正是为什么一个泄漏的 follower 会占着一条会话连接、让进程永远不退出。Effect（那个 TypeScript 库）正是为这道缝提议的：Context.Tag 给端口命名，Layer 提供实现，Scope 把获取到的资源绑到一段生命周期上 —— 于是释放是结构性的，而不是靠记得。这一页最后那个测试要的就是 Layer：把真的换成假的，同一个 conductor 在没有数据库的情况下跑起来。代价是真实的，而且是这个项目特有的。design.md §8 的立场是「不到具体的失败逼上门，不上仪式」，而预先引入一个框架正是那份清单要挡的形状；Effect 还有传染性 —— conductor 一旦返回 Effect，调用它的一切都得跟着。而这个仓库是由 agent 写的，一套陡峭的写法要在此后每一趟运行里重新付费。所以：只在缝上用，不铺满。domain、recipe、actions 仍然是被 Effect 代码调用的普通函数；端口和 conductor 用 Effect；宿主在最外层调 runPromise。这件事值得单独一份 ADR，而不是提案里的一行。

有一行要加个限定。actions 的职责里有「证明它们跑了」，而五个位置中有一个从来没跑过：admit 只被读一下，好把名字写进 GatesResolved，从没有人为它建过流水线。它和 #58 是同一个形状，至今没炸只是因为还没有任何 recipe 在那里声明过动作。今天下午合进来的 gate-audit 已经瞄准了它：第一个在 admit 上放动作的 recipe，会在那个 item 落地之后被告知 —— 它对合进去的东西没有产生任何影响。

顺序

  • 删掉 outbox。 整份提案里最大的一处净减，而且是删除不是搬家。它顺便让 projector 只剩一张目标表。
  • 删掉队列缓存。 #56 和 #57 都是缓存失效的 bug。它们随缓存一起消失。
  • 一种行为，两个宿主。 每个 append 的进程，在它活着的整段时间里都持有一个 projector —— daemon 本来就是，lingtai run 也变成这样。这是把「退出前追平一次」这个特例删掉，而不是在它旁边再加一套机制；#64 就是这样关掉的：事件驱动 projector，谁持有它都一样。同一条日志上跑两个 projector 从此是常态，而它按构造就是安全的 —— apply 幂等，checkpoint 与它的写在同一个事务里推进，所以第二个只会发现没活可干。这一点本来就成立；它从边缘情况变成了设计本身。board 是这条规则唯一够不到的宿主 —— 它的写是 request 级的，所以它 append 之后只能依赖 daemon。这可以接受，前提是它得说出来，而今天它没有：live 那个芯片报的是 SSE 连接是否打开，正是今早那个谎 —— 芯片写着 live，板子冻着。它该报的是投影的 lag 和心跳：落后 7 条，或者没有 daemon。延迟一旦可见，延迟就没问题。
  • 改名与拆分。 store → event-store + projector；env → agent-env + secrets；config → recipe；gates → actions；core → domain。机械操作，而且趁别的都不动时最便宜。
  • 抽出 repo 和 agent。 最大的一步。conductor 声明它需要的接口，两个包提供实现。用注入，不是搬文件。
  • 扩宽 reconcile。 启动时让四件事归位：投影追平、工作树清理、过期 claim 归还、GitHub 向日志说的样子收敛。

判定这件事成没成的那个测试

能不能给 conductor 一个假的 repo、一个假的 agent、一个假的 event-store，在没有数据库的情况下跑完一整趟 —— 产出「它想 append 哪些事件」和「它想做哪些调用」，交给测试去断言？

今天不能，而且 recipe 自己把话说明了：没有 TEST_DATABASE_URL 测试套件就拒绝启动，因为每一个测试都会 append 真实事件。仅这一个包里就有 23 处 append，分布在 6 个文件中。如果搬完之后答案依然是「不能」，那就等于没搬 —— 不管目录列表长成什么样。
