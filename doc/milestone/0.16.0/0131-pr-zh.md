# ADR 0131 讨论稿（中文）：一个 PR 怎么从草稿走到合并

*讨论稿，2026-11-21 起草，2026-11-22 修订。先用中文写，方便讨论和修改；定稿后翻成英文，成为
`doc/decisions/0131-…md`，同时把 0130 的第 5、6 节搬过去。这里标了“新”的规则还没写进任何 ADR。*

## 一、为什么要单独一个 ADR

0130 有 339 行，第 5、6 两节约 170 行，讲的都是 PR：它有哪些状态、每一步做什么、冲突怎么解、CI
怎么看、灵台怎么得知 PR 已合并。0130 本身的主题是“一个项目是 solo 还是 team”，PR 只是 team 模式下
分支和 `main` 之间的那一段。

今天又定了好几条 PR 的规则（CI 绿了之后怎么标 ready、别人往 PR 分支提交怎么办、合回个人分支时
`unknown` 是什么意思），塞进 0130 会更难读。按“一个主题一个 ADR”，PR 单独成一个。

**拆分后：**

| | 0130（solo 还是 team） | 0131（PR 的一生） |
|---|---|---|
| 管什么 | `mode`、`branch.main` / `branch.personal`、取哪些票、票落在哪个分支、票在 tracker 上什么时候关、team 模式不推 `main` | PR 的状态和看板、提交、同步 `main`、冲突、build、推送、CI、标 ready、pr-fix 票和返工、合回个人分支、灵台怎么得知结果、`pr:` 摘要 agent |
| 来自 | 0130 §1–§4、§7 | 0130 §5、§6 搬过来，加上新定的规则 |

0130 的第 5 节缩成一句话指向 0131；其它不动。

## 二、PR 的一生：每一步做什么，失败了去哪里

流程图：[`team-mode/pr-lifecycle.html`](team-mode/pr-lifecycle.html)（2026-11-21 定：ADR 用 mock 图，
不用文字图）。上面一排是 PR 页的状态，下面把 In progress 展开成十步，每一步写出做什么、走不下去去哪里、
返工时做什么。

In progress 的十步：① 冻结个人分支 → ② 合进 main → ③ build → ④ 合进别人的提交 → ⑤ 标题和摘要 →
⑥ 推送 PR 分支 → ⑦ 开草稿 PR → ⑧ CI → ⑨ 补充摘要 → ⑩ 标 ready。

| 步骤 | 走不下去的情况 | 去哪里 |
|---|---|---|
| ② 合进 main | 冲突 | 交给解冲突 agent（0108 §8），轮数按 `attempt.conflictResolutions` 计；用完了 → 等你处理 |
| ③ build | 红，而且这次合进了东西（② 或 ④） | 交给同一个解冲突 agent，轮数共用（新）；用完了 → 等你处理 |
| ③ | 红，但什么都没合进来 | 等你处理：个人分支本身就是坏的，不是同步造成的 |
| ④ 别人的提交（新） | 第一次 Submit | 远端还没有 PR 分支，跳过 |
| ④ | 合并冲突 | 交给同一个解冲突 agent |
| ④ | 对方 force-push（灵台上次推的提交已不在分支历史里） | 不合，等你处理 |
| ④ | PR 分支在远端被删 | 等你处理（和今天一样） |
| ⑤ 标题和摘要（新位置） | 项目被锁（暂停、当天上限、账号额度） | 不写摘要，用第一张票的标题照开，并说明原因 |
| ⑥ 推送 | 推送结果不明 | 看一次远端，绝不盲推第二次（#1125） |
| ⑦ 开草稿 PR | 平台不支持草稿 | 等你处理，不开成 ready 的 PR |
| ⑧ CI | 红 / 30 分钟内没有检查启动 / 超时 | 等你处理，写出失败的检查名 |
| ⑨ 补充摘要（新） | 第一版摘要之后没有新东西 | 跳过，不花钱 |
| ⑩ 标 ready | head 变了 | 不标，回到 ⑧，跟着新 head 的 CI（新）；不进等你处理 |
| 合回个人分支 | 推送结果不明（`unknown`） | 仍然欠着，下次再看（新） |

等你处理时，你可以：再给 agent 三轮；或者自己在 PR 分支上解决后点“再检查一次”（`lingtai pr retry`），
和 0130 §6 一样。

## 三、新定的规则

### 1. 标 ready：先读 head，变了就跟着新 head 的 CI（#1339）

CI 绿了以后，标 ready 之前读一次 PR 当前的 head：
- 还是 CI 检查过的那个提交 → 标 ready，PR 进 In review；
- 变了（有人往 PR 分支推了提交）→ 不标，回到 CI 这一步，等新 head 的 CI 结果。这不进“等你处理”；
- PR 在平台上已经是 ready（返工时）→ 什么都不做，灵台的 PR 页回到 In review。

读 head 和标 ready 之间有几百毫秒的空当，接受它；不做任何“标完再转回草稿”的补救。

### 2. 别人往 PR 分支提交：推送前先 fetch，合进来

采纳评审建议、点 Update branch、直接 push，都是正常的团队协作。GitHub 会在新 head 上重跑 CI，
灵台跟着等就行（第 1 条）。

灵台**自己要推送 PR 分支之前**（第 ⑥ 步，以及 pr-fix 票落地到 PR 分支时），先 fetch 远端的 PR 分支：
- 远端还没有这个分支（第一次 Submit）→ 跳过这一步；
- 远端就是灵台上次推的提交，或者是它的祖先 → 照常推；
- 远端在灵台上次推的提交之上多了别人的提交 → 把它们合进灵台要推的版本，**合完先 build 再推**，和
  同步 `main` 之后一样；
- 合并冲突，或者合完 build 红 → 交给同一个解冲突 agent，和同步 `main` 走同一套（第 7 条）；
- 对方 force-push，灵台上次推的提交已经不在分支历史里 → 不合，等你处理。合进来可能把对方有意删掉的
  提交加回去，这要人来定；
- 分支在远端被删 → 等你处理，和今天一样。

这条取代 0130 §5 里“落地到 PR 分支时，如果别人推过，就拒绝”的写法：pr-fix 票落地时发现分支被别人推过，
也按这条合进来，用同一个函数（2026-11-21 定）。#1341 现在做的是拒绝（`pr-branch-moved`），由开出的新票改掉。

### 3. 按分支名抓不到 PR 的 head 时，按 PR 的 ref 去抓（#1341）

镜像只抓 `refs/heads/*`。有人在 PR 分支上推了提交然后 squash 合并、平台随即删掉分支时，灵台按分支名
永远抓不到最后那个 head，于是证明不了哪些票的代码已经合进去。这时改用 `refs/pull/<n>/head` 去抓
（平台在分支删除后仍保留它），抓到一个临时 ref 里，用完删掉。两种都抓不到，就算“未证实”，不关票。

### 4. 合回个人分支：`unknown` 是“不知道，仍然欠着”（#1312、#1347）

合回发生在**每轮 In progress 走完之后**：第一次 Submit 之后一次，每次 pr-fix 返工之后一次（0130 §6：
“so the person's branch is current after every submit”），不是等 PR 合进 main 之后。合回前先 build，冲突交给
解冲突 agent，和同步 `main` 一样。

- 推送结果说不清时记 `PrMergeBackFailed { why: 'unknown' }`，意思是**不知道推上去没有，仍然欠着**，
  下次再看；不是“什么都没推”。
- 看远端时，如果灵台的合并提交已经在个人分支的历史里（不只是分支顶端），就算合回成功。
- 在个人分支上发现自己的合并提交时，直接记为合回成功，不重新 build。
- git 的报错原因（stderr）带进记录，“等你处理”能说清为什么。

### 5. 其它代码平台：先不做

流程定为“先开草稿 PR，CI 绿了再标 ready”。灵台目前只接了 GitHub；其它平台怎么做（平台适配器负责
草稿和 ready；不支持草稿的平台先只推分支跑 CI，绿了再开 PR）等接入第二个平台时再定。0131 只写一句
“其它平台见 later”。

### 6. 摘要在开 PR 之前写，CI 之后补充（2026-11-22 定）

0130 §5 的顺序是“开草稿 PR → CI → 写标题和摘要”，于是草稿 PR 先用第一张票的标题开出来，CI 跑完才换成
正式的。改成：

- **⑤ 标题和摘要**：在推送和开草稿 PR 之前，由 `pr:` agent 写。草稿 PR 一开出来就是正式的标题和摘要，
  GitHub 的通知和链接预览里也是。摘要不依赖 CI 的结果，所以放在前面不影响任何判断。项目被锁时照旧：
  不写摘要，用第一张票的标题开，并说明原因。返工时不重写，第一版留着。
- **⑨ 补充摘要**：CI 绿了之后、标 ready 之前。只写第一版摘要之后发生的事，没有就跳过、不花钱。第一次
  提交时一般会跳过，它主要在返工时起作用。它补充两样东西，都是灵台已经知道的：
  - 第 ④ 步合进来的别人的提交：谁推的、改了什么；
  - 落地的 pr-fix 票：评审要求改什么（票的正文），怎么改的（落地的提交）。
- **不读 PR 上的评审和评论。** 0130 定过，0.16 不读评审状态和评论（“Review state and comments are not
  read in 0.16”），这一项留在 later，和“PR 页显示评审状态和评论”放在一起，因为两者读的是同一份数据。
  所以讨论完、决定不改的意见，摘要里看不到；只有写成了 pr-fix 票的才有。
- `pr:` agent 每次运行都计入当天上限，和今天一样。

### 7. 合完 build 红了，先交给 agent（2026-11-22 定）

0130 §6 里，合并没冲突但 build 红了，直接等你（“rounds spent, a red build … the PR waits on you”）。这种红
一般是两边各自都对、合在一起才坏，比如 main 改了一个函数的签名，你分支上的新代码还在用旧的。改成：

- **合进了东西之后 build 红**（第 ② 步合了 main，或第 ④ 步合了别人的提交）→ 交给**同一个解冲突 agent**
  （0108 §8 的 `resolveConflict`）：告诉它这次是 build 红，交给它 build 的输出、这次合进来的提交，以及
  你这边相关的票。它做的和解冲突是同一件事：让两边的意图都成立。
- **轮数共用 `attempt.conflictResolutions`**，不另开一份预算。它的修改照样要过 build 和 review，没过就算
  下一轮；轮数用完 → 等你处理。spend 计入当天上限。
- **什么都没合进来就红** → 等你处理，和今天一样：个人分支本身就是坏的，不是同步造成的。

### 8. 返工：从第 ② 步重新走（2026-11-22 定）

团队在平台上提意见时，PR 留在 In review：灵台不读评论，也不知道有意见。你开一张 `lingtai:pr-fix` 票，
这张票在做的时候 PR 也还在 In review。它先走一遍普通的票流程（从 PR 分支切出、实现、build、review），
然后由合并通道落地到 PR 分支并推上去（推之前按第 2 条合进别人的提交）。落地之后 PR 回到 In progress，
**从第 ② 步重新走**，因为 PR 开着的这段时间，别人的 PR 可能已经合进了 main；不追上 main，就会在平台上
合并时才发现冲突，或者合完 main 才变红。

| 步骤 | 返工时 |
|---|---|
| ① 冻结 | 不做。PR 的内容就是 PR 分支本身，这段时间落在个人分支上的新票不进这个 PR |
| ② 合进 main | 做。main 已经是祖先就跳过 |
| ③ build | 做。红了按第 7 条 |
| ④ 别人的提交 | 做。这时远端已经有 PR 分支，这一步才真正起作用 |
| ⑤ 标题和摘要 | 不重写 |
| ⑥ 推送 | ② 或 ④ 合进了东西才推；没有就没有新内容可推 |
| ⑦ 开草稿 PR | 跳过。PR 已经开着，先按分支找到它，绝不开第二个 |
| ⑧ CI | 做，看新 head 上的检查 |
| ⑨ 补充摘要 | 做：把这张 pr-fix 票和别人推的提交补进去 |
| ⑩ 标 ready | 平台上已经是 ready，什么都不做；PR 页回到 In review |

**返工期间不把 PR 退回草稿。** 平台上的 PR 一直是 ready，灵台的 PR 页显示 In progress。改动推上去后平台
会在新 head 上重跑 CI，团队看得到；来回切换草稿只会给评审人多发通知。

## 四、从 0130 原样搬过来的

不改内容，只换位置：
- PR 的五个状态和 PR 看板；“PR 是一批工作的发布”。
- 只有人能提交；灵台从不自己提交、从不合并。（In progress 的步骤顺序按第二节，第 6、8 条改了它。）
- CI：草稿 PR、`checks: read` 和 `statuses: read` 两个权限、没有 workflow 就没有 CI 这一步、红了由人在
  平台上重跑、`CiProvider` 接口、`pr.ci` 配置。
- `lingtai:pr-fix` 票：排在所有 kind 前面、PR 打开时从 PR 分支切出并落在 PR 分支上、之后合回个人分支一次。
  （落地后怎么走按第 8 条。）
- PR 描述从日志生成，摘要由 `pr:` agent 写、人可以改；关闭不合并回到 Draft；一次只开一个 PR、工作
  不停；代码平台；中途重启；solo 没有 PR 页。
- PR 的两个编号；灵台怎么得知合并、关闭（git 可达，或平台报告；巡检计时器）；webhook 只是加速。
- `pr:` 摘要 agent 的配置块（它什么时候跑按第 6 条）。
- 0130 §6：只在提交和返工时同步 `main`、在合并通道里合、合完先 build、冲突交给 agent、解不了就
  等你处理、评审意见进 PR 名下的 backlog。（合完 build 红按第 7 条。）

## 五、已定（原待定）

1. **pr-fix 票落地时发现 PR 分支被别人推过：也自动合进来**，和推送用同一个“合进别人的提交”的函数；
   落地那一步因此也能调用解冲突 agent 和 build。
2. **流程图用 mock 图**：`team-mode/pr-lifecycle.html`。
3. **摘要挪到开草稿 PR 之前，CI 之后补充**（第三节第 6 条，2026-11-22）。
4. **合完 build 红先交给解冲突 agent，轮数共用**（第三节第 7 条，2026-11-22）。
5. **返工从第 ② 步重新走，期间不退回草稿**（第三节第 8 条，2026-11-22）。
6. **定稿后要开或要改的票**：
   - 新开一张：推送前和 pr-fix 落地前合进别人的提交（第 2 条），被 #1339 和 #1341 挡着；
   - 新开一张：合完 build 红交给解冲突 agent（第 7 条），被 #1313 挡着；
   - 改 #1318 的正文：⑤ 在开 PR 之前写，⑨ 在 CI 之后补充，返工时不重写（第 6 条）。

   第 1、3、4 条已经在 #1339、#1341、#1347 里做了或正在做；第 8 条的返工顺序由 #1339 的 IN_PROGRESS_STEPS
   和 ⑩ 的“已是 ready 就不做”（`agent/1339:packages/conductor/src/pr.ts:523`）承担。
