# 0.16 — more agents, through ACP

**Status** planning · 2026-11-18, decided after experiment 019 on 2026-11-19 ·
what 0.16.0 is to contain, as the operator agreed it in discussion. Not yet cut
into tickets; DeepSeek Harness's E7 is still to run.

## What 0.16.0 is

*Lingtai runs agents other than Claude Code and Codex, through the Agent
Client Protocol.* The operator narrowed the milestone on 2026-11-18 to one main
part, an acceptance run, and a part done only if there is time:

| Part | Plan |
|---|---|
| **An ACP runtime** | The main line. One adapter in which Lingtai is the ACP client, accepted on GitHub Copilot CLI. Any place that runs an agent may name it, as far as its capabilities reach (below) |
| **A GitLab remote with local tickets, as an acceptance run** | No feature of its own: with `source.tickets: db` the remote's host does not matter to the pass. One run on a clean machine with a GitLab remote, and the documentation that run proves |
| **Ticket sources: the common groundwork, then Linear** (decided 2026-11-20) | A ticket reference becomes a stable id and a display key, the GitHub-only verbs Lingtai uses move behind `Tickets`, each tracker declares what it can do, Markdown stays Lingtai's own format, `source` opens; then a Linear adapter. Measured first ([020](../../experiments/020-linear-measured.md)). The queue's *take only my tickets* works on every source. Jira moves to a later milestone |
| **Solo and team** (decided 2026-11-20) | A project is `solo` or `team`, `team` the default: a team takes only tickets assigned to the person and lands on their personal branch, never `main` (below) |

The ACP runtime is cut (#1298–#1305); the ticket-source part is cut after its experiments.

## Why ACP, and not one more agent

Surveyed 2026-11-18. Claude Code leads every survey and, with Codex, covers
most users already; OpenCode is 2.5–13% depending on the survey; Cursor and
GitHub Copilot are larger (13–42% each), Gemini CLI after them
([JetBrains via DEV](https://dev.to/jamilxt/claude-code-overtakes-github-copilot-what-jetbrains-survey-of-15000-developers-says-about-ai-3nhc),
[Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/ai-tooling-2026),
[First Page Sage](https://firstpagesage.com/seo-blog/ai-coding-assistant-market-share/)).

The ACP agent list includes OpenCode, Cursor CLI, GitHub Copilot CLI, Gemini
CLI, goose, Kiro CLI, Kimi CLI, Qwen Code, Cline and Junie
([agentclientprotocol.com/get-started/agents](https://agentclientprotocol.com/get-started/agents)).
One adapter therefore covers OpenCode and the larger agents beside it, and
every agent Vibe Kanban's users named, each as a profile of it (question 5 below)
([vibe-kanban-demand-vs-lingtai.md](vibe-kanban-demand-vs-lingtai.md)). An
OpenCode adapter of its own would buy nothing ACP does not, and is not built.

Claude Code and Codex keep their own adapters: they carry the hooks, the
sandbox wiring and the output schema that `review` and the judges need.

**0.16.0 adds ACP and nothing else** (2026-11-18). Claude Code and Codex keep
the adapters they have; every other agent, DeepSeek Harness (`dsh`) included,
is reached through the one ACP adapter. `dsh` is DeepSeek's own CLI and serves
ACP itself (`dsh --profile acp`,
[CLI README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md));
it matters for the Chinese market, where DeepSeek is what many people code
with, so it is one of the agents the experiments run. No agent gets an
adapter of its own in this milestone.

DeepSeek has no subscription: the API is prepaid and billed per token, in
yuan, at half price outside Beijing's weekday peak hours (9–12, 14–18), with
cache hits priced apart
([pricing](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)). Two
consequences: the rate card is dollars per million tokens by model, mode and
date (`RateRow`, `packages/domain/src/rate-card.ts:22`), so a DeepSeek estimate
needs a currency and a time of day it does not carry; and a DeepSeek account
does not hit a usage window as Claude's and ChatGPT's plans do, it runs out of
balance — an environment wait, not a lock that lifts by itself (0126).

## The ACP runtime: decided

| Decision | Why |
|---|---|
| **Where an ACP agent may run is decided by what the place needs, not by a list of steps** (2026-11-18). Steps that edit with full tools and answer in prose (`design`, `implement`, a fix round) need nothing ACP lacks. A place that wants a structured answer (`review`, a judge, triage) takes one from the agent's prose, validated, as triage already does on the route that cannot carry a schema (`apps/cli/src/triage.ts:1059`), where `review` today always sends one (`packages/actions/src/agent-action.ts:1010`). A place that needs an agent with no tools (a discussion, `DiscussAgent`, `packages/recipe/src/recipe.ts:2892`) takes ACP only if E2 shows every tool call can be refused. A recipe that names ACP where its capability does not reach is refused by name when it resolves | One rule for every plugin that runs an agent, held by the runtime's declared capabilities (`RuntimeCapabilities`, `packages/agent/src/runtime.ts:39`) rather than by step names |
| **Lingtai does not log anyone in.** The agent runs as the person, on the login its own CLI already holds, as Claude Code and Codex do | ACP leaves login to the agent: `authMethods` in `initialize`, and a `terminal` method is run outside the connection ([v1 authentication](https://agentclientprotocol.com/protocol/v1/authentication)) |
| An agent that answers `auth_required` is an **environment** wait, naming the agent's own login command; `lingtai doctor` and the setup page check the login before a run | 0108: a person is asked only for an environment only they can repair |
| **An ACP run Lingtai cannot price is shown unpriced, and the dollar ceilings do not hold it** (decided 2026-11-19). Neither agent sends `cost`, so `costUsd` is `null`. The adapter maps each agent's tokens onto `TokenCounts` (`packages/domain/src/spend.ts:18`) by that agent's own meaning — Copilot's `inputTokens` include the cached ones, so `fresh` is input less cache read and write; Antigravity's do not; both count thought tokens inside `output`, so `reasoning` is not added. The model is recorded where the agent names it (Antigravity's model option) and absent where it does not (Copilot over ACP). A run with no model or no rate row is *unpriced* on the board and `/spend`, tokens shown; `run.usd` and the day's ceiling do not count it, and turns and wall time are what bound it. `lingtai doctor` and the recipe's resolve say so for each agent that will run unpriced. A person who adds a rate row gets an estimate | Copilot over ACP never names its model ([019](../../experiments/019-acp-agents-measured.md) E1, E9), and the rate card has no Gemini row (`packages/domain/src/rate-card.ts:44`); requiring a price would leave Copilot, the acceptance agent, unusable. Both run on subscriptions, so an estimate is what the tokens would cost on the API, never what was billed |
| **Turns and wall time are counted by Lingtai** as the client, and a run past either is ended with `session/cancel` | ACP has neither limit; `enforces` (`runtime.ts:66`) is declared, not assumed (#89) |
| **Antigravity does not run sandboxed in 0.16.0** (2026-11-19). Where the sandbox is on but not required, an Antigravity run is unsandboxed, the run records that it was, and `lingtai doctor` says so by name for every project whose recipe names it. Where the recipe says `sandbox.required: true`, a recipe naming Antigravity is **refused by name when it resolves**, saying it cannot run sandboxed in this release and to set `required: false` or name another agent | Inside srt it needs a local port bound and the keychain read ([019](../../experiments/019-acp-agents-measured.md) E10), and the keychain is what 0127 §12 denies; the policy is not relaxed for one agent |
| Acceptance on **GitHub Copilot CLI** (decided 2026-11-19), on this repository with its sandbox on (`sandbox.enabled: true`): one real ticket claimed, implemented by Copilot over ACP inside srt, reviewed by Claude Code or Codex, and landed. Antigravity is not accepted separately | The two largest agents on the list that are not Claude Code or Codex and that the operator can run. Antigravity CLI in place of Gemini CLI since 2026-11-19: Google replaced Gemini CLI with it for unpaid and Google One users on 2026-06-18, Homebrew disables `gemini-cli` on 2026-12-18, and `agy acp` serves ACP since 1.5.0 ([docs](https://antigravity.google/docs/cli/acp/)) |

## The ACP runtime: to discuss after the experiments

1. **A null cost against the ceiling and `run.usd`**, from E1. Decided
   2026-11-19: estimated where the model and a rate row are known, otherwise
   unpriced and bounded by turns and wall time (the table above).
2. **The sandbox's hosts per agent**, from E5, and **its login inside the
   sandbox**, from E10. Decided 2026-11-19, for Copilot (the only ACP agent
   sandboxed in 0.16.0): **added by its runtime, as Codex's `~/.codex` is**
   (`CallerAdditions`, `packages/sandbox/src/policy.ts:37`) — a Copilot run, and
   no other, reaches `*.githubcopilot.com` and may write `~/.copilot`; the
   person declares nothing. `telemetry.*.githubcopilot.com` joins the known
   telemetry hosts (0127 §17) and stays refused. The wildcard covers the
   business and enterprise hosts E5 did not measure. Not in `BUILT_IN_DOMAINS`,
   which every run gets. The login is `COPILOT_GITHUB_TOKEN` in the run's
   environment, since `~/.config/gh` is denied (0127 §5) — where that token comes
   from is question 3.
3. **Where a sandboxed Copilot run's token comes from**, raised by question 2.
   Decided 2026-11-19: **a token of its own, as Claude Code's is** (0127 §8).
   The person makes a fine-grained personal access token, owned by their own
   account, with the one account permission *Copilot Requests*, and sets it as
   `copilot.github_token` in `~/.lingtai/config.yml` or exports
   `LINGTAI_COPILOT_GITHUB_TOKEN`; Lingtai reads it redacted and the run gets it
   as `COPILOT_GITHUB_TOKEN`. It can call Copilot and reach no repository. Never
   `gh auth token`: that would hand the run the login 0127 §5 denies.
   `lingtai doctor` checks it is set, and names a classic `ghp_` token, which
   Copilot ignores without a word
   ([GitHub's docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)).
4. **Permission requests and failing closed**, from E2 and E3. Decided
   2026-11-19: **recorded, never mediated**, as Claude Code's and Codex's hooks
   are — `canFailClosed` is the record, not a refusal (*"Not mediation — the hook
   refuses nothing it is not forced to (ADR 0016 §6)"*,
   `packages/agent/src/runtime.ts:49`), and srt is the boundary. The agent stays
   in its default mode, never an auto mode, so every request reaches Lingtai;
   each is answered *allow once* and recorded as asked and allowed. Every tool
   call arrives as `tool_call` (E2), which is the trace. The ACP runtime declares
   `canFailClosed: true`, on E3's evidence: Lingtai is the client, and an agent
   whose client is gone exits within two seconds; `canRewriteToolCall: false`.
   Refusing calls by rule (a `git push --force`, say) is the open
   implement-git-rules topic, not 0.16.0.
5. **`RuntimeId`**: one `acp` value with the agent's command in the recipe,
   or one value per agent. It names the runtime on `RunSpent`, keys the
   account and its usage-limit lock (`acct-{runtime}`, 0126), picks the login
   probe (`AUTH_PROBES`, `packages/agent/src/auth.ts:315`) and is what a
   recipe's step names. Decided 2026-11-19: **one value per agent** —
   `copilot`, `antigravity`, later `deepseek-harness` — each a profile of the
   one ACP adapter carrying what 019 found differs: the command and its mode id,
   how its tokens map onto `TokenCounts`, how a model is chosen, its login and
   `lingtai doctor` check, whether it can be sandboxed and its hosts, and how its
   process is ended. A recipe says `agent: copilot`; each agent's usage-limit
   lock is its own (`acct-copilot`, 0126). A new agent is a profile in code. No
   generic `acp` value in 0.16.0: an agent Lingtai has no profile for could be
   neither priced, sandboxed nor checked.
6. **What the adapter is built on**, from E12. Decided 2026-11-19: **the
   official `@agentclientprotocol/sdk`, pinned to 2.8.x, stable v1**, behind an
   Effect at Lingtai's edge (`Effect.tryPromise`, as CLAUDE.md's ratchet section
   asks of a library's promise). Its 2.0.0 rewrote the client API a month
   before (`ClientSideConnection` removed), so the pin is what keeps the next
   rewrite a choice. Raw messages are recorded through a `TransformStream` on
   each side of the stream it is handed. Two things are Lingtai's own, learned
   from acpx: the agent is spawned as its own process group and the group is
   killed at a limit (Antigravity's child outlives `session/cancel`, E4), and
   an outcome is classified — refused, out of time, or *ended `end_turn` but
   failed* (019's finding 4) — rather than read from `stopReason` alone. Not
   acpx: it spawns the agent itself, keeps a detached process in session mode,
   refuses `--model` for Copilot, and is on the SDK's pre-2.0 1.9.0.
7. **0129's Attempt owner**: built first only if the runtime adds new event
   types to `pass-` streams; if it only adds a `RuntimeId` value, it stays out.
   Decided 2026-11-19: **it stays out.** Every record the runtime writes has a
   type already: a tool call that changes a file is `RunTouchedFile` and the
   calls are counted as the hook's are (`packages/agent/src/hook-socket.ts:259`),
   spend is `RunSpent` with `costUsd: null`, the agents are two `RuntimeId`
   values. The one change to an existing type is additive: an Antigravity run's
   `SandboxBoundaryRecorded` is `unsandboxed`, and its `reason` gains a third
   value beside `off by choice` and `degraded` for *this runtime cannot run
   sandboxed* (`packages/domain/src/events.ts:1031`); every stored payload still
   parses.

## Ticket sources: the groundwork, then Linear

Decided 2026-11-20, from a survey of the trackers' APIs against what Lingtai
asks of one (the results are in [tracker-experiments.md](tracker-experiments.md)).

**Who uses what.** Stack Overflow's 2025 survey: Jira 52% of professional
developers, GitLab 37% and Azure DevOps 19% (both counted as whole platforms),
Linear 4% — but Linear's new-company adoption rose 67% in a year while Jira's
fell 32% ([survey](https://survey.stackoverflow.co/2025/technology),
[Bloomberry](https://bloomberry.com/blog/the-data-on-jira-vs-linear-whos-winning-new-customers/)).
Linear is first because it is the least work and the measurement is cheap;
Jira, the most used, is the hardest — its bodies are ADF with no official
Markdown converter, closing is a per-workflow transition, and JQL cannot ask
for unblocked tickets — and moves to a later milestone, measured first in the
same way.

**What Lingtai asks of a tracker today.**

- The ten verbs of `Tickets` (`packages/conductor/src/ticket-store.ts:76`),
  every reference a `number` (`getIssue(number)`, `comment(issue: number)`, …);
  34 source files take a reference as `number`; branch names `agent/<n>` are
  built in three places; a split child's `number` is in an event
  (`packages/domain/src/events.ts:428`). Most events already carry references as
  strings (`externalRef`, `issue: z.string()`).
- Verbs outside the interface that only GitHub answers: open-blocker counts on
  the listing and `addBlockedBy` (`packages/conductor/src/split-ticket.ts`),
  `addLabels`/`removeLabel`, a split child's milestone and assignees
  (`split-ticket.ts:116`). A webhook is optional: a five-minute sweep is the
  fallback (`packages/daemon/src/work-loop.ts:162`).
- `TicketSource = z.enum(['github', 'db'])` (`packages/recipe/src/recipe.ts:1112`);
  0109's *Not built yet* still lists the closed `source` enum.

**The groundwork**, whatever the tracker:

1. A reference is a string, and two of them: a **stable id** (Linear's UUID,
   Jira's numeric id) and a **display key** (ENG-123, PROJ-123), because both
   trackers change the key when an issue moves.
2. Blockers (read the open count, add a link), one label added or removed, and a
   child's placement move behind `Tickets`.
3. Each tracker declares its capabilities, as a runtime does: whether *replace
   the body only if unchanged* is exact, best-effort or absent (Jira none;
   GitHub and Linear best-effort, Linear's by `updatedAt`; `db` exact), whether it has blockers,
   whether it has assignees,
   whether a close carries *not planned*. Lingtai degrades or refuses by that,
   and `lingtai doctor` says so.
4. Markdown is Lingtai's format; an adapter converts at its edge.
5. `source` is open; one contract suite holds every adapter, as it holds
   `memoryTickets` and `dbTickets`.

6. Lingtai's own readers of a body accept the equivalent Markdown another
   tracker writes back: any tracker may re-serialise, and Linear does.
7. The order of the queue is Lingtai's: sorted on the client, never the page
   order a tracker returns.

**Decided by measurement** — [experiment 020](../../experiments/020-linear-measured.md),
2026-11-20. Every verb Lingtai needs works on Linear; what the adapter does by
name:

| Found | So |
|---|---|
| Linear rewrites Markdown (`-`→`*`, `\|--\|` rules, `](<url>)`, emphasis split at code); nothing lost, and its own form is a fixed point | The adapter keeps Linear's returned body as *the body as last read* and compares against that. The board's four-row table (`ticketOpening`, `apps/board/src/app/standing.tsx:678`) accepts `--` rules and `<url>` links — groundwork 6 |
| Label names are unique case-insensitively, and `Bug`/`Feature` exist from the start | Match by name ignoring case and reuse; create only a label nothing matches, at workspace level |
| Several states may share a type | Close done by type `completed`, not planned by `canceled`, the lowest `position` of each |
| `hasBlockedByRelations` and the open count behave as documented; a link made twice is one | The listing filters on it; the count comes from sized `inverseRelations` |
| `updatedAt` moves on body and label edits, not on comments; a check-then-write window of ~200 ms | *Replace if unchanged* is declared best-effort |
| A team move changes `HCZ-17` to `LTW-1`; the UUID and the old key both still resolve | The UUID is the stable id, the identifier the display key |
| `orderBy: createdAt` is newest-first with `first` and `last`; equal timestamps come back in any order | Sort by `createdAt`, then number, on the client — groundwork 7 |
| A sweep costs 38 complexity points, 0.015% of the hourly budget at one every five minutes | The five-minute sweep is enough; webhooks stay optional |
| `@linear/sdk`'s objects load lazily (10 extra requests for 5 issues) and its major moves weekly | Raw GraphQL with zod-checked responses |
| One assignee per issue, a user id; the key's own user is `viewer`, and `isMe` filters server-side | *Take only my tickets* on Linear needs no login written (below) |

Not measured: OAuth client credentials (no app), webhooks (no public address),
a checkbox ticked in Linear's UI. None changes a row above.

### Take only my tickets

Asked for 2026-11-20: a person who points Lingtai at a shared tracker wants it
to take their own tickets and leave everyone else's.

**It exists for GitHub.** `queue:`'s `assignee` is `{ login, take }`, `take` one
of `mine`, `unassigned`, `both` (`packages/recipe/src/recipe.ts:1162`,
`AssigneeRule` `:1172`; written as `runtime.assignee`, read through
`assigneeOf`, `packages/recipe/src/settings.ts:406`). `assigneeSkip`
(`packages/conductor/src/discover.ts:284`) applies it to the logins GitHub's
listing already carries (`packages/github/src/client.ts:576`), passing a ticket
over as `assigned-elsewhere`, `unassigned` or `assigned-to-me`, and `lingtai
add`'s summary prints the rule with the login (`describeAssignee`,
`packages/conductor/src/filter.ts:566`). `take: mine` without a login is refused
when the recipe resolves, because it would match nothing.

**What is missing is every other source.**

- `dbTickets` answers `assignees: []` for every ticket — *this store tracks no
  assignee* (`packages/conductor/src/db-tickets.ts:27`, `:213`). On a `db`
  project `take: mine` is an empty queue that reads as *nothing to do*, the very
  silence the login refusal exists to prevent.
- `login` is a GitHub word. Linear's assignee is a user id, one per issue, and
  *me* is the API key's own user (`viewer`, L11) — nothing to write, and the
  query filters by it. Jira's will be an account id.

**So, in the groundwork:** the listing carries assignees as the tracker's own
user ids; the adapter answers *who am I* — GitHub from the login the recipe
names (Lingtai acts as a GitHub App, which is nobody's assignee), Linear from
`viewer`; a source that tracks no assignee declares it (groundwork 3), and
`take: mine` or `take: unassigned` on it is refused by name when the recipe
resolves, never an empty queue.

Decided 2026-11-20:

1. **A `db` project refuses it.** `dbTickets` declares that it tracks no
   assignee; `take: mine` or `take: unassigned` on a `db` project is refused by
   name when the recipe resolves. Local tickets gain no assignee in 0.16.
2. **On Linear, *me* is the key's own user**, always: nothing is written, the
   query filters on `isMe`. Taking another person's tickets is that person's key.
3. **The board's Queued column shows only what this machine would take** — the
   same rule the queue applies, so the column and the queue never disagree.

## Solo and team

Decided 2026-11-20. Lingtai's defaults are a single person's: it takes every
ticket with a kind label and none of the hold labels, and lands on the base
unattended. On a shared tracker that is one person's tool imposing a duty on
eleven others: a teammate's bug is taken, branched, paid for and merged before
they hear of it, and the only way to stop it is a label *they* must remember.
A team needs the failure that costs nothing — a ticket not taken — so a project
is one of two modes, and `lingtai add` asks which, **defaulting to `team`**.

| | `solo` (today's behaviour) | `team` |
|---|---|---|
| Takes | every ticket with a kind label, none of the hold labels | the same, **assigned to me** |
| Hands work to the agent | writing the ticket; `lingtai:hold` keeps it off | assigning it to yourself; `lingtai:hold` pauses one |
| `take` | `all` | `mine` |
| Lands on | `branch.main` | `branch.personal`, never `branch.main` |
| A landed ticket | closed | open, labelled `lingtai:landed`; closed by the tracker when the person's PR reaches `main` |

Assignment is the trigger because a team already uses it to say *this is mine*:
nothing new to learn, a colleague sees at once that the ticket is taken, and two
people's Lingtai never take the same one. GitHub's Copilot coding agent and
Linear's agents are started the same way.

**Two branches, named in the recipe.** Today one `base` is both where a branch
is cut and where it lands (`packages/recipe/src/recipe.ts:916`). In team mode
those are two branches, and the recipe says both:

```yaml
mode: team
branch:
  main: main                # the team's trunk — Lingtai syncs from it and never pushes to it
  personal: steven/lingtai  # Lingtai cuts, lands and pushes here
```

`mode: solo` writes `branch.main` alone and lands there. `branch` replaces
`base` outright. In team mode **Lingtai never pushes `branch.main`** — a
guarantee a test holds — and a `personal` equal to `main` is refused by name.

**The person's PR is the unit the team reviews.** Lingtai lands each ticket on
the personal branch as its own merge commit (the lane is `git merge --no-ff`,
`recipe.ts:947`); the person reviews their branch and opens one PR to `main`
holding several tickets, with `Closes #…` for each. No PR storm; the team reviews
a colleague's PR as it always has. Merged into `main` with a merge commit, never
squashed, so one ticket the team refuses is one `git revert`. A ticket that needs
its own PR is that merge commit picked onto a branch of its own; Lingtai needs
nothing for it.

**Names.** Lingtai's own labels take one prefix, so a team's tracker can tell
them from its own and from other agents': `agent:hold` → `lingtai:hold`,
`agent:followup` → `lingtai:followup` (`HOLD`, `apps/cli/src/backlog.ts:34`),
beside `lingtai:working` and `lingtai:queued`; and `lingtai:landed` is new.
`take: both` becomes `take: all`. Renamed outright, this repository's tickets and
recipe migrated with them.

Decided 2026-11-20:

1. **The personal branch is kept current by Lingtai.** Before each claim it
   merges `origin/<branch.main>` into `branch.personal` and pushes; a conflict
   stops for a person and is never given to an agent, and nothing is claimed
   until it is resolved.
2. **`lingtai add` creates the personal branch** from `origin/<branch.main>`
   and pushes it, after asking, when it does not exist.
3. **The PR draft, and `lingtai pr`, are in 0.16.**

**The PR draft.** Each ticket landed on `branch.personal` joins the project's
open draft: its number and title, what changed, its merge commit, its spend.
The draft is in Lingtai's own log and on the board, never on the tracker — the
team sees no half-made PR and its CI does not run on every landing. The person
reads it on the board's draft page or with `lingtai pr`, and submits it with a
button there or with `lingtai pr submit`:

- **Submitting freezes it.** The personal branch at that commit is pushed as a
  branch of its own (`lingtai/pr/<n>`) and the PR opens from that to
  `branch.main`, so a ticket landed while the team reviews goes into the next
  draft and never into the PR under review. The personal branch carries on; the
  PR's commits come back to it through the sync once it reaches `main`.
- **The description**: the tickets with `Closes #…`, each one's merge commit and
  spend, generated from the log — exact and free; and an opening summary an agent
  writes, which the person may edit before submitting (one paid run per PR).
- **Taking a ticket out** before submitting reverts its merge commit on the
  personal branch and reopens it, so the branch and the draft never disagree.
- Lingtai opens the PR and never merges it.
