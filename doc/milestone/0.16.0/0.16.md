# 0.16 — more agents, through ACP

**Status** planning · 2026-11-18 · what 0.16.0 is to contain, as the operator
agreed it in discussion. Not yet cut into tickets.

## What 0.16.0 is

*Lingtai runs agents other than Claude Code and Codex, through the Agent
Client Protocol.* The operator narrowed the milestone on 2026-11-18 to one main
part, an acceptance run, and a part done only if there is time:

| Part | Plan |
|---|---|
| **An ACP runtime** | The main line. One adapter in which Lingtai is the ACP client, accepted on GitHub Copilot CLI or Gemini CLI. Any place that runs an agent may name it, as far as its capabilities reach (below) |
| **A GitLab remote with local tickets, as an acceptance run** | No feature of its own: with `source.tickets: db` the remote's host does not matter to the pass. One run on a clean machine with a GitLab remote, and the documentation that run proves |
| **Linear as a ticket source** (if time allows) | Ticket references become strings end to end, then a Linear adapter behind `Tickets`. Moved out of 0.16.0 rather than squeezed in |

About 10–13 tickets for the first two parts; Linear adds 6–9.

## Why ACP, and not one more agent

Surveyed 2026-11-18. Claude Code leads every survey and, with Codex, covers
most users already; OpenCode is 2.5–13% depending on the survey; Cursor and
GitHub Copilot are larger (13–42% each), Gemini CLI after them
([JetBrains via DEV](https://dev.to/jamilxt/claude-code-overtakes-github-copilot-what-jetbrains-survey-of-15000-developers-says-about-ai-3nhc),
[Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/ai-tooling-2026),
[First Page Sage](https://firstpagesage.com/seo-blog/ai-coding-assistant-market-share/)).

The ACP agent list includes OpenCode, Cursor CLI, GitHub Copilot CLI, Gemini
CLI, goose, Kiro CLI, Kimi CLI, Qwen Code, Cline and Junie
([agentclientprotocol.com/get-started/agents](https://agentclientprotocol.com/get-started/agents)).
One adapter therefore covers OpenCode and the larger agents beside it, and
every agent Vibe Kanban's users named
([vibe-kanban-demand-vs-lingtai.md](vibe-kanban-demand-vs-lingtai.md)). An
OpenCode adapter of its own would buy nothing ACP does not, and is not built.

Claude Code and Codex keep their own adapters: they carry the hooks, the
sandbox wiring and the output schema that `review` and the judges need.

**0.16.0 adds ACP and nothing else** (2026-11-18). Claude Code and Codex keep
the adapters they have; every other agent, DeepSeek Harness (`dsh`) included,
is reached through the one ACP adapter. `dsh` is DeepSeek's own CLI and serves
ACP itself (`dsh --profile acp`,
[CLI README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md));
it matters for the Chinese market, where DeepSeek is what many people code
with, so it is one of the agents the experiments run. No agent gets an
adapter of its own in this milestone.

DeepSeek has no subscription: the API is prepaid and billed per token, in
yuan, at half price outside Beijing's weekday peak hours (9–12, 14–18), with
cache hits priced apart
([pricing](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)). Two
consequences: the rate card is dollars per million tokens by model, mode and
date (`RateRow`, `packages/domain/src/rate-card.ts:22`), so a DeepSeek estimate
needs a currency and a time of day it does not carry; and a DeepSeek account
does not hit a usage window as Claude's and ChatGPT's plans do, it runs out of
balance — an environment wait, not a lock that lifts by itself (0126).

## The ACP runtime: decided

| Decision | Why |
|---|---|
| **Where an ACP agent may run is decided by what the place needs, not by a list of steps** (2026-11-18). Steps that edit with full tools and answer in prose (`design`, `implement`, a fix round) need nothing ACP lacks. A place that wants a structured answer (`review`, a judge, triage) takes one from the agent's prose, validated, as triage already does on the route that cannot carry a schema (`apps/cli/src/triage.ts:1059`), where `review` today always sends one (`packages/actions/src/agent-action.ts:1010`). A place that needs an agent with no tools (a discussion, `DiscussAgent`, `packages/recipe/src/recipe.ts:2892`) takes ACP only if E2 shows every tool call can be refused. A recipe that names ACP where its capability does not reach is refused by name when it resolves | One rule for every plugin that runs an agent, held by the runtime's declared capabilities (`RuntimeCapabilities`, `packages/agent/src/runtime.ts:39`) rather than by step names |
| **Lingtai does not log anyone in.** The agent runs as the person, on the login its own CLI already holds, as Claude Code and Codex do | ACP leaves login to the agent: `authMethods` in `initialize`, and a `terminal` method is run outside the connection ([v1 authentication](https://agentclientprotocol.com/protocol/v1/authentication)) |
| An agent that answers `auth_required` is an **environment** wait, naming the agent's own login command; `lingtai doctor` and the setup page check the login before a run | 0108: a person is asked only for an environment only they can repair |
| **Turns and wall time are counted by Lingtai** as the client, and a run past either is ended with `session/cancel` | ACP has neither limit; `enforces` (`runtime.ts:66`) is declared, not assumed (#89) |
| **Cost is what the agent reports, or null.** `usage_update`'s cumulative `cost` is stable since 2026-06-05 but optional to send, and Cursor's agent does not send it | `RunSpent.costUsd` is already required and nullable (`packages/domain/src/events.ts:1098`, 0110 §4): an ACP run writes `null` rather than a guess, and never zero |
| Acceptance on **GitHub Copilot CLI or Gemini CLI**: one real ticket claimed, implemented by the ACP agent, reviewed by Claude Code or Codex, and landed | The two largest agents on the list that are not Claude Code or Codex and that the operator can run |

## The ACP runtime: measured before it is discussed

Decided 2026-11-18: before the questions below are discussed, and before any
ticket, one round of experiments on GitHub Copilot CLI, Gemini CLI and DeepSeek
Harness as ACP agents, driven by a throwaway client. Each question is answered by what the
agents did, not by the spec. The procedure is [acp-experiments.md](acp-experiments.md); the results are written up as an experiment in `doc/experiments/`.

| # | Measure | Why it matters |
|---|---|---|
| E1 | **What each agent reports about spend**: `usage_update` with `cost`, with `used`/`size` only, or nothing; whether the `session/prompt` result carries tokens; on one run, the numbers set beside the vendor's own bill | A run the agent did not price is estimated from tokens on the rate card (0110); with no tokens either there is nothing to estimate from, and the ceiling's answer for that case is decided from this |
| E2 | **Which tool calls each agent asks permission for** (`session/request_permission`), in its default mode and in its auto-approve mode; whether every tool call also arrives as a `tool_call` update | Whether Lingtai can refuse a call and keep the run's trace from the protocol alone, in place of the hook Claude Code and Codex carry (`canFailClosed`) |
| E3 | **What happens when the client goes away mid-run**: the stdio closed, the client killed | The ACP equivalent of *a hook that cannot reach the conductor must stop the run* |
| E4 | **`session/cancel`**: whether the agent stops at once and what it leaves in the worktree | Turns and wall time are Lingtai's to enforce |
| E5 | **The hosts and files each agent touches** under sandbox-runtime with an empty allowlist: which model and login hosts it is refused, and which config directories it writes | What a per-agent entry in the sandbox needs |
| E7 | **DeepSeek Harness over ACP** (`dsh --profile acp`): E1–E6 on it, and in particular whether it passes the API's token counts, cache hits apart, so a run can be estimated | DeepSeek reports no money of its own, and its account ends at a balance, not a window |
| E6 | **Not logged in**: what `initialize` advertises in `authMethods`, and what error a prompt gets | The environment wait's wording and `lingtai doctor`'s check |
| E8 | **A structured answer without a schema**: `review`'s and triage's answer asked for in the prompt, on each agent, enough times to count how often the prose parses | Whether `review`, judges and triage may name an ACP agent, and whether one re-ask is enough |
| E9 | **Choosing the model**: whether the client can pick the agent's model over ACP, or only the agent's own configuration can | What a recipe's `model:` means for an ACP agent |
| E10 | **Whether the agent works inside srt at all**, under Lingtai's own policy: its own sandbox off (0127 §1: none runs nested), the operator's login denied with the macOS keychain (0127 §12), the task finished | An agent that cannot is limited to unsandboxed projects; what it needs in place of the keychain is its equivalent of `claude setup-token` (0127 §8) |

## The ACP runtime: to discuss after the experiments

1. **A null cost against the ceiling and `run.usd`**, from E1. Settled: an
   unpriced run with tokens is estimated, as the system already estimates.
2. **The sandbox's hosts per agent**, from E5, and **its login inside the
   sandbox**, from E10. Open: whether each ACP agent
   Lingtai knows carries its hosts and config directory built in, as
   Anthropic's and OpenAI's are (`BUILT_IN_DOMAINS`,
   `packages/sandbox/src/policy.ts:59`), or the person declares them, as a
   project's own hosts already are (`ProjectAdditions.network`, `:30`).
3. **Permission requests and failing closed**, from E2 and E3.
4. **`RuntimeId`**: one `acp` value with the agent's command in the recipe,
   or one value per agent. It names the runtime on `RunSpent`, keys the
   account and its usage-limit lock (`acct-{runtime}`, 0126), picks the login
   probe (`AUTH_PROBES`, `packages/agent/src/auth.ts:315`) and is what a
   recipe's step names.
5. **0129's Attempt owner**: built first only if the runtime adds new event
   types to `pass-` streams; if it only adds a `RuntimeId` value, it stays out.

## The GitLab acceptance run

Not a feature: with tickets in the local store, discovery, claiming and
landing never ask the remote's host anything, and the landing is a local
`git merge --no-edit` and a push (`packages/actions/src/merge-action.ts:47`).
`repo.remote` takes any git URL (#394). What is unproven is the run itself, so
the acceptance is:

- a clean machine with nothing of Lingtai on it, installed from the release
  script, measured from the first command to the first landing (the *first run
  on a clean machine* moved here from 0.15.0);
- a GitLab project as `repo.remote`, `source.tickets: db`, local tickets with a
  blocker between them;
- which credential the push used, written down;
- the documentation the run proves, and a ticket for each thing it found.

Bitbucket is the same claim and is not run separately.

## Linear, if there is time

The first child of the epic #340 is the cost: a ticket reference is a number
today (`getIssue(number)`, `packages/conductor/src/ticket-store.ts:78`), and a
Linear id is not. Branch names `agent/<n>`, `{{issue}}` and event fields take a
string first, then the adapter. If the ACP runtime and the acceptance run take
the milestone, Linear moves to a later one whole, with #340.
