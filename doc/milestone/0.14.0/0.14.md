# 0.14 — a boundary the agent cannot leave

**Status** open · 2026-11-13 · what 0.14.0 is to contain, as the operator
agreed it in discussion. 0.13.0 was released on 2026-11-13 and 0.14 has begun:
#1122 (S0) and #1128 (S0b) are open, and the other rows are filed from the
ticket plan below. How each part is built goes in its ticket.

The research behind it is
[agent-sandbox-options.md](agent-sandbox-options.md): it compares
OpenSandbox, sandbox-runtime, a Docker image, Docker Sandboxes and cloud
sandboxes, and recommends sandbox-runtime (`srt`). It also gives the levels
L0–L5 that this file uses.

## Where it stands

An agent runs as the operator, on the operator's machine
([safety.md](../../safety.md)). Lingtai launches Claude Code with
`bypassPermissions` (`packages/agent/src/claude-code.ts:305`) and no filesystem
sandbox (`claude-code.ts:73`, `providesTier: 'guarded'` at `:77`). Codex runs
under its own `workspace-write` and provides `sandboxed`
(`packages/agent/src/codex.ts:36`, `:214`). A `build:` command is a plain
`spawn(…, { shell: true })` in the worktree with a filtered environment
(`packages/actions/src/command.ts:453`, `:466`), so the code an agent just
wrote runs with no boundary at all.

| | Claude Code | Codex | build commands |
|---|---|---|---|
| L2 write | anywhere | worktree, tmp, git dirs | anywhere |
| L2 read | anything, `~/.ssh` and `~/.lingtai/config.yml` included | only what a user's profile denies | anything |
| L3 network | open | not measured | open |
| L4 credentials | `gh` login usable, credential files readable | same | same |

What exists and changes: the tier, `Tier = z.enum(['open', 'guarded',
'sandboxed'])` (`packages/domain/src/events.ts:87`), and refusing a recipe whose
tier a runtime cannot provide (`missingForTier`,
`packages/agent/src/runtime.ts:332`). Both go: the `sandbox` block takes the
tier's place, and failing closed becomes a fixed requirement (decision 10).

## What 0.14.0 contains

**One policy wraps Claude Code, Codex and every `run:` command, at every step, through
sandbox-runtime, on macOS and Linux.**

| | What is true | Level |
|---|---|---|
| **Files** | An agent and its build write only to its worktree, the temp directory and the git directories a commit needs. They cannot read a fixed list of credential paths (below). | L2 |
| **Network** | Only allowed domains are reachable: a built-in default of model APIs, package registries and GitHub, plus the project's own list in its recipe. | L3 |
| **Credentials** | Lingtai's own config and the operator's other credentials are unreadable, `gh`'s login included. | L4, partly |
| **One boundary** | `srt` is the only sandbox. Claude Code's own sandbox and Codex's `workspace-write` are switched off inside it, so the two runtimes and the build command answer to one policy. | — |
| **Refused, never downgraded** | A project that asks for the sandbox on a machine that cannot provide it (no `bwrap` on Linux, say) is refused by name. It does not run without the sandbox. | — |
| **Seen** | A connection the sandbox refused is an event, shown on the task page. A refused read or write is not: srt does not report one (017). Each run records the boundary it ran under. | — |
| **On by default** | A new project gets the sandbox from `lingtai init` and the add-repository wizard. | — |
| **Lingtai first** | Lingtai's own recipe is the first existing project to opt in. Every other existing project is left as it is, and `lingtai doctor` says it runs without a sandbox. | — |
| **Written down** | `safety.md` is rewritten from measurements on macOS and Linux, cell by cell. | — |

### The decisions, as agreed

1. **`srt` is the only boundary.** Codex runs inside it with its own sandbox
   off. Seatbelt is likely not nestable on macOS, so two layers would probably
   fail anyway, and one layer is one policy to measure and to explain.
2. **A refusal is an event in 0.14**, on the board, not only a line in the run
   log. A person learns more from what an agent tried than from a silent block.
   017 narrows this to refused connections, the only refusals srt reports on
   both platforms.
3. **One allowlist per project, plus built-in defaults.** Splitting it by step
   (`prepared` may install, `implement` may not, as #339 proposed) is later.
4. **Lingtai opts in first; other existing projects are unchanged.** New
   projects are on by default.
5. **`gh` is closed to the agent.** Lingtai pushes and merges outside the
   sandbox (`codex.ts:50`: *the lane runs git outside the sandbox*), and
   everything an agent needs from the ticket is in its brief, so the agent
   never needs GitHub credentials. `~/.config/gh` is on the deny list.
6. **The runtimes' own config directories stay readable, except Claude Code's
   login.** `~/.claude`, `~/.claude.json` and `~/.codex` stay readable: Codex
   runs on the login in `~/.codex`. Claude Code does not need the operator's
   login, since each run has a directory of its own with only an access token
   (decision 8, measured in 017 cases D, E, G1 and G2). So
   `~/.claude/.credentials.json` is denied, and on macOS so is
   `~/Library/Keychains`, which holds the same login. 0.14's L4 is therefore
   *Lingtai's and your other credentials are unreadable, and a Claude Code run
   holds no refresh token*. It is not *the agent holds no long-lived
   credential*, because Codex's run still reads `~/.codex/auth.json`. The
   safety manual says so plainly.

7. **On Linux the hook socket gets through with `allowAllUnixSockets`**, and
   the known dangerous sockets are read-denied instead, starting with
   `/var/run/docker.sock`. `lingtai doctor` and the safety manual say so.
   (017: seccomp cannot let one path through.)
8. **Each Claude Code run gets a configuration directory of its own, holding
   only an access token.** Lingtai makes a `CLAUDE_CONFIG_DIR` per run, and
   the operator's `~/.claude` and `~/.claude.json` are read-only to the run, so
   a run cannot plant a hook or an `mcpServers` entry that the operator's own
   sessions would run. **The run never holds the refresh token.** A refresh
   rotates it and revokes the old access token, so a run that refreshed in its
   own directory would log the operator out (017, measured). Before each
   Claude Code run, Lingtai refreshes the operator's login outside the
   sandbox if it expires within the run's wall limit plus a margin, with
   `claude auth status` against the operator's own configuration (a refresh
   with no model call), and copies only the access token into the run's
   directory. This reverses today's behaviour, where a run drops
   `CLAUDE_CONFIG_DIR` and reads `~/.claude`.
   **Where the operator's login is read from.** On macOS the store depends on
   the session: in the desktop session (and so under `lingtai service`, a
   LaunchAgent) Claude Code keeps the login in the Keychain item
   `Claude Code-credentials`; over SSH it keeps it in
   `~/.claude/.credentials.json` (017, measured). Lingtai reads the access
   token from the same store that session's Claude Code uses, and **judges it
   by `expiresAt`, never by `"loggedIn"`**: `claude auth status` answered
   `"loggedIn": true` on a token expired for 287 days. When the token still
   expires within the wall limit plus the margin after the refresh, the run is
   refused by name with *sign in again*, and nothing is started. The run's own
   directory needs no Keychain: with `CLAUDE_CONFIG_DIR` set, Claude Code reads
   that directory's file in the desktop session too.
9. **On macOS every run has `enableWeakerNetworkIsolation`**, because Codex
   needs `trustd` to verify TLS, and srt reads the option only from its
   process-wide configuration, never per command (`sandbox-manager.js`
   `getEnableWeakerNetworkIsolation`, 0.0.83). One srt per process (decision 3)
   means one setting for every run. Agreed 2026-11-13: on for all macOS runs,
   rather than a second srt process for Codex. The file and network rules are
   unchanged; what widens is access to the `trustd` service. Each run records
   it, and the manual says so.
10. **The `sandbox` block owns the sandbox, and `runtime.tier` goes.**
    Agreed 2026-11-12. `tier: sandboxed` required a runtime's own boundary,
    which decision 1 turns off, and the `sandbox` block's `enabled`/`required`
    say the same thing about srt: two switches for one thing, which allow
    `tier: sandboxed` with `enabled: false`, while `required: false`
    contradicts 0106 §4's *a tier is never downgraded*. Without `sandboxed`,
    the tier is `open | guarded`, and all `guarded` asks is that a runtime
    stops the run when its hook refuses (`canFailClosed`). Both runtimes that
    use tools already do (`claude-code.ts:70`, `codex.ts:210`), the code says
    the check is dead today (`runtime.ts:341`), and no recipe on the
    conducting machine sets a tier. So the key goes:
    - **Failing closed becomes a fixed requirement**, not a setting. A runtime
      that runs tools and cannot fail closed is refused by name, as `guarded`
      refuses it today. A model-only runtime (codex-text, `codex-text.ts:27`)
      has no tools and no hook to fail, and is exempt by what it is.
    - **What a run may reach is the `sandbox` block's alone**: whether there is
      a sandbox (`enabled`) and whether a host that cannot provide it stops the
      project (`required`). 0127 holds its rule, *never downgraded silently*,
      since `required: false` is a downgrade the recipe asked for and every run
      records.
    - **Gone:** `runtime.tier` in the recipe schema (`packages/recipe/src/recipe.ts:3248`),
      `Tier` and `providesTier`, `meetsTier` and `missingForTier`
      (`packages/agent/src/runtime.ts:332`), Codex's and codex-text's
      `providesTier: 'sandboxed'`, and the tier in the conductor's pass and its
      log line (`packages/conductor/src/conduct.ts:948`, `:1067`). 0106 §4 is
      rewritten: containment is 0127's, and failing closed is a capability.
    - **The log is read first.** `Tier` is in two event payloads,
      `DispatchRefused.requiredTier` and `Invocation.tier`
      (`packages/domain/src/events.ts:543`, `:572`), and every event already
      written must still decode. The ticket reads the log for what those
      fields hold, and says how old events decode once new ones stop carrying
      the field, before anything is removed.
    - **A recipe that still writes `runtime.tier` is refused with its
      replacement, by the value it had**, never with *delete the field* alone:
      a recipe that loses `tier: sandboxed` and has no `sandbox` block would
      fall to the default, no sandbox, and lose the containment it asked for.
      - `sandboxed` → *replace it with `sandbox: { enabled: true, required: true }`*,
        the same promise: contained, or nothing runs.
      - `guarded` → *delete it*: failing closed is now always required.
      - `open` → *delete it*, and the sentence says that a runtime which cannot
        fail closed is now refused rather than allowed.
      Lingtai never rewrites the operator's recipe; the refusal names the
      exact lines, and `lingtai doctor` shows the same sentence.
    - **Codex's own boundary is kept wherever srt is not.** Decision 1 turns
      the runtimes' own sandboxes off *inside* srt, because they cannot nest.
      A Codex run that is not wrapped (off by choice, or degraded) keeps
      today's `-s workspace-write` and the operator's permission profile
      (`packages/agent/src/codex.ts:1459-1478`), so moving from `tier:
      sandboxed` to a degraded sandbox never leaves a Codex run with less than
      it has today.
    - **The order guarantees the replacement exists first.** S3b is blocked by
      S7 (the `sandbox` block resolves and refuses a host that cannot provide
      it) and by S4 and S5 (both runtimes run inside the policy, which comes
      after S7), so on the
      day the tier is refused, `required: true` already does what `sandboxed`
      did.
11. **A run's caches are Lingtai's, never the host's.** Agreed 2026-11-12.
    017 made `~/.local/share/pnpm` and `~/.cache` writable so that
    `pnpm install` worked. That leaves a way out of the sandbox:
    `~/.local/share/pnpm` is `$PNPM_HOME`, on the operator's `PATH`, and holds
    their global executables (harbor: `acorn`, `chroma`, `csv2json`, …), and
    `~/.cache` holds programs they run outside (harbor: `mise`, `prisma`,
    `node-gyp`, `google-chrome`). A run that rewrites one of them has its code
    run the next time the operator does, unsandboxed. So:
    - **Each project gets a cache directory of Lingtai's**, `~/.lingtai/cache/<project>/`,
      the only cache a run may write. It sits beside the worktrees, on the same
      filesystem, so pnpm can still hard-link from its store. It is not under
      `~/.lingtai/<project>/`, which holds the recipe.
    - **The wrap points the tools at it** after the environment is filtered
      (S3), alongside srt's proxy variables: `XDG_CACHE_HOME`,
      `XDG_DATA_HOME`, `npm_config_store_dir`, `npm_config_cache`,
      `PIP_CACHE_DIR`, and so on. The list is the policy module's, and a tool
      that ignores all of them fails to write its cache, which is a refusal,
      not a hole.
    - **The host's tool and cache directories stay read-only to a run**:
      `~/.cache`, `~/.local`, `$PNPM_HOME`, `~/Library` on macOS, and every
      directory on the `PATH` Lingtai started with. A run still finds and
      executes the operator's `pnpm` and `node`; it cannot change them.
    - **Per project, not shared.** A cache one project's run poisoned is
      never read by another project's run. The cost is disk, and a cold first
      install for each project, which S6 measures.

### The deny list

These paths are unreadable and unwritable: `~/.ssh`, `~/.aws`, `~/.config/gh`,
`~/.gnupg`, `~/.netrc`, `~/.docker/config.json`, `~/.kube`, `~/.npmrc`, and
`~/.lingtai/config.yml` with every backup beside it, `~/.claude/.credentials.json`
(decision 6), and on macOS
`~/Library/Keychains`: without it a run reads the operator's Claude Code login
through `security find-generic-password` (017, measured, inside srt). The rest of `~/.lingtai`
is covered by the first trap below. Keeping the list in one place in the code
is part of the policy ticket. The final list is settled by the measurement,
and the manual prints it.

### What a person sees and sets

Agreed 2026-11-12. One new tab on the task page, and one icon on the bar.

**What is configurable is one block in the recipe, per project:**

```yaml
sandbox:
  enabled: true            # absent is off for an existing project; new projects get true
  required: false          # true: stop when this host cannot provide it; false: run unsandboxed, said loudly
  network:
    allow:                 # added to the built-in defaults; a default cannot be removed
      - pypi.org
      - "*.pythonhosted.org"
  write:                   # added to the built-in writable roots; never a host tool's own directory
    - ~/work/fixtures
  deny:                    # added to the built-in deny list; nothing here can lift a built-in deny
    - ~/work/secrets
```

- **Everything is add-only.** A project can widen the network and the writable
  roots, and narrow reading. It cannot remove a built-in default domain, lift
  a built-in deny, or unprotect a write deny.
- **`write` is refused at resolve, by name, when it reaches what the policy
  protects.** That covers a path on the deny list or inside it, `$HOME` itself,
  `~/.lingtai`, the mirror, a runtime's config directory, and the host's own
  tool and cache directories (decision 11): `~/.cache`, `~/.local`, `$PNPM_HOME`,
  `~/Library` on macOS, and any directory on the `PATH` Lingtai started with,
  or inside one.
- **A `deny` path inside a run's worktree or mirror is refused at resolve
  too.** srt's `allowRead` overrides `denyRead` (017), and the worktree and
  mirror are on `allowRead`, so such a deny would be silently void.
- **`required` decides what a host that cannot run the sandbox does.** That
  is common on Linux: many servers and minimal installs have no `bwrap`, and
  Ubuntu 24.04's default AppArmor setting stops it even when it is installed.
  Off by default, so such a host keeps working, unsandboxed and said loudly
  (below). Lingtai's own recipe sets `required: true`. The fallback is decided
  **once, before a run starts**. A wrap that fails during a run fails that run,
  and the run never carries on unsandboxed.
- **Not configurable**, because each one is a single line away from no
  sandbox: the built-in deny list, the write denies inside the writable roots
  (the mirror's `config`/`hooks`/`info`, `~/.claude`'s settings, hooks and
  plugins), how Claude Code's token is handled (decision 8), the weaker
  network isolation on macOS (decision 9), and the srt version, which ships
  with Lingtai and is recorded per run.
- **Nothing in `~/.lingtai/config.yml`.** The policy is per project
  (decision 3).

**What is shown.** Sandboxing is one of the things Lingtai is for, so it is
visible rather than buried in a run log. Both states are marked, and not
equally: a sandboxed run is calm (a shield, *sandboxed · srt <version>*), and an
unsandboxed one is in the warning colour (*unsandboxed*, with the reason),
because the case a person must not miss is the one with no protection. **The
mark says *sandboxed*, never *safe*.** Three things 0.14 does not cover are said
in the sandbox tab: Codex's login stays readable to a Codex run, srt does not
report refused file access, and srt is a research preview. Being plain about
what is not covered is what makes the mark worth believing.

1. **A *Sandbox* tab on the task page (S9)**, beside the ticket and the
   attempts. It has three parts:
   - **Allowed:** the writable roots and the reachable domains, each marked
     *recipe* or *built in*.
   - **Limited:** the paths that cannot be read and the paths that cannot be
     written, how Claude Code's token is handled, and the three things not
     covered.
   - **Blocked:** every refused connection across this task's runs, grouped by
     host with a count, the run it came from and the first time.

   The rules shown are **what each run recorded it ran under** (S8), not
   today's recipe, so a run from before a recipe change still shows its own.
   Each refused host has **Allow on this project**, a link to the recipe editor
   with the domain filled in. The tab writes nothing.
2. **The recipe page's sandbox section (S9b)** is the same view for the whole
   project: the project's own entries from `recipe.yml`, the built-in defaults,
   deny list and writable roots greyed as *built in*, and **recently blocked**
   across every task of the project. It is also where the block is edited,
   since editing a recipe happens on that page (#980). The two views share one
   component.
3. **Each run's row on the attempt page** carries the same mark, small.
4. **The bar gets one icon, beside `Report`** (below). Each project in the
   **filter's menu** carries the mark, and so does each card on the board.
   When a recipe requires the sandbox and it is not running,
   **health** says so, because that is the system not doing what its
   configuration says.
5. **When the host cannot provide the sandbox**, what happens is the recipe's
   `required` (above). With `required: false`, the run goes ahead unsandboxed,
   the banner says *this project is running without a sandbox*, with the reason
   and the install command, and every run is marked *unsandboxed (bwrap
   missing)*. With `required: true`, the project stops, and the banner says so,
   with the same fix. No banner reads a refused recipe today: a `ProjectRefused`
   shows only as the Queued column's reason (`apps/board/src/lib/board.ts:1035-1060`)
   and in `lingtai doctor`. S9c adds both banners.
6. **The new-project wizard (S11).** The sandbox is on. The wizard checks the
   host first: where it cannot run the sandbox, it says so with the install
   command. It shows the built-in allowlist with a field for more, and turning
   the sandbox off is an explicit choice, with one line on what that gives up.

**Four states, not four levels of safety.** Agreed 2026-11-12 after the mock
([sandbox-ui.html](sandbox-ui.html)). *Off by choice* and *degraded* protect
exactly as little as each other; what differs is whether it is what the operator
asked for. So the states rank how much they need a person, not how safe they
are, and each has its own shape as well as its colour:

| State | Mark | Colour | When | Work | Counted in the summary |
|---|---|---|---|---|---|
| Sandboxed | solid shield, tick | accent (teal) | every run inside the policy | goes on | no |
| Off by choice | dashed shield | muted (grey) | `enabled` is not set | goes on | no, and never an alarm |
| Degraded | shield, `!` | signal (amber) | wanted, this host cannot, `required: false` | goes on, unprotected | yes, the banner |
| Stopped | solid shield, `×` | fail (red) | required, this host cannot | nothing is claimed | yes, the banner and health |

The weaker network isolation on macOS is not a fifth state: the run is
inside the sandbox, and the Sandbox tab says it in words.

**The bar carries one icon for it, beside `Report`.** With a project selected,
it is that project's state. With *all projects*, it is the worst state among
them. It has no text. It has a tooltip and an accessible name with the
sentence (*chapter-garden is running without a sandbox — bwrap missing on
harbor*). It is a link, reached by Tab and opened with Enter. A click opens the
selected project's sandbox section on the recipe page (`/recipe/<project>#sandbox`).
With *all projects*, it opens that section for the one project in the worst
state, or, when several share it, a small list of the projects with their
states, each a link to its own section.
It is the only place on the bar: the filter's menu marks each project, and the
filter's own control does not. This is an exception to #902's three objects,
argued in [the-bar.md](../../design/the-bar.md): it answers *is the system doing what I
configured it to*, the same question as health, in one icon's width.

**A step that fails because the sandbox refused it goes to a person, never to
a fix round.** A fix agent cannot allow a host, so the round it buys is money
spent on a failure it cannot fix. When a step's run fails and that run
recorded at least one refused connection (not counting the telemetry list
below), the pass refuses with a reason of its own, `sandbox-refused`, instead
of `red`. The router offers only `human` for it: no built-in judge, and a
`judge:` declared at that `when` is refused when the recipe resolves. It lands
in **Waiting on you** with the refused hosts and a link to the recipe editor.
Allowing a host takes effect from the next attempt, so the answer is *allow,
then requeue*, and the page says so. A step that went red for an unrelated
reason while a host was refused also goes to a person. That errs toward a
person and costs nothing.

**Known telemetry hosts are built in and not shown.** Package managers and
frameworks call home on every run (npm's update check, Next.js telemetry,
error reporters). Those refusals would keep *Blocked* from ever being empty, and
a list that is never empty is not read. Lingtai keeps a built-in list of such
hosts. A refusal to one of them is still recorded on the run, but it is left
out of *Blocked*, out of the counts, and out of the `sandbox-refused` rule.
The list is Lingtai's, not the recipe's, and is not configurable. Build
commands also get `DO_NOT_TRACK=1` and `NEXT_TELEMETRY_DISABLED=1`, so fewer
of those calls are made.

**A host that loses the sandbox during an attempt.** The check runs before
each run, and one attempt has several runs. With `required: true`, the attempt
fails at that step with *sandbox unavailable*: it is not the agent's failure
and buys no fix round. With `required: false`, the later runs go ahead
unsandboxed, and the Sandbox tab marks each run with its own state.

## What the measurement found

The traps this plan named were measured on 2026-11-12, by hand, on harbor
(Linux) and foundry (macOS). The results are
[experiment 017](017-srt-under-lingtai.md). In short:

**Answered.**

- **`~/.lingtai` can be denied whole and a run's worktree and mirror allowed
  back**, on both platforms. A `git commit` in the worktree works.
- **The deny list holds**: `~/.ssh` and the `config.yml` canary are unreadable,
  `$HOME` is unwritable, and only allowed hosts are reachable, raw TCP included.
  Claude Code under `bypassPermissions`, told to read the canary and write
  outside, failed at both.
- **A runtime's own sandbox does not work inside srt.** On macOS it cannot
  start (`sandbox_apply: Operation not permitted`), and on Linux Codex's starts
  but cannot write even in the worktree. So srt being the only boundary
  (decision 1) is forced as well as chosen.
- **Codex runs inside srt on Linux** with its own sandbox off, and was refused
  the canary and a write outside, like Claude Code.
- **Bundling into the SEA is feasible.** The Windows-only 166 MB is a lazy
  import and can be left out. On Linux the 742 KB `apply-seccomp` has to be
  written to disk and named with `seccomp.applyPath`. That is S13.

**Build around these.**

- **The mirror's `config` is writable from a run**, so a run could set
  `core.hooksPath` or `core.fsmonitor` for Lingtai's own git, which runs
  outside the sandbox. The mirror's `config`, `hooks/` and `info/` must be
  write-denied.
- **On Linux, srt plants `/dev/null` stand-ins** for `.bashrc`, `.gitconfig`,
  `.vscode` and the rest in the worktree, so `git add -A` fails. Lingtai
  writing those names into the mirror's `info/exclude` at provision fixes it
  (measured).
- **A package manager needs a writable store**, or `pnpm install` fails. 017
  made `~/.local/share/pnpm` and `~/.cache` writable to get there, which is
  **not** what ships: both hold programs the operator runs outside the sandbox
  (decision 11).
- **One of Lingtai's unit tests fails only inside srt, and it is a test bug.**
  `conduct-before-the-claim.test.ts` *refuses before the claim when
  runtime.agent is not the runtime it was handed* passes no `signedIn`, so it
  spawns the real `claude auth status` and `codex login status`
  (`conduct.ts:859-870`). That breaks 0060 §1 on every machine. Inside srt it
  hangs, because `runnableEnv` drops the proxy variables (next point). It is
  #1122 (S0), and Lingtai cannot opt in until it lands.
- **The wrap must go outside the environment filter.** `runnableEnv` keeps six
  variables and drops srt's `HTTPS_PROXY`/`ALL_PROXY`. A child spawned with it
  inside srt has no network on Linux, and Claude Code hangs rather than fails
  (`claude auth status`: 2.7 s with them, no answer in 40 s without). So the
  policy module adds srt's variables after the filter.
- **srt is one instance per process, so a project's allowlist is registered
  per run.** `SandboxManager` is initialised once and runs one proxy
  (`dist/sandbox/sandbox-manager.d.ts:138` in `@anthropic-ai/sandbox-runtime`
  0.0.82), and one daemon conducts several passes at once (0122). The network
  list handed to a wrap does not change what that proxy lets through; only
  `registerCommandNetworkLists(commandId, …)` gives one invocation a list of its
  own. So the instance holds the built-in defaults only, each run registers its
  project's `network.allow` under an id of at least 128 random bits just before
  it starts and unregisters it when it exits or never started, and
  `strictAllowlist` stays off (it would ignore every per-run list). srt calls
  this id *attribution, not a boundary between concurrent commands*: a run that
  learns another live run's id gets that run's list. Measured (017): on
  Linux a run sees no other run's processes. On macOS it reads most of the
  operator's processes' command lines, though not their environment, and srt
  itself puts the id in the command line of the wrapper for the moment before
  it execs (`wrapWithSandboxArgv` is the same string behind `bash -c`). The probe
  did not catch it, but a run polling the process table could, and would gain
  another project's allowlist, not a way out. That residual is accepted and the
  manual says it, with the wider fact: on macOS a secret in any process's
  arguments is readable from inside srt. **The `env` srt returns with the argv
  is the daemon's own environment, Lingtai's database URL included, and is
  never passed to `spawn`**: the child gets the filtered environment plus srt's
  proxy variables, with `shell: false`.
- **The hook sockets' directory is write-denied.** Each run's hook socket is
  under `<tmpdir>/lingtai/` (`packages/agent/src/hook-config.ts:63`), and the
  temp directory is a writable root, so one run could remove or replace another
  run's socket and answer its hook. With `<tmpdir>/lingtai` on the write-deny
  list, a run still connects to its socket and cannot write beside it, remove
  it, or bind a new one there (017, measured on both hosts).
- **srt reports refused connections, not refused files.** Linux has no file
  report at all, and macOS's kernel log has the denials but srt did not
  attribute them to the command. So S8 records connections.

**Still open.**

- **Whether `claude auth status` refreshes a refreshable token held in the
  Keychain.** foundry's only Keychain token had a dead refresh token. Decision
  8 does not depend on the answer: Lingtai reads `expiresAt` after the refresh
  and refuses the run when it is still short.

**Answered since.** The 401 on foundry was a refused refresh: refreshing needs
`platform.claude.com`. And a refresh rotates the token, so a run must never
refresh. That is decision 8, and 017 has the measurements. **The macOS
Keychain** (017, measured by hand in foundry's desktop session): the store
Claude Code uses depends on the session, a run with its own
`CLAUDE_CONFIG_DIR` ignores the Keychain, and a run inside srt can read the
Keychain unless `~/Library/Keychains` is denied. That is decision 8's last
paragraph and the deny list.
- **Ubuntu 24.04's default AppArmor setting** was not measured, because harbor
  has it off already.

**Decided by the operator, 2026-11-12**: the Linux socket, `~/.claude`, and
`trustd` are decisions 7–9 above. One trade-off remains and needs no
decision: **`srt` is a research preview**, and its API may change. 017
measured 0.0.82, and its core cases were re-run on 0.0.83 on both hosts with the
same results. 0.14 pins **0.0.83**, exactly, and records it on every run; a
later version is taken only after S10's canary passes on both hosts.

## Not in 0.14

- **Credentials injected at the proxy** (the other half of L4), so that a
  project's own secret never sits where an agent can read it.
- **One allowlist per step.**
- **A container or VM boundary** (L5): Lingtai's Docker image is the server
  case and is separate. OpenSandbox and Docker Sandboxes are being watched.
- **A self-check of the operator's own runtime configuration** (#810). With
  the runtimes' own sandboxes off inside srt (decision 1) and each Claude Code
  run on a directory of its own (decision 8), that configuration no longer
  decides what a sandboxed run can reach, and an unsandboxed run is said to
  reach what the operator can. #810's one lasting point, *a configuration read
  is not a measurement*, is S10's canary.
- **Windows.**
