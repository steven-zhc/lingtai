## 2. 产品方向与优先级

1. **Reliable：**任何被确认的交付都有依据；崩溃、重启和外部结果不确定时能正确恢复。
2. **Simple：**安装、运行、观察结果和处理异常容易理解；正常路径尽量少操作。
3. **Transparent：**不用 PR 也能回答谁改了什么、检查了什么、为什么允许合并、最后落在哪里。
4. **用户掌控自主程度：**推荐 Direct Merge，由 recipe / Gates 显式决定何时需要审批及遇到问题如何处理。
5. **集成可选：**PR、更多 Agent 和外部系统增强体验，不成为核心交付的必要依赖。

P0 是可信交付与恢复的前提；P1 改善使用体验和掌控感；P2 是可选扩展。优先级表示建议投入顺序，不表示功能当前缺失，也不是仓库 Issue kind 的排队顺序。下面的 M1–M5 是本稿的规划分组，不是 GitHub milestone；只有第 6 节的首个切片已排进 0.15.0，其余没有承诺日期或版本号。

## 5. Merge Evidence 设计讨论

### 5.1 先回答哪些问题

每次交付要能回答：哪个 Ticket、哪次 attempt 产生了什么内容？哪些检查实际运行过？当时为什么允许合并？Git 最终发生了什么？系统如何确认这个结果？证据还有哪些缺口？

Merge Evidence 是这些事实的一致结构与读取契约，不预设一个新表、新事件类型、新 reducer 或独立审计系统。先映射现有事件、对象存储和读取路径，再决定最小增量。若现有数据已经满足要求，LM-01 可以以覆盖清单、缺口验证和统一读取完成。

**粒度提案：**以一次 delivery intent / decision 为证据单元，关联 Ticket、attempt/pass、Agent run 和候选版本；Ticket 页面聚合各次记录。这样一次 Ticket 的失败、重试和最终交付不会被压成最后一行。是否采纳这一粒度仍待讨论。

### 5.2 五段证据模型

以下是概念字段，不是已存在的 schema、API 或配置语法。

| 部分 | 保存的事实 | 关键约束 |
| --- | --- | --- |
| **Intent** | evidence / delivery 标识、仓库、Ticket、attempt/pass/run、Agent 身份、交付方式、目标 ref、预期 base SHA、候选 SHA | 在外部交付操作前确定身份与预期目标；重试可找到同一意图 |
| **Validation** | Gate 名称、检查对象 SHA/tree、配置快照或可解析版本、执行版本、时间、结果、输出引用；Review 结论及覆盖/截断情况 | 执行检查时就保存；未运行不当作通过，摘要不能替代实际结果 |
| **Decision** | 关联 intent 与 validations、允许/拒绝/待人、规则及原因、当时自主设置、必要的审批身份和对象 | 合并之前持久化决定；配置 hash 必须能找到对应内容，单有 hash 不够解释历史 |
| **Outcome** | Git 操作观察、base before、result SHA、目标分支、发生时间、local/remote 范围、push 结果、文件变化和 Diff 引用 | 区分本地合并与远端确认；命令超时不自动等于失败，命令成功也不替代状态确认 |
| **Reconciliation** | 观察时间、实际 ref/commit、与 intent 的对应关系、confirmed/unknown/mismatch、恢复动作及引用 | 先查事实再决定重试；后续观察追加，不能覆盖原决定或伪造旧检查 |

辅助字段包括证据格式版本、Lingtai/插件版本、稳定事件引用、缺失项与原因。成本为解释性信息，区分 reported、estimated、unknown；成本未知本身是否影响验证状态须与安全必需证据分开定义。

### 5.3 生命周期与状态表达

```text
形成候选 → 执行并保存检查 → 冻结交付意图与决定
                              ↓
                    在受控合并边界核验 base / candidate
                              ↓
                         执行 Git 操作
                              ↓
                 观察实际结果并持久化 → 读取证据
                              ↑
                     中断后先对账，再决定重试
```

Git 与事件存储不能被假定为同一事务。方案必须覆盖“外部操作已成功、成功事件尚未写入”的间隙，也要处理事件已经写入但读取投影仍落后的情况。

保留两个独立维度：

- **交付事实：**尚未操作、确认已落地、确认未落地、结果未知；“落地”具体指本地还是远端须在交付契约中声明。
- **证据状态：**完整且有效、待确认、缺失、已失效；证据状态不得掩盖已经发生的 Git 事实。

**No verified evidence, no verified delivery.** 已发生合并但缺少证据时，显示“已合并，证据待确认/不完整”，既不伪装成完整交付，也不因缺证据而自动再合并一次。历史记录不具备新字段时如实标明，不补造历史 Gate 或审批。

### 5.4 安全与持久性边界

- 检查通过后 base、候选内容或相关规则改变，需要明确失效规则；不能仅比较分支名。复用结果的条件必须可证明，否则重检或暂停。
- 最终 result SHA 可能不同于候选 SHA；必须说明检查覆盖的内容如何对应最终合并树。合并前的 base 核验与实际更新之间还存在并发窗口，具体消除方式在 LM-03 中设计。
- 工作区清理不能删除必要证据。Diff 和输出引用应指向保留的对象；对 Git 对象回收、远端改写、附件过期明确保留策略和缺失表现，不把一个失效链接视作证据仍可读取。
- Event Log 是 Lingtai 决策与观察记录的真相来源；外部 Git 结果需重新观察，并把观察写入日志。不能仅凭内存状态断言已交付。
- 证据以追加事实和可重建读取为基础；“不可随意修改”不等于已有密码学防篡改保证。稳定引用不能只依赖可重置的裸 `seq`；日志重置、导出和保留期限需有明确边界。
- 保存足够解释结果的内容，避免把凭证、环境变量和敏感原始输出无差别持久化；脱敏或截断要说明，不能偷偷丢掉决定性证据。
- 合并后集成检查单独显示，不追溯改写合并前的决定；“配置的 Gate 满足”不宣称软件不存在缺陷。

### 5.5 展示与读取

优先复用 `/landed`、任务详情、CLI 和既有 Issue 评论。默认展示结果、目标/result commit、允许交付的原因、关键检查及未确认项；再展开 Diff、各次检查、审批、恢复时间线。CLI 与 Board 从同一事实定义读取，不能分别推断出相互矛盾的状态。

展示示例（虚构，不代表真实 Ticket）：

```text
修复认证问题 · Direct Merge
交付：已确认到目标分支 main
证据：完整且有效
检查：已配置的 build / review 通过；未配置人工审批
决定：按本次冻结规则自动交付
变更：4 个文件 · base SHA → result SHA
详细：Diff / 检查对象与输出 / 决策 / 对账观察
```

## 6. 首个 release：Trustworthy Direct Merge

这是本 roadmap 的首个交付切片，**不是**项目首个版本，计划在 **0.15.0** 交付。原对话保留的建议顺序是：

`LM-01 → LM-02 → LM-03 → LR-02 → LM-04 → LR-01 → LX-05`

由于 LR、LX 的原始表不可恢复，这个顺序中的名称解释采用本稿补拟定义，需先确认。LM-01/02 先确定证据来源和数据契约；LM-03、LR-02、LM-04 协同明确副作用和对账边界。箭头是讨论顺序，不是已创建的 Issue 依赖。

| 纳入范围 | 首版边界 |
| --- | --- |
| LM-01、LM-02 | 最小必需证据、冻结检查/决定、历史缺失处理；复用 CLI / Board 入口，不要求新建完整 receipt 产品 |
| LM-03 | base/candidate 变化、有效检查与实际落地对象的一致性 |
| LR-02、LM-04、LR-01 | Direct Merge 与必要 push 的重试、结果未知及崩溃恢复；优先核验和补强已有机制 |
| LX-05 子集 | 交付、证据和恢复相关错误的清晰下一步 |
| LR-03 的必要验证子集（本稿补充） | 为上述范围提供故障注入验收；完整通用矩阵留在 M2，不建立通用故障平台 |

### Release 退出标准

- [ ] 每次被标为“已验证交付”的记录，都能关联有效检查、冻结决定与实际目标 Git 结果；必需字段可由 CLI / Board 读取。
- [ ] 修改 recipe、清理工作区、重启和重建读取状态后，保留的历史证据仍可解释；超出保留范围的内容明确标记缺失。
- [ ] base/candidate 改变不会静默复用过期检查或审批。
- [ ] 在 Git 操作前后、push 响应丢失、最终事件写入前后和投影更新前后的适用故障点运行实验；重复恢复没有第二次逻辑交付。
- [ ] 外部状态无法查询时停在可解释的未知/待对账状态；不会误报完整交付、永久失败或自动重复操作。
- [ ] 正常 Direct Merge 路径不增加必需人工步骤；需要介入时，用户看得懂原因与下一步。
- [ ] 原有资料覆盖的需求以证据关闭验证项；新增缺口才进入实现票，未完成事项明确列出。

首版不包含完整 Delivery History 筛选、Quickstart 改版、全套 Diff Viewer、Gate Presets、全量审批体验改版、PR Mode、新 Agent provider、复杂预算策略或历史证据批量回填。安全上必需的过期审批失效仍属于 LM-03；不因此排除安全边界。

恢复验收应在独立测试仓库和存储上执行；遵循 ADR 0115 的测试分层。单票不等待全量集成套件，release 验证另行安排真实 Git / 进程故障实验。本次文档整理没有执行这些实验。

## 7. 设计原则与明确不做的事

| 原则 | 讨论约束 |
| --- | --- |
| Default Delivery | Direct Merge 是推荐默认路径；具体行为取决于有效 recipe 和目标仓库规则 |
| Human Approval | 用户通过 Gate 显式配置；无法安全自动处理的情形暂停并给出原因 |
| Source of Truth | Lingtai 决策与记录来自 Event Log；Git 外部事实通过观察、对账记录进入系统 |
| Delivery Evidence | 所有已确认交付应具备结构化证据；先复用事实，再补缺口，不维护平行审计账本 |
| GitHub PR | 可选交付/协作方式，不进入核心调度必需路径；不绕过仓库保护要求 |
| Recovery | 先对账，再判断是否重试；未知不等于失败 |
| UI | 默认展示结果和下一步；按需展开细节，不增加用户必须理解的概念 |
| Agent Integration | 面向现有角色和插件契约，不绑定模型或供应商 |
| Failure Behavior | 不能证明安全时暂停并解释；缺失、跳过和未配置如实表达 |
| Scope | 每项增量由实际缺口驱动；不以竞品功能数量作为开发目标 |

暂缓完整 AI Planner / Epic Studio、多人管理和复杂 RBAC、云端托管、复杂 Policy DSL/模拟器、复杂 Kanban 管理、大量 provider 适配，以及批量独立 PR 工作流。Vibe Kanban / ProPR 仅作为原讨论中的体验和集成参考，本稿不复述未经本次核验的竞品事实。

## 8. 衡量方式

| 指标 | 目标及口径 |
| --- | --- |
| 证据完整性 | 已验证交付中 100% 满足必需证据契约；另列实际已合并但缺证据的数量，避免只缩小分母 |
| 恢复正确性 | 已定义故障矩阵全部通过；记录未覆盖场景，不能将未执行写成通过 |
| 意外重复交付 | 定义的重试和恢复自动化场景中为 0；不把有限测试宣称为全局 exactly-once 证明 |
| 无效检查合并 | base/candidate/审批失效测试中为 0；合并后集成结果分开统计 |
| 失败定位体验 | 为常见失败场景做用户验证，能从摘要找到原因与下一步，无需原始日志；耗时基线待测 |
| 首次使用 | 记录真实新用户的完成率、耗时和卡点，先建立基线再设数值目标 |
| 历史可访问性 | CLI / Board 对同一保留记录得到一致结论；工作区清理后仍可查必要证据 |

## 9. 待讨论问题与下一步

1. **补全编号：**LR/LX/LC 的 13 项划分是否符合原意？尤其 LR-02 与 LX-05 在首版顺序中的含义需先确认。
2. **真实缺口：**现有 `/landed`、任务页、Issue 评论、CLI 分别已有多少字段？#806 曾暂缓的缺失说明/重新检查，现在由哪个具体场景重新提出？
3. **记录粒度：**证据按 Ticket、attempt/pass、delivery intent 还是一次 landing 组织？一次候选多次决定怎样表达？读者是日常操作者、故障排查者还是发布审阅者？
4. **“已交付”的边界：**本地 base 更新、远端 push 确认、还是合并后检查结束？不同交付方式如何声明完成条件？
5. **最小契约：**哪些字段缺失必须阻止合并，哪些只阻止“已验证”标签？成本、摘要等解释性信息缺失如何处理？
6. **旧数据：**历史记录如何标记不完整？是否需要导出/保留策略？不回填时如何维持用户可理解的查询？
7. **检查有效性：**以 commit、tree 还是输入集合识别检查对象？base 改变后哪些 Gate 必须重跑？审批失效规则是什么？
8. **对账身份：**怎样识别“这次意图已经交付”，而不是仅发现一个相似 commit？远端移动、历史改写、push 超时和本地成功但远端失败如何区分？
9. **证据保留：**日志重置、工作区清理、Git GC 和附件过期后承诺保留多久？如何保存脱敏输出、配置内容和稳定引用？
10. **新增抽象：**现有事件和 reducer 是否足够？先做字段映射与缺口清单，何种证据才足以支持新事件或投影？
11. **首版边界：**是否接受上述 7 项主线和 LR-03 验证子集？发布版本定为 0.15.0；负责人、时间及独立验收环境待定。
12. **后续 PR 用例：**哪个具体协作或仓库规则需求足以推动 LI-01/02？在用例明确前保持 P2。
