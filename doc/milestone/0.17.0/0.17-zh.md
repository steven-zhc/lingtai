# 0.17.0 讨论稿（中文）：可验证的落地，和交给人的证据

*讨论稿，2026-11-21。用中文写，方便讨论和修改；定稿后翻成英文，并入
[README.md](README.md)。这里的内容都还没定，也没有开票。*

## 一、灵台最终要成为什么

用户只做两件事：**想业务需求，写票。**

从票到 `main` 的其余部分都由灵台完成：领票、分析、实现、测试，然后用一套方法验证两件事——**做出来的是不是票要的东西**，**程序是不是真的能跑起来**。功能完成后，灵台提交 PR 给团队，附上证据：截图、操作过程的录屏、新功能的演示视频。

所以人的角色变了：**以前读每一个 diff，现在定义“什么叫做完”，再看证据。** Claude Code 团队在
[这篇文章](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
里说的也是这件事。他们大约 90% 的代码由 Claude 写、由 Claude 评审，靠的就是验证闭环。

## 二、整条流水线，以及每一段证明什么

| 阶段 | 证明什么 | 现在 |
|---|---|---|
| 领票、分析 | 理解了需求 | 有（认领、讨论） |
| 写验收 | “什么叫做完”变成能跑的检查 | **0.17**：`doc/design/acceptance.md` |
| 实现 | 代码写出来了 | 有（implement） |
| 构建、测试 | 代码没坏 | 有（build：`pnpm test`） |
| **验证** | **做的是票要的，而且真的跑得起来** | **0.17** |
| 评审 | 代码读起来对 | 有（冷评审） |
| PR 和 CI | 和团队的代码合得上 | 0.16 |
| **证据** | 截图、录屏、演示视频，放在 PR 页和 PR 描述里 | **0.17** |
| 人决定 | 看证据，不读代码 | — |

验证分两层：

- **每张票**（工单流程里）：在 `design` 阶段，由另一个 agent 根据票写出验收检查，到 `build` 阶段运行。要求先在 base 上失败，再在新代码上通过。这一层就是 `acceptance.md` 的内容。
- **每个 PR**（PR 生命周期里）：在 CI 之后加一步 verify，把整个分支真正跑起来，按功能地图走一遍，录下证据。这一步正好落在 0.16 打好的地基上：PR 的“进行中”是一串固定的步骤，再加一步就行。

## 三、那篇文章里的做法，对应到灵台

**灵台已经有的（方向对，0.17 可以加强）：**

| 文章的做法 | 灵台现在 |
|---|---|
| 检查失败后自己修，修三轮还不行就叫人 | 0108“被拒一次买一轮”，加上“人是最后一道防线” |
| 被检查的改动不能修改检查本身 | recipe 放在 `~/.lingtai/`，不在任何工作树里（#180） |
| 只用一个主评审，后一轮带上前几轮的结论 | 冷评审；修复轮次会带上票的正文和分诊建议（#643） |
| 便宜的检查先跑 | 先 build 再评审 |
| 评审只对当前这个提交有效 | 合并前重新检查基线；PR 每次推送都重新跑 CI |

**灵台还没有的（0.17 要考虑）：**

1. **verify：真正把改动跑起来。** 网页用浏览器，后端在本地启动服务，产出步骤记录、截图和失败说明。文章举的例子：单元测试只报一句“超时 30 秒”；端到端检查却能指出“支付表单没加载出来，所以下单按钮一直是灰的”，还附上截图。我们自己的 #1196 就是这样漏掉的：结构上的验收条件全部通过，页面却和设计稿不一样。
2. **功能地图（feature map）。** 从用户的角度列出功能、路径、快捷键、预期结果。它既告诉 agent 怎么操作，也是打分的标准。它可以直接从票的 Done when 和设计稿生成。
3. **证据。** 每一步的截图、过程录屏、新功能的演示视频，挂在 PR 页上，并写进 PR 描述，团队在 GitHub 上也能看到。
4. **由 diff 触发的检查清单。** 每一条都写明：从 diff 里能看出来的触发条件、要检查什么、出自哪次事故。agent 读完 diff 后只跑命中的几条。原料现成：我们分析过的 724 条阻断性评审意见（12 类）。
5. **给每个提交盖章，写明它是怎么验证的。** “没有验证”也是一种章，这样就能查出哪些提交没被验证过。
6. **新关卡先用观察模式上线。** 先只记录“如果开启会拦下什么”，误报都看过了再改成强制。我们吃过这个亏：fmt:check 一上来就卡住了 #390。
7. **给检查本身打分。** 拿历史事故重放，看检查能不能抓到；用稳定合并过的改动做对照，防止误报；把原始发现、验证后的发现、最终结论三个阶段的召回率分开算。灵台的事件日志天然适合做这件事。
8. **从漏掉的问题里提炼规则。** 同一类问题出现在至少两个 PR 里、而且能从 diff 看出来，才写成规则；规则要经人批准。
9. **不稳定测试的规矩。** 不许跳过，不许加 sleep，不许一直重试到通过；查不出原因就删掉，并写明为什么。
10. **定期修剪。** 规则、检查项、提示词文件都要定期清理，不然只会越来越多。

## 四、还要再想的问题

- **验收和 verify 是两个东西还是一个？** 一个按票写、在 build 阶段跑；一个按 PR 跑、在 CI 之后。验收能不能直接就是 verify 走的功能地图？
- **证据存在哪里？** 截图和视频很大，不适合放进事件日志。日志里只记“证据在哪里”，按 0105 §8–9 的“定位符”方式？存本地还是上传到代码托管平台？
- **视频怎么录？** 浏览器的屏幕录制，还是把截图串成 GIF？演示视频谁来“导演”：按功能地图自动走，还是让 agent 自己决定怎么演示？
- **运行环境。** verify 要启动应用，要在沙箱里跑浏览器，还要有测试数据。对 Chapter Garden 这样的项目怎么配置？recipe 里加一个 `verify:` 块？
- **验收写错了怎么办？** 实现的 agent 改不了验收，所以判定者要能把问题退回给验收，而不是退回给代码（`acceptance.md` 已经提到）。
- **成本。** 每张票多一次 agent 运行，每个 PR 多一次真实运行和录制。先用实验量出来，不靠猜（参照 018 的做法）。
- **先做哪一层？** 我的倾向：先做 PR 层的 verify 和证据，因为它直接给到“人看证据”这个目标，而且 0.16 刚把位置留好；票层的验收按 018 的建议先做一次正向试验。
