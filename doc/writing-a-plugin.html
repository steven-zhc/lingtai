Change what a pass does

Lingtai walks a ticket through ten steps. What happens at each of them is yours to decide — you write it as a plugin and declare it in your recipe. This page starts from the thing you want, not from the shape of the code.

Most of those already exist — you declare them in your recipe and write no code at all. You write a plugin when the thing you want is not on this list.

One want, all the way through

“I want a Slack message when a ticket lands.”

Nothing that exists does this, so it is a plugin. It runs for effect after the pass has come to rest — that is the end step — and what you want to say depends on how the ticket ended, which end is the only step that knows.

export const slack = definePlugin("slack", {
  // what a recipe may write
  fields: {
    slack: z.strictObject({
      channel: z.string(),
      only: z.enum(["landed", "everything"]).default("landed"),
    }),
  },

  // where you run, and what you do there
  at: {
    end: async ({ outcome, context, actions }) => {
      const { channel, only } = read(actions);
      if (only === "landed" && outcome !== "landed") return { ending: "passed" };
      await post(channel, `${context.ticket} ${outcome}`);
      return { ending: "passed" };
    },
  },
});

Then in your recipe:

end:
  - name: tell the team
    slack:
      channel: "#releases"
      only: landed

The key you write — slack: — is what says which plugin this is. And at is what says where you are allowed to write it: declare this one at build and the recipe is refused, because it has no function for build.

What you tell the pass when you are done

Four things any step can say, and two more where they mean something.

you sayand it means
passedcarry on
helda person is needed, and here is the question to ask them
did-not-finishyou could not tell — you crashed, timed out, never got an answer
never-ranyou did not start at all
refusedyou read it and it is wrong. Only at the three that can stop the pass
routedgo here next. Only at proposed

Refused and did-not-finish are the pair to get right. “I read it and it is wrong” buys the agent another round to fix it. “I could not read it” does not — there is nothing for the agent to fix, and sending it anyway spends money repairing a defect that is not in the diff.

The one mistake worth warning about twice

Where a refusal goes is also yours

And the one thing that stays ours.

At proposed, what you return is the decision. A project that wants to look at every refusal itself, instead of paying for another round:

proposed:
  - name: everything comes to me
    judge: always-waiting

What you do not choose is what it costs. Sending the work back spends another round; your recipe says how many rounds a pass may buy and how many passes a ticket may buy. When there is no budget left the pass comes to you anyway — and it tells you which limit ran out, rather than quietly doing something else.

That is the one thing that cannot be yours. A plugin free to send the work anywhere can loop for ever, and the bill is real. Coming to you is the one destination that costs nothing, which is why it is the answer both when you ask for it and when the money runs out.

Turning it on

Five steps, and the fourth is the one people get wrong.

  1. Write it

    A schema for what your recipe may say, and an at for where you run.

  2. Register it

    Add it to the plugin set. What is not in it is not a plugin, and a recipe naming it is refused as an unknown key.

    Plugins are code in the Lingtai tree today — there is no installing one from elsewhere yet.

  3. Declare it in your recipe

    At a step your at covers. Your recipe is ~/.lingtai/<project>/recipe.yml — one per project, on the machine that runs the work, not in your repository.

  4. Restart — and only step 2 needs it

    Editing your recipe never needs a restart. It is read fresh on every pass; change it and the next one sees it.

    New code does. The daemon holds the code it started with. So if you declare a plugin it has not loaded, every pass is refused until it restarts — which looks like the machine has died. Land the code, restart, then edit the recipe.

  5. Watch one go through

    lingtai attach <runId>, or the run log on the ticket's page.

If it does not work

what happenedwhat it means
“not a plugin” You did not register it, or you misspelled the key.
“declared at claim, which it does not implement” You put it at a step your at does not cover. The message tells you which steps it does serve.
the whole recipe is refused, every pass You edited the recipe before restarting. The daemon does not know this plugin yet.
it runs twice That is a fix round — a pass can visit a step more than once. Look at the history you were handed if you need to tell which visit you are on.
it is declared and nothing happens This should be impossible: a plugin with no function for a step is refused before the pass starts, never silently skipped.
