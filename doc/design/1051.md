# Design: #1051, the projection runner as an Effect

## 1. What the ticket assumes that is not on `HEAD`

The ticket was written against ES3-3 as a draft, and three of the things it calls on are not reachable from `packages/projector`:

- **`follow`** has the signature `follow(options: FollowOptions, cell: FollowCell): Effect<void>` (`packages/event-store/src/subscribe.ts:155`). It returns no caught-up signal. The caller owns the `FollowCell` (`subscribe.ts:105-109`) and passes in `caughtUp: { resolve, reject }`. `follow` always calls `reject(new Error('subscription stopped before it caught up'))` and sets `cell.stopped = true` in its `ensuring` (`subscribe.ts:269-276`). `follow` is exported from the barrel (`packages/event-store/src/index.ts:117`) and from `@lingtai/event-store/subscribe`.
- **`fromPromiseWaker`** exists at `packages/event-store/src/store-face.ts:285`, but nothing exports it. `index.ts:105-116` lists `fromPromiseStore` and not the waker lift, and `store-face.ts` has no subpath in `package.json` `exports`.
- **`processEvents`** exists at `packages/event-store/src/choose.ts:216` and is not re-exported. `index.ts:15` imports it for its own use only. **The process waker is not exposed at all.** `deferredWakerPort` (`choose.ts:271-273`) is private, and its only use is inside `deferredLog()`'s promise `waker` (`choose.ts:283`).

**Decision: add three exports to `@lingtai/event-store`. Do not copy them into the projector.**

- In `choose.ts`, add `export function processWaker(name?: string): WakerPort { return deferredWakerPort(Effect.map(process_.get(), (o) => o.wake(name))) }`. That is the expression `deferredLog` already uses, given a name.
- Have `deferredLog().waker` call it.
- Re-export `processEvents`, `processWaker` and `fromPromiseWaker` from `index.ts`.

The alternatives are worse:

- A local copy of `fromPromiseWaker` would be a second implementation of the waker contract.
- `fromPromiseWaker(log.waker(name))` over the process log is a lift of the process's own port. That is the Effect → face → Effect round trip `packages/projector/src/store-face.ts:10-13` forbids (*"A moved caller is never handed a face"*).

This widens the ticket's `git diff --stat` box by `packages/event-store/src/{choose,index}.ts`. Say so in the commit body. Add no `async`, and add no `run` outside a listed face.

Reach the process ports the way `projection.ts:192` reaches the log today: `Effect.promise(() => import('@lingtai/event-store'))`, inside the Effect and only when the port is missing. The file's own header gives the reason (`projection.ts:28-34`): *"the process-wide log is reached for only when nobody supplied one"*. Import `follow` statically from `@lingtai/event-store/subscribe`, as `subscribe` is imported now (`:36`). That satisfies the Done-when item that says *imports `follow` from `@lingtai/event-store`*.

## 2. Where the pieces go

- **`projection.ts`** holds the following, so that `createProjectionRunner(` stays in exactly one `src/` file:
  - the `ProjectionRunnerPort` type (Effect methods);
  - `makeRunner(options)`;
  - `promiseRunner(r)`;
  - `createProjectionRunner`.
- **`runner-face.ts`** holds the six faces. Each one is literally `return Effect.runPromise(r.start())`, and so on. The ratchet refuses a face whose body is anything else (`packages/domain/unit/effect-ratchet.test.ts:205-212`). It imports only the port type from `projection.ts`.
- **`makeRunner` returns a plain object built synchronously, not an `Effect<Runner>`.** `createProjectionRunner` is synchronous, and a `runSync` there would be a counted `run`.

## 3. Runner state is plain fields, not `Ref`s

`promiseRunner`'s `failure` and `running` are synchronous getters that the daemon reads (`packages/daemon/src/daemon.ts:266-274`). So the state is one mutable record:

- `failure`
- `cursor`
- `cell: FollowCell | null`
- `scope: Scope.Closeable | null`

This is the same pattern as `FollowCell` itself. `running` is `cell !== null && !cell.stopped`, which is what `subscription.stopped` gave before (`projection.ts:220-222`). The ticket's *keep them in `Ref`s* is replaced by this, and the commit should say why.

## 4. Following

`startFollowing` is the local function renamed, so it no longer collides with the imported `follow`.

1. Resolve the two ports:
   - `options.store` → `fromPromiseStore`, else `options.log?.store` → `fromPromiseStore`, else `processEvents`;
   - the waker likewise, with `fromPromiseWaker(options.waker ?? options.log.waker(name))`, else `processWaker(\`lingtai-projection-${name}\`)`.
2. Read `checkpoint`, and set `cursor` from it.
3. Make a `Deferred<void>` for caught-up. Build the cell with `resolve`/`reject` completing that deferred, the way `store-face.ts:288-292` does with `Deferred.makeUnsafe`/`doneUnsafe`.
4. Run `Scope.make()`, then `Effect.forkIn(follow({ …, onBatch: commitBatch, onError }, cell), scope)`.
5. Await the deferred. **If the await fails or is interrupted, close the scope before propagating.** A `start` that never caught up must not leave a fiber behind.

`onError` sets `state.failure = error` when `phase === 'handler'`, and then calls `options.onError?.(error, phase)`. `follow` hands it `failed.cause`, which is `Cause.squash` of the reducer's die (`subscribe.ts:142`, `:260`). So `failure` is the reducer's own error, and a refused `advance`'s `CheckpointRewoundError` arrives the same way.

`start` still rejects with *"subscription stopped before it caught up"* when the first batch poisons. That is today's behaviour through `sub.caughtUp()` (`projection.ts:211`). Keep it, and do not swap in the reducer's error. The daemon reads `runner.failure` for that (`daemon.ts:266-274`).

`stop` takes the scope, clears `state.scope`, and runs `Scope.close(scope, Exit.void)`. That interrupts the fiber and waits for it, and the batch in flight finishes first because it is uninterruptible (`subscribe.ts:169-181`). The `pending`/`inflight` set (`projection.ts:174-184`) goes. A nudge-driven drain now runs on `follow`'s one fiber (`subscribe.ts:200`, *"Runs on the loop's fiber, never beside it"*), so there is nothing beside it to track.

`commitBatch` sets `cursor = last.seq` only after `transact` succeeds, as at `:166`.

## 5. The landing store

When `into` is absent, build a `closableOnceEffect(openProjections(url ? { url } : {}), (p) => p.close(), …)` once in `makeRunner`. This helper is exported from `@lingtai/event-store` (`index.ts:29-36`), and `packages/projector/src/choose.ts:99-103` already uses it. It gives:

- *racing first callers open once*;
- a `close()` with nothing opened that opens nothing, which `projection.ts:278-281` requires.

When `into` is given, every use is `Effect.succeed(into)`, and `close()` leaves it alone.

## 6. Faces file

- Add the six `runner*Face` entries in sorted order, with the ticket's `why`.
- Delete `shapeInFace` (`shape.ts:213-216`) and its entry. First grep the repository for `shapeInFace`: the runner is believed to be its only caller.
- Rewrite `projectionStore`'s `why`, because it still names *"the runner (projection.ts)"* (`effect-ratchet.faces.json:288`). Its one remaining caller is `the-written-choice.test.ts`.
- `projectionLag`/`readLag` stay listed. They are the only `runPromise` calls left in `projection.ts`, so `run` stays 0.

## 7. Tests

- **`runner-stop-waits.test.ts`**: change only `into: makeSqliteProjections(db)`. The promise `store` and `waker` stay, and now exercise the lifts.
- **New unit test for the dying reducer**:
  - a promise `EventStore` whose `readAll` serves seq 1 and seq 2, run with `batchSize: 1`;
  - a reducer that counts its calls and `Effect.die(e)` on the first one.
  - Assert:
    - `start()` rejects;
    - `failure === e`;
    - `onError` was called once, with `(e, 'handler')`;
    - `running === false`;
    - the reducer's count is 1 after a short wait;
    - `checkpoint` is still `0n`.

  The count of 1 is what shows the runner stopped instead of reconnecting.

These two unit tests stand in for the integration files named in the ticket. `sqlite.test.ts` and `follows-a-file.test.ts` are small enough to run on their own inside the pass; the Postgres files are not.

## 8. Settled by the log

None of this changes what is appended. A poisoned projection is still visible as the daemon's own reaction to `runner.failure` (`daemon.ts:246-251`). There is no new event to name.
