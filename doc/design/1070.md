# #1070: design note

## The worktree is not the ticket's `main`

DAEMON-1a has landed here. `packages/daemon/src/in-flight.ts` exists, `work-loop.ts` is 606 lines, and the ticket's line numbers are stale. Find things by name instead: `drain` is the `async function drain`, and `start` and `stop` are the object methods near the end of the file. `headSeq` is the last function in the file. `effect-ratchet.baseline.json:10` reads `"packages/daemon": { "async": 54, "run": 0 }`, so removing four `async` gives the ticket's 50. The `deliverFace` entry's `why` (`effect-ratchet.faces.json:24`) cites `work-loop.ts:606`, which is stale too, and the ticket's rewrite replaces it.

## The one decision: a look runs on its own root fiber, started by a synchronous `kick`

Today `pump(reason)` is synchronous and returns a promise. It is called from four places: `onEvent`, `started`'s settle, the sweep, and `start`. Keep that split. Do not turn the look into an Effect that callers fork:

- **`kick(reason): Promise<void>`** is synchronous, and it is today's `pump` body:
  - if `running`, it sets `again` and returns `lookInFlight ?? Promise.resolve()`;
  - otherwise it sets `running` and starts the look with `Effect.runPromiseWith(services)(drain(reason))`, then `.finally(() => { running = false; lookInFlight = null })`, then `passesInFlight.track(look)`.
- **`pump(reason): Effect<void>`** is `Effect.promise(() => kick(reason))`. Only `start` uses it, for the startup look.

**Why a root fiber and not `forkIn` or `forkChild`:**

- `InFlight.track` takes a `Promise` (`in-flight.ts:14`).
- Any `fork` from inside `onEvent` makes the look a child of the `follow` fiber. The ticket forbids exactly that: closing the following scope would interrupt the look.
- `runPromiseWith` starts a fiber that nothing in the loop owns. Interrupting whoever awaits its promise abandons the wait and never touches the look. That is the property the drain needs (0030 §1).
- The ratchet does not count it: `RUN = /^run[A-Z](?!\w*With$)/` (`packages/domain/unit/effect-ratchet.test.ts:70`). `runPromiseWith` is the same services-carrying run as `schedule.ts:295`. The ticket's `runForkWith` for the settle pump is satisfied by `started` calling `kick('completion')`: one starter, also uncounted.

**`services`** is a `let services: Context<never>`. `start` assigns it with `yield* Effect.context<never>()` before it forks `follow`. Nothing can call `kick` before that line, because `onEvent`, `started` and the sweep all exist only after it.

## `drain` as an Effect

`drain` is an `Effect.gen` with the same loop, the same order, the same wording and the same two catch levels.

- Lift each promise callback with **`Effect.tryPromise({ try: () => …, catch: (e) => e })`**. Do not use the one-argument form: Effect 4 wraps that failure in its own error type, and `(err as Error).message` would then print its message instead of the pass's. `store-face.ts:301-307` (`lift`) does it this way.
- `try` also catches a callback that throws synchronously, which today's `await` caught too.
- An absent `shutdown` or `paused` is `Effect.succeed(undefined)`.
- `onShutdown?.(why)` stays a synchronous call inside the generator, after `stopped = true`.

## `start` and `stop`

**`start`:**

1. `services`, then the head (`Effect.promise` over `withDaemonStore`).
2. **If `stopped`, return.** A Ctrl+C can reach the host's drain while the head read is in flight, and a scope created after that `stop` would never be closed. The ticket names only the check after the startup look; this check is the same rule one step earlier.
3. `Scope.makeUnsafe()` into a field, and the `FollowCell` as `projection.ts:238-246` builds it. A `caughtUp` with no-op `resolve`/`reject` is enough, because the loop never waits for catch-up. Then `Effect.forkIn(follow({ fromSeq, events, waker, onEvent, onError }, cell), scope)`.
   - The ports are `processEvents` (an Effect, `choose.ts:216`) and `processWaker('lingtai-daemon')` (`choose.ts:277`).
   - When `options.eventLog` is passed, use `fromPromiseStore(eventLog.store)` and `fromPromiseWaker(eventLog.waker('lingtai-daemon'))` instead (`store-face.ts:73`, `:283`).
   - The unit tests' fake waker, `{ open: () => ({ ready: Promise.resolve(), close() {} }) }` (`work-loop-stop.test.ts:15-24`), goes through `fromPromiseWaker` unchanged.
   - Import `follow` and `FollowCell` from `@lingtai/event-store/subscribe` (`packages/event-store/package.json:14`).
4. `yield* pump('startup')`.
5. **If `stopped`, return.**
6. If `every > 0`, fork the sweep into the same scope as `Effect.forever(Effect.sleep(every).pipe(Effect.andThen(Effect.sync(() => void kick('sweep')))))`.

The sweep fires and forgets, as `setInterval(() => void pump('sweep'))` does today. It never waits on a look, so the sweep fiber is only ever a timer, and closing the scope interrupts nothing but a sleep.

**`stop`:**

1. `stopped = true`.
2. If the scope exists, `Scope.close(scope, Exit.void)`. That interrupts `follow`, which lets an `onEvent` already running finish, since it is uninterruptible (`subscribe.ts:187`), and it interrupts the sweep. A second `stop` closing a closed scope is harmless.
3. `yield* passesInFlight.settled()`, with no timeout.

**A stop during start**, which the ticket's test holds:

- The startup look reads a shutdown, sets `stopped` and calls `onShutdown`. The host's drain then calls the `stop` face on a fiber of its own.
- That `stop` closes the scope and waits on `settled()`. The set holds the startup look, which returns as soon as `onShutdown` does.
- `start`'s `pump` then resolves, sees `stopped` and forks nothing.
- There is no deadlock: `onShutdown` returns `void` and nothing inside the look awaits `stop`.

## The `Effect.sleep` timer is ref'd, and that is the test's handle

The ticket's claim is that nothing keeps a stopped daemon process alive (`apps/cli/src/entry.ts:55` exits by `process.exitCode`). Behaviour alone cannot see a stray sweep after a stop: it kicks a look that breaks at `if (stopped) break` before calling `shutdown`, `paused` or `pass`.

So the *stop during start* and *after an ordinary stop* tests measure the claim itself. They compare `process.getActiveResourcesInfo().filter((r) => r === 'Timeout').length` before `start()` and after `stop()`, with `sweepMs` large (say `60_000`), so that a stray sweep would be a pending ref'd timer.

`getActiveResourcesInfo` lists only what holds the event loop open. The subscriber timeout stays `setTimeout(…).unref()` (`work-loop.ts:488` region), so it does not count. Use no subscribers in those tests anyway.

The `follow` fiber is checked behaviourally:

1. Append a trigger event (`COMPLETION_EVENTS[0]`) to the memory store after `stop()`.
2. Wait a few ticks.
3. Assert that a subscriber's `deliver` was not called.

## The two "never interrupted" tests

- Make the test's pass promise with `Effect.runPromise(Deferred.await(d).pipe(Effect.onInterrupt(() => Effect.sync(() => { interrupted = true }))))`. The ratchet counts runs in `src/` only.
- The `started` test hands that promise to `started` inside `pass`. The look test has `pass` itself await it.
- Both then call `stop()`, assert it is still pending after a few ticks, complete `d`, await `stop()`, and assert `interrupted === false`.
- No timers: use `await new Promise(setImmediate)` or a few microtask turns, not `setTimeout`.

Put these four tests in a new file (`unit/work-loop-effect.test.ts`) over `makeWorkLoop`, running `port.start()` and `port.stop()` with `Effect.runPromise`. Leave the existing three test files untouched.

## Faces and deletions

- `createWorkLoop` returns the getters plus `start: () => workLoopStartFace(port)` and `stop: () => workLoopStopFace(port)`.
- Each face body is exactly `return Effect.runPromise(port.start())` (or `port.stop()`). The ratchet refuses a face with any other body (`effect-ratchet.test.ts:209-230`).
- Delete `inFlightSettledFace` from `in-flight.ts`, and delete its `faces.json` entry (`effect-ratchet.faces.json:189-193`).
- Remove `subscribe`, `Subscription` and `processLog` from the import at `work-loop.ts:90`, as well as the `sweep`/`subscription` fields and `clearInterval`.

## The one check that is not a unit test

`integration/work-loop.test.ts` is the ticket's gate, and it runs on SQLite. Run it as `pnpm exec vitest run --project integration packages/daemon/integration/work-loop.test.ts`, which takes seconds, not the whole integration half.
