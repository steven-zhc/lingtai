# Design: #1074 — the control stream's reads and appends become Effects

Everything here is in `packages/daemon/src/control.ts` and `guard.ts`. The ticket's line numbers still hold at `215a6c3f`. The notes below cover only what the ticket does not settle on its own.

## 1. Choose the events port per call, inside the attempt

Use one internal helper. It must be an `Effect`, not a value worked out once when the function is called:

```ts
const portFor = (store: EventStore): Effect.Effect<EventsPort> =>
  store === eventStore ? processEvents : Effect.succeed(fromPromiseStore(store))
```

- **Why the identity check covers an absent store.** Every verb's parameter defaults to `eventStore` (for example `control.ts:195`). That is the barrel's `promiseStore(deferredEvents(processEvents))` (`event-store/src/index.ts:95`). So `store === eventStore` is true exactly when the caller passed nothing, or passed the process store itself.
- **There is precedent.** `failure-recorder.ts:26-29` does the same: *"Resolved inside each attempt: opening the process store is itself an IO that can be refused"*. So does `work-loop.ts:584`.
- **What the loops must do.** `requestShutdownUnlessStandingEffect` and `recordStartEffect` yield `portFor(store)` and read `head` from that port inside each attempt.
- **Imports.** Take `processEvents`, `fromPromiseStore` and `ConcurrencyError` from `'@lingtai/event-store'`, the barrel (`index.ts:26`, `:113`). A unit test's `vi.mock('@lingtai/event-store', …)` only reaches imports that go through the barrel.

## 2. `readControlEffect` still hands `readThroughSnapshot` the promise `eventStore`, and that is accepted

`readThroughSnapshot` takes a promise store: `store: Pick<EventStore, 'readTypes' | 'read'>` (`event-store/src/snapshot-read.ts:40-41`). So the read goes through `eventStore`'s faces, which is the Effect → face → Effect hop that `store-face.ts:11-14` warns about. It is unavoidable without changing that signature, and `packages/event-store` is outside this ticket's diff stat. `conduct.ts:1022` makes the same call today.

**Do not "fix" this here.** It is the port-based `readThroughSnapshot`'s ticket, not this one.

Keep the snapshot rule exactly as it is:

- `readControlEffect` passes `log.snapshots` only when `store === undefined` (`control.ts:113`).
- The two loops and `raiseDayCeiling` pass `store === eventStore ? log.snapshots : undefined` (`:167`, `:234`, `:279`).
- `control-snapshot.test.ts:13-22` mocks `log.snapshots` to throw. Any read that touches it eagerly with a store passed in fails that test.

## 3. Error channels

- **Reads.** `readThroughSnapshot`'s error is `unknown` (`snapshot-read.ts:46`), and `readControlEffect` keeps it.
  - The guard maps it with `asError` (`guard.ts:73`), so `lockedBy` still sees an `Error` (`guard.ts:156`, `:176`).
  - `raiseDayCeiling` is already `Effect.Effect<Raising, unknown>` (`control.ts:162`), so its type does not move.
- **The loops.** Retry on the **append alone**. Today the `try` wraps only `append` (`:236-241`, `:282-292`); the `head` and `readControl` reads sit outside it, so a failed read rejects without a retry. Keep that:

  ```ts
  appendEffect(…).pipe(Effect.catchTag('ConcurrencyError', (e) => attempt >= 4 ? Effect.fail(e) : loop(attempt + 1)))
  ```

  `_tag` exists for exactly this (`event-store.ts:64`). A non-`ConcurrencyError` from `fromPromiseStore`'s `append` is already a defect (`store-face.ts:83-85`), so it never reaches the `catchTag`.
- **Appends outside the loops.** `requestShutdown`, `resumeConductor` and `requestRun` call `append` with no `at`. That reads the head and appends with no retry (`:134-138`). A `ConcurrencyError` there fails the Effect and the face rejects with it, as today. Do not add a retry.

## 4. What does not change, though the ticket's Shape suggests it

**`requestsBetween` and `transitionProject` call none of the ten.**

- `requestsBetween` lifts `store.readTypes` (`:347`).
- `transitionProject` lifts `store.read` and `store.append` on a project stream (`:604-605`, `:621-623`).

Leave both alone. In `raiseDayCeiling`, only the `readControl` lift (`:166-169`) goes; its `store.head` and `store.append` lifts (`:165`, `:178`) are not around a control function, and rewriting them is not asked for.

**`daemon.ts:199` stays as it is.** It is `Effect.promise(options.watermark ?? (() => controlWatermark()))`, and `daemon.ts` is outside the diff stat. So:

- `controlWatermark`'s face `why` must also name `packages/daemon (daemon.ts watermark default)`, beside the apps/cli callers;
- `readState`'s `why` loses *"packages/daemon (control)"*, but `controlWatermark`'s does not lose packages/daemon.

**`index.ts` is not in the diff stat**, so the `…Effect` forms are exported from `control.ts` only. Every caller the ticket lists keeps the face it imports today (`index.ts:49-65`).

## 5. The three new unit tests

All three are runnable under `HOME=/nonexistent pnpm test`.

- **`inFlightEffect` answers `[]` on a defect.** `vi.mock('@lingtai/projector', …)` replaces `readTasksEffect` (exported at `projector/src/index.ts:109`) with `() => Effect.die(new Error('x'))`. Assert `[]`.
  - Use `Effect.catchCause` with `Cause.hasInterruptsOnly` (or the equivalent) so that an interrupt is not answered. The projector's store failures are defects (`task-view.ts:1016-1026` goes through `withStoreEffect`), which is why `Effect.catch` is not enough.
- **No store means `processEvents`, not `fromPromiseStore`.** Use `requestRunEffect` (or `resumeConductorEffect`), **not `recordStartEffect`**.
  - The loops also call `readControlEffect`, whose default read goes through the real `eventStore` face (§2). That would open the real `processEvents` under `HOME=/nonexistent`, which a mock of the `processEvents` export cannot intercept, because `eventStore` was built from the real one at import (`index.ts:95`).
  - Mock the barrel: `processEvents` becomes `Effect.succeed(<a port over a memory store>)` (build it with `fromPromiseStore(createMemoryEventStore())` *inside the mock factory*, from the real module), and `fromPromiseStore` becomes a `vi.fn` wrapping the real one.
  - Assert that the event landed in that memory store and that the spy was not called for the verb's own append.
- **`recordStartEffect` retries only on `ConcurrencyError`.**
  - Build a `createMemoryEventStore()` with `append` overridden to reject with `new Error('disk')` and count its calls.
  - Run `recordStartEffect(…, store)` with `Effect.exit`. Assert a `Die` and exactly one append.
  - Add a second case where the override rejects with `ConcurrencyError` every time. Assert five appends and a `Fail` whose error is that `ConcurrencyError`. That pins the `attempt >= 4` bound from both sides.

## 6. Verification reach

`shutdown.test.ts` is integration (`packages/daemon/integration/`). Its no-append-over-a-standing-request and since-watermark claims for these two loops can be run on their own, as the ticket's `Done when` asks: it runs on the SQLite default and does not need the 803-second half.

The unit-level stand-ins are:

- the existing `start-after.test.ts` and `control-head.test.ts`;
- the retry test in §5.

Whether a production start obeyed or ended a request is settled in the log by the order of `ConductorShutdownRequested.version` against the `ConductorStarted` that follows it on `ctl-conductor`, not by these tests.
