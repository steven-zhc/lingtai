# Design note: #1231, the landing line and who decided on `/landed`

The ticket already gives the outline. This note covers three things it leaves open: where the line is computed, how `onSha` gets to the board, and how stored `/landed` rows that predate this change are read.

## 1. Compute the line in `readAttempts`, not in the component

There are two ways onto the attempt tab, and both must show the line:

- `loadTask` serves the task page's default tab (`apps/board/src/app/task/[id]/page.tsx:35`).
- `loadAttemptTab` serves one attempt's page (`apps/board/src/lib/task.ts:2071`). Its comment says *"It never calls `loadTask`"*.

Both read `readAttempts`. That function already holds every fact the line needs:

- `ticketState`, returned at `task.ts:1813`, whose lifecycle carries `{ status: 'landed'; mergeCommit; base }` (`packages/domain/src/ticket.ts:175`).
- `landed = standing.state === 'landed'` and `last`, at `task.ts:1776-1777`. That block already treats the last attempt specially: *"Only the last, and `over` only where the item landed"*.

So the work goes in that same `.map` at `task.ts:1779`. Add an optional `landing` field to `AttemptView` (`task.ts:289`). Set it on index `last`, and only when `landed && ticketState.lifecycle.status === 'landed'`. Leave it `null` everywhere else. Neither loader then needs its own copy of the rule.

The tab only reads `run.landing`. When it is null, nothing is drawn. Draw the line as a sibling `<p>` straight after the `ameta` paragraph (`attempt-tab.tsx:105-109`). Give it its own small component file next to `evidence.tsx`.

## 2. `StepVerdict` has to carry `onSha`

`presentAttempt` reduces `onSha` to a boolean and drops the sha:

```ts
return { step: s.step, state: s.verdict, stale, evidence: s.evidence, findings: [...s.findings] }
```

That is at `task.ts:1180`. The field it builds is `StepVerdict.stale` (`task.ts:156`): *"True when the verdict was made against a commit that is no longer the head."* The line needs the sha itself (`review ✓ on f3fa0b6`), so add `onSha: string | null` to `StepVerdict` and pass through `s.onSha`. Every other reader of `stale` stays as it is.

Do **not** use `stale` as a stand-in for "the sha differs". The comment at `task.ts:1174-1175` says steps before `build` are never stale: *"their `onSha` is the commit they started on and is never the final head"*. The line starts at `build`, so that rule does not reach it. Even so, the pure function should compare `onSha` with `headSha` directly. That way it does not inherit a rule written for a different purpose.

## 3. The pure function

Put it in a new file, `apps/board/src/lib/landing-line.ts`, with this input:

```
{ steps: readonly StepVerdict[], headSha: string | null, mergeCommit: string }
```

It returns `{ merge, items: { step, ok, state, onSha: string | null }[], flaky: { count, tests: string[] } }`. Rules:

- **Grouping.** A step name is `step.slice(0, step.indexOf(':'))`, as at `task.ts:1173`. Keep only steps at or after `STEPS.indexOf('build')`, in `STEPS` order. Drop the synthetic `running` entry pushed at `task.ts:1183`. A landed attempt has none, but do not rely on that.
- **`ok` and the state word.** `ok` is true only when every action of the step has `state === 'passed'`. Otherwise the item shows the first non-passed action's `state` word.
- **The step's sha.** Use the actions' `onSha` when they all agree. Set it to `null` when it equals `headSha`, or when any action has `onSha` null (a landing from before shas were recorded). If a step's actions disagree, show the first action's sha that differs from the head. This case should not happen, and this rule is a choice made here, not something the ticket asks for.
- **Flaky tests.** Count findings on `build:*` actions where `isFlakyFinding(f)` holds. It is exported from `@lingtai/domain` (`packages/domain/src/failure/flaky.ts:32`, re-exported at `packages/domain/src/index.ts:2`). Name the tests with `flakyEntryOf(f.claim)` from the same file (`:24`), never by slicing the prefix yourself.

The component turns the result into `<Link href="/backlog">` with a `title` listing the entries. It uses the signal colour, the same class the bar uses for a warning; check the mock for which one. The backlog link already exists in this form at `evidence.tsx:123`.

Leave the merge sha unlinked unless the mock links it. If it does, build the URL the way `landed/view.tsx:95` builds `commit`.

Unit tests go in `apps/board/unit/` and call the function directly, with no store. Cover the five cases the ticket lists, plus a step whose actions disagree on sha.

## 4. `ReportWait.by` and `onSha`, and the stored rows that lack them

In `packages/projector/src/ticket-report.ts`:

- **Type.** Add `by: string | null` and `onSha: string | null` to `ReportWait` (`:88`).
- **Writing.** `reportWaitOf` (`:280`) writes `w.resolution?.by ?? null`. For `onSha`, narrow on `_tag` to `Approve | GrantFixRound` and read `.onSha`, else `null`. Both resolution shapes are at `packages/domain/src/wait.ts:246-248`. Narrow on `_tag`; do not use `'onSha' in r`.
- **Reading.** The reader does `waits: json(row.waits, [])` (`:224`). A row stored before this change therefore yields `by: undefined`, not `null`, despite the type. Normalise at that read: map each wait to `{ ...w, by: w.by ?? null, onSha: w.onSha ?? null }`. Then `view.tsx` only ever sees `null`, and the ticket's edge (*"read `null` until … rebuild"*) is true. Without this, `Notes` would print `— undefined`.

`Notes` (`landed/view.tsx:103-111`) appends a muted `<span>` after `moveTitle(...)`:

- `— {by}, on {onSha.slice(0,7)}` when both are set.
- `— {by}` when only `by` is set.
- Nothing when `by` is null, so old rows read as they do today.

Add a muted class next to `.ld-decision` (`globals.css:3085`).

This change adds no new IO and no `async` function, because both values come from data already loaded. The Effect ratchet does not move.

## What nothing in a pass can verify

Projecting `ticket_report` into Postgres is integration-only. The unit claim that stands in for it is the `reportWaitOf` test the ticket asks for, plus a unit test of the read normalisation on a stored wait with no `by`/`onSha`. If `reportWaitOf` is not exported, export it for the test; do not test it through the projection.

The by-eye check against `doc/design/what-landed.html` is for a person on the running board, not something `pnpm test` covers.
