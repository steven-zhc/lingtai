# Design note: #1261, publishing the split's children, keeping the parent's Done when, splitting at most once

Most of the shape is in the ticket. This note covers the four places where the code as it stands forces a choice the ticket does not make. Each choice is made below.

## 1. Once per root must not refuse a Retry of the same split

Today a Retry is a second call to the same writer, and **each call appends its own `SplitStarted`**. The writer calls `note('SplitStarted', …)` unconditionally at `split-ticket.ts:258-262`. The first one is only special because it freezes the plan: `const first = events.find((e) => e.type === 'SplitStarted' && … waitId === waitId)` at `:234`. The module comment says *"The plan freezes at the first `SplitStarted` for the wait. Every later call uses that plan"* (`:9-10`), and the board's `splitCard` comment says *"Both start the same writer: the first call freezes `plan`… a retry sends none"* (`apps/board/src/app/actions.ts:965-966`).

Read literally, *"refuse when the stream already has a `SplitStarted`"* refuses every Retry. That also fails the ticket's own Done-when item *"a second run removes it from both and appends one `TicketSplit`"*. The rule is:

- **A split is spent by a `SplitStarted` whose `waitId` differs from `options.waitId`.** Such a split is refused with or without a `TicketSplit` after it. A `SplitStarted` for the same wait is this split resuming, and it passes.
- A `TicketSplit` for the same wait needs no new check. After `WaitResolved` the ticket is no longer `blocked` on that wait, and `:238-239` already refuses with *"is not waiting on … nothing was written"*.

Put the check after the lifecycle and plan checks and before the `SplitStarted` append, among the *"Refuse before writing"* checks (`:231-246`), and return it through `stop(...)` so the result has the same shape. The domain side:

- Add `ticketSplits: 1` to `BOUNDS` (`packages/domain/src/failure/respond.ts:579-590`).
- In `causeBoundsFor`, replace the literal `ticketSplits: { used: 0, allowed: 1 }` (`packages/conductor/src/proposed-route.ts:220`) with `allowed: BOUNDS.ticketSplits`. `boundsFromOffer`'s literal at `:233` stays an offer-derived room, as its neighbours are.
- Wiring `used` from the stream is not this ticket's. `actionFor`'s comment says *"nothing calls this yet — acting on a cause is #1258's"* (`respond.ts:910-911`).
- The count the writer itself uses is *distinct `waitId`s among `SplitStarted`*. If you want that count in domain for #1258 to reuse, put it there as a pure function over events.

## 2. The body-marker refusal has to read the parent's body

The writer promises *"no GitHub call until every check passed"* (`split-ticket.ts:228`). The marker check needs the parent's body, and the stream does not hold it. One `github.getIssue(options.issue)` read is allowed before `SplitStarted`. It is a read, so *"nothing written"* still holds.

- **If that read fails, refuse with nothing written** and append no `SplitFailed`. `SplitFailed` is a terminal event that pairs with a `SplitStarted`, and no `SplitStarted` exists yet. The comment at `:248` explains the same ordering for `since`.
- **Match the child marker exactly**: `/<!-- lingtai:split \S+ \S+ -->/`, which is the shape `splitMarker` produces (`:63-65`). A bare substring search for `lingtai:split` is wrong. The parent's own `## Split into` section is written with `upsertSection`, whose open marker is `<!-- lingtai:answer <key> -->` (`body-section.ts:12-14`). A key such as `split-into` must therefore never be read as a child marker. Add a test that splits a parent, then retries it, and shows the retry is not refused by its own section.

## 3. `covers` and `uncovered` are not in the plan the writer freezes

`SplitPlanInput` has `{ key, title, body, kind }` and `blockedBy` (`split-ticket.ts:56-59`). `SplitStarted.plan` is `z.strictObject({ children: z.array(ChildTicket), blockedBy })` (`packages/domain/src/events.ts:461-465`). `ChildTicket` is a plain `z.object` of those four fields (`packages/domain/src/split.ts:23`), so zod strips any `covers` key on parse. Only `TriagePlan` carries `covers` and `uncovered` (`split.ts:213-233`).

The decision:

- Add an optional `covers?: string[]` to the plan's child and an optional `uncovered?: string[]` to the plan, both in `SplitPlanInput` and in `SplitStarted.plan`. In `SplitStarted`, use a child schema that extends `ChildTicket` with `covers` optional. Do not edit `ChildTicket` itself, because other schemas use it.
- Optional means an old `SplitStarted` row still parses, so no upcast is needed.
- The frozen plan is what `## Split into` is written from, on the first call and on every retry.
- Absent `covers` renders as the child's line with no items under it, as the ticket's Null edge says. An absent or empty `uncovered` renders no *Not covered by any child:* line.
- The board's `splitCard` (`actions.ts:972-1003`) passes them through only when its plan carries them. This ticket does not add them to the board's form.

The section text must not contain `lingtai:answer`, or `upsertSection` throws (`body-section.ts:87-91`). Done-when item text is arbitrary person-written text, so `splitIntoSection` should render each item with that substring defused. One option is to break it with a zero-width space. Alternatively, let the step fail by name. Failing silently is not acceptable. Keep the `ifUnchanged` retry loop `writeDoneWhen` already has (`split-ticket.ts:362-381`), and only swap the pure function inside it.

## 4. Where the label is added and removed, and the step list

**Adding the label.** `writeChild` creates with `[child.kind, PUBLISHING_LABEL]`. The ticket's step 1 also says *"a child found by its marker that lacks the label while the split is not recorded gets it added"*. That conflicts with the edge *"a crash after the label removals and before `TicketSplit`: the next run finds the labels gone… appends `TicketSplit`"*: re-adding there would put the label back on every child only to remove it again. The rule that satisfies both:

- **`SplitChildWritten` proves attachment, not publication.** Add the label to any child lacking it unless the whole split is already on GitHub (every child recorded, attached, and every link and parent blocker present, read once before the first child). Then a crash after the removals puts nothing back, and a split left by the previous writer is relabelled before its remaining children are created.
- Removal only happens after `record the split`'s reads, which include the parent's blocked-by.
- After a create, read the labels back with `getIssue`, and `addLabels` if the label is missing. That covers the *label does not exist in the repository* edge without guessing what GitHub answers.
- If the create itself errors on the label, create the label and retry. This is the second answer the ticket asks the double to cover. It needs a `createLabel` on the client only if the double's error branch is built. If you build it, put it beside `removeLabel`.

**Removing the label.** Add a new `publish <key>` step per child, placed after `record the split`'s reads and before `end the wait`.

- Each step calls `removeLabel(n, PUBLISHING_LABEL)`, then `getIssue(n)` to check that the label is absent and that every other label is still there.
- Never touch `agent:hold`, and never call `setLabels`. `setLabels` *"Replaces the whole label set"* (`packages/github/src/client.ts:281-289`).
- `SplitClient`'s `Pick` (`split-ticket.ts:44-54`) gains `removeLabel` and `addLabels`.

**The step bookkeeping.** `record the split` returns `'not-reached'`, and `end the wait` marks `steps[i - 1]` done or failed (`:471`, `:478-479`, `:493-496`). That only works while the two steps are adjacent, and the publish steps now sit between them. Look up `record the split` by name rather than by `i - 1`. `stepNames` (`:162-172`) has to list the same sequence:

- `read GitHub`
- `write <key>` for each child
- `chain <ticket>←<blockedBy>` for each link
- `hold parent ← <key>` for each child
- `split into`, which replaces `done when`
- `record the split`
- `publish <key>` for each child
- `end the wait`

The board renders whatever names the result carries. No other source file names these steps (grep for `'record the split'` and `end the wait` outside `split-ticket.ts` finds nothing relevant).

## Smaller decisions

- **`PUBLISHING_LABEL`** lives in `@lingtai/domain`, beside the split schemas in `split.ts`, so `discover.ts` and the writer import one constant.
- **`skip: 'publishing'`** extends `SkipReason` (`packages/conductor/src/discover.ts:154`). Every consumer that switches on it needs the new case: `apps/cli/src/status.ts`, `apps/cli/src/cli.ts`, `packages/conductor/src/why-nothing-runs.ts`, `packages/conductor/src/blockers.ts`, `apps/board/src/lib/queued.ts`, `apps/board/src/lib/board.ts`. These are all the non-test files that name `'blocked-by'`. Where they group `blocked-by` as *comes back on its own*, `publishing` belongs in that group.
- **`removeLabel`** must URL-encode the name, because `lingtai:publishing` contains a colon. A 404 counts as success. It goes on both `GitHubClient` interfaces (the Effect one near `client.ts:297` and the promise one near `:410`), plus every test double that implements the interface; typecheck will list them.
- **The ratchet.** Write the new client method and the new steps as Effects, the same way `ensure` and `writeDoneWhen` are written. The promise-side client method is the one existing exception, because every client method has a promise twin. If the ratchet counts that twin, it is one `async` the baseline already accepts per method. Check `effect-ratchet.baseline.json` before and after, and if the count rises, write the method without `async`.
- **Delete `split-body.ts`** and its cases in `packages/conductor/unit/split-ticket.test.ts`, which are its only users per grep. `splitIntoSection` can live in `split-ticket.ts`, or in a new pure `split-into.ts` if its tests need to stand alone.

## What verifies it

All of this is checked by `packages/conductor/unit/split-ticket.test.ts`, using the GitHub double and `createMemoryEventStore()`; none of it needs `pnpm test:integration`.

- **Ordering** is asserted on the double's call log: every `removeLabel` index comes after the last `listBlockedBy(parent)` read-back and after the read-backs of `record the split`.
- **The crash after the removals** is set up with a double whose children already lack the label, every `SplitChildWritten` already on the stream, and no `TicketSplit`. Assert one `TicketSplit`, and assert that no `addLabels` call was made.
- **On the log**, the fact that settles a run is the `SplitFailed` `step` field: it names `publish <key>` or `split into`. That is what to quote when a real split is checked after merge.
