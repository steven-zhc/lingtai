# Design note for #1002: `service` and `upgrade` withdraw no drain

The ticket's Fix is the shape of this change. This note adds four things the ticket leaves open or contradicts itself on. Line numbers are from this worktree, at `512e87b3`, which is after #998 and #1001.

## 1. Adopting a drain is one rule in three places, keyed by `by` alone

`restart.ts:419` already has the rule: *"This person's own request is the one the start ends (0126), so it is exempt by `by` and by nothing else."* `service shutdown` and `upgrade` should copy its form. They should not grow a separate idea of "own":

- **The `service shutdown` drain** (`service.ts:1407-1424`). `ask` returns `Asking` (`packages/daemon/src/control.ts:208-212`), so `!asked.asked && asked.standing.by === by` means adopt, and `mine = asked.standing.version`. Any other `!asked.asked` is a refusal, with the remedy from (3). Do not change the order of the steps: the queue is still taken before anything is asked (#174, `service.ts:1363`).
- **`askAgain`** (`service.ts:1437-1447`) becomes `ask`, with the same three outcomes the ticket lists. When it adopts, it sets `mine = again.standing.version`. Do not check that the adopted version equals the old `mine`. A copy that recorded its start ended the old request, and a second command by this person may have asked a newer one since. Both of those are this person's, and both are obeyed.
- **The supervised path in `restart.ts`** (`restart.ts:1178-1188`). Once `liftAdopted` is gone, the comment at :1178-1180 is false and has to go too. The `drain` built at :1191-1193 from the adopted request's `timeoutMs` and `force` stays. It now describes the request that `service shutdown` adopts rather than one it re-asks. That is the same rule as before, *never this invocation's flags*.

`service`'s `by` is `options.by ?? human:$USER` (`service.ts:802`), and restart's is `human:$USER` (`restart.ts:1173`). That they match is what lets `service shutdown` adopt the request restart left standing. Keep both defaults as they are.

## 2. `shutdownStands`: the logic goes into a pure function, and a failed read refuses

The ticket is inconsistent about an unreadable control stream:

- **Fix** says *"A read that fails keeps today's rule (:1161-1168)"*. Today's rule logs a note and returns `false`, which means proceed (`service.ts:1163-1168`).
- **Edges** says *"a control stream that could not be read is never nothing stands"*.
- **Done when** says *"a failed read refuses"*.

**Decision: a failed read refuses.** #1001's last commit (`3e78fecc`, *"a control stream that cannot be read is a refusal, never nothing standing"*) made the same choice for `startRefusals` (`restart.ts:420-426`). The reason has changed since the old comment at `service.ts:1152-1154` was written: since #998 a start *ends* any request standing. A start made over a request nobody could read may therefore end somebody else's drain, and the start cannot see that it did. Delete that comment rather than reword it. The refusal should say what failed and point to `lingtai status`, as `restart.ts:422-424` does. There is no waiver. Nothing in the ticket asks for one, and a database that cannot be read is also one a daemon cannot conduct on.

**Shape:** `shutdownStands` is a closure inside the service command, so it cannot be unit-tested as it stands. Pull its decision out into an exported pure function that mirrors `startRefusals`:

```
standingRefusal({ by, standing: { by, reason } | null | { unread: string }, unloaded, verb })
  → { refuse: true, lines } | { refuse: false, note: string | null }
```

The closure keeps the read, with `.then(…, err => ({ unread }))` as at `restart.ts:535-538`, and does the printing. The Done-when unit tests target the pure function in a new `apps/cli/unit/service-standing.test.ts`, covering three cases:

- this person's own request gives one muted note and no refusal;
- a foreign request gives a refusal containing `starting a conductor (lingtai daemon) ends it`;
- `{ unread }` gives a refusal.

For the foreign remedy, reuse the wording of `FOREIGN_REMEDY` (`restart.ts:910`), or export that constant and share it. Two sentences saying the same thing drift apart.

With the pause choreography gone (`service.ts:1179-1238`), `options.pause` has no reader. Remove it from the interface (`service.ts:617-622`) and from `serviceOptions()` (`daemon.ts:82-85`). Check whether `daemon.ts:44`, `pausedSentence`, is still used elsewhere in that file before you remove any import. It is: at `daemon.ts:563`.

## 3. Sentences

Two sentences in `service.ts` rest on #159's *"a daemon reads nothing asked before it started"*. That is still true, but it is no longer the reason a start is refused:

- the doc comment on `ServiceOptions.shutdown` (:611-616);
- `service.ts:1170-1177`.

The reason now is that **a start ends the drain**, so starting over a foreign request is deciding for somebody else. Rewrite both on that ground. The drain's numbered doc comment (:1350-1359) also changes:

- Step 2 becomes "or this person's own, adopted".
- Step 5 becomes "the lock released; the request stands until the next start ends it, and `service start` by this person is not refused over it".

## 4. `upgrade-drain.ts`

- Delete `withdrawing`, and return `{ ok: true, after: async () => {} }` from both places that used it. Hoist that value into one module constant, such as `NOTHING_AFTER`. Two inline `async () => {}` count twice in the ratchet. One constant counts once and still comes in under the deleted `async` arrow inside `withdrawing`.
- Delete the module comment's two bullets (:6-21). Both argue from #159 that an old request may never be obeyed. Replace them with the 0126 reason: a request still standing has not been ended by a start, so whatever holds the lock started before it, or has not yet recorded its start.
- In the holder branch (:94-107): if `own` stands, `version = own.version` and nothing is appended. If it does not, `request` runs as today.
- The `theirs` refusal (:56-64) says *"it is theirs to lift"*. Replace that with the shared foreign remedy from (2).

## The ratchet and the tests

- **Ratchet.** Deleting `askAgain`'s withdraw, the three `.withdraw(…).catch` sites, `liftAdopted` (an `async function`) and the `withdraw` wiring arrows should lower `apps/cli.async` from 416 (`effect-ratchet.baseline.json:2`). Lower it to the number the red ratchet test reports, and do not add any `async`. The adopted branch in `ask` needs no new function. `askAgain` was already `async`, and it is rewritten in place.
- **Unit tests.** `apps/cli/unit/upgrade-drain.test.ts` builds an `UpgradeDrain` with `withdraw`, so each fixture loses that port. To assert that no path withdraws, the fake store's events must contain no `ConductorShutdownWithdrawn` after each path. Keep `apps/cli/unit/verbs-accept-refuse.test.ts` and the others that `grep` matched on `pause:` unless they actually pass `ServiceOptions.pause`. Most of them match a `lingtai pause` verb instead.
- **Integration tests.** `apps/cli/integration/service.test.ts` and `apps/cli/integration/restart.test.ts` both reference the withdrawal. Rewrite their scenes to the new rule, and do not run them. `pnpm typecheck` covers those files' types, and the unit test in (2) stands in for their behaviour: it is the one place the exemption rule can be checked before the merge.
- **Proof in the log.** For the post-merge check, the claim that a `service shutdown` followed by `service start` left nothing standing is settled by `ConductorStarted` (the #998 end of the request), with no `ConductorShutdownWithdrawn` in between for that `version`.
