## Where the suppression goes

The ticket's step 3 puts the read inside `reconcile`, but `reconcile` can only produce a report-once finding from a real directory. The two mystery pushes run after a `readdir` of `<home>/worktrees` (`packages/daemon/src/reconcile.ts:235`) and `<home>/runs` (`:348`). The repo's unit precedent passes `home: '/nonexistent/lingtai-home'` (`packages/daemon/unit/reconcile-ticket-version.test.ts:46`), which yields no orphans at all. So two of the "Done when" boxes can't be reached through `reconcile` in the unit half: *every finding suppressed → no `Reconciled`* and *read throws → appended unchanged*.

So split it in two, both exported from `reconcile.ts`:

- **`unreported(findings, earlier: readonly Envelope[] | null): Finding[]`**: pure, exactly as the ticket describes.
- **`withoutReported(store: Pick<EventStore, 'readTypes'>, findings, log): Promise<Finding[]>`**:
  - calls `store.readTypes(CONTROL_STREAM, ['Reconciled'])` inside its own `try`, turning a throw into `null`;
  - calls `unreported`;
  - writes the two log lines from the ticket;
  - returns what is left.

`reconcile` calls `withoutReported(store, findings, log)` right before `if (findings.length === 0) return []` (`:654`) and keeps working on what it returns. `findings` is a `const` that the GitHub half pushes onto (`:642`), so take the result into a new binding rather than splicing it.

The unit tests then work against `createMemoryEventStore()`, which implements `readTypes` (`packages/event-store/test/memory.ts:232`):

- Seed a `Reconciled` on `CONTROL_STREAM`. Hand in findings built with `once: true`, then assert on `stream` and `once`, never on the `actual` sentence.
- Spread the memory store with a `readTypes` that throws, the same way `reconcile-ticket-version.test.ts:57-71` overrides `append`.
- "Every finding suppressed" is `withoutReported` returning `[]`. That this means no append follows from the existing `:654` line, and the integration test the ticket asks for (written, not run) checks it end to end.

The `try` covers `readTypes` and nothing else. A decode failure inside `readTypes` counts as a failed read, but a bug in `unreported` must not be swallowed as one.

Order relative to the repair loop (`:656-715`) does not matter for correctness, because the loop only touches `released` and `removed` and never a `once` finding. It must still come before `:654`, so a start that finds only old mysteries returns before `store.head(CONTROL_STREAM)` (`:717`).
