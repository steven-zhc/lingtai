# Design: #1157, a refusal the sandbox caused reaches a person as `sandbox-refused`

## The ticket's premise that did not land: nothing puts the refusals on an outcome

The ticket says the refused hosts and the unavailable flag arrive "on the `StepOutcome`, put there from the run outcome and action result the S8 plumbing fills." The S8 plumbing does not fill them. #1164's design chose the opposite, and the code follows it:

- `doc/design/1164.md` says: *"Do not put a field on `RunOutcome` or on the action result."*
- The read happens only in `recordingWrap`'s finalizer, and the only thing it does with the read is append `SandboxConnectionsRefused` (`packages/conductor/src/sandbox-record.ts`, the `Effect.addFinalizer` in `recordingWrap`).
- `StepOutcome` is still `{ step, round, actions }` (`packages/domain/src/action.ts:246-250`).

`nextOf` stays pure over `StepOutcome`, as the ticket requires. So this ticket adds the field and fills it. There are two sources: one for the hosts and one for the unavailable flag.

### 1. `StepOutcome` gains one optional field

```
sandbox?: { refused?: string[]; unavailable?: string }
```

- **Leave it absent when there is nothing to say.** That gives today's outcome byte for byte, and it is the *Null or unknown* edge.
- **`refused`** holds the distinct non-telemetry hosts, as `host:port`, or `host` when the port is null.
  - An entry whose line did not parse (`host: null`, `line` kept; `packages/sandbox/src/refusals.ts:49-56`) is shown by its `line`.
  - **It counts.** It is a refusal that is not on §17's list, and the ticket's rule errs toward a person.
- **`unavailable`** is srt's sentence.
- **Old `StepEnded` events still decode**, because the field is optional: `StepEnded.outcome` is this schema (`events.ts:1379-1382`). No upcaster is needed. The catalogue changes, so regenerate it with `packages/domain/scripts/events.ts`, as `19f3809a` did.

### 2. The hosts: tee conduct's refusals append, per pass, by step

Every wrapped invocation's refusals go through one function: `invocationAppends(stream).after` (`conduct.ts:857-862`). That covers the agent closure (`conduct.ts:921`) and `makeRunSandbox` (`sandbox-decision.ts`, last lines). Do this:

- Give that `after` a tee into a per-pass collector, **before** the append. A refused append (`catchDefect`, `:861`) must not lose a read that happened.
- The collector is a `Map<Step, RefusedRead[]>`, built inside the `conduct` call. Each pass has its own, which covers *two passes at once*.
- Put the pure parts in `sandbox-record.ts`, beside `recordingWrap`:
  - `refusedHostsOf(reads)`: drop `unreadable` reads (the ticket's *a read that fails*), drop `telemetry: true` entries, and keep `complete: false` reads (they still count);
  - a `drain(step)` that returns the step's reads and clears them.
- **Hand `runAttempt` a drain, not the map.** Add an option beside `actionsAt` (e.g. `sandboxAt?: (step) => StepOutcome['sandbox']`). `runStep` calls it once, right after `runActionPipelineEffect` returns, and spreads the result into the outcome it builds (the `stepOutcomeOf(spec.step, …)` call, `run-attempt.ts` about line 2326).
- **Draining is what makes a fix round's second `build` see only its own reads.**
- Every scope has closed by then:
  - `process-action.ts` runs `Effect.scoped` around wrap and spawn inside `action.run`;
  - the agent runtimes scope inside their own `run`.

  So the finalizer has fired before the pipeline returns.

Why not re-read the pass stream for `SandboxConnectionsRefused`? `runAttempt` holds no stream read today. It would also need the visit's start version to separate fix rounds, and a refused refusals append would make the read miss what the tee keeps.

### 3. The unavailable flag: a field on the `run:` action's result

A `SandboxUnavailable` from `wrap` appends nothing: the wrap failed before `recordingWrap` reached its boundary (`sandbox-record.ts`, *"A wrap that fails appends nothing"*). So the flag cannot come from the tee. It has to come from the action itself.

**Action result.** `ActionResultFields` already has `notWrapped?: true` (`packages/actions/src/action.ts:128-132`). Add `sandboxUnavailable?: string` beside it.

**Where `process-action.ts` sets it.** Only in the `SandboxUnavailable` arm of its `catchTags`. `SandboxWrapFailed` and `SandboxPolicyRefused` stay as they are: they are the profile or policy refusals #1155 built, and the ticket names only `SandboxUnavailable`.

**Carry it through.**
- `kept-run-action.ts:100-108` rebuilds the result when `notWrapped` is set; keep `sandboxUnavailable` there too.
- `step-outcome.ts`'s `actionOf` (`:75`) does not need it.
- `runStep` reads it off the pipeline's `result.results`. It sets `sandbox.unavailable` from the first action that carries the field, **only when `options.recipe.sandbox?.required === true`**. That is the ticket's *under `required: true`*.
- Under `required: false`, a mid-pass loss routes as today. 0127 §14's *"later runs go ahead unsandboxed, each marked"* is not built by this ticket. Leave a one-line comment that names it.

`SandboxDecision` does not carry `required` (`packages/recipe/src/sandbox.ts:51-55`), so read it from the recipe, not from the decision.

## The `refused` decision at the `run:` call sites is already closed; make it a failed action, not a throw

The ticket's *Watch out* describes #1152 as spawning as today for any decision that is not *sandboxed*. The landed code does not. `from-recipe.ts` (the `'run' in action` branch) treats `refused` as *wrapped*:

```
const wrapped = decided === 'sandboxed' || decided === 'refused'
```

So:
- `refused` without a sandbox throws `ActionUnavailableError` when the ports are built;
- `refused` with a sandbox would wrap.

Neither spawns unwrapped. Also, `conduct.ts:1002-1009` returns `stage: 'recipe'` for a `refused` pass before the claim, so in production this branch is reachable only from a test.

What to change:

- **The branch.** In `from-recipe.ts`, give `refused` a branch of its own. Pass `makeProcessAction` a `refused: decision.why`. Its `run` then returns `failed`, with `notWrapped: true` and `sandboxUnavailable: why`, and evidence through `wrapRefusal`'s sentence shape: `the sandbox would not wrap \`…\`: <why>`. It calls neither `wrap` nor `spawn`.
- **Why a failed action and not a throw.** If the conductor's early return ever moves, `refused` routes as `SandboxRefused{unavailable}` like any other loss, rather than escaping as a step that threw.
- **The `sandboxDecision` dep is a value, not the kind.** It is passed as `deps.sandboxDecision?.kind` today. Pass the decision itself so `why` is in hand.
- **Leave `sandboxed` with no sandbox as it is.** It still throws by name.

## The proposal and the rule

### `proposal.ts`

**The new variant:**

```
SandboxRefused = { _tag, from: Step, cause: 'connections', hosts: string[], output }
              | { _tag, from: Step, cause: 'unavailable', said: string, output }
```

- `output` is the evidence of the proposal it replaced. A person still needs the red log.
- Write it as one `z.object` with a nested discriminated `cause`, or as a discriminated union under one `_tag`. Pick whichever `StoredProposal` and the per-tag field list (`proposal.ts:221`) and the partial decoder (`:245`) accept without special cases.
- Add the tag to all three.
- Add `'sandbox-refused'` to `JudgeWhen` (`:26-40`), and fix the comment, which says *thirteen*.

### `attempt-next.ts`

Do not touch the four builders. Wrap the result **once** in `nextOf`, after `fellShortAs` (`:132-133`):

- If the answer is `Propose` with `_tag` in `BuildRed | VerifyRed | SetupRefused | CheckRefused`, and `outcome.sandbox` has a non-empty `refused` or an `unavailable`, return `SandboxRefused` instead.
- `unavailable` wins over `connections` when both are present: the host lost the sandbox, and a host list from earlier runs is secondary.
- `VerifyRed` reaches here through `mergeRefusalProposal` (`mergeCompletedRefused`, `:311-336`). The same post-filter covers it, with no separate case.
- `from` is the outcome's step.
- Everything else is untouched:
  - `ReviewFindings`, `AgentCrashed` and the others;
  - an agent whose wrap failed, which already reaches a person as `AgentCrashed` (`:351-354`);
  - an outcome with no `sandbox`.

### Routing and the judge

- **`whenOf`** (`proposed-route.ts:45`): `SandboxRefused` maps to `'sandbox-refused'`.
- **`offerFor`** (`routing.ts:191`): the case is an empty `break`, with nothing pushed to `available` and nothing to `unavailable`. That is what makes `notAskedWhy` (`proposed-route.ts:193`) say *nothing but a person was on offer*. A `round(..., false)` would push to `unavailable` and give a different sentence.
- **`BUILT_IN_FOR`** (`judge.ts:484`): `'sandbox-refused': null`.

### The recipe refusal

In `recipe.ts`, in the same `superRefine` loop that refuses `merge-the-base` away from `base-moved` (`:3490-3495`):

- refuse **any** `judge:` whose `when` is `sandbox-refused`, by name;
- the sentence says that allowing a host or installing the sandbox is the operator's.

### The compiler finds the rest

Every `Record<JudgeWhen, …>` and every exhaustive switch over `Proposal` gains a cell. `wait-words.ts:253` is one of them. Give it a plain sentence from the hosts or from `said`. The full *Waiting on you* text is S9, and out of scope. The step-matrix and judge tests each gain a row.

## Tests (unit only)

**Domain.** `nextOf`, fed hand-built outcomes:
- each of the four cells with `sandbox.refused` gives `SandboxRefused{connections}`;
- `sandbox` absent gives today's proposal;
- `sandbox.unavailable` at `build` gives `SandboxRefused{unavailable}`;
- `offerFor` returns empty `available` and empty `unavailable`.

**Telemetry-only, which is a test of the collector, not of `nextOf`.** `refusedHostsOf` is the function that drops telemetry entries and `unreadable` reads, so the case *"one with only telemetry hosts returns today's proposal"* is tested there, with these inputs:
- only telemetry entries;
- `unreadable`;
- `complete: false` with one real host;
- an unparsed line.

Then show that its empty answer leaves `sandbox` absent.

**Process action**, with a fake `CommandRunner` and a fake `RunSandbox`:
- `refused` calls neither the fake runner nor the fake `wrap`, and returns `failed` with `sandboxUnavailable`;
- a `SandboxUnavailable` from the fake `wrap` sets `sandboxUnavailable` too.

**`runStep`.** A `sandboxAt` that returns hosts reaches `StepEnded.outcome.sandbox`. A second visit to the same step after a drain sees none.

**Recipe.** `judge: same-worktree` at `when: sandbox-refused` is refused at resolve, and the message names the key.

**What only a real run can settle.** The first sandboxed `build` that is refused a host should show two things on the same pass stream:
- `StepEnded.outcome.sandbox.refused` matching that step's `SandboxConnectionsRefused.read.entries`, with telemetry removed;
- then `WaitStarted` for a person, with no `SpentFor{Judge}` between them.

Nothing here needs `pnpm test:integration`.
