# Design: #369, the reviewer answers a schema rather than prose

## The shape in one paragraph

Three layers change. Each one gets one job:

- **Domain** declares what a review answer is.
- **The runtime adapters** hand that schema to the binary and return the parsed object.
- **`createAgentAction`** reads the object when the runtime returns one. It falls back to `parseFindings` only when the runtime returns none.

Only the cold reviewer asks for a schema. The implementer, the `design:` drafter (`createDraftAction`, `agent-action.ts:855`) and the judge never send one. The drafter's answer is a fence by design (`parseDraft`, `agent-action.ts:791`), and #368 owns the recheck's prose.

## 1. One declaration: in `@lingtai/domain`, next to `Finding`

`Finding` already exists as a zod object (`packages/domain/src/events.ts:794`, *"Three copies of the shape would be three places for `failureScenario` to be summarised away"*). It is not exported. Only its type is. Domain is on zod 4.5.4, so `z.toJSONSchema` is available. `@lingtai/actions` has no zod dependency and should not get one for this.

What to add in `events.ts`:

- **`ReviewAnswer`**, built from `Finding` and `REFUSED_ABOUT` (`events.ts:843`). It is a strict object with two keys: `findings: z.array(Finding.strict())` and `about: z.enum(REFUSED_ABOUT).nullable()`.
- **`REVIEW_ANSWER_JSON_SCHEMA`**, which is `z.toJSONSchema(ReviewAnswer)`. Strip `$schema` if the binaries object to it.

Use `.strict()` on a derived copy, never on `Finding` itself. `Finding` parses stored `StepPassed`/`StepFailed` payloads (`events.ts:815`, `:845`), and tightening it would refuse old events.

Then make `ActionFinding` (`packages/actions/src/action.ts:81`) a re-export of domain's `Finding` type rather than a second interface. That is what makes "cannot diverge" true by construction. Write the Done-when test anyway, in `packages/actions/unit/agent-action.test.ts`:

- build a fully populated literal typed `satisfies Required<ActionFinding>`;
- assert its keys equal `Object.keys(REVIEW_ANSWER_JSON_SCHEMA.properties.findings.items.properties)`;
- assert `severity`'s enum equals `SEVERITIES`.

`StepFinding` (`packages/domain/src/run.ts:51`) is a third copy. Leave it alone: it is not this ticket.

**The schema is all-required, and `about` is required but nullable. This is a decision, not a quirk.**

- **The codex reason.** `codex exec --output-schema` is OpenAI structured output. Its strict mode rejects a schema with an optional property or without `additionalProperties: false` at every object level. One schema for both runtimes therefore has to be the strict form. Claude accepts it too: the ticket's measurement already shows claude constrains to a schema.
- **The `about` reason, which also fixes the ticket's measured problem.** All four runs filled `about` when leaving it out was available. Making *did not say* an explicit `null` turns it into a value the model has to choose, instead of an absence it was never going to choose.

`about: null` must read back as an **absent** key. `parseFindings`'s rule (`agent-action.ts:300`, *"a missing answer filled in with a default would be counted as the default"*) and `StepFailed`'s spread (`agent-action.ts:577`) stay exactly as they are.

Pin the generated JSON in a unit test, in domain or actions. The test asserts:

- `required` lists every key at both object levels;
- `additionalProperties` is `false` at both levels;
- `line` admits `null`.

If `toJSONSchema` emits something codex refuses (`minimum`/`maximum` from `.int()` is the likely one), the codex reviewer fails at request time on every pass. Nothing in `pnpm test` would see that.

## 2. The runtime seam: `RunRequest.outputSchema`, `RunOutcome.structured`

Two optional fields in `packages/agent/src/runtime.ts`:

- **`outputSchema?: Record<string, unknown>` on `RunRequest`** (`:70`). It is the JSON Schema. Absent means an ordinary run, which is every run but the reviewer's.
- **`structured?: unknown` on `RunOutcome`** (`:150`). It is the object the runtime returned, and it is absent when the runtime returned none. Keep `text` as it is: it is still the evidence, and still what the fallback reads.

Do not add a `RuntimeCapabilities` flag. Both runtimes have the flag, and a capability nobody branches on is a declaration that can only go stale.

**Claude** (`packages/agent/src/claude-code.ts`):

- `argsFor` (`:194`) adds `--json-schema JSON.stringify(request.outputSchema)` when the field is present. `invocation()` (`:298`) shares `argsFor`, so `RunStarted.invocation` records it. That record is how the log can say a review ran under a schema: the `--json-schema` member of `RunStarted.invocation.args`.
- `ClaudeResult` (`:118`) gains `structured_output?: unknown`.
- The success branch (`:473`) passes it through as `structured`.

**Codex** (`packages/agent/src/codex.ts`):

- `codexArgv` (`:900`) takes an `outputSchemaPath?: string` option, and `argsFor` (`:921`) emits `--output-schema <path>` **before the `--`** (`:957`, *"Behind `--`, and it is load-bearing"*). `codexArgv` stays pure (*"so the whole command line is a unit-level claim"*, `:893`), so the path is an argument, never computed inside it.
- `run()` writes the file and removes it once the process closes, on every ending.
- Put the file outside the worktree, under `os.tmpdir()`, for `settingsPath`'s reason (`runtime.ts:88`). Name it deterministically from `runId`, so that `invocation()` and `run()` record the same argv. `invocation()` must not create the file.
- Codex prints no `structured_output`. Under a schema, the final `agent_message` (`codex.ts:419`, `receipt.text`) *is* the constrained JSON. So `run()` `JSON.parse`s `receipt.text` into `structured` only when a schema was sent. If that parse fails, `structured` stays absent and the action's fallback reads the text: the same unreadable path as today.

## 3. The new failure kind, classified by the adapter

Add one member to `RUN_FAILURE_KINDS` (`events.ts:598`). I would call it `no-structured-answer`. The comment above it already says how: *"Additive to the enum. No stored event is rewritten and no version is bumped."*

`claude-code.ts`'s close handler branches on `parsed?.subtype === "error_max_structured_output_retries"` beside the `error_max_turns` branch (`:454`), carrying turns and cost. Update the two comments that say exactly one member is branched on (`:112`, and the header at `:30`).

**Extract the close decision into a pure exported function** (call it `claudeClose`, the way `codexClose` is `codex.ts:534`). The test that pins this subtype as `"crash"` is `packages/agent/integration/claude-code.test.ts:549`. It is in the **integration** half, which `pnpm test` does not run (`unit/claude-code.test.ts`'s header: *"Everything that spawns a process is in `integration/claude-code.test.ts`, which `pnpm test` does not run"*).

- Edit that row to the new kind, because it is correct there.
- The claim that stands in before the merge is a unit test of `claudeClose` in `packages/agent/unit/claude-code.test.ts`. Its cases: this subtype gives the new kind; `error_max_turns` still gives `out-of-turns`; `structured_output` passes through on `success`.

`tsc` will then demand an entry in two total records:

- **`STOP_OF`** (`packages/conductor/src/fix.ts:171`): give it `"crashed"`.
- **`RUN_OWNER`** (`packages/conductor/src/attribution.ts:159`): give it `lingtai`. The machinery dropped the answer, so it is not the repository's fault. `packages/conductor/unit/attribution.test.ts:135` already asserts every kind but `out-of-turns` is `lingtai`, so it needs no edit.

Both entries exist for totality. An implementer run never sends a schema, so neither can be reached from one.

## 4. The action: the kind maps to `unreadable`, never to `did-not-finish`

In `createAgentAction` (`agent-action.ts:399`):

1. **Pass `outputSchema: REVIEW_ANSWER_JSON_SCHEMA`** on the `runtime.run` call (`:446`).
2. **Map the new kind to `failed` + `unreadable: true`.** In the failure block (`:464`), before the generic `did-not-finish` return (`:521`), return `{ verdict: "failed", unreadable: true, findings: [], evidence }` with a sentence saying the runtime could not make the answer fit the schema.

   This reads the adapter's `kind` and does not re-derive it, so it respects the rule in the comment at `:510–516` (*"the adapter's `kind` is the answer"*).

   It also does not contradict [0057](doc/decisions-archive/0057-a-gate-that-did-not-finish.md) §1. That ADR is about a reviewer that never produced a judgement. This reviewer produced one and the machinery could not cast it, which is #279's case exactly.

   The route is the one the ticket asks for. `pass-steps.ts:894` answers `arrival.unreadable` first, sends it to a person, buys no round, and pays no judge (*"an answer nobody can read is not a criterion (0038 §2)"*). Returning `did-not-finish` would stand the pass down with the wrong sentence and no `StepFailed.unreadable` for the log to count.
3. **Read the answer.** Replace the `parseFindings(outcome.text)` call (`:530`) with a function that takes the outcome:
   - When `outcome.structured !== undefined`, normalise that object.
   - Otherwise call `parseFindings(outcome.text)`.

   **Factor `parseFindings`' inner loop (`:324–353`) into one function both paths call.** That keeps *"No failure scenario, no finding"* (`:331`), severity-off-the-ladder-raises (`:337`) and about-only-if-one-of-the-two-words (`:352`) in one place. A schema guarantees the keys, not that `failureScenario` is non-empty.

   If `structured` is present but carries no `findings` array, the result is `parsed: false`, and so `unreadable`. **Do not fall back to the text in that case.** Under claude the text is the same JSON as a string, and a second parse of it would just be a second opinion on one answer.

   Unit tests cover both paths with a stand-in `Runtime`:
   - `structured` present → findings, and `text` ignored;
   - `structured` absent → `parseFindings`;
   - the new kind → `unreadable: true`, `verdict: "failed"`.

## 5. `CONTRACT` (`agent-action.ts:143`)

**Delete:**

- *"Report as a single JSON object, and nothing else after it"*;
- the JSON example;
- *"The example above shows where the key goes"*;
- *"`line` may be null"*;
- the literal `{"findings":[]}`.

**Keep, in prose:**

- no failure scenario, no finding;
- findings only, no proposed fix;
- an empty list is a real answer.

*"Take the higher one"* is in `RUBRIC` (`:124`), which this ticket does not touch.

**Restate `about`** so it covers three cases:

- `null` whenever there are no findings that stop the change, and **always** when the list is empty;
- `null` when the reviewer cannot say which;
- `approach` only where no edit to these lines would fix it.

Name the cost: `approach` restarts the ticket from the base ([0040](doc/decisions-archive/0040-rounds-bound-depth-restarts-bound-breadth.md)) and `lines` buys one round. T4 answered `approach` for two ordinary line edits, which is the error in the expensive direction.

The schema enforces none of these rules. The prompt does, plus the existing `verdict === "failed"` guard (`:577`), which already drops an `about` that came with a pass.

## Watch out

- **An empty `findings` merges.** The structured path's failure mode is no longer "unreadable". It is a schema-valid `{"findings":[],"about":null}` from a model that gave up. Nothing here makes that worse than today, but no branch may read a missing or malformed `structured` as `findings: []`: every such case is `parsed: false`.
- **The codex path is unverified by anything `pnpm test` runs.** The argv is a unit claim through `codexArgv`, but whether codex's strict mode accepts the generated schema is not. One `codex exec --output-schema` call by hand settles it for cents. If you don't make that call, say so in the commit body rather than leaving it implied.
- **Do not commit with `fixes`/`closes` next to #368 or #318.** Neither is done by this.
