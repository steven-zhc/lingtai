## Design note: #1421, overlap the PR page's independent reads

Three edits. The page starts the board's load before it reads the bar. The two readers read their items in chunks of one named constant. `readPrPage` runs its two independent readers side by side. No ADR is touched. Everything below is checkable by `pnpm test`; nothing here relies on `pnpm test:integration`.

### 1. The page: start the board's load first

`Page` (`apps/board/src/app/pr/[project]/page.tsx:64-104`) awaits two reads at `:68` and `:73` before it returns any JSX. It awaits three more inline as `RecipeBar` props (`:86`, `:88`, `:89`). `<Board>` sits inside `<Suspense>` at `:97-99` and calls `loadPrBoard` itself at `:27`, so it cannot start until `Page` has returned.

The shape is to hoist the load, not to split the bar into its own component:

- Call `loadPrBoard(name)` on the line after `params` resolves (`:65`), before any bar read. Keep its promise, not its value.
- Pass that promise to `Board`, which awaits it where it now calls `loadPrBoard` (`:27`).
- Attach `.catch(() => undefined)` to a branch of the promise and discard the result. This marks it handled during the window while `Page` is still awaiting the bar; `Board`'s own `await` still sees a rejection. In practice `readPrPage` catches everything (`prs.ts:122-127`, `:129-170`), but `measure` rethrows (`timing.ts`: "Rethrown untouched and never read").
- Put the five bar reads into one `Promise.all`: `readRegistered`, `onBoardProjects`, `readProjectLocks`, `placeViewsOf(name)` and `pauseSlot(name)`. None of them takes another's result.
  - `pauseSlot` reads `readProjectLocks()` again (`lock-banner.tsx:61`). `readProjectLocks` is React `cache`d (`locks.ts:105`), so a call made concurrently gets the same promise and costs no extra read.
- Keep `listingError`'s precedence: `readRegistered`'s message wins over `onBoardProjects`'s (`:69` assigns, `:74` uses `??=`). Work it out from the two settled values after the `Promise.all`, not from catch callbacks whose order is no longer fixed.

Why hoist rather than give the bar its own async component: with the hoist, the overlap is visible in the code and does not depend on how React schedules sibling async server components. That makes Done-when's first box a check on the structure: the `loadPrBoard(name)` call comes before the first `await` that reads the bar. No unit test can render this page; the evidence after landing is a trace whose `pr.board` span starts near +0 ms rather than after the `locks.read` span (+3,772 ms in `d67f51003be977d4ff0af0db161eab5d`).

This edit does not touch the fallback `#1419` owns (`PrBoardSkeleton`, `:97`).

### 2. The constant and the two readers

**The constant.** Add `export const READ_CONCURRENCY = 8` in `packages/project/src/pr.ts`. It is exported through `packages/project/src/index.ts:12` (`export * from './pr.ts'`), and `apps/board/src/lib/prs.ts:17` already imports from `@lingtai/project`. That gives one constant for both readers.

Its comment says why it exists: a project with hundreds of items would otherwise open hundreds of reads on the store at once. The comment must cite the store's actual pool bound. I did not find a `max` in `packages/event-store/src/db.ts`; `:18` only says "Each call constructs its own `pg.Pool`". Find where the board's `eventStore` gets its pool (`packages/event-store/src/index.ts:87`) and cite that line rather than assuming pg's default.

**`readDraftTickets`** (`packages/project/src/pr.ts:620-632`):
- Replace the `for` loop with `Effect.forEach(draft, …, { concurrency: READ_CONCURRENCY })`. `forEach` returns results in input order, which is the stream's order the docstring promises at `:617`.
- On failure it stops at the first error and interrupts the reads still in flight. The draft read still fails as a whole and is "never *no tickets*" (`:618-619`).
- When two reads fail, the message shown may now be either ticket's rather than the first in order. That is acceptable.
- `packages/project` is held at `async: 0, run: 0` (`effect-ratchet.baseline.json:12`), so this stays pure Effect.

**`readProjectPrs`** (`apps/board/src/lib/prs.ts:61-83`):
- Keep `topPrNumber` (`:43-51`) serial.
- Build the numbers `top…1` newest first and walk them in chunks of `READ_CONCURRENCY`.
- Read each chunk with `Effect.forEach(chunk, (n) => readPr(...).pipe(Effect.result), { concurrency: READ_CONCURRENCY })`. Then run the existing loop body (`:70-80`) over the chunk's results in newest-first order:
  - a failure is pushed as `{ n, error }`, then continue;
  - `null` is skipped;
  - a `draft` PR is skipped;
  - otherwise push it.
- When the `since` check (`:79`) fires, break out of both loops. Results after the crossing PR in the same chunk are dropped, including any `{ n, error }` entries; the serial loop never read them. The output is then identical to the serial loop's.
- Use the chunked path whether or not `since` is given. One path is simpler than two, and the cost is one slow read per chunk of 8.
- Keep `reverse()` at `:82`.
- Each read is wrapped in `Effect.result`, so one unreadable PR never interrupts the others. That is the module's own rule: "one unreadable stream is returned as itself and the others are still read" (`prs.ts:6-7`).

### 3. `readPrPage`: the PRs and the draft side by side

`readPrPage` reads `readProjectPrs` and then `readDraftOf` one after the other (`prs.ts:134-135`). Neither takes the other's result: `readDraftOf` goes through `readDraft` → `listPrs` (`pr.ts:152-153`), not through the PRs already read. Only `spendByPr` (`:136-139`) depends on `prs`.

Run the two together with `Effect.all([...], { concurrency: 2 })`, then `spendByPr`. That is what *the slowest chain, not the sum* means here.

The bound is per reader, so the board peaks at 2 × `READ_CONCURRENCY` reads plus the bar's. Excess reads queue in the board process's own pool. Say that in the constant's comment next to the pool size.

The other callers that read the PRs and then the draft back to back can take the same `Effect.all`: `readLandedWhere` (`:186-187`), `readPrDetail`'s `'next'` branch (`:304-305`) and `:433-434`. That is optional, and it belongs to the same change if it is done.

`listPrs` (`pr.ts:87-97`) stays serial. It is shared with `draftTarget` (`:113-118`), whose version goes into appends, and how many times a page reads a stream is #1420's question.

### Tests (all unit, memory store, no clock)

**No existing test passes `since`.** Every call to `readProjectPrs` uses two arguments, including both tests at `apps/board/unit/pr-board.test.tsx:54-80`. So Done-when's "asserted by its existing test" has no test behind it: write one. It needs:
- merged PRs with `ended.at` on both sides of `since`, laid out so the crossing PR falls mid-chunk with more than `READ_CONCURRENCY` PRs above it;
- an assertion on the exact `n` list, oldest first;
- a case where an unreadable PR older than the crossing is absent from the result.

**Order under concurrency.** Wrap a `createMemoryEventStore()`'s `read` the way `pr-board.test.tsx:71-75` already does. Make each read wait a number of `await Promise.resolve()` turns that decreases with its position, so later items finish first, and record the most reads in flight at once. Assert:
- the results are the same items in the same order as the serial reader returned;
- the most in flight is greater than 1 and at most `READ_CONCURRENCY`.

Do this for `readProjectPrs` (in `pr-board.test.tsx`) and for `readDraftTickets` (in `packages/project/unit/pr.test.ts`, next to `:301-342`). The existing rejection test at `:342` (`rejects.toThrow('boom')`) must stay green. Use microtask turns, not `setTimeout`: the wall clock makes a test integration (0060 §1).

**Telemetry.** `apps/board/unit/trace-spans.test.ts:289` calls `loadPrBoard` with a fake reader, and a call to it is unchanged by the hoist. If the page now passes the promise rather than the name, check that the test still compiles.
