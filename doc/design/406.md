# #406 — only `WorkItemBlocked` writes `waiting`

## The decision: remove `state` from all four, and leave every other column alone

The ticket only commits to `RunAwaitingInput` and `RunFailed`. The other two can go as well, and each case keeps everything it writes except `state`.

- **`ApprovalRequested`** (`task-view.ts:680-690`): keep `note` and `awaiting_sha: d.onSha`, and drop `state`. A block always follows it:
  - The conductor's own request (`conduct.ts:3524-3546`) sits inside `if (!held && judged && onOrigin !== null)`. The `WorkItemBlocked` append right after it (`conduct.ts:3549-3567`) is not inside that `if`.
  - A plugin's `needs-approval` (`action.ts:795-811`) returns `heldAt`. `pass.ts:1752-1753` turns that into `ending: 'held'`. That ending reaches the same unconditional block append, and `held` only suppresses the conductor's second request.
  - `awaiting_sha` has to stay. The Approve button and `describeWait` (`task-view.ts:1146-1155`) read it, not `state`, and `describeWait` returns `null` unless `blocked`. So a card with no block offers nothing, whatever its state.
- **`IntegrationRefused`** (`task-view.ts:706-716`): keep `note` and `awaiting_sha: null`, and drop `state`. A block does **not** always follow it, and that is the reason to remove it rather than the reason to keep it:
  - `approve.ts:355-403` always blocks after a refusal.
  - The pass's merge lane (`conduct.ts:2073-2077`) returns `{ notMerged }` to the `merge` step, which goes to `proposed`. There the router may answer `verify-failed` mechanically (`BUILT_IN_FOR`) with a fix round, which writes `running` (`FixRequested`, `task-view.ts:621-631`). It never writes `waiting` for that.
  - Every way out writes its own state: a block, a release (`WorkItemReleased` → `queued`, `:301-318`), or a fix round. Writing `waiting` here was a guess about which of the three would come.
- **`RunFailed`** keeps `note: \`${kind}: ${detail}\``. **`RunAwaitingInput`** keeps `note: d.prompt`. On a running card that note stays until the next event that writes one. The ticket asks for exactly that.

`viaRun` and `set` already take a partial column set, so each case becomes the same call without `state`. No SQL changes.

## Where the tests go, and what `pnpm test` actually checks

**The Watch out is right that the cases belong in `packages/projector/test/contract.ts`. It is wrong that `pnpm test` will run them.** The contract runs from exactly two places:
- `integration/projection.test.ts` (Postgres)
- `integration/sqlite.test.ts`

Both are in the integration half. `sqlite.test.ts`'s header says: *"In `integration/` all the same, because a directory of its own is still the filesystem."* `packages/projector/unit/` holds only `drift.test.ts` and `one-store.test.ts`, and neither folds anything. Nothing in `pnpm test` will execute the new fold cases.

Still add them to the contract. It is the right home, and they run after the merge (T11). Model them on the #405 cases at `contract.ts:492-560` (`made(f, taskViewProjection, written)`, then `f.store.tasks(...)`):

1. Claimed, `RunStarted`, then `RunAwaitingInput` → `state === 'running'`, `note === prompt`, `blocked === false`.
2. Claimed, `RunStarted`, then `RunFailed` → `state === 'running'`, note set.
3. The same as 2, then `WorkItemBlocked` → `waiting`, `blocked`, and the note is the block's question. This pins *a card reaches `waiting` only through `WorkItemBlocked`*.
4. `ApprovalRequested` with no block → not `waiting`, and `awaitingApproval` is still true. Then add the block → `waiting`.

Say plainly in the PR that these are not run by the `build` gate. The only check `pnpm test` gives this change is `pnpm typecheck`.

## The existing integration fixture that this change breaks without anyone seeing

`integration/task-view.test.ts` is in `ON_POSTGRES` (`packages/event-store/test/postgres.ts:31`), so it is skipped here. Fixture **4** (`:172-187`) is an `IntegrationRefused` with no block after it, which is exactly the shape this ticket says is not a hold. Two places assert `waiting` on it:
- `:624`, `expect(card(tasks, 4)?.state).toBe('waiting')`
- `:774`, under a comment calling it *"a refused dispatch is `waiting`"*

After this change, card 4 holds only `WorkItemDiscovered` plus the lane refusal, so its state is whatever `WorkItemDiscovered` writes (`:263`, `queued`), with the refusal as its note.

Update both assertions and the comment at `:772-773`. Card 4 still checks `blocked === false`, and that half of `:775` stays. Fixtures 9 and 10 (`:245-300`, `:353-392`) both end in `WorkItemBlocked` and need no change.

## The two comments

- `pass.ts:350-351`: *"an agent stopped mid-flight through the hook (`RunAwaitingInput`)"*. That event is never a path to `asked`. The hook answers `{ allow: true }` (`hook-socket.ts:246-251`), and the only source of `{asked}` is the agent's own answer, which `work-action.ts:148-158` turns into `NEEDS_INPUT`.
- `agent-action.ts:897-900`: *"`hook-socket.ts` appends `RunAwaitingInput` and `work-action.ts` turns `asked` into this same token"*. Rewrite it so the two clauses are no longer one mechanism. The implementer's `asked` arrives in its answer, as the design agent's does. The difference that remains between the two steps is `unhookedSettings`, not the hook.

Name the event in the corrected text rather than citing it by line: say that `RunAwaitingInput` is a note on the card and nothing reads it.

## After it lands

Changing a stored value in a fold means someone has to run `lingtai projection rebuild task_view` on the conducting machine. The pass cannot do it, so the PR body should ask for it. Until that rebuild, rows already folded keep their old `waiting`.

To check the rebuild: after it, no row should have `state = 'waiting'` and `blocked = false`. Any such row is a log whose last state-writing event is a `RunFailed` or `RunAwaitingInput` with nothing after it. That is a crash between `RunFailed` and the block or release, and 0118 §1 calls it a defect to report, not one to cover over.
