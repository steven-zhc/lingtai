# Design note: #1125, retrying a push that GitHub answers with a 5xx

The ticket's steps are right and give the order to work in. This note covers three things it leaves out. One is a claim in the ticket that is wrong (the publish). One is a test fake that will silently make the existing lost-push tests pass for the wrong reason. The last is how the base-push check fits inside the try.

## 1. The publish needs the lease recovery too. The ticket says it doesn't.

Step 5 says *"The lease recovery from step 3 is not needed there: a push that lands sets `lease`/`published` as it does today."* That covers a push that succeeds. It does not cover the case this ticket exists for: a 500 that origin actually applied.

The publish push leases the branch: `--force-with-lease=refs/heads/${branch}:${lease ?? ''}` at `conduct.ts:2424`. If try 1 is applied but answered with a 500, try 2's lease is stale. Git answers `! [remote rejected] … (stale info)`. That is not transient, so `retryUnreachable` gives up (`network.ts:66`). Then the `armAlone` path at `conduct.ts:2439` records `arm-only` and the run ends `unpushed`. `unpushed` is exactly what drops Approve (`wait.ts:492-498`), even though the branch is on origin.

`gitAskedEffect` already takes a `recover` that runs inside each try (`conduct.ts:1851-1864`, *"`recover` runs inside each try, so what it reads is retried with the command"*). Give the publish one shaped like `landNow`'s (`conduct.ts:3233-3241`):

- On `stale info`, run `ls-remote origin refs/heads/<branch> refs/heads/<arm>`.
- Succeed only if `branch` is the sha this push sends (`wip === null ? head : branchHead`, matching the refspec at `:2430`) **and** `arm` is `head`. One command updates two refs and is not atomic (`:2434-2438`), so neither ref may be inferred from the other.
- If `ls-remote` fails as unreachable, return that failure so it is retried. Otherwise return the original `err`, as `landNow` does.
- Apply this only where `branchHead !== null`. With no lease there is no stale info.

The `armAlone` push (`:2439`) is forced and has no lease, so it only needs the `retry` argument.

Add a unit test beside the `stale info` cases in `packages/conductor/unit/conduct-what-a-claim-leaves.test.ts` (`:356`, `:387`): try 1 fails with a 500, try 2 fails with `stale info`, and `ls-remote` shows both refs at the pushed shas. The outcome must not be `arm-only` or `refused`. Without that test, *"the end-of-pass publish retries a 5xx"* passes and Approve is still dropped in the one case that matters.

## 2. The integrate fake will turn every lost push into a landing

`fakeGit` in `packages/repo/unit/integrate.test.ts:35-79` answers *"everything else succeeds"* (`:78`). Once step 4 adds `merge-base --is-ancestor <mergeCommit> FETCH_HEAD`, the fake answers exit 0. Every `[rejected]` test would then read "origin already took it" and land:

- `:223`, `:309`: `! [rejected] HEAD -> main (non-fast-forward)`
- every `LostPush` / recompute case

Those tests would keep passing, but for the wrong reason, or fail in a way that looks unrelated.

Change the fake before writing the code:

- `merge-base --is-ancestor` fails with `new RepoFailed({ …, exitCode: 1 })` by default.
- Add an option such as `landedAfterPush?: number` that answers 0 once that many pushes have happened.
- Leave the other `merge-base` call alone. `integrate.ts:609` asks `merge-base laneBase laneBranch` for the fork point and must keep answering.
- `failFetch` counts every `fetch` (`:66`). The new ancestry fetch adds to that count, so a test that sets both `failFetch` and `failPush` needs its count looked at again. None does today (`:293`, `:301`, `:317` stop before the push).

The ticket's sequence test (500 applied, read fails, `[rejected]`, lands) needs a per-call script for `fetch` or `merge-base`, not one boolean. Add a small ordered list of answers to the fake rather than a second fake.

The test fakes set `detail` only (`:67`, `:70`). The real "not an ancestor" answer comes from `exitCode` (`git.ts:89-90`, *"`git`'s exit code; null when there was none"*). The fake must set `exitCode: 1` explicitly, or the code will read every fake "no" as a failed read.

## 3. The base push: one function for one try, with the check inside it

Today, `integrate.ts:654-664` wraps a bare `at(['push', …])` in `retryUnreachable` and reads the result outside. Make the retried effect one try that includes the check:

```
tryPush = at(push).pipe(catch: err =>
  isRemoteErrorFailure(err) || PUSH_REJECTED.test(err.stderr ?? err.detail)
    ? landedAlready().pipe(
        // true  → succeed (the merge is on origin)
        // false → fail err
        // read failed → fail err, never the read's own failure
      )
    : fail err)
retryUnreachable(tryPush, waits)
```

- **`landedAlready`** runs `at(['fetch', 'origin', `refs/heads/${options.base}`], cwd)`, then `at(['merge-base', '--is-ancestor', mergeCommit, 'FETCH_HEAD'], cwd)`. It returns an `Effect<boolean, RepoFailed>`: success is `true`, a `RepoFailed` with `exitCode === 1` is `false`, and anything else fails. The caller turns a failure into the original `err`. Do not take a permit. It writes only the worktree's `FETCH_HEAD`, the same reasoning as `conduct.ts:1866-1871`.
- **The landed answer falls through.** It goes to the existing `update-ref` compare-and-swap (`:672-674`) and `succeed(mergeCommit)` with no new branch. The CAS already ignores every outcome (*"a landed merge must never become a refusal here, so every outcome is ignored"*, `:669-671`).
- **Retries stop on a rejection.** `[rejected]` stays non-retried: `isRemoteError` must return false when `PUSH_REJECTED` or `BASE_PROTECTED` matches, the same guard as `isUnreachable` (`network.ts:36`). A rejection that the check answered "not landed" therefore leaves `retryUnreachable` on its first failure, and the existing `PUSH_REJECTED` → `LostPush` at `:663-664` reads it unchanged.
- **Where `remote-error` is decided.** The `:663` `Effect.fail` for anything else still goes to the catch. The catch at `:686-689` becomes three arms: `isUnreachableFailure` → `unreachable`, then `isRemoteErrorFailure` → `remote-error`, then `unexpected`. The `refuse('remote-error', …)` call belongs only in that catch, not in the try.
- **Effect ratchet.** This is the only new IO in `packages/repo`, and it is all `Effect.gen` / `pipe` inside an existing Effect. It adds no `async` function and no `Effect.run*`, so the `packages/repo` row of `effect-ratchet.baseline.json` cannot rise. If it does, the shape is wrong.

## Smaller decisions

- **Name.** Keep `retryUnreachable`. A rename touches `conduct.ts`, which has five open tickets on it (Edges, *Shared files*). Change its doc comment to say it retries a remote 5xx too.
- **Classifier text.** `isRemoteError` reads `err.stderr ?? err.detail`, like `isUnreachableFailure` (`network.ts:41-43`). The base-push code still tests `BASE_PROTECTED` / `PUSH_REJECTED` against `.detail` (`:659`, `:663`). Leave those as they are. Changing what they read is outside this ticket.
- **The refusal sentence.** Name the ref from git's own frame: the `-> <dst>` of the matched line is `agent/<n>` or `<base>`. When nothing matches, use "the push" (#1030). For `landNow`, the detail is the push's `detail`, which carries ` (after 3 tries)`. Take the try count from there rather than writing "3" in the sentence; `UNREACHABLE_WAITS.length + 1` is the count.
- **What settles it after the merge.** On a later 500, the evidence is the `IntegrationRefused` event's `reason` (`remote-error`, not `push-rejected` or `unexpected`), and the run's `RunRefsPublished.outcome` (`published`, not `arm-only` or `refused`). The unit tests above stand in for that before the merge. No part of this needs `pnpm test:integration`.
