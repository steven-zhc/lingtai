# #316: what is in the ticket, what is not, and what it gets wrong

The ticket and 0110 already say where this goes. This note covers three things the ticket does not say. Two of them it gets wrong, and either one would put a confidently wrong number on the log.

0110 (`doc/decisions/0110-tokens-on-the-event-money-at-display.md`) is now the topic ADR for this; archived 0073 and 0075 are its history. Where this note corrects 0110, correct it by **editing 0110**. That is the repo's rule since 0100 (*"a decision that changes is an edit to its topic's ADR"*). The archived files stay untouched.

## 1. Codex's counts overlap. The event's must not.

0110 §3's table maps Codex `input_tokens` to *fresh input* and lists `reasoning_output_tokens` as a fifth count beside `output_tokens`. **On this machine's Codex both are wrong: `cached_input_tokens` is part of `input_tokens`, and `reasoning_output_tokens` is part of `output_tokens`.**

- **Measured.** The last `token_count` in a real rollout, `~/.codex/sessions/2026/09/08/rollout-…-01a08179….jsonl`, reads `input_tokens: 9046919, cached_input_tokens: 8614656, output_tokens: 42056, reasoning_output_tokens: 23883, total_tokens: 9088975`. The total is exactly input plus output.
- **The repo already says so in prose.** `packages/agent/unit/codex.test.ts:168`: *"Not `cached_input_tokens`, which is a discount on the input and not a second charge"*.
- **The real fixture agrees.** At `codex.test.ts:51`, input is 17018 and cached is 7680.

If the reported numbers were stored under the ADR's names and priced through `doc/rate-card.md`'s mapping (`rate-card.md:32-38`), that rollout would charge 9.0M tokens at the full input rate. About 0.43M were fresh. The 23883 reasoning tokens would also be charged twice.

**Decision: the five counts on the event are disjoint. Each token is in exactly one bucket, and the Codex adapter does the subtraction:**

| bucket | claude-code | codex |
|---|---|---|
| fresh | `inputTokens` | `input_tokens − cached_input_tokens` |
| cacheRead | `cacheReadInputTokens` | `cached_input_tokens` |
| cacheWrite | `cacheCreationInputTokens` | `cache_write_input_tokens` |
| output | `outputTokens` | `output_tokens − reasoning_output_tokens` |
| reasoning | absent | `reasoning_output_tokens` |

With disjoint buckets, `rate-card.md`'s mapping is correct as it stands, and pricing is `Σ bucket × rate` for both runtimes. Correct 0110 §3's table to this, and say there why Codex is subtracted.

Rules for the subtraction:
- **It happens only when both operands were reported.** If `cached_input_tokens` is absent, `fresh` is absent. It is never `input_tokens` taken whole, because that reads an absent cache count as zero, which is the exact inversion the ticket's Watch out names.
- **If `reasoning_output_tokens` is absent, `output` is the reported `output_tokens` and `reasoning` stays absent.** Both are charged at the same rate, so nothing is mispriced.
- **A difference below zero means the runtime said something incoherent.** Record both buckets as absent, not a negative or zero.

The existing fixture `clean()` (`codex.test.ts:51`) has no `cache_write_input_tokens` and no `reasoning_output_tokens`. It is already the test that absent stays absent.

## 2. The ticket's arithmetic about Codex turns is wrong

The ticket says *"4 turns, and the number shown is one turn's"*. It isn't:

- **`turns` counts `agent_message` items**, at `codex.ts:316-317`, not `turn.completed`.
- **One `turn.completed` per run is what was measured.** Every `"originator":"codex_exec"` rollout under `~/.codex/sessions/2026/09/29/` has exactly one `task_complete`.
- So **`1971890` is the whole run's input plus output**, with the cache hits counted inside the input. Assignment at `codex.ts:300` has cost nothing yet. The real defect is item 1's overlap.

Still accumulate across `turn.completed`, as 0110 §3 says, and write the two-turn fixture the Done-when asks for. In its docblock, say that the multi-turn case is synthetic and that one per `exec` is what was measured.

**Watch out.** I believe, but have not verified, that `turn.completed.usage` is the session's running total rather than one turn's. If it is, summing two would double-count. Lingtai never runs `exec resume` (`codex.ts:17`), so no stream it reads has two today. Whoever first sees one can settle it from the rollout: each `token_count` carries both `total_token_usage` and `last_token_usage`, and whichever one the stream's `usage` equals is the answer.

Leave `billedTokens` exactly as it is. It is the "did this reach a model" leg of never-started (`codex.ts:435`, `:486`, pinned at `codex.test.ts:160-170`), not a spend figure. Put the new counts beside it in `Tally` (`codex.ts:271`); do not repurpose it.

## 3. claude-code reports per model, so the event records per model

`modelUsage` on the receipt is keyed by model id. Each entry has its own four counts and its own `costUSD`, and a Claude Code run can bill a second, smaller model beside the one requested. Folding all of it under the model the recipe asked for would price the small model's tokens at the large model's rates.

**Decision: one optional key, holding one entry per model the call billed:**

```
usage?: Array<{ model?: string; mode?: string; tokens: { fresh?, cacheRead?, cacheWrite?, output?, reasoning? } }>
```

This keeps 0110's two groups: the pricing key (model, mode) and the counts. It keys the counts by model because a rate is a function of the model. Edit 0110 §3 to say so.

What fills each field:
- **`model` for claude-code:** the `modelUsage` key, verbatim. That is the runtime's own statement of which model was used.
- **`model` for Codex:** `request.model` where the recipe set one, otherwise absent. Its stream never names its model, and an absent model means unpriced, which `rate-card.md:69-75` already says Codex is.
- **`mode`:** set only where a receipt names one. Nothing Lingtai spawns asks for a premium mode (the only model flag is `claude-code.ts:205`'s `--model`), so `mode` is absent today. Do not write `"standard"` into the event: that is display reading absence, and display is #208's.

## Where it goes

- **The shape:** `packages/domain/src/spend.ts`, a new file exported from the domain index. It holds the zod schema and one pure helper, `addUsage(a, b)`.
  - Entries merge by (model, mode).
  - Within an entry, merging uses the same leniency `costUsd` already has at `packages/conductor/src/discuss.ts:516`: absent plus absent is absent, and present plus absent is the present value.
  - Every combination goes through this helper: Codex's fold per `turn.completed`, `holdDiscussion`'s rounds (`discuss.ts:513`), and `spendOf` for `DiscussionHeld` (`discuss.ts:614`). A second hand-written sum is where `?? 0` creeps in.

- **The four events:** add `usage: Usage.optional()` to `RunFinished` (`events.ts:563`), `FixApplied` (`:1219`), `DiscussionAnswered` (`:1765`) and `DiscussionHeld` (`:1795`).

- **Do not touch** `packages/projector/src`, `packages/domain/src/run.ts`, `ActionResult`, `agent-action.ts:558`/`:901`, or the judge's line at `conduct.ts:1844`. The last four are #324's.

## The rate-card test, and why its fixture must be real

Put the parser and the pricer, both pure, in `packages/domain/test/rate-card.ts`. `test/` is where shared non-test code lives. #208 promotes it to `src` when a display needs it, and nothing in `src` imports it here.

The test lives in a `unit/` file and reads `doc/rate-card.md` with `readFile`, the way `packages/actions/unit/tamper-watch.test.ts:17-30` reads its list from `doc/tamper-watch.md`.

**The "no reducer reads it" check:** read the source of every file under `packages/projector/src/` and assert that none mentions `rate-card` or imports from a `test/` path. Name `task-view.ts` in the test, as the ticket asks.

**The calibration check:**
- **It needs a real claude-code `result` line with `modelUsage`, captured once into a fixture.** One `claude -p "reply ok" --output-format json` costs cents, so capture one. A fixture whose dollars were computed from the rate card is circular and checks nothing. It is the easy way to make this green, and it must not be taken.
- **Compare per model:** `tokens × rate` against that entry's own `costUSD`, using the empty-`mode` row with the latest `from` on or before the capture date. A per-model comparison names the stale row; a total would not.
- **Tolerance is 1%.** Claude Code computes `costUSD` from its own price table, so the two should agree to rounding.
- **A `modelUsage` key with no matching row fails by name.** It must never be skipped.

**Watch out: it may be red on arrival, and that is the check working.** `rate-card.md:55-67` says the cache columns are derived rather than quoted and the rows are three months old. Do not widen the tolerance. Use the per-model buckets to work out which column is wrong, and fix it by **appending** a row dated the capture date (`rate-card.md:16-19`: append, never edit). If one receipt cannot pin down which column is wrong, capture a second whose cache mix differs.

**What this test cannot do:** notice a price change after today. It pins the card against one observation. Running the same comparison over real `RunFinished` events is what would notice a later change. That depends on this ticket landing and is a query over the log, not something `pnpm test` can reach. Say so in the test's docblock rather than implying more.
