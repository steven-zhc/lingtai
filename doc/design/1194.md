## The shape of `classify`

```ts
type Seen =
  | { platform: 'git'; text: string }
  | { platform: 'github'; status: number; text: string }
  | { platform: 'runtime'; text: string }

type Classified =
  | { kind: 'base-protected' | 'push-rejected' | 'remote-error' | 'unreachable'; platform: 'git' }
  | { kind: 'rate-limited'; platform: 'github' }
  | { kind: 'account-limit'; platform: 'runtime'; runtime: RuntimeId }

classify(seen: Seen): Classified | null
```

- **`platform: 'runtime'`, not a runtime id.** The caller does not know which runtime wrote the sentence: a fixing agent's detail wraps another run's sentence (`never-started.test.ts:458`). `accountWallOf` answers the runtime out of the text, so the row carries `runtime` and the result returns it.
- **Rows** are `{ platform, kind, pattern, status?, runtime?, waits?, says }`, where `says` is the sentence the generator prints.
- **`classify` returns the first row of its platform that matches.** Do not keep exclusions inside rows: today's *"a real rejection always wins"* checks (`network.ts:36`, `:59`) are reproduced purely by row order. Git's order is `BASE_PROTECTED`, `PUSH_REJECTED`, `REMOTE_ERROR`, `UNREACHABLE`; the runtime order is Codex, then Claude Code's two rows (`never-started.ts:66-73`). Empty text returns null before any row is tried (`network.ts:35`).
- **GitHub's row**: status 429 matches on its own. Status 403 matches only with `/rate limit/i` on the text (`app.ts:93-95`), so the rule needs two rows or one row with a status list and an optional pattern. Pick whichever renders more clearly.
- **`waits` on the two transient git rows (`remote-error`, `unreachable`).** Type it in domain as ``readonly `${number} seconds`[]``, not as effect's `Duration.Input`. Domain may not import `effect`, even as a type: it depends on `zod` alone (`packages/domain/package.json`), and the Done-when forbids it. That template type is assignable to `Duration.Input` (`effect/dist/Duration.d.ts:118`).
  - Export the one constant both rows point at as `UNREACHABLE_WAITS`, from domain. `conduct.ts:2543`, `:2572`, `:3383` and `integrate.ts:362` keep using it as their default and only change the import.

Do not export the regexes. The callers' `PUSH_REJECTED.test` and `BASE_PROTECTED.test` become reads of the kind.

## The callers, one by one (the only traps are here)

- **`integrate.ts:681`** is `isRemoteErrorFailure(err) || PUSH_REJECTED.test(stderr ?? detail)`. It becomes `kind === 'remote-error' || kind === 'push-rejected'` over `err.stderr ?? err.detail`.
  - Strictly, today's raw `PUSH_REJECTED.test` is also true for a text matching both `BASE_PROTECTED` and `PUSH_REJECTED`, and the new check is not.
  - The only cost is one `landedAlready` fetch that today is followed by the same `base-protected` refusal at `:693`. git never prints `[rejected]` and a protected-branch reason in one push (that refusal is `[remote rejected] … (protected branch hook declined)`), so this is the ticket's *synthetic input* case. Do not add a clause to preserve it.
- **`integrate.ts:693`/`:696`** classify `pushed.failure.detail`, not stderr, as the ticket's Edges say.
  - `base-protected` → `refuse('base-protected', …)`.
  - `push-rejected` → `LostPush`.
  - Anything else → `Effect.fail`.
- **`integrate.ts:720-722`** and **`conduct.ts:3397-3400`** use the kind with the same fall-through.
  - At `conduct.ts:3397`, everything that is not `unreachable` or `remote-error` still answers `'push-rejected'`, and that includes `base-protected` and null. Keep that default; do not add a `base-protected` branch.
- **`conduct.ts:2551`, `:3389`** become `classify(...)?.kind === 'unreachable'`.
- **`retryUnreachable` (`network.ts:97`)** retries when the kind is `unreachable` or `remote-error`. It still imports `RepoFailed` from `./git.ts`.
- **`conduct.ts:3251`, `:4963`, `:5719`**: `accountWallOf(d)` becomes a small local `const wallOf = (text) => { const c = classify({ platform: 'runtime', text }); return c?.kind === 'account-limit' ? c.runtime : null }` in `conduct.ts`. That is not a re-export; it narrows the result in the file that reads it.
- **`client.ts:574`** becomes `err.status === 403 && classify({ platform: 'github', status: err.status, text: err.detail })?.kind !== 'rate-limited'`.
- **`git.ts:68`'s comment** names `classify`'s git rows in `@lingtai/domain`.
- **`integrate.ts:462`'s comment** says *"a form `PUSH_REJECTED` does not read"*; rename it to the `push-rejected` row.

## Tests

- **Existing tests are converted, not rewritten.** Move each test beside the module (`packages/domain/unit/failure-*.test.ts`) or leave it where it is.
  - The predicates become, e.g., `classify({ platform: 'git', text })?.kind === 'unreachable'`.
  - `accountWallOf(x)` becomes the same narrowing as in `conduct.ts`.
- **`packages/github/unit/tagged-errors.test.ts:37-41`** is a fourth reader of `.rateLimited` that the ticket does not list. Convert its four assertions the same way; the expected booleans do not change.
- **The precedence test** is the ticket's two cases, plus one that iterates `FAILURE_ROWS` and asserts the git kinds appear in the order above. That guards against a sort without hard-coding indices.

## The generated section

- **Markers**: `<!-- generated by pnpm docs:errors — do not edit -->` and an end marker, placed around the four bullets under *What Lingtai recognises today* (`platform-errors.md:100-130`). The **Not built** bullet and everything after it stay hand-written, outside the markers.
- **The script**: `pnpm docs:errors` runs `node packages/domain/scripts/platform-errors.ts && oxfmt doc/design/platform-errors.md`. This follows `events:generate` (`package.json:31`), which runs a domain script and then formats.
  - Without the format step, the committed file fails `pnpm fmt:check` or the staleness test, depending on which ran last.
  - The test therefore compares against formatted output. Simplest is to have `renderRecognised` emit text oxfmt leaves alone (no long lines that it would rewrap), and verify that by running the script twice.
- **Render rule**: one bullet per platform, with its rows in table order. Name the pattern's source and the export (`classify`, `standDown`), never a `file:line`; line numbers are the staleness the ticket is removing.
- **What is not matched**: the current prose also says what is *not* matched, for example *"Nothing matches a 5xx, a 529, a 429…"* and *"`githubJson` … drops every header"*. Carry these as a per-platform `unmatched` sentence in a small `PLATFORMS` record in `classify.ts`, rendered after the rows, so the generated section loses no fact the hand-written one had.
  - Lift the sentences verbatim.
  - The Codex and Claude Code bullets' `neverStarted`/`codexClose` facts belong in that sentence too, because they are not classify rules (Out of scope).
- **The staleness test** sits in `packages/domain/unit/` and reads the committed file the way `apps/cli/unit/cli-doc.test.ts:16-18` does. Its message is `doc/design/platform-errors.md is stale — run \`pnpm docs:errors\` and commit it`.
