# #1158 — design note

## Where the refusal goes, and why there

Put it in `resolveSource` (`packages/recipe/src/resolve.ts:212`), next to `unknownKeys`. It runs after `applyPreset` and **before** `Recipe.safeParse`. It can't go anywhere later. `runtime` is a plain `z.object`, so once `tier` leaves the schema, zod drops the key without a word. `resolve.ts:277` already describes this failure: *"`Recipe` is `z.object` and not `z.strictObject`, so a key it does not know is **silently dropped**"*. A refusal written after the parse would never see the key. `unknownKeys` only looks at top-level keys, so this is a separate check of `applied.recipe.runtime?.tier`.

The check belongs in `resolveSource`, not in `local.ts`'s `shape` callback, because both paths go through `resolveSource`:
- `resolveRecipeEffect`, at `resolve.ts:197`
- `resolveLocalRecipe`, at `local.ts:37`

That covers the conductor, `lingtai doctor`'s recipe row and the board without further work. Presets carry no tier (`presets.ts` has no `tier`), so checking before or after the preset gives the same answer. Check after it, as `unknownKeys` does.

Values:
- `sandboxed`, `guarded`, `open`: the ticket's three sentences, one each.
- Anything else, including `null` and a typo: *delete `runtime.tier`: containment is the `sandbox` block, and failing closed is always required*. Every value present is refused. None is ignored.

Each sentence must start `runtime.tier: …`, the way the other refusals name their path.

## `ResolvedRecipe.tier` goes too

Delete the field (`resolve.ts:76-77`, `:269`). The compiler then lists every reader, and these four belong to this ticket because they stop compiling:

- `conduct.ts:1027`: the log line drops `, tier …`.
- `conduct.ts:1146`: replaced by the check below.
- `onboard.ts:626`: drop the `tier X, ` clause from the message. Don't substitute a value. Saying the setup *added at guarded* would be false now.
- `apps/board/src/lib/queued.ts:218` and `:315`: both read `recipe.runtime.tier`. Pass the literal `'guarded'`, and add a comment naming the follow-up ticket. That's the column default `board.ts:1401` already falls back to, so the board shows what it showed before. The follow-up deletes the field.

## The hash

In `forHash` (`resolve.ts:143`), return `{ ...recipe, runtime: { ...recipe.runtime, tier: 'guarded' }, steps }`. Write it unconditionally, not "only if absent":
- Every recipe that still resolves had `'guarded'` here before. `sandboxed` and `open` are now refused, so nothing that resolves had another value.
- The function stays idempotent, which the existing comment requires. `recorded-recipe.test.ts` hands `hashRecipe` a body that has already been through it.

Two consequences:
- `canonicalRecipe` will keep writing `runtime.tier: "guarded"` into `StepsResolved.recipe`. This is intended: it's the document the hash covers (0047 §2).
- The return type is already `Record<string, unknown>`, so `Recipe` losing the key costs no cast.

Put a comment beside `NOT_YET_IN_THE_HASH` that gives the same reason: *a hash cannot be upcast*.

**Record the fixture hash before editing anything.** Write a small fixture recipe with no `tier` key, and compute its `configHash` with this worktree's unmodified code. The worktree is at main's head, so that's the "hash recorded from `main`" that *Done when* asks for. Then hard-code that hash in the test. If you compute it after the edit, the test proves nothing.

## The failing-closed check

Replace `meetsTier` and `missingForTier` (`packages/agent/src/runtime.ts:327-363`) with one exported function. For example, `missingToFailClosed(capabilities): string[]` returns `['pre-tool-use-interception']` when `!capabilities.canFailClosed`, and `[]` otherwise. Keep that name. `runtime.ts:353` says why: *"The name predates 0016 and is kept because the event carries it"*. Old and new `DispatchRefused` events then use one vocabulary in `missing`.

In `conduct.ts`, section 3 (`:1145-1215`):
- Keep the walk over `[options.runtime.capabilities.id, ...secondRuntimes]` through `runtimeNamed`. Only the predicate changes.
- Keep the `DispatchRefused` append on the ticket stream, without `requiredTier`.
- Return `{ ok: false, ticketId, runId: null, stage: 'dispatch', detail }`, where `detail` is `${project}: ${id} cannot fail closed: missing pre-tool-use-interception.`
- Delete `pauseConductorOnce` (`:1086-1143`) and its call.
- Drop the `type Tier` import (`:43`) and `missingForTier` (`:35`).
- Drop `tier` from the invocation record at `:4445`.
- The block comment at `conduct.ts:111` (*match the tier*) gets reworded.

`runtime.ts:340` says this check never fires today: *"both runtimes declare `canFailClosed`"*. So it is tested only through the conductor's injected runtime (`options.runtime` or `runtimeFor`), using a fake whose `canFailClosed` is false. Without the pause, a runtime that can't fail closed would get a `DispatchRefused` appended on every pass. That's the per-project rule #676 chose. It can't happen with today's runtimes, so this ticket doesn't build anything to stop it repeating.

## Events and their readers

- `events.ts:543`: `requiredTier: Tier.optional()`. Rewrite the `@summary` above it. *"Never silently downgrade a tier"* is the old rule, and the new event is about failing closed.
- `events.ts:572`: `tier: Tier.optional()`.
- `ticket.ts:278`: `requiredTier?: Tier`. `ticket-codec.ts:77` reuses the `DispatchRefused` schema, so the snapshot codec widens with it. Making a field optional only widens what decodes, so old snapshots still decode and the reducer version stays unbumped.
- `history.ts:277`: when `requiredTier` is absent, render `${runtime} cannot fail closed — missing …`. Keep the old sentence when it is present.
- `task-view.ts:407`: same split, `${runtime} is missing …` with no `needs`.

`Tier` stays exported from `@lingtai/domain`, because the event schemas use it, so `doc/reference.md`'s term stays too. Regenerate with `pnpm events:generate`, and commit whatever it rewrites.

## Tests that move

- Delete `conduct-pause-snapshots.test.ts` (the ticket says why).
- Recipe and conductor tests that build `tier:` into a recipe: `rg -l "tier" packages/*/unit apps/*/unit packages/*/test` finds them. Fixtures that only *pass* `tier: 'guarded'` lose the key. Tests that exercise a `sandboxed` refusal turn into the failing-closed test.
- Test data that writes `requiredTier` (`packages/domain/test/histories.ts:336`, `packages/projector/test/contract.ts:221`, and others) can stay. That data is now the old shape, and it is exactly what the "old events still decode" claim needs. Add one new-shape `DispatchRefused` beside each reader test, rather than rewriting the old ones.

## Edges the ticket leaves to the design

- **Task page and old commits.** `recipeOfAttempt` re-resolves the in-repo `.lingtai/config.yaml` at an attempt's base commit (`apps/board/src/lib/recipe.ts:265`). If a pre-#180 commit wrote `runtime.tier` there, it is now refused. The page falls back to head and names the refusal, without throwing (`:308`). Accept this: it only affects attempts from before #180, and the page says why. This repository's copy has no `tier`.
- **Rebuild.** Projections reduced again from the old log see `requiredTier` present and keep the old sentence. Nothing in a rebuild needs the new path.
- **Integration half.** Nothing here depends on it. Every claim above has a unit-level test: resolve, hash, the conductor with a fake runtime, decode, and the two renderers.
