### Finding 1: the first header line is the title slot, and `parse` refuses a title that reads as something else

The failure is in `parseTicketForm`. Line 0 is already special for blank-line detection (`indexOf('', 1)`, `ticket.ts:298-301`, *"line 0 is always the title, however it reads"*). But the `#!` filter runs over the whole header before the title is chosen (`ticket.ts:305-306`). A title `#! foo` is therefore dropped, and the `labels:` line becomes the title. The labels come back `[]`, `parse` returns `ok: true`, and `ticketNew` creates the ticket and discards the file (`ticket.ts:430-436`).

Calling `titleAndLabelsRoundTrip` from `ticketNew` would **not** catch this, which is the trap in how the finding is worded. The parsed title `labels: bug` round-trips perfectly, because by then the damage is already done. The refusal has to come from looking at the text, not at the parsed form.

So make `parse` treat line 0 as the title, whatever it holds:
- Take `title` from `headerLines[0]`.
- Apply the `#!` filter only to `headerLines.slice(1)`.
- Return `ok: false` when line 0 starts with `#!`, with a reason naming it: *the first line is the title, and a title starting `#!` reads as an instruction*.
- Refuse a line 0 starting `labels:` the same way. It is the same silent failure from the other direction: a person in `new` deletes the empty first line, the `labels:` line becomes the title, and the labels are lost.

`render` never puts an instruction at line 0. `new`'s `#! kinds` line sits after `labels:` (`ticket.ts:277`), so `new`'s unchanged-form path and the round-trip test are untouched.

Consequences that need no extra code:
- `ticketNew` already handles `!after.ok` by keeping the file, printing the path and returning 1 (`ticket.ts:411-414`). That is exactly the refusal the finding asks for.
- `ticketEdit`'s pre-editor guard (`ticket.ts:360-366`) now refuses a stored `#!` title through `parsed.ok === false` instead of the title comparison. The test at `unit/ticket.test.ts:396` should still pass. Check its expected message.
- The precondition sentence in the `renderTicketForm` doc comment (`ticket.ts:262-267`) gains *"and does not start `labels:`"*.

### Finding 2: an unedited body is written back as the stored row's own bytes

`formFromTicket` trims the stored body so that "no change" is decided correctly (`ticket.ts:334-344`). That trim is right and stays. The bug is that the trimmed body is also what gets written: `updateFields(..., { body: after.form.body })` (`ticket.ts:525-529`). This happens even when `changed` (`ticket.ts:514-517`) does not contain `body`.

Fix it at the write: send `body: changed.includes('body') ? after.form.body : ticket.body`. `expected` is already the raw row (`ticket.ts:523`). The `WHERE` clause compares raw columns (`db-tickets.ts`, `updateFields`), and the write now leaves an untouched column untouched.

Title and labels need nothing. A stored title or label with surrounding whitespace already fails `titleAndLabelsRoundTrip` and is refused before the editor opens.

Test it against the real `dbTickets` on the `:memory:` seam the file already uses:
1. Create a ticket whose body is `'line\n\n'`.
2. Edit only the title.
3. Assert that `getIssue(n).body === 'line\n\n'` and that the log says `updated #n — title`.
