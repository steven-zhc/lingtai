## Design: `lingtai ticket new` / `lingtai ticket edit <n>` (#386)

### Where it goes

- **`apps/cli/src/ticket.ts`** gets `ticketNew(options, log, reading)` and `ticketEdit(options, log, reading)` beside `ticketList`/`ticketClose`. Each returns an exit code and starts the same way they do: `pickProject` (`ticket.ts:52`), then `resolveDbRecipe` (`ticket.ts:88`). It also gets the exported pure pair `renderTicketForm` and `parseTicketForm`.
- **`apps/cli/src/lingtai.ts`**: add `new` and `edit <n>` to the `case 'ticket'` switch (`lingtai.ts:1266-1287`). `edit` parses its number the way `close` does (`:1278-1282`). Add both to the fallthrough usage line (`:1285`) and to `USAGE` beside `:154`/`:161`.
- **`packages/conductor/src/db-tickets.ts`** gets two new verbs, which is the decision the ticket does not make (see the next two sections).

### Changing a title needs a verb, and it goes on `DbTickets`, not on `Tickets`

The ticket routes writes through `createIssue`, `setLabels` and `updateBody`. Nothing in that list changes a title. `Tickets` (`ticket-store.ts:58-71`) has no title verb, and neither does `dbTickets` (`db-tickets.ts:251-351`). If `edit` worked only through those three, a changed first line would be silently dropped.

Add `updateTitle(number, title)` to **`DbTickets`** (`db-tickets.ts:146`). Copy `updateBody`'s statement shape (`:343-350`), with the same `noSuchTicket` on zero rows. **Don't add it to `Tickets`.** That interface is pinned against `GitHubClient` structurally (*"`GitHubClient` satisfies this structurally — pinned in `unit/tickets.test.ts`"*, `ticket-store.ts:38-41`). Widening it means a GitHub method, a `memoryTickets` method and a contract case, all for a CLI that refuses every non-`db` project before it opens a store (`ticket.ts:99-104`). `commentBodies` is the precedent: a verb only the DB store has, on `DbTickets` (`db-tickets.ts:146-148`).

So `TicketReading.ticketsFor` (`ticket.ts:38`) changes to return `Promise<DbTickets>`. The existing tests already hand it `dbTickets(...)` (`unit/ticket.test.ts:73`), so they still compile. Add one case for `updateTitle` to `packages/conductor/unit/db-tickets.test.ts`: it changes the title, and an unknown number rejects.

### Closing the edit race needs the check and the write to be one statement

Two `edit` sessions on the same ticket can overlap: both read the row, one person's editor is open longer than the other's, and whichever saves second must not silently overwrite the first — the gap is however long an editor stays open, and a check that is a separate `SELECT` before the `UPDATE` only narrows that gap to the round trip between the two, which is still a window.

So the check **is** the write: `DbTickets.updateFields(issue, expected, next)` sets title, labels and body together in one `UPDATE`, with `expected`'s three fields in the `WHERE` clause alongside `project`/`number`. If the row no longer holds exactly what `expected` says, the statement matches zero rows and throws — there is no separate read for another writer to land inside of. `expected` is the raw row `ticketEdit` read with `getIssue`, before the editor opened, not the parsed/trimmed form: the `WHERE` clause is comparing the stored columns byte for byte, and the parsed form's `trimEnd()`ed body would never match a stored body that is not already trimmed.

### "Unchanged" compares parsed forms, never text and never the row

This is the part that makes `edit` "change only what changed". It is also the real way the ticket's round-trip trap bites.

- **Not text equality.** Most editors add a final newline on save, so the saved text differs from what was rendered even when the person touched nothing.
- **Not against the stored row.** `parse` trims, as described below, so a stored body with trailing whitespace would never compare equal and would be rewritten on every `edit`.

The rule: `before = parseTicketForm(rendered)` and `after = parseTicketForm(saved)`.

- If they are deep-equal, write nothing, keep the file, print `no change — nothing written` and exit 0. This is checked **before** the empty-title refusal. An unchanged `new` form has an empty title, and quitting it is the "do nothing" case, not an error.
- Otherwise, `edit` writes title, labels and body **together, in one statement** — `DbTickets.updateFields`, conditioned on the row still holding exactly what was read before the editor opened (see "Closing the edit race" below). Print which fields differed.
- `new` calls `createIssue` once with all three fields.

### The form, exactly

The header is everything before the **first blank line**. The body is everything after it, verbatim except that `trimEnd()` is applied.

In the header:
- Lines starting `#!` are dropped.
- The first remaining line is the title, trimmed.
- An optional `labels:` line follows. Split it on `,`, trim each entry and drop empty ones.
- **Any other header line is refused**, for example a forgotten blank line, so that body text lands in a header slot. Refuse by name rather than guessing which part was meant.

**`#!` is recognised only in the header.** That is how the Done-when round-trip holds for a body that contains a `#!` line or a `labels:` line without any escaping scheme. A body line is never a header line, because the first blank line ends the header and body blank lines come after it. `new` puts its instruction line in the header, after `labels:`:

    #! kinds: bug, tech-debt, feature, documentation — one belongs in labels:, or the queue never sees this ticket

It is built from `queueOf(recipe).kinds`, as `ticketList` does (`ticket.ts:123`). `render` takes these lines as an optional second argument. `edit` passes none, and the round-trip property is stated for `render(t)` with none.

`parse` returns `{ ok: true, form } | { ok: false, why }`, and the stray header line is its one `why`. **The empty title is not one** — `parse` accepts it, because both callers need to compare the parsed form against the ticket's unedited form to decide "no change" before they decide "no title", and folding the empty-title case into `parse` would make that comparison collapse two different saves (same blank title, different body) into one. `ticketNew`/`ticketEdit` check `after.form.title === ''` themselves, after the "no change" check.

Where the round-trip test lives: the property holds for titles and labels with no surrounding whitespace, no comma inside a label, a title not starting `#!`, and a body with no trailing whitespace. The unit test asserts it on such a ticket. It should also assert separately that a saved text with an extra trailing newline parses equal to the original.

### The editor seam, which covers the file as well as the process

0060 §1 makes a temporary file integration just as much as a spawned process. The ticket's own wording is *"A temporary directory is still the filesystem"* (CLAUDE.md). So the injected step has to own **the file as well as the editor**, or no unit test can check that "the text is kept" in a file:

```ts
// added to TicketReading
env?: Record<string, string | undefined>        // default process.env
edit?: (command: string, initial: string, name: string) =>
  Promise<{ text: string; path: string; discard(): Promise<void> }>
```

- **The editor command is resolved in `ticket.ts`, so its refusal is unit-testable.** Take the first non-blank of `env['VISUAL']` and `env['EDITOR']`. If neither is set, log a refusal naming both variables and exit 1. Do this **before** `getIssue` or any write. Reading `process.env['…']` directly for a non-`LINGTAI_` name is the house pattern (`lingtai.ts:701`, `restart.ts:891`).
- **What the default `edit` does:**
  1. `mkdtemp` under `os.tmpdir()`.
  2. Write `<project>-new.md` or `<project>-<n>.md`. The `.md` gives editors Markdown highlighting.
  3. Run `spawnSync('sh', ['-c', `${command} "$1"`, 'lingtai-editor', path], { stdio: 'inherit' })`. Going through `sh` lets `code -w` and `emacsclient -t` work, because `$EDITOR` carries arguments.
  4. Read the file back.

  A non-zero editor exit throws. `ticket.ts` catches that and treats it like a refusal: it keeps the file, prints the path and exits 1. The default `edit` is not unit-tested, by design.
- **Only a write that actually landed discards.** Call `discard()` after a successful `createIssue`/`updateFields` and nowhere else. The "unchanged" path does **not** discard, even though nothing was wrong with the form: `spawnSync` returning is not proof the editor is done — a non-blocking `$EDITOR` (`code`, `subl`, `open -a TextEdit`) returns immediately, and discarding here would delete the directory while the person is still typing into that path. Every other refusal (empty title, stray header line, editor failure) keeps too. Print `your text is kept at <path>` on every path that keeps. Unit tests fake `edit` with a fixed `path` and record whether `discard` was called.

`edit <n>` calls `getIssue(n)` before opening the editor. An unknown number is refused by name the way `ticketClose` refuses it (`ticket.ts:179-185`), so nobody types into a form for a ticket that does not exist.

### After `new` writes

Print `created #<n>  <title>`. If `kindOf(created, kinds)` is null (`discover.ts:95`, already imported at `ticket.ts:17`), add one line saying the ticket carries no kind label and the queue will not take it. Still create the ticket: the form told the person, and the store translates rather than judges (`ticket-store.ts:20`).

Like `close`, neither command appends an event or holds a projector (`ticket.ts:6-10`). Add `new`/`edit` to that header's first line.

### Tests

The new cases go in `apps/cli/unit/ticket.test.ts`, with the same three seams as today plus `env` and a fake `edit` that returns a scripted `text`. They cover every Done-when box. `pnpm test` and `pnpm typecheck` check all of it, and nothing here needs the integration half.
