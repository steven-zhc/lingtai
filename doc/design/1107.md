# Design: #1107 — the triage queue and its scans as Effects

Line numbers below are this worktree (`86df368f`). CLI-14 has landed here, so `daemon.ts` and `work-loop.ts` no longer match the ticket's `8abc8613` numbers.

## 1. `enqueue` is an Effect. `enqueueTriage` is a synchronous face over it, with no `services` captured

The ticket's plan is a single `Effect.runForkWith(services)` inside a synchronous `enqueueTriage`, with `services` captured in `daemonTriagePorts`. Don't build it that way. The daemon never calls `enqueueTriage`. Only the tests call it: `unit/triage-trigger.test.ts:130-187` and `unit/triage.test.ts:1168-1174`. The two daemon paths, `catchUpWait` (`triage.ts:159`) and `onWaitStarted` (`:318`), will be Effects themselves after this change.

So:

- **`enqueue(key, work: Effect<unknown, unknown>, log): Effect<{ added, done, settled }>`** (module-private).
  - The map check, the two `Deferred.makeUnsafe` and the `queued.set` are synchronous inside it.
  - It starts the worker with `Effect.forkDetach`. A detached fork keeps the caller's context, so the daemon's tracing (#791) reaches the agent's spans without any `services` parameter. `daemonTriagePorts`' signature does not change.
- **`catchUpWait` and `onWaitStarted` `yield* enqueue(…)`.**
- **`enqueueTriage(key, run, log)` stays exported and synchronous:** `Effect.runSyncWith(Context.empty())(enqueue(key, run, log)).added`.
  - The ratchet does not count this call. Its `RUN` pattern is `/^run[A-Z](?!\w*With$)/` (`packages/domain/unit/effect-ratchet.test.ts:70`), so `run` stays at 1.
  - A `forkDetach` without `startImmediately` returns before the child runs, so the sync run never suspends.

The permit is `const permit = Semaphore.makeUnsafe(1)` at module level, beside `queued`. The precedent in this tree is `packages/daemon/src/failure-recorder.ts:48`. Effect 4.1.2's semaphore keeps its waiters in an insertion-ordered `Set` and releases them in order (`effect/dist/Semaphore.js:86,117`). With one permit that is first-in-first-out, as the old `tail` chain was.

## 2. The worker's teardown, in the old order

The worker is `permit.withPermits(1)(work)`. Take its `Effect.exit`, then run the teardown below in this order. Wrap it so that a death or an interruption also reaches the key's deletion (`Effect.ensuring`).

1. **`Deferred.done(done, exit)`.**
   - `done` fails when the worker failed. `catchUpWait`'s `Deferred.await(done)` then fails the scan, as `await first.done` rejects today (`:186`).
   - `triage-catch-up.test.ts:447` and `:463` pin that rejection (`rejects.toThrow('temporary append failure')`).
2. **On a failure, log `triage ${waitId}: …`**, using the old formula `err instanceof Error ? err.message : String(err)` on `Cause.squash(cause)` (`:84-86`).
   - **Not `recovering`**: it reads `.message` off the squashed value (`apps/cli/src/exit.ts:31`), and `triage-trigger.test.ts:178-187` pins `triage wait-nullish: null` and `…: undefined` for a worker that rejects with `null` or `undefined`.
3. **`queued.delete(id)`.**
4. **`Deferred.succeed(settled, void)`.**

**The delete must come before `settled`.** The `HELD` rejoin (`:189-193`) awaits `settled` and then calls `start()` again. It must get a new worker (`added: true`), not the stale entry. Today the `.finally(delete)` is part of `tail`, and `tail` is `settled` (`:82-92`).

A worker that dies would otherwise leave its key in `queued` forever. Every later scan of that wait would join a dead worker, so it would never triage again. That is why the teardown needs `ensuring` and not only the success path.

## 3. `triageIssue` and `base` feed a promise port that stays a promise until CLI-17b

`TriagePorts.issue` and `TriagePorts.base` are promise-typed (`triage.ts:466-468`). `gatherEvidence` awaits them (`:512`, `:517`), and that code is out of scope here. Leave `TriagePorts` as it is and bridge inside `daemonTriagePorts`' `run`:

```
run: (request) => Effect.gen(function* () {
  const services = yield* Effect.context<never>()
  const now = Effect.runPromiseWith(services)
  return yield* lift(() => waitTriage({ …, issue: (id, s) => now(triageIssue()(id, s)), base: (id) => now(baseOf(id)) }, request))
})
```

- `baseOf` is the `:413` closure rewritten on `loadProjectEffect`.
- `runPromiseWith` is not counted, as at `apps/cli/src/approve.ts:77`.
- Neither closure is `async` any more.

`triageIssue(read, load)` takes the Effect readers:

- `read` is `readProjectTicketEffect`'s shape: `(state, number, options) => Effect<TicketRead>` (`packages/conductor/src/read-ticket.ts:60`).
- `load` is `loadProjectEffect`'s shape.
- `apps/cli/unit/ticket-reader.test.ts:45-57` runs it with `Effect.runPromise` and keeps its expected strings. Its comment at `:21` (*"still handed the promise reader (CLI-17)"*) becomes false: update it. This file is not in the ticket's list, but it calls `triageIssue`.

## 5. `onWaitStarted`'s fan-outs

- **Each branch is one `Effect.forkDetach`.**
  - In the `DayCeilingLifted` branch, `projects` (absent means none) is followed by one detached fiber per name.
  - Each project's `triageFor` plus `catchUpTriage` carries its own `catchCause`, so one bad project does not skip the rest.
  - Each project is its own detached fiber, as the per-project fan-out was, so a stalled read for one does not hold back the rest; the agents are still serialised by the queue.
- **The log strings stay `triage catch-up ${project}: …` and `triage catch-up: …`.**
- **The two inline `.catch` calls become `catchCause → null`, letting interruption through:** `triageFor(...).catch(() => null)` (`:303`) and the `daemonStartedAt` read (`:309-313`, #583). The handler then returns.

## Tests

The fakes become Effects, with a promise wrapped in `lift`. `triage.test.ts:1170` wraps `waitTriage`, and no expected string or boolean changes.

The tests wait with `drained()`. If it only flushes microtasks and `setImmediate`, Effect's scheduler may need one more turn. Change the helper, not an expectation.

The two new cases in the Done-when are unit tests, and everything here is checked by `pnpm test`. Nothing in this change rests on the integration half.

The ticket's precedent for the semaphore, `packages/projector/src/sqlite.ts:444`, is not where `Semaphore.makeUnsafe` is in this tree. Use `failure-recorder.ts:48`.
