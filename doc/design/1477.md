# #1477: how to build it

The ticket already gives the shape. This note covers three things it leaves implicit: where the test seam goes, how the board reaches `ProjectState`, and one wording decision.

## 1. The record goes through one exported helper, and `conductorTurn` is driven through its seams

`conductorTurn` used to reach the log, the registered projects, `hasGitHubApp()` and the world straight from the environment, so a test could not drive it; `projectsForTurn` was extracted for that reason (`conduct-ownerless.test.ts`). `ConductOptions` now carries four optional seams, `store`, `projects`, `githubApp` and `world`, which default to what a turn used before, so `conductorTurn` itself is unit-tested and removing a record call from it turns a test red.

- **Helper.** `refuseProjects(projects, detail, { store, codeSha, log })` calls the private `record()` with `{ refused: true, detail, ref: null, codeSha }` for each project with a name. `ref` is `null` because no recipe was read; `ProjectRefused.ref` is documented as *"Null when the pass failed before it knew"* (`events.ts:2516`).
- **Hook branch.** It loads the registered projects, calls the helper on every one, then pushes the `'*'` entry and `tell`s as before, so `daemon.ts:798-805` is unchanged. Nothing is recorded inside `projectsForTurn`: it stays pure. `conductorTurn` calls the helper on `registered.filter(p => !projects.includes(p))` after it: the owner projects it dropped for *no GitHub App*.
- **The tests.** `apps/cli/unit/conduct-refuse-projects.test.ts` runs `conductorTurn` over `createMemoryEventStore()`: a missing hook binary records one `ProjectRefused` per project, an identical second turn records nothing, and a turn with the binary back records `ProjectRecovered` through the real look (`where.looked`). A second case runs a turn with `githubApp: false` and checks only the GitHub project is refused, once.
- **Ordering.** The record happens before `return outcome`, so this turn's refusal is on the log when the line prints. `record()` already swallows its own failure.

**A failed project load in the refusal branch** is logged and swallowed. The turn still returns the refusal it already had. Today a store failure there doesn't exist, because nothing is read. Don't turn it into `turn failed`; that would hide the hook message the operator needs most.

**The idle-recovery edge is settled in code.** `where.looked` runs right after the recipe and the ticket client resolve, before anything is listed: `:281` for owner-less projects, `:332` for GitHub ones. The comment there says *"Looked at, now — not when the run below returns"*. So a project with nothing runnable still records `ProjectRecovered`, and no other recovery site is needed. Whether this happened on a real system is settled by a `ProjectRecovered` with that `data.project` following the `ProjectRefused`.

## 2. `WhyFacts.refused`, and its place in `rootBeforeChains`

Add `refused?: { detail: string; at: Date } | null` to `WhyFacts` (`why-nothing-runs.ts:32-51`). Make it optional, like `conductorHeld` (`:35`), so the existing fact literals in tests and callers keep compiling. In `rootBeforeChains`, put a `'refused'` branch after the `lock` block (`:161-169`) and before `return null` (`:170`).

- **Sentence.** Something like `` the conductor refused this project since HH:MM — ${detail} ``, built with the file's own `clock()` (`:136`).
- **Don't wrap `detail` in backticks.** `segmentsOf` (`why-line.ts:50-55`) treats backticks as code delimiters, and a detail could contain one.
- **Root kind.** Add `'refused'` to `RootKind` (`:53+`).
- **Board tone.** Give it a tone in `TONES` (`why-line.ts:39-47`). Use `'down'`: the system can't work this project, which is the same register as `no-daemon`. The map is `Partial`, so leaving it out would compile and silently draw the sentence untoned. That's why it's worth saying here.

`rootBeforeChains`' doc says *"Installation-wide stops"* (`:138`). A project's refusal isn't installation-wide, so edit that line to "stops that hold everything this project has queued".

## 3. The board looks up the `ProjectState` itself

The board has no `ProjectState` where the sentence is built. `readWhy.why` receives an `AskableFilter` (`why-read.ts:26-37`), which is `Extract<ProjectFilter, { ok: true }>` (`board.ts:955`), not a `ProjectState`. Thread nothing through `askProject` (`board.ts:993`). Inside `readWhy.why`, add `readRegistered()` (`locks.ts:52-61`) and find the entry by `filter.project`:

- It is `cache()`d per request, so it adds no read; `readProjectLocks` already calls it (`locks.ts:125`).
- If the lookup fails, set `refused: null`, inside the existing `Effect.catch` (`why-read.ts:103`).
- It's a promise, so it goes in `Effect.tryPromise`, like `readProjectLocks` at `:55`. That keeps the effect ratchet unchanged.

Status already holds `project` in its loop (`status.ts:462`), so it passes `project.refused` into the facts at `:656`.

## Where setup fails

`status.ts` builds the sentence for the queue it could read, and for a project the conductor refused even where the queue could not be read: no GitHub credentials or a recipe that would not resolve do not make the refusal less true, and the explicit *no GitHub App* refusal is exactly such a project. With the source unanswered, the log's queued rows are what is waiting, as the board reads them for an unanswered project. A project with no recorded refusal is explained as before, by the Queue section's own unreadable-source line.

The board does the same in `askQueue`: a project `queueFilters` could not resolve is not asked, so `readRefusedWhy` says its recorded refusal beside the problem the column already shows.

A refusal's time carries its date when it was recorded on another day: transition-only recording means a refusal outlives a day, and `since 09:05` would read as ten minutes old.

## Where the queue cannot be listed

A project whose setup failed has no queue to list, and one GitHub has not answered for may have no row in `task_view` yet. A recorded refusal holds whatever is waiting, so `WhyFacts.queueUnseen` lets `mayApply` pass on a refusal alone; `status.ts`, `readRefusedWhy` and the board's unanswered `readWhy.look` set it where they did not see the queue. The refusal root then carries no ticket numbers.

## Checks

Everything is unit-level and nothing needs `pnpm test:integration`:

- **`why-nothing-runs.test.ts`:** a `refused` root carries the detail, and there is no `unknown`; `lock` beats `refused`; with `queueUnseen` a refusal shows over no queued rows.
- **`apps/cli/unit/conduct-refuse-projects.test.ts`:** `conductorTurn` over the memory store, as described in §1.
- **`apps/cli/unit/status.test.ts`:** a `ProjectState` with `refused` set asserts on `root: 'refused'`, also where setup failed and no row is queued.
- **`apps/board/unit/refused-unreadable.test.ts`:** `askQueue` says the refusal of a project whose filter did not resolve.

No ADR is touched. 0027 (no clock) holds because `refused.at` is the event's own time (`project.ts:38-42`).
