## Decisions the ticket leaves open

**1. The completeness rule is stricter than the ticket's, because the ticket's rule loses entries.** srt keeps the last 100 entries across every command (`sandbox-violation-store.js:22-24`, `slice(-this.maxSize)`). The ticket says "incomplete when the count moved by more than what the read returned plus 100", and that rule can be wrong. Suppose 150 entries arrive after `wrap`: 60 of them are ours and sit in the newest 100. The oldest 50 were evicted, and some of those may have been ours too. The ticket's rule compares 150 with 160 and answers *complete*, which is false.

The sound rule is **`complete = 0 ≤ after − before ≤ 100`**. Every entry added since `before` is still held exactly when no more than 100 were added. If `after < before`, the store was replaced (a `reset`), so that case is also `complete: false`. This rule still passes the ticket's Done-when test, because `after − before > returned + 100` implies `> 100`. Name the 100 `SRT_STORE_SIZE` and quote `this.maxSize = 100` beside it.

**2. `before` is taken inside `wrap`, before `registerCommandNetworkLists`, and it travels on `Wrapped`.** Add `readonly violationsBefore: number` to the struct at `sandbox.ts:46-51`. Don't keep a map in the service: `Wrapped` is the only handle a caller has (`commandId` is minted at `:139`). A failed count read must not fail the wrap. Store `undefined` instead, and the read then answers `unreadable` with reason `the violation count could not be read at wrap`. Never treat that case as complete.

**3. The read happens inside the wrap's scope.** `wrap` runs under `Scope`, and closing it calls `cleanupAfterCommand` and `unregisterCommandNetworkLists` (`sandbox.ts:141-153`). The layer's own finalizer calls `srt.reset` (`:108`). I have not checked whether those clear the store, so the safe rule is that #1164 reads after the child exits and before the scope closes. Say so in the JSDoc of `refusedConnections`. That is what #1164 needs to be told.

**4. Lookup by `commandId` is correct in srt 0.0.83, with one blind spot.**
- `getViolationsForCommand(x)` compares `encodeSandboxedCommand(x)` (`sandbox-violation-store.js:39-42`). The attribution key is the `commandId` when one is passed (`sandbox-utils.js:991-994`, `attributionKeyFor`). So passing `commandId` to the port is right, and that key is what a violation carries.
- The blind spot: `recordOutboundDeny(host, port, reason)` at `sandbox-manager.js:772` passes no `encodedCommand`, so that deny is stored unattributed. No read by id can see it, and the count rule cannot detect it either. Write that in a comment and leave it alone. It is not this ticket's to fix.

**5. Violation lines come in three shapes, not one.** 017 recorded only the first. srt 0.0.83 produces all three (`sandbox-manager.js:458`, `:730`, `:760`):

| Line | Parse |
|---|---|
| `deny network-outbound example.com:443 (host is not on the allow list)` | `{ host, port }` |
| `deny socks-tunnel host:port (refuseOpaqueTunnels)` | `{ host, port }` |
| `deny http-request METHOD target (reason)` | the host and port of `target` when it is an absolute URL; otherwise unknown |

- Split `host:port` at the **last** colon, and strip `[` and `]` from an IPv6 literal.
- Anything else, including a file deny should srt ever start attributing one, is `{ host: null, port: null, line }`, kept whole as the ticket says.
- Write one unit test per row, plus an unknown line, plus an IPv6 case.

**6. How entries group.** One entry per `(host, port)`. An unknown line groups by its exact `line`. Each entry is `{ host: string | null, port: number | null, line?: string, count, firstAt, telemetry }`:
- `firstAt` is the earliest `timestamp` (an ISO string; srt gives a `Date`, `macos-sandbox-utils.d.ts:73-78`).
- `telemetry` is always `false` when the host is null.

**7. `TELEMETRY_HOSTS = ['sentry.io', '*.sentry.io']`.** Match it with a small pure function: `*.x` matches subdomains of `x` and not `x` itself, so the apex is listed separately. Do not import srt's matcher, because `unit/` must never load srt's module graph (`live.ts:1-3`).

**8. The read's value has the same shape as the event's variant.** It is:
- `{ kind: 'entries', entries, complete }`, or
- `{ kind: 'unreadable', reason }`.

Either port call throwing gives `unreadable`. The reason is fixed text, never the caught message, for the same reason as `sandbox.ts:84-85`: a message can carry a temp path. Export a pure `worthRecording(r)` that is false only for `entries` with an empty list and `complete: true`. That way #1164 does not re-decide the ticket's "appended only when…" rule at each call site.

**9. The resolved policy is built from the same functions `wrap` hands srt, so the two cannot disagree.** `resolvedPolicy(host, input)` returns:
- `allowedDomains`: `BUILT_IN_DOMAINS` and `runDomains(input)` (`policy.ts:53`, `:149`)
- `allowWrite`, `denyRead`, `denyWrite`: from `filesystemFor(host, input)` (`policy.ts:115`)
- `weakerNetworkIsolation`: `host.platform === 'darwin'`, mirroring `instanceConfig` (`:162`)
- `srtVersion`: `SRT_VERSION`

Expose it as `SandboxApi.policyOf(input)` using the service's own `Host`, because callers hold `Sandbox` and never `Host`. `SRT_VERSION = '0.0.83'` is a constant. A unit test holds it equal to `packages/sandbox/package.json`'s `dependencies['@anthropic-ai/sandbox-runtime']` through a JSON import. `resolveJsonModule` is on (`tsconfig.base.json:7`) and `apps/cli/src/version.ts` already does this. A JSON import is a module load, not a filesystem read in the test body, so it stays a unit test.

**10. The domain package owns the schemas; sandbox is held to them by a test.** `@lingtai/domain` depends only on `zod` (`packages/domain/package.json:18`), so it cannot import sandbox's types.
- Write the policy and entry schemas in `events.ts`.
- Add `@lingtai/domain` to `@lingtai/sandbox`'s **devDependencies** only.
- A sandbox unit test parses `resolvedPolicy(...)` and every read variant through the domain schemas, so a field added on one side alone fails the test.

**11. The boundary's discriminant copies `SandboxDecision` exactly** (`packages/recipe/src/sandbox.ts:51-55`). That means `kind` is `sandboxed | unsandboxed | refused`, `unsandboxed` carries `reason` (plus `why` when `degraded`), and `refused` carries `why`. Two warnings:
- **Do not reuse `Tier`.** `events.ts:87` already has a `'sandboxed'` value with a different meaning (0007's runtime tier).
- `sandboxed` carries `{ srtVersion, policy }`, not `project_additions`. The event records what was enforced, not what was asked for.

**12. Where each event is declared appended.** `EVENT_AT` is `['prepared', 'design', 'implement', 'review', 'build', 'proposed', 'merge']`, the union of `runPlugin.at` (`recipe.ts:189-195`) and `agentPlugin.at` (`recipe.ts:400-406`). The test at `conductor/unit/what-an-event-is-written-at.test.ts` checks *appended ⊆ declared* (comment at `events.ts:2550-2553`), so declaring it before any append is allowed. Give both payloads an `@summary` JSDoc like `RunFinished` (`events.ts:911`), because the generator reads it.

**13. The shared keys.**
- `step`: domain's `Step`.
- `action`: a string.
- `runtime`: optional, absent for a `run:`.
- `runId`: `z.string().nullable()`, required-but-null rather than optional, so "no run" is written down instead of left out.
- `commandId`: add it. It is the only key that ties an invocation's boundary to its refusals when one step runs the same action twice.

## Rules for the implementation

- **The ratchet.** `@lingtai/sandbox` is at 0 `async` and 0 `Effect.run*` (`live.ts:6`). The two new port members are `Effect.try` around `SandboxManager.getSandboxViolationStore().getViolationsForCommand(id)` and `.getTotalCount()`, both synchronous.
- **Fakes.** The existing fake in `unit/sandbox.test.ts` gains the two members. Keep it a fake per test; don't let one default store be shared.
- **Checks.** Every claim here is checkable by `pnpm test` and `pnpm typecheck`. Nothing in the shape needs the integration half. The live port's two lines are the one thing no unit test reaches, and #1164's first real run settles them: an empty `entries` with `complete: true` on a run that hit a host outside the allow list would be the failure. The event would then hold an empty list where the run log shows a refused host.
