# Design: #744, a build refusal the base shares buys no round

## 1. The base check is built but never called. Wiring it is half the work

`packages/conductor/src/base-check.ts:3-4` says so itself: *"the port the guard in #744 asks before a `build` refusal buys a round. Nothing calls it yet."* Nothing outside the unit test calls `createBaseCheck`. So `conduct.ts` has to build one, and **where it is built decides whether the 0122 edge holds**:

- The in-flight map is a local of `createBaseCheck` (`base-check.ts:70`).
- `runOnce` runs once per pass (`schedule.ts:254`, `:311`).
- So an instance built inside `runOnce` shares nothing between two passes running at once. Each would cut, install and run on its own.

**Build it once per process and per store.** Keep a module-level `WeakMap<EventStore, ReturnType<typeof createBaseCheck>>` in `conduct.ts`, read with `options.store ?? eventStore` (`conduct.ts:617`).

Because the instance outlives any one pass, its fixed deps cannot belong to a pass:

- **`note`** writes to the conductor's `options.log`, not to a pass's `runLog`.
- **`worktreePath`** is `(project, sha7, runId) => worktreePath(home, project, \`base-${sha7}-${runId}\`)`, using `packages/repo/src/worktree.ts:90`. The `base-` prefix keeps it clear of the pass's own `worktreePath(home, project, runId)` (`conduct.ts:1129`).
- **`cut`** is `git worktree add --force --detach <path> <sha>` and **`remove`** is `git worktree remove --force <path>`. Both run through `repo.git` against the project's clone, as `gitHere` does (`conduct.ts:1645`). Put the cwd in the question, not in the instance, or bind it per ask; either works.
- **`plant`** writes `renderEnvFile(env.values)` at `recipe.env.plantAt`. That is the same file `provisionWorktree` plants (`packages/repo/src/worktree.ts:213-215`, handed `env.values` at `conduct.ts:2434-2435`). `env` differs per pass, so plant is a per-ask concern as well.

`BaseCheckDeps` fixes `plant` and `cut` at construction, with no per-ask argument. The smallest honest change is to move `plant` (and, if needed, the cwd for `cut`) onto `BaseCheckQuestion`. Adjust `base-check.test.ts` to match. That is a change to #743's file, and it is in scope here because this ticket is its first caller.

## 2. The port's shape: `runPass` knows one half of the sha and `conduct.ts` the other

| Who knows | What |
|---|---|
| `runPass` | `mergedOnto`, a local in `runPass` (`pass.ts:1217`, set at `pass.ts:1372`) |
| `conduct.ts` | the cut, `continuation?.diffBaseSha ?? tree.baseSha` (`conduct.ts:2005`; the ticket's `:1980` has moved). The `baseShaOr` comment at `conduct.ts:1651-1659` explains why `tree.baseSha` alone is wrong on a continuation. |

So the port takes both:

```ts
readonly baseIsRed?: (asked: { readonly action: string; readonly mergedOnto: string | null }) =>
  Promise<{ readonly red: { command: string; base: string; baseSha: string; evidence: string } } | { readonly notRed: string }>
```

`conduct.ts` resolves the rest when it is asked:

- **The action.** Look `asked.action` up by name in `recipe.steps.build` for an entry with `'run' in action`. If none is found, note it on `runLog` and answer `notRed`.
- **`command`** is `action.run`.
- **`timeoutMs`** is `parseDuration(action.timeout)`, from `runPlugin`'s `timeout` default of `'15m'` (`packages/recipe/src/recipe.ts:125`).
- **`env`** is `envForExtension(action.env)` (`conduct.ts:859-860`), not `env.values`. Its doc says: *"Not `env.values`: that is the agent's"*.
- **`prepared`** is the `run:` texts of `recipe.steps.prepared`, in order.
- **`baseSha`** is `asked.mergedOnto ?? cutBase`.
- **`base`** is `spec.base`.

`unknown` becomes `notRed`, and the port notes `base not checked: <why>` on `runLog`. `green` becomes `notRed` and notes nothing.

**The signal.** A pass has no abort signal: `passContext` (`conduct.ts:3955`) sets none, and `ActionContext.signal` is optional (`packages/actions/src/action.ts:567`). Give the check a scoped `AbortController` that is aborted when the scope closes, as the judge does (`conduct.ts:2569-2572`). A drain then waits for the check the way it waits for `build`, which matches the ticket's drain edge.

## 3. Where it sits in `routeProposal`, and what the log says

Ask between `offerFor` (`pass.ts:1287`) and `replyFor` (`pass.ts:1297`), only when all of these hold:

- `proposal._tag === 'BuildRed'`;
- `reported?.ending.ending === 'refused'` and `reported.ending.at !== null` (`StepRefused.at`, `pass.ts:336`);
- `offer.available.some((c) => c.id === 'fix-lines')`. For `BuildRed`, `fix-lines` is the round (`packages/domain/src/routing.ts:172-173`); with rounds spent or `rounds: 0` it is in `unavailable`;
- `options.baseIsRed !== undefined`.

**On `red`, the route is still recorded and the judge is still not asked.** Every route appends a `proposed` visit and a `RouteTaken` (`pass.ts:1329-1344`), and `PassRouted` is how the log answers *why did this stop*. Do not return before those. Instead:

1. `reply = { _tag: 'NotAsked' }`. This is true, because no judge was asked. `decideRoute` turns it into `Escalated{NotAsked}` (`routing.ts:272`).
2. Use `routedVisit(offer, reply, decision)` but **replace its `why`** with the BaseRed sentence. Otherwise `notAskedWhy` (`proposed-route.ts:183-199`) would claim *no `judge:` is declared*, which is false and is the confusion that function's own comment was written to stop.
3. Push the `RouteTaken` with that `why`.
4. End with `stopped = reported` and `end = WaitOnPerson{ProposedEscalated{run, proposal: offer.proposal, because: {_tag: 'BaseRed', command, base, baseSha, evidence}}}`. Return `false`. Do not go through `routeNext`'s switch, since its `WaitOnPerson` would carry `NotAsked`.

`BaseRed` therefore goes into `EscalationBecause` beside `JudgeHandedOver` (`packages/domain/src/wait.ts:109`), as the ticket says, and **not** into `RouteEscalation`. `decideRoute` never produces it, and `route.ts`'s header keeps that union to the router's own four.

**One sentence, written once.** `reasonTextOf` (`packages/domain/src/wait-words.ts:172`) is not exported. Export a small `baseRedText(because)` from `wait-words.ts`, and have `reasonTextOf`'s new case and the routed visit's `why` both call it. The card and `PassRouted.why` then cannot drift apart.

In `escalatedColumns` (`wait-words.ts:214-226`), the `BuildRed` branch's evidence becomes:

```ts
because._tag === 'BaseRed' ? because.evidence : proposal.output
```

`defaultResolution`'s `ProposedEscalated` case (`wait.ts:618-619`) becomes `Requeue` when `proposal._tag === 'BudgetExhausted' || because._tag === 'BaseRed'`.

## 4. Tests: what stands in for the integration half

Everything is unit-level. `runPass` with fake ports is already how `conduct-a-whole-pass.test.ts` and the routing tests work.

- **The two-passes test from Done when.** Use `createBaseCheck` over `createMemoryEventStore()` (`@lingtai/event-store/memory`) with a `vi.fn()` `run` that exits 1, wrapped as a `baseIsRed` port, and handed to two sequential `runPass` calls. Assert `run` was called for the command once in total, and that the second pass's `ProposedEscalated.because._tag === 'BaseRed'`. This exercises the log cache, which is what the Done-when line asks for.
- **The live wiring** (`git worktree add`, the plant, the WeakMap) has no unit witness, and `conduct.ts`'s live path is reached only in the integration half, which runs after the merge. State that in the commit rather than reaching for `pnpm test:integration`.
- **The schema.** `EscalationBecause` is in `WaitStarted`'s payload. Run `packages/domain/unit/events-json.test.ts`. `doc/events.json` has no `JudgeHandedOver` today, so it probably does not expand this union, but the test decides that.
