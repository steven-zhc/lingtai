# #1282: pick up a stranded triage continuation on every pass

## Where it goes

The scan moves into the daemon's `pass` callback. It runs right after `conductorTurn` returns, beside the triage rescan that is already there:

```ts
for (const [project, triage] of recipes) yield* scanTriage(project, triage)   // daemon.ts:745
```

Keep the start-time call at `daemon.ts:798-811`. Rewrite its comment, because "Here only" stops being true.

**Why inside `pass`.** The work loop calls `pass` only when no pause is set and no shutdown has been asked for: it asks `options.paused` and returns before `options.pass(...)` (`packages/daemon/src/work-loop.ts:518-531`). That covers the ticket's "asks only when the pass would take work" edge for pause, drain and the setup pause, with no extra code.

**Scope.**
- Scan only the projects in `recipes`, the ones this turn actually looked at.
- Before scanning a project, ask `deps.locked(project)`. That is the same lock the turn asks, and it covers a project's own pause, the day's ceiling and a runtime limit (0126 §5).
- Skip a locked project and say nothing.
- Wrap each project in the same `recovering(...)` + `console.error` the start call uses, so one failed read never ends the pass.

**Do it after the turn, not before.** `ContinueRequested` is in the work loop's wake list (`work-loop.ts:147`). So a row appended after the turn wakes the next pass, and that pass's single control read (`apps/cli/src/conduct.ts:682`) sees it. Appending before the turn would gain nothing.

**The pass-entry check does not cover the end of the turn.** A pause or shutdown requested while the turn ran is not seen by the work loop until the pass returns, so the daemon asks `claiming` and the control stream's `shutdown` again after the turn, and skips the scan when either is set.

Factor the per-project loop out of `daemon.ts:800-811` into an exported function in `triage.ts`. Call it something like `catchUpRegisteredContinuations(projects, ports)`, with the lock check and the per-project recovery inside it. Both call sites use it, and the unit tests reach it without a daemon.

## The guard

The ticket's Watch out asks to skip a ticket whose attempt is "claimed or running". The code already does that:
- `continueTicket` is the only way out of `approved`. The comment on that lifecycle status says so (`packages/domain/src/ticket.ts:211-218`): *"`continueTicket` (`claim.ts`) is the only way out, onto the same `runId`."*
- The scan already reads the lifecycle and drops anything that is not `approved` (`apps/cli/src/triage.ts:355-356`).

So once a continuation is claimed or running, the scan does not see it. **What the guard must add is "already asked for, not yet claimed".**

- **The problem.** `ContinueRequested` has no consumed counterpart, so `control.continuing` only ever grows (`packages/domain/src/control.ts:90-98`, `apps/cli/src/continuing.ts:9-13`). A row that the pass declines at claim stays live, and the ticket stays `approved` on the log. The comment at `conduct.ts:357-363` covers this case: GitHub closed it, `agent:hold`, a new blocker. If the scan appended whenever it saw an approved, triage-resolved ticket, it would add one control-stream event per pass for as long as GitHub declines. Nothing bounds that. In detached mode, `declinedContinuations`' backoff (`conduct.ts:436-441`, `:463-467`) would also be beaten every time.
- **The rule.** Skip when `control.continuing` already holds a row with the same `project`, `issue` and `runId`. Use the same three-field match `stillOwed` uses (`continuing.ts:31-36`). Only request when there is no such row. That one rule also makes a second call idempotent.
- **Where to read the rows.** Read the control stream through the ports, fresh, at the top of each project's scan: `readThroughSnapshot(deps.store, controlReducer, CONTROL_STREAM, CONTROL_FOLD_TYPES, deps)`, the same read as `readControlEffect` (`packages/daemon/src/control.ts:120-128`), or `reduceControl` over `deps.store.read(CONTROL_STREAM)` (`packages/domain/src/control.ts:302`). Do not thread `conductorTurn`'s `control` through: that copy was read at the start of the turn, and an append made during the turn is not in it.
- **Apply it to the start-time call too.** It changes nothing there except that a restart no longer appends a duplicate row.

## Races

- **The triage runner's own append lands between the scan's control read and its append** (`triage.ts:1517-1530`; the ticket's `:1482-1494` has moved). The result is at most one duplicate row. It is harmless:
  - The first claim moves the ticket off `approved`.
  - `stillOwed` then drops the second row (`continuing.ts:9-13`).
  - The doc comment at `triage.ts:347` already says *"A request twice is safe, because the pass re-reads the ticket and refuses a request that is stale."*

  Do not add a version-checked append to close this window. `requestContinuation`'s blind retry is shared with `approve` (`packages/conductor/src/resolve-wait.ts:627-668`), and it is out of scope.
- **A detached continuation launched in this turn and not yet claimed.** Its row exists, so the guard skips it.
- **Two passes at once (0122).** Both scans run inside the one conductor-lock holder's loop, and the claim decides between continuations. Nothing new is needed.
- **The request failing again.** Leave `requestContinuation`'s `null`-or-message contract as it is. Log the message as today and let the next pass try again. A failed control read is a failure that the per-project recovery logs. It is never an empty `continuing` list, because an empty list would mean "request it".

## Comments to rewrite

Both of these say "start scan only", and the reason they give is the one this change answers:
- `triage.ts:343-348`
- `daemon.ts:798-799`

Say instead that the scan runs on start and on every pass, and that the `control.continuing` row is the guard. That guard is what makes it safe beside a continuation that has been asked for but not yet claimed.

## Tests

There is no unit test of `catchUpTriageContinuations` today; the only references are `daemon.ts` and `triage.ts`. Add the tests to `apps/cli/unit/triage-catch-up.test.ts`. Use `createMemoryEventStore()` and the fixture ports already there, with `readTasks` returning an `approved` card. Each test should cover one of these:

1. `WaitResolved{by:'triage', RedoStep}` with no `ContinueRequested` appends exactly one row. A second call appends nothing. This is the "picked up by the next pass" claim at the level the pass calls.
2. A `ContinueRequested` row exists for that `runId` and the ticket is still `approved` (claim declined): nothing is appended.
3. A ticket that is past `TicketContinued` (no longer `approved`): nothing is appended.
4. `locked` returns a sentence: nothing is appended. A lock read that fails is logged, and the next project is still scanned.

The daemon's `pass` wiring itself is only reachable through the daemon. The four tests above on the extracted function are what stand in for it; nothing in `pnpm test` drives `daemon.ts`'s callback.

Write the new function as `Effect.gen`, with no `async` and no `Effect.run*`, so `effect-ratchet.baseline.json` does not move.
