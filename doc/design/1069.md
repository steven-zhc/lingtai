# #1069 — design note

The ticket names the pieces. Five things it leaves open would build different code if guessed differently, so they are decided here.

## 1. The recorder is built synchronously, and the events port is resolved inside each attempt

`createWorkLoop` is a plain function. It builds `store` at `work-loop.ts:394` and `failuresAt` at `:408` with no Effect around them. If `makeFailureRecorder` were an Effect, it would need an `Effect.run*` to construct, and the ratchet would count that run. So:

- `makeFailureRecorder({ store?, tell })` is a plain function.
- It builds its permit with `Semaphore.makeUnsafe(1)`. There is a precedent at `packages/projector/src/sqlite.ts:444` (`const permit = Semaphore.makeUnsafe(1)`).
- `failuresAt` is a plain `let` in its closure. The permit already serialises every access to it, so a `Ref` buys nothing.

`yield* processEvents` belongs **inside each attempt**, not at construction, for two reasons:

- **It opens the process store.** `processEvents` is `Effect.map(process_.get(), (o) => o.events)` (`packages/event-store/src/choose.ts:216`). Today `eventStore` opens nothing until it is used (`choose.ts:185-200`, `index.ts:94`). Resolving it at construction would open the store whenever a work loop is created.
- **A failed open has to count as an attempt.** The doc comment says *"A rejected open — the 0056 refusal, or `ProcessLogClosedError` — is a defect"* (`choose.ts:211-215`). Today that open fails inside `store.read` (`:437`), which sits inside the `try`. So it counts as an attempt and is retried. Resolved per attempt, it stays inside the `catchCause` and keeps that behaviour.

When `options.store` is set, `fromPromiseStore(options.store)` can be built once. That is cheap, and the unit tests take this path.

## 2. Two layers of catching, not one

Per attempt, use `Effect.catchCause`:

- If `Cause.hasInterruptsOnly(cause)`, re-raise it with `Effect.failCause(cause)`.
- Otherwise set `failuresAt = null`. On the third attempt, `tell` with the message from `Cause.squash(cause)`. Keep today's text: `could not record ${name}'s failure: ${message}` (`:448`).

`fromPromiseStore` turns any rejection that is not a `ConcurrencyError` into a defect: `throw err` inside `Effect.promise` (`store-face.ts:80-82`). That is why `Effect.catch` would miss it.

Then add **one more `catchCause(() => Effect.void)` around the whole of `record`**, outside `uninterruptible` and `withPermits`. This is the Effect version of today's `.catch(() => {})` (`:455`). Its comment says *"Nothing above can reject, and the chain is caught anyway"*. Here it guards one thing: `tell` is the caller's callback. If it throws inside an `Effect.sync`, that is a defect, and without the outer catch it would reject `recordFailureFace`. `void recordFailureFace(…)` would then be exactly the unhandled rejection #120 removed.

With that outer catch, the type `Effect<void, never>` is also what actually happens at runtime.

## 3. `settled()` stays lazy, and `Effect.promise` is safe here

Write it as `Effect.gen(function* () { while (set.size > 0) yield* Effect.promise(() => Promise.all(set)) })`. It reads `set` when it runs, not when `settled()` is called.

- **Why reading at run time matters:** passes tracked while the drain waits belong to the drain. The comment says *"`settled()` loops until the set is empty rather than awaiting a snapshot … `track` is never refused"* (`in-flight.ts:4-8`). #640 decided this.
- **Why `Effect.promise` is safe:** it turns a rejection into a defect, but every tracked promise has already had its rejection swallowed (`in-flight.ts:25-28`). Nothing in the set can reject.

`track` and `size` do not change. `InFlight` in `in-flight.ts:10-17` changes only its `settled` signature and doc line.

## 4. Order is now the order of permit acquisition

Today's chain appends in the order `record` was called (`:433`). With the semaphore, each `recordFailureFace` starts its own root fiber, and appends follow the order the permits are taken. In practice this is call order, because each fiber runs synchronously up to the permit. Correctness never depended on it: what matters is that each append reads the version the previous one left (`:410-417`), and the permit guarantees that.

So the "two records in one tick" test should assert **consecutive versions and two `PluginFailed` events with no `ConcurrencyError` and no `tell`**. It should not assert which `name` lands first.

## 5. Where things live, and what the ratchet sees

- **`failure-recorder.ts`**, not a section of `work-loop.ts`. A unit test needs to import `makeFailureRecorder` without the work loop's imports. `work-loop.ts:90` pulls in `subscribe` and `processLog`.
- **Faces must be exported.** The ratchet refuses a face that is not *"`export function ${fn}`"*. A face's body must be exactly one `return Effect.runPromise(<call>)` with at most `{ signal }` (`packages/domain/unit/effect-ratchet.test.ts:198-235`). So both faces are exported:
  - `recordFailureFace`, from `failure-recorder.ts`;
  - `inFlightSettledFace`, from `in-flight.ts`.
- **The count:** 56 → 54. One is the `.then(async () =>` at `:434`, the other is `async settled()` at `in-flight.ts:34`. Faces are not counted (`effect-ratchet.test.ts:10-12`).
- **`record`'s existing comments move with the code**, onto the recorder: the `PluginFailed` guard (`:420-425`), the project rule (`:427-431`), and *ask it again* (`:443-445`).

## Tests that stand in for the integration file

`integration/work-loop.test.ts` runs on SQLite and is in reach. The unit claims below cover what it cannot isolate.

- **A store whose `append` throws a plain `Error`** (a defect through `fromPromiseStore`):
  - `await recordFailureFace(…)` resolves;
  - `append` is called three times;
  - `tell` is called once;
  - `read` is called before each attempt, because `failuresAt` is reset after each refusal.
- **A `tell` that throws:** `recordFailureFace` still resolves. This holds the outer catch from §2.
- **An event of type `PluginFailed`:** no read and no append.
- **`in-flight.test.ts`:** call `settled()` through `Effect.runPromise`, and keep the test that a pass tracked during the wait is waited for.
