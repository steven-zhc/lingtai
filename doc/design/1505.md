# #1505: design note

## Board: `recipe.test.tsx`

This is a one-line path fix. `apps/board/integration/recipe.test.tsx:373` scans `new URL('../src/app/recipe/', …)`, but that folder no longer exists. The route lives at `src/app/p/[project]/recipe/` now. Line 101's `PAGE` and line 386's `edit/` check already use that path. Point line 373 at the same segment. Do not loosen the guard `it('is reading the route…')` at :378. It asserts `segment` contains `page`, so a wrong path fails loudly and can't pass by finding nothing. No product change.

## CLI: `init.test.ts`

### Why a rerun is now refused

On a rerun, init now asks the store question again, with the store already set as the default. `apps/cli/src/init.ts:1041`:

> "A store that answers is asked about again with itself as the default (0125 §6): an answer equal to it writes nothing, and another is written and said."

ADR 0125 §6 (`doc/decisions/0125-setup-is-one-module-two-inputs.md:68`) says a later run "asks every question the first run asks… Only the defaults differ."

The fixture's `ask` returns `null` once `answers` is empty (`init.test.ts:192`). `questionEffect` turns `null` into `the store needs an answer: pass --store sqlite, or --store postgres --database-url <url>` (`question.ts:184`, flag text from `init.ts:1110`). That refusal is the exit 1 the ticket reports.

### Rule for every failing test whose machine already has a store and passes no `--store`/`--database-url`

- **Put `''` at the front of that world's `answers`.** That is Enter, which keeps the current store. For Postgres, `current` is the URL (`init.ts:1049`). For SQLite, `current` is `''` (`init.ts:1044`). Either way `validate` returns early on `''` (`init.ts:1122`), so `seen.connected` gains nothing.
- **Change `asked: []` to `asked: ['ask:database']`** in these tests. 0125 §6 says this question is asked now, and a test asserting it isn't is asserting the old behaviour.
- **Do not reach for `--defaults` instead.** It would make `asked` empty again through `acceptingDefaults` (`init.ts:1106`). But it skips the claim 0125 §6 actually makes: an answer equal to the current one writes nothing.
- In `it('re-running a finished init reports the state and changes nothing')` (:711), keep the `config(home)` equality and the `mtimeMs` equality. Those two now carry that claim.

**Tests a flag answers are not in scope of this rule.** That covers `--store sqlite` over SQLite (:942) and `--database-url newer` (:1026). The flag answers through `given` (`init.ts:1111`). If one of those fails, it is a different failure. Read it before you change it.

### A failure in a project question

A project question may reach the fixture's `ask` and trip `expect(question).toMatch(/Postgres/)` (:189). On a rerun of a registered project, #1497 asks the recipe's questions with the recipe's values as defaults. If that happens, handle it like the existing branches at :175–186: add a regex branch that returns `''`, meaning take the default. For example, `it('a local project, once registered, is listed on a re-run…')` (:347) asserts `asked: []` with no store answer, so it will meet the store question first.

**Do not count a recipe question as `ask:database`.** The Ctrl+C matrix at :526 is written against the database step alone (comment at :168).

### The one product change: the runtime refusal must come before the store question

`it('refuses a file that still names a runtime…')` (:668) shows a real ordering bug. Fix it in `init.ts`; don't rewrite the test around it.

The store is chosen at `init.ts:398`. `machineRuntimeRefusal` runs after it, at `init.ts:425`. Before #1474 that order didn't matter, because a store that answered was never asked. Now it matters:

- With no terminal, the migration message is unreachable. You get the store refusal, then the runtime one only after passing `--store`.
- At a terminal, a person can type another store. It gets written ("another is written and said"), and then they are refused with a message that ends `nothing was written` (`init.ts:1300`). That ending is now false.

`machineRuntimeRefusal` is "a pure function of the file" (`init.ts:1290`, and the docblock at `init.ts:44–48` calls it "a migration message… not a question"). `config` is already parsed at `init.ts:395`. So move the two lines at :425–426 to just after :395, before `chooseStore`. Leave the `// ---- the agent` comment block with them.

This puts it in the same place as the other refusals of the file itself. Both of these assert nothing is asked:
- `refuses a config.yml that does not parse` (:738)
- `refuses without git, before asking anything` (:680)

After the move, :668 passes unchanged. Leave its assertions as they are; they become correct again.

## Verification

- **Unit-level claim for the reorder.** `apps/cli/unit/init.test.ts` already drives `initCommandEffect` against an in-memory world (:38–40) and holds `machineRuntimeRefusal`'s own cases (:44). Add one case there: a file with `database.store: postgres`, a `url`, and `runtime.agent`, plus a world whose `ask` returns `null`. It must:
  - exit 1;
  - have the last line contain `runtime.agent in that project`;
  - never call `ask`.

  That is the reorder's claim inside `pnpm test`.
- **The 9 rerun tests are integration only.** Their fixture uses `liveMachine()` and real files (:170–172), so nothing in `pnpm test` covers them. Running the one file is in reach (`cd apps/cli && pnpm vitest run --project integration integration/init.test.ts`). So is the board file. Run both. Don't run `pnpm test:integration`.
- Also run `pnpm test` and `pnpm typecheck`.

## Edges

- **Read that fails / null value:**
  - An unparseable file is still refused at :395, before the moved check.
  - A missing file has no `runtime` key, so `machineRuntimeRefusal` returns null and nothing changes.
- **Restart / retry / two runs / shutdown / stale page:** none apply. This is a test fixture and an ordering inside one synchronous command.
- **Redone or skipped actions:** the reorder means the store step no longer runs at all on a file that names a runtime. That is the intent: nothing is written, which is what the message says.
- **Cost to every later change:** `asked: ['ask:database']` on reruns pins the 0125 §6 question order. A future change to rerun ordering will turn these tests red. That is correct, because they are the order's witnesses.

## ADRs

The reorder agrees with 0125 §6 and with the docblock's "migration message, not a question". It does not contradict any accepted ADR, so no superseding file is needed.
