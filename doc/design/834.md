# Design: #834 — `task_view` reads the ticket reduce

Everything the ticket needs from earlier work is already in this tree:

- `reduceStoredTicket` (`packages/projector/src/ticket-row.ts:17-24`), with no replay skip since #860.
- `TicketState.waits`, carrying each wait's `triage.started`, `result` and `headSha` (`packages/domain/src/ticket.ts:45-64`, `:365`).
- `lateHistories.ticket.triagedTwice` (`packages/domain/test/histories.ts:967`, `:1124`).

This note covers only the decisions the ticket leaves to whoever builds it.

## 1. Route by stream before the `switch`, and `continue`

In `apply` (`task-view.ts:217`), put the branch ahead of the `switch`:

```ts
if (isTicketStream(event.streamId)) { await applyTicketEvent(ctx, event); continue }
```

A ticket-stream event then never reaches `cardFactOf`'s `default` branch (`:513`). That is how the `WaitStarted`/`WaitResolved`/`TriageStarted`/`WaitTriaged` cases stop existing, rather than being deleted one at a time.

This is safe for what stays in the `default` branch:

- `StepEnded` is appended on `runId` (`conduct.ts:4688`), and so is `PassRouted`, the source of the `RoundOpened` fact (`conduct.ts:4295`, `read-model.ts:178-186`).
- `RunEnded` is read through `viaRun`.

None of them is on a ticket stream.

`isTicketStream` checks the `ticket-` prefix (`packages/domain/src/streams.ts:46-48`). An old `wi-` stream is not reduced. `ticket_report` (`ticket-report.ts:479`) and `spend` (`spend.ts:274`) both draw the same line, and that is the precedent. `splitTaskId`'s `wi-` fallback (`:736-740`) has no caller left on this path, so `project`/`issue` come from `TicketState.project`/`externalRef`.

## 2. Detect a change in TypeScript, not against the row

Write one pure function:

```ts
function columnsOf(t: TicketState): TicketColumns
```

It returns every column in **Want** except `state`, encoded the way the table stores them today:

- `wait_reason` as `JSON.stringify(reason)` (`:588`), because `waitOf` parses that (`:1010-1020`).
- `triage_result` as JSON text cast `::jsonb` (`:617`).
- `answer` as `{ question, answer, by }` from `answers.at(-1)`, with `runId` dropped. `readTasks` keeps its shape.

Two comparisons decide what an event writes:

- **Lifecycle moved:** `before.lifecycle` and `after.lifecycle` differ by deep equality. Only this writes `state = taskStateOf(after.lifecycle)`.
- **Card moved:** the lifecycle moved, or `columnsOf(before)` and `columnsOf(after)` differ by deep equality, or the event is one of the ticket's note events. Only this moves `updated_at`/`updated_seq` and `note`.

Neither comparison reads `task_view`. All it needs is the stored `ticket`, which is the one read the event already makes, so the pass costs no extra `select`.

**`awaiting_sha`** is cleared when `columnsOf(...).wait_id` changes, or on a claim. Today the claim clears it at `:808-810`, and a claim from `backlog` after an `IntegrationRefused` would otherwise keep a stale sha.

**The `verifying` overlay** follows from the lifecycle comparison:

- A `PromptEdited` or `IssueUpdated` during `verifying` moves no lifecycle and no column, so the event writes `ticket` alone.
- A `TicketReleased` or `WaitStarted` during `verifying` moves the lifecycle, so `state` is overwritten, as it should be.

## 3. The read and the write

1. Read `select ticket from task_view where task_id = $1`. If no row comes back, read `task_view_ticket`. `undefined` means neither table has the ticket.
2. Call `reduceStoredTicket(stored, event, TASK_VIEW_TABLE)`. A value that does not decode throws through `decodeTicket`, which names the projection and the stream. Wrap the error only to add `lingtai projection rebuild task_view` if `decodeTicket`'s message does not already say it.
3. Branch on the row and the event type:
   - **No row, and the event is one of the four row-makers** (a claim, `TicketDiscovered`, `DispatchRefused`, `WaitStarted`): insert the full row, with `state = taskStateOf(after.lifecycle)`, `columnsOf(after)` and the event's note. Then `delete from task_view_ticket where task_id = $1`.
   - **No row, any other event:** upsert `task_view_ticket`, following `spend.ts:278-283` (`$2::jsonb`, `on conflict … do update`).
   - **A row:** `update task_view` with `ticket`, plus whatever §2 says moved.

Decide row creation by **event type**, not by lifecycle. A `DispatchRefused` on an untouched issue leaves the lifecycle at `backlog`, and still makes a `queued` row with its sentence, as `:374` does today.

**What only a claim writes.** These are not derived from state:

- `linkRun(ctx, runId, streamId)`, as at `:254`. `RunStarted` and `viaRun` depend on it.
- `run_id = after.lifecycle.runId` while `claimed`.
- `note = null`.

Leave `verdicts` alone; it is keyed by run (`:98-105`).

**`repair_run_id`/`repair_pending`** keep their claim-time rule (`:818-821`) unchanged. They are out of scope and are only ever `false`/`null`.

**Plain SQL only.** Ticket-path writes set `updated_seq = $seq` with no `where updated_seq <=` guard, because one runner writes this table (#860). The `set` and `viaRun` helpers keep their guard for the run-stream cases (`:841`), as the ticket says.

## 4. Schema

Add `ticket jsonb` to `task_view`'s `create table` (`:78`), and create `task_view_ticket (task_id text primary key, ticket jsonb not null)` next to `task_view_run` (`:204`). `reset` drops both.

Make `ticket` `not null` in the DDL, with no default: every insert writes it, and a table built before this is refused by the shape check until rebuilt. A stored `null` would still go to `decodeTicket` and throw, never be treated as "none". `ticket-row.ts:14-15` makes that distinction: *"`null` is a stored value, `undefined` is none"*.

`shape.ts` declares columns from the `create table` itself (`shape.ts:28`), so the new column feeds the drift check with no further edit.

## 5. Tests

**Named tests.** Put them in a new `packages/projector/unit/task-view-ticket-fold.test.ts`.

**Merging a scenario.** A scenario holds several streams. Merge them with one helper, `[...a, ...b].sort((x, y) => (x.seq < y.seq ? -1 : 1))`, and feed the result to `taskViewProjection.apply`, batch by batch, inside the store's transaction. Check how `task-view-rebuild.test.ts` drives the store and reuse that.

**Batches of 1, 3 and all.** Loop over the same history list. Compare `select *` rows with `updated_at` included. That only holds if the "card moved" rule from §2 is applied identically in every batching, which a TypeScript comparison guarantees and a row comparison would not.

**The pin.** The ticket requires a comment above the regenerated snapshot that ties every changed row to a named rule. Generate that comment from the snapshot diff, by running `git diff` on the snapshot file, before writing it. Do not write it from memory of which cells should move.

**Verify with** `pnpm test`, `pnpm typecheck`, `pnpm lint` and `pnpm fmt:check`. `packages/projector/integration/task-view.test.ts` is Postgres-only and cannot be run inside the pass. Its D5/D6 assertions are edited by reading them, and the unit tests in this file are what stand in for it.
