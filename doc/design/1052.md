# Design: #1052, recipe IO as Effects

The ticket gives the shape. This note covers the decisions it leaves open, each of which would produce different code depending on how it is read.

## 1. Plain calls that throw: fail for the four classes, die for anything else

`Effect.try({ try, catch })` cannot do this, because its `catch` always *fails*. To get *"a thrown `RecipeInvalidError`, `RecipeMissingError`, `MachineConfigInvalidError` or `AgentUnresolvedError` is the failure. Anything else is a defect"*, write one helper in `files.ts` and use it at every plain call: `resolveSource`, `checkMachineConfig`, `namedIn`, `editedText`, `widenStepsIfNeeded`, the probe.

```ts
const plain = <A>(f: () => A): Effect<A, Refusal> =>
  Effect.suspend(() => { try { return Effect.succeed(f()) } catch (e) { return isRefusal(e) ? Effect.fail(e) : Effect.die(e) } })
```

- `Refusal` is the union of the four classes, and `isRefusal` is an `instanceof` over them.
- `files.ts` would import those classes from `resolve.ts` and `local.ts`. Both already import `files.ts` for `readRecipeFile`, so that creates a value cycle. If it bites, put `plain` and `isRefusal` in `local.ts`, which `write.ts` already imports (`write.ts:19`).

## 2. The probe in `resolveLocalRecipeEffect` catches by class, not by tag

The four classes are not tagged, so `catchTag` does not apply. Use `Effect.catchIf` (it exists in `effect@4.1.2`, `Effect.ts:6027`):

```ts
resolveAgent(written, signedIn, path).pipe(
  Effect.catchIf((e) => e instanceof AgentUnresolvedError,
    (err) => plain(() => resolveSource(source, …probe…)).pipe(Effect.andThen(Effect.fail(err)))))
```

- A `RecipeFailed { operation: 'signed-in' }` passes through without running the probe. That matches `local.ts:329`: `if (!(err instanceof AgentUnresolvedError)) throw err`.
- The probe's own `RecipeInvalidError` wins over the agent error, as it does today.

## 3. One resolver with an optional Effect reader, not a second export

`saveRecipeText` overrides `read` (`write.ts:272`). `LocalRecipeOptions.read` stays a promise port. To give the Effect path an Effect-shaped reader, add a third parameter:

```ts
resolveLocalRecipeEffect(project, options: LocalRecipeOptions, read?: (path: string) => Effect<string | null, RecipeFailed>)
```

- The reader is chosen in this order: `read` if given, else `options.read` lifted through `Effect.tryPromise` as `operation: 'read'`, else `readRecipeFile`.
- The face passes two arguments: `return Effect.runPromise(resolveLocalRecipeEffect(project, options))`.
- `saveRecipeTextEffect` passes `(p) => p === path ? Effect.succeed(text) : files.read(p)`, where `files` comes from `filesEffect`.
- There is no internal `resolveLocalWith`. `index.ts` does `export *` from `local.ts` (`index.ts:7`), so any helper `write.ts` needs would become public anyway.

## 4. `saveRecipeTextEffect` turns a defect into `invalid` too

Today's `catch` at `write.ts:275` catches *everything* that `resolveLocalRecipe` throws, including a bug, and returns `{ ok: false, reason: 'invalid', message }`. Keep that: catch the resolve's whole cause, failures and defects both, and take the message from the squashed error (`messageOf`, as `packages/setup/src/failure.ts` does).

There is one exception: let an interruption propagate (check `Cause.hasInterrupts` and re-fail with the cause). An interrupted save is not an invalid recipe.

The `stale`/`missing` checks and the `replace` stay outside that catch, as they are now. A `RecipeFailed` from the first `files.read` (`write.ts:257`) makes the face reject, which matches today, where that `await` is outside the `try`.

## 5. Faces must have exactly the checked shape

`face()` (`effect-ratchet.test.ts:167-268`) accepts only an exported `function` or `const = () =>` whose single statement is `return Effect.runPromise(<call>)`. It refuses a second statement (`:208`) and a first argument that is not a call (`:242`). So:

- **Defaults move into the Effects.** `options?.files ?? diskFiles`, `options.home ?? stateDir()` and `recipePath(…)` are all computed inside the `Effect.fn` body. A face that computes anything is refused.
- **`diskFiles` holds references, not inline arrows.** It is `{ read: readFileFace, replace: replaceFileFace }`. An inline arrow that calls `Effect.runPromise` inside the object literal is a counted run, not a face.
- **`RecipeFiles` stays in `write.ts`.** `files.ts` takes it with `import type { RecipeFiles } from './write.ts'`, which is erased at runtime, so it adds no cycle.
- **`diskFiles` moves to `files.ts`.** Nothing outside the package imports `../src/write.ts`. A re-export from `write.ts` is therefore not needed. If one is added anyway, `export *` of the same binding from two modules is not a conflict.

## 6. `RecipeFailed` follows `SetupFailed`

Use `packages/setup/src/failure.ts` as the template: `Data.TaggedError` with `{ operation, message, cause }`, plus a `messageOf` helper. Because the field is named `message`, `err.message` reads the same as today's raw error, which the callers at `onboard.ts:537`, `wizard.ts:274` and `apps/board/src/lib/recipe.ts:269` print.

## 7. The ratchet edit

- **Where the faces go.** `#1047` has landed (`89fe53da`), so the projector store's faces are already in `effect-ratchet.faces.json` (`:261-…`). The seven new entries go after the last `packages/projector/src/…` entry and before `packages/repo/src/git.ts`. Sorted by file, then by `fn` as a plain string comparison:
  - `files.ts`: `readFileFace`, `replaceFileFace`
  - `local.ts`: `resolveLocalRecipe`
  - `resolve.ts`: `resolveRecipe`
  - `write.ts`: `readRecipeKey`, `saveRecipeText`, `setRecipe`
- **Wording.** *"ten packages"* appears at `:3`, `:307`, `:509`, `:510` and `:522` of `effect-ratchet.test.ts`. `:509` and `:510` are `toMatch` regexes on the `:307` message, so change those three in one edit. `:522` is only a test title.
- **Keep the telegram case.** The checkFaces test at `:510` uses `packages/telegram/src/z.ts` as an outside path, and it must still be refused.
- **Version.** Use `effect@4.1.2`; both `4.1.2` and `4.0.0-rc.111` are present under `node_modules/.pnpm`.

## Tests, unit only

`packages/recipe/unit` must not touch the disk:

- Inject `files` as a `Map`, `options.read`, `signedIn` and a `ReadAtRef`.
- Test `isMissing` on hand-built errors with `code` set to `ENOENT` and `EACCES`.
- For `RecipeFailed`, assert `_tag`, `operation` and `message` on the rejection, using `await expect(face(…)).rejects`.
- `readRecipeFile` and `replaceRecipeFile` against a real path would be integration tests. Leave them uncovered at unit level, as the ticket's *Done when* does.

The existing `save-recipe-text.test.ts:50,100` (`reason: 'invalid'`) is the regression check for §4.
