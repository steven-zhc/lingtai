# #402: check the installation before anything is asked or written

## The code has moved since the ticket was written

The ticket's line numbers (`lingtai.ts:464–499`) are from before #396. The questions no longer sit in `addCommand`. They are in **`askBeforeGithubAdd`** (`apps/cli/src/lingtai.ts:427`), which `addCommand` calls at `:585`. It asks, in this order:

- `askAgents`, written with `setRecipe` at `:493-494`.
- `askTickets` and `askKinds`, from #396, written at `:519` and `:530`.
- `askLanding` and `askLimits`, which write for themselves.

`add()` is not called from `addCommand` any more. `chooseFirstProject` → `runGithubBranch` (`apps/cli/src/first-project.ts:457`) calls it through `world.github.add` at `:573`. So "the rest of `add()`" is reached through `chooseFirstProject`, and that path stays as it is. The only new work is a check placed at the top of `askBeforeGithubAdd`.

## The shape

**1. `checkInstallation` in `packages/conductor/src/onboard.ts`.** Lift today's steps 1 and 2 (`onboard.ts:251-272`) into an exported function. Use these names:

```ts
export async function checkInstallation(
  slug: string,
  log: (line: string) => void,
  known?: Installation,
  lookup: (owner: string, repo: string) => Promise<Installation> =
    (owner, repo) => installationForRepo(githubApp(), owner, repo),
): Promise<Installation | null>
```

- It returns null after logging the same lines `add()` logs today: `NotInstalledError`'s message, or the gap list ending *"Fix them in the App's settings, then re-run."*
- Any other error is rethrown, exactly as `add()` rethrows at `:259-261`. A 502 is not "not installed". `onboard.test.ts`'s *does not read any other failure as not installed* pins that for Recheck.
- `known` skips the lookup but **not** the permission check. That matches today, where `options.installation` (`onboard.ts:27-30`) skips only `installationForRepo`.

`add()` begins:

```ts
const installation = await checkInstallation(options.slug, log, options.installation)
if (installation === null) return 1
```

Everything after that stays as it is. `AddOptions`, `add`'s signature and `recheck` (`onboard.ts:80-120`) do not change. **The board's Recheck depends on nothing new**, and `onboard.test.ts`'s `Recheck` block is the evidence.

**2. Call the check first in `askBeforeGithubAdd`.** Place it after the `--land`/`--base` contradiction at `:439-445`, which writes nothing and needs no network, and before `diskFiles.read(path)` at `:458`. Everything below it stays in the order it has now. `askAgents` still runs before `add()`, for #398's reason quoted at `:447-449`: *"before `add()` resolves the recipe — because `resolveLocalRecipe` throws `AgentUnresolvedError` …"*.

- **The check says nothing on success.** Collect its lines into an array and print them with `console.error` only on refusal, then return 1. `add()` runs the same check again later and prints its own `installation …` / `permissions: …` lines through `runGithubBranch`'s `said` (`first-project.ts:571-583`). If the early check printed too, every successful add would show those two lines twice.
- **Pass the installation the check found to `defaultBranchOf`** (`lingtai.ts:406`) through a new optional parameter, so the land question does not make a third `installationForRepo` request. Do not try to pass it on to `add()` through `chooseFirstProject`. `flags` is a `Record<string, string>`, and `runGithubBranch` already supplies an installation from `choose()`. One repeat GET is cheaper than a new path through `FirstProjectWorld`.

## The decision the ticket doesn't make: no App configured

With no App on the machine, `githubApp()` throws (`packages/env/src/index.ts:1155-1163`), so there is nothing to check. Today that machine still gets every question and write. Then `runGithubBranch` reaches `!app.configured` (`first-project.ts:501`) and offers to create the App, and a `skip` returns `ok` with nothing registered (`:520-523`). That is the same half-onboarded state this ticket exists to remove.

**Decision:** when `hasGitHubApp()` (`packages/env/src/index.ts:1193`) is false, `askBeforeGithubAdd` asks nothing and writes nothing. It prints one line saying the setup questions are asked when `lingtai add <slug>` is run again once the App exists, and returns null so `chooseFirstProject` can create the App as it does now.

- After the App is created in that same run, `add()` registers the recipe as it stands. If that recipe cannot resolve without the writer question, `add()` refuses by name with `AgentUnresolvedError`, and a second run asks it.
- This is a narrower `lingtai add` on a fresh machine. Do not refuse outright instead: that would break the App-creation flow `add` has had since #394.

## The test

`lingtai.ts` calls `main()` when it is imported (its last lines), so a unit test cannot import `askBeforeGithubAdd` from where it is. **Move it to its own module, `apps/cli/src/add-github.ts`**, and have it take a deps argument:

- `check`: defaults to `checkInstallation` with the live lookup.
- `read`: defaults to `diskFiles.read`.
- `write`: defaults to `setRecipe`.
- `ask`: defaults to `liveAsk`.

`lingtai.ts` imports it and calls it with the defaults.

**Unit tests** go in `apps/cli/unit/`, one per refusal:

- A fake lookup throwing `NotInstalledError` returns 1.
- A fake installation with `issues: read` returns 1.
- In both cases `read`, `write` and `ask` are called zero times. Nothing was read, so nothing can have been written: that is the unit-level stand-in for "`recipe.yml` byte-for-byte unchanged".
- A third test: a good installation reaches `read`, which shows the ordering is not just "always return".

A byte comparison against a real file is the filesystem, so it belongs to the integration half under 0060 §1. Don't write it as the `Done when` evidence.

Add `checkInstallation`'s own cases to `packages/conductor/unit/onboard.test.ts`:

- known installation with a gap → null, with the gap lines logged.
- lookup rethrowing a non-`NotInstalledError` → throws.

## What would settle it in the log

A refused `lingtai add` appends nothing, so it shows as **no `ProjectConfigured` on `projectStream(<repo>)`** after the attempt (`onboard.ts`'s `eventStore.append`). The recipe file is not in the log at all. That is why the claim about the file is carried by the zero-calls unit test and not by a seq.
