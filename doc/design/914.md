# Design note — #914, the queued panel's start estimate

## Where it goes

There are three places to change and one new module. The log's half computes what it can without GitHub. The panel puts that together with GitHub's `position` while it renders.

**1. `apps/board/src/lib/queued-estimate.ts` (new, pure).**
- `typicalAttemptMs(rows: readonly TicketReportRow[], now: Date): { ms: number; count: number } | null`. Return the count as well as the median, because the `title` needs it (*12 landed tickets*).
- `estimateStart({ typicalMs, running: { remainingMs }[] | sinces, slots, position, now })` runs the ticket's simulation and returns S, plus whether the slot that frees first was a running attempt already past T.
- `estimateLine(view: QueuedView, inFlight: InFlight | null, typical: Typical | null, ceilingReached: boolean | null, now: number)` returns one of three things:
  - `{ kind: 'line', text, inputs }`
  - `{ kind: 'failure', text }`
  - `null`

  Every *never drawn* condition is checked here and nowhere else, so the ticket's "each never-drawn condition gives no line" test is a table test over this one function, with no render needed.
- `median` comes from `@lingtai/conductor/report`. That subpath is already exported (`packages/conductor/package.json:23`). Change `const median` at `packages/conductor/src/report.ts:216` to `export const median` and change nothing else in it. **Do not import `@/lib/report`** into this module: it imports `readTicketReport` from `@lingtai/projector` (`apps/board/src/lib/report.ts:146`), so the "pure" module would reach the store.

**2. `inFlightOf` carries `since` (`apps/board/src/lib/queued.ts:409-437`).**
- `InFlight.running` becomes `{ project; issue; since: Date | null }[]`.
- `heldBy` returns ids only (`queued.ts:430-433` splits `project#issue` back apart). So widen the `rows` parameter to also carry `lastAttemptAt: Date | null`, which the `readTasks` row already has (`packages/projector/src/task-view.ts:766`), and look each id up in `rows` to read its `lastAttemptAt`. `held` is still the one definition of in flight (the docstring at `:420` says so). Do not add a second filter on `state`.
- A row that `held` returns but the lookup cannot find gets `since: null`. A null `since` means no line, never 0.

**3. `loadTask` (`apps/board/src/lib/task.ts:1777-1780`, the `Promise.all` with `readTasks({})`).**
- Add one more entry, only when the ticket is queued: `readTicketReport({ project: ticket.project })`.
- The state is not known until `readOwn` resolves, so this cannot simply sit in the same `Promise.all`. Start it beside `inFlightFor` at `:1913`, after the state is known, and gate it on `standing.state === 'queued'` the way `inFlightFor` gates itself (`:1745`). That way no other page pays for the read.
- Fold the rows to `typicalAttemptMs(rows, now)` there. Put a new field on `TaskDetail` (`:967`, beside `inFlight`):
  `startEstimate: { typical: { ms; count } | null; ceilingReached: boolean | null } | { failure: string } | null`
  - `null` means not queued.
  - `{ failure }` means `readTicketReport` threw. Catch it here and return the message. Do not use `emptyIfUnbuilt`: an unbuilt table already comes back as `[]` (`packages/projector/src/read-ticket-report.ts:10-12`), and that is the "no line" case, not a failure.

**4. `QueuedBand` (`apps/board/src/app/standing.tsx:84-175`).**
- Add a `startEstimate` prop, threaded the same way `inFlight` is (`:200`, `:207`).
- Draw the line only on the resolved branch, directly after the `triage-summary` `<p>` (`:114-118`), as a muted `<p>`.
- The fallback (`resolved={false}`, `:200`) draws nothing: `position` is GitHub's, so there is no line until GitHub answers. A skeleton there would make a promise the line may not keep.
- Format the `title` here using `durationText` (`apps/board/src/lib/report.ts:214`, which `/report` uses for the same median at `panels.tsx:78`). `standing.tsx` has no `"use client"` (its first line is an import), so importing it is safe.

## The ceiling: the boolean already exists

The ticket says to add a boolean to `daySpend` if one is needed. It is already there: `ceilingReached(day, ceilingUsd)` at `packages/conductor/src/day-ceiling.ts:135`, which the conductor's own `dayCeilingPause` uses (`:196`). Call it. Do not add a new one.

Compute it in `loadTask` the way `readDayReading` does (`apps/board/src/lib/day-spend.ts:42-44`): `daySpend(await readSpend({ since: startOfLocalDay(now) }), now, readRateSnapshot())`, then `ceilingReached`. Only do this when `machineDayCeiling()` is set. With no ceiling the answer is `false`, not null: nothing can be reached. A throw here gives `ceilingReached: null`, which means no line. The ticket gives that sentence to the report read only, and this read is the bar's to report.

Do not change `DaySpendReading`'s shape. Two pages read it, and neither needs this.

This check is not redundant with the hold check. `dayCeilingPause` appends its pause only *"before each claim"* (`day-ceiling.ts:181-182`). Between the spend reaching the ceiling and the next claim there is no pause in the log, so `view.paused` is false while the ceiling is already reached.

## Decisions the ticket leaves open

- **A hold** is `holding(view, now) !== null` (`queued.ts:361-366`): not offered, paused, or backing off. It sits beside `position === null`, which already covers most of it. Check both. It costs nothing, and it keeps the line correct if `position` is ever drawn for a held ticket.
- **k is `view.position`**, and the title's *N ahead of it* is `k − 1`.
- **Buckets are decided on the unrounded S, then the number is rounded.** So 59 minutes reads *about 60 minutes*, 60 reads *about 1 hour*, 90 reads *about 2 hours* (`Math.round(1.5)`), and 25 h reads *more than a day*. The tests at 59, 60, 90 and 25 h pin exactly this. Use the singular for 1 hour. Minutes round up to a multiple of 5 with `Math.ceil(min / 5) * 5`, so S = 15 exactly stays 15.
- **The 30-day window** is `now − outcomeAt ≤ 30 × 86 400 000 ms`. A null `outcomeAt` is excluded.
- **`elapsed_i`** is `now − since_i`. A future `since` (clock skew) gives a negative elapsed, which `max(T − elapsed, 0)` lets through as *more* than T. Clamp elapsed at 0.
- **The "past their typical length" wording** applies only when k = 1, the slots are full, and the first value the simulation pops is a `remaining_i` of 0. Return that as a flag from `estimateStart`. Do not infer it from S = 0: S = 0 with a free slot is the "no line" case.

## Checks

Everything here is unit-level: the pure module's table tests, `inFlightOf` with `since`, and the band's render test. Nothing depends on `pnpm test:integration`. Two things are not covered by unit tests:
- the store read in `loadTask`, which the type checker covers;
- the Next build seeing a server import in a client graph (`apps/release/integration/build.test.ts`). That is only a risk if `queued-estimate.ts` ends up imported from a `"use client"` file, and it should not be.

The ticket's `git grep` check for one `median` covers `packages` and `apps/board`. Keep it that way: do not copy `median` into the board.

The behaviour the estimate rests on, that `lastAttemptAt` is the claim's own timestamp and moves on a continuation, is settled by the log. It is the `ClaimedTicket` or continuation event's `at` that the `task_view` reducer writes into `last_attempt_at` (`task-view.ts:342`), not anything the board can see.
