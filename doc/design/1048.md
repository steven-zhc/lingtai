# #1048: the shape

The ticket gives the types. This note covers the decisions it leaves to whoever builds it. Each one is a place where a direct translation of today's code into Effect would compile and still be wrong.

## Where things are today

- **ES3-1 has landed.** `choose.ts:106` is `const openEffect: Effect.Effect<Opened>`. `process_` is `closableOnceEffect(openEffect, …)` (`choose.ts:174`). `processEvents` is `Effect.map(process_.get(), …)` (`choose.ts:210`).
- **The open you need is `process_.get()`.** Its refusal is already a defect: the `processEvents` comment says *"A rejected open — the 0056 refusal, or `ProcessLogClosedError` — is a defect"* (`choose.ts:205-207`). So `deferredWakerPort` needs no error channel, and its `ready` rejects with the refusal itself, as `deferredWaker`'s does now (`choose.ts:259-261`).
- **The baseline reads 8** (`effect-ratchet.baseline.json:3`). The eight are `choose.ts:270`, `choose.ts:300`, `sqlite.ts:348`, `wake.ts:125` and `subscribe.ts:164, 205, 284, 306`. Removing the first four leaves the four in `subscribe.ts`, which is the 4 the ticket asks for.

## 1. A port's `open` carries no error, so every failure is a defect, and busy is retried before it becomes one

`WakerPort.open` is `Effect<…, never, Scope>`. A failed connect, `LISTEN`, first poll or busy-past-`BUSY_MS` is therefore `Effect.die(err)` with the driver's own error.

- **Postgres:** wrap each `pg` promise with `Effect.tryPromise(…)` and then `Effect.orDie`, or use `Effect.promise`. `Effect.promise` turns a rejection into a defect carrying the same value.
- **Through the face:** `Effect.runPromise` rejects with `causeSquash(exit.cause)` (`effect@4.1.2 internal/effect.ts:5853-5855`). For a single `Die`, that is the defect itself. So `ready` rejects with the same `err` object as today, and `subscribe.ts:250` reports it as `'connection'` unchanged.

For SQLite, the retry loop has to see busy as a **typed** failure:

1. One attempt is `Effect.try` of `openSqliteLog(path, 0)` followed by the first `max(seq)` read. On failure it closes the handle it opened, synchronously, inside the same `try`. That is today's `stop()` before the rethrow (`sqlite.ts:361`).
2. Retry that attempt while `isBusy(err)` and `Date.now() < giveUp`, sleeping `Math.min(every, POLL_MS)` between tries. Use `Effect.retry` with a `while` and `Schedule.spaced`, or a recursive `Effect.sleep`.
3. Only then apply `Effect.orDie`.

## 2. The SQLite acquire is one attempt, and the retry wraps it rather than sitting inside it

The ticket says *"acquires its connection the same way, retries a busy file with `Effect.sleep`"*. Read literally, that could put the retry loop inside `acquireRelease`'s acquire. Do not: an acquire is uninterruptible, so a `close()` during the busy wait would block for up to `BUSY_MS`. That is the hang from the Watch out row, arriving by a different route.

The shape is:

```
Effect.acquireRelease(oneAttempt /* sync: open + first read, closes itself on failure */,
                      ({ db }) => Effect.sync(() => { try { db.close() } catch {} }))
  .pipe(retry-while-busy-until-giveUp, Effect.orDie)
```

- Each attempt is synchronous, and the busy timeout is 0, so nothing in the acquire can block.
- A failed attempt registers no finalizer, because acquire failed.
- `Effect.retry` sleeps outside the acquire, so a close interrupts the sleep at once.
- The poll fiber is `Effect.forkScoped` **after** this. Finalizers run in reverse, so closing the scope stops the poll before the connection closes, as the ticket says.

The poll step:

- **Busy:** skip, and poll again on the next tick (`sqlite.ts:376`).
- **Any other error:** call `Deferred.doneUnsafe(lost, Effect.die(err))` and **end the fiber**. Do not keep polling a dead handle. Today's `stop()` before `lost(err)` (`sqlite.ts:380-381`) becomes "the fiber ends, and the scope closes the handle when the face's fiber exits".
- **A changed head:** call `nudge()`.

## 3. The face reports `lost` from inside the fiber, and the fiber itself never fails after ready

The scoped body that `wakeSessionFace` runs:

```
Effect.scoped(Effect.gen(function* () {
  const { lost } = yield* port.open(() => listener.nudge())
  onReady()
  const exit = yield* Effect.exit(lost)
  // exit is Success → listener.lost(); a Die → listener.lost(Cause.squash(exit.cause))
}))
```

- **An interrupt never reaches `listener.lost`.** A close aborts the signal, which interrupts the fiber while it is suspended in `Effect.exit(lost)`. Interrupting that wait interrupts the fiber, and the code after it never runs. `lost` itself is only ever completed by a driver event, never by a close.
- **Pass `e` itself.** The Done-when test checks `listener.lost` is called with `e`, so take it from `Cause.squash` or the `Die`'s defect, never from a wrapped `FiberFailure`.
- **The fiber succeeds after `lost`.** Any rejection of the face's promise therefore means the open failed. `promiseWaker` builds `ready` with `Promise.withResolvers` and settles it like this:
  - `onReady` resolves it.
  - The face's promise gets `.then(undefined, (err) => { if (!signal.aborted) reject(err) })`, attached at `open`.
  - `ready` gets `.catch(() => {})`, as `wake.ts:136-137` does today.
  - A close before ready leaves `ready` pending forever. The contract allows that (*"May never settle when nothing answers"*, `wake.ts:42-44`), and `subscribe.ts:234-237` races it against `closing`.
- **`close()` is the whole of a close.** It is `abort.abort()`, which is idempotent and never throws.
- **One known difference, accepted:** if `listener.lost` throws, that becomes a defect and lands in the swallowed rejection, where today it would throw out of a `pg` event handler.

## 4. `backendPid` is a getter on the result, never a spread

`makePostgresWaker` keeps the mutable `backendPid` in its closure, as `wake.ts:96` does now:

- `open` sets the session's `pid` after the pid query, and sets `backendPid` to it.
- The release clears `backendPid` if it still equals this session's `pid` (`wake.ts:143`).
- The release is registered at acquire time, so it reads `pid` by closure.

**The trap is in `createPostgresWaker`.** `{ ...promiseWaker(port), backendPid: port.backendPid }` copies `null` once and never changes again. Write it as:

```
const w = promiseWaker(port)
return { open: w.open, get backendPid() { return port.backendPid } }
```

`integration/subscribe.test.ts` reads `backendPid` to sever the connection. It runs only after the merge, so nothing in `pnpm test` would catch the spread.

The Postgres release is `Effect.sync(() => { clear pid; void client.end().catch(() => {}) })`. That is fire-and-forget, as the comment at `wake.ts:144-148` explains. Keep that comment in the new code, beside the release.

## 5. `Opened.wake`: build each port once, in `openEffect`

- **Postgres branch:** `wake: (name) => makePostgresWaker({ ...(name === undefined ? {} : { name }), url: choice.directUrl })`.
  - `choice.directUrl` is `string`, not optional (`packages/env/src/index.ts:464`). So the default `directPostgresUrl()` can never apply here, which is what the comment at `choose.ts:109-120` requires.
  - Keep `createPostgresLog`'s own `waker(name)` (`log.ts:91-96`) unchanged. `createPostgresWaker` is now a face over the port, so that path changes behaviour nowhere.
- **SQLite branch:** build one `makePollingWaker({ path: choice.path })` and return it as `wake: () => port`. That matches `createSqliteLog`'s one waker for every name (`sqlite.ts:673-683`).
  - A port is stateless: each `open` is its own connection. So it does not matter that this is a second instance beside the one `createSqliteLog` holds.
  - `makePollingWaker` lives in `sqlite.ts`, which `openEffect` already imports dynamically (`choose.ts:147`). Take it from that same `sqlite` binding.

`deferredWakerPort(open: Effect<WakerPort>): WakerPort` is `{ open: (nudge) => Effect.flatMap(open, (p) => p.open(nudge)) }`. `index.ts:104` becomes `deferredLog()`, and `deferredLog` builds:

```
waker: (name) => promiseWaker(deferredWakerPort(Effect.map(process_.get(), (o) => o.wake(name))))
```

Update the comment at `choose.ts:288-293` to stop mentioning `resolve`.

## 6. Tests, and what stands in for the integration half

- **The two new unit tests** go in `packages/event-store/unit/`, over fake `WakerPort`s. Neither needs a filesystem or a socket.
  - The never-ready port: `Effect.acquireRelease(Effect.void, () => Effect.sync(() => count++))`, then `Effect.never`.
  - The lost port: it completes `lost` with `Effect.die(e)` after ready.
  - Assert `close()` returns synchronously, which it does by construction. **The finalizer runs only after the interrupt propagates.** So check `count === 1` after a macrotask flush, never on the next line after `close()`.
- **`unit/wake.test.ts` and `projector/unit/runner-stop-waits.test.ts`** pass unchanged. They hold the promise contract, not the ports.
- **SQLite:** `integration/sqlite.test.ts` (the busy retry at `:276`, the contract at `:118`) is the only check of §2. It touches the filesystem, so it is integration, but it is the package's own file on SQLite and well under 600 s. Run it as the ticket's Done-when says.
- **Postgres:** nothing before the merge exercises `makePostgresWaker`. The unit stand-in is §3's face tests plus `pnpm typecheck`. Keep the Postgres code a line-for-line move of `wake.ts:103-149`, so the review can read it against the original.
