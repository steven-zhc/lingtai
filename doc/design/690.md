# #690: design note for `lingtai report`

## What does not exist yet

**Nothing reads `ticket_report` today.** #687 left out a reader on purpose (`doc/design/687.md`, *Not in this change*). The fold's `State` is private (`packages/projector/src/ticket-report.ts:86`). `ProjectionStore` has `tasks`, `backlog` and `spend`, and no fourth read (`packages/projector/src/store.ts:317-332`). The function #688 built takes `ReportTicketRow` (`packages/conductor/src/report.ts:16-33`), and its comment says *"the next ticket's reader maps SQL onto it"*. This ticket is that next ticket, so the reader is part of it. If the page sibling lands first with its own reader, use that one and skip this section.

### The reader, in `packages/projector`

- **Add `ticketReport(query: { project?: string }): Promise<TicketReportRow[]>` to `ProjectionStore`**, next to `spend` (`store.ts:332`). Implement it in both twins, `postgres.ts` next to `:372` and `sqlite.ts` next to `:724`, with the same rule: no table means `[]`. On Postgres that is the `42P01` catch (`postgres.ts:397`); on SQLite it is `allOrEmpty` (`sqlite.ts:445`).
  - Filter by project in SQL only; `ticket_report_project_idx` exists for that (`ticket-report.ts:279`).
  - Do **not** filter by window in SQL. An open ticket is placed by `passTimes`, and that test belongs to `report()` (`report.ts:396-398`).
- **Write the row mapper once**, as an exported `ticketReportRowOf(row)` in `ticket-report.ts`, and have both twins call it. Do not write a twin mapper in each file the way `toSpendRow` is done:
  - `load` already turns the same columns into values that work on both stores (`ticket-report.ts:130-150`). `json()` at `:107` takes a string (SQLite) or an object (Postgres jsonb), and `outcome_at` goes through `new Date(...)`.
  - Two hand-written copies is exactly the divergence the contract file exists to catch, and the contract file only runs in the integration half.
- **`TicketReportRow` is declared in projector, not imported from conductor.** Conductor depends on projector (`packages/conductor/package.json`), so the reverse import would be a cycle. Give it the same fields as `ReportTicketRow`, and leave out `claims`, `rounds`, `open_intervals` and `applied_seq`. #688's note leaves those three out of `ReportTicketRow` too. Add a type-level assertion in the CLI's unit test (`const _: ReportTicketRow = {} as TicketReportRow`) so typecheck fails if the two drift apart.
- **Add `readTicketReport({ project })`** using `withProjectionStore({ max: 1 }, …)`, the shape `readSpend` has (`spend.ts:318-322`), and export it from `index.ts`.
- **The unit-level claim:** a test on `createSqliteProjectionStore(openSqliteProjections(':memory:'))` that folds a few events through `ticketReportProjection` and reads them back as `TicketReportRow`s, with `outcomeAt` as a `Date` and the JSON columns parsed. An in-memory SQLite store counts as unit under 0060 §1; `packages/projector/unit/backlog-rebuild.test.ts:12-18` is the precedent and spells out why. The Postgres twin is checked only by `test/contract.ts`, which runs in the integration half. Add a `ticketReport` case there too, but nothing inside the pass will run it.

Then run `pnpm docs:cli` (`package.json:24`), which regenerates `doc/cli.md` and `doc/cli.json`.

## Decisions the ticket leaves open

**Reading does not mean catching up.** `backlog list` folds its projection to the head before it reads (`backlog.ts:135-142`). `report` does not:
- It reads `projectionLag()` for `ticket_report` and for `spend`.
- For each one whose `lag > 0n`, or that has no checkpoint row, it prints one line on **stderr**: `ticket_report is <n> events behind the log — figures may be older than it`. The figures are still printed.
- This matches the ticket's edge (*"said on stderr, figures printed"*) and its *"no flag of it changes state"*.
- Catching up `ticket_report` from an empty checkpoint replays the whole log, and that is `lingtai projection rebuild ticket_report`'s job.
- If `projectionLag()` itself throws, say that on stderr too and still print the figures. A lag that could not be read does not mean the projections are current.
- Under `--json`, the document also carries `lag: [{ name, lag }]` (bigints as strings). This follows `backlog`, which puts its `behind` in the document (`backlog.ts:204`).

**Flags → `report()`'s input:**
- **`--window` values:**
  - `today` and `7d` go through `resolveWindow`.
  - Any other value is a usage refusal.
  - Neither `--window` nor `--from` given means `7d`.
- **Parse `--from`/`--to` as local dates, never with `new Date('YYYY-MM-DD')`.** That form is **UTC** midnight. `resolveWindow` then takes `startOfLocalDay` of it (`report.ts:54`, `day-ceiling.ts:38`), and west of Greenwich that lands on the day before. Use `/^\d{4}-\d{2}-\d{2}$/`, then `new Date(y, m - 1, d)`, and reject a date that rolls over (`2026-02-30`).
  - Only one of `--from` and `--to` given: refuse, naming the missing one.
  - `--from` later than `--to`: refuse.
  - Every refusal is a usage error.
- **`--window` together with `--from` or `--to`:** refuse with exit 2, and the sentence names both flags, e.g. `--window and --from/--to choose the window two ways; give one`.
  - Under `--json`, this is `printJsonError('report', 'usage', sentence)` with `handlerCode = 2`. `printJsonError` itself returns 1 (`output.ts:128-131`), so set the code explicitly, as `board`'s port refusal does (`cli.ts:359-364`).
- **`--kind <k>`:**
  - Exactly one kind, which becomes `kinds: [k]`. It is not checked against the recipe's `source.kinds`: the report reads the log as it is, and an old kind is still on it.
  - No `--kind` means `kinds: null`. Unclassified tickets then show in the per-kind table as their own row.
  - There is no spelling that selects *unclassified* alone. #688 decided never to map null to a string (`doc/design/688.md`, *Per kind*), and a recipe could have a kind called `unclassified`. Render the null row as `(unclassified)` in text and as `null` in JSON.
- **`--project <p>`:** given, it becomes `project: p` and is also passed to `readTicketReport`. Absent, it is `null` (every project). Do **not** pass `project` to `readSpend`: `report()` filters spend by project itself (`report.ts:403-405`). Reading every project's rows when no project is given is also what keeps a `spend` row with a null ticket in the total.
- **`readSpend({ since: window.from })`** keeps the read bounded. `report()` filters again by the exclusive end (`report.ts:202-205`).
- **`now`** is a port that defaults to `new Date()`, so the tests pin the window.
- **`sortBy`** is always `'rounds'`. Sorting by cost is the page's toggle (0123 §4), and the ticket does not ask the CLI for a flag.

**`--json`'s shape** is `{ version: 1, command: 'report', query: { window, from, to, project, kind }, lag, ...Report }`:
- `Report` already serialises cleanly. Dates become ISO strings, and money stays as `{ reportedCents, estimatedCents, unknown }`. Never fold it into one number (0110 §5).
- An empty window is the same document with zeros, nulls and `[]`, exit 0. `report()` already guarantees there is no `NaN` (`doc/design/688.md`, *An empty window does not divide*). Assert that `JSON.stringify` of it contains no `null` where a count is expected, and that it parses.

**The text form** follows 0121 §1–4: a heading line, then sections, never wrapped by the command.
- **Order:**
  1. The window and the project.
  2. Landed, closed and open counts. If `intervals.empty + intervals.open > 0`, a sentence saying how many passes the machine time skipped.
  3. Mean and median of passes, fix rounds, waits, machine time and cost.
  4. The 0-or-1 and 5-or-more shares.
  5. The survival steps.
  6. The window's spend.
  7. The per-kind table.
  8. The top eight, with each ticket's `sentence` exactly as `report()` built it.
- **Money:** printed reported first, then estimated (marked as estimated), then `n unknown` when `unknown > 0`, never as one sum.
- **Nulls:** a null mean or median prints `—`, never `0`.
- **Empty window:** with no placed tickets and no spend, print one line, e.g. `no tickets and no spend in <window>`. Do not print a page of dashes.
- **No terminal charts.** They are out of scope; survival and days are rows of numbers.

## Tests, all in `apps/cli/unit/report.test.ts` and `packages/projector/unit/`

- **Each flag reaches `report()`'s input.** Through the ports, check:
  - `--window today` / `7d` → the resolved window for a pinned `now`;
  - `--from 2026-10-01 --to 2026-10-03` → local midnights. Run this one under `process.env.TZ = 'America/Chicago'` set before the import, or assert by `getDate()` rather than ISO, so the UTC trap fails here;
  - `--kind bug` → `['bug']`;
  - `--project p` → `project: 'p'` and `readTicketReport({ project: 'p' })`.
- **Refusals:** both window flags (exit 2, the output contains `--window` and `--from`); a lone `--from`; a bad date; and an unknown `--window` value. Check each one with and without `--json`.
- **`--json`:** stdout parses as one document with `version`, `command: 'report'`, `query`, `lag` and the `Report` keys, and nothing else is on stdout.
- **A projection behind:** a `lags` port that answers `lag: 5n` for `spend` puts a stderr line naming `spend`, and the figures are still printed.
- **Empty:** no rows means exit 0, the one-line text, and the empty document.
- **Help:** `help.test.ts`'s table includes `report`, and `report`'s definition says `reads`.
- **The reader:** the in-memory SQLite round trip described above.

## Edges

- **A read that fails:** the store throwing goes to `failed('report', json, err)` (`cli.ts:38-45`). That gives the `unavailable` document under `--json`, or the message and exit 1 otherwise. A missing table is an empty report, not a failure (the store rule above).
- **A projection behind:** stderr plus `lag` in the document, figures printed (decided above).
- **A rebuild in progress:** `ticket_report` reads as partly empty while it replays, with a large `lag`. The stderr line covers that. No hold like `spendRebuildHold` is needed, because nothing is decided on these figures.
- **Two runs at once, a daemon folding underneath, a restart, a pause, a retry:** none apply. The command only reads, and the two reads are not one snapshot. Each projection is at its own checkpoint anyway (0123 §6), so this is no new inconsistency.
- **Null values:** a null kind is its own row, null figures print `—`, and unknown is a count beside the money, never 0.
- **Cost to later tickets:** a column added to the fold later is a field of `TicketReportRow`. The type-level assertion makes a missing one a typecheck error rather than a silent zero.
