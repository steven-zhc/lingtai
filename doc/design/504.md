# Design: #504, one arm sentence on both surfaces

## Where it goes

There are three places to change, plus one test.

**1. `describeArm` stops reading the row's ceiling, and its ceiling argument becomes required.**
`packages/projector/src/task-view.ts:1106` today:

```ts
export function describeArm(
  card: Pick<TaskCard, 'restarts' | 'restartsOf'>,
  restartsOf: number | null = null,
): string | null {
  ...
  const of = card.restartsOf > 0 ? card.restartsOf : restartsOf
```

Change the signature to `(card: Pick<TaskCard, 'restarts'>, restartsOf: number | null)`, with no default, and drop the `card.restartsOf > 0 ?` branch completely. This is the decision the ticket leaves open, and the answer is to remove the branch rather than keep it as a fallback. The function's own comment (`task-view.ts:1111-1118`) already says *"nothing writes this column a nonzero value any more"*, and the ticket's Watch-out says not to read `restarts_of`. A branch that can never be taken would leave the column looking authoritative to the next reader. `null` stays a legal value and means *the recipe could not be read*: the sentence falls back to `restart N`, which the board already does today when `limits` is null (`board.ts:504`, `board.ts:535`).

Rewrite the docblock above it (`task-view.ts:1087-1105`). The part that is now false is *"the sentence is decided once, here, beside the fields it is read from"*. The truth is that the sentence is decided here, the ceiling comes from the recipe, and every caller has to hand that ceiling in, which the type now enforces.

**2. `status.ts` passes the recipe's ceiling, from the `filter` it already has.**
`apps/cli/src/status.ts:106` already resolves `const filter = await projectFilter(...)`. On the readable branch that object carries `limits.restarts` (`packages/conductor/src/filter.ts:145-147`, filled at `:335` from `ceilingOf(resolved.recipe).restarts`). That is the same field the board reads (`apps/board/src/lib/board.ts:709`: `restarts: filter.limits.restarts`). So the ceiling is `filter.ok ? filter.limits.restarts : null`. Use the same `filter.ok` test that `kinds` and `backoffMs` use at `status.ts:111` and `:159`. Compute it once per project, beside `backoffMs`. Do not call `limitsFor` or resolve the recipe a second time.

Then remove the `restartsOf` plumbing in `status.ts`, which becomes dead:
- `:175`: `restartsOf: rowOf.get(r.taskId)?.restartsOf ?? 0`
- `:242`: the row type's `restartsOf?: number`
- the `restartsOf: t.restartsOf ?? 0` inside the call at `:317`

Correct the comment at `:311-316`. It is still true that *"the sentence is `describeArm`'s and not this file's"*. What it needs to add is that the ceiling is the recipe's, read from the same `filter.limits` the board reads.

**3. Pull the arm line into a pure export, so it can be tested.**
`status()` is not unit-reachable. The header of `apps/cli/unit/status.test.ts:5-8` says so, and that is why `offerLine` and `offerFailedLine` were pulled out (`status.ts:56`, `:61`). Do the same here: add an exported pure function, for example `armLine(row: { restarts?: number }, restartsOf: number | null): string | null`, that wraps `describeArm` and returns the text without the indent or the `paint`. `status()` then logs it the way it does at `:318`.

## The side-by-side test

Put it in **`apps/board/unit/`** (a new file, or beside `rail.test.tsx`). It imports:
- `toCard` from `../src/lib/board.ts`, as `rail.test.tsx:28` already does
- the new export from `../../cli/src/status.ts`

Make one requeued `TaskCard` with `restarts: 1, restartsOf: 0` (the shape the projection writes since #502; see `packages/projector/integration/task-view.test.ts:751-752`). Use one ceiling, `{ rounds: 3, restarts: 2 }`. Assert that `toCard(t, null, null, null, limits).arm` equals the CLI's line, and that both equal `'restart 1 of 2'`. Add a second case with `limits = null` on both sides, which gives `'restart 1'`.

**Why the board side imports the CLI and not the reverse.** No unit test does a cross-app import today, so this is the first one, and the direction matters.
- `status.ts`'s imports (`:9-23`) are `@lingtai/conductor`, `@lingtai/env/colour`, `@lingtai/projector` and `@lingtai/recipe/settings`. All four are already dependencies of `@lingtai/board`.
- The board's tsconfig is a superset of the CLI's: it adds DOM, `jsx` and the react types.
- Going the other way would pull `board.ts`'s Next and React graph into the CLI's `tsc`.

If `pnpm typecheck` still refuses the relative import under `apps/board`, the fallback is to put the test in `apps/cli/unit/status.test.ts` and pin both `armLine` and a direct `describeArm(card, limits.restarts)` there. That is weaker, because it does not exercise `toCard`, so try the board-side placement first.

## Other callers the type change will break

- `board.ts:535` already passes `limits?.restarts ?? null` and needs no change. Its `t` still satisfies the narrower `Pick`.

## What would settle it in the log

For a requeued ticket, the facts behind both lines are:
- `TicketReleased{cause:{_tag:'Restart', restart}}`, which sets `task_view.restarts`
- the recipe's `runtime.limits.restarts`, which is not in `events` at all

So nothing in the log can disagree with the fix. The unit test above is the whole of the check.
