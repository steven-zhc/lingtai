# Design: #1009, account locks through `locksOn` and the guard

Two things on this branch differ from what the ticket assumes. The rest of this note follows from them.

## 1. Every field of `locksOn`'s input is optional today, and the guard calls it once per check

`packages/domain/src/locks.ts:35` is `locksOn(input: { project?: ProjectState; control?: ControlState })`. The comment above it says: *"A caller leaves out what it does not read: the guard asks the ceiling in its own check and the pause in another."* Each check in the guard calls `locksOn` with only its own aggregate:

- `projectPause` passes `{ project }` (`packages/daemon/src/guard.ts:71`).
- `dayCeiling` passes `{ control }` (`:84`, `:106`).

The guard then joins the checks' results with `.flat()` (`:115`).

So a required `accounts` field reaches the guard's own two checks as well as the readers. **Decision:** make `accounts` required as the ticket asks, and export one constant beside `locksOn`:

```ts
/** For a read that is not about accounts. Grep for it to find every reader that opted out. */
export const NO_ACCOUNTS: ReadonlyMap<RuntimeId, AccountState> = new Map()
```

Do not pass a bare `new Map()` anywhere. That would be the silent "no account lock" that a required field exists to stop. With the constant, every caller either passes real `accounts` or names `NO_ACCOUNTS`, and a reviewer can grep for the second kind. These callers use `NO_ACCOUNTS`:

- **The guard's `projectPause` and `dayCeiling` checks.** The account check supplies the account locks itself.
- **`askRefusal` on the board** (`apps/board/src/lib/locks.ts:197`). It is a synchronous pause-only read, and its sentence ends `— resume it, then ask` (`:198`), which is the wrong remedy for an account lock. The daemon's `locked` still stops the discussion turn. Changing the board is #1010.

These callers pass `accountsFor`:

- `readProjectLocks` (`apps/board/src/lib/locks.ts:80`).
- `status` (`apps/cli/src/status.ts:541`).

`lingtai now` does not call `locksOn`. It goes through `refuseIfLocked` → `guard.locksFor` (`apps/cli/src/project-pause.ts:156`), so it gets the account check with no edit.

## 2. The guard has no recipe, and `lingtai now`'s guard must not append

`makeGuard` gets `{ store, snapshots?, ceiling, now? }` (`guard.ts:48-62`). It is built in three places:

- `apps/cli/src/daemon.ts:513`
- `apps/cli/src/run.ts:170`
- `apps/cli/src/now.ts:21`, with `ceiling: 'not-the-holder'`

The comment at `guard.ts:53-59` says why that last one is different: *"the system locks are written by the lock holder only (0126 §4), so it reads the stored ceiling lock, appends nothing"*.

**Decisions:**

- **`GuardOptions` gains `recipeFor?: (state: ProjectState) => Promise<ResolvedRecipe>`, defaulting to `currentRecipe`** (`packages/conductor/src/projects.ts:153`). `@lingtai/daemon` already depends on `@lingtai/conductor` (`packages/daemon/package.json:19`). Making it optional is safe here, unlike `accounts`, because the default is the real resolver and not a silent empty answer. Tests inject one.
- **The account check reads `prj-{project}` itself** to get the `ProjectState` that `currentRecipe` needs. That is a second small read beside `projectPause`'s, and it keeps each check one function (`guard.ts:23`: *"A check is one function added to `CHECKS`"*).
- **A non-holder guard appends no `AccountLimitLifted`.** The account check obeys the same flag as the ceiling. Do not add a second option: rename or reuse it so that "not the holder" means *append nothing* for both checks, and keep the comment at `:53-59` true. So `lingtai now` refuses an account whose `until` has passed until the next look lifts it. That is the same behaviour the ceiling has today.
- **Order in `CHECKS`** (`guard.ts:110`): `[dayCeiling, accountLimits, projectPause]`. This follows 0126 line 147: *"Rows are ordered: the ceiling, then each account limit, then each…"*.

## Where the pieces go

**`runtimesOf`** goes in a new `packages/conductor/src/runtimes-of.ts`, written as a pure function over `ResolvedRecipe['recipe']`. It starts with `runtime.agent`, then lifts the loop at `packages/conductor/src/conduct.ts:834-840` as it stands. `:841` becomes `runtimesOf(recipe).filter(r => r !== ownRuntime)`, kept as a `Set` so `secondRuntimes.size` at `:843` still reads.

**`accountsFor`** goes in `packages/conductor/src/account.ts`, beside `readAccount` (`:23`):

- It is an Effect.
- `recipeFor` is wrapped in `Effect.tryPromise` and caught **to the empty map**: a recipe that throws gives no account locks.
- A `readAccount` failure is a failure.
- Export it from `packages/conductor/src/index.ts:162`, beside `readAccount`.

**The guard's account check** reuses the one-retry pattern of `transitionAccount` (`account.ts:33-57`), with `accountCheck` (`packages/domain/src/account.ts:91`) as the transition. Do not copy `dayCeiling`'s inline `attempt`. Either export a lift-on-time variant from `conductor/src/account.ts`, or give `transitionAccount` a `now`-taking caller. Either way, the append happens at `state.version` as it does at `:45`. After the appends, build the map from the re-read states and answer `locksOn({ accounts })`.

**A failed account read gets its own sentence.** `lockFailure` (`guard.ts:123-126`) answers *"could not read whether X is paused"* for any error that is not `CeilingUnchecked`, which is wrong for an `acct-` read. Add a tagged `AccountUnchecked { runtime, why }` beside `CeilingUnchecked` (`:35`), and a branch: `could not read whether ${project} is locked — ${runtime}'s account: ${why}`. Leave the pause sentence unchanged; existing tests pin it.

## Readers that switch on `Lock['kind']`

Besides `oneSentence` in `locks.ts:57`, two exhaustive switches in `apps/cli/src/ceiling-words.ts` will fail `tsc` until they handle `account`:

- **`lockLine` (`:34`).** Today it answers `null` for the ceiling because the ceiling is installation-wide. An account lock is per project in `status` (0126 §8, *"exactly the locks §5 returns for it"*), so answer a line, using `lockSentence`'s account wording.
- **`lockJson` (`:48`).** Dates as ISO, like the ceiling's case.

`status.ts:685` builds the Queue header's `nothing starts: <kinds>` from the lock kinds. It filters out a ceiling from another day. **Do not filter an account lock whose `until` has passed:** it still stops the gate until the guard lifts it, so `nothing starts: account` is true.

## `doctor`

Model the new rows on `pausedProjects` / `pausedRows` (`apps/cli/src/doctor.ts:1302-1315`):

- Use status **`info`**, not the ticket's `ok`. The comment at `:1298-1300` says why `info`: *"a fact and not a failure, so it is `info` and takes no part in the exit code"*. Account rows should match their sibling. The Done-when box checks only that the exit code is unchanged.
- Like `pausedProjects`, the function returns a Promise **without the `async` keyword**, so the ratchet (`packages/domain/unit/effect-ratchet.test.ts`) counts nothing new.
- Read each `RuntimeId.options` account through `readAccount`. For each limited one, call `accountsFor`'s recipe step per registered project to sort projects into *waits* and *takes work*.
- If the project list or an `acct-` read fails, give one `warn` row named for what failed, as `:1306` does.

## Tests that stand in for the integration half

Everything in the ticket's Done-when can be checked as a unit test: `createMemoryEventStore()`, an injected `recipeFor` and `now`. Nothing here needs `pnpm test:integration`.
