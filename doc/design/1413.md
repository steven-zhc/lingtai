## Design: #1413 — a local checkout keeps `db` and says how to take its origin's issues

The ticket's three edits are mechanical except for one tension it does not resolve. Everything below is grounded in the worktree as it stands.

### The one non-obvious decision: how a consumer tells the two local cases apart

After the fix, `proposeSetup` returns the **same `value`** for both local sub-cases — `{ source: 'db', repository: null }` — because Done-when #1 pins `repository: null` for a local path with a GitHub origin. Today those cases differ structurally: the GitHub-origin local path gets `repository = githubSlugOfRemote(origin.value)` (`propose-setup.ts:232`) carried into `value` (`:251`), and the no-origin path gets `{ source: 'db', repository: null }` with `because: 'no GitHub origin, so Lingtai keeps its own tickets'` (`propose-setup.ts:253-257`). Once the fix forces `repository: null` on **both**, the **only** thing that distinguishes them is the `because` string.

This matters because Fix bullet 3 says the CLI prints "when the proposal's origin was a GitHub repository," and the obvious gate for that — `proposal.tickets.value.repository !== null` — is now **always false**, so a naive implementation never prints and Done-when #3 fails. The history case is the opposite trap: `propose-setup.ts:244-249` keeps a **non-null** `repository` for a GitHub origin with history, so any gate that keys on `repository !== null` would over-print there, violating the Edges line *"History: ... the hint is not printed."*

**Decision.** The discriminator is the `because` text, read off the single origin read `proposeSetup` already did — do not add a second origin read in the CLI (it would make the Edges "a read that fails → no hint" depend on which of two reads failed), and do not reintroduce a structural `repository` on the local-`db` `value`.

Make it a symbol, not a copied literal: export the no-origin sentence from `propose-setup.ts` (today inlined at `:256`) as a named const, build the three local `because` strings from that one place, and gate the CLI print on:

```
proposal.tickets.known
  && !proposal.tickets.because.startsWith('kept:')   // excludes the history case (:249)
  && proposal.tickets.because !== <the no-origin const>
```

The board needs no discriminator: `lineOf` already sets `note: line.because` (`view.ts:20-22`), so dropping `localTicketsOf`/`ownerless` and setting `tickets: tickets` surfaces the GitHub-origin `because` — owner/repo and the command — as the line's note, which is the "one line" the Want asks for.

### The board deletion is wider than `:70`

The ticket names `githubOff` at `view.ts:70`. `githubOff` lives in **four** more places that all go, or `pnpm typecheck` stays red:

- `view.ts:127` — a **second** `githubOff` assignment, in the "could not be read" `unreadView` (that view also sets `tickets: unread(local ? 'db' : 'github')` at `:126`; for a local path that is already `'db'`, so it needs no change).
- `read-model.ts:68` — the `githubOff: string | null` field and its doc comment.
- `setup-form.tsx:233` — `disabled={view.githubOff !== null}` on the `github` radio, and `:237` — the `<span className="wiz-tag">{view.githubOff}</span>`.
- `setup-form.test.tsx:28` — `githubOff: null` in the view fixture.

On `setup-form.tsx`: with `githubOff` gone the `github` radio is no longer disabled for a local path. That is **not** a registration hole — a local target is written by `addLocalEffect` (`add-from-page.ts:468`), which registers from the resolved recipe and never reads `form.tickets`, so owner stays `null` and `ownerlessRefusal` still guards a recipe that somehow says `github`. Keep the change minimal: the `github` radio simply loses its `disabled` guard and its tag. Do not build a new "db-only" presentation for local — that is behaviour beyond the line the Watch-out forbids.
