# Design: #399, land or hold, and the limits

## Where it goes

There are three pieces, in three packages. The split exists so the test that matters most can reach the code it pins.

| Piece | File | Why it lives there |
|---|---|---|
| **What an answer writes** | `packages/recipe/src/answers.ts`, exported from `index.ts` | Turning an answer into `RecipeChange[]` (`emit.ts:64`) is pure and needs no terminal. The conductor's unit test has to import it, and `@lingtai/conductor` depends on `@lingtai/recipe`, not on `apps/cli`. |
| **The questions** | `apps/cli/src/landing.ts`, tests in `apps/cli/unit/landing.test.ts` | `askLanding` and `askLimits` go through `question()` (`question.ts:52`) and write each answer with `setRecipe` (`write.ts:172`). |
| **The caller** | `addCommand` (`lingtai.ts:362`) | `add` is the only command that has a project today. `init` gets one only when #394 lands, and #391's settled rule is that *"`lingtai add` is interactive too, by the same code"*. |

**Ask before `add()` runs, not inside it.** `add()` in `packages/conductor/src/onboard.ts` resolves the recipe at `:285`. It also has a second caller, the board's Recheck (#163), which must never ask a question. So the questions go in `addCommand`, before the call: write first, then let `add()` read what was written.

**Ask only when the recipe file already exists.** Use the same project key `add()` uses, `recipePath(repo)` (`onboard.ts:277`). #395's design says a new file cannot resolve from these keys alone: it needs `repo.base`, `source.kinds` and `env`. It also says *"for an absent file, the caller collects the first run's answers and calls `setRecipe` once"*. That first-run collection is #394/#396–#398's to build.

So when the file is absent, ask nothing and let `add()`'s existing "no recipe" refusal speak. Do not seed `source`/`env` to get around this; #395 explains why.

**This changes what `lingtai add` does without a terminal.** With no TTY and none of the four flags, it now refuses by name, because the seam refuses even when a current value exists (#392 decision 3). That is #391's rule, and nothing in the repository calls the `lingtai add` CLI non-interactively. The board calls `add()` directly.

## The land question: `--land <branch>|hold`

### What each answer writes

- **`hold`** appends one entry to `steps.proposed` and touches nothing else:
  ```yaml
  - name: hold every pass
    human: "Land this? The setup was answered 'hold'."
  ```
  - **It never writes `steps.merge`, and never writes it empty or absent.** At `conduct.ts:2297-2298` the comment says *"Until it lands, an `admit: []` cuts and a `merge: []` merges"*.
  - The resolver's own refusal points at this same place: *"To hold a pass before anything lands, declare a `human:` action at `proposed:`"* (`recipe.ts:2530`).
  - `humanPlugin` does not serve `merge` (`recipe.ts:698` onward), so writing it there would be refused anyway.
  - If `steps.proposed` already contains a `human:` entry, do nothing (`written: false`).
- **`<branch>`** does two things:
  1. It sets `repo.base` to the branch.
  2. It writes `steps.proposed` back **without any of its `human:` entries**. Every other entry stays: the `judge:` entries from #274, and `watch:`.
  - It removes *every* `human:` entry, not just the one `hold` wrote. Any `human:` at `proposed` holds every pass, so "land" with a hand-written hold still in place is not landing.
  - If a removed entry carries a comment, `editRecipe` throws `CommentWouldBeLostError`. Surface that refusal by name. Do not strip the comment to get past it.

### The pure builder in `answers.ts`

Its inputs are the answer and the list the file currently writes at `steps.proposed`. Read that list with `readRecipeKey(['steps','proposed'])`; null means `[]`. It returns the changes.

`setRecipe` already widens a first `steps.*` write on a file that has `extends:` (#395, `write.ts`). That widening **pins the preset's other steps into the file**, and #395 says the caller is where a person is told so. When `written` is true and the file had no `steps:` before, log one line saying it.

### The default

`current ?? detected`:

- **`current`**:
  - `'hold'` if the resolved recipe has a `human:` at `proposed`. Resolve the text with `resolveSource`, so a hold that comes from a preset also counts.
  - Otherwise, what the file writes at `repo.base` (`readRecipeKey`).
- **`detected`** is the repository's default branch, from `GitHubClient.defaultBranch()` (`packages/github/src/client.ts:404`).
  - Pass it into `askLanding` as a port, `defaultBranch: () => Promise<string | null>`. Unit tests give it a stub.
  - In `addCommand`, build it from `githubApp()` → `installationForRepo` → `createGitHubClient`, the same calls as `onboard.ts:251-276`. A failure answers null.
  - When there is no default at all, `validate` refuses an empty answer.

### `--base` against `--land`

`add`'s `--base` is a different flag: it says where to *read* the recipe, and `add()` refuses when it contradicts `repo.base` (`onboard.ts:290`). If both flags are given and name different branches, **refuse in `addCommand` before writing anything**. Otherwise `--land` writes a base and `add()` then refuses the `--base` the same person typed.

## The limits: `--rounds`, `--wall`, `--budget`

**A limit writes only when the answer differs from what the recipe resolves to now.** `detected` is the resolved value, and `current` is what the file writes. Pressing enter on an inherited `rounds: 2` must not write `rounds: 2` into the file. Writing it would pin the default, which is the thing `readRecipeKey`'s comment (`write.ts:190-197`) guards against.

| Flag | Key | Validation | Notes |
|---|---|---|---|
| `--rounds <n>` | `runtime.limits.rounds` (`recipe.ts:3100`) | integer ≥ 0 | The prompt says 0 means *every refusal goes to a person*. |
| `--wall <duration>` | `runtime.limits.wall` | `parseDuration` (`duration.ts:13`) must not throw and must be > 0 | Validate in the question so a bad answer is asked again. Otherwise it reaches `setRecipe` as a `RecipeInvalidError`. |
| `--budget <dollars>\|none` | **`runtime.limits.usd`** (`recipe.ts:3148`) | positive number, or `none` | Accept `5`, `5.00` and `$5`. `none` writes `value: undefined`, which removes the key. The default when absent is `none`: *"absent means no dollar ceiling, said out loud, never assumed"* (`recipe.ts:3144-3146`). |

**`--budget` does not touch the recipe's `budget:` key.** `runtime.budget` (`recipe.ts:3194`) is 0029's prompt budget: how many characters of evidence are quoted. Writing to it is the obvious wrong-key bug, so name the target key in a code comment.

**Showing the ceiling in money** is the third Done-when:

- The `show` for the budget question prints `$5.00` or `none`.
- The prompt says the ceiling is **per agent run**.
- After the three answers, log `passCeiling(...)` (`packages/conductor/src/ceiling.ts:58`, which `apps/cli` can import as `@lingtai/conductor/ceiling`). Feed it the values just answered. Its comment says *"Dollars add up across runs the same way time does"*, so the line states what a pass and a ticket may spend. Do not write that arithmetic a second time.

A runtime that cannot enforce `usd` (Codex, #370) is not refused here. `doctor.ts:1714` onward already reports it. Add one muted line saying so when the project's `runtime.agent` is not `claude-code`.

**Write each answer as soon as it is given.** Make one `setRecipe` call per answer, as in #392 decision 1 and #391's *"A Ctrl+C keeps what was answered"*.

## The tests

### `apps/cli/unit/landing.test.ts`

These use a `Map`-backed `RecipeFiles` and a scripted `QuestionWorld`. Nothing touches the disk (0060 §1). Start from a resolvable inline fixture that has `merge:` written. The pure builder also needs a case where `merge` is absent.

- **`--land hold`:**
  - The written text has exactly one `human:` at `steps.proposed`.
  - `resolveSource(text, …)` accepts it.
  - The resolved `steps.merge` is identical to the fixture's.
  - The `merge` node in the text is byte-identical to the fixture's.
  - Run it a second time: the result is `written: false`.
- **`--land release`** on a file holding at `proposed`:
  - `repo.base` is `release`.
  - No `human:` entry is left at `proposed`.
  - A `judge:` entry beside the hold survives.
- **The limits:**
  - `--rounds 0 --wall 30m --budget 4` each land at their `runtime.limits` key.
  - `--budget none` removes `usd`.
  - Enter on an inherited default writes nothing.
  - The budget prompt contains `$`.
  - The logged lines contain `passCeiling`'s sentence with the dollar figure.
- **With no terminal and no flag**, the result is `{ refused }` naming `--land`, and `replace` is never called.

### `packages/conductor/unit/conduct-a-whole-pass.test.ts`: the pin the ticket asks for

Add a case beside *"holds at a person the recipe declared before the lane"* (`:312`):

1. Start from `RECIPE` (`test/one-pass.ts:109`), which lands by default.
2. Apply the hold changes from `@lingtai/recipe`'s builder with `setRecipe` on `Map` files.
3. Hand the text to `fakeGitHub(said, text)` (`one-pass.ts:409`).
4. Run `once` with `merge: true` and `fakePorts(did, store, true)`.
5. Assert `result.ok === 'held'`, `result.step === 'proposed'`, `did` does not contain `'integrate'`, and the item's stream has no `WorkItemLanded`.

Add the inverse too: `--land main` applied to `HUMAN_BEFORE_THE_LANE` (`:374`) lands.

**This is what proves that what the setup writes actually holds the pass, and not just that it resolves.** The CLI test proves flag → file, and this one proves file → held. They are the same claim only because both import the same builder. So the CLI must not build the hold entry itself.

Everything above is in the unit half: `pnpm test` runs it and nothing needs `pnpm test:integration`. What no test reaches is `addCommand`'s real `defaultBranch` port (a network call) and `diskFiles`. Keep the port to the three calls `onboard.ts` already makes.

## What the log will show

Nothing in `setRecipe` appends. A changed recipe appears as a new `configHash` on the next `ProjectConfigured` that `add()` appends. A hold that works appears as `ApprovalRequested` on the run's stream for a pass that stopped at `proposed`, with no `WorkItemLanded` on the item. As always, a daemon started before this merged still runs the code it started with.
