The ticket already settles where the change goes and what it does. This note covers three things the ticket leaves open: how the mode slot gets the board, which files the recipe import may reach, and a test that would go red on wording alone.

## 1. The mode slot is handed `ctx.reads.board`; it does no reading of its own

`sandboxSlot(project, key)` reads for itself: `Icon` calls `readSandboxMark(project)` (`apps/board/src/app/sandbox-slot.tsx:11-12`). If `modeSlot` copies that shape literally, it ends up calling `projectRecipe` or `projectFilter`. That is the second read per render the ticket forbids: *"a recipe is still read once per project per render — reading one twice is how a render gets expensive"* (`lib/board.ts:1105-1106`).

Copy only the outer shape (a keyed `Suspense` around an async inner component) and pass in the promise the page already holds:

- Signature: `modeSlot(board: Promise<Pick<Board, 'askable' | 'projects'>>, param, key('mode'))`, with `Board` imported as a type only from `lib/board.ts`.
- Call site: `{modeSlot(ctx.reads.board, param, key('mode'))}`, between `{sandboxSlot(param, key('sandbox'))}` (`page.tsx:1307`) and `<Health` (`page.tsx:1308`). `key` is the closure at `page.tsx:1199`.
- Inside: `selectedProject(param, board.projects)` (`lib/board.ts:2015`), then `board.askable.find((f) => f.project === selected)`.
  - If nothing is selected or nothing matches, return `null`.
  - Otherwise render the link built from `modeMark(found.recipe)`.
  - Wrap the await in `.catch(() => null)`. Every other part awaits `ctx.reads.board` uncaught (`page.tsx:826`, `:876`, `:909`, …), so a rejection must not escape here either.

`board.askable` is `AskableFilter = Extract<ProjectFilter, { ok: true }>` (`lib/board.ts:955`). `queueFilters` already reads `filter.recipe` off it (`modeOf(filter.recipe)`, `lib/board.ts:1157`), so `.recipe` is there with no cast.

A unit test pins the shape:
- `mode-slot.tsx` does not contain `projectRecipe`, `readRecipe`, `projectFilter` or `readSandboxMark`.
- `page.tsx`'s rail contains `modeSlot(ctx.reads.board`.

This is the unit-level stand-in for *no new read*. The other witness would be the `board.recipes` timing (`lib/board.ts:1830`) still showing one entry per render, but no unit test can see that.

## 2. Keep `@lingtai/recipe` and `lib/recipe.ts` out of the glyph and row files

`lib/recipe-lines.ts` imports `readRecipe` from `./recipe.ts` (`recipe-lines.ts:19`), which is file IO. `modeMark` must call `modeLines`, so `lib/mode-mark.ts` carries that import with it. The rows sit inside `ProjectLink` and `FilterMenu`, which are `'use client'` (`project-link.tsx:1`, `filter-menu.tsx:1`). `ProjectRows` itself is a server component with no directive (`projects.tsx:1-33`). A server-only import reaching a client graph is the one failure `tsc` cannot see and `pnpm test` does not run: only `apps/release/integration/build.test.ts` catches it, after the merge (#230).

So:

- **`app/mode-glyph.tsx`** holds `ModeGlyph` (the two SVGs), `ModeLink` (the bar's `Link`) and `ProjectModeMark` (the row's `span role="img"`, the same span-in-a-link pattern as `sandbox-mark.tsx`). Each takes a `ModeMark` value (`{ mode, sentence }`, plus `project` for the link). The file imports `ModeMark` from `lib/mode-mark.ts` as a type only: `import type`. It never value-imports `lib/mode-mark.ts`, `lib/recipe-lines.ts` or `@lingtai/recipe`.
- **The menu's map** is built in `readMenu` (`page.tsx:825-829`), which already awaits `board`: `mode: new Map(board.askable.map((f) => [f.project, modeMark(f.recipe)]))`. Both `ProjectRows` call sites (`MenuRows`, `page.tsx:834-841`, and `FilterSlot`, `page.tsx:848-855`) pass `mode={m.mode}` beside `sandbox={m.sandbox}`.
- **The prop** on `ProjectRows` is `mode?: ReadonlyMap<string, ModeMark>`. Leaving it out draws nothing, which matches `sandbox?` (`projects.tsx:60-61`).

Make the row test check the import rule too: `projects.tsx` and `mode-glyph.tsx` may contain `from '@/lib/mode-mark.ts'` only as an `import type`.

## 3. Rendering `.pname`

Today `.pname` is drawn only when a sandbox state exists; otherwise the row's child is the bare `p` (`projects.tsx:90-98`). If a project has a mode but no sandbox entry and the mark is put inside that branch, it disappears. Build `.pname` when either map has an entry. Its children are, in order: the name, `ProjectSandboxMark` if there is one, then `ProjectModeMark` if there is one. The comment at `projects.tsx:93` (*"name and mark are one child, so the mark stays beside the name"*) explains why both marks go inside `.pname`.

The rail assertion at `:145-155` only lists what must *not* be in `.rail`, so `modeSlot` does not trip it. The ticket's *"gain the mode slot"* is the new order test (shield → mode → health), not an edit to that list.

## Edges this decides

- **The board read rejects:** the slot renders `null`, never a mode (§1). The menu needs nothing extra: `readMenu` already fails as a whole today, and the mode map adds no new way for it to fail.
- **`param` names a project not in `askable`** (an unresolved recipe, or a project that is not registered): `find` returns nothing and no icon is drawn. This is the absence the ticket's Edges already settle.
- **`ctx.reads.board` was already awaited elsewhere:** that is fine. It is one promise, and each `await` reuses the same result.
