**Design note — #1266, the base-fix ticket**

#1208 and #1211 are both built in this worktree, so this ticket adds to code that already exists. It does not create anything new beside it. There are three places to change, plus one new event.

### 1. The state: `baseStateOf` learns the first red commit and the fix ticket

`baseStateOf` (`packages/domain/src/integration.ts:173-195`) already reads `int-{project}-{base}` and answers `red` from the newest `BaseChecked`. Extend it so the `red` branch also carries:

- **`firstRedSha`** and **`firstRedAt`**. Walk back from the newest `BaseChecked` to the newest one with `ok: true`. The oldest red after that green gives `firstRedSha` (its `baseSha`) and `firstRedAt` (its envelope `at`, `envelope.ts:95`). If there is no green on the stream, use the oldest red overall. This is the ticket's *Watch out*. Ignore the command in this walk, because `baseStateOf` already ignores it for "newest".
- **`key`** = `base-red:<base>:<firstRedSha>`.
- **`fix`**: `{ key, externalRef, url } | null`. Take it from the newest `BaseFixProposed` on the same stream whose `key` equals the key above. Red, then green, then red again gives a new key, and the old record no longer matches.

Keep this function pure, in domain. It is the one answer that the look, `conduct.ts` and the status read all already use (`base-red.ts:29-44`, `conduct.ts:5554`).

**The new event.** Add `BaseFixProposed{ project, base, baseSha, key, externalRef, url }` to `events.ts`, next to `BaseChecked` (`:1544`).
- Add it to the registry (`:2717`-ish).
- Give it an `EVENT_AT` entry: `['end']`. Without one, `satisfies` refuses at `tsc` (`:2770-2775`).
- `reduceIntegration`'s `switch` already has a `default:` (`integration.ts:118`), so the lane's state does not move.

### 2. The look: `passOverBaseRed` exempts the fix ticket

Exempt it in `passOverBaseRed` (`base-red.ts:92`), not in `schedule.ts`.
- Both pickers call it: the queue (`schedule.ts:262`) and a `now` request (`passOverForRedBase`, `base-red.ts:154`). Putting the exemption here keeps the two from disagreeing, which that comment says is the point (#1208).
- `held` gains `fix: { externalRef, url } | null`, filled in by `lookAtBase` from the state.
- In `held`, the runnable entry whose `ref === fix.externalRef` stays in `runnable`, and every other entry is skipped as `base-red`.

The line then says one of two things:
- When the fix ticket is in `runnable`: *offering #N to fix it*.
- When it is absent: *#N, opened to fix it, is not in the queue*. That covers closed, held or backed off; the look cannot tell which, so the line does not claim one.

`unreadable` still skips everything. A log we cannot read cannot name the fix ticket either, and the ticket does not ask for a fix ticket while the mirror is down.

`why-nothing-runs.ts:38` reads `BaseRedLook`, so it receives the new field. It needs no change beyond what `tsc` asks for.

### 3. The attempt: the fix ticket gets no `baseIsRed` at all

There are **three** callers of `baseIsRed` in `run-attempt.ts`, not the two the ticket names:

| Line | What it is |
|---|---|
| `:1742` | the guard at `proposed` |
| `:2067` | #1208's first check (`baseFirst`) |
| `:2136` | #1211's continuation merge |

`AttemptOptions.baseIsRed` is optional, and `run-attempt.ts:935-939` reads: *"Absent where a caller says nothing"*. So the exemption goes in `conduct.ts` alone, with no change to the walk:

- At `conduct.ts:5554`, read `baseState` **whether or not this is a continuation**.
- Call the ticket `isBaseFix` when the state is `red`, it has a `fix`, and `fix.externalRef` is this ticket's issue number.
- When `isBaseFix`, pass neither `baseIsRed` nor `baseFirst` (`conduct.ts:5595`).

A red `build` then reaches the judge as it does on any ticket, and buys `fixRefusal`. A fix ticket from an earlier red (old key) is not exempt. A fix ticket on a green base needs no exemption.

### 4. Proposing: at the one `BaseRed` ending, after the release

Every `BaseRed` end reaches one block: `conduct.ts:5934-5947`. That covers the first check, the guard at `proposed`, and the continuation's red-again. Propose there, **after** `release(why, cause)`, as one Effect, say `proposeBaseFix` in a new `packages/conductor/src/base-fix.ts`, so the release never waits on it. Any failure becomes `runLog.note('base', …)` plus `log(…)` and is then swallowed.

**When to propose.** Propose on **every** `BaseRed` release whose state has no `fix` for the current key. Do not limit it to releases whose check `ran`.
- Every red that is recorded is already red twice. The rerun "can only turn a red into a green, never produce a red" (`base-check.ts:22-25`).
- Only a command that ran to an exit code is recorded (`:18-21`).
- So *red twice* holds for every `BaseRed`, from the log or not.
- Gating on `ran` would break the ticket's own edge: *"a failed propose … asked again on the next red release"*. The next release on the same commit is answered from the log, so a `ran` gate would never ask again until the base moved.
- When the record exists, nothing is proposed. That is the *"finds the ticket already there"* case.

**The door.** Build it with `githubTicketStore(options.client)`. `TurnClient` is `Tickets & …` (`conduct.ts:555`), and the store needs only `createIssue | listIssuesSince | comment | closeIssue` (`ticket-store.ts:154`). It is the only `TicketStore` implementation (`ticket-store.ts:153`). A project registered from a local directory gets its own `Tickets` behind the same verbs, so nothing here branches on GitHub.

**The `ProposedTicket` (`ticket-store.ts:97-111`).**

| Field | Value |
|---|---|
| `key` | the key from §1 |
| `since` | `firstRedAt` |
| `kind` | `kindsOf(recipe)[0] ?? 'bug'` (as `queue.ts:79`) |
| `labels` | `[]`, so no `agent:hold` |
| `title` / `body` | as the ticket's edges say |

`since` is load-bearing. The GitHub store only lists issues created after `since − 1h` (`:162-167`), so a `since` of *now* would miss the ticket an earlier release opened, and open a second.

The body's evidence:
- the first red's `baseSha`
- the current red's `command`, `boundary` and `evidence`
- `flaky` from the newest record carrying one since the last green, when there is one

**Recording it.** Record `BaseFixProposed` the way `base-check.ts` appends to this stream (`:320-350`), **not** the way `backlog.ts:333-358` does.
- The backlog appends at version `1` on a stream of its own, so a `ConcurrencyError` there *means* another opener won.
- `int-{project}-{base}` has other writers (the merge lane, base checks, `base-check.ts:29-31`), so here a lost race usually means something unrelated landed.
- So: read the stream, and if a `BaseFixProposed` for the key is now there, settle. If it names a different `externalRef` and our propose was `created`, call `withdraw(ours, theirs, why)`; that is the backlog's `settle` rule (`backlog.ts:365-`).
- If no record is there, append at the version just read. Retry a bounded number of times, then note the failure.

The second race `propose` itself covers (`ticket-store.ts:127-131`).

### Edges the ticket leaves to the design

- **A process dies between propose and record.** The next `BaseRed` release finds no record, proposes again, and gets the same issue back (`created: false`). It then records that issue.
- **Two conductors at once (0122).** `propose` converges on one issue, and the append race is handled as above.
- **Unknown ticket number.** `externalRef` is a string (`"212"`). Compare it to the offered entry's `ref` and to the attempt's issue number as strings, never as a parsed `Number`. Do not compare against `ticketId`.
- **Effect ratchet.** `proposeBaseFix` is an `Effect.gen` with `Effect.tryPromise` around `store.read`/`append`. `propose` is already an Effect. No new `async` and no `Effect.run*`.

### Tests (unit)

**`baseStateOf`**
- Red at A, then at B: key `…:A`.
- Red, green, red at C: key `…:C`.
- `fix` matches only its own key.

**`passOverBaseRed`**
- `held` with a fix ticket in `runnable`: it alone is offered.
- With the fix ticket absent: every ticket is skipped, and the line names it.

**`proposeBaseFix`**, against `createMemoryEventStore()` and a fake `TicketStore`
- No record: one `propose` with the key, title, kind and body, and one append.
- Record present: no `propose`.
- A propose that fails: a note and no append. The release was appended earlier and is untouched.
- An unrelated append between read and write: retried.
- A competing record for the same key: withdraws ours.

**The attempt.** Assert in `conduct-a-whole-pass` style that the fix ticket's pass is handed no `baseIsRed`, and that a red `build` routes `fix-lines`.

None of this needs `pnpm test:integration`.
