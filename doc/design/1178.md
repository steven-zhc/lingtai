## The three reads: new file `packages/project/src/read.ts`

**`recipeText(project, options?: { home?: string; store?: EventStore })`** returns `Effect<string | null, …>`. It has the same skeleton as `loadProject` (`load.ts:19-60`):

1. Take the store with `options.store ?? (yield* defaultStore())`.
2. Call `readProjectStateEffect` **before** the file, so a failed log read fails the text read (`load.ts:21-22`: *"a failed read of the log must fail here, never read as no recipe yet"*).
3. Read through `filesEffect(yield* ProjectFiles)`, inside `recordObservedRecipe`.

It differs from `loadProject` in two places:

- **A missing file** answers `null` and appends nothing.
- **A text `checkDeclared` refuses** is returned as text and nothing is recorded.

So the observation needs a "nothing to record" outcome. Change `recordObservedRecipe` (`commands.ts`) so that `observe` may answer `null`, and skip the append when it does. `loadProject`'s observer keeps failing on missing or refused text, so its behaviour is unchanged.

Keep the observation **inside** the attempt, and return the text from the last attempt. That retry-on-lost-race is the #1177 fix, and its comment (`commands.ts`, `recordObservedRecipe`: *"`observe` runs again on the retry of a lost race"*) is the reason. Factor the read → `sourceOf` → `checkDeclared` → payload steps into one helper that both `loadProject` and `recipeText` call, so there is one comparison and not two.

**`recipeValue(project, keyPath, options?)`** is `keyIn(yield* recipeText(...), keyPath)`. It keeps `readRecipeKeyEffect`'s rule from its doc comment (`write.ts:15-21`): *"What the file says, not what resolves."* Delete `readRecipeKeyEffect`.

**`projectsOnDisk(home): string[]` stays synchronous.** It holds `describeHome`'s body from `init.ts:1231-1234`: the directories of `home` that hold a recipe file. It records nothing.

- **Watch out:** `describeHome` is a plain function, `(home, path) => string`, in `liveMachine()`. If `projectsOnDisk` were an Effect, `apps/cli` would need an `Effect.runSync`, and `apps/cli` is `{ "async": 0, "run": 0 }` in `effect-ratchet.baseline.json`. That breaks *the ratchet only goes down*.
- It belongs in the module only so that the `existsSync` of the path sits inside `packages/project/src`.

## Rule for each site: draft inside an add, `recipeText` outside one

The ticket says *"A key read inside `lingtai add` reads the draft."* I extend that to **every** read inside an add flow, text included. That covers `lingtai add --local`, the `init` first-project path that shares it, `lingtai add <owner>/<repo>` and the board's add-from-page.

- **Inside an add:** read `draftRecipe(...)` with `.get` and `.text()`. These read through `ProjectFiles` and record nothing (`draft.ts:1-8`, `write.ts`'s `resolveDraftRecipeEffect` doc: *"It records nothing"*).
  - `first-project.ts` 590-662, 760 and 861 and `add-github.ts` 344-386: open one draft where the flow first needs the file, and read it there. One draft per flow is better; if handing it on to `askRecipeEffect` takes too much rework, a second `draftRecipe` read is acceptable.
  - `add-from-page.ts` `recipeIsNew` and `answersFor`: these only need "is there a file", so use `draft.text() !== null`.
- **Outside an add:** use `recipeText` or `recipeValue`, which record.
  - `init.ts:453` (the listing) → `recipeValue`.
  - `init.ts:685` and `:842` → `recipeText`.
  - `add.ts:285`, the read-back after `changeRecipe` → `recipeText`. It appends nothing, because the hash was just recorded.
  - The board's `textIfReadable` → `recipeText`.
- **The store:** pass `world.store` wherever the world has one. The init world hands in a memory store since `fe2d8abc`.

### The board's error page

- Run `recipeText` the way the board already runs Effects without being counted, such as `apps/board/src/lib/locks.ts:39`'s `Effect.runPromiseWith(Context.empty())`.
- Catch every failure to `null`, so `projectRecipe` still *"never throws"* (`recipe.ts:436`).
- A text that is shown because it does not resolve is usually refused by `checkDeclared`, so it records nothing.
- A fault of `'recipe'` whose text is a valid declaration (for example `AgentUnresolvedError`) **is** recorded `by: 'file'`. 0128 §6 says *"on every read"*, so that is correct.

### `resolveDraftRecipeEffect`

Read the other paths through `ProjectFiles`, as `loadProject` does. `first-project.ts:992` is its only outside caller. Without this, *"no exported function of the module takes a `files` option"* holds in name only. `LoadProjectOptions` already omits `read` (`load.ts:16`), for the same reason.

### `applySetup` and `previewSetup`

## Exports

In `packages/project/src/index.ts`, replace `export * from './files.ts'` with `export { ProjectFiles } from './files.ts'`.

- That stops exporting `diskFiles`, `filesEffect`, `readRecipeFile`, `replaceRecipeFile` and the two faces.
- `ProjectFiles` stays exported, because tests provide it.
- `@lingtai/project/test/seed-recipe` keeps importing from `../src/files.ts` directly.

**`RecipeFiles` stays a type in `@lingtai/recipe`** (`packages/recipe/src/write.ts:21`).

- `@lingtai/project` never re-exported it: `files.ts` imports the type and does not re-export it.
- 25 test files build memory ports with it.
- It is an interface and reads nothing, so 0128 §8's *"It reads no file"* still holds.
- 0128 §7 says it is *"the module's own"*. Here that is enforced by the tripwire refusing an import of it in source outside `packages/project/src`, not by moving the declaration. Moving it would be churn across 25 test files for no behaviour.

**`effect-ratchet.faces.json:327-338`.** The `why` on `readFileFace` and `replaceFileFace` names the board, and after this change the board no longer calls them.

- `unreferencedFaces` still passes, because `diskFiles` in `files.ts` references both, and *"A call in the declaring file counts"* (`effect-ratchet.test.ts:555`).
- Rewrite both `why`s to say what holds them now (the default `ProjectFiles` value).
- Do not touch the baseline.

## The tripwire: `packages/project/unit/recipe-file-boundary.test.ts`

**Scope:** every `.ts` and `.tsx` under `apps/*/src` and `packages/*/src`, except `packages/project/src`. Tests (`unit/`, `integration/`, `test/`) are not scanned: they provide `ProjectFiles` and seed ports, which is what §7 prescribes.

**Checker:** a pure function `(file, text) => string[]`, over the TypeScript AST as the ratchet does (`ts` parse). Working on the AST means comments, JSX text and message strings never match. It reports `file:line` for:

1. **An import of the port.** `diskFiles`, `filesEffect`, `ProjectFiles`, `readRecipeFile`, `replaceRecipeFile`, `readFileFace` or `replaceFileFace` from `@lingtai/project`; or `RecipeFiles` from `@lingtai/recipe`. Type-only imports count.
2. **A read or write of a recipe path.** A call whose callee is one of these:
   - `readFile`, `readFileSync`, `writeFile`, `writeFileSync`, `existsSync`, `stat`, `statSync`, `rename`, `access`;
   - any `.read(` or `.replace(` member call.

   It is reported when the call's **first argument** is one of these:
   - a `recipePath(…)` call;
   - a string literal or template containing `recipe.yml`;
   - a `join(…)` or `resolve(…)` with such an argument;
   - an identifier whose `const` initializer in the same file is one of the above. Follow one hop, no further (the ticket's Out of scope).

   Matching on the first argument is what keeps `String.prototype.replace(/re/, …)` legal.

**Self-tests:** check the checker against each pattern, and check that each of these passes:

- the four prose sites the ticket names (`pending.tsx:84`, `file-bar.tsx:7`, `doctor.ts:3494`, `init.ts:1203`);
- `packages/recipe/src/local.ts:39`'s `join(home, project, 'recipe.yml')`, which builds a path and reads nothing;
- `'x'.replace(/a/, 'b')`.

**Red on purpose:** make the test go red once on a scratch edit (a `readFileSync(recipePath('x'))` in some `apps/cli/src` file), revert the edit, and say in the header that this was done. That is the ticket's *What it costs later tickets* edge.

## Tests that lose a seam

`world.files`, `at.files`, `ports.files`, `target.files` and `deps.files` go away. So do the `files: diskFiles` defaults at `first-project.ts:1388`, `init.ts:1359` and `add-github.ts:175`. Their tests wrap the Effect under test in `Effect.provideService(ProjectFiles, port)` instead.

**Watch out:** a test that forgets the wrapper falls back to the real disk, and under `HOME=/nonexistent` it reads `null` and may pass while asserting nothing. Wherever a test used to hand in a seeded port, assert something that only the seeded text could produce. The sites that now record (`init.ts:453`, `:685`, `:842`, `add.ts:285`) need the test's memory store as `store`, or they reach `defaultStore()`.

**Required unit test:** on a memory port and a memory store, seed the recipe with `changeRecipe` (`by: 'human:t'`). Then:

1. `recipeText` reads it and appends nothing.
2. Edit the port's text and read again: exactly one `ProjectRecipeChanged { by: 'file' }`.
3. Read a third time, unchanged: nothing appended.
4. A missing file answers `null` with no append and no write; the port's `replace` is never called.

Everything here is checked by the unit half. Nothing in this change needs `pnpm test:integration`.
