## Design note

Put the exported, daemon-local queue and `onWaitStarted` in `apps/cli/src/triage.ts`. Keep a set of `(ticketId, waitId)` keys from enqueue until the worker settles, and a single promise tail for arrival order. Enqueue must add the key before scheduling work and return immediately; each worker catches and logs its failure, removes its key, and leaves the tail usable for the next wait. This matters because `waitTriage` can throw if its final `WaitTriaged` append still fails after retries (`apps/cli/src/triage.ts:459-495`). The handler’s returned promise must cover only recipe and stream reads plus enqueueing: `deliver` times out a handler without cancelling it (`packages/daemon/src/work-loop.ts:402-449`), while Discussion currently awaits its whole queue (`apps/cli/src/discuss.ts:469-483`).

Recheck that the same wait is current **when its queued worker starts**, as well as when handling `WaitStarted`. An earlier triage may take minutes, during which a person can resolve a later wait; `waitTriage` currently reads the stream and proceeds toward `TriageStarted` without checking `reduceTicket(...).lifecycle` (`apps/cli/src/triage.ts:182-220`; `packages/domain/src/ticket.ts:39-44`). Use `triageStatus` for the worker’s final eligibility check too; its comment calls it “A wait’s `TriageStatus`” and says it reads no recipe or clock itself (`packages/domain/src/wait.ts:632-655`). Capture the resolved `triage:` configuration per event, treating a missing or unreadable recipe as undeclared; the recipe explicitly says “Optional, with no default” (`packages/recipe/src/recipe.ts:3202-3212`). Do not introduce a reason-tag predicate.

Wire `triage` beside `discuss` in `createWorkLoop`, delivering `WaitStarted` before the existing trigger check and leaving its `pump('completion')` path intact (`packages/daemon/src/work-loop.ts:540-556`; `apps/cli/src/lingtai.ts:939-945`). Retain this daemon’s recorded start time for the handler: `startRecorder` currently returns no timestamp and `recordStart` returns `void`, while `startAfter` exposes the recorded event’s `at` (`apps/cli/src/restart.ts:1523-1545`; `packages/daemon/src/control.ts:245-269,270-305`). After a successful start append, read that event using the daemon’s existing control watermark and retain its `at`; use `null` if no start was recorded. This gives #447 the same context without substituting process wall time for a log fact. ADR 0118 §3 says triage runs “off the pass, without the lock” and that “a triage is keyed by its wait” (`doc/decisions/0118-a-hold-explains-itself.md:294-309,341-348`).
