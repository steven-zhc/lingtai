## Design: #890, the cold reviewer's summary

### The one decision the ticket leaves open: a summary is kept on both verdicts

`about` is set only on a refusal (`agent-action.ts:866-870`, *"the reviewer's own classification of its refusal, and only of a refusal"*). Do not copy that rule for `summary`. A review that **passes** is the main reason this field exists, because a landed change is one that passed.

- Carry `summary` on the readable return at `agent-action.ts:859-863`, whatever `verdictFor(kept)` says.
- Leave it off the `unreadable` return at `:842-847`. That answer was never read, so there is no summary to keep.

In `verdictResultOf` (`step-outcome.ts:125-153`), add it to the three arms that build a `Completed` assessment:

- `passed` (`:129-130`)
- the readable half of `failed` (`:136`)
- `needs-approval` (`:150`)

Spread it the way `head` and `about` are spread (`action.ts:860-878`), so that *no summary* reaches the log as a missing key and never as `summary: undefined`.

`AnswerUnreadable`, `Interrupted`, `NeverStarted` and `Waived` never carry one.

### Where it is read and bounded: `normaliseAnswer`, once

`ReadAnswer` gains `summary?: string`. In `normaliseAnswer` (`agent-action.ts:443-478`):

- **Not a string** → no summary. This is the same rule `about` follows at `:475-477`.
- **Empty after `.trim()`** → no summary.
- **Too long** → keep the **first** 4,000 characters, trimmed, followed by `…`.

Do **not** use `boundedEvidence` (`command.ts:224-228`). It keeps the *tail*, and appends a sentence of its own about clipping. For a summary the head is what matters, because the first sentence is the headline 0103 §3 asks for. Put the 4,000 in a named constant next to the function.

Because `parseFindings` hands its candidate JSON to `normaliseAnswer` (`:522`), the prose fallback gets the same rules without any extra code. An answer with a bad `summary` still has `parsed: true`. A summary must never change whether an answer counts as readable.

### The prompt

Add the summary request inside the existing `CONTRACT` string (`:211-234`), so it stays last (`:199-209`). If `CONTRACT` shows a JSON example, that example must include `"summary": "…"` beside `"about"`. A runtime with no schema (the `parseFindings` path) copies the example, so a key missing from it is a key the model leaves out.

Say there, in one line, that on a re-review the summary covers the whole diff and not the delta. The delta block (`:626-639`) sits just before `CONTRACT`, which is exactly what tempts a model to summarise only the delta.

### `reviewSummaryOf`

Put it in `packages/domain/src/action.ts`, beside `designOf` (`:368-374`), and copy its shape:

- If `outcome.step !== 'review'`, return `null`.
- Otherwise go through the actions and keep the **last** one with `yields === 'verdict'`, `result._tag === 'Completed'` and a string `assessment.summary`.

"Last wins" is the same rule `designOf` and `headOf` use. Give the return type as `{ summary: string; clipped?: boolean } | null` and leave `clipped` unset, so #892 can add it without changing the type.

Export it the same way `designOf` is exported from the package.

### Where it is lost if forgotten

The ticket names the two drop points: the spread list in `runPipeline` and `verdictResultOf`. One more is easy to miss:

- **The `results` element type** at `action.ts:657-690` lists its fields one by one. If `summary` is not added there, the spread in `runPipeline` does not compile.
- **`step-outcome.ts:24-28`'s header**, *"What is lost, named"*, lists `about` as dropped. `summary` is *not* dropped, so it must not be added to that list.

### Tests

All of these are unit tests; none needs `test:integration`.

- **The trip to the log:** use `outcomeOf` (`step-outcome.ts:327`) on a `PipelineResult` whose review result carries `summary`. Assert both `passed` and `failed` with findings. Then parse the result with the domain `StepOutcome` schema, to show the field survives being read back.
- **An old `StepEnded`:** an `Assessment` literal without `summary` parses, and `reviewSummaryOf` on it returns `null`.
- **Expect some existing tests to change once:** those that compare `REVIEW_ANSWER_JSON_SCHEMA` or the `CONTRACT` text exactly, and any `toEqual` on a review `ActionResult` built from a fixture answer that now includes `summary`.
