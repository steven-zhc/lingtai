## #378: the shape

### Most of the table is already done, and two rows have nothing to change

- **`discover.ts`, `tell.ts` and `ticket-store.ts` already take `Tickets`.** #377 did this.
  - `TicketSource = Pick<Tickets, 'listOpenIssues' | 'getIssue'>` (`discover.ts:74`)
  - `IssueChannel = Pick<Tickets, 'comment' | 'setLabels' | 'closeIssue' | 'updateBody'> & {getIssue…}` (`tell.ts:38`)
  - `githubTicketStore(client: Pick<Tickets, …>)` (`ticket-store.ts:130`)
  
  The first `Done when` grep already finds only comments. Check it again, but don't edit these files.
- **Leave `apps/cli/src/discuss.ts` and `apps/board/src/app/actions.ts` alone.** Neither has a parameter that carries a client:
  - `discuss.ts:191-192` builds one with `githubClientFor(state)` and calls `getIssue` on the next line.
  - `actions.ts` builds one at lines 78, 197, 236 and 425 with `createGitHubClient({`.
  
  The only edit possible in either is at the construction site, which belongs to #382/#383 (see the ticket's `Watch out`).

The real work is five types. Make them in this order, because each one feeds the next.

### 1. `conduct.ts`: one named intersection, and keep the field called `client`

`RunOnceOptions.client: GitHubClient` (`conduct.ts:325`) is used for ticket verbs, ref verbs and the repository's identity:

| Use | Line | Needs |
|---|---|---|
| `const tickets: TicketSource = options.client` | 1548 | `listOpenIssues`, `getIssue` |
| `tellGitHubAbout({ github: options.client })` | 994, 1599, 3257, 3439 | `IssueChannel & RefChannel` (`tell.ts:354`) |
| `armsOnOrigin(options.client, branch)` | 805 | `ArmChannel`, which is `matchingRefs` only (`arms.ts:31`) and so already inside `RefChannel` |
| `options.client.owner` / `.repo` | 559, 1664-1665, 1959-1960 | two strings |
| `currentRecipe(options.project, options.client)` | 545 | nothing (see §3) |

Declare it once in `conduct.ts`, export it, and use it for the field:

```ts
export type PassClient = Tickets & RefChannel & { readonly owner: string; readonly repo: string }
```

Use one intersected parameter rather than two. The ticket allows either, and the intersection is the one that keeps *callers keep passing the same `GitHubClient`* literally true. `packages/conductor/test/one-pass.ts`, `unit/conduct-before-the-claim.test.ts` and `apps/cli/src/run.ts` all hand in one `client:`. Splitting it in two would mean editing every one of them to pass the same value twice, for no gain until #383.

`Tickets` already satisfies `IssueChannel`; `unit/tickets.test.ts:32` pins that. So `PassClient` satisfies `tellGitHubAbout` without a cast.

Leave the comment at `conduct.ts:1544-1547` (*"swapping the source later is then a one-line change here"*) alone. It is still true.

### 2. `schedule.ts`: forward the pass's type

`ScheduleOptions.client` (`schedule.ts:49`) is used in two places:
- `runnableNow` at line 180, which needs only `TicketSource`
- `runOnce` at line 226, which needs `PassClient`

Type it `PassClient`. The narrower type would fail at line 226.

### 3. `filter.ts` and `projects.ts`: narrow what is carried, not what is built

- **`ProjectFilter.client`** (`filter.ts:174`) has two readers: `apps/board/src/lib/queued.ts:272` and `board.ts:523`. Both only do `runnableNow({ client: filter.client, … })`, so type the field `TicketSource`.
- **`ClientFor` (`filter.ts:179`) and `githubClientFor` (`filter.ts:202`) keep `GitHubClient`.** They are the construction site, and so is `clientsForProjects` in §4. Changing what a factory returns belongs to #382/#383. That is also why `filter.ts` keeps its `GitHubClient` import.
- **`RecipeFor`'s `client` parameter** (`filter.ts:191`) and **`currentRecipe`'s `_client?: GitHubClient`** (`projects.ts:156`) become `unknown`. The parameter is already dead; `projects.ts:140-141` says: *"`client` is unused and kept so every caller that conducts still passes through the one `RecipeFor` shape."* Change both together. `filter.ts:220` assigns `currentRecipe` as `RecipeFor`'s default, so if one is narrower than the other, `tsc` fails. `apps/cli/integration/status-preview.test.ts:126`'s `async () => resolved` is unaffected.
  - **Do not delete the parameter.** `base` is the third *positional* argument of `currentRecipe(state, _client, base, options)`. Removing `_client` shifts `base` into its slot at every call site that passes it. `tsc` would not necessarily notice, because `base?: string` and `options` are both optional, and it would quietly change which branch's recipe is read. That is behaviour, and this ticket is types only.

### 4. `packages/daemon/src/converge.ts`

`options.clients` (`converge.ts:160`) is used for:
- `getIssue` at line 277
- `matchingRefs` at line 340
- `setLabels`, `deleteRef` and `closeIssue` at lines 391-398

Type it `ReadonlyMap<string, Pick<Tickets, 'getIssue' | 'setLabels' | 'closeIssue'> & RefChannel>`. Import `Tickets` and `RefChannel` from `@lingtai/conductor`. Add them to its `index.ts` exports if they are missing; that file already re-exports `RecipeFor` at line 37.

`clientsForProjects` keeps `Map<string, GitHubClient>` (lines 94-95). It calls `createGitHubClient(` at line 100, so it is a construction site. A `Map<string, GitHubClient>` is assignable to the narrowed `ReadonlyMap`.

The daemon tests that build `clients` as `… as GitHubClient` (`unit/converge-refs.test.ts`, `integration/converge.test.ts`) still compile, because a `GitHubClient` is a subtype of the narrowed value. Leave them as they are.

### What checks it

None of this changes what runs, so no event or field in `events` moves, and there is nothing in the log to settle.

**`pnpm typecheck` is the whole check.** `pnpm test` cannot catch any of it: vitest's run mode does not typecheck (`unit/tickets.test.ts:5-8`: *"a broken pin stays green here. What catches it is `pnpm typecheck`"*).

To make *callers keep passing the same `GitHubClient`* a claim that is checked rather than one that is argued, add one assignment pin next to the existing two in `packages/conductor/unit/tickets.test.ts`, in the same style:

```ts
const _gitHubSatisfiesPassClient: PassClient = {} as GitHubClient
```
