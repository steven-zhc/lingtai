## Design: `task_view` carries the current wait (#440)

The ticket gets the shape right. This note settles three things it leaves open.

### 1. The columns follow `waiting`. `TaskCard.wait` follows `state`.

The ticket asks for two things that the fold does not keep in step:

- Clear the columns "wherever `waiting` is cleared".
- Make `wait` "non-null exactly when `state` is `'waiting'`".

These differ because some events change `state` without touching `waiting`:

- `TicketDiscovered` calls `upsert` with `attempt` unset. Its on-conflict branch writes `state = excluded.state` (`'queued'`) and keeps `waiting = task_view.waiting` when `$10 = 0` (`packages/projector/src/task-view.ts:250-258`, `:747`, `:761`).
- `RunStarted` writes `state: 'running'` through `viaRun` and leaves `waiting` alone (`:406-414`).
- `RunProposedCompletion` writes `state: 'verifying'` the same way (`:457-460`).

So a row can have `waiting = true` while `state` is something other than `'waiting'`. Do both, each in its own layer:

- **The fold** writes `wait_id` and `wait_reason` at exactly the sites the ticket lists, with the same rule as `waiting`. So `wait_reason is not null` holds exactly when `waiting` is true.
- **`toCard`** returns `wait` only when `state === 'waiting'`, and `null` for every other state, whatever the columns hold.
- **The refusal** is keyed on `state === 'waiting' && wait_reason === null`. That is the one combination the fold can never write. `state = 'waiting'` is only written in the `WaitStarted` case (`:579`, `:585`), in the same `set` that will write `wait_reason`. Every site that moves a row off `'waiting'` gives it a different `state`. A refusal keyed on `waiting` alone would be no stronger, and would read wrongly next to a contract stated on `state`.

Do not change the `TicketDiscovered`, `RunStarted` or `RunProposedCompletion` cases to clear the wait. Whether a waiting row actually gets those events is a question for the log: look for a `TicketDiscovered` or `RunStarted` whose stream's last `WaitStarted` has no `WaitResolved` with the same `waitId`. That is not this ticket.

### 2. The claim upsert has a second caller

`upsert` (`:714-770`) serves `TicketClaimed` with `attempt: true`, and also `TicketDiscovered`, `WaitStarted` and `DispatchRefused` with `$10 = 0`. Write the two new columns exactly like `waiting` at `:761`:

`wait_id = case when $10::int > 0 then null else task_view.wait_id end`, and the same for `wait_reason`.

Leave them out of the `insert … values` list. They default to null on a new row, and `WaitStarted`'s `set` fills them right after its own upsert (`:574-591`).

`DispatchRefused` has its own SQL at `:381-386`. Add both columns there with the `case when task_view.waiting then task_view.<col> else null end` form its siblings use.

### 3. One function maps the columns to `wait`, and both twins call it

The twins differ in what they get back:

- Postgres hands back a parsed object for a `jsonb` column (`postgres.ts:107-109`).
- SQLite hands back text, which goes through `parseJson` (`sqlite.ts:298`).

Put the mapping in one exported function next to `TaskCard` in `task-view.ts`, for example `waitOf(taskId, state, waitId, reason: unknown)`. Each twin passes in its own already-parsed value. The function:

- returns `null` unless `state === 'waiting'`;
- throws an error naming the task id when the reason is null;
- otherwise returns `{ waitId: WaitId.parse(waitId), reason: WaitReason.parse(reason) }`.

`WaitId` is `z.string().brand<'WaitId'>()` (`packages/domain/src/action.ts:26`), and `WaitReason` is the zod union at `packages/domain/src/wait.ts:187-201`.

If `WaitReason.parse` fails, also rethrow with the task id. A stored reason that no longer parses is the same kind of fault as a missing one. Keeping all of this in one function means the twins cannot disagree about the refusal, and one test covers both.

Write the reason the same way `diagnosis` is written: `wait_reason: JSON.stringify(fact.reason)` in the `WaitStarted` `set` (`:590`). `set` passes values through as parameters (`:788-801`), and both stores accept text into that column. The round trip is lossless: neither `wait.ts` nor `action.ts` uses `transform`, `preprocess` or `coerce`. Only `pass-next.ts` and `routing.ts` do. So `RunRef.unpushed` comes back as it was appended, and the `toCard` test should assert this with `toEqual` on a reason that has `unpushed` set.

### Smaller decisions

- **`wait` is a required field on `TaskCard`, not optional.** Then `tsc` points at every place that builds a card literal. Those are the two twins plus the board's test fixtures (`apps/board/unit/*.test.ts`, which `git grep -l "repairPending:" apps` lists). Non-waiting fixtures get `wait: null`. A fixture with `state: 'waiting'` gets a real `{ waitId, reason }`.
  - `apps/board/src/lib/queued.ts`, `apps/cli/src/status.ts` and `packages/conductor/src/queue.ts` also match that grep, but they only pass `{ lastAttemptAt, repairPending }` to `heldUntil`. They do not build cards.
- **The snapshot.** `task-view-rebuild.test.ts` snapshots `select * from task_view` (`packages/projector/unit/task-view-rebuild.test.ts:489`, `:500`). Vitest sorts object keys, so where the columns sit in the `create table` does not matter. Run `vitest -u` on that one file, then check that `git diff` on `__snapshots__/task-view-rebuild.test.ts.snap` adds only `wait_id` and `wait_reason` lines. That check is the real gate, because the file's own header says regenerating it turns the pin into a tautology (`:6-10`).
- **The new fold cases go in a new unit file** on the same `:memory:` SQLite store, built from the fixtures that file imports (`aClaim`, `aRelease`, `aResolution`, `aRunRef`, …). The rebuild test is a pin, not the place for new behaviour. Build the stream at module scope, for the reason given at `:18-21`.
- **No Postgres-only check is needed.** The DDL is shared (`sqlite.ts:105`, `:209` turn `jsonb` into `text`), and the Postgres twin differs only in not calling `parseJson`. The unit-level stand-in for the Postgres path is a direct test of `waitOf` given an already-parsed object, which is what Postgres hands back.
