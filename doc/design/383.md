# #383: one helper builds a project's client, and the sites stop building their own

## The shape

Ten construction sites build the same pair: a GitHub client, then the recipe. Put that pair behind **one function in `packages/conductor/src/filter.ts`**, next to `githubClientFor` (`filter.ts:214`). Every site in the ticket calls it. Don't put `ticketsFor` + `passClientOf` inline ten times.

```ts
export async function projectClient(
  state: ProjectState,
  options: { clientFor?: ClientFor; recipeFor?: RecipeFor; tickets?: TicketsForOptions } = {},
): Promise<{ client: TicketedClient; resolved: ResolvedRecipe }>
```

- It runs `clientFor(state)`, then `recipeFor(state, client)`, then `ticketsFor(state, resolved.recipe, client, options.tickets)`, and returns `passClientOf(client, tickets)`.
- That is the same sequence `projectFilter` runs at `filter.ts:235-238`, which is what the ticket's **Watch out** row asks for.
- It goes in `filter.ts` and not `ticket-store.ts` because `filter.ts` already imports `ticket-store.ts` (`filter.ts:37`). Putting `githubClientFor` in the other file would create an import cycle.
- `discuss.ts` already imports `@lingtai/conductor/filter` (`discuss.ts:54`). The board's `lib/board.ts` already reaches `projectFilter`. So no new package edge is needed.
- `currentRecipe` is a local file read and ignores the client (`projects.ts:153-165`, `_client?: unknown`). Loading the recipe at sites that don't load it today (`close`, `approve`, both `discuss` sites) costs no request.
- `options.tickets` exists for one reason: the unit tests below can hand `ticketsFor` a `:memory:` SQLite and a `memoryStore()` log. Without it, `ticketsFor` falls back to `processTicketSql()` (`ticket-store.ts:212-218`), and `HOME=/nonexistent pnpm test` can't reach that.

## The non-obvious decision: change `passClientOf`'s return type, not each callee

Today `passClientOf` returns `Tickets & RefChannel & { owner, repo }` (`ticket-store.ts:283`). Its comment explains why it can't return `GitHubClient`: *"`dbTickets` answers a label's `color` and the array it carries both as read-only … the two cannot both be true of one return type"* (`ticket-store.ts:273-281`).

The spread at `:286` already carries every other `GitHubClient` member at runtime, but the type drops them. The sites in this ticket need those members:

| Site | Needs |
|---|---|
| `apps/cli/src/approve.ts:54` | `defaultBranch()` |
| `apps/cli/src/approve.ts:60` | `token()` |
| `apps/board/src/app/actions.ts:87, :97` | `defaultBranch()`, `token()` |
| `approve()` in `packages/conductor/src/approve.ts:238` | `refSha` |

`refSha` is in neither `Tickets` nor `RefChannel` (`tell.ts:58-68`).

So export `type TicketedClient = Omit<GitHubClient, keyof Tickets> & Tickets` from `ticket-store.ts`, and make it `passClientOf`'s return type. The existing callers still type-check, because they assign the result to the narrower `PassClient`:

- `run.ts:255-260`
- `cli/conduct.ts:142`
- `converge.ts:130`

With that one type in place, each site keeps a single `client` and calls `token()` and `defaultBranch()` on it as it does today. Nobody has to carry a raw GitHub client beside a ticket client, and nobody gets the two confused.

Then **narrow the two conductor functions that take `GitHubClient` to what they actually use**:

- **`close()`, `close.ts:91`**: `client?: GitHubClient` becomes `client?: IssueChannel & RefChannel`. Its only use is `tellGitHubAbout({ github: options.client })` (`close.ts:158-165`). The truthiness check at `:119` stays as it is.
- **`ApproveOptions.client`, `approve.ts:117`**: becomes `PassClient & Pick<GitHubClient, 'refSha'>`. Its uses are `refSha` (`:238`), `owner`/`repo` (`:322-323`) and `tellGitHubAbout` (`:391`, `:414`).

`unit/close.test.ts:178` passes a `fakeGitHub`. It still fits.

## Site by site

- **`apps/cli/src/backlog.ts:195-207`** and **`apps/board/src/app/actions.ts:236-252`**
  - Use `githubTicketStore(client)` over the `TicketedClient`.
  - `githubTicketStore` only needs `createIssue`, `listIssuesSince`, `comment` and `closeIssue` (`ticket-store.ts:141`). On a `db` project those are `dbTickets`', so the key marker and the race-and-withdraw logic work unchanged.
  - Leave the store's `source: 'github-issue'` string alone. Nothing in `backlog.ts` reads `.source`.
  - `kindsOf(resolved.recipe)` replaces the second `currentRecipe` call.
- **`apps/cli/src/end.ts:63-90`**
  - Type the map as `Map<string, TicketedClient>`.
  - Build each entry with `projectClient(project)` inside the existing `try`, and reuse the `resolved` it returns instead of calling `currentRecipe` again at `:82`.
  - A `TicketSourceConflict` then comes out as `not replayed — …` for that project only, which is what the comment at `:95-96` asks for.
- **`apps/cli/src/close.ts:57`** and **`actions.ts:197`**
  - Pass `client` together with `recipe: async () => resolved`.
  - `close()` otherwise reads the recipe again itself (`close.ts:122`). Passing `recipe` guarantees that the recipe that chose the ticket source is the one whose `end` runs.
- **`apps/cli/src/approve.ts:38`** and **`actions.ts:78`**
  - Same as close, with `recipe: async () => resolved`.
  - Only the ticket verbs move. `integrate` still takes the token and `owner`/`repo`, the refs still go to GitHub, and so does the merge. That holds by construction, because `passClientOf` replaces only the eight `Tickets` verbs.
- **`apps/cli/src/discuss.ts:191-192`**
  - Use `(await projectClient(state)).client.getIssue(...)`.
  - A refusal lands in `ticketProblem`, as an unreachable App does today.
- **`actions.ts:425-431`**
  - Same as `discuss.ts`. `ticket = { github: client, body }` stays as it is, because `IssueChannel` is a subset of `TicketedClient`.

Leave the `hasGitHubApp()` early returns and their messages where they are.

- `githubClientFor` would throw the same fact, but in different words.
- The ticket says to keep building the client, so a `db` project on a machine with no App is still refused by these commands. That gap is real (`ticket.ts:12-16` routes around it for its own reason), and it is not this ticket.

## Tests: at the conductor seam, and why there

The commands themselves call `loadProject` (the log) and `hasGitHubApp()` (the config). Under `HOME=/nonexistent` both end the command before it reaches a ticket. The board actions are a `"use server"` module that calls `revalidatePath`. So the claim *a `db` project's ticket goes to `dbTickets`* is tested where the ticket call is made. The site wiring is held by `pnpm typecheck` and by the Done-when grep.

Fixtures: SQLite via `createSqliteTicketSql(openSqliteLog(':memory:'))`, a `memoryStore()` log and `fakeGitHub` from `test/one-pass.ts`, the same set `unit/ticket-store.test.ts:11-26` uses. Wrap the fake so its eight ticket verbs record into an array of their own, the way `doc/design/382.md` did. Use a recipe whose source is `db` and whose `end` carries a `close: true` action. `DB_YAML` in `apps/cli/unit/ticket.test.ts` is the model.

- **`projectClient`**, in `packages/conductor/unit/`:
  - For `github`, `client` is the fake itself (`toBe`).
  - For `db`, `getIssue` answers from `dbTickets`, while `token()`, `defaultBranch()` and `refSha` still answer from the fake.
- **backlog**:
  - Run `acceptFinding({ tickets: githubTicketStore(client) })`, injecting `entry` and `events` the way `unit/backlog.test.ts:140` does.
  - Expect the issue to appear in `dbTickets` carrying `keyMarker(key)`.
  - Expect the GitHub ticket-verb record to be empty.
- **close / approve / end**:
  - Run `close({ state, client, recipe, store })` against that recipe.
  - Expect the `dbTickets` ticket to be closed with its labels set.
  - Expect the GitHub ticket-verb record to be empty.
  - This also covers `end.ts` and `approve`, since all three write through `tellGitHubAbout`.
  - A full `approve()` needs `git`, which makes it integration, and an agent can't run that before the merge. The unit-level claim that stands in for it is the type: `approve()`'s ticket writes go through the same `tellGitHubAbout` call that `close` exercises.
- **board**:
  - Run `concludeDiscussion({ outcome: 'ticket', ticket: { github: client, body } })`.
  - Expect the new body in `dbTickets.getIssue(n).body`.
  - Expect the GitHub ticket-verb record to be empty.

## The PR body must say

The board's Next server, like the daemon, holds the code it started with. A merge reaches `actions.ts` only when the board restarts. The CLI commands pick it up on their next invocation.

On a `db` project, two things settle that the change took effect:

- A `TicketCommented` / `EndActionsResolved` carried out after the merge leaves the GitHub repository without an issue numbered as that work item.
- A `wi-<project>-<n>` stream whose `n` matches a `dbTickets` row is the one these commands touched.

No ADR is contradicted. This finishes what 0036 §2's single ticket port and #382 started.
