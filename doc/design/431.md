# Design: #431, one `askRecipe` behind `init`'s local branch and `add`'s GitHub path

## Where it goes

- **New file `apps/cli/src/recipe-flow.ts`.** It exports `askRecipe(world: QuestionWorld, at: RecipeAt): Promise<{ ok: true } | { refused: string }>`. `RecipeAt` carries:
  - `project` and `local: boolean`;
  - `runtimes: readonly RuntimeFound[]`, already probed. `AskAgentsAt` says *"this function never probes on its own"* (`agents.ts:108`), and `askRecipe` keeps that rule.
  - `reader: SetupReader`;
  - `flags: Readonly<Record<string, string>>`;
  - `defaultBranch: () => Promise<string | null>`;
  - `history`, `kept`, `home?`, `files?`.
- **Inside it, in this order:** `askAgents` → `askInstallAndBuild({ tryBuild: null, given: { check: null, … } })` → `askTickets` → `askKinds` → `askLanding` → `askLimits`.
  - Each `{ changes }` is written with `setRecipe(project, changes, { home, files })` straight after its answer. That is the `setRecipeOrRefuse` shape in `landing.ts:63-73`, and a throw becomes `{ refused }`.
  - `askAgents` returns two lists. Write `changes` and then `modelChanges`, as `add-github.ts:218-219` does today.
  - `askLanding` and `askLimits` already write for themselves (`landing.ts:171`, `:231`).
- **`--install` is read from the `flags` the callers already pass:** `install ?? null`. **`--build` is repeatable** (#431 fix round, finding 3): both parsers (`lingtai.ts`'s `parseFlags`, `init.ts`'s `parseArgs`) grew a `repeated` map alongside the last-wins `flags`, and `recipe-flow.ts` reads `at.buildFlags` — every `--build <cmd>` on the line, in order — rather than `[flags['build']]`. `askBuild` already understands `none` (`setup-build.ts:264-268`).
- **`ADD_KEPT` moves to `recipe-flow.ts`** (it is at `add-github.ts:58` today). `askRecipe` hands it to `askTickets` and `askKinds` as `kept`, because by then something has been written on both paths. `lingtai.ts:50` imports it from the new place.

## The decision the ticket does not make: a seeds-only file does not resolve

The ticket says the local branch *"keeps today's first write of its seeds (`repo.base`, `repo.remote`, `env.plantAt`), then calls `askRecipe` on the file that now exists."* Taken literally, that write is refused:

- `setRecipe` runs `resolveSource` before it writes anything (`write.ts:185`).
- `source.kinds` is `KINDS = z.array(z.string()).min(1)` with no default (`recipe.ts:989`, `:1071`).
- Today this works only because the kinds answer goes in the same write (`first-project.ts:417-431`). The comment there says so: *"`source.kinds` has no schema default either, but `askKinds` above already writes it unconditionally for a brand-new file."*

**So on an absent file, the first write also seeds `source.kinds: [...SETUP_KINDS]`** (`answers.ts:127`), under the same `existingText === null` condition that guards `env.plantAt` today. Then:

- `askKinds` later reads that seed as `current` instead of `fallback`. The default the person sees is the same text, Enter writes nothing (`source.ts:196-198`), and a different answer replaces it.
- `runtime.agent` needs no seed. The schema defaults it (`recipe.ts:3108`), and `askAgents` writes it explicitly before anything resolves the file with a signed-in check (`agents.ts`, `{ path: ['runtime', 'agent'] }`).
- `source.tickets` needs no seed either. `askTickets(local = true)` writes `db`, and the existing test at `first-project.test.ts:349` keeps holding that.
- On a file that already exists, the first write is only `repo.base` and `repo.remote`, as today.

What follows from this: if the run is stopped inside `askRecipe`, the file keeps kinds nobody answered. That is the accepted *"a Ctrl+C keeps what was answered"* policy (doc/design/399.md:82). The refusal's `kept` clause has to say the recipe was written, which is why `ADD_KEPT` rather than `world.kept` is the clause after the seed write.

## The local branch (`runLocalBranch`, `first-project.ts:292-462`)

1. **Probe runtimes once, before the seed write.** Add `runtimes: () => Promise<readonly RuntimeFound[]>` to `FirstProjectWorld`.
   - `liveFirstProjectWorld` uses `askRuntimes`.
   - `init.ts:422` passes the result `init` already probed at `init.ts:300`, as `async () => runtimes`, so nothing is probed twice.
   - If nothing is signed in, refuse before writing. Extract the refusal text at `agents.ts:134-140` into an exported function, and have both `askAgents` and this check use it.
   - This keeps the claim of *"no agent signed in is refused by name, before anything is written"* (`first-project.test.ts:277`) true unchanged.
2. **Delete the `resolveAgent` pre-check** (`first-project.ts:384-395`) together with its imports (`AgentUnresolvedError`, `resolveAgent`, `writtenAgent`). Step 1 covers *none signed in*, and `askAgents` answers *two signed in*.
3. **Seed write** (see above), then `askRecipe(world, { local: true, reader: world.setupReader(toplevel), defaultBranch: async () => detected, kept: ADD_KEPT, … })`.
   - Add `setupReader: (dir: string) => SetupReader` to `FirstProjectWorld`.
   - The live one is `node:fs` over `dir`: `has` is `existsSync`, and `read` returns null on ENOENT.
   - The unit harness gives a Map stub.
4. **The final base.** After `askRecipe` returns, read the file back through `world.files.read` and compute `baseOf(resolveSource(text, path, path).recipe)` (`settings.ts:228`, exported from `@lingtai/recipe`).
   - Use `baseOf` and not `repo.base`: `landingChanges` writes `steps.admit[…].worktree.base` instead of `repo.base` when a worktree entry exists (`answers.ts:75-88`).
   - If the final base differs from `baseAnswer.answer`, run `git rev-parse --verify <final>^{commit}` in `toplevel` for `fromSha`. If that fails, refuse with `<final> is not a branch in <toplevel> — … ${ADD_KEPT}`.
5. **Register last.** Call `resolveLocalRecipe(name, { …, base: final })` after that last read, and pass `configHash`, `resolved` and `base: final` to `world.register`. The `FirstProjectOutcome` returns `base: final` too.

**What the log settles:** the `ProjectConfigured` that `addLocal` appends carries `base`, `configHash` and `fromSha`. A stale hash would show as that `configHash` disagreeing with the next `RunStarted`'s `configHash` for the same project with no edit in between. You cannot read production `events`. The unit stand-in is to assert the `register` payload against `resolveLocalRecipe` run over `files.replaced[path]` after the call.

## `askBeforeGithubAdd` (`add-github.ts:83-279`)

- **Unchanged:** the `--land`/`--base` refusal, the #402 installation check and its order, the absent-file branch (refuse agent flags, ask nothing, return null), the preset-pins line, and the deletes of `flags['tickets']` and `flags['kinds']`. The deletes stay in this caller, after `askRecipe` returns, for the reason given at `add-github.ts:232-235`.
- **Replaced:** everything from `askRuntimes()` (`:210`) through `askLimits` (`:275`) becomes one `askRecipe` call with `local: false` and `history: liveHistory`.
- **Share one `defaultBranchOf` promise between the reader's ref and landing's `detected`.** Memoize it, so GitHub is asked once.
- **The reader is new, and nothing provides one yet.** No live `SetupReader` exists anywhere (only `unit/detect-setup.test.ts` and `unit/setup-build.test.ts` build one). Add a dep, `reader: (owner, repo, installation, ref) => SetupReader`. The live one is a `createGitHubClient` over `installation`:
  - `read` is `client.fileAt(path, ref)`.
  - `has` is `client.request('GET', \`/repos/${owner}/${repo}/contents/${path}?ref=…\`)` answering true, and a `GitHubError` with status 404 answering false.
  - **Do not build `has` on `fileAt`.** `fileAt` returns null when `content` is empty (`client.ts:415`). The contents API leaves `content` empty for files between 1 and 100 MB, so a large `pnpm-lock.yaml` would read as absent. This is the trap `detect-setup.ts:15-20` names.
  - `ref` is `--base`, else the default branch.
  - With no App (`installation === undefined`), no ref, or any throw, use an empty reader (`has → false`, `read → null`). Detection then suggests nothing, and the questions are still asked.
- **Replace the `read` and `write` deps with `files: RecipeFiles`** (live: `diskFiles`), and pass it into `askRecipe`.
  - `write` would otherwise be dead: `askLanding` and `askLimits` already bypass it and write through `setRecipe`.
  - The counters in `unit/add-github.test.ts` move onto that stub's `read` and `replace`. Every test there has `read → null`, so the *zero writes, zero asks* claims stay as they are.

## Tests

- **The scripts grow on every local test.** The new prompts, in order:
  - writer, model, reviewer;
  - install, which needs a typed answer such as `none`: with no detection and no current value, Enter gives `''` and `setup-build.ts:197` refuses it;
  - build, which takes Enter to finish;
  - kinds, landing, rounds, wall, budget.
  - `askTickets` never prompts for a local project.
- **The harness** gains `runtimes` (derived from its `signedIn` option, so the two cannot disagree) and `setupReader`.
- **The two new tests from Done-when:**
  - Order and hash: assert `asked` against the prompt strings in the order above, then that `registered[0].configHash` equals `resolveLocalRecipe(…).configHash` run over the final `files.replaced[path]`.
  - Moved base: plan `rev-parse --verify develop^{commit}` in `fakeGit`, answer the land question `develop` after a `main` base, and assert `registered[0]` has `base: 'develop'` and develop's sha. Add a twin where that git call fails, and assert a refusal naming the branch with nothing registered.
- **`unit/setup-build.test.ts`** should need no change, since `askInstallAndBuild`'s signature does not move. Touch it only if typecheck says otherwise.
- **`integration/init.test.ts`** builds a `FirstProjectWorld` through `InitWorld`. `pnpm typecheck` covers the new field. Its `--local` tests now drive `askRecipe`'s own questions too (`RECIPE_FLOW_FLAGS`, answered by flag — the suite's own `ask` only scripts the project, App, database and kinds questions), and the harness gained a `setupReader`; they only run after the merge (803s). The unit tests above are the claims that stand in for them.

**Nothing here spends money (#391):** `tryBuild` is `null`, `askRuntimes` only probes, and no agent is dispatched.
