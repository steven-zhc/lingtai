## Design: #776, the release notes list the tickets landed since the last release

### Where it goes

| Piece | File |
|---|---|
| The landing subject | new `packages/repo/src/landing-subject.ts`, which imports nothing. Exported as `"./landing-subject"` in `packages/repo/package.json`, beside `"."`. Other packages already have subpath exports of this kind: `@lingtai/env/colour` and `/lock` (`packages/env/package.json:8-9`), and `@lingtai/daemon/currency` (`packages/daemon/package.json:12`). |
| The caller | `packages/repo/src/integrate.ts:577` imports it by relative path. The comment at `:569-575` stays above the call. |
| The section | new `apps/release/src/tickets-changed.ts`. Pure functions first, then `if (import.meta.main)` at the bottom, as `apps/cli/src/cli-diff.ts:119` does it. |
| Tests | new `apps/release/unit/tickets-changed.test.ts`. `apps/release/tsconfig.json` already includes `unit`, and `vitest.config.ts:72` already globs it. |
| Workflow | `.github/workflows/release.yml`, the publish job only. |

### Decisions the ticket leaves open

**1. Leave `integrate.test.ts:105` as a literal string.** It reads `` expect(merge!.args[mIndex + 1]).toBe(`Merge branch '${BRANCH}' into HEAD`) ``. Do not rewrite it to call `landingSubject`. As written, it is the test that proves "byte-for-byte unchanged" (Done when, item 5). A version that calls the function compares the function with itself and proves nothing.

**2. The lockfile is part of the diff.** Adding `"@lingtai/repo": "workspace:*"` to `apps/release`'s `devDependencies` changes `pnpm-lock.yaml`, so run `pnpm install` and commit the lockfile with the change.
- If the lockfile is left out, the publish job's `pnpm install --frozen-lockfile` (`release.yml:119`) fails at the next tag, and so does `check.yml:39`.
- `pnpm typecheck` and `pnpm test` in the worktree pass either way, because the symlink is already in place locally. The build step will not catch this one.

**3. Git runs in the shell, and the script reads a file.** The script does not spawn git. The step writes the log to a file, and the script takes file paths as arguments, the way `cli-diff.ts` does.
- A failing `git log` then fails the step under `-e`, before the script runs.
- With no previous release, the step skips `git log` altogether. An empty `$PREV` would otherwise make the range `..<tag>`, which is a different range and not an error.

Suggested shape:

```
if [ -n "$PREV" ]; then git log --first-parent --merges --format=%s "$PREV..${{ github.ref_name }}" > landings.txt; fi
node apps/release/src/tickets-changed.ts "${{ github.repository }}" "${{ github.ref_name }}" ${PREV:+landings.txt "$PREV"} > tickets-changed.md
```

The script treats a missing third argument as "no earlier release". The step's `env` takes `GH_TOKEN: ${{ github.token }}` and `PREV: ${{ steps.prev.outputs.tag }}`, as the events step does (`release.yml:170-172`).

**4. Only 404 is "not found".** The ticket permits 404 alone to continue; every other status, `410 Gone` included, fails the step.
- A *transferred* issue answers 301. Leave `fetch`'s default `redirect: 'follow'` on, so a transfer becomes a 200 with the issue's new title.
- A unit test stubs a 410 and expects the throw.

**5. The issue reader's signature.** `readIssue(fetch, repo, token, n)` returns either `{ found: true, title, labels: string[] }` or `{ found: false }`, and throws on any other status. The thrown error names the status code and the issue number.
- Send the headers `Authorization: Bearer <token>`, `Accept: application/vnd.github+json` and `X-GitHub-Api-Version: 2022-11-28`.
- Label names come from `labels[].name`. In this API, `labels` is a list of objects, not strings.
- If `GH_TOKEN` is missing, fail before the first request. Do not send an anonymous request: its rate limit is a 403 at around 60 calls, which comes back as an error that does not point at the missing token.

**6. Order of `release-notes.md`.** `cat tickets-changed.md cli-changed.md events-changed.md > release-notes.md`. The tickets go first because they are the headline, and the `Full diff:` line closes that section.
- `renderTickets` ends its output with a newline, so the next section's `##` starts on a fresh line. The same applies to the other two files.

**7. `renderTickets` takes data, not responses.** Its input is `{ repo, tag, prev: string | undefined, tickets: Array<{ n, found: false } | { n, found: true, title, labels }> }`, in landing order. Inside a group, tickets keep that order. Keep the kind order in one exported constant (`bug`, `tech-debt`, `feature`, `documentation`), so a reader can see it in one place.

**8. Permissions.** The publish job's block (`release.yml:108-109`) becomes `contents: write` and `issues: read`. Nothing else is added.

### What nothing can check before the merge

The workflow runs only when a `v*` tag is pushed, and none of `pnpm test`, `typecheck`, `lint` or `fmt:check` runs YAML. Before the merge, the only witnesses are:
- the unit tests: parser, renderer, reader with a stubbed `fetch`, and the fixture built from `landingSubject('agent/771')`;
- reading the diff of `release.yml`.

To try it locally (optional), run `git log --first-parent --merges --format=%s v0.10.0..main > /tmp/l.txt` and then the script with a real token. It should list about 39 tickets. That is a manual check, not a gate, and nothing should wait on it.
