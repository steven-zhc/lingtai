# Design note: #512, the four integration files

None of the four is a code bug. Each test asserts something that a deliberate commit on `main` has since changed, and the code is right each time. So all four fixes go in the test files, and no file under `src/` changes. Make one commit per file. Each commit body should name the commit that moved the behaviour and say "the test was stale, not the code". Prove each fix by running that file alone with `pnpm vitest run --project integration <file>`. The unit half covers none of these four files, so `pnpm test` cannot stand in for those runs.

## 1. `packages/env/integration/board-port.test.ts:137`: a semicolon

The test looks for the literal `'export const RESERVED_PORT = 17821;'`. The source line is now `export const RESERVED_PORT = 17821` (`packages/env/src/index.ts:753`), with no semicolon. The oxfmt sweep `b56044f3` (*"style: the TypeScript is oxfmt's output and nothing else changed"*, the only entry in `.git-blame-ignore-revs`) removed it. The needle is inside a string, so the formatter could not update it.

- **Fix:** remove the `;` from the needle.
- **Don't** loosen it into a regex for `RESERVED_PORT`. The comment above it says the check is there so the scan cannot pass while seeing nothing: *"Or the scan found nothing and the assertion below is vacuous: this file's own package is in it, and so is the declaration."* The needle needs to keep matching the declaration exactly as written.

## 2. `apps/board/integration/recipe.test.tsx:216`: the preset's check moved

`b21b89ea` (*"fix(recipe): the pnpm-workspace preset declares its check at build, not proposed"*) moved `pnpm-workspace`'s check from `proposed` to `build`. See `packages/recipe/src/presets.ts:66-71`: *"The check is at `build:`, where a red one buys a fix round … a preset declares nothing there."* The page now renders `… prepared 1 · design 0 · implement 0 · build 1 · review 0 · proposed 0 · merge 0 · end 0`.

- **Fix:** update the expected string to that line.
- The unit twin already says the same thing in its own comma-separated form, at `packages/recipe/unit/local.test.ts:146`: `'claim 0, admit 0, prepared 1, … build 1, review 0, proposed 0, …'`. Use it as the cross-check.
- **Leave line 134 alone.** That test's own `RECIPE` declares `steps.proposed` itself (lines 62-64), so `proposed 1` is still correct there.

## 3. `apps/cli/integration/init.test.ts:164`: `#433` added a question the fake terminal doesn't recognise

`2e30f34a` (*"feat(433): --defaults accepts every recipe default in one answer"*) made `askRecipe`'s first question `use every default?`, with choices yes/no and fallback `yes` (`apps/cli/src/recipe-flow.ts:146-153`). The test's `ask` handler (lines 147-167) recognises the project, App and kinds questions. It treats every other question as the database question and asserts `/Postgres/` against it, and that assertion is what fails.

- **Fix:** add a branch beside the kinds branch: `if (/use every default/.test(question)) return ''`.
- **Why `''`:** an empty answer takes the fallback `yes`. `askRecipe` then wraps the world in `acceptingDefaults` (`apps/cli/src/question.ts:89-98`), so every later recipe question (agents, install/build, tickets, kinds, landing, limits; `recipe-flow.ts:178-281`) takes its default without reaching the test's `ask`. That matches the handler's own stance: *"answered with its own default … since nothing here is about which labels are work."*
- **Why not `'no'`:** it would send the agent, build, tickets and landing questions to the test's `ask`, and they would trip the `/Postgres/` assertion one by one.
- The store question is init's own (`apps/cli/src/init.ts:809`), asked through the unwrapped world, so the Ctrl+C matrix still sees it. Keep the kinds branch; it costs nothing.
- **Don't** record this question in `seen.asked`. The existing comment says the matrix is *"about the database question alone"*.
- The ticket reports three failing tests. If more than three fail after this, or a different assertion fails, stop. That is a different cause and outside this ticket.

## 4. `apps/cli/integration/telegram.test.ts:179-182`: the ticket misreads where the recipe comes from

This test does not read `~/.lingtai`. Lines 49-50 resolve the recipe with `resolveRecipe(async (path) => readFile(join(ROOT, path), 'utf8'), 'HEAD')`. `RECIPE_PATH` is `'.lingtai/config.yaml'` (`packages/recipe/src/resolve.ts:29`) and `ROOT` is this checkout (line 39). So the test reads the repository's checked-in copy, which is a fixture under version control. The file header says that copy is the test's subject: *"the `telegram` line this repository's recipe declares"*.

What changed is that copy. `9b265938`, one of #502's commits, rewrote it to `on: [TicketLanded, WaitStarted, RunFailed, RunAwaitingInput]` (`.lingtai/config.yaml:430`). `ApprovalRequested` and `WorkItemBlocked` are both gone with #502 (`packages/domain/src/vocabulary.ts:6-7`).

**Decision:** don't add a second fixture recipe. The checked-in file already meets the ticket's *Want* (it is not the machine's file), and a copy would only drift away from it.

- **Fix:** change the expected set to those four, and change the title from "five" to "four".
- **Commit body:** say plainly that the test never read `~/.lingtai`. The Fix row's premise came from the hand edit to the machine's file happening on the same day as `9b265938`.
- No other line in the file names either retired event (`grep ApprovalRequested\|WorkItemBlocked` matches only line 181), so nothing else in it moves.

## What none of these touch

There are no ADR conflicts; every change is to a test. `HOME=/nonexistent pnpm test` and `pnpm typecheck` are unaffected, because all four files are in the integration project. Run `pnpm fmt:check` after each edit: the board and init edits are long string literals, and oxfmt may wrap them.
