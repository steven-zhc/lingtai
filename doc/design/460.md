# #460 — design note

## Where it goes

Put it in `@lingtai/domain`, in a **new file `packages/domain/src/routing.ts`**, with its test at `packages/domain/unit/routing.test.ts`, exported from `index.ts`. None of the new names collide with a root export: `JudgeWhen` (`hold.ts:58`) is the only near miss, and you don't need it. Nothing in `packages/conductor` changes. #462 does the wiring.

**Not in `route.ts`, even though its header says it is "#460's to add" (`route.ts:8-13`).** `routeNext` returns `PassNext` and so has to import `pass-next.ts`. But `pass-next.ts` imports `wait.ts` (`pass-next.ts:25`), and `wait.ts` imports `route.ts` (`wait.ts:41`) to build `EscalationBecause` from `RouteEscalation.options` when the module loads (`wait.ts:102`). If `route.ts` imported `pass-next.ts`, that would close an ESM cycle. A zod schema read at load time inside that cycle is the same TDZ failure `hold.ts:15-19` warns about. So keep `route.ts` a leaf:
- Add only `JudgeReply` and `RouteDecision` there if you like, since both need nothing but `CandidateId` and `RouteEscalation`.
- Put everything that touches `PassNext` or `Proposal` in `routing.ts`, which nothing inside the domain imports.
- Update `route.ts`'s header so it stops promising `offerFor` and the other two.

Use zod schemas, not bare types (0101 §4, as in every sibling). §5's `PassRouted` will store `offer`, `reply` and `decision`, so they need to parse. For `CandidateNext`, reuse the `FixRound` and `Restart` schemas as `pass-next.ts:16-18` says, rather than declaring second copies. Pull them out of `PassNext.options` / `RequeueCause.options` by `_tag`, not by index. If that reads badly, exporting the two schemas from `pass-next.ts` is fine too.

Write `RouteDecision.Escalated.because` as `RouteEscalation` from `route.ts`. That is what makes `wait.ts:96-101`'s claim true by construction. Add a type-level test that `Extract<RouteDecision, {_tag:'Escalated'}>['because']` is assignable to `EscalationBecause`.

## `RoutingPolicy` is the two ceilings and nothing else

```ts
type RoutingPolicy = { rounds: number; restarts: number }  // totals, not "left"
```

These are the same two numbers `OfferInput` carries today: `rounds` is `runtime.limits.rounds`, `restarts` is `runtime.limits.restarts` (`judge.ts:221-226`). They pair with `Spent` (`pass-next.ts:69`), which already counts what was spent. Do **not** copy `Ceilings.restartsLeft` (`pass.ts:808`): that is "left", and `offerFor` would have to undo the subtraction. #462 converts at the call site.

`judge:` entries don't go into the policy. Nothing `offerFor` computes depends on which judge is declared. Choosing a judge stays where it is (`judgeDeclaredAt`, `judge.ts:104`), and so does calling a built-in or dispatching an agent. Both are the shell's job (0120 §3, *Where a reply comes from*). The domain can't import `@lingtai/recipe` anyway, because its only dependency is `zod`.

## `offerFor(proposal, policy, spent)`

Use fixed, exported ids rather than generating them. These are the strings a judge will answer with and that `PassRouted` will store:

| id | next | offered for |
|---|---|---|
| `'state-assumption'` | `FixRound{to: proposal.from, round}` | `InputNeeded` only |
| `'fix-lines'` | `FixRound{to:'implement', round}` | `BuildRed`, `ReviewFindings`, `ReviewEmpty`, `MergeConflict`, `VerifyRed` |
| `'restart'` | `Requeued{cause: Restart{restart}}` | `ReviewFindings`, `ReviewEmpty` |
| `'hand-to-person'` | `HandToPerson` | every proposal, always in `available` |

- **`InputNeeded` gets that step again and nothing else, even when it came from `implement`.** That rules out `fix-lines`. Today's `onOffer` does the same: an `asked` ending reaches only `at` (`pass.ts:962-965`: *"nobody but it knows the question, so the edges below are not reachable from a question either"*). Offering both would put two ids with the same `next` in front of a judge.
- **`'restart'` is listed against `ReviewEmpty` only so that it lands in `unavailable{NoCriterion}`**, and the same goes for `fix-lines` there. An offer for `ReviewEmpty` names the paid candidates it withheld, so a person reading `PassRouted` sees *why* only a person was left. That is what `unavailable` is for. The restart is never *available* for anything but `ReviewFindings`.
- **There is no `build` candidate.** `pass.ts:967`'s `if (at === 'merge') reachable.push('build')` has no counterpart here. The ticket's test that no offer contains a candidate from `merge` to `build`: since `FixRound.to` is `'design' | 'implement'` (`pass-next.ts:49`), the type already rules it out. Write the test anyway: for every `MergeConflict`/`VerifyRed` offer, no candidate in `available ∪ unavailable` has `next.to === 'build'` or an id mentioning build. That way someone who widens `FixRound` later trips over it.
- **Exclusion order: criterion first, then the ceiling.** Each paid candidate goes into `unavailable` with exactly one `because`. `NoCriterion` wins over `CeilingReached` when both apply. That is `judged`'s order (`pass-steps.ts:891-907`: readable, then criterion, then the judge), and it is the more useful thing to tell a person: raising a ceiling would not have helped.
- **What counts as no criterion:**
  - `ReviewEmpty` always. `nextOf` already split it off on "no finding with a failure scenario" (`pass-next.ts:252`).
  - `BuildRed` and **`VerifyRed`** when `output.trim() === ''`. The ticket names only `BuildRed`. I'm extending the rule to `VerifyRed` on purpose: today's `carriesACriterion` treats every non-`findings` direction the same way, by `evidence.trim() !== ''` (`pass-steps.ts:696-700`, and `judge.ts:302-306`). `VerifyRed.output` is the same kind of evidence, a command's output. Leaving it out would quietly start buying rounds for an empty re-verify, which nothing buys today.
  - `MergeConflict` and `InputNeeded` always carry one: paths and shas, or a question.
- **Ceilings:**
  - A round is available iff `spent.rounds < policy.rounds`, with `round = spent.rounds + 1`.
  - A restart is available iff `spent.restarts < policy.restarts`, with `restart = spent.restarts + 1`.
  - Both sides match `onOffer`'s `roundsSpent < ceilings.rounds` (`pass.ts:970`) and §4's "`round` and `restart` are what was spent plus one".
  - `state-assumption` and `fix-lines` both spend a round.
- **Order** `available` and `unavailable` the way the table lists them, cheapest first. That mirrors `stepsOnOffer` (`judge.ts:278-280`). It is not a priority, but a fixed order makes the offers deterministic to assert on.

## `decideRoute(offer, reply)`

Read only the offer, never `policy` or `spent`:

| reply | result |
|---|---|
| `NotAsked` | `Escalated{NotAsked}` |
| `Unreadable{raw}` | `Escalated{UnreadableReply{raw}}` |
| `Selected{candidate}`, id found in `available` | `Selected{candidate}` |
| `Selected{candidate}`, id found in `unavailable` | `Escalated{CandidateUnavailable{excluded: that entry}}` |
| `Selected{candidate}`, id found in neither | `Escalated{UnknownCandidate{candidate}}` |

A judge that selects `'hand-to-person'` gets a `Selected`. That is legitimate, and `routeNext` turns it into `JudgeHandedOver`.

## `routeNext(offer, reply, decision, run)`

**It takes a fourth argument, `run: RunRef`** (from `wait.ts:60`, the subpath model, not `hold.ts`'s). §3's signature leaves it out, but both `AgentQuestion` (`wait.ts:70-75`) and `ProposedEscalated` (`wait.ts:106-111`) require `run`. `nextOf` takes it for the same reason (`pass-next.ts:77`). This fills in a field the ADR's sketch elided. It is not a different decision, so it doesn't need a superseding ADR.

- **`Selected`**: look the id up in `offer.available`.
  - `FixRound` / `Requeued` → return the candidate's `next` exactly as stored. Don't recompute the round.
  - `HandToPerson` → `WaitOnPerson{ProposedEscalated{run, proposal, because: JudgeHandedOver{why: reply.why}}}`. This is why `reply` is a parameter.
- **`Escalated{NotAsked}` with an `InputNeeded` proposal** → `WaitOnPerson{AgentQuestion{run, step: proposal.from, question}}`. This is the only thing "unjudged" means here: `NotAsked`. An `InputNeeded` whose judge answered something unreadable or unknown is still `ProposedEscalated`, because the person has to see the judge failed, not just the question.
- **Every other `Escalated`** → `WaitOnPerson{ProposedEscalated{run, proposal, because}}`.
- **Inputs that `decideRoute` cannot produce throw**:
  - a `Selected` decision whose id isn't in `available`;
  - a `Selected` decision paired with a reply that isn't `Selected`.

  Reuse the `ImpossibleOutcomeError` precedent (`pass-next.ts:33`, which follows `upcast.ts:189`) with a small `ImpossibleRouteError` of its own, and don't coerce. Replay will call this on stored triples (§5), so a corrupt triple should fail loudly.

## Tests

The `Done when` list says what to cover. Two shapes make it exhaustive rather than just long:

- **Build the input space, don't pick examples.** Use one fixture per `Proposal` variant, with `BuildRed` and `VerifyRed` each appearing with and without output. Cross it with `spent` at `{0,0}`, at `rounds` ceiling, at `restarts` ceiling, and at both, under a policy like `{rounds: 2, restarts: 1}`. Then:
  - Assert each offer against a written-out expected value. Follow the table-driven style of `pass-next.test.ts`.
  - Over the same cross product × every reply (`NotAsked`, `Unreadable`, `Selected` of each id that appears, `Selected('nope')`), assert that `routeNext(o, r, decideRoute(o, r), run)._tag` is never `'HandToPerson'`, and that `.reason._tag` is `AgentQuestion` exactly when the proposal is `InputNeeded` and the reply is `NotAsked`.
- **Policy `{0, 0}`** must give every proposal an offer where `available` is exactly `['hand-to-person']`. That is the floor `onOffer` keeps (`pass.ts:974-976`: *"`waiting` costs nothing … keeps the set non-empty"*).

Everything here is pure, so `pnpm test`'s unit project covers it completely. No claim depends on the integration half or on the log. Whether the new route agrees with today's `judged` on real arrivals is #462's question, and it gets settled there by `PassRouted.offer`/`decision` against the `RouteTaken` events the current router writes.
