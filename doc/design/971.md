# #971 — design note

## Three premises in the ticket that the code contradicts

**`wizard-page.ts` has a user.** `packages/conductor/src/wizard.ts:60` imports `CHECKING_STEPS` and `nothingChecks` from it and uses both at `:138-139`.
- Move those two into `wizard.ts`, then delete the file and its test.
- Remove the `./wizard-page` export (`packages/conductor/package.json:46`).
- Fix the path in `doc/plugins/human.md:56`.
- If the deleted file held any `async`, lower `packages/conductor` in the ratchet baseline. The test goes red below baseline as well as above it (`effect-ratchet.test.ts`, the `n < base` branch).

**A local directory whose origin is on GitHub cannot be written as `github`.**
- `proposeSetup` proposes `github` for it (`propose-setup.ts:209-230`).
- The registration is `owner: null` (`onboard.ts:647`), and `ownerlessRefusal` then refuses every pass: *"has no owner and its recipe does not say source.tickets: db"* (`filter.ts:262-265`).
- `askTickets` refuses the same answer (`source.ts:136-143`), and #977 says *"never `github` on a project with no owner"*.

The decision: the form's value for a local target is `db`. The line's sentence says the origin is on GitHub and that a local directory cannot take its issues yet (#977). *change* shows `github` disabled with that reason.

Put this in one small function in `@lingtai/setup` that #977 can delete. Do not change `proposeSetup`, because `propose-setup.test.ts:44` pins that gap on purpose. The alternative of showing `github` and writing `db` would break *the preview is the writer's output*.

**The mock's values are not the target.** Use it for layout only. Where they differ, the Proposal wins:

| Line | Mock (`add-repository.html:976-1009`) | Real value |
|---|---|---|
| held by | `agent:hold` | null (`propose-setup.ts:72`) |
| wall | `1h` | `2h` (`:76`) |
| `repo.github`, `end: [{close: issue}]` | shown | not what is written |
| `proposed: []` | printed | not written |

On the last row: on an absent file, `lingtai add` writes no `steps.proposed` for *No* (`landing.ts:199`, `answers.ts:113-117`), and the done-when compares against that. *Yes* is `landingChanges({land:'hold'}, [], [])`.

## Where it goes

- `read-model.ts` holds plain types.
- `setup-form.tsx` is the client form.

**Client boundary.** The client file takes types only from `@lingtai/setup` and `@lingtai/recipe` (`setup/src/index.ts:1-5`). **`packages/conductor/src/add-from-page.ts`** (new, exported from `package.json`) holds the IO, because conductor already depends on `@lingtai/setup` and on env (`apply-setup.ts:12-15`). It has two Effects.

## Decisions that are not obvious

**A local project's base is `lingtai-base`, not the checked-out branch** (`first-project.ts:627`, 0104 §15). Pass it as the `defaultBranch` reader's answer. `Proposal.base` on a local target is *"the one the caller already worked out"* (`propose-setup.ts:62`).
- `first-project.ts:633-656` and `:784-801` both decide and make that branch. Extract them as Effects over the git port, and have the CLI call them.
- On the page, make the branch **inside `register`**, after the recipe is written. A refused write then leaves no branch, and a retry finds the branch already there.
- The name is `basename(toplevel)` and the remote is the toplevel itself (`first-project.ts:508-509`). Take both from `readLocalRepository`, re-run on the server, never from the query string.

**Live preview is a server action, not client code.** `setRecipe` and `previewSetup` need node.
- `previewAdd` returns `{ text, ceiling }` or `{ refused }`.
- `text` is `previewSetup(diskFiles target, answers)`. It reads any recipe already on disk, so a retry previews the real result.
- `ceiling` is `attemptCeiling` over `ceilingOf(resolveSource(text))`, as `apps/board/src/lib/recipe.ts:899` does. The sentence therefore cannot disagree with the YAML, and the client imports nothing from conductor.
- Debounce it, and drop any response older than the latest request.

**Already added uses `alreadyAdded` over `loadAllProjects()`** (`apply-setup.ts:136`, `projects.ts:62`), the same call the CLI makes (`first-project.ts:1304`). It reads the streams, not a projection, so a double-click sees the first Add. Check on render, showing the sentence instead of the form, and again first thing in `addRepository`. Unlike `add.ts:187`, the page does no owner repair, which stays in the terminal.

**Refusal sentences copy `add.ts:360-367`.**
- `SetupWriteError`: its message alone.
- A declined or thrown registration: `add`'s collected log or the error, then `keptSentence(path)`.
- An empty agent or base still lets Add be pressed, and is refused by name before any write (`agents.ts:210`, `add-github.ts:342-344`).

**Unticked checks need a command.** `skipped` has only `{script, why}` (`detect-setup.ts:49`, `:195`), but the mock shows `npm run dev`. Add `run` to it at detection and update the tests. A ticked one is written as `{ name: script, run }`.

**Smaller decisions:**
- `stack` writes no recipe key, so its *change* moves focus to install and checks.
- The turns dial is disabled and reads *unbounded* for a writer without a turn ceiling. The page passes that per runtime, since `everyRuntime` is server-only.
- With history in the log, the ticket line is locked (`source.ts:119-133`).

**Step 3 does not exist yet, and #972 is blocked by this ticket.** Add a stub at `/setup/repository/added?project=`, the same way `read/page.tsx` stubbed step 2, naming the project and recipe path. #972 replaces it.

## ADR

Turns, restarts, held-by and end are lines the terminal does not ask about, and the ticket requires them. That strains 0125 §2: *"neither asks a question the other does not"*. Do not add CLI questions here. Under this pass's append-only rule, the answer is a superseding file rather than an edit to 0125, but CLAUDE.md says a changed decision is an edit to its topic's ADR. Name the conflict in the summary and leave the choice to a person. Neither is in this diff.

## The test

Put it in `apps/cli/unit/`, the only place that can see both `askRecipe` and `@lingtai/setup`. `recipe-flow.test.ts:20-24` already drives `askRecipe` through `applySetup` over fake files.

Use a chapter-garden-shaped reader, run `askRecipe` with `--defaults`, and run the same answers through `setup-answers`. Compare the two written files byte for byte, comments included. Registration is a no-op `Effect.void`.

`addProject`'s branches get unit tests with fakes: already added, refused write, failed registration then retry, and the local `db` rule.
