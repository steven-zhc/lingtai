## Design: doctor answers for an owner-less project (#357)

### Where it goes

`apps/cli/src/doctor.ts` only has two loops to change. Every other per-project row already handles `owner: null`:

- **`projectRecipes`** (`doctor.ts:1555`) grades `projectFilters` output. Since `0b3ee57c`, `projectFilter` takes an owner-less project down its own branch (`packages/conductor/src/filter.ts:306`, *"A project with no owner … builds no `GitHubClient`"*). That branch already refuses a project missing `source.tickets: db` or `repo.remote` through `ownerlessRefusal` (`filter.ts:239`). Don't touch it.
- **`passRefusals`** (`doctor.ts:1061`) filters on `p.project !== null` and nothing else. Don't touch it either.
- **`declaredEnvironment`** (`doctor.ts:1996`) and **`recipeGovernsItsBase`** (`doctor.ts:2087`) are the two `if (!project.project || !project.owner) continue` lines.

**`declaredEnvironment`.** Delete `|| !project.owner`. Nothing in the loop body reads `owner`: `currentRecipe`, `resolveAgentEnv`, `extensionRow`, `limitsRow` and `dispatchedAuthRow` all take the project name only. This one row emits four results per project: `env: <p>`, the extension row, the limits row and `runtime: <p> signed in`. All four then answer for an owner-less project.

**`recipeGovernsItsBase`.** Delete `|| !project.owner`. The one place `owner` is read is the slug at `:2091`, `` `${project.owner}/${project.project}` ``. `baseDivergence` splices that slug straight after `lingtai add ` in its *Re-register:* sentence (`packages/recipe/src/resolve.ts:339`). With no owner it would print `lingtai add null/app --base …`. So pick the slug in this order:

1. `owner !== null` → `` `${owner}/${project}` ``, unchanged.
2. `owner === null` and `remoteOf(resolved.recipe) !== null` → `` `--local <dir>` ``. This is the convention `packages/conductor/src/conduct.ts:586` already uses for the same sentence: *"`ProjectState` never recorded the local directory `--local` needs, so `<dir>` names what the operator must fill in"*.
3. `owner === null` and no `repo.remote` → `` `<owner>/${project}` ``. This is a GitHub project registered before `ProjectConfigured` carried an owner. `apps/cli/src/init.ts:351` tells the two apart the same way: *"only the remote a local registration writes tells the two apart"*. Doctor has no `ownerlessRefusal` guard in front of this row the way `conduct.ts` has, so case 3 can happen here.

**`!project.project` must not keep a bare `continue`** either (Done-when 3). Make it a `skip` labelled with `project.project ?? '(unnamed)'`, which is `projectFilter`'s own spelling (`filter.ts:301`). Use `currentRecipe`'s own sentence as the detail: `no repository name recorded — re-run lingtai add` (`packages/conductor/src/projects.ts:159`).

### "Read its base from its remote" means no new read

The ticket's *Fix* says to read the base from the remote instead of GitHub. The base row never asked GitHub. It compares two recorded values:

- `resolved.ref`, which is `state.base`, the branch recorded at registration (`projects.ts:160`, `base: base ?? state.base ?? null`);
- the recipe's own `baseOf(recipe)` (`resolve.ts:331`).

For a `--local` project, `state.base` is the branch the operator gave at registration. `chooseFirstProject` asks for it (`apps/cli/src/first-project.ts:365–381`) and `addLocal` appends it on `ProjectConfigured.base` (`packages/conductor/src/onboard.ts:421`). The registration has already turned "the remote's default branch" into that recorded field.

**Do not add a `git ls-remote` or any fetch to this row.** It would be a process and a network call inside a row whose docstring says *"No App is needed to compare them: the recipe is this machine's file (#180)"* (`doctor.ts:2077`). A network blip would also turn into a red that gates `restart`. Done-when 2's "disagrees with its remote's default branch" is tested as: `state.base` differs from the recipe's `repo.base`. That is exactly what the GitHub case tests (`apps/cli/integration/doctor-recipe.test.ts:131`).

### The decision that is not obvious: the unit test needs a recipe seam, and `load` is not enough

The only test of these two rows today is `apps/cli/integration/doctor-recipe.test.ts`. It writes a recipe into a `mkdtemp` and sets `LINGTAI_HOME`. That is the filesystem, so it is integration under 0060 §1. Done-when 1 asks for `unit/`. Three things in these rows reach outside the process even when `load` is injected:

1. **`currentRecipe(project)`** (`doctor.ts:1999`, `:2090`) reads `~/.lingtai/<project>/recipe.yml` through `resolveLocalRecipe`. `projectFiltersOnce` (`doctor.ts:1529`) hits the same read through `projectFilters`' default `recipeFor`. The `runDoctor` docstring (`doctor.ts:2128`) already names the obligation: *"the projects a report is about are the caller's to name, and a caller that names them owes the recipes too."*
2. **`resolveAgentEnv`** reads `projectEnvPath(project, stateDir())` (`packages/agent-env/src/index.ts:461`). It is ENOENT-tolerant, but it is still a read of the real `$HOME`.
3. **`dispatchedAuthRow`** calls `createRuntime(agent).checkAuth` (`doctor.ts:1957`), which spawns `claude auth status`. `apps/cli/unit/doctor.test.ts`'s header names that spawn as one of the things `reach` exists to prevent.

Add these to `DoctorReach` (`doctor.ts:841`). It is already the per-reach-out seam, and `runDoctor` already takes `Partial<DoctorReach>`:

- **`recipe: RecipeFor`**, defaulting to `currentRecipe`. Thread it into `projectFiltersOnce` → `projectFilters(projects, recipeClientFor(env), recipe)`, and into both rows in place of the direct `currentRecipe(project)` calls. Then `recipe:`, `env:` and `base:` all read one injected source, which keeps `#389`'s *one resolve* comment true.
- **`agentEnv: typeof resolveAgentEnv`**, used only by `declaredEnvironment`.
- **The auth probe goes through the existing `reach.runtimes`.** Have `dispatchedAuthRow` find the runtime by `capabilities.id` in the `runtimes()` list (defaulting to `everyRuntime()`, as `runtimeAuth` does) rather than calling `createRuntime`. Don't add a second runtime seam beside the one `runtimeAuth` already has.

Change `declaredEnvironment` and `recipeGovernsItsBase` to take `reach: Partial<DoctorReach> = {}` as their third parameter. Then the integration test's two-argument calls are unchanged.

In the unit test, the recipe stub can still exercise the real resolver. `resolveLocalRecipe` accepts a `read` seam and a `home` (`packages/recipe/src/local.ts:268–281`), so a stub like `(s) => currentRecipe(s, undefined, undefined, { home: '/h', read: async (p) => (p.endsWith('recipe.yml') ? RECIPE : null), signedIn: async () => [] })` runs the real resolve and the real `baseDivergence` with no I/O. Give the test recipe `source.tickets: db` and `repo.remote`, or the `recipe:` row correctly fails it through `ownerlessRefusal`. That is not a defect: it is the "correctly set-up" in the ticket's *Want*.

**"No GitHub call" as an assertion:** pass `env` with no App variables, so `recipeClientFor` returns `offlineClient` (`doctor.ts:1503`). Then assert that the recipe stub was handed `undefined` as its client for the owner-less project, which is `projectFilter`'s owner-less branch (`filter.ts:307`). The Done-when says "by name", so assert each row by its exact name: `recipe: resolves for every project`'s row for the project, `env: app`, the extension and limits rows, `runtime: app signed in`, and `base: app`. A count of oks would pass even if a row went missing. Run the test under `HOME=/nonexistent pnpm test` to prove nothing reached the real home.

### Watch-outs this shape already handles

- **Doctor never writes.** The base row stays a `fail` with a remedy sentence and never re-registers anything (`doctor.ts:2068–2070`).
- **`restart` gating.** Case 3 above is the false-red risk. A legacy owner-less GitHub project whose bases agree must come out `ok`, not fail for having no remote: that question belongs to the `recipe:` row, not the base row. Add a unit case where `owner: null`, the recipe has no `repo.remote`, and the bases agree. It should give `base: <p>` ok.
- **The integration test file** still passes `owner: 'me'` and needs no change. Its claims are not weakened.
