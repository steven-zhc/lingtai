## Design note for #1020: keeping the failure channel down to `ConcurrencyError`

The ticket decides the structure. There is one place where following its wording literally gives the wrong types. Everything else, build as the ticket says.

### `Effect.try` / `Effect.tryPromise` with a `catch` makes every error a failure

`append`'s error type must be exactly `ConcurrencyError`, and everything else must be a defect (0101 §6: *"The event store's failures stay **defects** rather than tagged errors"*). Both `Effect.try({ try, catch })` and `Effect.tryPromise({ try, catch })` send **everything** thrown inside `try` through `catch` into the failure channel. So `catch: (e) => isVersionConflict(e) ? new ConcurrencyError(…) : e` types `E` as `unknown`. It also turns a dropped connection into a `Fail`, and `events-contract.ts`'s *"a lost race is a `Fail`, an unknown type is a `Die`"* can no longer tell the two apart. The fix is to decide, at the point where the error is caught, whether it is a failure or a defect, and to rethrow everything else:

- **SQLite.** Keep today's body (`sqlite.ts:223-258`) as it is: `BEGIN IMMEDIATE`, the inserts, `COMMIT`, and the `catch` with its guarded `ROLLBACK`. Wrap it in **`Effect.suspend(() => { … })`** instead of `Effect.try`. The `try` path returns `Effect.succeed(written)`. The conflict branch returns `Effect.fail(new ConcurrencyError(streamId, expectedVersion, rows.map(r => r.version), { cause: err }))` where it `throw`s today. Every other error is rethrown, and inside `suspend` a throw is a defect. This is still one synchronous thunk with no `yield*` between `BEGIN` and `COMMIT`, which is the actual invariant the ticket's *Watch out* is protecting (`sqlite.ts:219-222`: *"nothing else in this process runs between BEGIN and COMMIT"*). Read the ticket's "inside one `Effect.try`" as "inside one synchronous block". The reads are `Effect.sync`, so a closed `DatabaseSync` throwing comes out as the `Die` the SQLite contract run asserts.
- **Postgres.** Use `Effect.promise(() => client.transaction(async (tx) => …).then(Effect.succeed, (err) => { if (isVersionConflict(err)) return Effect.fail(new ConcurrencyError(…)); throw err }))`, then `Effect.flatten`, wrapped in `Effect.uninterruptible`. `Effect.promise` makes a rejection a defect, so only the conflict reaches the failure channel. The `.then` handlers are not `async`, so the only `async` left is Prisma's callback, which the ticket already counts (`event-store.ts:386`). The reads are `Effect.promise` too, not `tryPromise`.
- **`prepareAppend` and the empty-batch return stay first**, before the transaction, in the body of `Effect.fn('EventStore.append')`. A throw from the generator is a defect, so the `RangeError` and `UnknownEventTypeError` that `test/contract.ts:111-129` asserts on the promise side reach the face unchanged. If `prepareAppend` ends up *inside* a `try:` thunk, it becomes a `Fail`, and the new contract's *"an unknown type and a negative `expectedVersion` are each a `Die`"* goes red.
- **`fromPromiseStore`** is where `Effect.tryPromise` belongs: `catch: (e) => e`, then `Effect.catchIf((e): e is unknown => !(e instanceof ConcurrencyError), Effect.die)` (`catchIf` is at `effect@4.1.2/src/Effect.ts:6027`) on `append`. On the other four methods use plain `Effect.promise`, so their error type is `never` without any narrowing.

Unit-level stand-in: `events-contract.ts` run against `fromPromiseStore(createMemoryEventStore())` checks the face and the failure-vs-defect split in `pnpm test`. The SQLite run in `integration/sqlite.test.ts` is the only check of the `suspend` block above, and it runs on a SQLite file in about a second (`pnpm exec vitest run --project integration packages/event-store/integration/sqlite.test.ts`), so run it before committing. Nothing checks the Postgres body before the merge. `tsc` checking `append`'s declared `Effect<Envelope[], ConcurrencyError>` against the implementation is what catches a leaked `unknown` there.

### What the ratchet will accept as a face

The face checker (`packages/domain/unit/effect-ratchet.test.ts:170-265`) accepts an exported `function` or a single-declarator `export const x = (…) =>`. The body must be exactly one `return Effect.runPromise(<call>)`, and the argument must be a call expression, so `events.append(streamId, expectedVersion, batch)` is fine and `const e = …; return Effect.runPromise(e)` is refused. Write each face as `export function appendFace(events: EventsPort, streamId: string, …) { return Effect.runPromise(events.append(streamId, …)) }`, and have `promiseStore`'s non-`async` arrows call those faces by name. If `promiseStore` calls `Effect.runPromise` itself, the ratchet counts it as a run, and that is a red you must not fix by raising the baseline. The faces file names the function as `fn` (see the existing entries in `effect-ratchet.faces.json`), one entry per face.
