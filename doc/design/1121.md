# Design note: #1121, what each side did to a conflicted path, with the base commits and their tickets

## The ticket's premise that is wrong: #1120 did not put the base diff in the brief

The ticket says #1120's `mergedConflictHalf` already contains the `fromSha..baseSha` block. It does not. `mergedConflictHalf` (`packages/conductor/src/fix.ts:866-912`) is pure text. It only names commands for the agent to run: *"What landed on the base is `from..base` (`git log …` and `git diff …` show it)"* (`fix.ts:879-880`). Nothing on the fix path reads a diff. `fixRound` (`packages/conductor/src/conduct.ts:4439`) builds `refusal.merged` from `brief.context.conflictMerge` (`:4460-4467`), which is `{ baseSha, fromSha, paths }` and nothing more.

**So this ticket adds the first read to the fix brief.** That is the main piece of new work. The review side only needs to be widened.

The line numbers in the ticket are from before #1120. Use these:

- the `landed` closure is at `conduct.ts:3764-3775`;
- `mergeForConflict` is at `:3390-3458`;
- `conflictEvidence` is at `:3466-3497`;
- `landedOnBaseBlock` is at `packages/actions/src/agent-action.ts:435-484`;
- the `landed` deps are at `:159-164` (promise), `:203-208` (Effect) and `:226-229` (the lift);
- `ActionContext.landedOnBase` is at `packages/actions/src/action.ts:542`.

## Shape

### 1. The renderer splits into a section and two framings (`packages/actions/src/agent-action.ts`)

`landedOnBaseBlock` fuses two things: the per-path rendering under the cap, and the review's question (`:459-484`). The fixer must not be asked the review's question.

- Pull the loop at `:440-458` out into an exported `landedPathsSection(moved, per, capLines)`. It returns the `### <path>` sections and the cut and left-out notes, and implements Fix 4's widened entries and the shared budget.
- `landedOnBaseBlock` keeps both of its framings and calls the section.
- `mergedConflictHalf` calls the same section under its own heading, in place of the `git log`/`git diff` sentence at `fix.ts:879-880`.

`packages/conductor` already depends on `@lingtai/actions` (`conduct.ts:25`, `packages/conductor/package.json:53`), so `fix.ts` can import it. `fixBrief` stays pure: it is handed the entries and never reads anything.

**Entries carry data that is already resolved, not raw git output.** For example:

```
{ path, diff,
  commits?: { lines: { sha, subject, ticket?: { n, title } | { n, none: true } | { n, failed } }[] } | { failed },
  branchDiff?: string }
```

The renderer formats Fix 3's four line shapes and the empty-answer lines. The parse and the title reads stay in conduct. The exact type is the implementer's choice. What matters is that a failure is a variant the renderer prints, never a missing key.

### 2. One read, `landedOnBaseRead`, as an `Effect` defined in the pass scope of `conduct.ts`

Define it beside `mergeForConflict`. It needs `gitAskedEffect` (`:1851`), `store` and `project`, and all three are in scope there. Two callers use it:

- the review's `landed:` at `:3764`, which becomes a reference to it;
- `fixRound`, which calls it with `brief.context.conflictMerge` before building `refusal` and puts the entries on `merged`.

Since `fixRound` is already an `Effect.gen` (`:4439`), the call needs no new run.

**The read owns the order.** `applyConflictMerge` builds `paths` as overlap first, then conflicted (`run-attempt.ts:1448`), and so does the continuation (`:1719`). Neither of those changes. The read returns `conflicted` in its own order, then the remaining `paths`.

**The title read** is `Effect.tryPromise(() => store.read(ticketStream(project, n)))`, run once per distinct ticket and then `reduceTicket(events).title`. Both names are already imported (`conduct.ts:63`, `:68`).

- Use `Effect.result` around it, never `Effect.promise`. The two `Effect.promise(store.read…)` sites (`:3169`, `:4274`) are fatal on purpose; this read must not be.
- `tryPromise` is not counted by the ratchet. No `async` and no `Effect.run*` are added.

### 3. `branchSha`: both paths that produce a conflict merge can know it

**Fresh round.** In `mergeForConflict`, read `rev-parse HEAD` before `merge --no-commit` (`:3423`). Do it right after the `merge-base HEAD` read, which already depends on `HEAD` being readable.

- A failed read is `failed`, like the fork read at `:3420-3421`. The two can only fail together.
- Add `branchSha` to `ConflictMergeAnswer.conflicted` (`run-attempt.ts:1021-1029`).
- `applyConflictMerge` (`:1442-1457`) copies it onto `landedOnBase` and `conflictMerge`.
- Widen the types:
  - `from.landedOnBase` (`:990-995`);
  - the locals at `:1366-1373`;
  - `ActionContext.landedOnBase` (`action.ts:542`);
  - both `landed` signatures in `agent-action.ts`.

**Resumed review.** Here the ticket's edge is too pessimistic, so this note decides it differently. `conflictEvidence` already finds the merge's first parent, `ours` (`conduct.ts:3486`). That is exactly the branch head before the merge: *"It is the merge on the path from `baseSha` to `HEAD` that has `baseSha` as a parent"* (`:3471-3472`).

- Return it as `branchSha` alongside `fromSha` and `overlap`.
- The branch at `run-attempt.ts:1718-1723` carries it.

Only the `BaseMoved` continuation (`landedOnBaseOf`, `attempts.ts:273`) stays without a `branchSha` and without `conflicted`. It renders #594's block as it does today. The only change there is the `DIFF_FLAGS` spelling.

### 4. `ticketOfLandingSubject`

Put it in `packages/repo/src/landing-subject.ts`. It is reached through the existing `@lingtai/repo/landing-subject` subpath (`packages/repo/package.json:8`), so the module still imports nothing.

- `apps/release/src/tickets-changed.ts:11-17` drops `LANDING` and calls it.
- Conduct imports it from the subpath too.

## Where the tests go

- **Brief and review at conduct level:** `packages/conductor/unit/conduct-a-conflict-round-merges-first.test.ts` already drives #1120's opt-in conflict fields. Extend it rather than starting a new harness.
- **Resumed review with `branchSha` from `conflictEvidence`:** `conduct-continuation-conflict-keeps-its-head.test.ts`.
- **Byte-for-byte check for entries without `commits`:** pin `landedOnBaseBlock`'s current output in `agent-action.test.ts` before refactoring, so the split is proven not to change it.
- **Fix-brief rendering:** `packages/conductor/unit/fix.test.ts` covers `mergedConflictHalf` with entries, and with the `[could not read …]` variants.

The `--first-parent` walk over a real merge history is integration only (out of scope in the ticket). The unit claim that stands in for it is the `did` assertion on the exact argv.

## What settles it after the restart

After the restart, the next conflict round's recorded prompt shows whether it worked. Look at the `StepStarted`/prompt record for the `implement` visit whose `PassRouted.next` is `FixRound` from `merge` with `because: 'conflict'`. It should contain `What landed here:` and `What this branch did to it`. A prompt holding `(title not read: …)` is the failure path doing its job, not a regression.
