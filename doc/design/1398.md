## Shape: #1398

### What is already there, and why it matters

The ticket says the redo is blind. That is only partly true. A step redone whole already ends its brief with one paragraph. `redoParagraph` (`packages/actions/src/action.ts:1367`) writes it from `ActionContext.redo: RedoNote` (`action.ts:507-516`). In `redoStep` (`packages/conductor/src/run-attempt.ts:1838-1842`) that note's `why` is set to `` `the agent did not finish: ${reason.detail}` `` (`run-attempt.ts:2745`). So in #1371 the agent was told *"This step was interrupted (the agent did not finish: the final message declared no outcome) …"*. It was never told how its message ended, or what the block should look like. The run log settles this: the brief recorded on the redo's prompt event (`context.prompted`, `action.ts:529`) holds the sentence.

**Fix 3 is a change to `RedoNote` and `redoParagraph`. It is not a second paragraph.** The comment on `redoParagraph` says *"One function, so the three agents that are handed it cannot word it differently"* (`action.ts:1364-1365`). A second, separate paragraph would put two "this step was redone" texts at the end of one brief.

### 1. Reading (`packages/domain/src/implement-outcome.ts`)

- Keep `blockOf` (`:57-77`) as the one JSON-to-`Declared` gate. Add one pre-check before it: the body equals `Implemented` after trimming. Use that check only for the body of an ` ```outcome ` fence.
- To find json fences, use an opener built like `OPENS` (`:41`), namely `/^[ \t]*```json[ \t]*$/gm`, and the same `CLOSES` (`:42`). CRLF then behaves as it does today.
  - A json fence becomes a candidate only if `JSON.parse` returns a plain object with an own `outcome` key whose value is one of the four names. Otherwise it is skipped, not pushed as `null`.
  - That is the difference from today's loop (`:87-91`). There, every ` ```outcome ` fence pushes, and an unreadable one makes the message `null`. Keep that for outcome fences. A json fence that fails the key test is "not an outcome", and it must not poison the message.
  - A json fence that passes the key test but fails `Block` pushes `null`. The ticket's *unknown is never `Implemented`* depends on this.
- The last-line form is a candidate only if its line is not already inside a fence that was found. Otherwise a message ending in a json fence whose last body line is `{"outcome":…}` would count twice. Counting twice is harmless because the two agree, but it is untidy.
- Sort the candidates by their index in the text. The last one decides, and every candidate must agree with it (`:92-95`, unchanged).
- New return shape: `{ declared: Declared; form: 'fence' | 'json-fence' | 'last-line' | 'bare-word' } | null`. When the candidates mix forms, `form` is the deciding candidate's form.
  - There are three call sites, all in `packages/conductor/src/conduct.ts`: `:5378`, `:5725`, and the import at `:93`. Unwrap `.declared` at each.
  - Do not change `DecideInput.declared` (`:99`). `decideImplementOutcome` stays as it is, and that is what keeps the safe side in place.

### 2. The run-log line

Write it at the two call sites in `conduct.ts`, next to the parse, through the run log the step already writes to. The parse is pure and has no log. Write the line only when `form !== 'fence'`.

### 3. Getting the tail from `conduct.ts` to `redoStep`: the trap

The final message is available only in `conduct.ts` (`outcome.text`, `:5378`; `fixed.text`, `:5725`). `redoStep` sees only `reason.detail`. That comes from `declared.why` (`packages/domain/src/attempt-next.ts:284`), and the comment there is the trap:

> *"Our own sentence only: the agent's prose is not a runtime's failure text, and `wallOf` reads this detail for an account limit."* (`attempt-next.ts:281-283`)

`wallOf(reason.detail)` runs on every implement `AgentCrashed` (`conduct.ts:6574`). If the tail went into `why`, an agent whose last 300 characters mention a usage limit would lock the account.

So **add an optional field `said?: string` to the stored `AgentFailed`** (`implement-outcome.ts:18`). The stored schema is lenient on purpose (`:14`), so old rows still parse.

- `conduct.ts` sets it only when the parse returned `null` and the message was non-empty. Set it after `decideImplementOutcome`; do not add it as an input to the pure function.
- In `run-attempt.ts:2728-2731`, `failed` already reads `decided.result.outcome`. Read `.said` there:
  - Pass it as `redoStep`'s `said`, so it goes into `StepRedone.said` (`events.ts:1761`). That field's doc already allows *"the unreadable answer"*.
  - Pass it as a new `RedoNote.unread`.
- `why` and `detail` stay our own sentence.
- An `Implemented` with the head unmoved, or a bad `Disputed` index, has no `said`, so it gets no new text. The ticket asks the paragraph only for an unreadable outcome.

### 4. The paragraph (`action.ts:1367`)

When `redo.unread !== undefined`, `redoParagraph` appends to its usual sentence:

1. The tail, quoted.
2. That no outcome could be read from it.
3. The `Implemented` block exactly as `fix.ts:632-634` shows it.
4. "or another block as the brief above shows it".

Do not make the block depend on the step. The brief above already lists the outcomes that step may declare: fix offers `Disputed` (`fix.ts:613-647`) and implement offers `AlreadyDone`. Saying "the brief above" keeps the paragraph identical for both agents.

Quote the tail as a fence that cannot be closed by the quoted text. The tail will often contain ` ``` `. Use a longer fence, for example four backticks, or indent it.

Indent it, or make sure the quoted tail can never be read as a candidate in a message the agent might paste back. The agent's own next message is parsed, not the brief, so this matters only if the agent echoes the quote.

**Two follow-on edits:**

- `withRedoParagraph`'s `trailing` regex (`action.ts:1356-1357`) strips a recorded brief's old paragraph before adding the new one (#1246). The regex is anchored on `Carry on, and do not redo what is committed\.$`, so a paragraph that now ends with a quoted block would no longer be stripped, and redos would stack.
  - Either put the unread text *before* the closing `Carry on…` sentence and make the regex allow multi-line content in that span, or widen the regex.
  - Pin this with a test: a recorded brief that ends in the new paragraph, redone again, ends in exactly one paragraph.
- Stacking across redos is otherwise already handled. `redoStep` drops the earlier `redo` and keeps only its `startedAt` (`run-attempt.ts:1832-1840`), so redo 2 quotes redo 1's message only.

`fix.test.ts` pins the brief. The ticket says the paragraph is pinned once, there. Put the new pin wherever `redoParagraph` already has its tests, plus one assertion in `fix.test.ts`. A crash redo, where `rerunInPlace` is the branch at `run-attempt.ts:2738` and no `said` is set, gets the paragraph unchanged.

### Edges the ticket states that the code does not back

- **The board shows it.** `stepRedoneLine` (`apps/board/src/lib/history.ts:850-852`) never reads `said`, and it words every redo as *"cut off by an API error"*. Decision: leave the board line alone in this change, and add a backlog note. Changing the wording of every redo's history line is a different ticket. `lingtai status` reads the step's ending detail, which stays our own sentence.
- **A daemon stopped during the wait (widened by the person's answer).** A stop that interrupts a run while `StepRedone` is the last step row releases the claim with a new continuable cause, `StepRedoPending { runId, step }` (`events.ts`, `CONTINUABLE_CAUSES`). The next claim continues that run at `step` like an account-limit release, and `pendingRedoOf` reads that `StepRedone.said` into the redo's `RedoNote.unread`, so its brief quotes the tail. A process killed outright finalizes nothing, so two things are written before it can die: the redo after an unreadable outcome saves its head (a publish, `saveHead`) before `StepRedone` is written, and the dead-worker release reads the run's stream and names the redo (`continuableRedoOf`: only while a head was saved). A run stream that cannot be read fails that release, to be made again by the next scan, rather than releasing with no cause, which is final; the interrupt finalizer likewise leaves the claim to the scan.
