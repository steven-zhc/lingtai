# #1144: making the home page's trace account for its time

## The decision the ticket leaves open: shared packages start no spans of their own

Most of what this ticket asks for happens in packages that are not the board: the projection pool (`packages/projector`), the GitHub request (`packages/github`) and the snapshot read (`packages/event-store`). The obvious way to measure them is to call `@opentelemetry/api` from inside each package. **That is the wrong way here, for three reasons.**

1. **The board exports only its own scope.** `OnlyScope` forwards a span only when `span.instrumentationScope.name === this.scope` (`apps/board/src/lib/telemetry.ts:138`), and that scope is `'lingtai-board'` (`:15`). A span started by `trace.getTracer('lingtai-projector')` never leaves the machine. The test would pass and Jaeger would still show the gap.
2. **The daemon exports everything.** The conductor's provider is a bare `BatchSpanProcessor` with no scope filter (`packages/conductor/src/telemetry.ts:206-217`). An api span in `githubJson` or in the projection pool would land in every pass trace and every poll. That is a change to the daemon's traces, which this ticket does not ask for.
3. **`Effect.withSpan` / `Effect.fn` reach nothing on the board.** The board has no Effect tracer bridge: `installTracing` sets only the global api provider and context manager (`apps/board/src/lib/telemetry.ts:188-197`). The bridge lives in the conductor alone (`packages/conductor/src/telemetry.ts:10-27`). So the existing `Effect.fn('github.listOpenIssues')` (`packages/github/src/client.ts:691`) produces nothing in the board's trace today. Adding more of them would also produce nothing.

**So: each package gets a seam that does nothing until a caller installs it, and only the board installs it.** The span itself is always started by the board, under `'lingtai-board'`. The daemon never installs a seam, so its traces are unchanged.

### `apps/board/src/lib/timing.ts`: one new export beside `timed`

Add `traced(name, fn, attributes?)`, a span with no meta entry:

- It is an OpenTelemetry span under the same tracer as `timed`, and it is marked failed on a throw, the way `timed` is (`timing.ts:100-136`).
- It **does not** push into the `measure` scope. `timed` feeds `TimingMeta` (`page.tsx:814-815`). A span per card, per GitHub page or per connection checkout would make that meta grow with the board.
- Attributes are `lingtai.*` keys whose values are numbers, booleans or a project name, as `lingtai.count` is now (`timing.ts:118`).
- Write it as a non-`async` function that returns `startActiveSpan(…, span => fn().finally(…))`. `timing.ts` is not counted by the ratchet (`apps/board` is absent from `packages/domain/unit/effect-ratchet.baseline.json`). The packages below are counted, and every one of them is at `"async": 0, "run": 0`. Their seams must add neither an `async` function nor an `Effect.run*`.

Rule for which helper to use:

- **`timed`** for a read `loadBoard` waits for. These are a handful of fixed names, and the ticket wants them in the meta too.
- **`traced`** for anything that repeats per card, per request or per checkout.

## Where each piece goes

### `loadBoard` (`apps/board/src/lib/board.ts:1598-1645`): `timed`, keeping each `.catch` outside

- `loadAllProjects().catch(() => null)` (`:1603`) becomes `timed('projects.all', () => loadAllProjects()).catch(() => null)`. The span fails and the value is still `null`. `emptyIfUnbuilt` on `tasks.read` (`:1599`) already has this shape.
- `onBoardProjects()` (`:1604`) becomes `projects.onboard`.
- `readStatus()` (`:1634`) becomes `daemon.status`.
- `declaredTriage(…)` (`:1640`) becomes `triage.declared`. Only the call is wrapped, not the `all === null` branch: a skipped read gets no span, for the reason `spend.read` gives at `:1624-1628`.
- `laneProgress(...)` (`:1645`) becomes `board.progress`. Inside it:
  - wrap `boardWriterOrNone()` (`:1505`) as `traced('snapshot.writer', …)`;
  - wrap each `readState(...)` (`:1509`, `:1521`) as `traced('attempt.state', …)`.

  This decides the ticket's "many cards" edge: per-card spans, with no meta entries. If a board ever has hundreds of cards, the spans are the cost and the meta is not, so no count-collapsing is built now. Say that in the commit.

Use short names; the ones above are a suggestion. The ticket asks only that they be short and stable, because the `timed` names show in the meta.

### The queue: per project in the board, per request through a seam in `packages/github`

**Per project.** In `githubQueue` (`board.ts:1310-1318`), wrap each `ask(filter)` as `traced('queue.project', …, { 'lingtai.project': filter.project })`. Put the wrapper inside the existing `.catch`, so a project that fails is a failed span and still `unanswered`.

**Per request.** There are exactly two places that call `fetch` against the API:

- `githubJson`, *"One request to GitHub — the only place a header is built"* (`packages/github/src/app.ts:155-200`);
- `createGhReader().request` (`packages/github/src/gh-reader.ts:28-56`).

Add a module-level observer to `packages/github`, `undefined` by default, that the board sets once:

```
around<T>(info: { method: string; page: number | undefined }, run: () => Promise<{ value: T; remaining: number | undefined }>) => Promise<T>
```

The exact shape is yours. What it must do:

- **The package parses `page` out of the path** (`/[?&]page=(\d+)/`) and hands over the number only. **The path never crosses the seam.** It carries the owner, repo and issue numbers, and 0101 §6 allows no URL on a span. The method and page are enough.
- **`remaining` is read inside the `fetch(...).then`**, from `response.headers.get('x-ratelimit-remaining')`, before the body is consumed. Today `githubJson` throws the headers away.
- **With no observer installed, the code path is the current one**: no wrapper and no extra promise hop.
- **The `signal` stays owned by the one `tryPromise`** (`app.ts:166-167`). Wrap inside its `try`, not around the Effect, or an interruption stops aborting the transfer.

The board installs the observer as `traced('github.request', …, { 'lingtai.page': page, 'lingtai.ratelimit.remaining': remaining })`. Remaining is added after `run` resolves, through `span.setAttribute`; that is one reason to give `traced` a callback that receives the span. Install it from the same place `installTracing` runs (`apps/board/src/instrumentation.ts`), so that with no `telemetry.otlp_endpoint` nothing is installed. That is the ticket's "no provider" edge, met literally.

The board's queue clients come from `ticketSourceOf(filter.recipe)` (`board.ts:1097`). Whichever of the two fetch sites a project uses, the observer covers it. `readBlockers` (`board.ts:1022`) runs inside `askProject`, so its requests become children of `queue.project` without extra work.

### `events.control`: per-call hooks on `readThroughSnapshot`

`readControlOnce` calls `readControl(undefined, { writer })` (`apps/board/src/lib/locks.ts:50`). That reaches `readThroughSnapshot(…, { snapshots, writer })` (`packages/daemon/src/control.ts:117-127`, `packages/event-store/src/snapshot-read.ts:41`).

That options bag is already per call, so extend it rather than adding a global:

- add an optional `observe` (or a pair of `around` functions) to `SnapshotReadOptions`;
- pass it through `readControlEffect`'s `cache` argument.

It must report:

- **the read**: `snapshots.latest`, the tail `readFrom`, and the anchor re-check together as one span. Alternatively, the tail read alone with `latest` as a sibling; do not let it swallow the reduce.
- **the reduce**: `reduceFrom` (`snapshot-read.ts:89`) as its own span.
- **whether a snapshot served it**: a boolean attribute, true when `row !== null && start > 0` *and* the anchor re-check held. A re-check that falls back (`:80-84`) is `false`, because the whole stream was read.

`readThroughSnapshot` returns an Effect and must stay free of `run*`, as its header says (`snapshot-read.ts:17`). So each hook is promise-shaped around the `attempt(() => …)` that already exists, and the reduce is wrapped as `Effect.sync` inside the hook's promise or timed with two clock reads. The board passes the hooks only from `readControlOnce`.

**Do not touch the second `events.control` in `task.ts:1701`.** The task page is out of scope. It is a separate `timed` call that shares the name, and it simply stays coarse.

**The event store's pool is not the projection pool.** `events.control` reads through `@prisma/orm-postgres`'s own `pg.Pool` (`packages/event-store/src/db.ts:21-23`, built at `choose.ts:102`). That pool is **not** the four-connection one the ticket's Evidence names. Its connection wait is out of reach without opening up the Prisma runtime, and this ticket does not do that. The read span is the upper bound on that wait; write that in the commit so nobody reads `events.control.read` as pure query time.

### The projection pool: split `pool.query` into checkout and query (`packages/projector/src/postgres.ts`)

`rows` and `rowsOrNone` call `pool.query(...)` (`postgres.ts:255-266`), which hides the checkout. Rewrite both, **only where an observer is installed**, as:

1. `pool.connect()`, inside the seam (`traced('db.acquire', …)`);
2. `client.query(...)`, with `client.release()` in a `finally`;
3. on a driver error, `client.release(err)`, so a broken client is discarded. `pg`'s own `Pool.query` does this, and the `42P01` branch must still release before it returns `[]`.

With no observer, keep `pool.query`: that is zero change for the daemon and every CLI command. `transact` already does `pool.connect()` (`:276`) and can take the same wrap, but the board never transacts.

The seam is a module-level setter in `packages/projector`, re-exported from its index, which the board sets beside the GitHub one. The span is a sibling **inside** the read's `timed` span (`tasks.read`, `spend.read`, …), parented through the AsyncLocalStorage context manager the board installs (`telemetry.ts:197`). So in Jaeger, the time a read spent waiting on the pool is the `db.acquire` child under that read. That settles the ticket's guess: if `db.acquire` is most of `tasks.read`'s 371 ms, the four-connection pool (`choose.ts:84-90`) is the cause.

The SQLite store has no pool. Leave it alone; it records nothing.

## Edges the ticket leaves to the design, now decided

- **Two renders at once.** Both use the same process pool and the same module-level observers. The observers are stateless and every span parents through the active context, so each render's spans stay in their own trace. A `db.acquire` that waited on the *other* render's queries is exactly the contention this ticket is there to show.
- **An observer that throws.** It must not change what the read returns. The board's `traced` cannot throw except by rethrowing `fn`'s own error, so `traced` must never read the error's message (as `timing.ts:124-126` already refuses to).
- **A `remaining` header that is missing or not a number.** Leave the attribute off. Never write `0`, because that would claim a rate limit that was not seen. "Null is not zero" is the house rule.
- **The `/ queue` meta.** The queue's `measure` timings are discarded (`page.tsx:1012`, `.then(([github]) => github)`). Neither `queue.project` nor `github.request` is a `timed` call, so nothing changes there.

- **The pool.** A fake pool whose `connect()` resolves after a fake delay shows `db.acquire` apart from the query. This needs no Postgres: hand `makePostgresProjections` a pool, or test the split helper alone. A test that needs a live pool belongs to `ON_POSTGRES` (`packages/event-store/test/postgres`) and the integration half, which nothing runs before the merge. The fake-pool unit test is what has to stand in for it.
- **`readThroughSnapshot`.** The memory store plus a fake `SnapshotStore` covers both the served and the fallback cases of the snapshot attribute.

The Jaeger check in Done when (no gap longer than 100 ms) is a person's job after the restart, and nothing in the build can verify it.
