## Design note: #1272, a split's children get the parent's milestone and assignees

The ticket's line numbers are out of date: #1261 moved the code. Today the create is at `packages/conductor/src/split-ticket.ts:394-398`, and it already sends two labels, `[child.kind, PUBLISHING_LABEL]`. Keep both labels exactly as they are and add the two new fields next to them.

### Where the parent is read: the decision the ticket does not make

The ticket says the writer "already calls `github.getIssue(options.issue)`". That call (`split-ticket.ts:273`) is inside `if (first === undefined)`, so it runs only on the first attempt for a wait. A Retry (the "Retry what is missing" action) or a resume after a crash has `first` set and never reads the parent. If you reuse that value alone, a child created on a retry gets no milestone and no assignees. That breaks the ticket's first edge: "*Retry what is missing* reads it again."

Shape:

- Add one cached read per write, the same pattern as `publishedRead`/`alreadyPublished` at `split-ticket.ts:367-382`. For example, `placement: Effect<{ milestone: number | null; assignees: readonly string[] }, Error>` holds the result of the first `github.getIssue(options.issue)` and returns it on every later call in the same write.
- On a first attempt, seed the cache from the `parent` that line 273 already read. That costs no second request, and if the read fails there the attempt stops before `SplitStarted` with "nothing was written", as it does today.
- On a resumed write the cache starts empty. Read it inside `writeChild`, and only when `!found.has(child.key)`, so a retry where every child is already found by marker makes no extra read.
- `yield*` the placement before you build `create`, and keep it **outside** the `create` effect. If it sat inside `create`, a failed parent read would go through the `catchIf` fallback at `split-ticket.ts:404-430`: `findMarked`, then `createLabel`, then the create again. That would misread a read failure as a refused create.
- A failed read is then an ordinary error from that child's step. It goes through the existing step-failure path to `SplitFailed`, so the step stays retryable and no child is opened. That is the third *Done when* item.

Children created on two different write attempts can end up with different values if someone changed the parent in between. That is acceptable: the ticket only asks that values be the same within one write. Do **not** freeze the values into the `SplitStarted` plan. That changes an event payload and its reducer (`splitProgressOf`), which is more than this ticket needs.

### The types: put `milestone` on `Issue`, not on `TicketListing`

- **`Issue`** (`packages/github/src/client.ts:165-185`): add a required `milestone: number | null`, with a doc comment in the style of `assignees` (lines 165-173). `toIssue` (`client.ts:532`) gets `milestone?: { number?: number } | null` in its raw type. Return null unless the value is a safe positive integer, the same rule `parentOf` uses (`client.ts:517-522`).
- **`TicketListing`/`TicketDetail`** (`packages/conductor/src/discover.ts:44-90`): leave them alone. `dbTickets` has no milestone column ("this store tracks no assignee", `db-tickets.ts:27`). Adding the field there would mean a `null` in `toListing` (`db-tickets.ts:207`) and in every listing fixture, for no reader.
  - `Ticket` is built from these types, and `GitHubClient` still satisfies `Tickets` structurally because a wider `Issue` stays assignable to it. `unit/tickets.test.ts` pins that, so it is your check.
- **Fixtures:** only fakes typed as `Issue` (that is, as `SplitClient`/`GitHubClient`) need `milestone: null`. Let `pnpm typecheck` list them; do not grep-replace every `assignees: [`.

### `createIssue`

- **`GitHub.createIssue`** (`client.ts:359`, implementation `:799-811`): the input gains `milestone?: number` and `assignees?: readonly string[]`.
  - Spread each into the `POST` body only when it is present: `...(input.milestone === undefined ? {} : { milestone: input.milestone })`.
  - For `assignees`, also leave it out when the array is empty. An empty array sent to the API is a meaningful value, not an absence, and the ticket says "left out, not sent as null".
  - Make the same change on the promise face, `GitHubClient.createIssue` (`client.ts:429`, adapter `:901`). It stays an Effect, and the ratchet counts nothing new.
- **`Tickets.createIssue`** (`packages/conductor/src/ticket-store.ts:82`) and `dbTickets`: leave them unchanged. The writer's client is `SplitClient = Pick<GitHubClient, …>` (`split-ticket.ts:52-65`), and its doc comment says it is "not `Tickets` (#599 kept links off it)". Nothing that goes through `Tickets` needs the new fields. Widening that interface would only make `dbTickets` take arguments it throws away. This puts the ticket's "`dbTickets.createIssue` ignores the two optional fields" edge out of reach rather than handling it in code.

### In the writer

At the create (`split-ticket.ts:394-398`), add `...(p.milestone === null ? {} : { milestone: p.milestone })` and `...(p.assignees.length === 0 ? {} : { assignees: [...p.assignees] })`. Copy nothing else from the parent: no other labels. Update the module doc (`split-ticket.ts:1-29`) with one line: a child is opened with the parent's milestone and assignees as read in that write, and a child found by marker keeps what GitHub holds.

GitHub refusing an assignee or a closed milestone needs no new code. It goes through the existing fallback, `findMarked` then `createLabel` then create once more, with the same request. If that also fails, "the first error stands" (`split-ticket.ts:414-417`), so GitHub's message reaches `SplitFailed.detail`. Do not add a retry without the assignee.

### Tests (`pnpm test`, no integration half needed)

- **`packages/conductor/unit/split-ticket.test.ts`:**
  - The fake's `getIssue` for the parent returns `milestone: 3, assignees: ['a', 'b']`. Assert every recorded `createIssue` input carries both.
  - A parent with neither: assert the input has neither key (`'milestone' in input === false`), which is the writer-level claim.
  - A resumed write: run a first write whose first create succeeds and whose second step throws, then run a second write. Assert the second write's create carries the parent's values. This is the test that catches the gap described above; without it nothing does.
  - A resumed write whose parent read fails: assert no `createIssue` call, a `SplitFailed`, and that a later write converges.
- **`packages/github/unit/`**, wherever `toIssue` is reached through a faked `send`:
  - `milestone: { number: 3 }` reads as `3`; an absent or `null` milestone reads as `null`.
  - The body sent by `createIssue` leaves out both keys when they are not given.

`effect-ratchet.baseline.json` stays unchanged: the new read is a `lift(() => github.getIssue(...))` inside the existing `Effect.gen`.
