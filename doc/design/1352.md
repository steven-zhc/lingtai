## Design: a red build of a clean merge goes to the conflict agent (#1352)

The ticket gives the shape. This note covers three places where following it literally would loop, lose the merge's shape, or record the wrong ending, plus the smaller decisions.

### 1. The sync's build step must record the build step, or it burns a round on every serve

The ticket says a resolved red at `build` is recorded as `BranchSynced { how: 'resolved' }`, "as the sync step does for a conflict". Read against the reducer, that loops:

- `reducePrEvent` maps `how: 'resolved'` to the **sync** step: `const step = d.how === 'clean' ? 'build' : 'sync'` (`packages/domain/src/pr.ts:218`). The comment there says *"`already` and `resolved` are the sync step's own record"*.
- `withStep` keeps an existing record and never replaces it: `state.steps.some((r) => r.step === record.step) ? state.steps : [...]` (`pr.ts:132`). So the `sync` record keeps the clean red merge as its `headSha`, and no `build` record is added. Only `target` moves to the resolution (`pr.ts:222`).
- The next serve runs `buildStep` again. It builds `merge = synced.headSha` (`packages/conductor/src/pr-sync.ts:207`), which is the old red merge, not the target. That build is red again and buys another round, every serve, until the rounds are spent on a merge that was already resolved.

**Decision:** in the reducer, `BranchSynced` marks `build` when `how` is `clean`, **or when `sync` is already among `state.steps`**. A sync-step record never has `sync` there yet: the record goes in place of `PrStepDone` (`packages/conductor/src/pr.ts:175-178`). A build-step record always has it. Add a `reducePrEvent` unit test for this: sync recorded clean, then a `BranchSynced resolved` → `steps` holds `build` with the resolution's sha, and `target` equals it. Leave `adopted` as it is; the red path never runs for an adopted head.

The first Done-when box needs an extra assertion for this trap: a **second** serve after the resolution appends no second `SyncRoundStarted`.

### 2. The round is told which merge to stand up, and its parents are checked

`ConflictAsk.why` for a red is `{ kind: 'red'; merge; command; evidence }`, with one field added to the ticket's shape: **`merge` is the commit to stand up**. Its parents must be exactly `[start, commit]`, which the round checks once it is stood up. A mismatch answers `unknown` (the same shape `pr-resolve.ts:272-276` answers for a merge that could not be stood up), not a refused round.

The new `ConflictResolver` port method (`packages/conductor/src/pr.ts:147`) stands a worktree detached at `merge`. It uses the same `pr-sync-…` / `pr-back-…` naming and is never released by the round, like `standMerge`. The live adapter sits beside `standMergeUp` (`packages/repo/src/pr-sync.ts:147`) and is wired in at `apps/cli/src/pr-ports.ts:118`.

**Only the integration half reaches that adapter.** The unit stand-in is the fake resolver in `packages/conductor/unit/pr-resolve.test.ts`, which must assert that a red round calls the new method and never calls `standMerge`.

In `oneRound`, a red round differs from a conflict round in these places only:

- **Skip the "no longer conflicts" check.** `stood.paths.length === 0` answers `unknown` today (`pr-resolve.ts:278-283`); a clean merge has no paths by definition.
- **`theirs` is the whole merged range.** It is `git log start..commit` with no `-- paths` (today's is `pr-resolve.ts:181-189`).
- **`ours` is matched against the build's output.** Today `oursOf` keeps tickets whose merge touched a conflicted path (`pr-resolve.ts:157-158`). For a red round, keep the tickets that have any touched path appearing as a substring of `evidence`; if none match, keep every ticket. `touched` lists the matched paths, or every touched path in the fallback.
- **`ConflictEnd.paths`** for a red end is the union of the matched paths, or `[]`.

The graph check, the amend that rewords to `ask.subject` (`pr-resolve.ts:373-374`), the build and the `--remerge-diff` review stay unchanged. Two consequences follow, and both are wanted:

- An agent that **does nothing** passes the graph check, because the clean merge already has `[start, commit]`. It is then refused at `build`, which is correct.
- A commit **on top** has parents `[merge]`. It is refused at `answer` by the existing message (`pr-resolve.ts:365-369`). That covers the Done-when box about a commit on top, with no new code.

The briefs: add a red variant of `prConflictBrief` and of `sidesOf`'s headings (`pr-conflict-brief.ts:50-72`). Today's headings say *"the tickets whose code conflicts"*, which is wrong for a red. `prReviewBrief` gets the same variant, telling the reviewer the diff is the agent's change to a clean merge that failed `<command>`.

### 3. The merge back: the red after a resolution is a synthesized merge, not the `moved` one

**The first turn's red (`pr-sync.ts:400-408`).** Return a new `Back` variant (or widen `conflict` to carry a `why`) so the rounds run **outside** the lane. This matches `pr-resolve.ts:13`: *"A round runs outside any lane, and pushes nothing."* Before leaving the turn, `update-ref backRef(n) <merged.sha>` so the mirror keeps the commit. `resolveBack` already drops that ref in its `ensuring` (`pr-sync.ts:600`).

**The second turn's red (`pr-sync.ts:516-524`).** This is the Done-when case *"conflicted, resolved in one round, then built red"*. It can only happen here. The sync's own resolution is built inside its round (`pr-resolve.ts:377`), and `buildStep` skips it (`pr-sync.ts:203-205`).

The red commit there is `moved`, whose parents are `[resolution, personalNow]` (`pr-sync.ts:504-509`), not `[start, commit]`. **Decision:**

1. In the mirror, write `git commit-tree <moved>^{tree} -p <personalNow> -p <prHead> -m <backSubject>`.
2. Return `{ kind: 'again', start: personalNow, why: { kind: 'red', merge: <that>, … } }`.

That commit is the same tree, shaped like a merge of `prHead` into `personalNow`, under the subject the lost-record search greps for. Its second parent is `prHead`, which the search matches on (`pr-sync.ts:342-362`). Rounds are keyed by `(merging, commit)` and `commit` is still `prHead`, so this is round 2 of the same commit (`packages/domain/src/pr.ts:658`).

Re-merging `prHead` into `personalNow` from scratch would re-conflict on what round 1 resolved. That is why the conflict `again` restands the merge with markers and the red `again` must not.

**When the rounds are spent**, `resolveBack` records `failed('red', …)` when the last ask's `why` was red and `failed('conflict', …)` otherwise. Today it is always `'conflict'` (`pr-sync.ts:556-560`).

### 4. The sync's spent red waits, and is not grantable

On spent, `buildStep` waits `sync-red` with the build's words, `spentSentence(end)`, and the `ConflictEnd` attached as `PrWaiting.conflict`.

**Three more rounds stays refused for `sync-red`**: `grantTransition` answers *"rounds buy an agent only for a conflict"* (`packages/domain/src/pr.ts:751-755`). `prWaitOf` draws `sync-red` as a plain wait (`packages/domain/src/pr-wait.ts:75`). Both are unchanged, per Out of scope.

A *check again* re-serve with the same `main` commit merges clean again, and `resolveRounds` returns `spent` at once (`left === 0`, `pr-resolve.ts:547`). It spends nothing.

`locked` maps to `wait('sync-locked', …)` and `unknown` to `sync-unknown`, as at `pr-sync.ts:162-165`.

### 5. `SyncRoundStarted` gains an optional `why`

Add `why: z.enum(['conflict', 'red']).optional()` (`packages/domain/src/events.ts:2699`), with absent meaning `conflict` so old events still read. This is how the PR page can draw a red round "with its reason" (the ticket's stale-page edge) without parsing `said`.

Update its `@summary` and regenerate `doc/events.json`. `SyncRoundRefused` is unchanged. Counting stays one event per round, so `syncRoundTransition`'s `round === used + 1` (`pr.ts:658-659`) still holds across a conflict round followed by a red round.
