# #1499 — design note

## Where the pieces go

**1. A second, pure component for global pages, `PagePlace`, in `place-line.tsx`. Don't add a mode to `PlaceLine`.**

`PlaceLine` always draws a project crumb (`place-line.tsx:126`). Its `tail` is a single string (`:111`). `Lingtai / Setup / Repository` needs two crumbs and no views. Extending `PlaceLine` would mean a sentinel project value plus a `tail` that also accepts an array.

Instead, export this from the same file:

```ts
PagePlace({ crumbs: readonly string[] })
```

It emits the same markup as `PlaceLine`: `<span className="place">`, then a `slash` span and a `crumb` span for each entry. That way the CSS and any structural assertion match both forms.

- It draws no `View`, so the page has no `data-go`.
- It draws no `details.filter`.
- It imports nothing new. The server-only boundary in `place-line.tsx:5–14` stays as it is.
- The crumbs are plain text, not links. There is no `/setup` index route: `app/setup/` holds `claude-token`, `github-app`, `repository`, `wizard`, `terminal.tsx` and `gh-machine.ts`, and no `page.tsx`.

| Page | Call |
|---|---|
| `/report` | `crumbs={['Report']}` |
| each setup step | `crumbs={['Setup', 'Repository' / 'GitHub App' / 'Claude token']}` |
| `TerminalScreen` | `['Setup', 'Repository']` |
| `not-set-up.tsx` | `['Setup']` |

**2. Generalise `RecipeBar` into the one project bar. Don't write a third copy of the menu wiring.**

`recipe-bar.tsx:27` already builds `Bar` + `BarActions recipe={false}` + `PlaceLine` + `Projects`. It is a file of its own precisely so that it can be asserted in the unit half (`recipe-bar.tsx:5–7`). It has two limits:

- it requires `project: string`;
- it types `here` as `'recipe' | 'prs'`.

`/landed` and `/backlog` need:

- `project: string | undefined` (`all projects`);
- `here: 'tickets' | undefined`. Backlog selects no view, so `here` is left undefined and no `View` gets `view on` (`place-line.tsx:77–79`).

Widen the props to that, and keep `RecipeBar` as a name or re-export so the existing call sites and `unit/recipe-bar.test.tsx` don't churn.

- **`Bar`'s own `here`:** pass it only for `recipe`. `Bar` uses `here` only for Report's `aria-current` and for `BarActions` (`bar.tsx:68–70`).
- **Views for all projects:** use `viewsFor(undefined)`, which returns `Tickets` alone (`place-line.tsx:43–44`).
- **Views for a project:** the page passes `await placeViewsOf(project)`, as the PR page does (`pr/[project]/page.tsx:82`).

**3. Pause: guard the `actions` you pass. It is the trap in this design.**

When `actions` is given, it replaces `registered` (`bar.tsx:38–40`). `pauseSlot` returns a button for any defined project, registered or not (`lock-banner.tsx:59–63`). So passing `pause={await pauseSlot(only)}` straight through would put Pause on an unregistered project's landed page. Today that page has no Pause, because `/landed` passes `registered` (`landed/page.tsx` at the `<Bar>`).

The rule:

- **Registered project:** `actions={<BarActions project={p} pause={…} recipe={false} />}`.
- **Unregistered project, or all projects:** `actions={null}`. `Bar` tests `actions !== undefined`, so `null` draws nothing: no empty `pacts` span and no stray `vsep`.

The PR page has the same gap today. Fixing it there is out of scope; don't widen it.

**4. Reading the menu's inputs.**

`LandedBody` (`landed/page.tsx`) and `BacklogBody` (`backlog/page.tsx`) each need what `pr/[project]/page.tsx:71–88` reads: `readRegistered`, `onBoardProjects`, `readProjectLocks`, `placeViewsOf` and `pauseSlot`, combined with `filterOptions`, `lockMap` and `sandboxStates`.

Put that in one server helper, called from both pages: `readPlaceBar(project)`, in `lib/`. It returns the generalised bar's props plus a `listingError: string | null`.

- **Errors:** each read is caught to a value, the way the PR page does it.
- **Failed listing:** the page draws *"The list of projects could not be read: …"* under the `LockBanner` (`pr/[project]/page.tsx:104–107`).
- **Landed only:** `LandedBody` already reads `readRegistered()` and swallows a failure (`.catch(() => [])`). Let the helper's read replace it, so a failed listing is said once and is never an empty menu.
- **Ratchet:** follow whatever form the PR page's reads take. If the helper adds a new `async` function, `effect-ratchet.test.ts` will count it. Write it as an Effect, or keep the reads inline in the two pages. **Do not raise `effect-ratchet.baseline.json`.**
- **The PR page:** leave its inline reads alone. Moving them onto the helper is tidy-up and not this ticket.

**5. Which project the landed page is in.**

`/landed` still reads the project from `landedQuery(params, …)`. `LandedBody` does `{ ...given, project }`, so the path segment wins (`landed/page.tsx`, `LandedBody`). Feed the bar `only`, which comes from `query.project`. Don't read `?project=` in any new code.

`/report` keeps its `only` for Pause and for the Report link's `withProject` (`bar.tsx`, the Report `Link`). It draws no project crumb, whatever is in its query.

**6. Choosing a project from the menu leaves the page.**

`ProjectRows` links to `homePath(p)` (`projects.tsx:89`, `:100`). Picking a project on `/landed` lands on that project's Tickets, not on its Landed page. The PR page and the recipe page behave the same today. Accept it here. A per-page target is a backlog finding, not this ticket.

## Chips and facts

- **Chip spans:** delete the three `chip.tone`/`chip.label` spans. Keep the reads:
  - `backlog/page.tsx` still needs `chip.current` and `chip.title` for the *nothing open* sentence.
  - `/report` still computes `chip`. If nothing reads it once the span is gone, drop the local variable, not the function.
  - `/landed` loses its only use of `chip`. Drop the local variable and `projectionChip`'s import there.
- **Backlog first line:** `{open.length} open · from review findings that passed a gate` becomes a `<p>` as the first child of `.detail-body`, 10px mono `--muted` (`the-board-style.md:93–97`). Use the class the other untitled pages use for that line, if there is one.
- **Landed footer:** `LandedBody` returns a fragment, `<main>…</main><FooterFetched />`, the shape `/report` has (`report/page.tsx`, the end of the page). Remove `/landed` from CLAUDE.md's *not `/landed` or `/setup`* list.

## Tests

The pages are async and read the store, so test the bars, not the pages. The unit half can render two things:

- **The generalised project bar**, given props. Cover:
  - a registered project: Pause present, no `Recipe` in `.topnav`;
  - an unregistered project: no Pause, no `pacts`;
  - all projects: crumb `all projects`, views `Tickets` only;
  - `here="tickets"`: `aria-current` on Tickets, and `data-go="t"` present;
  - `here` undefined: no `view on`.
- **`<Bar><PagePlace …/></Bar>`** for Report and Setup. Cover:
  - no `details.filter`, no `data-go`;
  - Report's link carries `aria-current="page"` when `here="report"`;
  - no `chip` class and no `current` text in `.bar`;
  - no `Setup` link.

**The step names are only asserted if the bars live in importable files.** Put each setup page's bar and the backlog bar (`/report`'s too, if you like) in a small exported component, beside the page or in one `global-bars.tsx`. Then the tests can import the actual bars and their crumbs. Otherwise the step names are untested strings inside pages that cannot be rendered.

**`not-set-up.test.tsx` can render `NotSetUp` directly.** Extend it to assert `Setup` as a crumb, and keep its server-component claim (`:70–71`).

**Leave `unit/place-line.test.tsx:72` as it is.** The task layout still draws that bar.

**The person-check at 1440px is the only check on the layout.** `apps/release/integration/build.test.ts` is the only thing that sees a server import reaching a client graph, and it is out of reach in a pass. So keep every new bar file free of `@/lib/*` server imports, the way `recipe-bar.tsx` is. The reads live in the page.
