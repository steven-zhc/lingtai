## Design note: #1249, redo any crash or unreadable answer by rule

The change touches two pure rules in `packages/domain/src/failure/respond.ts`, the deletion of the per-arrival flag in `run-attempt.ts`, and one predicate in `conduct.ts`. Three things here are not obvious from the ticket. First, the account-limit check has to live **inside** `rerunInPlace`. Second, a fixer that committed and then crashed is affected too. Third, an unreadable answer stops offering a fix round.

### The ticket's line numbers have moved

Some of what the Fix row lists is already half gone. Today:

- `askedAgainOn` is at `packages/domain/src/attempt.ts:779-785`. **Nothing in `conduct.ts` calls it any more.** `git grep askedAgainOn` finds only its definition and `packages/domain/unit/cut-off-call.test.ts:4,35-41`. The work is to delete the function, its export and that `describe`.
- `askingAgain` / `arrivedAskedAgain` are at `run-attempt.ts:1459-1461`. They are set at `:1997`, `:2226-2227` and `:2410`, and passed to `offerFor` at `:1753`.
- `emitStepRedone(…, askedAgain = false)` is at `:1463-1474`. `redoStep`'s `askedAgain?` is at `:1652` and `:1656`, and the `askedAgain: offer.proposal._tag === 'AnswerUnreadable'` is at `:2015`. Remove all three, so that `StepRedone` is never written with `askedAgain` again.
- `offerFor`'s fourth parameter `askedAgain = false` is at `respond.ts:656`. Remove it. The board's `apps/board/test/visual-waiting.ts:123` already calls it with three arguments.
- Keep `StepRedone.askedAgain: z.boolean().optional()` (`packages/domain/src/events.ts:1691`) so that old rows still parse. Change its doc comment to say that nothing reads it since #1249. Do not delete the field.

### 1. `rerunInPlace` owns the account-limit check

The crash rule runs in `run-attempt.ts:2406-2420`, **before** `conduct.ts` ever sees the `AgentCrashed`. The account lock happens in `conduct.ts:6261-6264`, after the walk has ended:

```ts
const walled = reason._tag === 'AgentCrashed' && reason.cause === 'crash' ? wallOf(reason.detail) : null
```

So if `rerunInPlace` simply stopped checking `transient`, a crash on the account's limit would be redone three times inside the walk. Only after that would it reach the lock — exactly the trap in the ticket's *Watch out* row.

`classify` already separates the two cases. `packages/domain/src/failure/classify.ts:41` gives `{ platform: 'runtime'; kind: 'account-limit' | 'transient'; runtime }`, and `wallOf` is just `said?.kind === 'account-limit'` (`conduct.ts:346-349`). So the rule stays pure and stays in domain:

```
rerunInPlace(cause, detail, spent):
  cause !== 'crash' or spent >= BOUNDS.stepRedos → null
  classify(runtime, detail).kind === 'account-limit' → null   // §11's, checked first
  otherwise → { wait: BOUNDS.stepRedoWaits[spent], expected: kind === 'transient' }
```

- **`expected` is the only thing the transient list still decides.** It changes the words, never the move. At `run-attempt.ts:2418` the redo's `why` is `reason.detail` today. Make it say which kind of crash it was: a transient API error, or *a crash no rule recognises* (0108 §12's phrase). Keep the runtime's own words in `said`.
- **An empty `detail` is a crash and is redone.** `classify` returns null for it, so it falls to the `otherwise` line.
- Keep the step guard at `run-attempt.ts:2406` (`design | implement | review`). `AgentCrashed` can also come from `proposed` and `merge` (`packages/domain/src/attempt-next.ts:443`). But 0108 §12 *Where* says *"`redoStep` is used at `prepared`, `design`, `implement` and `review`. `merge` has `retryLanding`"*, so those two keep holding.
- When `stepRedos` is spent the walk ends with today's `WaitOnPerson AgentCrashed` (`run-attempt.ts:2422-2424`). That is this ticket's `askPerson(limit)`. **Do not add a new wait reason.** The redos that were spent are already on the log as `StepRedone` rows.
- The account-limit test belongs at unit level, against `rerunInPlace` with Claude Code's and Codex's limit sentences from the table. Add a second test through `runAttempt` that asserts no `StepRedone` was emitted and the end is `AgentCrashed` with the detail intact, which is what `conduct.ts:6261` reads. If a regression happened, the log would show it as `StepRedone` rows whose `said` is a limit sentence.

### 2. A fixer that committed and then crashed is a cut-off

`conduct.ts:5334` decides whether the walk sees a fixer's crash at all:

```ts
const cutOffTransient = fixed.failure?.kind === 'crash' && transientSaid(fixed.failure.detail)
```

It is commented *"the walk reruns it in place, so the commit is not the end of the round"* (#1201). A fixer that committed and then crashed with an unknown sentence goes on to build and review today. If that line is left alone, it never reaches the new rule.

Make it `fixed.failure?.kind === 'crash'`, and delete `transientSaid` (`conduct.ts:351-355`), which has no other caller. `cutOffByWall` (`:5337`) is unchanged and still checked in the same `if`.

### 3. `AnswerUnreadable` is a rule's, and it no longer offers a fix round

In `offerFor`'s `AnswerUnreadable` cell (`respond.ts:768-780`):

- Offer `ask-again` whenever `stepRedos` is left. There is no `raw.trim() !== ''` gate and no `askedAgain` gate.
- **Also drop the `fix-lines` and `restart` candidates.** 0108 §12 says a step that did not finish *"judged nothing, buys no `fixRefusal`"*, and *"with none left, the next one is `askPerson(limit)`"*. §18's table gives `answer-unreadable` exactly one answer: *"A rule: `redoStep` (§12)"*. The ticket's *Want* also ends at `askPerson(limit)`.

If those candidates stayed, a non-empty unreadable answer would still buy a judged round once its redos were spent. That is the inconsistency this ticket removes. With them gone, the spent offer is only `hand-to-person`, which is what `ReviewEmpty` already does (`respond.ts:747-753`): *"only a person is on offer and no judge is asked"*.

That changes `packages/conductor/unit/attempt-steps.test.ts:1958-1984`. It expects one `ask-again`, then a judge `when: 'answer-unreadable'`, then a wait. After this change it should see three `ask-again` routes, then a wait, and no judge. Rewrite it. Do not delete it.

The rule's place in `run-attempt.ts` is unchanged. `rerunCandidate` (`:1816-1819`) still answers before `replyFor` or any judge, and `RerunStep` (`:1993-2017`) still runs the step whole through `redoStep`. Only the `askingAgain` line goes.

### What a missing receipt is

The ticket defines it as `no-structured-answer`, and that already arrives as `AnswerUnreadable`. `packages/actions/src/agent-action.ts:481-490` returns `{verdict:'failed', unreadable:true}`, and `packages/conductor/src/step-outcome.ts:141-142` maps that to `AnswerUnreadable`.

One correction to the ticket: that path's `evidence` is **not** empty. It is *"the reviewer's runtime could not fit its answer to the schema: …"*. So the empty-`raw` test is a constructed `AnswerUnreadable{raw:''}`. Write it at `offerFor` level, and once through `runAttempt` with a canned reviewer whose result is `failed`, `unreadable`, with empty evidence. **Add no new detection code.** Today's `raw !== ''` gate was the only thing that sent an empty answer to a person.

### Docs

`packages/domain/src/failure/doc.ts:39` says *"a sentence on no row is a crash and holds for a person"*. That is now false. Rewrite it: *a crash on no row is redone too, up to `stepRedos`; the row only says the redo is expected to clear it*. Check the Codex block for the same sentence. Then run `pnpm docs:errors` (`packages/domain/scripts/platform-errors.ts`) to regenerate `doc/design/platform-errors.md`.

`packages/domain/unit/failure-classify.test.ts` compares the generated file with what is checked in, so forgetting to regenerate fails the unit tests. No ADR is edited: 0108 already says all of this. Update the comments at `respond.ts:592-595` and `BOUNDS.stepRedos` (`:579`), and `run-attempt.ts:2402-2404` and `:1816-1818`, so they stop saying *transient only* and *once per arrival*.

### Edges the ticket leaves open, decided here

- **A crash redo and an `ask-again` in the same attempt** both spend the one `stepRedosSpent` (`run-attempt.ts:1655`). There is no per-step and no per-arrival count: three in total, then a person.
- **A continuation after a person's answer** starts from `options.from`'s `stepRedosSpent`. With no flag left there is nothing to carry. It gets whatever `stepRedos` are left in the attempt, as 0108 §12 says (*"counted over the whole attempt"*).
- **Cost to later tickets.** Tests that assert *a non-transient crash waits for a person* become *a crash waits after three redos*. Each redo waits 1, 5 and 15 minutes, so those tests must pass `stepRedoWaits` (or the `options.stepRedoWaits` override already used at `run-attempt.ts:1823`) set to zero. A test that sleeps 21 minutes is the trap. No ratchet baseline moves: this is pure code plus deletions, and it adds no `async`.
