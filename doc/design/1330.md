# Design: #1330, the 0.16 reference pages and the upgrade page

The ticket's list of pages is right. Four facts in the worktree change what goes on them, and the implementer would otherwise work them out one review round at a time.

## 1. Write from ADR 0131 and `pr.ts`, not from 0130 §5–§6

`doc/decisions/0131-a-pr-goes-from-draft-to-merged.md` was written today (2026-11-22). Its header says *"Takes over 0130 §5 and §6, which now point here."* The ticket cites 0130 §5 for the PR rules and for the App permissions. Read those sections in 0131 instead, and check every sentence against the code. The header's *"not yet built"* is wrong: the code builds it.

- **The steps of In progress** are `IN_PROGRESS_STEPS` (`packages/conductor/src/pr.ts:717`): `sync`, `build`, `outside` (others' commits on the PR branch, #1353), `summary`, `push`, `open`, `ci`, `topup`, `ready`. A freeze comes first (`freezePr`, `:733`). That is 0131 §2's table of ten, not the ticket's *"submit, sync, build, CI and summary"*.
  - *A PR's life* in `concepts.md` gives the steps in the person's words and in this order: freeze, bring `main` in, build, take others' commits, summary, push, open as a draft, CI, top up, mark ready.
  - It does not number them as ten. The ten steps of a ticket (`the-pass.html`) are a different thing, and a reader would confuse the two.
- **The ways out of Waiting on you** are commands that exist: `lingtai pr submit`, `pr retry`, `pr rounds`, `pr back` (`apps/cli/src/commands.ts:154-165`). 0131 §2 describes them as *give the agent more rounds*, *check again* and *take it back to Draft*.
  - *Back to Draft* closes the PR on the code host and leaves its tickets in Draft. The ticket's Fix only has *closed without merging*, so add this one.
  - Name the verbs in prose. Their reference is `doc/cli.md`, which already lists them (17 hits for `lingtai pr`; `--base` refused at `:47`). It is generated: link to it, never edit it.
- **What a squash does.** `pr.ts:1233` notes that *"a squash merge deletes the PR branch"*. The squash sentence in `github.md` stays 0130's: it still counts as merged, and it loses one ticket = one `git revert`. Do not claim anything more about how a merge is detected.
- **`pr-fix` ranks first only in team mode** (`packages/conductor/src/discover.ts:146`, `queue.ts:40`: *"in team mode `lingtai:pr-fix` ranks ahead of `kinds`"*). The glossary and `concepts.md` must say *in team mode*.
- **A host that is not GitHub** opens nothing: `prHostOf` (`pr.ts:241`) answers `none`, and the PR is recorded In review, unfollowed (`:428`). Put one line in `github.md` or the glossary's *PR* entry, so nobody reads it as a broken state.

Leave the ADR status lines and the *"proposed; not yet built"* status column in `doc/README.md:116` alone. They are ADR text, which is out of scope. Mention the stale status in the commit body, without a closing verb.

## 2. The permissions table exists twice, and both copies are wrong

`REQUIRED_PERMISSIONS` (`packages/github/src/app.ts:266-274`) is now seven rows. `checks` and `statuses` were added at `read`, each with a `why` (*"reading a PR's check runs"*, *"reading a PR's commit statuses"*). The `issues` row's `why` now says *`lingtai:*` labels*.

The table is copied by hand in two places, and each copy should read the same as the code, row for row and with the same `why` text:
- `doc/github.md:44-48`, which the ticket names.
- `doc/operating.md:305`, which it does not. That page says *"set exactly these five"* and *"`lingtai add` checks these five by name and refuses"*. Both sentences are false now, and this is the page a person follows while editing their App. Fix it in the same commit.

The upgrade page's permissions step follows `gapRemedyLines` (`app.ts:302-312`). The order matters, because *"an installation can only accept what the App already asks for"*:
1. Add the two permissions on the **App's** permissions page, `github.com/settings/apps/<slug>/permissions` (an organisation has its own URL).
2. Accept them on the **installation**.
3. Re-run.

A person who only looks at the installation sees nothing to approve. Tell them to run `lingtai add` (or `lingtai doctor`) afterwards to confirm the gap has closed, rather than promising which command refuses: the refusal comes from `permissionGaps` (`:285`), which the code runs at add time.

## What the upgrade page says, in this order

1. **Nothing changes until you choose to.** A recipe that names no `mode` is solo (`packages/recipe/src/recipe.ts:3143-3148`, `mode: z.enum(['solo','team']).optional()`). Check that solo is what the code defaults to when `mode` is absent before writing it as a promise. A *new* project defaults to team (`README.md:116`); say both.
2. **The App permissions**, as in §2 above. Every installation needs this step, solo projects included.
3. **The label rename**, in #1327's order: relabel the held issues, then make `exclude` list both labels, then drop the old one. Each step comes with the reason a ticket would be unheld if the order were reversed. Take the procedure from `doc/design/1327.md` and #1327, not from memory.
4. **The recipe's old spellings.** Taken from `resolve.ts:331-395`:
   - `repo.base`, `steps.admit[0].worktree.base` and `take: both` (→ `all`) are named by `lingtai doctor`;
   - `lingtai doctor --fix` (`apps/cli/src/doctor.ts:34`, `commands.ts:661-663`) rewrites them as a new recipe change;
   - after that they are refused, and `init --base` is refused in favour of `--main` (`cli.md:47`).
   - The daemon loaded the old recipe, so tell the reader to restart afterwards (`lingtai restart`).
5. **Switching to team.** Set `mode: team` and `branch.personal`. Check the mode switch #1328 refuses, and how it words the refusal, against the merged code before you describe it.
