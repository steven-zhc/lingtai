# Design note: #1159, doctor's sandbox rows

## Where it goes

- **`packages/sandbox/src/install.ts`** (new, no srt import, exported from `.`): the install table, `installFor(platform)` → `{ missing: string[], command: string }` or `undefined` for a platform that cannot sandbox at all. Linux names `bwrap`, `socat` and `rg`; macOS names `rg`. #1160's wizard reads it too. It sits beside `checkHost` (`packages/sandbox/src/sandbox.ts:96`) and not in `apps/cli`, because the ticket says the table "lives once, in `@lingtai/sandbox`".
- **`apps/cli/src/sandbox-canary.ts`** (new): the canary as an Effect over two seams, `Pick<SandboxApi, 'wrap' | 'policyOf'>` and a small `CanaryIo` port. `CanaryIo` makes a temporary directory, writes a file, removes a path, and spawns an argv with an env and a timeout to get back `{ exit, stdout }`. The live `CanaryIo` and the live composition are in the same file. Production gets the `SandboxApi` from `processSandbox` (`packages/conductor/src/sandbox-service.ts:19`), the same memoised, never-closed service `conduct.ts` and `run.ts` already use (`apps/cli/src/conduct.ts:278`, `apps/cli/src/run.ts:494`). Do **not** build `SandboxLive` with a scope of its own. The file's own comment gives the reason: `makeSandbox` "resets it when its scope closes" (`sandbox.ts:122`), and `lingtai restart` runs doctor inside a process that goes on to do more.
- **`apps/cli/src/doctor.ts`**: the three row builders, the `DoctorReach` members, the steps in `runDoctor`, and a new `['Sandbox', ['sandbox']]` entry in `AREA_OF` (`doctor.ts:3869`), placed after `Projects`. The canary and the host row are about the machine, not a project, so the `Projects` heading would put them under the wrong title. The per-project rows are named `sandbox: <project>`, so a person can still find them.

`apps/cli` is at `{ "async": 0, "run": 0 }` in `effect-ratchet.baseline.json`. So the live `CanaryIo` uses `Effect.tryPromise` around `fs/promises` and an `Effect.callback`-style wrapper around `child_process.spawn`. It has no `async` function and no `spawnSync`, which is what `probeSeaBuild` uses (`apps/cli/src/sea-build.ts:59`), so do not copy that file.

## `DoctorReach`: one host seam, not two

`DoctorReach.sandboxHost?: HostAnswer | 'skip'` already exists (`doctor.ts:1262`), and `recipeLookup` hands it to `currentRecipeEffect` (`doctor.ts:1444-1452`). Narrow it to **`sandboxHost: HostAnswer`, required**, and use it for the host row as well. Do not add a second host seam. With two seams, the host row and the recipe rows could disagree about *can* in the same report. `checkHost`'s comment rules that out for the resolver and `wrap` ("the one question the resolver and `wrap` both ask, so they cannot disagree about *can*", `sandbox.ts:95`), and the same reasoning applies here.

Add **`sandboxCanary: () => Effect.Effect<CanaryResult>`**, also required. The `reach` parameter's type becomes `Partial<DoctorReach> & Pick<DoctorReach, 'sea' | 'sandboxHost' | 'sandboxCanary'>`.

**The `reach` default goes away.** Today it is `{ sea: probeSeaBuild }` (`doctor.ts:3481`), a default that does ask the real machine. The ticket says no default asks the real host. The only production caller is `doctorReportEffect` (`doctor.ts:3802-3813`), and it names all three:

- `sea: probeSeaBuild`
- `sandboxHost: hostHere` (`packages/conductor/src/projects.ts:220`, which is already the lazy srt import over `hostCanSandboxHere`)
- `sandboxCanary: liveCanary`

`apps/cli/integration/doctor.test.ts` calls `runDoctor(env({}))` about 23 times and relied on the default. Give it a shared fake from `apps/cli/test/` that answers *cannot* and *not run*. `apps/cli/tsconfig.json` includes `integration`, so `pnpm typecheck` finds every caller that misses it, although the build never runs those tests. The three unit files that build a `reach` (`apps/cli/unit/doctor.test.ts:105`, `doctor-progress.test.ts:44`, `log-predates-hold.test.ts:57`) gain fakes that count their calls.

`recipeLookup`'s own parameter keeps `HostAnswer | 'skip'`, because the per-project rows call it with `'skip'`.

## The canary

```
type CanaryResult =
  | { kind: 'held' }
  | { kind: 'leaked'; which: readonly ('read' | 'network')[] }
  | { kind: 'could-not-run'; why: string }
```

The row's `name` is `sandbox: canary`. `held` gives `ok`, and the other two give `fail`. The function does these steps in order:

1. **Read the host facts** with `readHost` (`packages/sandbox/src/host.ts:18`). They give `stateDir` and `cacheDir(host, 'lingtai-doctor-canary')`. A failure here is `could-not-run`.
2. **Make three directories.**
   - The worktree and the mirror are created with `mkdtemp` under `os.tmpdir()`.
   - The planted directory is created with `mkdtemp` under `<stateDir>`, as `doctor-canary-XXXX`.
   - All three directories and the cache directory are removed in an `Effect.acquireRelease` finalizer, so an interrupt or a timeout still cleans up. Remove the cache directory before the first wrap as well, which covers the "leftover is removed by the next run" edge.
3. **Check the planted path at runtime.** Compute `policyOf({ project, worktree, mirror })` and check, with `within` (exported from `protect.ts`), that the planted path is under `denyRead` and under no `allowRead` root. If it is not, return `could-not-run`.
   - `allowRead` overrides `denyRead` (`policy.ts:121`, "allowRead overrides denyRead (017)").
   - If an operator's `TMPDIR` placed the worktree so that it contains the planted directory, the negative would be measuring nothing. This check is reading only to make the measurement mean something; the verdict still comes from running the commands.
4. **Run four commands.** Each runs in its own `Effect.scoped`: `wrap`, then spawn `wrapped.argv` with `wrapped.env` and `shell: false`, then wait for exit, all inside the one scope. `wrap`'s releases call `cleanupAfterCommand` and unregister the network lists (`sandbox.ts:160-173`), so they must not run until the child has exited.
   - Every `wrap` gets `project: 'lingtai-doctor-canary'`, the canary's worktree and mirror, and a minimal `env` (`PATH` and `HOME` from the process). It gets **no `project_additions` and no `caller_additions`**, so the policy is the built-in one.
   - The commands:
     - Read the planted file: `['/bin/cat', planted]`.
     - Read the worktree's file: `['/bin/cat', <worktree>/canary]`. Its random content is different from the planted file's.
     - Connect to a host off the allowlist: `['curl', '-sS', '-o', '/dev/null', '--max-time', '10', 'https://example.com/']`.
     - Connect to an allowlisted host: the same argv with `https://github.com/`.
   - **Use `curl`, not `node -e`.** srt enforces the allowlist through a proxy whose address it puts in the command's environment (`HTTPS_PROXY=http://…localhost:<port>`, `sandbox-runtime/dist/sandbox/sandbox-utils.js:724`). `curl` follows it. Node's `net` and `fetch` do not, and would fail the positive control on every host. Leave out `--fail`: the question is whether the connection was made, not what HTTP status came back.
   - Each command gets a timeout of about 20 s, and a timeout is `could-not-run`.
5. **Judge.**
   - If either positive control failed, the result is `could-not-run`. That means the worktree read did not exit 0 with its content on stdout, or the `github.com` connect did not exit 0. This holds whatever the negatives did.
   - If a negative exited 0, add it to `leaked`. For the planted read, also add it if its random content appears on stdout.
   - Otherwise the result is `held`.
   - Never parse srt's messages.
   - Any error from `wrap` is `could-not-run`, with the error's `reason` and `sentences` in the detail. That covers `SandboxUnavailable`, `SandboxWrapFailed` and `SandboxPolicyRefused`.
   - Any error from `CanaryIo` is `could-not-run`, and so is any defect. Use `Effect.catchCause`, and let interrupts through, as `verdictOf` does (`packages/recipe/src/sandbox.ts:65-67`).

The ticket asks for a test that the canary uses the same builder as a run. That test is structural: the canary's type takes `Pick<SandboxApi, 'wrap' | 'policyOf'>` and nothing lower, so it cannot reach `customConfigFor` or `Srt`. The unit test hands in a fake `SandboxApi` that records every `wrap` input. It asserts four calls, `project === 'lingtai-doctor-canary'`, and no additions in any of them.

## The steps in `runDoctor`

Add one step, labelled `sandbox`, placed after `recipes` (`doctor.ts:3571`) and before the store-branch split, so that both branches get it. It does the following:

1. **Host row.** `verdictOf(reach.sandboxHost)` gives `sandbox: host`. If it is `ok`, the row says so. If it fails, the detail is `reason`, then srt's `sentences` joined, then `installFor(process.platform)`'s command as `fix`. For `platform … cannot be sandboxed` (`sandbox.ts:99`) there is no install command, and the row says so.
2. **Per-project rows.** Load the projects with `loadE`. For each project with a name, resolve with `recipeLookup({ ...reach, sandboxHost: 'skip' })` and apply `sandboxDecision(recipe.sandbox, verdict, homedir())`, giving `sandbox: <project>`.
   - `sandboxed` and *off by choice* are `ok`.
   - *degraded* is `fail`, with `why` and the fix *install …, or set `enabled: false`*.
   - `refused` is shown as **stopped** and is `fail`, with `why` and the fix *install …, or set `required: false`*.
   - A recipe that fails even with `'skip'` is `skip`, with detail *the recipe does not resolve — see `recipe: resolves for every project`*. Examples are a protected path in `write` or `deny` (`packages/recipe/src/sandbox.ts:136-165`) or a parse error. The recipe row already fails it, and two failures for one cause would be counted twice.
   - This is a second resolve per project. `ProjectFilter` (`packages/conductor/src/filter.ts:107`) does not carry the resolved recipe, so there is nothing to reuse. The extra read is a file read plus host facts, which is cheap.
3. **Canary row.**
   - If the host verdict is *cannot*, it is `skip`: *not run: the host row failed*. The host row already carries the failure.
   - If no project's block is `enabled`, it is `ok`: *not run: no project asks for the sandbox*. That wording is the ticket's.
   - Otherwise call `reach.sandboxCanary()`.
   - The `sandbox` step label must appear in `onProgress`. `apps/cli/unit/doctor-progress.test.ts` asserts the step list, so expect to add it there.

## Edges this note decides

- **The restart gate.** No sandbox row carries `restartAnswers`, so a failing canary, a *degraded* row or a *stopped* row gates `lingtai restart` (`gatingFailures`, `doctor.ts:1730`) unless `--despite-doctor` is passed. That is correct, because a restart does not install `bwrap`. But it is a new way for a restart to be refused, so say so in the PR body. `degraded` is a `fail` because the ticket says so; this note does not change that.
- **Two doctors at once.** Both use the fixed cache name `lingtai-doctor-canary`, and one may remove it while the other's wrap has just created it. The commands never use the cache, so nothing reads wrong. Only the second doctor's `ensureDir` work is wasted.
- **The daemon.** A daemon in another process has its own srt instance, which this canary never touches. In `lingtai restart`'s own process, `processSandbox` is that process's one instance, and doctor never closes it.
- **What the log can settle.** Nothing here. Doctor appends no event, and the canary leaves no record beyond its row. Whether the canary held on harbor or foundry is answered by running `lingtai doctor` there after the merge; that is the ticket's last checkbox, and nothing in `events` stands in for it.

## Verified only by unit tests before merge

The real canary, with srt, `curl` and the network, runs only on a host. No integration test adds coverage here, and none should be written to stand in for one. The unit-level claims that stand in are these:

- The judging rules, over a fake `CanaryIo` and a fake `wrap`:
  - all four commands as the canary needs them gives `held`;
  - a negative that exits 0 gives `leaked` naming that negative;
  - planted content on stdout with exit 1 gives `leaked`;
  - either positive failing gives `could-not-run` even when both negatives "refused";
  - an error from `wrap`, an error from `CanaryIo`, or a timeout each gives `could-not-run`.
- The planted path is outside the worktree, the mirror and the cache.
- The cache directory and all three temporary directories are removed, including after an injected failure.
- The canary calls `wrap` four times with the built-in policy.
- The host row, given a failing `HostAnswer` with sentences, shows the sentences and `installFor`'s command.
- The four project states, *stopped* included, come out right through an injected `recipe` that returns a required, enabled block, combined with a host that answers *cannot*.
