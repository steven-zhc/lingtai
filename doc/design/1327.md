## Design: #1327 — every hold Lingtai writes is `lingtai:hold`

The ticket leaves two choices open, and both are made here: how the local-store migration is written, and where the doctor row goes. Everything else follows the ticket as written.

**#1336 has landed in this worktree.** `foreignLabels` now keeps everything that is not in `OWN_LABELS`, and `OWN_LABELS` is derived from `labelsFor` (`packages/conductor/src/labels.ts:47-52`). So a `lingtai:hold` survives a whole-set write, and this diff does not touch that file except to add the two constants.

### 1. The migration is read-modify-write in TypeScript, not a JSON-function `UPDATE`

The ticket offers either approach. Plain SQL fails one of its edges: *"a row whose `labels` does not parse as JSON is left alone and the migration goes on, never stopping the store from opening."*

- **Why plain SQL fails that edge.** In SQLite, `json_each(labels)` raises `malformed JSON` on a bad row. In Postgres, `labels::jsonb` raises on the same row. Postgres also has no `IS JSON` before version 16. Either way, one bad row fails the whole statement, and with it `ensureTicketTablesEffect`. That locks every verb on the store out, because each verb waits on the ensure (`db-tickets.ts:296-310`).
- **The shape.** Write `migrateHoldLabelsEffect(port)` in `db-tickets.ts`, and have `ensureTicketTablesEffect` call it as its fourth step, after `LINKS_TABLE` (`db-tickets.ts:113-117`).
- **What it does, step by step.**
  - It runs `SELECT project, number, labels FROM tickets WHERE labels LIKE '%"agent:hold"%' OR labels LIKE '%"agent:followup"%'`. The `LIKE` only narrows the rows; it is not the test. The text is the same on both dialects.
  - For each row it does `JSON.parse` inside a `try`. A row that throws, or does not parse to an array of strings, is skipped.
  - It computes the new array: `lingtai:hold` is appended after the existing labels when `agent:hold` is present and `lingtai:hold` is absent, and likewise for `agent:followup` → `lingtai:followup`. Order is kept, so the Done-when arrays match exactly. Matching is exact by name.
  - Where the array changed, it runs `UPDATE tickets SET labels = $1 WHERE project = $2 AND number = $3 AND labels = $4`, with `$4` set to the text it read. Each row is a separate statement; there is no transaction verb (`db-tickets.ts:268-271`).
- **Why the guard on what was read.** It answers the ticket's two-processes edge without needing an "already contains" condition in SQL. If two ensures race, the second one's `UPDATE` matches nothing. If a `setLabels` lands between the read and the write, the `UPDATE` matches nothing too, and the next start tries again.
- **Do not bump `updated_at`.** Use `query`, not `exec`: `exec` is the DDL path (`execIdempotentlyEffect`, `packages/event-store/src/snapshots.ts:120`), and it takes no parameters.
- **Failures.** A query that fails is a defect, as the DDL's is. It fails the ensure, and `ensureReady` forgets the failure and retries (`db-tickets.ts:299-305`). That is the ticket's *read that fails* edge, with no new code.
- **Effects only.** Write it as `Effect.gen` over `port.query`, with no `async` and no `Effect.run*`. The ratchet stays where it is.

**What the migration covers.** `ensureTicketTablesEffect` runs once per store, not per project (`makeDbTickets` calls it, `db-tickets.ts:263-266`), so the migration covers every project's rows in one pass. That is intended: the label is the same in every project.

**Tests.**
- **Unit:** extend `packages/conductor/unit/db-tickets.test.ts` on its `:memory:` SQLite, using the three rows from Done-when. Add a fourth row whose `labels` is `'not json'`. Assert that the ensure still succeeds and leaves that row byte-identical. Run the ensure a second time and assert nothing changed.
- **Postgres:** the same cases go under `packages/conductor/integration/` behind the existing `skipIf`. That half does not run inside a pass, so the SQLite unit case is the claim that the build checks before the merge. Keep the SQL dialect-neutral (`$n` placeholders, `LIKE`, plain `=` on `TEXT`) so the unit case means something for Postgres too.

### 2. The doctor row is a sibling of `recipeRow`, built from the same `ProjectFilter`

`projectFiltersOnce` is the one place the recipe is resolved, and its comment says *"Do not resolve the recipe a second time"* (`apps/cli/src/doctor.ts:2409-2418`). Its result is mapped to `recipeRow` at `doctor.ts:2479`.

- **The function.** Add `export function holdLabelRow(f: ProjectFilter): CheckResult | null`.
  - It returns `null` when `!f.ok`. That project already shows `recipeRow`'s `fail`, and it is the ticket's *cannot be read is `skip`* case: no second row about a recipe that does not resolve.
  - It returns `null` unless `f.exclude` contains `agent:hold` and not `HOLD_LABEL`.
  - Compare case-insensitively, the way `discover.ts:246` matches `exclude`, so that a recipe listing `LINGTAI:HOLD` is not warned about.
- **The row.** Name it `hold label: ${f.project}` and give it status `warn`. Its title and detail carry the ticket's sentence and name both labels, and the detail also says that nothing changes until the recipe is edited by hand.
- **Wiring.** At `:2479`, use `flatMap` to emit `[recipeRow(...), holdLabelRow(f)]` with nulls filtered out, so the warning sits directly under its project's recipe row.
- **Test.** Add a unit test beside the existing `recipeRow` cases in `apps/cli/unit/doctor.test.ts`, with three cases: excludes only the old label (one warning naming both), excludes both, and excludes neither (no row).
- **Label name.** `apps/cli` reaches `HOLD_LABEL` through `@lingtai/conductor`, which `backlog.ts` also uses after this change. The doctor must not spell the label out.

### 3. Small things the agent would otherwise stop on

- **The constants.**
  - `HOLD_LABEL` and `FOLLOWUP_LABEL` are template literals on `LINGTAI_LABEL_PREFIX`, exported from `packages/conductor/src/index.ts` beside `labelsFor`.
  - They must **not** go into `LABEL_STATES` or `OWN_LABELS`. A person sets them, and putting them in `OWN_LABELS` would make `foreignLabels` drop them, which is the bug #1336 just fixed.
  - Add an assertion that `OWN_LABELS` contains neither constant to the existing `labels` unit test. This is cheap and catches anyone who later puts the hold in the computed set.
- **The board.** Check that the board's `actions.ts` already imports from `@lingtai/conductor` in a server-only file before adding the import. `decide-finding.tsx` is a client component: put the literal text `lingtai:hold` in its JSX, not an import of the conductor barrel. A server-only import that reaches a `"use client"` graph is caught only by the Next build, after the merge (#230).
- **The generated CLI docs.** After the help line changes, run `pnpm docs:cli`, and commit `doc/cli.md` and `doc/cli.json` as it writes them.
