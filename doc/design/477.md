## What "the column id `blocked`" is

The ticket's premise is half stale, and the agent will lose turns on it if nobody says so. **The lane id is already `waiting`** everywhere a lane is named:

- `ColumnId = 'queued' | 'running' | 'waiting' | 'landed'` (`apps/board/src/lib/board.ts:53`). `COLUMNS` has `{ id: 'waiting', label: 'Waiting on you' }` (`board.ts:408`), and so does `apps/site/src/lib/snapshot.ts:166`.
- `task_view.state` is written as `'waiting'` by `WorkItemBlocked` (`packages/projector/src/task-view.ts:334`, `:342`). The Waiting-oldest-first ordering already says `case when t.state = 'waiting'` (`postgres.ts:279`, `sqlite.ts:635`).
- `LABEL_STATES` already includes `'waiting'` (`packages/domain/src/streams.ts:108`).

The column that is still `blocked` is the **SQL column `task_view.blocked`**, `blocked boolean not null default false` (`task-view.ts:163`), and the `TaskCard.blocked` field it is read into. 0120 calls it this: *"a column id that is only a projection's (`blocked` → `waiting`) is renamed with a rebuild"* (`doc/decisions/0120-a-reason-is-a-type.md`, *Two phases*). 0118 lists it beside `WorkItemBlocked` as *"the `blocked` column"* (`0118-a-hold-explains-itself.md:135`). **That column and that field are this ticket.** Rename both to `waiting`.

## The trap: reading the renamed column before the rebuild

The rebuild drops the table: `reset` does `drop table if exists task_view` (`task-view.ts:242`–`:246`). But in the window between merge and rebuild, the live table still has `blocked` and has no `waiting`.

- **Writes fail loudly, which is fine.** `shape.ts`'s drift check reports `waiting` as missing and `blocked` as unexpected, and names the remedy. This is the #84 failure its header describes, and the reason it exists.
- **Reads fail silently.** `postgres.ts` reads `select t.*`, so on an old table `row.waiting === true` is `false` for every row and `parseBool(row.waiting)` is falsy. Every waiting card would lose its Approve/Requeue row (`page.tsx:378`) and its *waiting for your answer/review* chip (`describeWait`). `lingtai status` would stop printing the question (`status.ts:332`). Nothing would fail.

#249 renamed `verdicts` and hit exactly this. The fix it left is `columnOf` (`packages/projector/src/store.ts:131`), and its comment at `postgres.ts:59`–`:62` says why: *"`select t.*` on a table created before the column was renamed hands back no `verdicts` at all, and `row.verdicts ?? {}` would count that as a run with no verdicts rather than as the drift it is."* **Read `waiting` through `columnOf(row, 'task_view', 'waiting')` in both mappers**, the same way `verdicts` is read at `postgres.ts:63` and `sqlite.ts:261`. Then an un-rebuilt table throws `ProjectionShapeError`, which states the rebuild, instead of showing an empty Waiting lane's controls.

## Rename, don't delete

The fold sets `waiting = true` only together with `state = 'waiting'`, in `WorkItemBlocked` (`:342`–`:344`). Every write that clears it also moves `state` off `waiting`. So the boolean looks redundant with the state, and deleting it and testing `state = 'waiting'` is tempting. Don't:

- The replayed legacy `WorkItemDiscovered` upsert sets `state = 'queued'` and leaves the flag (`:263`–`:272`, `:847`/`:854` with `$10 = 0`).
- The `DispatchRefused` guard depends on the flag specifically.
- The comments at `page.tsx:362` and `status.ts:328`–`:331` claim the two differ: *"the lane also holds a run that asked something mid-flight"*. That half is stale: `RunAwaitingInput` *"is a note on the card, never a hold"* (`task-view.ts:517`–`:520`). It is worth correcting while those lines are open, but it does not justify dropping a column in a rename ticket.

So `card.waiting` (a boolean) will sit beside `card.state === 'waiting'`. That is principle 5's own wording: the page's word is the column id.
