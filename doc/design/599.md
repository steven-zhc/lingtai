# #599: design note

## Where it goes

Everything lands in `packages/github/src/client.ts`. Put the four interface entries after `createIssue` (`:266`). Put the implementations inside `createGitHubClient`'s returned object after `createIssue` (`:496`), and make every call through the local `request` (`:302`). Export any new type or error class from `packages/github/src/index.ts` (the `./client.ts` block). **Do not add them to `Tickets` or `PassClient`** in `packages/conductor`. The db ticket store has no equivalent. `TICKET_VERBS` in `packages/conductor/unit/ticket-store.test.ts:36` and `FAKE_DB_TICKETS` in `apps/cli/unit/run-ownerless.test.ts:78` stay at eight verbs.

## The shape

```ts
addSubIssue(parent: number, child: number): Promise<void>
listSubIssues(parent: number): Promise<LinkedIssue[]>
addBlockedBy(issue: number, blocker: number): Promise<void>
listBlockedBy(issue: number): Promise<LinkedIssue[]>
```

**Number to id is one private helper, `idOf(number)`.** It does `GET /repos/{o}/{r}/issues/{n}` and reads `.id`. `toIssue` (`:399`) drops `id`, so don't go through it. Either read `id` off the raw response, or widen `toIssue`'s parameter type without adding `id` to `Issue`.
- The **path** always takes a number: the parent's, or the blocked issue's.
- The **body** takes the other issue's id: `{ sub_issue_id: await idOf(child) }` or `{ issue_id: await idOf(blocker) }`.
- Send the id as a JS `number`, never a string. That is the CLAUDE.md `-F` point, and a ~5.5e9 id is well inside `Number.MAX_SAFE_INTEGER`.
- A 404 from `idOf` is a throw. It means no such issue in this repository. It is never "nothing to link".

**`LinkedIssue` is `Issue & { repository: string }`.** `repository` is `owner/repo`, taken from the tail of the raw object's `repository_url`. GitHub allows both kinds of link across repositories. Without the repository, a person's link to `other/repo#12` would compare equal to this repo's `#12`. The split writer will use these lists to decide "already attached, skip", so a false match would silently leave a link unwritten. Map each entry through `toIssue` and add `repository`. Don't filter out other repositories' issues. Return them and let the caller compare.

**The lists page, and they are complete or they throw.** Use `per_page=100&page=N` and stop on a short page, as `listOpenIssues` does (`:480–494`). Put a bound in a constant beside `LIST_SINCE_PAGES` (`:285`), and throw when it is exceeded instead of returning short. The reason is the one `listIssuesSince`'s doc gives (`:190`): *"The caller reads *not listed* as *does not exist* and opens one, so a listing that silently stopped short would be a duplicate."* Here the duplicate would be a second link attempt.

**A 404 on a list is never `[]`.** `matchingRefs` gives the reasoning at `:467–471`: a 404 there is the repository, not the absence of links.

**A link that already exists is a 422, and it throws as is.** `deleteRef`'s doc (`:175`) sets the precedent: the client stays thin, and a caller that must be idempotent lists first. **Never send `replace_parent: true`.** A child that already has a different parent should fail. Reparenting it would quietly move an issue somebody else filed.

## The 403

Add a `PermissionDenied` error class next to `BodyChanged` (`:31`). Either extend `GitHubError`, or carry its `status` and `path`, so existing `instanceof GitHubError` checks keep working. All four methods catch `GitHubError` with `status === 403` and rethrow it with a message that:
- names the permission (`issues`, at `write` for the adds and `read` for the lists);
- names the endpoint;
- says that the installation must grant it, or that the owner must accept the App's updated permissions.

`issues: write` is already in `REQUIRED_PERMISSIONS` (`packages/github/src/app.ts:179`, *"reading work items, writing agent:\* labels and comments"*). So a 403 on a correctly made App usually means an installation that predates the permission or never accepted it, and the message should say so. Extend that row's `why` to mention sub-issues and dependencies. Leave the level alone.

**Watch out: GitHub also sends 403 for secondary rate limits.** Their message contains `rate limit`. Rethrow those unchanged. Calling one a missing permission would send a person to the wrong settings page.

## The cost nobody listed: fakes that build the whole interface

The four methods will be **required** on `GitHubClient`. Every literal typed `GitHubClient` without a spread or cast then fails `pnpm typecheck`, and the tsconfigs include `integration/` (`packages/conductor/tsconfig.json`: `"include": ["src", "unit", "integration", "test"]`). I found these:
- `packages/conductor/unit/discover.test.ts:311` (`fakeClient`)
- `apps/cli/integration/status-preview.test.ts:62`
- `packages/conductor/integration/wizard.test.ts:107` (`readOnlyClient`)

Run `pnpm typecheck` to get the full list. Give each fake the four methods, throwing `not used`, in the style the fakes already use for writes (`discover.test.ts:330`). Don't make the methods optional to dodge this. The writer would then have to handle a client that cannot link. Casts (`as unknown as GitHubClient`) and the `Proxy` in `apps/cli/src/doctor.ts:1589` are unaffected.

## Tests

Write a new `packages/github/unit/links.test.ts`. Reuse `client.test.ts`'s setup: a real RSA key, the `/access_tokens` stub, and a hand-written `installation` (`:22–36`). Use a stub that routes by method and path and records `{ method, path, body }`.

**Give every fixture an `id` that differs from its `number`**, for example `number: 161, id: 5466453198`. If they are equal, a swapped argument or a number sent where the id belongs passes. That is the exact bug in *Watch out*. For each add, assert that the POST path carries the number and the body carries the id as a `number`. Also cover:
- a two-page listing (100, then fewer);
- a cross-repository `repository_url` carried through;
- a 403 surfacing as `PermissionDenied` naming `issues`;
- a 403 rate-limit message *not* surfacing as one;
- a 404 on a list throwing.

All of this is unit, since the HTTP is stubbed. No live call is needed or possible inside the pass. As `client.test.ts:8–14` says of its own fixture, a stub written by the same hand cannot catch a misspelled field name such as `sub_issue_id` or `issue_id`. The first real check of the spelling is the split writer's first live run, and a wrong key there is a 422 rather than a silent pass.
