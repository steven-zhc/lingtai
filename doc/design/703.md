## Shape

The ticket only fixes *which* strings get rewritten. What it leaves open is how one unit test can reach them. Most of the strings are written inline inside functions that take a whole `world`, and a few sit in private functions. So the change has two parts: (1) give each listed string an exported name it can be reached by, and (2) write one guard test that imports those names. The rewording is the easy part.

### 1. Every listed string gets an exported name, in its own module

The rule: **wherever the string is built today, put a small pure builder beside it, and have the call site call that builder.** Leave the world-taking function alone. Then the guard calls the builder with fixture arguments. It does not need a fake git, files or a prompter to get one sentence out.

### 2. Patterns catch more than the cited token

Several listed strings carry references the ticket doesn't name, and the guard will catch them:

- `testUrl` also says *"Since #275 the suite runs on a SQLite file…"* (`index.ts:328`). Drop the `#275` and keep the fact.
- `lockDir`'s message names `test-support/teardown.ts` (`index.ts:1084`). The path pattern only anchors on `packages|apps|doc`, so it would pass, but the Want says "no repository path". Rewrite it as "the integration suite's setup makes one fresh per run".
- `@lingtai/event-store/test/postgres's list` in `testUrl` is a package specifier, not a repo path. The patterns pass it. Leave it alone: it is test-side only, and it names the thing a developer has to edit.

### 3. The guard

It is **one file, `apps/cli/unit/plain-output.test.ts`**. `apps/cli` already depends on `@lingtai/env`, so this one file can hold both packages' strings. It has three parts:

- **`SET`**: an array of `[label, string]` pairs built from the exports above. Each builder is called once with fixture values that make every branch print. `landing`'s two branches are two entries. `postgresOnlyRows()` expands into one entry per row.
- **`references(text): string[]`**: the three regexes from the ticket, exactly as written. It returns what matched, so a failure names the token.
- **Tests:**
  - (a) `SET` is non-empty, and every entry is a non-empty string. Without this check, a builder renamed to return `undefined` turns the guard into a green that asserted nothing.
  - (b) `references(s)` is `[]` for every entry, with the label in the assertion message.
  - (c) `references` self-tests: `'… (0055 §3)'`, `'… (#381)'` and `'see packages/x.ts'` each match. `https://github.com/apps/<slug>/installations/new` and `https://github.com/settings/apps/<slug>` don't match. A fixture of the form `db ticket #12`, with a two-digit number in prose, *does* match. That pins the trade-off the ticket accepted.

This guard holds the listed set only. It does not scan source files: the ticket's `Want` limits it to the list, and scanning would catch code comments, which keep their references.

### What the rewrites must keep

Each reference stood for a fact, and that fact stays in the sentence:

- `0055 §3`: switching stores starts a new, empty log; nothing is moved.
- `0056 §3`: an exported URL wins over the file. That clause is already in the sentence, so drop just the parenthesis.
- `merge-action.ts:47`: Lingtai lands work by pushing to this repository's origin.
- `#63`: renamed so a project's own variable can't be mistaken for Lingtai's.
- `#273`: otherwise the lock would land in the operator's own `~/.lingtai/locks`.
- `#370`: only claude-code enforces a per-run dollar limit.
- `#381`: tickets from another source would be numbered into the same streams.
- `0006-github-app.md`: point to the board's setup page or `lingtai init`, which the same string already names.

The source comments above these strings that cite the ADRs stay as they are.
