## Design: scoped review after a base merge (#1274)

### The decision that matters: a second field next to `reviewedSha`, not a different meaning for it

Leave `reviewedSha` meaning what it means now. While it is set, the next review diffs `deps.diff(reviewedSha)`, and `diffBetween` runs `git diff DIFF_FLAGS a...b` (`packages/conductor/src/conduct.ts:2317-2331`). After a merge that triple-dot diff is the wrong delta, which is the Watch out. Three places depend on the current meaning, so none of them should move:
- `reviewedHeadStands` (`run-attempt.ts:1911`) decides the disjoint carry (#1210).
- The `approvedHeadStands ? approvedAt : null` branch (`:1996`), which the ticket keeps unchanged.
- The set at `:2322`.

Add one walk variable in `runAttempt`, next to `reviewedSha` (`run-attempt.ts:1530`):

```ts
/** A review read `reviewed`; a base merge onto `base` came after it, and no review has read the merged head whole (#1274). */
let mergedSinceReview: { reviewed: string; base: string; overlap: readonly string[] } | null = null
```

It reaches the review through `contextFor()` (`:1563-1574`) as a new optional `ActionContext` field, next to `reviewedSha` (`packages/actions/src/action.ts:631`). The two are exclusive by construction: every place that sets this field sets `reviewedSha` to null.

**Where it is set:**
- **`applyConflictMerge`** (`:1600-1621`). Today it sets `reviewedSha = null`. Before that line, set:
  - `reviewed`: `reviewedSha ?? mergedSinceReview?.reviewed`.
  - `base`: `baseSha`.
  - `overlap`: the new `landedOnBase.paths`, unioned with any earlier `overlap`.

  If neither `reviewed` source is set (no review read a head in this pass), leave the field null. That is today's full review.
- **The base-move `else` branch** (`:1995-2001`). Same rule with `base: next.toSha` and `overlap: offer.proposal.paths ?? []`. When `paths` is null the overlap is unknown, so set the field to null and the review is full, as the comment at `:1985-1986` already says for that case. When `approvedHeadStands` is true, keep today's `reviewedSha = approvedAt` and leave this field null, because that path is out of scope.
- **The disjoint branch** (`:1991-1994`) does not touch it. It only runs when `reviewedHeadStands || approvedHeadStands`.

  Watch the case where the field is already set (an unreviewed merge, then a disjoint move): `reviewedSha` is null then, so `reviewedHeadStands` is false and the walk takes the `else` branch. It updates `base` to the latest commit and adds no overlap. That gives the ticket's *two merges before one review* rule with no special case.

**Where it is cleared:** at `:2322`, in the same `if` that sets `reviewedSha = visitContext.onSha`. A clipped read (#892) leaves it standing, because a clipped review did not read the merged head whole. Since the field lives in walk memory, it is *never shared between passes* (comment at `:1527-1529`), the same as `reviewedSha`. If a process dies halfway, the continuation rebuilds it from the log: `reviewedHeadOf` (`attempts.ts`) names the head the last review read before the merge, and the merge's base and overlap come from the same record that restores `landedOnBase` (the lane's outcome, or `conflictEvidence` for a conflict round). Where the log cannot say (a clipped read, or another merge in between) the field stays null and the review is full, the safe direction.

### The git half is a new dep, not `diff`

`agent-action.ts:157` says *"the actions package does not know about git, and should not learn"*. So the review action does not run `merge-tree` itself, even though the ticket says *the review action computes that delta*. Add an optional dep next to `diff` (`agent-action.ts:159`):

```ts
diffSinceMerge?: (reviewed: string, base: string) => Promise<DiffRead>
```

Lift it in the Effect deps at `:242`, and supply it in `conduct.ts` next to `diff` (`:4416`). The conduct.ts side:

1. **The tree.** Run `git merge-tree --write-tree <reviewed> <base>`, keep stdout on exit 1, and require a 40–64 hex tree on line 1. Do not copy the version check and parse from `conflictedPathsAtEffect` (`packages/repo/src/mirror.ts:157-188`). Factor them out of that function into an exported Effect in `packages/repo` that takes a `cwd`, and have both callers use it. Run it in the **worktree's** cwd, not the mirror's, and **not** under `mirrorWrite`. The fetches in `conduct.ts` write the worktree's objects (comment at `:2302-2305`), and `merge-tree` moves no ref (mirror.ts:153-154), so 0122 §6's lock has nothing to guard.
2. **The delta.** Run `git diff DIFF_FLAGS <tree> <HEAD sha>`. Use **two dots**: a triple-dot diff needs a merge base, and a tree has none. Resolve `HEAD` to a sha first, as `diffBetween` does. Return `{ text, from: <reviewed>, to: <head> }`. `from` is the reviewed head and not the tree, so the prompt and the run log name commits a person can look up.

Every failure, including a missing dep, becomes the existing soft path: an `Exit` read, a note, and a full review (`agent-action.ts:944-973`). Word the note so the log tells this path apart from the old one: `the merge baseline could not be built (…); this is a full review`.

### The review action

In the block at `agent-action.ts:940-973`, add a second branch: `context.mergedSinceReview` set → `deps.diffSinceMerge`. Three differences from the fix branch:

- **Empty text is an empty delta, not "unreadable".** Line 950 turns `text.trim() === ''` into `null` and a full review. For the merge baseline, an empty diff means *the merge was clean and nobody edited*. That is the ticket's third Done-when, and `hunksOf('')` already returns empty hunks (`diff-hunks.ts:117-118`). A null from `hunksOf` on non-empty text is still unreadable, which means a full review.
- **No prompt reference.** `deltaParts` attaches `ref: { _tag: 'Diff', from, to }` when `exact` is true (`agent-action.ts:440-443`). The resolver would re-run that as a commit diff, which would be exactly the wrong delta. Build this `ReviewDelta` with `exact: false` (or no `exact`) so the text is always inline.
- **Its own prompt header.** Today's text says *"what changed since the last review read this diff. The rest of the diff above was already reviewed"* (`:431-434`). Add a variant, chosen by a field on `ReviewDelta` (for example `since: 'fix' | 'merge'`). The variant says three things:
  - The section is what changed against the merge as the base would have made it on its own (the resolution and later edits).
  - The overlap paths, listed by name, are also open for new findings.
  - An empty section means the merge needed no hand.

  This block sits beside `landedOnBaseBlock` (`:938-939`) and #1120's question. It does not replace either.

**Demotion.** Give `demoteOutsideFix` (`diff-hunks.ts:157`) an optional third parameter, `keep: ReadonlySet<string>`: the paths whose findings are never demoted. Pass `context.mergedSinceReview.overlap` from `scoredReview`'s call (`agent-action.ts:1239`). This has to reach the function that computes `afterFix`, so thread it the same way `deltaHunks` is threaded. A file-level finding (`line === null`) on an overlap path stays blocking. A recheck is still exempt before this point (`:1234-1236`). `demoteOutsideDiff` runs first and is unchanged: a finding outside the whole `mergedOnto...HEAD` diff is still `pre-existing`.

### What this does not change

No ADR states the exception. #671's ticket does, and 0108's review section stays as it is, so this needs neither a superseding file nor an edit.

These stay as they are:
- The first review of a pass.
- The disjoint carry (#1210).
- The approval path.
- `mergedOnto` and the whole-diff spelling.
- `landedOnBase` and the conflict brief.

### Checks

Everything the Done-when asks for can be checked at unit level:
- **Conductor half:** with fake deps, assert the context's `mergedSinceReview` after a conflict round and after an overlapping base move. Assert it is set and `reviewedSha` is absent, then that the review visit clears it.
- **Action half:** with a stubbed `diffSinceMerge`, check four cases: the resolution-only delta, an empty delta, a failing dep, and the overlap/recheck keep.

The one claim no unit test covers is the real `merge-tree` and the tree-to-commit diff in a real repo. That is integration, so it is out of reach inside the pass. The factored repo Effect can still unit-test its parse on canned `merge-tree -z` output.

Any existing unit test that expects `reviewedSha` absent and a full review after a conflict round changes its expectation once, here. Before raising any number in `effect-ratchet.baseline.json`, check it: write the new dep as an Effect in `conduct.ts` and lift it only where the deps interface is still promise-shaped.
