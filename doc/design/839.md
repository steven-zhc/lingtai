## Design note: #839, a stopped projection other than `task_view` stops alone

### 1. At start, `onError` runs before `start()` rejects

During catch-up, `subscribe` calls `options.onError?.(fatal.cause, 'handler')` (`packages/event-store/src/subscribe.ts:259-260`). Only after that does `run()` reach `ready.reject(...)` (`:293`), and only then does `runner.start()` reject. So on a restart, the new `onError` branch is the first thing to see the failure. The start loop's catch sees it second.

Two consequences:

- **Recording is idempotent by name.** Both paths call one `recordStopped(projection, runner, error)`, and the second call for a name that is already recorded does nothing. Keep today's `??=` meaning, applied per name.
- **`task_view` at start must not reach `shutdown`.** Today `onError` calls `shutdown('projection-failed')` during catch-up (`packages/daemon/src/daemon.ts:185`). `shutdown` releases the lock (`:170`), and so does the outer catch (`:212`): two releases, and a `stopped` that settles on a daemon that never returned. Add a `returned` flag that is set just before `startDaemon`'s `return`.
  - A `task_view` handler error **before** `returned` records the projection and leaves the throw to the start path.
  - A `task_view` handler error **after** `returned` calls `shutdown('projection-failed')` as today.
  - After the loop, throw if `task_view` is on the list. This catches `task_view` failing live while a later projection is still starting.
  - That keeps "a `task_view` failure at start throws out of `startDaemon`", and gives the lock one owner.

The fake runner in `unit/` should do the same as the real one: call `onError(err, 'handler')`, set `failure`, and then reject `start()`. A fake that only rejects tests an order production never produces.

### 2. The start loop's catch

In the inner catch (`daemon.ts:193-201`):

- If `err instanceof ProjectionShapeError`, or `runner.failure === null`, rethrow as today.
- Otherwise, if the projection is not `task_view`:
  - `await` its recording, so it has a checkpoint before the first beat.
  - Call `tell(paint.fail(`${name} stopped at ${checkpoint}: ${error}`))`.
  - Skip the `following at` line, and `continue`.
- Keep the runner in `runners`, so `shutdown` and the outer catch still `close()` it. A stopped runner still holds an opened store (`projection.ts:250-255`).

Still call `onRunner` for a runner that stopped at start. `trackLiveSpend` adding it does no harm, because `holdLiveSpend` keeps only `r.running` (`apps/cli/src/projector.ts:83`).

### 3. The checkpoint is read asynchronously

`onError` is synchronous, but `runner.lag()` is a store read (`projection.ts:266-268`). `recordStopped` therefore:

1. Keeps a per-name `Promise` in a map, which is the idempotence from §1.
2. Awaits `lag()`.
3. Pushes `{ name, checkpoint: lag.lastSeq, error: String(error) }` once the read resolves.

If `lag()` rejects, still push the entry with `checkpoint: null`. Losing the fact that the projection stopped, because the read that dates it failed, would be worse than an undated entry. So the type is `checkpoint: bigint | null`, and doctor prints `at an unread checkpoint` for `null`. This is the one change to the ticket's shape.

On the live path the recording is `void`. The next beat (`HEARTBEAT_MS`) carries the entry. Nothing makes the beacon write early.

### 4. Getting the list to the beacon

`startBeacon` is called after `openDaemon` has run `startDaemon` (`apps/cli/src/daemon.ts:220-227`, `:255`). `started.daemon` therefore exists when the beacon starts.

Do not add a fixed value to `BeatOptions`, because the beacon spreads `beatOptions` once (`control.ts:525`, `:546`). Instead:

- Add `stoppedProjections?: () => readonly StoppedProjection[]` to `BeaconOptions`.
- Read it inside `write()` on every beat and pass it to `beat()` → `store.beat({... stoppedProjections })`.
- A bare `beat()` with no function writes `[]`.
- The CLI passes `() => started.daemon.stoppedProjections`.

`StoppedProjection` belongs in `packages/daemon/src/store.ts`, beside `Beat`/`DaemonStatus`, and `daemon.ts` imports it from there. The board, in #840, reads the status type without importing the daemon.

`apps/cli/src/daemon.ts:698-701` becomes `started.daemon.stoppedProjections.find((p) => p.name === 'task_view')`.

### 5. SQLite widening happens in two places

`SCHEMA` is run by `openSqliteDaemon` (`packages/daemon/src/sqlite.ts:77`) and also by `create()` (`:115-117`). Write one function:

```ts
widen(db) {
  // PRAGMA table_info(daemon_status); if no stopped_projections:
  ALTER TABLE daemon_status ADD COLUMN stopped_projections TEXT
}
```

Call it after both `db.exec(SCHEMA)` calls.

- **Leave the column out of `SCHEMA`.** If `SCHEMA` declared it, a fresh file would take a different path from the conducting machine's file, which is the trap the ticket warns about. With `widen` as the only path that adds it, the unit test's `:memory:` file exercises the same path production does.
- **No `DEFAULT '[]'` on the column.** A row that exists from before the widening must read `NULL`, which is `null`, meaning unknown. The beat's `INSERT … ON CONFLICT DO UPDATE` (`:127-146`) names the column and always writes `JSON.stringify(list, bigint → string)`.
- **Postgres** uses `jsonb` with no default, nullable, beside `postgres.ts:86-89`, for the same `null` reason. The ticket's `not null default '[]'` would read an old row as `[]` and contradict its own edge on null values; the edge wins.
- **Decode in the store.** A `checkpoint` string goes back to a `bigint` in `status()`, in both stores. A value that will not parse throws, like `at()` does (`sqlite.ts:106-109`), rather than becoming a wrong number.

### 6. The doctor check

The check is `projections: stopped`. It sits beside `projections: lag` (`apps/cli/src/doctor.ts:713-731`), with its read injected as the neighbouring checks inject theirs (`:1165`, `:1340`).

**Do not** copy their `.catch(() => null)`. A `readStatus` that throws is a `fail` carrying the error, as the ticket says. It is also not `restartAnswers`, because a restart does not fix an unreadable beacon.

| Beacon state | Result |
|---|---|
| No row, or `!lastBeat(status).up` | `ok`, "no daemon running" |
| `null` list | `ok`, "the running daemon predates this check" |
| `[]` | `ok` |
| Otherwise | `fail`, `restartAnswers: true`, one line per projection |

`fix` should be the ticket's rebuild-then-restart sentence, not `RESTART_FIX` (`:1391`). Doctor prints `fix` as the thing to do, and on its own a restart reloads the same bad fold.

The test that goes with it asserts `gatingFailures` (`:1464-1466`) over a report that contains this row and counts 0.

### 7. What the tests can and cannot prove

Everything above is unit-testable:

- fake runners through `runnerFor` for the four `startDaemon` cases;
- `:memory:` SQLite for the widening;
- an injected read for doctor.

The Postgres `alter` is reached only by `pnpm test:integration`, which cannot run inside a pass. The unit-level stand-in is the SQLite widening test, plus the store contract in `packages/daemon/test/` if it asserts the row's shape.

**Settled in the log once this is live:** a `ConductorStarted` with no second `ConductorStarted` 30 s later, after a `spend` fold failure. Today the same failure appears as a `ConductorStarted` every ~30 s from one `code_sha`.
