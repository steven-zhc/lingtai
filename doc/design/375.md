# Design: #375 — the pass ceiling is the recipe's

## Most of this is already built, and the change is removing the override

`Recipe` already declares `runtime.limits`, defaults and all (`packages/recipe/src/recipe.ts:2970-3065`). Nothing in the schema refuses it. The refusal is a check in `resolveLocalRecipe`'s shape callback, which runs before the schema sees the file (`packages/recipe/src/local.ts:414-421`):

    for (const key of ["agent", "limits"]) {
      if (key in own) { refused.push(`runtime.${key}: moved to this machine (0046 §3) — write it in ${machineFile}, …`)

After that check, the callback overwrites the recipe's runtime with the machine's values: `raw["runtime"] = { ...own, agent: agent.agent, limits }` (`local.ts:423`). So "the recipe accepts `limits`" comes down to three deletions in `local.ts`:

1. Take `"limits"` out of that list. `"agent"` stays, because `agent` is `#372` and `resolveAgent` (`local.ts:214`) must not change.
2. Stop writing `limits` into `raw.runtime`. The callback becomes `raw["runtime"] = { ...own, agent: agent.agent }`, and the schema's `.default(...)` fills in any key the file did not write. This one change also fixes the `#371` unknown-key finding at its source. That finding was the wholesale replacement at line 423: whatever the file wrote under `limits` was thrown away before zod ever saw it.
3. Delete the provenance loop at `local.ts:379-394`, which merges `scoped`, `shared` and the defaults.

**The unknown key still needs a second fix.** The `runtime.limits` object is `z.object` (`recipe.ts:2971`), not strict. So once the file's block reaches the schema, `limits: { turn: 250 }` is stripped silently and resolves as `turns: 300 ← default`. Make it `z.strictObject`, as `DISPATCH.limits` already is (`recipe.ts:234`). `resolve.ts:283`'s `unknownKeys` only checks top-level keys, so it will not catch this.

Strict versus strip does not change what parses for a valid recipe, so `configHash` is unchanged for any file that only writes known keys. Check this with a unit test, not by reasoning: the same numbers, once from the machine file on today's code and once from the recipe on the new code, must give equal `hashRecipe`. In the log, the field that settles it is `StepsResolved.configHash` on the last pass before the restart compared with the first pass after it. For lingtai, after the hand migration, they should be equal.

## Where provenance comes from: use `originIn`, not a new rule

The machine-file merge goes, and nothing replaces it as a third source. Read each limit off the resolved recipe once `resolveSource` has returned, and name its source with the `from` that `originIn` already builds (`local.ts:455`). This is the same thing `assignee` started doing in `#373` (`local.ts:465-468`).

`originIn` asks at the section level (`runtime.limits`) first and then at the leaf (`local.ts:299-314`). So a file that writes only `turns: 250` reads `turns 250 ← …/recipe.yml` and `wall 2h ← default`. That is exactly the "absent says default" output the ticket asks for. A `limits:` whose block is commented out reads as `default` for every key, because of `carries`' null rule (`local.ts:263-278`). `presets.ts` declares no `limits` today; if one ever does, `originIn` already names `preset <name>`.

`usd` keeps its own line: `(none) ← default` when absent, because it is not in `LIMIT_DEFAULTS` (`local.ts:387-389`).

**Keep the five keys immediately after `runtime.agent` in the provenance object.** `provenanceLines` prints in insertion order (`apps/cli/src/doctor.ts:1469-1473`), so building them after the resolve and appending them at the end would move the rows in `lingtai doctor` and on the board's recipe page. Build the object at the end, in the old order.

With that, "doctor and add print every limit with its source" needs no new printing code. Both already print `provenance`. Only the source string changes, from the machine file to the recipe's path or `default`.

## The machine file

This follows the `#373` template exactly. Generalise `hasAssignee` (`local.ts:150-153`) into a check for "this runtime key is written under this scope". Add a `limitsRefusal(at, project, home)` next to `assigneeRefusal` that names `recipePath(project, home)` and says `Nothing here was applied`. Call it at the top level and inside the `projects` loop (`local.ts:180-189`).

Then delete `MachineLimits` (`local.ts:48-67`), so that `MachineRuntime` is `z.strictObject({ agent })`. Refusing before the schema is what makes the message name the recipe. A strict schema on its own would only say `Unrecognized key`.

## The part the ticket does not mention: two writers still put limits on the machine

**1. `machineFiles` (`local.ts:502-566`)** splits a wizard recipe into two files. Today it deletes `runtime.limits` from the recipe text (`:523`) and writes `ceilingOf(recipe)` under `projects.<p>.runtime` (`:528-535`). After this change:

- delete only `runtime.agent` from the recipe text;
- `choose()` returns `{ agent }` only.

The `isDeepStrictEqual` and `replace` logic can stay as it is. The section it compares now holds only `agent`, and a machine file that still holds `limits` never gets that far, because `parseMachineConfig` refuses it.

For a new onboarding this means `emitRecipe`'s full `Recipe.parse` output keeps its `runtime.limits` block, together with the `A pass: …` comment that `saidFor` attaches (`packages/conductor/src/wizard-page.ts:840-841`).

`#371` found that `emitRecipe` omits default-valued keys. Read `packages/recipe/src/emit.ts:89-108` before you assume it does or does not: `new Document(Recipe.parse(recipe))` looks like it carries every key. Settle it with a unit test asserting that a wizard-onboarded recipe states all four keys, and fix it only if that test is red.

**2. `editExisting` (`apps/board/src/app/setup/wizard/finish.ts:107-162`)** is where the board's limits row writes, and it is the path where both of `#371`'s attempts died.

- It builds `after` with the file's own limits so that `editRecipe` will not write the page's limits into the file (`:118-119`). Pass `drafted.runtime.limits` through instead.
- `changesFrom` already has one path per limit (`wizard-page.ts:808-811`, *"Editing one field changes one field"*), so moving one dial changes that one line of `recipe.yml` and leaves the comment above `limits:` alone.
- The `runtime` filter at `:140` must become `path[0] === "runtime" && path[1] === "agent"`. Otherwise a limit change is also sent to `machineFiles` and appears twice in `changed`.
- `describes` (`:121-122`) keeps working unchanged, because both sides now carry the drafted limits.

The unit tests for this are in `apps/board/unit/wizard.test.tsx` and `packages/conductor/unit/wizard-page.test.ts`. Write the regression from `#371`'s attempt 1 there: one move of each dial on a recipe that is silent about limits, in both directions, through `editExisting`. Each move must be offered, and the `file` returned must carry exactly that one key. That is the board row being alive, checked in the unit half.

## The migration order in the ticket is backwards for the daemon. Say so in the commit body and in `operating.md`

The ticket says to move the blocks into the recipes **before** this lands. But the daemon that is conducting runs the code it started with (CLAUDE.md, *"A running daemon holds the code it started with"*), and that code refuses `runtime.limits` in a recipe (`local.ts:414-421`). So a recipe migrated while the old daemon is still conducting is refused on every pass from then on, as `stage: "recipe"`, and the queue stops. Migrating after a restart onto the new code has the mirror problem: the machine file is refused. Neither order is safe while a conductor is running.

The order that changes no number and refuses nothing:

1. Let this land.
2. `pnpm lingtai shutdown "#375: moving runtime.limits into the recipes"` and wait for the drain to finish.
3. Move both blocks, comments included, and delete them from `config.yml`.
4. `pnpm lingtai restart`. Its doctor check is then running the new code against migrated files.

The agent cannot do any of this, because `~/.lingtai/` is outside the worktree (0046 §4). Write it in the commit body and as an upgrade note in `doc/operating.md`, so that the person reads it before restarting. Do not put it in a test.

## What this does not touch

`resolveAgent`, the `agent` refusal in the recipe callback, and the `runtime.agent` half of `machineFiles` all belong to `#372`. The limits row in `lingtai doctor` (`doctor.ts:1652`) and `filter.ts:228-233` already read through `ceilingOf` and need no change. Every claim above can be checked in `pnpm test`; none of it depends on the integration half.
