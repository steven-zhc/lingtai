## #1422: how to build it

The ticket's line numbers have drifted. More importantly, `readPrPage` does not call `readProjectPrs` the way the ticket assumes. Both points change where the edit goes.

### 1. The PRs board stops reading through `prsOf`

`readPrPage` gets its PRs from `prsOf(project)` (`apps/board/src/lib/prs.ts:151`), not from `readProjectPrs`. `prsOf` is a per-request `cache()` (`prs.ts:99`), and its comment fixes what it is:

> *"`readProjectPrs` for one request, once: every PR, never a `since`, through `requestStore()`. **A reader added later goes through this one**; a page that needs the `since` cut asks `readProjectPrs` itself, and reads through the same store."* (`prs.ts:96-97`)

`prsOf` is shared with `readLandedWhere` (`:205`), `readPrDetail` (`:324`), `readOnBranch` (`:453`) and `readSearchPrs` (`:473`). So:

- Do not add the option to `prsOf`.
- Do not add a second cached variant.
- In `readPrPage`, replace `Effect.tryPromise({ try: () => prsOf(project), catch: failed })` with `readProjectPrs(project, requestStore(), { merged: MERGED_SHOWN })`, yielded inside the `Effect.gen` that is already there. That adds no `async` and no `Effect.run*`, so the ratchet does not move.

Nothing else on `/pr/<project>` reads `prsOf` in the same request:

- `page()` in `apps/board/unit/request-reads.test.ts:111-117` lists what the page calls.
- `placeViewsOf` reads only `waitingPrs` (`prs.ts:237`).
- The ⌘K reader is a separate request (`app/api/search/route.ts:52`).

So the #1420 test *"reads prj once and each PR stream once"* (`request-reads.test.ts:144`) still holds unchanged. It has three PRs, all `requested`, which is under the cut.

### 2. Chunks are sized by how many merged PRs are still wanted

`readProjectPrs` no longer walks one PR at a time. It reads chunks of `READ_CONCURRENCY` (`= 8`, `packages/project/src/pr.ts:674`) in parallel, and the `since` cut throws away the rest of its chunk:

> *"Reads past the cut in its own chunk are dropped, errors included."* (`prs.ts:70-72`)

If the merged cut worked the same way, ten merged PRs would read eight streams. The Done-when test asks for five. So:

- Each chunk is `Math.min(READ_CONCURRENCY, high, wanted)`, where `wanted` is `options.merged` minus the merged PRs counted so far. Without `merged`, the bound is just `Infinity`, so the default is unchanged.
- The fifth merged PR is always the last read in its chunk, so this cut never reads anything it then throws away.
- A failed read, a `null` stream or a `draft` PR does not reduce `wanted`. The next chunk is sized again.
- `since` and `merged` can both be given, and the walk stops at whichever comes first. No caller passes both. Keep the `since` check where it is.
- The return value is still `reads.reverse()`, oldest first.
- Update the doc comment above `readProjectPrs` (`prs.ts:53-60`) to cover `merged`.

Test it the way the `since` test does (`unit/pr-board.test.tsx:96-118`): a memory store, with `store.read` wrapped to record stream ids.

- Ten merged PRs with `{ merged: 5 }`: exactly PRs 6–10 are read, and 6–10 are returned.
- Add a `draft` PR at 11: streams 11 and 6–10 are read, and 11 is not returned.
- Without the option: all ten are returned.

`topPrNumber` (`prs.ts:43-51`) still makes one `head` call per PR. Those are head reads, not stream reads, and fall under #1420 and #1421. Leave them alone, and say so in the PR description so nobody reads "cost no longer grows" as covering them.

### 3. Failed reads are not drawn in Merged

The ticket says a failed read is "drawn as the failed card where it is today". Today that is the **In progress** column, not Merged (`pr-board.ts:373-381`):

> *"Unreadable: it belongs to no column we can name, so the failure is drawn where the open work is."*

So `mergedAll` never holds a failed card, and the `.filter((c): c is CardView => !c.failed)` on `older` (`:623`) goes away with `older`. In the Merged column:

- `cards: mergedAll.slice(0, MERGED_SHOWN)`. The slice is a guard; the read already cut the list.
- `count: mergedAll.length`.
- `unread` stays as it is (`:625`). A failed read still makes the count a floor.
