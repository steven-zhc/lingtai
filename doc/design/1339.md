# #1339: the shape of the change

## The one decision that is not obvious: where the CI read happens

The ticket says the verdict is "decided on #1317's sweep read". **Do not add a checks read to `learnPrEnds`** (`packages/conductor/src/pr.ts:698-718`). The read belongs inside the `ci` step's own `run`. The sweep reaches that step already:

- `sweepPrs(true)` calls `resumePrs()` on every timer tick (`packages/daemon/src/work-loop.ts:476-479`). Its comment reads: *"A tick resumes them too: a step that answered `again` is retried here."*
- `resume` is `servePendingPrs`, which walks every PR whose status is `in-progress` (`pr.ts:506`).

So `ci` does one `observe` and one verdict each time it is served. It answers `again` while the verdict is `running`, and the next tick asks again. That gives:

- One append path. `walkPr` (`pr.ts:425-474`) is the only place that records `PrWaiting` or a step record.
- One fence. `walkPr:452-453` already throws away an answer whose `target` moved underneath it, which covers a pr-fix landing. A second writer in the sweep would have to repeat that fence.
- `ready` and `summary` are never run from the un-tracked sweep fiber. `stop()` does not wait for that fiber (`work-loop.ts:470-475`), and a GraphQL write must not be interrupted halfway.

The price is latency. Green becomes *In review* up to `SWEEP_MS` (5 min, `work-loop.ts:174`) after the last check finishes. That is acceptable, and the ticket already says so: CI "is read on the sweep".

**`bounded` must cover the new reads.** It wraps only `findOpenPull` and `getPull` (`pr.ts:555-561`), and spreads the rest of the client unbounded. Add `checkRunsAt` and `combinedStatusAt` to it, using the same `within(...)` and `GitHubFailed(0, …, 'timed out')`. A stalled checks read would otherwise hold the drain, because the walk is tracked (`work-loop.ts:462`). `markReadyForReview` is a **write** and stays unbounded, the way `push` is (`pr.ts:546-550`): *"A push is a write and is waited for"*. `ready`'s `getPull` look before the mutation makes it safe to run twice.

## How the provider reaches the step

The steps return `Effect<StepAnswer, Error>` with no requirements (`pr.ts:122`). `walkPr`, `servePr` and `makePrHandlers` all carry that. The GitHub face is *"A value, as 0101 §5 has it: passed in, not provided"* (`packages/github/src/client.ts:235-239`). So:

- Declare `CiProvider` in `ci.ts` with `Context.Service`, as this codebase writes services (`packages/conductor/src/ports.ts:190`). It is the interface every adapter implements and the tag fakes are written against.
- `PrPorts` gains `ci(project): Effect.Effect<CiProviderShape | null, Error>`. The live port resolves it from `ciOf(recipe).provider` (`packages/recipe/src/settings.ts:266-286`) through `CiProviders`:
  - `none` returns null.
  - `detect` builds `github-actions` and asks its `detect`.
  - The `github-actions` adapter is built over `ports.github(project)` and `ports.git(project, …)`.
- In the step, `Effect.provideService(CiProvider, provider)` around its CI part keeps `walkPr`'s requirement `never`.
- The source test the Done-when asks for: `pr.ts` imports nothing from `ci-github-actions.ts`. Only the live port (`apps/cli/src/pr-ports.ts` and the daemon's equivalent) names the adapter.

`ciOf` defaults matter to the verdict: `timeoutMs` is 3 600 000 when unset, and `required` is `'all'`, not `[]` (`settings.ts:276-279`).

## The reducer (`packages/domain/src/pr.ts`)

- **`PrChecked { verdict: 'green' }` is the `ci` step's record**, folded through `withStep` (`pr.ts:83-86`), the way `PrPushed` is `push`'s (`pr.ts:127-130`). That is the step's `record` in its `done` answer, per *"appended in place of `PrStepDone`"* (`conductor/src/pr.ts:100-104`). `PrCiSkipped` is the same.
- **`PrChecked { verdict: 'red' }` is not folded into `steps`.** If it were, a retry would skip `ci`. It sets a new `checked: { headSha, verdict } | null` field instead, and that field is what *"the same verdict on the same head appends nothing"* is checked against. `PrInProgress` does not reset `checked`. It is keyed by head, so a new head is a new read with no reset needed.
- **On red the step makes two appends**: `PrChecked red`, guarded by `checked`, inside its own `run`, and then the `wait` answer that `walkPr` records. A kill between them leaves `PrChecked` recorded and the wait not. The next serve finds `checked` equal, appends nothing, and answers `wait`.
- **`pushedAt`**: add `pushedAt: Date | null`, set from the `PrPushed` envelope's `at`. That event is appended for `found: 'existing'` as well (`pr.ts:193-196`). The 30-minute rule anchors there, and nothing else carries the push time today.

## The verdict, where the ticket leaves a gap

The ticket says *"a required name absent from the head is still running"* and *"`timed-out` when the oldest counted check started more than `timeoutMs` ago"*. Taken together, a required check that never appears, beside counted checks that are all green, stays `running` forever. **The timeout anchors on the oldest counted `startedAt`, or on `pushedAt` when no counted check has one.** A missing required check therefore ends in `timed-out`, not silence.

`none-started` still means there are no counted checks at all and `now - pushedAt ≥ 30 min`. Take `now` from `Clock.currentTimeMillis` inside the step, so `TestClock` drives the 30-minute and timeout tests.

## Events and their readers

- `PrWaitReason` (`packages/domain/src/events.ts:2558`) gains `ci-red`, `ci-none-started` and `ci-timeout`.
- Each new event needs:
  - its entry in `packages/domain/scripts/events.ts`, beside `PrOpened` (`:324-327`, `:515-518`);
  - its stream tag (`events.ts:3059-3062`);
  - **a sentence in `apps/board/src/lib/history.ts`**, beside `PrOpened` and `PrWaiting` (`:494-506`).
- `PrChecked.checks` carries the full `CiCheck` minus timings, **including `artifacts`**. There is no PR page on the board yet: `apps/board` reads PR events only in `history.ts`. So in this diff the "lists artifacts" line is `lingtai pr`'s (`apps/cli/src/pr.ts:100-103`, beside the `waiting on you` and `pull request #` lines). #1319 and #1320 draw the page from the same payload.

## `ready`

- `PullState` (`client.ts:158-164`) has no `draft`, and `getPull` validates exactly *"the five fields read"* (`client.ts:1016-1036`). Add `draft: boolean` to both. The sweep's fake in `packages/conductor/unit/pr-sweep.test.ts:57` returns a `PullState` and needs it too. The fakes are `as unknown as GitHub`, so no other fake breaks on typecheck.
- `markReadyForReview(nodeId)` goes through `send('POST', '/graphql', { query, variables })`. Then read the body:
  - an `errors` entry with `type: 'FORBIDDEN'` → `PermissionDenied(…, 'pull_requests', 'write')`;
  - any other non-empty `errors` → `GitHubFailed` naming the messages;
  - `data.markPullRequestReadyForReview.pullRequest.isDraft !== false` is a failure too.

  The step lets a non-person failure fail the effect, as `openStep` does (`pr.ts:331-332`). The walk is logged and retried on the next tick, and no `PrOpened` is appended.
- A host of `none` never reaches `ci` or `ready`: `openStep` appends `PrOpened` (`pr.ts:285-290`), the status becomes `in-review`, and `walkPr` stops (`:434`). Say so in the step's doc comment rather than adding a branch.

## Smaller decisions

- `start` is called only when `capabilities.trigger === 'api'`. No 0.16 adapter has that trigger, so nothing records *once per head*. The Jenkins ticket adds the event that does.
- `detect` runs against `state.target`, which `push` proved is in the mirror (`pr.ts:214`). `ls-tree` exits 0 with empty output when `.github/workflows` is absent, which means `none`. Exit 128 is a failed read, so the step answers `again`, never `none`.
- Map `403 && !isRateLimited` exactly as `asPullCall` does (`client.ts:749-754`), with `'checks'` and `'statuses'` as the permission names.
- **`lingtai pr retry` (#1314) is not built.** `apps/cli/src/pr.ts` has only `pr` and `pr submit` (`:3`). What this ticket owes it: after any CI wait, `ci` is not in `steps`, so whatever transition brings the PR back to `in-progress` re-runs it. Test that with the transition that exists, `recordPrRestart`. It re-walks `push` as `existing` and `open` from `state.host`, then reads checks again. Note that this re-appends `PrPushed` and so restarts the 30-minute clock, which is the right answer to *check again*.
- ADR 0130 §5 already carries the `CiProvider` paragraph (`doc/decisions/0130-a-project-is-solo-or-team.md:156-187`), so do not edit it. Edit 0114 §3's table in place (`doc/decisions/0114-a-github-app-not-a-token.md:85-93`), as the ticket says. That ADR is a topic ADR from 0100 up, which this repository edits rather than supersedes.
