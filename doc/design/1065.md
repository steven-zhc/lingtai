**#1065 design note: the shape is the one in the ticket, with three facts checked against this worktree**

The ticket's design holds. What follows are three things the ticket assumes, checked in this worktree, plus one point the doubles depend on.

1. **RUNTIME-1a has landed, so line numbers are one line later than the ticket's.**
   - `Runtime.run` is at `packages/agent/src/runtime.ts:263`.
   - `runtimeVersionOf` is at `:303`, beside `runtimeVersionOfEffect` at `:290`. Put `runtimeRun` right after it, in the same two-line form: `export function runtimeRun(…): Promise<RunOutcome> { return Effect.runPromise(runtime.run(request)) }`.
   - The adapter call sites are where the ticket says: `claude-code.ts:435` (`runClaudeCode` at `:695`), `codex-text.ts:40`, and `codex.ts:1417`.

2. **Interrupting a run no longer aborts `request.signal`. Each adapter stops its own run, so nothing else needs to.**
   - `dispatchRuntime` (`packages/actions/src/agent-action.ts:244-286`) ran each dispatch with a fresh `AbortController`, combined with the caller's signal through `AbortSignal.any`. On interruption it aborted that controller (*"An interruption aborts the run and then waits for it to settle"*).
   - Once it is deleted, an interruption does not abort the signal the adapter sees. It reaches the adapter's own finalizer instead.
     - `claudeCodeRun`'s finalizer calls `onAbort()` itself and then waits for `finish` (`claude-code.ts:681-689`: *"Interruption kills as an abort does, and waits for `finish`"*).
     - `codexTextRun` aborts its own `AbortController` in the release of `Effect.acquireRelease` (`codex-text.ts:74-80`).
   - So the adapters need no change. The doubles do. Any double that learned about interruption by listening to `request.signal` will now never hear it. That is why the ticket's step 2 makes them `Effect.callback` with an interrupt finalizer.
   - Do not "fix" this by passing a controller down into `run`. The ticket's design is that the wait belongs to the adapter's interruption, not to an abort.

3. **The step span parent is real, and it comes from the conductor.**
   - The `step ${spec.step}` span is opened in `packages/conductor/src/run-attempt.ts:1992`.
   - The judge's `Effect.withSpan('action judge', …)` is at `conduct.ts:2933`.
   - `firstDispatch` is at `conduct.ts:3939` and runs inside the step's fiber, so `agent.run` there has `step implement` as its parent.
   - Plugins' action spans come from `inSpanEffect` (`packages/actions/src/spans.ts:101`). Its doc says *"The span is not made active around `body`"*, so the fiber never sees it. That is why the reviewer's and the draft's `agent.run` sit under the step span and not under `action agent`.
   - The new `trace-an-attempt.test.ts` case should assert on parent span **names**: `action judge` for the judge's `agent.run`, and a name starting `step ` for every other one. Do not assert on a fixed count of `agent.run` spans. How many there are depends on the recipe's steps, and that count goes red whenever an unrelated step is added.

4. **Writing the step 2 doubles.** In effect `^4.1.2` the callback form is `Effect.callback<RunOutcome>((resume) => { …start…; return Effect.suspend(() => { …what the abort listener did…; return settled ? Effect.void : Effect.callback<void>((done) => { onSettled = () => done(Effect.void) }) }) })`. This is the same shape as `claude-code.ts:684-689`, so copy it from there rather than inventing a new one.
   - Each double keeps its event pushes (`'aborted'`, `'settled'`) at the same points they fire today. That is what keeps the asserted orders unchanged:
     - `conduct-the-implementer-is-in-the-fiber.test.ts:88`
     - `conduct-the-judge-is-in-the-fiber.test.ts:80`
     - `agent-port.test.ts:118`
