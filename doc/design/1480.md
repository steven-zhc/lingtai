A redone step currently records only who asked for the redo and what was said. Recording why it was redone is two call sites, one schema field and one board function. One part isn't obvious from the ticket: which kinds the line may quote.

## Where it goes

**There are two `redoStep` call sites, not three.** The rule route is at `packages/conductor/src/run-attempt.ts:2254` and the crash route at `:2769`. Between them they produce all five kinds. `emitStepRedone` (`:1529-1540`) is still the one place that appends the event, as its comment says: *"The one place `StepRedone` is appended"*. Make `cause` a **required** field on `redoStep`'s argument (`:1796-1805`) and pass it through to `emitStepRedone`, which writes it beside `unread`. Because it is required, a fourth call site cannot be added without naming a kind.

**Compute `cause` once at each call site, and build `why` from it.** That way the redo's brief (`:1858`) and the history row cannot disagree.
- **Crash route.** The same three-way choice `why` already makes at `:2775-2779` gives the kind. `failed` means agent-did-not-finish. Otherwise `again.expected` means transient, and anything else means crash.
- **Rule route.** Branch on `next.step === 'prepared'`, which is the condition `why` uses today at `:2264-2267`. `prepared` means registry-5xx; anything else means answer-unreadable. Do not switch to `offer.proposal._tag` (the key `said` uses at `:2258-2263`). Doing so could only change which kind an existing row gets, and this ticket only rewords.

**Schema.** Add `cause: z.enum([...]).optional()` to `StepRedone` (`packages/domain/src/events.ts:1770-1782`), with a doc comment saying that rows written before #1480 have no `cause`. Use these values: `transient`, `crash`, `agent-did-not-finish`, `registry-5xx`, `answer-unreadable`. `StepRerunInPlace` is the same object (`events.ts:1789`: `export const StepRerunInPlace = StepRedone`), so it gets the field too. That is harmless, because nothing appends that event any more (`:1784-1785`: *"Nothing appends it again"*).

Also reword two places in `events.ts`:
- the `@summary` at `:1768`;
- the first sentence of the prose at `:1760` (*"A run an API error cut off is run again in place"*). It makes the same claim, and it is not in the generated file.

Then run `pnpm events:generate` (`package.json:35`).

## The decision the ticket leaves implicit: quote by kind, not just by `unread`

The ticket says never to quote `said` when `unread` is set. That guard alone does not cover answer-unreadable. On the rule route `said` is `offer.proposal.raw` (`:2262`), which is the agent's own unreadable answer (`packages/domain/src/action.ts:100-104`: *"The agent answered, and the machine could not read it"*). Yet `redoStep` is called there without `unread` (`:2254-2270`), so the row carries no `unread: true`.

So `stepRedoneLine` decides whether to quote from the kind:

| `cause` | quotes `clip(said)`? | why |
|---|---|---|
| `transient` | yes, when non-empty | runtime's error text (`reason.detail`, `:2774`) |
| `crash` | yes, when non-empty | runtime's error text. This is the case that fixes the Foundry row |
| `registry-5xx` | yes, when non-empty | registry's output (`proposal.output`, `:2259`). `''` when the proposal had none |
| `agent-did-not-finish` | **never** | `said` is the agent's tail (`unread`, `:2765-2768`, #1398) |
| `answer-unreadable` | **never** | `said` is the agent's raw answer |
| absent / unrecognised | **never** | neutral line; nothing is inferred from `said` |

On top of that, `unread: true` suppresses the quote whatever the kind. That keeps the ticket's own test honest, even for a row with an odd combination of fields.

## The board

Everything stays inside `stepRedoneLine` (`apps/board/src/lib/history.ts:857-859`), which both event names already use (`:592-593`). Read `cause` from the loose `Payload` as a string, and look it up in a local `Record` of the five values. A miss falls through to the neutral line: `<step> stopped and runs again in place, after N min (rerun k)`. Do not parse it with the domain's `z.enum`: a value the board doesn't know must give the neutral line, never throw. Reuse `clip` (`:199`) as it is.

Word each kind as an event, not a diagnosis. For example: *"implement crashed on an error no rule recognises — "lingtai-hook: …" — and runs again in place, after 5 min (rerun 2)"*. Only `transient` may contain the words "API error". The test asserts that, so write the five strings once in a table and have the test loop over it.

Do not touch `routedLine`'s `RerunStep` branch (`:870-872`). It already quotes the route's `why`, and the ticket puts the other lines out of scope.

## Tests, and what they cost

- **Board.** In `apps/board/unit/history.test.ts`, the `StepRedone` fixture at `:260` has no `cause`, so it becomes the old-row case for free. Add:
  - one row per kind;
  - a `StepRerunInPlace` row;
  - an unknown `cause`;
  - `unread: true` with a quotable kind;
  - `registry-5xx` with `said: ''`, checking that nothing dangles after the kind.
- **Conductor.** `packages/conductor/unit/what-an-attempt-writes-today.test.ts` already drives the crash redo to `BOUNDS.stepRedos` (`:772`, `:1680`, `:1742`). It only counts the rows by type, so adding the field breaks nothing there. Add assertions on `data.cause` next to those counts, and next to whichever test drives the rule route's `RerunStep` for `prepared` and for an unreadable answer. Each writer's kind is checked at unit level; none of this needs `pnpm test:integration`.
- **Untouched by this change:**
  - `packages/conductor/unit/step-redos-and-landing-retries.test.ts:81` builds a row without `cause` and only checks the reducer.
  - The reducer reads `rerun`, not `cause`, so neither the reducer version nor `run-codec.ts` changes.
  - `packages/domain/unit/one-reducer.allowlist.json` names `StepRedone`. It should not need an edit, since no reducer reads the new field; if its test goes red, the reducer has started reading `cause`, and that is the bug.
- **`events-json.test.ts`** goes red until `doc/events.json` is regenerated. That is expected, not a reason to touch the test.

No new `async` function and no `Effect.run*` are needed: the field rides on an existing `options.emit` inside `Effect.gen`. The ratchet baseline does not move.
