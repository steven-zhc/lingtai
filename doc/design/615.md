## What the ADR has to get right that the ticket does not spell out

**1. The palette already exists. The ADR adds glyphs, not colours.** `packages/env/src/colour.ts:94-110` defines `paint.pass` (green), `fail` (bold red), `signal` (yellow), `held` (magenta), `accent` (cyan) and `muted` (dim). The comment there explains why: *"It is the board's vocabulary, not a second one"* (`colour.ts:9`). And amber: *"**Nothing else may use this**, on either surface: the moment amber means two things it means neither"* (`colour.ts:101-104`). That file has no glyphs today; a grep finds no `✓`/`✗`/`●` in `packages/env/src` or `apps/cli/src`. So the ADR's table pairs each glyph with an existing `paint` key:

| glyph | paint key | meaning |
|---|---|---|
| ✓ | `pass` | passed |
| ✗ | `fail` | failed |
| ● | `signal` | waiting on you, and nothing else |
| (no glyph) | `held` | held by a person |
| (no glyph) | `accent` | headings and running things |
| (no glyph) | `muted` | ids and clocks |

State colour by quoting `stateInk` (`colour.ts:121`). Don't restate it as a list of its own.

**2. Plain mode is the same text without escape codes. It is not a different layout.** This is the decision that makes "readable without colour and when redirected" (#548) true. Colour must never be the only carrier of a meaning: the glyph and the words carry it, and colour repeats them. Under plain mode the glyphs stay, because they are UTF-8 text and not escapes, and the alignment stays.

The ADR names `coloured()` (`colour.ts:59-68`) as the one place that decides plain mode. Its order is `NO_COLOR`, then `TERM=dumb`, then `FORCE_COLOR`, then `isTTY`, and it should be quoted rather than redescribed. `--no-color` is new. Define it as `NO_COLOR` for that process, so it beats `FORCE_COLOR` for the same reason `NO_COLOR` does (`colour.ts:49-51`).

Width rule:
- Don't wrap to the terminal.
- Keep each content line to a single fact.
- Where `columns` is narrower than a table, render each row as a key/value block.
- A redirected stream has no width, so it is never truncated to one. The existing 140-character one-line cap in `status.ts:39` (`oneLine`) is a content rule, not a width rule, and it stays.

**3. `--json`: one document on stdout, including on failure.** Make the ticket's rule concrete:
- A command is a "read command" when its definition says it only reads (point 5). Every read command takes `--json`.
- Under `--json`, stdout carries exactly one JSON value and nothing else: no prose, no progress lines.
- The top level is `{ "version": 1, "command": "<name>", ... }`. `version` is a per-command schema version, and adding a field does not bump it.
- A failure is still one document on stdout, `{ "version": 1, "command": …, "error": { "code": …, "message": … } }`, with a non-zero exit. That way a script needs one parser and one exit code. stderr is for people and is never parsed.
- Under `--json` there are no colours and no prompts.

**4. Help works with no project configured and no network (#549).** `apps/cli/src/entry.ts:5` already says *"Five commands answer before the rest is imported"*, which keeps them off the log. The ADR makes `help`, `--help` and `<command> --help` the sixth case: they are answered from the command definitions alone, before `lingtai.ts` is imported.

It also generalises the rule `lingtai.ts:1154` states for one family of commands: *"`--help` is a question, never an instruction"*. `--help` anywhere in the arguments prints help, does nothing else, and exits 0.

**5. A command's definition is the one source.** Each definition carries:
- its group (everyday / waiting on you / daemon / install and upkeep)
- a one-line task
- `reads` or `changes`
- one or two examples

`lingtai --help`, `lingtai <command> --help` and `doc/cli.md` are all generated from those definitions. The hand-written `USAGE` string at `lingtai.ts:111` is what this replaces, so say in Consequences that it is deleted when this is built, not edited.

Also give the group of every command `lingtai.ts` dispatches today (the `switch` that ends at `lingtai.ts:1550-1556`), each in exactly one group, so the building ticket has a table to check against. The test for a correct assignment: **waiting on you** holds the commands that answer a 0118 wait (`approve`, `answer`, and the like); **daemon** holds `daemon`, `restart`, `shutdown`, `pause`, `resume` and `service`; **install and upkeep** holds the five from `entry.ts:5` plus `doctor` and `projection`.

**6. Libraries, and the comment they contradict.** The ADR names `@effect/cli` for parsing and the command definitions, and `@clack/prompts` for interactive input. Neither is a dependency today (`apps/cli/package.json` has only `effect`).

`lingtai.ts:5` says *"Deliberately hand-rolled argument parsing. design.md §8 is a list of things not being built until a specific failure demands them"*. §8 (`doc/design.md:307`) does not actually list argument parsing, and `design.md` is not an ADR. **No supersession is needed.** The ADR's Context should name the specific failure §8 asks for: commands grew their own prose, scripts parse that prose, and help is maintained by hand. Consequences should say the `lingtai.ts:5` comment goes when this is built.

`@effect/cli` fits `0101`'s *"Effect where something is acquired and where configuration is read"*, so cite 0101 for it.

For prompts there is already a rule to carry over: `USAGE`'s `--defaults` text says *"With no terminal, one of this or an answer to every question is required"*. State it generally: a prompt never appears without a TTY. Every question has a flag, and when there is no terminal and no flag, the command refuses by name.

## The `status` example

Build the "today" half from the `log(...)` calls in `apps/cli/src/status.ts:90` onward. Don't invent it: the header `` `${name}  base=…` ``, the `describeFilter` lines, `offerLine`'s `` `  from ${source}: ${count} eligible` ``, the `dependenciesUnread` line, then the runnable and passed-over rows. You cannot run it against a real log, so label it as reconstructed from `status.ts`.

The "after" half shows:

- a key/value block for the project (base, recipe, kinds)
- a table of queued rows, with ids `muted`
- a `●` line per waiting task, worded with 0118's *what is asked*
- a closing *next step* line

Take the `--json` field names from what the function already computes:
- `project`, `base`
- the filter's `ok`/`kinds`/recipe hash
- `source`, `eligible`, `passedOver`, `dependenciesUnread`
- `runnable[]` (`taskId`, `ref`, `kind`, `restarts`)

Don't introduce a field the code has no value for. The example is illustration: put it in its own `## Example` section after Consequences, so it doesn't read as an additional clause of the decision.
