# Design: #473, the read model and the builders

## Where it goes, and the one move this ticket makes

Three files are new: `packages/domain/src/read-model.ts`, `packages/domain/test/events.ts` and `packages/domain/unit/read-model.test.ts`. One more thing has to happen before the builders can be written without a second mapping: **`eventOf` and `holdOf` move from `packages/conductor/src/adapters.ts` down into `@lingtai/domain`, and nothing in them changes.**

Why they have to move:

- **The builders have to emit today's events.** `aStepEnded(outcome)` has to produce today's step events, and `aWait(reason)` has to produce a `WorkItemBlocked{hold}`. Those two directions already exist as `eventOf` (`adapters.ts:421`) and `holdOf` (`adapters.ts:700`).
- **Domain cannot reach them where they are.** `@lingtai/domain` depends on `zod` and nothing else (`packages/domain/package.json`; 0101 §4 is cited at `route.ts:17`). Conductor depends on domain, so a builder in `packages/domain/test` that imported `adapters.ts` would close a package cycle.
- **Copying them is the second mapping the ticket forbids.** So they move.

What makes the move safe:

- **Their dependencies are already in domain.** `holdOf` uses `Hold`, `diagnoseRefusal`, `@lingtai/domain/wait` and a local `said`. `eventOf` returns `ActionEvent` (`packages/actions/src/action.ts:535`), which is just a union of `{ type, data: PayloadOf<…> }`. Declare the same union in domain (as `StepEvent`, say). It is structurally assignable to `ActionEvent[]`, so the callers need no cast.
- **Where they go:** put them in `packages/domain/src/adapters.ts` with the header's paragraphs on `eventOf`/`holdOf`, which explain `plugin`, `threwRatherThanAnswered` and `said`. Export `eventOf` and `holdOf` only. Do **not** re-export any `wait.ts` name from `index.ts`: `wait.ts:15-26` explains the TS2308 collision that keeps `WaitReason` on the subpath until #464.
- **No cycle inside domain.** The new file imports `hold.ts`, `wait.ts` and `events.ts`, and none of those may import it back (`wait.ts:33-35`, `hold.ts:15-19`).
- **Conductor's side.** `actionOf` and `outcomeOf` stay in conductor, because they read `@lingtai/actions`' `ActionResult`. Conductor's `adapters.ts` re-exports `eventOf` and `holdOf` from `@lingtai/domain`, so `pass.ts`, `conduct.ts` and `conductor/unit/adapters.test.ts` keep their imports. `adapters.test.ts` going green unchanged is the proof the move changed nothing.

This is not "moving a reader": `eventOf` and `holdOf` are the writer-side adapters. Make the move its own first commit.

## The read model's input is one item's slice of the log, not one stream

The ticket says "over a stream's events", but the facts each function needs are spread across streams:

| Fact | Where it is written |
|---|---|
| `PassRestarted` | the work item (`conduct.ts:3936`) |
| `FixRequested` | the run |
| `ApprovalGranted` (the `onSha` of `Approve`) | the run, `store.append(runId, …)` (`approve.ts:307-318`) |
| `IntegrationRefused`'s `paths`/`baseSha`/`headSha` | the integration stream |
| the merge sha (`WorkItemLanded.mergeCommit`) | the work item |

So every function takes `readonly Envelope[]`: **one work item's events together with its runs' events (and its integration events where present), in `seq` order.** Each function filters by `type` and keys by `runId`, so it is correct on any superset. That is also what the projections see, since they fold in global `seq` order.

Skip unknown types rather than throwing. Read `data` as `PayloadOf<T>`, the way the existing folds in `work-item.ts` do.

## `stepOutcomesOf`: where the facts 0120 §1 wants come from

Today's step events carry `{step, action, runId, onSha}` and nothing more (`stepBase`, `events.ts:709`). There is no `yields`, no `plugin`, no `round` and no `head`. Each one has to come from somewhere:

- **`yields` and `plugin`.** Read them from the action's own entry in `StepsResolved.recipe` (`events.ts:753`), which is the canonical recipe keyed by step with each action's `name`. The plugin key gives `plugin`. `yields` follows the plugins' own constants (`packages/actions/src/*-action.ts`, e.g. `watch-action.ts:76`, where `then: fail` is `verdict` and anything else is `signoff`); write them as a table in `read-model.ts`.
  - A name that is not in the recipe is one `conduct.ts` injected. Answer it from a per-step default: `admit` → `worktree`/`worktree`, `implement` → `agent`/`commit`, `merge` → `merge`/`merge`.
  - **Check this before writing the table:** print `StepsResolved` from fixture row 1 and look at which names it lists.
  - The `recipe` field is absent on v1 and v2 rows (`events.ts:762-766`). Fall back to the defaults there too.
- **`round`.** It is 0 until the first `FixRequested`, then that event's `round` (`events.ts:1283`) for every step event after it on the run.
- **`commit` results at `implement`.**
  - Round 0: `RunProposedCompletion.headSha` gives `head`. `RunFailed.kind` (`events.ts:674`) gives `Interrupted{cause}` for `crash`/`timeout`/`aborted`, and `Completed{head: null, question: null}` for `no-commits`.
  - A fix round: `FixApplied.headSha` and `FixApplied.failure` play the same roles.
  - `StepAsked` gives `Completed{question}`.
  - **Never parse `detail`.** The one string test allowed is `threwRatherThanAnswered` (`adapters.ts:584`), which moves with `eventOf`.
- **`merge`.**
  - `Integrated.mergeSha` comes from the `WorkItemLanded.mergeCommit` that follows the lane's `StepPassed`; use `''` where it is absent, as `mergeResultOf` does (`adapters.ts:341`).
  - A conflict is `Conflicted` with `IntegrationRefused`'s three optional fields, `null` where absent.
  - Any other refusal is `IntegrationRefused{reason}`.
- **Interrupted cause without a structured source** (row 14d's reviewer wall). Answer `crash`, which is `verdictResultOf`'s own default (`adapters.ts:215`), and let the row's test record that.
- **`claim` and `end` produce no `StepOutcome`.** `accepts` answers false for every `yields` there (`action.ts:381`), and 0120 §6 runs them outside `runPass`. Row 15's three `claim` events fold to `[]`.
- **Group** by `(runId, step, round)`, actions in event order. Finish with the same `droppingNotReachedAfterACleared` rule (`adapters.ts:403`), so that `wellFormed` (`action.ts:496`) holds for everything this returns. Assert that in the tests.

## `routesOf`: what it actually reads today

The ticket names `FixRequested`/`PassRestarted`/`FixDeclined`, but **today's record of a route is `PassRouted{from, chose, to, why, ceiling}`** (`events.ts:1391`, written by `conduct.ts`). **`FixDeclined` has no writer in `src`.** Row 7 (`what-a-pass-writes-today.test.ts:530`) writes `PassRouted` twice and no `FixDeclined`. Read `PassRouted` and pair it with the other two:

| `PassRouted` | Folds to |
|---|---|
| `to` is `implement`/`design` | `Selected{candidate: 'fix-lines'}` (`'state-assumption'` when `from` is the step it returns to), with next `FixRound{to, round}`, where `round` is the next `FixRequested.round` |
| `to: 'claim'` | `Selected{'restart'}`, with next `Requeued{Restart{restart}}`, where `restart` is the next `PassRestarted.restart` on the item |
| `to: 'waiting'`, `ceiling ≠ null` | `Escalated{CandidateUnavailable{excluded: {id: chose === 'claim' ? 'restart' : 'fix-lines', because: CeilingReached{ceiling}}}}` |
| `to: 'waiting'`, `ceiling: null` | `Escalated{NotAsked}` |
| `to` later on the spine than `from` | skipped: that is `Advance`, which 0120 §5 says is not recorded |
| legacy `FixDeclined` | `Escalated{CandidateUnavailable{CeilingReached{rounds}}}`, per the 0120 appendix |

The candidate ids are `routing.ts`'s own: `'fix-lines'`, `'state-assumption'`, `'restart'`, `'hand-to-person'` (`routing.ts:142-218`).

Return `{ runId, from, decision: RouteDecision, next: CandidateNext }`. Both types are already exported from `routing.ts`. **The offer and the reply cannot be rebuilt from today's events, so do not return them.**

**One loss, stated in the code comment:** a judge that answered unreadably, or handed over (rows 13, 5), and no judge at all both read `NotAsked`. Nothing on `PassRouted` tells them apart, and `why` is a sentence.

## `waitsOf`: invert `holdOf`, and prove it through `holdOf`

One entry per `WorkItemBlocked`: `{ reason: WaitReason, resolution: Resolution | null }`. The inverse, using structured events from the same slice where `Hold` dropped a fact:

| `Hold` | `WaitReason` |
|---|---|
| `Question` | `OwnQuestion` |
| `Asked` | `AgentQuestion` (0120 §3: an `InputNeeded` with no judge "becomes the more specific `AgentQuestion`") |
| `Human` | `SignoffRequired`, with `action` from the run's `ApprovalRequested` |
| `Declined` | `FixerDisagrees` |
| `Routed{when}` | `ProposedEscalated` (below) |
| `CheckRed` | `CheckRefused`, with `action`/`findings` from the refusing `StepFailed`; `AnswerUnreadable{step: 'merge'}` if that `StepFailed` is `unreadable` |
| `MergeRefused` | `MergeRefused` |
| `Ceiling` | `BudgetExhausted{cause: kind, call: null}` |
| `DidNotFinish` | by the run's `RunFailed.kind` / `FixApplied.failure`: `crash`/`timeout`/`aborted` → `AgentCrashed`; `no-commits` → `NothingProduced`; none → `SetupRefused` |
| `SetupRefused` | `SetupRefused` |

For `Routed{when}`, the proposal is chosen by `when`:

- `red` → `BuildRed{output: raw}`
- `verify-failed` → `VerifyRed{output: raw}`
- `conflict` → `MergeConflict` from the hold's `paths`/`baseSha`/`headSha` and `raw`
- `findings` → `ReviewFindings` when `findings` is non-empty, otherwise `ReviewEmpty{said: raw ?? ''}`, **unless** that run's `review` `StepFailed` carries `unreadable: true`, which makes it `AnswerUnreadable{step: 'review'}` (`answerUnreadableHold`, `adapters.ts:916`, writes both onto `Routed{findings}`)

`because` is the `decision.because` of that run's last escalated route from `routesOf`. **`waitsOf` calls `routesOf`; do not fold `PassRouted` a second time.**

Resolutions:

| What follows the wait | `Resolution` |
|---|---|
| `WorkItemUnblocked{withdrawn}` | `Requeue` (0120 appendix) |
| an unwithdrawn unblock of an `OwnQuestion` | `AnswerQuestion{choice: note}` (`ask.ts:150`) |
| any other unblock | `Requeue` (`approve.ts:555`); `EditBodyAndRequeue` has no event today, so say so in a comment |
| `ApprovalGranted` on the hold's run | `Approve{onSha}` |
| `WorkItemClosed` | `Close` |
| nothing yet | `null` |

**The check that this is the adapter's mapping and not a second one:** for every `WorkItemBlocked` in the fixture, `holdOf(waitsOf(…).reason, pass)._tag` and its `step` equal the stored hold's. Write it as one helper the row tests call. A divergence is then a failing row rather than a quiet second table.

## `releaseCauseOf`

0120 §5's four causes have no type yet. Define `ReleaseCause` in `read-model.ts`, reusing `Restart` (`pass-next.ts:58`) and `Extract<RequeueCause, {_tag: 'NeverStarted'}>`, and adding `ByPerson{waitId: WaitId}` (`action.ts:33`) and `ClaimUnconfirmed`. Return one entry per `WorkItemReleased`, each `ReleaseCause | null`:

| Before the release | Cause |
|---|---|
| a `PassRestarted` (`conduct.ts:3936-3953`) | `Restart{restart}` |
| no `WorkItemClaimed` since the item's last release or landing (row 15c: `['WorkItemReleased', 'IssueUpdated']`, written at `conduct.ts:3514`) | `ClaimUnconfirmed` |
| the run's last step event is `StepNeverRan` | `NeverStarted{scope: 'work-item'}` |
| anything else: an ordinary failed pass (`conduct.ts:4131`), `unexpected failure`, `the run was interrupted`, a foreign claim (`reconcile.ts:671`) | `null` |

`null` is a real answer: 0120 names no cause for these, and "only `Restart` counts" holds either way. Today a person's requeue is a `WorkItemUnblocked`, never a release, so `ByPerson` is unreachable from today's log. Keep it in the type for #464 and leave it out of the fold.

## Builders (`packages/domain/test/events.ts`)

Build on `makeStream` (`packages/domain/test/support.ts`), which already validates every payload through `parsePayload`. They take the new vocabulary and return `Envelope[]`:

- `aStepEnded(runStream, outcome)` is `eventOf(outcome, runId)`. For a `commit` at `implement` it also writes the `RunFailed`/`RunProposedCompletion`/`FixApplied` that `stepOutcomesOf` reads.
- `aWait(itemStream, reason, pass)` is `WorkItemBlocked{hold: holdOf(reason, pass)}`.
- `aResolution(…)` writes the table above, backwards.
- `aRoute(…)` writes `PassRouted`, plus `FixRequested` or `PassRestarted`.
- `aRelease(…)` writes `WorkItemReleased`.

"Covers every event the four functions read" is checkable. Keep a `READ` constant in `read-model.ts` listing the types it consults, and have a unit test assert that each one is produced by some builder.

## Tests

- **`packages/domain/unit/read-model.test.ts`**: builder round trips, i.e. `stepOutcomesOf(aStepEnded(o))` equals `o` for each yield × result cell `eventOf` handles, with `NotReached` dropped. Plus the cells named above as losses, asserted *as* losses.
- **#461's rows**: add the assertions inside each existing `it` in `packages/conductor/unit/what-a-pass-writes-today.test.ts`, over `[...theItem, ...theRuns].sort(bySeq)`. **Do not rebuild the events in domain.** The point of that fixture is that the events are the ones `once()` actually wrote. That is one test per row by construction: 1, 2, 4, 5, 6, 7, 9, 10a, 10b, 11, 12, 13, 13b, 14a–d, 15, 15b, 15c, 16.

All of this is unit: no process and no filesystem (0060 §1). `pnpm test` covers it, and nothing here needs `pnpm test:integration`.
