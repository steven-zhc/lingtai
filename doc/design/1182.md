# #1182: shape

## The new code goes in `packages/project/src/draft.ts`

Move `setRecipeEffect`'s body (`write.ts:54-77`) into a pure function there: `(current: string | null, changes, path, said) → text`, or a refusal. It runs these steps, unchanged:

1. `widenStepsIfNeeded`
2. `editedText`
3. `orderSteps` and `commentWritten`, only when `current === null`
4. `resolveSource`

`draftRecipe(project, { home?, said? })` is an `Effect.fn`. It yields `ProjectFiles` (`files.ts:74`, a `Context.Reference<RecipeFiles>` defaulting to `diskFiles`) and reads `recipePath(project, home)` once through `filesEffect(port).read` (`files.ts:53`). That read's failure is `draftRecipe`'s failure. It returns a plain object over two variables, `current: string | null` and `recorded: RecipeChange[]`:

- **`set(changes)`** returns `Effect<SetRecipeResult, Refusal>`. It runs the pure function over `current`. A refusal leaves both variables untouched. On success, if the text differs from `current`, it replaces `current`, pushes `changes` and answers `written: true`. Otherwise it answers `written: false` and records nothing (the ticket's *retry* edge). This differs from today: `write.ts:73` calls `files.recorded(changes)` before the no-change check. Replaying a no-op is harmless, so follow the ticket. `set` does **not** skip an empty change list. `setRecipeEffect` doesn't either, and `previewSetup` relies on that.
- **`get(path)`**, **`text()`**, **`changes()`** are synchronous: no IO, so no Effect and nothing for the ratchet to count.
  - `get` uses the same parse as `readRecipeKeyEffect` (`write.ts:96-98`). Extract that as a shared pure `keyIn(text, path)` so the two can't drift.
  - `text()` returns `string | null`. It is null only when the file was absent and no `set` has succeeded.
  - `changes()` returns a copy.

**`said` moves from each call to the draft.** Today it applies when *that call* finds no file (`write.ts:66`). In the draft it applies on the `set` that turns `current` from null into text, which is the first successful one. This matches every caller today:
- `askRecipeEffect` passes `SAID` only on the one absent-path write (`recipe-flow.ts:349`). Seeds and every answer before it are collected rather than set (`:255-336`), and `askLanding` and `askLimits` come after it.
- `previewSetup` and `applySetup` pass `said` only when `before === null` (`apply-setup.ts:88`, `:114`).

Export `draftRecipe` and a `RecipeDraft` type from `index.ts`. `index.ts` re-exports `write.ts` with `export *`, so to stop exporting `setRecipeEffect`, delete it. Don't just leave it unlisted.

## `applySetup` still writes, and #1177 is not built

#1177 is **open and is not a blocker** of #1182: the only blocker on the issue is #1175. `changeRecipe` exists nowhere in the tree. `applySetup` (`apply-setup.ts:99-119`) is the one writer (#968), and it writes through `setRecipeEffect`. So until #1177 lands it is written like this:

1. Read `before` through `target.files`, as it does now (`:107`).
2. Build `draftRecipe(project, { home, said })` with `ProjectFiles` provided as `target.files ?? diskFiles`.
3. Call `set(answers.changes)`, mapping a refusal to the same `SetupWriteError` text it has today.
4. Only if `draft.text() !== before`, call `filesEffect(target.files).replace(path, text)`. `filesEffect` is already exported (`files.ts:53`), and its disk branch is the temp-and-rename write (`files.ts:27`).

Validation and editing stay the module's. Only the replace call sits in `setup`, for one ticket. Put a comment on it saying #1177's `changeRecipe` takes it. Don't keep `setRecipeEffect` under another name: that leaves the module with the same two writers, just renamed.

`previewSetup` becomes three steps: the draft over `target.files`, `set(answers.changes)`, then `text()`. It is never null here, because `set` always ran.

Change every one of them to take `draft: RecipeDraft`:

Every caller listed above runs inside the add flow (checked by grep), so none of this touches #1178's callers. The other option, a `RecipeFiles` view of a draft for the helpers, is `draftFiles` under a new name, so don't build it.
