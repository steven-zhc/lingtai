# #1420: share each stream read across one board request

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

## The decision: memoize the store per request, not each reader

The ticket's Fix says to wrap `readProject`, `currentRecipe`, `readPr(project, n)` and the PR list in `cache()`. Done that way, the PR streams would still be read more than once. None of the PR reads go through a board function: they happen inside `@lingtai/project`, and each one reads through the `store` it was handed.

- `readProjectPrs` calls the package's `readPr(project, n, store)` (`apps/board/src/lib/prs.ts:69`).
- `waitingPrs` → `openPr` → `listPrs` reads every PR stream again with its own internal `readPr` (`packages/project/src/pr.ts:105-107`, `:87-97`).
- `readDraftOf` → `readDraftTickets` → `readDraft` reads the PR streams a third time (`pr.ts:620-622`). That is the "twice or three times" in the trace.

A board-side `cache(readPr)` never sees any of those calls. The alternative is to rewrite `listPrs`, `openPr` and `readDraft` in the board on top of a cached reader. That copies the rule the file header warns about: "Numbers are found by `head`, never by listing streams — `listPrs`' own rule in `@lingtai/project`" (`prs.ts:4`).

The `prj` repeats work the same way. `currentRecipe` → `loadProject` reads `prj` three times in one call:

1. `readProjectStateEffect(project, store)` at `packages/project/src/load.ts:22`.
2. `readProjectEvents` inside `recordObservedRecipe` at `packages/project/src/commands.ts:173`.
3. `readProjectStateEffect` again at `commands.ts:180`.

`accountsFor` calls `currentRecipe` once for each registered project (`packages/conductor/src/account.ts:115,120`). That accounts for `locks.account`'s six reads, three per project.

**So the shape is one request-scoped memoizing `EventStore`, and every board reader passes it to the packages.** Put it in a new `apps/board/src/lib/request-store.ts`:

- `export const requestStore = cache(() => memoStore(eventStore))`. `cache()` is what scopes it to one request. A module-level instance would be the cross-request `Map` the ticket forbids.
- `read(streamId, fromVersion?)` and `head(streamId)` are memoized by `(method, streamId, fromVersion)`, and what is stored is the **promise**. That gives the ticket's two edges directly:
  - Two callers asking at the same time share the one in-flight read.
  - A rejected read is stored as a rejection for the rest of the request, never as `[]`.
- `append` and `appendAll` pass through to `eventStore` and **drop the memo for every stream in the batch, whether the append succeeded or failed**. A render can append: `recordObservedRecipe` writes a `ProjectRecipeChanged` when the recipe file differs from what the log recorded (`load.ts:26-29`, `commands.ts:177`). It runs under `withOneRetry` (`commands.ts:171`). If a memoized read survived a `ConcurrencyError`, the retry would see the same stale version and fail again. With the drop rule, `commands.ts:180`'s read after a real append is a fresh read. Since that read is correct, "`prj` once" holds on a request where nothing was recorded. Whether a given request recorded something is settled by a `ProjectRecipeChanged` on `prj-<project>` in that request's window, not by the count.
- Every other method (`readAll` and the rest of `EventStore`, `packages/event-store/src/event-store.ts:375-392`) is a plain pass-through.

The board then passes `requestStore()` everywhere it reads today:

- `readProject(project, store)` (`packages/project/src/state.ts:88`).
- `currentRecipe(state, undefined, undefined, { store })`. `RecipeLookupOptions` carries `store` through `LoadProjectOptions` (`packages/conductor/src/projects.ts:125`, `load.ts:17`).
- `readProjectPrs`, `waitingPrs`, `readDraftOf` and `spendByPr`'s neighbours in `prs.ts`, which today take `eventStore`.
- `accountsFor(requestStore(), project, recipeOf)` in `readProjectLocks` (`locks.ts:120-121`).

`readRegistered` should read through it as well. `loadProjects(log?)` takes a `Log`, not a store (`state.ts:113-117`), so build one: `{ store: requestStore(), queries: log.queries, snapshots: log.snapshots, waker: (n) => log.waker(n) }`. Read `log`'s members at call time rather than spreading the object, because `log` is deferred (`packages/event-store/src/index.ts:98`). `projects.load` reads every `prj` stream (`state.ts:107-110`). Without this, the page pays one `prj` read there and one more everywhere else.

## The cached readers on top

Keep the readers the ticket names, as thin `cache()` wrappers over the store. They save the recipe file read and parse, and the reductions, and they give later code one named entry point:

- `projectOf = cache((project: string) => readProject(project, requestStore()))`
- `recipeOf = cache((project: string) => …currentRecipe(state, undefined, undefined, { store: requestStore() }))`
- `prsOf = cache((project: string) => run(readProjectPrs(project, requestStore())))`

**Key them by the project name, never by a `ProjectState`.** `cache()` compares arguments by identity, so a state object from a different read would always miss. `accountsFor`'s `recipeFor` parameter receives a state, so pass `(state) => recipeOf(state.project!)`.

`placeViewsOf` (`prs.ts:200-218`), `readPrPage` (`prs.ts:120-170`) and `readLandedWhere` (`prs.ts:177-193`) switch to these readers. The homepage half of Done when is `app/page.tsx:863,1120,1263`, which call `placeViewsOf` and `readLandedWhere`.

Each reader's doc comment says: *a reader added later goes through this one, and reads through `requestStore()`*.

## What does not change

**Server actions keep the uncached readers.** That means `app/actions.ts:97-309,699-706,1153`: they read, append and read again. React's `cache()` also scopes to an action's request, so a memoized read there would serve the state from before the action's own append. Say this on `requestStore`'s doc comment. Pages and their loaders use it. Actions never do.

`apps/board` is not in `effect-ratchet.baseline.json`; it is a host edge. The packages are held at `0/0`. Nothing in `packages/` needs to change, and if something does, it stays an `Effect`.

Leave alone: `readControlOnce`, which reads through the snapshot store and is out of scope; `task.ts`'s own `cache()` readers; and `onBoardProjects`.

## The test

The test is a unit test in `apps/board/unit/`, and it must **mock `react`'s `cache`**. vitest has no `react-server` condition, so `cache` is a passthrough there. `timing-load-task.test.ts:105-106` says so: "vitest has no such condition and `cache` is a passthrough, so this is not a claim about the number of reads in a render". Without the mock, a count test either fails or asserts nothing.

Copy `task-loader-spans.test.ts:22-46`. Its mock keys a `Map` per `AsyncLocalStorage` run, so `renders.run(new Map(), …)` is one request. That file also mocks `@lingtai/event-store`'s `eventStore` (`:48-50`) and `node:fs/promises`'s `readFile` (`:47`), which is how the recipe file is served (`packages/project/src/files.ts:5,43`).

Back the mocked `eventStore` and `log.store` with `createMemoryEventStore()` wrapped in a counter on `read`. Seed it with a team project and a few PRs. Inside one run, call what `/pr/[project]/page.tsx` calls: `readRegistered`, `readProjectLocks`, `placeViewsOf(name)`, `pauseSlot(name)` and `loadPrBoard(name)`. Then assert:

- `prj-<project>` is read once and each `pr-<project>-<n>` once. No recipe change was recorded, so `recordObservedRecipe` did not append.
- A second `renders.run` reads them all again. That is the never-across-requests claim, and it is what keeps *the board follows the log* true.
- A store whose `read` rejects for `prj` gives `readPrPage` `{ kind: 'failed' }` and `placeViewsOf` its `waiting: null` view in the same run. That shows the failure was shared and never turned into an empty value.

Everything here is checked by `pnpm test`. Nothing depends on `pnpm test:integration`.
