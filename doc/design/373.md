## Shape for #373: `assignee` is the recipe's, and the machine file refuses it

### The premise needs one correction before anything else

The recipe's `queue.assignee` **is already read.** There is no top-level `queue:` key. `queue:` is a plugin at `claim` (`recipe.ts:1138-1173`, `QUEUE_FIELDS` at `recipe.ts:1084-1089`). `assigneeOf` reads it before anything else:

```ts
// settings.ts:315-316
export function assigneeOf(recipe: Recipe): Recipe["runtime"]["assignee"] {
  return takeAt(recipe)?.assignee ?? recipe.runtime.assignee;
}
```

`queueOf` (`settings.ts:339-346`) is built on it, and so are `runnableNow` (`schedule.ts:181`, `wizard.ts:89`), `filter.ts:294` and the declared action in `conduct.ts:2362`. A recipe that declares `claim: [{ queue: { …, assignee } }]` is selected on its own assignee today.

Two things are actually wrong:

1. **The v1 spelling is backwards.** `runtime.assignee` written in the recipe is refused (`local.ts:415-421`, *"moved to this machine (0046 §3)"*). The one written in `~/.lingtai/config.yml` is merged in (`local.ts:377-395`, `local.ts:424`). So a recipe without a `queue:` block can only get an assignee rule from the laptop.
2. **The provenance rows never see the v2 spelling.** `runtime.assignee.take` and `.login` are computed from the machine file *before* `resolveSource` runs (`local.ts:394-395`). With a `claim` `queue:` deciding, they still read `both ← default`. This is the same mis-attribution the #269 review fixture recorded against the board (`packages/actions/test/fixtures/review-269-attempt-3.ts`, the `apps/board/src/lib/recipe.ts:695` finding).

**Do not add a top-level `queue:` key or a `source.assignee`.** `recipe.ts:931-937` explains why: *"Putting it in `source:` too would invent a third spelling that nothing reads, which is the silently-dropped key 0016 §4 is about."* The recipe already has its two spellings: `runtime.assignee` (v1) and `steps.claim[].queue.assignee` (v2). This ticket makes the recipe file the home of the v1 spelling. `assigneeOf` keeps choosing between the two, unchanged.

### The authority, and the ADR to edit

This is [0063](doc/decisions-archive/0063-every-setting-is-the-recipes.md) §3 and §4, done for one of the three keys. §4:

> **The machine file refuses `agent`, `limits` and `assignee` by name**, naming the recipe and the step each belongs on.
> **The write-back is deleted.**

0063 is archived and accepted, so nothing contradicts an ADR. The current topic ADR is `doc/decisions/0104-the-recipe-is-the-pipeline.md`, and it describes the old state in three places:
- line 14: *"assignee rule that have not yet moved"*
- §7, lines 95-98: *"reads `runtime.agent`, `runtime.limits` and `runtime.assignee` … A recipe that writes those three keys under `runtime:` is refused"*
- *Not built yet*, lines 188-197

Per CLAUDE.md, a decision that changes is **an edit to 0104**, not a new file:
- §7 now says two keys come from the machine and `assignee` is refused there.
- *Not built yet* drops `assignee` from its list.

### The decision the ticket defers, and why it isn't deferred here

The ticket's Fix says *"the machine key is refused in the ticket that closes the boundary."* **Refuse it in this one.** If `local.ts` stops reading `runtime.assignee` while `MachineRuntime` (`local.ts:82-84`) still accepts it, that key is accepted and dropped. The header of the same file forbids exactly that:

> **Both files refuse what belongs in the other, by name.** A key silently dropped and a key that does not exist are different facts to whoever wrote it (0016 §4) — `local.ts:21-24`

0063 §4 also calls the refusal *"the only thing that makes the move visible to whoever typed the old key"*. The ticket's *Related* section says nothing on this machine sets an assignee, so refusing now costs nothing here. Leaving the key accepted but unread is the one outcome that fails silently somewhere else.

How to refuse it: do it by name, **before the schema**, the way `steps` is refused (`parseMachineConfig`, `local.ts:164-170`; message built like `stepsRefusal`, `local.ts:132`).
- Check both `runtime.assignee` and `projects.<name>.runtime.assignee`.
- The message names `recipePath(project, home)` and both spellings: `runtime.assignee`, or `assignee` in `claim`'s `queue:`. It ends *"Nothing here was applied"*, as the existing refusals do.
- Delete `assignee` from `MachineRuntime`.
- `AssigneeTake` is then unused in `local.ts`'s imports (`local.ts:34`), so drop it there.

### `resolveLocalRecipe` (`local.ts:331-458`)

- **Delete `local.ts:377-392`** (the machine merge and its `AssigneeRule.safeParse`).
- **Remove `"assignee"` from the refusal loop** at `local.ts:415`. Its message still says *"moved to this machine"*, which stays true for the other two keys.
- **Write `raw["runtime"]` as `{ ...own, agent: agent.agent, limits }`** at `local.ts:424`. `...own` already carries a recipe-written `runtime.assignee` through untouched.
- **Validation is free.** `Recipe`'s `runtime.assignee` is `AssigneeRule.optional()` (`recipe.ts:3086`), so `take: mine` without a login, or `take: everyone`, fails in `resolveSource` as a `RecipeInvalidError` against `path`, under `runtime.assignee.*`. That satisfies the Done-when about errors naming the recipe's path. Don't wrap or re-throw it. The hand-built `MachineConfigInvalidError` branch is what goes away.
- **Absent stays absent.** It is `.optional()` and never `.default(...)`, and nothing here may write `assignee: undefined` or `{ take: "both" }` into `raw.runtime`. Today's no-assignee resolve omits the key (`local.ts:424`'s conditional spread), and the new code must produce the same object. Only `queueOf` fills in `EVERYONE` (`settings.ts:344`, `settings.ts:331-337`), and that value is the selection's, never the resolved recipe's. 0104 §6 is the rule.

**Provenance rows: move them below `resolveSource`.** They belong beside `recipeValues` (`local.ts:430-457`), because both spellings are only known after resolve:
- **Value:** `assigneeOf(recipe)?.take ?? "both"` and `assigneeOf(recipe)?.login ?? "(none)"`. Keep the row keys `runtime.assignee.take` and `runtime.assignee.login`. The board and doctor look them up by those names.
- **Source:**
  - If the `claim` step declares a `queue:` (find it the way `takeAt` does; `takeAt` is private to `settings.ts:253`, so either export a predicate or test `recipe.steps.claim.some((a) => "queue" in a)`), the source is the step itself. Use the recipe `path`, or `preset <name>` if that is where `steps` came from. `originIn` with `steps.claim` gives you that.
  - Otherwise, `originIn(wrote, resolved.preset, path)("runtime.assignee.take")` and the same for `.login`. `originIn` already splits on the first two segments (`local.ts:286`) and falls back to `"default"` for a nested key the file did not write. A file that writes only `login` reads `take: both ← default`, which is true.
  - `wrote` is cloned before the merge (`local.ts:408`), so it still shows what the file said.

### `machineFiles` (`local.ts:462-560`) also moves the other way

Today `machineFiles` moves a recipe's `runtime.assignee` *into* the machine file:
- `written` is captured at `local.ts:507`
- the key is deleted from the recipe text at `local.ts:511`
- `choose` re-emits it under `projects.<p>.runtime` at `local.ts:521`
- `kept` preserves an existing one at `local.ts:534-535`

After this change, every one of those writes produces a machine file that the new refusal rejects. **Leave `runtime.assignee` in the recipe text.** Delete:
- `written`
- the `deleteIn(["runtime","assignee"])` call
- `kept`
- the assignee branch of `choose`

Then rewrite the docblock (`local.ts:476-488`) and the `MachineFiles.recipe` comment (`local.ts:467-468`) to name two keys. An existing `projects.<p>.runtime.assignee` would now make the existing section differ from `chosen`, so the code returns the existing refusal, unless `replace` is set. That is correct. The file is refused at resolve anyway, so it is not a path worth special-casing.

### Tests

These are all unit tests (`packages/recipe/unit/local.test.ts`, the in-memory `read`), so `pnpm test` covers every claim here. Nothing in this change needs `pnpm test:integration`.

Rewrite the `runtime.assignee` describe (`local.test.ts:277-319`):
- **Absent:** the recipe says nothing and the machine says nothing. Assert `resolved.recipe.runtime` **does not have the property** `assignee`. Use `not.toHaveProperty`, not `toBeUndefined()`, which the current `:280` uses and which an `assignee: undefined` key would pass. Assert the provenance reads `both ← default`. Add one assertion that `configHash` is unchanged for a fixed recipe: either a literal captured from `main` before the edit, or equality with the hash of `resolveRecipe` on the same text with the machine's two keys merged by hand. This is the Done-when's hash claim. The `not.toHaveProperty` check is what actually guards it.
- **Recipe v1:** `runtime:\n  assignee:\n    login: alice\n    take: mine` in the recipe resolves to that rule. Both provenance rows name `recipePath("app", HOME)`.
- **Recipe v1, partial:** `login` only gives `take: "both"`, with provenance `take` `← default` and `login` `← <recipe path>`.
- **Recipe v1, invalid:** `take: mine` with no login rejects. The message contains the recipe path and `runtime.assignee.login`, and does **not** contain `config.yml`.
- **Recipe v2:** a `claim` `queue:` with `assignee: { take: unassigned }` and no `runtime.assignee`. The provenance rows read `unassigned ← <recipe path>`, which they don't today.
- **Machine:** `runtime.assignee` machine-wide, and separately under `projects.app.runtime.assignee`, are each refused as `MachineConfigInvalidError`. The message names the recipe path.

Rewrite *machineFiles and runtime.assignee* (`local.test.ts:321-360`) to the inverse: an assignee in the recipe text stays in `split.recipe` and never appears in `split.machine`.

`packages/conductor/unit/wizard-page.test.ts` and `apps/board` unit tests that build a machine file with an assignee will now be refused. Run `pnpm test` and move each one's assignee into its recipe fixture. `discover.test.ts`, `settings.test.ts` and `step-matrix.test.ts` exercise `assigneeOf` and `queue:` directly and should not change. If they do, the change has gone further than this design.

### What would settle it in the log

The resolved recipe is recorded beside its hash on each run. The `configHash` on the attempt's start event, before and after the merge on a machine whose recipe sets no assignee, should be byte-identical. The unit hash assertion stands in for that comparison, because nobody in a pass can read production `events`.
