# #503: give the conductor's signoff a name a recipe cannot write

## Decision: namespace the name and reserve the separator. Do not reserve the bare words

Rename the action at `packages/conductor/src/conduct.ts:3935` from `judge`/`unfixed` to **`conductor:judge`** / **`conductor:unfixed`**. Then add one rule to the recipe validator: **a declared action's `name` may not contain `:`**. Both halves are one decision, and the commit body should say why. The rule is what turns the prefix into a namespace. Without it, `name: z.string()` (`packages/recipe/src/recipe.ts:2736` shows the same unconstrained shape elsewhere; action names are read through `nameOf`, `recipe.ts:2235`) would still let an operator write `conductor:judge`. The finding would then be narrowed but still there.

**Why not refuse `judge`/`unfixed` at resolve.** `judge` is the name people actually give a judge entry: `judgePlugin` serves `proposed` (`recipe.ts:1356`), and the board's own fixture writes `judge: { name: 'judge', judge: 'claude-code', when: 'findings' }` (`apps/board/unit/run-recipe.test.tsx:544`). A machine recipe that names its judge that way would start resolving with a refusal. Per CLAUDE.md, *"a daemon restarted onto one takes nothing at all"*, and `conduct.ts` answers `stage: "recipe"` for every ticket. A `:` in a name is rare, and refusing it breaks no recipe anyone is likely to have. The machine's `~/.lingtai/lingtai/recipe.yml` has no action named `judge`. I did not grep it for a `:` in any name; do that before relying on the rule.

**The key shape survives a colon in the name.** The only parsers I found that split a key on `:` take the head: `apps/board/src/lib/progress.ts:231` `stepOf` (`label.split(':')[0]`). So `proposed:conductor:judge` still reads as step `proposed`. `run.ts:394` builds `${step}:${name}` and never parses it back, and `task_view`'s `run:point:action` key (`task-view.ts:541-547`) is opaque. No source file reads the literal `'judge'`/`'unfixed'` as an action name except the line being changed. The `grep` hits for `'unfixed'` are all test fixtures: `wait-handlers-answer-as-today.test.ts:52`, `verbs-accept-refuse.test.ts:70`, `waiting-card.test.tsx:346`. They build their own actions and keep passing. Update the ones that claim to be the conductor's own signoff (`waiting-card.test.tsx:75` builds `plugin: 'conductor'`) so they stop describing a name that is no longer written.

**No adapter, as the ticket says.** Rewrite the comment block at `conduct.ts:3901-3918`. It currently argues *"the same name `ApprovalRequested{step:'proposed'}` used"*, and that continuity is exactly what is being given up.

## The validator rule

Put it beside the uniqueness check at `recipe.ts:2425-2450` (*"An action's `name` is unique within its step (0110 §9)"*), in the same `kindRefusedAt(step, kind, entryName, …, REFUSED_WHEN_IT_RESOLVED)` form. The refusal should say why: `:` is the conductor's namespace, and a declared name containing it could stand in a key the conductor writes. Put it before the uniqueness check, so a refused name is never recorded in `namesAt`. Add a unit test in `packages/recipe/unit/`, using whichever file already pins the uniqueness refusal, that resolves a recipe with `name: conductor:judge` and expects the refusal by name.

This tightens 0110 §9's name rule rather than contradicting it. Edit that rule's comment; no ADR file is needed. I checked no ADR for this, so if `doc/decisions/` has a topic ADR stating what an action name may contain, edit that ADR to match. Don't add a new file.

## The test: make it fail first

`packages/conductor/unit/conduct-asks-for-approval.test.ts:69` reads `run.find(... outcome.step === 'proposed')`, which is the first of the two `StepEnded`s. Its fixture names the refusing agent `review` (`packages/conductor/test/one-pass.ts:184`), so nothing collides even on the old code. Do two things:

1. **Add a colliding fixture** beside `restartRecipe`: the same recipe with the `proposed` agent named `judge`. An `agent:` at `proposed` is legal (`step-matrix.test.ts:988` lists `agent`), and `refusingRuntime` refuses it. This is simpler than the ticket's `watch` scenario, and it reaches the same branch, `stopped.step === 'proposed'`, `judged`.
2. **Assert on the folded run, not on one event.** Run `reduceRun(run)` (`packages/domain/src/run.ts`), then check:
   - `steps['proposed:judge']` is the refusal (`verdict: 'failed'`, `onSha` the published head);
   - `steps['proposed:conductor:judge']` is the signoff, and `lifecycle` is `{status:'awaiting-approval', step:'proposed:conductor:judge'}`;
   - **`refusingOn(folded, headSha)` (`packages/conductor/src/approve.ts:102`) returns `['proposed:judge']`.** On the old code it returns `[]`, because the signoff overwrote the key and then excluded itself as `awaiting`.

   The third check is the *Done when*'s "cannot erase its own refusal". It is also the claim that stands in for `approveHolding`'s `reason-required` branch, which this test does not need to drive. Find the two `StepEnded`s by `plugin` (`'conductor'` versus not), not by position. Retitle the test and rewrite its header: *"one event… which this shape has no way to do"* is false since #502, because the signoff is a second `StepEnded` on the run's stream.

   Keep the existing `review`-named case as it is. It covers the ordinary path.

Run the new assertion against the unchanged `conduct.ts` first and watch it fail on `refusingOn`. Only then rename.
