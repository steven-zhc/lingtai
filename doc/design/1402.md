# #1402: making the five integration files match today's decisions

All five go to the test side. No code is wrong, including in #1397's daemon code. Each commit names the change the test is catching up to. Below, file by file, are the facts the ticket gets wrong or leaves open.

## `apps/cli/integration/init.test.ts`: the `--local` refusal is in `first-project.ts`, not `init.ts:480`

- **Which code refuses.** `init.ts:479-480` is on the path for a machine that is already set up. Its comment says *"Nothing below here reaches `chooseFirstProject`"*. A `--local /repo` first run takes the other path, and `apps/cli/src/first-project.ts:318` refuses it there: `` if (flags['base'] !== undefined) return `--base is now --main: pass --main ${flags['base']}. ${kept}` ``. That is the code behind the three failures.
- **Lines to change.** Swap `'--base', 'main'` for `'--main', 'main'` at `:328`, `:339` and `:885`; `:885` is the ticket's "`:888`".
- **The header comment.** Fix it at `:33-35` too (*"What git is asked about `--local /repo --base main`"*), or it describes a flag that no longer exists.
- **No conflict with `--land`.** `RECIPE_FLOW_FLAGS` (`:49`) carries no `--land`, so the `--land`/`--main` mismatch refusal at `first-project.ts:326` does not apply.
- **Keep one refusal test.** The sentence exists three times: `init.ts:480`, `first-project.ts:318` and `add-github.ts:248`. No test under `apps/cli/unit` or `apps/cli/integration` contains "is now --main". So the ticket's condition holds, and one test stays.
- **What that test asserts.** Put it in `init.test.ts`, next to the `:328` test, on the `--local` path (`first-project.ts:318`). It asserts:
  - `initCommand(...)` returns its non-zero exit code;
  - the printed line contains `--base is now --main: pass --main main`;
  - nothing was registered (`seen.registered` is `[]`).
- **Read the output, not the ticket.** The ticket says the exit is 1. Assert whatever the run prints and returns.
- **Commit cites `13a4060`.**

## `packages/daemon/integration/injected-store.test.ts`: the new entry is the first one, not the third

**What the code does.**
- `reconcileEffect` calls `recordOwedLandingsEffect` first (`packages/daemon/src/reconcile.ts:803-813`, *"The one write that comes first, on purpose"*). Only after that do `releaseForeignClaimsEffect` (`:820`) and converge (`:832-848`) run.
- Its read is `{ prefixes: ['int-${project}-%'], types: ['IntegrationSucceeded'] }` (`packages/daemon/src/owed-landings.ts:60-62`). It goes through `options.withStreams`, which is `withStreams(options, …)`, which calls `withDaemonStore(options.daemonStore, …)` (`reconcile.ts:117-119`). Per `reconcile.ts:113-114`, *"A store the caller injected is used as it is"*.
- So the owed-landings read goes to the injected store, and *one store for both halves* still holds. That makes it a test update, not a bug in #1397.

**The trap.**
- The new query lands at `asked[0]`, so changing only `toHaveLength(2)` to `3` is not enough.
- `asked[1]` is now the claim query, with prefixes `['ticket-pureproj-%']`. The `asked[1]!.prefixes` assertion at `:156` would fail next, and a fix that changed `[1]` to `[2]` without reading why would hide that the order changed.

**The fix.** Replace `:155-157` with one `toEqual` on the whole array, in pass order:
1. the owed-landings query;
2. the claim query, as at `:128`;
3. converge's `ticket-%` query that contains `TicketLanded`. Keep `:157`'s `toContain` for its types, because the full list is converge's to change.

Add a sentence to the comment saying the first entry is #1397's owed-landings read and that it, too, went to the injected store.

- **The first test stays as it is.** *reduces the claim…* calls `releaseForeignClaimsEffect` directly and never reaches the owed-landings read.
- **`recordingStore` stays as it is** (`:71-94`). It answers `[]` to the `int-` query, so owed-landings records nothing and the dry run writes nothing.

**What would settle it.** The run itself. If `asked[0]` is not the `int-pureproj-%`/`IntegrationSucceeded` query, the analysis above is wrong. Stop, and look in `owed-landings.ts` for a store opened outside `options.withStreams`; that would be the code bug the ticket's Fix 4 describes.

- **Commit cites `9b73067` (#1397).**
