## Design: the health dot warns when nothing conducts (#1015)

The ticket's Fix is right as it stands. These are the five places where its wording would lead to the wrong code, plus the order to build in.

### 1. Import the lock reader from the subpath, not the barrel

The ticket says `conductorLockHolder()` (from `@lingtai/daemon`). Import it from **`@lingtai/daemon/lock`** instead. The package exports that subpath (`packages/daemon/package.json:13`), and `lock.ts` itself imports only `@lingtai/env/lock` (`packages/daemon/src/lock.ts:37-44`). The board already refuses the barrel, in a comment you should follow (`apps/board/src/app/page.tsx:3-6`):

> *The subpath, not the barrel: the board reads the control stream and hosts no work, and `@lingtai/daemon` would drag the work loop and the runtime in behind it.*

`bearing.ts:27` and `live.tsx:86` import `Health` as `import type`, so the new runtime import in `health.ts` never reaches the client graph. Keep both of those as `import type`.

### 2. A seam for the "never reads the lock while the beacon is up" test

`readHealth()` cannot be called in a unit test. It calls `projectionLag()`, `readStatus()` and `readTasks()` directly (`apps/board/src/lib/health.ts:50-61`), and each of those reaches the store, which makes the test integration under 0060 §1. So the Done-when item *readHealth does not call the lock reader while the beacon is up (unit, with the reader injected)* needs a seam. Put it on the one decision, not on the whole read:

```ts
export async function askConductor(
  daemon: Health['daemon'],
  holder: () => Promise<string | null> = conductorLockHolder,
): Promise<Health['conductor']>
```

- It returns `null` without calling `holder` when `daemon === 'up'`.
- Otherwise it returns `{ held }`, or `{ unread: message }` when `holder` rejects.

`readHealth` calls it with the default reader. The unit test hands it a spy: the spy is never called for `'up'`, it is called once for `'stale'` and for `'never'`, and a rejection becomes `{ unread }` and never `{ held: null }`. Put the test in a new `apps/board/unit/health-conductor.test.ts`, not in `bar.test.ts`, which tests `bearing` and stays pure.

`apps/board` is not in `effect-ratchet.baseline.json`, so a plain `async` function here moves no count. Do not write it as an Effect for the ratchet's sake.

### 3. Sequencing inside `readHealth`

The lock read depends on `daemon`, so it cannot join the `Promise.all` at `health.ts:50`. Call `askConductor` after `status` is known, on both successful returns: the `!status` (`never`) return at :65, and the beat return at :73-80. Keep it out of the `try`'s reach. `askConductor` catches its own failures, so an unreadable lock can never become the whole read's `error`. The `catch` at :82-91 sets `conductor: null`.

### 4. Suspense in `Live`, and what the promise does when it fails

`Health` (`apps/board/src/app/health.tsx:91-93`) gains `runnable: Promise<number | null>` and passes it through.

At `page.tsx:728`, build the promise as `queue.then((q) => q.runnable, () => null)`:

- The rejection handler is not optional. `use()` on a rejected promise throws to the nearest error boundary and takes the dot down with it. A GitHub fan-out that failed is *unknown*, and unknown is `null`, which is today's answer.
- Build it once per render in the server component and hand it down. The client receives a serialized promise, which is the supported shape for `use`.

`Live`'s prop is `runnable: Promise<number | null> | null`:

- **`null`** (the `Following` path) draws `bearing(socket, health, code, null)` directly, with no `<Suspense>`.
- **A promise** draws `<Suspense fallback={<Said said={bearing(socket, health, code, null)} />}>` around a small inner component that calls `use(runnable)` and draws with the count.

`useFollow()` stays in `Live`, above the boundary (`live.tsx:307`), and the inner component takes `socket` and `health` as props. If the hook moved below the boundary, the `EventSource` would open only after GitHub answered. The warning appears at most one GitHub round-trip after first paint.

### 5. Make `bearing`'s fourth parameter required

Write it as `runnable: number | null`, not as an optional parameter. Every caller then has to state its answer, which is the same reason `code` is required:

- `Live`: the resolved count, or `null` in the fallback.
- `Following` at `live.tsx:262-281`: always `null`.
- The tests.

`tsc` will list every call site, and that list is the checklist.

### 6. Where the count comes from

Sum `answer.runnable.length` inside `githubQueue`, at the point where it already counts `answered` (`apps/board/src/lib/board.ts:1105-1109`, :1220). The cards it keeps are already filtered to those with no log row (:1161-1162), so the sum must come from `answer.runnable` before that filter, not from the cards it returns. Otherwise the count would not match `lingtai status`'s `Queue N runnable` (`apps/cli/src/status.ts:411`).

The null rule is the ticket's own and is not reopened here: `null` when `answered < asked` **and** the sum is 0.

`EMPTY_GITHUB` (`apps/board/src/app/queued-stream.tsx:164`) gets `runnable: null`, not `0`. It stands for "not yet asked", and 0 would claim an answer.

### Order of work

1. `askConductor`, the `conductor` field, and their test.
2. `GithubQueue.runnable`, `EMPTY_GITHUB`, and the `githubQueue` test.
3. `bearing`'s branch, plus the `EVERY_STATE` and #904 table rows (`apps/board/unit/bar.test.ts:55-64`, :384-393).
4. The `Health`/`Live`/`page.tsx` wiring last, keeping the literal `<Bar project={only}>`.

Steps 1–3 are pure or nearly so and are covered by `pnpm test`. Step 4 has no unit witness beyond `tsc` and `client-graph.test.ts`. The Suspense behaviour is checked only by the manual Done-when step at the end of the ticket, and that is accepted.
