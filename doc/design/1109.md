# Design note: #1109, the question seam and the recipe questions as Effects

The ticket gives the order and the shape. This note covers five things it leaves open or gets slightly wrong, each checked against this worktree. `apps/cli` reads `async: 94` here (`packages/domain/unit/effect-ratchet.baseline.json:2`), and `grep -c async` over the five files gives 3 + 10 + 4 + 4 + 6 = 27, so the target of 67 holds.

## 1. The error channel of `validate` is `unknown`, not `never`

The ticket writes `(answer) => Effect<string | null>`. Use `Effect.Effect<string | null, unknown>` instead.

- The face's `liftValidate` uses `lift` (`exit.ts:16`, `Effect.tryPromise({ try: f, catch: (e) => e })`), and its type is `Effect<A, unknown>`. A lifted promise `validate` cannot be assigned to a `never` channel.
- `world.ask` is lifted the same way, so `questionEffect` is `Effect<Answered, unknown>` whatever `validate` says. Widening `validate` costs nothing.
- The face rejects with the original error either way, so `unit/question.test.ts`'s *"an ask that throws propagates"* still sees the thrown object.

The validates in these five files are pure, so they become `Effect.succeed(…)`. One exception: `landing.ts:278`'s `try { parseDuration } catch` becomes `Effect.sync` + `Effect.catchCause`, or simply stays a plain `try` inside an `Effect.sync` thunk that returns the string. That is not IO and must not fail the Effect.

## 2. Two `Question` types, one exported name each

`Question` (`question.ts:46`) becomes the Effect shape. Add an exported `PromiseQuestion = Omit<Question, 'validate'> & { validate?: (answer: string) => Promise<string | null> }` and give it to the face only:

```ts
export function question(world: QuestionWorld, q: PromiseQuestion): Promise<Answered> {
  return Effect.runPromise(questionEffect(world, liftValidate(q)))
}
```

That body is one statement, `Effect.runPromise` with one call argument, which is exactly what the shape check asks for (`packages/domain/unit/effect-ratchet.test.ts:209-237`). `liftValidate` is a plain non-`async` function in `question.ts`.

No file outside `question.ts` annotates anything as `Question`; outside callers pass object literals. So the callers listed under *Faces* typecheck unedited against `PromiseQuestion`.

## 3. Every `try { await … } catch` here becomes `recovering`, already in `exit.ts:24`

`recovering(onError)` is the `catchCause` the ticket asks for. It lets an interrupts-only cause through and hands `onError` `Cause.squash(cause)`, which is the object `runPromise` used to throw, so `.message` is unchanged. Use it at:

- `setRecipeOrRefuse` (`landing.ts:65`) and `writeOrRefuse` (`recipe-flow.ts:186`), over `setRecipeEffect` (`packages/recipe/src/write.ts:162`). Today they catch **everything** `setRecipe` throws, including a read failure from `files.read`, and turn it into `{ refused }`. Keep that breadth. Do not narrow it to the typed `RecipeInvalidError`, or a filesystem failure that was a refusal sentence becomes a stack trace.
- `summariseRecipe` (`recipe-flow.ts:163-182`), `resolvedFile` (`landing.ts:97`) and `resolvedRecipe` (`source.ts:72`). Their `try` wraps only the synchronous `resolveSource`, so a plain `try` inside `Effect.sync` (or `Effect.try`) is equivalent. Their `files.read` (`RecipeFiles.read`, `write.ts:26`, a promise port) sits **outside** the `try` today and so propagates. Lift it with `lift` and leave it uncaught.
- `rawProposed` / `rawAdmit` (`landing.ts:153-154`) and `agents.ts:217-218` yield `readRecipeKeyEffect` (`write.ts:204`), uncaught, as today.

## 4. `toolOnPath` is not IO through a process

The ticket's shape says it "runs its child process through `Effect.callback` or `lift`". It does not spawn anything. It is `existsSync` over `PATH` (`recipe-flow.ts:60-64`). Drop the `async`. Either make it a plain `(tool) => boolean` (the ratchet counts the keyword, not the return type) or use `Effect.sync`. Do not add a `catchCause`: there is no failure to absorb.

## 5. The promise ports that stay promises

These are lifted with `lift` and stay promise-typed:

- `world.ask`
- `deps.defaultBranch()` (`landing.ts:50`, `:201`; `RecipeAt.defaultBranch`, `recipe-flow.ts:76`)
- `RecipeFiles.read`
- `askInstallAndBuild` (`recipe-flow.ts:269`)

`RecipeAt` and the landing deps keep their promise signatures, because `first-project.ts` and `add-github.ts` build them and are out of scope. Each `lift` keeps a thrown `PromptRefused` as itself, and the `askRecipe` face rejects with it unchanged.

`acceptingDefaults`' `ask` (`question.ts:107`) becomes `(prompt) => { …; return Promise.resolve(repeat ? null : '') }`. Its closure over `lastPrompt` is the repeat guard, so its order must not move.
