## Design: close the process log when a command finishes (#725)

### Where the pool leaks
In a Postgres process, only one connection outlives a command. It is the `createDb(choice.url)` client at `packages/event-store/src/choose.ts:106`, built inline and never kept. The other pieces already hold nothing open between calls:
- **Queries** open and close a client per question: `createPostgresLogQueries` in `queries.ts:192-213`, whose comment says *"a pool held here would be a connection a short command has to remember to end"*.
- **Ticket SQL** does the same at `queries.ts:344-358`.
- **The waker** closes with its own session (`wake.ts:148`).

So `Opened` (`choose.ts:51-54`) gains `close(): Promise<void>`:
- **Postgres:** keep the client in a local, `const db = createDb(choice.url)`, pass it to `createEventStore(db)`, and close it with `close: () => db.close()`. `db.ts:18-19` names the method: *"Close what you open — `await client.close()`"*.
- **SQLite:** close the one `db` from `choose.ts:116` with `close: async () => db.close()`. That is a synchronous `DatabaseSync.close()`, the same call `sqlite.ts:131` makes. The ticket SQL shares that handle, so nothing else gets closed.

Do not add a `close` to `Log` or `EventStore`. The ticket's *nothing else changes* means callers keep the interface they have. Closing is `choose.ts`'s business, through `closeProcessLog()`, and the deferred views at `choose.ts:140-199` stay as they are.

### `closeProcessLog()` and the refusal
- **Order inside `openOnce()`:** check `closed` first. If set, return `Promise.reject(new ProcessLogClosedError())` before `chosenStore()` runs. That makes the "nothing opened" unit test pure: it needs no env, no config and no `HOME`.
- **What `closeProcessLog()` does:**
  1. Set `closed = true` first, so a caller arriving during the close is refused rather than reopening.
  2. If `opening` is set, await it. **If that open rejected** (for example `chosenStore()` refused, or the connection failed), there is nothing to close: resolve. Do not throw that error again. The command already reported it and exited with its own code, and throwing it here would print it a second time as a close failure.
  3. Otherwise call `opened.close()` once. Memoise the close on a module promise, the same way `opening` is memoised. A second `closeProcessLog()` then returns that same promise and the handle is still closed exactly once.
- **The seam for the unit test** (Done-when item 2): a small `closableOnce(open: () => Promise<{ close(): Promise<void> }>)`, or similar. It returns `{ get, close }` and holds the `closed`, `opening` and close-promise logic. `choose.ts` uses it to wrap `open`, and the test gives it a fake with a counted `close`.
- **Name check:** neither the seam nor its test may name `createDb(`, `createPostgres…(` or `from 'pg'`.
- **Export:** `closeProcessLog` and `ProcessLogClosedError` go out through the barrel next to `processLog` (`packages/event-store/src/index.ts:18`).
- **The guard file:** the ticket cites `packages/event-store/unit/one-choice.test.ts:78-82`. That path is wrong. The guard is `packages/env/unit/one-choice.test.ts`: `CHOOSERS` at `:79-83`, and the name regex `/\bcreate(?:Postgres|Sqlite)[A-Za-z]*\(/` at `:61`. `ending.ts` passes it trivially, because it imports nothing from the event store.

### `apps/cli/src/ending.ts` takes `close` as an argument
`finish(run, close)` stays free of `@lingtai/event-store`. That matters for two reasons:
- **`entry.ts` must stay lazy.** Its header says *"`cli.ts` is imported lazily and a database nothing has configured yet is never called into by importing it"* (`entry.ts:5-11`). It also says help and unknown-command routes open nothing (`:35-40`). A static import of the barrel from `ending.ts` would load the store machinery for `lingtai help` too.
- **The `finish` test needs only fakes.**

In `entry.ts`, get the close function inside the existing promise chain:
```
import('./cli.ts').then(async ({ runCli }) => {
  const { closeProcessLog } = await import('@lingtai/event-store')
  const code = await finish(() => runCli(process.argv), closeProcessLog)
  …
})
```
`cli.ts` already does `await import('@lingtai/event-store')` (`cli.ts:549`), so this loads nothing new. It is also a dynamic import, which esbuild keeps lazy in the CJS bundle.

### What `finish` does when `run` rejects
`runCli` maps any failure inside the Effect run to `1` (`cli.ts:1345-1349`). But the argument checks before it, at `cli.ts:1335-1342`, are outside that catch, so a throw there rejects `runCli`.
- **On rejection:** `finish` closes (bounded, as below), then rejects again with the original error. `reportEnding` sets `exitCode = 1` as it does today. That gives the ticket's *close first, then set the code* without `reportEnding` needing a handle on the store.
- **When the import of `cli.ts` fails:** nothing was opened, so nothing is closed.

### Bounding the close
Race `close()` with a 2 s timer and call `unref()` on the timer: an un-unref'd 2 s timer would itself hold the process open on the happy path. Whether the close rejected or timed out, print one stderr line, for example *`lingtai: the log's connection did not close (…); exiting anyway`*. Then return the command's code unchanged.

The `init` refusal path keeps `process.exit(code)` (`entry.ts:31`), now after `finish` has closed.

### Tests
All are unit tests under `packages/event-store/unit/` and `apps/cli/unit/`.
- **The `choose.ts` refusal test:** call `vi.resetModules()` and then a dynamic import per case, because a closed module refuses for the rest of the file.
- **The `finish` hang case:** use `vi.useFakeTimers()` and advance 2000 ms.

Nothing here needs `pnpm test:integration`. The real claim, that a Postgres command exits with no ~30 s tail, is the operator's `time lingtai status` after the merge. The unit-level stand-ins are: the opened handle is closed exactly once, and `finish` closes before it returns.
