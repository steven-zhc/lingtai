# #1207: the shape of the base check's second run

## Where the rerun goes

The rerun goes inside `ran`'s inner `Effect.gen`, right after the first `runIn` of the check command (`packages/conductor/src/base-check.ts:254`). It must run before the `Effect.ensuring` that removes the tree (`:257-267`), because after that point there is no tree to run in. The inner gen returns `{ first, outcome, boundary }`, where `first` is the first run's outcome or `undefined` when there was no rerun.

Rerun only when **all** of these hold for the first outcome:

- `exitCode !== null`
- `exitCode !== 0`
- `!timedOut`
- `!q.signal.aborted`

A first run that did not reach an exit code is not run again. It falls through to the existing `unknown` branch (`:272-275`) exactly as it does today. Before the second `runIn`, check `q.signal.aborted` and return `unknownWith('the check was aborted')`, the same way the `prepared` loop does after each command (`:249`). The rerun calls the same `runIn(commands[commands.length - 1], commands.length - 1)`, so it reuses `profiles[i]` and the boundary computed once (`:196-213`), and `prepared` is not run again.

After `ran`, the existing checks at `:271-275` read `ran.outcome`, which is now the **second** run's outcome whenever there was one. A timeout or an abort on the second run therefore becomes `unknown` and nothing is recorded, with no new branch. Keep that property: never fall back to `first` when deciding `ok`.

## What gets recorded

- `ok`, `exitCode` and `evidence` come from the final outcome, as today. Red twice records the second run's `exitCode` and `boundedEvidence(outcome.evidence)`.
- `durationMs` is `first.durationMs + outcome.durationMs` when there was a rerun, rounded as at `:303`.
- `flaky` is added only when `first !== undefined && ok`, and only when `failingTestsOf(first.evidence)` returned a non-null value. Spread it in conditionally (`...(names === null ? {} : { flaky: names })`) so the event never carries `flaky: undefined`.
- On red then green, call `deps.note(\`base check: \`${q.command}\` failed once on ${q.baseSha.slice(0,7)} and passed on the rerun\`)`. It is the only visible trace outside the event, and `deps.note` is already the channel for this file's side remarks (`:309`).
- `BaseCheckAnswer` does not change. Nothing reads a "flaky" bit off the answer: `baseIsRed` (`conduct.ts:3794`) only asks red or not. `lookup` (`:133-161`) does not read `flaky` either.

## What `failingTestsOf` is fed

Feed it `first.evidence`, never `boundedEvidence(...)` of it. That evidence is already shaped by `runCommand`: `` `${run} exited ${code} after ${took}${note}\n\n${tail(out)}` `` (`packages/actions/src/command.ts:287`). It has colour stripped (`plain`, `:154`) and is clipped to the last 60 lines / 8,000 bytes plus a start (`tail`, `:176`). So:

- The first line is the `… exited 1 after 60.5s` header. The parser skips every line that is not a `FAIL` line or the `Test Files` summary.
- A run with many failures can lose some `FAIL` lines to the clip. The ticket's count rule (distinct files named < the `N failed` in `Test Files`) answers null there. That rule is what makes clipping safe, so do not loosen it.

## Parsing vitest's `FAIL` lines

The entry starts at the file path, not at `FAIL`. With projects, vitest prints a label between them (`FAIL   unit  apps/cli/unit/…`, #1130's evidence). Two rules, in this order:

1. Skip `FAIL` and then at most one label token: a single token with no `/` and no `.`.
2. The rest of the line, trimmed, is the entry.

The file is the entry's text before its first ` > `. That gives the file-only case and the distinct-file count. The summary is `/^\s*Test Files\s+(\d+) failed/m`.

Do not reconstruct titles from vitest's `×`/`❯` progress lines. Only `FAIL` lines are read, and an entry printed twice is deduplicated by exact string.
