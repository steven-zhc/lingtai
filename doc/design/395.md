# Design: #395, one writer for a project's recipe

## Most of it already exists: `editRecipe`

The comment-keeping edit the ticket asks for is already written and tested. It is `editRecipe` in `packages/recipe/src/emit.ts:119`, which was built for #162:

> *"**`parse` is fine for reading. It is `stringify` that must never touch a file a person has edited.** Parsing this repository's own recipe to an object and stringifying it back destroys 74 of its 503 lines"* (`emit.ts:7-10`)

It edits the `parseDocument` tree. It then carries only the changed lines onto the person's own text (`carry`, `emit.ts:~400`), and it throws `CommentWouldBeLostError` (`emit.ts:70`) rather than drop a comment it was not told to drop. It returns `existing` itself when nothing changed (`emit.ts:148`). The board's wizard already uses it (`apps/board/src/app/setup/wizard/finish.ts:120`).

**Do not write a second YAML editor.** Do not copy `init.ts`'s `Document` + `doc.toString()` either (`apps/cli/src/init.ts:196-201`). That is a whole rendering, and `emit.ts:22-24` says why it is wrong for this file: *"`Document.toString()` is a rendering, not the file: on this repository's recipe it drops a blank line and re-indents the sixteen-line comment above `merge:`"*. Take only the temp-then-rename idiom from `init.ts`.

What #395 adds is the part around `editRecipe`: the file, creating it, the resolver, the atomic replace, and reading a value back.

## Where it goes

- **Code:** a new `packages/recipe/src/write.ts`, exported from `packages/recipe/src/index.ts` like the others (`index.ts:1-9`).
- **Tests:** `packages/recipe/unit/write.test.ts`.
- **Nothing else changes.** No caller is wired in this ticket; #396–#399 are the callers.

## The shape

```ts
export interface RecipeFiles {
  read: (path: string) => Promise<string | null>     // null = absent
  replace: (path: string, text: string) => Promise<void>
}
export const diskFiles: RecipeFiles                    // the real one

export async function setRecipe(
  project: string,
  changes: readonly RecipeChange[],                    // emit.ts:64 — reuse it
  options?: { home?: string; files?: RecipeFiles },
): Promise<{ path: string; text: string; written: boolean }>

export async function readRecipeKey(
  project: string,
  path: readonly (string | number)[],
  options?: { home?: string; files?: RecipeFiles },
): Promise<unknown | null>
```

### The file seam

The path is always `recipePath(project, home)` (`local.ts:40`), never anything under a worktree (0046 §3, #180). The seam is what makes every Done-when test a `unit/` test: the tests hand in a `Map`-backed `RecipeFiles`.

`diskFiles.read` is the `ENOENT → null` pattern. `local.ts:283` already has it as `readIfThere`; move it or export it rather than writing a third copy (`packages/conductor/src/wizard.ts:285` is the second).

`diskFiles.replace` does three things:

1. `mkdir(dirname(path), { recursive: true })`
2. writes `${path}.${process.pid}.partial`
3. `rename`s it over `path`

**Keep the default mode, not `0600`.** `0600` is for `config.yml` because *"a database URL carries its password"* (`init.ts:193-194`). A recipe carries none, and `startOnboarding` writes it with the default mode (`wizard.ts:378`).

### `setRecipe`, in order

**1. Read the file.**

**2. Make the text.**

- **The file exists:** `editRecipe(existing, changes)`.
- **The file is absent:** apply the same `changes` to a seed of `version: ${RECIPE_VERSION}\n` (`recipe.ts:2671`). Either call `editRecipe` on that seed, or add a small `createRecipe(changes)` beside it in `emit.ts`, which uses `new Document({ version })`, `setIn` for each change, and `toString(RENDER)` so it can share `RENDER` (`emit.ts:87`).
  - **Do not use `emitRecipe`.** It runs `Recipe.parse` first (`emit.ts:92`), so it writes every schema default: `discuss`, `exclude: []`, `backoff: 1h`… That is not *"only the keys set"*. It also writes those defaults into a file that would otherwise have inherited them; `recipe.ts:2836-2841` explains why the code avoids that for `repo.remote`.
  - **The writer adds `version` itself.** No question asks for it. It is the file's format, not an answer, and a file without it never resolves (`Version`, `recipe.ts:2681`).

**3. Resolve the result:** `resolveSource(text, ref, path)` (`resolve.ts:205`).

- This is the same function a daemon reads the file with. It refuses unknown top-level keys by name (`unknownKeys`, `resolve.ts:290`), and `steps` is a `z.strictObject` (`recipe.ts:2571`). That is how *"write only keys the resolver accepts"* (#148) holds.
- `ref` is only what a refusal names (`wizard.ts:258-260` says the same). Use the result's own `repo.base` when it parses, else `path`.
- Use `resolveSource` and **not** `resolveLocalRecipe`. The local one asks what is signed in (`local.ts:316-330`) and reads `config.yml`, and a write should not depend on either.

**4. Write, or don't.**

- If the text equals what was read (`editRecipe` returns `existing` unchanged), **do not call `replace`**: return `written: false`. Pressing enter on a current default changes nothing, mtime included.
- Otherwise, `replace` and return `written: true`.

**Every refusal happens before `replace`, so a refused write leaves the file exactly as it was.** There are three kinds:

- `CommentWouldBeLostError`, from `editRecipe`.
- `RecipeInvalidError` (`resolve.ts:48`), from `resolveSource`.
- **A raw `ZodError`.** `editRecipe` runs its own `Recipe.parse` (`emit.ts:146`) before the resolver ever sees the text, and that throws a `ZodError`. Catch it and rethrow it as `RecipeInvalidError`, with issues formatted as `resolve.ts:240-245` formats them (`path: message`). Otherwise *"refused by name"* turns into a JSON dump.

### Widening a `steps.*` write for a file that `extends:` a preset

`applyPreset` (`presets.ts:149`) merges `steps` all-or-nothing — `recipe['steps'] ?? preset.steps` — unlike `repo` and `runtime`, which merge key by key. A file that `extends:` a preset and writes no `steps:` of its own inherits every step from the preset; the moment a change gives it its first `steps:` key, `recipe['steps']` turns truthy and *every* preset step stops applying, not only the one the change named.

So a narrow change — `setRecipe(project, [{ path: ['steps', 'build'], value: [...] }])` on a file that only `extends:` a preset — must widen to the whole resolved `steps` map before writing, with only the named step replaced: resolve the file as it stood before this change, resolve it again after the narrow edit, and if any step the change did not name moved, write the full map instead of the narrow one.

**"Before" is this call's other changes applied, not the raw file on disk.** A stub that `extends:` a preset but is still missing a required answer (`source.kinds`, `env.plantAt`) does not resolve on its own — and the call that supplies the missing answer is often the same one that writes the first `steps:` key. Resolve the file with this call's non-`steps` changes already applied, then widen against that.

**This pins the preset's current steps into the file, for good.** Once the file carries any `steps:` key, `applyPreset` never looks at the preset's `steps` again — a later correction to the preset (`presets.ts:26-33` records one: a gate command that did not exist in the repository the preset claimed to describe) does not reach a project that already answered one `steps.*` question. This is `applyPreset`'s own all-or-nothing merge, not something this writer chooses or can avoid by writing a narrower value — the writer cannot write "inherit every other step" into YAML, because the schema has no such marker. A caller showing this question to a person is the place to say so, not this module.

### `readRecipeKey`

`parseDocument(text).getIn(path)`, converted to JS. It returns null when the file is absent or the key is not written.

**It returns what the file says, not what resolves.** For a file that `extends:` a preset and does not write `steps.build`, the answer is null, not the preset's value. #392's seam takes `current ?? detected ?? fallback` (`apps/cli/src/question.ts:63`). Returning the preset's value as `current` would mean pressing enter writes the inherited value into the file. That changes the file without changing the recipe, and the next preset change would no longer reach it.

## The decision #396–#399 inherit: a new file is written once

A recipe resolves only with `version`, `repo.base`, `source.kinds` (`.min(1)`, `recipe.ts:957`) and `env` present. `local.test.ts:132-137` is the smallest such file. So a new file created from `steps.build` alone is **refused**: that is Done-when's third box, and it is correct.

The consequences:

- `setRecipe` takes a **list** of changes and writes them in one `replace`.
- For an **existing** file, a caller may still write each answer the moment it has it. This is #392's decision 1 (`doc/design/392.md`, *"The caller writes, the moment it gets `{ answer }`"*).
- For an **absent** file, the caller collects the first run's answers and calls `setRecipe` once.

Do not make the writer seed `repo`, `source` or `env` to work around this. Those are answers, and a guessed `kinds` is exactly the *"choice nobody wrote down"* that `local.ts:15-16` refuses.

## The unit tests (`packages/recipe/unit/write.test.ts`)

**Fixture.** Write the fixture as an inline string. Do not read `.lingtai/config.yaml` from disk the way `unit/edit-mechanism.test.ts:21` does: an inline string keeps the test free of the filesystem (0060 §1). The string should be a resolvable recipe with:

- a comment above a top-level key,
- a trailing comment on a line,
- a comment inside `steps`,
- a block scalar `prompt:`,
- a key the test never touches (for example `source.backoff`).

**Tests:**

1. **`steps.build` set on that fixture.** Use an exact string comparison. The output equals the input with only the `build:` lines different. Build the expected string by hand rather than from the code under test. This is the test that pins *"regenerating is the failure"*. Also assert `replace` was called exactly once with that text.
2. **Absent file.** The changes are `version`-less: `repo.base`, `source.kinds`, `env.plantAt`, `steps.build`. The written text contains those keys and `version: 2`, and no `discuss`, `exclude` or `backoff`. `resolveSource` accepts it.
3. **Refusals.** Each of these rejects with the named error, and `replace` is never called:
   - an absent file given only `steps.build`;
   - `steps.merg` (the misspelling `emit.test.ts:264` uses);
   - an existing file given a `source.kinds: []` change.
4. **`readRecipeKey`.** It returns the value for a written key. It returns null for an unwritten key, and null for an absent file.
5. **No-op.** Setting a key to its current value returns `written: false`, and `replace` is never called.

`pnpm test` runs all of this. **Nothing here needs `pnpm test:integration`.** `diskFiles` itself (`mkdir`, write, `rename`) is the only part that touches the disk. It is three lines, and nothing in the Done-when asks for it under test. If it gets a test, that test goes in `packages/recipe/integration/`, not `unit/`.

## What the writer cannot catch

`resolveSource` is the resolver of the code doing the writing. A daemon started before that code merged holds older code (CLAUDE.md, *"A running daemon holds the code it started with"*). It can still refuse a key this writer accepted. `doc/design/the-plugin-body.md` calls that ordering *code, restart, paste*, and it is the caller's to say, not this module's.

`ResolvedRecipe.configHash` changing is the observable effect of a write. The file changing shows up in the log only when the next run records its recipe hash; this module appends nothing.
