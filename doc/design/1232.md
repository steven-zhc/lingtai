# #1232 — the shape

## Where it goes

Both commands go in `packages/conductor/src/ticket/commands.ts`, beside `editPromptEffect` (`:578`), which already does the same job: it records a fact rather than making a decision, so it checks no state, reads the head and appends there. Callers outside the package import it from `@lingtai/conductor/ticket`, the export at `packages/conductor/package.json:8`. That covers `converge.ts`, which already imports from `@lingtai/conductor/tell` at `converge.ts:67`. The ratchet does not count anything under `packages/conductor/src/ticket/` (`aggregate-owners.test.ts:32`, `NOT_COUNTED_UNDER`).

## Signatures: what the ticket's four arguments leave out

```ts
recordIssueUpdate<T extends 'IssueUpdated' | 'IssueUpdateFailed'>(
  store, ticketId, type: T, data: PayloadOf<T>): Effect.Effect<void, unknown>

recordSplitProgress<T extends 'SplitStarted' | 'SplitFailed' | 'SplitChildWritten' | 'SplitLinkWritten'>(
  store, ticketId, type: T, data: PayloadOf<T>, actor: string): Effect.Effect<void, unknown>
```

- **The actor differs, so the split command takes one.** `recordEffect` writes `actor: 'conductor'` (`tell.ts:405`). `note` writes `actor: options.by` (`split-ticket.ts:241`, where `by: string` is declared at `:98`). If the split command hardcoded `'conductor'`, it would quietly change who the log says did the split. `recordIssueUpdate` keeps `'conductor'` built in.
- **`data` is `PayloadOf<T>`, not `Record<string, string>`.** Today `recordEffect` and `record` take `Record<string, string>` (`tell.ts:401`, `converge.ts:586`). A bad payload therefore fails only at run time, in `parsePayload`, and that failure is then swallowed. Typing the payload by `T` gives the `@ts-expect-error` case the ticket asks for, and it also catches a wrong field on the right type. The literals in `tell.ts` should already fit: `change: change.kind` is within the enum at `packages/domain/src/events.ts:1929`, and `converge.ts:272`'s `change` union is a subset of it. Keep `parsePayload(type, data)`, and call it **inside** the Effect (in the `tryPromise`/`try` thunk), never while building it. A throw outside the Effect would escape the caller's silence as a synchronous throw. Today it can't, because `parsePayload` is called inside `attempt`'s thunk (`tell.ts:405`).
- **The version comes from `store.head(ticketId)`, not from `read(...).length`.** `editPromptEffect` already does this (`commands.ts:585`), `head` is on the store interface (`packages/event-store/src/event-store.ts:364`), and it avoids a full read for a single row. Today's two forms, `events.length` (`tell.ts:405`) and `current.at(-1)?.version ?? 0` (`split-ticket.ts:241`), give the same head.
- **Failures are `unknown`, as in every other command in this file** (`commands.ts:316`, `:582`, `:603`). Neither command catches anything except what the ticket keeps:
  - `recordIssueUpdate` makes one attempt.
  - `recordSplitProgress` retries once on `ConcurrencyError`, matching `split-ticket.ts:243-248`. Use the same shape as `editPromptEffect`'s `appendLost` and then a second head (`commands.ts:584-589`).

## Each caller's silence, written at the call

The three silences differ today, and each stays exactly as it is:

- **`tell.ts` and `write-section.ts`** swallow every cause, interrupt included: `Effect.catchCause(() => Effect.void)` (`tell.ts:409`). They are inside `Effect.uninterruptible` anyway (`tell.ts:172`, `write-section.ts:120`).
  - Put one local `const quietly = Effect.catchCause(() => Effect.void)` in `tell.ts` and pipe each of the four calls through it.
  - Move the *"Appending the outcome must not be able to fail the caller either"* comment (`tell.ts:379-396`) onto it rather than deleting it.
  - `write-section.ts:121` does the same at its call. It loses its import of `recordEffect` (`write-section.ts:11`).
- **`converge.ts`** swallows every cause **except an interrupt**: `Effect.catchCause((cause) => unlessInterrupted(cause, ...))` (`converge.ts:593`, helper at `:218`). Keep that difference. Pipe both calls at `:548` and `:563` through it, and keep the comment at `:591-592` with them.
- **`split-ticket.ts`** is not silent. A failed `note` fails the step (`Effect.Effect<void, Error>`, `:238`), and only `noteFailed` catches it (`:259`, `:257-262`).
  - Keep a local `note` as a one-line adapter: `recordSplitProgress(store, ticketId, type, data, options.by).pipe(Effect.mapError(asFailure))`. `asFailure` is the mapping `lift` already uses (`split-ticket.ts:129`, imported at `:45`), so a step's error message is unchanged.
  - Keeping the name `note` matters for the next section.

## The `ELSEWHERE` rows

None of these appends is visible to the finder: the type is a variable in the helper, and `recordIssueUpdate`/`recordSplitProgress` are not in `APPEND_CALLEES` (`packages/domain/scripts/events.ts:28-34`). So the rows stay, anchored on the **callers**, and the ticket's line numbers for them are stale. They are at `events.ts:198-207` and `:295-316` today.

- **Split rows (`:298`, `:304`, `:310`, `:316`):** the anchors are `yield* note('SplitStarted', {` and similar. Because the adapter keeps the name `note`, all four stay valid untouched.
- **`IssueUpdateFailed` (`:207`):** the anchor is `'IssueUpdateFailed', // the update threw` in `tell.ts`. Keep that line and its comment exactly. It must still occur once, and the refs-sweep call at `:343` must not gain the same comment.
- **`IssueUpdated` (`:201`):** the anchor `recordEffect(store, ticketId, 'IssueUpdated', {` in `write-section.ts` must become `recordIssueUpdate(store, ticketId, 'IssueUpdated', {`. That line has to occur once in `write-section.ts`, and it does, because there is only one call.

## Tests (unit only)

Put them in a new `packages/conductor/unit/record-on-ticket.test.ts`, using `createMemoryEventStore()` with no filesystem.

1. `tellGitHubEffect` with a fake `IssueChannel` whose write succeeds, over a store whose `append` rejects. The Effect must succeed with `recorded: 'IssueUpdated'`: the write is not failed.
2. `recordIssueUpdate` called directly on the same store **fails**. This shows the silence is the caller's.
3. A `@ts-expect-error` on `recordIssueUpdate(store, id, 'SplitStarted', …)`, and the reverse case for `recordSplitProgress`.
4. `recordSplitProgress` over a store whose first append throws `ConcurrencyError` appends on the second try. A second `ConcurrencyError` fails.

The existing `integration/tell.test.ts` goes on running after the merge. Nothing here should need it, and the unit tests above stand in for it.
