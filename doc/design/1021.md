# #1021: design note

## Where each piece goes

- **The port goes in `queries.ts`**, beside `LogQueries` (`queries.ts:104-184`). Add `interface QueriesPort` with the same six methods, each returning `Effect.Effect<T>` (the error type is `never`), and `class Queries extends Context.Service<Queries, QueriesPort>()('@lingtai/event-store/Queries')`. Copy the shape of `Events` (`event-store.ts:389`, `:401`).
- **The implementations are new exported builders, and the old names become wrappers.**
  - Add `makePostgresQueries(options: PostgresLogQueriesOptions): QueriesPort` in `queries.ts` and `makeSqliteQueries(db: DatabaseSync): QueriesPort` in `sqlite.ts`, named after `makePostgresEvents` / `makeSqliteEvents` (`sqlite.ts:199`).
  - `createPostgresLogQueries` and `createSqliteLogQueries` then become one line each: `return promiseQueries(make…(…))`.
- **The faces, `promiseQueries` and `fromPromiseQueries` go in `store-face.ts`**, next to `promiseStore` / `fromPromiseStore`. `queries.ts` will then import `store-face.ts`, which imports `event-store.ts`. That is the same import cycle `event-store.ts` ↔ `store-face.ts` already has (`event-store.ts:42`), and it works because `queries.ts` uses only types from `event-store.ts`.
- **The barrel exports** `Queries`, `QueriesPort`, `promiseQueries`, `fromPromiseQueries`, `queriesLayer` and `logPredatesHoldEffect` from `index.ts`. `logPredatesHold`'s export moves from `./event-store.ts` (`index.ts:48`) to `./store-face.ts`.

## Decisions the ticket leaves open

**1. `choose.ts`: `Opened` gets `queries: QueriesPort`, and `queriesLayer` resolves through it, not through `log.queries`.**

- Add `processQueries = Effect.map(Effect.promise(openOnce), (o) => o.queries)` and `queriesLayer = Layer.succeed(Queries, deferredQueries(processQueries))`. This is the same pattern as `processEvents` / `eventsLayer` (`choose.ts:176-179`).
- `deferredQueries` becomes the shape of `deferredEvents` (`choose.ts:160-170`): it takes an `Effect<QueriesPort>` and `flatMap`s each method.
- `deferredLog`'s line becomes `queries: promiseQueries(deferredQueries(processQueries))`, so it no longer goes through `resolve`, the same way `store` doesn't (`choose.ts:236-241`). Update the doc comment there to say "store and queries".
- **Do not get the port by lifting `log.queries` with `fromPromiseQueries`.** That is Effect → face → Effect, which `store-face.ts`'s header rules out: *"A moved caller is never handed `fromPromiseStore(eventStore)` … the face's run starts a root fiber that drops the caller's span and interruption."*

**2. `open()` builds the port once, and each log is handed it.**

- `createSqliteLogQueries` prepares its statements when it is constructed (`sqlite.ts:425` onward, `db.prepare(…)`). Building a second instance would prepare everything twice on the shared handle.
- So give `PostgresLogOptions` (`log.ts:63`) and `SqliteLogOptions` an optional `queries?: LogQueries`, modelled on the existing optional `store` (`sqlite.ts:653`: `options.store ?? promiseStore(makeSqliteEvents(options.db))`).
- `open()` builds `makePostgresQueries({ url: choice.url })` or `makeSqliteQueries(db)`, puts it on `Opened`, and passes `promiseQueries(it)` to the log.
- Keep `choice.url` and never re-read `postgresUrl()`, for the reason given in the comment at `choose.ts:126-129`.

**3. `makeSqliteQueries` keeps preparing at construction.**

- Each method body is `Effect.sync(() => stmt.all(…))`, wrapped in `Effect.fn('LogQueries.<name>')`.
- A `prepare` that throws still throws synchronously from the builder, as it does today. That is construction, not a question, so leave it alone.
- **Consequence for the closed-database test in *Done when*:** call `createSqliteLogQueries(db)` *first*, then `db.close()`, then `typeCounts()`. If you close first, the test fails inside `prepare` and never reaches a face.

**4. Postgres: `ask` becomes a scoped Effect.**

- Structure: `Effect.acquireRelease(Effect.promise(connect), (c) => Effect.promise(() => c.end()))` around `Effect.promise(() => c.query(…))`, all inside `Effect.scoped`.
- Read `url()` *inside* the acquire. That keeps today's rule that building one never throws (`queries.ts:200-204`: *"Read per question rather than at construction, so building one of these never throws"*).
- Use `Effect.promise` everywhere, never `tryPromise`, because of the trap in the ticket's Watch out row.
- **Open question for you to settle in the code:** if `connect` rejects, `client.end()` is never called. That is what happens today, because `connect` sits outside the `try` (`queries.ts:207-208`). Keep it that way.

**5. `logPredatesHoldEffect` takes `Pick<QueriesPort, 'typeCounts'>`, not the whole port.**

- Callers pass a bare `MemoryEventStore` (`apps/cli/unit/log-predates-hold.test.ts:83`, `:93`, `:108`, `:124`). That object has `typeCounts` but not all six questions, so `fromPromiseQueries(queries)` will not typecheck against the face's existing parameter type `Pick<LogQueries, 'typeCounts'>` (`event-store.ts:299`).
- So the face lifts the one method inline:
  `return Effect.runPromise(logPredatesHoldEffect({ typeCounts: () => Effect.promise(() => queries.typeCounts()) }))`
- The ratchet's face check needs one `return` statement whose expression is `Effect.runPromise(<call>)` (`effect-ratchet.test.ts:208-242`). The arguments of that inner call are not checked.
- `logPredatesHoldEffect` stays in `event-store.ts` next to `LogPredatesHoldError`. Only the face moves to `store-face.ts`.
- Its body is `Effect.map(queries.typeCounts(), …)`, which *returns* the error and never calls `Effect.fail`. That way the face resolves to the error and does not reject, as the doc comment says (`event-store.ts:295`: *"Returned rather than thrown"*).

**6. `fromPromiseQueries` is six `Effect.promise` arrows.**

- No method can fail as a typed error, so unlike `fromPromiseStore`'s `append` there is no `.then` split.
- `runPromise` rejects with the defect itself (`store-face.ts:5-9`: *"else the `Die`'s defect itself"*). That is what makes the `rejects.toBe(sameInstance)` test in *Done when* hold.

## What stands in for the integration half

The Postgres `ask` runs only under `integration/queries.test.ts`, which is not run before the merge. Before the merge, two unit-level checks cover it:

- **The face test** over `fromPromiseQueries(fake)` shows a driver rejection reaches the caller as the same object.
- **The closed-`:memory:` SQLite test** shows `Effect.sync` turns a throw into a defect carrying `node:sqlite`'s own message.

The scoped release on Postgres (that `end` runs on failure or interruption) is not checked by anything before the merge. Write it as `acquireRelease`, so its correctness comes from the Effect primitive rather than from hand-written `finally` ordering.
