# Design note: #1004, the day's ceiling as a check in the guard

## Four things the ticket gets wrong or leaves out

**1. The pre-lock guard call in `lingtai run` is `heedTheLock`, not `heedThePause`.** #991 did not put the guard inside `heedThePause`. It added a separate step, `heedTheLock(locked, options.project)`, chained after `heedThePause` at the edge and before `program` takes the conductor lock (`apps/cli/src/run.ts:718-720`). `locked` is built at `run.ts:337` from `lockedFor` (`:170`).
- Delete `heedTheLock` from that chain at `:719`.
- As the first statement of `program`, after the conductor lock is held, call `locked(options.project)`. Keep `heedTheLock`'s mapping: a `could not ` sentence becomes `Refused` (exit 1), any other sentence becomes `ProjectLocked` (exit 0).
- `heedThePause` loses its `ceiling` parameter and `dayCeilingStop` call (`:152-156`) and keeps only `readControl`.
- The `Done when` item about the order can be checked by asserting that the first `store.append` of a `DayCeilingReached` comes after `ConductorLock` is acquired. A stub `locked` that records whether the lock layer was entered is enough.

**2. `lockedBy` throws away the sentence the ticket requires.** Every guard failure becomes `could not read whether ${project} is paused — ${err.message}` (`packages/daemon/src/guard.ts:66-68`). That sentence does start with `could not `, so `run.ts:582` and `:682` would still refuse. But it is the wrong sentence.
- Make `CeilingUnchecked` a `Data.TaggedError('CeilingUnchecked')<{ why: string }>`, exported from `@lingtai/daemon`.
- Type `locksFor` as `Effect<readonly Lock[], Error | CeilingUnchecked>`.
- In `lockedBy`, catch that tag first and answer `could not check the daily ceiling: ${why} — taking no work`. Other errors keep today's sentence.
- `refuseIfLocked` (`apps/cli/src/project-pause.ts:155-164`) maps failures the same way, so give it the same branch.

**3. `lingtai now` builds a guard, and it does not hold the conductor lock.** `apps/cli/src/now.ts:20` defaults to `makeGuard({ store: eventStore })`. 0126 §4 says the system locks are written "by one module, the guard, in the conductor-lock holder only". 0126 §5 still lists `lingtai now` among the gates that ask. So the port needs a form that answers without writing.
- The `ceiling` option is required and is either a `CeilingPort` or the literal `'not-the-holder'`.
- With `'not-the-holder'`, the check reads `ctl-conductor` and returns `locksOn({ project, control })` from what is stored. It reads no spend, calls no `ceilingCheck` and appends nothing.
- `now.ts` passes `'not-the-holder'`. So does any other `makeGuard` caller outside the lock holder; today the only other callers are `daemon.ts:513` and `run.ts:170`.
- The cost: a `reached` from yesterday still refuses `lingtai now` until the next look lifts it. A daemon's look is at most five minutes away, so this is acceptable. Write this in the `makeGuard` comment.
- `refuseIfLocked` adds `— lingtai resume ${project} first` (`project-pause.ts:162`), which is wrong for a ceiling lock. Choose the suffix from the locks: no suffix when a `ceiling` lock is present, because `lockSentence` already names `lingtai ceiling raise`.

**4. `lockSentence` assumes every lock is a pause.** It maps every lock to `${project} is paused by …` (`packages/domain/src/locks.ts:22-25`). Switch on `lock.kind`, and end the switch with an exhaustive `never` so the account-limit kind has to be handled when it arrives.

## The guard's check, concretely

Add `dayCeiling` to `CHECKS` (`guard.ts:39`), ahead of `projectPause`, so the order follows 0126 §8. Each check today returns its own `Lock[]` and the results are flattened (`guard.ts:44-45`). Keep that:
- `dayCeiling` returns only the `ceiling` lock.
- `projectPause` keeps calling `locksOn({ project })`.

That makes `locksOn`'s new `control` field optional rather than required. A caller that leaves it out gets no ceiling lock, and the project-pause check stays as it is. Readers outside the guard that want the ceiling pass `control`. This matches the comment at `locks.ts:4-8`: "`locksOn`'s input is an object so they can add what they read without changing what a caller passes."

What the check does:
- Read `ctl-conductor` whole with `readControl(store)`. That is the read `run.ts` already uses, and `scopeControl` is not applied to it.
- Reading through the snapshot is optional. `GuardOptions.snapshots` exists for this (`guard.ts:24-25`). The daemon does not pass it today (`daemon.ts:513`), so do not wire it here.
- Append with `expectedVersion` set to the version the read returned. On a version conflict, re-read once, call `ceilingCheck` again and append what it returns. If the second append also conflicts, fail with a plain `Error`. That stops the claim, and the next look decides again.
- The exact store call and the conflict error class are whatever `raiseDayCeiling` uses in #1003. Grep for it in `apps/cli/src/` and copy it rather than inventing another.
- `ceilingCheck` sets `actor: 'conductor'` (`packages/domain/src/ceiling-lock.ts:52,72`). Do not override it.

`now` is `options.now?.() ?? new Date()`. Read it once per `locksFor` call and use it both for `ceilingCheck` and for the port's `todaysSpend(now)`.

## The port's spend read is an Effect with no new `async`

Build `todaysSpend` as `Effect.gen`. The stall and rebuild reads go through `Effect.tryPromise` around the same calls `dayCeilingStop` makes (`apps/cli/src/day-ceiling.ts:80-113`). Each failure is `Effect.fail(new CeilingUnchecked({ why }))`, with the `why` texts copied from what that function says today.

`configuredUsd` wraps `machineDayCeiling()`, which throws on a malformed value (`packages/env/src/index.ts:979-1000`). Call it inside the check through `Effect.try`, and map the throw to `CeilingUnchecked`. Then a malformed figure fails before anything is appended, including a `config-removed` lift.

## The daemon

- `daemon.ts:513` becomes `makeGuard({ store: eventStore, ceiling: ceilingPort(undefined, {}) })`.
- `claiming` (`daemon.ts:557-563`) keeps calling `pausedSentence({ control })`. That function moves into `daemon.ts` with its `ceiling` member removed.
- Because the work loop's `paused` no longer sees the ceiling, the loop no longer ends a look for it. `conductProjects` already asks `locked(name)` per project and `continue`s (`apps/cli/src/conduct.ts:795-797`). The unit test with two projects in the `Done when` should drive that path.

## Wake

Add `DayCeilingLifted` to `COMPLETION_EVENTS` next to `AccountLimitLifted` (`packages/daemon/src/work-loop.ts:129-130`), with a comment in the same form. For #996 and #997, add it at whichever trigger lists contain `'ProjectResumed'` outside `work-loop.ts`; `rg "'ProjectResumed'" apps packages -g '!**/unit/**'` finds them.

## Ratchet

Deleting `dayCeilingPause`, `liftOwnPause`, `dayCeilingStop` and the two `pausedSentence`s removes `async` functions in `packages/conductor` and `apps/cli`. The `pausedSentence` that moves into `daemon.ts` stays `async`, which is a move within `apps/cli` and not an addition. Run `pnpm test -- effect-ratchet`. Lower each number it reports as fallen, in this change. Raise none.

## The only-writer test

A unit test that greps `apps/` and `packages/*/src` for `type: 'DayCeilingReached'` and `type: 'DayCeilingLifted'` will find `packages/domain/src/ceiling-lock.ts`. That file builds the events; it does not append them. So assert the set of files that call `ceilingCheck` or `raiseTransition`, not the files that hold the event literal:
- `ceilingCheck`: `packages/daemon/src/guard.ts` only.
- `raiseTransition`: the `raiseDayCeiling` module only.

`packages/domain/scripts/events.ts:136-145` anchors on the literal in `ceiling-lock.ts`. Update the prose naming the caller there, then run `pnpm events:generate`.
