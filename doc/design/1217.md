# Design: #1217 — resolve, ask and close become Ticket owner commands

## 1. The non-ticket checks run inside the command, through a hook, so the refusal order stays as it is

#1203 handled release's kill with a hook: `beforeAppend` runs between the transition and the append, against the same read (doc/design/1203.md §4). Use the same pattern here. The checks the ticket keeps outside cannot all run before the command is called, for two reasons:

- They need what the read returns. `savedHead` and `checkApprove` need `block.runId` and `block.reason` (`resolve-wait.ts:325`, `:357`). The triage answers need `triageFactsFromState(item, waitId)` (`:375`).
- The tests pin the order. `resolve-wait.test.ts:116` expects `split(sound)` with no kinds to answer `no-kinds`, and `:123` expects `split-not-written` only once kinds are given. Today the code checks `not-blocked` → `not-offered` → `no-kinds` → `invalid-split` → `split-not-written` (`resolve-wait.ts:263-318`). If every state check ran in one transition before anything else, `split(sound)` would answer `split-not-written`, and that test would go red.

**The owner's resolve command (e.g. `resolveTicketWaitEffect`) runs these steps:**

1. Read through the snapshot, with the caller's `snapshots`/`writer`, as `:228` does.
2. Call the domain's `resolveWaitTransition(state, { waitId, resolution })`. It answers one of:
   - `repeat`: the already-approved case at `:243-249`, carrying `runId`;
   - a refusal, `not-blocked` or `not-offered`;
   - `proceed`, carrying the `block`.
3. On `repeat`, return without appending.
4. On `proceed`, call the caller's `prepare(state, block)`. It returns either a refusal or `{ resolution, answers?, wroteBody }`. Everything the ticket keeps outside goes in this closure, which stays in `resolve-wait.ts`:
   - `no-kinds` and `invalid-split`;
   - `savedHead` and the remote ref, including the rewrite of `GrantFixRound` to `{onSha: head, ref}` (`:351`);
   - `checkApprove`;
   - the triage answers and `writeSectionEffect`.
5. Run the split-written check: `split-not-written`, done by the transition. It sits after `prepare`. For a `Split` resolution the only `prepare` checks that apply are `no-kinds` and `invalid-split`, so the order matches today.
6. If `wroteBody`, re-read and run the `not-blocked` check again. That is `:405-412`'s refusal, with `written: true` carried through. Then take the new version.
7. Build the events from the transition. Append `[...those events, ...with]` at the version. A `ConcurrencyError` becomes `lost`.

The `bad-sha` format check (`:216-226`) needs no state, so it stays in `resolve-wait.ts` before the command is called. The `stale` answer and its `written` flag (`:448-455`) are built by `resolve-wait.ts` from the command's `lost` result. The same goes for every refusal's `detail` text: the domain returns the reason and its data, and the detail sentences stay where they are now, so the existing tests that match on `detail` are unaffected.

**`ContinueRequested` stays in `resolve-wait.ts`.** That covers `requestContinuation` (`:530-565`), the `repeat` path's call at `:251-257`, and the call after the append at `:481-487`. The command returns enough for that call: the `block.runId`, or the `repeat`'s `runId`. It never calls `requestContinuation` itself. That file sits under `packages/conductor/src/ticket/`, where nothing is counted, and 0129 §4–5 is 0.16's.

`resolveWaitEffect` and `resolveWaitHoldingEffect` keep their names and signatures in `resolve-wait.ts`, so `approve.ts`, `split-ticket.ts`, `edit-body.ts` and the board (`apps/board/src/app/actions.ts:47`) do not change. `decidingEffect` keeps wrapping from outside (`:198-210`). Name the owner's commands `resolveTicketWaitEffect`, `askTicketEffect` and `closeTicketEffect`, after `claimTicketEffect` (`ticket/commands.ts:111`). This avoids a clash with `resolve-wait.ts`'s exported `resolveWaitEffect`.

`store` is required on each command, as in #1203 §2 (`ticket/commands.ts:72`, *"the owner opens no process store"*). The three outer files keep their `options.store ?? eventStore` default and pass the store down.

## 2. The person's release is a third `ReleaseInput` variant whose actor is the person

`releaseOf` writes `actor: options.by` and the reason `` `Requeued by ${by}${how}.` `` with `cause: {_tag:'ByPerson', waitId}` (`resolve-wait.ts:722-735`). `releaseTransition`'s `'run'` variant writes `actor: 'conductor'` (`packages/domain/src/ticket.ts:913`). Passing `{by:'run', …}` through as it is would change the actor on every person's requeue.

**Decision:** add `{ by: 'person'; person: string; runId: string; waitId: WaitId; how: 'Requeue' | 'EditBodyAndRequeue' | 'Split' }` to `ReleaseInput`.

- It never refuses.
- The `how` wording moves into the domain, as the dead-worker sentence did in #1203.
- The function's single `return` at `:913` takes the actor as a variable: `input.by === 'person' ? input.person : 'conductor'`.

**Do not write a second `type: 'TicketReleased'` literal.** The `ELSEWHERE` anchor `"type: 'TicketReleased'"` must occur exactly once in `ticket.ts` (`packages/domain/unit/events-json.test.ts:81-86`).

The resolve transition calls `releaseTransition` itself, and only when `block.runId !== null` and the resolution is one of those three tags. That is `releaseOf`'s condition at `:715-717`, and the call is composed into `proceed`'s events. Then delete `releaseOf`.

## 3. Close: one transition, the end plan loaded through a hook, and one append when blocked

`closeTicketEffect` reads raw events with `store.read`, as `close.ts:152` does, because `resolveEndActions` (`packages/conductor/src/end-step.ts:90`) needs the envelopes and not the state. The owner may import it, since `end-step.ts` is in the same package. The command runs these steps:

1. Run `closeTransition`'s first checks, in today's order:
   - `already-closed` (`:156`);
   - `landed` (`:159`);
   - `changed` against `ifVersion` (`:165`).

   The ticket's *Want* says *the checks these three make against the ticket's reduced state*, and these three are such checks, so they move with `wait-moved` even though the *Fix* list does not name them.
2. Call the caller's `loadEnd()` → `readonly StepAction[] | refusal`. That is the recipe read, `close.ts:175-197`, kept in `close.ts` as a closure. It runs after step 1 so that an already-closed ticket with an unreadable recipe still answers `already-closed`. Without a `state` and `client` it answers `[]`, as today.
3. `resolveEndActions(events, end, 'closed')`.
4. If the ticket is blocked, the transition checks `wait-moved` (`:221-229`). It then composes the resolve transition's output for `{_tag:'Close'}`, with the `waitId` the card sent and `note: reason`, followed by `TicketClosed` and the end plan.
   - This is one append at the version from step 1's read.
   - **The owner does not call its own resolve command.** That would be a second read at a second version.
   - `Close` is always offered and never releases (`releaseOf` returns `[]` for it), so `not-offered` cannot fire here.
   - A lost race answers `stale`, which is what `resolveWaitHoldingEffect` answered for a blocked close.
5. If the ticket is not blocked, append `[TicketClosed, ...ended]` at the same version. A lost race answers `changed` (`:243-248`).

`tellGitHubAboutEffect` and `labelsFor('closed')` stay in `close.ts`, after the command returns (`:252-266`).

`TicketClosed` is built in the domain transition, carrying `{by, reason}` with `actor: by`, as today (`:204-208`).

## 4. Ask

`askTicketEffect`:
- does the `not-backlog` transition (`ask.ts:69-77`);
- builds `WaitStarted{OwnQuestion}`;
- maps a `ConcurrencyError` to `changed`, as at `:105-107`.

The `waitId` comes from `crypto.randomUUID()`. **Generate it in the command and pass it to the transition**, so the transition stays pure and its test can name the id. The `blank` check (`:61`) reads no state, so it stays in `ask.ts`.

## 5. `events.ts`'s `ELSEWHERE`, which a run of the unit half will otherwise turn red

The finder attributes an event only where an append call's argument names it, so moving the literals into the domain changes four things:

- **`TicketSplit`** (`events.ts:283-287`): repoint its row to `packages/domain/src/ticket.ts`. Use an anchor that occurs once there, for example `"type: 'TicketSplit'"`.
- **`TicketClosed`** (`:277-281`): repoint the same way.
- **`WaitResolved`**: its only appender today is `resolve-wait.ts:426`. Moved, the finder loses it, so it needs a new row pointing at `ticket.ts`. Use the same `why` wording as the three rows #1203 added (`:59-76`).
- **`WaitStarted`**: still found at `conduct.ts:5713`, so it **must not** get a row. A row for an event the finder finds fails `events-json.test.ts:76-79`.

Then run `pnpm events:generate`.

## 6. Tests and bookkeeping

- **Transition tests** go in `packages/domain/unit/ticket-transitions.test.ts`. Cover each refusal, the `repeat`, and the person release's actor and reason.
- **Owner tests** go in `packages/conductor/unit/`, using `createMemoryEventStore()`:
  1. A blocked close appends `WaitResolved`, `TicketClosed` and the plan in one `append` call. Count the calls with a spy. The type sequence alone would not distinguish one append from two, and `close.test.ts:263` checks only the sequence.
  2. A `prepare` that writes to the same stream without `wroteBody` loses the race and answers `stale`; it does not succeed on a re-read.
  3. A `not-blocked` or `already-closed` refusal never calls `prepare` or `loadEnd`.
- **`aggregate-owners.baseline.json`**: drop the `ask.ts`, `close.ts` and `resolve-wait.ts` rows. Afterwards, check that `close.ts` contains no `type: 'TicketClosed'` in an append argument and that `resolve-wait.ts` contains no `ticketId` passed to an `append`. Either one is still counted (`aggregate-owners.test.ts`, its header's rule).
- **The ratchet**: this adds no `async`. Lower `effect-ratchet.baseline.json` only if its test says to, and never raise it.
- **Out of reach before the merge**: approve's GitHub-touching paths, and `split-ticket`'s real writes, are integration-only. The unit claims that stand in for them are the order tests already in `resolve-wait.test.ts:91-128` and `close.test.ts:241-292`, run unchanged.
