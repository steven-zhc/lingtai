# Design: #582 — the triage answer schema goes to the runtime

## The decision the ticket leaves open: triage has two reply shapes, and the root has to be an object

Each triage round is one runtime run (`apps/cli/src/triage.ts:641`, `:678`), and each run may answer in **either** of two shapes. The brief says so: *"One JSON object and nothing else. Two shapes, and only two."* (`packages/conductor/src/triage.ts:301`). The two shapes are `{"read":[…]}` (`READ_CONTRACT`, `packages/conductor/src/read-step.ts:41`) and the advice. `parseTriage` tries the read shape first (`triage.ts:363-365`). A schema that only describes the advice would make every round a forced answer, and the read rounds would be lost.

A root-level `anyOf`/`oneOf` of the two shapes cannot carry this. Claude Code's `--json-schema` is a forced tool call (`packages/agent/src/claude-code.ts:291-295`: *"A forced tool call … every run that carried this flag answered `stop_reason: "tool_use"`"*), and a tool's input schema has to be `type: object` at the root. OpenAI structured output has the same rule. **So the schema is an envelope:**

```
{ "read": string[] (maxItems READS_PER_TURN) | null,
  "answer": TriageAnswer | null }
```

Both keys are required and both are nullable. That is the convention `ReviewAnswer` already chose, and its comment gives the reason (`packages/domain/src/events.ts:974-982`: *"All-required, and `about` is required but nullable rather than optional — a decision, not a quirk"*). Put a `.meta({ description })` on each key that says to fill exactly one, so the instruction reaches the model inside the schema too. The brief's prose stays as it is.

**Unwrap, then run the one final check you already have.** When `outcome.structured` is present, build the flat object: `{read}` if `read` is non-null, otherwise `answer`. `JSON.stringify` it and hand the string to `parseTriage`. When `structured` is absent, call `parseTriage(outcome.text)` exactly as `triage.ts:725` does today. `createAgentAction` reads its answer the same way, structured first and text as the fallback (`packages/actions/src/agent-action.ts:624-630`). The reason to read `structured`: under `--json-schema` the constrained object arrives as `structured_output` (`claude-code.ts:582-583`), and `outcome.text` is not promised to contain it. `parseTriage` stays the only judge, which covers the third *Done when* box and also the refinements no schema can express:
- `recommended` names one of the answers (`packages/domain/src/triage.ts:51-54`)
- the `ConflictingHunks` total/hunks rule (`wait.ts:753`)
- the `Split`/`ContinueConflict` pairing (`wait.ts:791-806`)
- the split's acyclicity (`split.ts:177`)
- `BUDGET_NAMED` and `AnswerQuestion` (`conductor/src/triage.ts:381-397`)

## Where the schema comes from: one zod object, exported

`TriageAdvised` is a private `const` (`packages/domain/src/wait.ts:783`). It carries `_tag: 'TriageAdvised'`, which the agent never writes (`parseTriage` injects it at `conductor/src/triage.ts:403`), and it has a `.superRefine`. In zod 4, `.omit()` throws on an object that has refinements. **So split it.**

- Export a plain strict object, `TriageAnswer = z.strictObject({ cause, resolution, summary, want })`.
- Build `TriageAdvised` from it: `TriageAnswer.extend({ _tag: z.literal('TriageAdvised') }).superRefine(…)`.

There is then one copy of the bounds. Define the envelope and `TRIAGE_ANSWER_JSON_SCHEMA` beside it in `wait.ts`, in the same form as `REVIEW_ANSWER_JSON_SCHEMA` (`events.ts:999-1003`): `z.toJSONSchema(...)` with `$schema` deleted. Use `READS_PER_TURN` for the read bound; it lives in `conductor`, so either move the constant down into `domain` or have `conductor` re-export a domain constant. Do not hard-code a 6.

I ran `z.toJSONSchema(TriageResult)` in this worktree. It already emits:
- `maxLength: 500` on `fixes.items.properties.what`
- `maxItems: 20` on `fixes`
- `cause` as a `oneOf` of the six `const` `_tag`s
- `want` as `anyOf [string ≤200, null]`

So the generated schema has nothing to hand-edit. The unit test belongs in `packages/domain/unit/` next to `review-answer.test.ts`. It should assert:
- `answer.anyOf[0].properties.cause.oneOf` has six `_tag` consts
- the `what` `maxLength` equals `TRIAGE_TEXT_MAX`, compared to the constant rather than the literal `500`
- the root is `type: "object"` with no `$schema`
- both envelope keys are in `required`

## Which runtimes get it: a capability, not a runtime id

Triage always asks for `tools: 'none'` (`apps/cli/src/triage.ts:561`). That changes the ticket's runtime list:

- **Claude Code** (`runtimes.ts:89-93`) runs with a deny-list settings file (`apps/cli/src/discuss.ts:82-95`). `StructuredOutput` is not on that list. This route carries the schema.
- **Codex with `tools: 'none'` is always `createCodexTextRuntime`** (`packages/agent/src/runtimes.ts:116-137`). The Codex CLI's `--output-schema` (`codex.ts:968`) is **never reached by triage**. The text route refuses any schema outright: `if (request.outputSchema) return failure('crash', 'model-only calls do not support outputSchema')` (`codex-text.ts:50`).

**This is the trap.** If triage sends `outputSchema` unconditionally, every Codex triage turns into `TriageFailed{why:"crash: model-only calls…"}`. That is worse than the bug being fixed, and Codex triage is exactly the route #565 added.

Do not branch on `request.triage.agent === 'claude-code'`. Add a field to `RuntimeCapabilities` (`packages/agent/src/runtime.ts:37`), e.g. `acceptsOutputSchema: boolean`:
- `true` in `CLAUDE_CODE_CAPABILITIES`
- `true` in `CODEX_CAPABILITIES` (the CLI route, used by the cold reviewer)
- `false` in `codex-text.ts:22`

Triage spreads `outputSchema` into the `run` request only when `runtime.capabilities.acceptsOutputSchema`. The capability then tells the truth about each adapter, and the Responses route can turn it on later without triage changing. Update `RunRequest.outputSchema`'s comment (`runtime.ts:123-127`, *"sent only by the cold reviewer"*), which stops being true.

**Do not wire the schema into `codex-text.ts`'s Responses `text.format` in this ticket.** OpenAI strict mode refuses an optional property, and `TicketTooBig.split` is `.optional()` (`wait.ts:762`). It supports `anyOf` but not `oneOf`, and the triage schema is `oneOf` twice. `SplitProposal` is `z.object`, not strict (`split.ts:165`). And nothing in this repository has yet shown whether strict mode accepts `maxLength`: `REVIEW_ANSWER_JSON_SCHEMA` carries no length bound, so the cold reviewer's working Codex path proves nothing about it. The PR should say that the Codex text route still relies on the prompt sentence (`conductor/src/triage.ts:98-101`), which therefore stays, and why.

## What the unit half can check, and what it cannot

All of the following can be unit-tested in `apps/cli/unit/triage.test.ts`, whose fake runtime builds `capabilities` at `:81-89`:
- with the capability on, `seen[0].outputSchema` is `TRIAGE_ANSWER_JSON_SCHEMA`
- with it off, the request has no `outputSchema`
- a `structured` envelope with `read` set serves files and goes round again
- a `structured` answer whose `fixes[0].what` is 501 characters is still refused by `parseTriage`, which proves the final check survives a runtime that ignores the schema
- `structured` absent still falls back to `text`

What the unit half cannot show:
- that Claude Code accepts this nested schema under `permissionMode: 'default'` with the deny-list
- that the forced tool call fits the recipe's `triage.limits.turns` (`recipe.ts:2993-2996`); a forced tool call may cost a turn, and a recipe with very few turns could start ending in `out-of-turns`

Only a live run can show either, so check after the merge. An `error_max_structured_output_retries` surfaces as `failure.kind: 'no-structured-answer'` (`claude-code.ts:375-377`), and triage's existing failure branch (`apps/cli/src/triage.ts:716-720`) records it as `TriageFailed`. The fields that settle the question are `WaitTriaged.result.why` beginning `no-structured-answer:` or `out-of-turns`, and `RunSpent.turns` for `for._tag: 'Triage'`, read before and after the change.
