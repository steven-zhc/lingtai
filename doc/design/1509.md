The ticket already covers almost all of the change. These three points are what the code adds to it:

**1. Use `Effect.forEach` with `{ concurrency: 8 }`.** Put it in place of the loop at `packages/project/src/pr.ts:311`, over `1..(highest ?? 0)`.
- **Order:** `Effect.forEach` returns results in input order however many run at once, so `draftedTicketsIn` still gets streams in PR-number order. No extra sorting is needed.
- **Failure:** the first read that fails fails the whole effect and interrupts the reads still running. That is the edge the ticket wants, and it keeps the function's doc comment true: *"A failed read is the error, never *none drafted*"* (`pr.ts:308`).
- **Ratchet:** `Effect.forEach` is already used in `pr.ts` and `state.ts`. It adds no `async` function and no `Effect.run*`.
- Leave `readPrsUpTo` (`pr.ts:103–:111`) alone, even though it has the same serial loop. `listPrs` is out of scope.

**2. Sharing works through the existing cache key, so don't change any reader.**
- `readPrEvents` calls `store.read(prStream(project, n))` with no `fromVersion` (`pr.ts:78`).
- `memoStore` keeps each read under `` `${streamId}\0${fromVersion ?? 1}` `` (`apps/board/src/lib/request-store.ts`, the `read` method).
- `listPrs` reads through the same `readPrEvents` (`pr.ts:82–:83`, `:107`), so the page's reads and queue discovery's reads land on the same key and share one read.
- The project stream is shared the same way, through `highestPr` → `readProjectEvents` (`pr.ts:91–:100`).
- If this change ever needs `fromVersion` or a snapshot read, the sharing quietly stops. Point 3 includes a test that catches that.

**3. Making the call-site swap.**
- `board.ts:49` and `queued.ts:38` import `eventStore` from `@lingtai/event-store`. Neither imports `requestStore` yet.
- Import `requestStore` from `./request-store.ts` and pass `store: requestStore()` at `board.ts:1018` and `queued.ts:349`.
- Leave the `eventStore` import in `board.ts` if other code in that file still uses it.
- Don't touch the conductor's own calls to `landedFor`, at `packages/conductor/src/schedule.ts:241` and `conduct.ts:3279`. They pass the daemon's store and only get the concurrency half.
- `request-store.ts` gives the rule: *"Pages and their loaders read through `requestStore()`. A server action never does."* Both call sites are on a render path, so neither is affected by it.
