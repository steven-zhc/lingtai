# Design note: #962, `init.test.ts` passing again

## What these tests are, and why the ticket's `gh` theory misses

`apps/cli/integration/init.test.ts` does not start a `lingtai` process. It calls `initCommand` directly, inside the test process, with a scripted `InitWorld` (`world()`, `init.test.ts:122-262`). These tests never look at whether the test machine has `gh`:

- `ghStatus` is a stub that always answers `{ ok: false, reason: 'missing', detail: 'gh is not installed' }` (`init.test.ts:203`).
- `ask` answers `app` to #710's question on purpose (`init.test.ts:163-166`: *"The world's `ghStatus` is never ready, so `app` is the one answer that carries on to the App question these tests were written against"*).

So `github  gh cannot be used yet — …` (`github-auth.ts:173`) is the path these tests chose. It is the end of the captured output, not the failure. **Do not add a `gh` stub on `PATH`, and do not change `ghStatus`.** The "same command line exits 0 by hand" observation is a different world: real git, real `gh`.

Reading the code, none of the ten looks like a fault in `init`. All ten trace to two changes in `init` that the test fixtures never followed. Confirm each one against the run's output before you mark it in the commit.

## Cause 1: the exit 1s (`:306`, `:323`, `:858`) are a stale `gitPlan` key

Each of the three local tests plans `'/repo::rev-parse --verify main^{commit}'` and `'/repo::symbolic-ref --short refs/remotes/origin/HEAD'`. The local branch no longer asks git either of those:

- A given base is checked as `rev-parse --verify refs/heads/${answer}^{commit}` (`first-project.ts:559`), and again at `:729` if the landing moved it.
- The checked-out branch is read as `symbolic-ref --short -q HEAD` (`first-project.ts:568`), and only when the answer is `lingtai-base`.

Any call not in the plan throws ``unplanned git call: ${dir}::${gitArgs.join(' ')}`` (`init.test.ts:224`). Read the first run's output to confirm that this is the message behind the exit 1, and find which layer turns the throw into a refusal. Then fix the fixture:

- Change the key to `refs/heads/main^{commit}`.
- Delete the `origin/HEAD` entry if nothing calls it. A plan entry that is never used hides the next drift.
- Pull the three copies into one `const LOCAL_REPO_GIT` next to `RECIPE_FLOW_FLAGS`, so the next change to these calls is a one-line edit.

**Mark these *stale expectation*.** If the output shows a refusal from `init` or `first-project` with the correct key in place, it is a fault in `init`, and it is in scope.

## Cause 2: blocks that are held back and then dropped (`:532`, `:658`, `:682`, `:742`, `:753`, `:806`, and `:858`'s later lines)

#773 holds the heading, `Machine` and `Store` blocks in `held` (`init.ts:328`: *"The heading, `Machine` and `Store` are printed only by a run that does not end on the card"*). These lines are dropped from the output:

- The local branch drops `held` (`init.ts:661`, `held.length = 0`). So does every GitHub branch, through `machineCard` (`init.ts:541`).
- `doc/design/773.md:127` still says *"A GitHub or already-registered run still contains `Machine` and `Store`"*. Since the GitHub paths moved onto `machineCard`, only a run that already has projects keeps those blocks.

So these sentences never reach `seen.lines` on the paths these tests take:

- `tables present` (`init.ts:828`)
- `SQLITE_MACHINE` (`sqliteChosen`, `init.ts:1139-1140`)
- `…, exported into this process` (`describeStore` → `packages/env/src/index.ts:628`)
- the line that starts with `store ` (what `:753` searches for)

`app  lingtai-me, owned by me — it answered` (`github-app.ts:142`) is printed only when the App was just made. On a re-run with the App already configured, what remains is the card's `github` row, `the App lingtai-me` (`reachRow`, `init.ts:569`).

What the card does carry is its `this machine` group (`setup-card.ts:170-176`):

- `home`
- `log`: `SQLite · lingtai.db`, or `Postgres · db.example` (`logRow`, `setup-card.ts:107-115`)
- `agents`
- `github`, when the run is on a GitHub path

**Re-pin each claim to what still proves it. Do not swap in a looser substring.**

- **`:532`**: the second run's `github` row is `the App lingtai-me`. Keep `failing.seen.lines` not containing `it answered`, and keep `apps === 1`.
- **`:658` "uses a database already set in the environment"**: these already prove the variable was used: `seen.connected` equals `[URL_]`, `config(home)` equals `GITHUB_APP`, and `asked` equals `[]`. Add that the card's `log` row is `Postgres · db.example`. Drop the `exported into this process` line.
- **`:806` "the exported variable wins"**: the file says `store: sqlite`. The card's `log` row reading `Postgres · db.example` together with `connected` equal to `[URL_]` is the proof that the variable won. Assert both, and keep the check that the file is unchanged.
- **`:682`**: replace `tables present` with the database actually being reached again (`again.seen.connected` equals `[URL_]`) plus the `log` row. Expect a cascade: `lingtai-me, owned by me` at the end of this test is a held line too, so pin it to `the App lingtai-me`. Check whether `claude-code  signed in via claude.ai` still matches the card's `agents` row rather than assuming it does.
- **`:742`, and `:858` once Cause 1 is fixed**: replace `SQLITE_MACHINE` with the `log` row `SQLite · lingtai.db`. `storeChoice(...)` is already asserted beside it, and that assertion is what these tests exist for.
- **`:753` "confirms with the same function a later command asks"**: the card's row is drawn from `storeNow = storeChoice(world.env, machineFor(world, path))` (`init.ts:376`), which is the reader later commands use. Find the `log` row and assert that it equals what `storeChoice({ LINGTAI_HOME: home })` reads, rendered as `Postgres · ${new URL(url).hostname}`. Only export `logRow` if that rendering would otherwise be copied by hand in more than one test.

**How to match card rows**, following `773.md:127`: strip ANSI colour, then match on the label with `trimStart().startsWith('log ')`. Never match a fragment that could appear anywhere in the output.

**Test titles that now overclaim.** `:806`'s title says *"and it says which it was"*. The card no longer names where the store came from. Rename the title to what the test now asserts. The commit then says outright that the provenance sentence is gone from these paths, and adds it as a backlog line. **Putting `exported into this process` back into the card is out of scope**: what the card holds is `doc/design/the-card.md`'s decision, not this ticket's.

## Cause 3: `:876`'s sentence was replaced by #762

The test expects `the store chosen above is kept`. The refusal is `` `${q.name} needs an answer: pass ${q.flag}. ${q.kept}` `` (`question.ts:149`). Here `kept` comes from `initKept` (`init.ts:1118-1136`). On a fresh home where this run wrote the file, that is `the store is kept, SQLite at ${db}, chosen in ${configPath}` (`:1133`). `the store chosen above is kept` is now returned only when the store choice was refused (`:1123`).

The new sentence is a stronger true claim, so this is a stale expectation. Assert the full sentence, built from `join(home, 'lingtai.db')` and `configPath({ LINGTAI_HOME: home })`. Keep `not.toContain('Nothing was written')`, `boards === 0`, and the flag-text check.

## Things not to change

- **The fixture's `ask`**: `expect(question).toMatch(/Postgres/)` (`init.test.ts:174`) makes any unrecognised question fail the test. That is the fixture's guard. If a new question turns up, answer it by flag the way `RECIPE_FLOW_FLAGS` does, rather than loosening the guard.
- **Fix one failure at a time, and re-run after each.** Several tests have a second stale line behind the first, as `:682` and `:858` do.
