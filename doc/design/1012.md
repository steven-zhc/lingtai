## Design note for #1012: reword the setup pause, and show a project's lock on the task page's Queued panel

Every predecessor has landed in this worktree: #994, #995, #1006/#1007, #1008–#1011 and #1013 (`3f5aaf7d Merge branch 'agent/1013'`). The ticket's line numbers are out of date. The places to edit are below by name, with the line each sits at today.

### 1. Lock words get one owner, in `lock-marks.ts`

The ticket wants the task page's `holding` to use "the same phrase the home page's queued card uses … from the one function #995/E/F use". No such function exists yet. The phrases are inline in `queuedStanding`: three branches, for the ceiling, an account limit and a project pause, at `apps/board/src/lib/board.ts:1845-1871`, in that order.

- Move those three branches out into a pure function in `apps/board/src/lib/lock-marks.ts`, something like `lockStanding(project, locks, now)`. It returns `null`, or `{ kind, text, title, waitsFor }`. Keep the existing order: ceiling, then account (the first one by runtime), then paused.
- `lock-marks.ts` is the right home because its header says it is *"Pure and import-light on purpose"* (`lock-marks.ts:5`). It already imports `@lingtai/domain`, which is where `whenLabel` comes from (`locks.ts:28`).
- `queued.ts` must not import `board.ts`. That file is 86K and reaches `eventStore` (`board.ts:31`).
- Each of the three lock phrases must keep exactly the words it has today. They are now shared by the card and the panel, and a home-page test already pins them.
- `queuedStanding` keeps its own setup branch first (`board.ts:1838`), then calls `lockStanding`, then falls through to the backoff.
- `waitsFor` is the clause `runNowCaption` needs:
  - *`<project>` is resumed*
  - *midnight, or until today's ceiling is raised*
  - *`<runtime>`'s limit passes (`whenLabel(until)`)*
- The panel's short chip word is the kind itself: `paused`, `ceiling` or `usage limit`.

### 2. What `QueuedView` gains

`QueuedView` (`queued.ts:~130-186`) has no project field, but the sentence needs to name the project. Add two fields:

- `project: string`
- `locks: readonly Lock[] | null`, where **`null` means the read failed** and `[]` means nothing holds the project. These must stay two different values: #77, and `lockMap`'s own *"unknown is not paused"* (`lock-marks.ts:15`).

`queuedFor`'s input (`queued.ts:263`) and `refused(problem, plan, paused)` (`queued.ts:238`) both take the project and the locks and pass them through. Every early return of `refused` (`queued.ts:274`, `:278`, `:339`) carries them as well.

Where the locks come from: in `loadTaskAnswer` (`task.ts:2117`), inside the `standing.state === 'queued'` branch:

- Await `readProjectLocks()`. It never rejects (`locks.ts:81-114`).
- Pass `read.ok ? (read.held.find(h => h.project === parsed.project)?.locks ?? []) : null`.
- That includes the `.catch` → `refusedQueued(…)` path at `task.ts:2144`.

This costs no extra read. `task/[id]/layout.tsx:279` already renders `<LockBanner project={project} />`, which calls the same `cache`d `readProjectLocks` in the same request.

**A `controlProblem` is not counted as a failed read.** `readProjectLocks` can answer `ok: true` with `controlProblem` set (`locks.ts:62`), which means the ceiling is unknown. The panel follows #995's cards there: `lockMap` looks only at `ok` (`lock-marks.ts:16-18`). The banner on the same page already says the control read failed. This also matches the ticket's Edges, which keep the `emptyControl` fallback (`task.ts:1699-1703`) as it is.

### 3. Precedence on the panel

`holding` (`queued.ts:368`) checks these in order:

1. not offered (unchanged)
2. `paused`, the setup pause, with the setup sentence
3. `locks === null`: *could not read whether `<project>` is held*
4. `lockStanding(...)?.text`
5. the backoff

`runNowCaption` (`queued.ts:379`) follows the same order:

- setup: *the request waits until the setup is fixed and the conductor resumed*
- unread: *whether the request would wait could not be read*
- a lock: *the request waits until `<waitsFor>`*

`queuedChip` (`queued.ts:452`):

- **Keep position first**, as it is today, and add the new branches after `notOffered`: setup → `paused`, unread → `unknown`, a lock → its kind word, then the backoff.
- Today a setup-paused ticket in line already shows `1st of 3` on the chip and the pause in the sentence. A card under a lock likewise *"keeps its place"*, as the home page puts it (`board.ts:1869`). So the place is still true, and `queuedSentence` (`queued.ts:463`) puts `holding` first.
- Write the chip tests with `position: null`, as the existing ones do (`queued.shape.test.ts:79`).

Two things come with this order and need no extra code:

- **`queued-estimate.ts:120` hides the start estimate** whenever `holding` is not null. A lock, or an unread read, therefore also removes *Taken next…*.
- **The panel shows no resume and no lift.** The only button on it is Run now (`standing.tsx:1675`), which stays, and its caption carries the wait.
