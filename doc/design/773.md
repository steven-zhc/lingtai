# Design note for #773

## Where it goes

- **`apps/cli/src/setup-end.ts`** (new). It holds one printer, `printSetupEnd(world, facts, hints, doctor)`, used by both `init` and `add`. It prints `renderSetupCard(facts)`, then each line of `hints` muted, then `renderReadyLine(...)`, then doctor's short blocks when there is anything to fix. It returns `{ failed: boolean }` so `init` can build its `next:` line. The same file holds `liveSetupDoctor()`, the dynamic-import doctor that `init.ts:1159-1169` has today, moved here so that `liveAddWorld` and `liveInitWorld` share it.
- **`apps/cli/src/setup-card.ts`**: drop its value import of `doctor.ts` (below).
- **`init.ts`**: hold back the machine and store sections, draw the card on the local branch, and keep the board check without printing it.
- **`add.ts`**: `AddWorld` gains `log`, `doctor`, `store` and `userHome`. `addFlow` draws the card when `result.project === 'local'`.
- **`first-project.ts`**: the local arm of `FirstProjectOutcome` (`:200`) carries what the card needs.
- **`recipe-flow.ts`**: `renderSummary` is deleted, the price hints are returned instead of printed, and the confirm gets new words.
- **`source.ts`, `landing.ts`, `setup-build.ts`, `question.ts`, `prompt.ts`**: the echoes go, and the detection lines move onto the question.
- **`packages/conductor/src/onboard.ts`**: `addLocal` also returns `updated`.

## Keep `doctor.ts` out of `init`'s static import graph

`init.ts` imports doctor dynamically on purpose: *"Dynamic, never a static import of `./doctor.ts` — this file's header warns that an eager log read breaks a fresh machine"* (`init.ts:1156-1157`). `setup-card.ts:12` imports `toFixSummary` from `./doctor.ts` as a **value**. If `init.ts` imported `setup-card.ts` statically, that rule would break without anyone noticing.

So:

- `setup-card.ts` imports only types from `doctor.ts`.
- `ReadyInput` becomes `{ report: Pick<DoctorReport, 'ok' | 'notChecked' | 'deferred'>; toFix: { count: number; failed: boolean } } | { threw: string }`.
- The doctor a world provides is `() => Promise<{ report; toFix; blocks: string }>`. The live one does `await import('./doctor.ts')` and fills in `toFix: toFixSummary(report)` and `blocks: formatReport(report)` (`doctor.ts:3435`, `:3483`). A throw from it becomes `{ threw }`, worded as `init.ts:654` words it today.
- `InitWorld.doctor` (`init.ts:243`) changes to that type, and `AddWorld` gets the same field.
- Unit tests fake all three fields, so they never load `doctor.ts`.
- Update `setup-card.test.ts`'s ready-line cases to the new input.

The blocks print only when `toFix.count > 0`. `toFix.failed`, or a throw, becomes `init`'s `doctorFailed`, which adds `lingtai doctor --verbose` to `next:` (`init.ts:686`, `:690`). Use `toFix.failed` rather than `report.failed`, for the reason #754's note gives: then the ready line, the blocks and `next:` cannot disagree.

## `init`: the machine and store sections are held back, not deleted

The `Machine` section (`init.ts:326-333`) and the `Store` pass lines (`chooseStore`'s `fact(world, 'Store', …)` calls, and `sqliteChosen` at `init.ts:1009-1011`) are printed **before** anyone knows whether this run is local. The ticket keeps the GitHub paths and the machine-with-projects path as they are (Out of scope: #755, #756). So:

- Collect those sections into a local `held: string[]` instead of `world.log`.
- Flush `held` at the first point the run is known **not** to end on the card:
  - the already-has-projects branch, before its listing (so its order is unchanged);
  - `chosen.project === 'github'`.
- The local branch discards `held` and draws the card.
- A refusal prints its own sentence and does not flush.
- Lines painted `fail` (`chooseStore`'s "does not answer" at `:801`, `:832`, `:811`) are warnings: they print immediately, never held.

One ordering change follows, and it is accepted: an `init` where the project question is **asked** and answered `github` now prints Machine/Store after that branch's App flow rather than before the question. With `--project github` given as a flag nothing else is printed before that point, so its output is the same, only later. #755 removes these sections anyway. Do not try to predict the path early.

The local branch (`init.ts:583-588`) replaces the `Projects` fact with the card. The facts come from values already on hand:

- `runtimes` (`:327`).
- `store`: the `storeChoice(...)` already computed for `storeKept` (`:353`). Hoist it to a const.
- `homeIsNew`: the same `!hadConfig && world.machine.read(path) !== null` as `:356`.
- `userHome`: from `world.env.HOME`, never `os.homedir()`.
- The recipe, the trial, `updated` and the hints come from the outcome (below).

**`Board` (`:660-678`) stops printing but still runs.** `needBoard` decides whether `lingtai board` goes into `next:` (`:691`), so `world.boardAt(port)` is still called and its line is dropped. `init.test.ts:309`/`:320` count that call, and they must keep passing. The board's **refused** line (`:674`) is a failure and still prints.

## What the local outcome carries

The local arm in `first-project.ts:200` gains:

- `card: CardRecipe`: `cardRecipe(finalRecipe, toplevel)`. `finalRecipe` is already resolved at `:696`, so nothing reads the file a second time.
- `updated: boolean`.
- `hints: string[]`.

`updated` comes from the registration, never from a guess. `addLocal` (`onboard.ts:663`) returns `{ line, updated: isRegistered(reduceProject(existing)) }`, the same test `registrationLine` uses (`onboard.ts:639-643`), and its `log` is optional with a no-op default. `FirstProjectWorld.register` (`:147`) and `InitWorld.registerLocal` (`init.ts:234`) return that object. Both live worlds (`init.ts:1149-1153`, `first-project.ts:1046-1050`) stop passing `console.log`, so the `added … — tier …` line is not printed on the local path. Test fakes that return `` `added ${p}` `` (`init.test.ts:142`, `integration/init.test.ts:247`) now return `{ line, updated: false }`. The integration file has to compile, and `pnpm typecheck` covers that.

## The confirm says its own facts

`recipe-flow.ts:415-416` removes `renderSummary` and its print. `summariseRecipe` stays: it is the read-back that refuses an unreadable recipe (`:198`, `:217`), and the confirm reads it.

`priceHints(...)` (`:418`) is returned rather than logged. `askRecipe`'s ok arm becomes `{ ok: true; trial; hints }`.

- The local callers print `hints` through `printSetupEnd`, after the card.
- `add-github.ts:367` logs them right after `askRecipe` returns ok, which is the same place they appear today.

The confirm (`:418-438`) builds its prompt from the two flags it already computes:

- **Both**: `nothing checks a diff before review, and a pass lands on <base> with no one asking — register anyway?`
- **Only the empty build**: `nothing checks a diff before review — register anyway?`
- **Only unattended**: `a pass lands on <base> with no one asking — register anyway?`

`name: 'the summary above'` (`:421`) and the refusal *"stopped at the summary"* (`:433`) both refer to a block that no longer exists. Reword them to `registering with these defaults` and `stopped before registering`. The confirm is still asked only under the guard at `:418`.

`renderSummary` is shared, so the GitHub `add` path also loses `Before registering`. That is intended: its settings dump (`onboard.ts:513-582`) still states those settings until #755.

## Echoes go, warnings stay, detection moves onto the question

These lines are deleted: `source.ts:142`, `:156`, `:219`; `landing.ts:189-193`; `landing.ts:296-304` (the `a pass` line). The same functions serve the GitHub `add`, so it loses them as well, which is fine because its dump covers them.

These lines stay where they are, because each one warns:

- `source.ts:125` (a `--tickets` value kept because of history);
- `landing.ts:182-187`;
- `landing.ts:310`;
- `agents.ts:104`, `:148`;
- `setup-build.ts:213` (not on PATH);
- `setup-build.ts:346`, `:380` (*nothing will check a diff before review*);
- the per-command `failed:` and `not run:` lines of a red trial (`:297-298`).

Detection: `question()` cannot tell a terminal from `--defaults`. `acceptingDefaults` answers `''` exactly as an empty line would (`question.ts`, its doc comment). It also cannot tell a terminal from no terminal before it calls `ask`. So the lines go to the one place that knows:

- Add `Question.why?: readonly string[]`, passed through as `AskShape.why`.
- `liveAsk` prints `why` after its `refusal('', how)` check and before it draws the question (`prompt.ts:76-80`). With no terminal it returns `null` first and prints nothing.
- `acceptingDefaults` ignores `shape`.
- A `given` flag returns before `ask` is ever called (`question.ts`, the `q.given !== null` branch).

That gives all four cases in the Done-when without a mode flag.

`printFound` (`setup-build.ts:198-218`) keeps only the PATH probe:

- The `install:` line becomes the `why` of `askInstall`'s question (`:231`).
- The `build (…)` lines, `skipped` and `notes` become the `why` of `askBuild`'s *run these before review?* (`:353`), but only when `defaultList` came from `detected`, not from `current`. On a re-run the default is the file's own list, and the detection would explain something that is not on offer.
- With nothing detected, `skipped` and `notes` go on the first prompt of the typing loop (`:366`).

The unit test uses a fake `ask` that, like `liveAsk`, logs `shape.why` before answering. That stands in for "asked at a terminal". `ask: async () => null`, `--install`, and `acceptingDefaults` each leave no line behind.

## `add`

`liveAddWorld` (`add.ts:81-86`) adds:

- `log: console.log`;
- `doctor: liveSetupDoctor`;
- `store: () => storeChoice(process.env, …)`, the same reader `init` uses;
- `userHome: process.env.HOME ?? ''`.

`homeIsNew` is `false` for `add`: only `init`'s `chooseStore` writes `config.yml`. The card's heading reads `add`. A doctor that throws puts `✗ not ready — doctor did not finish (…)` on the ready line, and `addFlow` still returns 0. `add` gets no `next:` line; that is #756.

## Tests

- Rewrite `recipe-summary.test.ts`'s `Before registering` cases (`:71`, `:91`, `:111`, `:130`, `:179`) to cover the confirm's three wordings and the hints returned on `askRecipe`'s result.
- Rewrite `init.test.ts:221-232`. A local run's output contains none of `Machine`, `Store`, `GitHub App`, `Projects`, `Before registering`, `Board`, and no line matching `/^added .* tier /`. Its card rows are found by label (strip colour, then `trimStart().startsWith('trial ')`, as #754's tests do). A GitHub or already-registered run still contains `Machine` and `Store`.
- The remaining Done-when tests are unit tests through `InitWorld`/`AddWorld`, with doctor faked as `{ report, toFix, blocks }`. `pnpm typecheck` and `HOME=/nonexistent pnpm test` are the whole check. Nothing here needs the integration half, except that `integration/init.test.ts`'s fake has to typecheck.
