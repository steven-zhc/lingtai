# Design note for #968: `applySetup` and the `lingtai add` refusal

The answer blocks on this ticket mention `apply-setup.ts`, `fresh` and `doc/design/968.md`. Those exist only on the abandoned branches `agent/968*`, not in this worktree. Do not carry over `registeredElsewhere`, the guarded `replace`, the rollback, the recipe lock, `previewSetup` or `fresh`. The ticket's Out of scope rules out the first four, and the last two are not needed in this shape.

## `applySetup`

It goes in `packages/setup/src/apply-setup.ts` and is exported from `index.ts`.

```ts
applySetup(
  target: SetupTarget,                // propose-setup.ts:24; the project name is the rule at propose-setup.ts:153, extracted
  answers: Answers,                   // { changes: readonly RecipeChange[]; said?: Said }
  at: { register: Effect<A, E>; home?: string; files?: RecipeFiles },
): Effect<{ path: string; registered: A }, SetupWriteError | E>
```

**Registration is an argument because importing it would be a cycle.** `@lingtai/conductor` depends on `@lingtai/setup` (`packages/conductor/package.json:62`). The registration the ticket asked to have found is `add()` (`packages/conductor/src/onboard.ts:498`, append at `:571`) for GitHub and `addLocal()` (`onboard.ts:634`, append at `:641`) for a directory. Both append `ProjectConfigured`.

**The body is two steps.**
1. One `setRecipe(project, changes, { home, files, said })` in `Effect.tryPromise`, whose throw becomes `SetupWriteError` with nothing written. `said` can always be passed, because `setRecipe` applies it only when the file is absent (`packages/recipe/src/write.ts:193`).
2. `yield* register`.

There is no other read and nothing around the write. A `register` failure passes through and the file stays.

**`register` runs after the write and reads the file as written.** So each caller hands in what follows its write today.
- **GitHub:** the whole `chooseFirstProject(...)` call at `apps/cli/src/add.ts:190`.
  - `add()` resolves the recipe from disk (`onboard.ts:531`).
  - The App-create path needs the recipe to exist already (`add-github.ts:18-21`, *"a recipe written for a project whose App does not exist yet"*).
  - `ADD_KEPT` at `add.ts:180` stays true.
- **Local:** `first-project.ts:768-802`, meaning the base re-read, `rev-parse`, `resolveLocalRecipe` and `world.register`. The refusal at `:780` stays after the write, so `ADD_KEPT` stays true there too.

Write these as `Effect.gen` with `Effect.tryPromise`. The ratchet counts async arrows (`packages/domain/unit/effect-ratchet.test.ts:99`), and `runEffect` (`first-project.ts:1078`) is the edge it does not count.

**Say what was kept.** `runGithubBranch`'s `!added.ok` refusals carry `said` and not `world.kept` (`first-project.ts:902-904`, `:1013-1015`). So `addFlow` appends `ADD_KEPT` when `asked !== null` and the refusal does not already contain it. A value thrown through `E` gets the same treatment, on both paths.

## `Answers` and the questions

`askRecipe` builds a `draftFiles(at.files ?? diskFiles, path)`: reads fall through until the first write, writes stay in memory, and the change sets are kept in order. It hands that draft to every question. `landing.ts:211` and `:268` keep calling `setRecipe`, and they now land in the draft. Add an optional `RecipeFiles.recorded` that `setRecipe` calls after `resolveSource` and before the no-op return at `write.ts:199`. Write the draft without `async`, using `Promise.resolve`.

`askRecipe` returns `{ ok, trial, hints, answers }`, and `askBeforeGithubAdd` passes `answers` on through `AskedBeforeAdd`.

- The trial reads the recipe through `files` (`packages/setup/src/trial-build.ts:99,117,133`), so `tryBuild` must be built over the draft. `at.tryBuild` may be a function of `files`, or the object the existing tests pass.
- These now claim a write that has not happened, so change them:
  - `add-github.ts:423` becomes `'Nothing was written'`;
  - `seededKept` at `first-project.ts:710`;
  - `sayKept` at `recipe-flow.ts:330`;
  - the refusal at `recipe-flow.ts:432`;
  - the headers at `add-github.ts:16-17`, `recipe-flow.ts:5-13` and `landing.ts:11-12`.
- `ADD_KEPT` keeps its text. It now describes only refusals after the write.

## The refusal

Add one predicate beside `same` (`packages/setup/src/list-repositories.ts:108`): `state.project !== null && (state.owner !== null || state.configHash !== null)`. That is exactly `registered`, `pending` and `unrecorded`.

**GitHub slug.** The check goes in `addFlow` before `askBeforeGithubAdd` (`add.ts:173`), because that function's deps have no `projects`. Read `world.project.projects()`, match on the name in any case, and take the first case that fits:

| Found | Outcome |
|---|---|
| The read failed | Exit 1, nothing written, never read as "not added" |
| Another owner | Exit 1 with `taken(...)` (`pick-repository.ts:206`), before any question, because the recipe file is keyed by name |
| `owner: null`, added | The repair: skip `askBeforeGithubAdd` and go on to `chooseFirstProject` |
| Otherwise added | Exit 1, naming `recipePath` and saying it is edited there |

On the repair path, `add()` records the owner and no recipe is written. `runGithubBranch` already refuses recipe flags by name (`first-project.ts:841-861`). `add.ts:249` draws no card when `asked === null`, so print one line with the recipe path.

**Local.** The check goes in `runLocalBranch` after the name guards (`first-project.ts:554`), before the base question. Existing refusals stay. For an added `found`:
- **`moving`, with ports (#772):** the repair. No `askRecipe`.
  - Reuse the `acceptingDefaults` wrapper at `:567` so the base is not asked. Keep the lands line, in-flight check, confirmation and mirror removal.
  - Refuse any `RECIPE_FLAGS` (`:429`) by name rather than dropping it.
  - `answers.changes` is `landOnBranchChanges(base, null, rawAdmit)` plus `repo.remote`. A `worktree:` at `admit` is where `baseOf` reads (`packages/recipe/src/answers.ts:58-63`), and `askLanding`, which would have corrected it, does not run.
  - Trial is `not-run`.
- **Not `moving`, with ports:** refuse, naming `recipePath(name, world.home)`.
- **No ports (`init --local`, which `explicitChoice` lets reach here, `init.ts:432`):** log that it is already added and return an ok `local` outcome built from the file (`updated: true`), with no write and no `register`.

**A running daemon needs no restart, so no restart line.** `conductorTurn` calls `loadProjects()` every pass (`apps/cli/src/conduct.ts:589`), and the loop's interval sweep is the fallback that reaches it (`packages/daemon/src/work-loop.ts:23`). Say that in the summary. What is read only at start is the daemon's `registered` (`apps/cli/src/daemon.ts:317`), which feeds reconcile (`:360`) and subscriber `filters` (`:331`), so a new project's `subscribers:` wait for a restart. Whether a pass actually took it is settled by the first claim event on that project after its `ProjectConfigured`.

## Checks

- `apps/cli/unit/add.test.ts`: a registered slug exits non-zero, asks nothing, writes nothing and names the path. Also a read that fails, the owner repair, and a rerun with a file and no stream.

## Assumptions

- **`Answers` is the change list, not plain values.** The ticket says `applySetup` builds the changes with the pure helpers. Those helpers need the file being edited (`landingChanges`' `currentProposed`, `kindsChanges`' `rawClaim`, `askAgents`' action index at `agents.ts:367`), and `add-github.test.ts:330` pins a byte-for-byte rerun. So the questions build the changes, with those helpers, and `applySetup` writes them. A page builds the same list. Moving the agent and run-action builders into `answers.ts` belongs to the page's ticket.
- **`fresh` is not added.** The ticket says the second add is refused by whatever registration refuses today, and that is only the expected-version append (`onboard.ts:571`, `:641`, `ConcurrencyError`). If the second add's append comes after the first has finished, it succeeds as *updated*, and its recipe may be the one that stays. Say this window in `apply-setup.ts`'s header and here. It is accepted in the third answer block.
- **Pending on the local path.** `project(name, null)` in `first-project.test.ts:46-50` has no owner and no hash. Nothing writes that state, because `ProjectOnboardingStarted` always sets an owner (`packages/domain/src/project.ts:76-80`) and both registrations carry a hash. The predicate treats it as not added, so the #772 tests, including `:1408` and the base-only `:1429` and `:1450`, stay unchanged, as the second answer block requires. A base-only change on a really registered project is refused, since that answer names only the remote move.
- **"Flag-only tests pass unchanged" covers `addFlow`.** `askBeforeGithubAdd` and `askRecipe` stop writing by design, so tests that read the file afterwards get one local wrapper calling `applySetup` with `Effect.void`. No `expect` changes.
- **The local refusal comes after the directory question.** The name is unknown until then.
- **A rerun over a recipe with no stream** (a crash, or a legacy file) goes through the questions and one edit. Replaying recorded changes in one call differs from sequential calls only for an `extends:` file with no `steps:` (`write.ts:128`). Add one test that the written text equals the draft's.
- **A pause, a shutdown or a page** do not apply: `add` appends and takes no conductor state. A retry is the rerun above.
