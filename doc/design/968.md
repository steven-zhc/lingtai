# Design note for #968: `applySetup` and the `lingtai add` refusal

## Where it goes

**`packages/setup/src/apply-setup.ts`**, exported from `packages/setup/src/index.ts`. It is one `Effect.gen`. Do not write an `async` function or call `Effect.run*` here; `packages/domain/unit/effect-ratchet.test.ts` counts both. The CLI runs it through the `runEffect` it already uses for `proposeSetup` (`add-github.ts:362`, `first-project.ts` local branch).

**`applySetup` cannot import the registration, so registration is a port it is handed.** `@lingtai/conductor` depends on `@lingtai/setup` (`packages/conductor/package.json:62`; `pick-repository.ts` and `ticket-history.ts` import it). `add` and `addLocal` live in `packages/conductor/src/onboard.ts`, so importing them would create a cycle. This is the registration the ticket asked to have found:

- **GitHub:** `add()` at `onboard.ts:498`. It checks reach (`deps.check`/`checkGh`), resolves the recipe (`resolveLocalRecipe`, `:531`), refuses a contradicting `--base` (`:536`), reads `fromSha`, applies the owner guard at the write (`otherOwner`, `:566`), and appends `ProjectConfigured` with `owner` (`:570-586`).
- **Local:** `addLocal()` at `onboard.ts:634`. It appends `ProjectConfigured` with `owner: null` (`:640-654`). It is reached through `FirstProjectWorld.register` (`first-project.ts:141`).

So the registration is an `Effect` handed in, and the signature is:

```ts
applySetup(
  target: ApplyTarget,                 // { home?, files? } — where the recipe lives
  answers: Answers,                    // { project, changes: RecipeChange[], said? }
  register: Effect<A, E>,              // the caller's add() / addLocal(), run after the write
): Effect<{ path, registered: A }, SetupWriteError | E>
```

`applySetup` does three things in order:

1. It reads the file once, through `files.read(recipePath(project, home))`.
2. It calls `setRecipe` once with `answers.changes`, wrapped in `Effect.tryPromise`, passing `said` only when the file was absent. There is no compare-and-swap in `RecipeFiles`: two adds of one new project at once can both write, and the expected-version append in `onboard.ts` refuses the second registration. That window is accepted (no lock, no re-read, no rollback).
3. It calls `register`. If that fails the recipe stays and the error passes through, so a rerun proceeds because *registered* is the test, not *the file exists*.

`SAID` stays in `apps/cli/src/recipe-flow.ts` and travels in `Answers.said`, so the package does not import it.

The resolve-back, the base re-read and the `rev-parse` that `runLocalBranch` does after `askRecipe` happen before it registers, using `previewSetup(target, answers)`, which computes the text `applySetup` will write without writing it.

## What `Answers` is

`Answers` is **already-built changes**, not values to convert: `{ project, changes: RecipeChange[], said? }`.

`askRecipe` asks every question against a draft (`draftFiles(base, path)`) of the recipe that never touches the disk and records each change set `setRecipe` applies (`RecipeFiles.recorded`). The `RecipeChange[]` it returns is that record, in order — so the question helpers (`askAgents`, `askInstallAndBuild`, `askTickets`, `askKinds`, `askLanding`, `askLimits`) keep their own change builders and still write, but into the draft. A refusal anywhere leaves the disk as it was. Moving those builders into `answers.ts` is a separate refactor.

A page that already has the changes calls `applySetup` with them; one that has plain values builds the changes with the `answers.ts` helpers (`ticketsChange`, `kindsChanges`, `landingChanges`, `roundsChange`, …) first.

## Where the refusal goes

**Put the refusal in `lingtai add`, not in `chooseFirstProject`.** `init` reaches `chooseFirstProject` too (`init.ts:645`), and it must go on rather than refuse.

- **GitHub, by slug.** In `addFlow` (`add.ts`), before `askBeforeGithubAdd` (`add.ts:173`), read `world.project.projects()` (`first-project.ts:131`) and look for the name compared case-insensitively.
  - The same owner, or the owner rule `onboardedAs` gives (`list-repositories.ts:110-126`), means the project is already added. Refuse with exit 1, before any question, naming `recipePath(repo)` and saying it is edited there.
  - Another owner is left to the existing `taken` refusal.
  - Put the check here and not inside `askBeforeGithubAdd`. Every `add-github.test.ts` call drives `askBeforeGithubAdd` with deps that have no `projects` seam, so adding one there would change those tests. That breaks *"flag-only tests pass unchanged"*.
- **The `owner: null` repair** (the second answer block). `addFlow` skips `askBeforeGithubAdd` entirely and goes straight to `chooseFirstProject` → `runGithubBranch` → `add()`. That path already re-registers and is pinned by `first-project.test.ts:931` and `:1117`, so it records the owner and writes no recipe. `runGithubBranch` already refuses any recipe flag on a slug (the `recipeFlagNames` refusal), and that is the right answer for a repair that asks nothing. `addFlow` ends on a card only when `asked !== null` (`add.ts:243`), so a repair needs its own short ending: `add()`'s *updated* line and the recipe path.
- **Local.** The name is known only after the directory question, so the check sits in `runLocalBranch` where `found` is computed today (`first-project.ts:~513`).
  - `found.owner !== null` keeps its refusal.
  - When `found` is registered, `migrating` is true and `ports !== null` (that is `add`, not `init`), it is the #772 repair. It keeps the lands line, the in-flight check, the confirmation and the mirror removal. It then writes only the seeds (`repo.base`, `repo.remote`) in one `setRecipe` (through `applySetup` with empty answers) and registers. It does not ask `askRecipe`.
  - When `found` is registered, not migrating and `ports !== null`, refuse naming the recipe path.
  - When `ports === null` (that is `init`), return an ok `local` outcome saying the project is already added, with no write and no `register`. `init.ts` reads the card back from the file anyway (after `:654`).
- **The daemon reads projects on every pass**, so a newly added project needs no restart. `conductorTurn` calls `loadProjects()` at the start of each turn (`apps/cli/src/conduct.ts:589`, *"Read once for the whole pass"*). Say so in the summary, and do not add a restart line.

## Assumptions

- **The #772 fixtures are pending streams, and on the local path pending is not refused.** `first-project.test.ts:46-50` builds `project(name, null)` with `configHash: null`, which `isPending` treats as pending (`packages/domain/src/project.ts:145`). `:1408` expects that re-add to succeed while asking nothing, and the answer says *"#772's tests stay"*. `addLocal` never writes a pending stream: it always carries a `configHash`. So on the local path the rule is `isRegistered` (`project.ts:127`). The `registered | pending | unrecorded` rule stays for the GitHub slug, where the board's wizard does produce `pending`. A reviewer holding the local path to "pending refuses" should read this entry first.
- **An existing file with no registration is edited, not rewritten.** This covers the crash-after-write rerun and a legacy unregistered recipe. `applySetup` makes one `setRecipe` call over the existing file. Each question still shows the file's value as its current answer, because it reads the file through `readRecipeKey`, and an unchanged answer produces no change. That is why `add-github.test.ts:330` (*"leaves an existing recipe byte for byte"*) keeps passing.
- **A failure between write and register** returns the refusal `ADD_KEPT` already words (`recipe-flow.ts:55`): the recipe is kept and nothing is registered. Nothing deletes the file. The case is settled by the absence of a `ProjectConfigured` event on `prj-<project>` for that run, and that absence is the reason the rerun is not refused.
- **A read of `projects()` that fails** refuses with nothing written. It never counts as *not registered*, because a failed read is never treated as "nothing there", which is the rule `liveInFlight` follows (`first-project.ts:455-461`).
- **Two adds at once:** the optimistic append on the version read inside `add`/`addLocal` (`onboard.ts:569`, `:640`) is what refuses the second one. No lock is added.
- **Cost to later changes:** `askRecipe` goes from returning `{ok, trial, hints}` to returning `Answers`, so every caller (`add-github.ts:372` and `first-project.ts`'s local branch) changes in this ticket. No test that only passes flags should need editing. If one does, the change is wrong.
