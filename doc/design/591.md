# #591 design: remove `ContinueConflict` and keep the log readable

Most of this ticket is deletion, and the compiler finds most of it for you. This note covers the three things it won't find:

1. A triage advice the log may already hold.
2. A brief that becomes dead once the resolution is gone.
3. One grep hit that has to stay.

## 1. The trap: `WaitTriaged` may already carry `'ContinueConflict'`

Every stored row goes through validation on its way out of the store. `packages/event-store/src/event-store.ts:253` runs `data = parseStoredPayload(row.type, row.schemaVer, row.data)`, and the comment above it says: *"the store never hands out unvalidated data."*

Two schemas name the tag:

- **`Resolution`** (`packages/domain/src/wait.ts:238-249`), read by `WaitResolved` (`events.ts:308-313`). It is safe to cut. No production caller can write one:
  - The board only ever sends `GrantFixRound` (`apps/board/src/app/actions.ts:183`).
  - The CLI likewise (`apps/cli/src/grant-fix-round.ts:46`).
  - The board drops the card (`standing.tsx:566`).
  - Nothing outside tests passes `resolveWait` the `base`/`conflicts` options that `ContinueConflict` needs (`resolve-wait.ts:146-155`; `git grep "conflicts:"` finds no caller in `apps/`).
- **`TriageAdvice`** (`wait.ts:259-267`), read by `TriageAnswer.resolution` (`:802`), which sits inside `WaitTriaged.result` (`events.ts:1898-1904`, a `strictObject`). It is **not** safe to cut:
  - Since #557, triage's prompt invites this answer (`packages/conductor/src/triage.ts:136-137`: *"`"ContinueConflict"` only with `ConflictingHunks` listing at least one hunk"*).
  - So the conducting machine's log may hold `WaitTriaged{result:{_tag:'TriageAdvised', resolution:'ContinueConflict'}}`.
  - Drop the enum member with nothing else, and that row throws on every read. The ticket's stream stops folding, and `lingtai projection rebuild task_view` fails.
  - We cannot read production `events`. The fact that settles it is whether any `WaitTriaged` has `data.result.resolution = 'ContinueConflict'`. The answer has to hold either way.

The house rule for history is written down twice:

- `events.ts:15`: *"Bump `SCHEMA_VER` for a type and add an upcaster rather than changing a payload in place."*
- `lane-busy` (`events.ts:153-163`): *"a reader that can no longer parse it cannot read this repository's own history."*

**Decision: bump `WaitTriaged` to 2 in `BUMPED` (`events.ts:2017`) and add a `1 →` upcaster in `UPCASTERS` (`packages/domain/src/upcast.ts:57`).** The upcaster rewrites `result.resolution: 'ContinueConflict'` to `'GrantFixRound'` and leaves every other payload alone.

- `GrantFixRound` is what the operator decided a conflict is now (2026-10-24).
- `allowedResolutions` already offers `GrantFixRound` on a pushed `MergeConflict`, because `grantCriterion` always returns a criterion for one (`wait.ts:384-387`).
- So an old advice still recommends a card the page draws, not nothing.
- The `TriageAdvised` superRefine's `ContinueConflict` arm (`wait.ts:815-822`) goes, so a rewritten advice is checked by the remaining rules only.

Do **not** keep `ContinueConflict` in either schema as read-only (the `lane-busy` approach). That keeps the variant in the domain, and the ticket wants it out. The `_triageAdviceCoversResolution` assertion (`wait.ts:270-274`) would also force it back into `Resolution`.

`Resolution` needs no upcaster: nothing ever wrote that variant. Say so in a comment beside the `WaitTriaged` upcaster, so the next reader doesn't add one.

**The one grep hit that stays.** The upcaster has to match the literal string `'ContinueConflict'`. It is the single permitted hit for the Done-when check: `git grep -nE "ContinueConflict|continueConflict" -- packages apps ':!packages/domain/src/upcast.ts' ':!*/unit/*'` should find nothing. Don't hide the string by concatenating it.

Unit tests (in `packages/domain/unit/`, beside the existing upcaster tests):

- A v1 `WaitTriaged` with `resolution: 'ContinueConflict'` passes through `parseStoredPayload('WaitTriaged', 1, …)` and comes out as `GrantFixRound`.
- A v1 with any other advice comes out unchanged.
- A v1 `TriageFailed` comes out unchanged.

A running daemon at the old `SCHEMA_VER` will refuse a v2 row (`upcast.ts:181`). This is the usual *code, restart* order, and `lingtai restart` covers it.

## 2. The confirmed brief is dead code once the resolution goes; delete it too

`ContinueConflict` is the only thing that sets `continuation.conflict`:

- It is set at `packages/conductor/src/conduct.ts:1055-1072` (`confirmed` comes from `resolved?._tag === 'ContinueConflict'`, `:991`).
- It is read at `:3551` (`confirmed: continuation.conflict.hunks`) and `:3671` (the crash guard `fixed.failure && continuation?.conflict`).

Remove all of the following:

- In `conduct.ts`:
  - The stale-base re-wait block (`:992-1022`).
  - The `confirmed` spread (`:1055-1072`).
  - `confirmed === null &&` in the `GrantFixRound` guard (`:1074`), which leaves that guard as `granted && grantCriterion(reason) !== null`.
  - The `conflict` field on the continuation type.
  - The `&& continuation?.conflict` clause at `:3671`. The line becomes `if (!committed)`. Keep the comment above it accurate.
  - The `refSha` option documented at `:375` ("Read only to see that a confirmed conflict's base has not moved"), if nothing else reads it. Check this before deleting.
- In `packages/conductor/src/fix.ts`:
  - The `confirmed?` member of the conflict brief (`:474`).
  - `conflictHalf`'s `confirmed` parameter (`:646`).
  - `confirmedSection` (`:697`).
  - The *left out when confirmed* comment on `STOP_AND_ASK` (`:635-636`). **`STOP_AND_ASK` is then always in the conflict brief.** That is the operator's decision (*a fix round with the conflict brief*), and the brief a granted conflict round already gets.
  - #589's last commit (`54b74aed`) added the omission. Its test of the *with* case goes; its test that the unconfirmed brief carries the line stays.
- In `packages/domain/src/triage.ts:87-105`: `ConfirmedHunk`, once `fix.ts` and `wait.ts` no longer import it.
- In `wait.ts`:
  - `ContinueConflictRefusal`, `conflictRoundsExhausted` and `continueConflictRefusal` (`:421-500`).
  - The `continuable` arm of `allowedResolutions` (`:404-418`).
  - **`MERGE_HUNKS_ONE_BY_ONE` and `ConflictingHunks` stay.** Triage's cause still uses them (`wait.ts:760-771`, `apps/cli/src/triage.ts:620`, `standing.tsx:211`).

`priorGrant` (`conduct.ts:1024-1029`) keeps its `GrantFixRound` half. It is what caps a second human grant on one run, and it doesn't depend on this resolution.
