### 2. Which client the label step uses

The ticket offers two ways to get the App installation: return it from `askBeforeGithubAdd`, or look it up again. **Look it up again.** Returning it from `askBeforeGithubAdd` misses one case.

On a machine where the App is chosen and created during this same `add`, `askBeforeGithubAdd` never gets an installation:
- `reach` is set only inside `if (kind !== 'gh' && hasGitHubApp())` (`apps/cli/src/add-github.ts:361`).
- The comment above it says an `app` answer *"writes nothing until the App exists, and is told on to `chooseFirstProject`"* (`add-github.ts:332`).
- The installation is found later, inside `addEffect`: `const found = yield* deps.check(options.slug, log, options.installation)` (`packages/conductor/src/onboard.ts:443`).

So `AskedBeforeAdd` has no installation to pass on in exactly the template-repository case that started this ticket.

`result.reach` is set on every path that reaches the card (`onboard.ts:422`, `{ ok: true; …; reach: GithubReach }`), so build the client from `result.reach.kind`:
- `gh` → `createGitHubClient({ auth: { kind: 'gh' }, owner, repo })`
- `app` → `githubApp()`, then `installationForRepo(auth, owner, repo)`, then `createGitHubClient({ auth, owner, repo, installation })`. This is the same three steps `readDefaultBranch` already takes (`add-github.ts:91-95`).

That costs one extra request on App machines and needs no new auth or permission.

Don't add the installation to `GithubReach` instead. `Added` also goes to the board through `apps/board/src/app/actions.ts`, and the board's setup page is out of scope.

### 3. Where it lives and how a test stubs it

Write one function, say `ensureLabelsEffect(client, names)`. It returns `{ created: string[]; existed: string[]; missing: { name; why: 'denied' | 'unchecked' }[] }`. Put it next to `githubRow` in `add.ts`, or in a small `add-labels.ts`.

For each name, run `createLabel` and catch every failure per name. A failure for one label is recorded as missing for that label only and never stops the others:
- an error that carries an HTTP `status` (403, 404, anything else) → `denied`, printed as *could not be made*;
- no status (network, or building the client failed) → `unchecked`, printed as *could not be checked*.

If building the client fails, every name is `unchecked`. Nothing in this step ever makes the add exit non-zero.

Use a sequential `Effect.forEach`, not concurrent: there are at most about six names. Write the step with `Effect.gen` and use `lift` for the Promise client the same way `add-github.ts:86-87` does. Add no `async` function and no `Effect.run*`, so the ratchet doesn't move.

Build the names from the recipe `add.ts:288` already resolves, not from the `CardRecipe`:
```
kindsOf(recipe) ++ [HOLD_LABEL] ++ (modeOf(recipe) === 'team' ? [PR_FIX_LABEL] : [])
```
Lower-case each name, drop duplicates (keep the first spelling), and pass the original spelling to `createLabel`. Today the read-back returns only `cardRecipe(…)`, so change it to return the `Recipe` as well. `kindsOf` and `modeOf` come from `packages/recipe/src/settings.ts:360` and `:255`; `HOLD_LABEL` and `PR_FIX_LABEL` from `packages/conductor/src/labels.ts:33` and `:30`.

The tests need a seam. Add an optional `labels?: (owner, repo, reach: GithubReach) => Effect<Pick<GitHubClient, 'createLabel'>, unknown>` to `AddWorld` (`add.ts:51`), filled with the live builder above in `liveAddWorld`. Following the `githubDeps` pattern (`add.ts:54`), leaving it out means the live one. The three `Done when` tests go in `apps/cli/unit/add.test.ts`, which already drives a full GitHub add through `h.world.githubDeps` (`:218`). They add a `labels` stub that records names, answers `'exists'` for `bug`, and fails with `{ status: 403 }` for one name.

### 4. Where it runs and how the card shows it

It runs between a successful read-back (`add.ts:293`, after the `'threw' in read` refusal) and `printSetupEndEffect` (`:296`). If the read-back fails, the add already exits 1 with no card, so no labels are attempted. That's acceptable: the names come from that recipe.

Add an optional `labels?: { created; missing; slug }` to `SetupCardFacts` (`apps/cli/src/setup-card.ts:50`) and render it there:
- one line listing the labels created;
- nothing about the ones that already existed;
- for each missing label, a line with its reason and `gh label create <name> --repo <owner>/<repo>`.

Put it on the card rather than as a `world.log` before it, because the ticket says *"the card lists"*. `init` passes no `labels`, so the field is absent and the card is unchanged there.

`--local` and the owner-repair path never reach this branch (`add.ts:276` requires `asked !== null`), so they need no guard.
