## Where it goes

Add `oxlint-tsgolint` to the root `devDependencies` beside `"oxlint": "1.86.0"` (`package.json:35`), and commit `pnpm-lock.yaml` with it. The lockfile already declares it as oxlint's optional peer (`pnpm-lock.yaml:3681`, `oxlint-tsgolint: '>=7.0.2003'`). It is not installed yet: `node_modules/oxlint-tsgolint` does not exist.
- `.oxlintrc.json`: this is where the decision below goes.
- Each violation site: fix the caller, never the callee's signature (Out of scope).

There is **no root `tsconfig.json`**. There is only `tsconfig.base.json`. You do not need one. Every package has its own `tsconfig.json`, and every one of them includes `"src", "unit", "integration", "test"` (for example `apps/cli/tsconfig.json`, and `packages/event-store/tsconfig.json`, which says *"a test `tsc` never reads is a test that can go stale without saying so"*). tsgolint picks the nearest tsconfig for each file, so the test files the ticket wants covered already belong to a program. Do not add a root tsconfig or use `--tsconfig`. That flag "Override[s] the TypeScript config used for import resolution" (`oxlint --help`), and it would put twenty packages under one config that none of them uses today. A file that belongs to no tsconfig (the root `vitest.config.ts`, `scripts/`, `doc/`) gets no type information. Check what tsgolint does with such files on the first run. If it skips them, that is fine. If it errors on them, add them to `ignorePatterns` and give the reason in a comment.

## The decision that isn't in the ticket: `--type-aware` turns on fifteen rules, not one

`.oxlintrc.json` sets `"categories": { "correctness": "warn" }`. The comment there explains why: it is *"The floor, written out rather than left to the default (0064 §5)"*. `await-thenable` belongs to `correctness`, and so do fourteen other type-aware rules. They are not running today only because `--type-aware` is off. `oxlint --rules --format json`, filtered to `type_aware && category === "correctness"`, lists all fifteen:

```
await-thenable  no-array-delete  no-base-to-string  no-duplicate-type-constituents
no-floating-promises  no-for-in-array  no-implied-eval  no-meaningless-void-operator
no-misused-spread  no-redundant-type-constituents  no-unsafe-unary-minus
no-useless-default-assignment  require-array-sort-compare
restrict-template-expressions  unbound-method
```

If you add only the flag, all fifteen run under `--deny-warnings`. That brings in `unbound-method`, `restrict-template-expressions` and `no-floating-promises`, any of which could produce hundreds of hits in an Effect codebase. All of that is excluded by the ticket's **Out of scope: Other type-aware rules**.

So in `.oxlintrc.json`, add `"typescript/await-thenable": "warn"` explicitly, even though the category already enables it. Then add the other fourteen as `"off"`, each by name, under one comment saying they are switched off because #1136 enabled type-aware linting for `await-thenable` alone, and that turning any of them on is a separate ticket. This follows how the file already treats `unicorn/no-thenable` (*"the rule is off rather than silenced site by site"*). It also keeps 0064 §5's promise that the gate cannot widen without the change showing in a diff. Do not set the category to `"off"` and list the rules you want on instead. That would drop the non-type-aware `correctness` floor #366 set up.

**This list is version-bound.** A later oxlint that adds a type-aware rule to `correctness` will switch it on without any diff. Put a sentence about that in the comment. Keeping the list current is not this ticket's job.

## Fixing the violations

- **In `unit/`, `integration/` and `test/`**, the fix for `await <Effect>` is `await Effect.runPromise(<Effect>)`, as at `apps/cli/integration/ask.test.ts:90`. That costs the ratchet nothing: `effect-ratchet.test.ts:480` only counts files under `${p}/src/`.
- **In `src/`**, `Effect.runPromise` is *not* free. Every run you add under a counted package (`PACKAGES`, `packages/domain/unit/effect-ratchet.test.ts:37-49`) raises the count, and per CLAUDE.md you must never raise `effect-ratchet.baseline.json`. In `src/`, fix the call by `yield*`-ing it from the surrounding `Effect.gen`. If the caller is still a promise function, that is a #790 conversion. Do it, or leave the site in the commit as a finding. Do not add a run to make it pass.
- **An `await` of a plain value** (not an Effect, not a thenable) means removing the `await`. Check that the function is not `async` only because of that `await`. If it is, making it a plain function lowers the ratchet's `async` count. Lower the baseline in the same commit; that is the one way the baseline is allowed to move.
- **Unions that may be a Promise** pass, as the ticket's Edges section says, and that is the rule's own behaviour. Do not add an option for it.

## What stands in for the integration half

Most violations the ticket is about are probably in `integration/`, and that half cannot run inside a pass (803 s). The rule does not need it, though: tsgolint type-checks those files without running them. So `pnpm lint` going green over `integration/` *is* the check for fixes there. What nothing can verify before the merge is whether a fixed integration test then *passes*. Say so in the commit, and name the files you touched under `integration/`.

## Measuring

Run `pnpm lint` before installing anything and again after the change, timed the same way each time (`time pnpm lint`, warm cache, both runs on this machine). Put both numbers in the commit. tsgolint builds one program per tsconfig, and there are twenty, so a large jump is plausible. If it happens, report it as a finding and keep the gate on, as the ticket asks.

The `Done when` demonstration (`await Effect.succeed(1)` in a scratch file fails, and passes once removed) goes in the commit body as pasted output. Put the scratch file inside a package directory such as `packages/domain/src/`, so it gets type information. A scratch file at the root may not be covered by any tsconfig and would prove nothing. Delete it before you commit.
