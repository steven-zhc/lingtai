# #937: design note

## Where it goes

Write `ownChangeStart` twice: once as an exported function in the module, and once as a closure in the pass that calls it. This is the one choice the ticket leaves open.

Every git call in a pass is a closure over `gitHere`: `gitOrDie` and `gitAsked` at `packages/conductor/src/conduct.ts:1752-1753`. So a function written only inside the pass, next to `heldBaseMerge`, can only be tested through `once(...)` and `fakePorts`. That fake answers `git` with `''` for any verb it does not know (`packages/conductor/test/one-attempt.ts:795`), so its `merge-base` always fails. You could never assert the fetch-succeeded case through it. The ticket's *Done when* asks for a faked git port, so:

- **Module level, next to `changedFilesArgs` (`conduct.ts:308`):**
  `export const ownChangeStart = async (port: { git: (args: string[]) => Promise<Either<…, string>>; note: (line: string) => void; base: string; fallback: string }): Promise<string>`.
  The port takes the same `Either` that `gitAsked` returns, so the closure passes it in unchanged.
  - Fetch with `['fetch', 'origin', \`refs/heads/${base}\`]`, the same args `mergeBase` uses at `:3033`.
  - Then run `['merge-base', fetched ? 'FETCH_HEAD' : \`refs/heads/${base}\`, 'HEAD']`.
  - Accept the output only when it trims to exactly one line of 40 hex characters. Anything else returns `fallback`, with a note.
  - It never throws. That matters because three of the four callers run inside a review or a finalizer.
- **In the pass, after `baseShaOr` (`:1784`):**
  `const changeStart = () => ownChangeStart({ git: gitAsked, note: (l) => runLog.note('base', l), base, fallback: baseShaOr('HEAD') })`.
  `base` and `runLog` are already in scope there; `mergeBase` and `baseIsRed` use both. The fallback is still `baseShaOr('HEAD')`, as the ticket's second edge says, so a continuation's fallback is still `diffBaseSha` (#465).

The unit test the ticket asks for calls the exported function directly, with a scripted `git` that answers per verb. Put it in a new file, `packages/conductor/unit/own-change-start.test.ts`. It has no process or filesystem, so it is unit by 0060 §1.

## The four callers

- **`stepDeps.agent.diff` (`:3304`):** `diffBetween(from ?? (await changeStart()))`. Delete `heldBaseMerge` (`:3115-3141`, including its comment).
- **`fix`'s `underReview` (`:4023`):** `diffBetween(await changeStart())`. Rewrite the comment above it (`:4017-4022`) as well. It explains `continuation?.diffBaseSha ?? tree.baseSha`, and that reason now lives in the fallback.
- **`numstat` (`:1793`):** a default parameter cannot await. Make it `numstat(from?: string, to = 'HEAD')` and resolve `from ?? (await changeStart())` in the body.
  - The only default-start caller is `recordDiff` (`:1961`). It passes `to = head`, where `head` can be one commit behind a WIP commit on `HEAD` (#468). The WIP is a non-merge child of `head`, so `merge-base FETCH_HEAD HEAD` gives the same answer as asking about `head`. Do not add a `tip` parameter for this.
  - Leave `:2088` (`numstat(made.parent, made.sha)`) alone. It is out of scope.
- **`watch.changedFiles` (`:3343`):** `changedFilesArgs(await changeStart())`. It still uses three dots. Once `from` is an ancestor of `HEAD`, three dots and two give the same diff.

Leave `publishWhatIsCommitted`'s `cutBase` (`:2130`) and `baseIsRed`'s `baseSha` (`:3068`) alone. Neither measures the change. `cutBase` asks *has this run committed anything*, and the original cut answers that correctly.

## `agent-action.ts`

Replace `:679-683` with `const read = readOf(await deps.diff())`. Keep `const moved = context.landedOnBase` at `:678`: `landedOnBaseBlock` still reads it further down. Rewrite the comment at `:679-681`. It says *"After a base merge the original cut is still the merge-base"*, which is the premise this ticket shows is false once an agent merges the base.

`context.mergedOnto` then has no reader left in `agent-action.ts`. Before deleting it from `ActionContext`, check every other reader with `git grep -n mergedOnto packages/`. `baseIsRed` (`:3068`) is out of scope, so expect the field to stay.

## Tests that go red, and why that is right

In `packages/actions/unit/agent-action.test.ts`, two assertions pin the old start and must be inverted, not deleted:

- **`:2036-2038`**, *"diffs against the merged commit in a later round"*: change `expect(diffFrom).toEqual(['base0002'])` to `[undefined]`. Rename the test to say the first diff is asked with no start even when `mergedOnto` is set. That is the ticket's second *Done when* item.
- **`:2194-2212`**, *"classifies against the diff taken from mergedOnto"*: its fake returns the shifted hunk only when `from === 'base0002'`. It should now return the shifted hunk for `undefined`, and the expected list becomes `[undefined]`.
- **`:2331-2337`**, the fix-delta test with `mergedOnto` and `landedOnBase`: its fake answers `FULL` for anything that is not `reviewedSha`, so it should pass unchanged. It already shows that `deps.diff(context.reviewedSha)` keeps its start. Add `expect(froms).toEqual([undefined, SECOND.reviewedSha])` there, or in a sibling test, so the incremental call is pinned explicitly.

On the conductor side, `fakePorts` answers `merge-base` with `''`, so every pass test falls back to `baseShaOr('HEAD')`, which is today's start. `conduct-continuation-diffs-the-base.test.ts` (#465) stays green for that reason. No unit test asserts a sequence of `git` verbs: `expect(did).toEqual` appears only in `conduct-before-the-claim.test.ts`, before any git call. So the extra `git fetch` and `git merge-base` entries in `did` cost nothing.

## What only the integration half would show

No unit test runs real `git merge-base` over a branch an agent merged into. That is the #892 shape, and only a real repository has it, which makes it integration by 0060 §1 and out of reach in this pass. The unit-level claim that stands in for it: the exported function returns exactly the sha that `merge-base` printed. Anyone checking afterwards can confirm the effect in the log: the next review's `RunPrompted` diff refs (#927) should show `from` equal to `git merge-base main <headSha>`, not the second parent of a `Merge main at …` commit.

## Cost

Each call is one `fetch` over the network. Per attempt that means one review, one fix brief per round, one `changedFiles` per `watch:`, and one `recordDiff`, so a handful of fetches. `recordDiff` runs in a finalizer, so a hanging fetch would delay the finalizer the same way any other `gitHere` call would. Do not add a timeout here: `mergeBase` (`:3033`) has none either, and adding one only on this path would make the two disagree.

No ADR is contradicted. #594's comment on `heldBaseMerge` is in code, not in an ADR.
