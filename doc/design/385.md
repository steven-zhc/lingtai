## Design: `lingtai ticket list` / `lingtai ticket close` (#385)

### Where it goes

- **`apps/cli/src/ticket.ts`**, new. It exports `ticketList(options, log, reading)` and `ticketClose(options, log, reading)`. Each returns an exit code, the way `status` and `closeCommand` do.
- **`apps/cli/src/lingtai.ts`**: add one `case 'ticket':` that dispatches on `positional[0]` (`list` | `close`) and parses the rest with `parseFlags`. Use `'all' in flags` the way `status` does (`lingtai.ts:1282-1285`). Add both commands to `USAGE` (`lingtai.ts:99`). #386 adds `new` and `edit` to this same `case` and this same file, so build the sub-verb switch to take more entries.
- **`packages/conductor`**: `dbTickets` is not exported today. Neither `src/index.ts` nor any `exports` entry in `package.json` names `db-tickets.ts`; the subpaths end at `./wizard-page` (`package.json:30`). Add a `"./db-tickets": "./src/db-tickets.ts"` subpath. Don't add it to the root index: everything that imports `@lingtai/conductor` would then pull in `@lingtai/event-store`'s ticket SQL.

### The seam, so the unit tests can inject the store

Do it the same way `StatusReading` does (`status.ts:53-56`): a third argument whose fields are defaulted.

```ts
export interface TicketReading {
  projects?: () => Promise<ProjectState[]>             // default loadProjects
  recipeFor?: (s: ProjectState) => Promise<ResolvedRecipe>  // default currentRecipe
  ticketsFor?: (project: string) => Promise<Tickets>   // default dbTickets(await processTicketSql(), project)
}
```

`processTicketSql()` is exported from `@lingtai/event-store` (`index.ts:18`, `choose.ts:86`). It opens whichever database the log is in, so the default touches nothing a test controls. The tests pass `ticketsFor` returning `dbTickets(createSqliteTicketSql(openSqliteLog(':memory:')), 'p')`, as `packages/conductor/unit/db-tickets.test.ts:14-21` does. Do not use `memoryTickets()`: it lives in `packages/conductor/test/`, which no `exports` entry reaches from `apps/cli`. `dbTickets` on `:memory:` is unit by 0060 §1, as the file header of that test says.

The new file is `apps/cli/unit/ticket.test.ts`. `apps/cli/unit/` already exists, so the root config picks the file up.

### Picking the project and its source: **not** through `projectFilter`

The ticket says "the way `lingtai status` does". Take that as the rule only, and don't call `projectFilter`. `projectFilter`'s default `clientFor` is `githubClientFor` (`filter.ts:220`), and that throws `'no GitHub App configured…'` (`filter.ts:204`). A `db`-only machine is exactly the machine with no App, so `ticket list` would refuse on the one machine it exists for.

The recipe needs no client. `currentRecipe(state, _client?)` ignores its client (`projects.ts:153-165`) and resolves `~/.lingtai/<project>/recipe.yml`. `apps/board/src/lib/task.ts:1296-1298` already calls it that way for the same question: `currentRecipe(state).then((r) => ticketSourceOf(r.recipe))`.

Order of operations:

1. Get `loadProjects()`.
   - With `--project p`, take that one, or answer `no project named "p"`, worded as `status.ts:65-70` words it.
   - Without `--project`, exactly one project is the default. Zero projects gets `status`'s *no projects registered* line.
   - More than one is refused, and the refusal lists the names. `status` lists them all (`status.ts:64`), but that doesn't fit here: `close <n>` against the wrong project closes a different ticket that has the same number.
2. Get `currentRecipe(state)`. If it throws, print the error and exit 1.
3. **If `ticketSourceOf(resolved.recipe) !== 'db'`, refuse by name before any store is opened.** `ticketSourceOf` is `recipe.source.tickets ?? 'github'` (`settings.ts:309-311`), so a recipe that never mentions tickets is `github`, and that is every project today. The wording should say the tickets are on GitHub at `owner/repo` and that `gh issue list` reads them. This check comes first because `dbTickets` creates its tables on first use (`db-tickets.ts:123-127`, *"Called by `dbTickets`, on first use"*). Falling through would create empty `tickets` tables on a GitHub machine, then print nothing.

### `list`

- **Open tickets:** call `listOpenIssues()`. It is already `ORDER BY number` (`db-tickets.ts:257`).
- **`--all`:** call `listIssuesSince(new Date(0))`. It is the only verb on `Tickets` that returns closed tickets: *"Every ticket, open or closed, created at or after `since` — oldest first"* (`ticket-store.ts:60-61`). It sorts by `created_at, number` (`db-tickets.ts:266`), so re-sort by number. Don't add a `listAll` verb to `Tickets`. That would widen an interface that `GitHubClient`, `memoryTickets` and `dbTickets` all implement, and the contract suite `describeTicketsContract` would need a new case for each of them, all for one CLI flag.
- **Kind:** `kindOf(listing, queueOf(resolved.recipe).kinds)`, where `kindOf` is from `@lingtai/conductor` (`discover.ts:95`) and `queueOf` is from `@lingtai/recipe/settings`, the same pair `status.ts:23,105` uses. Print `—` when it returns `null`. **The bracketed labels are every label except the one `kindOf` matched.** Use `kindLabelOf` (`discover.ts:107`) to get that label's exact name, so a label that differs only in case or whitespace isn't printed twice. Lowercasing a comparison yourself would be a second matching rule, and `discover.ts:102-105` warns against exactly that.
- **Columns:** pad the number and kind columns to their widest value in the listing, and pass titles through a one-line truncation like `status.ts:39-42`'s `oneLine`. A copy is fine; it is not exported.
- **Empty result:** print `no open tickets for <p>`, not nothing. An empty output can't be told apart from a broken one.

### `close`

1. `getIssue(n)` first. It rejects on an unknown number with `no ticket #n for project "p"` (`db-tickets.ts:174-176`). Catch that and print it as the refusal, exit 1. Don't let it surface as a stack trace.
2. If the ticket is already closed, say so and exit 0. `closeIssue` on a closed row succeeds silently (`UPDATE … RETURNING`, `db-tickets.ts:334-341`), so without this check a second close reads as a first one.
3. Otherwise `closeIssue(n)`, and print `closed #n  <title>`.

`closeIssue` takes a `reason` and does not store it (`db-tickets.ts:29-30`). So the command takes no reason argument. A `"<reason>"` that is silently thrown away would be worse than none.

**It appends no event and holds no projector.** The table is not the log. The board's Queued column asks the source when it renders (CLAUDE.md, *"The board's Queued column asks GitHub on render; every other column is the fold"*). So a closed ticket drops out of Queued on the next render with nothing appended.

### Two things the help text has to carry

- **`lingtai close` already exists, and it is a different thing.** `close.ts:1-5` defines `lingtai close <project> --issue <n> "<reason>"`, *"a ticket nobody is going to do, ended on the log"*. It appends a terminal for the work item and runs the `end` point. `ticket close` only changes the row in the table. The `USAGE` lines for the two must say which is which, in one clause each. Say whether `ticket close` stops a work item that is already in flight only if you have read code that settles it. In `events`, that would be a `WorkItem*` terminal on `wi-<project>-<n>` appended after the close. Without that evidence, say only what the ticket says.
- **The daemon notices on its next sweep, not at once.** The sweep interval is `options.sweepMs ?? SWEEP_MS` in **`packages/daemon/src/work-loop.ts:563`**. The ticket says `daemon/src/work-loop.ts`, and that path does not exist. Read `SWEEP_MS`'s value and put it in the help text rather than writing "soon".

**No `delete`**, as the ticket says. If the sub-verb switch has a default, it should answer unknown verbs with the usage line. It should not mention `delete`.

### Tests (`apps/cli/unit/ticket.test.ts`)

Inject all three seams. Projects are plain `ProjectState` literals. `recipeFor` returns a `ResolvedRecipe` whose `recipe.source.tickets` is `'db'` or absent. Pass `log` as an array push. Cover:

- open tickets come out in number order;
- `--all` adds closed tickets, marked `closed`, and still in number order even when they were created out of number order (use `dbTickets`' `now` option);
- the kind column, `—` for a ticket with no kind, and the other labels in brackets;
- `close` closes, and a following `list` no longer shows the ticket;
- closing an unknown number is refused by name;
- a project with no `tickets:` (that is, `github`) is refused by name **and `ticketsFor` is never called**, which pins the "no tables created" point above;
- two projects and no `--project` is refused.

`pnpm test` and `pnpm typecheck` cover all of this. No part of it needs the integration half.
