# #1075: the shape of the change

The ticket's shape holds. This note covers three things the ticket leaves open: how a unit test reaches the port, what the face test needs from `beaconBeatFace`, and when the beat's arguments are read. The ticket's line numbers are out of date, and the right ones are below.

## Line numbers are from an older `main`

DAEMON-5 has landed, so everything in the ticket has moved down by about 90 lines. In this worktree:

- `createStatusTable` is `control.ts:502`.
- `beat` is `:534`.
- `startBeacon` is `:605`, and its chain is at `:621-641`.
- `stop: async` is `:660`.

`grep -c async packages/daemon/src/control.ts` returns 5, and those five are the ones above. `effect-ratchet.baseline.json:10` reads `"packages/daemon": { "async": 20, "run": 0 }`, so the ticket's target of 15 is exactly these five removed.

## The decision: a seam so a test can hand in a port

The fourth *Done when* asks for "a fake port whose `beat` is interrupted". A port that `startBeacon` builds for itself cannot be faked, and a fake `DaemonStore` cannot produce an interruption. `withDaemonStore` lifted with `Effect.promise` turns a rejection into a defect, never an interrupt. So split the function:

```ts
export function startBeaconOn(port: BeaconPort, state: string, options: { every?: number } = {}): Beacon
export function startBeacon(state: string, options: BeaconOptions = {}): Beacon  // = startBeaconOn(makeBeacon(rest), state, { every })
```

- `startBeaconOn` owns `current`, `stopped`, `owed`, `chain` and the timer.
- `makeBeacon` owns `begun`, `startedAt`, `stoppedProjections` and the other beat options.
- Neither function runs anything or is `async`, so the ratchet counts nothing for either.
- `startBeacon`'s signature is unchanged. `apps/cli/src/daemon.ts:269` and both existing unit tests keep calling it as they do today.

The *interrupted link keeps the chain alive* test goes through `startBeaconOn` with `{ beat: () => Effect.interrupt }`. The other new tests should go through `startBeacon` with a fake `DaemonStore`, as `unit/beacon-fresh.test.ts` does. That way they hold the path production uses: `makeBeacon` → `beatEffect` → `withDaemonStore(store)`.

## `beaconBeatFace` must be exported and take the face shape exactly

The checker accepts only one shape for a face (`packages/domain/unit/effect-ratchet.test.ts:9-14`, enforced at `:175-230`). It must be:

- `export function name(…) { return Effect.runPromise(<call>) }` or `export const name = (…) => Effect.runPromise(<call>)`;
- not unexported. An unexported function is refused as *"is not exported"*;
- declared alone, not beside other declarations.

So write `export const beaconBeatFace = (port: BeaconPort, word: string): Promise<void> => Effect.runPromise(port.beat(word))`. Export `BeaconPort` and `makeBeacon` with it.

In `effect-ratchet.faces.json`, the four control.ts entries sort among the existing ones at `:183-235`:

- `beaconBeatFace` and `beat` go first, in that order (`beac` < `beat`).
- `createStatusTable` goes after `controlWatermark`.
- `readStatus` goes between `readControl` and `recordStart`.

## Read `begun` and `stoppedProjections()` when a link runs, not when it is queued

`makeBeacon`'s `beat(word)` should be `Effect.suspend(() => beatEffect(word, { …, fresh: !begun, stoppedProjections: stoppedProjections?.() ?? [] }))`, followed by `Effect.tap(() => { begun = true })` and then the `catchCause` described below.

Today both values are read inside the `.then` (`control.ts:624-626`), so a beat queued behind a failing first beat is still `fresh`. That is what `beacon-fresh.test.ts`'s *"keeps the next beat fresh when the first one failed to land"* holds (`[true, true, false, false]`). Building the Effect eagerly would freeze `fresh` at the moment the word was queued, and it would only pass that test because the face happens to be called inside `.then`.

Set `begun` in an `Effect.tap` that sits before the catch. That way a failed beat, a defect and an interruption all leave `begun` false. The catch is `Effect.catchCause((c) => Cause.hasInterruptsOnly(c) ? Effect.failCause(c as Cause.Cause<never>) : Effect.void)`, the same shape already in this file at `inFlightEffect` (`control.ts:459-462`).

## The chain, as it will be

```ts
const write = (word: string): Promise<void> => {
  owed += 1
  chain = chain.then(() => beaconBeatFace(port, word)).catch(() => {}).finally(() => { owed -= 1 })
  return chain
}
```

- The comment at `:629-635` explains why a beat must never throw: a thrown beat once stranded the conductor lock. It moves to `makeBeacon`'s catch, because that is now where the rule is enforced. The `.catch` here is the backstop for an interruption, so give it a one-line comment saying so.
- `stop` becomes `(last) => { clearInterval(timer); if (!stopped && last !== undefined) { current = last; void write(last) }; stopped = true; return chain }`, with no `async`. `say` is unchanged.

## The ordering test

The third *Done when* asks for a store whose `beat` "resolves out of order". Build it so it would fail if the chain were gone: each call to the fake `beat` takes a decreasing delay, for example 30, 20 and 10 ms, and pushes its state when it **resolves**, not when it is called.

- With the chain, the second write does not start until the first has landed, so the record is the asked order.
- Without the chain, the record would come out reversed.
- Keep `every: 3_600_000`, as the existing tests do, so the timer never fires.

The test that the store going away leaves the next beat `fresh` can be a store whose `beat` throws. To also cover a defect, a non-`Error` throw is enough.
