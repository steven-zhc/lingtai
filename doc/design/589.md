## Shape

**The offer and the brief both come from `grantCriterion`, not from the table.** `tableResolutions` doesn't list `GrantFixRound` for any variant. `allowedResolutions` appends it whenever `grantCriterion(reason) !== null` and the run is pushed: `...(fixable && !unpushed ? (['GrantFixRound'] as const) : [])` (`packages/domain/src/wait.ts:410`). The function's own comment says it is "One function for both the offer (`allowedResolutions`) and the brief (`conduct.ts`), so they cannot drift apart" (`wait.ts:339-342`). So leave the `MergeConflict` row at `wait.ts:301-303` alone, apart from its comment. The change is a `case 'MergeConflict':` in `grantCriterion`'s `ProposedEscalated` switch (`wait.ts:361-383`), which today falls to `default: return null`. The pushed-head rule then comes along with no extra code: `!unpushed` in `allowedResolutions`, plus `savedHead` and the remote-ref check in `resolve-wait.ts:286-314`.

**What it returns:** `{ printed: { step: 'merge', detail: (proposal.paths ?? []).join('\n') }, findings: [] }`. It is never `null`, because a conflict always has a criterion: merge the base, resolve, commit.
- **`step: 'merge'` is what reaches the conflict brief.** `fixRound` sets `from = again.printed?.step` and builds `on: 'conflict'` when `from === 'merge'`, with `paths: said` and `base: continuation?.conflict?.baseSha ?? base` (`packages/conductor/src/conduct.ts:3537-3550`). A plain grant has no `continuation.conflict`, so `base` is the branch name. The agent therefore merges whatever the base is now, which is what the ticket wants.
- **The `detail` format is the one the `ContinueConflict` branch already uses:** paths joined by newlines (`conduct.ts:1066`).
- **An empty `detail` is safe.** `''` is not nullish, so it reaches `conflictHalf`, which already prints *"(git named no files; run git merge … first, then `git status` …)"* (`fix.ts:657`).
- **Keep `checkBrief`'s guard.** Its comment says the merge-step brief must never be produced *except* here: "`fixRound` reads a printed `merge` as a conflict" (`wait.ts:350-352`, pinned by `wait.test.ts:123`). `CheckRefused` at `merge` must still print `proposed`.

## The trap: `ContinueConflict` is also `granted`

`ticket.ts:372-374` sets `grantRef` for `ContinueConflict` as well as for `GrantFixRound`, so `granted` is true for both (`conduct.ts:986`). `conduct.ts:1054-1081` spreads the confirmed-conflict grant first and the `granted && grantCriterion(reason) !== null` grant second. Until now the second spread was dead for a conflict, and the comment at `:1057` says so: *"Not `grantCriterion`: that is `null` for `MergeConflict` on purpose"*. After this change, the second spread would overwrite the confirmed grant's `why` and `printed` on every `ContinueConflict` continuation. Only the `conflict` key would survive.

- Guard the second spread with `confirmed === null`.
- Rewrite the `:1057` comment, which will no longer be true.
- Don't otherwise touch the `ContinueConflict` path: no change to its offer, its validation (`continueConflictRefusal`, `wait.ts:459`), or the `confirmedSection` brief.

## The stop-and-ask sentence

**It goes in `conflictHalf`'s `criterion`** (`fix.ts:660-680`), as one more bullet beside *"Keep both intentions."* `conflictHalf` is shared, so the recipe's automatic `judge: claude-code` `when: conflict` rounds get the sentence too. That is intended: it's the same brief.

**"Ask" has to name the channel that already exists.** That channel is *"change nothing and commit nothing … It is how your objection reaches a person"* (`fix.ts:533-538`).

**It must not contradict the brief's own rule against aborting.** The brief says *"Do not `git merge --abort`"* (`fix.ts:672`). So the sentence says:
- stop without committing the merge;
- say in the final message which two behaviours contradict and why the ticket does not settle it.

A merge left standing uncommitted is already handled by the next round's evidence, through the `MERGE_HEAD` bullet (`fix.ts:646-650`).

**What a no-commit conflict round becomes is not established here.** I could not read the log. The `WaitStarted` that follows such a round, and its `reason._tag`, would settle it. Don't write a test that asserts a particular tag.
