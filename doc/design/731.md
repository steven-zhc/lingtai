# #731: one reader for a project's ticket

## Where it goes

Put it in a new module, `packages/conductor/src/read-ticket.ts`, and export it as `./read-ticket` in `packages/conductor/package.json`, beside `"./filter": "./src/filter.ts"` (line 18). Don't put it in `filter.ts`. That file is what `lingtai status` loads first, and its own comment says it "must not open one merely by importing" (`ticket-store.ts`, on `ticketsFor`). A small module that only imports `ticketsFor`, `githubClientFor`, `currentRecipe` and `ticketSourceOf` keeps that true. It also adds nothing new to the board's server graph: `task.ts:1-3` already imports `filter`, `ownerless` and `projects` from the same package.

## The helper's shape

```ts
readProjectTicket(state: ProjectState, number: number, options?: {
  signal?: AbortSignal
  recipeFor?: RecipeFor          // default currentRecipe
  clientFor?: ClientFor          // default githubClientFor
  tickets?: TicketsForOptions    // the :memory: seam, as projectClient has (filter.ts:276-279)
}): Promise<
  | { ok: true;  from: 'db' | 'github'; ticket: Ticket }
  | { ok: false; from: 'db' | 'github' | null; error: unknown }
>
```

**It takes a `ProjectState`, not a project name.** All three callers already call `loadProject`, and each one words the unregistered case differently:

- the board: `` `${project} is not a registered project` `` (`task.ts:1615`)
- the discussion: the same sentence (`discuss.ts:193`)
- triage: `` `${parsed.project} is not registered` `` (`triage.ts:319`)

Keeping that check in the callers keeps those three sentences exactly as they are.

**It returns a tagged result and does not throw.** The board needs two things from a failure that a message string loses:

- **Was GitHub asked?** That is `askedGitHub`. The renderers use it to decide whether a sentence that names GitHub is true (`task.ts:190-199`).
- **Was it a GitHub 404?** That is `found: false` (`task.ts:1666`, `err instanceof GitHubError && err.status === 404`). `exists()` (`task.ts:1693`) rests a 404 page on it.

So the caught error goes back unchanged, and `from` says who was asked. `from: null` means nobody was asked, because the recipe could not be read.

## The order inside the helper

1. **Resolve the recipe without a client:** `recipeFor(state, undefined)`. `currentRecipe` ignores its second argument (`projects.ts:155`, `_client?: unknown`), and `projectFilter` already does this for an ownerless project (`filter.ts:318`). `projectClient`'s order (client, then recipe, then tickets, at `filter.ts:283-285`) is the defect itself, so do not route through it. If the recipe throws, return `{ ok: false, from: null, error }`.
2. **If `ticketSourceOf(recipe) === 'db'`,** call `ticketsFor(state, recipe, undefined as unknown as Tickets, options.tickets)` and then `getIssue(number, signal)`. This is the same cast `ownerlessClient` makes (`ownerless.ts:59-62`: "Never read: … `ticketsFor`'s only branch that does not pass its third argument straight through"). The answer has `from: 'db'`, whether the read succeeds or fails. `TicketSourceConflict` (`ticket-store.ts:203`) and `noSuchTicket` (`db-tickets.ts:193`, *"no ticket #N for project …"*) both arrive here as `error`. The ticket's *"says so, not an empty body"* is met by that message.
3. **Otherwise,** call `clientFor(state, signal)` and then `getIssue(number, signal)`, with `from: 'github'`.

**Don't call `ownerlessClient`, even though the ticket names it.** Its refusal also requires `repo.remote` (`filter.ts:251-253`), which a read does not need. Its client is only `ticketsFor`'s `db` branch plus git refs. The `db` branch in step 2 already covers every ownerless project that can have tickets. An ownerless project whose recipe does not say `db` falls to step 3, and `githubClientFor` refuses it by name (`filter.ts:224-226`, *"no owner recorded — re-run lingtai add …"*). That message is the right `problem`.

## A behaviour change you must make on purpose

Today, when the board cannot read a recipe, it treats the ticket source as unknown (`task.ts:1626-1628`, `.catch(() => null)`) and **still asks GitHub** (`task.ts:1641-1643`). A recipe that cannot be read might say `db`, so the helper refuses instead (step 1). Only the board changes here. The discussion and triage already fail on a bad recipe, through `projectClient`'s `recipeFor`. The board keeps its own `.catch(() => null)` for `url` and `compareUrl`, which it builds before asking anyone, so those links do not change.

## How each caller maps the result

**Board, `loadTicket` (`task.ts:1595`).** Delete the `tickets === 'db'` early return (`:1633-1641`) and the `githubClientFor` call (`:1642`). Then call the helper and map its answer:

| Answer | `found` | `askedGitHub` | `labels` | `url` | `body` | `problem` |
|---|---|---|---|---|---|---|
| `ok` from `github` | `true` | `true` | `live.labels` | `live.url` | `live.body` | `null` |
| `ok` from `db` | `true` | `false` | `live.labels` | **the `url` already built** | `live.body` | `null` |
| not `ok` | 404 → `false`, otherwise `null` | `from === 'github'` | (unchanged) | (unchanged) | `null` | `error.message` |

In every row, `title` is `live.title` where the read succeeded. On the `db` row, keep the built `url` because `toTicket` gives `url: null` (`db-tickets.ts:215`).

**On a failed `db` read, `found` stays `null`.** The `db` store has no typed "missing" error, only a plain `Error`, and matching on its text is the guess #113 removed. `null` keeps the page and states the reason. `TicketView.found`'s comment (`task.ts:179-187`) already lists *"never being asked at all, because the project's tickets are not on GitHub"* as a `null` case. Update that comment and the one on `askedGitHub` so they say a `db` read happens.

Don't move `loadTicket` or export it. The Done-when allows *"or the shared helper it calls"*, so the `db` unit test runs against the helper, which has the `tickets.sql` seam. `loadTicket` itself reaches `loadProject` on disk.

**Discussion, `gatherEvidence` (`apps/cli/src/discuss.ts:172`).** Don't give it the reader as a whole new parameter. `gatherEvidence` also reads `eventStore` (`:175`, `:180`), `refSha` and `listAt` (`:203-211`), all real, so passing a fake reader alone would still not make it a unit test. Instead, pull lines `187-202` out into an exported function:

```ts
ticketEvidence(state: ProjectState | null, project: string, issue: number, read = readProjectTicket)
  : Promise<{ ticket: DiscussionEvidence['ticket']; ticketProblem: string | null }>
```

`gatherEvidence` calls it with the default reader. That pure function is where the Done-when's two `gatherEvidence` checks are written (a `db` answer, and a rejection). Say in the test's name that it stands in for `gatherEvidence`. Keep `ref: String(live.number)` as it is today.

**Triage (`apps/cli/src/triage.ts:315-324`).** Pull the inline `issue:` closure out into an exported `triageIssue(read = readProjectTicket)`. It returns the `(ticketId, signal) => Promise<{ ref, title, body }>` port, and the object passes `issue: triageIssue()`. On `!ok` it throws `error` unchanged, so the triage brief's *"The ticket could not be read"* (`packages/conductor/src/triage.ts:176`) still gets the same message. Keep its parse and not-registered throws as they are, and pass `signal` through to the helper.

After this, nothing in `apps/board/src/lib/task.ts`, `apps/cli/src/discuss.ts` or `apps/cli/src/triage.ts` calls `githubClientFor` or `projectClient` to read a ticket. Check that with a grep:

- **The board's `task.ts:1906-1911`** (its `ownerlessClient` use, for the arms and approve path) is not a ticket read and stays.
- **`discuss.ts:54`'s import of `projectClient`** goes away if nothing else in the file uses it.

## Tests

All of these run under `HOME=/nonexistent pnpm test`.

- **Helper, `db` with an owner:**
  - A `ProjectState` with `owner: 'someone'`.
  - `recipeFor` answers a recipe whose `source.tickets` is `db`.
  - `tickets: { sql: <:memory: TicketSql>, log: { projectStreams: async () => [] } }`. Find how `ownerless`'s and `projectClient`'s unit tests build that `:memory:` SQL and copy it.
  - `clientFor` is a function that fails the test if it is called.

  Assert `ok`, `from: 'db'`, and the title and body. Add a second case with a number that is not in the table: `!ok`, `from: 'db'`, and a message that contains `no ticket #`.
- **Helper, GitHub:** `clientFor` returns a fake whose `getIssue` answers. Assert `from: 'github'`, and that `getIssue` was called with the number and the signal. A rejection comes back as the same error object, so a `GitHubError` with status 404 survives.
- **Helper, recipe that cannot be read:** `from: null`, and `clientFor` is never called.
- **`ticketEvidence` and `triageIssue`:** each gets a fake reader. One case answers `ok`, the other answers `!ok`.

There is no ADR or doc change: `source.tickets` already decides where the tickets live. The post-merge Next build is the only thing that would catch a server-only import reaching a client graph. The new module adds no import that `task.ts` does not already pull from `@lingtai/conductor`, so there is nothing new for that build to see.
