## Design note — #778, the frame for queued, running and approved pages

### One predicate, read by both files

The page class (`app/task/[id]/page.tsx:815`) and the header branch (`app/standing.tsx:686`) each decide the frame on their own today. Both happen to test `state === 'blocked'`, which is the only reason they agree. This ticket gives them a second condition, so they need one shared source. Export a predicate from `standing.tsx`:

```ts
export const framed = (state: StandingView['state']) =>
  state === 'blocked' || state === 'queued' || state === 'running' || state === 'approved'
```

Use it in both files. If the page and the component disagree, you get the `swaiting-head` markup on a page with no rules for it, or the rules with no markup. Either way you see the giant `.sread .sstate` (`globals.css:978`) inside a one-line header, and no test catches it, because both halves render. Check the exact state literals against `StandingView`'s type rather than this list.

In `page.tsx`, add classes independently rather than choosing one from a ternary:
- `detail--waiting` if blocked
- `detail--framed` if `framed(state) && state !== 'blocked'`
- `detail--resolved` if `afterMove`

A blocked page keeps exactly the class string it has today (the ticket's "Blocked: no change at all").

In `standing.tsx`, `const waiting = standing.state === 'blocked'` (`:624`) stays, and `quiet` (`:676`) keeps reading it. Change these three reads to `isFramed`:
- **`:686`, the header branch.** In the header's `<Rail>` at `:703`, change `live={false}` to `live={standing.state === 'running'}`. `held={budget}` can stay as it is: `rail.tsx:295` prints `held` only when `!live`, and the prop's own doc says *"`Rail` itself only ever prints it in the two non-live readings, so passing it on a running item costs nothing extra there"* (`standing.tsx:496-500`).
- **`:762`, the readout:** `{isFramed ? null : stateReadout}`.
- **`:764`, the second rail:** `!isFramed && …`. The rest of that condition stays, so `landed` or `closed` with an `afterMove` keeps its rail where it is.

### Which CSS rules take `.detail--framed`

"The header and opening rule groups" means these selectors in `globals.css`, and only these. Add `.detail--framed` beside `.detail--waiting` or into the `:is(…)`:

| Group | Lines |
|---|---|
| header grid | `1198` `.swaiting-head` |
| compact rail in the header | `1209-1212` `.swaiting-head .segs/.slab/.sbar/.snow` |
| meta line, title, small state word | `1215-1243` `.swaiting-meta*`, `.swaiting-title*`, `.swaiting-meta .sread*`, `.sage::before` |
| opening | `1206-1208` `.topening`, `.tcontext` margins; `1268-1309` `.topening`, `.tcontext*`, `.tcontext-field*`; the `@media (max-width: 46rem)` block |
| flattened ticket | the `.sticket` half of `1199-1205` (see below) |

Do **not** add it to:
- `1173`, the canvas grid.
- `1178-1197`, the `.detail-body` width and the `.standing`, `.sticket` and `.swhere` surface boxes. Those are the waiting and resolved reading frame, not the header.
- `1213-1217`, the `.swhere` top rule and the `--quiet` rules.
- `.swant`, `.ssubject`, `.stitle` (`1244-1260`). `.swaiting-title .stitle` already sizes the title.
- the `.chatask` rules the ticket names.

**The non-obvious case is framed plus resolved.** An approved or queued ticket with an `afterMove` carries both classes, so `:is(.detail--waiting, .detail--resolved) .sticket` (`1190`, `1197`) gives the header's `.sticket` a surface box with padding, which puts a box around the opening. Waiting avoids this with `1199-1205`, a rule of equal specificity that comes later in the file. So split that rule: `.detail--waiting .sticket, .detail--framed .sticket { padding: 0; border: 0; background: transparent; }` and the `gap: 0.5rem` line. Keep `.detail--waiting .swhere` on its own, so the resolved `.swhere` box below the header stays as it is today. Both selectors have specificity (0,2,0), so the split rule only wins if it stays **after** `1190-1197`.

Colour needs nothing new. `.standing.live .sread .sstate` (`931`) and `.standing.onyou .sread .sstate` (`1000`) don't depend on the page class, so the state word in the meta line keeps its `mark` colour.

### Tests

There is no CSS test, so the unit checks are structural:
- **Page class:** in `unit/task-page.test.tsx`, queued, running and approved contain `detail--framed` and not `detail--waiting`. The `afterMove` cases (`:207`, `:221`, `:244`, `:258`) still contain `detail--resolved`.
- **Header:** in `unit/standing.test.tsx` and `unit/queued.detail.test.tsx`, `.swaiting-head` holds `.sref`, `.sread`, an `<h1>` and `.tcontext`.
- **Rail:** exactly one `.seq` on the page, inside `.swaiting-head` when `progress` is non-null. It is live for running.
- **Where it is:** `[data-rank="where"]` holds no `.sread`.
- **Blocked:** its existing tests don't change.

The visual result (columns and sizes) can only be checked by looking at it. Nothing in `pnpm test` covers it, and that is acceptable because the ticket puts pixel matching out of scope.
