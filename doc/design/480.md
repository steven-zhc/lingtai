# Design: #480, `task_view` folds through the read model

## The shape: one per-event entry point in the read model, and the SQL does not move

`task_view` is an incremental fold. `apply(events, ctx)` gets whatever batch the runner hands it (`task-view.ts:249-252`) and writes each event's effect at that event's `seq`. The four read-model functions work differently: each takes *an item's whole slice* and answers about its history (`read-model.ts:6-14`). None of them can be called on one event and give back what the card writes at that event:

- **Rounds from `routesOf`.** `PassRouted` is appended *after* the `FixRequested` it explains (`read-model.ts:736-743`: "every `FixRequested`/`PassRestarted` a route bought is already on the run **before** the `PassRouted`"). So at `FixRequested`'s seq there is no route yet. The note also needs `of`, the findings count and `action` (`task-view.ts:632-635`). `RoutedPass` (`read-model.ts:717-722`) and `FixRound` (`pass-next.ts:50-54`) carry none of them.
- **Restarts from `releaseCauseOf`.** `Restart` is `{ _tag, restart }` (`pass-next.ts:58`), with no `of`, and `restarts_of` is a column. The function also needs the item event *before* the release (`read-model.ts:1237-1241`). On a one-event slice it answers `ClaimUnconfirmed` (`:1242`).
- **The hold columns from `waitsOf`.** `WaitReason` drops facts that the columns print:
  - `toRunRef` keeps only `runId` and `unpushed` (`read-model.ts:839-841`), but `legacy-columns.ts`'s `repairDone` prints `run.repairOf` into `diagnosis.done`.
  - Going back through `holdOf` rebuilds a `Routed.why` from `branch`/`base` (`adapters.ts:361`, `escalatedHold`). The stored `why` was composed by `conduct.ts` and is what `note` holds (`legacy-columns.ts`, `case 'Routed'`: "the one variant whose composed line is on the hold itself").

The ticket's Watch out and Done when both demand byte-identical rows, column for column. **So byte-identity wins over the literal "from `routesOf`/`releaseCauseOf`/`waitsOf`".** The read model gets one more export that answers per event. It is the only place that names an old type or `Hold`, so #464 changes it and leaves `task-view.ts` alone, which is what 0120 *Two phases* asks: "at the switch only the read model and the builders change". No ADR is contradicted.

### `cardFactOf(event: Envelope): CardFact | null`, in `packages/domain/src/read-model.ts`

It answers `null` for any type it does not own. It owns exactly the types `task_view` folds that 0120's appendix retires or reshapes:

- the nine step and approval types (`task-view.ts:670-711`)
- `FixRequested`, `FixApplied`, `FixDeclined` (`:627-668`)
- `PassRestarted` (`:408-412`)
- `WorkItemBlocked`, `WorkItemUnblocked` (`:321-380`)
- `RepairRequested` (`:393-395`)
- `RunFailed` (`:600-609`; the appendix turns `RunFailed{no-commits}` into `StepEnded`, so route all of `RunFailed` here to keep one place)

Suggested variants. The names are yours, but every field below is something a column needs:

| Variant | Carries | Replaces |
|---|---|---|
| `Verdict` | `runId` (**the event's `streamId`**, as `setStep` is called today, `:685`), `key: \`${step}:${action}\``, `verdict`, and for the three approval types what happens to `awaiting_sha`/`note` | `:670-711`. `VERDICT` (`:764-786`) moves into the read model with its comment. |
| `RoundOpened` | `runId` (streamId), `round`, `of`, `findings: number`, `action` | `:627-638`. Keep the `of > 0` wording rule in `task-view.ts`, because it is card wording. |
| `RoundSpent` | streamId for the lookup, **`data.runId`** for the key, `round`, `costUsd` | `:640-659`. The two ids differ on purpose: `viaRunQuery` takes `event.streamId`, and the key is `${d.runId}#fix${d.round}`. |
| `RoundsDeclined` | `round`, `why` | `:661-668` |
| `Restarted` | a `Restart` plus `of` | `:408-412` |
| `WaitStarted` | `reason: WaitReason` from the same `reasonFromHold` `waitsOf` uses (`read-model.ts:977`), and `card: { question, needs, diagnosis }` from `legacyColumns(hold)` | `:321-350` |
| `WaitResolved` | `by`, `note`, `withdrawn` | `:352-380`. `Resolution` drops `by`, which the `answer` column writes. |
| `RunEnded` | `kind`, `detail` | `:600-609` |
| `RepairBought` | nothing | `:393-395`. Retired by #143. Say in its comment that #464's reset deletes it. |

How `WaitStarted` works:

- **`asked` is read off `reason._tag === 'OwnQuestion'`.** That is the one hold column that really comes from `waitsOf`'s vocabulary. It equals today's `cols.runId === null`, because only `Question` has a null `runId` (`legacy-columns.ts:76-82`; every other branch returns `hold.run.runId`).
- **`reasonFromHold` is safe on a one-element slice.** Its lookups (`refusingStepFailed`, `becauseFor`, `approvalActionFor`) find nothing and fall back, and `asked` uses only `_tag`.

`task-view.ts` keeps its `switch` for the types the appendix leaves alone:

- `WorkItemDiscovered`, `WorkItemClaimed`, `WorkItemReleased`, `WorkItemClosed`, `WorkItemLanded`, `DispatchRefused`
- `RunStarted`, `RunAwaitingInput`, `RunProducedDiff`, `RunProposedCompletion`
- `RunFinished`: cost is #455's.
- `IntegrationRefused`: it reads `reason`/`detail`, which survive.
- `IntegrationSucceeded`

Its `default:` calls `cardFactOf(event)` and switches on `fact._tag`. The import of `legacyColumns` and `PayloadOf<'WorkItemBlocked'>` leaves the file.

**Do not change a single SQL statement or write helper** (`upsert`, `set`, `viaRun`, `viaRunQuery`, `setStep`, `:818-965`). Each fact branch makes the same helper call with the same arguments, in the same order, that its old `case` made. Keep the order inside one event too: `ApprovalRequested` calls `setStep` before `viaRun`, and `WorkItemBlocked` calls `upsert` before `set`. That is what makes byte-identity cheap. The only thing that changes is where each value comes from.

## The pin test: `packages/projector/unit/task-view-rebuild.test.ts`, committed before any `src` change

**It runs on `createSqliteProjectionStore(openSqliteProjections(':memory:'))` (`sqlite.ts:366,378`), through `store.transact`.**

- That is the real fold path, and `:memory:` skips WAL (`sqlite.ts:370`).
- It touches no file, starts no process and reads no `$HOME`, so it is unit under 0060 §1 and `HOME=/nonexistent pnpm test` stays green.
- Every existing `task_view` test is integration and Postgres-only: `integration/task-view.test.ts` imports `pg` and `postgresUnderTest`. **Nothing in `pnpm test` folds `task_view` today**, so this file is the only check inside the pass.

What it pins:

- `select * from task_view order by task_id` and `select * from task_view_run order by run_id`, compared whole as row objects. Use an inline snapshot or a literal.
- **Also the rows after each prefix of the stream that ends on an event this change reroutes**, not only the final rows. The live board is the fold at every prefix. `FixRequested`'s note is overwritten by the end of every complete pass, so a final-rows-only pin would let "fixing round 2 of 3" vanish from a running card unnoticed. The same applies to `ApprovalRequested`'s `awaiting_sha` before its block, and to `PassRestarted` before its release.
- **Generate the expected rows from today's code in the pinning commit, and never regenerate them after the `src` change.** `vitest -u` after the change turns the test into a tautology.

How the stream is built:

- **Build the stream once, at module scope.** `makeStream` takes its seq from a module-global counter (`packages/domain/test/support.ts:11,23`), so a stream built inside an `it` gets different `updated_seq`s depending on which tests ran first.
- `at` is a fixed default (`support.ts:31`), which is fine: `updated_seq` already says which event wrote last.

What the stream must cover:

- **Every `Hold` tag** (`hold.ts:114-293`): `Question`, `Asked`, `Human`, `Declined`, `Routed` once for each of `red`/`verify-failed`/`conflict`/`findings`, `CheckRed`, `MergeRefused`, `Ceiling`, `DidNotFinish`, `SetupRefused`.
- **The rest of the rerouted events:**
  - an `ApprovalRequested` → `ApprovalGranted` pair, and an `ApprovalRevoked`
  - `FixRequested` with `of: 0` and with `of > 0` (`task-view.ts:632`)
  - `FixApplied` with `costUsd: null` and without (`:642`)
  - `FixDeclined`
  - `PassRestarted` then a release
  - `RepairRequested` → claim → `RunFinished`, which exercises the repair branch at `:588`
  - an unblock that is withdrawn and one that is not (`:360`)
  - a `DispatchRefused` landing on a row that is already waiting (`:481`)
- **#461's endings.** Mirror the item-stream type sequences that `packages/conductor/unit/what-a-pass-writes-today.test.ts` asserts row by row (rows 1, 2, 4, 5, 6, 7, 9, 10a, 10b, 11, 12, 13, 13b, 14a–d, 15, 15b, 15c, 16), one work item each, and comment each with its row number.
  - Do not fold that file's real events instead. It is 1,858 lines in another package, and #474 was split out because a diff that wide does not converge.

## Builders

- **Export them.** Add `"./test/events": "./test/events.ts"` to `packages/domain/package.json`'s `exports`. That is the pattern `@lingtai/event-store/test/postgres` already uses, and today nothing outside domain imports them (only `domain/unit/read-model.test.ts:27`, by a relative path).
- **Old event types are built only through the builders** (`aRun().aStepEnded`, `aWait`, `aResolution`, `aWithdrawal`, `aRoute`, `aRelease`, `aClaim`, `aLanding`, `anIntegrationRefusal`).
- **Some old events have no builder yet:** `FixDeclined`, `ApprovalRevoked`, `RepairRequested`, and `FixApplied` with a cost if `aStepEnded` does not write one. Add each to `test/events.ts` with a comment saying it has no writer today.
- **The types 0120 leaves unchanged may use `makeStream` directly.** It is the builders' own base and validates every payload (`support.ts:6-7`). At #464 those events do not change, so neither do the tests that make them.

## Moving the existing tests

- **`integration/task-view.test.ts` and `task_view`'s half of `test/contract.ts`** (`:340-351` and the `made(f, taskViewProjection, …)` cases from `:442` on) swap their hand-written payloads of old types for builder output. Both append through a real store, so map each envelope to `{ type, actor, data }` and append it under the stream ids those files already generate.
- **Leave `backlogProjection` and every backlog case in `contract.ts` alone.** They are #481's, and `backlog.ts` is not touched.
- **What checks this conversion:** both files run only in `pnpm test:integration`, and `task-view.test.ts` skips without `LINGTAI_TEST_DATABASE_URL`. Inside the pass the only thing that checks them is `pnpm typecheck`. The unit pin test stands in for them; do not run the integration half.

If the pin goes red in step 3, the fold changed. Fix the fold, never the snapshot.
