# Design: #1111 — the setup ports become Effects

The ticket's shape is right. This note covers what it misses: the ports' failure channel, two callers of the repo faces that the ticket does not list, `runPort`'s other callers, and the `why` lines that go stale.

## 1. A port may fail, and no caller converts a failure into `false`

Give every port a failure channel of `unknown`, not `never`. Two places need it:

- **`EMPTY_SETUP_READER.has` must keep failing on purpose.** `detect-setup.ts:31-38` says: *"`has` rejects rather than resolving `false` … resolving `false` the way a real check's negative does would print a lockfile or a `package.json` as missing (#431 fix round, finding 2)"*. So it becomes `Effect.fail(new Error('nothing can be read here'))`, and its comment says "fails" where it now says "rejects". `read` stays `Effect.succeed(null)`.
- **`TrialDeps.remove` must be able to fail**, even though `removeWorktreeEffect` never does (`worktree.ts`, `Effect.ignore`). `trial-build.test.ts:195-204` fakes a `remove` that throws `EACCES` and asserts the `cleanup` row's evidence contains `EACCES`. That fake becomes `Effect.fail(new Error('EACCES'))`, and the type has to allow it.

## 2. Turn the whole cause into a value, in three places

`Effect.tryPromise` used to catch a throw. An Effect port can also die (a defect), and none of today's handlers catches a defect: `Effect.catch` does not, and `Effect.result` does not either.

Use one rule everywhere: `Effect.catchCause` with `Cause.squash(cause)` turns the cause into the error `reasonOf`/`messageOf` already read. That keeps today's text exactly (`Effect.runPromise` rejected with the squashed error).

- **`propose-setup.ts` `settle`/`attempt`** (`:100-116`) take `Effect<T, unknown>`. They map success as today and use `catchCause` for the other branch. The call sites change from `settle(readers.runtimes)` to `settle(readers.runtimes())` (`:174`, `:205`, `:206`, and `attempt` at `:165`).
- **`detect-setup.ts` `readPath`/`hasOrUnknown`** (`:111-123`) are also `tryPromise` over the reader. They become `reader.read(path).pipe(Effect.catchCause(c => Effect.fail(failed(Cause.squash(c)))))`. Without this, a defect in `read` escapes `detectSetupEffect`, and `proposeSetup`'s `Effect.result` at `:155` does not catch it. The ticket's required unit test (a `read` that dies) fails exactly there, so put the test in `propose-setup.test.ts` and let it prove this path.
- **`trial-build.ts`'s `provision`** (`:196-213`): `Effect.uninterruptible(deps.provision({...}).pipe(Effect.catchCause(...)))`, then the same `match`. Keep the comment *"Uninterruptible: `remove` must not start while git is still writing"*.

**Trap: `remove`'s release reads `err.cause`.** The release at `:268-277` calls `messageOf(err.cause)`, because `tryPromise` wraps the rejection in an `UnknownException`. A plain Effect's error is not wrapped, so the line becomes `messageOf(squashed)`. If `.cause` stays, the evidence reads `undefined`, and `trial-build.test.ts:203` (`toContain('EACCES')`) goes red.

## 3. `watched` re-raises the cause it saw

`watched` (`propose-setup.ts:118-149`) records the first failure and rethrows it. `detectSetup` must keep seeing the failure: `hasOrUnknown` turns it into `'unknown'`, not into absent.

Rewrite it as:
- `reader.has(path).pipe(Effect.tap(there => …present.add), Effect.tapCause(c => Effect.sync(() => { failed ??= reasonOf(Cause.squash(c)) })))`.
- `read` gets the same treatment, keeping its `null`-after-`has` rule.

Use `tapCause`, not `tapError`, so a defect is recorded as well.

## 4. Fillers outside the four arrows

The CLI's own world ports stay promises. `world.history`, `world.runtimes` and `FirstProjectWorld`'s members are out of scope ("beyond the four reader arrows and the lines that build readers"). So the lines that build a `ProposalReaders` lift them, and lifting does not count against the ratchet:

- `first-project.ts:841-845` and `:877-890`: `history: (p) => Effect.tryPromise(() => world.history(p))`, `defaultBranch: () => Effect.succeed(base)`, `runtimes: () => Effect.succeed(runtimes)`. `origin` is the same pattern.
- `add-github.ts:383-387`: the same pattern.

`add-from-page.ts:156-175` uses the Effects directly:
- `defaultBranch: () => ref`
- `runtimes: () => askRuntimesEffect()` (`runtimes.ts:35`)
- `history: liveHistoryEffect` (`ticket-history.ts:22`)
- `origin` without `runPort`
- `Effect.succeed(null)` / `Effect.succeed(LINGTAI_BASE)`

`diskReader` and `githubReader` (`:95-145`) lose their `runPort` wrappers. Then delete the `runPort` import (`:53`) and correct the header comment at `:19` (*"filled with `runPort` … until they are Effect ports"*).

## 5. Faces

- **`runPort` stays.** It still has callers in `create-app.ts`, `db-tickets.ts`, `telemetry.ts`, `git-refs.ts` and `ownerless.ts`. Only `add-from-page.ts` drops it. If its `why` names add-from-page, rewrite it.
- **`provisionWorktree`/`removeWorktree` are deleted** (`worktree.ts:256-258`, `:286-288`, and the exports at `repo/src/index.ts:29,31`). Two callers the ticket does not list must move to `Effect.runPromise(provisionWorktreeEffect(...))`, or tests must be rewritten as Effects:
  - `packages/repo/unit/provision-permit.test.ts:37,68,73` (unit, so `pnpm test` checks it). Keep the permit's ordering assertions unchanged.
  - `packages/repo/integration/worktree.test.ts` (`:18` and every call). Nothing runs this file inside the pass, but `pnpm typecheck` covers it, and that is the only check available before the merge.
- **`rung-1.ts` is already stale.** It imports `prepareWorktree`, `provisionWorktree`, `removeWorktree`, `resolveAgentEnv` and `runnableEnv` from `@lingtai/conductor` (`rung-1.ts:2`), but `packages/conductor/src/index.ts` exports none of them. There is no re-export to delete, and `tsc` never sees the script: `apps/cli/tsconfig.json` includes only `src`, `unit`, `integration` and `test`. Move only the two worktree calls to `@lingtai/repo`'s Effects, run with `Effect.runPromise` at `:115` and `:153` (`.catch` becomes `Effect.catch` or a try). Leave the rest of the script alone. Nothing checks it, so say so in the commit.
- **Rewrite these `why` lines; delete no entry:**
  - `liveHistory` (`faces.json:410-415`): it names *"`packages/setup`'s promise `history` port"* and `add-from-page.ts`, both now false. Its remaining callers are apps/cli's world `history` (`first-project.ts:1345`, `init.ts:1304`, `add-github.ts:171`).
  - `askRuntimes`: drop `add-from-page.ts` from its `why`.
  - `runCommand`: rewrite only if `TrialDeps.run` moves. Leave `run` as `runCommand` unless its face is already gone.

## Edges the ticket leaves open

- **Interruption:** `catchCause` would also catch an interrupt. The trial's Ctrl+C uses `at.interrupt` (an `AbortSignal`), not fiber interruption (`trial-build.ts:226-230`), and `provision` is uninterruptible. So for the trial this changes nothing. For a reader, an interrupted `init` exits anyway. Do not add a filter for interrupts.
- **Ratchet:** after the four arrows go, `apps/cli` should read 47. If the count comes out higher, a new `async` slipped in at a lifting line. Fix the line; never raise the baseline.
