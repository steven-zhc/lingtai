# Design: #619 — `lingtai doctor` on `@effect/cli`, grouped by area, with `--json`

## Scope: one command

As in #618, the plural in the ticket is template wording. This change migrates `doctor` and no other command, so `MIGRATED_COMMANDS` becomes `['version', 'status', 'doctor']` (`migrated.ts:9`). Nothing to do with `--help` routing: `routeOf` already sends `--help` for every migrated command except `version` to the definitions (`migrated.ts:21`). Add these rows to `migrated.test.ts`:
- `['doctor'] → effect`
- `['doctor', '--json'] → effect`
- `['doctor', '--help'] → help`

## The restart already reads the structured result. Do not change it.

The ticket's last trap is already handled. The new code must not undo it, for example by having `restart` run `doctor --json`.
- `restart` calls `doctorReport()` directly (`restart.ts:688`). It gates on `gatingFailures(report.results)` (`restart.ts:741`, `:1433`), which reads `status` and `restartAnswers` and never reads text. Its comment says: *"The same report the command prints, from the same function, so the two cannot disagree"* (`restart.ts:733-735`).
- `upgrade`'s drain does the same thing (`world.ts:293-297`).
- The only other code that uses doctor's text is `init`. It prints the text and parses nothing (`init.ts:1075-1078`, `init.ts:629-635`).

So keep `restart` and `upgrade` as they are. The PR should say they already read `DoctorReport.results`, citing those lines. `formatFailures` (`restart.ts:1444`) is restart's own output and stays outside this ticket.

## Split the module into read, tally, render and JSON

`lingtai.ts:112-133` builds the report, appends the release row, counts it by hand and prints. Replace it with these parts:

- **`tally(results): Omit<DoctorReport, 'results'>`** in `doctor.ts`. Take it from `runDoctor`'s return (`doctor.ts:2668-2676`) and have `runDoctor` use it.
  - The handler appends the release row and calls `tally` again, so nothing is incremented by hand.
  - The result is the same as `lingtai.ts:118-127` today. A `skip` without `deferred` counts as `notChecked`, which matches #214's comment there.
- **The release check stays outside `runDoctor`.** Its reason is `lingtai.ts:114-116`: *"the one outbound request this tool makes is asked by `doctor` and `upgrade` (#184), and a restart is neither"*. The `doctor` handler in `cli.ts` calls `releaseCheck` from `install.ts`, exactly as `lingtai.ts:117` does now.
- **`renderDoctor(report, { columns }): string[]`** in `doctor.ts`. It uses only `output.ts`'s `heading`, `section` and `symbol`. **`formatReport(report)` stays exported as `renderDoctor(report, {}).join('\n')`**. `init.ts:1076` keeps calling it, and so do the integration asserts listed below.
- **`doctorJson(report): Record<string, unknown>`**, which `printJson('doctor', …)` wraps.

Delete `doctor()` and `case 'doctor'` from `lingtai.ts` (lines `112-133`, `1211-1212`), and remove `doctorReport, formatReport` from the import at `lingtai.ts:71`. `daemonLiveness` is still used there, so it stays.

## Areas: assigned by the name's prefix, through one table

A check has no area field. Its `name` already carries one, as the text before the first `": "`: `node:`, `postgres:`, `schema:`, `log:`, `daemon:`, `recipe:`, `runtime:` and so on. The names are listed at `doctor.ts:262…2431` as `const name = …`, plus `install.ts:732` (`release: newest`).

Do **not** add an `area` to the many `CheckResult` literals. Add one `AREA_OF` table in `doctor.ts` that maps each prefix to a section:

| section | prefixes |
|---|---|
| Machine | `node`, `packages load under Node` (no colon, so match the whole name), `release` |
| Store and log | `store`, `environment`, `postgres`, `schema`, `log`, `projections` |
| Daemon | `daemon`, `conductor`, `worktrees`, `subscribers` |
| Projects | `recipe`, `env`, `base`, `triage`, `steps` |
| GitHub | `github` |
| Runtimes | `runtime` |
| Not implemented here | every row with `deferred: true`, whatever its prefix (`DEFERRED`, `doctor.ts:868`) |

- An unknown prefix goes to an `Other` section. It must never be dropped.
- A unit test fails if `Other` is used. Run it over the rows the existing unit fixtures produce: `apps/cli/unit/doctor.test.ts:95` and onward call `runDoctor` with every seam stubbed. Also run it over `postgresOnlyRows()` (`doctor.ts:314`), so the Postgres-only names are covered too, since no unit test reaches them otherwise.
- Dynamic names such as `` `recipe: ${f.project}` `` (`doctor.ts:1725`) and `` `steps: ${project} ${agent} signed in` `` (`:2227`) work because only the prefix is read.

## Layout: failures first

```
doctor

Store and log
  ✗     environment
        LINGTAI_DATABASE_URL … — they must be one database
  ✓     store: the machine's written choice
        sqlite ← ~/.lingtai/config.yml · …
Daemon
  note  daemon: currency
        running 8f3a1c2 — 3 commit(s) behind origin/main … restart the daemon to take them
  ✓     daemon: liveness
        up, last beat 2s ago
…
Not implemented here
  skip  hook: fail closed
        every run proves it immediately before dispatching …

1 check(s) FAILED — 23 ok, 1 to note, 4 not checked here, 3 not implemented yet
```

- **Order:** sections that contain a failure come first, then sections that contain a note, then the rest, keeping the table's order within each tier. Inside a section the order is `fail`, `warn`, `ok`, `skip`, and `runDoctor`'s order within each status. *Not implemented here* is always last.
- **Each check is two lines.** The first is the marker and the name. The second is `detail`, indented under the name.
  - The ticket's "remedy on the next line" means this `detail` line. `CheckResult.detail` is documented as *"What it found — never just a tick"* (`doctor.ts:146`), and the checks already put their remedy in it.
  - **Do not add a `remedy` field.** Splitting each detail would touch every check in a 2,774-line file, and a mechanical split would lose words. Losing words is the one thing this ticket forbids.
- **Markers.** Pad them to one 4-column slot with `output.ts`'s `width()`.

  | status | marker | colour |
  |---|---|---|
  | `ok` | `✓` | `symbol.pass()` |
  | `fail` | `✗` | `symbol.fail()` |
  | `warn` | the word `note` | **none** |
  | `skip` | the word `skip` | `paint.muted` |

- **`note` is no longer amber, on purpose.** `TAG` (`doctor.ts:2733-2741`) draws `note` in `paint.signal` and argues that *"a check that passed but wants a person to look at it is a person being waited on."* 0121 §2 overrides that: `●`/`signal` means *"waiting on you, and nothing else"*, and *"a command never draws amber for a thing that is not waiting on a person"*. `CheckStatus`'s own docstring says a warn means *"nothing is wrong and you should know anyway"* (`doctor.ts:126`), which is not a wait. Delete `TAG` along with its comment. Sorting notes above the `ok` rows is what makes them visible now.
- **Keep the summary line word for word** (`doctor.ts:2758-2773`): `N ok, N to note, N not checked here, N not implemented yet, 0 failed`, and the `N check(s) FAILED — …` form. #214's comment explains why both halves are always printed. Keeping the words is also what keeps the asserts in `apps/cli/integration/doctor.test.ts:417`, `:423-424` and `:802` true. Those files cannot run in the pass, so check them by reading. **There is no `next:` line.** Doctor has no single next command, and the remedies are on the check lines (0121 §1: *"when something can be done next"*).
- **`restartAnswers` is not shown in the text.** The old text did not show it either. It is carried in the JSON.

## `--json`

```
{ version: 1, command: "doctor",
  ok, failed, warned, skipped, deferred, notChecked,
  checks: [ { area, name, status, detail, deferred, restartAnswers } ] }
```

- `checks` is in `runDoctor`'s order, not the rendered order. `area` lets a script group the checks itself.
- `status` uses the `CheckStatus` values (`ok | warn | fail | skip`), not the markers. This is the same rule #618 used for the projection's `state` values.
- `deferred` and `restartAnswers` are always present as booleans that default to `false`, so the shape does not depend on the row. This is the fact `gatingFailures` reads, so a script can tell *red* from *red, but a restart fixes it*.
- **Exit code:** a red doctor prints this report document and exits `1`. The error document is only for a report that could not be produced.
  - `commands.ts:486` says *"Exits non-zero on any failure"*, and `--json` must not weaken that.
  - 0121 §5's error document is for a command that failed. A doctor that found failures has done its job.
  - So a script tests `.error` first, then `.failed`. Say this in the definition's usage.

## The handler in `cli.ts`

- Copy the shape of `status`'s handler (`cli.ts:28-55`):
  - `applyNoColor()`;
  - a **dynamic** `import('./doctor.ts')` and `import('./install.ts')` inside the handler, never at the top. The reason is at `cli.ts:36-37`: `version` is what `upgrade` spawns.
  - `handlerCode = report.failed === 0 ? 0 : 1`.
- On a thrown error:
  - under `--json`: `printJsonError('doctor', 'unavailable', message)`;
  - otherwise: the message, then `(LINGTAI_DEBUG=1 for the stack)`.
- `status` and `doctor` now share that catch block, so move it into one helper in `cli.ts` instead of copying it.
- `runCli` already lets a handler's code through without turning it into `usage` (`cli.ts:94-98`, `handlerCode !== 0`).
- In `commands.ts:482-488`:
  - usage becomes `lingtai doctor [--json] [--no-color]`, followed by the exit-code sentence above;
  - add `lingtai doctor --json` as the second example;
  - give the command `Command.withDescription(definitionOf('doctor').task)`.

## Tests (unit, so they run in the pass)

- **`doctorJson`, pinned with `toEqual`**, on a hand-built `DoctorReport`. It covers:
  - one `fail` with `restartAnswers: true`;
  - one plain `fail`;
  - a `warn`, an `ok`, a not-checked `skip` and a `deferred` row;
  - at least three areas, including the whole-name `packages load under Node`.
- **`renderDoctor` on the same fixture**:
  - checks the section order and the order within a section;
  - checks that every `name` and every `detail` appears;
  - checks all five summary counts, in both the green form and the FAILED form;
  - under `NO_COLOR=1`, finds no `\u001b`; under `FORCE_COLOR=1`, the `✗` is coloured and `note` is not.

  Name each fact this test checks in the PR. That is the ticket's "no fact lost" list.
- **Through `runCli`**: use the `vi.doMock` pattern from `status.test.ts:362-384`.
  - Mock `doctor.ts`'s `doctorReport` and `install.ts`'s `releaseCheck`. **The release check is a real request to GitHub** (`lingtai.ts:117`, `fetch`), so a unit test that does not mock it reaches the network.
  - `doctor --json` gives one document and exit 0. A report with a failure gives the report document and exit 1. A `doctorReport` that throws gives `error.code: "unavailable"`.
- **The `AREA_OF` coverage test** described above.
- **`init.test.ts` should not change.** Its `doctor` world member returns a canned string (`unit/init.test.ts:134`, `:159`). Leave it.
