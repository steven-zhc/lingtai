# #1382: shape of the change

Docs and site wiring only. Three code readings below change what the chapter tells the reader. Two of them go against the ticket's assumptions, and the code wins.

## 1. The add command is `--github-auth gh`, run after `gh auth login`

A bare `lingtai add <owner>/<repo>` in the home chapter 1 made with `init --local` stops before it asks how to reach GitHub.

- That home has no `github.auth` and no App, so `deps.auth()` returns `null` (`apps/cli/src/add-github.ts:281-286`). At a terminal with no flag, `kind` stays `null` (`:289-294`), so no `gh` check runs and `reach` stays undefined.
- `defaultBranchOf` then reaches `githubApp()`. Its comment says that call *"throws where no App is configured — the ordinary case, a defect here and answered null below"* (`:85-90`).
- The recipe for a new repository is absent, so the seed fails: *"`<path>` does not exist and there is no base branch to write into it: pass --main <branch>. Nothing was written"* (`:390-397`).
- The sign-in offer, `askGithubAuthEffect` (`apps/cli/src/github-auth.ts:136-176`, *"sign-in, to sign gh in now"*), is reached only later, through `chooseFirstProject` (`first-project.ts:1202`). The refusal above comes first.

`--github-auth gh` sets `kind = 'gh'` (`add-github.ts:290`). The saved login's scopes and push right are then checked before any question (`:300-317`). The default branch comes from that check, so no `--main` is needed. The login becomes `knownLogin` for the team questions (`:461`), and `runGithubBranch` writes `github.auth: gh` (comment at `:287-288`).

The flag does not sign anybody in. A `gh` that is signed out or missing a scope is refused with the check's own lines (`:305-311`). So the chapter gives two commands, in this order:

```sh
gh auth login --hostname github.com --scopes repo,workflow   # github-auth.ts:65, LOGIN
lingtai add <owner>/<repo> --github-auth gh
```

This is a reading of the code, not a run. Before writing the chapter, confirm it against the `askBeforeGithubAdd` tests under `apps/cli/unit/`, specifically a case with `auth: () => null`, no flag, and an absent recipe. If no test covers that case, the attempt's summary says the bare-`add` refusal was read from `add-github.ts:79-90, 390-397` and not run. It also says that `add` in an `init --local` home cannot offer sign-in itself; `--github-auth gh` after `gh auth login` is the one way in. Neither problem gets fixed here: changing what `add` asks is out of scope.

There is no new `LINGTAI_HOME`. Nothing requires one. The only collision is by repository name (`alreadyAdded`, `packages/setup/src/apply-setup.ts:121-123`, called at `apps/cli/src/add.ts:179-183`, case-insensitive). The chapter gets one line on it: a repository named `chapter-garden` is refused as *already added*.

## 2. CI: `add` writes no `pr.ci`, and the reader writes none either

The ticket's *"CI is waited on only if the recipe names it"* is the wrong way round.

- `ciOf` (`packages/recipe/src/settings.ts:266-287`): *"absent means `detect`, every check (`'all'`) and 60 minutes"*.
- `pr.ts:595-597` skips CI only when detection finds nothing: `'no workflow runs on pull requests'`.
- ADR 0131 §6 agrees: *"absent, a workflow on pull requests means `github-actions`"*, and `required` is *"absent, every check on the head"*.
- No writer of `['pr', …]` exists outside the tests in `packages/` or `apps/`, so `add` writes nothing for `pr`.

Write it this way: if the repository has a workflow that runs on `pull_request`, the draft PR waits for every check on its head. If it has none, the PR page says there is no CI step. `pr.ci.required` is only for narrowing which checks count. There is no ADR conflict, because this is what 0131 §6 says.
