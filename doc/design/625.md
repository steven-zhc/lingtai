# Design: #625. `env`, `projection`, `upgrade`, `rollback` and `uninstall` move to `@effect/cli`, and `install` is `install.sh`

## `install` is not a `lingtai` command

No `install` command exists anywhere in the CLI:

- `lingtai.ts`'s switch has no `install` case (`:879-997`).
- `commands.ts` defines no `install`.
- `INSTALL_COMMANDS` is `['upgrade', 'rollback', 'uninstall']` (`install.ts:56`).

The `install` the ticket means is the installer, `apps/site/public/install.sh`. The Watch out row says *"`upgrade` and `install` run from the release bundle"*, and `integration/install.test.ts`'s `install(version)` is what runs that script. `release.yml:88` ships it byte for byte.

It is POSIX `sh`, piped from `curl`, so `@effect/cli` cannot parse it and `output.ts` cannot reach it. It changes state, so it takes no `--json` either. What this ticket gives it is the layout, written by hand:

- a heading line `lingtai install` on stdout first;
- `say` lines that report a success get `✓ ` (`:129` installed, `:150` already runs, `:155` now runs);
- `refuse()` (`:46`) prints `✗ <sentence>` on stderr in place of `lingtai: <sentence>`;
- every other `say`, and every sentence, stays word for word.

It gets no colour. Plain is a valid rendering of the layout (0121 §3: *"plain output is the same text with no escape codes"*), and a shell script cannot use `colour.ts`. The only check on it is `integration/install.test.ts`, which is out of reach inside a pass. Its assertions are `toContain` on sentences, so they survive a prefix. Say this in the PR.

## Routing: the `install` route goes away

Add `'env'`, `'projection'`, `'upgrade'`, `'rollback'` and `'uninstall'` to `MIGRATED_COMMANDS` (`migrated.ts:9-28`). Then delete:

- `INSTALL_ONLY` (`:31`);
- the `'install'` member of `Route` (`:33`) and its branch (`:45`);
- `entry.ts`'s `install` branch (`:49-60`), and the `installCommand` and `liveWorld` imports (`:22`, `:25`). Update the header comment at `:5-16`.

**Leaving the install route does not bring in the log.** `cli.ts` already carries `version`, which *"is what `upgrade` spawns, and it must not pay for the conductor"* (`cli.ts:57-58`). It imports nothing from `@lingtai/event-store` at the top. Every handler `await import()`s its own module. The three install handlers must do the same: `await import('./install.ts')` and `await import('./world.ts')`, never a static import.

**`self` has to stay the file the process started from.** It is `liveWorld(import.meta.filename)` in `entry.ts` today (`:50`). `installedVersion` realpaths `self` to decide installed or checkout (`install.ts:250-254`). From `cli.ts`, use `import.meta.filename`, as `doctor`'s `releaseCheck` already does (`cli.ts:85`):

- In the bundle, `entry.ts` and `cli.ts` are one file, so it is the same path.
- In a checkout, both are under `apps/cli/src`, so the answer is `null` either way.

The only test that sees the bundled binary is `apps/release/integration/build.test.ts:149`. It is integration, and on this machine it is skipped anyway (SEA is disabled in Homebrew's Node). What stands in for it is the unit row below, which asserts what reached the runner.

**`version`'s plain line is load-bearing.** `versionRuns` spawns the unpacked binary's `version` and splits its stdout into `lingtai <v>` (`install.ts:307-311`). `cli.ts:24` says so. Nothing in this ticket may add a heading to `version`.

In `lingtai.ts`:

- Move `env` (`:890-891`) and `projection` (`:956-957`) into the "runs from the entry" group (`:961-983`), and add #625 to its comment.
- `upgrade`/`rollback`/`uninstall` (`:985-991`) keep their own group; reword its comment to say `cli.ts` answers them.
- Remove the imports this leaves unused, or lint fails: `envCommand` (`:54`), `rebuildProjection` (`:58`), `createProjectionRunner`/`projectionLag` (`:43`), and `projectionCommand` (`:88-146`) entirely.

Nothing writes `lingtai.ts env` or `lingtai.ts projection` into a service job (`service.ts` names only `board` and `daemon`, per #624's note), so there is no `board`-style second door.

## `PROJECTIONS` moves to `projection.ts`

The daemon uses `PROJECTIONS` (`lingtai.ts:86`, `:280`, `:396`), and so must the new `projection rebuild` handler. `cli.ts` cannot import `lingtai.ts`, because it calls `main()` on import (`projection.ts:3-5`).

- Move the constant, with its *"named here in the open"* comment, to `projection.ts`, and have `lingtai.ts` import it from there.
- `help.test.ts:66` rebuilds the list from the three projections. Point it at the moved `PROJECTIONS` instead.
- Fix the comment at `commands.ts:30` (*"holds this to `lingtai.ts`'s list"*).

`projection.ts` imports `@lingtai/event-store` (`:7`). That is fine, because only the handler's `await import()` reaches it.

## Parsing: where `@effect/cli` cannot say what the hand parser said

Follow #624: one injectable runner per command in `Runners` (`cli.ts:394`), each handed the parsed request, with the live runner as the default.

| today | after |
|---|---|
| `env` with no verb or no project prints `USAGE` (`env.ts:27-30`) and exits 2 | The parent `env` command's handler prints `USAGE` and returns 2, as `ticket` does (`cli.ts:618-622`). The subcommands are `set`, `list` and `unset`, each with `Args.text('project')` optional and the exit-2 check in the handler. |
| `env set p KEY=--anything` is legitimate, which is why `env` never went through `parseFlags` (`lingtai.ts:888-889`) | `KEY=…` is one token that starts with a letter, so `Args.text` takes it whole. Pin `env set p 'K=--x=y=='` with a runner test: the first `=` splits it (`env.ts:120-122`), and base64 padding survives. |
| `env set p KEY`, with no `=`, reads stdin unechoed (`env.ts:60-99`) | Unchanged. It is the runner's work, not the parser's. `runCli` uses `Effect.runPromise` (`cli.ts:842`), which installs no stdin or SIGINT handling, so raw mode and the Ctrl-C at `env.ts:89` keep working. |
| `projection` with no verb or an unknown verb prints `commandHelp('projection')` and exits 2 (`lingtai.ts:144-145`) | The parent handler does the same. Unknown verbs: see the next row. |
| `projection run` gets its own *"is gone"* sentence and exits 2 (`lingtai.ts:137-142`) | Precheck it in `runCli`, beside `board shutdown` (`cli.ts:811-818`): the same sentence, with `✗`, exit 2, and the error document under `--json`. As a subcommand it would only be a usage error. |
| `projection rebuild` with no name: `lingtai projection rebuild <name>`, exit 2. An unknown name: `unknown projection "x" — known: …`, exit 2 (`:104-116`) | Optional `Args.text`, with both checks in the handler and the same sentences and exit 2. |
| `upgrade --bogus`, `uninstall --bogus`, or `rollback a b` / `rollback --x`: a sentence and exit 2 (`install.ts:459-460`, `:520`, `:573`) | `@effect/cli`'s usage error, exit 1. This is the change #623 and #624 accepted; name it in the PR. `upgrade` gets `Options.boolean('despite-doctor')`. `rollback` gets an optional `Args.text('version')`. `uninstall` gets `Options.boolean('yes')` and `Options.boolean('nothing-conducts')`. |

**`installCommand(argv, world)` (`install.ts:429-441`) is deleted, not kept as a second parser.** Export `upgrade`, `rollback` and `uninstall` taking `({ despiteDoctor }, world)`, `({ version? }, world)` and `({ yes, nothingConducts }, world)`, and drop their own `argv.find` checks.

`integration/install.test.ts` calls `installCommand([...], world())` about thirty times. Rewrite those calls mechanically. `tsc` covers `integration/` (`apps/cli/tsconfig.json`), so `pnpm typecheck` checks the rewrite even though nothing in the pass can run it.

`uninstall`'s question already follows 0121 §9. It goes through `askConfirm(…, '--yes', interactivity(false))` (`world.ts:88-95`), and with no terminal it names the flag. Leave it.

`upgrade`'s drain wait installs its own SIGINT handler (`restart.ts:1326`, and the `'interrupted'` → 130 path at `:1017-1026`). Nothing in `runCli` competes with it, but do not wrap the handler in anything that does.

## Output

Glyphs go by meaning, never by the `paint` key a line already has:

- `✓` only on a line that says the command did what it was asked;
- `✗` only on a line that ends the command non-zero;
- every sentence stays word for word;
- every other line keeps its paint and gets no glyph.

### `install.ts`

- `refuse()` (`:442-445`) becomes `world.log(`${symbol.fail()} ${line}`)`. `output.ts` imports only `@lingtai/env/colour` (`:9`), so `install.ts` may import it without breaking its *"may not import `@lingtai/event-store`"* rule (`:45-49`).
- Each command opens with `heading('upgrade' | 'rollback' | 'uninstall')`.
- `✓` goes on these lines:
  - `is current` (`:486`);
  - `now runs … (was …)` (`:511`);
  - `already runs … Nothing changed` (`:540`);
  - `runs … again (was …)` (`:547`);
  - `Removed …` (`:666`);
  - `nothing is installed: …` (`:584`).
- `✗` goes on the `not uninstalling — …` lines (`:595`, `:619-622`). They are `paint.fail` today and exit 1.
- **The `paint.fail` warnings about the event log (`:637-647`, `:704-708`) take no `✗`.** The command did not fail at that point, and a glyph that means *failed* would say it had.
- The `paint.signal` lines about the GitHub App (`:672-692`) and the `paint.held` line `the shim still runs …` (`:503`) keep their colour and take no glyph.
- Add no `next:` line. Each closing sentence already names its command, and #625 is not the ticket to reword them.

`integration/install.test.ts:710` asserts `'now runs 1.0.1 (was 1.0.0'` on install.sh's output. That substring stays.

### `env`

Make `formatEnvList` return `string[]` under a new name, `renderEnvList(listing)`, and keep `formatEnvList` as `renderEnvList(l).join('\n')`. `integration/env.test.ts:35-50` calls it with `toContain` on a string, and the same call on an array would compile and assert something else.

- **`list`:**
  - The heading is `env <project>`.
  - Then `keyValues([['file', listing.file]])`, followed by `N name(s), values never shown`. That phrase is the promise `env.ts:13-15` makes, so it stays as written.
  - Then `table(['NAME', 'LAYER'], …)`. The deferred names keep their sentence in the LAYER cell (`env.ts:44-46`).
  - The empty case stays one line, `no names — nothing in <file>`, exit 0 (0121 §1).
- **`set`:** `✓` on `written to` / `replaced in`.
- **`unset`:** `✓` on `removed from`, and `✗` on `was not set in`, which exits 1 (`env.ts:138-142`).

### `projection`

- **`lag`:**
  - The heading is `projections`, then `table(['NAME', 'AT', 'BEHIND', 'UPDATED'], …)`, which replaces the tab-separated line (`lingtai.ts:98`).
  - `AT` is `lastSeq/headSeq`. `UPDATED` is the ISO time or `never`.
  - `no projection has a checkpoint yet` stays one line, exit 0.
- **`rebuild`:**
  - The `… rebuilt — at …` line (`projection.ts:39`) keeps its sentence: `✓` when `lag === 0n`, `✗` otherwise (it already exits 1).
  - `✗` on the guard's refusal (`:31`) and on the unknown-name sentence.
  - `unit/log-predates-hold.test.ts:222-260` drives `rebuildProjection` through injected `log`/`error`. Keep those sinks, and edit those assertions only where a glyph moved a string.

## `--json`: `env list` and `projection lag`

Both commands are `effect: 'changes'` (`commands.ts:207`, `:527`). What makes these two verbs take `--json` is §5's read-only-verb paragraph (*"`board status`, `ticket list` and the listing `backlog [<project>]` today"*, 0121 lines 93-96). Extend that list with `env list` (`"env list"`) and `projection lag` (`"projection lag"`). This is an edit to `doc/decisions/0121-…`, the topic's own ADR, as #621, #623 and #624 did. No archived file is touched.

`upgrade`, `rollback`, `uninstall`, `env set`/`unset` and `projection rebuild` change state and answer with no verdict, so §5 gives them nothing. The ticket's *"each read command"* is these two.

Split each into read, render and json, as #624 did with `ticketList`:

```json
{"version":1,"command":"env list","project":"p","file":"/…/p.env",
 "names":[{"name":"API_KEY","layer":"project file","deferred":false}]}
```

- **No field may carry a value.** Pin it the way `integration/env.test.ts:42-44` does, but in a unit test over a hand-built `ProjectEnvListing`: plant a value string in the fixture and assert it is absent from the document.

```json
{"version":1,"command":"projection lag",
 "projections":[{"name":"task_view","lastSeq":"812","headSeq":"812","lag":"0","updatedAt":"…ISO…"}]}
```

- **The seqs are decimal strings.** `ProjectionLag`'s three numbers are `bigint` (`packages/projector/src/store.ts:190-199`), and `JSON.stringify` throws on a `bigint`. That would reach `failed()` as an `unavailable` document on every call, which no shape test would catch unless it fed a real bigint. The fixture must use `812n`, not `812`.
- `updatedAt` is ISO or `null`.
- An empty log gives `"projections": []`, not an error.
- A `projectionLag()` that throws goes through `failed('projection lag', true, err)` (`cli.ts:34`).
- Under `--json`, an unknown env project goes to an `error` document. `checkProject` throws (`agent-env/src/index.ts:737`), so that is `failed()`'s `unavailable`, exit 1.

In `commands.ts`, add `[--json] [--no-color]` to `lingtai env list <project>` (`:213`) and `lingtai projection lag` (`:529`), within the 76 columns `help.test.ts` measures (`commands.ts:10-12`).
