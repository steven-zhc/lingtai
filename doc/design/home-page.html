A working loop for coding agents

Let your backlog move. Keep control of what lands.

Lingtai picks up your GitHub issues, or tickets kept on your machine, and lets an agent work on them. It runs your repository’s checks and lands passing work. If a run needs you, it stops and says why.

The loop, one stop at a time

What you see at each stop, and what you can do there.

Four stops from a ticket to a decision. Each one shows a small illustration of what it looks like; none of them is real data.

  1. 01

    A ticket

    A GitHub issue with one of your recipe’s kind labels, or a ticket kept on this machine with lingtai ticket new (local projects only). The queue passes over anything with an open blocker.

    You see

    • The ticket in the Queued column, in the order your kinds set
    • A blocked ticket counted as blocked, not lost

    You can

    • Add agent:hold to keep it out of the queue
    • Chain tickets with GitHub’s blocked by

  2. 02

    A worktree

    The agent works in its own worktree, with an environment filtered to what the recipe allows. Each attempt’s commits are kept, and the next attempt starts from them.

    You see

    • The run’s log as it happens (lingtai attach)
    • One line per ticket from lingtai start: steps, cost, where it stopped 0.11

    You can

    • Let it run; nothing here needs you
    • Choose the agent. Codex adds a filesystem boundary; Claude Code runs guarded. No container per run
    $ lingtai start 0.11

  3. 03

    Your checks

    Your test command runs, then a second reviewer reads the diff cold. A failure goes back to the agent for a fix round. Turns, wall time and rounds are bounded.

    You see

    • A verdict per step on the board
    • What a day cost, in dollars, on /report

    You can

    • Choose the checks in your recipe
    • Leave a red check to buy a fix round. A check already red on the base buys none and holds as base is red 0.11

    Wait, or land

    Passing work lands if your recipe says so. Otherwise, or when something goes wrong, the ticket stops and says why.

    ✓ It lands

    You see

Money in dollars, with a ceiling you set

What a day cost and what it landed, on /report. A cost Lingtai cannot know shows as unknown, never as $0.

A daily ceiling stops new work once it is reached. It is not a cap on the day’s total: a pass already running finishes.

Several tickets at once

Set how many each project runs. Lingtai never starts two on one blocked-by chain or two that touch the same file, and lands them one at a time.

More than one needs a daily dollar ceiling, so parallel work can’t run up a bill unattended.

The work, in the open

A board that shows the stops, too.

The local board puts queued, running, waiting and landed work together. On the real page this is Lingtai’s own board from a publishable snapshot, not a demo.

Know the edges: Not a container sandbox · one machine, macOS or Linux · pre-1.0 — what it does not do yet →

Lingtai runs on one machine of yours. It keeps its log in a local SQLite file by default, alongside a clone of each repository it manages and the agent processes it starts. There is no hosted service and nothing to sign up for — install the CLI and run lingtai init.

Built in the open. Source, releases, and issues live on GitHub.
