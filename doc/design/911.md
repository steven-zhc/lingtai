# Design: the queued panel (#911)

## Where the data comes from

**`inFlight` is not passed to `Standing` today, so passing it in is the first edit.** `TaskDetail.inFlight` exists (`apps/board/src/lib/task.ts:964-965`), and `loadTask` fills it only for a queued ticket (`task.ts:1739`, `if (state !== 'queued') return null`). But nothing on the page reads it:

- `StandingProps` has no such field.
- `layout.tsx:175-200` does not pass it to `DeferredStanding`.

Make these changes:

- Add `inFlight?: InFlight | null` to `Standing`'s props, beside `queued`.
- Pass `inFlight={task.inFlight}` from `layout.tsx`.

`DeferredStanding`'s `Omit<…>` list (`standing.tsx:1629-1632`) does not name `inFlight`, so the prop reaches `Standing` through `...props` with no change there. It must stay a plain prop, not a field of `TaskAnswer`. Anything in `TaskAnswer` waits for GitHub, and 0118 §2 says *what is running* is drawn at once.

**The text is already written.** `queuedChip`, `queuedSentence` and `kindOrder` are in `apps/board/src/lib/queued.ts:435-466`, and `InFlight` is at `queued.ts:406-409`. `QueuedView` already carries `kind`, `kinds` and `behind` (`queued.ts:177-181`). Do not add another function that phrases the same thing. If a wording in the mock differs, change it in `queued.ts`, where a unit test pins it.

## Where the panel goes in `Standing`

The `Where it is` section (`standing.tsx:938-1069`, `<section className="swhere…">`) is shared by every state. **Wrap the whole section in `standing.state !== 'queued'`. Do not strip the queued branches out of it one by one.** The blocked, running and approved pages then render exactly as they do now, which is what the *blocked page renders as before* checkbox needs.

A queued page draws the following in that slot. Each item lists where the content comes from today.

1. **The `unknownOf` refusal.** Today it is the first `Gh` inside `FollowedLog` (`:976-987`). Draw the same `Gh`, unchanged, above the panel. The ticket's edge says "drawn as today, above the panel".
2. **`<div className="sreading sreading--advised">` holding a `QueuedPanel`.** This is the only child. Discussion is not drawn on a queued page today: `{discussion}` appears only in the blocked branch (`:1086`). Adding it is out of scope.
3. **`LastAttempt`, outside the `Gh` but inside the panel's section.** It is the log's data (`standing.deciding`). Inside the boundary it would wait for GitHub and be drawn twice, once in the fallback and once in the answer. Drawn after the `Gh`, it appears once, at once.

**`QueuedPanel` is a function component in `standing.tsx` and takes `{ g, pending, inFlight, missing, project }`.** Its body is one `Gh`:

- **Fallback:** the skeleton panel.
- **Children:** `(a) => missingOf(a) ? null : <Panel view={a.queued} …/>`.

When `missingOf` holds, the page is the heading's *GitHub has no issue #N* (`:778-779`) and nothing else, as today.

A null `a.queued` on a resolved answer means `TaskAnswer` carried nothing (`DeferredStanding` passes `queued={null}`, `:1638`). Draw the panel with chip `unknown` and the sentence *Its place in the queue could not be read*, and no skeleton. Never leave an answered boundary as a skeleton (0111 §15).

**Draw the facts row from one helper in both branches**, so that *running now* is the same markup before and after GitHub answers. The resolved branch adds *why first* and *behind it*. The fallback puts a `Skeleton` where *behind it* goes and omits *why first*. When the boundary resolves, the row's cells change in place rather than the row being swapped for a different one.

*Running now* links each entry to `/task/ticket-${project}-${issue}`, the shape the projector writes (`packages/projector/src/task-view.ts:266`). Prefix it with the project only when the project is not `project`, the page's own.

`soWhatLine` (`:822-830`) and `stoppedOf` lose their queued callers when the section is gated. **`stoppedOf` goes, and `soWhatLine` stays**, because blocked and running still use it.

**`whoWaits`' queued default** (`task.ts:783-786`) becomes `'queued'`, as the ticket says. Check `standing.test.tsx:228` and `:1921` against it, and leave `who` populated for the `sowhat` paths that do not draw it.

## CSS

There are two class edits in `layout.tsx:148`:

- Add `detail--queued` or `detail--running` beside `detail--framed`.
- Keep `detail--framed` itself. Other rules key on it.

**Widen the rules as comma-separated selectors, one class per line, not as `:is(...)`.** For example:

```
.detail--waiting .triage-band,
.detail--queued .triage-band,
.detail--running .triage-band { … }
```

The checkbox's unit test reads `globals.css` as text. A literal `.detail--queued .triage-band` is a substring check. An `:is(...)` list would make the test parse selectors, and would invite the test to accept `:is(.detail--framed, …)`.

The rules to widen are the ones the ticket lists:

- `globals.css:1387-1417`: `.triage-band`, `.triage-label`, `.triage-head`, both `.triage-cause` rules, `.triage-summary` and `.triage-recommendation`.
- `globals.css:1458-1475+`: `.sreading--advised` and its `.triage-band`, `.spair` and `.chat` children.

Leave these alone:

- `.triage-evidence`, `.triage-fixes`, `.triage-hunk*` and `.triage-band--failed`. The panel does not use them.
- Every `.chatask` rule (`globals.css:2103-2109`). This is the ticket's watch-out.

**The new classes are new names, so they are not scoped to a page.** These are `.cause-chip--queue` (next to `globals.css:394-399`, using `--surface-2` and `--ink-2`), `.band-facts`, `.fact`, `.fk`, `.fv` and `.fs`. No `.fact` rule exists today; the only mention is in a comment at `globals.css:915`. Prefix the cell rules with `.band-facts`, as in `.band-facts .fs`, because `fs` and `fv` are names short enough to collide with something later.

`.sreading--advised .triage-band` sets `padding: 0 0 1rem` because a `.spair` follows it (`:1464-1468`). On a queued page nothing follows, so the band leaves a 1rem trailing gap. If the mock does not show that gap, add `.detail--queued .sreading--advised .triage-band:last-child { padding-bottom: 0 }`. This adds a rule rather than changing the waiting page's.

## Decisions the ticket left open

- **A queued page that has `afterMove`** (requeued by a move) also carries `detail--resolved` (`layout.tsx:148`). The `:is(.detail--waiting, .detail--resolved)` rules at `globals.css:1198-1217` already apply to it. The panel draws below the `saftermove` section, which is unchanged.
- **The running page** gets `detail--running` and the widened rules, but draws no band, so nothing visible changes. #901's tickets fill it in.
- **A stale or live-refreshed page:** use the same `Gh`/`Deferred` seam as the other boundaries on the page. Add no boundary of your own and no client state of your own.

## Tests

**The render tests go in `apps/board/unit/queued.detail.test.tsx`**, beside the existing queued block tests (`describe('the block, for a ticket that has never run'`, `:361`).

For the never-resolving case, pass a promise that never settles as `github` and check what is drawn: three `asking GitHub…` labels, and *running now* with its `#n` links.

The approved-page assertion is a render of `layout`'s class string. `framed` is exported (`standing.tsx:54-56`), so either test the class expression directly, or move it into a small exported `detailClass(state, afterMove)` so the test does not need to render a layout. The second is the cleaner change, and nothing else depends on the inline form.
