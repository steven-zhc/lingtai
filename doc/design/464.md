# #464: design

The ticket explains why this is one switch. This note covers what it leaves open: **where** each new event gets written, the **seven choices** it leaves to the implementer, and **how to show that the readers did not move**.

## Commits, in order

1. **The stored renames, alone.** `streams.ts:13,15` change once (`'wi-'` → `'ticket-'`, `'run-'` → `'pass-'`), and `envelope.ts:45` follows them by construction (#490). Rename the six `WorkItem*` types and `workItemId` → `ticketId`.
   - Carry their `BUMPED` (`events.ts:2394`) and `UPCASTERS` keys over under the new names, unchanged.
   - In the 106 test files, replace the literal ids mechanically.
   - **Payload reads keyed by a string escape `tsc`.** For example, `reconcile.ts:250` reads `(e.data as { workItemId?: string })`. The Done-when grep is what catches these; run it at this commit.
   - Integration files are edited here too. `pnpm typecheck` is the only check they get before the merge.
2. **Pin the read model before switching it.** In `packages/conductor/unit/what-a-pass-writes-today.test.ts`, add to every row the outputs of `stepOutcomesOf`, `routesOf`, `waitsOf` and `releaseCauseOf`, written out as literals, as they are today. This is the unit-level stand-in for "readers show the same thing". After the switch, each row's event-type lists change and these literals stay the same. Where one must change (the `afterApproval` case below), change it in the switch commit and say why there.
3. **The switch**, then the deletions, then the guard. The commits between may be red. The merge is the atomic unit, and the build step judges only the head.

## Where each event is written

- **`StepStarted` and `StepEnded` belong to `pass.ts`'s `runStep`, not to the pipeline.**
  - Today `runActionPipeline` emits `StepRequested`, `StepStarted` and the terminal per action (`packages/actions/src/action.ts:712`, `:745`, `:842–938`).
  - After the switch it emits only `RunSpent` (`:768`), and `ActionEvent` narrows to that one type.
  - `runStep` writes `StepStarted{runId, step, round}` before the pipeline. It writes `StepEnded{runId, outcome}` from the `outcome` it already builds at `pass.ts:1603`.
  - **Rule:** a `StepEnded` exists exactly where `reached.outcome !== undefined`. So there is none for `claim` or `end`, and none for a routed `proposed` visit (its fact is `PassRouted`).
  - A body that threw leaves a `StepStarted` with no `StepEnded`, followed by `WaitStarted{AgentCrashed}`. That is how the log tells it.
- **The implement body in `conduct.ts` stops appending three events:** `RunFailed{no-commits}` (`:3168`, the no-commits kind only; other kinds stay), `FixRequested` (`:3296`) and `FixApplied` (`:3380`). The `StepEnded` above carries what they said.
- **`PassRouted{runId, offer, reply, decision}`:** all three values are in hand at `routeProposal` (`pass.ts` around `:1146–1167`).
  - `routes` carries them instead of `{from, chose, to, why, ceiling}`, and `conduct.ts:3670` writes them.
  - A restart writes `TicketReleased{cause: Restart{restart}}` where `PassRestarted` was (`:4001`).
  - `PassRouted` goes on the pass stream before the `WaitStarted` on the ticket stream. These are two appends, in that order.
- **`conduct.ts` writes `WaitStarted{waitId, reason: pass.end.reason}` verbatim, with no translation layer in between.**
  - `holdFor` (`conduct.ts:3791–3898`), `holdOfPass` and the whole of `hold-of.ts` go.
  - The header of 0118 §1 says a `WaitReason` is built by `routeNext` and `nextOf` *"and nothing else does"*. So each rewrite `holdFor` does today must either move into one of those pure functions (if it changes the variant a person sees) or vanish (if it only fed `Hold` or `legacyColumns` fields).
    - **Moves:** `BudgetExhausted` with `ceilingHit === null` read as `DidNotFinish` (`:3825–3846`).
    - **Vanish:** turns and cost from `ceilingHit`, which is spend; `declined.said`, which `FixerDisagrees.said` already carries.
  - For a `pass.unanswered` stop, put the sentence that `stopped` carried into `unansweredEnd`'s `detail` (`pass.ts:1387`). `detailOf` (`:1407`) already builds it.
  - The row literals from commit 2 will show whether a moved rewrite still shows the same thing.

## The seven choices

**1. `WaitReason` uses `ProposedEscalated{proposal}` for all seven of #471's stops.** This is already what gets written: `routeNext` builds it (`routing.ts:273`, `:292`) from `nextOf`'s `Propose` (`pass-next.ts:295–335`). And 0118 §1 says *"Every proposal the route hands over is `ProposedEscalated`, whatever it was."*

- The seven direct variants stay in the union with no writer. Deleting them would edit 0118 §1's type, so it needs a superseding ADR, not this ticket.
- A writer test pins that no pass produces them.
- The board already reads the kind off the proposal (`wait.ts:232–257`).
- **The one exception is `approve.ts`'s refusal after an approved merge.** It writes `ProposedEscalated{proposal, because: NotAsked}` with no `PassRouted` before it, because no route ran.
  - Build the proposal with the same mapping `pass-next.ts:280–295` uses: pull it out as a function and have both call it.
  - Feed it from `IntegrateResult.conflict` (`integrate.ts:109`), not from the log.
  - `afterApproval` goes. 0118 §11 says it is *"derived, not stored"* from the `WaitResolved{Approve}` before it.
  - #465 removes this exception.
  - Write all of this in the commit body, as the ticket asks.

**2. `waitId` is a UUID minted by the writer**, the way `conduct.ts:916` mints a run id.

- The three writers are `conduct.ts`, `ask.ts` and `approve.ts`.
- `TriageStarted` and `WaitTriaged` key by `waitId` instead of `blocked`. No `src` file outside `events.ts` reads `blocked`.
- `syntheticWaitId` (`read-model.ts:252`) goes.

**3. `WaitStarted` and `WaitResolved` go on the ticket stream. Approve appends `WaitResolved{Approve{onSha}}` there, at the ticket's version.**

- Today `approve.ts:317–330` appends `StepWaived`s and `ApprovalGranted` to the pass stream. Both events are removed and nothing replaces the waivers. #465 brings back `Waived{waitId}` on the continued run's `StepEnded`.
- An expected version on the ticket stream is 0118 §11's *"`waitId` is the item's current wait"* check, done by the store.
- A person's requeue writes `WaitResolved{Requeue}`, then `TicketReleased{cause: ByPerson{waitId}}`.

**4. `TicketReleased.cause` is `ReleaseCause | null`, as a zod schema.** Today `ReleaseCause` is a TS type only (`read-model.ts:1212`). Two releases have no 0120 cause:

- the reconciler's release of a dead worker (`reconcile.ts:664`);
- `releaseWorkItem`'s free-text callers (`claim.ts:134`).

`releaseCauseOf` already answers `null` for these (`:1255`), and the readers moved by #474–#476 already take `null`. A fifth variant would be a change to 0120.

**5. Payloads that change shape change in place, with no bump.** These are `PassRouted`, `TicketReleased` (gains `cause`), `IntegrationRefused` (loses its conflict fields), `TriageStarted`, and the cost fields below.

- This follows #445's precedent for `WorkItemBlocked` (comment at `events.ts:2398–2404`). The reset is what makes it legal.
- Remove `RepairRequested` and `RepairDeclined` from `RETIRED` (`events.ts:2482`). The `Outbox*` entries stay.
- `FixRequested`'s, `StepPassed`'s and `StepDidNotFinish`'s `BUMPED` lines go with their types.

**6. The old-log guard checks for a stored type this build has no schema for. It no longer checks for a `WorkItemBlocked` shape.**

- `logPredatesHold` (`event-store.ts:265`) asks `rowsOfType('WorkItemBlocked')`, which is no longer an `EventType`.
- Instead, read `typeCounts()` (`queries.ts:147`) and refuse on the first stored `type` that `isEventType` rejects. Name that type and its count, since there is no seq to name.
- This is certain, not heuristic: every pre-switch log holds `WorkItemDiscovered`, renamed in commit 1.
- `decodeRow`'s unknown-type-on-read (`event-store.ts:216`) throws the same error. It replaces the `WorkItemBlocked` special case at `:229–231`.
- Rename the guard to match (`logPredatesSwitch` / `LogPredatesSwitchError`). It has four callers: `daemon.ts:113`, `doctor.ts:1320`, `projection.ts:29` and `projector.ts:57`.
- Update the opening line of `doc/operating.md`'s "Resetting the log" section, which names doctor's row.

**7. Not everything in `hold.ts` and `triage.ts` goes.**

- `JudgeWhen` (`hold.ts:71`) is used by `recipe`, `actions`, `conductor` and the board. Move it to `proposal.ts` before deleting `hold.ts`.
- From `triage.ts` delete `Cause`, `Move`, the five move schemas, `Failed`/`Advised`, its `TriageResult` and its `TriageStatus`. Keep `Hunk`, `TriageQuestion` and the bounds, which `wait.ts` imports.
- `wait.ts`'s header (`:15–26`) says this is when it goes into `index.ts` and the `@lingtai/domain/wait` subpath is dropped.

## Not adapters, but the module still goes

- `conductor/src/adapters.ts` holds `actionOf` and `outcomeOf`, which build the `StepOutcome` `runStep` writes. That is the forward direction and is still needed.
  - Move both into a file named for what they do (for example `step-outcome.ts`) and delete `adapters.ts` in both packages. The Done-when greps for the module.
- `pass-steps.ts`'s `StepPassed` and `StepDidNotFinish` (`:142`) are the pass's own report types, not events. Leave them.
- Domain folds that still read the old types directly change here: `run.ts:387–430` (`StepWaived`, `ApprovalGranted`) and `work-item.ts` (restarts from `PassRestarted`).
- These are readers that the prep tickets missed. Fix them here and name them in the commit body:
  - `packages/extension/src/index.ts:105–108`, which switches on `ApprovalRequested` and `WorkItemBlocked`.
  - Spend read off old events rather than `RunSpent`:
    - `apps/board/src/lib/history.ts:223` (`RunFinished`) and `:324–334` (`DiscussionAnswered`, `DiscussionHeld`);
    - `history.ts:448–451` (`RoundEnded`, from `FixApplied`);
    - `apps/board/src/lib/task.ts:874`;
    - `apps/board/src/app/discussion.tsx:638`;
    - `apps/cli/src/discuss.ts:403`.
- The cost fields that go are on `RunFinished`, `DiscussionAnswered`, `DiscussionHeld` and `TriageAgent` (now under `WaitTriaged`). `RunSpent`'s fields stay.
- On `task_view`, only `cost_usd` and `repair_costs` go. `repair_pending` stays, because `conductor/src/queue.ts:140` reads it.

## Trap: `WIP_COMMIT_PREFIX` stays `'wip: run-'`

`integrate.ts:448` refuses any branch carrying a commit whose message starts with this prefix. Agent branches on origin outlive the log reset. If the prefix followed the stream rename, a pre-reset branch holding a ceiling-stopped WIP commit could land on `main`.

- Keep the constant (`vocabulary.ts:82`).
- `conduct.ts:1692` keeps writing `${WIP_COMMIT_PREFIX}${passIdOf(runId)}`, which is still unique to this conductor.
- Correct its comment (`:76–80`): it no longer mirrors the stream prefix.
- The Done-when grep does not match it, because a space comes before `run-`.

## What can be checked before the merge

  - every event a row of `conduct-a-whole-pass.test.ts` appends must pass `parsePayload` and fold through `boardFactOf`, `cardFactOf` and `attemptFactOf` without a `null` where the row expects a fact;

The person proves it as the last step of the reset, by running the rebuild, and T11 proves it later. Say this in the commit body rather than claiming it.

## The commit body's reset steps

Follow `doc/operating.md`'s "Resetting the log" in its own order, *Before → Archive → Reset → After*, with three placements:

- The merge goes after *Before*'s drain is confirmed: doctor's **daemon: liveness** row reads `not running`.
- The reset goes after the merge.
- *After* rebuilds all three projections (`task_view`, `finding_backlog`, `spend`) before the restart.

Two notes for the person running it:

- An un-reset log now refuses daemon start by naming its first unknown type. That is the guard working, not a fault.
- Leftover `worktrees/<project>/run-*` directories show up as *"a run with no RunStarted"* findings and are left in place by design (`reconcile.ts:254`). Remove them by hand if #448's procedure does not.
