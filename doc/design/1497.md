## The one function

Move the slug branch out of `addFlowEffect` (`add.ts:178-195` plus the GitHub card block at `:280-330`) into a new exported Effect:

```
setUpGithubProjectEffect(slug, flags, buildFlags, world: AddWorld, command: 'add' | 'init'): Effect<number>
```

Put it in a new file, `apps/cli/src/github-project.ts`. `init.ts` can then import it without importing `add.ts`'s command wiring. It does, in order:

1. Reads `alreadyAdded(projects, repo)` once and decides which case applies, before any question:
   - **`found === undefined`**: the first run, exactly as today.
   - **Owner repair** (`found.owner === null && found.configHash !== null`, the condition at `add.ts:184`): unchanged. It asks nothing and goes straight to `chooseFirstProjectEffect`, then prints `add.ts:330-332`'s line.
   - **`found.owner !== null` and it differs from the slug's owner** (case-insensitive): refused before any question with the same `taken({ slug, repo, takenBy })` sentence that `first-project.ts:1486-1488` and `onboard.ts:510` print. Today the refusal at `add.ts:185` hides this case; once that refusal is gone, the only other check is `runGithubBranch`'s, which runs after every question.
   - **`found.owner === null && found.configHash === null`** (a stream with no `ProjectConfigured` hash): keep `alreadyAddedSentence`'s refusal. Nothing says this slug owns it, so it is not a rerun. This is the *null/unknown* edge, decided here.
   - **The same owner**: a rerun. First check that the recipe resolves (`resolveSource` on `draftRecipe(repo).text()`). If it does not, refuse by name before any question, with the same wording as the local rerun (`first-project.ts:660-668`).
2. Calls `askBeforeGithubAddEffect`, unchanged. #1488's list is inside it, so there is no second list.
3. **Unchanged rerun.** On a rerun where `asked.answers.changes.length === 0`, return before `chooseFirstProjectEffect`. Registration and `applySetup` happen only through `world.github.add`, inside `runGithubBranch`. Still run `ensureLabelsEffect`, then draw the card with `unchanged: true`, read from the recipe on disk.

   The card and the labels need a `GithubReach`, which today comes from `add()`'s result (`onboard.ts:422`). So add `reach: GithubReach` to `AskedBeforeAdd` (`add-github.ts:240`):
   - gh: `{ kind: 'gh', login: ghLogin }`.
   - App: `{ kind: 'app', slug: null }` unless the installation carries the App's slug.

   `liveLabelClient` needs only the kind (`add-labels.ts:54-61`).

   `make` is always `undefined` here: a branch to make implies a changed `branch.personal`, so `changes` would not be empty.
4. **Otherwise**, as today: `chooseFirstProjectEffect` with `github.add` overridden to `addWithSetup`, then the card. Pass `command` through to `printSetupEndEffect` and widen its type if it only takes `'add'`.

After this, `addFlowEffect`'s slug branch is a single call to this function.

## `addWithSetup`'s guard

Give `addWithSetup` the first read's answer: `rerun: boolean`, meaning `found` was registered under this owner. Inside the lock, refuse only when `!rerun` and `alreadyAdded(...)` is now defined. That keeps 0122's race for a first add (another process registered it in between) and lets a rerun through to `applySetup`. Every changed rerun registers again through `add()`, as the local rerun does (`first-project.ts:1300-1320`). So `ProjectConfigured` is appended on any changed rerun, not only on a changed `branch.main`. The test still asserts it for `branch.main` because `conduct.ts:134-135` depends on that case.

## Team to solo

Don't add a check of your own. The refusal comes from `changeRecipe`'s `mode-switch` (`packages/project/src/change.ts:178-193`), inside `applySetup`, inside `add()`. `addWithSetup` already turns it into a logged `SetupWriteError` and `{ ok: false }` (`add.ts:393-402`). `runGithubBranch` then returns `refused`, so the card block, and with it `ensureLabelsEffect`, never runs. That gives the ticket's *no label created*.

No branch is made either way: `make` is set only in the team branch (`recipe-flow.ts:381-456`). The test must seed the draft the way production reads it: a `ProjectPrNumbered` event in the store handed to `world.store`, not a stubbed `changeRecipe`. What settles the claim is the absence of a `ProjectRecipeChanged` for the project and an unchanged file.

## The card: compare URL

Keep #1474's commit list. Add `https://github.com/<owner>/<repo>/compare/<new>...<old>` to the line. For a GitHub project, also use the URL in place of the `git log --oneline origin/…` fallback in `changedLeftBehind` (`recipe-flow.ts:259-264`, and the `… more not listed` line at `add-github.ts:569-572`). The local card stays as it is.

For the *"one function"* test, hand the same stub `AddWorld` to both entries. Assert that the recorded prompt list from `init --github` ends with exactly the list from `add`. Put the test next to #1488's question-list test in `apps/cli/unit/recipe-flow.test.ts` (or `add.test.ts`).

## Edges the ticket leaves open, decided here

- **Ctrl+C between `makePersonalBranch` and `applySetup`.** This is the existing behaviour (`add-github.ts:643-644`): the next rerun finds the branch *exists* and uses it. Rerunning with the same answers then counts as a change (`branch.personal` differs), so the rerun writes it. Nothing new is needed.
- **The *unchanged* return skips `deps.claudeToken`** (`add-github.ts:656-664` runs inside `askBeforeGithubAdd`, before the return, so it still runs). That matches the local rerun, which asks it too. Leave it.
- **`--defaults` on a rerun** is the unchanged case. `--defaults` answers only the mode, login and branch questions through `acceptingDefaults` (`recipe-flow.ts:303`), and each one takes `current`.
