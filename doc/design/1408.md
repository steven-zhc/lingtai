## The decision the ticket doesn't make: the board's generated box must know whether there is a summary

The ticket says the board "renders the same function, so it shows the new format at once". That is true, but the board doesn't render the same *input*. `generatedBody` always passes `summary: null`:

```ts
/** The generated rest of the description: what the daemon regenerates from the log, under the person's summary. */
export function generatedBody(pr: PrState, facts: PrPageInput['facts']): string {
  return prDescription({
    title: null,
    summary: null,
```

(`pr-page.ts:470-474`). Today that does no harm, because `ticketsSection` writes the same lines either way and only the leading `---` depends on the summary (`pr-description.ts:53`). After this change the summary decides *which content* appears. Under a person's summary the board would show the full `- <title> (#n)` list, while GitHub shows only `Closes …`. The read-only box (`pr-generated-box.tsx:1`, *"The generated rest of a PR's description, read-only"*) would then misdescribe what was pushed.

**Decision:** make the summary's presence an input to the generated rest, not a constant.

- In `pr-description.ts`, export the generated part as named sections, e.g. `GENERATED_SECTIONS = [ticketsSection, footerSection]`, with `PR_SECTIONS = [summarySection, ...GENERATED_SECTIONS]`. Don't let the board slice `PR_SECTIONS` by index.
- `generatedBody` passes `summary: pr.summary?.text ?? null`, rendered with `GENERATED_SECTIONS`. The summary text itself is still never in the box; the box gets the `---` and the `Closes` line, exactly as they sit under the summary on GitHub.
- `pr.summary` is the same field the daemon reads (`packages/conductor/src/pr.ts:378-379`: `state?.summary?.text`; type at `packages/domain/src/pr.ts:125`). Both sides therefore decide "has a summary" from the same fold, and both use `hasSummary` (`pr-description.ts:37`), so a summary that is all whitespace counts as none on both.
- Both callers of `generatedBody`, `pr-page.ts:596` and `prs.ts:431`, already have the `PrState`, so their signatures don't change.

A person who saves an edited summary sees the box change from list to `Closes` only on the next render, which reads `PrSummaryEdited` from the log. That is the same staleness the page has today.

## `DescribedTicket` loses `spend` and `mergeCommit`

Once the footer and the ticket lines stop printing them, nothing reads `DescribedTicket.spend` or `.mergeCommit`. They are read today only at `pr-description.ts:51` and `:57-58`. The ticket's Out of scope allows removing them in that case, and leaving them would invite the next section to print them again. So:

- Drop both fields from the interface (`:10-18`).
- Drop `spend: read?.spend ?? null` from the two call sites, `pr.ts:382` and `pr-page.ts:477`. `mergeCommit` reaches them through `...t` and can stay in the spread.

The **facts port keeps `spend`**: `PrPorts.facts` (`pr.ts:107-110`) and the board's `ticketFacts` both still return it. `prs.ts:362` sums it into the *Spend* fact, which the ticket keeps (`pr-page.ts:232`, `:619`).

## The no-summary list

Write `- <title> (#n)`; a non-GitHub ticket is `- <title>`, using `isGithubTicket` (`:31`). Per the ticket's Edges, a ticket with an empty title is `- #n`. Under the list goes the `Closes` line. With a summary, the `---` rule stays where `:53` puts it, followed by the `Closes` line. With no open ticket and a summary, nothing appears between the summary and the footer: no orphan rule.

## Briefs

Both briefs keep *"no list of the tickets, and no "Closes #…" lines: Lingtai appends them itself"*. Reword it to *"no Closes lines"*, because the brief now asks for ticket numbers inside the bullets, and a literal "no list of the tickets" would contradict that. Put the example in one shared string constant that both briefs interpolate, so the unit test can assert on it once. The example contains no `Closes`, so the model has no `Closes` to copy.
