# Design: #628, the `at` declaration and the test that holds passes to it

## Where the declaration goes

Put it in `packages/domain/src/events.ts`, directly under `EVENTS` (`events.ts:2034`) and `RETIRED` (`events.ts:2140`):

```ts
export type At = Step | 'outside'
export const EVENT_AT = { TicketDiscovered: [...], … } as const satisfies { readonly [T in EventType]: readonly At[] }
```

- **Use a mapped type with `satisfies`, not `Partial`.** A missing key, or an extra one, then fails `tsc`.
- `Step` is already in scope there. It comes from `vocabulary.ts:22`, and `events.ts:33`/`46` import it.
- `packages/domain/src/index.ts:4` re-exports all of `events.ts`, so the conductor's test can import `EVENT_AT` from `@lingtai/domain` with no other wiring.
- `RETIRED` types (`OutboxDelivered`, `OutboxFailed`) declare `[]`. Add a one-line unit assertion in the domain package that a type is in `RETIRED` exactly when its `at` is `[]`, so the two lists cannot drift.

**`'outside'` is one more member of the array, and a type can have both.** Some types are written both by a pass and by something that is not a pass. Example: `ConductorPaused` comes from the control stream, and `conduct.ts:878` also appends it while a pass is running. Such a type lists each step it is written at plus `'outside'`. The test treats `'outside'` as matching no step. So a type that is appended during a pass must name that step, even when it is also written outside one.

## How the test knows which step was active

This is the part the ticket leaves open, and the obvious approach gets it wrong.

**What the log marks:** `StepStarted` is appended once per visit to a spine step, by `pass.ts:1395`.

**What it does not mark:**
- **`claim`, `end` and routing visits get no `StepStarted`.** The comment at `pass.ts:1388–1393` says so: *"`claim` and `end` run outside this loop (`claimStep`, `resolveEndActions`) and never reach here, and a routing visit is built directly by `routeProposal`'s own `record()` calls rather than through `runStep` — so neither gets one either."*
- **`conduct.ts` appends some events after `runPass` returns.** These include:
  - `PassRouted` (`conduct.ts:4018`), whose routes are taken in the walk but recorded after it;
  - the held `StepEnded` (`conduct.ts:4389`);
  - `WaitStarted` together with `endPlan` (`conduct.ts:4415`);
  - `TicketLanded` (`conduct.ts:4162`).

  The block comment at `conduct.ts:3831` calls this part *"the ending, written once"*.

So the rule "the step of the last `StepStarted`" would put `PassRouted` at `review` and `EndActionsResolved` at `merge`. The declarations would then be written to please the recorder, which is the opposite of the ticket's *declaration first*.

**Use this fold instead. It needs no change to production code:**

1. Read every stream in `memoryStore().streams` (`test/one-pass.ts:87`) and sort the envelopes by `seq`. That fixture's `seq` is one counter across all streams (`one-pass.ts:89`, `102`), so sorting gives the global append order.
2. Track a current step. Before the first `StepStarted` it is `claim`; this covers `TicketClaimed`, which `claimStep` appends before the walk at `conduct.ts:3857`. Each `StepStarted` sets it to `data.step`.
3. An envelope appended while the current step is `X` is allowed at `{X, 'proposed', 'end'}` (but `{claim}` only, before the first `StepStarted`). `proposed` and `end` are the two steps a pass can be in without announcing them.
4. The check is `EVENT_AT[type] ∩ window ≠ ∅` for each envelope. Any envelope that fails is reported with its type, its window and its declared list.

Write this as a pure function in the test file, taking `(envelopes, at)`. The deliberate mis-declaration test calls it with `{ ...EVENT_AT, RunStarted: ['claim'] }` and asserts it reports exactly `RunStarted`. `RunStarted` is appended inside `implement`'s dispatch (`conduct.ts:3375`), where the window is `{implement, proposed, end}`.

**The cost of this rule:** declarations of `proposed` and `end` are only checked loosely. Something declared only `['end']` passes wherever it appears after the claim. Say this in the test's doc comment. Choose the mis-declaration to fall outside `{proposed, end}`, or it proves nothing. A tighter check would need `conduct.ts` to announce `end` and routing visits, which is a production change this ticket does not ask for.

## Which passes, and one that cannot be built

Drive the passes with `once()` and `fakePorts()` from `test/one-pass.ts`, never with `runPass`, because `runPass` appends nothing. `what-a-pass-writes-today.test.ts` explains why in its header (lines 10–12). That file already has three of the four passes:

| Ticket asks for | Use |
|---|---|
| a pass that lands | row 1 (`what-a-pass-writes-today.test.ts:144`) |
| refused at `review`, waits for a person | `JUDGED` with the judge entry removed. `findings` has no built-in, so the pass parks at `waiting` (`one-pass.ts:246–250`). The reviewer is `refusingRuntime`. |
| a merge conflict | row 10a (`:902`), with `ports.repo.integrate` returning `reason: 'conflict'` |
| refused at `build`, then fixed in a round | **cannot be a unit test.** Use row 2 (`:210`) instead: review lines, then judge, then an `implement` round, then green. |

**Why the `build` row cannot be unit:** the same file's header (lines 18–21) explains it. Only `runPlugin` serves `build`, and `run:` spawns a real process (`actions/src/command.ts:43`). That makes it integration under 0060 §1. Row 2 is the unit-level stand-in: it covers a refusal that buys a round and a second `StepStarted{step:'implement', round:1}`, which is what the round case is there to exercise. Say this in the test's doc comment. Do not try to fake `run:`.

Adding rows 11 (`StepAsked`) and 12 (a `human:` at `proposed`) is cheap, and they reach `RunAwaitingInput`/`WaitStarted` paths. They are optional.

## Writing the declarations

Write every declaration from reading the code that appends the event, not from what the fixtures happen to produce. The test only catches a declaration that is too narrow, never one that is too wide.

- `RunContextExhausted` and `RunAwaitingInput` come from the hook server during the agent's run. They are `implement`, plus every other step that dispatches an agent (`design`, and `review` for the cold reviewer).
- The ticket's list of `outside` producers (control, project, queue, triage, discussion, GitHub app, extension) covers the types that no pass writes.

Unit half only: `pnpm typecheck` and `HOME=/nonexistent pnpm test` are the whole check.
