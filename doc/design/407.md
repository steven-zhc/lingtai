# #407: the last pass, starting from `agent/407`

`agent/407`'s own design note — **the addendum**, below — covered two things,
and the merge that brought it onto `main` discarded it in favour of this one
(the add/add conflict on this path, resolved by keeping this pass's copy). Both
are recorded here instead, so neither is lost a second time:

**The ref the conflict brief tells the agent to merge is bare `<base>`, never
`origin/<base>`, and the brief never tells the agent to fetch.** Both follow
from how the worktree is provisioned (`packages/repo/src/worktree.ts`):

- The mirror is bare and fetches `+refs/heads/*:refs/heads/*` (`worktree.ts:60-63`),
  landing the base at `refs/heads/<base>` — never at `refs/remotes/origin/<base>`,
  which this mirror never populates. The agent's worktree shares the mirror's
  refs, so `<base>` resolves and `origin/<base>` does not.
- The bare clone's `origin` is wired by `remote set-url`, with no stored
  credential (`worktree.ts:103,111-113`). A `git fetch origin` from inside the
  worktree has no refspec to follow and no token to authenticate with — only the
  conductor's own `git()` calls carry one (`TokenSource`). The brief must not
  tell the agent to fetch, because the agent has no access to make one succeed.

**How far `conflictHalf` goes**: resolve and commit the merge it names, nothing
more. It does not push — the merge lane re-attempts that on what the agent
commits — and it does not fetch, for the reason above: the base it names is
already on disk, at `refs/heads/<base>`, by the time the agent reads the brief.

This note covers three more things: **how to get onto `agent/407` without
losing it or `main`**, **one phrase to use in every place it lists**, and
**two places it missed**.

## Getting onto `agent/407`: merge it into HEAD, don't reset to it

This worktree is detached at `main` (`0108f9d3`). `agent/407` (`e0f16502`) forked from `c212777c`, and `main` has 14 commits since then. Four of them touch files this ticket edits: `integrate.ts`, `attribution.ts`, `attribution.test.ts` and `recipe.ts` (#408's conflict paths and the new `unexpected` reason).

- **Do not `git reset --hard agent/407`.** The gates diff against `baseSha`, which is `main` (`worktree.ts:137`, and *"every gate works on the diff against `baseSha`"*, `worktree.ts:160-161`). A HEAD without `main`'s 14 commits would look like a diff that reverts them.
- **Do not start fresh from HEAD either.** The push is `HEAD:refs/heads/<branch>` (`worktree.ts:159`), leased against `remoteHead`, which is `e0f16502` (`worktree.ts:138`). Anything that is not a descendant of `e0f16502` overwrites the five reviewed commits.
- **Run `git merge --no-edit agent/407` from HEAD.** `git merge-tree --write-tree HEAD agent/407` reports no conflicts. The one exception: if the design step has committed this note as `doc/design/407.md` before you merge, the merge stops on an add/add conflict for that one file. Keep this pass's copy (`git checkout --ours doc/design/407.md`). Every other file merges cleanly.

All line numbers below are **after that merge**. Most match the addendum's, and the ones that moved are marked.

## One phrase, used everywhere

What the lane does (`integrate.ts:395-475`):

1. Cut a throwaway worktree detached at the freshly fetched base.
2. Merge the branch into it with `git merge --no-edit <branch>` (`:400`).
3. Verify there (`:440-449`).
4. Push `HEAD:refs/heads/<base>` (`:464`), which is a fast-forward of the base.

There is no separate "merge out". The push is the landing. `doc/plugins/merge.md:5` on `agent/407` already says it: *"merge the branch into the base inside a throwaway worktree, push"*. **Use that wording, shortened where it has to be, in every place below**, so no reader has to reconcile two versions.

- `integrate.ts:6`: *the integrator: merge the branch into the base in a throwaway worktree, verify, push.*
- `integrate.ts:88`: the `verify` doc. Re-run after the branch is merged into the base, before the push. The rest of that comment is true, so keep it.
- `integrate.ts:448` (the addendum's `:427`): change the detail to `` `verification after merging ${options.branch} into ${options.base} failed:` ``. The detail is shown to a person and stored in `IntegrationRefused.detail`. Old events keep the old text, which is correct. No unit test asserts the prefix (`git grep "verification after merging"` finds only the integration test name). Because the sentence changes, rename that test at `integrate.test.ts:195`. Its comments at `:235` and `:299` (*"fetched and merged in"*, *"the base is merged in"*) say the same wrong thing, so correct them too. All three are comments or names, and nothing asserts them.
- `merge-action.ts:30` and `recipe.ts:891`: change *"the base in, verify, the base out"* to *"the branch into the base, verify, push"*.
- `recipe.ts:1715-1716`: this one is a **string**, `ONLY_THE_LANE_LANDS`, shown to a person when a recipe is refused. It is not a comment. Change it to *"merges the branch into the base in a throwaway worktree, re-verifies against what landed in the meantime, and pushes"*. Run `git grep -n "merges the base"` after the edit: if a recipe test pins the old text, update the assertion rather than keep the sentence.
- `doc/backlog.py:329`: correct it. Nothing generates from it, so editing it is the whole job.
- `scripts/the-pass.py`: **two lines, EN `:245` and ZH `:371`** (*"base 并进来、verify、再合出去"*). The script writes both `doc/the-pass.html` and `doc/the-pass.zh.html` (its docstring, `:2`). Edit both lines, run `python3 scripts/the-pass.py`, and commit both HTML files. For ZH, something like *"分支并进 base、verify、push"*. Keep it as short as the EN line, because it sits under a box in the drawing.
