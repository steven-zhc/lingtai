# Design for #662: warn about a protected base at `add`, and name the push it refuses at merge

## Shape

There are two independent halves and one shared sentence. The decisions the ticket leaves open are below. Where this note disagrees with the ticket's **Fix** row, it says why.

### 1. The two remedies are one constant in `@lingtai/domain`

Both the onboarding warning and the merge refusal have to give the same two remedies. Write them once and export them from `packages/domain/src/attribution.ts`, beside the `push-rejected` card. Use a function of `base`, for example `baseProtectedRemedies(base)`. Both `@lingtai/conductor` and `@lingtai/repo` already depend on domain (`packages/repo/package.json:14`).

The ticket says "the two remedies" without naming them. Take them to be:

- **(a)** let the Lingtai App bypass the branch's protection: add it to the ruleset's bypass list, or to the classic rule's allowed actors and push restrictions.
- **(b)** point the recipe's `repo.base` at a branch that accepts direct pushes.

Both sentences must also say: *Lingtai pushes a merge commit straight to the base and does not open pull requests.* That is the fact the user is missing.

### 2. Onboarding: the check goes in `add()`, not in `checkInstallation`

The ticket puts it beside the permission check in `checkInstallation` (`onboard.ts:271-306`). It cannot live there, for two reasons:

- **`checkInstallation` does not know the base.** It runs before the recipe is read. The base is first known at `onboard.ts:339`: `const base = baseOf(resolved.recipe)`. The file's own header says the base is the recipe's: *"The recipe's own `repo.base` says what the base *is*."* (`onboard.ts:22-23`).
- **It runs twice.** `checkInstallation` is called once by `askBeforeGithubAdd` (`apps/cli/src/add-github.ts:142`) and again by `add()` (`onboard.ts:322`). A warning there would print twice.

So put it in `add()`, after `client.refSha(base)` (`onboard.ts:347`). That way a base missing on the remote still fails the way it does today, before anything is said about protection. `add()` is what both GitHub paths run:

- `lingtai add`;
- `init`'s GitHub branch, through `first-project.ts:773` (`add: (opts, log) => add(opts, log)`).

`Recheck` also goes through `add()`, so it warns too, which is correct. `init --local` goes through `addLocal` (`apps/cli/src/init.ts:112`) and never reaches this code. That covers the *local project* edge with no extra check.

**Write a standalone function over `client.request`, not a new `GitHubClient` method.** `request` exists *"for the calls that do not have a method yet"* (`packages/github/src/client.ts:167-168`). The interface has hand-written fakes in at least nine test files (`git grep -l defaultBranch`). A new required method would make every one of them a typecheck failure the agent has to visit.

Export something like `baseProtection(request, owner, repo, base)`. It returns one of three answers:

- `protected`, with which source said so;
- `not-protected`;
- `unknown`, with the error.

Keep the logging in a second function, `warnIfProtected(..., log)`, so the unit test can call it the way `checkInstallation`'s tests call that function (`packages/conductor/unit/onboard.test.ts:260`). `add()` ignores the result except to log it. **It never changes the return code.**

**How to read the two endpoints:**

- **`GET /repos/{o}/{r}/branches/{base}`, the `protected` field.** `true` means warn. Do not call `/branches/{base}/protection`: that needs admin permission, which the App does not request (`onboard.ts:300`, *"issues, contents, pull requests write; metadata read"*).
- **`GET /repos/{o}/{r}/rules/branches/{base}`.** This returns `[]` when no ruleset applies. Not every rule refuses a fast-forward push:
  - `deletion`, `non_fast_forward` and `creation` never refuse one, and GitHub's suggested default ruleset is often exactly those. Warning on them would make the warning noise.
  - **Every other type warns, including types this code does not recognise.** That keeps the check on the warn-not-refuse side.
  - Call out `required_linear_history` in a comment. The lane makes a merge commit (`git merge --no-edit`, CLAUDE.md), so that rule refuses every landing.
- **Combining them.** Either endpoint reporting protection means `protected`. If both reads fail, the answer is `unknown`. If one fails and the other says unprotected, the answer is also `unknown`, never `not-protected`. This is the ticket's edge: *never treat a failed read as not protected in the wording.*

The ticket names a 404 on rulesets for a plan without them as a failed read. The function needs no special case for it: it falls into `unknown` like any other failure.

### 3. The merge lane: `base-protected` is refused inside `attempt`

At `integrate.ts:593-596`, check a new `BASE_PROTECTED` regex before `PUSH_REJECTED`. Match `protected branch hook declined`, `GH006`, and, for rulesets, `GH013` and `repository rule violations`. The ticket names only the first two. GitHub reports a ruleset refusal as `GH013`, and the onboarding check reads rulesets, so the merge side should name the same refusal.

On a match, call `return yield* refuse('base-protected', …)` right there, inside `attempt`.

**That one placement is what keeps it out of the retry, with no change to the loop.** `refuse` appends `IntegrationRefused` and returns an `IntegrateResult` (`integrate.ts:265-277`). That result has no `lostThePush`, so the loop at `:658-662` returns it on the first push. Do not return a `LostPush`.

The detail is git's own text followed by the remedies constant. It is cut to 2,000 characters by `refuse` (`:276`), so put the remedies **first** and git's text after them.

`PUSH_REJECTED`'s doc comment (`:162-170`) says *"a push that failed for some other reason … goes to the unexpected channel"*. Add one line there naming the protection case as the exception, with a pointer to the new regex.

Leave `conduct.ts:2751` alone. It labels any failed push of the **agent's** branch `push-rejected`, which is a different ref and out of scope.

### 4. The new reason, where it must be added

Copy the path `wip-commit` took. It is the most recent ordinary reason, and it appears in exactly these places (`git grep "'wip-commit'"`):

| Where | What to add | What happens if it is missed |
|---|---|---|
| `packages/domain/src/vocabulary.ts:52-68` | the enum member | — |
| `attribution.ts`, `INTEGRATION_OWNER` (`:116`) | an owner | compile error (total `Record`) |
| `attribution.ts`, the cards record (`:279` area) | `says` and `move` | compile error (total `Record`) |
| `packages/conductor/src/step-outcome.ts:53-63`, `REFUSAL_REASONS` | `'base-protected'` | **no compile error** |
| `packages/domain/unit/attribution.test.ts:51-60, 100-111, 165-178` | the value in each hand-written list | the tests stop covering it |

**The `step-outcome.ts` row is the trap.** `REFUSAL_REASONS` is a hand-written array, not a total record, and `refusalReasonOf` (`:65-68`) turns anything missing from it into `'unexpected'`. A `base-protected` missing there would type-check, pass every test, and reach the board as *"the merge lane failed in a way it does not handle"*, which is the generic failure this ticket exists to remove. A unit test should feed `because: 'base-protected'` through `step-outcome.ts:307` and assert that the reason survives.

**Owner: `'person'`.** By attribution.ts's own definitions (`:56-65`) it is not `repository`, which means the diff or its gates. It is not `lingtai` either: *"Nothing in the repository is broken"* would be the wrong thing to say when a repository setting is the cause. It is a hold that only a person's change to settings can lift, which is the shape `person` gives `pending-migration`. Write the reasoning in the record's doc comment.

**Move: `null`.** Requeueing lands on the same refusal, the same argument `pending-migration` and `unexpected` make (`:266-267`, `:302-304`). The remedies go in `says`, from the constant.

`JudgeWhen` (`packages/domain/src/proposal.ts:28-40`) and `BUILT_IN_FOR` (`judge.ts:483`) need nothing new. The refusal arrives as `merge-refused` like the other seven lane refusals (ADR 0120, `doc/decisions/0120-a-reason-is-a-type.md:483-485`), and a person is the floor there.

### 5. Docs

- **The ADR is 0120, not 0118.** 0118 does not list the merge refusals. 0120 does, at `0120-a-reason-is-a-type.md:483-485` (*"The seven lane refusals … are `dirty-base`, …"*). Under this repository's one-ADR-per-topic rule (`doc/README.md`), that is an edit to 0120: *eight*, with `base-protected` in the list. No new file.
- **The other two places that list the reasons:** `doc/reference.md:1766` and `doc/design.md:150`.
- **`doc/operating.md`'s onboarding section and `doc/tutorial.md` Part 2**, as the ticket says. Use the remedies wording from step 1, so the docs, the warning and the card match.

## Tests (unit half only)

- **Onboarding.** Pass `warnIfProtected` a stub `request` and capture what it logs. Assert:
  - `protected: true` from the branch read logs both remedies;
  - a ruleset holding only `deletion` and `non_fast_forward` logs no warning;
  - a branch read that throws logs *could not tell whether `main` is protected*.

  A test of `add()` itself would need `githubApp()` and the event store, so these cases pin the function rather than `add()`.
- **The lane.** Extend `fakeGit` in `packages/repo/unit/integrate.test.ts:31-53` with a `failPush` detail, in the same pattern as `failMerge`. Two cases:
  - With GH006 text, assert `reason === 'base-protected'`, that `calls.filter(push)` has length 1, and that the stored `detail` holds both remedies.
  - With `! [rejected] … (non-fast-forward)`, assert four pushes and `push-rejected`.

  This is the unit-level stand-in for `packages/repo/integration/integrate.test.ts:351`, which needs real git and is out of reach in a pass.
- **The domain list.** The `step-outcome` survival test from step 4.

## What the log will show

A refused landing appears as `IntegrationRefused` with `data.reason = 'base-protected'`. There is one `IntegrationAttempted` before it and **no** other `IntegrationRefused` between the two. That pair is how anyone reading `events` later can confirm the push was not retried.

The onboarding warning appends nothing. It is a line `add` logs, and there is no event to cite for it.
