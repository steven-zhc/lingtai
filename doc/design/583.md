## Design note: #583, triage status never reads a substituted input

There are two separate changes, one in the board and one in the daemon. Both follow one rule: an input that could not be read is passed along as *unknown*, and nothing decides from it.

### 1. The card: unknown is a word on the card, not a missing chip

**What happens today.** `loadBoard` turns a failed registry read into `[]` (`apps/board/src/lib/board.ts:972`, `loadAllProjects().catch(() => [])`). `declaredTriage([])` then returns an empty set (`:539-542`), every card gets `triageContextOf(false, daemon)` (`:1042`), and a wait with no attempt yet comes out `NotDeclared`. The card's `triage` field only carries `Queued | Running | Interrupted` (`:149`, `:602-603`). So `NotDeclared` becomes `null` there, and `page.tsx:184-187` draws the note's first line instead.

**The trap: "no chip" changes nothing anyone can see.** A card whose `triage` is `null` already shows only its fallback line, and that is exactly the symptom the review reported. So do not write unknown as `null`. Add a fourth value to the card's `triage` union, `'Unknown'`, and a matching entry in `TRIAGE_WORDS` (`apps/board/src/app/page.tsx:87`). Keep the wording neutral, something like *triage status unknown — the project list could not be read*. The card is still drawn and still sits in its column. Only the line changes.

**Unknown applies only where the answer reads `declared`.** In `statusOfFacts` (`packages/domain/src/wait.ts:921-929`), `Done`, `Running` and `Interrupted` come from `facts` and `daemonStartedAt` before `declared` is ever looked at. Only the final `Queued` / `NotDeclared` branch depends on it. So:
- an advised `Done` result keeps its cause chip when the registry read fails;
- a started attempt still says Running or Interrupted;
- only a wait with no `TriageStarted` turns into `'Unknown'`.

A simple way to write this in `cardTriageStatus` (`board.ts:528`): when `declared` is unknown, evaluate `triageStatus` once with `true` and once with `false`. If the two agree, that is the answer. If not, the card says `Unknown`.

**Leave the domain alone.** `triageStatus`'s context stays `{ declared: boolean; … }`, and `TriageStatus` gets no new tag. 0118 §1's order is unchanged, and the daemon and the page keep calling it with a boolean. Widen only the board's card path:
- `TriageContext.declared` becomes `boolean | null`, or `toCard`'s parameter becomes a board-local type.
- `task.ts:1779` and `currentTriageStatus` (`task.ts:1759`) still hand the domain a boolean. Watch that `triageContextOf` widening does not leak into `task.ts:73`'s import and break `pnpm typecheck` there. Keep a boolean signature for the page, and a separate entry point or overload for the card.

**Where unknown comes from.** In `loadBoard`, turn `loadAllProjects()`'s rejection into `null` instead of `[]`:
- Everything else that used `registered` (the queue, the filter options) still gets `[]`, as it does today. This ticket is about triage, and it does not fix the Queued column going quiet on the same failure.
- `triageDeclared` becomes `null` without calling `declaredTriage`.
- At `:1042`, pass `triageDeclared === null ? null : triageDeclared.has(t.project)`.

That is still one registry read per render, never one per card.

**Do not loosen `declaredTriage`'s own failure.** An unreadable *recipe* still makes the board reject, as its doc comment requires (`:532-538`, *"answering `false` for it would let the page … say `Queued` about a wait the card said nothing of"*). Unknown covers the registry read only.

**Test**, in `apps/board/unit/triage-context.test.ts` alongside the existing `toCard` cases:
- A card with an unknown declaration and no attempt has `triage === 'Unknown'`.
- With a started attempt it still reads `Running` or `Interrupted`.
- With a `TriageAdvised` result it still carries `cause`.

The `loadBoard` wiring itself only runs under integration, so the unit claim that stands in for it is the builder: given unknown, the card never reads `NotDeclared`.

### 2. The daemon: nothing is decided until the start time has been read

**What happens today.** `daemonStartedAt` is a `Date` read once (`apps/cli/src/lingtai.ts:696-698`). When `readStatus` rejects, or the row belongs to another pid, it falls back to `new Date()`, the host clock, and that value is captured by both `daemonTriagePorts(daemonStartedAt, …)` call sites (`:937`, `:977`) for the life of the process.

**Retrying once is not enough, and a fallback for that one call reproduces the bug.** `catchUpChangedTriage` pins the recipe hash once a scan succeeds (`apps/cli/src/triage.ts:192-202`). A single catch-up that runs on a skewed host clock reads the interrupted attempt as `Running`, skips it, and pins the hash. That project is never scanned again until its `triage:` changes. So the rule is: **while the start time is unknown, catch-up fails instead of skipping.**
- Make the port `daemonStartedAt: () => Promise<Date>` in both `TriageTriggerPorts` and `CatchUpTriagePorts` (`triage.ts:88-103`).
- `catchUpTriage` awaits it before scanning. A rejection reaches `scanTriage`'s catch (`lingtai.ts:931-942`), the hash stays unset, and the per-pass scan (`lingtai.ts:1037`) asks again on every pass until it succeeds.

**The resolver.** Put it in `triage.ts` so it can be unit-tested; `lingtai.ts` is not. It is a small memo around `readStatus`:
- It resolves to `row.startedAt` only when `row !== null && row.pid === process.pid`.
- It caches the first such success.
- It rejects, without caching, on a failed read or a row from another pid. Neither case falls back to the host clock any more.

`lingtai.ts:696-698` becomes building this memo; the `.catch(() => new Date())` is deleted.

**The live trigger waits too, which is less obvious.** `onWaitStarted` only ever enqueues a `Queued` wait, and `Queued` never reads `daemonStartedAt`. But the row's `started_at` is dated by the *first beat that lands*, not by the process start:
- `control.ts:527-531`: *"Cleared by a beat that landed … so a first beat that fails leaves the next one fresh"*.
- `postgres.ts:108` and `sqlite.ts:133`: `started_at` moves only on a `fresh` beat.

So if the first beat fails, a triage attempt this daemon starts before a later beat lands carries an earlier `TriageStarted.at` than the eventual `startedAt`. Catch-up would then read the daemon's own attempt as `Interrupted` and pay for a second one. Therefore `onWaitStarted` awaits the same port, and on rejection it logs and returns. This loses nothing, because the catch-up has not pinned the hash and will find the wait `Queued` on the next pass.

**Tests**, in `apps/cli/unit/triage-catch-up.test.ts`. The existing `daemonStartedAt: startedAt` ports (`:50`, `:208`, `:229`) become `async () => startedAt`.
- **The new case:** the port rejects first and then resolves. A `TriageStarted` older than the resolved time:
  - On the first `catchUpChangedTriage`, it rejects, the hash is not set, and `run` is not called.
  - On the second, `run` is called for the `Interrupted` attempt.
- **The resolver's own test:**
  - a row for another pid rejects;
  - a failed read rejects and a later successful read resolves;
  - once resolved, it never reads again.

**What would settle it in the log:** after a daemon start whose first beat failed, look for a `TriageStarted` on the interrupted wait with `attempt: 2` (re-bought by catch-up), or a `WaitTriaged` with `result._tag: 'TriageFailed', why: 'interrupted'`. Either one, dated after the `ConductorStarted`, means the interrupted attempt was not skipped.
