## The decision the ticket gets subtly wrong: the `report` guard

Today `report` already carries `if: always() && github.ref == 'refs/heads/main'` (`integration.yml:115`). A `pull_request` run's `github.ref` is `refs/pull/<n>/merge`, so a PR run would already skip `report` with no edit.

Fix 2 suggests `if: github.event_name != 'pull_request'`. Do not swap the ref check for that. Taken alone, it would let a `workflow_dispatch` on any branch other than `main` comment on #1124 or open the held issue. Today that cannot happen, because the ref check refuses it. Keep both conditions:

```
if: always() && github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
```

The event check states the intent where a reader looks. The ref check keeps the guarantee #963 gave: only `main` reports. Update the comment at `:18-19` to say a PR's red run shows as a failed check on the PR and nowhere else.

## Concurrency

Use `group: integration-${{ github.ref }}`, as the ticket says. For a PR that is `refs/pull/<n>/merge`, so a new push to the PR cancels that PR's older run, and `main` keeps its own group. `push` and `workflow_dispatch` on `main` still share one group and cancel each other, as `integration-main` does today (`:27-29`). Keep `cancel-in-progress: true`.

A cancelled PR run leaves its two legs as `cancelled`, not green. Per the ticket's *Null and unknown* edge, the PR's CI step waits for the run on the latest head.

## Triggers

Add `pull_request: branches: [main]`. Don't list `types:`; the defaults (`opened`, `synchronize`, `reopened`) are what we want. A push to `steven-zhc/studio` while its PR into `main` is open re-runs the legs through `synchronize`. That is the PR run the ticket asks for, not the per-push run its *Out of scope* excludes.

Job permissions stay `contents: read` on the legs and `issues: write` on `report` only (`:31-32`, `:117-119`). A skipped `report` on a PR is harmless: the recipe filters by check name (`required` "names the checks that count", `packages/recipe/src/recipe.ts:3020-3021`), and `report` is not in the list now or after Fix 4.

## "Required" means the recipe, not branch protection

The comment at `integration.yml:15-16` (*"Not a required check on `main`: the merge lane lands by `git merge` and a push, never a pull request"*) and the one at `check.yml:15-18` say two things, and only one of them still holds:

- **Still true:** the merge lane lands on `steven-zhc/studio` by `git merge` and a push (`packages/actions/src/merge-action.ts:47`). So no GitHub branch-protection rule may require these checks on `studio`, and this ticket adds none anywhere.
- **No longer true:** "never a pull request". In team mode, `main` moves only by a PR. What a PR into `main` waits on is Lingtai's own PR CI step, driven by `pr.ci.required` in the conducting recipe. GitHub's required checks play no part.

Rewrite both comments to say exactly that. In `check.yml:10-12`, *"belongs to T11, after the merge"* becomes: after the merge lane lands on `studio`, on the PR into `main`, and again on the push to `main`.

## What can and cannot be checked before the merge

Nothing in `pnpm test` reads `.github/workflows/*.yml`. `git grep` finds those files named only in comments, docs and README badges. So the first four `Done when` boxes have no unit-level stand-in:

- **"A PR shows the two checks"** is shown by this ticket's own PR into `main`, which should show `integration (sqlite)` and `integration (postgres)`. Both are expected to be red until the fix ticket lands.
- **"No comment on #1124"** is shown by that same red PR run listing `report` as *skipped*, with #1124's comment count unchanged.
- **"A push to `main` still reports"** can only be seen after the merge.

Inside the pass the agent can check two things:

- **The YAML still parses.** Read it with any YAML parser, and make no file change for it.
- **The expressions are right**, by reading them.

`pnpm typecheck` and `HOME=/nonexistent pnpm test` stay green trivially, and `effect-ratchet.baseline.json` cannot move. The PR body should say this plainly instead of ticking the first three boxes.
