# Design: #604, closing a split parent at claim

## Where it goes

There are two halves, and they belong in two files. `claimTicket` (`packages/conductor/src/claim.ts:90`) can reach only the event store. Its options are `runId`, `worker`, `title`, `kind` and `store` (`:28-49`). It cannot reach GitHub and it cannot resolve a recipe. The close needs both, because `end` runs on every terminal outcome. `close.ts:71-72` says so: *"And `end` runs, because `end` is the point that runs on every terminal outcome"*, which is 0044.

1. **`claim.ts` decides.** Give `ClaimOptions` an optional `children?: Pick<Tickets, 'getIssue'>`. When it is given, `claimTicket` checks the split after the `held` and `not-claimable` checks (`:97-106`) and before the append (`:108`). The check is:
   - If the stream has a `TicketSplit`, call `getIssue` for exactly its `children[].number` and nothing else.
   - If any child is open, return a new refusal, `{ reason: 'split-open', open: number[] }`.
   - If every child is closed, return `{ reason: 'split-done', waitId, children: { number, stateReason }[] }`.
   - In both cases, append nothing.

   When `children` is omitted, behaviour is unchanged. The ten calls in `integration/claim.test.ts` keep working untouched.
2. **`conduct.ts` acts.** In `take` (`conduct.ts:2165`), pass `children: options.client` into `claimTicket` (`:2204`). The `getIssue(options.issue)` at `:2190` stays where it is.
   - On `split-done`, call `closeHolding` from `close.ts:140`. Pass `by: 'conductor'`, a `reason` naming the children, `state: options.project`, `client: options.client`, and `recipe` returning the recipe this pass already resolved (`:638`).
   - Use `closeHolding`, not `close()`. `close()` wraps it in `deciding` → `createFileLocker()`, which is the filesystem and so cannot be unit-tested (`close.ts:134-138`). `closeHolding`'s own version check already turns a concurrent move into `ok: false` (`:215-224`).
   - Once `closeHolding` returns `ok`, post the comment through `tellGitHub` with `{ kind: 'comment' }` (`tell.ts:173`), so that `IssueUpdated` or `IssueUpdateFailed` is on the log. The comment goes **before** the explicit close: it has no record of its own to retry from, and a close that fails is finished later by reconciliation, which would otherwise close the issue without ever saying why.
   - Return `{ notClaimed: JSON.stringify(refusal) }`, as every other refusal does (`:2213`).
   - Do not open the run log and do not set `took` or `onStream`. No run existed.

**"Release it without running" means refuse, not claim-then-release.** The check sits before the append, so nothing is held and there is nothing to give back. A `TicketClaimed` followed by a `TicketReleased` would put a run with no work on the board and in `attempts`. `split-open` is that refusal. It is also not supposed to happen: the split holds the parent with a blocked-by on every child (`doc/design/600.md:29`), so `runnableNow` passes over it as `blocked-by` before claim (`discover.ts:131-150`). Reaching `split-open` means somebody removed a GitHub link.

**A child read that throws closes nothing.** `claimTicket` answers `{ reason: 'split-unreadable', detail }`, and `take` returns it as `notClaimed` like any refusal. It must not throw: `take` reads a throw as `mayHold` and sets `onStream`, and the cleanup would then release a stream this run never claimed — silently undoing a hold a person placed meanwhile. Nothing was appended, so the worst outcome is a pass that took nothing. The other path, a partial read treated as *all closed*, is the silent failure this ticket must not have.

## Fold the split into `TicketState`

`claimTicket` already reads the stream and reduces it (`claim.ts:94-95`). Add `split: { waitId, children: SplitChild[] } | null` to `TicketState` in `packages/domain/src/ticket.ts`:

- Assign it from a `TicketSplit` event; the last one wins.
- Do **not** add `TicketSplit` to `LIFECYCLE_EVENTS` (`ticket.ts:214-221`, *"`closed` has to absorb exactly these and nothing else"*).

`doc/design/600.md:37` deferred this work to this ticket by name: *"Folding the split into `TicketState` belongs to the close-rule ticket."* Read the numbers from that field only. Never read them from the body or from GitHub's sub-issue list (`doc/decisions/0118/Split.dc.html:313`).

## "Not planned" needs a field that does not exist yet

The ticket wants the comment to say a child was closed as *not planned*. Nothing returns that today:

- `Issue` has `state: 'open' | 'closed'` and no reason (`packages/github/src/client.ts:131`).
- `toIssue` drops `state_reason` (`:494-520`), although `closeIssue` writes it (`:385-388`).

Add `stateReason: 'completed' | 'not_planned' | null` to `Issue`, read from `raw.state_reason`. Add the same field to `TicketDetail` (`discover.ts:64`), required and nullable, following the `dependencies` rule in `discover.ts:49-54`.

- **`memoryTickets`:** store the `reason` that `closeIssue` is given (`test/memory-tickets.ts:118` ignores it today) and answer with it. The "not planned" test needs this.
- **`dbTickets`:** answer `null`. Its own header says *"`closeIssue`'s `reason` is accepted and not stored"* (`db-tickets.ts:32-33`).
- **The comment:** render `null` as "closed (reason not reported)", never as "completed".

## The comment

Name the split's `waitId` and every child with how it closed, for example *#161 completed, #162 not planned*. Then say that a not-planned child counts as closed, and that work still wanted is a new ticket: `closed` is absorbing (`close.ts:65-69`).

## Watch out

- **Only `backlog` reaches the check.** `WaitResolved{Split}` does not move the lifecycle (`ticket.ts:372-377`), so a stream that ends there is still `blocked`. `claimTicket` refuses it as `not-claimable` before the split check runs. `Split.dc.html:308` says the split ends *"as a requeue"*. That requeue belongs to the split writer, and no writer exists yet: the only references to `TicketSplit` are the schema, the test helpers and the projector. Do not add the requeue here. Do not run the check on a `blocked` stream either: `closeHolding` would then try to resolve a wait that is already resolved (`close.ts:185-213`).
- **The parent's GitHub issue is closed by `take` itself, whatever the recipe's `end` says.** `closeHolding` appends `TicketClosed` plus what `end` resolved to (`close.ts:172-176, 232-240`), and `end: []` or a close restricted to `when: landed` would leave the issue open under a terminal event. So `take` then calls `tellGitHub` with `{ kind: 'closed' }` after the comment; a failed close is `IssueUpdateFailed` on the log.

## Tests (unit; nothing here needs the integration half)

- **`claimTicket`, in a new `packages/conductor/unit/claim-split.test.ts`:** use `createMemoryEventStore`, `memoryTickets`, and `aSplit` (`packages/domain/test/events.ts:83`) on a fresh stream. A fresh stream stays `backlog` because `TicketSplit` is not a lifecycle event. Cover:
  - all children closed → `split-done`, with the stream version unchanged;
  - one child open → `split-open`, nothing appended;
  - a hand-attached issue → wrap `getIssue` in a spy and assert it was called with exactly the recorded numbers, while an open issue that the parent's body names does not stop the close;
  - `children` omitted → claims exactly as before.
- **The whole path:** a whole-pass case beside `conductor/unit/conduct-a-whole-pass.test.ts`, using `test/one-pass.ts`. Assert that no agent is dispatched, that `TicketClosed` is on the stream with `by: 'conductor'`, and that the comment body names both children and says "not planned" for the one closed that way.
- **The fold:** a small case in `packages/domain/unit` showing `split` is set by `TicketSplit` and that a second `TicketSplit` replaces the first.
