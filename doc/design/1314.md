# #1314 design note: what a person can do when a PR waits on them

## What is already in place

- `conflictRoundsLeft(state, merging, commit, bound, granted = 0)` (`packages/domain/src/pr.ts:346-355`) already takes a `granted` argument. Its one caller (`packages/conductor/src/pr-resolve.ts:534`) does not pass it yet. The bound itself comes from `ceiling.attempt.conflictResolutions` (`pr-resolve.ts:236`).
- `ConflictEnd` (`packages/domain/src/events.ts:2586-2599`) already carries `paths`, `ours`, `theirs`, `unread`, `roundsUsed` and `last` on `PrWaiting.conflict`. The view reads these and never reads git, as that comment says: *"#1314 reads this and never git."*
- **#1339 has not landed.** `PrWaitReason` (`events.ts:2570-2580`) has no `ci-*` value, and `IN_PROGRESS_STEPS` stops at `open` (`packages/conductor/src/pr.ts:405-410`: *"`ci` (#1339) … after"*).
  - The retry below does not depend on the wait's reason, so CI waits get it for free once #1339 adds them.
  - The Done-when about a `ci-red` wait is tested with a wait that exists today and has the same shape: unchanged head, any reason, for example `sync-red`.
  - `prWaitOf`'s CI branch (the failing checks and the `lingtai pr retry` line) belongs to #1339. Here, every reason other than the `sync-*` conflict family takes the `{ since, reason, detail }` branch.

## The PR state gains four fields (`packages/domain/src/pr.ts`)

| field | set by | cleared by | why |
|---|---|---|---|
| `pending: { kind: 'retry' \| 'back', by, seq } \| null` | `PrRetryRequested`, `PrBackRequested` | `PrInProgress`, `PrWaiting`, `PrClosed` | The serve needs to know a request has not been answered yet. `servePr` only walks `in-progress` (`pr.ts:493`, `:552-555`), so a waiting PR is otherwise never served. |
| `grants: PayloadOf<'PrRoundsGranted'>[]` | `PrRoundsGranted` | never (same rule as `rounds`, 0108 §8) | `grantedFor(state, merging, commit)` sums them and is passed as `granted` at `pr-resolve.ts:534`. |
| `adopted: string \| null` | `PrHeadAdopted` | `PrStepDone { step: 'build', headSha: adopted }` | Closes the build-step trap described below. |
| `waitSince: Date \| null` | `PrWaiting` (its `event.at`) | when `wait` clears | This is the view's `since`. `wait` has no time today (`pr.ts:68`). |

`PrHeadAdopted` sets `lastPushed` and `target` to `head`.

**One slot for requests.** `grantTransition`, `retryRequestTransition` and `backRequestTransition` each refuse by name while `pending !== null`. The sentence is along the lines of *"a retry is already asked for; lingtai pr says when it is served"*. This answers the two-requests-at-once edge, and it means a grant appended after an unserved back can never revive a PR that is being closed.

## The grant: the event moves the PR itself, with no answer event

The `PrRoundsGranted` reducer sets `status: 'in-progress'` and `wait: null`. This mirrors what `withStep` already does when a person's answer takes effect (`pr.ts:106-110`).

The wait was raised at `sync`, which is the first step, so `walkPr` resumes there (`pr.ts:494`). The sync step merges `main` again:
- if `main` is still at the same commit, `resolveRounds` finds `left = bound + granted - used > 0` and dispatches round `used + 1`;
- if `main` moved, the commit is new and the count starts from the bound alone.

Nothing else is needed for the *"belongs to one commit"* trap, as long as `grantedFor` filters on both `merging` and `commit`.

Refusal rules for the grant, beyond the ticket's list:
- **Refuse when `wait.conflict` is null.** That is the case where no resolver is configured: `pr-sync.ts:136` waits `sync-conflict` with no `conflict` field. Rounds would buy nothing there, and the PR would wait again at once. The sentence is *"no agent resolves conflicts for this project — fix it by hand, then lingtai pr retry"*.
- **`merging` and `commit` must match `wait.conflict`.** `grantPrRounds` takes both, so a stale page is refused. The CLI's `lingtai pr rounds` reads them from the state it just read.
- **A merge-back conflict never reaches a grant.** It is `PrMergeBackFailed` on an `in-review` PR, not a wait (that case is out of scope).

`PR_EVENTS` (`packages/daemon/src/work-loop.ts:119`) gains the three request types. `serve` already dispatches anything on a `pr-` stream (`pr.ts:811-812`).

## The retry is served before the walk, and always gets an answer

In `servePr`, under the permit and before `walkPr`: when `pending?.kind === 'retry'`, run `serveRetry`.

**Where it runs.** It is one turn of `(ports.lane ?? landingLane).through(integrationStream(project, prBranch), { pr: prStream(project, n) }, …)`, the same call as `pushStep` (`pr.ts:293-299`). Every read and both appends happen inside that turn.

**What it reads.**
1. `remoteSha` of `refs/heads/<prBranch>` (`pr-git.ts`, exact-ref match).
2. If the branch is present, `fetchInto` it to a new `fetchedRef(n, 'head')`. Widen the union at `pr-git.ts:10` to include `'head'`, and drop the ref in an `ensuring`.
3. `merge-base --is-ancestor <frozen> H`, reading only its exit code.

**Branch absent, or the same as `lastPushed`, or never pushed and absent.** Append `PrInProgress { because: 'retry' }`.

**`H` does not hold the frozen commit.** Append `PrWaiting { step: 'sync', reason: 'sync-rewritten', … }`.

**Otherwise.** Append `PrHeadAdopted`, then `PrInProgress { because: 'retry' }`.

**A failed read.** Append `PrWaiting { reason: 'sync-unknown' }` with git's text.

**The answer is always an append, and that needs one change.** `waitTransition` drops a wait with the same step and reason as the current one (`pr.ts:421`). A retry on a `sync-rewritten` wait that fails the frozen check again would therefore append nothing. `pending` would never clear, and the CLI would wait for an answer that never comes. So `waitTransition` skips that de-duplication while `pending !== null`.

**`retryTransition` is new.** It requires `status === 'waiting'` and a pending retry. `restartTransition` only accepts `in-progress` (`pr.ts:282`). Both build the same `PrInProgress` payload from the freeze. `PrInProgress.because` gains `'retry'` (`events.ts:2553`).

**The `PrInProgress` reducer still resets `target` to `frozenSha` (`pr.ts:141`), and that is fine.** `startOf` (`pr-sync.ts:65-76`) finds `frozen` is an ancestor of `lastPushed = H` and starts the sync from `H`. The remote check at `pr-sync.ts:110` then sees `at === lastPushed`. Do not change that reducer.

## The trap: the build step would wave an adopted head through unbuilt

When `main` is already in `H`, the sync records `BranchSynced { how: 'already', head: H }` (`pr-sync.ts:117-123`), so the target becomes `H`. `buildStep` then hits *"Nothing was merged: the sync's commit is the target, and it was built when it was made"* (`pr-sync.ts:202-203`) and records `build` done without building anything. That comment is true of a commit Lingtai made, and false of a commit a person pushed.

The fix:
- Take that shortcut only when `target !== state.adopted`.
- For an adopted target, build `target` itself with `ports.build(… sha: target …)`.
  - Red: wait `sync-red` with the new evidence.
  - Green: record a plain `PrStepDone { step: 'build', headSha: target }`, not `BranchSynced`. `H^2` is not a `main` commit when `H` is not a merge, so `mainCommit` cannot come from `${merge}^2` (`pr-sync.ts:217`) on this path.

**How this reconciles the ticket.** The ticket's table says `PrHeadAdopted` is recorded *"once it builds green"*, while Fix 2 appends it before the walk. This note follows Fix 2's order, and *"once it builds green"* holds because nothing gets past `build` unless it is green.

**The person retries a red `H` without pushing.** `H === lastPushed`, so the retry only appends `PrInProgress`. `adopted` is still `H`, so `H` is built again rather than skipped.

**`H` lacks `main`.** The sync merges `main` into `H` and the normal build path builds that merge. `adopted` never needs to be consulted.

## Back

**Requests.** `backRequestTransition` refuses `requested` and `in-progress`. It accepts `waiting` and `in-review`.

**Serving.** `serveBack` runs in `servePr` before the walk and before `mergePrBack`. Once `PrClosed` is appended, `mergeBackOwed` is false (`pr-sync.ts:248`), so nothing runs after it.

**`closedTransition` cannot record back as it stands.** It refuses when `state.host === null` (`pr.ts:414`), and back must append `PrClosed` with no host number. Add `backClosedTransition`, which allows `host === null` only when `pending?.kind === 'back'`. Leave the sweep's guard as it is: the sweep still only learns a close from the host.

**`headSha`.** Use `lastPushed ?? target ?? frozenSha`.

**`closePull(number)` on the `GitHub` interface** (`packages/github/src/client.ts:330-336`, implemented near `:1005-1016`):
- Every fake that implements `GitHub` in the unit tests has to gain this member.
- Do **not** wrap it in `bounded`'s read timeout (`pr.ts:620-628`). It is a write, like the push at `pr.ts:613-616`.
- A `GitHubFailed` with status 422 whose message says the PR is closed counts as closed. Any other failure fails the serve, nothing is recorded, and `pending` stays set.

**Resume.** `servePendingPrs`' filter (`pr.ts:573`) adds `pr.pending !== null`. Without it, a back or retry whose serve failed is only retried when some later event lands on that stream.

## The view

The signature is `prWaitOf(state, { project, checkout: string | null, conflictResolutions: number })`. It is pure, but it is not *"PR state alone"*: the bound and the checkout are recipe facts, the state does not hold them, and a grant changes the bound.
- The caller passes `ceilingOf(recipe).attempt.conflictResolutions` (as `pr-resolve.ts:235-236` reads it) and the local checkout path. I did not find where the recipe holds that path, so the CLI resolves it, and `null` means no `-C`.

**Fields.**
- `roundsAllowed = conflictResolutions + grantedFor(state, c.merging, c.commit)`.
- `roundsUsed` is counted from `state.rounds`, not from `c.roundsUsed`, so a grant that is still being served reads correctly.
- `mainAhead = c.theirs.length`, or `null` when `c.unread?.theirs` is set.
- `ours` and `theirs` are `null` (unknown) when their `unread` side is set, or when `conflict` is absent because the wait predates #1313's field. Never return `[]` for either case.
- `ours[].issue` maps `ConflictEnd.ours[].number`.

**Branches.**
- `sync-conflict` and `sync-locked` waits that carry `conflict` get the full view.
- Any other reason gets `{ since, reason, detail }`, plus `commands: [retry line]` only for the `sync-*` reasons this ticket's retry ends.

**What reads it.** `lingtai pr` (`apps/cli/src/pr.ts:97-103`) prints it under the PR line in place of the one-line `waiting on you at …`, and adds it to the JSON next to `wait`.

## The CLI

- `prRetryVerdict`, `prRoundsVerdict` and `prBackVerdict` follow `prSubmitVerdict`'s loop (`apps/cli/src/pr.ts:151-208`).
- The conductor's answer is the first event whose seq is after the request's that clears `pending`, or, for a grant, the first `SyncRoundStarted` or `PrWaiting`.
- When there is no answer, they print the same sentence about who is conducting.
