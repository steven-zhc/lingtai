## Decision 1: a local team project follows 0130 §2, not the ticket's prefill

The ticket fills the field with `defaultPersonalBranch(login, host)` in every case. 0130 §2 says otherwise for a local project: *"`branch.main` is the branch checked out when the project is added, and `branch.personal` defaults to `lingtai-base`"*. The CLI does that: `fallback: … LINGTAI_BASE` at `first-project.ts:~705`. 0130 §3 adds that on the local store *"mine"* is *"every ticket"*, so a local project needs no login.

On the board, a local team form is therefore:

- `base` (meaning `branch.main`) is the checked-out branch, read again by `trusted` with `git symbolic-ref --short -q HEAD`. Today `trusted` sets `LINGTAI_BASE` for every local form (`read/actions.ts:41`); keep that for solo only.
- `personal` is prefilled with `lingtai-base`.
- There is no login field and no *Takes issues assigned to…* line. That line reads *Takes every ticket in this project* instead.
- `refusalOf` asks for a login only when `target.kind === 'github'`. The ticket already scopes it that way.

A GitHub team form is as the ticket describes.

## Decision 2: where the keys are written

Every key is written in `setupChanges` (`packages/setup/src/setup-answers.ts`, from about line 166), never in the page or in `addProject`:

- **Team:** `mode: team`, `branch.personal`, and `assigneeChanges({ login, take: 'mine' }, rawClaim)` (`packages/recipe/src/answers.ts:173`). That is the same call the CLI makes at `recipe-flow.ts:329`.
  - `rawClaim` is `steps.claim` from the draft. `answersFor` (`add-from-page.ts`, *"The answers, written in full when a recipe is already on disk"*) already holds that draft, so `setupAnswers` takes `rawClaim` as a third argument.
  - On a local team project, write no assignee, as the CLI writes none.
- **Solo with `rewrite`:** `mode: solo` is written explicitly, for the reason the function's doc gives: a failed earlier attempt's value would otherwise stand. Also check whether `setRecipe` can remove `branch.personal`. 0130 §2 says it is *refused in solo*, so a retry from team to solo must not leave it behind. Settle this with a test, not by assumption.
- **Local team:** `landOnBranchChanges(form.base, [])` now gets `branch.main`, the checked-out branch, as at `first-project.ts:~935`.

## Decision 3: making the branch is a port of `addProject`, run inside the lock

Add `AddPorts.makePersonal: (form) => Effect<'made' | 'exists', Error>`. Call it in `checkAndWrite` after the `alreadyAdded` check and before `applySetup`, only for a team form. That keeps it inside `exclusiveAdd`, before the write. A failure becomes `{ ok: false, say }`, with no `keptSentence` because nothing was kept. The fake port lets the Done-when unit test run with no git and no GitHub.

The live port, built in `livePorts`:

- **GitHub:** first `branchExists(personal)`. If it exists, the answer is `'exists'`. Otherwise call `refSha(base)` and then `createBranch`, as in `makePersonalBranch`. Read a 422 *Reference already exists* from `createBranch` as `'exists'`; this covers the stale-page case in the ticket's edges. If the existence read fails at Add, refuse with *could not read whether `<name>` exists on GitHub — nothing was made*, as the CLI does at `recipe-flow.ts:296-299`. Do not create blind. The ticket's *"Add is still possible"* holds only for the message shown while typing.
- **Local:** `rev-parse --verify refs/heads/<personal>^{commit}`. If it is absent, run `git branch <personal> <base>`, using the `gitIn` helper at `add-from-page.ts:62`.

`liveRegister`'s local half (`add-from-page.ts:~340-353`) makes `LINGTAI_BASE` after the write and reads `form.base`'s tip as `fromSha`. In team mode it must not make anything. It must read the tip of `branchOf(resolved.recipe)`, which is `branch.personal` in team mode, because `addLocalEffect` already receives `base: branchOf(...)`. Today it reads `form.base` twice; change both reads to the resolved branch, and keep the `LINGTAI_BASE` creation for solo only.

The login comes from the server, never from the page, except where nothing on the server can name it. On a `gh` machine, `trusted` reads the signed-in login and overrides the form. `add-github.ts:308` (`access.login`) shows where the CLI gets it; reuse that read, as an Effect, in `packages/conductor`, not in the action. On an App machine the typed login is taken and checked against `GITHUB_LOGIN`, the pattern `recipe-flow.ts:271-273` uses.

## Decision 4: the check while typing is one shared function

Put the pure half in `@lingtai/setup`: `personalRefusal(name, base): string | null`, which is `branchNameRefusal` plus the ignore-case comparison with `base`. Both `refusalOf` and the `checkPersonal` server action call it.

The *use `<fix>`* suggestion is a function of the name: run it through `machineName`'s rules part by part, splitting at `/`. That turns `Steven's MacBook Pro` into `steven-s-macbook-pro`. Show it only when its own result passes `branchNameRefusal`.

`checkPersonal` takes only the target and the name, and reads `base` and the login itself as `trusted` does. Its existence read has the `'unreadable'` result, which becomes the *could not check* line.

The client keeps a request counter and drops any answer that is not the latest. Do not use an `AbortController`: a server action cannot be aborted.

## Effect ratchet

Write `makePersonal`, the login read and `checkPersonal`'s body as Effects. `checkPersonal` is an `async` export because a server action must be one. Counting it in `apps/board` is the cost of the action, as `previewAdd` and `addRepository` are already counted. Run `pnpm test`'s `effect-ratchet.test.ts` before committing. If `apps/board`'s `async` count rises by one, move an existing `async` in that package to an Effect in the same commit rather than raising the baseline. Do not touch `effect-ratchet.baseline.json` upward.
