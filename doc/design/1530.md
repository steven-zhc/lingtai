# #1530 design note: the runner's three extensions, the view, the moved helpers and the pieces

Line numbers are for this worktree at `eef55c166`. `doc/design/1529.md` (`b1901c1f4`) §1, §3, §4 and §6 is the spec. This note covers only what it and the ticket leave open, plus three places where today's code has a second copy the ticket does not name.

## 1. The runner (`packages/setup/src/setup-list.ts`)

- **`confirm.declined`.** The type at `:70` widens to `string | ((ctx: C) => string)`. It is resolved at the one place it is read, `:317`. Nothing else changes.
- **A confirmation answers `yes` on the flag only.** In the condition at `:269` and the `if (!defaults)` at `:270`, change `defaults` to `input.defaults`. Leave the local `defaults` everywhere else:
  - `:264` (`noTerminal`) keeps it;
  - the switch branches at `:272` and `:275` keep it;
  - the `DefaultsMode` handed to `systemDefault` at `:252` keeps it.

  The result: after a switch answered yes at a terminal, a `confirm` reaches its asker. Without a terminal, the switch never set the local `defaults`; that is the `:275-286` branch, *"No terminal to ask on: the walk goes on, and nothing is written (#433)"*. So a confirmation there is still refused at `:270` naming `--defaults`. The existing test at `setup-list.test.ts:92-98` (*answers yes under --defaults*) passes `defaults: true` on the input, so it still holds.

  The new test: `[sw, c]` with `interactive: true` and askers `{ sw: answering('yes'), c: answering('no') }`. Expect `refused` to be `c`'s declined words and `entries[1]` to be absent. That proves the confirmation was asked.
- **`systemDefault` may refuse.** Widen the return at `:52` to `string | null | { refused: string }`. Keep calling it where it is called today (`:251-252`), so the `mode` the existing test at `:127-137` asserts is unchanged. Split the result into two locals:
  - `system`: the string, or null when it refused;
  - `systemRefused`: the refusal, or null.

  `systemRefused` is returned in one place only. That is the `defaults || !input.interactive` branch (`:287`), when `fallback` is null (nothing in force answered), checked before the generic *"needs an answer: pass …"* refusal. Everywhere else it is dropped:
  - **A flag answered:** `:265` runs first.
  - **Something in force:** `inForceAnswer` is non-null, so `fallback` is non-null.
  - **A confirmation or a switch:** these never read `system`.
  - **At a terminal:** the asker answers, not the default, so it is handed `default: inForceAnswer` (null), as today's `--main` question is when `defaultBranch()` answers null. In that case `recipe-flow.ts:346` sets `detected: mainBranch` to null and the prompt draws no bracket (`question.ts:162-164`).

  This is the reading of *"only where the default would have been the answer"*: at a terminal the default is only the bracket.

  The new test covers three runs of one question whose `systemDefault` refuses:
  - with its flag: written, no refusal;
  - with `interactive: true`: the asker is called with `default: null`;
  - with neither: `refused` is the port's words.

  `machine-list.ts:204`, `:264`, `:320` and `:387` return strings, and a wider return type still accepts them.

## 2. The view (`packages/project/src/draft.ts`)

- **The overlay loop must exist once.** `replace` and `dropOldBase` are private to `packages/recipe/src/emit.ts` (`:293`, `:148`). Copying the `:178-184` loop into `draft.ts` would leave it in two places.
  - So `emit.ts` exports one function, `overlaid(existing: string, changes): Document`. It does the `read`, the loop and the `dropOldBase` line (`:172`, `:178-184`). `editRecipe` calls it.
  - `editRecipe` keeps its own two throws (`:173-174`), its blank-line pass and `Recipe.parse` (`:193`).
  - The view calls `overlaid` and none of those.
- **`projectView(start, pending)`.**
  - `start` is `Pick<RecipeDraft, 'text' | 'path'>`. The tests can then hand it a literal object, with no `ProjectFiles` layer (compare `draft.test.ts:8`).
  - `pending` is read **live** at every call, with no snapshot or cache. #1531's `ctx.pending` grows as each entry writes, and a view built before the first entry must see every later change.
  - A start whose `text()` is null overlays onto the base `editedText` uses (`packages/recipe/src/write.ts:59`, `` `version: ${RECIPE_VERSION}\n` ``). That way `get` and `resolved()` agree about the same document.
- **`get` never throws.** If the starting document is not a mapping, the overlay's `setIn` would throw. In that case `get` answers null at every path, and `resolved()` answers null too. `draft.set` refuses such a text (`emit.ts:174`), so it is reachable only from a file broken by hand. A view must never throw, because a catch around it would turn every later read into an absent value (1529 §3).
- **`resolved()`** returns `ResolvedRecipe | null`. It is the `:66-72` chain without `orderSteps`/`commentWritten`, which change the layout and not what resolves. Every throw becomes null.
- **Tests:** a new `packages/project/unit/project-view.test.ts` covers:
  - overlay;
  - delete (`value: undefined`);
  - later-wins at one path;
  - a change pushed onto `pending` *after* the view was made, which `get` must see;
  - `resolved()` null over a null start with no `env.plantAt` seed (`recipe.ts:3307`, `plantAt: z.string()`, has no default).

## 4. The pieces: where the words live

**A piece owns its words, and its caller owns only `given`, `current`/`fallback`, `validate` and `kept`.** `validate` is always a parameter and never baked in. The old `ask*` passes the #1528 check (`project-checks.ts`), and #1529's asker will pass `d.question.validate`.

`askModel` (`agents.ts:103`) is a mechanism with no words of its own. If it were the only export, the writer-model words (`:196-199`) and the reviewer-model words (`:286-289`) would sit in `askAgents` and again in #1529's askers. So:

- export `askModel`;
- export **`askWriterModel`** and **`askReviewerModel`**, which hold those words and call it.

The same rule gives these pieces, each exported from the file it is in today:

- **`agents.ts`**:
  - `askWriter({ given, offered, current, detected, validate, kept })`, whose words are built from `offered.join(', ')`;
  - `askReviewer(...)`, the same, plus `'none'`.
- **`sandbox-step.ts`**: `askSandboxMode` and `askSandboxHosts`. The hosts prompt needs `builtIns` (`:71`).
  - The `cannot` line (`:39`) and `SANDBOX_OFF_LINE` (`:54`) stay in `askSandbox`. They print whether or not a prompt is drawn, so in #1531 they are `ctx.log` lines (1529 §2).
- **`landing.ts`**:
  - `askRefusalFixes`, `askConflictResolutions`, `askWall` and `askBudget`. `askBudget` carries its `show`.
  - `askLandingChoice({ given, current, kept })`. It keeps both of today's forms: with a `given`, the branch question with no `choices` and flag `--land <branch>|hold` (`:150-158`); without one, the `WAIT`/`LAND` choice with the other flag text (`:164-172`).
  - `askLimits` keeps `ROUNDS_RETIRED` (`:234`) and the dollar-ceiling note (`:313-318`).
- **`source.ts`**:
  - `askTicketSource`, the `questionEffect` at `:131-139`. The early *"not one of github, db"* refusal (`:91-93`), the history clash and the local branch stay in `askTickets`, because they are decided rather than asked.
  - `askKindsList`, the `:173-184` call.

- **`first-project.ts`**: `askMoveLanding({ name, oldRemote, kept })`, which answers `'yes' | 'no'`. It is still a raw `world.ask`, and **null (no terminal) answers `'yes'`**, as `:891`'s *"`null` is no terminal: the line above is the record"*. *"…landing was not moved"* (`:892`) stays the caller's refusal, so it can become #1531's `confirm.declined`.

## 5. Order of work, and what proves it

1. Commit `doc/design/1529.md` alone, unchanged.
2. Export the pieces, rewrite each `ask*` to call them, and move the helpers.
3. Then run the eight pinned files: `agents`, `landing`, `setup-build`, `source`, `team`, `recipe-flow`, `init` and `init-golden` under `apps/cli/unit/`. Add `recipe-summary.test.ts`, whose `Summary` import is the one most likely to break. Run them before the runner or view work, so a red names the split and not the runner.
   - `apps/cli/integration/init.test.ts` is a different file. It runs after the merge, not in this pass.

Nothing in this slice reaches git, a process or the network. Every claim is unit-checkable with `pnpm typecheck` and `HOME=/nonexistent pnpm test`. Nothing here adds an `async` or an `Effect.run*`:

- the pieces are `Effect.fn` or `questionEffect` pipes;
- the view and the helpers are synchronous;
- `lift` in `askMoveLanding` is already the `first-project.ts:883` call.

So `effect-ratchet.baseline.json:11` is not touched.

No accepted ADR is contradicted. 0125 §9's split, *"A descriptor decides; an asker only asks"* (`setup-list.ts:6`), is what puts the words in the pieces and the checks in `validate`.
