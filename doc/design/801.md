## Design note: #801, `@summary` per event

### Where the tag goes in each comment: last

TypeScript's JSDoc parser gives a tag everything from the tag to the next tag or the end of the comment. If `@summary` goes on the first line, every developer paragraph after it becomes part of the summary. Put it as the **last** block of each comment:

```ts
/**
 * …the developer text, unchanged…
 *
 * @summary An agent's run started on a worktree.
 */
```

This is safe today because no comment in the file has a line starting with `@` (`grep -nE '^\s*\*\s*@' packages/domain/src/events.ts` returns nothing). The test still holds the length rule, so a tag that swallows developer text fails on length rather than passing.

### Reading it: the touching comment only, through the compiler

`definitions` (`packages/domain/scripts/events.ts:398-420`) already picks which comment counts: *"Only a comment touching the statement is its doc: one with a blank line between is the file's own prose (the note above `TicketDiscovered`)"* (`:411-416`). The JSDoc API does not apply that rule. `ts.getJSDocTags(stmt)` collects tags from **every** `/** */` attached to the statement. `TicketDiscovered` (`events.ts:178`) has the `RefusalReason` prose attached (`:136-174`), with a blank line and a banner in between.

So keep the existing range selection. Read tags only from the JSDoc node whose start equals that range's `pos`, found by walking the statement's JSDoc nodes from `ts.getJSDocCommentsAndTags(decl)` or the statement itself. Take each tag's text with `ts.getTextOfJSDocComment(tag.comment)`, which handles the `string | NodeArray` form. Then collapse whitespace to single spaces, so a tag that wraps over two lines comes out as one line.

`Definition` (`:395`) becomes `{ line, group, summaries: string[] }`, and the generator writes `summary: def.summaries[0] ?? null` (`:532`). **The generator does not throw** on zero or two summaries. `events.json is current` calls `generate()` (`events-json.test.ts:139`), so a throw there would turn the readable per-event failure from the new test into a crash of the whole `describe`. Counting is the new test's job. `summary` stays `string | null` (`:313`), as the ticket says.

### The test

Put it in `packages/domain/unit/events-json.test.ts`, replacing `describe('firstSentence', …)` (`:90-135`), and drop `firstSentence` from the import at `:16`.

- **What it reads.** Export a small function from the script, such as `summaries(root): Map<string, string[]>`, built from the same `definitions`. Testing the real file through the real parser is the point; a separate regex parse in the test would check something the generator does not use.
- **One summary per type.** For every key of `EVENTS`, assert exactly one entry.
- **Style rules.** Assert rules 1, 3 and 4 with **one array of `"<Type>: <what is wrong>"` strings**, compared to `[]`. A violation then names the type and the rule in the failure output, as `badRows` already does at `:62-71`.
- **Fixtures.** Add two or three cases on a fixture comment string: a tag before developer text, two tags, and a wrapped tag. They pin the parsing rule above without depending on the real file.

### Comments that must be written new

`TicketDiscovered` has no touching comment: the banner at `:176` and a blank line come straight before `:178`. Every other event the ticket lists as having *no description* may be in the same position. For each one, add a `/** @summary … */` directly above the `export const`, with no blank line in between. Do not attach anything to the `RefusalReason` prose.

### Where the banner sentence goes

The file's head comment (`events.ts:1-16`) already lists *"Two rules hold for every entry"*. Make it three: every event's doc comment ends in one `@summary` sentence for a reader of the docs, and `pnpm test` fails without it. That comment is the first thing anyone adding an event reads; the `work item` banner is a single `//` rule line.

### Retired types

The three types in `RETIRED` (`events.ts:2292`: `OutboxDelivered`, `OutboxFailed`, `TicketLinked`) get the *"No longer written:"* prefix. The test checks the prefix against `RETIRED`, not against the comment text.

### Commit order

Every inserted `@summary` line moves the line numbers in `events.ts`. `eventLevel` ignores `definition` and site line numbers (`events-json.test.ts:42-45`), so that alone is not stale. `summary` changes for all 66 events, though, so run `pnpm events:generate` (`package.json:31`) after the last sentence is written, and commit both files together.

All of this can be checked at unit level: `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test`. No integration test is involved.
