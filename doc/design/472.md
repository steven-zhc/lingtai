# #472 design note: fall-shorts go through `proposed`'s router

## The shape in one paragraph

All of the routing machinery is already in place. Once `nextOf` answers `Propose`, `runPass`'s existing `Propose` branch (`pass.ts:1317-1325`) hands it to `routeProposal`. That function calls `offerFor` (whose cells for all seven exist, `routing.ts:173-210`), then `replyFor`, then `routeNext`, which returns `WaitOnPerson{ProposedEscalated}`. `conduct.ts`'s `holdFor` turns that into a `Hold` through `escalatedHold`, which #471 built so that `holdOf(ProposedEscalated{X})` equals `holdOf(X's direct WaitReason)` (`adapters.ts:622-628`). So the change is: swap eight return sites in `pass-next.ts`, delete two branches and a variable in `pass.ts`, and then fix the three places where the two hold paths are *not* actually equal end to end. Those three are listed under **Where the hold would move**, and they are what this note is for.

## `nextOf`: field mapping

Each helper keeps its signature and builds a `Proposal` literal. The fields go across like this. `action`, `findings` and `call` have no home on the proposal and are dropped. Nothing downstream reads them: `checkRedHold` uses only the evidence (`adapters.ts:651`), and `holdFor` never reads `call`.

| helper (`pass-next.ts`) | becomes |
|---|---|
| `setupRefused` (:330) | `{ _tag: 'SetupRefused', from: step, output: why }` |
| `checkRefused` (:334) | `{ _tag: 'CheckRefused', from: step, output: evidence }`, keeping its step guard |
| `answerUnreadable` (:323) | `{ _tag: 'AnswerUnreadable', from: step, raw }`, keeping its step guard |
| `changedNothing` branch (:101-107) | `{ _tag: 'FixerDisagrees' \| 'NothingProduced', said }` |
| `mergeCompletedRefused`'s non-verify arm (:298) | `{ _tag: 'MergeRefused', reason: integration.reason, output: evidence }` |
| `interruptedAs`'s budget arm (:311-313) | `{ _tag: 'BudgetExhausted', from: step, kind: cause, turns: null, costUsd: null, detail }` |

Some notes on the table:

- **`turns`/`costUsd: null` is correct, not a gap.** The direct path wrote `null` too (`adapters.ts:726-728`). `holdFor` patches the real numbers from `ceilingHit` (`conduct.ts:3675-3677`) on whichever path the `Ceiling` arrives by, so row 14a is unaffected.
- **`run` stays a parameter.** `AgentCrashed` and `SignoffRequired` still need it.
- **What still answers `WaitOnPerson`:** `AgentCrashed`, `SignoffRequired` and nothing else. `NextOfResult` keeps the variant.
- The header comments of `pass-next.ts`, `hold-of.ts` (:5-25, :107-111) and `runPass` (`pass.ts:1046-1050`) all describe the old split. Correct them in the same commit.

## `pass.ts`: what is deleted

- `pendingUnreadableReview` (:1079-1088), its consumer block at the top of the lap (:1228-1258), and the `AnswerUnreadable && at === 'review'` carry (:1327-1336).
- `db205f85`'s `MergeRefused` block (:1338-1356).

After that, the `WaitOnPerson` branch is just `stoppedAt = { step: at, ending }; waitOn = next.reason; break`.

**Do not change `reported`'s rule** (`pass.ts:1322`: null when `ending.ending === 'passed'`). `review` always ends `passed` on an unreadable answer (the doc comment at `pass.test.ts:1172-1174`: *"`review` always ends `passed` (`endingOf`)"*). With the rule unchanged, review's routed `AnswerUnreadable` leaves `stoppedAt === null` and `PassRouted.from === 'proposed'`, which is what the deleted fixed row produced (`pass-steps.test.ts:1824` pins `from: 'proposed'`). Row 13b's `step: 'proposed'` then holds. Row 14d asserts `step: 'review'` (`what-a-pass-writes-today.test.ts:1171`), and the reviewer's *interrupted* visit evidently does not end `passed`, since 14d stops at `review` today. That keeps `reported` non-null there. If 14d turns out to reach `routeProposal` with `reported === null`, read the next paragraph first.

## Where the hold would move, and what keeps it still

1. **The ceiling branch of `holdFor` dereferences `pass.stoppedAt!`** (`conduct.ts:3660-3666`). It is reached for the wrapped `BudgetExhausted` whenever `ceilingHit === null` (rows 14c, 14d). Take the step from the proposal (`pass.waitOn.proposal.from`) on the wrapped form, not from `stoppedAt`. `nextOf` no longer produces the direct form, but keep its arm, because `WaitReason` still has the variant.

2. **`MergeRefused` loses `paths`/`baseSha`/`headSha`.** Today 10b reaches `holdOfPass` step 2, which fills them from `lastIntegrationRefusal` (`conduct.ts:3693-3696`, `hold-of.ts:124-126`). Through `holdOf`, `mergeRefusedHold` writes `null` for all three (`adapters.ts:668-670`), and approval reads those columns (`approve.ts:388-395`). In `holdFor`'s `waitOn` branch, when `withRun._tag === 'MergeRefused'`, call `lastIntegrationRefusal(store, project, base, workItemId, branch)` and spread the three fields in. Do it the same way the `Ceiling` and `Declined` patches beside it work. 10b asserts only `reason`, so that fixture will not catch a miss; add `paths`/`baseSha`/`headSha` to 10b's `toMatchObject`.

3. **Review's unreadable answer loses its sentence.** Today the card's `why` comes from the fixed row's long sentence through `holdOfPass` step 4, and 13b pins `toContain('could not be read at all')` (`what-a-pass-writes-today.test.ts:1072`). Through `escalatedHold`, `answerUnreadableHold` gives `"<branch> into <base> is waiting on you. <said(raw)>"` (`adapters.ts:914-925`), which does not contain it. Move a short form of that sentence into `answerUnreadableHold`'s `review`/`proposed` branch, **ahead of** `raw`, inside the same `said(…, 400)`. That way the prefix survives clipping, and `adapters.test.ts:585-591` (no newline, shorter than a long `raw`) and the parity test at :699-709 still hold. This is the one shared builder, so both paths move together.

Expect some `PassRouted.why` texts to change. 10b, the unreadable review and every other moved row now carry `notAskedWhy`'s sentence (`proposed-route.ts:184-189`, *no `judge:` is declared for a "merge-refused"…*) in place of the hand-written ones. The ticket's rule covers event *types* and the hold; `why` on the route row is the router's own text, so update the strings that pin it.

## Tests that change besides the ticket's list

`replyFor` calls the judge port whenever two or more candidates are on offer (`proposed-route.ts:137-142`), before it knows whether anything is declared. Every one of the seven offers at least a `restart` beside `hand-to-person` (`routing.ts:173-210`), so the port is now asked for all of them. In the `pass-steps.test.ts` harness the port records the call before it answers `noJudge` (:361-363). This costs nothing at run time, because `noJudge` → `BUILT_IN_FOR[when] === null` → `NotAsked`. It does flip two pins:

- `pass-steps.test.ts:778` (*never offers the judge `implement` for a `prepared` refusal, by never asking*): it is asked now. Rewrite it to assert that `asked.judge[0].offering` does not contain `'implement'` (`bornAtOrAfterImplement('prepared')` is false). The name's claim then holds by *offering*, not by never asking.
- `pass-steps.test.ts:1812-1829`: `asked.judge` gains one `{ when: 'answer-unreadable' }`. `routes[0].why` becomes `notAskedWhy`'s sentence. `waitOn` becomes `ProposedEscalated{AnswerUnreadable}` (not `null`). `rested` stays `'waiting'`.

Other changes:

- Row 6 asserts `not.toContain('PassRouted')` (`what-a-pass-writes-today.test.ts:513`). Flip it, and rewrite the file header bullet at :32-35.
- Row 9's comment at :657-662 explains the old absence. Replace it.
- `pass.test.ts:1185` becomes: `ran` has no `proposed` entry, `result.waitOn` is `ProposedEscalated` with `proposal._tag === 'AnswerUnreadable'`, `rested === 'waiting'`. Say so in the commit body, as the ticket asks.

**The seven *`human:` is not run* tests** go beside `pass.test.ts:1149` and copy its shape: `watchingActions` with a `proposed: [sign off]` that would answer `needs-approval`, then assert:

- `ran` contains no `proposed` entry;
- `steps.find(s => s.step === 'proposed').results` is `[]`;
- `rested === 'waiting'`;
- `waitOn._tag === 'ProposedEscalated'`.

**The judge test** is cheapest with `SetupRefused` at `prepared` through `pass-steps.test.ts`'s `answers.judge` function form. Answer `restart` for `when === 'setup-refused'`, then assert `asked.judge[0].when === 'setup-refused'` and `rested === 'requeued'`.

## What nothing here can verify before the merge

`conduct-a-whole-pass.test.ts` and the fixture file are unit tests (fakes, memory store), so every claim above is checked by `pnpm test`. The live question is whether a real `IntegrationRefused` row carries `paths`/`baseSha`/`headSha` for a dirty base, so that point 2's patch shows anything on a card. That is settled by the `IntegrationRefused` event's `paths`/`baseSha`/`headSha` fields on the integration stream, which only the integration half and production reach. The unit-level stand-in is 10b with a fake `IntegrationRefused` appended before the pass, asserting that the hold carries those fields.
