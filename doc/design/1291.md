# #1291: design note

## The one thing the ticket does not say: the stage reads its words from the list you are moving

`FailurePathsStage` has no copy of its own. When it mounts, it reads the copy from the DOM of its own section:

- `failure-paths-stage.tsx:1483`: `const section = host?.closest('section')`
- `:785-792`: `section.querySelectorAll('.fp-item')`, then for each item `.fp-say`, `.fp-what`, `.fp-bound`, `.fp-ext` and `.fp-ask`
- `:1448-1449`: closes `.fp-all` and every `.fp-item` once the script runs
- `:1420-1422`: copies the `.fp-ask` figure into `.fp-askslot` for *unclear*

`failure-paths.tsx:4-5` explains why: *"This list is the whole section without script, and the drawing reads each item's words from it, so the two cannot disagree."*

The ticket moves *Every path, as a list* (`failure-paths.tsx:134-153`) out of the `<section id="when-it-fails">` and into the FAQ. That leaves `querySelectorAll('.fp-item')` with nothing to find. You get `items = []`, no chips, and no error. Typecheck and every unit test stay green, because the tests render on the server and the stage never mounts there.

**Decision: `ITEMS` stays the only source, and the stage gets it as a prop instead of reading the DOM.**

- Export the item type and pass `<FailurePathsStage items={ITEMS} />` from `FailurePaths`. The data is plain strings, so it serialises across the client boundary. `mount(host, items, …)` maps it the way `:785` does today.
- Render `<QuestionCard />` as a child of the stage, inside `.fp-live`, in a slot that is always hidden. `mount` clones it from there. Today the card is only ever seen in the scripted view, and `.fp-live` is `hidden` until script runs (`:1490`), so nothing changes for a reader without JS.
- Delete the `all` lookup and the item-closing lines (`:783`, `:1448-1449`). The FAQ table is meant to stay open: the mock's `faq-item faq-wide` has `open=""`.
- The FAQ table is a second export from `failure-paths.tsx` (call it `FailurePathsTable`), mapped over the same `ITEMS`. `page.tsx` renders it as the first `faq-item`. Both views come from one constant, so the "cannot disagree" promise holds. Rewrite the comment at `:4-5` to say that, rather than talk about the DOM.
- Give each table row `<tr data-key={it.key}>` and keep the `fp-say` / `fp-what` / `fp-bound` / `fp-ext` class names on the cells. The tests below rely on those hooks.
- The closing line *"If the quick look itself fails, it asks once more, then hands it to you and says so."* (`:152`) is copy, and the ticket says copy only moves. `failure-paths.test.tsx:67` asserts it. Put it in the table's `<tfoot>` or under the table, but keep it.

**Without JS** the section is now the heading, the legend and nothing else. The FAQ table, open by default, is what reads in order. That is the ticket's *"the page reads in order"*.

## The arrow: one client component, separate from both sections

The arrow needs three things to position it: the *See how ↓* cell (ledger, server-rendered in `page.tsx:287-293`), the ledger `<table>`'s right edge, and the heading block (`failure-paths.tsx`). Do not thread refs between them.

- Write a new `'use client'` file, `route-arrow.tsx`, rendered once inside the why section.
- It finds its anchors by data attribute: `data-route-from` on the link, `data-route-table` on the ledger table, `data-route-to` on the heading-plus-legend block.
- Coordinates are relative to an ancestor that is `position: relative` (the why section), not the page. That makes scroll and anything inserted above the section irrelevant. The mock's snapshot shows absolute page coordinates baked in (`smart-routing.html:12139`, `style="left: 817.648px; top: 4224.67px"`). That is the output of a script, not the shape to copy.
- Gutter is the container's right edge minus the table's right edge. Below 90px, render no `<svg>` at all rather than a clipped one. Every x the path uses is ≥ `tableRight + margin`, so the path cannot cross the table by construction. Do not check for overlap after drawing.
- Redraw from a `ResizeObserver` on the section, and once from `document.fonts.ready.then(redraw)`. The hand fonts are system fonts, but the body font may still be swapping in. Disconnect the observer in the effect's cleanup.
- Use `.then`, not an `async` function. The ratchet counts `async` functions in `apps/site` too: `effect-ratchet.test.ts:455` says *"The board and the site keep promises for good (0101 §7)"*, and they are still counted. Do not raise the baseline.
- `prefers-reduced-motion`: the arrow does not animate, so there is nothing to check.

The bracket and *try one →* are CSS only. They come from the mock's `.fpm-h`, `.fpm-arrow text` and `#when-it-fails .fp-chips::before` (`smart-routing.html:12043-12058`). Use the system hand stack exactly as written there. Do not load a font.

## The ledger row has a link, and `LEDGER` holds only strings

`LEDGER` (`page.tsx:15-35`) holds `lingtai: string`, rendered as `{row.lingtai}` (`:291`). The new row ends in `<a href="#when-it-fails" data-route-from>See how ↓</a>`. Add an optional field to the row type, e.g. `see?: { href, label }`. Do not turn every row into JSX. The row goes second, after *Who says it's done*.

## Placement

The ticket says the failure section goes inside the why section, after the ledger. The mock instead closes `why`, renders the heading and the `fp` section, then opens `<section class="why why-faq">` (`smart-routing.html` body, around line 12131). Follow the mock's DOM: it is what the side-by-side check is made against.

`<section id="when-it-fails">` stays its own element with that id. `#when-it-fails` is a `<section>`, so `closest('section')` keeps working for the stage's resize observer. The heading moves inside it, so the anchor lands on the heading.

## Tests to change, once

**`failure-paths.test.tsx`:**

- `item()` (`:36-40`) slices from `data-key="…"` to the next `</details>`. In a table, that slice runs to the end of the FAQ item and takes in every later row. `item('flaky')` would then contain *review*'s text, and the per-number assertions would pass without testing anything. Change the end marker to `</tr>`.
- *"sits after the replay and before the sandbox band"* (`:54`) becomes: after `class="ledger"` and before the FAQ's first `faq-item`.
- `/class="fp-item"/` ×7 (`:64`) becomes seven `<tr data-key=`.
- *"links the FAQ answer…"* (`:71-78`) tests *Will it loop forever?*. Delete it, and assert that the question is gone.
- *"opens the list until script runs"* (`:81`) asserts the FAQ table's `<details … open`.
- Add one assertion that `Pick a failure. See where it goes.` is gone and `Here is what happens when something breaks.` is present.

**`page.test.tsx:156`** lists *Will it loop forever?* among the FAQ questions. Replace it with *What does it do in each case?* in first position.

**`home-css.test.ts`:** if it asserts the `.fp` top rule at `home.css:213`, it changes with that rule.

**What no unit test can catch:** a stage that mounts with zero items. Add a unit test that calls `FailurePaths()` and asserts the stage element's `items` prop has length 7. That stands in for the browser check, which only the side-by-side at 1440px covers.
