# #439: the shape

## The decision the ticket gets wrong: zod, not `Data.TaggedEnum`

The ticket's Fix says *"`Data.TaggedEnum` (Effect, 0101)"*. 0101 says the opposite, three times:

- §4: `domain` is *"Vocabulary … It imports only `zod`."*
- §6: *"Effect at the ports and past them, and nowhere else."* The list of packages Effect is a dependency of does not include `domain`.
- §7: *"`domain`, `recipe`, … are plain functions that Effect code calls."*

`packages/domain/package.json` agrees: its only dependency is `zod`. So `effect` stays out of `@lingtai/domain`. A person who really wants `Data.TaggedEnum` there is asking for 0101 to change. Per CLAUDE.md that is an edit to 0101's own topic ADR, and it is not this ticket's to make.

Zod is also what keeps the model in one definition. 0101 §1 says *"Events are zod schemas in `@lingtai/domain`"*, and #445 puts a `Hold` on `WorkItemBlocked`, so #445 needs a schema for it. If this ticket wrote plain TypeScript types (or an Effect enum), #445 would have to write a zod twin, and the model would exist twice. That is the duplication the ticket exists to prevent. So:

- **Write each variant as `z.object({ _tag: z.literal('X'), … })`**, each union as `z.discriminatedUnion('_tag', […])`, and each type as `z.infer`, with value and type under the same name. `events.ts` does this already (`RefusalReason`, `events.ts:133`/`:171`).
- **Use `_tag` as the tag key, not `kind`.** It is Effect's convention (`Data.TaggedError` in `packages/repo/src/git.ts:71`, `packages/agent/src/hook-config.ts:226`). Readers in conductor code that match with Effect's `Match.tag` then keep working, and a later move to `Data.TaggedEnum` would not change a single value on the log.
- **This is still types only.** A schema is not an event: there is no `parsePayload` entry, no `EventType`, no appender and no fold.

## The model, variant by variant

Below, every `Judgement` and `Failure` leaf carries `run: RunRef`. `Question` does not, and that absence is what the first `@ts-expect-error` pins.

**Flatten the leaves.** `Hold` is `z.discriminatedUnion('_tag', [Question, Judgement, Failure])`, with nine distinct tags. Do not wrap them as `{ _tag: 'Judgement', judgement: … }`: that would make `Judgement` the name of both a wrapper and a union. Zod 4 accepts a discriminated union as an option of another one on the same key. If the installed version (`^4.5.4`) refuses that, spread `Judgement.options` and `Failure.options` into `Hold` instead. A reader that wants only the three kinds matches the grouped `case`s. Write no `holdKind` helper; #441 can add one if `allowedMoves` needs it.

**`RunRef`**: `{ runId: string, unpushed?: { branch: string, said: string }, repairOf?: string }`.
- Both fields are `.optional()`, as the ticket says, not `.nullable()`: the ordinary run carries neither.
- `unpushed.said` is git's own words, which `conduct.ts:3138-3139` holds today as `notPushed` and turns into a parenthetical.
- `repairOf` is the run id that `retiredRepairPending` (`work-item.ts:425-437`) returns as `after`.

**`Question`**: `{ question: string, by: string }`. 0118 §1 asks for *"the person's own question and who asked it"*. `by` is the value `ask.ts:71` writes as the envelope's `actor`.

**`Judgement`** = `Asked | Gate | Routed`, and **no fourth variant**:
- `Asked { run, step: Step, question: string }`
- `Gate { run, step: Step, source: 'declared' | 'injected', question: string }`. The `question` is the text the page shows (the-waiting-lane.md's `Gate` rows: *"the declared question"*). That is a person's words, so it lives in the variant.
- `Routed { run, when: JudgeWhen, why: string }`, typed over **all five** `JudgeWhen` values, as 0118 §1 has it.

Three of #404's open questions touch these variants. Per the Watch out, none of them is settled here:

- **Question 1** (whether rounds-spent `red`/`verify-failed` routes are `Routed` or `Failure`) is about which variant a producer writes, and #445 does the writing. Typing `when` as `'findings'` alone would settle it by narrowing, which is a choice. The full `JudgeWhen` is 0118's text and also the only reason the ticket moves `JudgeWhen` into the domain.
- **Question 4** (whether a declined fixer is a `Judgement`) is left open. **Add no `Declined` variant.** A declined fix round stays `DidNotFinish`, which is what it is recorded as today (`work-action.ts:170`).
- **Questions 2 and 3** (migrations and repairs) do not change the type. Both land in variants that already exist: `Gate` with `source: 'injected'`, or `MergeRefused`.

Put one sentence in the module's doc comment naming questions 1 and 4 as #404's and still open, so the next reader does not take the three variants for a settled list.

**`Failure`**: the evidence and raw text the ticket asks for live in each variant. `raw` is `string | null`, as `BlockDiagnosis.raw` is at `events.ts:254`.
- `CheckRed { run, step: Step, why: string, raw }`. Leave out the rounds: 0118 §4 says *"Rounds and restarts left are facts on the log, shown on the rail line."*
- `MergeRefused { run, reason: RefusalReason, why: string, paths: string[] | null, baseSha: string | null, headSha: string | null, raw }`. These mirror `IntegrationRefused` (`events.ts:1149-1160`), where `paths` and the two shas are set only for `conflict`. Here they are `null` rather than optional, so the board says *none* rather than *unknown*.
- `Ceiling { run, kind: 'out-of-turns' | 'out-of-usd', detail: string, turns: number | null, costUsd: number | null }`.
  - `kind` is `Extract` from `RunFailureKind` (`events.ts:614-625`), so it cannot drift from it.
  - The two numbers are what was spent, as the runtime reported it, and `null` where it said nothing. 0118 §3's own rule for `HoldTriaged` is to record no number rather than a zero the runtime never stated.
- `DidNotFinish { run, step: Step, why: string, raw }`
- `SetupRefused { run, step: Step, lifts: 'by-itself' | 'person', why: string, raw }`. `lifts` is 0118 §1's *"whether that lifts by itself or needs a person"*. #404's question 6 is whether the `by-itself` half has a producer yet. That is a question about producers, and the type follows the ADR.

There is no `needs`, no `recommendation` and no `diagnosis` anywhere in this module, because all three are derived (0118 §1).

## Triage

**`TriageQuestion`** is the shape the ticket says `Decision` and a divergent hunk share: `{ id, text, answers: { id, text }[], recommended: string }`. It gets its own name so it cannot be confused with the `Question` hold. A `.refine` checks that `recommended` is one of the answers' `id`s. That is a claim a unit test can hold.

**`Cause`**:
- `Decision { questions: TriageQuestion[] }`
- `Lines { fixes: { path: string, line: number | null, what: string }[] }`
- `Approach {}`
- `Merge { hunks: Hunk[], total: number }`
- `Narrower {}`
- `Setup { lifts: 'by-itself' | 'person' }`. 0118 §4 says *"Triage says which of two it is"*. The enum is shared with `Failure.SetupRefused`.

**`Hunk`** = `Mechanical { path, line } | Divergent { path, line, question: TriageQuestion }`. A mechanical hunk's type has no `question` key, and that is the second `@ts-expect-error`.

The 20-hunk rule goes into the schema once, as `export const MERGE_HUNKS_ONE_BY_ONE = 20` and a refinement on `Merge`:
- If `total ≤ 20`, then `hunks.length === total`.
- If `total > 20`, then `hunks` is empty (0118 §8).

Leave the other bounds to the ticket that parses the agent's answer (*"a few questions with a few answers each"*, 0118 §3). They are limits on what an agent may write, not part of the model.

**`Move`**: `Approve | Requeue | Close | BodyAndRequeue | Answer`, each one a `{ _tag }` with no other fields.

**`TriageResult`** = `Failed { why: string } | Advised { cause: Cause, move: Move, card: string, wants: string | null }`.
- These four fields are 0118 §3's *"the cause, the recommended move, one sentence for the card, and one sentence of what the ticket wants (or none)"*.
- Usage and who answered (`Agent` or `Mechanical`) belong to `HoldTriaged`, not to the result, so they are not here.

**`TriageStatus` gets no zod schema, on purpose.** It is a plain discriminated TypeScript type with the same `_tag` key: `NotDeclared | Queued | Running | Interrupted | Done { result: TriageResult }`. 0118 §1 says it is *"derived on read and never stored"*, and §10 says *"It cannot keep a `TriageStatus`"*. A schema is what a projection or an event would reach for, and nothing should ever parse one. Leave `triageStatus()` out too; it is §10's ticket.

## Tests: unit only

Write them in `packages/domain/unit/hold.test.ts`.

- **`@ts-expect-error` cases.**
  - A `Question` literal with a `run` key, assigned to `Question` and to `Hold`.
  - A `Mechanical` hunk literal with a `question` key.
  - These are checked by `pnpm typecheck`, not by vitest. `packages/domain/tsconfig.json` includes `unit`, so the directives are compiled. The assignment has to be a fresh object literal, or TypeScript skips the excess-property check and the directive fails the build for the wrong reason.
- **Runtime cases.**
  - Each union round-trips through `.parse`.
  - The hunk refinement: 3 of 3 passes, 21 with none passes, 21 with 3 is refused.
  - `recommended` must name one of the answers.
- **The import boundary.** Copy `packages/extension/unit/imports.test.ts`: it uses `ts.preProcessFile` and refuses computed imports. Point it at `packages/domain/src` and `packages/domain/unit`, and assert that no specifier starts with `@lingtai/recipe` or `@lingtai/conductor`. Also assert that `packages/domain/package.json`'s dependencies name neither, which stops a future `effect` slipping in by the same door.

None of this needs `pnpm test:integration`. Every claim above is checked by `pnpm typecheck` or `pnpm test`.
