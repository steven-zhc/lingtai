**Design: #1430. The Queued column's GitHub ask starts from the board's early value**

### Shape

There is one new export in `apps/board/src/lib/board.ts` and one changed call in `apps/board/src/app/page.tsx`. No other file changes behaviour.

**`startBoard(project)` returns two promises from one set of reads: `{ queueAsk, board }`.** `queueAsk: Promise<{ askable: AskableFilter[]; known: ReadonlySet<string> }>` settles as soon as `tasks.read` and `board.recipes` have both answered. `board: Promise<Board>` is the rest of today's `loadBoard`, and it awaits the same `queueAsk` promise. `loadBoard(project)` stays, as `startBoard(project).board`. `trace-spans.test.ts:131` calls it, and it keeps every span name that test asserts.

Why two promises and not a callback or a field on `Board`: the page hands promises to its parts (`page.tsx:725-726`: *"**Each is its own promise**, so a part awaits the reads it draws from and no others"*). `queueAsk` is one more of those. The *"started once and awaited from both boundaries"* rule (`page.tsx:1216-1217`) stays true because `queue` is still built once, at `page.tsx:1218`.

### Inside `startBoard`, and the decision the ticket leaves implicit

**`queueAsk` must not wait for the other three reads at `board.ts:1806`.** Today `board.recipes` sits in one `Promise.all` with `spend.read`, `daemon.status` and `triage.declared` (`board.ts:1806-1829`). If `queueAsk` is resolved "after that `await`", the queue still waits for spend and the beacon. Instead:

- Bind the `board.recipes` promise to a name.
- Derive `queueAsk` from that promise and the already-read `tasks`.
- Pass the same `queued` promise into the four-way `Promise.all`, so `board.recipes` is still read once.

`board.recipes` still starts after the first `Promise.all` (`board.ts:1785-1793`), which includes `projects.onboard`. Leave that alone: it is not in the slowest trace, and moving it changes `/`'s span order for no measured gain.

**`known` is built once, inside `queueAsk`, as `new Set(tasks.map((t) => t.taskId))`.** `Board.known` is that same `Set` object. Delete the second construction at `board.ts:1880` and move its comment with it (`:1877-1879`: *"A task released back to the queue has a row *and* is offered by GitHub, so it would otherwise appear twice. The row wins … `githubQueue` applies that with this set (#884)"*).

This is the same set as today. `fromLog` is `tasks.map(...)`, one card per task (`board.ts:1850`), so `fromLog.map(c => c.taskId)` equals `tasks.map(t => t.taskId)`. Keep `askable` and `known` on `Board` (`board.ts:1887-1888`) so the type does not change. Nothing outside `page.tsx:1224,1228` reads them.

**Rejection needs no new catch.** `board` awaits `queueAsk`, so if `board.recipes` throws, both reject, as both do today through `ctx.reads.board`. If the tasks read fails, `emptyIfUnbuilt` (`board.ts:1786`) has already turned it into `[]` before `queueAsk` exists.

The *"Never rejects"* in `githubQueue`'s doc (`board.ts:1369-1371`) is about GitHub's answer, not this. Do not wrap `queueAsk` in a `.catch`: the page would then draw an empty queue where it draws a failure today.

### The page

- `startReads` (`page.tsx:737-753`) calls `startBoard(param)` once, in place of `loadBoard(param)`, and returns `queueAsk` beside `board`.
- `Promise.all(Object.values(started))` at `page.tsx:1205` then also waits for `queueAsk`. That is harmless, because `board` already waits for it.
- `queue` stays at `page.tsx:1218`, outside `measure`'s scope. Only the source of the chain changes: `ctx.reads.queueAsk.then((ask) => …)`.
- `recordQueuedOffered` (`:1228`) takes `ask.askable`.
- Keep the comment at `:1213-1217`, but change *"waits for `board` alone"*: it now waits for the recipes and the task rows alone.

### Tests that break without saying so

- `not-set-up.test.tsx:13` mocks `loadBoard` and asserts it is never called (`:57`, `:66`). Once the page calls `startBoard`, that assertion still passes but checks nothing. Mock `startBoard` there and assert on it.
- `home-streams.test.tsx:13,23,69,75` mocks `loadBoard`, and `:139-141` and `:171` count its calls per render. Mock `startBoard` instead, returning `{ queueAsk, board }`. *"calls loadBoard once per render"* becomes *"startBoard once"*, which is the claim that the GitHub fan-out happens once.

### The unit test the ticket asks for

`laneProgress` is module-private (`board.ts:1661`), so a test cannot replace it. Stall it at its first `await` instead:

- That `await` is `traced('snapshot.writer', () => boardWriterOrNone())` (`board.ts:1684`). It runs on every call, unlike `readAttemptState`, which runs only for railed cards.
- Mock `../src/lib/snapshot-writer.ts` the way `trace-spans.test.ts:52` does, but with a promise that never resolves.

For `askable` to be non-empty (otherwise a count of 0 proves nothing):

- `loadAllProjects` returns one project that `splitRegister` keeps in `registered` (`board.ts:1917-1925`).
- `@lingtai/conductor/filter`'s `projectFilter` resolves to a filter. The `project('lingtai')` and `lingtai` fixtures in `render-cost.test.ts:293-298` have the shape.
- `readTasks` returns one row (`trace-spans.test.ts:93-128` has a complete `TaskCard`).

Assert:

1. `await queueAsk` settles while `board` is still pending. Use a `Promise.race` against a resolved sentinel, the way `render-cost.test.ts:298` does.
2. `githubQueue(ask.askable, ask.known, countingAsk)` calls `countingAsk` once per `askable` entry.
3. `ask.known` equals the task ids.

A second test, with the writer mock resolving, asserts `(await board).known === ask.known`. That identity is the unit-level version of *"the same set the board draws"*.

Put both in a new `apps/board/unit/queue-early.test.ts`. `trace-spans.test.ts` mocks a resolving `boardWriterOrNone` for every test in its file.

### How the operator will see it

This is a Jaeger reading, not the event log. Under `page / queue`, the `queue.project` span's start should fall before the end of `page /`'s `board.progress` span. In the slowest trace today it starts at +2,639 ms, after `board.progress` ended at about +2,637 ms. `doc/experiments/021/summarize.py` reads both spans.
