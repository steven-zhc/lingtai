# Design note — Waiting task surfaces

Give the Waiting view its own layout scope in `TaskBody`, then style the upper page through that scope in `apps/board/src/app/globals.css`. Keep the existing `Standing` order and data flow: `standing.tsx:488–516` renders the ticket before the rail, and `standing.tsx:631–647` places triage before resolutions. ADR 0118 §2 says, “The page is in this order: the ticket, where it is, triage, the resolutions, the record.” Limit the new width, spacing and panel rules to the Waiting view so the record and other task states retain their layout.

Make the ticket a bounded white reading surface with a prominent title and a quieter number, triage reading and collapsed opening. Do not turn the mockup’s Problem/Want/Watch out columns into parsed ticket fields: `standing.tsx:191–194` takes the first eight body lines, while ADR 0118 §2 says, “A body is not assumed to have any structure.” Keep the whole-ticket link. Give “Where it is” a clear panel and more room for the existing ten-step `Rail`; preserve its step marks and the stopping words beneath it. The rail’s comment calls for “All ten, always” (`rail.tsx:100–121`).

Make `TriageBand` the distinct teal surface. Within it, use a readable cause label, summary and grouped evidence; give failed triage a failure accent and conflict triage its own cause emphasis. Keep `TriageChoices` and disagreement content in their current reading order (`standing.tsx:84–171`). Derive every displayed fact from the status and result already passed in. In particular, `standing.tsx:59–61` returns no band for `NotNeeded` or `NotDeclared`; ADR 0118 §3 says that without declared `triage:`, “the page shows the ticket, where it is, and the stopping step’s own words.” Do not copy the mockups’ costs, ticket fields or claims about resolved hunks.

Use responsive columns only where the available width supports them; stack ticket content and triage evidence in DOM order on narrow screens. Keep long evidence contained within its own surface. The existing layout comment documents the overflow failure caused by an uncapped grid track (`globals.css:952–960`).

For visual verification, render an advised-wait fixture and the live #524 no-triage page at desktop and narrow widths, capture before and after screenshots, and link them in #528. For the fixture, the settling facts are the current `WaitStarted.reason` and `WaitTriaged.result`, not illustrative mockup text; ADR 0118 §1 names those event fields. Run the four ticket gates and unit checks, without the integration suite.
