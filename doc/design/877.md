# #877 — design note

## The one helper, and how each package reaches it

`readState` (`packages/conductor/src/snapshot-state.ts:14`) is the helper the ticket means. Its header says it is "the one place outside `runOnce` that runs the Effect `readThroughSnapshot` returns, so that `effect-ratchet.test.ts` counts one `async` and one run for every promise-shaped caller". Call it at every site as `await readState(store, ticketReducer, ticketId, 'all', { snapshots, writer })`. A failed read rejects with the store's own error (`snapshot-state.ts:21-22`), so every existing `catch` keeps its meaning.

**It is only exported from the barrel today** (`packages/conductor/src/index.ts:1`). The daemon and the board must not import the barrel. `reconcile.ts:72-74` says: *"A subpath, never the barrel … `@lingtai/conductor`'s index pulls in the gate pipeline and its child-process types, and the board imports this package."* So add `"./snapshot-state": "./src/snapshot-state.ts"` to `packages/conductor/package.json`'s `exports`, next to `./claim`. `reconcile.ts`, `apps/board/src/app/actions.ts`, `apps/cli/src/triage.ts`, `requeue.ts` and `grant-fix-round.ts` import from that subpath. Files inside `packages/conductor` import `./snapshot-state.ts` directly, as `claim.ts` does.

Every site is already inside an `async` function, so swapping `reduceTicket(await store.read(id))` for `await readState(...)` adds no `async` and no `Effect.run*`. The baseline (`packages/domain/unit/effect-ratchet.baseline.json`) stays as it is. Do not add a wrapper function per package: each new wrapper is a new `async`.

## Which snapshots: one rule, computed where the store is chosen

Follow `packages/daemon/src/control.ts:141-142`, which is already the precedent: *"The default snapshots belong to the default store's log; a store passed in has none of its own."*

```ts
const snapshots = options.snapshots ?? (options.store === undefined ? log.snapshots : undefined)
```

- **Conductor functions** (`ask`, `answer`, `approve`, `requeue`, `resolveWait`, `editBodyAndRequeue`): their options types gain `snapshots?` and `writer?`. Use `extends SnapshotReadOptions`, as `ClaimOptions` does at `claim.ts:31`. Compute the line above at the public entry, where `options.store ?? eventStore` is already computed (`ask.ts:54`, `:136`; `approve.ts:117`, `:330`; `resolve-wait.ts:200`; `edit-body.ts:165`). Pass it into the `…Holding` functions, which take `store` positionally (`answerHolding` at `ask.ts:159`, `requeueHolding` at `approve.ts:352`, `editBodyAndRequeueHolding` at `edit-body.ts:181`). Each gains a trailing `SnapshotReadOptions = {}` parameter, matching what `releaseTicket` got (`claim.ts:255`). Where `resolveWait` calls `approveHolding` or `requeueHolding` internally, it must pass its own snapshots and writer on. Without that, the board's writer stops at the first hop.
- **Reconcile:** `logOf` (`reconcile.ts:115-117`) falls back to `options.daemonStore?.events` **before** `eventStore`. So the default snapshots apply only when **both** `options.store` and `options.daemonStore` are undefined. Otherwise a daemon-store log would be paired with the process log's snapshots, which is the wrong-log mistake `logOf`'s own comment describes. Compute this once per function, next to `logOf(options)`. `ReconcileOptions` gains `writer?`. `daemon.ts:354` passes `writer ?? undefined`, and the daemon's `writer` is in scope there (`daemon.ts:229`). Doctor's dry run (`doctor.ts:1617`) passes no writer.
- **Triage:** `CatchUpTriagePorts` (`apps/cli/src/triage.ts:99`) gains `snapshots?` and `writer?`. `daemonTriagePorts` (`triage.ts:308`) sets `store: eventStore`, so it sets `snapshots: log.snapshots`. It takes the writer as a new parameter, and both callers (`daemon.ts:518`, `:578`) pass `writer ?? undefined`. The port's store type is `Pick<EventStore, 'read' | 'append'>`, but `readState` wants `'readTypes' | 'read'`. Widen the port to `'read' | 'readTypes' | 'append'`. The fake at `apps/cli/unit/triage-catch-up.test.ts:48` then gets a `readTypes` that throws, because `'all'` only ever calls `read` (`snapshot-read.ts:49-50`). Leave `readThroughSnapshot`'s signature alone.
- **Board:** `actions.ts` uses the default `eventStore`, so its own read at `:714` passes `{ snapshots: log.snapshots, writer: await boardWriterOrNone() }`. Its calls to `approve`, `resolveWait`, `answer`, `requeue` and `editBodyAndRequeue` (`:129`, `:181`, `:229`, `:272`, `:304`) pass only `writer: await boardWriterOrNone()`, and the function supplies the snapshots. That is the same shape as `page.tsx:615`.
- **CLI** (`requeue.ts:78`, `grant-fix-round.ts:33`): no writer. `requeue.ts:78` uses `deps.store ?? eventStore`, so it gets snapshots only when `deps.store` is undefined. `grant-fix-round.ts` always uses `eventStore`, so it always gets `log.snapshots`.

## The helpers that are only a reduce

Use the `…FromState` forms that #876 already added at `packages/domain/src/read-model.ts`: `waitsFromState` (`:96`) and `triageFactsFromState` (`:125`). Do not add new ones. `actions.ts:716`'s `waitsOf(events)`, `ask.ts:174` and `approve.ts:178` become `waitsFromState(state)`. `triage.ts:128`, `:140` and `:165` become `triageFactsFromState(state, waitId)`.

`finishInterrupted` already reads `reduced.waits` (`triage.ts:171`), and that is the state as it stands. `approve.ts:174`'s `runEvents` and `triage.ts:174`'s `reduceAttempt(...)` stay raw reads, because attempt streams are out of scope.

`currentWait` (`triage.ts:229`) and `onWaitStarted` are not in the ticket's list of sites. Leave them.

## The reconcile `.catch(() => [])` sites

The reconcile sites at `reconcile.ts:268`, `:376` and `:474` become:

```ts
await readState(...).catch(() => reduceTicket([]))
```

That keeps today's meaning: a ticket that could not be read reduces as an empty one. Do not write `ticketReducer.initial`, because that leans on `reduceFrom` returning `initial` untouched for an empty list.

## The two length-only appends

- `reconcile.ts:668`: `events.length` becomes `state.version`. The `TicketReleased` lands on the state that decided `life.status === 'claimed'`.
- `triage.ts:177`: the same change, inside the existing five-try loop. Each try already reads again (`:161`).

## Tests

These are the unit-level claims. All are on `createMemoryEventStore()` from `@lingtai/event-store/memory`.

- **A snapshot below the head.** Copy the shape of #876's `packages/conductor/unit/claim-snapshot.test.ts`. Plant a ticket snapshot below the head through a memory `SnapshotStore`, and pass it with the store. Call `ask`, `approveHolding` and `resolveWait`. Assert two things: each append lands at the head (no `ConcurrencyError`), and each answer equals the answer with no snapshots.
- **No snapshots means `log.snapshots` is never touched.** Spy on `log.snapshots.latest` so it throws. `log` is exported at `packages/event-store/src/index.ts:79`. Then call a conductor function with a store passed in and no `snapshots`, and assert the spy was never called.
- **An append between the read and the append.** For the reconcile `TicketReleased` and the triage `WaitTriaged`, wrap the store's `append` so an event lands first, and expect `ConcurrencyError`. For reconcile, `killWorker` lies between the two calls. Use a worker string that `parseWorker` rejects, so nothing is killed.

`pnpm typecheck` and `HOME=/nonexistent pnpm test` are enough to check all of this. Nothing here needs the integration half.
