## Design note: #840, a stopped projection on the health dot

### The trap the ticket does not name: `checkpoint` is a `bigint`, and `Health` goes over the wire as JSON

`StoppedProjection.checkpoint` is `bigint | null` (`packages/daemon/src/store.ts:63`). The beacon's own column encodes it as a string for this reason: *"`checkpoint` is a string, since JSON has no bigint"* (`store.ts:67`). `Health` reaches the page as `JSON.stringify(await readHealth())` in the SSE route (`apps/board/src/app/api/stream/route.ts:94`). The `catch {}` around it swallows the failure: *"The next tick asks again."* (`:95-97`).

So if `readHealth` passes the beacon's list through unchanged, the first stopped projection makes every health frame throw. The page never hears about the stopped projection. It keeps the last answer it had, which is green. That is the exact failure this ticket exists to remove, and no test of `bearing` would catch it.

**Decision.** `Health.stoppedProjections` is `readonly { name: string; checkpoint: string | null; error: string }[] | null`. The type is declared in `health.ts`, not imported from `@lingtai/daemon`. `readHealth` maps `checkpoint` with `.toString()`. Do the mapping in a small exported pure function, for example `stoppedOnTheWire(status)`. Its unit test asserts `JSON.stringify` of a `Health` carrying a stopped `spend` at `12n` does not throw and round-trips `'12'`. If importing `health.ts` in a unit test reaches a database (it imports `@lingtai/daemon/control` and `@lingtai/projector`, `health.ts:18-19`), put the function in a sibling file with no imports.

### What `readHealth` returns in each case

| Case | `stoppedProjections` |
|---|---|
| `status` present | `status.stoppedProjections` mapped. `null` stays `null`, which means the daemon predates 17a (#839). |
| `!status` (`health.ts`) | `null`, and only for a row that is absent: `daemon: 'never'`. A `readStatus` that rejects, or a list `decodeStopped` refused (`store.ts:76`), is thrown into the `catch` below, so the dot says *unknown*, never green. |
| The `catch` branch (`:67`) | `null`, beside `error`. |

`bearing` treats `null` as *unknown* in every branch. It never treats it as empty.

### Where the branch goes in `bearing`

The new branch goes after `board.error` (`bearing.ts:118-125`) and before `board.lag === null` (`:126`). Its guard is `board.daemon === 'up' && (board.stoppedProjections?.length ?? 0) > 0`.

- **Ahead of `lag === null`.** Once 17c (#841) lands, a stopped `task_view` can sit beside a projection that was never built. The stopped report is the more specific fault, and its remedy is the rebuild.
- **Ahead of `code?.wrong` (`:151`).** That branch's remedy is a restart, and a restart alone throws again on the same event (`daemon.ts:26-27`). The remedy has to say *rebuild first*. Keep `code.said` in the title through `also()`, as every branch does (`bearing.ts:15-17`).
- **Only while `up`.** On a `stale` beacon the list belongs to a dead process, so the stopped branch does not fire. The result is **exactly** what `bearing` returns today for the same input with the list removed. That means behind/no-daemon `warn` when lag is above 0, and today's `pass` when lag is 0, with `no beat for Ns` in the title. The test for "stale says *stale*, not *stopped*" is: deep-equal to the same call with `stoppedProjections: []`, and no `stopped` in label, why or title. Making a stale beacon at lag 0 non-green is a separate ticket, and its edge is out of scope here.

### The words

The remedy matches `lingtai doctor` (`apps/cli/src/doctor.ts:732`), so the board and doctor say one thing about one row, as `health.ts:51-53` asks.

| Part | One stopped | Several stopped |
|---|---|---|
| `label` | `spend stopped` | `3 projections stopped` |
| `why` | `spend stopped — rebuild first: lingtai projection rebuild spend, then lingtai restart` | One `rebuild` per name, then `lingtai restart` |
| `title` | `also(...)` of `<name> stopped at seq <checkpoint>: <error>` (with `at an unread checkpoint` when `null`), then `beating(board)` | Same, one entry per projection, `; `-joined |

**`null` while `up`.** Add the *"the running daemon predates the stopped-projection report"* clause in `beating()`'s `up` arm (`bearing.ts:73-77`), next to the in-flight count. The clause is a helper, `predates()`, shared by `beating()` and the `lag === null` branch, which returns before `beating()` is called. Every other `up` title goes through `beating()`. Under `stale` or `never`, `beating()` is unchanged.

### `Following()` warns too, and that is intended

`warning()` (`live.tsx:263-266`) shows the dot on every other bar whenever `bearing` returns `warn`. So a stopped projection appears there too. That is correct: it is *the system not doing what the code says*. It is not a new chip.

### Tests (all unit, in `apps/board/unit/bar.test.ts` beside the existing `bearing` cases)

- The `board()` fixture (`bar.test.ts:26-32`) gains `stoppedProjections: []`. With that default, every existing expectation stays as it is. Do not edit any of them; an edited expectation is a change in behaviour.
- New cases: the four the ticket lists, plus the JSON round-trip above.
- **Order matters:** `stoppedProjections` alongside `code: behind` gives the stopped `why`, and the title still contains `behind.said`.

Nothing here needs `pnpm test:integration`. The person's check in `## Done when` stands in for the end-to-end path. The event that settles it on the log is the beacon row's `stopped_projections` column, since stopping writes no event of its own.
