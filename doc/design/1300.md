# #1300: the shape of the change

The runtime part is as small as the ticket says. Most of the work is in the recipe: `copilot` is refused everywhere except `implement` today, so a recipe with `agent: copilot` at `review` does not resolve. The ticket also asks for triage, and triage cannot be built on an ACP agent. §3 records that decision.

## 1. The runtime: append the section once, and send that text everywhere

`acpRun` (`packages/agent/src/acp.ts:317`) sends `request.prompt` in two places:
- to the hook socket as `UserPromptSubmit` (`:519–520`, `prompt: request.prompt`);
- to the agent itself (`:533`, `prompt: [{ type: 'text', text: request.prompt }]`).

Build the prompt that is actually sent once, near the top of `acpRun`:
- with `request.outputSchema` set, it is the request's prompt plus the *How to reply* section, in E8's text;
- without one, it is `request.prompt` itself, the same string. This is the unchanged case the first Done-when test checks.

Use that one value at both call sites. The hook record and the agent must not see different prompts. Make the builder a small exported pure function, e.g. `withReplyShape(prompt, schema)`, so the unit test can check the exact text without spawning anything.

Write the run-log line through the `note` already in scope (`acp.ts:344`, `trace?.note(label, detail)`), e.g. `note('reply shape', 'appended the output schema, N bytes')`. Write it only when the section was added.

`COPILOT_CAPABILITIES.acceptsOutputSchema` stays `false` (`acp.ts:47`). The runtime never sets `outcome.structured`, so review falls to `parseFindings(outcome.text)` (`packages/actions/src/agent-action.ts:1330–1331`). The capability's own doc says it means *"Whether `RunRequest.outputSchema` reaches the model"* (`packages/agent/src/runtime.ts:44`). After this change the schema does reach the model, but as text, not as a constraint. Add one sentence to that doc comment: a runtime may still ask for the shape in prose when the flag is false. Without it, a later reader will "fix" the flag to `true`.

Nothing in `claude-code.ts`, `codex.ts` or `codex-text.ts` changes.

## 2. The recipe: copilot is no longer limited to `implement`; it is limited to unsandboxed recipes

`IMPLEMENT_ONLY_AGENTS` / `isImplementOnlyAgent` (`packages/recipe/src/recipe.ts:1387–1394`) gives two reasons: *"an ACP agent takes no output schema … and it is not sandboxed yet."* This ticket removes the first. The second still holds: nothing in the ACP runtime reads `RunRequest.sandbox`.

In `Recipe.superRefine` (`recipe.ts:3519–3549`):
- **Drop the refusal of `runtime.agent: copilot`** (`:3519–3526`). `agentRefusal` already holds `runtime.agent` to the runtime this conductor dispatches (`packages/conductor/src/conduct.ts:495–506`). Triage does not read `runtime.agent` (see §3), so nothing else depends on it.
- **Drop the step/judge refusal** (`:3539–3543`). `agent: copilot` becomes legal at every step whose `agentPlugin.at` serves it, and `judge: copilot` becomes legal wherever a judge is. A judge needs nothing more: `askTheAgent` builds whatever runtime the entry names through `runtimeNamed` → `createRuntime(id)` (`conduct.ts:1242–1251`, `:3580`). The judge prompt already asks for its answer in prose (`packages/conductor/src/judge-agent.ts:219`), and the judge sends no `outputSchema` (that file never mentions it).
- **Widen the sandbox refusal to every place copilot is named**: any step's `agent:`, any `judge:`, and `runtime.agent`. Today it fires only at `implement` (`:3544–3548`) because every other place was already refused. A judge can run sandboxed (`conduct.ts`, `judgeDecision.kind === 'sandboxed'` inside `askTheAgentBody`). So can a review, through the same `sandboxFor` port (`agent-action.ts:190`). Any of these would run unwrapped without saying so. Keep the existing wording, *"… copilot cannot run sandboxed yet"*, which the current test matches (`packages/recipe/unit/implement-only-agent.test.ts`).
- **Rename the set** to what it now means: e.g. `UNSANDBOXED_AGENTS` / `isUnsandboxedAgent`, with its doc comment rewritten to give the sandbox reason only. Its two other readers keep their filters:
  - the setup wizard (`packages/setup/src/propose-setup.ts:104–105`);
  - `offeredRuntimes` (`apps/cli/src/agents.ts:199`).

  The wizard proposes a sandbox step (`propose-setup.ts:259`), and a wizard that proposes both copilot and a sandbox writes a recipe §2 refuses. Proposing copilot in setup is out of scope here. Fix the comment at `propose-setup.ts:104`, which says *"runs only at `implement`"*.

Rewrite `implement-only-agent.test.ts` (and rename it to match):
- copilot resolves at `review`, as `judge:` at `proposed` with `when: findings`, and as `runtime.agent`. The first is the ticket's Done-when line.
- each of those, under `sandbox: { enabled: true }`, is refused with the sandbox sentence.
- `discuss.agent: copilot` is still refused by the enum. Keep that case.

## 3. Triage cannot run on copilot, and this ticket does not make it

The ticket's *Want* names triage. The code does not allow it, and the ticket's own *Fix* (*"Nothing changes in … `triage.ts`"*) and *Edges* (*"does not widen"* `DiscussAgent`) close the only way to build it:

- `Triage.agent` is `DiscussAgent.default('claude-code')` (`recipe.ts:3033`), and `DiscussAgent` is `z.enum(['claude-code', 'codex'])` (`:2928`). `triage: { agent: copilot }` is refused when the recipe resolves.
- Triage runs with `tools: 'none'` unless `agent: codex` (`recipe.ts:3061–3064`; `apps/cli/src/triage.ts:1344`). Copilot throws `ToolsCannotBeDenied` for `tools: 'none'`, because its ACP agent has no tool-free mode (doc/design/1298.md §4, experiment 019 E2). That is why `DiscussAgent` excludes it, and `apps/cli/unit/discuss-agent.test.ts` holds the enum to that.

So triage on copilot is not built here. Nothing about the schema blocks it: `triage.ts:1456` already leaves the schema out when `acceptsOutputSchema` is false, and the brief asks in prose. If someone later wants it, it is a separate ticket, and that ticket has to decide whether triage may run an agent that can use tools. Say this in the commit body, without a closing verb (*"triage on an ACP agent is not done by this; see `DiscussAgent`"*), so the ticket's *Want* is not read as met.

## 4. Tests

- `packages/agent/unit/acp.test.ts` already drives a fake agent and a fake hook (`:434` builds the capabilities; see its `hook`/`spawn` seams in `AcpOptions`, `acp.ts:263`). For a request with `outputSchema`, assert that **both** the text in `session/prompt` and the hook's `UserPromptSubmit.prompt` end with the section. For a request without one, assert both equal `request.prompt` exactly.
- Review over a fake runtime with `acceptsOutputSchema: false` and no `structured` (use the fake-runtime helpers the existing `agent-action` unit tests use):
  - reply text that is a valid `ReviewAnswer` JSON yields its findings;
  - reply text that is prose with no JSON yields `unreadable`.

  This tests the route; it does not spawn copilot.
- All of this is unit-level. Nothing here needs `pnpm test:integration`. A real Copilot is measured only by E8, and that stays out of reach inside a pass.

## Edges the ticket does not settle

- **A fix round re-runs review**: each run builds the prompt again from its own request, so the section is never appended twice. The builder is pure and keeps no state.
- **What settles a disputed reply afterwards**: the review's own recorded outcome, as the review action already emits it. The prompt record (`context.prompted`, `agent-action.ts:1121`) still lacks the section, as the ticket accepts. The run log's `reply shape` line shows that the section was added while the run's log still exists.
- **A daemon running the old code**: the recipe change is in `packages/recipe`, which a running daemon loaded at start. A recipe naming `agent: copilot` at `review` is refused by that daemon until it restarts. Write the recipe after the restart, not before (*code, restart, paste*, doc/design/the-plugin-body.md).
