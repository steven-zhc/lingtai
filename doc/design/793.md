# Design note: #793, one shared projection store per process

## Where it goes

All of the change is in `packages/projector/src/choose.ts`, plus two small additions in `@lingtai/event-store` and two callers that need to close the store. None of the eight reader call sites change. They already send `url` through as `undefined` when the caller gave none (`task-view.ts:1167`, `spend.ts:319`, `projection.ts:282`, …). The only one that passes a `url` is `lingtai doctor`. The comment at `choose.ts:31` says so: *"`lingtai doctor` reports on a URL it was given, and that is the only caller that passes one (#214)."*

## The decisions the ticket leaves open

**1. Reuse `closableOnce` by exporting it. Do not copy it.**
`closableOnce` is in `packages/event-store/src/closable.ts:29`, but `packages/event-store/src/index.ts:18-19` exports only `ProcessLogClosedError`. Its refusal is hard-coded: `if (closed) return Promise.reject(new ProcessLogClosedError())` (`closable.ts:35`). That error's message is *"the process log was closed when the command finished"*, which is the wrong name for a projection read.
- Export `closableOnce` from `@lingtai/event-store`.
- Give it an optional second argument, `refuse?: () => Error`, defaulting to today's `ProcessLogClosedError`. The log's behaviour stays the same.
- `@lingtai/projector` already depends on `@lingtai/event-store` (`packages/projector/package.json:18`), so this adds no edge to the dependency graph.
- Add `ProcessProjectionsClosedError` in projector. Export it from `index.ts` beside `withProjectionStore` (`index.ts:43`).

**2. The seam a unit test can reach.**
The first *Done when* item asks for a fake factory that counts opens. Today `withProjectionStore` calls `projectionStore` directly (`choose.ts:67`), so a test cannot substitute anything. Split it like this:
- An internal `withStoreFrom(shared: ClosableOnce<ProjectionStore>, open, options, fn)` holds the branching:
  - With `url` set, it does what `choose.ts:67-72` does now: open, run, close in `finally`.
  - With `url` unset, it does `fn(await shared.get())` with no `close`.
- The module holds `const process_ = closableOnce(() => projectionStore({ max: 4 }), () => new ProcessProjectionsClosedError())`, the same pattern as `packages/event-store/src/choose.ts:63`.
- `withProjectionStore` is `withStoreFrom(process_, projectionStore, …)`.

The unit test builds its own `closableOnce` around a fake opener and drives `withStoreFrom`. It never touches `chosenStore()` or a database.

**3. The caller's `max` is ignored on the shared path.**
Every reader passes `max: 1`, and that number describes a pool that lives for one query. The shared store is always opened with `max: 4`. It is the first open that decides the pool, so honouring the caller's `max` would leave pool size to whichever read came first. The `url` path keeps the caller's `max`, as today.

**4. The `'error'` listener goes in `createPostgresProjectionStore`, on every pool.**
Put it at `postgres.ts:223`, not only on the shared pool. The runners' long-lived pools (`projection.ts:145`) have no listener either, and they face the same dropped-idle-client throw. Adding a listener changes nothing in a runner except that it no longer crashes. That is not "changing the runners' stores", which the ticket puts out of scope.
- Write it as a small exported function, `listenForIdleErrors(emitter, write = console.error)`, that writes one line to stderr. `postgres.ts` calls it on the pool.
- The *Done when* test hands it a plain `EventEmitter`, emits `'error'`, and asserts that nothing throws and one line was written.
- That keeps `pg` out of the unit half. It also stays clear of `packages/event-store/unit/on-postgres.test.ts`, which fails any integration file that reaches `pg` without being listed in `ON_POSTGRES`.

**5. Also set `allowExitOnIdle: true` on the shared Postgres pool.**
Do this as well as closing it explicitly, not instead. The trap the ticket names is a socket holding the process open, and there is a caller the ticket does not mention: `apps/site/scripts/snapshot.ts` imports `readTasks` and `readSpend` (`:4-5`) and never closes anything. Today each read closes its own pool. With a shared pool and no unref'd idle clients, that script would hang for pg's idle timeout. Also add `closeProcessProjections()` to that script's end, in a `finally`.

## Closing it in the CLI

`finish` takes **one** `close` (`apps/cli/src/ending.ts:38-42`), and `entry.ts:29` passes it `closeProcessLog`. Pass a combined close instead:
- Run `closeProcessLog()` and `closeProcessProjections()` under `Promise.allSettled`, so neither waits on the other and one rejecting does not skip the other. Then rethrow the first rejection.
- Both run inside the single `CLOSE_BUDGET_MS` (`ending.ts:9`), and the existing exit fallback still covers a close that hangs.
- Import `@lingtai/projector` dynamically in the same place `@lingtai/event-store` is imported (`entry.ts:26`), so help and unknown commands still load neither.
- `ending.ts:24`'s message names *"the log's connection"*. Make it say *"the store's connections"*.

**The daemon is a CLI command and needs nothing extra.** `packages/daemon/src/control.ts` and `packages/conductor/src/queue.ts` / `day-ceiling.ts` call these readers. They will share the pool for the daemon's whole life, and `entry.ts` closes it on exit like any other command.

**The board never closes it, and that is correct.** It is one process for its whole lifetime.

## SQLite

`projectionStore()` hands out a fresh `openSqliteProjections(choice.path)` handle per call (`choose.ts:58-59`). The shared path holds one handle until `closeProcessProjections()`. `node:sqlite` is synchronous, so the parallel reads the board makes queue on that one handle rather than racing.

Rewrite the doc comment at `choose.ts:42-49`, which says *"Not memoised, because every caller here opens one around a single read"*. That is now false for the shared path and still true for the `url` path. Say which is which.

## What can be checked inside a pass

Everything in *Done when* is unit-level: the fake opener, the `EventEmitter`, and the refusal after close.

The one claim nothing here can check before the merge is that a real Postgres pool, shared across the board's parallel `Promise.all` reads, behaves as measured. That needs the integration half or the live board. Afterwards, the `spend.lag` and `tasks.read` spans from #787 settle it: `spend.lag`'s p50 was 345ms and should fall toward the 6–9ms a reused pool measured.
