# Design note: #1171, two `prj-` events and their reduce

The ticket already gives the shapes, the transitions and the traps. This note adds the one cost the ticket does not mention and the few choices it leaves to you.

## The cost the ticket leaves out: ~30 hand-built `ProjectState` literals

`ProjectState` (`packages/domain/src/project.ts:19-54`) is the type of more than `emptyProject`. Twenty files besides `project.ts` declare a `ProjectState` value by hand. **Seventeen of them write every field out and do not spread `emptyProject`.** For example, `apps/cli/unit/conduct-continuing.test.ts:25-35` lists `project … refused: null, paused: null, version: 1, lastSeq: null`.

Adding `recipe` and `sandboxObserved` as required fields therefore turns each of those into a `tsc` error. The files are:

- **apps/cli**
  - `unit/conduct-continuing.test.ts`
  - `unit/conduct-ownerless.test.ts` (2 literals)
  - `unit/run-continuing.test.ts`
  - `unit/run-ownerless.test.ts` (2 literals)
  - `integration/init.test.ts` (4 literals, at `:354`, `:379`, `:401`, `:425`)
- **packages/conductor**
  - `test/one-attempt.ts`
  - `unit/github-client-for.test.ts`
- **packages/daemon**
  - `unit/clients-for-projects.test.ts` (3 literals)
  - `unit/continued-is-read.test.ts`
  - `unit/converge-approved-label.test.ts`
  - `unit/converge-ownerless.test.ts`
  - `unit/converge-refs.test.ts`
  - `unit/converge-write-and-record.test.ts`
  - `unit/decisions-over-a-recorded-stream.test.ts`
  - `unit/reconcile-release.test.ts`
  - `unit/reconcile-ticket-version.test.ts`
  - `integration/converge.test.ts`
  - `integration/injected-store.test.ts`

These three already spread `emptyProject` and need nothing:

- `apps/board/unit/pending.test.tsx:27-43`
- `packages/setup/unit/apply-setup.test.ts`
- `emptyProject` itself, which only needs the two new `null`s

**Decision:** keep both fields required, typed `… | null`, the same way `refused` and `paused` are typed today. Add `recipe: null, sandboxObserved: null` to each literal, beside `paused: null`. Make no other edit to those files.

Do not make the fields optional (`recipe?:`) to dodge the edits. That would let *absent* mean the same as *not recorded yet*, which is what the ticket's Edges rule out ("never an empty recipe"). It would also let a later reader forget the null check.

Do not convert those literals to `...emptyProject` spreads either. That changes far more lines in files this ticket does not own.

**Watch out: four of these files sit outside `pnpm test`.** `apps/cli/integration/init.test.ts`, `packages/daemon/integration/converge.test.ts`, `packages/daemon/integration/injected-store.test.ts` and `packages/conductor/test/one-attempt.ts` are type-checked by `pnpm typecheck` (`pnpm -r --if-present typecheck`, root `package.json:15`) but never run by the unit suite. A green `pnpm test` says nothing about them, so `pnpm typecheck` is the check that matters here. Find the sites with:

```
git grep -nE 'ProjectState = \{|satisfies ProjectState'
```

This lists every literal without opening files one by one.

## Where each piece goes

**Reducer.** Two `case`s in `reduceProjectEvent` (`project.ts:71-123`), placed before the `default:`. Each follows the shape of `case 'ProjectRefused'` (`:103-106`):

```ts
{ ...state, ...at, recipe: { ...d, seq: event.seq, at: event.at } }
```

- Neither case touches `project`, `configHash` or `paused`. That is what keeps a stream holding only `ProjectRecipeChanged` neither registered nor pending.
- A later `ProjectConfigured` keeps the recipe without extra code: its case (`:89-101`) spreads `...state`, so the recipe survives provided nothing in that case is changed.
- `ProjectSandboxObserved` stores `{ kind, runId, seq, at }`, so `sandboxObserved` matches what the ticket specifies.

**Payloads.** Neither payload carries `project`, unlike `ProjectRefused`, `ProjectRecovered` and `ProjectConfigured`. Follow the ticket's shapes exactly. The stream id already names the project, and leaving `project` out is what lets `recipeChange` work before `state.project` is set. `turnTransition` instead returns null on `project === null` (`:194-195`), because its payload needs the name. **Do not copy that guard.**

**Actor typing needs no cast.** `ToAppend` takes `actor` from `Envelope.actor: string` (`envelope.ts:92`, `:99`), so `actor: by === 'file' ? 'conductor' : by` type-checks as written. The runtime check is `Actor`'s regex (`envelope.ts:33-38`). The `by` schema's `human:` alternative must use the same character class, `[\w.@-]+`. That way every `by` the schema accepts is also an `Actor` the store accepts. The test the ticket asks for, `Actor.parse(next.actor)` on both branches, is what pins this.

**Return types.** Each transition returns exactly its own event, not a union with the other:

- `recipeChange` returns `ToAppend<PayloadOf<'ProjectRecipeChanged'>> | null`.
- `sandboxObservation` returns `ToAppend<PayloadOf<'ProjectSandboxObserved'>> | null`.

**`EVENT_AT` rows.** `ProjectSandboxObserved` gets the union of the two rows the ticket names:

- `SandboxBoundaryRecorded` is `['prepared', ...AGENT_STEPS, 'build', 'proposed', 'merge']` (`events.ts:2666`).
- `BaseChecked` is `['proposed', 'end']` (`:2682`).
- The new row is `['prepared', ...AGENT_STEPS, 'build', 'proposed', 'merge', 'end']`. Write it out spread like this, not as a hand-expanded list.

`ProjectRecipeChanged` is `['claim', 'end', 'outside']`.

**No `BUMPED` entry.** Both types are new, so they start at schemaVer 1. `BUMPED` (`events.ts:2723`) lists only types that have moved on.

**`NOT_YET_APPENDED`.** The set is `scripts/events.ts:56`. Add both types to it, and widen its docstring (`:49-55`) to name #1175 and #1180 as the tickets that remove them. That docstring already describes the "declared before anything appends them" case for #1164. The test fails the moment the finder sees an append site for an entry in this set (`events-json.test.ts:72-73`). The builders in `project.ts` are not inside an `append(` call, so they do not trip it. Do **not** add `ELSEWHERE` rows yet: an `ELSEWHERE` row and a `NOT_YET_APPENDED` entry for the same event would contradict each other.

## The header and `ProjectConfigured`'s text

**The header.** The `project.ts` header (`:1-14`) cites `doc/decisions-archive/0005-config-in-target-repo.md`. Replace it, cite 0128 instead, and drop the 0005 link entirely. This is an edit to a code comment, not to an ADR, so it needs no superseding file: 0128 is the superseding decision, and it is already accepted.

**`ProjectConfigured`.** Its `@summary` (`events.ts:2247`) reads *"The conductor read a project's recipe from its base branch and recorded which version it was."* Rewrite it as the registration 0128 §3 describes: owner, base, and a resolved `configHash` that is not the Project's recipe. It must stay one sentence of at most 140 characters, with no ADR or issue number (`events-json.test.ts:127-150`). The docstring's opening also says *"The recipe as resolved from origin/<base>"* (the ticket cites `events.ts:2228`). The line numbers have moved; find it by searching for the phrase rather than by line. `pnpm events:generate` carries the new summary into `doc/events.json`, so regenerate *after* the text is final.

**Do not touch `ProjectState.base`'s field comment.** It says *"The branch this project's recipe is read from and merged into"* (`project.ts:27-28`). That claim belongs to F5, which is out of scope.
