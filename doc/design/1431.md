# #1431: design note for the shared question pools

## Where it goes

Everything lives in `packages/event-store/src/queries.ts`, plus one constant used in `choose.ts`/`db.ts`. No caller changes.

1. **A pool registry with an injected factory.** Don't use a bare module-level `Map`. Add `makePostgresPools(create)`. It returns `poolFor(url)`, which builds a pool the first time it sees a URL and returns the same pool after that. Export a process default as well: `sharedPostgresPools = makePostgresPools((cfg) => new pg.Pool(cfg))`.
   - `PostgresLogQueriesOptions` and `PostgresTicketSqlOptions` (`queries.ts:208`, `:380`) each get an optional `pools`, defaulting to the shared registry.
   - The unit test builds its own registry over a fake `create` and hands the same one to both factories. That proves "two factories on one URL share it" without process-global state leaking between tests.
   - The fake pool should look like the projector's `QueryPool` (`packages/projector/src/postgres.ts:247`, *"The part of a `pg.Pool` a read needs, so a test can hand a fake one"*), extended with `connect` and the client's `release`.

2. **Look the pool up per question, not at construction.** `queries.ts:227-231` keeps the URL lazy on purpose: *"Read per question rather than at construction, so building one of these never throws: `postgresUrl()` refuses when nothing is configured"*. So `ask` and `withClient` call `pools.poolFor(url())` inside the Effect. Don't call it when the factory is built.

3. **Use one helper for both factories.** `ask` (`queries.ts:236-247`) and `withClient` (`:393-402`) become a single acquire/use/release over `pool.connect()`:
   - On success the client is released with `client.release()`.
   - On failure it is released with `client.release(err)`, which tells pg-pool to discard the client rather than reuse it. That is what makes the ticket's edge *"a connection the server dropped … the next query takes a fresh one"* hold.
   - Write it with `Effect.acquireUseRelease`, keeping `Effect.promise` and not `tryPromise`. The rule at `:233-235` stays: *"a driver's error must be the defect itself, not Effect's `UnknownError` around it"*.
   - Add no `async` function, so the ratchet doesn't move.
   - The `exec` arm (`:409-411`) goes through the same helper.

4. **Rewrite both comments.** The ticket only names `:384-388`, but `:213-219` makes the same claim: *"kept rather than pooled on purpose … a pool held here would be a connection a short command has to remember to end"*. Both should now say that `allowExitOnIdle` is what removes the "remember to end" cost.

## Traps

**The pool needs an `error` listener, or the board and the daemon die.** Without one, the ticket's edge "the pool discards a client whose connection errored" is false. #793 already hit this:

> *"An idle client the server drops emits `error` on the pool; with no listener Node throws and the board or the daemon dies (#793)"* (`projector/src/postgres.ts:228-238`)

Prisma's pool has the same guard (`suppressIdleConnectionErrors`, `@prisma/orm-postgres` `runtime.mjs:86`).

- The registry attaches a listener when it creates each pool. One line to stderr is enough, as `listenForIdleErrors` does.
- A client that is checked out needs a listener too, attached inside `connect`'s callback. The reasoning is at `projector/src/postgres.ts:258-263`: *"attached after a promise hop, an error arriving with the handoff is uncaught"*.
- `event-store` cannot import from `projector`, so copy the pattern; don't import it.
- The unit test should assert that `create`'s pool has an `error` listener once it is built.

**Shared pools need a long idle timeout too, not only `createDb`.** pg-pool's own default `idleTimeoutMillis` is 10 s. If only `createDb` gets the longer timeout, the snapshot pools go cold between two board renders, and the ticket's own figure (432 ms after 35 s idle) comes back.

- Define one named constant, for example `KEPT_IDLE_MS` in `queries.ts`, exported. Its comment should quote that measurement.
- Pass it to the shared pools as `idleTimeoutMillis`, and to `createDb` through `poolOptions.idleTimeoutMillis`.
- Use minutes, not hours (see the next trap).

**`createDb` cannot get `allowExitOnIdle`.** Prisma's `poolOptions` carries only `connectionTimeoutMillis` and `idleTimeoutMillis` (`postgres-*.d.mts:102-105`, forwarded at `runtime.mjs:86-90`).

- The process store's pool still exits only through `close` (`choose.ts:127`), which `closeStores` runs at the end of every CLI command (`apps/cli/src/cli.ts:1789-1793`).
- Any process that opens the process log and never calls `closeStores` will now linger for the new constant instead of 30 s. That is why the constant stays in minutes.
- `createDb(url)` at `choose.ts:102` gains a second argument, or the `poolOptions` are set inside `db.ts:20`. Prefer the second argument, so that `db.ts`'s "a second, independent connection" factory (0009) keeps its defaults for every other caller.

**`close` does not end the shared pools.**

- `closeProcessLogEffect` (`choose.ts:75`) still ends only `db`.
- Other factories may hold the same shared pool: doctor's direct URL (`apps/cli/src/doctor.ts:4095,4123`) and `log.ts:84,90`'s defaults. Ending it under them would break them.
- `allowExitOnIdle` is how a command exits with them idle. The unit test asserts that the option is passed, and that is the unit-level stand-in.
- The spawned-process proof that the CLI exits is integration (0060 §1). It can only be checked after the merge, which the ticket already accepts.

## What stays as it is

- **The waker.** `wake.ts:131` keeps its own `new pg.Client` on `directUrl`, as 0009 requires. The Done-when's "no `new pg.Client` left" applies to `queries.ts` only.
- **`max`.** It stays at pg-pool's default of 10.
- **Transactions.** No caller of `LogSql` relies on session state across calls. With a fresh client per question today, it couldn't. So moving to a pool changes no semantics.
- **The integration tests in `on-postgres.test.ts`'s list.** `packages/conductor/integration/db-tickets.test.ts:157-184` builds a `createPostgresTicketSql` per case. Those cases now share one pool, which is fine for the same reason.
- **The new unit test file.** It must not import `pg`. The fake factory keeps it off `REACHES_POSTGRES` (`packages/event-store/unit/on-postgres.test.ts:69`). That check scans integration files only, but a unit file that reaches `pg` would be integration by 0060 §1 anyway.
