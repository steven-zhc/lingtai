## Design note for #1340: the place line

### 1. Choose the project for the views the same way the menu does
The ticket says the crumb and views "are built from the URL's `project`, so they draw at once". That holds only when `?project=` is present. With no param and exactly one project, the home page selects that project from a read: `selectedProject` returns `param ?? (filters.length === 1 ? filters[0] : undefined)` (`src/lib/board.ts:1910-1912`). `FilterSlot` waits for that read for the same reason (`page.tsx:774-792`, and the comment at `:1138-1140`: *"without one, the selection needs `filters` (#993), so the whole slot waits"*).

So on `page.tsx`:
- **`param` set:** build the whole `PlaceLine` in the shell, with crumb `param`, views `Tickets · Recipe` and the streamed `MenuRows` inside the menu, as today.
- **`param` absent:** build the whole `PlaceLine` inside `FilterSlot`, from `m.only`. Its fallback is the line with the `<Pulse />` summary and no views.

If you build the views from `param` in the second case, a one-project install shows `Tickets` alone and has no route to Recipe. That is the #993 regression.

`ActionsPart` (`page.tsx:795-800`) already resolves `only` the same way. Leave it computing Pause from it.

### 2. Recipe is a view whenever a project is in view, registered or not
Today `Recipe` appears only for a registered project: `ActionsPart` returns null otherwise (`page.tsx:798`), and so does `Bar` without `registered` (`bar.tsx:53-55`). The shell cannot know registration without a read, and point 1 wants the line drawn at once. Draw `Recipe` for any project in view. The recipe page already answers a project that has no recipe (`Bar … here="recipe"` at `recipe/[project]/page.tsx:238` and `:360`). Pause keeps its registration check, because it stays in `ActionsPart`.

### 3. Taking Recipe out of `.topnav` on just two pages
Every other page must keep `Recipe` (task page, ticket step 3), so do not delete it from `BarActions`. Add `recipe?: boolean` to `BarActions` (`bar.tsx:71-95`), defaulting to `true`:
- `ActionsPart` passes `recipe={false}`.
- `RecipeBar` stops relying on `Bar`'s `registered` path. It passes `actions={<BarActions project={project} pause={pause} recipe={false} />}`, plus `here="recipe"` for `Report`'s marking.

The recipe page's two no-recipe paths (`:238`, `:360`) draw `PlaceLine` with no menu. `menu` is optional, and without it the crumb is the project name as plain text. Those paths have no `filters` read, and the ticket's Null edge wants `Recipe` drawn and current there.

`Projects` (`projects.tsx:131-162`) loses `AddProject`. `RecipeBar` hands `<Projects …/>` to `PlaceLine` as `menu`.

### 4. `+` becomes a row in `ProjectRows`
`ProjectRows` (`projects.tsx:56-115`) feeds both `MenuRows` and `FilterSlot`, so a last row there covers the streamed and unstreamed cases at once:
- The row is `<Link className="tab" href={where}>{why}</Link>`, using the existing `addTarget(app)` (`:35-38`). Its text follows the App (*add a repository* / *create the GitHub App…*), as the `+`'s title does today.
- The no-project branch (`:78-84`) is already a link to the same target, so it gets no extra row and no views.
- Delete `AddProject` and its use at `page.tsx:1160`.
- `FilterMenu` closes on any followed link (`filter-menu.tsx:26-28`), so the new row needs nothing of its own.

### 5. Key logic in `search.ts`, the DOM in `palette.tsx`
`search.ts` may import only types (`unit/palette.test.tsx:124-141`), so the pure functions receive plain data:
- **`isHashKey(k, t)` and `goKey(state, k, t, now)`:** `t` is the target described as `{ tag: string; editable: boolean }`. `palette.tsx` builds it from `e.target` (`tagName`, `isContentEditable`).
- **`goKey`'s result:** `{ state: { armedAt: number | null }, effect: { go: 't' | 'p' | 's' } | null }`. It is the same shape as `paletteKey`'s, and `composing()` (`search.ts:164`) is reused.
- **Effects in `palette.tsx`:** `t` and `p` call `.click()` on `[data-go=…]`, or on `.bar .brand` for `t`. That makes Next's `Link` do the client navigation, and it keeps `?project=` (`bar.tsx:47`). `s` sets `open` on `.bar details.filter` and focuses its first `a`.

In the capture listener (`palette.tsx:138-148`):
- Keep the ⌘K branch first and unchanged. It toggles even while the dialog is open.
- After it, the new keys return at once when `d.open`.
- Call `preventDefault` only when an effect fires, so a lone `g` on a page still types nowhere and costs nothing.

**Shared open function.** `open()` is a closure inside the effect today (`:119-136`). Lift it into a ref so three callers share it: the key, `#`, and a `document` `click` listener on `[data-palette]`, added in the same effect and removed in its cleanup.

**`#` must set the query after `showModal()`.** `onClose` resets the query to `''` (`:151-153`), so set `setQuery('#')` after `showModal()`. That is ordinary React state, so the caret lands at the end when the input value renders.

### 6. The Search button's key text
`bar.tsx` is pure, and the server cannot tell macOS from anything else. Draw both labels, `<kbd className="k-mac">⌘K</kbd><kbd className="k-pc">Ctrl K</kbd>`, and let CSS hide one by an attribute that `Palette` sets once on `<html>` (`data-os="mac"`, from the `isMacNow()` it already has). Do not write the text into the button from the client. An RSC navigation re-renders the bar and would put back the server's text. `RootLayout`'s `<html>` (`layout.tsx`) is not replaced on navigation, so an attribute set there persists. Until it is set, show `⌘K`. Both labels share one fixed-width slot, so nothing shifts.

The `title` cannot be switched by CSS, so it reads `Search · ⌘K / Ctrl K`. The Done-when test asserts it names the key.

### 7. Where the views and the badge sit
- **Markup:** the views carry `data-go` (`Tickets` → `t`; `PRs` → `p` later, from #1319). Their `title` is `Tickets · G T`. The project summary's title is `<p> · G S`.
- **Pure helper:** `placeViews` lives in `place-line.tsx` beside the component, so the unit test needs no DOM for the four-and-`More ▾` rule.
- **CSS:** put the badge selector (`.place .badge`) in `globals.css` with `--fail`. The amber scan in `bar.test.ts` (`:193-325`) covers everything rendered in `.bar`, so it will read the new selector; leave it unchanged and let it pass.

### Checks
Everything in this note is unit-level: the key reducer, `placeViews`, `PlaceLine` markup and the reshaped tests in `projects.test.tsx`, `bar-component.test.tsx` and `recipe-bar.test.tsx`. Nothing depends on `pnpm test:integration`. The one claim no unit test reaches is that `place-line.tsx` stays out of any `"use client"` graph. Keep it free of client imports, as `bar.tsx` is: the Next build (`apps/release/integration/build.test.ts`) is the only thing that would catch it, and that runs only after the merge.
