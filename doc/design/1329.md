# #1329 — the shape

## What is already there, and what it changes

#1301 and #1302 have landed in this worktree, so this ticket only reads what they added. The Fix's fallback, *"if they left them inside closures, lift them"*, applies to one value, covered below.

- **Who cannot be sandboxed is already declared in one place.** `UNSANDBOXABLE_RUNTIMES` and `isUnsandboxableRuntime` live in `packages/domain/src/events.ts:151-153`. The comment there reads: *"A fact about the agent, so it sits beside the id it is about."* `invocationDecision` (`packages/recipe/src/sandbox.ts:92-95`) and the resolve refusal (`packages/recipe/src/recipe.ts:3590-3597`) both read it. The board reads it from `@lingtai/domain`. Do not write a second list.
- **Copilot's host is exported, but its folder is not.**
  - The host is `COPILOT_NETWORK = ['*.githubcopilot.com']` (`packages/agent/src/copilot-sandbox.ts:23`).
  - The folder is computed inside the launch closure: `posix.join(home, '.copilot')` (`copilot-sandbox.ts:65`).
- **Copilot's telemetry is refused for every run, not as a Copilot addition.** `KNOWN_TELEMETRY_DOMAINS` (`packages/sandbox/src/policy.ts:172`) is written into the instance's `deniedDomains` (`policy.ts:186`). The board already imports from `@lingtai/sandbox/policy` (`sandbox-section.tsx:2`, `sandbox-view.ts:13`). So *"its telemetry refused"* in Copilot's line is a true sentence with no new fact behind it. Don't add a `telemetry` field to any runtime.
- **Codex's write folder is per run and the board cannot know it.** It is `run.codexHome`, which is `$CODEX_HOME` or `~/.codex` (`codex-sandbox.ts:92,127`). The ticket only asks for Copilot's sub-rows, so Codex gets none. Its line keeps the sign-in sentence only.

## Decision 1: the facts go in a leaf module behind a subpath

Create `packages/agent/src/sandbox-facts.ts` and export it as `@lingtai/agent/sandbox-facts` in `packages/agent/package.json`, beside `./auth` (`package.json:10`). Do not export it through the package root.

**Why not the root:** `@lingtai/agent`'s `index.ts` brings in the ACP SDK, `@lingtai/env`, the runtimes and every adapter. `sandbox-view.ts` is imported by `attempt-tab.tsx:9` and `sandbox-panel.tsx:19`, and its header says it is *"as data: no React and no reads"* (`sandbox-view.ts:2`). It should not gain that import graph.

**What the module holds:**

- A `Record<RuntimeId, RuntimeSandboxFacts>`, so a new `RuntimeId` with no row is a type error in this table. This follows `runtimes.ts`'s own argument (header comment: *"a `RuntimeId` added to the enum with no row is then a type error at this table"*).
- Each row holds data, not sentences:
  - `name`: Claude Code, Codex, GitHub Copilot, Antigravity.
  - `login`: a closed union, `'own token' | 'login readable'`.
  - `tokenCommand`: present only for Copilot, `lingtai token copilot`.
  - `network`: the hosts the runtime adds for itself.
  - `homeFolder`: the folder name under `$HOME` that it writes, `'.copilot'` for Copilot.
- `sandboxed` is derived with `isUnsandboxableRuntime`, never stored. The Antigravity row needs only `name`.

**Move, don't copy:** `COPILOT_NETWORK` and the `'.copilot'` segment move into this file, and `copilot-sandbox.ts` imports them back. That way the board and the launcher cannot disagree. Keep `COPILOT_NETWORK` exported under its current name so `copilot-sandbox.ts`'s callers and tests stay unchanged. Copilot's behaviour does not change.

**Imports:** only `import type { RuntimeId }` and `isUnsandboxableRuntime` from `@lingtai/domain`. No `@lingtai/env`, no `node:*`.

## Decision 2: the sentences belong to the board

`agentsInSandbox(runtimes, own)` goes in `apps/board/src/lib/sandbox-view.ts` and maps `login` to prose with an exhaustive `switch`. A new login kind is then a type error there rather than a blank line on the page.

**Reuse the sentences, don't rewrite them:**

- Codex's line uses the wording of `NOT_COVERED[0]` (`sandbox-view.ts:105`), *"its login stays readable to a Codex run"*. Pull it into a shared constant that `NOT_COVERED` also uses.
- Claude Code's line, *"signs in with its own long-lived token, never your login"*, is the short form of `CLAUDE_CODE_AUTH` (`sandbox-view.ts:110-111`).
- Leave `NOT_COVERED`'s and `CLAUDE_CODE_AUTH`'s rendered text on the task tab exactly as it is. That tab is out of scope.

**Return shape:** as the ticket gives it. In each `inside` entry, `adds.writes` is an absolute path, `posix.join(home, homeFolder)`, with `home` taken from the `roots` the card already has (`page.tsx:443`). Then `chipsOf` (`sandbox-view.ts:482`) draws it as `~/.copilot` like every other path chip. So the signature becomes `agentsInSandbox(runtimes, own, home)`. It stays pure, because `home` is an argument.

**An unknown id:** the result type keeps a third kind, `unknown: [{ id }]`, rather than putting it into `outside`. An unknown agent is not known to run outside the sandbox either. The lookup is `FACTS[id as RuntimeId]` with an `undefined` check. `runtimesOf`'s type says this cannot happen, so the test casts a string to reach it.

**Off:** `own === undefined || !own.enabled` returns `null`. Required or not makes no difference to the block (ticket Edges).

## Decision 3: the card gets `runtimes`, not the recipe

In `page.tsx`, at the `<SandboxSection …>` call (now at `page.tsx:436-444`, not `394-404` as the ticket says), pass `runtimes={view.ok ? runtimesOf(view.recipe) : []}`.

- `runtimesOf` lives in `packages/recipe/src/runtimes-of.ts:13`. Check that `@lingtai/recipe` exports it before reaching for a deep path.
- It reads `runtime.agent` and each step's `agent:`/`judge:`, and *"`discuss.agent` and `triage.agent` are not in it"* (`runtimes-of.ts:9-11`). That is the ticket's Done-when about `discuss:`/`pr:`. Test it through `agentsInSandbox(runtimesOf(recipe), …)`, so the claim is about the composed result.

`SandboxSection` stays a server component (no `'use client'` in `sandbox-section.tsx` or `page.tsx`).

**Where the block goes:** between `<p className="rcard-lede">` and `<Row name="state">` (`sandbox-section.tsx:153-158` in the ticket's numbering). It is drawn when `!recipeError && agents !== null`.

**The two sub-rows:**

- *reachable*: a `<Sub label="copilot">` beside *this recipe* and the vendor groups.
- *writable*: pass an extra sub-row into `PathsRow`, rather than forking it.
- Both are drawn only when some `inside` entry has non-empty `adds`. This is keyed on the facts, not on `id === 'copilot'`. The next runtime that adds something then gets a row for free, and the render test still pins "only when the recipe names Copilot".

## Edges the ticket leaves implicit

- **A required recipe naming Antigravity at `runtime.agent` rather than a step's `agent:`.** The resolve refusal reads steps only (`recipe.ts:3580-3597`). Whether such a recipe resolves is #1302's business. If it does resolve, this block draws Antigravity outside, which is the truth at run time (`invocationDecision`). Do not add a refusal here.
- **The cost to later tickets:** the `Record` type is the check, and the unit test that walks `RuntimeId.options` is its runtime twin. A test that greps the rendered page for a fixed agent list would go red on every new runtime; assert on `agentsInSandbox`'s data instead and render only once.
