# #488: design note

## What is actually there

The ticket says all five files match on today's events and `Hold`. **That is not true of their code.** Each one only *mentions* a retired name. None branches on one:

| File | Retired name it carries | What its code reads |
|---|---|---|
| `backlog.ts` | `StepFailed`, in a comment (`backlog.ts:73`) | `FindingProposed`/`FindingAccepted`/`FindingDeclined` on its own backlog stream (`:177`, `:184`, `:344`). These are concurrency checks around its own appends. |
| `branches.ts` | `PassRestarted`, in a comment (`branches.ts:29`) | nothing. *"this module imports nothing"* (`:16`) |
| `queue.ts` | `RepairRequested`, in a comment (`queue.ts:113`) | `task_view` rows through `readTasks`: `row.state`, `lastAttemptAt` and `repairPending` (`:79-103`, `:132-137`) |
| `schedule.ts` | `WorkItemBlocked`, in a comment (`schedule.ts:274`) | `reduceWorkItem(events).lifecycle.status` (`:304`) |
| `wizard.ts` | none. The three `Hold` hits (`:31`, `:145`, `:303`) are the **`Hold all` button and its label**, not the `Hold` type | `reduceProject`, and its own `ProjectOnboardingStarted` append (`:419`) |

0120's appendix decides which names retire (`doc/decisions/0120-a-reason-is-a-type.md:628-654`). The finding events, `ProjectOnboardingStarted`, `WorkItemLanded` and `IntegrationSucceeded` are **not** on that list: *"**Unchanged**: … `WorkItemLanded`, `IntegrationAttempted`, `IntegrationSucceeded`, … and the rest of `EVENTS`."* `WorkItemReleased` only gains a `cause`.

So in four files the `src` diff is a comment rewording. Do it the way `e0873ae8` did for `progress.ts`: describe the fact rather than spell the retired type. Leave `wizard.ts` alone; it has nothing to change. Do not invent read-model calls in order to look moved.

## The decisions

**1. `backlog.ts` keeps its `Finding*` matches.** They are the read half of its own writes: `acceptFinding` and `declineFinding` check the stream's last event before appending. They are about events that are not retiring. The ticket says *do not touch the writers*. Only `:73` changes, to something like *"the step still ends refused"*.

**2. `queue.ts`: change the comment only, and keep `repairPending`.** This is the trap. The comment at `:111-114` is the only place in the file that names `RepairRequested`, and it reads like an invitation to delete the field. But `heldUntil` returns `null` on `repairPending` (`:133`), and that is the exemption for logs written before #143 (`:121-129`). Removing it changes what the queue passes over, which the ticket forbids. Reword the comment to name the fact: *a repair bought before #143 and not yet claimed*. Leave the code byte-for-byte as it is.

The ticket says to pin `queue.ts` first, and `selectRunnable` reads the projection through `readTasks`. That makes it integration-only (`integration/queue.test.ts`), and integration tests cannot run inside a pass. With a comment-only diff, the unit-level guard is:
- `git diff -- packages/conductor/src/queue.ts` touches only lines inside `/** */`;
- `heldUntil`'s four cases (`integration/queue.test.ts:255-276`). These are pure. Copy them into a new `packages/conductor/unit/queue.test.ts` as the pin, so they run under `pnpm test`.

Do not extract `selectRunnable`'s filter into a pure function to make it unit-testable. That is a `src` change made only to pin a file whose code is not changing.

**3. `schedule.ts`: `tallyPass` keeps `reduceWorkItem`.** Only the `:274` comment changes; it becomes the lifecycle status (`blocked`) instead of the event. Moving the tally to `waitsOf` would **change its answers**:
- `reduceWorkItem` lets a later `WorkItemClaimed` or `WorkItemReleased` replace a block (`work-item.ts:261-263`, `:325-329`).
- `waitsOf`'s `resolutionAfter` resolves a wait only on `WorkItemUnblocked`, `ApprovalGranted` or `WorkItemClosed` (`read-model.ts:1173-1187`).
- `ApprovalGranted` is searched on the **run** stream, and `tallyPass` reads only the work item's stream (`schedule.ts:293`).

So a block followed by a release reads as `stopped` today and would read as `held` under `waitsOf`. Phase 2 changes `reduceWorkItem` together with the writers that also decide on it, which is 0120's *"at the switch only the read model and the builders change"*.

**4. Delete `triageRuns` and add nothing in its place.** It lives in `packages/domain/src/moves.ts:58`, not in any of the five files, and **it has no caller**. Running `grep -rn triageRuns` over `packages` and `apps` finds only its definition and `domain/unit/moves.test.ts`. No `src` file outside `domain` names `HoldTriaged` either, so nothing triages today.

The work:
- delete the function;
- delete its doc comment's mention in `moves.ts:1-5`;
- delete the `describe('triageRuns')` block and `triageRunsTags` in `moves.test.ts` (`:18`, `:201-323`).

Touching `moves.ts` and its test is in scope even though the ticket says *only these five files*, because its **Want** names the deletion.

**Do not add a `WaitReason`-keyed `triageRuns` to `wait.ts`.** 0118 §3 does name one (*"one pure function of the wait, `triageRuns`, beside `allowedResolutions`"*, `0118-a-hold-explains-itself.md:291-294`). But it would have no caller, and it would make *"`triageRuns` is gone"* false by grep. It belongs to whichever ticket wires the triage step, which will have a caller to test it against. Leave the `doc/design/*.md` mentions as they are.

## Tests

**`unit/tally.test.ts` is the one test that has to move onto the builders.** It hand-writes a `WorkItemBlocked` with a `CheckRed` `Hold` literal (`:46-58`). Move it in the first commit, before any `src` change, together with the new `unit/queue.test.ts`:
- Build the events with `aClaim`, `aWait`, `aLanding` and `aRelease` from `@lingtai/domain/test/events` (`packages/domain/test/events.ts:200`, `:311`, `:320`, `:325`).
- Build the wait as a `WaitReason`, e.g. `CheckRed`'s reason, passed through `aWait`.
- The builders return `Envelope`s and `tallyPass` reads a store. Either append `({ type, actor, data })` mapped from each built envelope to the memory store, or hand `tallyPass` an `EventStore` whose `read` returns the built slice.

Then add the case decision 3 turns on: blocked, then released, with no unblock, tallies as `stopped`. Today it reads `stopped`, and this case would go red if anyone later moves the tally to `waitsOf`. Every existing assertion stays as it is.

Leave these alone:
- `unit/backlog.test.ts` makes `Finding*` events, and no builder exists for them.
- `integration/queue.test.ts` makes only `WorkItemClaimed`/`WorkItemReleased`, which are unchanged, and nothing can run it inside the pass.
- `wizard`'s tests.
