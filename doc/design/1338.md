The ticket gets most of the shape right. There are three places where building exactly what it says would miss its own `Done when`, and they are what this note settles.

## 1. Refused on meaning or not parsed: two error classes, and the ticket's Fix 1 picks the wrong one

`resolveRecipe` turns every schema failure into a plain `RecipeInvalidError` (`packages/recipe/src/resolve.ts:301-307`). Only `refuseOnMeaning`'s output becomes a `RecipeRefusedError` (`resolve.ts:310-311`). The class's own comment says the two are told apart *"by `_tag` and never by the sentence"* (`resolve.ts:64-70`). So a refusal written into the schema arrives as the wrong class:

- **`required: []`**: do **not** put `.min(1)` on the array, as Fix 1 does. It would fail the parse and answer `RecipeInvalidError`, but `Done when` asks for `RecipeRefusedError`. Declare `z.array(z.string().min(1)).optional()`, and refuse the empty list in `refuseOnMeaning`.
- **`provider: jenkins`**: it is in the enum, so it parses. Refuse it in `refuseOnMeaning`, next to the existing `pr:` refusals (`resolve.ts:516-521`).
- **A `jenkins:` block when the provider is not `jenkins`**: also in `refuseOnMeaning`. When the provider *is* `jenkins`, write one sentence covering both keys (the "next release" sentence), not two lines.
- **`jenkins.user` / `jenkins.token`**: this check must run **before the parse**. `jenkins` is a `strictObject`, so an unknown key fails at `Recipe.safeParse` and is a `RecipeInvalidError` before `refuseOnMeaning` ever runs. Write a raw-input check in the style of `retiredTier` / `retiredLimits` (`resolve.ts:563`). It walks `raw.pr.ci.jenkins` defensively (any level may be a non-object) and returns one line per credential key: `` pr.ci.jenkins.token: credentials are never in the recipe — they go in `~/.lingtai/config.yml` as `jenkins.user` and `jenkins.token` (ADR 0117) ``.
  - Call it in `resolveRecipe` after the `retired` check (`resolve.ts:289-290`) and before the `withRuntime`/parse block.
  - Throw what it returns as `new RecipeRefusedError(ref, lines, where)`.
  - Any other unknown key inside `jenkins:` stays the strict object's plain `RecipeInvalidError`, as the ticket says.
  - Export the check beside `retiredLimits` so a unit test can call it directly as well as through `resolveRecipe`.

The ci refusals do not test for team mode. A solo recipe with `pr.ci.provider: jenkins` gets both the existing `pr:` line and the jenkins line. Each names its own key, and fixing either one alone does not make the file valid.

## 2. The schema, and where the defaults are not

Add `ci` to `Pr` (`packages/recipe/src/recipe.ts:3002`). `Pr` is already a `strictObject`, and its `limits` keeps its existing `.default` (that one predates this ticket and is not touched). Nothing inside `ci` gets a default:

- **`timeout`**: copy the `wall` refine that `limits` uses (`recipe.ts:308-311`: `z.string().refine((text) => positiveDuration(text), …)`) but **without** `Pr.limits.wall`'s `.default('5m')` (`recipe.ts:3009-3012`). That line is the easiest thing to copy by mistake.
- **`url`**: use zod 4's `z.url()`. zod is `^4.5.4` (`packages/recipe/package.json:24`). A path is never a Jenkins address, so the reason `repo.remote` avoided `z.url()` (`recipe.ts:3149-3153`) does not apply here.
- **The comment**: say what each key means. Name `~/.lingtai/config.yml` as the place for credentials. Carry the `source.tickets` sentence on hashing (`recipe.ts:1129-1137`) by reference rather than restating it.

**The hash test.** Test the cause rather than a pinned hash literal, which goes red whenever any unrelated default moves:

- `Recipe.parse` of a team recipe with `pr: {}` gives a `pr` that has no `ci` key (`'ci' in parsed.pr === false`).
- `hashRecipe` of that recipe equals `hashRecipe` of the same recipe after a `JSON` round trip with `ci` absent.

Together these show a file that does not write the key hashes as it did before.

**Older daemons.** An older daemon handed `pr.ci` refuses it, because `Pr` is strict. That is *code, restart, paste* working as intended; it needs no handling here.

## 3. `ciOf` in `settings.ts`, and the board reads only it

Put `ciOf(recipe)` beside `modeOf` / `branchOf` (`packages/recipe/src/settings.ts:255-270`) and export it through `packages/recipe/src/index.ts`. It returns:

- `provider`: `'github-actions' | 'none' | 'detect'`
- `required`: `readonly string[] | 'all'`
- `timeoutMs`: from `parseDuration` (`packages/recipe/src/duration.ts:13`), 3 600 000 when absent
- `from`: `{ provider, required, timeout }`, each `'recipe' | 'default'`

`'jenkins'` is not in the return type. A resolved recipe cannot carry it, but a test that calls `Recipe.parse` directly can. In that case `ciOf` throws an `Error` saying the recipe reached it unresolved. Do not widen the type, because #1339 would then have to handle a provider that has no adapter.

## 4. The board

`modeLines` takes `(recipe)` only, not `(recipe, source)` as the ticket says (`apps/board/src/lib/recipe-lines.ts:179`). Keep that signature.

- Add `ci` to the team branch's `pr` object (`recipe-lines.ts:207-213`), built from `ciOf(recipe)` and not from `recipe.pr?.ci`. That follows the rule the function's own comment states: *"a reading of the recipe … and never a second statement of the rule"* (`recipe-lines.ts:173-177`).
- Format the timeout with the formatter beside `parseDuration` (`duration.ts:22`), so a default shows as `60m`.
- Widen the type at `recipe-lines.ts:170`.
- Draw it as a second `step-set` row labelled `CI`, directly under the `PR` row at `apps/board/src/app/recipe/[project]/page.tsx:125-133`. Use the same markup and the same `← default` / `← recipe.yml` suffix convention, applied per value: a recipe that wrote only `timeout` shows `detect … ← default · every check ← default · 30m ← recipe.yml`.
- Solo stays `pr: null` and draws nothing.
