# Design: #392, one seam for `init`'s questions

## Where it goes

**`apps/cli/src/question.ts`, not `ask.ts`.** `apps/cli/src/ask.ts` is already taken. It holds `lingtai ask` / `lingtai answer`, the hold-a-ticket command from #147, and `lingtai.ts:52` imports it. Put the seam in a file of its own, with tests in `apps/cli/unit/question.test.ts`, which the root config's unit glob `{apps,packages}/*/unit/**/*.test.ts?(x)` already reaches (`vitest.config.ts:72`).

**`question.ts` imports nothing from `init.ts`.** It declares the slice of the world it needs:

```ts
{ ask: (prompt: string) => Promise<string | null>; log: (line: string) => void }
```

`InitWorld` (`init.ts:122`) already satisfies that shape. #391 says *"`lingtai add` asks the same recipe questions … through the same code"*, and `addCommand` (`lingtai.ts:362`) has no `InitWorld`. A seam typed on `InitWorld` would drag `init.ts`'s imports into `add` (`board.ts`, `@lingtai/event-store/schema`). The only import `question.ts` should need is `paint` from `@lingtai/env/colour`.

`add` is not wired in this ticket. It asks nothing today, and the ticket says no new questions.

## The shape

```ts
question(world, {
  name,        // 'the store' — the subject of the refusal
  flag,        // the text after "pass": '--store sqlite, or --store postgres --database-url <url>'
  given,       // what the flags said, already mapped to an answer; null when no flag spoke
  prompt,      // the words shown at a terminal
  current, detected, fallback,   // the default is the first of these that is not null
  show?,       // how a default is printed — the store's must be redactUrl
  choices?,
  validate?,   // (answer) => Promise<string | null>: null accepts, a string is why not
}) => Promise<{ answer: string } | { refused: string }>
```

### The decisions the ticket leaves open

**1. The seam writes nothing. The caller writes, the moment it gets `{ answer }`.**

- The store's write is not one key. It sets `database.store` and either sets or deletes `database.url` (`init.ts:450-452`, `:464-466`).
- It happens only after `world.database()` answered. The header says *"Nothing is written before its choice. The URL is written after the connection answered and the tables exist"* (`init.ts:18-19`).

With the write left to the caller, *"no TTY and no flag writes nothing"* holds by construction. The unit test then asserts that `validate` was never called, and that the result is `{ refused }`.

**2. `validate` is async, and the store's connection check lives inside it.**

The store's `validate` does three things:

- Accepts `''` (SQLite).
- Refuses anything not matching `/^postgres(ql)?:\/\//` with today's sentence (`init.ts:460`).
- Otherwise awaits `world.database(answer)`. On success it keeps the `SchemaOutcome` in a closure for the `describeSchema` line. On failure it returns `${redactUrl(answer)} does not answer — ${why}. Nothing was written`.

That is what *"validate refusing re-asks at a TTY and refuses without one"* means for the store. It is also what lets `chooseStore`'s `for (;;)` (`init.ts:403-478`) collapse:

- The settled-store check runs once, and the inherited-URL check runs once (the `inherited` flag at `:401` exists only to stop that loop going round).
- Then one `question()` call.
- The re-ask loop lives in the seam.

**3. How the seam answers:**

- **`given !== null`** is the flag's answer. Run `validate` on it once. If it fails, return `{ refused }` and never ask, even at a terminal. A flag cannot be re-asked.
  - This is today's `--store postgres` rule (`init.ts:474-477`, *"Going round again would reach … a question whose empty answer is the store it did not name"*), and `init.ts:477` becomes dead.
  - It also changes one untested path: a bare `--database-url <bad>` at a terminal used to fall through to the question (`candidate = null` at `:478`). It now refuses. This is #391's rule, and nothing in `integration/init.test.ts` pins the old behaviour (`'--database-url'` appears there only beside `--store`, at `:571`, `:626`, `:639`, `:642`, `:652`, `:668`).
- **`world.ask` returns null** means nobody is at a terminal. Return `{ refused: \`${name} needs an answer: pass ${flag}. Nothing was written\` }`. This happens **even when a `current` exists**: the ticket's rule has no exception for it, and #391's *"accept every default is one keystroke"* is a later ticket's flag.
- **An empty typed answer** takes the default. A typed answer is trimmed. `choices`, when given, rejects anything outside the list by re-asking. That goes through the same path as `validate`: log `paint.fail(why)` and ask again.
- **The prompt** is `paint.signal(prompt)`, plus ` [${show(default)}]` only when the default is non-empty, plus `': '`.

**4. The store's arguments:**

| Argument | Value |
|---|---|
| `given` | `named === 'sqlite' ? '' : flags['database-url'] ?? null` |
| `current` | `null` |
| `detected` | `null` |
| `fallback` | `''` |
| `show` | `redactUrl` |

`current` is null because the store reaches the question only when what is written does not answer. A working store returns before the question (`init.ts:407-412`). The header makes that deliberate: *"A store already written and connecting is reported and not asked about again"* (`init.ts:45-48`).

The test at `integration/init.test.ts:182-184` pins it (*"What the first run settled, the second does not ask again"*). #391's *"Re-running init asks every question again"* contradicts it. **Do not resolve that here**: the ticket requires those tests unchanged. The seam's `current` handling is proven in the unit tests with a synthetic question.

The pre-question refusals stay where they are, ahead of the seam, because they are not questions:

- `sqliteRefused`
- the exported-URL preset (`init.ts:379-397`)
- `--store postgres` with no URL (`:402-410`)
- `--store sqlite` beside `--database-url` (`:225`)

## The traps in the existing tests

All of these are in `apps/cli/integration/init.test.ts`:

- **`:75`: `expect(question).toMatch(/Postgres/)`.** The prompt the world receives must still contain *Postgres*. Keep the words `a Postgres URL for the log — empty for SQLite`.
- **`:435`: `not.toContain('--database-url')`** across all lines of a run that answered `''` at a terminal. **The flag text appears only in the refusal**, never in the prompt or in a re-ask line.
- **`:520`: `seen.lines.at(-1)` contains `'--store sqlite'`** with no terminal. The refusal must be the **last** line logged, and its `flag` text must contain `--store sqlite` verbatim.
- **`:194`: `interruptAt: 'ask:database'` throws from `world.ask`** and expects `rejects.toThrow(Interrupted)`. That is the Ctrl+C. The seam must not catch what `world.ask` throws.
- **`:668`: a failing `--store postgres --database-url`** must leave `seen.asked` `[]` and `seen.connected` `[gone]`. Decision 3 gives that.

**These tests are the integration half.** The file sits in `apps/cli/integration/` because it writes a real `config.yml` under a temporary `LINGTAI_HOME` (0060 §1: *"a temporary directory is still the filesystem"*). `pnpm test` does not run it, and it is under 803 seconds only as part of `pnpm test:integration`.

Running that one file is fine:

```sh
pnpm vitest run --project integration apps/cli/integration/init.test.ts
```

It needs no database: every world in it is scripted. What `pnpm test` can claim before the merge is the seam's unit tests. *"Every existing `init.test.ts` case passes unchanged"* is checked by that single-file run. The `build` step does not check it.

## Unit tests (`apps/cli/unit/question.test.ts`)

A fake world: `ask` shifts from a scripted array and returns `null` when it is empty, and every prompt and log line is recorded. Nothing touches the filesystem or a process.

- **`given` answers without calling `ask`.**
- **`given` failing `validate`** returns `{ refused }`, and `ask` is never called.
- **No answers, no `given`** returns `{ refused }` whose text is exactly `<name> needs an answer: pass <flag>. Nothing was written`. `validate` is never called.
- **`current: 'a'`, `detected: 'b'`** shows `[a]` in the prompt, and `''` returns `'a'`. With `current: null`, it shows `[b]`. With both null and `fallback: ''`, there is no bracket.
- **`show`** is applied to the bracketed default and never to the returned answer.
- **`validate` refusing a typed answer** logs the reason and asks again, and the second answer is returned. If the script then runs out (no TTY), the result is `{ refused }`.
- **`choices`**: an answer outside the list is asked again.
- **An `ask` that throws** propagates.
