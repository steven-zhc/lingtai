# Design: the problems behind *handled for you* (#1284)

## The shape in one paragraph

The projection keeps a raw list of **raised** facts, made of routes and redos, in a new bookkeeping column. On every `save` it calls the pure `problemsOf(raised, ticketState.waits, ticketState.claims)` in `packages/domain`, and writes the result to a second new column, `problems`. Problems cannot be reduced one event at a time: a route's answer is a wait that may resolve days later, on another stream, and `ticketState.waits` already holds that wait with its `resolution.by` (`packages/domain/src/ticket.ts:62-75`). So the projection stores the inputs, and `problemsOf` decides everything from them on each save. The pairing of a route with its wait, the kind, and `system` versus `you` are all decided inside `problemsOf`, and the projection makes none of those decisions. That keeps to the ticket's "one rule, called by the projection".

## Where it goes

**`packages/domain/src/problems.ts` (new), exported from the index.**
- `type Raised` is one of three shapes:
  - `{ _tag: 'Route', seq, at, runId, proposal: <tag>, candidate: <id> | null, decision: 'Selected' | 'Escalated' }`
  - `{ _tag: 'Redo', seq, at, runId, step }`
  - `{ _tag: 'Answer', seq, at, waitId, by, resolution }`: every `WaitResolved`, kept because the ticket reduce keeps only the first and the last one decides
- `type Problem = { kind, at, attempt: number | null, answeredBy: 'system' | 'you', waitId: string | null }`
- `problemsOf(raised, waits, claims): Problem[]`
- `PROBLEM_KINDS`: the 11 kinds in the ticket's order, `other` last. The panel tickets read this list, so the order is defined once.
- `seq` is kept as a string, as `ReportReview.seq` is (`ticket-report.ts:80`). It exists only for ordering.

**`packages/projector/src/ticket-report.ts`.**
- `State` gains `raised: Raised[]`.
- New `case`s in the reduce switch (`:508`). Each resolves the ticket with `ticketOf(ctx, event.streamId)`, the same way `RunProducedDiff` does (`:578`), and pushes onto `raised`:
  - `ProposalRouted`
  - `PassRouted`: same payload shape for these fields, and `routesOf` already reads both (`read-model.ts:90-91`)
  - `StepRedone`, and its retired name (the type after `StepRedone` in `events.ts`; check `RETIRED` for the exact type string)
- Routes are appended on the run's stream (`conduct.ts:5994`, `appendAt(runId, …)`). That stream is linked by `TicketClaimed` (`:524`) and `RunStarted` (`:511`) before any route is written.
- Dedupe on `seq` before pushing. A batch replayed after a crash must not add a fact twice.
- Two new columns, `raised jsonb not null` and `problems jsonb not null`. They must be added in five places:
  - `create`
  - `load`, where `raised` is read like `rounds`
  - `save`'s insert/upsert, where `problems` comes from `problemsOf(s.raised, t.waits, t.claims)`
  - `TICKET_REPORT_COLUMNS` and `ticketReportRowOf`, for `problems` only, read with `json(row.problems, [])`
  - `TicketReportRow.problems`
- `raised` stays bookkeeping the way `rounds` and `paid` are: in `load` and `save`, and absent from `TicketReportRow` (comment at `:142`).
- `packages/projector/unit/declared-shape.test.ts`'s `EXPECTED` gains both columns.
- `__snapshots__/ticket-report-rebuild.test.ts.snap` will change. Update it with `-u` after reading the diff. A snapshot that grew only `problems: []` and `raised: […]` is correct.

**`packages/conductor/src/report.ts`.**
- `report()` (`:463`) adds `handled`, built from `filtered` (project and kind already applied, `:467`), not from `placed`. A problem is placed by its own `at` (the ticket's Edges), not by the ticket's outcome.
- `answeringCost` is the sum of the window's `byPurpose` (`:509-516`) over `Answering`, `Judge` and `Triage`. The window, project and kind filters are already applied there, and reported, estimated and unknown are already kept apart (`Money`). Do not re-read spend for it.
- `latest`: the newest problems first, each carrying the ticket. Take 8, as `top` does (`:562`).
- `days` iterates the same day keys as the spend `days` (`:475`) so both charts share an axis.

## The decision the ticket leaves open: how a route meets its wait

The ticket says an escalated route is counted through "the wait it opened". Nothing on the log links the two: `ProposedEscalated` carries `run` and `proposal` (`wait.ts:147-152`), and `ProposalRouted` carries no `waitId`. Three facts in the code shape the rule.

1. **More waits than the ticket names come after a `Selected` route.** `run-attempt.ts` ends a pass with `ProposedEscalated` after a route was `Selected` and its move then failed:
   - the base could not be merged in (`:2121-2133`)
   - a conflict round could not be started (`:1756-1764`)
   - a land-again that could not be recorded (`:2096-2108`)

   A route-only count calls those `system`, and a separate wait count adds a second `you` for the same problem. That is the double count the ticket forbids, in a case the ticket does not list.
2. **Not every escalation opens a `ProposedEscalated`.** An unjudged `InputNeeded` opens `AgentQuestion` (`routing.ts:186-197`, and the doc at `:162-165`: "an unjudged `InputNeeded` … is the only case that reaches `AgentQuestion` rather than `ProposedEscalated`").
3. **Routes are written before the wait.** They are appended in one batch after the walk returns (`conduct.ts:5988-6004`), on the run's stream, and the pass's ending, the wait included, follows. So within a run the route that ended the pass is the run's last route by `seq` before the wait.

**The rule.** A wait with a `run` claims the **last** route on that `run.runId` whose `seq` is below the wait's, if all of these hold:
- the route is not already claimed;
- the tags agree: `ProposedEscalated.proposal._tag === route.proposal`, or `AgentQuestion` ↔ `InputNeeded`;
- any `Selected` decision is allowed. Escalated or not does not matter, which is how fact 1 is covered.

The pair becomes **one** problem:
- **kind**: from the route;
- **at**: the route's `at`, its own time (the ticket's Edges);
- **answeredBy**: from the wait, using its `resolution?.by === 'triage'`.

**What the pairing needs from the waits.**
- `TicketWait` has `at` but no `seq` (`ticket.ts:62-66`). Compare by `at`, with `seq` as the tie-breaker among routes.
- That is safe because the route batch is appended before the ending, and `Envelope.at` is the append time. The order is a fact of the log, not of this code. The events that settle it on a real log are `ProposalRouted.at` and the following `WaitStarted.at` for the same run.

**Everything left over.**
- A route left unclaimed counts as itself:
  - `Selected` with any candidate other than `hand-to-person` → `system`;
  - `Escalated`, or `Selected` `hand-to-person`, with no wait → `you`. That covers the "process died between" edge.
- A wait left unclaimed counts as itself, by its reason.

**Redos.**
- A run of `Redo`s on the same `runId` and `step`, with no route between them, is **one** `stopped` problem, answered `system`. Rerun 1, 2 and 3 of one crashed step are one problem by the ticket's "counted once by who finally answered it".
- An `AgentCrashed` wait on that run and step claims the last unclaimed redo group of that step at or before it, whatever routes lie between: routes are appended after the walk returns, so append order is not the order things happened in, and a crash wait looks only among redos (a route wait only among routes). The problem is then answered by the wait, since the redos ran out and the crash went to a person. `AgentCrashed` carries `run` and `step` (`wait.ts:235-239`); `StepRedone` carries `runId` and `step` (`events.ts:1725-1728`).

**`TicketSplit` needs no reading of its own.**
- A split is written only `by: 'triage'` (`wait.ts:323-324`, "written only `by: 'triage'`"), as the `SplitResolution` of the `ProposedEscalated{DiffTooLarge}` wait it answers.
- That wait's `resolution.by` already says `system`.

## Kind, and who answered

- **Kind** comes first from the route: proposal tag plus candidate, per the ticket's table. For example, `ReviewFindings` with `restart` → `review-restarted`, and any other `ReviewFindings` → `review-fixed`.
- A wait counted on its own takes its kind from its reason:
  - `AgentCrashed` → `stopped`
  - `FixerDisagrees` → `disputed`
  - `AgentQuestion` → `asked`
  - `SetupRefused` → `setup`
  - `ProposedEscalated` → its `proposal._tag`, mapped like a route
- **A triage cause overrides the kind:** `UndecidedQuestion` → `asked`, `SetupBroken` → `setup`. It is the later and more specific diagnosis. These two kinds are always `you`: the table says so, and a triage that names them did not resolve the wait.
- **Any tag the mapping does not name → `other`.** That includes the 17 proposal tags (`proposal.ts:250-268`) and any tag added later. Use a lookup with a default, not an exhaustive `switch` that a new tag would fail to compile. The ticket asks for `other`, not for a type error.
- **`OwnQuestion` is not a problem.** It is a person's own `lingtai ask` before any run (`wait.ts:73-74`, "No `run`: there is nothing to attach one to"). No step raised it. Every other unnamed wait reason, `SignoffRequired` included, is `other`.
- **`answeredBy`:** `system` exactly when the deciding resolution has `by === 'triage'` (`read-model.ts:399`). Otherwise it is `you`, including while the wait is open (`resolution === null`).
- **Last vs first resolution.** The ticket's Edges say "its last `WaitResolved` decides". The reduce keeps the **first** (`ticket.ts:120`: `w.waitId === d.waitId && w.resolution === null`, doc at `:67`). The projection therefore keeps every `WaitResolved` as an `Answer` raised fact, and `problemsOf` lets the **last** one decide who answered, as the Edges say; the ticket reduce is not changed. Facts that are history rather than state are not erased by a later resolution: a wait that was ever resolved with `Split` stays `too-big`.
- **Attempt:** `claims.findIndex(c => c.runId === runId) + 1`. For a continuation run (not a claim, 0123's Words) or an unknown run, use the number of claims with `at ≤` the problem's `at`, or `null` when that is 0. `landingAttempt` counts the same way (`ticket-report.ts:398`).

## Tests (all unit)

- `packages/domain/unit/problems.test.ts`: pure `problemsOf` over hand-built `Raised[]` and `TicketWait[]`. One case per kind, plus:
  - escalated `ReviewFindings` + person-approved wait → one `review-fixed`, `you`; the same wait resolved by `triage` → `system`;
  - `Selected merge-base` followed by a `ProposedEscalated{BaseMoved}` wait → **one** problem, not two;
  - unknown tag → `other`;
  - `Escalated` with no wait → `you`;
  - three `Redo`s, then nothing → one `stopped`, `system`.
- One projector test (`packages/projector/unit/ticket-report.test.ts`, existing harness) feeds `RunStarted`, `ProposalRouted` and `WaitStarted`/`WaitResolved` and reads `problems` off the row. It pins the stream link and the save, and leaves the rule to the domain tests.
- `packages/conductor/unit/report.test.ts`: `handled` for a 7-day window, as the ticket's Done-when says.
- None of this needs `pnpm test:integration`. The SQLite/Postgres DDL is checked at unit level by `declared-shape.test.ts`.

## Edges the ticket does not settle, decided

- **A store already holding `ticket_report`.** The new columns are shape drift (`packages/projector/src/shape.ts`). `lingtai projection rebuild ticket_report` is the remedy, as the ticket's Watch out says. No migration, and no `alter table`.
- **No async, no `Effect.run*`.** `problemsOf` is pure and the projection cases are `Effect.gen` like their neighbours, so the effect-ratchet baseline does not move.
- **ADR.** 0123 is a current-style ADR in `doc/decisions/`, so it is edited in place. Add a `problems` row to §2's table and a line to §6, as the ticket says. Put the pairing rule above into that row, because it is the one fact a later reader of the report cannot reconstruct from the code's name.
