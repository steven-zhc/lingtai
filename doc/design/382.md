# #382: where the ticket verbs split from the client

## The shape in one sentence

The pass keeps receiving **one** `PassClient` (`conduct.ts:330`: `Tickets & RefChannel & { owner, repo }`). For a `db` project, its eight ticket verbs come from `dbTickets`, and everything else comes from the GitHub client, which is still built. `runOnce`, `runQueue` (`schedule.ts:179,225`), `tell.ts` and the lane stay unchanged. Only the four places that build the client change.

## Two functions in `packages/conductor/src/ticket-store.ts`

**`ticketsFor(state, recipe, client, options?: { sql?: TicketSql; log?: LogQueries }): Promise<Tickets>`**

- `ticketSourceOf(recipe)` is `'github'`: return **`client` itself**, the same object. A project that writes nothing in its recipe then gets the identical value it gets today.
- `'db'`: return `dbTickets(sql, state.project, …)`, after running the refusal below.
- The default `sql` is `(await import('@lingtai/event-store')).processTicketSql()`, a **dynamic** import. This is the same reason as `projects.ts:14-28`: *"a caller that brings its own log should still load no store at all"*. It also keeps `filter.ts`, which `lingtai status` reaches first, from opening a store at import. The unit tests pass `createSqliteTicketSql(openSqliteLog(':memory:'))`, the same as `unit/db-tickets.test.ts:14-16`.

**`passClientOf(client, tickets)`**

- When `tickets === client`, return `client`.
- Otherwise return `{ ...client, listOpenIssues: tickets.listOpenIssues, getIssue: …, … }` with all eight `Tickets` verbs taken from `tickets`. Name them explicitly. Do not spread `tickets`: `DbTickets` may carry extras.
- Spreading is safe on both sides because each is an object literal of closures with no `this`. `createGitHubClient` returns one (`packages/github/src/client.ts:392`) and so does `dbTickets` (`db-tickets.ts:236` onward).
- **Keep the result typed `GitHubClient`, not `PassClient`.** The callers still need `token()` (`run.ts:263`, `cli/conduct.ts`), `defaultBranch()` (`cli/conduct.ts:133`) and `fileAt`. The test harness `once()` takes `client: GitHubClient` (`test/one-pass.ts:50`) and reads the recipe through `options.client.fileAt`.

This keeps the ticket's **Watch out** row by construction: refs, `fileAt`, the default branch and the token still reach GitHub because the client is still built. Nothing in this design stops building it for a `db` project.

**Name collision.** `discover.ts:74` already exports a type called `TicketSource` (`Pick<Tickets, 'listOpenIssues' | 'getIssue'>`), and `@lingtai/recipe/settings` exports `TicketSource = 'github' | 'db'`. Import the recipe one under an alias in `ticket-store.ts`. Do not rename either.

## The four call sites

1. **`filter.ts` `projectFilter` (`:217-249`).**
   - After `recipeFor` resolves, call `ticketsFor(state, resolved.recipe, client)`.
   - Add `tickets: TicketSource` to the ok branch of `ProjectFilter` (beside `client` at `:175`).
   - In `apps/board/src/lib/board.ts:523` and `queued.ts:272`, switch `runnableNow({ client: filter.client, … })` to `filter.tickets`. Those are the only two readers of `filter.client` (checked with `git grep`).
   - A thrown refusal lands in the existing `catch` and comes out as `ok: false, problem`. The daemon's start-up block prints that (`lingtai.ts:711`), and so do `lingtai status` and the board.
   - **Leave `ProjectFilter.client` in place.** Removing it touches more call sites than this ticket covers.
   - No `"use client"` file in `apps/board/src` imports `@lingtai/conductor/filter` or `lib/recipe.ts`. The dynamic import adds nothing to a client graph. `apps/release/integration/build.test.ts` is the only test that would see it if it did, and `pnpm test` does not run that file.
2. **`apps/cli/src/run.ts`.** After `resolved` (`:248`), set `common.client` to `passClientOf(client, await ticketsFor(project, resolved.recipe, client))`. A refusal goes through `refuse(...)`. This covers both the queue branch and the `--issue` branch, whose `runOnce` calls `getIssue` through the client.
3. **`apps/cli/src/conduct.ts` `work` (`:119-140`).** Do the same right after `currentRecipe` and **before `await where.looked()`**. That ordering is what makes the refusal durable. A throw before `looked()` is appended as `ProjectRefused` on the project's `prj-` stream with `detail` set to the message (`conduct.ts:296-317`). A throw after it is only a `log` line. The comment at `:306-311` explains why.
4. **`packages/daemon/src/converge.ts` `clientsForProjects` (`:95-107`).**
   - For each project, resolve `currentRecipe(p)`. This is a local file read with no request (`projects.ts:152-165`).
   - Set `passClientOf(client, await ticketsFor(...))` in the map.
   - A recipe that won't resolve or a refusal goes in the existing `catch`, which skips the project. That matches the comment *"One repository's expired installation must not cost the rest their convergence"*.
   - The map's value type at `:161` already accepts this.
   - The only caller is `apps/cli/src/lingtai.ts:721`.

`schedule.ts`, `conduct.ts` (the package) and `tell.ts` take no diff.

## The refusal: read the log, not `task_view`

The ticket words the condition as *`task_view` rows exist*. Read the **log** instead: `queries.projectStreams(\`wi-${project}-\`)` (`LogQueries`, `event-store/src/queries.ts:99`), filtered with `parseWorkItemStream(id)?.project === project` (`domain/src/streams.ts`). The filter matters because `projectStreams` matches on a prefix, so `foo` would otherwise also match `foo-bar`'s streams.

What the refusal protects is stream *names* (`workItemStream`, `streams.ts:14`). Those are in `events` whether or not the projection is current. `converge.ts:107-113` makes the same choice for the same reason: *"reconciliation has to work when a projection is the thing that is broken"*.

The rule:

- Recipe says `db`.
- At least one `wi-<project>-*` stream exists.
- `dbTickets.listIssuesSince(new Date(0))` is empty.
- → Throw an error whose message names the project, the source and the fix, e.g. `purecheck: source.tickets is db, but the log already has GitHub-numbered work items (wi-purecheck-212, …) — db would number from 1 into them; remove source.tickets or use a fresh project`.

Export it as a class (`TicketSourceConflict`) so the test can match it by name. Once `dbTickets` holds any ticket, the project has been switched deliberately and the check passes.

**Cost.** This runs on every `projectFilter`, which means every board render. On a `db` project that is one `projectStreams` query plus one ticket query. On a `github` project it is nothing, because the branch never enters. That is acceptable. Do not cache it.

## Tests (all `unit/`)

- **`ticketsFor`:**
  - An absent field and `github` each return the very same `client` (`toBe`).
  - `db` returns something that is not the client and that answers a `createIssue` made through a second `dbTickets` on the same `:memory:` sql.
- **The pass:**
  - Wrap `fakeGitHub(said)` (`test/one-pass.ts:409`) so that its eight ticket verbs record into a second array.
  - Seed `dbTickets` with `createIssue`.
  - Call `once({ client: passClientOf(fake, db), … })` with a recipe that has `source.tickets: db`.
  - Assert the pass claims `wi-purecheck-1`.
  - Assert the comment, labels and close show up in `db.getIssue(1)` and its comments.
  - Assert the GitHub ticket-verb record is **empty**.
  - `fakeGitHub` has no `matchingRefs` or `deleteRef`. If the pass reaches the ref sweep, add them to the wrapper so they record into `said`, not into the ticket-verb array.
- **The refusal:**
  - Use a `memoryStore()` log with one `wi-purecheck-212` stream, an empty `:memory:` `dbTickets` and a `db` recipe. Assert it rejects with `TicketSourceConflict`.
  - Assert the same setup with one ticket already in `dbTickets` resolves.

Every one of these claims is checkable with `pnpm test`. The Postgres half of `dbTickets` stays in `integration/db-tickets.test.ts`, which this ticket does not change.

## The PR body must say

**The daemon's code is frozen at start.** Until `pnpm lingtai restart "picking up #382"`, `source.tickets: db` stays silently ignored by the running conductor, and it goes on taking GitHub issues. `ticketSourceOf`'s own doc comment says so: *"Nothing reads this yet — #382 is what wires a `db` answer into the pass"* (`recipe/src/settings.ts:304-305`). Update that sentence.

After the restart, a `ProjectStarted…`/`ConductorStarted` event whose `commit` is at or after the merge settles whether the change reached the daemon. If a `db` project then ends up with a work item stream for an issue number that `dbTickets` never issued, the change didn't reach it.
