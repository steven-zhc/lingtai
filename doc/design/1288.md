# #1288: design note

## The grouping goes back to #1284's, and the move comes from the same lookup

The person's answer settles it: undo #1287's grouping, then add `yourMove`. Today every site in `problemsOf` reads `answeredBy: alwaysYou(kind) ? 'you' : 'system'` (`packages/domain/src/problems.ts:211`, `:221`, `:233`). #1287 (`f93da502`) deleted the who-answered machinery. Its parent still has that machinery, and the diff is small enough to restore by hand. Read it with `git show 60daea75:packages/domain/src/problems.ts`:

- `Answers` and the `answers` map, filled in the `Answer` branch next to `splits` (the parent's `:164`, `:171`).
- `finalOf` (`:146-148`): *"The wait's deciding resolution: the last `WaitResolved` kept, else the reduce's first."*
- `answerOf` (`:150-151`).
- The three call sites, including the route's `handed` rule (`:233-234`: an escalation or `hand-to-person` with no wait is `you`).

Restore the code only. Do **not** `git revert` `f93da502`. That commit also edited `doc/design/handled-for-you.html` and the 0123 row, and those are handled below.

Then derive `yourMove` from the same `finalOf` call that decides `answeredBy`. Do not add a second lookup. `answerOf` should return both values, so the two can never disagree:

- **`answeredBy: 'system'`**: the key is absent. Write it as a conditional spread, not `yourMove: undefined`. The projector stores `JSON.stringify(problemsOf(...))` (`packages/projector/src/ticket-report.ts:386`). JSON cannot hold `undefined`, so the only way to store "absent" is to leave the key out.
- **`you`, with no deciding resolution** (an open wait, or a `handed` route with no wait): `null`.
- **`you`, final `by` is a person**: the resolution `_tag`, as a plain `string`. `Raised.Answer.resolution` is already a string (`:61`), and a tag the board does not know falls through to *you decided*.
- **`you`, final `by` is `'triage'`**: the string `'triage'`. This only happens for `asked`/`setup`, because `alwaysYou` forces them to `you` whoever answered (`:144`). Recording the triage's own tag would make the row say *→ you answered* about a question the person never saw. Lower-case `'triage'` is not a `Resolution` tag (`packages/domain/src/wait.ts:321-336`), so it cannot be mistaken for one.

Type it on `Problem` as `readonly yourMove?: string | null`. Update the `answeredBy` doc comment (`:69`) and the module header (`:11-13`, *"grouped by its kind … whoever answered it"*) back to the who-finally-answered wording. `ce2c8737` changed both to describe #1287's rule.

## `report().handled` gains one list, and its totals are not recomputed

Leave `Handled.kinds` and `days` as they are (`packages/conductor/src/report.ts:204-213`, `:581-597`). They already count `system`/`you` per kind off `answeredBy`, so restoring the grouping restores #1284's figures with no change here.

Add one field: `needed: { kind: string; move: string | null; count: number }[]`, built from `raised.filter(p => p.answeredBy === 'you')`.

- Key on the raw tag, not on the verb. The CLI spreads `Report` into `--json` (`:497-500`), and data belongs there, not English.
- A stored problem that has no `yourMove` key (anything saved before the rebuild) is keyed `'unknown'`, kept apart from `null`. Before the rebuild it must not read *waiting on you*.
- Order: `PROBLEM_KINDS` order, then count descending.

The unit test the ticket asks for: per kind, the sum of `needed` equals `kinds[k].you`. Assert that equality directly; it is the "totals unchanged" claim. Per the answer, the baseline for that claim is #1284's grouping, not today's.

## Edges this note decides

- **A read that fails, two runs at once, retry, pause, restart halfway**: none apply. `problemsOf` is pure, it runs on every save of the one projection writer (CLAUDE.md, 0100 §13), and the board only reads.
- **Before the rebuild**: stored problems carry #1287's grouping and no `yourMove`. Every NEEDED YOU row reads *→ you decided* (`'unknown'`), and most person-approved problems are still under AUTO-FIXED. Both are corrected by `lingtai projection rebuild ticket_report`, which needs the daemon drained (it takes the conductor lock, per `ce2c8737`'s note in `doc/design/1287.md`). The implementing agent cannot run it. Say in the commit body that the operator must run it after the merge and restart.
- **What settles the regrouping on the real log**: for each problem, the `WaitResolved` with that `waitId`: its `by` and `resolution._tag`. That is the event to read when checking that the 34 *AI review found problems* are `Approve` by a person (#1250, #1258, #1274).
