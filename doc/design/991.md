# Design: #991, the per-project pause, from the domain to the gates

The ticket covers the shape. This note covers what it leaves open: how `locked` is built without raising the ratchet, what the guard's error channel carries, how `lingtai run` refuses, and the order of checks at each gate.

## 1. Build `locked` once, in `guard.ts`, and run it with the uncounted run

Today `apps/cli/src/daemon.ts` imports no `Effect` at all. Its `claiming` hook (`daemon.ts:557-563`) is a non-`async` arrow that chains `.then`. Writing `locked` there as `async (name) => Effect.runPromise(guard.locksFor(name))` would raise both of `apps/cli`'s numbers (`"apps/cli": { "async": 417, "run": 6 }`, `effect-ratchet.baseline.json:2`):
- The counter counts every `async` arrow (`effect-ratchet.test.ts`: `ts.isArrowFunction(node) … AsyncKeyword`).
- It counts every `Effect.run*` except the `*With` runs (`RUN = /^run[A-Z](?!\w*With$)/`).

So put the conversion next to the guard and write it once:

```ts
// packages/daemon/src/guard.ts
export const lockedBy = (guard: Guard): ((project: string) => Promise<string | null>) => (project) =>
  run(guard.locksFor(project).pipe(
    Effect.map((locks) => lockSentence(project, locks)),
    Effect.catch((err) => Effect.succeed(`could not read whether ${project} is paused — ${err.message}`)),
  ))
const run = Effect.runPromiseWith(Context.empty())
```

- This copies the precedent at `apps/cli/src/first-project.ts:1253-1256`: *"`runPromiseWith` is the run the ratchet does not count, and it starts no fiber of a caller's tracer because there is no caller here."*
- `daemon.ts` and `run.ts` each call `lockedBy(makeGuard({ store }))`. Nothing else builds the callback, so the read-failed sentence exists in one place, which is the edge the ticket decided (unknown is not unpaused).
- `daemon.ts` adds no `async` and no `run`. It needs no `effect` import beyond what `lockedBy` hides.
- The callback **never rejects**. That lets `schedule.ts` keep using `Effect.promise` (`schedule.ts:199`), which would turn a rejection into a defect rather than a stop.

## 2. The guard's error channel is typed, not a die

`locksFor(project): Effect<readonly Lock[], Error>`:
- Read `prj-{project}` with `Effect.tryPromise(() => store.read(projectStream(project)))` (`projectStream` is at `packages/domain/src/streams.ts:108`), then `reduceProject` (`project.ts:109`), then `locksOn({ project })`.
- `store.read` and `store.head` reject on a failed read (`event-store.ts:352-356`: *"no caller may turn a failed read into 0"*), and the guard must not either.
- The ticket writes `Effect<readonly Lock[]>`. Read that as shorthand. A guard that swallowed the failure could not let `lockedBy` say *could not read*.
- Write the guard as `const CHECKS = [projectPause] as const`, with each check `(project) => Effect<readonly Lock[], Error>`, and `locksFor` = `Effect.forEach(CHECKS, …)` flattened. That makes a later ceiling or account check one entry in the list.
- `snapshots?` is accepted and unused. Project is not a snapshotted reducer (`reducers.ts:6`).

## 3. The appenders are Effects in `control.ts`; retry the conflict, not every error

`control.ts` is all `async` today, with a retry loop at `:242`, `:285` and `:372` (`if (!(err instanceof ConcurrencyError) || attempt >= 4) throw err`). Do not copy that loop: it is an `async` function.
- Write `pauseProject` as `Effect.gen`:
  - `tryPromise` read, then `reduceProject`, then `pauseTransition(state, by)`;
  - if that returns `null`, answer `{ kind: 'already', since: state.paused!.at }`;
  - otherwise `tryPromise` `store.append(stream, state.version, [next])`, as `record()` does at `conduct.ts:806-807`.
- Keep the `ConcurrencyError` as the failure value: `catch: (e) => e`, then narrow with `instanceof`. Retry exactly once with `Effect.catchIf(isConcurrency, () => attempt)`. The ticket says *re-reads once*, and a second conflict fails the Effect.
- `resumeProject` has the same shape and answers `appended` or `not-paused`.
- Type the answer as a discriminated union on `kind`, so the next ticket's CLI can switch on it.
- Export both, plus `makeGuard`, `lockedBy` and `type Guard`, from `packages/daemon/src/index.ts`.

## 4. Order at each gate: the conductor-wide pause first, then the lock

| Gate | Order | On a sentence |
|---|---|---|
| `conductProjects`, `conduct.ts:745` | `paused()` first (still `break`), then `locked?.(name)` | `say(\`${name}: not looked at — ${why}\`)`, then `continue` |
| `launch`, `conduct.ts:369` | `paused` first, then `locked` | `say(\`${name}: #${issue} not started — ${why}\`)`, then `return false` |
| `runQueue`'s `stopIfPaused`, `schedule.ts:196` | `paused`, then `locked(name)` (`name` is in scope at `:190`) | the existing `log(why)`, `told(failed)`, `finish('paused')` |
| `work-loop.ts:524` | **not asked** | the loop has no project. The per-project gates cover it |

- `launch` and `conductProjects` are already `async`, so the extra `await` adds no `async` function.
- In `stopIfPaused`, add a second `Effect.promise` inside the same generator. Do not add a new generator. Both calls per loop (`:207` and the second one) pick it up for free.
- Thread `locked` through `ConductOptions` (`:92`), the turn options (`:170`) and `ProjectsOptions` (`:722`), wherever `paused` already goes.

## 5. `lingtai run`: a lock is a person's decision, so it exits 0

`heedThePause` (`run.ts:152`) runs before the lock and fails with `Paused`. That is caught at `:682` with exit 0, *"nothing went wrong, a person decided this"*; a read that fails is `refuse(...)`, which exits 1 (`:689-693`). Give the project lock the same split:
- Add `heedTheLock(locked, project)`, an `Effect.promise(() => locked(project))`. A sentence starting `could not ` fails with `refuse(sentence)`. Any other sentence fails with a new tagged `ProjectLocked { sentence }`.
- Chain it after `heedThePause` at `:677`. Catch `ProjectLocked` beside `Paused`: log the sentence plus `nothing was taken`, and exit 0.
- **Between continuations (`:545-551`)**: after the conductor read, ask `locked`. Treat the answer exactly as `pausedSentence`'s answer is treated there: `could not …` refuses, and anything else stops.
- **`stillPaused` (`:183`)**: when it is built for `runQueue` at `:596`, pass `locked` to `runQueue` as its own option. Do not fold it into `stillPaused`. It is the same callback the daemon passes, so `schedule.ts` reaches the lock the same way from both hosts.

## 6. `lockSentence` prints `since` as `toISOString()`

The ticket's `since 14:20` is an example. A local wall-clock time makes the unit test depend on `TZ`. `saidPaused` already prints `until` with `toISOString()` (`run.ts:167-168`), so use that. The sentence is `${project} is paused by ${by} since ${since.toISOString()}`. With no lock it returns `null`. With several locks (later tickets) it joins them with `; `.

## 7. Reducer details

- `ProjectPaused` reads `event.seq` and `event.at` as `ProjectRefused` does (`project.ts:95`), and changes nothing when `paused !== null`.
- `seq` is a `bigint` on the envelope. Check what `ProjectRefused` stores and match that type in the `paused` field, rather than the ticket's `number`, if they differ.
- `pauseTransition` and `resumeTransition` return a `ToAppend` with `type` and `data: { project, by }`, as `turnTransition` builds at `project.ts:176-201`.

## Checks that stand in for integration

Every claim here is unit-level and runs on the memory store (`@lingtai/event-store/memory`):
- the guard, read fresh three times;
- the appenders, idempotent and retried on a conflict (make the retry with a store wrapper whose first `append` throws a `ConcurrencyError`);
- `conductProjects` with two projects;
- `launch` and `runQueue` with a `locked` stub that flips between calls, and one that answers `could not read …`.

Nothing here needs `pnpm test:integration`.
