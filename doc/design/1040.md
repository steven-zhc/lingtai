## Design: #1040 — a re-entrant mirror permit is refused, not wedged

### Where it goes

All the logic goes in `packages/repo/src/mirror-lock.ts`. Two other files have to change, and the ticket's *Done when* is inconsistent about one of them:

- **`packages/repo/src/index.ts:23`** has `export { mirrorWrite, withMirrorWrite } from './mirror-lock.ts'`. Deleting `withMirrorWrite` requires changing this line to export `mirrorWrite` alone. The ticket asks both that `withMirrorWrite` be gone "from … index exports" and that the diff touch "only `mirror-lock.ts` and `packages/repo/unit/`". The first requirement wins. A one-line edit to `index.ts` is the expected diff, and a reviewer should not count it against the second.
- **`packages/repo/unit/provision-permit.test.ts:36,62`** imports `withMirrorWrite` and uses it to hold a mirror from outside. It is in `unit/`, so it is in scope.

Nothing outside `packages/repo` imports `withMirrorWrite`. A grep over `packages` and `apps` finds it only in `mirror-lock.ts:35`, `index.ts:23`, `unit/mirror-lock.test.ts` and `unit/provision-permit.test.ts`.

### The shape of `mirrorWrite`

```
const Held = Context.Reference<ReadonlyArray<Token>>('@lingtai/repo/MirrorHeld', { defaultValue: () => [] })
type Token = { readonly key: string; released: boolean }
```

`Context.Reference(key, { defaultValue })` is the v4 form (`effect/dist/Context.d.ts:1741`). The repo is on `effect@4.1.2`, and `packages/conductor/src/schedule.ts:178` already relies on *"On Effect 4 the tracer is a `Context.Reference`"*. Because a Reference has a default, reading it adds nothing to `R`, so `mirrorWrite`'s signature `Effect<A, E, R>` (`mirror-lock.ts:43`) does not change.

The order inside `mirrorWrite`:

1. **Check before anything calls `acquire`.** The check is `const key = resolve(path)`, then `yield* Held`, then: if any token has `t.key === key && !t.released`, return `Effect.die(new Error(…key…))`. This must happen inside an `Effect.gen` or `Effect.suspend`, before the `Effect.promise(() => acquire(path))` runs. The reason is that `acquire` calls `tails.set` synchronously when it is called (`mirror-lock.ts:23-24`), not when its promise resolves. A refusal that comes after that call has already joined the chain, which is the wedge the *Watch out* row describes.
2. **Acquire as today.** The acquire step of `acquireUseRelease` returns `{ release, token }`, with the token `{ key, released: false }` made right after the grant. Keep it uninterruptible, as `mirror-lock.ts:40-41` explains: *"an abandoned queued grant would never be released and would wedge the mirror."*
3. **Use:** `Effect.provideService(effect, Held, [...held, token])`. Build a new array; never push onto the inherited one. A child fiber shares its parent's array object, and mutating it would make a token visible to fibers that never held it.
4. **Release:** `Effect.sync(() => { token.released = true; release() })`, in that order. The token is the only mutable thing. It is shared by reference with every fiber forked inside `effect`, which is how a `forkDaemon`'d continuation sees the release (the *Watch out* row).

Use the path `resolve(path)` as the token's key and in the message, so the `/m/x/../a.git` normalisation the existing test pins (`mirror-lock.test.ts:38`) applies to refusals too. The die message must contain `key`. The ticket's wording is fine.

Add one sentence to the doc comment above `tails` (`mirror-lock.ts:5-14`): the permit is not re-entrant, and a holder that asks again, from its own fiber or a fiber forked inside it, is refused at once as a defect naming the mirror.

### What a refused write does to its outer holder

The inner `Effect.die` reaches the outer `mirrorWrite`'s `use`, and `acquireUseRelease` runs the outer release. The outer holder therefore exits with the same defect, and the queue moves on. The *Done when* test should assert three things:

- the outer `Effect.exit` is a die whose message contains the resolved path;
- this happens with no timer advanced;
- a third writer queued on the same path behind the outer then runs.

Don't catch the defect inside the test's held block to "prove" the outer survives. Nothing in the ticket wants that, and it is not the shape.

### Rewriting the `withMirrorWrite` tests

Every use of `withMirrorWrite` in the tests is an **outside holder**: it holds the mirror while something else runs (`mirror-lock.test.ts:22-78`, `:110`, `:119`; `provision-permit.test.ts:62`). Its direct replacement is

```
Effect.runPromise(mirrorWrite(path, Effect.promise(() => latch.promise)))
```

`Effect.runPromise` starts a new root fiber, so the fiber starts with the empty default and behaves exactly as the promise form did. The ratchet counts only `src/` (`packages/domain/unit/effect-ratchet.test.ts:307`, `entry.file.startsWith(\`${p}/src/\`)`), so `Effect.run*` in `unit/` raises nothing, and `packages/repo`'s `async: 0, run: 0` (`effect-ratchet.baseline.json:6`) holds as long as `src/` gains no `async` and no `Effect.run*`.

`mirror-lock.test.ts`'s *"holds no permit while the merge runs"* (`:129-146`) needs one deliberate choice. Keep its probe on a **root fiber**, written as `void Effect.runPromise(mirrorWrite(…))` inside the `Effect.promise`, rather than as a `mirrorWrite` yielded in the same fiber as the merge. The test asks whether a permit is held during the merge, which is a question about waiting, and a root-fiber probe answers it the way it did before. An in-fiber probe would turn a regression into a die rather than a wait, and the test's expectation would no longer describe it.

The rest of the throw, interruption and ordering tests that only exercised the promise wrapper (`:44-54`) move onto `mirrorWrite` with `Effect.fail` or `Effect.die` and `Effect.exit`. Delete any that duplicate the existing Effect-side tests.

### Edges the ticket leaves to the design

- **A fiber forked inside the holder, still running before the release**, asks for the same path: it is refused. The ticket already decides this (its *Edges*, "`Effect.all` with concurrency inside a held block"). No test is required beyond the `forkDaemon`-after-release one, but a short one is cheap.
- **The `forkDaemon` test** needs an explicit latch. The child must wait until the outer `mirrorWrite` has returned before it calls `mirrorWrite` itself. Otherwise the test checks the still-held case by accident and dies. Await the child's fiber (`Fiber.join`) to show it ran.
- **The refusal is not counted in the log.** No event is appended, and none should be: the defect surfaces as whatever the attempt already records for a die. If someone later needs to know whether this fired in production, the attempt's failure event carries the defect text, and the mirror path in it is what to look for. This change does not settle that question, and does not need to.
