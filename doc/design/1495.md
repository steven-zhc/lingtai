## The shape

The ticket gets one thing wrong: if `answered` is a required field on `Deciding`, the existing tests go red. Everything else follows the ticket. The sections below say where each piece goes and what to decide along the way.

### 1. Reducer and codec (`packages/domain`)

- **`ticket.ts`.** Add `readonly at: Date` to `TicketWait.resolution` (`ticket.ts:68-75`). In the `WaitResolved` arm (`ticket.ts:117-131`), add `at: event.at` beside `resolution` and `by`.
- **`ticket-codec.ts`.** Add a required `at: IsoDate` to the `resolution` strict object (`ticket-codec.ts:40-49`). `IsoDate` already turns the string back into a `Date` (`ticket-codec.ts:22`). `encodeTicket` is a plain `JSON.stringify` (`ticket-codec.ts:140-141`), so a `Date` is written as ISO with no further work.
- **Version.** Bump `version: 15` to `16` (`ticket-codec.ts:198`). Add `// 16: a wait's resolution carries its at (#1495); a version-15 snapshot lost it.`, following the `// 11:` line for `note` (`ticket-codec.ts:193`).
- **Hand-built fixtures.** `packages/domain/unit/system-line.test.ts` is the only file that builds `resolution: { resolution …` by hand. It gains `at`.

### 2. `answered` is optional on `Deciding`

The ticket writes `answered: … | null`. Make it `answered?: { asked: string; at: string; by: string; resolution: Resolution['_tag'] } | 'unmatched'`, and leave the key absent in every other case. The reason is that two tests compare whole `Deciding` objects with `toEqual`:

- `apps/board/unit/standing.test.tsx:307` (a blocked `CheckRefused`)
- `apps/board/unit/standing.test.tsx:450`

Two more files type `Deciding` literals by hand: `standing.test.tsx:689` and `:1085`.

A required `answered: null` would turn all four red. That contradicts the ticket's *existing task-page tests stay green unchanged*. An absent key keeps them as written.

The fields:
- `asked` and `at` are ISO strings, because `StandingView` is serialized: `since` is `.toISOString()`'d at `task.ts:1271`.
- `'unmatched'` is the edge where no wait matches. It draws the muted line without the answer clause.

### 3. Where `answered` is computed

It belongs in `standingOf`, not in `decidingOf`. `decidingOf(runs, run)` (`task.ts:849-860`) has no waits. `standingOf` already reduces `item` (`task.ts:1191`).

**Attach it only when `life.status !== 'blocked'`.** That is what makes item 4 (*a blocked ticket is untouched*) true by construction.

**Recognise the asked arm with a helper, not by reading the string.** Today the only sign that `refusalOn` took the asked arm is the `'asked — '` prefix on `line` (`task.ts:801-806`). Split that arm out of `refusalOn` into a file-local `askedOn(run): Deciding | null`, and have `refusalOn`'s asked arm call it.

`refusalOn` ranks did-not-finish above asked (`task.ts:787-796`), so a run that has an asked step does not always return that step. So `standingOf` treats the deciding line as the asked one only when all of these hold:
- the deciding attempt's run is `runs.find(r => r.attempt === deciding.attempt)`;
- `askedOn(thatRun)` is not null;
- its `source` and `evidence` equal `deciding`'s.

`fromStep` cannot settle this: refusals have `fromStep: true` too (`task.ts:813`).

**Pick the wait.** Take the newest `item.waits` entry that meets all of these:
- `resolution !== null`;
- `'run' in reason`;
- `reason.run.runId === thatRun.runId`.

Use `AskLimit.asked` for the run when the reason is an `AskLimit`, as `reasonOf` does (`problems.ts:108`). If nothing matches, `answered` is `'unmatched'`.

**The answered step is usually not the deciding line any more.** An answer to an agent's question re-runs the step that asked: `AnswerQuestions` means *"the asking step runs again"* (`wait.ts:300-303`), and so does `RedoStep` (`wait.ts:289-292`). After either, the step's verdict is no longer `asked` and this path is not reached. The case that does reach it is the ticket's own example, an `Approve` at `proposed` that then merged.

**A wrong pairing is possible but not handled.** It needs a step that stays `asked` after its run went on through a second wait on the same `runId`. Nothing here protects against that; this ticket accepts it rather than adding a time to `StepVerdict`. The log would show it: a `StepEnded` with verdict `asked`, then two `WaitStarted` whose `reason.run.runId` is the same.

### 4. Render (`apps/board/src/app/standing.tsx`)

Write one `AnsweredAsk` component and call it first in two places:
- `Reason`'s `if (!diagnosed)` branch (`standing.tsx:2105`);
- `LastAttempt`, before its `RawEvidence` and `sevidence` arms (`standing.tsx:2167-2186`).

What it draws:
- **The question** is `oneLine(deciding.evidence)`, not `deciding.line`, which already carries the `asked — ` prefix.
- **The clock** is `iso.slice(11, 16)`, the UTC slice `Coords` prints (`standing.tsx:2012`).
- **The name.** `personName` (`apps/board/src/lib/history.ts:167`) is not exported. Export it rather than copying it, because the two copies would drift apart.
- **The word table** is a `Record<Resolution['_tag'], string>` beside the component. With a `Record`, adding a new `Resolution` tag (`wait.ts:323-336`) fails `pnpm typecheck` until the table has a word for it. `Approve` → `merge` when the asked step is at `proposed`, otherwise `continue`.
- **The pointer.** Keep the `in Attempt N ↓` link when `deciding.attempt !== attempt`, and the `↓` link in `LastAttempt`.

**CSS.** `.past` does not exist in `apps/board/src/app/globals.css` yet; this ticket adds it. Copy the mock, `board-mocks.html:55-56`:
- `border-left: 2px solid var(--rule-2)`, which is a rule colour and not an accent. That is what the ticket's *no accent border* means. Do not drop the border.
- `color: var(--muted)`.
- `.past b { color: var(--ink-2); font-weight: 500 }`.

Write it with the stylesheet's own tokens, as the neighbouring `.sevidence` is written (`globals.css:1721-1730`).

### 5. Tests that stand in for the integration half

These are all unit tests; none needs `pnpm test:integration`:
- **Domain.** Reduce a `WaitStarted` and a `WaitResolved`, encode with `encodeTicket`, decode through `ticketReducer.decode`, and check `resolution.at`. Also decode a version-15-shaped row (a `resolution` without `at`) and expect it to throw `TicketCodecError`. That is the path `ticket-report.ts:227-228` and `0124` rely on.
- **Board.** Build a landed ticket from a run with an asked `proposed:conductor:judge` step plus `WaitStarted` and `WaitResolved{Approve}`, and render `TaskBody`. Assert one `.past` that contains both times and `merge`, and no `.sevidence`.
- **Board, unmatched.** The same ticket with a `WaitResolved` whose reason has no `run`. Assert `→ answered`.

No ADR is touched. 0124 already says a snapshot of another version is void.
