# #1177 — the shape

## Where it goes

`changeRecipe` gets a file of its own, `packages/project/src/change.ts`, exported from `index.ts`. It should not go in `commands.ts`. That file's header says *"No process store is reached from here: every command takes `store`"* (`commands.ts:4-6`). `changeRecipe` takes `store?` and falls back to `defaultStore()`, the way `loadProject` does (`load.ts:20`). So it belongs beside `load.ts`.

`saveRecipeTextEffect` and `saveRecipeText` are deleted from `write.ts` (`:57-115`). Delete `saveRecipeText`'s entry in `packages/domain/unit/effect-ratchet.faces.json:362-367` in the same commit, because the ratchet checks that file against the code. `packages/project` is `{ async: 0, run: 0 }` in the baseline (`effect-ratchet.baseline.json:12`) and stays at zero. The board already calls `Effect.runPromise` at its own edge (`apps/board/src/app/actions.ts:540`), so its save does the same.

## The signature: what the ticket's `{ by, store?, home? }` leaves out

Each arm needs one thing the ticket does not give it. Put that thing on the arm's input, not in the shared options:

- **`{ changes, said? }`.** `said` is the comment written above each block, and it is used only when the file is created (`apply-setup.ts:36-37`, applied in `draft.ts:70`). `applySetup` passes it into the draft today (`apply-setup.ts:66-70`). If `changeRecipe` replays the changes without it, every new project's recipe loses its comments.
- **`{ text, expected, base, signedIn, hostFacts }`.** The text arm runs the editor's full resolve. That resolve needs `base`, `signedIn` and `hostFacts` (`write.ts:78-87`, passed in by the board at `actions.ts:1014-1017`). Only this arm needs them.

Options are `{ by: string, store?: EventStore, home?: string }`. Files come from `yield* ProjectFiles` (`files.ts:74`), as in `load.ts:24`.

## The two arms

**`{ changes }`.** Open `draftRecipe(project, { home, said })` and call `set(changes)` on it. `set` already makes the edit and the validation (`editRecipe`/`widenStepsIfNeeded`, then `resolveSource`, `draft.ts:64-77`). Compare the draft's text before and after, as `applySetup` does now (`apply-setup.ts:96-100`). A refusal from `set` fails the change before anything is written. The `{ changes }` arm has no stale check: the changes are applied to the file as it is now. That is what `applySetup` does today.

**`{ text, expected }`.** Move `saveRecipeTextEffect`'s body across unchanged: `missing` (`write.ts:63`), `stale` against `expected` (`:65-71`), the CRLF rule (`:74-75`), the resolve under `host: 'skip'` mapped to `invalid` with interrupts let through (`:78-98`), and `written: false` when the text equals the file (`:100`). Keep `SaveRecipeTextResult` (`packages/recipe/src/write.ts:138-141`) as the result, so the board's answers stay byte-identical.

## The event

Both arms end the same way. If the file's text differs, call `replaceRecipeFile` through the port. **Then** append:

```
const source = sourceOf(text)
recordFileRecipe(project, { sourceHash: sourceHashOf(source), source, by }, store)
```

The source and hash must be computed exactly as `loadProject` computes them (`load.ts:43-45`). Otherwise the next load sees a different hash and records the same save a second time as `by: 'file'`.

Append through `recordFileRecipe` (`commands.ts:153-157`), not a new `transitionProject` call and not a new `append(` with a type literal:

- It already runs `recipeChange`, which returns null when the hash equals the Project's (`domain/src/project.ts:251`). That is the ticket's second check, already written.
- It already has the one retry on a lost race (`commands.ts:170-178`).
- The `ProjectRecipeChanged` `ELSEWHERE` row is anchored on `type: 'ProjectRecipeChanged'` in `domain/src/project.ts` (design note 1175, line 103). It keeps accounting for this append with nothing moved, so `doc/events.json` should not change. Run `events-json.test.ts` to confirm that.

`actor` comes out as `by` for a person (`project.ts:254`).

**The append does not depend on the write.** A save whose text equals the file but whose hash is not the Project's still appends, `by` the person. That is the case of a file somebody hand-edited and no load has recorded since: the person saving it is the one vouching for it. A text that equals the file *and* the Project's hash is the ticket's retry case, and does nothing.

`by` must match `^human:[\w.@-]+$` (`domain/src/events.ts:2276`). A username outside that pattern fails at the append, which comes after the write. That is the ticket's *failed append* edge: the change is reported failed and the file stands. Do not validate `by` up front to avoid it; the edge already covers it.

## `applySetup`

`previewSetup` still takes `ApplyTarget`. Do not put `by` on `ApplyTarget`, or the preview would need a person it never uses. Give `applySetup` its own target type, `ApplyTarget & { by: string; store?: EventStore }`.

The body becomes:

1. `changeRecipe(project, { changes: answers.changes, said: answers.said }, { by, store, home })`, provided with `ProjectFiles` = `target.files ?? diskFiles`, exactly as `draftOver` does (`apply-setup.ts:69`). `target.files` stays: removing it is #1178's.
2. Map a failure to `SetupWriteError`.
3. If the append fails after the write, the message says the file is written and not recorded: `${path} was written but not recorded: …`. Do **not** run `register`; a rerun of `lingtai add` will register.
4. Run `register`.

The `filesEffect(target.files)` port (`apply-setup.ts:87`) and the draft's own read go away.

## The trap: every test of an add would now reach the real log

`store` defaults to `defaultStore()`. A unit test that calls `applySetup`, `addProject` or the CLI's add without handing in a store would open the machine's log. That is the filesystem, so it does not belong in the unit half (0060 §1), and it fails under `HOME=/nonexistent`. So `store` has to be threaded through to every caller:

- **The board's Add:** `AddPorts` (`packages/conductor/src/add-from-page.ts:242-251`) gains `store?: EventStore`, passed to `applySetup` at `:308`. The board's live ports pass `eventStore` (imported in `apps/board/src/app/actions.ts:65`). `by` there is `actor()` (`apps/board/src/lib/actor.ts:15-17`), because that code runs in the board process.
- **The CLI:** the world `first-project.ts` uses (interface at `:172-191`, live at `:1381-1401`) and the world `add.ts` uses gain `store?`. The live worlds leave it undefined. `by` is `` `human:${userInfo().username}` ``, as in `approve.ts:212`.
- **Tests:** every unit test that reaches `applySetup` hands in `createMemoryEventStore()` (`@lingtai/event-store/memory`). The ones to touch are `packages/setup/unit/apply-setup.test.ts`, `packages/setup/unit/sandbox-step.test.ts`, `packages/conductor/unit/add-from-page.test.ts`, and in `apps/cli/unit/` `add-github.test.ts`, `add-github-gh.test.ts`, `add-from-page-equals-add.test.ts` and `recipe-flow.test.ts`.

The order to check is: port write, then store append. The `Map`-backed port in `apply-setup.test.ts:19-29` already records an `events` list. Push into the same list from the store side (wrap `append`) and assert the order.

## The board's save

`saveRecipe` (`actions.ts:999-1031`) calls

```
Effect.runPromise(changeRecipe(name, { text, expected: loaded, base, signedIn, hostFacts }, { by: actor(), store: eventStore }))
```

and keeps its current mapping of the result. A failed append throws, and the existing `catch` (`:1028-1030`) shows its message.

`packages/project/unit/save-recipe-text.test.ts` is re-pointed at `changeRecipe`'s text arm with a memory store. Its assertions on `stale`, `missing` and `invalid` must not change. That is the Done-when.

## How to check it without the log

All of this is unit-checkable: a memory store plus a `Map` port. The integration half is not needed. In a real run, `ProjectRecipeChanged.data.by` is what shows it worked: `human:<user>` on the seq right after a board save or an add, and no `by: 'file'` event for the same `sourceHash` after it.
