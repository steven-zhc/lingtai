## Design note: #1057, CONDUCT-3. `firstDispatch`, `fixRound` and `dispatch` run in the pass's fiber

**The line numbers have moved.** The ticket cites `b64aa4af`, and this worktree is about 170 lines further down. Here the code is:
- `firstDispatch` at `conduct.ts:3916` and `fixRound` at `:4239`.
- The six runs at `:3940`, `:3944`, `:3965`, `:4274`, `:4341` and `:4444`.
- `workPort` at `:3514-3517`, and `gitOrDie` / `gitOrDieEffect` at `:1844-1846`.

The baseline today is `"packages/conductor": { "async": 161, "run": 8 }` (`effect-ratchet.baseline.json:9`). The target of 157 / 2 is exactly this ticket's four `async` and six runs.

### 1. Delete the local `AbortController` in both bodies; `dispatchRuntime` owns the abort

Both bodies acquire a controller and abort it on release, then pass `abort.signal` to `dispatched.run` (`:4090-4100` and `:4344-4360`). `dispatchRuntime` makes its own controller and, on interruption, "aborts the run and then waits for it to settle" (`packages/actions/src/agent-action.ts:271-282`). A second controller beside it is dead weight, and keeping it would also put a release ahead of the wait. So remove the `acquireRelease(new AbortController)` in both places.

Inside the socket's `Effect.scoped` block in `firstDispatch`, the dispatch is the effect that is running when an interruption arrives. Its own finalizer (abort, then wait) runs first. Then the scope's finalizers run in reverse order of acquisition: `server.unregister` (`:4083-4086`), then `host.serve`'s close. That is the order the Done-when test asserts (abort → settle → unregister). Do not move the registration's `acquireRelease` after the dispatch to "simplify" it.

### 2. `context.signal` is unset in production today, so the new signal changes nothing

Use `brief.context.signal`, the `ActionContext` that `dispatch(spec, context)` was handed (`action.ts:606`, `signal?: AbortSignal`). No caller in `packages/conductor/src` sets it on the context it builds. The only readers are `process-action.ts:71` and `agent-action.ts:898` and `:1552`.

So today the abort comes only from interruption, as it did through the old controller. Do not invent a signal to pass instead.

### 3. `stepDeps.work` stays an arrow

The comment at `:3631-3632` explains why: *"An arrow rather than `{ work: dispatch }`: `dispatch` is declared six hundred lines down, and this object literal is evaluated here."* That reason still holds once `dispatch` returns an Effect.

So `workPort` becomes `{ work: (spec, context) => dispatch(spec, context) }`. Delete its docblock (`:3514`, "lifted until `work` is an Effect (CONDUCT-3)").

### 4. Handle a rejection in `fixRound` with `Effect.catchDefect`, around the dispatch only

`dispatchRuntime` resumes with `Effect.die(error)`, and the error is the thrown value itself (`agent-action.ts:268-270`). So the handler keeps today's `(err as Error).message` for `failure.detail` (`:4362-4371`).

`Effect.catchDefect` exists in the installed effect (`effect@4.0.0-rc.111`, `Effect.d.ts:4934`), and `conduct.ts` already uses it. An interruption is not a defect, so it passes through with no extra code.

Wrap only the `dispatchRuntime(...)` call. A defect from `recordPrompt`, `appendNow` or `gitOrDieEffect` must stay a defect, as it is today.

`firstDispatch` gets no catch. Today its rejection escapes `Effect.runPromise` and becomes a defect at the `Effect.promise` lift (`:3516`). `Effect.result` around the scoped block does not catch defects, so yielding it unwrapped keeps the same answer.

### 5. Keep where `stoppedBy` is written

- `firstDispatch` sets `stoppedBy = 'interrupted'` at `:4089`, after the registration and before the dispatch.
- `fixRound` sets it at about `:4290`, before its `recordPrompt` and dispatch.

Keep both writes where they are. An interrupted fiber returns from neither body, so no later assignment (`:4152`, `:4163`, `:4405-4439`) runs. The flag stays `'interrupted'` for the worktree finalizer's keep. That is the commit made with `${WIP_COMMIT_PREFIX}… stopped by ${stoppedBy}` at `:2178`, guarded by `stoppedBy === null` at `:2141`.

### 6. Model the tests on `conduct-the-judge-is-in-the-fiber.test.ts`

That test (#1054) is the same shape for the judge:
- It uses `runOnce` with `fakePorts`, `memoryStore` and `refusingRuntime` from `packages/conductor/test/one-attempt.ts`.
- It forks the pass and waits for a promise the fake `run` resolves on entry.
- It aborts through `request.signal`, interrupts with `Fiber.interrupt`, and compares an ordered `log` array (`:46-80`).

For `implement`, the fake `run` matches the implementer's `runId`, not `:judge:`. The `unregister` entry has to come from the fake hook server's `serve`, so wrap or extend whatever `fakePorts` hands as `host`.

For the `stoppedBy` test:
- The fake git has to report a dirty tree, so that the keep has something to commit.
- The observable is the keep's git calls, the WIP commit message carrying `stopped by interrupted`, or the run-log note at `:2195-2196`. Check whichever the fake already records.
- Also assert that no `RunProposedCompletion` and no `RunSpent` is appended (#1041).

The ticket asks for a test with no timer. The judge test uses none, so follow it.

- **`runtimeVersionOf` then `recordPrompt`:** these are two lifts or one `.then` chain. Either is the same order, so keep the chain as it is (`:4069-4078`).
