# Design note for #891: stop for a person when the reviewer would get a truncated diff

## Where the stop goes

`createAgentAction`'s `run()` (`packages/actions/src/agent-action.ts:595-605`). Put it right after the empty-diff early return and **before `deps.issue()`**. The over-limit path then dispatches nothing, reads no ticket from GitHub and emits no `RunSpent`. The test is `diff.length > deps.limits.diffBytes`, applied to the same `diff` variable that is later passed to `buildReviewPrompt` (`:671`, clipped at `:386-387`). That variable is already the `from`-based diff (`context.mergedOnto ?? moved?.toSha`, `:600-601`). So after a base merge, the stop measures exactly the string the reviewer would have read, not the full branch diff. Pull the comparison into one exported helper, e.g. `clippedAt(diff, limit): boolean`, and have both `buildReviewPrompt` and the stop call it. Then the two cannot drift apart. `fix.ts:513-514` keeps its own clip, as the ticket says.

`createAgentAction` builds every non-`design` `agent:` action (`packages/actions/src/from-recipe.ts:338`), not only the one at `review:`. **Decision: the stop fires wherever that action runs.** Any of them would have judged a truncated diff, and 0108 §14's reason ("no reviewer … is paid") holds at every step. So the proposal carries the step it came from, as `AnswerUnreadable` does (it reads `proposal.from` at `packages/domain/src/routing.ts:226`). On this repo's recipe it only ever fires at `review`.

## The result, end to end

- **`ActionResult`**: `verdict: 'failed'`, `findings: []`, an `evidence` sentence that names both numbers, and a new optional `diffTooLarge: { size: number; limit: number }`. Add the same field to `PipelineResult.results[]` (`packages/actions/src/action.ts:660-690`) and spread it in `runPipeline` the way `unreadable` is (`:877`). Use `'failed'` rather than a new `ActionVerdict`. The pipeline already stops on `failed` and the step already refuses on it, and a new verdict word would open the switches on every other yield as well.
- **`verdictResultOf`** (`packages/conductor/src/step-outcome.ts:134-139`): in the `failed` arm, check `outcome.diffTooLarge !== undefined` **before** `unreadable`, and return `{ _tag: 'DiffTooLarge', size, limit }`. If that check were missing, the result would fall through to `Completed{refused, findings: []}`. At `review` that becomes `ReviewEmpty` (`packages/domain/src/attempt-next.ts:289-294`), which a declared judge is paid for. That is exactly the fallthrough the ticket's *Watch out* names.
- **`VerdictAction.result`** (`packages/domain/src/action.ts:127-136`): add `DiffTooLarge{ size, limit }`.
- **`verdictFellShort`** (`attempt-next.ts:175-189`): return `{ _tag: 'Propose', proposal: { _tag: 'DiffTooLarge', from: step, size, limit } }`.

## Routing: no new `JudgeWhen`

`offerFor`'s `DiffTooLarge` case calls `round('fix-lines', 'implement', false)` and `restart(false)`, exactly like `ReviewEmpty` (`routing.ts:208-211`). Only `hand-to-person` is available, and the two exclusions read as "nothing holds an agent to it" in `notAskedWhy`'s sentence (`packages/conductor/src/proposed-route.ts:183-191`). `replyFor` then returns `NotAsked` at `:146`, `decideRoute` gives `because: { _tag: 'NotAsked' }` (`routing.ts:272`), and `routeNext` builds `ProposedEscalated{ proposal: DiffTooLarge, because: NotAsked }`.

**Do not add `'diff-too-large'` to `JudgeWhen`** (`packages/domain/src/proposal.ts:26-39`). That enum is the vocabulary of the recipe's `judge … when:` (`packages/recipe/src/recipe.ts:1394`). A `when:` that a judge can never be asked about is a recipe line that silently does nothing, and 0108 §14 says no judge is paid. `whenOf` is only reached once two or more candidates are on offer (`proposed-route.ts:146-148`, `:184-193`). So its `DiffTooLarge` cell throws `ImpossibleRouteError`, already exported from `routing.ts`, with a comment citing 0108 §14. Don't map it to `'findings'`: a `judge when: findings` would then appear to cover it.

## The wait

- **`tableResolutions`** (`packages/domain/src/wait.ts:309-341`): add a `ProposedEscalated` cell returning `['Requeue', 'EditBodyAndRequeue', 'Split', 'Close']`. There is no `Approve` (that is #892) and no `GrantFixRound`.
  - **Check `allowedResolutions`'s append path too.** `MergeConflict`'s comment says `GrantFixRound` "is appended by `allowedResolutions`". The grant-criterion function above it (`:356+`) decides that, so its `DiffTooLarge` cell must return `null`. Otherwise the third *Done when* fails.
- **`defaultResolution`** (`:631-632`): widen the `ProposedEscalated` condition to `proposal._tag === 'BudgetExhausted' || proposal._tag === 'DiffTooLarge' || because._tag === 'BaseRed'`.
- **Split** is still gated by `TriageAdvised`'s refine (`wait.ts:826-833`), so the wait never recommends Split by itself. Adding Split to the table only lets a person pick it once triage has advised it.
- **Triage** (`packages/conductor/src/triage.ts:144-155`): add one bullet to `RULES`. It should say a `DiffTooLarge` wait is evidence for `TicketTooBig`, and that `Split` comes with its plan only when the ticket really holds separable work. A scripted rename like #848 does not, and gets `Requeue` or `EditBodyAndRequeue`.
- **`wait-words.ts`** (`escalatedColumns`, next to `ReviewEmpty` at `:273`): the copy names both numbers in the same unit the clip uses ("characters of diff", not "bytes"). It also says the reviewer was not run and no round is offered.

## Tests (all unit)

- **The boundary, in `packages/actions/unit/`.** A diff of `limit + 1` returns `diffTooLarge` and the `agent` dep is never called. Assert the reviewer stub's call count and that `deps.issue` was not called. A diff of exactly `limit` dispatches.
- **The fold.** A `StepEnded` built from that pipeline result reaches `ProposedEscalated{ DiffTooLarge{ size, limit }, because: NotAsked }`. Use the same harness as `conductor/unit/conduct-a-whole-pass.test.ts`.
- **No judge.** The same pass with a `judge: claude-code` declared at `proposed` never calls the judge dep. This is the case that would catch the `ReviewEmpty` fallthrough.
- **The offer.** `allowedResolutions` on the wait gives the four moves, with neither `Approve` nor `GrantFixRound`. A `db` ticket shows Split as unavailable, using that table's existing fixture.

Expect the tests that enumerate `Proposal` and result tags (the step matrix, the wait-words tables) to need a row each. That is the ticket's stated cost. Nothing here needs the integration half to be checked.

## The log

You cannot read production `events`. Once this is deployed, the settling fact is a `review` `StepEnded` whose action `result._tag` is `DiffTooLarge`. It should have no `RunSpent` with `for.step: 'review'` for that round, and be followed by a wait whose `reason.proposal._tag` is `DiffTooLarge`. An old `StepEnded` has no such tag, so nothing upcasts. This agrees with 0108 §14 as written, so no ADR edit is needed.
