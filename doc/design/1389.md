## Design note for #1389: `appendAll`

The ticket fixes the contract. This note covers three things it leaves open: a check that goes red if the new face is written in the wrong shape, how a store finds out which batch conflicted, and a second contract suite the ticket does not mention.

### 1. The new face must be the exact shape the ratchet accepts

`effect-ratchet.baseline.json` holds every package at 0/0. The header of `packages/domain/unit/effect-ratchet.test.ts:10-15` says:

> A promise face is not counted. A face is an exported function whose whole body is `return Effect.runPromise(<call>)` … and listed in `effect-ratchet.faces.json` … The shape is checked, not trusted.

So `promiseStore`'s `appendAll` cannot be an inline `Effect.runPromise(...)`: the ratchet would count it, and the baseline may not be raised. Follow `appendFace` (`packages/event-store/src/store-face.ts:27-29`):

```ts
export function appendAllFace(events: EventsPort, batches: readonly StreamBatch[]) {
  return Effect.runPromise(events.appendAll(batches))
}
```

Then:
- Add `appendAll: (batches) => appendAllFace(events, batches)` to `promiseStore` (`store-face.ts:47-55`).
- Add an entry to `packages/domain/unit/effect-ratchet.faces.json` beside `appendFace`'s (`:200-205`), with the same `until: "0101 §7"` and a `why` naming the same board hosts.
- The call from `promiseStore` in the same file is enough for the "has a reference" check: "A call in the declaring file counts" (`effect-ratchet.test.ts:555`).

`fromPromiseStore` (`store-face.ts:61-80`) gets `appendAll` the same way its `append` works: `Effect.flatten(Effect.promise(...))`, with `ConcurrencyError` as the failure and anything else rethrown. That uses no `run*`.

### 2. Postgres and SQLite need to know which batch conflicted

In both stores, today's `append` builds its `ConcurrencyError` from the single `streamId`/`rows` it was given:
- Postgres: `event-store.ts:446-455`
- SQLite: `sqlite.ts:264-272`

`isVersionConflict` only says *that* `events_stream_id_version_key` was hit (`event-store.ts:220-229`), not on which stream. Don't parse the driver's message to find out.

**Decision:** write batch by batch, and keep a local `current` index that is set before each batch's rows are inserted.
- **Postgres:** `Effect.forEach` over the batches, with each batch's rows written in turn inside the one `client.transaction`. The rejection handler builds the error from `prepared[current]`: `streamId`, `expectedVersion`, `rows.map(r => r.version)`.
- **SQLite:** the same, as a plain loop inside the one synchronous thunk between `BEGIN IMMEDIATE` and `COMMIT`. The rule in the comment at `sqlite.ts:226-232` ("no `yield*` between BEGIN and COMMIT") applies to the whole call, not to each batch.

Because rows go in batch order, the first conflict the database raises is the first conflicting batch written. That is the ticket's "names the first one written" for free.

Keep `Effect.uninterruptible` and the `Effect.runPromiseWith(context)` row writes exactly as `append` has them (`event-store.ts:424-436`).

Shared work:
- Do validation and the duplicate-stream `RangeError` once, before any transaction, in a small helper beside `prepareAppend` (`event-store.ts:316-338`). It maps every batch through `prepareAppend` and refuses a repeated `streamId`.
- Both stores import that helper, the way they share `prepareAppend` today.
- Empty batches are filtered out *after* validation (an empty batch with a bad stream id still throws), but their `[]` slot stays in the result.

### 3. Memory store: check every batch before writing any

`createMemoryEventStore`'s `append` asks `versionOf(streamId) !== expectedVersion` before it pushes (`packages/event-store/test/memory.ts:164-174`). For `appendAll`:
1. Validate every batch, as above.
2. Then check every non-empty batch's version, in batch order.
3. Throw the first mismatch's `ConcurrencyError`.
4. Only then assign `seq` and push.

Pushing inside the check loop would leave the first stream written when the second one conflicts, and the contract case for that is the one this store exists to pass.

**The gap case:** the memory store treats any mismatch as a conflict, including `expectedVersion` *above* the head. Postgres and SQLite only conflict when `expectedVersion + 1` already exists. `append` has the same divergence today. Do not write an `appendAll` contract case with a too-high expected version: it would pass on memory and fail in the integration half, where nothing can see it before the merge.

### 4. Two contract suites, not one

There are two suites, and the ticket names only one of them:
- `describeEventStoreContract` (`packages/event-store/test/contract.ts`) is the promise contract. The ticket's `Done when` list goes there.
- `describeEventsContract` (`packages/event-store/test/events-contract.ts:20`) asserts on `Exit`. It runs on memory in `packages/event-store/unit/events-memory.test.ts` and on SQLite in `packages/event-store/integration/sqlite.test.ts:88`.

Add two cases to `describeEventsContract`, matching its first two (`:22-50`):
- a conflict on the second batch is a `Fail` carrying a `ConcurrencyError`, not a `Die`;
- a duplicate stream id, and an unknown type in the second batch, are each a `Die`.

That is the unit-level proof that `ConcurrencyError` is `appendAll`'s only failure.

### 5. What else has to implement it

The only `EventsPort` implementations are the three stores and the three faces:
- `makePostgresEvents`
- `makeSqliteEvents`
- `fromPromiseStore`
- `deferredEvents` (`packages/event-store/src/choose.ts:179-188`)
- the spread fake in `events-contract.ts:56`, which inherits `appendAll` from `...events`

`packages/daemon/src/control.ts:141`, `packages/daemon/src/failure-recorder.ts:26` and `packages/projector/src/projection.ts:276` only receive a port; none of them build one. The hand-written `EventStore` objects the ticket lists are the whole of the typecheck fallout outside the package.

Export `StreamBatch` and `appendAllFace` from `packages/event-store/src/index.ts`, beside `EventsPort` (`:61`).

### Verification

Only `unit/memory.test.ts` and `unit/events-memory.test.ts` run inside the pass. The Postgres and SQLite runs of the same cases are in the integration half, which runs after the merge. What stands in for them before the merge: the memory store passes the same cases, and the two real stores share the validation helper and the `current`-index pattern. Run `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test`. The ratchet test is in that last run and goes red if the face shape or the faces entry is wrong.
