# Design note: #931, a `PassRouted` names the `StepEnded` its proposal came from

## The one decision the ticket gets wrong: `reported` is the wrong carrier

The ticket's Fix step 2 says to take `ended` from `reported`, and to write `null` when there is no `reported` visit. That breaks the ticket's own **Want** in one common case. `reported` is null exactly when `review` *passed* while carrying findings above the bar:

```ts
// run-attempt.ts:1628
const reported = ending.ending === 'passed' ? null : { step: at, ending }
```

The comment at `:1621-1627` says: *"`reported` is null only for that one case — `review` passing on its own way through, carrying findings above the bar."* Those findings are still on a `StepEnded`, the one review wrote. The route's `offer.proposal.findings` is a copy of them. Following the ticket's Fix would write `ended: null` there and silently drop every such route from T6b's reference.

`reported` exists for something else: *"what a person should be shown if this escalates"* (`run-attempt.ts:1308-1311`). That is a different question from *which `StepEnded` produced this proposal*.

**So:**
- Take `ended` from the visit whose `StepEnded` produced the proposal. At `:1629` that is `reached` (`next.proposal` comes from `nextOf` over that visit's outcome).
- Hand it to `routeProposal` as its own argument. Do not derive it from `reported`.
- Both `routes.push` sites (`:1344`, `:1398`) use that argument.
- `ended` is `null` only where the visit wrote no `StepEnded` (`outcome === undefined`, `:1515`) or `decidingAction(outcome)` is `null` (`action.ts:341-344`).

The Want wins over the Fix because the Want is the definition, and this is the case T6b depends on. Pin it with a test: a `review` that passes with findings above the bar yields a route whose `ended.version` is that review's `StepEnded`.

## Where the version is caught

The `StepEnded` is emitted inside the callback `runAttempt` hands to `runStep` (`run-attempt.ts:1513-1519`). `record(visit)` runs *before* the emit, and it pushes the visit into `steps` (`:1292-1296`). So the version can't be written onto the recorded `StepReached`: that object is already pushed and is `readonly`.

- **Use a lap-local `let endedAt: number | null = null`.** Reset it before each `runStep` call and assign it in that callback's `.then`. Read it after `runStep` returns, next to `reached`.
- **Do not add a field to `StepReached`** (`:563-577`). It is the walk's in-memory record, and `test/one-attempt.ts` compares against it. A new field there spreads into every test fixture for no reader.
- If the emit is refused, the callback throws, `unappended` is set, and the pass dies before any route is appended (`conduct.ts:4306-4309`). So a stale or null `endedAt` can never reach a stored route.

The action name is `decidingAction(reached.outcome)?.name`, the same choice `nextOf` makes (`attempt-next.ts:121`). Use the same function so the two can't disagree.

## `emit`'s return

- `appendAt` (`conduct.ts:697-700`) returns the version of the last envelope `store.append` gives back. `append` resolves to `Envelope[]`, and each envelope's `version` is `expectedVersion + 1 + i` (`event-store.ts:320`, `:346`).
- `appendNow` (`:725-732`) passes that through. Nothing else changes in either.
- The other caller of `appendAt` is the tolerant `PassRouted` append, which ignores the return, and that is fine.
- Type `AttemptOptions.emit` (`run-attempt.ts:850`) as `(event) => Promise<number | void> | number | void`. The fakes in `packages/conductor/unit/{run-attempt,attempt-steps,a-base-that-moved,what-a-destination-costs,a-base-that-is-red-buys-no-round}.test.ts` and `test/a-url-destination.ts` then still type-check without edits.
- A `void` back from a fake becomes `endedAt = null`. That is honest: a test that does not number its events gets no reference.
- The new tests use a fake that numbers what it receives, per the ticket's Done when.

## Keep `ended` off the in-memory `RouteOffer`

- Put `ended` on `RouteTaken` (`run-attempt.ts:985`), next to `offer`, and merge it in only at the append (`conduct.ts:4355-4360`): `offer: { ...route.offer, ended: route.ended }`.
- `offerFor` (`routing.ts:135`) never sets it.
- The `offer` handed to `replyFor` and the judge stays exactly as it is today. A `judge: claude-code` agent is shown the offer, and it has no use for a log version.
- The optional field on the `RouteOffer` schema (`routing.ts:71-75`) is what lets `parsePayload('PassRouted', …)` (`events.ts:1427`) accept the field and keep it.
- Because the field is optional, the inferred `RouteOffer` type gains `ended?:`. No constructor has to supply it.

## Checks

Everything here is unit-level: a fake `emit`, `runAttempt`, and `parsePayload`. Nothing depends on `pnpm test:integration`.

The live check stays the person's, as the ticket says. For each `PassRouted` after the restart, read the event at `offer.ended.version` on the same `pass-` stream. It must be a `StepEnded` whose action named `offer.ended.action` has `evidence`/`findings` equal to `offer.proposal`'s `output`/`said`/`findings`.

No ADR is contradicted: 0100 §14 already decides the reference, and §4 allows the optional field.
