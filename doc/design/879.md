## `census()` in SQL

Two statements, in this order:

1. **Ask the catalogue whether the table exists.**
   - Postgres: `SELECT to_regclass('"public"."stream_snapshots"') IS NOT NULL AS "result"`, the form of `schema.ts:174`.
   - SQLite: `SELECT 1 FROM sqlite_master WHERE type = 'table' AND name = 'stream_snapshots'`.
   - No table means `[]`. **Never call `ensure()`.** It is `CREATE TABLE IF NOT EXISTS` (`snapshots.ts:200-206`), and doctor's own header says *"It never writes"* (`doctor.ts:26`).
2. **One grouped statement over the table:**
   ```sql
   SELECT reducer, reducer_version, count(*) AS rows,
          sum(CASE WHEN <anchor> THEN 1 ELSE 0 END) AS anchored,
          sum(<length>) AS bytes
   FROM stream_snapshots s
   GROUP BY reducer, reducer_version
   ```
   - `<anchor>` is the existing `stored('s')` (`snapshots.ts:209-215`). Use it unchanged, so the census and `latest` cannot disagree about what holds. That matters most for Postgres's `date_trunc` note at `:136-142`.
   - `<length>` is `octet_length(s.state::text)` on Postgres and `length(CAST(s.state AS BLOB))` on SQLite.

The two statements are not atomic. If the table is dropped between them, the second one throws, and the row turns that into `warn`. Nothing needs a lock.

**Parse the numbers through `integerOf`** (`snapshots.ts:163-168`). Postgres returns `count(*)` as `bigint` text and `sum` as `numeric` text. A plain `Number(row.rows)` happens to work, but a `typeof === 'number'` check reads every Postgres row as malformed. If a cell parses to null, `census()` throws. It never answers zero.

## The contract case must survive a shared log

The Postgres harness shares one log with other cases (the `plant` and `empty?` comments, `test/snapshot-contract.ts:15-18`). The census is aggregated over the whole table, with no stream filter. If the case used the suite's `reducer: 'control'` (`:24`), it would count rows from every other case and every earlier run, and go red in the integration half after the merge.

So the case uses reducer names unique to the harness, such as `` `census-a-${h.sid}` `` and `` `census-b-${h.sid}` ``. It asserts only on census rows whose `reducer` is one of those. Build the three rows like this:

- **Usable:** `put` an anchored row at name A, v2.
- **Older version:** `put` an anchored row at name A, v1.
- **Void anchor:** `plant` a row at name B, v1, with a `lastSeq` no event has.

That checks `rows`, `anchored` and `bytes > 0` per `(reducer, reducerVersion)` on memory and SQLite in `pnpm test`. The same case runs against Postgres in `integration/snapshots.test.ts:46`, which a pass cannot run, so the unique names are the unit-level stand-in that keeps it green there.

**The absent-table test is not in the contract**, because the memory store has no table. Put it in `unit/snapshots.test.ts`'s SQLite block:

1. On a freshly opened SQLite log, call `createSqlSnapshotStore(...).census()` and expect `[]`.
2. Then check that `sqlite_master` still has no `stream_snapshots` row.

Opening the log does not create the table, because the snapshot store is lazy (`sqlite.ts:636` only constructs it).

## The row

Name it `snapshots`, following `readableTypes` (`doctor.ts:1653-1671`): an exported `async function snapshotCensus(census: () => Promise<SnapshotCensusRow[]>)`. Classify against `REDUCERS` from `@lingtai/domain`. `apps/cli` already depends on it (`doctor.ts:71`).

Wire it into both branches, after `holds`:

- **File-backed:** `log.snapshots.census`.
- **Postgres:** `createSqlSnapshotStore(createPostgresTicketSql({ url: direct })).census`. `createPostgresTicketSql` opens and ends a client per query (`queries.ts:352-360`), so there is nothing to close.

**Classifying one census row.** It carries `rows` and `anchored`, but not which rows are anchored:

- Name not in `REDUCERS`, or version above the registered one: all `rows` are other code's.
- Version below the registered one: all `rows` are void, older version. This is where *both older and unanchored counts once* falls out.
- Version equal: `anchored` rows are usable, and `rows − anchored` are void by anchor.

Bytes are reported per census row. For a current-version row that is part usable and part void, divide the bytes by row count. That is good enough, since the ticket puts *exact byte figures* out of scope.

**Statuses.** The ticket says only that void is `info`. This note decides the rest:

| What the census holds | Status |
|---|---|
| Every row usable | `ok` |
| Any void or other code's row | `info` |
| Table absent (`[]`) | `ok`, *no snapshots yet* |
| `census()` rejected | `warn`, naming the error |

Other code's rows are `info` too, never `warn`. They are true and there is nothing to do, which is how `info` is defined at `doctor.ts:143-146`.

The failing read gets its own `.catch`, so it never reaches `readableTypes`'s `catch(() => null)` → `ok`. The ticket's edge says a failed read is never `ok`.

The detail follows the ticket's example. List other code's rows as `other code: <reducer> v<n> ×<rows> (<KB>)`, never under `void:`. There is no `fix` line.

`gatingFailures` (`restart.ts:1464-1466`) counts only `fail`. The *unchanged* checkbox is one assertion on a report that contains this row as `info`.
