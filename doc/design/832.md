## Design note for #832: what the ticket leaves implicit

The ticket already gives the shape. These are the points where the code makes it easy to get wrong.

### 1. Where the fixtures go, and why the order matters

`histories.ts` stamps every event from two module counters, `nextSeq` and `slot`, at the moment the expression is evaluated (`packages/domain/test/histories.ts:55-63`, `stamp`). The order the module evaluates in today is: `histories` (`:442`), then `scenarios` (`:581`), then `lateHistories` (`:722`), whose `run:` entries are function calls inside the object literal.

The conversion the ticket asks for:

- Put one `const` per current `lateHistories.run` entry directly above `export const lateHistories`, below `implementThenReviewed`'s definition (`:707`). Keep today's order: `fixRoundRouted` … `implementThenReviewed`.
- Put `const githubLedger = …` and then `const bodyBeforeAnotherWait = …` after them.
- Make the literal only reference these consts: `run: { fixRoundRouted, … }` and `ticket: { githubLedger, bodyBeforeAnotherWait }`.

Hash keys are `${kind}.${name}` across `histories` and `lateHistories` together (`unit/histories.test.ts:51-56`). That means `lateHistories.ticket` and `histories.ticket` share one namespace in `histories.hashes.json` (`"ticket.claimedReleasedClaimedLanded"` …, `:12-17`). The two new names don't collide with anything there.

Build wait ids with the file's own `wait(name)` (`histories.ts:64`, `` `wait-${name}` ``), for example `wait('ledger-1')`. Don't use `aWaitId()` (`test/events.ts:26`): it is a module counter, so a history's ids would depend on how many came before it. Use `aWait` for the `SignoffRequired` reason, as the other ticket histories do.

### 2. Closed absorption is already handled; don't handle it again

The guard at `ticket.ts:249` returns before the `switch` only for `LIFECYCLE_EVENTS` (`:224-232`). The two new cases are not in that set, so they apply on a closed ticket with no extra code.

`github.lastWait` should be set **inside the existing `WaitStarted` case** (`:339`), next to `lifecycle`, and nowhere else. Then a `WaitStarted` after `TicketClosed` is absorbed with no special code, which is what the ticket's D6 edge requires.

Each of the three cases spreads `state.github` (`{ ...state.github, … }`), and `emptyTicket` (`:199`) gets the empty ledger.

### 3. Converge compares event-type strings at four places

`lastOutcome` is a `Map<string, string>` holding the **event type** (`converge.ts:345`, `:368`). Every read compares against `'IssueUpdateFailed'`:

- `:374` `outstanding`
- `:411` `closed`
- `:422` `comment`
- `:448` `refs`

Swapping in `item.github.last` means each of these becomes `?.outcome === 'failed'`. Leave one as it is and it type-checks (comparing a `GitHubWrite | undefined` to a string is a TS2367 error only when the types can't overlap; `Map.get` results are not checked that way) but quietly stops matching.

Recommended: read through a small helper so that `comment-edited` is excluded in exactly one place:

```ts
const failed = (c: IssueChange) => c !== 'comment-edited' && item.github.last[c]?.outcome === 'failed'
```

Then `outstanding` is `Object.keys(item.github.last).some(failed)`. Write the `:367` comment (*"attempted once and never repaired, so it is no divergence"*) on this helper.

`lastWrote` becomes `item.github.labels ?? []` and is read only at `:382`.

The `for` loop keeps only the `EndActionsResolved` branch (`:356-361`). Drop its `continue`.

### 4. The board: wait identity replaces position, and `item` already exists

`standingOf` already folds `own` into `item` with `applyTicket` (`apps/board/src/lib/task.ts:822-828`). So `item.github` is there for free; don't add a `reduceTicket` call.

The current test is by position: the body event's index is after `own.findLastIndex(WaitStarted)` (`:901`, `:929-931`). The new test is by identity: `bodyAfterWait === lastWait`, both non-null. The two agree whenever wait ids are unique on a ticket. They differ in one case: a `WaitStarted` after `TicketClosed`. Today that hides an earlier body outcome; under the fold it does not, because `lastWait` didn't move. That is the intended D6 behaviour, and the ticket says the conductor never writes one (`claim.ts:127`). Delete `bodyEvent`, `bodyData` and `lastWaitStarted` (`:893-901`) completely; nothing else in `standingOf` reads them.

### 5. `editEndedWaits`: only the `else if` goes

In `tell.ts:464-481`, delete the `IssueUpdated`/`IssueUpdateFailed` branch. Replace the `posted`/`edited` declarations (`:460-461`) with:

```ts
const ledger = reduceTicket(events).github
const edited = new Set(ledger.edited)
const posted = ledger.comments
```

The four other branches of the `forEach` (`WaitStarted`, `WaitResolved`, `TicketLanded`, `TicketClosed`) stay as they are.

Today `edited` is keyed by `string`. With `WaitId` it is a branded string, so `edited.has(p.waitId)` still holds. If `started.get(p.waitId)` complains, widen `started`'s key type rather than casting in the loop.

### 6. Checks

Every claim here is reached by `pnpm test`:

- the D9 tests and the hash and coverage locks in `packages/domain/unit/`;
- the six reader tests the ticket names.

None of this needs `pnpm test:integration`.
