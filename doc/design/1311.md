The ticket already gives the shape. Four points are worth fixing before the work starts.

**1. Where each caller gets `mode`.** The ticket names `modeOf`. It exists at `packages/recipe/src/settings.ts:255`, and `selectionOf(recipe).mode` (`settings.ts:450-451`) is the same value. Every `runnableNowEffect` caller already passes `selection: selectionOf(...)`, so `considerIssue` and `kindLabelOf` at `discover.ts:481` need no new plumbing: read `selection.mode` / `options.selection.mode` where they are.

`selectRunnable(Effect)` has no recipe in hand. Fill `mode` at each call site from the recipe that call site already holds:

- `packages/conductor/src/schedule.ts:275-278`: `modeOf(options.recipe)`.
- `apps/cli/src/conduct.ts:553-556`: `modeOf(resolved.recipe)`. It goes through `world.selectRunnable`, so the test worlds' fakes take the field too. `tsc` will name them.
- `apps/cli/src/status.ts:531`: `filter.ok ? modeOf(filter.recipe) : 'solo'`. When the filter is not ok, `offered` is empty (`status.ts:527-528`, *"Zero when the recipe would not resolve: nothing was offered either"*), so the fallback decides nothing.
- `apps/board/src/lib/board.ts:1028` (`select({... kinds: filter.kinds ...})`) and `apps/board/src/lib/queued.ts:339`: `modeOf(filter.recipe)`.

**2. The order inside `selectRunnableEffect`.** Apply the `['bug']` default first (`queue.ts:79`) and rank the result: `rankedKinds(kinds.length > 0 ? kinds : ['bug'], mode)`. This is the ticket's *"before the `['bug']` default"* edge. Use that one ranked list for both the filter (`queue.ts:97`) and the sort (`queue.ts:110`). If the filter and the sort read different lists, a pr-fix either disappears or sorts at index −1, ahead of everything for the wrong reason.

In `discover.ts`, compute `rankedKinds(queue.kinds, selection.mode)` once in `runnableNowEffect` and once in `considerIssue`. Do not default it there. With an empty `queue.kinds` in team mode, a pr-fix-only ticket is runnable and everything else stays `no-kind`, as it is today.

**3. `rankedKinds` stays in the queue path only.** Many other readers call `kindsOf(recipe)`: triage (`apps/cli/src/triage.ts:659`, `packages/conductor/src/triage.ts:487`), backlog (`packages/conductor/src/backlog.ts:269`), `lingtai ticket` (`apps/cli/src/ticket.ts:306`, `:757`), the recipe page (`apps/board/src/lib/recipe.ts:917`) and `base-fix.ts:106`. They answer *what kinds does this recipe name*, and a pr-fix is not one of them. If triage or `base-fix`'s `kindsOf(...)[0]` picked up `lingtai:pr-fix`, they would default new tickets to pr-fix. The only callers that change are the three in the Fix and the five `selectRunnable` callers above.

Downstream of the claim, I found nothing that checks a ticket's kind against the recipe's list. The report groups by whatever string `kind` holds (`packages/conductor/src/report.ts:240`, `:642`). So a claimed pr-fix records `kind: 'lingtai:pr-fix'` and shows up there as its own row. That is intended: it is a kind.

**4. Where `rankedKinds` lives and what it does with duplicates.** Put it in `discover.ts`, export it from `@lingtai/conductor`, and have `queue.ts` import it. It removes any entry from `kinds` whose `normaliseLabel` equals `PR_FIX_LABEL`, then prepends `PR_FIX_LABEL`. That way a recipe that names `lingtai:pr-fix` itself, in any case, gets exactly one entry, ranked first. In solo mode, return `kinds` unchanged. The `pr-fix-elsewhere` skip in `considerIssue` runs before `no-kind` is ever reached, so a recipe that names the kind on a solo machine still cannot take a pr-fix. That is the ticket's *"no recipe can lift that"*.
