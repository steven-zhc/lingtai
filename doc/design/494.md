# Design note for #494: the cold reviewer and the designer append `RunSpent`

## The decision: the pipeline emits it, and `conduct.ts` doesn't change

The ticket's *Fix* row says to carry the spend to `emit` → `appendNow(runId)`. That path already exists. Every event `runActionPipeline` produces goes through `emit` (`packages/actions/src/action.ts:649`, "the pipeline does not touch the store itself … keeping the append in one place makes that impossible to forget"). `conduct.ts`'s `emit` (`packages/conductor/src/conduct.ts:2891-2899`) appends whatever `ActionEvent` it is handed, through `parsePayload(event.type, event.data)`, onto the run stream.

So the shape has three parts:

1. **`ActionResult` gets `spent?: ActionSpent`** (`action.ts:99`), where `ActionSpent` is `Omit<PayloadOf<'RunSpent'>, 'for'>`: `runtime`, `turns`, `durationMs`, `usage`, `costUsd`. `PayloadOf` is already imported at `action.ts:38`. The action doesn't know its step or round, so it leaves out `for`. The pipeline knows both.
   - The field is optional on `ActionResult` because seven other kinds dispatch nothing.
   - Absent means *no process returned a `RunOutcome`*. Write that on the field's docblock in the style of the fields around it.
2. **`ActionEvent` gains `| { type: 'RunSpent'; data: PayloadOf<'RunSpent'> }`** (`action.ts:535`).
3. **`runActionPipeline` emits it once.** Do it right after `result` is settled, meaning after the `try/catch` at `action.ts:726-737` and before `results.push`, so before any verdict event:

   ```
   if (result.spent !== undefined)
     await emit({ type: 'RunSpent', data: { for: { _tag: 'Action', step, name: action.name, round: context.round ?? 0 }, ...result.spent } })
   ```

   Putting it before the verdict branches is the point. There is one emit site above `passed`, `never-ran`, `did-not-finish`/asked, `needs-approval` and `failed`, so no verdict branch can skip it. That is exactly the gap the ticket describes.

Don't add a field to `PipelineResult.results`. Nothing above the pipeline reads spend.

## Why `round` is right without extra work

`context.round` is "which fix round this pipeline is judging — 0 before any fix was bought" (`action.ts:463-466`). `pass.ts:1114` builds every visit's context as `{ ...options.context, onSha, round: roundsSpent, recheck }`, and `roundsSpent = next.round` when a round is bought (`pass.ts:1187`). The fix round in `conduct.ts` reads the same value: `const round = brief.context.round ?? 1`, the number on `FixRequested`, `FixApplied` and implement's `RunSpent` since #493. So a review after fix round *n* carries `round: n`.

`?? 0` covers contexts that tests build by hand. `claimStep` sets `round: 0` explicitly (`pass.ts:1367`).

## Inside `agent-action.ts`: typed so a branch cannot leave it out

Both actions already make the outcome and every branch in one function. Split each into two parts:

- a pure `reviewAnswer(outcome, …)` / `draftAnswer(outcome)` that returns `ActionResult` with the branches **moved unchanged**;
- a `run()` that calls `deps.runtime.run(...)` and then does `return { ...reviewAnswer(outcome, …), spent: spentOf(outcome, deps.runtime) }`.

The spend is attached at one site after every branch, so a new branch added later gets it without anyone remembering. Moving the branches unchanged is also what keeps `evidence` byte-identical: the `(N turns · $X)` suffixes at `agent-action.ts:~616` and in the design `passed` branch stay as they are.

`spentOf(outcome, runtime)` lives in `agent-action.ts`:

- `runtime: runtime.capabilities.id`. Use `deps.runtime` and not a pass-wide default. `dispatchDeps` swaps in the action's own runtime (`packages/actions/src/from-recipe.ts:226`, `deps.runtimeFor(action.agent)`), and a recipe may review with `agent: codex` (`one-pass.ts`'s *two runtimes in one pass*). This is #493's `dispatched.capabilities.id` rule.
- `turns`, `durationMs`, `costUsd` copied off the outcome. `null` stays `null` (`events.ts:703-710`: "neither field ever defaults to zero").
- `usage: outcome.usage ?? []`. `RunOutcome.usage` is optional (`packages/agent/src/runtime.ts:183`) and `RunSpent.usage` is required.

**What gets no `RunSpent`, with no code needed to make it so:**

- The review's empty-diff return (`agent-action.ts:438-442`). It is before the dispatch and there is no outcome. Keep it outside the wrapped part.
- A `deps.runtime.run` that rejects. The action throws, the pipeline's `catch` makes up a `failed` with no `spent` (`action.ts:729-736`), and that is 0110 §2's *a process killed with no result records nothing*.

**Don't set `spent` on `createWorkAction`'s result.** `implement`'s spend is appended by `conduct.ts` itself since #493 (`runSpentFrom`, inside the `RunFinished`/`RunFailed`/`FixApplied` batches). If the work action also carried it, the pipeline would write a second `RunSpent` for the same `(implement, name, round)`.

## What stays untouched

- Step event payloads. `RunSpent` is its own event, so `StepPassed`/`StepFailed`/`StepDidNotFinish`/`StepNeverRan`/`StepAsked` are emitted exactly as now (0110 §2).
- `@lingtai/domain`'s `StepEvent` (`packages/domain/src/adapters.ts:44-52`). It is documented as "structurally identical" to `ActionEvent`, but it is what `eventOf` reproduces from a `StepOutcome`, and no outcome carries spend. A subset is still assignable where an `ActionEvent` is wanted, so typecheck holds. Add a line to that header saying `RunSpent` is deliberately not in the list.
- `ACTION_EVENT_TYPES` in `packages/conductor/test/one-pass.ts:47`. `once()` compares the run stream filtered by that set against `eventOf` (`one-pass.ts:123-128`). Leave `RunSpent` out of the set and that parity check is unaffected. Put it in and every review row fails parity.
- `conduct.ts`. If `emit`'s `as ToAppend` cast refuses the widened union, fix it there and nowhere else.

## Tests

Add to `packages/actions/unit/agent-action.test.ts`. It already drives `runActionPipeline` with a fake runtime and collects `ActionEvent[]` (`:740`, `:759`, `:805`). Write one test per branch, each asserting **exactly one** `RunSpent` whose `for` is `{_tag:'Action', step, name, round}` and whose `turns`, `durationMs`, `usage`, `costUsd` are the outcome's:

- **Review:** `never-started`, `no-structured-answer`, did-not-finish (one of `crash`/`timeout`/`out-of-turns`), unreadable, `passed`, `failed`.
- **Design:** `never-started`, did-not-finish, question (`StepAsked`), unreadable, `passed`.

Also cover:

- `costUsd: null` and an outcome with no `usage`, which writes `[]`;
- `round` taken from `context.round`;
- `runtime` being the dispatched runtime's id;
- **none** for the empty diff and for a runtime whose `run` rejects;
- `RunSpent` sitting before the verdict event;
- for one existing row, `toEqual` on the verdict event's `data` against what it asserts today, so a stray field on a step event fails.

**Fixtures that will go red, and the only correct edit:** the conductor's fake pass runs the real `createAgentAction` against fake runtimes. So `packages/conductor/unit/what-a-pass-writes-today.test.ts`, and any other test that lists run-stream event types for a pass with a reviewer or drafter (`attempts.test.ts`, `pass.test.ts`, `what-a-destination-costs.test.ts`), gain one `'RunSpent'` immediately before each review or design verdict event. Insert it there only. Any other change to a list means an order or payload moved. In one review-after-a-fix row, assert that the review's `RunSpent.data.for.round` equals the preceding `FixApplied.data.round`.

All of this is in `pnpm test`, so nothing here depends on the integration half. On the live log, the claim is settled by a pass stream where every `StepStarted` for a `review`/`design` agent action is followed by one `RunSpent` with that `step` and `action` name before its verdict event. A review round should show a `costUsd` matching the `$X` in that verdict's `evidence`.
