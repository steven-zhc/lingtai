## Shape

The field and its accessor follow `source.tickets` / `ticketSourceOf` (#381) exactly. That pair is the precedent for "optional, no schema default, the accessor supplies the absent case". Copy it instead of inventing a new shape.

**The field.** It goes in `repo:` in `Recipe`, beside `base` and `submodules` (`packages/recipe/src/recipe.ts:2827-2832`). Write it as `remote: z.string().min(1).optional()`.

- **No `.default(...)`**, for the reason at `recipe.ts:1049-1058`: *"a schema default would put `tickets: 'github'` into every recipe's parsed body and change every project's `configHash` the moment a restarted daemon loaded this code, with no edit to any recipe file (`resolveRecipe`'s `hashRecipe(parsed.data)`, `0047` §2)."* A null default does the same damage.
- **Don't parse the value.** `z.url()` would refuse the absolute path that #394 writes for a directory project. Git accepts URLs, scp-style `git@host:path` and paths, and it is the only reader that needs to understand them. `min(1)` refuses the one value that is certainly wrong.

**Only in `repo:`, not on `worktree:`.** `baseOf` and `submodulesOf` read `cutAt(recipe)` first because 0061 §4 moved those two onto `admit` (`settings.ts:28-36`, `228-263`). Nothing moves `remote`, and it is not a property of one cut. The mirror at `worktree.ts:102` is per project, and the merge lane pushes to the same remote. `worktreePlugin`'s fields are a `z.strictObject` (`recipe.ts:836`), so leave them alone: adding `remote` there would create a second spelling that `remoteOf` would have to choose between. `the-v2-recipe.md:107` says *"`repo:` was never a section about the repository. It was about what `admit` cuts"*. That is a design note, not an ADR, and this field makes `repo:` about the repository again, so add one sentence to the field's doc comment saying so. No ADR is contradicted, and no superseding file is needed.

**The accessor.** Add `remoteOf(recipe: Recipe): string | null` to `packages/recipe/src/settings.ts`, after `ticketSourceOf` (`settings.ts:338-340`), returning `recipe.repo.remote ?? null`. `index.ts` already re-exports `settings.ts`, so nothing else needs exporting.

**The guard.** `MOVING` at `packages/recipe/unit/settings.test.ts:466` fails on any `src/` that reads a moved setting directly:

    const MOVING = /\w\.(runtime\.(limits|assignee)|repo\.(base|submodules)|source\.(kinds|exclude|backoff))\b/

Add `remote` to the `repo\.(…)` group. That is how "every reader asks the accessor" holds when #352 arrives, and not just in this diff. Nothing reads `.repo.remote` today, so the guard stays green. `options.remote` (`conduct.ts:376`, `schedule.ts:76`) does not match, because the pattern requires `repo.` before `remote`.

## The field's doc comment: correct the ticket's *Watch out*

The ticket says a running daemon *refuses* a recipe key its code does not know (#148). **That is false for `repo:`.** `repo` is a `z.object`, not a `z.strictObject` (`recipe.ts:2827`). An older daemon handed `repo.remote` silently drops the key and goes on using the GitHub URL, exactly as `recipe.ts:1060-1064` says of `source:`:

> `source:` is `z.object`, not `z.strictObject`, so an older daemon handed `tickets: db` does not refuse it — it silently drops the key and keeps running the project from GitHub. There is no refusal to notice that by

Write *code, restart, paste* with that consequence: there is no refusal to notice. Don't make `repo` strict to get one. That would refuse every recipe carrying a key some preset or an older `propose` wrote, and it is a separate decision.

The comment must also say:
- The value is the repository's own `origin`, written by `init`/`add` (#394, #391), and no bare repository is made.
- Absent means `https://github.com/<owner>/<repo>.git` (`worktree.ts:102`).
- This field is not where tickets live; that is `source.tickets` (#381).
