**The stream already has writers, and they race.** `int-<project>-<base>` is the merge lane's stream. `integrate.ts` already retries there on a lost race (`packages/repo/src/integrate.ts:251-256`): "The lane's stream has more than one writer *by design* … an append here re-reads and retries on a lost race — which is exactly what `ConcurrencyError` means". `store.append` takes an expected version (`packages/event-store/src/event-store.ts:346`). An integration that lands while a check runs for 35 seconds will have moved the version you read before the run. So append the same way `integrate.ts:263-277` does:
- read the stream;
- append at `events.length`;
- on `ConcurrencyError`, wait a little and re-read; on any other error, stop.
- Keep it bounded: 8 attempts, as there.

If the retries run out or anything else is thrown, that is the ticket's *the append fails after the command ran* edge. The answer is still returned, and the failure is noted.

Adding `BaseChecked` to that stream does not disturb the lane's own fold. `applyIntegration`'s `default` arm ignores a type it does not know and only advances the version (`packages/domain/src/integration.ts:118-120`: "ignored, not rejected"). `landing-lane.ts` does not read the stream at all; no `read(` in it matches.

**Do not take `conduct.ts`'s `appendNow` as the append dep.** On failure it sets `unappended` and re-raises the whole pass as a defect (`conduct.ts:661-669`; the comment above it says "the pass is re-raised into the defect channel the moment it returns"). That contradicts the ticket's edge, which says the answer is still returned and the failure is noted. The port takes the store (`read` and `append`) as a dep and calls `store.append(stream, at, [{ type: 'BaseChecked', actor: 'conductor', data: parsePayload('BaseChecked', {...}) }])` itself.

The finder accepts this as written:
- `append` is in `APPEND_CALLEES` (`scripts/events.ts:28-34`).
- A property-access callee counts (`:357-361`).
- An object literal inside an array argument is searched (`:364-367`).

So no `ELSEWHERE` row is needed, as long as the `type:` string stays inside the literal at the call. Do not build the payload in a helper and pass a variable.

**The shape of the port**

- **Deps:**
  - `store`: `read` and `append`.
  - `cut(path, sha)`: wraps `git worktree add --force --detach`, the call at `packages/repo/src/worktree.ts:201`.
  - `remove(path)`.
  - `plant(path)`: the env file, as `trial-build.ts` plants it.
  - `run`: `runCommand`'s signature.
  - `worktreePath(project, sha7, runId)`.
  - `note(line)`: the run-log line for a failed append or a failed removal.
- **The question:** `{ project, base, baseSha, command, prepared: readonly string[], runId, signal, timeoutMs }`. `prepared` is the `run:` texts only. The port does not resolve the recipe; that is #744's job, and it keeps the unit tests free of recipe fixtures.
- **The answer:** a union of
  - `{ verdict: 'green', exitCode: 0, from }`
  - `{ verdict: 'red', exitCode, evidence, from }`
  - `{ verdict: 'unknown', why }`

  `from` is `'log' | 'ran'`. #744's hold wording will want to say whether this pass paid for the run. It also lets the "reads the log, runner never called" test assert on the answer, not only on the fake.
- **The verdict:** `ok` comes from `exitCode === 0`. Record only when `!timedOut && exitCode !== null && !signal.aborted`, checked after the run returns. A `runCommand` that returned after an abort can still carry an exit code from the killed group, and that must not be recorded.

**The in-flight map**

- Key it on `(stream, baseSha, command)`, where `stream` is `integrationStream(project, base)`, not `(project, …)`. The stream is the log's key, so two bases at one sha are two questions. Sharing one run across them would append to only one of the two streams.
- Look in the map before reading the log. A second asker that arrives while the first is reading or running gets the same promise.
- Delete the entry in the promise's `finally`.
- The shared run uses the **first** asker's `signal` and `runId`. If the first pass is aborted, the second asker also gets `unknown`, nothing is appended, and its next ask runs it again. Write that in the file's header comment so nobody "fixes" it later.

**The order inside one ask**

1. Read the stream. If the read rejects, answer `unknown` and do not cut.
2. Find the last `BaseChecked` whose `baseSha` and `command` match exactly. If there is one, answer from it, using its `evidence`.
3. Cut. A cut failure is `unknown`, and it still goes through the `finally`.
4. Plant the env file.
5. Run the `prepared` commands in order. The first one that does not exit 0, or times out, is `unknown`, and its own evidence goes in `why`.
6. Run the command itself.
7. Remove the worktree in `finally`. A failed removal is a `note`, never a change to the verdict (as at `trial-build.ts:204-224`).
8. Append with the retry above, but only on a recordable outcome.

**Tests**

- All in the unit project, with `createMemoryEventStore()` and fakes for `cut`, `plant`, `remove` and `run`. No `git` and no temporary directory (0060 §1).
- Lost race: append an `IntegrationAttempted` to the memory store from inside the fake `run`, then assert that exactly one `BaseChecked` lands. That is the unit-level stand-in for a race with a real merge lane, which only the integration half could show.
- Concurrency: two `ask`s started before either resolves, a `run` fake that resolves on a deferred, and `expect(run).toHaveBeenCalledTimes(1)` on the command itself. The `prepared` runs are counted separately.
- `what-an-event-is-written-at.test.ts` checks *appended ⊆ declared*. Nothing calls the port yet, so no fixture reaches `BaseChecked`. The `EVENT_AT` row is a declaration for #744, and `satisfies` (`events.ts:2152`) is the only thing that holds it today.
