# Design: #620 — `init` and `add` on `@effect/cli`, asking through `@clack/prompts`

## Neither command takes `--json`, and that is 0121, not an omission

`commands.ts:41` and `:410` mark both `add` and `init` as `effect: 'changes'`. 0121 §5 says *"Every command whose definition says it only reads takes `--json`"*, and §6 says *"The `reads`/`changes` marker is what decides whether a command takes `--json`"*. A finished `init` run with no flags changes nothing, but that is not enough to make it a read command. So:

- Do not add `--json` to either command.
- The *Done when* row about `--json` shape tests has no subject in this change. Say that in the PR, and quote §5 when you do.
- `world.ts` has no read command either. Its only question is `uninstall`'s `[y/N]` (`world.ts:88-99`, asked from `install.ts:651`).

The ticket's *Watch out* still applies to text: whatever quotes the old lines has to move in this same change. I searched the repo outside `apps/cli/src`. Only these quote the output:

- `doc/tutorial.md:267` quotes `app          <slug>, owned by <owner> — it answered`. The padding is about to change, so rewrite that line in the tutorial.
- `apps/cli/integration/init.test.ts:333`, `:414` and `:940` assert three phrases: `lingtai add asks GitHub-or-directory`, `run lingtai init again`, and `lingtai init --store sqlite again`. Those words must stay exactly as they are. Those tests cannot run inside a pass, so check them by reading, and say so in the PR.
- `apps/site/public/install.sh:174,176` only names `lingtai init`. It parses none of its output.

## Routing: both commands join `MIGRATED_COMMANDS`

- In `migrated.ts:9`, the list becomes `['version', 'status', 'doctor', 'init', 'add']`.
- Delete the `'init'` route, both from `Route` and from `routeOf` (`migrated.ts:28`).
- Delete `entry.ts`'s `init` branch (`entry.ts:38-60`).
- Delete `lingtai.ts`'s `addCommand` (`lingtai.ts:116-118`) and its `case 'add'` (`:1001-1002`). `parseFlags` stays in `add.ts`: `lingtai.ts` still uses it in eight places (`lingtai.ts:890…1156`).

**Keep the `process.exit` that init needs.** `entry.ts:46-53` exits through `process.exit(code)` when the code is non-zero. The reason is that *"the board's listening socket holds the event loop open past it (#394 finding 1)"*. The `effect` branch (`entry.ts:31-37`) only sets `process.exitCode`. If init moves there unchanged, any refusal that comes after the board starts will hang.

Do not make `process.exit` the rule for every migrated command. It can cut off `doctor --json` partway through writing to a pipe. Instead, keep the rule for init alone: in the `effect` branch, write `if (code !== 0 && argv[0] === 'init') process.exit(code)`, and carry the #394 comment over with it.

`routeOf` already sends `init --help` and `add --help` to the definitions (`migrated.ts:21`). Add these rows to `migrated.test.ts`:

| argv | route |
|---|---|
| `init` | `effect` |
| `init --store sqlite --defaults` | `effect` |
| `add owner/repo` | `effect` |
| `add --local . --defaults` | `effect` |
| `init --help` | `help` |
| `add --help` | `help` |

## Parsing: typed options, mapped back onto the record the wizards already read

`chooseFirstProject`, `askBeforeGithubAdd` and `askRecipe` all take `flags: Record<string, string>` and `buildFlags: string[]` (`add.ts:101,109`, `init.ts:466`, `recipe-flow.ts:97-99`). Under them, roughly twenty refusals work by looking up keys in that record:

- `init.ts:438-455`
- `first-project.ts:157`, `:510-541`
- `add.ts:86-97`

**Do not retype those modules.** Here is the shape instead:

1. **Write the options once, in `cli.ts`.** Every key must exist today:
   - init's twenty keys are the list at `init.ts:282-301`.
   - add's keys are the ones the grep finds read across `add.ts`, `add-github.ts`, `first-project.ts` and `recipe-flow.ts`: `github`, `local`, `project`, `github-app`, `base`, `tickets`, `kinds`, `agent`, `model`, `reviewer`, `reviewer-model`, `install`, `build`, `land`, `rounds`, `wall`, `budget`, `defaults`.
   - Share the recipe flags between init and add as one record of options.
   - `--build` is `Options.text('build').pipe(Options.repeated)`.
   - `--defaults` is `Options.boolean`.
   - `add` takes one optional positional, `Args.text({ name: 'owner/repo' })`.
   - Make every other option `Options.text(...).pipe(Options.optional)`.
   - Leave `--store` and `--port` as text options, not `Options.choice` or `Options.integer`. `init.ts:335-341` refuses them in its own words, and those words are what scripts and tests read.
2. **Map the parsed options with `flagsOf(parsed): { flags, repeated }`.** It is a pure function, and it rebuilds exactly the shape `parseArgs` and `parseFlags` return today:
   - an absent option gives an absent key
   - `--defaults` gives `''`
   - `flags.build` is the last value, and `repeated.build` holds every value
3. **Change the entry points.** `initCommand(args: { flags, repeated }, world)` and `addFlow(args: { positional?, flags, repeated }, world)` take that shape. Delete `init.ts`'s `parseArgs` and `USAGE` (`init.ts:226-231`, `:274-323`). The handler bodies are otherwise unchanged.
4. **Add a test helper.** Put one helper under `apps/cli/test/` that turns the existing `['--local', '/repo', …]` fixtures into `{ flags, repeated }`. The unit tests can then keep their arrays (`init.test.ts:166`, `:200`, `:210`, `:218`, `:241`, `add.test.ts:111`, …). Pin `flagsOf` itself through `runCli` with a fake handler. If that is awkward, export the `Command` factory, which takes the world as a parameter, and call that instead.

**The handlers import their modules dynamically.** `init.ts` loads the board server: *"Only once asked: `init.ts` loads the board's server module"* (`entry.ts:39`). So the `init` and `add` `Command`s live in `cli.ts`, and their handlers `await import('./init.ts')` or `('./add.ts')`, the same way `status` does at `cli.ts:46-49`.

**Behaviour that changes on purpose. Name each change in the PR:**

- An unknown flag on `add` was silently ignored before, because `parseFlags` accepts anything. Now it is refused as a usage error.
- `--x=value` is now accepted.
- A usage error now exits 1, as every migrated command does (`cli.ts:128`). Before, init used `refuse(…, 2)`.
- `add`'s exit 2 for "no repository was picked" (`add.ts:122`) is a handler result, not a usage error, so it stays 2.
- `--build` given with no value used to reach `setup-build.ts:279`'s *"--build takes a command, or none — not empty"*. Now `@effect/cli` refuses it as a usage error.

Test both orders, `add --defaults owner/repo` and `add owner/repo --defaults`. `add.ts:61-65` exists only because the first order broke once (#433).

**Make help match.** `commands.ts:411-425` lists 4 of init's 20 flags. 0121 §6 makes the definition the one source of help, so list every option the `Command` accepts.

## Questions: one seam, `question()`, now with a clack front end

Every question in both wizards goes through `question()` (`question.ts:110`) and calls `world.ask(prompt)`. That includes the ones in `agents.ts`, `setup-build.ts`, `source.ts`, `landing.ts`, `runtimes.ts`, `first-project.ts` and `init.ts:805`. **Change the seam. Do not change the callers.**

- **Give `QuestionWorld.ask` an optional second argument:** `ask(prompt: string, shape?: { message: string; defaultValue: string; choices?: readonly string[] })`.
  - `question()` passes `q.prompt`, the default it has already computed (`question.ts:122`), and `q.choices`.
  - The first argument stays byte-for-byte what it is now, painted bracket and all. Every fake world matches on it: `init.test.ts:94`, `first-project.test.ts:111`, `landing.test.ts:55`, `question.test.ts:32` and others. None of those fakes needs to change.
- **Put the live ask in `prompt.ts` and delete `liveAsk`** (`question.ts:60-74`).
  - When `refusal()` (`prompt.ts:19`) is non-null, return `null`. `question()` already turns `null` into the by-name refusal along with its `kept` clause (`question.ts:126-127`). Do not use `askText`'s throwing path for this.
  - Otherwise, `choices` gets a `clack.select` with `initialValue` set to the default. Anything else gets a `clack.text` with `defaultValue` and a placeholder.
  - The `validate` loop stays inside `question()`.
  - The live ask is shared by `liveAddWorld` (`add.ts:129`) and `liveInitWorld` (`init.ts:1005`).
- **This tightens one thing, on purpose.** Today a terminal stdin with stdout piped (`lingtai init | tee`) still prompts. After this change it refuses, naming the flag. 0121 §9: *"A prompt never appears without a TTY"*. Mention it in the PR.
- **Ctrl+C at a clack prompt** (`isCancel`) prints the same sentence and exits 130, exactly like the readline `SIGINT` handler at `question.ts:64-67`.
- **`world.ts`'s `uninstall` confirm becomes `askConfirm`** (`prompt.ts:51`), with `--yes` as its flag.
  - Keep the non-TTY sentence at `world.ts:90` word for word. It already names `--yes`.
  - `askConfirm` throws `PromptRefused`. Turn that into `return false` at this call site, so `install.ts:651` is untouched.
- **Spinners.** Add an optional `spin<T>(label, fn: () => Promise<T>): Promise<T>` to `QuestionWorld`. Where it is absent, it just runs the function. The live one uses `clack.spinner()` only when both streams are TTYs.
  - Wrap `world.runtimes()` (`init.ts:358`), `world.database(url)` inside `chooseStore`, `world.register(...)` (`first-project.ts:493`) and `world.github.add(...)` (`first-project.ts:630`).
  - Stop the spinner before the fact line is logged. That way, output off a TTY is byte-identical with or without one.

Facts are never printed through `clack.log`, `intro` or `outro`. They go through `output.ts` (0121 §1). clack draws only the prompt.

## #542: the summary goes at the end of `askRecipe`, and only defaults can trip the confirm

Both CLI registrations happen right after `askRecipe` returns:

- local: `world.register` at `first-project.ts:493`
- GitHub: `askBeforeGithubAdd` leads to `chooseFirstProject`, then `world.github.add` at `first-project.ts:630`

So the summary is the last step of `askRecipe`, after `askLimits` (`recipe-flow.ts:287`). It reads the **file as written**, the same way `askLanding` does (`resolvedFile`, `landing.ts:141`) and the same way `askInstallAndBuild` does (`resolvedRunActions(project, 'build')`, `setup-build.ts:355`). It never reads the answers in memory:

```
Before registering chapter-garden
  checks    npm test · npm run lint
            — or: none — steps.build is empty, so nothing checks a diff before review
  review    claude-code
            — or: none
  landing   unattended — a pass that clears review lands on <base> with no person
            — or: held — every pass stops at proposed for a person
  change    lingtai add --local <dir>    (or lingtai add <owner>/<repo>)
```

`RecipeAt` gets a new field, `again: string`, which is the `change` row's command. Each caller knows its own value: `first-project.ts:449` and `add-github.ts`.

**The decision the ticket leaves open is when the summary must stop the run.** Under "use every default? yes", `askWorld` is `acceptingDefaults(world)` (`recipe-flow.ts:162`), and every question is answered `''` without a pause. That is exactly the #542 path: `npm ci`, `build: []`, landing on the base branch. The confirm question is asked when all three of these hold:

1. defaults were taken, meaning `askWorld !== world`;
2. the summary has a risky row: an empty build with `at.buildFlags.length === 0`, or unattended landing with `at.flags.land === undefined`;
3. no flag named that choice explicitly. An explicit `--build none` or `--land main` is a person choosing, and the ticket keeps that available.

**Ask it of `world`, not `askWorld`.** That way a terminal user who accepted every default still has to stop and read. The call is `question(world, { name: 'the summary above', flag: '--defaults, or --build <cmd>|none and --land <branch>|hold to choose explicitly', given: at.flags.defaults !== undefined ? 'yes' : null, choices: ['yes', 'no'], fallback: 'yes', kept: at.kept })`.

- The `--defaults` *flag* answers it. The summary is printed first, so headless runs keep working. The help text (`commands.ts:73-75`) promises that, and `doc/tutorial.md:61,73` relies on it.
- A `no` answer is a refusal with `at.kept`: the recipe is kept, and nothing is registered. Running again offers what was written as the defaults.

`init --project github` registers through the board, not through `askRecipe`, so it is outside this change. Say so in the PR.

Tests go in `recipe-flow.test.ts`:

- defaults at a "terminal" (a fake `ask` that answers `''`, plus an empty detected build) shows the summary lines, then asks the confirm; registration does not happen before both
- explicit `--build none --land main` never asks the confirm
- `--defaults` given as a flag prints the summary and asks nothing
- `ask` returning `null` without `--defaults` refuses with the flag text
