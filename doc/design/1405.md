## Design note: #1405, wait for the count in the two PR-sweep timer tests

**Where:** only `packages/daemon/unit/work-loop-pr.test.ts`, in the two tests at `:50-74` and `:78-96`. The first test (`:23-47`) and `work-loop.ts` stay as they are.

### Decision 1: use `vi.waitFor`, always with explicit options

Write each wait as an assertion inside `vi.waitFor`:

```ts
await vi.waitFor(() => expect(calls).toBeGreaterThan(2), { timeout: 5_000, interval: 5 })
```

Don't write your own polling helper. When the deadline passes, `vi.waitFor` throws the callback's last error. That error is the `expect` failure, so it already reports the count reached (`expected 1 to be greater than 2`), which is what the ticket asks the helper to do.

**Never call it without options.** Vitest's defaults are a 1000 ms timeout and a 50 ms interval. A 1 s wall-clock deadline is the same race as today's 120 ms, just at a bigger number, which is the trap the ticket's *Watch out* row names. The 5 s deadline is well inside the unit project's `testTimeout: 20_000` (`vitest.config.ts:78`). The comment there says that bound is *"a bound on a runaway, not on a round trip"*. So a passed deadline shows up as `waitFor`'s own message, not as a vitest timeout with no count in it.

Add `vi` to the existing `import { describe, expect, it } from 'vitest'` (`:8`).

### Decision 2: `stop()` goes in a `finally`, and the assertions come after it

In both tests, put the wait in `try { … } finally { await Effect.runPromise(port.stop()) }`. Then repeat the assertions after the `finally`, as today: `calls > 2` and `overlapped === false` in test 1, `resumes > 1` in test 2.

The reason is what happens when the deadline passes. Without the `finally`, the test throws before `stop()` and leaves the `Effect.forever(Effect.sleep(every) …)` fiber running. That fiber is forked in the loop's scope (`work-loop.ts:729-743`) on the real clock. It would keep ticking every 10 ms for the rest of the full run, which is exactly the loaded event loop that caused this flake.

Test 2 is about the drain: *"stop() returns while a sweep is hung"*. Its `stop()` must still be reached and must still return while `sweep: () => Effect.never` is outstanding. In the `finally` it is reached on both the passing path and the failing path, so that claim is checked either way.

### What each test still proves

- **The overlap guard is in the code, not the test.** `sweepPrs` returns early while `sweepingPrs` is set (`work-loop.ts:491`, `if (handlers?.sweep === undefined || sweepingPrs || stopped) return`). Waiting longer gives an overlap more chances to happen, not fewer, so `overlapped === false` keeps its meaning.
- **The `sweepMs: 0` hand check.** With `every > 0` false (`work-loop.ts:729`), only the startup `sweepPrs(true)` at `:723-725` runs. Both tests should then fail after 5 s with a count of 1. The `waitFor` message gives the actual count; quote it in the commit body rather than assuming it. Put `sweepMs` back to 10 before committing.
