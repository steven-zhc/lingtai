## Design note for #634: a `cli.json` release asset and a *CLI changed* section

### Where it goes

- **The diff is a new file, `apps/cli/src/cli-diff.ts`.** It should not live in root `scripts/` beside `scripts/cli-doc.ts`. No tsconfig includes root `scripts/`: the root has only `tsconfig.base.json`, and `apps/cli/tsconfig.json` includes `["src", "unit", "integration", "test"]`. So `pnpm typecheck` would never see a file placed there. The unit project's glob is `{apps,packages}/*/unit/**` (`vitest.config.ts:72`), so the test has to live under a package anyway.
  - The file has two pure exports, the same shape as `packages/domain/scripts/events-diff.ts:20,38`:
    - `diffCli(old: Manifest, next: Manifest) → CliChanges`
    - `renderCliChanged({ previousTag, previous: Manifest | null, next }) → string`
  - It also has an `import.meta.main` block that reads `[old] next [tag]`, as in `events-diff.ts:87-96`.
  - **Import `Manifest` with `import type` only.** `cli-doc.ts:1` imports `root` from `./cli.ts`, which is the whole CLI. A value import would load all of it into a CI step that only compares two JSON files. Node strips a type-only import.
  - `entry.ts` never imports this file, so it never reaches the bundle.
- **The test is `apps/cli/unit/cli-diff.test.ts`.** Build small `Manifest` fixtures by hand, and never read the real `doc/cli.json`. That file already has its staleness test in `apps/cli/unit/cli-doc.test.ts:24-26`. A fixture built on the real file would go red whenever a flag is added.
- **The workflow is `.github/workflows/release.yml`, `publish` job only.**

### What the diff reports

Match commands by `name`. The relevant fields are those of `ManifestCommand` (`apps/cli/src/cli-doc.ts:19-30`).

**Commands:**

- **added**: in `next`, not in `old`.
- **removed**: in `old`, not in `next`.
- Do not also list an added or removed command's flags.

**Per command present in both:**

- **flags added and removed**: a set difference on `flags`. The flags are sorted already ("*Every option the parser takes under this command, verbs included, sorted*", `cli-doc.ts:26`).
- **`--json` version bumped**: `json` is non-null on both sides and differs; render it as `old → new`.
  - When `json` goes null → n or n → null, the change is already reported as `--json` added or removed in the flag diff, so do not add a second line for it. `json` is set exactly when `flags` contains `--json` (`cli-doc.ts:95`).
- **effect changed**: `reads` ↔ `changes`. This one is not in *Done when*, but it costs one comparison, and the ticket's *Want* names read-or-change as part of the contract. A script that assumed a command only reads needs to know.

**Ignored:** `group`, `task`, `usage` and `examples`. That prose changes in most releases and breaks no script.

**One `--json` version for every command.** `JSON_VERSION` is a single constant (`apps/cli/src/output.ts:110`, `export const JSON_VERSION = 1`), so a bump bumps every `--json` command at once. The section should list each of them anyway: do not collapse them into one line. A script author looks up the one command they call.

**Order:** `next`'s order for added and changed entries, then `old`'s order for removed ones, as `events-diff.ts:24-34` does.

**Refuse a manifest the diff does not understand.** The reader should check:

- the input is an object with `version === 1`, the only version `Manifest` admits (`cli-doc.ts:32`);
- it has a `commands` array;
- every entry has a string `name` and a `flags` array.

Anything else throws by name, as `readDoc` does in `events-diff.ts:78-85`. If the manifest format ever reaches version 2, the step should go red rather than publish a misleading diff.

### What the notes say

`## CLI changed`, then one of three bodies, mirroring `renderEventsChanged` (`events-diff.ts:47-75`):

- **`previous === null`**: *"First release with a CLI manifest."* If there is a previous tag, append *"(\<tag\> has none)"*.
  - **The next release takes this branch.** `v0.9.0` is the only tag, and `git cat-file -e v0.9.0:doc/cli.json` fails, because the file was introduced by `5a186aa9`, after it.
- **Empty diff**: *"No command, flag or `--json` version changed since \<tag\>."*
- **Otherwise**, one block per non-empty category:
  - commands added
  - commands removed
  - then one line per changed command, for example `` `status`: `--all` added, `--json` 1 → 2, now changes state ``

### The previous manifest comes from git, not from the asset

The events step downloads the previous release's `events.json` asset (`release.yml`, *Events manifest and what changed*). The events manifest needs that, because its links name the tag (`generate`'s `ref`, `packages/domain/scripts/events.ts:451-456`).

`doc/cli.json` carries no stamp of any kind: *"No timestamp, commit or package version goes in either file"* (`cli-doc.ts:13-14`). Its staleness test holds the committed file equal to what the code generates. So `git show "$prev:doc/cli.json"` is exactly the manifest that release shipped, and reading it from git has two advantages:

- it involves no `gh` call that can fail halfway;
- every earlier tag that carries the file gets a real diff, not just releases published after this change.

`fetch-depth: 0` already brings the tags.

- **No previous manifest**: `git cat-file -e "$prev:doc/cli.json"` fails. `prev` is a tag the step just listed, so a failure there can only mean the file is absent. Pass no old path in that case.
- **Any other failure fails the step.** For example, `git show` failing after `cat-file` succeeded must not read as "no previous manifest". That is the same rule #632 applied to `gh release download`.

### The `publish` job

1. **Hoist the previous-release lookup into its own step, `id: prev`.** Move the `published` / `tags` / `for t in $tags` loop out of the events step unchanged, and have it write `tag=$prev` to `$GITHUB_OUTPUT`. The events step and the CLI step both read `steps.prev.outputs.tag`.
   - Both sections must name the same baseline, and the existing *CLI contract diff* step does not. It uses `git describe --tags --abbrev=0 --match 'v*' "<tag>^"`, which finds only an ancestor tag and takes no notice of whether that tag has a published release. That is exactly what `53df46f8` and `ac0985fd` fixed in the events step.
2. **Replace the *CLI contract diff* step; do not add a step beside it.** The ticket's section supersedes a raw `git diff` of `doc/cli.json`, which is mostly `usage` prose. Delete `cli-contract.md`.
   - The new step does three things:
     - regenerate with `node scripts/cli-doc.ts`;
     - `git diff --exit-code -- doc/cli.json doc/cli.md`, which refuses a tag whose committed manifest is stale. Nothing in `release.yml` runs the unit half, so this check is what makes *generated from the command definitions at the tag* true;
     - `cp doc/cli.json artifacts/cli.json`, **before `checksums`**, so that `SHA256SUMS` covers it, for #632's reason.
   - Then fetch the old manifest as described above and run `node apps/cli/src/cli-diff.ts [old] artifacts/cli.json "$prev" > cli-changed.md`.
   - `cli-doc.ts` imports the CLI tree. The CLI test suite already does that with `HOME=/nonexistent`, so no `LINGTAI_*` variable is needed. If the step finds otherwise, set `LINGTAI_DATABASE_URL: postgres://127.0.0.1:1/none`, as the binary job does for `version`.
3. **The notes become `cat cli-changed.md events-changed.md > release-notes.md`**, which is the seam #632's note left for this ticket. Move that line out of the events step into a step of its own after both sections exist.

Keep the shell to these calls. Every decision belongs in `cli-diff.ts`, where a unit test can see it.

### What nothing can check before a tag

`publish` runs only on `refs/tags/v*`. The hoisted `prev` step, the `git cat-file` / `git show` probe and the `--exit-code` refusal all run in CI only. Neither `pnpm test` nor `check.yml` reaches them, and 0060 §1 keeps `git` out of the unit half.

What stands in for them is the unit test of `diffCli` and `renderCliChanged`. It covers:

- command added
- command removed
- flag added
- flag removed
- `--json` going null → 1, which reads as a flag added with no bump line
- `--json` 1 → 2
- effect changed
- nothing changed
- no previous manifest, with and without a previous tag
- a reader that refuses a manifest with `version: 2`

The first tagged release is the integration test. Say so in the commit body, as #632's commit did.

### Edges

- **No previous tag**: the section reads *first release with a CLI manifest*.
- **Previous tag has no published release**: it is passed over by the shared `prev` step, so the CLI and events sections name the same baseline.
- **Stale `doc/cli.json` at the tag**: `publish` fails before anything is uploaded. The binaries are already built by then, but nothing is released, and re-tagging after the fix is the remedy, as it is for the version check (`release.yml:66-71`).
- **Re-run of a failed `publish`**: `gh release create` fails on the existing release, as it does today, so this change makes nothing worse.
- **Pause, drain, two passes at once, or the board**: none of these apply. This is CI only and touches no event.
- **`doc/cli.md` and the site**: unchanged. This change adds no field to `Manifest`, so `cli-doc.test.ts` stays green without a regenerate.

### Out of scope

- A generic multi-manifest abstraction shared with `events-diff.ts`. The two shapes differ, and #632's note already declined one.
- Per-verb flags. `flags` is per top-level command, with verbs folded in (`cli-doc.ts:26`), and the diff reports at that grain.
