## Design note for #798: fixed event histories for the one-fold epic

### The decision the ticket doesn't make: re-stamp `seq` and `at` after building

The ticket's Watch out row says to build each history once, at module scope. That is necessary, but on its own it does not make `seq` fixed. It also asks for an explicit `at` on every event, and most of the builders can't give one. So `histories.ts` builds with the builders and then passes every history through one local function that overwrites `seq` and `at`. Call it `timeline(events, start)`.

- **The global counter does not belong to this module.** `nextSeq` is module-global (`packages/domain/test/support.ts:11`), and so is `unknownEvent`'s use of it (`:42`). Under ES evaluation order, every module a test file imports *before* `@lingtai/domain/test/histories` runs first. If one of those modules calls `makeStream` at module scope, every `seq` in the histories moves. T0b–T0d test files will import these histories next to their own fixtures, and fold state carries `lastSeq: event.seq` (`packages/domain/src/run.ts:305`, `ticket.ts:235`). A `seq` that depends on import order would therefore make every later pin flaky, which is the very thing the ticket warns about. `task-view-rebuild.test.ts:19-21` only guards against test order *inside* one file; it does not cover this.
- **The builders cannot take an `at`.** `aClaim`, `aLanding`, `aRelease`, `aRunFailure`, `aWait`, `aResolution`, `aSplit`, `aRoute`, `aTriaged` and `aRun().aStepEnded` all call the appender without `extra` (`packages/domain/test/events.ts:42-190`). Only `aTriageStart` accepts one (`:99-106`). Each of them would fall back to the one fixed default at `support.ts:31`.

What `timeline` does:

- Keep `streamId`, `version`, `type`, `data`, `actor` and `schemaVer` exactly as `makeStream` set them. `version` is already per stream, and `parsePayload` has already checked the payload.
- Set `seq` from a counter that belongs to `histories.ts`. It starts at a fixed `bigint` base and increases in module order across all histories and scenarios. Append-only then means what the Edges section says.
- Set `at` from a fixed start for each history plus a fixed step for each event, so `at` strictly increases.
- Make the module constant `NOW` later than the last `at` the module produces. The test checks this; it is not left to a comment.

A **scenario** is built as one array in the order things happened: ticket, run and integration events interleaved. That array goes through `timeline` once and is then split into `{ ticket, runs, integration? }` by `streamId`. `seq` and `at` therefore increase across the whole bundle, and each stream keeps its own versions.

### The other module-global counter: wait ids

`aWait` defaults `waitId` to `aWaitId()`, which reads `nextWaitId` (`events.ts:23-27`, `:65`). A wait id is part of the payload, so `timeline` cannot repair it. Every wait in `histories.ts` passes a literal id, such as `'wait-run-fix-1' as WaitId`. Nothing in the module calls `aWaitId()`.

The same applies to every other time-shaped value inside a payload. `ConductorPaused`'s `until` is the main one. Write each as a literal offset from `NOW`. Do not call `new Date()` and do not use the builder default. The lifted pause gets an `until` before `NOW` and the held pause one after it.

### Stream ids come from the helpers

Build ids with `ticketStream(project, issue)`, `chatStream`, `integrationStream(project, base)` (`packages/domain/src/streams.ts:23`, `:91`, `:132`), and the run-id form the existing run tests use. Do not type the strings by hand. That makes "the ids agree" true by construction, and the scenario test only needs to check `RunStarted.ticketId` against the ticket stream's id.

Use one project and base for the whole module (for example `lingtai` and `main`). The integration stream is then `int-lingtai-main`.

### Reading the case labels

Follow `effect-ratchet.test.ts`'s `parse` (`:51-61`): one `ts.createSourceFile` per file, with parse diagnostics checked. Then:

1. Find the `FunctionDeclaration` named `applyRun`, `applyTicket` or `reduceControl`.
2. Walk its body and collect every `CaseClause` whose expression is a string literal.
3. Keep only the labels that are keys of `EVENTS` (`packages/domain/src/events.ts:2093`).

The filter matters. These functions contain nested switches on payload tags, and walking only the named function keeps `stepStateOf`'s action-result labels (`run.ts:197`) out without listing them.

If a named function is not found, or it yields zero catalogue labels, the test fails. Otherwise a rename would turn the check vacuous and leave it green.

### The hash lock

- **Serializing.** Use `JSON.stringify` with a replacer that turns `bigint` into a string. `Date` already serializes through `toJSON` before the replacer sees it. Hash each history's envelope array with `node:crypto`'s `createHash('sha256')`. This is in-process, so it is unit-level under 0060 §1.
- **Names in `histories.hashes.json`** are flat dotted keys: `run.landedFirstTry`, `ticket.claimedAfterClosed`, `scenario.integratedWithoutLanding`, and so on.
- **Failures.** The test fails when a listed name is missing, when a listed hash differs, or when a built name is not listed.
- **The test never writes the file.** On a red it prints the JSON value to paste, as `effect-ratchet.test.ts:10-11` does: *"The test never writes the baseline: a unit test that edits the checkout would undo the ratchet."* The agent creates the file once by pasting that output.

### The twelve cells

Each cell is a named entry. The test holds a literal list of the twelve names.

- Cells 10 and 11 are scenarios.
- Cell 12 has two halves under two names, `ticket.continuedUnclaimedRun` and `chat.orphanAnswer`, and the list has two rows for it.
- Cell 8, a `TicketClaimed` after `TicketClosed`, is written with the ticket stream's appender after `TicketClosed`. It can't go through any helper that checks lifecycle, and `makeStream` checks nothing.

Each cell carries a one-line comment naming its decision (D1–D11 from `doc/design/one-fold-per-stream.md` §5). The doc comment at the top of the module says three things:

- Append only, because `seq` comes from position in the module.
- Never call `aWaitId()` or `new Date()`.
- `NOW` is what every clock-reading fold gets.

### Where this lands

- New files:
  - `packages/domain/test/histories.ts`
  - `packages/domain/unit/histories.test.ts`
  - `packages/domain/unit/histories.hashes.json`
- One new line in `packages/domain/package.json` `exports`: `"./test/histories": "./test/histories.ts"`.
- `support.ts` and `events.ts` are **not** edited. Changing `makeStream`'s counter or defaults would move every existing domain test's `seq`. Re-stamping in `histories.ts` leaves them alone.
- The JSON import uses the same `import … from './x.json'` form `effect-ratchet.test.ts:19` already compiles under `pnpm typecheck`.

`pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` cover all of this. Nothing here needs the integration half.
