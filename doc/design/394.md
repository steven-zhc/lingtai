# #394: design note

## Where it goes

Add a new file, `apps/cli/src/first-project.ts`. It exports one function, `chooseFirstProject(world, flags)`. Both `initCommand` (`init.ts:336`) and `addCommand` (`lingtai.ts:362`) call it. It asks its questions through `question()` (`question.ts:62`) and gets everything else from a `FirstProjectWorld` declared in that file. Follow the rule `question.ts` and `github-app.ts:5-8` already follow: declare the slice of the world you need, don't depend on `InitWorld`. `add` has no `InitWorld`.

```
FirstProjectWorld = QuestionWorld & {
  git(dir, args) → { ok, stdout, stderr }          // never a shell string
  projects() → ProjectState[]                       // loadAllProjects, conductor/projects.ts:62
  files: RecipeFiles; home                          // write.ts:23 — a Map in tests
  signedIn: SignedIn                                // local.ts:64
  register(payload) → string                        // appends ProjectConfigured, returns the line
  github: { app(), waitForApp(...), picker(), add(options, log) }
}
```

In the unit test every seam is a fake: a Map-backed `RecipeFiles` and an array for `register`. That puts the test in `unit/` under 0060 §1, alongside `apps/cli/unit/github-app.test.ts`.

## Flags

`--project github|local` and `--github-app` stay; #393 landed them and `github-app.test.ts` pins them. Add two flags that answer more:

- `--local <dir>` answers the kind question as `local` **and** gives the directory.
- `--github <owner>/<repo>` answers it as `github` **and** gives the repository.

Refuse contradictions by name, the way `askFirstProject` already refuses `--project local --github-app …` (`github-app.ts:41-48`):
- `--local` together with `--github`
- `--local` together with `--project github` or `--github-app create`

`--project local` without `--local`, at a non-TTY, asks the directory question. That question's flag is `--local <dir>`, so the refusal names it.

In `lingtai add`, `lingtai add owner/repo` (positional) still means `--github owner/repo`, so every existing invocation keeps working. Calling `add` with no positional and no flag now asks the question; today it returns 2 (`lingtai.ts:364-367`). For the TTY `ask`, reuse `liveInitWorld`'s `ask` (`init.ts:808`) by moving it somewhere both callers can import; don't write a second readline.

## The local branch, in this order (nothing is written until step 6)

1. **The directory is a repository.** Run `git -C <dir> rev-parse --show-toplevel`. If it fails, refuse: *`<dir>` is not a git repository*. Everything after this uses the top level, not `<dir>`.
2. **It has an `origin`.** Run `git -C <top> remote get-url origin`. If it fails, refuse by name. Give the reason the ticket gives: the merge lane pushes there (`packages/actions/src/merge-action.ts:47`). **Trap:** git stores `origin` verbatim, so a relative path comes back relative (`../foo.git`). The mirror clones from somewhere else, so resolve a path that is not a URL and not scp-style against `<top>` before you write it. `recipe.ts:2843-2847` says the field is deliberately not URL-parsed: "a directory project (#394) writes an absolute path here".
3. **Its name.** The project is `basename(<top>)`; the stream is `prj-{name}` (`onboard.ts:347`) and the recipe is `~/.lingtai/<name>/recipe.yml`. Check the name against `projects()`:
   - **A project with an `owner`** is someone's GitHub project. Refuse and name it. This is the same rule as `pick-repository.ts:122`'s `taken`.
   - **`owner: null` with a different `repo.remote`** (`readRecipeKey`, `write.ts:199`): refuse and name both remotes.
   - **`owner: null` with the same remote** is a re-run. Let it through; `registrationLine` (`onboard.ts:383`) will say *updated*.
4. **The base.** `repo.base` is required by the schema (`recipe.ts:2828`, `base: z.string()`). `setRecipe` creates a new file from `version:` alone (`write.ts:81`), and a file with no base is refused (`write.test.ts:123`). So this branch has to answer the base too, or it can never create a recipe. Ask it with `question()`, flag `--base`. The default comes from, in order:
   - `current`: the file's own `repo.base`
   - `detected`: `git symbolic-ref --short refs/remotes/origin/HEAD` with `origin/` stripped, else the current branch

   Validate with `git rev-parse --verify <base>^{commit}` in `<top>`. Its output is `fromSha`. Use the local ref and don't fetch: `add` asks GitHub (`onboard.ts:315`), and this branch has nothing to ask.
5. **An agent will resolve.** `resolveLocalRecipe` resolves `runtime.agent` from `signedIn` when the file names none (`local.ts:172`). Check that before writing, so a machine with nothing signed in is refused in step 5 rather than after step 6. `init` has already checked this (`checkAgent`, `init.ts:291`); `add` has not.
6. **Write, then append.**
   - One `setRecipe(name, [repo.base, repo.remote], { home, files })` call. It validates before replacing (`write.ts:182`).
   - Then `resolveLocalRecipe(name, …)` for `configHash`.
   - Then `register({ project: name, owner: null, base, configHash, fromSha })`.

   The live `register` is a new `addLocal` beside `add` in `packages/conductor/src/onboard.ts`. It reuses the same stream-version append (`onboard.ts:346-363`) and `registrationLine`, so the two ways of registering a project cannot disagree about the stream.

**No schema change.** `ProjectConfigured.owner` is already nullable (`events.ts:1973`) and the fold keeps a null (`project.ts:88`). Don't add a directory path to the event or the recipe. The schema has no such key, and adding one is a code-restart-paste change (`recipe.ts:2850-2853`) that this ticket does not need. The mirror reads `repo.remote`; the directory is never read again.

## The GitHub branch

1. **No App configured:** run #393's step unchanged, `askFirstProject`'s App question and then `waitForApp` (`github-app.ts:24`, `:99`). `waitForApp` needs a board URL.
   - `init` has one (`init.ts:350`).
   - `add` uses a board answering at `boardPort()` if there is one. If there isn't, it refuses and names `lingtai init --project github`. It does not start a board of its own.
2. **A slug was given:** check it with `choose(await listRepositories(...), slug)` (`pick-repository.ts:200`). A repository the App can't see is refused with `why` and `fix.href`, the install link. That is today's install path.
3. **The slug passes:** hand it to today's `add({ slug, base })` (`onboard.ts:265`), unchanged.
4. **`init` with no slug:** keep today's handoff to `${board}/setup/repository` (`init.ts:350-356`). The board's wizard is what writes a GitHub project's recipe, and this ticket does not move that.

## Remembering the answer, and undoing it

Record the answer in the log, not in `config.yml`. A registered project **is** the record:

- **No project registered:** `init` asks.
- **Projects registered** (`world.projects()` non-empty): `init` asks nothing and prints each one, *`<name>` — local, `<remote>`* or *`owner/name` — github*. Then it prints one line saying how to change it: **`lingtai add` asks GitHub-or-directory for another project; `lingtai init --project github` sets up the GitHub App on a machine that has only local projects.**

Only an explicit `--project github` or `--github` reopens the App step on such a machine. That is the undo: nothing machine-wide holds `local`, so nothing needs removing. That is the difference from #393's backed-out `project: local`, which nothing read back. The comment at `init.ts:333-335` and the local line at `init.ts:345-349` ("not built yet (#394)") are both replaced.

`init` calls `projects()` only after `chooseStore` has written the store. The event-store client is built at module scope (`entry.ts:5-10`), so the live seam must `import()` `@lingtai/conductor/projects` lazily at call time, never at the top of `init.ts`.

## Out of scope

`run.ts:243` (not `:184`) still refuses a project with no owner: *"has no owner recorded — re-run lingtai add"*. That is #352. Its advice now points at a command that will register the same ownerless project again, so leave its wording to #352; don't fix it here.

## What can be checked inside the pass

- **The unit test on `chooseFirstProject` is the claim.** It covers: `--local` with an origin (one `register` call, `owner: null`, and both `repo.remote` and `repo.base` in the written text); a non-repository, no `origin`, and a name taken by an owner (each refused by name, with `files.replaced` and `register` both empty); a relative `origin` written absolute; `--github` reaching `waitForApp`, then `choose`, then `add`; and contradicting flags refused.
- **`initCommand`'s wiring cannot be checked in the pass.** Its tests are `integration/init.test.ts` (`github-app.test.ts:4`), which is out of reach. Keep the wiring in `init.ts` to a call and a print, so the unit test covers the behaviour.
- **`github-app.test.ts` must stay green unchanged.** `askFirstProject`'s signature does not change.
