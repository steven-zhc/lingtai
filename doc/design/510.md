# #510: design note

## Half 1 is mostly built already, so keep it small

Commit `dce93abc` and the #508 work already landed most of the "failed read" fix:

- `apps/board/src/app/page.tsx:379-391`: when `card.waiting && card.waitId === null`, the card renders the refusal *"the wait on this card could not be read — reload and read it again"* and no `Decide`/`Requeue`.
- `decide.tsx:84` and `decide.tsx:285`: `Decide` and `Requeue` take `waitId: WaitId`, not `| null`, so the type checker already stops a null being passed to them.
- `packages/conductor/src/close.ts:166-179`: on a blocked item, the server refuses `waitId === null` by name (*"this card showed no wait and … nothing was closed"*).

What is still wrong is that branch keeps offering `<Close … waitId={null} />` (`page.tsx:389`, and the same at `standing.tsx:419`). `laneWaitIds` (`board.ts:896-928`) returns null for two reasons: the read failed five times, or the fold had already moved off `blocked`. In the first case the item is still blocked, so `close.ts:171` refuses every click. That is a control bound to refuse, which the comment above it forbids: *"a button bound to resolve 'whatever is open now' is the `#84` complaint this file already states as a rule"*.

**Decision: drop `Close` from both null branches and leave the refusal sentence on its own.** Do not try to tell the two null causes apart. In both, the card is out of date with the log, and "reload" is the right instruction either way. Leave `Close`'s own `waitId: WaitId | null` alone, because the queued card at `page.tsx:427` sends null on purpose (`decide.tsx:432-434`).

Update the comments at `page.tsx:380-385` and `standing.tsx:411-416`. Both currently say "Close still works"; after this change it does not appear.

**Test:** in `apps/board/unit/waiting-card.test.tsx` (or `standing.test.tsx` for the task page), render a waiting card with `waitId: null`. Assert the refusal text is present and that none of the Decide/Requeue/Close controls appear. Read how the file already renders a card and reuse that helper; I did not check its shape.

Out of scope: the `options.waitId ?? item.lifecycle.waitId` fallbacks at `approve.ts:394` and `close.ts:183`.

## Half 2: add a real `approved` state, don't filter in `inFlight()`

**Decision: add `approved` to `LABEL_STATES` and fold `WaitResolved{Approve}` to it.** The filter option doesn't work, because the `task_view` row has nothing an `inFlight()` filter could use:

- `run_id` still names the previous pass, so `runId !== null` doesn't separate the two.
- `note` is prose.
- `TicketClaimed` (`task-view.ts:262-286`) has no field of its own that marks a live claim.

The continuation's claim is itself a `TicketClaimed` (`packages/conductor/src/claim.ts:179`, appended by `continueWorkItem`). It folds back to `running` at `task-view.ts:281`. So `approved` lasts exactly from the approval to the next claim, which is the window the finding describes.

There is a precedent: `verifying` was added the same way. Its comment (`task-view.ts:452-455`) says: *"It is a stored value, so `lingtai projection rebuild task_view` is what an existing table needs… `LABEL_STATES`, `labelsFor`, `stateInk` and the board's `COLUMN_OF` move with it."* This change follows the same path. It contradicts no ADR.

### `inFlight()`

`control.ts:378` needs no logic change: once approvals stop folding to `running`, `running || verifying` is correct. Two edits:

1. **Rewrite the comment at `control.ts:367`.** Make it say that a claim folds as `running` and an approval as `approved`, so this list only names passes a conductor holds.
2. **Pull the predicate out so it can be unit-tested.** As written, `inFlight()` goes through `readTasks`, which needs a database, so a unit test can't reach it. Extract a pure function, e.g. `export function held(tasks: readonly TaskCard[]): string[]`. `inFlight` becomes `held(await readTasks(…))`. The unit test passes a `running` card and an `approved` card and asserts only the first comes back. That is the "Done when" box.

The other test that matters is the fold itself. `packages/projector/unit/task-view-rebuild.test.ts` already replays `WaitResolved{Approve}` (`:238`, and `aSignoffApproved` at `:441-467`). Its expected rows around `:508-577` currently say `state: 'running'` for the approved ones. Update each approved row to `'approved'`, but leave alone any row whose last event is a later `TicketClaimed`. Work out which is which from the events pushed above each one, not from the comment.

## After it lands

The stored value changed, so run `lingtai projection rebuild task_view` on the conducting machine, and restart the daemon (`pnpm lingtai restart …`) so the running daemon and board load the new `LABEL_STATES`. Until the rebuild, existing approved rows keep reading `running`. One way to confirm it worked: a ticket with `WaitResolved` (`resolution._tag: 'Approve'`) as its last fact in `events`, and no later `TicketClaimed`, should read `approved` in `task_view`.
