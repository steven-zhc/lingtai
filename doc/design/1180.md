# #1180 — the shape

## The command lives in `@lingtai/project`, not in the conductor

0129 says one module owns every append to its aggregate's stream. #1174 made that true for `prj-`: `packages/project/src/commands.ts:2` says *"every append to `prj-{project}` (0128 §7, #1174)"*. So `observeSandbox` is a fifth command in that file, built the same way as `recordTurn` (`commands.ts:87-93`):

```ts
export const observeSandbox = (project: string, seen: PayloadOf<'ProjectSandboxObserved'>, store: EventStore) =>
  transitionProject(store, project, (state) => sandboxObservation(state, seen), () => undefined)
```

- `transitionProject` (`commands.ts:46-60`) reads, decides, appends at the version it read, and retries a lost race once. That one retry is the ticket's *the other re-reads and appends nothing* edge.
- `sandboxObservation` is already written (`packages/domain/src/project.ts:260-270`) and tested (`packages/domain/unit/project.test.ts:288-294`).
- The conductor already depends on `@lingtai/project` (`packages/conductor/package.json:59`).
- Do not write a second append path in `conduct.ts`.

`observeSandbox` returns `Effect<void, Error>`. Never wrapping it is the caller's job, not the command's: the board imports this module too (`commands.ts:5`).

## The boundary hook: the `before` port, after its own append

`invocationAppends` (`conduct.ts:865-871`) builds the one port every boundary goes through. That covers agents through `sandboxOf` (`:906`), unwrapped `run:` commands (`:4108`) and wrapped ones (`makeRunSandbox`'s `appends`, `:3755`).

Change only `before`:

1. Run `appendInvocation(stream, events, true)` exactly as it does now.
2. **Only if that append succeeded**, look through `events` for each `SandboxBoundaryRecorded`, map its `data.boundary` to a kind, and call `observeSandbox(project, { kind, runId: stream }, store)`.

The mapping:

| `boundary` | kind |
|---|---|
| `sandboxed` | `sandboxed` |
| `unsandboxed` / `degraded` | `degraded` |
| `unsandboxed` / `off by choice` | `off by choice` |
| `refused` | nothing |

`boundaryOfDecision` (`sandbox-record.ts:46-51`) produces these shapes. Put the mapping beside it as one exported pure function, say `observedKindOf(boundary)`, so a unit test can walk every case. The base check uses the same function, through the boundary `boundaryOfDecision` gives.

Three decisions:

- **`runId` is `stream`, the attempt's, not `keys.runId`.** In `sandboxOf`, `keys.runId` is *"the dispatch's own"* (`conduct.ts:899`), and `InvocationKeys.runId` is `string | null` (`sandbox-record.ts:22`). The payload's comment says *"`runId` is the attempt whose run met it"* (`events.ts:2281`), and it is `z.string()` (`:2288`). `invocationAppends` is always handed the pass's `runId` as its stream (`:3755`, `:4108`, and `record.stream` at `:906`).
- **Nothing the observation does can fail or kill `before`.** Wrap the call in `Effect.catchCause` and write one line through `log` and, once the run log exists, through `runLog.note` (declared later, so handed back by a forward reference), because the run log is what an operator reads on the task page. Do not use `remember`: `appendInvocation`'s `remember` makes a refused append the pass's defect (`:841-842`), and that is exactly what this must not become. `sandbox-record.ts:29-31` says a refused `before` *"is a defect that stops the child from starting"*. That rule is about the boundary, never the observation.
- **The observation runs before the child starts.** In `recordingWrap` (`sandbox-record.ts:100-110`) and in `recordUnwrapped`, `before` runs before the child does. So the observation costs one `prj-` read, and on a transition one append, before every invocation starts. That is the cost the ticket accepts. Do not move it into a finalizer: an observation tied to the child exiting is lost whenever the child is killed.

## The base check: observed in `baseIsRed`, from the pass's decision

After `baseCheckFor(...).ask(...)` returns (`conduct.ts:3777`), observe only when `answer.verdict !== 'unknown' && answer.from === 'ran'`. `unknown` carries no `from` (`base-check.ts:95-98`).

Take the kind from what the pass decided:

- `runSandbox !== undefined` → `sandboxed`.
- Otherwise, `sandboxDecision` is `unsandboxed` → that decision run through `boundaryOfDecision`, then the same mapping.

Reaching this code with any other decision is impossible: `refused` returns at `:1011`, and `sandboxed` with no service returns at `:1020`. Still, write the helper as total and let *other* answer nothing, rather than casting.

`runId` is the pass's own `runId`, the same value the question carries (`:3786`). The question also carries `observedAs`, the kind, which joins the in-flight key when unsandboxed: two passes whose unsandboxed reasons differ run their own check rather than share one answer.

Do not read `BaseChecked.boundary`. The ticket's Watch out already says why: it is a cache key.

`from: 'ran'` is sound as a test of *a command actually ran under this boundary*. A failed sandboxed wrap answers with exit code `null` (`base-check.ts:220-227`), which becomes `unknown` (`:267-268`). A refused operator profile also becomes `unknown` (`:180-184`). So `ran` only ever follows a real exit code.

Use the same `catchCause` → `log` + run-log guard as the boundary hook. A failed observation must not change what `baseIsRed` answers.

## Tests (all unit)

- **`packages/project/unit/`, against `createMemoryEventStore()`:**
  - first observation appends;
  - the same kind appends nothing;
  - a new kind appends;
  - a store whose `read` rejects fails with an `Error` and appends nothing.
- **The mapping function:** every boundary shape, including `refused` → nothing.
- **The conductor:** use the fixtures in `packages/conductor/test/one-attempt.ts`, which already build a `ProjectState` with `sandboxObserved: null` (`:460`). Add a store wrapper that rejects `append` on `prj-` streams and passes everything else through. With it, the invocation still starts, and its `SandboxBoundaryRecorded` is still on the pass stream.
- **The base check:** `from: 'ran'` unsandboxed by choice appends `off by choice`; `from: 'log'` and `unknown` append nothing.

What none of these can show is the order of two daemons appending against real Postgres. That is integration work and out of scope here. The unit claim that stands in for it: `transitionProject`'s retry, given a `ConcurrencyError` on the first append, re-reads and appends nothing when the kind is now the same.
