## Design: #1259 — a wait the system resolved reads as one line

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

### Where it goes

| Piece | File |
|---|---|
| `systemLine`, plus the words for each cause and action | `packages/domain/src/wait-words.ts`, beside `judgeCauseWords` (`:455`) |
| `systemBoundOf(state, wait, limits)` and `standingSystemResolution(state)` | `packages/domain/src/read-model.ts`, beside `triageSpentOf` (`:391`) |
| The record row | `apps/board/src/lib/history.ts:716-719`, using a new optional `LineContext` member |
| The card | `toCard` (`apps/board/src/lib/board.ts:823`), a read next to `laneProgress` (`:1515`), and the non-waiting branch of `<Card>` (`apps/board/src/app/page.tsx:266` on) |
| `lingtai status` | `StatusRow`, `rowOf` and `renderStatus` in `apps/cli/src/status.ts` |

Everything here is pure or reads the log, so every check is a unit test. The integration half covers none of it.

### 1. The inputs are already reduced; use them, and add nothing to the snapshot

`TicketWait` (`packages/domain/src/ticket.ts:60-84`) already has everything except the note:

- `resolution: { resolution, by, spent? }` — `spent` is #1258's: *"What a system resolution spent, and the number its continuation records for it"* (`ticket.ts:69`).
- `triage.result` — the `WaitTriaged` for the latest attempt.
- `at`.

The `WaitTriaged` that `actOnTriageTransition` writes goes into the same append as its `WaitResolved{by:'triage'}`: `return { ok: true, events: [triaged, ...resolved.events], … }` (`ticket.ts:1418`). So `wait.triage.result` is the answer that was acted on.

**Do not add `note` to the reduced wait.** That changes the snapshot shape and forces a `ticket-codec.ts` bump (currently `version: 10`, `ticket-codec.ts:189`). It also adds nothing: the note of a triage resolution is `input.result.summary` (`ticket.ts:1414`), which is exactly what the ticket wants one click away rather than on the line. Only the record row has the payload, so only the record row shows the note in the missing-`WaitTriaged` case:

- record row: *resolved by triage: \<note\>*
- card and status: *resolved by triage*

**Signature.** Keep the ticket's three arguments:

```
systemLine(resolved: TicketWait['resolution'] (non-null, by === 'triage'),
           triage: TriageResult | null,
           counter: { used: number; allowed: number } | null)
  → { action: string; because: string | null; bound: string }
```

- `because` is `null` when `triage` is null or is not a `TriageAnswered`.
- `bound` is `'bound unknown'` whenever `counter` is null. It is never `0 of N`.

The history row builds `resolved` from the event payload, which has the same three fields (`events.ts:385-401`).

### 2. Which counter, and from where

**`used` is on the log; take it from there.**

- **`FixRefusal` / `RedoStep`:** `used` is `resolved.spent.n`. That is `context.counters[bound].used + 1`, the spend at that moment (`ticket.ts:1415`).
- **`StartNewAttempt`:** it has no `spent` (`bound` stays `null`, `ticket.ts:1393-1395`). Its spend is the release written in the same append: `{ by: 'triage', runId, newAttempt: state.newAttempts.length + 1 }` (`ticket.ts:1176`). The reducer records that as `{ after: d.runId, newAttempt }` (`ticket.ts:606-608`). So `used` = `state.newAttempts.find(r => r.after === <the wait's runId>)?.newAttempt`.

Do not read the attempt counter, and do not read `max(…)` from `triageSpentOf`. Those are the spend *now*, and the line is about the moment of the resolution.

**`allowed` is not on the log.** No event records the limits, so it comes from the source the card already uses for its ceilings:

- `stepRedos` → `BOUNDS.stepRedos` (`packages/domain/src/failure/respond.ts:581`).
- `refusalFixes`, `conflictResolutions`, `newAttempts` → the recipe as resolved at render.
  - On the board: `queued.limits` (`AttemptLimitsView`, `board.ts:356-375`, already carrying `conflictResolutions`).
  - On the task page: `planAndLimits` (`apps/board/src/lib/task.ts:1699-1706`). Widen its `Pick` to include `conflictResolutions`.
  - In status: `filter.limits` (`packages/conductor/src/filter.ts:155-158`).
  - That is the same source `describeHeld` and `describeArm` take their *of N* from (`board.ts:907-913`), so the line and the chips agree.
- An unread recipe gives a `null` limits. Then the line says **bound unknown**.
- If the recipe was lowered after the resolution, the line can read *3 of 2*. Do not clamp it: it is true of both numbers it is made from.

`systemBoundOf(state, wait, limits)` in `read-model.ts` is the one place this is joined. The board, the task page and status all call it, so the three cannot disagree.

### 3. Action and cause words

**Action:** read the action from `spent.bound` first, and from the cause only as a fallback.

`fixRefusal` and `resolveConflict` both resolve as `FixRefusal` (`ticket.ts:1403-1407`). What tells them apart on the log is `spent.bound`: `'refusalFixes'` or `'conflictResolutions'`. If a `FixRefusal` has no `spent`, use the cause: `ConflictingHunks` reads as the conflict, anything else as the lines.

Make the switch over `resolution._tag` exhaustive with no `default`.

- **`AnswerQuestions`, `Approve`, `Close`, …** Triage never writes these (`ticket.ts:1390-1408`). If one does appear `by: 'triage'`, it reads *resolved by triage*, the same fallback as a missing cause. It never gets made-up wording.

**Cause:** write new words for each cause in the past tense. Do not reuse the board's `presentCause` labels (`apps/board/src/lib/triage-cause.ts:10-18`). Those are instructions to a person (*Merge by hand*, *Fix the setup*), and *Merge by hand* would be false on a conflict the system resolved. Make the words a `Record<Cause['_tag'], string>` so a new cause fails to compile. The ticket's sentence is the template: *Triage read **\<cause\>**; \<action\> — \<n\> of \<N\> \<bound noun\> used*.

### 4. The card: one pure rule for when the line is current

Add `standingSystemResolution(state: TicketState): TicketWait | null` in `read-model.ts`. The card and status both use it.

**Rule:** take the **last** wait in `state.waits`. It counts when all three hold:

- its `resolution?.by === 'triage'`;
- no claim in `state.claims` has `at > wait.at` with a `runId` other than the wait's run;
- `state.lifecycle.status` is not `landed`, `closed` or `satisfied`.

How the rule covers the three stop points:

- **A later `WaitStarted`** makes some other wait the last one. That covers the first stop.
- **A new attempt's claim:** comparing `runId`s, not just "any claim after", is what keeps the line through the continuation. Claims carry `at` (`ticket.ts:540`). A continuation of the same run is not a new attempt (`claimShapeOf`, `task.ts:1531-1536`).
- **A wait with no `run` in its reason:** any later claim ends the line.

**The read.** `task_view` has no column for this, and *any new projection column* is out of scope. So the board reads the ticket stream:

- Use `readState(eventStore, ticketReducer, taskId, 'all', read)` with the same `read = { snapshots, writer }` `laneProgress` builds (`board.ts:1537`). `actions.ts:929` already reads ticket state this way.
- Run it in parallel with `laneProgress`.
- Only read rows whose state is `queued` with `attempts > 0`, or `running`, `verifying` or `approved`. Those are the only states the line can show in. `approved` is drawn in Running (`board.ts:668-670`), and a triage `StartNewAttempt` lands in Queued.
- Waiting and Landed cards can never carry the line, so skip them without reading.

**A failed ticket read means no line,** caught like `laneProgress`'s (`board.ts:1550-1552`). A card cannot report a resolution it never read. The task page's record is where the line always is.

**Rendering:**

- `BoardCard` gains `system: { action, because, bound } | null`.
- `toCard` takes it as one more trailing parameter, defaulting to `null`. Leave the queued-card stub alone.
- `<Card>` draws it on the non-waiting branch, directly under the title `Link`.
- The summary is one click away: the title already links to `/task/…`, where the `WaitTriaged` row right before the resolution says *read the cause: \<label\>: \<summary\>* (`history.ts:727-728`). The card does not repeat the summary.

### 5. The record row

- Add an optional `systemLine?: (waitId: string) => { action; because; bound } | undefined` to `LineContext` (`history.ts:111-123`). Document it like `endedAt`: *a caller with only the one event has none*.
- Set it where the task page has both `ticketState` and `limits` (`task.ts:1929`), and pass it through `toLine` at `task.ts:1541`.
- In `FORMAT.WaitResolved`:
  - `f.by === 'triage'` → the joined sentence. If there is no `because`, write *resolved by triage* and append the note.
  - With no `systemLine` in context, build it from the payload with `counter: null`. The bound then reads *bound unknown*. It is never dropped silently.
  - Every other `by` keeps today's `` `${f.by}: ${note}` ``.
- Leave the `WaitTriaged` row alone.

### 6. `lingtai status`

- Add `system: string | null` to `StatusRow`, so it also appears in `--json`.
- Fill it in `rowOf` (`status.ts:516`) by reading the ticket through `readThroughSnapshot` with `ticketReducer`, using the same candidate filter as the card. `readThroughSnapshot` is already imported at `:58`.
- Use `filter.limits` from `:506`. When the recipe did not resolve, the limits are null and the line says *bound unknown*.

**Where it prints:** running and approved rows are not listed without `--all` (`status.ts:784-797`). So print the line in its own section after the queue, shaped like *Waiting on you* (`status.ts:814-833`):

- `#ref  title`
- the line, indented
- under `--all`, the summary on a further indented line

Call the section something like *Decided for you*. Never colour it amber: amber is reserved for a person being waited on (0121 §2, quoted at `status.ts:712`).

### Edges this note decides beyond the ticket

- **The ticket stream read fails** on the board or in status → no line there. The task page's record still has it.
- **The recipe is unread** → *bound unknown*. `used` is still known, but the line does not give it without the *of N*. Half a fraction reads like a full one.
- **`spent` absent on a triage `FixRefusal`/`RedoStep`** (a log written in the window before #1258's field) → *bound unknown*.
- **A cost to later tickets:**
  - The cause-words `Record` makes a new `Cause` a compile error here, on purpose.
  - Tests pin the shape of `bound`, never a counter a recipe default could move. Build the limits in each test.
