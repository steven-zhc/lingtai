# Design note: #275, one database URL for the suite

## Where the default goes: `storeChoice`, not `testUrl`

The ticket's **Fix** row says "`testUrl`'s refusal becomes a SQLite default". That can't be done literally. `testUrl` returns a connection string (`packages/env/src/index.ts:175`), and only `postgresUrl()` (`:839`) and `directPostgresUrl()` (`:871`) reach it. Both are called by code that is about to open a `pg` connection, so a SQLite path is no answer for them. Two of their refusals are also asserted, and they must stay true:

- `packages/conductor/integration/status-on-a-file.test.ts:104`, the "guard on the guard": *"if this ever stops throwing, every assertion below proves only that the machine running them has a database."*
- `packages/env/integration/env.test.ts:190`, which expects `postgresUrl({ LINGTAI_HOME: home, VITEST: "true" })` to throw.

So `testUrl` keeps throwing, and only its message changes. It should stop telling the reader to go and set up a second database (`:183-185`). It should say that this caller needs Postgres, that the suite runs without it, and that only the files on the Postgres list below use it.

The default goes in **`storeChoice`** (`:524`). That is the one place a store is chosen: `chosenStore()` (`:640`) wraps it, and the three factories open whatever it answers (`packages/event-store/src/choose.ts:67`, `packages/projector/src/choose.ts:50`, `packages/daemon/src/choose.ts:51`). Today a test with no URL falls through, because `machineChoiceFile` returns `null` under test (`:408`), and gets `notSetUp` (`:479`). The change goes straight after the URL branch (`:537-545`):

- **When `inTest(from)`, no test URL is set, and `LINGTAI_TEST_SQLITE_PATH` is set:** answer `{ store: "sqlite", path: <that>, where: "environment", from: "LINGTAI_TEST_SQLITE_PATH, …" }`.
- **Neither set:** refuse as it does now, and name both variables in the refusal.

**The trap: never default to `join(stateDir(), SQLITE_LOG)`.** `SQLITE_LOG` is `lingtai.db` (`:352`), and `stateDir()` is `~/.lingtai` (`:961`). On a developer machine that ran `lingtai init` and chose SQLite, that file *is the operator's log*. Defaulting to it would bring back exactly the failure `testUrl`'s comment describes: "twenty-four cards from ten throwaway `esctest*` projects". A path under `tmpdir()` with a fixed name is wrong as well, because two worktrees running the suite at once would share it. The path has to be specific to one run, and set by the run.

### Who sets the path

`packages/event-store/test-support/teardown.ts` is already the integration project's `globalSetup` (`vitest.config.ts`, the `globalSetup` line), and its `setup()` is empty (`teardown.ts:78`). Changes:

- **`setup()`:** `mkdtemp` a directory and set `process.env.LINGTAI_TEST_SQLITE_PATH` to `<dir>/lingtai.db`. Only when no test URL is set.
- **Workers and children:** vitest 4's default pool is `forks`, and the workers are forked after `globalSetup` runs, so they inherit the variable. Any CLI child a test spawns inherits it from its worker.
- **`teardown()`:** remove the directory. With SQLite this replaces the whole residue sweep, and the "real streams" guard has nothing to guard. The existing Postgres branch (`:83` onward) stays as it is for a run that does have a URL.

Two consequences:

- **The unit project has no `globalSetup`,** so a unit test that reaches a real store still gets a refusal by name. That is wanted: unit tests use `createMemoryEventStore()`.
- **The new variable begins `LINGTAI_`,** so `packages/env/unit/prefix.test.ts` accepts it.

The claim that workers inherit the variable is an assumption, and only an integration run shows it. If it turns out wrong, the fallback is vitest's `provide`/`inject` plus setting the variable in a `setupFiles` entry. That still reaches spawned children, because they inherit from the worker.

## Which integration files stay on Postgres

Of the 74 files, 38 reach Postgres by name (`from "pg"`, `createDb(`, `createPostgres*`, or a no-argument `directPostgresUrl()`). They fall into two groups.

### Group A: these assert Postgres itself

These stay on Postgres behind an explicit skip:

| File | What it asserts that only Postgres has |
|---|---|
| `packages/event-store/integration/event-store.test.ts` | two clients `a`/`b` racing an append (`:48-49`) |
| `packages/conductor/integration/claim.test.ts` | two clients racing a claim (`:48-49`) |
| `packages/event-store/integration/subscribe.test.ts` | `createPostgresWaker`, i.e. `LISTEN`/`NOTIFY` (`:60`, `:74`, `:104`, `:123`) |
| `packages/event-store/integration/queries.test.ts` | the Postgres side of the queries contract (`:38`) |
| `packages/projector/integration/projection.test.ts` | the Postgres projection store and `projectionShape` (`:179`, `:396`) |
| `packages/daemon/integration/daemon-store.test.ts` | `createPostgresDaemonStore` (`:43`) |
| `packages/daemon/integration/beacon.test.ts` | the Postgres beacon (`:39`) |
| `packages/daemon/integration/the-written-choice.test.ts` | that a Postgres process never loads the SQLite module, and the waker's session URL (`:272`) |
| `apps/cli/integration/doctor.test.ts` | **Partly.** Only the rows about session mode and the pooler (`:838`, `:924`, `:936`). Skip those `describe` blocks, not the file. |

`packages/projector/integration/task-view.test.ts` goes in Group A only if its raw SQL (`:119`, `:522`) is more than cleanup. Otherwise it belongs in Group B.

### Group B: these use Postgres only as a convenient store

These convert to the store the run chose:

- apps/cli: `ask`, `conduct`, `projector`, `requeue`, `status-preview`, `subscribers`, `telegram`
- packages/conductor: `discuss`, `projects`, `queue`, `tell`, `wizard`
- packages/daemon: `converge`, `reconcile`, `work-loop`
- packages/projector: `backlog`
- packages/repo: `integrate`

The shape is `createDb()` plus a `pg.Client` on `directPostgresUrl()` in `afterAll`, which deletes that file's `esctest*` rows. Convert them to `processLog()` (`packages/event-store/src/choose.ts:57`) and drop the cleanup, since the file is removed at teardown.

`processLog()` already carries a Postgres URL when one is set, so these files keep running on Postgres for anyone who has one. **If a file in this group turns out to use SQL in an assertion** (`queue.test.ts:315`, `:329` are the first to check), move it to Group A and give its reason. Don't bend it to fit SQLite: a file that stays green while asserting nothing is 0016 §4's shape.

**`packages/daemon/integration/lock.test.ts:55`** (`expect(directPostgresUrl()).toBeTruthy()`) throws without a URL and asserts a rule that is gone: every lock has been a file since 0052 (`packages/env/src/index.ts:945`, *"No lock does: every lock is a file"*). Delete the line and its comment.

**The pure files are not on either list:** `packages/env/integration/env.test.ts`, `store.test.ts` and `two-questions.test.ts`, and `apps/cli/integration/doctor-environment.test.ts`. They hand in explicit `from` objects and open nothing, so they stay as they are, apart from the assertions noted under the last heading below.

## Write the list as data, and have a unit test enforce it

A list kept in prose drifts, which is the thing 0055 §1 warns about: *"a set maintained by memory rather than by a type"*. So:

- **`packages/event-store/test/postgres.ts`** exports `onPostgres(file, reason)` (or an exported `ON_POSTGRES` table of path → reason) and a `postgresUnderTest()` that reads `dbVar("DATABASE_URL")` **without throwing**. Group A files wrap themselves in `describe.skipIf(!postgresUnderTest())`. That makes the skip visible in vitest's count rather than a green file that asserted nothing.
- **A new unit test** (e.g. `packages/event-store/unit/on-postgres.test.ts`) reads every `{apps,packages}/*/integration/**/*.test.ts`. Reading source files already has precedent in the unit half: `packages/env/unit/prefix.test.ts` and `one-choice.test.ts` do it. It fails in either of two cases:
  - a file imports `pg`, calls `createDb(`, calls `createPostgres*`, or calls a no-argument `(direct)postgresUrl()` and is not in the table;
  - a file in the table no longer does any of those.

**This test is the unit-level claim that stands in for `pnpm test:integration`.** That run is 803s against a 600s ceiling, so no pass can check "passes with no URL". What `pnpm test` can check is that no file reaches Postgres without being on the skip list. The integration result itself is only known after the merge, per 0060 / T11. Say this in the PR.

## This needs a superseding ADR: 0074

Three accepted decisions say the opposite, in the same words:

- **0046** (`doc/decisions/0046-lingtai-is-personal.md:231-234`): *"That rule must not reach the test variables … a fallback there would let a suite that exists to assert Postgres pass against SQLite."*
- **0055 §2** (`:81-83`): *"`LINGTAI_TEST_DATABASE_URL` is untouched and remains the exception."*
- **0056 §4** (`:126-128`): the same sentence.

A SQLite default for the test side is that fallback, so the answer is a new file, `0074-the-test-side-defaults-to-a-file-of-its-own.md` (or similar), and none of those three is edited.

The argument: the reason those ADRs give is **kept**, and only the mechanism changes. A suite that exists to assert Postgres still never passes against SQLite, because the Group A files skip rather than run, and the unit test above holds that set. What goes is the refusal as the thing that kept the reason.

The ADR should also say plainly that **on this machine the skip means "not asserted"**. Nobody sets the variable any more, so Group A runs nowhere until somebody points it at a Postgres. Name those files there, the way the recipe's `build` comment names the 28 files that `test:db`'s suspension stopped checking. That is the "written down" the ticket asks for.

Write it out rather than leaving the key absent: a missing key and a deliberate empty list read the same, and this repository writes its policy out (see the `backoff`/`env: []` comments in `.lingtai/config.yaml`).
- **`.lingtai/config.yaml:70-91`, the in-repo copy.** Nothing reads it, but its comment says the suite refuses without the variable. Bring it in line.
- **`lingtai doctor`.** It asks only for what `recipe.env.required` lists (`apps/cli/src/doctor.ts:1887`), and nothing in `doctor.ts` names the variable. So this "Done when" item is met by the recipe edit, and no code change is needed. Say so in the PR rather than inventing one.
