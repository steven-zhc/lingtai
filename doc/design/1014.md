## Design note: #1014: one bad recipe stays inside its project

The ticket already sets out most of the shape. This note covers two things it leaves open: **how `toCard` tells the two unknowns apart**, and **how `Problems` tells a recipe problem from a GitHub one**. Neither can be seen from the data as it is today.

### 1. `declaredTriage`: a change in place, still one `async` function

`board.ts:595-598` becomes:

```ts
export async function declaredTriage(
  projects: ProjectState[],
  recipeFor: (p: ProjectState) => Promise<ResolvedRecipe> = (p) => currentRecipe(p),
): Promise<Map<string, boolean | null>>
```

Use `.then(r => r.recipe.triage !== undefined, () => null)` on each project's promise. Do not wrap it in `try`/`catch`. The `Promise.all` stays as it is and can no longer reject. `project === null` stays skipped, as now (`:597`). The seam follows `projectFilter`'s `recipeFor: RecipeFor = currentRecipe` (`packages/conductor/src/filter.ts:321`). If `RecipeFor` is exported, reuse it rather than writing a new type. Rewrite the docstring at `:588-593`: the reasoning it gives against `false` still holds, but its claim *"rejects and reaches the board as an error"* stops being true.

None of this adds an `async` function or an `Effect.run*`. The ratchet counts `async` functions per package, so an extra `async` arrow inside the `.then`, or a helper of its own, would raise it. Keep the catch as a plain callback.

### 2. Telling the two unknowns apart: a field on `TriageContext`, not a new `toCard` argument

`cardTriageStatus` (`board.ts:573-586`) has to stay unaware of *why* `declared` is null. Its `'Unknown'` answer is correct in both cases, and the task page shares the type (`task.ts:1688`). The reason goes on the context instead:

```ts
export interface TriageContext {
  declared: boolean | null
  daemonStartedAt: Date | null
  /** Set only with `declared: null`: the registry read, this project's recipe did not (#1014). Absent is the registry (#583). */
  unread?: 'recipe'
}
```

- `triageContextOf` gets an optional third parameter. Its two existing overloads (`:563-567`) and both callers (`:1452` and `task.ts:1688`) stay as they are.
- At `:1452`, when `triageDeclared === null`, call `triageContextOf(null, daemon)`. Otherwise read `v = triageDeclared.get(t.project)`:
  - `v === undefined` gives `null` without the `'recipe'` flag. An unregistered project is not a recipe failure.
  - `v === null` gives `triageContextOf(null, daemon, 'recipe')`.
  - Otherwise pass `v` through.
- In `toCard` (`:711-713`), change `status === 'Unknown' ? 'Unknown'` to `status === 'Unknown' ? (triage.unread === 'recipe' ? 'RecipeUnreadable' : 'Unknown')`.
- `moveOf` (`:606`) and `cause` (`:707`) receive `status`, never `card.triage`, so they need no change. `moveOf` already returns `null` for `'Unknown'`.

I rejected a 13th positional argument on `toCard` (signature at `:645-680`). Every test that calls `toCard` with a context would have to change, and the reason belongs with the context it qualifies.

### 3. The card's words and link

Add `RecipeUnreadable: 'triage status unknown — this project's recipe could not be read'` to `TRIAGE_WORDS` (`page.tsx:115-120`). Add `'RecipeUnreadable'` to `BoardCard.triage` (`board.ts:189`). At `page.tsx:226-227`, when the value is `'RecipeUnreadable'`, wrap the words in `<Link href={`/recipe/${encodeURIComponent(card.project)}`}>`. That is the encoding `projects.tsx:85` uses. The other three values keep their bare `<p>`. Any other `TRIAGE_WORDS[card.triage]` lookup, or any exhaustive switch over that union, will fail typecheck. That is how you find them.

### 4. `Problems`: the caller says which problems are about the recipe

`QueueProblem` (`board.ts:424-427`) has no field saying where a problem came from, and `queued-stream.tsx:364` merges `unreadable` with `github.problems` into one list before it calls `Problems` (`:392`). Do not add a tag to `QueueProblem`. Give `Problems` a `recipe: boolean` prop instead:

- `:304`, the fallback, only ever receives `unreadable`. It calls `<Problems recipe problems={unreadable} />`.
- `:364`/`:392` stop merging. They render `<Problems recipe problems={unreadable} />` and then `<Problems recipe={false} problems={github.problems} />`, in the same order as today.
- Keys stay `p.project`. A project that failed `queueFilters` is never asked GitHub (`board.ts:939-943`), so the same project cannot appear in both lists.

With `recipe` set, the `<strong>{p.project}</strong>` sits inside a `<Link>` to `/recipe/<project>`. The sentence after the dash stays unchanged. Update `queued-stream.test.tsx:61` to assert the full new markup, `<a href="/recipe/broken"><strong>broken</strong></a>: the queue could not be listed — recipe.yml: missing`, or whichever nesting you choose. Keep the assertion as strict as the one it replaces.

**This will also link some failures that are not about the recipe, and the ticket accepts that.** `projectFilter` returns `ok: false` for any throw inside its `try` (`filter.ts:324-376`). That includes `clientFor` failing to build a GitHub client (`:340`), `ownerlessRefusal` (`:333`) and `ticketsOf` (`:341`). The ticket's Fix says to link "the column's recipe problems (`unreadable`, the `queueFilters` half)", and the recipe page is still a reasonable place to look for every one of those causes. Do not split `projectFilter`'s failure by cause; that is out of scope.

### Tests

- Put the `declaredTriage` and `toCard` cases in `apps/board/unit/`, next to the existing `toCard` tests (`columns.test.ts:64` shows the shape).
- The `RecipeUnreadable` and `Unknown` cases build the context with `triageContextOf(null, null, 'recipe')` and `triageContextOf(null, null)`, so they need no `loadBoard`, store or `$HOME`.
- The `Problems` case extends `queued-stream.test.tsx`: give `QueuedFallback`/the stream one `unreadable` and one GitHub `unanswered` problem, and assert that only the first is linked.
- The person's check in `## Done when`, breaking a real `recipe.yml`, is the only test of the `loadBoard` wiring at `:1408-1411`. No unit test reaches `loadBoard`, and none should be added for this ticket.
