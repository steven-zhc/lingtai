The ticket fixes the shape. This note covers the three things it leaves to the implementer: where the empty in-flight entry gets dropped, how to test `stateOf` when it isn't exported, and one more comment that has to change.

**Keep `['', 'running']` in `progressOf` and drop it only where text is printed.** `progress.ts:402-404` pushes `['', 'running']` into `mine`. Two readers need it there:
- `stateOf` reads it as its `seen` (`progress.ts:405-408`).
- `labelTone` (`rail.tsx:75`) and `segTitle` (`rail.tsx:84`) treat `p.actions.length === 0` as "nothing configured". The `extra` (`progress.ts:420-421`) keeps that list non-empty for a step the log shows in flight.

If you remove the push, or filter `''` out of `extra`, those reads change in ways the ticket doesn't ask for. So `actions` keeps its unnamed entry, and the filtering happens in `segTitle`. Its last line (`rail.tsx:94`) maps every entry of `p.actions` to `${a.name} ${a.state}`, which is where the stray ` running` comes from today. Change it to:
- list the named entries with their states;
- prefix the step's own state when it is `running`, giving `build: running — install pending, …, lint failed`. A verdict from an earlier round stays beside its action, as the ticket asks.

**`Segs` stops reading `p.actions` for drawing.** Every step draws one `<span className={`scell ${CELL_TONE[p.state]}`} />`. The special case at `rail.tsx:159` (`p.actions.length === 0 ? [{ name: p.step, state: p.state }] : p.actions`) goes away, because the single-cell branch becomes the only branch. `plannedSegments` (`rail.tsx:393-403`) needs no change: its `state` is already the step's own.

**`stateOf` is module-private** (`progress.ts:279`, `function stateOf(`, not exported). Test it through `progressOf` rather than exporting it just for the test. Give it an `AttemptState` where:
- `steps['build:lint']` has verdict `failed`;
- `step` names `build`;
- `resolved` plans `build: [install, format, lint, build]`.

Assert `steps.find(s => s.step === 'build').state === 'running'`. Then run the same state with `step: null` and assert `failed`. That covers the third *Done when* without widening the module's surface.

**One more comment to rewrite.** Add `stateOf`'s doc comment to the ticket's list. It says *"Ordered worst-first, the way the card's stripe is: a failure is the answer even when something after it also ran, and a point still running outranks the ones that have already passed"* (`progress.ts:275-277`). Once `running` is checked before `failed`, the first half is wrong for the step in flight. Say instead that a step in flight is `running` whatever an earlier round left on it, and that `failed` outranks everything settled.

**What the reorder does not reach.** The card's `refused` line is computed only when nothing is live: `const refused = now === null && !live ? refusedAt(progress.steps) : null` (`rail.tsx:309`). During a fix round in `build`, the earlier `build:lint failed` still sits in `actions`. It is not printed as a refusal, because a step is in flight. So `refusedAt` stays as it is, as the ticket says.

`labelTone` (`rail.tsx:76-78`) checks `p.state === 'failed'` before `running`. It reads the step state, so it turns `l-at` on its own once `stateOf` changes. It needs no edit.

The one piece of the log that settles a disputed case is whether `AttemptState.step` names the step while a fix round runs `build` again. That comes from `StepStarted`, and the `StepEnded` that clears it ends the step. The unit tests build this `AttemptState` by hand, so nothing here needs the integration half.
