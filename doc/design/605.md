What is missing or wrong:

- That a partial split leaves the wait open.
- What happens to the parent: it is released, held by every child, and closed at claim.

## Number §12's rules, so the citations in code resolve

The code already cites **"0118 §12 rule 7"**:

- `apps/board/src/lib/split-instance.ts:25`: *"Whether a writer for this wait is running in this process — what *writing* means (0118 §12 rule 7)"*
- `apps/board/unit/split-instance.test.ts:53`

§12 has no numbered rules today. `doc/design/603.md` also uses rules 3, 4, 6 and 7 with fixed meanings (`:36`, `:61`, `:48`, `:76`). Write §12 as a numbered list in this order, so that every existing citation points at the right rule:

1. **The plan is advice until a person approves it on the page.**
   - Triage may recommend `Split` at the first wait, with at most 8 children (`packages/domain/src/triage.ts:38`).
   - The waiting page draws the plan. The person edits titles, bodies, kinds, which children are included, and the chain, then presses **Create all**.
   - A project whose tickets are in `db` sees the plan with splitting marked unavailable (`split-mode.ts:15–17`).
2. **The plan freezes at the first Create all.**
   - `SplitStarted.plan` is the frozen plan. A retry sends no plan, and the writer reads the frozen one from the log (`apps/board/src/app/actions.ts:826–835`; `split-ticket.ts:175`).
   - After a failure the only split action is **Retry what is missing**. A different split means taking one of the wait's other resolutions.
3. **A child is known by its marker and nothing else.** Keep the current bullet, and add one sentence: a child found by its marker keeps GitHub's title and body (`split-ticket.ts:11–16`).
4. **Every run reconciles against GitHub, never against the log.** `TicketSplit` records what GitHub returned on read-back, not the plan (`split-ticket.ts:20–21`, `:365–385`). The progress events (rule 5) are for the page. A retry never trusts them to skip a write (`doc/design/608.md:52`).
5. **Progress is recorded as it goes.**
   - `SplitStarted{waitId, plan, instance}`, then one `SplitChildWritten` per child and one `SplitLinkWritten` per child-to-child link, each read back. The run ends with `TicketSplit` or `SplitFailed{step, detail}` (`packages/domain/src/events.ts:365–398`).
   - Every one of these events carries `waitId`, because a parent can wait again (`events.ts:367–371`).
   - The page draws progress from the log through `splitProgressOf` (`packages/domain/src/split-progress.ts:1–12`).
   - This replaces the old claim that there is no `SplitStarted`. #608 removed that from `TicketSplit`'s docblock, and the ADR must not bring it back.
6. **One child at a time:** create it, attach it, record it, then the next (`split-ticket.ts:17–19`).
7. **Writing or interrupted, and the lock.**
   - A `SplitStarted` with nothing terminal after it means *writing* only if both of these hold:
     - its `instance` is this board process's own;
     - this process says a writer for that wait is running.
   - Otherwise it is *interrupted*. That state is derived and never written (`split-progress.ts:6–12`; `events.ts:365–370`).
   - The page is locked exactly while the split is *writing* (`split-mode.ts:7`, `:22`). It offers Retry on `failed` and on `interrupted`.
   - An unfinished split started by an earlier board process therefore reads as *interrupted*, and the page offers Retry.
8. **A partial split resolves nothing; a complete one resolves the wait.**
   - Partial: whatever progress events were written stay. Nothing else is appended: no `TicketSplit` and no `WaitResolved`. The wait stays open, and a retry reconciles from what GitHub has.
   - Complete: `TicketSplit` and then `WaitResolved{Split}` are appended in one transaction (`packages/conductor/src/resolve-wait.ts:312–313`; `split-ticket.ts:26–28`). That transaction also releases the claim with *"after a split"* (`resolve-wait.ts:571–588`).
9. **The parent waits on its children and is closed at claim when they are all closed.**
   - The writer marks the parent blocked by each child (`split-ticket.ts:355–359`). It also rewrites the parent's `## Done when` as one checkbox per child (`packages/conductor/src/split-body.ts:15–24`).
   - While any child is open, the queue passes the parent over as `blocked-by`.
   - At claim, `claimTicket` reads exactly `TicketSplit.children` (`claim.ts:130–157`; `packages/domain/src/ticket.ts:129–135`). It does not read the body or GitHub's sub-issue list.
   - All children closed: the parent is closed with no run. A comment is posted saying why, and then the issue is closed (`packages/conductor/src/conduct.ts:2250–2283`).
   - Any child open: `split-open`.
   - A child that cannot be read: `split-unreadable`, and nothing is closed.

Rules 3, 4, 6 and 7 line up with `603.md`'s use of those numbers. Keep that order if you reword them.

## The wording trap

The ticket says *"a partial split appends nothing"*. The Done-when list says progress is recorded as it goes. Both are true only if the ADR says exactly what a partial split does not append: `TicketSplit` and `WaitResolved`. Write it that way, as in rule 8. A bare "appends nothing" contradicts rule 5.
