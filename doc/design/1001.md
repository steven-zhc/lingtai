# #1001 — design note

## Where the terminal check reads, and why `by` is needed there

On the terminal path, `startRefusals` runs inside `openDaemon` (`apps/cli/src/restart.ts:491-497`). That happens **before** the daemon records its start. `daemonCommand` builds `startRecorder` → `recordStart(…, started.since)` only after `openDaemon` returns (`apps/cli/src/daemon.ts:302-308`). So `how.control()` at :495 still sees the restart's own request standing, at a version `<= started.since`. Once the withdrawal at :1063-1087 is gone, the drain check at :404 would refuse every restart that drained. Exempting by `by` is what keeps that path working, not a nicety.

`daemonCommand` already passes `{ by, reason, examined }` (`daemon.ts:219`) to `openDaemon`. Only the parameter type at `restart.ts:449` needs widening.

## One input for both paths: a list of drains

Change `startRefusals` from `standing: ShutdownRequest | null` to:

```ts
by: string
drains: readonly ShutdownRequest[] | { unread: string }
```

`startRefusals` drops every drain whose `by === input.by` and refuses each one left, naming it. Do this filtering **inside** `startRefusals`, not at the call sites. Then the exemption lives in one place and the unit tests reach it.

- **Terminal** (`openDaemon`) passes `[standing]` when `standing.version <= started.since`, and `[]` otherwise. A failed `control()` read is `null` today (:495 `.catch(() => null)`). Keep that behaviour: this ticket does not change how the terminal path treats an unread stream.
- **Supervised** passes `requestsBetween(startMark, record.version)`. If that read fails, it passes `{ unread }`, and `startRefusals` turns that into a refusal. This is the ticket's "a read that fails is a refusal".

Use different wording on each side:
- Terminal: the request is still standing, so keep *"landed between the checks and the start … would take work over that stop"* (:407).
- Supervised: the start has already ended the request, so say *"the start ended a shutdown asked by X — Y — that landed between the checks and the start"*.

Pass `startRefusals` a flag, or two arrays, so it knows which sentence to use. The ticket's supervised sentence would be false on the terminal path, where nothing has been ended.

## Why `(startMark, record.version]` is the right window

`recordStart` ends only a request `<= since`. If the standing request is newer than `since`, it records nothing and returns `{recorded: false}` (`packages/daemon/src/control.ts:263-283`): *"One above `since` landed while this daemon was starting, and is its to obey: nothing is recorded"*. So when a record exists, no request in `(since, record.version)` was ended, and `record.version` is a safe upper bound even though the record does not carry `since`.

Below `startMark`, `checkAfterTheWait` covers the gap, and `service start` refuses a request that is still standing (`REFUSED_OVER_SHUTDOWN`, `apps/cli/src/service.ts:239-249`).

Return **every** request in the window, not only the newest. The reducer keeps only the newest (`packages/domain/src/control.ts:199-212`), so reading the state after the start would hide the earlier ones. That is exactly the problem at :1251.

## `requestsBetween`: where it lives and how it decodes

- **Location:** `packages/daemon/src/control.ts`, beside `startAfter` (:319). Export it from `packages/daemon/src/index.ts` beside `startAfter` (:54).
- **Effect:** write it as an `Effect` using `Effect.tryPromise` over `store.readTypes(CONTROL_STREAM, ['ConductorShutdownRequested'], from + 1)`, keeping `version <= to`.
- **Decoding:** do not write a second decoder. Move the reducer's inline decode (`packages/domain/src/control.ts:199-211`) into an exported function, and have both the reducer and `requestsBetween` call it. That decode has the rule that a missing `force` means `false` (the pre-#159 comment), and it should exist in one place only.
- **Wiring:** `RestartFacts` stays Promise-shaped, so tests can keep passing plain functions. `liveFacts` (:686) adapts the Effect with `Effect.runPromiseWith(Context.empty())`. The ratchet does not count that form (`packages/domain/unit/effect-ratchet.test.ts:55`, `RUN = /^run[A-Z](?!\w*With$)/`), and `apps/cli/src/first-project.ts:1256` (`runEffect`) already does the same. A bare `Effect.runPromise` here would raise `apps/cli.run` (6 today).

## Ratchet

Expect no drop in `apps/cli.async`. `liftAdopted` remains an `async` function because the supervised call at :1147 keeps it; only its terminal call goes. Nothing here should add an `async` function in `packages/daemon` either.

Run `pnpm test` and lower a number only where the ratchet reports less than the baseline. Raising any number means the shape is wrong.

## Terminal path details the ticket does not spell out

- **Adopted, daemon holds the lock** (:925): with `liftAdopted` gone, `facts.ask` answers `{asked:false, standing}` with `standing.by === by`. That goes to the existing branch at :976-986. Two log lines then say the same thing: the one at :917-920 (*"taken over, and asked again"*, which is now false) and the one at :981. Keep one, and make it say the request is waited on as it stands.
- **Adopted, nothing conducting** (`plan.go === 'start'`): `request` is still set (:922), which sends the code into `waitForTheLock` through the condition at :1000 on a lock that is free. Change that condition to `plan.go !== 'start'`. Keep `request` only for the Ctrl+C and refusal sentences. The log at :918 becomes *"the start ends it"*.
- **After the wait:** with the withdrawal deleted, `checkAfterTheWait` → `planRestart` sees this person's own request standing and adopts it (:334). That is not a refusal, so no change is needed there.

## What settles it in the log

On a terminal restart that drained, the log should show `ConductorShutdownRequested{by}` at v, then no `ConductorShutdownWithdrawn`, then `ConductorStarted{by, reason: "restarting: …"}` at a higher version. After that, `readControl().shutdown` is `null`. The integration scene *"starts on both paths when nothing refuses"* should check those three facts on the event types, not on the output text.
