# #1132: design note — the rule lives in `classify` now, not in a getter

## The ticket's anchor has moved

The ticket says to change "the `rateLimited` getter (`app.ts:91-94`)". That getter no longer exists. Commit `e830fa1d` (*refactor(failure): what a platform's words mean … are tables in domain's failure module*) moved the rule into a table:

- `GitHubFailed` (`packages/github/src/app.ts:79-90`) carries only `status`, `path` and `detail`.
- The rule is two rows of `FAILURE_ROWS` in `packages/domain/src/failure/classify.ts`. Row `:111-116` is `status: 429` and nothing else. Row `:117-123` is `status: 403, pattern: /rate limit/i`.
- `asLinkCall` asks `classify({ platform: 'github', status: err.status, text: err.detail })?.kind !== 'rate-limited'` (`packages/github/src/client.ts:572-578`).
- The unit test does the same through a local helper `rateLimited` (`packages/github/unit/tagged-errors.test.ts:11-12`).

The module header says why the rule must stay there: *"The packages that meet a failure hand what they saw to `classify` and read the kind; none keeps a pattern of its own"* (`classify.ts:4-5`). **So do not add a `rateLimited` getter to `GitHubFailed`.** Hand the headers to `classify` and decide there. `asLinkCall` then changes only by passing the new fields along. The ticket's "`asLinkCall` needs no change" was written against the old getter.

## The shape

**1. Read the headers once, beside `remainingOf`.** `packages/github/src/observe.ts:67-72` already parses `x-ratelimit-remaining` correctly for this ticket: *"missing or not a number is `undefined`, never `0`"*, using `/^\d+$/`. Add a sibling there that returns all three headers as `number | null`, using the same `/^\d+$/` test for each:

```ts
{ ratelimitRemaining, ratelimitReset, retryAfter }
```

- `retry-after` may legally be an HTTP-date. Anything that isn't plain digits is `null`, per the ticket's edge: *"treated as absent, never as `0`"*.
- `x-ratelimit-reset` is epoch seconds. Keep it as the number; don't convert it to a `Date`.

**2. Carry the headers on `GitHubFailed`.** Add an optional fourth constructor argument, `limits?: { … }`, defaulting all three fields to `null`, and spread it into `super({...})`.

- The positional constructor is called from about ten places, including `gh.ts:89-106`, `app.ts:144`, `app.ts:416`, `app.ts:454`, `client.ts:586` and tests. Every one of those keeps compiling unchanged and gets nulls. That is how the *"`gh` path keeps the message rule"* edge holds without touching `gh.ts`.
- `message` (`app.ts:87-89`) stays as it is. `tagged-errors.test.ts:15-20` pins it.

**3. Fill the headers in where a `Response` exists.**

- **`githubJson`.** Widen the failure branch at `app.ts:186` to `{ ok: false, status, text, limits }`, reading the headers off `response` before `response.text()`. Pass them to `new GitHubFailed` at `:203`.
- **`gh-reader.ts:57` and `:72`.** This file makes the same `fetch` and builds the same `GitHubFailed`. Its headers are real: the token comes from `gh`, but GitHub answers the request. Fill them in here too. The ticket's *"do not invent header values"* is about `gh.ts`'s CLI errors, which have no response at all.

**4. `PermissionDenied` keeps the headers.** Its constructor (`client.ts:64-75`) copies `status` and `path` from `denied`. Pass `denied`'s three fields through as well. Otherwise the most important case — a 403 called a permission — is exactly the one that loses its evidence.

**5. Let `classify` see the headers.** Widen the `github` arm of `Seen` (`classify.ts:21`) with optional `ratelimitRemaining` and `retryAfter` (`number | null`). Optional, so the test helper and any other caller still compile. `reset` is carried on the error, but no row reads it.

Then the GitHub rows become four, **in this order, because row order is precedence** (`classify.ts:7-12`):

| Row | Matches when |
|---|---|
| 429 | status alone, as now |
| 403 + exhausted | `ratelimitRemaining === 0` |
| 403 + told to wait | `retryAfter !== null` |
| 403 + message | `/rate limit/i`, as now |

`GitHubRow` gets an optional header predicate beside `pattern` (`classify.ts:51-57`), and the loop at `:159-163` tests it like the pattern. Each new row needs its own `says`.

**Watch the early return.** `classify` starts with `if (seen.text === '') return null` (`:157`). A 403 with `x-ratelimit-remaining: 0` and an empty or non-JSON body must still come back `rate-limited`. Move that check below the GitHub branch, or apply it only to rows that have a `pattern`. Test that case.

**6. Call sites.** `client.ts:577` passes `err.ratelimitRemaining` and `err.retryAfter`. Change the test helper the same way.

## The decision the ticket leaves open: `x-ratelimit-remaining > 0`

The ticket's Want says to fall back to the message rule *"only when no header says either way."* A remaining count above zero does not say "not rate limited." GitHub's secondary limit arrives as a 403 while the hourly budget still has headroom, often with no `retry-after` (`doc/design/platform-errors.md:24`). The code already protects exactly that case: *"A secondary rate limit is also a 403 and is passed on unchanged: calling it a permission would send a person to the wrong page"* (`client.ts:568-570`).

**So the headers can only add a yes, never a no.** If `remaining === 0` or `retry-after` is present, it is rate limited. Otherwise the message row decides, as it does today. This meets all four Done-when cases:

- A 403 with `remaining: 42` and *"Resource not accessible"* is false.
- A 403 with `remaining: 0` and a permission message is true, because its row sits above the message row.

Letting `remaining > 0` decide "no" would turn a worded secondary limit back into `PermissionDenied`. That is the regression this ticket exists to prevent.

## Generated doc

`packages/domain/src/failure/doc.ts:27` says *"`githubJson` … drops every header, so `retry-after`, `x-ratelimit-remaining` and `x-ratelimit-reset` are never read."* That stops being true with this change.

- Rewrite it to say what is now read, and that nothing retries or waits on these fields yet.
- Run `pnpm docs:errors` so `doc/design/platform-errors.md` picks up the edited sentence and the new rows' `says`. The domain unit test fails if the committed section differs.
- This is the one doc edit the ticket's *"Docs: none"* missed.

## Tests (unit only; nothing here needs integration)

- **`packages/domain/unit/failure-classify.test.ts`** — the classifier matrix:
  - 403 with remaining 0 and a permission message → rate limited
  - 403 with remaining 0 and empty text → rate limited
  - 403 with `retry-after` → rate limited
  - 403 with remaining 42 and a permission message → not rate limited
  - 403 with remaining 42 and "secondary rate limit" → rate limited
  - no headers → today's answers
- **`observe.ts` header reader** — on a fake `{ headers: { get } }`: absent, `""`, `"abc"`, an HTTP-date `retry-after` → `null`; `"0"` → `0`.
- **`packages/github/unit/links.test.ts`** — it already stubs `fetch` for the 403 → `PermissionDenied` case (`:154-206`). Add one end-to-end case: a 403 whose body says *"Resource not accessible"* but whose response carries `x-ratelimit-remaining: 0` is **not** `PermissionDenied`, and its error carries `ratelimitRemaining: 0`.

## Not touched

- ADR 0108 §19 defines the table. Adding rows is what it's for, so no superseding ADR is needed.
- The effect ratchet is unaffected: the header reader is synchronous and adds no `async` and no `Effect.run*`.
