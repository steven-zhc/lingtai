# #603: design note

## Where it goes

There are three places to change, plus one small signature change in `packages/domain`:

1. **`packages/conductor/src/split-ticket.ts`.** Rewrite the body of `splitTicketHolding` as a reconciliation done one child at a time. Keep these as they are:
   - the `deciding` lock (`:113-118`)
   - the `note` helper (`:172-182`)
   - `ensure` (`:240-254`)
   - `writeDoneWhen` (`:276-292`)
   - the `resolveWaitHolding` ending (`:386-404`)
2. **`packages/domain/src/split-progress.ts`.** `splitProgressOf` gets one more input, `running: boolean`. This is how rule 7 is applied (see below). The domain stays pure. It never holds the set; the caller asks the set and passes the answer in.
3. **The board:**
   - `apps/board/src/lib/split-instance.ts` (new): the process id and the running set.
   - `apps/board/src/app/actions.ts`: a new `splitCard` action.
   - `apps/board/src/lib/task.ts`: puts the progress on `StandingView`.
   - `apps/board/src/app/split-plan.tsx` and `standing.tsx`: the modes and the lock.

The page needs no polling. `live.tsx:130` already calls `router.refresh()` on every append, so each `SplitChildWritten` re-renders the page.

## The writer

### The plan is the first `SplitStarted` for this wait
Read the stream, which is done already at `:153`. Take the **first** `SplitStarted` whose `waitId` is this wait.
- **If it exists**, its `plan` is the plan. `options.plan` is ignored: it is not validated and not compared. Make `plan` optional on `SplitTicketOptions`, so Retry sends nothing.
- **If it does not exist**, `options.plan` is required. It goes through `splitPlanProblems` (`:159-161`) and becomes the frozen plan.

Every `SplitStarted` the writer appends must carry **the frozen plan**, retries included. `splitProgressOf().plan` is documented as "the latest attempt's plan" (`split-progress.ts:22`), so it is only right because every attempt writes the same plan. A retry whose `SplitStarted` copies the submission would make the fold show a plan nobody froze.

Work out `since` from that first `SplitStarted`'s envelope `at`, minus `SKEW_MS`, or from now minus `SKEW_MS` on the first attempt. **Do this before appending this attempt's `SplitStarted`.** A store read that throws after the append leaves a start with nothing terminal after it. Attempt 7 had to fix exactly this in its last commit.

### Delete
- The duplicate-title refusal (`:162-165`).
- The adopt-by-title block over `listSubIssues` (`:197-214`).
- `repair` and every call to it (`:260-274`, `:303`, `:308`, `:313`). A child found by marker keeps GitHub's title, body and labels (rule 3).
- `addLabels` from `SplitClient` (`:43`). `getIssue` and `updateBody` stay for `writeDoneWhen` only, which writes to the parent.
- The *key now names another issue* bookkeeping (`:333-335`). A marker binds a key to one issue, so a key cannot move.
- The `create *` / `attach *` step lists (`:121-131`, `:297-339`). They are what produce "all creates, then all attaches", which rule 6 forbids.

When you are done, `split-ticket.ts` compares no `.title` anywhere. The diff shows this, and so does the same-title test.

### The order
1. **List once, before any write.** Call `listIssuesSince(since)`, keep the issues whose `body.includes(splitMarker(waitId, key))`, and take the lowest number per key, as `carrying` does (`ticket-store.ts:161-167`).
   - If the call throws, append `SplitFailed{step: 'read GitHub'}` and return. Nothing else gets recorded: no `SplitChildWritten` and no `TicketSplit`.
   - `listIssuesSince` already throws rather than answering short (`client.ts:223-227`: "**Complete, or it throws.**").
   - The `SplitFailed` still has to be written. It is what *nothing recorded* means here, because without a terminal event the page has nothing to end on.
2. **For each child in plan order: create, then attach, then record (rule 6).**
   - **Create.** If no marker answers for the key, call `createIssue({ title, body: expectedBody(child), labels: [kind] })`. `expectedBody` is at `:256-257`.
     - If the create throws, list again and look for the marker. If it is there, adopt it. If not, fail.
     - The catch at `:309-313` is that case today; keep it without `repair`.
   - **Attach.** `ensure` over `listSubIssues` (`:321-325`).
   - **Record.** Take `id` from the sub-issue listing (`:328-331`), because no create call returns one (`:367-368`).
     - Append `SplitChildWritten` unless `prior.children` already has that key with that number.
     - Only then start the next child's create.
3. **Planned links.** `ensure` over `listBlockedBy`, then `SplitLinkWritten` (`:340-355`).
4. **The parent's holds and Done-when** stay as they are (`:356-365`). They write to the parent, not to a child, so they do not break *never touches an issue it did not create*.
5. **Read back.** Call `listBlockedBy(n)` for every child.
   - Keep only entries where `repository` matches and the number is another child's. Map numbers back to keys.
   - Every planned link must be in that set, or the step fails.
   - `TicketSplit.blockedBy` is **that read-back set**, not `plan.blockedBy`. Today `:379` copies the plan, and rule 4 is what that gets wrong.
   - `children` comes from the sub-issue listing, as `:371-378` does now.
   - `WaitResolved{Split}` keeps the frozen plan (`:392`).

Do not carry over attempt 7's approach of parsing children back out of `SplitFailed.detail`, or its `earlier` field on the fold. Those existed only because batched creates left children with no `SplitChildWritten`. Rule 6 shrinks that window to one crash between a create and its record, and Retry covers that window by marker.

Children already created are listed on the page from `progress.children`.

### Starting and returning
Add an `onStarted?: () => void` option, called straight after this attempt's `SplitStarted` append. The action waits until either that fires or the writer resolves:
- If the writer resolved first, it was refused before writing anything. Return its `detail`.
- If `onStarted` fired, the write is running. Call `revalidatePath` and return ok.

This way the action's own re-render already reads *writing*. If it returned before the append, it would render *idle*, with Create all live again for a moment.

## Rule 7: the running set

`apps/board/src/lib/split-instance.ts` holds two things on `globalThis`, under a `Symbol.for` key:
- `splitInstance()`: one `randomUUID()` per process. The reason is in `split-ticket.ts:84-89`: Next's dev HMR re-runs a module-level one.
- A `Set<WaitId>` of the waits whose writer is running in this process.

`runSplit(waitId, start)` does three things:
1. It **refuses synchronously if `waitId` is already in the set**, without calling the writer.
2. Otherwise it adds `waitId` and calls `start()`.
3. It removes `waitId` in a `finally` on the detached promise, and that promise also gets a `.catch` so a rejection is never unhandled.

The refuse-before-add order matters. If a second click called the writer, `deciding` would refuse it, but its `finally` would then remove the first writer's entry, and the page would read *interrupted* while the first writer is still running.

`splitProgressOf(events, { waitId, instance, running })` answers:
- `writing` only when nothing terminal follows the latest `SplitStarted`, **and** `started.instance === instance`, **and** `running` is true;
- `interrupted` otherwise.

Callers:
- `task.ts` passes `isSplitRunning(waitId)`.
- The writer's own call at `:167` reads only `children` and `links`, so it passes `running: true`.

Because the `finally` removes the entry whether or not the last `SplitFailed` append succeeded, a writer whose final append throws reads as *interrupted*, and Retry is offered.

## The page

Leave `standing.tsx:576` filtering `Split` out of the resolution cards. The controls belong to the plan panel the triage band already draws (`standing.tsx:208`).

Pass `SplitPlan` two new props:
- `progress`: off `StandingView`, filled in `loadTask` (`task.ts:1806`) from the events that function already reads.
- `tickets: 'github' | 'db'`, from `ticketSourceOf(recipe)`.

Derive the page's mode with a **pure exported function**, so a unit test can cover it without rendering React Flow:

| `progress.state` | Plan drawn | Edits | Button | Other moves |
|---|---|---|---|---|
| `idle`, github | page state | on | **Create all (n)** | live |
| `idle`, db | triage's | off | none; shows *splitting is not available there yet* | live |
| `writing` | `progress.plan` | off | none | disabled |
| `failed` / `interrupted` | `progress.plan` | off | **Retry what is missing** | live |

Other details:
- **Create all** sends the included children only, and drops every link that touches an `off` child (`split-plan.tsx:88`).
- A card turns *written* when its key is in `progress.children`. On `failed` or `interrupted`, those children are named by `#number` and left for the person to close.
- Selecting a card to read it works in every mode. Only the inputs inside `split-panel` are disabled.

### `splitCard` (actions.ts)
`splitCard({ project, issue, waitId, plan? })` does the following:
- answers `no GitHub App configured` if `hasGitHubApp()` is false;
- loads the project and its recipe;
- refuses `db` projects in the same words the page uses;
- builds the client with `githubClientFor(state)` (`filter.ts:218`), not `projectClient`, because the writer wants a `GitHubClient` and not `Tickets`;
- passes `kindsOf(recipe)`, `` `${owner}/${project}` ``, `actor()` and `splitInstance()`, and starts the writer through `runSplit`.

## Checks

These all run in `pnpm test`.

- **Writer:** through `splitTicketHolding`, with `createMemoryEventStore()` and the fake already in `packages/conductor/unit/split-ticket.test.ts`.
  - **Rule 6:** an assertion over the fake's call order.
  - **The same-title test:** seed an unrelated sub-issue of the parent with the planned child's exact title and kind. Then assert that no call in the fake's log names its number.
  - **Delete** the tests that assert the behaviour removed here: adopt by title, the label repairs, and the title swap.
- **Rule 7:** `runSplit` around `splitTicketHolding`, using a store that throws on the `SplitFailed` append. After it settles, `splitProgressOf` with `running: isSplitRunning(waitId)` must read `interrupted`.
- **`splitCard` itself:** it takes the file lock and the real App, so by 0060 §1 it is integration and nothing covers it before the merge.
  - What stands in for it is a writer test where the fake's first GitHub call asserts that the store already holds this attempt's `SplitStarted` and that `onStarted` has fired.

## Settled by the log

Whether a real split converged shows on the parent's stream:
- every `SplitStarted` for the `waitId` carries an identical `plan`;
- each `key` has exactly one `SplitChildWritten.number`, and a second number for the same key means a child was created twice;
- `TicketSplit.blockedBy` equals GitHub's `blocked_by` for those numbers.
