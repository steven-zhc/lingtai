A run that stops at `run.turns`, `run.wall` or `run.usd` should go to triage, and triage should redo the step or split the ticket. Two things in the code stand in the way today. The wait a stop at the turn or dollar limit opens does not offer `RedoStep` at all, so the system could not choose it. And the ticket's own ordering contradicts itself.

# Design: #1260 — what triage does with a run that met its limit

## Where it goes

The pure table already exists. `actionFor` takes a `CauseOrigin` of `'run-limit' | 'diff-too-large' | 'other'` (`packages/domain/src/failure/respond.ts:918`). It already turns `TicketTooBig` without a plan into `writeSpentOnThenRedoStep` (`respond.ts:966`) and `Unfinished` into `redoStep` (`respond.ts:968`).

Four things are missing:

1. Nothing produces `run-limit`.
2. Nothing restricts which causes triage may answer for that origin.
3. The transition refuses to act on `writeSpentOnThenRedoStep`: `if (action._tag === 'askPerson' || action._tag === 'writeSpentOnThenRedoStep') return advice` (`packages/domain/src/ticket.ts:1460`), and its comment says *"`writeSpentOnThenRedoStep` (#1260) is not built"* (`ticket.ts:1416`).
4. The wait a budget stop opens does not offer `RedoStep` (see *The trap* below).

**Files:** `failure/respond.ts`, `wait.ts`, `ticket.ts` (domain); `ticket/commands.ts` and `triage.ts` (conductor); `apps/cli/src/triage.ts`.

## 1. One function names the origin

Add `causeOriginOf(reason: WaitReason): CauseOrigin` beside `CauseOrigin` in `respond.ts`. Today the origin is worked out inline in `readActContext`, and it only knows `DiffTooLarge`:

```
request.reason._tag === 'ProposedEscalated' && request.reason.proposal._tag === 'DiffTooLarge' ? 'diff-too-large' : 'other'
```

(`apps/cli/src/triage.ts:1065-1068`). Replace that with a call to the new function, and have the brief call the same function, so the two cannot disagree.

The origin is `run-limit` when:
- the wait is `BudgetExhausted` with `kind` `out-of-turns` or `out-of-usd`, either as the wait itself or as a `ProposedEscalated` proposal, and its `from` is `design`, `implement` or `review`; or
- the wait is `AgentCrashed` with `cause: 'timeout'`, at one of the same three steps, and with no `standing`.

`AgentCrashed{timeout}` can also happen at `proposed` and `merge` (`attempt-next.ts:504`). Those are a judge or the lane timing out, not a step's own run, so they are `other`.

**#1249's crash rule already leaves `timeout` alone.** `rerunInPlace` begins `if (cause !== 'crash' || spent >= BOUNDS.stepRedos) return null` (`respond.ts:608`). Don't change it. Pin it with a unit assertion that `rerunInPlace('timeout', …, 0)` is `null`, beside the new origin test.

## 2. The trap: `RedoStep` has to be offered on a budget wait

`actOnTriageTransition` resolves through `resolveWaitTransition`, *"the person's own path, so what it accepts is what a person may choose"* (`ticket.ts:1413-1414`). If the wait does not offer the resolution, the answer becomes `not-offered` (`ticket.ts:1496`). Today:

- **`RedoStep` is offered only where `rerunStepOf` returns a step** (`wait.ts:600`).
- **`rerunStepOf` returns `null` for `BudgetExhausted`.** It handles `AgentCrashed` at design, implement or review (`wait.ts:710-712`); everything else falls to `default: return null` (`wait.ts:720-726`).
- **A budget wait offers only** `['EditBodyAndStartNewAttempt', 'StartNewAttempt', 'Close']` (`wait.ts:686-688`, `wait.ts:701-704`).

So nothing in this ticket would ever run on `out-of-turns` or `out-of-usd` until `rerunStepOf` learns `BudgetExhausted`, both as the wait itself and inside `ProposedEscalated`: return its `from` when that is `design`, `implement` or `review`.

That also adds a **Run this step again** button to every budget wait a person sees. That is intended: it is the click the ticket says a person makes today.

The continuation reads the same `rerunStepOf` (`conduct.ts:1610`), so the offer and the step that is redone stay one answer. Check `defaultResolution` (`wait.ts:904`) and the board's offer tests, which will move.

## 3. The brief, and refusing other causes

### The brief

`triageBrief` (`packages/conductor/src/triage.ts:187`) takes the wait's reason as `evidence.reason`. When `causeOriginOf(evidence.reason) === 'run-limit'`, it adds a block that:
- says the run was cut off;
- names the step and the limit it met (`run.turns`, `run.wall` or `run.usd`);
- admits only `Unfinished` and `TicketTooBig`.

This replaces, for this origin only, the rule *"The budget is never a cause … or say the run did not finish (`Unfinished`, or `TicketTooBig` …)"* (`triage.ts:166-169`). Other origins keep the brief exactly as it is.

### Refusing any other cause

The check is not made in `parseTriage`. It is a new `ActOnTriageRefusal` in `actOnTriageTransition`, checked after `streamChanged` and before `actionFor`. Its `why` names the cause, for example *"FixableLines is not a cause for a run that met its limit"*.

That path already records `WaitTriaged{TriageFailed{why}}` (`commands.ts:640-644`). The caller already turns a refusal into a failed attempt (`apps/cli/src/triage.ts:1631-1640`), and a failed attempt is asked again while `attempt <= BOUNDS.triageRetries` (`apps/cli/src/triage.ts:223`, `respond.ts:591`). That is the ticket's *"recorded `TriageFailed` and asked once more"* with no new machinery, and it can be tested purely.

The check runs only where `act` is given. Without a `limits` port the answer is advice only (`apps/cli/src/triage.ts:1617-1619`), and a person reading `FixableLines` as advice has lost nothing. Leave that alone.

## 4. Write the body before recording the redo, not after

The ticket says the conductor writes the section *after* `WaitResolved` and *"a write that fails twice leaves the wait for a person"*. Both cannot hold: once `WaitResolved` is appended the wait is not a person's to keep.

The codebase already settled this for the person's path. *"The answers are written before the wait resolves … A failed write resolves nothing"* (`packages/conductor/src/resolve-wait.ts:461-463`, #1254). The `WaitResolved.answers` schema says *"the section exactly as handed to the write. Absent when nothing was written"* (`packages/domain/src/events.ts:401-405`). So `answers.section` claims a write already happened.

**Decision: write first, then make the one append.**

### The transition (`ticket.ts`)

- **The section text:**
  - `TicketTooBig{plan: null}` → `spentOn`;
  - `Unfinished` → `addToBody`.

  `Unfinished` stays `redoStep` in `actionFor`; the transition reads the text from the cause. Both write under the same one key, so a ticket carries one such section.
- **Null text** — including `TicketTooBig` with both `plan` and `spentOn` null — **is a plain `RedoStep`.** `actionFor` returns `writeSpentOnThenRedoStep{spentOn: null}` there, and the transition treats it as `redoStep`.
- **Non-null text** takes the `redoStep` branch (`ticket.ts:1476-1480`) unchanged: the same `context.redo` and `head-moved` refusals, and the same `spent: {bound: 'stepRedos', n}`. It also passes `answers: { picks: [], section: text }` to `resolvedEvents`, which already accepts `answers` (`ticket.ts:1182`).
- **Return the text** on `ActOnTriageDecision`, for example `section: string | null`, so the effect knows what to write.

### The effect (`finishTriage`, `packages/conductor/src/ticket/commands.ts:567`)

- **Inject the write as a port; do not import it.** `write-section.ts` already imports from `./ticket/commands.ts` (`write-section.ts:13`), so `commands.ts` importing `writeSectionEffect` would be a cycle. Add an option such as `writeSection?: (text: string) => Effect.Effect<WriteSectionResult>`.
- **Supply it from `apps/cli/src/triage.ts`.** It already builds a GitHub client (`apps/cli/src/triage.ts:651`). Call `writeSectionEffect({ store, github, ticketId, key: \`${ticketId}/spent-on\`, text, verified: true })`.
  - `verified: true` because the redo must not start on a body that only might have the section (`write-section.ts:51`).
  - The key is per ticket, not the `${ticketId}/${waitId}` keys the person's path uses (`resolve-wait.ts:506`, `resolve-wait.ts:538`). That is what makes it *one section, replaced* (`write-section.ts:33-35`).
- **Order:** after the transition decides and before `appendLost`.
  - If the write fails (`written: false`), do not append the resolution. Append `WaitTriaged` alone, the transition's `advice` shape, so the wait stays a person's.
  - The write's detail is already on the log: `writeSectionEffect` goes through `tellGitHub`, which records `IssueUpdateFailed` (`write-section.ts:40-45`). Don't add an event for it.
  - Do not record this as `TriageFailed`. That would buy a second triage agent to answer the same question, and the answer was not at fault.

### What this ordering does on each edge

- **The append loses its version** (`lost`) **or the process dies between the write and the append.** The next try or the next triage writes the same key again, replacing it in place. The body holds one section either way. A body note with no `WaitResolved` behind it is harmless: the wait is still open and the note is true.
- **A person clicks `RedoStep` from a page loaded before triage resolved it.** That is already refused, by `waitId` and by version.
- **Two cut-off runs on one ticket.** One `spent-on` section holding the second run's text. Each `WaitResolved.answers.section` keeps its own run's text.
- **What triggers the redo after the append.** The `requestContinuation` call that already follows a `RedoStep` (`apps/cli/src/triage.ts:1646-1660`); nothing new. The continuation's brief carries #1245's interrupted paragraph as it already does.

## 5. A spent bound

`stepRedos.used` is already the larger of `run.stepRedos` and what triage has spent (`apps/cli/src/triage.ts:1050-1053`), and its `allowed` is `BOUNDS.stepRedos` (3, `respond.ts:581`). With it spent, `actionFor` returns `askPerson{limit, bound: 'stepRedos', used}` (`respond.ts:954`), and the transition returns advice, so the wait stays.

For the line *"`stepRedos` … 3 of 3"*:
- **Today's wording:** `wait-words.ts:559` (`${counter.used} of ${counter.allowed} ${noun} used`) and the judge path's `counted` (`proposed-route.ts:257-258`).
- **The gap:** `systemBoundOf` (`read-model.ts:448`) reads only a *resolved* wait, so it does not reach a wait that stayed open.
- **How to fill it:** in the reader, from `WaitTriaged.result` plus `causeOriginOf` plus the counters the ticket and run state already hold. Don't put a new field on `WaitTriaged`.
- **Keep it out of `wait.ts`:** that would close the cycle `causeResolution`'s comment warns about (`wait.ts:932-935`). Put it in the board or cli reader, or in `read-model.ts`.

## What checks it

Every claim here can be checked in the unit half. Nothing needs `pnpm test:integration`.

- **`causeOriginOf`:** a table test over the wait reasons, including `AgentCrashed{timeout}` at `proposed` → `other`.
- **`rerunStepOf` and `allowedResolutions`:** `RedoStep` on both shapes of `BudgetExhausted`.
- **`act-on-triage.test.ts`:**
  - run-limit + `Unfinished{addToBody}` → `WaitResolved{RedoStep, answers.section, spent.n}`;
  - `TicketTooBig{spentOn}` → the same;
  - both null → no `answers`;
  - `FixableLines` → the new refusal;
  - counters spent → advice only.
- **`finish-triage.test.ts`**, with a fake `writeSection`:
  - a failed write appends `WaitTriaged` only;
  - a successful write precedes the append.
- **`triage.test.ts`:** the brief's run-limit block appears for `out-of-usd` and `timeout`, and nowhere else.

Pin the origin, not a turn count. `effect-ratchet.baseline.json` does not move: the port is an `Effect`, so no new `async` function or `Effect.run*` is needed.

## Contradicts no ADR

0108 §12 already sends a wall to triage and a crash to `redoStep`. Writing before resolving follows #1254's rule (`resolve-wait.ts:461`); it is not a new decision.
