## Design: #1312 — sync, build, merge back

### Where it goes

- **`packages/conductor/src/pr-sync.ts`**: `syncStep`, `buildStep` and `mergePrBack`. `syncStep` and `buildStep` go at the front of `IN_PROGRESS_STEPS`, so it reads `[syncStep, buildStep, pushStep, openStep]` (`packages/conductor/src/pr.ts:339`). Its comment already says *"`sync` and `build` (#1312) before them"* (`pr.ts:335`).
- **`packages/repo/src/pr-sync.ts`**: one Effect, `mergeInWorktree`. It takes `{ project, home, name, at, theirs, message }` and answers `{ merged: sha } | { conflict: paths } | { failed: text }`. It cuts the worktree, merges, and on a conflict reads the unmerged paths and runs `merge --abort`, as `integrate.ts:546-562` does. It releases the worktree on every exit. The worktree is named `pr-sync-<n>-<epoch>` or `pr-back-<n>-<epoch>`, never `integrator-…`.
- **`PrPorts`** (`pr.ts:48`) gains two ports, so the unit tests fake them the way they already fake `git`/`remote`:
  - `merge(project, …)` → the repo Effect above.
  - `build(project, { sha, base, checkId })` → `{ green } | { red: { command, evidence } } | { unknown: why }`.
- **Pushes go only through `ports.remote`.** That makes 0130 §7's test a check over the fake `remote`'s recorded `push` calls: nothing may name `refs/heads/<main>`, and the sync makes no push at all.

### The build port: one base check, the pass's rules

`baseCheckQuestion` needs four things a pass already has:
- the resolved env (`host.resolveEnv`, `conduct.ts:1274`);
- the sandbox decision (`decidePassSandbox(recipe.sandbox, options.sandbox)`, `conduct.ts:1180`);
- `Repo`;
- the per-store instance `baseCheckFor(store, log, home)`. It is private to `conduct.ts:375`, and it is the in-flight map that makes two asks of one commit a single run (#744).

So:
- **Move `baseCheckFor` into `base-check.ts` and export it**, so a PR build and a pass share one instance.
- Write `buildAt` in `conductor/src/pr-sync.ts` as an Effect that requires `Repo | AgentHost`. It asks once per entry of `buildRunsOf(recipe)` (`base-red.ts:22`), in order, and stops at the first red.
  - `notBuilt` (`base-check.ts:426-440`) and `unknown` both answer `unknown`.
  - An empty list answers `green`.
- `livePrPorts` (`apps/cli/src/pr-ports.ts:23`) provides `PortsLive` and `processSandbox` to `buildAt`, the same ones `run.ts:534` hands a pass. Its two callers (`daemon.ts:679`, `run.ts:340`) pass whatever extra argument that needs.

### Departure from the ticket: no PR build is recorded under `base: branch.personal`

The ticket says the merge back is built `base: branch.personal`. **Don't do that.** `createBaseCheck` appends `BaseChecked` on `integrationStream(q.project, q.base)` (`base-check.ts:356`). Three readers take the **newest** `BaseChecked` on that stream, whatever commit it was recorded at, as the state of the project's base:
- `baseStateOf` reads *"the newest `BaseChecked`, whatever its command or boundary"* (`packages/domain/src/integration.ts:154`, `:187`).
- The queue's `lookAtBase` on `branchOf(recipe)` (`schedule.ts:245`) uses it.
- `proposeBaseFix` (`base-fix.ts`, called at `conduct.ts:6295`) uses it.
- The flake verdict reads every `BaseChecked` of a command, on any sha (`flaky-port.ts:41`).

Two things break if the merge back records there:
- **A green merge-back build masks a real red `branch.personal`.** `lookAtBase` then answers `clear`, and every queued ticket is claimed only to be requeued on its own base check.
- **A red one is folded into the next base-fix ticket's key.** That ticket is opened against a commit that was never on the branch.

So **both PR builds ask with `base: prBranch`**, with `checkId` `pr-<n>-sync` or `pr-<n>-back`. The base-check worktree is `base-<sha7>-<checkId>` (`conduct.ts:379`), which the lane's sweep does not touch.

The only other readers of `int-{project}-{prBranch}` are #1337's push lane and #1341's pr-fix landings:
- The lane's state is folded from `Integration*` events, not `BaseChecked` (`laneIsBusy`, `integration.ts:148`), so the lane is unaffected.
- A pr-fix base check is sha-keyed.
- The one residue: a sync red can still be folded into the key of a base-fix ticket proposed for the PR branch, if a pr-fix ticket is requeued for a red base there. That is said here, not prevented.

The settling field is `BaseChecked.base` and `BaseChecked.runId` on `int-{project}-{personal}`: after this change, no row there has a `pr-` `runId`.

### Which commit the sync starts from, and what it accepts on the remote

`target` is reset to `frozenSha` by every `PrInProgress` (`packages/domain/src/pr.ts:111`), and `lastPushed` is not (`pr.ts:41-43`). Two passes must not wedge on that:

- **After a `restart`**, `target` is `frozenSha` but the remote holds an earlier merge, `M`.
  - Starting from `frozenSha` would make a new merge, `M′`, that does not descend from `M`.
  - `pushStep` then answers `again` for ever, since it reads a non-descending target as *"a pr-fix landing that went first"* (`conductor/src/pr.ts:206-209`).
- **On a pr-fix pass (#1341)**, the new commits are in `target`. Starting from `lastPushed` would drop them.

**The start commit:**
- `lastPushed === null` → `target`.
- Otherwise, the descendant of `target` and `lastPushed`, by two `merge-base --is-ancestor` asks.
- Neither descends from the other → `rewritten`.

**The remote check** uses `remoteSha` (`conductor/src/pr.ts:141`), which is exact-ref matched already. Accept:
- absent, while `lastPushed` is null;
- `lastPushed`;
- the start commit.

Anything else is `sync-rewritten { expected, found }`. That covers #1341 whether or not it records its landing as a push.

**`BranchSynced` sets `target = head` for every `how`, `already` included.** In the restart case, `already` must move `target` to `lastPushed`. Otherwise `pushStep` sees `at === lastPushed` with a `target` that does not descend from it, and stalls (`pr.ts:197-209`).

### How sync hands the merge to build

**sync:**
- `already` → it records `BranchSynced { how: 'already', mainCommit, head: start }` as its step record. Use the `PrRecord` "in place of `PrStepDone`" path (`pr.ts:89-92`).
- Merged → it writes `refs/lingtai/pr/<n>/target` → M (`update-ref`, in the mirror), then answers `done { headSha: M }`, which records `PrStepDone { step: 'sync', headSha: M }`.

**build:**
- It reads M from the `sync` record.
- If that record's `headSha === state.target`, nothing was merged: it answers `done` and builds nothing.
- `cat-file -e M^{commit}` fails → `restart`, exactly as `pushStep` does (`pr.ts:202-203`).
- Green → `BranchSynced { how: 'clean', head: M }`, folded as the `build` step, with `target = M`.

The walk's fence (`pr.ts:441`) compares `target` *before* the record is appended, so neither step trips it.

**Resolve shas after `ports.fetch`** (`rev-parse --verify refs/heads/<main>^{commit}`, as `freezePr` does at `pr.ts:360-367`) and work by sha. The mirror's `refs/heads/*` are the remote's after a fetch, so the per-step fetch refs the ticket describes buy nothing here. The sync and the merge back fetch into `refs/lingtai/pr/<n>/main` and `…/personal`, and each deletes its own when the step ends, on every outcome. `refs/lingtai/pr/<n>/target` keeps an unpushed merge and is deleted once `PrPushed` names it. A PR's build worktree (`base-<sha7>-pr-<n>-sync|back`) is swept with the others. A fetch goes through `retryUnreachable` in the live remote port.

**Sweep:** at the start of the sync and of the merge back, remove every `pr-sync-*` and `pr-back-*` entry in `worktree list --porcelain`, then `worktree prune`, as `integrate.ts:356-371` does but without the age test. `permitOf` makes one serve per project at a time (`pr.ts:116-124`), so none of them can be live.

**Waits:** extend `PrWaitReason` (`events.ts:2558`) with `sync-conflict`, `sync-red`, `sync-unknown` and `sync-rewritten`.
- Every git or build failure inside the two steps answers `wait`; the steps never `Effect.fail`. Otherwise `walkPr` fails, and only a log line says so (`pr.ts:496`).
- `waitTransition` already drops a second wait with the same step and reason (`domain/src/pr.ts:284-288`).

### The merge back

**Trigger:** in `servePr`, after `walkPr`, when all of the following hold:
- `status === 'in-review'`;
- `lastPushed !== null`;
- the reducer's new `mergeBack: { prHead, outcome } | null` does not name `lastPushed`.

Both `PrMergedBack` and `PrMergeBackFailed` set `mergeBack`. That is what keeps a red merge back from being rebuilt on every later PR-stream event: each attempt makes a new merge sha, so the base check's log cache never hits.

Also widen `servePendingPrs`'s filter (`pr.ts:494`) to an `in-review` PR whose `mergeBack` is unset. A daemon killed between `PrOpened` and the merge back would otherwise never come back to it.

**What it merges:** `lastPushed`, the commit Lingtai pushed, not whatever the remote PR branch says. A person's push to the PR branch never reaches `branch.personal` this way.

**Which branch it pushes:** the branch the PR recorded at the freeze (`state.branch`). If `state.branch === state.main`, push nothing and record `PrMergeBackFailed { why: 'unknown' }`. `freezePr` falls back to `branch.personal ?? main` (`pr.ts:355`), and that fallback must never become a push to main.

**The order inside the lane:**
1. Take the turn: `(ports.lane ?? landingLane).through(integrationStream(project, state.branch), { pr: prStream(project, n) }, …)`, shaped like `pushStep` (`pr.ts:222-228`).
2. Inside the turn: fetch, then the ancestry check, then the local-remote check (`integrate.ts:438-449`).
3. Merge with `ports.merge` and build with `ports.build`, `base: prBranch`.
4. Push `M:refs/heads/<state.branch>`, never forced.
5. A lost push gets one look, then the recompute #1210 allows.

**Two things the implementer should know:**
- **The PR head already being an ancestor appends nothing**, as the ticket says. The gate above keeps that to one fetch per later event.
- **The build runs inside the lane turn, and that turn is uninterruptible** (`landing-lane.ts:87-89`). Every landing on `branch.personal` waits behind one build per In review. That is 0122 §3's price, and it is the reason for the `MergeLaneWaited { behind: { pr } }` row in Done when.

### Unit-level claims that stand in for the integration half

Everything in Done when is reachable with the fake `PrPorts` that `pr-push-open.test.ts` and `pr-serve.test.ts` already use, plus fakes for `merge` and `build`. Add one `repo/unit` test of `mergeInWorktree` against a fake git port in the style of `integrate.test.ts`: conflict paths split on NUL, `--abort` called, and a failure with no unmerged path is `failed`. The real-git path of `mergeInWorktree` is the one thing only `pnpm test:integration` reaches. Leave it to the post-merge run; don't wait on it here.

Regenerate `doc/events.json` for `BranchSynced`, `PrMergedBack` and `PrMergeBackFailed`, each with an `@summary` and an `EVENT_AT` row of `['outside']`, like the PR events at `events.ts:3036-3039`.
