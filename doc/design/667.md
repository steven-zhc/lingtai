## Design for #667: Codex user permission profile under Lingtai

All of this lives in `packages/agent/src/codex.ts`, with tests in `packages/agent/unit/codex.test.ts`. No other package changes.

### 1. The reader returns a verdict, not a list of denies

The ticket describes four outcomes. They need different behaviour in `run()`, and `invocation()` has no run log to write to. So the reader returns a discriminated union. Each caller decides what to do with it:

```ts
type UserPermissions =
  | { kind: 'none' }                              // no config, no default_permissions, a built-in, or no denies
  | { kind: 'denies'; paths: readonly string[] }  // keys exactly as the user wrote them
  | { kind: 'kept'; why: string }                 // sandbox_mode is set too: today's argv, with a run-log line
  | { kind: 'unreadable'; why: string }           // today's argv, with a run-log line
```

Split it the way `readCodexConfig` / `configModelFor` are split (`codex.ts:505-557`):

- **A pure function, exported and unit-tested:** `userPermissionsFrom(text: string)`. It parses with `smol-toml` and returns the verdict.
- **A thin file-reading wrapper beside `hookWiringAt` (`:950`):** `userPermissionsAt(env, cwd)`. It reads `codexConfigPath(env, cwd)` and never throws.

The tests for collecting denies, following `extends`, detecting cycles and catching `sandbox_mode` all go against the pure function. None of them touch the filesystem.

**A missing file is `none`, and nothing is written to the log.** `configModelFor` already stays silent on `ENOENT`/`ENOTDIR` (`:546`), and this does the same. No file means the user set no profile, and saying "could not be read" on every run without a Codex config would be false. Any other read error, and TOML that does not parse, give `unreadable`. The ticket lists "missing" among the cases that get a log line. I read that as a file `default_permissions` depends on and cannot reach, not as the ordinary case of having no config.

### 2. Rules for the pure function

- **Finding the active `default_permissions`:** use the same lookup `readCodexConfig` uses for `model` (`:512-520`). The active `[profiles.<profile>]` table wins over the top level.
- **Checking for `sandbox_mode`:** if `sandbox_mode` appears at the top level or in that active profile table, and a non-built-in `default_permissions` is in effect, the answer is `kept`. A `sandbox_mode` with no `default_permissions` is `none`, because there was nothing of the user's to apply.
- **Built-in names give `none`:** that is `default_permissions` starting with `:` (`:workspace`, `:read-only`, `:danger-full-access`).
- **Collecting denies:** walk `[permissions.<name>]` and then its `extends`.
  - Stop at a `:`-prefixed parent; it contributes nothing.
  - An unknown parent, or a cycle (track visited names in a Set), gives `unreadable`.
  - Collect `filesystem` entries whose value is the *string* `"deny"` or `"none"`.
  - An entry whose value is anything other than a string (an inline table, say) gives `unreadable`. A nested shape might hold denies this code cannot copy faithfully, and narrowing less than the user meant is exactly the bug this ticket fixes.
  - `read` and `write` entries are skipped.
  - Remove duplicate paths. Order: first seen, from the child up to its parents.
- **Name collision:** if `permissions.lingtai_workspace_write` or `permissions.lingtai_read_only` exists in the user's file, the answer is `unreadable`.
- **No denies:** a chain with no deny entries is `none`.

### 3. `codexArgv` takes the denies as one more option

Add `denies?: readonly string[]` to `codexArgv`'s options (`:1074`). `argsFor` (`:1098`) branches on `denies.length > 0`:

- **Empty or absent:** the argv is exactly today's. The test is a byte-for-byte array equality against a literal, not a "does not contain" check.
- **Non-empty:** drop `'--sandbox', sandbox` and the `--add-dir` flatMap, and emit two `-c` pairs in their place. Everything else keeps its position: `--cd`, `approval_policy=never`, the hooks, `--model`, `--output-schema`, `extraArgs`, `--`.
  - The name is `lingtai_${sandbox.replace('-', '_')}`.
  - `extends` comes from the role alone: `':workspace'` for `workspace-write`, `':read-only'` for `read-only`.
  - **Never use the user's own `extends`.** Their chain may end at `:danger-full-access`, and inheriting it would widen the run.
  - `filesystem` holds `toml(dir) = "write"` for each writable root, then `toml(path) = "deny"` for each deny. Every deny is written out as `"deny"`, including one the user wrote as `none`.
  - Build that inline table with `toml()` (`:932`) for every key and value. It is `JSON.stringify`, and a JSON string is a valid TOML basic string.

`writable` is already `[]` for a reader (`writableFor`, `:1172`), so the reader's table has no `write` entries without any extra code.

### 4. The callers

Both callers call `userPermissionsAt(request.env, request.cwd)` and pass `denies: verdict.kind === 'denies' ? verdict.paths : undefined`. Only `run()` acts on the other three kinds of verdict, and it does so after the hook-wiring refusal (`:1212-1229`):

- **`kept` / `unreadable`:** `trace.note('codex', why)`, then today's argv. The sentence must say that the user's profile **did not narrow this run**, and why.
- **`denies`, but one covers a root:** refuse, with the same `{ exitCode: null, failure: { kind: 'crash', detail } … }` shape and a `trace.note`. The detail names the deny path and the root it covers.

`invocation()` records the profile argv even where `run()` would refuse, because it cannot refuse. The two still cannot drift on any run that actually spawns.

**Checking whether a deny covers a root.** Put it in a pure exported helper: `denyCoveringRoot(paths, roots, home): { path; root } | undefined`.

- The roots are `writable ∪ {request.cwd}`, all already absolute.
- A key qualifies only if it is a literal path. That means it starts with `/`, or it starts with `~/`, which is expanded against `request.env.HOME` (never `process.env.HOME`; if HOME is unset, skip the key). It must also contain none of `*?[{`.
- Keys starting with `:` and glob keys are copied without the check.
- Compare after `path.resolve`, using `root === p || root.startsWith(p + sep)`.
- Run the check on writable roots for both roles. A reader's writable list is empty, so for a reader only `cwd` matters.

### 5. Gotchas

- **`gitWritableRoots` has a side effect.** It creates `<common>/logs` (doc comment at `:1003-1009`), and both callers already invoke it through `writableFor`. Leave that alone; this change neither adds that call nor removes one.
- **`run()` now reads `config.toml` twice:** once for the model (`:1242`) and once here. This is a sub-kilobyte file, so leave it. Sharing the text between the two would put file I/O inside the pure path.
- **No ADR changes.** 0106's role mapping holds, because `:workspace`/`:read-only` measured the same as today's `--sandbox` modes (the ticket's table).

### 6. How to check it

Every claim here is a unit-level claim, made either against `userPermissionsFrom`, `denyCoveringRoot` or `codexArgv`, or against `createCodexRuntime({ binary: <stub> })`, which the existing `codex.test.ts` already drives.

The *invocation and run build the same argv* test should write a `config.toml` under a temp `HOME`, the way that file's existing run tests set up the environment. Check that it stays green under `HOME=/nonexistent pnpm test`.

Nothing here needs `pnpm test:integration`. Whether Codex actually enforces the profile is the paid probe, which the ticket puts out of scope. The person running it after the merge would see the profile argv in the run's recorded `args`, written from `invocation()`.
