# #578 — what the change looks like

Most of this ticket is find-and-replace. Two parts are not: where the `ByPerson` release gets appended, and how `answer` and `close` take the lock without moving their unit tests into the integration half. The rename also reaches about 30 files, not the dozen the ticket lists.

## 1. Append the `ByPerson` release in `resolveWaitHolding`, not in its callers

Put the append inside the one `store.append` in `packages/conductor/src/resolve-wait.ts:351-362`, between `WaitResolved` and `...(options.with ?? [])`. Add it when both of these hold:

- the resolution is `Requeue` or `EditBodyAndRequeue`, and
- `block.runId !== null`.

```
WaitResolved{Requeue|EditBodyAndRequeue}
TicketReleased{ runId: block.runId, reason: <sentence>, cause: { _tag: 'ByPerson', waitId: options.waitId } }
...with
```

Do it here rather than in `requeueHolding` (`approve.ts:340`) and `editBodyAndRequeueHolding` (`edit-body.ts:211`). The file's header says it is *"The only writer of `WaitResolved`"* (`resolve-wait.ts:4`). If the release lives beside that write, every requeue path gets it, including the next one somebody adds. It also lands in the same version-checked append as the resolution, so the two cannot come apart.

**Only when a run is held.** `TicketReleased.runId` is a required `z.string()` (`packages/domain/src/events.ts:231`). An `OwnQuestion` has no run: `ticket.ts:333` sets `runId: 'run' in d.reason ? … : null`. Withdrawing a question, or answering one with `AnswerQuestion` (only an `OwnQuestion` offers it, `ask.ts:143-145`), releases no claim, so nothing is appended. That matches the board's `released` branch, which accepts only `Requeue`/`EditBodyAndRequeue` (`apps/board/src/lib/task.ts:794`).

**Who reads it, and what they will see now:**

- **The fold:** `TicketReleased` sets `lifecycle: backlog` and adds to `restarts` only when `d.cause?._tag === 'Restart'` (`packages/domain/src/ticket.ts:313-316`). `answers`, which the `WaitResolved` case just wrote, is not touched. So the order above leaves the fold's state as it is today, apart from `version`.
- **`task_view`:** the `TicketReleased` case writes `note: d.reason` and writes `restarts` only for `Restart` (`packages/projector/src/task-view.ts:270-285`). Today `WaitResolved` leaves `note = null` (`task-view.ts:665`). After this change, **the queued card shows the release's `reason`**, so write it as the sentence a person should read there.
- **The task page:** for a held run, the move now resolves through `released` rather than `requeued`. `latestLifecycle` becomes the `TicketReleased` (`task.ts:577`, `task.ts:782-791`), and the line rendered is `` `${reason} A new pass starts from base.` `` (`task.ts:833`). So `reason` must be a full sentence ending in a period. Use `` `Requeued by ${by}.` `` (for `EditBodyAndRequeue`, `` `Requeued by ${by} with an edited body.` ``). Don't put `note` in it: the note is already shown beside it as `move.note`.
- **The attempt record:** `attempts.ts:199-203` sets `ended = reason` on the held run's attempt. `conduct.ts:1098` logs that line on the next attempt.
- **Restart counting:** nothing that counts restarts reads `ByPerson`. `conduct.ts:1118` uses `folded.restarts.length`, and `conduct.ts:4117` uses `folded.restarts.length + 1`; both come from the fold above. `releaseCauseOf` (`packages/domain/src/read-model.ts:136`) has no production caller.

**The test the Watch out row asks for** goes in `packages/conductor/unit/resolve-wait.test.ts`, on the memory store. Set up a blocked run whose stream already carries one `TicketReleased{cause: Restart}`. Then call `resolveWaitHolding` with `Requeue`, and assert:

- `reduceTicket(...).restarts` has the same length before and after;
- `releaseCauseOf` ends `{_tag: 'ByPerson', waitId}`;
- an `OwnQuestion` requeue appends no `TicketReleased`.

That fold is what `conduct.ts:1118` reads, so it is the unit-level claim for "restarts-left is unchanged". `task_view`'s `restarts` column is the same rule on Postgres (`task-view.ts:285`), and a test there would be `packages/projector/integration/`, which is out of reach inside a pass.

**Tests that will now fail are expected to.** Any test asserting the exact list of events a requeue appends will now see one more. Places to look: `resolve-wait.test.ts`, the `requeueHolding` and `editBodyAndRequeueHolding` tests, and `wait-handlers-answer-as-today.test.ts`. Update the expectation. Don't special-case the code to keep them green.

## 2. Lock `answer` and `close` the way `approve` and `requeue` do

Use the split already in the codebase. The public function takes `deciding` (exported from `approve.ts:27`, and already imported by `edit-body.ts`) and calls an exported `*Holding` function that does all the work:

- `answer()` → `deciding(ticketId, busy, () => answerHolding(options, store, ticketId))`
- `close()` → `deciding(ticketId, busy, () => closeHolding(options, store, ticketId))`

**Why the split is required, not optional:** `createFileLocker()` is the filesystem. By 0060 §1, a unit test that reaches it belongs in the integration half. `approveHolding`'s own comment says so: *"`approve()` above takes `createFileLocker()` … so by 0060 §1 the whole of `approve()` cannot be unit-tested — this function underneath it can"* (`approve.ts:115-119`). Today `packages/conductor/unit/close.test.ts:196,215,227,254,314` call `close()`, and `wait-handlers-answer-as-today.test.ts:116,122` call `answer()`. Point those calls at the `*Holding` variants. Don't export the `*Holding` functions from `index.ts` (`index.ts:84-85` stays `answer`, `close`), for the reason `approve.ts:117-119` gives.

**How far the lock reaches:**

- **What stays outside it:** the argument checks that read nothing (`'an answer needs an answer'`, `ask.ts:134-136`; `'a close needs a reason'`, `close.ts:118-120`).
- **What goes inside it:** everything from the `store.read` onward, including `close`'s recipe read and its `tellGitHubAbout`. `editBodyAndRequeue` already holds the lock across GitHub I/O (`writeSection`, `edit-body.ts:204`), so that has a precedent.
- **Unblocked closes too:** `close` takes the lock even when the item is not blocked (the `else` branch at `close.ts:193`). An approval that is mid-flight is exactly what a close must not run beside.

**Comments to change with it:**

- Delete `ask.ts:171-173`: *"`answer` never took the decide-lock `approve`/`requeue` do … so it calls the unlocked half directly rather than gaining one now"*.
- `resolve-wait.ts:84-104` carries a private copy of `deciding`. Leave it; folding the two copies together is not this ticket.
