# Design: #1128, a stored expiry under `claude auth status`

## Where it goes

All of the change is in `packages/agent/src/auth.ts`, and no caller changes. Every sign-in question the ticket lists already reaches `claudeCodeAuthEffect` (`auth.ts:168`):
- `createClaudeCodeRuntime().checkAuth` calls `claudeCodeAuth` (`claude-code.ts:423-425`). That covers `signedInHere`/`signedInProbe` (`projects.ts:150-152`) and the doctor.
- Setup goes through `AUTH_PROBES['claude-code']` (`auth.ts:216-217`).

If the Effect gets the answer right, all of them do. Leave `claudeCodeAuth`'s and `AUTH_PROBES`' signatures as they are.

The file header says it imports "nothing but `node:child_process`" (`auth.ts:4-9`). The reason it gives is that it must not pull in `@lingtai/event-store`. Adding `node:fs/promises`, `node:os` and `node:path` keeps that reason intact. Change the sentence to say *nothing but Node built-ins*.

## Three pieces, so the order and the judging are unit tests

1. **`withStoredExpiry(status: AuthStatus, stored: StoredExpiry, now: number): AuthStatus`**. This is pure. It applies only when `status.state === 'signed-in' && status.method === 'claude.ai'`. In every other case it returns `status` unchanged.
   - A `stored` of `{ kind: 'expires', at }` with `at <= now` gives `status('signed-out', …, 'claude.ai')`.
   - Anything else returns `status` unchanged.
   - Leave `classifyClaudeAuth` as it is. The ticket's `(ProbeEnd, stored, now)` shape is `withStoredExpiry(classifyClaudeAuth(end), stored, now)`, and that is how the tests call it.
   - Keep the store's condition in one exported predicate, `needsStoredExpiry(status)`. The orchestrator uses the same predicate, so the two cannot drift.

2. **`claudeAuthThenStore(askStatus: Effect<ProbeEnd>, readStore: Effect<StoredExpiry>, now: () => number = Date.now)`**. It classifies first. If `needsStoredExpiry` is false it returns without ever yielding `readStore`. Otherwise it yields `readStore` and judges.
   - `claudeCodeAuthEffect(binary, env)` becomes this function, with `probe(binary, ['auth','status'], env)` and the real reader.
   - The recording-reader test hands in `Effect.succeed(end)` and a `readStore` that pushes to an array. That needs no fake child process and no clock, and it is how the Done-when on order is met.
   - Taking `now` as a parameter follows `signedInProbe`'s `now: () => number = Date.now` (`projects.ts:142`).

3. **`readClaudeStoredExpiry(env)`**. This is IO and has no unit test.
   - **Keychain**, on `process.platform === 'darwin'` only. Use the existing `probe('security', ['find-generic-password', '-s', 'Claude Code-credentials', '-w'], env, { timeoutMs: 5_000 })`, the same helper `runtimeVersionEffect` uses with 5 s (`auth.ts:148-149`).
     - Use the probe's own `env`, not `process.env`. `runnableEnv` passes `USER`, and its docstring says that is what lets macOS find the item: "macOS finds a keychain item by who is asking" (`agent-env/src/index.ts:134-140`).
     - The Keychain wins only when `security` exits 0 **and** the output parses with a `claudeAiOauth` object. Otherwise fall through to the file.
     - If the Keychain JSON has `claudeAiOauth` but no usable `expiresAt`, the answer is `unreadable`. Do **not** fall through to the file: 017 shows the desktop session's Claude Code ignores the file when the Keychain holds a login (017 §*Claude Code's login in the macOS Keychain*).
   - **File**: `join(env.HOME ?? homedir(), '.claude', '.credentials.json')`, read with `Effect.tryPromise(() => readFile(p, 'utf8'))`.
     - Use `env.HOME` because that is the HOME `claude` itself was given. It also makes `HOME=/nonexistent pnpm test` see `unreadable` and never the operator's login.
   - Never write `async`. `effect-ratchet.baseline.json` must not move. An arrow handed to `Effect.tryPromise` is not counted.
   - Both stores go through one pure parser, `expiryFromCredentials(text): number | null`. It returns `claudeAiOauth.expiresAt` only when that is a finite number. Exporting it lets the token-absence test feed it directly.

`StoredExpiry`:

```
{ kind: 'expires'; at: number; from: 'keychain' | 'file' }
| { kind: 'unreadable'; why: string }
```

Include `from` in the signed-out detail. Then a person sees *which* store is dead, which is how one machine can be signed in over SSH and dead in the desktop session. Example detail:

`signed in via claude.ai, but the token in the Keychain expired at 2026-01-29T…Z and did not refresh — sign in again: run \`claude\`, then /login`

## The trap: where the secret can leak

`security -w` prints the item's whole data, access and refresh tokens included, into `ProbeEnd.out`.
- That `ProbeEnd` must **never** reach `classifyClaudeAuth`, `unreadable()`, or any helper that slices `out` or `err` into a detail. `classifyClaudeAuth` does exactly that, at `auth.ts:54` and `:60`.
- **A `JSON.parse` error message carries a fragment of its input.** Current V8 quotes the text it choked on (`… "eyJ…" is not valid JSON`). So `why` must be a fixed phrase chosen by the code, never `String(e)`, `e.message`, `out` or `err`. Fixed phrases look like `security exited 44`, `no claudeAiOauth.expiresAt`, `file unreadable (ENOENT)`. The errno code is safe; the message is not.
- `why` is never shown in a signed-in result anyway. It exists for a reader's own debugging. Do not put it into the unchanged status's `detail` either, because that would change today's output for a case the ticket says stays as it is.

The token-absence test feeds `expiryFromCredentials` and `withStoredExpiry` a credentials blob with a distinctive `accessToken`/`refreshToken`. It also feeds a malformed blob containing the same strings. Then it asserts that neither string appears in `JSON.stringify` of any result.

## Decisions the ticket left to the design

- **The comparison is `at <= now`.** A token expiring exactly now is expired. There is no margin, as the ticket says.
- **`loggedIn` on the result follows `state`**, through `status()` (`auth.ts:28-29`), and `AuthStatus.state`'s comment requires that (`runtime.ts:252`). So `signedInProbe`'s `auth?.loggedIn` (`projects.ts:152`) drops Claude Code with no edit there.
- **This changes detection, on purpose.** "Detection is allowed only when exactly one is signed in" (`projects.ts:128-131`). A machine with an expired Claude Code login and a live Codex login now detects Codex. A recipe that names `runtime.agent` does not detect. Say this in the commit body. Nothing else needs to change for it.
- **Cache:** `signedInProbe`'s 60 s TTL (`projects.ts:141`) already covers the extra read. No change.
- **Docstring at `auth.ts:156-167`:**
  - Drop *Free — it reads the credential and does not call the API.* Replace it with what 017 measured: `auth status` may refresh a refreshable token, which is a call to `platform.claude.com` though not to the model (017 case F). It answers `loggedIn: true` for a token that expired and cannot refresh (017, Keychain section).
  - So the store is read **after** it, and the reason is that reading before would sign out every login that is merely due for refresh.
  - Keep the paragraph about the exit code.

## What checks it

The whole change is unit-checkable. Its tests are `packages/agent/unit/auth.test.ts`, next to the existing `classifyClaudeAuth` block:
- the five `withStoredExpiry` cases from Done when;
- the order and skip assertions through `claudeAuthThenStore`;
- the token-absence test.

Nothing here needs `pnpm test:integration`. The reader is IO with no test, so its only check before the merge is `pnpm typecheck`. In use, it is checked by `lingtai doctor`'s Claude Code line on a machine with a dead Keychain login, which no pass can reach. No event is added: this is a probe, and nothing is appended.
