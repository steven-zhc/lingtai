# Design: #1203 — the Ticket owner's first three commands

## 1. Reaching `readThroughSnapshot` without the barrel

`readThroughSnapshot` is only exported from the barrel today (`packages/event-store/src/index.ts:43`). No subpath in `packages/event-store/package.json` `exports` reaches `snapshot-read.ts`. The owner may not import the barrel: the *Done when* line says "its only `@lingtai/event-store` imports are `/store` and types".

**Decision: re-export `readThroughSnapshot` and `type SnapshotReadOptions` from `packages/event-store/src/event-store.ts`, the `/store` module.**

- This is safe. `snapshot-read.ts`'s only runtime imports are `@lingtai/domain` and `effect` (`snapshot-read.ts:18-22`), and `event-store.ts` already imports `@lingtai/domain` at runtime (`event-store.ts:15-27`).
- The import cycle is type-only. `snapshot-read.ts` imports `type EventStore` from `./event-store.ts`, so nothing is constructed.
- Leave the barrel's own export at `index.ts:43` alone. Eleven other files import it from there.
- Rejected: a new `./snapshot-read` subpath. It would be a second module for the owner to import, and it breaks the *Done when* wording.

`ConcurrencyError` already comes from `/store`, as `packages/project/src/commands.ts:21` does it. Take `ticketReducer` from `@lingtai/domain` (`packages/domain/src/ticket-codec.ts:170`).

## 3. The transitions, and where the GitHub read sits

The new code in `packages/domain/src/ticket.ts`, after `reduceTicketEvent` (`:426`), is three functions. Each returns `ToAppend<…>` or a refusal value:

- `claimTransition(state, { runId, worker, title, kind, body?, children })`
- `continueTransition(state, { runId, worker, body? })`
- `releaseTransition(state, input)` — see §4.

Move the refusal unions into domain, without `lost-race`:
- `ClaimRefusal`'s five deciding variants (`claim.ts:86-100`).
- `ContinueRefusal`'s `not-approved` and `wrong-run` (`claim.ts:217-223`).
- `SplitChildState`.

The owner's `ClaimRefusal` is then the domain's union plus `{ reason: 'lost-race' }`, and the same goes for `ContinueRefusal`. A lost race is a fact about the append, not about the state, so a transition never sees one.

**The split children are read in the command, and only where today's code reads them.** Today the read happens only after `held` and `not-claimable` have passed (`claim.ts:130-140`), and only when `state.split !== null && options.children !== undefined` (`:142`). Asking GitHub about a held ticket would be a new network call on every pass that finds one. So the command:

1. Reads the state.
2. Fetches the children only when `state.lifecycle.status === 'backlog' && state.split !== null && options.children !== undefined`.
3. Hands the transition `children` as one of three shapes:
   - `null` — not asked.
   - `{ unreadable: detail }` — the read failed.
   - `{ read: { number, state: 'open' | 'closed', stateReason }[] }`

The transition then checks, in today's order: `held` → `not-claimable` → `split-unreadable` / `split-open` / `split-done` → the `TicketClaimed` payload. It repeats the backlog and split checks itself; the command's condition only decides whether to spend the read. Note that `split-done` carries `state.version`, as at `:164`.

Keep exactly the `Effect.result` / `Effect.tryPromise` shape around the children read (`claim.ts:150-160`) and around the append (`:177-199`). `conduct.ts:2802-2810` treats any failure of the claim effect as `mayHold`. A defect that escaped `Effect.result` would leave an item held by nobody (comment at `:173-176`).

## 4. `release`: one transition, two inputs, and the kill passed in as a hook

There are two releases today, and they must stay byte-for-byte the same events:

- **`conduct.ts`'s release** (`claim.ts:286-307`) has no check. It appends `{ runId, reason, cause }` at the version it read, with no lost-race handling, so a `ConcurrencyError` fails the effect. `conduct.ts:1626-1631` reads that failure as "not released".
- **`releaseOne` in `reconcile.ts`** runs four steps inside `Effect.uninterruptible` (`reconcile.ts:672-673`, #87):
  1. Reads the state.
  2. Refuses if the status is not `claimed` or the worker is `mine` (`:681-686`).
  3. **Kills the worker** (`:694`).
  4. Appends at the version from step 1, with `runId: life.runId`, the reason sentence at `:704`, and `cause: null` (`:698-711`).

**The input is a union:**

```
| { by: 'run', runId, reason, cause: ReleaseCause | null }
| { by: 'dead-worker', mine: string, lock: string }
```

- The `'run'` variant never refuses.
- The `'dead-worker'` variant refuses `{ reason: 'moved-on', status, worker? }` when `status !== 'claimed' || worker === mine`. Otherwise it builds the `TicketReleased` payload itself: `runId` from `state.lifecycle.runId`, reason `` `${mine} holds ${lock}, so ${worker} was not coming back` ``, and `cause: null`.

That reason is the dead-worker rule's own sentence, so it moves into the domain. `reconcile.ts` passes `lock: DAEMON_LOCK_KEY`.

**The kill must stay between the guard and the append, against the same read.** If reconcile called the owner after the kill, the owner would re-read and append at a newer version. That silently turns today's "could not release" (a `ConcurrencyError`, caught at `:714-720`) into a success. If reconcile killed before calling the owner, it would kill a worker on a guard it decided itself, which is the duplicate check this ticket removes.

So `releaseTicketEffect` gets an optional last argument, `{ beforeAppend?: (held: TicketClaim) => Effect.Effect<void, unknown> }`. The owner:

1. Reads the state.
2. Runs the transition. On a refusal it returns `{ ok: false, refusal }` and does not call the hook.
3. Runs `beforeAppend` with `state.lifecycle`.
4. Appends at the version it read.

`releaseOne` keeps four things:
- its `Effect.uninterruptible` around the whole owner call;
- its `catchCause` (`:714-721`);
- the `moved-on` mapping to `f.action = 'reported'` with the existing "(claimed again before it could be released)" text;
- `killWorkerEffect` and the `fate` logging, inside the closure it passes as `beforeAppend`.

Process IO stays in `reconcile.ts`, as the ticket's Edges ask.

**The return type changes:** `releaseTicketEffect` returns `{ ok: true } | { ok: false; refusal }` instead of `void`. `conduct.ts:1626` only looks at `Result.isFailure`, so it needs no edit; a `'run'` release never answers `ok: false`.

After this, `reconcile.ts` imports neither `parsePayload` nor `TicketReleased`. Drop them if nothing else there uses them. Its `readThroughSnapshot` import goes too if `releaseOne` was its only user — check before removing.

## 5. What is out of reach before the merge, and the unit claims that stand in

These are integration-only, so `pnpm test` will not run them:
- `packages/conductor/integration/claim.test.ts`
- `packages/daemon/integration/shutdown.test.ts`
- reconcile's own tests under `packages/daemon/integration/`

The orderings that matter therefore need unit tests in `packages/conductor/unit/`, using `createMemoryEventStore()`:
- A `dead-worker` release whose `beforeAppend` appends to the same stream fails with the `ConcurrencyError`. It must not succeed on a re-read.
- A `moved-on` refusal never calls `beforeAppend`.
- A `held` claim with `children` given never calls `getIssue`.

The transition tests the ticket lists go in `packages/domain/unit/`.
