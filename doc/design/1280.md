## Design note: #1280, a person's fix round counted from the step it started

### The decision the ticket leaves open: what ties a `StepStarted` to a grant

The ticket says to count a person's round "from the event that raises `implementRound` for it". That event is `StepStarted{step: 'implement'}`: `attempt.ts:610` raises `implementRound` to `Math.max(state.implementRound, d.round)`. But `StepStarted` cannot name a grant today. Its payload is `runId`, `step`, `round`, `startedAt` and nothing else (`events.ts:1319-1329`). So the reader alone cannot tell which `StepStarted` a person's `waitId` paid for, and matching rounds to waits across the ticket and run streams by order is guesswork.

**So `StepStarted` gains an optional `grant: WaitId`, with the same meaning `SpentFor.Action.grant` already has.** Its doc says (`events.ts:670-672`): *"`Action.grant` names the person's decision that paid for the round — the `waitId` of the `WaitResolved{FixRefusal}` it spent. It is absent on every automatic round, and optional so a payload written before it existed still parses."* Copy that sentence onto the new field.

- **Additive and optional**, the way `startedAt` was added (`events.ts:1322-1327`, *"Absent on a row written before it existed"*). No stored event is rewritten.
- **No reducer version bump.** The attempt reducer does not read the field. `personFixRoundsOf` reads the raw run events (`read-model.ts:412-418`), not reduced state, so `run-codec.ts` and the snapshot are untouched. If you find yourself bumping a reducer version, the shape has gone wrong.

### The writer: `run-attempt.ts`

The `StepStarted` emit is at `packages/conductor/src/run-attempt.ts:2459-2469`. It sits inside the step's span, before the pipeline runs: *"the visit begins at the `StepStarted` write"* (`:2455`). That is exactly the point the ticket wants counted, since a settings-preparation failure comes after it.

`runAttempt` does not have the `waitId` today. `from.grant` is a `SentBack`, a why/asked/printed record (`run-attempt.ts:1102-1103`), and the wait id is only on the conductor's `continuation.resumedWaitId` (`conduct.ts:1730`). Thread it through:

- Add one field to `AttemptOptions['from']`, e.g. `grantWait?: WaitId`.
- Set it in `conduct.ts` beside the existing `grant` (`:1748`), and only for a person's grant. Use the same exclusion the dispatch already applies at `conduct.ts:5437`: `continuation?.grant && !continuation.byTriage`. A triage grant's `StepStarted` carries nothing, so `read-model.ts:422`'s *triage's own rounds still counted* stays as it is.
- Write `grant` on the `StepStarted` of the first `implement` visit of that continuation. Use the condition the `again` context already uses for "the visit the grant is consumed on" (`run-attempt.ts:3056-3060`): `spec.step === 'implement' && options.from?.step === 'implement' && !reached.some(v => v.step === 'implement') && options.from.grant`.

### The reader: `personFixRoundsOf`

The `ran` set becomes the union of two sources:

1. **New:** every `StepStarted` whose `grant` is set.
2. **Kept:** every `RunPrompted`/`RunSpent` whose `for.grant` is set (`read-model.ts:414-418`).

The second source stays for one reason only: an attempt stream written before this change has no `grant` on its `StepStarted`, and dropping that path would charge its past person rounds to triage. Everything after `ran` stays as it is (`:419-426`). Update the doc comment at `:405-411`: it currently says a grant counts *"only once its fix round was dispatched"*, which is the behaviour this ticket removes.

**Each grant counts once.** That comes from `ran` being a `Set` of `waitId`s, not from counting events. Three cases repeat the step under one grant:

- **A rerun in place in the same process (#1201)**: rebuilds `visitContext` from `rerun.context` (`run-attempt.ts:2384-2385`) and emits another `StepStarted`.
- **An account-limit redo**: a new continuation whose `resumedWaitId` is `account-limit:…` (`conduct.ts:1533`), so its `StepStarted` carries no grant at all.
- **An answer continuation** (`run-attempt.ts:2398-2410`): same as the redo.

Whether the rerun's `StepStarted` repeats the `grant` or omits it, the count stays at one. So don't try to suppress the field on a rerun; the set handles it.

### Callers

The callers stay as they are, as the ticket says: `continuationSpentWithTriage` (`conduct.ts:833-854`) and `readActContext` (`apps/cli/src/triage.ts:890`). One thing to check: `triage.ts:882` reads `runEvents` with `deps.store.read(runId)`, which is the whole stream, so the new `StepStarted`s are in it. A read that fails goes down the Effect's error channel, as now, and is never taken as zero.

### Tests

All unit tests; none needs the integration half.

- **`packages/domain/unit/read-model.test.ts`**, the reader. Each case builds a ticket state with one resolved person `FixRefusal` and a run stream:
  - `StepStarted{implement, round: 1, grant}` with no `RunPrompted` → 1. The pre-fix code gives 0, so this is the red that proves the fix.
  - The same `StepStarted` twice plus a `RunSpent{for.grant}` → 1. This is the ticket's rerun case.
  - A legacy stream: `StepStarted` without `grant`, plus `RunPrompted{for.grant}` → 1.
  - A triage resolution with a `StepStarted{grant}` → 0.
- **`packages/conductor/unit/continuation-spent-with-triage.test.ts`** (or `triage.ts`'s own test): the ticket's first box. Build the same stream (grant, `StepStarted{implement}`, failure before `RunPrompted`), and with `implementRound: 1`, `refusalFixes` comes out 0.
- **The writer.** A test in `packages/conductor/unit/run-attempt.test.ts` or `what-an-attempt-writes-today.test.ts`:
  - a continuation with a person's grant writes `StepStarted{implement}` with `grant` set to that wait's id;
  - a triage grant writes it without one.

  Without this, the reader tests pass against a field nothing writes.

`effect-ratchet.baseline.json` must not move. The reader is a pure function, and the writer change is a payload field inside an existing `Effect.gen`.
