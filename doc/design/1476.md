## Shape for #1476

The change sits in two places that do not depend on each other. One is the absent path of `askRecipeEffect` (`apps/cli/src/recipe-flow.ts`). The other is the discuss half of the `discuss`/`triage` loop in doctor's `declaredEnvironment` (`apps/cli/src/doctor.ts:3633-3674`). Nothing in `packages/recipe` changes, and neither does the schema or any ADR.

### 1. Init: one seam, one push

**`codex_text` comes in through a seam, not a direct read.** `RecipeAt` (`recipe-flow.ts:62-117`) says it is "Already probed — this function never probes on its own" (`:66`). Give it an optional `codexText?: () => CodexTextConfig | undefined` that defaults to `() => codexTextConfig()`. This is the same name and type doctor already uses: `LookupReach.codexText` (`doctor.ts:1290`), with the same fallback `reach.codexText ?? (() => codexTextConfig(env))` (`doctor.ts:3670`). Tests inject it. Production callers leave it out. A unit test does not reach the operator's file, because `codexTextConfig` says "tests never read the operator's file" (`packages/env/src/index.ts:198`). It does throw on an unreadable machine file (`:203`), so wrap the call as `try { … } catch { undefined }` at the point of use. This is the ticket's "treated as no `codex_text`". Doctor's own `codexRoleRow` catch (`doctor.ts:3385-3398`) still reports the read failure, because it calls the same function again. Nothing is lost by not reporting it here.

**Where the push goes.** Put it right after `collected.push(...agents.changes, ...agents.modelChanges)` (`recipe-flow.ts:353-354`), inside the same `if (absent)`. The existing-file branch (`:355-360`) gets nothing. A refusal from `askAgents` returns before this point (`:352`), so the push only runs when a writer was chosen. "Nothing signed in" is therefore unchanged (`agents.ts:204-206`).

**"claude-code is not signed in"** means `at.runtimes.find((r) => r.id === 'claude-code')?.signedIn !== true`. That covers both cases: probed and signed out, and not in the list at all (not installed). It is the same `signedIn` field `askAgents` filters on (`agents.ts:197`).

**codex's own CLI login is not part of the condition.** The ticket's Fix row conditions on claude-code and `codexTextConfig()` only. The model-only route is "separately billed" (`doctor.ts:3378`) and is reached without the Codex CLI ("never probe the Codex CLI as a substitute", `doctor.ts:3370`). So do not add `codex.signedIn` to the condition. The "codex signed in" in the first Done-when test is only the F2 setup.

**The change itself:** `{ path: ['discuss', 'agent'], value: 'codex' }`. Write no `discuss.model`. `codexRoleRow` fails a model that differs from `config.model` (`doctor.ts:3372-3379`), and an absent one passes.

**Comment for the new block.** Every block of a new file gets a sentence from `SAID` (`packages/setup/src/setup-answers.ts:46-62`, "The sentence above each block of a new file, keyed by its dotted path"). Add a `discuss` entry, for example `discuss: 'who answers when a ticket is discussed'`. The cost: `apps/cli/unit/add-github.test.ts:366-375` walks every `SAID` key and allows only `['steps.proposed', 'runtime.limits', 'sandbox', 'repo']` to be missing. Add `'discuss'` to that list. Its `:387` assertion `expect(doc.getIn(['discuss'])).toBeUndefined()` stays true, because that test's machine does not take the codex branch. Do not "fix" that assertion. It pins the signed-in edge.

**What stays unchanged.** The claude-code-signed-in path writes nothing, so `init-golden.fixture.json` and its test should not change. If the golden diff moves, the push landed on the wrong side of the condition.

### 2. Doctor: degrade on the recipe's shape, read from `resolved.source`

**"Declares `discuss:`" is a fact about the file's text, not the resolved recipe.** `resolved.recipe.discuss` is always present (`Discuss.default(DISCUSS_DEFAULTS)`, `recipe.ts:3334`). `ResolvedRecipe.source` is "The raw file, kept so a diff against a later version is possible" (`packages/recipe/src/resolve.ts:112-113`), and it is already in hand inside the loop. Parse it with `yaml`'s `parse` and check `'discuss' in` the top-level record, using the `asRecord`/`isRecord` style `resolve.ts:356-362` uses for raw-key questions. Do not re-read the recipe file, and do not use `provenance`. That field exists only for `resolveLocalRecipe` (`resolve.ts:117-121`), so a GitHub project's recipe has none.

**A preset cannot hide a declaration.** `extends:` cannot supply `discuss:`, because no preset mentions it (`grep discuss packages/recipe/src/presets.ts` returns nothing). The raw text is the whole answer.

**The degrade.** Apply it in the `else if (selected)` branch (`doctor.ts:3672-3674`), and only when `role === 'discuss'`, the file has no `discuss` key, and the row `dispatchedAuthRow` returned has `status: 'fail'`. In that case keep `name` and `detail`, set `status: 'warn'`, and replace `title` with the card's sentence: discussions need claude-code signed in, or `codex_text` configured. Everything else is passed through as is:
- `skip` ("cannot be asked cheaply", `doctor.ts:3321-3323`) stays `skip`.
- A declared `discuss:` keeps `fail`.
- The `codexRoleRow` branch is not touched. Init writes `discuss.agent: codex` only when `codex_text` exists, so a failing codex row means the person declared it.

Pull the rule out as a small exported pure function next to `codexRoleRow`, for example `defaultDiscussRow(row, declared)`. That way the shape-versus-status pin is one table test, separate from the probe.

**What the card does with it.** `renderReadyLine` already reads a warning as ready (`setup-card.ts:287-289`: `failed` gives "not ready", `count > 0` gives "✓ ready · N to fix"). So once the row is `warn`, the card is ready and the new title is the line it shows. Nothing in `setup-card.ts` changes.

### Tests, and what stands in for the integration half

Everything above can be checked at unit level. No step's only check is `pnpm test:integration`.

- **Init:** `apps/cli/unit/recipe-flow.test.ts`. Use fake `runtimes` with claude-code `signedIn: false` and codex `signedIn: true`, plus an injected `codexText`. Cover three cases: returns a config, returns `undefined`, throws. Assert on the written text: `discuss.agent === 'codex'` and no `discuss.model`, or no `discuss` key at all.
- **Doctor:** `apps/cli/unit/doctor-titles-projects.test.ts` already drives `declaredEnvironment` with `recipe: recipeOf(RECIPE)` and fake `runtimes` (`:183-196`, `recipeOf` at `:138`). Add two recipe texts, one with and one without `discuss: { agent: claude-code }`, and a claude-code runtime whose `checkAuth` answers signed out. Assert only `status` (`warn` versus `fail`) on the `discuss: alpha signed in` row, not its wording, as the Edges ask.
- **Card:** a `renderReadyLine` case on a report whose only finding is a `warn` (`toFix: { count: 1, failed: false }`) covers "the card is ready" without starting `init`.

The real-machine F2 check is the only thing that settles the end-to-end claim. On the log side it is the `ProjectConfigured` event that init's write records (`resolve.ts:107`). Its `configHash` changes only on the codex path, so a `ProjectConfigured` from a machine with claude-code signed in that carries a new hash for an unchanged recipe would mean the push leaked onto the signed-in path.

### Ratchet

Both additions are plain synchronous code inside existing `Effect.gen` bodies: a `try`/`catch` around a sync function, and a YAML parse. Neither adds an `async` function or an `Effect.run*`, so `effect-ratchet.baseline.json` does not move.
