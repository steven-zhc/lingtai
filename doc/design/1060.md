# #1060: design note for `ticket new --title`

The ticket settles what the command does. This note settles three things it leaves open: how the stdin read fits under the ratchet, where each check runs, and how the flag values are normalised.

## 1. The flag path is one Effect, run once inside `ticketNew`

`apps/cli` is at `{ "async": 410, "run": 6 }` (`packages/domain/unit/effect-ratchet.baseline.json:2`). The ratchet counts the `async` modifier on any function, arrows included (`effect-ratchet.test.ts:132`). Its run pattern is `/^run[A-Z](?!\w*With$)/` (`effect-ratchet.test.ts:70`), so a `runPromiseWith` is not counted. That is why `runEffect = Effect.runPromiseWith(Context.empty())` exists, at `project-pause.ts:60` (*"The run the ratchet does not count"*) and again at `first-project.ts:1256`.

The shape:

- Add `newFromFlags(flags, log, reading)` to `ticket.ts`. It is an `Effect.gen` that returns the exit code.
- `ticketNew` keeps its `async` signature. Its first statement is `if (options.title !== undefined || options.label !== undefined || options.body !== undefined) return runEffect(newFromFlags(…))`, with `runEffect` imported from `./project-pause.ts`. The existing editor body underneath does not change.
- Inside the Effect, call the existing promise helpers through `Effect.promise(() => pickProject(…))`, `Effect.promise(() => resolveDbRecipe(…))`, `Effect.tryPromise(() => ticketsFor(name))` and `Effect.tryPromise(() => tickets.createIssue(…))`. Each wrapper is an arrow returning a promise, not an `async` arrow, so nothing is counted. `pickProject` and `resolveDbRecipe` log and return `null` rather than reject (`ticket.ts:530-535` treats a falsy result as "already said why, exit 1"), so `Effect.promise` is right for those two.

**The stdin seam is a stream, not a reader function.** Add `stdin?: NodeJS.ReadableStream & { isTTY?: boolean }` to `TicketReading` (`ticket.ts:56-62`), defaulting to `process.stdin`, and read it with `Effect.tryPromise(() => text(stream))` from `node:stream/consumers`. That gives three things:

- No `async` arrow anywhere. A reader written like `readValueFromStdin` (`env.ts:77`) would need `for await`, which means a new `async` function.
- The TTY refusal can be checked in `newFromFlags` itself (`if (stdin.isTTY) …`), so a unit test reaches it by passing `{ isTTY: true }`. A test of a fake reader that throws would test nothing.
- The happy-path test passes `Readable.from(['the body\n'])`, which is in memory and stays in the unit half.

Do not copy `env.ts`'s `replace(/\r?\n$/, '')`. The body gets the form's `trimEnd()` (`ticket.ts:459`), and that already covers the trailing newline.

## 2. Order of checks, and where each one lives

All refusals live in `ticket.ts`, not `cli.ts`, so the unit tests reach them. `cli.ts` only carries the raw strings. `--body -` reaches the runner as the literal `'-'`, which is what the parser test in the ticket's *Done when* asserts. `given()` (`cli.ts:239`) keeps `''` as `''`, so `--title ''` arrives as an empty string rather than `undefined`, and the empty-title refusal does not fall through to the editor path.

Inside `newFromFlags`, in this order:

1. **Checks that need no IO.**
   - `--label`/`--body` without `--title`: refused by name.
   - An empty title after trimming: refused with `a ticket needs a title`, with the editor path's `— your text is kept…` clause removed (`ticket.ts:563-565`).
   - Then `titleAndLabelsRoundTrip({ title, labels: labels.map((name) => ({ name })) })` (`ticket.ts:500`). Its parameter takes labels as `{ name }` objects, so map them first. A non-null result is printed as the refusal.
2. **`pickProject`, then `resolveDbRecipe`**, unchanged from `ticket.ts:530-535`. A GitHub-backed project is refused there, as today.
3. **Stdin**, only when `body === '-'`. Refuse on a TTY first, then read. A failed read is refused naming `--body -`.
4. **`createIssue`**, then the `created #N` line and the kind warning, worded as at `ticket.ts:575-580`. There is no `edited.discard()`, and no "kept at" clause on failure.

The editor check (`ticket.ts:524-528`) is never reached on this path. That is what lets the *Done when* test run with an `env` holding neither variable and an `edit` seam that throws.

## 3. Normalise exactly as the form does, then guard

- **Title:** `.trim()`, as the form does at `ticket.ts:439`. So `--title " Fix it "` stores `Fix it` and is not refused.
- **Labels:** `split(',').map(s => s.trim()).filter(s => s !== '')`, the form's own line at `ticket.ts:445-449`. Factor it into one small exported function used by both paths, so the two cannot drift. Because of this split, `--label ''` means no labels: the ticket is created with the kind warning.
- **Body:** `.trimEnd()`.

One line in the ticket's *Edges* cannot happen under this rule: *a label with surrounding whitespace* is trimmed by the split, so it never reaches the round-trip check. That follows from the *Fix* row ("split the way the form splits"), and *Fix* wins. The round-trip check still guards what survives the split. The two refusal tests the *Done when* asks for should use:

- **A title** `"a\nb"` or `"#!x"`.
- **A label** containing a newline, `--label $'bug\nx'`. It renders as a second header line and `parseTicketForm` rejects it with *"a line in the header is neither the title nor labels:"* (`ticket.ts:451-456`), so `titleAndLabelsRoundTrip` returns non-null.
