# #1019: the shape

The ticket covers most of this. Three things are not obvious from it. #1026's permit has already landed. With that permit in place, the ticket's literal `Effect.tryPromise` lets go of the mirror before the killed `git` has exited. And the permit test has to be ported with a lazy mock.

## 1. #1026 has landed, so carry its permits into the new shape

`packages/repo/src/mirror-lock.ts` exists in this worktree, and it gives two ways to take one permit:
- `withMirrorWrite(path, run)` is the promise form (`mirror-lock.ts:35`).
- `mirrorWrite(path, effect)` is the Effect form, an `Effect.acquireUseRelease` whose acquire cannot be interrupted (`mirror-lock.ts:43-49`).

`worktree.ts` takes the promise form at three places today:
- `ensureMirror`'s check-and-clone/fetch is one hold (`worktree.ts:117-140`). The comment there says why: *"The presence check is inside the hold: it and the fetch-or-clone are one decision about the mirror, or two provisions could both read it absent."*
- `worktree add` (`:211-216`).
- `worktree prune` (`:240`).

`integrate.ts` already uses `mirrorWrite` around its port: `:413-430`, `:472-473`, `:495`, `:520-521` and `:688`.

So in `worktree.ts`, every `withMirrorWrite(p, () => git(…))` becomes `mirrorWrite(p, gitEffect(…))`. `ensureMirrorEffect` is one `mirrorWrite(path, Effect.gen(…))` over:
1. the `rev-parse --git-dir` probe;
2. then either the fetch, or the `mkdir`, `rm`, `clone` and `set-url`.

The filesystem calls stay inside that hold, as they are today.

`withMirrorWrite` stays exported:
- `index.ts:15` exports it.
- `mirror-lock.test.ts` and `provision-permit.test.ts` use it as the "somebody else holds it" side.
- It is a plain `function`, not `async`, so the ratchet does not count it.

## 2. An interrupted `git` must hold its permit until the child has exited

This is the decision the ticket leaves open, and it is the one that matters. The ticket's interruption edge says *"git removes its own `.lock` files on `SIGTERM`, so the mirror is not left locked."* That is only true **after the child has exited**. Two things release the permit before then.

**Effect does not wait.** On interrupt, `Effect.tryPromise` aborts the signal and returns `exitVoid` as its finalizer, without waiting for the promise. In `node_modules/.pnpm/effect@4.1.2/node_modules/effect/src/internal/effect.ts`, `tryPromise` (`:1150-1178`) has no canceller, so `asyncFinalizer` runs `controller?.abort(); return onCancel ?? exitVoid` (`:1229-1233`).

**Node does not wait either.** When `execFile`'s `signal` aborts, Node kills the child and fires the callback with an `AbortError` immediately. It does not wait for `close`.

The result: `mirrorWrite`'s `Effect.sync(release)` runs while the SIGTERMed `git fetch` still holds `packed-refs.lock` or a ref lock. The next writer queued on that mirror then starts and fails with `cannot lock ref` — the 0122 §6 race #1026 closed, reopened by this ticket.

The race is real for two reasons:
- Interruption is what this ticket adds.
- `integrate.ts`'s finalizers run `mirrorWrite(… 'worktree', 'remove' …)` right after an interrupt (`:521`).

So `gitEffect` is built on `Effect.callback` (`effect.ts:1262`), not `Effect.tryPromise`. Effect awaits the cleanup Effect it returns.

**`gitEffect`, step by step:**
1. Resolve the token. A function is called through `Effect.tryPromise`; its failure is `RepoFailed { exitCode: null }`.
2. Run `gitInvocation(args, token, env)`, unchanged.
3. In `Effect.callback((resume, signal) => …)`, call `execFile` in callback form (no `promisify`), passing:
   - `cwd`, `env`, `maxBuffer: 32 * 1024 * 1024`;
   - `signal: AbortSignal.any([signal, options.signal].filter(Boolean))`.
4. On the callback:
   - success: `resume(Effect.succeed(trim ? stdout.trim() : stdout))`;
   - error: `resume(Effect.fail(new RepoFailed({ … })))`.
5. Keep the `ChildProcess` that `execFile` returns. The callback returns a canceller: an `Effect.callback` that resumes once the child has **exited**.
   - If `child.exitCode !== null || child.signalCode !== null` already, resume at once.
   - Otherwise resume on `child.once('close')`.
   - The fiber signal's abort has already sent the SIGTERM, so the canceller only waits.

This still meets the ticket's Done-when: the fake `execFile` is handed a signal, and the signal is aborted. Add a second assertion to that same unit test: the interrupt does not finish until the fake child emits `close`.

That test mocks `node:child_process`:
- The fake `execFile` returns an `EventEmitter` with `exitCode: null`, `signalCode: null` and a `kill` spy.
- It captures the options and the callback.

Name the canceller in a comment so it is not "simplified" back to `tryPromise` later. Quote 0122 §6 and `mirror-lock.ts:11-13` (*"one would let a second writer start beside a holder whose git is still running"*).

**What `RepoFailed` reads from `execFile`'s error**, in callback form:
- `detail`: `err.message`. This is today's `Command failed: git …\n<stderr>` text, so `PUSH_REJECTED` and `BASE_PROTECTED` (`integrate.ts:668,677`) still match.
- `stdout` and `stderr`: the callback's own arguments.
- `exitCode`: `typeof err.code === 'number' ? err.code : null`.

`err.code` is a **string** in three cases — `'ENOENT'`, `'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'` and `'ABORT_ERR'` — and none of them is an exit code. Don't write `err.code ?? null`.

**`operation`** stays `` `git ${args[0] ?? ''}` ``, as today (`git.ts:115`).

**`message`** is a getter returning `detail`. `Data.TaggedError` sets `message` from the props only when one is passed, so check that the getter is not shadowed by an own property. The ticket's unit test (message equals detail) settles it.

## 3. The mirror reads and `provisionWorktreeEffect`

**Each mirror read** wraps the same steps in `Effect.fn('<name>Effect')`. A `RepoFailed` is never retagged inside `provisionWorktreeEffect`.

**`provisionWorktreeEffect`'s `operation: 'provision'`** comes from one `Effect.mapError`, at the end, over the whole generator:

```ts
(e) => new RepoFailed({ ...e, operation: 'provision' })
```

This is how every failure gets `'provision'` while keeping `exitCode`, `stdout` and `stderr`. Today the same thing happens through `tryPromise`'s catch (`worktree.ts:259`). The stale-continuation refusal (`:182`) is `yield* new RepoFailed({ operation: 'provision', detail: <same text> })`.

**`removeWorktreeEffect`** is `rm`, then `mirrorWrite(mirror, gitEffect(['worktree', 'prune'], …))`, all under `Effect.ignore`. The ignore covers the `rm` too, as `:262-266`'s does today.

**Spans:**
- `repo.git` gets one attribute only: `git.subcommand` = `args[0]`.
- `repo.provision` and `repo.ensureMirror` come from `Effect.fn`.

## 4. Porting `provision-permit.test.ts`: the mock must be lazy

This file is #1026's test, and the Done-when says it moves into the Effect shape with the same assertions. It mocks `git` (`provision-permit.test.ts:10-21`), so it now has to mock `gitEffect`.

**The mock records inside `Effect.suspend`, not when it is called.** `mirrorWrite(p, gitEffect([...]))` builds the Effect before the permit is taken. A mock that pushes to `calls.list` when called would record `worktree add` while it is still queued. That would break `expect(calls.list).toEqual([])` at `:62`, and the test would look as if the permit failed.

`mirror-lock.test.ts:80-88` already has the right shape: `lazyGit`, *"a call is recorded when the Effect runs, not when it is built."*

Two more changes in that file:
- **`RepoFailed`** comes from `vi.importActual`, not `class extends Error {}`: the code now constructs it with fields and reads `exitCode`.
- **The two `ensureMirror(...)` calls** become `Effect.runPromise(ensureMirrorEffect(...))`.

The same laziness applies to `unit/mirror.test.ts`'s new `gitEffect` mock. The maxBuffer case rejects with:

```ts
new RepoFailed({ operation: 'git show', detail: 'stdout maxBuffer length exceeded', exitCode: null })
```

The 128 case passes `exitCode: 128` and the `stderr`.

## 5. `conflictedPathsAt`'s two exit-code reads

`mirror.ts:168-170` reads `exitCode === 1` and `stdout`; `mirror.ts:197-198` reads `exitCode === 128` and `stderr`. Both go through `Effect.catchTag('RepoFailed', …)` or `Effect.catch` on the specific call, and any other failure is re-raised.

`.catch(() => null)` becomes `Effect.orElseSucceed(() => null)` on that one call only, never around a whole generator. Otherwise a `RepoFailed` from a later step (the *git too old* check at `:161`) would become `null` and read as absence.
