## Where the runtime rides on a `never-ran`

**A `never-ran` action result is its own type.** In `packages/actions/src/action.ts:118`, `ActionResult` is one interface with `verdict: ActionVerdict`. Split it into a union: the existing interface with `verdict: Exclude<ActionVerdict, 'never-ran'>`, plus a `never-ran` member that requires `runtime: RuntimeId`. That union is how *a `never-ran` with no runtime is a type error* becomes true.

Don't take the runtime from `spent?.runtime`. `spent` is optional on purpose: *"Absent means no process ran"* (`action.ts:327-331`). The work action's `never-ran` has no `spent` at all (`work-action.ts:179-183`).

Every place that builds a result passes a literal `verdict` (checked with `rg "verdict: [a-z]"`), so splitting the type breaks no constructor that uses a variable. Each place that builds a `never-ran` changes:

- **Review and draft actions.** `reviewAnswer` (`agent-action.ts:865`) and `draftAnswer` (`:1445`) have no runtime in scope. Give each a `runtime: RuntimeId` parameter, and pass `deps.runtime.capabilities.id` from `:846` and `:1435`, the same value `spentOf` uses (`:92`).
- **Work action.** `WorkedAnswer.neverStarted.agent` becomes `RuntimeId` (`work-action.ts:58`), and the branch at `:173-184` copies it into `runtime`. Replace the comment at `:174-178`: since #314 it is false that *"one conductor dispatches one"*.
- **Pipeline.** `neverRanAt` gains `runtime` (`action.ts:648`, `:1025`, taken from `result.runtime`). `StepNeverRan` gains `readonly runtime: RuntimeId` (`run-attempt.ts:461-465`). `endingOf` (`:2116`) fills it from `neverRanAt`, and the judge's ending (`:1401-1405`) fills it from `reply.neverStarted.agent`, which is already the runtime there.
- **First dispatch.** `conduct.ts:3999` reports `dispatched.capabilities.id` (the fix round already does, at `:4251`).

## The two-projects test

Put it in `apps/cli/unit/conduct-locked.test.ts`, beside the #1009 case at its end. That case already builds a guard whose `recipeFor` gives `first` `claude-code` and the other projects `codex`.

The new case runs all three projects through one `conductProjects` call with `locked: lockedBy(guard)`. Use a separate `recipeFor` that puts `first` and `third` on `claude-code` and `second` on `codex`, so the existing test keeps its own. `work` for `first` calls `reachAccountLimit(store, 'claude-code', …)`, which is what the attempt does. Assert:

- `entered` is `['first', 'second']`;
- `third` is reported as not looked at;
- `ctl-conductor` is empty.

That covers *the other is looked at* within the same pass, and that a project on the locked runtime after it is skipped. No daemon or wall clock is needed, so it stays in the unit half.

## Decided here

- **No runtime for a step's `AgentCrashed` crash at `:5028`** (it carries none, `wait.ts:213-225`, and adding one is out of scope): `accountWallOf` is the only source. If it returns `null`, nothing is locked, which is #655's miss.
- **The `acct-` append fails:** the run's own ending stands. The conductor-wide pause is not used as a fallback; doing so would put back the bug this ticket removes.
- **The judge's mid-run site (`:2946`) is reached through `runPass`'s judge.** Its test goes in `conduct-stands-the-conductor-down.test.ts` with the others, asserting `acct-<the judge's runtime>`.
