# #755 — design note

## The decision: `add()` returns its outcome, and its log keeps the failure transcript

Today `add()` returns `Promise<number>` (`packages/conductor/src/onboard.ts:495`). Two callers read the number:
- `recheck`: `code === 0` at `:173`, and it joins `said` as the detail at `:178`.
- the CLI: `first-project.ts:842` and `:945`, which print `said` on success at `:845` and `:948`.

**Change the return to an outcome:**

```ts
type Added = { ok: true; updated: boolean; warnings: readonly string[] } | { ok: false }
```

**`log` is still the whole transcript.** It carries every line `add()` and its checks say, and it is what a refusal and Recheck's detail are built from. **The success path never prints `said`.** It prints `outcome.warnings`, then the card.

The ticket allows a second option: log only warnings and failures. That option does not work, because `checkInstallation` logs two lines that are not failures:
- `installation <id> on <account> (…)` at `:299`
- `permissions: …` at `:310`

Both are context on the failure at `:305-307`, and they are also success-path output. The ticket keeps "`checkGh`/`check`'s own" lines. Keeping them in the transcript but out of the success output is the only reading that keeps both. Separating them in the printer would need a text filter, which the ticket forbids. With the outcome type, they reach a refusal and never reach the card.

**Warnings.** In `add()`, wrap the log handed to `warnIfProtected` (`:547`):

```ts
const warn = (l: string) => { warnings.push(l); log(l) }
```

Both the protected line (`:474`) and the could-not-tell line (`:476`) are then reported in both places. Nothing reads prose to tell a warning from the rest.

**`updated`.** `registrationLine`'s test is `isRegistered(reduceProject(prior))` (`:631-632`). Set `updated` from that test and stop logging the line at `:617`. Delete `registrationLine` and its tests (`packages/conductor/unit/onboard.test.ts:342-358`) unless something else still calls it. `recipeLine` (`:491-492`) goes with `:516`. Remove both strings from `SET` in `apps/cli/unit/plain-output.test.ts:50` in the same diff.

**Lines to delete** are the ones the ticket lists. The file has moved since the ticket was written, so use these numbers:

| Line(s) now | What it prints |
|---|---|
| `:516` | `reading …` |
| `:540` | `base: …` |
| `:542-545` | provenance rows |
| `:549` | `recipe: … hash` |
| `:559-562` | the ten steps |
| `:574-582` | `a pass` |
| `:583` | `runtime …, kinds …` |
| `:585` | `tier …` |
| `:617` | the added/updated line |

**Keep:** `:526`, `:531`, `:596`, and everything inside `checkGhAccess` and `checkInstallation`.

The comments justifying the step list cite ADR 0016 §4 and 0061 §5 (`:550-558`). Remove them with the lines. The steps are still visible in the recipe file the ready line names. That is the 0121 decision (`doc/decisions/0121-…:243-245` lists this dump as *not built yet*), not a contradiction of 0016, so no superseding ADR is needed.

**`RecheckDeps.register`** (`:127`) takes the new return type. `recheck` tests `outcome.ok`, and the failure branch at `:174-183` is unchanged. Every fake `register`/`add` in `onboard.test.ts` and the CLI tests returns `{ ok: true, updated: false, warnings: [] }` or `{ ok: false }` instead of `0`/`1`. A typecheck error is how to find all of them.

## The CLI side

### The outcome type

`FirstProjectOutcome`'s GitHub arm (`first-project.ts:217`) gains these fields when a slug was registered:

```ts
updated: boolean
warnings: readonly string[]
```

Both registering sites (`:830-846` for `gh`, `:933-949` for the App) set them from the outcome. On `!ok` they keep today's refusal from `said`.

### Where the card's facts come from

`add.ts:80-106` draws the card only for `result.project === 'local'`. Add a GitHub branch beside it that calls the same `printSetupEnd` (`setup-end.ts:35`). It needs these facts:

- **`recipe`**: read the file back with `cardRecipe(resolveSource(text, path, path).recipe, …)`, as the local path does (`first-project.ts:722-724`). This is the "read-back fails → say so, no card" edge, and it mirrors `init.ts:603-606`. Do not take the base from `add()`. The read-back gives `baseOf` the same answer `add()` registered (`onboard.ts:536-539`).
- **`trial` and `hints`**:
  - `askBeforeGithubAdd` returns `number | null` (`add-github.ts:180`) and discards the trial.
  - It prints its own hints before registration (`:428`); the local path prints them after the card (`setup-end.ts:57`).
  - Change its success return to `{ trial, hints }` and stop printing at `:428`, so that `add.ts` hands both to `printSetupEnd` and the order matches local.
  - It can also return before `askRecipe` runs, for a recipe that already exists (around `:133-149`). There the trial is `{ trial: 'not-run', because: 'declined' }`; do not invent a new reason. Check whether that path really skips `askRecipe` before you write it.

### Card shape

`renderSetupCard` hard-codes `local` in the `code` row (`setup-card.ts:167`). Its `landsOnRow` prints `<base>, in <remote>` (`:121-133`). It has no `github` row and no machine-only form. Widen `SetupCardFacts` instead of writing a second renderer:

- **`where: 'local' | 'github'`**: drives the `code` row's suffix, and makes `lands on` read `<base>, on GitHub`. For `github`, set `code` to `<owner>/<repo>` in `cardRecipe`'s `code` argument.
- **`github?: string`**: when present, adds a `github` row to *this machine*. The value is `gh, signed in as <login>`, `gh, signed in` with no login, or `the App <slug>`. `gh`'s login comes from the `ghStatus` result that `checkGhAccess` already reads (`onboard.ts:360-399`). Expose it on `GhAccess`; do not make a second call. The App slug is `AppCheck.slug`.
- **A machine-only form for `init --project github`**: make `recipe` and `trial` optional together, as one `project?: { recipe; trial; recipePath }` group. Absent, the card draws *this machine* only. `renderReadyLine` (`:195`) then needs the recipe tail to be optional, so it drops ` · recipe: <path>`.

Keep the card a pure function (the header at `setup-card.ts:1-5`). Every new fact arrives on `facts`.

### `init`'s GitHub branch

The branch is `init.ts:630-663`. The App line at `:642` (`fact(world, 'GitHub App', …)`) becomes the `github` row. The `the recipe is written once…` line at `:663` goes. The App-create flow's `waitForApp` and `appComeBackLine` output is out of scope and still prints before the card.

The branch at `:665-677` (machine already has projects, App configured) is not named in the ticket. It is `init` on a GitHub machine, so give it the same machine card.

On these branches, the separate doctor block at `:680-691` (`if (!cardDrawn)`) is replaced by `printSetupEnd` with no project group, so set `cardDrawn = true`. Leave the `next:` ordering after it alone. That ordering is #739's and #756's.

## Tests: the unit-level claims

- **`onboard.test.ts`**:
  - a fake-world `add()` on success returns `updated` and has logged none of the deleted lines;
  - a protected base appears in both `warnings` and the log;
  - the Recheck failure cases stay as they are.
- **CLI, the add path**: a fake `github.add` that logs a dump line *and* returns `ok` → the output contains the card and not that line. This proves `said` is no longer printed on success, without relying on the deleted strings.
  - A doctor fake with `failed: true` → `✗ not ready · recipe:` and never `✓ ready`.
- **`setup-card` unit**:
  - a `github` card has the `code`, `lands on` and `github` rows;
  - the machine-only form has no *this project* or *each pass* group;
  - the ready line without a recipe has no `recipe:`.

Everything here can be checked by `pnpm test` with no integration file involved.
