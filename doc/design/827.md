# #827 — the shape

The ticket settles almost everything. This note covers the four places where the obvious way to write it would get it wrong, and corrects line numbers that have moved.

## Line numbers have moved

`foldProgress` is at `apps/board/src/lib/progress.ts:356` now, not `:359`. `clearAgentPhase` and its comment are at `:414-424` (*"the run ending always comes"*). `STEP_ENDING_STATE` is at `:260`. In `packages/domain/src/run.ts`:

Search by name rather than trusting either set of numbers.

## 1. `openedAt` goes in the `at` stamp, not in each case

`applyRun` opens with `const at = { version: event.version, lastSeq: event.seq }` (`run.ts:349`). Every case spreads it, and that includes `default` (`run.ts:500-502`). Write the field there:

```ts
const at = { version: event.version, lastSeq: event.seq, openedAt: state.openedAt ?? event.at }
```

That is the whole of "set once on whatever event comes first". It also counts an event type the reducer ignores, which matches `foldProgress`'s `events[0]` (`progress.ts:374`). Do not set it in individual cases.

The other instants go in their own cases:

- `step.since` in `StepStarted`.
- `agentStartedAt` in `RunStarted`.
- `laneWaitedAt` in the new `MergeLaneWaited` case.
- `resolved` in the new `StepsResolved` case.
- `askedAt` inside the `StepEnded` loop, in the same `if` that sets `awaiting-approval` (`run.ts:479-489`).

For `askedAt`, use the event's `at`. Set it on `next`, which is later spread under `...at`; nothing in `at` names it, so the spread will not overwrite it.

## 2. The verdicts are already the same values, so there is no mapping table

The board's `STEP_ENDING_STATE` (`progress.ts:260-267`) maps `boardEndingOf` onto `StepState`. `boardEndingOf` is built on `verdictOf` (`read-model.ts:335`, `:353`), which is the same function `RunState.steps` stores through `stepStateOf` (`run.ts:333-345`).

`StepVerdict` (`run.ts:44`) is `'passed' | 'failed' | 'never-ran' | 'did-not-finish' | 'asked' | 'waived'`, and every one of those is a member of the board's `StepState` (`progress.ts:79`). A requested signoff is already `'asked'` (`run.ts:282`).

So `state.steps[key].verdict` can be used as a `StepState` with no translation. Delete `STEP_ENDING_STATE`; do not rebuild it.

The `RunState.steps` record is keyed by `step:action`, because `stepStateOf` writes `step: key` and `withStep` keys by it (`run.ts:219-221`). Build `mine` this way:

1. Take `Object.entries(state.steps)`, filtered on the `${step}:` prefix and sliced the way `:568-570` slices today.
2. If `state.step?.step === step`, append `['', 'running']` at the end.

The empty name is today's placeholder. `extra` (`:588`) picks it up as an action not in the plan, exactly as it does now. Object key order is insertion order for these non-integer keys, and the spread in `withStep` keeps an existing key where it was, as `Map.set` does. The order of the extras therefore does not change.

`boardFactOf` stays in `@lingtai/domain`. Only `progress.ts`'s import of it goes. `history.ts`, `task.ts`, `conduct.ts`, `wait-words.ts` and `apps/board/test/waits.ts` still call it.

## 3. `now`: the latest phase wins, and there is no fallback to an older one

Build four candidates in the order asked, lane, agent, step. Each is `{ began: Date | null, live: boolean, phase }`, and the step candidate's `began` is `state.step?.since ?? null`.

1. Take the greatest `began.getTime()` among the candidates that have one.
2. Keep only the candidates whose `began` equals it, in that order.
3. `now` is the first live one among them, or null.

**Do not fall back to an older live phase when the latest one is dead.** The ticket's "null only when none of those is live" means the tied latest phases, not all four. Two of its cases depend on this:

- **`RunFinished` inside `implement`.** `agentStartedAt` is later than `step.since(implement)`, the agent is dead, so `now` is null. It is not `implement`.
- **After merge's `StepEnded`.** `step` is null, so the latest is `laneWaitedAt`, and the lane is dead, so `now` is null.

A version that "picks the latest live phase" passes the fixing-round and tie tests and quietly fails these two.

Compare with `getTime()`. Two different `Date` objects are never `===`, and `makeStream` gives every event the same instant unless it is passed an `at` (`packages/domain/test/support.ts:31`). Ties are therefore the common case in the existing tests. The board's `Phase.since` stays a string: write `began.toISOString()`.

The agent is live when `lifecycle.status` is `running` or `awaiting-input`. Both `RunFinished` and `RunFailed` move the lifecycle off those (`run.ts:405-427`), so `receipt` and the sticky `failure` (`run.ts:160`) are never consulted.

## 4. The domain import stays type-only

`progressOf` takes a `RunState` and needs `STEPS` and the `Step` type. Change `progress.ts:35` to:

```ts
import { STEPS, type RunState, type Step } from '@lingtai/domain'
```

Drop `boardFactOf`, `BoardFact` and `Envelope`; they were the only things that kept the client graph that `rail.tsx` pulls in reaching runtime fold code. `reduceRun` is called by the server callers (`board.ts`'s `laneProgress`, and `task.ts`'s `foldRun` and the last-attempt call), never by `progress.ts`.

## The fixture histories

`lateHistories` has only a `run` key today (`packages/domain/test/histories.ts:678-679`). Append `planResolved` and `laneWaited` inside it, after the last entry. The fallback the ticket describes, a module-level `const`, is not needed unless another key has appeared by the time you start.

`laneWaited` must pass explicit, distinct `at`s if it goes through `stamp()`. The `stamp()` instants already differ (`histories.ts:58-61`).

The board test `the lane wait ends with merge` folds two prefixes of the same history: before and after merge's `StepEnded`.
