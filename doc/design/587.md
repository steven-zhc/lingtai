## Design: restore the worktree after a review (#587)

### Where the git goes: a caller-supplied dep, not git inside `agent-action.ts`

The ticket's **Fix** row puts `git rev-parse` / `git status` / `git reset` in `agent-action.ts`. That package has a rule against exactly that: `packages/actions/src/agent-action.ts:112-113`: *"Supplied by the caller: the actions package does not know about git, and should not learn."* So follow the `diff` dep's shape:

- **The action decides when to restore.** It does so after `deps.runtime.run` returns or throws (`agent-action.ts:500`). It also decides what to record.
- **The caller does the git.** `conduct.ts` supplies it as a new key on `AgentActionDeps` (`agent-action.ts:107`), for example `restore: (onSha: string) => Promise<RestoreAnswer>`.
- **The answer has three shapes:** `{ untouched: true }`, `{ restored: string }` (a plain-text account of what was found) and `{ failed: string }`. These match `CleanAnswer` / `KeptRunAnswer`.

**Make the key required, not optional.** An optional `restore` that some path leaves out would silently restore nothing, which is the bug this ticket exists to remove. The compiler is what proves that `conduct.ts`'s `stepDeps.agent` (`packages/conductor/src/conduct.ts:2899`) carries it. Unit fixtures that build `AgentActionDeps` get a no-op that answers `{ untouched: true }`. The files are listed by `grep -l settingsPath` under `unit/` and `test/`, and `packages/conductor/test/one-pass.ts` is the shared one.

**`dispatchDeps` must carry the new key.** It is in `packages/actions/src/from-recipe.ts:220-240` and rebuilds the deps object key by key, so a key it does not copy never reaches the action. Update the comment at `from-recipe.ts:45` too (*"The five keys stay exactly the five `createAgentAction` reads"*).

### The git: next to `keptRunPort`, reusing its rules

Put the implementation in `packages/conductor/src/kept-run-port.ts`, or in a sibling module built the same way. Build it in `conduct.ts` from `gitAsked` (`conduct.ts:1628`) and `recipe.env.plantAt`, the same way `keptRunPort` is (`conduct.ts:2840-2843`). That module already settles the two traps:

- **Spare the planted file with `-e /<plantAt>`, not a pathspec.** `kept-run-port.ts:25-27`: *"A pathspec still lets `git clean -fd` remove an untracked directory whole, with the planted file inside it; `-e` with a leading `/` names exactly the one path."* So the clean is `git clean -fd -e /<plantAt>`. Never add `-x`: ignored files (such as `node_modules` or a test cache) are not the reviewer's to lose, and porcelain does not report them anyway.
- **Ignore the untracked planted file, and only that, when checking for dirt.** This is the trap the ticket does not name. If the repository does not gitignore `plantAt`, `git status --porcelain` shows `?? .env.local` after every review. A check that does not drop that line would reset and record a note on every clean review, which fails the second Done-when box. Filter it the way `conduct.ts:1883-1886` already does (*"a porcelain line for it alone must read the same as a clean tree"*). Lift that filter into a shared function rather than copying it.

The order matters:

1. Read `rev-parse HEAD` and `status --porcelain` first, and build the `restored` sentence from them: the reviewer's head, and the dirty paths, bounded.
2. Only when either check differs, run `reset --mixed <onSha>`, `checkout -- .` and `clean -ffd -e /<plantAt>` (never `--hard`: a reviewer that committed the planted file leaves it tracked, and `--hard` would delete it), then read status again and fail if anything but `?? <plantAt>` remains.

That makes "changed nothing → no reset" structural. Unlike `keptRunPort.clean`, this does compare against a baseline. It can, because `onSha` is the baseline: only `admit` and `implement` move the head (`pass-steps.ts:97-100`, *"which is why `admit` and `implement` return one and nothing here reads `onSha` back"*).

### In the action: wrap the run, not the whole `run()`

Put a `try/finally` around `deps.runtime.run` only:

- **The empty-diff early return** (`agent-action.ts:460-464`) dispatches nothing and needs no restore.
- **Concurrency:** steps in a pass run one after another, so restoring inside the action's own `run` cannot overlap another step's use of the worktree. That covers the ticket's *must never run while another step uses the worktree*.

**Recording, given that the run log is not a record.** A `note` alone fails the **Want**'s *"the log says so"*, because `runLog.note` is a trace and is lost when the run lands (0034, CLAUDE.md, *"It is a trace and never a record"*). Make two records:

- **Run log:** `context.log?.note('review', <the restored sentence>)`, beside the existing note at `agent-action.ts:495`.
- **Log:** append the same sentence to the result's `evidence`. That string reaches `events` as `ActionBase.evidence` (`packages/domain/src/action.ts:111-112`, *"What the plugin said, for a person; nothing branches on it"*), so `StepReached.results[].evidence` is the field that settles it later. Append it after `reviewAnswer(outcome)` so `evidence`'s existing shape is unchanged (`agent-action.ts:528-533`, *"byte-for-byte"*). Pass it through `boundedEvidence`.
- **Do not change `verdict`, `findings` or `because`.** A reviewer that edited the tree has not refused the diff, and the result must route exactly as it would have.

On a **throwing** run there is no result to carry the sentence. Restore anyway, note it, and rethrow with the restoration note appended to the message (the original stays as `cause`; with nothing restored, the original unchanged). `runStep` already turns a throw into the step's report (`conduct.ts:1423`), and rewording the error would lose its cause.

**If the restore itself fails (`{ failed }`), throw.** Do not return the review's verdict as if nothing happened: the next round would be a fix round on a worktree known to be wrong, which is the failure this ticket names. If the run had also thrown, the restore failure's error replaces it. Say so in the error message and put both messages in it.

### Not in scope

- **`createDraftAction`** (`agent-action.ts:911`, the `design:` drafter) also runs in this worktree under a prompt-only *"Do not change it"* (`:784`). Its leftovers reach `implement`'s `git add -A` the same way. The ticket names the review only. Shape `restore` so the drafter could take it later, but do not wire it here.
- **No merge guard.** Per the ticket's **Watch out**, `merge-action.ts:88-109` lands `onSha`.
- **Keep `reviewId`'s derivation** (`agent-action.ts:494`, #195).

### Tests

- **Unit**, in `packages/actions/unit/agent-action.test.ts`: a fake runtime plus a recording `restore` covers Done-when boxes 2 and 3.
  - `restore` is called once, with `context.onSha`, on a passing, a refusing and a throwing run.
  - `untouched` adds no note and leaves `evidence` unchanged.
  - `restored` adds the note and appends the sentence to `evidence`.
  - `failed` throws.
  - The empty-diff path never calls `restore`.
- **Integration**, Done-when box 1: the real-git half (edit a tracked file, add an untracked one, commit, and leave a non-ignored `.env.local` in place) uses the `git` binary. By 0060 §1 that makes it integration. Put it beside `packages/conductor/integration/kept-run-port.test.ts`, which already drives that module against a real repository.
  - That half is out of reach inside a pass (803s). Write it and commit it; do not wait for it.
  - The unit claims above stand in for it before the merge.
  - The porcelain filter is a pure function, so unit-test it directly with and without the planted line. That is the part most likely to be got wrong.
