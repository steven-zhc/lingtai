# Design note for #1216: the Queued column's *why nothing runs* line, the banner's limit sentence, and no account mark on a queued card

## What is already in this worktree

#1215 and #1214 have both merged into this worktree's HEAD (`3f742192`). This ticket only draws what they built:

- The sentence: `whyNothingRuns(facts, blockers)` in `packages/conductor/src/why-nothing-runs.ts:218`.
- The installation-wide roots: `rootBeforeChains`, at `:150`.
- The count behind the mock's *and N more*: `omittedTickets`, at `:207`.
- The limit wording: `limitSentence`, in `packages/domain/src/failure/explain.ts:81`.

Today only `lingtai status` puts the facts together and decides what to read lazily (`apps/cli/src/status.ts:603-641`). On the board, the only thing the sentence needs that already exists is the blocker read (`askProject`, `apps/board/src/lib/board.ts:951`).

## 1. Share the sequence, not just the function

The decision that is not obvious from the ticket: **#1215's "same function" covers more than `whyNothingRuns`. It also covers the order in which status reads things before calling it** (`status.ts:615-641`):

1. `mayApply` first.
2. Then the beacon and `conductorLockHolder`.
3. Then `rootBeforeChains`.
4. Blockers only if `applies` still holds.

Two of #1215's fix commits are in that sequence:
- `0798c487`: *a live conductor that suppresses the sentence reads no blockers*.
- `3a99fb4c`: *an old running row is a pass in flight while any conductor holds the lock*.

A board that copies those lines will drift from status the next time one of them changes. So move the sequence into `why-nothing-runs.ts`:

- `explainQueueEffect(facts, reads)`, where `reads` is `{ beacon: Effect<Beacon>, conductorHeld: Effect<boolean>, blockers: Effect<BlockedSkip[] | null> }`. It returns `WhyNothingRuns | null`.
- A pure `whyRows(tasks, backoffMs, now): WhyRow[]`, for the `rows` mapping at `status.ts:612-626`.

The reads are injected because the beacon reader (`readStatusEffect`) and `conductorLockHolder` live in `@lingtai/daemon`, and `packages/conductor/package.json` does not depend on it. `status.ts` then calls these two and nothing else, with no behaviour change, so its existing unit tests are the check.

## 2. Where the board gathers the facts

Gather them inside `askProject`'s single `Effect.runPromise` (`board.ts:951`), so the board's count in `effect-ratchet.baseline.json` stays the same. Do not add a second `run*`, and do not add a new `async` function. Each read becomes a `yield*`, a `recovering` or an `Effect.tryPromise`:

- **The base**: `lookAtBase` with `mirrorBranchShaEffect`, exactly as `status.ts:475-503` does (no fetch).
- **Pass over for a red base**: run `passOverBaseRed` over `offered` before `select`.
  - This is a deliberate behaviour change. `queued.ts:114` says *"The board does not read the mirror, so it never draws this one"*. Today, while the base is red, the board shows tickets as runnable that the conductor will not take (`schedule.ts:262`). The mock's red state shows `0 runnable`, which needs this.
  - The `base-red` skips then reach `notes` through `passedOver`, because `DRAWN_SKIPS` (`board.ts:1173`) does not include `base-red`. Drop that note for a project only when its why line has a `base-red` root. Otherwise keep it, because when a pass is in flight the line is suppressed and the note is the only place those tickets show.
- **Rows**: `readTasksEffect({ project })` → `whyRows`.
- **Locks**: `readProjectLocks()` (`apps/board/src/lib/locks.ts:98`, a `cache`d read the banner already makes). A project missing from `held` has `[]`. `!ok` → `{ unread: problem }`.
- **Drain**: `readControlOnce` (`locks.ts:51`) → `shutdown !== null`.
- **Blockers**: `Effect.succeed(blocked)`, the list `askProject` has already read.

**This must not break the unit seam.** `apps/board/unit/ask-project-ownerless.test.ts` calls the real `askProject` without a database, and `HOME=/nonexistent pnpm test` has to stay green. So put the explanation behind an option, `options.explain`. Only `page.tsx`'s wrapper passes the real reader. When it is absent, `why` is `null`.

`ProjectQueue`'s `listed` case and `GithubQueue` (`board.ts:1175`) gain `why: { project: string; why: WhyNothingRuns }[]`. A test of `githubQueue` that passes its own `ask` returns `why` directly.

When `askProject` fails, the project is `unanswered`. Its line is then computed from what needs no GitHub (pass `offered: []`). That gives the daemon, drain, lock and locks-unread roots, and `whyNothingRuns` cannot reach *nothing blocks them*, because `unheldQueued` is empty unless something is offered. In practice this means no line at all unless a log row is `queued`, and that is acceptable: `problems` already says GitHub did not answer.

## 3. Drawing the line: `QueuedAnswered`

Put a pure helper in `apps/board/src/lib/why-line.ts` that maps a `Root` to `{ tone, parts }`. `QueuedAnswered` (`queued-stream.tsx:334`) renders the mock's markup above `summary`:

```html
<p class="whynot {tone}"><span class="wk">why nothing runs</span><span>…</span></p>
```

Copy the `.whynot*` rules from the mock into `apps/board/src/app/globals.css`. `--held-soft`, `--signal-soft` and `--fail-soft` already exist there.

**Tone, by `root.root`:**

| Root | Class |
|---|---|
| `lock`, `locks-unread` | `lock` |
| `base-red`, `base-unreadable` | `red` |
| `no-daemon`, `beacon-unread`, `drain` | `down` |
| `chain` whose root ticket waits on you | `person` |
| anything else | none (the base `.whynot`) |

**The text:**

- **Lock roots** are drawn from `root.lock`, never from `root.sentence`. `root.sentence` is `lockSentence(...) + ' — see above'`, which carries the reset and `lingtai account lift`: a second banner. The field exists for this — *"For `lock`, the lock, so a reader can draw it its own way"* (`why-nothing-runs.ts:73`). The line reads `held by {name} — see above`, where `{name}` is:
  - an account lock with `named`: the head of `limitSentence`. Export it from `explain.ts` as `limitName(account, kind)`; `limitSentence` builds `head` at `:89-90` and should use it.
  - an account lock without `named`: `accountWords` (`domain/src/locks.ts`) → *Claude Code's usage limit*.
  - a ceiling lock: *today's spend ceiling*.
  - a paused lock: *{project}'s pause*.
- **Every other root** renders `root.sentence` verbatim. Backtick spans become `<code>`. For a chain root, the root ticket's `#N` becomes a link.
  - To know the root ticket and whether it waits, add an optional `on?: { ref: number; waits: boolean }` to `Root`, set in `rootVerdict` (`why-nothing-runs.ts:333`) and carried through `Held`. This adds a field and changes no wording, so status is unaffected. Do not parse the sentence for it.
  - The link target is the Waiting on you card. Give that card an `id` (e.g. `waiting-{project}-{ref}`) and link to it.
- **The words are #1215's, even where the mock's differ.** The `no-daemon` sentence is *the daemon is not running — lingtai daemon or lingtai service start*; the mock has *`lingtai daemon` starts it*. The base sha is not in backticks. Changing these is changing #1215's wording, which the ticket puts out of scope. The visual check is position, type and colour. Say this in the landing comment, next to that state's screenshots.
- `omittedTickets(why) > 0` → `<span class="more"> · and N more for other reasons</span>`, matching the mock's *several roots* state.
- **Several projects**: one line per project in `why`, in `askable` order, prefixed `<strong>{project}</strong>: ` only when `projects.size > 1`, the same rule as `showProject`. The mock has one project and no prefix. The project filter narrows `askable` already.
- **Only held tickets**: `whyNothingRuns` returns null, because `unheldQueued` is empty, so no line. That needs no special case.

**`QueuedFallback`** (`:290`): keep a module-level `lastWhy` set of projects that had a line on the last answer, beside `lastOffered` (`board.ts:1061`). Draw one `Skeleton` per entry, with a line shape sized to `.whynot`. Add the shape to `skeleton.tsx` if none fits; per that file, *"no words, for anyone (0111 §15)"*.

## 4. The banner: `AccountRow`

`bannerRows` (`locks.ts:178`) carries the lock's `named` and `untilFrom`/`said` onto the account `BannerRow`.

**When `named` is present:**

- The label is `{display name} limit`, giving the mock's *Claude Code limit*. Export the display name from `explain.ts`, where `ACCOUNT_NAMES` lives (`:62`).
- `.what` is `limitSentence(...)` followed by:
  - ` — nothing starts until then` when `resetsAt` is set and not passed;
  - `; raise it, then Lift` when `resetsAt` is null (the mock's monthly state);
  - the existing `passed` sub, when it has passed.
- The `waiting`/scope tail is dropped, as in the mock. The `others` clause (#1010: *other projects still take work*) is kept as a `.sub` only when it is non-empty; the mock never draws that case.

**Without `named`**: today's markup exactly. `LiftButton` is unchanged.

## 5. The card mark: `lockStanding`

Delete the account branch (`lock-marks.ts:97-108`) and narrow `LockStanding.kind` to `'ceiling' | 'paused'`. Then let `tsc` find every place that switched on `'usage limit'`/`'rate limit'`: `queued.ts:408`, `:423`, `:499`, `board.ts:1857`, `page.tsx:271`, `decide.tsx:855`. Each of those loses only that case.

The ceiling's and the pause's text are unchanged. A backoff mark is not `lockStanding`'s, so it is untouched.

`accountsHolding` stays, because `locks.ts:195` reads it.

## Tests (unit only)

- **`why-line`**: one case per root kind, checking tone and text. Include the lock root's *see above* text with and without `named`. Also check the `on.waits` link.
- **`QueuedAnswered`**, rendered with a `github.why`: each mock state's text, and no `.whynot` when `why` is empty.
- **`explainQueueEffect`**:
  - It does not read the beacon when `mayApply` is false.
  - It does not read blockers when a lock root answers.
  - Status's existing tests cover the rest once status calls it.
- **`lockStanding`** and **`AccountRow`**, as the ticket's Done when lists.

Nothing here needs `pnpm test:integration`. The `askProject` reads are integration-shaped, and the `explain` seam is what keeps them out of the unit half.

## Watch out

- **`askProject`'s single `Effect.runPromise` is the board's ratchet budget.** Fold every new read into it.
- **Applying `passOverBaseRed` on the board is the change most likely to surprise a reviewer.** Name it in the commit message as making the board agree with `schedule.ts:262`.
