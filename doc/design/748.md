# #748: design note

## Where the change goes

Three files change: `apps/cli/src/approve.ts`, `apps/cli/src/verdict.ts` and `apps/cli/unit/verdict.test.ts`. There is also one bullet to delete from `doc/decisions/0121-the-cli-output-and-input-contract.md:238-239`. The rest of that *Not built yet* section stays, because the `doctor` bullet under it is still true. `packages/conductor` and `packages/domain` do not change. The ticket wants only a CLI-side read of the outcome, and #465 keeps `approve` from doing anything more.

## The trap: "leaves `approved`" is too early

The ticket says to re-read until the lifecycle "leaves `approved`". The first event a conductor appends when it continues is its re-claim, and a claim replaces the lifecycle with `claimed`:

> "Replaces whatever lifecycle was there." — `packages/domain/src/ticket.ts:279-286` (`lifecycle: { status: 'claimed', runId, worker }`)

The fixture already shows this sequence: *"The continuation's own reclaim, then its landing — the ticket is no longer `approved`"* (`apps/cli/unit/conduct-continuing.test.ts:83-100`, `aClaim` then `aLanding`). If the loop stopped at the first read that isn't `approved`, it would almost always stop on `claimed` and print nothing useful.

**Decision:** keep waiting while `lifecycle.status` is `approved` or `claimed`, and stop on the first of these:

- `landed` → the *landed* line
- `blocked` → the *held again* line
- `closed` or `backlog` → the *moved some other way* clause: `closed`, or `requeued` for `backlog`

The re-read is `reduceTicket` over `store.read(ticketStream(project, issue))`, the same fold `approveHolding` uses (`packages/conductor/src/approve.ts:1`, `:117-120`).

Add a test for this: a holder, then `aClaim` followed later by `aLanding`. The result must be the *landed* line, not one read off `claimed`.

## The seam

`approveVerdict` (`apps/cli/src/approve.ts:31-101`) has no injection points today. It calls `loadProject`, `hasGitHubAuth`, `projectClient`, `withProjector` and `approveRun` directly. Don't push fakes through all five.

**Decision:** split out an exported function that runs after a successful `approveRun`, something like:

```ts
followApproval(
  { project, issue, ticketId },
  { holder, store, now, sleep, signal },
): Promise<{ detail: string; outcome: 'landed' | 'held' | 'pending' | 'no-conductor' | 'unknown'; extra?: … }>
```

- `approveVerdict` calls it with the live values:
  - `holder: () => conductorLockHolder()`: the CLI imports it from `@lingtai/daemon` as `doctor.ts:61` and `restart.ts:67` do. `restart.ts:1425` uses the same `how.holder ?? (() => conductorLockHolder())` default pattern.
  - `store: eventStore`, `Date.now`, a timer sleep, and a signal.
- The outcome tests in the Done-when list go against this function, using `createMemoryEventStore()` and `ticketStream`/`aWait`/`aResolution`/`aLanding` from `@lingtai/domain/test/events`, as `conduct-continuing.test.ts:1-5` does.
  - The injected `sleep` is where a test appends events "at 59 seconds" and moves the fake clock forward.
  - This is the "tests on `approveVerdict` with the holder and store injected" the ticket asks for, at the point where the outcome is decided. Say so in the test file's header comment.
- Poll interval: about 1 s. Nothing in the tests depends on it.
- Run the wait **after** `withProjector` returns, not inside it. `withProjector` holds a session connection and keeps the event loop alive (`apps/cli/src/projector.ts:28-34`). This command appends nothing during the wait, and the conductor's own projector follows the landing.
- **The signal:** `approveVerdict` takes an optional `signal`. `cli.ts:229-230` creates the `AbortController` and calls `process.on('SIGINT', …)` only around the approve call, the same way `cli.ts:474` does for `attach`.
  - Register it after `approveRun` has returned, i.e. only for the wait. Ctrl+C before the approval commits should keep Node's default behaviour.
  - Use `process.once`, so a second Ctrl+C gets Node's default, which is what the ticket's edge asks for.
  - `sleep` must resolve early on abort so the loop ends promptly.
- **Exit code:** the result of `followApproval` only replaces `detail`, `outcome` and `extra`; `code` stays 0.
  - Each failure inside it is caught at the step that failed: the holder throws → *could not tell*; a read throws → *could not read the outcome*.
  - Nothing it does may propagate as a throw: `printAnswer` would turn a throw into `failed(...)` with a non-zero exit (`cli.ts:197-199`).

## The *held again* words

Use `waitWords(block.reason, {...}).line`. The fold already uses it for a blocked lifecycle's question (`packages/domain/src/ticket.ts:404-410`). Pass `branch` and `base` as the fold does there, and `next: lingtai status <project>`.

## Rendering the one-line form

`renderVerdict` (`apps/cli/src/verdict.ts:31-45`) is shared by every verb. `cli.ts:192` and `daemon.ts:717,776` call it directly, as well as `logVerdict`. So the one-line form must be opt-in on the `Verdict` itself, not keyed off the verb string.

**Decision:** add an optional field to `Verdict` (e.g. `form?: 'sentence'`), and set the subject through the existing `subject` field (`verdict.ts:18-19`) as `#${issue}`.

- `verdictJson` does not emit `subject` (`verdict.ts:48-57`), so `--json` keeps `ticketId` with no other change.
- With the flag set, an accepted verdict prints `✓ #n approved — <detail>` on one line, then `  next: …` when `next` is set.
- **`unscheduled`** also uses the one-line form with the subject `#n`. Its detail sentence and `next:` stay word for word, and it does not wait. "Unchanged" in the ticket covers the sentence, not the `ticket-` subject.
- **Refusals** do not set the flag. They keep today's head and indented detail, with `subject: '#n'` replacing the stream id (`✗ not approved (busy) #1`). The early refusals at `approve.ts:37` and `:49` have no `ticketId`, and they keep printing no subject.
- Rewrite `verdict.test.ts:20-21` for the one-line form. Check that the unscheduled case right after it (`:24-30`) still asserts what it means to, now that it renders in that form.

## `extra`

Keep `continuesAt` (and `unscheduled` where present). Add `outcome`, plus `mergeCommit` and `base` when the ticket landed, read from the `landed` lifecycle (`ticket.ts:58`, `:437-442`).

- The ticket's `outcome` list has no entry for the *moved some other way* edge or for Ctrl+C. Use `'unknown'` for an interrupted wait, a failed read and a failed holder read.
- Use `'held'` for `closed` or requeued.
- Add `became: 'closed' | 'requeued'` in `extra` so a script can still tell them apart.

## What the build can check

All of this is unit-level: a memory store, an injected clock, sleep and signal, and an injected holder. `pnpm typecheck` and `HOME=/nonexistent pnpm test` cover it. Nothing here needs the integration half.

The one thing no unit test reaches is that `cli.ts`'s live SIGINT wiring really aborts the wait. That is the same coverage `attach` has today.
