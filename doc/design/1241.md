# Design note for #1241: retire four names, read every old row with the same meaning

The ticket's plan is right. Five things in the code differ from what the ticket says, and each one changes what you write. They come first; then the decisions the ticket leaves open.

## 1. The ceiling sits at different paths than the ticket says

`CeilingReached` (`packages/domain/src/route.ts:27-30`) is reached through `ExcludedCandidate.because` (`route.ts:39-42`). That type is stored in three places, and the ticket names only one:

| Event | Path to the ceiling | Condition |
|---|---|---|
| `ProposalRouted`, `PassRouted` | `offer.unavailable[].because.ceiling` | `because._tag === 'CeilingReached'` (it may also be `NoCriterion`) |
| `ProposalRouted`, `PassRouted` | `decision.because.excluded.because.ceiling` | `decision._tag === 'Escalated'` and `because._tag === 'CandidateUnavailable'` |
| `WaitStarted` | `reason.because.excluded.because.ceiling` | `reason._tag === 'ProposedEscalated'` and `because._tag === 'CandidateUnavailable'` |

- The second row exists because `RouteDecision.Escalated.because` is `RouteEscalation` (`packages/domain/src/routing.ts:106`, and the events-side copy at `events.ts`'s `RouteDecision`). `RouteEscalation` includes `CandidateUnavailable{excluded: ExcludedCandidate}` (`route.ts:57-58`).
- The third row exists because `WaitStarted.reason` is `WaitReason` (`events.ts:368-371`). Its `ProposedEscalated.because` is a single `EscalationBecause` (`packages/domain/src/wait.ts:121,125-130`), **not an array**. The ticket's `because[].ceiling` does not exist.

The `ProposalRouted`/`PassRouted` upcaster therefore rewrites three places: `offer.available[].next`, `offer.unavailable[]` and `decision`. The `WaitStarted` 1 → 2 upcaster rewrites only the third row's path. Leave every other `WaitReason` variant untouched.

**The `Done when` test for the ceilings must include an escalated decision.** Use a stored `ProposalRouted` whose `decision` is `Escalated{CandidateUnavailable}`, not only one whose `offer.unavailable` holds the ceiling. Without that case the test passes while the second row stays unrewritten.

## 2. The ceiling and release-cause types are each declared twice

- **Release cause.** `ReleaseCause` declares `Restart` inline (`events.ts:284`), although its own comment says *"`Restart` and `NeverStarted` are `attempt-next.ts`'s own `RequeueCause` variants, spread in rather than redeclared"* (`events.ts:279-281`). Make the comment true: build `ReleaseCause` from `...RequeueCause.options` plus its own three variants. Then the rename happens once, in `attempt-next.ts:62-63`.
- **Ceiling.** `run-attempt.ts:1219` declares `type Ceiling = 'rounds' | 'restarts' | 'base-merges' | 'conflict-rounds'` separately from `route.ts:29`. Replace it with `CeilingReached['ceiling']` from `@lingtai/domain`. Leaving both means one of them ends up wrong.

## 3. `askedAgainOn` must read both event types

`askedAgainOn` (`packages/domain/src/attempt.ts:757-763`) scans a run's events for `type === 'StepRerunInPlace'` with `askedAgain === true`. Its comment: *"a continuation of it is not granted another (#1205)"*.

The trap: a run asked again before the deploy and continued after it would be granted a second ask-again if this function checked only `StepRedone`. Use one predicate, `isStepRedo(type)`, that is true for both types, and use it here and in the reducer case (`attempt.ts:580`).

`run-attempt.ts:836` (the emit union) and the writer at `:1421-1424` change to `StepRedone` only.

## 4. Do not search and replace the strings `'rounds'` and `'restarts'`

They are also:
- recipe knobs: `packages/recipe/src/recipe.ts:219,303-304`, `packages/recipe/src/resolve.ts:325,331`;
- the report's sort key: `packages/conductor/src/report.ts:190,488`, `apps/board/src/lib/report.ts:26`;
- CLI flags: `apps/cli/src/init.ts:490`, `first-project.ts:493`;
- a projection column: `packages/projector/src/task-view.ts:637`.

None of those is a ceiling value, and all are out of scope. The writers that need to change are exactly the four at `packages/domain/src/failure/respond.ts:667,679,710,722`, plus the enum and the type in section 2.

## 5. Escalation sentences will print the new names

`proposed-route.ts:215,231` and `wait-words.ts:198` interpolate `because.ceiling` verbatim (`` `${c.id}` — `${c.because.ceiling}` is spent ``). After this change they say `` `refusalFixes` is spent ``.

**Decision: let them.** The new value names the recipe bound a person would raise (`runtime.limits.attempt.refusalFixes`, `recipe.ts:224`). Because the upcaster also rewrites rows held from before the deploy, a held wait and a new one say the same word.

The ticket's *Out of scope* line about sentences covers the wording a person reads. It does not cover a value the sentence quotes. Update the tests that pin these strings.

One caveat: `baseBranchMerges` is not a recipe knob yet. It is named only in 0108 (`doc/decisions/0108-a-refusal-buys-a-round.md:177`), and nothing in `packages/recipe/src` declares it. The sentence still names the bound 0108 gives it, which is the ticket's choice.

## The decisions the ticket leaves open

**`StepRedone`'s payload is `StepRerunInPlace`'s, byte for byte (`events.ts:1658-1667`).** That includes the field `rerun`: the ticket keeps fields out of scope. This is what lets one reducer case and `isStepRedo` read either type with no branch on which one it is.

**Write the upcasters over plain JSON, not the zod schemas.** Today's schema is v2. A v1 row decoded against it fails, and that is the reason the upcaster exists. Follow the style of `WaitTriaged`'s upcaster (`upcast.ts:85-97`):
- check `_tag` and rewrite;
- return the input unchanged when nothing matches, so an upcaster is safe on a row without the old tag.

Put two helpers in `upcast.ts`: `renameNext(next)` (`FixRound`, `MergeBase`, and `Requeued.cause.Restart{restart}` → `NewAttempt{newAttempt}`) and `renameCeiling(value)`. All four upcasters use them. They stay private to `upcast.ts`, so the old strings live only there, in `RETIRED` and the catalogue, and in tests.

**`SCHEMA_VER` entries** go in `BUMPED` (`events.ts:2854`), one comment line each, as the existing entries are written:

| Type | Version | Upcaster key |
|---|---|---|
| `TicketReleased` | 2 | `1:` in `UPCASTERS` |
| `ProposalRouted` | 2 | `1:` |
| `PassRouted` | 2 | `1:` |
| `WaitStarted` | 2 | `1:` |

`PassRouted` is retired but still read, and its rows can hold the old tags, so it needs the upcaster all the same.

**Reducer versions** (each with a comment line in the existing style):
- `attemptReducer` 10 → 11 (`run-codec.ts:207`).
- `ticketReducer` 2 → 3 (`ticket-codec.ts:172`): `TicketState` stores `claims[].cause` and `WaitStarted.reason` (`ticket.ts:85,572`).
- `controlReducer` (`control.ts:310`) folds none of these and stays as it is.

**Generator** (`packages/domain/scripts/events.ts`):
- Point the writer anchor at `:228-231` to `StepRedone` (`anchor: "type: 'StepRedone',"`).
- Add `StepRedone: ['pass-']` to the stream table and keep `StepRerunInPlace: ['pass-']` at `:403`, as `PassRouted` stays at `:401`. A retired type is still listed, and `RETIRED.has(name)` marks it `*(retired)*` (`:715`).

## How each check is verified

Everything here is checkable by the unit half:
- each upcaster, by a unit test in `packages/domain/unit/` next to the existing upcast tests;
- the identical-rebuild claim, by the four `packages/projector/unit/*-rebuild.test.ts` harnesses;
- the refusal of an old reduced state, by `decodeRun`/`decodeTicket` (`run-codec.ts:183-188`, `ticket-codec.ts:160-167`).

No claim here depends on `pnpm test:integration`. Postgres's `jsonb` store and SQLite's both read through `decodeRow` (`packages/event-store/src/event-store.ts:242-262`), so one upcaster serves both.

No accepted ADR is contradicted. 0108 names these renames as *Not built yet*. Editing that line and 0120's code names is what the ticket asks for, since the ADRs from `doc/decisions/` onward are edited in place under the one-ADR-per-topic rule.
