## Design note — #570

### Where it goes

All of it goes in `packages/conductor/src/pass.ts`, next to `roundLimit`. `routeProposal` is where `offerFor` is called (`pass.ts:1230-1236`), and it is the only place `ceilings.restarts` reaches routing:

```ts
const offer = offerFor(
  proposal,
  { rounds: roundLimit, restarts: ceilings.restarts },
  { rounds: roundsSpent, restarts: ceilings.restartsSpent },
)
```

Work out a `restartLimit` once at the top of `runPass`, alongside `roundLimit` at `pass.ts:1162`, and pass it in place of `ceilings.restarts`. `packages/domain/src/routing.ts` does not change, as the ticket says. Its `restart()` already withholds itself with `CeilingReached{ceiling:'restarts'}` when `spent.restarts >= policy.restarts` (`routing.ts:137-140`).

### The decision: key it on the same fact `roundLimit` uses, not on `grant` alone

The ticket's Fix says to check `options.from?.grant`. That covers only the lap that spends the grant. The run has a second state that comes from a grant, and the restart cap has to cover it too.

- `conduct.ts:974-979` computes `priorGrant`, which is true when any wait on this run was resolved `GrantFixRound`. `conduct.ts:1004` then sets `roundLimit` on every later continuation of that run, including one from a plain `Approve` that carries no `grant`.
- The field's doc says why (`pass.ts:927`): *"A prior human grant caps automatic fix routing across later continuations."*
- `pass.test.ts:1576` pins it: *"keeps the granted round cap after an intervening human approval"*, with `from: { step: 'build', …, roundLimit: 1 }` and no `grant`.

A restart is automatic fix routing too, and a bigger kind than a round (0118 §1: *"another round needs another decision"*). If the restart cap is keyed on `grant` alone, this sequence still restarts with nobody deciding it:

1. A round is granted.
2. Its lap holds at a `human:` action.
3. A person approves.
4. The review on that continuation refuses.

So cap restarts under the same condition `roundLimit` is capped under:

```ts
const grantedRun = options.from?.grant !== undefined || options.from?.roundLimit !== undefined
const restartLimit = grantedRun ? ceilings.restartsSpent : ceilings.restarts
```

Read the ticket's "a continuation from `Approve` without a grant keeps the recipe's restarts" as meaning a run on which no `GrantFixRound` was ever recorded. That is exactly when `conduct.ts` leaves `roundLimit` unset. An ordinary pass has no `from`, so it is unaffected.

Do not change `continuationRound`, or how `conduct.ts` decides `priorGrant`. The fact is already carried through to `runPass`; only the restart cap ignores it today.

### What follows without further code

`replyFor` asks no judge when `offer.available.length < 2` (`proposed-route.ts:137`). Take a granted lap whose review refuses: `fix-lines` is withheld by the rounds cap and `restart` by the new cap, so only `hand-to-person` is left. The judge is never called, and nothing is spent on it.

That is the right result. In #557 and #560 a paid judge chose `claim` (a restart). The cap also means the declared `judge: claude-code` at `findings` is no longer dispatched on a granted lap, so the new test should check that as well.

`judge.ts:286` builds its own `claim` offer from `restartsSpent < restarts`. That is the separate `judgeDeclaredAt` path, which is handed recipe numbers. Check whether `askTheAgent` in `conduct.ts` is reached from `routeProposal` with `offer.available` or with those numbers. If it is reached with the numbers, it would offer `claim` that `decideRoute` then refuses. That refusal is safe, but the judge was still paid for it. My reading is that `replyFor` stands in front of it (`proposed-route.ts:137-142` passes `offering` from `offer.available`), so no change is needed there. Confirm that rather than assume it.

### Tests (unit, in `packages/conductor/unit/pass.test.ts`)

Add them under `describe('a granted fix round')` at `:1535`, built the same way as its two existing cases and as *"ends the pass when the judge chooses a restart"* at `:1850`:

1. **Granted lap, review refuses with a finding, restarts left.**
   - Setup: `ceilings: { rounds: 3, restarts: 2, restartsSpent: 0 }`, `from: { step: 'implement', roundsSpent: 1, grant: … }`, `review` returns a failed finding, and the judge answers `claim` and counts its calls.
   - Assert: `result.end._tag === 'WaitOnPerson'`, not `Requeued`; the judge was called 0 times; and the offer recorded `restart` as unavailable with `CeilingReached` `'restarts'`.
2. **Same as (1), but with `roundLimit: 1` and no `grant`** (the post-approval continuation). Assert it ends in `WaitOnPerson`.
3. **Ungranted pass, same proposal and same ceilings, no `from`.** Assert it still ends in `Requeued{cause:{_tag:'Restart'}}`. The existing `:1850` case already shows this with `restarts: 1`. Add the explicit pair, or add a line beside that case naming #570, so the contrast is visible.

All of these are pure `runPass` calls with injected bodies, judge and actions, so `pnpm test` covers them. Nothing here needs `pnpm test:integration`.

### How it is settled in the log

After a granted lap, the expected sequence on the run is the `RouteTaken` from `proposed` with `to: 'waiting'`, then a new wait, and no `TicketReleased` with `cause._tag === 'Restart'`. In the pass log, the line *"restart N of M"* (as in the #557 and #560 excerpts) should never come after a `GrantFixRound` on the same `runId`.

### ADRs

There is no conflict. This makes the router keep what 0118 §1 and 0108 §8 already decided, so no new ADR is needed.
