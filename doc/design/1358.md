# Design: make `branch.personal` at `admit` when the remote has none (#1358)

## Where it goes

The change sits in one place in `conduct.ts`: the `cut` closure at `admit` (`packages/conductor/src/conduct.ts:3396`), around its one `repo.provision` call (`:3449`). Nothing new happens before the claim, and nothing new happens at any other step.

### 1. The trigger comes from the mirror's own fetch, not from an extra request

`provisionWorktreeEffect` calls `ensureMirrorEffect` first, and that call already fetches `+refs/heads/*:refs/heads/*` (`packages/repo/src/worktree.ts:146`). A failed fetch fails the provision; it is not swallowed. Then the provision resolves the base with a bare `rev-parse options.base` (`:214`), and that is the line that fails today.

So the provision should report the absence itself:
- Resolve the base with `rev-parse --verify --quiet refs/heads/<base>`, used only when `options.at` is unset. Exit 1 means the ref is absent. Then fail with a new flag on `RepoFailed`, `baseAbsent: true`, beside `stale` (`packages/repo/src/git.ts:96`).
- Any other failure stays exactly as it is now.
- Keep the resolved value as the sha: `^{commit}` or the existing `rev-parse`, so `baseSha` is unchanged.

In `cut`, when the provision fails with `baseAbsent`, and only when every guard in §2 holds:
1. Ensure the branch through the port in §3.
2. On `made` or `exists`, call `repo.provision` **once more**. That second provision runs `ensureMirror` again, which is the fetch.
3. A second failure is answered as today, with `notCut: provisioned.failure.detail`. There is never a loop.

This costs no GitHub request on an ordinary pass, which a check run before every cut would.

### 2. Guards

The ticket says *"team mode only"*. That is not tight enough, because in team mode `cut`'s base is not always `branch.personal`: `attemptBase()` is a PR's branch for a team `lingtai:pr-fix` claim (`conduct.ts:1177-1184`, #1341). Making a missing PR branch from `main` would be wrong. So all three must hold:

- `modeOf(recipe) === 'team'`
- `spec.base === recipe.branch.personal`. Compare against the action's base, never against `passBase`.
- `continuation === null`. A continuation cuts at `at` and never resolves the base (`worktree.ts:214`), so it cannot reach `baseAbsent` anyway. Guard it explicitly all the same.

### 3. The port

Add one optional field to `RunOnceOptions` (`conduct.ts:544`):

```ts
personalBranch?: (name: string, from: string) => Effect.Effect<{ made: string } | { exists: true }, Error>
```

- When it is absent, `cut` behaves as today. Every existing test and every caller that does not wire it keeps the old refusal.
- `TurnClient` (`:538`) carries none of `branchExists`, `refSha` or `createBranch`. It must not be widened: `ownerlessClient` (`packages/conductor/src/ownerless.ts:31-35`) and every test fake build that type.
- The log line is `made <personal> at <sha7> from <branch.main>`, written through `log`. Tests assert the port's calls, never this sentence.

The wiring lives in `apps/cli/src/conduct.ts`, which builds `common` for both kinds of project (`:257-320`):

- **A GitHub project** uses `passClient`'s Effect methods (`packages/github/src/client.ts:287-301`):
  - `branchExists` answers 200 → true, 404 → false, anything else fails (`:290-294`).
  - `createBranch` reads a 422 *already exists* as success (`:947-953`).
- **An ownerless project** (*"local"* in the ticket) needs a different shape from the one the ticket's Fix row describes. The conductor has no checkout path: `ProjectState` holds `project`, `owner` and `base` (`packages/domain/src/project.ts:19-31`), and the pass has only `remote`, which is `repo.remote` (`ownerless.ts:62`). So it does the same thing against the remote, from the mirror:
  1. **Read:** `git ls-remote <remote> refs/heads/<personal>`. Exit 0 with a line means it exists. Exit 0 with no output means it is absent. A non-zero exit is a failed read.
  2. **Make:** from the bare mirror, push `refs/heads/<main>:refs/heads/<personal>` with `--force-with-lease=refs/heads/<personal>:`. An empty expected value means *the ref must not exist*, so this can never move a branch that is there.
  3. **If the push is rejected,** run `ls-remote` once more. If the branch is there now, answer `exists`. Otherwise it is a failure.
  4. Use the mirror's path as `ensureMirrorEffect` computes it (`worktree.ts:107`). Put this half in `packages/repo`, beside the mirror.
  5. Do **not** reuse `gitRefShaEffect` (`packages/conductor/src/git-refs.ts:75-83`) for the read. It fails both when the ref is absent and when `ls-remote` fails, and those are the two answers this must never confuse.

For a path remote, this ends with the same ref in the same repository as the ticket's `git branch` in the checkout.

### 4. The shared function

The ticket names the CLI's `makePersonalBranch` as the rule. It is not the whole rule:
- It does `refSha` then `createBranch` and reads no existence (`apps/cli/src/add-github.ts:218-224`). *"Read first"* there means reading `main`'s sha.
- The existence read lives in the board's `liveMakePersonal` (`packages/conductor/src/add-from-page.ts:377-393`): *"an existence read that fails makes nothing"* (`:375`).

So create `packages/conductor/src/personal-branch.ts` with two functions:
- **`makePersonalBranch(port, name, from)`**, moved there as it is. `add-github.ts` re-exports it, so `apps/cli/unit/team.test.ts:12` and its two cases (`:165-197`) run unchanged.
- **`ensurePersonalBranch(port, name, from)`**: `branchExists`, then `makePersonalBranch`. It answers `{ made: sha } | { exists: true }`. A failed read fails with *"could not read whether X exists on GitHub — nothing was made: …"*, which is the board's own sentence (`add-from-page.ts:387`).

Then:
- `liveMakePersonal`'s GitHub half calls `ensurePersonalBranch` and maps the answer to its own `'made' | 'exists'`.
- The CLI's add path keeps calling `makePersonalBranch` (`add-github.ts:531`). It only gets there when the recipe step decided a branch is to be made.
- The GitHub half of the conductor's port is `ensurePersonalBranch` over `passClient`.

## Refusals

A failure from the port becomes `notCut: <its message>`. That is today's class for a cut that did not happen (`conduct.ts:3388-3394`, 0057), so nothing about the ending changes, and the refusal sentence names the failed read.

To check the behaviour, read the `admit` step's recorded result for the attempt:
- On the GitHub path, its detail should carry *"could not read whether … nothing was made"*, not *"unknown revision"*.
- A pass that made the branch has the log line and a `worktree … at <sha>` line whose sha is `main`'s tip.

## Edges this note decides

- **GitHub is slow to show the new ref.** A `createBranch` that succeeded, followed by a fetch that still does not show the ref, fails the second provision as today. The next pass reads `exists` and cuts. There is no retry loop.
- **The mirror is stale.** It cannot be at this point: the fetch either succeeded inside this provision or failed it.
- **Two passes at once.** Covered by `createBranch`'s 422 and by the lease on the ownerless push. Both answer `exists`.

## Tests (unit, in `packages/conductor/unit/`)

These use the conductor fakes that the `admit` tests already use, for example `a-reviewer-built-before-the-cut.test.ts`.

- **The branch is missing.** A fake `repo.provision` fails once with `baseAbsent`, then succeeds. A fake `personalBranch` records its calls.
  - Assert one call, `('steven-zhc/studio', 'main')`, and two provisions.
  - The same case with the port answering `exists`: still two provisions.
- **The read fails.** The port fails: assert no second provision and a `notCut` whose detail names the read.
- **The guards.** `baseAbsent` in solo mode, on a `pr-fix` cut whose base is a PR branch, and with `personalBranch` unset: assert no port call.
- **`ensurePersonalBranch`.** With fake `branchExists`, `refSha` and `createBranch`:
  - absent → made
  - present → no `createBranch`
  - `branchExists` fails → no `refSha` and no `createBranch`
- **The `ls-remote` reading.** Exists, absent and failed, as a pure function over exit code and stdout.

Two pieces run `git` and so are integration only (0060 §1). They cannot be verified inside the pass, and the unit cases above stand in for them:
- the real `baseAbsent` detection in `provisionWorktreeEffect`
- the ownerless push from the mirror

Write all of it as `Effect.gen` with no new `async`. `effect-ratchet.baseline.json` does not move.
