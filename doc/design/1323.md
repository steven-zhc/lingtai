## The decisions the ticket leaves open

### 1. The section is keyed on `TicketState.landed`, not on `life.status === 'landed'`

`packages/domain/src/ticket.ts:300`: *"Where the ticket landed, kept after a `TicketClosed` replaces `lifecycle`; null if it never landed (0130 §4)."*

Two of the ticket's cases have a closed ticket:
- the person-closed one;
- the merged-PR one, if #1317's close appends `TicketClosed`.

The ticket's lifecycle has already lost its `base` in both, so `whoWaits`'s `life.base` cannot feed them. Feed `whereOnBranch` from `reduceTicket(own).landed` (`{ mergeCommit, base }`) and `.cutFrom` (`ticket.ts:306`). Mount `OnYourBranch` for any state but `running`/`queued` whenever `landed !== null`.

The poster's big word stays whatever `stateWord` draws, and `OnYourBranch` adds only the small line beside it. So a merged ticket that Lingtai closed may read *closed · MERGED* rather than *LANDED · MERGED*. Whether it does is settled by whether the ticket's stream carries a `TicketClosed` after the PR stream's `PrMerged`, and by its `by` field. Do not add a state to make it read *LANDED*; that is out of scope.

### 2. Which PR holds the ticket follows the store's own rules, not a scan of `pr.tickets`

A closed PR gives its tickets back to the draft:
- `pr.ts:944`: *"`PrClosed` … returns its tickets to Draft"*;
- `packages/project/src/pr.ts:462-466` skips `closed` and `refused` PRs when it decides what is held.

A merged PR holds only what its merged commit held:
- `domain/src/pr.ts:55`: *"`mergedTickets` … the rest landed on the PR branch after it and are not merged"*.

Resolve the ticket `t` with `base` from `landed` in this order. The first match wins.
1. An open PR (status not `merged`, `closed` or `refused`) whose `tickets` or `fixesLanded` contains `t` → **open PR**.
2. A merged PR whose `mergedTickets` contains `t` → **merged PR**. If `t` is in its `tickets` but not in `mergedTickets` and `mergedExact` is false (`pr.ts:57`), say *merged · whether this ticket's commit is in the merge is still being checked*. Never say *merged* outright in that case, because `closeMergedTickets` (`conductor/src/pr.ts:1226-1232`) has not proven it either.
3. `base` equals some PR's `prBranch`, that PR has ended, and step 2 did not match → the pr-fix *"after `<PR>` was merged/closed — not on your branch"* reading.
4. `t` is in `readDraftOf`'s list → **draft**.
5. None of these, but `base === branch.personal` → *In: no PR or draft holds it*. This happens when it landed before the project became team: `readDraftOn` drops `landedAt <= since` (`project/src/pr.ts:480`). Never fall back to *not in a PR yet* here.

The read fails in two shapes: `readProjectPrs` itself fails, or any entry is `{ n, error }`, which makes `readDraftOf` answer `{ error }` (`prs.ts:98-99`). Either way the result is `holder: { kind: 'unread', error }` and *which PR holds it could not be read* in the fail colour, as the ticket says.

There is one exception. If step 1 or step 2 matched on a PR that was read, keep that answer: a failure elsewhere cannot change which PR holds the ticket.

### 3. The gate is `landed.base`, and step 3 needs the PR list before it can decide

`whereOnBranch` returns `null` unless one of these is true:
- `landed.base === recipe.branch.personal`;
- `landed.base` is some read PR's `prBranch`.

The second can only be decided after the read. So the read runs only when the recipe is `mode: team` (`modeOf`, as in `prs.ts:295`), never on a solo project. A solo project therefore does no new read, and that is what makes the *same markup* done-when hold.

Today's mode does not override `base`. A team project's landing on `main` still answers `null` (the ticket's Watch out).

### 4. Shape: a pure core, one Effect read, a streamed part

- **`whereOnBranch(input)`.** `input` is `{ landed, cutFrom, closed: boolean, ticket, source, github: boolean, owner, project, branch: { main, personal }, holder }`. `holder` is the resolution from decision 2, already made in pure code by a separate exported `holderOf(ticket, base, prs, draft)`, so both can be tested without a store. It returns `null` or `{ small, in, mergeCommit, closedWhen, change: PrFixLink | null, sketch }`.
- **`sketch`** is `{ main, personal, box: 'pr' | 'draft' | null, label, dots, more, thisIndex }`. Pick the dots in `whereOnBranch`:
  - take a window of at most five around this ticket, in landing order: the holder's `tickets` order for a PR, `readDraftOf`'s order for the draft (it sorts by landing time, `project/src/pr.ts:485`);
  - put the rest on `more`.

  Do not copy `pr-page.ts:492`'s `slice(-3)`: it can drop this ticket.
- **The read** is a new `readWhereOnBranch(project, recipe)` in `prs.ts`. Write it as an `Effect.gen` that composes `readProjectPrs` and `readDraftOf`. Run it once, at the part's edge, the way `readPrDetail` does (`prs.ts:296`). `apps/board` has no row in `effect-ratchet.baseline.json`, so the ratchet does not count it, but still add no new `async` IO function: the loader is the Effect, and the component calls `Effect.runPromise` on it.
- **`OnYourBranch`** is an `async` server component inside `<Suspense>`. Its fallback is a box at the sketch's and the panel's final size (0111 §15). `stateReadout` draws first, exactly as today. Get the recipe with `currentRecipe` (`task.ts:6`).
  - Pass the small line as a `small` prop into the readout only if that is cheap.
  - Otherwise draw it at the top of `OnYourBranch`. It depends only on `landed.base` and the recipe, so it can be decided before the read: the read changes `ON YOUR BRANCH` only to `MERGED` or `IN <PR>`. Pass the prop through to the readout if that is easy; if not, draw it at the head of the part and accept that it pops in with the stream.
- **Live updates.** The page redraws from `FollowedLog` (`standing.tsx:1287`), which follows the ticket's stream. A PR's append (`PrMerged`, `PrFixLanded`) is on the PR stream, so check whether `Live` re-renders the route on any append or only on the ticket's own stream.
  - If only the ticket's: the page reads a PR merge on its next render. That is the ticket's own *what the log says* reading, so it is acceptable.
  - Do not subscribe the page to every PR stream for this.

### 5. The drawing is a separate component from the PR page's

`pr-detail.tsx:28` (`Drawing`) draws a different picture: the PR branch as its own rail between the two. Lifting it is a PR-page change, and that is out of scope.

`branch-sketch.tsx` has its own SVG (`viewBox="0 0 640 170"` as in the mock):
- the rails, using the `prp-line main` and `prp-line personal` classes;
- the dots, using `prp-dot`, and `prp-dot fix` for a pr-fix;
- this ticket larger, with a ring;
- the box: solid for a PR, `strokeDasharray` for the draft;
- each dot carries a `<title>` the way `pr-detail.tsx:57` does.

Add the ring, box and pill classes next to the `prp-*` rules in `globals.css`. Tests assert the panel's text and links and `aria-label`s, never coordinates.

### 6. The *Closed when* wording

There are two sources of truth.
- **The ticket's source.** `ticketsOnGitHub(recipe)` decides whether the *(the PR also says `Closes #<n>`)* clause appears, and whether `change` is a link or a command. `prFixTicketLink` already returns the `command` shape for a local source (`pr-page.ts:55-60`).
- **Whether the ticket is closed.** Show the `Closes` clause only while the ticket is not closed (`landed !== null` and no close since).

A person-closed ticket is decided by state: `closed` is true and the holder is not a merged PR. Then the line is *closed by a person; its code goes into the PR without `Closes`*. Do not branch on `TicketClosed.by`.
