# #860: design note

The ticket covers most of this. This note settles four things it leaves open: where the rebuild lock lives so a unit test can reach it, one shared helper for the no-conductor line, what `approve` does, and where the live-`spend` registry goes.

## 1. The rebuild lock: a wrapper in `projection.ts`, called only by the handler

The ticket's done-when needs a unit test that stubs `acquire` and `runnerFor`. The handler at `cli.ts:582-593` is a closure inside the command table, and no test reaches it today. `rates.ts:111` must keep calling bare `rebuildProjection`, as the ticket's Watch out says.

So add a second exported function next to `rebuildProjection` (`apps/cli/src/projection.ts:74`), for example `rebuildUnderLock(options)`. Its options are `RebuildProjectionOptions` plus `acquire?: (o: AcquireDaemonLockOptions) => Promise<LockResult>`. It does three things:

- It calls `(options.acquire ?? acquireDaemonLock)({ name: 'lingtai projection rebuild', locker: options.acquire ? NO_LOCKER : createFileLocker() })`. This copies the daemon's own trick (`packages/daemon/src/daemon.ts:135-137,173`). Its comment says why: a unit test that replaces `acquire` must not build this machine's real locker, which *"under test has nowhere of its own to resolve to (`lockDir()`, #273)"*. `NO_LOCKER` is module-private there. Write a local one rather than exporting it.
- If the result is `!held.ok`, it calls `error(...)` with the ticket's refusal sentence and returns `1`. It never calls `runnerFor`. `holder` can be `null` (`packages/env/src/lock.ts:76-77`, *"when they recorded one"*), so word that case as `another process holds the conductor lock …`, never `null holds`. If `acquire` throws, that is the ticket's "rebuild whose lock read fails". Catch it, print `could not take the conductor lock (…)`, return 1, and touch nothing.
- Otherwise it calls `try { return await rebuildProjection(options) } finally { await held.lock.release() }`. `release()` is safe to call twice (`lock.ts:70`).

The handler at `cli.ts:589` then calls `rebuildUnderLock` instead of `rebuildProjection`. Its `createProjectionRunner(` stays in `cli.ts`, so `cli.ts` stays on the structural list. The comment above the new function must say why the lock is not inside `rebuildProjection`: it must point at `rates.ts:100-115`, whose caller already holds the lock.

Put the unit test in `apps/cli/unit/log-predates-hold.test.ts`, next to the two `rebuildProjection` cases at `:222-260`, and reuse their `runnerFor` stub. It needs two cases:

- **Held:** `acquire` resolves `{ ok: false, holder: 'lingtai daemon (pid 1 on h)' }`. Assert the result is 1, `runnerFor` was not called, and `error` was called with a string containing the holder.
- **Free:** `acquire` resolves `{ ok: true, lock: { release } }`. Assert the result is 0, `rebuild` was called once, and `release` was called once. Add a third case where `rebuild` rejects, and assert `release` is still called once.

The `logPredatesHold` refusal now runs *after* the lock is taken. That is fine, because the `finally` releases the lock.

## 2. The no-conductor line: one helper, written to `progress`

The line goes into one function. Six of the commands will call it, and each one bounding its own `conductorLockHolder()` call would be the copy-paste a reviewer flags.

Put it in a new `apps/cli/src/conductor-note.ts`:

```ts
export async function conductorNote(world?: { holder?: () => Promise<string | null>; bound?: Bound; signal?: AbortSignal }): Promise<string | null>
```

- It returns `null` when a holder answers.
- It returns the ticket's `no conductor is running — the board shows this when one starts: lingtai start, or lingtai run` when the answer is `null`.
- It returns `could not tell whether a conductor is running (…); lingtai doctor says` on a throw or a timeout.

For the timeout, reuse `approve.ts`'s `WAIT_MS` and its `Bound` type (`approve.ts:34,49`). Move `boundReal` (`:56`) into the new module and have `approve.ts` import it from there, so there is one bound and not two. The default `holder` is `() => conductorLockHolder()` from `@lingtai/daemon` (`packages/daemon/src/lock.ts:88-90`). Any other throw is a design error, so wrap the whole body; the command must never fail because of this line.

Each caller asks once, **after** its work returns, and passes a non-null result to the `progress` callback it already has. It does not put the line in the verdict. That keeps `--json` stdout unchanged, and puts the line where `withProjector`'s own lines used to go.

**`approve` gets no new line.** After its work, `approve` already runs `followApproval` (`approve.ts:99-128`). That asks the same question with the same bound and already says *"it lands when a conductor runs: lingtai start, or lingtai run"* (`:125`). A second line would say the same fact twice. Unwrap `approve.ts:222` and stop there.

The other callers each get the line: `ask` and `answer` (`ask.ts:53`), `backlog` accept and decline (`backlog.ts:239,265`), `close.ts:58`, `end.ts:82`, `grant-fix-round.ts:31` and `requeue.ts:72`.

For the `requeue` unit test the ticket asks for, replace `RequeueDeps.withProjector` (`requeue.ts:52`) with `conductorNote?: typeof conductorNote` or a `holder` seam. Do not create the stub's `holder` through the real file locker.

## 3. `lingtai backlog accept`/`decline` on a fresh finding

The ticket's edge says the CLI adds the lag to *no backlog entry* when the lag is over 0. Do this in `apps/cli/src/backlog.ts`, not in the conductor: when the verdict is the no-entry refusal, call `readLag('finding_backlog')` (the same read the listing now uses) and add ` — finding_backlog is N behind; it folds when a conductor runs`. If `readLag` throws, add nothing. A refusal that already explains itself should not grow a second failure. Recognise the refusal by its `reason` code if `packages/conductor/src/backlog.ts:199` gives one; match on the text only if it does not.

## 4. The live-`spend` registry: `apps/cli/src/live-spend.ts`

Move `liveSpend`, `trackLiveSpend` and `holdLiveSpend` (`apps/cli/src/projector.ts:74-93`) there unchanged. Repoint the three importers: `daemon.ts:49`, `rates.ts:19`, and `projector.ts` itself, which uses it in `followSecondary` (`:108`) and `releaseSecondary` (`:123`). Also repoint `apps/cli/unit/rates.test.ts:24`.

The new module must import nothing from `projector.ts`. That keeps `rates.ts`, which runs inside the daemon, from loading `run`'s `ProjectorLive` module just to reach a `Set`.

## 5. The structural test

Put it at `apps/cli/unit/one-writer.test.ts`. It sits beside the code it guards, and the board's own check stays where it is (`apps/board/unit/read-not-fold.test.ts:34-39`).

It globs `apps/*/src/**/*.ts` and `packages/*/src/**/*.ts` from the repo root, skipping `node_modules` and `.next`. It asserts that the set of files containing `createProjectionRunner(` **equals** the committed map, which has five entries, each with a reason. Use set equality, not a subset check: a file that drops off the list should fail too, so the list cannot go stale.

This test reads the filesystem. `read-not-fold.test.ts` already does the same and is in the unit half, so follow its precedent and do not reopen the 0060 §1 question in this ticket.

## 6. The guards to delete

- **`packages/projector/src/backlog.ts`:** #838 has landed, so the guard is in this worktree. Delete the column (`:141`), the `last_seq` read in the select (`:184`), the early `break` and its comment (`:196-198`), the `and (last_seq is null or last_seq < $5)` on both updates (`:207`, `:216`), and the `last_seq = $5` assignments (`:206`, `:215`). Also drop `last_seq` from the row type (`:43`). Then renumber the bind parameters. A leftover `$5` with nothing bound to it fails at runtime, not in `tsc`.
- **`ticket_report`:** a `shape()` check covers the DDL, so make sure the expected-columns list in `ticket-report.ts` loses `applied_seq` in the same commit as the `create table`. Otherwise `start()` reports drift against the code's own DDL (`projection.ts:220-221`).
- **Lingering references:** `grep -rn "applied_seq\|appliedSeq\|last_seq" packages/projector apps/board apps/cli` after the edit. Any hit that is not `projection_checkpoint.last_seq` or `TicketState.lastSeq` is a leftover. `apps/board/src/lib/report.ts:136-138` is on the ticket's comment list for that reason.

## 7. `notTakingWork`

Change the sentence at `packages/daemon/src/daemon.ts:91` to say `lingtai shutdown`, then `lingtai projection rebuild task_view`, then `lingtai start`. The current `lingtai restart` would start a daemon onto the same stopped table, and `restart` cannot be the remedy, because the rebuild now refuses while that daemon holds the lock. Update its unit test to match, wherever it lives (`grep -rn notTakingWork packages/daemon/unit`).

## What only the integration half can check

Three claims have no unit-level check: that the live tables drift, that the runbook's rebuilds bring them back to shape, and that the real `fcntl` lock turns a second rebuild away. The unit stand-ins are:

- **Drift:** each projection's `shape()` expected-column list matches its own DDL. The existing shape unit tests cover this once the column list is edited.
- **Rebuilds:** none. Only the runbook on the conducting machine checks this, after the merge.
- **The lock:** the `rebuildUnderLock` held and free cases, with `acquire` stubbed.

Say this in the PR body, so whoever runs the runbook knows that the rebuild in step 3 is the first real execution of the drop-and-replay against the new DDL.
