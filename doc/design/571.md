# Design: #571 — `GrantFixRound` on `CheckRefused` and `FixerDisagrees`

## The decision: one function says whether a grant is possible and what it briefs

Today two places decide whether a grant can happen, and they can drift apart:
- `allowedResolutions` decides whether a grant is *offered*, using its `fixable` expression (`packages/domain/src/wait.ts:345-350`).
- `conduct.ts:1004-1018` decides what the granted round *is told*, with a ternary on `reason.proposal._tag`.

Both list the same fixable tags. If you add `CheckRefused` and `FixerDisagrees` to only one of them, this ticket's bug comes back in the other direction: the grant is offered but gets a review brief with no findings.

Replace both with one pure function in `packages/domain/src/wait.ts`, exported next to `allowedResolutions`:

```ts
/** What a granted round would be told to fix, or null when there is no criterion (0118 §1: "No branch to fix or no criterion for a fixer means no grant"). */
export function grantCriterion(reason: WaitReason): { printed: { step: Step; detail: string }; findings: Finding[] } | null
```

- `allowedResolutions` becomes `fixable = grantCriterion(reason) !== null`. The `unpushed` rule stays exactly as it is (`wait.ts:360`), so it covers the new rows without any change.
- `conduct.ts:1004` becomes `granted && grantCriterion(reason) !== null ? { grant: { why, asked: null, printed: c.printed }, findings: c.findings } : {}`.
- After this, the brief no longer depends on `ProposedEscalated` alone. A direct `CheckRefused` or `FixerDisagrees` gets the same brief as its escalated form. Those direct variants are never built today (`pass-next.ts:109,329` both `Propose`), but the table offers them a grant, so they get one.

This is also why the old `CheckRefused`/`FixerDisagrees` arms in `tableResolutions` stay without `GrantFixRound`. The grant is added only through `fixable`, the same way `ReviewFindings`, `BuildRed` and `VerifyRed` already get it. Do not write it into the table rows.

## What counts as a criterion, case by case

| reason | criterion when | `printed` | `findings` |
|---|---|---|---|
| `ProposedEscalated{ReviewFindings}` | some `failureScenario.trim()` non-empty (unchanged) | `{ step: 'review', detail: 'Fix the recorded review findings.' }` (unchanged) | `proposal.findings` |
| `ProposedEscalated{BuildRed}` | `output.trim()` non-empty (unchanged) | `{ step: 'build', detail: output }` | `[]` |
| `ProposedEscalated{VerifyRed}` | same (unchanged) | `{ step: 'build', detail: 'merge verification failed: …' }` | `[]` |
| direct `CheckRefused` (`wait.ts:120-127`) | `evidence.trim()` non-empty **or** some finding with a `failureScenario` | see trap below | the findings that have a `failureScenario` |
| `ProposedEscalated{CheckRefused}` (`proposal.ts:101-123`) | `output.trim()` non-empty | see trap below | `[]` (the proposal carries none) |
| `FixerDisagrees`, direct (`wait.ts:92`) and escalated (`proposal.ts:139`) | `said?.trim()` non-empty | `{ step: 'review', detail: said }` | `[]` |

All three existing `ProposedEscalated` rows must come out of `grantCriterion` with the same values they get today.

**`FixerDisagrees` is tied to `said` on purpose.**
- 0118 §1 says a fixer that disagreed is "fixable review findings". The only thing the wait itself holds is the fixer's last word. `said` is `lastCommitEvidence` (`pass-next.ts:354-360`), and it is null when the agent's commit evidence was empty.
- A null `said` means the person would be granting a round with nothing written down to argue against, so that counts as no criterion.
- Do not reach into the run's events to recover the reviewer's findings. `allowedResolutions` works "from the wait alone" (0118 §1, `wait.ts:271`). The board (`apps/board/src/lib/task.ts:1853`) and `resolve-wait.ts:221` call it without the run's stream.

## Trap: a `CheckRefused` from `merge` must not brief `step: 'merge'`

`fixRound` reads `again.printed.step === 'merge'` as *a merge conflict*. It then treats `detail` as the conflict's paths:

```ts
: from === 'merge'
  ? ({ on: 'conflict', base, paths: said } as const)
```

That is `conduct.ts:3474-3481`. `CheckRefused.from` / `.step` can be `'merge'` (`proposal.ts:103`, `wait.ts:122`). A check that refused before the lane would therefore send the fixer a conflict brief made of its own output.

So the `CheckRefused` criterion uses **`step: 'proposed'`** whatever step it came from. Put the origin in the text instead: `` `the ${action ?? 'declared'} check at ${from} refused:\n\n${output}` ``. `action` is nullable on old proposals (`proposal.ts:118-122`).

Pin this with a unit test on `grantCriterion` for `from: 'merge'` that asserts `printed.step !== 'merge'`.

## The coverage test

Rebuild `wait.test.ts:167-170` the same way the `WaitReason` check at `:226-229` is built:

```ts
const tags = ProposalSchema.options.map((o) => o.shape._tag.value)
```

Import `Proposal` from `../src/proposal.ts` as a value, not only as a type (`:10`).

That check only goes green when `parseProposed` has run for all thirteen tags. So the seven missing `it`s are required, not optional:
- one each for `CheckRefused`, `FixerDisagrees`, `MergeRefused`, `NothingProduced`, `BudgetExhausted`, `AnswerUnreadable`, `SetupRefused`;
- `CheckRefused` and `FixerDisagrees` each also need a no-evidence case (no `GrantFixRound`) and an `unpushed` case (no `GrantFixRound`, no `Approve`). Use `unpushedRun` at `:28`.

Do the same on the direct side for `CheckRefused` and `FixerDisagrees`: with evidence, without, and unpushed.

Assert full arrays with `toEqual`, as the existing rows do. `GrantFixRound` comes last because of where it is appended (`wait.ts:360`).

## What follows on its own, and what to check

`resolve-wait.ts:221` enforces `allowedResolutions`. The CLI's `grant-fix-round.ts` and the board's grant button (`task.ts:1853`, `actions.ts:183`) read the same function. None of them needs changing.

Run `git grep -n "GrantFixRound" -- '*/unit/*'` to find tests that asserted `CheckRefused`/`FixerDisagrees` rows *without* the grant. Expect hits in `apps/board/unit`, `packages/conductor/unit/resolve-wait*`, and `wait-disagreement.test.ts`. Those assertions were pinning the bug, so update them to match the new rows.

A conduct-level test that a granted `CheckRefused` round's brief carries the output would need a continuation driven end to end, which is integration territory. In the unit half, the `grantCriterion` tests stand in for it: the brief is now `grantCriterion`'s output passed straight through.

`MergeConflict` keeps its current row (#557/#559).
