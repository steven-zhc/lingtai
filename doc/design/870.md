# Design note for #870: the snapshot writer

## Where it goes

- **`packages/event-store/src/snapshot-writer.ts`** (new). It imports `Effect`, `Queue` and `Scope` from `effect`. From `./snapshots.ts` it imports only the types (`Snapshot`, `SnapshotKey`, `SnapshotStore`). That module's header says it *"imports types only, no driver"* (`snapshots.ts:20`), and this file keeps to that.
- **`packages/event-store/package.json`**:
  - Add `"./snapshot-writer": "./src/snapshot-writer.ts"` under `exports`.
  - Add `"effect": "^3.22.1"` under `dependencies`. That is the same range `packages/env`, `packages/github`, `packages/repo`, `packages/agent`, `packages/conductor` and `apps/cli` already use, so nothing new gets resolved.
  - Run `pnpm install` so `pnpm-lock.yaml` records the importer. A dependency missing from the lockfile fails the next frozen install.
- **`packages/event-store/unit/snapshot-writer.test.ts`** (new). It sits beside `unit/snapshots.test.ts`. It uses `createMemoryEventStore` and `createMemorySnapshotStore` from `test/memory.ts:242`. These are memory only, so the file is unit under 0060 §1, and it never touches `pg`, so `on-postgres.test.ts` has nothing to say about it.

## The signature

```ts
export interface SnapshotWriter { offer(snapshot: Snapshot): void }
export function makeSnapshotWriter(
  store: Pick<SnapshotStore, 'put'>,
  log: (line: string) => void,
): Effect.Effect<SnapshotWriter, never, Scope.Scope>
```

- **`store` is the snapshot store, not the event `Log`.** A caller passes `log.snapshots` (`log.ts:55`). Taking `put` alone also lets a test hand in a gated or failing `put` without building a whole store.
- **`log` is a line sink**, the `(line: string) => void` shape conductor already uses (`conduct.ts:261`, `schedule.ts:394`). It is not the event `Log`. Name the parameter `log` as the ticket does, but keep the two types apart.

## Inside

All of the state is closed over by the returned object:

- `pending: Map<string, Snapshot>`. The key string is `JSON.stringify([streamId, reducer, reducerVersion])`, which is the same `id` the memory store uses (`test/memory.ts:247-248`). Do not join the parts with a delimiter: a `streamId` may contain any character.
- `failing: Set<string>`: the keys whose last `put` failed.
- `closed: boolean`.
- `wake`: from `Queue.sliding<void>(1)`.

**`offer(s)`** is plain synchronous code:

1. If `closed`, return.
2. Compare against the pending entry for the same key. If that entry has a higher `streamVersion`, return. Otherwise set `s` as the entry (a tie goes to the later offer).
3. Call `Queue.unsafeOffer(wake, undefined)`.

A sliding queue of capacity one means any number of offers between two wakes collapse into a single wake. `unsafeOffer` on a queue that has been shut down returns `false` and does not throw, but the `closed` check is what stops the Map from filling up after close.

**The consumer** is a single loop, started with `Effect.forkScoped`:

1. `Queue.take(wake)`.
2. Drain the Map. Take its first entry and **delete it from `pending` before the `put` starts**. Then `yield* Effect.tryPromise(() => store.put(s))`. Repeat until the Map is empty, then go back to step 1.
   - Deleting first is what makes *"an offer that arrives while its key's `put` is in flight becomes the new pending entry"* work with no extra state.
   - A key that is offered again goes back in at the end of the Map's insertion order, so one busy key cannot starve the others.
   - **Do not compare an offer against the snapshot whose `put` is in flight.** The coalescing rule applies to the pending entry only. If an older snapshot arrives during a newer one's `put`, the store answers `'kept'` (0124 §7).
3. Handle each `put` result:
   - **Success**, `'written'` or `'kept'`: delete the key from `failing`. Log nothing.
   - **Failure**: use `Effect.catchAll` on the `UnknownException` from `tryPromise`. This catches a rejection and a synchronous throw inside the thunk alike. If the key is not in `failing`, add it and log one line containing the key's three parts and `String(cause.error)`. If it is already there, log nothing.
   - **Call `log` inside a `try` block** inside an `Effect.sync`. If the sink throws, that throw becomes a defect, and a defect ends the loop for good. Nothing would report that.

On close, an `Effect.addFinalizer` sets `closed = true` and runs `Queue.shutdown(wake)`. When the scope closes, `forkScoped` interrupts the consumer, and the entries still pending are simply dropped.

## Effect API constraints

There are no `async` functions, no `Effect.run*`, and no `Effect.fork`, `forkDaemon` or `runFork` anywhere in the file. The ratchet parses the source with TypeScript (`effect-ratchet.test.ts:7-8`), so even a `runFork` sitting in dead code counts. `Effect.gen(function* …)` is a generator, not `async`, so it is not counted. The baseline `{ async: 64, run: 0 }` for `packages/event-store` stays as it is.

## What interrupting a running `put` actually does

The ticket decides that *"a `put` already running is interrupted"*, and this design keeps that. But `Effect.tryPromise` cannot cancel a promise: interrupting it **abandons** the promise, and the SQL statement still runs to completion or failure on its own.

- What the writer does guarantee: the abandoned promise's settlement goes nowhere. It is not logged, and it is not an unhandled rejection, because `tryPromise` attached the handlers.
- What it does not guarantee: that the statement finished before the store closed. If a caller closes the store straight after the writer's scope, that statement may fail against a closed pool, and nobody hears about it.
- That costs only a snapshot (0124 §5), and waiting is out of scope. Write this down in the file's doc comment so the caller tickets (child 4 and the board child of #866) know the order is theirs: close the writer's scope before the store.
- Do not make the `put` uninterruptible. The ticket's "`put` that never resolves" test would then hang at scope close, and a stuck connection would hang a daemon drain.

## The tests

**A deterministic way to wait.** Wrap `put` in a spy that records each call and resolves a `Deferred`, or a plain promise kept in a variable, when its *n*-th call returns. Await that inside the test's `Effect.gen` instead of sleeping. `Effect.runPromise(Effect.scoped(...))` is allowed under `unit/`, because the ratchet only walks `src/` (`effect-ratchet.test.ts:197`).

**How each case is shown:**

- **"Three offers before the consumer runs"**: make the three `offer` calls one after another in the same synchronous code. JS cannot run the consumer fiber in between, so this needs no assumption about when `forkScoped` first schedules it.
- **The anchor case**: use `createMemorySnapshotStore(events)` for a key whose `(streamVersion, lastSeq, lastAt)` matches no event. Its `put` rejects with `anchorNotInLogError` (`test/memory.ts:267`). Offer a valid snapshot for a second key after it, and assert that the second one is written.
- **"`offer` returns before `put` resolves"**: use a `put` that stays open until the test releases it. Assert that `offer` returned and that `put` was called once. Close the scope without releasing it; the interruption is what ends that fiber. This shows that close does not wait.
- **After close**: return the writer out of `Effect.scoped`, then call `offer` on it. Assert that it does not throw, that `put` is not called again, and that `log` was not called.
