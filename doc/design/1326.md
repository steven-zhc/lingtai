### Design note: #1326, the mode card on `/recipe`

#1306 and #1310 have both landed in this worktree. Every recipe-side reader this card needs already exists, so the change stays inside `apps/board`. Six things below are not obvious from the ticket.

#### 1. Read from the accessors, never from the schema fields

`packages/recipe/src/settings.ts` already holds every reading `modeLines` needs:

- `modeOf(recipe)` at `:255`. Its comment says *"`solo` unless it writes `mode: team`"*, so `recipe.mode === undefined` is the only way to tell that no mode was written. `named` is `recipe.mode !== undefined`, and `mode` is `modeOf(recipe)`.
- `branchOf` at `:265`. In team mode it returns `recipe.branch.personal ?? recipe.branch.main`. The card's `personal` is `branchOf(recipe)` when the mode is team, and `main` is `recipe.branch.main`.
- `assigneeOf` at `:404`, `ticketSourceOf` at `:363` (`'github'` or `'db'`), and `kindsOf` / `excludeOf` at `:310` / `:323`.
- `selectionOf` at `:450`, which returns `{ mode, tickets }`. #1310 added it so that *"the conductor, `lingtai run`, `lingtai status` and the board answer one question one way"* (`:439-441`).

The *Takes* branch should key on `selectionOf(recipe)`: team with `tickets === 'db'` reads *every ticket — local tickets are yours*; team on GitHub names `assigneeOf(recipe)`'s login. The ticket's "local store" is the value `'db'`.

`modeLines` should take the recipe alone, with no second `source` argument, because the source is a reading of the recipe (`ticketSourceOf`). Two arguments would let a test hand in a pair that no recipe can produce.

#### 2. Import the label names, don't retype them

These are exported from `packages/conductor/src/labels.ts`:

- `LANDED_LABEL` at `:27`
- `PR_FIX_LABEL` at `:30`

The board already depends on `@lingtai/conductor` (`apps/board/package.json:22`). `packages/daemon/src/converge.ts:63` imports `@lingtai/conductor/labels` the same way.

For solo's excluded labels, print `excludeOf(recipe)` and not `HOLD_LABEL`.

#### 3. `landsUnattended` stays in the CLI

The predicate is one expression at `apps/cli/src/recipe-flow.ts:192`: `!(steps['proposed'] ?? []).some((a) => 'human' in a)`. The board must not import from `apps/cli`, and that package is not in the board's dependencies.

Write the same expression in `modeLines` and cite `recipe-flow.ts:192` in a comment. Moving it into `@lingtai/recipe` would be a second change touching the CLI, and it is out of proportion for one line.

#### 4. The PR row

The `Pr` schema is at `packages/recipe/src/recipe.ts:3002-3016`. Its `limits` default to `{ turns: 20, wall: '5m' }`, so a present `pr:` block always carries limits. Show `← default` only when `recipe.pr === undefined`.

`agent` is optional, and its comment says *"An absent `agent` means `runtime.agent` where that runtime is one of `DiscussAgent`'s."* No accessor for this exists in any `packages/*/src`; I searched for `prOf` and `*AgentOf` and found none. Show `recipe.pr?.agent ?? recipe.runtime.agent`, and mark the second case `← runtime.agent`. Do not add a resolver: the dispatch that chooses the agent is #1319's and #1311's to own.

#### 5. Header: read the branches from the recipe, not from `view.ref`

`view.ref` is `resolved.ref` (`apps/board/src/lib/recipe.ts:506`), and `packages/project/src/local.ts:254` sets it to `options.base ?? branchOf(resolved.recipe)`. In team mode that is already the personal branch, and a recorded `base` can override it. So the team header takes:

- `main` from `recipe.branch.main`
- `yours` from `branchOf(recipe)`

Solo keeps `base ${view.ref}` exactly as it is now.

#### 6. The refusal: a third fault, and its sentence comes from `problems`

`RecipeRefusedError` is at `packages/recipe/src/resolve.ts:71`:

- It **extends `RecipeInvalidError`**: *"Still an `instanceof RecipeInvalidError`, so every existing catch takes both."*
- `OldSpellingRefusedError` at `:85` extends it in turn.
- The comment says a reader tells these apart *"by `_tag` and never by the sentence"*.

`faultOf` (`apps/board/src/lib/recipe.ts:435-439`) should check `MachineConfigInvalidError` first, as it does today, then `_tag === 'RecipeRefused'`, then fall through to `recipe`. Read the tag as a property (`typeof err === 'object' && err !== null && '_tag' in err && err._tag === 'RecipeRefused'`) and not with `instanceof`, so the test can build the error from the package's own class and still pin the tag. An old spelling (#1308) will then read *recipe refused —* as well. That is correct: it parsed and was refused on its meaning, and the sentence names the fix.

Two places that would go wrong:

- **The wording.** `problem` is `err.message` flattened (`recipe.ts:494`), and `RecipeInvalidError`'s message starts `` `${where} is not valid:` `` (`resolve.ts:59`). *recipe refused — recipe.yml on main is not valid: …* is the wording the mock does not have. For a refused fault, set `problem` to `err.problems.join(' ')`, the sentences alone. Recipe and machine faults keep the message they have today.
- **The editor.** `text: fault.fault === 'recipe' ? await textIfReadable(project) : null` (`recipe.ts:493`) decides whether the editor opens on the broken file (#980). A refused file is exactly the one somebody needs to edit, so make this `fault.fault !== 'machine'`. Check the other two `fault` reads at `page.tsx:254` and `:273` the same way:
  - The header fact at `:254`: use *it was refused, so nothing will be taken from this project*.
  - The paragraph at `:273`: give it a third arm.

  Without these changes a `refused` fault falls into the machine wording.

Widen the `fault` union in the `ProjectRecipe` type (`recipe.ts:416`) and let `tsc` find every reader. Today there are exactly those three, plus the existing `apps/board/unit/recipe-unreadable.test.ts`, which is the natural home for the new `faultOf` and refusal render tests.

#### The graph component

`mode-graph.tsx` does not exist anywhere in the board yet, so this ticket creates it under `apps/board/src/components/`. Make it pure props in, inline SVG out: `{ mode, main, personal | null }`. That leaves #1325 able to draw it on the add step with no change.

#### Checks

Everything named here is unit-reachable: `modeLines` is pure, and the render tests use the existing `.tsx` pattern in `apps/board/unit/`. Nothing depends on `pnpm test:integration`.

The only after-merge witness is the Next build (`apps/release/integration/build.test.ts`), which catches a server-only import reaching a client graph. To stay out of its way, keep `ModeCard` and `mode-graph.tsx` free of `"use client"`, and do not import anything from `@lingtai/conductor` beyond `/labels`.
