# Design note for #754

## Where it goes

- **`apps/cli/src/setup-card.ts`** (new). It holds `renderSetupCard(facts)`, `renderReadyLine(...)`, the `SetupCardFacts` type and `formatTrialTime(ms)`. It imports nothing that touches a file or a process: `paint` from `@lingtai/env/colour`, `redactUrl` from `@lingtai/env`, and a type plus one helper from `doctor.ts` (below).
- **`apps/cli/src/setup-build.ts`**: `tryTheBuild` and `askInstallAndBuild` return a trial outcome.
- **`apps/cli/src/recipe-flow.ts`**: `askRecipe` passes the outcome up.
- **`apps/cli/src/first-project.ts`**: `runLocalBranch` now lives here, not in `init.ts` as the ticket says (`first-project.ts:370`). Its `ok` value carries the outcome.
- **`apps/cli/src/doctor.ts`**: one export, described below.

Nothing else changes, and nothing calls `renderSetupCard` outside its tests.

## The ticket's trial-build citations are out of date

`TrialResult` is no longer a single result. Since #734 it is one entry per command, `{command, outcome: 'passed'|'failed', evidence} | {command, outcome: 'not-run', because}`, and `TrialReport` holds `results` and `nothingDeclared` (`setup-build.ts:26-38`). `tryBuild` is called at `setup-build.ts:268-271`, not 262-265. The card's outcome is something new that sits above the per-command results. It does not replace them.

```ts
export type TrialOutcome =
  | { trial: 'passed'; ms: number }
  | { trial: 'failed-kept'; command: string; ms: number }   // first failed command
  | { trial: 'not-run'; because: 'declined' | 'no checkout' | 'no checks' }
```

Put it in `setup-build.ts` and export it, because that file produces it. `setup-card.ts` imports the type.

How each outcome comes out of `tryTheBuild` (`setup-build.ts:238-310`):

- `build.length === 0` gives `no checks`. Check this before `tryBuild === null`, so an empty list on a machine with no checkout still reads *no checks*.
- `input.tryBuild === null` gives `no checkout`.
- `check.answer === 'no'` gives `declined`. This includes the case where `--defaults` forces `check: 'no'` (`recipe-flow.ts:327-329`), which is a decline.
- A report with no `failed` result gives `passed`. This follows the existing rule *"Colour is decided by what failed, never by what was not run"* (`setup-build.ts:275-276`), so a mix of passed and not-run is still `✓`.
- `decide.answer === 'write'` gives `failed-kept`, naming the first failed result's `command`.
- The `edit` refusal and `TrialInterrupted` are refusals as they are today. They return no outcome and no time.

Measure time with `Date.now()` taken immediately before and after the `await input.tryBuild(...)`. Do not use `performance.now()`: `vi.useFakeTimers()` fakes `Date` by default, and the Done-when test runs under fake timers, so `tryBuild` can call `await vi.advanceTimersByTimeAsync(125_000)` and the result can assert `ms: 125_000`.

`AskInstallAndBuildResult` (`setup-build.ts:64`) becomes `{ changes: RecipeChange[]; trial: TrialOutcome } | { refused: string }`. `askRecipe`'s return becomes `{ ok: true; trial: TrialOutcome } | { refused }`: keep `setup.trial` in a local after `recipe-flow.ts:338` and return it at `:433`. `FirstProjectOutcome`'s local arm (`first-project.ts:185`) gains `trial: TrialOutcome`, set at `:599`.

**This breaks existing tests.** `unit/recipe-flow.test.ts` asserts `expect(result).toEqual({ ok: true })` at least ten times (`:111`, `:170`, `:218`, …). `toEqual` ignores a key only when its value is `undefined`, and `trial` is always defined. Change those assertions to `toMatchObject({ ok: true })`, or assert the trial where the test is about the trial. The ticket requires `recipe-summary.test.ts` and `init.test.ts` to pass unedited, and the change above leaves both untouched. `first-project.test.ts` uses `toEqual` only on the `github` arm (`:788`, `:1059`, `:1118`, `:1129`, `:1226`), and that arm does not change. `add-github.ts:367` reads `askRecipe`'s refusal only, so the wider `ok` type compiles there.

## The facts the renderer takes

`SetupCardFacts` is a plain object, and every field is something the renderer only formats:

```ts
{
  command: 'init' | 'add'; project: string; updated: boolean
  home: string; homeIsNew: boolean; userHome: string        // userHome: for the ~ substitution, passed in, never os.homedir()
  store: StoreChoice                                         // from @lingtai/env
  runtimes: readonly RuntimeFound[]                          // runtimes.ts:16-23
  recipe: CardRecipe; trial: TrialOutcome; recipePath: string
}
```

The renderer must not call `os.homedir()`, because a test should not depend on the machine's real `$HOME`. That is why `userHome` comes in on `facts`.

`CardRecipe` is the recipe half: `code` (the checkout's top level), `base`, `remote`, `tickets: 'db' | 'github'`, `kinds`, `writer` and `reviewer` (each `{agent, model} | null`), `checks`, and `approves`. Add a pure `cardRecipe(recipe: Recipe, code: string): CardRecipe` beside the renderer that reads a recipe **already resolved** the same way `summariseRecipe` does (`recipe-flow.ts:203-215`): the first `agent:` at `implement` and at `review`, the `run:` commands at `build`, `human` at `proposed`, and `baseOf(recipe)`. Tests feed it `resolveSource(text, path, path).recipe` built from a literal string, so nothing reads a file.

**Do not extend `Summary` or `renderSummary`.** `recipe-summary.test.ts` has to pass unedited, and #773 deletes `renderSummary` anyway.

Row decisions the ticket leaves open:

- **`log`.** For Postgres, use `new URL(choice.url).hostname`. The host alone is safer than `redactUrl`, which still prints the user. If the URL does not parse, print `Postgres · (a URL that does not parse)`, the same words `redactUrl` uses (`packages/env/src/index.ts:774`). For SQLite, use `basename(choice.path)`. For a refusal, print `choice.refused` in `paint.fail`.
  - Do not reuse `describeStore` (`index.ts:753-758`) for a chosen store: it prints the path and `← from`, which is longer than one fact.
- **`agents`.** `signed-in` gives `✓`. `signed-out` and `not-installed` give `✗`. `did-not-start` gives `?`, which is the "could not tell" case. Those are the four `AuthState` values in `packages/agent/src/runtime.ts:248`.
- **`lands on`.** A remote that is an absolute path gets `~` substituted. Pass any other remote through `redactUrl`.
  - Watch the case where `redactUrl` cannot parse the remote: it returns `(a URL that does not parse)`. An scp-style remote like `git@github.com:o/r` is exactly that case. Print such a remote as written: it has no `user:password@` form to leak.
- **Trial time.** Round to the nearest second. Under 60s it reads `41s`. From 60s up it reads `2m 05s`, with the seconds padded to two digits. Under 1s it reads `<1s`, never `0s`.
- **Label column.** Pad from the widest label, which is `lands on`. Measure with `width()` from `output.ts:45`, so escapes are not counted (the `labelled` comment in `doctor.ts:3340` explains why). The ticket's own example puts no space between `lands on` and its value. Use one consistent gap of two spaces everywhere.

## The ready line uses doctor's own counting

`toFix` is not exported (`doctor.ts:3402`). It is also not the same thing as `report.warned + report.failed`, because it merges rows that share a `fix` and drops deferred rows (`doctor.ts:3408-3414`). Export it, or a one-line `toFixCount(report)` built on it, from `doctor.ts`, and have the ready line take that number. This keeps `N to fix` equal to the count doctor's own short view prints on the line below (`doctor.ts:3355`).

Which branch to take also comes from `toFix`: any entry with `status === 'fail'` gives `✗ not ready`. Do not use `report.failed`, so the card and doctor's block cannot disagree.

Give the input as `{ report: DoctorReport } | { threw: string }`. `all N passed` uses `report.ok`, the same field doctor's short view uses (`doctor.ts:3354`). The ready line is one string. Printing doctor's blocks under it is #773's job.

## Tests

Put the tests in `apps/cli/unit/setup-card.test.ts` (pure) and the timing test in `unit/setup-build.test.ts`. Also add one `first-project` test showing `trial` reaching `runLocalBranch`'s return value: the existing local-branch tests already inject `tryBuild` through `liveTrialBuild`'s seam, so check how they stub it first.

- **Find a row by its label.** Strip colour with `stripColour` (`output.ts:14`), then `lines.find(l => l.trimStart().startsWith('trial '))`.
- **Plain mode.** Set `NO_COLOR=1` with `vi.stubEnv`. `coloured()` is read on every call (`packages/env/src/colour.ts:55-57`), so the stub takes effect without a reload. Assert the output has no `\x1b`.
- **The password test.** Use `postgres://u:s3cret@db.x.supabase.co:5432/p` and assert `s3cret` appears nowhere in the card.

This is all unit-level. `pnpm test` and `pnpm typecheck` are enough, and nothing here touches the integration half.
