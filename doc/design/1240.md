# Design note for #1240: runtime.limits grouped as run, attempt and ticket

The ticket already gives the schema, the defaults, the refusal messages and the list of readers. This note covers only the decisions the ticket leaves open, where two reasonable builds would come out different.

## 1. Refuse the old keys before zod sees them, not in the schema

**Decision:** add a function `retiredLimits(raw)` to `packages/recipe/src/resolve.ts`, next to `retiredTier` (`resolve.ts:290`). Call it at both places that already call `retiredTier`, before `Recipe.safeParse` runs:
- `resolve.ts:248` (`resolveSource`)
- `packages/recipe/src/declared.ts:49`

It reads `raw.runtime?.limits`. It returns one sentence for each flat key it finds there: `rounds`, `restarts`, `turns`, `wall` or `usd`. Each sentence names the new key and its group.

A file that mixes the two shapes (a flat `rounds` beside a grouped `attempt:`) is refused in the same way. The flat key is the problem, whatever sits beside it.

**Why not in the schema:** the alternative is to put the old names into the new `limits` object as `z.never({error}).optional()` fields, the way `boundsThePass` does it (`recipe.ts:213-226`). That would leave `rounds?: undefined` in the inferred `Recipe` type. Then a reader still writing `` `${limits.rounds}` `` or `limits.rounds ?? 2` would still pass typecheck. The ticket relies on typecheck going red at every reader this commit has not moved. A check on the raw file keeps the type clean.

Two side effects:
- The strict `limits` object would also refuse the old keys with zod's generic "unrecognized key" message. Because this check throws first, the named refusal is the one a person reads.
- The `repair` sentence in `unknownKeys` (`resolve.ts:340-345`) says *"now one number, `runtime.limits.rounds`"*. It moves to `runtime.limits.attempt.refusalFixes` in the same edit. Otherwise it points somebody at a key that is itself refused.

`boundsThePass` stays the mechanism inside a dispatch's own `limits:`:
- Widen its parameter to `'rounds' | 'restarts' | 'refusalFixes' | 'conflictResolutions' | 'newAttempts'`.
- Give each its sentence naming `runtime.limits.attempt.<k>` or `runtime.limits.ticket.newAttempts`.
- Put the three new names as fields next to the two at `recipe.ts:293-294`.

That type pollution is acceptable there, because nothing reads a dispatch's `rounds`.

## 2. `limitsFor` answers one run, `ceilingOf` answers the whole block

`limitsFor(recipe, step)` (`packages/recipe/src/settings.ts:140`) returns `Recipe['runtime']['limits']` today: the ceiling, with turns and wall narrowed by the step's dispatches.

**Decision:** its return type becomes `Recipe['runtime']['limits']['run']`, i.e. `{ turns, wall, usd? }`. It narrows `ceiling.run` the same way it does today. A dispatch can only narrow `turns`/`wall`, so the other two groups never belong in a per-step answer.

`ceilingOf` (`settings.ts:177`) keeps returning the whole grouped block. Its doc already says *"the day the ceiling moves it moves here"*.

In the narrowing check (`recipe.ts:3458-3535`), `ceiling` becomes `recipe.runtime.limits.run`. Its two messages name `runtime.limits.run.turns` and `runtime.limits.run.wall`.

## 3. Ceilings and routing: rename the policy, not the counters

There are three layers. Only the first is renamed in this ticket.

**Renamed — the limits, which are the recipe's:**
- `RoutingPolicy` (`packages/domain/src/routing.ts:36-41`) becomes `{ refusalFixes, conflictResolutions, newAttempts }`.
- `offerFor`'s policy argument takes that type.
- `respond.ts:709` compares against `policy.conflictResolutions`.
- `Ceilings` in `run-attempt.ts:797-814` becomes `{ refusalFixes, conflictResolutions, newAttempts, newAttemptsSpent }`, and `NOTHING_SPARE` follows it.
- `run-attempt.ts:1627` becomes `{ refusalFixes: roundLimit, newAttempts: restartLimit, conflictResolutions: ceilings.conflictResolutions }`.
- `conduct.ts`, which computes `Ceilings` from the recipe (#462), reads `ceilingOf(recipe).attempt` and `.ticket`.

**Kept — the spent counters:** `Spent.rounds`, `Spent.conflictRounds`, `Spent.restarts` (`attempt-next.ts:138`, `attempt.ts:247`, `run-codec.ts:143`). They are folded from the stream and cached in snapshots. Renaming them is a codec-version change, and the log-rename ticket owns those names. The same applies to the `Ceiling` union (`run-attempt.ts:1211`), whose strings go onto `CeilingReached`.

**One comment at the junction:** where `run-attempt.ts:1627` pairs the new limit names with the old counter names, add a comment saying `refusalFixes` is spent as `rounds` and `conflictResolutions` as `conflictRounds` until the log rename.

**Grant behaviour does not change:** a grant caps `refusalFixes` (`run-attempt.ts:1448`) and never `conflictResolutions`, which is #1200's rule (`routing.ts:39`).

**The unit test for "1 refusal fix, 3 conflict resolutions":** write it against `offerFor`/`routeNext` in `@lingtai/domain`, not through `runAttempt`. That is the smallest place where both counters and both limits meet, and it needs no IO.

## 4. `attemptCeiling`'s new input and sentence

`attemptCeiling` takes:
- `{ refusalFixes, conflictResolutions, newAttempts, turns, wall, wallMs, usd?, steps? }`
- `wall`, `turns` and `usd` come from `limitsFor(recipe, 'implement')`, i.e. the run group.
- `steps` stays as it is: the per-step list of narrowed run bounds (`ceiling.ts:68-70`).

Arithmetic:
- per attempt: `1 + refusalFixes + conflictResolutions + BOUNDS.stepRedos`
- total: `(newAttempts + 1) × per-attempt + BOUNDS.personAsks`
- with the new defaults: `3 × 16 + 5 = 53`

The wall and dollar figures multiply the same total.

Then add one clause per other agent step, none of them summed into the figure:
- `design`
- `review`: once after each `implement`, once more after a `mergeBaseBranch` that touched the branch's files
- a judge
- triage

The ticket deliberately breaks the old *"byte-identical"* comment block (`ceiling.ts:44-56`). Rewrite it rather than leave it claiming something false.

The zero cases name `runtime.limits.attempt.refusalFixes: 0` and `runtime.limits.ticket.newAttempts: 0`. Every caller goes through `filter.ts:439-440`, which reads `ceilingOf(...).rounds`/`.restarts` today. Change it there once.

## 5. Recipe writers write the new paths and migrate nothing

The builders in `packages/recipe/src/answers.ts` change as follows:
- `roundsChange` (`:119-122`) splits into `refusalFixesChange` and `conflictResolutionsChange`, at `['runtime','limits','attempt',…]`.
- `restartsChange` (`:195-198`) becomes `newAttemptsChange` at `['runtime','limits','ticket','newAttempts']`.
- `turnsChange`, `unboundedTurnsChange`, `wallChange` and `budgetChange` move under `'run'`.

`unboundedTurnsChange`'s caller checks that the file does not already declare turns (`answers.ts:124-130`). That check must read `runtime.limits.run.turns`.

None of these writers rewrites a flat block it finds in the file. A `lingtai add` against an old-shaped file then leaves a file that still refuses, and the refusal names the new key. That matches the ticket's *no migration*: the two old numbers become three, and only the operator can say what was meant.

In `packages/project/src/local.ts:171-179`, the provenance loop walks the nested `LIMIT_DEFAULTS` and emits keys such as `runtime.limits.attempt.refusalFixes`. `usd` keeps its own branch, now `runtime.limits.run.usd`.

## 6. The refused `--rounds` flag

Commander's own error for an unknown option names nothing useful. So keep `--rounds <n>` declared but hidden on `lingtai add`/`init` (`commands.ts:85,537`, `init.ts:270`). If it is present, fail the parse with a sentence naming `--refusal-fixes` and `--conflict-resolutions`. The *"refused naming both"* unit test is on that parse.

## 7. Tests and fixtures

- Most of the work is moving fixtures. Grep `rounds:` / `restarts:` under every package's `unit/`, `test/` and `integration/`.
- Move the integration fixtures too, even though `pnpm test:integration` cannot run in this pass. The unit-level check that stands in for them is `resolveSource` refusing each old key. A fixture left flat would then fail after the merge with a named refusal, not silently.
- `packages/recipe/unit/settings.test.ts`'s *nothing reaches past them* grep for `recipe.runtime.limits` must stay green. Read through `ceilingOf`/`limitsFor`; do not inline the path.
- Every new function here is synchronous and pure. Nothing in this ticket adds an `async` or an `Effect.run*`, so `effect-ratchet.baseline.json` must not move.
