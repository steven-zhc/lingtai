## Design: #1359, the queue's stage spans

### The decision: the stage's context goes with the fiber, not with AsyncLocalStorage

The ticket says a raw `Effect.withSpan` is not enough. The bigger trap is that a plain `context.with(stageCtx, …)` around a stage is not enough either.

The board's context manager is `AsyncLocalStorageContextManager` (`apps/board/src/lib/telemetry.ts:199`). Effect 4 runs a fiber's continuations from a shared dispatcher. `MixedSchedulerDispatcher.scheduleTask` queues the task and calls `setImmediate(this.afterScheduled)` only when nothing is pending. `runTasks` then drains every queued task in that one callback (`node_modules/.pnpm/effect@4.1.2/node_modules/effect/src/Scheduler.ts:231-250`). Whichever context scheduled the first task is therefore the context every task in that batch resumes in. Two consequences:

- **Within one project:** the `look` that runs after a listing resumes in the listing's context, so its children would be parented to `queue.list`.
- **Across projects:** `githubQueue` runs projects concurrently (`board.ts:1361-1376`), and each one has its own `Effect.runPromise` (`board.ts:995`). One project's continuation can resume in another project's context. This is the "do not mix trace context" edge.

`look`, `why` and the blocker reads are Effects. Their promise thunks live inside packages: `links.listBlockedBy` is called from `packages/conductor/src/blockers.ts:67-69`, and `readTasksEffect`, `readProjectLocks` and `readControlOnce` from `apps/board/src/lib/why-read.ts:51-55`. The board cannot wrap those thunks one by one.

So use Effect's own per-primitive hook, the one the conductor's bridge uses. That bridge's comment says *"Called for every primitive the fiber evaluates: it runs each one with the fiber's span as the active OpenTelemetry span, which is what an api span started in a promise underneath finds as its parent"* (`packages/conductor/src/telemetry.ts:116-127`). The run loop calls `cache.tracerContext(current, this)` for every primitive when a tracer has `context` (`effect/src/internal/effect.ts:698-700`). The cache is rebuilt from the fiber's context (`:791-798`), so a tracer provided to a region applies to that region.

Do not reuse the conductor's `bridgedTracer`. It starts spans on `SCOPE = 'lingtai-conductor'` (`packages/actions/src/spans.ts:18`, used at `telemetry.ts:73`). The board's `OnlyScope` exports only `'lingtai-board'` (`apps/board/src/lib/telemetry.ts:17`, `:195`), so those spans would never be exported. Write a small board-local adapter instead, beside `traced` in `apps/board/src/lib/timing.ts`:

- **`ApiContext`:** a `Context.Reference<otel Context | undefined>`, defaulting to `undefined`. It is the OpenTelemetry context this fiber region belongs to.
- **`boardTracer`:** `Tracer.make({ span: (o) => Tracer.nativeTracer.span(o), context: (primitive, fiber) => … })`.
  - `span` delegates to the native tracer, so the package `Effect.withSpan`s that exist (e.g. `packages/projector/src/spend.ts:146`) still export nothing. That keeps "no broad export".
  - `context` reads `fiber.getRef(ApiContext)`. It runs `primitive['~effect/Effect/evaluate'](fiber)` inside `context.with(ctx, …)` when that ref is set, and plainly otherwise. That key is the one the conductor already relies on (`packages/conductor/src/telemetry.ts:35`), and `EffectPrimitive` is marked `@stability stable` (`effect/src/Tracer.ts:47-58`).
- **`tracedEffect(name, effect)`:** an arrow returning an Effect, never `async` and never `Effect.run*`, so the ratchet does not move. It:
  1. reads `ApiContext`;
  2. starts `trace.getTracer('lingtai-board').startSpan(name, {}, parent)`;
  3. runs `effect` with `ApiContext` set to `trace.setSpan(parent, span)`;
  4. in `Effect.onExit`, sets `ERROR` on a failure (never the cause, which may carry a URL; see `timing.ts:124-125`) and ends the span.

`askProject` captures `context.active()` synchronously before `Effect.runPromise`. That is the `queue.project` context, because `askProject` is called inside `traced`'s callback (`board.ts:1364-1367`). It then pipes the whole generator through `Effect.withTracer(boardTracer)` and `Effect.provideService(ApiContext, captured)`. That is still one run (`board.ts:994`, *"One run for every read"*).

Because each fiber carries its own `ApiContext`, it no longer matters which batch resumed it. That is what keeps concurrent projects apart.

With telemetry disabled, no provider is installed. `startSpan` returns a non-recording span and `context.with` on the no-op manager just calls the function. No exporter is created, and values and call counts are unchanged.

### Where each stage goes in `askProject`

| Stage | What it wraps | Parent |
|---|---|---|
| `queue.list` | The `Effect.tryPromise(runnableNow…)` (`board.ts:998-1005`) | `queue.project` |
| `queue.look` | `explain.look(filter)` (`:1011`) | `queue.project` |
| `queue.explain` | Each `explain.why` (`:1017` failed listing, `:1046` listed) | `queue.project` |
| `queue.select` | `select_(offered.runnable)` (`:1037`) | `queue.project` |
| `queue.select-base` | The second `select_` (`:1041`) | `queue.project` |
| `queue.blockers` | `readBlockersEffect` (`:1042`) | `queue.project` |

- **`queue.list`:** wrap only the `tryPromise`. The existing `Effect.map`/`Effect.catch` (`:1006-1007`) stays *outside* the stage, so the stage sees the rejection and ends `ERROR` before the catch turns it into `{ ok: false }`.
- **`queue.look` and `queue.explain`:** wrap only on the branch that calls them. The `explain === undefined` / `look === null` branches stay as they are and emit nothing.
- **`queue.explain` on a failed listing:** this is the sibling of a failed `queue.list` that shows the explanatory work after a failure.
- **`queue.select`:** `select_` stays a function. Wrap its result at the call site, so the same helper produces two names.
- **`queue.select-base`:** only when `passedBase.length > 0`, as today.
- **`queue.blockers`:** always present on the listed path, because the call always happens. That holds even when it reads nothing (no `blocked-by` skips, `links === null`, every entry a cache hit, `blockers.ts:58`, `:63-65`). The span is the step that ran, not a promise that GitHub was asked. Do not add a pre-filter to skip it.

`queue.select`, `queue.select-base` and `queue.blockers` belong to the listed path only.

- **Attributes:** none. The project is already on the parent, and the children's count is the number of `github.request`/`db.acquire` children.
- **Value-returned answers:** a `look` that comes back unreadable, or a `why` of `null`, is a value. Neither marks its stage failed.
- **A select rejection:** it fails the Effect as today, and reaches the outer `catch` (`:1050`) after `queue.select` has ended `ERROR`.

Read order, fan-out (`Effect.all(…, { concurrency: 'unbounded' })` at `blockers.ts:81`), cache policy and every returned shape are untouched. The stages wrap expressions and do not reorder them.

### Tests: a new `apps/board/unit/queue-stages.test.ts`

Reuse `trace-spans.test.ts`'s setup: `installTracing(on, none, exporter)`, the `parentOf` helper, and the `afterEach` that clears the observers and disables `trace`/`context` (`trace-spans.test.ts:64-90`). Call `askProject` itself, not `githubQueue` with an injected `ask` (that is what `trace-spans.test.ts:164-192` does, and that test stays as it is). Run it under a `traced('queue.project', …)` so there is a parent.

- **Fakes.** Pass `select` and `explain` as options (`board.ts:989`). A `filter.tickets` client and a `filter.links` work as in `blocked-skips.test.ts:38-68`.
  - Each fake does its IO through the real request observer, as `trace-spans.test.ts:179-181` does: `githubJson` with `fetch` stubbed.
  - Put an `Effect.yieldNow()` or an awaited resolution *before* each request. Execution is then resumed from the dispatcher, which is the case that proves the context is live during execution and not just while the Effect value is built.
- **Parents.** Check `queue.list`, `queue.look`, both `queue.explain` paths, `queue.select`, `queue.select-base` and `queue.blockers` → `queue.project`. Then check each `github.request` → its stage. Assert by name and parent, never by line or by timing.
- **Deferred.** Hold a `select` fake on an unresolved deferred: `queue.select` is open and has no `github.request` child. Hold `fetch` inside the listing: `queue.list` is open with an open `github.request` under it.
  - The exporter sees only ended spans. Read starts through a `SpanProcessor` whose `onStart` records them, added beside the exporter, or by inspecting after releasing the deferreds in order.
- **Skipped.** With no `explain` and with `passedBase` empty: no `queue.look`/`queue.explain`/`queue.select-base`, and the fakes' call counts are unchanged.
- **Concurrent.** Two `askProject`s under two different `queue.project` spans, with deferreds released in interleaved order. Every child's trace and parent stays with its own project. This is the test that fails without the `ApiContext` hook.
- **Rejected.** A rejecting listing: `queue.list` ends `ERROR`, and `queue.look` plus `queue.explain` are siblings under the project. The answer is `unanswered` with the same `problem` as today. A rejecting `select`: `queue.select` ends `ERROR` and the answer is the outer `catch`'s.
- **Disabled.** Without `installTracing`, the same values and call counts as with it.

No integration test is needed or wanted. The claim that stands in for the live trace: the `github.request`s the listing and blocker reads make go through the observer installed in `trace-seams.ts:18-29`, and the stage context is active when their thunks run.

### Not an ADR change

No accepted ADR is contradicted. The new spans are started by the board, as `doc/design/1144.md:3` requires (*"shared packages start no spans of their own"*). They carry no attribute, which stays within what `timing.ts:136` allows: *"numbers, booleans and a project's name, never a URL, a title or a body (0101 §6)"*. `ApiContext`, `boardTracer` and `tracedEffect` add no `async` function and no `Effect.run*`, so `effect-ratchet.baseline.json` must not move.
