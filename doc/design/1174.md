# Design note for #1174: the commands on `prj-` move into `@lingtai/project`

## Where it goes

Create one new file, `packages/project/src/commands.ts`, and export it from `packages/project/src/index.ts:1-6`. It holds `pauseProject`, `resumeProject`, `recordTurn`, `registerProject`, `ProjectPauseAnswer` and `otherOwner`. The shared helper and the retry stay private to the file.

Today the done-when grep finds exactly six lines, and all six must go:
- `apps/cli/src/conduct.ts:898,900`
- `packages/conductor/src/onboard.ts:568,640`
- `packages/daemon/src/control.ts:732,749`

## The read: two shapes from one call

Three of the commands decide on a `ProjectState`. `registerProject` also needs the number of events on the stream. `registrationLine` prints `its ${prior.length} earlier event(s)` (`onboard.ts:620-625`), and `readProjectStateEffect` (`packages/project/src/state.ts:43-52`) returns only the reduced state.

So split that read in `state.ts`:
- a non-exported `readProjectEvents(project, store)` that returns the envelopes, with the same `tryPromise` → `Error` mapping as today;
- `readProjectStateEffect` becomes `readProjectEvents(...).pipe(Effect.map(reduceProject))`.

Both shapes then come from one `store.read(projectStream(…))` in the module. Don't add a second read in `commands.ts`. You can use `state.version` as the expected version without checking the last envelope: `reduceProjectEvent`'s `default:` branch also spreads `...at` (`packages/domain/src/project.ts:82-83`, and line 63 of the switch). So `state.version` equals the last envelope's version, which is what onboarding computes by hand today (`onboard.ts:594`).

## One retry, two users

Write the retry once, as a private combinator: run the attempt; on `ConcurrencyError`, run it once more; map any other error to `Error`. That is `control.ts:752-758` lifted out.

- `transitionProject(store, project, transition, answer)` is built on it, as in the ticket. It is used by `pauseProject`, `resumeProject` and `recordTurn`.
- `registerProject` is also built on it, but not on `transitionProject`. Its attempt is: read the events, run the owner guard, append. Because the guard is inside the attempt, the retry re-runs it on the re-read for free. That is the "again on the re-read" the ticket asks for.

Import `ConcurrencyError` as a **value** from `@lingtai/event-store/store`. It is defined in `packages/event-store/src/event-store.ts:62`, and that file's top-level imports are `effect` and its own siblings (`:15-43`). Never import it from the barrel.

## Signatures, and decisions the ticket leaves open

- **`store: EventStore` is required on all four commands.** There is no default and no `defaultLog` fallback. Every caller already has a store, or holds the barrel itself:
  - the board passes `store` (`apps/board/src/lib/locks.ts:258`);
  - the CLI's `project-pause.ts` already imports `eventStore` (`:20`), so it passes `options.store ?? eventStore` at `:75` and `:101`;
  - `record` has `store` in hand (`conduct.ts:891`);
  - onboarding keeps its `import { eventStore } from '@lingtai/event-store'` (`onboard.ts:4`) and passes it in.

  The done-when bans `eventStore.read(` and `eventStore.append(` in `onboard.ts`. It does not ban the import.
- **`registerProject(project, data, { store })`. The owner guard reads `data.owner`, not a separate `owner` option.** `data` is the parsed `ProjectConfigured` payload, and its `owner` is the owner being written (`onboard.ts:581-583`, `:645`). A second `owner` argument could only drift from it. **When `data.owner` is `null`, the guard is skipped.** That is today's behaviour for `addLocalEffect`, which has no guard (`onboard.ts:640-661`). Whether a local registration should be refused over a GitHub-owned name is a separate question; this ticket doesn't change it.
- **`registerProject` returns a union:**
  - `{ kind: 'taken'; holder: string }`, or
  - `{ kind: 'registered'; before: ProjectState; priorEvents: number }`.

  `addEffect` turns `taken` into its existing `log(taken(...))` and `{ ok: false }` (`onboard.ts:575-579`). A taken name is an answer, like `ProjectPauseAnswer`, not an error. `before` and `priorEvents` must come from **the read the successful append used**, which is the re-read when there was a retry. Don't take them from the first read.
- **`otherOwner` moves into the module and takes `(state: ProjectState, owner: string)`**, because the attempt has already reduced the stream. Move its unit cases from `packages/conductor/unit/onboard.test.ts:374-378` to `packages/project/unit/`, building the state with `reduceProject([...])`.
- **`registrationLine` stays in `onboard.ts`** (it reads the recipe) and becomes `(before: ProjectState, priorEvents: number, repo, resolved)`. `updated` becomes `isRegistered(answer.before)` at both `:601` and `:660`. The cases at `onboard.test.ts:353-368` reduce first and pass the count.
- **`recordTurn(project: string, seen: TurnObservation, store)`.** `seen` is `turnTransition`'s second parameter (`packages/domain/src/project.ts:214-217`). `recordTurn` *gains* the one retry. Today's `record` has none (`conduct.ts:897-900`), which is the edge the ticket names. `record` becomes `recordTurn(name, seen, store).pipe(recovering(...))`. The `recovering` from `apps/cli/src/exit.ts:24` catches the whole cause, typed failure included, so the log line at `:902-903` is unchanged. `recordTurn`'s answer can be `void`.

## The `ProjectConfigured` literal and `doc/events.json`

Write the append in `registerProject` as `store.append(projectStream(project), state.version, [{ type: 'ProjectConfigured', actor: 'conductor', data }])`. The literal goes inside the call, and the finder matches the callee by property name `append` (`packages/domain/scripts/events.ts:503-510`).

**`doc/events.json` will change by more than line numbers, and that is expected.** `ProjectConfigured` has two sites today, both in `onboard.ts` (`doc/events.json:901-904`). After this change it has one, in `packages/project/src/commands.ts`. The staleness test compares the **number** of sites, not their URLs (`packages/domain/unit/events-json.test.ts:50-53`: `sites: sites.length`). So the count going from 2 to 1 turns it red until you run `pnpm events:generate`. Commit what that generates. The only rows that should change are `ProjectConfigured`'s `sites` and the URLs for lines that moved. A diff to any other field of any event means the literal was moved wrong.

The other four types are covered by `ELSEWHERE` rows anchored in `packages/domain/src/` (`scripts/events.ts:137-142`, `:186-190`). Those rows are untouched, and the moved `append([next])` calls carry no literal, so the finder still finds nothing there.

## The daemon and its tests

- Delete `control.ts:725-779`. That is `ProjectPauseAnswer`, the private `readProject`, `transitionProject`, `pauseProject` and `resumeProject`.
- Delete the re-exports at `packages/daemon/src/index.ts:53-55`, and any imports in `control.ts` that only those lines used (`ConcurrencyError`, `pauseTransition`, `resumeTransition`, and so on). `pnpm lint` catches the rest.
- `packages/daemon/unit/project-lock.test.ts:10` imports both commands from `../src/control.ts`. Its `describe('pauseProject and resumeProject')` block (`:53` onward) moves to `packages/project/unit/`. The guard tests above it use `pauseProject` only to set up state, so they import it from `@lingtai/project`. The daemon already depends on it (`packages/daemon/package.json:20`).
- The board's import line `locks.ts:13` keeps `raiseDayCeiling` and `readControl` from `@lingtai/daemon/control`. Only the two commands move to the existing `@lingtai/project` import at `:30`.

## The import test

`modulesOf` (`packages/domain/test/ts-modules.ts:16-17`) also reports `import(…)`. `state.ts:23` has exactly that dynamic import of the barrel, and it is the lazy load that is allowed. So the new unit test must assert on **static** `import` and `export … from` declarations only, with the specifier exactly `'@lingtai/event-store'`, across every file in `packages/project/src`. If it counted everything `modulesOf` returns, it would go red on `state.ts` the moment it was written.

## The ratchet

`packages/project` is at `{ "async": 0, "run": 0 }` (`packages/domain/unit/effect-ratchet.baseline.json:12`). The four commands are Effect-only, with no promise faces. Every caller is already inside an Effect:
- `setProjectPaused` is an `Effect.gen` (`locks.ts:253`);
- `pauseProjects` and `resumeProjects` are Effects (`project-pause.ts:61`, `:87`);
- `record` is an Effect;
- `addEffect` and `addLocalEffect` are `Effect.fn`.

A face such as `pauseProjectPromise` would add a `run` the baseline doesn't allow, so don't add one.

## What stands in for the log

None of this can be checked against production `events`. The unit tests on `createMemoryEventStore()` are the claim.

**The race tests.** To produce the race, give the command a store that wraps the memory store. On the first `append`, the wrapper appends a competing event at the same version, then forwards the call, which then hits `ConcurrencyError`. Three tests use it:
- **`recordTurn` loses the race:** the competing event is the same `ProjectRefused`. After the re-read, `turnTransition` returns null and the stream has exactly one refusal.
- **`registerProject` loses the race to another owner:** the competing event is a `ProjectConfigured` with that owner. The answer is `taken`, and the stream's last event is the competitor's.
- **`registerProject` against an owner already on the stream:** with no race at all, it answers `taken` and appends nothing.

**`priorEvents`.** On a stream that started with `ProjectOnboardingStarted`, the answer says `priorEvents: 1` and `isRegistered(before) === false`. That is the *added* path from #163, which is what `registrationLine`'s doc comment (`onboard.ts:609-619`) is about.
