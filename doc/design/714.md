# Design note for #714: token-carrying `git` calls run no hooks

## Where it goes

The change goes in one place: `git()` in `packages/repo/src/git.ts:44`, inside the `if (token)` branch at `:49`. That is where the token is put into the child's environment. When a token was resolved, add `['-c', 'core.hooksPath=/dev/null']` to the **front** of `args`. Git reads `-c` only before the subcommand, so `git push -c …` would be an error.

The flag is tied to the resolved token, not to whether `options.token` was passed. `TokenSource` can be a function (`git.ts:24`), it is resolved per call at `:48`, and `if (token)` treats `''` as "no token". So a source that resolves to an empty string gets no `-c` and no extraheader. The test should pin both.

The value `/dev/null` follows `apps/cli/src/triage-checkout.ts:59`, which does the same thing with `git config core.hooksPath /dev/null`. Keep the value the same so a later grep finds both.

## Every git call that carries a token, not just push, fetch and clone

The ticket's grep returns more than those three. The token travels on a shared `run` object, and that object is spread into every call at that site:

- `packages/repo/src/integrate.ts:247`: `run = { token: options.token, … }`. The merge lane's own commands use it, including `merge --no-ff` at `:521`, `merge --abort` at `:531`, `worktree add` at `:458` and `push` at `:607`. So the lane's merge stops running the managed repository's `pre-merge-commit`, `commit-msg` and `post-merge` hooks, as well as `pre-push`.
- `packages/repo/src/worktree.ts:112` and `:136`: `rev-parse`, `fetch --prune`, `clone --bare` and `remote set-url` in `ensureMirror` and `provisionWorktree`.
- `packages/conductor/src/conduct.ts:1620`: `gitHere` passes `options.token` on **every** command it runs in the pass's worktree, for example `push` at `:2113`.

All of these now skip hooks. That is the intent: it is the code-execution path the ticket means to close. **The PR must say so in those words**: a repository's merge-time and push-time hooks no longer run under the conductor, and its own checks belong at `build:` (0060).

Two calls are unchanged because they carry no token. Their hooks still run, and the ticket's *"Invocations that carry no token are unchanged"* puts them out of scope:

- `worktree.ts:201`, `git worktree add` with no `token`. It can still fire `post-checkout`.
- `worktree.ts:228`, `git worktree prune`.

## The test needs a seam that does not exist yet

`git()` calls `execFile` directly (`git.ts:59`), and a spawned `git` is integration under 0060 §1. A unit test cannot observe its argv. There is nothing in `packages/repo/unit/` for this today: the files that touch `git` are in `packages/repo/integration/`.

Split the pure half out. Add an exported function in `git.ts` that takes `args`, the resolved token and the base env, and returns `{ args, env }`. Have `git()` call it. A new `packages/repo/unit/git.test.ts` then asserts:

- With a token: argv starts with `-c`, `core.hooksPath=/dev/null`, and then the caller's subcommand.
- With a token: the token appears **nowhere in argv** and only in `GIT_CONFIG_VALUE_0`. This is the ticket's *"`-c` is argv, but carries no secret"*.
- With no token, or with `''`: argv equals the input and there is no `GIT_CONFIG_*`.
- `GIT_TERMINAL_PROMPT=0` is set in both cases.

`git()` should keep resolving the function form itself; only the already-resolved string goes into the pure function.

Don't move the hooks setting into the environment as a second `GIT_CONFIG_KEY_1`. It would work just as well, but the ticket's *Done when* is written against argv, and the explicit `-c` is easier to see in `ps` output and in a failure message.

## The cost to later tickets is smaller than the ticket says

The `-c` pair is added inside `git()`, below every caller. The argv a caller hands to `repo.git` or to a fake port is unchanged, so tests that record what `conduct.ts` asked for (through `gitHere` or a stubbed `repo.git`) do not change. The only argv that changes is the one passed to `execFile`, and only the new unit test reads that.

`RepoFailed.operation` is built as `` `git ${args[0]}` `` (`git.ts:96`) from the **caller's** args. It must keep saying `git push` and not `git -c`. That holds as long as the prefix is added inside `git()`, after `gitEffect` has built its label.

## Docs

In `doc/github.md`, under *How the token reaches `git`, and the two ways it does not* (`:138`), add one line below the `GIT_TERMINAL_PROMPT` paragraph. It should say that a call carrying the token also gets `-c core.hooksPath=/dev/null`, so no code from the managed repository runs while the token is in that environment, and that the `-c` carries no secret.

The doc quotes `git.ts:45` as the location. Update that line number if the extraction moves it.

## Checks

Run `pnpm test`, `pnpm typecheck`, `pnpm lint` and `pnpm fmt:check`. Run the tests as `HOME=/nonexistent pnpm test`; the new test reads no `$HOME`.

That a real `git` honours `core.hooksPath=/dev/null` when it comes from `-c` is only checkable with a spawned process, so it is out of reach inside a pass. The unit claim on argv stands in for it, with `triage-checkout.ts:59` as the existing precedent for that value.
