## Design note: #1085, onboarding as Effects

### The one decision the ticket leaves open: what the failure channel carries

The ticket says two things that pull against each other. The Shape says *"a store or filesystem failure is a defect"*. The Watch-out says *"every `throw` that today's callers print stays a typed failure with its message"*. The board's add is a caller that prints every throw. **The Watch-out wins:** anything `add`, `addLocal`, `recheck`, `checkInstallation` or `checkGhAccess` throws today becomes a failure on the error channel. That failure is **the original rejection value itself, never a wrapper**.

Here is why, from the code:

- **The board's add prints every rejection.** `add-from-page.ts:289-291` lifts `add` with `catch: reasonOf`. `:321-335` lifts `addLocal` with `catch: (e) => new Error(reasonOf(e))`. `checkAndWrite`'s `Effect.catch` (`:270-275`) turns that failure into `say: \`${err.message}. ${keptSentence(path)}\``. So a failed `eventStore.append` already reaches a person as a sentence:
  - a version conflict when two adds race past the owner check (the comment at `onboard.ts:565-569` says *"the append below is optimistic on the version read here"*), or
  - a refused `client.refSha(base)` (`onboard.ts:551`), or
  - `createGitHubClient` failing (`:522`).
- **A defect bypasses that catch.** If any of these becomes a defect (`Effect.promise`, `orDie`), `Effect.catch` no longer sees it. The board's server action would then reject with a stack, and the registration might already be written. That is exactly the half-added project the Watch-out names.
- **Unwrapped keeps the faces honest.** If the failure is the thrown value unchanged, each face's `Effect.runPromise` rejects with what the promise version throws today (Effect 4: `"effect": "^4.1.2"`, `packages/conductor/package.json:68`). That keeps three things working:
  - `instanceof` checks and messages downstream;
  - the CLI callers' `catch` blocks;
  - the two `.rejects.toThrow('502')` tests (`unit/onboard.test.ts:253`, `:292`), with no change to either.

So each promise inside these functions is lifted with `Effect.tryPromise({ try, catch: (e) => e as Error })`. A narrower type is fine where one is known. Do not use `Effect.promise`. Error types in signatures can stay `Error`; inventing a tagged error per call site buys nothing, since every reader takes `.message`.

The **answers** stay answers: `{ ok: false }`, `null`, `Rechecked` and `Governing`. The functions catch `NotInstalledError` (`onboard.ts:157`, `:288`) and `GitHubFailed` (`:366-389`) and turn them into a log line plus a refusal value. In Effect form those are `Effect.catch` on the lifted call, matching on the same `instanceof`, with the same return. The rethrow of anything else (`:157`, `:292`) is simply not catching it.

### Order matters in two places

- **`baseProtection` (`:445`) uses `Promise.allSettled`.** Its replacement is `Effect.all([...].map(Effect.result), { concurrency: 2 })` or the equivalent: both reads run, and neither one's failure fails the other. A sequential `yield*` of two `tryPromise`s would turn a `rules` 403 into a failed add, when today it is a `could not tell whether … is protected` warning. `warnIfProtected`'s comment, *"Never changes the outcome of `add`"* (`:463`), is the claim to keep.
- **`add`'s sequence stays exactly `:508-593`:**
  1. check;
  2. client;
  3. `resolveLocalRecipe`, where a throw becomes `log(message)` + `{ ok: false }` (`:534-539`), an answer and not a failure;
  4. the `--base` refusal;
  5. `refSha`;
  6. the warning;
  7. read;
  8. owner guard;
  9. append.

  Nothing reorders. In particular, the append stays last, after every refusal.

### Seams that stay promises

- **`AddDeps` (`:479-489`) keeps `check: typeof checkInstallation`.** `apps/cli/src/add-github.ts:132` names the same type. `liveAddDeps.check` therefore points at the **face**, and `addEffect` lifts `deps.check(...)` with `tryPromise`. This means a face runs inside `addEffect`'s live path. That is accepted: the ratchet counts the face's one `runPromise` as a face, and the ticket keeps the seam a promise port.
- **`checkGhAccess` and `recheck`'s deps are lifted the same way.** That covers `checkGh`, `GhAccessDeps.status`/`.repository` and `RecheckDeps.installation`/`.register`. Their defaults stay promise-typed.
- **The only `async` in `liveGhAccessDeps` (`:327`)** becomes `.then` on `createGitHubClient(...)`. That is a port's live value, not a function this ticket converts, so the *"a `.then` chain is not a conversion"* rule does not apply to it. Say so in a one-line comment so a reviewer does not read it as a dodge.
- **`RecheckDeps.register` defaults to `add`, which is now the face.** Keep it that way; `recheckEffect` lifts it.

### Faces

The ratchet's rule is quoted at `packages/domain/unit/effect-ratchet.test.ts:10-14`: a face is an exported function whose whole body is `return Effect.runPromise(<call>)`. The face takes the same parameters, including defaults, as today's function.

There are five faces:

| Face | Who still awaits it |
|---|---|
| `add` | `apps/cli/src/first-project.ts:1358` |
| `addLocal` | `apps/cli/src/first-project.ts:1336`, `apps/cli/src/init.ts:1300` |
| `checkGhAccess` | `apps/cli/src/add-github.ts:164` and `liveAddDeps` |
| `checkInstallation` | `apps/cli/src/add-github.ts:158`, `liveAddDeps`; type named at `add-github.ts:132`, `onboard.ts:482` |
| `recheck` | `apps/board/src/app/actions.ts:515`, which 0101 §7 lets keep a promise |

Each `why` names its callers in that form. Insert the entries in sorted position among the existing `packages/conductor/src/…` rows.

`governing`, `baseProtection` and `warnIfProtected` get no face. Their tests in `unit/onboard.test.ts` call `Effect.runPromise(governingEffect(...))` and so on; `unit/` is not counted. Keep the names `xEffect` exported.

### `add-from-page.ts`

Only the two calls change:

- **`:289-299`:** `addEffect({ slug }, (line) => lines.push(line))`, then `Effect.mapError((e) => new Error(reasonOf(e)))` in place of today's `catch: reasonOf` + `mapError`. The `added.ok` branch stays as it is.
- **`:321-335`:** `resolveLocalRecipe` stays inside its own `Effect.tryPromise`, because it is a `@lingtai/recipe` promise and out of scope. It is followed by `yield* addLocalEffect(...).pipe(Effect.mapError((e) => new Error(reasonOf(e))))`.

The header comment at `:18-19` stays: the rest of the file is still `.then`.

### Checks

The ratchet test in the unit half is the only witness that `async` really reached 0. It also refuses a face whose body is anything but the one `runPromise`, so the faces are held without integration.

The board's add path (`liveRegister`) has no unit test of a store failure reaching `say`. A one-case unit test there is worth adding: a `register` whose `addEffect` fails with `new Error('conflict')` comes back as `{ ok: false, say: 'conflict. …' }`. It needs the memory event store (`@lingtai/event-store/memory`) or an injected failing dep. Without it, the defect-versus-failure choice above is checked by nothing before the merge.
