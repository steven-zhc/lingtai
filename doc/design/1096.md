# #1096 — the shape

The ticket covers the ports, the order and the faces. This note covers four places where the converted Effect code still has to pass through a promise (two promise-shaped helpers, a try/finally and a Ctrl+C path), and gives the decision for each.

## 1. `askAgain` goes into the promise `LockQueue`, so it needs a runner that the ratchet does not count

`queue.wait(waitLog, askAgain, progress)` (`service.ts:1428`) keeps the `LockQueue` signature `retaken?: () => Promise<void>` (`service.ts:607-611`) until CLI-08b. After this ticket `askAgain` is an Effect: it yields `options.drain.ask`. It has to be handed over as a promise thunk without adding an `Effect.run*`, and `run` has to stay at 6.

- **Decision:** inside `drain`'s `Effect.gen`, write `const run = Effect.runPromiseWith(yield* Effect.context<never>())` and pass `() => run(askAgain)`. This copies `restart.ts:1072`, whose comment says `waitForTheLock` *"is a promise until CLI-08a and takes the facts as thunks: the fiber it starts for each carries this one's services."* The ratchet does not count it, because of `RUN = /^run[A-Z](?!\w*With$)/` (`packages/domain/unit/effect-ratchet.test.ts:70`).
- **The rejection must still be an `Error` with a `.message`.** `queueForTheLock` reads it as `` `, and asking for the drain again failed — ${(err as Error).message}` `` (`restart.ts:1480-1483`).
  - The foreign-standing case (`service.ts:1411-1413`) is `Effect.fail(new Error(...))`.
  - `requestShutdownUnlessStandingEffect` fails through the defect channel when the store fails. So end `askAgain` with `Effect.catchCause`: let a cause that is interrupts only through, and turn anything else into `Effect.fail(asError(Cause.squash(cause)))`. Do not depend on whatever `runPromiseWith` rejects with for a die.

## 2. `keepAsked` takes Effects now, and keeps its root fork

`keepAsked` (`service.ts:104-113`) wraps two promise thunks in `Effect.tryPromise` so it can feed `keepAskedLoop`. Once `options.shutdown` and `askAgain` are Effects, that wrapping goes.

- **Decision:** change its parameters to `Effect.Effect<unknown, unknown>` and pass them straight to `keepAskedLoop`.
- **Keep** `Effect.runForkWith(Context.empty())`. It is uncounted, and CLI-08b deletes the helper (its doc comment says so). An empty context is enough because the daemon Effects need no services: `readControlEffect` and the others are `Effect<…>` with `R = never` (`packages/daemon/src/control.ts:117`, `:152`, `:391`, `:458`). The loop already drops a round that dies (`upgrade-drain.ts:44-46`, *"A round that fails — or dies, as a store's failure does — is dropped"*).
- `stop` stays a promise and is lifted where it is called (see §3).
- Do not fork it as a child of the command's fiber in this ticket. That changes when the loop is interrupted, and CLI-08b owns that change.

## 3. `drain`'s `try/finally` becomes `Effect.ensuring`

`service.ts:1468-1472` stops the watcher and leaves the queue on every way out. A store defect is now a way out that the old `finally` never saw as a separate case.

- **Decision:** wrap the body after the queue was taken in `Effect.ensuring(Effect.suspend(() => …))`. The finalizer lifts `watcher?.stop()` and then `queue.leave()`, in that order, with each lift's failure ignored.
- `watcher` stays a `let` that the body assigns, so the finalizer has to read it lazily through `suspend`.
- `leave` is *"Safe to call twice"* (`service.ts:619`), so keep the early `leave` calls at `:1438` and `:1458` as they are.

## 4. Ctrl+C reaches the wait, not the fiber, and must stay that way

Nothing interrupts the command's fiber on SIGINT:

- `cli.ts:1549` runs the root with `Effect.runPromise` and installs no signal-to-interrupt handler.
- `waitForTheLock` installs its own handler (`restart.ts:1392`) and returns `'interrupted'`. `drain` turns that into the *"stopped waiting, and the supervisor was told nothing"* line and exit code 130 (`service.ts:1437-1444`).

Do not add an interrupt on SIGINT anywhere in this chain. If you did, the lifted `queue.wait` would be abandoned mid-promise, the 130 path and its sentence would never run, and the drain request would be left unmentioned.

## The catches, one shape everywhere

Every `.catch` that turns a failed read into words becomes the shape at `daemon.ts:796-799`:

```ts
Effect.catchCause((cause) =>
  Cause.hasInterruptsOnly(cause)
    ? Effect.failCause(cause)
    : Effect.succeed(/* the same answer */))
```

The message comes from `Cause.squash(cause)`. Each site keeps the answer it gives today:

| Site | Answer on a failed read |
|---|---|
| `shutdownStands` | `{ unread }` (`:1208`) |
| `startAndConfirm` watermark | the two error lines (`:1223`, `:1226-1231`) |
| poll loop | `unread = message` (`:1251-1256`) |
| `drain.queue` | the supervisor fallback (`:1339`) |
| `drain.ask` | *"the shutdown could not be asked for"* (`:1385`) |
| `holding` | `'what is in flight could not be read'` (`:1402`) |
| `queue.holds` (lifted) | `false` (`:1433`) |
| `status`'s `liveness` | `{ unread }` (`:1488`) |
| `boardAnswers` | as today |

`Effect.catch` would be wrong at every one of these sites. Every daemon Effect here has error type `never` (`control.ts:152`, `:458`, `:717`), so a store failure arrives as a die, and `Effect.catch` would let it through.

## The defect test

Put it in a new or existing `unit/` file:

- **Setup:** `serviceCommand(['start'], …)` with `shutdown: () => Effect.die(new Error('store gone'))` and an `exec` that records every call.
- **Check 1:** it returns the refusal code.
- **Check 2:** stderr carries `standingRefusal`'s *could not be read* lines with `store gone` in them.
- **Check 3:** `exec` saw no `launchctl bootstrap`, no `launchctl kickstart` and no `systemctl start`.

This is the unit-level stand-in for the claim the integration files would otherwise make: `integration/{service,board}.test.ts` only typecheck before the merge, and they run after it.

**Which event would confirm it in production:** a `service start` refused this way appends nothing. Over the window of the attempt, the control stream shows no `ConductorStarted` and no `ShutdownRequest` cleared.
