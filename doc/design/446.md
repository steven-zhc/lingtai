# Design: #446: `upsertSection` and `updateBody(…, { ifUnchanged })`

Three separate pieces: a pure function, one interface change across three trackers, and a board test. There are no callers to move. `appendToBody` (`packages/conductor/src/discuss.ts:646`) and `tell.ts:168` stay exactly as they are.

## 1. `upsertSection`: a new file, not `discuss.ts`

Put it in `packages/conductor/src/body-section.ts`, with its tests in `packages/conductor/unit/body-section.test.ts`. `discuss.ts` imports the event store, and this function has to stay pure. Export the two marker builders from the same file, the way `keyMarker` sits in `ticket-store.ts:122` (`/** How a GitHub issue says which finding it is. Invisible when rendered. */`).

These are the decisions the ticket leaves open:

- **Match the whole open marker, including ` -->`.** Searching for `<!-- lingtai:answer w-1@review` would also find `w-1@reviewer`. The close marker carries no key, so look for it after the open marker and never before it. Sections never nest.
- **Write the markers with a blank line on each side:**
  ```
  ${body.trimEnd()}\n\n<!-- lingtai:answer KEY -->\n\n${text.trim()}\n\n<!-- /lingtai:answer -->\n
  ```
  In CommonMark an HTML comment block ends at the line holding `-->`. With the blank lines, the text between the markers is its own markdown block, so a heading or a list inside an answer renders as one. I checked this by rendering through the board's own pipeline (below): `<!-- … -->\nthe answer, *here*\n<!-- /… -->` came out as `<p>the answer, <em>here</em></p>`.
- **"Same text" means `===` on the result.** Build what the section would be. If the body already contains exactly that, return the input string itself. #422 can then skip the write with `if (next === body)`, and a retry costs no PATCH. Compare `text.trim()` with what sits between the markers, also trimmed, so differences in surrounding whitespace never count as a change.
- **Replace only the span from the open marker to its close marker.** Text before and after it, written by a person, is kept byte for byte.
- **Refuse what cannot be upserted safely.** Throw if:
  - the key contains `-->` or a newline, because it would end the marker early;
  - the text contains a `lingtai:answer` marker (open or close), because it would be read back as a section boundary on the next call;
  - an open marker for the key has no close marker after it, or the first close after it actually belongs to another section's open marker sitting in between.

  Treating an unclosed marker as absent would append a second copy, which is the very bug this ticket exists to prevent. Treating it as running to the end of the body, or to the next close regardless of what lies between, would delete a person's text.
- **Two open markers for one key** can only come from someone pasting by hand. Replace the first one and leave the other alone.

## 2. `updateBody(issue, body, opts?: { ifUnchanged?: string })`

### The refusal is a named error class

`BodyChanged extends Error` carries the issue number. A caller tells a refusal apart from a network failure with `instanceof`. #422 needs that distinction: a refusal means read again and upsert again, while a network failure says nothing about whether the write landed.

The one existing precedent is a bare `Error`: `db-tickets.ts:382`, `throw new Error(\`#${number} changed since this form was opened\`)`. That was enough for a CLI that only prints the message. It is not enough here, and `updateFields` should stay as it is.

Define the class in **`packages/github/src/client.ts`** and export it from `packages/github/src/index.ts`, next to `GitHubError` (`app.ts:72`, which has the same `override readonly name` shape). The reason for that location is that `@lingtai/github` cannot import `@lingtai/conductor`, while the conductor already depends on github (`ticket-store.ts:27`). Re-export it from `ticket-store.ts` so conductor callers import it from where `Tickets` lives.

### The trap: `GitHubClient` must declare the option itself

`unit/tickets.test.ts` pins `const _gitHubSatisfiesTickets: Tickets = {} as GitHubClient`. A function with fewer parameters is assignable to one with more. So if only `Tickets.updateBody` (`ticket-store.ts:77`) gains the option, `GitHubClient.updateBody(issue, body)` (`client.ts:229`) still type-checks and **silently ignores `ifUnchanged`**. `passClientOf` (`ticket-store.ts:296`) hands that client out unchanged when `tickets === client`.

So:

- Change the signature at `client.ts:229`, in the implementation at `client.ts:314`, and in the `Tickets` interface.
- Add a `tsc` pin in `unit/tickets.test.ts`:
  ```ts
  const _gitHubTakesIfUnchanged: Parameters<GitHubClient['updateBody']>[2] = { ifUnchanged: '' }
  ```
  `tsc` rejects an index past a tuple's length, so this pin fails the moment the GitHub side drops the option. As that file's header says, this is a `pnpm typecheck` claim and not a `pnpm test` one.

### Per tracker

- **`db`** (`db-tickets.ts:355`): when `ifUnchanged` is given, add `AND body = $5` to the existing `UPDATE … RETURNING number`. Zero rows can mean either no such ticket or a changed body. Settle which with a follow-up `SELECT 1`: throw `noSuchTicket` if the row is gone, otherwise `BodyChanged`. That select only diagnoses the failure; it plays no part in deciding whether to write.
- **memory** (`test/memory-tickets.ts:122`): throw `BodyChanged` if `require(number).body !== ifUnchanged`.
- **GitHub** (`client.ts:314`): call `getIssue`, compare, then PATCH. Compare against the body after `toIssue`'s normalisation (`client.ts:381`, `body: raw.body ?? ''`), because that is what any caller read.
  - The comment must say plainly that this is best-effort. For example: *GitHub's issue PATCH takes no `If-Match`, so this is a read and a write, not a conditional write: an edit landing between the two is lost. 0118 §6 accepts that window; this narrows it and does not close it.*
  - The same comment should name what `ifUnchanged` must be: **the body as `getIssue` returned it, never a body this process composed.** GitHub may normalise what it stores (line endings from the web editor, for one), so comparing against what was last *sent* would refuse every time.

### The test

Write one test in `packages/conductor/test/tickets-contract.ts`, beside the `updateBody replaces only the body` case at line 97. `describeTicketsContract` already runs that file against memory (`unit/tickets.test.ts`) and against `db` on a unit store (`unit/db-tickets.test.ts:12`), so one test covers both trackers inside `pnpm test`. The test should:

1. read a ticket;
2. call `updateBody` without the option, standing in for the other writer;
3. call `updateBody(n, x, { ifUnchanged: firstRead })` and expect it to reject with `BodyChanged`;
4. assert the other writer's body is still there.

Add a second test where the body did not change and the write lands. The GitHub path's read-compare-throw is not untestable for lack of a network: `packages/github/unit/client.test.ts` already drives `createGitHubClient` in the unit half with `vi.stubGlobal('fetch', …)`, the way `listOpenIssues` and the refs tests do. Add a case there that stubs the GET to answer a body, then asserts `updateBody(n, x, { ifUnchanged: … })` throws `BodyChanged` and sends no PATCH when the stubbed body differs, and sends the PATCH when it matches — so dropping the throw, or hoisting the PATCH above the compare, fails `pnpm test` rather than only the comment and the type pin above.

## 3. The board already hides the marker, and only because of `rehype-sanitize`

The ticket names `apps/board/src/lib/markdown.ts`, but that file only holds the rules. The renderer is `apps/board/src/app/markdown.tsx`.

I rendered a body with the markers through `react-markdown` in this checkout:

- **With** `rehypePlugins={[rehypeSanitize]}`, the configuration `Rendered` uses: the comments, block and inline, leave no trace.
- **Without it:** each comment comes out as `&lt;!-- lingtai:answer w-1@review --&gt;`.

The reason is that react-markdown v10 hands raw HTML to rehype as `raw` nodes and turns any that survive into text (`node_modules/react-markdown/lib/index.js:360`). `hast-util-sanitize` drops node types it does not know, and `raw` is one of them.

So there is no renderer change to make. Two things are needed:

- **A test that pins this behaviour.** Add it to `apps/board/unit/markdown.test.tsx`, which already uses `renderToStaticMarkup`. Render `<DocumentBody source="ticket-body" …>` with a body containing both markers and an inline comment. Assert that the markup contains neither `lingtai:answer` nor `&lt;!--`, and that the answer's own text is still present. The test must go through `DocumentBody`, not bare `ReactMarkdown`, because removing the sanitiser is the regression it guards against. The same test also covers `keyMarker`'s `<!-- lingtai:finding … -->`, which nothing tests today.
- **A correction to the comment at `markdown.tsx:16-18`.** It says `` `react-markdown` drops HTML nodes unless `rehype-raw` is added `` and that `rehype-sanitize` runs "anyway". The first half is false: react-markdown escapes HTML and prints it. The sanitiser is what removes it, so it is load-bearing and not a second line of defence. The comment should say that, so nobody removes the sanitiser as redundant.
