## Design note for #732: a binary is described by its release version, not by a commit or a checkout

### The one decision: the caller passes the build in, and only a binary gets new behaviour

Each of the four places takes a small optional parameter, `build: Pick<ReturnType<typeof versionFacts>, 'lingtai' | 'form'>`. It defaults to `versionFacts()` (`apps/cli/src/version.ts:19-26`). Tests pass `{ form: 'binary', lingtai: '0.10.0' }` in directly, because `isSea()` is false under vitest. `schemaChecks(…, { checkout: !isSea() })` (`doctor.ts:668`) already works this way.

Put the parameter at the end of the signature with a default. **Do not add it to `World`** (`install.ts:112`). `layout-625.test.ts:244-258` builds a `World` literal field by field, and a required field breaks every fixture like it. An optional field on `World` would make the binary branch reachable only from tests that remember to set it.

The rule in all four places: when `form === 'script'`, run exactly today's code, including `installedVersion`, the git read and every sentence. The new branch runs only when `form === 'binary'`. That keeps `layout-625.test.ts:270-273` (*"✗ this lingtai is not under … — a checkout upgrades"*, whose `self` is `/checkout/apps/cli/src/cli.ts`) and `apps/cli/integration/doctor.test.ts:855` passing unchanged.

### The four places

**1. The start line, `apps/cli/src/daemon.ts:236-239`.**
- Today the sentence is built inside `daemonCommand` (`daemon.ts:187`), which no unit test can reach without a store.
- Move it into an exported pure function, for example `startLine(code: { sha; dirty }, build)`. `daemonCommand` calls it with `versionFacts()`.
- On a binary it returns `running lingtai ${build.lingtai}`. It says nothing about a commit, a dirty worktree or doctor.
- Nothing else changes. `readCodeVersion()` (`daemon.ts:211`) still runs, and the beacon and `ConductorStarted` still record a null sha.
- The test goes in `apps/cli/unit/daemon-cli.test.ts` or a new unit file.

**2. `daemonCurrency`, `apps/cli/src/doctor.ts:1325`.**
- Add `build` as the second parameter. The callers at `doctor.ts:3068` and `:3111` keep the default.
- Only the `!status.codeSha` branch (`:1350-1362`) checks the form. On a binary it returns `status: 'ok'`, with no `fix` and no `title`. Suggested detail, in the board's terms (`health.tsx:52-58`): *"running an installed binary, lingtai X — it has a release version, not a commit; `release: newest` says whether a newer one is out"*.
- Use `ok`, not `skip`. The daemon is up and what it runs is a known fact. The board answers `wrong: null` for this case.
- The beacon carries no form, so `lingtai X` is doctor's own version, not the daemon's. Word the detail so it does not claim the daemon's version. For example: *"this lingtai is X; the daemon records no commit, as a binary's never does"*. Recording the daemon's version is out of scope.
- The form decides, not the beacon: on a binary a non-null `codeSha` (a checkout daemon seen by a binary's doctor) is also `ok`, and `codeCurrency` is not called, because a commit comparison read from a binary's directory says nothing about a release.
- The test goes beside `apps/cli/unit/doctor-titles.test.ts:56`, which already calls `daemonCurrency` with a fake beacon. Add a binary case and keep the checkout case asserting `warn` and `lingtai restart "picking up main"`.

**3. `releaseCheck`, `apps/cli/src/install.ts:742-757`.**
- On a binary, the current version is `build.lingtai`, the version compiled into the binary, whatever directory the file sits in. `installedVersion` (`install.ts:251-255`) is not consulted for a binary.
- On a binary, the "a checkout" row (`:747-751`) can no longer be returned. The fetch and `releaseRow` are unchanged, and so is the GitHub-unreachable `warn` (`:719-727`).
- The caller is `cli.ts:111`. It keeps the default.
- Test: a binary with `self` outside `$LINGTAI_HOME/versions` (the `NOWHERE` env in `layout-625.test.ts:260-264` will do) and a fake `fetch` returning a release. Assert that fetch was called and the row's name is `release: newest` and not "checkout".

**4. `upgrade`'s first refusal, `apps/cli/src/install.ts:448-453`.**
- `upgrade(options, world, build = versionFacts())`. The caller is `cli.ts:567`, and it keeps the default.
- When `installedVersion` is null on a binary, refuse with a sentence naming three things:
  - `dirname(world.self)`, where this binary runs from
  - `paths.versions`, the `versions/` directory `LINGTAI_HOME` points at
  - the remedy: unset `LINGTAI_HOME`, or point it at the home this binary was installed under
- Do not use the word "checkout" and do not mention `git pull`. Nothing is fetched, as today.
- The upgrade itself still refuses there, because it moves the shim under `paths` (ADR 0113 §10). The sentence is the only change.
- Do not resolve the path. `world.self` can be the shim's target or the shim itself, so show `dirname(world.self)` as given, the same way `installedVersion` reads it before its `realpath`.

### What stays the same
- `versionLine` and `--json` (`version.ts:29-32`). `upgrade` parses the new binary's line.
- `RESTART_FIX`, `currencyRow` (`doctor.ts:1369-1375`) and the null-sha strings listed under Out of scope.
- ADR 0113. §16's *"skipped on a checkout"* is still true, and the check now tells the two forms apart correctly. No ADR file.

### Checks
Every Done-when item can be checked by a unit test through the injected `build`. Nothing depends on `pnpm test:integration` or on a real SEA binary. That matters because the four binary tests in `apps/release` fail on this machine's Homebrew Node, whatever the diff. `pnpm typecheck`, `pnpm lint`, `pnpm fmt:check` and `HOME=/nonexistent pnpm test` must pass. Whether the live binary prints the new lines can only be confirmed by a rerun of the #612 trial (A13, B6, C3) after the merge.
