# Design: the `spend` projection (#497)

## Where it goes

There is one new file, `packages/projector/src/spend.ts`. It exports `SPEND_TABLE = 'spend'` and `spendProjection: Projection`, and follows the layout of `backlog.ts`: `create` / `reset` / `apply`, its own tables and its own checkpoint name. Re-export both from `packages/projector/src/index.ts` beside the `BACKLOG_TABLE` block (`index.ts:50`).

Wiring is two edits, plus one that comes for free:

- `apps/cli/src/lingtai.ts:100`: add the projection to `PROJECTIONS`. Four things use that constant, so this one edit covers them all: `projection rebuild <name>` at `:406`, the usage line at `:346`, the daemon's runners at `:655` (`startDaemon({ projections: PROJECTIONS … })`), and reconcile's lag judgement at `:764`.
- `apps/cli/src/doctor.ts:647`: `projectionShapes` hardcodes `[taskViewProjection, backlogProjection]` and does not read `PROJECTIONS`. Add `spendProjection` there and import it beside `backlogProjection` at `:94`.
- `projection lag` needs no edit. `projectionLag` (`projection.ts:272`) returns `store.lags()`, which is `select … from checkpoints` on both stores (`postgres.ts:245`, `sqlite.ts:598`). `spend` appears there once its runner has written a checkpoint.

Do **not** add it to `withProjector` in `apps/cli/src/projector.ts:80`. That function follows `task_view` and the backlog for a bare `lingtai run`, because a person is watching those two while the run is in progress. Nobody watches `spend` during a run, and the daemon catches it up from its checkpoint. A third runner there would cost a third connection for nothing.

## Tables

```
spend (
  seq         bigint primary key,   -- the RunSpent's own seq
  at          timestamptz not null, -- event.at; the rate card prices by this (0110 §6, §7)
  stream_id   text not null,        -- run-… / wi-… / chat-…
  ticket      text,                 -- a wi-… id; null only as below
  project     text,                 -- parseWorkItemStream(ticket)?.project, for /spend's per-project row (0110 §7)
  pass        text,                 -- event.streamId when isPassStream, else null
  purpose     text not null,        -- for._tag
  step        text, action text, round integer,   -- Action only
  spent_for   jsonb not null,       -- the whole SpentFor, so Judge.when and Triage.waitId are not lost
  runtime     text not null,
  turns       integer not null,
  duration_ms bigint not null,
  cost_usd    double precision,     -- null stays null (0110 §4)
  usage       jsonb not null
)
spend_stream (stream_id text primary key, ticket text not null)
```

**The column is `purpose`, not `for`.** `for` is a reserved word in both SQL dialects, and every query would have to quote it. 0110 §11 lists a `for` column "with its `step`, `action` and `round`". This spells the same facts differently and decides nothing new, so no superseding ADR is needed. 0110 §7 already calls them purposes.

Insert with `on conflict (seq) do nothing`. Write the JSON columns as `JSON.stringify(...)` with `$n::jsonb`. `translate` strips the cast for SQLite and stores `jsonb` as `text` (`sqlite.ts:103`, `:207`), the same way `task_view` already does.

## Filling `ticket`

`spend_stream` maps a stream to its ticket. It is kept here and not read from `finding_backlog_run` or `task_view_run`, for the reason `backlog.ts` gives for its own link table: "another projection's table is at another projection's checkpoint."

| `RunSpent` on | link written by | key | ticket |
|---|---|---|---|
| `run-…` (implement, fix, reviewer, designer, judge) | `RunStarted` | `event.streamId` | `d.workItemId` |
| `wi-…` (triage) | none | — | `event.streamId` itself |
| `chat-…` (discussion) | `DiscussionRequested` | `chatStream(d.chatId)` | `d.workItemId` |

**`DiscussionRequested` is on the control stream, not the chat stream.** The board appends it to `CONTROL_STREAM` (`apps/board/src/app/actions.ts:398-410`). The discussion's `RunSpent` goes to `chatStream(options.chatId)` (`packages/conductor/src/discuss.ts:503`, `:579`). So the link key is `d.chatId` passed through `chatStream` (`streams.ts:79`, which is idempotent on an id that already starts with `chat-`). Keying on `event.streamId` there would key every discussion on `ctl-…`. A follow-up question carries the same `chatId`, so its link insert uses `on conflict do nothing`.

**When no link is found, keep the row with `ticket` and `project` null.** The ticket says never to drop a row. That happens on a `run-…` with no `RunStarted`, a `chat-…` whose request the fold never saw, or any other stream prefix. Do not backfill the row later. The link is always written before the `RunSpent` that needs it: `RunStarted` opens the pass stream, and the daemon dispatches a discussion only in reaction to `DiscussionRequested` (`packages/daemon/src/work-loop.ts:550`). A null therefore means the source event is missing, and a later event will not supply it. A backfill would be a second write path whose only job is a case that should not occur. Leaving it out keeps the rebuild and the live fold trivially identical. The facts that would show a null in production are the row's `stream_id` and whether a `RunStarted` exists on that stream. An agent cannot read production `events`.

**Triage has no writer yet.** 0110 §10 says "Triage has no dispatch yet". `for: Triage` therefore appears only in the test stream, which is fine.

## The fold reads `RunSpent` and the three link events, and nothing else

Use a `switch (event.type)` with four cases: `RunStarted`, `DiscussionRequested`, `RunSpent`, and a `default` that does nothing. There is no clock, rate card, network access or price column (0110 §5).

After this change, update the comment on `RunSpent` at `packages/domain/src/events.ts:708-711` ("Nothing writes or reads this yet, and no fold may start reading it until its own ticket"). It should say that `spend` reads it and that `task_view` and `finding_backlog` still must not. Leave the two #499 tests as they are (`task-view-rebuild.test.ts:555`, `backlog-rebuild.test.ts:446`). They still hold, and they are the other half of 0110 §13.

## Tests (`packages/projector/unit/`)

- **`spend-rebuild.test.ts`** follows the pattern of `backlog-rebuild.test.ts`:
  - Use `createSqliteProjectionStore(openSqliteProjections(':memory:'))`, `aRun` and `makeStream`.
  - Build the stream once at module scope. The seq counter is module-global (`backlog-rebuild.test.ts:19-22`).
  - Include one `RunSpent` for each `for` variant, each with its link event: `Action` on a run stream after `RunStarted`, `Judge` on the same run stream, `Triage` on a `wi-…` stream, and `Discussion` on a `chat-…` stream after a `DiscussionRequested` on `ctl-…`.
  - Include one `RunSpent` on a run stream with no `RunStarted`, and assert its row exists with `ticket: null`.
  - Include one `costUsd: null` row, and assert it stays null rather than becoming 0.
  - For "byte-identical": compare one fold of the whole stream with a fold in two batches split between a `RunStarted` and its `RunSpent` (as at `backlog-rebuild.test.ts:438`). Also compare with the runner's `rebuild()` over the same stream, if that can be driven against the in-memory store. Do **not** commit a `vitest -u` snapshot generated after writing the fold. There is no "before" fold to pin against, so assert the rows explicitly.
- **The pin on old spend sources** can go in the same file or its own. Read `src/spend.ts` with `readFileSync` and strip comments with the same regex as `one-store.test.ts:35`, because the file's prose will cite 0110 §13 and name these types. Then assert that none of `RunFinished`, `FixApplied`, `DiscussionAnswered`, `DiscussionHeld` or `TriageAgent` appears. Reading a file under `src/` is already done in the unit half (`one-store.test.ts:30-32`). Also add `'spend.ts'` to the list `one-store.test.ts:42` checks for, so its "pg only in postgres.ts" assertions are known to cover the new file.

## What the pass cannot check

The Postgres half is checked only in `pnpm test:integration`. That means adding `spendProjection` beside the backlog case in `packages/projector/test/contract.ts:691-695`, which runs through `integration/sqlite.test.ts` and `integration/projection.test.ts`. Add that case so the post-merge run covers it, but nothing inside the pass will run it. The unit-level claim that stands in for it is the SQLite fold above. That claim holds only because the DDL uses nothing `translate` does not already rewrite for `task_view`: `jsonb`, `timestamptz`, `bigint`, `double precision`, `$n::` casts and `on conflict … do nothing`. Do not introduce any other Postgres-only syntax.
