# Design: #709 — the App asks for `Workflows: write`

## The data side is mechanical
`defaultPermissions()` (`packages/github/src/manifest.ts:61`) is `Object.fromEntries(REQUIRED_PERMISSIONS.map(...))`. So the manifest picks up the new row once `REQUIRED_PERMISSIONS` (`app.ts:178`) has it. Don't edit `manifest.ts`.

The row is `{ name: 'workflows', level: 'write', why: 'pushing changes to .github/workflows' }`. GitHub's manifest key is `workflows`.

`manifest.test.ts`'s `documented()` builds its list from every three-column `| a | b | c |` row anywhere in `doc/decisions/0114-a-github-app-not-a-token.md`. It turns each name into a key with `toLowerCase().replace(/\s+/g, '_')`, and any level containing `write` becomes `write`. A row `| Workflows | read + write | pushing changes to \`.github/workflows\` |` therefore gives `workflows: 'write'`. Keep the text in that one row only: any other three-column table added to the ADR would also be read as permissions.

## The decision the ticket leaves to the design: what the gap tells its owner
Two places print a gap today, and both give a remedy that is wrong for the new permission:

- `packages/conductor/src/onboard.ts:300` says `"Fix them in the App's settings, then re-run."`
- `packages/conductor/src/pick-repository.ts:280` uses `fix: settings(listed.installation, "Grant them on the installation's page")`. `refusalLines` (`:203`) prints that label and `installation.htmlUrl`.

An installation can only accept permissions the App already requests. The manifest only applies when an App is created. So for an App that already exists, the installation page has nothing to grant. The first step is the App's own permissions page.

**Decision:**
1. Add an `appSlug: string | null` to `Installation` (`app.ts:40–50`). Read it from GitHub's `app_slug` on the raw installation, in `RawInstallation`/`toInstallation` (`app.ts:53–69`). It is null when GitHub leaves it out, in the same way `htmlUrl` is.
2. Add one exported function in `packages/github/src/app.ts`, next to `permissionGaps`, that returns the remedy lines in this order:
   - (a) The App's permissions page: `https://github.com/settings/apps/<appSlug>/permissions`. The line also says an organisation-owned App's page is `https://github.com/organizations/<org>/settings/apps/<appSlug>/permissions`. Lingtai doesn't know who owns the App, so name both pages and don't guess. Add that this step is only needed if the page does not already ask for the permission. When `appSlug` is null, name the page in words.
   - (b) Then accept the new permission on the installation: `installation.htmlUrl` when it is known, otherwise in words. Then re-run.
3. Both call sites use it:
   - `onboard.ts:300` replaces its single line with these lines.
   - In `choose()`'s gap branch (`pick-repository.ts:276–282`), the `why` stays. The two steps come before the fix link, so the App's page is printed first.
   - The cleanest way is for `refusalLines` to print the remedy lines whenever `gaps.length > 0`, with the gap branch's `fix` becoming the installation link labelled as the acceptance step. That covers the last-branch case at `:312` too.
   - Keep the order *gaps → App page → installation* as one block. Don't scatter it.

The same remedy is correct for any gap, not only `workflows`. An installation missing `issues: write` also lacks it either because the App doesn't ask for it or because the installation hasn't accepted it.

## The success line
`onboard.ts:302` hard-codes `'permissions: issues, contents, pull requests write; metadata read'`. Build it from `REQUIRED_PERMISSIONS` rather than adding a fifth word by hand, so it can't fall behind the table again. Something like grouping by level and turning `_` into a space gives `issues, contents, pull requests, workflows write; metadata read`. If a test asserts the old string, update it to the new one.
