# Design note: #508, the approved card's continue button

## What is actually open

The server already refuses a `waitId` that does not match the open wait. `resolveWaitHolding` returns `not-blocked: <ticket> is not waiting on <waitId>` when `item.lifecycle.waitId !== options.waitId` (`packages/conductor/src/resolve-wait.ts:195`). That check is defeated in one way only: the caller leaves `waitId` out, and then every resolver fills it in from the fold:

- `approve.ts:137` and `:227`: `waitId: options.waitId ?? item.lifecycle.waitId` / `?? block.waitId`
- `approve.ts:356` (requeue), `close.ts:164`, `ask.ts:179`: the same pattern

So the fix is mostly about **who may leave it out**. The comparison itself is already written.

There are two ways the board leaves it out today:

1. **`ScheduleContinuation`** sends `{ project, issue, note: '' }` (`apps/board/src/app/decide.tsx:211`). It has no wait to send, because `standingOf` nulls `waitId` everywhere except `blocked`: `waitId: blocked ? life.waitId : null` (`apps/board/src/lib/task.ts:741`). The `approved` lifecycle does carry both values — `{ status: 'approved'; runId; waitId; onSha }` (`packages/domain/src/work-item.ts:79`). They are just not surfaced.
2. **Every other control** spreads `...(waitId === null ? {} : { waitId })` (`decide.tsx:111`, `:360`, `:460`). A null `waitId` therefore drops the key, which the server reads as "whatever is open". `laneWaitIds`'s own doc already names this as the hole: "a null `waitId` is not 'no rail drawn', it is 'resolve whatever is open now'" (`apps/board/src/lib/board.ts:865-871`). Its `return null` paths (read failed five times, or the fold says not blocked) still hand a card `waitId: null`. The props doc on `Decide` ("Null where the caller has no wait id to offer (the home board's own cards…)", `decide.tsx:71-78`) describes this as intended, and is out of date.

## Shape

### 1. Surface the approved wait on `StandingView`

In `standingOf` (`task.ts:691`), make `waitId` the wait of the lifecycle when it is `blocked` **or** `approved`. Add `approvedSha: string | null`, which is `life.onSha` when the lifecycle is `approved` and null otherwise.

Do not reuse `awaitingSha` for this. `standing.tsx:410` gates `Decide` on it being non-null, and only inside `state === 'blocked'`. Widening it would put a sha on a field whose doc says "only while a person is holding it" (`task.ts:721`).

Then `standing.tsx:487` passes both values into `ScheduleContinuation`, and the component sends `{ project, issue, onSha, waitId, note: '' }`.

Rewrite `ScheduleContinuation`'s doc (`decide.tsx:186-192`). "Safe to click whenever it is shown" was only true while the lifecycle stayed `approved`. It is now true because the click names the approval it was shown. On a ticket that has since moved to wait B, the click is refused by name; it does not land on B.

### 2. Board boundary: `waitId` is required, and checked at runtime

In `apps/board/src/app/actions.ts`:

- **`approveCard`**: `waitId: WaitId` and `onSha: string`, both required.
- **`requeueCard`, `answerCard`**: `waitId: WaitId`, required.
- **`closeCard`**: `waitId: WaitId | null`, with the key required. `null` means "the card rendered no wait": the queued row at `standing.tsx:476` and the home board's queued card. Pass the `null` through to `close()` (see §3).

A server action's input is whatever JSON the client posts, so the type alone is not a check. Each action also refuses a missing or empty `waitId` before it builds a client, with a sentence like `stale: this card was rendered without the wait it is about — reload and read it again`.

Also rewrite the doc at `actions.ts:82-88`, which documents `ScheduleContinuation` as the caller that omits `onSha`.

**On the controls**, make the `waitId` prop on `Decide` and `Requeue` non-nullable (`WaitId`), and drop the conditional spreads. A card whose `waitId` is null does not render the resolving controls:

- In `page.tsx:379` and `standing.tsx:408`, render a single `<p className="refusal">` saying the wait could not be read and to reload.
- Keep `Close` there with `waitId={null}`. It is still the one move that is always offered, and §3 makes a null-wait close refuse on a blocked item.

Rendering a button that the server is bound to refuse is the #84 complaint again ("A card must never offer only a control that refuses", `approve.ts` requeue header). Rendering no button is the honest version.

### 3. Conductor: the CLI's omission becomes a typed decision

The ticket's Watch-out row asks how `lingtai approve` is told apart from the board. Do not answer by caller identity: `approveHolding` cannot know who called it. Answer in the type:

- `ApproveOptions.waitId` (`approve.ts:66`) becomes **required**, typed `WaitId | 'open'`.
- `'open'` means "resolve the wait that is open at this read". Only a caller that reads and resolves inside one `deciding` hold may honestly say that.
- `apps/cli/src/approve.ts:59` passes `waitId: 'open'` explicitly, with the comment that already justifies it (`approve.ts:62-65`: "Omitted by the CLI, which reads and resolves inside one `deciding` hold…").
- A future caller cannot leave the field out by accident: `tsc` refuses the omission.

In `approveHolding`, resolve `'open'` to the fold's wait in exactly one place. Then add an explicit wait check in **both** branches, **before** the sha checks (`:121`, `:199`):

```
if (options.waitId !== 'open' && options.waitId !== <lifecycle>.waitId)
  → { ok: false, reason: 'stale', detail: `the card showed wait ${options.waitId} and ${ticketId} is now <blocked on|approved at> ${actual} — nothing was resolved. Reload and read it again.` }
```

It goes first so the refusal names the wait, as the first box in Done-when asks. With the sha check first, a click from the approved card on a new wait at a different sha would be refused by sha instead. `resolveWaitHolding`'s own check stays as the backstop.

For `close()`, widen `waitId?: WaitId` to `waitId?: WaitId | null`:

- `null` on a `blocked` item refuses (`this card showed no wait and <ticket> is now waiting on <id>`).
- `undefined` keeps the CLI's current fallback.

`requeue()` and `answer()` keep their optional `waitId` and their fallback. The board can no longer reach them without an id after §2, and giving them the `'open'` sentinel is the same change repeated. Leave it, and say in the commit body that it is not done here.

### Commit body

Say how the CLI and the board are told apart:

> `lingtai approve` sends `waitId: 'open'`, a value only a caller holding `deciding` across its read may send. The board's server actions refuse a request without a concrete `waitId`, so the board cannot express "whatever is open".

## Tests (unit half only)

- **`packages/conductor/unit/wait-handlers-answer-as-today.test.ts`**. At `:429`, "appends WaitResolved{Approve}…" pins the unsafe call shape. Give it `waitId` taken from the seeded `WaitStarted`; the existing `aWait` helper and `waitsOf` give you the id. Then add a case: the same seed, but called with a **different** `waitId` → `reason: 'stale'`, `detail` contains both ids, and no `WaitResolved` is appended. Every other `approveHolding(...)` call in that file and in `apps/cli/unit/verbs-accept-refuse.test.ts` needs `waitId: 'open'` or a real id; `tsc` will list them.
- **The Done-when's "renders… clicks the button" test.** `apps/board/unit` has no DOM: `waiting-card.test.tsx:32` uses `renderToStaticMarkup`, and `apps/board/package.json` has no jsdom, happy-dom or testing-library. Adding one changes the lockfile, so do not. The stand-in claim, in a new `apps/board/unit/` file:
  1. Seed a memory store to `approved` on wait A at sha A (`aClaim`, `aWait`, a `WaitResolved{Approve}`).
  2. Fold it with `standingOf` and take `{ waitId, approvedSha }`. That is exactly what `standing.tsx` hands `ScheduleContinuation`.
  3. Assert those values appear in the rendered props, via the HTML or by importing the element tree.
  4. Append a second `WaitStarted` (wait B).
  5. Call `approveHolding` with `{ onSha: approvedSha, waitId }` — the payload the button posts.
  6. Assert `ok: false`, a `detail` naming wait A and wait B, and that `waitsOf(...)` for B has `resolution: null`.

  State in the test's header that this is the click, as far as there is no DOM to click in.
- **The second Done-when box.** Pin it with a source test in the style of `requeue-note.test.tsx:36-41`, which already slices `actions.ts` by function. For each of `approveCard`/`requeueCard`/`closeCard`/`answerCard`, assert that every call site in `decide.tsx` passes `waitId` and that no `waitId === null ? {} :` spread remains. (`decideCard` does not exist; the grep finds no definition.)
- **`apps/board/unit/standing.test.tsx:1243`** ("offers Schedule it, and nothing else, on an approved item"). Its `HELD` fixture needs a `waitId` and an `approvedSha` for the approved state.

Whether a real approved-then-blocked-again ticket was ever approved this way is settled by the log, not by these tests. Look for a `WaitResolved{Approve}` whose `waitId` names a `WaitStarted` with a higher seq than the `ContinueRequested` that followed an earlier `WaitResolved{Approve}` on the same ticket, and whose `note` is `''`.
