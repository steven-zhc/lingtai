# Design: #833, ticket_report reads the ticket reduce

## 1. The column is `ticket_state`, not `ticket`

The ticket asks for "a `ticket` jsonb column", but that name is already taken. `ticket` is the table's primary key, `ticket text primary key` (`packages/projector/src/ticket-report.ts:303`). It is also the `State.ticket` field that `save` writes as `$1` (`:229`). So:

- The new column is **`ticket_state jsonb not null`**.
- The rebuild pin's "every column except the `ticket` column" means every column except **`ticket_state`**. The pin keeps `ticket`, because the key is what makes a row recognisable in the snapshot.
- Adding a column to `create` is drift to every runner that still has the old table. The start-time shape check (`projection.ts:214-215`) already refuses that table, which is the runbook's step 4. Nothing new is needed for it.

## 2. One path for every event on a ticket stream

Today `apply` writes a row only when the `switch` produced a `change`, or for an event on a pass stream (`:508-534`). Every other event on a ticket stream falls out at `:520` (`if (ticket === null || change === null) continue`). Under this change, events the switch never named must still reach `applyTicket`, or `TicketState` goes stale. That includes `TriageStarted` (without it `reduceWaits` never opens an attempt, `domain/src/ticket.ts:98-108`), `DiscussionHeld`, `PromptEdited`, `IssueUpdated`, `TicketDiscovered` and `DispatchRefused`.

The shape inside the loop:

1. **Find the row.** If `isTicketStream(event.streamId)`, the row is `event.streamId`, whatever the type.
2. **Load it once.** If no row exists, start from `fresh(ticket)` with `emptyTicket`. If a row exists, **always decode `ticket_state`, for every event**, including a pass-stream sign of life (`:509-518`) and a `StepEnded`. This keeps `save` simple: it re-derives the facts and writes `encodeTicket(state)` every time. It also means a row that will not decode stops the runner on the first event that touches it, not only on the next lifecycle event. That matches the Edges rule *"a row whose `ticket` does not decode throws"*.
   - A missing row and a row whose column is `null` or garbage are different cases. `reduceStoredTicket(undefined, …)` reduces from `emptyTicket`. `decodeTicket(null, …)` throws. Only `load`'s "no row" branch passes `undefined`.
3. **Reduce a ticket-stream event.** Call `reduceStoredTicket(row.ticket_state, event, 'ticket_report')`. If it returns `null`, it was a replay: `continue` and save nothing.
4. **Run the cross-stream change, if there is one.** That means intervals, cost, rounds, paid and reviews. `RunSpent` matters most here: a triage `RunSpent` is on the ticket's own stream (header, `:22-23`), so it reduces *and* bills in the same pass through the loop.
5. **Save once.** Today `appliedSeq` is set at `:525`, and that stays. `outcome`, `outcome_at`, `passes`, `pass_times`, `kind`, `waits` and `unknown_claims` are derived from the state inside `save`. They are not fields on `State` any more. Delete those fields, and delete `fresh`'s copies of them.

What `State` keeps:

- `ticketState: TicketState`
- `machineMs`
- `intervalsEmpty`
- `reviews`
- `cost`
- `paid: string[]`
- `rounds`
- `open`
- `appliedSeq`

**Intervals open on the reduced state, not the event.** The `TicketClaimed`/`TicketContinued` change runs after step 3, and it pushes an `OpenInterval` only when `after.lifecycle.status === 'claimed' && after.lifecycle.runId === d.runId`. This is the ticket's rule. It sits in step 4 so that `after` exists when the check runs. `link(ctx, d.runId, event.streamId)` (`:361`) still runs for every claim and continuation, absorbed ones included. A pass stream whose claim was absorbed still belongs to that ticket's row for cost.

**Paid.** Push `event.streamId` onto `paid` for every `Action` `RunSpent` on a pass stream that is not already there. Drop today's `in s.claims` guard (`:499`). Then `unknown_claims = claims.filter((c) => !paid.includes(c.runId)).length`. Only membership is ever read, so a paid run that was never a claim costs nothing. And no event order can mark a claim paid before the claim exists.

**Waits.** The ticket's mapping, from `state.waits`. When `triage.result !== null`, `triage.started` is non-null by construction: `WaitTriaged` sets a result only where `started?.attempt === d.attempt` (`domain/src/ticket.ts:113`). Narrow `started` with a check that throws, not with `!`, so a broken invariant names itself.

## 3. The dedupe: one atomic write, using the condition already there

The write is already atomic. `save`'s upsert ends `where ticket_report.applied_seq < excluded.applied_seq` (`:213`), so of two runners that both loaded the old row, the second's write touches 0 rows. **Keep that as the only write condition, and do not add a JSON-path comparison on `ticket_state->>'lastSeq'`.** A JSON path is written differently in SQLite and in Postgres, and it would add nothing:

- `applied_seq` is set to `event.seq` on every save (`:525`, `:514`).
- Every save of a ticket-stream event also sets `state.lastSeq = event.seq` (`domain/src/ticket.ts:438`, which runs on every branch of `applyTicket`, including `closed`'s absorb at `:453` and `default` at `:757`).
- So `applied_seq >= state.lastSeq` holds for every stored row. A write guarded on `applied_seq` is therefore at least as strict as one guarded on `lastSeq`.

Write that argument in a comment beside the `WHERE`.

`reduceStoredTicket`'s own `event.seq <= state.lastSeq → null` check is the "skip before `applyTicket`" that the spy asserts. On the projection path, `:522`'s `appliedSeq >= event.seq` check already comes before it. Keep both: the function is shared with tickets 11 and 13, which have no `applied_seq`.

**The interleaved test** goes in `ticket-report.test.ts` or the replay test file. Wrap the `ProjectionContext` so that the second `apply` gets the `select * from ticket_report` result the first `apply` saw *before* its save. Then run `apply([e])` with the real context, and `apply([e])` with the wrapped one. Assert that the row matches one delivery: `passes`, `pass_times`, `waits`, and the `ticket_state` decoded. Nothing in `src` needs exporting for this.

## 4. The codec: a zod schema in domain, not hand-written checks

Put it in `packages/domain/src/ticket-codec.ts`, exported from `@lingtai/domain` the way `ticket.ts` is. Domain already depends on `zod` ^4 (`packages/domain/package.json:18`).

`decodeTicket` parses a `z.strictObject` for `TicketState`. Its nested reasons and payload copies reuse the event schemas:

- `WaitReason`, `Resolution` (`wait.ts:229`, `:259`)
- `TriageResult` (`wait.ts:874`)
- `TriageStartedBy`, `ReleaseCause`, `SplitChild`, `Tier` (`events.ts:2164`, `:249`, `:352`, `:85`)
- `DiscussionHeld.shape.outcome` (`events.ts:1873`)
- the `IssueUpdated` change enum, for `github.last`'s keys

Then:

- **Text or value.** Accept a `string` and `JSON.parse` it (SQLite), or take a parsed value as-is (Postgres `jsonb`). A `JSON.parse` failure throws the same named error.
- **`Date`.** These fields hold one:
  - `claims[].at`
  - `lastAttemptAt`
  - `since`
  - `waits[].at`
  - `waits[].triage.started.at`

  Each is an ISO string encoded and a `Date` decoded.
- **`lastSeq`.** It must be `null` or a string of digits, then `BigInt(...)`. A JSON number is refused, which is the Done-when case.
- **`grantRef`.** The `approved` lifecycle's `grantRef` is optional. `applyTicket` spreads it in only when present (`ticket.ts:668`), so the schema marks it `.optional()` and the encoder never writes `undefined`.
- **The error.** The message names the zod issue's `path` joined with `.`, the ticket's stream id (pass it in, or let the projector wrap the error), and `lingtai projection rebuild ticket_report`. Throw a named error class so the runner's `failure` carries it.
- **`.default()`.** Several payload schemas in `events.ts` carry one (`:1413`, `:1426`, …). None of them is a type that `TicketState` holds. If one is ever added, a default would quietly fill a gap. That is exactly the case the round-trip test exists to catch, so do not loosen the test to make one pass.

**A trap in the round-trip test.** `JSON.stringify` drops a key whose value is `undefined`, and `toStrictEqual` treats `{a: undefined}` and `{}` as different. A fixture payload copied into the state with an explicit `undefined` would fail the round trip without any defect in the codec. A real log cannot hold such a key: payloads come back from JSON. If you hit one, it is the fixture's, so name it in the test. Do not invent an encoding for `undefined`.

## 5. The rebuild pin: what its diff will actually touch

Merging every history by `seq` puts each `ticketStream(PROJECT, n)` on its own row, except one: every run history shares `runTicket`, `ticket-…-9001` (`domain/test/histories.ts:105`). That row has no ticket-stream lifecycle events, so its derived facts should not move.

**The ticket's list of touched rows misses one.** `lateHistories.ticket.closedByPersonThenClaimed` (9113, `histories.ts:947-963`) ends with `TicketClosed` and then a fresh claim. That is a second D6 cell, and today's code reopens it (`:371-375`). Assert it in the same `it('D6: …')` as `claimedAfterClosed`. Do not leave it as an unexplained line in the snapshot diff.

If the diff touches any row beyond those five (four from the ticket, plus 9113) and the `claims` reshape, that row is a cell nobody named:

- Give it its own `it`, citing the domain rule that decides it.
- Never change `src` to keep it out of the diff.
- Never regenerate the snapshot after the `src` commit (`backlog-rebuild.test.ts:5-10`).

## 6. Existing assertions that change, and which cell each one is

- **`ticket-report.test.ts:160-172`** asserts `reopened` → `outcome: 'open'`. This is D6, so it becomes `'closed'`, with no new pass and no open interval.
- **`ticket-report.test.ts:194-197`** is *"takes the kind of the last claim even when it is null"*. This is D4, so `kind` is the previous non-null value. Rename the `it` to say so.

`ticket-report-read.test.ts` reads through `ticketReportRowOf` (`:139-157`). It ignores columns it does not name, so `ticket_state` and the reshaped `claims` do not reach the report. No changes are expected there.

## 7. The header comment

The comment at `:13-14` currently reads *"A pass is a claim, and a continuation is not (`claimShapeOf`, 0109 §5). Both open an interval of machine time."* That is now wrong in two ways:

- A pass is one of `TicketState.claims`.
- An interval opens only where the reduce holds that run.

Add one line saying that `ticket_state` is the stored `TicketState`, and that a change to what `applyTicket` returns makes stored rows stale (§4.5's runbook).
