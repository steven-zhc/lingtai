# #781 design note: fold *What will happen* into the rail

## Where it goes

Three files change, plus the tests named below:
- `apps/board/src/app/rail.tsx`
- `apps/board/src/app/standing.tsx`
- `apps/board/src/app/globals.css`

`plan.tsx` stops being a component.

## `Rail`: what `plan` means in each case

`Rail` (`rail.tsx:229-264`) gets two prop changes: `progress: RunProgress | null` and `plan?: PlanView | null`. **`undefined` and `null` mean different things on `plan`. Keep them apart.**

| `plan` | meaning | draws |
|---|---|---|
| `undefined` | the card, or a running, blocked or approved page | exactly today's markup. No new element, no new attribute and no new style, so `rail.test.tsx` passes unchanged. |
| `null` | a queued page whose recipe could not be read | today's segments and line (when `progress` is set), then `<p className="empty">The recipe could not be read, so what a run would do here is not known.</p>`. When `progress` is also null, that sentence is all `.seq` holds. |
| `PlanView` | a queued page | segments, then the line, then the closed `<details>` |

The `null` row puts #76's rule (`plan.tsx:68-75`, *"Never merely absent"*) inside `Rail`. Then `standing.tsx` has one call to make and no second branch for the sentence.

If `progress` is null and `plan` is `undefined`, `Rail` returns `null`. No caller does this; the guard is only there for the type.

## The header call site

Today the header draws the rail only when `progress !== null` (`standing.tsx:708`). A never-run queued ticket has no progress, so the condition becomes `progress !== null || queued !== null`. Pass `plan={queued?.plan}`: on a non-queued page `queued` is null, so this gives `undefined`. Do not pass `?? null`, which would turn every running page into the *recipe could not be read* case.

The unframed branch at `standing.tsx:768-773` is never reached for `queued`, because `framed()` at `:27-28` includes it. Leave it alone.

Delete `<Plan plan={queued.plan} />` at `standing.tsx:1099`. Then delete the import at `:45` and the comment at `:1074-1076` that still says *prompt or plan first*.

## With no progress: segments built from the plan

Build `StepProgress[]` (`progress.ts:148-161`) from `plan.steps` inside `rail.tsx`. Each step becomes `{ step, planned: actions, state, actions: actions.map(name => ({ name, state })) }`, where `state` is `'skipped'` when `p.skipped` and `'pending'` otherwise. Hand that to `Segs` with `at={null}`.

**Do not call `foldProgress` for this.** It takes a `StepPlan` map (`progress.ts:359-361`), not a `PlanView`, and folding an empty stream to say "nothing has happened" is a detour.

`PlannedStep.step` is a `string` (`queued.ts:42`) and `StepProgress.step` is a `Step`. Narrow it with the same `STEPS.includes` test that `stepOf` uses (`progress.ts:240-243`); do not cast.

With progress null there is no `now` and no sentence line. This is what the ticket asks for, and it means `held` is ignored in this case.

## The plan row and the column rule

**This is the decision the ticket leaves open.** `.segs` has ten fixed columns: `grid-template-columns: repeat(10, minmax(0, 1fr))` (`globals.css:492`). The ticket's rule appends any plan step the rail does not have, which can give eleven columns. Two other approaches were considered and rejected:
- **Padding the rail's `steps` with fake entries.** Rejected: that draws a segment claiming the step was `skipped` in a run that never had it, which is exactly the kind of false mark 0016 §4 exists to prevent.
- **Clipping the plan to ten columns.** Rejected: that drops a plan step, which the ticket forbids.

Do this instead:
1. Change the rule at `globals.css:492` to `repeat(var(--steps, 10), minmax(0, 1fr))`.
2. When `plan` is a `PlanView`, compute the column list once: the rail's steps in order, then any plan step the rail lacks.
3. Set `style={{ '--steps': n }}` on the `.seq` (cast the style object; `CSSProperties` has no custom properties).
4. `Segs` still draws only its own steps, so an appended column has no segment above it. That is the honest picture: the old run never reached that step.
5. The plan row inherits `--steps` and lines up cell for cell.

The card never sets `--steps`, so its markup does not change.

The plan row is `<ol>` with a class of its own, for example `splanrow`, given the same grid declaration. **Do not reuse `.segs` or `.seg`:** tests and selectors count those as the rail.

Each cell is one of:
- the step name, then `actions.join(', ')`;
- the step name, then a muted `skipped` (a class, not the old `.pill`);
- empty, for a rail step with no plan entry. Keep it as an empty `<li>` so it holds its place in the grid; do not drop it.

The `<details>` gets its own class (for example `srailplan`) and no `open` attribute. The summary reads `What the next pass does at each step`. `limits(plan)` goes under the row as a `<p>`.

**No element may carry the class `plan`.** The *Done when* checks `no .plan`.

Ten labels on a page-wide rail are fine. On the card's narrow lane they get cut, but the card never draws a plan row. Inside a cell, allow wrapping with `overflow-wrap: anywhere`; do not use an ellipsis, because the action names are the content here, not a convenience.

## `plan.tsx` and its tests

Move `limits` (`plan.tsx:30-58`) into `rail.tsx`, keeping its doc comment: the *straight to you* paragraph is the reason the code looks the way it does. Then delete `plan.tsx`.

It has one other importer: `unit/queued.detail.test.tsx:24`, which renders `<Plan>` at `:306`, `:333`, `:352` and `:364`. **Port those four assertions to `Rail`; do not delete them.**
- the *straight to you* and *N restart(s)* footer, which pins 0040 §5;
- the null-plan sentence;
- whatever `:306` and `:352` check about step lines and the over case.

Render them as `<Rail progress={null} live={false} plan={…} />`. They are the only unit tests guarding `limits`.

In `globals.css`:
- delete the `.plan`, `.planhead` and `.plan .step(s)` rules (`:1870-1892`);
- delete the `.spair > .plan` selectors (`:1698`, `:1712`, `:1727`, `:1737`).

The pair is now two children in the existing 1fr/1fr grid (`:1706-1709`). Equal width needs no new rule.

## Tests

- **`rail.test.tsx`:** keep every existing case as is, and add:
  - a plan row: one cell per step, the `<details>` is closed, the summary text, the `limits` line;
  - mismatched steps: a rail step with no plan entry gives an empty cell, and a plan step with no rail entry gives an appended cell with `--steps` above 10;
  - `progress: null` with a plan: ten `.seg`, no `.snow`;
  - `plan: null`: the sentence.
- **Queued `task-page.test.tsx` cases:**
  - exactly one `.seq` and no `.plan`;
  - the children of `[data-rank="pair"]` are `.outgoing` and then the discussion;
  - a never-run queued fixture (no progress) still draws the segments.

All of this is unit-level and checked by `HOME=/nonexistent pnpm test` and `pnpm typecheck`. Nothing here needs `pnpm test:integration`.

## Edges the ticket does not settle

- **A queued ticket with a previous run and `live={false}`:** the header passes `held={budget}` as today, so the line reads *nothing running* or *X refused*. This is #778's behaviour and is unchanged.
- **The `--steps` cast** is the one place a later change to `.segs` could quietly break alignment. Add a comment at `globals.css:492` saying the plan row reads the same variable.
