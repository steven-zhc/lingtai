## Design: *add to this resolution* (#574)

### Where it goes

The channel already exists: `TriagePicks` wraps the whole blocked page (`apps/board/src/app/standing.tsx:691` to `:1095`). The blocked-page `{discussion}` at `standing.tsx:890` sits inside that provider, beside the resolution cards. So the Discussion pane gets its target through `useTriageDraft()`. It needs no new prop drilled through `standing.tsx`. A Discussion rendered outside the provider gets `null` back, which means "not under a wait". It then keeps today's two buttons, including `concludeChat({outcome:'ticket'})` (`discussion.tsx:734-747`).

### The decision: move the drafts into `TriagePicks`

Today the provider only *derives* the composed text (`triage-picks.tsx:37-43`). The two drafts it needs to reach are local `useState` in two components:

- **Body draft.** `EditBodyAndRequeue` holds `text`, `draftWaitId` and `edited` (`decide.tsx:319-325`). It shows `composed` until `edited` (`decide.tsx:328`: `draftWaitId === waitId && edited ? text : composed`).
- **Answer box.** It is not a separate component. It is `Requeue` with `asked={true}` (`standing.tsx:981-990`), and its state is the local `note` and `asking` (`decide.tsx:455-457`). The box is closed until *Answer* is clicked.

A sibling cannot write into either one. So the provider should own both drafts, with the same wait-scoping the body editor uses today:

- `body: { waitId, text } | null`. Null means not edited, so the editor follows the picks. This replaces `edited` and `draftWaitId`.
- `answer: { waitId, text } | null`.
- `add(text)`: appends to whichever one is the current target.

The components read and write through the context instead of their own state.

**Keep this behaviour:** when a wait ends, the unsent body draft stays on screen (`decide.tsx:340-342`, *"Your unsent draft is below; copy it before leaving."*). The provider must not clear a draft when `waitId` goes null. Today the component compares `draftWaitId` to the current wait instead of resetting, and the provider should do the same.

### What *add* does

`add` is page state and nothing else. It does not call `concludeChat`, writes no event, and makes no server call. This is the ticket's Watch out: 0118 §6 says *"_Write it into the body & requeue_ is one resolution. It writes a section to the ticket's body through the existing `ticket` outcome"* (`doc/decisions/0118-a-hold-explains-itself.md:441-443`). The resolution is the only thing that writes.

Append is a pure function. Put it in `triage-picks.tsx` and export it so it can be tested:

- `next = current.trim() === '' ? addition : current + '\n\n' + addition`
- For the body, `current` is `body?.text ?? composed`. The first add freezes the composed picks into the draft, and from then on `body !== null` means edited. That is the ticket's *"stops following triage's picks"*. The picks already in the text stay there. Later picks no longer change it.
- For the answer, `current` is `answer?.text ?? ''`. The add also has to open `Requeue`'s box (`asking = 'primary'`), so the open/closed state moves into the context too, or is derived from `answer !== null`. Otherwise the person never sees what was added.

**The answer box is an `<input>`** (`decide.tsx:488`), so a pasted multi-line answer loses its line breaks. When `asked` is true, make it a `<textarea>`, as the body box already is (`decide.tsx:345`). Leave the withdraw box and the requeue *why* box alone.

### Which resolution is the target

The target is the resolution the page draws first, and only when it writes text a person can see:

- **With a judge/triage disagreement:** `recommendedBy[reading]` (`standing.tsx:571-575`). The reading is client state (`triage-picks.tsx:35`), and `ResolutionCard` already chooses this way (`triage-picks.tsx:163-164`).
- **Otherwise:** `recommended` (`standing.tsx:569`).
- **Then:** it counts as a target only if it is `EditBodyAndRequeue` or `AnswerQuestion`. Anything else, or a *Neither* reading, means there is no target.

Pass `recommended` and `recommendedBy` into `TriagePicks` as props and compute the target there with a pure `draftTarget(...)`. The server already computed both; nothing new is asked of `recommendedResolution`.

Split and the fixes list are #563's and are not targets. The comment at `standing.tsx:563-564` says *"`Split` has no card until its editor exists (#563)"*.

### In the Discussion pane

- **Under a wait with a target:** *Add to this resolution* **replaces** *Add to the ticket*. It must not sit beside it. Keeping both is exactly the double write the Watch out describes: the body gets written now, and the resolution writes it again later. *Use for the next run* stays.
- **Under a wait with no target:** both of today's buttons stay, unchanged.
- **What gets added:** the proposal's text when the turn has a proposal. Otherwise the answer's own `t.answer.text` (`discussion.tsx:682`), so that every answered turn offers the action, as the first Done-when line asks.
- **No `d.held` check.** The proposal block is gated on `d.held === null` (`discussion.tsx:708`). An add concludes nothing, so it does not need that gate.

### Tests (`pnpm test` only; nothing here touches integration)

- **Pure functions.** Unit-test the append function and `draftTarget`. Cases: composed picks plus an answer gives both texts, joined by a blank line. A *Neither* reading gives no target. `Close` or `Approve` as the recommended resolution gives no target.
- **Component tests.** Use the harness pattern from `unit/edit-body-and-requeue.test.tsx`. **That harness mocks `useState` by position** (`harness.values[4]`, line 70) **and returns `harness.triage` for every `useContext`** (line 24). Moving state out of the component shifts those indices and changes the shape the context has to have. Rewrite those assertions; don't patch the indices one by one. Add two cases:
  - An add into an `EditBodyAndRequeue` draft renders in the textarea, and the draft no longer changes when the picks change.
  - An add into the `AnswerQuestion` box opens the box and shows the text.
- **Nothing written.** Assert that `editBodyAndRequeueCard`, `answerCard` and `concludeChat` are all **not** called by an add. This is the unit-level stand-in for "writes nothing". The event that would settle it in the log is the absence of any `Discussion…Concluded` (or similar) and of any `WaitResolved` between the add and the person's click on the resolution.
- **Static render.** A `renderToStaticMarkup` check in the style of `unit/discussion-live.test.tsx`: inside `TriagePicks` with an `EditBodyAndRequeue` target, the label reads *Add to this resolution* and *Add to the ticket* is absent. Outside the provider, *Add to the ticket* is still there.

No ADR conflicts with this. It implements the sentence 0118 §6 already makes.
