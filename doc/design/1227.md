# Design: #1227: `blocked by:` on the local ticket form, `--blocked-by` and the list tag

The ticket settles most of the shape. This note covers only what the code forces and the ticket leaves open. #1226's store is already here in full: `addBlockedBy` / `removeBlockedBy` / `listBlockedBy` are on `DbTicketsEffects` (`packages/conductor/src/db-tickets.ts:252-254`). Every listing row carries `dependencies.blockedBy` as an **open**-blocker count, from the subquery at `db-tickets.ts:174-175` mapped at `:216`. So the CLI only calls these. Nothing in `packages/conductor` changes.

## 1. One parser for a blocker list, shared by the form and the flag

Write `splitBlockers(value: string): { ok: true; numbers: number[] } | { ok: false; why: string }` beside `splitLabels` (`apps/cli/src/ticket.ts:497`):

- Split on `,`, trim each item and drop empty ones, as `splitLabels` does.
- Strip one leading `#`.
- Each item must be a positive integer. Otherwise refuse with `blocked by: "x" is not a ticket number`.
- Return the numbers sorted ascending, without duplicates.

`parseTicketForm`'s `blocked by:` line and `newFromFlags`' `--blocked-by` both call it. Then `--blocked-by '#3, 5'` and a form line `blocked by: #3, 5` cannot disagree. The comment on `splitLabels` already makes the same promise: *"`--label` uses the same rule"*.

## 2. `parseTicketForm` has three places that know the names of the form's lines, not one

Each of these needs `blocked by:`. The second is easy to miss.

- **The title-slot check** (`ticket.ts:468-470`). It keeps the blank title slot only when the first non-blank line `startsWith('labels:')` or `#!`. In `new`'s empty form, if the person deletes the `labels:` line, the first non-blank line becomes `blocked by: `. That line gets promoted into the title slot and is then refused as a title. Add `blocked by:` to that predicate so the slot is kept.
- **The title refusal** (`:474-476`). Add a parallel refusal: *a title starting `blocked by:` reads as the blocked by line*.
- **The header walk** (`:480-491`). Read the optional `labels:` line, then an optional `blocked by:` line, in that order only. The refusal names both lines: *"neither the title, labels: nor blocked by:"*.

The round-trip comment (`:405-412`) gains: *"…and whose `blockedBy` is ascending and unique"*.

## 3. Every place that builds a `TicketFormFields` today

Once the field is added, `tsc` will point at each of these. The decision for each:

- `sameLabels` / `formsEqual` (`:504-510`). Compare `blockedBy` element-wise. Add a `sameNumbers` helper, or generalise `sameLabels`.
- `formFromTicket` (`:518-526`). It takes a `Ticket`, and `getIssue` returns no links. Give it a second argument, `blockedBy: readonly number[]`, and pass it through. Don't run the numbers through render and parse: they come from `listBlockedBy`, which already orders by number (`db-tickets.ts:551`) and has a primary key that rules out duplicates (`:68`).
- `titleAndLabelsRoundTrip` (`:542-549`). Build `raw` with `blockedBy: []`. Links can't fail the round trip because they are integers by construction, so this guard does not change.
- `newFromEditor`'s `empty` (`:661`). Add `blockedBy: []`. The *no change* check at `:678` then still compares against it.

## 4. `edit`: check what can be checked before the first write

The ticket's order is `updateFields`, then every remove, then every add, stopping at the first refusal. Keep that order. But move the two refusals the CLI can predict to **before** `updateFields`, so the common mistakes write nothing:

- the ticket's own number in `blocked by:`. `addBlockedBy` would refuse it with `#n cannot block itself` (`db-tickets.ts:483`);
- a number that doesn't exist. Check it with `getIssue`, the same pre-check `new` does.

Both refuse with the store's own wording, keep the text and exit 1. After that, only a cycle (`db-tickets.ts:512-516`) or a store failure can stop `edit` halfway. That case uses the ticket's partial-write sentence.

Build that sentence from what actually landed:

- `changed` (`:780-783`) gets one entry, `blocked by +#9 -#2`, listing the adds and removes that went through.
- The refusal is appended after it.

If nothing landed before the refusal, say `nothing written` rather than `updated #4 — `.

`original.blockedBy` comes from `listBlockedBy(options.issue)`, read through `attempt` right after `getIssue` (`:743`). If that read fails, `edit` exits 1 before the editor opens (ticket's Edges). Map the result with `.map((l) => l.number)`, keeping open and closed links (ticket §2).

The `title === ''` refusal (`:775-778`) stays where it is. A form whose only change is `blocked by:` still has the stored title, so it passes that refusal and skips `updateFields`.

## 5. `new`

- **Choosing the flag path.** The flag path is chosen when any flag is present (`:628-635`). Add `options.blockedBy !== undefined` to that condition.
- **The `stray` message** (`:572-576`). It picks the first stray flag in the order `--label`, `--blocked-by`, `--body`.
- **Where the blocker checks go.** In the flag path, parse `--blocked-by` before `pickProject`, next to the `titleAndLabelsRoundTrip` check (`:584-588`): a parse refusal needs no store. In both paths, run the `getIssue` existence checks after `ticketsFor(name)` and before `createIssue` (`:607`, `:692`).
- **Store access.** `newFromFlags` currently reaches the store only inside one `Effect.flatMap` (`:607-609`). Resolve `tickets` once (`yield* ticketsFor(name)`, as `ticketEdit` does at `:741`) and use it for the checks, the create and the links.
- **A link that fails after the create.** It can't be a cycle or a self-block, so only a store failure can do this. Report `created #n` first, then the refusal, and exit 1. The ticket exists, and the line has to say so, so the person doesn't rerun and get a duplicate.
- **The editor path** keeps the text file on that failure, the same as any other refusal after a write.

## 6. `list`

`readTicketListing` maps synchronously (`:290-302`). Replace that with `Effect.forEach` over the issues, calling `listBlockedBy` only when `t.dependencies?.blockedBy` is greater than 0. `Ticket.dependencies` may be `null` on the shared type ("Null is not zero"), but this store always fills it in (`db-tickets.ts:214-216`), so treat `null` as nothing to read.

Keep `.filter((l) => l.state === 'open').map((l) => l.number)`. Route the read through `attempt`, so that a failure is reported as a refusal sentence, not as a defect that throws.

The type is `TicketListRead`, whose failure arm is `TicketRefusal`. Find how that union's refusals carry a message, and return the store's `why` through the same arm.

## Tests

All of these are unit tests on the existing `:memory:` SQLite seam (`apps/cli/unit/ticket.test.ts:141`). That counts as unit under 0060 §1 here: it is in-process and touches no filesystem. The `edit` cases use the scripted `edit` seam (`ticket.ts:72-77`).

Existing expectations on rendered forms each gain a `blocked by: ` line once, as the ticket notes. Nothing here needs `pnpm test:integration`. Nothing adds an `async` function or an `Effect.run*`.
