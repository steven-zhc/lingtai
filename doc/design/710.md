# Design: #710, the machine's GitHub-auth question

## Where the line numbers moved

The ticket cites `first-project.ts:515` and `:607-614`. Both are out of date since #708 landed:

- `runGithubBranch` is at `apps/cli/src/first-project.ts:530`, and its `gh` branch is at `:577`.
- Init's GitHub ending is in `apps/cli/src/init.ts`, not in first-project. It runs from `:563` to `:587`.
- The App-machine path for a machine that already has projects is at `init.ts:589`.

## One new module, two callers

Put the question in a new `apps/cli/src/github-auth.ts`, as `askGithubAuth(world, flags, kept)`. It sits beside `github-app.ts` and follows that file's rule of declaring only the slice of the world it uses (`github-app.ts:6-8`). It returns one of:

- `{ auth: 'gh', login }`
- `{ auth: 'app' }`
- `{ refused }`

`runGithubBranch` calls it first, ahead of the `world.github.auth?.() === 'gh'` test at `:577`. That test then reads the function's answer instead of `world.github.auth` directly. `init` and `add` both reach it through `runGithubBranch`.

**`chooseFirstProject` must stop asking the App's create/skip question before this one runs.** Today a machine with no App and no auth goes to `askFirstProject` at `first-project.ts:308`, which asks the project question *and then* "create the GitHub App now, or skip it". That would put the App question ahead of the auth question. The fix:

- In that last `else`, call `askProjectKind` (`:212`) instead. `askedApp` stays `null`.
- `runGithubBranch`'s App path already asks create/skip on its own when `askedApp === null` (`:642-646`). After the auth question answers `app`, that call takes over unchanged.
- Leave `askFirstProject` itself alone. `github-app.test.ts` pins it to "asks both questions every time" (`first-project.ts:206-210`).

## World seams

`FirstProjectWorld.github` (`first-project.ts:143`) gains two seams:

- **`ghStatus: () => Promise<GhStatus>`**. Live, this is `ghStatus()` from `@lingtai/github` (`packages/github/src/gh.ts:102`). Tests get a fake. Call it only when the question is actually asked or `--github-auth gh` was given. Never call it on a machine whose auth is already settled.
- **`writeAuth: (kind) => Promise<void>`**. This is the document edit. Write one function, in `github-auth.ts`, that takes `{ read, write }` and a path. It re-reads the file, runs `parseDocument`, calls `setIn(['github','auth'], kind)` and writes `toString()`. That is the same shape as `init.ts:252-262`/`:779-781` and `create-app.ts:794-799`, and it keeps every other key and comment (0114 §6).
  - Init's world passes `world.machine.read`/`write` with `configPath(world.env)`.
  - `liveFirstProjectWorld` passes `node:fs`.
  - Re-reading, rather than reusing init's in-memory `config` Document, is deliberate: `chooseStore` has already written the file. A file that does not parse is refused by name and nothing is written.

**Init's world must pass `auth` now.** `first-project.ts:145-147` says "Absent reads as 'not `gh`' — `init`'s world leaves it out". That is no longer true after this change. Init cannot call `githubAuthKind()` as it stands, because that reads the real disk (`packages/env/src/index.ts:1412`), and init's tests use the `world.machine` fake. Add a small export in `packages/env` that `githubAuthKind` itself delegates to. It elects over `world.env` and a `MachineFile`:

```
electGithubAuth(githubSection(environmentProvider(env)), machineGithub(file))
```

`machineGithub` (`:1210`) is the one piece that is not exported today. Init feeds it `machineFor(world, path)` (`init.ts:265`).

A refused `github.auth` (for example `"foo"`) throws. That makes init refuse by name before anything is asked, the way `add` already does at `add-github.ts:210`.

## The question itself

1. **When it is skipped.** `auth()` is non-null, or the `AppCheck` says configured. In that case log one `github  <gh|app> — <source>` line and ask nothing. `ElectedGitHubAuth.source` (`index.ts:1349`) already names the file or `LINGTAI_GITHUB_AUTH`.
   - A `--github-auth` that disagrees with what is set is refused by name, for example `--github-auth app, but github.auth is gh here`.
   - A `--github-auth` that agrees with what is set is accepted.
2. **When it is asked:**
   - **`ghStatus` ok and `ghScopeGap(status) === null`** (`gh.ts:144`):
     - `choices: ['gh','app']`, `fallback: 'gh'`.
     - The prompt names the login and says that Lingtai's labels, comments, pull requests and pushes will appear as it.
   - **Anything else:**
     - Log the reason first: `status.detail`, or `ghScopeGap`'s sentence, which already carries the exact `gh auth refresh … --scopes <missing>` command.
     - For `missing`, the line also says how to install `gh`.
     - Then ask with `choices: ['app','gh']` and `fallback: 'app'`.
     - **Answering `gh` here is the same refusal as `--github-auth gh` on a login that is not ready**: it names the command to run (`gh auth login --hostname github.com --web --scopes workflow`, or the refresh command), ends in "and run this again", and writes nothing.
     - That gives one code path for "checked, not trusted", whether the `gh` came from the flag or from the terminal.
3. **Ask through the world as it arrives.** Never pass it through `acceptingDefaults` (`question.ts:82`). Only the local branch wraps today (`first-project.ts:417`), so keep it that way. 0114 §1: "`--defaults` does not, because it decides whose name Lingtai acts under". With no TTY and no flag, `question()` refuses with `flag: '--github-auth gh, or --github-auth app'`.
4. **Which answers get written, and when:**
   - **`gh` is written at the answer**, before `runGithubBranch` goes on.
   - **`app` is written only once the App has answered** (`'made'` in the `waitForApp` result), never on skip or timeout.
   - Why: once `github.auth: app` is written, `githubAuthKind` returns `'app'` with no `app_id` behind it. `add` would then take its App check (`add-github.ts`, `deps.check`). Its comment says `checkInstallation` calls `githubApp()`, "which throws rather than answering 'not installed'". Today, at a terminal, the nothing-configured path runs the questions and then offers to create the App instead.
   - Leaving `app` unwritten until the App exists keeps a skipped App on the question next run, and that is the right answer, because nothing was set up. It still satisfies 0114 §1's "`lingtai init` writes it" for every machine that finished.

## Conflicting flags

Put these in `conflictingFlags` (`first-project.ts:164`), so they are refused before anything is asked:

- `--github-auth gh` with `--github-app create`. `--github-app skip` beside `gh` is allowed, as `:581` already allows it.
- `--github-auth` with `--project local`, or with `--local <dir>`.
- An answer of `local` at the terminal together with `--github-auth` is refused inside `askProjectKind`, in the same way that `--github-app` is refused at `:222-228`.
- `--github-auth gh` on a machine with an App configured. That check happens at the skip in step 1, since only there is the `AppCheck` known.

Init's no-question path (`init.ts:418`, `discardedFlag`) gets `'github-auth'` in its list. Otherwise the flag is silently dropped on a machine that already has projects.

## Init's ending

`FirstProjectOutcome`'s github variant (`first-project.ts:159`) gains `auth: 'gh' | 'app'`. In `init.ts`:

- **`:563`.** Under `gh`, skip the `chosen.app === 'already'` block entirely: no `startBoard()` and no `/setup/repository`. Go straight to the existing `next: lingtai add <owner>/<repo>` at `:587`.
- **`:589`.** The `else if (app.configured)` path is guarded on the elected auth not being `gh`, so a `gh` machine that also carries an App never opens the App's wizard.
- **`:363`.** The "GitHub App" fact. Under `gh`, it must not say "the board's first screen creates it". Say `not used — github.auth is gh`. That is a one-line change, and the board itself is #713.

## `add` with a slug

`askBeforeGithubAdd` refuses at `add-github.ts:223` before `runGithubBranch` is ever reached. That refusal is the ticket's "run `lingtai init`" edge, and it stays, **except when `--github-auth` is given**:

- With `gh`, treat `kind` as `'gh'` for the early check. That runs `ghAccess`, so the scope and push check happens before any recipe question.
- With `app`, take today's nothing-configured path.

`runGithubBranch` then asks `ghStatus` a second time. That is a second local `gh auth status`; leave it rather than threading the first answer through.

If registration fails after `gh` was written, the refusal's `kept` clause must say `github.auth: gh` was written.

## Edges the ticket leaves to the design

- **`ghStatus` read fails** (`too-old`, `unparsed`, `no-account`, `signed-out`): treated as not ready. Its `detail` is printed, and `app` is the default.
- **`LINGTAI_GITHUB_AUTH` exported:** counts as set. The question is not asked, and nothing is written.
- **A process that dies between the answer and the write:** nothing is written, and the next run asks again.
- **A process that dies after the write:** the next run is not asked. That is the re-run edge.

None of this touches `events`, so no seq settles it. It is all unit-checkable through the fakes.

## Tests

- **`first-project.test.ts`:** the harness gains a `ghStatus` fake and a recording `writeAuth`. Assert the written kind, and assert that `boardUrl` is never called under `gh`.
- **`init.test.ts`:** the world gains `ghStatus`. Assert under `gh` that `world.board` and `world.open` are never called and that the last line is `next: lingtai add <owner>/<repo>`.
- **Existing tests:** any test that reaches the no-App path now sees the auth question before create/skip. Answer it with `--github-auth app` in those flags, rather than changing what the test asserts.
- **Docs:** `--github-auth <gh|app>` goes in `wizard-options.ts`'s `initOptions` and `addOptions`, and in both help blocks in `commands.ts`, next to `--github-app` at `:53` and `:460`. Then run `pnpm docs:cli`.
