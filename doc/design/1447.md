# #1447: design note

## The decision: an optional flag on `CeilingReached`, not a new exclusion variant

Add an optional field to `CeilingReached` in `packages/domain/src/route.ts:27-30`, for example `by: z.literal('grant').optional()`. Do not add a third `_tag` to `ExcludedCandidate.because` (`route.ts:40`).

**Why a field and not a variant.** `RouteOffer.unavailable` is stored in the log: `ProposalRouted.offer`, built from `z.array(ExcludedCandidate)` at `packages/domain/src/routing.ts:68`. A decision's or a wait's `CandidateUnavailable.excluded` carries the same type (`route.ts:57`). Other processes parse that schema with whatever code they started on, such as the board or a daemon from before this merge. A zod `object` drops a key it doesn't know, so an old reader still parses a new event. A `discriminatedUnion` rejects a `_tag` it doesn't know, so an old reader would fail on every new grant-capped route. The field also covers the ticket's edge about old events: an old `CeilingReached` has no `by` and reads exactly as it does today, so no upcast is needed. The existing upcast at `packages/domain/src/upcast.ts:87-93` already spreads `because` and keeps the new field.

`ceilingOf` (`packages/conductor/src/proposed-route.ts:366-369`) still answers the ceiling for a grant-capped exclusion. What the lap spent and how it is counted don't change. Only the words do.

## How the cause gets to `offerFor`

`offerFor` only sees numbers (`packages/domain/src/failure/respond.ts:668-697`). Carry the cause on `RoutingPolicy` (`routing.ts:36-43`). That type is never parsed ("Not a zod schema … never parsed off the log"), so a new optional key there costs no schema change. For example: `grantCapped?: { refusalFixes?: true; newAttempts?: true }`. `round()` (`respond.ts:678`) and `restart()` (`respond.ts:691`) add `by: 'grant'` to the exclusion when their key is set. `conflictResolutions` is never grant-capped ("never a grant-capped one (#1200)", `routing.ts:41`), so it gets no key.

`run-attempt.ts` builds the policy at `:1894-1899`. It already computes both causes:

- **`refusalFixes`**: capped by a person's grant exactly when `!limitIsAllowance` (`run-attempt.ts:1544`). That covers a lap carrying the grant itself and a later continuation carrying `roundLimit`, which `conduct.ts:1811-1812` sets only for a grant that isn't triage's ("An earlier person's grant does not cap a triage round").
- **`newAttempts`**: capped exactly when `options.from?.grant !== undefined && !options.from.byTriage` (`run-attempt.ts:1549-1550`). It is not tied to `roundLimit`: a later continuation with no grant keeps the recipe's restarts, so the two flags are set independently.

Reuse those two conditions; don't restate them. `byTriage` sets neither flag, so the triage edge keeps today's words.

**When the grant and the recipe both cap.** If the recipe's own ceiling would also have excluded the candidate, the grant still wins and the words name the grant. The comment at `run-attempt.ts:1546-1548` decided the stop belongs to the grant: "the lap that spends a human grant ends at a person rather than at a restart nobody decided". Finding out whether the recipe would also have stopped would mean redoing the `personRounds` allowance arithmetic (`:1545`) just to choose a sentence.

## The words: three places

1. **`notAskedWhy`** (`proposed-route.ts:296-304`). Split `offer.unavailable` into grant-capped and the rest. Each of the rest keeps today's clause. All grant-capped ids share one clause that names the grant once, for example ``(`fix-lines`, `restart` — the round a person granted is used, so the next step is theirs)``. That covers the edge where both caps come from the grant.
2. **`unavailableWhy`** (`proposed-route.ts:315-318`) and **`reasonTextOf`'s `CandidateUnavailable`** (`packages/domain/src/wait-words.ts:197-200`). The comment at `proposed-route.ts:314` says they are the same words. Give both the grant sentence when `by === 'grant'`, through one helper in `@lingtai/domain` that both call so the two can't drift. A judge can reach this path in a `roundLimit` continuation, where `restart` is still on offer, so two candidates are available and the judge is asked. That wait's card shows this sentence, and changing it is intended.
3. **`causeReply`'s `askPerson` / `limit`** (`proposed-route.ts:274-276`). It says ``` `${bound}` is spent, N of N used ``` from `causeBoundsFor(policy, …)` (`:216-222`), where `policy.refusalFixes` is the grant-capped number. The ticket doesn't name this one, but it breaks the same rule ("never says a recipe ceiling is spent"), and it is reachable on the same `roundLimit` path. When the matching exclusion in `offer.unavailable` has `by: 'grant'`, say the grant there too.

## What settles it in the log

On a real run, the `ProposalRouted` after the grant lap's refusal should carry `offer.unavailable[].because.by === 'grant'` for `fix-lines` and `restart`. The `StepStarted` that opened the lap carries the `grantWait` of the person's grant (`run-attempt.ts:1110-1111`). The two do not have to appear together: a later continuation after an intervening approval carries `roundLimit` but no `grant` or `grantWait`, and its next refusal legitimately produces `by: 'grant'` for `fix-lines` (the cap propagates, `conduct.ts:1811-1812`). So `by` with no `grantWait` on the lap is valid when the lap's `roundLimit` is set. What is wrong is `by` on a lap with neither a `grant` nor a `roundLimit`, or a grant lap (not `byTriage`) whose exclusions lack `by`.
