# #896: the landing comment

The ticket is mostly right about where this goes. Three things it does not say would each produce a wrong build. They are covered first, then the layout.

## 1. Read the summary from the run's stream, not from `pass.steps`

The ticket says "the summary read from the landing run through `reviewSummaryOf`". The obvious source at the landing call is `pass.steps`, and that source is wrong. A pass that continues a held run does not visit `review` again. Examples: a pass approved at `proposed:`, or one granted a round. In those cases `pass.steps` has no review visit, and the visits that do have one carry an `outcome?: StepOutcome` that is optional (`run-attempt.ts:575`).

The review that cleared this change is on the run's own stream as a `StepEnded`. Read it from there:

- Read the `runId` stream.
- Run `stepOutcomesOf(events)` (`packages/domain/src/read-model.ts:52`).
- Keep the outcomes whose `runId` matches, and take the **last** one with `step === 'review'`.
- Pass it to `reviewSummaryOf` (`packages/domain/src/action.ts:383`).

Use the last review, not the last review that had a summary. A summary from an earlier review describes a diff that later changed.

If the read fails, use `summary: null` and post the landing line alone. A failed read must not stop the comment.

What settles this on a real ticket: the run stream's last `StepEnded` with `outcome.step = 'review'`, specifically its `verdict` action's `result.assessment.summary`.

## 2. The "already posted" scan must also count a failed post

`tellGitHub` records a refused post as `IssueUpdateFailed{ change: 'comment' }`, not as `IssueUpdated` (`tell.ts:208-223`). If the scan only looks for `IssueUpdated` after the latest `TicketLanded`, a failed post gets retried. The Done-when box "a failed post is recorded and not retried" forbids that.

The rule: post nothing if, after the ticket stream's **latest** `TicketLanded`, there is any `IssueUpdated` **or** `IssueUpdateFailed` with `change === 'comment'` and no `waitId`. This is the same rule `editEndedWaits` uses for edits. A failed attempt counts as done (`ticket.ts:617-630` adds a failed `comment-edited` to `edited`).

Use the latest `TicketLanded` rather than the first, so a ticket that lands a second time after a reopen still gets its own comment.

Scan the raw envelopes, as the ticket says. Do not add anything to `TicketState.github`: the codec is strict (`ticket-codec.ts:67`, and `:108` keys `last` by `change`). Nothing else posts a comment with no `waitId` after a landing: `editEndedWaits` writes only `comment-edited` (`tell.ts:476-481`), and the question comment always carries a `waitId` at landing time. So the scan does not need a marker.

## 3. "Attempt N" uses the board's numbering, not the claim count

There are two numberings in the code, and they disagree for a continuation:

- `priorAttemptsFromState` numbers by `state.claims` (`attempts.ts:177-178`). A continuation's re-claim is a second claim on the **same** `runId` (`conduct.ts:1213-1229`), so this count runs one high.
- The detail page and Discussion's `attempt-<n>` number by `state.runs`, which holds each `runId` once (`ticket.ts:515`). `apps/cli/src/triage.ts:457-462` says so: *"1-based, in the ticket's own claim order (`item.runs`) — the same numbering the detail page and Discussion's `attempt-<n>` ref use."*

Use `reduceTicket(...).runs.indexOf(runId) + 1`, with the same fallback to 1 that `triage.ts:462` uses. The landing site already has the reduced ticket state, so compute it there and pass it in `landed.attempt`. Do not compute it inside `tell.ts`.

## Shape

**`conduct.ts:4502-4511`.** Pass `landed: { mergeCommit: merged, base, attempt, summary }` to the existing `tellGitHubAbout` call. Build `summary` as in §1 and `attempt` as in §3. Do not add a second call: the ordering below depends on there being one.

**`tellGitHubAbout`**, `tell.ts:495`. Add a `landed?` option. Handle it after `editEndedWaits` and after the labels write, and before the `appended` loop (`tell.ts:569`). That order has two effects:

- The edited waiting comment reads *Landed…* before this new comment appears.
- The comment is posted before any `close` declared in `end:`.

Steps:

1. Run the scan from §2. If it finds a prior post, return.
2. Build the body with a pure, exported `landingComment({ mergeCommit, base, attempt, summary })`:
   - `**Landed on \`<base>\` in \`<sha7>\`.**`
   - If `summary` is not null, a blank line and then `unmention(summary)`.
   - A blank line, then `Attempt N · reviewed cold`.
   - Format the sha exactly as `editEndedWaits` does (`tell.ts:471-472`): `slice(0, 7)`, and leave out the ` in …` clause when the sha is empty.
3. Post it with `tell({ kind: 'comment', body })`, with no `waitId` and no `question`.

The existing `try/catch` style holds: like the rest of `tell.ts`, nothing here throws. If the scan's read fails, post nothing and record nothing. That is the same choice `editEndedWaits` makes (`tell.ts:450-452`). The landing then has no comment, which is acceptable because a duplicate is the worse error.

**`unmention(markdown)`** is a pure function in `tell.ts` and is exported for the test.

- Outside fenced blocks (```` ``` ```` and `~~~`) and inline code spans, replace each `@` that starts a word, i.e. `/(^|[^\w`])@(?=[\w-])/`, with `@` followed by U+200D.
- Inside code spans, leave the text as it is. The tests need ``` `@types/node` ``` unchanged and `@someone` neutralised.
- Do the splitting with a small scan for backtick runs and fences. Do not pull in a markdown parser.
- An email address like `a@b.c` is not word-initial and is left alone. That is correct, because it does not mention anyone.

**Secrets.** The comment is built only from `base`, the sha, the attempt number and the reviewer's summary. Nothing from `worktreePath`, `home` or `runLog` goes into it. The summary is the reviewer's own text and can still name a path, so `landingComment` runs it through `withoutLocalPaths` before `unmention`. With no summary the comment is the landing line alone, with no attempt footer.

## Edges not in the ticket

- **A continuation landing.** Covered by §1 and §3. Test it: a run stream whose review `StepEnded` comes before the hold, with no review visit in the landing pass, still gets its summary.
- **A `db` source.** `split(ticketId)` returns null, so `tellGitHub` posts and records nothing (`tell.ts:169-170`). The scan runs anyway and finds nothing. That is harmless and needs no special case.
- **A restart between the post and the record.** Accepted, as the ticket says. Copy the wording into the function's doc comment, as `editEndedWaits` has it at `tell.ts:441-444`.
