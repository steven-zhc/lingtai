# Design note: #1220, the operating guide and glossary on how a failure is answered

The ticket's row table is the plan. This note covers only the places where the code on `main` disagrees with the ticket, and the order of work that keeps the attempt inside the wall.

## 1. Build the bounds table from the code, not from 0108 §8's list

The ticket's table names nine action/bound pairs taken from 0108. The code does not have all nine. Write the rows the code has, and list in the PR every pair the code lacks (the ticket's first Edge says to do this).

**What the code has:**

- **`CauseAction`** (`packages/domain/src/failure/respond.ts:967-975`): `fixRefusal`, `startNewAttempt`, `splitTicket`, `writeSpentOnThenRedoStep`, `redoStep`, `resolveConflict`, `askPerson`.
  - `askPerson` carries `why: unclear | environment | limit`. That is the "person only for…" layer: *"Why a person is asked rather than anything done: the question is theirs, the environment is, or a bound is spent"* (`:959`).
  - `actionFor` (`:986`) is the cause → action table. Quote its doc comment for the second layer.
- **`BOUNDS`** (`respond.ts:579-595`) holds the constants: `stepRedos: 3`, `stepRedoWaits: ['1 minute', '5 minutes', '15 minutes']`, `landingRetries: 3`, `baseBranchMerges: 10`, `personAsks: PERSON_ASKS` (5, `packages/domain/src/wait.ts:605`), `triageRetries: 1`, `ticketSplits: 1`.
  - For the *constant* column, quote its comment: *"A constant and not a recipe knob: a knob is a value somebody can set to a loop. Each is counted on the attempt's own stream (`personAsks` and `ticketSplits` on the ticket's, `newAttempts` across the ticket), so a continuation does not reset it."*
- **Recipe keys** (`packages/recipe/src/recipe.ts` around `:3352-3390`): `runtime.limits.attempt.refusalFixes` (default 6), `attempt.conflictResolutions` (6), `ticket.newAttempts` (2), and `run: { turns: 300, wall: '2h' }` with an optional `usd`. Use these defaults in the recipe example at `operating.md:473`.

**What the code lacks:**

- **`commandReruns` / `rerunCommand`.** These appear nowhere in `packages/` or `apps/`. Write no row for them, and say so in the PR.
- **`mergeBaseBranch` and `retryLanding`.** These are not `CauseAction` tags. Base merges and landing retries are done by the conductor (`packages/conductor/src/run-attempt.ts:1869` reads `BOUNDS.landingRetries`).
  - Give them rows by their bound name (`baseBranchMerges`, `landingRetries`) and describe what the system does.
  - Do not invent an action name for either.
- **The count "nine".** Don't print it unless the table really has nine rows.
- **`writeSpentOnThenRedoStep`.** This is the *too big* answer (write where the turns went into the body, then redo). It belongs under *A step redone*, not as a row of its own.
- **`triageRetries: 1`.** This is the source of "if triage gives no usable answer twice, the wait is yours". Cite it there, not in the table.
