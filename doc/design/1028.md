# #1028 — design note

The ticket covers the ports, the faces, the `Ref`, the retry and the count. This note adds four decisions the ticket doesn't make, plus two code traps.

## 1. `logSqlLayer` opens the log when the layer is built; `snapshotsLayer` waits for first use

`eventsLayer` is `Layer.succeed(Events, deferredEvents(processEvents))` (`choose.ts:189`). Each deferred method there is `Effect.flatMap(open, …)` (`choose.ts:170-179`), so nothing opens until a method runs. `LogSql` can't be built that way. `dialect` is a plain field, and a deferred port has no dialect to give until `openOnce()` has chosen a store. `open()` reads the choice with `chosenStore()` (`choose.ts:107`).

- **`logSqlLayer`**: `Layer.effect(LogSql, processLogSql)`, where `processLogSql = Effect.map(Effect.promise(openOnce), (o) => o.logSql)`, written the same way as `processQueries` (`choose.ts:203`). The open happens when a program provides the layer, not when the barrel is imported. A refused open is a defect carrying the 0056 refusal, as the ticket says. Do **not** compute `dialect` from `chosenStore()` in a getter: a second read can answer something other than what `open()` chose, and the comment at `choose.ts:129-131` forbids exactly that ("a second read could answer a stale export rather than the choice this process already made").
- **`snapshotsLayer`**: `Layer.succeed(Snapshots, deferredSnapshotsPort(processSnapshots))`, written like `deferredQueries` (`choose.ts:191-200`). `SnapshotsPort` has no field that needs the open.
- **`deferredLog`'s `snapshots`** is `promiseSnapshots(deferredSnapshotsPort(processSnapshots))`. `deferredSnapshots` (`choose.ts:208-214`) and its three `async` arrows are deleted.

`Opened` (`choose.ts:54-63`) gains `logSql: LogSqlPort` and `snapshots: SnapshotsPort`. It keeps `tickets: promiseLogSql(logSql)` so that `processTicketSql` (`choose.ts:102`) doesn't change.

## 2. Where each face lives

The faces file matches a face by `file` + `fn`, and any file is allowed: `packages/conductor/src/snapshot-state.ts` is listed today (`effect-ratchet.faces.json:3`).

- **In `store-face.ts`**: `queryFace`, `execFace`, `latestFace`, `putFace`, `censusFace`, `promiseLogSql`, `fromPromiseLogSql`, `promiseSnapshots`, `fromPromiseSnapshots`, and `execIdempotently`. This follows how `logPredatesHold` moved (`store-face.ts:142`, re-exported by the barrel at `index.ts:93`).
  - Change `index.ts:29-36` so `execIdempotently` comes from `./store-face.ts` and not `./snapshots.ts`. `db-tickets.ts:1` imports it from the barrel, so it doesn't change.
  - `execIdempotentlyEffect` and `isPostgresCreateRace` stay in `snapshots.ts`.
- **`createSchema` stays in `schema.ts`**, as a face listed with `"file": "packages/event-store/src/schema.ts"`. This is a deliberate departure from the ticket's "they live beside … in `src/store-face.ts`", for two reasons:
  - Callers import it by path. `apps/cli/src/init.ts:135` uses the `@lingtai/event-store/schema` subpath, and `unit/schema.test.ts:7` imports `'../src/schema.ts'`, so `schema.ts` has to export it either way.
  - `store-face.ts` is loaded with every import of the store, through `event-store.ts:42`. Making it import `schema.ts` would pull both migration JSONs (`schema.ts:30-31`) into every process, where today only `init` loads them.
- The import cycle `snapshots.ts → store-face.ts → snapshots.ts` is safe in the same way `event-store.ts ↔ store-face.ts` already is: neither file's top level calls the other's exports.

## 3. Effect 4 traps to avoid in the code

- **`Effect.fn` can't express `query<T>`.** `Effect.fn` loses a generic type parameter. Write `query` as a plain generic function whose body ends in `Effect.withSpan('LogSql.query')`. `exec`, `latest`, `put` and `census` can use `Effect.fn('…')` the way `queries.ts:343` does.
- **No `async` keyword anywhere, including inside `Effect.promise`.** The ratchet counts every async arrow (`effect-ratchet.test.ts`, the `visit` over `ArrowFunction`). Write `Effect.promise(() => client.connect().then(() => client))`, not `Effect.promise(async () => …)`; one stray arrow and the count reads 16.
- **Postgres per-call connection**: use `Effect.acquireUseRelease(connect, use, (c) => Effect.promise(() => c.end()))`. It keeps `Scope` out of the port's type, and the release runs on success, failure and interruption, like the `finally` the ticket cites (`queries.ts:357-359`).
- **`createSchemaEffect`**:
  - Wrap the whole thing in `Effect.uninterruptible`.
  - Run the body between `BEGIN` and `COMMIT` under `Effect.onError(…, () => rollback)`. `onError` re-raises the original cause unchanged, so `notLingtais` (`schema.ts:161-166`) and the postcheck `Error` (`schema.ts:195`) still reach the face's caller as the same instance.
  - Keep `rollback` as `Effect.promise(() => client.query('ROLLBACK').catch(() => {}))`. Today's `.catch(() => {})` (`schema.ts:209`) means a failed ROLLBACK never replaces the error that caused it.
  - Raise `notLingtais` and the postcheck error with `Effect.die(err)`, or `throw` inside `Effect.gen`. Both are a defect carrying that object.
- **`fromPromiseLogSql`** copies `dialect` and wraps each method in `Effect.promise`, so a rejection becomes a defect carrying the same object. That's what `execIdempotentlyEffect`'s `catchDefect` reads `.code` from when called through the face from `db-tickets.ts:102-103`.

## 4. Both log constructors build from the Effect implementation

- `createPostgresLog` (`log.ts:85`): `options.snapshots ?? promiseSnapshots(makeSqlSnapshots(makePostgresLogSql({ url: options.url })))`. Pass the URL through exactly as `createPostgresTicketSql`'s options do today, so the `postgresUrl()` default (`queries.ts`, `PostgresTicketSqlOptions`) applies in the same place.
- `createSqliteLog` (`sqlite.ts:672`): `options.snapshots ?? promiseSnapshots(makeSqlSnapshots(makeSqliteLogSql(options.db)))`.
- `makeSqliteLogSql` belongs in `sqlite.ts`, beside `createSqliteTicketSql` (`sqlite.ts:643-653`), which becomes `promiseLogSql(makeSqliteLogSql(db))`. `makePostgresLogSql` belongs in `queries.ts`, beside `createPostgresTicketSql`.

## What stands in for the integration half

Both Postgres paths can only be checked after the merge (`integration/snapshots.test.ts`, `integration/queries.test.ts`): the per-call connection's release, and the retry against a real `42P07`. Before the merge, these unit tests stand in for them: the fake-`LogSqlPort` retry test, the face-identity test (`rejects.toBe`), and the SQLite run of `test/snapshot-contract.ts`. A failure on Postgres after the merge would show up as a `PluginFailed` event or a red run of the integration half on `main`. Nothing inside the pass can produce it.
