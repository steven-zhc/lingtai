# #1511: one spend read for a PR's tickets, shared by the page and the description

## Where the change goes

The whole change is in `apps/board/src/lib/prs.ts`, plus a test in `apps/board/unit/request-reads.test.ts`. The projector already serves the batch read, so it is not touched: Postgres builds `ticket = any($1::text[])` at `packages/projector/src/postgres.ts:534–537`, and SQLite builds `ticket in (?, …)` at `packages/projector/src/sqlite.ts:796–799`.

Split `ticketFacts` (`prs.ts:283–318`) into three parts:

1. **A pure function from rows to per-ticket spend.** Its input is `rows: SpendRow[] | null` and the list of tickets. Group the rows by `row.ticket`, which the projection stores as `ticketStream(project, ticket)` (see the comment at `prs.ts:294`). Then apply today's rule from `prs.ts:299–303` to each group:
   - drop rows whose `streamId` starts with `pr-`;
   - a ticket with no rows is `null`;
   - a ticket with any row whose `costUsd` is null is `null`;
   - otherwise the spend is the sum.
   
   When `rows === null`, every ticket is `null`. Make it a function so the unit test can check the edges without a store.
2. **A shared read of the rows** (described in the next section).
3. **`ticketFacts` itself**, which keeps the per-ticket `getIssue` reads exactly as `prs.ts:288–297` has them (the same `ISSUE_READ_BUDGET` and `orElseSucceed(null)`). It joins each ticket's open state with the spend from part 1. It now needs `n` so that it can reach the shared read.

The two callers, `prs.ts:381` (the page) and `prs.ts:454` (`readGeneratedBody`), pass `n`. Neither caller does anything else differently.

## The decision the ticket leaves open: how two runs share one read

The page and the generated description run as **two separate root runs**: `Effect.runPromise` at `prs.ts:354` and again at `prs.ts:450`. The second one is called from the streamed `PrGeneratedStream` (`pr-host-stream.tsx:39`). Because of this, `Effect.cached`, a `Ref`, or any other sharing inside Effect cannot cover both. The sharing has to be a promise kept by `react`'s `cache()` for the request.

That is the rule #1420 already follows. `request-store.ts:9–11` says:

> *What is kept is the **promise**, so two callers asking at once share one in-flight read, and a read that rejected stays a rejection for the rest of the request — never an empty value.*

**The shape:**

- **A slot per `(project, n)`.** Use `cache((project: string, n: number) => ({ rows: undefined as Promise<SpendRow[]> | undefined }))`. Key it by those two primitives, never by the array of tickets. `cache()` compares arguments by identity, so an array key would miss every time; `request-reads.ts:2–3` warns about the same thing for `ProjectState`.
- **The Effect that reads through the slot.** Inside an `Effect.gen`:
  - When `tickets` is empty, return `[]` without touching the slot.
  - When the slot is empty, fill it with `Effect.runPromiseWith(yield* Effect.context())(tracedEffect('spend.read', readSpendEffect({ project, ticket: streams })))`.
  - Then `yield* Effect.tryPromise(() => slot.rows)`.
  - Map a failure to `null` once, at this point, so a rejected read becomes "every ticket null" rather than an exception.

**Why `runPromiseWith` and not `runPromise`.** The ticket allows no new `Effect.run*`. `runPromiseWith` with the caller's context is the run the ratchet does not count (`packages/domain/unit/effect-ratchet.test.ts:106–117`: *"`Effect.runPromiseWith(services)` … carry the caller's services, its tracer among them … and are not counted"*). It is also what `packages/conductor/src/schedule.ts:182–186` does for the same reason. It carries the first caller's tracer and `ApiContext`, so the one `spend.read` span lands in the request's trace.

Do not copy `prsOf` (`prs.ts:108–117`), which is `cache(() => Effect.runPromise(...))`. That would be the new run the ticket forbids. Do not use the `readSpend` promise face (`packages/projector/src/spend.ts:393`) either: it runs with no tracer, and the read would drop out of the trace that is the evidence for this ticket. `apps/board` has no entry in `effect-ratchet.baseline.json`, so the ratchet cannot catch either mistake here; review has to.

**Why `(project, n)` is a safe key although the read needs the tickets.** Both callers take `pr.tickets` from `reducePr(yield* readPrEvents(project, n, requestStore()))`. `requestStore()` keeps each stream's read for the request, so both callers fold the same events and pass the same list. Whichever caller fills the slot first decides the streams.

**Where `tracedEffect` goes.** It wraps the read **inside** the slot, not each caller's wait. Then one request shows one `spend.read` span for the tickets and one for `spendByPr` (`prs.ts:142`). That is the 2 the ticket asks for, and the same count the witness measured as 73.

## Edges the code has to handle

- **No tickets means no read, and the guard belongs in the board, not the store.** On SQLite an empty `ticket` array builds `ticket in ()`, which is not valid SQL. `stream` is guarded with `0 = 1` (`sqlite.ts:807`), but `ticket` is not. Do not hand an empty list to `readSpendEffect`.
- **The page's total when the read fails.** With every ticket `null`, `prs.ts:387` already gives `tickets = null` and `prs.ts:388` gives `spend = null`. No change is needed there. Keep `spendParts.pr` showing the PR's own spend: that is a separate read and is not presented as the sum.
- **Server actions.** Nothing reaches `ticketFacts` from an action: its only callers are `prs.ts:381` and `prs.ts:454`, and `readGeneratedBody`'s only caller is `pr-host-stream.tsx:39`. Say in the slot's doc comment that pages read through it and actions never do, quoting `request-store.ts:15–16`.

## Tests (all unit, all in `pnpm test`)

`apps/board/unit/request-reads.test.ts` already provides what these tests need:

- a `cache` mock per `AsyncLocalStorage` run, one run being one request (`:29–46`);
- `readSpendEffect` routed to `h.spend` (`:94–97`);
- the same style for `spendByPr` (`:217–`).

Add three kinds of test:

- **One request, one read.** Record a PR with 36 tickets. Inside one `h.renders.run(new Map(), …)`, call `readPrDetail(project, n)` and `readGeneratedBody(project, n)`. Assert that `h.spend` received one call whose `ticket` holds the 36 `ticketStream`s, plus the PR's own call with `stream`. That is 2 calls. Outside a run, the same two calls make 2 ticket reads, because `cache` keeps nothing there.
- **A shared failure.** With `h.spend` failing, both callers show every ticket's spend as `null`, and `h.spend` is still called once for the tickets.
- **The pure grouping function.** Feed it rows directly:
  - a ticket with no rows gives `null`;
  - one row with null `costUsd` gives `null`;
  - a `pr-` row is not counted;
  - rows of two tickets sum separately;
  - `null` rows give all tickets `null`.

None of this needs `pnpm test:integration`. The per-store batch query is already covered by the projector's own tests.

What settles the change in production is a trace, not the log. In Jaeger, a `/p/<project>/pr/<n>` request shows two `spend.read` spans where trace `932461439da893cc28c9103c14cfd70b` showed 73. Its projection acquisitions (`withStoreEffect`, `spend.ts:389`) drop by the same amount.
