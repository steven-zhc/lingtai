# #1394: shape

## Where it goes

**`backfillDraft` goes in `packages/project/src/pr.ts`, and it reads the PR streams once.** Call `listPrs` one time and use that list twice:

- Pass it to `readPrDraft` as its fifth argument. The parameter already exists: `readDraftOn`'s `prs` is documented as *"The PRs, where the caller has read them already: the stream is then not read a second time"* (`pr.ts:524-525`).
- Pass it to the module-private `draftOf` (`pr.ts:119-126`) to get the target.

Do not call the exported `draftTarget` (`pr.ts:112`). It runs `listPrs` again, so `wanted` and `have` could come from two different reads.

`have` is the highest PR's `draft` when `target.state !== null`, and `[]` otherwise. That is the same choice `draftBatchFor` makes at `pr.ts:141-142`.

**One state serves every event in the batch.** `addDraftTicket` checks only `state.status` (`packages/domain/src/pr.ts:618`: `if (state.status !== null && state.status !== 'draft' && state.status !== 'requested') return null`). Adding a ticket never changes the status, so the state read once is valid for each event. You do not need to fold events between them.

A `null` from `addDraftTicket` is a defect, which matches `draftBatchFor`'s `Effect.die` at `pr.ts:144-145`. `draftOf` never names a PR in a status that refuses.

**The append:** `store.append(prStream(project, target.n), target.version, events)`, wrapped in `Effect.tryPromise`.

- `target.version` is `0` when the target is the next number, and the append creates that stream.
- The reducer takes `n` and `project` from the stream id on the first `PrDraftTicketAdded` (`domain/src/pr.ts:241-249`), so no other event is needed to open a PR stream.
- On `ConcurrencyError` (`packages/event-store/src/event-store.ts:62`), read again from `listPrs` and decide again. **My decision:** allow at most three attempts, then fail that project's backfill with a log line. Nothing should be able to loop forever at the start.

## How the reconcile reaches it

`reconcileEffect` lives in `packages/daemon`. The recipe and candidates it needs are built in `apps/cli`:

- `recipeOf`: `apps/cli/src/pr-ports.ts:69-74`
- `candidates`: `pr-ports.ts:255-259`

Both are inner closures of `livePrPorts`. That function is called only at `daemon.ts:679`, after the reconcile at `:535`, and it takes `locked`, which does not exist until `:614`.

**Decision:** pull those two closures out into one exported function in `pr-ports.ts`, for example `draftPorts(store)`, returning `{ recipe, candidates }`. `livePrPorts` spreads its result, and `daemon.ts:535` passes it into a new optional field on `ReconcileOptions`, for example `draft?: { recipe; candidates }`.

That optional field follows the pattern of `github`. Its doc comment says *"Omit it and that check is skipped rather than guessed at"* (`reconcile.ts:293-297`). With one source for both ports, the backfill and the submit compute the draft from the same inputs.

Do not add `apps/cli` as a dependency of the daemon package. It cannot have one: `packages/daemon/package.json` depends on `@lingtai/project` but not on the CLI.

**Where the step sits in `reconcileEffect`:** right after `recordOwedLandingsEffect` (`reconcile.ts:806-813`), and before the read-then-act scans.

- **Why after:** that step writes the `TicketLanded`s a dead conductor owed (#1397). Its writer is `landTicketEffect` (`owed-landings.ts:89`), not the landing #1392 changed, so those tickets reach their draft stream only through this backfill, and only if their landing is already on the log when it reads.
- **Why before the `findings` block:** the backfill writes to PR streams, not to findings. Keep it out of `Reconciled`. A step that appended nothing for a project must not leave a `Reconciled` entry, per the header's warning against an empty one every startup (`reconcile.ts:42`).

**Mechanics of the step:**

- Loop over `options.projects` the way `recordOwedLandingsEffect` does (`owed-landings.ts:103-108`): `catchCause(unlessInterrupted(...))` around each project. A failure is logged as `could not backfill the draft of <project>: …`, and the loop moves on to the next project.
- Read the recipe through the port. A project whose recipe read fails is skipped with that same log line.
- Under `options.dryRun`, skip the step entirely. Nothing calls `reconcileEffect` except `daemon.ts:535` today, but `dryRun` promises no writes (`reconcile.ts:232-236`).

## Undecided in the ticket: decided here

**Candidates come from `task_view`, and it may lag at the start.** `candidates` is `readTasksEffect` (`pr-ports.ts:256`), a projection that the daemon itself catches up. A ticket landed but not yet projected is missing from `wanted`. It is then not backfilled at this start and is picked up at the next one.

That gap only ever under-adds, so I accept it rather than gating on projection catch-up. Say so in the function's comment.

What would settle whether this happens on this machine: compare the `task_view` checkpoint against the `seq` of the newest `TicketLanded` at `ConductorStarted`.

**What "written" means in the log line.** Log `backfilled N draft ticket(s) of <project>` only when `N > 0`, per the ticket. A project that appends nothing logs nothing.

## Tests

The six cases in `## Done when` all run in the unit half:

- **`packages/project/unit/pr.test.ts`:** the five `backfillDraft` cases on `createMemoryEventStore()`. For the `in-review` case, assert that the PR stream at `n+1` was created at version 0.
- **`packages/daemon/unit/`:** the reconcile case. Pass a stub `draft` port and two projects, one solo and one team. Assert that the port's `recipe` is asked for both and that an append happens only on the team project's `pr-` stream. Also assert that omitting `draft` skips the step without failing.

None of this needs `pnpm test:integration`.

**The effect ratchet:** every new function is an `Effect.gen` or a wrapped promise. There is no `async` and no `Effect.run*`, so `effect-ratchet.baseline.json` does not move.

This contradicts no ADR. It writes what ADR 0131 §1 (as #1374 edited it) already says the stream holds.
