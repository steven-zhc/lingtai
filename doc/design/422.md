# #422: the shape of `writeSection` and `editBodyAndRequeue`

## Where it goes

- **`packages/conductor/src/edit-body.ts`** (new) holds `writeSection`, `editBodyAndRequeue`, and `editBodyAndRequeueHolding`. Export them from `packages/conductor/src/index.ts`, next to `BodyChanged` (`index.ts:121`).
- **`tell.ts`** changes in three places. `IssueChannel.getIssue` returns `{ labels; body: string }` (`tell.ts:45`). The body variant of `IssueChange` gains `ifUnchanged?: string` (`:97`), and the body case passes it on (`:167-168`). `tellGitHub` returns what it recorded.
- **`discuss.ts`** moves its `ticket` branch (`:707-724`) onto `writeSection`.
- **Tests:** a new `packages/conductor/unit/edit-body.test.ts`, plus a case in the existing `packages/conductor/unit/discuss.test.ts`. The other discuss tests are in `integration/discuss.test.ts`, which nobody runs during a ticket, so put the discussion case in the unit file.

No change to `domain`, `events.ts` or the fold. `ticket.ts:383-393` already sends `EditBodyAndRequeue` to the backlog.

## What `tellGitHub` returns: the error, not just the event name

The ticket asks `tellGitHub` to return whether it recorded `IssueUpdated` or `IssueUpdateFailed`. Only the event name is not enough. `writeSection` has to tell a `BodyChanged` (retry) from any other failure (stop), and `tellGitHub` catches the error at `tell.ts:174` and keeps only its `.message`. So return:

```ts
type Told =
  | { recorded: 'IssueUpdated' }
  | { recorded: 'IssueUpdateFailed'; error: unknown }
  | { recorded: null }          // the ticketId did not parse; nothing was tried (tell.ts:144)
```

`writeSection` tests `error instanceof BodyChanged` (`ticket-store.ts:38` re-exports the class). The other caller, `tellGitHubAbout` (`tell.ts:369`), ignores the return value and needs no change.

## How to tell that the section landed

Do not compare the read-back body with `next`. A person's edit in the meantime would make them differ even though the section landed. Check that **the section itself** is in the body:

- Get the exact text with `upsertSection('', key, text).trim()`. That is the same string `upsertSection` puts in (`body-section.ts:87`), so you need no second copy of the format and no new export.
- Replace `\r\n` with `\n` in the body you read before `includes`. A body a person edited in GitHub's web editor can come back with CRLF line endings, and a CRLF body would then never match.

## The loop in `writeSection`

`writeSection({ store, github, ticketId, key, text })` returns `{ written: true } | { written: false; detail: string }` and never throws. Each try:

1. **Read the body.** If `getIssue` throws, return `written: false`. Nothing was attempted, so append nothing.
2. **Compose `next = upsertSection(body, key, text)`.** This happens **before any write**. If it throws (text carries a marker, `:85`; an unclosed or nested marker in the body, `:97`, `:105`), return `written: false` with its message. No `IssueUpdateFailed` is appended, because nothing was sent to GitHub. This is "refuse before you write" applied to the body as well as the wait.
3. **Write:** `tellGitHub({ change: { kind: 'body', body: next, ifUnchanged: body } })`.
4. **Read back.** Then, depending on what the read finds:

| The read-back finds | and the write | then |
|---|---|---|
| the section | recorded `IssueUpdated` | `written: true` |
| the section | recorded `IssueUpdateFailed` | append `IssueUpdated{ change: 'body', detail: 'found on read-back after: <error message>' }`, then `written: true` |
| no section | failed with `BodyChanged` | try again from step 1 |
| no section | recorded `IssueUpdated` (a later edit removed it) | try again from step 1 |
| no section | failed with any other error | stop: `written: false` |
| — | the read-back itself throws | stop: `written: false` with the original outcome. Do not retry without knowing what the first write did |

Two tries in all. The extra `IssueUpdated` needs no schema change, because `detail` is a free string (`events.ts:1424`). `record` in `tell.ts` is private, so either export it or append through `parsePayload('IssueUpdated', …)`. Get `project` and `issue` from `parseTicketStream`, as `split` does (`tell.ts:120`).

## `editBodyAndRequeue`

Its options are `{ project, issue, waitId, text, by, note?, github: IssueChannel, store? }`. The wrapper has the same shape as `requeue` (`approve.ts:332-342`): `deciding(ticketId, busy, () => editBodyAndRequeueHolding(...))`.

The holding function takes the lock once, so it calls `resolveWaitHolding` (`resolve-wait.ts:168`) and **never `resolveWait`**. `resolveWait` takes the same lock again (`:150`). As `resolve-wait.ts:162-166` notes, the wrapper reaches the filesystem, so the unit tests target `editBodyAndRequeueHolding` and `deciding` is not tested here.

Inside the holding function, in this order:

1. **Refuse before writing.** Run `reduceTicket(await store.read(ticketId))`. Refuse unless `lifecycle.status === 'blocked'`, `lifecycle.waitId === waitId`, and `allowedResolutions(lifecycle.reason)` includes `'EditBodyAndRequeue'`. Word the refusals like `resolve-wait.ts:196-212` so the board, in #520, can show one message for both refusal paths.
2. **Write the section.** Call `writeSection` with `key = \`${ticketId}/${waitId}\``. If it returns `written: false`, return `{ ok: false, written: false, detail }` and append no `WaitResolved`.
3. **Resolve.** Call `resolveWaitHolding({ waitId, resolution: { _tag: 'EditBodyAndRequeue' }, by, note, store }, ticketId)`. If it refuses (in practice `stale`, or `not-blocked` after a concurrent decision), re-read the ticket. Return `{ ok: false, written: true, detail }`, where `detail` gives the refusal and the lifecycle status now. For example: *"the answer is in the body; the ticket is already `backlog`, and the next pass reads it."*

Running it again for the same wait is safe. The section is rewritten in place, and the second resolve is refused as `not-blocked`. That double run is the "running it twice leaves one section" test.

## Test seams

- Use `createMemoryEventStore()` and `memoryTickets()` (`packages/conductor/test/memory-tickets.ts`). Its `updateBody` already honours `ifUnchanged` (`:122-124`).
- Each failure case is a small wrapper around it:
  - **Lands but throws:** call through to `updateBody`, then throw `new Error('socket hang up')`.
  - **Fails twice:** throw a plain `Error` before calling through.
  - **`BodyChanged` on the first write:** inside the first `updateBody` call, change `t.body` through the same tracker before delegating. The `ifUnchanged` check refuses, and the retry has to keep that edit.
- For a blocked ticket with a `waitId`, reuse the fixtures in `unit/resolve-wait.test.ts` rather than building new events. They already build `MergeRefused` and offered-reason waits.
