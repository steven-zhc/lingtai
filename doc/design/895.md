## Design note for #895: `/landed`

### Where it goes

- `apps/board/src/lib/landed.ts`: the loader, plus pure functions for the URL, the cursor, days, totals and cost text. The page and its tests work from these functions. Nothing in this file renders.
- `apps/board/src/app/landed/page.tsx`: the server page, plus a small client component for the "load more as the reader nears the end" behaviour.
- `packages/projector/src/read-landed.ts`: a `readLanded(options)` wrapper, exported from `packages/projector/src/index.ts` beside `readTicketReport` (`index.ts:79`). It has the same shape as `read-ticket-report.ts:14-18`. The board cannot call #894's `landed()` today: it is a method on `ProjectionStore` (`store.ts:366`), and there is no top-level read for it like `readBacklog` (`backlog.ts:296`).
- `apps/board/src/app/page.tsx`: the column heading. The ticket's `:889-890` is out of date. The heading is now `page.tsx:865-873`, which renders `<span>{col.label}</span>` for every column.

### Decision 1: the kind filter goes into the store query, not the loader

`TicketReportLandedQuery` (`store.ts:245-252`) narrows by `project` and `before` only. If the loader filtered `?kind=` itself, a filtered page would hold fewer than twenty rows, and the cursor rules would get harder. So:

- Add `kind?: string` to `TicketReportLandedQuery`.
- Add it to both implementations as one more `where` clause, beside `project`: `sqlite.ts:771-781` and `postgres.ts:453-462`.
- `readLanded` passes it through.

How it is checked:
- Unit: extend `packages/projector/unit/ticket-report-read.test.ts` with an in-memory SQLite case (`openSqliteProjections(':memory:')`, as that file already does). Cover the kind filter, the cursor's strict `<`, and ties broken by `ticket desc`.
- Postgres: no test runs this query. The file's own header says so: *"its query is not run by any test: `test/contract.ts` has no `ticketReport` case"*. Keep the Postgres clause identical in shape to `project`'s, and say in the commit that only the SQLite twin is under test.

What counts as a valid `kind`:
- It must be one of the recipe's kinds. Anything else is a malformed `kind` and is ignored, as the ticket says.
- The filter offers no *unclassified* chip.

### Decision 2: the cursor, and how *Earlier* knows to appear

- The URL form is `?before=<ISO outcome_at>,<ticket>`, URL-encoded.
- Parse it by splitting on the **first** comma. Ticket ids contain hyphens, not commas.
- Reject it (show the first page) if the date is not a real date or the ticket part is empty.
- Read `limit: 21` and show 20. *Earlier* appears only when a 21st row came back. A stale cursor then yields an empty page with no link, without a separate check.
- The *Earlier* href is the 20th row's `(outcomeAt, ticket)`, carrying `?project=` and `?kind=`.

Unit test: parsing round-trips, and both a garbage value and a non-date fall back to `null`.

### Decision 3: colour comes from the recipe's kinds, through `kindSeries` unchanged

- Get the kinds the way the board already does, with nothing asked of GitHub: `queueFilters(projects)` returns `kindOrder` (`board.ts:846-847, 857, 878`). Its doc says *"It asks GitHub nothing (#884). The recipe is a local file"* (`board.ts:824`).
- Hand that list to `kindSeries` (`report.ts:245-260`).
- **Do not "fix" `kindSeries` to keep the order it is given.** It re-sorts alphabetically through `sortKinds` (`report.ts:105-107, 249`). With the recipe's full list as input, the slot each kind gets is still stable across pages and filters, which is what 0123 §7 needs. Changing it would recolour `/report`.
- Kinds past the fourth, and `null`, get `OTHER` (`var(--muted)`).
- The marker is the series colour at about half strength. Use `color-mix(in srgb, <colour> 50%, transparent)` so the same token works in light and dark.
- `/report` itself passes the page's own kinds (`report/page.tsx:73`), not the recipe's. So the two pages can disagree for a kind `/report` has no rows for. **That is not this ticket.** Leave it alone and mention it in the commit as a follow-up.

### Decision 4: cost and the currency chip come from `ticket_report` alone

- A ticket's cost is `ticketMoney(row)` (`packages/conductor/src/report.ts:227-237`).
- It reads *cost unknown* when `reportedCents + estimatedCents === 0 && unknown > 0`. Otherwise it is `moneyText` (`report.ts:204-210`), which already refuses `$0.00` when something is unknown.
- Day totals and header totals are sums of `Money` over **the rows shown on this page**, which is what the ticket says. A day that runs across a page boundary therefore shows a partial count on each page. That is accepted, and the second page repeats that day's date column.
- `/landed` does not read `spend`, so its chip names `ticket_report` only.
  - `reportChip` (`report.ts:161-193`) hard-codes the pair.
  - Pull the loop body into a `projectionPart(name, lag)` helper that both use.
  - Leave `reportChip`'s output byte-for-byte unchanged; `apps/board/unit/report-lib.test.ts` holds it.
- Take the lag before the rows, as `currentReport` does (`report.ts:144-145`).

### Decision 5: notes and facts, and where each comes from

| What | Source | Rule |
|---|---|---|
| A decision a person made | each `row.waits[i].resolution` (`ticket-report.ts:87-93`, filled at `:292`) that is not null | Show `moveTitle(tag)` (`resolution-copy.ts:64-66`), which already covers an unknown tag. Write it in ink, never amber. |
| Minor findings sent to the backlog | one `readBacklog({ project, taskIds })` call over the page's `row.ticket`s, with no `status` filter (taskIds are stream ids, `store.ts:230-231`) | Grouped per ticket into a `<details>` that opens to the claims. |
| *the reviewer read the first N of M* | `row.summaryClipped` | Copy the wording from `attempt-tab.tsx:54-58`. |
| Summary | `leadOf(row.summary)` (`lib/markdown.ts:100`), each half through `<DocumentBody source="summary" …>` (`app/markdown.tsx:108`) | Exactly as `attempt-tab.tsx:42-53` does. This page renders no markdown of its own. |
| Issue link | `issueUrl(owner, project, ref, ticketSources.get(project))` (`board.ts:1696-1704`); the number comes from `parseTicketStream` | No known source means no link, as that function's doc says (*"A dead link is worse than none"*). |
| Merge commit | `row.mergeCommit` | Short sha. Link it only where `issueUrl` would link. |
| Diff | `diffFiles` / `diffInsertions` / `diffDeletions` | All null means omit the squares and the numbers. |
| Attempt N | `landingAttempt` and `landingFixRounds` | |

**If the backlog read fails, the page still renders.** The cards drop their finding notes, and one line at the top of the page says the backlog could not be read.

### Decision 6: loading the next page as the reader scrolls

- Do it without a new route. A client component watches the *Earlier* link with an `IntersectionObserver`.
- When the link comes into view, it `fetch`es the link's href, pulls out `[data-landed-page]` with `DOMParser`, appends it, and swaps in the new *Earlier* link.
- The cards are static server HTML with nothing interactive inside them except native `<details>`. Copying that HTML in keeps the board's one renderer.
- If the fetch fails or returns a non-OK status, leave the link where it is. With JavaScript off, the link is the whole mechanism.

### Decision 7: the home page heading

- Pull the column header out into a small exported component, or at least an exported `landedHref(only)`, using the same expression as `page.tsx:766`'s `/report` link.
- `Page` is an async component that loads the whole board, so the unit test should render the extracted piece with `renderToStaticMarkup`, as `apps/board/unit/report-panels.test.tsx:9` does.
- Only the `landed` column's label becomes an `<a>`. This adds nothing to the bar (`the-bar.md`).

### Failures the loader handles

- A `ProjectionShapeError` from `landed()` (`sqlite.ts:793-797`, `postgres.ts:477-480`) becomes a failure line carrying the error's message, which names the rebuild. This follows how `report/page.tsx:83-86` handles `failure`.
- A missing table reads as no rows (`postgres.ts:475`), which gives *nothing has landed yet*.

### What runs where

- The page's unit test renders the page from fixture `TicketReportRow`s. That needs a seam: the page's body takes the loaded data as props, and `page.tsx` only loads.
- No part of this needs `pnpm test:integration`. The one claim no test makes is the Postgres `kind` clause; Decision 1 says how to cover it.
