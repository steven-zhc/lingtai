# Design: #618 — `lingtai status` through `@effect/cli`, in sections, with `--json`

## The ticket says "commands", but it means one

The ticket's plural ("each read command", "migrate the commands") is left over from a template. The only command it names is `status`, so this change migrates `status` and nothing else. `MIGRATED_COMMANDS` becomes `['version', 'status']` (`migrated.ts:9`).

## Split `status()` into read, render and JSON

Today `status()` reads and prints in the same loop through a `log` callback (`status.ts:90-364`). Because of that, its output can't be unit-tested. `status.test.ts:5-8` says so: *"`status()` itself calls `selectRunnable` and `readTasks`, which reach the log, so it is not unit-reachable"*. The ticket's "no fact lost" and "a test pinning its shape" both need a unit test, so split the file the way #616 split `versionFacts`/`versionLine`:

- **`readStatus(options, reading): Promise<StatusReport>`** keeps every read `status()` does today, in the same order, but prints nothing. `StatusReport` is `{ projects: ProjectStatus[] }` or a "no project" answer. A `ProjectStatus` holds:
  - the typed values the old lines were built from: name, base, the `ProjectFilter`, source name, eligible count, the `found.skipped` list and `passedOver`'s sentence;
  - `dependenciesUnread` (a `string | null`, `discover.ts:299`), or the offer error;
  - `runnable` with restarts, the `elsewhere` counts, `askedBefore`;
  - the rows: each with its `wait` words, `held` / `unoffered`, and the arm line.

  Compute `now`, `heldUntil`, `waitWords`, `describeWait` and `armLine` here, so the renderer stays pure.
- **`renderStatus(report, { all, columns }): string[]`** uses `output.ts`'s `heading` / `section` / `keyValues` / `table` / `symbol.signal` only.
- **`statusJson(report): Record<string, unknown>`** gives the body that `printJson('status', …)` wraps.

`status()` can stay as a thin `readStatus` → `renderStatus` → `log` wrapper for `ask.test.ts` and `status-preview.test.ts` (see below), or those two can be moved onto `readStatus`. Either is fine; pick one.

## The Project section keeps `describeFilter`'s words, through a facts function

`describeFilter` is shared with the daemon's startup block (`lingtai.ts:509`). `status.ts:110-115` gives the reason: *"said by the same function `lingtai daemon` prints at startup, so the two cannot disagree (#76)"*. Its output is pinned byte-for-byte (`conductor/unit/filter.test.ts:507`). So:

- Don't hand-build the Project key/values in `status.ts`.
- Add `filterFacts(filter): readonly (readonly [string, string])[]` to `packages/conductor/src/filter.ts`, and rebuild `describeFilter` from it. The keys are the labels it prints today: `recipe` (hash + `from <ref>`), `picks up`, `excludes`, `assignee`, `a pass`, `retries`.
- For `!filter.ok`, the facts are `recipe: INVALID — <problem>` and `nothing will be taken from this project`.
- `filter.test.ts` stays green unchanged. That is the proof that the daemon's text did not move.

## Layout (0121 §1, and its Example at `0121…md:145-163`)

```
<project>

Project
  base       main
  recipe     3f2a91c9d04e from main
  picks up   bug > tech-debt > …   (in priority order)
  …
Queue  3 runnable — 3 eligible from GitHub, 1 passed over — agent:hold 1
  (GitHub reported no issue dependencies …)        ← only when dependenciesUnread
  ID     KIND     TITLE                 STATE
  #612   bug      …                     backing off — runnable in 32m
Waiting on you
  ● #609  <title> — <waitWords.line, oneLine'd>
next: lingtai answer <project> --issue 609 "<choice>"
```

**The queue heading line keeps the word `runnable`, and `eligible` stays its own number.** #54 is why they must not merge. `status.ts:146-151`: *"`eligible`, not `runnable`. They are answers to different questions"*. The `elsewhere` counts (`1 running, 2 landed`) stay on that heading line. The exception is `waiting on you`: it is now the Waiting section, so it isn't counted there as well.

**Waiting on you** has one ● line for every row whose `wait != null`, every time, not only under `--all`.
- Old behaviour:
  - `OwnQuestion` waits were listed (`status.ts:228-237`).
  - Every other wait was only a count, `N waiting on you`.
  - The `describeWaitLines` detail appeared only under `--all` (`:350-360`).
- New behaviour:
  - The ● line carries `waitWords(...).line` through `oneLine`. 0121 §4 keeps `oneLine`.
  - Under `--all`, the `describeWaitLines` lines and the *"(the failure itself is on the log, and on the card)"* line follow each ● line, indented.
- Amber is ● and nothing else (0121 §2). The `[waiting for your answer]` chip loses its `stateInk` amber because the ● carries it now. **Keep the words `waiting for your answer` on the ● line**, because `apps/cli/integration/ask.test.ts:88` asserts them.

**`next:`** appears only where the old output named a command. That is the `OwnQuestion` case, `lingtai answer <name> --issue <n> "<choice>"` (`status.ts:229`). Don't invent a command for the other waits.

**The table** is `ID / KIND / TITLE / STATE`. STATE carries:
- `[backing off …]`;
- `[not offered]`;
- `describeWait`'s words, or the state;
- the arm line (`armLine`, muted). It goes either as a second line under the row or as a column; a column is wide, so a second line in the narrow fallback is acceptable.

`columns` is `process.stdout.columns`. It is `undefined` when redirected, which means the output is never truncated (`output.ts:84-86`).

The no-project answer stays one line and exits 0 (0121 §1, `status.ts:97-104`).

## `--json` shape

`{ version: 1, command: "status", projects: [ … ] }`. Each project has:

- `project`, `base` (null when unrecorded)
- `filter`: `{ ok: true, recipe: <full configHash>, ref, kinds, exclude }` or `{ ok: false, problem }`
- `source`: `"GitHub" | "the ticket table"`
- `eligible`: a number, or `null` when the source was not asked
- `offerError`: string or null
- `passedOver`: `[{ ref, reason }]` from `found.skipped`
- `dependenciesUnread`: **string or null**, which is the real type. 0121's example shows `false`, but that example is illustration and must not change the type.
- `runnable`: `[{ taskId, ref, kind, title, restarts }]`, in `selectRunnable`'s order
- `byState`: `{ <projection state>: [{ taskId, ref, kind, title }] }`. Use the projection's own `state` values, not the `NAMES` labels, so `verifying` stays `verifying`.
- `waiting`: `[{ taskId, ref, reason: wait.reason._tag, line, needs, asked }]`

Without `--all`, `byState` still carries the counts' rows. JSON has no reason to hide what the text counts.

Write a **`statusJson` unit test that pins the whole shape with `toEqual`** on a hand-built `StatusReport` that covers:
- a valid filter and an invalid one;
- an offer that failed;
- a passed-over item;
- `dependenciesUnread`;
- a backing-off row and an unoffered row;
- a restart arm;
- an `OwnQuestion` wait and one other wait.

Use the same fixture in a `renderStatus` test that greps for each fact the old `log(...)` calls printed. That test is the "no fact lost" list, and the PR names each fact. Run it once under `NO_COLOR=1` (no `\u001b`) and once under `FORCE_COLOR=1`, and check alignment (`output.ts` already measures visible width).

## Errors under `--json`

`runCli` cannot carry a runtime failure as it stands:
- `Effect.as(0)` (`cli.ts:66`) discards the handler's exit code.
- `catchAllCause` maps every failure to `1` (`cli.ts:67`). Under `--json`, `cli.ts:70-72` then prints `code: "usage"`.

So a `status` whose `loadProjects()` throws (no store configured, a dropped connection) would be reported as a *usage* error. Fix it this way:

- Let a handler return its exit code; for example, the handler writes into a `let code` that `runCli` returns.
- The `status` handler catches its own failure:
  - Under `--json`: `printJsonError('status', 'unavailable', message)`.
  - Otherwise: the message on stderr plus `(LINGTAI_DEBUG=1 for the stack)`, which matches what `lingtai.ts:1350-1356` prints today.
- `"usage"` stays reserved for parse errors.

## Routing, loading and help

- **Import `status.ts` dynamically inside the `status` handler in `cli.ts`**, never at the top. A static import would make `lingtai version`, which `upgrade` spawns (`doc/design/616.md`, *"must not change by a byte"*), load `@lingtai/conductor`, `@lingtai/projector` and the store's code. `entry.ts:18-19` gives the same reasoning.
- **`status --help` stays on the definitions (the `help` route), not `@effect/cli`'s generated help.** `migrated.test.ts` pins `['status', '--help'] → help` (`doc/design/617.md:124`). 0121 §6 makes the definition the one source of help. Today `routeOf` checks migrated commands first (`migrated.ts:18`), so adding `status` there would flip that row.
  - Order `routeOf` so that `--help` / `-h` goes to `help` for every migrated command except `version`. #617 deliberately left `version`'s help to `@effect/cli` (`doc/design/617.md:41,109`).
  - Keep both rows in `migrated.test.ts`, and add `['status'] → effect` and `['status', 'lingtai', '--json'] → effect`.
- Update the `status` definition's `usage` (`commands.ts:98-102`) to `lingtai status [<project>] [--all] [--json] [--no-color]`. Give the command `Command.withDescription(definitionOf('status').task)`, as `version` already has (`cli.ts:25`).
- **Positional first must still parse.** `lingtai status lingtai --all` is the definition's own example (`commands.ts:103`). The old `parseFlags` takes flags anywhere (`add.ts:48-73`). Test both `status lingtai --all` and `status --all lingtai` through `runCli`, with the handler's reading stubbed, before relying on `@effect/cli`'s ordering.
- Unknown flags were silently ignored by `parseFlags`, and are now refused. `doc/operating.md:705-706` documents a `status --refresh` that no code reads. Remove it from that doc rather than accepting the flag.
- Delete `case 'status'` from `lingtai.ts:1212-1215`, along with the now-unused import at `lingtai.ts:91`. No service starts `lingtai.ts` with `status`, unlike `version`'s case, which stays.

## Everything that reads the old text moves in this change

- **`apps/cli/integration/status-preview.test.ts:145-160`** greps `/^ {4}#\d/`, `queue:` and `from GitHub:` out of the prose. Rewrite it against `readStatus`:
  - `runnable.map(r => r.ref)` equals the preview's order;
  - `runnable.length` is the count;
  - `passedOver`'s sentence equals `preview.passedOver`.

  This is integration, so it cannot run inside the pass. The unit claim that stands in for it is the `statusJson`/`renderStatus` fixture test, plus `typecheck` on the rewritten file. Say this in the PR.
- **`apps/cli/integration/ask.test.ts:86-91`** asserts the question text and `waiting for your answer`, and asserts no `\d+ waiting on you`. All three still hold under the layout above. Check them by reading, because this file cannot run in the pass either.
- **`doc/operating.md:700-760`**: replace the sample blocks with the new layout and add a `--json` example. The ticket's "monitors read `queue:`" refers to readers outside this repository; a search of `doc`, `scripts`, `.claude` and `CLAUDE.md` finds no in-repo reader of `queue:`. So the PR, and that section of `operating.md`, must give the replacement explicitly: `lingtai status --json | jq '.projects[] | {project, runnable: (.runnable | length)}'`.

Finish with `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test`.
