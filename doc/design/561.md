# #561: reconciling a split against GitHub

## Start fresh, but keep the adapter

Two attempts are on `agent/561-attempt-1` and `agent/561`, and neither was merged. Both reviews failed on the same machinery: **withdrawing duplicates**. That meant closing an extra child, unlinking it as a sub-issue and as a blocker, and then hunting the "stray links" those withdrawals left behind. Each round patched one more corner of it. The judge's last comment on #561 said so: *"the prior rounds have already patched this same reconciliation logic repeatedly. A person should decide whether another patch or a fresh approach is w…"*.

This design removes that machinery. **Lingtai never closes, unlinks or withdraws an issue during a split.** The design makes a duplicate structurally unlikely. If one appears anyway, it is reported and it blocks completion, and a person closes it.

What you can take from `agent/561`, and what you can't:

- **Take the adapter half:** `git show agent/561:packages/github/src/client.ts` and its tests in `packages/github/unit/client.test.ts`. That means `IssueId` (branded), `id` on `Issue` (taken from `raw.id` in `toIssue`, `client.ts:396-420` today), `LinkedIssue`, `listLinked`, `subIssues`, `addSubIssue`, `blockedBy` and `addBlockedBy`. Both POST bodies send the id as a JSON integer.
- **Drop `removeSubIssue` and `removeBlockedBy`.** Nothing calls them in this design.
- **Adding `id` to `Issue` breaks the test fakes.** Attempt 2 fixed them with one-line edits across about ten test files (`git diff HEAD agent/561 --stat` lists them).
- **Do not start from `agent/561:packages/conductor/src/split.ts`.** Its shape is the withdrawal design.

## The events

```ts
SplitStarted    { waitId, by, plan: SplitPlan, planHash }   // before the first write
SplitReconciled {                                           // after every attempt, in a finally
  waitId,
  children: { key, number, id, via: 'created' | 'adopted' }[],      // cumulative
  observed: { children: string[], subIssues: string[], blockedBy: Dependency[] },  // what this attempt's GETs confirmed
  strays:   { key, number }[],     // open issues carrying this plan's marker for a key, other than its child
  failure:  string | null,
}
```

### Identity is what the log recorded

This is the operator's ruling of 2026-10-24. `splitIdentitiesOf(events, waitId)` folds every `SplitReconciled` that comes after the governing `SplitStarted`. For each key, the first `{number, id}` recorded wins, permanently. A later attempt that cannot see that child erases nothing.

A recorded key is never:

- searched for by marker,
- adopted, or
- created.

Instead it is read back with `getIssue(number)`. It counts as observed only when the returned `id` equals the recorded one. A 404, a throw, or a different id goes into `failure`, and the child stays owed, but it is never re-created. Done-when #1 pins exactly this.

### The marker is a hint, used for unrecorded keys only

The marker is `<!-- lingtai:split <waitId> <planHash> <key> -->`. Do not reuse `keyMarker`'s `lingtai:finding`: the backlog's `settle` would treat a split child as a finding's duplicate.

`waitId` and `planHash` are both in the marker so that no child is adopted under a wait or a plan it was not made for.

### The plan is fixed once anything exists

A retry reconciles the plan in the governing `SplitStarted`, not the plan in the new command:

- **A different plan is accepted** (as a new `SplitStarted`) only while `splitIdentitiesOf` is empty.
- **Otherwise it is refused** as `split-in-progress`, and the refusal names the recorded children by `#number`.
- **Compare plans structurally:** keys, titles, bodies, kinds and edges.

### What is owed is derived, never stored

`splitOwed(plan, identities, observed, strays)` is a pure function in `domain/src/split.ts`. It returns:

- keys with no identity,
- identified keys the last read-back did not confirm,
- missing sub-issues,
- missing edges,
- strays,
- `complete`, which is true only when all of the above are empty.

`splitProgressOf(events, waitId)` sits beside `triageFactsOf` (`read-model.ts:108`) and follows the same pattern: the latest `SplitStarted` for the wait, the folded identities, and the latest `SplitReconciled` after it.

There is no `task_view` column and no rebuild. `reduceTicket` must not move the lifecycle on either event.

## One attempt

The `Split` branch already runs inside the `decide:<ticketId>` lock (`resolve-wait.ts:100-108`), after the `no-kinds` and `invalid-split` checks (`:262-277`). The steps:

1. **Read.**
   - Read each recorded child by number.
   - List `listIssuesSince(SplitStarted envelope time − a skew)` and pick out this plan's markers.
   - For an unrecorded key, **adopt the oldest match**, open or closed. This is the case of a create that timed out but landed.
   - For any key, an *open* match whose id is not the key's child is a stray.
   - List `subIssues(parent)`, and `blockedBy(child)` for each dependent child.
2. **Write what is missing, in order:** children, then sub-issue attachments, then blocked-by edges.
   - **Each child is created with its kind label and `agent:hold`.** Without the hold, a dependent child is claimable before its edge exists, which repeats #131 from the other direction.
   - **A child whose create returned is recorded `via: 'created'` immediately in memory**, so the `finally` appends it even if a later write throws.
   - **A blocker is always named by its `Issue.id`**, taken from the read or from the create's response. Never by `.number`.
   - **The first write that throws stops all writing for this attempt.** That includes a timeout, a 5xx, and a 422. The outcome of that write is unknown. It is neither done nor failed, and the next attempt's read in step 1 decides it.
3. **Read everything again**, in the `finally`. If a read throws, record whatever was read before it and record the failure. **Anything unread counts as owed, never as present.**
4. **Append `SplitReconciled`.**

### Why this closes the duplicate hole without any withdrawal

A key is only created when two things are true:

- the log has no identity for it, and
- a listing in the same attempt found no marker for it.

After any create whose outcome is unknown, the attempt stops before anything else is written. So two creates for one key are always separated by a listing that saw nothing.

Only links to recorded identities are ever written. A stray therefore never carries a Lingtai link, and there is nothing to unlink.

**The residue, stated in a code comment rather than engineered against:** the process dies between a 201 and the `finally`'s append, *and* a person deletes that child's marker before the next attempt. Then a second child is created. Even that second child is not silent: the first child carries no marker any more and is invisible to the listing, but the case is narrow.

**A child that is already a sub-issue of a different parent is a `failure`.** It is never moved: GitHub allows only one parent per sub-issue.

### What the `Split` branch returns

It returns `ok: false` in both outcomes:

- **`split-partial`**, when anything is owed. The detail lists the children by `#number` and every owed item, strays included ("close #N, a duplicate of `key`").
- **`split-not-resolved`**, when the split is complete. The detail says the children and links exist and are held, and that resolving the wait is #562.

Update the `split-not-built` assertion at `packages/conductor/unit/resolve-wait.test.ts:121`.

### The link port

The writes need the link verbs. Add an optional field to `ResolveWaitOptions`:

```ts
split?: Pick<GitHubClient, 'getIssue' | 'listIssuesSince' | 'createIssue' | 'subIssues' | 'addSubIssue' | 'blockedBy' | 'addBlockedBy'>
```

This mirrors how `client?` serves `Approve` (`:133-138`). When it is absent, the branch refuses with `split-unsupported` before any write. That is also the answer for a `source.tickets: db` project.

Find whatever submits a `Split` resolution in `apps/board/src/app/actions.ts`, and in `apps/cli` if anything there does, and pass it the project's `GitHubClient`. `actions.ts:172-177` shows how the board gets one.

## The page

The board's task page reads `splitProgressOf` off the stream, the way `task.ts:1748` reads triage:

- the children as `#number` links,

## Tests (unit only)

Run against `createMemoryEventStore()` and a fake GitHub with these rules:

- **Ids are not numbers:** `id = number * 1000 + 7`.
- `addSubIssue` and `addBlockedBy` reject any id the fake never issued, so passing a number as an id fails loudly.
- Bodies are editable, so a test can delete a marker.

Cases:

- **Done-when #1.** Record children a, b and c. Delete a's marker. Make c's edge fail. Retry until complete. Assert:
  - exactly three issues exist,
  - `createIssue` was never called for a,
  - a was verified by `getIssue` against its recorded id.
- **Every write position × two failure modes.** The modes are *throws before landing* and *lands, then throws*, at each child, each sub-issue and each edge. For every case, rerun until complete and assert:
  - one issue per key,
  - each edge is on the dependent and names the blocker's `id`,
  - every `SplitReconciled` before the last leaves something owed,
  - `WaitResolved` is never appended.
- **A planted stray.** An open issue carrying the marker for a recorded key keeps the split incomplete and is named. Once the fake closes it, the split completes.
- **A plan change.** It is refused once an identity exists, and accepted before any does.
- **`splitProgressOf`** reads only its own wait and only the latest attempt.

**What stands in for a real GitHub before the merge** is the path and integer-body pins in `client.test.ts`. `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` are the check.

**Whether a real run behaved is settled on the ticket's stream:** compare each `SplitReconciled.observed` and `.strays` against its `SplitStarted.plan`.
