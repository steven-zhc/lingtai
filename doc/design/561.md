# #561: reconciling a split, where the log holds each child's identity

### The defect the operator reproduced is in the code

On that branch, a child is found only by its body marker, both before writing and when reading back:

- `findChildren` (`agent/561:packages/conductor/src/split.ts:95-116`) filters `listIssuesSince` by `splitMarker(...)`.
- `readBack` (`:158-163`) rebuilds `observed.children` from `findChildren()` alone.
- Step 1 (`:184-190`) seeds `issues` from that read-back, and the create loop skips a key only when `issues.has(child.key)` (`:207`).

So a child whose marker a person deleted is missing from every later read, and it is created again. Nothing on the log stops this: the `children` recorded by the previous `SplitReconciled` are never read back in. The plan-change rule in §2 has the same hole. *"accepted only if the latest `SplitReconciled` for this wait saw no children"* is a marker-based observation too, so it would let a person replace a plan whose children exist but have lost their markers.

## The decision: identities are sticky and come from the log; observations are per attempt

Split `SplitReconciled` into two things the old `SplitObserved` mixed together:

```ts
SplitReconciled {
  waitId
  children: { key; number; id; via: 'created' | 'adopted' }[]  // every identity known after this attempt, cumulative
  observed: { children: string[]; subIssues: string[]; blockedBy: Dependency[] } // keys and edges this attempt's GETs confirmed
  failure: string | null
}
```

**`splitIdentitiesOf(events, waitId)`** is a pure fold in `read-model.ts`, placed beside `triageFactsOf` (`packages/domain/src/read-model.ts:108`). It reads every `SplitReconciled` for the wait after the governing `SplitStarted`. For each key, the first `{number, id}` ever recorded wins and is never dropped. A later attempt whose read-back failed, or that could not find the child, does not erase it. `reconcileSplit` takes these identities as input (the caller reads the stream; it already does so for `SplitStarted`). Every attempt writes the union back into `children`, so the latest event alone carries the full set and the fold does not depend on that.

How a key gets its identity, in this order:

1. **It is recorded.** Use it. Never search for it by marker and never create it, whatever its body now says.
2. **This attempt's `createIssue` returned.** A 2xx response carries `number` and `Issue.id`, and that is an accepted write, not an inference. Record it as `via: 'created'` in this attempt's event, even if every later step throws. A `createIssue` that *threw* records nothing.
3. **There is no recorded identity and the marker matches.** Adopt the oldest match (`via: 'adopted'`). This is the only case the marker exists for: a create that timed out but landed, or a process that died between a 201 and the append. **The marker is a hint, used only for keys the log has nothing for.**

What remains: if the process dies after a 201 *and* the person removes the marker before the next attempt, a second child can appear. Say that in the module comment. Do not append one event per create to close the window. The operator ruled that the identity is "the one `SplitReconciled` recorded", and one event per attempt is that.

### Read-back of a recorded child is by number, checked by id

`getIssue(number)` already exists (`packages/github/src/client.ts:527-529`). It returns `toIssue`, which gains `id` per §1 (the `Issue` interface is at `client.ts:100`). The child counts as verified only if the returned `id` equals the recorded one. A 404, a throw, or a different id (the issue was transferred, or its number was reused elsewhere) leaves the key **not verified**, and `failure` names the child: `recorded child #N for "key" is not readable`. The child stays owed and is **never re-created**. That wait remains `split-partial` until a person deals with it, which is the honest answer. A child a person *closed* is still the child: verified, kept, and noted in `failure` so the progress block shows it.

Sub-issue and blocked-by verification stays as it is on the branch (`readBack`'s `:165-179`, matched by id). The only change is that it iterates over the **identities** instead of the marker hits.

### Duplicates against an identity

The rule "oldest marker match wins" applies only to keys with no recorded identity. For a recorded key, every marker match whose `id` differs from the recorded `id` is a duplicate. That includes an issue *older* than the recorded one: identity beats age. Withdraw it and unlink its stray links, using the branch's `withdraw`/`strayLinks` machinery.

### `splitOwed` and the plan-change rule

- `splitOwed(plan, identities, observed)`: a child is owed when it has no identity **or** is not in `observed.children`. `complete` requires every key to be both identified and verified, plus every sub-issue and edge in `observed`. A key that has an identity but is not verified is reported as an *unverified child #N*, not as a *missing child*. That keeps the board from offering to create it.
- **A different plan is accepted only when `splitIdentitiesOf` is empty**, not when the latest observation saw no children. Otherwise refuse `split-in-progress` and name the recorded children by `#number`.

## Tests (all unit)

Keep the branch's fault matrix. Its fake already gives ids that differ from numbers. Add:

- **The operator's case.** Run 1 creates the children and records them. The fake strips the marker from child `a`'s body. Run 2 makes **zero** `createIssue` calls for `a`, and the run ends with exactly `plan.children.length` issues carrying the split's labels. Also assert this when run 1 stopped partway, after `a` was created but before its sub-issue was attached.
- **A thrown create, then a removed marker.** No identity was recorded, so adoption has nothing to go on and run 2 creates `a`. This pins the case as the documented residual window, so nobody later mistakes it for a regression.
- **A recorded child returns 404 or a different id.** It is not verified, nothing is created, `failure` names it, and the result is not complete.
- **An older marker-carrying issue for a recorded key** is withdrawn, and the recorded child is kept.
- **`splitIdentitiesOf`.** First record wins; a later event missing a key does not drop it; other waits are ignored.
- **Plan change.** Refused once any identity exists, even if no marker can be found.

The check is `pnpm typecheck` and `HOME=/nonexistent pnpm test`. Real GitHub is not exercised before the merge. What stands in for it is the endpoint paths and integer bodies pinned in `client.test.ts`, carried over from the branch. On a real run, what settles whether this worked is the ticket stream: every `SplitReconciled.children` for one `waitId` has at most one entry per key, and the issues behind those numbers are the only ones that carry the split's labels.
