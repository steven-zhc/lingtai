# #561 — reconciling a split's children and links

| Layer | File | What it gains |

| Adapter | `packages/github/src/client.ts` | `id` on `Issue`, and four verbs for links |
| Domain, pure | `packages/domain/src/split.ts`, `events.ts`, `read-model.ts` | `SplitObserved`, `splitOwed`, two events, `splitProgressOf` |

| Caller | `packages/conductor/src/resolve-wait.ts:257-283` | the `Split` branch calls `reconcileSplit`. **It still does not append `WaitResolved`.** |

`WaitResolved{Split}` belongs to #562, and so does the parent's epic label and exclusion from the queue. This ticket ends with every child and link either confirmed by a read-back from GitHub or listed as still owed, and the wait still current.

## 1. Number and id are different types

`toIssue` (`client.ts:396-420`) drops GitHub's `raw.id`. Add `id: number` to `Issue`. It is already on every listing and on the `createIssue` response, so it costs no extra request.

Do **not** add `id` to `Tickets`/`TicketDetail` (`ticket-store.ts:73-93`). `dbTickets` has no such id, and `passClientOf` (`ticket-store.ts:309-323`) would then promise one it cannot give.

Put the link verbs on `GitHubClient` and nowhere else:

```ts
/** GitHub's internal issue id — never an issue number. */
type IssueId = number & { readonly __brand: 'IssueId' }

subIssues(parent: number): Promise<{ number: number; id: IssueId }[]>   // GET  …/issues/{parent}/sub_issues, paged at 100
addSubIssue(parent: number, child: IssueId): Promise<void>              // POST …/issues/{parent}/sub_issues  { sub_issue_id }
blockedBy(issue: number): Promise<{ number: number; id: IssueId }[]>    // GET  …/issues/{issue}/dependencies/blocked_by, paged
addBlockedBy(issue: number, blocker: IssueId): Promise<void>            // POST …/issues/{issue}/dependencies/blocked_by { issue_id }
```

- **The id is branded.** Then passing an issue number where an `IssueId` is expected fails `tsc`, not a test.
- **Both bodies send the id as a JSON integer.** CLAUDE.md records the failure for a string id: `Invalid property /issue_id: "…" is not of type integer`.
- **Pin each path and body in `packages/github/unit/client.test.ts`.** That file already stubs `fetch` (`:55`, `:174`). Use an `id` far from the `number` in the fixture, so a mix-up cannot pass by accident.

A project on `source.tickets: db` has none of these verbs. The `Split` branch refuses it by name (`reason: 'split-unsupported'`) before any write. `resolveWait` takes the link port as an optional `links?:` field, the same way it takes `client` for `Approve` (`resolve-wait.ts:133-138`). If `links` is absent, the branch refuses.

## 2. What is durable, and what is only seen

GitHub is the truth. The log keeps the plan, plus what each read-back actually saw. Add two strict events on the ticket stream and register them in `EVENTS` (`events.ts:1938`):

```ts
SplitStarted    { waitId, by, plan: SplitPlan }        // once, before the first write
SplitReconciled {                                      // after every attempt, success or not
  waitId
  children: { key; number; id; via: 'created' | 'adopted' }[]  // every identity known after this attempt, cumulative
  observed: { children: string[]; subIssues: string[]; blockedBy: Dependency[] }  // what this attempt's GETs confirmed
  failure: string | null
}
```

**Identities are sticky and come from the log; observations are per attempt.** `splitIdentitiesOf(events, waitId)` folds every `SplitReconciled` after the governing `SplitStarted`; for a key, the first `{number, id}` recorded wins and a later attempt that could not see the child erases nothing.

**`observed` holds only what a GET returned (an identity, by contrast, may come from a `createIssue` that returned: a 2xx carries `number` and `id`, an accepted write).** A write that returned 2xx has still not been "seen" until the read-back after it. A write that threw — a timeout, a 5xx, or a 422 because the link already exists — is unknown, never failed and never done. This is the ticket's *do not infer success from a timed-out call*, and the event's type enforces it.

**What is owed is derived, never stored.** Add `splitOwed(plan, identities, observed)` as a pure function in `packages/domain/src/split.ts`. It returns the children with no identity, the *unverified* ones (identified, not confirmed by the last read-back, never re-created), the sub-issues and edges still missing, and `complete` when all are empty. Add `splitProgressOf(events, waitId)` beside `triageFactsOf` in `read-model.ts:108`, following the same pattern: the latest `SplitStarted` for the wait, the identities, the latest `SplitReconciled` after it, and their `splitOwed`. The board's task page reads it off the stream the same way it reads triage (`apps/board/src/lib/task.ts:1748`). A partial result shows the children by `#number` and lists every owed item. Nothing says complete unless `complete` is true.

There is no `task_view` column and no rebuild. The card does not show the split. `task-view.ts:496`'s `default` already ignores events it does not know, and `reduceTicket`'s lifecycle must not move on either event.

**The plan is fixed at the first `SplitStarted`.** A retry reconciles that plan, not the one in the new command. Children may already exist under the old keys, and quietly re-keying them is how duplicates appear. A different plan is accepted (as a new `SplitStarted`) only when `splitIdentitiesOf` is empty — not when a search for markers finds nothing. Otherwise refuse with `split-in-progress` and name the recorded children by `#number`. Compare plans structurally: keys, titles, bodies, kinds and edges.

## 3. How a child is identified

The marker is `<!-- lingtai:split <parentIssue> <waitId> <planHash> <childKey> -->`, and **it is a hint, not the identity**. A person may delete it from a body.

1. **Recorded:** a key with an identity on the log is that child. It is never searched for by marker and never created; it is read back with `getIssue(number)` and counts as verified only if the returned `id` is the recorded one. A 404, a throw or another id leaves it unverified, named in `failure` (`recorded child #N for "key" is not readable`), still owed, never re-created. A child a person closed is still the child; `failure` notes it.
2. **Created this attempt:** a `createIssue` that returned is recorded as `via: 'created'` even if every later step throws. One that threw records nothing.
3. **Unrecorded:** only then, search `listIssuesSince(SplitStarted.at − SKEW_MS)` for the marker and adopt the oldest match (`via: 'adopted'`) — a create that timed out but landed.
4. **Duplicates:** for a recorded key, every marker match with another id is a duplicate (identity beats age, so an older one too); for an unrecorded key, the newer matches. Duplicates are withdrawn and their sub-issue and blocked-by links removed (`removeSubIssue`, `removeBlockedBy`).

What remains is a process that dies after a 201 and before the append, with the marker removed before the next attempt: a second child. One event per attempt is the identity the operator ruled; it is not closed by an event per create.

The plan hash in the marker keeps a child made under a superseded plan from being adopted by its replacement.

**Do not reuse `keyMarker`.** `lingtai:finding` is the backlog's identity, and `settle` would treat a split child as a finding's duplicate.

**The marker includes `waitId`.** A split abandoned by a Requeue or Close leaves its children behind. A later wait's split then makes new ones rather than adopting children whose plan a person never approved for that wait.

**Each child is created with its `kind` label and `agent:hold`.** Children exist before their blocked-by links do. Without the hold, a dependent child is claimable in that gap and the queue takes it ahead of its blocker — the same failure #131 shows, coming from a different direction. Removing the hold is #562's last step, together with the parent's exclusion. It is not this ticket's.

Children made by an abandoned split stay held. Note that in the code comment and leave cleanup alone.

## 4. `reconcileSplit`, one attempt

The `Split` branch already runs inside `resolveWait`'s `decide:<ticketId>` lock (`resolve-wait.ts:100-108`). It runs after the existing `no-kinds`/`invalid-split` checks at `:262-277`. It appends `SplitStarted` if none applies, then calls `reconcileSplit`, which does this:

1. **Read.** Take the recorded identities, adopt by marker only the unrecorded keys, read each child by number, list `subIssues(parent)`, and list `blockedBy(child)` for each dependent child.
2. **Write what is missing, in order:** children, then sub-issue attachments, then blocked-by edges. A dependency's blocker id comes from the read in step 1 or from the `createIssue` response — always `Issue.id`, never `.number`. **The first write that throws stops writing.** Do not keep pressing a GitHub that is failing.
3. **Read everything again**, in a `finally`, so it also runs after a write threw.
4. **Append `SplitReconciled`** with what step 3 saw and the error message, or `null`.

Then the `Split` branch returns `ok: false` either way, since nothing is resolved yet:

- `split-partial`, when `splitOwed` is non-empty. The detail lists what exists and what is still owed.
- `split-not-resolved`, when the split is complete. The detail says the children and links exist and are held, and that resolving the wait is #562.

Replace `split-not-built` and its comment at `:257-260` with these, and update the assertion at `packages/conductor/unit/resolve-wait.test.ts:121`.

If the step-3 read itself throws, record what was read before the error, and record `failure`. An unread item counts as owed, never as present.

**A sub-issue can have only one parent on GitHub.** If a child already appears under a *different* parent, that is a failure named on `SplitReconciled`. Do not move it.

## Tests (all unit)

Test against `createMemoryEventStore()` and a fake that implements both `Tickets` and the four link verbs.

- **Fake ids differ from numbers.** Use `id = number * 1000 + 7`, and have `addBlockedBy`/`addSubIssue` reject any id the fake never issued. A number passed as an id then fails loudly.
- **Each write can fail two ways:** *throw before landing* and *land, then throw*. Cover each child, sub-issue and edge position. For every case, run the same command again until `complete`, then assert:
  - one issue per key, with no duplicates;
  - every edge exists on the dependent child and names the blocker's id;
  - every `SplitReconciled` before the last one leaves owed non-empty;
  - nothing ever appends `WaitResolved`.
- **A plan change.** After a child exists, a different plan is refused as `split-in-progress`. Before any child exists, it is accepted.
- **Read-model.** `splitProgressOf` takes the latest attempt for the given wait and ignores other waits.

`pnpm typecheck` and `HOME=/nonexistent pnpm test` are the check. A real GitHub is not exercised before the merge. What stands in for it is the endpoint path and integer-body pins in `client.test.ts` above. Whether a real run behaved is settled by the `SplitReconciled` events on that ticket's stream: `observed` against the plan in its `SplitStarted`.
