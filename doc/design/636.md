## The word "pass" means two things in the code. Fix that first.

In `packages/daemon/src/work-loop.ts` a "pass" is one look over every project (`pump` → `drain` → `options.pass`, lines 453–508). In 0103 and the ticket, a pass is one ticket's ten steps. The comment at work-loop.ts:35–40, *"One pass at a time … Running a second one concurrently would race for the same claim"*, is about the look.

Use **pass** for the 0103 sense only. Call the work loop's iteration **a look** and define it in the ADR's first paragraph. Then the decision reads cleanly:

**Looks stay one at a time. A look starts passes into free slots and does not wait for them. A pass finishing triggers another look** (it already does: completion events, work-loop.ts:87).

Keeping looks serial is what keeps the claim race closed. The claim's expected-version append (0109 §5) is the backstop.

## What each point decides, and the code it changes

1. **`runtime.concurrency`, default 1, an integer ≥ 1, is a recipe key, so slots are per project.**
   - The installation has no cap beyond the sum of each project's slots. Money is bounded by point 5, not by a slot count.
   - Code today:
     - `apps/cli/src/conduct.ts:354` passes `max: options.max ?? 1` per project per look. The comment there reads *"One ticket today"*.
     - `runQueue` in `packages/conductor/src/schedule.ts:158–259` awaits each `runOnce` in a `for (;;)`.
     - The work loop's single `running`/`again` flags are at work-loop.ts:324–326.
   - State the slot as **(project, count in flight)**. #449 can then stop one project's slots without touching another's.
   - Lingtai's own `concurrency: 2` is an operator change after a restart (#341's last child). The key has to exist in the running daemon's schema before it is pasted into the recipe (*code, restart, paste*, `doc/design/the-plugin-body.md`).

2. **The selection rule.**
   - **Order is `selectRunnable`'s, unchanged.** It sorts by kind, then by issue number (`packages/conductor/src/queue.ts:101–106`). The ticket's Fix row puts `selectRunnable` in `schedule.ts`; it lives in `queue.ts:71` and is called from `schedule.ts:189`. Cite both.
   - **Fill free slots by walking that order and skipping any candidate that collides with a pass in flight in the same project.** Skip, don't stop: a higher ticket that collides waits for the collision to clear, and a lower one that doesn't collide takes the slot.
   - **Blocked-by chain:** this is already satisfied, and the ADR should say so rather than build it again. A ticket with an open blocker is passed over as `blocked-by` (`packages/conductor/src/discover.ts:153`). A blocker in flight is still open until it lands and closes. A→B→C excludes C through B.
   - **Same `Fix`-row files:** read the four-row table's `Fix` cell from the issue body.
     - A file is a backticked token containing a `/` or an extension, with any `:line` stripped.
     - Two tickets collide when any path is equal, or when a bare name matches the last segment of the other's path.
     - **No Fix row, or no file in it, means no collision.** #341 says *"everything else runs"*; no paid scope prediction.
     - Conflicts this lets through are caught by base-moved re-review (#593) and conflict waits (#589).
   - **Watch out — projection lag:** a ticket claimed a moment ago may still read `queued` in `task_view` on the next look (`queue.ts:96`). The conductor's in-memory set of passes in flight is what the next look subtracts first. The claim's version check refuses a second claim if both miss.

3. **One landing at a time, per project and base, held in the conductor's memory. Not a file lock.**
   - The serialising point is the `land` the conductor builds, at `packages/conductor/src/conduct.ts:2705`, handed to `createMergeAction` (`packages/actions/src/merge-action.ts:104–111`, via `conduct.ts:3215` and `from-recipe.ts:388`). The second landing's `land` call waits for the first to answer.
   - **`integrate.ts` does not change:**
     - Its comment at `packages/repo/src/integrate.ts:28` (*"The lane holds no lock, because git is what makes a merge safe"*) stays true. Git is still the guarantee against a person's push or another machine.
     - The re-check on the new base is already built. Each `attempt` (`integrate.ts:385`) fetches the base afresh and runs the `base-moved` overlap at `:547–560`, and the lost-push retry loop (`:663`) re-runs all of it.
     - Serialising means the later landing starts *after* the earlier push. Its fetch therefore sees the new base, and `base-moved` (#593) sends it back to `build`/`review` when the files overlap.
   - Why serialise when git is already safe: two concurrent lanes both run `verify` and the loser runs it again. The operator decided *"lands them one at a time"* (#341), and this records that as ordering, not safety.

4. **A drain waits for every pass in flight.**
   - The change is `stop()`/`busy` in work-loop.ts:304–316. Today it awaits one retained promise; it must await every pass's.
   - `apps/cli/src/restart.ts` needs no new mechanism. It already waits for the lock to be free (`waitForTheLock`, `restart.ts:1006`), and the lock frees only when the daemon exits. `facts.inFlight()` already returns `string[]` (`restart.ts:674`, `:993`).
   - Its sentence at `:997` (*"What one may spend is ${WALL_LIMIT}"*) stays one pass's ceiling, because the passes run side by side and none starts after the drain. Say that in the ADR.

5. **The daily dollar ceiling pauses taking new work and never stops a pass in flight.**
   - #341: it *"lands before any N > 1"*. Make that structural: **while no ceiling is set, a project's effective slots are 1**, and `lingtai doctor` says so.
   - **It stays installation-wide**, because one account pays. It lives in `~/.lingtai/config.yml` (0117 naming, so it can also be exported as a `LINGTAI_` variable).
   - The day is the machine's local calendar day.
   - Spend is the sum of today's `spend` rows. A null `costUsd` is priced from the rate card at the moment of reading, never in a fold (0110 §5–6). A row that cannot be priced is named as unknown, never counted as zero.
   - It is checked where the pause is already asked before each claim (`schedule.ts:160`, work-loop.ts:491).
   - Reaching it appends `ConductorPaused` with `until` set to the next local midnight. The reason names the figure and today's spend. Use the existing standing-down path (`packages/conductor/src/conduct.ts:844–884`, 0108 §11). It needs no `holdsAcrossStarts`, because a restarted daemon recomputes and pauses again at its first check.
   - The overshoot is bounded by *slots × one pass's ceiling* (`passCeiling`, `packages/conductor/src/ceiling.ts`). Say that number is the price of never killing a pass.

6. **Per pass vs shared.**

   | Per pass, already | Where |
   |---|---|
   | Worktree | `~/.lingtai/worktrees/<project>/<runId>` (`packages/conductor/src/run-log.ts:41`) |
   | Branch | `agent/<issue>` |
   | Run log | `runLogPath`, `run-log.ts:56` |
   | Test store | made per vitest run by `packages/event-store/test-support/teardown.ts` |

   - **Ports:** none are assigned. A test that binds a fixed port is a defect at N > 1, and the resources child audits for it.
   - **Shared:**
     - the event store
     - the lock
     - the beacon
     - the projector
     - the GitHub App token
     - the runtime's account and quota
     - the recipe file
     - the bare mirror: its writes (fetch, `worktree add`/`remove`) are taken one at a time in the conductor, the same in-memory ordering as point 3, because concurrent fetches into one repository can fail to lock a ref.
