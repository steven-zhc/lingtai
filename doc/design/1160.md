# Design note: #1160, a sandbox step for new projects

## Where the code differs from the ticket

- **`first-project.ts` can see a recipe that already exists.** The ticket says its recipe is always new. It is not: `first-project.ts:850` reads `existingText`, and `:866` seeds `env.plantAt` only "when there is no file yet". A recipe can be written and then left unregistered when the registration fails. `apply-setup.ts:17` covers this case: "A failure between the write and the registration leaves the recipe". So every entry point decides by reading the file, not by asking whether the project is registered.
- **The CLI has one place to gate, not three.** `add-github.ts` and `first-project.ts` both ask their questions through `askRecipeEffect` (`apps/cli/src/recipe-flow.ts:202`). That function already computes `const absent = existing === null` over its draft (`:233-234`). Ask the sandbox question there, under `absent`. Do not add a gate in each caller.
- **The board shows step 2 over a recipe that is not registered.** `read/page.tsx` refuses only a project `alreadyAdded` finds. `answersFor` (`add-from-page.ts:214-221`) then passes `existing !== null` to `setupChanges` as `rewrite`. In `setup-answers.ts:130-135`, `rewrite` means "a recipe already on disk — a registration that failed after the write, now retried". On that path the sandbox block is not written, whatever the form says.

## Shape

### 1. `@lingtai/setup`: the proposal

- **Readers.** `ProposalReaders` (`propose-setup.ts:61`) gains an optional `host?: { answer: HostAnswer; platform: string }`. A caller passes it only when the recipe is new.
- **The new line.** `Proposal` gains `sandbox: SandboxProposal | null`. It is `null` when no `host` was passed, and `null` means the step is not asked. This keeps the existing-project case from even loading srt.
- **What the line holds.**
  - `verdict: HostVerdict`. Read it through `verdictOf(readers.host.answer)` (`packages/recipe/src/sandbox.ts:62`). Do not use `settle` or `attempt`: a throw must read as *the host check could not be read*, and `verdictOf` already guarantees that.
  - `install: InstallAdvice | null`, from `installFor(platform)` (`packages/sandbox/src/install.ts:22`). `undefined` becomes `null`, meaning the platform cannot be sandboxed at all; the sentence says so and offers no command.
  - `builtIns: readonly string[]`, set to `BUILT_IN_DOMAINS`.
- **Not a `Line<T>`.** The proposal always suggests *on*. A host that cannot is not a failed read; it is a fact shown under the default.
- **`platform` is passed in rather than read from `process.platform`.** That lets a unit test get the Linux install command on macOS without stubbing anything global.

### 2. `@lingtai/setup`: the answers

- **`SetupForm`** (`setup-answers.ts:76`) gains `sandbox: { enabled: boolean; allow: string[] } | null`.
- **`setupChanges`** writes the change only when `!rewrite && form.sandbox !== null`:
  - On: `{ path: ['sandbox'], value: { enabled: true } }`, plus `network: { allow }` when `allow` is non-empty.
  - Off: `{ enabled: false }`.
  - Never `required`.
- **Position: directly after the `steps.review` change.** The step comes after the runtimes in the UI. `askRecipe` must push the change at the same point, after `agents` and before `askInstallAndBuild`.
- **The two sides must match.** `apps/cli/unit/add-from-page-equals-add.test.ts` holds the page and `lingtai add` to writing the same text. Extend that test with the sandbox on and with it off. A difference in order shows up there first.
- **`SAID`** gains a `sandbox` sentence, for example *what an agent's commands may reach*.
- **Checking the extra hosts.** Each typed host is checked with `isNetworkEntry` (`packages/recipe/src/sandbox-block.ts:22`), the block's own rule:
  - On the CLI, inside the question's `validate`.
  - On the board, a bad entry is refused by name through `refusalOf`. That is the same function `addProject` and `previewOf` already call first. Do not write a second regex.

### 3. CLI (`recipe-flow.ts`)

- **When it is asked.** One question, asked only when `absent` and `at.proposal?.sandbox != null`. If `absent` but no proposal line was handed in, the step is **not** asked: `askRecipeEffect` has no host answer to show, and a null `proposal.sandbox` means *not asked*. A caller that adds a project must therefore pass the host reader — the three live ones do (`add-github.ts`, `first-project.ts` via `init`, and the board's `liveReaders`), each only for a recipe that is new — and omitting it writes no block.
- **The answers.** `questionEffect` with `choices: ['on', 'off']`, `fallback: 'on'` and a new `--sandbox on|off` flag.
  - **Off.** Before the choice is accepted, log the line from the ticket, *Agents and build commands will reach …*.
  - **Cannot.** When the verdict is *cannot*, log the cannot sentence before the question. Show srt's `reason` and `sentences` exactly as srt wrote them, joined the way `said()` joins them (`sandbox.ts:85`).
  - **On.** Show the built-in hosts, then a second question for extra hosts. It takes comma-separated input to match `--kinds`, an empty answer means none, and it is skipped under `acceptingDefaults`.
- **Headless runs.** A headless run with no `--sandbox` and no `--defaults` is refused by name, like every other question (`question.ts:178`). Scripted adds and unit tests that pass every flag must add `--sandbox`. That is a one-time cost, and it is deliberate: a default nobody saw is what `--defaults` exists to say out loud.
- **Clearing the flag.** Add `'sandbox'` to the list `add-github.ts:456` deletes after `askRecipe`. Otherwise `chooseFirstProject` sees the flag again (#396 and #431 fix rounds).
- **Passing the host.**
  - `add-github.ts:401` passes `host: { answer: hostHere, platform: process.platform }` only when `existing === null` (`:346`).
  - `first-project.ts:878` passes it only when `existingText === null` (`:850`) and the run is not `repairOnly`.
  - `hostHere` comes from `@lingtai/conductor/projects`, as `doctor.ts:59` already imports it.

### 4. Board

- **The page.** `read/page.tsx` reads the recipe before `proposalFor`. It uses `diskFiles.read(recipePath(project))`, and a read that throws counts as *exists*, which is the conservative side. `liveReaders(target, { recipeIsNew })` (`add-from-page.ts:155`) adds `host: { answer: hostHere, platform: process.platform }` only when the recipe is new. `hostHere` keeps its dynamic `import('@lingtai/sandbox/live')` (`projects.ts:220-223`). Do not import `live.ts` anywhere else.
- **The view.** `view.ts` is the server-side mapper and may import values. It turns the proposal into a plain `ReadView.sandbox`, or `null`, which holds:
  - `builtIns: string[]` from `BUILT_IN_DOMAINS`
  - `can: boolean`
  - `cannot: string | null`, the full sentence including the install command
  - `offLine: string`
- **The form.** `setup-form.tsx` renders the step only when `view.sandbox !== null`. It holds `{ enabled, allow }` and sends it as `form.sandbox`.
  - `read-model.ts` stays type-only.
  - `apps/board/unit/client-graph.test.ts` already fails when a client file reaches `@lingtai/setup`. Check that it also covers `@lingtai/sandbox` and `@lingtai/recipe`. If it does not, extend its list rather than adding a new test.
- **The token step.** Nothing new is built, in either input. `askClaudeTokenForRecipe` (`apps/cli/src/claude-token.ts:143-147`) and `tokenSay` (`apps/board/src/app/setup/repository/added/page.tsx:27-33`) both read the final recipe through `needsClaudeToken`. A new `claude-code` project with `sandbox.enabled: true` now meets their condition by itself. Add one unit test asserting `needsClaudeToken` is true for the recipe the default answers produce, and false for the same recipe with *off*.

## Decisions the ticket left open

- **A stale page.** A page rendered while the recipe was new, and submitted after another tab wrote it, sends `form.sandbox`. The server's `rewrite` drops it. The server's read is the one that counts.
- **The host check's cost.** The check runs once per proposal, only for a new recipe. `hostCanSandboxHere` keeps the answer for `HOST_CHECK_TTL`, and it is never built through `SandboxLayer` (`live.ts:73-90`).
- **No event.** Nothing new is appended. What settles *did this project get the block* is the recipe file, and `ProjectRegistered`'s `configHash` changes with it. No log field is needed.

## Tests (unit only, and nothing runs the real host)

- **`propose-setup.test.ts`.**
  - A fake `answer` that succeeds gives `can: true`.
  - One that fails with `SandboxUnavailable` gives `can: false` with srt's sentences.
  - One that dies gives *the host check could not be read*.
  - No `host` passed gives `sandbox: null`.
  - `platform: 'linux'` gives the `bwrap` command.
- **`setup-answers` tests.**
  - On, with no hosts, gives `{ enabled: true }` with no `network` key.
  - On with hosts gives `network.allow`.
  - Off gives `{ enabled: false }`.
  - `rewrite: true` writes no `sandbox` change.
  - Each is read back through the resolver with `HOST_FOR_SAVING`.
- **Each entry point gets an existing recipe and writes no `sandbox` change.**
  - `askRecipe` with a recipe already present.
  - `add-github` with `existing !== null` passes no `host`.
  - `first-project` with `existingText !== null`.
  - `addProject` over a file already on disk.
- **The ratchet.** New IO is Effects. `verdictOf` is already one, and nothing here adds an `async` function or an `Effect.run*`. The page's existing `Effect.runPromise` stays the page's single edge.

## What only the integration half or a person would see

The Next build (`apps/release/integration/build.test.ts`) is the only thing that sees `node:crypto` reach a client graph, and it runs only after the merge (#230). Before the merge, the extended `client-graph.test.ts` stands in for it. The visual check of the step against the wizard's existing steps belongs to the operator after the merge.
