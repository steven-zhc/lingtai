# Design: #868 — `stream_snapshots`, one store, written once over `TicketSql`

## Where it goes

- **`packages/event-store/src/snapshots.ts`** (new). It holds the ticket's `SnapshotKey`/`Snapshot`/`SnapshotStore` types, the DDL, and **one** SQL implementation: `createSqlSnapshotStore(sql: TicketSql)`. Don't write separate Postgres and SQLite versions. `TicketSql` is already the seam both stores answer, it carries `dialect` *"because the DDL is different text for each store"*, and *"Parameters are written Postgres-style, `$1`…`$n`, for both stores"* (`src/ticket-sql.ts:16-24`). So the upsert and the read are written once, and only the DDL and the epoch expression branch on `dialect`. This file imports types only, not a driver, which is the same rule `ticket-sql.ts:9-10` follows.
- **`execIdempotently` and `isPostgresCreateRace`** move from `packages/conductor/src/db-tickets.ts:87-117` into `snapshots.ts`, or into a small `src/ddl.ts` beside it. Export them, and import them back into `db-tickets.ts`. That is a move, not a copy.
- **`Log`** (`src/log.ts:48-59`) gains `readonly snapshots: SnapshotStore`:
  - `createPostgresLog` (`log.ts:75-87`) builds it on `createPostgresTicketSql({ url })` (`src/queries.ts:349-371`). Use the same `options.url` the queries use, so it is the direct connection wherever the queries are.
  - `createSqliteLog` (`sqlite.ts:618-628`) builds it on `createSqliteTicketSql(options.db)`.
  - `deferredLog` (`choose.ts:206-212`) gets a `deferredSnapshots`, written the way `deferredQueries` is (`choose.ts:161-170`).
- **Memory:** `createMemorySnapshotStore(events: MemoryEventStore)` goes in `test/memory.ts`. It keeps a `Map` keyed on the three key fields, and takes its epoch from `events.all()[0]`. It needs a way to empty its events for the contract. Add a test-only `clear()` to `MemoryEventStore`, beside `plant` (`test/memory.ts:83-91`), that empties `log` and **does not reset `seq`**. That is what `AUTOINCREMENT` does (`sqlite.ts:17-18`), and it makes the post-reset epoch differ by `seq` without depending on the clock.
- Export the types and `createSqlSnapshotStore` from `src/index.ts`. No new subpath is needed. If you add one anyway, it goes in `package.json` `exports`.

## The decisions the ticket leaves to you

**1. The epoch is formatted in SQL, not in JS.** `TicketSql` returns rows *"as each driver gives them, not normalised. A `timestamptz` column comes back a `Date` from `pg`"* (`ticket-sql.ts:26-29`), and a `Date` drops Postgres's microseconds (`timestamptz.ts:36-39`). So:

- **Postgres:**
  `SELECT seq::text || '@' || to_char(at AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"') AS epoch FROM events ORDER BY seq LIMIT 1`
- **SQLite:**
  `SELECT seq || '@' || at AS epoch FROM events ORDER BY seq LIMIT 1`
  `at` is already ISO text (`sqlite.ts:106`).
- **Memory:** `` `${row.seq}@${row.at.toISOString()}` ``.

The three formats are allowed to differ. An epoch is only ever compared within one store, so the contract asserts equality and inequality and never the string itself.

**2. `put` is one read of the epoch, then the one conditional statement.** In order:

1. Validate the snapshot; anything out of range is a `RangeError`.
2. `ensure()` the table.
3. Read `epoch()`. If it is `null`, or not `snapshot.epoch`, throw an `Error` that names both epochs.
4. Run the upsert from the ticket with `RETURNING stream_id`. One row back means `'written'`; none means `'kept'`.

A reset could land between steps 3 and 4. If it does, an old-epoch row gets written, and that row is void on arrival: `latest` filters it out and the next `put` replaces it, because of the `epoch <>` arm. So the check does not have to be folded into the `INSERT`. Keep the statement readable.

`RETURNING` on an `ON CONFLICT DO UPDATE … WHERE` returns nothing when the `WHERE` is false. That holds on both Postgres and SQLite ≥ 3.35, and `node:sqlite` is well past 3.35.

**3. `state` on Postgres is `jsonb`, and it is read back as `state::text`.** The interface says `state: string`, and #867's `decode` accepts a string. So `latest` selects `state::text` on Postgres, inserts with `$n::jsonb`, and uses plain `TEXT` on SQLite.

**Watch out:** `jsonb` does not keep the text it was given. It reorders keys and normalises whitespace. A round-trip assertion that compares the `state` strings exactly is green on SQLite and memory and **red on Postgres**. The contract therefore compares `JSON.parse(got.state)` with `toEqual(JSON.parse(put.state))`, and every other field with `toBe`/`toEqual`.

That failure can only show up in `pnpm test:integration`, which runs after the merge. The unit-level claim that stands in for it is this: the contract's own round-trip case parses `state` before comparing it. Write that case that way on purpose, and leave a comment saying why.

**4. Rows are normalised in `latest`, and a bad row rejects.** `pg` returns `bigint` as a string and SQLite returns a number (`ticket-sql.ts:29-30`).

- `lastSeq` is `BigInt(String(v))`.
- `streamVersion` and `reducerVersion` are `Number(v)`, and must be checked with `Number.isInteger`.
- Anything that is not one of these throws an error naming the key. It never resolves `null`.
- Bind `lastSeq` as a `bigint` for SQLite, which `node:sqlite` accepts. For `pg`, bind it as `String(lastSeq)`.

**5. `ensure()` is memoised as a promise and cleared on rejection.** Keep one `let ready: Promise<void> | null`. It is set to `execIdempotently(sql, DDL)`, and set back to `null` in a `.catch` that rethrows. It is never a boolean set beside the `exec`, which is the bug `projector/src/sqlite.ts:533-544` records.

On SQLite, `openSqliteLog` already runs `SCHEMA` on every open (`sqlite.ts:128`). Do **not** add `stream_snapshots` to that `SCHEMA`. If you did, the two stores would make the table by two different paths, and the Postgres path would be the only one left under-tested. One `ensure()` covers both.

**6. `written_at`** is `timestamptz NOT NULL DEFAULT now()` on Postgres and `TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))` on SQLite. The upsert's `SET` writes it again. It is not part of `Snapshot` and nothing reads it yet.

## The contract

`test/snapshot-contract.ts` exports `describeSnapshotContract(name, harness)`. Each case calls the harness for a fresh instance, and gets back:

```ts
{
  snapshots: SnapshotStore
  append(): Promise<void>      // one event on a stream of the harness's own
  empty?: () => Promise<void>  // empties this log's events; absent where the log is shared
}
```

The cases are the ticket's *Done when* list. Each case calls `append()` once before it reads `epoch()`, except the *empty log is `null`* case. `put`'s epoch is `await snapshots.epoch()`. The *different after emptied* case runs only where `empty` is given, using `it.skipIf(!h.empty)`.

- **Unit:** add `packages/event-store/unit/snapshots.test.ts`.
  - The memory harness's `empty` is `clear()`.
  - The SQLite harness opens `openSqliteLog(':memory:')`, the way `packages/conductor/unit/db-tickets.test.ts:13-15` does, and its `empty` is `DELETE FROM events`. There is no append-only trigger on SQLite to stop that. Check `sqlite.ts` once before relying on it.
  - These two runs carry every case, including the reset case.
- **Integration:** add `packages/event-store/integration/snapshots.test.ts`, wrapped in `describe.skipIf(!postgresUnderTest())`. It follows `integration/queries.test.ts`, using `created` and `cleanupStreams` for the streams it appends. **It gives no `empty`.** The test database is shared across files, and truncating its `events` would delete rows other files' cleanup expects to find. Within one file this is safe because the integration project runs with `fileParallelism: false` (`vitest.config.ts:98`). Delete this file's `stream_snapshots` rows by `stream_id` in `afterAll`.
- **`ON_POSTGRES`:** add `'packages/event-store/integration/snapshots.test.ts': 'the Postgres stream_snapshots DDL, jsonb state and the conditional upsert'` to `test/postgres.ts:23-37`. Without that line `unit/on-postgres.test.ts` fails, because the file reaches `createPostgresTicketSql`.
- **Move check:** `packages/conductor/unit/db-tickets.test.ts` must stay green. It is what shows the `execIdempotently` move changed nothing.
