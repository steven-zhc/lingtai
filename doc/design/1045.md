# Design: #1045, the process log's open and close as Effects

The ticket already gives the shape. This note covers three decisions it leaves open: how the memo is held without running anything at import, where the uninterruptible region starts, and how to write the new test so it doesn't close the log for other tests.

## 1. The memo is a `Deferred`, made when the first `get` runs, never at import

`closableOnceEffect` keeps the same three variables `closableOnce` keeps today (`closable.ts:34-36`): `opening`, `closing` and `closed`. Two of them change type:

- `opening: Deferred<T> | null`
- `closing: Deferred<void> | null`

Make each one with `Deferred.makeUnsafe()` (`effect/dist/Deferred.d.ts:126`, Effect 4.1.2). The ratchet doesn't count it: `RUN` matches only `run*` names (`effect-ratchet.test.ts:69`). It also has a precedent in this package: `makeSqlSnapshots` builds its cell with `Ref.makeUnsafe(false)` (`snapshots.ts:237`).

Make the `Deferred` **inside the `Effect.suspend` thunk**, not when `closableOnceEffect` is called. Both `closableOnce(open)` calls sit at module scope (`choose.ts:73` here, `packages/projector/src/choose.ts:79`), so construction must allocate nothing and run nothing.

Do not use `Effect.cached`. It hands back its memo only after an Effect has run, which forces either a run at import (refused by the ticket) or a `yield*` between the null check and the assignment. That gap is where two first callers could both start an open.

Inside the thunk, the check and the set are one synchronous JavaScript step, so they can't interleave. That is what keeps the guarantee in `unit/closable.test.ts:6-16` (two racing first callers, one open).

## 2. `get()` is masked from the start, so an interrupted first caller still fills the cell

The shape:

```
get: () => Effect.uninterruptibleMask((restore) => Effect.suspend(() => {
  if (closed) return Effect.die(refuse())
  if (opening) return restore(Deferred.await(opening))
  const d = (opening = Deferred.makeUnsafe<T>())
  return Effect.exit(open).pipe(
    Effect.flatMap((exit) => Deferred.done(d, exit)),
    Effect.andThen(restore(Deferred.await(d))))
}))
```

- **The mask goes outside the `suspend`.** If it went inside, the thunk could set `opening` and the fiber could then be interrupted before the open's uninterruptible region started. The cell would be set and never filled, and every later caller would hang. That is the trap the ticket's **Watch out** row names.
- **Only the waiting is restored.** A second caller interrupted while it waits leaves; the open the first caller started runs on and fills the cell.
- **`Effect.exit(open)` catches defects as well as failures.** `open` is `Effect<T>`, so the 0056 refusal and a bad URL arrive as defects, through `Effect.promise`. `Deferred.done(d, exit)` stores that exit. Every later `get` dies with the same defect and never opens again, which is today's `opening ??= open()` (`closable.ts:40`) memoising a rejected promise.
- **`closed` is read inside the thunk, before the memo check**, in the same order as `closable.ts:39-40`. This is the suspension the ticket asks for: `processEvents`, `processQueries`, `processLogSql` and `processSnapshots` call `process_.get()` once, at import, and each later run reads `closed` again.

`close()` has the same shape:

1. Mask, then `suspend`.
2. Set `closed = true`.
3. If `closing` exists, `Deferred.await` it.
4. Otherwise make `closing` and fill it with the exit of: nothing, if `opening` is null; otherwise the exit of `Deferred.await(opening)`, then `close(t)` on success and nothing on failure (today's `.catch(() => null)`, `closable.ts:48`).

`close` is uninterruptible from start to finish. A failing `close(t)` is remembered in `closing` the same way, so a second `closeProcessLog()` repeats the outcome of the first, as the memoised `closing` promise does today (`closable.ts:44`).

## 3. Faces and the types

- **`closableGetFace` and `closableCloseFace`** must be **exported** generic function declarations whose whole body is `return Effect.runPromise(c.get())` or `return Effect.runPromise(c.close())`. The face check refuses anything that isn't exported (`effect-ratchet.test.ts:192-197`) and any body that is not exactly one `return` statement (`:204-213`). A call on a parameter passes the check: `c.get()` is a `CallExpression` (`:240-242`). `closable.ts` must import `Effect` from `effect`, or `importsOf` will not recognise the run.
- **The type parameter.** `closableOnceEffect<T>` has no bound, because closing goes through the `close` function. `closableOnce<T extends Closable>` keeps the bound and the `ClosableOnce<T>` interface it returns today.
- **`Opened.close: Effect<void>`** (`choose.ts:54-66`):
  - Postgres: `Effect.promise(() => db.close())`.
  - SQLite: `Effect.sync(() => db.close())`. Today's `async () => db.close()` (`choose.ts:169`) only wraps a synchronous call; `sqlite.ts:134` calls the same `db.close()` with no await.
  - `Opened` is not exported (`choose.ts:54`), so nothing outside the package sees the change.
- **One Effect function behind each `choose.ts` face**, for example `const processLogEffect = () => Effect.map(process_.get(), (o) => o.log)`. Each face is then `return Effect.runPromise(processLogEffect())`. `processEventStore`'s Effect maps `.log.store`; it does not go through `processLog`'s face.

## 4. `append`: the inner run, and the error that comes out of it

`writeRows(tx, rows)` is an `Effect.forEach` with **no `concurrency` option**. Leaving it out is what keeps the rows sequential, and the comment at `event-store.ts:430-431` stays above it. Each row is `Effect.promise(() => tx.orm.public.Event.create(row))` mapped through `toEnvelope`. The `.then` that sorts `isVersionConflict` from defects (`:438-452`) does not change, and neither does `Effect.uninterruptible` around the whole thing (`:426`).

The behaviour that matters is that **`runPromiseWith` must reject with the driver's own error**, not a wrapper or a `Cause`. That error is what lets the transaction roll back and what `isVersionConflict` (`:220-229`) reads `code` and `constraint` from. The two fake-`tx` unit tests the ticket asks for are the check (`ConcurrencyError` on `23505`, and `rejects.toBe(e)` otherwise). If the second one fails, the fix belongs in the inner run, not in the `.then`.

## 5. Tests

**The suspension test** needs a fresh copy of the module. It closes `choose.ts`'s module-level `process_`, so it must follow `unit/closable.test.ts:37-45`: call `vi.resetModules()`, then `await import('../src/index.ts')`. A static import would leave the log closed for every later test in that module graph. Put it in that `describe`.

**The interrupted-first-`get` test:**

- Give `closableOnceEffect` an `open` that waits on a latch.
- Fork the first `get`, interrupt it while the open is in flight, then release the latch.
- Assert that a second `get` resolves to the same value and that `open` was entered exactly once.

Interrupting before the latch is released is what proves the masked open still fills the cell.

None of this needs Postgres or the filesystem, so it all belongs in the unit half. The Postgres `append` path (`integration/event-store.test.ts`) can't be run before the merge. The fake-`tx` tests in §4 are the unit-level stand-in for it.
