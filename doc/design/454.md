### The cause

`2185efa8`'s explanation (Next's `WriteStream` augmentation) is also wrong. Next 16.3.3's `next/types/global.d.ts` contains this:

```ts
interface ProcessEnv {
  // TODO: Should be optional and possibly undefined
  readonly NODE_ENV: 'development' | 'production' | 'test'
}
```

Any program with Next's types therefore makes `NODE_ENV` a required property of `NodeJS.ProcessEnv`. `RunCommandOptions.env` is `Record<string, string>` (`command.ts:87`), which has no `NODE_ENV`. So `spawn(…, { env, … })` at `command.ts:403` and `:411` matches no overload. tsc falls through to the `readonly string[]` overload (TS2769), and `child` becomes the intersection of every `ChildProcessByStdio` variant, reduced to `never` (TS2339 on `stdin`, `:420-421`).

I reproduced it outside the repo using only the worktree's own `tsc` and `@types/node`. A three-line file passes `declare const env: Readonly<Record<string, string>>` to `spawn` with `stdio: ['pipe','pipe','pipe']`. It is green with `--types node` alone. Adding `next/types/global.d.ts` to the file list reproduces the exact pair `TS2769 … 'shell' does not exist in type 'readonly string[]'` and `TS2339: Property 'stdin' does not exist on type 'never'`. Next's `global.d.ts` without an `env` stays green, which rules out `WriteStream`.

### The fix

**Fix it in `command.ts`, not by keeping the board away from the barrel.** Keeping the board away is what `2185efa8` did, and #452 broke it again within hours, through a different file. Cutting `hold-of.ts → pass-steps.ts` would only fix #452's branch, and `judge.ts` is a second route to the same barrel. `command.ts` itself is fine except under Next's globals, and the repository already handles this exact situation twice:

- `packages/agent/src/auth.ts:32-34`: `// Cast for a compiler that widens \`ProcessEnv\` — Next's does, and the board reaches this through \`currentRecipe\`'s sign-in detection.` followed by `env: env as NodeJS.ProcessEnv,`
- `packages/agent/src/claude-code.ts:407` and `codex.ts:1086`: `env: request.env as NodeJS.ProcessEnv,`

`command.ts` is the only `spawn` in `packages/*/src` or `apps/*/src` that passes a `Record<string, string>` env without that cast. (`conduct.ts:430` spreads `process.env`, so it carries `NODE_ENV` already.) In `spawnChild` (`command.ts:398-399`), type the computed `env` once as `NodeJS.ProcessEnv` with an `as`. Write a comment in the style of `auth.ts`: why Next makes `NODE_ENV` required, and that this child's environment is deliberately chosen whole (the `:81` doc comment, *"nothing is inherited from this process"*), so adding a `NODE_ENV` would be a behaviour change and is wrong. Use the cast only; do not touch `RunCommandOptions.env`'s public type or anything its callers build. I checked that the cast compiles with and without Next's `global.d.ts`. It is a type assertion on one value, not a suppression of the kind the ticket forbids: no `@ts-expect-error`, no `skipLibCheck` change, and `apps/board` stays in `typecheck`.

**Make `pnpm typecheck` keep proving it.** This bug has now been found three times: `auth.ts` in `77d90da8`, `command.ts` in #445, and `command.ts` again in #452. Each time a ticket that didn't cause it found it, because the board reaching that file was an accident. Add `apps/board/test/next-globals.ts`. `test/` is in the board's `tsconfig.json` `include`, and it is not matched by vitest's `*/unit/**/*.test.ts?(x)` glob (`vitest.config.ts:72`), so it is never run as a test. The file is a type-only re-export from the `@lingtai/actions` barrel, e.g. `export type { RunCommandOptions } from '@lingtai/actions'`, with a comment citing #454: it puts the whole barrel into a program with Next's globals on purpose. A type-only export costs nothing at runtime and nothing for the Next bundle. Leave `2185efa8`'s `./action` subpath in place: it is harmless and narrower. Its commit message's `WriteStream` claim is history. Correct it in your commit body, not by rewriting anything.
