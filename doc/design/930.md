# Design note for #930: record the recipe once per hash on its own stream

The ticket already gives the shape. Three things below are not obvious from it, and the first one breaks the change silently if it is missed.

## 1. Do not append through `appendNow` or `appendAt`

`appendAt` takes its version from a fresh read:

```ts
const appendAt = async (stream: string, events: readonly ToAppend[]): Promise<void> => {
  const at = (await store.read(stream)).length
  await store.append(stream, at, events)
}
```

(`packages/conductor/src/conduct.ts:697-700`.) `appendNow` wraps it (`:725-732`). If the recipe went through either one, the second dispatch would read length 1 and append at 1. It would succeed, and `rcp-<hash>` would grow by one copy per dispatch. That is the 451 copies again, moved to another stream. Nothing would go red, because every append succeeds.

So the recipe append calls `store.append(recipeStream(hash), 0, …)` itself. It handles two cases:

- **`ConcurrencyError`:** the recipe is already recorded. Return and carry on. Do the same as `backlog.ts:244-262`, with `ConcurrencyError` imported from `@lingtai/event-store` (`backlog.ts:50`). `conduct.ts:75` does not import it yet.
- **Any other error:** a defect. It must still set `unappended ??= defect` and re-throw, as `appendNow` does at `:729`. Otherwise the defect handler at `:4179` / `:4298` never sees it. That is the case `appendNow`'s own comment describes at `:704-722`: a store refusal turns into a step that *"did-not-finish: threw"* and parks the item at a person.

The simplest form is a third helper beside `appendNow`, for example `appendFirst(stream, events): Promise<'appended' | 'already'>`, with a doc comment explaining why it does not read the version first.

## 2. Put the append where a unit test can reach it

The fourth Done-when box needs a `createMemoryEventStore()` test: two dispatches leave one event on the stream, and a different recipe gets its own stream. `conduct.ts` is too large to drive from a unit test for that. So put the append in `packages/conductor/src/steps-resolved.ts`, next to `stepsResolved()`:

```ts
recordRecipe(store: Pick<EventStore, 'append'>, resolved: ResolvedRecipe): Promise<'recorded' | 'already'>
```

`recordRecipe` builds the `RecipeRecorded` payload with `canonicalRecipe(resolved.recipe)`, the same expression as `steps-resolved.ts:23` today, and swallows only `ConcurrencyError`.

- **`conduct.ts`** wraps the call, setting `unappended` on any other throw as in §1, and puts it in its own `yield* Effect.promise(...)` just before the `StepsResolved` one (`:3702-3710`).
- **The unit test** calls `recordRecipe` twice against the memory store (`packages/event-store/test/memory.ts:131`). The memory store throws `ConcurrencyError` on a version already taken (`memory.ts:170`), so the test checks the same rule the real store enforces.

The second half of that box, *"the second dispatch's `StepsResolved` is still appended"*, holds by construction: the two appends are sequential, and the first returns rather than throws. To check it in a test, call `recordRecipe` and then append `stepsResolved()` to a run stream, twice, on one store. Do not try to drive `conduct`.

Update the module doc at `steps-resolved.ts:1-7`. It says the payload is *"the canonical recipe beside the hash it verifies against"*, and after this change it is the hash alone.

## 3. `STREAM_ID_PATTERN`'s comment stops being true

The comment at `packages/domain/src/envelope.ts:38-42` says:

> `int`, `ctl`, `ext` and `bkl` have no constant of their own … so this pattern's `.source` is byte-identical to the one it replaced.

`rcp` will have a constant (`RECIPE_STREAM_PREFIX`, as the ticket asks), so add it as `${noDash(RECIPE_STREAM_PREFIX)}` and not as a literal. Then rewrite the last sentence, because the `.source` changes.

The `StreamId` error message right below (`envelope.ts:48-…`) lists what each prefix is. Add `rcp` there too, or a refused id will name every prefix except this one.

## Smaller decisions

- **Actor:** `'conductor'`, the same as the `StepsResolved` beside it.
- **Payload:** `configHash` is in the payload even though the stream name already carries it. The record then verifies itself without parsing the stream id.
- **Where the type goes in `EVENT_AT`:** next to `StepsResolved`, with the same steps. `what-an-event-is-written-at.test.ts` holds this against real fixture passes, and since the new event is appended in the same dispatch it will be seen at the same steps. If that test names a different step set, use what it names. It reads what passes actually wrote, so it wins over the ticket.
- **Tripwire, `recorded-recipe.test.ts:121-185`:** add `RecipeRecorded` to the same type list as `StepsResolved`. Nothing changes structurally.
- **Checks:** nothing here needs `pnpm test:integration`. What the SQLite and Postgres stores do at version 0 is already covered by the store contract (`packages/event-store/test/contract.ts`), which runs against the memory store in the unit half.
