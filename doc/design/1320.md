## The read: one stream read, kept as events as well as folded

The page reads the PR's events once, with `readPrEvents(project, n)`. It folds them with `reducePr` to get the state, and keeps the events themselves. The events are needed because two panels cannot be drawn from `PrState`:

- **History** is `toLine` over each event.
- **Step durations** need each event's own time. `PrStepRecord` is `{ step, headSha }` and no more (`pr.ts:19-22`), and `PrStepDone`'s payload is the same two fields (`events.ts:2590`). A step's duration is its `PrStepDone`'s time minus the time of the event before it, counted from the last `PrInProgress`. The first step counts from that `PrInProgress` itself.

`prPage` takes `events` beside `state`, and stays pure.

The spend read is the one `readPrPage` does: rows whose `streamId` is `prStream(project, n)` (`prs.ts:126-133`). Move that loop into a helper both readers call, so there is one copy.

For `/pr/<p>/next` (the draft), **extract the draft half of `readPrPage` into a function and call it from both pages**. The PR board's draft is decided from every PR's tickets (`prs.ts:104-118`, *"never an empty draft"*), and the page must not decide it differently. *Submit is disabled while another PR is open* is decided from the same `prs` list. `submitPrNow` refuses a second submit as well, so the disabled button is only a courtesy.

## What *What Lingtai did* can actually say

`prStepRows` gives each step one of three statuses: `done`, `waiting` or `pending`. Everything the mock draws beyond the status has to come from a field the log really records. Draw these, and nothing else:

| Step | Its detail line, and where it comes from |
|---|---|
| sync | The latest `BranchSynced.how` (`events.ts:2734`). `already` reads *nothing to bring in*. `clean` reads *main brought in, clean*. `resolved` reads *1 conflict resolved*, with `state.rounds` and `state.refusals` for the round count and the last refusal. While waiting, `state.wait.conflict` gives the paths, rounds used and `mainAhead`. |
| build | ✓ or ✕, and the duration. **No test count**: nothing records *1,214 passed*. |
| push | `PrPushed.found` (`pushed` / `existing`) and the short head. |
| ci | From `state.checks`: n of m green and each check's `url`. Or `state.ciSkipped.why`, which reads *no CI step*. |
| summary | `state.summary`, `state.summaryNotWritten` (reads *no summary: <why>*), and `state.edited`. **No turn count and no per-step spend**: the spend rows are per stream, and nothing splits them by step. |

The mock's *9 turns*, *1,214 passed* and *$0.06 summary* figures are not drawn. Spend appears once, in Facts, as the stream's total. Split it into *tickets / sync / summary* only if the spend row turns out to carry a field that says which run each cost came from. The agent should read the row type in `packages/projector/src/spend.ts` and check before drawing the split.

`pending` means two different things, and the view must keep them apart:

- When `state.status` is `in-progress`, the first `pending` row is the step **in flight**.
- When the status is `waiting`, `merged`, `closed` or `in-review`, a `pending` row after the step that stopped is *not reached — the PR stopped before it*.

A `pending` row is never drawn as ✓. This is the Done-when test for *Summary · not reached*.

*The last time through In progress* takes care of itself: `PrInProgress` resets `steps` (`pr.ts:264`). It does **not** reset `rounds`, `grants` or the summary fields (`pr.ts:86-90, 117-121`), so the summary row stays accurate across a pr-fix pass.

## The render-time host read: `getPull`, and the link comes from the log

The code host is asked with `GitHubClient.getPull(state.host.number)` (`packages/github/src/client.ts:360`). It answers a `PullState` holding `state`, `merged`, `draft`, `headSha`, `updatedAt` and `mergeCommitSha` (`client.ts:158-166`). **It has no `html_url`.** The ticket's Edge that reads `html_url` is wrong on that one field. The link is `state.host.url`, recorded by `PrDraftOpened` (`pr.ts:62`). That means the link is drawn at once, from the log, and does not wait on the streamed part. The streamed part only adds the host's word on whether the PR is open, draft, merged or closed.

When to ask:

- Ask only when `prHostOf(recipe) === 'github'` (`packages/conductor/src/pr.ts:240`) and `state.host !== null`.
- Ask only while the log says the PR is open. Once the log records `PrMerged` or `PrClosed`, the log is the answer and nothing is asked.

The sweep's reaction to a failed read is the model to follow: `pr.ts:1138-1144` catches the failure and treats the PR as unread, never as closed.

The board builds no `GitHubClient` today. The only uses are a type (`apps/board/src/lib/recipe.ts:23`) and `createAppReader` in the setup routes. The agent must find how the Queued column's GitHub read gets its client and use the same construction. If that read goes through a different seam than `GitHubClient`, put a narrow `getPull` port beside it. **Do not add a second way of minting an installation token.** Write the read as an Effect (0101 §6). The ratchet counts any new `async` function.

Follow `queued-stream.tsx`'s shape: a pure part over its arguments, plus a `Suspense` boundary with a skeleton in place. There is one skeleton (the poster's small line) because only one fact streams.

## Summary save: an append the daemon serves, not a write to GitHub

`editPrSummary` appends `PrSummaryEdited`. Its comment says the daemon *"regenerates the description and puts it on the code host"* (`packages/project/src/pr.ts:692-695`), and `PrSummaryEdited` is in the daemon's `PR_EVENTS` (`packages/daemon/src/work-loop.ts:124`). **Saving does not push synchronously.** So:

- `savePrSummaryNow` follows `retryPrNow`'s shape exactly: `prRef`, then `editPrSummary(ref, { by: actor(), summary })`, then `revalidatePath`. It touches no GitHub client.
- The button reads **Save**, and after the click the page says *saved — Lingtai puts it on GitHub* until `state.descriptionOwed` is false. `descriptionOwed` (`pr.ts:139`) is cleared by `PrDescriptionPushed`. Calling the button *Save to GitHub* would claim a push that has not happened yet. While the description is owed, the small line under the field reads *GitHub's copy is behind; Lingtai puts it there on its next pass*.
- `summaryEditTransition` already refuses a solo project, a project with no PR, a PR that has ended, and an empty summary, by name (`pr.ts:1124-1137`). The page draws the refusal's `detail`. On a closed or merged PR the editor is read-only, because the command would refuse a save anyway.
- `state.summary.text` fills the textarea, and nothing else does. The read-only part under it is `describePr`'s body with the summary section removed. **Do not regenerate the description in the board.** `describePr` (`conductor/src/pr.ts:338`) is what gets pushed. It takes `ports`, so build them the way `apps/cli/src/pr.ts:85` does. If those ports reach IO the board lacks, fall back to `prDescription` over the state's tickets, and say in the run's last message that you did.

## `prFixTicketLink`

`prs.ts:144` hard-codes `'lingtai:pr-fix'` today and drops the title. Replace it with the helper and import `PR_FIX_LABEL` from `@lingtai/conductor/labels`, as `recipe-lines.ts:1` already does.

- For a GitHub project (`prHostOf(recipe) === 'github'`, owner from `readProject`), the link is `issues/new?labels=…&title=…`. The title is `pr-fix for <prName>: `.
- For a project with no GitHub host (`'none'`), it is the command `lingtai ticket new --project <p>` drawn as code. `--project` exists (`apps/cli/src/ticket.ts:150-183`), and so does the `labels:` line (`ticket.ts:440`).

`prBoard`'s `newFixHref` input becomes this helper's output.

## Decisions on the edges

- **Stale page, summary**: `summaryEditTransition` lets a stale page replace the summary on purpose (*"the person's latest words are the summary"*, `pr.ts:1121-1122`). Nothing compares versions on the board's side.
- **Stale page, rounds**: send the `commit` the page drew, as `moreRoundsNow` already does (`actions.ts:711-716`).
- **Host says merged before the log does**: draw the note in the poster's small line only. The strip and Do still follow the log, so no button disappears on the strength of a read the log has not confirmed.
- **No host number** (`state.host === null`, e.g. `draft-unsupported`): use `prName`'s fallback, draw no link, and make no request.
- **A `PrMergeBackFailed` whose `prHead` is the current head**, read from `state.mergeBack` (`pr.ts:81-86`): Facts says the line from the ticket. `why: 'unknown'` reads *will be tried again*, not *failed*, per that field's own comment.
- **Cost to later tickets**: none beyond the extracted helpers. The `prPage` tests pin only words that are data in `pr-page.ts`.
