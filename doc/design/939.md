## Design note — #939

### Where the bar actually is

The ticket says the column holds "the bar, `<main>` and the footer". In the code, **the bar is not next to `<main>`. It is the first child inside it**: `page.tsx:722-724` opens `<main>`, then `<TimingMeta>`, then `<div className="bar">`. After the bar come `<Pending>` (`page.tsx:813`) and `.cols` (`page.tsx:821`). The page returns a fragment (`page.tsx:721`, `<>`). `<Footer>` follows `</main>` (`page.tsx:921-928`).

Leave the bar where it is. Moving it out of `<main>` changes the landmarks, and no ticket asks for that. So the shape is two nested columns:

- **Outer:** the fragment at `page.tsx:721` becomes `<div className="home">`. That is the one wrapper the ticket allows.
  - `.home { display: flex; flex-direction: column; min-height: 100vh; min-height: 100dvh; }`. The second declaration overrides the first wherever `dvh` is supported.
  - It holds `<main>` and `<Footer>`, so the footer stays outside `<main>`, as the comment at `:922` requires.
- **Inner:** `.home > main` is also a column (`display: flex; flex-direction: column`) and takes the free space.
  - Inside it, the bar, `TimingMeta` and `Pending` keep their natural height.
  - `.cols` takes what is left.

`flex: 1` on `<main>` alone does nothing for the lanes, because `.cols` is a block child of `<main>` and would not stretch.

`<body>` has no height of its own (`globals.css:81-87`), and `layout.tsx` renders `{children}` straight into it. So the `min-height` has to be on `.home`. A percentage height chained down from `html` would not work here.

### Use `flex: 1 0 auto`, not `flex: 1`

Use `flex: 1 0 auto` on both `.home > main` and `.cols`. `.cols` has `overflow-x: auto` (`globals.css:287`). Once one overflow axis is not `visible`, the other computes to `auto`, so `.cols` is a scroll container. A scroll container's automatic minimum height is 0. With a shrink factor of 1 and a basis of `0%`, a browser may squeeze the lanes and give them a vertical scrollbar of their own, which the ticket's Out of scope rules out ("Inner scrolling for each lane").

- `flex-shrink: 0` with an `auto` basis means the lanes are never shorter than their cards.
- `flex-grow: 1` means they fill whatever space is left.
- Long lanes: `.home` only has a `min-height`, so it grows with the content and the footer follows the last card.

### Delete the 41 px rule and the comment that relies on it

Delete `min-height: calc(100vh - 41px)` (`globals.css:288`), and do not replace it with another number.

The footer's `margin-top: 8px` (`globals.css:157`) can stay: flex puts it inside the column's total, so it adds no overflow. It shows as an 8 px band of `--ground` between the lanes' bottom rule and the footer. That band is there today and is not this ticket's concern.

Add the CSS for `.home` next to `.cols`. Give it a comment saying why the bar's and the footer's heights are not written anywhere, and cite `f0068477`'s 41 px as the number that went stale.

### The test: render the shell, not `Page`

`Page` (`page.tsx:648`) is an async server component that reads the projections. No unit test renders it, and `grep -rn "src/app/page" apps/board/unit` finds nothing. Rendering it would put the database in a unit test, which 0060 §1 forbids.

So the "unit test renders the home page" in Done when is met like this:

- **Extract a component.** Move the outer structure into a small presentational component, e.g. `HomeFrame({ children, footer })` in its own file under `apps/board/src/app/`. It renders `<div className="home"><main>{children}</main>{footer}</div>`. `Page` passes the bar, `Pending` and `.cols` as children, and `<Footer …/>` as `footer`.
- **Render it with stand-ins.** The test renders `HomeFrame` with `renderToStaticMarkup`, a `.bar` and a `.cols` as children, and a plain `<footer>` stand-in. It asserts:
  - one `.home` root;
  - inside it, `<main>` and then `<footer>`, in that order;
  - `<footer>` is not a descendant of `<main>`;
  - `.bar` comes before `.cols`, both inside `<main>`.
- **Stand in for `Footer`.** Passing the real `Footer` into the frame test would pull its data props into it. `footer.test.tsx` already covers `Footer` on its own.
- **Check the CSS by reading it.** Read `globals.css` the way `unit/panel-css.test.ts:11-19` does. Assert:
  - the `.cols` rule has no `min-height` built from `vh`;
  - no `calc(100vh -` appears anywhere in the file;
  - `.home` declares `min-height` with `100dvh`.

  This guards the CSS half; nothing in jsdom lays anything out.

The layout itself — the footer on the first screen when the lanes are short, after the last card when they are long — is only checked by a person in the browser (Done when's third box). No unit or integration test measures it.

### Edges this touches beyond the ticket's list

- **`loading.tsx` / skeleton (#897):** there is no `app/loading.tsx` in this app. `ls apps/board/src/app` shows `skeleton.tsx`, which renders inside the lanes. If a skeleton renders its own `.cols` outside `Page`, it does not get the column, and its lanes are content-height. Run `git grep -n 'cols' apps/board/src/app/skeleton.tsx` first. If it does render one, wrap it in the same frame rather than writing a second rule.
- **Narrow windows:** when the bar wraps to two lines (`.bar` has `flex-wrap: wrap`, `globals.css:93`), it is simply taller and the lanes get less space. That is the reason the fix is a flex column and not a constant.
- **Other pages:** `.home` and `.home > main` are scoped to the new class, so the other pages' `<main>` elements are unaffected.
