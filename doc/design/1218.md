# #1218: design note for `lingtai rerun`

## What already exists, and the decision that matters

Most of what this ticket needs was built by #1205, under another name. #1205 re-cuts at the saved head and applies the kept WIP. It reruns the cut-off call with its recorded prompt. It numbers the dispatch id. All of that is wired for exactly one source: a ticket that went back to the backlog on an `AccountLimit` release, the `continuableRelease` branch at `packages/conductor/src/conduct.ts:1325-1401`.

This ticket's job is to give that machinery a second source, an approved wait whose resolution is `RerunStep`. It should not build a parallel path. Everything below follows from that.

## 1. `rerunHeadOf` is `releasedHeadOf`'s rows lifted into the domain, not a new rule

`releasedHeadOf` (`packages/conductor/src/attempts.ts:704-744`) already answers "where is a stopped attempt re-cut, and what is carried onto the cut". Its doc comment: *"`at` is the commit, `atRef` the ref that must still carry it (`null`: none does, it is the attempt's base), `carry` the kept WIP put on it uncommitted. `cannot` says why the head is not one to continue."*

Its rows are stricter than the ticket's *Edges* line. On a `Saved` head it refuses when an arm commit beside the head has no `RunKeptUncommitted` record (`attempts.ts:713-716`). The comment says *"a re-cut on the clean head would publish over the arm that holds it"*. Keep that refusal: the ticket's three-case summary is a paraphrase, and the stricter rule is the one that protects work.

The shape:

- **`rerunHeadOf(state: AttemptState)`** goes in `packages/domain/src/attempt.ts`, beside `savedHeadOf` (`attempt.ts:776`). It holds the same `switch` as `releasedHeadOf`, with one change. Its `NoSavedHead` + `nothing-committed` row answers a `{ base: true, carry: null }`-style marker, not a sha. The reason is that the base sha comes from `diffBaseShaOf(runEvents)` in the conductor, and the board (#1219) only has state.
- **`releasedHeadOf(runEvents)`** becomes `rerunHeadOf(reduceAttempt(runEvents))`, plus resolving that marker through `diffBaseShaOf`. That gives one table, with #1205's answers unchanged. `conduct-continues-an-account-limit.test.ts` and the `releasedHeadOf` unit tests stay green without edits, and that is the check that nothing moved.
- **Unit tests:** one per `savedHeadOf` answer, against `rerunHeadOf` (Done-when 2). That means `Saved`, `Saved` with a recorded carry, `Saved` with an unrecorded arm, recorded `WipHead`, unrecorded `WipHead`, `BranchDiverged`, `NoSavedHead` + `nothing-committed`, and `NoSavedHead` otherwise.

## 2. One `rerunStepOf(reason): Step | null` in `wait.ts` decides both the offer and the step

`allowedResolutions` (`wait.ts:495-503`) appends `RerunStep` exactly where `rerunStepOf(reason) !== null`. `conduct.ts` takes the continuation's step from the same function. This is how `grantCriterion` already feeds both the offer and the grant (`wait.ts:498`, `conduct.ts:1418`), and it means the offer and the step can never disagree.

The rows:

| Wait | Step |
|---|---|
| `AgentCrashed` with `standing === undefined` and `step` in `design`, `implement`, `review` | `reason.step` |
| `ProposedEscalated{BuildRed}` | `'build'` (`fromOf`, `proposal.ts:308-309`) |
| `ProposedEscalated{CheckRefused}` with `fromOf(proposal) === 'proposed'` | `'proposed'` |
| `CheckRefused` with `step === 'proposed'` | `'proposed'` |
| everything else | `null` |

**`VerifyRed` is not offered.** The ticket's *Edges* lists it, but `fromOf` answers `'merge'` for it (`proposal.ts:326-328`: *"`MergeConflict` / `BaseMoved` / `VerifyRed` / `MergeRefused` → `'merge'`"*). The same *Edges* list says *"Not `merge` (Approve and #1221 own it)"*, and *Out of scope* says *"Rerunning `merge`"*. The rule that holds both is "offered where the step it reruns is not `merge`", so `VerifyRed` falls out. The test file should name this case with a test that asserts `RerunStep` is **not** offered on `{VerifyRed}`.

**A standing crash is `null`.** `tableResolutions` hands on the stood wait's offer (`wait.ts:297-299`). That offer is `GrantFixRound` again, which is how to rerun a granted round that crashed. `rerunStepOf` does not recurse into `standing`.

**An unpushed run is dropped, as `Approve` is** (`wait.ts:497-500`). The branch never reached origin, so no saved head can be checked.

## 3. The resolution's shape

```ts
const RerunStepResolution = z.object({ _tag: z.literal('RerunStep'), onSha: z.string(), ref: z.string().nullable() })
```

- **The const gets a different local name** because `packages/domain/src/attempt-next.ts:108` already exports a `RerunStep` (the walk's own *run again in place*, #1224). The `_tag` stays `'RerunStep'` as the ticket says. Never import one where the other is meant.
- **`ref` is nullable** because a recorded-WIP head and a nothing-committed head have no ref that must carry them (`atRef: null`). `onSha` is `rerunHeadOf`'s `at` for the first two cases. For the base case it is the base sha, which the server resolves the same way `releasedHeadOf` does.

Then edit the two exhaustive tables:

- **`TriageAdvice` assertion** (`wait.ts:283-286`): change it to `Exclude<Resolution['_tag'], 'AnswerQuestion' | 'RerunStep'>`, with a comment saying why. Triage cannot judge flakiness, and a follow-up adds it once people have used the move.
- **`RESOLUTION_COPY`** (`apps/board/src/lib/resolution-copy.ts:6`): add the `RerunStep` entry.

## 4. `resolveWaitEffect`

Add a `RerunStep` branch beside `GrantFixRound`'s (`resolve-wait.ts:321-353`). Do not reuse `savedHead()` (`:441-478`), because it refuses `WipHead`, which this move accepts. Read the attempt the same way and call `rerunHeadOf`. Then:

- **`cannot`** refuses with the answer's own words, under one new `reason`, for example `'no-rerun-head'`. Add it to the `Refused` reason union; the CLI already prints `detail`.
- **`onSha` not matching** refuses `'stale'` (this is `--if-head`).
- **A non-null `atRef`** needs `options.client` and the `refShaOrNull` check, exactly as in `:336-352`. A null `atRef` needs no remote read.
- **Rewrite the resolution** to the server's own `{ onSha: at, ref: atRef }`, as `:352` does.

Every refusal is before any append, which is the existing invariant at `:300`. Add `RerunStep` to the `ContinueRequested` condition (`:481-487`).

If #1217 has landed by the time you start, the append is the Ticket owner's resolve command. Check what `resolve-wait.ts` calls at HEAD and add the case there.

## 5. The ticket reducer

On `WaitResolved{RerunStep}`, the ticket moves to `approved` with `onSha`, beside `Approve`/`GrantFixRound` (`ticket.ts:665`). It gets no `grantRef`, and `lifecycle` gets **no new field**. `conduct.ts` knows it is a rerun from the wait's own recorded resolution: `waitsFromState(reduced).find(w => w.waitId === approvedWaitId)?.resolution?._tag === 'RerunStep'`.

So the lifecycle schema is unchanged. No stored event carries the tag yet, so no cached ticket snapshot folded it differently, and `ticket-codec.ts:172`'s `version: 2` stays.

## 6. `conductWork`: the approved branch hands its result to #1205's fields

In the approved branch (`conduct.ts:1402-1527`), when the approved wait was resolved `RerunStep`:

- **`step`** is `rerunStepOf(reason)`, not `continuationOf(...)`. `continuationOf` answers `null` for `BuildRed` and for a crash, and that `null` would end the continuation at `:1419`.
- **No grant, criterion, findings or advice.** `granted` is false, and `roundsSpent` is `continuationRound(runState, false)`. Counters come from `continuationSpent(runState)` unchanged (#1200).
- **`waive`** stays `waivedActionsAt(...)`, as for `Approve`. A rerun at `proposed` must not re-run an action an earlier approval on this run already waived. The rerun adds no waiver of its own.
- **`released`** is populated as the account branch populates it (`:1388-1400`): `runId` is the approved run, `head` is `releasedHeadOf(runEvents)` read fresh here, and `rerun` comes from `cutOffPromptOf(runEvents)`. Keep the guard `cutOff.for.step === step` (`:1360`). For `build` or `proposed`, the last call is an earlier agent's, so `rerun.for` is null, and `run-attempt` walks from that step with no recorded prompt and no agent. That is Done-when 5, and nothing check-specific is needed for it.
- **The dispatch number.** `accountReruns` is `accountLimitReleases(ticketEvents, runId)` plus the number of `WaitResolved{RerunStep}` on waits whose `reason.run.runId === runId`, this one included. `run-attempt.ts:2033-2038` makes the suffix `transientRetriesSpent + accountReruns`. Each of the three kinds raises one summand, so ids never repeat, and the first person rerun on a run with none of the others is `:rerun:1`.
- **Tell the two sources apart on `released`** with a `by: 'release' | 'person'` field, and use it in two places:
  - **`headGone`:** a head that turned out to be gone at the cut (`:3153-3156`, `:3190`) restarts the attempt **only for `'release'`** (`:5922`). For `'person'`, it holds for a person with the cut's `notCut` detail. The person chose this attempt over a restart, and a silent restart from base is exactly the cost the move exists to avoid.
  - **`expectVersion`** (`:2980`) stays the release's only. The approved path is already checked by `continueTicketEffect`'s `approved`-and-`runId` test.

Both are `Effect`s inside the existing `Effect.gen`, so they add no `async` and no `Effect.run*`.

**The unit test** is `packages/conductor/unit/conduct-continues-an-account-limit.test.ts`'s shape, with a `RerunStep` wait in place of the release. It covers Done-when 4 (a crashed `review`, same `runId`, the recorded prompt, `:rerun:1`, `roundsSpent` unchanged) and Done-when 5 (`BuildRed`: `build` again, no dispatch). No integration file is needed. Name the evidence each assertion reads:

- the continued run's `RunPrompted.for.step` and its `prompt`;
- the dispatch id the fake runtime was handed;
- `StepReached` / `StepEnded` for the step;
- the absence of any `RunSpent` on the `build` path.

## 7. CLI

`apps/cli/src/rerun.ts` copies `grant-fix-round.ts:17-71`. `--if-head` maps to `onSha`, and omitting it sends `''`, which skips the stale check as `resolve-wait.ts:328` does today. After a successful append it runs `noteConductor`'s lock sentence. Register it at the four places `grant-fix-round` is (`cli.ts:178`, `:254-273`, `:1331`, `:1422`), then regenerate `doc/cli.md`.
