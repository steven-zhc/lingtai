# Design note — #763

The ticket's file list, edges and done-when are right and are not repeated here. The checks I ran against the tree confirmed everything it cites. This note adds one decision the ticket leaves contradictory, and lists the tests that will change.

## 1. Where `waiting for your review:` goes: the preview wins

The ticket's Fix §2 says the sentence line gets "`w.words` prefix as today, when there is one, then `oneLine(w.line)`". For a held pass, `w.words` comes from `describeWait`. It returns `'waiting for your review'` whenever `awaitingSha !== null` (`packages/projector/src/task-view.ts:1106-1119`), so a held pass always has one. Following Fix §2 literally prints:

```
      waiting for your review: ready to land — the recipe asks you to approve each pass
```

The operator approved a preview without that prefix, and the ticket's Want line has none either. The done-when list would not catch the difference, because a `toContain` check passes with the prefix in front.

**Decision:** a reason whose `short` is non-null (only `SignoffRequired` today) prints `oneLine(w.line)` on its sentence line with **no** `words` prefix. "ready to land" already says what "waiting for your review" said. Every other reason keeps the prefix, as #147 asks. So the `OwnQuestion` row still reads `waiting for your answer: which approach should I take?`, and `apps/cli/unit/status.test.ts:312` still holds as written.

The status row needs `short` to make this choice. Carry it on `StatusRow.wait` next to `line` (built at `status.ts:466-482`). It is not added to `--json`: Fix §3 freezes the JSON shape, and an extra key would break that.

**Pin it:** for a `SignoffRequired` row, the rendered output has a line that equals `ready to land — the recipe asks you to approve each pass` once it is trimmed. Check that line exactly, not with `toContain`. Also assert the output does not contain `waiting for your review:`.

## 2. The empty question is handled in `waitWords`, not in status

The "render it as `ready to land`, with no dash" edge goes in `wait-words.ts`. That gives all nine callers the same sentence (#100), and the GitHub comment (`conduct.ts:4414`) never prints a trailing dash. Trim first: `reason.question.trim() === ''` gives `line: 'ready to land'`.

`raw` stays `reason.question` (`wait-words.ts:313`), as the ticket says. That means `w.raw` stays true for a hold. The CLI simply stops reading it, so that line is deleted outright, with no condition left behind.

## 3. What `--all` still prints under a signoff row

Each `SignoffRequired` produces exactly these from `describeWaitLines` (`task-view.ts:1053-1075`) via `judgement()` (`wait-words.ts:78-88`):

- `needs`: always dropped.
- `what`: equal to `line`, or `line` plus the unpushed suffix.
- `rec`: only when `step === 'merge'` and there are no findings (`wait-words.ts:312`).

It never carries `done`.

`waitDetail` returns `string[]` and loses the `part` tags (`status.ts:106-113`). So filter the strings in the render:

- Drop `your judgement is needed` and `a failure needs acknowledging`.
- Drop any string equal to `w.line`.
- For a string that starts with `w.line`, print only the rest, trimmed.

Do not change `waitDetail`'s return type for this. It is exported, the board places conflict lines with it (#656), and changing it is a wider change than this ticket.

The `a failure needs acknowledging` text itself stays as it is in `describeWaitLines`, because the board reads it too. The CLI just stops printing the `needs` line.

It becomes `'ready to land — the \`proposed\` step held: land it?'`, because the fixture's question already contains the old wording. Change the expected value and leave the fixture alone. It still proves what it is for: the note comes from the reason, not from the stale copy.
- `packages/domain/unit/wait-words.test.ts:46` (`'the \`proposed\` step held: go ahead?'`) becomes `'ready to land — go ahead?'`.
- `packages/domain/unit/ticket.test.ts:92`'s question is fixture input. Change only the assertions that read the computed line.
- `apps/cli/unit/status.test.ts:314` (`next: lingtai answer lingtai --issue 609 "<choice>"`) becomes `lingtai answer lingtai --issue 609 "<choice>"   (or the board)`. Also assert that no line starts with `next:`.
- `packages/projector/unit/__snapshots__/task-view-rebuild.test.ts.snap:402` holds an `answer` payload that is fixture data, not computed output. If the snapshot run reports no difference on that line, do not edit it. Regenerate only what vitest says changed, with `-u`, and read the diff before committing.

`packages/projector/integration/task-view.test.ts:946` is the one change nothing checks before the merge, as the ticket says. The unit check that stands in for it: `waitWords` of `SignoffRequired{step:'merge', question:'a repair is waiting on you'}` has `line` `ready to land — a repair is waiting on you`. Put that case in `wait-words.test.ts`.
