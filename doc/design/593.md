## Shape

The ticket gives the lane half. The rest of this note is the pass half, because the routing machinery is built so that this cannot be a `FixRound`.

### 1. The lane: `packages/repo/src/integrate.ts`

The check goes after the clean trial merge and before `options.verify`, which is between `:497` (end of the conflict branch) and `:499`. A conflict wins by position alone: the `conflict` refusal at `:491-495` returns first.

- **Use `-z` on both diffs.** That is the conflict branch's own reason at `:478-481`: git C-quotes non-ASCII paths in `\n` output.
- **Skip the second diff when `fork === localBase`.** That case is "the base did not move", and nothing is computed for it.
- **Put the rule in a pure exported function**, for example `baseMovedOn(ours: string[], theirs: string[]): string[]`, which returns the sorted intersection. The first *Done when* is a unit test over that function.
- **The git half is integration and cannot be checked inside a pass.** `integrate.ts` needs the `git` binary, so per 0060 §1 every test of it is integration. A test there is worth writing, but it runs after the merge. The pure function is the unit-level claim that stands in for it.
- **`refuse`** (`:241-245`) takes `conflict?` as its third argument. Add a sibling `baseMoved?: { paths; fromSha; toSha }`, and thread it out on `IntegrateResult` (`:109`) the same way.
- **Leave `IntegrationRefused`'s event payload alone** (`events.ts:1104-1109`). It carries `reason` and `detail` only, and `detail` should name the paths, as `conflict`'s does.

### 2. Thread it the way `conflict` is threaded, not the way the other seven are

`IntegrationRefused{reason}` (`domain/src/action.ts:60-63`) carries no payload. The paths and both shas would be lost at `mergeResultOf` (`step-outcome.ts:294`). So add:

- **`base-moved`** to `RefusalReason` (`vocabulary.ts:52`).
- **A `BaseMoved{paths, fromSha, toSha}` member of `Integration`**, beside `Conflicted` (`action.ts:47-58`). Add `'base-moved'` to `IntegrationRefused`'s `.exclude` at `:62`.
- **`baseMoved?`** on `LandAnswer.notMerged` (`merge-action.ts:73-76`), on `ActionResult` beside `conflict`, and in `land` (`conduct.ts:2690-2696`).
- **A `case 'base-moved'`** in `mergeResultOf` (`step-outcome.ts:279`), before the fallthrough. `RefusalReasonNoConflict` and `REFUSAL_REASONS` (`:51-63`) exclude it as they exclude `conflict`.
- **A `BaseMoved` `Proposal`**, built by `mergeRefusalProposal` (`proposal.ts:217-235`) and by `mergeCompletedRefused` (`pass-next.ts:278`). `fromOf` maps it to `'merge'`. `MergeRefused`'s and `wait.ts:135`'s `.exclude` lists gain `'base-moved'`.
- **`'base-moved'`** in `JudgeWhen` (`proposal.ts:26`), mapped by `whenOf` (`proposed-route.ts:41`).

Every total record then fails `tsc` until it has a cell. That is the point of them, so let the compiler give you the list: `INTEGRATION_OWNER` and `REFUSAL_READING` (`attribution.ts:113`, `:228`), `BUILT_IN_FOR` (`judge.ts:474`), wait-words, and wait.ts's resolutions.

- **Owner:** `INTEGRATION_OWNER['base-moved']` is not the agent. Nothing about the branch is wrong.
- **Hold row:** for a `ProposedEscalated` over `BaseMoved`, mirror `MergeRefused`'s `['Approve', 'Requeue', 'Close']` (`wait.ts:297-298`). `Approve` starts a continuation whose count is zero (see §4), so it reads as *keep merging the base in*, which is the right meaning.

### 3. The decision the ticket leaves implicit: this is a new candidate, not a `FixRound`

`FixRound.to` is `'design' | 'implement'` (`pass-next.ts:52`). `offerFor` says so in its own doc: *"No candidate ever sends `merge` back to `build`"* (`routing.ts:112-114`). And `routeProposal` spends a round on every `FixRound`: `roundsSpent = next.round` (`pass.ts:1281`). So widening `FixRound` would spend `rounds`, and the ticket's *Watch out* forbids that.

Add a fourth `CandidateNext`, and the same shape as a `PassNext` variant, because `routeNext` returns `candidate.next` as is (`routing.ts:279`):

```
{ _tag: 'MergeBase', toSha: string, merge: number }   // merge = baseMergesSpent + 1
```

**The offer.** `offerFor` gains `case 'BaseMoved'`: a candidate `id: 'merge-base'`.

- When `spent.baseMerges >= policy.baseMerges`, it goes to `unavailable` with `CeilingReached{ceiling: 'base-merges'}`.
- `Spent` (`pass-next.ts:76`), `RoutingPolicy` (`routing.ts:36`), `CeilingReached.ceiling` (`route.ts:27`) and `Ceiling` (`pass.ts:989`) each gain the field or value.
- **`policy.baseMerges` is a constant `2`** in `routing.ts`, not a recipe knob. The ticket fixes the number, and a knob would be a value somebody can set to a loop.

**The third arrival.** Only `hand-to-person` is then available, so `replyFor` answers `NotAsked` without asking anyone (`proposed-route.ts:136`). `notAskedWhy` names the spent ceiling (`:181-187`). That is the third *Done when*, with no new code beyond the cell.

**The judge.** Add a second built-in, `merge-the-base`, to `BUILT_IN_JUDGES` (`packages/recipe/src/judges.ts`).

- `BUILT_IN_FOR['base-moved'] = 'merge-the-base'`.
- `MECHANICAL_WANTS['merge-the-base'] = 'build'` (`proposed-route.ts:73`).
- `destinationOf` (`:83`) maps the `MergeBase` next, and the excluded id `merge-base`, to `'build'`.
- `judge.ts`'s `BUILT_IN` record (`:442`) is total over `BuiltInJudge`, and its vocabulary has no `build`. Give it `() => 'human'`, with a comment saying the live answer is `MECHANICAL_WANTS`. Then check that `pass-steps.test.ts`'s *the mechanical answer is `judge.ts`'s, cell for cell* still holds, or extend it to cover the new cell.
- **Refuse `judge: merge-the-base` at any `when:` other than `base-moved`** when the recipe resolves. At any other direction `toReply` finds no candidate for `build` and answers `UnknownCandidate`. That reaches a person, so it is safe, but it is a recipe line that silently means nothing.

### 4. Where the merge happens, and the third mover of `onSha`

**`runPass` owns the count.** Add `let baseMergesSpent = 0` beside `roundsSpent` (`pass.ts:1161`). Do not seed it from `options.from`: the bound is *per pass*, and a continuation is a new pass.

**The git is behind a new optional `PassOptions` port**, for example `mergeBase(toSha): Promise<{ head: string } | { failed: string }>`. `runPass` is plain and runs no git (`pass-steps.ts:63-70`). `conduct.ts` implements the port with `gitAsked` in the pass's worktree:

- `fetch origin refs/heads/<base>`, so that `toSha` is present.
- `merge --no-edit -m "Merge <base> at <toSha7> into <branch>" <toSha>`.
- `rev-parse HEAD`.

The subject cannot start with `WIP_COMMIT_PREFIX`, so the lane's guard (`integrate.ts:447`) passes it.

**Merge `toSha`, not the base's current tip.** `toSha` is what the trial merge just proved clean. If the base has moved again since, the next `merge` visit sees that and counts it, which is what the bound is for.

**Don't push here.** The ticket asks for a push, but `land` already pushes `HEAD` with `--force-with-lease` against `lease` (`conduct.ts:2648-2655`), and `lease` is the head pushed last. The merge commit is a fast-forward of that head, so the next `merge` visit publishes it. Any ending before that, such as a red `build`, publishes from the finalizer (`publishWhatIsCommitted`, `:1923`). A push here would be a third push site that has to keep `lease` in step.

**`onSha` moves through `record`, still the one writer** (`pass.ts:1218-1222`, *"the one place any of them is written"*). `StepRouted` already extends `LeftTheTreeAt` (`pass.ts:490`). In `routeProposal`:

- Compute `routeNext` before the `record` at `:1265`.
- When it answers `MergeBase`, call the port first, then record the routed visit as `{ ...routed, head }`.
- On `{ head }`:
  - set `baseMergesSpent = next.merge` and `lapStart = steps.length`, so a later fix round's `recheck` reads only the post-merge lap;
  - leave `recheck` and `roundsSpent` untouched;
  - set `at = 'build'` and `return true`.

  The walk then runs `build` → `review` → `proposed` → `merge` on the merge commit with nothing else changed. `review`'s diff is against the new base, which is what the operator asked for. The extra "what landed since" diff is the separate ticket.
- On `{ failed }`, or when the port is absent: `stopped = reported`, and `end` is `WaitOnPerson` with `ProposedEscalated{proposal, because: JudgeHandedOver{why: "the base could not be merged in: <git>"}}`. Abort the merge in the tree first. A clean merge that fails in a tree the lane just proved is a defect, and a person is the floor.

### 5. Tests (all unit)

- **The overlap rule:** over the pure function (Done when 1).
- **The route:** in `conductor/unit/`, a `runPass` with fakes, in the style of `conduct-a-whole-pass.test.ts`:
  - a `merge` action that answers `base-moved` once, then lands;
  - a `mergeBase` fake that returns a new head.
  - Assert three things:
    - the `StepStarted` sequence after the first `merge` is `proposed, build, review, proposed, merge`;
    - the second `merge` action's `ActionContext.onSha` is the fake's head;
    - `round` did not move.
- **The ceiling:** the same setup, refusing three times. The third ends `WaitOnPerson`, the fake is called exactly twice, and the `RouteTaken` excludes `merge-base` with `ceiling: 'base-merges'`.
- **`offerFor` cells** in `domain/unit/` for `BaseMoved` at 0, 1 and 2 spent.
- **Conflict still wins** is positional in `integrate.ts`, so its proof is integration. The unit claim that stands in for it: `mergeResultOf` maps `because: 'conflict'` to `Conflicted` and `because: 'base-moved'` to `BaseMoved`, never one for the other.

### 6. Not verifiable here

**Does a second `build`/`review` visit at the same `round` fold cleanly?** `StepStarted` carries `{runId, step, round}` (`pass.ts:1311-1314`), and this is the first route that revisits a step without changing `round`. Nobody has watched it happen. What settles it is the `task_view` fold and the board's step timeline: if either keys a visit by `(runId, step, round)`, the second visit replaces the first. Read the fold before relying on it, and if it does key that way, say so in the commit rather than guessing.
