# Design: #672, a finding may name its class

## The decision the ticket gets wrong: `class` is not optional in the answer schema

The ticket asks for an optional `class: string` on both `Finding` and `REVIEW_ANSWER_JSON_SCHEMA`. The answer schema cannot take an optional property. `events.ts:1066-1076` says:

> **All-required, and `about` is required but nullable rather than optional — a decision, not a quirk.** `codex exec --output-schema` is OpenAI structured output, whose strict mode refuses an optional property …

`packages/domain/unit/review-answer.test.ts:40-41` holds the finding object to five required keys. So `class` takes two shapes, the same split `about` already has:

- **`Finding` (`vocabulary.ts:127`)** is the shape stored events are parsed against: `class: z.string().optional()`. An old `StepEnded` has no key and still parses, so no upcast is needed. This change is required and not just tidy: `Finding` is a plain `z.object`, and zod drops keys it doesn't know. Without the field, a `class` written to the log would be lost on the next read, and the fix brief, which reads the findings back from the event, would never see it.
- **`ReviewAnswer` (`events.ts:1078`)** uses `Finding.strict()` today. Change it to `Finding.extend({ class: z.string().nullable() }).strict()` so that `REVIEW_ANSWER_JSON_SCHEMA` gets `class` as **required and nullable**. Update `review-answer.test.ts:40-41` to six keys and `class`. The comment at `:1062-1065` already explains why this is a derived, stricter copy, and its last sentence is the reason for `null` over absent ("`null` is a value it has to choose"). Add one line pointing at #672 there rather than a new paragraph.

## The value is lost at one more place: `normaliseAnswer`

`packages/actions/src/agent-action.ts:404-425` rebuilds each finding field by field: `file`, `line`, `claim`, `failureScenario`, `severity`. Any other key is dropped, so a schema change alone would never reach the log. Add `class` there:

- **Keep it only when it is a non-empty string after trim.** `null`, `""`, a number or a missing key all produce **no `class` key**, not `class: undefined` and not `class: null`. Spread it the way `about` is spread at `:434`.
- The reason is the Done-when line *"without one it is byte-for-byte today's output"*. That holds by construction only if an unclassed finding is the same object it is today, in the event payload and in the brief.
- Don't validate or normalise the text. That is out of scope by the ticket. Trimming is enough.

`ActionFinding` is `Finding` (`packages/actions/src/action.ts:95`), so the type follows with no second edit. `StepFinding` in `packages/domain/src/run.ts:52` is a separate interface used for the board's read. Leave it alone: showing `class` is out of scope.

## The review brief: one rule in `CONTRACT`

`CONTRACT` (`agent-action.ts:208-227`) is the rules block. Its comment (`:196-206`) says it is deliberately the last thing the reviewer reads, so put the sentence there, as a bullet right after *Say what your findings are about*. It should say:

- where the same mistake could occur elsewhere, name its class in `class` in a few words;
- list in `claim` every place in **this diff** where it occurs;
- otherwise answer `null`.

Two things to watch when writing it:

- **Phrase it as a finding, not a remedy.** The next bullet (`:221-223`) says *Do not propose the fix*. "List every place it occurs" is a finding. "And fix them" is not, so the reviewer sentence says nothing about fixing.
- **Say "in this diff".** The reviewer is the first place a repository-wide reading could creep in. If its `claim` lists places outside the diff, the fixer is handed them.

Leave `recheckBlock` (`:250`) alone. A recheck that raises the finding again carries `class` through the same `normaliseAnswer`, which is the ticket's "nothing new".

## The fix brief: in `findingsHalf`, not `fixBrief`

The per-finding rendering is `findingsHalf` (`fix.ts:653-667`), not the `fixBrief` signature at `:462`.

**For a finding with a class**, add lines to its `items` entry after `f.claim` and before the failure scenario:

- a `Class: <class>` line;
- **only on the first finding that carries that exact string**, the every-instance sentence: *this is a class of mistake: find and fix every instance of it in the diff, not only the line cited*. Later findings with the same class get just the `Class:` line.

Match class strings exactly. There is no fuzzy grouping, since the class text isn't validated.

**For a finding without a class**, the array is today's array. Build the extra lines conditionally and spread them in. Don't add an empty string that would change the line breaks.

**The scope limit goes in the sentence itself.** It is the ticket's Watch-out row, and the only place the fixer will read it is beside the finding. Say *in the diff shown below (`## The change under review`)* and *not elsewhere in the repository*. Leave the `What counts as done` criterion (`:677-692`) unchanged. The re-review is still asked about each cited scenario, and any other instance of the class is simply something the next review would otherwise find.

## Tests

All unit tests; nothing here needs the integration half.

- `packages/domain/unit/review-answer.test.ts`:
  - a finding with `class` parses through `ReviewAnswer`;
  - `class: null` parses too;
  - a finding with `class` survives `StepEnded`'s schema and comes back with the key, while one without it comes back with no key;
  - the schema's finding `required` list is six keys.
- `agent-action` unit tests (wherever `normaliseAnswer` / `parseFindings` are covered today):
  - `class: "x"` is kept;
  - `class: null` and `class: ""` produce no key;
  - pin the new `CONTRACT` sentence.
- `packages/conductor/unit/fix.test.ts`:
  - two findings with the same class contain the sentence exactly once;
  - two findings with different classes contain it twice;
  - an unclassed set equals the output of a fixture that never mentions `class`. Compare against today's string, so that "byte for byte" is checked, not just argued.

Settling it in the log, after the merge: the field is `StepEnded.outcome.actions[*].findings[*].class` on the review step. A first refusal that has the key and a fix round whose re-review raises no other instance of that class is the behaviour the ticket wants.
