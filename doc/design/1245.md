# Design: #1245 — redo a whole step from the attempt's head

## Where it goes

- **`run-attempt.ts`**: one local `redoStep(step, why, visit)` closure, next to `emitStepRedone` (`run-attempt.ts:1422`). It replaces `rerunOf` (`:1435-1455`). Both callers hand it the visit they already hold:
  - the crash path passes `{ context: visitContext, reached: visitedBefore, results }` (`:2238`);
  - the `RerunStep` case passes `lastVisit` (`:1900-1915`).
- **`kept-run-port.ts`**: a new `resetToHead({ git, plantAt })`. It is wired in `conduct.ts` where `stepRedoWaits` is passed (`conduct.ts:5546`).
- **`action.ts`**: drop `resumedAfter`, its skip loop (`:961-980`) and its strip (`:1066-1068`), and add `redo?: { why; startedAt; head }`.
- **The three briefs** render the paragraph through one exported function in `@lingtai/actions`, so the three cannot drift.

## The decisions the ticket leaves open

**1. The redo is handed the visit list from *before* the cut-off visit, never `steps`.**
Keep `rerunOf`'s `reached: visit.reached`; only its context changes. The brief's `design` and `again` are reduced over that list:
- `designOn` takes the last `design` visit (`run-attempt.ts:2407-2410`).
- `sentBackTo` reads `reached.at(-1)` and wants a `proposed` routed to this step (`:2424-2428`).

Read off today's `steps`, it goes wrong in two ways:
- After a crash, the last visit is the crashed one, so a redone fix round loses its `again`.
- After an `ask-again`, the last visit is the `RerunStep` route, which `sentBackTo` would misread as a route back to this step.

So "built as on the step's first arrival" means: `visit.context`, without `resumedAfter`, without `design` and without `recorded`, plus `rerun: n` and `redo`. `design` is then filled at `:2636-2639` by plain `designOn(reached)`, and the `rerun !== undefined` branch there is deleted.

**2. `rerun` stays on every action of a redone step. Only `redo` is stripped, after the first `agent` action.**
Today the strip fires at the first action whenever `resumedAfter` is absent (`action.ts:1066`). In a whole-step redo, that means a `run:` ahead of the agent would consume `rerun`. Two things break:
- The agent would be dispatched under its plain id. Every id is built from `context.rerun` (`action.ts:1319-1320`; `agent-action.ts:936`, `:1646`; `conduct.ts:4785`, `:5121`). The plain id is the cut-off run's, and the comment at `action.ts:525-526` says *"a reused one is refused"*.
- Every later agent in the step would be measured from the current `HEAD` instead of from where the step first started, because `firstDispatch` keys on `brief.context.rerun !== undefined`.

Every agent in the step ran before, so every one needs the suffix. The #1205 account path keeps its current rule: strip `rerun`/`recorded` at the action that `recorded.name` names. It is out of scope (#1246), so do not touch it beyond deleting `resumedAfter` from that destructure.

**3. `kept` is not on the context. `conduct.ts` reads it from `wips`.**
- WIPs are only ever made by `keepUncommittedWork` (`conduct.ts:2493`). That runs on the implementer path (`:4988`) and the fixer path (`:5300`, `:5327`), and at publish (`:2710`). No design visit makes one.
- So `ActionContext.redo` is `{ why, startedAt, head }`.
- `firstDispatch` and `fixRound` record `wips.length` when `brief.context.redo === undefined` (the step's first dispatch). On a redo they render `wips.slice(thatIndex)` shas that are not null.
- The design brief always renders with `kept` empty.

**4. Which sha is `startedAt`.**
- `redoStep` sets `redo.startedAt = visit.context.onSha`. Because the redo context *is* `visit.context`, a second redo carries the first one's value.
- `firstDispatch` on a rerun (`context.rerun`, which every agent of a redone step carries) measures from where that same agent (arrival and action name, `agentStarts`) first found the tree, so an agent that finished before the cut-off still finds its work counted; an agent that never ran reads `HEAD`. The paragraph's `began at` is the arrival's first start (`stepFirst`), never blank.
- The fixer uses `redo.startedAt` (`fixRound`'s own baseline is `brief.context.onSha`, per the comment at `:4747-4749`).
- `redo.head` is the sha `resetToHead` reads back.

**5. The reset happens after the WIP commit by construction. Keep it that way.**
`keepUncommittedWork` runs inside the dispatch, before the step returns to `run-attempt.ts`. So a reset called from `redoStep` cannot come before it. Do not move the reset into `conduct.ts`'s dispatch functions: that is the one place it could run first.

**6. `resetToHead`'s spelling is `restoreAfterReview`'s, not the ticket's literal `-e <plantAt>`.**
- Run `posix.normalize(plantAt)`, then `reset --mixed HEAD` and `checkout -- .` (as `restoreAfterReview` does: `--hard` deletes a *staged* planted file that `HEAD` lacks), then `clean -ffd -e /<escaped>`, then `rev-parse HEAD`.
- `kept-run-port.ts:26-28` says *"`-e` with a leading `/` names exactly the one path"*.
- `:237-241` says *"a single `-f` skips a nested repository"*, and the escaping is there because `-e` is a gitignore pattern.
- No `-x`, so ignored files stay.
- Each call is judged by its exit code. The answer is `{ head } | { failed: "git <verb> refused it: …" }`.
- The option is **optional** on both option interfaces, so `tsc` does not catch a missing wire. An attempt handed none ends a redo at a person with `this attempt was handed no way to reset the worktree`, never an agent on an unreset tree. The unit test helpers supply a recording stub.

**7. Waits.**
- `redoStep` reads `(options.stepRedoWaits ?? BOUNDS.stepRedoWaits)[n-1]` for every entry.
- The crash path today uses `rerunInPlace`'s `wait`, which ignores `options.stepRedoWaits` (`respond.ts:596-606`). It now keeps `rerunInPlace` only as the trigger.
- `rerunWait`'s `prepared`-only condition (`run-attempt.ts:1709-1712`) goes.
- The `ask-again` `why` at `:1733` names the wait, as the `prepared` one does.
- The order is: `emitStepRedone`, then sleep, then reset, then `at = step`.

**8. A failed reset.**
- Record a visit of the step ending `did-not-finish` with git's words.
- End as the crash path does when it gives up: `stopped = { step, ending }` and `WaitOnPerson`.
- The redo is already spent, because `StepRedone` was on the log first. `StepRedone.rerun` against the next `StepStarted` for that step settles whether a dispatch followed.

**9. A redone conflict round re-merges.**
- A conflict-round fixer stands in a `--no-commit` merge, and `keepUncommittedWork` returns early when `inConflictRound` (`conduct.ts:2495`). `reset --hard HEAD` aborts that merge.
- When `visit.context.conflictMerge` is set (`contextFor`, `run-attempt.ts:1547`), `redoStep` calls `options.mergeForConflict` with the same base after the reset.
- A failure ends as `conflictNotStarted` does at `:2026-2038`.
- When the base is already an ancestor of `HEAD` (`mergeAlreadyIn`), the fixer committed its merge before it was cut off: the reset keeps that commit and the merge is not made again.
- Add one unit case for it.

## Tests and where they live

- **The temp-repo test is integration, not unit.** The ticket's "port (temp repo)" check is the filesystem plus the `git` binary, which 0060 §1 calls integration. It belongs in `packages/conductor/integration/kept-run-port.test.ts`, beside `restoreAfterReview`'s.
- **The unit check that stands in for it** is a fake `GitHere` that records argv. It asserts the four calls and their exact arguments (no `-x`, `-e /<escaped>`), and that a failure at any call returns `failed` without making the later calls.
- **`run-attempt.test.ts:3462`** asserts `resumedAfter` is undefined. Rewrite it to assert that the injected `resetToHead` was called, and that `contexts[1]` has `redo` and `rerun: 1`.

No ADR changes: 0108 §12 and §23 already describe this, and nothing here contradicts them.
