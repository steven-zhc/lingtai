# #1176: what the change looks like

The ticket is right about the overall change. This note covers three things it does not settle: the type change, which of the three registration call sites must not go through `loadProject`, and what replaces the `read` option.

## 1. `currentRecipeEffect` becomes a thin wrapper around `loadProject`

- **The options type.** `RecipeLookupOptions` (`packages/conductor/src/projects.ts:117-121`) is currently built from `LocalRecipeOptions`. Build it from `LoadProjectOptions` (`packages/project/src/load.ts:17`, `Omit<LocalRecipeOptions, 'read'> & { store?: EventStore }`) instead, with the same `Omit` and the same three optional overrides. That one change does two things:
  - `store` appears on the options.
  - `read` disappears, and the compiler then lists every caller that still passes it.
- **The body.** Keep the `state.project` null check. Call `loadProject(project, { ...options, base, signedIn, host, hostFacts })` with the defaults it uses today, and return `.recipe`.
- **No new default store.** When `store` is absent, `loadProject` already falls back to the process log, and it opens it lazily: `options.store ?? (yield* defaultStore())` (`load.ts:20`), where `defaultStore` is the dynamic `import('@lingtai/event-store')` at `packages/project/src/state.ts:29-33`. The ticket's `projects.ts:37-38` is stale; the private `defaultLog` moved to `state.ts` in #1173. Do not add a second default in the conductor.
- **The file port is a service, not an option.** `loadProject` reads through `ProjectFiles`, a `Context.Reference` that defaults to `diskFiles` (`packages/project/src/files.ts:66-74`). Its doc says *"A service and not a parameter, so no caller holds one"*, and 0128 §7 says the same. Because it has a default value, `currentRecipeEffect`'s type stays `Effect<ResolvedRecipe, Error>` with no service requirement. If the error union does not narrow to `Error`, map it there; do not widen the signature, because every caller uses that type.
- **Update the doc comment** above `RecipeLookupOptions` (`projects.ts:73-93`). *"Read from the file every time rather than from anything stored"* is still true: the recipe is still resolved from the file (`load.ts:44`). Add that the read now also records an edit the log has not seen (0128 §6). The `recorded-recipe.test.ts` guard (`:161-190`) is not affected: it looks for reads of `recipe` off `StepsResolved` / `RecipeRecorded`, and `loadProject` reads neither.

## 2. Tests that passed `read` now provide `ProjectFiles`

`packages/conductor/unit/read-a-project-as-effects.test.ts:32-34` passes `read: () => Promise.reject(...)`. It becomes:
- `Effect.provideService(ProjectFiles, { read: () => Promise.reject(...), replace: … })`, and
- `store: createMemoryEventStore()` in the options.

Without the store, `loadProject` reads the log before it touches the file (`load.ts:21-22`) and would open the machine's log. `packages/project/unit/load-project.test.ts:39` already shows the provide pattern. The assertion stays the same: a typed failure whose message contains `disk on fire`, not a defect.

The test of an edit recorded once (Done when, second box) cannot go through the promise face `currentRecipe`, because there is nowhere to provide `ProjectFiles` to it. Write it against `currentRecipeEffect`, in `packages/conductor/unit/`:
- Use a `Map`-backed `ProjectFiles`, a memory store, `host: 'skip'`, a stubbed `hostFacts` and `signedIn`, and a fixed `home`.
- Run three reads: v1, then v2, then v2 again.
- Expect exactly two `ProjectRecipeChanged` on `prj-<name>`. The second has `by: 'file'` and v2's `sourceHash`. The third read appends nothing.

The face is the same code run through `Effect.runPromise` (`projects.ts:152-159`), so testing the Effect covers it.

## 3. The three registration resolves: two move, one must not

- **`onboard.ts:536` moves to `loadProject`.** Pass the `eventStore` the same function already gives to `registerProject` (`onboard.ts:577`).
- **`add-from-page.ts:359` moves to `loadProject`.** Pass `home`. Leave `store` to its default, since this is the board's live Add.
- **`apps/cli/src/first-project.ts:980` must not go through `loadProject`.** It resolves a draft that is not on disk yet: `read: (p) => (p === path ? Promise.resolve(previewed) : …)`, under the comment *"The recipe is still only a draft (`applySetup` is its one writer), so it is resolved over that text"*. `loadProject` reads the disk (`load.ts:25`), so it would see either:
  - no file, and fail with `RecipeMissingError`, refusing every first `lingtai init`; or
  - the old file, and record it as the person's declaration, which is false.

  Done when's first box says *no function outside `packages/project/src` calls `resolveLocalRecipeEffect` except through `loadProject`*. To meet it, give the draft resolve its own name inside the project module: a small Effect in `packages/project/src/write.ts`, beside `saveRecipeTextEffect`, which already does the same thing inline (`write.ts:136-146`, resolve over `text` for `path`, the file port for everything else). Call it from `first-project.ts`. It records nothing, because a draft is not a read.

  The file that `applySetup` then writes is recorded by whichever reader reaches it first: the next `currentRecipe` from the daemon, a board render or `doctor`. That is the ticket's own rule.

## 4. The attempt's start

At `conduct.ts:884`, change `currentRecipeEffect(options.project, options.client)` to pass `{ store }`, using the `store` bound at `conduct.ts:750`. Do not also start passing `home` there; today it uses the `stateDir()` default, and this ticket does not change that. The `catchCause` → `stage: 'recipe'` wrapper stays as it is, so a store failure is reported the same way as a bad recipe.

## Checks

Everything here is unit-level. `HOME=/nonexistent pnpm test` is what shows whether a test reaches the machine's log. A test that reaches `currentRecipe` without a `store` either fails there or reads the per-run SQLite file. So run it that way after each batch of test changes, not only at the end.

The new draft-resolve export and every changed body must be Effects, with no `async` and no new `Effect.run*`. The face list (`effect-ratchet.faces.json:130`) and the baseline do not change.
