# Design note: #957, epics in the queue

The ticket already says most of what to build. This note covers four decisions it leaves open, and one place where the split-parent path behaves differently from what you might expect.

## 1. Where `epic` goes in `considerIssue`

The order is `closed`, then `epic`, then everything that exists today (`packages/conductor/src/discover.ts:186-230`).

- **`closed` stays first.** It reads `state`, not a label, so the ticket's rule "before any label is read" still holds. A closed issue whose summary says `{5,7}` should report `closed`.
- **The comment on `epic` should say why it comes before `excluded-label`.** An epic is not something a person is holding or something whose turn has not come yet. It is never work at all, so it is the most permanent reason. The comment at `:216-219` ranks the reasons from most to least permanent. `epic` belongs above `agent:hold` on that scale.
- **Keep the `kindColors` harvest before the skip** (`:389-394`). An epic labelled `feature` still tells the board what colour `feature` is, which is the same argument the comment there makes for a held ticket.
- **Keep the `dependenciesUnread` push before the skip** (`:387`). The ticket does not change that count, so an epic still contributes to it.

`isEpic` takes `{ subIssues: { total: number; completed: number } | null }` and returns `s !== null && s.total > s.completed`. Both of these work through the same function:

- `considerIssue`, which receives a `TicketListing`
- the board, which receives an `Offered['skipped']` entry

## 2. Parsing in `toIssue` follows `dependenciesOf`

`toIssue` (`packages/github/src/client.ts:542-570`) gets two helpers next to `dependenciesOf` (`:485-493`). They follow its rule: *"Refused rather than repaired when it is not two numbers."*

**`parentOf(raw.parent_issue_url)`**
- Match `^https?://[^/]+/repos/([^/]+/[^/]+)/issues/(\d+)$` against the URL. Matching the host loosely keeps GitHub Enterprise working.
- `repository` is the `owner/repo` string. `listLinked` at `:533` already writes `repository` in the same form, so a reader can compare the two directly.
- A URL that does not match, or a number that does not parse to a positive integer, gives `null`. So does an absent, `null` or empty-string field.

**`subIssuesOf(raw.sub_issues_summary)`**
- Both `total` and `completed` must be numbers, or the result is `null`.
- Do not clamp `completed > total`. `isEpic` already reads that case as not an epic, which is the safe direction.
- Ignore `percent_completed`.

Add both raw fields to `toIssue`'s parameter type as optional and nullable, the way `issue_dependencies_summary` is typed.

`toIssue` serves the listing, `getIssue` and `listLinked` (`:533`). So `LinkedIssue` gains the two fields too. That is harmless, and do not remove them from it.

## 3. Threading the fields through

- **`TicketListing`** (`discover.ts:41-55`) gets two required, nullable keys. Copy the doc comment's reasoning from `dependencies` at `:49-53`: an optional key would let a source leave it out, and then `undefined` reads as "not an epic" without anyone noticing.
- **`TicketDetail`** extends `TicketListing`, so it inherits both.
- **`Offered.runnable`** gets `parent` and `subIssues` added from `issue`.
- **`Offered.skipped`** goes from `{ ref, reason }` to `{ ref, reason, parent, subIssues }`.
- **`passedOver`** (`:334-343`) counts by `reason` only, so it needs no change. `epic 1` appears in `lingtai status` on its own.

Places that build `Offered`-shaped or listing-shaped literals have to be updated. Use `pnpm typecheck` to find them rather than this list:
- `db-tickets.ts:179`
- `test/memory-tickets.ts:70`
- `fakeClient` in `packages/conductor/unit/discover.test.ts`
- `test/tickets-contract.ts`, if it compares whole objects
- the board's and the CLI's fixtures

`ticketedClientOf` (used at `unit/ticket-store.test.ts:293`) wraps a `GitHubClient`. Check whether it copies fields one by one. If it does, it needs both new fields, or `null` will mask whatever GitHub actually sent.

## 4. The split parent: what changes, and what must not

**Today**, a split parent whose children are still open passes discovery as runnable:
- It carries a kind label.
- `split-ticket.ts` adds no `blocked_by` from the parent to its children; its `blockedBy` is between children.

What actually holds it is the log. Its lifecycle is `blocked` (`split-ticket.ts:180`), so `selectRunnable` subtracts it. `claim.ts`'s `split-open` refusal (`:91`) is the backstop: *"A recorded child is still open, so the ticket should not have been eligible."*

**After this change**, discovery passes it over as `epic` before the log is consulted. That is the intended effect. One visible difference: `lingtai status`'s passed-over line now counts it, where before it was silent.

**Once every child closes**, the summary reads `{n,n}`. Discovery offers the parent as before, and `claimTicket` reaches `split-done` (`claim.ts:90`) and closes it. The discovery test for `{7,7}` with a kind label covers this.

**Do not remove `split-open` or `split-unreadable`** as now-unreachable:
- `claim.ts:134-138` deliberately reads the numbers the split *recorded*, "never GitHub's sub-issue list, which a person may have added to by hand".
- The summary counts that list, so the two can disagree. One example: a person detaches a still-open child. The summary then says `{k,k}` while the recorded child is still open.
- Keeping both checks is correct. The summary only decides what is offered, and the recorded split decides what is closed.

The reverse disagreement is also intended: a person attaches an extra open sub-issue by hand. The parent stays an epic and is never claimed until that issue closes. This is the ticket's rule (*open* sub-issues, whatever their origin), not a regression.

## Tests

All of these are unit tests. Nothing here needs `pnpm test:integration`.

- **`toIssue`:** its cases from the ticket go wherever `dependenciesOf` is unit-tested today (`packages/github/unit/`). Exercise them through the client's mapping with a stub transport, not by exporting the helpers.
- **Discovery:** in `discover.test.ts`, add:
  - a `{5,7}` ticket, skipped as `epic` and carrying `subIssues` on the skip
  - a `{5,7}` ticket that is also labelled `agent:hold`, skipped as `epic`
  - `{7,7}`, `{0,0}` and `null` tickets with a kind label, all runnable
  - a closed `{5,7}` ticket, skipped as `closed`
- **Board:** `NOT_OFFERED` is a `Record<SkipReason, string>`, so `tsc` enforces the new `epic` entry. Do not add a separate test for it.
