## Design: #1315, a PR resolution review's minors become backlog entries

### Where it goes

**The projection, `packages/projector/src/backlog.ts`.** In the `default` branch (`:228-260`), choose the finding's subject before the `finding_backlog_run` lookup:

- `parsePrStream(event.streamId)` (`packages/domain/src/streams.ts:133`) answers a PR → the subject is that PR, with no link lookup.
- Otherwise → the ticket path, as today.

Nothing else is needed to *see* these findings:

- **`findingsRaisedOf` already reads them.** It does not look at the stream (`packages/domain/src/read-model.ts:183-199`). #1313 appends with exactly that in mind (`packages/conductor/src/pr-resolve.ts:395`: *"On the PR's stream with the run id the review's spend names, so `findingsRaisedOf` reads its minors unchanged"*).
- **`on_sha` is already the resolution commit.** Each reviewer action carries `onSha: sha` (`pr-resolve.ts:459`). Proposals cite `entry.onSha` as the resolution and need no new column for it.
- **`run_id` is already filled.** It is `pr-{project}-{n}:review:{merging}:{short commit}:{round}` (`pr-resolve.ts:503`).

**Rows from a review round that refused.** A refused round's `StepEnded` still carries any reviewer action that answered `accepted` (`pr-resolve.ts:475-482`). `findingsRaisedOf` takes those per action, exactly as for a ticket's step. So with two reviewers, where one refused and one accepted, the accepting reviewer's minors are filed. That is today's ticket behaviour, not a new rule. Do not add a "the whole round passed" filter.

### The row and the type

- **Columns.** `issue` and `task_id` lose `not null`. Add `pr_stream text` and `pr_n integer`.
  - Map the new columns in both stores' row mappers: `postgres.ts:99-105` and `sqlite.ts:280-286`, plus the twin comment at `sqlite.ts:362`.
- **`BacklogEntry` (`backlog.ts:82-88`).** Make the subject a field rather than two nullable strings readers must check:
  - `issue: string | null`, `taskId: string | null`, `pr: { stream: string; n: number } | null`.
  - Add one helper next to the type, `subjectOf(entry)`, answering `{ kind: 'ticket', issue, taskId } | { kind: 'pr', stream, n } | { kind: 'unknown' }`.
  - Every reader switches on it. That is how *"a reader that meets a null subject on both sides says unknown subject"* stays in one place instead of four.
- **One subject per row.** The reduce writes exactly one subject, and a unit test asserts it on a row. No SQL `check` constraint: the shape check compares columns only, and a constraint is something no drift report would name.

**Why the shape change is safe to roll out.** Adding `pr_stream` and `pr_n` is what makes the old table *detectably* stale. `start()` fails a drifted projection with `ProjectionShapeError` (`packages/projector/src/projection.ts:300-301`). The nullability change alone would be invisible: the drift is column-level (`packages/projector/src/shape.ts:193`). The first PR row would then fail with a not-null violation instead, as the misleading *"subscription stopped before it caught up"* that `store.ts:182-189` describes. So keep the two new columns as columns. Do not encode the PR inside `issue`.

### The key

Call `findingKey({ issue: event.streamId, step, action, file, claim })`. The slot carries the stream id `pr-{project}-{n}`, not the bare `n`.

- A ticket's slot holds its issue number as a string, so `"7"` versus `"pr-p-7"` cannot collide between ticket 7 and PR 7.
- `findingKey` itself is unchanged (`packages/domain/src/backlog.ts:25-40`), so every ticket key stays byte-identical.

### The readers

`tsc` will list every reader once the fields are nullable.

- **`proposalFor` (`packages/conductor/src/backlog.ts:133-160`).** It is pure, and the entry does not carry the PR's branch, `main`, or code-host number. **Decision: these are read when the entry is decided, not stored in the row.**
  - `proposalFor` takes an optional fourth argument, `pr: Pick<PrState, 'branch' | 'main' | 'prBranch' | 'host'> | null`.
  - The deciding Effect reads it with `readPr(entry.project, entry.pr.n, events)` (`packages/project/src/pr.ts:56`; conductor already imports `@lingtai/project`, `pr-resolve.ts:24`).
  - Why at decision time: the code host number arrives with `PrDraftOpened` (`PrState.host`, `packages/domain/src/pr.ts:46`), which can come after the review. Reading it then cites the number the PR has now. It also keeps the projection reading only its own event, as `backlog.ts:146-149` requires.
  - If the read fails or answers null, the proposal still cites `pr-{project}-{n}` and the resolution sha and leaves out the branch line. A missing branch never refuses the accept.
- **The decided detail at `:363`.** It names `ticketStream(entry.project, entry.issue)`. For a PR it names `entry.pr.stream`.
- **`apps/cli/src/backlog.ts`.**
  - `:84` prints *raised resolving PR <n>'s merge with main*.
  - The title lookup at `:177-180` is skipped for a PR entry. It is keyed `project#issue` and would ask for `p#null`.
- **`apps/board/src/app/backlog/page.tsx:37`** renders plain `PR <n>` (the link is #1320's).
- **`apps/board/src/lib/landed.ts:271-273`** needs no change. It filters on `task_id`, a PR row's is null, and so it never matches. Leave it.

### Rollout: drain, rebuild, start

The ticket's *"rebuild after the daemon restarts"* cannot be done literally:

- A daemon on the new code fails `finding_backlog`'s start on drift.
- `lingtai projection rebuild` refuses while that daemon holds the conductor lock.

So the order for the PR description is:

1. `pnpm lingtai shutdown "…"` and wait for the drain.
2. From the checkout at the merged `main`, run `pnpm lingtai projection rebuild finding_backlog`.
3. Start the daemon (or `lingtai service start`).

`lingtai restart` does not fit, because it drains and starts with no step between. The rebuild replays the whole log, so the minors #1313 has already recorded become entries then.

### Tests

All of these are unit tests: the memory event store plus the SQLite projection store, as the existing backlog projection unit tests use (find them next to `packages/projector/unit/drift.test.ts`). None needs `pnpm test:integration`.

- A `StepEnded` on `pr-p-7` with two minors gives two rows:
  - `pr_stream = 'pr-p-7'`, `pr_n = 7`, `issue` and `task_id` null.
  - No `RunStarted` anywhere in the fixture.
- The same file and claim again on `pr-p-7` in a later round: one row. On `pr-p-8`: two rows.
- A `pr-` stream id that does not parse files nothing.
- `proposalFor` with a PR entry plus a `PrState` slice:
  - The body contains the PR number, `prBranch`, the host number and `onSha.slice(0, 12)`.
  - It contains neither `#null` nor `ticket:`.
  - With `pr = null` it still names the PR stream.
