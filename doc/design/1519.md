**Design note for #1519: init's findings judge on a rerun**

**Where it goes.** All of it is inside `askAgents` in `apps/cli/src/agents.ts`. `leftoverRefusal` keeps its signature and its body. The fix is in what `askAgents` passes it: one more `editedInPlace` entry, plus one more `RecipeChange`. Don't add a special case for the judge inside `leftoverRefusal`'s walk. Its doc comment already says what `editedInPlace` is for: it "names the one action within a step this write edits where it stands" (`agents.ts:76-78`). Once the judge is in that list, the walk passes over it by the existing `continue` at `agents.ts:94`. The "fix or remove that one by hand" refusal (`agents.ts:121-125`) stays in force for every other entry.

**Which entry counts as init's.** Take the first entry in `steps.proposed` that `isFindingsJudge` matches. It is init's only if its `judge` equals `writingAgent`. Do not search for the first findings judge that names the writer, because the conductor only ever reads one entry: `judgeDeclaredAt` returns the first action with `'judge' in action` and a matching `when` (`packages/conductor/src/judge.ts:106-111`). `findingsJudgeChanges` adds nothing when "a `findings` judge is already there" (`answers.ts:89`), so init never writes a second one. If the first findings judge names another runtime, a person chose it, and it governs the pass. Any later entry that names the writer is dead weight a person wrote, and it is logged or refused as it is today. This rule also settles the ticket's "two findings judges both naming the writer" edge.

- Put the lookup next to `findAgentAction` (`agents.ts:59-64`) as a sibling with the same `{ index, action } | null` shape.
- Read `steps.proposed` off `at.draft` the same way `reviewList` is read (`agents.ts:236`).
- Export `isFindingsJudge` from `packages/recipe/src/answers.ts:70` as it is. `packages/recipe/src/index.ts:1` already does `export * from './answers.ts'`, so the CLI imports it from `@lingtai/recipe` next to `isImplementOnlyAgent` (`agents.ts:28`).
- `writingAgent` is already computed at `agents.ts:239-243`: the first `steps.implement` `agent:`, or `runtime.agent`. When it is `null`, nothing is recognised.

**When to skip it, and when to rewrite it.** Both happen in one branch, after the writer answer and before the `leftoverRefusal` call at `agents.ts:346`. Let `judgeAction` be the entry found above.

- **Writer unchanged** (`writer === writingAgent`): push `{ step: 'proposed', index }` onto `editedInPlace` and write no change.
  - Signed in, this removes the "also names judge codex" line.
  - Signed out, it removes the "kept as written" line (`agents.ts:114-119`). That is safe: the entry names the kept writer, which #1473's `keptRuntimes` (`agents.ts:342`) would have let through anyway.
- **Writer changed and not implement-only** (`!isImplementOnlyAgent(writer)`): push the `editedInPlace` entry, and push `{ path: ['steps', 'proposed', index, 'judge'], value: writer }` onto `changes`.
  - Use `changes`, not `modelChanges`. `recipe-flow.ts:575` writes `changes` through one `writeOrRefuse`, so `runtime.agent` and the judge land together or not at all.
- **Writer changed to an implement-only agent**: don't push anything. The entry stays in the walk, which logs or refuses it as today. This mirrors the refusal in `answers.ts:88`. `signedInIds` filters out implement-only ids (`agents.ts:212`), so this branch is defensive and should never be reached.

This is the ticket's Watch out turned into a condition: an entry goes into `editedInPlace` only when it either already names the runtime this write keeps, or this write rewrites it.

**Decisions the ticket leaves open:**

- **Only `judge` is rewritten.** Init never writes `model:` or `limits:` on this entry (`answers.ts:93`). If a person added a `model:`, leave it alone, as the ticket's rule reads only `judge` and `when`. Clearing it would be a second guess about an entry the ticket already calls init's. A stale model is the same risk `steps.implement` already has when a hand-written `model:` sits beside a changed writer and the model answer is kept. It is not new here.
- **The reviewer answer has no effect on this entry** (out of scope). Even when `reviewer === 'none'`, only `steps.review` is replaced (`agents.ts:337`), and `proposed` is never in `fullyReplaced`.
- **Where the change sits in `changes`.** Push it after the `runtime.agent` change (`agents.ts:378-380`). The order doesn't matter to `writeOrRefuse`, but it does matter to any test that compares `changes` with `toEqual` on the whole array. Read the existing tests at `agents.test.ts:329-435` before you choose an assertion style. Prefer `toContainEqual` for the new path, so a later change elsewhere in `changes` doesn't turn these tests red.
- **Comments.** Update the comment at `agents.ts:328-332`. It says "Only the first `agent:` entry in `steps.implement` and in `steps.review` is ever rewritten below", and that is no longer true. Name #1519 and the `judgeDeclaredAt` reason for taking the first findings judge.

**Tests.** Everything is unit-level and lives in `apps/cli/unit/agents.test.ts`, using the same fake `QuestionWorld` and draft the "left as written" tests at `:336` and `:419` use. Use the fixture `findingsJudgeChanges` actually writes: `{ name: 'send findings back to the writer', judge: <writer>, when: 'findings' }`, not one written by hand. Nothing needs `pnpm test:integration`. The claim that `lingtai add` behaves the same rests on `add-github.ts:546` reaching the same `askAgents`, and needs no separate test.

On top of the four tests the ticket asks for, add one for the case the first-entry rule decides: a first findings judge naming `claude-code` and a second naming the writer `codex`. Expect the first to be left alone and not rewritten when the writer changes, and the second to be logged.

**What settles it after the merge.** After the merge, the 0.16.0 acceptance rerun settles it. The second `lingtai init --github steven-zhc/comic-r2` should print `init  comic-r2  unchanged` and no `also names judge` line, and the `init` exit carries no change under `steps.proposed`. No event is involved, because this is the CLI's in-memory draft and nothing is appended to the log.
