# Design note: #679, store each run's estimate and kind in `spend`

## The fold cannot import the snapshot reader where it lives today

`readRateSnapshot` lives in `packages/conductor/src/rate-snapshot.ts:62`. `@lingtai/conductor` depends on `@lingtai/projector` (`packages/conductor/package.json:53`), so `spend.ts` cannot import it without making a cycle. Projector already depends on `@lingtai/domain` and `@lingtai/env` (`packages/projector/package.json:15-19`), so the read half can move down with nothing new added:

- Move `home`, `snapshotPath`, `readJson` and `readRateSnapshot` (`rate-snapshot.ts:31-65`) into a new `packages/projector/src/rate-snapshot.ts`. Export `readRateSnapshot`, plus the directory helper that `notePath` and `realRatePorts.write` still need.
- Keep the *"Under a test with no `LINGTAI_HOME` of its own the snapshot reads empty"* guard (`rate-snapshot.ts:31-35`) as it is. It is why no test prices from a developer's real file.
- Conductor's `rate-snapshot.ts` keeps the fetch, write and note half. It imports the read half from `@lingtai/projector` and **re-exports `readRateSnapshot`**, so `apps/cli/src/doctor.ts:56` and `packages/conductor/unit/rate-snapshot.test.ts:10` keep their import path.

## The fold takes the snapshot as a port

The first Done-when needs a fold that prices from a snapshot row in a unit test. Writing a temp `rates.json` under a `LINGTAI_HOME` would be the filesystem, so that test would no longer be unit (0060 §1).

- Make `spendProjection` (`spend.ts:57`) the result of a factory: `spendProjectionWith({ snapshot: () => readonly RateRow[] })`.
- Export `spendProjection = spendProjectionWith({ snapshot: () => readRateSnapshot() })`. Every caller keeps using that name: `apps/board/src/lib/spend.ts:229`, `apps/cli/src/projection.ts:11`, `apps/cli/src/doctor.ts:104`, `packages/projector/test/contract.ts:718`.
- Tests pass a literal array to the factory. They run on `openSqliteProjections(':memory:')`, the same way `unit/spend-rebuild.test.ts:5-8` already does.

Inside `apply` (`spend.ts:103`):

- Read the snapshot **at most once per `apply(events)` call**, lazily, and only when the batch contains a `RunSpent` whose `costUsd` is null. A rebuild folds the whole log, and reading the file once per row would make it pay that cost on every row.
- `readRateSnapshot` already returns `[]` for an absent or malformed file (`rate-snapshot.ts:46-53`). That covers the *unreadable during a fold* edge, so add no try/catch.
- Call `estimateRow({ at: event.at, usage: d.usage }, snapshot)` (`packages/domain/src/rate-card.ts:125`) unchanged. It prices by the row's own `at` and reads no clock.
- When `costUsd` is not null, do not call it: `estimated_usd` and `estimate_fetched` are both null. That is the rule *"A reported figure is never repriced"* from `day-ceiling.ts:9-10`, now applied once in the fold.

## Columns

On `spend` (`spend.ts:62-79`), add:

- `estimated_usd double precision`
- `estimate_fetched boolean` (null exactly when `estimated_usd` is null)
- `kind text`

Read them in both `toSpendRow` functions:

- `postgres.ts:174` reads them as they come back.
- `sqlite.ts:332` uses `parseBool`, as it does for `task_view`'s booleans (`sqlite.ts:327`), and `Number(...)`/null for the dollar figure.

`SpendRow` (`spend.ts:205`) gains `estimatedUsd: number | null`, `estimateFetched: boolean | null` and `kind: string | null`.

An existing live table will report these as drift (`shape.ts:135-138`: a missing column on a table that exists is drift, not absent). That is what makes doctor name the required `lingtai projection rebuild spend`, so this needs nothing beyond what the ticket's Edges already say.

## `kind`: where the fold gets it

`TicketClaimed` carries `kind: z.string().nullable()` (`packages/domain/src/events.ts:213`). **`TicketContinued` does not exist in the code yet.** Nothing under `packages/` or `apps/` names it; 0109 §5 (revised 2026-10-28) only decides it. So the continuation the Done-when tests is the old form: a second `TicketClaimed` on the same stream with the same `runId` and `kind: null` (0109 §5, *"The log already holds continuations written as claims"*). Build for that form. When `TicketContinued` lands it needs no case here, because it carries no kind and its `runId` is already linked.

- **The pass stream's kind goes on the link.** Add a nullable `kind` column to `spend_stream` (`spend.ts:92-95`). In the `TicketClaimed` case (`spend.ts:118-126`), replace `do nothing` with `on conflict (stream_id) do update set kind = coalesce(spend_stream.kind, excluded.kind)`. This gives three results:
  - A claim fills the kind even if a `RunStarted` (`spend.ts:108-116`, which writes no kind) linked the stream first.
  - A continuation-as-claim, with a null kind, never clears it.
  - A second claim can never overwrite the first claim's kind.
- **The ticket's latest kind goes in its own table.** Add `spend_kind (ticket text primary key, kind text not null)`, created in `create` and dropped in `reset` (`spend.ts:98-101`). Upsert it on every `TicketClaimed` whose `kind` is non-null. A null never overwrites, which matches 0123 §3: *"A continuation carries none (0109 §5), so it never clears the kind… A ticket whose every claim has a null kind is unclassified."*
- **At `RunSpent`, the row's kind depends on the stream:**
  - Pass stream: `spend_stream.kind` for the stream, falling back to `spend_kind[ticket]`. A claim made with no queue entry carries null (`events.ts:206-209`), and the fallback names the ticket's kind rather than leaving it unclassified.
  - `ticket-…` (triage) and `chat-…` (discussion) streams: `spend_kind[ticket]`.
  - Unlinked rows (`ticket` null): `kind` null.
- The kind is read at fold time and never updated afterwards. The ticket puts relabelling out of scope.

## What stands in for the integration half

The Postgres side of the new DDL (`double precision`, `boolean`, the `on conflict … do update` upsert) is only exercised by `packages/projector/test/contract.ts` under `pnpm test:integration`, which cannot run inside a pass. The unit-level claims that stand in for it:

- the fold tests on `:memory:` SQLite, through the same `apply` SQL;
- the shape test, which recovers columns from the DDL text, so a column declared in `create` but not read by `toSpendRow` shows up only as a type error. Add the three fields to `SpendRow`, and both `toSpendRow` functions then fail `tsc` if either one forgets them.
