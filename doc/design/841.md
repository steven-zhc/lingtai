## Design note: #841, a stopped `task_view` stops claiming, not the process

### Where the code goes

**1. `packages/daemon/src/daemon.ts`: remove the exception, don't move it.**
- Delete `STOPS_THE_DAEMON` (`:80`).
- Delete `taskViewFailed` and `returned` (`:170-171`). `returned` exists only to guard the live `shutdown('projection-failed')` (`:242-247`, the comment says *"Before `returned`, the start path throws and owns the lock"*). Once that call is gone, nothing reads it.
- `onError` becomes `if (phase !== 'handler') return; void recordStopped(...)`.
- Remove the `&& projection.name !== STOPS_THE_DAEMON` test from the start loop's catch (`:270`).
- Delete the post-loop throw (`:279`).
- `StopReason` becomes `'asked'` (`:120`). Keep the type rather than turning `stopped` into `Promise<void>`: the CLI and the index export (`packages/daemon/src/index.ts:15`) use it, and a one-member union is the smallest change.
- Rewrite the header paragraph `:21-29`. It still says *"`task_view` is the exception for now: the conductor drains on it…"*. The new sentence: `task_view` stops alone like the rest, and the conductor stops claiming while it is stopped.

**2. One pure function decides "not taking work", next to `Daemon`.** Export it from `packages/daemon`. Something like:

```ts
export function notTakingWork(stopped: readonly StoppedProjection[]): string | null
```

It returns the ticket's sentence when an entry named `task_view` is in the list, and `null` otherwise. Put it in this package, not in `apps/cli/src/daemon.ts`:
- The ticket's second test drives `createWorkLoop` with a hook built from a daemon's list. `packages/daemon/unit/work-loop-stop.test.ts` already exists to show how to drive the loop without the CLI.
- The board imports `@lingtai/daemon` (`packages/daemon/src/reconcile.ts:74`: *"the board imports this package"*). So `bearing.ts` can use the same name constant instead of repeating `'task_view'`.

**3. `apps/cli/src/daemon.ts`: both hooks become one composed hook.**
- Define one local, e.g. `const claiming = async () => notTakingWork(started.daemon.stoppedProjections) ?? (await pausedSentence({ control: () => readControl(undefined, since) }))`.
- Pass it at `:551` and at `:595`. Two copies of the composition would drift, which is the #210 failure the second hook exists to prevent.
- Delete the `projection-failed` branch at `:698-702`. The process now always exits through `console.log('stopped'); return 0`.

**4. `apps/board/src/lib/bearing.ts:134-150`: one sentence, no new branch.** When `stopped` contains `task_view`, the `why` gains *not taking work*, e.g. `task_view stopped — not taking work; rebuild first: …, then lingtai restart`. Label, tone and title stay as #840 wrote them.

Add the case to `apps/board/unit/bar.test.ts`'s `EVERY_STATE` (`:60`). Its comment at `:54` says it is *"Written out rather than generated, so adding a branch to `bearing()` without…"*. This is not a new branch, but the `task_view` row is the one this ticket's test pins.

### Decisions the ticket leaves open

- **A null checkpoint.** `recordStopped` lists the entry at once with `checkpoint: null` and fills it in after a store read (`daemon.ts:203-216`).
  - So the first hook call after a live failure can see `null`.
  - In that case the sentence says *at an unread checkpoint*, the same words `bearing.ts:140` uses, not `seq null`.
  - The hook reads the getter on every call (`daemon.ts:297-299` returns a fresh copy), so later calls carry the seq. Nothing caches it.
- **Shutdown still wins.** The loop asks `shutdown` before `paused` (`work-loop.ts:514-531`: *"A shutdown is asked first, because it is the stronger answer"*). So a drain or a restart still works while `task_view` is stopped. Put the check in `paused` only, never in `shutdown`.
- **Start ordering needs no new code.** `recordStopped` pushes the entry synchronously, before its `await` (`daemon.ts:205`). So the list already holds `task_view` when `startDaemon` returns, and `loop.start()` comes later (`apps/cli/src/daemon.ts:637`).
  - Keep the existing catch-up path unchanged for `task_view`: record, `dated(...)`, `onRunner`, `continue` (`:270-273`).
  - The startup `reconcile` runs before the loop. It decides from `events`, not `task_view` (`converge.ts:213`: *"rather than from `task_view`, because reconciliation has to work when a…"*). A stale board does not change what it releases.
- **Discussions and triage are not gated.** A person's pause does not gate them either: they go through `discuss`/`triage`, not `pass`, and *"take no claim"* (`apps/cli/src/daemon.ts:539-547`). The ticket says no new *claim*, and this keeps a stopped `task_view` the same as a pause in that respect.

### Tests to change, not just add

`packages/daemon/unit/stopped-projections.test.ts:97-120` asserts the old behaviour:
- `'task_view still stops the daemon'` expects `'projection-failed'`.
- `'task_view failing at start throws out of startDaemon…'`.

Rewrite these two into the ticket's `'a stopped task_view leaves the daemon up'`, covering live and at start, and asserting that `stopped` has not resolved. Don't add the new test beside them and leave them to go red.

The *resume does not lift it* test is a unit test of the composed hook: `notTakingWork([{ name: 'task_view', … }]) ?? pausedSentence({ ceiling: async () => null, control: async () => ({ paused: false }) })` returns the sentence.

### What settles it on a live system

This can't be checked inside a pass, and `pnpm test` stands in for it. A person can check two things:
- **The log:** after the throw, no `TicketClaimed`-type claim event is appended, and no control event either.
- **The beacon:** the `stopped_projections` column lists `task_view`.

`doc/design/839.md` names `STOPS_THE_DAEMON`. It is the record of a past ticket, so leave it unchanged.
