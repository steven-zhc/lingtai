# Design note: #568, picking tool-enabled Codex triage in the recipe

## Most of this ticket was already built by #567

The ticket's evidence is older than the merge of `agent/567` (`d4cf9b86`). It says triage "forces `tools: 'none'`", but that is no longer true. Today:

- **Schema.** `Triage` has `tools: z.enum(['none', 'full']).default('none')` (`packages/recipe/src/recipe.ts:2961-2962`). It also refuses `tools: full` with any agent other than codex, with the message *"tools: full needs agent: codex — only the Codex CLI runs against a checkout"* (`recipe.ts:2989-2992`). This is pinned by `packages/recipe/unit/triage.test.ts:43-46`.
- **Wiring.** `waitTriage` works out `full = agent === 'codex' && tools === 'full'`, prepares the disposable checkout, and asks for `deps.runtime(agent, { tools: full ? 'full' : 'none' })` (`apps/cli/src/triage.ts:706-732`). This is pinned by `apps/cli/unit/triage.test.ts:274-279`.
- **Doctor.** `declaredEnvironment` already has a separate branch for `codex` + `full`. That branch writes a `triage: <p> signed in` row from the CLI login and a `triage: <p> limits` warn row. Every other codex selection goes to `codexRoleRow`, which checks `codex_text` (`apps/cli/src/doctor.ts:2198-2216`).
- **Discussion.** It is unchanged. `Discuss` is a `z.strictObject` with no `tools` key (`recipe.ts:2905`), so `discuss: { tools: full }` is already refused by name.

So the first Done-when box and the recipe half of the second are already true. **Do not rebuild them, and do not add a second key.** This change is what is still missing:

1. Doctor says which Codex route will run.
2. The board says the same, and stops presenting the CLI route's turns and dollars as limits.
3. The operator's example shows the CLI route with no `codex_text` block.

## 1. Doctor: one row that names the route

Today you can only tell which route a codex triage will take from which rows appear: `signed in` for the CLI, `codex ready` for the API. Neither row says which route was chosen. Add the route sentence to the `detail` of rows that already exist, and keep their names. `doctor-ownerless.test.ts:105-118` finds rows by name, and so may an operator's own scripts.

- **Model-only branch** (`codexRoleRow`, `doctor.ts:2097-2116`). The ok detail already says *"model-only API route ready for triage; separately billed"*. When the role is triage, add a remedy to the failing detail: `triage.tools: full` takes the Codex CLI route and needs no `codex_text`. Today, an operator who wrote `agent: codex` without the API block is only told about the API block. That is how somebody ends up writing `codex_text.approved`, which the ticket's *Watch out* forbids.
- **CLI branch** (`doctor.ts:2200-2208`). Keep the `signed in` row. Its detail should say that the route is the **Codex CLI with tools in a disposable checkout of the attempt's head**, billed to the Codex login, and that `codex_text` is not read. Keep the limits row as `warn`, but its text must match what the code does today:
  - `wall` is enforced.
  - `turns` is passed to the runtime and not enforced.
  - **`usd` is not even observed.** The CLI receipt carries `costUsd: null` (`packages/agent/src/codex.ts:24`, *"no dollars, so `costUsd` is `null` — never `0`"*). `waitTriage` only adds to `costSpent` when `outcome.costUsd !== null` (`triage.ts:897`), so the `out of usd` check at `triage.ts:827-829` can never fire on this route.

  The current text, *"turns and USD are passed to the runtime but Codex CLI does not enforce them"*, is true but understates this. The Done-when line *"whether its limits are actually enforced"* is exactly this sentence.

Unit test: add to `apps/cli/unit/doctor-ownerless.test.ts`, in the same shape as lines 88-118. Use a recipe with `triage: { agent: codex, tools: full }` and **no `codex_text` configured** (`reach.codexText` returns `undefined`). Assert that:

- there is no `triage: … codex ready` row;
- `signed in` is asked of `codex` through the injected `runtimes`, so no binary is spawned;
- the limits row is `warn` and names `wall` as enforced and `usd` as unobserved.

## 2. Board: route and enforcement, not readiness by spawn

The recipe summary row (`apps/board/src/lib/recipe.ts:893-899`) prints `agent, model, N turns, wall and $usd per hold` and ignores `tools`.

- Add `triage.tools` to `keys`.
- When `tools === 'full'`, say *Codex CLI with tools, in a disposable checkout*, and write the bounds as the wall enforced and the turns and `$` declared but not enforced.
- When the agent is codex and tools is none, say *model-only API, separately billed*.
- Leave claude-code's sentence as it is.

**The board says readiness beside the route.** An operator who selects `tools: full` on a machine with no Codex login must not see a healthy board and learn at the first failed wait. `projectRecipe` asks the Codex login probe (`codexAuth`, the one `lingtai doctor` asks) only when the recipe selects the CLI route, and appends *Codex login ready* or *NOT READY — … triage cannot run* to the triage row. That is one spawn on that page for that recipe, the same kind `currentRecipe` already makes for its sign-in detection; no other recipe spawns anything on a render. The probe is injected so a test spawns nothing.

Unit test: a board unit test on the function that builds these rows, with three cases: `codex`+`full`, `codex`+`none`, and `claude-code`. Assert the sentence and that `triage.tools` is in `keys`.

## 3. The example the operator copies

`config.example.yml:78-97` shows `triage: { agent: codex, … }` directly above a `codex_text:` block with `approved: 'true'`. This is the only written guidance for codex triage, and it leads to the billed route.

- Add a second `triage:` example with `agent: codex` and `tools: full`.
- Say in one line that it uses the Codex login and needs none of the `codex_text` block below.
- Say that `turns` and `usd` do not bind it.

Do not change the `codex_text` block itself; Discussion still needs it.

## Not this change

- **The active recipe.** `~/.lingtai/lingtai/recipe.yml` is outside every worktree and is the operator's to edit. The paste comes **after** a restart onto code that has `tools`, never before. A daemon whose `Triage` schema lacks the key would refuse the recipe every pass (CLAUDE.md, *code, restart, paste*). `tools` is already on `main`, so this only matters if a daemon older than `d4cf9b86` is still running.
- **The live wait** in Done-when 3 and 4 belongs to #530. It is settled from the log, not from tests:
  - a `WaitTriaged` for the `waitId`, carrying the head that `waitTriage` chose;
  - `RunSpent { for: Triage { waitId } }` is **not** evidence of the route: both the CLI receipt and the model-only API (`packages/agent/src/codex-text.ts:44,151`) return `costUsd: null`, and the event carries no route field. Take the route from the recipe in force when the wait ran — `triage.agent: codex` with `triage.tools: full`, which the board's triage row and `lingtai doctor` both name — and not from the receipt;
  - do not read the absence of a `codex_text` block in the config file as proof either: the same API configuration can be supplied through environment variables (`config.yml` and exported variables are the two sources).

  An agent cannot read production `events`, so leave those boxes for the operator.
- **ADR 0118 §3** still says triage runs *"with no tools"* (`doc/decisions/0118-a-hold-explains-itself.md:356`). `doc/design/567.md` already flagged this and left it to a separate ticket. Leave it. This change adds no new contradiction; the contradiction came with #567.

## Checks

Every claim above has a unit-level check: the doctor rows, the board row, and the existing recipe refusals. `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` cover all of it. Nothing here depends on `pnpm test:integration`. `apps/cli/integration/triage-checkout.test.ts` already covers the CLI route's process and git behaviour, and this change does not touch it.
