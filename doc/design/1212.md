## Design: #1212 — an account names a platform

### Upcasting is already done once, in the store

Every read goes through `parseStoredPayload` in `packages/event-store/src/event-store.ts:258`. Its comment says *"the store never hands out unvalidated data"*. That covers the board's history too, because `apps/board/src/lib/history.ts:762` formats `event.data` as the store returned it. So after the upcaster, every reader sees only `account`:

- Write no fallback that reads `d['runtime'] ?? d['account']` anywhere.
- `history.ts:454-458` becomes `need(d, 'account')`, and only that.

The bump goes in `BUMPED` (`packages/domain/src/events.ts:2767`), with a comment line for each type in the style already there:

```ts
// 2: `runtime` became `account`, which names a platform (0126 §2, #1212).
AccountLimitReached: 2,
AccountLimitLifted: 2,
```

The upcasters go in `UPCASTERS` (`packages/domain/src/upcast.ts:56`). Both events use the same step, so write it once as a named const:

```ts
1: ({ runtime, ...rest }) => ({ ...rest, account: runtime })
```

It has to work on both `AccountLimitLifted` variants: with `by` and without.

The test should call `parseStoredPayload(type, 1, { runtime: 'claude-code', … })` directly, then feed the result to the account reducer. A memory store appends at the current `SCHEMA_VER`, so it cannot hold a v1 row.

Snapshots need nothing. `packages/domain/src/account.ts:5` says the aggregate is *"reduced whole and never snapshotted"*.

### Where `Account` lives, and the one words function

`Account` goes beside `RuntimeId` in `events.ts:140`. Keep `RuntimeId` as it is: recipes, runtimes and `runtimesOf` still mean runtimes.

Put one function in `packages/domain/src/locks.ts`, exported from the package. The CLI and the board both import it, and nothing else writes these words:

```ts
accountWords(a: Account): { name: string; limit: string }
// 'github'      → { name: 'GitHub',      limit: 'rate limit' }
// 'claude-code' → { name: 'claude-code', limit: 'usage limit' }
// 'codex'       → { name: 'codex',       limit: 'usage limit' }
```

- Every sentence that today says `${x} … usage limit` builds from this function.
- The command a sentence suggests keeps the raw id: `lingtai account lift github`, never `GitHub`.
- `untilFromWords` and the `untilFrom` enum do not change. `'retry-after'`, `'ratelimit-reset'` and `'doubling'` belong to #1213.

### Wording where "the recipe uses" stops being true

Three sentences would be false for `github`, because a project uses GitHub by having an owner, not through its recipe:

| Where | Today | For `github` |
|---|---|---|
| `lock-banner.tsx:99` | `${scope}'s recipe uses ${runtime}, so it waits` | `${scope} is on GitHub, so it waits` |
| `lock-marks.ts:103` (card title) | `${project}'s recipe uses ${runtime}` | `${project} is on GitHub` |
| `lock-marks.ts:102`, `:104` (card text) | — | built from `accountWords`, e.g. `GitHub is at its rate limit until …`, `GitHub's limit passes (…)` |

Branch on `account === 'github'` next to `accountWords`; don't add a second table.

The "runs on X and still takes work" clauses are at `lock-banner.tsx:104-106` and `board.ts:608-610`. They now draw on `uses`, which is `Account[]`. They name **runtimes only**: filter to `RuntimeId`, because a project does not *run on* GitHub. If the filtered list is empty, drop ` on …` and keep the rest of the sentence.

That case can happen now. An owned project whose recipe does not resolve gets accounts `{github}` and so enters `uses` (`apps/board/src/lib/locks.ts:111`). Today it was left out.

### `accountsFor`

`packages/conductor/src/account.ts:110-124`:

- Read the recipe's runtimes as today. If `state.owner !== null`, append `'github'` to that list. Read every entry with `readAccount` as before.
- The `Effect.catch` that turns a failed recipe into `[]` stays on the runtimes branch only. The ticket's edge says why: the owner is the project's own state, not the recipe's.
- The map comes back in the order runtimes, then `github`. The banner sorts by walking `Account.options` (`locks.ts:201`), so for display the map's order does not matter.

What needs no change, apart from the widened type:

- `liftPassedAccountLimit` in the guard (`packages/daemon/src/guard.ts:126-130`) walks `before.keys()`, so it picks up `github` with no new code.
- `reachAccountLimit(store, runtime, …)` at `packages/conductor/src/conduct.ts:1697` passes a `RuntimeId`, which is a subtype of `Account`. Only the parameter type changes.

### `lingtai status --json`

`apps/cli/src/ceiling-words.ts:67` writes `runtime:` into the JSON the CLI emits. Rename that key to `account` too. The ticket says no field named `runtime` may name an account, and this is the only machine-readable surface. Its test, and `status.ts:212-213`'s doc line and type, change with it.

### Help text

The help at `apps/cli/src/commands.ts:601-611` becomes: *"Says an account — a runtime, or github — is no longer at its limit."* After that change, regenerate `doc/cli.md`, and run `pnpm events:generate` for `doc/events.json` and `doc/reference.md:153`.

Everything above can be checked with `pnpm typecheck` and `pnpm test`; none of it needs the integration half.
