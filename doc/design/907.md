# #907: the shape

#905 has landed in this worktree. `DaySpendReading` carries `day: DaySpend | null` and `ceilingUsd: number | undefined` (`apps/board/src/lib/day-spend.ts:11-20`), and `page.tsx` already has `today` in scope where `<Health />` is mounted (`page.tsx:676`, `:756`). Neither line is where the ticket says any more: `<Health />` is at `:756`, not `:800`, and `Live` is at `live.tsx:305-308`. The ticket's four steps are the right ones. Four decisions are not spelled out in it, and they follow.

## 1. The sentence goes in `Live`, never in `Said`

`Said` (`live.tsx:285-303`) is shared. `Live` uses it on the home bar, and `Following` uses it on every other bar (`:276-283`). If `near` goes into `Said`, the task page has to be handed the spend too, and that page is out of scope. So `Live` takes `{ code, near }` and returns `<><Said said={bearing(...)} />{near ? <span className="near">{near}</span> : null}</>`.

That order is the ticket's: the sentence and command first, then this. It falls out of the code without any extra work. `Health` (`health.tsx:91-93`) becomes `Health({ near }: { near: string | null })` and passes it on. `near` is a plain string, so it can cross the `'use client'` boundary (`live.tsx:1`).

**`.near` must not also carry `.why`.** `.bar .why` truncates at 46ch (`globals.css:214-217`), and the reason given there is that *"the command is the part that must never be cut"*. The figures in this sentence are the same kind of thing. `.bar .near` should copy the font treatment of `.bar code`, with `white-space: nowrap`, `font-variant-numeric: tabular-nums` and `color: var(--fail)` (`--fail` is defined at `:28` and `:66`). It must not use `--signal`.

The amber guard counts only selectors that use `var(--signal` (`bar.test.ts:202-206`). `.near` will appear in `barClasses`, because the guard reads `live.tsx` (`:223`), but it does not wear amber, so `:264` stays `['.bar .head.sig']`. Add `'near'` to the list at `bar.test.ts:269`, so that a later edit that stops the guard reading `live.tsx` fails the test. The guard's regex matches `className="near"` written as a string literal (`:232`), so write it that way and not as a template.

## 2. The threshold is compared in integers

Rounding the ceiling to cents copies `ceilingReached` (`packages/conductor/src/day-ceiling.ts:134-136`, *"Reached when reported plus estimated cents are at the figure. Unknown rows count toward nothing."*). The comparison itself is:

    const ceilingCents = Math.round(ceilingUsd * 100)
    (day.reportedCents + day.estimatedCents) * 5 >= ceilingCents * 4

Do not compute `0.8 * ceilingCents`. A ceiling of `$0.07` gives 5.6 cents, and whether 5.6 rounds up or down decides whether the exactly-80% case shows. The integer form has no floating-point rounding in it, and it makes the ticket's "exactly 80%, `>=`" edge testable without a tolerance. `machineDayCeiling` only ever returns a positive number or `undefined` (`packages/env/src/index.ts:984-991`), so a zero ceiling cannot occur and needs no case.

## 3. The reported figure is `dayFigure(day)`, not a raw `$R`

The ticket writes `today $R + ~$E of $C`. The house rule is *"Never `$0.00` over unknown rows"* (`day-ceiling.ts:103`), and `dayFigure` says `no reported cost` when there are no reported runs but there are estimated or unknown ones (`:100-101`). The footer and `daySpendText` both follow that rule, and the warning should not be the one surface that breaks it. In practice that case is the likeliest one to cross 80% on a machine with no reported costs: `today no reported cost + ~$170.00 of $200.00`.

`nearCeiling` therefore returns:

    `today ${dayFigure(day)} + ~${dollars(day.estimatedCents)} of ${dollars(ceilingCents)}` + (day.unknown > 0 ? ` + ${day.unknown} unknown` : '')

- `dayFigure` comes from `@lingtai/conductor`, which `day-spend.ts:7` already imports.
- `dollars` is the board's own, `apps/board/src/lib/report.ts:211`. It is identical to the private `dollars` in `day-ceiling.ts:97`, so the ceiling prints as `$200.00`, the way `daySpendText` prints it (`:111`). Do not export conductor's `dollars` just for this.
- The unknown reasons (`unknownWhyText`) are deliberately left out. The bar is one line, and the footer and `/spend` carry the reasons.
- "Never one summed figure" can be tested directly: the output never contains the dollar string of `reportedCents + estimatedCents` when both are non-zero.

`nearCeiling(day: DaySpend | null, ceilingUsd: number | undefined)` takes the two fields separately rather than the whole `DaySpendReading`, as the ticket's signature says. It returns null when either is missing. `day-reading.test.ts` already imports `day-spend.ts` in the unit half, so the new tests go in that file.

## 4. The `Live` test is a static render

`renderToStaticMarkup(<Live code={…} near="…" />)` does not run `useFollow`'s effect, so no `EventSource` is opened. `socket` stays at its initial value and `health` is null. Check what `bearing('connecting', null, code)` returns for that state before choosing the fixtures: the "fault bearing" in the Done-when has to come from a `code` whose `wrong` is set (see `health.tsx:84-88`, `daemon N commits behind` / `lingtai restart`), not from a socket state a static render cannot reach.

If the connecting state already carries a sentence of its own, test `Said` plus `near` through a small pure helper instead of asserting on that sentence. What must be pinned is the order (`.why`, then `code`, then `.near`) and the fact that the dot's tone does not change when `near` is set.

`Following` gets no new test. It never receives `near`, and leaving that test untouched is how the task page is shown to be unchanged.

## Nothing here needs the integration half

Every claim above can be checked by the unit tests and `tsc`. `page.tsx` is a server component that passes a string to a client one, so the Next build (`apps/release/integration/build.test.ts`) has nothing new to catch. Nothing is appended to the log, so no event settles this ticket. The person's check in Done-when is the only end-to-end proof.
