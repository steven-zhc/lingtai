# Design: the PRs board (#1319)

## The shape, in one paragraph

Everything the ticket's Fix asks the board to call already exists. **Reuse it and write no second version of any of it.** The board side is four things:
- a server-only read, `apps/board/src/lib/prs.ts`;
- a pure view, `prBoard`;
- one route, `app/pr/[project]/page.tsx`, with one card component;
- three server actions.

The place line gets one more argument. Nothing new goes into `packages/*`. If something must go there (for example a shared sentence), it is an Effect, because every backend package's ratchet is at zero (`packages/domain/unit/effect-ratchet.baseline.json`).

What is already built, and what this change uses from it:

| Need | Where it is |
|---|---|
| Reduce one PR | `readPr` / `reducePr` (`packages/project/src/pr.ts:72`, `packages/domain/src/pr.ts:501`) |
| List the project's PRs | `listPrs` (`packages/project/src/pr.ts:81`) |
| The draft | `readPrDraft` (`:414`) |
| Submit | `requestPrSubmit` (`:129`) |
| More rounds | `grantPrRounds` (`:572`) |
| Check again | `requestPrRetry` (`:580`) |
| The waiting PR's view | `prWaitOf` (`packages/domain/src/pr-wait.ts:85`) |
| The step rows | `prStepRows` (`packages/domain/src/pr.ts:878`) over `inProgressStepNames()` (`packages/conductor/src/pr.ts:226`) |
| The model for every read | `prReport` in `apps/cli/src/pr.ts:157-250`, which reads all of the above. Draw what it prints, in the same words where it has them. |

## Decision 1: list by number, not by prefix

The ticket's Fix 1 lists `projectStreams('pr-'+project+'-')` and filters with `parsePrStream`. **Don't.** `listPrs` already answers this without a listing:

> *"Numbers are consecutive from 1 and found by `head` — one past the highest stream with any event — so no listing of the log … is needed."* (`packages/project/src/pr.ts:76-80`)

The numbers are consecutive by construction: `requestPrSubmit` appends at `(previous?.n ?? 0) + 1` (`:139`). This removes the Watch out's two traps (`pr-lingtai-x-3`, string order) instead of guarding against them.

The main reason, though, is agreement. **The board's "is a PR open?" must be the same answer `requestSubmit` refuses on** (`latestPr` → `listPrs`, `packages/project/src/pr.ts:94,136`). If the board read by a different method, it could enable Submit while the command refuses it.

`listPrs` itself fails as a whole when any one read fails. The ticket's edge wants one bad stream drawn in place, with the rest still drawn. So `readProjectPrs` writes the same loop in the board:
- probe `store.head(prStream(project, n))` for n = 1, 2, … until a head is 0;
- then read each stream with `readPr(project, n, eventStore)` wrapped in `Effect.either`, and return `{ n, pr } | { n, error }` per PR;
- a failed `head` is a failed listing.

With `since` (for #1321), probe to the top first, then read from the top down. Only the highest PR can be open (one at a time), so stop at the first merged PR whose `ended.at < since`.

**The Done when fixture changes because of this.** Seed `pr-lingtai-1` through `pr-lingtai-10` plus `pr-lingtai-x-3`. Assert:
- 9 comes before 10;
- `x-3` is absent;
- a project named `lingtai-x` gets its own PR 3 and nothing of `lingtai`'s.

Streams 9 and 10 alone would list as nothing, and that is correct, because a PR numbered 9 with no 1–8 cannot exist. A short comment in the test should say why it seeds 1–10.

For the draft's candidates, use exactly what the CLI uses: `readTasksEffect({ project, retentionDays: EVERY_LANDED_ROW_DAYS })` (`apps/cli/src/pr-ports.ts:255-259`, constant at `packages/projector/src/task-view.ts:1034`). `actions.ts:68` already imports both.

## Decision 2: which column each status goes in

`PrStatus` has seven values (`packages/domain/src/pr.ts:16`); the ticket names five columns.

| Status | Where it is drawn |
|---|---|
| `requested` | **The Draft card, not In progress.** The freeze has not happened, so `tickets` is still empty and the draft still holds them. Submit is replaced by *submitted*, plus the CLI's sentence picked by `conductorLockHolder()` (`apps/cli/src/pr.ts:281-289`: *it is served when a conductor runs…* / *`<holder>` is freezing it…*). Lift that ternary into one exported function the CLI and the board both call. |

> Superseded by #1409 ([1409.md](1409.md)): a `requested` PR is a `queued` card in In progress, and the board no longer draws the holder's words.
| `refused` | The Draft card carries *the last submit was refused: `<state.refusal.detail>`*, and Submit is enabled again (`isOpen` is false). |
| `in-progress` | In progress |
| `waiting` | Waiting on you |
| `in-review` | In review |
| `merged` | Merged |
| `closed` | **Not drawn.** Its tickets are back in the draft through `readPrDraft` (#1317). |

## Decision 3: the chips are the conductor's list, not the ticket's

The ticket lists the step order as *sync · build · push · open · CI · summary · ready*. **The code's order is different**, and it has eight steps: `sync, build, summary, push, open, ci, topup, ready` (`IN_PROGRESS_STEPS`, `packages/conductor/src/pr.ts:690-699`). Summary comes before the push, per 0131 §2.

Draw `prStepRows(inProgressStepNames(), pr)`: one chip per row, `done` → ✓, `waiting` → ✕, `pending` → not reached. Never draw a hand-written list.

Three chips have special words:
- `ci` with `pr.ciSkipped` set and no `checks` reads *no CI* (the CLI's rule, `apps/cli/src/pr.ts:36`).
- `summary` with a `PrSummaryNotWritten` reads *no summary: `<why>`*.
- A sync that needed nothing reads what `BranchSynced.how` recorded, never a bare ✓.

`topup` with nothing owed draws nothing. Import the names from `@lingtai/conductor` only in `lib/prs.ts`, which is server-only. The board already imports that root in `lib/board.ts:1`. A `"use client"` file must never import it (#230; only the post-merge Next build would catch it).

## Decision 4: the waiting card has more reasons than the mock

`PrWaitReason` has twelve values (`packages/domain/src/events.ts:2593-2606`). Branch on `prWaitOf`'s `kind`:

- **`conflict`** (`sync-conflict`, `sync-locked`):
  - Draw the facts the view carries: `paths`, `roundsUsed`/`roundsAllowed`, `ours`, `theirs`, `lastRefusal`.
  - `theirs[].author` is recorded, so draw it. That answers the ticket's *"draw it only if they do"*.
  - Draw `commands` as the by-hand lines.
  - **Give the agent 3 more rounds** appears only for `sync-conflict` with `commit !== null` (`apps/cli/src/pr.ts:148`).
  - Every null value reads *unknown*.
  - `prWaitOf` takes `conflictResolutions: ceilingOf(recipe).attempt.conflictResolutions` and `checkout` exactly as `waitViewOf` builds them (`apps/cli/src/pr.ts:114-119`). Move `localCheckout` and `waitViewOf` somewhere both can import, or call the same expression.
- **`plain`**:
  - The header word comes from a reason → words table in `prBoard`. Cover all twelve reasons; the test walks the enum so a new reason fails it.
  - **Check again** appears only where `view.commands.length > 0`. That is exactly the retryable set (`pr-wait.ts:11-20`). `denied`, `branch-moved`, `several-open` and `draft-unsupported` get their detail and no button.
  - CI waits add **Open the run ↗** (the failing check's `url` from `pr.checks`, picked as `ciLines` does) and **New pr-fix ticket** (#1320's link; until it lands, a plain link to a new issue with the `lingtai:pr-fix` label is acceptable).

**Spend** on the conflict card comes from `readSpendEffect({ project })` (`packages/projector/src/spend.ts:386`), filtered to `row.streamId === prStream(project, n)`, summing the reported `costUsd`. No rows read *unknown*, never `$0`.

## Decision 5: the place line stays pure

Change `viewsFor(project)` (`apps/board/src/app/place-line.tsx:32`) to `viewsFor(project, prs?: { waiting: number | null })`:
- `undefined` means solo or *All projects*: no `PRs` view.
- `waiting: null` means the read failed: `PRs` with no badge, titled *could not read the PRs*.
- `0` means no badge.
- `n > 0` gives `badge: { n, title: 'N PR(s) waiting on you' }`.

`PRs` sits between `Tickets` and `Recipe` with `key: 'P'`.

The callers compute `prs`:
- `page.tsx:794` and `:1153`;
- `recipe/[project]/page.tsx:293` and `:423`;
- `recipe-bar.tsx:42`, which gets it as a prop.

Each caller resolves the recipe (`currentRecipe`, as `actions.ts:47`), checks `modeOf(recipe) === 'team'`, and calls a cheap `waitingPrs(project)`. That function reads only the highest PR (one head probe walk, then one `readPr`) and does not reduce every merged PR on every home render.

## The actions

Add `submitPrNow({ project })`, `moreRoundsNow({ project, n, merging, commit })` and `retryPrNow({ project, n })` to `actions.ts`. Each one:
- runs the `@lingtai/project` command under `Effect.runPromise` with `actor()`, in the shape of `projectLock` (`actions.ts:663-670`);
- returns `{ ok, detail }`, with `detail` being the refusal's sentence;
- calls `revalidatePath('/', 'layout')`.

None of them waits for the conductor the way the CLI does. `Live` redraws when `PrInProgress` or `PrWaiting` lands.

The `merging` and `commit` of a grant come from the card as drawn. A page that is stale by a commit is then refused by `grantTransition` itself rather than granting rounds for a commit nobody looked at.

Mode for the `PrRef` comes from the resolved recipe. A solo recipe is refused before anything is appended, with the solo sentence.

## Tests that stand in for the visual check

These are unit tests only:
- `prBoard` over hand-built `PrState`s, starting from `emptyPr` with fields overridden.
- `viewsFor` with the four `prs` cases.
- `readProjectPrs` over `createMemoryEventStore()`. The board's `eventStore` import needs a seam, so pass the store in.
- The no-append source test: no file under `apps/board/src` names `prStream(` together with `.append(`, and none imports a `record*`/`requestPr*` except `actions.ts`.

Existing tests that assert `viewsFor`'s output, such as `recipe-bar.test.tsx`, gain the solo case and stay otherwise unchanged.
