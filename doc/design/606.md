# #606 — design note

## Where it goes

All of it is in `createClaudeCodeRuntime().run` in `packages/agent/src/claude-code.ts`, plus one test seam in `ClaudeCodeOptions` (`:318-325`). Nothing outside `packages/agent` changes. `RunOutcome` keeps its shape, and the `{ kind: 'timeout' | 'aborted' }` failure the stopped run reports today is the same one it reports afterwards.

## What it does today, and the hole

- `kill` (`:493-518`) sends `child.kill('SIGTERM')`. After 5s it sends `child.kill('SIGKILL')`, and if `close` still hasn't come after another 5s it calls `finish(killed!)`.
- The `close` handler's first line is `if (killed !== undefined) return finish(killed)` (`:543`). So the stopped run's outcome resolves as soon as the CLI's pipes close.
- The comment above `killed` (`:489-491`) says what that wait is for: *"the outcome waits for the process to be gone, because a caller that resolves on SIGTERM can restore the worktree (`#587`) while the agent is still writing to it."* `close` only shows the **CLI** is gone. A tool with its own stdio keeps running in the group and doesn't hold the pipes.

## The decision the ticket leaves open: how "the group is gone" is known

**Probe the group itself, and stop using `close` as the signal for a stopped run.** Use `process.kill(-pid, 0)`, which sends no signal and only checks the group exists. Run it on a short interval (100ms is fine), and `unref` the interval.

- **`ESRCH` from the probe** means the group is gone, so `finish(killed)`.
- **Any other result** (success, or `EPERM`) means something in the group is still alive, so keep waiting.

The bound stays as today: SIGKILL to `-pid` at 5s, then a `last` timer of one probe tick (`KILL_GRACE_MS`, 100ms) as the final backstop, so a stopped run never waits past ~5s after the stop (`:513-515`).

Why not just finish right after the SIGKILL is sent, which the ticket also allows? Because the probe costs nothing and usually answers within one tick of the SIGKILL. Keeping `last` means a group stuck in uninterruptible I/O still ends the run.

Why `close` cannot be the signal: `codex.ts:1355-1357` already says so: *"`close` waits for every holder of the pipes, so a detached tool that inherited them would keep it from ever firing"*. And a tool that *didn't* inherit them lets `close` fire too early, which is this ticket's bug. Either way `close` says nothing about the group. So for a killed run the `close` handler just returns (`if (killed !== undefined) return`) and leaves the outcome to the probe or to `last`.

Do not copy codex's marker env and process scan (`stopProcesses`, `codex.ts:1179-1184`, `:1320`). That covers processes that left the group with `setsid`, which the ticket doesn't ask about. It also means a new env var in `spawnEnvFor`, which is one of the 0007 boundaries.

### Signalling

Copy `codex.ts:1275-1287`'s `signalGroup` close to word for word: `process.kill(-child.pid, signal)`, falling back to `child.kill(signal)` when `process.platform === 'win32' || child.pid === undefined`. Keep codex's comment, reworded for Claude Code's tools.

Its `catch` has to tell the cases apart, which codex's doesn't need to:

- **`ESRCH` on the SIGTERM or the SIGKILL** means the group is already gone. That is the ticket's *Watch out*: call `finish(killed)` straight away instead of waiting for the next probe.
- **Any other error** is swallowed and the probe or the bound decides, as in codex. A throw must not escape the timer or abort handler that called it.

On the fallback path (Windows or no pid) there is no group to probe. Keep today's behaviour exactly: `finish` on `close`, with `last` as the bound. So the early return in `close` is conditional on whether the group path was taken. Keep a `grouped` boolean set in `kill`, rather than checking the platform again.

### Timers

`finish` (`:481-487`) clears `wall` and nothing else. The probe interval, `hard` and `last` all have to be cleared in `finish` too, the way codex's `finish` clears `hard` and `tracker` (`codex.ts:1253-1258`). Otherwise a run that settled at `last` keeps probing a pid number the OS may already have reused.

A clean run (no `kill`) never starts the probe and goes through the unchanged `close` path. The ticket says it stays unchanged. Don't copy codex's SIGKILL-the-group-on-every-`close` (`codex.ts:1372`); that would be a different ticket.

## The test seam: an option, not `vi.mock`

`pnpm test` runs no process. `claude-code.ts:340` says so (*"`pnpm test` runs no process"*), and that is why `claudeClose` was pulled out as a pure function. A "fake child whose group outlives it" therefore needs both the spawn and the signal injected.

Add two optional fields to `ClaudeCodeOptions`, in the style of codex's `stopProcesses?` (`codex.ts:255`, *"Replaces the scan … a test makes it throw"*):

- `spawn?: typeof spawn`, defaulting to `node:child_process`'s.
- `signal?: (pid: number, signal: NodeJS.Signals | 0) => void`, defaulting to `process.kill`.

I found no `vi.mock('node:child_process')` anywhere in `packages/agent`, so don't add the first one. An option is also what codex already does.

The test belongs in `packages/agent/unit/claude-code.test.ts`. The fake child is an `EventEmitter` with a `pid`, `stdout` and `stderr` as `PassThrough` streams, and a spied `kill`. The fake `signal` records `(pid, sig)` calls and throws an `ESRCH`-coded error (`Object.assign(new Error(), { code: 'ESRCH' })`) once the test says the group is gone. Use `vi.useFakeTimers()` and a small `wallMs`. The cases:

1. **The group outlives the CLI.** After the wall, the fake child emits `exit` and `close`, and the group probe keeps succeeding. The outcome is still pending. The calls recorded are `(-pid, 'SIGTERM')`; after 5s, `(-pid, 'SIGKILL')`. When the probe starts throwing `ESRCH`, the outcome resolves with `failure.kind === 'timeout'`. Assert it doesn't resolve before the group signal. That is the first *Done when*.
2. **`ESRCH` on the SIGTERM.** It resolves without the 5s SIGKILL ever being sent. That is the second *Done when*.
3. **An abort.** Same as case 1 through `request.signal`, with `kind: 'aborted'`. This one is cheap, and it pins the second way into `kill`.
4. **A clean run.** The child emits a receipt and `close` with no kill. `signal` is never called. This pins *a clean, unkilled run is unchanged*.

The existing integration test *turns a run that never ends into a timeout* (`integration/claude-code.test.ts:334-339`) exercises the real process-group path with a stand-in `sleep 30`. Nothing can run it inside a pass (803s). It runs after the merge, and the unit cases above are the claim that stands in for it before the merge.

## What would settle it in production

`RunFinished` for a stopped `claude-code` run. Its `durationMs` is the time at which the stop began (the outcome is built when `kill` starts), so it does not move. What moves is when `RunFinished` is appended: no earlier than the group's exit, rather than the CLI's `close`. And #587's restore event should never come before it for the same run. Neither can be read from inside a pass.

## ADRs

The change agrees with [0030](doc/decisions-archive/0030-shutting-down-safely.md) §3, which cites detaching as what makes the drain true (`:441-450`). It adds nothing that needs a new ADR.
