## Design note: #1255, own answers and recommended-first order on the Waiting page

### The one type, and where it goes

Add a single pick type to `packages/domain/src/triage.ts`, beside `TriageQuestion`:

```ts
export const TriagePick = z.union([z.string().max(TRIAGE_TEXT_MAX), z.strictObject({ own: z.string() })])
export type TriagePick = z.infer<typeof TriagePick>
```

A string is an answer id, as it is today. `{ own }` is the person's own words. Use it everywhere a pick map is typed as `Record<number, string>` today:

- `triageAnswersText`'s `picks` (`triage.ts:175`)
- `AnswerQuestions.answers`, which becomes `z.record(z.string(), TriagePick)` (`packages/domain/src/wait.ts:304-309`)
- `RequeueOptions.picks` and `RequeueHoldingOptions.picks` (`packages/conductor/src/approve.ts:357`, `:390`)
- `resolveWait`'s `picks` (`packages/conductor/src/resolve-wait.ts:149`)
- the board actions' `picks` and `answers` (`apps/board/src/app/actions.ts:192`, `:284`, `:389`)

**The own answer must also reach the `FixRefusal` and `StartNewAttempt` path, not only `AnswerQuestions`.** That is where a conflict's divergent-hunk questions go. `continueFixingCard` sends `triage.picks` (`apps/board/src/app/decide.tsx:310`, `:321`), and the decide card sends `shared.picks` (`decide.tsx:669`). The server composes from `options.picks` (`resolve-wait.ts:513`). Widening `AnswerQuestions` alone would let a person write their own answer to a `design` question but not to a hunk, and the ticket asks for both.

The CLI's `parsePicks` (`apps/cli/src/answer-questions.ts:23`) still produces strings, which are assignable to the union. Nothing there changes (Out of scope).

### Why `{ own }` and not a reserved id

An agent writes the answer ids, and `TriageQuestion` only bounds their length (`triage.ts:58-60`). Any reserved string, such as `"own"`, could be the id an agent chose. A string pick always means "look this id up", and only the object form means "write this text". That is how the Watch-out row is kept: an own answer never reaches the `answers.find` lookup at `triage.ts:186`, so it can never be reported as *triage changed since this page was drawn*.

### `triageAnswersText`

The loop at `triage.ts:184-195` branches on the pick's type:

- **A string, or no pick:** works as today.
- **`{ own }` whose text is blank after `trim()`:** return `{ ok: false, detail: \`question ${i + 1} has no answer written — write one or pick a listed answer\` }`. This message must not say *triage changed*.
- **`{ own }` with text:** the line is `- ${where}${question.text} — ${own}`. Every `\n` in `own` is replaced with `\n  ` so the rest of the text stays inside the list item. Otherwise the text is verbatim: no trim, no `cut`.

The index check at `triage.ts:177-179` is unchanged and applies to own picks too, which covers the ticket's stale-page edge.

The return's `picks` element becomes `{ index: number; answerId: string } | { index: number; own: string }`, recording the text exactly as written. The composition is still a pure function of `(cause, picks)`, so a retry writes the same section.

The same function is the page's preview. `TriagePicks` composes the body text with it (`apps/board/src/app/triage-picks.tsx:84-88`), and the comment there says *the server writes this same text for the same picks (#921)*. So the page and the server get the same own-answer rule from one place, with nothing re-implemented in the page.

### `WaitResolved.answers.picks`

At `packages/domain/src/events.ts:408`, the element becomes:

```ts
z.union([z.object({ index, answerId: z.string() }), z.object({ index, own: z.string() })])
```

A stored row has `answerId` and decodes through the first branch unchanged, so no upcast is needed. Check every reader of `answers.picks` (`rg -n "answers\.picks|answerId"`) and make each one handle the second branch. The section text is what readers show, so this should be small.

### Page state (`TriageDraft`)

`Picks` (`triage-picks.tsx:7`) gets two more maps, both keyed by question index: `own` for the triage source and `askedOwn` for the asked source. They hold the text even after the person switches back to a listed answer, so returning to *My own answer* restores what they wrote.

The selection maps keep holding an answer id, or a pick of `{ own: <current text> }`. `selected()` returns `TriagePick`. Add `setOwn(index, text, source)`, which updates the stored text and, while own is selected, the pick itself. All of this resets when `waitId` changes, as the existing maps do (`triage-picks.tsx:76-77`).

**Empty own text on the page:** `triageAnswersText` refuses, and `text` then falls to `''` (`triage-picks.tsx:88`). That would blank the body preview, so do not rely on it:

- Expose the refusal's `detail` from the draft.
- `decide.tsx` disables *Answer and continue the step* (`decide.tsx:456`) and shows the detail as its `title`.
- The `continueFixingCard` button at `decide.tsx:310-321` does the same.

The page refuses first and the composer refuses again on the server. Both are required by Done when.

### `TriageChoices`

- **Number:** the legend reads `${index + 1}. ${question.text}`. `index` is already the position in `triageQuestionsOf`'s order at every call site: `decide.tsx:439`, `standing.tsx:515`, and `standing.tsx:590`, where `index` counts divergent hunks only, the same filter as `triage.ts:157-158`.
  - The divergent `<ol>` at `standing.tsx:583` already numbers its items. Give it `list-style: none` (or make it a `<ul>`) so a hunk is not numbered twice.
- **Order:** render `[recommended, ...others]` as a sorted copy. Never mutate `question.answers`. Each radio's `value` stays its id, so the order changes nothing about what is sent.
- **Own option:** one more `label.triage-choice` after the listed answers. Its text is *My own answer*, its subtitle *Write it yourself.*, and its radio `value` is a page-only constant that is never sent. While it is selected, a `<textarea>` labelled *Your own answer* is drawn under the grid (mock `More.dc.html:70`, `:74`, `:266`).
  - Radio names are already split by source (`triage-picks.tsx:146`), so the own option needs nothing extra for that.
  - Reuse the existing `.triage-choice` classes and add only what the textarea needs (`globals.css:1260-1288`). Do not add a new colour.
