# Design: #1262: the daemon carries out triage's split

## Where it goes

Five places change. Only the first makes a decision; the other four carry it out or stop offering it.

1. **The decision**, in `actOnTriageTransition` (`packages/domain/src/ticket.ts:1376`). Today `splitTicket` returns advice only: `ticket.ts:1391` reads `if (action._tag === 'askPerson' || action._tag === 'writeSpentOnThenRedoStep' || action._tag === 'splitTicket') return advice`, and the doc comment at `:1372-1373` says *"`splitTicket` (#1262) … not built"*. The new branch sits before the head checks, because a split continues no head. It returns `[triaged, SplitStarted]` with `resolution: null`, so `finishTriage` (`packages/conductor/src/ticket/commands.ts:532`) appends both at `state.version` through its existing `appendLost` path. Nothing there changes apart from the new refusal described below.
2. **The facts the decision needs**, read by `readActContext` (`apps/cli/src/triage.ts:933`).
3. **The writer**, `splitTicketHoldingEffect` (`packages/conductor/src/split-ticket.ts:250`). It changes from "first call freezes a plan it was handed" to "carry out a `SplitStarted` that is already on the log".
4. **The daemon's two triggers**, which are the live event and the catch-up.
5. **The removals**: the board's editor and action, `Split` in `allowedResolutions`, and the brief's sentence.

## 1. The decision and its facts

Extend `ActContext` (`ticket.ts:1343`) with `split: { instance: string; kinds: readonly string[] } | null`. It is `null` when the action is not `splitTicket`, so no other path pays for the read.

Set `split` and the counter in `readActContext`:

- **`ticketSplits.used`**. Today it is hard-coded: `ticketSplits: { used: 0, allowed: BOUNDS.ticketSplits }` (`triage.ts:971`). Set it to 1 when either of these holds:
  - The ticket's stream holds a `SplitStarted` for any **other** `waitId`. One for this wait cannot exist yet, because the decision is what appends it.
  - The ticket's body carries a child marker. This is the *"or on a child"* case.
  
  Reason: 0118 §12.2 says *"The count is read from `SplitStarted` on the ticket's stream — the decision, not the finished write"*. Today the child check exists only inside the writer, at `split-ticket.ts:282-288`, and only on a first call (`first === undefined`). Once the decision appends `SplitStarted`, the writer never makes a first call, so the check has to move here.
  - Move `ANY_SPLIT_MARKER` (`split-ticket.ts:82`) into `packages/domain/src/split.ts` so both places use one regex.
  - Read the body through the `deps.issue` port that the evidence already uses (`triage.ts:830`). That port reads a `db` project's ticket too (#731).
- **A `db` project**: set `ticketSplits.allowed` to 0. `actionFor`'s `within` (`packages/domain/src/failure/respond.ts:954-957`) then answers `askPerson{limit, bound: 'ticketSplits'}` with no new branch. That is 0118 §12.1: *"A project whose tickets are in `db` is answered `askPerson(limit)` instead, with the plan shown."* Get the source from `ticketSourceOf(recipe)`, the same call the board makes at `apps/board/src/app/actions.ts:1071`. It is also where `kinds` comes from, and the `kinds` port (`triage.ts:648-654`) already resolves this recipe.
- **`instance`**: build it from the daemon's beacon row as `daemon:<pid>@<startedAt ISO>`. `memoDaemonStartedAt` (`triage.ts:531`) already reads `{pid, startedAt}` and checks that the pid is ours. Expose that pair on the ports, not just the date. Reason: `SplitStarted.instance` exists so that *"a later reader tells a writer still running from one that is gone"* (`packages/domain/src/events.ts:466-470`), and §4 below explains how the board tells.

In the transition, when `action._tag === 'splitTicket'`:

- **The plan has problems**: `splitPlanProblems(plan, {kinds})` is not empty. Return `{ ok: false, refusal: 'plan-refused', why: <describeSplitProblem joined> }`. Add `'plan-refused'` to `ActOnTriageRefusal` (`ticket.ts:1340`).
  - `finishTriage` already records `TriageFailed{why: decided.why ?? decided.refusal}` (`commands.ts:620-621`).
  - `runTriage` (`triage.ts:205-230`) asks once more while `attempt <= BOUNDS.triageRetries`, and after that the wait belongs to a person. No new retry code is needed.
- **The plan is sound**: return `[triaged, splitStarted]`.
  - Build `SplitStarted` with `actor: 'conductor'`, payload `{waitId, plan, instance}`.
  - Strip the plan exactly as `split-ticket.ts:305-313` does today. Factor that into one function so the two copies cannot drift.
  - **No `WaitResolved` goes in this append.** 0108 §6 (3) wants the decision appended before any effect, and that decision is `SplitStarted`. 0118 §12.7 wants `WaitResolved` beside `TicketSplit`, which only the writer can produce.

## 2. The writer

Make these changes in `split-ticket.ts`:

- **No `SplitStarted` for this wait means refuse.** Write *"nothing decided to split …"* and refuse, then delete `options.plan`, `onStarted` and the `first === undefined` branch (`:259-289`). That branch covered the problem check, the body read and the marker refusal; the decision now owns all three. The writer's own once-per-root guard (`:275-277`) stays as written: it is #1261's guard, and ticket item 3 keeps it.
- **Replace the `allowedResolutions(...).includes('Split')` gate at `:265`** with the predicate described under "Split" below. Otherwise the writer refuses the very split it was asked to finish.
- **Append its own `SplitStarted` only on a resume.** Today it appends one on every call (`:304`). Skip the append when the latest `SplitStarted` for this wait has the writer's own `instance` and nothing terminal after it, which is the decision's own record. Otherwise append one carrying the frozen plan, so that `splitProgressOf` reads the new attempt from its start. Several `SplitStarted` events for one wait are harmless: the count in §1 is by `waitId`, not by event.
- **The end**: `resolveWaitHoldingEffect` is called with `by: 'triage'` (today `by: options.by`, `:600`), so `WaitResolved{by: 'triage', resolution: Split{…}}` lands after `TicketSplit` in one append, exactly as `resolvedEvents` already orders them (`ticket.ts:1150-1164`).
  - `resolveWaitHoldingEffect` has no `system` option today (`packages/conductor/src/resolve-wait.ts:94-150`). Add a way to pass `system: {}` through to `resolvedEvents` from `commands.ts:417`. That records the actor as `conductor`.
  - Leave `spent` out: `ticketSplits` is counted from `SplitStarted`, not from the resolution.

**The release must not spend `newAttempts`.** With `system` set, `resolvedEvents` releases with `{ by: 'triage', newAttempt: state.newAttempts.length + 1 }` (`ticket.ts:1185-1186`). That writes `cause: NewAttempt`, and the reducer appends that to `newAttempts` (`ticket.ts:616-619`). A split is not a new attempt; 0118 §12.8 keeps even the parent's later return out of `newAttempts`.

- Give `releaseTransition`'s triage input a split form that writes `cause: null` with reason `Released by triage after a split.`. `TicketReleased.cause` is already `.nullable()` (`events.ts:305`).
- Add a unit test asserting that `state.newAttempts` is unchanged after the split's append.

### `Split` stays in the union and leaves the offer

- **Remove `'Split'` from every row of `tableResolutions`**: `packages/domain/src/wait.ts:398, 403, 431, 441, 449`.
- **Add one domain predicate, `systemSplitAllowed(state, waitId, by)`**. It is true iff `by === 'triage'` and the stream holds a `SplitStarted` for this wait. It does not consult the wait reason's table: `actionFor` decides a split from the cause alone, whatever the wait.
- **Use the predicate in the three places that check the offer**:
  - `resolveWaitTransition`'s check (`ticket.ts:1125`). This needs `by` added to its input.
  - The re-check after `prepare` (`commands.ts:403-408`).
  - The writer's gate (`split-ticket.ts:265`).
  
  A `Split` from any other `by` is refused `not-offered`, which is the *"refused (unit test)"* line in Done when. The reducer keeps accepting old `WaitResolved{Split}` rows whatever their `by`; only new appends are refused.
- **`causeResolution`** (`wait.ts:948-950`, commented *"the person's own split stays until #1262 removes it"*): map `TicketTooBig` with a plan to `EditBodyAndStartNewAttempt`. That is what 0118 §1 leaves a person whose split is spent: *"waits as `limit`, where a person edits the body or closes it."*
- **A split that a person started on old code has a board-instance `SplitStarted`.** The daemon's catch-up (§3) finishes it and resolves it `by: 'triage'`. Accept that rather than special-casing it.

0118 §1 says *"There is no `Split` resolution"*. The ticket reads this as *none a person chooses*, and the code here keeps to that reading. Put the reading in the comment on `SplitResolution` in the `Resolution` union (`wait.ts:332`). The ticket says no doc change, so the ADR is not edited.

## 3. The daemon's triggers

**Live.** Add `'SplitStarted'` to `TRIAGE_EVENTS` (`packages/daemon/src/work-loop.ts:119`). In `onWaitStarted` (`triage.ts:441`), add a `SplitStarted` branch next to the `ProjectResumed` branch.

- Fork the branch with `forkDetach`, as that branch does. The comment at `:449-450` gives the reason: a handler that has not settled within `SUBSCRIBER_TIMEOUT_MS` is reported as a failure.
- The forked fiber does three things:
  1. It returns if this process already runs a writer for the `waitId`. Keep a `Set<waitId>` on the ports. It is also the "running" fact, and it stops the writer's own resume `SplitStarted` from waking a second writer.
  2. It asks `locked(project)`. A held project is left for the catch-up.
  3. It runs `splitTicketEffect` with `by: 'triage'`, the daemon's `instance`, and a GitHub client for the project.
- `decidingEffect` (`split-ticket.ts:202`) is still the cross-process guard. A board still running old code that calls `splitCard` until it is restarted takes the same file lock, and the writer hands it the frozen plan.

**Catch-up.** Add `catchUpRegisteredSplits` next to `catchUpRegisteredContinuations`, and call it at both sites where that function is called:

- `apps/cli/src/daemon.ts:811-815`, at start.
- `daemon.ts:748-756`, after every pass, behind the same not-stopped and not-draining guard.

It also belongs in `catchUpProject` for `ProjectResumed`. The scan:

- Read the board's `blocked` cards and reduce each ticket's stream. A candidate is a ticket whose current wait has a `SplitStarted` and no `TicketSplit`, and whose waitId is not in the running set.
- **Interrupted** means the latest `SplitStarted` has nothing terminal after it. That writer is gone, because its instance is not running here. Run it now, whether at start or after a pass.
- **Failed** means the latest is `SplitFailed`. Run it only when `now − SplitFailed.at ≥ source.backoff`. Read `now` from Effect's `Clock`, so the unit test drives it with `TestClock`.
- Measure from the event, not from the daemon's own memory. A daemon restarted in a loop then cannot retry a failing GitHub more often than once per backoff, and *on start* and *on the next look* follow one rule.
- `source.backoff` defaults to `1h` (`packages/recipe/src/recipe.ts:1126`).

**Drain.** Run the writer in the daemon's scope (`forkIn` the loop's scope), not as a root fiber. A shutdown then interrupts it: `writeChild` is already `uninterruptible` (`split-ticket.ts:422`), so the child in flight is recorded, and the next start's catch-up finishes the split as *interrupted*. The writer does not hold the pass slot, so this ticket does not make a drain wait for it.

## 4. The board

- **Delete `splitCard`** (`apps/board/src/app/actions.ts:1056-1100`), the editor in `apps/board/src/app/split-plan.tsx`, and `runSplit` in `apps/board/src/lib/split-instance.ts`. Also delete `splitInstance` from that file once nothing calls it.
  - A page drawn before the change posts to a server action that no longer exists. Next answers that with an error, and the page's existing failure path shows it. Add nothing for it.
- **Change the gate on `standing.split`** (`apps/board/src/lib/task.ts:2149-2152`). Today it is `allowedResolutions(...).includes('Split')`; make it *the wait's triage answered `TicketTooBig` with a plan, or the stream has a `SplitStarted` for this wait*. Draw the plan read-only, plus `splitProgressOf`.
- **Change the `running` input to `splitProgressOf`.** Today it is `isSplitRunning`, an in-process set of the board's own. Make it *the progress's `instance` equals `daemon:<pid>@<startedAt>` from the `readStatus()` row this page already reads* (`task.ts:1805`) *and that beat is fresh* (`lastBeat`, as `apps/board/src/lib/health.ts:20` uses it). Otherwise a daemon's split always reads as interrupted.
- **When the plan is shown but no split started**, i.e. `db`, spent, or refused, the moves are the wait's `allowedResolutions`, which no longer contain `Split`.
- **The visual test** `apps/board/test/visual-waiting.ts` changes once.

**The brief.** Rewrite the line in `packages/conductor/src/triage.ts` that reads *"The plan is advice a person edits; nothing is opened until they approve it."* It should now say that the system writes the plan as given: once per root ticket, never for a child, and never for a `db` project.

## Tests (unit half; no new integration file)

| Test | What it covers |
|---|---|
| `actOnTriageTransition`, pure | sound plan → `[WaitTriaged, SplitStarted]`; problems → `plan-refused` with the described problems; `ticketSplits.used` 1 → only `WaitTriaged`, `askPerson{limit, ticketSplits}`; `allowed` 0 (`db`) → the same. |
| `readActContext` with ports doubled | `used` is 1 from another wait's `SplitStarted`, and from a body carrying a marker. |
| The writer, through `splitTicketHolding` (memory store, a `SplitClient` double) | called with the decision's `SplitStarted` already on the stream: appends no second `SplitStarted`, ends with `TicketSplit` + `WaitResolved{by:'triage'}` + a release with `cause: null` in one append. Called again after a fault injected mid-children: finds children by marker and opens no second issue for any key. |
| `resolveWaitTransition` | `Split` with `by: 'alice'` → `not-offered`; with `by: 'triage'` and no `SplitStarted` → `not-offered`; `allowedResolutions` never contains `Split` (walk every `WaitReason`). |
| `catchUpSplits` with `TestClock` | at start: an interrupted split runs. A failed split does not run until `source.backoff` has passed since its `SplitFailed.at`; then it runs once and not again within the same window. |

The decide lock is the filesystem, so `splitTicketEffect` itself stays out of the unit half, as `splitTicketHolding`'s comment already says (`split-ticket.ts:236`). No part of this needs `pnpm test:integration` to be believed.

## What would settle it on the log

- **For a live split:** `WaitTriaged` and `SplitStarted` at consecutive seqs in one append, both `actor: conductor`, with `SplitStarted.instance` beginning `daemon:`. Later, `TicketSplit` and `WaitResolved{by:'triage'}` at consecutive seqs, and a `TicketReleased` with `cause: null`.
- **For a second plan on the same root:** a `WaitTriaged` with no `SplitStarted` after it.
