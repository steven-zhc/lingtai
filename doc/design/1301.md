# #1301: running a Copilot run inside srt

## The trap: today a sandboxed Copilot run would not be sandboxed at all

`acpRun` never reads `request.sandbox`. It spawns `binary, profile.args` directly with `request.env` (`packages/agent/src/acp.ts:345`, via `spawnAgent` at `packages/agent/src/acp-session.ts:105`). The only thing that stops a sandboxed Copilot run today is the recipe refusal at `packages/recipe/src/recipe.ts:3592-3596` (*"`${value}` cannot run sandboxed yet"*). That refusal is the "interim refusal" the ticket says to remove.

**Delete that refusal in the same commit that wires the wrap, never before it.** If you delete only the refusal, the recipe resolves, the conductor builds a `RunSandbox` for the run (`packages/conductor/src/conduct.ts:1070-1105`), and Copilot runs unwrapped on the host while the pass believes it is sandboxed. No test would go red. Add a unit test for this case: a `RunRequest` with `sandbox` set, sent to `acpRun` with a fake `spawn`, must have the spawned command be the *wrapped* argv and not `copilot`.

## Where it goes

**New file `packages/agent/src/copilot-sandbox.ts`**, beside `codex-sandbox.ts`, exporting `copilotSandboxedLaunch(sandbox, run, ports)`. It returns `Effect<SandboxedLaunch, SandboxRunRefused, Scope>`, the same shape as `codexSandboxedLaunch` (`codex-sandbox.ts:112-178`). It reuses `SandboxRunRefused`, `collidingDenies` and `SandboxedLaunch` from `claude-sandbox.ts`. It does these steps in this order:

1. If `decision.kind === 'refused'`, refuse with the same sentence Codex and Claude Code use (`codex-sandbox.ts:119-121`).
2. Read the token through a port (`ports.githubToken ?? copilotGithubToken`), using `Effect.try`. A reader that throws gives a refusal carrying the reader's own sentence (`claude-sandbox.ts:162-165`). `undefined` gives the no-token refusal. **A value beginning `ghp_` also refuses before spawn**, with the same *"a classic token, which Copilot ignores"* sentence doctor uses. We know Copilot would treat it as unset and fail at `session/new`. Refusing by name costs nothing, and it is the only way the person sees the cause rather than *Authentication required* with a token visibly set. Export the sentences as constants (`NO_COPILOT_TOKEN_SENTENCE`, `CLASSIC_COPILOT_TOKEN_SENTENCE`) so doctor and the tests share them. Neither sentence may contain the value.
3. Find the Copilot home: `<run.env.HOME>/.copilot`. With no `HOME`, refuse by name, as Codex does for its home (`codex-sandbox.ts:123-127`).
4. Apply the operator's Codex profile denies, as Claude Code does (`claude-sandbox.ts:185-195`, `operatorCodexDenies` with `sandbox.codexNamed`). This rule applies to every non-Codex run (#1155, 0127 §16), and a Copilot run is one. Check `collidingDenies` against `[worktree, mirror, cache, copilotHome, ...sandbox.read]`.
5. Call `sandbox.wrap` with `caller_additions: { network: ['*.githubcopilot.com'], write: [copilotHome], read: [...sandbox.read], deny: profile.paths }`. `CallerAdditions` already carries `network` (`packages/sandbox/src/policy.ts:44`), and `runDomains` registers it per command (`policy.ts:172-173`). So the instance's allowlist does not change.
6. Build the env like this: `{ ...withoutGithubTokens(run.env), COPILOT_GITHUB_TOKEN: Redacted.value(token) }`. Delete `GH_TOKEN` and `GITHUB_TOKEN` *before* spreading, and add ours last so the recipe cannot override them (the same rule as `claude-sandbox.ts:213`). Unwrap the `Redacted` value only at that line.

**Argv.** Pass `[binary, ...profile.args, '--no-sandbox']`, and only on this path. The unsandboxed spawn keeps `profile.args` exactly as it is now. Do not put `--no-sandbox` into `COPILOT_PROFILE` (`acp-session.ts:77-86`): `probeSession` uses that profile for the auth probe and doctor (`acp-session.ts:174`), and an unsandboxed run must keep Copilot's own sandbox. That is 0127 §1's point that *none runs nested*, read in both directions.

**`acpRun`.** Branch the same way `claudeCodeRun` does (`claude-code.ts:451-494`):
- `request.sandbox === undefined` runs today's path untouched.
- Otherwise use `Effect.scoped(copilotSandboxedLaunch(...).pipe(Effect.matchEffect(...)))`, which spawns the launch's `command/args/env`.

The current `Effect.callback` body has to take a `{ command, args, env }` instead of reading `binary`/`profile.args`/`request.env` itself. Factor that body into a `runChild(options, request, launch)` as Claude Code did. The scope must stay open until the child has exited, because srt's per-command network list is cleaned up when it closes. That is why the wrap and the callback sit inside the same `Effect.scoped`. Do not add an `async` function or an `Effect.run*`: the ratchet (`packages/domain/unit/effect-ratchet.test.ts`) is the check.

**A refusal is `crash`, not `never-started`.** The ticket says *refused by name before spawn* and does not say which kind. Follow `claude-code.ts:478-481`: *"A refusal is a crash and never `never-started`: that stands the whole conductor down as an account fact (0031), and this is about the host or the project, which a person has to read."* A missing token is a machine-configuration fact, but `never-started` would pause every project, including ones that never name Copilot.

**The expired-token edge.** `session/new` answering -32000 under a sandbox is still `never-started`, because the ticket says so. At `acp.ts:564-567`, the detail becomes *"copilot refused its token (code -32000): set a fine-grained token with Copilot Requests in `copilot.github_token`…"* when the run was sandboxed, and stays `run \`copilot login\`` otherwise. Pass the "sandboxed" bit into `runChild` rather than reading `request.sandbox` again.

**Recorded invocation.** `createAcpRuntime`'s `invocation` (`acp.ts:285`) records `profile.args` and does not see the request's sandbox. Leave it. The boundary record that `recordingWrap` appends (`conduct.ts:1092`) is what says the run was wrapped and under which policy.

## `packages/env`

Add `copilotGithubToken(from, file)` and `copilotTokenState(from, path, text)` next to `claudeOauthToken` and `claudeTokenState` (`packages/env/src/index.ts:254-288`). They are line-for-line the same, using `stringAt(…, 'copilot', 'github_token')`, so `LINGTAI_COPILOT_GITHUB_TOKEN` comes through `environmentProvider` like every other key. Do not generalise the two into one parameterised reader in this ticket: the unreadable-file sentence names the key, and the tests mirror the Claude ones one for one. Add the key to `config.example.yml` with a comment:
- it must be a fine-grained token with *Copilot Requests*;
- `ghp_` is ignored;
- never paste `gh auth token`'s output.

## Doctor

Add `copilotTokenRow` next to `claudeTokenRow` (`apps/cli/src/doctor.ts:3098`), with its own reach port (`reach.copilotToken`). The port answers a small sum, `'set' | 'classic' | 'unset'` or the reader's error. It never returns the value: the `ghp_` test runs inside the reader's Effect, and only the classification leaves it. Name the row `copilot: token`, as the ticket says.

For *fail when a sandboxed project names `copilot`*, the row needs the projects. Reuse the `load()` / `recipeFor(p)` / `runtimesOf` pattern at `doctor.ts:1484-1499`, and check `resolved.recipe.sandbox?.enabled`. A recipe that cannot be resolved counts as not naming it: the `project recipes` step already reports that recipe as failed. Wire the row into the `step(...)` list at `doctor.ts:3977-3980`, after `claude token`.

## What `pnpm test` can and cannot prove

All of the above is unit-level: fake `spawn`, a fake `wrap` that records its `WrapInput`, and ports for the token and the Codex profile. Whether Copilot actually reaches `api.individual.githubcopilot.com` through srt with this token is experiment 019 E10's measurement, and nothing in `pnpm test` re-proves it. After the merge, the 0.16.0 acceptance run (`doc/milestone/0.16.0/0.16.md:76`) settles it. Read the attempt's `RunFinished` `failure` (none, versus `never-started` with code -32000), and check the boundary record for zero refused connections other than `telemetry.individual.githubcopilot.com`.
