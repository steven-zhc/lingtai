# #1362: export two sanitized Next phase spans from `OnlyScope`

All of the change goes in `apps/board/src/lib/telemetry.ts`, plus one new unit test file and three doc edits. Nothing outside the board changes.

## What the two allowed spans measure in Next 16.3.3

I read the installed `node_modules/.pnpm/next@16.3.3…/node_modules/next/dist` to find out how long each span actually lives. The two spans do not mean the same kind of thing, and that difference drives the rest of the shape.

- **`NextNodeServer.startResponse` is an instant, not an interval.**
  - It appears in `server/pipe-readable.js:75` and `:167`, as `getTracer().trace(NextNodeServerSpan.startResponse, { spanName: 'start response' }, ()=>undefined)`.
  - It fires once, on the first chunk, straight after `res.flushHeaders()` (`:63`–`:74`, comment: *"this ensures that we don't actually flush the headers until we've started writing chunks"*).
  - The callback is synchronous, so the span ends as soon as it starts.
  - **`next.start-response` therefore marks the moment the first response bytes reach the socket.** It is never a duration. The doc and the tests must say this, and that is the ticket's *Watch out* settled from the code.
- **`AppRender.getBodyResult` runs from the start of the render until React has finished it, not until the response is delivered.**
  - The live dynamic path creates it by hand at `server/app-render/app-render.js:1928`–`:1934` (*"so we can keep it open during streaming"*).
  - It ends in `allReady.finally(() => renderSpan.end())` (`:2254`–`:2256`, also `:2205`–`:2207`), under the comment *"End the render span only after React completed rendering (including anything inside Suspense boundaries)"*.
  - On an error it ends at `endSpanWithError` (`:1936`–`:1947`). That path sets `status.message` to `err.message` and records an exception event, and the copy must drop both.
  - It is **not emitted for RSC requests**. The `isRSCRequest` branch (`:1703`–`:1716`) returns `generateDynamicFlightRenderResult` and never reaches `renderToStream`.
  - So an RSC sample will show at most `next.start-response`. That is expected, not a bug.
  - A not-found re-render (`:1740`) can call `renderToStream` a second time, so one request may carry two render-body spans.

**What stays unmeasured** (this goes in the docs, and nothing gets relabelled to cover it):

- On HTML requests: from the later of render-body end and start-response to request end. That is stream delivery: write backpressure (`pipe-readable.js:88`–`:89`), `waitUntilForEnd`, and `res.end()`/`finished` (`:108`–`:116`).
- On RSC requests: the whole Flight render after the page spans.
- Client disconnect, which goes through the abort path (`:104`–`:107`, `:132`–`:134`).

**Next measurement seam** for a later ticket:

- A Node `res` `'finish'` versus `'close'` timestamp, which tells completion apart from disconnect.
- Or `BaseServer.renderToResponseWithComponents` (`base-server.js:1206`). It is not on `NextVanillaSpanAllowlist` (`constants.js:185`–`:200`), so it needs a verbose-tracing change, and its lifetime would have to be checked the same way as above.

## The decision the ticket leaves open: admission happens at request end

The request span only gets its `next.route` in the `finally` of `handleRequestImpl` (`server/base-server.js:505`, `:528`–`:535`), right before it ends. `OnlyScope` also decides whether a trace counts as measured only at that point: the request copy leaves only `if (request?.spanId === span.spanContext().spanId)` (`telemetry.ts:150`–`:152`). Both phase types end before the request does.

So the shape is **buffer at phase end, decide at request end**:

1. **Phase `onEnd`.** A span is a phase when both hold:
   - `instrumentationScope.name === 'next.js'`, and
   - `attributes['next.span_type']` is a key of `const PHASES = { 'AppRender.getBodyResult': 'next.render-body', 'NextNodeServer.startResponse': 'next.start-response' }`.

   Then:
   - Look up `#requests.get(traceId)` (`:118`). If there is none, drop the phase now: there is no known request, so nothing is buffered.
   - Otherwise build the sanitized copy straight away and push it onto `#phases: Map<traceId, { request: spanId, copies: ReadableSpan[] }>`. The map holds sanitized copies and ids only; the source span is never kept.
2. **Request `onEnd`** (the branch at `:147`). Admission happens only if both hold:
   - the request copy is being forwarded (the existing `:152` condition), and
   - `span.attributes['next.route']` is in an exact set: `'/'`, `'/task/[id]'`, `'/task/[id]/ticket'`, `'/task/[id]/sandbox'`, `'/task/[id]/attempt/[n]'`.

   If admitted, forward each buffered copy whose `request` equals this span's id. Then `#phases.delete(traceId)` either way.

   Use the exact set, not a prefix, so that a new task tab is not admitted by accident. The set matches the pages that `measure` today: `app/page.tsx:1207`, and `task/[id]/{page,ticket/page,sandbox/page,attempt/[n]/page}.tsx`. `/pr/*`, `/landed` and `/report` also call `measure`. They keep their request copy but get no phases.
3. **Parent of a copy:**
   - `next.start-response`: if its source parent is a buffered render-body copy in the same trace, that copy is the parent. Otherwise the request is.
   - `next.render-body`: always the request.

   Its real parent is whatever Next has active at that point, a span that never leaves the machine.
4. **Page spans are unchanged.** They stay under the request (`:144`). They are forwarded at their own end, before anyone knows whether a render-body will be exported. Moving them under one would mean buffering application spans as well. *Keep existing application-page parenting compatible* settles this: render-body is a sibling of the pages, not their parent.

**A phase that ends after its request is dropped.** Possible causes are a disconnect, or `allReady` settling late. The request's entry is gone by then. Keeping a record of finished requests would be the *"unbounded completed state"* the ticket rules out. An unfinished phase never reaches `onEnd`, so it emits nothing. Both cases go in the doc comment as *absent, not zero*.

## The copy

Model it on `requestCopy` (`telemetry.ts:42`–`:69`), in a sibling `phaseCopy(span, name, parent)`:

- **Kept:** the fixed mapped name, `bare()` span context (`:35`), the chosen parent through `bare()`, source `startTime`/`endTime`/`duration`/`ended`, `kind`, `resource`, `instrumentationScope`, and `status: { code }`.
- **Dropped:** every attribute (`attributes: {}`, because `next.span_name` and `next.route` from `app-render.js:1930`–`:1932` carry the page path), plus all events, links and the dropped-counts.

Keep the copy free of attributes: the name already says which phase it is.

## Bounds, written next to the fields

- `#phases` uses the constructor's existing `limit` (default 1000, `:119`) for traces, evicting the oldest first, as at `:131`.
- Each trace holds at most **4** copies. Up to two render-bodies plus one start-response is the most expected; beyond that, drop the newer phase.
- When `#requests` evicts a trace (`:131`), delete its `#phases` entry too.
- Expose a `phasesRemembered` getter beside `remembered` (`:124`) so the tests can assert cleanup.
- A request that never ends, such as SSE, holds at most 4 copies until it is evicted.
- None of this is `async`, so the Effect ratchet does not move.

## Tests

Put them in a new `apps/board/unit/telemetry-phases.test.ts`.

**Setup:** drive `OnlyScope` directly. Use a small `limit` and an inner processor that records `onEnd`, as in `telemetry.test.ts:239`–`:304`. Use a `next.js` tracer whose spans carry `next.span_type`. Set `next.route` on the request span just before `end()`, to mirror `base-server.js:531`.

**Assert:**

- Both copies leave with the mapped names, no attributes, events or links, a status code without a message, the source timestamps, and the parents described above.
- The source spans still carry their URL, message and event, as at `:186`.
- None of these leave:
  - a disallowed type (`BaseServer.renderToResponseWithComponents`);
  - a span named like a phase but without the matching `next.span_type`;
  - the right type from a non-`next.js` scope;
  - `/pr/[project]` or a route-less request;
  - a request that never held a page span.
- The state and ordering edges:
  - a phase that ends before the first page starts;
  - two page segments;
  - two interleaved traces;
  - eviction of both maps;
  - a phase that ends after the request;
  - an ERROR render-body.
- After each case, `phasesRemembered === 0`.

**Avoid:** don't pin Next source lines or any span name Next does not put in `next.span_type`.

## Docs

- **`telemetry.ts:7`–`:16`:** the header contract gains the phase exception and its route set.
- **`timing.ts:47`–`:58`:** the comment that says Next's render spans are dropped gains *except the two copies*, and *"a `measure` span describes its loader's lifetime"* stays.
- **ADR 0101 §6 tracing bullet (`doc/decisions/0101-…md:138`–`:144`):** this is an edit, not a superseding file. `doc/decisions/` is one ADR per topic, edited in place (`CLAUDE.md`), and the change extends *"The board's own read spans … follow the same rules"* rather than contradicting it.
- **Version assumption:** record "Next 16.3.3; types on `NextVanillaSpanAllowlist`" in the comment.

## What the build can and cannot check

`pnpm test`, `pnpm typecheck` and `pnpm lint` cover all of the above. Whether Next actually emits these spans to this provider in production cannot be checked before the merge. That is the operator's sample: in a Harbor trace, spans named `next.render-body` and `next.start-response` under the `GET /task/[id]` request. In the unit tests, the in-memory `next.js` spans stand in for that evidence.
