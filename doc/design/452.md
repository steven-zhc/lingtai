# #452: classify the pass's `Hold` by who sent the item to a person

## Where the change goes

The ticket says the mapping lives in `conduct.ts`. It does not. #445 moved it into `holdOfPass` in `packages/conductor/src/hold-of.ts:78-176`, so it can be tested on literals (header, `hold-of.ts:1-19`). `conduct.ts:3191-3208` (`holdFor`) only collects the inputs and calls it. **The classification changes in `hold-of.ts`. `conduct.ts` only gains two inputs to pass in.** `pass.ts` and `pass-steps.ts`'s routing do not change, and `stoppedAt` keeps its meaning.

The tests go in `packages/conductor/unit/hold-of.test.ts`, which already builds `HoldOfPassInput` literals. Every Done-when checkbox about a variant can be met there, and none of them needs a whole pass.

## The input `holdOfPass` lacks: `rested`

A red build with the rounds spent and unsatisfied findings both reach a person through the same line, `take` in `pass.ts:1343-1356`:

```ts
if (route.to === 'waiting' || route.to === 'claim') {
  rested = route.to === 'claim' ? 'requeued' : 'waiting'
  // What a person reads is the step that did not pass, never the router that
  // sent it to them; where it was sent is `routes`.
  stoppedAt = reported
```

Findings are judged on `proposed`'s way through, where `reported` is `null` (`pass.ts:1405-1412`). A red arrives from `build`, so `reported` is `{build, refused}` (`pass.ts:1447`). That is the whole accident: `holdOfPass` branches on `stopped === null` (`hold-of.ts:123`), so the first becomes `Routed` and the second falls through to `CheckRed` (`hold-of.ts:161`).

What tells "the router sent it to a person" apart from "a step broke" is `PassResult.rested === 'waiting'` (`pass.ts:1199-1209`). Its doc says `null` covers *"a `never-ran`, a crash, a `proposed` whose own plugins refused, a judge that answered something it was not offered"*. When the router itself fails, `stoppedAt` is `{step: 'proposed', …}` and `rested` stays `null` (`pass.ts:1450-1455`). Add `rested: Rest | null` to `HoldOfPassInput` and pass `pass.rested` from `holdFor`.

## The direction: export `directionOf` and don't copy it

`Routed.when` has to be a `JudgeWhen`. The router already derives it from the arriving step in one place: `directionOf` in `pass-steps.ts:613-622`, which is private today:

```ts
if (ending.ending === 'asked') return NEEDS_INPUT
if (ending.ending !== 'refused') return null
if (arriving.step !== 'merge') return 'red'
if (ending.because === 'conflict') return 'conflict'
return ending.because === 'verify-failed' ? 'verify-failed' : null
```

Export it and call it from `hold-of.ts`. Narrow its parameter to `Pick<StepReached, 'step' | 'ending'>` so `stoppedAt`, which is `{step, ending: StepReport}` (`pass.ts:1190`), fits it. A copy in `hold-of.ts` would let the router and the card disagree about the direction. Nothing guards what may import `pass-steps.ts`: `conduct.ts` and `judge-agent.ts` already do, and its header line 9 (*"nothing in the conductor imports it"*) is stale.

## The order `holdOfPass` checks in

1. **The router sent it to a person.** `rested === 'waiting'` and one of:
   - `stopped === null` gives `Routed{when: 'findings'}`. This is today's branch, unchanged.
   - `stopped.ending.ending === 'refused'` and `directionOf(stopped)` is not null gives `Routed{when}`.
     - `raw` is the step's own output (`detailOf(stopped.ending)`), which is the red output Done-when asks for.
     - `findings` is `input.findings`.
     - `paths`/`baseSha`/`headSha` come from `input.integrationRefusal` when `when === 'conflict'`, and are `null` otherwise.
     - `why` stays the composed line, `` `${branch} into ${base} is waiting on you. …` ``, built from `lastRoute.why`. `legacyColumns` uses `hold.why` verbatim as the card's question (`legacy-columns.ts:126-127`).

   This check must come **before** the `merge`/`MergeRefused` branch at `hold-of.ts:86`. Otherwise a `conflict` or `verify-failed` refusal the router sent on stays `MergeRefused`.
2. **The merge lane refused with no direction.** These are `dirty-base`, `push-rejected`, `unexpected` and the rest. They become `MergeRefused` as today, or `CheckRed` when `because` is not a `RefusalReason`. The router does send these to a person too (`pass-steps.ts:1275-1279`, *"not a direction any `judge:` answers"*), but `Routed.when` cannot hold them. `JudgeWhen`'s own doc says why: *"they stop the lane before the diff is what is in doubt"* (`hold.ts:44-50`). **The decision: an arrival becomes `Routed` only when it has a direction.** A directionless arrival keeps its `Failure` variant, which matches the ticket's table listing `MergeRefused` under *nobody decided*.
3. `ceilingHit` gives `Ceiling`, unchanged.
4. Then the `switch` on `stopped.ending.ending`:
   - `asked` stays `Asked`, **even though it went through the router** (`goesToTheRouter`, `pass.ts:1036`, with direction `needs-input`). The ticket's first row says *"a step ended `asked`"*, and `Asked` carries the agent's question, which `Routed` has no field for. So `Routed{when: 'needs-input'}` is never written. Say so in a comment rather than leaving the reader to wonder.
   - `held` stays `Human`.
   - `did-not-finish` becomes `Declined` when the new `declined` input is set (next section), and `DidNotFinish` otherwise.
   - `refused` only reaches here when the router did not send it on, which in practice is `proposed`. It stays `CheckRed`. The `prepared` → `SetupRefused` branch is now dead for the pass, because a `prepared` refusal has direction `red` (*"`prepared`'s install, which is the same kind of evidence one step earlier"*, `pass-steps.ts:597-598`). It becomes `Routed{when: 'red'}`. **Follow the rule, don't add an exception**, and delete the dead branch along with its test (`hold-of.test.ts:134`).

## `Declined`: a closure flag, like `ceilingHit`

The fix round's two stops differ only in their text. `conduct.ts:2953-2959` returns `{stopped: …}` either way, and a stop at `implement` is `did-not-finish`, which does not go to the router (`pass.ts:1036`). The pass cannot tell them apart, and it shouldn't have to. `ceilingHit` already makes the same choice for the same reason (`conduct.ts:1240-1251`):

> *"so the distinction is kept here rather than pushed into a vocabulary the pass would then have to carry."*

So:

- Add `let declined: { said: string | null } | null = null` beside `ceilingHit`.
- Set it in the fix branch exactly when `!committed && !fixed.failure`, with `said: fixSaid`. That is the same value `FixApplied.said` gets at `conduct.ts:2920-2933`, so the hold and the event cannot disagree.
- Pass it to `holdOfPass` as `declined`.

A decline returns `stopped`, and that ends the pass at `implement`, so the flag only survives into `holdFor` when the decline was what stopped the pass. `ceilingHit` is only set on the first dispatch's failure path (`conduct.ts:2763`), so the two cannot both be set.

`Declined` in `hold.ts` is `{ _tag, run: RunRef, step: Step, said: string | null }`, added to `Judgement` (`hold.ts:169`). `Hold` spreads `Judgement.options` (`hold.ts:271`), so it picks the variant up without further change. `step` is `stopped.step`, which is `implement`.

The exhaustive switches that will go red under `pnpm typecheck`, and what each should say:

- `moves.ts` `allowedMoves`: `[Approve, Requeue, BodyAndRequeue, Close]`, exactly as the ticket says. `BodyAndRequeue` exists (`triage.ts:127`).
- `moves.ts` `triageRuns`: `true`.
- `legacy-columns.ts` `legacyColumns`: `needs: 'judgement'` and `recommendation: null`. Its line is `stepLine(step, 'declined', said ?? 'the fixing agent committed nothing')`.

Give `Declined` its own fixture in both `moves.test.ts` describes, plus one in `hold.test.ts` and one in `legacy-columns.test.ts`. Typecheck may find more readers (`apps/board`, `packages/extension`); answer each the way it already answers `Routed`.

## What changes on the card

`Routed{when: 'red' | 'verify-failed' | 'conflict'}` gets `recommendation: null` (`legacy-columns.ts:138`, which only recommends for `findings` with none raised) and `needs: 'judgement'` in place of `'acknowledgement'`.

- **A red is not a regression:** `CheckRed`'s recommendation was already `null` (`legacy-columns.ts:158`), not `requeue` as the ticket supposes.
- **A conflict or verify-failed is a regression.** It loses `diagnoseRefusal`'s `done` and `recommendation` (`legacy-columns.ts:170-182`).

Say both in the commit body and leave the recommendations to #444. The moves stay the same: `Routed` and `CheckRed` share a case, and `MergeRefused` with `afterApproval: false` offers the same three (`moves.ts:29-42`).

## `Failure.CheckRed` after this

Three paths still produce it:

- a `merge` refusal whose `because` is not a `RefusalReason`, such as a declared check's `action-refused` before the lane (`hold-of.ts:109`)
- `proposed`'s own plugins refusing on the way through
- the router failing to answer (`pass.ts:1453`)

So the variant stays, and the commit body says so. `SetupRefused` is no longer produced by `holdOfPass`. The body should say that too, and leave the variant in place.
