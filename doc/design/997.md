## Design note — #997, triage held by a project lock

#991 and the discussion sibling (#996) have both landed in this worktree. Follow #996's shape, which is already in `main`. The line numbers below are today's, and several differ from the ticket's.

### The trap the ticket does not name: never await the resume scan

`deliver` gives every handler `SUBSCRIBER_TIMEOUT_MS = 10 * 60_000` (`packages/daemon/src/work-loop.ts:154`). A handler that has not settled by then is reported as `triage failed on ProjectResumed: did not return within 600s`, and `record` turns that into a `PluginFailed` (`work-loop.ts:460-485`, `:406`).

`catchUpTriage` awaits each worker's `.done` (`apps/cli/src/triage.ts:144-161`, `await queueTriage(...).done`). Each worker runs a triage agent, which can take up to `runtime.limits.wall`. So a `ProjectResumed` branch that awaits `catchUpTriage` produces a false failure on the log for every resume with a real wait behind it.

The live branch already avoids this. `onWaitStarted`'s docstring says *"The returned promise never waits for its worker"* (`triage.ts:244`). The resume branch must keep that promise:

```ts
// inside onWaitStarted, no new async function
if (event.type === 'ProjectResumed') {
  const { project } = event.data as PayloadOf<'ProjectResumed'>
  void deps.triageFor(project)
    .then((triage) => catchUpTriage(project, triage, deps))
    .catch((err: Error) => deps.log?.(`triage catch-up ${project}: ${err.message}`))
  return
}
```

Use `.then` chains, not an `async` closure. `packages/domain/unit/effect-ratchet.test.ts` counts `async` functions, and this change adds none: the new branch sits inside the existing `async function onWaitStarted`, and the hold is two lines inside the two existing worker closures.

### Name the delivered events once, as #996 did

#996 added `DISCUSSION_EVENTS = ['DiscussionRequested', 'ProjectResumed']` (`work-loop.ts:101`). The loop's delivery reads it at `:596`, and so does the handler's own guard (`apps/cli/src/discuss.ts:566`). Its docstring gives the reason: *"so the next unlock event is added once"*.

Do the same here:
- Add `TRIAGE_EVENTS = ['WaitStarted', 'ProjectResumed'] as const` next to it, exported from `@lingtai/daemon`.
- Use it at `work-loop.ts:599` in place of `event.type === 'WaitStarted'`.
- Replace `onWaitStarted`'s first-line return (`triage.ts:245`) with a check against the same list.
- Update the `triage` option's docstring (`work-loop.ts:263`).

This is the "cost to later tickets" edge: the ceiling and account unlocks get added to this list.

For the "work loop hands `ProjectResumed` to triage" Done-when, copy `packages/daemon/unit/work-loop-discuss.test.ts`. Its real-loop test (*"hands a ProjectResumed to discuss, and not a pause"*) appends the events before `start` and passes only `discuss`. Pass only `triage` instead, in that file or in a sibling.

### `locked` in daemon.ts has to move up

`scanTriage` is built at `apps/cli/src/daemon.ts:512-523`. `locked` is declared later, at `:568` (*"One `locked`, asked by every gate that starts an agent (0126 §5); it caches nothing."*), inside the `!('no-conduct' in flags)` block.

`scanTriage` is only called from inside that block (the pass at `:646`, startup at `:698-703`), so the `locked` declaration should move above `scanTriage`, still inside the block. Without that move, `scanTriage` cannot reach `locked`. Then:
- `daemonTriagePorts(daemonStartedAt, log, writer)` (`triage.ts:315`) takes `locked` as a fourth parameter and returns it.
- Both call sites (`:518` and `:579`) pass the one `locked`.
- Build no second guard and no second `lockedBy`.

### The hold, in both workers

- **Live worker:** after the existing `Queued` re-check, at `triage.ts:266`.
- **Catch-up worker:** inside the `Queued || first-Interrupted` branch, before `deps.run`, at `triage.ts:153-154`. The `finishInterrupted` branch (`:156-157`) is not asked.

Ask:

```ts
const why = await (deps.locked ?? notLocked)(project).catch((err: Error) => err.message)
```

Then log `triage <waitId> on <ticketId>: not started — <why>` and `return`.

`lockedBy` never rejects (`packages/daemon/src/guard.ts`: *"It never rejects. A read that fails answers a sentence"*). The `.catch` is still there because #996 did the same (`discuss.ts:513`), and because it makes a test port that rejects count as held, not as `could not start triage`.

The project in each worker:
- **Live:** `parsed.project`, already in scope (`triage.ts:246`).
- **Catch-up:** `catchUpWait` has only the `ticketId`, so use `parseTicketStream(ticketId)!.project`, as `finishInterrupted` does (`:185`).

### What a test should drive

Both suites inject the ports and use no store beyond memory, so `pnpm test` covers everything here. No claim needs `pnpm test:integration`.

**Resume scan test** (`triage-trigger.test.ts`):
- Before the `ProjectResumed`, call `catchUpChangedTriage` once for the project while it is locked, so the hash is pinned.
- Then hand `onWaitStarted` a `ProjectResumed` with `locked` answering null, and assert `run` is called.
- `onWaitStarted` returns before the worker finishes, so wait on `run` being called, not on the returned promise.

**Interrupted test** (`triage-catch-up.test.ts`): the existing fixtures that already reach `finishInterrupted` show that a locked project still gets `TriageFailed: interrupted` appended.

### Edges decided here

- A `ProjectResumed` for a project that is not registered, or whose recipe has no `triage`: `triageFor` answers null and `catchUpTriage` returns at `:122`. Nothing is logged.
- A `ProjectResumed` that arrives while the daemon's start time is still unread: `catchUpTriage` rejects at `:125`. The rejection is logged through the `.catch` above, and the waits are left for the next restart, as the ticket accepts.
- `--no-conduct`: triage is not wired in that branch today, and that stays.
