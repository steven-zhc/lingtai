# Design note for #1433: cache the GitHub installation and token per App id

## Where it goes

Almost all of the change goes in `packages/github/src/app.ts`. There is a small change in `makeGitHub` (`packages/github/src/client.ts:743-856`) and a comment edit in `apps/board/src/lib/board.ts:1102`. Do not change any caller: `filter.ts`, the board and the daemon keep calling `createGitHubClient`/`makeGitHub` exactly as they do now.

## The cache

Put it at module level in `app.ts`, next to `installationToken` (`app.ts:333`):

```
Map<appId, { repos: Map<"owner/repo" lowercased, Installation>,
             tokens: Map<installationId, Effect<string, GitHubFailed>> }>
```

- **Lowercase the repository key.** GitHub resolves `Owner/Repo` and `owner/repo` to the same installation. A mixed-case spelling in some project's config would otherwise cost one extra lookup, which is harmless but pointless.
- **Store `installationToken`'s inner Effect as the token value.** That is the `Effect.Effect<string, GitHubFailed>` it returns (`app.ts:336`). Its `Semaphore` and `Ref` are created once per installation, so the comment *"Checked again inside the permit: whoever was queued behind the one request wants its answer, not another request"* (`app.ts:353-354`) now holds across the whole process with no further work.
- **Do the cache-miss path the same way `createAppReader` does** (`app.ts:388-405`): a `get`, then build on a miss, then a `set`. Its comment already accepts the race this leaves: *"two first reads for one installation can each build a cache: one extra token request, once per reader."*
- **Only cache a successful installation lookup.** A failure from `installationForRepoEffect`, including `NotInstalledError`, is never stored.

## The decision the ticket leaves implicit: where "the token is no longer good" is detected

`send` (`client.ts:781-782`) runs the token mint and the request in a single `Effect.flatMap`. Both fail with the same `GitHubFailed`, and a 404 from the request itself is normal: `idOf` says *"A 404 fails: there is no such issue to link"* (`client.ts:786`). Checking `err.status === 404` on `send`'s combined error would therefore drop the cache every time someone looks up a missing issue. Detect the two cases separately:

1. **Mint failure: 401 or 404.** Wrap the token source itself with `Effect.tapError` before it is used. On 401/404 it forgets the token entry and the repository's installation entry. This wrapper belongs in `makeGitHub`, because that is the only place that knows both `owner/repo` and `installation.id`. `tokenSourceOf` knows only the id.
   - The wrapped token feeds both `send` and the exported `github.token` (`client.ts:853`, used by git). A mint failure seen by git therefore drops the entry too.
2. **Request failure: 401 only.** Put a `tapError` on the `githubJson(...)` call inside `send`, after the token has been obtained. Do not add one for 404.

In both cases the error is passed on unchanged, and nothing is retried; the ticket's Out of scope excludes retries.

**Forget only the exact entry that failed.** Compare the stored source against the one that failed (`===`) before deleting it. Otherwise a slow failure from an old client could delete the fresh entry a concurrent render has just created.

**With `options.installation` given**, the client still gets its token through `tokenSourceOf`. On failure it drops only that installation's token source, plus the repository entry if one exists. That is harmless, and it keeps the code to one rule.

**Git failures are not detected.** A 401 from git itself (clone or push run with `github.token`) never reaches this code. If a key is rotated mid-pass, the next mint or `send` drops the entry. That is acceptable, and the note should say so in a comment rather than try to handle it.

## Tests: who has to start from an empty cache

Vitest runs each test file with its own module graph, so the cache does not leak between files. It does leak between tests within one file. These files build clients against `appId: '123456'` (or `'1'`) and installation `1`, and their fake fetch counts or fails mints:

- `packages/github/unit/make-github.test.ts:25`, e.g. *"asks for one token across several calls"* counts `tokens`.
- `client.test.ts:30`, `links.test.ts:22`, `checks.test.ts:14`, `list-since.test.ts:65`.
- `packages/conductor/unit/github-limit.test.ts:36`, `github-limit-waits.test.ts:25`. These test a mint refused for rate; a token cached by an earlier test would hide that refusal.

Add `forgetGitHubAuthCache()` to each of these files' `beforeEach`. Do it in one sweep, before diagnosing individual failures. Export it from `packages/github/src/index.ts` next to the other `app.ts` exports.

The three new tests in Done when go in `make-github.test.ts`. They use `vi.stubGlobal('fetch', …)` and count by URL: `/installation` for lookups, `/access_tokens` for mints. For *"404 on mint drops the entry"*, build without `options.installation`, so the repository entry exists and its re-lookup can be counted.

## Out of reach in a pass

The production Jaeger check (no `github.request` under `board.recipes`, no `POST` under `queue.list`) can only be done after deploy. Before the merge, the first unit test stands in for it: two clients for one repository and one App id make one installation `GET` and one token `POST` between them. No integration test covers this change.

## Ratchet

Write the cache helpers as `Effect.gen`, with no `async` functions and no `Effect.run*` calls, so `effect-ratchet.baseline.json` is unaffected. Do not edit that file.
