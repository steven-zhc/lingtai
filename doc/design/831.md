# #831: where the change goes

## 1. Handle `current` and `then` in one place before the `switch`

Most of `lastMove`'s rule is about which kind of event arrived, so write it once, the way `since` is handled at `packages/domain/src/ticket.ts:298-301`, instead of adding a clause to all seven cases.

**Where it goes.** Put it right after the `closed` guard (`ticket.ts:316-318`) and before `switch (event.type)`. That position matters. The guard returns early for every `LIFECYCLE_EVENTS` event while the ticket is `closed`, so a claim, close or release after a close never reaches this code. That is exactly D6: *a claim after the close does not end the move*. You get it for free, and the guard needs no change.

**What it does.** Only events in `LIFECYCLE_EVENTS` (`ticket.ts:280-288`) are affected:

- **`WaitResolved`**: leave `lastMove` alone here. The case sets it (§2).
- **`TicketClosed` or `TicketReleased`, with `lastMove?.current && lastMove.then === null`**: set `then` from the payload.
  - For a close: `{ kind: 'closed', reason: d.reason }`.
  - For a release: `{ kind: 'released', reason: d.reason, cause: d.cause ?? null }`.
- **Any other lifecycle event, or a close or release when `then` is already set**: if `lastMove` is not null, set `current: false`.

**A continuation of an unclaimed run** returns early at `ticket.ts:338-340`. It is still a lifecycle event, so the pre-switch line ends the move, as the ticket asks. Putting the rule before the `switch` is what makes that happen without another edit.

## 2. In the `WaitResolved` case, compute the move once and add it to every return

The case has four `return`s (`ticket.ts:483`, `491-501`, `512`, `514-533`).

At the top of the case, after `block` (`ticket.ts:478`), compute this once:

```ts
const lastMove = {
  waitId: d.waitId,
  resolution: d.resolution,
  by: d.by,
  note: d.note,
  current: block !== null && block.waitId === d.waitId,
  then: null,
}
```

Then spread `lastMove` into each of the four returns. `block` is read from `state.lifecycle`, and `state` has not changed the lifecycle at this point, because the `since` line only touches `since`. So this is the lifecycle *before* the event, as the ticket's *Watch out* requires.
