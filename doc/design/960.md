# #960 — shape

## Data first: `GithubQueue` lacks one fact the table needs, and passes the note one fact too many

The work is in `githubQueue` (`apps/board/src/lib/board.ts:1036`), before any markup:

1. **The note leaves out `blocked-by`.** At `board.ts:1076` the call is `passedOver(offered.skipped)`. Make it `passedOver(offered.skipped.filter((s) => s.reason !== 'blocked-by'))`. `passedOver` itself (`packages/conductor/src/discover.ts:376`) does not change, so `lingtai status` does not change either. When every skip is `blocked-by`, the filtered call returns `null` and the column shows no note.
   - The comment above the call at `:1074-1075` says *"The same two sentences `lingtai status` prints, from the same functions, so the column and the terminal cannot count a held ticket differently."* That is no longer true. It should now say that the column counts the skips it does not draw as cards.
   - `apps/board/unit/render-cost.test.ts:224` expects `'3 passed over — excluded-label 2, blocked-by 1'`. It becomes `'2 passed over — excluded-label 2'`.

2. **Add `held` to `GithubQueue`.** The row "it is an `excluded-label` skip → `bk` held" has nothing to read today: `GithubQueue` (`board.ts:1009-1021`) carries only the `passedOver` sentence. Add `held: { project: string; ref: number }[]`, filled from `offered.skipped` where `reason === 'excluded-label'`. Carry the refs only. Drawing held tickets is #955 and stays out of scope.

3. **Drop a blocked skip the log already has a card for.** Do it where it is pushed (`board.ts:1068`, `blocked.push(...answer.blocked)`), with the same test runnable cards get at `:1081`: `known.has(ticketStream(filter.project, s.ref))`. `ticketStream` is from `@lingtai/domain` (`packages/domain/src/streams.ts:23`) and `queue.ts:100` builds task ids with it. A dropped skip is not drawn and is not counted in `<m>`. It is still a valid blocker for other cards, and its state then comes from whichever column the log puts it in. That follows the existing rule at `board.ts:1377-1379`: *"The row wins: it carries the attempts."*

4. **Give each blocked entry its kind colour.** On the way into `GithubQueue.blocked`, take it from `offered.kindColors[s.kind]`, the same way cards get theirs at `:1087`. Without it the `kdot` has no colour, and `queued-stream.tsx` is pure, so it cannot call `lastKindColor` itself.

## Where the state is decided

**The inputs are built in `page.tsx`. The table itself lives in a pure lib function.** The ticket puts the decision "in `page.tsx`, where the columns are". Two facts mean the rule cannot live there:

- `page.tsx` may export nothing but the page. `queued-stream.tsx:11-12` says: *"`Card` and `Queued` live in `page.tsx`, which may export nothing but the page."* So a function written there could not be tested.
- Half of the table's inputs (GitHub's queued cards, `blocked`, `held`) arrive only inside the Suspense boundary, in `QueuedAnswered`.

So the split is:

- **`page.tsx` builds the board's half** and passes it to `QueuedAnswered` as a new prop. That half is:
  - a `Map<string, 'running' | 'waiting' | 'queued'>` keyed `` `${project}#${ref}` ``, filled from the `running`, `waiting` and `queued` columns (`ColumnId`, `board.ts:90`);
  - each project's own repository, `` `${links.owner}/${links.repo}` ``, from `askable` (`AskableFilter.links`, `packages/conductor/src/filter.ts:202`; null when the project has no link reader).
- **A new `apps/board/src/lib/blocker-state.ts` holds the table** as one function. It takes the blocker (`LinkedIssue`), the skip's project, that board half and the `GithubQueue`, and returns `{ state, cls, word, label }`. The rows are tried in the table's order and the first match wins.
- **`QueuedAnswered` calls it**, so the markup test drives the real table with literal values.

Details the implementer will hit:

- **Key types differ.** `BoardCard.ref` is a `string` (`board.ts:104`); `BlockedSkip.ref` and `LinkedIssue.number` are numbers. Build every key with `String(n)`.
- **"Own repository" means `repository` equals the project's `owner/repo`, compared case-insensitively.** `LinkedIssue.repository` comes from GitHub's `repository_url` (`packages/github/src/client.ts:564`), which uses GitHub's canonical case; the configured owner and repo may not. A blocker from another repository gets the label `owner/repo#n` and only `closed` or `open` (from `state`, `client.ts:140`); it is never looked up in the columns.
- **Several projects:** look up columns by the skip's own project, never only by number. Two projects can both have a `#12`.

## The column

Everything new goes in `QueuedAnswered` (`queued-stream.tsx:76`). `QueuedFallback` does not change, which covers the *before GitHub answers* edge with no extra code.

- **`n`** is `cards.length` (`:91`), the same number `QueuedCountAnswered` shows in the header (`:128`), and the header does not change. **`m`** is `github.blocked.length` after step 3, unread skips included.
- **Order:** the `qsum` summary comes first, then the problems and notes as today, then `list(...)`, then the blocked cards in `ref` order. That is the order `readBlockers` already sorts them in (`board.ts:796`). After the cards comes one `+k more waiting on a blocker` line for the `unread` ones.
- **The `cards.length === 0 && problems.length === 0 ? empty` branch at `:107`** keeps `empty` only when `m === 0`. Otherwise the summary `nothing runnable · <m> waiting on a blocker` replaces it, as the ticket asks. When there are problems, the column draws no empty note today, and a summary is still drawn if `m > 0`.
- **`showProject`** is decided over runnable and blocked projects together (extend `projects` at `:94`). A blocked-only project must be named, and runnable and blocked cards have to agree on whether a project name is shown. Today that set is built from runnable cards only.
- **`bkwhen`:**
  - The open blockers are the read ones whose `state !== 'closed'`, from any repository, each labelled as on its chip.
  - One open blocker reads "starts when #a lands"; more read "starts when #a, #b land".
  - None open reads "starts on the next turn". The blocker cache is trusted for 60 s (`BLOCKERS_FRESH_MS`, `board.ts:777`), so a just-closed blocker can briefly show this; that is accepted.
- **No chips can be drawn** when `blockers` is `{ ok: false }`, or is `null` with `unread: false` (no link reader, `board.ts:759-761`). The card then reads `blockers could not be read` in place of the chips and **has no `bkwhen`**: there is nothing true to name. The ticket decides the first case; the second is decided here the same way.
- The blocked card is a plain `<div className="card q-blocked">` built in `queued-stream.tsx`. It is not `page.tsx`'s `Card`, which brings standing, moves and attempts that a skip does not have.
