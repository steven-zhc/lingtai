## Design: `source.tickets` (#381)

### Where it goes

- **Schema:** add a fourth field to `SOURCE_FIELDS` (`packages/recipe/src/recipe.ts:1013`). Declare the enum as an exported named schema beside `AssigneeTake` (`recipe.ts:1027`), e.g. `export const TicketSource = z.enum(['github', 'db'])`, with its type. Then #382 can import the type without restating the two words.
- **Accessor:** put `ticketSourceOf(recipe)` in `packages/recipe/src/settings.ts`, beside `kindsOf`, `excludeOf` and `backoffOf` (`settings.ts:263–291`). It already reaches the package's exports, because `packages/recipe/src/index.ts` does `export * from './settings.ts'`.
- **Leave `QUEUE_FIELDS` and `queueOf` alone** (`recipe.ts:1080`, `settings.ts:339`). This setting does not move onto `claim`.
  - The comment on `QUEUE_FIELDS` says: *"All four are required, and none of them defaults … A block is the four values this step selects on"* (#269).
  - So adding `tickets` there would make every pasted `queue:` block fail to resolve until it names the new field.
  - `takeAt` therefore plays no part in it. The accessor reads `recipe.source.tickets` and nothing else.

### The decision the ticket doesn't make: default in the accessor, not in the schema

Declare the field `.optional()` and let `ticketSourceOf` return `recipe.source.tickets ?? 'github'`. Do not use `.default('github')`. This follows the precedent of `runtime.assignee` (`recipe.ts:3087`, `AssigneeRule.optional()`), whose accessor comment says it is *"returned absent rather than filled in"*.

The reason is the hash:
- `resolveRecipe` returns `configHash: hashRecipe(parsed.data)` (`resolve.ts:257`).
- `forHash` hashes the parsed recipe as it stands, `return { ...recipe, steps }` (`resolve.ts:155`).
- A schema default therefore puts `tickets: 'github'` into every recipe's parsed body. Every project's `configHash` would change at the restart that loads this code, with no edit to any recipe file.
- `StepsResolved` records that body next to that hash. 0047 §2 relies on that pair, and the task page reads it as *same document as head*. Every run since the restart would read as a different document from every run before it.

With `.optional()`, a recipe that does not write the key hashes exactly as it did before.

What would settle this in the log is `StepsResolved.configHash` for one project, on either side of the restart. The unit-level stand-in: `canonicalRecipe(parsed).source` has no `tickets` key when the file wrote none.

The ticket's *defaulting to `github`* is still met, because the accessor is the only reader.

### Correction to the ticket's Watch-out: an old daemon drops the key without saying so

The ticket says a recipe carrying a key the daemon does not know *"is refused every pass (#148)"*. That holds for top-level keys only:
- `unknownKeys` reads `Object.keys(Recipe.shape)` (`resolve.ts:290–293`), which is only the top-level keys.
- `source:` is `z.object(SOURCE_FIELDS)` (`recipe.ts:2809`), not a `strictObject`, and `z.object` silently drops keys it does not declare.

So a daemon started before this lands, handed `source: { tickets: db }`, resolves the recipe fine and runs the project from GitHub. Nothing says so.

The doc comment must state that, not repeat the ticket's "refused". *Code, restart, paste* is the remedy either way, and it matters more because the failure is silent. Do not make `source:` strict in this change: that would refuse every existing recipe that has a stray key under `source:`, and it is not this ticket's subject.

### What the field's doc comment has to carry

Write it in the house style of `KINDS`, `EXCLUDE` and `BACKOFF` (`recipe.ts:938–1011`):

- **Values:** `github` means tickets are the repository's GitHub issues. `db` means the `tickets` table on whichever store this machine chose (`5517e86`, `ensureTicketTables`).
- **Default:** absent is `github`, filled in by `ticketSourceOf` and not by the schema, for the hash reason above.
- ***Code, restart, paste*** ([doc/design/the-plugin-body.md](doc/design/the-plugin-body.md)), and why: an older daemon drops the key without a word, so a `db` project would be run from GitHub.
- **Switching a project with history is unsupported.** Work items are the streams `wi-<project>-<number>` (`packages/domain/src/streams.ts:14`). A DB ticket numbered from 1 would append into the stream of the GitHub issue with the same number. Refusing that by name is #382's job; this comment only says it.
- **This field is not `source.local` (#351).** That field says where code is pushed; this one says where tickets live. They are independent axes.

### The `MOVING` guard

`packages/recipe/unit/settings.test.ts:418` lists the settings that 0061 §4 and 0063 §3 move onto steps, and its comment says *"the list is the ADRs' and not `settings.ts`'s"*. `tickets` is not one of them. Do not add it there.

### Tests

Put them in `packages/recipe/unit/settings.test.ts`, building on the recipe fixture at `settings.test.ts:65`:

- **Absent:** `ticketSourceOf` returns `'github'`, and the parsed `source` has no `tickets` key (this pins the hash decision).
- **`tickets: db`:** returns `'db'`.
- **Any other value** (e.g. `gitlab`): `Recipe.safeParse` fails with an issue whose path is `['source', 'tickets']`. That path is what `resolve.ts:248` turns into `source.tickets: …`, which is the "refused by name" part.

None of this touches the filesystem, so all of it belongs in the `unit` project. `pnpm test`, `HOME=/nonexistent pnpm test` and `pnpm typecheck` cover it. No part of this needs the integration half.
