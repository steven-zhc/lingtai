# Design: #491, a `requeueCommand` call that waits 180s

## Where the two paths split

Under test, `requeueCommand` and `requeue()` read the same store. Every store this command reaches comes from one `chosenStore()`:

- `loadProject` uses `defaultLog()`, which is `(await import('@lingtai/event-store')).log` (`packages/conductor/src/projects.ts:27`, `:44`).
- The runner reads from the same barrel log (`packages/projector/src/projection.ts:165`).
- The runner's fold lands in `projectionStore()`, which also calls `chosenStore()` (`packages/projector/src/choose.ts:51`).
- The test's `processEventStore()` is that same memoised open (`packages/event-store/src/choose.ts:63-78`).

So nothing in `apps/cli/src` can reach a `~/.lingtai` the test did not choose. Settle that first, as the ticket asks, but expect the answer to be "no".

What does differ is the environment. `setup()` returns before making the temporary SQLite directory whenever `LINGTAI_TEST_DATABASE_URL` is exported (`packages/event-store/test-support/teardown.ts:126`). `HOME=/nonexistent` does not unset that variable. In that case the whole file runs on the shared Postgres test database, which has a long log behind it. That is how the reviewer's "accumulated test log" can be true without contradicting `:127`. The commit body has to say which of the two the slow run was on. Read it with `describeStore(storeChoice())` (`packages/env/src/index.ts:696`), for example in a throwaway `console.log` in `beforeAll` that you do not commit.

Inside `requeueCommand`, the only thing `requeue()` does not also do is `withProjector` (`apps/cli/src/requeue.ts:52`). That wraps up to three `runner.start()` calls (`apps/cli/src/projector.ts:97`, `:103-104`). Each one opens a **waker** as well as reading the store: `follow()` takes `from.waker(…)` (`projection.ts:166`) and waits on `sub.caughtUp()` (`:186`). `requeue()` called directly opens no waker.

## Reproduce by test, not by file

Run each test alone with `-t`, both with and without `env -u LINGTAI_TEST_DATABASE_URL`. That is four short runs instead of one 12-minute one.

**The test at `:170` is the discriminator.** A project that was never registered returns at `requeue.ts:45-48`, before `withProjector` is reached. If that test times out when run alone, the wait is not the projector. It is upstream, in opening the process log. Stop and follow that instead, because nothing below would then apply. If it is fast alone and only slow after the others, that is the earlier tests' runners: a timed-out test is not cancelled, so its `start()` keeps running into the next test.

## The likely cause: `start()` cannot fail, only hang

`subscribe` never gives up on a connection. `session()` swallows a connection error into `'reconnect'` (`packages/event-store/src/subscribe.ts:252-254`). `run()` loops with backoff capped at 10s until somebody closes it (`:274-283`). `caughtUp()` rejects only on stop. So a waker whose `ready` never resolves leaves `runner.start()` pending for ever, and nothing throws. Two ways that happens:

- **Postgres:** `LISTEN` goes to `directUrl` (`packages/env/src/index.ts:478-481`), a different host than the pool's.
- **SQLite:** the polling waker gives up after `BUSY_MS = 5_000` (`packages/event-store/src/sqlite.ts:68`, `:304-318`), and the next session tries again.

`withProjector`'s promise, *"A projector that will not start is reported and never fatal"* (`projector.ts:85-88`), only holds for a start that throws.

To confirm it, pass `onError` to the runner and log every `'connection'` error. Today `projector.ts:91` passes none, so these errors are invisible. That logging is the evidence the commit body cites.

The other reading is an honest catch-up over a large Postgres log: about 50ms per event, measured at `projection.ts:60-68`. If that is the cause, the fold is making progress, and you will see it as `lag()` rising rather than as connection errors.

## The decision: bound the start in the CLI, not in the runner or `subscribe`

If it is the waker, make `withProjector` (and `ProjectorLive`, `projector.ts:139-167`, which repeats the same acquire) give up when the first session fails. Hand the runner an `onError`. When a `'connection'` error arrives before `caughtUp`, close that runner and treat it as a failed start. The existing `catch` then logs "will not follow" and the work runs.

**Do not change `subscribe` or `createProjectionRunner.start()` to reject on a connection error.** The daemon relies on the opposite behaviour:

- `packages/daemon/src/daemon.ts:171-175`: *"A connection error retries inside `subscribe`"*.
- Its `start()` failure is rethrown and releases the lock (`:184-202`).

A runner that rejected on the first connection error would turn a brief database blip at daemon start into a daemon that exits. The board's two runners (`apps/board/src/lib/spend.ts:227`, `apps/board/src/lib/backlog.ts:32`) would be affected the same way. A command that a person is waiting on is the one caller that should give up.

## If it is the catch-up instead

Then nothing is wrong with the code, and the cost belongs to the shared Postgres test log. This file is not in `ON_POSTGRES` (`packages/event-store/test/postgres.ts:23`), so it was never meant to need Postgres. Say that in the commit body. Do not shrink the fold, skip the projector under test, or raise `testTimeout`. A file-specific workaround hides the same wait that a real `lingtai requeue` pays against a lagging checkpoint. If that wait is the finding, it needs a ticket of its own, and this one closes on naming it.

## Checks

- **Done when, item 3** (a unit test if the command reached another store) applies only if the "which store" question above finds a real leak. Using the Postgres test database because it was exported is not a leak: `teardown.ts:126` does it by design.
- **The unit-level claim for the bound:** `withProjector` returns `work()`'s result and logs "the board will not follow this run" when a runner's waker never becomes ready. A fake runner is enough, because the claim is about `withProjector`, not about `subscribe`. That needs a factory parameter so a test can hand one in, since `projector.ts:91` constructs its own runner today.
- Re-run the integration file one test at a time with `-t` (the four runs above), never the whole half.
