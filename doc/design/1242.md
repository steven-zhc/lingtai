## Design note for #1242: renaming a person's four moves

### 1. The seam is advice → resolution, and three of its five readers fail silently

Today the code assumes `TriageAdvice` and `Resolution['_tag']` are the same strings. The only thing that says so is the type assertion at `packages/domain/src/wait.ts:296-299` (`AssertEqual<TriageAdvice, Exclude<Resolution['_tag'], 'AnswerQuestion' | 'RerunStep'>>`). The readers lean on that assumption in five ways, and the compiler catches only some of them after the rename:

| Site | What it does | After the rename |
|---|---|---|
| `wait.ts:780` | `allowed.includes(advised)` | `tsc` goes red |
| `standing.tsx:574,581`, `history.ts:727` | `RESOLUTION_COPY[result.resolution]` (keyed by `Resolution['_tag']`, `resolution-copy.ts:6`) | `tsc` goes red |
| `standing.tsx:563` | `recommendedResolution(...) === result.resolution` | **compiles, wrong** |
| `board.ts:769` | `status.result.resolution === resolution ? {} : { advised: ... }` | **compiles, wrong** |
| `board.ts:1507`, `status.ts:568` | `t.triage.result.resolution === 'GrantFixRound'` | compiles, wrong |

The `===` comparisons compile because the two unions still share `Approve`, `Split` and `Close`. A `Requeue` advice would then never be "kept", and every card would carry an `advised:` that differs from its own move.

**How to build it:**
- Add one exported table in `wait.ts`, next to `TriageAdvice`: `ADVISED: { readonly [A in TriageAdvice]: Resolution['_tag'] }`.
- Rewrite the assertion at `:296` over the table's values: `AssertEqual<(typeof ADVISED)[TriageAdvice], Exclude<Resolution['_tag'], 'AnswerQuestion' | 'RedoStep'>>`. A later resolution tag still has to be listed or excluded on purpose.
- Put a function beside the table (`resolutionAdvised(advice)`) and convert on the **first line** of `recommendedResolution` (`wait.ts:765`): `const advised = resolutionAdvised(status.result.resolution)`. Everything below that line then works in resolution tags.
- Every other site in the table goes through the same function. To find them: `grep -rn "result.resolution" apps packages | grep -v test`.
- `standing.tsx:563` stays an `===`, so it is the line a reviewer should check.

The `WaitTriaged` 1 → 2 upcaster (`upcast.ts:155-166`) keeps writing `'GrantFixRound'`, because that value is a `TriageAdvice` and stays one. Its comment's last sentence, *"`WaitResolved`'s `Resolution` needs no step"*, stops being true here. Edit it to point at the new step.

### 2. Two of the new tags already exist in the domain as route tags

`attempt-next.ts:51` has `_tag: 'FixRefusal'` (a route) and `attempt-next.ts:108` exports `RerunStep` (the walk's route, which #1241 kept). Both are exported through `export *` in `packages/domain/src/index.ts`. So:

- **Keep the resolution's zod consts unexported.** Today they are file-local (`wait.ts:247-263`). Suffix them as `FixRefusalResolution`, `RedoStepResolution` and so on, so the file reads unambiguously beside `attempt-next.ts`. An exported `FixRefusal` from `wait.ts` would clash with the existing one.
- **The reducer reads both kinds.** `ticket.ts:668` and `:1014-1017` test `resolution._tag === 'RerunStep'`, and that becomes `'RedoStep'`. `attempt.ts:621` tests `next._tag === 'RerunStep'`, which is the walk's and **does not change**.
  - Do not use search-and-replace on `RerunStep`. Rename only the occurrences typed as `Resolution`.
  - The ticket's grep in `Done when` will still find the walk's `RerunStep` in `attempt-next.ts`, `attempt.ts`, `routing.ts` and `run-codec.ts`. Those hits are correct.

### 3. What the stored state holds

- **The resolution sits in `TicketState`.** `state.waits[].resolution.resolution._tag` is read at `ticket.ts:1017`.
- **Rename `RestartRecord` with its field.** `TicketState.restarts` is `readonly RestartRecord[]` with `{ after, restart }` (`ticket.ts:205-208`, `:337`). Make it `newAttempts: readonly NewAttemptRecord[]` with `{ after, newAttempt }`, which matches the `cause.newAttempt` it is copied from at `ticket.ts:575`.
- **Bump the ticket reducer.** `ticketReducer.version` goes 3 → 4 (`ticket-codec.ts:172`), with one comment line naming the new tags and `newAttempts`. A version-3 snapshot is then discarded, never decoded.
- **Old projection rows already fail loudly.** `parseStored` re-encodes and compares (`ticket-codec.ts:150`, *"not part of today's shape"*), and `decodeTicket` throws naming `lingtai projection rebuild <projection>`. Nothing needs adding for the read-that-fails edge, except that the rebuild-equality test should also decode each rebuilt row.
- **`WaitResolved` gets a version step.** Add `WaitResolved: 2` to `BUMPED` (`events.ts:2864`) with the house comment (`// 2: … (0108, #1242). See the upcaster.`). Add the 1 → 2 step in `upcast.ts`, in the style of `TicketReleased`'s at `:143`: rewrite `data.resolution._tag` by a four-entry map and pass every other tag through. No other event carries a `Resolution`; `events.ts:385` is the only field.

### 4. The stale page: the board never posts a tag

Each move on the board is its own server action: `continueFixingCard` (`actions.ts:185`), `rerunStepCard` (`:232`), `requeueCard` (`:329`) and `editBodyAndRequeueCard` (`:364`). Each builds the `Resolution` on the server, as at `:210` and `:254`. A page loaded before the deploy holds the old build's action ids, so after the board restarts its call fails in Next's action lookup before any of this code runs.

**Decision:**
- Rename the four actions to follow the moves (`fixRefusalCard`, `redoStepCard`, `startNewAttemptCard`, `editBodyAndStartNewAttemptCard`).
- **Do not** add a path that posts a tag just so it can be refused.
- The edge holds because the deploy's last step restarts the board and the old action ids stop existing.
- If the client wrapper that calls these actions already turns a thrown action into a message, make that message say *reload the page*, the way `actions.ts:1034` does for a malformed form. If it does not, leave it alone: that is a board-wide behaviour, not this rename's.

### 5. The CLI's refusing verbs must stop before anything is appended

`grant-fix-round`, `requeue` and `rerun` currently go through `answerWith(...)` (`cli.ts:238`, `:265`, and the `rerun` block from `:277`), which resolves the wait. Their replacements must be a separate command that:

- takes the same options, so that `lingtai requeue --issue 12` reaches the refusal rather than an option-parse error;
- **never calls `answerWith`**;
- prints *`requeue` is now `lingtai start-new-attempt`* and exits non-zero.

Keep the `'grant-fix-round': ['issue']` entry at `cli.ts:178` only if the refusing command needs it. The new verbs take over the old ones' entries in `commands.ts:320-356`.

For the per-verb `Done when` test, the "appended nothing" claim should be proven against `createMemoryEventStore()` (`@lingtai/event-store/memory`), so it stays a unit test.

### 6. Checks that stand in for the deploy

The ticket's `Done when` already covers the unit level. In addition:

- **Fixture equality is not enough for the rebuild test.** Two logs that differ only in tags, rebuilt to identical rows, is the whole claim, so the fixture must hold one `WaitResolved` of **each** of the four old tags. It must also hold one `TicketReleased` with `cause: NewAttempt`, so that `newAttempts` is non-empty in the compared rows.
- **The person's check after the deploy stays a person's.** Nothing in `pnpm test` reaches a running daemon, a board build or a live projection. The unit stand-ins are the upcaster test, the rebuild-equality test and the `ADVISED` coverage assertion.
- **The ratchet must not move.** The upcaster step and `resolutionAdvised` are pure and synchronous, and the refusing commands perform no IO beyond the exit, so no `async` function and no `Effect.run*` is added.
