# #1083: design note

## The decision the ticket leaves open: how `answered` and the semaphore fit together

Today, `finish`'s check and its set both run synchronously, before the first `await`. The check is `answered.get(state)` at `create-app.ts:339`. The set is `answered.set(state, …)` at `:369`. The promise stored by that set is created at `:346`. Splitting that check-then-set across a `yield*` reopens the double exchange. The Effect version must keep it **one synchronous step**.

This package already does that once. Copy its shape, not the ticket's wording:

> `// Set and checked in one synchronous step, so two first callers cannot both ensure; masked so an interrupted first caller still fills the cell its joiners wait on.` (`packages/conductor/src/db-tickets.ts:257-259`, the code at `:261-275`)

So `finishEffect(options)` is, in order:

1. **`Effect.suspend(() => { … })` does all of the following in one synchronous body:**
   - Call `forgetLapsedAnswers(now)`.
   - If `answered.get(state)` exists, return `Deferred.await(entry.outcome)`.
   - Otherwise look up the `attempt` and make `const cell = Deferred.makeUnsafe<Outcome>()`.
   - If `state !== null && attempt !== undefined`, do `answered.set(state, { startedAtMs: attempt.startedAtMs, outcome: cell })`.
   - Return step 2.

   Keep the condition on the set exactly as `:368` has it. A `state` this process never issued is not memoised. A return carrying it refuses before the exchange, so two of them cost nothing.
2. **`semaphore.withPermits(1)(…)` around the section `:346-362` holds today:**
   - `convertAndWriteEffect`.
   - Then `issued.delete`, the `latest` reset, `last = settled` and the `mint` update, all as `Effect.sync`.

   They stay inside the permit, for the reason the comment at `:342-345` gives.
3. **`Effect.exit` of step 2, then `Deferred.done(cell, exit)`, then re-raise the exit.** Always complete the cell with the **exit**, not with the success alone:
   - Today a disk defect rejects `outcome` (`:346`). That rejected promise sits in `answered`, so a reload with the same `state` gets the same rejection rather than a second exchange.
   - A cell completed only on success would leave the second caller waiting until the window lapses.

Wrap the whole of it in `Effect.uninterruptibleMask`, with `restore` only around the `Deferred.await` of a joiner (as in `db-tickets.ts:261`). The section between `convertManifest` and the last write must not be cut. `:556-563` explain why: after the exchange, *"the PEM in hand is the only copy GitHub will ever hand over"*. A promise could not be cancelled, so making the section uninterruptible keeps today's behaviour exactly.

The ticket's interruption edge still holds:
- The permit is released however the section ends.
- In practice nothing interrupts: `runPort` is a bare `Effect.runPromise` with no signal (`port-face.ts:10-12`).

**Building the semaphore.** `createCreationSession()` is synchronous and runs at module load, inside the `globalThis` `??=` at `:410`. So build the semaphore with `Semaphore.makeUnsafe(1)` (`effect@4.1.2`, `dist/Semaphore.d.ts:217`), not `Semaphore.make` (an Effect, as `github/src/app.ts:312` uses it). The `converting` variable (`:272`) goes away, and its doc comment moves onto the semaphore. That comment is the one `writeMachineConfig`'s comment points at (`:776-779`): *"It is the `converting` serialisation in `createCreationSession`"*. Update that sentence to name the semaphore, since it calls the serialisation load-bearing.

**The type of `answered`** becomes `Map<string, { startedAtMs: number; outcome: Deferred.Deferred<Outcome> }>`. `Outcome` has no failure channel, because refusals are values. A defect travels through the exit.

## The `readFile` seam

Correction to the ticket: `FinishOptions.readFile` cannot be `(path) => Effect<string | null>`. `configuration` turns a read that fails for any reason other than absence into `unreadable` (`:915-920`), and that becomes the refusal at `:511-520`. `readOrNull` rethrows anything that is not `absent` (`:824-831`).

So the seam is `readFile?: (path: string) => Effect.Effect<string | null, Error>`:
- Its default is the live `readOrNullEffect`, which is `tryPromise`, mapping absent to `null` and failing with the error otherwise.
- `configurationEffect` catches that failure into `unreadable`, with the same words.

Pass the seam to `configuration`'s read only (`:916`). It is the only read before the exchange: the only filesystem calls in `convertAndWrite` before `convertManifest` (`:565`) are the `configuration` call at `:510`. The two reads in `writeMachineConfig` (`:782`, `:805`) and the `exists` in `writeKey` (`:722`) stay on the live functions, and a refused exchange never reaches them.

## The lifts

- **`tryPromise`, with the error kept**, for the reads whose failure today's code handles:
  - `exists` (`:734`): any failure is `false`.
  - `readOrNull` (`:824`).
  - `recordedApp` inside `configuration` (`:902-906`): its failure is `unanswered`.
- **`tryPromise`, with the error kept as the failure**, for the writes too: `writeKey`, `writeMachineConfig`, and the `mkdir`/`chmod` with `KEY_DIR_MODE`/`KEY_FILE_MODE`. Their callers catch the failure into a refusal that carries the recovery steps, so a defect would bypass it. Synchronous throws (`doc.setIn` on `github: null`, `resolvePath`) are lifted with `Effect.try` for the same reason. Keep the arguments exactly as they are, including `flag: 'wx'` at `:815`.
- **`convertManifest` (`:565`)** is lifted as `tryPromise`, because today its rejection is caught into a refusal. Map the failure to that same refusal.

## Edges

The ticket decided its edges. Two notes on top of it:

- **A joiner never re-runs a defect.** A second `finish` with the same `state` after a disk defect gets the same rejection, which is today's behaviour. The state is then done until `ATTEMPT_WINDOW_MS` lapses (`:101`), as now.
- **The log cannot show a double exchange.** `GitHubAppCreated` records only `appId` and `slug` (`:167-168`), never the `state`, so two events say nothing about whether one code was spent twice (two Apps with different ids would show it, but that is GitHub's refusal, not the guard's). The unit test below is the check.

## The unit test

- **Location:** `packages/conductor/unit/create-app-finish.test.ts`.
- **Setup:**
  - `createCreationSession()`, then `begin()` to get an issued `state`.
  - `fetch` stub: a `Deferred`-gated fake that answers 422.
  - `readFile` stub: `() => Effect.succeed(null)`.
  - Store: `createMemoryEventStore()`.
  - `env: {}`.
- **Run:** start two `finish` calls with the same `state` and `code` *before* releasing the gate. Then release it.
- **Assert:**
  - `fetch` was called once.
  - Both results are `===` the same refusal.
  - The memory store holds no events.
- **Filesystem:** set `configFile` and `keyPath` to paths that do not exist and are never touched. A refused exchange writes nothing, so the test proves that too.

This test is the unit-level stand-in for the written-key half. That half stays in `integration/create-app.test.ts`, which runs after the merge and not before it.
