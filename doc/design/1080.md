# #1080: the shape

Line numbers below are this worktree at `ee45d64c`. They have moved since the ticket's `8abc8613`, so where they differ the ticket's numbers are out of date and these are the current ones. The ticket already gives the mechanical change (`await` → `yield*`, the four faces, the baseline down 15 from today's 64 at `effect-ratchet.baseline.json:9`). This note covers the three places where a naive conversion changes behaviour without any test going red.

## 1. Which failures stay typed and which become defects: decided per call site, not per file

The ticket's edge says *"any other store failure is a defect"*. That rule is right for the tells and wrong for the claim and the release. Today those two catch **every** rejection, not only `ConcurrencyError`:

- **Claim and continue.** `conduct.ts:2689-2706` lifts both with `Effect.tryPromise({ …, catch: (error) => error })`. `:2707-2716` then turns *any* failure into `mayHold`, setting `onStream = ticketId` because *"the append may have committed, so the item may be held by this run"*. Suppose `claimTicketEffect` lifted `readState` or `store.append` with `Effect.promise`. A dropped connection would then be a defect. `Effect.result` does not see defects, so it would escape the `Effect.uninterruptible` region at `:2677` with `onStream` still `null`. The release at `:1517-1521` would answer *nothing to release*, and a ticket the append did write would be held by nobody. That is 0122's failure, caused by a refactor.
  **Decision:** `claimTicketEffect` and `continueTicketEffect` lift each store call with `Effect.tryPromise({ try, catch: (e) => e })`, so the error channel is `unknown` and the call site keeps `Effect.result` unchanged. The `ConcurrencyError` → `lost-race` refusals (`claim.ts:183`, `:243`) stay inside, as `Effect.catchIf`/`catch` on that one class.
- **Release.** Today's `.catch` at `conduct.ts:1528-1531` takes any rejection from `releaseTicket` (`claim.ts:263-270`: a read and an append) and answers `backInTheQueue = false` plus the log line *"the item was not released"*.
  **Decision:** `releaseTicketEffect` fails typed with whatever the store rejected with, lifted the same way. The release answers it with `Effect.catch`/`Effect.result` and the same log line.
- **Tells, end actions, `armsOnOrigin`.** Every call site lifts these with `Effect.promise` today (`conduct.ts:1329`, `:2796`, and the rest). A rejection is a defect now and stays one, so the helpers may lift their port calls with `Effect.promise`. Where a helper catches internally today, it keeps doing so: `sweepRefsHeld` writes `IssueUpdateFailed`, and `tellGitHub` writes its record.

## 2. The release swallows the whole cause, not just the failure

Today the release body is `Effect.tryPromise({ try: async () => …, catch: (err) => err }).pipe(Effect.ignore)` (`conduct.ts:1524-1556`). That swallows a throw from any of its three steps, including `tellGitHubAbout`. The comment there gives the reason: *"one that threw would replace the reason the run ended with the reason the cleanup did."*

Once `tellGitHubAboutEffect` dies on a GitHub or store rejection, `Effect.ignore` no longer catches it. So the shape is:

```
released = true
Effect.uninterruptible(body).pipe(<catch the cause: log it, succeed with void>)
```

Use the cause-catching combinator this file already uses: `Effect.catchCause` at `:2606`, so it is Effect 4's name. The catch goes **outside** the `uninterruptible`, so a defect in the body still stops the body. Only its escape is stopped.

Inside the body, `appendAt` is still `async`, because it belongs to CONDUCT8-6 and is out of scope. It stays lifted with `Effect.tryPromise`, and its existing failure answer (*"end actions not recorded"*, `:1537-1540`) stays as a catch on that lift. The ticket's grep names no `appendAt`, so this lift is allowed.

## 3. The base check's in-flight map has to keep sharing across passes

`createBaseCheck` (`base-check.ts:83-201`) does more than call `check`. Its `inFlight` map hands two passes that ask the same `[stream, baseSha, command]` **one** run (#744, the comment at `conduct.ts:283-286`: *"its in-flight map is what makes two passes asking about one commit and command one run"*). It also turns any rejection into `{ verdict: 'unknown', why }` (`base-check.ts:196`).

A literal conversion that stores an Effect in the map would re-run the check for every asker. One that stores a fiber forked from the first asker's fiber would let that pass's interruption kill the second pass's answer, and leave a cut worktree unremoved.

**Decision:**
- `ask` returns `Effect.Effect<BaseCheckAnswer>` that never fails.
- The map holds `Fiber`s started with `Effect.forkDaemon(checkEffect(q, stream).pipe(<catch the cause → unknown>), Effect.ensuring(delete key))`. Each asker `Fiber.join`s.
- The daemon fork keeps today's property that the check runs to the end whoever stops waiting, which is what `Effect.promise` around a promise gives now.
- The `record` loop's `setTimeout` (`:184`) becomes `Effect.sleep`.
- `deps.run` (`runCommand`, a face in `effect-ratchet.faces.json`) and `tree.cut`/`remove`/`plant` stay promise ports, lifted inside `check`. `conduct.ts`'s `tree` callbacks already use `Effect.runPromiseWith(services)` (`:3670`), which the ratchet does not count.
- The call site at `conduct.ts:3678` becomes `yield* baseCheckFor(store, log, home).ask({…})`.

Accepted cost: the daemon fiber does not inherit the pass's span, so #791's trace stops at the join for the base check alone.

## 5. The interruption test

The ticket's `Done when` asks for a `Deferred`-gated fake `tellGitHubAbout` inside the release.

The fake goes on `options.client`'s issue port, the `IssueChannel` call the labels write reaches, and waits on the `Deferred`. The test then:

1. interrupts the pass fiber;
2. completes the `Deferred`;
3. awaits the fiber's exit;
4. reads the memory store for `TicketReleased`, and for `EndActionsResolved` with `failed` when an end plan is set;
5. asserts that the labels call was recorded.

It uses no timer. Model it on `a-claim-is-not-split-by-an-interrupt.test.ts`, which already interrupts across `uninterruptible`.
