# #787 — the page span: the shape

## `measure`: the span goes on the outside and the scope goes on the inside

`measure` (`apps/board/src/lib/timing.ts:47-67`) starts a span with `trace.getTracer('lingtai-board').startActiveSpan(\`page ${label}\`, { root: true }, async (span) => …)`. **Inside** that callback it runs the existing `scope.run({ now, entries, calls: 0 }, fn)` (`:55`). The order matters. `timed` takes its parent from the active OTel context (`:82`) and its `<meta>` entry from the `AsyncLocalStorage` scope (`:84`). Both have to be live when `fn` runs, and opening the span first makes it active for everything `fn` awaits.

Inside the span callback:

- `catch`: `span.setStatus({ code: SpanStatusCode.ERROR })`, then rethrow. Never read the error and never call `recordException`. `timing.ts:106-107` says why: *"its message may carry a URL or a token"*.
- `finally`: `span.end()`, plus the existing slow-page `say(...)` block (`:58-65`) unchanged. The stderr line keeps its own `now()` clock. Don't derive it from the span.
- Set no attribute on the page span. It carries no count, so it ends up with no attributes at all.

The default `label` stays `'/'` (`:51`). A `measure` called without options, such as `unit/timing-load-task.test.ts:86`, becomes a `page /` span. That is harmless.

Add one sentence to the doc comment at `:46`: a page that loads outside `measure` has no root span, and its reads export as orphans. That covers the ticket's cost-to-later-tickets edge.

## Every page uses the same read names

| page | read | name | how |
|---|---|---|---|
| `/` | `readDayReading()` (`app/page.tsx:612`) | `spend.day` | a fourth element of the `Promise.all` at `:605-609` |
| `/spend` | `loadBoard(only)` (`app/spend/page.tsx:43`) | `board.load` | `timed` around the call |
| `/spend` | `readDayReading({ fetchedNote: true })` (`:44`) | `spend.day` | same name as on `/`, since it is the same read |
| `/report` | `currentReport(...)` (`app/report/page.tsx:64`) | `report.read` | see below |

`readDayReading` never throws. Its doc comment (`lib/day-spend.ts:37`) says *"Never throws"*, and it signals failure with a value: `short: 'today unreadable'` (`:47`). So both of its `timed` calls pass `failed: (r) => r.short === 'today unreadable'`. Without that, a failed read records as a success. This is the case `TimedOptions.failed` exists for: *"For a read whose failure is a value, not a throw"* (`timing.ts:72`).

On `/spend`, `board.load` is a parent span, not a leaf: `loadBoard` already times `tasks.read`, `board.queue` and `spend.read` inside itself (`lib/board.ts:1100,1121,1129`). So the trace reads `page /spend → board.load → spend.read`, and the `<meta>` list carries overlapping entries. That is acceptable. On `/`, don't wrap `loadBoard`. The ticket asks for it on `/spend` only.

On `/`, keep the destructure flat. Moving `today` into the tuple is all that changes. `readDayReading` takes nothing from the other three reads, so running it in parallel changes nothing but the timing.

## `/report`: `measure` goes inside the existing `try`

`page.tsx:63-80` turns a thrown `currentReport` into a rendered failure sentence. Put only the read inside `measure(() => timed('report.read', () => currentReport(query.project, query.window.from)), { label: '/report' })`, inside the existing `try`. `buildReport` and the chip stay where they are. A failed read then marks both `report.read` and `page /report` as ERROR, and the `catch` renders the page exactly as it does today. Don't widen `measure` to cover `buildReport`. That is pure computation, not a read, and if `measure` wrapped the whole `try`, a failed read would never mark the page span.

`/spend` has no `try`. Wrap both reads in a single `measure(..., { label: '/spend' })` holding a `Promise.all`. They are independent: `day-spend.ts:2-4` says readDayReading reads every project's rows and never `loadBoard(only)`'s.

## Render the `<meta>` list on `/spend` and `/report`

`measure` returns the timings, and `<TimingMeta>` (`lib/timing-meta.tsx:4`) renders nothing for an empty list. Render it on both pages, as `/` and `/task` already do (`app/page.tsx:644`, `app/task/[id]/page.tsx:906`). On `/report`, a failed read means `measure` never returns a value, so there are no timings. Declare `timings` as `let` with `[]` before the `try`.

## The test goes in `unit/telemetry.test.ts`

That file already has the setup the new test needs:

- `installTracing(on, none, exporter)` with an `InMemorySpanExporter` (`:40-50`);
- the `afterEach` that calls `trace.disable()` / `context.disable()` (`:13-16`);
- `installTracing` registering the `AsyncLocalStorageContextManager` (`lib/telemetry.ts:72`). Without that, `startActiveSpan` does not pass the parent across an `await`, and the children-have-a-parent assertion would fail for a reason unrelated to the code under test.

The parent field is `parentSpanContext?: SpanContext` on `ReadableSpan` in the installed SDK 2.12.0 (`node_modules/.pnpm/@opentelemetry+sdk-trace@2.12.0…/build/src/export/ReadableSpan.d.ts:9`). There is no `parentSpanId`. Write the assertions as:

- root: `page.parentSpanContext === undefined`;
- each child: `child.parentSpanContext?.spanId === page.spanContext().spanId`;
- every child has the same `traceId`.

**Test that `root: true` is doing its job.** Open a foreign-scope span around the `measure`: `trace.getTracer('next.js').startActiveSpan('GET /task', …)`. This stands in for Next's request span. `OnlyScope` drops it, and `page /task` must still have no parent. Without the wrapper, the test passes even if `root: true` is deleted, which is exactly the trap in the ticket's *Watch out*.

The other two *Done when* checks:

- **Attributes:** every exported span's attribute keys are a subset of `['lingtai.count']`.
- **Names:** no span name matches `/\/\d+(\/|$)/`.

The error test is a `measure` whose `fn` rejects with `new Error('https://x?token=y')`. The `page /task` span has `status` `{ code: 2 }` with no `message` key, `events` is `[]`, and the rejection is the same object. This mirrors `:62-73`.

`/spend` and `/report` are async Server Components. The only test that renders them is the Next build, which runs in the integration half (`apps/release/integration/build.test.ts`), so nothing checks their wiring before the merge. What stands in at unit level is the `measure` and `timed` tests above, plus `pnpm typecheck` over the pages.
