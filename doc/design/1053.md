The ticket's shape holds. Four things in it are not obvious from the ticket or are easy to get wrong.

## 1. The catch in `runStepBody`: check for an interruption first, then the defect

The ticket allows `Effect.catchDefect`. **Don't use it.** In the version this repository resolves (`packages/conductor/package.json:69` → `effect@4.1.2`), it recovers *any cause that contains a Die*, including one that also carries an Interrupt:

- `node_modules/.pnpm/effect@4.1.2/node_modules/effect/dist/internal/effect.js:1447`: `catchDefect = … catchCauseFilter(self, findDefect, f)`.
- `:100`: `findDefect` is `self.reasons.find(isDieReason)`.
- `Effect.d.ts:5332` warns about this: *"`catchDefect` recovers any cause that contains a defect, including causes that also contain typed errors."*

So an interrupted step whose finalizer died would become *did-not-finish: threw*. That is a verdict made out of a drain, the exact thing *Watch out* forbids.

Use the order #1041 already uses one layer down (`packages/actions/src/action.ts:1005-1019`):

1. `Effect.exit` the body.
2. Success: return the value.
3. `Cause.hasInterrupts(exit.cause)`: `Effect.failCause(exit.cause)`, untouched.
4. Anything else: `threw(spec, Cause.squash(exit.cause))`.

Every error channel is `never`, so step 4 only ever sees a defect.

**The catch must still carry what the step had already learned.** Today's `catch` returns `{ step, ending: threw(spec, error), results, outcome }` (`run-attempt.ts:2060-2061`). `outcome` is set by the pipeline before the body runs, and its doc says it is carried *"onto every return below it, including a body that then threw"* (`:1933-1939`).

- Keep `results`, `outcome`, `leftTheTreeAt` and `wroteTheDesign` as `let`s declared **outside** the `Effect.gen`, assigned inside it, and read by the `Exit` match.
- A refactor that turns them into the generator's locals still typechecks. It then reports a throwing `implement` with no `outcome`, and `nextOf` reads that differently.

## 2. The catch covers what it covers today, and `begin`/`finish` stay outside it

`runStep` runs `begin` (the `StepStarted` write) and `finish` (the `StepEnded` write) inside the span but **outside** `runStepBody`'s `try` (`run-attempt.ts:1904-1906`). Keep that boundary exactly.

`trace-an-attempt.test.ts:271-278` pins it. A refused `StepEnded` append must:

- leave the pass `{ ok: false, stage: 'unexpected' }`, not *threw*;
- leave `step implement` `ERROR`.

So `finish`'s rejection is a defect that leaves the step's `withSpan`. `BridgedSpan.end` turns that exit into `ERROR` by itself (`telemetry.ts:79`).

The `end` step keeps its spanless branch (`:1903`); `tell.ts` makes its span. Lift `begin` and `finish` with `Effect.promise` for now.

## 3. The order inside a step span

Write a step as

```
Effect.gen(begin → runStepBody → finish)
  .pipe(Effect.onExit(failure → Effect.annotateCurrentSpan(FAILED, true)),
        Effect.withSpan(`step ${spec.step}`, { attributes: { 'lingtai.round': … } }, { captureStackTrace: false }))
```

- **`onExit` comes before `withSpan` in the pipe.** Otherwise the annotation lands on the parent span, and every failed step marks the run directly rather than through the rule below.
- **Build `runActionPipelineEffect({...})` inside the generator, never in `runStep`'s argument list.** It captures `context.active()` when it is called (`action.ts:870-875`). Called outside the `withSpan`, it captures the run span, and every `action <kind>` span becomes a sibling of its step. The test at `trace-an-attempt.test.ts:107-120` catches that, but only after a full red run.
- `step proposed` (`run-attempt.ts:1331`) follows the same rule.

## 4. `telemetry.ts`: what the parent rule needs from `BridgedSpan`

- `attribute(FAILED, true)` today only sets the status and returns (`telemetry.ts:88-91`). It leaves no record that `end` can read. Add a `failed` field, set there.
- In `end`: if `this.sink.errored || this.failed`, and `this.parent` is `Some` and an `instanceof BridgedSpan`, set `parent.sink.errored = true`.
  - A child always ends before its parent, so the parent's `end` sees the flag.
  - A non-bridged parent (`trace.wrapSpanContext`, `:63`) has no sink and is skipped.
- A bare `Exit.isFailure` must **not** propagate. Typed failures of inner Effect spans stay local, which is the second half of the telemetry test in *Done when*.

**What stays unchanged:**

- `inSpan` under a bridged span already reports to the right sink: the tracer's `context` hook installs `span.sink` (`telemetry.ts:105-107`). So the `action judge` span inside `step proposed` needs no change.
- Where nothing installs the bridged tracer (the promise faces, most unit tests), `Effect.withSpan` falls back to Effect's native tracer and nothing is exported, as today when no endpoint is set.

## The interruption test

- Fork `runAttemptEffect(attemptPortsFrom(…))` with `Effect.forkChild`, using an action port whose `run` is `Deferred.await` on a deferred nobody completes.
- To know the port has been entered without a timer, have it complete a second `Deferred` first, and `Deferred.await` that before `Fiber.interrupt`.
- Then assert:
  - `Exit.isInterrupted` on the `Fiber.await` result;
  - the memory store holds a `StepStarted` and no `StepEnded` for that step.

This runs without Postgres, the clock or a process, so it belongs in `unit/`.
