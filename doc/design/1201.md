## Design: #1201, rerun a run that a transient API error cut off

### The decision the ticket gets slightly wrong: `Reaching` is not the whole brief

Keeping the cut-off visit's `Reaching` is necessary but does not give the rerun the same brief. `runVisit` works out the two facts that make up the brief from the **`reached` list**, not from `Reaching`:

- `design: designOn(reached)`
- `again: … sentBackTo(spec.step, reached)` (`packages/conductor/src/run-attempt.ts:2358-2365`)
- `firstVisitOfFrom`, which decides `waive`/`readClipped`, also reads `reached` (`run-attempt.ts:2328`).

`runStep` is handed `[...steps]`, a copy taken at call time (`run-attempt.ts:1815-1819`). The crashed visit is then pushed by `record` (`run-attempt.ts:1460-1464`). The rerun must therefore be handed **two** things captured at the cut-off visit's call site:

- `visitContext` (`run-attempt.ts:1803`)
- that `[...steps]` snapshot

Leave the crashed visit in `steps`. It is real history: it has its own `StepStarted`/`StepEnded`. Every later `sentBackTo`/`designOn` reads the end of the list, and after the rerun the end is the rerun's visit, so they still work.

Shape: when the `WaitOnPerson` branch (`run-attempt.ts:1964-1972`) decides to rerun, set a loop-local `rerun = { reached, context, n }`, leave `at` unchanged and `continue`. At the `runStep` call, use `rerun?.reached ?? [...steps]` and `rerun ? { ...rerun.context, rerun: rerun.n } : contextFor()`, then clear `rerun`. Nothing between the loop top and `runStep` runs twice:

- the conflict-evidence read is guarded by `conflictEvidenceRead` (`:1739`);
- the granted pre-merge is guarded by `grantedConflictMerged` (`:1781`);
- a fix round's conflict pre-merge happens in `routing` (`:1690-1708`), and a rerun never routes.

### The count: follow #1200's pattern exactly

- Add `let transientRetriesSpent = options.from?.transientRetriesSpent ?? 0` beside `baseMergesSpent` (`run-attempt.ts:1364-1366`), with the matching `from` field (`:994-996`).
- Add `transientRetries: run.transientRetries ?? 0` to `continuationSpent` (`packages/conductor/src/conduct.ts:756-759`), passed through where `baseMergesSpent` is (`conduct.ts:1354`, `:5153`). This is how *a continuation keeps it*.
- The reducer case in `packages/domain/src/attempt.ts` (beside `baseMerges` at `:603`) sets `transientRetries` from the event's `rerun` with `Math.max`, the same idiom. It does not do `+1`, so a replay cannot double it.
- Declare `StepRerunInPlace { step, rerun, said, waitMs }` in `events.ts`.
- `attempt.ts:248`'s comment (*"Nothing raises it yet"*) changes.

### classify and respond

Today `classify` has no transient runtime kind. `RuntimeRow.kind` is `'account-limit'` only (`packages/domain/src/failure/classify.ts:70-75`, `Classified` at `:33-39`).

- Widen both to `'account-limit' | 'transient'`.
- Append the transient rows **after** the three account-limit rows (`:150-178`). Row order is precedence (`classify.ts:7-12`), and that is what makes an account wall that also contains `503` an account wall.
- Give every transient row `runtime: 'claude-code'`, the Cloudflare row included: it is Claude Code relaying its API's edge. `doc.ts` splits rows into sections by `runtime` (`failure/doc.ts:40-52`), so a row with no runtime would not render.
- Match Cloudflare on `Attention Required! | Cloudflare`, never on `403`.
- The one existing runtime caller already checks `kind === 'account-limit'` (`wallOf`, `conduct.ts:306-309`), so the new kind cannot be read as a wall. Keep it that way.
- Regenerate the doc with `pnpm docs:errors` (`package.json:25`). `packages/domain/unit/failure-classify.test.ts` holds the generated section to the rows.

There is no `respond` function today. `respond.ts` has only the constants (`:500-503`) and `offerFor`. Add one pure function, `rerunInPlace(cause, detail, spent) → { wait } | null`. It answers `null` when:

- `cause !== 'crash'`
- `classify({ platform: 'runtime', text: detail })?.kind !== 'transient'`
- `spent >= TRANSIENT_RETRIES_LIMIT`

Otherwise it answers `TRANSIENT_WAITS[spent]`. It is unit-testable alone. The walk gates on step too: rerun only at `design`, `implement` or `review`. A `proposed` judge crash is out of scope, and `merge` is #1221's.

In the walk, in this order:

1. `yield* options.emit(StepRerunInPlace)`
2. `yield* Effect.sleep(wait)`
3. `continue`

Emit before sleeping, so a daemon that dies during the wait has already spent the count, as the ticket's Edges decide. `waitMs` is `Duration.toMillis` of the same input the sleep gets. The sleep is an Effect inside the walk, so the ratchet is untouched.

### The dispatch id: one field on `ActionContext`, four call sites

The walk cannot see dispatch ids; each is built where its agent is dispatched. Add `rerun?: number` to `ActionContext` (`packages/actions/src/action.ts`, near `onSha` at `:522`), plus a helper there, `rerunId(id, context)`, which appends `:rerun:${n}` when `rerun` is set. Apply it at:

- **design**: `draftId`, `packages/actions/src/agent-action.ts:1639`
- **review**: `reviewId`, `agent-action.ts:933`. It is keyed on `onSha`, which the rerun keeps, so it would collide without the suffix.
- **fixer**: `fixId`, `conduct.ts:4773-4776`. The suffix goes on both branches.
- **implementer**: `conduct.ts:4449-4450` (`invocation`) and `:4568-4569` (`dispatched.run`). **Only those two.**

At the implementer, `runId` is also the attempt's **stream and hook key**. These must keep the bare `runId`:

- `host.wire({ runId })` (`:4426`)
- `server.register`/`unregister`/`flush`/`get` (`:4555-4585`)
- `recordPrompt(store, runId, …)` (`:4543`)
- `appendFrom(runId, …)` (`:4616`, `:4656`)
- the `stream:` half of `sandboxOf` (`:4581`)

Renaming those would send the rerun's hook events and its `RunFailed`/`RunSpent` to a stream nobody reads. Only the session id derives from the dispatch id (`packages/agent/src/claude-code.ts:91`, `:269`).

### startedAt

`startedAt` is taken fresh inside `firstDispatch` (`conduct.ts:4423`), and the walk cannot supply it. Keep a pass-level `let implementerStartedAt: string | null` in the same closure as `stoppedBy`:

- set it on a dispatch whose `brief.context.rerun` is undefined;
- reuse it when `rerun` is set.

The fix round needs nothing here: it already compares against `brief.context.onSha` (comment at `conduct.ts:4416-4418`), and the rerun is handed the same context. A second `host.wire` and smoke test on the rerun is acceptable: it re-proves the hook fails closed, and costs no agent.

### Where each Done-when is checkable (all unit)

- **Waits, count, per-attempt limit, timeout, account wall, sentence on no row**: `packages/conductor/unit/run-attempt.test.ts`. Use stub bodies whose `implement`/`review` end `did-not-finish` with `interrupted: 'crash'` and a detail. Read `waitMs` off the emitted `StepRerunInPlace`. To prove the sleep, fork the walk and `TestClock.adjust`.
- **Distinct dispatch ids, byte-equal fix-round prompt, the not-*produced-no-commits* case**: `packages/conductor/unit/conduct-a-whole-attempt.test.ts`. They need conduct's closures. Use a fake runtime that records `request.runId`, and read `RunPrompted` off the stream.
- **Row tests**: `packages/domain/unit/failure-classify.test.ts`.

What settles whether a real cut-off ever matches is the log: `RunFailed.detail` with `kind: 'crash'` on an attempt stream shows what Claude Code actually printed. A row matches as a substring, so the `crash: ` prefix that `stopped` adds (`conduct.ts:4640`) does not matter.
