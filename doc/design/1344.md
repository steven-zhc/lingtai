## Design: #1344 — each part of the answer form is drawn in its own card

### Where it goes

All the work is in three files. Nothing in `packages/` changes.

- **`apps/board/src/app/decide.tsx`**: `EditBodyAndRequeue` (`:385`) gets a `part` prop.
- **`apps/board/src/app/standing.tsx`**: the call site at `:1766-1776` draws the form once per card, each time with a different part.
- **`apps/board/src/app/globals.css`**: one rule changes (`:1688`).

### What each part draws

`part: 'answer' | 'edit'`. The default is the whole form as it is drawn today, so the direct-render tests in `apps/board/unit/edit-body-and-requeue.test.tsx` keep pinning what gets sent. `standing.tsx` always passes a part.

- **`'answer'`**, drawn in the `AnswerQuestions` card:
  - the choices for `ownAsked` (`decide.tsx:427`). It never draws `triageAsked`, because the triage block already draws those (`standing.tsx:535-538`).
  - the *Answer and continue the step* button (`decide.tsx:472-505`), with the same guard, `disabled` and `title` as today.
  - It draws nothing at all when `waitId === null`.
- **`'edit'`**, drawn in the `EditBodyAndStartNewAttempt` card:
  - the *"no longer waiting on you"* paragraph (`:449-453`)
  - the prose `question` (`:456-457`)
  - the textarea
  - the body-edit button (*Answer* or *Write it into the body…*, `:506-529`)
  - It draws no `TriageChoices` at all.
- **`answerOnly` (#1254)** is the `'answer'` part plus `triageAsked`. That wait has no `EditBodyAndStartNewAttempt` card, so the condition at `standing.tsx:1767` that draws the form in the `AnswerQuestions` card stays as it is. The questions appear twice there: once in the triage block, once in the card. That is how it is drawn today, and its test (`:1655`) pins it, so leave it alone.

### A decision the ticket leaves open: where the agent's own questions go

The ticket says to keep drawing `ownAsked` *as today*. Today that means in the edit card. But an `AgentQuestion` that has questions is allowed both `AnswerQuestions` and `EditBodyAndStartNewAttempt` (`packages/domain/src/wait.ts:384-386`). If its choices stayed in the edit card while *Answer and continue* moved to the answer card, the choices would sit in one card and the button that sends them in another. That is this bug again.

**Decision: the agent's own choices go with the button that sends them, in the `'answer'` part.** This keeps the ticket's actual rule: only `triageAsked` is skipped, because only that set is drawn somewhere else.

The edit card's textarea still fills itself from the composed picks: `TriagePicks` composes `asked` into `text` (`triage-picks.tsx`, the `composedAsked` line). So the body-edit *Answer* sends exactly the same text as before.

A prose `AgentQuestion` (`questions.length === 0`) is not offered `AnswerQuestions` (`wait.ts:386`). Its question and its *Answer* button stay in the edit card, unchanged.

Check `edit-body-and-requeue.test.tsx:453-560` (the `AgentQuestion` cases). They render the component with no `part`, so they should stay green. Any test in `standing.test.tsx` or `task-page.test.tsx` that finds the agent's choices inside the edit card's HTML is asserting the old arrangement and should be changed to look in the `AnswerQuestions` card.

### Shared pending state lives in `TriagePicks`

Today `pending`, `doneWaitId` and `detail` are local `useState` in `EditBodyAndRequeue` (`decide.tsx:402-404`). Two instances would mean two separate copies. Then pressing one button would leave the other enabled, which breaks the ticket's *pressing twice* edge.

`standing.tsx` is a server component: it has no `'use client'`, and it wraps the page in `<TriagePicks>` at `:1281`. So the only client parent the two cards share is the `TriagePicks` provider.

- **Add a sending slot to `TriagePicks`'s context**: `{ pending, doneWaitId }` and a setter. Both parts use it to disable their buttons.
- **`detail` stays local to each part**, so a result message appears in the card whose button was pressed.
- **Without the provider** (a standalone render, `triage === null`), fall back to local state. The answer button already needs `triage !== null` (`decide.tsx:474`), so only the edit button ever uses that fallback.

### CSS

At `globals.css:1688`, the line becomes `.sresolutiongrid > .sresolution--recommended:not([hidden]) { grid-column: 1; }`. Drop `grid-row: span 2` and `align-self: stretch`.

- Leave the grid's `align-items: stretch` (`:1660`) as it is. It is #596's *rows as tall as their tallest card*.
- After the split, the tallest card in the first row is the edit card: textarea and button, about 200px.
- The narrow-breakpoint override `grid-row: auto` (`:1692`) now does nothing. Removing it is optional.
- `.sresolution[data-resolution='EditBodyAndStartNewAttempt']:has(.sresolutionaction:empty)` (`:1680`) still hides an edit card whose part rendered nothing. Make sure the `'edit'` part still returns `null` under the same condition as `:445`.

### Tests

These are the claims the ticket's *Done when* boxes rest on. Add them to `standing.test.tsx`, sliced by `data-resolution` as `:1348` already does.

- **Triage asked, edit allowed:**
  - The page's HTML contains each triage option's label once.
  - The `AnswerQuestions` slice contains *Answer and continue the step*.
  - The `EditBodyAndStartNewAttempt` slice contains a `<textarea` and no `TriageChoices` markup.
- **Agent's own `AgentQuestion`:** the `AnswerQuestions` slice contains its choices and its button.
- **Pressing twice:** with both parts under one `TriagePicks`, a click on *Answer and continue* disables the body-edit button too. That needs a DOM render, the way `edit-body-and-requeue.test.tsx` already does it.

Card height is checked by a person in a browser. No unit test can see it, and none should compare pixels.
