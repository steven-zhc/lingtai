# Design: #273 — the suite's locks go in a directory made for the run

## Where the change goes

Change the **fallback** in `createFileLocker`, not the call sites. The fallback is `packages/env/src/lock.ts:245`, which today reads `const dir = options.dir ?? join(stateDir(), 'locks')`. Under test it should resolve to a directory that `globalSetup` created for this run. This is the same move #275 made for the store: `storeChoice` answers `LINGTAI_TEST_SQLITE_PATH` under `inTest` (`packages/env/src/index.ts:575`), and `teardown.ts`'s `setup()` creates the file with `mkdtemp` (`packages/event-store/test-support/teardown.ts:112-115`). Locks follow the same pattern.

### Why not pass `options.dir` at each call site

The ticket's **Fix** row suggests that, and here it would be wrong. Most of the residue does not come from test code. It comes from production code that the tests drive, and that code calls `createFileLocker()` with no argument:

| key prefix in the residue | taken by |
|---|---|
| `decide:` (3556 files) | `packages/conductor/src/approve.ts:55`, `createFileLocker().tryLock(\`decide:${workItemId}\`, …)` |
| `lingtai:test:` | `packages/daemon/src/daemon.ts:108` (`options.locker ?? createFileLocker()`), `apps/cli/src/conductor-lock.ts:71`, `apps/cli/src/lingtai.ts:650` |
| `board:` | `apps/cli/src/init.ts:850`, `apps/cli/src/lingtai.ts:593` |

`merge:` (176 files) has no current taker in `src/`. It is history from the integrator that `db811442` and the commits before it removed, and it needs nothing from this change.

**A per-test `dir` also breaks a test silently, without making it fail.** `apps/cli/integration/conductor-lock.test.ts:21` builds `createFileLocker()` and holds `lingtai:test:<hex>` with it (line 27). It then calls `run()` in-process and expects `run` to be refused (lines 35-43). `run` finds the holder through its own `createFileLocker()` at `conductor-lock.ts:71`. If only the test's locker moved, the two would look in different directories, `run` would find the lock free and claim, and "refuses while something else holds the lock" would be asserting about two unrelated directories. Locks only exclude each other when they share a directory. That is why the directory has to come from one resolver that every process in the run reads, and why it is carried in the environment rather than as an argument.

## The resolver

Put it in `packages/env/src/index.ts` next to `stateDir()` (line 945), exported, because `inTest` (line 45) is private to that module. `lock.ts` already imports from `./index.ts` (line 67). Call it something like `lockDir(from = process.env)`. It answers in this order:

1. **`from.LINGTAI_HOME` is set** → `join(stateDir(from), 'locks')`, exactly as today. This is the `ownHome` rule at `index.ts:105-106`: *"An environment that names its own `LINGTAI_HOME` reads that one: it is how `lingtai doctor` and a test are pointed at a home of their own."* `doctor.test.ts:907` and `doctor-recipe.test.ts:40` set it on `process.env`, and `world.test.ts:271,351` give spawned children `LINGTAI_HOME: dir`. Those keep working unchanged.
2. **`inTest(from)`** with `LINGTAI_TEST_LOCK_DIR` set → that directory.
3. **`inTest(from)`** with it unset → **throw, naming `LINGTAI_TEST_LOCK_DIR` and `globalSetup`**. Do not fall back. This is how `storeChoice`'s test side refuses (`notSetUp(\`${name} or ${PREFIX}TEST_SQLITE_PATH\`, null)`, `index.ts:585`). The refusal is the ticket's *"a test fails if a lock is taken under `stateDir()` during the suite"*: any path you missed fails loudly instead of leaking.
4. Otherwise → `join(stateDir(from), 'locks')`.

`lock.ts:245` becomes `options.dir ?? lockDir()`. Update the `FileLockerOptions.dir` comment at `lock.ts:139` to match. It currently says *"`~/.lingtai/locks`, or `$LINGTAI_HOME/locks`"*, and after this change that is true only outside a test.

**`$LINGTAI_HOME` is not the variable to use for this.** The ticket's **Watch out** row already explains why: it also moves config, recipes and runs. `stateDir()` itself stays as it is.

## The directory

In `teardown.ts`'s `setup()`, create the directory with `mkdtemp(join(tmpdir(), 'lingtai-test-locks-'))` and export it as `LINGTAI_TEST_LOCK_DIR`. Do this **unconditionally**, before the early `return` at line 113 that skips the SQLite branch when a Postgres URL is set, because locks are needed with either store.

The module comment already explains why a fixed name under `tmpdir()` is wrong: *"two worktrees running the suite at once would share it. The directory has to be made fresh, by this run, for this run."* Workers inherit it because the forks are made after `globalSetup` runs (same comment, lines 52-56). Spawned children inherit it with the rest of `process.env`.

`teardown()` removes the directory. That removal has to come **before both early returns**: the `LINGTAI_KEEP_TEST_DATA` one (line 119, where you may choose to keep the directory too) and the `if (sqliteDir) … return`.

**This removal does not break `lock.ts:43`'s rule.** The rule exists because *"a process that opens the path after it was removed locks a new file"*. Once the run's workers are gone, nothing will ever name a path in this directory again, because the name exists only in this run's environment. Say that in a comment at the `rm`, so the next reader does not take it as the prune the ticket rules out. Leave the 4567 existing files in `~/.lingtai/locks/` untouched. No sweep, no migration.

## What can verify it inside a pass

The only end-to-end check is `pnpm test:integration`, and a pass cannot run it (803s against a 600s kill). Two unit-level claims stand in for it:

- **A unit test of the resolver** in `packages/env/unit/`, next to `store-choice-test-side.test.ts`, which is the same shape. Hand it built environments and never touch the filesystem:
  - `{VITEST:'true', LINGTAI_TEST_LOCK_DIR:'/x'}` → `/x`
  - `{VITEST:'true', HOME:'/h'}` → throws, and the message names `LINGTAI_TEST_LOCK_DIR`
  - `{VITEST:'true', LINGTAI_HOME:'/l'}` → `/l/locks`
  - `{HOME:'/h'}` → `/h/.lingtai/locks`

  The second case is the Done-when test.
- **`HOME=/nonexistent pnpm test` stays green.** A unit test that reached a default `createFileLocker()` already fails there at `mkdirSync`. With this change it fails by name even with a real `HOME`, so a red result points at a unit test touching the filesystem, not at this diff.

Ticking the first Done-when box (no file added to `~/.lingtai/locks/` by `pnpm test:integration`) happens after the merge. The check is `ls ~/.lingtai/locks | wc -l` before and after one run. Say so in the PR; do not leave the box ticked on inference.

## The trap

**A child spawned with a hand-built environment that drops `VITEST`/`LINGTAI_TEST` and omits `LINGTAI_HOME` resolves the real `~/.lingtai/locks` and does not trip the refusal**, because to that child it is not a test. The children in `world.test.ts` are safe since they set `LINGTAI_HOME`. Before committing, grep `*/integration/**` for `spawn`/`execFile`/`fork` calls passing `env: {` and confirm each one either spreads `process.env` or names a `LINGTAI_HOME`. If one does neither, add `LINGTAI_HOME` to it. Do not widen the resolver to honour `LINGTAI_TEST_LOCK_DIR` outside `inTest`: that would let a stray exported variable redirect a real conductor's lock away from the one the daemon holds.
