# Design: the `disk: space` row in `lingtai doctor` (#1451)

## The decision the ticket leaves open: doctor already has an orphan rule, and it is the wrong one

`doctor.ts` already lists orphans. Its `worktrees: reconciliation` row (`apps/cli/src/doctor.ts:1878-1884`) calls `findOrphansEffect` / `findOrphanLogsEffect` / `findOrphanClaudeDirsEffect` with `dryRun: true`. It reaches those through `reach.orphans`, which the store-backed branch passes at `doctor.ts:4067` and the Postgres branch leaves to its default at `doctor.ts:4128`. That is the obvious thing to reuse, and it is the drift the ticket's *Watch out* warns about. `clean.ts` says why it is a different rule:

> It has its own classifier for that reason: `findOrphansEffect` reads a failed ticket as backlog, which would make a live worktree an orphan. — `apps/cli/src/clean.ts:6-8`

So the new row must not touch `reach.orphans`, `Orphan` or `orphansRow`. It counts with `clean.ts`'s `classifyWorktree` (`clean.ts:57`), by calling `clean`'s own listing.

## Shape

### 1. Split the listing out of `cleanEffect` (`apps/cli/src/clean.ts`)

Today the listing lives inside `cleanEffect` (`clean.ts:273-328`), and the only things that come out are printed lines and an `Outcome` (`clean.ts:385`). Doctor cannot use it without parsing `log` output, and parsing printed lines is a second rule by another route.

Move the first half into an exported Effect, for example `cleanListingEffect(options)`. It covers projects, `registered`, `judgeWorktree`, `judgeLog` and the `sizeKb` loop, which is everything up to `clean.ts:329`. It returns:

- the `Item`s, with `kind`, `path`, `verdict` and `sizeKb`; export `Item` or a read-only view of it;
- the directories whose `listOf` failed (`clean.ts:285-292`). Today that path sets `failed = true` and prints. Return it as data instead, and let `cleanEffect` print it as before.

`cleanEffect` becomes this listing plus the loop from `clean.ts:336` onward. Its options (`CleanOptions`, `clean.ts:167`) already take `store`, `port`, `now` and `home`, so doctor passes the same shape with `yes` left out. The re-judge before removal (`clean.ts:352-361`) stays in `cleanEffect`; it is part of removing, not listing.

`apps/cli/unit/clean.test.ts` must stay green **with no edits**. That is the unit-level proof that the rule did not move while being split.

### 2. One row in `doctor.ts`: `disk: space`

Name it `disk: space`, with a `title` sentence. Write it as two parts:

- **A pure function** `diskSpaceRow(listing: Read<…>, free: Read<number>): CheckResult`. All four `Done when` tests call this directly.
- **An Effect** that gathers both inputs.

Rules:

- **What counts.** Sum `sizeKb` of items with `kind === 'worktree'` and `verdict.verdict === 'remove'`. Logs do not count: the ticket says worktrees. `keep` items do not count, including `uncommitted changes`, because `clean` will not remove them and doctor must not send a person to a command that frees nothing.
- **Counting failed.** The orphans could not be counted if any of these is true:
  - the listing failed outright;
  - any directory was unreadable;
  - any worktree item came back `unchecked`;
  - any `remove` worktree has `sizeKb === null`. Today `clean.ts:328` turns a failed `du` into `null`, which would quietly count as 0.

  Any of these gives `warn` with *the orphans could not be counted: <reason>*, never `ok`. If the part that was counted already reaches the threshold, say that as well.
- **Units.** Use binary units, matching `clean`'s `sizeWord` (`clean.ts:331-332`):
  - `ORPHANS_WARN_KB = 1024 * 1024`
  - `FREE_WARN_BYTES = 5 * 1024 ** 3`

  Both are module constants and not configuration (ticket, *Out of scope*). The test cases (1.2 GB / 200 MB, 3 GB / 50 GB) sit well clear of the GB-vs-GiB gap.
- **One line.** A `warn` carries every clause that applies, joined in one `detail`. The `fix` is `lingtai clean` when the orphan clause applies. `fix` is documented as *"The command that fixes it … a person can run as written"* (`doctor.ts:233-236`). With only the free-space clause, still name `lingtai clean`: the ticket's *Want* says the remedy names it.
- **Never `fail`.** `CheckStatus` documents `warn` as *"nothing is wrong and you should know anyway"* (`doctor.ts:190-195`). Leave `restartAnswers` unset; it is only for failures.

### 3. Free space

Use `node:fs/promises` `statfs(home)` wrapped in `Effect.tryPromise`; free space is `bavail * bsize`. Do not write a new `async` function, because the ratchet counts them (CLAUDE.md, *New IO is an Effect*).

`home` is the same expression `clean` uses, `process.env['LINGTAI_HOME'] ?? `${process.env['HOME'] ?? '.'}/.lingtai`` (`apps/cli/src/cli.ts:1363`). Doctor and clean must agree on which home they look at. If a shared helper already exists in `@lingtai/env` (imported at `doctor.ts:117`), use it in both places; otherwise copy the expression.

A `statfs` failure, including a home that does not exist, gives `warn` with the reason, as the ticket says.

### 4. Injection, so the unit half spawns nothing

Add one optional key to `DoctorReach` (`doctor.ts:1250`), for example `diskSpace?: () => Effect.Effect<{ listing; free }>`. Default it to the real `cleanListingEffect({ home })` plus `statfs`.

The three unit files that drive `runDoctor` through the store-backed branch already fake `orphans` and must fake this key too. Otherwise they would run `du`, `git` and `statfs` against the real `$HOME`, which `HOME=/nonexistent pnpm test` exists to catch:

- `apps/cli/unit/doctor.test.ts:87`
- `apps/cli/unit/doctor-progress.test.ts:41`
- `apps/cli/unit/log-predates-hold.test.ts:54`

### 5. Where it runs

Add `yield* step('disk space', …)` in both store branches, right after their `'orphans'` steps (`doctor.ts:4067` and `doctor.ts:4128`).

The listing reads the log (`readRun`, plus `loadClaims` paging all of `readAll`, `clean.ts:199-216`), so it needs a store. Leave it out of the no-store `else` branch (`doctor.ts:4136`). Doctor there is already reporting that it has no log, and a row that could only answer *could not be counted* adds nothing.

Pass the store doctor already opened as `store`, as the `clean.test.ts:74` call does. `cleanEffect`'s `own` flag (`clean.ts:277`) then turns off snapshot reads of the process log, which is also right for a read-only check.

## Costs to watch

- **Time.** `du -sk` runs once per `remove` or listed-keep item (`clean.ts:326-329`), and `loadClaims` scans the whole log once. On the 2026-11-25 machine that is five `du` calls over 6.9 GB. It is acceptable, but this row is the slowest new step; `onProgress` covers it through `step`.
- **Pinned counts.** These count rows and need updating for the new row:
  - `apps/cli/unit/doctor-render.test.ts`
  - `apps/cli/unit/doctor-titles.test.ts`
  - `apps/cli/unit/doctor-titles-store-log.test.ts`
  - `apps/cli/unit/restart-order.test.ts`

  Update a pinned count only where this row is the reason it moved.
- **Restart.** `lingtai restart` gates on failed checks (`restart.ts:54`: *"a failed doctor with `--despite-doctor`"*). A `warn` is not counted as failed. Add one assertion in `restart-order.test.ts` that a report whose only non-`ok` row is `disk: space`/`warn` is not refused. That is the unit-level stand-in for *restart is not refused by this check*; nothing here needs `pnpm test:integration`.
- **Integration.** `apps/cli/integration/doctor.test.ts` pins Postgres-only rows by name (`doctor.ts:449`). This row is not one of them and is not in `postgresOnlyRows()`, so nothing changes there.

## What the log would settle

Nothing in this row is decided by the log. The orphan verdict comes from `classifyWorktree`, whose log inputs come from the run's stream and the ticket fold (`readRun`, `clean.ts:224-243`). If doctor and `clean` ever disagree about a worktree, the first thing to read is the `runId` on that ticket stream's events and the fold's `lifecycle.status`. After this split they share one call, so they cannot disagree.
