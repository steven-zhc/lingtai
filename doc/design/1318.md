# Design: #1318, the PR summary agent

## Where it goes

| Piece | File |

## 1. The summary facts belong to the PR, not to one pass through In progress

`walkPr` picks *"the first step not recorded since the latest `PrInProgress`"* (`pr.ts:690`, `:710`). `PrState.steps` is *"the steps recorded since the latest `PrInProgress`: a later pass through In progress starts empty"* (`domain/src/pr.ts`, the `steps` field). A pr-fix landing goes through `recordPrFixRestart` (`pr.ts:705-708`), so `summary` is reached again on every pr-fix pass. "A rework never rewrites it" therefore cannot be a step record. It has to be state that `PrInProgress` does not reset, in the same way as `lastPushed`, `host` and `rounds`. Add to `PrState`, none of it reset by `PrInProgress`:

- **`summary`**: `{ title: string | null, text: string | null, by: 'agent' | <person>, seq }` or null. It is set by `PrSummaryWritten` and, for `text` only, by `PrSummaryEdited`. An edit leaves `title` as the agent wrote it, because only the summary is the person's (0131 §5).
- **`summaryTriedSeq`**: the seq of the latest `PrSummaryWritten` or `PrSummaryNotWritten`.
  - The `summary` step runs only when this is null.
  - `topup` is owed when some `PrFixLanded` has a seq greater than this.
  - This needs `PrFixLanded`'s seq kept per ticket. Today the fold only adds the ticket to `tickets` (`domain/src/pr.ts`, the `PrFixLanded` case), so keep a `fixesLanded: { ticket, mergeCommit, seq }[]` beside it.
  - A `PrSummaryEdited` does **not** move this mark. A person's edit does not mean the pr-fix was summarised.
- **`descriptionOwed`**: true when the latest `PrSummaryWritten`, `PrSummaryNotWritten` or `PrSummaryEdited` comes after the latest `PrDescriptionPushed`. Add it to the condition in `servePendingPrs` (`pr.ts:916-922`) beside `pr.fixOwed`, together with `host !== null`. Without the host clause, a PR whose remote is not GitHub would be served on every sweep forever.

## 2. The paid run is recorded inside the step, not as its `record`

`walkPr` throws away a step's answer when the target moved while the step ran: `now.target !== state.target` then `continue` (`pr.ts:727-728`). A summary run can take 5 minutes, and a pr-fix can land during it. If `PrSummaryWritten` were the step's `record`, that fence would drop it, and the next walk would pay for the run a second time.

So the step appends its prompt (`recordPrompt`, as `pr-resolve.ts`'s `paid` does at `:339-356`), then `RunSpent`, then `PrSummaryWritten` or `PrSummaryNotWritten`, all inside `run`. It then answers `done` with no `record`, so the walk appends a plain `PrStepDone`.

- If the fence fires, the next walk reaches `summary` again. It sees `summaryTriedSeq` set and answers `done` with no run.
- On the following pass, `topup` sees the new `PrFixLanded` and extends the summary.
- Both steps answer `done` with the `headSha` of `state.target ?? state.frozenSha`, as `open` does (`pr.ts:359`).

## 3. The person's words win, in the transition rather than in the step

Every append in `@lingtai/project` happens *"at the head it was read at"* (`project/src/pr.ts:94-113`): `store.append(stream, state.version, …)` inside `withOneRetry`. The rule therefore goes in a pure `summaryWrittenTransition(state, written)`:

- If `state.summary?.by` is a person and `state.summary.seq > written.basedOn`, it returns **`PrSummaryNotWritten { why: 'set aside: <who> edited the summary while the agent was writing' }`** instead of the `PrSummaryWritten`.
- A `PrSummaryEdited` appended between the step's read and its append moves the version. The append then conflicts, is retried once, and the retry sees the edit. Check and append cannot race.
- `NotWritten` is still an attempt, so it moves `summaryTriedSeq`. The pr-fix the run was about counts as covered, and the PR is not topped up again for it.
- `basedOn` is `state.version` as read before the prompt was built.
- Unit test: an in-memory store where `PrSummaryEdited` is appended inside the fake runtime's `run`.

## 4. The description is pushed once, by one function, from `servePr`

`pushDescription(ports, project, n)` runs in `servePr` after `walkPr` and `mergePrBack` (`pr.ts:896-898`). Its condition is `descriptionOwed && isOpen(state) && state.host !== null`. Because it runs at that point, one function serves all four cases:

- the top-up,
- a locked or failed top-up (`NotWritten` also makes it owed),
- the person's edit, at any status: `walkPr` returns early when the PR is not `in-progress` (`pr.ts:709`), and the push still runs after it,
- a daemon that died between `PrSummaryWritten` and the PATCH.

What it does:

1. Render with `describePr`. Stop passing `title: null, summary: null` (`pr.ts:342-343`) and pass `state.summary`'s fields instead.
2. Hash `title + '\n' + body`. This is the `bodyHash` field.
3. If the hash differs from the last pushed one, call `github.updatePull(number, { title, body })`. This is a new method beside `openDraftPull` (`github/src/client.ts:387`, `:1191`).
4. Append `PrDescriptionPushed { bodyHash }` **even when the hash is equal**. Otherwise `descriptionOwed` never clears and the sweep serves the PR forever.
5. A failure the person did not cause (`notThePersons`, `pr.ts:325`) appends nothing, and the PR is served again at the next sweep.

On the first submit, `open` records `PrDescriptionPushed` for the body it opened with. Fold that into `recordPrDraftOpened`'s transition so it is one append. That keeps the *no PATCH on a first submit* checkbox true: the `PrSummaryWritten` comes before the open, so nothing is owed afterwards.

`IN_PROGRESS_STEPS` (`pr.ts:620`) becomes `[sync, build, summary, push, open, ci, topup, ready]`. The comment at `pr.ts:615-617` still says *"`summary` (#1318) comes between `ci` and `ready`, in 0130 §5's order"*, which is stale. Rewrite it to cite 0131 §2. 0131 already records the new order, so no superseding ADR is needed.

`topup` answers `done` without dispatching when no pr-fix is owed. Being cheap is what lets it sit on every pass.

## 5. A summary port of its own, not `resolver`

`resolver` is absent exactly when no conflict agent can run: *"Absent means no agent can"* (`pr.ts:131-135`). It is built only when `locked` is supplied (`pr-ports.ts:116-118`), and its `dispatch` is a full-tools runtime in a worktree with a sandbox (`pr-ports.ts:127-160`).

Add a separate port, `summarizer?: { write(project, PrDispatch-without-cwd): Effect<PrDispatched, Error>; runtimeVersion; locked(project) }`:

- Build it in `pr-ports.ts` with `createRuntime(agent, { tools: 'none' })`, as `apps/cli/src/discuss.ts:442` does, with the cwd chosen the way `discuss.ts` chooses it.
- `locked` is the same `lockedEffect` sentence that `ConflictResolver.locked` already carries (`pr.ts:174-175`).
- **When the port is absent, the step answers `done` and appends nothing.** Every existing `pr.ts` unit test then keeps its event counts.
- The run's limits are `{ turns, wallMs }` from `callForPr`. There is no `usd`, because `Pr` is a `strictObject` and refuses one (`recipe.ts:2996-3015`).

## 6. `SpentFor`: one member, split by `purpose`

`Pr` today *requires* `merging`, `commit` and `round` (`events.ts:710-716`), so `purpose: 'summary'` cannot just be added to the enum. Make the `Pr` option a `z.discriminatedUnion('purpose', [...])` with two shapes:

- `{ _tag: 'Pr', purpose: 'resolve' | 'review', merging, commit, round }`
- `{ _tag: 'Pr', purpose: 'summary', at: 'submit' | 'pr-fix' }`

Zod 4 (`domain/package.json`: `^4.5.4`) accepts a discriminated union as an option of another. Pin it with a unit test that parses an old `resolve` payload and a new `summary` payload.

The tag stays `Pr`, so `projector/src/spend.ts:260-264` files the row under its project unchanged, and `apps/board/src/lib/spend.ts:135` still maps it to `PR`. **One reader does need a label edit, not a new case:** `apps/board/src/lib/history.ts:279-280` renders `` `the conflict agent (${purpose})` ``, and `:955-956` renders `'the conflict agent'`. A summary row would read *"the conflict agent (summary)"*. Branch on `purpose === 'summary'` to say *the summary agent*. Before finishing, grep for other readers of `for.merging`, `for.commit` and `for.round` on `Pr` and narrow them.

`runId`: `pr-${project}-${n}:summary:${at}:${summaryTriedSeq ?? 0}`, in the shape of `pr-resolve.ts:334-335`.

## 7. The edit request

`PrSummaryEdited { by, summary }`, appended through a transition that refuses unless `isOpen(state)`. Add it to `PR_EVENTS` (`work-loop.ts:119-128`), and it is served by `servePr` → `pushDescription`. `lingtai pr summary --file` waits for the `PrDescriptionPushed` whose seq is after its own edit, the way `submit` waits.

## Decided edges the ticket leaves implicit

- **Answer parsing.** The first non-empty line, stripped of a leading `#`, is the title, cut to 256 characters. The rest is trimmed and becomes the summary. A one-line answer gives `summary: null`, never `''`. An empty answer, or a `failure` on `PrDispatched` (`pr.ts:158`), gives `PrSummaryNotWritten`.
- **When the `RunSpent` append fails.** Log it with `ports.log` and still record the text, as the discussion does.
- **A topup when the person edited.** The prompt carries `state.summary.text`, which by then is the person's.
- **Test cost.** Each event type needs `@summary`, `['outside']` and `['pr-']`, plus the generated `doc/events.json`, `doc/reference.md` and `doc/cli.*`. All of it is checked by the unit half. Nothing in this shape depends on `pnpm test:integration`: the PATCH is a fake `GitHub` and the run is a fake `summarizer`.
