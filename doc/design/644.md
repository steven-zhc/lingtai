# Design: #644, a reconnected stream makes the page read *writing* again

## Where the change goes

There are three edits and one test. The ticket names the first three. This note covers the decisions it leaves open.

**1. `apps/board/src/app/live.tsx`, inside the `EventSource` effect (`live.tsx:171–210`).** Today `open` only sets the socket state: `source.addEventListener('open', () => setSocket('open'))` (`live.tsx:174`).

- **Keep the "have we opened before" flag in a `let` inside the effect.** Do not use a `useRef` or anything module-level. Each run of the effect makes a new `EventSource` for a page the server has just rendered, so that source's first `open` is the page load. The cases that matter:
  - Navigating to another task remounts `Follow`, so the flag starts fresh.
  - React StrictMode runs the effect twice in dev. Each run has its own source and its own closure, so neither counts the other's open.
  - A ref would survive both of these and refresh on the first open of a new mount. That is the double render the ticket's Watch out row forbids.
- **On a reconnect, call the existing `schedule()` (`live.tsx:142–149`). Do not call `router.refresh()` directly** (the ticket says `router.refresh()`, but `schedule()` is the intended way to get there). `schedule()` sets `stale`, coalesces, refuses to start a second render while one is in flight, and waits for a hidden tab to become visible. A reconnect is just one more reason the page may be stale, so it goes through the same gate as an append. Two consequences:
  - A reconnect that arrives together with replayed `append` frames costs one render, not two.
  - A background tab that reconnects re-reads when it is looked at, through the `visibilitychange` hook (`live.tsx:162–169`).
- **Why this is enough.** The file's header already says *"`EventSource` reconnects on its own and sends `Last-Event-ID`"* (`live.tsx:31–32`). The browser fires `open` again on that automatic reconnect. That is the exact moment the page may have missed something, and the old design needed a frame from the server to learn it.
- **The `'open'` listener must call `schedule()` itself.** Don't route the reconnect through the `health` frame the server sends on connect (`route.ts:100`, `void sendHealth()`). That frame is a notification too, and it is the pattern this ticket removes.

**2. `apps/board/src/lib/split-instance.ts`:**
- Delete `COUNT`, `splitsEnded()` and its doc comment (`split-instance.ts:37–47`).
- Delete the counter increment inside `runSplit`'s `finally` (`split-instance.ts:76`).
- **Keep `onSplitEnded` and its listener set** (`split-instance.ts:30–35`, `49–57`). The ticket deletes the *connect-time* frame. The live one is a different case: a writer ending while a stream is connected, with no append behind it (*"e.g. when its last SplitFailed append threw"*, `route.ts:126–128`). That case still has no other path to the page, and a reconnect does not cover it because nothing disconnected.

**3. `apps/board/src/app/api/stream/route.ts`:**
- Delete the `splitsEnded() > 0` block and its comment (`route.ts:131–133`).
- Drop `splitsEnded` from the import (`route.ts:33`).
- `splitEnded`, `unlistenSplit` and `onSplitEnded(splitEnded)` (`route.ts:129–130`) stay, for the reason above.

**4. `apps/board/unit/split-instance.test.ts`:**
- Delete the `describe('splitsEnded', …)` block (`split-instance.test.ts:53–59`).
- Remove `splitsEnded` from the import on line 8.
- Leave the `onSplitEnded` test as it is.

## The test: pull the decision out as a pure function

**There is no DOM and no `EventSource` in the unit half.** `unit/discussion-live.test.tsx:15–21` says so: *"There is no DOM here and no `EventSource`, so a test of `Thinking` could only ever assert its first frame"*. `unit/task-follow.test.tsx:13–15` adds that `Follow` *"needs Next's app router to render at all"*. So the Done-when test cannot mount `useFollow`.

Follow the pattern `run-log.tsx` uses for `againAfter` / `reported` / `asksAgain` (`run-log.tsx:92`, `115`, `132`): export a small pure function from `live.tsx` and test that.

- **The function:** a factory, something like `export function onOpen(reread: () => void): () => void`. It returns the listener: the first call does nothing, and every later call runs `reread` once.
- **Wiring it in:** the effect does `const opened = onOpen(schedule)`, then `source.addEventListener('open', () => { setSocket('open'); opened() })`. The `let` from section 1 lives inside the factory's closure, and the effect calls the factory once per run.
- **The test:** a new `apps/board/unit/live-reconnect.test.ts` (or a `describe` in `task-follow.test.tsx`, which already imports from `live.tsx`). Call the returned function with a `vi.fn()`:
  - the first call does not run it;
  - the second call runs it once;
  - the third call runs it once more;
  - two factories made separately do not share state. This is the remount and StrictMode case, and the one a ref-based version would fail.

The unit test cannot reach two things:
- **That the browser fires `open` on an automatic reconnect.** That is the platform's behaviour.
- **That a fresh board process renders *interrupted* with Retry.** That is already pinned by `split-instance.test.ts:61`, *"reads interrupted, not writing, once a writer whose SplitFailed append threw has ended"*: an empty running set plus the log gives *interrupted*. An empty set is exactly what a restarted process has, since `running()` lives on `globalThis` (`split-instance.ts:18–23`). Point to that test in the commit body rather than writing another.

## What not to add

- No replacement for the counter.
- No "last seen instance" field in the stream's frames.
- No check that compares `splitInstance()` across a reconnect.

Every one of these is a fact that would have to survive the restart, and the ticket's Watch out row says the point is that nothing has to. The re-render is enough: `loadTask` reads `isSplitRunning` against the current process when it renders.

## Evidence, if anyone asks what happened

In the log, the three-fault case reads:
- a `SplitStarted` whose `instance` is the old board process;
- no `SplitFailed` or `SplitCompleted` after it on that ticket stream;
- a later `SplitStarted.instance` (or none at all) from a different process.

*Writing* versus *interrupted* is decided by `SplitStarted.instance` against `splitInstance()` plus the running set (`split-instance.ts:4–10`). The event never records whether a page was connected, which is why no event can settle this and the fix is a re-read instead.
