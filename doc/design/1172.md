# Design: #1172 — `@lingtai/project` holds the recipe file and the host read

The ticket says what moves. This note covers the one seam the ticket leaves open — the **private** helpers the moved functions call — and fixes the file layout so the ratchet's face paths and the moved tests have one obvious place to go.

## 1. The moved functions call private helpers, and those helpers stay

Neither moved Effect stands on its own. Each calls private helpers in its file:

- **`resolveLocalRecipeEffect`** (`packages/recipe/src/local.ts:306`) calls:
  - `namedIn` (`:340`, defined `:508`)
  - `asRecord` (`:357`, `:383`, defined `:52`)
  - `SCHEMA_PROBE_AGENT` (`:357`, defined `:63`)
  - `originIn` (`:396`, defined `:271`), which calls `carries` (`:242`)
  - and the exported `checkMachineConfig`, `resolveAgent`, `isRefusal`, `PROVENANCE_ARROW` and `checkSandboxBlock`.
- **`setRecipeEffect`** (`packages/recipe/src/write.ts:163`) calls the private `widenStepsIfNeeded` (`:171`), `editedText` (`:172`) and `refFor` (`:180`).

**Decision: apply the ticket's rule to these too.** The rule is *what is a function of text stays*. So every helper above stays in `@lingtai/recipe` under its current name, gains `export`, and leaves the recipe package through the barrel (`packages/recipe/src/index.ts` is `export *` per file). The ticket already calls `editedText`, `widenStepsIfNeeded` and `refFor` functions of text. `asRecord`, `namedIn`, `originIn`, `carries` and `SCHEMA_PROBE_AGENT` read no file either.

- `asRecord` stays for a second reason: `checkMachineConfig` (`:148`, `:155`, `:158`) and `writtenAgent` (`:501`) also use it, and both stay.
- Do not copy any helper into `packages/project`. Two `asRecord`s is how the two packages drift apart.

This is not the shim the ticket forbids. No moved name is re-exported, and every name newly exported from `@lingtai/recipe` is one that reads nothing. The `node:fs` test in §4 is what holds that.

## 2. Where the files go

Keep each moved function in a file with the **same basename** as the one it came from:

| `packages/project/src/` | holds | from |
|---|---|---|
| `local.ts` | `recipePath`, `machinePath`, `LocalRecipeOptions`, `resolveLocalRecipeEffect` | `recipe/src/local.ts:42-49`, `:284-484` |
| `files.ts` | `readRecipeFile`, `replaceRecipeFile`, `readFileFace`, `replaceFileFace`, `diskFiles`, `filesEffect` | `recipe/src/files.ts:52-108` |

Same basenames mean the three faces in `effect-ratchet.faces.json:500-523` change one path segment each (`packages/recipe/` becomes `packages/project/`) and nothing else.

- Their `why` strings still name `apps/board/src/lib/recipe.ts` and `apps/board/src/app/actions.ts`. Re-read those two files after rewriting imports, and keep the `why`s true.
- `resolveRecipe` (`faces.json:513`) stays in `recipe/src/resolve.ts`, and its entry stays as it is.

What stays in `@lingtai/recipe`:

- **`files.ts`** keeps `RecipeFailed`, `messageOf`, `failed`, `isMissing` and `plainWhen`, and loses its `node:fs/promises` and `node:path` imports (`:8-9`). Its `import type { RecipeFiles } from './write.ts'` (`:13`) goes once `diskFiles` leaves. Keep the file name, so `resolve.ts:24` and `local.ts:34` keep their import lines.
- **`write.ts`** keeps `RecipeFiles`, `SetRecipeResult`, `SaveRecipeTextResult` and the three text helpers.
- **`sandbox.ts`** keeps `SandboxHostOptions`, `HostFactsEffect`, `checkSandboxBlock` and `sandboxDecision`. It still imports `@lingtai/sandbox`'s `.` entry, which the ticket allows.
- **`local.ts`** loses `recipePath`/`machinePath`. Check whether `stateDir` (`:30`) is still used once they leave. `checkMachineConfig` takes `home` as a parameter (`:139`), so the import probably goes from this file. `recipe.ts:2` keeps `@lingtai/env`.

## 3. No cycle, and what `packages/project` declares

None of `@lingtai/env`, `@lingtai/sandbox`, `@lingtai/domain` or `@lingtai/event-store` lists `@lingtai/recipe` in its `package.json` (checked). So `project → recipe → {domain, env, sandbox}` is acyclic.

The moved code imports `effect`, `yaml` (`parseDocument`, `isNode` in `readRecipeKeyEffect`; `parse` in `resolveLocalRecipeEffect`) and `node:path`. Declare:

- **dependencies:** `effect`, `yaml`, and the `@lingtai/*` the ticket names.
- **devDependencies:** `@types/node`, `typescript`, `vitest`, as in `packages/recipe/package.json`.

No file moved here imports `@lingtai/event-store`. Declaring it, as the ticket asks, is harmless, but the `git grep -ho` check in Done-when will not find it. Do not add an import just to satisfy that check.

`tsconfig.json` should be the same one-liner as `packages/recipe/tsconfig.json`:

```json
{ "extends": "../../tsconfig.base.json", "include": ["src", "unit"] }
```

The root vitest `unit` project already globs `{apps,packages}/*/unit/**/*.test.ts?(x)` (`vitest.config.ts:72`). So the moved tests run with no config change.

## 4. Tests

**The seven files the ticket lists** are `packages/recipe/unit/{local,write,save-recipe-text,effects,sandbox,allow-host,the-design-block}.test.ts`; all import `'../src/index.ts'`.

- Cases that exercise a moved name go to `packages/project/unit/<same name>`.
- There, they import moved names from `'../src/index.ts'` and the rest from `@lingtai/recipe`.
- The fake host is imported as `@lingtai/recipe/test/sandbox-host` instead of `'../test/sandbox-host.ts'`. The export already exists in `packages/recipe/package.json`.

**Splitting a file.** Where only some cases move, leave the others where they are. A case that calls `resolveLocalRecipeEffect` only to reach a text helper still moves, because it goes through the read. Do not rewrite it against the helper: the ticket says this is a move, and a rewritten assertion is a new test.

**The no-IO test** goes in `packages/recipe/unit/reads-no-file.test.ts`:

- Parse each `packages/recipe/src/*.ts` with the TypeScript parser, the way `packages/domain/test/ts-modules.ts` does.
- Collect every import and export-from specifier.
- Fail on `node:fs`, `node:fs/promises`, `fs` and `@lingtai/sandbox/host`, naming the file.
- Do **not** forbid `node:` in general: `resolve.ts:19` imports `node:crypto`, and `local.ts:27`, `sandbox.ts:11` import `node:path`, and all three are legitimate.
- Reading the source files is the filesystem. Under 0060 §1 that would make this an integration test, so do the same as the ratchet test does with its source reads (`packages/domain/unit/effect-ratchet.test.ts`, which lives in `unit/`) and say so in the file's head comment.

**`client-graph.test.ts`:** add one line to `FORBIDDEN` (`apps/board/unit/client-graph.test.ts:21-29`), in the same shape as the `@lingtai/sandbox` line, with a comment that its `files.ts` imports `node:fs/promises`.

## 5. The ratchet should need nothing but the new key

`packages/recipe` is at `{ "async": 0, "run": 0 }` today (`effect-ratchet.baseline.json:12`). The only promise-returning functions that move (`readFileFace`, `replaceFileFace`, `saveRecipeText`) are listed faces, and the faces are exempt from the counts. So `packages/project` holds at 0/0, and `packages/recipe` stays at 0/0.

Add `'packages/project'` to `PACKAGES` (`effect-ratchet.test.ts:38-51`) and the same key to the baseline. **If either package reads non-zero, the move changed a function** — a face lost its listed shape, or an `Effect.fn` became an `async`. Fix the code; never the number.

## 6. What only shows after the merge

The Next build is the only check that sees a missing `transpilePackages` entry (`apps/board/next.config.ts:13-25`), and it runs in `apps/release/integration/build.test.ts`, out of reach in a pass. Two unit-level claims stand in for it:

- `client-graph.test.ts` refuses a `'use client'` import of `@lingtai/project`.
- The `next.config.ts` diff names the package. Check it by reading the diff.

Nothing in the unit half checks `transpilePackages`. Do not write a test that parses `next.config.ts` for it; it would be a second list to keep in step with the first.

`pnpm install` writes `pnpm-lock.yaml` and the `node_modules` links. Run it once, after every `package.json` is final, and commit the lockfile in the same commit as the move.
