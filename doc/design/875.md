# #875 — the shape

## Where the writer is acquired

Wrap the two handlers in `apps/cli/src/cli.ts`, `startCommand` (`:1039-1055`) and `restart`'s (`:1111-1115`). Don't change `daemonHandler` itself. `daemonHandler` also serves `shutdown`, `pause`, `resume` and `service` (`:1012`, *"`start`, `daemon`, `service`, `restart`, `shutdown`, `pause` and `resume`"*). All of those exit when their command does, and 0124 §5 gives them no writer.

So the handler becomes, in shape:

    Effect.scoped(
      Effect.gen(function* () {
        const { log } = yield* Effect.promise(() => import('@lingtai/event-store'))
        const { makeSnapshotWriter } = yield* Effect.promise(() => import('@lingtai/event-store/snapshot-writer'))
        const writer = yield* makeSnapshotWriter(log.snapshots, (line) => console.error(line))
        yield* daemonHandler(args, async () => { … daemonCommand(…, writer) … })
      }),
    )

Two things here are deliberate:

- **The imports stay dynamic.** `cli.ts` imports nothing from `@lingtai/event-store` at the top. Every heavy module comes in through `await import(...)` inside a handler (`:1041`, `:1113`, `:585`). The writer must not be the first top-level import of the store package. `() => import(...)` is not an `async` function, so the ratchet does not count it (`effect-ratchet.test.ts` counts `async` functions and `run[A-Z]` calls, `:45-48`, `:85-110`). The `async () =>` passed to `daemonHandler` is already there today.
- **Pass `log.snapshots` directly.** It is a deferred store: `deferredLog` builds `snapshots: deferredSnapshots(async () => (await resolve()).snapshots)` (`packages/event-store/src/choose.ts:215-221`). Naming it opens nothing. On the supervised-restart path the writer is never offered anything, so the log is never resolved on its account. No wrapper or branch is needed.

`makeSnapshotWriter`'s header says *"**Close the writer's scope before the store.**"* (`snapshot-writer.ts:10`). That holds here: the scope closes when `daemonHandler`'s promise settles, and that is before `main` returns and the process exits.

## The parameter

Add an optional parameter at the end of `daemonCommand` (`daemon.ts:202-213`): `writer: Pick<SnapshotWriter, 'offer'> | null = null`. A positional fifth argument matches the four already there. An options object would mean rewriting every caller.

`restartCommand(args, steps)` (`:828`) also gains an optional `writer`. It forwards that to its one `daemonCommand` call at `:896`, which today passes `true` for `verbose`. Callers that pass nothing, which is every existing test, get today's behaviour.

`ConductOptions` (`apps/cli/src/conduct.ts:63`) gains `controlWriter?: Pick<SnapshotWriter, 'offer'>`. `conductorTurn` (`:554`) uses it at `:576`: `readControl(undefined, 0, controlWriter ? { writer: controlWriter } : {})`. Two things to know before touching it:

- The read once per pass is in **`apps/cli/src/conduct.ts`**, not in `packages/conductor`.
- The daemon's call site is `daemon.ts:600`, which already passes `paused: claiming`. Add `controlWriter: writer` beside it.

## One reader, built once — and that is the test seam

Don't pass `{ writer }` at four call sites in `daemonCommand`. Build the reader once near the top of the conducting branch:

    export function daemonControlRead(
      writer: Pick<SnapshotWriter, 'offer'> | null,
      read: typeof readControl = readControl,
    ): (since?: number) => Promise<ControlState> {
      return (since = 0) => read(undefined, since, writer ? { writer } : {})
    }

Then `:542`, `:569`, `:647` and `:681` call it. `:542` becomes `control: () => controlRead(since)`. `:681` becomes `controlRead()`, which still reads with `since` 0, the same as today's `readControl()`.

The function always passes `undefined` as the store. That is how the ticket's rule (*only the default log's writer*) becomes structural rather than a convention: nothing built from it can hand this writer to a store passed in.

The `openDaemon` reads (`:79`, `:81`, `:242`) keep calling `readControl()` directly and get no writer.

The `read` parameter exists only so the unit test can run without the network. `readControl` with no store reads the process's `eventStore` and `log.snapshots` (`control.ts:140-142`), and a unit test must touch neither. `packages/daemon/unit/control-snapshot.test.ts:13-23` mocks `log.snapshots` to throw, for the same reason. The test:

1. Builds a memory store and `createMemorySnapshotStore` (`control-snapshot.test.ts:27-41` shows the setup) and appends enough control events to cross a commit point. Take the count from `crossesCommitBoundary` in `@lingtai/domain`, not a literal 5.
2. Passes `read = (_s, since, cache) => readControl(store, since, { ...cache, snapshots })`.
3. Gives a stub `{ offer: vi.fn() }`, calls the returned function once, and asserts exactly one `offer`. The offer's `streamVersion`, `lastSeq` and `lastAt` must equal the last envelope's (`snapshot-read.ts:83-90`).
4. Also asserts that `daemonControlRead(null, read)` offers nothing. That case is every existing caller.

This is the helper-level test the ticket's *Done when* allows. Driving `daemonCommand` itself takes the lock under `~/.lingtai/locks/`, the beacon and `loadProjects()`, which is integration under 0060 §1.

The four call sites are not covered by a test. What stands in is that the reader is built once and every read in the conducting branch is a call to it. A reviewer can check that with `grep -n readControl apps/cli/src/daemon.ts`: after the change it should name only the import, `:79`, `:81`, `:242` and the comments.

## What settles it in production

You cannot read production `events`. What would settle it is `snapshots` rows for the `ctl-conductor` stream key — `controlReducer.name` and `controlReducer.version` — whose `streamVersion` keeps advancing while no board is running. No new event is appended for it. A `put` that fails reaches `lingtai service`'s log as one `console.error` line per key (#870).
