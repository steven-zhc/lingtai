# Design: #915 — the running panel

Both tickets this one waits on have landed in this worktree (`9dfcbff2`), and two of them didn't land the way #915 describes. The interfaces below are the ones that exist now. Where they differ from the ticket, follow this note.

## What landed differently from the ticket

- **`planStepLine` takes positional arguments and returns nothing for a skipped step.**
  - It is `planStepLine(_step, actions, skipped)` at `apps/board/src/app/rail.tsx:430`, which returns `''` when `skipped`.
  - `<PlanStep>` at `rail.tsx:435-443` returns `null` for a skipped step. Its comment says *"a skipped step is not drawn (the list names it in its nothing configured line)"*.
  - So *"`planStepLine`'s `skipped` row, never silence"* from the ticket's Edges can't be had by calling it.
  - **Decision:** when the step in flight has an empty `planned`, draw the queued list's own words: `<li className="none">nothing configured at: {step}</li>` (`apps/board/src/app/standing.tsx:201-209`). Otherwise draw `<PlanStep step actions={planned} skipped={false} />` inside an `<ol className="planlist">`, as `standing.tsx:198-200` does.
  - Do not change `planStepLine` or `PlanStep`. The queued list owns them.
- **The panel CSS is already scoped to `detail--running`, and the class is already applied.**
  - The band's rules list `.detail--running` (`apps/board/src/app/globals.css:1392-1434`), and so do the `.sreading--advised` rules (`:1476-1503`).
  - `main` already gets ` detail--running` (`standing.tsx:75`).
  - Use `<div className="sreading sreading--advised">` exactly as `QueuedPanel` does (`standing.tsx:249`, Discussion in `.spair` at `:285-287`). Add no CSS.
  - For the chip, use `triage-cause cause-chip`, as the queued band's head does (`standing.tsx:114-124`).

## Where the data goes: through `StandingView`, not a new prop

`Standing` never receives an `AttemptView`. It gets `standing: StandingView` and a separate `progress` prop (`standing.tsx:719`, `:819`).

`standingOf(own, runs)` does hold the attempt in flight: it is the `run` it finds at `apps/board/src/lib/task.ts:813-815`, and it already copies `runId` from it (`:888`).

So:

1. `presentAttempt` (`task.ts:1135`) adds `stepNow` and `refusal` to `AttemptView`, as the ticket says. `since` is `state.step.since.toISOString()`.
2. `StandingView` gains `running: RunningPanel | null`. `standingOf` sets it to `runningPanelOf(run)` when the state is `running` and `run` exists, and to `null` otherwise.
3. `runningPanelOf` reads progress from `run.progress`. `AttemptView` already carries it (`task.ts:342`, set at `:1188`), so its signature is `runningPanelOf(run: AttemptView)`, not the two arguments the ticket gives.

This keeps `Standing` reading one view and makes the panel a pure function of events. It also means the existing `renderToStaticMarkup` fixtures, which build `StandingView` through `standingOf`, get the panel for free.

`RunningPanel` (the component) renders `standing.running`. It renders nothing when that is `null`, which would be a running ticket with no attempt found. A head of *Running* alone is acceptable there too; pick one and test it.

## The refusal is `standingRefusal`, not the raw `state.refusal`

`AttemptState.refusal` is *"The last refused verdict … Not cleared by a later pass or a new head"* (`packages/domain/src/attempt.ts:193`). #935 added `standingRefusal(state)` (`attempt.ts:632-641`) for exactly the panel's question: *"The refusal a fixer was still answering, or `undefined`: … it counts only while its own gate's latest verdict is still `failed`"*.

The raw field gets one case wrong. Suppose round 1's review refused, the re-review then passed, and a round 2 was granted over a hold with no verdict. Round 2's panel would then claim to be fixing round 1's finding.

**Decision:** `presentAttempt` sets `refusal` from `standingRefusal(state) ?? null`. That turns the ticket's *"refusal null in a fix round → Fixing what was sent back"* into the real path for that case.

Copy only `key`, `evidence` and `findings`, as the ticket lists them. `endedVersion` and `action` (`attempt.ts:196-198`) are the route's business, not the page's. The refusal's step is `key.slice(0, key.indexOf(':'))`, as `presentAttempt` already does for `s.step` (`task.ts:1147`).

There is no reducer change, so `attemptReducer.version` is not bumped.

## A fix round is `implement` with `round > 0`, as the ticket says

`state.step.round` is the round the step was entered on (`attempt.ts:160-166`). Use that, not `state.implementRound` (`attempt.ts:180-183`), which is a high-water mark.

A `build` or `review` re-run inside round 1 is therefore *"at any other step"* and draws that step's row, and its head has no `fix round N`. This is what the ticket asks for; it is spelled out here because a reviewer might expect *fix round 1* on the re-review.

## *Then*

*Then* is built in this order:

1. Find `stepNow.step` in `run.progress.steps` and take the entries after it whose `planned` is non-empty. `progress.steps` is in spine order (`apps/board/src/lib/progress.ts:373-384`).
2. When `stepNow` is null, start after the last step whose `state` is not `pending` or `skipped`.
3. When `progress` has no recipe plan and no `StepsResolved`, every `planned` is empty. *Then* is then the rail's `UNREADABLE` (`rail.tsx`, already imported at `standing.tsx:309`), never an empty arrow list.
