## Design note: #872, `EventStore.head`

Most of the shape is in the ticket. This note covers four things the ticket does not decide.

### 1. `head` is the highest version, not a row count

Read the stream's highest version: `max(version)`, with a fallback to 0. The ticket's edge says *versions have no gaps*, so a count would give the same number today. The contract test is what holds them together, and only `max` can be served from the `UNIQUE (stream_id, version)` index (`sqlite.ts:108`) without visiting every row.

- **SQLite:** add one prepared statement next to `readStream` (`sqlite.ts:205`): `SELECT coalesce(max(version), 0) AS head FROM events WHERE stream_id = ?`. Every statement there is wrapped in `bigints(...)`, so the column comes back as a `bigint`. Return `Number(...)`, as `toEnvelope` does for `version` (`sqlite.ts:180`). If you skip that, `head` returns `0n`, `expected + 1` in `control.ts:210` throws a `TypeError` for mixing BigInt and number, and the memory store will not catch it.
  - **Naming:** there is already a local called `head` at `sqlite.ts:322-329` (`SELECT coalesce(max(seq), 0) AS head FROM events`, used by the subscriber). Name the new statement `streamHead` so nobody reading the file confuses a stream's version with the log's seq.
- **Postgres:** the store only has the ORM (`client.orm.public.Event…`, `event-store.ts:400-406`). Read the single highest row: `Event.where({ streamId }).orderBy((e) => e.version.desc()).limit(1).all()`, then take `rows[0]?.version ?? 0`. This shape is the same as the `readAll` chain at `event-store.ts:430-433`, so nothing new is needed from the ORM. It reads one row and no aggregate.
- **Memory:** take the max over `log.filter(e => e.streamId === streamId)`, with 0 for an empty list. This sits beside `read` in `test/memory.ts:215`, and that file is not counted by the ratchet.

**The ratchet:** in `sqlite.ts`, `event-store.ts` and `choose.ts`, write `head` without the `async` keyword. In the two stores that means a method returning `Promise.resolve(...)` for SQLite and a `.then(...)` chain for Postgres. In `deferredEventStore` (`choose.ts:153-160`) it means `head: (streamId) => resolve().then((s) => s.head(streamId))`. The comment above that function says *"each one is already `async`"* (`choose.ts:148-151`). Change it to say that every method returns a promise, because the new one is the exception the comment would otherwise get wrong.

### 2. Rewrite the `readTypes` doc comment

The interface currently says *"an append's `expectedVersion` comes from the full `read` (#796)"* (`event-store.ts:353-355`). After this ticket that sentence is false. Change it to point at `head`. #796's rule stays: never take a version from a filtered list's length. Only the remedy changes. Give `head` its own JSDoc stating that it returns 0 for an empty or unknown stream, that it reads no events, and that it **rejects as `read` would**. No caller may turn a failed read into 0.

### 3. Leave `append(..., at?)` in `control.ts` as it is

`append` at `control.ts:205-211` becomes `at ?? (await store.head(CONTROL_STREAM))`. `recordStart` keeps its loop (`:323-336`) and passes `at` from `head` on each try, as it does now. Do not merge the two reads into one. The out-of-scope appenders (`requestShutdownUnlessStanding`, `withdrawShutdown`) also pass `at`, from a version they took from a full read. The next child of #866 changes those, and this ticket must not change what `at` means.

### 4. `startAfter` and the webhook

- **`startAfter`:** `readTypes(CONTROL_STREAM, ['ConductorStarted'], version + 1)[0]`. `fromVersion` is inclusive (`event-store.ts:351`), so `version + 1` gives today's `e.version > version` (`control.ts:362`). The unit test for this must include a `ConductorStarted` *at* `version` that is not returned, plus one after it that is. Without both, an off-by-one passes.
- **The webhook (`route.ts:61-71`):** first `const at = await eventStore.head(CONTROL_STREAM)`, then the `readTypes` for `QueueChanged`, then `append(CONTROL_STREAM, at, …)`. Get the order wrong and a duplicate delivery can land unseen; that is the ticket's trap. No unit test reaches this route. The `QueueChanged` read and the append are inline there, so the only check is code review, and saying so is fine.

### What checks it

The contract suite (`test/contract.ts`) runs against all three stores, but the Postgres and SQLite runs are the integration half, which cannot be run inside a pass. The unit half only sees `head` through the memory store. So for the SQLite store, the unit-level stand-in is whatever unit test already opens it in memory, if one exists. If none does, add a single unit case: with the store's own types, `typeof (await store.head(id)) === 'number'`, after one append to that stream and one to another. That is the claim the `bigint` trap would break. Postgres is checked only after the merge.

Fakes that the type checker will make you give `head`: they are listed in the ticket. When a fake's `read` returns a fixed array, its `head` should return that array's length, so a test using the fake keeps the same expected version.
