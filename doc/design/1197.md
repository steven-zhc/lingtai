## 1. `withAllowedHost` says what it did, and on which lines

Today it returns `string | null` (`packages/recipe/src/allow-host.ts:16`). It answers `null` for three different cases: a host the recipe refuses, a host that is already listed (`:25`), and text that does not parse. The editor needs to tell the second case apart from the other two. Change it to a discriminated result:

```ts
type AllowedHost =
  | { kind: 'added'; text: string; lines: readonly number[] }   // 1-based, ascending, deduplicated
  | { kind: 'listed'; lines: readonly number[] }                  // the existing entry's line, in `text` as given
  | null                                                          // refused, metadata, or does not parse — unchanged
```

**The lines come from parsing again, not from comparing text.** After `doc.toString()`, parse the new text with `parseDocument(next, { lineCounter })` and look up these nodes:
- the `allow` sequence item whose value is the host;
- for each of `sandbox`, `network` and `allow` that `doc.hasIn` said was absent before the edit, that key's `Scalar` in its parent map.

Turn each node's `range[0]` into a line with `lineCounter.linePos(offset).line`.

For `listed`, use the first parse with a `LineCounter` and the item already there.

A flow sequence (`allow: [a, b]`) puts the host on the `allow:` line. Deduplicating handles that.

If any node cannot be found, the result is still `added`, with `lines: []`. This matches the ticket's edge: *the host is still added and the editor opens without a highlight*.

The only caller is `recipe-form.tsx`. The existing tests are `packages/project/unit/allow-host.test.ts`, not `packages/recipe/unit`. Extend that file with the positions the Done-when asks for:
- no `sandbox:` block: four lines;
- `sandbox:` present but no `network:`;
- an existing block-style `allow:` list: one line;
- a flow-style list;
- already listed: `listed` with that line;
- a comment above the block, so a line count that ignores comments goes red.

## 2. The form says which host, and the editor marks lines

`recipe-form.tsx` keeps `added: boolean` (`:49`) and has one hard-coded sentence (`:81-82`). Replace both with one piece of state: `said: { host; kind: 'added' | 'listed'; lines; rev } | null`.

- **When it is set:** both where `withAllowedHost` runs (`:43-44`, and the `useEffect` at `:51-60`) set it from the result. `null` sets nothing, so a refused host still opens the editor silently, as it does today.
- **What it shows:** *`<host>` was added for you — not saved*, or *`<host>` is already allowed*, in the same `.rfile-said` span.
- **When it clears:** when `state.ok` turns true after a save. Close unmounts the form, so closing clears it with nothing extra.

`yaml-editor.tsx` gets a prop `mark: { rev: number; lines: readonly number[] } | null`. It sits beside `push`, and the two stay separate on purpose. The `listed` case marks lines without changing the text, and `push`'s effect returns early when the text is equal (`yaml-editor.tsx:104`). Folding marks into `push` would drop exactly that case.

Inside the editor:
- **The field:** a `StateField<DecorationSet>` holds the marks. One `StateEffect` sets them and another clears them.
- **Mapping:** it maps through `tr.changes`, so typing above a marked line moves the mark with the line, and deleting the line removes the mark.
- **Creation:** the field goes into the extensions at `:84`, seeded with the `mark` from first render, as `initial` is.
- **Later changes:** a new `rev` dispatches the set effect, plus `EditorView.scrollIntoView(firstLinePos, { y: 'center' })`. Dispatch it after any `push` in the same commit, so the line numbers refer to the pushed text: run the mark effect after the push effect, in declaration order.
- **Clamping:** clamp each line to `1..doc.lines`. Text typed into the fallback textarea before the chunk loaded can shift the lines. That costs a slightly wrong mark, never a throw.
- **Style:** goes in the editor's `theme` (`:43`) as `.cm-added`, `{ background: 'var(--accent-soft)', borderLeft: '2px solid var(--accent)' }`.

The fallback textarea shows no mark, but the sentence still names the host. A decoration has nothing to draw on in a plain textarea.

`AllowRequest` (`recipe-text.tsx:10`) stays `{ host, nonce }`. The ticket says the allow request should *carry the added lines*. They are computed in the form from its own draft, because they depend on what has been typed there, which the URL cannot know.

## 3. The card

**Chips.**
- *Built-in paths:* use `chipsOf(paths, roots)`. Do not fold them; the ticket asks for chips, not `/… (N)`.
- *Built-in hosts:* use `vendorGroupsOf(builtIn.domains.map(host => ({ host, source: 'built-in' })))`. Check the `source` literal against `PolicyGroup['domains'][number]` and use whatever value means *not the recipe's*.
- *The recipe's own entries:* `network.allow`, `write` and `deny` are drawn **as written**, with no short name, because they are the YAML's own spelling (the mock's `~/secrets`).

- Add its legend line by hand: *each attempt's own, under `<lingtai home>/worktrees/<project>/`*.
- The other legend lines come from `legendOf` over the built-in chips.

**Markup.** Use one `.rcard#sandbox`:

The source column's rule (`← recipe.yml` when the recipe has entries for that row, else `← built in`) is a small pure function. Test that function rather than rendered HTML.

**CSS.**
- `.also` is used only by *Also set* (`page.tsx:187`), and its key column is 112px (`globals.css:3448`). Change that rule itself to 118px. A scoped override would misalign the two cards stacked in one column.

- `.chip-code` (`:3437`) keeps its `--rule` border. The dashed variant uses `--rule` too, never `--muted`.
