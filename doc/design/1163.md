# #1163 — design note

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

## The shape in one paragraph

Four pieces. Two pure functions go in `@lingtai/recipe`. One pure state module goes in `apps/board/src/lib/sandbox-state.ts`. One `cache()`d server read feeds a Suspense slot, and that slot is handed to `Bar` as a node. The facts come from the `ProjectState`s the board already has in memory. No new read is added, and nothing outside `prj-` is read. You need no new event, store method or projection: `ProjectState.refused`, `.recipe` and `.sandboxObserved` are already on main (`packages/domain/src/project.ts:43,53,56`, reduced at `:117-130`).

## 1. `@lingtai/recipe`: the predicate and the parse

**The predicate goes in `packages/recipe/src/sandbox.ts`.** Carry over `SANDBOX_REQUIRED_REFUSAL` and `isSandboxRequiredRefusal` from `agent/1163`'s copy of that file, and make the template at `sandbox.ts:164` use the constant. That way the sentence and its reader change together.

- Match by substring, not by equality. `ProjectRefused.detail` is *"The error, as the pass caught it"* (`events.ts`, `ProjectRefused`). That means the whole `RecipeInvalidError` message, which may carry a ref and other problems.
- **Do not carry over the branch's `HOST_FOR_SAVING` or its `readHost` import.** On main it moved to `packages/project/src/sandbox.ts:9`. The branch's copy would put `@lingtai/sandbox/host` back into `@lingtai/recipe`, and with it into the board's import graph.
- `apps/cli/integration/doctor-recipe.test.ts:160` asserts the sentence's prefix, so leave the text unchanged.

**The parse goes in `packages/recipe/src/declared.ts`.** That file's header already says *"Everything here is a function of text (0128 §8)"*. Add one function:

```ts
declaredSandbox(source: string):
  | { kind: 'block'; block: SandboxBlock | undefined }
  | { kind: 'unreadable'; why: string }
```

- Run `parseYaml`, then `asRecord`, then read the `sandbox` key, then `SandboxBlock.safeParse` (`sandbox-block.ts:34`).
- **Validate only the `sandbox:` key, not the whole recipe.** `Recipe.safeParse` needs `SCHEMA_PROBE_AGENT` and the preset dance (`declared.ts:39-56`). A recorded source has already passed `checkDeclared` to be recorded at all.
- No preset carries `sandbox` (`git grep sandbox packages/recipe/src/presets.ts` finds nothing). So `extends:` cannot supply the block, and `applyPreset` is not needed.
- These cases are *unreadable*, never *off*: YAML that does not parse, a root that is not a mapping, or a `sandbox:` that fails the schema.
- An absent key is `block: undefined`, which is *off by choice*. That matches `sandboxDecision` at `sandbox.ts:87`: `block === undefined || !block.enabled` is `'off by choice'`.

Unit tests go in `packages/recipe/unit/`, one per case above.

## 2. The state: `apps/board/src/lib/sandbox-state.ts`

Carry over the branch file's `sandboxState` / `worstOf` structure and its `RANK`. Change its input to what the Project holds:

```ts
interface SandboxFacts {
  refused: string | null                        // ProjectState.refused?.detail
  declared: 'none' | ReturnType<typeof declaredSandbox>   // 'none' = ProjectState.recipe === null
  observed: 'sandboxed' | 'degraded' | 'off by choice' | null  // ProjectState.sandboxObserved?.kind
}
```

Add `sandboxFactsOf(p: ProjectState): SandboxFacts` beside it. It is pure and calls `declaredSandbox(p.recipe.source)`. The state function itself must stay free of `@lingtai/project`, so #1166 and #1167 can import it client-side. That is the same split `lock-marks.ts` has from `locks.ts`.

**Order of the checks.** This is the ticket's table, read top to bottom; the first match wins:

1. `refused` matches the predicate → `stopped`.
2. `declared === 'none'` → `unknown`.
3. `declared.kind === 'unreadable'` → `unreadable`.
4. The block is absent or `enabled: false` → `off`. **The declared recipe outranks an older observation**: a degraded run followed by turning the sandbox off reads *off*.
5. `observed === 'degraded'` → `degraded`.
6. `observed === 'sandboxed'` → `sandboxed`.
7. Otherwise (`null`, or an `'off by choice'` observation from before the block was enabled): `sandboxed` if `refused === null`, else `unknown`.

**What to delete from the branch's version:**
- The `'incomplete'` boundary and the `'unreadable'` boundary. One stream read either succeeds or fails as a whole; that is a page-level failure (§4), not a per-project fact.
- The `b.why` branch. `ProjectSandboxObserved` is `{ kind, runId }` only (`events.ts`, `ProjectSandboxObserved`). The degraded sentence is the fixed string *degraded: the last run went without a sandbox because none was available*, and a test pins it.
- The `unknown` sentence's *"no sandbox record could be established"*. Make it *not yet known: no recipe has been recorded for this project* or similar, and pin it.

Keep `worstOf` as it is, including how it counts unreadable projects beside the worst one.

**Tests:** `apps/board/unit/sandbox-state.test.ts`, one test per row of the ticket's table. Add the two orderings that cost the earlier attempts rounds: a degraded run then turned off reads `off`, and a degraded run then re-enabled reads `degraded`. Add `worstOf` with one project and with several in the worst state.

## 3. The read: no new read at all

`apps/board/src/lib/locks.ts:42` already has `readRegistered = cache(() => loadProjects())`. `loadProjects` is `loadAllProjectsEffect` filtered by `isRegistered` (`packages/project/src/state.ts:134`). The home page (`page.tsx:648`), `/landed` (`landed/page.tsx:41`) and the recipe page already call it each render, so **the icon's facts cost nothing on those pages**.

Use `readRegistered`, not a new `cache(loadAllProjects)`, for two reasons. A pending project has no recipe and no name the bar can link to. And a second cached function would be a second read of every `prj-` stream on the same render.

Put `readSandboxMark(project?: string)` in a new `apps/board/src/lib/sandbox-read.ts`. Keep that file name, but do not carry over the branch's contents:
- It calls `readRegistered()`.
- It maps each project through `sandboxFactsOf` and then `sandboxState`.
- With `project` given, it is that project's state alone.
- With no `project`, it is `worstOf` over all of them.

`git grep -n "rcp-\|readTypes\|sandbox-walk" -- apps/board/src` must find nothing new. Do not bring `sandbox-walk.ts` or its test over at all.

## 4. The slot and `Bar`

**`Bar` gets `sandbox?: ReactNode` and nothing else.** Drop the branch's `SandboxMark | ReactNode` union and its `isMark` shape test. The node renders in `.topnav`, after the actions and before the Report link (`bar.tsx:48-61`). `SandboxIcon` can stay in `bar.tsx` beside `Bar`, as on the branch, because it is pure: React and `next/link` only.

**`apps/board/src/app/sandbox-slot.tsx`:** carry it over as it is. It is a `Suspense` whose fallback is the skeleton `<span className="sbx sbx-skeleton" aria-hidden>` with no label text, around an async component that awaits `readSandboxMark`.

**On a failed read:**
- If `readRegistered()` rejects, the slot renders the branch's `role="img"` span with the sentence *the sandbox state could not be read*. It is never *sandboxed* and never a link.
- **No projects registered** → `worstOf` returns `undefined` → the slot renders nothing.

Hand `sandboxSlot(project)` to every `<Bar>` the branch did: home (with `key('sandbox')`, `page.tsx` near `:1026`), backlog, landed, report, recipe (through `recipe-bar.tsx`) and the task layout. **Not** `/setup/*` or `not-set-up.tsx`.

Pages that read the projects only through the icon would add one read. They are `/backlog`, `/report` and `/task`: confirm whether each already calls `readRegistered` or `readProjectLocks`. Even where they do not, it is one read per render, and `cache()` dedupes it, so it is never a read per project.

**CSS:** carry over the branch's `globals.css` additions. *Off* must be grey with a dashed outline and an empty glyph, never an alarm colour. Each state has its own shape, so colour is never the only difference.

## Checks that stand in

- Everything here is unit-level. The one thing nothing checks before the merge is the Next build (`apps/release/integration/build.test.ts`). It is the only check that would see `@lingtai/sandbox/live` or srt reaching the board.
- The unit claim that stands in for it is the #1152 import-graph test. It must stay green. `declaredSandbox` and `isSandboxRequiredRefusal` add no import beyond `yaml`, zod and `./sandbox-block.ts` / `@lingtai/sandbox`'s pure index, which `sandbox.ts` already imports.
- Never call `hostHere`, `resolveRecipe`, `checkSandboxBlock` or `verdictOf` from `apps/board`.
- Whether a real project shows *stopped* depends on its last `ProjectRefused.detail` containing the constant's text, with no `ProjectRecovered` after it on `prj-<project>`. *Degraded* depends on the last `ProjectSandboxObserved.kind`. Those two events settle it, not the code.
