# Design note for #1163: sandbox state icon beside Report

## Where the three sources come from

The board already has two of the three. Only the boundary record needs a new read.

**Stopped comes from the projects read the bar already does.** `ProjectState.refused` is *"the refusal a conductor's pass last recorded, while nothing has recovered from it (#148). Null is not refusing, whether nothing ever was or a `ProjectRecovered` followed"* (`packages/domain/src/project.ts:37-43`). The board reads `ProjectState[]` once per render as `readRegistered = cache(() => loadProjects())` (`apps/board/src/lib/locks.ts:44`). So the rule "last refusal with no recovery after it" is already applied in the domain fold. Do not read `ProjectRefused` / `ProjectRecovered` again. The state is *stopped* when `refused !== null && isSandboxRequiredRefusal(refused.detail)`. The test "stopped cleared by a later `ProjectRecovered`" folds the two events through `reduceProject` and hands the result to the pure function.

**The predicate goes beside the sentence it matches.** The text comes from `checkSandboxBlock`: `` `sandbox.required: this recipe requires a sandbox and this machine cannot provide one (${said(verdict)}) — ` `` (`packages/recipe/src/sandbox.ts:170-171`). It reaches `detail` as a `RecipeInvalidError` problem caught by `conduct.ts`.
- Lift the fixed prefix into an exported constant in `sandbox.ts`, used both to build the sentence and by `isSandboxRequiredRefusal(detail: string): boolean`. If the wording changes, the two change together.
- Match the substring `sandbox.required: this recipe requires a sandbox`, not a prefix. `detail` is the whole error message, and other problems or a ref may come before it.
- A `sandbox.write` / `sandbox.deny` path refusal (`sandbox.ts:151-160`) is **not** *stopped*. It is a broken recipe, not a host that cannot sandbox. The project is still refused, and #1167's banner covers that. The unit test asserts both cases.
- `@lingtai/recipe` is already imported across the board (`apps/board/src/lib/board.ts`, `landed.ts`, `progress.ts`). Importing it does not load srt, because `sandbox.ts` imports `@lingtai/sandbox/host`, not `/live` (`sandbox.ts:20`).

**Off by choice comes from the recorded recipe, not the file.** `ProjectState.configHash` is *"the last resolved recipe hash"* (`project.ts:33`). The recipe it names sits on `rcp-<configHash>` as `RecipeRecorded.recipe`, *"`canonical(recipe)` as an object: parsed, `undefined` dropped"* (`packages/domain/src/events.ts:1171-1180`, appended by `recordRecipe` at `packages/conductor/src/steps-resolved.ts:39-46`).
- Read it with `readTypes(recipeStream(hash), ['RecipeRecorded'])`.
- No `sandbox` key, or `sandbox.enabled === false`, means off by choice. Once parsed, `enabled` defaults to `true` (`packages/recipe/src/sandbox-block.ts:37`), so a block that was written is enabled unless it says otherwise.
- Do not resolve `~/.lingtai/<p>/recipe.yml` on render. That is the host-asking path the ticket's Watch out rules out.
- No `rcp-` event yet (registered, never dispatched) is the *not known* case, not off by choice.

**Degraded / sandboxed come from the latest boundary record, which lives on a pass stream.**
- `SandboxBoundaryRecorded` *"goes on the attempt's `pass-` stream before the child starts"* (`packages/conductor/src/sandbox-record.ts:4`), and its payload has no `project` field (`events.ts:965-968`).
- So "the project's latest record" means: take the project's most recent attempt from `task_view` (it has `project` and `run_id`, `packages/projector/src/task-view.ts:99,107`), then `readTypes(<that run_id's stream>, ['SandboxBoundaryRecorded'])` and keep the last one.
- Check how `run_id` is spelled in `task_view` against `attemptStream` / `attemptIdOf` (`packages/domain/src/streams.ts:64-76`) before building the stream id.
- `boundary.kind === 'unsandboxed' && reason === 'degraded'` → degraded. `kind === 'sandboxed'` → sandboxed.

## "One shared read, never one log read per project": what is actually possible

The store has no read across streams by type. The port is `read`, `head`, `readTypes(streamId, …)` and `readAll(fromSeq, limit)` (`packages/event-store/src/event-store.ts:354-380`). Adding one means an implementation in Postgres, SQLite and memory, and two of those are only exercised by the integration half, which nothing runs before the merge.

So the decision is:
- **One `cache()`'d read per render** (`readSandboxStates`, next to `readProjectLocks` in `apps/board/src/lib/locks.ts` or in a new `apps/board/src/lib/sandbox-state-read.ts`).
- Inside it, **one `readTypes` per registered project** for its `rcp-` recipe and one for its latest pass, run concurrently.
- Every caller in the render shares it.

There is precedent. `readProjectLocks` already makes one `accountsFor` read per project inside its `cache` (`locks.ts:106-108`), and `loadProjects` reads every `prj-` stream. The edge's intent is no read per caller and no read per card, and this keeps it. The literal "never one log read per project" is not met, because the port cannot meet it without a new store method. Say so in the read's doc comment, and say a cross-stream type read is the change that would remove it.

New IO is an Effect (`packages/domain/unit/effect-ratchet.test.ts`). Write the read as an `Effect.gen` over `eventStore`'s Effect face. Run it once at the `cache` edge, as `readProjectLocks` does with `run(...)` (`locks.ts:42`). **Do not raise `effect-ratchet.baseline.json`.** If a new `async` would be needed, the code is wrong.

## The pure function and the order

`apps/board/src/lib/sandbox-state.ts`. It imports nothing that reaches the store, so `projects.tsx`-style client neighbours and #1166 / #1167 can import it, the way `lock-marks.ts` is split from `locks.ts` (`lock-marks.ts:5-7`).

**`sandboxState({ refused, recipe, boundary })`** returns `{ state, sentence }`, where `state` is one of `'stopped' | 'off' | 'degraded' | 'sandboxed' | 'unknown'`. The checks run in this order:

1. **stopped**: the refusal matches the predicate.
2. **off**: the recorded recipe has no block, or `enabled: false`. The current recipe beats an older run's degraded record: a person who turned it off after a degraded run sees *off*.
3. **degraded**: the latest record is `unsandboxed / degraded`.
4. **sandboxed**: the latest record is `sandboxed`.
5. **unknown**: everything else. That covers a failed read, no `rcp-` event, no boundary record yet, and a latest record of kind `refused` with no standing `ProjectRefused`. That last one is not *stopped*: after `ProjectRecovered` the old `refused` record would still be the latest until the next run, which would break "stopped is cleared by a later `ProjectRecovered`".

*unknown* is the ticket's "not yet known" and "cannot be read" edge. It is a fifth value for the code, not a fifth state in 0.14.md's table. It is never drawn as *sandboxed*.

**`worstOf(states)`** ranks by how much a person is needed (0.14.md, *Four states, not four levels*: *"the states rank how much they need a person, not how safe they are"*):

**stopped > degraded > unknown > off > sandboxed**

*Off* ranks above *sandboxed* only so that "all projects" never claims *sandboxed* while one project is off. It is still grey and dashed, never an alarm. `worstOf` returns the rank and every project that holds it, so the bar can choose a link or a disclosure.

## The bar

`Bar` gains one optional prop, `sandbox?: SandboxMark` (the projects and states already worked out), and renders it in `.topnav` immediately before the Report `<Link>` (`apps/board/src/app/bar.tsx:55`), after `actions` / `BarActions`. It stays React plus `next/link` (`bar.tsx:5-6`).

- **One project in the worst state:** a `<Link className="sbx sbx-<state>" href="/recipe/<p>#sandbox" aria-label={sentence} title={sentence}>` with an empty `aria-hidden` mark span and no text.
- **Several:** a `<details className="sbx-list">` whose `<summary>` has the same `aria-label` / `title`, then a list with one link per project.
- **Absent prop** (no projects, `/setup`): nothing.
- **Loading:** pages that stream the bar's actions (the home page, `bar.tsx:32-35`) pass a skeleton node in the same slot with no label text.

Colour comes from existing tokens: accent, muted with a dashed border, signal, fail. Unknown is muted with no shape claim.

**Pages.** Every page that renders `<Bar` with projects passes `sandbox={await readSandboxMark(project)}`, except the `/setup` ones. That is about 13 call sites (`git grep -l '<Bar' apps/board/src`), each one line, because the read is cached.

## Tests

- `apps/board/unit/sandbox-state.test.ts`: the five results, stopped cleared through `reduceProject`, path refusal ≠ stopped, off beats an earlier degraded record, and `worstOf` with one project and with several.
- `packages/recipe/unit/`: the predicate, positive and negative, built from the same constant `checkSandboxBlock` uses.
- `apps/board/unit/bar-component.test.tsx:52-58`: rewrite it to remove only the icon's element before asserting `not.toContain('/recipe/')`. Do not loosen the assertion, so any other `/recipe/` link still fails. Add one case asserting the icon sits before `/report`, and one for `<details>`.
- The import-graph tests already hold the `/live` rule (`packages/domain/unit/sandbox-live-import.test.ts`, `packages/sandbox/unit/no-live-import.test.ts`). Do not import `@lingtai/conductor`'s `hostHere` (`packages/conductor/src/projects.ts:230`) anywhere in this change.

## Doc

`doc/design/the-bar.md:133-134` says the icon is *"at the end of `.bar` in `apps/board/src/app/page.tsx`"*. Change it to `.topnav` in `apps/board/src/app/bar.tsx`, before Report, drawn on every page that renders the bar except `/setup`. This is an edit to a design doc, not an ADR, so no superseding file is needed.

## What settles it after merge

The unit tests stand in for what the log would show. On the real log:
- *stopped* should line up with the project's latest `ProjectRefused.detail` containing the `sandbox.required:` prefix and no later `ProjectRecovered` on `prj-<p>`.
- *degraded* should line up with the latest `SandboxBoundaryRecorded.boundary` on that project's newest `pass-` stream reading `{kind: 'unsandboxed', reason: 'degraded'}`.
