# Design note — #1170: the conductor applies a kept WIP before any agent runs

## Where it goes

**In `cut`, after `repo.provision` succeeds and before `cut` returns** (`packages/conductor/src/conduct.ts:2994-3001`). `cut` is `admit`'s dep (`conduct.ts:2898-2912`), so every agent step runs after it, `design` included. Applying the WIP here satisfies "before any agent runs" without adding a new step and without touching the step matrix.

A restart does not cut twice within one `conduct` call. Choosing `claim` "ends this pass: a restart is a requeue" (`run-attempt.ts:798-800`). A continuation never carries anything: `previous` is `undefined` when `continuation !== null` (`conduct.ts:1424`), and nothing is read without a previous attempt.

The git sequence goes in **a new module beside `kept-run-port.ts`**, for example `packages/conductor/src/carry-wip.ts`. It is written against the same `GitHere` runner that `commitWipExceptPlanted` takes (`kept-run-port.ts:87-91`). That precedent is the reason `unit/kept-run-port.test.ts` can pin the call order with a scripted fake git and no git binary (its header: *"No git binary, so this is `unit/` by 0060 §1"*). Write it as an Effect over `GitHere`, with no `async`, because of the ratchet.

## The pipe is two commands, not a pipe

`RepoPort.git` runs one command and has no stdin (`GitRunOptions`, `packages/repo/src/git.ts:25-41`). ADR 0109 §8 names `git diff <parentSha> <sha> | git apply --3way`. Build it as two commands with a file between them, so the conductor needs no filesystem port:

1. `git rev-parse --git-path lingtai-carry.patch`. In a linked worktree this resolves inside that worktree's own git dir. It is per-pass, it is not in the work tree, and it goes when the worktree is removed.
2. `git diff --no-color --no-ext-diff --no-textconv --binary --output=<that path> <parentSha> <sha>`
3. `git apply --numstat -z <path>` is the **parse check** and the list of paths. If this fails, the diff "cannot be parsed": nothing is applied and the brief says so. Do not proceed to step 4.
4. `git apply --3way <path>`. `--3way` implies `--index`.
5. If step 4 exited non-zero, run `git diff --name-only --diff-filter=U -z` to list the unmerged paths. For each one, run `git checkout --no-overlay HEAD -- <path>`. `HEAD` is the cut, which is the base, so this is the "left at the base's version" the ticket asks for. `--no-overlay` also removes a path the base does not have. **The checkout source is always `HEAD`, never `<sha>`** (the ticket's Watch out).
6. If step 4 failed and nothing was unmerged, git refused the patch as a whole. Run `git checkout --no-overlay HEAD -- .` to be sure nothing half-applied stays, and report nothing as applied, with git's own words.
7. `git reset -q` unstages everything, so the carried edits sit in the worktree exactly as a stopped agent's dirty tree did. The planted env file is untracked and is untouched by both resets.

**You do not need a separate fetch.** `provision` runs `ensureMirrorEffect`, which does `fetch --prune origin +refs/heads/*:refs/heads/*` on every call (`packages/repo/src/worktree.ts:143`), and the worktree shares the mirror's objects. Before step 2, check `git cat-file -e <sha>^{commit}` and the same for `parentSha`. If either is missing, that is the ticket's "could not be fetched" edge: carry nothing and name the arm and sha in the brief. `RunKeptUncommitted` is appended only after the arm is on origin (`conduct.ts:2355-2360`: *"a sha named on the log must be fetchable"*). So this edge is rare, but it is reachable, for example when someone has deleted the arm since.

**Never die inside the carry, with one exception.** In steps 1–4 a failure leaves the tree as it was cut, so the pass goes on with "nothing carried, because…". A failure in steps 5–7 leaves conflict markers or a half-applied tree, and an agent must not start on that. In that case `cut` returns `{ notCut: … }` (`conduct.ts:2996`). That is 0057's machine-fact class: no round is bought, and the item is released or blocked like any other cut that did not finish.

## The brief is rendered after the cut, not before

This is the part the ticket does not show. Today `nextPrompt` runs **before the pass**, at `conduct.ts:1435-1442`, and `promptVersion = next.version` hashes `failure` (`prompt.ts:141-150`). The carry's result is only known inside `cut`.

`next.failure` and `promptVersion` are read only at `implement`: `RunStarted.promptVersion` at `conduct.ts:4471`, `renderPromptParts(… next.failure …)` at `:4498`, and `recordPrompt` at `:4531`. So:

- Keep the early `nextPrompt` call. `next.attempt` and the arm (`:1446`) still come from it.
- `cut` stores its result in a pass-scoped `let carried: Carried | null`, the same way it already stores `worktree` and `lease`.
- At `implement`, call `nextPrompt` again with `carried` added. It is pure, and its inputs (`reduced`, `lastRun`, `arms`) are already in hand. Use that call's `failure` and `version`, so the recorded version hashes the text that was actually sent.

`attemptBrief` (`attempts.ts:388`) takes `carried` as a fourth parameter and replaces both WIP passages. One is the `produced === null` branch (`:441-462`). The other is the `produced !== null` add-on (`:473-480`). Both currently say `git diff … | git apply`. What `carried` can say:

- **Applied:** the worktree already holds N file(s) of the stopped run's edits, from `<arm>` at `<sha7>`, stopped by `<stoppedBy>`, uncommitted. They were never built or reviewed. Commit them as the work stands. If any paths were left out, name each one with `git show <sha7>:<path>` and `git diff <parent7> <sha7> -- <path>` to read it from. The judgement on those paths is the agent's.
- **Not applied:** say why, in git's words, and give the arm and sha. Do not offer the old pipe as a fallback instruction.
- **Both `produced` and `kept`:** the WIP's parent is that attempt's last commit, which the fresh worktree does not have (`:468`). Say that the edits were applied against the base, and that a path the commits also touched is the likely left-out path.
- **`carried === null` while `kept !== null`:** this happens when the caller did not carry, for example in a test that renders the brief directly. Say nothing about applying, and do not resurrect the old verbs.

The existing comment at `attempts.ts:416-418` says `unit/attempts.test.ts` "reads this wording for the verbs it must not use". Add `git apply` and `checkout <sha>` to what the WIP passage must not tell the agent to run.

## The event

Add a new run event, for example `RunCarriedKeptWork`, appended to **this** run's stream inside `cut`. Its data:

- `from: { runId, arm, sha, parentSha }`
- `applied: string[]`
- `leftOut: string[]`
- `why: string | null`, which is non-null exactly when nothing was applied

Declare it in `packages/domain/src/events.ts` beside `RunKeptUncommitted` (`:890`), and add a row to the step table at `:2700` with `['admit']`. If the store refuses the append, log it and go on, as `noteKept` does (`conduct.ts:2384-2387`). The worktree already holds the edits and the brief says so.

**Do not fold it into `AttemptState`.** Nothing reads it yet: no app renders `.kept` either. A fold would change the snapshot codec (`run-codec.ts:135`) and void every snapshot for no reader. The board line is a follow-up, and that follow-up adds the fold. The log can already answer what was carried and what was left out.

## Edges the ticket leaves implicit

- **A pass that carries and then stops before the agent touches anything** (never-started, or a quota wall): `keepUncommittedWork` returns early when `stoppedBy === null` (`conduct.ts:2257`). The carried edits go with the worktree, and the next attempt's previous run has no `RunKeptUncommitted`. The WIP still sits on its older arm. This is not a regression, because today's brief also reads only the last attempt. Changing it is "changing when a WIP is written", which the ticket puts out of scope.
- **The agent crashes after the carry:** the keep's `parent..sha` now spans both the carried edits and the new ones, so the next attempt carries the accumulated work. That is the intended chain.
- **Two passes at once (0122):** each pass writes only to its own worktree, its index, and a per-worktree path. The `--3way` blobs go to the shared object store, which is safe without `mirrorWrite` (`conduct.ts:1973-1979` holds that lock for ref and metadata writes only).

## Tests

- `unit/carry-wip.test.ts`, with a scripted `GitHere` in the style of `kept-run-port.test.ts`:
  - The diff flags are pinned exactly.
  - A failed `--numstat` makes no `apply` call.
  - An unmerged path is restored with `checkout --no-overlay HEAD -- <path>`, and no call anywhere names `<sha>` as a checkout or reset source.
  - A missing sha carries nothing.
  - A failed restore is reported as a failure, not as "nothing carried".
- `unit/attempts.test.ts`: the applied, left-out and not-applied wordings, plus the forbidden verbs.
- A conduct-level unit test in `conduct-a-whole-attempt.test.ts`'s style:
  - `lastRun` carries a `RunKeptUncommitted`.
  - The fake `repo.git`'s `apply --3way` call comes before the agent dispatch.
  - `RunCarriedKeptWork` is appended.
  - The recorded implementer prompt holds the carried section.
  
  These cover the ticket's two "Done when" unit tests. They pin the call order and the wording, not git's behaviour.
- **What a fake cannot show** is what real `git apply --3way` leaves on a conflicting path, and that `--no-overlay` restores it, including a path the base does not have. Put that in an `integration/` test against a real repository. It cannot run inside the pass, so it is caught after the merge (0060).
