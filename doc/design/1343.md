## The fact that sets the shape: on a local project, the reader's checkout is the remote

`lingtai init --local chapter-garden` writes the checkout's own top-level path as `repo.remote`. See `apps/cli/src/first-project.ts:558-559`: *"The checkout itself is the remote (0104 §15): nothing a pass makes leaves the machine."* `remote = toplevel`.

Because of that, `prHostOf` returns `'none'` (`packages/conductor/src/pr.ts:243`: *"`github` where the recipe names no remote of its own, `none` for any other"*). Every step below follows from this.

- **PR branch name.** It is `` `${frozen.branch}-pr-${state.n}` `` (`packages/domain/src/pr.ts:683`), so the first PR's branch is `lingtai-base-pr-<n>`. Before you write the number, check where `n` is assigned for the first PR. Either way, tell the reader that `lingtai pr` prints the name on the line `PR <n>: in-review — lingtai-base-pr-<n>` (`apps/cli/src/pr.ts:197-199`).
- **Where it is pushed.** It is pushed into the reader's own `chapter-garden` checkout, by the `push` step (`pr.ts:255`: *"The only push of a PR branch, never forced"*). The `open` step then records `host: 'none'` and opens nothing (`pr.ts:440-446`). The `ci` step skips where nothing is configured (`pr.ts:575`).
- **The "open it by hand" text.** `lingtai pr` prints *"`<branch>` is pushed; open the pull request by hand with:"* and then the description (`apps/cli/src/pr.ts:203-211`). On Chapter Garden there is nowhere to open a pull request.
  - **Decision:** the chapter says so in one sentence: the description is there to read, and the PR is reviewed by reading `git diff main...lingtai-base-pr-<n>` and merged by the `git` lines below.
  - The sentence the CLI prints is awkward for a local project. Changing it is out of scope; file it as a backlog entry and do not change the code.
- **How the reader merges.** Run it in the checkout, on `main`, as a merge commit:

  ```sh
  git -C chapter-garden switch main
  git -C chapter-garden merge --no-ff lingtai-base-pr-<n>
  ```

  - **No `git push`.** The checkout's `main` is the remote's `main`.
  - **Merge the PR branch, not `lingtai-base`.** `lingtai-base` may already hold landings that came after the freeze, and those belong to the next draft.
  - **Why `--no-ff`, from the code.** Without it, git fast-forwards silently whenever `main` has not moved, and 0130's *Consequences* wants a merge commit. A squash is worse: it is never detected as merged (next bullet).
- **What marks it *Merged*.** The PR sweep fetches (`pr.ts:1212-1213`) and then asks `git merge-base --is-ancestor <lastPushed> refs/heads/main` (`pr.ts:1171`). A yes appends `PrMerged { how: 'git' }` (`pr.ts:1228-1229`). A squash commit does not contain `lastPushed`, so the PR would stay *In review* forever. That is the reason to give the reader.
  - After the sweep, `lingtai pr` prints `PR <n>: merged by git at …` (`apps/cli/src/pr.ts:183-187`).
  - `closeMergedTickets` (`pr.ts:1245`) closes the tickets the merged commit held.
  - Both run only in a running conductor, so the chapter repeats *keep `lingtai start` running* at the merge step, not only at the submit step.
- **The catch-up after the merge.** After the merge, Lingtai merges `main` back into `lingtai-base`. `lingtai pr` then prints `caught up lingtai-base with main at <sha>` (`catchUpLine`, `apps/cli/src/pr.ts:339-346`). That push into the checkout is refused while `lingtai-base` is checked out (`packages/repo/src/integrate.ts:169-177`). So the edge *the reader is on `lingtai-base` or the PR branch* gets one rule, which covers the merge and the catch-up: *stay on `main`*. Showing the catch-up line is optional; include it if the word budget allows.

These claims hold up in code only. Nothing in the unit half runs this path from start to finish against a real checkout, and the integration half (803 s) is out of reach in a pass. The unit claim that stands in is `prReport`'s output for `prHostOf === 'none'` and for an ended PR (`apps/cli/src/pr.ts:183-211`). Quote the CLI's lines from that code, not from 0131.

## Cost, said once, as chapter 1 says it

`tutorial.md`'s Step 3 states what `lingtai start` spends. This chapter does the same:

- **Each new ticket** is one more paid attempt, with a writer and a reviewer.
- **`submit`** buys one more paid agent run: `summaryStep`, *"The `pr:` agent writes a PR's title and summary"* (`packages/conductor/src/pr-summary.ts:2`). It also runs the build (`IN_PROGRESS_STEPS`, `pr.ts:719-729`).
