## Design: #368. Put the output contract last, and say where a re-review's verdict goes

### Start from `main`, not from attempt 1

`agent/368-attempt-1` (`b21e6d1`) branches from `c8389b9`, which is before #369's `53c81d1`. That commit rewrote `CONTRACT` (`packages/actions/src/agent-action.ts:149-172`). It deleted *"Report as a single JSON object, and nothing else after it"* and the JSON example, and its message says why: *"CONTRACT drops the JSON-shape rules the schema now enforces and keeps the judgement ones."* Attempt 1's `CONTRACT` hunk edits the old text. A cherry-pick conflicts, and resolving it the easy way brings back the example #369 removed on purpose. Use attempt 1 as a reference and write the change again on today's `CONTRACT`.

That also makes part of the ticket's evidence out of date. The contract no longer opens with a format sentence. Today it is the judgement rules and ends *"An empty findings list is a real answer."* (`:166`), followed by the "do not read other issues" paragraph (`:168-169`). Two consequences:

- After #369, `claim` and `failureScenario` appear nowhere in the prompt's prose. Only `REVIEW_ANSWER_JSON_SCHEMA` carries them, sent as `outputSchema` at `:475`. The recheck sentence will be the only place the prompt names those keys. That is right, because the schema is sent on every review. Spell them exactly as the schema does.
- The minor finding about `toContain("failureScenario")` being satisfied by `CONTRACT`'s example does not reproduce on today's tree. Keep the test discipline anyway: the next edit to `CONTRACT` could add an example back.

### The reorder (`buildReviewPrompt`, `:239`)

The order becomes:

    ticket → checklist → severity → project extras → recheck block → diff → ## How to report

- **Project extras stay above the diff.** Only the contract moves to the end. Extras are allowed to add concerns, not to have the last word (`AgentActionSpec.prompt`, `:75`: *"Appended to the fixed brief. Adds concerns; cannot remove them."*).
- **Inside `CONTRACT`, move the "Do not read other issues … the diff above" paragraph to the top**, as attempt 1 did. The last thing the reviewer reads is then the Rules list, not a scope rule. *"the diff above"* is still true after the move. That edit was right, so reuse it.
- `clipped` still bounds only the diff, so the contract is never truncated. The truncation marker `[diff truncated at N bytes]` now sits inside the fence, above the contract. That is fine.
- `judge-agent.ts:71` says *"The shape is `buildReviewPrompt`'s, deliberately"* and is about the kind of content, not the order. Leave it alone.

### The recheck sentence (`recheckBlock`, `:193`): the decision that matters

Attempt 1's major finding was a placement bug as much as a wording bug. Its new bullet came **last**, was bolded, and had no scope, so it overrode the "simply not reported" bullet above it. The fix is structural:

1. **Put the verdict-placement instruction inside the bullet it qualifies**, the first one: *"A scenario that is still reachable by \*any\* path is still a finding. Report it again …"* (`:217-218`). Extend that bullet so that a scenario that still reproduces, wholly or in part, is reported as a finding:
   - `claim` says what is still wrong.
   - `failureScenario` gives the sequence as the code now stands, narrower than the quote where only part survives.
   - A scenario with two surviving paths is two findings.

   Keep that last point from attempt 1. It answers the ticket's Watch out ("cram the narrative into `claim`") directly, and it is the part #369 does not cover. A conditional bullet cannot be read as covering every scenario.
2. **Keep "simply not reported" as the last scenario bullet**, and give it the empty case in words: on a re-review where every scenario is closed and nothing else is wrong, the answer is an empty findings list. Never write "every verdict is a finding" or "each scenario gets an entry" anywhere in the block.
3. **Use no format phrase about prose**, such as "never a sentence beside the JSON". Under `--json-schema` there is no "beside", and the phrase would mean something different on each runtime. The point is *where the verdict goes*, and items 1 and 2 already say that.

Leave the removal bullet (`:219-224`, *"say so in a new finding"*) as it is. It already puts its verdict in a finding.

### Tests (`packages/actions/unit/agent-action.test.ts`)

Assert against the recheck block's own text without exporting `recheckBlock`. Slice the prompt from `## Scenarios that must no longer happen` to `## The diff`. Both headings are fixed strings, and the existing test at `:236` already relies on the first one. Put a small helper at the top of the `describe("asking the reviewer again after a fix")` block at `:174`.

**Contract after the diff**
- `prompt.indexOf("## How to report") > prompt.lastIndexOf("\`\`\`diff")`, and also greater than the index of the diff's own text.
- Check all three shapes: plain, with `spec.prompt`, and with `recheck`.
- Add one case with a diff over `DIFF_BYTES`: the contract is still present and still last.

**Verdict placement, on the slice only**
- With recheck findings, the slice contains `` `claim` `` and `` `failureScenario` ``.
- On a first review the slice is empty, and the existing *"says nothing about a re-review"* test at `:154` stays green.

**No contradiction**
- Split the slice into bullets on `\n- `.
- The bullet that names `failureScenario` is the one that matches `/still reachable/`, which makes it conditional by construction.
- The bullet matching `/simply not reported/` comes after it.
- The slice matches the empty-findings sentence.
- Nothing in the slice matches `/every (verdict|scenario)[^.]*finding/i`.

This is the *"a re-review of a diff that fixed everything must be able to answer `{"findings":[]}`"* check, asserted on the prompt. It is the only level at which it can be checked before the merge.

The existing assertions at `:196-213` still match the re-ordered prompt word for word. Do not reword them.

### What only the log can confirm

Whether a reviewer now writes narrower findings, or still crams them, is not something a unit test can show.

- **Unreadable answers:** look for `StepFailed` on the `review` step carrying `unreadable: true`.
- **Crammed findings:** compare the `claim` length of findings on a re-review's `StepFailed`, where the run log notes *"rechecking N finding(s)"* (`:466`), with first reviews.

Name those in the commit body. Do not claim them as verified.

`pnpm typecheck` and `pnpm test` are the whole check. Nothing here touches the integration half.
