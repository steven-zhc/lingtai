## Design: #368. The contract goes last, and each re-check verdict goes in a finding

### What is there today

`buildReviewPrompt` (`packages/actions/src/agent-action.ts:231`) builds the prompt in this order:

    preamble → ## The ticket → ## The checklist → ## Severity → ## How to report (CONTRACT)
             → ## Also for this project (spec.prompt) → recheckBlock → ## The diff

The clip only touches the diff. `diff.slice(0, limitBytes)` at `:238` runs on `diff` alone, not on the whole prompt, so moving `CONTRACT` after the fence cannot get it truncated. You do not need to change how the clipping works.

`CONTRACT` (`:143`) already reads as if it came after the diff. Its last paragraph says *"look at anything outside this worktree and the diff above"* (`:166-167`), and today the diff is below it. Once the move is done, that sentence is true.

### The order after the change

    preamble → ticket → checklist → severity → Also for this project → recheckBlock → ## The diff → ## How to report

- **The project extras stay before the diff.** They add strictness, as the test at `unit/agent-action.test.ts:119` says (*"A recipe adds strictness and never removes it"*). They are not part of the output format, and nothing may sit between the diff and the contract.
- **Reorder the inside of `CONTRACT` as well, so the prompt ends on the format.** Today the last thing in `CONTRACT` is the scope paragraph (*"Do not read other issues, run `gh`… Your value is that you do not know what anyone concluded."*, `:166-167`). That is a rule about what the reviewer may look at, not about how it answers. Put that paragraph first. Then come *"Report as a single JSON object, and nothing else after it"*, the example and the rules, so the last words of the prompt are *"An empty list is a real answer. Say {"findings":[]}."* Change the order only, not the text. Every phrase the existing tests match must survive: *no failure scenario, no finding*, *say what a refusal is about*, *omit the key when you cannot say which* (`unit/agent-action.test.ts:115,147-151`).

### The sentence in `recheckBlock`

It goes in the bullet list at `:220-232`, with the last bullet: *"A scenario that genuinely can no longer produce its outcome is simply not reported. Do not say so…"*. That bullet already covers half of what the ticket asks: a fixed scenario is absent. Add the other half there. Do not add a new paragraph after the list, because that would be prose sitting after the instruction to *"review the diff as it now stands for anything else"*.

What it must say, and the decision the ticket leaves open:

- **A scenario that still reproduces, fully or partly, is a finding, in the format at the end of the prompt.** Its verdict is the finding. It is not a sentence before the JSON or beside it. Point forward to *How to report* by name, since that section now comes after this one.
- **The narrative goes in `failureScenario`, not in `claim`.** This is the decision that matters, and it answers the ticket's *Watch out*. `CONTRACT` defines `claim` as *"one sentence, what is wrong"* (`:147`). In #318's answer, the useful content (*"`severity` is guarded; `file` is not"*, the guard at `:450` and its twin at `:418`) is a sequence, and sequences are what `failureScenario` is for. It has no length rule. If the sentence says only *"put it in `claim`"*, it creates exactly the cramming pressure #369 will make worse. So the sentence says:
  - `claim` states what is still wrong.
  - `failureScenario` is the sequence that still produces the outcome, **as the code now stands**. That may be narrower than the quoted scenario, for example the surviving `file` path rather than the original one.
- **A half-fixed scenario with two surviving paths is two findings, not one finding with a long claim.** Say this explicitly. It is the cheap way out of the cram pressure.
- **Do not weaken 0038 §2.** The verbatim quote is a guard on what the reviewer *reads*. What it *writes* is a new finding, and the next fixer is held to that finding verbatim in its turn. Rewriting the scenario so it matches the path that still survives is the point, not a paraphrase. No ADR is contradicted.

### Tests (all in `packages/actions/unit/agent-action.test.ts`, unit project)

- **Order.** Assert `prompt.indexOf("## How to report")` is greater than `prompt.lastIndexOf("```")`, the closing fence of the diff. Use `lastIndexOf` rather than `indexOf("```diff")`: the opening fence would also pass if the contract ended up inside the fenced block. Run it on three prompts:
  - a first review;
  - a re-review (`refused`);
  - a review with a non-empty `spec.prompt`.

  The third one pins the extras above the diff. Use a diff string that contains neither `` ``` `` nor the heading, such as the existing `"THE-DIFF"`.
- **The end of the prompt.** Assert `prompt.trimEnd().endsWith('{"findings":[]}.')`, or whatever the last rule ends with after the reorder. This is cheap, and it catches a later edit that puts something after the contract.
- **The new sentence.** Match it on the `refused` prompt and assert it is absent on the first-review prompt. That absence already follows from `recheckBlock` not being called (`:256`), but the Done-when asks for it. Match on `failureScenario` together with words that place the verdict *in a finding*, so that a later edit cannot leave `claim` as the only place named.
- The existing tests `says nothing about a re-review…` (`:153`) and `keeps the rubric, the checklist and the diff…` (`:204`) should pass unchanged. If either goes red, the reorder dropped some text.

### What this cannot show

`pnpm test` proves the prompt's shape. It cannot prove that a reviewer now answers in JSON. Only the log can show that: the review step's `StepFailed` with reason `unreadable`, against a re-review attempt that carries recheck findings, counted before and after this lands. No unit test stands in for that count. Say so in the commit body, and do not claim the behaviour is fixed.
