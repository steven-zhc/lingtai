# Design note for #1076: the daemon store is opened by an Effect and closed by its scope

## Where it goes

Almost all of this is `packages/daemon/src/choose.ts`. The other four files each change one call to `withDaemonStore`. There are five such calls today:

| Site | Today |
|---|---|
| `control.ts:503` `createStatusTableEffect` | `Effect.promise(() => withDaemonStore(store, {}, (it) => it.create()))` |
| `control.ts:538-552` `beatEffect` | `Effect.promise(() => { …destructure…; return withDaemonStore(options.store, {}, (store) => store.beat({…})) })` |
| `control.ts:716` `readStatusEffect` | `Effect.promise(() => withDaemonStore(store, {}, (it) => it.status()))` |
| `converge.ts:384-386` `findIssueDriftEffect` | `yield* Effect.promise(() => withDaemonStore(…, candidates))` |
| `reconcile.ts:115-118` `withStreams` | `attempt(() => withDaemonStore(…, fn))`, where `attempt` is `Effect.tryPromise({ try, catch: (e) => e })` (`:121`) |
| `work-loop.ts:667-673` `headSeq` | `Effect.promise(() => withDaemonStore(…, (store) => store.head()))` |

Nothing outside `packages/daemon/src` calls `withDaemonStore`. The only caller of `processDaemonStore` outside the package is a spawned script in `integration/the-written-choice.test.ts:218-222`. It also gets re-exported from `index.ts:39`. Changing `withDaemonStore`'s signature therefore breaks no other package. `index.ts` is not on the ticket's diff list, so leave it alone. **Do not export `processDaemonStoreEffect` from the barrel**, because nothing outside the package needs it.

## `choose.ts`

```ts
export const processDaemonStoreEffect = (options: DaemonStoreOptions = {}): Effect.Effect<DaemonStore> =>
  Effect.suspend(() => {
    const choice = chosenStore()                       // throws → defect, at run time
    if (choice.store === 'postgres') return Effect.succeed(createPostgresDaemonStore({...}))
    return Effect.promise(() => import('./sqlite.ts')).pipe(
      Effect.map((sqlite) => sqlite.createSqliteDaemonStore(sqlite.openSqliteDaemon(choice.path), options.events)),
    )
  })
```

- **Build the SQLite import inside the `sqlite` branch and nowhere else.** Do not put `import('./sqlite.ts')` in a module-level constant or a helper that runs eagerly. `the-written-choice.test.ts` reads `process.moduleLoadList` after opening a Postgres store, and it fails if `node:sqlite` was ever evaluated.
- `openSqliteDaemon` is synchronous and can throw, for example on a path it cannot open. Inside `Effect.map` that throw becomes a defect, which is what the ticket wants. Do not wrap it in `Effect.try`. That would give the Effect an `E` channel that every caller then has to type.
- `withDaemonStore`'s `given` branch is `use(given)`, with no acquire and no release (`choose.ts:76` today). The other branch is `Effect.acquireUseRelease(processDaemonStoreEffect(options), use, (s) => Effect.promise(() => s.close()))`. Acquire is uninterruptible, so an interrupt that arrives during the dynamic import or the open waits for it to finish and then releases the store. That is what we want: no handle can be opened without being closed.
- Keep `chosenStore(` and both `create…DaemonStore` names in this file. `unit/one-store.test.ts:95-103` requires that `choose.ts` is the only file containing both names.
- The module comment at `:22-26` ("every caller here now closes the store it did not receive") still holds. Add one sentence saying the close is the release of an `acquireUseRelease`, so an interrupted beat also closes its store. Change the one-line doc at `:70` to match.

## The callers

- Each `use` lifts exactly the store method it calls, as `(s) => Effect.promise(() => s.head())` and so on. `converge`'s use is `(s) => Effect.promise(() => candidates(s))`. `candidates` (`converge.ts:361`) is a plain function returning a promise, not an `async` one, so the ratchet does not count it.
- `beatEffect`: the destructuring of `options` no longer needs a promise around it. Do it inside an `Effect.suspend` (or `Effect.gen`) and return `withDaemonStore(...)`. The reason is that `beatEffect` is built once and could be run many times (`startBeacon`), so the options must be read when the Effect runs. Reading them while it is built would be wrong.
- Delete the comments that say the lift stays "until DAEMON-7a": `converge.ts:382-383`, `reconcile.ts:116` and `work-loop.ts:665`. They describe this ticket.

## Reconcile: the one change in behaviour

Today a refusal or a rejection inside `withStreams` is a **failure** (`attempt` is `tryPromise`). The catch at `reconcile.ts:564` turns it into `[]` with `Effect.catch`, which sees failures only. After this change the same events are **defects**: `Effect.promise` turns a rejection into a defect, and `Effect.suspend` turns `chosenStore()`'s throw into one. `Effect.catch` would let them through, and `releaseForeignClaimsEffect` would die on a machine that wrote no choice.

So:

- `withStreams` returns `Effect.Effect<T>` with no error channel. It stops calling `attempt`, which stays because `:309`, `:320`, `:333` and others still use it.
- The catch at `:564` becomes the same expression already used at `:497`, `Effect.catchCause((cause) => (Cause.hasInterruptsOnly(cause) ? Effect.failCause(cause) : Effect.succeed([] as string[])))`. Copy it as written rather than inventing a variant: an interrupt must stay an interrupt, never become `[]`.
- Nobody reads the message off that error: `:116` says "a message read off it is the store's", but `:564` was its only consumer and it discards the error. Drop that sentence.

## Tests (new files in `packages/daemon/unit/` only)

**What a unit test can rely on:** the `unit` project has no `globalSetup` (`vitest.config.ts:106` sets one only for `integration`). Under unit, `LINGTAI_TEST_SQLITE_PATH` is therefore unset, and `storeChoice` refuses (`packages/env/src/index.ts:650-660`) **unless the shell exported `LINGTAI_TEST_DATABASE_URL`**, in which case it answers Postgres (`:620-629`). Neither test may depend on the shell, so each sets that variable itself and restores it afterwards.

1. **`withDaemonStore` closes what it opened.**
   - Setup: set `LINGTAI_TEST_DATABASE_URL` to any URL (nothing connects to it) and `vi.mock('../src/postgres.ts')` so that `createPostgresDaemonStore` returns a fake whose `close` is a spy.
   - Interrupted use: fork `withDaemonStore(undefined, {}, () => Effect.never)`, interrupt the fiber, and assert `close` was called once.
   - Failing use: a `use` that fails also leaves `close` called once.
   - Given store: pass a fake store as `given`, interrupt the same way, and assert its `close` was never called.
   - Use `vi.mock`, not a real SQLite file: a temporary file is the filesystem, and by the 0060 §1 rule in `CLAUDE.md` that makes the test integration.
2. **Reconcile answers `[]` when the chooser refuses.**
   - Setup: delete `LINGTAI_TEST_DATABASE_URL` from `process.env` and restore it afterwards, which leaves the chooser refusing.
   - Call: `releaseForeignClaimsEffect` with `projects: [{ project: 'p' }]`, no `daemonStore`, and a memory log as the `store` that `logOf` reads.
   - Assert: it succeeds with `[]`. Today's `Effect.catch` would let it die, so the test is red before the `:564` change and green after it.
   - To keep the test from relying on how the refusal travels, assert the outcome with `Effect.exit` rather than catching inside the test.

## Ratchet

- `"packages/daemon"`'s `async` goes from 15 to 13, exactly the two `async` keywords removed from `choose.ts`. `run` stays 0, because the `Effect.runPromise` inside `processDaemonStore` is exempted by its face.
- `effect-ratchet.faces.json` gains one entry: `{ file: "packages/daemon/src/choose.ts", fn: "processDaemonStore", until: "#790", why: … }`.
  - Its place is before the first `packages/daemon/src/control.ts` entry (currently `:183`).
  - The `why` is the ticket's: `packages/daemon/integration/the-written-choice.test.ts` opens it in a spawned script.
- No face is kept for `withDaemonStore`: nothing outside the package calls it, so the promise version is removed outright.

## What only integration can check

The interrupt-and-release behaviour against a real SQLite handle, and the requirement that `node:sqlite` never loads on a Postgres choice, are covered only by `integration/the-written-choice.test.ts`. The ticket's `Done when` names that file. It needs no Postgres and runs in seconds, so run it inside the pass. Unit test 1 stands in for the release; the module-load check has no unit stand-in.
