# Design note — #1175, `loadProject`

## Where it goes

| Piece | File | New or changed |
|---|---|---|
| `sourceOf`, `sourceHashOf`, `checkDeclared` | new `packages/recipe/src/declared.ts`, re-exported from the package index | new |
| `ProjectFiles` | `packages/project/src/files.ts`, next to `diskFiles` | new |
| `recordFileRecipe` (the append) | `packages/project/src/commands.ts` | new |
| `loadProject` | new `packages/project/src/load.ts`, exported from `index.ts` | new |
| catalogue row | `packages/domain/scripts/events.ts` | changed |

`commands.ts`'s header says *"every append to `prj-{project}`"* happens there (#1174). So the append goes there and `load.ts` only calls it. Nothing else moves.

## `checkDeclared` and the private helpers in `resolve.ts`

`unknownKeys` (`resolve.ts:334`) and `retiredTier` (`resolve.ts:290`) are module-private `function`s. Export them from `resolve.ts` under the same names. Do not copy them: a second copy would drift from the one `resolveSource` uses.

Skipping `applyPreset` is safe, and this is why:
- `extends: z.string().optional()` is declared in the schema (`recipe.ts:3023`).
- The only things a preset fills are `repo.submodules` and `steps` (`presets.ts`, `Preset` type plus the one `pnpm-workspace` entry). Both have schema defaults: `submodules: z.boolean().default(false)` at `recipe.ts:3029`, and `steps: StepMap.default({…})` in the same schema.
- So a raw mapping parses without the merge, and the `extends:` row in *Done when* passes.

`checkDeclared` must copy two steps from `resolveSource` (`resolve.ts:250–256` and `local.ts`'s probe callback):
- a `runtime` that is `null` or absent becomes `{}`;
- `runtime.agent` is set to `SCHEMA_PROBE_AGENT` only where the file names none.

Without those, every recipe that names no agent is refused, which is the case the ticket most needs to pass.

`checkDeclared` does **not** look up `extends:` in `PRESETS`. *"No preset is consulted"* includes the lookup. An unknown preset name is recorded, and then `resolveLocalRecipeEffect` refuses it through `resolveSource`'s `UnknownPresetError` wrapping (`resolve.ts:240`). That is the ticket's last Edges row (*`checkDeclared` passes, the full resolve refuses*) applied to presets.

Wording and arguments:
- `RecipeInvalidError(ref, problems, where)` (`resolve.ts:55`). Pass `refFor(text, where)` (`write.ts`) as `ref` so the error names a file's `repo.base` the way the existing refusals do.
- Parse-error text: copy `resolveSource`'s `could not be parsed as YAML: …` exactly.
- A non-mapping root: `(root): expected a mapping`.
- An empty file (`parseYaml` → `null`): refuse it as `(root): expected a mapping`. `resolveSource` would let `null` reach the schema and fail on `version`. An empty file is never a declaration worth recording.

## `ProjectFiles`

```ts
export const ProjectFiles = Context.Reference<RecipeFiles>('@lingtai/project/ProjectFiles', {
  defaultValue: () => diskFiles,
})
```

This is the shape of `mirror-lock.ts:42`. Inside `loadProject`, read the file through `filesEffect(yield* ProjectFiles)` (`files.ts`). That function sends `diskFiles` straight to `readRecipeFile` and wraps any other port in `Effect.tryPromise` with `failed('read')`. A port that rejects therefore fails with the same `RecipeFailed { operation: 'read' }` the disk does, and no `Effect.run*` is added. The ratchet holds `packages/project` at `async: 0, run: 0` (`effect-ratchet.baseline.json:12`).

## The append: `recordFileRecipe(project, seen, store)`

`transitionProject` (`commands.ts:44`) is module-private, and its `answer` receives the state **read before** the append. `loadProject` has to return the state **after** it, or row 2 and row 3 hand back a `state.recipe` that is out of date or `null`.

So `recordFileRecipe` does two things:
1. Calls `transitionProject(store, project, (s) => recipeChange(s, seen), (_, appended) => appended)`.
2. Re-reads with `readProjectStateEffect(project, store)` (`state.ts:52`) and returns that state.

Re-read even when nothing was appended. That keeps the function to one path, and it is the same read the losing pass in a race needs. One extra stream read per load costs nothing beside the resolve that follows.

## `loadProject`'s order, and why

1. `readProjectStateEffect(project, store)`, **before** the file. A failed store read must fail before anything decides *no recipe yet*. This read also tells nothing new to `transitionProject`, which reads again on its own; it is here only so that failure comes first. (A plain `transitionProject` call would already fail on a bad read; keeping it explicit makes the ordering checkable in a test.)
2. The port reads `recipePath(project, home)`.
   - `null` → fail with `RecipeMissingError`. Copy the message from `local.ts`'s current text: `ref` is `options.base ?? path`, and the message names `0046 §3`.
   - a `RecipeFailed` → let it through unchanged.
3. `source = sourceOf(text)`, then `checkDeclared(source, path)`. Run it through `plainWhen(…, isRefusal)` so the throw becomes a typed failure, as `local.ts` does.
4. `recordFileRecipe(project, { sourceHash: sourceHashOf(text), source, by: 'file' }, store)`.
5. `resolveLocalRecipeEffect(project, options, readWith)` (`local.ts:71`).

### What `readWith` is

```ts
(p) => p === path ? Effect.succeed(source) : files.read(p)
```

That function reads **two** paths: the recipe, and the machine file (`machinePath(home)`), which it reads for `checkMachineConfig`'s refusals. The recipe answers with `source`, the normalised text, so the resolve sees exactly what the log recorded. The machine file goes **through the same port**, which keeps a test's `Map` port in charge of `config.yml` too. A test that leaves `config.yml` out of the `Map` gets `null`, and `checkMachineConfig(null, …)` refuses nothing.

### What it returns

`{ state, recipe }`. `recipe` is `resolveLocalRecipeEffect`'s own result, which also carries `provenance` and `ref`. Type it as that function's success type rather than narrowing it to `ResolvedRecipe`; #1176's caller will want `provenance`.

### Options

| Option | Rule |
|---|---|
| `signedIn` | required, as in `LocalRecipeOptions` |
| `read` | **remove it from `loadProject`'s options type** (`Omit<LocalRecipeOptions, 'read'> & { store?: EventStore }`). It is a file port in all but name, and 0128 §7 says no caller holds one. `resolveLocalRecipeEffect` keeps it, because `readWith` wins over it (`local.ts:73`). |
| `store` | `undefined` passes through to `readProjectEvents`, whose default is `defaultLog()` (`state.ts:30`) |

## The hash

```ts
sourceHashOf(text) = createHash('sha256').update(sourceOf(text), 'utf8').digest('hex')
```

Hash `sourceOf(text)`, never the raw text, or CRLF and LF hash differently.

`recipeChange` compares only `sourceHash` (`project.ts:247–249`). Nothing in this path computes, compares or passes on `configHash`. A test that switches `signedIn` between two loads, on a recipe that names no agent, proves that: the first load appends, and the second sees an equal hash.

## Tests

| File | What it holds |
|---|---|
| `packages/recipe/unit/declared.test.ts` | every `checkDeclared` case in *Done when* |
| `packages/project/unit/load-project.test.ts` | every `loadProject` case |

**`declared.test.ts` reads three files from disk:** `doc/examples/lingtai-recipe.yml`, `.lingtai/config.yaml`, and one `extends:` text per `PRESETS` name. Under 0060 §1, reading a repository file is filesystem access. Two ways to keep the file in the unit half:
- use `import … with { type: 'text' }` or `?raw`, if the root vitest config allows it; or
- use `readFileSync` the way other `unit/` tests already read docs. `packages/actions/unit/tamper-watch.test.ts` reads `doc/tamper-watch.md`, so that is the precedent.

Write each `extends:` text inline, built from `Object.keys(PRESETS)`.

**`load-project.test.ts`** uses:
- `createMemoryEventStore()` from `@lingtai/event-store/memory`;
- a `Map`-backed `RecipeFiles` whose `replace` pushes to a `writes` array;
- `Effect.provideService(ProjectFiles, port)`;
- `home: '/h'`, so `recipePath` is `/h/<project>/recipe.yml`.

For "unreadable", use a port whose `read` rejects, and assert `RecipeFailed` with `operation: 'read'`.

Every refusing row asserts two things:
- the stream holds no events (`store.read(projectStream(p))`);
- `writes` is empty.

Every passing row also asserts that `writes` is empty.

For the race, call `recordFileRecipe` twice on one memory store at once (`Effect.all([...], { concurrency: 2 })`) and assert one `ProjectRecipeChanged`. This is a unit-level check of 0122. Whether the memory store raises `ConcurrencyError` on a stale version is fixed by `packages/event-store/test/contract.ts`, so it does not need the integration half.
