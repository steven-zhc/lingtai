# Design note for #668: accept a short sha in `grant-fix-round --if-head`

The change belongs in `packages/conductor/src/resolve-wait.ts`. Write one small matcher and use it in **two** places. The ticket names only one of them.

## 1. One matcher, used twice

Add a module-private helper beside `resolveWaitHolding`. It takes the given value and the saved head and returns one of three answers: a match, `bad-sha`, or a mismatch.

- It lower-cases the given value.
- It checks the value against `/^[0-9a-f]{7,40}$/`.
- It matches when `head.startsWith(given)`.

The empty string is not handled here. Each caller keeps its existing `!onSha` skip, so a missing `--if-head` never reaches the pattern check.

**Place 1: the check the ticket names.** It is at `resolve-wait.ts:278`: `if (resolution.onSha && resolution.onSha !== head)`. Replace it with the helper:
- A mismatch returns `stale`, with today's detail word for word.
- `bad-sha` returns `{ ok: false, reason: 'bad-sha', detail: … }`.

The resolution carried onward is already rebuilt from the saved head at `:302` (`resolution = { _tag: 'GrantFixRound', onSha: head, ref }`). So the `WaitResolved` that gets appended records the full head with no further change.

**Place 2: the retry path. The ticket's edges do not mention it.** It is at `:203-209`. A `GrantFixRound` that was already committed (the lifecycle is `approved`, `grantRef` is set, and the `waitId` is the same) skips straight to `requestContinuation`, but only when this holds:

```ts
(!options.resolution.onSha || item.lifecycle.onSha === options.resolution.onSha)
```

`item.lifecycle.onSha` is the full head written at `:302`. Picture a person who granted with `--if-head 609d8894`, and the grant's `ContinueRequested` was left unscheduled (#465). If they rerun the same command, the exact compare fails. The run falls through to `not-blocked`, and they cannot reach the row they are owed. The CLI lets this state through on purpose: `apps/cli/src/grant-fix-round.ts:34-37` passes `approved && grantRef !== undefined` on to `resolveWait`.

So use the same prefix match in the `GrantFixRound` arm of that condition. The `Approve` arm (`: item.lifecycle.onSha === options.resolution.onSha`) stays exact. The ticket's *Out of scope* covers this.

## 2. Where `bad-sha` is checked

Check the pattern **first** in `resolveWaitHolding`, before the retry block at `:203`. Do it only when `_tag === 'GrantFixRound'` and `onSha` is non-empty.

- It is a pure check of the input, with no read of state.
- Checked first, a malformed value is always refused as `bad-sha` and never shows up as `not-blocked` or `stale`, depending on whatever state the ticket happens to be in. That is the *"the refusal says which of the two happened"* that the ticket asks for.
- It returns before every `store.append`, so *"append nothing"* holds without any special handling.

Suggested detail: `` `--if-head needs a commit SHA of at least 7 hex characters, not ${given} — nothing was resolved.` `` The phrase "nothing was resolved" matches the house wording at `:221` and `:234`.

`reason` is typed `string` (`:165`, `:372`). There is no union to extend. The CLI passes `result.reason` through to `refusal(1, …)` unchanged (`grant-fix-round.ts:49`), so the CLI side needs no code change for the new reason.

## 3. The board is unaffected by construction

`apps/board/src/app/actions.ts:170` refuses an empty `onSha`. Line `:185` sends the full sha read from the wait. A full lower-case 40-character sha passes the pattern and is a prefix of itself. Do not touch `actions.ts`.

## 4. Text

- `apps/cli/src/cli.ts:1189`: change `TAKES['grant-fix-round']` to `'--if-head takes the commit SHA, full or at least 7 characters'`. This is the sentence #621 owns. Grep the CLI tests for the old string `--if-head takes the displayed commit SHA` and update any assertion that pins it.
- `apps/cli/src/commands.ts:279-283`: `[--if-head <sha>]` already reads correctly. Leave it as it is unless a usage line comes to claim "full".
- `doc/cli.md`: `pnpm docs:cli` is `node scripts/cli-doc.ts` (`package.json:24`). Run it if it picks up the `TAKES` text or the usage. If the regenerated file shows no diff, nothing needs committing.

## 5. Tests

Put them in `packages/conductor/unit/resolve-wait.test.ts`, going through `resolveWaitHolding`. That function is exported for exactly this purpose (`:182-185`: *"the whole of `resolveWait()` cannot be unit-tested — this function underneath it can"*). Use the memory store and the fake `client.refSha` that the file already sets up.

Cover the ticket's four *Done when* cases, plus one more for the retry path: a committed `GrantFixRound` retried with a 7-character prefix of the saved head schedules the continuation and appends no second `WaitResolved`. That last one is checked by the event types in the stream: there is exactly one `WaitResolved` and the newest event is `ContinueRequested`.

All of this is unit-level. Nothing here needs `pnpm test:integration`.
