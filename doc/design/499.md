# Design note for #499: `RunSpent`, `SpentFor`, `CallId` deleted, duplicate action names refused

## Where it goes

**`RunSpent` and `SpentFor` go in `packages/domain/src/events.ts`, not in `spend.ts` or `action.ts`.** Everything they need can be imported there without a cycle:
- `RuntimeId` is declared in `events.ts` itself (`events.ts:130`).
- `JudgeWhen` is in `hold.ts:71`, which `events.ts` already imports (`events.ts:20`).
- `Usage` is already imported from `spend.ts` (`events.ts:21`).
- `WaitId` is in `action.ts:32`, and `action.ts` imports only `vocabulary.ts` (`action.ts:19`), so importing it into `events.ts` closes no loop.
- `Step` is in `vocabulary.ts:23`.

Add `RunSpent` to `EVENTS` (`events.ts:2265`). It gets no `BUMPED` entry: `SCHEMA_VER` gives every type without one version 1 (`events.ts:2405-2407`).

**The field shapes. These are the decisions the ticket leaves open:**

- `for: SpentFor` is required. Write `SpentFor` as `z.discriminatedUnion('_tag', …)` over the four variants in 0110 §9, the same convention `action.ts` uses (`action.ts:6-8`: *"`_tag` is the discriminant on each result union"*).
  - `Action`: `{ step: Step, name: z.string(), round: z.number().int().nonnegative() }`. Use non-negative, not ≥ 1: implement is round 0, and only a fix round is ≥ 1 (0110 §10, *"`Action`, `round` ≥ 1"* for a fix round only).
  - `Judge`: `{ when: JudgeWhen }`.
  - `Triage`: `{ waitId: WaitId }`.
  - `Discussion`: carries only its `_tag`.
- `runtime: RuntimeId`.
- `turns` and `durationMs` are `z.number().int()`, copied from `RunFinished` (`events.ts:625-632`).
- **`costUsd: z.number().nullable()` with no `.optional()`.** 0110 §4: *"`costUsd` is written, and `null` when not said"*. A payload with the key missing is refused.
- **`usage: Usage` is required, not `Usage.optional()` as on `RunFinished`.** 0110 §1 lists it unconditionally. A runtime that reported no tokens writes `[]`, and the *not said* lives in the optional fields of `TokenCounts` (`spend.ts:18-29`). Making it optional too would add a second spelling of *nothing*.
- No price field, and no `.default(…)` anywhere (0110 §1, §4).

**The unit test** goes in a new `packages/domain/unit/run-spent.test.ts`. It should cover:
- Each of the four `for` variants parses.
- `costUsd: null` and `usage: []` both parse.
- A missing `for`, a missing `costUsd`, and an `Action` without `round` are each refused.
- A `Triage` with no `waitId` is refused.

## `CallId`: what "never stored" rests on

The commit body should say this. `call` exists only on in-memory shapes:
- `Action` is built by `actionFromEvent` (`read-model.ts:588`, `call: null`) and by `adapters.ts:108` and `:128`, both `call: null`.
- `BudgetExhausted` is built at `read-model.ts:1042`, also `call: null`.
- **There is no `StepEnded` in `EVENTS`** (`events.ts:2265-2338`). `aStepEnded` is a test builder (`packages/domain/test/events.ts`), and `action.ts:10-11` says *"Types only — nothing calls these yet. #464 puts `StepOutcome` on the log"*.

So no stored payload carries `call`. Delete:
- `action.ts:22-27`, together with the doc comment above it.
- `action.ts:118-119`.
- The import at `wait.ts:39` and the field at `wait.ts:146`.
- The three `call: null` writers above.

`tsc`'s excess-property check then finds every test fixture: about 100 `call: null` lines under `packages/*/unit`, `packages/*/integration`, `packages/projector/test/contract.ts` and `apps/board/unit/waiting-card.test.tsx:374`. `pass-next.test.ts:18` spells it `call: null as string | null`.

**Do not touch the other `call` — `DiscussionRequested`'s.** In `packages/conductor/src/discuss.ts:446`, `:464` and the `call: CALL` in `conductor/{unit,integration}/discuss.test.ts`, `call` is a dispatch config (`{ model?, turns, wallMs }`), not a `CallId`. A blanket `sed` over `call: ` breaks discussions. Delete by type error, not by pattern.

## Duplicate action names: not refused today, so add the refusal

`actionsAt` (`packages/recipe/src/recipe.ts:2275`) asks five list-level questions. Two of them are about duplicates, and only for single plugins: a second `worktree:` (#268, `:2442`) and a second `queue:` (#269, `:2474`). Nothing compares `name`s.

Add a sixth question beside those two, built the same way:
- Keep a `Map<string, number>` of the first index of each **accepted** entry's `name`, filled where `cuts` and `takes` are pushed (`:2421-2426`), so a refused entry is not compared.
- For each later entry with the same name, `ctx.addIssue` at `path: [i]`.
- The message uses `kindRefusedAt(step, kind, name, …, REFUSED_WHEN_IT_RESOLVED)` and names the step, the name, and the entry it collides with.
- The reason is 0110 §9: *"`step`, `name` and `round` find it, which holds while an action's `name` is unique within its step"*. `task_view` already relies on the same key: `run:point:action` (`packages/projector/src/task-view.ts:554-557`).
- Update the header comment's *"five questions about the list"* (`:2258`) to six.

The test goes beside #268's, in `packages/recipe/unit/settings.test.ts:241`.

**This does not refuse the conducting machine's own recipe.** `~/.lingtai/lingtai/recipe.yml` holds 19 action names and none repeats within a step, so a restart onto this code still takes work.

Injected actions do not pass through `actionsAt`: the `--no-merge` `human:`, the default merge lane, and the default implementing agent. A declared name colliding with one of those is out of scope.

## The folds

Neither fold needs a code change, and neither should get one:
- `task_view`'s `default:` branch (`task-view.ts:549`) goes through `cardFactOf` (`read-model.ts:1354`). That is a switch with no `RunSpent` case, so it returns `null`.
- `finding_backlog` switches on four types only (`backlog.ts:131-162`).

The Done-when claim is a unit test, not a reading of the code. Add one `RunSpent` envelope to each of the streams in `packages/projector/unit/task-view-rebuild.test.ts` and `backlog-rebuild.test.ts`. Both run on SQLite `:memory:`, so they are unit. Assert that the rows match the rows without it.

`apps/board/unit/history.test.ts:38` loops over `Object.keys(EVENTS)` and requires a non-empty summary for every type. The payload fallback should satisfy it without a formatter, and a formatter is a reader, which this ticket does not add. Run that test to confirm.
