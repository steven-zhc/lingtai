# Design note: #640, a drain that waits for every pass in flight

## Read this first: #638 may not have landed

#640's only blocker in GitHub is #636, the ADR, and it is closed. #638 is the ticket that makes a look start passes without waiting for them, and it is still open with no ordering against this ticket. So when this ticket runs, the work loop may still be single-flight: `pump` keeps one promise (`work-loop.ts:336`, `let inFlight: Promise<void> | null`), and `options.pass` waits for the whole look (`work-loop.ts:494`).

**So this ticket builds the seam that #638 fills. It does not wait for #638.** Nothing in production can put two passes in flight yet. The unit test makes two by hand, and with `concurrency: 1` the behaviour stays identical because nobody calls the new hook.

## 1. The work loop holds a set (`packages/daemon/src/work-loop.ts`)

- **Put the set in its own small module, `packages/daemon/src/in-flight.ts`.** It has `track(p: Promise<void>)`, `size`, and `settled(): Promise<void>`. The loop's own test with a real log is `packages/daemon/integration/work-loop.test.ts`; `packages/daemon/unit/work-loop-stop.test.ts` drives `start()` and `stop()` with injected dependencies. A module of its own keeps the set testable by itself.
- **`settled()` loops until the set is empty. It does not await one snapshot.** If a look is already running when `stop()` is called, it may still have claimed a ticket and started its pass. That pass belongs to the drain, so `track` is never refused after `stop()`. 0030 §1 is the rule: "the boundary is the pass, not the agent". Keep the "no timeout here on purpose (0030 §6)" comment at `work-loop.ts:585–589`.
- **How a pass gets into the set: `pass` takes a second argument, `started(p: Promise<void>)`.** A look calls it for each pass it starts but does not wait for. Today's `pass` in `apps/cli/src/lingtai.ts:557` never calls it, so `concurrency: 1` does not change. #638 then only has to call `started` for each `runOnce` it leaves running.
- **The look's own promise is tracked too.** `stop()` therefore covers today's case (the look *is* the pass) and the new one (the look has returned and its passes have not).
- `busy` becomes "a look is running, or the set is non-empty". `running` and `again` keep their meaning: they are about the look, and looks stay serial (0122 §1, *"Looks stay one at a time"*). Rename the retained look promise so that `inFlight` no longer means two different things.
- **Rewrite the header sections at `work-loop.ts:35–50` and the `stop()` doc at `:303–311`** so they speak of looks and passes as 0122's *Words* paragraph defines them.

## 2. The count lives in `describeInFlight` (`packages/daemon/src/control.ts:390`)

- Every drain sentence already goes through this function with the full list from `task_view`:
  - `restart.ts:994` and `:1354`
  - `lingtai.ts:413` and `:776–777`
  - `doctor.ts:1031`
  - `draining.tsx:50`
- `held()` (`control.ts:376`) already returns every `running` or `verifying` card, so the read side was plural all along.
- **The shape:**
  - With one item, the output stays byte-for-byte `finishing lingtai#94` (the ticket's *Watch out*).
  - With two or more it becomes `finishing 2 passes: lingtai#94, lingtai#95`.
  - The wait loop re-reads the list every `sayEveryMs` (`restart.ts:1349–1351`), so "how many remain" counts down without anything else being built.
- **Pluralise only when the list has more than one item.** This applies to the sentences around the count that say "the pass in flight":
  - `lingtai.ts:776`, *"the daemon finishes the pass in flight first"*
  - `lingtai.ts:777`
  - `draining.tsx:39`, the `said` string
- **The `WALL_LIMIT` sentence stays as it is** (`restart.ts:998`, `lingtai.ts:430`). 0122 §4: *"Its sentence about what a drain may spend stays one pass's ceiling (`WALL_LIMIT`), because the passes run side by side and none starts after the drain is asked for."*

## 3. `restart.ts`: an injection point, nothing else

- `waitForTheLock` calls the module's `inFlight()` directly at `restart.ts:1351`, so a unit test cannot hand it two runs. Add `how.held?: () => Promise<string[]>`, defaulting to `inFlight`, and have `restart` pass `facts.inFlight` (`restart.ts:674`, `:692`). The test then drives `ask` (always held, then free) and `held` (two items, then one), and asserts that the repeated line says `2 passes`, and then not.
- **Leave untouched:**
  - `onSignal`, the `interrupted` returns, and the `130` exit (`restart.ts:1323–1327`, `:1345`, `:1022`)
  - the `ctrlC` text
  - `RESTART_GUARDS`
- 0121 §10 is about who owns `SIGINT`, and nothing here adds a listener or a spinner.

## 4. `status --json` gives each running pass its step (`apps/cli/src/status.ts`)

- `byState.running` already lists every running card (`statusJson`, `status.ts:426–434`). `verifying` stays its own key there, because `byState` uses the projection's state value as-is (`StatusRow.state`, `:112`).
- **What is missing is the step.** `TaskCard` has `runId` (`packages/projector/src/task-view.ts:892`) and no step. Add `runId` and `step` (and `round`) to rows whose state is `running` or `verifying`.
- **Where the step comes from:**
  - Read the run's stream, the way the board does: `eventStore.read(task.runId)`, `board.ts:924`.
  - Take the `step` and `round` of its last `StepStarted` (`packages/domain/src/events.ts:975–980`). It is null when there is none.
  - progress.ts's header defines it: *"the last `StepStarted` with no matching verdict is the step the run is at."*
  - This is one read per running card, and the running lane is bounded by the slots.
  - Put the read behind `StatusReading` so a unit test builds a report with two running rows by hand. `readStatus` already takes `reading` at `status.ts:177`.
- 0121 §5: *"adding a field does not change"* `version`.
- **The human `renderStatus` does not change.** Its `elsewhere` count already says `2 running` (`status.ts:359–366`).

## 5. The board: the column is already plural, so fix the comments and the bar

- The Working column is `ColumnId` `running` (`board.ts:77`). `railCandidates` (`board.ts:967–976`) already folds *every* running card, with no cut. A unit test on `toColumns` plus `railCandidates` with two running cards is the Done-when check.
- Correct the claim in `progress.ts`'s header: *"only the first of them is small by nature, at a card per conductor"*. It is now a card per slot, bounded by the sum of each project's `concurrency`.
- **Health dot: the count goes in the title (the tooltip), never in a new visible chip.**
  - CLAUDE.md, from #134: *"A chip is not free, and the row is the unit."*
  - Add `inFlight: string[]` to `Health` (`apps/board/src/lib/health.ts:21`), read in `readHealth` beside `readStatus`.
  - The title gains `2 passes in flight` only when there are two or more.
  - While draining, the visible count is the existing `draining` chip's `why` (§2).
- **`doctor`'s `daemon: liveness`** (`doctor.ts:1030–1040`): when the state is `up` and two or more passes are in flight, append ` — 2 passes in flight`. With zero or one, the line is unchanged.

## Not in this ticket

- **The beacon's `currentRunId` stays one column.** 0122 §4 says the beacon names every run, and that is unbuilt rather than contradicted. No production caller ever sets it: `beat()` defaults it to null (`control.ts:450`), and the only call, at `control.ts:538`, passes no run. Nothing reads it outside `packages/daemon/test/contract.ts`. Making it a set means a schema change in both stores (`sqlite.ts:53`, `postgres.ts:79`), and #640's *Want* does not ask for it.
- **`attach` takes an explicit `runId`** (`attach.ts:35`), and on a miss it already lists several logs (`attach.ts:63`). Nothing to change.

## Checks

- **Everything above can be checked with `pnpm test`:**
  - `in-flight.ts` (two tracked promises, `settled()` resolving only after both, and a `track` that arrives during `settled()`)
  - `describeInFlight` with one item and with two
  - `waitForTheLock` with `ask` and `held` injected
  - `statusJson` from a hand-built report
  - `toColumns` and `railCandidates`
- **Seeing a real daemon drain two real passes needs #638 merged and a recipe at `concurrency: 2`**, and then `pnpm test:integration`. That cannot be done inside a pass. Here, the in-flight unit test stands in for it.
