## 1. Deleting `writeSection` reaches further than `discuss.ts`

`discuss.ts:738` is the last caller in production code. But the face is also reachable from three places that will fail the build if left alone:

- `packages/conductor/src/index.ts:150` exports `writeSection`.
- `packages/conductor/src/edit-body.ts:24` re-exports it: `export { writeSection, type WriteSectionResult } from './write-section.ts'`.
- `packages/conductor/unit/edit-body.test.ts:16` imports it, and the `describe('writeSection', …)` block at `:313-371` awaits it four times.

**Decision:**

- Delete `writeSection` at `write-section.ts:46-48`.
- Drop it from both export lists, and keep `WriteSectionResult` in both.
- In `edit-body.test.ts`, change the `writeSection` block to `Effect.runPromise(writeSectionEffect(...))`. Its assertions do not change.

The ticket's *Nothing else changes* list does not include `edit-body.test.ts`. Treat that file as one more allowed edit, under the same rule as `judge.test.ts`: only the call changes.

`apps/board/src/app/actions.ts:666` mentions `writeSection` only in a comment, so it is not a caller. Change the name there to `writeSectionEffect`, or leave it. No other app imports the face.

Also remove the faces-file entry at `effect-ratchet.faces.json:308-313`. Its `why` reads *"`discuss.ts` awaits it until CONDUCT8-7"*, and this ticket is that step.

## 2. Two of the Effects the ticket yields do not exist yet

Two of the Effects already exist:

- `currentRecipeEffect` at `projects.ts:201`.
- `closeHoldingEffect` at `close.ts:157`.

`runnableNowEffect` and `selectRunnableEffect` do not exist anywhere. They are this ticket's bodies, and each old name becomes a one-run face over its Effect.

Rule for the conversion: **move the bodies, not the answers.** `await` becomes `yield*` in the same order. Anything that `runnableNow` (`discover.ts:424`) or `selectRunnable` (`queue.ts:71`) catches today, it still catches. Anything it rejects with today, it still fails with, in the error channel and with the same message.

`readTasks` stays a promise from `@lingtai/projector`, as the ticket's *Out of scope* says. Lift it with `Effect.tryPromise`, not `Effect.promise`. `Effect.promise` would turn an unreadable `task_view` into a defect, and that would breach the edge *fails as today, with its reason*.

`schedule.ts:228-230` and `conduct.ts:2667` both wrap the old face in `Effect.promise(() => runnableNow(...))`. That turns any rejection into a defect. Once they `yield* runnableNowEffect(...)`, the same rejection is a typed failure. The pass already ends on either kind of cause, so this is not a change in behaviour. But keep both call sites from catching that failure: an empty queue must never stand in for a failed read.

## 3. How the faces counter treats `refreshRates`

The ratchet counts a function as a face only if it has exactly one counted run in its body. Its refusal reads *"has no counted run in its …"* (`effect-ratchet.test.ts:267`).

The ticket splits the function in two:

- `refreshRates`, at `rate-snapshot.ts:118-123`, keeps the `inflight ??=` dedupe and calls `refreshOnce(ports)`. It contains no `Effect.run*`, so it is neither counted nor listed.
- `refreshOnce` is the only listed face.

Keep `inflight` as the promise that `refreshRates` returns, so that `ratesSettled` (`:126`) still awaits it. Do not let `inflight` hold the inner `Effect.runPromise` from somewhere else. The `.finally(() => { inflight = null })` stays on the outer promise.
