# #352: design note

## Where it goes

All of the branching happens in `apps/cli/src/run.ts`. The pass doesn't change. `runOnce` and `runQueue` already accept `remote` (`conduct.ts:377`, `schedule.ts:76`). `remote` reaches `repo.provision` and nothing else (`conduct.ts:1684`). That is enough, because `ensureMirror` clones and then sets the mirror's `origin` to that remote (`packages/repo/src/worktree.ts:102,111-113`). `integrate` pushes from the mirror, so the landing goes to the same remote without anyone threading it through. `owner` is only read where `remote` is absent (`worktree.ts:102`; `integrate.ts:73` declares it and never reads it). So a no-owner pass that always passes `remote` never builds a `github.com/null/...` URL.

## The order inside `run()`

The lock stays the first statement (`run.ts:221`). Today the App check runs before `loadProject` (`run.ts:223-245`). Move it below `loadProject` and branch on `project.owner`:

- **`owner` set:** keep today's App refusal, word for word, and today's `createGitHubClient`, `token`, `ticketsFor` and `passClientOf`. Keep `remote` absent, as it is today. Don't start passing `remoteOf(recipe)` for GitHub projects, because "a GitHub project behaves exactly as today" covers the clone URL too.
- **`owner === null`:** don't check for the App, don't construct a client, and leave `token` undefined (not `() => undefined`). With no token, `git()` sets no `GIT_CONFIG_*` (`packages/repo/src/git.ts:44-50`), so git uses this machine's own credentials. That is the ticket's "the user's own key".

The one visible change: `lingtai run no-such-project` with no App configured now says "no project named …" instead of "no GitHub App configured". That's correct, so don't keep the old order to preserve it.

The recipe is resolved inside `work` (`run.ts:302`), which is after the lock. Keep it there. `currentRecipe` ignores its client (`projects.ts:139`: *"`client` is unused"*), so the no-owner branch passes `undefined`.

## Two refusals the ticket doesn't list, and both are needed

Both go right after `resolved`, before `statedBeforeDispatch` prints anything:

1. **No `repo.remote`.** `remoteOf(recipe)` is `null` when the recipe names none (`settings.ts:352`), and the pass would then fall back to the GitHub URL built from a null owner. Refuse by name, e.g. `<project> has no owner and its recipe names no repo.remote — re-run lingtai add --local`.
2. **`source.tickets` isn't `db`.** `ticketsFor` returns its `client` argument unchanged for `github` or an absent field (`ticket-store.ts:239`), and here there is no client. #394's local registration writes `repo.base` and `repo.remote` and **does not write `source.tickets`** (`apps/cli/src/first-project.ts:400-408`). So a freshly registered local project reaches this refusal every time. That's intended, not a bug: say what to write (`source.tickets: db`). Don't silently default a no-owner project to `db`. That decision belongs to #394's registration and the recipe.

## The client a no-owner pass gets

`runOnce` takes a `PassClient`: `Tickets & RefChannel & { owner: string; repo: string }` (`conduct.ts:331`).

- **Tickets** come from `ticketsFor` (`dbTickets`).
- **`owner`:** widen `PassClient.owner` to `string | null` rather than invent a string. It's read in three places:
  - `baseDivergence`'s slug (`conduct.ts:569`). This only appears in a "re-register" sentence, so give it `repo` alone when `owner` is null.
  - `provision` and `integrate` (`conduct.ts:1674,1969`). Pass `owner ?? ''` there, with a one-line comment saying the remote is always set when `owner` is null. Don't widen `ProvisionOptions` or `IntegrateOptions` in `@lingtai/repo` for this.
- **The refs are the decision.** `tellGitHubAbout` needs `IssueChannel & RefChannel`, and *"a channel that silently cannot delete is a recipe that resolved an effect nothing ran, which is `#61`"* (`tell.ts:351-353`). Use **git against the remote, not a skip.** Nothing else will ever clean these refs up for a no-owner project: `convergeIssues` asks GitHub, and the daemon skips owner-less projects entirely (`apps/cli/src/conduct.ts:284`). Skipping would leave `agent/*` refs piling up with nothing converging them.

  Build a small `RefChannel` over the remote URL:
  - `matchingRefs(prefix)`: `git ls-remote --heads <remote>`, keep the lines whose ref starts with `refs/<prefix>`, and return them without `refs/` (the contract at `tell.ts:59-64`).
  - `deleteRef(ref)`: `git push <remote> --delete refs/<ref>`.
  - Both run with no token.

  Put it in `packages/conductor` beside `ticket-store.ts`, using `git` from `@lingtai/repo` (`packages/repo/src/index.ts`). It satisfies `RefChannel` structurally. A failure throws, and `sweepRefs` already turns a throw into `IssueUpdateFailed` with `change: 'refs'` and the names it had already deleted (`tell.ts:262-270`). That covers the "with a reason" requirement.

Assemble the result in one function, e.g. `ownerlessPassClient(project, remote, tickets, refs)`. Don't use `passClientOf`: it spreads a `GitHubClient` (`ticket-store.ts:296`), and there isn't one here.

## The seam the unit tests need

`run()` has no seam today. `run-before-dispatch.test.ts`'s header says so: `hasGitHubApp`, `loadProject` and `createGitHubClient` all reach outside the process. Add a third parameter, `run(options, log, world = liveRunWorld())`, following `apps/cli/src/world.ts`'s `Live` pattern. It should carry exactly what the tests must not reach:

- `hasGitHubApp`, `loadProject`, `createGitHubClient`, `currentRecipe`, `ticketsFor`
- the file reads for the hook and the prompt
- `runOnce` / `runQueue` / `tallyPass`
- the three layers: `ConductorLockLive(...)`, `ProjectorLive(log)` and `PortsLive`

**The world supplies the layers. It doesn't decide their order.** `Effect.provide(world.lock)` stays exactly where `ConductorLockLive` is provided at `run.ts:407`, so #93's lock-first guarantee is still a fact about `run.ts`'s own code.

Test 1 records what the fake `runQueue` was handed and asserts three things:
- `remote` is set
- `token` is `undefined`
- the ticket verbs are the fake db tickets'

Test 2 asserts nothing was constructed by giving the world a `createGitHubClient` that throws. The "GitHub project still refuses" test uses the same world with an owner and `hasGitHubApp: () => false`, and asserts the exact current sentence.

## What only the integration half can check

The landing onto a real remote with no token is already `packages/repo/integration/integrate.test.ts`'s claim: it passes `remote:` pointing at a local repository. The new thing that needs a real git binary is the git `RefChannel`. Add one `integration/` test for it in `packages/conductor/integration/`, against a bare repository in a temp dir: push `agent/24-attempt-1` and `agent/240-attempt-1`, then sweep 24 and check that 240 is still there (`tell.ts:209-214` explains why that prefix filter matters).

Nothing checks that before the merge. In the unit half, the test-1 assertions on `remote` and `token` stand in for it. Per CLAUDE.md, don't run `pnpm test:integration`.
