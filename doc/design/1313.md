## Design note: #1313 — an agent resolves a PR's conflicting sync and merge back

#1312 has landed in this worktree. `packages/conductor/src/pr-sync.ts` holds the sync, the build and the merge back. `BranchSynced.how` and `PrMergedBack.how` already have `'resolved'` (`packages/domain/src/events.ts:2622-2638`). So this ticket fills in an end that is already named. Below are the decisions the ticket does not settle, and three places where the code has moved since the ticket was written.

### 1. Where each piece lives

- **`packages/repo/src/pr-sync.ts`: a new `standMergeUp`.**
  - Do not reuse `mergeInWorktree`. That function aborts a conflict (`git merge --abort`) and removes its worktree on every ending (`pr-sync.ts:62-98`, *"A conflict is aborted before it is answered; the worktree is released on every ending"*).
  - `standMergeUp` cuts the same detached `pr-sync-<n>-<epoch>` / `pr-back-<n>-<epoch>` worktree under `mirrorWrite`. It runs `merge --no-commit --no-ff <commit>` and answers `{ cwd, paths }` with the markers left in place.
  - It has no `acquireRelease`. `sweepPrWorktrees` already takes these prefixes (`PR_WORKTREE_PREFIXES`, `:48`) and is the only thing that removes them.
- **`packages/conductor/src/pr-conflict-brief.ts`: `prConflictBrief`, pure.** It takes the paths, the ours and theirs lists, the round, the bound and the last refusal, and returns `RecordPart[]`. The review's brief goes here too (see §6).
- **`packages/conductor/src/pr-resolve.ts`: the round loop (`resolveRounds`).** The sync step and the merge back both call it. It answers one of:
  - `{ kind: 'resolved', sha }`
  - `{ kind: 'spent', end }`
  - `{ kind: 'locked', sentence }`
  - `{ kind: 'unknown', why }`
- **`packages/domain/src/pr.ts`: the fold and the arithmetic.**
  - `SyncRoundStarted` folds into a new `PrState.rounds`: an array of `{ merging, commit, round }`.
  - The `PrInProgress` case must not reset it. Today it spreads `...state` and resets only `steps` and `wait` (`pr.ts:121-135`), so a new field survives as long as it stays out of that literal. That survival is the *"never refunded by a restart"* rule (0108 §8), held in the reducer.
  - `conflictRoundsLeft(state, merging, commit, bound, grants)` is the pure function. `grants` is `[]` until #1314 adds the event, so do not invent that event here.

### 2. The ports `PrPorts` needs (`packages/conductor/src/pr.ts:57`)

Four new members, wired in `apps/cli/src/pr-ports.ts`:

- `standMerge`.
- `dispatch(project, { runtime, model, cwd, prompt, limits, sandboxed })`: one agent run, answering what `discuss.ts`'s `ask` answers (turns, durationMs, costUsd, usage, text, failure).
- `runtimeVersion`.
- `locks(project)`: returns `Lock[]`. Build it from the reads `packages/daemon/src/guard.ts:76-135` already makes. Pass `accounts` for the runtimes at `implement` and `review`. `locksOn` makes `accounts` required for exactly this reason (`locks.ts:51-54`).

**`bounded` (`pr.ts`, *"The ports with every **read** bounded"*) must not wrap `dispatch`.** It times reads out at `READ_MS = 60_000`. A round is not a read, and its limit is `run.wall`.

### 3. Hooked or unhooked: use `unhookedSettings`

The ticket says *"unhooked settings … as `fixRound` uses them"*. That stopped being true today: `4f4508538` (#1346) changed `fixRound` to `host.wire` per round.

Use `unhookedSettings` anyway, the call the cold reviewer gets (`packages/actions/src/agent-action.ts:1688`; live at `packages/conductor/src/live.ts:72`). The hook socket appends `RunTouchedFile`, `RunAwaitingInput` and similar events, and `STREAMS` allows those on `pass-` only (`packages/domain/scripts/events.ts:471-473`). A PR round has no pass stream.

The run's limits are the runtime's own flags (`--max-turns`, wall, `--max-budget-usd`) and none of the hook's. Say so in a comment.

### 4. The sync: `resolved` is the sync step's record, not the build's

Today `BranchSynced` records step `sync` only for `already` and records `build` for everything else (`packages/domain/src/pr.ts:157-163` and `syncedTransition`, `:317-326`).

**Change both so `resolved` records `sync`, like `already`.** Then:

- The sync step resolves, builds and reviews inside its own run, and answers `done` with a `record` that appends `BranchSynced { how: 'resolved', head: <resolution> }` and moves `targetRef(n)` to the resolution.
- `buildStep` then finds `synced.headSha === target` and passes without building again (`pr-sync.ts:160-161`, *"Nothing was merged: the sync's commit is the target, and it was built when it was made"*). That comment becomes true of a resolution too.

If you leave the mapping alone, `resolved` records `build` while `sync` stays unrecorded, and `walkPr` runs the sync again for ever.

One consequence to keep: if a pr-fix landing moves `target` during a round, `walkPr` drops the answer (`pr.ts`, *"a newer pass … moved the target meanwhile, so nothing is recorded"*). The round stays spent, and the next walk counts on from it for the same `main` commit. That is correct, so do not "fix" it.

The answer types change as follows:

- `wait('sync-conflict', …)` at `pr-sync.ts:126-131` becomes the call to `resolveRounds`.
- `'sync-locked'` joins `PrWaitReason` (`events.ts:2558`).
- **A sync-locked wait is not resumed automatically when the lock lifts.** `servePendingPrs` serves only `requested`, `in-progress` and `mergeBackOwed`. Leaving the wait is #1314's retry, and the ticket chose a wait.

### 5. The merge back: two lane turns, and the conductor writes the subject

Today the whole of `mergePrBack` is one turn of `branch.personal`'s lane, and the conflict is found inside it (`pr-sync.ts:283-295`, `:387-392`). The ticket forbids holding that lane for an agent's run. So:

- **Turn 1** is today's turn, except that `conflict` becomes a new outcome `{ kind: 'conflict', personalSha, paths }`. That outcome leaves the turn without recording anything.
- **The rounds** run outside any lane, still under `permitOf(project)`, so the sweep cannot pull the worktree away.
- **Turn 2**:
  1. Re-read the PR. Re-fetch `branch.personal`.
  2. If it moved, `ports.merge` the moved branch into the resolution, with no agent, and build that. A conflict here costs a round, so leave the turn and go back to the loop.
  3. Push once with today's push and look code (`:310-328`). Then `recordPrMergedBack { how: 'resolved' }`.

**The conductor writes the resolution commit's subject.** Before the build, run `git commit --amend --only -m "<backSubject>"` in the round's worktree. That changes neither the tree nor the parents.

Without it, the lost-record search finds nothing. That search greps `branch.personal` for merges under `backSubject` whose second parent is `prHead` (`:249-270`), and the agent's own message would not match. The amend keeps the resolution findable even when §5's moved-branch merge sits on top of it. Amend the sync's resolution the same way, to `Merge <main> at <sha7> into <prBranch>`, so both are uniform.

The same `--amend` is then the last write to the worktree. Read the parents check (`rev-parse HEAD^1 HEAD^2` equals `[start, commit]`, and no `MERGE_HEAD`) **before** the amend.

**`mergeBackOwed` must treat `why: 'locked'` as owed again**, as it already treats `unknown` (`:205-210`). Otherwise a merge back refused under a pause is never tried again for that head. `PrMergeBackFailed.why` gains `'locked'`. `mergeBackFailedTransition` already appends only once per head and `why`, so a long pause does not spam the stream.

### 6. Review: a dispatch, not `makeAgentAction`

`makeAgentAction` is an `ActionPort` and needs a pass. Instead:

1. Dispatch the runtime of the recipe's `review` entry.
2. Brief it with `prConflictBrief`'s review form: the ours and theirs lists plus `git show --remerge-diff <DIFF_FLAGS> <resolution>`, clipped at `runtime.budget.diff` with `clippedAt`.
3. Parse the answer with the exported `parseFindings`, and judge it with `verdictFor` (`agent-action.ts:878`, `:921`).

An unreadable answer is a refusal and buys the next round with that sentence. It is never a pass.

`StepEnded` must carry what `findingsRaisedOf` reads: `outcome.step: 'review'` and one action with `yields: 'verdict'` and `result: { _tag: 'Completed', assessment }` (`packages/domain/src/read-model.ts:183-199`).

`StepEnded` and `RunPrompted` are `['pass-']` in `STREAMS` (`scripts/events.ts:470`, `:488`), so both rows gain `'pr-'` along with `RunSpent`'s. The ticket names only `RunSpent`, and the generator throws on the others.

**Do not touch `finding_backlog`.** Its reduce skips a run with no `RunStarted` link (`packages/projector/src/backlog.ts:238-241`, *"A pass on a run nothing started names no ticket"*). So contrary to the ticket's Out of scope, a rebuild does *not* pick these minors up yet. #1315 makes that true.

### 7. Where the rounds end up: a structured field, not prose

Add `conflict: ConflictEnd.nullable().default(null)` to both `PrWaiting` and `PrMergeBackFailed`. `ConflictEnd` holds:

- `merging`, `commit`, `paths`
- `ours[]` (number, title, mergeCommit)
- `theirs[]` (sha, author, subject)
- `roundsUsed`
- `last: { step, said }`

`detail` stays the person's sentence. #1314 reads the field. Encoding all this into `detail` would make #1314 parse prose.

### 8. Order inside one round

1. `readPr`, then `conflictRoundsLeft`. If none are left, answer `spent`.
2. `ports.locks`. If any lock is set, answer `locked`, with no event.
3. Append `SyncRoundStarted`.
4. `standMerge`, then the brief reads, then `recordPrompt` followed by `dispatch` followed by `RunSpent` (`purpose: 'resolve'`).
5. Check the parents.
6. Amend the subject.
7. Build.
8. Lock check again. A pause in the middle of a round must not buy the review. Answer `locked` here too; the round is already spent.
9. `recordPrompt` followed by `dispatch` followed by `RunSpent` (`purpose: 'review'`) and `StepEnded`.

Two more rules:

- A `readPr` that fails, fails the effect. `orUnknown` turns that into `sync-unknown` (`pr-sync.ts:27-35`), and no round starts.
- `recordPrompt` returns a Promise and never rejects (`record-prompt.ts:76-80`). Call it with `Effect.promise`, as `discuss.ts:586` does. That adds no `async` and no `Effect.run*` to the ratchet.

Run ids:
- `pr-<project>-<n>:resolve:<merging>:<sha7>:<round>`
- `pr-<project>-<n>:review:<merging>:<sha7>:<round>`

### 9. Lifting `landedOnBaseRead`

It is a closure over the pass's `gitAskedEffect` (`conduct.ts:4038`). Lift it into a module-level function of `(git: (args) => Effect<Result<string, …>>, moved)`. `conduct.ts` passes `gitAskedEffect` at both call sites (`:4544`, `:5344`). The PR passes a `ports.git` adapter whose cwd is the round's worktree. The #1121 tests stay unchanged.

### 10. What can be checked before the merge

Everything in *Done when* is unit-level: fake `PrPorts` that answer by exit code, as `packages/conductor/unit/pr-sync.test.ts` does, plus a fake `dispatch`. `standMergeUp` itself touches the git binary, so it is integration and cannot run inside the pass. The unit stand-in is the claim that the sync step leaves the worktree to the sweep and never calls `merge --abort`. Assert that against the fake.

For the `spend` row:
- `packages/projector` assigns the project with `parsePrStream` (already exported from domain, used at `pr.ts:17`), at `spend.ts:236`.
- `purpose` stays `d.for._tag`.
- `step`, `action` and `round` stay null for `Pr`, so the `Action`-only lines at `:238-240` are unchanged.
