# #1225: a GitHub call made inside an attempt waits out the `acct-github` lock and is made again

#1213 has landed (`5f0edfbd`, `36382e10`, `dc10e49e`), so the port this ticket extends is in the tree.

## 1. The port answers with an Effect, and the client does the sleeping

Today the port returns nothing:

`onRateLimited?: (failed: GitHubFailed) => Effect.Effect<void, never>` (`packages/github/src/client.ts:441`)

`locking` calls it with `Effect.tapError`, so the error always passes through (`client.ts:563-567`). Change the return type to an answer:

```ts
export type RateLimitAnswer = { kind: 'fail' } | { kind: 'retry'; after: Duration.Duration }
onRateLimited?: (failed: GitHubFailed) => Effect.Effect<RateLimitAnswer, never>
```

`locking` becomes a loop:

1. Run `eff`.
2. If the error is a rate limit (`isRateLimited`, `client.ts:550`), ask the port.
3. On `retry`, `Effect.sleep(after)` and then run `eff` again.
4. On `fail`, or when there is no port, fail with the original `GitHubFailed`, as today.

Write it as a recursive `Effect.catchIf` / `Effect.suspend` and not a `Schedule`: the delay comes from the log on each failure, not from a policy fixed in advance.

The one-minute floor goes in the client: `Duration.max(after, Duration.minutes(1))`, applied in `locking`. Every retrying port then gets the ticket's *Watch out* guard, and a port written later cannot sleep zero. Put that constant beside `isRateLimited` and give it a comment quoting `doc/design/platform-errors.md` §1 ("may result in the banning of your integration").

`token: locking(token)` (`client.ts:635`) goes through the same loop. It is the installation-token request that git's push and fetch use, a REST call made inside the attempt, and #1213 already locks on it for that reason (the comment at `client.ts:633-634`). Only the pass's derived form waits; the look's token keeps failing.

## 2. `githubLimitPort` answers the `until` it read, and has a waiting variant

`githubLimitPort` (`packages/conductor/src/account.ts:136-160`) already sees both `until`s:

- `at.until` when it appends;
- `state.limit!.until` in the `already` branch (`:156`).

Return them instead of dropping them, and add a parameter that selects the answer:

```ts
githubLimitPort(store, log, { wait: boolean, now? })
```

- `wait: false` (the look) locks exactly as today and answers `{ kind: 'fail' }`.
- `wait: true` (the pass) locks and answers `{ kind: 'retry', after: until − now }`. The client then raises that to at least one minute.

Use `Clock.currentTimeMillis` for `now` rather than `new Date()`, so a `TestClock` test controls both how long the wait is computed to be and how long the sleep lasts. The existing `now: () => Date` parameter is only for `githubLimitUntil`, and can stay.

**A store failure answers `fail`, even under `wait: true`.** The existing `Effect.catch` at `:160` says *"a lock that could not be written never changes the error the call fails with"* (doc at `client.ts:437-440`). Without a lock on the log, there is no `until` to wait for, and nothing on the banner tells a person why the pass is stopped. Keep that contract and say so in the comment.

## 3. The derived form: `withRateLimited(port)` on `GitHub` and `GitHubClient`

Inside `makeGitHub`, everything after the `token` is resolved is a function of `(installation, token, port)`: `send`, `idOf`, `asLinkCall`, `listLinked`, and the `github` object literal at `client.ts:629`. Move that into a local `build(port)`:

- `makeGitHub` returns `build(options.onRateLimited)`.
- The returned `GitHub` gains `withRateLimited(port): GitHub = build(port)`.

`withRateLimited` reuses the same `token` Effect and its cache (`installationToken`, `packages/github/src/app.ts:332-351`, whose `Ref`/`Semaphore` live in the closure), and the same `installation`. It makes no lookup and mints no token. `makeGitHubClient` (`client.ts:806`) adds `withRateLimited: (port) => toClient(github.withRateLimited(port))`, so pull the object literal at `:809-835` into a `toClient(github)` helper.

Under `gh` auth, `token` is `ghTokenEffect` per call (`client.ts:570-573`) and there is no installation, so the derived form changes nothing there.

The one-installation-lookup test in *Done when* builds through `createGitHubClient`. It must:

- pass **no** `installation` option, so that the lookup actually happens;
- count fetches to `/repos/o/r/installation` (`installationForRepoEffect`);
- count `/access_tokens` mints too, which should also be one.

## 4. Wiring: the look keeps `client`, the pass gets the derived client, and `ticketsFor` is handed the derived client

In `apps/cli/src/conduct.ts:288-316`, keep building `client` with `githubLimitPort(store, options.log, { wait: false })`. It is used for `defaultBranch` (`:295`) and `currentRecipe` (`:297`). Then:

```ts
const passClient = client.withRateLimited(githubLimitPort(store, options.log, { wait: true }))
```

Pass `passClient` to **all three**:

- `world.ticketsFor(project, recipe, passClient)` (`:305`);
- `ticketedClientOf(passClient, tickets)` (`:311`);
- `token: () => passClient.token()` (`:316`).

**This is the trap in the wiring.** For a `github` source, `ticketsForEffect` returns the very client it was given (`packages/conductor/src/ticket-store.ts:274`). `ticketedClientOf` then checks `tickets === client` (`:334`) and otherwise *overwrites* the nine ticket verbs with `tickets`' own (`:335-346`). If `ticketsFor` is handed the look's `client` and `ticketedClientOf` is handed `passClient`, then `comment`, `setLabels` and `closeIssue` (the calls this ticket is about) go back to the failing client. The refs and the token would wait, and the ticket writes would not. For `github`, `ticketsFor` makes no GitHub call (it returns at `:274`), so handing it `passClient` during the look costs nothing.

`apps/cli/src/run.ts` does the same at `:396-402` (build), `:532` (`ticketsFor`), `:538` (`ticketedClientOf`) and `:544` (`token`). `lingtai run` is a conductor holding the same lock (#93) and runs the same pass, so it gets the same treatment, and its `currentRecipe` at `:467` keeps the failing client. The ticket names only `conduct.ts`; this is the design decision that extends it to `run.ts`.

Unchanged:

- `wantsMany` at `conduct.ts:753-758` is a look, so it keeps `{ wait: false }`.
- Clients with no port (the board, the other CLI commands) neither lock nor wait, because `locking` treats an absent port as `fail`.

## 5. Interruption reaches the Effect face only

The pass calls the promise face: `runGitHub` is `Effect.runPromise(effect, { signal })` (`packages/github/src/app.ts:143-148`), a fresh fiber for each call. Interrupting the pass's fiber therefore does not interrupt a sleep running inside a promise-face call. What ends it in practice is the process exiting (a second Ctrl+C, `--timeout`), which is the ticket's *the process dies mid-wait* edge: the next conductor cleans up the claim.

The Done-when interruption test is therefore written against `makeGitHub(...)`'s Effect face:

1. fork the call;
2. `TestClock.adjust` part of the way into the wait;
3. `Fiber.interrupt`;
4. assert exactly one non-token request was made.

Do not thread a signal through `TicketStore` to make the promise face interruptible. That is #790's migration, not this ticket.

## 6. Tests

All of these are unit tests: a stubbed `fetch` and `createMemoryEventStore`, as in `packages/conductor/unit/github-limit.test.ts:24-36`. Put them beside that file, because they need `githubLimitPort`, and `@lingtai/github` cannot import the conductor.

- **Retry after a 429, `retry-after: 60`, then 200.** Use the Effect face under `TestClock` (in effect 4 it comes from `effect/testing`; the package is on `^4.1.2`, `packages/github/package.json:13`). Fork the call:
  - at 59 s of test time there has been one request;
  - at 60 s there have been two;
  - the call returns the 200's data;
  - there is one `AccountLimitReached` on `acct-github`.
- **A standing lock with a past `until`.** Seed one, then answer 429, 200. At 59 s there is still one request; at 60 s there are two. This exercises the `already` branch together with the client's minimum wait.
- **Interruption**, as in §5.
- **The look's client still fails.** Same token and installation: the look's client rejects on the first rate limit, and `client.withRateLimited(...)` waits. Assert the lookup and mint counts from §3.
- **The port returns `fail` with `wait: true`.** A store whose `append` rejects: the call fails with the original `GitHubFailed` and no second request is made. This pins §2's decision.

None of this needs `pnpm test:integration`. The real wiring in `conduct.ts` and `run.ts` (that `ticketsFor` gets `passClient`) has no unit test today. A unit check on `ticketedClientOf(passClient, passClient) === passClient` would record why the order matters. Otherwise, leave a comment at both sites naming the trap in §4.

## 7. The ratchet

The loop, the port and `withRateLimited` are all Effects, and the promise face gains only an arrow into `runGitHub`, which already exists. No new `async` function and no new `Effect.run*` should appear. If `packages/domain/unit/effect-ratchet.test.ts` goes red, the change is wrong, not the baseline.

No ADR changes: 0126 §2 is what this builds. Update the comment at `client.ts:437-440`: the port is no longer "told … before it fails as it always did". It now answers whether the call fails, and only the pass's derived client waits.
