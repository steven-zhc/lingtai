# #1347: design note

The ticket gives most of the shape. Two decisions are not in it, and both change what the tests have to prove. A few smaller calls follow them.

## 1. The ancestry test must decide on the first try, before `tries === 0`

The failing case already partly recovers itself today. Here is the path:

- On the first try, `looked.success !== merged.sha` sends the code to `if (tries === 0) return { kind: 'lost' }` (`packages/conductor/src/pr-sync.ts:327`).
- `turn` then runs `attempt(1)` (`pr-sync.ts:355`).
- `attempt(1)` fetches `branch.personal` again (`:243`) and runs `log --merges --grep <backSubject> -n 200` over it (`:248-262`). That search finds the merge the first try pushed, and returns `{ kind: 'merged', mergeCommit: sha }` (`:267`).

So the case the ticket describes is recorded wrongly **only on the second try**. That is the second push also losing its acknowledgement and being built on, or the merge falling outside the 200-commit window.

This matters for the tests. If the test lets the fake's `log` return the merge, it goes green without the fix. Build it this way:

- **Put the ancestry look right after the equality test and before the `tries` branch.** Then a descendant tip is recorded on the first try. Nothing does a second `fetchInto`, `log`, `ports.merge` or `ports.build`.
- **The "descendant → `PrMergedBack`" test asserts the decision was made in one attempt.** `ports.merge` and `ports.build` are each called once. Also add one case at `tries === 1`, where the fake `log` never finds the merge. That case is the one that records `lost-push` today and must record `PrMergedBack` after the fix.

## 2. Reuse the existing fetched ref, and handle a failure inside the look

The ancestry check needs the remote tip in the mirror. Use `fetchInto(ports, project, [[`refs/heads/${branch}`, fetchedRef(n, 'personal')]])`, the same call `attempt` begins with (`pr-sync.ts:243`). Then ask `isAncestor(ports, project, merged.sha, fetchedRef(n, 'personal'))` (`pr-sync.ts:45-53`).

- **No new ref.** `fetchedRef` takes only `'main' | 'personal'` (`pr-git.ts:8`). `attempt` already ends with `Effect.ensuring(dropRef(ports, project, fetchedRef(n, 'personal')))` (`pr-sync.ts:329`), so the existing ref is cleaned up as before. The ticket's out-of-scope note about a ref of its own therefore does not arise.
- **Fetch the branch, not the sha.** Fetching a bare sha needs server support. The fetched ref may already be ahead of the tip `ls-remote` returned. That is harmless: if the merge is an ancestor of a later tip, the push still landed.
- **The merge commit is already local.** `ports.merge` made it in the mirror, so `--is-ancestor` needs no second object.
- **Wrap the fetch and the check together in `Effect.result`,** as the `remoteSha` look is wrapped (`pr-sync.ts:319-323`). A failure in either one returns `{ kind: 'failed', why: 'unknown', detail }`, and the detail says *the push may have landed*. If they are not wrapped, the error escapes to `turn`'s catch (`pr-sync.ts:357-358`). That catch records `unknown` too, but its sentence is the general *"a read failed …"*, which never mentions the push.
- **`PermissionDenied` does not need separate handling.** `fetchInto` and `isAncestor` are `Effect<_, Error>` (`pr-git.ts:36-41`, `pr-sync.ts:45`), and `mergePrBack` is not wrapped in `orUnknown`.

## 3. A push that threw: its message goes in `stderr`

Today a thrown push becomes `{ code: null, stdout: asError(pushed.failure).message }` (`pr-sync.ts:313-315`). `gitSaid` reads only `code`, so `lost-push`'s detail, `gitSaid(push, answer)` (`:328`), says *"answered nothing"* and drops the message. Once `PrGitAnswer` has a `stderr` field, put the message there instead. That is the one line where the ticket's stderr rule applies to an answer the live adapter never produced.

## 4. Smaller calls

- **The `stderr` field is required, not optional.** `readonly stderr: string` on `PrGitAnswer` (`packages/conductor/src/pr.ts:52-55`). With a required field, `tsc` points to every fake that has to fill it. The fakes are in `packages/conductor/unit/pr-*.test.ts`, mainly `pr-sync.test.ts`, `pr-serve.test.ts`, `pr-push-open.test.ts` and `pr-sweep.test.ts`. An optional field would let a fake leave it out without any error.
- **The live adapter.** `answered` (`apps/cli/src/pr-ports.ts:80-88`) fills `stderr: err.stderr ?? ''` from `RepoFailed.stderr` (`packages/repo/src/git.ts:94`), and `''` on success. stderr is already English: `env['LC_ALL'] = 'C'` (`git.ts:68-69`, *"English stderr, so `classify`'s git rows … read git's words (#1029)"*).
- **Token leak.** None. The token travels as an `http.…extraheader` in the environment (`git.ts:58-62`), never in a URL, so git's stderr cannot echo it.
- **`gitSaid` (`pr-git.ts:16-17`).** Take the first non-empty line of `stderr`, trim it, and cut it to 300 characters. Append `: <line>` after `answered exit N` or `answered nothing`. Empty stderr leaves the sentence exactly as it is today, so a test that checks a whole sentence for a silent fake stays green.
- **Callers.** `gitSaid` is the only place that turns an answer into words. Its callers are `pr-git.ts`, `pr-sync.ts` and `pr.ts`, so changing it covers `fetchInto`, `remoteSha`, `resolve`, `isAncestor`, the push and the `pr.ts` callers. None of them needs its own edit.
- **`cat-file -e` (`pr-sync.ts:271-274`).** Keep the ticket's rule:
  - exit 1 or 128 with empty stderr: `` `<sha>` is not in the mirror ``;
  - otherwise: `` `<sha>` could not be read in the mirror (<gitSaid>) ``.

  With `^{commit}`, a real git may answer a missing object with exit 128 and a `fatal: Not a valid object name …` line. That then reads as git's words rather than *not in the mirror*. Either way it is `why: 'unknown'` and stays owed, so the outcome is the same. Only the wording differs, and git's own line is the more accurate one. Do not match on that stderr text: it is quoted, never parsed.
- **Words.** Five places need rewording:
  - `packages/domain/src/events.ts:2640-2645`, the comment and the `@summary`;
  - `packages/project/src/pr.ts:226`;
  - `packages/domain/src/pr.ts:319`;
  - the comment at `pr-sync.ts:373-374`, *"finds the merge in `branch.personal`'s history, builds it, and records it"*. Drop *builds it*: the `found` path at `:264-267` records without a rebuild, and its own comment says so (*"it is recorded as found, not rebuilt"*);
  - `doc/events.json`. It is generated from the `@summary`, so regenerate it with the repo's generator and never edit it by hand. The check test fails on a hand edit that drifts from the generator.
- **Out of scope, though it sits close by.** Two of `turn`'s catch sentences, *"whether anything was pushed is not known"* (`pr-sync.ts:335-336`, `:357`), are already consistent with the new meaning of `unknown`. Leave them.

## What checks this

All of it is checkable in the unit half with fake ports. Nothing here needs `pnpm test:integration`. On a live run, two things settle it:

- The descendant case shows as `PrMergedBack.mergeCommit` equal to the merge the same attempt pushed, with no `PrMergeBackFailed { why: 'lost-push' }` on that PR's stream for that `prHead`.
- The stderr half shows as the `detail` on `PrWaiting` and `PrMergeBackFailed`, which now ends with `: <git's line>`.

No ADR changes, and nothing here contradicts 0130 §6.
