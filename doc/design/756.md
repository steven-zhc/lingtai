# #756 design note: the numbered NEXT block for `init` and `add`

## The ticket's line numbers and `InitWorld.doctor` shape are out of date

#773, #755 and #758 landed after the ticket was written, so ignore the ticket's `init.ts` line numbers. Here is what holds today:

- **The doctor seam is `SetupDoctor`, not a new `{ text, failed, next }`.** It is `apps/cli/src/setup-end.ts:14-18` (`report`, `toFix`, `blocks`), and `InitWorld.doctor` (`init.ts:244`) and `AddWorld.doctor` (`add.ts:39`) both use it. Add one optional field to it: `next?: string`. Fill it in `liveSetupDoctor` (`setup-end.ts:21-32`) with `nextOf(report.results)`, taken from the same dynamic `import('./doctor.ts')` that already provides `toFixSummary`. That file's header says why the import has to stay dynamic: "Imports nothing from `doctor.ts` by value — `init.ts` reaches this". Keep the field optional so the existing fakes in `init.test.ts`, `add.test.ts` and `upgrade-drain.test.ts` still compile.
- **Doctor's blocks already carry no `NEXT` line.** `formatReport` is `renderDoctor(report, { next: false })` (`doctor.ts:3483-3484`). So the single failure `NEXT` line that init or add prints is the only one on screen. Do not turn `next` on.
- **`printSetupEnd` should return what it closes on.** Today it returns `{ failed }` (`setup-end.ts:38-60`); change it to return `{ failed, fix?: string }`. `fix` is `done.next` when `done.toFix.failed` is true, and `'lingtai doctor --verbose'` when `world.doctor()` threw. The `!cardDrawn` path in `init.ts:707-718` calls `world.doctor()` itself and has to work out the same pair.
- **`git` already has a seam.** `InitWorld.runGit(dir, args)` exists (`init.ts:229`). B1 runs `world.runGit(world.cwd, ['rev-parse', '--show-toplevel'])`, the call `runLocalBranch` makes (`first-project.ts:469-474`), so the only new field is `cwd: string`, set to `process.cwd()` in the live world (`init.ts:~1235`). Make it required, as the ticket says, and add it to the test helper that builds a fake `InitWorld`.

## Where the pieces go

- **`apps/cli/src/output.ts`**
  - Move in `LABEL_COLUMN` and `labelled` from `doctor.ts:3337-3343`.
  - Add `renderNextBlock(steps: readonly NextStep[]): string[]`.
  - Add `renderNextLine(command: string): string` and use it at `doctor.ts:3376-3378`, so doctor's closing line and the failure line here are the same drawing.
  - `output.ts` already imports `paint` from `@lingtai/env/colour`; `badge` comes from there too (`colour.ts:134`, and its plain mode `[next]` is already handled there).
- **New file `apps/cli/src/next-steps.ts`, pure.** It holds `type NextStep = { command: string; for: string }` and one builder per row of the ticket's table:
  - `localInitSteps(needBoard)`
  - `githubInitSteps(setupUrl?)`
  - `addSteps({ project, tickets, kinds, slug? })`
  - `hereSteps(here)`, where `here` is `{ kind: 'outside' } | { kind: 'unregistered', toplevel } | { kind: 'registered', project, tickets, kinds, owner }`

  The table tests call these. Keep them out of `setup-end.ts`, which is about printing.
- **One closing call per command, and it comes last.** In `init.ts`, replace the whole tail at `:753-770` with a single `close(...)` after the board lines (`:720-751`). It prints either `renderNextLine(fix)` or the optional preface line followed by `renderNextBlock(steps)`. Nothing may be logged after it. In `add.ts`, both successful branches call `printSetupEnd` (`:96-113` and `:132-150`); put the block straight after each, built from that branch's own `CardRecipe`.

## Decisions the ticket leaves open

1. **Where `add` gets `source.tickets` and the kinds: from the `CardRecipe` it already has, with no new read.** `CardRecipe.tickets` and `.kinds` are at `setup-card.ts:28-29`. On the GitHub path that card is the recipe read back from disk (`add.ts:121-125`). On the local path it is `cardRecipe(finalRecipe, toplevel)` (`first-project.ts:762`), the recipe that was written. Both are the recipe as written, which is what the ticket's Watch out asks for. The ticket's "the recipe cannot be read" edge therefore never comes up for `add`: an unreadable GitHub recipe already exits 1 with no card (`add.ts:127-130`), and a refusal exits before any block. That edge applies only to B1.
2. **B1 covers both has-projects paths.** That is the `!cardDrawn` path, and the configured-App re-run (`init.ts:695-706`), whose comment says it "closes on nothing" (`:753-754`). Both get the `cwd` block, which makes "every path ends on the block" true.
3. **How B1 classifies the directory.**
   - It reuses `registered` from `init.ts:416`; do not call `projects()` a second time. A project matches when `basename(toplevel)` equals its name, compared case-insensitively.
   - For a match, read the tickets source and the kinds with `readRecipeKey(p.project, ['source', 'tickets' | 'kinds'], { home, files: world.files })`, the way `init.ts:428` reads `repo.remote` (the function is at `packages/recipe/src/write.ts:213`).
   - `gh issue create -R` needs an owner. If the recipe says `tickets: github` but the project has no recorded owner (`p.owner === null`), handle it like an unreadable recipe: drop the ticket line and keep only `lingtai start`.
   - Do the `rev-parse` call and the reads before the board section, and print the result in `close`.
4. **A failure replaces everything, including B1's preface.** When `fix` is set, the output ends on exactly one `NEXT  <fix>` line: no number, no *for*, and no `<toplevel> is not a project here`.
5. **Placeholders versus real names.** `init`'s GitHub steps keep the literal `<owner>/<repo>`, as today. `add`'s steps use the real slug and project.
