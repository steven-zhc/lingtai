# #1067: the shape

Four decisions the ticket leaves open. Each one is something a straight `await` → `yield*` conversion gets wrong.

## 1. Split `dbTickets` in two so one memo is shared

Today `ticketsFor` builds a single `dbTickets(sql, project)`. It uses that object for the `listIssuesSince(new Date(0))` check and then returns the same object (`ticket-store.ts:259-262`). So the store the caller gets back already has its tables ensured. If `ticketsForEffect` checks through `makeDbTickets(...)` and then returns a fresh `dbTickets(...)`, the returned store runs the DDL a second time on its first call. That is an extra `exec` that today's code never makes.

Build it in two layers:

- `makeDbTickets(sql, project, options): DbTicketsEffects` owns the memo.
- `promiseDbTickets(t: DbTicketsEffects): DbTickets` is the object literal. Each member is `(…) => runPort(t.member(…))`.
- `dbTickets(sql, project, options) = promiseDbTickets(makeDbTickets(sql, project, options))`. Its signature does not change.

`ticketsForEffect` does three things:

1. It makes `t` once.
2. It runs `yield* t.listIssuesSince(new Date(0))`.
3. It returns `promiseDbTickets(t)`.

`liveHistoryEffect` yields `makeDbTickets(sql, project).listIssuesSince(...)` directly and never goes through a face.

The members of `promiseDbTickets` contain no `Effect.run*`, so the ratchet does not count them. `runPort` is the only listed face.

## 2. `ensureReady` follows `closableOnceEffect`, but forgets a failure

`packages/event-store/src/closable.ts:46-67` is the in-repo precedent. It uses `Deferred.makeUnsafe` inside `Effect.uninterruptibleMask` + `Effect.suspend`, so "two first callers cannot both open". Its comment also says *"A failed open is remembered."* That is the opposite of what `db-tickets.ts:224-233` does, so `closableOnceEffect` cannot be reused as it is. Copy the shape instead, inside `makeDbTickets`:

- Keep a cell: `let ready: Deferred.Deferred<void> | null = null`.
- Inside `uninterruptibleMask(restore => suspend(...))`:
  - If `ready` is set, return `restore(Deferred.await(ready))`.
  - Otherwise set `ready = Deferred.makeUnsafe()`, run `Effect.exit(ensureTicketTablesEffect(sql))`, and complete the cell with that exit.
  - If the exit is a failure, set `ready = null` **before** completing the cell.
  - Then return `restore(Deferred.await(cell))`.
- Any callers already waiting on that cell get the failure, just as every awaiter of today's rejected `ready` does. The next caller starts again.

The mask matters. An interrupted first caller must still fill the cell. If it did not, every joiner would hang on a `Deferred` that never completes. Today's promise cannot be interrupted, so this case never comes up there.

Do not use `Effect.cached`, as the ticket already says. Do not use `Effect.runPromise` to fill a `Promise` cell either: the ratchet counts that run, and it is not a face.

## 3. One SQL adapter, and only the duplicate insert is typed

`ensureTicketTables` today calls `execIdempotently`, and that is itself a face: `store-face.ts:219-221` is `Effect.runPromise(execIdempotentlyEffect(fromPromiseLogSql(sql), ddl))`. Calling it from inside an Effect would be Effect → face → Effect, and `store-face.ts:11-14` forbids that for a moved caller because *"the face's run starts a root fiber that drops the caller's span and interruption"*.

- `ensureTicketTablesEffect(sql)` yields `execIdempotentlyEffect(port, …)` twice, in today's order, where `port = fromPromiseLogSql(sql)`. Both names are exported from `@lingtai/event-store` (`index.ts:42`, `:109`).
- The same `port` serves every other `query` in the store. `fromPromiseLogSql` already lifts each call with `Effect.promise`, so a failure is a defect carrying the driver's own error (`store-face.ts:180-186`). That is the ticket's "`Effect.promise` where it does not catch", done once instead of in thirteen places.
- `createIssue`'s INSERT is the one call that goes to the raw `sql`, through `Effect.tryPromise({ try: () => sql.query(...), catch: (e) => e })`.
  - Write the retry as a recursive `attempt(n)`, the shape of `execIdempotentlyEffect` (`snapshots.ts:120-126`). Don't use a `Schedule`.
  - `now()` is read inside each attempt, as it is today.
  - A failure where `isDuplicateTicketNumber(err) && n < MAX_RETRIES` tries again. That is 8 tries in total, matching `attempt >= MAX_RETRIES` at `:279`.
  - Any other error, and the last duplicate, goes to `Effect.die(err)`. That keeps every member's `E` to `BodyChanged | Error` (from `noSuchTicket` and `updateFields`).
  - `runPromise` rejects with the squashed cause: the failure itself, or the defect itself (`store-face.ts:6-9`). So the face rejects with the same object `throw err` gives today.
- The failures today's code throws by hand become `Effect.fail`, built by the same helpers with the same wording: `noSuchTicket`, `editComment`'s `no comment …`, `updateFields`'s `#n changed since this form was opened`, and `new BodyChanged(number)`.
- `JSON.parse` in `parseLabels`, and `rows[0]!`, throw synchronously inside `Effect.gen`. That becomes a defect, and the face rejects with the same `SyntaxError` or `TypeError` as today. Leave them as they are.

## 4. `ticketsForEffect` and `liveHistoryEffect`

- Keep the dynamic imports for the reason `ticket-store.ts:236-240` gives: *"`filter.ts` … must not open one merely by importing this function"*.
  - Lift each with `Effect.promise(() => import('@lingtai/event-store'))`, then call `processTicketSql()` inside another `Effect.promise`.
  - `liveHistory` imports `@lingtai/domain` the same way (`ticket-history.ts:21-22`).
  - `defaultSql` and `defaultLogQueries` become plain Effects with no `async` (or are inlined). They are counted today (`:223`, `:227`) and must not be left behind as `async`.
- `log.queries.projectStreams` / `options.log.projectStreams` is a promise `LogQueries` member. Lift it with `Effect.promise`; `QueriesPort` is out of scope.
- Keep the order exactly:
  1. return `client` for a source that is not `db`;
  2. `no repository name recorded` as `Effect.fail(new Error(...))`;
  3. sql;
  4. the table check;
  5. only if the table is empty, the log's streams;
  6. `TicketSourceConflict` as `Effect.fail`.
- The face is `export function ticketsFor(state, recipe, client, options = {}) { return Effect.runPromise(ticketsForEffect(state, recipe, client, options)) }`. A default parameter value is allowed. `effect-ratchet.test.ts:203-215` requires exactly one `return Effect.runPromise(<call>)` statement, and nothing about the parameters.
- `liveHistory` is the same: `return Effect.runPromise(liveHistoryEffect(project))`.

## Tests

- **`ensureReady` unit test** (the ticket's checkbox):
  - Use a `TicketSql` fake with `dialect: 'sqlite'`, so `execIdempotentlyEffect`'s Postgres race retry stays out of the count.
  - Count every `exec`. Expect 1 on the first member call (rejected, and the member rejects with that same error), 2 on the second, and 0 on the third.
  - Add one concurrent case: two first calls made in the same tick produce exactly 2 `exec`s, not 4. This is the claim decision 2 makes, and the unit half is the only place it can be checked before the merge.
- The eight-way `createIssue` race only runs in `integration/db-tickets.test.ts`, which is Postgres-only and not part of the unit run. That makes it after-the-merge evidence. Before the merge, two things stand in for it:
  - the unchanged contract suite on SQLite;
  - a unit test with a fake whose first two INSERTs reject with `{ code: '23505' }` and whose third answers. The member must resolve after exactly 3 INSERTs. A second fake rejects 8 times, and the face must reject with the 8th error itself.
- `ensureTicketTables` is deleted, not left as a face. The tests that call it switch to `Effect.runPromise(ensureTicketTablesEffect(sql))`, as the ticket says.
