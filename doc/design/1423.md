## Design note for #1423: the queue in team mode stops treating a blocker that landed on `branch.personal` as holding

### Use `listBlockedBy`, don't add `blockersOf`

The ticket says nothing reads the per-issue endpoint. That's wrong: the grep missed it because the path is built from a template string.

- `GitHub.listBlockedBy(issue): E<LinkedIssue[]>` already exists (`packages/github/src/client.ts:511-512`). Its doc comment says *"Every issue blocking `issue`, open or closed, across all pages, or a throw."*
- It is built at `client.ts:1030-1032` on `listLinked` (`client.ts:815-844`). `listLinked` reads `per_page=100`, takes `repository` from `repository_url` (`client.ts:836`), and fails past `LINK_PAGES = 20` (`client.ts:585`) *"so it cannot say a link is not there"*.
- The board and `lingtai status` already reach it through `TicketLinks` (`packages/conductor/src/filter.ts:230-251`). That port answers `TicketLink { repository, number, title, state }` (`packages/conductor/src/db-tickets.ts:189-194`).

So use `TicketLinks.listBlockedBy`. Wrap it in `Effect.tryPromise`; that adds no `async` and no `Effect.run*` to the ratchet. Wherever the ticket says `blockersOf`, read `listBlockedBy`; the counting fake in *Done when* counts that call.

This also settles the "more than 100 blockers" edge. Past 100 the read costs one more request per page, and past 2000 it is a failure, which holds the ticket under the read-failure rule. A short list is never possible.

### The decision goes in `runnableNowEffect`, not in one caller

`considerIssue` (`packages/conductor/src/discover.ts:240-297`) is pure and synchronous, so it stays as it is. The new step goes into `runnableNowEffect` (`discover.ts:474-524`) as an optional `landed` option:

- what reads blockers: a `TicketLinks` and its `repository`;
- what reads the log: store and project;
- `branch.personal`, for the sentence.

When `landed` is absent, behaviour is exactly today's. A caller passes it only when `selection.mode === 'team'` and `selection.tickets !== 'db'`. A null `TicketLinks` (no way to list blockers) also gives today's behaviour.

It has to live here because six places compute the offer and they must agree:

- `packages/conductor/src/schedule.ts:237`: the pass's pick.
- `packages/conductor/src/conduct.ts:3281-3291`: `take` re-reads with `only: [options.issue]` and answers `passedOver` from `considerIssue`'s reason. If only the schedule knew about landed blockers, the schedule would pick the dependent and `take` would refuse it as `blocked-by`, every pass.
- `apps/cli/src/conduct.ts:550`: `lingtai now`.
- `apps/cli/src/status.ts:495`.
- `apps/board/src/lib/board.ts:1003` and `apps/board/src/lib/queued.ts:335`: the board. If the board were left out, it would draw a ticket as blocked that the conductor is taking.

### Which skips get the extra read

Blocked-by is checked before the assignee rule (`discover.ts:290-294`: *"An issue both blocked and somebody else's reports `blocked-by`"*). Releasing a ticket from `blocked-by` must not skip the checks that come after it.

For each issue that `considerIssue` skips as `blocked-by` with `blockedBy > 0`:

1. Call `considerIssue` again with `dependencies: { blockedBy: 0 }`.
2. If that still skips the issue (for example `assigned-elsewhere`), keep today's `blocked-by` skip and make **no request**.
3. Only an issue that would otherwise be runnable gets its blockers read.

This keeps the *"one request per blocked ticket"* rule and cuts that down to the tickets that could actually be taken.

### What counts as held on the branch

Define it as *joined a draft*, read from `PrDraftTicketAdded` events. Don't use `PrState.draft ∪ PrState.tickets`. Two facts push this way:

- ADR 0131 §1 makes joining the draft the record of a landing on `branch.personal`.
- `PrInProgress` empties `draft` (`packages/domain/src/pr.ts:301-302`), so the draft alone forgets earlier landings.
- `PrFixLanded` adds a ticket to `tickets` (`packages/domain/src/pr.ts:332-337`), but a pr-fix lands on the PR's branch, not the personal branch. `draftOfLanding` is *"Null for a solo project and for a pr-fix, whose base is the PR's branch"* (`packages/conductor/src/conduct.ts:1199-1203`). Counting `tickets` would release a dependent onto a personal branch that doesn't have its blocker's code. That is the guess the ticket forbids. `TicketLink` carries no labels, so `lingtai:pr-fix` can't be filtered out from the GitHub side either.

How to build it:

- Add a helper in `packages/project/src/pr.ts`, next to `listPrs` and `draftIn` (`pr.ts:87-97`, `156-159`).
- It reads each PR stream once with `readPrEvents` (`pr.ts:73-75`), reduces it with `reducePr` for the status, and collects `PrDraftTicketAdded.ticket` from PRs whose status is `draft`, `requested`, `in-progress`, `waiting`, `in-review` or `merged`. Put the pure fold over envelopes in its own function so it can be unit-tested.
- `ticket` is the issue number as a string (`packages/conductor/src/ticket/commands.ts:934-943` passes `named.issue`), so compare it with `String(blocker.number)`.
- A ticket handed back from a refused or closed PR rejoins the next draft (`PrDraftTicketAdded.from`, `events.ts:2560-2568`), so it is found there. That fits the ticket's "in the draft" rule.
- Read it lazily: once per call, only if at least one issue reached the blocker read.
- If it fails, every such issue keeps `blocked-by` with the sentence *"could not read the project's PRs: <why>"*. This edge isn't in the ticket's list; it follows the same rule as an unreadable blocker list.

A blocker **holds** unless one of these is true:

- its `state` is `closed`;
- its `repository` equals `links.repository` (compare case-insensitively; GitHub logins are) **and** its number is in the set above.

### What the result carries

Make both new fields **optional**, so no fixture or `Offered` literal changes:

- `Offered.runnable[]` gains `landedBlockers?: readonly number[]`.
- `Offered.skipped[]` gains `held?: string`. Its reason stays `blocked-by` (`SkipReason` is unchanged), so `passedOver` counts as today.

Write each sentence in one exported function in `discover.ts`, the way `dependenciesUnread` is (`discover.ts:376-400`: *"One phrase rather than a flag … must not come to word it differently"*):

- *"its blockers #1420 landed on steven-zhc/studio"*
- *"could not read its blockers: <why>"*

Where they are printed:

- **Status:** beside `dependenciesUnread` at `apps/cli/src/status.ts:827-829`, joined by ref from `found.runnable` (`status.ts:503-524`).
- **Board:** the queue card in `apps/board/src/lib/queued.ts:334-360` and `apps/board/src/app/queued-stream.tsx:123-154`.

`whyNothingRuns` needs no change. A released ticket is no longer in `skipped`. A held one is still `blocked-by`, and `whyNothingRuns` follows it through its *open* blockers (`packages/conductor/src/why-nothing-runs.ts:296-330`).

### Caching: the conductor reads fresh, the board and status use the existing cache

- **Conductor** (`schedule.ts`, both `conduct.ts`): pass `links` raw. The ticket says no state is kept across a pass, a restart or a retry.
- **Board and status:** pass `links` through the existing per-process cache in `blockers.ts` (`packages/conductor/src/blockers.ts:27-33, 58-64`, keyed `${project}#${ref}` plus `blockedBy`, 60 s). Export a reader from that file. The Queued column asks GitHub on every render (CLAUDE.md), and status then calls `readBlockersEffect` for the same refs (`status.ts:666-668`). Through the shared cache that second call is free instead of a second request.

To build `TicketLinks` for the conductor callers, export `ticketLinksOf` (`filter.ts:238-251`) and use it. Don't reimplement it.

### ADRs this contradicts

- **0130**, line 122-124: *"A blocker stays a blocker until it is closed: a ticket blocked by one that has landed on `branch.personal` waits until that one's PR merges"*. Its own "Left for later" (line 177-178) lists *"a blocker that has landed on the branch no longer blocking"*. 0130's status line reads "proposed".
- **0122**, line 59-62: *"A blocked-by chain never runs together … a blocker in flight is open until it lands and closes."*
  - This still holds for a blocker in flight before it lands: it joins the draft only when it lands.
  - It no longer holds for a landed blocker that was requeued. That blocker is still in the draft, so its dependent can run beside it. The ticket decides that it does not hold; put the comment it asks for at that spot.

In both cases the answer is a superseding file, not an edit to 0130 or 0122. Writing one is outside this diff (*Out of scope*: any document), so tell the reviewer it is still owed.

### Checks

Every *Done when* item is a unit test. None of it needs `pnpm test:integration`.

- `packages/conductor/unit/discover.test.ts`: a team case with `createMemoryEventStore()` carrying `PrDraftTicketAdded` and PR-status events, and a counting fake `listBlockedBy`.
- The `packages/project` fold over envelopes, with PR events for the merged, closed and refused cases.
- `apps/cli/unit/status.test.ts`: the *landed on* line.

Nothing here reaches a `"use client"` graph. `queued.ts` and `board.ts` are server libs, so the Next build check that only runs after the merge isn't put at risk.
