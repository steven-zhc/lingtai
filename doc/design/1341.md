# Design note: #1341, a pr-fix ticket is cut from and lands on the open PR's branch

## The shape in one paragraph

Each attempt gets its own branch, `attempt: { branch, pr: number | null }`. It is a `let` in `conduct.ts`'s pass scope, set once for the attempt and never reassigned after that. Every reader that runs after the claim calls `attemptBase()` instead of closing over `base`. On the PR side, a pr-fix landing appends `PrFixLanded` **inside its lane turn**, not from the ending. The PR stream records that In progress is owed again, and `walkPr` answers it. There are three decisions below that the ticket does not make, or makes in a way that contradicts its own edges.

## 1. Rename `base` so the compiler finds every reader

`const base = branchOf(recipe)` is at `packages/conductor/src/conduct.ts:1192`; the ticket says `:1194`, and its other line numbers have drifted by about 3 too. Rename it to `passBase` and add `const attemptBase = (): string => attempt?.branch ?? passBase`. Then let `pnpm typecheck` list every reader. There are more than the ticket names, for example:

- the run-log line, `:2378`
- `merge-tree … reviewed base`, `:2483`
- `ownChangeStart({ base })`, `:2515`
- `baseStateEffect({ base })`, `:4294`
- the red record's `base`, `:4337`

Every reader that runs after the claim reads `attemptBase()`. Only the code that runs before the claim keeps `passBase`.

Two readers are built before `take` runs, so they must become lazy:

- **`stepDeps.base` (`:4518`).** Declared `worktree:` actions read their base from the deps: *"The base is not the block's: it is `branchOf`'s, handed in as `deps.base` — one value that flows (0104 §5)"* (`packages/actions/src/from-recipe.ts:514-522`). `actionsAt` is called when each step runs (`run-attempt.ts:3096`). So have `actionsAt` (`conduct.ts:4804`) pass `{ ...stepDeps, base: attemptBase() }` instead of the stored object. `defaultsAt`'s `admit` row (`:4772`) also reads `attemptBase()`. Once both do, `cut` (`:3375`) needs no special case: `spec.base` already is the attempt's branch.
- **`flakyPortOf({ stream: integrationStream(project, base) })` (`:4524`).** `stream` is a plain string (`flaky-port.ts:16`). Make it `stream: () => string` and read it where `flaky-port.ts:38` reads the stream.

**Where `attempt` is set:**

- **A continuation:** set it where `continuation` is computed (`:1399`), from `reduced` — the ticket state the claim is about to append at. This has to happen before the claim, because the `BaseRed` continuation reads `repo.baseHead({ base })` there (`:1420-1425`).
- **A fresh claim:** set it in `take`, after `runnableNowEffect` (`:3245`) and **before** the `Effect.uninterruptible` region (`:3269`). The read holds nothing, so it does not belong inside a region whose comment says it *"stops short of `runnableNow` and `getIssue`, which hold nothing"*.

**What makes a claim a pr-fix:**

- The mode check is `modeOf(recipe) === 'team'` (`modeOf` is imported at `:234`).
- The kind check is `normaliseLabel(runnable.kind) === normaliseLabel(PR_FIX_LABEL)`. `runnable.kind` is the string from `rankedKinds`, which puts `PR_FIX_LABEL` first in team mode (`discover.ts:149-153`, `:524`).

**The PR read, and what each answer means.** Call `latestPr(project, store)` (`packages/project/src/pr.ts:76`).

- **The read fails:** return `{ notClaimed: … }`. `queue-action.ts:143` turns that into the `not-claimed` failed verdict.
- **An open PR with `lastPushed === null`:** this is a decision the ticket does not make. It covers `requested`, or In progress before its first push: `isOpen` holds, but `origin/<prBranch>` may not exist yet, and `provision` cuts from `origin/<base>` (`worktree-action.ts:66`). Answer `notClaimed` with "the PR branch is not on the remote yet". The ticket is taken on a later look, once the PR has pushed. Treating this case as *no PR* would land the fix on `branch.personal` while a freeze is reading that branch.
- **An open PR with `lastPushed !== null`:** `{ branch: state.prBranch, pr: state.n }`.
- **No open PR:** `{ branch: passBase, pr: null }`.

**The claim and the ticket state:**

- `cutFrom` goes on `claimTicketEffect` only. `continueTicketEffect` never writes it.
- `TicketClaimed` and `TicketContinued` share one reduce case (`packages/domain/src/ticket.ts:550-551`). Write `cutFrom` **only when `shape === 'claim'`**, and leave it alone on a continuation. Otherwise a continuation, whose payload has no `cutFrom`, would erase the branch it is meant to keep.
- Bump the codec version with a comment line, in the list at `ticket-codec.ts:184-191`.

## 2. Skip the base-red check for an attempt on a PR branch

The ticket lists "the base-red and base-check reads" among the readers to move. If they did move, a red PR branch would release the pr-fix with `BaseRed`, and `proposeBaseFix` would open a fix ticket. That ticket is an ordinary kind, so it is cut from and lands on `branch.personal` (`base-fix.ts:1-11`), while its body names the PR branch. It would never make that PR branch green.

The PR branch only reaches the remote after the walk's own `build` step: `IN_PROGRESS_STEPS = [syncStep, buildStep, pushStep, openStep]` (`packages/conductor/src/pr.ts:366`). So the red-base question at `:4285-4345` should answer `notRed: 'a PR branch is built by the PR's own walk (#1312)'` when `attempt.pr !== null`, without asking anything.

A refusing `build` then buys a fix round, as for any ticket. The `flaky` port still reads `integrationStream(project, attemptBase())`; for a PR branch that stream simply holds no `BaseChecked`.

## 3. `PrFixLanded` is appended inside the lane turn

The ticket's Fix 3 says "after `TicketLanded`, the ending appends `PrFixLanded`". Its own Edge says "the second's `expectBase` is the first's merge, because `PrFixLanded` moved `lastPushed` before the second took the lane". Only an append inside the first landing's lane turn makes that edge true.

The ending runs after `land` (`:3949`) has released the lane. In that gap, two things go wrong:

- A second pr-fix reads a stale `lastPushed` and refuses `pr-branch-moved` for a person.
- The walk's push step reads the remote at the fix's merge, which is `≠ lastPushed`, and answers `moved(at)`. That records `PrWaiting branch-moved` for a person (`pr.ts:221-225`). The push step already records `PrPushed` "**inside** the lane's turn" for this exact reason (`pr.ts:201-202`).

So, in `landNow` (`:3865`), for `attempt.pr !== null`:

1. Before `repo.integrate`, read the PR with `readPr(project, attempt.pr, store)` and pass `expectBase: state.lastPushed`. `landNow` runs inside the lane's `through`, so this read is inside the turn.
2. On `result.ok`, append `PrFixLanded { ticket, mergeCommit }` through `recordPrFixLanded`, then return.

If that append fails, **do not fail the landing**: the push has happened. Log it and leave it to the sweep repair (Fix 4). The sweep repair keys on `TicketLanded`, which the ending still appends as it does today (`:6143`).

## 4. PR stream details the ticket leaves implicit

- **The `PrInProgress` that answers a fix needs `frozenSha = state.lastPushed`.** The reducer sets `target: d.frozenSha` (`packages/domain/src/pr.ts:121-135`). Anything else moves the target back behind the remote head, and the push step answers `again` forever on the `--is-ancestor` check (`conductor/src/pr.ts:232-236`). Pass `tickets: state.tickets`, which already includes the fix, and keep `branch` and `main` from state. Model it on `restartTransition` (`domain/src/pr.ts:267-278`).
- **`PrFixLanded` reduces to `lastPushed = target = mergeCommit`, appends the ticket to `tickets`, and sets a new `fixOwed: true`.** `PrInProgress` clears `fixOwed`.
- **The transition returns `null` in three cases:**
  - the PR is `!isOpen`;
  - the status is `'requested'`;
  - the ticket is already in `state.tickets`. This makes the in-lane append and the sweep repair idempotent.
- **`walkPr` (`conductor/src/pr.ts:440`) answers the owed In progress before its status check, on every pass through its loop.** A walk already in flight when a fix lands sees `now.target !== state.target` and `continue`s (`:466-467`). Without this check it would carry on with the old pass's `sync`/`build` records and skip them for the new head.
- **Two other filters must hold off while a fix is owed.**
  - `mergeBackOwed` must be false while `fixOwed` is true, so nothing merges back into `branch.personal` before the fix has been built.
  - `servePendingPrs` (`:520`) must also serve a PR with `fixOwed`.
- **Add `PrFixLanded` to `PR_EVENTS`** (`packages/daemon/src/work-loop.ts:119`). `makePrHandlers.serve` already routes an event on a PR stream to `servePr` (`conductor/src/pr.ts:761-762`).
- **Fix 4's repair goes in `learnPrEnds`, beside `learnOnePr`, for the open latest PR** (`:723-725`).
  - Read `ports.candidates(project)`.
  - Reduce each candidate's stream.
  - Any candidate with `landed.base === latest.prBranch` that is not in `latest.tickets` gets `recordPrFixLanded`.
  - `readDraftOn` already excludes these landings from the next draft, because `state.landed.base !== personal` (`project/src/pr.ts:367`). No change is needed there.

## The lane refusal

Put the `expectBase` check in `integrate.ts` directly after the `head-moved` check (`:470-473`). That is after the fetch and before `sweepAbandoned` and the worktree, so nothing is merged or pushed. Compare `(yield* at(['rev-parse', laneBase], mirror)).trim()` with `options.expectBase`.

Then add the new reason in the places that already handle `base-checked-out`:

- `'pr-branch-moved'` goes into `RefusalReason` (`vocabulary.ts:52-89`);
- it is owned by `'person'` (`failure/explain.ts:204`);
- its sentence goes beside `explain.ts:377`.

`tsc` will point at any exhaustive map that also needs the new value. The test goes beside `packages/repo/unit/base-checked-out.test.ts`.

## Edges this note settles

- **A process killed after the lane pushed and before `PrFixLanded`:** no `TicketLanded` is recorded, the claim is released (0109 §5), and the next claim ends `satisfied` (as the ticket says). Nothing writes `PrFixLanded` in this case. The PR's next push step sees an unknown head and waits for a person with `branch-moved`; `lingtai pr retry` (#1314) takes it. This is accepted as a rare path. The log settles it: a `PrWaiting { reason: 'branch-moved' }` whose `detail` names the satisfied ticket's merge.
- **The PR merged or closed between the claim and the landing:** `expectBase` is still `lastPushed`, so the lane checks the head as usual. The transition returns `null`; log it in the run log, and no request is made.

## Tests

All of these are unit tests; nothing here needs the integration half.

- **The claim:** add to `packages/conductor/unit/conduct-what-a-claim-leaves.test.ts`, whose fake `Repo` already sees `provision`. Also check that a declared `worktree:` action gets the PR branch, through `actionsAt`.
- **The lane:** add `expectBase` cases beside `packages/repo/unit/base-checked-out.test.ts`.
- **The PR reduce and walk:**
  - `PrFixLanded` followed by `walkPr` appends `PrInProgress { because: 'pr-fix', frozenSha: mergeCommit }`;
  - a `PrFixLanded` on a merged PR appends nothing;
  - the sweep repair runs once and is idempotent on a second sweep.
- **Two pr-fixes in a row:** with a fake lane, the second's `expectBase` is the first's `mergeCommit`. This is the unit-level stand-in for the 0122 edge.

`effect-ratchet.baseline.json` must not go up. The PR read in `take` is `latestPr`, which is already an Effect, and `recordPrFixLanded` follows the `record*` shape of its neighbours in `packages/project/src/pr.ts`.

No ADR is contradicted: 0130 §5 is the decision this implements.
