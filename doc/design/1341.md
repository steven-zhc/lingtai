## Design: #1341, a pr-fix ticket is cut from and lands on the open PR's branch

Line numbers are from this worktree. They sit about two lines below the ticket's: `const base = branchOf(recipe)` is now `conduct.ts:1192`.

### 1. The attempt's branch is one mutable value

Put a `let attemptBranch: { branch: string; pr: number | null } | null` at pass scope, beside `took` and `onStream`. Add a reader `baseNow()` that returns `attemptBranch?.branch ?? branchOf(recipe)`. Every `base` the ticket lists becomes a call to `baseNow()`. Keep `const base` for nothing else, and delete it if it ends up unread.

The value is set in two places, and one of them comes before `take`:

- **A continuation sets it before the claim.** The `BaseRed` continuation reads the base head at `conduct.ts:1420-1428` (`repo.baseHead({ …, base })`), and that happens before `take` runs. Set `attemptBranch` from `reduced`'s kept `cutFrom` where `continuation` is computed, before that read. Otherwise a released pr-fix continuation compares the red sha against `branch.personal`'s head.
- **A fresh claim sets it in `take`**, after `getIssue` (`conduct.ts:3259`) and **outside** the uninterruptible region (`:3268`). That region's comment says it *"stops short of `runnableNow` and `getIssue`, which hold nothing"*, and the open-PR read holds nothing either.

There are three readers that capture `base` early, not two:

1. **`defaultsAt` (`conduct.ts:4772`).** Change it to `baseNow()`.
2. **The flaky port's stream (`conduct.ts:4524`), `stream: integrationStream(project, base)`.** It is computed when `stepDeps` is built. Turn it into a function that is called when the read happens.
3. **`stepDeps.base` (`conduct.ts:4518`).** The ticket doesn't list this one. `actionPortsFromRecipe` hands it to a *declared* `worktree:` action as `{ base: deps.base }` (`packages/actions/src/from-recipe.ts:517-522`, documented at `:210`: *"The branch a `worktree:` action cuts from: `branchOf`'s answer"*). The value is copied when the object is built.

**Decision: the cut decides the branch, not the action's spec.** In `cut` (`conduct.ts:3375`), call `repo.provision` with `baseNow()` and ignore `spec.base`. Add a `from: string` field to `CutAnswer`'s `head` variant (`packages/actions/src/worktree-action.ts:48`). Change the evidence string at `:95`, which today prints `from origin/${spec.base}`, to print `answer.from`. That fixes the default and the declared `worktree:` action at one site, without passing a function through `@lingtai/actions`. `spec.base` stays as what other callers of `makeWorktreeAction` hand in. Update the fake `cut`s in tests to return `from`.

### 2. The open-PR read in `take`

This is a new Effect in `conduct.ts`: `latestPr(project, store)` from `@lingtai/project` (`packages/project/src/pr.ts:76`). It runs only when both of these hold:

- `modeOf(recipe) === 'team'`
- `runnable.kind` equals `PR_FIX_LABEL` (`packages/conductor/src/labels.ts:30`), compared the way `discover.ts:151` normalises it

The outcomes:

| What the read finds | What happens |
|---|---|
| The read fails | `{ notClaimed: 'the open PR could not be read: …' }` |
| `isOpen(pr)`, `pr.prBranch !== null` and `pr.lastPushed !== null` | `{ branch: pr.prBranch, pr: pr.n }` |
| `isOpen(pr)` but the branch has never been pushed (`requested`, or `in-progress` before its first `PrPushed`) | `notClaimed`, saying the PR's branch is not on the remote yet |
| No open PR | `{ branch: branchOf(recipe), pr: null }` |

**The never-pushed case is a decision the ticket leaves open.** `integrate` fetches `+refs/heads/<prBranch>` (`packages/repo/src/integrate.ts:459`), and that branch doesn't exist until #1337's push step records `PrPushed` (`packages/domain/src/pr.ts:143-145` sets `lastPushed`). Falling back to `branch.personal` would be the failure the ticket's Watch out names. The ticket is taken again on a later look once the push lands.

`cutFrom` goes into `claimTicketEffect`'s input. The continuation path (`continueTicketEffect`) records nothing new, because its claim already carries the branch.

### 3. `expectBase` is read inside the lane's turn

`land` (`conduct.ts:3950`) calls `landingLane.through(integrationStream(project, base), …)`, and `landNow` runs inside that turn. When `attemptBranch?.pr` is not null, `landNow` calls `readPr(project, pr)` just before `repo.integrate`. It passes `expectBase: state.lastPushed`. If the PR is no longer open, it still passes that `lastPushed`, so the landing goes ahead, as the ticket's merged-meanwhile edge accepts.

Reading it here, and not at the claim, is what lets a second pr-fix on the same PR see the first one's merge.

In `integrate`, the check goes right after `fetchedHead` (`integrate.ts:470-473`):

```ts
yield* at(['rev-parse', laneBase], mirror)
```

It must come before `sweepAbandoned` and before the worktree is added. `pr-branch-moved` is a new value in `vocabulary.ts`'s `RefusalReason`. It is owned by `'person'` beside `base-checked-out` (`packages/domain/src/failure/explain.ts:204`), and its sentence sits beside `:377-384`.

### 4. The PR side: what PrFixLanded must not trigger

**Trap: the merge back runs too early.** `mergeBackOwed` (`packages/conductor/src/pr-sync.ts:205-210`) is true for any `in-review` PR whose `lastPushed` differs from the last merge back's `prHead`. If `PrFixLanded` moves `lastPushed` while the status is still `in-review`, the next `servePr` (`conductor/src/pr.ts:492-506`) calls `mergePrBack`. That merges the pr-fix head into `branch.personal` before sync, build and CI have run on it, and a resume after a crash in that gap does the same.

The fix:

- The PR reduce keeps `prFixOwed: boolean` on `PrState`. `PrFixLanded` sets it and the next `PrInProgress` clears it.
- `mergeBackOwed` returns false while it is set.
- `servePr`'s **first** act, before `freezePr`, `walkPr` and `mergePrBack`, appends `PrInProgress { because: 'pr-fix' }` when `prFixOwed` is set.
- `servePendingPrs` (`conductor/src/pr.ts:522`) also serves a PR that has `prFixOwed`.

**`PrInProgress` resets `target` to `frozenSha` (`packages/domain/src/pr.ts:131`), and that is fine.** The pr-fix transition carries the PR's own `branch`, `main`, `frozenSha` and `prBranch`, as `restartTransition` does (`pr.ts:267-278`), plus the tickets with the fix appended. The sync step starts from `startOf(target, lastPushed)` (`pr-sync.ts:68-75`), which picks `lastPushed` when it descends from `target`. The state comment at `pr.ts:41-43` says why: *"`PrInProgress` does not reset it: a pr-fix pass starts its steps again, and its push is a fast-forward from here."* So `PrFixLanded` must move `lastPushed` and `tickets`. Moving `target` as well is overwritten one event later, so don't depend on it.

The `because` enum is `packages/domain/src/events.ts:2541`. Add `'pr-fix'` there, and add `PrFixLanded`, with a doc comment, beside the other PR events.

Other wiring:

- `PR_EVENTS` is in `packages/daemon/src/work-loop.ts:119`, not in conductor, and its serve path goes through `parsePrStream`. `PrFixLanded` is on `pr-…`, so `makePrHandlers.serve` (`conductor/src/pr.ts:760-766`) already routes it to `servePr`.
- A walk in flight when the fix lands is already handled. The push step re-reads inside its turn, and a target that doesn't descend from the moved `lastPushed` answers `again` (`conductor/src/pr.ts:228-232`, comment at `:176-181`). The serve that follows holds the same project permit (`:497`), so it runs after that walk.
- The pr-fix walk is drawn from the same `IN_PROGRESS_STEPS` (`:366`). #1339's `ci`, #1318's `summary` and `ready` appear there as those tickets land. This ticket adds no step.

### 5. The repair runs in the sweep

Fix 4 goes in `learnPrEnds` (`conductor/src/pr.ts:715-734`), inside the branch that already reads `latest` when it is open and not `requested`. Read the candidates the way `readDraftOn` does (`packages/project/src/pr.ts:346-368`). That function keeps only `state.landed.base === personal`; keep only `state.landed.base === latest.prBranch` instead, and only tickets not in `latest.tickets`. For each one, call `recordPrFixLanded`, whose transition refuses a duplicate or a PR that is not open.

This also means a pr-fix ticket never enters the *next* PR's draft. `readDraftOn` filters by `base === personal` (`:367`), and a pr-fix's `TicketLanded.base` is the PR branch.

Add one test there: `PrFixLanded` on an `in-review` PR whose merge back is already done appends `PrInProgress { because: 'pr-fix' }`, and calls `merge` for no `pr-back-…`.
