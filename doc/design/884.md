# #884: shape of the change

## 1. The seam: `loadBoard` hands back the resolved filters. GitHub is asked later, by a loader that takes them

`askProject` (`apps/board/src/lib/board.ts:773-798`) splits at `:783`. Everything above that line is `projectFilter`. It is the one recipe resolve per project per render that `queuedCards`' comment insists on (*"this loop already resolved every recipe, and reading one twice is how a render gets expensive"*, `:836-842`).

- **What stays in `loadBoard`:** the `projectFilter` fan-out, plus the facts reduced from it today in the `queuedCards` loop (`:875-880`): `limits`, `backoffMs`, `plans`, `ticketSources`, `kindOrder`, and the `'unreadable'` problems (`:871-873`).
- **What `loadBoard` returns in addition:**
  - the `ok: true` filters themselves, as a new field (call it `askable`);
  - the log's task ids, the `known` set at `:1206`.
- **The new loader:** it takes `(askable, known)` and does `:785-791` plus the card-building half of today's loop (`:885-960`). It returns `{ cards, problems /* 'unanswered' only */, notes, answered: number, asked: number }`.

Why the filters cross into the page rather than the loader resolving them again: a second resolve would undo the one-resolve rule. Passing a filter that carries a GitHub client from `Page` to an **async server component** is fine. It never reaches a `"use client"` graph, so nothing serialises it.

**`notes` move with the GitHub cards.** `passedOver` and `dependenciesUnread` (`:891-895`) are read off `offered`, so they belong to the streamed part. `toColumns(cards, problems, notes)` (`:1339`) keeps its signature. `loadBoard` passes it the `'unreadable'` problems and no notes.

**Keep `askProject`'s test seam.** The `select`/`filterFor` options exist so `ask-project-ownerless.test.ts:49` reaches the code without `HOME`. Give the GitHub loader the same seam: an `ask(filter)` default that the tests replace. `render-cost.test.ts:87-160` and `pending.test.tsx:69` then move to whichever half now holds what they assert:

- the fan-out/overlap property goes to the loader;
- *pending is never asked* stays with `splitRegister` and the filter fan-out.

The loader **never rejects**. `askProject`'s existing `try` already covers `select`; `selectRunnable` reads `task_view`, and on an unbuilt projection that read becomes `'unanswered'` as it does today. Two components await the loader's promise and there is no error boundary, so a rejection would take the page down. Keep any new code inside the per-project `try`.

## 2. Kind colours: a module-level map in `board.ts`

- `const lastKindColors = new Map<string, Record<string, string>>()` sits beside the loader.
- The loader writes `lastKindColors.set(project, offered.kindColors)` for each `'listed'` answer.
- `loadBoard`'s `toCard` call (`:1195`) reads `lastKindColors.get(t.project)?.[t.kind] ?? null` in place of `queued.kindColors`.
- GitHub's own cards keep taking their colour from their own fresh answer (`:906`).
- Export a reset (e.g. `forgetKindColors()`) so the colour test can start from *no answer seen*. Without it, test order leaks through the module.

## 3. The Queued column: the fallback is the log's cards, and the answer is the whole column again

The decision the ticket does not make explicit: `groupQueue` (`board.ts:1468-1488`) groups **all** queued cards by kind and marks one group *taken first* (`:1485`). The ticket takes order out of scope (*"Which cards the Queued column shows, and in what order"*). Appending a second `<Queued>` below the log's would break that: two `bug` headings, and two *taken first* markers.

So the `<Suspense>` wraps the column's card area rather than sitting under it:

- **Fallback:**
  1. the `'unreadable'` problems;
  2. the log's queued cards through `<Queued>`, with *taken first* suppressed (pass a flag that makes `groupQueue`'s `next` stay false);
  3. the line *asking GitHub for runnable issues…*

  *Taken first* is a claim about GitHub's offer too, and is not known yet.
- **Resolved:**
  1. the `'unreadable'` problems;
  2. the `'unanswered'` problems;
  3. the notes;
  4. one `<Queued>` over the log's queued cards plus the loader's cards (already de-duplicated against `known`).

  That is exactly today's markup, so the column reads as it did before once the answer is in.
- **The empty note** (`page.tsx:852`, `emptyNote`) is decided only in the resolved part. The log-only part must never say *Nothing here yet* while GitHub is still being asked.
- **The header count** (`page.tsx:821`, `col.cards.length`) is a `<Suspense>` for Queued alone. Its fallback is the log's count followed by `…`. Resolved, it is log count + GitHub's cards.

`showProject` for the resolved Queued list is computed from `onBoard` ∪ the loader's card projects (ticket's Edges). The fallback uses `onBoard` alone.

## 4. The bar's segment

`rest` (`page.tsx:637-640`) excludes the `queued` column from the parts that render at once. The streamed segment stands where Queued's count stands today and carries **the whole queued count**: log + GitHub. The ticket puts it *"where Queued's count stands today"*, and a separate log-only `N queued` beside it would print the word twice.

- Fallback: *asking GitHub…*
- Resolved:
  - `N queued` when N > 0;
  - nothing at all when N = 0, as an empty column is dropped from `rest` today;
  - when `asked > 0 && answered === 0`, the segment says it could not be counted. Write it as `queued uncounted` when the log has none, and `N+ queued, GitHub uncounted` when it has some. Never `0`, and never a log-only number presented as the total.
- With `asked === 0` (no readable recipe), GitHub was never asked, so the count is the log's alone.

Separators: the segment component takes whether anything follows it and renders its own ` · `. The `total === 0` text (*nothing in the log yet*) and the `title` attribute stay log-only. The segment still renders before that text, so a fresh board with runnable issues reads `3 queued · nothing in the log yet`.

## 5. Where the loader starts, and its timing

In `Page`, after `measure(…, { label: '/' })` has returned (`page.tsx:610`), start one promise:

```ts
const queue = measure(() => runnableCards(askable, known), { label: '/ queue' }).then(([v]) => v)
```

Hand the same promise to both the column's and the bar's `<Suspense>` children, which `await` it. **Do not call it twice**: two calls are two GitHub fan-outs.

Starting it inside the page's `measure` would push into `entries` after `ordered(entries)` has been serialised (`timing.ts:66`), and those timings would be lost silently. The `/ queue` timings go to the span and to the slow-line on stderr only; `<TimingMeta>` is already sent.

`/spend` (`spend/page.tsx:50`) calls `loadBoard` and never starts the loader, so it asks GitHub nothing from now on, as the ticket decides.

## 6. What stands in for what a unit test cannot see

The Jaeger ordering (`page /` ends before `page / queue`) is the person's check. Every `Done when` line other than that one is unit-level:

- `loadBoard` against an `ask` that never resolves, for the first box;
- `renderToString` / `renderToStaticMarkup` of the fallback and resolved components, fed literal values, for the rest.

None of it needs `pnpm test:integration`. Changing `page.tsx`'s imports could put a server-only module into a client graph. Only `apps/release/integration/build.test.ts` sees that, after the merge (#230). Keep the new components in server files and import nothing new into `live.tsx`.
