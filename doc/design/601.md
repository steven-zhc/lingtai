# #601: design note

## Where it goes

Put it in a new `packages/conductor/src/split-ticket.ts` and export it as `./split-ticket` in `packages/conductor/package.json`, next to `./edit-body` (`:32`). `edit-body.ts` is the model to copy. It says *"The body is written first, and a failed write resolves nothing"* (`edit-body.ts:8-11`), and it is laid out in the same three layers this needs:

- `splitTicket(options)` takes the `deciding` lock (`approve.ts:27`) on the parent's stream and holds it through every write, because a second Create all must not start while the first is still writing.
- `splitTicketHolding(options, store, ticketId)` is exported for the unit half only. The lock is the filesystem, so it is out of reach for unit tests. `editBodyAndRequeueHolding` and `resolveWaitHolding:174-179` do the same, for the same reason.
- The final append goes through `resolveWaitHolding`. It is still the only writer of `WaitResolved` (`resolve-wait.ts:4`).

The board is not wired to it here. That is #604 ("Create all locks the page", `Split.dc.html:382`). This ticket ships the function and its unit test.

**The client is a narrow port, not `GitHubClient`:**
`Pick<GitHubClient, 'getIssue' | 'createIssue' | 'updateBody' | 'addSubIssue' | 'listSubIssues' | 'addBlockedBy' | 'listBlockedBy' | 'listIssuesSince'>`. Don't route it through `Tickets`/`IssueChannel`. #599 kept the link verbs off `Tickets` on purpose (`doc/design/599.md`, *Do not add them to `Tickets`*), and a `db` project has no sub-issues.

## Refuse before writing

Do this in order, with no GitHub call until every step has passed:

1. Read the parent. It must be `blocked` on `waitId`.
2. `allowedResolutions(reason)` must include `Split`.
3. `splitPlanProblems(plan, { kinds })` must be empty. `kinds` is required, as at `resolve-wait.ts:236`.
4. Refuse a plan where **two children share a trimmed title**. `splitPlanProblems` does not catch this (`split.ts:84-126` checks keys, not titles), and adoption by title would map both children onto one issue. Put it in the writer and keep it out of `split.ts`: it is a rule about how this writer reconciles, not about whether a plan is sound.

## The reconcile read, before any write

Build one `have: Map<key, {number, id}>` from GitHub. Never build it from the log, because a partial split leaves nothing on the log:

- **Attached children.** Call `listSubIssues(parent)` and keep entries whose `repository` is this project's `owner/repo`. The caller passes it in. #599 returns other repositories' issues on purpose so the caller can compare them (`599.md`, *`LinkedIssue`*). Match a plan child by exact trimmed title. If two sub-issues match one title, refuse by name.
- **Created but never attached.** This is the *timed-out create* from the Watch out. An issue whose create response was lost is not a sub-issue, so the list above cannot find it, and a retry would create it a second time. The precedent is `githubTicketStore`'s idempotent `propose` (`ticket-store.ts:139-167`). It puts an invisible marker in the body (`keyMarker`, `:140`, appended at `:184`), then finds it with `listIssuesSince(since − SKEW_MS)` (`:148`, `:161-167`). The listing is *"complete, or it throws"* (`client.ts`, `listIssuesSince`'s doc). Do the same here:
  - Append `<!-- lingtai:split <waitId> <key> -->` to each child's body when you create it.
  - Before creating any child missing from `have`, call `listIssuesSince` from the `WaitStarted` that opened `waitId`, minus the skew. Use that event's own timestamp off the stored envelope: the value the projector passes to `set` as `at`.
  - Adopt the oldest issue that carries the marker.
  - Read this list once per call, not once per child, and again only after a create that threw.

**Ids.** `TicketSplit` needs each child's REST `id` (`events.ts:323-327`), and no client call returns one today. `Issue` has no `id` (`client.ts:126`). #599 deliberately kept it off `Issue` (*"without adding `id` to `Issue`"*) and off `LinkedIssue = Issue & { repository }`. **Add `id: number` to `LinkedIssue` only**: `listLinked` already holds the raw object (`client.ts`, `listLinked`'s `request<…>`). Every child is listed as a sub-issue once it is attached, so the attach read-back is where its id comes from. Don't add `id` to `createIssue`'s return or to `Issue`. Give the #599 fakes an `id` (`packages/github/unit/links.test.ts`). `pnpm typecheck` will list the rest.

## The writes, each read back

Do these in order, skipping anything already in `have` or already listed:

1. **Create each missing child:** `createIssue({ title, body: body + marker, labels: [kind] })`. Do not add `agent:hold`. 0118 §12 says *"children enter the queue subject to their blockers"* (`0118-a-hold-explains-itself.md:620`).
   - If the create throws, read back with the marker listing before deciding anything.
   - Found → adopt it.
   - Not found → this call stops there, failed at that step. Do not create again in the same call. The person retries.
2. **Attach** each child that is not yet a sub-issue, then call `listSubIssues` again. Every child must now be present, and that read is where its `id` comes from.
3. **Blocked-by between children:**
   - For each `{ticket, blockedBy}`, call `listBlockedBy(have[ticket].number)` and add the link only if it is absent, matching on `number` and `repository`.
   - #599 makes an existing link a thrown 422 (`client.ts`, `addSubIssue`'s doc: *"a caller that must be idempotent lists first"*). Listing first is the only thing that makes a retry safe.
   - Read each link back after adding it.
4. **Hold the parent:** call `listBlockedBy(parent)`, add every child that is missing, and read it back.
5. **The parent's `## Done when`** is a pure function in its own file (`split-body.ts`, beside `body-section.ts`):
   - Keep everything before the first line matching `/^## Done when\s*$/m` **byte for byte**.
   - Replace that heading and everything after it up to the next `## ` heading, or the end, with one `- [ ] #N is closed` per child, then the attribution line (`Split.dc.html:478-479`).
   - Keep any later sections after the new block.
   - No such heading → append the section at the end.
   - Don't reuse `upsertSection`. Its markers are `lingtai:answer`, and this replaces a person's heading rather than a marked span.
   - Write with `updateBody(parent, next, { ifUnchanged: body as just read })` (`client.ts:275-282`), then `getIssue` and check the section landed.
   - On `BodyChanged`, re-read and retry once, as `writeSection` does (`edit-body.ts:76-130`). If the body already carries exactly this section, skip the write.
   - **Call the client directly, not `tellGitHub`.** `tellGitHub` appends `IssueUpdated`/`IssueUpdateFailed` (`edit-body.ts:93`), and the Watch out says to append nothing until every write is read back.

## The append: one transaction, and the changes it needs

`resolveWaitHolding` appends `[WaitResolved, ...releaseOf, ...with]` (`resolve-wait.ts:297-310`). `TicketSplit` must come **before** `WaitResolved` (`600.md`, *Order on the parent's stream*; 0118 §12 `:618-619`), so `with` puts it in the wrong place. Three edits to `resolve-wait.ts`:

- **Replace the `split-not-built` refusal at `:251-256`** with a check that `options.split` (a new, already-built `TicketSplit` payload) is present and names this `waitId`. Without it, refuse as `split-not-written`.
  - If you remove the refusal outright, any caller that passes `{ _tag: 'Split' }` gets a `WaitResolved{Split}` with no child opened. That is exactly what the comment at `:231-234` forbids.
  - Keep the `no-kinds` and `invalid-split` checks above it.
  - Update `resolve-wait.test.ts:121` to the new reason, and add a case where a Split carrying `split` appends both events.
- **Prepend** `{ type: 'TicketSplit', data: parsePayload('TicketSplit', options.split) }` ahead of `WaitResolved`, in the same `store.append`. A `ConcurrencyError` there leaves nothing appended. Every GitHub write is already done by then, so the retry re-reads and lands only the append. That is the resume the Watch out asks for.
- **`releaseOf` (`:578-581`) must release on `Split` too.** Most waits that offer `Split` hold a run (`wait.ts:269,274,297,307`), and a requeue that keeps its claim is not one.

**The requeue is not in the fold yet: change `ticket.ts:373-377`.** `applyTicket`'s `WaitResolved` case moves the lifecycle to `backlog` only for `Requeue`, `EditBodyAndRequeue` and `AnswerQuestion`. Anything else returns `{ ...state, ...at }`, which leaves the parent **`blocked` on a resolved wait**. Meanwhile `task_view` folds every non-Approve resolution to `state = 'queued'` (`task-view.ts:674-680`), so the two would disagree. #600's note says *"A split parent goes back to `queued` through `WaitResolved`, as today"*, which is true of the projection only. Add `Split` to that list.

Two things settle it when replayed:
- the ticket stream's last `WaitResolved{resolution._tag: 'Split'}`, followed by `reduceTicket(...).lifecycle.status === 'backlog'`;
- the `TicketReleased{cause: ByPerson}` in the same append.

This is a fold change, so `lingtai projection rebuild task_view` is not needed for it, because the projection already says `queued`.

## What it returns

Return progress as a list of rows. Use the row names the mockup already draws (`Split.dc.html:442-449`): `create <key>`, `attach <key>`, `chain <ticket>←<blockedBy>`, `hold parent ← <key>`, `done when`, `record the split`, `end the wait`. Each row is `done | skipped | failed | not-reached`, with a `detail` when it failed, plus the `{key, number}` known so far. #604 renders that list. "Skipped" is what makes *retry writes only what is missing* visible on the page.

## Tests (all unit)

Write `packages/conductor/unit/split-ticket.test.ts` over `createMemoryEventStore()` and a hand-written in-memory fake of the port. The fake holds issues, sub-issue edges and blocked-by edges, and **gives every issue an `id` different from its `number`** (#599's rule). Make `failAt(stepName, mode)` able to throw before the write takes effect or **after** it (a lost response). The second mode is the timed-out create.

- **Full plan:**
  - The writes happen in order.
  - The stream gains exactly `TicketSplit, WaitResolved{Split}, TicketReleased` in one append.
  - `reduceTicket` says `backlog`.
- **For every step index, both modes:** fail once, and assert the stream is unchanged. Then call again with no failure, and assert:
  - one issue per key;
  - no duplicate edges, because the fake rejects a duplicate as a 422, as GitHub does;
  - both events exactly once.
- **`split-body.ts`:** text above `## Done when` survives byte for byte, including CRLF and a later `## Related`. With no heading, the section is appended. Applying it twice is a no-op.
- **`resolveWaitHolding`:** a Split without `split` is refused, and nothing is appended.

None of this proves the field names GitHub accepts. That stays as #599 left it: *"The first real check of the spelling is the split writer's first live run"*. That run belongs to #604, not to this pass.
