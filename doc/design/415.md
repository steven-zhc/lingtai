# Design: #415 — the held line under the rail

## What exists already, and what the ticket gets wrong

On the **card**, the rail is already drawn for waiting items. `page.tsx:335` draws `<Rail progress={card.progress} live={card.column === 'running'} />` for any card that has `progress`. `laneProgress` (`board.ts:749`) folds a stream for the cards `railCandidates` picks, and that includes the head of Waiting: `WAITING_RAILS = 6` (`board.ts:391`). When `live` is false, `Rail` already prints `{step:action} refused` (`rail.tsx:274-290`). So the card needs the held line added, not a new rail.

On the **task page**, the ticket is right: `standing.tsx:294` draws the rail only when `standing.state === 'running'`.

**Keep `WAITING_RAILS` as it is.** A waiting card past the sixth gets no progress, so no rail and no line. Raising the cap changes how many streams one render reads, and `railCandidates` exists to hold that number. That is not this ticket's decision. It does settle the pill (see below): the pill must keep the arm on any card that does not draw the line.

## Where each number comes from

| Fact | Read from | Today |
|---|---|---|
| what refused | `refusedAt(progress.steps)` | already in `Rail` |
| rounds spent | the run's stream: highest `round` on `FixRequested`, or on `FixDeclined` (its `round` is "rounds already spent when this was decided", `events.ts:1310`) | nothing keeps it after the round ends. `foldProgress` holds `fixing` only while a round is in flight (`progress.ts:370-414`) |
| rounds ceiling | the last `FixRequested.of` when it is above 0 (`events.ts:1261`, "so *round 2 of 3* is readable from the event"). Otherwise the recipe's `runtime.limits.rounds` | the board reads it per project as `PassLimitsView.rounds` (`board.ts:650`). The page does not read it |
| restarts used | card: `card.restarts` (`task_view.restarts`, written by `PassRestarted`, `task-view.ts:404-407`). Page: `item.restarts.length` from `applyWorkItem` (`work-item.ts:278`), which `task.ts:662-668` already folds and then throws away | |
| restarts ceiling | `card.restartsOf` or the last `RestartRecord.of` when above 0. Otherwise the recipe's `runtime.limits.restarts` (`board.ts:651`) | `restartsOf` is 0 until the first `PassRestarted`, and that is every ticket today (`task-view.ts:967`) |

**The ceiling comes from the event when the log has one, and from the recipe only when it does not.** The event records what the pass actually ran under. The recipe is today's file, and it may have been edited since. A zero-round, zero-restart pass has no event carrying either ceiling, so the recipe is the only source there. Say which source it was in the line's `title`, so the two cannot be mistaken for each other. None of this calls an agent, and none of it reads anything that is not already read on that render except the page's recipe limits (below).

## Shape

1. **`foldProgress` counts rounds.** Add `rounds: { spent: number; of: number | null }` to `RunProgress` (`progress.ts:186`). `spent` is the highest `round` on `FixRequested`/`FixDeclined`, or 0. `of` is the last non-zero `FixRequested.of`, or null. It is a fold over the stream it already reads, so it adds no read. The pinning test goes in `unit/progress.test.ts`.

2. **One function words the line**, beside `FIXING` in `lib/progress.ts`, so the card and the page cannot say it two ways. That is the #100 argument `describeArm`'s comment makes (`task-view.ts:1124-1128`). Input: `{ spent, roundsOf, restarts, restartsOf }`, with the ceilings already resolved event-then-recipe. Output: for example `2 of 3 rounds · 1 restart left`. A zero ceiling reads `no rounds` / `no restarts left`, never `0 of 0`.

3. **`Rail` takes a new optional `held` prop**: the resolved budget, or null. It is appended to the line in the two non-live readings: after `{refused} refused`, and after `nothing running` (the merge lane's refusal is still a held item with a budget). Render it as its own `<span>` inside `p.snow`. Then the existing `rail.test.tsx:626` assertion (`'proposed:build refused'`, which has no `held`) stays exactly as it is, and the new held case asserts the whole line. Never append it to the live readings: a running card's `fixing round 2 of 3` already says the depth.

4. **Card.** `page.tsx:335` passes `held` built from `card.restarts`, `card.restartsOf` and the project's `PassLimitsView`. The board already has `limits` and needs to reach the card render. Check how `limits` reaches `page.tsx` before adding a prop path.

5. **The pill (`page.tsx:287-298`).** Drop `card.arm` from the pill **only on a card whose rail carries the held line**: `card.progress && card.column !== 'running'`. Keep `attempt N` everywhere. It counts claims, not rounds or restarts, and the comment at `page.tsx:275-279` says why the two are different numbers. Keep the arm on queued cards: after a restart, `PassRestarted` is followed by a release to `queued` (`task-view.ts:396-399`), and those cards draw no rail. Update the pill's comment to say the arm moved and where.

6. **Page.**
   - `standing.tsx:294` becomes `(state === 'running' || state === 'blocked') && progress !== null`, with `live={state === 'running'}`. The comment there (*"`live`, because the state is `running`"*) needs rewriting, not just the condition.
   - The page needs the recipe's limits for a blocked item. `planFor` (`task.ts:1381`) already calls `projectFilter`. Have it return `{ plan, limits }`, and call it when `standing.state === 'blocked'` as well (`task.ts:1492`).
   - That makes `plan !== undefined` true for a blocked item, so `task.ts:1504` refolds the last attempt with the plan. That is harmless: the plan only bounds a phase in flight, and `over` stays `landed`.
   - Expose the restart count and the last `of` on the standing (`task.ts:680-700`) from `item.restarts`. Do not refold the work item.
   - Pass `held` into `Rail` from `Standing`.

## Tests

- **`rail.test.tsx`:** a held case. Use the `refused()` stream (`rail.test.tsx:131`) plus a `FixRequested`/`FixApplied` pair and a `FixDeclined`, with `held` given, and assert the whole sentence. Add one case where the ceiling falls back to the recipe (no `FixRequested`). Add one case for the card: on a waiting card with `card.arm` set, the pill no longer contains `restart`; on a queued card it still does.
- **`task-page.test.tsx` snapshot:** only the blocked snapshot's `why:` line should change, with the rail's labels and the held line coming before `proposed / review 1 line…`. The running snapshot must stay byte-identical. Read the diff of `__snapshots__/task-page.test.tsx.snap` before accepting `-u`. A change to any rank other than `why`, or to the running export, is a bug in the change, not a snapshot to update.

Everything above is in the unit half. Nothing here needs `pnpm test:integration`.

## What would settle behaviour in the log

Whether a held run's stream actually carries `FixDeclined` as its last round event (rather than ending at a `FixApplied`) is a fact about the log, not something I could check from here. `FixDeclined.round` on the run stream, beside the item's `WorkItemBlocked` seq, settles it. The fold takes the highest of the two events for exactly this reason, so either answer reads correctly.
