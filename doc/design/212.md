# Design: #212 — `lingtai doctor` checks that this Node can build a SEA

## Two corrections to the ticket

- **The pin is `.node-version`, not `.nvmrc`.** There is no `.nvmrc` in the tree. `.node-version` says `26`, and `runDoctor` already reads it at `apps/cli/src/doctor.ts:2318-2324`. It passes the contents to `nodeRow` (`doctor.ts:2248`), which compares major versions only. Leave both files and `engines` (`package.json:8-10`, `">=26"`) alone, as the ticket says.
- **`build.test.ts` is at `apps/release/integration/build.test.ts`**, not `test/`. Since #225 it belongs to the integration half, so a broken `--build-sea` no longer turns `pnpm test` red. This ticket is still worth doing, because `release.yml`, `pnpm binary` and the post-merge integration run all still depend on it.

## What actually decides "can build" today, and why it is wrong

`apps/release/src/binary.ts:47-51`:

```ts
/** Whether this Node can build a SEA without a separate injector. */
export function canBuildSea(version: string = process.versions.node): boolean {
  const [major = 0, minor = 0] = version.split('.').map(Number)
  return major > 25 || (major === 25 && minor >= 5)
}
```

This is a version comparison, which the ticket shows cannot answer the question: Homebrew's 26.7.0 passes it. `build.test.ts:48` uses it (`const sea = canBuildSea()`) to choose the skip names at `:88` and `:124` (`(skipped: node --build-sea needs Node 25.5)`). `buildBinary` uses it as its guard at `binary.ts:56`. So on Homebrew's Node the tests run, and they fail inside `run()` (`binary.ts:93-98`) with a bare `exited 1`.

**Replace it everywhere with one probe that actually runs the build.** Delete `canBuildSea`; do not leave a version-based copy beside the probe.

## Where the probe lives

Put it in a new file, `apps/cli/src/sea-build.ts`. `apps/cli` must not import `apps/release`, and the import already runs the other way: `binary.ts:30` has `import { platformName } from '../../cli/src/version.ts'`. So `binary.ts` imports the probe from the CLI the same way, and `doctor.ts` imports it from next door.

The file has two layers:

1. **`classifySeaBuild(status: number | null, stderr: string, error?: Error)`: pure, and unit-tested.** It returns something like:
   ```ts
   { can: true }
   | { can: false; why: 'disabled' | 'unsupported' | 'failed'; said: string }
   ```
   - `disabled` matches `/single executable application is disabled/i`.
   - `unsupported` matches `/bad option: --build-sea/`.
   - `failed` covers any other non-zero exit or a spawn error.
   - `said` is the first line of stderr, so the row can quote what Node actually said.

   Use the two strings measured in the ticket as the test inputs, verbatim.
2. **`probeSeaBuild(node = process.execPath): SeaProbe`: the effectful part, never called by a unit test.** It:
   - makes a `mkdtempSync` directory and writes a one-line `main.js` plus a config with `useCodeCache: false` and `useSnapshot: false` (the same choices `binary.ts:63-79` makes);
   - runs `spawnSync(node, ['--build-sea', config], { encoding: 'utf8', timeout: 30_000 })`;
   - classifies the result, then `rmSync`s the directory in a `finally`.

   Make it synchronous, so `build.test.ts` can still decide its skips at module load, as `:48` does now.

Use `process.execPath`, not `node` from PATH. `binary.ts:82` builds with `process.execPath`, so the probe asks the same interpreter that would do the build. The row's detail names that path, which also answers the "three Nodes on this machine" question.

The output is a full copy of the Node binary (roughly 100 MB) written into a temporary directory and removed straight away. That does not break the rule at the top of `doctor.ts` (*"It never writes"*, `doctor.ts:24-30`), which is about the event log. Add one sentence saying so beside the row, so the next reader does not have to argue it again.

## The row in `doctor.ts`

- Add a pure function, `seaRow(node: string, version: string, probe: SeaProbe): CheckResult`, named `'node: can build a single executable'`. Shape it like `nodeRow`, whose docstring explains why: *"The read stays outside this function… keeps this a unit test that can call it directly."*
  - `ok`: names the path and the version.
  - `fail` for `disabled`: names the interpreter path and its version, quotes `said`, says this Node build has SEA compiled out and that Homebrew's `node` ships that way, and gives the remedy: `brew unlink node`, or put a Node with SEA first on PATH (`mise use node@26`).
  - `fail` for `unsupported`: says `--build-sea` needs 25.5 or later and names `.node-version`.
  - `fail` for `failed`: quotes `said`.
- **It is a `fail` and carries no `restartAnswers`**, so it gates `lingtai restart` (`gatingFailures`, `apps/cli/src/restart.ts:1433-1435`). That follows the precedent at `doctor.ts:2265-2268`: *"a daemon started on this Node is a daemon on a version CI no longer tests, so this should gate `lingtai restart`"*.
- **In `runDoctor` it goes into the existing `isSea()` fork at `doctor.ts:2309`.**
  - In the SEA branch, push a `skip`. There, `process.execPath` is the `lingtai` binary rather than a Node, and a SEA passes `--build-sea` to the application as an argument. The detail should say that building a binary is a checkout's job and the binary does not do it.
  - In the `else` branch, push the row right after `nodeRow`.
  - This is the only `skip`. A spawn error or a timeout is a `fail` (`failed`), not a skip.

## The seam, and the trap in it

Add `sea: () => SeaProbe` to `DoctorReach` (`doctor.ts:888-905`), and call it in `runDoctor` as `reach.sea?.() ?? probeSeaBuild()`. This matches how `runtimes` is read at `doctor.ts:2071`.

**Unit tests already call `runDoctor`.** They are `apps/cli/unit/doctor.test.ts:93,115,128,146` and `apps/cli/unit/log-predates-hold.test.ts:148,165`. Both build a full `DoctorReach` literal (`doctor.test.ts:64-82`). Making `sea` a **required** key of `DoctorReach` is what keeps those six calls from spawning Node and writing 100 MB per call inside the unit half: `pnpm typecheck` fails until each literal has `sea: () => ({ can: true })`. Do not make the key optional on the interface to save editing those two files.

`apps/cli/integration/doctor.test.ts` passes no stand-in, so it will really run the probe. That is correct (it is integration), and on a Homebrew-Node machine its "is green" test will go red, which is the truth.

## The release side

- **`build.test.ts:48`:** `const sea = probeSeaBuild()`. The describe names at `:88` and `:124` become `` `(skipped: ${sea.said})` `` when `!sea.can`, so the skip reports what this Node said. The `it.runIf(sea && …)` at `:112` becomes `sea.can && …`. Update the file comment at `:36-38`.
- **`buildBinary`:** delete the pre-check at `binary.ts:56-58` rather than replacing it with a second probe, because a second probe means a second copy of Node on every build. When `run(process.execPath, ['--build-sea', config])` fails, pass its status and stderr through `classifySeaBuild` and throw that sentence instead of the bare `exited 1`. `run()` therefore needs to return the result, or a variant of it does.
- Fix the header at `binary.ts:12-14` (*"`node --build-sea` (Node 25.5) does the copy"*): the version is necessary but not sufficient.
