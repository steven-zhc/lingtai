# Design note — #1208: a red base belongs to the project, the queue compares shas, and the next attempt checks first

There are five pieces: one pure function, one Effect, one pass-over, one early check inside the attempt, and one new release cause. The ticket's Fix list is right. What follows are the decisions it leaves open, each worked out against the code.

## 1. `BaseRed` is a `RequeueCause`, not only a `ReleaseCause`

The ticket says `ReleaseCause` (`events.ts:284`) gains `BaseRed`. That alone does not type-check:
- `runAttempt` ends a pass `AttemptEnd`, which is `Extract<AttemptNext, { _tag: 'Requeued' | … }>` (`run-attempt.ts:1247`).
- `Requeued`'s cause is `RequeueCause` (`packages/domain/src/attempt-next.ts:69-73`). Today that holds only `NewAttempt | NeverStarted`.

So the change goes like this:
- Add the variant to `RequeueCause` in `attempt-next.ts`. `ReleaseCause` then gets it through its spread, `...RequeueCause.options` (`events.ts:285`). The comment at `events.ts:280-282` gives the reason: *"spread in rather than redeclared, so the two schemas cannot say two different things about one tag."*
- Its fields are the ticket's: `runId`, `headSha`, `base`, `baseSha`, `command`, `boundary`. There is no `evidence`.
- `outcomeOf` already maps `Requeued` to `failed` (`run-attempt.ts:1348`), so it needs no change.
- In `conduct.ts`, the release for this end sits beside the two `NewAttempt` releases (`conduct.ts:5889`, `:5918`): `release(why, { _tag: 'BaseRed', … })`.
- `headSha` is the pass's final `onSha`, published first like every ending that did not land.
- Check the `restarted` test at `conduct.ts:5689`. It keys on `NewAttempt` only, so a `BaseRed` end must not reach the `NewAttempt` paths.

Codec bumps:
- The ticket reducer keeps the cause in `claims` (`endClaim(…, { cause: d.cause })`, `packages/domain/src/ticket.ts:572`), so the ticket codec goes from `version: 3` to 4 (`ticket-codec.ts:173`).
- If a run snapshot encodes `AttemptNext`, raise `run-codec.ts:209` (`version: 12`) too. Grep `run-codec.ts` for where `AttemptNext` or `RequeueCause` is used, and raise it only if it is.

## 2. The base-state function maps a command back to an action name

`baseIsRed` is asked for an **action name**, not a command: `baseCheckQuestion` does `recipe.steps.build.find((a) => a.name === input.action)` and answers `notBuilt: 'not a run: action in the recipe'` otherwise (`base-check.ts:436-437`). `BaseChecked` stores the `run:` **string** (`command: action.run`, `base-check.ts:479`).

So the pure function in `domain` takes both the events and the recipe's build runs, as plain data, because `@lingtai/domain` has no `@lingtai/*` dependency:

```
baseStateOf(events: readonly Envelope[], builds: readonly { name: string; run: string }[])
  → { red: { action, command, baseSha, boundary, runId } } | { notRed: 'none' | 'green' | 'not-built' }
```

- Put it beside `reduceIntegration` in `packages/domain/src/integration.ts:124`; it reads the same stream.
- The newest `BaseChecked` decides. If it is red but no build action has `run === command`, the answer is `not-built`, which is not red. The lookup that fails is the same test that answers *a command the recipe no longer builds*, so there is one rule, not two.
- `boundary` defaults to `'unsandboxed'` when missing, as `lookup` does (`base-check.ts:169`, `UNSANDBOXED`).

## 3. Reading the base's head goes through the `Repo` port

`RepoPort` has `provision`, `remove`, `git` and `integrate` and nothing that fetches (`packages/conductor/src/ports.ts:49-62`). Do not call `ensureMirrorEffect` or `mirrorBranchShaEffect` directly from `schedule.ts`; that would make the look untestable at unit level.

- Add one method, `baseHead(options) → Effect<{ at: string } | { unreadable: string }>`.
- Implement it in the real layer as `ensureMirrorEffect` (`packages/repo/src/worktree.ts:107`) followed by `mirrorBranchShaEffect` (`mirror.ts:55`) on `refs/heads/<base>`. The ref form is the one `mirrorBranchShaEffect`'s `for-each-ref` call takes (`mirror.ts:62`).
- `{ missing: true }`, and any answer that is not 40 hex characters, count as `unreadable`.
- Every fake `RepoPort` in `unit/` gains the method. That is the only cost to other tests.

The look already runs with `Repo` in context: `schedule.ts` starts `runOnce` through `Effect.runPromiseWith(runtime!)`, and `runOnce` asks for `Repo` (`ports.ts:146`).

## 4. One Effect answers the project's state; one pure step passes tickets over

Make `base-red.ts` in `packages/conductor/src`:
- **`projectBaseRed({ store, project, base, recipe, ... })`** is an Effect:
  1. Read `integrationStream(project, base)` (`streams.ts:150`) and apply §2.
  2. Only if the answer is red, ask `Repo.baseHead`.
  3. Answer one of `clear`, `{ red, head }` with head equal to `baseSha`, `{ moved }`, or `{ unreadable: why }`. A failed stream read and a failed fetch both become `unreadable`, never `clear`.
- **`passOverBaseRed(offered, answer)`** is pure. For `red` (head equal) and for `unreadable`, it moves every entry in `offered.runnable` into `offered.skipped` with `reason: 'base-red'`. It also returns one line for the look:
  - ``base-red: `<command>` failed on <sha7>; <n> passed over until <base> moves``
  - ``base-red: <why> — <n> passed over this look``

  Then `passedOver` (`discover.ts:384-393`) counts `base-red N` with no change of its own. That covers the `lingtai status` item in Done when.

Do **not** put this inside `runnableNowEffect`. Its doc says *"Nothing is appended and nothing is stored … Ask GitHub what it is offering"* (`discover.ts:410-420`), and it is GitHub-only on purpose.

Where it is applied:
- **`schedule.ts:233`**, the daemon's look: after `runnableNowEffect` and before `selectRunnable`. Log the line once per look, as `dependenciesUnread` is logged once.
- **`apps/cli/src/conduct.ts:524`**, the `now` path: the same place. A `now` on a base-red ticket then matches nothing, so the request stays pending. That is the right outcome, because it is consumed when the ticket is claimed later. But it must not be silent (#95 is the silent version, described at `:514-522`). When the requested issue is among the base-red skipped, say ``#N not started — base-red: `<command>` on <sha7>``.
- **`apps/cli/src/status.ts:436`**, for the count. Status is a read, so here call `mirrorBranchShaEffect` **without** `ensureMirrorEffect`. It shows the head the last look fetched, never a fetch of its own. Say so in a comment.
- **Not** `conduct.ts:2990` (`runOnce`'s `only` re-read). That would be a second fetch per attempt, and the check inside the attempt (§5) is the guard against that race anyway.

## 5. The first check lives inside `runAttempt`, between `admit` and `prepared`

`conduct.ts` reads `projectBaseRed`'s **log half only** (no fetch) once, after the claim, for a fresh claim (`continuation === null`). It does not take the answer from the look:
- The look's answer is a moment old.
- `now` does not go through the look.
- Two passes (0122) each claim on their own.

If that read is red, `conduct.ts` hands `runAttempt` a new option, `baseFirst: { action }`, taken from §2's `action`.

In `runAttempt` the walk starts at `admit` (`run-attempt.ts:1452`). When the `admit` visit has passed and `options.baseFirst` is set:
- Ask `options.baseIsRed({ action, mergedOnto: null })`. It already resolves the base commit as `worktree?.baseSha` (`conduct.ts:4060`), which `admit` has just cut (`conduct.ts:3248`).
- **`red`** → end `Requeued{ BaseRed }` with no `prepared` visit and no agent step. The record matches on sha, command and boundary, so an unchanged base is answered from the log (`base-check.ts:164-170`).
- **`notRed`** (green, unknown or not-built) → go on to `prepared`. Unknown is not green, but it is not red either. The guard at `proposed` (`:1723-1731`) asks again later.

The check is not a step and is not recorded as a visit, so `redoStep` cannot repeat it. A continuation does not get it:
- A continuation re-cuts at `onSha`, not at the base (`conduct.ts:3232-3240`).
- Its `baseIsRed` commit is `continuation.diffBaseSha` (`conduct.ts:4060`), which the red record says nothing about.
- A person decided it.

`inFlight` (`base-check.ts:146`) already shares one run between attempts claimed in the same look.

## 6. The `proposed` guard ends the same way

`run-attempt.ts:1732-1759` builds `ProposedEscalated{ because: BaseRed }` and ends `WaitOnPerson`. Replace that end with the same `Requeued{ BaseRed }` as in §5. Keep the `record(...)` and the `routes.push(...)`, so the visit and its `why` (`baseRedText`) still say what happened. The stored route is a `Selected` reply for an offer that gains one candidate, `base-red`, whose `next` is the `Requeued{ BaseRed }` release, so replaying `routeNext` on it answers the release and not a wait. This build-refusal path runs after an implementation; the first check (§5) runs before any agent. That changes `a-base-that-is-red-buys-no-round.test.ts`'s expected end, which is the one test change the ticket accepts.

Do not delete the `BaseRed` variant of `ProposedEscalated.because`. Old logs carry it, and the board renders it.

## 7. The backoff: a `BaseRed` release resets `lastAttemptAt` to `null`

`heldUntil` reads only `lastAttemptAt` and `repairPending` (`queue.ts:148-153`). It has three readers:
- `selectRunnable`, through `task_view.last_attempt_at` (`projector/src/task-view.ts:348`, from the reducer);
- `lingtai status` (`status.ts:486`);
- the board, from `reduceTicket(own).lastAttemptAt` (`apps/board/src/lib/queued.ts:247`).

Make the one change in the ticket reducer's `TicketReleased` case (`ticket.ts:558`): when the cause is `BaseRed`, set `lastAttemptAt: null`. All three readers then agree, with no new column and no projection migration.

Why `null` is correct and not a loss: this ticket was just *claimed*. So whatever earlier attempt's backoff window existed had already run out, or a person had jumped it with `now`. The attempt this would make the backoff count is one the base's state ended, either before any agent ran (§5) or after a build refusal the base shares (§6); neither says anything about the ticket.

Readers of `lastAttemptAt` that are not the backoff:
- the approval guard at `task-view.ts:456`, which only matters while `blocked`, and a release leaves the ticket in `backlog`;
- `queued-estimate.ts:50`, which counts running attempts only.

Neither sees a released ticket. `task_view` recomputes its columns on every event for a row that exists (`task-view.ts:720-736`), so no projection rebuild is needed.

## Unit-level claims that stand in

Nothing here needs `pnpm test:integration`. The fetch is behind `Repo.baseHead`, and the log is `createMemoryEventStore()`. The Done-when tests map like this:

| Test | Where it is written |
|---|---|
| Base-state function (none, green, red, red then green, red with a command the recipe no longer builds) | domain `unit/`, on plain arrays |
| Look tests (head equal, head moved, fetch failed, state green with the mirror not read) | `passOverBaseRed` plus `projectBaseRed` with a fake `RepoPort` whose `baseHead` counts calls |
| Attempt tests | the shape of `a-base-that-is-red-buys-no-round.test.ts`, with `baseFirst` set and `baseIsRed` faked |
| Release cause | reducer test: `TicketReleased{ BaseRed }` leaves `lastAttemptAt === null` |

The real `baseHead` is three git calls inside the already-tested repo package. Its only check before the merge is `tsc`, and that is the line to say out loud in the commit.
