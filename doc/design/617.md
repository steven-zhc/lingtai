# Design: #617 — grouped `lingtai --help`, and `lingtai <command> --help` for every command

## Where it goes

**A new module, `apps/cli/src/commands.ts`, holds one definition per command, and imports no library.** It is the same kind of file as `migrated.ts`, which says *"No library imports, on purpose: `entry.ts` runs on import and a test cannot load it, so the decision is here, where a unit test can"* (`migrated.ts:4-5`). Each definition carries what 0121 §6 lists:

- `name`
- `group`: `'everyday' | 'waiting on you' | 'daemon' | 'install and upkeep'`
- `task`: one line
- `effect`: `'reads' | 'changes'`
- `usage`: lines
- `examples`: one or two

Export `COMMANDS` and `type CommandName = (typeof COMMANDS)[number]['name']`. This table is what #545 will generate `doc/cli.md` from. **Do not build that generator here**: `doc/cli.md` and the test that compares it with the checked-in copy are #545's.

**The groups are 0121 §7's table, copied exactly.** It covers 30 commands:
- everyday: 10
- waiting on you: 6
- daemon: 7
- install and upkeep: 7

That is exactly the set the code dispatches today:
- 27 `case` labels in `main` (`lingtai.ts:1257-1546`: `add` … `projection`, `version`, `init`)
- `upgrade`, `rollback` and `uninstall` from `INSTALL_COMMANDS` (`install.ts:56`)

`help` is not a command in the table. It is the help route itself.

**A second module, `apps/cli/src/help.ts`, renders help.** It imports only `commands.ts`, `output.ts` and `@lingtai/env/colour`. It exports:
- `rootHelp(): string`
- `commandHelp(name): string`
- `helpCommand(argv): number`, which prints and returns the exit code

Rendering returns strings, as `output.ts:5` already requires: *"Rendering returns strings and printing is separate, so the module is tested with no process."* Use `heading`, `section` and `keyValues`/`table` from `output.ts:68-88`. Choose no colour here, because plain mode is `coloured()`'s decision (0121 §3).

## The route: help is answered in `entry.ts`, before `init.ts`, `install.ts` or `lingtai.ts`

0121 §8: *"`help`, `--help` and `<command> --help` are answered from the command definitions alone, before `lingtai.ts` is imported … `--help` anywhere in the arguments prints that command's help, does nothing else, and exits 0."*

Add a `'help'` value to `Route` in `migrated.ts:14`, and order `routeOf`'s checks like this:

1. **Migrated commands first, `--help` included.** `version --help` stays `'effect'` so `@effect/cli` generates it, as the ticket asks. `migrated.test.ts` already pins `['version', '--help']` → `effect`, so keep that row.
2. **Then `help`.** It applies when `argv` is empty, or `argv[0]` is `help`/`--help`/`-h`, or any element is exactly `--help` or `-h`. Compare whole elements only. `ask … "what about --help"` is one element that is not equal to `--help`, so it does not count.
3. Then `init`, `install` and `lingtai`, as today.

The rows `[[], 'lingtai']` and `[['--help'], 'lingtai']` in `migrated.test.ts` change to `'help'`, on purpose. #616's design deferred this to "a later ticket", and this is that ticket.

In `entry.ts`, add a branch for the `'help'` route that calls `helpCommand(argv)`. A static import of `help.ts` is fine. Its graph is the colour module and two plain files, and `world.ts` is already imported statically for the same reason (`entry.ts:23-24`: *"Neither reaches the log"*). Apply `--no-color` with `applyNoColor()` (`output.ts:131`) before rendering, as `cli.ts:59` does.

**What this fixes for #549.** `init.ts:305` answers any unknown flag with `` `${USAGE} — no ${name}` `` and exit 2. Once `init --help` is routed to help, `init.ts` never sees it. `upgrade --help` and `uninstall --help` are fixed the same way: today `install.ts:460` and `install.ts:566` refuse them with `— no --help`. Leave those refusals in place for every other unknown flag.

**Exit codes:**
- `help`, `--help`, `-h` and `<cmd> --help` exit 0.
- An empty `argv` prints the root help and keeps exit **2**, as `lingtai.ts:1553` does today (`command === undefined ? 2 : 0`). Running nothing is not a question, and a script that runs `lingtai` with no command should keep failing.
- `<unknown> --help`, for example `lingtai bogus --help`, prints `unknown command "bogus"` and the root help to stderr and exits 2. This matches `lingtai.ts:1556`.

## The dispatcher test, and why it is a type as well as a test

`lingtai.ts` cannot be imported by a test, because it calls `main()` on import (`lingtai.ts:1584`, and `add.ts`'s move for #435 exists for exactly this reason). A test therefore cannot read the `switch` at runtime. So split the claim in two:

- **Make the compiler hold `main` to `COMMANDS`.** Narrow `command` with an `isCommand` guard from `commands.ts`, and send unknown strings to the existing unknown-command branch. Then `switch` over `CommandName`, with `default: return command satisfies never`.
  - A definition with no `case` fails `pnpm typecheck` at `satisfies never`.
  - A `case 'foo'` with no definition fails with TS2678 (*not comparable*).
  - The switch then has to cover `upgrade`, `rollback` and `uninstall`. Answer them the way `init` is answered at `lingtai.ts:1543-1547`: *"runs from the entry, before the log is loaded"*. They are reached only by a process started on `lingtai.ts` directly.
- **A unit test, `apps/cli/unit/help.test.ts`, holds `COMMANDS` to the routes.** It checks:
  - every definition's name, routed alone, reaches a route that answers it: `MIGRATED_COMMANDS` → `effect`, `init` → `init`, the install three → `install`, everything else → `lingtai`;
  - `INSTALL_ONLY` in `migrated.ts:12` equals `INSTALL_COMMANDS`;
  - every name appears exactly once in `rootHelp()`, under its own group's heading;
  - the four groups' members are exactly 0121 §7's table. Write that table into the test literally, so a change to the groups has to be made in two places.

`help` itself is answered by the route, not by `COMMANDS`, so it is not in the table. Remove its `case 'help'`, `'--help'` and `'-h'` labels from `main`, or keep them typed outside `CommandName`. Either way, they are no longer how `lingtai --help` gets answered.

## `USAGE` is deleted, and its text moves into the definitions

0121's Consequences: *"The hand-written `USAGE` in `lingtai.ts` is deleted when this is built, not edited."* Each `lingtai <cmd> …` block of `USAGE` (`lingtai.ts:111-408`), with the flag lines under it, becomes that command's `usage`. Its first clause becomes the seed for `task`.

The four places that print `USAGE` change:

| Where | Today | After |
|---|---|---|
| `lingtai.ts:449` | `projection` with no or a bad subcommand prints `USAGE`, exit 2 | `commandHelp('projection')` to stderr, exit 2 |
| `lingtai.ts:1158-1160` | `controlCommand`'s `--help` guard | Keep the guard: it is defence for a process started on `lingtai.ts` directly, where the route did not run. Print `commandHelp(verb)` |
| `lingtai.ts:1553` | no command, or `help` | `rootHelp()` |
| `lingtai.ts:1556` | unknown command | `rootHelp()` |

Leave the `lingtai.ts:5` *"Deliberately hand-rolled argument parsing"* comment alone. It is still true of every command except `version`, and 0121 deletes it when the parsing moves, which is not this ticket.

**The usage text has to be reflowed, not moved as it is.** Ten of `USAGE`'s lines are 81 to 84 columns wide, for example:
- `lingtai add [<owner>/<repo>]      onboard a GitHub repository the App is installed` is 84.
- the `--rounds` and `ticket list` lines are 81 and 82.

They also hang their prose at column 34, beside a `lingtai <cmd>` prefix that per-command help does not need. Under `Usage`, put the invocation line on its own line, with the prose and flags beneath it at a small fixed indent. 0121 §4 says *"A line is never wrapped by the command"*, so every line is short at the source. The test asserts `width(line) <= 80` (`output.ts:45`) for every line of `rootHelp()` and of each `commandHelp(name)`.

**`projection`'s help has to name the projections.** `USAGE` ended with `Projections: ${PROJECTIONS.map((p) => p.name).join(', ')}`. The comment at `lingtai.ts:415-417` depends on that: *"a projection missing from it is missing from `--help` too."* `commands.ts` cannot import `PROJECTIONS`, which lives in `lingtai.ts`, or `@lingtai/projector` without leaving the light import graph. So write the three names as a literal in the definition. In the unit test, import `taskViewProjection`, `backlogProjection` and `spendProjection` from `@lingtai/projector`, as `lingtai.ts:48` does, and assert that their names equal the literal. Update the `lingtai.ts:415-417` comment to point at that test.

## What the two help screens look like

**Root help** is a heading, then four sections in 0121 §7's order. Each section is a `keyValues` block of `name  task`, one line per command. The longest name is `grant-fix-round`, at 15 characters. With a 2-space indent and a 2-space gap, that leaves about 60 columns for `task`, so every `task` must fit there: the test above catches one that doesn't. The help ends with one `next:` line, as 0121 §1 requires: `next: lingtai <command> --help`.

**`lingtai <command> --help`** prints:
1. a heading: `lingtai <name>` and its task
2. a `Usage` section: the reflowed usage and flag lines
3. a `reads` or `changes` line
4. an `Examples` section

The ticket asks for "usage, flags and an example". The flags stay inside `Usage`, under the form they belong to, because `backlog`, `ticket`, `board`, `env` and `service` have subforms whose flags differ. **One help per top-level command; no subcommand help.** `lingtai board start --help` prints `board`'s help, which already lists `start`.

Examples are new text. Write one or two real invocations per command and take the flags from the usage text. Don't invent a flag.

**`version`** is the exception. Its per-command help is `@effect/cli`'s. Give the `version` command in `cli.ts:17` its `task` from `commands.ts` with `Command.withDescription`, so the two cannot drift. The root listing still includes `version` from `COMMANDS`.

## Plain, piped, no project, no network

- **Plain mode.** Colour comes only from `output.ts`'s `paint` calls, so `NO_COLOR`, `TERM=dumb` and a non-TTY stream are handled by `coloured()`. In the test, render under `NO_COLOR=1` and assert there is no `\u001b`. Render again under `FORCE_COLOR=1` and assert that `stripColour` of the output equals the plain render, which is 0121 §3's *"the same text with no escape codes — not a different layout"*. Restore `process.env` after each test, as `version-cli.test.ts` does.
- **No project and no network.** The unit claim is the import graph: `help.ts` → `commands.ts`, `output.ts`, `@lingtai/env/colour`, and nothing else. The test calls `helpCommand(['init', '--help'])` and `helpCommand(['status', '--help'])` under `HOME=/nonexistent`, captures stdout as `version-cli.test.ts:7-13` does, and asserts:
  - exit 0
  - the text contains `lingtai init`
  - the text does not contain `no --help` (#549)

  A spawned `lingtai init --help` would be a process, so it is integration and cannot run in the pass. Say so in the PR, and run `pnpm lingtai init --help; echo $?` and `pnpm lingtai --help | cat` by hand once.

## Tests, all in `apps/cli/unit/`

- `help.test.ts`: the route/`COMMANDS` equality, the four groups, every name exactly once in the root help, the projection names, 80 columns, plain under `NO_COLOR` and the same text under `FORCE_COLOR`, and `init`/`upgrade`/`uninstall --help` exiting 0.
- `migrated.test.ts`: the new `'help'` rows. Add `['init', '--help']`, `['upgrade', '--help']`, `['status', '--help']`, `['shutdown', '-h']` and `['board', 'start', '--help']` → `help`. Add `['ask', 'p', '--issue', '1', 'what --help']` → `lingtai`, and keep `['version', '--help']` → `effect`.

Finish with `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` (this is where the dispatcher's `satisfies never` is checked) and `HOME=/nonexistent pnpm test`.
