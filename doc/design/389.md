# #389: design note

## The facts the shape depends on

- **Reconcile is not on the loop.** `reconcile(` has one caller, `apps/cli/src/lingtai.ts:739`, and `clientsForProjects` also has one, `lingtai.ts:746`. Both run once, when the daemon starts, before any work is taken. So for this code the transition #148 asks about is *a daemon starts*. A line printed from here cannot repeat every sweep, because nothing on the work loop reaches it. Do not add memory inside the process to dedupe it.
- **The same failure is already recorded when it changes.** `clientsForProjects` resolves with `currentRecipe` (`converge.ts:128`). The pass resolves the same recipe and, when it throws, appends `ProjectRefused` only if it differs from the last one (`conduct.ts:307-321`, `passTransition` at `packages/domain/src/project.ts:174`). That event is defined as *"`PassOutcome.refused` on the log — the catch in `conduct.ts`, and nothing else"* (`events.ts:1990-1991`). **Reconcile must not append `ProjectRefused`.** That would break the definition, and the next pass's `ProjectRecovered` could pair against it.
- **Do not put it in `Reconciled` either.** That is the one existing event that might seem to fit. But `lingtai.ts:751` prints `paint.pass("reconciled N divergence(s)")` over every finding, so a broken recipe would be counted, in green, as something repaired. **No event at all**, as the ticket allows: a log line, plus a doctor row that reads the recipe live.
- **Daemon startup already prints `RECIPE INVALID — <problem> / nothing will be taken from this project`** for this exact failure (`lingtai.ts:736-737` → `describeFilter`, `packages/conductor/src/filter.ts:331`). What nobody says is the second consequence: reconcile will not converge this project's labels, closes or leftover arms (#240). The new line names that consequence and does not repeat the first one.

## 1. `packages/daemon/src/converge.ts`: return the skip; do not log it

`clientsForProjects` returns `{ clients, unresolved: { project: string; problem: string }[] }` instead of the bare map. The `catch` at `:130` pushes `{ project: p.project, problem: <message folded to one line> }`. Fold it the way `filter.ts:310` `oneLine` does, because `RecipeInvalidError` puts one problem per line.

- **Returned, not logged.** The function gets no `log`. A unit test then checks data, not captured stdout.
- **Seams for the test.** Today the function returns empty whenever `hasGitHubApp()` is false (`:117`), and that is always the case under `HOME=/nonexistent`. Add an optional second argument, `{ hasApp?, clientFor?: ClientFor, recipeFor?: RecipeFor }`, using the types at `packages/conductor/src/filter.ts:191,203`. The defaults are today's behaviour: `hasGitHubApp`, `createGitHubClient({auth: githubApp(), …})` and `currentRecipe`.
- **Leave the client-build `catch` at `:122` as it is.** Its comment says *"Named by its absence"*, and `doctor` already covers missing credentials. Widening this change to cover it is a different ticket.
- **Rewrite the doc comment at `:100-112`.** It says *"this project is skipped for the pass instead"*. Make it say the skip is returned to the caller and reported, and that the reason for not falling back to the raw client still stands.

## 2. `apps/cli/src/lingtai.ts:746`: print the skip

Destructure the result. Hand `clients` to `reconcile` exactly as now. Then print one `paint.fail` line per entry, next to reconcile's own output, something like:

`reconcile skipped <project>: its recipe will not resolve — <problem>. Labels, closes and leftover arms are not converged until it does.`

There is no remedy clause and no fallback. That is the ticket's *report, don't repair*.

## 3. `apps/cli/src/doctor.ts`: two rows learn about the skip

Both rows read **one** `projectFilters(projects, recipeClientFor(env))` result. Today `projectRecipes` makes that call (`:1511`). Lift the load and the call into a helper and run it once, before the store branch at about `:2140`. Hand the result to `projectRecipes`, which keeps its `load() === null` → `skip` behaviour. Hand it also to `unconverged`, in both branches (`:2166`, `:2206`), as a `ReadonlyMap<project, problem>` built from `!f.ok` filters. **Do not resolve the recipe a second time.**

- **`unconverged` (`:1358`).** Split the rows by project before the existing comment/computable split. If any rows belong to a project in the map, the row's status is **`fail`**, and the detail names the project and the recipe's problem: *reconcile cannot converge these until the recipe resolves*. The sentence *"The next reconcile recomputes and writes the difference"* (`:1387`) is kept **only** for rows whose project resolves. A report that mixes both says both.
- **To unit-test it, extract the grading as a pure exported function.** `unconverged` is not exported, and its rows come from `LogQueries`. Name it something like `unconvergedRow(rows, titles, unresolved)`, alongside `recipeRow` (`:1556`), which is already tested that way. `unconverged` becomes the read, then a call to it.
- **`recipeRow`'s fail detail (`:1590`).** Append the reconcile consequence to `— nothing will be taken from this project`. The doctor then says it even when the log has no `IssueUpdateFailed` rows for that project, which is the common case.

## 4. `apps/cli/src/status.ts:92-117`: name the ticket source

`filter.recipe` is in scope inside `if (filter.ok)`. Derive a name from `ticketSourceOf(filter.recipe)` (`packages/recipe/src/settings.ts:316`):

- `github` → `GitHub`
- `db` → `the ticket table` (`recipe.ts:1015-1016` calls it *"the `tickets` table on whichever store this machine chose"*)

Use that name in the success line (`from <source>: N eligible`) and the failure line (`(<source> unavailable: … — the queue cannot be listed)`). Fix the comments at `:92`, `:95` and `:97` the same way.

**Extract the two sentences as pure exported functions**, for example `offerLine(source, count, passed)` and `offerFailedLine(source, err)`, and test those. `status()` itself calls `selectRunnable` and `readTasks`, which reach the log, so they are not unit-reachable.

## Tests (all `unit/`)

- **`packages/daemon/unit/` (new file, next to `converge-refs.test.ts`).** Use two projects, with `hasApp: () => true`, a `clientFor` returning a stub, and a `recipeFor` that throws for one project and resolves a `github` recipe for the other.
  - The resolved project gets a client.
  - The other appears in `unresolved` exactly once, with the thrown message.
  - Call it a second time over the same projects: the same single entry comes back, and a `createMemoryEventStore()` handed in nowhere gains no rows.

  That is the honest form of *"a second sweep reports nothing new"*: nothing accumulates, and nothing is written to the log. Say in the test's header comment that reconcile runs once per daemon start (`lingtai.ts:739`), and that the per-transition record of the same failure is the pass's `ProjectRefused`.
- **`apps/cli/unit/doctor.test.ts`.**
  - `unconvergedRow` given a row whose project is unresolved → `fail`, the detail names the project and the problem, and it does not contain `next reconcile recomputes`.
  - The same row with nothing unresolved → `warn` with today's sentence.
  - `recipeRow` on a `!ok` filter mentions reconcile.
- **Status test (new or existing file under `apps/cli/unit/`).** For `db`, neither line contains `GitHub`. For `github`, both still do.

## How it could be checked against the log

This change appends nothing new. The daemon line is console output only. What already exists to check the same failure against is `ProjectRefused { project, detail, ref, codeSha }` on `prj-<project>`, from the pass. Its `detail` should be the same message the new line prints.
