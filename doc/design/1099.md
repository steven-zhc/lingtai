## The one decision the ticket leaves open: the bounded read in `followApproval`

The ticket wants two things that pull against each other inside `followApproval`:

- The `readState` call there must go. The *Done when* `rg` checks `approve.ts`.
- `FollowWorld`'s ports must stay promises, and `approve-outcome.test.ts`'s fakes must not change.

Today the ticket read is handed to `bound`, which is a promise port: `Bound = <T>(op: Promise<T>, ms, signal) => Promise<…>` (`conductor-note.ts:16-20`). It is called as `bound(readState(…), deadline - world.now(), world.signal)` (`approve.ts:96-100`). The tests depend on that read reaching `bound` as a promise:

- `approve-outcome.test.ts:133-136` injects a `bound` that lets the first call (the holder) through and answers `timeout` on the second call, which is the read. It expects `pending`.
- `:195-212` checks that a read rejecting *after* Ctrl+C causes no `unhandledRejection`. `boundReal` handles this today by attaching to `op` before anything can settle (`conductor-note.ts:35`).

**Decision:** `followApproval` becomes an `Effect.gen`. It takes `const ctx = yield* Effect.context<never>()` once, then hands `bound` the promise `Effect.runPromiseWith(ctx)(readThroughSnapshot(world.store, ticketReducer, stream, 'all', { snapshots: world.snapshots }))`. Each call to `bound` is lifted with `Effect.promise`. `bound` never rejects; it settles to `{ ok }`.

- **Why this doesn't break the ratchet:** the ratchet does not count this run. `RUN = /^run[A-Z](?!\w*With$)/` (`packages/domain/unit/effect-ratchet.test.ts:70`), and `:65` says *"A run that starts a fiber of its own. `Effect.runPromiseWith(services)` …"*. CLAUDE.md names `Effect.runPromiseWith(yield* Effect.context())` as the allowed form.
- **Precedent:** `doctor.ts:3319-3321` uses the same form: *"run through the report's own services (`runPromiseWith` is the form the ratchet allows)"*.
- **Error messages stay the same:** `snapshot-state.ts:6-7` says *"`runPromise` rejects with the store's own error (`causeSquash`)"*, and `runPromiseWith` rejects the same way. So `:111`'s `could not read the outcome (store down)` keeps its wording.
- **This is not the `runEffect` dodge the ticket removes from `now.ts`.** That one runs with `Context.empty()` so that a caller's services are thrown away. This one carries the caller's services.

Two other readings exist; don't build either:

- **(a) Replace `bound` around the read with `Effect.timeout` plus an interrupt on `signal`.** That changes the fake at `:135`, and the ticket says the fakes do not change.
- **(b) Keep `readState`.** The *Done when* `rg` forbids it.

The holder read stays `bound(world.holder(), WAIT_MS, world.signal)`, unchanged and lifted the same way. `world.sleep` is lifted with `Effect.promise`.

**What can still go wrong after the approval:** two places, and each keeps the `try/catch` it has today, wrapped around the lifted `bound`:

- A port that *throws synchronously* (`holder: async () => { throw … }` at `:116-121` rejects rather than throws, but a non-async fake could throw).
- `readThroughSnapshot` *failing* inside the run.

Use `Effect.catch` (or `Effect.either`) around each lifted call, mapping to today's `detail`. Use `Effect.promise`, never `lift` or `tryPromise`, for `bound` and `sleep`. They do not reject, and if one ever did, a defect is still squashed and printed (see *Errors* below), not silently swallowed. The function's type is `Effect<Followed>`, with `never` in the error channel. That type is how the code states the ticket's *"nothing after it throws or turns the exit code"*.

The tests call `await followApproval(target, w)`. The ticket allows edits that only run the Effect, so they become `await Effect.runPromise(followApproval(target, w))`.

## The SIGINT listener

`approveVerdict` registers `process.once('SIGINT', onInt)` only after the grant has committed, and removes it in a `finally` (`approve.ts:241-276`). Keep the order:

1. `grant` (an Effect) runs.
2. The refusal and `unscheduled` early returns follow.
3. Then `Effect.acquireUseRelease(register, () => followApproval(…), unregister)`.

The `if (world.signal === undefined)` guard stays inside `register`.

This is a lifetime scope for a listener, not a second decide hold. The decide hold is `approveEffect`'s, at `packages/conductor/src/deciding.ts:20`, and nothing here wraps a verb in another one. `runCli` installs no SIGINT handler that interrupts the main fiber. The only `SIGINT` in `cli.ts` is `:506`, which belongs to another command. So Ctrl+C still reaches `abort` and ends the wait as `stopped waiting …`, as it does today.

## Errors keep their words without any `mapError`

Each conductor verb is `Effect<…, unknown>`, for example:

- `approveEffect` (`packages/conductor/src/approve.ts:104`)
- `requeueEffect` (`:361`)
- `resolveWaitEffect` (`resolve-wait.ts:180`)
- `closeEffect` (`close.ts:129`)
- `askEffect` and `answerEffect` (`ask.ts:68`, `:168`)
- `editBodyAndRequeueEffect` (`edit-body.ts:59`)

Today each one reaches the CLI as the face's `Effect.runPromise` rejection, re-lifted by `lift` (`exit.ts:16`). After this change it is yielded straight into `answerWith`. Either way the failure lands in `orFailed` → `printedBy`, which uses `Effect.catchCause`. It takes the typed error, or `Cause.squash` for a defect, and prints `failed()`'s `err.message` (`exit.ts:38-48`, `:21-28`). So *message, exit 1* is unchanged whether the verb fails or dies.

Do not add a `mapError` or a wrapper error type. A wrapped error would change the printed message, and `answer-cli.test.ts` would not catch it, because it fakes the verdicts.

In `cli.ts`, the dynamic `import()` is lifted with `lift` today (`cli.ts:219`, `:240`, `:269`, `:283`, `:297`, `:311`, `:333`). Keep `lift` there, not the `Effect.promise` the ticket's *The shape* mentions. A failed import then stays a typed failure, exactly as now. Only the second `lift` on each line (`:220`, `:241`, …) goes away.
