# Design: #434, the end of `init`, and a board only when one is asked for

`doc/design/400.md` §*`init`: what moves* gives the shape. This note covers the three things it leaves open: how the unit tests reach a local `init` before #435 lands, what the lazy board does when it is refused, and what the end of each path prints.

## The unit tests do not wait for #435

#434's only blocker is #432, which is closed. The `machine` seam (`InitWorld.machine`, `machineFileFrom`) is **#435's** work, not this ticket's. Do not build it here. A local `init` can already be driven from `unit/` with no file written, because the store can be answered entirely from the environment you hand in:

- **The env:** `world.env = { VITEST: '1', HOME: '/nonexistent', LINGTAI_TEST_SQLITE_PATH: '/nonexistent/log.sqlite' }`, with **no `LINGTAI_HOME`**.
  - `machineFilePath` returns null under `inTest` when there is no `LINGTAI_HOME` (`packages/env/src/index.ts:104-108`).
  - `storeChoice` then answers `sqlite` / `where: 'environment'` from `LINGTAI_TEST_SQLITE_PATH`, but only if `inTest(from)` is true. That check reads the `from` you pass, not `process.env` (`index.ts:573-581`), which is why `VITEST` has to be in the world's env.
- **Do not pass `--store sqlite`.** With no flag, `chooseStore` takes `settled.store === 'sqlite'` → `sqliteChosen`, which only logs (`init.ts:835-839`). Nothing reaches `writeConfig`.
- **What `init` itself still touches on disk** is `existsSync` on `/nonexistent/.lingtai/config.yml`. That happens in `readConfig` (`init.ts:215`) and `describeHome` (`init.ts:548`), and both answer "nothing there". `boardPort` falls back to 17820 because `machineFile`'s path is null. This is the residue #435's seam removes. Leave it alone here.
- **Everything else is already injected:**
  - `chooseFirstProject`'s local branch reads and writes the recipe through `world.files` (`first-project.ts:429-430`).
  - `registerLocal`, `runGit`, `setupReader`, `app`, `projects` and `history` are all `InitWorld` fields.
  - Reuse `unit/first-project.test.ts`'s `mapFiles` / `EMPTY_SETUP_READER` style.
  - Pass `--local <dir> --defaults` with `ask` answering null, so no recipe question needs a script.

Put the tests in `apps/cli/unit/init.test.ts` beside `machineRuntimeRefusal`'s. Done-when 3 (the GitHub branch) is reachable the same way: `app()` answers not configured, and `appeared` / `pressed` are scripted to resolve.

## The lazy board: one start, memoised, and its refusal keeps its own words

Today the board starts unconditionally at `init.ts:453-460`, before `if (askProject)`. Replace that with one local helper, `startBoard()`. It memoises a single promise of `{ url, started: boolean } | { refused }`, so it is `boardAt(port)` first, then `board(port)`, as today, run at most once per run.

- **`port` is still read where it is now** (`init.ts:450`), before the project question. `boardPort` throws on a `board.port` that is not a port (`index.ts:756-768`). Moving that read into the lazy start would let a local `init` succeed on a broken file without a word.
- **`github.boardUrl`** becomes `async () => { const b = await startBoard(); return 'url' in b ? b.url : null }`.
  - **The trap is the null.** `runGithubBranch` turns a null `boardUrl` into *"no board is running here … start one with lingtai init --project github"* (`first-project.ts:583-589`). That is `add`'s sentence, and absurd inside `init`.
  - So when `chooseFirstProject` returns `refused` and the memoised start was `refused`, `init` refuses with today's sentence, *"the board did not start — … lingtai init again continues from here"* (`init.ts:456-459`), and not with `chosen.refused`.
- **The two wizard paths call `startBoard()` themselves.** They are `chosen.app === 'already'` (`init.ts:517-523`) and the listed-projects path with an App configured (`init.ts:529-538`). Each needs its own refusal check, because nothing upstream asked for a URL.
- **The `'made'`, skipped and timed-out outcomes** have already started the board through `boardUrl()`. Read `board.url` from the memo and do not start a second one.

## The end of each path

After the per-path line (`project local — …`, `opened …`, `next, install it …`), every path that returns 0 ends with the same three parts. All of them are written through `world.log`:

1. **The recipe.**
   - **Local:** print `recipePath(chosen.name, home)` (the same `@lingtai/recipe` export `first-project.ts:63` imports), then `await world.files.read(path)` exactly as returned, unpainted. Do not trim it and do not add a prefix to each line. The test compares the logged lines against the bytes in the map files after the run.
   - **If the read returns null**, which a correct branch never does, log that the file could not be read back. Do not crash.
   - **GitHub branch:** no slug, so no recipe. Say the recipe is written when a repository is picked, and that `lingtai add <owner>/<repo>` asks its questions at the terminal.
   - **Listed-projects path** (`askProject === false`): no recipe line at all. The listing above it already names every project.
2. **Doctor.** Call `await world.doctor()` and log what it returns.
   - Wrap the call in try/catch. A doctor that throws logs `doctor did not finish — <message>`, and the run still returns 0. "Never sets the exit code" covers a throw too, not only a warning.
   - The live seam lives in `liveInitWorld`:

     ```ts
     doctor: async () => {
       const { doctorReport, formatReport } = await import('./doctor.ts')
       return formatReport(await doctorReport())
     }
     ```

     These are the two exports at `doctor.ts:2448` and `:2515`. Use no static import of `./doctor.ts` anywhere in `init.ts`, which matters for the reason the header gives at `init.ts:92-95`. No `releaseCheck`.
3. **The board line.** It replaces the one at `init.ts:540-545`, and the memo decides which wording:
   - started this run → today's *"keeps running in this terminal — ctrl-c stops it…"*
   - found already running → today's *"was already running at … — this started none"*
   - never asked for → a new line: *"no board was started — lingtai board starts it"*

   A local run always gets the third.

`entry.ts:39` already sets only `process.exitCode` on 0. A local run that never binds a socket therefore exits on its own, and `entry.ts` needs no change.

## Fixtures that move with it

- `integration/init.test.ts` builds `InitWorld` objects (400.md §*The unit tests*), so it needs a `doctor` field.
- Its board-ordering assertions will no longer match. Update them so `pnpm typecheck` compiles them, but they only run after the merge.
- The three unit tests in Done-when are the claims that stand in for it. The one that is integration-only is the real `install.sh` run exiting with no terminal. The unit-level proof of that is *a local `init` never calls `world.board` or `world.boardAt`*: assert both, not only `board`.
