## Design note for #692: naming today's unknown runs

### The decision that isn't in the ticket: unknown-ness and its reason come from different moments

Today a row counts as unknown when its stored `estimatedUsd` is null (`packages/conductor/src/day-ceiling.ts:59-62`). The `spend` fold set that value when it folded the row, using whatever snapshot it read for that batch: `snapshot ??= ports.snapshot(); estimate = estimateRow(...)` (`packages/projector/src/spend.ts:217-219`). A later fetch writes new prices and then rebuilds the stored estimates (`startRates` hands `rebuildEstimates` to `realRatePorts`, and `refreshRates` calls it after newly priced models are written), but that rebuild can lag or fail before it replaces a row. So a row that was folded as unknown can be priceable by the snapshot read at display time.

**Rule: `daySpend` keeps deciding unknown-ness from the stored `estimatedUsd`, exactly as now. The new function only explains a row already counted unknown; it never decides whether a row is unknown.** If it decided too, the reasons would no longer add up to `unknown`, which is the ticket's first Done-when. This also covers the ticket's #678 check: a row the earliest snapshot row prices has a non-null `estimatedUsd` (the fold used the same `estimateRow`, `rate-card.ts:136-138`), so it never reaches the explainer. Write that test against `estimateRow` → `DayRow` → `daySpend`, not against the explainer alone.

### One per-entry check, shared with `estimateRow`

The ticket's warning is "computed the same way the fold priced the row". Make that hold in the code structure, not by having two loops that are kept in step:

- Pull the body of `estimateRow`'s loop (`rate-card.ts:129-146`) into a private helper in `rate-card.ts`. For one entry it returns either the rate it priced at plus whether that rate was `listed`, or why it failed: `no-usage` (no `model`, or no token field) or `unpriced` (no rate, `withdrawn`, or a null rate for a class the entry has tokens in).
- `estimateRow` and the new `unpricedReason(row, snapshot, card = RATE_CARD): string` both walk entries through that helper in order and stop at the first failure. That matches the edge where a row with two unpriced models is counted under the first.
- Empty `usage` → `'no usage reported'`. An entry failing `no-usage` → `'no usage reported'`. An entry failing `unpriced` → its `entry.model`, which covers the withdrawn-row and null-`cacheRead` edges.
- **The case the fold can't see: no entry fails now.** The snapshot changed after the fold, and which model the fold lacked a price for is not recoverable from the row, so naming one would guess. Return a reason that names no model, `REPRICED_REASON` (`priced since, rebuild pending`), which the rebuild clears. Give this case its own unit test, because it is the one a reviewer will ask about.
- Export it from `@lingtai/domain/rate-card` beside `estimateRow`, not from `index.ts`. The file header gives the reason: *"a price function must stay out of a reducer's reach"* (`rate-card.ts:12-14`).

### Where the snapshot comes from

`daySpend` is pure and has no snapshot today. Give it a third parameter, `snapshot: readonly RateRow[] = []`. It calls `unpricedReason` only on rows it counts as unknown. Add `usage: Usage` to `DayRow` (`day-ceiling.ts:19-24`); `SpendRow` already has it (`packages/projector/src/spend.ts:300`).

Callers pass `readRateSnapshot()`. Under vitest with no `LINGTAI_HOME` it reads empty (`packages/projector/src/rate-snapshot.ts:17-21`), so no test picks up a real snapshot. The callers are:

- `readDaySpend` (`apps/cli/src/day-ceiling.ts:129-132`). This one feeds both `status` and doctor's `spendToday` (`doctor.ts:1539`).
- `readDayReading` (`apps/board/src/lib/day-spend.ts:44`).
- `dayCeilingPause` (`packages/conductor/src/day-ceiling.ts:183`). Use `./rate-snapshot.ts`'s re-export (`packages/conductor/src/rate-snapshot.ts:46`).

The pause's `reason` (`:188`, appended as `ConductorPaused.reason`) now carries the names. That is harmless: `resumedPast` and `liftOwnPause` only test `startsWith(CEILING_REASON)` (`:107`, `:146`).

### The list and the sentence

- Add `DaySpend.unknownWhy: { reason: string; runs: number }[]`. Sort it inside `daySpend`: most runs first, then reason ascending. `'no usage reported'` sorts like any other entry. The list is never capped; capping is only for display.
- `daySpendText` (`day-ceiling.ts:86-95`) appends ` (a ×n, b ×m, c ×k)` right after `${day.unknown} unknown`. With more than three entries it shows the first three, then `, +N more`, where **N counts entries, not runs**. When `unknown === 0` it adds nothing, so `+ 0 unknown` stays as it is. Use `×` (U+00D7), as the ticket's example does.
- The board bar's `short` (`apps/board/src/lib/day-spend.ts:33`) is **not** changed. The ticket names `/spend`, and that page shows `text` (`apps/board/src/app/spend/page.tsx:42`), which picks this up for free. The bar is one line of four objects (#134).
- **Doctor needs no code change.** `spendToday` already puts `daySpendText` in both the `ok` and `warn` details (`doctor.ts:1544-1551`). The level logic stays as it is. Done-when 4 is a test of `spendToday` with an injected `read` that returns a `DaySpend` with `unknownWhy`.

### `status --json`

`StatusReading.spendLine` returns a bare string (`apps/cli/src/status.ts:181`), and `statusJson` copies `report.spend` (`:625`). Make `daySpendLine` return `{ text: string; unknownWhy: DaySpend['unknownWhy'] | null }`. `null` is for the two paths that return no reading: the read failure (`apps/cli/src/day-ceiling.ts:144-146`) and the stall (`:141`).

Change the port's type and `StatusReport` to match, keeping `spend: string` and adding `spendUnknown?`. Then `statusJson` emits `spendUnknown` beside `spend`, and the text render (`status.ts:550`) is unchanged. On a read failure, `spendUnknown` is left out rather than set to `[]`, because `[]` would claim that nothing is unknown. `git grep spendLine` finds only `status.ts`, so no test currently stubs that port.

### Verification

All of this is unit-level. `daySpend`, `daySpendText`, `unpricedReason`, `spendToday` with an injected `read`, and `statusJson` are all pure, so `pnpm test` covers every Done-when and nothing waits on `pnpm test:integration`. Tests that pin today's exact `daySpendText` sentence only change where a row is unknown. Rows built as `DayRow` literals need a `usage` field added, and `[]` keeps their meaning.
