# Design: #621. The six wait-answering commands move to `@effect/cli`, print one verdict, and take `--json`

## The `--json` half contradicts 0121, so 0121 changes in this same PR

All six commands, and `ask` too, are `effect: 'changes'` (`commands.ts:116`, `:236`, `:251`, `:263`, `:275`, `:287`, `:300`). 0121 §5 says *"Every command whose definition says it only reads takes `--json`"*. §6 says *"The `reads`/`changes` marker is what decides whether a command takes `--json`"*. #620 applied that rule and gave `init` and `add` no `--json` (`doc/design/620.md`, first section). Read literally, the ticket's *"each read command takes `--json`"* matches none of the six commands. Its *Want* and *Watch out* still clearly ask for an outcome document carrying the refusal codes. **The ticket wins, and 0121 is edited to say so.** This repository keeps one ADR per topic: *"A decision that changes is an edit to its topic's ADR"* (`doc/README.md:76-77`, and CLAUDE.md agrees). So this is an edit to 0121, not a new file. The *append-only* wording at `doc/README.md:60` belongs to the archive's era. The edit:

- **§5** gains a paragraph. A command that changes state and answers with a verdict takes `--json`. Today that is the *waiting on you* group plus `now`. Its document reports the verdict, not state: `outcome` is `"accepted"` or `"refused"`, and `reason` carries the refusal code where one exists. A refusal is an outcome, not an `error`. The `error` document is still only for "could not run": a usage error, or a handler that threw (`cli.ts:31-37`, `:172-176`).
- **§6.** The sentence about the `reads`/`changes` marker now covers read commands only.
- `commands.ts:24`'s doc comment changes to match. Do not add a third `effect` value. These commands really do change state, and `help.ts:34` should keep saying so.

## Migrate `ask` too

`ask` and `answer` are one function, `decide()` (`ask.ts:28-59`), and one `case` (`lingtai.ts:1074-1090`). 0121 §7 puts `ask` in *waiting on you* alongside the other five. Leaving it on `parseFlags` would mean one module with two output layouts. Migrate it as well, and say in the PR that the ticket did not name it.

## Routing

- `MIGRATED_COMMANDS` (`migrated.ts:9`) gains `approve`, `requeue`, `grant-fix-round`, `close`, `answer`, `ask` and `now`.
- In `lingtai.ts`, delete their `case` bodies (`:1022-1050`, `:1053-1102`). Move their names into the "runs from the entry" group at `:1270-1277`, so `satisfies never` still holds.
- Delete `now`'s branch of `controlCommand` (`:977-985`) and narrow that function's `verb` type. `now` keeps `controlCommand`'s rule: it holds **no** projector (`lingtai.ts:866-869`).
- Add a `migrated.test.ts` row for each command, both plain and with `--help`, as #620 did.
- Nothing here needs `entry.ts`'s `process.exit` special case (`entry.ts:41-43`). `lingtai.ts:1306-1309` also only sets `process.exitCode`, so behaviour does not change.

## Parsing. Keep every hand-written refusal sentence that is an API

In `cli.ts`, the handlers `await import()` their modules, like `status` does (`cli.ts:46-49`). `--issue` becomes `Options.integer`.

| today | after |
|---|---|
| `answer`/`ask`/`close` join every positional after the project into the text (`lingtai.ts:1086`, `:1101`) | `Args.text({ name: 'project' })` and then `Args.text(…).pipe(Args.repeated)`, joined with `' '`. Test both `close lingtai --issue 5 superseded by 9` and `close lingtai superseded --issue 5`. |
| blank text is a handler refusal, exit 2, in its own words (`ask.ts:36-43`, `close.ts:41-43`) | unchanged. An empty `repeated` list reaches the handler as `''`. |
| `approve --reject` gives two named lines and exit 2 (`lingtai.ts:1041-1047`) | declare `reject` as a hidden `Options.boolean` and refuse in the handler with the same two lines. Otherwise it becomes a generic unknown-flag error. |
| `requeue --note` with no value is recorded as `""` (#424, `lingtai.ts:1063-1065`) | in `runCli`, before parsing, **drop** a bare `--note` from `requeue`'s argv. Absent and bare already mean the same `''`. Pin it with a test. |
| `--into-body` / `--if-head` with no value print `--into-body takes text` / `--if-head takes the displayed commit SHA` and exit 2 (`:1029-1031`, `:1059-1061`) | a precheck in `runCli`, next to the `valuelessFlag` one at `cli.ts:163-169`, prints those exact sentences. |
| `now` accepts `--issue <n>` **or** a second positional, as any string (`lingtai.ts:978`) | keep both forms: `Args.text` optional, plus `Options.integer('issue')` optional. A non-integer issue is now refused. Say so in the PR. |

Missing `project` or `--issue` used to print a hand-written usage line and exit 2. It now becomes `@effect/cli`'s usage error and exits 1, as `init` and `add` already do. Name that change in the PR.

## Shape. A value comes back, the wrapper keeps its signature

Add `apps/cli/src/verdict.ts`, which is pure:

```ts
type Verdict = {
  outcome: 'accepted' | 'refused'
  ticketId?: string
  reason?: string
  detail: string
  next?: string
  extra?: Record<string, unknown>
}
renderVerdict(verb: string, v: Verdict): string[]
verdictJson(v: Verdict): Record<string, unknown>
```

- In each command module, split the body out into `<verb>Verdict(options, progress, deps?) → Promise<{ code: number; verdict: Verdict }>`.
- **Keep `approveCommand(options, log)`, `requeueCommand(options, log, deps)` and the rest, with their signatures, returning the exit code.** Each becomes a thin wrapper that renders the verdict through `log`. `apps/cli/integration/ask.test.ts` and `requeue.test.ts` call them with that exact shape. They cannot run inside a pass, so the shape is held by not changing it, and the PR says those files were checked by reading.
- The `cli.ts` handlers call `<verb>Verdict` and then print either `renderVerdict` or `printJson` (`output.ts:115-118`).

**`progress` goes to stdout in text mode and to stderr under `--json`.** Two things write through it:

- `withProjector`'s warnings (`projector.ts:136-158`)
- `approveRun`'s own line, `approved <sha7> by <by> — continues at <step>` (`packages/conductor/src/approve.ts:180`, `:278`)

That line is the only place the sha and the actor appear. It stays in text mode, which counts as a fact kept, and moves to stderr under `--json`. 0121 §5: *"stdout carries exactly one JSON value and nothing else."*

## Reason codes. Keep the ones that exist, and don't make up conductor ones

Only `ApproveResult` and `ResolveWaitResult` carry `reason` (`approve.ts:82-91`, `resolve-wait.ts:152-165`). The outcomes for requeue, answer, close and edit-body are `{ ok, ticketId, detail }` and nothing more (`approve.ts:333`, `ask.ts:31-35`, `close.ts:116-120`, `edit-body.ts:135-141`). The board's actions also consume them.

**Do not add codes to `packages/conductor` in this change.** `reason` is set only where the function returning the outcome names one, and the key is left out rather than set to `null`. Adding it later is additive under 0121 §5 (*"adding a field does not change it"*). Open a follow-up `tech-debt` ticket for requeue, answer and close codes, with `agent:hold`, and cite it in the PR.

The CLI's own refusals do get codes, all of them `outcome: "refused"`:

| code | where |

| `no-project` | `approve.ts:31-34`, `requeue.ts:62-65`, `grant-fix-round.ts:18-20`, `close.ts:46-48`, `ask.ts:45-48` |
| `no-github-app` | `approve.ts:46-50`, `grant-fix-round.ts:27-29`, `close.ts:49-54` |
| `blank` | exit 2: an empty question, answer or reason |

| `not-waiting` | `grant-fix-round.ts:34-40` |

Keep today's exit codes: 0 accepted, 1 refused, 2 for `blank` and `removed-flag`.

## Text. A verdict line, the old sentence beneath it, and `next:` only where it already existed

```
✓ approved ticket-lingtai-617
  continues at merge
```

```
✗ not approved (reason-required)
  <detail, verbatim>
```

- **The glyph:** ✓ `pass` for accepted, ✗ `fail` for refused (`output.ts:63-67`). Amber is not drawn anywhere here (0121 §2).
- **Verdict line:** the verb in the old words (`approved`, `not approved`, `fix round granted`, `fix round refused`, `requested`, and so on), then the ticket id in `muted`.
- **Under it:** the old sentence, `outcome.detail`, indented and **unchanged word for word**. The integration tests assert on `said.join('\n')`: `'back in the queue'`, `'claimed'`, `'withdrawn'`, `'no project named'` (`requeue.test.ts:103`, `:149`, `:165`, `:178`, `ask.test.ts:89`, `:97`, `:120`).
- **`requeue-into-body.test.ts:51` and `:63-…`** match one whole array element. Change them to `join('\n')` containment. The test follows the layout, and the sentence is unchanged.
- **`next:` lines.** Write one only where the old text already named a command. Do not invent advice:
  - approve's unscheduled branch becomes `next: lingtai approve <p> --issue <n>` (`approve.ts:79`)
  - `--reject` becomes `next: lingtai requeue <p> --issue <n>`
  - grant-fix-round's `scheduling failed` gets nothing, because the old text names no command
  - a `detail` that names a command (for example `ask.ts:176`'s `use lingtai requeue …`) stays in the detail line

## Done when, in unit-reachable terms

- **Pure tests in `verdict.test.ts`.** Under `NO_COLOR`, there is one case per command per branch, and each fact the old line printed is asserted:
  - ticketId
  - `continuesAt`
  - `unscheduled`
  - reason code in parentheses
  - detail verbatim
  - `requested <project> #<n>`
- **`--json` shape tests.** One accepted and one refused document per command, for `verdictJson`, plus `JSON.parse` on what `printJson` writes.
- **`runCli` tests.** These use fake handlers, or an exported `Command` factory with the world as a parameter, as #620 suggested. They cover:
  - the bare-`--note` drop
  - the `--into-body` and `--if-head` sentences
  - `--reject`
  - the variadic text in both orders
  - a usage error under `--json` becoming the `usage` error document (`cli.ts:172-176`)
- **`commands.ts` usage lines** gain `[--json] [--no-color]`. Keep `help.test.ts`'s 76-column limit (`commands.ts:10-12`).
- `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck`, `HOME=/nonexistent pnpm test`.
- **Bundle check.** Run `pnpm build`, then `node dist/lingtai.cjs approve --help` and `node dist/lingtai.cjs now --help`.

The parts no unit test reaches are the live `approve()`, `requeue()`, `answer()` and `close()`. They take the file lock (`verbs-accept-refuse.test.ts:10-20`), and the integration files above are out of reach inside a pass. What stands in for them is the unchanged `*Command` signatures and the verbatim detail lines.
