## Design: #975, the lightbox is one solid panel

### Where it goes

The rules all live in `apps/site/src/app/home.css:109-113`, and the work is there. The ticket's two declarations are correct and enough for the background and the width:

- `.shot-box` (`home.css:109`) has `background: transparent`. Change it to `var(--surface)`.
- `.shot-box p` (`home.css:113`) needs `max-width: none`. Today it inherits `p { max-width: var(--measure); }` from `site.css:129`, and `--measure` is `68ch` (`site.css:42`). That inheritance is where the 571px comes from.

### The decision: the caption and the buttons are one sticky footer

The ticket's evidence already answers its "check whether the sticky nav covers the caption". `.shot-nav` is sticky at `y=812` and the caption sits at `y=864`, so the nav covers it. Today the nav is the only sticky element (`home.css:111`, `position: sticky; bottom: 0`), and the `<p>` is an ordinary block above it (`shots.tsx:92-93`). On a full image taller than the dialog, the nav pins to the bottom and slides over the caption.

Build it like this: wrap the `<p>` and the `.shot-nav` div in `shots.tsx` in one element, for example `<div className="shot-foot">`. Move `position: sticky; bottom: 0; background: var(--surface); border-top` from `.shot-nav` onto `.shot-foot`, so the caption and the ← → ✕ row stay stuck together below the image. Don't use either of these instead:

- **Dropping the sticky.** On a tall image the ← → ✕ row would sit below the fold. The Edges ask that the buttons "stay reachable", and they should not depend on scrolling.
- **A second sticky with `bottom: 61px` on the `<p>`.** The 61px is the nav's height added up by hand (8 + 44 + 8 padding and button, plus a 1px border). It breaks silently the next time someone changes the button size.

This is a markup change but not a behaviour change, so it stays within the ticket's "Watch out", which forbids changing `shots.tsx`'s *behaviour*. Keep the dialog's `onClick` and `onKeyDown` (`shots.tsx:81-90`) and the three buttons' handlers exactly as they are; only the wrapper is new. Once the caption is on the full panel width it can drop its own `background` (`home.css:113`), because the footer already supplies one.

### Backdrop click, verified rather than assumed

The dialog closes only when `e.target === box.current` (`shots.tsx:81-83`). A click on `::backdrop` reports the `<dialog>` itself as its target, so that close still works. The new risk is different: any part of the now-solid panel that no child covers would also report the dialog as the target. Such a spot looks like the panel but closes it.

The dialog has `padding: 0` (`home.css:109`) and default fit-content width. The image is `width: 100%; max-width: 1440px` (`home.css:110`), and the footer is a block, so between them they should cover the whole dialog.

- **Check it** at 1440×900 and at a viewport wider than 1440/0.94 ≈ 1532px, where the image hits its 1440 cap. Call `document.elementFromPoint` at a few points inside the panel: none should return the `<dialog>`.
- **If one does**, the image is narrower than the dialog. Fix it by sizing the dialog to the image (e.g. `width: min(94vw, 1440px)`), not by touching the click handler.

### Edges this shape decides

- **Narrow viewport (390×844):** the image is 94vw. The caption wraps inside the sticky footer, and the footer grows taller rather than covering anything.
- **Tall image that scrolls:** the image scrolls under the footer, the footer is opaque, and the caption and buttons never overlap each other.
- **Not opened yet:** don't give `.shot-box` a `display` value. An unopened dialog is hidden by the browser's own `dialog:not([open]) { display: none }`, and a `display` set on the class overrides it, leaving the dialog on screen.
- **Restart, pause, two runs, retry, null values:** none apply. This is a static page.

### Tests

`apps/site/unit/page.test.tsx:304-326` asserts the captions, the full-image `href`s and the three button labels by string. A wrapper div changes none of those strings, so the file needs no edit and should stay green. No unit test can see layout. The ticket's two screenshots are the only check that the caption is as wide as the image and that no part of the page shows through, so take them after the change and put them in the summary.
