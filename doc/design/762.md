# #762 design note: what Ctrl+C at a setup question says

## Where it goes

Four places. Nothing else moves.

1. **`apps/cli/src/question.ts`**
   - `AskShape` (`:18-24`) gets `kept`, `startOver?` and `command?`.
   - `Question` (`:37-64`) gets `startOver?` and `command?` beside `kept`.
   - `question()` passes all three on the shape it hands `world.ask` (`:121-126`).
   - `kept` keeps its default, `'Nothing was written'`, which is the same default as the refusal at `:131`. Put it on the shape already defaulted, so the cancel line and the refusal can never disagree.
   - The refusal at `:131` stays exactly as it is and never reads `startOver`.
2. **`apps/cli/src/prompt.ts`**
   - Delete `STOPPED_AT_QUESTION` (`:57-58`).
   - Add an exported pure builder, e.g. `stoppedAtQuestion(shape: Pick<AskShape, 'kept' | 'startOver' | 'command'>): string`. This is the only code that writes the line.
   - The cancel branch (`:83-86`) prints `\n${stoppedAtQuestion(shape)}`. The `process.exit(130)` beside it is not touched.
   - The builder is what the unit tests assert, because `liveAsk` itself exits the process and only runs at a TTY.
3. **`apps/cli/src/init.ts`**: work out `kept` and `startOver` from the store this run settled on, and pass them on `FirstProjectWorld` (`:506-523`).
4. **`apps/cli/src/first-project.ts`**
   - `FirstProjectWorld` gets `startOver?` and `command?` beside `kept` (`:156`).
   - Pass them only at the `question()` calls whose `kept` is `world.kept`: the kind question (`:260-268`), the directory question (`:377-382`) and the base-branch question (`:447-456`).

## Decisions the ticket leaves to the implementer

**`startOver` goes only where `kept` is `world.kept`, and never into `askRecipe`.**
- From `askRecipe`'s first write onward, a fresh home holds more than the store. The recipe at `recipePath(name, home)` is written, as the comment beside `seededKept` says (`first-project.ts:530-533`: *"a refusal placed after its write must say what that write left behind"*).
- When `madeKept` is set, a branch also exists in the person's own checkout (`first-project.ts:512`).
- At those points, *delete those two files* would be false. So `recipe-flow.ts`'s `kept` / `keptBeforeWrite` (`:133-140`, `:297`) carry no `startOver`.
- Since `askKept = absent ? at.keptBeforeWrite : at.kept` (`recipe-flow.ts:297`), it would take reasoning about *absent* per question to show a start-over sentence there is still true. This ticket does not need it.
- `add` passes no `startOver` anywhere, as the ticket says.

**`chooseStore` returns the choice it settled on, not `null`.**
- Today it returns `null | number` (`init.ts:781-784`, `:812-816`, `:850-863`). Every success path already holds a `StoreChosen`: `settled`, or `read` from `confirm(...)`.
- Return that, so `init` builds `kept` from what was actually chosen. Rebuilding it from a second reading of the file would be a second answer to the same question.
- Use `choice.path` for SQLite, not `join(home, SQLITE_LOG)`. A SQLite choice can name a path other than the home's, and `describeStore` already prints `choice.path` (`packages/env/src/index.ts:757`).

**The start-over sentence needs two facts: the home had no `config.yml`, and this run wrote one.**
- *Had none at the start* comes from the read `readConfig` already does (`init.ts:262-264`: `if (text === null) return new Document({})`). That function throws the distinction away today.
  - Have it also report `existed`, or move the `read(path)` up into `initCommand` and pass the text in. Do not add a second read of the file for this.
- *This run wrote it*: the Postgres path can settle with no write at all, when the choice comes from an exported `LINGTAI_DATABASE_URL` (`settled` at `:781`). That fresh home has no `config.yml` to delete.
  - So set `startOver` only where `chooseStore` took one of its three `world.machine.write(path, …)` branches (`:812`, `:853`, `:860`).
  - The simplest way is a `wrote: boolean` on what `chooseStore` returns.
- With either fact false, `startOver` is absent. Do not reword it into something softer.

**The `-wal`/`-shm` check happens when `kept` is built**, at `init.ts:506`, through `world.exists` (already on `InitWorld`, `:196-197`). It reflects the disk at that moment, and that is good enough.
- Name `lingtai.db` itself even if it does not exist yet. With `--local`, `world.projects()` (`:393`) is skipped, so the file may not have been opened.
- The wording stays *delete those files*, and deleting a missing file is harmless.
- Put the clause builder in `init.ts` as an exported pure function so the tests reach it without a world, e.g. `initKept({ choice, configPath, startedWithConfig, wrote, sidecars })` returning `{ kept, startOver? }`.

**Postgres `kept` names no URL at all**, not even a redacted one. The form is `the store is kept, Postgres, chosen in <configPath>`, which is the ticket's form and satisfies the *no Postgres URL* check without depending on `redactUrl`. If the choice came from the environment, say `chosen by <choice.from>` in place of the path.

**Where `command` comes from**
- `init` passes `'lingtai init'`, both on `FirstProjectWorld` and on its own store question (`init.ts:827`).
- `add` passes `command` only where an exact re-run string is already built. `again` (`first-project.ts:557`) is one.
- Everywhere else, leave it absent and let the builder's fallback (`running the command again continues from here`) speak. Do not go through every `question()` call site to fill it in.

## What does not change

- **`github-app.ts:34`'s `askFirstProject` default** (`'the store chosen above is kept'`) is pinned by `unit/github-app.test.ts:58`, and so are its refusal sentences. It receives `world.kept` from `chooseFirstProject`, so through `init` it now prints the new clause. Its default for any other caller stays.
- **The `first-project.test.ts` and `source.test.ts` assertions** that pass their own `kept` (`:364-411`, `:289-302`) keep passing, because they never go through `init`.
- **The refusals that end in `${world.kept}`** (`first-project.ts:191-243`, `:320-387`) will now end with the new `init` clause, which is still true there. They never get `startOver`, because only `question()` hands it to `world.ask`.

## Checks

The unit half covers all of this:
- tests over `stoppedAtQuestion`;
- tests over `initKept`, covering a fresh home with SQLite, a fresh home with Postgres, a Postgres choice from the environment with no write, and a home that already had a `config.yml`;
- a test of `question()` with a world whose `ask` returns `null`, given a `Question` that carries both `kept` and `startOver`, asserting that `startOver` is not in the refusal;
- a test that `question()` passes all three on the shape, with a recording `ask`.

Exit code 130 is the existing line, untouched. No integration test is needed.
