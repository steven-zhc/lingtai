# #688: design note for the report's one pure function

## Where it goes

- **`packages/conductor/src/report.ts`**, exported as `./report` in `packages/conductor/package.json`, the same way `./ceiling` is. It does no I/O, never calls `Date.now()`, and makes no store call. `day-ceiling.ts` is the precedent the ticket names, but it is *not* pure throughout: it imports `EventStore` (`day-ceiling.ts:17`) and reads rows through a port at `:183`. Copy its pure half, `daySpend` (`:44-73`), and nothing else.
- **Tests:** `packages/conductor/unit/report.test.ts`. Every claim the ticket makes is checked here at the unit level. There is no integration half to this change.

## Inputs

**`ticket_report` has no reader and no exported row type.** #687's note said *"Do not add a `readTicketReport` store method"* (`doc/design/687.md`, *Not in this change*). The fold's `State` is private (`packages/projector/src/ticket-report.ts:86`). So `report.ts` declares the row it consumes, and the next ticket's reader maps SQL onto it:

```ts
interface ReportTicketRow {
  ticket: string; project: string | null; kind: string | null
  outcome: 'open' | 'landed' | 'closed'; outcomeAt: Date | null
  passes: number; fixRounds: number; machineMs: number
  intervalsEmpty: number; intervalsOpen: number; unknownClaims: number
  passTimes: string[]; reviews: ReportReview[]; waits: ReportWait[]
  cost: Record<string, PurposeCost>
}
```

- `ReportReview`, `ReportWait` and `PurposeCost` come from `@lingtai/projector` (`packages/projector/src/index.ts:65-67`). Conductor already depends on projector (`packages/conductor/package.json:53`).
- Leave out `claims`, `rounds` and `open_intervals`. They are the fold's working state, and their counts are already in the scalar columns (`ticket-report.ts:177,180,181`).
- The spend input is `Pick<SpendRow, 'at' | 'ticket' | 'project' | 'purpose' | 'round' | 'costUsd' | 'estimatedUsd' | 'estimateFetched' | 'kind'>` (`packages/projector/src/spend.ts:284`).

**Signature:**

```ts
report({ tickets, spend, window, project, kinds, sortBy, now })
```

- `window` is already resolved to `{ from: Date; to: Date }`, half-open.
- A separate exported `resolveWindow(spec, now)` turns `today | 7d | { from, to }` into that shape. Both the CLI's `--window` / `--from` / `--to` and the page's filters go through this one function.
- `project` is `string | null`, and null means every project.
- `kinds` is `readonly (string | null)[] | null`. Null means every kind; a `null` inside the list is *unclassified*.
- `sortBy` is `'rounds' | 'cost'`, for §4.

## Decisions the ticket leaves to the design

**Windows are in local days, using `day-ceiling.ts`'s helpers** (`startOfLocalDay` and `nextLocalMidnight`, `:38-41`):

- `today` is from `startOfLocalDay(now)` to `nextLocalMidnight(now)`.
- `7d` is today plus the six local days before it, so the per-day chart always has seven whole bars.
- A date range includes both dates: it runs from the local midnight of `from` to the midnight after `to`.
- A run's day is its `at` in local time. That matches how the daily ceiling counts a day, so *today* reads the same on `/report` as in the ceiling sentence.

**Placement follows 0123 §1 as written:**

- Landed and closed tickets are placed by `outcomeAt`.
- An open ticket is placed when any of its `passTimes` falls in the window. A pass that started before the window and is still running does not place the ticket. That is the ADR's *"contains any of its passes"*, and the ticket's *open across the edge* case is exactly this rule.
- The project filter and the kind filter apply to every figure: tickets on `row.project` / `row.kind`, and spend on its own `project` / `kind` (0123 §3: *"by the kind `spend` recorded on each run"*).
- A `spend` row with `ticket` null has `project` null. It counts only when there is no project filter.

**Each figure has its own population. Say so in the type names, not only in comments:**

| Figure | Population |
|---|---|
| counts, means, medians, the two shares | placed tickets; averages over the landed ones only |
| spend in the window | `spend` rows whose `at` is in the window, whatever the outcome |
| survival curve | tickets whose **first review's `at`** is in the window, any outcome (§3) |
| wait × cause table | waits whose `at` is in the window, on tickets that pass the filters |
| top eight | placed tickets, any outcome (§4) |

**Money always has three parts and a count, never one number** (0110 §5, and `day-ceiling.ts:5-14`).

- Every dollar figure is `{ reportedCents, estimatedCents, unknown }`.
- Estimates are summed in dollars and rounded once per cell, as `day-ceiling.ts:70` does.
- The window's spend tile is the **sum of the rounded day cells**, so the tile equals the sum of the chart's bars (§3: *"the tile is the sum of the chart's bars"*).
- A ticket's `unknown` is the sum of `cost[*].unknown` plus `unknownClaims` (0123 §2's *unknown* row).
- A ticket's **ordering cost** is reported plus estimated. That is the same sum `ceilingReached` makes (`day-ceiling.ts:102-103`), and it is used only to rank §4 and to take medians.
- Mean cost is returned as a separate mean for reported and for estimated. The two add up correctly, because means are linear.
- Median cost is the median of the ordering cost, with a flag that says whether any of it was estimated.
- Spend rows have `purpose` as `for._tag` (`spend.ts:291`). Split `Action` into `Work` (round 0) and `Answering` (round ≥ 1), exactly like `purposeOf` (`ticket-report.ts:211-212`). This is the third copy of that rule; add a test that pins it to the fold's copy.

**An empty window does not divide.**

- Every mean, median and share is `number | null`, and null means *no landed tickets*.
- The curve is `[]`.
- The day buckets are still all present, with zeros and `unknown: 0`.
- The per-kind table has no rows.
- No `NaN` reaches a caller. Assert that the empty-window result contains no `NaN` anywhere (walk the object).

**Medians:**

- An even count takes the mean of the two middle values, so a median of 1.5 rounds is allowed.
- Machine time is a mean and median of `machineMs` over landed tickets.
- Beside it, the result carries the sums of `intervalsEmpty` and `intervalsOpen` over placed tickets. Those sums are §2's *"says how many such passes it skipped"*.

**Per kind:**

- The key is `string | null`, and null is *unclassified*. A null kind is never dropped and never mapped to a string, because a recipe could have a kind actually named that.
- If `kinds` was given, rows come in that order. Otherwise they are sorted alphabetically, with null last.

**The survival curve (Kaplan–Meier, 0123 §3):**

- Each ticket's reviews are sorted by `BigInt(seq)` across passes. Compare as BigInt: the seqs are strings (`ReportReview.seq`, `ticket-report.ts:60`), and string order breaks at the first seq with more digits.
- **A review passed when `blocking === 0 && cleared`.** This is the decision #687 deferred (`doc/design/687.md`: *"lets the next ticket decide the passed rule"*). Under §2's literal wording (*"a review with none of those passed"*), an `Interrupted` or `AnswerUnreadable` review counts as passed (`cleared` returns false for both, `packages/domain/src/action.ts:243-246`). A review that did not finish has not got the ticket past review. Make this edit to 0123 §2's *reviews* row in the same change. 0123 is still *proposed*, and a topic ADR is edited in place (CLAUDE.md). The ticket's *Docs* edge allows it.
- A ticket's first passing review is its event, and anything after it is ignored. A ticket with m reviews and none passed is censored after review m.
- Return `{ k, atRisk, passed, censored, survival }` for k = 1 up to the largest k reached. `survival` is the running product of `(1 − passed/atRisk)`. The page labels each step with `atRisk` (§7).

**Wait × cause:**

- The row is `reason` and the column is `triage?.cause ?? null`.
- A wait triaged with no `TriageAdvised` result (so cause is null, `ticket-report.ts:416`) shares the null column with an untriaged wait. That column is §7's *"no triage"* in the sense of *no triage cause*.
- The cell is a count.

**Top eight and the sentence (§4):**

- Sort by `fixRounds` descending, then ordering cost descending, then `ticket`, so the order is the same on every run. With `sortBy: 'cost'`, cost comes first and rounds second.
- Each ticket carries its cost, each purpose's share of the ordering cost, its passes, rounds and waits, and each wait's reason, cause and resolution.
- The sentence is a template built from those fields and nothing else:
  - It leads with the largest purpose share: `72% answering refusals over 6 fix rounds · 3 passes · waited 3 times (FixableLines ×2, ConflictingHunks)`.
  - Purpose words: `Work` → work, `Answering` → answering refusals, `Judge` → judging, `Triage` → triage, `Discussion` → discussion.
  - Get the singulars right (`1 fix round`, `1 pass`, `waited once`). With no waits, leave the wait clause out.
  - Reasons are listed by count, highest first, with `×n` when n > 1.
  - When a ticket's ordering cost is 0 and `unknown > 0`, lead with `cost unknown` instead of a percentage.
  - Whenever `unknown > 0`, append `· n runs unknown`. A sentence without it would read as a complete cost.

## The fixture

- Build the §3 baseline as a **generated** fixture: a table of *(reviews until the first pass, or censored after m)* × count, expanded into rows.
- It has 174 reviewed tickets whose curve rounds to 54 / 33 / 27 / 19 / 12 / 9% at k = 1, 2, 3, 4, 5, 7.
- Separately, 167 landed tickets, 10% of them at 5 rounds or more.
- The ADR's figures are rounded, so assert `Math.round(survival * 100)`.

Each edge also needs a hand-written fixture of a few rows:

- censoring;
- an open ticket placed only by a pass in the window, and one not placed because its only pass is before the window;
- unclassified kind;
- a `spend` row outside the window that is still in the ticket's own cost;
- an interrupted review;
- a seq-order trap: `"9"` before `"10"`.

## Edges

- **A read that fails, a restart, two runs, a pause, a retry:** none apply. The function is pure and the readers are the next tickets.
- **A stale page:** none here. The function sees only the rows it is handed.
- **Null values:** handled by the decisions above. A kind or cause that is `null` is a value of its own, and an unknown cost is a count, never 0.
- **Cost to later tickets:** none at runtime. The `ReportTicketRow` type is the contract the next ticket's reader must produce. A column added to the fold later is not seen here until the type is extended, which is a typecheck error and not a silent zero.
