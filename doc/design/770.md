## Design note for #770: refuse any integer flag that is not a whole number, by name, before the parser runs

### Where it goes

The new check goes in `runCli`, next to the `TAKES` loop (`apps/cli/src/cli.ts:1303-1310`), and works the same way. It runs after the `board shutdown` and `projection run` early exits and before `@effect/cli` parses anything. It reads values through the existing `flagValue` (`cli.ts:1214-1228`). That function returns `undefined` when the flag is absent, `null` when "it has nothing after it (the end of the line, or another flag)", and otherwise the text. It already handles both `--issue=x` and `--issue x`, so you don't need a second reader. A refusal does the same as `TAKES`:

- under `--json` (`args.some(jsonOn)`), call `printJsonError(args[0], 'usage', sentence)`;
- otherwise, print the bare sentence with `console.error(sentence)`, with no `symbol.fail()` (the test at `answer-cli.test.ts:111` pins the bare form);
- `return 2`.

### The one list, and how the declarations read it

The list is keyed by **the first word of argv**, as `TAKES` is (`TAKES[args[0] ?? '']`). It is not keyed by subcommand, for two reasons:

- `board` declares `--port` on the parent and on all four subcommands (`cli.ts:390-398`).
- `end` declares `--issue` only on `replay` (`cli.ts:658-660`).

A first-word key covers both without anyone knowing the command tree. A first-word key is also what keeps `init`/`add` out of scope: their `--port` is `text('port')` (`wizard-options.ts:40`), and a list keyed by flag name alone would refuse `init --port abc` in the wrong words.

So the list maps each command to its integer flags:

- `approve`, `requeue`, `grant-fix-round`, `ask`, `answer`, `close`, `now` and `end` each have `issue`;
- `run` has `issue` and `max`;
- `board` has `port`.

The six commands sharing `issueOption` are at `cli.ts:214, 238, 262, 272, 280, 289`. Check each one's `Command.make` name before you write its key.

To make "every `Options.integer` takes its name from that list" something `tsc` enforces rather than something a reviewer remembers, the only way to make an integer option is a helper typed over the list. For example:

```ts
integerOption<C extends keyof typeof INTEGER_FLAGS>(command: C, flag: (typeof INTEGER_FLAGS)[C][number])
```

It returns `Options.integer(flag)`, and callers add `.pipe(Options.optional)` where they do today. Changes that follow from this:

- `issueOption` (`:204`) can no longer be one shared constant. Each command writes `integerOption('approve', 'issue')`, and so on.
- `optionalInteger` (`:592`) and `portOption` (`:352`) take the command as well.
- After the change, `grep "Options.integer(" src/cli.ts` should find exactly one hit, inside the helper.

An integer flag added later then can't be declared without its pair being in the list, and the walking test covers it with no new line.

### The sentence

Each flag in the list carries a noun:

- `issue`: `an issue number`
- `max`: `a number`
- `port`: `a port number`, which matches the wording `boardHandler` already uses for out-of-range ports (`cli.ts:369`, `` `${BOARD_USAGE} — --port takes a port number` ``).

The sentence has two forms:

- With a value (including `''`): `` `--issue takes an issue number, not '${value}'` ``. This is the ticket's own example, with the value in single quotes.
- With no value (`flagValue` returns `null`): `--issue takes an issue number`. This is the `TAKES` form, because there is nothing to quote.

Neither form contains the words "a integer".

### Decisions the ticket leaves open

- **The value test is `/^\d+$/` on the untrimmed text**, as the ticket's Edges say. So `-3`, `+3`, `1.5`, ` 5` and `1e3` are all refused. `flagValue` returns `-3` as the value because it only treats a `--` prefix as another flag, so `--issue -3` reaches the regex and is refused there.
- **A flag given twice**: `flagValue` returns only the first occurrence. Check every occurrence, so `--issue 5 --issue x` is refused. A small local loop over `args.slice(1)` is enough. Don't change `flagValue`'s contract, because `TAKES` relies on it.
- **Range checks are unchanged.** `--port 0` passes the regex and is still refused by `boardHandler`'s own check (`:367-369`). `--issue 0` still reaches the verb.
- **`now`'s positional issue** keeps its own refusal (`cli.ts:307-308`). This check reads only `--issue`.

### Tests

Put them in `apps/cli/unit/`, through `runCli` and `answer-cli.test.ts`'s `capture`. Because the check runs before parsing and keys on `args[0]` alone, the walking test can build argv as `[command, '--' + flag, 'x']` with no project and no subcommand. That form works for `end` and `board` as well, and it avoids repeating each command's positionals. Walk the list, and for each value in this set assert exit 2, an empty stdout, and stderr equal to the sentence:

`''`, `=`, `=abc`, `abc`, `1.5`, `-3`, and a bare flag at the end.

Also assert that `--json` gives exactly one `error` document.

For the "still parses" cases, use `approve p --issue 5` and `--issue=5` against the stubbed runner, as `answer-cli.test.ts:95-101` does. Assert that `issue: 5` reaches the runner.

Nothing in `unit/` or `integration/` asserts the library's "is not a …" sentence today; a grep for it finds nothing. So no existing test should change.

### Checks

Every check here is unit-level: `pnpm typecheck` covers the helper's typing, and `HOME=/nonexistent pnpm test` covers the refusals. Nothing depends on the integration half.
