## Design note for #700: `--yes` and defaulting the base branch

### 1. Make `--yes` the same flag as `--defaults` inside `flagsOf`

Fold `--yes` into `--defaults` at the point where flags are parsed. Don't teach each reader about a second key.

Today several places read `flags['defaults']`, and each one is a place `--yes` could be forgotten:
- `recipe-flow.ts:271`: the "use every default?" question gets `given: at.flags['defaults'] !== undefined ? 'yes' : null`.
- `recipe-flow.ts:429`: the summary stop reads the same thing.
- `recipe-flow.ts:334`: the trial-build rule reads it indirectly, because it is keyed on the world (`askWorld !== world ? 'no' : null`).
- The new base-branch wrap in `first-project.ts` will be one more.

If the check were `flags['yes'] ?? flags['defaults']` at each site, the first site somebody missed would quietly behave differently under `--yes`.

So:
- Add `yes: Options.boolean('yes')` beside `defaults` in `recipeOptions` (`wizard-options.ts:31`). Both `initOptions` and `addOptions` spread `recipeOptions`, so this covers both commands.
- In `flagsOf` (`wizard-options.ts:63`), when `yes` is true, write `flags.defaults = ''` and `repeated.defaults = ['']`, and do not emit a `yes` key. Its doc comment says *"`--defaults` is `''`"*; make it say that of `--yes` too.
- Add `'yes'` to `VALUELESS_OK` (`wizard-options.ts:87`). Otherwise `valuelessFlag` treats `--yes --local <dir>` as `--yes` with no value. That is the case the ticket's `Done when` names. Test it through `valuelessFlag` as well as through the flow.

That keeps "`--yes` and `--defaults` both" the same as either one, with no extra code.

### 2. Wrap only the base-branch question, and only on the flag

In `first-project.ts:403`, call `question(...)` with `flags['defaults'] !== undefined ? { ...world, ...acceptingDefaults(world) } : world`.

- **Key it on the flag, not on the "use every default?" answer.** That question is asked later, inside `askRecipe` (`recipe-flow.ts:268`). A person at a terminal still gets asked about the base branch, as today.
- **Spread order matters.** `acceptingDefaults` returns only `log`, `spin` and `ask` (`question.ts:82-91`), so put it last to override `ask` and keep `git`, `files`, `kept`, `home` and the rest from `world`.
- **Make a fresh wrap at this call site.** Don't share one with anything else. Its repeat guard (`lastPrompt`, `question.ts:83`) only works within one question.

The project, App, store and directory questions (`first-project.ts:213`, `:329`; `github-app.ts:37`, `:61`; `init.ts:778`) don't change. Nothing in this change should touch them.

### 3. What "refuses with the validation's reason" builds to

When the detected base fails `validate`:
1. `question()` writes the reason with `world.log(paint.fail(why))` (`question.ts:123`) and asks again with the same prompt.
2. `acceptingDefaults` returns `null` because the prompt repeated.
3. The refusal is `the base branch needs an answer: pass --base <branch>` (`question.ts:119-120`).

So the reason goes to the log, and the refusal string names the flag. The unit test should assert both: the log contains `<branch> is not a branch in <toplevel>` (`first-project.ts:413`), and `refused` names `--base`. Don't change `question()` to put the reason into the refusal string. That would change every question's refusal, and the ticket's edge cites `question.ts:74-80` as the mechanism to keep.

### 4. Help and docs

- Change both help blocks (`commands.ts:80-85`, `:478-483`) to say `--defaults, --yes`. The wording should be "the default for every question whose answer was detected or is easy to change later". Keep the existing lines about the trial build and the summary stop.
- Add `--yes` to the usage line in `init.ts:240`, which shows `[--defaults]` today.
- Then run `pnpm docs:cli`; `apps/cli/unit/cli-doc.test.ts` stays red until you do.

### Checks

Everything here is unit-level: `apps/cli/unit/first-project.test.ts`, `github-app.test.ts`, and a `flagsOf`/`valuelessFlag` test. Nothing depends on `pnpm test:integration`.

For the "no `--project`" test, assert that the refusal names `--project` **and** that the test world's `open`, and whatever starts the board, were never called. A refusal string alone would also pass if the App flow had started and then failed.
