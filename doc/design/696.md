# Design: Go detector (#696)

## Where it goes

Add `goDetector: StackDetector` in `apps/cli/src/detect-setup.ts`, after `pythonDetector` (`:367`). Append it third: `DETECTORS = [nodeDetector, pythonDetector, goDetector]` (`:468`). You don't need anything new for a repository that has both `package.json` and `go.mod`. `detectSetup` (`:476`) already lets "the first stack present" supply install and build, and only names every later one: `${other.stack} is also at the root; ${first.stack} was used`. So Node wins, and the Go part is one note. Set `stack: 'Go'`.

## The detector

- **Presence** comes from `hasOrUnknown(reader, 'go.mod')` (`:215`). An `'unknown'` answer returns `presence: 'unknown'` with the note `could not tell whether a Go module is at the root`. That is the rule from the comment on `EMPTY_SETUP_READER` (`:27`): a rejected `has` "reads as could not tell rather than a confirmed absence". Never read or parse `go.mod`. Its existence is the whole claim, and `go mod download` validates the file itself, which the #436 trial will show.
- **Install** is always `{ run: 'go mod download', because: 'go.mod is at the root' }`.
- **Build** entries, in this order (the `name` is only printed, as `build (${b.name}): …` at `setup-build.ts:443`):
  1. `format`: `out=$(gofmt -l .) && test -z "$out"`. Copy this string exactly; the quotes matter, and the assignment is what carries gofmt's exit status (inside `test -z "$(…)"` it is discarded, so a missing gofmt would pass). Run actions go through a shell (`packages/actions/src/command.ts:446`/`:459`, `shell: true`), so `$(…)` and `test` work. The test must state the Watch-out directly: the command is built on `test -z`, never on a bare `gofmt -l .`.
  2. `vet`: `go vet ./...`
  3. `lint`: `golangci-lint run`, only when a config is found (see below).
  4. `test`: `go test ./...`
- **`vendor/`**: check it with `hasOrUnknown(reader, 'vendor')`. `has` already answers for directories; Python asks it about `tests` (`PYTHON_TOOLS`, `:236`). When it is present, install stays the same and the note says: `vendor/ is at the root; go mod download still fetches the module cache, and gofmt -l . checks vendor/ too`. The second half is the trap on this edge: `gofmt -l .` does not skip `vendor/`, so unformatted vendored code makes the format check fail. Say this in the note; don't change the command (build tags, workspaces and other variants are out of scope, and the #436 trial is what catches it). An `'unknown'` answer gets the note `could not tell whether vendor/ is at the root`.

## golangci config

Try `.golangci.yml`, `.golangci.yaml`, `.golangci.toml` in that order, the order golangci-lint itself looks them up.

- The first one that is present and parses supplies `because: '<file> is at the root'`.
- Every other one found is a note: `<file> is also at the root; <chosen> was used`. This matches the lockfile wording at `:120`.
- A file that is present but doesn't parse gets the note `<file> does not parse`, and nothing is suggested from it. Don't fall through to the next file in that case: golangci would pick the broken one up too.
- A file whose `has` rejects gets `could not tell whether <file> is at the root`, and `golangci-lint run` is not suggested; no later file is used in its place.

For parsing, `configParses` (`:296`) already does the read, the "could not be read" note and the `said` dedupe. Today, though, anything that isn't `.toml` goes to `iniParses`, which would wrongly refuse YAML. Add a `.yml`/`.yaml` branch there that uses `parse` from `yaml`; it is already a dependency (`apps/cli/package.json:35`), so nothing needs adding. Don't write a second reader. An empty YAML file parses to `null`. Count that as "parses": golangci accepts it.

## The PATH note: the one change outside the detector

`printFound` (`apps/cli/src/setup-build.ts:235`) probes the **first word** of each command (`c.split(' ')[0]`). For the gofmt check that word is `test`, a shell builtin, so the probe would never name `gofmt`. The ticket's edge, "a note naming the missing tool", would then pass a test without ever happening.

The fix: add an optional `tool?: string` to the build entry type in `DetectedSetup` (`detect-setup.ts:44`), and have `printFound` probe `b.tool ?? firstWord`. The Go detector sets `tool: 'gofmt'` on the format entry. For the others the first word (`go`, `golangci-lint`) is already correct.

Keep the comment at `:241`, "ruff, mypy and pytest come from the project's environment", accurate. Go's tools don't come from a project environment, so they are all probed; add one clause saying so.

Unit-test this in whatever file covers `askInstallAndBuild` today. Hand it a fake `onPath` that answers false for `gofmt`, and assert that the logged line names `gofmt`, not `test`.

## Tests

Put them in `apps/cli/unit/detect-setup.test.ts`, beside the Python cases, using its fake `SetupReader`:

- `go.mod` alone gives the install and the three build commands.
- Each of the three golangci files adds `lint`.
- Two of them: the first is used, and a note names the second.
- A `.golangci.yml` that doesn't parse: a note, and no `lint`.
- `has('go.mod')` rejects: presence is `unknown` and the note is there.
- `vendor/` present: the note is there and install is unchanged.
- `package.json` plus `go.mod`: Node is used and the note names Go.

The ticket's "the gofmt check fails on output" is a claim about the command string. Pin the exact `run` text including `test -z`. Don't run gofmt, which is out of scope.
