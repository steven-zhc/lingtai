# 0.14 — a boundary the agent cannot leave

**Status** planning · 2026-11-12 · what 0.14.0 is to contain, as the operator
agreed it in discussion. No ticket is open yet. **0.14 starts when 0.13.0
closes**; until then this file is the plan and nothing is cut from it. How each
part is built goes in its ticket.

The research behind it is
[agent-sandbox-options.md](../research/agent-sandbox-options.md): it compares
OpenSandbox, sandbox-runtime, a Docker image, Docker Sandboxes and cloud
sandboxes, and recommends sandbox-runtime (`srt`). It also gives the levels
L0–L5 that this file uses.

## Where it stands

An agent runs as the operator, on the operator's machine
([safety.md](../safety.md)). Lingtai launches Claude Code with
`bypassPermissions` (`packages/agent/src/claude-code.ts:305`) and no filesystem
sandbox (`claude-code.ts:73`, `providesTier: 'guarded'` at `:77`). Codex runs
under its own `workspace-write` and provides `sandboxed`
(`packages/agent/src/codex.ts:36`, `:214`). A `build:` command is a plain
`spawn(…, { shell: true })` in the worktree with a filtered environment
(`packages/actions/src/command.ts:453`, `:466`), so the code an agent just
wrote runs with no boundary at all.

| | Claude Code | Codex | build commands |
|---|---|---|---|
| L2 write | anywhere | worktree, tmp, git dirs | anywhere |
| L2 read | anything, `~/.ssh` and `~/.lingtai/config.yml` included | only what a user's profile denies | anything |
| L3 network | open | not measured | open |
| L4 credentials | `gh` login usable, credential files readable | same | same |

What already exists and is reused: the tier, `Tier = z.enum(['open',
'guarded', 'sandboxed'])` (`packages/domain/src/events.ts:87`), and refusing a
recipe whose tier a runtime cannot provide, never downgrading
(`missingForTier`, `packages/agent/src/runtime.ts:332`).

## What 0.14.0 contains

**One policy wraps Claude Code, Codex and every `build:` command, through
sandbox-runtime, on macOS and Linux.**

| | What is true | Level |
|---|---|---|
| **Files** | An agent and its build write only to its worktree, the temp directory and the git directories a commit needs. They cannot read a fixed list of credential paths (below). | L2 |
| **Network** | Only allowed domains are reachable: a built-in default of model APIs, package registries and GitHub, plus the project's own list in its recipe. | L3 |
| **Credentials** | Lingtai's own config and the operator's other credentials are unreadable, `gh`'s login included. | L4, partly |
| **One boundary** | `srt` is the only sandbox. Claude Code's own sandbox and Codex's `workspace-write` are switched off inside it, so the two runtimes and the build command answer to one policy. | — |
| **Refused, never downgraded** | A project that asks for the sandbox on a machine that cannot provide it (no `bwrap` on Linux, say) is refused by name. It does not run without the sandbox. | — |
| **Seen** | A connection the sandbox refused is an event, shown on the task page. A refused read or write is not: srt does not report one (017). Each run records the boundary it ran under. | — |
| **On by default** | A new project gets the sandbox from `lingtai init` and the add-repository wizard. | — |
| **Lingtai first** | Lingtai's own recipe is the first existing project to opt in. Every other existing project is left as it is, and `lingtai doctor` says it runs without a sandbox. | — |
| **Written down** | `safety.md` is rewritten from measurements on macOS and Linux, cell by cell. | — |

### The decisions, as agreed

1. **`srt` is the only boundary.** Codex runs inside it with its own sandbox
   off. Seatbelt is likely not nestable on macOS, so two layers would probably
   fail anyway, and one layer is one policy to measure and to explain.
2. **A refusal is an event in 0.14**, on the board, not only a line in the run
   log. A person learns more from what an agent tried than from a silent block.
   017 narrows this to refused connections, the only refusals srt reports on
   both platforms.
3. **One allowlist per project, plus built-in defaults.** Splitting it by step
   (`prepared` may install, `implement` may not, as #339 proposed) is later.
4. **Lingtai opts in first; other existing projects are unchanged.** New
   projects are on by default.
5. **`gh` is closed to the agent.** Lingtai pushes and merges outside the
   sandbox (`codex.ts:50`: *the lane runs git outside the sandbox*), and
   everything an agent needs from the ticket is in its brief, so the agent
   never needs GitHub credentials. `~/.config/gh` is on the deny list.
6. **The runtimes' own config directories stay readable.** `~/.claude`,
   `~/.claude.json` and `~/.codex` hold the login the agent runs on. So 0.14's
   L4 is *Lingtai's and your other credentials are unreadable*, not *the agent
   holds no long-lived credential*, and the safety manual says so plainly.

7. **On Linux the hook socket gets through with `allowAllUnixSockets`**, and
   the known dangerous sockets are read-denied instead, starting with
   `/var/run/docker.sock`. `lingtai doctor` and the safety manual say so.
   (017: seccomp cannot let one path through.)
8. **Each Claude Code run gets a configuration directory of its own.** Lingtai
   makes a `CLAUDE_CONFIG_DIR` per run and copies only the login into it, and
   the operator's `~/.claude` and `~/.claude.json` are read-only to the run. A
   run then cannot plant a hook or an `mcpServers` entry that the operator's
   own sessions would run. This reverses today's behaviour, where a run drops
   `CLAUDE_CONFIG_DIR` and reads `~/.claude`. How a refreshed token gets back
   to the operator's login is part of S1.
9. **On macOS only Codex runs with `enableWeakerNetworkIsolation`**, because
   it needs `trustd` to verify TLS. Claude Code and the build commands do not.
   Each Codex run records that it had the option on, and the manual says so.

### The deny list

These paths are unreadable and unwritable: `~/.ssh`, `~/.aws`, `~/.config/gh`,
`~/.gnupg`, `~/.netrc`, `~/.docker/config.json`, `~/.kube`, `~/.npmrc`, and
`~/.lingtai/config.yml` with every backup beside it. The rest of `~/.lingtai`
is covered by the first trap below. Keeping the list in one place in the code
is part of the policy ticket. The final list is settled by the measurement,
and the manual prints it.

## What the measurement found

The traps this plan named were measured on 2026-11-12, by hand, on harbor
(Linux) and foundry (macOS). The results are
[experiment 017](../experiments/017-srt-under-lingtai.md). In short:

**Answered.**

- **`~/.lingtai` can be denied whole and a run's worktree and mirror allowed
  back**, on both platforms. A `git commit` in the worktree works.
- **The deny list holds**: `~/.ssh` and the `config.yml` canary are unreadable,
  `$HOME` is unwritable, and only allowed hosts are reachable, raw TCP included.
  Claude Code under `bypassPermissions`, told to read the canary and write
  outside, failed at both.
- **A runtime's own sandbox does not work inside srt.** On macOS it cannot
  start (`sandbox_apply: Operation not permitted`), and on Linux Codex's starts
  but cannot write even in the worktree. So srt being the only boundary
  (decision 1) is forced as well as chosen.
- **Codex runs inside srt on Linux** with its own sandbox off, and was refused
  the canary and a write outside, like Claude Code.
- **Bundling into the SEA is feasible.** The Windows-only 166 MB is a lazy
  import and can be left out. On Linux the 742 KB `apply-seccomp` has to be
  written to disk and named with `seccomp.applyPath`.

**Build around these.**

- **The mirror's `config` is writable from a run**, so a run could set
  `core.hooksPath` or `core.fsmonitor` for Lingtai's own git, which runs
  outside the sandbox. The mirror's `config`, `hooks/` and `info/` must be
  write-denied.
- **On Linux, srt plants `/dev/null` stand-ins** for `.bashrc`, `.gitconfig`,
  `.vscode` and the rest in the worktree, so `git add -A` fails. Lingtai
  writing those names into the mirror's `info/exclude` at provision fixes it
  (measured).
- **A package manager's shared store must be writable**
  (`~/.local/share/pnpm`, `~/.cache`), or `pnpm install` fails.
- **One of Lingtai's unit tests fails only inside srt, and it is a test bug.**
  `conduct-before-the-claim.test.ts` *refuses before the claim when
  runtime.agent is not the runtime it was handed* passes no `signedIn`, so it
  spawns the real `claude auth status` and `codex login status`
  (`conduct.ts:851-856`). That breaks 0060 §1 on every machine. Inside srt it
  hangs, because `runnableEnv` drops the proxy variables (next point). It is
  ticket S0, and Lingtai cannot opt in until it lands.
- **The wrap must go outside the environment filter.** `runnableEnv` keeps six
  variables and drops srt's `HTTPS_PROXY`/`ALL_PROXY`. A child spawned with it
  inside srt has no network on Linux, and Claude Code hangs rather than fails
  (`claude auth status`: 2.7 s with them, no answer in 40 s without). So the
  policy module adds srt's variables after the filter.
- **srt reports refused connections, not refused files.** Linux has no file
  report at all, and macOS's kernel log has the denials but srt did not
  attribute them to the command. So S8 records connections.

**Still open.**

- **Claude Code's token refresh inside srt.** The first sandboxed run on
  foundry got a 401 while the same command outside worked. Every run after the
  outside one had refreshed the token succeeded.
- **Ubuntu 24.04's default AppArmor setting** was not measured, because harbor
  has it off already.

**Decided by the operator, 2026-11-12**: the Linux socket, `~/.claude`, and
Codex's `trustd` are decisions 7–9 above. One trade-off remains and needs no
decision: **`srt` is a research preview** (0.0.82), and its API may change. Pin
a version, and record it on the run.

**Not a ticket: Lingtai opting in.** The recipe is
`~/.lingtai/lingtai/recipe.yml` on the conducting machine. After S4–S7 land
the operator restarts the daemon and then pastes the `sandbox` block in, in
that order (*code, restart, paste*). It is done before S12 is measured, so the
manual describes a project that runs this way every day.

S4, S5 and S6 can run in any order once S3 has landed, but self-hosting takes
one at a time.

## Not in 0.14

- **Credentials injected at the proxy** (the other half of L4), so that a
  project's own secret never sits where an agent can read it.
- **One allowlist per step.**
- **A container or VM boundary** (L5): Lingtai's Docker image is the server
  case and is separate. OpenSandbox and Docker Sandboxes are being watched.
- **The safety self-check** (#810): a measurement of the operator's own
  runtime configuration. S10 reports whether the sandbox can run, which is a
  different question.
- **Windows.**
