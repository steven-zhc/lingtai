## The shape: `TaskBody` stays sync and the layout hands it promises

`TaskBody` is rendered with no database by `unit/task-page.test.tsx:240`, `:927`, `:946` and `unit/visual-waiting.test.tsx:38`. Its doc comment says it is *"Apart from the route so a test can render the whole arrangement without a database (#152)"* (`layout.tsx:94-96`). So it must not await anything new. The board already has a pattern for this: `Answered<T> = T | Promise<T>` and `Deferred` (`app/deferred.tsx:11`, `:28-43`). The comment there reads *"Each place that reads it is a synchronous component given a resolved value … a test passes the value itself"*. `github` already reaches `TaskBody` this way (`layout.tsx:142`, `:262`).

Add two optional props to `TaskBody`. Both are `Answered`, and both have defaults so the existing test call sites compile unchanged:

- **`views?: Answered<PlaceView[]>`**
  - The layout passes `placeViewsOf(project).catch(() => viewsFor(project, { waiting: null }))`. It is started and not awaited, like `github` at `:262`.
  - `Deferred` warns *"The promise must never reject: a rejection goes to the error boundary and replaces the page"* (`deferred.tsx:25-26`). `placeViewsOf` catches its own reads (`lib/prs.ts:244-258`), so the `.catch` is belt and braces, and it costs nothing.
  - Default: `viewsFor(project)`.
- **`menu?: Answered<MenuInputs | null>`**
  - `MenuInputs` holds what `Projects` needs: `filters`, `registered`, `locks`, `sandbox`, `app` (`projects.tsx:142-158`).
  - The PR page gathers these from `readRegistered`, `onBoardProjects`, `readProjectLocks`, `filterOptions`, `sandboxStates` and `hasGitHubAuth` (`app/p/[project]/pr/[n]/page.tsx:92-123`).
  - The layout already awaits `readRegistered` beside `loadTask` (`layout.tsx:263-269`). Reuse that result. Do not read it a second time.
  - Start `onBoardProjects()` and `readProjectLocks()` unawaited, combine them with `.then`, and `.catch(() => null)`.
  - `null` (and the default) draws no menu. `PlaceLine` then prints the project name as a plain `.crumb` (`place-line.tsx:128`), which is how a failed listing reads.

Draw the place line in `TaskBody` itself, not through `RecipeBar`. `RecipeBar` takes resolved filter props and lives under `recipe/` (`recipe-bar.tsx:27-38`). Widening its `here` would still force the layout to await the menu reads.

```
<Bar project={project} registered={registered}
     actions={project !== undefined && registered ? <BarActions project={project} pause={pause} recipe={false} /> : null}>
  <Deferred value={views} fallback={<PlaceLine … views={viewsFor(project)} pendingAfter="tickets" />}>
    {(v) => <PlaceLine project={project} views={v} here="tickets" tail={`#${n}`} menu={…} />}
  </Deferred>
  <WaitingNav … />
  <Following />
</Bar>
```

- **`actions`.** Pass `null` rather than `undefined` when the project is unregistered. `Bar` only draws `BarActions` when `registered` is true (`bar.tsx:64-68`), and `actions !== undefined` is what overrides that. So `null` keeps today's rule that an unregistered project gets no Pause.
- **The menu inside both arms.** The menu is a `FilterMenu` whose summary is the project name, drawn at once. Its rows come through a second `Deferred` inside it. This is `/`'s shape at `app/page.tsx:1300-1309`: *"the crumb and views are the shell's and only the rows stream"*.

**No new `async` function anywhere.** The two promises are `.then` chains, and the components read them with `use` through `Deferred`. `apps/board` is not in the ratchet's `PACKAGES` (`packages/domain/unit/effect-ratchet.test.ts:38-52`), but it has a faces file. This shape gives it nothing new to judge.

## The PR slot while it is pending (decided here)

The 2026-11-26 decision says *"a skeleton in place, no label text"*. Whether a project is a team project is itself inside `placeViewsOf` (`lib/prs.ts:244-257`), so the fallback cannot know whether `PRs` exists.

- The fallback draws `Tickets`, then one skeleton view in `PRs`'s place, then `Recipe`, all from `viewsFor(project)`.
- Add an optional `pendingAfter?: PlaceView['id']` to `PlaceLine`. It draws `<span className="view" aria-busy="true"><span className="sk-bar" aria-hidden="true" /></span>` after that view. That is `Skeleton`'s rule of *"no words, for anyone"* (`skeleton.tsx:21-22`), inline in the bar.
- `place-line.tsx` must keep importing only React and `next/link` (`place-line.tsx:5-6`). The `Deferred` stays in `TaskBody`.
- For a solo project the skeleton disappears when the answer comes, and `Recipe` moves left by one slot. That breaks `skeleton.tsx:3-4` (*"so that nothing else moves"*). It is the price of not splitting `placeViewsOf` into a local half and a GitHub half. That split would add async functions, so it is not this ticket.

## The tail

```
n = issueNumber ?? Number(ticketRefOf(task.taskId)?.issue)
```

`issueNumber` is at `layout.tsx:148-149`. `ticketRefOf` (`lib/paths.ts:32-35`) returns null unless the issue is `/^[1-9]\d*$/`. `knowable` 404s anything else first, so `n` is never null on a page that renders. Still, guard it: draw no `tail` rather than `#NaN`. The tail is a plain `.crumb`, never a link (`place-line.tsx:153-160`).

## The facts line

Build it inside `facts()`, so the pending branch (`:1240`) and the answered branch (`:1245`) cannot differ. The order is:

`#ref ↗` · named times · `never run` · queued place · `offered by GitHub` · `from|after Attempt k of m ↓`

- **The running arm.** Prepend `namedTimes({ firstClaimAt, state: 'running', since: null })` to `runningFacts(...)`. With `since` null, `namedTimes` prints only `claimed HH:MM` (`lib/took.ts:32-33`). That is the 2026-11-26 decision, and it needs no new formatter.
- **`never run`.** Drawn when `standing.attempts === 0`, in both branches. It is a log fact.
- **`offered by GitHub`.** `facts()` gets a second argument: the answered `queued` view, `null` in the fallback. Keep `Coords`'s condition exactly: `queued !== null && queued.problem === null && queued.notOffered === null` (`standing.tsx:2029`).
- **The pointer.** Move the `Link` from `standing.tsx:2033-2042` verbatim: same `attemptTabPath`, `scroll={false}` and `title`. Draw it in both branches. Also draw it in the *"GitHub has no issue #n"* branch (`:1243-1244`), after the refusal. Today the bar draws it whatever GitHub said, and dropping it there would lose the way down on exactly the page where something is wrong.
- **CSS trap.** `.sptr { margin-left: auto; }` (`globals.css:1770`) pushes the pointer to the far right of whatever row holds it. `.coords .sfrom { margin-left: 0 }` (`:1260`) is what undid that in the bar. Replace it with `.ot-meta .sfrom { margin-left: 0; }` (`object-title.tsx:68` renders `<p className="ot-meta">`), then delete `.coords` (`:1249-1260`). Without this the pointer floats off the line, and no unit test will notice.

## What cannot be checked before the merge

`PlaceLine` pulls `ProjectLink` into the ticket page's server graph. `/` and the PR page already render it from server components, so this should be safe. But only `apps/release/integration/build.test.ts` (the Next build) would catch a server-only import reaching a `"use client"` graph, and that runs after the merge. The person's production-build check in *Done when* is the real witness for the streaming too. `react-dom/server` in a unit test shows the fallback for a promise that never resolves (`deferred.tsx:17-19`). It cannot show that the first byte left before GitHub answered. Name that in the PR.
