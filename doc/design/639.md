# Design: #639, landings onto one base, one at a time

## Where the lock goes

The lock wraps the `repo.integrate(...)` call inside `land`, at `packages/conductor/src/conduct.ts:2705`–`2752`. It does not wrap the whole of `land`. Hold it only for that call.

- **Leave the push of the agent's branch outside it.** That push is the `--force-with-lease` at `conduct.ts:2706`. It touches only `agent/<issue>`, so it cannot collide with another pass.
- **Leave `merge-action.ts` and `integrate.ts` unchanged.** [0122](../decisions/0122-several-passes-share-one-conductor.md) §3 already decided this: *"The serialising point is the `land` function `conduct.ts` builds and hands to `createMergeAction` … It is not a file lock and `packages/repo/src/integrate.ts` does not change. Its statement that the lane holds no lock stays true of git."*
  - That statement is `integrate.ts:27`: *"The lane holds no lock, because git is what makes a merge safe (#194)."* It stays true and needs no edit. The lock is an ordering inside the conductor, not a safety mechanism.
  - This design is §3 as written, so it needs no superseding ADR.

## The re-check needs no new code, so don't write any

Each `integrate` call does its own `git fetch` of the base, at `integrate.ts:422`–`424`, into refs that belong to that call alone. It then runs the `base-moved` overlap check at `integrate.ts:547`–`561`.

So a second landing that has waited for the lane:

1. fetches the base the first landing has just pushed;
2. finds `fork !== localBase`;
3. if the files overlap, refuses with `base-moved`;
4. goes through the existing #593 route: `MergeBase` at `pass.ts:1298`, then `build` and `review` again.

If the files don't overlap, it lands. The ticket's *"re-checks on the moved base"* is therefore **the lock plus the code that already exists**. Do not add a second overlap check in the conductor; a copy would be a second reader of one rule.

**Release the lane before the re-review starts.** The `base-moved` refusal comes back from `integrate` and the lane is released then. The pass takes the lane again when the route brings it back to `merge`. Holding the lane across a build and a cold review would stop every other landing in the project for the length of a whole step.

## One lane per process, by default

Put it in a small new module, `packages/conductor/src/merge-lane.ts`:

- a promise-chain mutex keyed by `` `${project}\0${base}` ``;
- `base` is the value at `conduct.ts:726`, the same one already handed to `integrate`;
- one method, roughly `take(key, onWait?: () => Promise<void>): Promise<() => void>`. It returns a release function. It calls `onWait` only when the lane is already held.

**The decision that is not obvious: `RunOnceOptions` gets an optional `lane?: MergeLane`, and its default is one module-level instance, not a fresh lane per call.**

- `runOnce` has three production callers: `packages/conductor/src/schedule.ts:223`, `apps/cli/src/conduct.ts:278`/`342` and `apps/cli/src/run.ts:523`.
- If each call made its own lane, every caller would have to thread one shared instance through. A caller that forgot would serialise nothing, and no test would notice.
- One conductor per machine is guaranteed by the lock in [0102](../decisions/0102-one-conductor-holds-the-lock.md). So *one lane per process* is exactly *one lane per conductor*.
- Tests pass their own `createMergeLane()`, so that two test files never share a lane.

## Release on every outcome

Take the lane, then `try { await Effect.runPromise(repo.integrate(...)) } finally { release() }`.

- `integrate` promises it never throws (`unexpected`, `integrate.ts:318`), but a fake can throw, and a defect can escape `Effect.runPromise`. The `finally` covers both. This is the Done-when item *"a pass failing while holding the lane releases it"*.
- If the process crashes, the lane goes with it: it is memory, so there is nothing to clean up after a restart. Say that in the module's comment rather than building anything for it.
- The lane has no timeout. A hung `integrate` would hold it, but it would also hang its own pass, which is the wall limit's problem and not this ticket's.

## The wait, on the log

Add one event, `MergeLaneWaited { runId, behind }`, on the run's own stream:

- `behind` is the `runId` holding the lane;
- append it with `appendNow(runId, …)` (`conduct.ts:624`), the same path `emit` uses at `conduct.ts:3269`.

**Append it only when the lane is actually held, and before waiting.**

- *Only when held* keeps every pass that runs alone appending exactly what it appends today. This repository runs one pass at a time until a ceiling is set (0122 §5). The snapshot-style tests (`what-a-pass-writes-today.test.ts`, `what-an-event-is-written-at.test.ts`) must not move for a pass that never waited.
- *Before waiting* means that if the append throws, the lane was never taken, so nothing leaks.

Registering the event:

- the schema and the union list in `packages/domain/src/events.ts`;
- `EVENT_AT: MergeLaneWaited: ['merge']` (`events.ts:2124`);
- a `FORMAT` entry in `apps/board/src/lib/history.ts:141`;
- a `case` in `apps/board/src/lib/progress.ts`'s fold that sets `now = { label: 'waiting for the merge lane', since, budgetMs: null }`.

No `task_view` column is needed: the card's *now* is the run-stream fold in `progress.ts`, not the projection. Check that the `StepEnded` at `merge` (`progress.ts:528`), or the next `StepStarted` on a `base-moved` route, replaces the label.

The label will still say *waiting* during the few seconds of the landing itself. That is acceptable: `land` passes no `verify`, so `integrate` is seconds. A `MergeLaneTaken` event to close the gap would be a second event for a few seconds of wording.

## The test

Put it in `packages/conductor/unit/`, built on `test/one-pass.ts`. Run two `runOnce` calls concurrently with one shared `createMergeLane()` and a fake `ports.repo.integrate` that holds a shared "origin base":

- **Ordering.** The first `integrate` blocks on a deferred until the second pass has appended `MergeLaneWaited`. Assert that the two integrate calls never overlap: a concurrency counter whose maximum is 1, and the order is first then second.
- **The base moved under the second pass's files.** When the first landing finishes, it records the files it moved. The second call answers `base-moved` when the files overlap and `merged` when they don't. Use the real `baseMovedOn` from `@lingtai/repo` for that decision, so the fake decides by the production rule.
  - With overlap: the second pass's run stream has `build` and `review` `StepStarted` after its first `merge`, then a landing.
  - Without overlap: neither appears.
- **Release on a throw.** The first fake `integrate` throws, and the second still lands.

`a-base-that-moved.test.ts` already proves what `runPass` does with a `base-moved` answer. This test proves only that the lock produces one.

**What no unit test can check:** that a real second `git fetch` sees the first push. That is `packages/repo/integration/integrate.test.ts`'s territory, which runs after the merge (0060 §1). The unit-level stand-in is the fake base above, deciding through `baseMovedOn`.

`schedule.ts` still runs one pass at a time, and running several is other tickets in #341. This lock is exercised only by the test until slots exist, which is the intended order.
