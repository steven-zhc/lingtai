# #682: design note

## The decision the ticket leaves open: the helper has to work one event at a time

The ticket describes the helper as taking "a stream's events". But one of the two readers it names never holds the whole stream:

- `reduceTicket` is just `events.reduce(applyTicket, emptyTicket)` (`packages/domain/src/ticket.ts:457-458`).
- `applyTicket` is exported and folded one event at a time by the board: `item = applyTicket(item, e)` (`apps/board/src/lib/task.ts:768`).
- `task_view`'s projector, which is the next ticket, folds the same way.

A helper that only takes a whole array therefore can't be called from inside `applyTicket`. If you build the whole-array helper and then add a second check inside `applyTicket`, you get the two separate implementations of the rule that this ticket exists to remove.

So build the rule as one per-event function, and make the whole-stream form a loop over it:

```ts
// packages/domain/src/claims.ts (new), exported from index.ts
export type ClaimShape = 'claim' | 'continuation'
/** null for an event that is neither. `claimed` = runIds a TicketClaimed already carried, earlier on this stream. */
export function claimShapeOf(event: Envelope, claimed: ReadonlySet<string> | readonly string[]): ClaimShape | null
/** The whole-stream form: one entry per claim-shaped event, in order. */
export function claimsOf(events: readonly Envelope[]): Array<{ event: Envelope; runId: string; shape: ClaimShape }>
```

- **`applyTicket` already keeps the set of claimed runs.** `state.runs` is appended to only in the `TicketClaimed` case, and only when the runId is new (`ticket.ts:279`: `runs: state.runs.includes(d.runId) ? state.runs : [...state.runs, d.runId]`). So `applyTicket` passes `state.runs` and needs no new state.
- **`priorAttempts` already keeps it too, as `byRun`** (`attempts.ts:154`). It can call `claimShapeOf(event, byRun)` after changing the helper's parameter to accept a `Map`'s keys, or it can iterate `claimsOf`. Pick whichever keeps the existing `cardFactOf` loop (`attempts.ts:156-176`) intact.

The rule, which is ADR 0109 §5's (`doc/decisions/0109-the-core-takes-a-ticket.md:115-116`): *"a `TicketClaimed` whose `runId` was already claimed on its stream is read as a `TicketContinued`."*

- Only a `TicketClaimed` adds a runId to the claimed set. A `TicketContinued` never does, so a `TicketContinued` on an unknown runId leaves the set unchanged.
- **Do not read `title`/`kind`.** The ADR describes the old form as `title: null, kind: null` (`:111`), and then says *"The rule is structural, needs no text read"* (`:116-117`). A first claim made "without the queue entry to hand" is also null/null (`events.ts:206-208`), so testing nulls would misclassify it as a continuation.
- A `TicketContinued` whose runId has no earlier claim still returns `'continuation'` from the helper. Each reader decides what to do with it (next section). That keeps the helper free of any policy.

## The catalogue

- Add `TicketContinued = z.object({ runId: z.string(), worker: z.string() })` directly after `TicketClaimed` (`events.ts:188-213`).
  - Its doc comment cites 0109 §5 at its path, `doc/decisions/0109-the-core-takes-a-ticket.md`. That ADR is in `decisions/`, not `decisions-archive/`.
  - The comment states the old form and the rule in one sentence, and says that `claimShapeOf` is where the rule lives.
- Register it wherever `TicketClaimed` is registered (`events.ts:2056`).
- Add it to `EVENT_AT` as `['claim']`, next to `TicketClaimed: ['claim']` (`:2147`). The `satisfies` at `:2210` will refuse a missing entry, so `tsc` catches it.
- Do **not** add it to `BUMPED` (`:2216`). Leaving it out is what makes its `SCHEMA_VER` 1 (`:2237-2239`).
- Run `pnpm events:generate` (`package.json:31`). `domain/unit/events-json.test.ts` and `events-diff.test.ts` check `doc/events.json`, so expect them to fail until you regenerate.
- `domain/unit/retired-names.test.ts` is 74K and may enumerate types. Run it, and don't patch it blind.

## `applyTicket`

- Add `'TicketContinued'` to `LIFECYCLE_EVENTS` (`ticket.ts:223-230`). Otherwise a continuation on a closed ticket would get past the absorbing guard (`:247`). Today the old form is absorbed there, so this is required to preserve behaviour.
- Make the two event types share one body:
  - If the event is a `'continuation'` whose runId is in `state.runs`:
    - set `lifecycle: { status: 'claimed', runId, worker }`;
    - leave `runs` untouched;
    - set `pendingPrompt: null`;
    - apply the version via `...at`.

    The old form does exactly this today. The `includes` at `:279` is the de-duplication, and `pendingPrompt: null` is unconditional (`:288`). The ticket's watch-out is right that the pending prompt is consumed, and nothing shows otherwise.
  - If it is a `TicketContinued` whose runId is **not** in `state.runs`, return `{ ...state, ...at }`, as the edges section asks: it continues nothing and records nothing.
  - Otherwise it is a claim: today's body, unchanged.
- An old-form `TicketClaimed` never reaches the unknown-runId branch. By definition its runId is in `runs`, otherwise it is a claim.

## `priorAttempts`

- `'continuation'`, of either form, maps to `break`. That is today's `if (byRun.has(d.runId)) break` (`attempts.ts:186`).
- Don't touch `ended`. A continuation today leaves the attempt's `ended` as whatever `WaitStarted` set (`blocked, asking: …`, `:173`), and the ticket asks for today's output.
- `armFor` (`:231-240`) and `prompt.ts:112` read `priorAttempts`, so they follow automatically.
- The comments that describe `continueTicket` writing a `TicketClaimed` are still true, because nothing writes the new event yet (`attempts.ts:180-185`, `:214-224`; `claim.ts:200-208`). Leave them for the child ticket that changes `continueTicket`.

## Tests (all unit tests, using in-memory `Envelope[]` fixtures; no store needed)

- **`domain/unit/claims.test.ts`:**
  - an old-form continuation is classified `'continuation'`;
  - a `TicketContinued` is classified `'continuation'`;
  - a first `TicketClaimed` with null title and kind is classified `'claim'`;
  - two different runIds give two claims;
  - a `TicketContinued` on an unknown runId is a `'continuation'` and does not add its runId to the claimed set: a later `TicketClaimed` of that runId is still a `'claim'`.
- **One fixture pair per reader.** Each fixture is: claim(r1) → `WaitStarted` for r1 → `WaitResolved{Approve}` → `PromptEdited` → continuation(r1), once in the old form and once as `TicketContinued`.
  - Assert `reduceTicket` gives the identical `TicketState`, ignoring `version`/`lastSeq`, which only differ if the seqs differ. Keep the seqs equal and assert the whole state.
  - Assert `priorAttempts` gives the identical output.
  - Assert those values literally (one attempt, `runs: ['r1']`, `pendingPrompt: null`, `claimed`), so that "today's output" is pinned rather than just "equal to each other".
  - Use the `WaitStarted`/`WaitResolved` builders that `ticket.test.ts` already uses.
- **Closed absorbs:** close a ticket, then send a `TicketContinued`; the lifecycle stays `closed`.
- **Unknown-runId `TicketContinued`:** in `applyTicket`, nothing changes except the version.
- Run `pnpm test` and `pnpm typecheck`. The integration half is not needed: nothing here touches a store, a process or a projection table.
