# Design: #917, the running panel quotes the agent, and the run log has one tail

The ticket's citations into `standing.tsx` were written before #916 landed and are now out of date. The current lines are:
- `RunningPanel`: `standing.tsx:259`
- `following`: `:1030`
- the `swhere` section: `:1286`
- `FollowedLog` in `swhy`: `:1334-1373`
- `RunningPanel`'s mount: `:1407`

Three things are not obvious from the ticket. The first one changes the ticket's own Fix (4).

## 1. Hold-on-end: lift the state up, not the element

Fix (4) asks for *one `FollowedLog` element, in the same position in the tree*, sitting inside the panel while the run is live and where `logBelow` puts it once the run has ended. React cannot do both. The two places are different parents:
- `RunningPanel` is mounted only while `standing.state === 'running' && standing.running` (`standing.tsx:1406-1408`).
- `swhy` is inside `swhere`.

An element that moves from one parent to another is a new mount, so the open state and the lines are lost. That is exactly the close-under-the-reader that `heldRun` exists to prevent (`run-log.tsx:310-318`: *"Derived, the log would unmount under the person reading its last lines — its open state and its scroll gone with it"*).

So the state stays put and the views move:

- **`FollowedLog` becomes a provider at one fixed position.** `Standing` renders it every time, whatever the state, wrapping both the `swhere` section and the panels (`QueuedPanel`, `RunningPanel`, the blocked reading).
  - It keeps `held` / `heldRun` / `logBelow` as they are.
  - It owns the tail: `useLogTail(shown, live || open)`, where `live = running === shown`.
  - It puts `{ shown, live, below, lines, state, open, setOpen, tags }` into a React context.
  - With `running === null` and nothing held, it renders only its children.
  - If it were rendered only in some states, every state change would remount the whole reading.
- **The views are small client components that read that context**, so they can mount and unmount anywhere inside it:
  - `<SaidLast/>` goes inside `RunningPanel`, under `<Meters>`.
  - `<RawRunLog where="running"/>` goes inside `RunningPanel`, under *Then*. It draws only when `live`.
  - `<RawRunLog where="ended"/>` goes at the end of `swhy`, after the `Reason` block. It draws only when `below`, which replaces today's children-reorder.
  - `RunningPanel` is a server-rendered tree and cannot take a render prop, so a context is the only way in.
- **Open state lives in the provider and is keyed by run.** Use `const [opened, setOpened] = useState<string | null>(null)` and `open = opened === shown`.
  - A new run is therefore closed without remounting anything.
  - Do **not** key the provider by `runId`: that remounts all of its children, including the discussion box inside `RunningPanel` (`standing.tsx:310-312`).
  - `useLogTail` already restarts when its `id` changes: `start` depends on `id` (`run-log.tsx:229`) and clears the lines (`:176`).
  - `useLatch` is not used here. Its only effect is to open the log, which is the opposite of *closed by default*. Opening only by the reader is what `opened` does.
- **Scroll.** `RawRunLog` follows the bottom while the reader is at it. A reader who scrolled back keeps their place, including across the remount from the panel to `swhy`: the place (`run`, `top`, `pinned`) lives in the provider and is restored by the new element. The place is about one run (`run`), so another run's log starts pinned to its bottom.
- **What the reader sees.** The `<details>` DOM node is replaced when the run ends, but it reads `open === true` and the same `lines` from the provider. Lines and open state are what the reader would notice; nothing they can see is lost.
- **`swhere` is not drawn for `running`.** Nothing in it holds the tail any more, so not drawing it costs nothing. The queued case (`standing.tsx:1281-1288`, *"stays mounted, with `FollowedLog` in the same place"*) keeps its quiet section. The reason in that comment now rests on the provider, so update the comment.

`RunLog` (`run-log.tsx:259`) stays for the record's attempt tabs, unchanged.

**Tests.**
- `FollowedLog`'s render tests use `renderToStaticMarkup` on the provider plus the views. Effects do not run there, so no `EventSource` is needed.
- The *ended* move is a pure claim on `logBelow` / `heldRun` and is already tested. The new claim to test is that `open` is computed from `opened === shown`: a pure `openFor(opened, shown)` helper, tested alone, next to the `live || open` rule.

## 2. A phase boundary: stop at the newest `started ·` line

Matching on the tag alone breaks the ticket's own edge, *an earlier round's lines are never shown as this round's*. `review:review` has the same tag in every round, so round 2's review would show round 1's sentences until round 2 wrote one.

The log already marks every action's start. `action.ts:842-843` writes:

```ts
context.log?.note(tag, `started · ${action.kind} on ${context.onSha.slice(0, 7)}${round}`)
```

where `tag = `${step}:${action.name}`` (`:820`) and the round suffix is ` · round N` only when `context.round` is non-zero (`:821`). The ticket's evidence shows one: `02:06:53  implement:write the change started · agent on 87dc4f4 · round 1`.

**The rule:** scan the held lines from newest to oldest, collecting said lines for the tags in flight. Stop at the first start line that is a **phase boundary**: one of another step's, or the phase's first action (`tags[0]`).
- A later action of the same phase (a second reviewer) is only an action boundary and is skipped: the earlier action's speech still belongs to this round.
- A start line of a tag outside the phase means a later phase has started, or the board's events got ahead of the file and the current phase has not written its start line yet.
- Either way, nothing older belongs to this round.
- This needs no round arithmetic.

This works for the implementer and the fixer too, even though their prose is not tagged with the action's tag:
- `implement` runs as the work action `write the change` (`conduct.ts:3542`). Its start line therefore carries `implement:write the change`.
- `dispatch` then writes the agent's lines through `runLog` untagged (round 0, `conduct.ts:3833`) or through `taggedTrace(runLog, \`fix:${round}\`)` (`conduct.ts:4093`).
- So the start line comes first, and the agent's lines follow it with a different tag.

**Recognising a start line.** Put `runLogStarted(line): boolean` in `run-log-format.ts`, beside `runLogSaid`:
- The label column holds a `:` (an untagged adapter label like `agent`, `Bash` or `think` never does).
- The rest of the line matches `started · \S+ on [0-9a-f]{7}( · round \d+)?$` exactly.
- Tagged prose cannot match: `taggedTrace` puts the adapter label first in the detail (`run-log.ts:173-177`).
- A sentence an agent writes that ends in that exact shape falls under *lines a reviewer could construct*, which the ticket puts out of scope.

**What a missed boundary costs.** The two copies of the format must agree here: `action.ts:843` writes the start line and `runLogStarted` reads it. Add a unit test in `packages/agent/unit/` that builds a start line with `runLogLine` in the same shape. Do not add an import from `@lingtai/actions`. A change to the writer that goes unnoticed costs fewer quotes, never wrong ones: no start line found means the scan runs further back, and only into lines with other tags, except in the shared-tag case above.

**Empty states.**
- *Nothing said in the last 2,000 lines*: no start line was found **and** the buffer is full.
- *Nothing said yet in this round*: every other empty case.
- Export `KEEP_LINES` from `run-log.tsx`, or expose a `full` flag from the provider. Do not copy the number.

Put the scan, `saidLast(lines, tags, n = 3)`, in a pure board module such as `apps/board/src/lib/said.ts`, built on `runLogSaid` and `runLogStarted`. It is the board's rule (three lines, newest first, stop at a phase boundary), not part of the log format.

## 3. Where the tags come from: computed on `RunningPanelView`

Add `said: readonly (string | null)[]` to `RunningPanelView` and compute it in `runningPanelOf` (`apps/board/src/lib/running.ts:89`). That function already has everything it needs:

| Case | `said` |
|---|---|
| `now === null` | `[]`, so *Nothing said yet in this round* |
| `fix` (`now.step === 'implement' && now.round > 0`, `:92`) | `` [`fix:${now.round}`] `` |
| `implement`, round 0 | `[null]`, the untagged reading |
| any other step | `planned(now.step).map(a => \`${now.step}:${a}\`)`, empty when no plan is known |

Pass `standing.running.said` to the provider as `tags`. The test of this table goes beside the existing `runningPanelOf` tests. It is the unit-level stand-in for *the page passes the tag of the phase in flight*.

**Judges are not quoted.** A judge writes under `judge:<when>` (`conduct.ts:2766`). It runs at `proposed`, which `planned` names by plan entry and not by `when`, and it writes no `started ·` line. So while a judge is deciding, the panel says *Nothing said yet in this round*, because `proposed`'s start line, or the previous phase's, stops the scan. Say so in a comment, not in the UI: the judge's JSON answer would be filtered out by the `{` rule anyway.

## Format module

The ticket lists `LABEL_AT`, `LABEL_WIDTH`, `runLogLine`, `RUN_LOG_END` and `runLogEnded` to move. Move `runLogEnd` and `RunLogEnding` with them. `runLogEnded`'s comment says the writer and reader live in *"one module, so the two cannot drift"* (`run-log.ts:200-201`), and splitting them would make that sentence false. Both are pure. `run-log.ts` re-exports all of them, so no call site changes.

`packages/agent/package.json:8` gets `"./run-log-format": "./src/run-log-format.ts"`.

The no-import test is the only thing before the merge that stands in for `apps/release/integration/build.test.ts`. The board must import `runLogSaid`, `runLogStarted` and `LABEL_*` from `@lingtai/agent/run-log-format`, never from `@lingtai/agent/run-log`.
