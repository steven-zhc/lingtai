# Design note for #695: a Python detector for setup

## Where it goes

All of the detection goes in `apps/cli/src/detect-setup.ts`. Child 1's refactor has already landed. `StackDetector` is defined at `:51-55`, and `DETECTORS` at `:201` is currently `[nodeDetector]`. Add a `pythonDetector` with `stack: 'Python'` and append it to get `[nodeDetector, pythonDetector]`. You do not need to change `detectSetup` (`:209-231`). Its comment already covers both stacks being present: *"The first stack present supplies `install` and `build`; every later one is only named in a note."* So in a repository with both a `package.json` and a `pyproject.toml`, Node wins and Python is named in a note. Put it in that order on purpose and test it.

Keep the detector free of side effects, as the file's header requires (`:6`: *"Pure. Everything here is a function of what `SetupReader` answers"*). The only part that touches this machine is the PATH note, and it goes in `setup-build.ts` (see below).

## Parse `pyproject.toml` with a real TOML parser

Add `smol-toml` as a direct dependency of `apps/cli`. Do not scan lines for `[tool.ruff]`, for two reasons:

- **Tables are often implicit.** A project that configures ruff with only `[tool.ruff.lint]` never writes a `[tool.ruff]` header, and a header scan would decide it has no ruff. With a parser, the check is `typeof parsed.tool?.ruff === 'object'`, and that is also true for `[tool.ruff.lint]` alone. The same check covers `tool.mypy` and `tool.pytest.ini_options`.
- **The ticket needs to know the file failed to parse.** Its edge *"a configuration file that does not parse: a note says so"* cannot be met by a scan that never parses anything.

`toml@3.0.0` is already in `pnpm-lock.yaml` (`:4711`), but only as a dependency of `@effect/cli`. pnpm's strict layout does not let `apps/cli` import it. The CLI binary is bundled by esbuild (`apps/release/src/build.ts:155-159`, `bundle: true`), so a pure-JS parser needs no other change there. The lockfile changes, which is expected.

## How `pythonDetector` decides

**Presence.** Python is `present` when `pyproject.toml`, `uv.lock`, `poetry.lock` or `requirements.txt` is at the root. If any of those `has` calls rejects and none came back true, presence is `unknown`. Copy the `uncertain` pattern from `detectInstall` (`:104-117`): *"A lockfile whose `has` rejected is neither present nor confirmed absent."*

**Install.**

| What is at the root | Install suggestion | Note |
|---|---|---|
| `uv.lock` | `uv sync --frozen` | none |
| `poetry.lock` | `poetry install --no-interaction` | none |
| both lockfiles | `uv sync --frozen` | `poetry.lock is also at the root; uv.lock was used` (same wording as Node's `:121`) |
| `requirements.txt` and neither lockfile | none | says to create a virtual environment and type the install command |
| `pyproject.toml` alone | none | no `uv.lock` or `poetry.lock` at the root |

**Build commands need a manager.** If there is no lockfile there is no `uv run` or `poetry run` prefix, so suggest **no build commands at all** and add a note saying build commands are suggested only through uv or poetry.

This is my decision, not something the ticket states. A bare `pytest` would run against whatever Python happens to be on the conductor's PATH, not the project's environment, and that is the same reason the ticket gives no install for a project with only `requirements.txt`. Pin it with a test: `requirements.txt` plus `[tool.pytest.ini_options]` gives `build: []` and the note.

**Build order and names.** Use the same keys as Node's `BUILD_ORDER` (`:66-71`) so `printFound` and the recipe show them the same way:

| Name | Command | Configured by |
|---|---|---|
| `format` | `<prefix> ruff format --check .` | `tool.ruff` in `pyproject.toml`, or `ruff.toml` |
| `lint` | `<prefix> ruff check .` | same as `format` |
| `typecheck` | `<prefix> mypy .` | `tool.mypy`, or `mypy.ini` |
| `test` | `<prefix> pytest` | `tool.pytest.ini_options`, `pytest.ini`, or `tests/` |

`<prefix>` is `uv run` or `poetry run`. The `because` text names whatever triggered the command, for example ``[tool.ruff] in pyproject.toml`` or `tests/ is at the root`.

Only the files the ticket lists count. Do not add `.ruff.toml`, `setup.cfg` or `tox.ini`. The ticket's main warning is never to suggest a tool the project did not configure, so stay inside its list.

**Checking for `tests/`.** Use `reader.has('tests')`. Both real readers return true for a directory:

- `liveSetupReader` uses `existsSync(join(dir, path))` (`apps/cli/src/first-project.ts:716`).
- The GitHub reader treats any non-404 response from `/contents/<path>` as present (`apps/cli/src/add-github.ts:91-102`), and that endpoint returns 200 for a directory.

**Reads that fail.** These all follow the rule child 1 set: a failure means *could not tell*, never absent.

- **`has` rejects for a standalone file** (`ruff.toml`, `mypy.ini`, `pytest.ini`, `tests`): add a note `could not tell whether <path> is at the root` and do not suggest that tool from that file. It can still be suggested from the other source.
- **`pyproject.toml` exists but `read` returns `null`**: add the note `pyproject.toml could not be read`, as Node does for `package.json` at `:168-170`. The `tool.*` tables then count as unknown, not absent, and the standalone files still count.
- **`pyproject.toml` does not parse**: add the note `pyproject.toml does not parse` and handle it exactly like the unreadable case.

## The PATH note goes in `setup-build.ts`

`SetupWorld` is `QuestionWorld` (`apps/cli/src/setup-build.ts:25`). That type is shared and has only `ask`, `log` and `spin` (`apps/cli/src/question.ts:24-30`), so do not add the probe there. Add an optional `onPath?: (tool: string) => Promise<boolean>` to `AskInstallAndBuildInput` (`setup-build.ts:39-49`).

Pass it in from the only live caller (`apps/cli/src/recipe-flow.ts:317`), with a probe that walks `process.env.PATH`. When the field is absent, nothing is checked, so existing `setup-build` tests that build the input themselves keep passing unchanged.

`printFound` (`setup-build.ts:173-178`) is synchronous today. Make it async, and await it at the existing call site, which is already async.

**Probe only the first word of each suggested command, deduplicated.** That word is the manager: `uv` or `poetry`, and for Node `pnpm`, `yarn` or `npm`. Do not probe `ruff`, `mypy` or `pytest`. After an install they come from the project's environment through `uv run` or `poetry run`, so a missing global `ruff` is not a fault. If the project never declared ruff as a dev dependency, that is a wrong guess, and #436's one-time trial is what catches it.

If a probe answers false, log `<tool> is not on this machine's PATH; the conductor runs these commands here` and still show the suggestion. A probe that throws should log nothing. The PATH note is extra information, and setup should never fail over it.

## Tests

**`apps/cli/unit/detect-setup.test.ts`.** Every case uses a fake `SetupReader`. In addition to the ticket's checklist, cover:

- both lockfiles at the root;
- Node and Python in one root: Node wins and Python is named in a note;
- `[tool.ruff.lint]` alone counts as ruff;
- a `pyproject.toml` that does not parse gives a note, and no suggestion comes from it;
- a `has` that rejects gives *could not tell*.

**`apps/cli/unit/setup-build.test.ts`.** One case where `onPath` returns false for `uv`: the suggestion is still offered and the note is logged.

None of this needs the integration half. `pnpm test` and `pnpm typecheck` cover all of it.
