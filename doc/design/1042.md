## Design note — #1042

The ticket's shape is right. This note fills in three things it leaves open: how `spawnCommand` hands back its result, how interrupting `commandEffect` waits, and how the subscriber's failure is tested without starting a process. Line numbers are this worktree's. The pipeline ticket has landed here: `ActionPort`, `liftPromise`, `actionRunFace` and `promiseAction` are at `packages/actions/src/action.ts:804-850`, and the baseline already reads `"packages/actions": { "async": 6, "run": 0 }` (`effect-ratchet.baseline.json:8`).

### 1. `spawnCommand` reports the raw end, not the outcome

Today `spawnCommand(options, report)` (`command.ts:287`) builds every `CommandOutcome` itself. The one async step it has is `settleOnExit` (`:390-412`), and it is the only reason that function is `async`. Change `report`'s argument to a two-case end:

- `{ kind: 'exited', code: number | null, endedAt: number }`, sent from the `close` handler (`:414-424`) in place of `void settleOnExit(code)`;
- `{ kind: 'outcome', outcome: CommandOutcome }`, sent for the timeout, the abort, the spawn `error`, and the `close` that comes after a timeout. All four already build their outcome synchronously through `finish` (`:300-306`).

`finish` still sets `settled`, clears the timer and removes the abort listener before it reports. For an `exited` end, that means the abort listener is gone once the code is known.

`settleOnExit`'s body moves into `commandEffect` and runs after the resume, against the `endedAt` it was handed. `took` and `durationMs` are both computed from that `endedAt`, never from `Date.now()`. That keeps the rule in the comment at `:294`: *"When the process ended, so reading the result file is not billed to it."* The evidence strings stay the same, character for character, because the integration tests match them.

**One timing window changes behaviour, and this note decides it.** Today an abort that fires while `readResult` is still awaiting finds `settled === false`, sees `child.exitCode !== null` (`:366-369`), and reports `aborted`. After this change the exit code has already been reported and the abort listener has been removed, so the exit code's verdict stands. The command has exited and nothing is still writing, so `kept-run-action.ts`'s cleanup is still safe. The only thing that changes is which word the evidence uses for a command that finished before it was stopped. Nothing tests this window, and nothing should be added to pin it.

### 2. Interruption follows `claude-code.ts:682-690`, word for word

`spawnCommand` now returns `{ interrupt(): void; settled(): boolean; onSettled(cb): void }` instead of `void`:

- `interrupt` is the existing `onAbort` (`:358-377`), unchanged.
- `onSettled` registers a callback that `finish` calls after `report`.

`commandEffect`'s `Effect.callback` registration returns this cleanup:

```ts
Effect.suspend(() => {
  if (handle.settled()) return Effect.void
  handle.interrupt()
  return Effect.callback<void>((done) => handle.onSettled(() => done(Effect.void)))
})
```

So the interruption completes exactly when the abort path's report would have gone out:
- when the child's `exit` fires, or
- at the 5 s `SIGKILL` plus 1 s that `reportAbort`'s timers already guarantee (`:373-376`).

This keeps the six-second bound without adding a timer of its own. Two rules:

- **Do not use `Effect.callback`'s `signal` parameter, and do not combine `options.signal` with an internal `AbortController` through `AbortSignal.any`.** `options.signal` keeps its listener inside `spawnCommand` exactly as it is now. Interruption calls the same function directly.
- **`settled()` is checked first.** `onAbort` on a child that has already exited calls `reportAbort` at once (`:366-369`), and with `ownGroup` set that sends a group `SIGKILL` (`:361`). That is harmless today because `finish` returns early, but it is not something an interruption should do to a command that has already been reported.

An interruption that arrives after the resume, while `readResultEffect` runs, interrupts a file read. The child has already gone, so there is nothing to wait for.

**Neither guarantee can be checked before the merge.** Both live in `packages/actions/integration/command.test.ts`, which spawns processes. No unit test stands in for the interruption bound, and the review should read this cleanup against the `claude-code.ts` precedent rather than trust a green run. Do not add an integration test for interruption in this ticket: nothing interrupts these Effects yet (the ticket's *Edges*), and row 7 is where interruption gets exercised.

### 3. `readResultEffect` and its unit test

`readResultEffect(path?: string)` is `Effect.promise(() => readFile(path, 'utf8'))` folded with `Effect.catch` (or `Effect.orElseSucceed` on a `tryPromise`) into `{}`. Its JSON branch keeps the exact `problem` text from `:500-504`, and it never fails.

**Its unit test has to stay out of the filesystem.** By 0060 §1, the absent / blank / not-JSON cases are a filesystem test if they read a real file, and that would make them integration. Split the parse from the read:
- export a pure `parseResult(text: string, path: string)` that holds the blank and not-JSON branches;
- unit-test that function, plus `readResultEffect(undefined)` returning `{}`.

The *absent file* case then stands as the read's `catch` branch. Its real-file proof is the existing integration tests that run with `resultPath` set and no file written. Say so in the test's header.

### 4. The subscriber

- **`SubscriberFailed`** is defined in `subscriber.ts` as `Data.TaggedError('SubscriberFailed')<{ readonly message: string }>`. `work-loop.ts:497` records `err instanceof Error ? err.message : err`. A `Data.TaggedError` is an `Error`, and `causeSquash` hands `Effect.runPromise` that object itself, so `message` reaches `PluginFailed.data` unchanged. The unit test proves this claim, because nothing else can before the merge.
- **The command is injected, so the unit test needs no process.** `SubscriberPortOptions` and `SubscriberOptions` each gain an optional `command?: (options: RunCommandOptions) => Effect.Effect<CommandOutcome>`, defaulting to `commandEffect`. The field is optional and additive: `apps/cli/src/subscribers.ts:233` does not change, and the ticket's *"keeps its signature"* holds for every existing caller. The Done-when test calls `createSubscriber({ …, command: () => Effect.succeed({ ok: false, evidence: 'boom', … }) }).deliver(event)` and asserts `rejects.toMatchObject({ _tag: 'SubscriberFailed', message: 'boom' })` plus `toBeInstanceOf(Error)`. With `ok: true` it resolves.
- **`makeSubscriber`'s `deliver`** returns early, as an `Effect.void`, for the `on:` miss and for the other project's event (`:171`, `:173`). It yields `subject` and `env`, then yields `command(...)`. On `!ok` it does `yield* new SubscriberFailed({ message: outcome.evidence })`.
- **`createSubscriber`** lifts `subject` and `env` with `liftPromise` (`action.ts:819`), not a bare `Effect.promise`. `liftPromise` also catches a synchronous throw, and the face then rejects with that thrown value itself. That is what `subscriber.ts:156-157` promises: *"A rejection rejects `deliver`, and so is a `PluginFailed`"*. A plain `Record` `env` becomes `Effect.succeed(env)`.
- **Deleting `startCommand` changes nothing about waiting.** `deliver` already awaits the report through a promise (`:192-206`), and `work-loop.ts:491` already voids that promise. What `startCommand` added was `report`'s try/catch (`:273-279`). There is no `report` callback any more, so that try/catch has nothing left to protect.

### 5. `command.test.ts` and comments

- In the `a command the core does not wait for` block (`:149-229`), *still enforces the timeout* and *reports a non-zero exit* become `runCommand` calls. Before moving them, check whether the file's `runCommand` blocks already make the same assertions. If they do, delete the moved copies rather than duplicate them.
- *Returns before the command does* (`:157`) and *holds a report that throws* (`:208`) test only `startCommand`, so they are deleted along with it. That is the whole of *"rewritten only where it named `startCommand`"*.
- `startCommand`'s doc comment (`:238-268`) carries 0037 §3, §6 and §7's reasoning. Move what is still true — that the timeout bounds a subscriber, and that the exit code is read in exactly one place — into `subscriber.ts`'s *Where the failure goes* section (`:33-54`). Its line 44 (*"read in `startCommand`'s report"*) should name `makeSubscriber` instead.
- `index.ts:114` drops `startCommand` and adds `commandEffect`. `subscriber.ts`'s new names are exported beside `createSubscriber`.

### 6. The ratchet

The four `async` functions go, which takes the count from 6 to 2. `runCommand` and `deliverFace` are the only new `Effect.runPromise` calls, and both are listed in `effect-ratchet.faces.json` in sorted order:
- `packages/actions/src/command.ts` / `runCommand` sorts after `action.ts`'s two entries.
- `packages/actions/src/subscriber.ts` / `deliverFace` sorts before `packages/agent/…`.

`makeProcessAction`'s `run` is an `Effect.gen`, not an `async` function, and `createProcessAction` reaches the runtime through `actionRunFace`, which is already listed. If the ratchet prints a number other than 2 / 0, the code is wrong, not the baseline.
