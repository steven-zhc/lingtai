# Design: #320 — the App's credentials come from one source, and `config.yml` is the third

The specification is `doc/design/308.md` on `agent/308`, in its section *`packages/env`: the reader and the election*. Port that section's code from `7e5b817`, which is the env commit inside `cbd2713`'s chain: `git show 7e5b817 -- packages/env apps/cli/src/doctor.ts`. The branch is already present locally, so nothing needs fetching. This note covers only three things: where `7e5b817` is wrong, a gap in the ticket's account of `doctor`, and which existing tests change.

## What to take from `7e5b817` unchanged

- `GITHUB_CONFIG_KEYS`, `githubSectionFrom`, `githubRecordFromSection(section, home)` and `resolveAgainst`. The relative-path resolution against `stateDir()` is already correct there, and its unit tests assert it.
- `machineGithub(from)`, read through `machineChoiceFile` (`packages/env/src/index.ts:411`). It gives three answers: values, `{}`, or `unreadable`.
- The `source` refinement in `appValues`. When `from === process.env` and the election says `"environment"`, it checks `optional(idName, realEnvironment(from))` (`:398`). If the real environment does not name the id, the source becomes the first env file that does.
- `githubApp`'s not-set error appending `value.unreadable`, and doctor's `app N from <source>, key from <keySource>` (`apps/cli/src/doctor.ts:772`).
- `source: string` on `GitHubAppCredentials` (`:964`).

Do **not** take the `init`, board or docs commits (`1644a2b`, `cbd2713`). They belong to the other slices of #308. **`create-app.ts` is the one exception** — see *Addendum* at the end of this note: `configuration()` ended up needing `config.yml` as a third source too, so the version that landed is not `3684d12`'s and is not nothing.

## The decision: the winner answers every name, and nothing falls through

`7e5b817`'s `electGithubSource` keeps today's rule from `appValues` (`:1069-1079`). The owner goes first in the order, but every other source is still asked for anything the owner leaves out. The doc comment on `:1052-1053` states it: *"the source that names the id is asked first for every other name, and the rest only for what it does not say."* `7e5b817`'s own unit test pins exactly the pairing this ticket forbids:

```ts
// The env file says nothing about the webhook secret, so — and only then
// — the next source is asked, same as an ordinary fallback chain would.
expect(elected.get(WEBHOOK)).toBe("machine-secret");
```

That is App 222 from `.env.local` paired with App 111's secret from `config.yml`. **Change the election so that `get` asks the owner and only the owner.**

- When no source names the id, `get` answers `undefined` for every name, the webhook secret included.
- Delete the falls-back test, and reverse the case quoted above so it asserts `undefined`.
- Rewrite the comment at `:1052-1053`. It currently describes the fallthrough as the rule.

**Why this is safe for this process's own environment.** `process.env` already holds every env file's values, merged by dotenv at import (`:54-57`). So when `from === process.env` and the environment owns the id, the "environment" record already contains `.env.local`'s key path and secret. Removing the fallthrough loses nothing there.

It only changes the result for an **environment handed in** that names the id but not its key. For that case it is the intended change: such a pair is one nobody configured.

**The integration test it turns red, which the pass will not see.** In `packages/env/integration/env.test.ts:115-124`, *"lets a variable in the environment win over the file"* hands in `{ LINGTAI_GITHUB_APP_ID: "2" }` with a file naming App 1's key, and asserts `privateKey === "from-file"`. That is App 2 signed with App 1's key: the bug, written down as the expected behaviour.

- Under the new election that call throws *"Neither … PRIVATE_KEY_PATH nor … PRIVATE_KEY is set"*.
- Rewrite it to assert that throw, or give the environment its own key and assert that key wins.
- `pnpm test` does not run this file, so a stale assertion here goes red only after the merge (T11). Edit it in this change anyway.

The other webhook test (`:147-155`) already names the id in the file, so it still holds.

## Doctor: the ticket's fix covers tests but not the real command

The ticket says `machineChoiceFile`'s rule is what lets `doctor` find `config.yml`. That is true for a test that hands in `LINGTAI_HOME`. It is **not** true for `lingtai doctor` on an operator's machine:

- `doctorReport` passes `doctorEnvironment()` (`apps/cli/src/doctor.ts:2198`), which is `{ ...from }`, a copy (`:2218`).
- A copy is never `=== process.env`, so `machineChoiceFile` takes its second branch: `from["LINGTAI_HOME"] ? … : null` (`packages/env/src/index.ts:413`).
- On a machine that has not exported `LINGTAI_HOME`, which is the ordinary install, doctor never reads `config.yml`.
- The result: doctor reports *not set* while `conduct` (`githubApp()`, on `process.env`) authenticates from that same file.

**Fix it in `doctorEnvironment`, not in `packages/env`.** When `from === process.env && !inTest(from)`, write `LINGTAI_HOME = stateDir(from)` into the copy.

- `stateDir` answers the same value with the name set (`:996`), so no other check's reading moves.
- `machineChoiceFile` is the only place in `packages/env` that branches on the name (`:413`).
- `world.ts:211`'s rule is the same shape, and it is handed its own environment rather than doctor's.
- `inTest` is private to `packages/env` (`:84`), so either export it or test `VITEST`/`LINGTAI_TEST` directly, as `world.ts:211` does.
- An environment that is handed in keeps its current semantics, and `doctor-environment.test.ts` (integration) is unaffected.

**One limitation to accept, not fix here.** Doctor's copy is also not `process.env` for the `source` refinement: `realEnvironment(copy)` is the copy itself, and it already carries `.env.local`'s merged values. So an App whose id is in `.env.local` shows as `from environment` in doctor's line, while `githubApp()` in the daemon says `.env.local`.

- The pairing is still right; only the label is coarse.
- Leave a comment at `githubCredentials` (`doctor.ts:752`) saying so.
- Do not add a parameter to `runDoctor` for it. Every call site in `apps/cli/integration/doctor.test.ts` would move.

## Tests, and what stands in for what

Everything below goes in `packages/env/unit/github-app-source.test.ts`. It is pure, so it runs in `pnpm test`.

- **The pairing pair (the second and third Done-when items):**
  - A machine record `{ID:"222", KEY_PATH:"/machine"}` beside an environment record carrying only a stale `KEY_PATH` → `/machine` is chosen.
  - An env-file record `{ID, KEY_PATH}` placed before a machine record that names all three → the env file answers the id and the key path, and the secret is **`undefined`**.
- **The secret follows the App:** a machine record that names the secret, while the env file owns the id → `get(WEBHOOK)` is `undefined`. This is the cold review's reproduction, as a unit test.
- `githubRecordFromSection(..., "/home/.lingtai")` resolving `key.pem` to `/home/.lingtai/key.pem`. This is the `stateDir()` claim. `root` is never passed in, so there is no way for it to resolve against the checkout.

The `source` labelling depends on `realEnvironment` and on `exported`, which is captured at import. A unit test cannot reach `exported` without the filesystem, so the claim at the unit level is `electGithubSource(...).source` returning the owner's `label`.

The `realEnvironment` branch, the *no env files anywhere* case and the unreadable-YAML case stay as `7e5b817` wrote them in `packages/env/integration/env.test.ts`. They are verified after the merge, not in this pass.

`HOME=/nonexistent pnpm test` stays green for two reasons:

- `machineChoiceFile` returns `null` under `inTest` when `LINGTAI_HOME` is absent.
- A missing file is `{}` (`7e5b817`'s `machineGithub`, matching `machineDatabase` at `:253-256`).

## Addendum: `create-app.ts` was touched after all

This note's own list above was wrong about one commit. The cold review against the first pass found `configuration()` — the setup page's guard against minting a second App — still asked only `hasGitHubApp`/an env file for the id, never `config.yml`, so an installed binary with its App only in `config.yml` was offered Create beside the App it already had. That is the same stranding `githubApp()` itself was fixed against in this note's main section, one caller downstream of it.

What landed in `packages/conductor/src/create-app.ts`, in this same commit:

- `configuration()` asks `githubAppSource()` for a third, `config.yml`-only source once the environment and the env files have both answered null — the same precedence `appValues` already gives the three sources.
- It also asks `githubConfigUnreadable()`, so a `config.yml` that fails to parse answers `unanswered` rather than reading as *no App configured* — `hasGitHubApp` cannot tell the two apart on its own, and `configured: null` beside `unanswered: null` is the one combination that draws the Create button.
- The id alone is enough to call `config.yml` *configured*, matching `namedIn`'s existing rule for an env file: an `app_id` written ahead of `private_key_path` is a half-finished configuration, not an absent one.

None of this is `3684d12`'s version — it is scoped to exactly the three-source gap `githubApp()` already closed, asked through the same two functions (`githubAppSource`, `githubConfigUnreadable`) `@lingtai/env` exports for it. An agent picking up the `init` slice should assume `configuration()` already knows about `config.yml` and extend it, not port `3684d12` over it or add the third source a second time.
