# #686 — the shape

All four sites are folds over one item's own stream, and three are pure and exported (`backoffOf`, `standingOf`, `claimsOf`). The change is per event: `claimShapeOf(event, claimed)` from `@lingtai/domain` (`packages/domain/src/claims.ts:23`). Only `queued.ts` and `task.ts` change. Nothing in `packages/` does.

## Import `claimShapeOf`, not the domain's `claimsOf`

`task.ts` already exports a `claimsOf` of its own (`apps/board/src/lib/task.ts:1175`), which `loadTask` calls (`:1789`). The domain package exports `claimsOf` too (`claims.ts:32`, re-exported by `packages/domain/src/index.ts:14`). Add `claimShapeOf` to the existing `@lingtai/domain` import block (`task.ts:5-25`; `queued.ts:36` for the other file). Do not import the domain's `claimsOf`, and do not rename the board's. Renaming would be a second change hidden inside this one.

## Each site, and what "the same as today" means there

Today an old-form continuation is a `TicketClaimed` that repeats a runId. Every reader below already sees it as a `TicketClaimed`, so it is the yardstick for how each site must treat a `TicketContinued`.

1. **`backoffOf`, `queued.ts:211`.** Today *every* `TicketClaimed` moves `lastAttemptAt`, old-form continuations included. So a `TicketContinued` must move it as well: the test is `claimShapeOf(e, …) !== null`, not `=== 'claim'`. Keep a running set of claimed runIds as the helper's contract asks (`claims.ts:18-21`), even though either shape gives the same answer here.
   - The doc comment above this function says *"this fold and that row cannot disagree"* (`queued.ts:198-200`). The projection only handles `TicketClaimed` (`packages/projector/src/task-view.ts:243`), and the projection is out of scope. The two cannot actually disagree until something appends `TicketContinued`.
   - Leave the comment true by adding one clause: the projection's half is the projection ticket in #681. Do not touch `task-view.ts`.

2. **`LIFECYCLE_MOVES`, `task.ts:597`.** Add `'TicketContinued'` to the set. `standingOf` (`:764-769`) folds `applyTicket`, which already handles `TicketContinued` (`packages/domain/src/ticket.ts:268`). Without the addition, `since` would stay at the wait while the lifecycle had moved to `claimed`. `:808` (`latestLifecycle`) reads the same set and needs nothing else.
   - **Decision: plain set membership, even for a `TicketContinued` naming a run nobody claimed.** `applyTicket` ignores that event (`ticket.ts:271-274`: *"A continuation of a run nobody claimed continues nothing and records nothing"*), so `since` would move while the state did not.
   - That case has no old-form counterpart: an old-form `TicketClaimed` with an unknown runId is a fresh claim. Nothing writes either event today, so it costs nothing and is not worth a second rule here. Write it down in a one-line comment.

3. **The board's `claimsOf`, `task.ts:1185`.** Replace the `e.type === 'TicketClaimed'` test and the `claims.some(...)` dedupe with `claimShapeOf(e, claims.map((c) => c.runId)) === 'claim'`.
   - That is exactly today's dedupe: the helper's "a runId an earlier `TicketClaimed` carried" is the old `!claims.some(c => c.runId === runId)`.
   - A `TicketContinued` therefore never opens a `Claim`, the same as an old-form one today. That is what keeps `foldRun`'s attempt numbering and the run list unchanged.
   - The `!runId` guard stays as it is.
   - The `TicketReleased` branch below it is untouched.

4. **The title, `task.ts:1565`.** **Leave the type test as `TicketDiscovered || TicketClaimed`, and do not add `TicketContinued`.**
   - `TicketContinued`'s schema is `{ runId, worker }` and has no title (`packages/domain/src/events.ts:226-229`).
   - The old-form continuation writes `title: null, kind: null` and no `labels` (`packages/conductor/src/claim.ts:233`). The `?? title` and `Array.isArray` guards already make it a no-op in this loop.
   - So leaving `TicketContinued` out of the loop is the identical behaviour. Routing it through the helper would only add a way to get it wrong.

## The title test needs a seam

`loadTicket` is private and async, and it calls `loadProject` (`task.ts:1553`, `:1572`), so no unit test can reach the loop at `:1561-1569`.
- Lift that loop into an exported pure function, `ticketFieldsOf(own): { title, kind, labels }`, and have `loadTicket` call it. That is the only refactor this ticket needs.
- Keep the `:1547` comment on `loadTicket`, and add a line saying a continuation carries no title, which is why `TicketContinued` is absent from the loop.

## Tests

Put them in the existing `apps/board/unit/task.test.ts` and `apps/board/unit/queued.test.ts`. They are unit tests: envelopes in memory, no database. Build one stream fixture:
- a `TicketDiscovered` or first `TicketClaimed` with a title, kind and labels;
- a wait (`WaitStarted`) and an approval (`WaitResolved`);
- the continuation, in two variants:
  - old form: a `TicketClaimed`, same runId, `title: null, kind: null`;
  - new form: a `TicketContinued { runId, worker }`, same runId, same `at`.

For each reader, assert the old-form output against a literal value (today's), then assert the `TicketContinued` stream deep-equals it:
- `backoffOf`: same `Date`, which is the continuation's `at`.
- `standingOf(own, runs)`: same `since` and the same state.
- the board's `claimsOf`: length 1, same `Claim`.
- `ticketFieldsOf`: the title, kind and labels of the first claim, not null.

`at` is wall-clock data in the fixture. Give the continuation a distinct, fixed `Date` so the `backoffOf` and `since` assertions prove the continuation moved them, rather than the first claim.

Because nothing writes `TicketContinued`, no behaviour is observable in `events`. These unit equalities are the whole claim, and `pnpm test` checks them. Nothing here needs `pnpm test:integration`.
