## Design: `dist/vendor/` for srt's two vendored files (#1154)

**The blocker has landed.** `@lingtai/sandbox` is now imported from `packages/conductor/src/conduct.ts`, `packages/conductor/src/sandbox-service.ts` and `packages/agent/src/claude-sandbox.ts`, so `lingtai.cjs` contains srt today. Nothing here waits on #1150.

### Where it goes

- **A new `apps/release/src/vendor.ts`** holds four things:
  - the pin: the version `0.0.83` and the three paths with their sha256, written as a literal;
  - `vendorFiles(platform, arch)`, which returns `{ files: { path, sha256, mode }[], note?: string }`;
  - `checkVendor(version, read)`, which returns a refusal as a string, or nothing;
  - an impure `readVendor(root, platform, arch)` that does the resolve and the reads.

  The first three are pure. Only `readVendor` touches the disk.
- **`apps/release/src/build.ts`** gets one new step and an updated header comment. The header's layout block (`build.ts:4-9`) is the in-repo statement of what `dist/` holds, so `vendor/` goes there too.
- **`.github/workflows/release.yml:86`** adds `vendor` to the `tar` list.
- **`apps/site/public/install.sh` does not change.** It unpacks the whole tarball (`:122-124`).
- **`effect-ratchet.baseline.json` does not change.** `apps/release` is not one of its counted packages; the baseline lists `apps/cli` and eleven packages.

### Decisions the ticket leaves to the builder

1. **Check before emptying.** `buildRelease` empties `out` first (`build.ts:30`, `rmSync(out, …)`). If the vendor check ran after that, a refusal would leave an empty or half-built `dist/`, not "writes no `dist/`". So:
   - call `readVendor` as the first line of `buildRelease`, before the `rmSync`;
   - have it return the bytes it read, already checked;
   - write those same buffers later.

   The board build is the slow step, so a mismatch also fails in a second, not after `next build`.
2. **Hash the bytes you write.** Use `readFileSync` → `createHash('sha256')` → `writeFileSync(dest, bytes, { mode })`, followed by an explicit `chmodSync`. Do not hash the source and then `cpSync` it.
   - The file that was checked is then the file that ships.
   - The mode does not depend on what pnpm's store left on the source file.
   - `apply-seccomp` gets `0o755` and the jar gets `0o644`.
3. **Platform and arch are the host's**, `process.platform` and `process.arch`. That matches how the rest of the build works:
   - the hook is a host-native `bun build --compile` with no target (`build.ts:41-44`);
   - every `release.yml` matrix row builds on its own runner (`release.yml:31-34`), because a *SEA copies the Node that builds it* (`:3`).

   `buildRelease` takes no new option. `readVendor` takes them as parameters only so a test or a later cross-build can pass them.
4. **An unknown arch is a note, not a refusal.** On Linux with an arch other than `x64` or `arm64`, `vendorFiles` returns the jar alone plus a `note`, and the `if (process.argv[1] === import.meta.filename)` block prints it beside `built …`. This is the ticket's Watch out: a host without `apply-seccomp` still sandboxes.
   - Any platform other than `linux` or `darwin` gets nothing and a note, since Windows is out of scope.
   - A missing file **inside** the srt package, or a hash mismatch, is still a throw.
5. **The refusal text** names the path inside the package, the pinned sha256 and the actual one. A version mismatch names both versions and says the hashes in `vendor.ts` move together with the pin in `packages/sandbox/package.json`.

### What the unit half can check, and what stands in for the rest

Reading the real srt package from `node_modules` is the filesystem, so by 0060 §1 it is integration. That means `pnpm test` cannot hash the real files.

The unit test (`apps/release/unit/vendor.test.ts`) covers only the pure parts:
- `vendorFiles` for linux x64, linux arm64, darwin, and linux with an unknown arch (jar plus note);
- the pinned literal equals the ticket's three hashes;
- `checkVendor` refuses a wrong version, and refuses a fake reader that returns bytes hashing to something else. Its message must name the path and both hashes.

**One unit-level stand-in that the ticket does not ask for, and should get:** the unit test imports `packages/sandbox/package.json` as JSON and asserts its `dependencies['@anthropic-ai/sandbox-runtime']` equals the pinned version in `vendor.ts`. Without it:
- a ticket that bumps srt in `packages/sandbox` alone passes every pre-merge check;
- the release build is the first thing to refuse, after the merge.

With it, moving the pin without moving the hashes turns `pnpm test` red in the same diff.

### What is checked only after the merge

These are not reachable inside a pass:
- that `dist/vendor/` really exists with the right modes;
- that the hashes really match the installed package;
- that `build.test.ts:82`'s top-level list now includes `vendor`.

All of them run in `apps/release/integration/build.test.ts`. Change line 82 there, and add assertions on:
- the expected `vendor/…` paths for the host;
- `apply-seccomp`'s mode (`& 0o777` equal to `0o755`) on Linux.

Leave them for the integration half rather than running them as part of this ticket.

**Whether srt actually finds the files** in an installed release cannot be read from this log. There is no Lingtai event for srt's lookup. It shows up only as the absence of srt's *seccomp not available* warning from `checkLinuxDependencies`, and as no `npm root -g` child process. That is S10's canary (out of scope), not a test here.
