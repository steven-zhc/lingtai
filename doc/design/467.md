# Design: #467, the pass acts on `nextOf`

## Where it goes

The change is in `runPass`'s `while` loop (`packages/conductor/src/pass.ts:1408-1460`), in `holdFor` (`conduct.ts:3625`), and one new field on `PassResult` (`pass.ts:1167`). Leave `runStep`, `endingOf` and every body in `pass-steps.ts` alone. `runStep` already builds the visit's `StepOutcome` and puts it on `StepReached.outcome` (`pass.ts:1676`). The comment at `pass.ts:535-541` says *"Nothing reads it yet … #467 is what puts `nextOf` in charge"*. This ticket adds the reader.

## The loop, after the change

Keep the existing `if (ending.ending === 'routed')` branch first and unchanged. It is `proposed`'s way-through router, and that belongs to #462. Then, for every other visit:

1. **Decide whether `nextOf` is asked at all.** Ask it only when `reached.outcome` is defined, `at` is not `claim`, and `decidingAction(reached.outcome) !== null`.
   - `nextOf` throws on `claim` and `end` (`pass-next.ts:86-88`).
   - It throws on a `merge` that cleared without an `Integrated` (`pass-next.ts:111-113`). An empty `merge:` list or a fake without a lane reaches that case.
   - Today's `ending` decides in each of those cases. That covers `claim`'s declines, which keep today's behaviour (row 15).
   - `nextOf` is called in the loop, outside `runStep`'s `try`. Any `ImpossibleOutcomeError` that still escapes would take `end` with it, and `end` is the guarantee `threw` exists for (`pass.ts:1700-1720`). So wrap the call. On a throw, record `stoppedAt = { step: at, ending: threw(spec, error) }` and break. That is the same ending a throwing body gets today.
2. **If `nextOf` says `Advance` or `Landed` but `ending.ending !== 'passed'`, today's stop wins.** The plugins cleared and the *body* did not: it threw, or it answered `never-ran` itself (`proposed`'s judge, `pass-steps.ts:1252-1256`). Set `stoppedAt = { step: at, ending }` and break, as the deleted `!goesToTheRouter` branch did. This is the rule from that branch that 0120 §4 does not have. Keep it, and name it in the commit body.
3. **Act on the answer:**

| `nextOf` | what the loop does |
|---|---|
| `Advance`, `Landed` | `at = after(at)`, as `passed` does today. `Landed` at `merge` gives `after` = `end`. |
| `Propose`, and the visit's ending is `refused` or `asked` | Today's arrival: `onOffer(at, ending, …)`, the second `runStep(SPEC.proposed, …)` with `arriving: reached`, then `take`. Move the existing block as it is. |
| `Propose`, and the ending is `passed` | **Only `review` produces this.** `endingOf` turns a reviewer's `failed` into `passed` (`pass.ts:1830`), and `verdictRefusedAs` answers `Propose{ReviewFindings\|ReviewEmpty}` (`pass-next.ts:279-285`). Today `review` walks on to `proposed`'s way-through visit, which judges the findings. Do that: `at = after(at)`. Sending it down the arrival path instead would change rows 2, 4 and 5 and the `onOffer` it is judged against. |
| `WaitOnPerson` | `stoppedAt = { step: at, ending }`, `waitOn = next.reason`, then break. No router visit. `rested` stays `null`, as it is today for a stop that never reached `take`. |
| `Requeued{NeverStarted}` | `stoppedAt = { step: at, ending }`, then break, exactly as today. **Do not set `rested = 'requeued'`.** `conduct.ts`'s `outcomeOf` reads `never-ran` as `failed`, and `requeued` would write a different set of events. |

Then delete `ARRIVE_AT_THE_ROUTER` (`pass.ts:1026`) and `goesToTheRouter` (`pass.ts:1052`). They have to go together with the table above: the four permitted changes are exactly the cells where the table's answer differs from those two.
- `prepared` and `merge` were on the router list, and now `SetupRefused` and `CheckRefused` wait without visiting it.
- `AnswerUnreadable` at `review` used to pass on to the way-through visit, and now waits.

Fix the comments that name them: `pass.ts:956`, `:1744`, and `pass-steps.ts:1025`, `:1254`. Also `conduct.ts:3652`, and the `actions` reference the ticket names in `agent-action.ts`. Point each at `nextOf`. Do not chase any further references than those.

`RunRef` for `nextOf` is `{ runId: options.context.runId }`. `holdFor` puts the full one back on (see below), so nothing more is needed here.

## `PassResult.waitOn`

Add `readonly waitOn: WaitReason | null` to `PassResult`, importing `WaitReason` from `@lingtai/domain/wait` as `adapters.ts` does. It is set only in the `WaitOnPerson` cell. It is not a second `stoppedAt`: `stoppedAt` is still set on every stop, because `conduct.ts` reads it for far more than the hold (the `claim` early return at `:3680`, `outcomeOf`, the *merge it anyway* veto at `:3830`). **Change none of those readers.** #463 changes `runPass`'s return type, and this ticket adds one field.

## `holdFor`

```
pass.waitOn !== null
  ? patched(holdOf(pass.waitOn, { branch, base, findings }))
  : holdOfPass({...as today})
```

`patched` exists because `holdOf` cannot know two things that only `conduct.ts` holds. Both are fixture-visible:

- **`run`.** `wait.ts`'s `RunRef` has no `repairOf` (`wait.ts:60-63`), and `unpushed` is only known after the pass, from `notPushed`. Replace the hold's `run` with the one `holdOfPass` builds today (`hold-of.ts:97-102`).
- **`Ceiling.turns`/`costUsd`.** `holdOf` writes `null` on purpose (`adapters.ts`, *"0118 §3's rule: `null` rather than an invented zero"*). Row 14a asserts `turns: 10, costUsd: 1.1` (`what-a-pass-writes-today.test.ts:~1079`). Where the hold is a `Ceiling` and `ceilingHit !== null` (`conduct.ts:3141`), fill both from `ceilingHit`.

`ceilingHit` is set only for `out-of-turns`/`out-of-usd`. `interruptedAs` gives `BudgetExhausted` for exactly those two causes and `AgentCrashed` for `timeout`, which `holdOf` turns into `DidNotFinish`. So row 14b keeps today's answer through the adapter, with no special case. If `Declined.said` differs from today's `declined.said` (`conduct.ts:3353`) in row 7, apply the same treatment: overwrite it from `declined`. Do not edit the row.

**`holdOfPass` stays, and is reached only when `waitOn` is null.** That is the router's own rest: `rested === 'waiting'`, the way-through `stopped === null`, and a router body that failed. Here is how to read Done-when's *"deleted or used only by the adapter"* for this ticket:
- `nextOf` produces no `WaitReason` for those rests.
- The `ProposedEscalated{because}` they would become needs #460's `RouteEscalation`. Building `JudgeHandedOver{why: route.why}` here would claim a judge handed it over on a mechanical route where no judge ran (`NotAsked`).
- #462 moves `proposed` onto those functions, and #462 is what deletes `holdOfPass`.

Say this in the commit body. Do not delete its now-dead cases (`refused` at `prepared`, `held`, `did-not-finish`) in this ticket either. Retiring the whole function is #462's single change.

## The four fixture changes, and where each one shows

The test names below are suggestions. Each change is its own commit.

- **`prepared` refuses → `SetupRefused`, no routing.** Row 8 is not in the fixture (its header, lines 22-27: only `run:` can make `prepared` refuse, and that spawns a process). Prove it in `pass.test.ts` with a fake `prepared` plugin that refuses. Assert that `steps` has no `proposed` visit, `routes` is `[]`, and `waitOn._tag === 'SetupRefused'`.
- **Check before the lane at `merge` → `CheckRefused`, no routing.** This is row 9. The only line that moves is `'PassRouted'` in the run stream (`what-a-pass-writes-today.test.ts:641`). The hold is still `CheckRed`, through `holdOf`'s `CheckRefused` arm, which is the kept cell. If any other line in row 9 moves, that is a regression.
- **`AnswerUnreadable` before any judge.** Row 13 is the *router's* judge being unreadable. That is `proposed`'s body, and **it must not move**. Prove this change in `pass.test.ts`: a `review` reviewer whose result maps to `AnswerUnreadable` gives `WaitOnPerson`, with no visit to `proposed`.
- **`implement` changed nothing → `NothingProduced`/`FixerDisagrees`.** Rows 6 and 7 hold `DidNotFinish`/`Declined` through `holdOf` already (`adapters.ts`'s `NothingProduced` → `DidNotFinish` at `implement`). They may not move at all. If they do not, leave them. The behaviour that changes is *read off the whole step*: `changedNothing(outcome)` sees a kept `run:` after the agent. Test that in `pass.test.ts` with `implement: [agent, run]`, where the run commits.

## The five kept cells

Each kept cell already comes back to today's `Hold` through `holdOf` and the table above:

| Kept cell | How it comes back |
|---|---|
| `NotDone` at `implement` | `SetupRefused` at a step other than `prepared` → `DidNotFinish` |
| `timeout` | `AgentCrashed` → `DidNotFinish` |
| Restarts spent | The router's rest, on `holdOfPass` |
| `agent:` check at `merge` | `CheckRefused` → `CheckRed` |
| `claim` passed over | `claim` is never asked |

If a row for any of them moves, the fix goes in the loop or in `holdFor`'s patch, never in the row.
