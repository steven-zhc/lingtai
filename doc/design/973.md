# Design note — #973: the recipe editor

## Where it goes

- **New page:** `apps/board/src/app/setup/recipe/[project]/page.tsx`, with a small client component beside it for the textarea, the button and the result list.
- **New module:** `apps/board/src/lib/recipe-edit.ts`. It holds the read, the check, the stale-file test and the write. This is the code the unit tests exercise.
- **New action:** `saveRecipe` in `apps/board/src/app/actions.ts`, returning `ActionResult` from `@/lib/diff`. 0111 §4 names that file as where the board's controls live (`doc/decisions/0111-the-board-is-a-local-app.md:52-53`).
- **Edit:** `apps/board/src/app/projects.tsx:84-86`. Each project row gets an `edit` link beside `recipe`, pointing at `/setup/recipe/<project>`.

### Not under `/recipe/[project]`

That route is read-only, and a test enforces it:

- `apps/board/integration/recipe.test.tsx:336-347` says *"the scan is the segment's whole tree for a handler, a filesystem write and a server directive, and the page's imports followed through for the directive"*.
- Lines 369-383 fail on a `'use server'` or a `writeFile` in that tree or in anything the page imports.

So:

- No edit page goes under that segment.
- `lib/recipe.ts` must never import `lib/recipe-edit.ts`. The read page imports `lib/recipe.ts`.
- The editor may import from `lib/recipe.ts`, for example to export and reuse `faultOf` (`apps/board/src/lib/recipe.ts:421`).

That test is in `integration/`, so `pnpm test` will not catch a break. Keep the boundary by structure.

`/setup/` fits because the mock's crumb on `?v=4` is *add a repository*. 0125 §6 decides that editing is a page and not a wizard. It does not decide the URL.

### Step 3 does not exist yet

The ticket says the editor is also reached from step 3. That step is not on the board:

- 0125 *Not built yet* says *"`/setup/repository` still renders `terminal.tsx`"*.
- `apps/board/src/app/setup/repository/page.tsx` still renders `terminal.tsx`.

The link from step 3 belongs to the ticket that builds the wizard's step 3. The URL above is what that page should link to. Do not build step 3 here.

## The check is doctor's call, not `setRecipe`'s

There are two resolve paths. Use the one doctor uses.

- **Doctor's path:** doctor's `recipe: resolves for every project` goes `projectFilters` → `currentRecipe` (`packages/conductor/src/filter.ts:294`). That reaches `resolveLocalRecipe` (`packages/recipe/src/local.ts`), which does three things:
  - it runs `checkMachineConfig` on `~/.lingtai/config.yml`;
  - it runs `resolveAgent` against the signed-in runtimes;
  - it calls `resolveSource`.
- **`setRecipe`'s path** (`packages/recipe/src/write.ts:204`) calls only `resolveSource`. A text it accepts can still fail doctor: for example a recipe with no `runtime.agent` on a machine where two runtimes are signed in.

So resolve the draft in memory with the same function, swapping only the recipe file's read:

```ts
currentRecipe(state, undefined, undefined, {
  read: (p) => (p === recipePath(project) ? Promise.resolve(draft) : readFromDisk(p)),
})
```

- `currentRecipe` accepts `read` (`packages/conductor/src/projects.ts:157`, `LocalRecipeOptions.read` at `local.ts`).
- It passes `state.base` and `signedInHere` itself (`projects.ts:160-164`).
- Either the board then judges exactly as doctor does, or a test can show where they differ.

In `recipe-edit.ts`, take the whole `options` object (`read`, `signedIn`, `home`) as a parameter. The unit test can then run the real resolver with a `Map`-backed read and a stub `signedIn`, touching no filesystem and spawning no process.

**Show the resolver's message as it is.** That is the ticket's *Watch out*.

- `RecipeInvalidError` lists `path: message` problems (`packages/recipe/src/resolve.ts:48-54`). Show one line per problem, as the mock does.
- Use `faultOf` to tell the two cases apart. A `MachineConfigInvalidError` is refused just the same, because doctor would be red too. The message must name `config.yml` as the file at fault and not suggest the recipe is wrong. That is the same split the read page already makes (`app/recipe/[project]/page.tsx`, the `view.fault === 'recipe'` branch).
- An `AgentUnresolvedError` is the recipe's fault (`lib/recipe.ts:413-420`).

## Writing

- **Reuse `diskFiles.replace`** (`packages/recipe/src/write.ts:45-53`). It writes a file beside the target and renames it over: *"an interruption mid-write leaves the old file or the new one, never half of either"*. Thread it through `recipe-edit.ts` as a `RecipeFiles` (`write.ts:24-28`), so the test hands in a `Map`.
- **Change the temporary file's name** from `${path}.${process.pid}.partial` to include a `randomUUID()`. The board is one process. Two tabs saving at the same moment would write the same temporary file and rename whatever mix of the two ended up in it. Only `setRecipe` shares this code, and the change only makes it safer.
- **Write the text exactly as typed.** Never send it through `editRecipe` or `parseDocument`; `emit.ts`'s header says why nothing may re-serialise an edited recipe. Writing the text unchanged is what keeps the comments and the formatting.
- **One normalisation is required: `\r\n` → `\n`, applied before the check and the write.** A browser submits a `<textarea>` with CRLF line endings. Without this, every save turns the file into CRLF, and the stale-file comparison below fails every time.
- **Nothing to save:** if the normalised draft equals what is on disk, nothing is written. Answer *nothing changed*. `setRecipe` has the same rule (`write.ts:207`).

## Edges, decided

- **The file changed since the page loaded.** The page sends a hidden `loaded` field holding the sha256 of the text it rendered. Send a hash rather than the text, because a hidden input is not CRLF-normalised and the textarea is. The action re-reads the file and compares hashes. If they differ, refuse with *changed on disk since you opened it — reload*, and write nothing. A file deleted since loading reads as `null`, gives a different hash, and is refused the same way.
  - Between that comparison and the rename there is a short window, for example a `lingtai add` landing at that instant. It is accepted: this is one person on one machine, and the rename is still atomic.
- **The file is missing on load.** Say *no recipe at `<path>`*, with `underHome` as the read page uses it, and show no editor. Do not offer to create one. Creating a recipe is setup's job (0125 §1).
- **The read fails.** `readIfThere` (`local.ts`) rethrows anything other than `ENOENT`. The page shows that message and no editor. The action returns `{ ok: false, detail }`.
- **Unknown project.** Call `notFound()`, as the read page does, from `loadProjects`.
- **The daemon is mid-pass.** After a successful save, say: *saved — a pass already running keeps the recipe it read; the next pass reads this one*. 0104 §1: *"The file is read on every resolve, so an edit reaches the next attempt without a restart."* Do not tell anyone to restart.
  - One sentence of caveat, in the code comment and not on the page: the board checked the draft with **its own** loaded copy of the code. A daemon started on older code can refuse a plugin at a step the board accepts (CLAUDE.md, *code, restart, paste*). `lingtai doctor`'s `daemon: currency` is what reports that, and it is not this ticket's to close.
- **A retry.** Saving twice is harmless. The second save either matches the disk (*nothing changed*) or is refused as stale.
- **Event log.** Saving appends no event. 0111 §4 says *"Every control is a Server Action that appends an event"*. This is the first control that writes a file instead, and 0125 §6 is the accepted decision that makes it a board control. `lingtai add`'s `setRecipe` appends nothing either. The next pass records what it actually ran as `RecipeRecorded` on `rcp-<configHash>` (`packages/domain/src/events.ts:1073-1088`), and that hash is how a person can see whether a change took effect. Do not add an event type in this ticket, and do not edit 0111 here.
- **After saving,** call `revalidatePath` for `/recipe/<project>` and for this page.

## Effect

`apps/board` is not in `effect-ratchet.baseline.json`, so the ratchet stays green whatever this code looks like. 0101 §6 still applies. Write `recipe-edit.ts`'s save as an `Effect.gen`:

- wrap `files.read`, the resolve and `files.replace` in `Effect.tryPromise`;
- run it once with `Effect.runPromise` inside `saveRecipe`, which is the host's edge.

Do not add an `async` function to any package that is counted.

## Tests (unit: `apps/board/unit/recipe-edit.test.ts`)

All of these use a `Map`-backed `RecipeFiles` and the real `resolveLocalRecipe`, with `home` set to a fake path, a `Map` read, and a stub `signedIn`:

- **Does not resolve.** For example an unknown top-level key, which 0104 §2 says is *refused by name*. Expect `ok: false`, the resolver's own `path: message` in `detail`, `replace` never called, and the `Map` entry unchanged byte for byte.
- **Resolves.** Expect `replace` called exactly once, with the draft exactly as typed: the comments are still in it, and the CRLF input arrives as LF.
- **Atomic.** The claim the unit test can make is *the save goes through `RecipeFiles.replace` and nothing else*. The temporary-file-and-rename on disk is `diskFiles`'s job, and a test of it is integration (filesystem). Do not move one into `unit/`.
- **Stale.** A `loaded` hash that differs from the current file, and a file deleted since loading, are both refused with `replace` never called.
- **Machine-file fault.** A broken `config.yml` with a valid draft is refused, and the result names `config.yml`.

`apps/board/unit/projects.test.tsx:36-40` asserts the menu's `recipe` link. Add one assertion for the `edit` href there.

The visual check is the mock's `?v=4`: the card, the hint line with the path, and the results list. Mono text in a plain `<textarea>` is enough, with no highlighting. The hint must not repeat the mock's *Save runs `lingtai doctor`*: the page resolves the recipe and does not run doctor.
