# #973: design note

## Where it goes

**One new library function, in `packages/recipe/src/write.ts`, beside `setRecipe`.** Call it `saveRecipeText(project, { loaded, text }, { home?, files?, base, signedIn })`. It does three things, in this order, and touches nothing else:

1. **The stale check.** Read the file through `files.read`. If it is not byte-for-byte `loaded`, refuse with a reload message. That includes "it was there and is gone now".
2. **The resolve.** Resolve `text` in memory with `resolveLocalRecipe(project, { home, base, signedIn, read })` (`packages/recipe/src/local.ts:298`). The injected `read` returns `text` for `recipePath(project, home)` and hands every other path, which means `config.yml`, to `files.read`.
3. **The write.** Call `files.replace(path, text)`, writing the text exactly as typed. Never use `editRecipe` or any re-serialisation here: `write.ts`'s header says *"Nothing here re-serialises a recipe a person has edited"*. That is what makes the comments-and-formatting edge true.

`text === loaded` writes nothing and says so, the way `setRecipe` returns `written: false` (`write.ts:236`).

**Why `resolveLocalRecipe` and not `resolveSource`, which is what `setRecipe` calls (`write.ts:234`):** the ticket asks for doctor's judgement.
- Doctor reaches `resolveLocalRecipe` through `currentRecipe` (`packages/conductor/src/projects.ts:153`).
- That function also runs `checkMachineConfig` against `~/.lingtai/config.yml` and `resolveAgent` against what is signed in (`local.ts:316-336`).
- `resolveSource` alone does neither. It would save a recipe that names no agent on a machine with two runtimes signed in, and the next pass would refuse it.

**Doctor's extra row is not carried over.** `recipeRow`'s `agentRefusal` (`apps/cli/src/doctor.ts:2183`) lives in `apps/cli`, and the ticket's *Watch out* rules out importing doctor. Say this in the function's comment rather than reimplementing it.

**The atomic write already exists. Reuse it.** `diskFiles.replace` (`write.ts:44-53`) writes `${path}.${pid}.partial` and renames it over the file: *"an interruption mid-write leaves the old file or the new one, never half of either"*. Do not write a second temp-and-rename.

**Write it as an Effect** (0101 §6, *"every backend function that does IO is an Effect"*):
- Use `Effect.tryPromise` around `files.read`, `resolveLocalRecipe` and `files.replace`.
- Give the three outcomes their own failure tags: `stale`, `invalid` (carrying the resolver's `err.message` unchanged) and `missing`.
- Run it with `Effect.runPromise` only in the server action, which is the host's edge.

The ratchet counts neither `packages/recipe` nor `apps/board` (`packages/domain/unit/effect-ratchet.test.ts:25-35`), so nothing will go red if it is an `async function`. The rule still applies.

**The server action goes in `apps/board/src/app/actions.ts`**, the board's one `'use server'` module (`actions.ts:1`). Call it `saveRecipe`. It passes `signedIn: signedInHere` and `base: state.base`, the same arguments `currentRecipe` passes (`projects.ts:160-164`), and returns a plain `{ ok } | { ok: false, reason, message }` for the page.

## The pages

- **The editor's address is `/recipe/[project]/edit`.** The editor is a server `page.tsx` that reads the file once and hands its text to a small `'use client'` form: a textarea, a hidden `loaded`, and `useActionState(saveRecipe)`. **The client file imports nothing from `@lingtai/recipe` or `@lingtai/conductor`.** `apps/board/unit/client-graph.test.ts:98` fails on any `"use client"` file that reaches a server module. That is the #230 failure, and here it would only show up in the Next build after the merge.
- **When the file is missing,** the page says `no recipe at <path>` and renders no editor. The `missing` failure covers the file disappearing between load and save.
- **When the recipe will not resolve,** the page shows `err.message` verbatim. `RecipeInvalidError` already carries the path and the YAML path: `${where} is not valid:\n  steps.build[1]: …` (`packages/recipe/src/resolve.ts:53-55`). Do not draw the mock's *✓ recipe resolves* line beside a failure, and do not add a script-existence line.
- **After a save,** the page says the recipe applies from the next pass and that a pass in flight keeps the one it read. That sentence is true because the file is read on every resolve (`local.ts:18-19`, *"an edit reaches the next run and a daemon holds nothing stale"*).
  - **One caveat to know about, not to build for:** the board resolves with the board's code, so a recipe naming a plugin key the running daemon predates will save here and be refused there. That is CLAUDE.md's *code, restart, paste*, and doctor has the same blind spot.
  - **What settles "did it apply"** is the next `StepsResolved` for that project and its `configHash` (`packages/domain/src/events.ts:1058-1060`). No new event is appended for a save.
- **How you reach it:** add an *edit* link next to the existing `recipe` link in the project menu (`apps/board/src/app/projects.tsx:85-87`), plus one on the read-only view's header.
  - **Step 3 does not exist on the board yet.** 0125's *Not built yet* says *"`/setup/repository` still renders `terminal.tsx`"*. Keep `/recipe/<p>/edit` a stable address so the ticket that builds step 3 can link to it. Do not build step 3 here.

## The claim this breaks, and what replaces it

The view says it is read-only on purpose, and a test holds that line:
- `apps/board/src/app/recipe/[project]/page.tsx:25-31` says *"Read-only, and that is not fastidiousness … Editing is #206's"*, arguing from 0046 §4.
- `apps/board/integration/recipe.test.tsx:349-396` scans the whole `src/app/recipe/` tree. It fails on `use server`, on an import of `actions`, on `node:fs`, and on a `<form>` or `<button>` in the view's render.

[0125](doc/decisions/0125-setup-is-one-module-two-inputs.md) §6 is the decision that replaces that argument: *"Changing an existing project is editing its recipe YAML. Saving resolves the recipe and writes nothing that fails to resolve"*. 0125 already exists, so this needs no new ADR. Two edits follow:

- **Rewrite the page's "Read-only" paragraph:** the view still writes nothing, the writer is the `edit` segment, and it writes through `actions.ts`'s `saveRecipe` (0125 §6).
- **Narrow the `read-only` describe block to the view.**
  - The method-handler and `node:fs` scans keep covering the whole segment, `edit/` included. The edit page reads through `@lingtai/recipe`, not `node:fs`.
  - The `use server` and `actions` import scans, and the render check, cover the view's `page.tsx` and what it imports. They exclude `edit/`.
  - Add one assertion that `edit/` reaches `actions` and does not declare its own `'use server'`. That keeps *the board's one writer is `app/actions.ts`* true.

That test is in the integration project, so the gate never runs it. It is a single file with no Postgres, though. Run it alone before committing (`pnpm vitest run --project integration apps/board/integration/recipe.test.tsx`), not as part of the 803-second half.

## Tests (unit)

- **Add `packages/recipe/unit/save-recipe-text.test.ts`.** It runs on a `Map`-backed `RecipeFiles`, which is the seam `write.ts:23` names for this, with a fake `signedIn` and a `home` string. It touches no filesystem and spawns nothing. It covers:
  - unresolvable text is refused with the resolver's message, and the map's entry is unchanged;
  - `loaded` differing from the map is refused as stale, and nothing is written;
  - resolvable text lands through `replace` byte-for-byte, comments included;
  - a `config.yml` that `checkMachineConfig` refuses is refused, which proves the machine file is read.
- **"Written atomically"** is `replace` being the one call that writes. Assert that `saveRecipeText` calls `replace` and nothing else on the files. Do not re-test `diskFiles` on a real disk: that would make it an integration test.

## Edges the ticket leaves open, decided

- **A read that fails, other than a missing file** (`EACCES`): fail as the read error, and write nothing.
- **A retry after a successful save:** `loaded` is now stale against the file just written, so a second submit of the same form is refused. After `ok`, the form resets `loaded` to the saved text, so the next edit starts from it.
- **A crash or restart mid-save:** rename leaves either the old file or the new one. A leftover `.partial` file is harmless, because nothing reads it.
