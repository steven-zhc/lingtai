# Design note — #789, the events page as one list

## The non-obvious decision: the filter is applied after mount, never during render

`apps/site/next.config.ts` sets `output: 'export'`. Do **not** read `?step=` with `useSearchParams`. In a static export, a client component that calls it falls back to client-side rendering up to the nearest `<Suspense>`. The exported HTML then contains the fallback instead of the entries. That breaks the ticket's *every event in the HTML with JS off*, and only `next build` shows it. `pnpm test` and `tsc` won't, and neither will `renderToStaticMarkup` in a unit test.

Do it this way instead:

- The client component's initial state is always *no filter*, so its server-rendered output is the whole list.
- In a `useEffect`, it reads `window.location.search` and `location.hash` and sets the state.
- It writes the state back with `history.replaceState`, as the mock does (`doc/design/events-page.html:1215`).

A `#Name` hidden by the current filter clears the filter. Check this on mount and again on `hashchange`.

Don't copy the mock's structure either. It renders every entry from a JSON `<script>` in client JS (`events-page.html:232`, `:1163`). Take only the layout and spacing from it.

## Where the code goes

Three modules, split by what each is allowed to import.

**1. `apps/site/src/lib/event-filter.ts`: pure, no `'use client'`, no `node:` imports, nothing from `./docs` or `./events`.**

- `lib/events.ts` imports `node:fs/promises` and `./docs` (`events.ts:1-7`). Importing even `OUTSIDE` from it into a client file pulls the filesystem into the client graph, which is the #230 failure.
- So this module holds `OUTSIDE`, `NONE = 'none'`, and the following:
  - `parseStep(search, steps)` returns a step, `'outside'`, `'none'`, or `null` for an absent or unknown value.
  - `matches(at, filter)`: `'none'` matches an empty `at`. `'outside'` matches `at.includes('outside')` only, so the three events with no step are no longer counted as outside (today `events.ts:31` puts them there).
  - `counts(events, steps)`: per-node counts.
  - `byGroup(events)`: groups in first-appearance order from `events.json`.
- `lib/events.ts` re-exports `OUTSIDE` from here. Delete `bySection` (`events.ts:27`); nothing else uses it once `events-body.tsx` is rewritten.
- **This is where the filter's unit test goes.** There is no DOM environment in this vitest setup: `vitest.config.ts` sets no `environment`, and the site tests use `renderToStaticMarkup` (`apps/site/unit/events.test.tsx:4`). So *`?step=review` leaves exactly the events whose `at` includes `review`, and hides groups with none* is tested as `parseStep` + `matches` + `byGroup` over `doc/events.json`. Don't try to click a rendered component.

**2. `apps/site/src/app/docs/events/events-filter.tsx`: `'use client'`. The spine, the group headings with their counts, and the right rail.**

- Props are plain data only:
  - `steps: string[]`: `STEPS`, passed from the server page so `@lingtai/domain` isn't pulled into the bundle.
  - `index: { name, group, at }[]`
  - `entries: Record<string, ReactNode>`
- It renders the spine, then one `<section>` per group (heading, then `entries[name]` in a wrapper with `hidden` when unmatched), then the `.contents` rail.
- It returns a fragment: the article content and the rail must be siblings in `.doc-layout`'s three-column grid (`site.css:297-300`; compare `[...slug]/page.tsx:109-125`). So `page.tsx` places `<EventsFilter>` so that its rail lands in the third column, not inside `<article>`.
- The rail reuses the `.contents` class (`site.css:334-`) for sticky positioning and styling, with one link per group to the group's `id` and its count. It does **not** use `Contents` from `docs/contents.tsx`, which takes headings and hides itself below four (`contents.tsx:15`).
- Wrapping entries in a client component does not make them client code. A server component passed as a prop is rendered on the server, and the client receives the rendered output.

**3. `events-body.tsx`: stays a server component.** It renders each `Event` and the summary markdown, builds `entries`, and passes them with `index` to `EventsFilter`. `react-markdown` therefore stays out of the client bundle.

## The summary as inline markdown

- Use `react-markdown` (already a dependency; used server-side in `docs/document.tsx:7`) with `allowedElements={['p','code','strong','em','a']}` and `unwrapDisallowed`.
- Map `p` to a fragment so the summary sits on its own line without nested block elements.
- No `rehype-raw`, as in `document.tsx:124`. Unclosed backticks or `**` are then left as literal text, which covers that edge without extra code.
- Relative links: resolve with `new URL(href, base)`, where `base` is `https://github.com/steven-zhc/lingtai/blob/${doc.sha}/packages/domain/src/events.ts`.
  - Derive the `https://github.com/<owner>/<repo>/blob/` prefix from any `definition` URL, which already has this form (`doc/events.json`, e.g. `TicketDiscovered`). Don't hard-code the repository name in a second place.
  - Leave absolute and `#` links as they are.
  - The only relative link in today's data is `OutboxDelivered`'s `../../../doc/decisions-archive/0022-the-seams.md`. It should resolve to `…/blob/<sha>/doc/decisions-archive/0022-the-seams.md`. Use it as a test fixture next to a synthetic summary for `` `code` `` and `**bold**`.
- Don't use `resolveHref` from `lib/docs.ts`. It resolves against `doc/` for site pages (`document.tsx:110-115`), which is a different job.
- Keep `label()` (`events-body.tsx:14-18`) for the *defined* and *appended* links.

## Hiding, and CSS

- Hide with the `hidden` attribute, which the client sets after mount, so no CSS has to know the step names.
- Show `n of N` in a group heading, and hide the group, only while a filter is set.
- A node whose count is 0 renders as a disabled `<button>`.
- Spine nodes are `<button>`s. Without JS they do nothing, and that is acceptable: the page still reads as a complete document.
- Replace the `/docs/events/` block in `site.css` (`:586-` through the `.ev-body` rules), including the `:target` rules at `:597-598`; nothing renders `.ev-section` any more.
- Spine: `position: sticky; top: 0`, as in the mock (`events-page.html:169`). The bar isn't sticky (`site.css` has no sticky `.bar` rule), so `top: 0` is "under the bar".
- Entries: `scroll-margin-top` at least the spine's height.
- At ≤1080px the spine keeps today's `overflow-x: auto` plus a fixed `min-width` (`site.css:588`).
- The rail should do what `.contents` does at ≤1080px on the other doc pages; don't add a new rule for it.

## Tests that change

In `apps/site/unit/events.test.tsx`:

- *has a section for each step and for the lane outside the pass*: delete it. Replace it with:
  - each event's `id="<name>"` appears exactly once;
  - each of the ten `STEPS`, `outside` and `no step` appears in the spine with its count.
- *names no event in its own source* (`:36-46`): add `events-filter.tsx` and `lib/event-filter.ts` to its list.
- `renderToStaticMarkup(<EventsBody …/>)` still works on a tree that contains a client component. It renders that component's initial (unfiltered) state, which is the JS-off claim the first new case makes.

## What only the build can check

The *no server-only import in the client graph* claim is checked only by `apps/release/integration/build.test.ts` (the Next build), after the merge. The unit-level stand-in is a case that reads `events-filter.tsx` and `lib/event-filter.ts` as text and asserts:

- neither contains `node:`;
- neither imports from `@/lib/events`, `@/lib/docs` or `@lingtai/domain`.

It's cheap, and it fails on exactly the edit that would cause a second #230.
