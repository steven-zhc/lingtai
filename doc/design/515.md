I wrote the design note below. Two findings shaped it. Every `workItem` the grep finds is the subscriber's JSON payload key, not a conductor local as the ticket says. And no `workItemId` is left anywhere, so that part of the rename is already done.

# Design: #515

## The three verbs need no design

`claimWorkItem` and `releaseWorkItem` are exported from `packages/conductor/src/claim.ts:90` and `:199` and re-exported at `packages/conductor/src/index.ts:2,4`. `continueWorkItem` is at `claim.ts:158`. Nothing named `claimTicket`, `releaseTicket` or `continueTicket` exists yet under `packages/` or `apps/` (`git grep -w` finds nothing), so a plain replace collides with nothing. About half the hits are backticked names in comments (for example `attempts.ts:176`, `task-view.ts:613`, `domain/src/ticket.ts:76`, `daemon/src/control.ts:366`). The Done-when grep counts them, so rename them too.

## The 26 `workItem` hits are not locals: they are a wire key

No local named `workItem` or `workItemId` is left in the conductor. Every hit for `(?<![A-Za-z])workItem` is one field and the code that reads or writes it: the JSON that the daemon pipes on stdin to every subscriber command.

- Producer: `packages/actions/src/subscriber.ts:113`, `SubscriberPayload.workItem: EventSubject`, filled at `:172-187`.
- Consumer: `packages/extension/src/index.ts:59`, `NotifyPayload.workItem`. It is read in `describe` (`:104-107`) and checked in `parsePayload` (`:154-163`). Its error strings name the key: `'stdin carried no workItem — expected …'`.
- Fixtures and assertions:
  - `packages/extension/unit/describe.test.ts:3,16`
  - `apps/cli/integration/notify.test.ts:13,36,178,191`. Line 178 asserts that the error text `toContain('workItem')`.
  - `packages/telegram/integration/telegram.test.ts:27`
  - `packages/actions/integration/subscriber.test.ts:115`

**Decision: rename the key to `ticket`, and rename every site of it in the same commit.** The Done-when grep requires the rename, and the key is not a stored name: it is built per delivery and never appended. But it is a contract between two processes, and that changes two things.

1. **`tsc` does not connect the two sides.** `extension/src/index.ts:40-43` explains why: the extension declares its own narrower type (*"Narrower than `Envelope` on purpose: this is JSON from another process"*) and does not import `@lingtai/actions`. Renaming only one side still typechecks and still passes `pnpm test`.
   - The only test that crosses the boundary is `actions/integration/subscriber.test.ts:115`, which is out of reach.
   - The unit-level stand-in is `extension/unit/describe.test.ts`. Change its fixture, and change `subscriber.ts` and `extension/src/index.ts`, in **one** commit, even though the ticket says one commit per package. That commit is the only point where the two sides are checked against each other.
   - Also rename the key inside the two error strings and the assertion at `notify.test.ts:178`. Otherwise the message tells a subscriber author to send a key that is no longer read.
2. **Leave the type name `NotifiedWorkItem` (`extension/src/index.ts:51`) alone.** The ticket covers verbs and locals. The grep is case-sensitive and does not match it.

**Do not make `parsePayload` accept both `workItem` and `ticket`.** A fallback is a behaviour change, and the ticket rules those out.

The cost goes in the commit body instead. Both subscribers in the conducting machine's recipe are commands that load code fresh on every delivery:

- `node apps/cli/src/notify.ts`
- `node packages/telegram/src/cli.ts`

Both run in the daemon's own checkout (`SubscriberOptions.cwd`, `subscriber.ts:146`: *"There is no worktree for an event, so this is the daemon's own"*). Once this lands on disk, a daemon that has not restarted still sends `workItem` from the `subscriber.ts` it loaded at start. The new `parsePayload` then refuses every notification, each as a `PluginFailed` naming `desktop` or `telegram`, until `lingtai restart`. So write in the commit body that the subscriber payload key changed and that the daemon has to be restarted to pick it up. A count of `PluginFailed` events whose `data` names those subscribers after the merge would settle whether that happened.

## Shadowing

The ticket's warning does not apply to any site that exists today:

- `subscriber.ts:160-195` and `extension/src/index.ts:100-170` contain no `ticket` identifier.
- `conduct.ts` already uses `ticketId` (`:2085`), which is the parameter name `claim.ts:90` already takes.

So `const { event, ticket } = payload` and `const ticket = await options.subject(event)` shadow nothing. Check again only if a site turns up that this list missed.
