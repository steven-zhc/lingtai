# #691: design note

## Where the cap goes

Put the cap in `survivalCurve` (`packages/conductor/src/report.ts:306-325`) and nowhere else. The board, `lingtai report` and `--json` all read `report.survival`, which is built at `report.ts:476`. Capping it once caps all three. Don't cap only in `SurvivalPanel`: the CLI table at `apps/cli/src/report.ts:197-213` prints one row per step, and it would keep printing 34 rows.

Today's loop runs `for (let k = 1; k <= maxK; k++)` (`report.ts:317`) and keeps multiplying `survival *= 1 - passed / atRisk`. Keep that loop exactly as it is. Then split the steps it produces:

- **`k` from 1 to 6**: push the steps unchanged.
- **`k ≥ 7`**: fold them into one step:
  - `k: 7` and `plus: true`;
  - `atRisk` is the count at `k = 7`, which is `spans.filter((s) => s.k >= 7).length`;
  - `passed` and `censored` are the sums over every `k ≥ 7`;
  - `survival` is the running product after the last `k`, which is `maxK`.

For the 7+ step, `atRisk === passed + censored`. Every ticket counted at 7 ends somewhere at 7 or later. That gives the unit test a cheap invariant to assert.

Folding after the running product, rather than reducing `maxK` before the loop, is what keeps steps 1–6 identical. This is the ticket's *Watch out*. If you clamp `s.k` to 7 before the loop, a ticket that passed at review 12 is counted as passing at review 7. The bucket would then have the wrong `survival`, even though steps 1–6 would still match.

## The type

Add `plus?: true` to `SurvivalStep` (`report.ts:125-132`). Give it a doc comment saying the step is *k or more reviews*. Make it optional, not `plus: boolean` on every step: the existing tests compare whole step objects with `toEqual` (`packages/conductor/unit/report.test.ts:112`, `:122`), and steps 1–6 should still match them. `--json` serialises the object as it stands, so the JSON shape needs no separate change.

**When `maxK` is exactly 7**, still mark the step `plus: true`. The numbers are the same either way, and the label is then the same on every window that reaches 7. When `maxK < 7` there is no step at 7, so nothing is marked. That is the ticket's first edge, and it needs no code beyond the split.

## The §3 baseline test still holds, and why

`report.test.ts:68-85` builds tickets whose longest run is 8 reviews: 16 tickets censored at 8. It reads `survival[k - 1]` for k = 7 and expects 9%. After the cap, `survival[6]` is the 7+ step. Its `survival` is the product through k = 8. At k = 8 only censoring happens, so the factor is `1 - 0/16` and the value stays 9%. The test should pass unchanged. Don't change its expectation to make it pass. If it goes red, the fold is wrong.

Also add the Done-when test. Build rows with up to 34 reviews and compare the capped output's first six steps against the uncapped curve for the same rows. Get the uncapped curve by recomputing it inline in the test (the same few lines of Kaplan–Meier). Don't export a second function from `report.ts` just for the test.

## The panel (`apps/board/src/app/report/charts.tsx:230-276`)

- **Axis scale.** `K = steps.length` (`:232`) stays as it is; it is now at most 7.
- **Axis tick label** (`:250-254`): print `p.plus ? '7+' : p.k`, or `${p.k}+` so the 7 is not repeated. Add the axis caption *reviews done* under the ticks. `B = 26` (`:30`) leaves room for the ticks only, so the caption either goes at the right end of the axis row or `B` grows by about 14 for this panel. Pick one; neither changes another panel.
- **Remove the `n=` text** (`:271-273`) from every knot, including k = 0's *start*. The hover `<title>` (`:260-264`) already carries the count as `… still counted at this review`, and that line is now the only place the count appears.
- **Hover for the 7+ knot**: change *after 7 reviews* to *after 7 or more reviews*. Change *not yet past review* in that template to *still not passed*, so the hover and the legend use the same words.
- **Legend and aria-label** (`:240-241`): the legend becomes *still not passed*. The aria-label becomes *share of tickets still not passed after k reviews*.
- **Percentage labels** sit at `x + 7, y - 7` (`:268`). With 7 steps across `W - L - right = 452` units (`:25-27`), knots are about 64 apart, which is wide enough for a 3-character `NN%`. Nothing else needs to move to meet *labels never overlap*. The smear came from the step count, not from the label placement.

Update the doc comment above `SurvivalPanel` (`:225-229`). It currently says *each step is labelled with its `atRisk`*, and that stops being true.

## The page (`apps/board/src/app/report/page.tsx:109-114`)

Change the title to *reviews to pass* and the subtitle to *share still not passed after k reviews*. The ticket gives the subtitle; the current long subtitle's *falling fast is converging…* goes.

## The CLI

`apps/cli/src/report.ts:204-210` prints `String(s.k)` in the *review* column. Print `7+` when `s.plus` is set; otherwise that row says `7` for a bucket. The ticket doesn't mention this, but it follows from capping in the shared fold. The section heading *getting past review* (`:200`) and the *not yet past* column header can stay. *Out of scope* is any other panel, and these are CLI words, not the panel's. Renaming them is optional.

## Tests that change once

- `apps/board/unit/report-panels.test.tsx:86-103` asserts `n=10`, `n=5` and the old hover string. Change it to assert that no `n=` is drawn, that the hover contains *still counted at this review*, and that a step with `plus: true` draws `7+` on the axis.
- The Done-when page-title assertion (*reviews to pass*) belongs to whichever test renders `page.tsx`. If none renders it at the unit level, assert the title from a render of the `Panel` with those props instead, and say so in the commit.
