# #1211 — the shape

## Where it goes

All the parts the ticket needs exist already. This change adds `BaseRed` to the paths #1205 and #1208 built. It needs no new event and no new continuation path.

1. **`packages/domain/src/ticket.ts:858`**: add `'BaseRed'` to `CONTINUABLE_CAUSES`. Its comment already reads *"#1211 adds `BaseRed`"*. `continueTransition` (`:893-904`) then accepts a queued ticket released `BaseRed`, and it accepts it only at the version the look read (`expectVersion`, `conduct.ts:3032`). That check is the race guard the ticket's *Watch out* asks for. Do not touch `continueTicketEffect`.

2. **`packages/conductor/src/conduct.ts:1350-1352`**: the release-sourced branch returns `null` for any cause other than `AccountLimit` (*"#1211 adds `BaseRed` to the causes this takes"*). Give `BaseRed` a sibling block in the same `Effect.gen`. It returns the same object shape as the `AccountLimit` block (`:1376-1414`), with these differences:
   - `step: 'build'`.
   - `released.head`: the head this change computes itself (below), not `releasedHeadOf`.
   - `rerun: { for: null, prompt: null, accountReruns }`. Nothing was cut off mid-call, so nothing is asked again.
   - `resumedWaitId: \`base-red:${n}\``. Here `n` is the number of `BaseRed` releases on this `runId` in the ticket stream. Generalise `accountLimitReleases` (`ticket.ts:876`) to take the cause tag rather than copying it. The id has to differ between two continuations of one run (#580, `conduct.ts:2031-2035`).
   - A new `baseMerge: { toSha: B, action }` field on `released`, described below.

   The counters come from `continuationSpent(releasedState)` and `continuationRound`, exactly as for `AccountLimit`. That carries `roundsSpent`, `baseMerges`, `conflictRounds`, `stepRedos` and `landingRetries` forward (#1200). Do not reset any of them.

3. **`packages/conductor/src/run-attempt.ts`**: two small hooks in the walk loop (`:2048`). Both are needed because a continuation today skips the base check (`baseFirst` *"Never set for a continuation"*, `:955-960`), and nothing makes a merge at the start of a walk.

## The decisions

**The head is read before the claim, not at the cut.** The ticket requires that a failed read of origin leaves the ticket unclaimed. `TicketContinued` is appended before `admit` cuts (`conduct.ts:3027` against `:3203`), so a failure at the cut is too late. In the `BaseRed` block, before returning, run `ls-remote origin refs/heads/<branch>` through `repo.git([...], { token: options.token, env: options.gitEnv, cwd: mirrorPathFor(project, home) })`, the same call shape as `recordedPromptOf` (`:1320-1328`). Then:
- One line `<sha>\t<ref>` whose sha equals `cause.headSha` gives `head = { at: cause.headSha, atRef: branch }`. `provisionWorktree`'s own `at` check (`packages/repo/src/worktree.ts:222-237`) still runs at the cut and catches a push in between as `stale`, which is `headGone` (`conduct.ts:3246`).
- No line, or a different sha, gives `head = { cannot: \`the saved head ${sha7} of ${branch} is no longer on origin\` }`. From there #1205's path takes over: `notCut` at `:3205-3208`, then a restart while `reduced.restarts.length < ceiling.ticket.newAttempts` (`:5939-5956`), otherwise the person's wait carrying that sentence. **Do not add a `BuildRed`-specific wait.** The ticket names one, but it also says to use #1205's rule, and a second hold shape is the second path its *Watch out* forbids. The `Done when` check is that the wait names the head and offers `Requeue`. Assert that against whatever #1205's wait is.
- A failed `git` call, or output that is not `<sha>\t<ref>`, sets `releasedDeclined = \`origin could not be read: …\`` and returns `null`. `:3013` turns that into `notClaimed` and nothing is appended. It is never read as *head gone*.

**The base to merge is read before the claim too.** Use `repo.baseHead` through `fetchedHead` (`base-red.ts:60-64`) to get `B`, the base's head now. A read that fails declines the same way. If `B === cause.baseSha`, decline with *"the base is still at the red commit"*. The queue already passes the project over in that case (`lookAtBase`, `base-red.ts:72-83`), but `lingtai run --issue` does not go through the look. `action` is `baseStateEffect(...).red.action` (`base-red.ts:29`, `conduct.ts:5464`). If the state is not red (`notRed`/`unread`), take the first `run:` in `buildRunsOf(recipe)` whose `run` equals `cause.command`. If there is none, decline. A recipe that no longer has the command is no reason to merge blind.

**The green check is #1208's `baseFirst`, pointed at `B`.** Widen `AttemptOptions.baseFirst` to `{ action, baseSha?: string }`. In `conduct.ts:5463-5464`, set it for a `BaseRed` continuation as `{ action, baseSha: B }`. Keep `baseState`'s read for `continuation === null` only. In the `baseIsRed` port (`:4059-4061`), let `asked.baseSha` win over `mergedOnto ?? diffBaseSha ?? worktree.baseSha`, and pass it from the `prepared` hook (`run-attempt.ts:2059-2061`). Without this change the port checks `worktree.baseSha`, which on a continuation is `H`, the head itself (`worktree.ts:214`). What each answer does:
- **Red**: the existing hook releases `BaseRed` again with `headSha: onSha`, which is still `H`. The head is kept, no merge is spent, and the queue waits for the base to move again.
- **`notRed`, green or unknown**: go on. Unknown is not red, and the guard at `proposed` asks again on a `BuildRed` (`:1735-1741`), the same rule `baseFirst` already follows (`:2056-2058`).

**The merge is a real route, not a hidden merge.** Add `baseMerge?: { toSha: string }` to `AttemptOptions.from`. On the first arrival at `build` with `from.baseMerge` set, guarded by a flag like `grantedConflictMerged` (`:2123`), call:

    routing({ _tag: 'BaseMoved', paths: null, fromSha: null, toSha }, null, { findings: [], evidence: '' }, null)

and `continue` when it returns true. This gives everything the ticket lists, with no new code for any of it:
- `offerFor` offers `merge-base` with `merge: baseMerges + 1`. Once `BOUNDS.baseBranchMerges` is spent it offers `CeilingReached` instead (`packages/domain/src/failure/respond.ts:719-731`), and that goes to a person exactly as a spent `base-moved` does.
- `BUILT_IN_FOR['base-moved']` is `merge-the-base` (`respond.ts:876`), so no judge is paid.
- `mergeBase(toSha)` runs (`run-attempt.ts:1845-1850`). A failure ends at `JudgeHandedOver{ the base could not be merged in }` (`:1908-1925`).
- The `proposed` visit moves `onSha` to the merge commit, and `baseMergesSpent`/`mergedOnto` are set (`:1931-1934`).
- One `ProposalRouted` is written, which is the *"one `MergeBase` route onto `B`"* the first `Done when` reads.

`paths: null` means an unknown overlap, so #1210's carry does not apply (`:1943-1944`) and `review` reads the whole head. That is correct, because `H`'s last `build` was red, so no review ever read it. Computing the overlap to earn a skipped review is out of scope.

**A `BaseRed` released before any agent ran is not continued.** #1208's `prepared` hook releases with `headSha: onSha` where `onSha` is still the cut base (`run-attempt.ts:2062-2072`), so that head is no work at all. Continuing it would jump to `build` with nothing implemented, and its branch is usually absent from origin, which would buy a restart. In the `BaseRed` block, return `null` when `cause.headSha === diffBaseShaOf(releasedEvents)` without setting `releasedDeclined`. The look then makes an ordinary claim (`claimTicketEffect`, `:3036`; `claimTransition` does not look at the release cause, `ticket.ts:803-812`): a new attempt from the base with no restart counted, which is what happens today. A continuation's own `prepared` release keeps `H ≠ diffBaseSha`, so this predicate never catches it.

## What settles it in the log

On the continuation's `runId`, in stream order:
- `TicketContinued` on the ticket stream at the read version
- `BaseChecked` on `B` (integration stream)
- the `proposed` `StepEnded` with `head` = merge commit
- `ProposalRouted{ offer.proposal._tag: 'BaseMoved', decision → MergeBaseBranch{ toSha: B, merge: n+1 } }`
- `build`, `review`, `proposed` visits
- no `implement` `StepStarted`
