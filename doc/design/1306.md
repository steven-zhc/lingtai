## Design note for #1306

The ticket says what to build. This note covers the places it touches that it does not name, where the obvious version of the change breaks something.

### 1. There are three raw parses of the recipe, not one

`Recipe.safeParse` / `Recipe.parse` runs in three places outside tests:

- `packages/recipe/src/resolve.ts:260`, in `resolveSource`. The ticket names this one.
- `packages/recipe/src/declared.ts:57`, in `checkDeclared` ("the text alone, before any host, machine file or preset is asked", `declared.ts:2-3`).
- `packages/recipe/src/emit.ts:173`, in `editRecipe`, which validates the *edited* document with `Recipe.parse({ runtime: {}, ...doc.toJS() })`. Every writer goes through it via `editedText` (`write.ts:56-61`).

Once `branch` is required and `worktree:` is `strictObject` without `base`, the second and third parses refuse every file still in the old spelling. That includes this repository's own recipe. It also includes an edit that has nothing to do with the base: the setup page writing `env.plantAt` on an old file would throw at `emit.ts:173`. The old spellings would be broken at write time and at record time while the ticket keeps them readable at resolve.

**Decision:** the rewrite is one exported pure function in `resolve.ts`, say `readOldSpellings(raw): { recipe, found: string[] }`, and all three parses call it.

- In `resolveSource`, call it **after `applyPreset` and before `unknownKeys`**, so it sits where `retiredLimits` sits (`resolve.ts:245-248`). Running it after the preset is safe: no preset carries a base (`presets.ts:44` is `repo: { submodules: true }`, and `applyPreset` merges `repo` key by key, `presets.ts:127-133`). Running it before `unknownKeys` is irrelevant for `branch`/`mode`/`pr`, because those three are in `Recipe.shape` once added. It matters for the two-homes refusal, which must see the file's own keys.
- In `checkDeclared`, call it at the same point, `declared.ts:46-49`.
- In `editRecipe`, run it on `doc.toJS()` before the `Recipe.parse` at `emit.ts:173`.

**The refusals on meaning (§3 of the ticket) are one pure function too**, e.g. `refuseOnMeaning(recipe, wroteAgent: boolean): string[]`, run after a successful parse in `resolveSource` and `checkDeclared`, and thrown as `RecipeRefusedError`. `editRecipe` does not call it: `editedText` only turns a `ZodError` into a refusal (`write.ts:62-69`), and the resolve that follows a write refuses anyway.

### 2. `checkDeclared` must not refuse a team recipe because of its probe agent

`checkDeclared` fills an absent `runtime.agent` with `SCHEMA_PROBE_AGENT` (`declared.ts:53-56`, `local.ts:59`). The machine's real agent is put in later, by `resolveLocalRecipe`'s `shape`.

- Today the probe is `'claude-code'`, which is in `DiscussAgent` (`recipe.ts:2919`), so the check would pass by accident. The check is still wrong, because it would be testing the probe's value rather than the file's.
- So the *team, no `pr.agent`, `runtime.agent` outside `DiscussAgent`* refusal runs in `checkDeclared` only when the text itself writes `runtime.agent`. That is what the `wroteAgent` parameter is for.
- In `resolveSource`, `runtime.agent` is always present after the parse (`RuntimeId.default('claude-code')`, `recipe.ts:3300`), so the check there always runs.

### 3. A writer that writes `branch.main` also removes the old spelling it replaces

If a writer adds `branch.main` to a file that still says `repo.base`, the file now has two homes for one setting, and the ticket's own refusal turns it away. So every writer in the Evidence list needs one helper in `answers.ts`, say `branchMainChanges(branch, onDisk)`, which returns:

- `{ path: ['branch','main'], value: branch }`;
- `{ path: ['repo','base'], value: undefined }` when the file has `repo.base`. A `value` of `undefined` deletes the key (`emit.ts:162`);
- **`{ path: ['repo'], value: undefined }` instead of the line above when `base` was the only key in `repo`**, so the file never ends up with `repo: {}`. An empty `repo: {}` parses to `{ submodules: false }` through the inner default (`recipe.ts:3089`), while an absent `repo` stays absent. The two would hash differently and break the twin-hash promise;
- for `steps.admit`, the worktree entry with `base` removed, when it has one. The ticket says `landOnBranchChanges` "no longer edits admit's `worktree:`". Read that as *never writes a base there*. Removing an old one is the only edit it may still make to that entry.

`readOldSpellings` follows the same rule: **delete the key, and drop a `repo` that the deletion left empty.** Never set a key to `undefined` and leave it in place. That keeps the old file and its hand-written twin at the same `hashRecipe`.

### 4. One more raw reader the ticket's list misses

`refFor` (`write.ts:39-48`) reads `repo.base` straight from the text to name a refusal ("What a refusal names: the file's own `repo.base`"). It should read the value through `readOldSpellings`, then `branch.main`, and otherwise fall back to `path`. It must not call `branchOf`: the text may not resolve at all, and that is exactly when `refFor` is needed.

### 5. `RecipeRefusedError` and `name`

The parent declares `override readonly name = 'RecipeInvalidError'` (`resolve.ts:51`). That gives `name` a literal type, so a subclass cannot assign `'RecipeRefusedError'` to it. Widen the parent's field to `readonly name: string = 'RecipeInvalidError'`. Give the subclass:

- its own `name`;
- `readonly _tag = 'RecipeRefused' as const`;
- the same `(ref, problems, where)` constructor.

Do not use a parameter property for any of these.

### 6. `branchOf` before the parse

`first-project.ts:628` should read the current base through the resolved recipe, as the ticket says. Where it runs before anything can resolve (no file yet), the answer is `null`, and the code should fall through to the existing `LINGTAI_BASE` detection at `:632`. There is no third raw-path reader.

### What stands in for integration

The only integration test is the `git check-ref-format --branch` table, and it is out of reach inside a pass. The unit check that covers it is the same table run against the pure TypeScript copy. Keep the table in one exported constant under `packages/recipe/test/`, so both halves read the same rows and a row added to one is in the other.
