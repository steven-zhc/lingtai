# #836 — design note

The ticket covers the fold split, the four writers and the fixtures, and I checked those claims against the tree. This note only adds the decisions it leaves open. They are small, and each one is easy to get wrong while still having a green suite.

## 1. `applyControl` copies; it does not push

Today's fold makes one mutable copy and pushes into it: `const state = { ...emptyControl, requested: [], continuing: [], discussions: [] }` (`packages/domain/src/control.ts:157`), then `state.requested.push(...)` and the same for the other two arrays (`:217`, `:224`, `:233`). With `events.reduce(applyControl, emptyControl)`, a push writes into `emptyControl`'s own arrays. Every later fold in the same process then starts dirty. The `the histories fold` loop in `histories.test.ts:85-90` would catch that only by accident.

**The rule:** follow the sibling folds. `applyTicket` returns `{ ...state, ...at, links: [...state.links, d] }` (`ticket.ts:433`, `:452`), and `reduceTicket` is a bare `events.reduce(applyTicket, emptyTicket)` (`ticket.ts:469-471`).

- Spread the three arrays the same way.
- Freeze nothing, so no `Object.freeze`.

This makes the fold quadratic in the number of `RunRequested`, `ContinueRequested` and `DiscussionRequested` events on the stream. That is accepted here: pruning those arrays is the ticket's Out of scope (0124's Consequences).

**The test:** fold the same history twice through `reduceControl` and assert that `emptyControl.requested` is still `[]`. One assertion in `control.test.ts` is enough.

`holdsAcrossStarts ||= …` (`:173`) becomes `holdsAcrossStarts: state.holdsAcrossStarts || d['holdsAcrossStarts'] === true`. Its comment moves with it. It is still sticky: a person's pause on top of a `setup` pause makes `cause` `person` but keeps `holdsAcrossStarts` true. That is right, because the two fields answer different questions.

## 2. Reading `cause` from untyped data

The fold reads `e.data` as `Record<string, unknown>` through `str()` (`control.ts:162-163`). It never reads it as `PayloadOf<…>`, and that choice is deliberate: rows on the log were written by older code.

- Read `cause` with `PauseCause.safeParse(d['cause'])`, or an equivalent `PauseCause.options.includes` check.
- A string outside the enum folds to `null`, exactly like an absent one. Do not throw, because #822's "a stream that will not fold throws" is about streams, not unknown enum values.
- An old row and a garbled row are therefore both "nobody's in particular". The `0100 §4` test can cover both cases with two assertions.

## 3. `evaluateControl` and the ceiling waiver

`evaluateControl` is `control.ts:251-257` plus two changes:

- it also sets `cause = null` when the pause lapses;
- it nulls `ceilingWaivedUntil` when `ceilingWaivedUntil.getTime() <= now.getTime()`.

That `<=` mirrors today's `now.getTime() < until` (`day-ceiling.ts:154`) exactly. The lapse at `:251` already uses `<=`, so the two clocks agree on the boundary instant.

On the `ConductorResumed` side, copy the standing `until` as it is. When it is null (a ceiling pause whose `until` did not parse; `control.ts:167-169` turns that into `null`), the waiver is null too. That matches today's `until !== null && !Number.isNaN(until)` guard (`day-ceiling.ts:154`). It needs no extra branch, but the comment should say so.

Return the input state unchanged when nothing lapses. That costs nothing, and a later snapshot (0124 §1) can compare states by reference.

## 4. `day-ceiling.ts`: one fold per entry point

Today `dayCeilingPause` reads the stream once (`:214`), then folds it twice: once inside `resumedPast` and once at `:218`.

- After the change it folds once: `const control = reduceControl(events, now)`.
- `if (control.ceilingWaivedUntil !== null) return null`, then `if (!control.paused) append…`.
- `resumedPast` disappears as a function rather than becoming a one-line wrapper. Its doc comment ("True when the last ceiling pause has been resumed…") moves onto the `ceilingWaivedUntil` field.
- `liftOwnPause` keeps its own read, because it is called on the other branch (`:206`, `:211`).

`CEILING_REASON`'s comment (`:130`) currently says it is "what tells them apart". That stops being true, so rewrite it: it is the opening of the sentence a person reads, and `cause` is what tells the pauses apart.

## 6. Fixture histories

`lateHistories` already holds `run` and `ticket` as module-level consts (`histories.ts:722-746`, `:786-806`), so the ticket's conversion step is already done.

- Add the five consts after `late_escalatedThenRequeued` (`:767`), and add a `control:` key after `ticket:` in `lateHistories`.
- Build them with a ceiling-pause helper beside them, not by editing `pause()` (`:352`). That helper feeds the three locked `control.paused*` hashes (`histories.hashes.json:18-20`).
- For the already-lapsed cell, give the ceiling pause `until: LIFTED_UNTIL` (`:349`). For the rest use `HOLDING_UNTIL` (`:350`).

`histories.test.ts:77` names the function in its title as well as at `:80`. Rename both to `applyControl`.

## 7. Nothing here needs the integration half

Every claim above has a unit-level check:

- `day-ceiling.test.ts`;
- `control.test.ts`;
- `histories.test.ts`;

- the two `conduct-*` files;
- `pauseConductor`'s writer test in `control-since.test.ts` (the daemon contract in `test/contract.ts` runs only in the integration half, so its added assertions are a second witness there, not the unit gate's).
