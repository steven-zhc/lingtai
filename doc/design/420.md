The boundary is the **current wait**, not the run’s route history. Put the pure functions in `packages/domain/src/wait.ts` and pass `standing.reason` into `TriageBand` alongside its existing status. `StandingView` already holds the current reason and triage status, and the band currently receives only the status (`apps/board/src/lib/task.ts:379`, `apps/board/src/lib/task.ts:498`, `apps/board/src/app/standing.tsx:30`, `apps/board/src/app/standing.tsx:530`). Return the original `TriageAdvised` as `disagreement(...).triage`: compare its `cause`, but keep its summary, details, and advice together for display. Render the judge reading beside that existing triage content only for a disagreement. ADR 0118 §5 says, “Neither one is hidden” (`doc/decisions/0118-a-hold-explains-itself.md:379`).

For `CandidateUnavailable`, leave `judge.why` null in the pure function and do not add a `PassRouted` lookup to this change. The wait reason contains the excluded candidate (`packages/domain/src/route.ts:53`, `packages/domain/src/wait.ts:107`); the reply’s `why` is a separate field (`packages/domain/src/routing.ts:61`). `wait.ts` explicitly says, “Imports leaves only, never `events.ts`” because that would create a cycle (`packages/domain/src/wait.ts:20`). The band can therefore show both readings from the current reason and result without making its display depend on a second event read. Keep the resolutions below it on their existing path: `Standing` already derives them from `allowedResolutions` and `recommendedResolution` (`apps/board/src/app/standing.tsx:288`, `apps/board/src/app/standing.tsx:305`), and ADR 0118 §1 says a disallowed triage recommendation “is simply not drawn” (`packages/domain/src/wait.ts:480`).
