# Design: #1353, merging others' commits into a PR branch before Lingtai pushes it

The ticket gives the order of the cases and the wiring. This note covers four things the ticket does not say: a lease that would undo item 6, a `merging` switch that would send `'outside'` down the wrong branch, how `outside` builds its own merge, and the order of checks in `push`.

## 1. The lane's lease must move with its check (item 6)

`integrate.ts:484` is one of two places that pin the PR branch to `expectBase`. The other is the push:

```ts
// integrate.ts:644-647
const lease = options.expectBase === undefined ? []
  : [`--force-with-lease=refs/heads/${options.base}:${options.expectBase}`]
```

If you relax only the check, the lane merges onto the fetched base and then origin refuses the push. The lease names `expectBase`, but the remote is at `fetchedBase`. The refusal comes back as `push-rejected` (`:650`), then `landedAlready`, then a failure. Done-when line 9 (#1341's finding 3) goes red for exactly this reason. So:

- Keep the lease.
- Lease to **`fetchedBase`**, the commit the lane actually merged onto. The comment at `:642-643` still holds: a reset after the fetch is still rejected.
- Read `fetchedBase` once, above the check at `:482`, and pass that same value to the lease.

The relaxed check is:
- `git merge-base --is-ancestor <expectBase> <fetchedBase>`, run in `mirror` with the existing `at(…)` helper.
- Exit 0: land.
- Exit 1: `refuse('pr-branch-moved', …)`.
- Any other exit: a `RepoFailed`, as every other `at` failure is. It is never treated as *yes*.
- A gone base already fails the `rev-parse` of `laneBase`. Keep it that way, so a deleted branch is still a refusal rather than a creation.
- Update the doc comment at `integrate.ts:101-105`. It currently says "a branch somebody else pushed to is refused".

## 2. `merging: 'outside'` is a three-way switch everywhere, not a widened enum

Today every reader treats "not `main`" as `back`:

- `pr-resolve.ts:156`: `ask.merging === 'main' ? state.tickets : readPrDraft(…)`. For `outside`, *ours* is `state.tickets`, the PR's own tickets, the same as `main`. The draft is the merge back's alone.
- `pr-resolve.ts:294`: the worktree name is `pr-sync` or else `pr-back`. Give `outside` its own name, `pr-outside-${n}-…`. It must not collide with a sync standing up at the same time after a restart.
- `pr-conflict-brief.ts`: the *theirs* side. For `outside` that is the commit list (authors and subjects), not a `main` commit.

The enum is `z.enum(['main', 'back'])` in five places in `packages/domain/src/events.ts`: `:714`, `:2613`, `:2775`, `:2791` and `:2825`. It is also typed by hand at `packages/domain/src/pr.ts:116` and `:679`.

- Widen all seven together. Widening is safe for old events, so no upcast is needed.
- Then grep for `=== 'main'` and `=== 'back'` across `packages/` and `apps/board`. Make every one exhaustive, with a `never` default where the result is a value. One branch left as `else` is one wrong brief or one wrong page row.
- The round count (`pr-resolve.ts:427`, `:542`) already keys on `(merging, commit)`, so `grantedFor` works unchanged, as the ticket says.

## 3. `outside` builds its own merge; it does not reuse `buildStep`

`buildStep` (`pr-sync.ts:193-282`) is tied to `sync`:
- It reads `state.steps.find(s => s.step === 'sync')`.
- It takes `main`'s commit from `merge^2`.
- It records `PrBranchSynced`.

Do not generalise it. Inside `pr-outside.ts`, copy the shape of its body:

1. `cat-file -e` the merge; on exit 1 or 128 answer `restart`.
2. `ports.sweep`.
3. `ports.build(project, { sha: merge, base: prBranch, checkId: \`pr-${n}-outside\` })`. The check id must differ from `pr-${n}-sync`, or the two builds share a worktree path and a status.
4. On red, call `resolveRounds` with:
   - `merging: 'outside'`
   - `commit: at`
   - `start: target`
   - `why: { kind: 'red', merge, … }`
5. Take `start` as the `target` you merged onto. Do not use `merge^1` from a lookup.

For the green and resolved `done`, copy how `buildStep`'s green path (`pr-sync.ts:270-276`) and the sync's resolved path (`:160`) turn a `headSha` into the PR's `target` and keep `targetRef(n)`. Use whatever mechanism those use. Do not invent a second way for the target to move.

`outside` has no "adopted" case (`pr-sync.ts:203-206`). A remote head is either merged, or it is a force-push and waits.

## 4. What `outside` compares against when `lastPushed` is null

`push` accepts `at === state.frozenSha` before the first push (`pr.ts:295`). It does that because the sync's retry adoption (#1314, `pr.ts:841`) can leave a branch on the remote with no `PrPushed`.

So `outside`'s base is `lastPushed ?? frozenSha`, and the cases are:

| Remote | `lastPushed` | Answer |
|---|---|---|
| absent | null | `done`, nothing appended |
| absent | set | `branch-moved` |
| `at` is `target`, or an ancestor of it | — | `done` |
| `at` descends from the base | — | merge |
| otherwise | — | `branch-moved` |

Every ancestry check goes through `isAncestor` (`pr-git.ts`). Check that it maps exit 1 to `false` and any other non-zero exit to a failure. The whole step is wrapped in `orUnknown` as `sync` is (`pr-sync.ts:79`), so a read that fails becomes `sync-unknown` and is never mistaken for a case in the table.

## 5. `push`: replace the condition, keep the order

Today the moved check at `pr.ts:295-297` runs before the `cat-file` and the `--is-ancestor at target` check (`:304-308`, where exit 1 answers `again`). Replace only `:295`:

- `at === null && lastPushed !== null` → `moved(null)`. This stays at `:293`.
- `at` is `lastPushed`, or the `frozenSha` case → go on as today.
- Otherwise, run `merge-base --is-ancestor <lastPushed ?? frozenSha> <at>`:
  - exit 0 → `{ kind: 'restart' }` (somebody pushed after `outside` looked).
  - exit 1 → `moved(at)`.
  - any other exit → fail with `gitSaid`, as `:307` does.

`restart` is already the answer `walkPr` re-enters from `sync` with (`pr.ts:301`), so no new variant is needed. Rewrite the doc comment at `pr.ts:225-229`.

Two loops cannot happen:
- Each `restart` makes `outside` merge the newer head.
- Someone pushing on every round is the race the ticket accepts; it never waits.

## 6. `sync` (item 4)

Change only the condition at `pr-sync.ts:109`:
- At or equal to `lastPushed` or `start` → pass, as now.
- Otherwise, `lastPushed` non-null and `isAncestor(lastPushed, at)` → pass.
- Anything else → `sync-rewritten`, as now.

Replace the comment at `:106`. It says a merge on anything else "would be pushed over it", which is no longer true, because `outside` merges it before `push`.

`startOf` (`:98`) is unchanged: it compares `target` with `lastPushed`, not with the remote.

## 7. The step list and the summary

`IN_PROGRESS_STEPS` (`pr.ts:690-699`) becomes:

```
sync, build, outside, summary, push, open, ci, topup, ready
```

The doc comment above it at `pr.ts:685-688` names the list. The PR page draws its rows from `inProgressStepNames`, so the board shows the new row without its own change. A test that pins the list changes once.

`PrOutsideMerged` is new in `PrState`'s reducer (`packages/domain/src/pr.ts`). It needs at least `remoteHead`, `head`, `how` and `commits` in state, so that:
- the top-up can select the commits since the last `PrSummaryWritten` by seq;
- the page can say *merged N commits others pushed*.

The commit list is capped at 50 with a count of the rest (`omitted`). Store the cap in the event, not just the prompt, so the page and the prompt agree.

## 8. What settles it

**The log settles the flow.** The walk should read `PrOutsideMerged` before `PrPushed` on `pr-{project}-{n}`, with `PrPushed.headSha === PrOutsideMerged.head`. A raced push reads `PrStepStarted { step: 'outside' }` twice, with nothing in between. `restart` appends nothing, so its absence is the proof.

**All the Done-when checks are unit-level with fake ports.** The ancestry exit codes in sections 1 and 5 are `git` behaviour. The repo-side change (`integrate.ts`) is exercised for real only by `packages/repo`'s integration tests, which nothing runs inside a pass.

The unit-level stand-in is a fake `at` in the lane's unit test that:
- answers `--is-ancestor` with 0, 1 and 128;
- asserts that the push argv carries `--force-with-lease=…:<fetchedBase>`.

Say so in the PR body.
