Both callers use it: the `outcome.structured` path (`:581-582`) and the strict loop in `parseFindings` (`:366-375`). `6de930c` split that rule into `listIn`, `findingsFromList` and `aboutIn`. **Drop those three and keep `normaliseAnswer`.** The repair-only guards described below go inside the tolerant loop of `parseFindings`. ## The blocker: a reading must use up its whole candidate

`readTolerantJson` (6de930c `tolerant-json.ts`, last line) returns `parseValue()` and never checks what comes after the value. `JSON.parse` does check. That is the only reason a brace candidate with trailing prose fails strict parsing today.

So, for example:
1. The reviewer quotes an example `{"findings":[{…"severity":"major"}]}` in its prose.
2. Its real answer then breaks.
3. Every strict candidate fails.
4. The tolerant reader reads the quoted example and ignores everything after it.
5. Invented findings come back as the reviewer's own.

**Fix it inside `readTolerantJson`, not in `parseFindings`.** After the top-level value, skip whitespace. If anything is left, fail at that index and name that character. After this, the contract is one sentence: *the same candidates, the same extent rule as `JSON.parse`, and only the listed repairs on top.* Write that sentence in the header comment, where "It is not a general 'accept anything' reader" already sits.

What this costs: an unfenced object followed by a closing sentence is not recovered. Strict parsing does not recover it today either. A fenced block is how such an answer gets through, because a fenced candidate ends at the fence.

Tests:
- In `tolerant-json.test.ts`: `'{"a":1} x'` fails at offset 8 with `x`.
- In `agent-action.test.ts`: prose, a findings-shaped example object, more prose, then a broken real answer. Assert `parsed: false`, and assert that no finding from the example appears.

## One gate for a repaired reading: every entry is a complete finding

`6de930c` has two guards: `findings.length !== list.length` and `!isSeverity(…severity)`. Scenario 3 showed what they miss. A reading truncated before `file` still gets `file: "(unknown)"` from `normaliseAnswer`'s `String(f.file ?? "(unknown)")` (`:308`). The same defaults also hide a missing `line`, because `typeof f.line === "number" ? f.line : null`.

The keys an entry must have are already written down: `Finding` (`packages/domain/src/events.ts:812-819`) requires `file`, `line` (a number or null), `claim`, `failureScenario`, and a `severity` from `SEVERITIES`. **Replace both guards with one check that every raw entry has all five keys with those types.** Write it as a small hand-written check in `agent-action.ts`. Do not use `ReviewAnswer.shape.findings.element`: that is `Finding.strict()`, so it would also refuse an entry with an extra key, and a truncation never adds keys.

Keep `verdictFor(findings) === "failed"` exactly as it is in `6de930c`. A repaired reading may buy a fix round but never a pass. That decision from round one stands, and the review did not question it.

## `furthest`: what it records, and the scenario 1 fix

There are three changes, all inside `parseFindings`.

1. **Declare `furthest` before the strict loop, not after it.** When `JSON.parse` succeeds and `normaliseAnswer` comes back `parsed: false`, record a reason. On `main` that is the `if (result.parsed) return result;` line (`:373`), which is the twin the review cited as 6de930c `:418`. Then record the same reason in the tolerant loop where its own `if (!list) continue;` stood (6de930c `:450`).
   - The reason is *"it had no `findings` array"*.
   - The offset is where the object ended: the candidate's start plus the trimmed candidate's length. After the blocker fix this is accurate on both paths, because both use up the whole candidate.
2. **On a tie at the same end offset, the earlier start wins.** Candidates are tried last brace first, so an inner object of `{"result":{…}}` is recorded before the outer one. The outer object is the answer a person should be pointed at.
3. **Do not count the whole-text candidate's failure unless the trimmed text starts with `{`.** Today, prose with no JSON at all becomes ``unexpected `I` (U+0049) at offset 0``. That is the sentence scenario 1 kept producing, and the ticket's last box rules it out ("say so in those words"). Without that failure, `furthest` stays unset and `describeUnreadable` returns its existing *"no JSON object was found in it"*.
   - Two 6de930c tests change their assertion: `agent-action.test.ts:490-493` (`offset: 0, char: "I"`) and `:784` (``unexpected `l` (U+006C) at offset 0``). Both now expect the no-JSON sentence.
   - Keep the `:784` test asserting the full sentence, not just "not readable". That was its point.

## The `reason` sentences must claim only what the reading showed

The review found that two of the three wording choices overclaim:

- **"every finding in it was a minor"** is also what an empty `findings: []` produces, and that list had no findings at all. Say *"nothing in it was a blocker or a major, and a repaired reading may not pass"*.
- **"a finding in it had no severity"** fires on `"severity":"critical"` too. The completeness gate above replaces it. Name the entry and the key, using only what was seen: *"finding 3 of 4 has no `file`"*, *"finding 2's `severity` is `critical`, not one of blocker, major or minor"*.
- **"it read as an object ending at offset N"** was false in `6de930c`, because `end` was `start + candidate.length` and the reader never checked it used up the candidate. The blocker fix makes it true. Do not reword it.
