# Design: #318 — repairing a reviewer's JSON without touching what it wrote

## Where it goes

All the code is in `packages/actions`. `parseFindings` (`packages/actions/src/agent-action.ts:293`) keeps its signature. It gains an optional `unreadableAt` on the not-parsed return. One caller reads that field: the `!parsed` branch at `agent-action.ts:530-555`, which puts it into the `evidence` sentence. Nothing in `packages/conductor` changes, and neither does `ActionResult`: `unreadable?: true` (`action.ts:163`) stays the only flag, and 0038 §2 is untouched.

Add a new file, `packages/actions/src/tolerant-json.ts`, with its own `unit/tolerant-json.test.ts`. It holds a small hand-written recursive-descent reader. **Use this, not a dependency.**

- **No JSON-repair library is installed.** Nothing in `node_modules/.pnpm` matches `json5`, `jsonrepair` or `partial-json`.
- **JSON5 cannot handle either failure.** It does not read U+FF1A as a colon and does not close a truncated object.
- **`jsonrepair` repairs too much.** It is built to make *anything* parse: it closes open strings and turns prose into string values. That is the opposite of what this ticket needs.
- **The ticket needs the failing character and its offset in the refusal.** V8's `JSON.parse` message reports a position for some errors and not for others. A reader we write ourselves always knows both.

## What the reader repairs, and nothing else

It is a JSON tokenizer and only accepts these departures from JSON:

1. **Full-width structural punctuation outside a string.** Accept `：` (U+FF1A) where `:` is expected and `，` (U+FF0C) where `,` is expected. Optionally also accept `｛｝［］`. "Where expected" means the parser's current state asks for that token. **A full-width character inside a string literal is copied through unchanged, because the string scanner never consults the repair table.** This is the ticket's safety argument, and it holds by construction: the string scanner and the punctuation table are separate code paths.
2. **A trailing comma before `]` or `}`.**
3. **End of input while arrays or objects are still open**, with the last value complete. The reader closes them. This is `#269`: the fixture ends `}]` (`agent-action.test.ts:451`), so every value is complete and only the outer `}` is missing.

It does **not** close an unterminated string, an unfinished number or literal, or a key with no value. End of input in any of those positions is a failure at that offset. `"claim":"the ending is` (`agent-action.test.ts:423`) must still be refused.

On failure it returns `{ ok: false, offset, char }`, where `char` is the code point found, or end of input. It never throws.

## Where it runs in `parseFindings`

1. **The strict loop stays exactly as it is.** Only if every candidate fails do you go on to step 2.
2. **Run the tolerant reader over the same candidate list, in the same order.** That is the fenced blocks first, then every brace from last to first, then the whole text (`agent-action.ts:309-314`). Take the first candidate that reads to an object whose `findings` is an array. Running it per candidate keeps #272's lesson: a brace inside the prose is not where the answer starts. A few hundred candidates of a ~20KB answer is cheap.
3. **If nothing reads, report the candidate that got furthest.** That is the largest `candidateStart + offset` in `text`'s coordinates; it is the most JSON-like reading and the one a person wants pointed at. Return it as `unreadableAt: { offset, char }`.

## The decision the ticket does not make: a repaired answer may refuse, never pass

A repaired reading counts only when **every raw entry in its `findings` survived the rule** (`agent-action.ts:323-327`: no `claim` or no `failureScenario` → dropped) **and `verdictFor` on the result is `failed`**. In every other case, return `parsed: false` with `unreadableAt` set, exactly as today.

- **Why every entry must survive.** Inside a repaired reading, a dropped entry is evidence of truncation, not a reviewer breaking the rule. A finding cut off before its `failureScenario` would otherwise vanish without a trace, and the findings that remain would read as the whole review.
- **Why it must be a failure.** Repair is a guess about where the writer stopped. The safe use of a guess is to buy a round on findings that are really there; the unsafe use is to let a diff through because the guessed reading looks clean. An empty `findings: []` reached only by repair would be a green action for a review nobody can be sure of. Today's comment says it is not (`agent-action.ts:290-291`, "*A truncated answer … is still refused: that difference is the only thing the refusal below is for*"), and that rule still holds for every reading that would pass.

What this costs: a review with a bad byte that contains only minors is still refused, as it is today. The minors are not filed. `#243` (a major and two minors) and `#269` (a major and three minors) are both recovered.

Use `verdictFor` from the same file (`agent-action.ts:374`), not `BAR` spelled again.

## The `#243` fixture

The ticket asks for it byte for byte, and **it is not on this machine**. `~/.lingtai/runs/lingtai/` has no `run-06145376*` log. The file is kept only while a run is owed an explanation (0034), and this agent cannot read production `events`. The text survives in two places:

- `StepFailed.data.evidence` for that step. It is `boundedEvidence(...)` (`agent-action.ts:551`), so check that it is whole before using it.
- The reviewer's transcript.

If neither can be reached, **do not retype it**:

- Write a fixture that keeps the shape: several findings, one `"failureScenario"：` in the third, quoted code containing a `：` inside a `claim`. Name it as a reconstruction in its header.
- Leave that `Done when` box unchecked and say so in the commit body.

A retyped "real" fixture is worse than an honest synthetic one.

## The sentence

`agent-action.ts:551` becomes `the reviewer's answer was not readable as findings: unexpected \`：\` (U+FF1A) at offset 4127:\n${text}`, or `…: it ended at offset N inside a string` (or inside whatever value it was in). The code point goes in as `U+XXXX`, because a stray full-width or invisible character is exactly what a person cannot see in a terminal. Assert this in the existing `unreadable` test at `agent-action.test.ts:670-678`; `findings: []` and `unreadable: true` stay as they are.

## What checks it

Everything here is unit-level and in reach of `pnpm test`. `parseFindings` is pure, and the reader has no I/O. Nothing needs `test:integration`.

Write the safety test in `tolerant-json.test.ts`, directly against the reader:

- A `claim` containing `：`, `，`, `{`, and a trailing `,]` sequence inside the quotes must come back character-for-character.
- That document must also be broken by a structural `：`, so the repair path really runs.

Also run it through `parseFindings` to show the string survives the whole path.
