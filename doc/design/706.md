# #706: how the change is laid out

The ticket says what to build. This note covers the four places where the code as it stands pushes against it, plus the choices the ticket leaves open.

## 1. `auth` is read with the `github:` section but chosen outside the App election

`GITHUB_APP` (`packages/env/src/index.ts:1165-1173`) declares the four keys under `github`, and `githubSection` (`:1184`) turns any provider into a `GitHubAppSection`. Add `auth: Config.option(Config.string('auth'))` there and `auth?: string` to `GitHubAppSection` (`:1176`). That way `LINGTAI_GITHUB_AUTH` and the file's `github.auth` come in through the same two providers as every other key.

**Do not take `auth` from `electGithubApp`'s `values`** (`:1239`). That function returns one source's section whole: *"whichever source names the id is asked for the rest"* (`:1230`). So a file with `auth: gh` beside an exported `LINGTAI_GITHUB_APP_ID` would lose its `auth`, which is the opposite of what the ticket asks. Instead, write a pure resolver beside it that takes the two sections already read, the same way `electGithubApp` does:

```ts
export function electGithubAuth(environment: GitHubAppSection, machine: MachineGithub):
  { kind: 'app' | 'gh'; source: 'environment' | string } | { kind: null; unreadable?: string } | { refused: string }
```

- The rule is `environment.auth ?? machine.section.auth`.
- Any value other than `app` or `gh` is refused, and the refusal names the source it came from.
- If both are absent, use `hasGitHubApp`'s test (`:1337`: id plus a key or a path) on the elected App to answer `app` or nothing.
- `githubAuth(from)` and `hasGitHubAuth(from)` are thin wrappers that read `environmentProvider(from)` and `machineGithub(machineFile(from))`, just as `githubAppValues` does (`:1250`).
- `githubAuth` throws on refused and on nothing. Its message carries `machine.unreadable` when the file could not be read, in the same shape `githubApp` uses (`:1308`).
- `hasGitHubAuth` returns false on refused and on unreadable, and never throws.

The unit test goes in a new file beside `packages/env/unit/github-app.test.ts`, built with that file's `machine()` helper (`:13`). It covers the pure resolver only.

`githubSection` stays total. A `foo` comes through it as a string and is refused by the resolver, not by the parser. An empty value is already treated as absent (`:1190`).

## 2. `config.example.yml` has to carry `auth` as a live key, not a comment

`prefix.test.ts:149-157` parses the example and asserts that `Object.keys(example.github)` equals the `read` map's keys. A commented-out `# auth:` does not parse into the YAML, so adding `auth: 'auth'` to `read` would fail that assertion.

So write `auth: app` as a real line at the top of `github:` (`config.example.yml:55`). Put a comment above it naming both values:

- `app` is the keys below.
- `gh` is the machine's saved `gh auth login`. Under `gh` the App keys are not read.

`LINGTAI_GITHUB_AUTH` overrides it. This is how the ticket's "commented, with its two values" should be read. The test's second assertion already passes a non-empty value for every key (`webhook_secret: 'x'`), and `app` is non-empty, so it needs no change.

## 3. `GitHubClient.installation` becomes `Installation | null`

The interface says `readonly installation: Installation` (`client.ts:165`), and the client returns it (`:549`). Under `gh` there is none, so change the type to `Installation | null`. Do not invent a fake installation.

The only reader in the tree is `apps/cli/scripts/rung-1.ts:87` (`client.installation.id`). `tsc` will name it. Give it a `?.id ?? 'none (gh)'`.

`CreateClientOptions.installation` (`:355`) only makes sense for the App, so ignore it under `gh`.

Do not reword `PermissionDenied` (`:57`, raised at `:484`), which talks about "the App's permission". Nothing builds a `gh` client yet, so that text belongs to child 2.

## 4. The `gh` runner is the port, and it never rejects with stdout attached

Create a new module, `packages/github/src/gh.ts`, exported from `packages/github/src/index.ts`. It has three parts.

**The port.**

```ts
type GhRun = (args: readonly string[], opts?: { stdio?: 'pipe' | 'inherit'; signal?: AbortSignal })
  => Promise<{ code: number; stdout: string; stderr: string } | { missing: true }>
```

**The live runner (`liveGh`).**

- It calls `execFile('gh', args, { env: scrubbedEnv(process.env), signal, timeout: 15_000 })`. It always passes `env` and never omits it.
- `stdio: 'inherit'` uses `spawn` with the same `env` and returns empty strings for the output. That case is #710's.
- It catches `execFile`'s rejection *inside the runner*:
  - `ENOENT` becomes `{ missing: true }`.
  - Anything else becomes `{ code, stdout, stderr }` built from the error's fields.
- A rejection object never leaves the runner. This is where the ticket's *"the rejection carries `stdout`"* trap is closed for every caller at once, not only in `ghToken`.
- The timeout is a choice made here: a keyring prompt that never returns should not hang a pass. If it fires, it becomes a named "gh did not answer in 15s" error.

**`scrubbedEnv`.** It is pure: it copies its input and deletes the four names. The test hands it `GH_TOKEN` and the others and asserts they are gone. Add a second assertion that `liveGh` builds its options through `scrubbedEnv`. Do this by exporting the options builder (`ghExecOptions(parent)`) and testing it, never by spawning a process.

**`ghToken(run = liveGh)` and `ghStatus(run = liveGh)`.**

- Both take the port as their last argument.
- `ghToken` returns `stdout.trim()` only when `code === 0` and the trimmed output is non-empty. Every other outcome throws a new `Error` built from the exit code and `stderr` only:
  - `missing` reads "gh is not installed".
  - Empty output reads "gh answered no token".
  - Run the stderr through a filter that drops any `gh[opsu]_…` or `github_pat_…` substring before it goes into the message. This is cheap insurance in case a stderr ever echoes a token.
- `ghStatus` parses `stdout` as JSON *whatever the exit code*. A signed-out host may exit non-zero and still print the hosts. Read the result this way:
  - Find the entry under `hosts['github.com']` with `active: true`.
  - No entry means "no github.com account".
  - `state !== 'success'` means "signed out".
  - Split `scopes` on `,` and trim each entry; `''` is an empty list.
  - Output that is not JSON and whose `stderr` matches `unknown flag` means "gh is too old for `auth status --json`; 2.x with `--json` is needed". Write the minimum version as a constant beside the check, so that a person can correct it in one place.
  - Return a discriminated union (`{ ok: true; login; scopes } | { ok: false; reason: 'missing' | 'signed-out' | 'no-account' | 'too-old' | 'unparsed'; detail }`). Do not throw: doctor and `lingtai add` (child 3) want to render a reason, not catch one.

## 5. How `createGitHubClient` tells the two shapes apart

`AppAuth` (`app.ts:32`) has no `kind`. Keep it unchanged and discriminate with `'kind' in auth && auth.kind === 'gh'`. Changing `AppAuth` would touch every existing caller, and the ticket says nothing calls the new shape yet.

The test needs to reach the port. Add `gh?: GhRun` to `CreateClientOptions`; it defaults to `liveGh` and is read only under `gh`. Do not put the port on the auth value, which is what `packages/env` will hand over in child 2.

Under `gh`, set `tokenFor = (signal) => ghToken(run, signal)`. It is a fresh spawn per call with nothing captured, which matches the existing comment that callers *"resolve it per git invocation"* (`client.ts:336-339`).

The client test follows the stubbed `fetch` already in `packages/github/unit/client.test.ts:55`:

- Assert that no URL containing `/installation` was requested.
- Assert that the request carried `authorization: Bearer <the faked token>`.
- Assert that `token()` asks the port again on a second call. That last assertion is what pins "never cached".

## What is checked where

Everything above is unit-level: pure resolvers, a faked port, and stubbed `fetch`. Nothing needs `pnpm test:integration`.

The one thing no test here proves is that git accepts a `gho_` token in `git.ts:45-52`'s `x-access-token:` header. The ticket already moves that check to a manual run, recorded in the PR.
