# #1038: design note

## Where each piece goes

**The write goes in `loadBoard`, not in `toColumns`.** `toColumns` (`apps/board/src/lib/board.ts:1766`) is a pure bucketing function and does not know the scope. `loadBoard(project?)` (`board.ts:1524`) does know it, and it builds the columns at `board.ts:1624`: `columns: toColumns(fromLog, queued.problems)`. Bind that result to a name, record each column's `cards.length` under `` `${project ?? ''}/${c.id}` ``, then return it. `loadBoard` has one caller, `startReads` (`apps/board/src/app/page.tsx:644`), so this records once per render. It uses the same key the boundaries are built from: `const projectKey = param ?? ''` (`page.tsx:978`).

Keep the key to the URL's `param`. Do not use `selectedProject(param, …)` (`page.tsx:670`). A one-project setup shown without `?project=` is the `''` scope, and its boundaries are keyed `''` too.

**A read that fails records nothing, and that needs no extra code.** `tasks.read` already turns an *unbuilt* projection into `[]` (`.catch(emptyIfUnbuilt)`, `board.ts:1535`). Recording 0 there is a true answer: the projection is empty. Any other failure throws before line 1624, so the last good count stays.

**The read is `columnSkeletonCount(project: string | undefined, columnId)`, next to `skeletonCount` (`board.ts:1145`).**
- Never seen: `SKELETON_UNKNOWN`.
- `landed`: `Math.min(n, LANDED_OPEN)`. `LANDED_OPEN = 3` is at `board.ts:482`, and `Landed` draws only that many rows open (`page.tsx:575`).
- Every other column: `Math.min(n, SKELETON_MOST)`.

Reuse the two constants at `board.ts:1138-1139` rather than adding new ones. Clear the new map inside `forgetSkeletonCounts()` (`board.ts:1134`) instead of adding a second `forget…`. That function's doc already says *"Forgets every count"*, and `apps/board/unit/home-streams.test.tsx` mocks only `loadBoard` (`:23`), so the fallbacks it renders read the real map. Call `forgetSkeletonCounts()` in that file's `beforeEach`.

## Queued's outer fallback: the decision the ticket leaves open

Queued waits twice:
1. **The outer wait.** The `cards-queued` boundary (`page.tsx:1134-1141`) shows its fallback until `board` resolves.
2. **The inner wait.** `QueuedFallback` then draws the log's real cards plus `skeletonCount(askable…)` skeletons until GitHub answers (`page.tsx:906-916`, `queued-stream.tsx:308-327`).

If the outer fallback were sized from the log's half alone, the column would grow by GitHub's half the moment the board answers. That is the jump 0111 §15 forbids.

**So the outer Queued fallback is sized for the whole column, as one count.** Add `queuedSkeletonCount(project)` in `board.ts`:
- `log` is the map's `queued` entry for the scope.
- `offered` is `lastOffered.get(project)` (`board.ts:1131`, recorded at `:1372`) for a named project. For `''` it is the sum over every project `lastOffered` holds, because the outer fallback runs before `askable` is known.
- If neither is known, answer `SKELETON_UNKNOWN`. Do not answer 2 + 2: the board has one unknown count.
- Otherwise answer `Math.min((log ?? 0) + (offered ?? 0), SKELETON_MOST)`.

For `''`, a project removed from the register keeps adding its last offer until a restart. That is the ticket's *a count wrong by one* case and is accepted.

The inner fallback is unchanged. It already draws the real log cards and keeps `skeletonCount` for GitHub's half.

## The fade: one wrapper inside the keyed boundary, in `page.tsx`

The wrapper goes inside the `cards-${col.id}` `<Suspense>` (`page.tsx:1134-1141`) and around `<CardsPart …/>`, not inside `CardsPart`. `CardsPart` has four separate returns: Queued, empty, Landed and the card list (`page.tsx:902-968`). One wrapper at the call site covers all four and the empty note.

The wrapper's identity is the boundary's key, so it does the following:
- **It mounts once per switch**, and its CSS animation runs once.
- **On a live re-render of the same project nothing replays.** React reconciles the same `div`, and that does not restart a CSS animation. Cards appended inside it mount inside an element that is already shown, so nothing fades. This is the ticket's *a live append fades nothing*.

**Watch out: the layout.** `.cards` is `display: flex; flex-direction: column; gap: 7px` (`globals.css:360`). A plain `div` between `.cards` and the cards makes them its children, so the 7px gap goes away and the cards stack touching. Give the wrapper the same rule, for example `.cards, .cards-in { … }`, with `className="cards-in arrive"`. **Do not use `display: contents`**: it has no box, so nothing animates.

**Do not set `Card`'s own `arrive` prop instead.** It puts `.arrive` on each card (`page.tsx:271`), so every card a live append mounts would fade in by itself.

In Queued, GitHub's cards still get their own `.arrive` from `arriving` (`queued-stream.tsx:257`). They mount when GitHub answers, after the wrapper's 200 ms is over, so nothing fades twice in a way that shows. Under reduced motion `.arrive` is off already (`globals.css:3265`).
