# Design note: #1098, doctor's first-half checks as Effects

This note covers four things the ticket leaves open. Everything else follows the ticket's *Shape*. The line numbers below are this worktree's: they match the ticket's for the checks, and `runDoctor`'s file-backed branch is `doctor.ts:3387-3420`.

## 1. Three seams are shared with CLI-12's checks, so bridge them back to promises

These checks are out of scope, but they read the same `reach` keys this ticket turns into Effects:

- `daemonCurrency(reach.status)` at `doctor.ts:3396` (an `async` at `:1489`).
- `spendToday(reach.spend, reach.pause ? () => reach.pause!().then(…) : …)` at `:3404-3411`. Its `control` parameter is `() => Promise<ControlState>` (`:1994`).

Change `DoctorReach.status`, `.pause`, `.lags`, `.shapes`, `.settings` and `.accounts` (`:1158-1176`) to return Effects. Inside `runDoctor`'s `Effect.gen`, take `const ctx = yield* Effect.context<never>()` once, and give the two CLI-12 callers a promise view:

- `() => Effect.runPromiseWith(ctx)(reach.status())`
- the same for `pause`, keeping today's `c ?? Promise.reject(new Error('the control stream could not be read'))`.

The ratchet does not count this run. `RUN = /^run[A-Z](?!\w*With$)/` (`packages/domain/unit/effect-ratchet.test.ts:70`), and CLAUDE.md names `runPromiseWith(yield* Effect.context())` as the sanctioned form. So `run` stays at 6. CLI-12 deletes both bridges when those checks become Effects.

Do **not** use `Effect.runPromise` there: it moves `run` to 7, and the baseline must not move up.

## 2. Two seams stay as they are

- **`runtimes`** returns `everyRuntime()`'s array synchronously, not IO. It is also read by the recipe rows at `:2857`, which are CLI-12's. Keep its type. `runtimeAuth` becomes an Effect over that array, and lifts each `runtime.checkAuth(env)` with `lift` (`apps/cli/src/exit.ts:16`).
- **`gh`** is a `GhRun` runner (`packages/github/src/gh.ts:45`), which is exactly what `ghStatusEffect(run)` takes (`gh.ts:122`). `ghLogin(env, gh)` keeps that parameter and yields `ghStatusEffect(gh)` (or `ghStatusEffect()` when `gh` is absent).

Seams stay **thunks returning Effects** (`() => Effect<…>`, `(p) => Effect<…>`), not bare Effect values. `shapes` takes an argument, and the bridge in §1 wraps a thunk.

## 3. Catching: one local helper, and the message comes from `Cause.squash`

The rows print `(err as Error).message` today, for example `stoppedProjections` (`:772-777`), `projections` (`:806-811`) and `logReachable`. Under `catchCause`, the original error is `Cause.squash(cause)`. Use the shape `restart.ts:757-763` already uses:

```ts
Cause.hasInterruptsOnly(cause)
  ? Effect.failCause(cause as Cause.Cause<never>)
  : Effect.succeed(onFail(Cause.squash(cause)))
```

Define one private helper in `doctor.ts` for that shape. Don't import `restart.ts`'s `recovering`: it is not exported, and `restart.ts` already imports from doctor. Then every row's detail stays the same text.

`readStatusEffect` is `Effect<DaemonStatus | null>` with **no error channel** (`packages/daemon/src/control.ts:717`), so every beacon failure is a defect. `readControlEffect` is `Effect<ControlState, unknown>` (`control.ts:117-120`) and can fail either way. A plain `Effect.catch` would let a beacon read through as a crash, and `runDoctor` has no catch around a step. That would end the whole report instead of writing the `the beacon could not be read` row.

Where today's code catches, and what it answers (keep each one):

| Check | On failure |
|---|---|
| `daemonLiveness` defaults (`:1240-1242`) | `null` |
| `daemonLiveness` `readTasks` (`:1294`) | `null` |
| `stoppedProjections` | the fail row |
| `projections`, `projectionShapes` | their fail rows |
| `pausedProjects` | the warn row |
| `accountLimits` | the warn row, with `Cause.squash` in place of the `err` that `runEffect(...).catch` received at `:1386` |
| `spendLagNow` | `undefined` |
| `logReachable`, `pooledConnection`, `directIsSessionMode`, `schema` | their own rows |

Nowhere else. Seams passed into `daemonLiveness` still propagate, so `daemon.ts:85`'s `liveness` port keeps failing on an unreadable beacon. It becomes `daemonLiveness(() => readStatusEffect()).pipe(Effect.map((live) => live.detail))` with no `lift`.

`accountLimits`' inner `Effect.tryPromise`s around `load`, `readControl` and `recipeFor` (`:1356-1360`) become `loadProjectsEffect()` and `readControlEffect(store)`. `recipeFor`'s default becomes `currentRecipeEffect`. Its per-project `Effect.catch(() => Effect.succeed(null))` (`:1370`) must become the same `catchCause` helper: `currentRecipeEffect` can die, and today `tryPromise` turned that into a failure.

## 4. Postgres clients

`withClient(url, fn)` is `Effect.scoped(Effect.acquireRelease(connect, end).pipe(Effect.flatMap(fn)))`:

- **Acquire** is `lift(() => c.connect())`, which keeps pg's message for the row.
- **Release** is `Effect.promise(() => c.end()).pipe(Effect.ignore)`. Today's `finally` would rethrow an `end()` error and mask the result (`:249-251`). Ignoring it is the `directIsSessionMode` precedent (`:589-590`).
- **The queries inside `fn`** go through `lift`.

Build `directIsSessionMode` from two `acquireRelease`s:

- The notifier is acquired **after** the 1.5 s `Effect.sleep`, as today (`:563-566`). Acquiring both up front changes what the probe measures.
- The poll is `Effect.sleep('50 millis')` in a loop up to the 5 s deadline. A `Schedule`-based retry would also work, but the loop matches the code line for line.
- The outer `catchCause` answers `the direct database connection failed` with the squashed message, as at `:586`.

Unit test for `withClient` interrupt: the client is `new pg.Client` inside the function. Either inject the constructor as an optional parameter (`make = (url) => new pg.Client(…)`) or `vi.mock('pg')`. Prefer the parameter, because a mock of `pg` reaches every import in the file. Then interrupt a `fn` that is `Effect.never` and assert `end` was called once.

## What can and cannot be checked before the merge

`pnpm test` checks all the row text through the six pinned unit files and the two new unit tests. That is the claim the `build` step can verify.

The Postgres branch (`pooledConnection`, `directIsSessionMode`, `schema` against a real server) is exercised only by `apps/cli/integration/doctor.test.ts`, which runs after the merge. Before the merge, the `withClient` interrupt test stands in for it. The rest of the Postgres branch is checked by reading the diff against `:550-591` and `:668-`.
