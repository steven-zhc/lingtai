## Design note for #1181: the guides and ADRs say what 0128 made true about the recipe file

This ticket only changes prose and one hand-drawn SVG. The ticket says where every edit goes; this note covers three places where the ticket is wrong or leaves something open, plus the facts each edit has to match. Check each sentence against the code cited, not against the ticket's evidence bullets.

### 1. Nothing rewrites a deleted file, though one evidence bullet says it does

The `doc/operating.md:58-67` bullet says *"the next read rewrites it"*. That is false. Follow the ticket's title and 0128 §6 instead: *"the module never writes it from the log … the file is missing … nothing is appended and nothing is written; the read fails with that refusal"*. The code agrees:
- `packages/project/src/read.ts:3`: *"the file is never written"*.
- `read.ts:26`: *"a missing file records nothing, whatever the Project holds"*.

So the *safe to delete* paragraph keeps `<project>/recipe.yml` among the things not to delete, but for a new reason:
- Deleting it stops that project's attempts. Each read is refused, naming the file, until a person writes the file again.
- The content is not lost. Every version is a `ProjectRecipeChanged` on `prj-{project}` with its `source` and `by`.
- `config.yml` and `env/` keep the old wording (*you wrote it, nothing else has a copy*).

Do not name a restore command, because none exists. Outside tests, `ProjectRecipeChanged` is read only by the domain reducer and by the board's history line (`apps/board/src/lib/history.ts:447`). If the guide says where to see the versions, it says "the project's history on the board". A recipe history view is out of scope (0128, *Not decided here*).

### 2. Who writes the file, and what a read records

Use these facts in the same words on every page: `recipe.md` *Where it is*, `operating.md`, `glossary.md` (ProjectState) and `concepts.md` (Recipe).

- **Changes made through Lingtai.** `changeRecipe` is the only writer (`packages/project/src/change.ts:1-2`). It is used by the board's save, setup and `lingtai add` (0128 §6). It writes the file first and then appends `ProjectRecipeChanged` naming the person (`change.ts:129-137`).
- **A hand edit.** It is allowed. The next read of the file records it as `by: 'file'` (`read.ts:28`, `recipeText`).
- **Text that does not parse, or that the schema refuses.** It is recorded nowhere, and the caller's refusal says why (`read.ts:27`). Validity depends only on the declared text: no host probe and no preset (0128 §6). So a hand edit is recorded even on a host that cannot sandbox.
- **A project added before 0128.** It gets its first recorded recipe the first time anything reads it, and nobody has to do anything (0128 §6, *"or the Project has no recipe yet"*).
- **The run's own copy.** `StepsResolved.recipe` holds the resolved recipe a run used. It is *"present on every event written since 0128 §4"* (`packages/domain/src/events.ts:1149-1157`). `RecipeRecorded` is *"Readable for ever, appended never"* (`events.ts:1160-1161`).

The ProjectState row in the glossary changes in four ways:
- It is one per project, not "one per repository".
- It holds the declared recipe (`sourceHash` and source) and the observed sandbox state (0128 §5).
- It does not hold "the recipe hash last resolved".
- *Repository* stays only where it means the GitHub `owner/repo`.
