## Design: #1258 — triage acts on its own answer

### Where it goes

| Piece | File |
|---|---|
| `actOnTriageTransition`, required `ifVersion`, the "unchanged" check | `packages/domain/src/ticket.ts` (next to `finishTriageTransition`, `:1184`) |
| `BOUNDS.triageRetries: 1` | `packages/domain/src/failure/respond.ts:579` |
| `triageSpentOf(state, runId)`, the one reader of what triage has spent | `packages/domain/src/read-model.ts` (next to `triageFactsFromState`, `:150`) |
| `startTriage` returns its version; `finishTriage` takes the tail after it | `packages/conductor/src/ticket/commands.ts:457-525` |

The tests are unit tests. `apps/cli/unit/triage.test.ts` and `triage-catch-up.test.ts` already exist, and `createMemoryEventStore()` is enough for all of them. The integration half covers none of this.

### 1. The binding is captured once, right after `TriageStarted` lands

- **`v0`.** `startTriage` answers `{ok: true}` and nothing else (`commands.ts:487-489`). It discards what `store.append` returns, which is the `Envelope[]` (`event-store.ts:353`) with the appended `version`. Return that version as `{ok: true, version}`. Do not compute it in the runner.
- **The head comes from the log, not from `headSha`.** The runner's `headSha` is the mirror's resolution of the attempt's head (`triage.ts:702`). The final append also falls back to `baseSha ?? ''` (`triage.ts:1243-1246`). Binding a `FixRefusal` to that value would bind it to the base commit whenever the mirror misses.
  - Bind to `AttemptState.headSha`, which `gatherEvidence` already reads as `head` (`triage.ts:687-690`; its comment: *"the log is what settles whether the attempt produced a commit"*).
  - Read it right after `TriageStarted` in **both** paths. The mechanical merge-conflict path (`triage.ts:818-848`) never calls `gatherEvidence`.
  - `null` is a legal head: an attempt that committed nothing.
  - `WaitTriaged.headSha` keeps its current value and meaning. It is §9's "the head it read", not the binding.

### 2. "Unchanged since `v0`" reads events, not state

`finishTriage` reads only the reduced state (`commands.ts:513`), and a `TicketState` cannot tell which events came after `v0`. Have it also read `store.read(ticketId, v0 + 1)` (`fromVersion` is inclusive, `event-store.ts:355-356`) and pass that tail to the pure transition.

The rule: every event in the tail is a `RunPrompted` or `RunSpent` whose `for` is `{_tag: 'Triage', waitId}`. That `for` is set at `commands.ts:565` and used on both records (`:569`, `:603`).

**`finishTriage` maps `changed` to `lost` today (`commands.ts:518-521`), and the runner retries `lost` five times and then fails (`triage.ts:1257`, `:1266`).** If that mapping stays, an unrelated event fails the whole triage instead of recording `TriageFailed{changed}`. `changed` must become a refusal.

A lost append still re-reads, because a concurrent writer might only have added this triage's own run facts. The re-read re-runs the whole check, including the tail. It does not just move the version.

Add a code comment that a body edited on GitHub is not on the log and is not caught (0118 *Consequences*).

### 3. `actOnTriageTransition` builds the resolution through `resolveTransition` and `resolvedEvents`

Do not hand-build the `WaitResolved`. There are three reasons:

- `resolveTransition` already holds the `allowedResolutions` check (`ticket.ts:1045`).
- `StartNewAttempt` puts a `TicketReleased` in the same append (`ticket.ts:1093-1107`). A hand-built pair would leave the claim held.
- A future resolution tag stays one table.

`resolveTransition`'s `repeat` answer (`ticket.ts:1023-1042`) exists so a person's re-click can reschedule. For triage it means `wait-not-current`, never `repeat`.

**Inputs the transition cannot read itself.** The head and the counters live on the attempt stream, so the runner reads them at answer time and passes:

- `headNow`: `AttemptState.headSha`, read again at answer time.
- For `FixRefusal`, the `{head, ref}` that `savedHead` gives the person's path (`resolve-wait.ts:330-360`).
- For `RedoStep`, `rerunHeadOf(state)` (`resolve-wait.ts:363-422`). Use these tables, not a hand-written `agent/<n>`, so triage resolves only what the person path would accept and the next pass can cut.
- The counters, built with `causeBoundsFor` (`proposed-route.ts:210`) from:
  - the recipe's limits — extend the `triageFor` port, which already resolves the recipe at `triage.ts:482-486`;
  - `continuationSpent(run)` and `implementRound`;
  - `reduced.newAttempts.length` and `personAsksFromState`;
  - each attempt-stream counter taken through `triageSpentOf` (§4).

**Origin for `actionFor`:**
- A `ProposedEscalated` wait with a `DiffTooLarge` proposal → `'diff-too-large'`.
- Anything else → `'other'`. `'run-limit'` only matters for `writeSpentOnThenRedoStep`, which is #1260's.

**Head rules:**
- `headNow` differs from the bound head → `head-moved`.
- `FixRefusal` with no saved head → `head-moved`.
- `RedoStep` on `atBase` with a bound head of `null` is allowed. A person can do the same, and `Unfinished` with no commits is the common case.
- `StartNewAttempt` needs no head.
- The person path also checks the remote ref through a GitHub client (`resolve-wait.ts:345-357`), and the runner has no GitHub client. Use `deps.mirror.refSha` on the saved ref (`triage.ts:536`) in its place. A mismatch is `head-moved`; a failed read is `TriageFailed`, counted toward the retry.

**`StartNewAttempt`'s release** must not use the `person` arm. That arm writes *"Requeued by triage"* with `cause: ByPerson` (`ticket.ts:951-962`). Add a `triage` arm whose cause is `{_tag: 'NewAttempt', newAttempt: used + 1}`. The existing reducer then counts it (`ticket.ts:577-580`), and so does the existing reader (`conduct.ts:1772`), in the same append as the `WaitResolved`.

### 4. The spend: store the number and read the max, never add

**This is the decision the ticket does not make, and the code is wrong without it.**

The attempt-scoped counters live on the **attempt** stream (`attempt.ts:244-251`), and `WaitResolved` is on the **ticket** stream. The attempt reducer cannot see a triage resolution, so "count `WaitResolved{by: 'triage'}`" has to be done by a reader that sees both. That reader cannot *add* the triage count to the attempt counter: the continuation records its own number for the same bound, and the sum then counts it twice.

- **`refusalFixes`.** The continuation passes `roundsSpent: continuationRound(runState, true)`, which is `implementRound + 1` (`conduct.ts:793-795`). The implement step then records that round on the attempt stream.
- **`stepRedos`.** A person's `RedoStep` continuation writes no `StepRedone` (`conduct.ts:1512-1517`: *"the counters are the attempt's own, unchanged"*). But a later crash in that same continuation emits `StepRedone{rerun: spent + 1}` (`run-attempt.ts:1468-1471`, `:1660`). If `spent` included the triage count, from then on `attempt.stepRedos` already contains it, and a sum counts it again.

**The shape.** Add an optional `spent: {bound: CauseBound, n: number}` to `WaitResolved` (`events.ts:385`).

- Triage writes `n` as the number the continuation will itself record for that bound:
  - `refusalFixes`: `continuationRound(run, true)`
  - `stepRedos`: `stepRedos + 1`
  - `conflictResolutions`: `conflictRounds + 1`
- The field is needed because the resolution tag alone does not say which bound was spent. `fixRefusal` and `resolveConflict` both resolve as `FixRefusal`, and a conflict's round is *"its own budget, never `rounds`"* (`respond.ts:705`).
- Keep the field in the reduced wait's `resolution` record (`ticket.ts:94-100`). That changes the ticket snapshot's shape, so bump `ticket-codec.ts`'s version the way #1268 did (`:172`).
- A person's resolution has no `spent` and spends nothing.

**The reader.** `triageSpentOf(state, runId)` returns the highest `n` per bound over the waits on `runId` whose resolution `by === 'triage'`. Each counter is then:

> `max(attempt's own counter, triageSpentOf[bound])`

This is the attempt reducer's own idiom: *"A rerun in place raises the count by its own number, never by one: a replay cannot double it (#1201)"* (`attempt.ts:579`).

It is used in two places:
- the counters `actionFor` reads;
- every `continuationSpent` / `roundsSpent` handed to a continuation (`conduct.ts:1520-1545` and `:1649-1655`).

The result is one spend whether or not the continuation has run yet, which satisfies the restart test in *Done when*.

`newAttempts` needs none of this, because §3's release carries it.

**`priorGrant` (`conduct.ts:1573-1578`)** must count only a person's `FixRefusal`. Otherwise a triage round is capped like a person's one-lap grant (`roundLimit`, `:1656`). Also, the grant text at `:1660` says *"A person granted…"*; make it say triage when the resolution came from triage.

`personRerunsOf` (`conduct.ts:334`) counts every `RedoStep` and stays that way. It is a summand of the dispatch-id suffix, not a bound, and a triage rerun needs a distinct id too.

### 5. Carrying it out needs `ContinueRequested`, not just `WaitResolved`

`WaitResolved` wakes the loop (`work-loop.ts:131`), but what tells a pass which issue to continue is the control stream's `continuing`, built from `ContinueRequested` (`control.ts:261-272`; `resolve-wait.ts:256-262`: *"What tells the next pass which issue to look at, not what wakes it"*).

The person path appends it after `Approve`, `FixRefusal` and `RedoStep` (`resolve-wait.ts:279-284`). Export `requestContinuation` (`resolve-wait.ts:559`) and call it from the runner after a resolving append, with `by: 'triage'`. `StartNewAttempt` needs none, because it releases.

**Restart between the two appends.** A person recovers from this by clicking again (`repeat`). Nobody clicks for triage.

- Add a step to the triage catch-up, which today visits only cards whose `state === 'waiting'` (`triage.ts:185`): when a ticket's lifecycle is `approved`, and the wait it names was resolved `by: 'triage'`, append `ContinueRequested` again.
- Run it only from the daemon-start scan. A catch-up triggered by a resume or a recipe change can run beside a live continuation.
- A duplicate is safe because `continueTicket` re-reads the ticket and refuses stale rows (`resolve-wait.ts:258-261`).
- The log settles whether this happened: a control-stream `ContinueRequested{runId}` after the ticket's `WaitResolved{by: 'triage'}`, then the attempt's next `StepStarted`.

### 6. A refusal is recorded even when the wait has moved on

*Done when* asks that a person's `WaitResolved` racing the answer still produce an appended `TriageFailed`. 0118 §9 agrees (*"A triage that finishes after the person has acted is still recorded, for its cost, and shown nowhere"*).

Today the runner appends nothing on `wait-not-current` (`triage.ts:1253-1255`). After this change, the failure record:
- is an expected-version append at the version it just read, so it never interleaves with another append;
- does not check that the wait is current;
- never resolves anything.

That is how this note reads item 4's *"still bound by item 2"*.

### 7. The retry

**Eligibility.** The next attempt starts iff the latest attempt number is `≤ BOUNDS.triageRetries`, whether that attempt ended interrupted or `Done{TriageFailed}`. This replaces the literal `< 2` at `triage.ts:212` and `:252`. 0118 §3's *"at most twice in all"* holds for interruptions and failures alike.

**What does not count as an attempt.** A result with `started: false` (no `TriageStarted`, `triage.ts:796-803`), and a refusal that was `wait-not-current`.

**Where it runs:**
- In the enqueued worker, right after `deps.run` returns a failure: same queue key, and the same `locked` check first (`triage.ts:213-219`), so a pause or a usage limit holds the retry the way it holds the first attempt.
- In the catch-up, for a daemon that restarted in between.

**Leave `triageStatus` (`wait.ts:1134`) alone.** The board shares it, and the decision to retry is the daemon's.

### Edges this note decides beyond the ticket

- **The attempt-stream read fails** at the binding or at the answer → `TriageFailed`, which counts toward the retry. It is never read as "unchanged".
- **`finishInterrupted`** already passes `ifVersion: reduced.version` (`triage.ts:271`). With the tail rule that still means "unchanged".
- **Cost to later tickets:**
  - Every new continuation branch in `conduct.ts` must take its counters through `triageSpentOf`.
  - A unit test pins that `max(…)`: a triage `RedoStep` followed by a crash in the continuation leaves `stepRedos === 2`, not 3.
