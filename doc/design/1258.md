# #1258 design: a triage answer that resolves its own wait

Most of this is laid out in the ticket. These are the places where the code today pushes the shape somewhere the ticket does not say, or where an obvious reading gets it wrong.

## 1. The unchanged check reads events, so it lives in the command and not in the reducer

`TicketState` keeps a `version` but not the events, so `finishTriageTransition(state, …)` cannot tell the triage's own `RunPrompted`/`RunSpent` apart from a person's edit (`packages/domain/src/ticket.ts:1161-1192`). Keep the transition pure and hand it the tail:

- `actOnTriageTransition(state, { binding, answer, counters, since, headNow })`. Here `since` is `events.slice(v0)` and `headNow` is the attempt's head as read at answer time. `since` is unchanged when every element is a `RunPrompted` or `RunSpent` whose `data.for` is `{_tag: 'Triage', waitId}` for this wait. Version equals the event count on this store: `recordTriageRun` appends at `current.length` (`packages/conductor/src/ticket/commands.ts:~590`).
- The new command `actOnTriage` in `commands.ts`, beside `finishTriage`, does the reads. It reads state through the snapshot and reads the raw stream the way `startTriage` already does (`commands.ts:472`), then appends at `state.version`, not at `v0`.
- Do **not** add a reducer field such as "the last version that was not a triage run fact". It changes the snapshot shape and needs a reducer-version bump (0124), and it only buys a purity the read above already gives.
- `finishTriageTransition`'s `ifVersion` becomes required and uses the same tail rule. `finishInterrupted` already passes one (`apps/cli/src/triage.ts:272`).

**Where `v0` comes from.** `startTriage` returns `{ ok: true }` and no version (`commands.ts:487-488`). Make it return `state.version + decided.events.length`. The runner keeps that number from the append that actually landed, which is the last pass through its retry loop (`triage.ts:860-889`).

## 2. `changed` stops being `lost`

Today `finishTriage` maps `changed` to `{ok: false, lost: true}` (`commands.ts:518-521`), and the runner retries `lost` five times, re-reading each time (`triage.ts:1235-1265`). Once `v0` is fixed, a real `changed` fails identically five times. Then the function fails (`triage.ts:1262-1265`), no `WaitTriaged` lands, the catch-up reads `Interrupted`, and the stale answer becomes an uncounted extra attempt. So:

- `lost` means only the append lost a race. The runner re-reads and decides again against the same binding.
- `changed`, `head-moved` and `not-offered` are refusals. They go to item 4's failure append and are never retried in that loop.

## 3. What a refusal appends

The ticket's item 4 says the `TriageFailed` is "still bound by item 2". Taken literally, a `TriageFailed{changed}` could then never land, because the stream did change. The rule to build instead:

- **`changed`, `head-moved`, `not-offered`, and a read that failed:** append `WaitTriaged{TriageFailed{why}}`, gated on the wait still being current at a fresh read and at that read's version. Do not gate it on `v0`. A person's resolution that won the race makes the wait not current, so the "never a stale failure after a person's resolution" property still holds.
- **`wait-not-current`:** append nothing, as today (`triage.ts:1253-1255`). The cost is already on the ticket as `RunSpent{for: Triage}`, which is 0118 §9's *recorded for its cost and shown nowhere*.
  - For the Done-when case where a person resolves first: the runner's result is `TriageFailed{wait no longer current}`, there is one `WaitResolved` on the stream, and there is no second `TriageStarted`. **I read that bullet's "appends `TriageFailed`" as the runner's result, not an event.** Appending one would be the stale failure item 4 forbids.

## 4. Head binding: use the log's head, not the mirror's

The runner has two heads. One is `AttemptState.headSha`, the log's claim, which it reads as `head = run.headSha` (`triage.ts:690`) and records as `recordedHead`. The other is `deps.mirror.refSha(...)` (`triage.ts:702`), which is what gets passed as `headSha` today.

Bind to the log's head. At answer time, re-read the attempt stream (`readThroughSnapshot(…, attemptReducer, runId, …)`, as `finishInterrupted` does at `triage.ts:259-260`) and compare. That needs no mirror call, so the comparison has no network failure mode of its own. A failed attempt read is the *read that fails* edge: `TriageFailed`, never treated as unchanged.

No run, or a head of `''`: `FixRefusal` and `RedoStep` are refused as `head-moved`, and `StartNewAttempt` goes ahead (ticket edge).

## 5. Spending: the counters live on the attempt stream and the count lands on the ticket stream

This is where the "spend once" trap really sits.

- `stepRedos` is raised only by `StepRedone`/`StepRerunInPlace` and by `RerunStep` routes, on the **attempt** stream (`packages/domain/src/attempt.ts:580-584`, `:621-622`).
- `refusalFixes.used` is `spent.rounds` (`packages/conductor/src/proposed-route.ts:216`), which is the implement round.
- `newAttempts` is the ticket's `newAttempts` list. It grows only on a `TicketReleased{cause: NewAttempt}` (`ticket.ts:577-580`), which only the conductor's own restart writes (`conduct.ts:6067`, `:6096`).
- `WaitResolved` is on the **ticket** stream. The wait reduce keeps `resolution: { resolution, by }` (`ticket.ts:98`).

So the count cannot be a reducer on one stream. It is **a summand read off the ticket's waits wherever counters are built.** Add one pure helper in `@lingtai/domain`, `triageSpentOn(ticketState, runId)`, and use it in three places:

- `continuationSpent` (`conduct.ts:798`) and its callers (`:1400`, `:1454`, `:1522`, `:1652-1655`);
- `causeBoundsFor` (`proposed-route.ts:210`);
- the triage runner's own `counters`.

Per bound:

- **`stepRedos`:** count every `RedoStep` with `by: 'triage'` on a wait of this `runId`, always. Its continuation is the released-rerun path, which writes **no** `StepRedone` and spends nothing (`run-attempt.ts:1043`: *"No `StepRedone` is written and `stepRedos` is not spent"*). The continuation's own event therefore cannot double it. This is the Done-when test with the restart.
- **`newAttempts`:** count every `StartNewAttempt` with `by: 'triage'` on the ticket, always. A person's `StartNewAttempt` goes through `approve.ts:440` and writes no `NewAttempt` release, so nothing else counts it.
- **`refusalFixes` and `conflictResolutions`:** this is where it double-counts. The continuation of a `FixRefusal` goes through the grant path. `roundsSpent: continuationRound(runState, granted)` (`conduct.ts:1651`) raises the implement round, and that round *is* `refusalFixes.used`. Count a triage `FixRefusal` only while its continuation has not yet been taken up: the ticket lifecycle is `approved` on that `waitId` and the attempt has no implement round past the one at the wait. After that, the round is the record.
  - Pin it with a test that mirrors the `StepRedone` one: a triage `FixRefusal`, then its continuation's implement round, gives exactly one used, and a restart between the two also gives one.
  - Check whether a conflict continuation raises `conflictRounds` the same way. If it does, the same pending-only rule applies.
- **A person's resolution adds no summand.** The grant raising the round for a person's `FixRefusal` is today's behaviour and is left alone. *Still spends nothing* means this ticket adds nothing for it.

`personRerunsOf` (`conduct.ts:334`) filters on `_tag` alone, so it will count a triage `RedoStep` too. That is correct: it is a dispatch-id suffix, not a bound. Leave it as it is.

## 6. Carrying it out: `WaitResolved` alone is not enough

`WaitResolved{FixRefusal|RedoStep}` moves the lifecycle to `approved` (`ticket.ts:668-670`). But after a person's resolution, `resolveWaitHoldingEffect` also appends `ContinueRequested` on the control stream (`packages/conductor/src/resolve-wait.ts:257-273`). Per that comment, it is *"what tells the next pass which issue to look at, not what wakes it."*

- Export `requestContinuation` (`resolve-wait.ts:559`) and call it after `actOnTriage` commits, for `FixRefusal`/`RedoStep` only, with the same never-throw handling.
- `StartNewAttempt` needs none, as for a person.
- A request lost to a crash is the same gap a person's has today ("a request this append loses is simply never offered"). It is not a new one.
- Update `resolve-wait.ts`'s header (*"The only writer of `WaitResolved`"*, `:4`): there are now two writers, and both enforce `allowedResolutions`. No ADR says there is one writer, so this is an edit, not a superseding file.
- `actOnTriageTransition`'s `not-offered` check is `allowedResolutions(wait.reason).includes(resolution._tag)`, the same table `resolveWait` uses.

## 7. Asking once more

The catch-up retries only `Queued`, or `Interrupted` with `started.attempt < 2` (`triage.ts:212`). Generalise it to one rule: **another attempt is allowed while `started.attempt < 1 + BOUNDS.triageRetries`, when the latest result is `TriageFailed` or the attempt was interrupted.**

- `TriageFailed` currently reads as `Done` in `triageStatus`, so the change belongs there or in the catch-up predicate.
- Count attempts *started*, not failures, so an interruption and a failure share the one retry.
- The live path is the runner itself: after appending a `TriageFailed`, it enqueues the next attempt through the same `enqueueTriage`. The catch-up covers a restart in between, and `startTriageTransition`'s `already-started` check stops the two from both buying it.
- Add `triageRetries: 1` to `BOUNDS` (`packages/domain/src/failure/respond.ts:579`).

## Checks

Everything above can be checked at unit level:

- the transition and the helper are pure;
- `actOnTriage` and the runner run against `createMemoryEventStore()`;
- the race cases are built by appending between `TriageStarted` and the answer.

Nothing here needs the integration half.
