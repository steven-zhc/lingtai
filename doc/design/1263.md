## Design note: #1263, the split parent's return attempt

### Where it goes

**1. The claim: `packages/domain/src/ticket.ts:882-898`**

Delete the `split-done` return. Once no child is open, control falls through to the ordinary `TicketClaimed` at `:900`. Also remove `split-done` from `ClaimDecline` (`:859`). `split-open` (`:888`) and `split-unreadable` (`:884`) stay exactly as they are.

`SplitChildState` (`:844`) stays, because the brief needs it.

The only files that name `split-done` are `ticket.ts`, `conduct.ts`, `conductor/unit/claim-split.test.ts` and `domain/unit/ticket-transitions.test.ts`. Once the union member is gone, tsc will point at every reader.

**2. The children's read travels on the claim's success, not on the refusal**

The GitHub read is done by `claimTicketEffect` (`packages/conductor/src/ticket/commands.ts:152-170`). The comment there says it is *"asked only where it always was — never of a held or landed ticket"*. Keep that read where it is:

- Widen `Claim` (`commands.ts:112-118`) with `splitChildren: readonly { number; title; stateReason }[] | null`.
- Fill it from `children.read`. `TicketDetail` (`discover.ts:86-90`) already carries `title` (via `TicketListing`) and `stateReason`, so this needs no new request.
- Write `stateReason ?? null` and keep it null. `ticket.ts:843` says *"`stateReason` null is *not reported*, never *completed*"*.

Do **not** put the children on `TicketClaimed`. That would widen a payload, which means changing the codec and its fixture, only to record something GitHub can answer again. The durable list of children is already `state.split.children` (`ticket.ts:311-317`): *"The only list of a split's children a close rule may read"*.

**3. The close-at-claim goes: `conduct.ts:3329-3368`**

Delete that block, plus `splitChildrenWords` (`:391`) and `splitClosedComment` (`:400`). Also drop the `SplitChildState` import at `:345` if nothing else uses it.

The `if (!claim.ok)` at `:3369` then covers every refusal left. `closeHoldingEffect`, `editEndedWaitsEffect` and `tellGitHubEffect` keep their other callers, so check before removing any import. The split's wait was already resolved by `WaitResolved{Split}`, so dropping `editEndedWaitsEffect` here leaves no wait unedited.

**4. The brief**

The paragraph is a separate, pure function in `packages/conductor/src/prompt.ts`, for example `splitReturnParagraph(children, doneWhen)`. It is appended as its own part at the `implementerParts` site (`conduct.ts:5079-5107`), next to `alsoText` and `redoNote`. Do not thread it through `renderPromptParts`'s template slots.

- It renders only when `reduced.split !== null`. Every other ticket's prompt stays byte-identical, so the existing prompt tests do not move.
- **The source of the children:**
  - Use `took?.claim.splitChildren` when this pass made the claim.
  - Otherwise use `reduced.split.children` (number only) and say *closed; title and reason not read on this pass*. That covers a continuation (`continueTicketEffect` at `:3299` does no children read) and a claim racing a reopened child.
  - The check is against the base either way, so how a child closed is a hint and never the criterion. Do not add a second GitHub read for a continuation.
- A run cut off by an account limit is handed its recorded brief (`:5077-5081`, #1205), so it keeps the paragraph it was first given with no extra work.
- **No `## Done when`:** this is decided by the same `doneWhenItems(claimedBody)` that `decideImplementOutcome` uses (`conduct.ts:5297`, `domain/src/done-when.ts:25`). Null means the paragraph says there is no `## Done when` section, so `AlreadyDone` is not available: implement, or declare `Unclear`.
  - Check whether `decideImplementOutcome` already turns an `AlreadyDone` against `doneWhen: null` into something other than `AlreadyDone`. If it does, the prompt is just being honest about that. If it does not, the paragraph is not what enforces it, and that refusal belongs in `implement-outcome.ts` (#1251's code) as a one-line test, not here.

**5. The ending is already wired**

`conduct.ts:5881-5882` passes `splitParent: reduced.split !== null`, commented *"A parent after a split ends `satisfied` the moment its check passes; any other ticket waits to be confirmed (#1251)."* `confirm-satisfied.ts:2` is for a *non-split* ticket only.

So no code is needed here. The `Done when` item is a test showing that a claim through the new path reaches that flag with `split` set.

### `newAttempts`: test the return attempt, and leave the split's own release alone

The counter is appended only for `TicketReleased{cause: NewAttempt}` (`ticket.ts:617-620`). The return attempt starts with a `TicketClaimed`, which appends nothing to it. The unit test is: fold the parent's events through the split, read `newAttempts.length`, add the return attempt's claim and its satisfied end, and read it again. The two values must be equal.

One thing to know so that nobody "fixes" it here: a `Split` resolved by the system is released with `by: 'triage', newAttempt: state.newAttempts.length + 1` (`ticket.ts:1181-1190`). That split's own release *is* counted, but it happens before the return attempt, and the `Done when` measures across the return attempt only.

- Do not subtract it.
- Do not add a flag.
- Do not add a second counter.

If it matters, it is a backlog entry about the split, which is #1261's territory. The field that settles it on the log is the `TicketReleased.cause._tag` that sits immediately before `TicketSplit`'s `WaitResolved`.

### The retry and "at most once"

There is nothing to build for *once*. A return attempt that ends `satisfied` or `landed` is terminal. One that fails and is released goes back to `backlog`, and `state.split` is still set. The next claim reads the children again and makes another return attempt, within the ordinary bounds. That is the ticket's own retry edge.

A return attempt that comes out `TicketTooBig` reaches #1261's once-per-root refusal (`split-ticket.ts:275-277`, *"a `SplitStarted` for another wait has spent the split"*). Do not add a guard of your own.

### Tests

- **`domain/unit/ticket-transitions.test.ts`:** a split with every child closed is now `ok: true` with one `TicketClaimed`. `split-open` and `split-unreadable` are unchanged.
- **`conductor/unit/claim-split.test.ts`:**
  - Rewrite `:30` and `:65`/`:72` to show that the claim succeeds, that `claim.splitChildren` names every child with its title and `stateReason`, and that no `TicketClosed` is appended.
  - The test at `:97-101` reads `refusal.version`. It pins the version the old close used, so delete it with the close rather than porting it.
- **`prompt.ts`'s paragraph:** a pure unit test covering:
  - every child named;
  - a `not_planned` child said as such;
  - null worded as *not reported*;
  - the no-`## Done when` variant;
  - an absent paragraph when `split` is null.
- **Ending and counter:** a fold-level test as described above.

Every one of these is unit-level. None of this behaviour needs `pnpm test:integration` to be checked.
