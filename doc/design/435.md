# Design: #435, `init` and `add` driven from `unit/`

`doc/design/400.md` §*`add`: move it where a test can reach it* and §*The unit tests, and the seam they need* still describe the shape. This note covers only what has changed since that was written, and the places where following it literally goes wrong.

## The store's test side stops answering `init`, and the #434 tests feel it

Today `storeChoice` reads the file through `machineFile`, which returns `path: null` under vitest with no `LINGTAI_HOME` (`packages/env/src/index.ts:104-108`). `storeChoice` then takes the test side and answers SQLite from `LINGTAI_TEST_SQLITE_PATH` (`index.ts:557-584`). The existing #434 tests rely on that. Their header says so: *"`env` carries no `LINGTAI_HOME`, so `storeChoice` answers from `LINGTAI_TEST_SQLITE_PATH` alone"* (`apps/cli/unit/init.test.ts:10-12`). Their `ENV` sets that variable (`:44`).

`machineFileFrom(path, text)` always has a non-null `path`, so passing it to `storeChoice` skips the test side completely. That is the intent: the injected `machine` *is* the machine. As a result:

- **The five #434 tests in `unit/init.test.ts` change behaviour.** With `machine.read` returning null, the store now reads `nothing chosen`, so the store question is asked and takes the `''` that the tests currently script for a later question. Add `--store sqlite` to their argv rather than re-counting answers, and drop the header sentence quoted above. The test that #434 marked as deferred ("the `machine` seam is that ticket's") is this ticket.
- **Keep `storeChoice`'s order.** The exported-URL check (`dbVar`/`optional`, `index.ts:544-554`) still runs before the file argument is consulted. Only the `machineFile(from)` line at `:556` becomes `file ?? machineFile(from)`. `boardPort` → `machineBoardPort` does the same at `:756`, after its exported-variable check.
- **`machineFileFrom(path: string, text: string | null)`.** Null means absent and answers `{ path, provider: {} }`. A parse failure answers `unreadable`, exactly as `index.ts:137-143` does. `machineFile` becomes: compute the path, return early on null, read with `readFileSync` (keeping its open-failure `unreadable` branch at `:132-134`), then call `machineFileFrom`.

## Every `storeChoice`/`boardPort` call in `init.ts` takes the file, including the helpers

The calls are at `init.ts:474` (`boardPort`) and `:719`, `:768`, `:876` (`sqliteRefused`), `:909` (`confirm`). `sqliteRefused` takes `Pick<InitWorld, 'env'>` (`:875`). Widen it to `'env' | 'machine'`.

Read the file at the call, not once at the top. `confirm` exists to read back what `writeConfig` just wrote (`:897-917`), so a cached text would confirm the old file. A small `machineFor(world)` that returns `machineFileFrom(path, world.machine.read(path))` keeps each call one line.

The live `machine`:

- `read`: today's `existsSync`/`readFileSync`, returning null when absent.
- `write`: all of `writeConfig`'s body (`:247-252`), meaning the mkdir, the `.partial`, the `chmod 0600` and the rename. Do not split the mode out of the seam. The password-bearing file being `0600` is the live implementation's promise.
- `describeHome`: `:651-668` moved verbatim.

`readConfig` (`:231`) then parses `world.machine.read(path)`. After this, `init.ts` imports nothing from `node:fs`. That is the check that the seam is complete.

## One map behind both seams in the test

`resolveLocalRecipe` reads `config.yml` through the *recipe* `read`, which is `world.files.read` (`packages/recipe/src/local.ts:300-314`, `checkMachineConfig(await read(machineFile), …)`). `init` writes it through `world.machine.write`. Back `files` and `machine` with **one** `Map<string, string>` in the harness, so the recipe resolve sees the `config.yml` that `init` wrote. Two maps would pass while testing less.

`describeHome` in the harness can derive its answer from the same map, or return a fixed string. Nothing in the Done-when asserts on it.

## `add.ts`

`addFlow(args, world)`, where:

```ts
interface AddWorld {
  project: FirstProjectWorld
  githubDeps?: AskBeforeGithubAddDeps
  error: (line: string) => void
}
```

- The `console.error` calls at `lingtai.ts:441`, `:468` and `:478` go through `error`.
- `parseFlags` is used only by `addCommand` (the `--defaults` handling at `lingtai.ts:403-414`). Move it into `add.ts` with `addFlow`, or export it from `lingtai.ts`. Importing `lingtai.ts` from a test runs `main()`, so the move is the one that works.
- `kept`: `addCommand` passes `kept: ADD_KEPT` to `liveFirstProjectWorld` only when there is a slug (`lingtai.ts:464`). Inside `addFlow`, write `{ ...world.project, kept: ADD_KEPT }` on the slug path. The live wrapper then builds `liveFirstProjectWorld` without `kept`, and the behaviour is the same.
- **Do not add `doctor` to `add`.** 400.md lists it in `add`'s world, but #434 put doctor at the end of `init` only, and `addCommand` prints none today. The ticket's *only where the code lives changes* wins.
- `askBeforeGithubAdd` still reaches `hasGitHubApp()` and `console` directly (`add-github.ts:189`, `:167`). Leave them. The Done-when-3 test drives `add` with no positional, so the slug path is never reached.

**Done-when 3** is `addFlow([], world)` with an `ask` that records each prompt and answers `local`, then `/repo`, then `''`. A non-null `ask` is what "at a TTY" means here: `liveAsk` is null only when stdin is not a TTY (`question.ts:61`). The test asserts:

- the first recorded prompt is the GitHub-or-directory question;
- every later prompt is the base question or a recipe question;
- `error` was never called and the exit code is 0.

## Done-when 4 is a re-run of `init --local /repo`, not a bare `init`

A bare `init` on a machine with projects lists them instead of asking (`init.ts:343-399` per 400.md, #394 finding 3), and the harness's `projects` returns `[]` anyway. Run the same argv twice against the same map:

- first: `['--local', '/repo']` with every answer `''`;
- second: the same argv, with every answer `''` again.

Then assert that `config.yml` and `recipe.yml` are equal by string to their first-run values. Also count `machine.write` calls on the second run and expect 0. The settled store is reported rather than rewritten (`:768-775`), and the count makes that a claim instead of something that only happens to hold.

## Not checkable before the merge

`integration/init.test.ts` builds `InitWorld` (`apps/cli/integration/init.test.ts`). Give its fixture the live `machine`, meaning the same object `liveInitWorld` uses. Those tests write a real `LINGTAI_HOME`, and its `storeChoice({ LINGTAI_HOME: home })` assertions read that file directly.

`pnpm typecheck` proves the fixture compiles. Its assertions run only after the merge. The four unit tests and the five rewritten #434 tests are the claims that stand in for it.
