# #1377: design note

The ticket covers most of the shape. These are the five things it does not settle, each with what the code does today.

## 1. Previous and next is a pure function that takes the served set

The edge *"a `BOOK` slug that is not servable is skipped"* has to be tested. It cannot be tested through `servable()`, because that reads two constants: `DOCS_PUBLIC = false` (`apps/site/src/lib/docs.ts:53`) and `PUBLIC_SLUGS` (`:70-84`). All five rows are servable today, since `tutorial`, `concepts`, `when-it-fails`, `recipe` and `safety` are each in `PUBLIC_SLUGS`. So put this in `docs.ts`:

```ts
export function neighboursOf(slug: string, served: ReadonlySet<string>): { previous: BookRow | null; next: BookRow | null }
```

- It walks `BOOK` and drops any row whose `slugOf(file)` is not in `served`.
- A `slug` that is not in what is left gives `{ previous: null, next: null }`, and the page then renders no footer.
- The unit test passes in hand-made sets. One example: a set without `concepts` should give `tutorial` → next `when-it-fails`.
- The page builds the set exactly as `treeOf` does: `new Set((await servable()).map(slugOf))` (`:633`). `files` is already in hand at `[...slug]/page.tsx:93`.

The titles for the two links come from the tree's `book` group, which the page already has (`const tree = await treeOf()`, `page.tsx:97`). Look them up by slug there. Do not read the two files a second time.

## 2. The number goes on the entry, not into the title

Add `n?: number` to `TreeGroup['entries']` (`docs.ts:611-615`) and set it in `treeOf` from `BOOK` for the `book` group. Two places render it as `` `${n} · ${title}` ``, each through one small shared helper:

- `DocTree` (`doctree.tsx:30`)
- the index's `<span className="t">` (`docs/page.tsx:73`)

Do not change `title`, for two reasons:

- `title={entry.title}` (`doctree.tsx:27`) is the hover text.
- The Events test compares a whole entry with `toEqual({ slug: 'events', title: 'Events' })` (`unit/docs.test.ts:437`). A number baked into titles would make that kind of assertion brittle for every book entry.

For the index, `entriesOf` (`docs.ts:400-408`) returns `DocEntry` with no number. Look `n` up from `BOOK` by `source` when `section.id === 'book'`. Do not widen `DocEntry`.

## 3. The footer goes at the end of `<article>`, and it is not tied to the *Rendered from* line

The *Rendered from* paragraph is skipped for the tutorial: `{slug !== 'tutorial' && (<p className="source">…`, at `page.tsx:115`. The tutorial is chapter 1 and needs a next link. So render the footer as its own element, last in `<article>`, after that conditional. Do not put it inside the conditional.

Use `<nav aria-label="Chapters">` holding two `Link`s, the previous one left and the next one right. Give it `className="source"`. That class (`site.css:426-430`) already provides the top rule, the muted colour and the small size. Lay it out with an inline `style` (flex, `justify-content: space-between`), the way this page already styles inline (`page.tsx:102`). That adds no new colour and no new CSS.

On the tutorial, the footer sits right under the file's own `## Next` paragraph (`doc/tutorial.md`, last section), which links to several pages. Both stay. Editing the chapter is out of scope.

## 4. Sections: three explicit arrays, plus one guard the ticket does not list

- `book.files` is `BOOK.map((row) => row.file)`. Do not write the list out again.
- The Events splice at `docs.ts:645-650` changes `'guides'` to `'reference'`. Nothing else in it changes. The `reference` tree therefore reads `cli`, `events`, `requirements`, `upgrading-to-0.16`.
- `published()` (`docs.ts:306-310`) pushes each section's files with no de-duplication. A file listed in two sections would come out of `generateStaticParams` (`page.tsx:42-53`) twice. Add a unit test that no file appears in more than one array section. It does not pin any list, so adding a `BOOK` row cannot turn it red.
- A former `guides` file that ends up in no section is already caught at runtime: it shows under *In the repository, not on this site* (`unpublished()`, `docs.ts:320`). No test pins that list, so the *exactly one of the three* check in Done-when is the implementer's to verify by reading the diff.
- Generalise the existing test at `unit/docs.test.ts:41-48` (*"takes every guide the sections name, and they all exist"*) from `guides` to `book`, `reference` and `more`, and keep its comparison `expect(await filesOf(s)).toEqual(files)`. This works because `filesOf` drops a missing file (`docs.ts:300`). For `book`, the same comparison is the ticket's *"every `BOOK` file exists"* test, so a chapter row added before its file fails and names the file.
- Rewrite `unit/docs.test.ts:429-438` to read the `reference` group.

## 5. Corrections to the ticket's reading of today's site

- **The docs index is not served while `DOCS_PUBLIC` is off.** `docs/page.tsx:24` starts with `if (!DOCS_PUBLIC) notFound()`. Change the index anyway. But the Done-when check in `pnpm --filter @lingtai/site dev` is the tree and the footer on `/docs/concepts/`. The index cannot be checked there without flipping the switch, and the switch must not be committed flipped.
- ***More* is visible in the tree today.** Its three entries, `tutorial-more`, `guide` and `from-symphony`, are all in `PUBLIC_SLUGS` (`docs.ts:72, 79, 81`). The ticket's edge *"*More* becomes visible with `DOCS_PUBLIC`"* only holds for the other five. Nothing needs to change for this. Just don't write a test that assumes *More* is empty today.

## ADR

This builds ADR 0112 §13 (the table of ten chapters in four parts) and §17: *"A chapter ends with one way on: the next chapter. The site draws previous and next from the order in §13."* (`doc/decisions/0112-the-site-projects-the-repository.md:87-115`).

§18 also lists `plugins/` among the reference pages. Keeping `plugins` as its own section, as the ticket says, is a grouping on the site and does not contradict the ADR. No ADR change is needed.

## Checks

Everything here is unit-level:
- `docs.test.ts` reads the real `doc/` directory through the existing helpers, just as it does today.
- `neighboursOf` is pure.

`pnpm typecheck` and `HOME=/nonexistent pnpm test` cover all of it. The one thing they cannot see is the rendered footer, so the check in `pnpm --filter @lingtai/site dev` is the only witness for item 3. There is no log to read for any of this: it is a static build.
