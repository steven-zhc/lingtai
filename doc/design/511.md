# #511: the design

## The decision: one of the four "did the behaviour change?" cases is a code bug

The ticket names four cases (`reconcile`, the `sqlite` RunFailed note, `converge`, `integrate`) and asks whether the code or the test is wrong in each. I checked all four. **Only `reconcile` is a code bug**, and it is a one-line fix. Do it first, as its own commit, before any test edits.

### `reconcile`: the code is wrong (fix it here)

`packages/daemon/src/reconcile.ts:666` builds the release like this:

```ts
data: parsePayload('TicketReleased', {
  runId: life.runId,
  reason: `${mine} holds ${DAEMON_LOCK_KEY}, so ${life.worker} was not coming back`,
}),
```

Since #502, `cause` is required and nullable: `export const TicketReleased = z.object({ runId: z.string(), reason: z.string(), cause: ReleaseCause.nullable() })` (`packages/domain/src/events.ts:232`). So `parsePayload` throws a ZodError. The `catch` at `reconcile.ts:675` turns that into `f.action = 'reported'` with `(could not release: …)`. That is the test's `expected 'reported' to be 'released'`.

**The effect in production: since #502, a daemon killed while holding a claim leaves that ticket out of circulation for good.** This is exactly #87, which `releaseForeignClaims` exists to prevent (`reconcile.ts:430-434`).

The fix is `cause: null`, and the intent is already written down. `packages/conductor/src/claim.ts:193-196` says:

> `cause` is `null` for every caller here and the reconciler's own release of a dead worker — neither has one of 0120's causes to name (#502, 464.md choice 4)

Do not choose a `ReleaseCause` variant. None of the four in `events.ts:224-229` (`Restart`, `NeverStarted`, `ByPerson`, `ClaimUnconfirmed`) describes "the conductor holding this claim died."

- **Commit:** `fix(daemon): reconcile's release carries cause: null, so a dead worker's claim is released again`. The body should say the code was wrong and the test was right.
- **Check:** `packages/daemon/integration/reconcile.test.ts` should go green with no edit to its *releases the claim it inherited* case. If that case still needs an edit after the fix, stop and look again.
- **What settles it in production:** a `Reconciled` event on the control stream whose finding for a `ticket-…` stream says `reported` with `could not release: … cause`, and no `TicketReleased` after the orphaned `TicketClaimed`.
- **No unit test reaches this function.** It calls `killWorker` and `rm`. The integration file is the only check, so run it.

### The other three: the test is wrong

**`sqlite` (the failing case lives in `packages/projector/test/contract.ts:654`):**
- `RunFailed` is still in `EVENTS` (`events.ts:1964`), and the conductor still appends it (`packages/conductor/src/conduct.ts:3249`).
- The projector still turns it into the note: `cardFactOf` maps `case 'RunFailed'` to `RunEnded` (`packages/domain/src/read-model.ts:304-307`), and `task-view.ts:661-666` writes `` `${fact.kind}: ${fact.detail}` ``.
- The test is wrong because its own `runFailed` fixture (`contract.ts:183-204`) no longer writes a `RunFailed`. It writes `StepStarted`/`StepEnded{Interrupted}` through `aRun().aStepEnded`. The comment above it says "0120 retires it", which is not true of the catalogue as it stands.
- Fix: make the fixture append a real `RunFailed{kind, detail}` on the run stream.
- No builder exists for it. Add one beside the others in `packages/domain/test/events.ts`, e.g. `aRunFailure(run, kind, detail)` → `[run.event('RunFailed', { kind, detail })]`, so the ticket's "through the builders" holds. Correct the misleading comment.
- The *reaches waiting only through …* case right after it (`contract.ts:674`) uses `blocked()`, which writes `WorkItemBlocked`. Move it to `aWait` with an `AgentQuestion` reason. The expected note `'the \`implement\` step asked: …'` is whatever `legacyColumns` produces now; read it off the code, do not keep the old string.
- `contract.ts` is shared with the Postgres store's test. That one skips without `LINGTAI_TEST_DATABASE_URL`, so the SQLite run is your only check, and the commit body should say so.

**`converge`:** a fixture-only change. `packages/daemon/integration/converge.test.ts:174` hand-writes `{ type: 'TicketReleased', data: { runId, reason: 'killed' } }` with no `cause`. Replace it with `aRelease(...)` (`events.ts`, default `cause: null`). `converge.ts` only reads `TicketReleased` (`converge.ts:300`) and never writes one, so the code has nothing to fix.

**`integrate`:** the conflict paths moved off the event and onto the result.
- `IntegrationRefused` is `{ticketId, branch, reason, detail}` (`events.ts:1093-1098`). `anIntegrationRefusal`'s comment says: "since #502 carries only `reason`/`detail`; the three conflict fields moved to the merge action's own `Conflicted` result".
- `refuse()` in `packages/repo/src/integrate.ts:241-254` still spreads `...conflict` into the payload, and Zod strips it. The return value still carries `conflict: {paths, baseSha, headSha}`.
- So in `integrate.test.ts:192-195`, assert `result.conflict` (`paths: ['README.md']`, `baseSha: developSha`, `headSha: agent2Sha`) instead of `refusal.data[...]`. Keep the `reason === 'conflict'` assertion on the event.
- Leave the dead spread in `integrate.ts` alone. Removing it changes nothing and is not this ticket.

## Where the remaining nine files' new assertions come from

None of these is a code bug. In each case the code already says what the new shape is, and the test should assert that shape rather than drop the check.

- **`notify.test.ts` and `packages/telegram/integration/telegram.test.ts`:** `describe()` handles `WaitStarted` (`packages/extension/src/index.ts:110-111`). The title is `` `${ref} is waiting on you` ``, and the body is `reasonText(d.reason)`, which reads `question`/`said`/`evidence`/`raw`/`why` off the reason (`:89-100`). The desktop sentence did not lose anything. The test hands it `ApprovalRequested`, which falls to `default` (`:133`) and yields the bare `#123`.
  - Build the payload's `event.data` as a real `WaitStarted{waitId, reason}`.
  - For the "Merge agent/123 into main?" case, use a reason variant that carries a `question`. Pick it from `packages/domain/src/wait.ts`.
  - `apps/cli` may import `@lingtai/domain`'s test builders. Only `packages/extension` may not (`unit/imports.test.ts`).
  - The `WorkItemBlocked{hold}` payloads lower in `notify.test.ts` become the same thing.
- **`watch-action.test.ts`:** since #502 the pipeline emits `RunSpent` and nothing else (`packages/actions/src/action.ts:563-576`): "`ApprovalRequested` is gone with them: a `signoff` action's live `requested` rides on the `StepEnded` outcome itself now."
  - Delete the `types` assertions and the "same event the flag emits" comment.
  - Keep `heldAt`/`failedAt`, which are the behaviour being tested.
  - To keep "hold and failure are distinguishable", assert the per-action verdicts in the result (`needs-approval` vs `failed`) rather than events.
- **`run-once-against-the-machines-recipe.test.ts:96-97`:** replace the `ApprovalRequested` filter with the run stream's `StepEnded` whose `outcome.step === 'proposed'`. It should have an action named `tamper` with `yields: 'signoff'`, and that action's result `Completed` with `requested !== null`; this is the shape `boardFactOf` reads (`read-model.ts:470-478`). If the item stream is in reach, also assert the `WaitStarted` that follows. Keep `did` not containing `integrate`.
- **`discuss.test.ts:135-137`:** `DiscussionHeld` is `{chatId, outcome, by}` (`events.ts:1587-1591`). The cost is a `RunSpent{for: {_tag: 'Discussion'}, costUsd}` appended per process on the chat stream (`packages/conductor/src/discuss.ts:575-580`, and the header at `:63-67`). Move the `0.42` assertion onto that event.
- **`ask.test.ts`, `requeue.test.ts`, `subscribers.test.ts`, `subscriber-set.test.ts`:**
  - Seed with `aWait`/`aResolution`/`aWithdrawal`/`aClaim`/`aRelease`.
  - Assert `WaitStarted`/`WaitResolved` types and their payloads: `{waitId, by, resolution, note}`, with `resolution: {_tag: 'Requeue'}` for a withdrawal (see `aWithdrawal`).
  - `ask.test.ts:122` expected `{by, note, withdrawn: true}`. Assert whatever `ask`'s requeue path actually writes; read it, do not copy the builder's `by: 'steven'`.
  - For `subscribers.test.ts`, check which type names the subscriber config in the test declares. A subscription to `ApprovalRequested` becomes one to `WaitStarted`.

## Order, and what to run

1. `reconcile.ts` fix → run `reconcile.test.ts` → commit.
2. Add the builder in `packages/domain/test/events.ts` → `contract.ts` → run `packages/projector/integration/sqlite.test.ts` → commit.
3. One commit per remaining package. Run each file alone: `pnpm vitest run --project integration <file>`, without `LINGTAI_TEST_DATABASE_URL`.
4. Finish with `pnpm fmt:check && pnpm lint && pnpm typecheck && HOME=/nonexistent pnpm test`.

That last step is the only part the `build` step re-checks. The thirteen integration files are verified only by your own per-file runs, so name each file you ran, with its pass count, in the commit that fixed it.

To check the second *Done when* box: `git grep -nE "'(WorkItemBlocked|WorkItemUnblocked|ApprovalRequested|StepFailed|StepPassed)'" -- '*/integration/*' '*/test/*'` should return only `log-predates-hold`'s retired-name cases.

Do not write `fixes #511`. Per CLAUDE.md, the commit that finishes should say `see #511`.
