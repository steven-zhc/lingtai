## Design: #680, rebuilding the estimate projections when a model gets its first price

### Where it goes

**The comparison is a pure function in `packages/conductor/src/rate-snapshot.ts`, and the rebuild is a port.** `packages/conductor` cannot import `apps/cli`, and the runner `lingtai projection rebuild` uses lives in `apps/cli`: `rebuildProjection` at `apps/cli/src/projection.ts:73`, wired at `apps/cli/src/cli.ts:546-550`. So:

- **The new function.** Export `newlyPriced(before: readonly RateRow[], after: readonly RateRow[]): string[]`. It returns the models that have no row of any mode in `before` and have a row in `after` that is not `withdrawn`.
- **Why that rule matches 0110 §5.** It matches *"a model that had no row when it was folded"* exactly. The snapshot never contains a withdrawn row for a model that was never priced: `mergeSnapshot` skips it with `// Nothing priced to withdraw.` (`packages/domain/src/rate-card.ts:243`).
- **A model repriced after a withdrawal is not "new".** Re-folding would not change it anyway. Its new row is dated today, and `estimateRow` only reaches back to `earliestRow` when `rateFor` finds nothing (`rate-card.ts:139-141`). A run during the withdrawal still finds the withdrawn row and stays unknown (`rate-card.ts:142`).
- **Shipped models never reach the snapshot.** `run` filters them out at `rate-snapshot.ts:118`.
- **In `run`, rebuild only after the write.** Read `before = ports.read()` once. Call the port only after `ports.write(merged)` has returned, and only when `merged !== null` and `newlyPriced(before, merged)` is not empty.
  - The order matters: replay reads the snapshot from the file at fold time (`packages/projector/src/spend.ts:218`, `snapshot ??= ports.snapshot()`). A rebuild before the rename would re-fold with the old prices and price nothing.
- **The new port.** Add `RatePorts.rebuild: (priced: string[]) => Promise<string>`, which resolves to a short outcome such as `spend rebuilt`. Record `priced` and the outcome on `FetchNote` as optional fields.
- **`doctor` reads them.** `ratesCheck` (`apps/cli/src/doctor.ts:1064`) puts `; priced gpt-6-astra; spend rebuilt` beside `last fetched …, ok`. A refused or failed rebuild makes the line a `warn` that names `lingtai projection rebuild spend`.
- **The port must not throw out of `run`.** `refreshRates` is documented *"Never throws"* (`rate-snapshot.ts:90`). A rebuild that throws is caught and written as an outcome on the note. It does not become `ok: false`: the snapshot write succeeded, and `ok: false` would claim *"the previous snapshot stands"* (`doctor.ts:1080`), which would be false.

**The real port is in `apps/cli/src/rates.ts`.** `realRatePorts(wanted)` at `rates.ts:56` gains the rebuild from there:

- It calls `rebuildProjection({ name: 'spend', queries: log.queries, runnerFor: () => createProjectionRunner({ projection: spendProjection }), log, error })`. The lines go to the outcome string, not to the console.
- Going through `rebuildProjection` keeps the `logPredatesHold` refusal (`projection.ts:77-81`) for free. A refusal is returned as the outcome.
- **Exit code 1 is not always a failure.** `rebuildProjection` returns 1 both when it refuses and when it finishes a few events behind because a pass appended meanwhile (`projection.ts:87-91`). Use the logged line as the outcome; don't branch on the exit code.
- **`ticket_report` does not exist in this tree**: `rg ticket_report -g '*.ts'` finds nothing. Make the list of projections a constant next to the port, holding `spend` alone. A comment says that `ticket_report` (0123) joins it when it lands.

### The decision the ticket leaves implicit: how the ceiling learns that `spend` is mid-rebuild

**The existing stall check does not catch a rebuild.** It would read a half-replayed table as current.

- `rebuild()` rewinds the checkpoint to zero, then replays (`packages/projector/src/projection.ts:225-244`).
- Every batch advances the checkpoint with a fresh `updatedAt` (`projection.ts:150-157`).
- `spendStall` treats *behind but moved in the last 60s* as healthy (`apps/cli/src/day-ceiling.ts:13-14`, *"the lag after a pass is not"*; `:55`).
- So during a replay, `dayCeilingStop` falls through to `dayCeilingPause` over a partial table. That is exactly the *"little spent today"* reading the Watch out forbids.

**So the hold is explicit, and it lives in the process doing the rebuild:**

- **What `rates.ts` exports.** `spendRebuildHold(): string | null`, backed by module state. The state is set before `rebuildProjection` is called.
- **Where the ceiling reads it.** `DayCeilingPorts` gains `rebuilding?: () => string | null`, defaulting to `spendRebuildHold`. `dayCeilingStop` asks it in the same place it asks `spendStallIn` (`day-ceiling.ts:81-88`): only when a ceiling is set. When it returns a sentence, the answer is `could not check the daily ceiling: <sentence> — taking no work`.
- **The hold lifts on a reading, not on the promise.** It lifts the first time the ceiling, after the rebuild has resolved, reads the `spend` lag as `0n` from `ports.lags`. It does not lift merely because the rebuild promise settled. This one rule covers both edges:
  - **A rebuild that threw partway.** The table is partial, the checkpoint is recent, and `spendStall` would say healthy for 60s. The hold stays up. Its sentence names `lingtai projection rebuild spend`.
  - **A rebuild that finished a few events behind.** The live projector closes the gap, and the hold lifts on the next ask.
- **In-process is enough for the claim the ticket makes.** Only a conductor-lock holder refreshes: *"One writer per machine, by construction"* (`rate-snapshot.ts:5-7`). Both callers of the ceiling are that same process: `run.ts:151,174,533` and `daemon.ts` through `pausedSentence`.
- **Other processes do not see the hold.** A `lingtai status` in another process may briefly print a low `daySpendLine` (`day-ceiling.ts:120`). It takes no work, so this is accepted. Say so in a comment rather than building a cross-process flag.

### Edges

- **A pass in flight, and shutdown or restart.**
  - A pass in flight keeps running. Only `runQueue`'s `paused` callback, which the ceiling feeds, holds new claims (0122).
  - The rebuild runs inside `run`, so `ratesSettled()` waits for it before the lock is released (`run.ts:571`, `daemon.ts:384,657`). A shutdown therefore waits for the replay. It is O(events), with roughly 50 ms per event measured on Postgres (`projection.ts:61-69`). Note this in `doc/operating.md`.
- **The daemon's own live `spend` runner is stood down for the rebuild.** `rebuild()` rewinds the checkpoint, and a live runner that commits an event meanwhile advances that checkpoint to the head before the new runner's `follow()` reads where to start; the replay would then skip history and report zero lag. Conflict-safe inserts do not protect the checkpoint. So `followSecondary` registers its `spend` runner, `holdLiveSpend` (`apps/cli/src/projector.ts`) stops it before the rebuild, and it is started again from the checkpoint the rebuild left. A `lingtai projection rebuild spend` run beside a daemon is the unguarded case, as it is today.
- **The ceiling re-checks after its read.** `dayCeilingStop` counts rebuilds begun (`spendRebuilds`) before it checks the hold and again after `dayCeilingPause` returns; if one began in between, the read is discarded and the answer is *taking no work*.
- **`doctor` reads the projection, not the note.** `ratesCheck` warns only while the `spend` lag is nonzero now; the note's outcome is the fallback where the lag cannot be read.
- **A killed process mid-rebuild.** The next start's refresh will not call the model new. The hold died with the process, and the stall check takes over after 60s of quiet. `doctor` names the rebuild. This is the ticket's *restart* edge, and it needs no code.

### Tests (unit, fake ports, no filesystem)

- **`run` with fake `read`, `write` and `table`, and a `rebuild` spy.**
  - A first row for a model calls `rebuild` once, after `write`.
  - A changed price for a known model never calls it.
  - Each of these never calls it: a withdrawn-only result, `merged === null`, and a failed fetch.
  - A rebuild that throws still produces `ok: true` and an outcome on the note.
  - Put these in `packages/conductor/unit/`, beside wherever `refreshRates` is already tested.
- **`dayCeilingStop` with `rebuilding: () => 'rebuilding spend…'`.** It answers `could not check … — taking no work` even when `rows` returns a total under the ceiling. The behaviour that lifts the hold (only once a lag of `0n` is seen) is tested on the `rates.ts` state, using a fake runner through `runnerFor`.
- **`ratesCheck` renders `priced …; spend rebuilt`.** `doctor.ts` already takes `from` as a seam.
