# #545: generate `/docs/cli/` from the definitions and the parser

## Two sources, one per field. Neither is written twice

The ticket says the page is generated "from the CLI's own command definitions". In this tree those are two objects, and each owns different fields:

- **`COMMANDS` in `apps/cli/src/commands.ts`** owns `group`, `task`, `effect`, `usage` and `examples`. Its header already makes the promise: *"One definition per command: the source for `lingtai --help`, for `lingtai <command> --help`, and for the page `doc/cli.md` is generated from"* (`commands.ts:1-4`). `help.ts:13-38` renders `--help` from it. The page has to render from the same object, or "one source" stops being true.
- **`root` in `apps/cli/src/cli.ts:1080`** owns the **flags**. In `COMMANDS` the flags exist only as prose inside `usage`. The `@effect/cli` tree is what actually parses them.

So `cli.json`'s `flags` field is read from the tree, never parsed out of the `usage` prose. The page shows the `usage` prose verbatim as "syntax and key options", because that prose is the person-facing part and it is what `--help` prints.

**How to read the tree.** `Command.getSubcommands(root)` is what `one-parser.test.ts:33` uses, but it does **not** reach a verb's options. I probed it:
- `getUsage` on what `getSubcommands(root)` returns for `ticket`, `backlog`, `env`, `projection` and `service` misses every flag their verbs take (`--all`, `--kind`, `--reason`, `--json`…). Those commands are `Command.withSubcommands` parents (`cli.ts:706,770,824,864,1070`).
- Walking `root.descriptor` (`_tag: 'Subcommands'`, with `.children`) and collecting every option node's `fullName` gets them all. For example, `backlog` yields `--all --json --no-color --kind --unheld --reason`.

Collect **options only, not `Args`**. An `Args` node carries a `name` like `project`, and a careless walk turns it into `--<project>`.

That descriptor shape is `@effect/cli` internals (0.73.2). Pin it with a test that `flags` for `backlog` contains `--kind` and `--reason`, and that `flags` for `ticket` contains `--project`. Then a library bump that changes the shape fails by name instead of quietly emptying the column.

## Where the code goes

- **`apps/cli/src/cli-doc.ts`**, all pure:
  - `cliManifest()` builds the JSON value from `COMMANDS` + `root`.
  - `renderCliPage(manifest)` turns that value into the markdown string.

  This is how "the page renders from `cli.json`" is true: the markdown is a function of the manifest value, and nothing else reaches it. It is a new file, not part of `help.ts`, because `help.ts` must import no library (`help.ts:4-6`, 0121 §8), and this file imports `cli.ts`.
- **`scripts/cli-doc.ts`** writes `doc/cli.json` and `doc/cli.md`, and nothing more. Wire it as a root `package.json` script, `"docs:cli": "node scripts/cli-doc.ts"`. It runs unbuilt (0101); `apps/site/src/lib/docs.ts:31` already relies on `node scripts/*.ts`. This is the counterpart of `scripts/the-pass.py`.
- **`apps/cli/unit/cli-doc.test.ts`**:
  - Regenerate both strings in memory and `toBe`-compare them with the committed files. The failure message names `pnpm docs:cli`.
  - Reading a committed doc from a unit test has precedent: `packages/recipe/unit/plugin-pages.test.ts` reads `doc/plugins/index.md`, and its header explains why the judgement sits beside the code.

## `doc/cli.json`'s shape

```
{ "version": 1, "commands": [ { "name", "group", "task", "effect", "usage", "examples", "flags", "json" } ] }
```

- **Order.** Commands follow `GROUPS` order, then definition order within a group. That order is already 0121 §7's table: `help.test.ts:71` holds the listing to it. Sort `flags`.
- **`json`.**
  - Its value is the `--json` document version when the tree has a `--json` anywhere under the command, verbs included, and `null` otherwise.
  - That version is hardcoded today as `version: 1` inside `jsonDocument` (`apps/cli/src/output.ts:111`). Export it as a `JSON_VERSION` constant, use it there, and read it here. Otherwise the manifest is a second place that types `1`.
  - It is one version for every command because there is one today. 0121 §5 says *"`version` belongs to that command's shape"*, so if a command ever bumps, it is that constant that splits, not this file.
- **No timestamp, commit or package version anywhere** in either file. A stamp makes the staleness test red on every commit and makes the release diff noise.
- **2-space JSON with a trailing newline.**

**The release diff is not wired by this ticket.** `release.yml:115` runs `gh release create … --generate-notes`. The checkbox is met by `cli.json` being committed, stable and diffable: `git diff <prev-tag>..<tag> -- doc/cli.json` is the diff. A step in `release.yml` cannot be checked inside a pass, because it runs on a tag. Raise it as a follow-up.

## The page leads with tasks

- **Order:** a title, one visible line, then one `##` per group, in the ADR's words, capitalised.
  - The visible line is *generated from `apps/cli/src/commands.ts` and the parser; `lingtai --help` prints the same; do not edit — `pnpm docs:cli`*. Write it as prose, not an HTML comment: nothing shows the site's renderer keeps a comment.
- **Under each group:** first a two-column table, **To… | Run**. The task comes first, and the `Run` cell links to that command's section.
- **Then one section per command**, headed `### lingtai <name>`. Plain text, no backticks: `slugify` makes the anchor `lingtai-<name>`, and `apps/site/unit/docs.test.ts:236` shows what backticks do to a slug. Each section holds:
  - the task line
  - *Reads only — takes `--json` (version N)*, or *Changes state*, with *`--json` on its verdict* when `json` is non-null
  - the `usage` lines in one fenced block
  - the `examples` in another

## Placeholders go in the definition, not in the renderer

The watch-out says ids must show a placeholder. But examples are shared with `--help` (`help.ts:35`), so rewriting them only on the page would make the two sources disagree.

- **Change the definitions in `commands.ts`:**
  - `--issue 617` → `--issue <n>`
  - `attach 2d6f1c` → `attach <runId>`
  - `a1b2c3` → `<findingId>`
  - `--if-head 53fe949` → `--if-head <sha>`

  `<n>` follows the tutorial's own `--issue <ticket-number>` style (`doc/tutorial.md:190`). Project names like `lingtai` stay: they are not the tutorial's `chapter-garden`.
- **Fix the comment** that says *"`examples` are real invocations"* (`commands.ts:12-13`) so it says ids are placeholders.
- **Add one assertion** to `help.test.ts`: no example contains `chapter-garden` or a bare run of digits or hex after `--issue`, `attach`, `--if-head` or an `accept`/`decline` verb.
- **Expect no other test to break.** `layout-624`, `migrated`, `five-commands-cli` and `verdict` contain `617`/`2d6f1c` as their own argv fixtures, not read off `COMMANDS`. Run `pnpm test` to confirm.

## A drift test that is green today

In `cli-doc.test.ts`: every `--flag` the `usage` prose names must exist in that command's tree `flags`. Allow `--help` as the one exception. The reverse is not checked: prose picks the *key* options, and the tree carries others the prose leaves out, such as `--no-color` and restart's `--reason`.

With the walk above I found no prose-only flag in any of the 30 commands. If one appears while you work, fix the prose. Do not add to an allowlist.
