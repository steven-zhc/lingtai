## 1. The runner needs three small extensions, in `setup-list.ts`

Three things `projectList` needs are not in #1527's runner. Add each one to `packages/setup/src/setup-list.ts` with a new test in `setup-list.test.ts`, and edit no existing assertion.

1. **`confirm.declined` may be a function, `string | ((ctx: C) => string)`.**
   - Two of the declined sentences name values only known partway through the walk.
     - `recipe-flow.ts:489-493`: *"`${personal}` was not made … git push origin origin/`${from}`:refs/heads/`${personal}`"*.
     - The local variant at `first-project.ts:970-975`: *"… git branch `${base}` `${source}`"*.
   - Today `confirm` is `{ declined: string }` (`setup-list.ts:70`), and `projectList(ports)` builds its descriptors before any `ctx` exists.
   - No machine descriptor uses `confirm`. The only test is `setup-list.test.ts:91-110`, which passes a string, so it still holds.
2. **A confirmation answers `yes` on `input.defaults` (the flag) only, never on the switched-on defaults.**
   - Today `setup-list.ts:269` tests the local `defaults`, and `:330` sets that once *use every default?* is answered yes.
   - That is harmless for `make-branch` and `move-landing`, which come before the switch.
   - It breaks `register`, the only confirmation after the switch:
     - `recipe-flow.ts:746` asks it of `world`, *"never `askWorld`: a terminal that accepted every default still stops to read"*.
     - Its `given` is only `flags['defaults']` (`:757`).
   - `register` applies only under the defaults. With the runner as it stands, it would always be answered without being asked, and the entry would never reach anyone.
   - With no terminal it is still refused naming `--defaults`. That already holds, through the `!input.interactive` half of `:269`.
3. **`systemDefault` may answer `{ refused }`, and the runner returns it only where the default would have been the answer.** That is where there is no flag and nothing in force.
   - This is the ticket's *"a port that fails: … never an absent value"*.
   - `defaultBranch` failing must refuse with the port's own words, *"could not read … default branch — … Pass --main <branch>"*, but only when `--main` did not answer.
   - With the runner as it is, a port failure from `systemDefault` (`setup-list.ts:252`) is an Effect failure, not a refusal.

Nothing else in the runner changes.

## 2. The context and the ports: what the ticket's list leaves out

`ProjectContext` holds the following.

- **From the ticket:**
  - `start`, the `RecipeDraft`, never `set`;
  - `buildFlags`;
  - `pending: RecipeChange[]`;
  - `view`;
  - `answers`;
  - `ports`.
- **Added:**
  - `flags`: the same object as `input.flags`. `register.applies` needs `--land` and `--build`, and `login.fixed` needs `--login`. `applies` and `fixed` do not receive flags (`setup-list.ts:64-66`).
  - `kept`: the constant from `doc/design/1525.md` §4. A `write` that refuses needs it, and `write` sees only `ctx`.
  - `log`: lines that print today whether or not there is a terminal. Examples:
    - `whyMissing` for each signed-out runtime (`agents.ts:141-143`);
    - *"the reviewer runs the writer's runtime …"* (`agents.ts:294`);
    - the no-checkout line (`setup-build.ts:301-303`);
    - `SANDBOX_OFF_LINE`.
    A line that prints only where a prompt is drawn stays in the asker.

`ProjectPorts`, beyond the ticket's list. Each of these is read by today's code and has no other route into `@lingtai/setup`. All are Effects.

- **`proposal?: Proposal`.** `askRecipeEffect` takes the first-run defaults for sandbox, detection and kinds from it (`recipe-flow.ts:580`, `:614`, `:666`). `doc/design/1525.md` §4 keeps `proposeSetup` before the first entry, so its result arrives as a port. When it is absent, `sandbox` does not apply, as at `:580`. That makes the ticket's `sandboxHost` this port's `sandbox` field, not a separate port.
- **`checkout: string | null`.** `move-landing.applies` compares this checkout with the recipe's `repo.remote` (`first-project.ts:883-889`). `local: boolean` cannot say which checkout this is.
- **`codexText: Effect<boolean>`.** On a first run, `discuss.agent: codex` is written when claude-code is not signed in (`recipe-flow.ts:555-566`). That write belongs to `writer.write` on a first run. Without this port it would be lost when #1525 switches over. A read that throws answers `false`, as `:561-563` does.
- **`onPath: (tool) => Effect<boolean>`.** `printFound` (`setup-build.ts:219`) prints the detected toolchain before the install question, at a terminal and without one. Today `toolOnPath` returns a promise (`recipe-flow.ts:64`).

`packages/setup` stands at `{ "async": 0, "run": 0 }` in `effect-ratchet.baseline.json:11`. So no port is a promise, and nothing in `project-list.ts` calls `Effect.run*`.

## 3. The view

Put `projectView(start, pending)` in `packages/project/src/draft.ts`, beside `keyIn` (`:27`). That file already owns `yaml` and `RecipeDraft`.

- **`view.get(path)`** is `keyIn` over the starting text with `pending` overlaid, applied in order. Use the same `deleteIn` / `replace` / `setIn` loop `editRecipe` runs (`packages/recipe/src/emit.ts:178-182`), and **not** `editedText`.
  - `editedText` → `editRecipe` runs `Recipe.parse` over the whole document (`emit.ts:193`). Whether that parse accepts a first-run prefix with no `source.kinds` yet is not settled by anything in this worktree.
  - A view that throws halfway through a first run would silently turn every later `get` into an absent value.
- **`view.resolved()`** is `widenStepsIfNeeded` + `editedText` + `resolveSource`, the three calls at `draft.ts:66-71`. Every throw becomes `null`.
- **Later changes win.** `pending` is applied in order, so a later change at the same path replaces an earlier one. The trial relies on that (§4), so pin it in a test of the view.

`draft.set` appears nowhere in `packages/setup/src/project-list.ts`. Add a test that walks the whole list with a `start` whose `set` dies, and that `start.changes()` is empty afterwards. That is the ticket's *pending is never applied*.

## 4. The entries: only the decisions that are not obvious

The list has **25 descriptors**: design §4 numbers 22, and its item 21 is four entries. `PROJECT_QUESTION_IDS` lists all 25, and the order test asserts 25 ids.

- **`where` is `fixed` from the ports. It takes no flags and has no asker.**
  - The ports exist only once it is answered: the reader and the default branch depend on the repository. `doc/design/1525.md` §4 puts the reader and `proposeSetup` *before the first entry*.
  - So `where.fixed` answers `ports.local ? 'local' : 'github'`, and its `write` appends nothing. The caller's seeds are `pending`'s first entries (1525 §4).
  - The refusal *"the project needs an answer: pass --project github, or --project local"* stays in `askProjectKind` (`first-project.ts:392-401`), which this ticket does not touch.
  - Its `flags` is `[]`. `--local`, `--github` and `--project` are not in `recipeOptions` (`wizard-options.ts:15-46`), and the equality test in §5 would otherwise fail.
- **`login.fixed(ctx, flag)` returns `null` whenever `flag !== null`.**
  - The runner calls `fixed` before it uses a flag (`setup-list.ts:193-199`). Today the flag wins: `recipe-flow.ts:399`, `given ?? known…`.
  - `login` applies only in team mode and not locally. The local team path asks no login (`first-project.ts:725-731`).
- **`branch.write` records facts for the entries after it, in `ctx.answers`:**
  - whether the branch exists (`ports.branchExists`; `'unreadable'` refuses with `recipe-flow.ts:452-455`'s words);
  - the branch it is cut from (the old personal branch where that exists, `:465-473`);
  - `commitsOnlyIn` for the move.
  
  `make-branch.applies` reads those facts. Do not record them in `validate`: the runner may call it more than once, and the local `validate` that decides `source` today (`first-project.ts:732-745`) says so itself (*"Decides only: `validate` can run again"*).
  - Locally, the default is `currentBase ?? LINGTAI_BASE` (`first-project.ts:729`, `:750-751`). `LINGTAI_BASE` is already in `@lingtai/setup`, at `setup-answers.ts:42`.
  - On GitHub in team mode, the default is `defaultPersonalBranch(login, ports.hostname)` (`personal-branch.ts:30`).
- **`writer` and `writer-model`, `reviewer` and `reviewer-model`, are separate writes into one action.**
  - `writer.write` appends what `agents.ts:316-343` appends for the agent alone. That is `runtime.agent`, `unboundedTurnsChange` and the implement action, plus the first-run `discuss.agent` from §2.
  - `writer-model.write` reads the implement action back through `view.get` and edits its `model` in place.
  - The reviewer pair works the same way.
  - A writer with no runtime signed in is refused with `noRuntimesSignedInRefusal` (`agents.ts:144-146`) from `writer.inForce`, as `{ fault, fatal: true }`. The runner returns that text unchanged (`setup-list.ts:220`).
- **`leftoverRefusal` runs in `reviewer.write`.** It skips `followedJudgeIndex(startProposed, oldWriter)` (`answers.ts:103`). That is already the predicate design §5 asks for, so write no new one.
  - The old writer is always the **starting** recipe's.
  - `findings-judge.derive` returns the new writer.
  - Its `write` appends `followWriterJudgeChanges(oldWriter, newWriter, view.get(['steps','proposed']))` (`answers.ts:119`). This is one rule on both shapes: with `oldWriter === null` it falls through to `findingsJudgeChanges`.
- **`install`, `checks` and `trial`.**
  - Move `resolvedRunActions`, `namedFromTyped` and `mergeRunActions` (`setup-build.ts:104`, `:187`, `:202`, all private and pure) into `@lingtai/setup`, and import them back into `setup-build.ts`.
  - Move the no-checkout sentence (`:302`) there too. `checks.write` logs it when the answer is non-empty and `ports.trial` is absent. That is exactly where it prints today: straight after the build question, before anything else.
  - The `trial` port is `(at: { text, install, checks, given, kept }) => Effect<{ install, checks, trial: TrialOutcome } | { refused }>`. Its body, in `apps/cli`, is the loop at `setup-build.ts:497-521`, exported as one function that `askInstallAndBuildEffect` also calls. On *edit* it re-asks through the same install and checks pieces (§6).
  - `trial.write` appends the `steps.prepared` and `steps.build` changes for what the loop returned. Under §3's later-wins rule, those replace the install and checks entries' own changes.
  - `trial.systemDefault` is `'no'` whenever `mode.defaults || !mode.interactive`.
- **`register.applies`** needs the two facts `summariseRecipe` computes (`recipe-flow.ts:196`, `:207`) over `view.resolved()`. `summariseRecipe` is pure, so move it into `@lingtai/setup` and re-export it from `recipe-flow.ts`. #1524's card reads it too, so there must be one copy.
  - `register` applies under `answers.defaults === 'yes'`. The runner calls the switch's `write` with `'yes'` both for `--defaults` and for a typed yes (`setup-list.ts:272-274`).
- **`landing` and the limits compare against `view.resolved()`.** Where that is still `null` on a first run, the answer is written, as design §3 says a first run does. `askLanding` calls `setRecipeOrRefuse` (`landing.ts:193`), so the entry's `write` is new code over `landingChanges`, `holdRemovalChanges` and `landOnBranchChanges`, not a call into `askLanding`.

## 5. `PROJECT_FLAGS`, and where adding `defaults` breaks `add` today

Each `recipeOptions` key is owned by exactly one entry:

| Flag | Entry |
|---|---|
| `main`, `personal` | `branch` |
| `rounds`, `refusal-fixes` | `refusal-fixes` (it refuses `--rounds` with `ROUNDS_RETIRED`) |
| `check-build` | `trial` |
| `land` | `landing` |
| `build` | `checks` (it reads `ctx.buildFlags`) |
| `defaults` | `defaults` |
| every other key | the entry of the same name |

The equality test compares sets.

**`defaults` reaches two consumers the ticket does not name.** `PROJECT_FLAGS` (`wizard-options.ts:52-54`) has three readers:

- `init.ts:628`, which the ticket covers.
- `add-github.ts:606-607`, which runs `delete flags[name]`.
- `first-project.ts:506`, the `deferRecipeFlags` filter.

The last two hand `flags` on to `runGithubBranch`, which ends in `askTokenFor(machine, options, flags, recipe)` (`first-project.ts:1773`). `askTokenFor` reads `defaults: flags['defaults'] !== undefined` (`machine-askers.ts`, `askTokenFor`).

If either of those two removes `defaults`, `lingtai add owner/repo --defaults` at a terminal starts asking the Claude token question, and that is a change to today's `add`. So:

- `wizard-options.ts` exports `HANDED_OFF_FLAGS = PROJECT_FLAGS.filter((n) => n !== 'defaults')`. Its comment says it is today's set and why.
- Both hand-off sites read `HANDED_OFF_FLAGS`.
- `init.ts:628` adds `defaults` to its exclusions, as 1525 §2 says.
- `apps/cli/unit/project-flags.test.ts` also asserts that `HANDED_OFF_FLAGS` is the old literal set. #1525 deletes both sites and the constant.

`wizard-options.ts` imports `@lingtai/setup`'s index. Its importers are `cli.ts`, `init.ts`, `add-github.ts` and `first-project.ts`, all Node-side, so no client graph is affected.

## 6. Askers: what "split at the seams" means in code

The exported piece is the `questionEffect` call with its words, taking:

- `given`;
- `current`;
- `fallback` / `detected`;
- `validate`;
- `kept`;
- whatever else the words need (offer lists, the base in the trial prompt).

`askMode`, `askLogin` and `askPersonal` (`team.ts:35`, `:53`, `:68`) already have this shape, so they *already fit* and are used as they are. The rest get the same shape:

- `askModel`, exported;
- the writer and reviewer questions;
- the two sandbox questions;
- the four limits;
- the tickets and kinds questions;
- the landing choice;
- install, the build loop and the trial yes/no;
- the move-landing prompt (`first-project.ts:883-889`), which is a raw `world.ask`, not `questionEffect`.

The old `ask*` calls the pieces with `given` from flags and its own `validate`. Each validate is a #1528 check, so the words exist once.

The asker in `project-askers.ts` calls each piece with these values:

| Argument | Value |
|---|---|
| `given` | `null` |
| `validate` | `d.question.validate` |
| `kept` | `d.kept` |
| `current` | `d.default` where `d.inForce !== null` |
| `fallback` | `d.default` otherwise |

The prompt's bracket is `current ?? detected ?? fallback` (`question.ts:161`), so the line drawn is the same either way.

The offer lists the writer and reviewer show must match what their validates accept. Compute them with one helper in `@lingtai/setup`, the filter at `agents.ts:139` (`isImplementOnlyAgent`). The descriptor and the asker both call it.

`PROJECT_ASKERS` is `Record<Exclude<ProjectQuestionId, 'where' | 'findings-judge'>, Asker<ProjectContext>>`. The comment says why those two are left out: `where` is always `fixed`, and the judge is `derive`.

## 7. Tests, and what cannot be checked here

- **The first-run walk must resolve.** It needs the caller's seeds in `ctx.pending` before the walk: `env.plantAt` and `steps.end` (1525 §4). `plantAt` has no schema default (`recipe.ts:3307`, `plantAt: z.string()`), so an empty draft without seeds can never resolve. `source.tickets` has no schema default either (`recipe-flow.ts:657-664`). So `tickets.write` writes on a first run even when the answer equals the default.
- **Per-entry tests** go through one helper: `walk(ports, { flags, interactive, askers, start })` → `{ result, ctx }`. It runs the whole list, because later entries read earlier answers. Each test asserts on its own entry's `Entry`, on what it adds to `pending`, and on `ctx.log`.
- **The unchanged old tests** (`agents.test.ts`, `landing.test.ts`, `setup-build.test.ts`, `source.test.ts`, `team.test.ts`, `init.test.ts`, `init-golden.test.ts`) are the check that the split did not move a word. Run them before touching `project-list.ts`, once the pieces are exported.
- **Integration.** Nothing in this slice reaches git, the network or a process. Everything is checked by `pnpm typecheck` and `HOME=/nonexistent pnpm test`, and no claim here depends on the 803-second integration run.
