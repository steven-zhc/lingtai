## 1. The askers are built from a world, so the name is a function

An asker draws on a `QuestionWorld`, so it can't be a module constant. The twin already builds its askers inside `machineSetup(world, …)`: `const askers: Record<MachineQuestionId, Asker> = {…}` at `machine-askers.ts:243`. Do the same here:

```ts
export type ProjectAskers = Record<Exclude<ProjectQuestionId, 'where' | 'findings-judge'>, Asker<ProjectContext>>
export function projectAskers(world: QuestionWorld, opts: { command: string }): ProjectAskers
```

The ticket's `PROJECT_ASKERS` is this record. Its "missing asker fails `tsc`" claim is carried by the annotated return type. The `@ts-expect-error` test types a partial object literal as `ProjectAskers`. The comment on the type says why those two ids are left out: `where` is always `fixed`, with *"Always fixed: … it takes no flag and has no asker"* at `project-list.ts:522`, and `findings-judge` is `derive` at `project-list.ts:857`.

## 3. The default goes in through the piece's own fallback

The ticket's table applies to the pieces that take `current`/`fallback`:

- `current: d.default` where `d.inForce !== null`;
- otherwise `fallback: d.default ?? undefined`.

Pass `undefined` rather than `null` or `''`. The runner hands `default: null` for an entry with no `systemDefault`: the `defaults` switch, and the three confirmations (`setup-list.ts:319`, `default: fallback`). The pieces already carry today's bracket as `at.fallback ?? 'yes'` (`setup-build.ts:235`, `sandbox-step.ts` `fallback: at.fallback ?? 'on'`). So passing `undefined` keeps the bracket today's, and passing `''` would erase it. The extracted confirmations take no default at all and keep `fallback: 'yes'` inside, as their inline forms have it.

The confirmations always pass `given: null`. The runner answers a confirmation under `--defaults` itself (`setup-list.ts:283-285`) and never reaches the asker.

## 5. The trial port: the entry has already asked, so the loop must not ask again

The `trial` entry asks *yes/no* through its asker. Its `write` then calls `ports.trial` on yes (`project-list.ts:1121-1124` and `:1136-1150`). `runTrialLoop`'s first `tryTheBuild` asks `askTrial` again, because `asked` starts `true` (`setup-build.ts:385`, `:283-291`). Called unchanged, the port would draw the trial prompt twice.

Fix it in the piece. Add `askFirst: boolean` to `TrialLoopInput`, which seeds only the first round's `asked`:

- `askInstallAndBuildEffect` passes `true` (`setup-build.ts:485`).
- `liveTrialPort` passes `false`.

The re-ask after an *edit* still happens, because `asked` resets per outer round. That is today's behaviour. Do not fake it with `given.check: 'yes'`: that would also suppress the re-ask after an edit, which today draws.

The port cannot see `ctx`, and it needs the cut-from branch for both the run and the re-ask's base. Add `make: { name: string; from: string } | null` to `ProjectTrialAt`, and pass `ctx.answers.make ?? null` in the trial entry's `write`. That type and that call are what `project-list.ts:155` and `:161` hand to this ticket: *"#1529 retypes the port body"*, *"Its live body is #1529's"*. While there, make `setup-build.ts:69`'s `TrialOutcome` an import of `project-list.ts:156`'s, so there is one union, not two.

`liveTrialPort(world, at: { project, owner, repo, remote?, token?, home? })` does the following:

- builds `liveTrialBuild({…at, base: <the §4 base>, draft: <view with the make substitution> })`;
- passes `recipeFile: recipePath(project, home)`, `given: at.given` and `kept: at.kept`;
- maps `build` to `checks` on the way out.

The ticket names it `liveTrialPort(world)`, but the `TrialAt` fields have to come from #1525's caller.

**`again` cannot go through the record as it stands.** An asker takes a `Decided<ProjectContext>`, and the port has no `ctx` and no descriptor. Split the `install` and `checks` askers into two ctx-free functions in this file:

- `installAsk(world, {current, detected, fallback?, validate, kept})`;
- `checksAsk(world, {list, why, kept})`.

The record's entries call these with `d` and detection. `again.install` calls `installAsk` with `current: previous ?? 'none', detected: null` (today's `setup-build.ts:157-162`), and `validate` is `installRefusal` from `project-checks.ts`. The *edit* path is therefore the same code as the asker's, which is what the ticket's "re-asking through the same install and checks askers" needs.

## 6. The test: answering Enter everywhere would test almost nothing

`acceptingDefaults` answers `''` **without calling the world's `ask`** (`question.ts:132-141`). The runner answers every non-confirmation itself once the switch is yes (`setup-list.ts:301`). Enter is `yes` at *use every default?* (`recipe-flow.ts:481`), so a pure-Enter walk records mode, login, branch, make-branch, defaults and register, and nothing between them, on both sides.

Run each case twice:

- **(a)** Enter everywhere;
- **(b)** `no` at *use every default?* and Enter at everything else. Only this run reaches the agent, sandbox, install, checks, trial, tickets, landing and limit askers.

The oracle is `askRecipeEffect` over `Effect.provideService(ProjectFiles, mapFiles(…))`, as `recipe-flow.test.ts:20-22` does. That is a unit test by 0060 §1, so no filesystem is involved. The fake `QuestionWorld` records `(prompt, opts.choices, opts.defaultValue)` and nothing else. `kept` is the runner's `input.kept`, and #1525 decides it, so it is not part of the comparison. Hand both sides one fake trial with one report, and a fixed `knownLogin`.

**Local.** `askRecipeEffect` skips mode and the base when `at.local` (`recipe-flow.ts:283`). The local *mode / branch / make-branch / move-landing* prompts belong to `first-project.ts`. So the local comparison against `askRecipeEffect` starts at `defaults`. The four before it are held by the grep in Done-when and by the pieces being the ones `first-project.ts` calls.

The list may draw a prompt today's flow never drew. One example: `make-branch` applies to a local *solo* rerun that names a new base (`project-list.ts:728-731`, from `80b971477`), and today that branch is made without asking (`first-project.ts:992-994`). The *edit* test drives the fake trial red, then answers `edit`. It asserts:

## 7. Edges the ticket leaves open, decided

- **Ctrl+C at move-landing:** `askMoveLanding` maps `null` to `yes` (`first-project.ts:182`). At a terminal, Ctrl+C throws `PromptRefused` (`prompt.ts:37-39`) or exits 130 (`prompt.ts:115`), and never returns `null`. The runner never calls an asker without a terminal, so `null → yes` is unreachable here. Map `'yes' | 'no'` to `{ answer }` and nothing else.
- **A detection read that fails inside an asker:** there is nothing to say, so pass `detected: null, why: []`. The entry's `inForce` has already refused a failed read by name (`project-list.ts:1050-1052`), before any asker runs.
- **The ratchet:** no new `async` and no `Effect.run*`. The fake world's `ask` in the test is a promise, but that is test code, which the ratchet does not count. That holds as long as the helper uses `Effect.runPromise` only inside a test file.
- **Integration:** nothing here reaches git, a process or the network. `pnpm typecheck` and `HOME=/nonexistent pnpm test` are the whole check. The old pieces' tests listed in `doc/design/1529.md` §7 (`agents.test.ts`, `setup-build.test.ts`, `team.test.ts`, `recipe-flow.test.ts`, `first-project.test.ts`, …) must stay green unchanged across the extractions in §2. That is the check that no word moved.
