# #1251 design note: AlreadyDone → check → satisfied

The ticket gives the five pieces. This note covers where they join the walk, and the decisions the ticket leaves open. Line numbers are as of `5f474b5a`.

## 1. The declaration

**The Done-when list is parsed in one place.** Nothing in the code parses a `## Done when` section today. Only prompts and prose mention it (`packages/conductor/src/triage.ts:165`, `packages/domain/src/split.ts:219`). Add a pure `doneWhenItems(body: string): string[] | null` in `packages/domain/src`.
- An item is a top-level list line (`- `, `* `, `1. `) between `## Done when` and the next `## ` heading, with any `[ ]` or `[x]` removed.
- A nested line belongs to its parent and is never an item of its own.
- Whitespace is collapsed before comparing, and nothing else is normalised.
- It returns `null` when the section is absent or holds no items. The ticket says that case is `AgentFailed`.

Both the implement decision and the check call this function, so they cannot disagree about what the items are.

**The body is the claimed body, never a fresh fetch.** That is `TicketClaimed.body`, or `TicketContinued.body` on a continuation (`events.ts:251`, `:275`). It is the body the implement prompt was built from. **`bodyVersion` is the ticket-stream version of that event.** No "body version" exists anywhere today, and that event carries the body word for word, so a reader can follow the number. If the version is not already in hand at the decision, read the stream's last `TicketClaimed`/`TicketContinued` for this `runId`.

**`decideImplementOutcome`** (`packages/domain/src/implement-outcome.ts:94`):
- `DecideInput` gains `doneWhen: readonly string[] | null` and `offersAlreadyDone: boolean`.
- `Block`, `Declared` and the stored `ImplementOutcome` each gain `AlreadyDone`. The stored one is `{ items: {item, evidence}[], baseSha, bodyVersion }`, kept lenient for the reason at `:13`.
- The decision returns `{items}`. `conduct.ts` adds `baseSha` and `bodyVersion` before storing, so the function stays pure.

The rows, in order:
- head moved → `Implemented`;
- `doneWhen === null` → `AgentFailed`;
- a body item with no answer, or with empty evidence → `AgentFailed`, with a `why` that quotes the first unanswered item word for word, so the redo is told exactly what was missing;
- otherwise → `AlreadyDone`.

An `item` the agent sent that matches no body item is ignored, not refused. Only the body's own items count.

**Which call sites may accept it.** Only the first implement call sets `offersAlreadyDone: true` (`conduct.ts:5105`). The abnormal-ending call (`:5049`) and the fix and conflict-round call (`:5400`) pass `false`. There, `AlreadyDone` decides `AgentFailed` with the why *AlreadyDone answers the ticket, not a finding; declare Disputed*.
- **Why:** after a refused check, the fixer is handed the unmet items as findings. A fixer that thinks an item is met already has `Disputed` to say so. Letting it say `AlreadyDone` instead would loop check → refuse → check, a round each time, without the dispute ever reaching the router as one.
- `fix.ts:610-643` (the fixer's brief) therefore does not offer `AlreadyDone`. Only `prompts/ticket.md` does, and its interim *also what to declare when the work is already on the base branch* (`prompts/ticket.md:68-69`) goes.

**What the step shows.** `verdictOf` gives a commit-yielding `AlreadyDone` the verdict `passed` (`packages/domain/src/attempt.ts:349-359`): the step did its job. `commitFellShort` (`packages/domain/src/attempt-next.ts:252`) gains the case `AlreadyDone` → `Propose { AlreadyDone{ items, baseSha, bodyVersion } }`.

## 2. The route: a new next, chosen by rule before any judge

The router has no move to `review` today:
- `CandidateNext` is `FixRound | MergeBase | LandAgain | RerunStep | Requeued | HandToPerson` (`packages/domain/src/routing.ts:47-54`).
- `RerunStep` spends `stepRedos` (`attempt.ts:637-638`) and re-runs the last visit, so reusing it is wrong.

**Add `CheckDone { baseSha, items, bodyVersion }` to `AttemptNext` and `CandidateNext`**, with candidate id `check-done`. It spends nothing and has no counter in the `PassRouted` reduction (`attempt.ts:625-655`). `destinationOf` maps it to `'review'` (`packages/conductor/src/proposed-route.ts:107-120`).

**The items ride on the next itself, not only in the walk's memory.** `PassRouted` stores the next (`events.ts:1619`). A process that dies during the check can therefore rebuild check mode from the log, which is what the ticket's *restart redoes `review`* edge needs.

**`offerFor`** (`packages/domain/src/failure/respond.ts:700`) gives `AlreadyDone` `check-done` plus the usual `hand-to-person`. It offers no fix round and no restart: there is no criterion yet.

**The built-in.** Add `already-done` to `JudgeWhen` (`packages/domain/src/proposal.ts:27`) and a built-in `check-the-evidence`, following `merge-the-base` exactly:
- `BUILT_IN_FOR['already-done'] = 'check-the-evidence'` (`respond.ts:868`);
- `MECHANICAL_WANTS['check-the-evidence'] = 'review'` (`proposed-route.ts:91`);
- a `BUILT_IN` cell answering `'human'` as the floor (`packages/conductor/src/judge.ts:453`). Its comment says why: this vocabulary has no `review`, so the live answer is `MECHANICAL_WANTS`.

**But the walk selects `check-done` by rule, before `replyFor` or any judge.** It is a new branch in the same chain as `land-again` and `ask-again` (`packages/conductor/src/run-attempt.ts:1810-1860`), recorded as a `Selected` reply, so `routeMove`'s replay accepts it. A recipe that declares `judge … when: already-done` resolves, but the judge is never asked, the same way a `merge-refused` judge is never paid while `land-again` is on offer (#1221).

## 3. Check mode in the walk

On `CheckDone`, the walk:
- sets `checking = { baseSha, items, bodyVersion, doneWhen }`;
- sets `lapStart = steps.length` and `at = 'review'`. `build` is skipped.
- `contextFor()` puts `checking` on the context as `alreadyDone`. An `ask-again` redo of an unreadable check reuses `lastVisit.context` (`run-attempt.ts:2016-2020`) and so keeps check mode.

After the `review` visit, while `checking !== null`:
- **Passed** → the walk ends. It does not `Advance` to `proposed` or `merge`.
  - It needs to know whether this is a split parent, so `runAttempt` takes a `splitParent: boolean` option, computed by `conduct.ts` from `state.split !== null`.
  - Split parent → a new `AttemptEnd` variant `Satisfied { baseSha, bodyVersion, items }`.
  - Otherwise → `WaitOnPerson { SatisfiedUnconfirmed { run, baseSha, bodyVersion, items, reading } }`, where `reading` is the reviewer's summary (`reviewSummaryOf`). That summary is "the reviewer's per-item reading", so no new parser is needed.
  - Deciding this inside the walk keeps `AttemptOver.end` true, and keeps `outcomeOf` total (`run-attempt.ts:1379`): `Satisfied` → `'satisfied'`, and the wait stays `'blocked'` through the existing `holdTicketEffect` path.
- **`ReviewFindings`** → selected by rule: `fix-lines`, i.e. `FixRefusal{to:'implement'}`, placed before any judge. A judge declared at `findings` is never dispatched, and that is the ticket's test. If `fix-lines` is unavailable because `refusalFixes` is spent, the offer's own floor applies: a person.
  - Taking it clears `checking`. The existing `recheck = findingsIn(...)` (`run-attempt.ts:2045`) then carries the unmet items into the next ordinary review, which is what should happen.
- **`ReviewEmpty`** (refused with no findings) → there is no criterion, so the offer's floor applies: a person. It is not `fixRefusal`.
- **`AnswerUnreadable`** → the existing `ask-again` rule.

Two variables need care:
- Leave `reviewedSha` alone during a check. Otherwise the fix round's ordinary review would take a delta against a check that read no diff (`agent-action.ts:944`).
- Leave `landedOnBase` alone as well.

## 4. Check mode in the action

`ActionContext` gains `alreadyDone?: { baseSha, items, doneWhen }` beside `recheck` and `landedOnBase` (`packages/actions/src/action.ts:580-600`). In `makeAgentAction.run` (`packages/actions/src/agent-action.ts:875`), branch **before** `deps.diff()`. That is the trap the ticket names at `:880-885`.

The branch:
- reads no diff and no issue;
- builds a check prompt from three things: the Done-when items as written, the agent's evidence for each, and the sha;
- dispatches under its own session id `${runId}:check:${spec.name}:${baseSha.slice(0,7)}`, never the review's id (the reasoning at `:929-935`);
- parses the answer with the existing `parseFindings` (`:804`).

The prompt says:
- Judge each item **at `baseSha`** (`git show <sha>:<path>`, `git grep <pat> <sha>`), not at the checked-out head.
- Each unmet item is one blocking finding, with the item word for word as its `failureScenario`.

**Why `baseSha` and not the head.** The head can carry commits that will never land: `design`'s note (`conduct.ts:4289-4295`), or WIP kept from an earlier round. Evidence that only holds because of those commits is not "already on the base". An item met only by such a commit is refused, and the fix round lands it.

`refusedAbout` is ignored in check mode, because the route is fixed by rule.

**Other actions at `review`.** A `run:` (process) action there runs unchanged against the head. Every agent action at `review` runs in check mode. A tree that is the base plus at most a note gives a process check nothing new to fail on.

## 5. The ending

**Split parent, in `conduct.ts`.** Beside the `landed` block at `:5964`, add `satisfyTicketEffect(ticketId, { baseSha, bodyVersion, items, endPlan })` in `packages/conductor/src/ticket/commands.ts`. It appends `TicketSatisfied` and the end plan in one append, as `landTicketEffect` does at `:711-724`. Then `released = true`, and GitHub is told the same way a landing is.

**Non-split.** Add `confirmSatisfiedEffect` in `commands.ts`, shaped like `closeTicketEffect` (`:641-667`). The data for `TicketSatisfied` comes from the wait reason alone, which is why `SatisfiedUnconfirmed` carries `bodyVersion`. It does this:
- runs `resolveWaitTransition` with `ConfirmSatisfied` (`packages/domain/src/ticket.ts:1014`);
- loads the recipe's `end` actions;
- calls `resolveEndActions(events, end, 'satisfied')`;
- appends `WaitResolved{ConfirmSatisfied}`, `TicketSatisfied` and `EndActionsResolved` in one append.

`ConfirmSatisfied` starts no continuation: every switch in `wait.ts` (`continuationOf`, `grantCriterion`, `:600`, `:733`) gets a terminal cell for it. No CLI verb or board button is added here (that is #1252). Until then the wait can still be answered with `Close` or `StartNewAttempt`; say so in the PR.

**Terminal state.**
- `TicketLifecycle` gains `{ status: 'satisfied'; baseSha; bodyVersion }` (`ticket.ts:175-182`).
- Claim already refuses anything that is not `backlog` (`ticket.ts:816`), so `satisfied` needs no claim code, only a test.
- `closeChecks` gains a `satisfied` decline (`ticket.ts:1197`).
- `satisfyTicketEffect` and `confirmSatisfiedEffect` refuse from any terminal, which covers the ticket's *a second `TicketSatisfied`* edge.

**Enums that gain `satisfied`.**
- `TerminalOutcome` (`packages/conductor/src/end-step.ts:63`)
- `EndActionsResolved.outcome` (`events.ts:1266`)
- recipe `WHEN` — **`packages/recipe/src/recipe.ts:118`, not `:109` as the ticket says**

`refs:` stays `when: landed` only, so a satisfied ticket's arms are never deleted by it.

**Docs and paste.**
- Add a `when: satisfied / close: true` entry to `doc/examples/lingtai-recipe.yml` beside `:215`.
- The conducting machine's paste stays the operator's, after the restart.

## Edges the ticket did not settle

- **A design note or kept WIP on the head:** it is dropped. A satisfied ending lands nothing, and the check judged `baseSha` (section 4).
- **A continuation's base:** `baseSha` is `continuation?.diffBaseSha ?? worktree.baseSha` (`baseShaOr`, `conduct.ts:2342`). It is never bare `worktree.baseSha`, which on a continuation is the prior head (`:2334`).
- **A daemon running the old code meets `PassRouted{CheckDone}` or `TicketSatisfied`:** the schema refuses it. Every stored shape here is additive, and #1253's bar is the writer's.
- **Split parents today never reach implement:** claim answers `split-done` (`ticket.ts:817-831`) until #1263. The split branch is therefore tested at unit level with `state.split` set, and is not reachable live yet.

## Checks

- **Pure units:**
  - the decision rows, including the fix-round row;
  - `doneWhenItems`;
  - `offerFor` for `AlreadyDone`;
  - the transitions: `ConfirmSatisfied`'s allowed list, the claim and close refusals;
  - `resolveEndActions(…, 'satisfied')`.
- **The walk:** the tests in `conductor/unit/conduct-a-whole-pass.test.ts` with fake ports and a fake runtime that answers check findings. That is where *the agent was dispatched on an empty diff* and *no judge was dispatched where one is declared at `findings`* are asserted.
- **Integration only:** GitHub actually closing the issue at `end`. The unit stand-in is the `EndActionsResolved{satisfied, actions:[close]}` that the satisfy append carries.
- **Effect ratchet:** every new IO function (`satisfyTicketEffect`, `confirmSatisfiedEffect`, the check dispatch) is an `Effect`. Never raise `effect-ratchet.baseline.json`.

No ADR is contradicted: 0108 §18 and §21 already describe this.
