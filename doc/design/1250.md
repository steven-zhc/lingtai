## The trap the ticket does not name: `StepEnded` stores `Completed{head, question}`

`StepEnded.outcome` is a `StepOutcome` (`events.ts:1439`). The commit result lives inside it as `Completed{head, question}` (`action.ts:172`). Renaming the field in place makes every stored `implement` `StepEnded` undecodable, which is the same failure the ticket's Watch out row warns about for `JudgeWhen`.

**Bump the shape and upcast old rows, per the rule at `events.ts:18`: *"Bump `SCHEMA_VER` for a type and add an upcaster rather than changing a payload in place"*.**

- Add `StepEnded: 2` to `BUMPED` (`events.ts:2891`), with an upcaster in `upcast.ts`.
- The upcaster rewrites each `yields: 'commit'` `Completed` as follows:

| Stored row | Becomes |
|---|---|
| `question !== null` | `outcome: Unclear{questions: [], said: question}` |
| `head !== null`, `question === null` | `outcome: Implemented` |
| `head === null`, `question === null`, `plugin === 'agent'`, round 0 | `outcome: AgentFailed` |
| `head === null`, `question === null`, `plugin === 'agent'`, round > 0 | `outcome: Disputed{findings: []}` |
| any other plugin | `outcome: null` |

- **Make the stored schema lenient.** `Unclear.questions` is `TriageQuestion[]` with no minimum, plus an optional `said`. Only the writer uses `AskedQuestions` (`triage.ts:81`). This is the same writer-only bar #1253 set at `triage.ts:70-73`: *"nothing on the log may become unreadable because of it"*.
- **This mapping is what keeps the projections equal before and after a rebuild.**
  - `attempt.ts:341-347` derives `asked`, `passed` and `did-not-finish` from this result. Rewrite it so that `Unclear` → `asked`, `Implemented` → `passed`, and `AgentFailed` or `Disputed` → `did-not-finish`.
  - `outcome: null` keeps today's rule: `head !== null ? passed : did-not-finish`.
  - `questionOf` (`attempt.ts:419`) reads `Unclear`'s `said`, or else its questions' text.
- **Unit-level stand-in for "rebuild every projection and they agree":** fold `packages/domain/test/histories.ts` before and after the upcaster, and assert that each attempt gets the same status. Two fixtures carry the old shape: `commitCompletedNoHead` at `:155-165` and the `head: 'sha-…'` rows. The real rebuild runs against Postgres, which is integration-only and out of reach inside a pass.

## `outcome` is nullable because the agent is not the only `commit` yielder

`makeKeptRunAction` also yields `commit` (`kept-run-action.ts:83`). A `run:` written after the agent at `implement` produces `Completed{head: null}` when it has nothing to keep. The `commitCompletedNoHead` fixture is that case, and *"it still clears"*.

- The live schema is `Completed{head: string | null, outcome: ImplementOutcome | null}`. It is `null` for anything but the agent.
- `cleared` (`action.ts:304-307`): a `Completed` clears when `outcome` is `null` or `Implemented`.

## Where `nextOf` decides it: through `cleared`, not a new branch

Delete the `changedNothing` branch at `attempt-next.ts:187-193` outright.

- **`Implemented`:**
  - `work-action` answers `verdict: 'passed'`, so the pipeline continues to any kept `run:` after the agent.
  - That action decides the step and clears, and `nextOf` reaches `Advance build` as it does today.
  - This is the same reason the agent's own result must not be the deciding action: the head a formatter moves afterwards is not the agent's receipt.
- **`AgentFailed`, `Disputed` and `Unclear`:**
  - These answer `did-not-finish`, so the pipeline stops at the agent. `step-outcome.ts:33-40` already handles a trailing `NotReached`.
  - The agent is then `decidingAction`. It does not clear, so the outcome reaches `commitFellShort` (`attempt-next.ts:259-264`).
  - That function's `Completed` cell becomes a switch on `outcome._tag`. The `action.result.question!` non-null assertion goes with it.
- `changedNothing` is left with readers that this change removes: `run-attempt.ts:2628` and `:2639`. Delete the function along with them.

## The `AgentFailed` redo: model it on the crash path, not `RerunStep`

`RerunStep.step` is `z.enum(['prepared', 'design', 'review', 'proposed', 'merge'])` (`attempt-next.ts:125`). `implement` cannot be rerun through the router's `ask-again` the way `AnswerUnreadable` is (`respond.ts:764-776`). The one path that already redoes `implement` by rule is the crash path:

- `nextOf` answers `WaitOnPerson{AgentCrashed}`.
- `run-attempt.ts:2401-2415` calls `rerunInPlace` (`respond.ts:598`), then `redoStep`.
- The retry count is on the log before the wait.

Copy that pattern:

- **The wait reason:** add an `AgentFailed{run, step: 'implement', why, said}` arm to `WaitReason` (`wait.ts`). The tag is new, so no bump is needed. `nextOf` answers `WaitOnPerson{AgentFailed}`.
- **The rule:** add a pure `redoAgentFailed(spent)` in `respond.ts`, beside `rerunInPlace`, bounded by `BOUNDS.stepRedos` with `BOUNDS.stepRedoWaits`. This puts the rule in `failure/`, as 0108 §19 requires.
- **The redo:** `run-attempt.ts`'s `WaitOnPerson` branch redoes the step while `redoAgentFailed` allows. When it does not, the wait stands for a person.
- **Exhaustive switches:** these will go red until the new arm is added — `wait.ts` (around `:375`, `:392`, `:641`, `:755`, `:1067`), `wait-words.ts`, and the board's lists in `apps/board/src/lib/task.ts` and `board.ts`.

## Ended abnormally keeps today's cells

The pure decision answers `AgentFailed` for a run that ended abnormally, because that is the table's first row and its test. The wiring does not change, though: a crash, a timeout, `out-of-turns`, `out-of-usd` or a drain still returns `{stopped, interrupted}` and becomes `Interrupted{cause}`. Then `interruptedAs` (`attempt-next.ts:439-455`) answers as it does today:

- **Turns or spend:** `BudgetExhausted` goes to the router, where the conducting recipe declares a judge.
- **A crash:** `AgentCrashed`, which `rerunInPlace` redoes.
- **Not touched in `fixRound`:** `never-started`, `cutOffTransient` and `cutOffByWall` (`conduct.ts:5315-5333`).

The ticket's own Edges row settles this: *"the same as today's `interrupted`"*. The Out of scope section agrees: *"the redo itself (#1245, #1246); this ticket only chooses `AgentFailed`"*. Rerouting `budget-exhausted` would bypass a judge someone declared, and 0108's "Not built yet" list gives it another destination: *"a run that met `run.turns` or `run.wall` sent to triage"*.

## The dispatch seam

`WorkedAnswer` (`work-action.ts:60-76`) replaces the `{asked}` arm and `committedNothing` with one arm:

```
{ declared: AgentFailed | Disputed | Unclear, stopped: string }
```

- `{committed}` remains the `Implemented` arm.
- `ActionResult` carries the declared outcome in place of `committedNothing`.
- `commitResultOf` (`step-outcome.ts:196-209`) builds `Completed{head, outcome}`.
- `NEEDS_INPUT` keeps its other users.
- **Both dispatches** call the pure decision after `rev-parse HEAD`:
  - `firstDispatch` at `:5060`.
  - `fixRound` at `:5293`.
  - The decision function is never handed a crash. It only sees runs that finished normally.

## The block and its parser

- **Location:** `parseImplementOutcome` goes in `@lingtai/domain`, next to `TriageQuestion`.
- **Fence regexes:** reuse `parseDraft`'s fence handling (`agent-action.ts:1557-1600`), with ```` ```outcome ```` in place of ```` ```question ````.
- **Unclear's questions:** validate with `AskedQuestions`.
- **Reading the fences:**
  - Collect every outcome fence.
  - If two parse to different values, the answer is *none*.
  - Otherwise use the last one. The ticket's *"the last fence"* rule and its *"two fences that disagree"* test are reconciled this way.
- **The `Disputed` index:**
  - It is 1-based and matches the numbering the fixer is shown: `### ${i + 1}.` (`fix.ts:770`, `:858`).
  - For the `on: 'output'` arm (a red build, or `verify-failed`), the refusal counts as one finding, so the only valid index is `1`.
  - At a first dispatch the count is 0, so any `Disputed` there is `AgentFailed`.
  - The decision takes the count offered as an input.
- **`FixerDisagrees{said}`** is the rendered lines: `finding <n>: <why>`.
