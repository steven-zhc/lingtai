# Design note: #1209, the lane lands only the sha the steps checked

The ticket's shape holds. This note covers three things the ticket does not decide, plus a few placement points the agent would otherwise have to work out.

## 1. `head-moved` needs an owner as well as a reading

`RefusalReason` has two total records, and the ticket names only one. The other is `INTEGRATION_OWNER: Record<RefusalReason, FailureOwner>` (`packages/domain/src/attribution.ts:126`). Its doc comment says: *"a tenth `RefusalReason` will not compile until somebody decides who owns it"* (`:121-124`).

**Decision: `'head-moved': 'lingtai'`.** The comment for the row should say that nothing about the diff was judged. The lane refused because the branch on origin is not the sha it was told the steps passed. The two ways to get there are:
- a recipe step that committed after the checks;
- a push to `agent/<n>` from outside.

Neither is a verdict on the branch's code, so it is not `'repository'`. Nobody meant it as a hold, so it is not `'person'`, which is reserved for *"a hold Lingtai means"* (`pending-migration`, `base-protected`, `base-checked-out`). The precedent is `wip-commit`, which is `'lingtai'` (`:165-170`): a commit on the branch that must not land, with the code itself not in question.

The person still gets the card. Owner and route are independent: `BUILT_IN_FOR['merge-refused']` is `null`, as the ticket says.

## 2. The `REFUSAL_READING` row

The ticket fixes the content. Here is its shape, written like the existing rows (`attribution.ts:259-380`):

- `says` reads both shas from `detail`. The lane writes detail as `expected <headSha> found <fetched>`. Parse it with a regex the same way `remote-error`'s `says` reads its detail (`:318-323`), and fall back to a sentence with no shas when the regex misses. That fallback matters because `diagnoseRefusal` is also fed `'x'` and arbitrary details in `attribution.test.ts:170-226`. The sentence: `${branch}` on origin is not the commit the steps passed, so it was not merged into `${base}`.
- `move: { action: 'requeue', why: … }`. The `why` says that Approve would re-land the same `onSha` against the same moved branch, and that a requeue starts again from the base.

## 3. `attribution.test.ts` keeps three hand-written lists

Each list says it exists because *"the compiler's version disappears if anyone reaches for an index signature"*:

- the `'lingtai'` list, `:51-62`;
- `every`, `:100-114`;
- the reading list, `:188-204`.

Add `'head-moved'` to all three. Add one `diagnoseRefusal` case beside the `unreachable` and `remote-error` ones (`:170-185`) that asserts all of the following:
- the recommendation is `requeue`;
- the recommendation is never `approve`;
- both shas appear in `what` when the detail carries them.

Nothing else needs a list edit. Three places derive from `RefusalReason.options` or `.exclude([...])`, so `head-moved` reaches them without a change:
- `step-outcome.ts:54`, so the merge plugin carries the reason through rather than collapsing it to `unexpected`;
- `proposal.ts:173`;
- `action.ts:75`.

The parametrised `it.each` at `domain/unit/attempt-next.test.ts:471` also picks it up, and it expects `Propose{MergeRefused}`, which is what the ticket wants.

## Placement in the lane (`packages/repo/src/integrate.ts`)

- **Put the assertion after `retryUnreachable(...)` (`:479-492`), not inside the retried Effect.** A mismatch is not unreachable and must not be tried again. Read it with `at(['rev-parse', laneBranch], mirror)`, `.trim()` it, then `refuse('head-moved', \`expected ${options.headSha} found ${fetched}\`)`.
- **Put it before `sweepAbandoned` and before the worktree `acquireRelease` (`:511`).** That way a refusal never cuts a worktree. The lane refs are already released by the finalizer at `:451-459`, which is registered before the fetch, so refusing there leaks nothing. `refuse` is already used at this depth: `base-checked-out` at `:472`.
- **On the conflict path, reuse the variable** in place of the second `rev-parse` at `:599`. The ref is under this lane's own `laneId` (`:449-450`), so the second read could only ever return the same value.
- **"Each try fetches again" (ticket Edges, `LOST_PUSHES`).** Check whether the lost-push retry re-enters `attempt` from the top or only re-runs the push at `:672`. If it re-enters, the assertion runs on every try for free. If it does not, leave it alone: the branch ref is not re-read between push tries, and widening the retry is #1221's territory, not this ticket's.

## Placement in the conductor (`packages/conductor/src/conduct.ts`)

- Change only `:3377`, to `${on.onSha}:refs/heads/${branch}`. A raw sha as the source with a full `refs/heads/` destination is legal even when the ref does not exist on origin yet. The object is local because `onSha` is a commit in this worktree.
- **Leave the end-of-pass publish alone**: `+HEAD:refs/heads/${arm}` at `:2541` and `:2571`. It is not a landing, and `conduct-what-a-claim-leaves.test.ts:240,343` pin it. A grep for `HEAD:refs/heads/` will turn those lines up, and they are out of scope.
- Rewrite the comment at `:3470-3476` as the ticket says.
- For the refspec test, `land-unreachable.test.ts` already collects every push into `pushes` (`:21`, `:37`). One more `it` there can assert that `pushes[0]`'s last argument is `` `${onSha}:refs/heads/agent/<n>` `` with the `onSha` the test handed in. Do not assert `HEAD`.

## Lane test

Change only the fixture: `options()` `headSha` becomes `'1'.repeat(40)` (`integrate.test.ts:117`), to match the fake's `sha` at `:59`.

For the new `head-moved` test, do not special-case the fake. Pass `headSha: '2'.repeat(40)` through the existing `options(git)` spread, then assert three things:
- the result is `{ ok: false, reason: 'head-moved' }`;
- `calls` has no `merge` and no `push`;
- the integration stream holds one `IntegrationRefused` with `reason: 'head-moved'`. Look at how the `base-protected` test at `:236` reads the stream.

## What settles it on the log

This cannot be checked from here. In production, the claim is that every `IntegrationSucceeded` follows an `IntegrationAttempted` whose `headSha` equals the visit's `head` from the `StepEnded` for `review`. A refused landing shows as `IntegrationRefused.reason = 'head-moved'`, with both shas in its `detail`.
