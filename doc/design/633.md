## Design note for #633: `lingtai events`

### Where the manifest comes from: a JSON import, not a copied file

Import the manifest the way `version.ts` already imports the version:

```ts
import manifest from '../../../doc/events.json' with { type: 'json' }
```

`apps/cli/src/version.ts:3` does exactly this with `package.json`, and its comment states what follows from it: *"from the source that is the checkout's `package.json`, and bundled it is inlined by esbuild, so the binary reports the version it was built at."* `bundleCli` is `bundle: true` over `entry.ts` (`apps/release/src/build.ts:155-160`), so the manifest ends up inside `lingtai.cjs` and inside the SEA. `tsconfig.base.json` already sets `resolveJsonModule: true`.

This means **`apps/release/src/build.ts` does not change**, even though the ticket's Fix names it. Copying the file into `dist/` would be wrong:

- `apps/release/integration/build.test.ts:82` pins the layout to `['board', 'lingtai.cjs', 'package.json', 'packages', 'prompts']`.
- `release.yml`'s `pack` tars only `lingtai packages prompts`, so a copied file would never reach an installed machine.

Inlining also satisfies "never fetched" by construction, because nothing reads the file at run time.

Type the import as `EventsDoc`. Use a type-only import from `packages/domain/scripts/events.ts:308`, which is erased, so `typescript` (which that script imports at its top) is never loaded. `@lingtai/domain`'s `exports` has no `./scripts` entry (`packages/domain/package.json:6-11`), so either reach it by relative path the way `version.ts` reaches `package.json`, or add `"./events-doc": "./scripts/events.ts"` and import it with `import type`. Prefer the relative path: one consumer does not justify a package export.

### "Generated at the version's commit": what the bundled file actually is

The committed `doc/events.json` carries `"sha": "b88a3f16…"`, the commit it was last generated at, not HEAD. Its event-level facts are held current by `staleEvents` (`packages/domain/unit/events-json.test.ts:41-51`), which compares everything except `definition` and the site URLs (the site count is compared). So a source checkout lists the right events, with permalinks that are valid at an ancestor commit. That is acceptable for the source form; do not regenerate from the CLI.

For a release there is a gap. The published `events.json` asset is regenerated with `--ref <tag>` in the **publish** job (`release.yml:146-147`), but the binaries are built earlier, in the **binary** job, from the committed file. Close the gap in `release.yml`: in the binary job, before `pnpm build && pnpm binary`, add a step that runs only when `github.ref_type == 'tag'`:

```
node packages/domain/scripts/events.ts --ref "$GITHUB_REF_NAME"
```

Call the script directly, not through `pnpm events:generate`; the trap is spelled out at `release.yml:142-143` and `doc/design/632.md:24`.

- The checkout is clean, so the dirty check (`events.ts:518`) passes.
- `--ref` is the tag, so the ref-is-HEAD check (`events.ts:509`) passes.
- The script reads only `apps` and `packages` through `git archive`, so all four runners produce the same file.

After this step the manifest inlined into the binary is byte-for-byte the asset published beside it. Nothing can check this before the merge, because it is workflow YAML. The unit claim that stands in for it is the `--json` test below: the bundle prints whatever file it inlined. Say this in the commit body.

### The command

- **`apps/cli/src/events.ts`** (new): pure render functions plus the imported manifest, with no I/O, so it can be unit-tested the way `output.ts` is.
  - `eventsBySection(doc)`: an ordered list of `[at, events[]]` built from `STEPS` (`packages/domain/src/vocabulary.ts:43`, *"each writing its own list is how one of them ends up missing a step"*) followed by `'outside'` (`events.ts:2124`, `At = Step | 'outside'`).
    - An event whose `at` names several steps is listed under each of them; `TicketReleased` is `['claim', 'end', 'outside']`.
    - Retired events have `at: []` (`events.ts:2137-2138`), so they appear in no section. That is correct for the listing.
    - Skip steps with no events instead of printing empty headings.
  - `renderEvents(doc, columns)`: one `section(at, …)` per step (`output.ts:72`) containing a `table(['event', 'v', 'stream', 'defined'], …, { columns })`.
    - The definition link is up to 119 columns, so on most terminals `table` will fall back to key/value blocks (`output.ts:85-96`). Accept that; it is 0121 §4's rule, not something to work around.
    - The `sites` links appear only in the single-event view. Sixty-four events times every site in the listing is not a reading.
  - `renderEvent(event)`: `keyValues` over group, stream, schema version, retired, at, summary (omitted when `null`; 50 of 64 have one), defined, one `appended` row per site, and subscribers.
  - `findEvent(doc, name)`: an exact match first, then a case-insensitive one. Retired events are found; their `retired` row says so.
- **`--json` is the manifest inside 0121 §5's envelope**: `printJson('events', manifest)`, giving `{version, command, sha, events}`.
  - The manifest has no `version` or `command` key, so spreading it is lossless (`output.ts:110-112`).
  - Do not break the envelope to print the bare file. Every `--json` in this CLI carries it, and `doc/cli.json` reads `JSON_VERSION` from there.
  - `events <Name> --json` prints the **same shape filtered to one event**, `{version, command, sha, events: [e]}`, so one reader handles both forms.
  - An unknown name returns `printJsonError('events', 'unknown-event', …)` under `--json`. Otherwise it prints `symbol.fail()` plus a sentence naming `lingtai events`. It exits 1 in both cases.
- **`cli.ts`**: add `Command.make('events', { name: Args.text({ name: 'name' }).pipe(Args.optional), json, noColor }, …)`, put it into `root`'s subcommands (`cli.ts:1080`), and make the handler `await import('./events.ts')`. That matches `status`'s *"Loaded here and not at the top"* (`cli.ts:53-54`), so other commands never parse 38K of JSON.
- **`commands.ts`**: add a `define({ name: 'events', effect: 'reads', group: 'install and upkeep', … })`. Keep every usage line at 76 columns or fewer; `help.test.ts` measures them. Without the definition, `routeOf` sends the word to `unknown` (`migrated.ts:19`), and `one-parser.test.ts:32-35` fails.
- **Regenerate `doc/cli.json` and `doc/cli.md`** with `pnpm docs:cli`. Otherwise `cli-doc.test.ts:24-29` goes red.

### Tests (unit only)

- **`apps/cli/unit/events.test.ts`**:
  - Run `runCli(['node', 'lingtai', 'events', '--json'])` in process, capturing stdout the way `five-commands-cli.test.ts:6-17` does. Take the parsed output, remove `version` and `command`, and `toEqual(JSON.parse(readFileSync('doc/events.json')))`. That is the Done-when pin.
  - Run it again with a name, and with an unknown name to get the error document and exit 1.
  - Check that `eventsBySection` puts sections in `STEPS` order with `outside` last, that a multi-step event appears under each of its steps, and that a retired event appears in no section.
  - These tests read the real manifest only for the pin. Every assertion about rendering uses a small hand-built `EventsDoc`, for the reason `doc/design/632.md:9` gives: assertions on the real file go red every time an event is added.
- **Offline, no project**: the in-process `runCli` run with `HOME=/nonexistent pnpm test` is the claim. The handler touches no store and no network, so make sure `events.ts` imports nothing from `@lingtai/event-store` or `@lingtai/env` apart from `@lingtai/env/colour`, which `output.ts` already uses.
- **From the bundle**: add one assertion to `apps/release/integration/build.test.ts`, that the bundled `lingtai.cjs events --json` parses and its `events` has the committed length. That file is integration (803 s, run after the merge, per CLAUDE.md), so it does not stand in for the unit pin above. It is the after-merge witness to the ticket's "the release bundle must still build and run".

### Edges

- **A stale committed manifest** cannot ship: `events-json.test.ts` fails the `build` step first.
- **A pause, a drain or a running daemon** does not matter: the command reads no log and takes no lock.
- **A non-TTY or redirected stdout**: `columns` is `undefined`, so tables are never folded (`output.ts:82-83`). `--no-color` goes through `applyNoColor`, as every other command does.
- **Future events added to the manifest**: the pin compares against the file, not a count, so it stays green when events are added.
