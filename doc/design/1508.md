## #1508: the shape

**Where it goes.** All of the change is in `packages/conductor/src/blockers.ts`. The tests go in `packages/conductor/unit/read-blockers.test.ts`, the file that already tests the two readers sharing one read (`:58`, *"a discovery read through cachedBlockers is the one request"*). No caller changes. `board.ts:1017`, `queued.ts:348` and `status.ts:517` already go through `cachedBlockers`, and the reader they get still has the `listBlockedBy(issue, blockedBy?): Promise<…>` shape that `discover.ts:487` declares.

**A second map with the same key, not a wider `blockerCache` entry.** Add `const blockerReads = new Map<string, { blockedBy: number | null; read: Promise<readonly TicketLink[]> }>()` next to `blockerCache` (`:32`). Use the same `${project}#${issue}` key (`:106`). `forgetBlockers()` (`:35`) clears both maps. Keep `blockerCache`'s entry type as it is. `readBlockersEffect` reads that type at `:67–:70`, and the ticket puts that function out of scope. If the entry type grew a pending state, `readBlockersEffect` would have to understand it.

**The order inside `listBlockedBy` (`:105`):**
1. A fresh completed answer with the same count. Answer as `:109–:111` does now.
2. Otherwise, an in-flight read with the same count. Return its `read`, the same promise object.
3. Otherwise, start a read. If an in-flight read for a different count exists, the new one replaces it in `blockerReads`. That is the ticket's *"not shared. A new request is made."*

**The shared promise is the `.then(onOk, onErr)` chain itself**, the expression at `:113–:125`. Every waiter holds that one promise, so they all reject with the original error object that `:123` rethrows. That error has the same message the cached-failure path rebuilds at `:110`. Do not hang removal on a separate `.finally(...)`. That makes a second promise, and when the read fails nobody handles that promise, so Node reports an unhandled rejection.

**The decision the ticket leaves open: only the current read settles the key.** Inside both handlers, first check `blockerReads.get(key)?.read === this read`. Only when that holds does the handler:
- delete the in-flight entry, and
- write the completed answer: the `issues.length < BLOCKERS_PAGE` guard at `:116` on success, and `:122` on failure.

Delete first, then write, in the same handler, so no caller after the read settles finds neither entry.

The handler needs to compare against its own promise. Assign the chain to a `const` before storing it. The handlers run on a later microtask, so they can safely refer to that `const`.

The guard covers two cases that would otherwise go wrong:
- **`forgetBlockers()` while a read is in flight.** Without the guard, the old read would refill the cache the test just emptied.
- **A superseded count.** Without the guard, the older read's handler would delete the newer read's entry, and could write an answer under the old count over the newer one. Today `:117`/`:122` write whichever read settles last. The guard closes that too.

A superseded read still resolves or rejects for the callers already holding it. It just records nothing.

Keep `at = now()` taken when the request starts, as `:112` does. The expiry check at `:109` still measures from the request, not from when it settled.

**Ratchet.** The function already returns a bare Promise and is not `async`. The change adds `.then` handlers and nothing else, so no `async` function and no `Effect.run*` are added.

**Tests** (unit, using a fake `links` whose promises the test resolves or rejects by hand; inject `now` as the existing tests do; reset with `forgetBlockers()` in `beforeEach`):
- **Same key and count, concurrent:** two calls, then resolve the read. The fake is called once, and both get the same list.
- **Failure:** reject the read. Both callers reject with the same message, and a third call before `BLOCKERS_FRESH_MS` rejects from the cache without a second request.
- **Different counts:** concurrent calls with two counts make two requests. Settle the older read last, then check that a later call with the newer count is answered from the cache.
- **Full page:** a list of `BLOCKERS_PAGE` items is shared while in flight. After it settles, the next call makes a new request.
- **Expiry:** settle a read, then move `now` past `BLOCKERS_FRESH_MS`. The next call makes a new request, which shows no in-flight entry was left behind.
- **`forgetBlockers()` in flight:** call `forgetBlockers()` before the read resolves, then resolve it. The next call makes a new request.

**What cannot be checked inside the pass.** These unit tests are the claim. The traces in the ticket carry no issue number, so no span or event will confirm the fix in production. A Jaeger export after the fix could show it: two overlapping `queue.list` spans where the second makes fewer GitHub requests than the 7 in trace `9816cdc4…`. Nothing in `pnpm test:integration` depends on this change, so it is not needed.
