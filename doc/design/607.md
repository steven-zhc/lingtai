## Design: #607: the record the continuation writes, not the check that reads it

### What the log will show (check this first)

Read the stream `pass-aee78f71-7798-474f-917b-03dd8699fdf9` and confirm this before writing code. It should hold **two** `RunRefsPublished` rows:

- an earlier row with `outcome: 'published'` and `headSha: 0e3f229…`, written when the held pass ended at `proposed`;
- a later row with `outcome: 'nothing-committed'` and `headSha: null`, written by the continuation's finalizer after the lane refused with a conflict.

`savedHead` takes the last row (`resolve-wait.ts:384`, `.at(-1)`). So does the board's `savedFixWork` (`task.ts:917`, `findLast`). Both see `nothing-committed` and refuse `no-saved-head`. The run never failed to record a publish. The continuation recorded a second, false one on top of it.

If the stream has a different shape (no `published` row at all, or a different last outcome), stop and re-read. The rest of this note assumes the shape above.

### Why the continuation writes it

- **The re-cut.** A continuation re-cuts its worktree at the approved sha: `{ at: continuation.onSha, … }` at `conduct.ts:2380`. The fake makes the same promise: `baseSha: o.at ?? 'a'.repeat(40)` (`one-pass.ts`, `provision`). So for a continuation, `tree.baseSha` is `0e3f229`.
- **No new commit.** An approve continuation goes straight to `merge` without dispatching an agent, so `HEAD` stays at `0e3f229`.
- **The land push.** `land` pushes the branch and sets `published = on.onSha` (`conduct.ts:2700-2716`). The lane then refuses, `didLand` stays false, and the finalizer runs `publishWhatIsCommitted` (`conduct.ts:2163`).
- **The wrong comparison.** At `conduct.ts:1989` it asks `if (head === tree.baseSha)`. That is true, so it records `noteRefs('nothing-committed', null, …)` and returns. It never reaches the `branchHead === published && head === armPublished` branch below it.

The code already knows this comparison is wrong for a continuation. `baseShaOr`'s comment at `conduct.ts:1594` says:

> **Never `worktree.baseSha` on its own, once there is a continuation** (#465) — `worktree.baseSha` is where this re-cut's tree was checked out, the run's own prior head, and diffing against it is diffing a commit against itself until a new one lands.

`publishWhatIsCommitted` is the one reader of `tree.baseSha` that #465 did not convert. #465 converted the reviewer's diff (`conduct.ts:3632-3636`), `numstat` and `changedFilesArgs`.

The automatic-round path never shows this, because a fresh claim cuts at the base and the agent's commit moves `HEAD` off it. That is why only *approve → conflict* fails. The same ending follows every lane refusal on a continuation with no new commit: `conflict`, `no-commits`, `pending-migration` and `dirty-base` all reach this finalizer.

### The shape

All of this is in `publishWhatIsCommitted` in `conduct.ts`. Nothing changes in `resolve-wait.ts`, in `task.ts`, or in the event schema.

1. **Compare against the run's real cut.** Make a local base the same way `baseShaOr` does: `continuation?.diffBaseSha ?? tree.baseSha`. `diffBaseShaOf` can return `null` (`attempts.ts:267-270`), which is why the fallback is kept. Use that base in three places:
   - `conduct.ts:1989`: `head === tree.baseSha` → `nothing-committed`.
   - `conduct.ts:1988`: `wip.parent === tree.baseSha` → `branchHead = null`. Today, a continuation whose agent left only a dirty tree is recorded `branchCarries: false`, and `savedHead` refuses it `wip-head`. In fact `agent/<n>` already carries the clean approved head, and the comment at `resolve-wait.ts:388` says that case must continue: *"A WIP commit on the arm does not taint the clean head already published on the issue branch."* This is the same bug in its other form, so fix both together.
   - `conduct.ts:2151`: the `keepHead` guard, so a defect after the read still keeps a continuation's unchanged head.

2. **Let the existing push run.** With the corrected base, the conflict ending gets past `head === base`. `published === head` but `armPublished` is still `null`, so it falls through to the push at `conduct.ts:2061`:
   - The branch refspec is a no-op at a head origin already has. The lease is right because `land` set `lease = on.onSha`.
   - The forced arm goes up, which is exactly what the *"Both refs, because the row says both"* comment (`conduct.ts:2000-2020`) says a refused-lane ending must do.
   - The row it records is `published` with `headSha: 0e3f229` and `branchCarries` not false. `savedHead` and `savedFixWork` both accept that row as it stands.

   Do not add a new short-circuit that records `already-published` without the arm. That is the #251 loss the same comment describes.

3. **Keep the last-row readers as they are.** Do not change `savedHead` or `savedFixWork` to skip `nothing-committed` and look further back. The ticket's *Watch out* forbids it, and it would break a real case: a later attempt that truly committed nothing must still win over an older head.

The board agrees because it reads the same row. Its only change is a test.

### Tests (all unit, per 0060 §1)

- **`conduct.ts`.** Write a new test file next to `conduct-continuation-diffs-the-base.test.ts` and use it as the template: same `once` / `fakePorts` / `memoryStore`, `continuing: { runId: first.runId }`, and `merge: true`.
  - **Recipe:** `human:` at `proposed`.
  - **First pass:** it holds. Resolve it with `aResolution` Approve at the published head.
  - **Second pass:** override `repo.integrate` to answer a conflict. Spread `fakePorts(…)` and replace that one method. Check what `repo.integrate`'s conflict answer looks like in `packages/repo` rather than guessing it.
  - **Assertions:**
    - The run stream's last `RunRefsPublished` is `published` with `headSha` equal to the approved sha.
    - The `did` log has a `git push` naming the arm.
    - Calling `resolveWait` with `GrantFixRound` on the conflict wait is accepted, not refused `no-saved-head`. Use whatever entry point the existing #589 grant-on-conflict tests use.
- **The WIP form.** In the same file, add a continuation whose tree is dirty with no new commit. Assert `branchCarries` is not `false` and `armSha` names the WIP. Model it on the WIP cases in `conduct-what-a-claim-leaves.test.ts:579-736`.
- **The board.** In `apps/board/unit/standing.test.tsx`, which already covers `savedFixWork`, add one case with the two-row stream from the log:
  - `published` then `nothing-committed`: refused, which is today's behaviour, pinned so nobody "fixes" it on the reader side;
  - `published` then the new `published`: `{ head, ref }`, so the Continue fixing card is enabled.
- **Before committing.** Run `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `pnpm test`. Nothing here needs the integration half.
