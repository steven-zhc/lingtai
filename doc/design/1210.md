## Design note for #1210: every base move goes through `build`, and review is carried across a disjoint move

There are two halves. The lane in `packages/repo/src/integrate.ts` stops landing anything nobody built. The walk in `packages/conductor/src/run-attempt.ts` learns to skip one review visit. Line numbers below are from this worktree. Some have drifted a few lines from the ticket's.

### 1. The lane: always refuse a moved base, and never retry a push

**The overlap check.** At `integrate.ts:620-634`, refuse `base-moved` whenever `fork !== localBase`, with `paths = baseMovedOn(...)`, which may be `[]`. The detail text needs two wordings: one naming the files, and one saying the base moved on files the branch did not touch. Keep `baseMovedOn` (`:157`). It now decides what `paths` holds, not whether the lane refuses, so rewrite its doc comment (`:149-156`, which says *"lands after `verify` as it always did"*). Rewrite the comment above the check (`:611-619`) the same way.

**`verify`.** Delete the `verify` option (`:121-126`) and its branch (`:637-650`). Do not delete the `'verify-failed'` reason. `attempt` still produces it for `!options.stepsPassed` (`:425`), and `judge-agent.ts:190`, `respond.ts:706`, `proposal.ts:360` and `wait-words.ts` all read it.

**The lost push.** Delete `LOST_PUSHES` (`:220-237`) and `LostPush` (`:190-215`). The loop at `:771-782` becomes:

1. Run `attempt` once. If it returns anything but a lost push, return that.
2. If the push was lost, run `attempt` **once more** with a flag that forbids the push, a private `{ push: false }` argument to `attempt`. Since `attempt` is a value today, it becomes a function.
3. That second run fetches again. The base has moved, so `fork !== localBase` now refuses `base-moved` against the new base, or `conflict` if the new base conflicts. Either way, it appends the one terminal through `refuse` as today.
4. If the second run reaches the push point anyway (origin rejected the push but the re-fetch shows no move), refuse `unexpected` with git's rejection text. Do not push again. That case is not a race this lane understands, so a person should see it.

This shape is what makes the *exactly one push call* checkbox hold. `attempt` still returns an internal non-terminal value on a lost push, so keep a small private type for it. Just do not name it `LostPush`, which the checkbox deletes. Keep the comment about why a lost push appends nothing, but rewrite it to *"a lost push is followed by one recompute that ends in a refusal"*. Also rewrite the file header (`:36-51`) and the loop doc (`:737-761`), which describe four pushes.

Keep the `landedAlready` check (#1125, `:670-685`) exactly as it is. It runs inside the push try, before anything is called a lost push.

After this, `push-rejected` comes out of the lane only through the catch-all classification at the bottom, if at all. Leave `vocabulary.ts`, `explain.ts` and `classify.ts` alone: `conduct.ts:3417` still produces `push-rejected` for a stale lease. Rewrite only the comment at `vocabulary.ts:65-67`, as the ticket says.

**0122 §3 becomes false in two sentences.**
- `doc/decisions/0122-several-passes-share-one-conductor.md:88` says *"two lanes at once would both run `verify`"*.
- `:92-94` says a landing goes back to `build` and `review` *"when the changed files overlap"*, and *"The lost-push retry already re-runs all of it."*

This repo's rule (CLAUDE.md: *"A decision that changes is an edit to its topic's ADR"*; only `decisions-archive/` is frozen) makes this an edit to 0122 §3, not a new file. The edit should say that any move goes back to `build`, that `review` is carried when the move is disjoint, and that a lost push is one recompute ending in `base-moved`.

### 2. The walk: carry review across a disjoint merge

**The decision that is not obvious: carrying means *not visiting*, not visiting and passing.**
- No `runStep` call.
- No `StepStarted` or `StepEnded`.
- No `record()` call.

#1229 reads *"no review visit at the merge commit"* as the evidence, and a synthetic `passed` visit would also make `landedOnBaseOf` (`attempts.ts:279`) think a review saw the merge.

**Where the carry is decided.** Add one variable beside `reviewedSha` (`run-attempt.ts:1417`): `let reviewCarriedTo: string | null = null`. Set it in the `MergeBase` case, at `:1658-1683`, before `reviewedSha` is overwritten at `:1676`. All of these must hold:
- `offer.proposal._tag === 'BaseMoved'`.
- `offer.proposal.paths !== null && offer.proposal.paths.length === 0`. **`null` is not `[]`**: `mergeRefusalProposal` makes `paths: null` when the lane's result carried no `baseMoved` (`proposal.ts:345`). An unknown overlap is a full review.
- `reviewedSha === onSha` **as it stood before `record` moved it**, or `approvedHeadStands` (`:1627`). Read `reviewedSha === onSha` next to `approvedHeadStands`, before `record`, for the same reason that line gives: *"Read before `record` moves `onSha` to the merge commit (#671)."*

When all of these hold:
- `reviewCarriedTo` is `merged.head`.
- `reviewedSha` and `landedOnBase` are `null`. With `paths: []` there is no overlap to show. A non-null `landedOnBase` would also survive a fix round that never visited review (`:1694`) and hand the next full review an empty landed section.

Otherwise, `reviewCarriedTo` is `null` and everything happens as it does today.

`reviewedSha` must be `null` on the carry path even when a person approved the head. Otherwise a review after a later fix round would be a delta against a head from before the merge, which is the base's commits (the ticket's Watch out). That is why the ticket's edge says *"the next review is full"*.

**Where the skip happens.** At the top of the `while` loop (`:1736`), before the conflict-evidence block and before `contextFor()`:

```ts
if (at === 'review' && reviewCarriedTo !== null && reviewCarriedTo === onSha) {
  reviewCarriedTo = null
  at = nextStep('review')
  continue
}
```

Use `nextStep` rather than `after`, so a continuation's `prepared` rule (`:1383`) stays the one place that decides it.

**Where the carry is cleared**, so no stale value can match:
- after the skip uses it (above);
- in `applyConflictMerge` (`:1477`);
- at the top of every `MergeBase` case, before the new value is set;
- in the `FixRound` case.

Comparing against `onSha` already handles an implement that moved the head. The explicit clears exist so that no reader has to prove that.

**A continuation never carries.** `reviewCarriedTo` starts `null`, like `reviewedSha` (*"Never shared between passes"*, `:1416`). Since there is no landed section, `landedOnBaseOf` must not hand one to a continuation for a `paths: []` move. Make it return `null` when `moved.paths.length === 0` (`attempts.ts:280`). Without that, a pass that stops after a carried merge (build red with no judge, say) and resumes at `review` gets an empty *"what landed"* block.

**The landing comment** reads the last `review` outcome in the run's stream (`conduct.ts:5429`). With a carry, that is the review before the merge, which is the review that cleared the head being landed. This is correct and needs no change.

- **Unit tests that stub `verify-failed` as an `IntegrateResult`** (`conduct-a-whole-attempt.test.ts:795,884`, `conduct-stands-the-conductor-down.test.ts:460`, `attempt-steps.test.ts:2247`) stay. That reason still exists.

None of this is new IO, so no `async` function and no `Effect.run*` should appear. If the effect ratchet goes red, the change is what is wrong, not the baseline.
