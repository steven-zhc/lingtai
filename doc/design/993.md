# Design note for #993: the project filter scopes the bar

The ticket gives the shape. This note covers four things it leaves open, which you would otherwise have to work out mid-change.

## 1. In `page.tsx`, two names: the URL's value and the selection

`only` is read at `page.tsx:614` and used in two different ways.

**It is passed to the read.** `loadBoard(only)` at `:648` runs inside the `measure` closure, before `filters` exists. Rename this one to `param`:

```ts
const param = (await searchParams).project
… loadBoard(param) …
```

**It is passed to everything drawn after the read.** Declare `only` after `measure` returns:

```ts
const only = param ?? (filters.length === 1 ? filters[0] : undefined)
```

Every later reader then takes the selection without being touched:
- `<Bar project={only}>` at `:712`, so the literal the five test slices look for survives (Watch out);
- `Projects` at `:719`;
- `LandedCount` at `:824`;
- `emptyNote` at `:887` and `:893`.

**`emptyNote` changes wording, on purpose.** On a one-project board it will now say *Nothing in lingtai is waiting on you.* (`lib/board.ts:515-521`). That is true, and it matches the summary, which already names the project. Leave it.

**Factor the default into a pure function** next to `filterOptions`: `selectedProject(param, filters)` in `lib/board.ts`. Test it in `unit/filter.test.ts`. That is the "pure resolver" Done when allows, and it covers *`Report` and Landed carry `?project=`*:
- `LandedCount` is already a pure export (`page.tsx:458`);
- `landedLink` and `withProject` are pure.

Once that is in place, `inView` (`projects.tsx:42`) goes away. `Projects` takes `only` as given.

## 2. "Registered" means `loadProjects()`, and `/` already has it

`loadProjects()` filters on `isRegistered` (`packages/conductor/src/projects.ts:81-83`). A repository waiting for `Recheck` (#163, #182) does not come back from it. That is the same set the recipe page answers for, and anything else gets `notFound()` (`recipe/[project]/page.tsx:301-302`). Take every `registered` from it, so `Recipe` is never drawn for a project whose recipe page 404s.

**On `/`:**
- `registered` is already `loadProjects()` with `.catch(() => [])` (`page.tsx:649`).
- Pass `registered={only !== undefined && owners.has(only)}` to `Bar`. `owners` is built at `:688`.
- Pass `registered.map((p) => p.project).filter((p): p is string => p !== null)` to `Projects`. This is the same null filter as `lib/board.ts:1430`.
- Make `Projects`' `registered` prop **required**. Its only callers are `page.tsx` and the recipe bar below, so the compiler finds both.

**On `/report`, `/landed` and `/task/[id]/layout.tsx`:**
- Add `loadProjects().catch(() => [])` beside the page's existing reads.
- Pass `registered={project !== undefined && list.some((p) => p.project === project)}`.

The Effect ratchet does not apply here. `effect-ratchet.baseline.json` has no `apps/board` entry: it counts `apps/cli` and `packages/*` only. Still, add no named `async` function. Put the call in the existing `Promise.all` or `await`.

## 3. The recipe page's bar goes in a file of its own

`Recipe` is exported and pure, but `recipe/[project]/page.tsx` imports `@/lib/recipe` and `@lingtai/conductor/projects` (`:1-5`). Its only render test is the integration one, which needs module mocks to import it (`integration/recipe.test.tsx:38-42`). The *Done when* item for the recipe page's bar has to be a unit test, so put the bar in a pure file in the segment:

```
recipe/[project]/recipe-bar.tsx
  export function RecipeBar({ project, filters, registered, app })
  // <Bar project={project} registered here="recipe">
  //   <span className="sep" /> <Projects … only={project} />
  // </Bar>
```

**`Recipe` gains one optional prop**, `bar?: { filters; registered; app }`:
- **With the prop:** `Recipe` renders `RecipeBar` with it.
- **Without the prop** (`integration/recipe.test.tsx:101` passes only `view` and `edit`): `Recipe` renders `<Bar project={view.project} registered here="recipe" />` with no children, so there is no filter and no `recipe · `.

**`RecipePage` builds `bar`:**
- `filters` is `filterOptions(<names from the loadProjects() it already reads at :301>, await onBoardProjects().catch(() => []))`.
- The `.catch` is required. `onBoardProjects` swallows only `does not exist` and rethrows everything else (`lib/board.ts:1575-1581`), and the recipe page must not 500 over `task_view`.
- `app` is `hasGitHubAuth()` from `@lingtai/env`, imported as `page.tsx:10` imports it. It is synchronous.

**The unit test** imports `recipe-bar.tsx` and renders it with `renderToStaticMarkup`. It asserts that:
- the summary names the project;
- `Recipe` has the `on` class and `aria-current="page"`;
- there is no `recipe · `.

**Integration rules that also apply to the new file.** `recipe-bar.tsx` sits under the segment, so it is scanned by `integration/recipe.test.tsx:396-415`:
- no `"use server"`;
- no `node:fs`;
- nothing imports `app/actions` except `recipe-form.tsx`.

The new file and its imports must pass all three. These are the files the recipe page now reaches through it: `bar.tsx`, `projects.tsx` and `filter-menu.tsx` (`'use client'`, React only).

That integration half does not run before the merge. Stand in for it with a unit test: read those four sources and assert that none of them matches `from ['"][^'"]*actions['"]`. That is the claim ticket C must keep when it adds Pause.

## 4. The hint and the `+` stay inside `Projects`

`Projects` returns a fragment: the `FilterMenu`, then the `+` link.

- In the empty-board branch (`projects.tsx:47-53`) it stays the single setup link, with no `+`.
- The `+` keeps `where` and `why` exactly as at `:37-38`.

Each row's `.phint` is drawn only when `registered.includes(p)`. Ticket C will make the hint's text depend on the project, so build it in one place, a `hint(p)` that returns `'recipe'` or `null`. Do not inline the string in the JSX.

`unit/bar.test.ts:216-225` reads `projects.tsx` and `bar.tsx` as sources for the amber guard. `recipe-bar.tsx` contributes no class of its own, so it does not need to be added there.
