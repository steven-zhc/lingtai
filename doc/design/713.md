# #713: design note

**What already exists and what doesn't.** The add-repository page has no installation flow to remove. `apps/board/src/app/setup/repository/page.tsx:23` renders `<TerminalScreen requested={…} />`, and `apps/board/src/app/setup/terminal.tsx` contains no install link. Its comment says *"It calls neither GitHub, the env nor the log — the one import is `next/link`"*. What the screen gets wrong on a `gh` machine is its wording. It describes `pnpm lingtai add` as the command *"which picks from what the App can see (#394)"* (`terminal.tsx:46-47`). It also shows the `requested` note about an organisation owner approving an install (`terminal.tsx:38-43`). Both are App facts. So this change is wording on that screen, plus one prop in `page.tsx`.

## Shape

1. **The bar's first step.** In `apps/board/src/app/page.tsx:632`, change `app={hasGitHubApp()}` to `app={hasGitHubAuth()}`, and change the import at `page.tsx:10` to match.
   - `hasGitHubAuth` (`packages/env/src/index.ts:1419`) returns true for an elected `gh`. It returns false for a refused `github.auth` and for nothing configured, and it never throws.
   - `Projects` (`projects.tsx:58-59`) then sends a `gh` machine to `/setup/repository` with "add a repository".
   - Keep the prop name `app`: `projects.test.tsx` and the docstring at `projects.tsx:38-44` both use it. Do update the docstring sentence *"`page.tsx` reads `hasGitHubApp()` and hands the answer down"* so it names `hasGitHubAuth()` and says the prop means *GitHub is reachable*, not *an App exists*. Without that edit the comment says something false.

2. **The screen.** Give `TerminalScreen` a second prop, `gh?: boolean`, with default `false`. Keep the component pure and env-free so `terminal.test.tsx` can keep calling it with plain props. Have the page read the env and pass the answer down. This is the pattern `projects.tsx` already uses, and the comment at `terminal.tsx:7-13` gives the reason: an env import inside a component under `setup/` is the kind of import #230 caught late.
   - When `gh` is true, the paragraph says this machine reaches GitHub with the saved `gh` login, so there is no App to install. It shows `lingtai add <owner>/<repo>` as the way to add a repository.
   - Do not repeat the *"picks from what the App can see"* sentence there. The `gh` branch of `apps/cli/src/add-github.ts:233-247` checks the access of a slug it was given (`deps.ghAccess(slug, …)`). Listing repositories under `gh` is explicitly out of scope, so the slug form is the only one to name.
   - When `gh` is true, do not render the `requested` note, even if `?requested=1` is present. Only the App's setup URL, via `installed/route.ts`, produces that query string, and on a `gh` machine it describes an approval nothing is waiting for. With `gh` false, the output is byte-for-byte what it is today.

3. **Reading the auth kind in the page.** `repository/page.tsx` computes the value as `githubAuthKind() === 'gh'` (`packages/env/src/index.ts:1412`).
   - Do not use `githubAuth()`. It throws on an unconfigured machine (`index.ts:1398-1405`), and that would turn today's screen into a 500 on exactly the machine that should see today's screen.
   - `githubAuthKind()` still throws on a refused value, such as `github.auth: banana`. Catch that and treat it as not `gh`, so the page renders today's screen. Diagnosing a refused value is `lingtai doctor`'s job, not the job of a help page.
   - `/setup/wizard/page.tsx:11` renders the same screen. Pass it the same value so the two addresses do not say different things. That is the same three lines in a second file.

## Edges the ticket leaves to the design

- **A long-lived board.** `githubAuthKind` and `hasGitHubAuth` read the file on every call (`machineFile(from)` inside `githubAuthElection`, `index.ts:1386`). Both pages are request-time: `repository/page.tsx:19` already exports `dynamic = 'force-dynamic'`. Confirm the board page `page.tsx` is dynamic as well (it reads the log on every render, so it should be), and read the value inside the render function, never at module scope. A test that pins this: render twice with two different `from` environments and expect two answers. In practice that is already covered by testing `hasGitHubAuth` on its own terms, so do not add an env-reading test to the board for it.
- **A machine with a full App and `auth: gh`.** This is a `gh` machine (`add-github.ts:228-230`: *"a machine with a full App and `auth: gh` is a `gh` machine"*). It sees the `gh` sentence.
- **`/setup/github-app` reached by hand on a `gh` machine.** It is unchanged and not part of this ticket. Nothing on the board links there any more.
- **`installed/route.ts`.** It is unchanged. It still guards on `hasGitHubApp()` and 303s to `/setup/repository`, which now shows the `gh` screen where that applies.

## Tests (unit only)

- `projects.test.tsx` already shows that `app=true` produces `/setup/repository` and no `/setup/github-app`. The new claim is about `page.tsx`. Add a source-level assertion next to the existing `read('../src/app/page.tsx')` block (`projects.test.tsx:125-127`) that `<Projects` is passed `hasGitHubAuth()` and that `hasGitHubApp` is no longer imported there.
- In `terminal.test.tsx`, add a `gh` case:
  - `<TerminalScreen gh />` contains `gh` login wording and `lingtai add &lt;owner&gt;/&lt;repo&gt;`. The output is static markup, so the angle brackets are escaped.
  - It does not contain `/setup/github-app`, `installations/new`, `the App can see`, or `owner has to approve`.
  - `<TerminalScreen gh requested />` also does not contain `owner has to approve`.
- In the same file, assert that the default render is unchanged.

All of this is covered by `pnpm test`, so nothing waits on the integration half.
