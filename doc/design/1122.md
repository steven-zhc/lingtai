## Shape

Two small edits that don't depend on each other: one in `conduct.ts`, one in `doctor.ts`. Each comes with a test that records how many times the probe was called. Nothing is appended and no ADR changes.

### 1. `runOnce`: decide `runtime.agent` before probing

`runtimesOf` puts `runtime.agent` in the set first (`packages/conductor/src/runtimes-of.ts:12`, `const seen = new Set<RuntimeId>([recipe.runtime.agent as RuntimeId])`). So `secondRuntimes` (`conduct.ts:866`) holds the recipe's `runtime.agent` whenever that differs from the conductor's own runtime. That is why the test probes when no step names anything.

**Decision: keep the order of the steps and narrow the condition the probe runs under.** Don't reorder the code.

- Probe only when `recipe.runtime.agent === ownRuntime` **and** `secondRuntimes.size > 0`.
- Otherwise `dispatchable = []`.
- Then call `agentRefusal(resolved, …, dispatchable)` exactly as today.

Why this is safe:

- **When `runtime.agent` differs:** `agentRefusal`'s first branch returns before the step loop ever reads `signedIn` (`conduct.ts:436-445`). The empty list can't change that answer, and the `detail` text (`conduct.ts:877-885`) is untouched.
- **When `runtime.agent` matches:** the `runtime.agent` entry in `secondRuntimes` is filtered out as `ownRuntime` (`:866`). What's left is exactly "the runtimes a step names", so the step path behaves as today and #314 is untouched.

Don't do these instead:

- **Don't call `agentRefusal` twice.** For example, once with `[]` to "check the first branch". On a recipe where `runtime.agent` matches but a step names `codex`, that first call returns the step refusal, which is wrong.
- **Don't split `agentRefusal` into two exported functions.** `doctor.ts` calls it through `recipeRow` with a precomputed list, and the two halves are one function on purpose (comment at `conduct.ts:862-863`: *"so the two facts stay one branch"*).

Rewrite the comment above `secondRuntimes` (`conduct.ts:856-864`) to say that a `runtime.agent` other than the conductor's own is refused without the probe, because that branch never reads it. Also fix the `signedIn` option's doc comment (`conduct.ts:515-523`). It currently says *"A unit test that names one runtime never reaches it"*. That was false for this test, since it named `codex` only at `runtime.agent`. It should say the probe is reached only where `runtime.agent` is the conductor's own runtime **and** a step names a different one.

**Test.** Change the test at `packages/conductor/unit/conduct-before-the-claim.test.ts:299-316`:

- Pass `signedIn: () => { calls++; return Promise.resolve([]) }`.
- Assert the same `stage: 'recipe'` and `detail` it asserts today, plus `calls === 0`.
- Leave `:359` and `:408` untouched.

The ratchet counts only `src/` (`packages/domain/unit/effect-ratchet.test.ts:480`), so the form of the stub doesn't matter to it. A plain function returning `Promise.resolve` still keeps the file free of a new `async`.

### 2. Doctor: `DoctorReach.signedIn`

- **Type:** `signedIn?: SignedIn`, the type `@lingtai/recipe` already exports (`packages/recipe/src/local.ts:65`, `() => Promise<readonly RuntimeId[]>`). It is the same shape `runOnce` takes, so a stub fits both. Put it beside `gh?` (`doctor.ts:1252`). The doc line should follow `gh`'s: *"injectable so a unit test spawns nothing."*
- **Wiring:** `projectRecipes(filters)` becomes `projectRecipes(filters, reach.signedIn ?? signedInHere)`. The body does `yield* lift(() => signedIn())` where it now calls `signedInHere()` directly (`doctor.ts:2432`). The call site is `doctor.ts:3690`. `runDoctor`'s `reach` is already `Partial<DoctorReach> & Pick<DoctorReach,'sea'>` (`:3409`), so leaving it optional is all it takes for no existing caller or literal to change.
- **Decision: the doctor probe stays at one call per report.** It is not gated on any project naming a second runtime. The ticket's "Done when" asks for *called once* with one registered project. The comment at `:2429-2431` justifies the single machine-wide probe, and `lingtai doctor` is not on the hot path that `runOnce` is. Making it conditional would be a behaviour change this ticket doesn't ask for.

**Test.** No doctor unit test reaches `projectRecipes` with a registered project today: it returns early on `filters.length === 0` (`:2416`).

- Build the new test on `apps/cli/unit/doctor.test.ts`'s existing `reach`. Its `recipe:` stub (`:107-108`) is what `projectFiltersOnce` reads (`doctor.ts:3499`).
- Give it a `load` that returns one project and a `recipe` that resolves for it. That gives one `ok` filter.
- Assert the `recipe: resolves for every project` row is present and the recording `signedIn` ran exactly once.
- For "nothing else was spawned", the injected `gh`, `runtimes`, `sea`, `accounts` and `codexText` already cover the other spawning rows. Assert on the probe count only. Don't build a spawn guard; the ticket puts that out of scope.

### What checks it

`pnpm typecheck` and `HOME=/nonexistent pnpm test` check both edits. The PATH stand-in check in "Done when" is a manual run of the same unit suite, and it needs no integration test. A unit test can't watch the doctor path spawn for real, so the probe count is what pins it.
