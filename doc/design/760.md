## Design: #760, naming a typed check by its command

The ticket's line numbers are out of date. In this worktree `nameForCommand` is at `apps/cli/src/setup-build.ts:153-173`, `namedFromTyped` is at `:175-178`, `mergeRunActions` is at `:189-204`, and the write that replaces the name is at `:197`. Look these up again before editing.

### 1. The kept names are read before naming, so `askBuild` needs the file

Naming happens in `askBuild` (`--build` at `:399`, the typed list at `:446`). The file is read much later, in `askInstallAndBuild` at `:506` (`readRecipeKey(input.project, ['steps', 'build'], fileOptions)`), after the trial and the edit loop. So the seed set the ticket asks for cannot come from what the merge reads. It has to be read separately where the naming happens.

- **Read the raw key, the same one the merge reads.** That means `readRecipeKey(..., ['steps', 'build'], …)` and not `resolvedRunActions` (`:118-133`). `resolvedRunActions` resolves `extends:`, so it would offer preset-default names that `mergeRunActions(originalBuild ?? [], …)` (`:507`) never keeps. A `null` key means nothing is kept, so the seed starts empty. That matches the merge.
- **The kept names come from one helper both sides can call:** `keptNames(original: unknown[], wantedRuns: string[])`. It returns the `name` of every non-run action that has a string name, plus the name of every `isRunAction` entry whose `run` is `===` to one of `wantedRuns`. This is the same test as `:194`. Keep it beside `mergeRunActions` so the two cannot drift apart.
- **`namedFromTyped(commands, original)`** seeds `used` with `keptNames(original, commands)`. A command whose `run` matches a kept run entry takes that entry's name directly and does not go through `nameForCommand`. Otherwise it could take a `-2` name for itself and push a later command off its natural name, even though the merge would throw that name away.
- **At the merge, `:197` writes `name: item.name`, not `next!.name`.** After this change the two agree. The change still matters on the "keep this list? yes" path (`:426`), which returns `defaultList` names without calling `namedFromTyped`.

The edit loop calls `askBuild` again with no change to the file, so reading the key inside `askBuild` each time is correct. Do not cache it across `askInstallAndBuild`.

### 2. `nameForCommand`

- Remove the `index` parameter. Nothing uses it once the fallback is the command itself.
- Fallback: `command.trim().replace(/\s+/g, ' ')`. When that is longer than 40 characters, it becomes `.slice(0, 39) + '…'`. That makes the name exactly 40 characters (`…` is one UTF-16 unit), which is what the Done-when checks. Do not `trimEnd` before adding the `…`. A trailing space before it is acceptable, and trimming would break the "40-character" claim for some inputs.
- Replace `:` with `-` on `base`, from either the script rule or the fallback, **before** the uniqueness loop. Then `-2` is checked against the name that will actually be written. Leave the script regex (`/^[\w:.-]+$/`) alone: `fmt:check` should still pass it and come out as `fmt-check`, not fall through to the fallback.
- The schema refuses nothing else in a name. It checks only for `:` (`packages/recipe/src/recipe.ts:2450-2464`) and then uniqueness (0110 §9, the comment that follows), so spaces and `…` are legal. Add a test that resolves the written recipe for `uv run pytest` and for `pnpm fmt:check`. That is the unit-level proof that the name round-trips.

### 3. The setup page

At `packages/conductor/src/wizard-page.ts:361`, when `action.name === action.run`, the label is `action.run`. Compare exactly; do not normalise. A `run:` with doubled spaces will draw both, which is honest. The `id` at `:360` (`${step}.${i}:${action.name}`) is only compared as a string (`:491`, `:499`), so a name with spaces is safe there. Its assertion goes beside the existing label check at `packages/conductor/unit/wizard-page.test.ts:295`.
