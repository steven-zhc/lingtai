# Design note for #947: one `Bar`, and the home moves to the footer

## Where it goes

**`apps/board/src/app/bar.tsx`** is a new file. It exports `Bar({ project, here, children })`.

- It imports only React and `next/link`, the same rule `footer.tsx:7-8` states for itself.
- It renders `<div className="bar">`. Inside, in order:
  1. The brand, as a `<Link className="brand">` holding `<span className="mark" aria-hidden="true" />` and the word `Lingtai`.
  2. The children.
  3. `<nav className="topnav"><Link className="navlink">Report</Link></nav>`.
- **The mark goes on every page, not only `/`.** In the mock (`board-navigation.html`, both proposed views), the brand is `<a class="brand"><span class="mark" …></span>Lingtai</a>` on the home page and on `/report` alike. Today only `/` (`page.tsx:739-743`) and the not-set-up page (`not-set-up.tsx:27-31`) draw it.
- **The home page's brand becomes a link.** Today it is a `<span>` (`page.tsx:739`). The ticket says `Lingtai` is the link home on every bar.
- **`withProject` moves to `bar.tsx` and `footer.tsx` imports it from there.** It is currently private to `footer.tsx:18-19`. Do not write a second copy: the ticket's edge says the Report button follows "the same `withProject` rule the footer uses". Both the brand href and the Report href go through it.
- **`here?: 'report'`**: `/report` passes it, and the Report link then gets `className="navlink on"` and `aria-current="page"`. The mock's `/report` view draws `<a class="navlink on">Report</a>`. No other page passes `here`.

## Report is pushed right by its own auto margin, so the rail loses its own

`.bar .rail` has `margin-left: auto` today (`globals.css:150-153`). That is how the home page's rail reaches the right edge. If `.topnav` also has `margin-left: auto`, the two auto margins split the free space and the rail ends up floating in the middle of the bar.

The mock puts the rail straight after the filter's separator, then `<span class="grow">`, then `.topnav`. So:
- drop `margin-left: auto` from `.bar .rail`;
- put `margin-left: auto` on `.bar .topnav`.

Keep the rail a single `span`. The comment at `page.tsx:752-757` explains why: a narrow window should break between the filters and the rail. Report stays the last child, so it wraps last.

Style `.navlink` from the mock's `.topnav`/`.navlink` rules, and check it by eye against `?v=c` and `?v=report`. `globals.css` has neither class today.

## Each page's `project`

Each page passes what its brand href and its `FooterFetched` already pass. This is not a new decision per page:
- `/report`, `/spend`, `/landed`: `only` (`report/page.tsx:95`, `landed/page.tsx:56`, `spend/page.tsx:142`).
- recipe page: `view.project` (`recipe/[project]/page.tsx:158`).
- task page: `task.ticket?.project ?? undefined` (`task/[id]/layout.tsx:228`).
- `/`: `only`.
- `/backlog`: `undefined`, because its footer gets `undefined` today (`backlog/page.tsx:122`).
- `/setup/*` and not-set-up: `undefined`.

## The home reaches the footer as data

- **`FooterReading`** (`lib/footer.ts:24`) gains `home: { path: string; shown: string }`.
- **`loadFooter`** (`lib/footer.ts:39`) fills it from `theHome()`. `lib/footer.ts` is already server-only (it imports `@lingtai/projector`, line 9), so importing `@/lib/home` there is safe. `/api/footer` sends it as plain JSON.
- **`FooterFetched`** (`footer-fetched.tsx:38`) passes `state.reading.home` through. The `asking` and `failed` branches draw no home, as the ticket's edge says.
- **`Footer`** takes `home` as a **required** prop. That keeps #767's posture, as quoted at `setup/terminal.tsx:35`: *"Required, so a page that draws this bar cannot forget the home"*. It draws the home as its last child, after `.links`. `.links` already has `margin-left: auto` (`globals.css:174`), so links and home sit together at the right end. Use the mock's markup:

  ```tsx
  <span className="home-at mono" title={`${path} — the Lingtai home this board reads`}>
    home <b>{shown}</b>
  </span>
  ```

  Copy `.footer .home-at` and `.footer .home-at b` from the mock into `globals.css`. Leave the footer's own size and links alone (#950).
- **The home page** passes `home={theHome()}` to its `<Footer>` (`page.tsx:724`).

## What becomes dead, and goes

- **`app/home.tsx`**: its only uses are the ten brands (`git grep -n '<Home'`). Delete it.
- **The `.bar .brand .home` rule** (`globals.css:3152-3157`). Delete it.
- **`TerminalScreen`'s `home` prop** (`setup/terminal.tsx:31-36`): it is used only inside the bar. Remove it, and the `theHome()` calls that fed it at `setup/repository/page.tsx:26` and `setup/wizard/page.tsx:16`.
- **`theHome` imports** on every page that used it only for `<Home>`. `oxlint` reports unused imports, and `pnpm lint` is in `build`.
- **`NotSetUp` keeps its `home` prop**: the body still uses it (`not-set-up.tsx:40`).

## Tests that move with it

- **`unit/not-set-up.test.tsx:27-38`**, *"names the home … inside the brand"*: its last assertion, `/class="brand"[^]*~\/lingtai-trial\/a…/`, has to go. The home is no longer in the brand. The `Nothing is set up in ~/lingtai-trial/a.` assertion above it remains the claim.
- **The import guard at `not-set-up.test.tsx:72-79`** lists `'../src/app/home.tsx'`. Replace that entry with `'../src/app/bar.tsx'` and `'../src/app/footer.tsx'`. The footer is in the `"use client"` graph through `FooterFetched`, and the Bar must stay importable the same way. The guard's regex already allows `import type` (line 77), which is all `footer.tsx` takes from `@/lib`.
- **`unit/footer-fetched.test.tsx`**: its `FooterReading` fixtures need a `home`. Add one assertion that the read state draws `home <shown>` with the path in its title, and one that the failed state does not.
- **New `unit/bar.test.tsx`**, using `renderToStaticMarkup` as `not-set-up.test.tsx` does. It checks:
  - the brand links to `/` with no project and to `/?project=a%20b` with one;
  - Report links to `/report` and to `/report?project=…`;
  - no `←` anywhere in the output;
  - children render between the brand and `.topnav`;
  - `here="report"` gives `aria-current="page"`.

  Do not snapshot any page.

Nothing here depends on the log or on `pnpm test:integration`. The Next build (`apps/release/integration/build.test.ts`) is the only check that would see a server import reaching the client graph through `footer.tsx` or `bar.tsx`, and it runs after the merge. The import-guard entries above are the unit-level claim standing in for it.
