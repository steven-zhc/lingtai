# #791: the shape of the change

## What the ticket leaves for the implementer to find

1. **0120 §1's single reading of an action's result is decided but not built.** `2cedd8c6` wrote the rule into `doc/decisions/0120-a-reason-is-a-type.md:253` (*"is one function, used by the gates, the approval's list of unpassed steps, the board and `task_view` alike"*). No exported function in `@lingtai/domain` does it today. There are two private readings, and they disagree with each other and with the ADR's table:
   - `read-model.ts:158` `verdictOf` reads `design` `AnswerUnreadable` as `did-not-finish`, where the ADR says `failed`. It also reads a requested signoff as `pending`, where the ADR says `asked`.
   - `run.ts:197` `stepStateOf` reads `commit` `Completed{head:null, question:null}` as `passed`, and `worktree` `NotDone` as `failed`. The ADR says `did-not-finish` for both.

2. **The raw `ActionResult.verdict` is not that reading, and keying status off it gets the ticket's own counter-examples wrong.** `ActionVerdict` is `'passed' | 'failed' | 'needs-approval' | 'never-ran' | 'did-not-finish' | 'waived'` (`actions/src/action.ts:87`). An agent that asked a question comes back as `did-not-finish` with `because === NEEDS_INPUT`. Only `commitResultOf` turns that into `Completed{question}` (`conductor/src/step-outcome.ts:195-197`). A span that read `verdict === 'did-not-finish'` would mark an `InputNeeded` as `ERROR`.

3. **A judge is not an action in `runActionPipeline`.** `routeProposal` records the `proposed` visit directly (`pass.ts:1301`, `:1365`, `:1387`, all with `results: []`). The judge is reached through `replyFor` (`proposed-route.ts:151`). A runtime judge that crashed never reaches `replyFor` as a failure: `askTheAgent` turns `outcome.failure` into `held(…)` (`conduct.ts:2725-2733`), which `replyFor` cannot tell apart from a judge that chose to wait. So the judge's status can only be read inside `askTheAgent`.

4. **`runOnce` never fails in its error channel.** Its type is `Effect<RunOnceResult, never, …>` (`conduct.ts:668`). It does `Effect.die` on a store that refused an append (`conduct.ts:4116`), and otherwise returns a result with a `stage`. So:
   - `Effect.withSpan`'s own status cannot express "a child was `ERROR`".
   - On a die, Effect's tracer writes a status message from the cause, which the ticket forbids.
   - As I remember `@effect/opentelemetry`, a successful exit sets status `OK` when the span ends, which would overwrite an `ERROR` set earlier. **Check this in the installed package** before relying on it either way. The design below works whichever way it goes.

## The shape

### `@lingtai/domain`: build the reading

Add `readingOf(action: Action)` to `packages/domain/src/action.ts`. It answers `passed | failed | did-not-finish | asked | never-ran | waived | not-reached`, following 0120 §1's table and including the four "cautious" rows. Unit-test it cell by cell.

**Do not move `verdictOf` or `stepStateOf` onto it in this ticket.** That changes what the board shows, which is a separate change. Name the divergence in the commit body so it can become a backlog entry.

### Spans and their status

| span | opened at | `ERROR` when |
|---|---|---|
| `action <kind>` | around `action.run` in `runActionPipeline` (`action.ts:811`). No span for `waived` (it never ran) or `NotReached` | the reading is `failed`, `did-not-finish` or `never-ran` |
| `step <name>` | `pass.ts:1484`, ended after the `StepEnded` emit at `:1500`, or after `record()` when no `StepEnded` is written | any action in `reached.outcome` reads `ERROR`, or the emit threw |
| `step proposed` | around each `routeProposal` call (`pass.ts:1558`, `:1599`) | its `action judge` child is `ERROR` |
| `action judge` | in `askTheAgent` (`conduct.ts:2603`), runtime judges only; a built-in spends nothing and is not an action | `outcome.failure` of any kind, including `never-started`, or the `unreadable` return |
| `step claim` | around the `claimStep` call (`conduct.ts:4111`) | same rule as any step |
| `step end` | the `end` step's actions | same rule as any step |

**Action spans need a hook, because of the package direction.** The action span needs the domain `Action`, which comes from `actionOf` in conductor (`step-outcome.ts:81`), and `@lingtai/actions` cannot import conductor. So `runActionPipeline` takes an optional `PipelineOptions.isError?(action, entry) => boolean`. `pass.ts:1877` (the only call site of `runActionPipeline` I found) passes `(a, e) => errorReading(readingOf(actionOf(a, e, onSha)))`. With no hook, the span's status stays unset.

**Step spans use the same predicate.** A step's status comes from `reached.outcome.actions` — the `StepOutcome` that `outcomeOf` built and `StepEnded` carries — through the same `errorReading`. Two code paths, one predicate, so they cannot drift apart.

**The run's status is collected, not read back from the spans.** The OTel API cannot read a span's children. Instead:
- `runOnce` puts a per-run sink in the OTel context under a `createContextKey`.
- Every step or action span that ends `ERROR` marks the sink.
- `conductor.run` is `ERROR` iff the sink was marked, or the stage is `unexpected`.

The sink rides the same `AsyncLocalStorage` chain as the parent links, so two passes at once (0122) never share one. It is never a module global. The test for *"reads only children + `unexpected`"* can drive a held pass and a crashed-agent pass that both have `ok: false`, and assert different statuses.

### Joining the Effect spans to the promise code

**One provider for both kinds of span.** Install the global `TracerProvider` and `AsyncLocalStorageContextManager` the way the board does (`apps/board/src/lib/telemetry.ts:66-72`). Give Effect `@effect/opentelemetry`'s global-tracer layer — I believe it is `Tracer.layerGlobal`; check the name. Then `Effect.withSpan` and `trace.getTracer('lingtai-conductor')` write to the same provider. Do not use a second `NodeSdk` provider.

**Crossing into `runPass` and `claimStep`.** Conductor gets an optional service, read with `Effect.serviceOption`, that runs a promise thunk inside `context.with(trace.setSpan(context.active(), otelSpan), thunk)`. The host's tracing layer provides it, using `Tracer.currentOtelSpan`. When the service is absent, the thunk runs as is. This keeps `@effect/opentelemetry` out of conductor's static imports.
- Conductor imports only `@opentelemetry/api`, statically. It is a no-op without a registered provider; the board does the same at `telemetry.ts:2`.
- `runOnce`'s requirements stay `Repo | AgentHost`.

### The host edge: `apps/cli/src/telemetry.ts`

- Mirror the board's `installTracing`. Read the endpoint with `machineOtlpEndpoint` (`env/src/index.ts:860`). Import the SDK, the exporter and `@effect/opentelemetry` dynamically, behind that check.
- Accept an injected exporter, so a test opens no socket.
- `resource` sets `service.name: lingtai-conductor`, which keeps `unknown_service:<argv0>` (a local path) from leaving the machine.
- **Enforce the attribute and status rules in one span processor, not at each call site.** It must:
  - forward only spans whose names match the five patterns above;
  - drop every attribute except `lingtai.ticket`, `lingtai.round` and `lingtai.index`;
  - drop events and any status message;
  - re-impose the sink's verdict on `conductor.run`.

  `@effect/platform` or anything else Effect instruments would otherwise export URLs. This is the board's `OnlyScope` (`telemetry.ts:24-42`) taken one step further. Changing the status from a processor depends on `onEnding` running before the span is sealed: check `sdk-trace-base`'s `Span.end` before relying on it. If it does not, set the `conductor.run` status from inside the Effect after the pass returns, and test whether Effect's exit overwrites it.
- Install the layer beside `PortsLive` at every edge the ticket lists.
- Flush at the drain and at `lingtai run`'s exit, using `Promise.race` against a timeout of about 3 seconds. A flush that is lost is dropped, never awaited.

## Edges the ticket leaves open (decided here)

- **A `StepEnded` append that throws:** end the step span `ERROR` in a `finally`, mark the sink, and rethrow. A span that is never ended is never exported, and a missing span here would hide exactly the failure it is meant to show.
- **A judge asked twice in one pass** (two `routeProposal`s): two `step proposed` spans, each with its own judge child.
- **`lingtai.round` on `claim`, `end` and `proposed`:** leave it off; the ticket's table gives none.

## Checks

Everything in this design is unit-level:
- `BasicTracerProvider` with an `InMemorySpanExporter` and the context manager, around `conduct-a-whole-pass.test.ts`'s fakes;
- the no-endpoint import check, modelled on the board's `apps/board/unit/telemetry.test.ts`.

Register the global provider and context manager once per test file, and `reset` the exporter between cases.

Add `@opentelemetry/api` to conductor's dependencies. Add `@opentelemetry/api` to actions only for the hook's span calls; if actions is handed a tracer instead, it needs nothing. Add `sdk-trace-base` and `context-async-hooks` as conductor devDependencies.

The release binary's bundling of the dynamic imports is only seen by `apps/release/integration/build.test.ts`, after the merge, so nothing in this ticket can check it.
