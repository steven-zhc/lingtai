**Design note: #791, a pass as one OTLP trace**

The ticket describes the spans. This note covers four things it does not: why the trace would still come apart, why the Effect spans and the `@opentelemetry/api` spans have to share one provider, the cleanup the attribute and status rules need, and where each span goes.

## 1. One provider, registered globally, with Effect reading from it

The ticket puts two kinds of span in one trace. `runOnce` and `runQueue` use `Effect.withSpan`. `pass.ts` and `action.ts` stay promises and use `@opentelemetry/api`. Those `api` spans go to whatever provider is registered globally. If the Effect side gets its own provider, from `@effect/opentelemetry`'s `NodeSdk.layer`, the two halves export separately, and the `api` side gets no provider at all: no step or action span would ever be recorded.

So build **one** `BasicTracerProvider`, the way the board does (`apps/board/src/lib/telemetry.ts:62-73`):

- register it with `trace.setGlobalTracerProvider`;
- register `context.setGlobalContextManager(new AsyncLocalStorageContextManager().enable())`;
- give Effect `@effect/opentelemetry`'s `Tracer.layerGlobal`. As I recall it, that needs a `Resource` layer for `lingtai-conductor`. Check that against the version you install, which must be the 0.x line that pairs with `effect@3.22.1` (the version in `packages/conductor/package.json`).

The service name that gets exported is the one on the **provider's** resource. Copy the board's comment about why the resource is given explicitly: the default `unknown_service:<argv0>` is a path.

**Put the installer in `packages/conductor/src/telemetry.ts`, not in `apps/cli`.** Two reasons:

- The Done-when test is a conductor unit test built on `packages/conductor/test/one-pass.ts`'s `once`, and it needs the same installer with an in-memory exporter injected. The board does this with its `exporter?` parameter (`telemetry.ts:56`).
- Both hosts are in `apps/cli` and can import it from `@lingtai/conductor`.

Its shape: `installTracing(env, file, exporter?) → { layer, flush } | undefined`. Every SDK module is imported dynamically behind `machineOtlpEndpoint` (`packages/env/src/index.ts:860`). That includes `@effect/opentelemetry`, so no host file imports it statically.

**Install once per process, at the command entry, and keep the layer cheap.** The daemon provides layers per pass at `apps/cli/src/conduct.ts:373`, `:418`, `:486` and `:515`, and `lingtai run` at `run.ts:291` and `:671`. A provider built inside that `Layer` would be created and shut down on every pass. So:

- the provider lives for the whole process;
- the `Layer` only points at the global provider;
- each of those six sites becomes `Effect.provide(Layer.merge(PortsLive, tracing))`, with `Layer.empty` when the endpoint is unset.

Static imports: `@opentelemetry/api` goes into `packages/conductor` and `packages/actions` (today only `apps/board` has it, `apps/board/package.json:25`). It is a no-op until a provider is registered, so the "nothing is loaded" rule is about the SDK, the exporter and `@effect/opentelemetry`, not about the `api`. The no-endpoint test follows `apps/board/unit/telemetry.test.ts`.

## 2. Carrying the parent into the promise code

`claimStep` (`conduct.ts:4111`) and `runPass` (`conduct.ts:4173`) are both entered through `Effect.promise`. Both need the run span as their active OTel context; otherwise `step claim` comes out as a root of its own.

Use one helper in conductor for both. It reads `Effect.currentSpan`, wrapped in `Effect.option` because it fails when no span is active. If there is a span, it runs the thunk inside `context.with(trace.setSpan(context.active(), …), thunk)`.

To build the OTel span I recommend `trace.wrapSpanContext({ traceId, spanId, traceFlags: 1 })` from the Effect span's own ids, rather than `@effect/opentelemetry`'s `Tracer.currentOtelSpan`. It keeps `@effect/opentelemetry` out of conductor's static imports. It also stays harmless when nothing is installed: no provider means non-recording spans. The Done-when parent-link test checks that the ids match. If they don't with the installed version, fall back to `currentOtelSpan`, imported dynamically. Wrap any other `Effect.promise` in `runOnce` that reaches `runStep` the same way; `grep 'Effect.promise('` in `runOnce`'s body is the check.

**Concurrent passes (0122) lose the tracer today, and this is the trap.** With slots set, `runQueue` starts each pass with a nested `Effect.runPromise(runOnce(...).pipe(Effect.provide(context!)))` (`schedule.ts:264-281`). That `context` is `Effect.context<Repo | AgentHost>()` (`schedule.ts:167`), which holds only services. The tracer set by the layer does not cross into the new root fiber. Every concurrent `conductor.run` would go to Effect's built-in tracer and never export, while its `api` step spans still export, as roots.

Fix: capture `Effect.runtime<Repo | AgentHost>()` and launch with `Runtime.runPromise(rt)(…)`. The serial path at `schedule.ts:326` (`yield* runOnce`) already inherits the tracer. 0101 §6 already forbids a `runPromise` nested in an Effect for exactly this reason: it "loses the caller's scope, its interruption and its span". So this brings the code into line with the ADR. Turning the slots path into a proper fiber fork is #790's job.

**`conductor.run` is a root**: `Effect.withSpan('conductor.run', { root: true, … })`. `runQueue` calls `runOnce` (`schedule.ts:265` and `:326`), and the ticket says every pass is *one* trace with the run as its root. Nested under `conductor.queue`, a whole queue pass would become one trace. `conductor.queue` is then its own short trace covering discovery and selection.

## 3. Scrub at export, not only at the call sites

Wrap the injected or OTLP exporter in a scrubbing `SpanExporter`. It sits inside the installer, so the test's in-memory exporter sits behind it too. Before calling the inner exporter it:

- drops any span whose name is not `conductor.queue`, `conductor.run`, `step <name>` or `action <kind>`;
- keeps only the `lingtai.ticket`, `lingtai.round` and `lingtai.index` attributes;
- removes every event;
- keeps status `ERROR` but with no message.

The ticket's rules cannot hold by call-site discipline alone, because Effect adds things you didn't write:

- **`code.stacktrace`.** `Effect.withSpan` captures its call site, and as I recall `@effect/opentelemetry` exports it as a `code.stacktrace` attribute, which is a file path. Also pass `captureStackTrace: false` at both `withSpan` sites.
- **Failure detail.** On a failed exit, `@effect/opentelemetry` writes the cause into the status message and/or an exception event. `runOnce` dies at `conduct.ts:4116` (`Effect.die(unappended)`), whose message is free text.

Because the scrubber runs inside the installer, Done-when items 2 and 3 test it directly. The trade-off: a span dropped by name would leave its children pointing at a missing parent. No `Effect.withSpan` exists in any package's `src` today, so nothing falls between run and step now. Once #790 adds spans for git, GitHub and the store, it adds their names to this allowlist.

## 4. Where the step and action spans go

**Step spans go in `runStep` (`pass.ts:1819`), not around the `while` loop.** `runStep` is the one function every step goes through: `claim` (`pass.ts:1664`), each spine visit (`:1489`) and `end` (`:1640`). So one site produces `step claim`, `step <name>` and `step end`. That answers the ticket's question about where `end` runs: `resolveEndActions` only chooses the actions, and they run in `runStep(SPEC.end, …)`.

- Name: `step ${spec.step}`. `lingtai.round`: `reaching.context.round ?? 0`, the same expression `StepStarted` uses (`pass.ts:1486`).
- The routing arrival at `proposed` is built by `routeProposal`'s `record()` and never reaches `runStep` (comment at `pass.ts:1478-1482`). It gets no span, and that is correct: no action runs there.
- Run the rest of `runStep` inside `context.with(trace.setSpan(…))` so the pipeline sees the step as its parent.
- Status `ERROR` when the step reports a refusal or a failure, or its body throws. End the span in a `finally`.

**Action spans go in `runActionPipeline`, around `action.run` only** (`action.ts:811`).

- Name: `action ${action.kind}`, never `action.name`. A recipe author writes the name, and it can be the command itself.
- `lingtai.index`: the `index` from `actions.entries()` (`action.ts:760`).
- A waived entry `continue`s before `run` (`action.ts:762-774`), so it gets no span.
- `ERROR` when `result.verdict === 'failed'`, which already includes the `catch` at `action.ts:812-819`.
- Use `trace.getTracer('lingtai-conductor')`, and use the same tracer name in `pass.ts`.

## 5. Shutdown

`flush` is `Promise.race([provider.forceFlush(), timeout(3000)])`, and a timeout is swallowed. Call it:

- in the daemon after `await started.daemon.stopped` (`apps/cli/src/daemon.ts:692`);
- at the end of `lingtai run`.

Do not call it on the `stopNow` path (second signal, `daemon.ts:687`). That path promises to stop now, and losing those spans is the ticket's "killed mid-pass" case.

## 6. The test and how to check the work

- **Shared global state.** `trace.setGlobalTracerProvider` and the context manager can each be set only once per process. Install them once in `beforeAll` of the new test file and call `trace.disable()` and `context.disable()` in `afterAll`.
- **Flushing.** Use `BatchSpanProcessor` as production does and call `flush` before asserting, or `SimpleSpanProcessor` in the test only. Either way, the scrubbing wrapper must be in the path.
- **The failing-action case.** `refusingRuntime` in `one-pass.ts:514` already gives you one.
- **The command-text assertion.** Use a recipe whose `run:` command is a distinctive string, and assert that it never appears in any exported span.
- **Checks.** Everything here is checked by `pnpm test` and `pnpm typecheck`. The only check out of reach is that the dynamic SDK imports survive the release bundle (`apps/release/integration/build.test.ts`), which runs after the merge. The no-endpoint unit test is what stands in for it before the merge.

The daemon picks this up only after `lingtai restart`. Nothing in this design contradicts 0101 §6: the `api` spans are the stopgap the ticket names, and #790 replaces them.
