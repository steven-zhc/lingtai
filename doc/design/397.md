# Design: #397, install and build detected from the repository

## What this ticket builds, and what it does not wire

**Nothing calls the new code from `init` or `add` in this ticket.** Neither command has a project step yet. `init` asks the store, then the agent, App and board (`apps/cli/src/init.ts:5-9`). `add` takes a slug and nothing else (`apps/cli/src/lingtai.ts:362-376`). The first project is #394, and putting the questions in order inside `init`/`add` is #400 (#330: *"#400 `init` and `add` run as one flow … (after #393, #394, #396–#399)"*). #397 is blocked only by #392 and #395, so it delivers:

- `apps/cli/src/detect-setup.ts`: the detector. It is pure, and it reads through a small reader interface.
- `apps/cli/src/setup-build.ts`: the two questions on `question()`, the optional trial run, and the `RecipeChange[]` they produce.
- `apps/cli/unit/detect-setup.test.ts` and `apps/cli/unit/setup-build.test.ts`.

**Do not add `--install`/`--build` to either flag parser yet.** `init`'s `parseArgs` accepts only `--store`, `--database-url` and `--port` and refuses anything else by name (`init.ts:214-224`). A flag it accepted and then ignored would be the failure `lingtai.ts:336-340` warns about: *"a flag that reads as ignored is the one kind that is worse than a flag that errors"*. Both parsers are also last-wins (`init.ts:221`, `lingtai.ts:349-353`), so a repeatable `--build` has to be collected as a list by whoever wires it. This ticket's function takes the flags already parsed: `install: string | null`, `build: string[] | null`. #400 owns the parsing.

## Reuse `propose.ts`'s knowledge, not its function

`packages/recipe/src/propose.ts` already detects a package manager from the lockfile (`:207-213`) and picks check scripts (`:95-118`, `:237-290`). It is the board wizard's fast lane (#161). Do not call it, for three reasons:

- It reads only GitHub, through `request` and a tree listing (`:136-162`), and it builds a whole `Recipe`.
- It joins the picked checks into one `build` action with `&&` (`:290`). The ticket wants one named action per check.
- Its ranking is typecheck, lint, test (`checkRank`, `:113-118`). The ticket wants format check, lint, typecheck, test.
- Its `CHECK` regex picks `test:[\w:.-]+` (`:95`), which **picks `test:integration`**. That is exactly the script this ticket must refuse to suggest.

Leave `propose.ts` alone, since the board still calls it until #401. Copy two things from it:

- `runFor`'s per-manager spelling (`:372-377`): `pnpm x`, `yarn x`, `npm run x`.
- `NEEDS_A_WORLD` (`:102`), which skips a script whose *command* drives a browser even when its name doesn't say `e2e`.

## The detector

```ts
interface SetupReader {
  has(path: string): Promise<boolean>
  read(path: string): Promise<string | null>
}

interface DetectedSetup {
  install: { run: string; because: string } | null      // because: "pnpm-lock.yaml is at the root"
  build: { name: string; run: string; because: string }[]
  skipped: { script: string; why: string }[]
  notes: string[]                                       // "no lockfile at the root", "package.json does not parse"
}

detectSetup(reader: SetupReader): Promise<DetectedSetup>
```

**`has` is separate from `read`, and the GitHub reader must not build `has` on `fileAt`.** `fileAt` returns null when the API's `content` is empty (`packages/github/src/client.ts:415`). The contents API leaves `content` empty for a file between 1 and 100 MB, and a monorepo's `pnpm-lock.yaml` is often that size. On `fileAt` alone, the biggest lockfiles would look absent. The GitHub `has` is therefore a `GET /repos/{o}/{r}/contents/{path}?ref=<default branch>` through `client.request`, where 404 means false and anything else means true. The GitHub `read` is `fileAt`, used only for `package.json`.

The local reader reads files under the directory the person named. Detection only produces suggestions. The trial run below is what checks the base.

**The rules:**

- **Install comes from the root lockfile, in the ticket's table.** Check `pnpm-lock.yaml`, then `yarn.lock`, then `package-lock.json`, and take the first one found.
  - If more than one is present, still take the first and put the others in `notes`.
  - If there is no lockfile, `install` is null, with the note *no lockfile at the root*. Do **not** fall back to `npm install` because a `package.json` exists, the way `propose.ts:211` does. The ticket says an unrecognised setup gets an empty default and a question, not a guess.
- **Build comes only from the root `package.json`'s scripts, in a fixed order:**

  | Order | Script | Action name |
  |---|---|---|
  | 1 | `fmt:check`, or `format:check` if there is no `fmt:check` | `format` |
  | 2 | `lint` | `lint` |
  | 3 | `typecheck` | `typecheck` |
  | 4 | `test` | `test` |

  - The action names match the ones the conducting machine's own recipe already uses for this repository (`format`, `lint`).
  - The command is spelled with `runFor`'s rule for the lockfile's manager, or `npm run` when there is none.
  - `because` names the script and what it runs: *"`test` runs `vitest run --project unit`"*.
- **Skipped, with reasons:**
  - Any root script whose name matches `/integration|e2e/i` goes into `skipped`, with the 803-second reason from CLAUDE.md: *integration tests do not fit inside a pass*.
  - A *candidate* (e.g. `test`) whose command matches `/integration|e2e/i` or `NEEDS_A_WORLD` is skipped too, not suggested, with the reason naming what it runs.

  On this repository, that leaves `test:integration` and `test:db` in `skipped`. `test:db` is caught because its command is `pnpm test:integration`. `test:all` is not a candidate and not skipped. Its command is `vitest run`, and nothing in the name or command says integration. Leaving it out of `skipped` is correct, because the skip list is about what was *not suggested for a reason*, and `test:all` was never a candidate.
- **Nested `package.json` files are not read.** If the root has none, add a note, and the build default is empty.

## The questions

```ts
askInstallAndBuild(world: SetupWorld, input: {
  project: string
  reader: SetupReader
  given: { install: string | null; build: string[] | null; check: 'yes' | 'no' | null }
  tryBuild: ((install: string | null, build: string[]) => Promise<TrialResult[]>) | null
  files?: RecipeFiles                 // for readRecipeKey, as #395's tests do
}): Promise<{ changes: RecipeChange[] } | { refused: string }>
```

### Decisions

**1. Return changes, and let the caller write them.** #395 settled this (`doc/design/395.md`, *"a new file is written once"*): `setRecipe` refuses to *create* a file from `steps.*` alone, because a recipe needs `repo.base`, `source.kinds` and `env` before it resolves. On a first run, #400 will collect answers and write them once. On an existing file, the caller writes immediately. Both are the caller's choice only if this function returns `RecipeChange[]` (`emit.ts:64`) and does not call `setRecipe` itself. This is #392's decision 1 one level up: *"The seam writes nothing."* Your test for *"the questions write `steps.prepared` and `steps.build`"* hands the returned changes to `setRecipe` with a `Map`-backed `RecipeFiles` on an inline fixture that already resolves. That is the same pattern as `packages/recipe/unit/write.test.ts`.

**2. Print first, then ask.** Before either question, log every `because`, every `skipped` entry with its `why`, and every note. This is the ticket's *"print what was found and why"*. It is printed whether the answer comes from a flag or a terminal.

**3. Install is one `question()` call.**

| Argument | Value |
|---|---|
| `name` | `the install command` |
| `flag` | `--install <command>, or --install none` |
| `given` | `given.install` |
| `current` | the `run` of the file's own `run:` action at `steps.prepared`, via `readRecipeKey(project, ['steps','prepared'])` |
| `detected` | `detected.install?.run` |
| `fallback` | `''` |

- **`none` is the explicit empty answer**, both as a flag and when typed. An empty typed answer takes the default (`question.ts:70`), so without `none` a person shown a detected default could never answer "no install". `none` writes no `run:` action. #398 uses `--reviewer none` the same way.
- **If the answer is `''` with no default**, it is refused by the seam's `validate` (*"type a command, or none"*). An empty answer must not be read as a choice nobody made.

**4. Build is a list, and the seam returns one string, so ask it in two shapes.** Do not pack a list into one string with `&&` or `;` and split it afterwards: `cd web && pnpm test` would split into two broken actions.

- **`given.build !== null`:** the list is the answer, and nothing is asked. `['none']` means no build actions. If `none` appears beside other values, refuse by name.
- **A default exists** (current, otherwise detected): ask one question.
  - Prompt: *"Run these before review? yes, or no to write your own"*.
  - `choices: ['yes', 'no']`, `fallback: 'yes'`, flag `--build <command> (repeatable), or --build none`.
  - `yes` takes the default list, which is the one-keystroke path.
- **No default, or `no`:** loop on `question()`.
  - Prompt: *"A command that must pass before review — empty when done"*, `fallback: ''`, with no `validate` refusing `''`.
  - An empty answer ends the list. An empty list is a real answer: log *nothing will check a diff before review* and return it.
- **With no terminal and no flag**, the first `question()` refuses (`question.ts:69`), and that refusal is returned unchanged. This is the ticket's *"asked, not given a guess"*.

**5. Pressing enter on a re-run writes nothing.**

- If the accepted list equals the `run` strings of the file's current `run:` actions, return **the file's own action objects unchanged**, not ones rebuilt from strings.
- The conducting machine's recipe has `timeout: 5m` and `env: []` on its build actions. Rebuilding from `run` would drop them, and `setRecipe` would then report `written: true` on what was a no-op.
- Actions at `steps.prepared`/`steps.build` that are not `run:` actions keep their positions. Only the `run:` entries are replaced.

**6. New actions are `{ name, run }` and nothing else.**

- `timeout` and `env` take the schema's defaults (`recipe.ts:111-113`).
- A typed command's name is the script it invokes, when it has the shape `<pm> [run] <script>`. Otherwise, use `check-<n>`.
- Names are de-duplicated within the step. No resolver refusal enforces unique names, which is why this has to be done here.

**7. Nothing to remove at `proposed`.** The `pnpm-workspace` preset declares its check at `build:` (`b21b89ea`), so the person's build answer replaces it, and a declined build leaves `build: []` with nothing left over at `proposed:`. An earlier version of this ticket stripped the preset's `proposed` check from outside, and every fix round found another path it missed. A `proposed:` the file wrote itself is never touched; that is #399's step.

## The trial run

The ticket asks for it, and #390 is the reason: a check added to `build` that is already red on the base fails every ticket.

- **It is a question too, so it has a flag.**

  | Argument | Value |
  |---|---|
  | `name` | `the trial run` |
  | `flag` | `--check-build yes, or --check-build no` |
  | `choices` | `['yes', 'no']` |
  | `fallback` | `'yes'` |

  Ask it only when the build list is non-empty and `tryBuild` is not null.
- **`tryBuild` is injected.** The unit tests pass a fake. It is null when there is nothing to run it in. For GitHub, that means #400 has no installation token at hand. In that case, log *"not run — no checkout on this machine; the first pass's `build` is where these first run"* rather than skipping it silently.
- **What the real `tryBuild` does** (it lives with the wiring, not in `unit/`):
  - Cut a scratch worktree with `provisionWorktree` (`packages/repo/src/worktree.ts:118`). Use a `runId` such as `setup-<timestamp>` and `remote:` set to the same remote the pass will clone (`repo.remote` for a local project, #351). The scratch tree is then the **base** as the pass sees it, not the person's dirty checkout.
  - Run the install, then each build command, through `runCommand` (`packages/actions/src/command.ts:226`) with `runnableEnv({})` as the whole environment. That is the same six names a `run:` action gets with `env: []` (`command.ts:79-84`, 0037 §1). **Keep going after a failure**, so every red command is reported, not just the first.
  - Remove the worktree with `removeWorktree` (`worktree.ts:189`).
  - This spends no money, so #330's *"Nothing that spends money runs inside `init`"* holds. It can take minutes, so say so before starting.
- **What a failure does:** print each failing command with its `evidence` tail (`CommandOutcome.evidence`, `command.ts:57`), then ask again: *"Write them anyway, or edit the list?"* with `choices: ['write', 'edit']`, `fallback: 'edit'`, flag `--check-build no` to skip the trial.
  - With no terminal, `--check-build yes` and a red result is a **refusal**, not a write. A flag is never re-asked (`question.ts:53-58`), and writing a check the person was just shown is red is what #390 is about.

The real `tryBuild` spawns `git` and package managers, which makes it integration under 0060 §1. **Nothing in this ticket runs it before the merge.** What stands in for it at unit level is the fake: it returns `{ command, ok, evidence }[]`, and the tests assert that a red result is printed and blocks a flag-only write.

## Unit tests

**`detect-setup.test.ts`** uses an in-memory `SetupReader` over a `Map`:

- Each lockfile gives its install command.
- With two lockfiles, the first in the table wins and the other is noted.
- No lockfile gives `install: null` and the note.
- All four scripts come out in format → lint → typecheck → test order with the right manager's spelling.
- Only `format:check` gives a `format` action.
- No `package.json` gives an empty build and a note.
- `test:integration`, `test:e2e` and a `test` whose command runs `playwright` are each in `skipped` with a reason, and none is in `build`.
- This repository's own scripts, inlined, give `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `pnpm test`, with `test:integration` and `test:db` skipped.
- A `has` that is true while `read` returns null still detects the lockfile. That is the large-lockfile case.

**`setup-build.test.ts`** uses a fake world (scripted `ask`, null when the script is empty, as `question.test.ts` does):

- Flags only produce changes that `setRecipe` writes as named `run:` actions at `steps.prepared` and `steps.build`, and the result resolves.
- `--install none` / `--build none` write no `run:` actions.
- No TTY and no flags give `{ refused }` naming `--install`.
- `yes` takes the detected list.
- A re-run where enter is pressed on a fixture with `timeout: 5m` gives `written: false`.
- An inline recipe that `extends: pnpm-workspace` ends with the answered build at `build:` and nothing at `proposed`.
- A red fake `tryBuild` under `--check-build yes` refuses and returns no changes.

All of this is `pnpm test`. Nothing here needs `pnpm test:integration`.
