## Design note for #1391: the PR owner answers "which PR is open" and "which stream is the draft's"

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

### Where the rule lives

The rule goes in one pure function. `packages/domain/src/pr.ts` gets `openAmong(prs: readonly PrState[]): PrState | null` beside `isOpen` (`packages/domain/src/pr.ts:555`). It takes the highest-numbered PR whose `status !== 'draft'` and returns it if `isOpen` says so, otherwise null.

The three readers the ticket asks for live in `packages/project/src/pr.ts`. Each is one `listPrs` (`:82-92`) followed by a pure pick:

- `openPr` is `listPrs` → `openAmong`.
- `draftTarget` takes the last PR of the list. It returns that PR when its status is `draft` or `requested`, and `{ n: last.n + 1, version: 0, state: null }` otherwise. For no PR at all that is n 1.
- `readDraft` returns `last.draft` when the last PR is in `draft`, and `[]` otherwise.

The pure function is needed because two of the listed sites never touch the store. Both run over a list `readProjectPrs` already read:

- `prBoard` takes `good[good.length - 1]` and then `isOpen` (`apps/board/src/lib/pr-board.ts:253-254`).
- `readPrDetail`'s `n === 'next'` branch does the same with `latest` (`apps/board/src/lib/prs.ts:331`, `:339`).

These two cannot `yield*` an Effect, so they call `openAmong(good.map(r => r.pr))` instead. That way the store-backed and the list-backed answers are the same rule, and the board does not rely on `readProjectPrs` having filtered drafts out. `openAmong` also stands in for "latest + isOpen" in the done-when grep.

### `requestPrSubmit`: one read, two answers

Today it reads `latestPr` and calls `requestSubmit(previous, …)` with the default `foundDraft = true` (`packages/project/src/pr.ts:138-139`). It then appends at version 0 of `previous.n + 1` (`:141-142`).

After the change, inside the same `withOneRetry` (`packages/project/src/commands.ts:33-40`, "catchIf … ConcurrencyError … () => attempt"):

1. Call `listPrs` once. Take `open = openAmong(prs)` and `highest = prs.at(-1)` from that one list. `listPrs` reads the streams one after another, so the list is not a snapshot: before appending, `head` of every stream below the target is read again and must equal the version read, else the attempt fails as a `ConcurrencyError` and reads afresh. The target itself is guarded by the append's version. Do not call `openPr` and `draftTarget` separately: two reads could straddle a landing and disagree.
2. Call `requestSubmit(open, mode, project, by, highest?.status === 'draft')`. The decider already checks in the ticket's order, so no domain logic changes (`packages/domain/src/pr.ts:583-597`):
   - `solo`;
   - then `open-pr` whenever `isOpen(previous)`;
   - then `nothing-landed` when `!foundDraft`.

   A `requested` highest PR is not `draft`, so `openAmong` returns it and the answer is `open-pr`. That covers the edge where two Submits run at once.
3. Append to `prStream(project, highest.n)` at `highest.version`. `version` is the last event's version (`packages/domain/src/pr.ts:237`, `const at = { version: event.version, … }`), which is what `transitionPr` appends at (`packages/project/src/pr.ts:111`). Return `{ kind: 'requested', n: highest.n }`. The number never moves.

Also update the docstrings, which say the wrong thing once this lands:

- `packages/domain/src/pr.ts:572-574`: "while the project's latest PR is open. The new PR's number is the caller's, one past the highest". It should now read "the open PR below any draft; the draft's own number".
- `packages/project/src/pr.ts:128-130`: the "version 0" two-Submits paragraph.

### Ratchet

All three new readers are Effect pipelines over `listPrs`. `openAmong` is pure. Nothing adds an `async` or an `Effect.run*`.

### Summary for the user

The note is ready for the implementing agent; I didn't need to ask anything. Three decisions in it go beyond the ticket:

- **A pure `openAmong` in `packages/domain/src/pr.ts`.** Two of the listed board sites (`prBoard` and the `/pr/<project>/next` branch of `readPrDetail`) only see a list that's already been read and can't call the store-backed `openPr`. Both now use the same rule.
- **`requestPrSubmit` reads the PR list once.** It takes the open PR and the draft from that one read, and re-checks the heads of the streams below the draft before appending, so a stale early read cannot be acted on. It passes the open PR to the existing `requestSubmit` decider, which then needs no change.
- **`lingtai pr summary` changes behaviour.** It now only answers for an open PR, so it can no longer show the last merged PR's summary.

The conductor line numbers in the ticket have drifted: the pr-fix cut is now at `packages/conductor/src/conduct.ts:3287-3290`.
