# #1271 — design note

## The decision the ticket does not make: where triage's `kind` is overwritten

The ticket says to set each child's kind "when a `TriageAdvised` carries a split … before `WaitTriaged` is appended". That is too late. The reply meets two schemas that require `kind` before the runner ever holds a `TriageAdvised`:

1. **The output schema the runtime enforces.** `TRIAGE_ANSWER_JSON_SCHEMA` (`packages/domain/src/wait.ts:968`) is `z.toJSONSchema(TriageEnvelope)`. That envelope holds `TriageAnswer` → `RootCause` → `TicketTooBig` (`wait.ts:906`, `split: SplitProposal.optional()`) → `SplitProposal`, whose child requires `kind: z.string().max(TRIAGE_TEXT_MAX)` (`packages/domain/src/split.ts:169-174`). It goes to the runtime as `outputSchema` whenever `acceptsOutputSchema` is true (`apps/cli/src/triage.ts:1025-1027`). On that route the model is still forced to invent a kind, even after the prompt stops mentioning one.
2. **The parse.** `parseTriage` runs `TriageResult.safeParse` (`packages/conductor/src/triage.ts:410`) against the same `SplitProposal`. A reply with no `kind` is refused with a `cause.split.children.N.kind` issue, and its why becomes a `TriageFailed`. That is the opposite of *Done when*'s second box. A kind longer than `TRIAGE_TEXT_MAX` is also refused rather than ignored.

So the parent's kind has to be known **before** the parse, and it has to be written onto the raw reply. Two schemas come out of this:

- **The record schema is unchanged.** `SplitProposal`, `RootCause`, `TriageResult` and `WaitTriaged.result` (`packages/domain/src/events.ts:2637`) keep `kind` required. The board reads its type straight off `RootCause` (`apps/board/src/app/split-plan.tsx:32`), and `split-ticket.ts:318` reads `child.kind`. Both stay as they are, which is the ticket's *event shapes unchanged*.
- **The answer schema drops `kind`.** Add a proposal schema with no `kind` on the child (for example `SplitProposalAnswer` in `split.ts`) and use it only on the answer side: `TriageAnswer` → `TriageEnvelope` → `TRIAGE_ANSWER_JSON_SCHEMA`.
  - Do not copy the six-cause union by hand. Build both unions from one function of the split schema, so the causes cannot drift apart. For example: `causesWith(split)`, with `RootCause = causesWith(SplitProposal)` and the answer's union `causesWith(SplitProposalAnswer)`.
  - `TriageAdvised` is currently `TriageAnswer.extend(...)` (`wait.ts:938`). It must be built over the record-side union instead, so the log's shape keeps `kind`.
  - `refuseProblems` takes a `SplitPlanShape` whose children are `ChildTicket` (`split.ts:35-38`, `152`). Loosen that parameter to the fields it reads, so the answer-side proposal can keep the structural refinements. `splitPlanProblems` checks `kind` only when `kinds` is passed (`split.ts:83`), and the schema never passes it.

**`parseTriage(text, { kind })` does the overwrite.** It is pure.
- After the candidate object is found and before `safeParse`, if `cause._tag === 'TicketTooBig'` and `cause.split.children` is an array, replace every child's `kind` with the parent's. Delete whatever the model sent, then set it. Do this on the raw object, so a reply that sent no kind and a reply that sent `"refactor"` record the same thing.
- **No repair:** the docstring at `triage.ts:345-346` says *"An answer that misses the schema is never coerced into one that fits"*. This rewrite does not break that rule. `kind` is no longer part of the answer; it is a field the runner owns. Say so in the docstring beside that rule.
- `kind: null` means the parent's kind could not be settled (see below). In that case a reply that carries a split is refused with a why that says so, such as `the recipe's kinds could not be read, so a split has no kind`. Any reply without a split parses exactly as it does today.

## Where the parent's kind comes from

The kind comes from the runner, in the evidence step (`apps/cli/src/triage.ts:626-634`). It is settled once per request, before the first round, and passed to every `parseTriage` call (`triage.ts:1080`).

- **Labels:** the `issue` port (`triage.ts:545`; production `triageIssue`, `triage.ts:423-437`) also returns the ticket's `labels`. The read already gives a `Ticket = TicketDetail & …` (`packages/conductor/src/ticket-store.ts:54`; `TicketDetail extends TicketListing`, `discover.ts:85`), so nothing extra is fetched. `TriageEvidence.ticket` (`packages/conductor/src/triage.ts:58`) does not need the labels, so keep them off the brief.
- **Kinds:** add one port, `kinds(ticketId): Effect<readonly string[], unknown>`, for the recipe's `source.kinds`. Its production body follows `triageFor` (`triage.ts:470-475`): `readProjectEffect` and then `currentRecipeEffect(state)`. It is new IO, so it is an Effect, and it adds no `async` and no `Effect.run*`.
  - Why not fold it into `issue`: when the ticket read fails, the children still need the recipe's first kind (ticket *Edges*, *"The parent cannot be read"*). That failure must not take the kinds with it.
- **The choice:** a small pure function, for example `splitChildKind(labels | null, kinds): string | null`, in `packages/conductor/src/triage.ts`.
  - Labels known → `kindOf({ labels }, kinds) ?? kinds[0] ?? null`.
  - Ticket unread → `kinds[0] ?? null`.
  - Kinds port failed → `null`.
- **Do not put the fallback inside `kindOf`.** Its docstring (`discover.ts:114-117`) says *"Null when nothing says. That is not a defaulting opportunity: … guessing the first kind would put unclassified issues at the front of the queue."* That is right for the queue, and the queue still calls `kindOf`. The first-kind fallback is a split-only rule, chosen by the operator on 2026-11-18, and it belongs beside `parseTriage`.
- `kindOf` takes a `TicketListing`, but `kindLabelOf` reads only `issue.labels` (`discover.ts:135`). Either pass the whole ticket or narrow the parameter type to `Pick<TicketListing, 'labels'>`; narrowing changes no behaviour.

**The recipe cannot be read mid-request** (not in the ticket's Edges). The kind is `null`, and a split reply becomes `TriageFailed` with the why above. The card then says triage failed and why, instead of recording a plan whose kind nobody chose. Every other cause records normally. Settling the kind once also covers *"the label changes between triage and Create all"*: the plan is frozen at triage, as the ticket says.

## The brief

`RECORD`'s `TicketTooBig` line (`packages/conductor/src/triage.ts:129-134`):
- The example child becomes `{"key": "parser", "title": "…", "body": "…"}`.
- Add one sentence: each child is opened with this ticket's own kind, so the plan does not name one. The model then stops inferring a kind from a conventional-commit prefix. That inference is how #1242's plan got `refactor`.
- The *Done when* test asserts on `triageBrief(...)`'s text: the `TicketTooBig` paragraph contains no `"kind"`.

## Tests

All of these are unit tests; nothing here needs the integration half.
- **`packages/conductor/unit/triage.test.ts`:** `parseTriage` with `{ kind: 'tech-debt' }`.
  - Children carrying `"kind": "refactor"` → advised, and every child is `tech-debt`.
  - Children with no `kind` → advised, `tech-debt`.
  - An over-long `kind` → advised, not refused.
  - `{ kind: null }` with a split → refused. Without a split → advised.
- **`splitChildKind`:** a parent labelled `Tech Debt` gives `tech-debt`; no recipe kind gives `kinds[0]`; an unread ticket gives `kinds[0]`.
- **`apps/cli/unit/triage.test.ts`:** one runner test through `waitTriage` with fake `issue` and `kinds` ports, showing the recorded `WaitTriaged` children carry the parent's kind. This file already imports `TRIAGE_ANSWER_JSON_SCHEMA`; any fixture there with a `kind` in a split's children must still pass.
- **`packages/domain/unit/triage-answer-schema.test.ts`:** assert that a split child in `TRIAGE_ANSWER_JSON_SCHEMA` has no `kind` property and does not list it under `required`. Assert separately that `TriageResult` still refuses a recorded child without `kind`, which keeps the log's shape pinned.

Every existing fake `issue` port gains `labels` and every fake `TriageDeps` gains `kinds`. That is mechanical. It is also the one place this change costs other tests anything.
