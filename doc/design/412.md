# #412: triageBrief and parseTriage — design

## Where it goes

- **New `packages/conductor/src/read-step.ts`.** It holds the read half of Discussion's protocol, moved out of `discuss.ts`:
  - `READS_PER_TURN` (`discuss.ts:101`) and `MAX_READ_ROUNDS` (`:111`)
  - `ReadableRef` (`:129`)
  - the `{"read":[...]}` paragraph of `CONTRACT` (`:224-235`), as an exported `READ_CONTRACT` string
  - the file-index and files-served renderers, which are the two inline blocks in `buildBrief` (`:274-299`)
  - `jsonCandidates` (`:425`)
  - `readOf(v)`, the `Array.isArray(v['read'])` branch of `parseReply` (`:390-400`), applied to one already-parsed candidate so a caller can ask the read-or-answer question per candidate rather than across all of them. A `parseRead(text)` built on top of it scans every candidate for the first one `readOf` calls a read, for a caller that wants that whole-text answer instead.
- **`discuss.ts` imports these back and re-exports the names it exports today.** `apps/board/src/lib/recipe.ts:17` imports `MAX_READ_ROUNDS` from `@lingtai/conductor/discuss`, and `discuss.test.ts` imports `buildBrief`, `READS_PER_TURN` and the rest. `buildBrief`'s output must stay byte-identical, and `discuss.test.ts` is what checks that.
- **New `packages/conductor/src/triage.ts`.** It exports `triageBrief`, `parseTriage`, `TriageEvidence` and `TriageReply`, and imports only `@lingtai/domain`, `@lingtai/domain/wait` and `./read-step.ts`.
- **`packages/conductor/package.json`** gets `"./triage": "./src/triage.ts"`, next to `"./discuss"`.

### Why a new module, and not imports from `discuss.ts`

1. **The read paragraph cannot be reused as it stands.** `CONTRACT` is not exported. It is also one string that holds both shapes, and the second shape is Discussion's `{"answer", "cannot", "proposal"}`. A triage brief that quoted it would offer the agent an answer shape that `parseTriage` refuses.
2. **The import stays pure.** `discuss.ts` imports `./tell.ts`, `./attempts.ts` and a type from `@lingtai/event-store`. `read-step.ts` imports nothing, so "the board can import both without compiling a runtime" holds by construction.

Moving the code does not make a second read protocol: `discuss.ts`'s `parseReply` and `triage.ts`'s `parseTriage` both call the same `readOf` on each JSON candidate in turn, so a read request outranks an answer only within the candidate that carries it — never across candidates, and never by scanning the whole text for a `read` array first (`read-step.ts:92-101`'s `readOf`, used directly by both parsers rather than through the whole-text `parseRead`).

## The decision the ticket gets wrong: no `headSha`, no `Resolution` object

The ticket's **Fix** row says to build a `Resolution`, with `Approve` getting `onSha: headSha` from the caller. That is not what the domain says now:

- **#517 made `resolution` a bare tag.** `TriageAdvised.resolution` is `TriageAdvice` (`packages/domain/src/wait.ts:564-570`), which is `z.enum(['Approve', 'Requeue', 'EditBodyAndRequeue', 'Close'])` (`:226`). The comment at `:218-225` explains why:

  > *"A bare tag, not a `Resolution`: the only field one ever carries beyond its tag is `Approve`'s `onSha`, which is the head at the moment a person approves, not something triage knows ahead of them (0118 §1)."*

- **The ADR agrees.** 0118 writes `resolution: TriageAdvice` (`doc/decisions/0118-a-hold-explains-itself.md:186`).

So `parseTriage(text)` takes **no `headSha` option**. A parameter nothing reads would let a caller believe an approval had been pinned to a sha when it had not. The ticket's own **Done when** already asks for the bare-tag behaviour: *returns the tag `'Approve'`, and an object resolution is refused*.

## `parseTriage`

```ts
export type TriageReply =
  | { kind: 'read'; paths: string[] }
  | { kind: 'advised'; result: Extract<TriageResult, { _tag: 'TriageAdvised' }> }
  | { kind: 'refused'; why: string; raw: string }
```

### Order of checks

1. **A read request.** `parseRead(text)` first. If it returns a read, that is the answer.
2. **Find the JSON.** Otherwise, take the first `jsonCandidates` entry that parses to an object. If none does, refuse with `why: 'no JSON object in the reply'`.
3. **The budget, by name.** Do this before the schema. If `cause` is a string, or `cause._tag` is a string, and it matches `/out[- ]of[- ](turns|usd|rounds|budget)|budget/i`, refuse with `the budget is not a cause (0118 §4): "<what it said>"`.
   - Without this step, the schema still refuses the reply, but the message says the discriminator is invalid. The ticket asks that the refusal say *which*.
   - The two machine names come from `BudgetExhausted.cause`: `'out-of-turns'` and `'out-of-usd'` (`wait.ts:145`).
4. **`AnswerQuestion`, by name.** If `resolution === 'AnswerQuestion'`, refuse with `AnswerQuestion is an OwnQuestion's own resolution and triage never makes it (0118 §1)`.
   - If `resolution` is an object, refuse with `resolution is a tag, not an object`. This covers `{"_tag":"Approve","onSha":…}`.
5. **The schema.** Run `TriageResult.safeParse({ _tag: 'TriageAdvised', ...value })`, using `TriageResult` and `RootCause` from `@lingtai/domain/wait`. **Do not write a second schema or restate a bound.** `TriageAdvised` itself is not exported; parsing through the union with the `_tag` filled in is the way to reach it.
6. **A failed parse.** Refuse, and build `why` from the zod issues as `<path>: <message>`, joined with `; `. Zod 4's `too_big` message carries the bound itself, for example `cause.questions: Too big: expected array to have <=5 items`, so the refusal names the bound without the code repeating `TRIAGE_QUESTIONS_MAX`. The refinements already carry their own messages:
   - `ConflictingHunks` (`wait.ts:534-537`)
   - `TriageQuestion.recommended` (`triage.ts:49-52`)

   Unit tests should assert on the path and the number, not the whole message text.
7. **Cap `why`.** Clip it to `TRIAGE_TEXT_MAX` (`triage.ts:32`). #428 will put a refusal into `TriageFailed.why`, which is `.max(TRIAGE_TEXT_MAX)` (`wait.ts:557`), so an overlong `why` would turn a refused reply into a refused append.

### What `parseTriage` does not do

- **No mapping to `TriageFailed`.** `parseTriage` returns `refused`, and #428 decides what that becomes. A refusal at round 2 might still be followed by another round.
- **No repair.** An answer that misses the schema is never coerced into one that fits. This follows `parseReply`'s rule (`discuss.ts:369-375`): *"An unreadable reply is **not** repaired into an answer."*
- **No check against `allowedResolutions`.** An advised kind the wait does not offer still parses. `recommendedResolution` already returns `null` for it (`wait.ts:489-494`).

## `triageBrief`

### Evidence

`TriageEvidence` is a plain value:

| Field | Shape |
|---|---|
| `ticketId` | string |
| `ticket` | `{ ref, title, body } \| null` |
| `ticketProblem` | `string \| null` |
| `reason` | `WaitReason` |
| `routed` | `PayloadOf<'PassRouted'> \| null` |
| `published` | `PayloadOf<'RunRefsPublished'> \| null` |
| `diffStat` | `string \| null` |
| `reading` | `readonly string[]` |
| `refs` | `readonly ReadableRef[]` |

Use `DiscussionTicket` for the ticket. Check that `PayloadOf` is the right helper: `tell.ts:30` imports it from `@lingtai/domain`.

`triageBrief` also takes `served`, `roundsLeft` and `prompt?`, as `buildBrief` does (`discuss.ts:262-277`).

### The machine's words go in whole, under a label

- **Do not write a per-variant switch over the twelve `WaitReason` tags** (`wait.ts:187-200`). Render the whole value with `JSON.stringify(reason, null, 2)` in a fenced block, under a heading that says it is a claim. Wording along these lines:

  > **What the step that stopped said.** These are the words of the step that held the pass, quoted as it wrote them. They are its claim, not something established. Check each one against the refs and the diff below before you repeat it.

- **Why whole, and not field by field.** The words that misled #427 can sit in many places:
  - `said`, `question`, `evidence`, `detail`, `raw` or `why`
  - `ProposedEscalated.proposal`
  - `because.why` (`JudgeHandedOver`, `wait.ts:94`)

  A switch that names fields would miss the next one somebody adds. The JSON carries every field, and the label covers all of them.
- **The judge's reply.** Render `routed.reply` the same way under its own heading: *the judge's reason for its choice, its claim*. That covers `Selected.why` (`packages/domain/src/routing.ts:61`) and `Unreadable.raw` (`:63`). Put `routed.decision` beside it.

### What the attempt left behind

This is the gap #427 found. Render:

- `published.branch`, `arm`, `headSha` and which of the six publish outcomes it was (`events.ts:514-560`)
- `diffStat`
- for each of `published` and `diffStat`, an explicit sentence when it is `null`. A `null` must never be left as an empty section. `events.ts:504-512` says the absence of `RunRefsPublished` *"is evidence and not proof"*, so the sentence says that too.

### The rest of the brief

- The index and the served files come from `read-step.ts`'s renderers.
- Then `READ_CONTRACT`, then the answer shape written out with the six cause `_tag`s and the four resolution tags.
- Then the rules:
  - one cause
  - the parts belong to the cause (0118 §3, `0118-a-hold-explains-itself.md:325-329`)
  - the budget is not a cause
  - where the body does not say what the ticket wants: `want: null` and an `UndecidedQuestion` that asks it (`:330`)
- `prompt` goes last, trimmed and only if non-empty, as at `discuss.ts:336`.

## Tests

### `packages/conductor/unit/triage.test.ts`

- the cases in the ticket's **Done when**
- **the import fence:** starting from `src/triage.ts` and `src/read-step.ts`, walk every local `from './x.ts'` import recursively — not just those two files by name — strip comments as `one-store.test.ts:40` does on each one reached, and assert that none of them has a `from '@lingtai/agent…'` or `from '@lingtai/repo…'`. Following the import graph itself, rather than grepping a fixed pair of files, is what makes the fence transitive: a later local import added to either file is walked too, however many files deep it goes.
- **the brief test:** put a known sentence in, for example `MergeRefused.raw = "was merged in first"`, and a `Selected.why`. Assert that each appears **after** its claim label.

It must pass unchanged. That is the check that the move kept `buildBrief` byte-identical.
