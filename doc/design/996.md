# #996 — design note

#991 and #992 have landed in this worktree, so most of the line numbers in the ticket have moved. The current ones are used below. Three things are not obvious from the ticket: there must be a single `locked` in the daemon, the board can do its refusal without touching the ratchet, and there is a unit-level place to test the work loop.

## 1. One `locked` in the daemon, built once

Today `locked` is built inline, inside the `pass` options: `locked: lockedBy(makeGuard({ store: eventStore }))` (`apps/cli/src/daemon.ts:637`).
- Move it into one `const locked = lockedBy(makeGuard({ store: eventStore }))`, placed before `createWorkLoop` (`daemon.ts:567`).
- Use that const in three places:
  - the `pass` options at :637;
  - the `discuss:` line at :574;
  - the startup `answerOutstanding` at :705.

Sharing it is safe because the guard caches nothing. `guard.ts:16-17` says: *"Asked at the moment a gate would start work, every time, never cached across a look."* Each `locked(project)` call re-reads `prj-`.

`lockedBy` never rejects. A read that fails answers *"could not read whether <project> is paused — …"* (`packages/daemon/src/guard.ts:52-71`). So the ticket's read-failure edge in the daemon is already handled, as long as the callback that reaches `answerOutstanding` is this one.

`answerOutstanding` should still treat a rejecting `locked` as held: catch the rejection, use its message as the sentence, and `break`. A stub or a future guard might reject. That is the "unknown is not unlocked" rule, and costs one `.catch`.

## 2. `answerOutstanding`'s new signature

Today it is `answerOutstanding(log)`, positional (`apps/cli/src/discuss.ts:463`).
- Change it to take one options object: `{ log?, locked?, control?, read?, answer? }`.
- Return `{ answered, heldBack }`.
- It stays the one existing `async` function. The ratchet's baseline for `apps/cli` is `{ "async": 413, "run": 6 }` (`packages/domain/unit/effect-ratchet.baseline.json:2`). Adding ports adds nothing to that, as long as the defaults are references (`readControl`, `(id) => eventStore.read(chatStream(id))`, `answerDiscussion`), not new `async` arrow functions.
- The ratchet walks `${pkg}/src` only (`effect-ratchet.test.ts:212`), so test stubs are free.

Where the check goes inside the per-chat `for (;;)` (:475):
1. After `next` is computed and is not null.
2. Before `answer`.
3. Then `break`.

`project` comes from `parseTicketStream(next.ticketId)?.project`. When that is null or `''`, skip the check entirely; do not call `locked('')`.

`onDiscussionRequested` (:510-519): keep the name, and widen its guard at :511 to the events in §3's constant. Pass `locked` through to the queued `answerOutstanding`.

## 3. Work loop: one named constant, shared by both sides

`ProjectResumed` is already in `COMPLETION_EVENTS` (`packages/daemon/src/work-loop.ts:113-114`), so it wakes `pump`. The delivery to `discuss` is the `if` at :589-591.
- Add an exported constant, `DISCUSSION_EVENTS = ['DiscussionRequested', 'ProjectResumed'] as const`, beside `COMPLETION_EVENTS`.
- Use it in the `if` at :589.
- Export it from `packages/daemon/src/index.ts`, and have the guard in `apps/cli/src/discuss.ts` read the same constant. The two lists cannot then drift: the next unlock event (the ceiling or the account) is added in one place and reaches both.

A `ProjectResumed` that `discuss` fails on is recorded as `PluginFailed` with `project: null`. `record` takes the project only from a ticket or a subscriber's owner (`work-loop.ts:410`). That is acceptable; leave it.

**Unit test seam.** `packages/daemon/unit/work-loop-stop.test.ts:15-24` already runs `createWorkLoop` on `createMemoryEventStore()` with a waker that never fires.
- Model the delivery test on it.
- If the memory subscription only delivers on catch-up, append the `ProjectResumed` before `loop.start()`. Then assert that `discuss` received it and that a `TicketLanded` was not delivered.
- If that seam does not deliver at all, the claim stands on a membership test of `DISCUSSION_EVENTS` plus `onDiscussionRequested` acting on a `ProjectResumed` envelope. Say so in the commit; do not move the test to `integration/`.

## 4. The board: no new `Effect.run*`, no import of the root `@lingtai/daemon`

- **No guard on the board.** `@lingtai/daemon` exports `guard.ts` only from its root `"."` (`packages/daemon/package.json:7-13`). The board imports only subpaths, `@lingtai/daemon/control` (`apps/board/src/app/actions.ts:51`, `apps/board/src/lib/locks.ts:13`). Do not import the root to reach `makeGuard`: it drags the daemon's whole module graph into a Next server action, and `tsc` will not catch that; only the post-merge Next build would (CLAUDE.md, #230). Read `prj-` directly, as `locks.ts:76` already does (`store.read(projectStream(project))` then `reduceProject`), and call `locksOn({ project: state })` then `lockSentence`.
- **No new `Effect.run*`.** `projectLock` already uses `Effect.runPromise` (`actions.ts:539`); one more call raises `apps/board`'s `run` count. Inside `askDiscussion` (already `async`):
  - `await eventStore.read(projectStream(project))` in its own `try`;
  - pass the result, or the caught `Error`, to a pure, synchronous `askRefusal(project, read: readonly Envelope[] | Error): string | null`.

  That needs no new `async` function and no new run call. Put `askRefusal` in `apps/board/src/lib/locks.ts` beside `setProjectPaused`; its unit test needs no store.
- **Wording.**
  - Locked: `${sentence} — resume it, then ask`. The CLI's own form is `— lingtai resume ${project} first` (`apps/cli/src/project-pause.ts:161`); the board says "resume it" because its Resume button is on the banner.
  - Read failure: `could not read whether ${project} is paused — ${message}`, the same phrasing as `guard.ts:68`.
- **Project.** It comes from `parseTicketStream(input.taskId)?.project`; null means no refusal.
- **Order.** The refusal returns before `eventStore.head(CONTROL_STREAM)` (`actions.ts:583`), so nothing is read from or appended to `ctl-`. The pane already keeps the typed text on `!ok` (`apps/board/src/app/discussion.tsx:608-622`).

## 5. Decided edges the ticket left open

- **A turn held, then the same `answerOutstanding` run reaches another chat on the same project**: that chat asks `locked` again. There is no per-run cache, for the reason `guard.ts:16` gives.
- **`heldBack`** counts held chats, not held turns. A chat with three outstanding turns behind a lock counts as 1.
- **The startup line** goes at `daemon.ts:709`. Print the held line only when `heldBack > 0`. The `.catch` fallback at :705-708 returns `{ answered: 0, heldBack: 0 }`.
- **What settles behaviour after the merge**: on the log, a `DiscussionRequested` on `ctl-conductor` for a ticket whose `prj-` carries `ProjectPaused`, with no `DiscussionAsked` on `chat-<chatId>` until after the `ProjectResumed` seq. No unit test can show the log ordering under a real daemon; §2's `answer`-port test stands in for it.
