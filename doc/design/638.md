# Design: #638, `runtime.concurrency` slots in the work loop

## The decision this note makes: at the default, nothing new runs

The Watch out row asks for byte-for-byte behaviour at `concurrency: 1`. The simple way to build slots breaks that. If every look started its passes without waiting for them, then even at N=1 the look would return at once. Events arriving mid-pass would then each start a look: one `runnableNow` call to GitHub per event, a `readControl` each time, and a `pass (completion): …` line printed for each. Today those events only set `again` (`work-loop.ts:459-463`). The burst-collapse would be gone, and the log would look different on every machine.

**So there are two modes, and the installation picks one at the start of each look:**

- **Awaited (today's mode).** Used when the effective slot count is 1 for every project. The look runs exactly the code it runs today: `conductWork` awaits `runOnce` (`apps/cli/src/conduct.ts:276-284`, `:341-343`), `runQueue` gets `max: options.max ?? 1` (`:354`), and nobody calls `started`. Nothing on this path changes, and that is the byte-for-byte guarantee. Don't refactor it.
- **Detached.** Used only when some project's effective slot count is above 1. The look fills each project's free slots, hands each started pass to `started`, and returns without waiting for them.

**The effective slot count** of a project is `concurrencyOf(recipe)` when a daily ceiling is configured (`machineDayCeiling()`, used at `apps/cli/src/day-ceiling.ts:79`), and 1 when none is. 0122 §5 says: *"While none is set, the installation runs one pass in all, whatever each project's `concurrency` says."* With no ceiling, the awaited mode already gives one pass in all: `conductProjects` walks projects serially (`conduct.ts:492`) and each project awaits its pass. That needs no extra code. When a recipe says `concurrency: 2` and no ceiling is set, log one line per look saying the setting is ignored and why. A `doctor` check is out of scope here.

In detached mode, every project's passes are detached, including N=1 projects. Otherwise one project's hour-long pass would hold the look, and no other project's slots could refill.

## The recipe key: optional, never defaulted

Add `concurrency: z.number().int().min(1).optional()` to `runtime` (`packages/recipe/src/recipe.ts:3235`). Add an accessor `concurrencyOf(recipe) = recipe.runtime.concurrency ?? 1` in `packages/recipe/src/settings.ts`, beside `ceilingOf` (`:177`).

**Do not write `.default(1)`.** `recipe.ts:246-249` says: *"`configHash` is the hash of the *resolved* recipe (0047 §2), so a `.default({})` on `limits` would change the hash of every project's recipe — including the one stored on every `RunStarted` and `StepsResolved` — for a file nobody edited."* `runtime.limits.usd` is `.optional()` for the same reason (`:3356`). Add a unit test that hashes a recipe without the key and checks the hash is the same as before the change.

`runtime` is a `z.object`, not a strict one (`:3235`), so a daemon older than this change silently drops the key. That is the *code, restart, paste* order 0122 §1 asks for. **Do not edit `~/.lingtai/lingtai/recipe.yml`** (see the ticket's Watch out).

## Where the slots live

The in-flight set has to outlive a single look, so it can't live in `runQueue`. Today `conductorPass` (`conduct.ts:399`) is a fresh call on every look. The daemon creates the set once, beside `loop` (`apps/cli/src/daemon.ts:547`), and passes it in through `conductorPass` → `conductWork`.

Put the set in `packages/conductor/src/slots.ts`, keyed by project:

- Each entry is `{ ticketId, issue, files }`.
- An entry goes in **before** `runOnce` is started and comes out when that promise settles, however it settles.
- `free(project, n)` returns `n - inFlight(project)`.

0122 §2 requires: *"The in-memory set of passes in flight is subtracted first. A ticket claimed a moment ago may still read `queued` in `task_view` on the next look, because the projection lags the claim."* `selectRunnable` reads only `task_view` (`packages/conductor/src/queue.ts:75-99`), so the look removes in-flight tickets from its result before walking it.

**`runQueue` gets an optional `slots` argument, and without it nothing changes.** `apps/cli/src/run.ts:500` also calls `runQueue`, for the foreground `lingtai run`, and it must keep awaiting. With `slots`, the `for (;;)` (`packages/conductor/src/schedule.ts:158`) works like this:

1. Walk the queue.
2. Skip any ticket that is in flight or collides with one (next section).
3. Start `runOnce` with `Effect.runFork` or `runPromise`, but don't `yield*` it. Hand the promise to `started`.
4. Stop when the free slots are used up or the queue is walked. Return `stopped: 'max'` or `'empty'`.

Keep the `paused` question before each start (`:160-167`). That is where the daily ceiling is checked (`day-ceiling.ts:1-6`), and 0122 §5 puts it *"before each claim"*. Detached mode adds no new place where work is taken without that question being asked.

The hand-picked request (`conduct.ts:334-347`) and the continuation (`:271-294`) also start through the slots in detached mode, and each uses a slot. A request that arrives with no free slot waits for the next look. The request stays pending until its ticket stops being queued (`:303-305`), so it is not lost.

## The work loop: a pass settling triggers a look

`work-loop.ts` already has most of what this needs from #640. `started` is `passesInFlight.track` (`:507`), and `stop()` awaits `passesInFlight.settled()` (`:598`). Two changes:

- **Wrap `started`** so that a tracked pass, when it settles, calls `void pump('completion')`. Completion events usually cover this (`COMPLETION_EVENTS`, `:95-114`). But a pass that ends at `stage: 'claim'` or `'env'` appends no event, and its slot would then stay unused until the next sweep (`SWEEP_MS`, five minutes). At N=1 nothing calls `started`, so this costs nothing there. After `stop()`, the pump lapses on `if (stopped) break` (`:479`).
- **Replace the header section *One pass at a time*** (`:35-40`). Its claim *"Running a second one concurrently would race for the same claim"* is the sentence 0122 §1 replaces. Write instead: looks stay serial (`running`/`again` keep their meaning), a look fills slots, the claim's version check is the backstop, and the default is the awaited mode.

The failure-loop guard doesn't move. `last_attempt_at` is applied in `selectRunnable` (`queue.ts:98`). Each look's `attempted` set is fresh, as it already is today, because each look is a new `runQueue` call.

## Same-file collisions: a pure function, and where the body comes from

Create `packages/conductor/src/same-file.ts` with two pure functions:

- `fixFiles(body): string[]` implements 0122 §2's rule. Find the first table row whose label cell is `**Fix**` (the board's reader matches the same label, `apps/board/src/app/standing.tsx:239`). Take its backticked tokens that contain a `/` or an extension, and strip a trailing `:line`. No row means `[]`.
- `collision(a, b): { file } | null`. Two files collide when the paths are equal, or when one is a bare name equal to the last segment of the other's path. **An empty list collides with nothing.**

The standing.tsx parser lives in an app and is strict about layout, so it can't be imported here. Don't move it.

**The listing has no body.** `discover.ts:59-62` says *"the listing is cheap and holds no body, and the body is fetched once, for the ticket that was claimed"*, and `Runnable` carries only `taskId, issue, title, kind` (`queue.ts:17-22`). So the look calls `client.getIssue(n)` for a candidate only when that project has a pass in flight. An empty project needs no check. An in-flight entry's `files` come from the `getIssue` made when it was started.

**A `getIssue` that fails counts as a collision for that look, not as *no files*.** If you can't read a ticket's Fix row, you don't know it is safe to run beside the others. The same rule as *null is not zero*: an unread value is never treated as an empty one.

**Blocked-by chains need nothing built.** 0122 §2 says: *"a blocker in flight is open until it lands and closes. A→B→C excludes C through B. Nothing is built for it."* `runnableNow` already passes over an open blocker as `blocked-by`. The ticket's first Done-when item still asks for a test of it. Write that test against the existing skip: a fake client whose dependent issue reports `dependencies: { blockedBy: 1 }` while the blocker is in flight.

## The skip as a reason: computed, not appended

The existing skip reasons are computed fresh from GitHub by every reader. `status` does it at `apps/cli/src/status.ts:261-267`, and the board's queued page maps them to words at `apps/board/src/lib/queued.ts:101-115`. Do the same here, and append no event per skip per look. Otherwise every look while something is in flight would add rows to `events`.

`lingtai status` already lists the queue. It can work out *"waits for #N in flight — both name `path`"* without the daemon's memory:

- what is in flight comes from the `task_view` rows in `claimed`;
- the files come from `getIssue` on those tickets and on the queued ones;
- the overlap comes from `collision`.

So the reason is a value one function produces, and both the look and `status` call that function. Print it in `status`. Wiring it into `queued.ts`'s view is the board's half, and stays out of scope unless it turns out to be one field.

## The claim race test

`claimTicket` appends at `state.version` and turns a `ConcurrencyError` into `lost-race` (`packages/conductor/src/claim.ts:160-181`). The existing `lost-race` case in `unit/claim.test.ts:96` is about `continueTicket`. Add a test that runs two `claimTicket` calls on one ticket at once with `Promise.all`, against `createMemoryEventStore()`:

- exactly one returns `ok: true`;
- the stream holds exactly one `TicketClaimed`.

"Never two runs" means `runOnce` returns `stage: 'claim'` before `runPass` (`conduct.ts:3970-3986`). In production you would check this with two `RunStarted` for one ticket stream inside one claim. The unit test is the stand-in for that.

## Tests (unit half only)

- **N=2:** fake `runOnce` promises that don't resolve until released. Check that two independent tickets are both in flight after one look.
- **Same-file pair:** check that the second ticket is started only after the first settles, and that a lower, non-colliding ticket takes the slot in the meantime (*skipping, not stopping at*, 0122 §2).
- **Blocked-by pair:** check that they run one after the other.
- **N=1:** record the call order to `runOnce`, `paused` and the log lines with no ceiling configured. Check it is the same with the new code as with the awaited path. The cleanest form is one test run over the same fake world twice, once with `slots` absent.
- **Work loop:** in `packages/daemon/unit/work-loop-stop.test.ts`, check that a `started` pass settling calls `pass` again, and that `stop()` still waits for it.

## Edges

- **A daemon restarts mid-pass.** The in-memory set is gone. The new conductor kills the agent and releases its claim before taking work (CLAUDE.md, *The drain*), so `task_view` and GitHub are the only truth after a start. Nothing here survives a restart, and that is correct.
- **Pause, ceiling or drain.** No new pass starts, and the ones in flight finish (0122 §5, 0030 §1). `stop()` already waits for all of them.
- **Two looks at once.** Can't happen: looks stay serial on `running` (`work-loop.ts:459`).
- **Mirror writes.** 0122 §6 says *"Writes to the mirror (fetch, `worktree add`, `worktree remove`) are taken one at a time in the conductor."* No serialiser for them shows up in `packages/repo/src` (only `integrate.ts`'s comments mention serialising, at `:399`, `:582`). That doesn't matter at N=1. It is a prerequisite for the operator turning on `concurrency: 2`, and not part of this ticket. Say so in the PR rather than building it here.
- **The beacon** still names one `currentRunId` (`packages/daemon/src/store.ts:67`). 0122 §4 changes that, but it belongs to a different ticket.
