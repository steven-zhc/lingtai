# #377: design note

## The decision the ticket leaves open: `IssueChannel` cannot be a bare `Pick`

`Tickets.getIssue` has to return the whole ticket, because discovery reads the body (`discover.ts:56-64`, `TicketDetail`). `IssueChannel.getIssue` is narrowed on purpose. It returns `Promise<{ labels: readonly { name: string }[] }>` (`tell.ts:41`), and its comment says *"Only the names matter here: what Lingtai writes back is a set of names"* (`tell.ts:36-39`). Three test fakes rely on that narrowing, and every one is typed `IssueChannel` and returns a labels-only object:

- `packages/conductor/unit/sweep-refs.test.ts:233` returns `{ labels: [] }`
- `packages/conductor/integration/discuss.test.ts:147` returns `{ labels: [] }`
- `packages/conductor/integration/tell.test.ts:40` returns `{ labels: [...{ name, color: null }] }`

If `IssueChannel` becomes `Pick<Tickets, 'getIssue' | …>`, all three fail `tsc`, and fixing them breaks the ticket's *no file outside these three changes*. **No other files changing is the rule to keep.** So derive `IssueChannel` from `Tickets` in two parts:

- **The four writes are a `Pick`:** `Pick<Tickets, 'comment' | 'setLabels' | 'closeIssue' | 'updateBody'>`.
- **`getIssue` keeps its narrow, labels-only return type**, intersected onto that `Pick`.
- **Pin the relationship with a type assertion** that `Tickets` is assignable to `IssueChannel`. Drift then fails `tsc` just as a bare `Pick` would. Keep the "only the names matter" comment.

`closeIssue` needs nothing special. `Tickets.closeIssue(n, reason?)` comes through the `Pick` with `reason` optional, and the existing one-argument fakes, such as `close.test.ts:161`, still assign.

`TicketSource` can be a bare `Pick<Tickets, 'listOpenIssues' | 'getIssue'>`. The only hand-written implementation, `discover.test.ts:546`, builds its tickets with `discover.test.ts:54`'s `issue()`. That helper returns a full `Issue`, `url` included, so it still assigns.

## The types, in `ticket-store.ts`

`TicketListing` and `TicketDetail` stay declared in `discover.ts`. They are exported from there (`index.ts:24`), and moving them would change an import somewhere. `ticket-store.ts` imports them as types.

**Do not add a runtime import from `discover.ts` into `ticket-store.ts`.** `discover.ts` will import `Tickets` back for its `Pick`, and that cycle is safe only while both sides use `import type`.

Add one record type, `Ticket = TicketDetail & { url: string | null }`. `getIssue`, `listIssuesSince` and `createIssue` all return `Ticket`. `listOpenIssues` returns `TicketListing[]`, matching 0109 §1's *"the listing is cheap and holds no body"*, which `discover.ts:57-59` cites.

`githubTicketStore` takes `Pick<Tickets, 'createIssue' | 'listIssuesSince' | 'comment' | 'closeIssue'>`. Its `ref()` at `ticket-store.ts:89` then takes a `Ticket` rather than an `Issue`. `ProposedRef.url` is already `string | null` (`ticket-store.ts:50`), so nothing else in that file moves.

After this change, `import type { GitHubClient, Issue }` at `ticket-store.ts:28` is needed only for the type assertion. Put that assertion in the unit test instead and drop the import here, so the port file does not name GitHub at all.

Update the header comment's *"`propose`, and the `withdraw` that undoes it, are the only verbs here yet"* (`ticket-store.ts:5-11`). It stops being true with this change. Say that the verbs are declared and that moving the callers onto them is #378.

## Structural assignability is a `tsc` claim, not a `pnpm test` claim

Write the `GitHubClient` → `Tickets` pin, and the `Tickets` → `IssueChannel` pin, as plain assignments in a unit file. For example: `const _pinned: Tickets = {} as GitHubClient`, or a `satisfies` form. This repo's only precedent for a type pin is `packages/agent/unit/runtimes.test.ts:48`, which is a `satisfies`.

**`expectTypeOf` is not enough.** Vitest's run mode does not typecheck, so a broken pin stays green under `pnpm test`. What catches it is `pnpm typecheck`: the conductor's `tsc --noEmit` (`packages/conductor/package.json:33`) includes `unit/` and `test/` (`tsconfig.json:3`), and `check.yml` runs it. Say this in a comment beside the pin.

`Issue` (`packages/github/src/client.ts:80-106`) already assigns to `Ticket`:

- `url: string` assigns to `string | null`.
- `Label[]` assigns to `readonly { name; color }[]`.
- `Dependencies` has an extra `totalBlockedBy`, and extra properties are fine structurally.

If the pin fails, the interface is wrong. Do not fix it with a wrapper.

## Files

- **`packages/conductor/test/tickets-contract.ts`:** `describeTicketsContract(name, make: () => Promise<Tickets>)`. Name and shape follow `describeEventStoreContract` (`packages/event-store/test/contract.ts:52`), which runs against both stores. Each case calls `make()` for a fresh implementation, so cases never share numbers.
- **`packages/conductor/test/memory-tickets.ts`:** `memoryTickets()`. It must be the first implementation the suite runs against, under `unit/`. It must touch no filesystem and no clock, because `vitest.config.ts:10-12` counts the wall clock as outside the system.
- **`packages/conductor/unit/tickets.test.ts`:** runs the contract against `memoryTickets()` and holds the two type pins.

## Rules for `memoryTickets()` that the suite should pin

- **`dependencies` is `{ blockedBy: 0 }` on listings and on details.** It is never `null`, because `discover.ts:46-53` reads null as *unread*, not *clear*. A suite case asserts this.
- **Time comes from a `now` option**, defaulting to an injected counter or a clock the caller passes in. `listIssuesSince(t)` filters on the creation time it stored, and a case can then place `t` exactly. Without this, the "at or after `t`" case is a race against `Date.now()`.
- **Label colour is `null`.** `setLabels` and `createIssue` take only names, and `Label.color`'s comment says a missing colour *"is an answer rather than a gap"* (`client.ts:46-49`).
- **`url` is `null`.** The interface allows it, and this is the implementation with no web pages.
- **`getIssue` on an unknown number rejects.** Do not return a stub: `converge.ts:277` and `conduct.ts:1559` handle a missing ticket through the rejection.
- **Returned objects are copies.** A caller that mutates a result must not change what the next `getIssue` returns, and a case can check that.

## Not in this change

`RefChannel` (`tell.ts:56`), `matchingRefs`, `deleteRef`, `defaultBranch`, `fileAt`, `refSha` and `token` stay out of `Tickets`. `tellGitHubAbout`'s `IssueChannel & RefChannel` (`tell.ts:359`) is unchanged. `conduct.ts:1548`'s `const tickets: TicketSource = options.client` keeps compiling untouched, and that line is itself a check that `TicketSource` did not narrow anything `GitHubClient` provides.

This contradicts no ADR. It is the extraction that `ticket-store.ts:5-11` says 0036 named and that had not happened yet.
