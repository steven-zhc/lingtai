It is already exported, because `packages/recipe/src/index.ts:7` is `export * from './declared.ts'`. Its steps are the front half of `checkDeclared` (`declared.ts:36-79`) and nothing else:

   - The runtime probe (`declared.ts:63-67`).
   - `Recipe.safeParse`, returning `parsed.data` or `null`.

   Pull the preset-and-probe step into one private helper and use it from both functions, so the two can't drift. **`checkDeclared`'s error messages must not change.** `packages/recipe/unit/declared.test.ts` pins them, and that file is also where the new `parseDeclared` cases go.

2. **`apps/board/src/lib/mode-mark.ts`: add `modeMarks(projects: readonly ProjectState[]): ReadonlyMap<string, ModeMark>`.** Copy the shape of `sandboxStates` (`sandbox-state.ts:82-89`):

   `modeMark` itself stays as it is. It is the one reading of `modeLines`, and the file's comment says so: *"A reading of `modeLines`, never a second statement of the rule"*. The file header also says *"the recipe is the one the board already read (`board.askable`)"*. After this change that is true only for the bar's `mode-slot.tsx`, so reword it to name both callers.

3. **`apps/board/src/app/page.tsx:830`:** change it to `const mode = modeMarks(registered)`. `registered` is already awaited on the line above (`page.tsx:828`). `board` is still needed there for `shape(board, param)` and `board.projects`, so keep it in the `Promise.all`. Only the `askable` read goes. Don't move `mode` into `lockShape`: that function builds the lock and sandbox maps (`page.tsx:800-814`), and the mode glyph isn't a lock. Make it a sibling line to `lockShape`'s call.

## The decision the ticket doesn't spell out: `parseDeclared` is lenient

It answers one question: does this text parse to a `Recipe`? It does **not** run `checkDeclared`'s refusals:
- `oldSpellingsIn`
- `unknownKeys`
- `retiredTier` and `retiredLimits`
- `refuseOnMeaning` (`declared.ts:55-78`)

Why:
- **The shield works the same way.** `declaredSandbox` checks only the `sandbox` key (`declared.ts:83-87`: *"only this one key is validated"*). A project refused for some other reason still shows its shield, because `sandboxFactsOf` takes `refused` as a separate fact (`sandbox-state.ts:48-51`). The glyph should report what the file declares in the same way, and leave refusals to the existing marks.
- **The real case.** `refuseOnMeaning` refuses `mode: team` with no `branch.personal` (`resolve.ts:521-523`). With the lenient parse, that row shows the team glyph and `modeMark`'s sentence reads `lands on ${personal ?? main}` (`mode-mark.ts:17`). That matches what the file says. The refusal belongs to the resolve, not the menu.
- **What the lenient parse still rejects.** The root `Recipe` is `z.object`, not strict (`recipe.ts:3128-3129`), so unknown top-level keys are stripped rather than failing the parse. Anything `safeParse` itself rejects, like a non-mapping `branch:` or a `mode:` outside the enum, gives `null` and no glyph. The ticket's Out of scope already covers that.

The code doesn't settle whether a refused team project really appears in the register with a recipe. The log does: a `ProjectRecipeChanged` (`payload.source`) followed by a `ProjectRefused` for the same project. The lenient parse doesn't depend on which way that goes.

## Tests (all unit, nothing touches the filesystem)

- **`packages/recipe/unit/declared.test.ts`, for `parseDeclared`:**
  - a team text gives `mode: 'team'` and `branch.personal`;
  - text with no `mode:` gives a `Recipe` whose `modeOf` is `solo`;
  - an `extends:` preset is applied;
  - an unknown `extends:` name is parsed as written;
  - YAML that doesn't parse, a non-mapping root, and a schema failure each give `null`.
- **`apps/board/unit/mode-mark.test.tsx`, which already renders `ProjectRows` (`:65`, `:83`):**
  - Build `ProjectState` fixtures with `recipe: { source } | null`, run `modeMarks` on them, and render `ProjectRows` with `only="a"`.
  - Assert the team glyph appears on row `b`, which is a team project and not selected.
  - Assert there is no mode glyph on a row with `recipe: null` or with source that doesn't parse.
  - Look rows up by project name. Don't assert row order or the other marks, because the ticket's Edges forbid it.
- **No ratchet change.** All of this is pure and synchronous: no `async` and no `Effect.run*`, so `effect-ratchet.baseline.json` doesn't move.
- **The production-build check in Done-when is the person's.** Nothing at unit level covers the Next build (`apps/release/integration/build.test.ts`). `parseDeclared` imports nothing new into the board: `sandbox-state.ts:13` already pulls `@lingtai/recipe`, including `declared.ts` and its `node:crypto`, into the same server module graph. So the build risk is no higher than today's.
