# Design: #348, a preamble for `lingtai run` before dispatch

## Where it goes

In `apps/cli/src/run.ts`, inside `work`, right after `resolved` is read (`run.ts:249-252`) and before `common` is built (`run.ts:264`). The queue branch (`runQueue`, `:284`) and the `--issue` branch (`runOnce`, `:310`) both run after that point, so the lines print once per `lingtai run`. They come before anything is claimed, after every refusal, and after the lock. They are not per pass. The comment above `resolved` already argues for this spot: *"Both need it here now, because naming the runtime is reading a field off it."*

Do not print it from `conduct.ts`. The daemon conducts through the same `runPass`, so putting it there would write it into every daemon pass's run log. The ticket asks for it from `run`.

## The shape: a pure function, printed by `run`

Export a function from `run.ts` (or a small sibling file), something like `statedBeforeDispatch(recipe: Recipe): string[]`. It returns the lines, and `run` passes each one to `log`. It has to be pure because `run()` cannot be driven to dispatch in the unit half:

- `hasGitHubApp()` reads `~/.lingtai/config.yml`.
- `loadProject` reads the log.
- `createGitHubClient` goes to the network.
- `run()` has no seam for a fake runtime: `createRuntime(...)` is called inline at `run.ts:268`.

Under 0060 §1 all of that is integration. So the first *Done when* checkbox ("before the fake runtime's first dispatch") **cannot be reached by a unit test through `run()`**. Two unit-level claims stand in for it:

1. **The lines.** Call `statedBeforeDispatch` on a resolved recipe fixture and assert the runtime line and `passCeiling`'s sentence verbatim, plus the further-runs line (next section).
2. **The order.** A source-reading assertion, the same technique `run-pause.test.ts` already uses on `lingtai.ts`. In `run.ts`, the `statedBeforeDispatch(` call has to come before both `runQueue(` and `runOnce(`.

Say this in the test's docstring. Do not inject a runtime factory into `RunOptions` just to make the claim end-to-end. `run.ts:243-248` and `conduct.ts:340-349` both rejected changing that port, because every test that passes a fake runtime goes through it.

## The ceiling line: copy onboard's call exactly

Build the argument the way `onboard.ts:335-341` and `apps/board/src/lib/recipe.ts:827` do:

```
passCeiling({ ...limitsFor(recipe, 'implement'), wallMs: parseDuration(limitsFor(recipe, 'implement').wall), steps: boundsBesides(recipe, 'implement') })
```

That way `run`, `add` and the board print the same sentence for the same recipe. `ceiling.ts:51-52` explains why that matters: *"so this line and the drain's cannot say different things about the same recipe"*. Do not touch `passCeiling`.

**On "no dollar estimate":** `limitsFor` returns `runtime.limits` and everything in it, `usd` included. So `passCeiling` prints a `$` figure only when the recipe declares `runtime.limits.usd` (`ceiling.ts:47-53`, `recipe.ts:3114`). That figure is a cap the recipe wrote and the runtime enforces, not a price derived from tokens. Passing it through is correct, and it is what `add` prints. Do not strip `usd` and do not add a price of your own.

## The decision the ticket does not make: "further runs" means every other dispatching step, not just `review:`

The ticket only mentions `review:`. This project's own recipe (`~/.lingtai/lingtai/recipe.yml`) also has an `agent: claude-code` at `design:` (line 56), alongside `implement:` (81) and `review:` (110). A runtime `judge:` at `proposed:` is a paid call too (#277). A line that names only the reviewer would under-report the paid runs on the very recipe this repository uses.

So name **every step other than `implement` whose actions dispatch**, as further agent runs that are not in the sentence above. For example: *"not in that sentence: an agent run at design, review — each its own run on the same account"*.

The test for "dispatches" already exists: it is `dispatchedBy` at `packages/recipe/src/settings.ts:82-86`, which is not exported. Its comment says it must stay *"Exactly `agentRefusal`'s test, and the schema's: the three places that ask *is this a paid call* have to agree"*. Do not write a fourth copy in `apps/cli`. Add an exported helper next to `boundsBesides` in `settings.ts`, something like `dispatchingSteps(recipe): Step[]`, built on `dispatchedBy`. `boundsBesides` cannot serve here: it drops a step whose bound equals `implement`'s (`settings.ts:191`), and that is exactly the common case of a reviewer on the default ceiling.

Word the judge case with *may*. A runtime judge at `proposed:` only runs when its `when:` matches (`judge.ts`, `judgeDeclaredAt`). Leave the line out entirely when nothing besides `implement` dispatches.

## The runtime line

Name `resolved.recipe.runtime.agent` (`recipe.ts:2994`, default `claude-code`). Say that it runs on whatever account that CLI is signed in to on this machine. Lingtai holds no key of its own; the runtime is the local binary. If any step's `agent:` names a runtime other than `runtime.agent`, which is allowed since #314 (`conduct.ts:306-310`), name those too. The same `dispatchingSteps` walk can collect the distinct ids. Keep it to one line.

## Tests

- New `apps/cli/unit/run-before-dispatch.test.ts`. It covers the two claims above, plus a recipe with `review:` and `design:` agents that asserts both are named, and a recipe with only `implement` that asserts no further-runs line. Build the fixture through the recipe package's resolve path, not a hand-written object, so defaults apply.
- A unit test for `dispatchingSteps` in `packages/recipe/unit/`, next to the `boundsBesides` tests.
- `packages/conductor`'s `passCeiling` tests are not edited.
