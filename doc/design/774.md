## Design: #774, timing the board's reads

The ticket already covers the names, the edges and the tests. What follows are the choices it leaves to whoever builds it, and two traps found while reading the code.

### 1. The clock is set by `measure`, not by `timed`

The pin calls `loadTask` as it is, and `loadTask(taskId)` takes no options (`apps/board/src/lib/task.ts:1826`). So an injected clock cannot be passed into the `timed` calls inside it. `measure(fn, { now, slowMs, say, label })` puts `now` into the `AsyncLocalStorage` store, and every `timed` inside that scope reads its clock from the store. `timed`'s own options are only `{ desc?: string; failed?: (value) => boolean }`.

Outside a scope there is no clock, and `timed` just returns `fn()`. Don't fall back to `performance.now` when there is no scope: nothing would read the result.

### 2. `start` is taken when `timed` is called, before `fn` runs

`start = now()` is taken synchronously, then `fn()` is called. Inside a `Promise.all([...])`, the elements' `timed` calls all run synchronously in array order. So start order equals the order they appear in the source. One exception: `github.issue` runs inside `loadTicket` after that function's own awaits (`loadProject` and `currentRecipe`, `task.ts:1646`). Its start therefore comes after `events.control`, `spend.read` and `tasks.read` have all started.

With a counter clock, the `landed` harness should read: `events.task, events.run, events.control, spend.read, tasks.read, github.issue, [events.chat if the fixture has chats], recipe.run`. Confirm that against the harness and write the observed list out as literals, as the ticket asks.

Don't sort in place in a way that loses the tie order. Store a sequence number with each entry, or use `toSorted` (stable). Sort once, in `measure`.

### 3. `measure` wraps only the load, never the render

- **Task page.** Change `const task = await loadTask(...)` in `TaskPage` (`task/[id]/page.tsx:899`) to `const [task, timings] = await measure(() => loadTask(...), { label: '/task' })`. `notFound()` stays after it, outside the scope.
- **The tag's placement.** Render `<TimingMeta timings={timings} />` in `TaskPage`'s fragment, beside `<Follow>`, not inside `TaskBody`. `unit/task-page.test.tsx` renders `TaskBody` directly, so a tag inside it would change those renders.
- **`/`.** Wrap the `Promise.all` at `page.tsx:599`, which the ticket cites as `:591-592`. The `NotSetUp` early return (`page.tsx:588`) sits before it and renders no tag, which is correct.
- **No `generateMetadata`.** Next runs it as a separate function from the page, so using it would either read everything twice or measure nothing.

React 19 may move a plain `<meta name=…>` into `<head>`. That is fine either way. The `TimingMeta` test uses `renderToStaticMarkup` on the component alone and finds the string wherever it lands.

### 4. Where each wrap goes in `loadTask`

These are the spots that are easy to get wrong:

- **`events.run`.** `claims.length > 0 ? timed('events.run', () => Promise.all(...), { desc: String(claims.length) }) : Promise.resolve([])`. The `events.chat` read at `:1865` follows the same pattern with `chats.length`.
- **The `.catch` reads.** For `events.control` and `tasks.read`, the `timed` call sits inside and `.catch` stays outside it: `timed('tasks.read', () => readTasks({})).catch(emptyIfUnbuilt)`. A failure is then recorded as `failed` and handled exactly as it is today.
- **`recipe.run`.** Wrap only the `Promise.all(runs.map(...recipeOfRun...))` at `:1759`, inside the existing `try`. The `loadProject` and `githubClientFor` calls before it are not in the table.
- **`github.ref`.** Wrap only `client.refSha(...)` at `:1926`, inside its `try`.
- **The `next.*` reads.** Wrap each branch's call, not the `null` or `undefined` placeholder, so a read that is not made records nothing.
- **`mirror.ref`.** Wrap `refSha` at `:1872` and `mirrorBranchSha` at `:1902`, each under its own `timed` call, both named `mirror.ref`.

### 5. The `measure` result type, and `finally`

`measure` returns `Promise<[T, readonly Timing[]]>`. Its error path is a `try/finally`: `finally` computes the total and calls `say` if the total is over `slowMs`, and the error propagates as the same object.

The default `say` is `(line) => process.stderr.write(line + '\n')`. Nothing in `src/lib` logs that way today. `console.error` appears only in `split-instance.ts:59` and `:68`. Either works; `stderr.write` keeps it to one line with no inspector formatting.

### 6. Rendering the header string

One exported function, `serverTiming(timings): string`, produces `name;dur=N` or `name;dur=N;desc="…"`, joined by `", "`. `TimingMeta` and the tests both use it.

`desc` can only be `failed` or a decimal count produced inside `timed`. Neither can contain a quote, so it needs no escaping. Don't add a general-purpose escaper, because that would invite passing a message through it.

`timed`'s `catch` block records the entry and rethrows. It must not read `err` at all, not even `err.name`.

### 7. The harness's mocks: add `@lingtai/repo` and `@lingtai/conductor/filter`'s client

The ticket's mock list leaves out `@lingtai/repo`, which provides `refSha`, `mirrorBranchSha` and `mirrorPathFor` (`task.ts:75`). Those calls run `git` against a mirror. A `landed` fixture with no unpushed mirror never reaches them. Mock the module anyway, so that a later fixture change cannot silently start running `git` (0060 §1: that would make it an integration test).

`recipesFor` calls `githubClientFor(state)` (`task.ts:1756`). Its mock must return an object; `recipeOfRun` is mocked, so the object is never actually used.

### 8. The `"use client"` check stays manual

`timing.ts` is imported only by the four files the ticket names. Don't re-export it from any barrel. A unit test that scans the import graph is out of scope. The Next build after the merge is the only mechanical check (#230), and before that the check is a reviewer reading the import lists.
