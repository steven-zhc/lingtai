# Design: #308, the GitHub App's credentials in `~/.lingtai/config.yml`

## The section

```yaml
github:
  app_id: "123456"
  private_key_path: /Users/you/.ssh/lingtai-agent.private-key.pem
  webhook_secret: …
```

- **The key names are the file's own, and one table maps them.** A table in `packages/env` maps them to `LINGTAI_GITHUB_APP_ID`, `…_PRIVATE_KEY_PATH` and `…_WEBHOOK_SECRET`, so `appValues` still asks for the names it asks for today.
- **There is no inline-key form here.** `LINGTAI_GITHUB_APP_PRIVATE_KEY` exists because *"some hosts can only carry the key as one line"* (`packages/env/src/index.ts:1131`), and that is a hosting reason, not a machine-file reason.
- **A relative `private_key_path` resolves against `stateDir()`, never against `root`.** `resolvePath` resolves a relative path against `root` (`:1002`), and bundled, `root` is under `versions/` (`:36`). Do the resolving inside the new source, so the value reaching `githubApp` is already absolute or `~/…`. Every writer below writes an absolute path anyway.
- **`MachineConfig` accepts the new section without a change.** It is `z.object`, not strict, at the top (`packages/recipe/src/local.ts:89-94`): *"a section some other reader owns is not this reader's to refuse"*.

## `packages/env`: the reader and the election

**Read the file under `machineChoiceFile`'s rule, not `machineUrl`'s.** `machineUrl` (`:268`) only reads the file for `process.env`. `machineChoiceFile` (`:411`) also reads it for an environment handed in, but only when that environment names `LINGTAI_HOME`. Doctor calls `githubCredentials(env)` with an environment handed in (`apps/cli/src/doctor.ts:2167`), so this is the rule that lets a test point doctor at a temporary home. Under `inTest` with no `LINGTAI_HOME` the path is `null`, which keeps `HOME=/nonexistent pnpm test` green.

**The source can answer in three ways, like `machineDatabase` (`:250`): values, nothing, or unreadable.**
- The election treats unreadable as silence, matching *"A file that cannot be read says nothing"* (`:1061`).
- `githubApp`'s not-set error (`:1117`) appends the reason, so a broken `config.yml` is named rather than reported as *not set*.
- That error's remedy, *"Copy .env.example to .env.local"*, becomes: the board's setup page or `lingtai init` writes `github:` in `config.yml`, and `.env.local` is also read.
- The doctor skip text (`doctor.ts:758`) changes the same way.

**The election.** Push the machine source last in `sources` (`:1059`), and leave line `:1071` alone:

```ts
const owner = sources.find((source) => source(`${PREFIX}GITHUB_APP_ID`) !== undefined);
```

The watch-out is then satisfied by construction:
- A `config.yml` that names the id is asked first for the key path, even when a stale variable is exported.
- A `.env.local` that names the id is found before `config.yml`, so it wins for every name.

Do not reorder anything else. `process.env` includes `.env.local`'s values merged at import (`:56`), and that is already how the environment beats the files.

**Split it for the unit half.** Tests that write a temporary `config.yml` or `.env.local` are integration tests under 0060 §1 ("a temporary directory is still the filesystem"). So:
- Make the election a pure exported function over sources that are already parsed: `Record<string, string>`s plus the parsed `github:` section.
- Give the YAML-text-to-record step its own pure function.
- The ticket's pairing checkbox is then a **unit** test in `packages/env/unit/`, handing in plain objects:
  - the machine record names the id, and an env record carries a stale key path: the machine's key path is chosen;
  - an env-file record names the id: it wins both names over the machine record.
- The first checkbox (*no env files anywhere, credentials from `config.yml`*) needs a real file under `LINGTAI_HOME`, so it belongs in `packages/env/integration/env.test.ts` and is verified after the merge, not in the pass. The unit test is what stands in for it before the merge.

**Say where the App came from.** Add `source` to `GitHubAppCredentials`, taking one of three values:

| `source` | When |
|---|---|
| `"environment"` | the id was really exported |
| an env file's path | the id came from that file |
| the `config.yml` path | the id came from the machine file |

`process.env` alone cannot answer this, because it already holds `.env.local`'s values (`:39-52`). When the winning source is `process.env`, use `realEnvironment(from)` (`:398`) to decide:
- if the pre-dotenv snapshot names the id, the source is `"environment"`;
- otherwise it is the first env file that names the id.

`keySource` stays as it is. Doctor's `ok` detail at `doctor.ts:772` becomes `app N from <source>, key from <keySource>`.

## `create-app.ts`: the target moves, and the guard widens

**The write target becomes `join(stateDir(), "config.yml")`**, replacing `join(repoRoot(), ".env.local")` at `:457` and `:1026`. Rename `options.envFile` and the result's `envFile` to say what they are now. `packages/conductor/integration/create-app.test.ts` and the board page follow the rename.

**The writer is a sibling of `writeEnv` (`:762`), on a YAML `Document`, and keeps each of its guarantees:**
- It refuses when `github.app_id` is already set: the `keep` check.
- It re-reads the file just before writing and refuses if it changed.
- It writes beside and renames over, as `init.ts`'s `writeConfig` does (`apps/cli/src/init.ts:165-171`).
- It edits a `parseDocument` tree so `database:`, `runtime:` and `projects:` survive with their comments.
- **It calls `chmod 0600` every time, not only when it creates the file.** `packages/conductor/src/wizard.ts:381` writes `config.yml` with no mode, so a machine whose file the wizard created can be `0644` from before this write. A webhook secret must not land in it at that mode.

Export the writer. `init` uses it too (below), because `apps/cli` cannot own a writer that `packages/conductor` needs.

**`configuration()` (`:888`) asks three places, not two, and keeps the existing checks.**
- `.env.local` and `.env` are still checked (`:911-912`), but for a new reason. `config.yml` is now behind both in the election, so an id in either of them would **shadow** what this flow writes, not be overwritten by it. Refusing there is still right. Rewrite the comment at `:905-910`, because its reasoning is now the reverse of what it says.
- Add `github.app_id` from `config.yml` as the third check. `Configured.where` gains a `"config.yml"` case.
- Without this third check, an App configured only in `config.yml` reads as unconfigured, and the page mints a second App. That is the failure this function's docblock exists to prevent.

**Error strings.**
- `:522` and `:536` name the new file.
- `:653` tells the person to add lines by hand, and has to give them as YAML under `github:`, not `NAME=value`.
- The file header (`:30-47`) says `.env.local` in three places, and all three move.

## `lingtai init`: it moves the App, it does not create one

`init` has never created the App. That is the board's manifest flow (`init.ts:19-21`), and `init` only verifies an App with `liveApp` (`:638`). So *"init writes the section"* means this: when `liveApp` answered `ok`, and `githubApp().source` is not `config.yml`, write the id, the key path resolved to an absolute path (with `resolvePath`, against the checkout it came from), and the webhook secret if one is set.

This is the same rule as for `database.url`: write only what was verified. It is also the only route by which **this** machine reaches the checkbox that closes the ticket:
1. `lingtai init` copies `.env.local`'s App into `config.yml`.
2. `.env.local` is deleted.
3. `lingtai doctor` is still green.

`init` never edits `.env.local`. While it still names the id it keeps winning, and doctor's `source` says so.

## Docs

- `.env.example` and `doc/tutorial.md` should say the App's lines are a convenience for a checkout.
- `doc/decisions/0006-github-app.md` is not edited. This does not contradict 0006, 0046 or 0056; it applies 0056 §4's argument to one more fact, so no superseding file is needed.

## What settles it after the merge

The log carries no credential source, so a run cannot prove which file signed. After the merge, the evidence is doctor's `github: app credentials` line naming `config.yml`, together with events after a restart. Look for a `ConductorStarted` with the new commit, followed by a pass that claims or comments. That pass must have authenticated as the App, since the App is the only way it can.
