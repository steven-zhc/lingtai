# Design note for #429

The board needs one owner for the answer picks: the task page, which renders both `TriageBand` and `EditBodyAndRequeue` (`apps/board/src/app/standing.tsx:605`, `:735`). Keep selected answer IDs there, scoped to the current `waitId`, and use the same question control for `UndecidedQuestion.questions` and each `Divergent` hunk’s `question`. Those are the two places the band currently lists answers as text (`apps/board/src/app/standing.tsx:72`, `:108`; `packages/domain/src/triage.ts:37-54`, `:68-73`). Start each selection at `recommended`.

Pass a composed draft and note to `EditBodyAndRequeue`. The draft is one line per question, containing its text and the selected answer text; collapse embedded whitespace so an answer cannot turn one question into several prompt lines. The note describes the picks for the person. Keep the editor’s own text and an “edited” flag in the control: picks update the draft only until the person changes the textarea, including clearing it. Reset that state when the wait changes, while preserving the mounted editor’s pending result when a Follow refresh removes the blocked wait. The control already stays mounted for a body write in flight, tracks `draftWaitId`, and submits through an action that accepts an optional `note` (`apps/board/src/app/standing.tsx:732-741`; `apps/board/src/app/decide.tsx:258-319`; `apps/board/src/app/actions.ts:243-264`). Pass the composed note through that existing action; the conductor already records it on resolution (`packages/conductor/src/edit-body.ts:205-220`). ADR 0118 §6 says, “The appended text is composed from the answers the person picked. It is editable, and it stops following the answers once it is edited,” and “The requeue’s reason is written for the person from those answers.”

For Discussion, add `triage: TriageAdvised | null` to `DiscussionEvidence` (`packages/conductor/src/discuss.ts:139-156`). In `gatherEvidence`, use the ticket stream it already reads and folds (`apps/cli/src/discuss.ts:167-172`). Select triage only when the folded lifecycle is a current blocked wait, using `triageFactsOf(own, waitId)` and accepting only its `TriageAdvised` result. That helper pairs the latest `TriageStarted` attempt with its `WaitTriaged`, so an older attempt, another wait, and `TriageFailed` cannot supply the brief (`packages/domain/src/read-model.ts:99-133`; `packages/domain/src/ticket.ts:340-349`). This follows ADR 0118 §9: “A triage that finishes after the person has acted is still recorded, for its cost, and shown nowhere.”

Insert the optional *What triage found* section in `buildBrief` immediately after the ticket. Render the cause, summary, questions and recommended answers, and any fixes as quoted data; keep the section absent when `triage` is null so the existing template is byte-for-byte unchanged (`packages/conductor/src/discuss.ts:266-345`). The cause owns those parts rather than a parallel field (`packages/domain/src/wait.ts:523-582`); ADR 0118 §3 says, “The parts belong to the cause.” Read triage when the daemon gathers evidence, without changing `DiscussionRequested`, so a request made before triage finishes can still receive it when answered (`apps/cli/src/discuss.ts:167-172`, `:472-490`).

Unit tests should cover pick changes before and after a manual edit, reset on a new wait, the submitted note, current versus stale or failed triage selection, and both brief outputs. Pin the null case against the present brief’s exact text. ADR 0118 §3 says Discussion opens “with triage’s analysis as its context”; keeping the analysis in a conditional evidence section makes that context available without changing briefs for other tickets.
