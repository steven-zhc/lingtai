# #1103: design note

The ticket already gives the order, the faces and the baseline. This note covers four things it leaves open. In each one, the obvious port compiles and passes the unit half, but it changes what the daemon does when something fails or when somebody stops it.

## Every drain is a root fiber, never a child

`onShutdown` is called from inside the look's own fiber. `work-loop.ts:513` runs `options.onShutdown?.(why)` in the middle of `drain`, and `drain` runs on the fiber that `kick` starts (`:481`). The daemon's `onShutdown` (`daemon.ts:607-616`) calls `void drain(...)`, and `drain` waits for `loop.stop()` (`:490`). `loop.stop()` waits for every look in flight, which is #1070's rule (`work-loop.ts:55`: *"`stop()` waits for every…"*).

So if `drain` becomes `Effect.forkChild(drain(...))` inside `onShutdown`, it either waits on its own parent or is interrupted when that parent ends. Either way, the drain never reaches `beacon.stop` or `daemon.stop()`, and the daemon never exits.

All five ways a drain or stop can start must use `Effect.runForkWith(services)(…)`, and none may use `Effect.fork*`:

- `onShutdown`'s drain
- `onShutdown`'s `stopNow`
- the signal handler (`:743-752`)
- the `--timeout` timer (`:478`)
- the `--no-conduct` interval (`:741`)

`kick`'s own comment states the same rule: *"Not a child of whoever called: a look is never interrupted"* (`work-loop.ts:470-472`). `runForkWith` is not counted by the ratchet (`RUN = /^run[A-Z](?!\w*With$)/`, `effect-ratchet.test.ts:70`).

Two branches already sit on the main fiber and can call `yield* drain(...)` directly: `!start.take` at `:668` and at `:735`. A drain started there is not inside a look.

**Nothing may interrupt the main fiber.** `cli.ts:1532` runs the CLI with `Effect.runPromise` and has no `NodeRuntime.runMain`, so a SIGINT reaches only the `process.on` handlers. Keep it that way. `runMain` interrupts the main fiber on SIGINT, and that would interrupt the drain, which 0030 §6 forbids.

Take `services` with `yield* Effect.context()` after `openDaemon` returns `ok`. The context holds `Console`, `CliOutput` and `NodeServices` (`cli.ts:1533-1536`).

## The loop's catch moves from `Effect.catch` to `catchCause`

Today the loop reads its `shutdown` and `paused` ports through `attempt`, which is `Effect.tryPromise` (`work-loop.ts:492`, `:506`, `:516`). A rejected control read becomes a typed failure. The outer `Effect.catch` (`:537-539`) catches it and tells `loop failed: …`, and the look returns normally.

Once the ports are `Effect<string | null>` and `Effect<boolean | string | null>` with no error channel, a failed read arrives as a `Die`. `Effect.catch` does not see a `Die`. The look's `runPromiseWith` then rejects, and the loop stops looking until a person notices.

The fix:

- Write the outer catch the way the pass's catch is already written (`:527-532`): `Effect.catchCause`, pass an interrupts-only cause through, and tell `loop failed: ${(Cause.squash(cause) as Error).message}`.
- Wrap each port use in `Effect.suspend(() => options.shutdown!)` so that a throw while the port is being built is still caught.

On the host side:

- **The `shutdown` port** has no catch today. Its `controlRead()` rejection becomes `loop failed:`, and it must stay that way.
- **`claiming`** must keep `pausedSentence`'s recovery (`daemon.ts:978-985`): *a pause that could not be read is not consent*. When `pausedSentence` becomes an Effect, its recovery is `recovering` (`exit.ts:24-35`), not `Effect.catch`, because `readControl` fails with a defect (0101 §6).
- **Both ports must read fresh on every ask.** Build them with `Effect.gen` or `Effect.suspend`. Do not build them from a value read once when the loop is wired: #1102's note warns about exactly this for `paused`.

## `deliver` is still settled through a promise, inside the loop

`work-loop.ts:434-466` has a timer and a `settled` flag. Their comment says *"The timeout does not cancel anything"* (`:428`). `discuss` goes through the same function and stays a promise port (out of scope).

Keep that function and its `run: (e) => Promise<void>` parameter. Do not rewrite it with `Effect.timeout`: that would interrupt a subscriber's command, which today runs to its own end.

The subscriber call site at `:552` becomes:

```ts
deliver(s.name, event, (e) => Effect.runPromiseWith(services)(Effect.suspend(() => s.deliver(e))), s.project)
```

`services` is set at `:579`, before any event is delivered.

`runPromiseWith` rejects with `Cause.squash`. So both failures reach the rejection arm at `:458` carrying the message `deliverFace`'s `runPromise` gives it today (`subscriber.ts:241-243`):

- a `SubscriberFailed` from `makeSubscriber`;
- a subject read that was made a defect with `Effect.orDie`, matching `liftPromise`'s `Effect.promise` at `action.ts:839-840`.

That is why `subscribers-run-subject.test.ts:55`'s expected string does not move.

Type `EventSubscriber.deliver` as `(event: Envelope) => Effect.Effect<void, unknown>`. `SubscriberPort` then satisfies it structurally, and `packages/daemon` takes no import from `@lingtai/actions`.

## `openDaemon` keeps two recoveries, and the second must catch defects

- **`how.control()`'s rejection becomes `{ unread }`** (`restart.ts:537-540`). Once `how.control` is `readControlEffect`, a store failure is a `Die`. Map it with `recovering`, not `Effect.catch`, so it reaches `startRefusals` as `unread: <message>` exactly as today.
- **The refusal branch's `started.daemon.stop(); await started.daemon.stopped`** (`:547-548`) becomes `yield* port.stop()` then `yield* port.stopped()`. `stop()` is uninterruptible, and a second call is a no-op (`packages/daemon/src/daemon.ts:144`).

The return type's `started` becomes the `ok` arm of `DaemonStartPort` (`daemon.ts:138`).

A `how.start()` or `how.code()` that fails is not recovered today. It rejects out of `daemonCommand`, and `daemonHandler`'s `printedBy` prints it and exits 1 (`cli.ts:1022`, `exit.ts:56-65`). `printedBy` squashes defects too, so an Effect `daemonCommand` keeps that outcome with no wrapper. Do not add a release of the lock here: that is new behaviour, and the ticket asks for none.

In `drain`'s tail and in `stopNow`, `started.daemon.stop()` is a fire-and-forget face today (`daemon.ts:364`). Yielding `port.stop()` waits for the runners to close and the lock to be released before going on. That is harmless on a root fiber, and it is the only order change; nothing is printed between those steps.

## The SIGINT unit test needs the stopping block extracted

The `Done when` SIGINT test cannot reach today's closure without a lock, a store and `process.exit`. Move `stopNow`, `drain` and the signal counter (`:398-497`, `:743-752`) into one exported function in `daemon.ts`, for example `daemonStopping(ports)`, that returns `{ drain, stopNow, onSignal }`.

Its ports:

- `beacon`
- `daemon: DaemonPort`
- `loop: () => { stop(): Effect<void> } | null`
- `inFlight`
- `clearListening`
- `services`
- `exit`, which defaults to `process.exit`

The closure's `draining`, `stopping`, `asked` and `failedStart` flags stay plain `let`s inside it, read and set synchronously as now.

`daemonCommand` calls `process.on('SIGINT', () => stopping.onSignal('SIGINT'))`. The test calls `onSignal('SIGINT')` directly; it does not send a real signal, which would make it integration under 0060 §1.

The test's fake `loop.stop()` is `Deferred.await(d).pipe(Effect.onInterrupt(() => …record…))`. Assert:

- the draining lines are printed once;
- `daemon.stop` is not called before `Deferred.succeed`;
- nothing was interrupted.

Copy the sentences exactly. `integration/service.test.ts` pins *draining —*.

## What only the integration half sees

These run only after the merge, so nothing checks them inside the pass:

- `RESTART_GUARDS` through `openDaemon` (`integration/restart.test.ts:654`)
- the Telegram subscriber end to end (`integration/telegram.test.ts:137-138`)
- `subscriber-set.test.ts`

The unit tests that stand in for them:

- **`openDaemon` refuses on an unread control:** `how.control` is `Effect.die(new Error('x'))`, and `startRefusals` gets `unread: 'x'`.
- **A failed shutdown read does not stop the loop:** `shutdown` is `Effect.die(new Error('x'))`, the loop tells `loop failed: x`, and it takes the next kick.

Both expected strings are new, so they are added assertions and not edits to existing ones.
