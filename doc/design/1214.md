# #1214 — design note

## The decision the ticket leaves open: there is one reset reading, not two

The ticket's Fix gives `limitOf(text)` both jobs, *the kind of limit and its reset*. Don't build it that way. The reset is already read once, by `standDown`'s `readReset` (`packages/domain/src/failure/respond.ts:348-392`, which returns `{ until, untilFrom, said, reason }`). A second clock-reading parse in `limitOf` could disagree with the lock's `until` by a rollover or a zone guess, and then the sentence would contradict the lock it is printed on.

So the work is split:

- **`limitOf(detail): LimitKind`** is pure and reads no clock. It goes in `packages/domain/src/failure/` and returns `'5-hour' | 'weekly' | 'monthly-spend' | 'rate' | 'usage'`.
  - It looks first for a kind next to the reset marker: the `your 5-hour limit resets …` clause, or `session limit · resets`, which also means `5-hour`.
  - Only if that finds nothing does it fall back to the first `You've hit your X limit` clause.
  - Use `RESET_MARKER` (`respond.ts:155`) as the anchor rather than writing a second reset regex.
- **`standDown` builds the payload field.** It gains `limit: { kind: limitOf(detail), resetsAt }` in its return.
  - `resetsAt` is `until.toISOString()` only when `untilFrom` is `'message'` or `'message-latest'`. Otherwise it is `null`: `backoff` and `backoff-unreadable` mean the runtime named no reset that was read, and the backoff must never be passed off as the runtime's reset (ticket, Edges).
  - It is the same `now` and the same read, so there is nothing to disagree with.
- **`githubLimitUntil`** (`respond.ts:401-447`) builds `limit: { kind: 'rate', resetsAt }` in the same way:
  - `resetsAt` is `until` for `retry-after` and `ratelimit-reset`;
  - it is `null` for `doubling`, because GitHub named no time.
  - Its caller passes it through at `packages/conductor/src/account.ts:159-163`.

`standDownAccount` (`conduct.ts:1835-1869`) passes `limit` to `reachAccountLimit`. That function's `fields` parameter is typed `Omit<PayloadOf<'AccountLimitReached'>, 'account'>` (`account.ts:67-70`), so once the schema has the field it goes through with no other change.

## Where it is stored

1. **Event.** `AccountLimitReached` (`packages/domain/src/events.ts:2435-2450`) gets
   `limit: z.object({ kind: z.enum([...]), resetsAt: z.string().datetime({ offset: true }).nullable() }).optional()`.
   ADR 0126 §2 already lists `limit?` (`doc/decisions/0126-…md:38`), so this needs no ADR change. Run `pnpm events:generate` and commit what it writes.
2. **Reducer.** `AccountState.limit` is already the name of the standing lock (`packages/domain/src/account.ts:30`), so don't nest another `limit` inside it.
   - Add `named: { kind; resetsAt: Date | null } | null` to the `AccountLimit` type (`account.ts:12-24`).
   - Fill it at `account.ts:60` from `d.limit ?? null`.
   - A second `Reached` while a lock stands already changes nothing (`:48`), so the first event's kind is the one that stays. That is the "a second wall writes nothing" claim; test it over `reduceAccount` and over `reachAccountLimit` with a memory store.
3. **Lock.** The `account` member of `Lock` (`packages/domain/src/locks.ts:28-36`) gets `named` too, copied in `locksOn` (`:68-79`).
   - `lockJson` (`apps/cli/src/ceiling-words.ts:50-75`) adds it, so `--json` carries it.
   - `status` needs no other change: `lockLine`'s `account` case already calls `lockSentence` (`ceiling-words.ts:40-41`), and status prints `lockLine` (`apps/cli/src/status.ts:655`). The Done-when test for status goes over `lockLine` or the renderer with a lock that has `named`.

## The sentence

**Where `limitSentence(account, named, now)` goes:** in `failure/explain.ts`, as the ticket says. It is pure and its only clock is the `now` it is handed.

**The names table:** `accountWords` (`locks.ts:103-105`) is documented as *"the one place these words are written"*, and today it returns `{ name: account }` for runtimes, which is how `claude-code's usage limit` gets printed. Don't change `name`: the no-`limit` sentence must stay exactly as it is. Two parts:

- Move the display table (`claude-code` → Claude Code, `codex` → Codex, `github` → GitHub, anything else → its id) into `explain.ts`, next to `limitSentence`.
- Keep `accountWords` where it is.

**No import cycle:** `explain.ts` must not import `locks.ts`. Only `index.ts` imports `locks.ts` today, and the direction stays `locks.ts → failure/explain.ts`.

**`oneSentence`'s `account` case** (`locks.ts:131-132`):

- With `lock.named === null`, it returns today's string unchanged.
- Otherwise it returns `lingtai waits for ${limitSentence(…)} — lingtai account lift ${account} once it is over`.

**What `limitSentence` says** (kind words: `5-hour limit`, `weekly limit`, `monthly spend limit`, `rate limit`, `usage limit`):

| Case | Sentence |
|---|---|
| `resetsAt` set, after `now` | `Claude Code's 5-hour limit, resets 23:20` |
| `resetsAt` set, at or before `now` | `…, reset 23:20 — passed` |
| `resetsAt` null | `Claude Code's monthly spend limit — no reset named` |

- The time is formatted with `whenLabel` (`locks.ts:94-100`), which `explain.ts` can import.
- In the null case, `oneSentence` adds the lift command. It also names the backoff `until` with today's `untilFromWords` wording, because the guard still lifts the lock at that time and saying nothing about it would be a lie. Quote the fragment when `untilFrom` is `backoff-unreadable`; the fragment is in `said`.

## The judge's hold at `proposed`

The hold is at `conduct.ts:3509-3518`. Today `standDownAccount` returns a `boolean`, and the hold's `why` needs the limit that this message names.

**Change the return** to `Effect<{ locked: boolean; limit: … }>`, where `limit` is this message's own reading, even when the answer is `already`. The other three call sites change from `if (yield* standDownAccount(…))` to `.locked`; they are at `:5934`, `:6089` and `:6110` (`:5238` is only a comment that names it). Don't call `limitOf` and `parseResetAt` a second time at the judge site: that is the two-readings problem again.

**The `why` becomes**

```
the "${named}" judge did not answer (${kind}): ${limitSentence(walled, limit, now)} — ${detail} — so the attempt is held for a person (${spent})
```

with `now` being the same instant `standDown` used. Pass `now` into `standDown` explicitly rather than letting it default (`respond.ts:358`).

`within` refuses a reset in the past (`respond.ts:458-464`), so this `why` can only say *resets*, never *passed*. That is correct here, because the `why` is fixed text on a Ticket event. No field is added to the wait.

## Unit claims that stand in for the integration half

Everything above is pure apart from `standDownAccount`. The memory-store test of `reachAccountLimit` (`createMemoryEventStore()`) is the only IO-level check, and it is unit. Nothing here needs `pnpm test:integration`.

The existing domain tests to extend are `packages/domain/unit/account.test.ts`, `locks.test.ts` and `github-limit.test.ts`. The judge-hold `why` is easiest to test by unit-testing the string builder once it is a named function, rather than by running a whole conduct.

## The ratchet

No new `async` and no `Effect.run*` anywhere: `limitOf` and `limitSentence` are plain functions, and `standDownAccount` stays an `Effect.gen`.
