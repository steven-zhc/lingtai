# Design: #1254: an answer continues the step that asked, and `personAsks` hands the sixth stop to a person

Most of this is already built. Since the ticket was written, `designAsks` was renamed to `personAsks` (`packages/domain/src/read-model.ts:126-132`), `BOUNDS.personAsks` is 5 (`packages/domain/src/failure/respond.ts:589`), `implement`'s `Unclear` asks in triage's question shape (`packages/domain/src/implement-outcome.ts:23`), and a person's `RedoStep` already continues an attempt on its saved head (`packages/conductor/src/conduct.ts:1529-1580`). So this change has three parts:

1. `AnswerQuestions` is a second kind of `RedoStep` that writes the body first.
2. `personAsks` becomes a reason the ticket's reduce writes.
3. The design brief stops telling the agent to assume.

Because a few line numbers have moved, the code is cited below as it stands at `baab5a26`.

## 1. The resolution is a `RedoStep` with answers

```ts
const AnswerQuestions = z.object({
  _tag: z.literal('AnswerQuestions'),
  onSha: z.string(), ref: z.string().nullable(),          // as RedoStep (wait.ts:276-280)
  answers: z.record(z.coerce.number(), z.string()),      // = options.picks (resolve-wait.ts:149)
})
```

- **Why it carries `onSha` and `ref`.** The continuation machinery runs off a lifecycle with `status: 'approved'` and `onSha`. `ticket.ts:672-689` moves the lifecycle there for `Approve`, `FixRefusal` and `RedoStep`, so add `AnswerQuestions` to that list. Do not add it to the requeue list at `ticket.ts:694-699`.
- **`answers` is the picks map `resolve-wait.ts` already takes.** Do not invent `{index, answerId}[]`. A missing index means the recommended answer, as `triageAnswersText` already reads it.
- **Bump `ticket-codec.ts`'s `version` from 8 to 9.** Add a comment line with it: a new resolution tag, plus the reduce change in §3. A version-8 snapshot has never held either.

### Where it is offered

`allowedResolutions` stays a function of the reason, so put the reason-derived offer in `tableResolutions` (`wait.ts:336-356`):

- `AgentQuestion` with `questions.length > 0`: `['AnswerQuestions', 'EditBodyAndStartNewAttempt', 'StartNewAttempt', 'Close']`.
- `ProposedEscalated{InputNeeded}` with `questions.length > 0`: the same list.
- Old prose-only waits (`said`, empty `questions`) keep today's row. This is the ticket's *empty list offers nothing*.

Triage's `UndecidedQuestion` lives on the wait, not on the reason. Add one function beside `allowedResolutions`:

- `offeredResolutions(wait: { reason, triage: { result } })` appends `AnswerQuestions` when `triageCauseOf(result)` is an `UndecidedQuestion` with questions.
- Use it in every place that decides what a person may do: `resolveTicket`'s check (`ticket.ts:1058`, which has `state.waits` to hand), `waitMoves` and the board.
- The bare `allowedResolutions(reason)` stays for readers that only describe a reason.

Also:

- `causeResolution` returns `'AnswerQuestions'` for `UndecidedQuestion` (`wait.ts:797-798`).
- `recommendedResolution` must see the triaged offer. Pass it the same wait, or run its filter over `offeredResolutions`. Otherwise a recommendation of `AnswerQuestions` is dropped as *not allowed* (`wait.ts:813-814`'s rule).

Leave `ConflictingHunks`'s `Divergent` questions alone. `triageQuestionsOf` reads them (`triage.ts:156-160`), but their answer feeds a conflict round, not a step continuation. The ticket names three kinds of stop, and Divergent is not one.

### Which step continues

Write `answerStepOf(reason, triaged)` in `wait.ts`, next to `rerunStepOf` (`wait.ts:563`):

| Wait | Step |
|---|---|
| `AgentQuestion` | `reason.step` |
| `InputNeeded` | `proposal.from` |
| Triaged `UndecidedQuestion`, wait named `design`, `implement`, `review` or `prepared` | that step |
| Triaged `UndecidedQuestion`, wait named `build`, `proposed` or `merge` | `implement` |

On the triaged rows:

- `admit` cannot be redone and maps to `prepared`.
- `build` is my addition to the ticket's *proposed or merge*. `build` runs commands and reads no body, so redoing it with answers changes nothing. 0108 §12's *Where* lists `prepared`, `design`, `implement`, `review` as the steps `redoStep` runs at.
- The step a wait names comes from the reason's own field: `AgentCrashed.step`, `CheckRefused.step`, `fromOf(proposal)`, and so on. For a crash that stands in for another wait, read the standing reason.

## 2. `resolveWait`: check the head, then write the body, then resolve

In `prepare` (`resolve-wait.ts:312`), run the `RedoStep` block (`:374-434`) unchanged for `AnswerQuestions`, then the body write. That order is the ticket's two traps:

- **A lost saved head refuses before anything is written.** A body written for a resolution that is then refused is the failure to avoid. `rerunHeadOf`'s `cannot` (`:384-390`) and the remote-ref check (`:410-427`) both return before the write.
- **The body write comes before the append.** The questions passed to `triageAnswersText` are:
  - the wait's own `questions` (`AgentQuestion`, `InputNeeded`), as `{ _tag: 'UndecidedQuestion', questions }`, which is what `apps/board/src/app/triage-picks.tsx:85` already passes;
  - or triage's cause.

  Write it with `writeSectionEffect`, `key: ${ticketId}/${waitId}`, exactly as `:466-477` does. The marker is what makes a retry replace the section rather than add a second one.
  - A failed write ends at `write-failed` (`:475`). No `WaitResolved` is appended, so the wait stays open and nothing continues.
  - Picks against questions that changed end at `stale` (`:452-458`).
- Record `answers: { picks, section }` on `WaitResolved`, as `:477` does today.
- Add `AnswerQuestions` to the `requestContinuation` condition (`resolve-wait.ts:290`).

The continuation is guaranteed to see the new body for one reason: every pass, including a continuation, calls `tickets.getIssue` before it claims (`conduct.ts:3138`) and pins that body on the claim event (`:3252-3258`, `bodyAt`). The body is written before `WaitResolved`, so the continuation's claim reads it. Do not cache the issue anywhere on the continuation path.

## 3. The continuation in `conduct.ts`

Extend the `RedoStep` branch at `conduct.ts:1535` to `AnswerQuestions`, with `step = answerStepOf(...)` in place of `rerunStepOf`. It has three differences from `RedoStep`, and each one is a trap:

- **Never replay a recorded prompt.** `cutOffPromptOf` (`:1543-1546`) can return a design prompt that an earlier account limit cut off. Replaying it sends the old body, which is the reversal the ticket's *Watch out* names. For `AnswerQuestions`, set `rerun` to `{ for: null, prompt: null, accountReruns }`.
- **Count it in `personRerunsOf` (`conduct.ts:343-345`).** That count is a summand of the rerun's dispatch suffix. Leave `AnswerQuestions` out and the second design dispatch gets the same id as the first.
- **Add a paragraph saying what was answered, instead of `again`.** `again` on `implement` makes the brief a fix round (`conduct.ts:5566`: `brief.again === null ? firstDispatch : fixRound`), which is wrong here.
  - Carry the section's heading text on the continuation as an `answered` field, passed through `options.from` the way `redo` is.
  - On the first visit to that step, `run-attempt.ts` sets `context.answered`, next to the `again` computation at `:3022-3035`.
  - `designText` renders one paragraph from it. So does `implement`'s `firstDispatch`, which must also say the branch's commits are its own to continue.

Spending: `continuationSpent` is unchanged, so no `stepRedos` is spent. The ask was already counted when the wait opened (§4).

## 4. `personAsks` is a reason the reduce writes (the answer in the body settles this)

Add a `WaitReason` variant (it is not a flag):

```ts
const AskLimit = z.object({
  _tag: z.literal('AskLimit'),
  run: AttemptRef,
  bound: z.literal('personAsks'),
  used: z.number(),
  allowed: z.number(),
  asked: StandingReason,
})
```

- `run` is copied from `asked`, so every reader that checks `'run' in reason` keeps working.
- `asked` keeps the original reason for the words and for `RedoStep`'s step.
- Nothing appends it. Only the reduce produces it.

The reduce, in both `reduceWaits` (`ticket.ts:76-136`) and `reduceTicket`'s `lifecycle.reason` (`:587-606`):

- **A wait counts as an ask** when its stored reason is `AgentQuestion` or `ProposedEscalated{InputNeeded}`, or its triage result is `UndecidedQuestion`. That includes a triage of an `AgentCrashed`. Each wait counts once. An `AskLimit` wait does not count, so `used` never passes 5.
- **On `WaitStarted`:** if the reason is an ask and 5 waits already count, store `AskLimit{used: 5, allowed: 5, asked}` as the wait's reason, and as `lifecycle.reason` too.
- **On `WaitTriaged`** (`:113-121`): if this result turns the wait into an ask and 5 others already count, rewrite that wait's reason. Rewrite `lifecycle.reason` as well when `lifecycle.waitId` is this wait.
- `personAsksFromState` becomes that count (`read-model.ts:131-132`). `conduct.ts:1794` and `:4456` already feed it to `causeBoundsFor`.

What the limit wait offers:

- `tableResolutions(AskLimit)` returns exactly `['EditBodyAndStartNewAttempt', 'Close']`. It is written out, not filtered from `asked`'s row.
- `rerunStepOf(AskLimit)` returns `answerStepOf(asked, …)`, so `allowedResolutions` appends `RedoStep` (`wait.ts:554`). The existing `RedoStep` continuation then runs the step the ask would have continued, with no new code.
- Never `AnswerQuestions`.

The exhaustive switches turn red, and each needs a case:

- `continuationOf` returns `null`.
- `grantCriterion` returns `null`.
- `wait-words.ts`'s sentence names `personAsks` and `5 of 5`, then says what was asked.
- `tell.ts`, `report.ts` and `resolution-copy.ts` need the new resolution's words.

Readers do not compute a limit of their own. The board, `task.ts`, `lingtai status` and `waitMoves` read the reason. A reader that cannot read the ticket offers no moves and says the read failed. Attempt 1's `pastLimit` patches are not carried over.

  - Remove `personAsks` from `AgentActionDeps` (`:153-156`, `:223`, `:249`, `:1807`) and from `from-recipe.ts:325`. Nothing at claim reads the count any more; the reduce owns it.

## 6. The CLI and the board

- **CLI.** `lingtai answer` (`apps/cli/src/commands.ts:297`, `ask.ts:76`) branches on the wait.
  - On an `OwnQuestion` it keeps its positional `<choice>`.
  - On a wait whose offer includes `AnswerQuestions` it takes repeated `--pick <q>=<a>`, where `q` is the 1-based question number and is converted to an index. With no picks it takes every recommended answer.
  - `waitCommand` (`wait-command.ts:10-50`) spells `AnswerQuestions` as `lingtai answer … [--pick 1=a]`, and for these waits it comes first. For them, drop `--into-body "<answer>"`.
- **Board.** `triage-picks.tsx` posts `AnswerQuestions`, with the `onSha` the page drew, through `apps/board/src/app/actions.ts` (as `:254` does for `RedoStep`). It is offered for the three wait kinds, not only triaged ones.

## Edges the ticket leaves to the design

- **Redone, and the step's other actions.** The asking step runs again from its first action, as `RedoStep` does (0108 §12, §23), and the actions after it in the step are not skipped. A `design` that asks again is an ordinary sixth-or-earlier stop.
- **A body write that succeeded, then a refused append (`staleResult`, `written: true`).** The section stays in the body, and a retry replaces it by marker. That is the accepted cost: an answer written to a body nobody continues on is harmless; an attempt that continues without the answer is not.
- **A pause.** `AnswerQuestions` lifts no pause. `requestContinuation` is carried out when the conductor resumes, as `RedoStep`'s is.
