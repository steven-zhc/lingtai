# Design note for #728: mypy's path follows the config mypy reads, and ruff lint never fixes

## Where it goes

All of the code change is in `apps/cli/src/detect-setup.ts`, and all of the test change is in `apps/cli/unit/detect-setup.test.ts`. `setup-build.ts` needs no change. It logs `run` and `because` exactly as they come (`setup-build.ts:184-185`). It also probes only the first word, the manager, against PATH, and that word is still `uv` or `poetry` (`setup-build.ts:189-193`).

## The typecheck row stops being data

Today the loop at `detect-setup.ts:376-394` treats all four rows of `PYTHON_TOOLS` the same way. It checks the table first. It then checks the files, and stops at the first hit (`if (because !== null) break`, `:383`). The `run` string is fixed. That shape cannot express *which config mypy reads* or *a run that depends on its contents*.

Restructure it like this:

- Keep the typecheck row in `PYTHON_TOOLS`, so the build order (format, lint, typecheck, test) stays where it is.
- In the loop, send the typecheck row to a function of its own, for example `detectMypy(reader, tool, notes, unreadable)`. It returns `{ run, because } | null`, and the loop adds the manager prefix as it does now (`:393`).
- The other three rows keep today's table-then-files path unchanged.

Do not generalise the row type with a hook just for this one row.

`detectMypy`, in order:

1. `hasOrUnknown(reader, 'mypy.ini')`.
   - **`'unknown'`**: write the existing note (`could not tell whether mypy.ini is at the root`) and return `null`, **even when `[tool.mypy]` is present**. We cannot tell which config mypy would read, so we cannot tell whether `files` is set. That is the ticket's "never taken as no `files`".
   - The existing test at `detect-setup.test.ts:250-257` still passes: its fixture has no `[tool.mypy]`.
2. **Present**: read the file and parse it.
   - **Unreadable or unparseable**: write the existing note and return `null`, again even beside `[tool.mypy]`. mypy itself fails on a broken `mypy.ini` rather than falling back.
   - This changes what happens today, where `[tool.mypy]` meant `mypy.ini` was never opened. The ticket's Edges already state the rule.
3. **Parses, with a `[mypy]` section**: that section decides.
   - A non-empty `files` gives `mypy`, with `because` `` mypy.ini names files ``.
   - Anything else gives `mypy .`, with `because` `mypy.ini is at the root`.
4. **Parses, with no `[mypy]` section**: write a note, `mypy.ini has no [mypy] section; mypy does not read it`, and fall through to step 5.
   - The ticket says such a file "does not count". The note keeps that from being silent, because before this change the same file gave a typecheck.
5. **`[tool.mypy]` in the parsed pyproject.toml** (`tableAt(tool, ['mypy'])`):
   - A non-empty `files` gives `mypy`, with `because` `` [tool.mypy] files is set in pyproject.toml, so mypy checks those ``.
   - Otherwise it gives `mypy .`, with today's `because`.
   - With no `[tool.mypy]`, return `null`.

## Reading `files`

### TOML

`files` is set when it is either:

- a string whose trimmed value is non-empty, or
- an array with at least one element, where every element is a string with a non-empty trimmed value.

Anything else counts as not set: `[]`, `""`, a number, or an array containing a non-string. mypy would reject a non-string itself, and `mypy .` is the conservative answer.

### ini

`configParses` (`detect-setup.ts:275-301`) returns only a boolean. `iniParses` (`:251-269`) validates but extracts nothing. **Do not write a second ini reader beside them.** Turn `iniParses` into a parser, for example `parseIni(text): Map<string, Map<string, string>> | null`, that follows the same configparser rules as its doc comment (`:245-250`):

- A continuation line is appended to the key before it.
- A key is everything before the first `=` or `:`, trimmed and lower-cased (configparser's `optionxform`).
- A section name is case-sensitive, so only `[mypy]` counts.

Then `iniParses(text)` is `parseIni(text) !== null`, so `pytest.ini` keeps one rule set.

For `configParses`, the smallest change is to return the text when it parsed (`string | null`) instead of `true`. Its other callers (`ruff.toml`, `pytest.ini`) only test for non-null.

The ini `files` is set when its value, split on commas and trimmed, has at least one non-empty entry. mypy splits it the same way, and this makes `files = src, tests` and the multi-line form both count.

## Ruff

The only ruff change is `run: 'ruff check --no-fix .'` at `detect-setup.ts:231`. The format row stays as it is.

## Tests that move, beyond the ticket's Done-when

- **`:176`, `:187`**: these become `ruff check --no-fix .`. The mypy lines stay `mypy .`, because `ALL` (`:169`) has no `files`.
- **`:212-216`**: the fixture `'mypy.ini': ''` has no `[mypy]` section, so under the new rule it gives no typecheck. Change the fixture to `'[mypy]\n'`. The expected `because` stays `mypy.ini is at the root`.
- **`:287-298`**: these keep passing. `'  [mypy]\n  strict = true\n'` and `'[mypy]\nplugins =\n  a\n  b\n'` both have a `[mypy]` section with no `files`, so both still give typecheck.

Add one case for step 1 or step 2 with `[tool.mypy] files = ["src"]` beside it. Either `has` rejects for `mypy.ini`, or `mypy.ini` does not parse. In both, the result is no typecheck and a note. This pins the "never taken as no files" edge, which none of the Done-when items cover.

All of this is unit-level. `pnpm test` and `pnpm typecheck` are the whole check, and nothing here touches the integration half.
