# #428: waitTriage — design

## Where it goes

- **New `apps/cli/src/triage.ts`** holds `waitTriage`, a `TriagePorts` interface, and a `triagePorts()` that wires the real ports. The loop goes here and not in `packages/conductor/src/triage.ts`, because that module is "**Pure only.** No runtime, no mirror, no store, no clock — the caller in `apps/cli` (`#428`) gathers the evidence below and runs the agent" (`packages/conductor/src/triage.ts:5-6`). Leave it pure. **Not built this way in #428's own commit.** There is no `triagePorts()` — see "The ports" below, which is where that correction actually lives.
- **`apps/cli/src/discuss.ts`** gets two `export`s: `prepare` (`:107`) and nothing else new. `headOf` (`:148`) is exported already. Nothing in that file changes otherwise.
- **`packages/repo/src/mirror.ts`** gets `diffStatAt`. Put it beside `readAt`/`listAt` and give it the same rule they follow: "**Absence is an answer, never an error**" (`mirror.ts:17`). A failed `git` returns `null` (as at `:60`). Cap the output the way `readAt` caps at `:62-64`. Its test is integration (0060 §1). The unit tests inject it.

## Reuse the pieces, not the two functions

The ticket says to reuse `gatherEvidence` and `holdDiscussion`. Neither can be called as it stands, so take their pieces and their shape:

- **`gatherEvidence` (`apps/cli/src/discuss.ts:168`) is wired to globals.** It reads `eventStore` directly (`:171`, `:175`), calls `projectClient(...).getIssue` (`:191-192`) and `refSha`/`listAt` from `@lingtai/repo` (`:199-213`). It also returns `DiscussionEvidence`, which is indexed by a 1-based `attempt` (`:179`). The ticket wants all four injected. So write a `gatherTriageEvidence(ports, ticketId, reason)` that returns `TriageEvidence` (`packages/conductor/src/triage.ts:53-69`) and follows the same steps through ports:
  - the issue fetch, whose failure becomes `ticketProblem` (as at `:194-196`);
  - base and head refs, each listed only when `refSha` finds it (as at `:201-213`);
  - the head from `headOf` over the run's stream.

  **Not named this way in #428's own commit.** The shipped function is `gatherEvidence` (`apps/cli/src/triage.ts:88`) — module-local, not exported — taking `(deps, request, before)` rather than `(ports, ticketId, reason)`. It is the `discuss.ts` function of the same name this one must not be confused with, not this one.
- **`holdDiscussion` (`packages/conductor/src/discuss.ts:509-583`) appends `DiscussionAnswered` on a chat stream** and parses with `parseReply`. Write the triage loop beside it in `apps/cli/src/triage.ts` and copy its three rules:
  1. a call that threw is turned into a failure and gets **no** `RunSpent` (`:519-536`);
  2. a call that returned gets exactly one `RunSpent` (`:538-547`);
  3. every path ends in exactly one terminal append (`:549-583`).

  Only the event names and the parser are different.

## The decisions the ticket leaves open

### 1. `triage.limits` bounds the whole triage, not each call

`holdDiscussion` hands every round the full `call` (`discuss.ts:525`). There can be `MAX_READ_ROUNDS + 1 = 5` rounds (`read-step.ts:28`). At the default `5m` wall that is 25 minutes. `TRIAGE_WALL_MAX` exists so that triage's wall stays under the subscriber's 10 minutes (`recipe.ts:2942-2949`), and the schema says `limits` is "What one triage run may spend" (`recipe.ts:2972`).

So take one deadline at the first call, `start + triageCallFor(triage).wallMs`, and hand each call only what is left:

- `wallMs: deadline - now`
- `turns`: the limit minus the turns already reported
- `usd`: the limit minus the `costUsd` already reported. A call that reported `null` subtracts nothing, because there is no estimate.

If any of the three is used up before a round starts, end with `TriageFailed` (`timeout`, or `out of turns` / `out of usd`). Do not dispatch.

The unit test "limits equal `triageCallFor(triage)`" applies to the **first** call. Add a second assertion: a later round's `wallMs` is smaller.

**Not added in #428's own commit.** `apps/cli/src/triage.ts`'s only assertion on `limits` is the first call's; nothing there pins a later round's `wallMs` to a smaller number.

### 2. `timeout` vs `aborted` comes from which signal fired, not from `failure.kind`

Both adapters map *any* abort of `RunRequest.signal` to kind `'aborted'` (`claude-code.ts:502-524`, `codex.ts:1165-1195`). If you combine the caller's signal with your deadline using `AbortSignal.any([request.signal, AbortSignal.timeout(remaining)])`, a wall expiry also comes back as `'aborted'`.

So after a call returns, decide the reason in this order:

1. `request.signal?.aborted` → `aborted`
2. the deadline has passed → `timeout`
3. otherwise use the runtime's own `failure`

The returned outcome still gets its `RunSpent` with whatever it reported, and only then comes `WaitTriaged`. If the caller's signal is already aborted before a round starts, append `WaitTriaged` (`aborted`) with no call and no `RunSpent`.

**Not built this way in #428's own commit.** `triage.ts:380-382` decides `timeout` vs `aborted` straight from `outcome.failure.kind`, the thing this section says not to trust; the three-step order above, and the `AbortSignal.any` combination that makes it necessary, are not in the shipped code. What is there is the second half: `request.signal?.aborted` is checked once before each round starts (`triage.ts:306`), so an abort between rounds ends the triage without another dispatch — but a wall expiry *during* a dispatched call still comes back labelled by whatever the runtime itself called it.

### 3. `by.model` when the recipe names none

`TriageAgent.model` and `TriageStartedAgent.model` are required strings (`events.ts:1849`, `:1861`). `triageCallFor` omits `model` when the recipe does (`recipe.ts:3005`). `RunOutcome` reports no model (`runtime.ts:160-175`). Write `triage.model ?? ''`. That is the existing precedent for "the runtime's own default" on a required field (`conduct.ts:3198`, `model: spec.model ?? ''`). `runtime` is `triage.agent`. Use the same `by` on `TriageStarted` and `WaitTriaged`.

### 4. A wait with no `run`

`WaitReason` includes `OwnQuestion`, which has no `run` (`wait.ts:67`). Narrow with `'run' in reason` so that it compiles. Without a run, gather no run stream, so `routed`, `published` and the head are all null, and carry on. **Do not refuse here.** Whether to triage is `triageStatus`'s decision (#444), and the ticket says not to check the kind a second time.

### 5. The diff stat is three-dot

Use `git diff --stat <base>...<head>`, not `<base> <head>`. The refs are the base branch's current tip (as Discussion lists it, `discuss.ts:199`) and the head. A two-dot diff against a `main` that moved after the run started would show every change `main` gained as if the attempt had reverted it. Three-dot diffs from the merge base, which is "what this attempt changed".

When there is no head (`NothingProduced`):

- do not call `diffStatAt`, and pass `diffStat: null`;
- `headSha` is the base sha, as the ticket says;
- if the mirror has no base either (`refSha` → `null`), `headSha` is `''` and the triage still runs on the body and the wait alone. A missing mirror is "a fact … and 'no file can be read' is the honest brief for it" (`discuss.ts:165-166`).

### 6. `published` is the run stream's last `RunRefsPublished`

Read it the same way `headOf` reads its events: a last-wins scan over the run's stream. `routed` is the last `PassRouted` on that same stream. Neither is an extra request, because the run stream is read once and both are taken from it.

## The ports

**What shipped, not the shape above.** `apps/cli/src/triage.ts:52-70`:

```ts
interface TriagePorts {
  store: EventStore
  runtime(agent: DiscussAgent, options: { tools: 'none' }): Runtime
  mirror: { refSha; listAt; readAt; diffStatAt } // @lingtai/repo's signatures
  issue(ticketId: string): Promise<{ ref: string; title: string; body: string }> // throws → ticketProblem
  base(ticketId: string): Promise<string>
  prepare(id: string): Promise<{ cwd: string; settingsPath: string }> // discuss.ts's, exported
  now(): number
  log?(line: string): void
}
```

No `project` port — `base(ticketId)` alone, rather than a lookup that also hands back a name. **No `triagePorts()`**: the file's own header says so — "this file does not wire them" — and nothing in `apps/cli/src/triage.ts` calls `eventStore`, `createRuntime`, `loadProject` or `@lingtai/repo` directly. Wiring the real ports is `#413`'s and `#447`'s, not this ticket's.

- The `prepare` id is `triage-<waitId>`.
- The runtime's `runId` is `triage-<waitId>:<attempt>:<round>`, unique per call, for the reason given at `discuss.ts:380-383`: reusing one would make the runtime resume a session.
- Build the call the way `discussionAsk` does (`discuss.ts:242-262`): `model` spread in only when present, `env: runnableEnv({})`, plus `signal`.
- No run log in this ticket. `RunRequest.log` is optional. If #413 wants the board to follow a triage, that is its own change.

## Never throws

- Wrap everything after `TriageStarted` in one `try`. Its `catch` appends the failed `WaitTriaged` carrying the error's message.
- Clip every `why` to `TRIAGE_TEXT_MAX`. `TriageFailed.why` is `.max(TRIAGE_TEXT_MAX)` (`wait.ts:557`), and an adapter's `detail` has no bound, so an unclipped one would turn a failure into a refused append.
- If the store refuses the `TriageStarted` append, log it and return the result anyway — nothing was dispatched, so there is nothing a later `WaitTriaged` would be reporting on.
- **Not the `WaitTriaged` append.** That one is retried (the same five-attempt bound as `RunSpent`) and, if it still will not land, *thrown* rather than swallowed: it is the one append this function's contract is about, and a caller told `TriageAdvised` landed when the log carries no `WaitTriaged` is exactly `triageStatus` reading `Interrupted` and buying a second triage of a wait this one already answered.
- If reading the stream fails before `TriageStarted`, nothing is appended and the function returns `{ attempt: 0, result: TriageFailed }`. That is the one path that ends with no `WaitTriaged`, because no attempt was ever started.

## The read loop

- `parseTriage` returns `read`, `advised` or `refused` (`triage.ts:293-297`).
- On `read`, while `round < MAX_READ_ROUNDS`: serve each `ref:path` through a ref→sha map, so the file comes from `readAt` at that commit (as at `discuss.ts:363-368`). Then go round again.
- On `read` at the last round, end with `TriageFailed('out of read rounds')`.
- On `refused`, end with `TriageFailed(reply.why)`. Do not retry. Discussion ends on an unreadable reply too (`discuss.ts:571-582`), and a retry would be a second paid call that the attempt count does not show.

## What `pnpm test` can and cannot see

- Every Done-when item is a unit test against the ports above.
- `diffStatAt`'s own test spawns `git`, so it belongs in `packages/repo/integration/` and nothing before the merge runs it. What stands in for it before the merge is the unit test showing that the stat the stub returns reaches `triageBrief`'s evidence.
- Nothing here proves the real adapters kill the process on abort. `claude-code.ts:523` is what claims that, and only a real run will show it. The `RunSpent` with `turns`/`durationMs` from a killed call, followed by a `WaitTriaged` whose `result.why` is `aborted` with no later event on the ticket stream, is what would settle it in the log.
