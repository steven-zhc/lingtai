# Design note: #766, `lingtai start` prints one line per ticket

## Where the line actually has to go: five places, not two

The ticket names `report` in `apps/cli/src/conduct.ts:324-329` and the continuation twin. The pass's ending is printed in **five** places, though, and the busiest one is in the scheduler, not in `conduct.ts`:

| site | path |
|---|---|
| `apps/cli/src/conduct.ts:324-329` `report` | a detached `launch` (0122) |
| `apps/cli/src/conduct.ts:409-411` | an awaited continuation |
| `apps/cli/src/conduct.ts:466-468` | an awaited hand-picked issue (`lingtai now`) |
| `packages/conductor/src/schedule.ts:273` `reportEnding` | a detached queue pass |
| `packages/conductor/src/schedule.ts:331` `reportEnding` | **an awaited queue pass. This is the ordinary case, and the one round A ran** (its `taking ticket-…` came from `schedule.ts:309`) |

Change only `report` and a plain `start` still prints no line for any queued ticket. The `held at proposed` in the experiment's excerpt is printed by `reportEnding` (`schedule.ts:353-357`).

So the shape is **one formatter and one callback**:

- **`ScheduleOptions`** (`packages/conductor/src/schedule.ts:~100`, beside `log?`) gains two optional observers: `took?: (entry) => void` and `ended?: (result: RunOnceResult) => void`.
  - `took` is called beside both `taking` lines (`:250`, `:309`).
  - `ended` is called beside both `reportEnding` calls (`:273`, `:331`).
  - `reportEnding` itself stays and keeps writing to `log`, which is now trace. That is why `--verbose` still prints `held at proposed` exactly as today.
  - A throw from either observer is caught. It must not end the pass.
- **`ConductWorkOptions`** (`apps/cli/src/conduct.ts:148`) gains `tell: (line: string) => void`, the person sink.
  - `conductWork` hands `took` and `ended` to `runQueue` (`:475`).
  - The three local ending sites call one local `tellEnding(result)`, which writes the line through `tell`.
  - The three existing `options.log` ending lines stay, on trace.
- The formatter is a pure exported function in `apps/cli/src/conduct.ts`, `endingLine(result, { project?: string })`. It returns `string | null`, and `null` means a declined-before-work result. The unit tests drive this function. No daemon is involved.

`common.log` (`conduct.ts`, inside `CommonPassOptions`) is the `log` that `runOnce` gets. It stays trace, so every line `packages/conductor/src/conduct.ts` writes moves off the terminal without touching that file's call sites.

## The waiting command: share #763's rule, don't copy it

#763 landed its rule as a private function, `waitCommand` in `apps/cli/src/status.ts:627-631`:

```ts
if (reason === 'SignoffRequired') return `lingtai approve ${project} --issue ${ref}   (or the board)`
if (reason === 'OwnQuestion') return `lingtai answer ${project} --issue ${ref} "<choice>"   (or the board)`
return 'decide on the board'
```

- Export it, keyed on `WaitReason['_tag']`, and call it from `endingLine`. The ticket's own warning, *one command rule, not two*, means a second copy in `conduct.ts` is the wrong answer. #769 will widen this function, and both commands should follow when it does.
- **It already carries `   (or the board)`**, so the line is `waiting for you: ${waitCommand(...)}`, with nothing appended. Appending the ticket's literal `(or the board)` would print it twice.
- For the third branch the line reads `waiting for you: decide on the board`.

## The summary on `RunOnceResult`

`RunOnceResult` is at `packages/conductor/src/conduct.ts:521-529`. Add `summary?: PassSummary` to all three variants, optional so that `test/one-pass.ts` and the other callers compile unchanged. It carries:

- **`ref` and `title`.** These are on the ticket from claim onwards. A result that never reached claim (`recipe`, `env`, at `:724`, `:742`, `:864`, `:868`, `:900`) carries no summary.
- **`ran: { step, ending }[]`**, built from `pass.steps` with the **same test `passLine` already applies** (`conduct.ts:567-576`). Its doc comment: *"A visit that passed having run no action, at a step the recipe declared nothing for, prints `skipped`"*.
  - Factor that predicate out of `passLine`, and use it in both places, so the `pass:` line and the person line cannot disagree about which step ran.
  - #730 has landed, so this is reuse, not new logic.
- **`cost: { usd: number; unknown: number }`.** Keep a local accumulator next to `runSpentFrom` (`conduct.ts:2500`).
  - Every place that appends one (`:2661`, `:3696`, `:3741`, `:3909`) adds that run's dollars, or adds 1 to `unknown` when the outcome reported none.
  - A judge's run (`:2661`) counts: it is money this pass spent.
- **`wait: WaitReason['_tag']`** on the `held` variant. `reason` is in scope where it returns (`conduct.ts:4660-4671`).

#738 has not landed: only its design note is in the tree. So format the cost as `$${usd.toFixed(2)}`, the same way `discuss.ts:422` does, and keep it in one small function next to `endingLine` that #738 can replace. The rules: `cost unknown` when `usd === 0 && unknown > 0`; `$0.40 + 1 unknown` when both are non-zero; and never `$0.00` for an unknown (0110 §7).

## Which lines go to which sink: one rule

**A line that says why something did not happen, or that a person's hand is on, goes to the person sink. A line that says what the machinery did goes to trace.** That settles the lines the ticket's table does not list:

| line | sink |
|---|---|
| `${name}: not looked at — ${why}` (`apps/cli/src/conduct.ts:657`) | person: a refusal |
| `${name}: ${err.message}` (`apps/cli/src/conduct.ts:677`) | person: a refusal |
| `${name}: #${issue} failed — …` (`conduct.ts:357`) | person: a failure |
| `${entry.taskId}: pass failed — …` (`schedule.ts:279`) | person: a failure. This one is inside the scheduler and only has `log`, so route it through `ended`'s sibling, or give `ScheduleOptions` a `fail?` sink |
| `${name}: #${issue} not started — ${paused}` (`conduct.ts:340`) | person: the pause sentence |
| `runtime.concurrency N is ignored …` (`conduct.ts:309`) | person: it is why only one pass runs |
| `${name}: #${issue} ${why}` (a file collision, `conduct.ts:345`) | trace: the ticket runs on a later look |
| `continuing #… — asked for by …` (`conduct.ts:384`) | trace: the result line follows it |
| `skipping …`, `stopped: … — N run(s)` (`schedule.ts`) | trace |

`conductorPass` takes a single `log` (`daemon.ts:577`). It also needs `tell`, which it passes through to `conductWork` and to `conductProjects`'s refusal lines.

`paint.fail` lines, `console.error` lines and the paused and draining `paint.held` lines in `daemon.ts` keep their direct `console.log` / `console.error` calls. Do not route them through `trace`.

## Flag wiring

`startFlags` is at `apps/cli/src/cli.ts:1028`, not `:991`. `startCommand` is at `:1030-1041`.

- `restart` also enters `daemonCommand` (`daemon.ts:859`). It must get `verbose: true`: what `restart` starts is the supervisor's daemon, or a terminal daemon in its place, and the ticket keeps that output unchanged.
- So `daemonCommand` takes `verbose` as a parameter whose default is `true`. Only `startCommand` passes `name !== 'start' || flags.verbose`.
- The unit test asserts that value for `daemon`, `start` and `start --verbose`, as the ticket says. A fourth case covers `restart`, which reaches `daemonCommand` without passing it.

## Project prefix

`conductWork` knows `name`, but not how many projects there are. The daemon has `registered` at `daemon.ts:297`, so pass `many: registered.length > 1` into `conductorPass`, and from there into `endingLine` and the `took` line. The prefix is only needed in the daemon path. `lingtai run` (out of scope) can pass `false`.

## What stands in for the integration half

Everything here can be checked at unit level:

- `endingLine` over constructed `RunOnceResult`s;
- a fake `runOnce` that drives `runQueue`'s `took` and `ended` (`schedule.ts` already takes `runOnce` through `world`);
- the `verbose` value per command name.

Whether a real held pass carries the right `wait` is settled on the log by `WaitStarted.reason._tag` for that run. The summary is built from the same `reason` variable that is appended there (`conduct.ts:4660`), so there is no separate source to drift.
