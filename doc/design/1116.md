# Design: #1116 — one run at `lingtai`'s entry, and exclusions the ratchet measures

Line numbers below are from this worktree. CLOSE-790a1 has landed here. `apps/cli` measures exactly 14 `async` and 1 run, matching `effect-ratchet.baseline.json:2` and the ticket's table. The one difference is that `runCli` is at `cli.ts:1449` and its run is at `cli.ts:1531`, not `:1486`/`:1568`.

## 1. The bounded close: the trap the ticket's Fix does not see

The ticket says to bound the close with `Effect.timeout(CLOSE_BUDGET_MS)`. Done directly, the close is not bounded.

Both stores close through `closableOnceEffect` (`packages/event-store/src/closable.ts:46-91`, and the projector's `process_` at `packages/projector/src/choose.ts:99-103`). Its comment says: *"Both methods are masked from the start … only the waiting is interruptible."* `close()` is `Effect.uninterruptibleMask`, and the actual `close(opened.value)` runs inside `Effect.exit(work)`, outside `restore` (`closable.ts:68-87`).

`Effect.timeout` interrupts the loser and waits for that interruption to finish. An uninterruptible pg `end()` on a dead network therefore holds `finishEffect` for as long as the socket does. That is the hang #725 bounded with a `Promise.race` that simply stopped listening (`ending.ts:12-30`).

**The shape:** detach the close, then time out the *join*:

```ts
Effect.forkDetach(close).pipe(
  Effect.flatMap((fiber) => Fiber.join(fiber)),
  Effect.timeout(CLOSE_BUDGET_MS),
)
```

`forkDetach` is the Effect 4.1.2 name (`node_modules/.pnpm/effect@4.1.2/.../src/Effect.ts:18425`). There is no `disconnect` in 4.x. `Fiber.join` is interruptible, so the timeout returns on time and the detached close keeps its socket. That is why `exit(code)` must still be called on that path.

- **Stderr line, byte for byte:** `lingtai: the store's connections did not close (${message}); exiting anyway` (`ending.ts:23-25`).
- **Timeout message:** the message for a timeout must stay `no answer in ${CLOSE_BUDGET_MS} ms` (`ending.ts:15`). Map the timeout to that `Error` yourself, because Effect's `TimeoutError` message is not it.

**Unit claim that stands in.** Add a sixth case to `ending.test.ts`: a close that is `Effect.uninterruptible(Effect.never)`, or an uninterruptible sleep longer than the budget. Run it under fake time or a short budget, and assert that `finishEffect` settles and `exit` is called. Without that case the five existing cases all pass with a plain `Effect.timeout`, because their hanging close is an interruptible `new Promise(() => {})`. Nothing would catch the regression.

## 2. `finishEffect` and how a failed run is re-raised

- Run `Effect.exit(run)`, then the bounded close, then either return the code or re-raise the *same cause*: `Effect.failCause(exit.cause)`, not a new error.
- `Effect.runPromise` rejects with `causeSquash(exit.cause)` (`effect/src/internal/effect.ts:5852-5854`). A rejection that entered through `Effect.promise` therefore reaches `reportEnding` as the original `Error`, and its sentence (`entry.ts:78-84`) is unchanged.
- `ending.test.ts` wraps its promise-shaped runs and closes with `Effect.promise`, keeping the five codes (3, 2, 4, 4, 7).
- The case at `:47`/`:54` must still see the thrown error's message after the close.

## 3. Where `closeStores` lives: in `cli.ts`, exported beside `cli`

Today `entry.ts:26-27` does two more dynamic imports inside an `async` callback.

- Define `closeStores: Effect<void>` in `cli.ts`. It loads the two packages with `Effect.promise(() => import(…))`, as `cli.ts:572-582` and `:1047` already do. It then runs `closeProcessLogEffect` and `closeProcessProjectionsEffect` with `Effect.all([…], { mode: 'result' })` and fails with the first failure.
- `entry.ts` then gets `{ cli, closeStores }` from its one `import('./cli.ts')`, so the callbacks need no `async`. `HOST_EDGES` asserts `async: 0` for `entry.ts`, so any `async` arrow left in it goes red.
- `cli.ts` imports neither store at its top level (it lifts them lazily), so this adds no import cost to `help`.
- Keep the three `entry.ts` paths byte for byte:
  - the close-gave-up exit (`:36-43`);
  - init's `process.exit` (`:45-55`);
  - `.catch(reportEnding)`.

## 4. `cli`: keep `catchCause → 1`, and the ticket's first edge is wrong

`cli.ts:1531-1544` ends with `Effect.catchCause(() => Effect.succeed(1))`. Today the parser's run never fails: a handler defect is exit 1 with no `reportEnding` sentence. The ticket's edge says *anything else is a defect, which reportEnding prints*, which would change that.

**Keep `catchCause` exactly where it is.**

- Only what is outside the parser's pipe can reach `reportEnding`: the hand refusals, the `backlog.ts` import at `:1457`, and the `--json` usage branch (`:1546-1549`).
- Each of those becomes an `Effect.sync` or `Effect.promise` inside `cli`, in the same order and with the same words.
- The module-level writes `boardRunner = …` and `runners = …` (`:1453-1454`) and `restartArgs = null` (`:1508`) go inside `Effect.suspend`/`gen`. Building `cli(argv)` must do nothing until it is run.

## 7. The ratchet

- **One table for both lists.** `NOT_COUNTED` and `HOST_EDGES` share the entry shape `{ path, async, run, reason }`.
- **Measured, not trusted.** Each listed file is still `count()`ed, with the same `shared` set, and must equal its entry exactly. A wrong count in either direction is a red that names the file and both numbers.
- **Out of the package total.** Those counts are then left out of the package's total. `NOT_COUNTED` files stay out of `sources` (so out of the package loop), but must still be read and counted for this check.
- **What is printed.**
  - On any problem, print a `not counted, listed as …` block for both lists, next to the faces block (`:765-772`).
  - The red over a baseline (`:748-751`) gains the ticket's sentence.
  - `checkFaces`'s `skip` (`:390`, `:409`) covers both lists' paths, so no face can be listed in an excluded file.
- **Pure function.** Write the check as a pure function in the style of `checkFaces`, taking the list and a `read`. Its unit cases then need no filesystem:
  - a sixth `async` in a listed file is red;
  - a second run in `entry.ts` is red;
  - a count one *below* is red too.
- **`notify.ts` import check.** Walk the parsed file; do not use a regex. Cover:
  - every `ImportDeclaration`, including `import type` (`notify.ts:56` is one);
  - every `export … from`;
  - every `import(…)` and `require(…)` call.

  Each specifier must be `node:*` or exactly `../../../packages/extension/src/index.ts`. A red names the specifier and the line. Add a unit case with one forbidden import.

## Edges

- **A close that never answers:** §1. It is the only edge where this design differs from the ticket's Fix.
- **Ctrl+C:** nothing is installed; not `NodeRuntime.runMain`, as the ticket says. A SIGINT does not interrupt the root fiber, so the daemon's drain (`daemon.ts`'s own listener) is untouched.
- **Process dying halfway, two at once, retries, a stale page:** these do not apply. Nothing here writes.
- **No question needs the log:** this is process-exit behaviour. The unit tests in §1 and §2 are the whole check, and nothing here needs `pnpm test:integration`.
