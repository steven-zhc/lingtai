# #560: `Split` as a resolution with a checked child plan

## Scope: types, a validator and triage advice. No effects.

Three later tickets each take part of 0118 §12: #561 (GitHub writes and reconciliation, blocked by this ticket), #562 (`resolveWait` completes the split and the parent becomes an epic) and #563 (board and CLI flow). **This ticket writes nothing to GitHub and appends nothing new.** Adding `Split` to `Resolution` creates a hazard that this ticket has to close itself:

`resolveWait` checks only `allowedResolutions(reason).includes(tag)` (`packages/conductor/src/resolve-wait.ts:210-218`) and then appends `WaitResolved` (`:299-312`). So once `allowedResolutions` offers `Split`, any caller passing `{_tag:'Split', …}` would get `WaitResolved{Split}` on the log with no children created. That breaks 0118 §11: *"`WaitResolved` records the completed choice; a partial split cannot resolve the wait."* The ticket fold makes it worse. `WaitResolved` with a tag other than Requeue, EditBodyAndRequeue or AnswerQuestion leaves the lifecycle where it was (`packages/domain/src/ticket.ts:373-378`), so the item would show as still blocked on a wait the log calls resolved.

**So `resolveWaitHolding` gets a `Split` branch right after the `not-offered` check. It validates the plan, then refuses.** An invalid plan is refused as `reason: 'invalid-split'`, with every problem named. A valid plan is refused as `reason: 'split-not-built'`, with a detail saying nothing was created or resolved. Both return before any append. #562 replaces the second refusal with the real path, so the validation sits in front of every future external write. This is how "invalid plans are refused before any external write" can be tested in the unit half today: call `resolveWaitHolding` with `createMemoryEventStore()` and assert the store's version did not move.

## The shapes

```ts
ChildTicket  = { key, title, body, kind }        // all strings
Dependency   = { ticket: key, blockedBy: key }   // 0118:221, unchanged
SplitPlan    = { children: ChildTicket[], blockedBy: Dependency[] }
Resolution.Split = { _tag: 'Split', ...SplitPlan }
```

**`kind` is new to 0118's sketch.** `ChildTicket` there is `{ key, title, body }` (`0118:220`), and the ADR says those values *"describe the person's approved plan, not a claim that these contracts are implemented"* (`:241-242`). The ticket's *Want* names kinds explicitly, and a child without a kind is invisible to the queue (CLAUDE.md, *An issue needs a kind label or the queue never sees it*). Adding the field fills in the sketch and contradicts no decision. Leave 0118's text for #564, which owns *"0118 … describe built … split resolutions"*.

**The proposal and the approved command share one schema and stay two values.** Triage's plan goes **on the cause**, as `TicketTooBig{ split?: SplitPlan }`. That follows the house rule *"the parts belong to the cause"* (`triage.ts:137-139`): fixes live in `FixableLines` and hunks in `ConflictingHunks`. Make `split` **optional, not nullable-required**. `WaitTriaged` rows already on the log hold a bare `{_tag:'TicketTooBig'}` (strictObject, `wait.ts:570`), and they must still parse. The approved plan exists only as the `Resolution.Split` a person submits. Nothing copies triage's plan into a command. #563 seeds an editor from it, and the editor's output is what gets submitted.

**`TriageAdvised` refuses `resolution: 'Split'` unless `cause` is `TicketTooBig` and carries `split`.** Put this as a `.superRefine` on `TriageAdvised` (`wait.ts:594-600`). zod 4 is in use (`packages/domain/package.json`, `^4.5.4`), and `ConflictingHunks` already puts a refined member inside a discriminated union (`:558-567`). A refused answer reaches `parseReply`'s `safeParse` (`triage.ts:394-397`) and becomes a failed triage, as 0118 §4 requires: *"Advice that will not parse into a cause and its parts is recorded as a failed triage."*

## The validator: one pure function, two callers

`splitPlanProblems(plan, { kinds?: readonly string[] }): SplitProblem[]` returns an empty array when the plan is valid. Each problem is a tagged value naming the keys involved, so #563 can point to the exact row. It checks, in this order:

- **At least two children.** A split into one child is an `EditBodyAndRequeue` plus an epic with nothing to coordinate.
- **Keys:** each matches `^[a-z0-9][a-z0-9-]*$` and is bounded. Duplicate keys are refused.
- **Title and body:** each non-blank after trim. A blank body cannot be worked from.
- **Dependencies:**
  - each `ticket` and `blockedBy` names a child key (*missing node*);
  - `ticket !== blockedBy` (*self*);
  - no duplicate edge;
  - no cycle. Use DFS or Kahn's algorithm and report the keys on the cycle.
- **`kind ∈ kinds`, only when `kinds` is given.** A kind outside the recipe's `source.kinds` is *the plan that leaves a child invisible to the queue*.

The two callers:

1. **The zod refine on `SplitPlan`**, called without `kinds`. The structural graph rules then hold wherever the schema parses: triage's answer, and `WaitResolved.resolution` through `parsePayload` (`events.ts:309-314`). The domain cannot see the recipe, so the schema cannot check kinds.
2. **`resolveWaitHolding`**, called with `kinds`. Add `kinds?: readonly string[]` to `ResolveWaitOptions`. A `Split` arriving without it is refused by name (`no-kinds`), the same way a missing `client` is refused for `Approve` (`resolve-wait.ts:469-476`) and not skipped. Triage's proposal is never checked against kinds: triage may guess a kind, and the person corrects it.

Bound the proposal's text with `TRIAGE_TEXT_MAX` for `title`. Add new constants beside the others in `packages/domain/src/triage.ts:23-34`: a children cap (8) and a body cap, which `TRIAGE_TEXT_MAX`'s 500 is too small for. Those caps apply to the proposal only. The person's command keeps only the structural rules.
