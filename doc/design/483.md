# Design: #483, the waiting card's four board files stop reading `Hold`'s shape

## What the four files actually read today

**None of the four files names the type `Hold`.** Run `grep -nwE 'Hold' apps/board/src/app/{actions.ts,decide.tsx,rail.tsx,standing.tsx}` and it finds nothing. What they read is `Hold`'s *projection*: the `needs`/`diagnosis` columns `legacyColumns` writes, which reach them as props on `BoardCard` (`lib/board.ts:184,193`) and `StandingView` (`lib/task.ts:410,412`). They also read one lifecycle field that only a `Question` hold sets. Those views are `lib/`, which is #484's. So this ticket changes what the four files *decide* and *name*, and leaves the props they are handed alone. The same split appears in `doc/design/487.md`'s first section: *"the ticket's Problem row is wrong about that word"*.

Every old name in the four files, from the 0120 appendix's *Today* column (`doc/decisions/0120-a-reason-is-a-type.md:631-650`):

| Site | Name | Kind |
|---|---|---|
| `actions.ts:573-574` | `reduceWorkItem(...).lifecycle`, `status === 'blocked' && runId === null` | **the one decision**: "is this an `OwnQuestion`" |
| `actions.ts:14-15` | `ApprovalRevoked`, `StepWaived` | comment |

`IntegrationRefused` (`rail.tsx:222,326`) stays. The appendix keeps that name and only drops three of its fields. `reduceWorkItem` is domain's reducer, not an event. #487 left it alone too (`ask.ts:130` still reads `item.lifecycle.status`).

Rewrite each comment in 0118's words: *a wait started*, *the wait resolved*, *a sign-off was requested*, *a waiver*. Don't drop the history the comment carries (#150, #147).

## Decision 1: `sendAttempt` reads `waitsOf`, the way `answer()` already does

`actions.ts:573-576` refuses Send on a question asked before any run. Mirror `ask.ts:130-139` (#487 Decision 2) exactly:

- Keep `reduceWorkItem(events).lifecycle.status === 'blocked'` as the first test.
- Then `const wait = waitsOf(events).at(-1)` and refuse when `wait !== undefined && allowedResolutions(wait.reason).includes('AnswerQuestion')`.
- Keep the detail string byte-identical.

Only `OwnQuestion` offers `AnswerQuestion` (`wait.ts:226-227`), and only a `Question` hold maps to `OwnQuestion` (`read-model.ts:984-985`), so this answers exactly what `runId === null` answers. Read the item stream alone. That arm reads no other event, which is #487's own finding.

**Do not gate on `EditBodyAndRequeue`, though Send is that move.** `MergeRefused` and `SetupRefused` omit it (`wait.ts:248-251`), so Send would start refusing on cards where it works today.

Imports: `waitsOf` from `@lingtai/domain` (it is in the barrel, `index.ts:11`) and `allowedResolutions` from `@lingtai/domain/wait`. This is a `'use server'` file, so either import is safe.

There is no unit test of `sendAttempt`, and none can be added cheaply. A `'use server'` module may only export async functions (`actions.ts:60`), and this one reaches `eventStore`. The unit-level claim that stands in is #487's `packages/conductor/unit/wait-handlers-answer-as-today.test.ts`, which pins the same `AnswerQuestion` ⇔ `Question` equivalence for `answer()`. Do not extract a helper into `lib/` to test it, because `lib/` is #484's.

## Decision 2: the buttons stay decided by `awaitingSha`, not by `allowedResolutions`

The card's buttons are not chosen in these four files. `page.tsx:378-405` draws `Decide` iff `card.awaitingSha`, then `Requeue`, then `Close`. `standing.tsx:400-455` does the same on the task page. **`allowedResolutions` disagrees with #482's pins**, so it cannot decide which buttons appear without turning them red:

- `waiting-card.test.tsx:158-187`: `ProposedEscalated{BuildRed}` pins `['Approve', 'Back to the queue', 'Close']`, but `allowedResolutions` omits `Approve` for `BuildRed` (`wait.ts:240-244`).
- `waiting-card.test.tsx:419-448`: `AnswerUnreadable` pins `Approve`, but its row is `EditBodyAndRequeue, Requeue, Close` (`wait.ts:255-259`).

Those are #487's disagreement cells (`doc/design/487.md`, Decision 2), and refusing them is #443's change. So in `standing.tsx`, do not replace `standing.awaitingSha !== null` with an `allowedResolutions` test. The pins pass unedited because nothing the card renders from changes.

**`decide.tsx`'s prop types stay as they are.** `Recommended` (`decide.tsx:33`) is `BlockRecommendation.action`'s vocabulary (`events.ts:228`). Moving it to `Resolution['_tag']` would force both call sites in `page.tsx:386,394`, which is not one of the four files. The conversion would also have no home here:

- A client module cannot export a function to a server component (`decide.tsx:37-40`).
- `lib/` is #484's.

#484 rewrites `BoardCard`/`StandingView` and their call sites together, so that ticket changes the prop. **Add no import to `decide.tsx` at all.** It is `'use client'`, and keeping its import list unchanged is the simplest way to stay clear of #230.

## Decision 3: `describeHold` stays in `standing.tsx`

`standing.tsx:6` imports `describeHold`/`HoldLine` from `@lingtai/projector/task-view`. `grep -w Hold` does not match either name, and both read `needs`/`diagnosis` off `StandingView`. Rewording those lines inside `standing.tsx` would make a second copy of words that `page.tsx` and `apps/cli/src/status.ts` share. `task-view.ts:1045-1047` forbids that: *"two places that disagree about why something is blocked is the failure this repository keeps finding — so the wording is decided once, here"*. Renaming it in the projector is outside these four files. Leave it, and change only the comment at `:242`.

## Tests: `standing.test.tsx` onto the builders, and nothing else

`standing.test.tsx` builds events with its own `e()` (`:26-38`). That includes 10 `WorkItemBlocked` with raw `hold` literals (e.g. `:63-75`, a `Routed{when:'findings'}`), 3 `ApprovalRequested`, 1 `ApprovalGranted`, 1 `RepairRequested`, and step verdicts.

- Move them to `@lingtai/domain/test/events`: `aWait`, `aClaim`, `aRelease`, `aResolution`, `aRepairRequested`, and `aRun(...)`'s step methods.
- For types with no builder, use `makeStream` from `@lingtai/domain/test/support`.
- **Assertions are not edited.** `aWait` goes through `holdOf`, and its hold may differ from the hand literal in a field an assertion reads (`why`, `raw`, `findings`). Where it does, use `aLegacyHold(item, <the literal>)` (`test/events.ts:442`) and add a one-line comment naming the field.
- `makeStream` validates payloads, so a hand payload that was never valid fails at once. Fix the payload to the real shape, not the assertion.

Leave `rail.test.tsx` and `task-page.test.tsx` alone. Their events are inputs to `foldProgress`/`loadTask` (`lib/`, #484's), and `Rail`'s own input is `RunProgress`, not events. `close.test.tsx`, `requeue-note.test.tsx` and `moves-row.test.ts` build no events.
