### Exhaustiveness has to come from the compiler, not from a missing `default`

A `switch` with no `default`, followed by facts logic after it, is **not** checked: a new `WaitReason` tag would silently fall through to the facts, which is the thing 0118 §3 forbids. `defaultResolution` gets its check from a different shape (`wait.ts:458-476`). Every case `return`s, nothing comes after the switch, and the declared return type makes `tsc` refuse a missing tag (*"Function lacks ending return statement"*).

`triageStatus` should use that same shape:

```ts
export function triageStatus(reason, facts, context): TriageStatus {
  switch (reason._tag) {
    case 'OwnQuestion':
    case 'SignoffRequired':
      return { _tag: 'NotNeeded' }
    case 'AgentQuestion':
    case 'FixerDisagrees':
    /* …every other tag, listed by name… */
      return statusOfFacts(facts, context)
  }
}
```

- `statusOfFacts` is an unexported helper. It holds steps 2–4 of the order.
- Take the list of other tags from `defaultResolution`'s cases: `BudgetExhausted`, `AgentCrashed`, `ProposedEscalated`, `AgentQuestion`, `FixerDisagrees`, `NothingProduced`, `CheckRefused`, `MergeRefused`, `SetupRefused`, `AnswerUnreadable`.
- `recommendedResolution` becomes `switch (status._tag)` in the same style. `Done` keeps its inner check on `status.result._tag === 'TriageAdvised'`, and `TriageFailed` falls back to the default. The other five tags return the fallback. Keep the shared `allowed`/`fallback` computation outside the switch so the existing tests at `wait.test.ts:206` pass unchanged.

### `triageFactsOf`: "latest" means highest `attempt`, matched by `waitId`

- **Choosing `started`:** filter `TriageStarted` envelopes whose `data.waitId === waitId`, then take the one with the highest `data.attempt`. Use the attempt number, not the position in the slice.
  - `read-model.ts`'s header promises every function *"is correct on any superset of that slice"* (`read-model.ts:9-12`). An attempt number is stable under that promise; a position is not.
  - `events.ts:1871` defines `attempt` as *"one more than the last `TriageStarted` for it"*, so the highest attempt is the latest.
- **The `at` value:** `started.at` is the envelope's `at`, which is already a `Date` (`envelope.ts:88`). Do not copy or parse it.
- **Choosing `result`:** take the `WaitTriaged` with the same `waitId` **and** `attempt === started.attempt`. This follows `events.ts:1883-1884`: *"`attempt` matches the `TriageStarted` it finishes; a reader takes only the latest attempt's result."*
- **A `WaitTriaged` with no matching `TriageStarted` gives `result: null`** (and `started: null` if there are no starts at all). Nothing in 0118 appends one, and returning a result with no attempt behind it would make a fact up.
- **Test this case too:** attempt 1 started and triaged, then attempt 2 started. That gives attempt 2 as `started` with `result: null`, and the status is `Running`/`Interrupted`, not `Done`. The ticket's first `triageFactsOf` checkbox covers it; also assert the resulting `triageStatus` in the same test.

### The time comparison

Use `started.at.getTime() < daemonStartedAt.getTime()` for `Interrupted`. Starting exactly at `daemonStartedAt` is `Running`, as the ticket requires, and the test should use two identical `Date`s to pin that edge. No `Date.now()` anywhere.
