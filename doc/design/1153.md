## 1. `RunSandbox` becomes one read, then a wrap with no reads

`RunSandbox` is in `packages/actions/src/process-action.ts:42`. Today its `wrap` reads the profile itself (`packages/conductor/src/sandbox-decision.ts:80-84`). Split it into three members:

```ts
type OperatorProfile = ReturnType<typeof operatorCodexDenies>   // the value wrap computes today
interface RunSandbox {
  /** The only reader of the operator's Codex profile on a command's path. One call per command. */
  profile(worktree: string, env: Record<string, string>): OperatorProfile
  /** Reads nothing. The fingerprint of the policy `wrap` would apply with this profile; without one, the policy before any profile. */
  fingerprint(worktree: string, profile?: OperatorProfile): string
  /** Reads nothing. Refuses on `!profile.ok` and on `collidingDenies`, as today. Notes `profile.note` to `log`. */
  wrap(command, worktree, env, profile: OperatorProfile, log?, keys?): Effect<Wrapped, SandboxWrapError, Scope>
}
```

- In `makeRunSandbox`, `fingerprint` and `wrap` build their `WrapInput` through **one private `inputOf(worktree, env, profile)`**. That function is today's `:98-106`. Sharing it means the recorded key and the applied policy cannot disagree. `fingerprint` is `service.fingerprintOf(inputOf(…))`.
- `process-action.ts:162-169` calls `sandbox.profile(context.cwd, spec.env)` once and hands the value to `wrap`. This is the S6a path. After this change it is the only way a `run:` command is wrapped.
- `profile.note` stays a log line written inside `wrap` from the value it was handed. Logging a value is not a read.
- **The agents' wrap is outside this ticket.** That is `packages/agent`'s own `RunSandbox` (`claude-sandbox.ts:29`), whose `operatorCodex` thunk reads once per launch (`claude-code.ts:464-469`). The ticket names the actions/conductor `RunSandbox`, so leave the agents' one alone.
- Update the fakes in `conductor/unit/sandbox-decision.test.ts:99` and `sandbox-record.test.ts:141`. Pin it in a test: a `readCodexPermissions` counter equals 1 per command for a wrapped `run:`, and 1 per command for a base check.

## 2. `policyFingerprint` replaces the worktree as a path prefix everywhere

Take `agent/1153`'s `fingerprintSource` and change one thing. It builds from `{ ...input, worktree: WORKTREE_PLACEHOLDER }`, which removes the tree only from `filesystemFor`'s own uses. The profile's relative denies arrive as `caller_additions.deny` entries under the real tree (see above). Before building, map every entry of `project_additions.*` and `caller_additions.*`:

- `p === worktree` becomes `<worktree>`;
- `p.startsWith(worktree + '/')` becomes `<worktree>` + the rest.

Test it: a profile whose relative key is resolved against `/x/base-abc1234-r1` and against `/x/base-abc1234-r2` gives one fingerprint.

## 3. The base check: dedupe before the cut, key after it

The person decided that the profile is read once per command, *after the cut*. So the recorded boundary cannot be known until the tree exists. Add one field to the question, beside `tree` (`base-check.ts:53`): `sandbox?: RunSandbox` (absent means *unsandboxed*). Then the order is:

1. **`ask` (`:219-235`).** `fp0 = q.sandbox ? q.sandbox.fingerprint(path) : 'unsandboxed'`, where `path` is `deps.worktreePath(…)`, now computed in `ask`. The in-flight key is `[stream, baseSha, command, fp0]`. This is "the fingerprint alone": no profile, no read.
   - Two projects never share a run anyway, because the stream is per project (`integrationStream(q.project, q.base)`, `:221`).
   - One project asked sandboxed and unsandboxed on one commit runs twice.
2. **Unsandboxed** (`q.sandbox` absent): exactly as today. Read the log first, matching `(data.boundary ?? 'unsandboxed') === 'unsandboxed'`, and cut only on a miss. Always write `boundary: 'unsandboxed'` on new events.
3. **Sandboxed**:
   - Cut first. Do not plant yet: the planted env file holds secrets, and a cache hit needs no env file.
   - Read `profiles = [...prepared, command].map(c => q.sandbox.profile(path, c.env))`. This is the only read.
   - If any profile is `!ok`, answer `unknown` with its refusal sentence and record nothing. This is the same outcome as a wrap that failed.
   - Otherwise `fps = profiles.map(p => q.sandbox.fingerprint(path, p))`, and `boundary = every equal ? fps[0] : sha256(JSON.stringify(fps))`. In the ordinary case all are equal, so a test can assert `boundary === fingerprintOf(…)`.
   - Read the log matching `(data.boundary ?? 'unsandboxed') === boundary`. On a hit, remove the tree and answer `from: 'log'`.
   - On a miss, plant, then run each command through `Effect.scoped(q.sandbox.wrap(['/bin/sh','-c',c.run], path, c.env, profiles[i]).pipe(flatMap(w => deps.run({…, wrapped: {argv: w.argv, env: w.env}, ownGroup: true}))))`. This follows `process-action.ts:160-183`.
   - A wrap error becomes `{ ok: false, exitCode: null, timedOut: false, durationMs: 0, evidence: wrapRefusal(c.run, e) }`. The existing *did not succeed* path (`:151-153`) and *did not run to an exit code* path (`:174-176`) then answer `unknown` and record nothing. Never fall back to an unwrapped spawn.
   - Record with `boundary`.
   - The existing `Effect.ensuring` removal (`:158-168`) must enclose the profile read and the log read too.
4. **Abort.** Keep the `q.signal.aborted` check before the first spawn. Add one after the wrap resolves (it is awaited, and `runCommand` only hears aborts that come after it starts, `:136-137`).

**The cost, which is deliberate:** under a sandboxed decision a cache hit now pays for a cut, a `submodule update` when the recipe uses submodules (`conduct.ts:3781-3788`), and a removal. That is the price of reading the profile after the cut. Unsandboxed asks cost what they cost today.

`makeRunSandbox` is called without `keys`, so `wrap` takes the plain `service.wrap` branch (`sandbox-decision.ts:108-109`) and appends no `SandboxBoundaryRecorded`. `BaseChecked.boundary` is the record of what the check ran under.

## Edges not in the ticket

- **The profile is read once per command, and each command gets its own reading.** `HOME` comes from each command's own `env`. So a `prepared` command and the checked command can carry different denies. The digest of `fps` keeps that distinction, and each command's wrap is handed its own reading.
- **The first asker's run answers a joined asker.** The joined asker's profile is never read. Both asks are in one process with one stream and one `fp0`, and the boundary recorded is the one that ran. This matches the ticket's *"whatever was read once is what ran"*.
- **What settles behaviour in production:** `BaseChecked.boundary` on `int-<project>-<base>`. There should be one event per `(baseSha, command, boundary)`, and `'unsandboxed'` should appear only from passes whose `SandboxBoundaryRecorded` says unsandboxed.
