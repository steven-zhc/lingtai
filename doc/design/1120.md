## Design note for #1120: two decisions the ticket leaves implicit

The ticket is close to a diff already. Follow it. These are the two places where reading it literally builds the wrong code.

### 1. The port aborts a standing merge before it checks for dirt, which is the reverse of the ticket's Fix 1 order

Fix 1 lists the steps as (1) a dirty tree answers `failed`, then (2) a standing `MERGE_HEAD` is aborted. Built in that order, step 2 can never run. A standing merge always leaves `UU`/`AA` porcelain lines, so step 1 turns it into `failed` first. Then the ticket's own edges, *"A retry: the port aborts any standing merge first"* and *"A later round aborts the standing merge first"*, become false, and a second conflict round goes to a person.

The order is:

1. `rev-parse -q --verify MERGE_HEAD`. If it succeeds, run `merge --abort`. If the abort fails, answer `failed`.
2. `status --porcelain`. Anything other than `onlyThePlantedFileIsDirty(…, recipe.env.plantAt)` (the same check `keepUncommittedWork` uses at `conduct.ts:2166`) answers `failed` and names the paths.
3. `merge-base HEAD <baseSha>` gives `fromSha`.
4. `merge --no-commit --no-ff <baseSha>`.
5. `diff --name-only --diff-filter=U -z`, split on NUL.

A `rev-parse … MERGE_HEAD` that exits 1 means no merge stands: that is how git says the ref is missing. Any other failure (exit 128, a killed process, a spawn that failed) is *unknown*, not absent, and answers `failed`, so unreadable merge state goes to a person. Every other failed read answers `failed` too.

### 2. In this port, a failed merge is the success path, so do not copy `mergeBase`'s failure branch

`mergeBase` (`conduct.ts:3307-3324`) treats `Result.isFailure(merged)` as the end. It runs `merge --abort` and answers `{ failed }`. The new port has to do the opposite:

- **Step 4 failed**: go to step 5. Non-empty paths answer `{ conflicted: { paths, fromSha } }` with the merge left standing.
- **Step 4 failed and step 5 found no paths**: the merge failed for some other reason, such as an untracked file in the way. That is `merge --abort` and then `failed`.
- **Step 4 succeeded**: also `merge --abort`, then `failed` with the *"did not reproduce"* sentence. `--no-commit` leaves a `MERGE_HEAD` even on a clean merge.

Do not factor `mergeBase` and this port into one helper. Their failure branches mean opposite things, and a shared helper is how the abort would end up on the conflicted path.

### Where the after-round check reads from

`conflictMerge` is route state in `runAttemptEffect` and reaches `fixRound` on `contextFor()`. The `--is-ancestor` check sits beside `committed` (`conduct.ts:4394-4395`), so it must read `baseSha` from the brief context the round was dispatched with. It must not read the proposal again: by then the route may already have cleared `conflictMerge` for the next lap.

In the test fake, `--is-ancestor` with `ancestor: false` must fail with `RepoFailed`, not answer `''`. An empty answer is what the default fake gives, and it reads as *is an ancestor*.

### Checks

Every claim here can be checked by the unit tests the ticket lists, run against the extended `FakeTree`. The only thing those tests cannot show is that a real `git merge --no-commit` leaves `MERGE_HEAD` and markers on disk. That check belongs in `packages/conductor/integration/` and runs after the merge (0060 §1). Within the pass, the stand-in is the `did` assertion: the full `merge --no-commit --no-ff <baseSha>` args are recorded before the runtime's `run`.
