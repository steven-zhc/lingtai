# Design note for #1120: the conductor merges the base in before a conflict round

The ticket's shape holds, and the line numbers I checked match the worktree. Four things are not obvious from the ticket. In one of them the ticket's Fix 5, taken literally, routes the failure to the wrong place.

## 1. "Committed without the merge" cannot be returned from `fixRound` as a decline

Fix 5 says to run `--is-ancestor` beside `committed` (`conduct.ts:4394-4395`) and "end at a person". The dispatch has only two ways out there, and neither one reaches a person.

- **`return { committed: after }`** goes on to `build`. That is the outcome the gate exists to prevent.
- **`return { stopped, committedNothing: true }`** is not a person either. `attempt-next.ts:136-141` turns it into `FixerDisagrees` only when `changedNothing(outcome)`, and here HEAD did move. Even when it does become `FixerDisagrees`, `routing.ts:265-269` answers it with `round('fix-lines', 'implement', hasCriterion)`, which buys another round.
- **`interrupted: <cause>`** does reach a person, as `AgentCrashed` (`attempt-next.ts:339-355`). But it says the agent crashed, which is not true here.

**Decision: the walk enforces the gate, through a second Effect port. The dispatch does not.**

- Add `mergeCommitted?: (baseSha: string) => Effect.Effect<boolean>` to `AttemptPortOptions`, next to `mergeForConflict`.
  - It is implemented in `conduct.ts` next to `mergeBase`, as `gitAskedEffect(['merge-base', '--is-ancestor', baseSha, 'HEAD'])`.
  - Any non-zero exit, or a failed read, answers `false`.
- In `runAttemptEffect`, after the `implement` visit of a round whose context carried `conflictMerge`, and before the walk moves on to `build`, call the port.
  - On `false`, or if the port is absent, end the same way the `MergeBase` failure does at `run-attempt.ts:1512-1527`. That is `WaitOnPerson` → `ProposedEscalated` → `JudgeHandedOver`, with `why: \`the round committed without the merge of ${baseSha.slice(0, 7)}\``.
- Only run it when the visit committed. A visit that committed nothing is still today's decline path, exactly as the ticket's Edges say.

This keeps the person's sentence exact. It adds no new event type, and it means "no `build` ran" can be asserted at the `run-attempt` level. Both ports are Effects with error channel `never`, the same as `mergeBase`, so the ratchet does not move.

## 2. The port has to answer the overlap, not just the conflicted paths

Fix 2 sets `landedOnBase.paths` to *files changed in `fromSha..baseSha` ∩ files changed on the branch*. But `MergeConflict` carries only the unmerged `paths` (`proposal.ts:68-74`), and the walk has no git.

So the conflicted answer is `{ conflicted: { paths, overlap, fromSha } }`. `overlap` is computed inside the port, after `fromSha` is known:

- `diff --name-only -z <fromSha> <baseSha>` intersected with `diff --name-only -z <fromSha> HEAD`;
- both split on NUL;
- `paths` is unioned in, so a conflicted file is never missing from the overlap.

A failed read of either diff makes the whole answer `failed`. Unknown is never "no overlap".

## 3. The `landedOnBase` type gains `conflicted`, in three places

The shape `{ paths, fromSha, toSha }` is declared three times:

- `ActionContext` in `packages/actions/src/action.ts:542`;
- `AttemptOptions['from']` at `run-attempt.ts:990`;
- the local at `run-attempt.ts:1327`.

Add `conflicted?: readonly string[]` to all three. `landedOnBaseBlock` (`agent-action.ts:433-468`) picks the conflict variant on `conflicted !== undefined`. The `deps.landed` call (`agent-action.ts:159-163`) is unchanged: it still reads the per-path diff of `paths` (the overlap). The variant only marks which of those paths were conflicted and asks the lost-changes question.

`conflictMerge` is a separate field on `contextFor()` (`run-attempt.ts:1363-1370`), next to `landedOnBase`. It is cleared in the `FixRound` and `MergeBase` cases.

- Set it **after** line 1553. Line 1553 nulls `landedOnBase` whenever a review ran in the lap, and a conflict round always follows a review.
- The ordering applies to `mergedOnto` too. `baseIsRed` reads it (`run-attempt.ts:1427`, `conduct.ts:3348`). After a resolved conflict, a red build has to be compared against `baseSha`, not the pre-merge fork.

## 4. A continuation after the conflict round does not get the conflict block back (decided, not fixed)

A continuation is a fresh `runAttempt`. Its `landedOnBase` and `mergedOnto` come from `landedOnBaseOf(runEvents)` (`conduct.ts:1270`). That function only rebuilds a `BaseMoved` merge: `movedIn` matches `integration._tag === 'BaseMoved'` (`attempts.ts:286-298`), and it requires a `MergeBase` route (`:281-282`).

So suppose a resolved conflict round goes red at `build`, and a person grants a round. The review after it gets the ordinary prompt with no lost-changes question. `baseIsRed` falls back to `continuation?.diffBaseSha` (`conduct.ts:3348`).

Rebuilding it from the log would need the overlap, and that is not in any event; the ticket rules out a new event type. **Leave `landedOnBaseOf` as it is.** Add a comment at `attempts.ts:264` saying that a conflict merge's block does not survive a continuation. Record this as a known gap in the commit message.

## 5. The granted path

- **The criterion.** `grantCriterion`'s `MergeConflict` case (`wait.ts:431-439`) returns `{ printed, findings }`. Add `conflict?: { baseSha: string; paths: readonly string[] }` to the criterion type, set only when `proposal.baseSha !== null`.
- **Forwarding.** `conduct.ts:1243-1251` puts it on `options.from` next to `grant`, using a conditional spread, the way `declined` is passed. Do not use an `undefined` key: `attemptPortsFrom` copies key by key, because *"an `undefined` key would read as present"* (`run-attempt.ts:1028`).
- **The call.** In the walk, call `mergeForConflict` once, before the first `implement` visit, when `options.from?.conflict` is set. It applies the same bookkeeping as the bought round. Use a single `let` flag so a second `implement` in the same walk never merges again.
- **Old waits.** With no `conflict` on `from`, the brief stays `conflictHalf`.

## Tests

- **Fake git.** The opt-in `FakeTree` fields go in `packages/conductor/test/one-attempt.ts:774-806`, as the ticket says. `ancestor: false` is what drives the new `mergeCommitted` port to `false`. The "no `build` runs" assertion goes at both levels:
  - in `run-attempt.test.ts`, with `mergeCommitted: () => Effect.succeed(false)`;
  - in the conduct-level test, through the fake.
- **What is not checked before the merge.** Nothing in the unit half sees a real `MERGE_HEAD`, real markers, or a real `--is-ancestor` on a no-commit merge. The ticket puts that test in `packages/conductor/integration/`, which runs after the merge. Until then, the unit-level stand-in is the full-args `did` assertion: `merge --no-commit --no-ff <baseSha>` comes before `run`, and `merge-base --is-ancestor <baseSha> HEAD` comes after it.
