The ticket says where the refusal goes. What it leaves open is how `doctor` finds the old spellings in a file that no longer resolves. The answer here is that the refusal carries them itself, so neither doctor path needs a new read.

## 1. One pure reader, run where `readOldSpellings` runs today

Replace `readOldSpellings` (`packages/recipe/src/resolve.ts:335`) with one exported pure function, for example `oldSpellingsIn(raw)`. For each spelling it finds, it returns:

This replaces `oldSpellingFixes` (`resolve.ts:585`). That function only exists to turn those strings back into paths with a regex (`resolve.ts:593`). Build the structured value once and drop the string round-trip.

**Where it runs:**
- **Keep the call where `readOldSpellings` is called today** (`resolve.ts:271`, `declared.ts:55`): after `applyPreset` and **before `unknownKeys`**.
- Do not move it down beside `retiredLimits` at `:278`. The `Recipe` type has no `repo.base`, so `unknownKeys` (`resolve.ts:522`) or the schema would answer first with a generic sentence. This ticket exists to stop that.

**The two-homes case.** This is a file that writes `branch:` and also an old base (`resolve.ts:355-360`).
- The refusal: same check, same sentence, now just one more found spelling.
- Its fix writes `branch.main` with the file's **own existing** `branch.main` value. That rule matches the current sentence: *"Keep `branch.main` and delete the old one"*.
- Without a `branch:` block, the value is admit's `worktree.base`, then `repo.base`. That is the precedence the comment at `resolve.ts:319` keeps (*"it wins over `repo.base`, as the old accessor did"*).

Either way the fix contains a `branch` change, and a `branch` change is what makes `editRecipe` call `dropOldBase` (`emit.ts:186`). One rule removes the old keys in both cases.

## 2. The refusal carries what it found

Throw `OldSpellingRefusedError extends RecipeRefusedError`, with `readonly spellings: readonly OldSpelling[]` assigned in the constructor body. Do not use a parameter property.

- It is still `_tag: 'RecipeRefused'` and still `instanceof RecipeInvalidError`, so every existing catch keeps working. `isRefusal` (`packages/recipe/src/local.ts:82`) is one of them.
- Its `problems` are the sentences.

**Why carry the data instead of re-reading the file.** Every doctor recipe row resolves through `recipeLookup` (`apps/cli/src/doctor.ts:1469`). Tests inject `reach.recipe` there. If the row read the file again, it would need a second, file-reading path and a file port in the tests. Carrying the data costs no IO and keeps the ratchet flat.

**The chain it passes through:**
- `plainWhen` fails with the thrown value itself (`packages/recipe/src/files.ts:42`).
- `projectFilterEffect` turns the failure into `ok: false` with `Cause.squash(cause)` (`packages/conductor/src/filter.ts:473-478`). Add an optional `oldSpellings` to the `ok: false` variant (`filter.ts:213`). Set it there when the squashed error is an `OldSpellingRefusedError`.

- `loadProject`'s agent fallback re-resolves with a probe agent and returns that error (`packages/project/src/local.ts:116-127`). Add a unit test asserting the class survives the whole chain, because the row stands on it.

## 3. Doctor

**The row.** `recipeSpellings` (`doctor.ts:2460`):
- `fail` when the filter is `ok: false` with `oldSpellings`;
- `ok` when the filter is `ok: true`, because a resolving file cannot hold an old spelling now;

Rewrite its doc comment. The reason it gives for `warn` (*"a `fail` would block the very restart"*) is exactly the trade the ticket's Watch out accepts. The `recipe: resolves` row will also be red with the same sentences. Two rows for one cause is fine: only the spelling row carries `fix: lingtai doctor --fix`.

**`--fix`.** `fixOldSpellings` (`doctor.ts:2498`) catches `OldSpellingRefusedError` **before** the general `RecipeInvalidError → 'nothing'` branch at `:2516-2520`, then hands the concatenated `changes` to `changeRecipe`. A resolving file is now always `nothing`.

**What `changeRecipe` sees:**
- `draft.ts:67` calls `widenStepsIfNeeded`. That swallows a failed resolve of the old file and returns the changes unchanged (`write.ts:116-121`).
- `editRecipe` then applies the changes and `dropOldBase`, and parses the result.
- Only the final text is resolved (`draft.ts:72`). With the fix applied, that text is in the new spelling.

**Gaps the fix leaves:**
- A file that is refused on an old spelling *and* has a second fault comes out of `--fix` showing the second fault. The pre-parse check throws first, so `--fix` cannot see past it. Say so in the `failed` detail, and do not try to fix both.
- A `steps.admit` item whose `worktree:` held only `base` is left as `worktree: {}`. `dropOldBase` only deletes the key (`emit.ts:159`), and `submodules` is required with no default (`recipe.ts:904-910`). The final resolve then refuses that file. The leniency did the same thing today, so this is not new. Add one `--fix` test on that shape and let it say whether to also delete the emptied `worktree`. Do not guess the value of `submodules`.
