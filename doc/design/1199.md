# #1199: what a judge at `fixer-disagrees` is shown, and the round it buys

Five places change. The `recheck` line the ticket warns about is one of them. The one thing the ticket does not show is the brief: if you only keep `recheck`, the objection and the ruling are silently dropped from it (§3). Model the tests on `packages/conductor/unit/nothing-produced-judge.test.ts`, the test #1198 added for its half of §18. Put this ticket's tests in a sibling file, `fixer-disagrees-judge.test.ts`.

## 1. The offer: `packages/domain/src/failure/respond.ts:643-648`

`routing.ts:270` in the ticket has moved; the cell is here now. Change `restart(hasCriterion)` to `restart(false)`, the same as `NothingProduced` two cells above (`:640`). Nothing else in `offerFor` changes.

A judge that answers `claim` then finds no restart on offer. `decideRoute` escalates `CandidateUnavailable` and a person is reached; no new code is needed for that.

## 2. What the judge is shown: in `run-attempt.ts`, not in `whatArrived`

`replyFor` receives `arrived` from the two `routing(...)` calls at `run-attempt.ts:1908` and `:1949`, which pass `whatArrived(reached)`. It uses it at `:1575`:

```ts
const reply = yield* replyFor(offer, arrived, options.judge)
```

Swap `arrived` just before that call, inside the `routing` closure. That closure is the only place that holds `recheck` (declared at `:1395`):

- If `offer.proposal._tag === 'FixerDisagrees'`, pass `{ findings: recheck, evidence: offer.proposal.said ?? '' }`.
- Otherwise pass `arrived` unchanged.

Leave `whatArrived` (`attempt-steps.ts:593`) alone. Its contract is *"what the arriving visit's ending said"*, and its doc pins `evidence` as `''` for review (`:583-591`). What the declined round was sent with belongs to the lap, not to the visit.

`said` is already resolved at this point. `replyFor` reads `offer.proposal.said` for `NothingProduced` (`proposed-route.ts:165`), and `resolve` fills `said` from the deciding action's `evidence` (`routing.ts:261`: *"`output` and `said` are both the deciding action's `evidence`"*).

Putting the fixer's message on `evidence`, as the ticket asks, rather than on `Judging.said` (which #1198 uses), is safe for the prompt record. `judgePromptParts` marks evidence as an `onStep` part (`judge-agent.ts:106`), and `withStepRef` only references a `StepEnded` whose action value equals the text exactly; otherwise it writes the text out (`record-prompt.ts:30-37`). Here the text *is* the implement action's evidence (`attempt-next.ts:136`, `lastCommitEvidence`), so the record points at the fixer's own `StepEnded`.

Update the doc comments that the change makes false:

- `Judging.findings`: *"the whole of the `findings` direction"* (`attempt-steps.ts:356`).
- `Judging.evidence`: *"What the step printed"* (`:358`).

## 3. The round it buys: two changes that must land together

**(a) `recheck`.** In `case 'FixRound'` (`run-attempt.ts:1680`), guard the existing line with `offer.proposal._tag !== 'FixerDisagrees'`. The other two lines (`landedOnBase` at `:1683` and `lapStart` at `:1684`) still run for every route. The fixer's lap has no `review` visit, so `landedOnBase` stays where it was, which is correct.

Key the guard on the proposal and on nothing else. A red build's route has to keep reading the lap, and the existing tests are what prove it.

**(b) The brief.** Keeping `recheck` alone is not enough. `fixRound` picks the refusal arm at `conduct.ts:4755-4761`:

```ts
: findings.length > 0
  ? ({ on: 'findings', findings } as const)
  : again.said != null
    ? ({ on: 'unfinished', said: again.said, why: again.why } as const)
```

With `recheck` non-empty this picks `findings`, and `again.why` (the judge's ruling) is never rendered. The fixer is never told it was overruled. The only check that would catch this is the `Done when` assertion on the brief, so write that one first.

- **Do not use `SentBack.said` for the objection.** `sentBackTo` sets `said` only when `arrived.outcome.round === 0` (`run-attempt.ts:2160-2168`), and `fixRound` reads `said` as *"use the `unfinished` arm"* when there are no findings. A fixer that declined a red build's round has an empty `recheck`, because builds raise no findings. Relaxing that gate would brief it *"You are continuing an implementation that stopped"* (`fix.ts:567`). That is the wrong prompt.
- **Add a separate optional field**, e.g. `SentBack.objection?: string | null` (`packages/actions/src/action.ts:487-500`). `sentBackTo` sets it under the same conditions as `said` except `round > 0`, so the two are mutually exclusive by construction.
- **Pass it into `fixBriefParts` as its own input**, e.g. `overruled?: { objection: string; ruling: string }`, with `ruling` set to `again.why`. Render a new section next to `declinedSection` (`fix.ts:686`): the objection verbatim, then the ruling verbatim, under a heading that names it a judge's ruling against that objection.
  - Do not reuse `declinedSection` itself. Its text says *"you may disagree with this text"* (`:696`), which is the opposite message.
  - The refusal arm stays exactly as it is chosen today: `findings` when `recheck` is non-empty, otherwise `output`.
  - Do not touch the decline instruction (`fix.ts:631-645`); 0108 §5 keeps it.
- **Do not show both sections.** `continuation.declined` (#935, passed at `conduct.ts:4820`) is set for every round of a pass resumed from a grant. If such a pass is overruled again, it would carry both. When `objection` is present, leave `declined` out: the newer objection replaces the older one.

## 4. The judge's row: `packages/conductor/src/judge-agent.ts:175`

`'fixer-disagrees': REFUSED_ROW` becomes its own `WhenRow`, following `NOTHING_PRODUCED_ROW`'s shape.

`arrived` renders:

- *"The findings the fixer was sent with, verbatim"* followed by `on.findings`, or a sentence saying the round was not bought on findings when the list is empty.
- *"The fixer's message, verbatim"* followed by the evidence slot.

Keep exactly one `${evidence}` interpolation. `judgePromptParts` splits on `EVIDENCE_SLOT` and falls back to plain text if it finds more than one (`:104`).

`means`:

- `implement`: the reviewer is right. One more round, and the fixer is told it was overruled.
- `waiting`: the fixer is right, or you cannot tell. A person decides, and your `why` is what they read.

`weigh` is the question 0108 §18 asks: does the fixer's objection show that a finding cannot happen, or is not this diff's? Or does it just restate the decline?

## Tests

All of these are in the unit half; nothing here needs `pnpm test:integration`.

- **`offerFor` cell:** with `said: 'the finding is wrong'`, a round left and a restart left, it offers `fix-lines` and `hand-to-person` only.
- **Whole attempt with a stub judge.** Script these laps: implement, review with findings F, a round bought, the fixer commits nothing and says S, then the judge.
  - The `Judging` it receives has `findings` equal to F and `evidence` equal to S. `judgePrompt(on)` contains F, S and the new *What to weigh*.
  - **`implement`:** the next `implement` gets `context.recheck` equal to F and `again.objection` equal to S. The `review` after it gets `recheck` equal to F. `fixBrief` with `overruled` contains F, S and the `why` under the ruling heading.
  - **`waiting`:** the result is `ProposedEscalated` with `because.why` equal to the judge's `why`.
  - **`claim`:** a person is reached.
  - **No judge:** `NotAsked`, and the judge stub is never called.
- **Regression:** a red build's route keeps the lap's `recheck`. The existing tests pass unchanged; do not edit them to make them pass.
