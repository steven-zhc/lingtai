# #436: the shape of the change

## Where it goes

Add one new file, `apps/cli/src/trial-build.ts`. It exports `trialBuild(at, deps)` and returns a function with the type `AskInstallAndBuildInput['tryBuild']` (`setup-build.ts:44`). `deps` is the seam the unit tests fake:

- `provision`, which is `provisionWorktree` (`packages/repo/src/worktree.ts:127`)
- `remove`, which is `removeWorktree` (`worktree.ts:214`)
- `run`, which is `runCommand` (`packages/actions/src/command.ts:226`)
- `resolveEnv`, which is `resolveAgentEnv` from `@lingtai/agent-env`, the same function the conductor's live host calls (`packages/conductor/src/live.ts:48`)
- `interrupt`, an `AbortSignal`

`apps/cli/package.json` already depends on `@lingtai/actions`, `@lingtai/repo` and `@lingtai/agent-env`, so no new package edge is needed.

`setup-build.ts` keeps its questions. Its only change is how an interruption is handled (see below).

## Who knows where to cut from: the caller, not `askRecipe`

`askRecipe` doesn't know the remote, the token or the base. The local branch knows the remote and base (`first-project.ts:438-440` seeds `repo.remote`). The GitHub branch knows `owner`, `repo`, `installation` and `ref` (`add-github.ts:294-296`).

So add an optional field to `RecipeAt` (`recipe-flow.ts:100`): `tryBuild?: AskInstallAndBuildInput['tryBuild']`. Each caller builds its own with `trialBuild(...)`, and `askRecipe` passes `at.tryBuild ?? null` where `recipe-flow.ts:322` hard-codes `null` today.

- **Local branch:** `remote` is the resolved origin and `owner` is `''`, the same way a pass treats an ownerless project (`conduct.ts:2395-2402`).
- **GitHub branch:** `owner`/`repo`, plus a `token` from the installation, because a private repository's mirror clone needs one.
- **No installation, or no ref:** where `add-github.ts:85` falls back to `EMPTY_SETUP_READER`, pass no `tryBuild`. The existing *"the trial run was not run"* line (`setup-build.ts:215-217`) then stays true.

Also fix the comment at `recipe-flow.ts:14-15`. It says *"with `tryBuild: null` — nothing here spends money, #391"*. It should now say the trial spends machine time and no money.

## `--defaults`: decided in `recipe-flow.ts`, not in `setup-build.ts`

`tryTheBuild` can't tell whether its world is `acceptingDefaults`, so leave its `fallback: 'yes'` alone. In `askRecipe`, pass:

`check: at.flags['check-build'] ?? (askWorld !== world ? 'no' : null)`

Key this on `askWorld !== world`, which is how line 409 already checks it, not on whether the `--defaults` flag is present. A person who types `yes` at *"use every default?"* (`recipe-flow.ts:257-273`) gets an `acceptingDefaults` world just as the flag does, and must not start the trial either.

A bad `--check-build` value is refused by `question()`'s own `choices` check on `given` (`question.ts:106-108`).

`--defaults --check-build yes` that comes back red reaches the `write`/`edit` question. Under defaults that question answers `edit` (fallback at `setup-build.ts:250`) and refuses. That is the intended result: a scripted setup with a red build list stops rather than writing it.

Register `check-build` wherever `reviewer-model` is listed:

- `wizard-options.ts:23`
- `init.ts:424`
- `first-project.ts:534`
- the delete list at `add-github.ts:317-330`

If it is missing from that delete list, `chooseFirstProject` sees the flag a second time.

## What the trial actually does, step by step

1. **Run id.** Use `setup-<Date.now()>`. `worktreePath` (`worktree.ts:90`) keys on it, so a running daemon's pass never shares a path with the trial.
2. **Env.** Resolve it before provisioning, with `env.required/allow/deny/refuseHosts` read from the recipe file as it stands. If the file is absent, nothing is declared yet: the env question comes after this one (`recipe-flow.ts:376`).
   - An `env.refusal` is a failed trial. Its one result carries the refusal as evidence, and no worktree is cut.
   - `plantAt` is the file's `env.plantAt`, or `ENV_PLANT_AT` (`recipe-flow.ts:59`) when the file is absent.
   - **Deviation from the ticket:** `provisionWorktree` always writes the planted file (`worktree.ts:206-208`), even when it is empty. So "plants nothing" really means "plants an empty file, exactly as a pass would". Don't special-case it. When no names were declared, add `(no env declared)` to a red result's evidence.
3. **Provision.** Call `provision({ …, base, branch: 'setup-trial', runId, plantAt, env: env.values })`. Pass no `at`.
   - The mirror clone can take minutes, so log `cloning <remote> into the mirror — first time only` before the call.
   - A throw is one failed `TrialResult` whose `command` is `git` and whose evidence is `boundedEvidence(err.message)`. It is never a setup crash.
4. **Commands.** Run install, then each build command, through `deps.run`:
   - `cwd` is the worktree.
   - `env` is `runnableEnv(env.values)`, which is what a pass gives a command (`conduct.ts:2569`).
   - `signal` is the interrupt.
   - `ok` means `exitCode === 0`.
   - Evidence is `boundedEvidence` of the output. On a timeout it is the outcome's own message, which already carries `timeoutLabel`.
   - The first failure stops the run. The commands that never ran are not listed as passed: add one more result saying they were not run because `<command>` failed.
5. **Timeouts.** A command that matches an existing `run:` action in the file's `steps.prepared`/`steps.build` by its `run` text uses that action's `timeout`. That is the same matching `mergeRunActions` does (`setup-build.ts:156-171`), and it means a kept `timeout: 30m` isn't tried at 15m and wrongly reported red. Every other command uses `15m`. Name it as a constant whose comment cites `runPlugin`'s default (`packages/recipe/src/recipe.ts:125`); don't repeat the literal.
6. **Cleanup.** Call `remove({ project, runId, home })` in a `finally` that wraps steps 3–5. Like the Effect version's comment says (`worktree.ts:230-233`), a failed cleanup must not replace the failure it cleans up after.

## Ctrl+C: interruption is not a result

A `TrialResult[]` can't say "stopped". Returning a fake failed result would send an interrupted trial into the `write`/`edit` question. Instead:

- The runner throws a named `TrialInterrupted` after its `finally` has removed the worktree.
- `tryTheBuild` catches only that error, around `input.tryBuild(...)` at `setup-build.ts:235`, and returns `{ refused: \`the trial run was interrupted. ${input.kept ?? 'Nothing was written'}\` }`. That is the same `kept` sentence the questions use.
- Any other throw propagates. The runner converts git and command failures to results itself, so anything else is a bug and should look like one.

The CLI side: for the duration of the trial only, the caller installs a `process.once('SIGINT')` listener that aborts the controller. Remove it in the same `finally`, so the process's default Ctrl+C handling comes back afterwards. With the listener in place, Node does not exit before the `finally` has run.

## Tests

All of these are unit tests. Nothing here is integration-only.

- **`apps/cli/unit/trial-build.test.ts`** drives the runner with fakes:
  - commands run in order in the provisioned path;
  - a red install stops the rest;
  - a timeout's evidence names the label;
  - a provision throw becomes a result;
  - `remove` is called on green, on red, on a provision throw and on an abort;
  - an abort throws `TrialInterrupted`;
  - an env refusal never provisions.
- **The existing `askRecipe` tests** cover the flag wiring:
  - `--defaults` never calls the fake `tryBuild`;
  - `--defaults --check-build yes` calls it;
  - `--check-build no` doesn't call it and asks nothing.

  Every existing test that drives `askRecipe` without a `tryBuild` keeps today's "not run" line, which is the cost the ticket names.
- **What only integration would see:** a real `git clone --bare` from a local remote, and a real `sh -c`. There is no new integration file, and the unit fakes are what stand in for it before the merge.
