# #963 — the shape

## What the ticket gets wrong: one URL moves the whole half onto Postgres

The ticket's Fix sets `LINGTAI_TEST_DATABASE_URL` on one job and expects "both the SQLite files and the `ON_POSTGRES` files" to run. That is not what happens. That variable picks the store for **every** integration file, not only for the twelve on the `ON_POSTGRES` list:

- `packages/event-store/test-support/teardown.ts`'s `setup()` returns before it makes the SQLite file: `if (process.env['LINGTAI_TEST_DATABASE_URL']) return`, just above `sqliteDir = await mkdtemp(...)`.
- `storeChoice` (`packages/env/src/index.ts:617-630`) answers `store: 'postgres'` whenever `dbVar('DATABASE_URL')` is set. Under vitest, `dbVar` (`:265-267`, with `inTest` at `:47-49`) is the `TEST_` name.

So one job with the URL set runs 1,198 tests on Postgres and runs the SQLite store, which is the default product store since #275, nowhere at all. To get both stores, use **two legs of one job** with `strategy.matrix.store: [sqlite, postgres]` and `fail-fast: false`:

- **Both legs** get the `postgres:17` service. GitHub cannot make a service conditional, and an idle container costs nothing that matters.
- **Only the `postgres` leg** gets the URL. Add a step with `if: matrix.store == 'postgres'` that appends it to `$GITHUB_ENV`. Do not set `env:` to an empty string on the sqlite leg. `optional()` (`index.ts:1166`) goes through a config provider, and nobody has checked that it reads `''` as absent.
- **On the `postgres` leg** the `ON_POSTGRES` files stop skipping (`postgresUnderTest`, `packages/event-store/test/postgres.ts:51-53`), and every other file also runs against Postgres. That is how the suite ran before #275.
- **On the `sqlite` leg** the suite runs exactly as it does locally today: `14 failed | 1021 passed | 163 skipped` before #961 and #962.

You only need the URL. `directUrl` falls back to `url` (`sessionUrlFor`, `index.ts:536`, called at `:626`), and teardown reads `LINGTAI_TEST_DIRECT_DATABASE_URL ?? LINGTAI_TEST_DATABASE_URL` (`teardown.ts`, right after the `if (sqliteDir)` block). Use `127.0.0.1:5432` with the container's own credentials: no pooler (#157), and no `LINGTAI_*` secret anywhere in the file. The schema creates itself: `CREATE OR REPLACE RULE lingtai_events_no_delete` is in `packages/event-store/src/schema.ts:104`, and teardown's `disable rule` depends on it.

Expect the `postgres` leg to be the one that goes red on its first run, in more files than the twelve. Nothing has run the whole half on Postgres since #275. The ticket's first Edge already counts that as the workflow doing its job.

## Only one job writes to issues

The issue logic goes in a **separate third job**, `report`:

- `needs: integration`
- `if: always() && github.ref == 'refs/heads/main'`
- `permissions: issues: write` on this job only. The test legs keep `contents: read`, as in `check.yml`.

It is separate because two legs that each run "find the open issue, otherwise open one" could both find nothing and both open one. That is the two-at-once case, inside a single run. One job deciding from both legs' results cannot race itself.

What `report` does with `needs.integration.result`:

| Result | Action |
|---|---|
| `failure` | Comment on the open issue, or open one with `--label bug --label agent:hold`. Both labels exist on the repository today. |
| `success` | If the issue is open, comment `green again on <sha>`. Do not close it. |
| `cancelled` / `skipped` | Do nothing. |

The `cancelled` row matters. `concurrency: integration-main` with `cancel-in-progress: true` cancels the older run whenever two pushes land close together. Treated as red, every cancellation would post a false alarm.

**Finding the open issue:** run `gh issue list --state open --search 'in:title "integration tests are red on main"' --json number,title`, then keep only an exact title match with `jq`. Search is fuzzy, so the exact-title filter is what keeps a similarly named issue from being picked up. Set `GH_TOKEN: ${{ github.token }}`.

**On `workflow_dispatch` from a branch other than `main`**, the ref condition skips `report` entirely. The legs still run, and their result shows only on the run page.

## Naming the failing files

The ticket wants the issue to name the failing files.

1. Each leg runs `pnpm test:integration --reporter=default --reporter=json --outputFile.json=integration-<store>.json`. pnpm passes the trailing arguments through to the script's `vitest run --project integration` (`package.json:20`).
2. Each leg uploads that file with `actions/upload-artifact`, using `if: always()` and `if-no-files-found: ignore`.
3. `report` downloads both and extracts `.testResults[] | select(.status == "failed") | .name`, strips the `$GITHUB_WORKSPACE/` prefix, and groups the names by leg. A file red on Postgres only is a different finding from one red on both.

A leg that left no report (failed at install, or hit the timeout) is written as *"<store>: no report — it failed before vitest finished; see the run"*, never as an empty list. The body links `${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}` and names `${{ github.sha }}`.

## Smaller choices, made

- **Timeout and trigger.** `timeout-minutes: 45` on each leg, `ubuntu-24.04`, the same `pnpm/action-setup` and `setup-node` with `node-version-file: .node-version` as `check.yml`. That is the official Node 26 build, so the binary tests in `apps/release` that fail on Homebrew's Node (no SEA) do run here.
- **Do not set `HOME: /nonexistent`.** That is the unit half's claim (`check.yml`'s test step). Integration tests are allowed to reach the filesystem and a real `$HOME` (0060 §1), and the runner's home is throwaway anyway.
- **Git identity.** Run `git config --global user.name/user.email` once before the tests. Integration tests drive the real `git` binary, and a runner has no identity. This is a precaution, not a checked claim: if no test commits without one, it costs nothing.
- **No path filter.** Every push to `main` runs it, as the ticket says.

## What can be checked before the merge

No unit test can check this change, and `pnpm test` cannot see a workflow file. `actionlint` is not installed on this machine, so the check before merging is reading the YAML carefully. `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `pnpm test` stay green because nothing they read changes; only the docs and `.github/` are touched. The real verification is the operator's `gh workflow run integration.yml` after the merge, which is already the last item of *Done when*. **Do not run `pnpm test:integration` to check it** (803 s, past the 600 s an agent has).
