# #1446 design: the project stream records the highest PR number

## Where the change goes

The whole change sits in `packages/project/src/pr.ts`, plus one caller in the conductor and the board's copy of the walk. The ticket's own Fix list covers the domain side: the event, `ProjectState.highestPr`, and `reduceProject`'s new case beside `ProjectResumed` (`packages/domain/src/project.ts:139`). The ADR paragraph is an edit to 0131 itself (`doc/decisions/0131-a-pr-goes-from-draft-to-merged.md:36` is the anchor). That is allowed: `CLAUDE.md` says *"A decision that changes is an edit to its topic's ADR, not a new file beside it"*, so no superseding file is needed.

## The decision the ticket leaves implicit: readers and writers need two different listings

Today one function, `listPrs` (`pr.ts:88-97`), serves two kinds of caller:

- **Readers**: `latestPr` (`pr.ts:124`), `draftTarget` (`pr.ts:141`), and the callers outside this file.
- **Writers inside `pr.ts`**: `draftBatchFor` (`pr.ts:164`), `requestPrSubmit` (`pr.ts:277`) and `closeAndHandBack` (`pr.ts:594`).

If `listPrs` simply becomes "read `highestPr`; null means none", every existing project breaks at once:

- `draftBatchFor` gets `[]` back, `draftOf` answers `{ n: 1, version: 0 }` (`pr.ts:146`), and the landing writes `PrDraftTicketAdded` onto `pr-lingtai-1`. That is exactly the trap in the ticket's Watch out row.
- `closeAndHandBack` finds no `state` for `n` and returns `false` (`pr.ts:595-596`), so a closed PR is silently never recorded.
- `requestPrSubmit` is refused `nothing-landed`.

So there are two private functions, and every writer in this file goes through the second:

- **`highestPr(project, store)`** reads `readProjectEvents` (`state.ts:59`) and reduces it.
  - It answers `{ highest: number | null, version }`. The project stream's version comes from the same read, so a writer can pin its append to it.
  - The readers use this: `listPrs`, `listTailPrs`, `readDraftedTickets`, and the board's `readProjectPrs`.
  - `null` means none. These readers never call `head`.
- **`numberedPrs(project, store)`** (writers only) reads the same project state.
  - When `highest` is `null`, it runs the existing upward walk exactly once. That walk now lives here alone; it is today's `listTailPrs` loop at `pr.ts:107-112`.
  - It then reads PRs `1..top` as `listPrs` does today.
  - It answers `{ prs, projectVersion, recorded }`, where `recorded` is the record before this write (`null` or a number).
- **`numberBatch(project, target, numbered)`** returns `[]` or exactly one batch:
  - The batch is `{ streamId: projectStream(project), expectedVersion: projectVersion, events: [ProjectPrNumbered { n }] }`.
  - It is returned when `recorded === null` or when the batch's target number is above `recorded`.
  - `n` is the larger of the target and the highest the probe found. When the record is null, record the probed highest even if this write targets a lower stream. Otherwise readers would lose the PRs above the target.

The writers that use `numberedPrs` and add `numberBatch` to their batches:

| Writer | Where | Target number |
|---|---|---|
| `draftBatchFor` | `pr.ts:158-173` | `draftOf(prs).n` |
| `closeAndHandBack` | `pr.ts:586-606` | `target.n` when tickets are handed back, else `n` |
| `requestPrSubmit` | `pr.ts:269-296` | `target.n`; it never opens a number, but in the window it must find the draft |
| The freeze hand-off in `recordPrInProgress` | `pr.ts:343-373` | `n + 1`, only when `handed.length > 0` |

The freeze hand-off has one extra step. Its pinned path reads nothing today (`pr.ts:339`: *"No retry in here, and no read of PR `n`"*), so it must now read the project state itself, inside the same `Effect.gen`. The caller's `withOneRetry` at `packages/conductor/src/pr.ts:808` already re-reads on a `ConcurrencyError`, and a conflict on the project stream is one of those.

**The other ~30 `record*` writes through `transitionPr` (`pr.ts:239-258`) do not touch the project stream.**
- Each is handed an `n` whose stream already has events, so it can never raise the true highest.
- If one of them recorded its own `n` while the record is null, it could record 6 while 7 exists, and the draft would disappear from every reader.
- This narrows the ticket's *"any other that targets `pr-{project}-{n}`"* on purpose. Write it in the comment above `transitionPr`.

## The caller that must change: `landTicketEffect`

`draftBatchFor` will return either one or two batches. Make its return type `StreamBatch[]` so nobody can forget the second. Its only non-test caller is `landTicketEffect` (`packages/conductor/src/ticket/commands.ts:941-958`), and that function has two problems with the change:

- It spreads a single `batch` into `appendAll`. That needs to become the list.
- It loops only when `refused.streamId === batch.streamId` (`:952`). Anything else goes to `Effect.die` (`:956`).

So a lost race on `prj-{project}` would kill the landing, after the push has already happened (`:913-916`: *"giving up would lose the record of a landing"*). The condition must become "the conflict is on any stream in the draft's batches". This is the one change outside `pr.ts` that the ticket does not name.

The project stream also takes `ProjectPaused`, `ProjectRecipeChanged`, `ProjectRefused` and similar events, appended by other writers (`commands.ts:46-60` in `@lingtai/project`). A landing that loses to one of those just goes round the loop again. That is the same unlimited loop as today, with one log line per round.

## Readers

- **`listPrs`**: `for n = 1..highest`. A stream that reads empty is skipped. If `highest` is null, it returns `[]`.
- **`listTailPrs`**: starts at `highest` and walks down. It keeps the stop-at-the-first-non-`draft` rule (`pr.ts:113-118`).
- **`readDraftedTickets`**: reads `1..highest`.
- **Board**: `topPrNumber` (`apps/board/src/lib/prs.ts:43-52`) is deleted. `readProjectPrs` (`prs.ts:72`) takes `highestPr(...).highest ?? 0`, which means `highestPr` must be exported from `@lingtai/project`.
- **Header comments**: the board file's header (`prs.ts:4`, *"Numbers are found by `head`, never by listing streams"*) changes along with `pr.ts:84-86`, `:103` and `streams.ts:113-116`.

A project-stream read that fails is the read's error, never "no PRs". This already holds because `readProjectEvents` fails typed (`state.ts:63-66`).

## The tests

All of these are unit tests over `createMemoryEventStore()`. Nothing here needs the integration half.

- **The head-counting store**:
  - Wrap the memory store so that `head` records which stream it was asked about.
  - Assert no `pr-` stream is ever asked about by `listPrs`, `listTailPrs`, `readDraftedTickets` and `readProjectPrs` (the last one in `apps/board/unit/`).
  - Assert exactly one walk from `draftBatchFor` when the record is null.
- **The race test**:
  - Two `draftBatchFor` calls read the same state.
  - The first `appendAll` lands; the second must fail with `ConcurrencyError` on `prj-…` and land on retry.
  - Drive it through `landTicketEffect`, so the widened retry condition is what the test pins.
- **Fixtures**: existing tests that build `pr-` streams by hand and then read them through `listPrs` will go red (the ticket's *"Cost to later tickets"*). Fix each one by also appending `ProjectPrNumbered`. Do not add a fallback to the reader. To find them: `grep -rln "prStream(" packages/*/unit apps/*/unit`.

## What the log settles

Once deployed:

- **The window closed**: the first `ProjectPrNumbered` on `prj-lingtai` should carry `n` equal to the highest `pr-lingtai-*` stream with events. If it carries anything lower, the "record the probed highest, not the target" rule was missed.
- **No collision**: after that, no two `PrDraftTicketAdded` events on different `pr-lingtai-{n}` streams should name the same `ticket` while both PRs are in `draft`.
