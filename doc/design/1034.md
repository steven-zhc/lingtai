# #1034: design note

## The stub's id is `claude-code`, and that is what matters

Once the `config.yml` write at `apps/cli/integration/doctor.test.ts:914` is deleted, the per-project rows read the recipe for the first time. Until now the refusal stopped them. One of those rows asks a runtime the same question the machine row asks, so take that into account when you build the stub.

- `declaredEnvironment` (`apps/cli/src/doctor.ts:2837`) reads `reach.runtimes?.() ?? everyRuntime()` (`:2857`). It then calls `dispatchedAuthRow` for every agent the recipe dispatches, and `resolved.recipe.runtime.agent` is always one of them (`:2929`, `:2940`). The comment there says *"`runtime.agent` always (an unconfigured `implement` runs on it)"*.
- The test's `RECIPE` names `runtime: { agent: claude-code }`. Left unnamed, `resolveAgent` (`packages/recipe/src/local.ts:172`) asks `signedInHere`, the real probe, which `reach.runtimes` does not reach; with no runtime signed in (CI) it throws `AgentUnresolvedError`.
- `dispatchedAuthRow` looks the runtime up by id: `runtimes.find((r) => r.capabilities.id === agent)` (`doctor.ts:2750`). If no stub has that id, it gets `null` and the row becomes `skip`, *"claude-code cannot be asked cheaply"* (`:2754-2755`). That is green, but it exercises nothing. This is the same trap the ticket's *Null or unknown* edge names for the machine row.

So build **one** stub, with `capabilities: CLAUDE_CODE_CAPABILITIES`. It is already imported at `doctor.test.ts:6`. Give it a `checkAuth` that resolves `{ state: 'signed-in', loggedIn: true, method: null, detail: '…' }`, the same shape as `apps/cli/unit/doctor-ownerless.test.ts:153-156`. The one stub answers both rows:

- `runtime: signed in` (`runtimeAuth`, `doctor.ts:977`, `:3471`)
- `runtime: esctestdoctorsown signed in`

Cast the list the way the unit test does (`as unknown as DoctorReach['runtimes']`, `doctor-ownerless.test.ts:159`), because `Runtime` has more members than the stub. You will need two imports:

- `DoctorReach` (a type) from `../src/doctor.ts`
- `probeSeaBuild` from `../src/sea-build.ts` (`:43`)

The `sea` is still the real `probeSeaBuild`, which is also the default (`doctor.ts:3231`). Passing it by name only satisfies the `Pick<DoctorReach, 'sea'>`. It does not change what the row measures.

`limitsRow` builds its capabilities with `createRuntime(...)` itself (`doctor.ts:2920`), not from `reach.runtimes`. The stub does not reach it, and nothing else about it needs to change.

## Assert the runtime rows ran

The test now owns these rows, so assert them next to the `recipe:`, `env:` and `base:` asserts at `:948-950`:

- `find(report.results, 'runtime: signed in').status` is `'ok'`
- `find(report.results, \`runtime: ${OWN} signed in\`).status` is `'ok'`

Without these, a stub with the wrong id passes as a `skip`. That is the *green that means nothing* the comment at `:925-926` warns against.

## Where the change goes

Put the `reach` inside `reportOf` (`:917-927`), as the sixth argument after `load`, rather than inside `is green`. Two reasons:

- The red twin (`:959`) calls the same `reportOf`, so both tests read the same machine. Its asserts name `recipe: ${OWN}` and `env: ${OWN}` with `toContain` (`:966-971`), so they still hold.
- With the stub in place, CI produces no runtime failure. Without the recipe file, `recipeFor` throws before the per-project runtime row is reached, so that row is never written.

Update the comment above the arguments (`:920-922`, *"so the fifth argument can be"*): it should now say the sixth is given too, and why. The machine has no `claude` binary, and #242 says the test builds the machine it reports on.
