One reduce per stream：最终逻辑说明

0.12 的主题叫「一本账」（one set of books），对应 epic #797。本文是英文规格书 doc/design/one-fold-per-stream.md 的中文导读（文件名保留旧词 reduce，内容已改用 reduce），说明这项工作做完后系统怎么运作。更新于 2026-11-03（晚）：术语统一成 reduce / reducer、attempt、stale；加入「一份实现」和「按 seq 去重」两条原则，以及由此新增的 #842–#848 和 attempt 改名票。

01第一性原则

系统就是一个 event log。把一个事件 reduce 进一条 stream 的状态，这条规则只有一份实现，放在 @lingtai/domain 里。conductor、CLI、board、projection 都调用它，谁都不再自己扫事件去算状态。

  • 代码可以共享，规则不能复制。如果共享之后调用变得别扭（比如投影读不到一条 stream），就去优化调用方式，例如加一个 codec、把 state 存进行里，而不是另写一份规则。
  • 功能内聚。同一个功能只放在一个地方。投影里只允许留纯粹的连接（link 表、一行一条的 RunSpent），它们不算状态。
  • 投递至少一次，按 seq 去重（D18）。两个 runner 可能把同一个事件各投递一次；存下来的 state 用 lastSeq 跳过已经处理过的事件。#838 就是卡在这里，已经按这条规则补上 fix round。
  • 不留中间状态（D15）。每张票加一个最终形态的字段，把所有读者都迁过去，旧代码在同一个 diff 里删掉。

改动之前，§0 统计出 domain 之外按事件类型分支的地方有 151 处，其中很多是同一件事被算了好几遍，而且规则略有不同。比如「这个 run 有没有能续做的 saved head」，conductor、lingtai status 和 board 各写了一份判断。

02名词表

event / 事件
events 表里的一行，只追加、不修改。日志是唯一的事实来源。
stream / 流
关于同一个主题的那一串事件，按顺序排列。从 id 的前缀能看出它是什么主题。主题有意分开：一张票、对它的每次 attempt、关于它的每场讨论是三条 stream，靠事件里带的 id 互相引用（TicketClaimed.runId、RunStarted.ticketId、DiscussionHeld.chatId），不合成一条。
reduce / reducer
reduce 是动作，reducer 是这条规则本身（the run reducer），结果叫 state。reducer 拿到一条 stream 的当前 state 和下一个事件，返回之后的 state。每种 stream 只有一条这样的规则。代码里 reduceRunEvent(state, event) 处理一个事件，reduceRun(events) 从头 reduce 整条 stream。旧名字 reduce 和 apply 说的是同一件事，以后统一叫 reduce。一个事件那一步现在还叫 reduceRunEvent/reduceTicketEvent，最后由改名票 #848 统一改掉。
state / 状态
把一条 stream 的全部事件 reduce 完得到的结果。一个 state 只描述一条 stream；需要两条 stream 才能回答的问题，属于 projection 或调用方自己做的 join。
projection / 投影
按 seq 顺序读整个日志建出来的表，用来回答跨很多 stream 的问题：task_view（看板和队列）、ticket_report、spend、finding_backlog。一行需要某条 stream 的 state 时，就把这份 state 存在行里，每来一个新事件就用 domain 的同一条规则 reduce 进去。投影出错只能用 lingtai projection rebuild 重放修正。
codec
把 state 编码后存进行里、读出来再解码。哪个投影第一个存某种 state，这种 state 的 codec 就跟着那张票落地（ADR 0124 §1）。形状不对的 state 会按名字报错，并提示要做哪次 rebuild。ticket 的 codec 在 #833，run 的 codec 在 #844。
按 seq 去重（D18）
CLI 和 daemon 各有一个投影 runner，共用同一个 checkpoint，同一个事件可能被两边各处理一次。存进行里的 state 带着 lastSeq，一个事件的 seq 如果不大于它，就在 reduce 之前跳过。去重只看事件身份，所以写入方写不出的序列照样抛错。
present
把 state 画成页面需要的样子，比如 presentRun(state, …)。present 只负责画，不能再 reduce 一次。
verdict ladder
某个 step 的某个 action 的结果，算 passed、failed 还是 did-not-finish 的那张对照表。原来有两份，#821 合成了一份。
attempt / agent run
attempt（尝试）是 Lingtai 对一张票的一次修改尝试：领一次票，从头到尾走一遍 step，对应一条 pass-… stream。批准、批 fix round 都还在同一个 attempt 里继续；requeue 或 restart 会开一个新的 attempt。agent run 是 attempt 里的一次 agent 调用（implement、每个 fix round、judge）。pass 这个词不再使用。日志里已经写下的名字保持不变：pass- 前缀、runId 字段、Run… 事件名（D20）。
head / base
每个 attempt 在自己的分支上干活。base 是 attempt 开始时 base 分支上的那个 commit；head 是 agent 在分支上做出的最新 commit（RunState.headSha，来自 RunProducedDiff 和 RunProposedCompletion）。
onSha / stale
onSha 是事实：一个 verdict 判定时针对的 commit。stale 是由它推出的判断：从 build 开始，onSha 已经不是 head 的 verdict 就是 stale（D2）。只说 stale，不说「不是 current」；board 上的 current: boolean 会在 #848 里改名为 stale。
saved head
被 hold 住的 attempt 留下的一个干净、已经 push 的 head，fix round 可以接着它做。由 savedHeadOf(state) 判断，结果有四种：Saved、WipHead、BranchDiverged、NoSavedHead。
upcast（D16）
不再新增 upcaster。新加的 payload 字段都是可选的，旧事件读出来就是没有这个字段（ADR 0100 §4、0124 §4）。
fixture histories
packages/domain/test/histories.ts 里手工造的事件序列，每条都用 hash 锁定、不再修改。新的 history 一律写成模块级 const，接在最后一个后面，这样已有的 seq 不会变动。
snapshot（0124）
以后会缓存 state，读的时候只 reduce 快照之后的那一段尾巴。这一步放在最后做，不在 0.12 里。

03数据怎么流

写入方daemon、CLI、board 上的操作，往日志里追加事件
events唯一的事实来源，只追加不修改
domain 的 reduce每种 stream 一条规则：run · ticket · control · project · integration · chat · finding
读者conductor、CLI、board 拿到 state 后决定做什么、画什么；投影把 state 存在行里

读者的规矩

  • 要一条 stream 的任何事实，先 reduce 出 state，再读字段。不要写 for (const e of events) if (e.type === …) 去算状态。
  • 投影也一样：一行要用到的 ticket 部分和 run 部分，都存一份 state，新事件来了用 domain 的 reduce 处理。投影里只剩纯粹的连接。
  • 措辞由各个界面自己决定。domain 返回的是带类型的答案，conductor、status、board 各自翻译成自己的句子。
  • reduce 抛错就让它抛（#822）。现在投影里一抛错，整个 daemon 就会停；#839–#841 改成只停这一个投影，task_view 停了就只是不再领票。

06其他 state

  • ControlState（#836）：拆成不读时钟的 reduce，加上 evaluateControl(state, now)。ConductorPaused 多了一个可选的 cause（person、setup、account-limit、day-ceiling），没有升版本，也没有 upcaster（D8）。day ceiling 只看 cause，再加上 ceilingWaivedUntil，就知道这次暂停是不是自己设的。
  • ChatState（#837）：一个回答归到它之前最近一个还没回答的提问。「还有没有待处理的请求」比较的是请求数和已回答数，而不是「有没有哪个提问没回答」，否则一次崩溃就会让 CLI 每一轮都再买一次讨论（D14）。
  • finding state（#838 已批 fix round）：一个 finding 是 proposed、accepted 还是 declined。conductor 和 finding_backlog 都读它；finding_backlog 加一列 last_seq 用来去重。

09走一遍：一个 attempt 的事件和 RunState

  1. RunStarted　lifecycle=running，记下 openedAt、agentStartedAt
  2. StepsResolved　resolved = {configHash, 十个 step}
  3. StepStarted implement 0　step = {implement, 0, since}
  4. RunProducedDiff → sha-1　produced 和 headSha 都是 sha-1
  5. StepEnded implement　step = null；implement 的 verdict = passed
  6. StepStarted review → StepEnded review（拒绝）　review:cold 判为 failed，onSha=sha-1；记下 refusal
  7. PassRouted → FixRound(1)　route；implementRound = 1；roundsOpened = [1]
  8. StepStarted implement 1 → RunProducedDiff → sha-2　headSha = sha-2，review:cold 过期（D2）
  9. StepStarted merge → MergeLaneWaited　记下 laneWaitedAt，进度条显示正在等 merge lane
  10. StepEnded merge　step = null，等待结束（这是 #827 修掉的 bug）

这些事件 task_view 也会收到。#844 之后，它把同一份 RunState 存在行里，卡片上的列直接从 state 算出来，不再自己写 case。

10定下来的规则（D1–D16）

  • D1 全系统只有一张 verdict ladder。
  • D2 过期的 verdict 要显示出来，从 build 开始算。
  • D3 失败一直算失败；请求过的 signoff 在 lifecycle 往前走之后清掉。
  • D4–D6 票的字段来自 claim 和 stream id；task_view 以 domain 的结论为准；closed 是终态。
  • D7–D9 新增 chat 和 finding 两个 reduce；pause 带一个可选的 cause；GitHub 写入账本放进 TicketState。
  • D10 进度相关的事实放在 RunState 里，只记时间点。
  • D11–D14 续做算一次移动；step 只由它自己的 StepEnded 结束；一次 attempt 只有一个结局，带上 wait 的原因；比较请求数和已回答数。
  • D15 不留中间状态。D16 不针对旧日志写分支，不新增 upcaster。
  • D17 一份实现：投影也调用 domain 的 reducer，只有纯连接、reaction 和 select 可以留在 domain 之外，名单由 #846 提交并用测试守住。
  • D18 按 seq 去重：投递至少一次，存下来的 state 跳过 seq 不大于 lastSeq 的事件。
  • D19 统一叫 reduce：动作叫 reduce，规则叫 reducer，结果叫 state。
  • D20 统一叫 attempt：对一张票的一次修改尝试叫 attempt；run 只指一次 agent 调用；pass 不再使用。

11用户能看到的变化

这是一次重构，大部分东西应该和以前一样。下面这些变化是有意的，各自只在对应的那张票里落地。

  • task page 上，针对旧 head 作出的 verdict 会标成过期（#828）；signoff 显示 asked（#821）；请求过人的 step 会显示它问的问题（#828）。
  • 等过 merge lane、之后被拒的卡片显示拒绝原因（#827）。
  • 如果这张票正卡在这次 attempt 的 wait 上，attempt 显示 asked；人处理之后，回到它的 run 本身的状态（#829）。
  • task_view（#834）：批了 fix round 之后状态是 approved，note 写「fix round granted — continues once a conductor is free」；Close 一直显示 waiting，直到 TicketClosed 落地；只有 TicketLanded 才算 landed。
  • 卡片（#844/#845）：新 claim 刚开始时还没有 head，不再显示上一个 run 的 head；approval 只在这次 attempt 被请求 signoff 时出现；两条短暂的 integration note 不再显示。
  • 每次 rebuild 期间，board 上看到的表不完整。

12用 DDD 的话说

每条 stream 是一个 aggregate，这条 stream 上的事件全部 reduce 到它自己的 state 上。边界划得小：只有必须一起原子成立的不变量才放进同一个 aggregate。Lingtai 里没有哪个不变量要求一张票和它的 attempt、或者一张票和它的讨论在一次写入里同时改，所以它们是不同的 aggregate。

DDDLingtai
aggregate 类型一类 stream：ticket、attempt、discussion、merge lane、project、control
aggregate一条 stream（ticket-lingtai-829、pass-…）
aggregate 的 stateTicketState、RunState（将改为 attempt state）……
apply / whenreducer
command handlerconductor、CLI、board：读 state，做决定，append(stream, expectedVersion, events)
一致性边界一条 stream 的版本号：只有在同一条 stream 内，一次写入才是原子的
引用别的 aggregate事件上带对方的 id
process managerconductor 按顺序往几条 stream 写；reconcile 把崩溃留下的半截状态推完或撤回
read model投影：task_view、ticket_report、spend、finding_backlog

跨 aggregate 怎么做到最终一致

  • 单点裁决：需要互斥的决定只在一个 aggregate 上做，比如能不能领票只看 ticket stream 的版本号。
  • 先写意图：TicketClaimed 带着 runId，后面的步骤都能从它推出来。
  • process manager 推进：conductor 读几份 state，往下一条 stream 写。
  • 补偿：推不下去就追加一条反向事件，比如 reconcile 发现领票的 worker 已经不在，就追加 TicketReleased。
  • 幂等：写入带 expectedVersion；投影按 seq 去重（D18）。
  • 读的一方接受中间态：已领票、还没开始的 attempt，就照实显示 claimed。
  • 日志本身就是 outbox：订阅方从日志读，读到哪里记在 checkpoint 里。
