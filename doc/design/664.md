# Design: #664, what a user's own runtime restrictions can narrow

## What this worktree actually holds

The ticket says to replace every *not yet measured* in `doc/operating.md` with what *this branch's probe* found. Neither exists here. `scripts/` holds `cli-doc.ts`, `deploy-site.sh` and `the-pass.py`, and nothing else. `grep "not yet measured\|lingtai-probe"` over `doc/operating.md`, `README.md` and `doc/decisions/` finds nothing. So both are written from scratch:

- **The probe is written and not run.** Re-running it is out of scope.
- **The section is new.** It is not an edit of an existing placeholder.

The issue body already carries the measured results, with the versions and the snippets. That body is the record the `Done when` asks for, so the agent does not post a comment on #664.

## The probe: `scripts/runtime-restrictions-probe.ts`

Run it as `node scripts/runtime-restrictions-probe.ts`, the same way `scripts/cli-doc.ts` runs. Do not add a `package.json` alias: a named script invites someone to run it casually, and it uses real accounts.

It stays out of `pnpm test` without any extra work. The unit project only includes `{apps,packages}/*/unit/**/*.test.ts?(x)` (`vitest.config.ts:72`). `pnpm typecheck` is `pnpm -r` over packages, so it never reaches `scripts/`. `pnpm lint` (`oxlint --deny-warnings`) does reach it, so the script has to lint clean.

**Build the argv the way a pass does, never by hand.** A hand-written argv would measure a different command from the one Lingtai launches.

- Claude Code:
  - Call `createClaudeCodeRuntime().invocation(request)` (`packages/agent/src/claude-code.ts:425-430`).
  - The default mode is `bypassPermissions` (`:412`).
  - Swap the element equal to `PROMPT_ELIDED` (exported, `claude-code.ts:194`, `index.ts:30`) for the probe's prompt.
- Codex:
  - Call `createCodexRuntime({ sandbox }).invocation(request)` (`codex.ts:1121-1133`) once with `workspace-write` and once with `read-only`.
  - That reaches `--sandbox` and `-c approval_policy=never` through `argsFor` (`codex.ts:1044-1052`). The probe adds no flag of its own.
- Environment: spawn with `runnableEnv({})` (`packages/agent-env/src/index.ts:148`). That is what a pass with no `env.required` hands an agent, and it drops `CLAUDE_CONFIG_DIR` and `CODEX_HOME` the same way a pass does (`RUNNABLE`, `:146`).

**The `Invocable` the probe builds.** The type is `Omit<RunRequest, 'prompt' | 'signal'>` (`runtime.ts:161`).

- **`cwd`**: a fresh temporary directory with `git init` run in it. `writableFor` calls `gitWritableRoots(cwd)` for `workspace-write` (`codex.ts:1102-1104`), so `cwd` has to be a repository.
- **`settingsPath`**: a temporary file holding `{}`. It must not be real hook wiring.
  - The reason: no hook socket is running, and the hook fails closed (`doc/operating.md:838-840`).
  - What is lost: Lingtai wires no `PreToolUse` (0106 §3), so hooks have no bearing on permissions.
  - Before relying on it: read what `hookWiringAt` (`codex.ts:1127`) does with the file, and check that `{}` yields no hook overrides rather than a throw.

**The probe never writes `~/.claude/settings.json` or `~/.codex/config.toml`.** The ticket keeps it a script a person runs (Watch out, and *making it non-interactive* is out of scope). For each row it:

1. prints the snippet to merge;
2. waits for Enter;
3. runs the row;
4. tells the person to restore the file.

The only files it creates and removes are its own:

- `~/.lingtai-probe/secret.txt`, holding a token generated per run, so the model cannot guess the contents;
- the temporary directories.

It must never touch `~/.ssh` or `~/.lingtai`.

**Recording each row.** Next to each row it prints:

- `claude --version` or `codex --version`;
- `read` when the token appears in the output, otherwise `refused`;
- the last few hundred characters of the output, so a person can see *inconclusive* cases like x0 and x1.

Name the rows c0–c5 and x0–x4 to match the table in the issue, so the document and the script cite each other.

## The document

**1. A new `### What your own runtime configuration can narrow` in `doc/operating.md`, under `## Running work`.**

- Place it right after the paragraph at `:843-848`.
- It holds the table, the versions (Claude Code 2.1.310, codex-cli 0.164.0, darwin, 2026-10-27), the c4b snippet as the recommendation, the Codex profile, and the three conclusions exactly as the ticket states them.
- **#667** is named as the open fix for Codex.
- The `env.required` path for a config kept in a non-default directory is covered, citing `operating.md:1589` and `conduct.ts:3411`, and marked as not measured.

**c5 is recorded and must not read as a suggestion.** `disableBypassPermissionsMode: "disable"` removes the mode Lingtai launches with. `claude-code.ts:252-260` records what a run without that mode looks like: *"45 turns and $3.35 … could not write a single file"*.

State two things as unmeasured:

- **Linux without bubblewrap.** Per the ticket's Edges, that is the user's setup and not Lingtai's to install.
- **A full pass under c4b.** A commit from a Lingtai worktree writes into the main checkout's `.git`, which is outside `cwd`. That is why Codex's argv widens by `--add-dir` (`codex.ts:1053-1056`). Whether Claude Code's sandbox allows that write was not measured. If it does not, the agent fails visibly, and the ticket's Edges call that the user's choice. Say where to look rather than guessing a setting.

**2. Correct the paragraph it follows.** `operating.md:843-848` says `permissions.deny` holds under `bypassPermissions` *"because it removes the tool from the model's list so nothing is ever attempted (experiment 008)"*. That is true of a whole-tool deny, which is what 008 tested (`{"deny": ["Bash"]}`). c1 and c2 show the narrower case:

- a path-scoped `Read(...)` deny refuses the call instead of removing the tool;
- a subprocess is not covered by it at all.

Narrow the sentence and point it at the new section. Leave `doc/experiments/008-*.md` alone: it is a record of what was run.

`packages/agent/src/hook-socket.ts:282-284` makes the same overgeneralised claim in a comment. Correct that comment in the same commit. It is a comment, not argv, so it is inside *this ticket changes no argv*.

**3. README `## What an agent can reach` (`README.md:94-124`, #660).**

- `:111` says *"The Claude Code runtime has no filesystem sandbox"*. Keep the claim that *Lingtai* gives it none, and add that a user's own sandbox with `allowUnsandboxedCommands: false` holds under Lingtai.
- In the Codex bullet (`:114-118`), add that a user's own permission profile is replaced by Lingtai's `--sandbox` until #667.
- Each bullet gets one clause and a link to the `operating.md` section. The table belongs there, not in the README.

**4. 0106 §4.** Append the ticket's sentence after *"the runtime's sandbox."* (`doc/decisions/0106-…md`, around line 65). `doc/decisions/` is one ADR per topic and is edited in place (`CLAUDE.md`), so no superseding file is needed.

The Context paragraph's *"Claude Code … has no filesystem sandbox"* is about what Lingtai provides (the tier). Leave it as it is.
