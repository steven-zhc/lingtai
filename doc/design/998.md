# Design note: #998

## The one decision the ticket leaves open: what the recorder returns

Today `startRecorder` (`apps/cli/src/restart.ts:1554-1574`) is handed a control read and returns `void`. It "never throws: a start that could not be recorded is said, and the daemon still conducts" (:1550-1551). That shape has to change. The read now happens inside `recordStart`, so the caller can no longer see what was read. And the caller now needs three outcomes from the recorder, not none:

```ts
type StartDecision =
  | { take: true }                                   // ConductorStarted appended
  | { take: false; standing: ShutdownRequest }       // a drain asked of *this* daemon
  | { take: false; failed: string }                  // could not record → exit non-zero
```

- `startRecorder({ restart, tty, user, record, log })` returns `() => Promise<StartDecision>`.
- It takes no argument.
- It is memoised on the **promise**, not on a `decided` boolean. The loop's shutdown check and anything that runs alongside it must await the same single `recordStart`, never start a second one.
- `record` becomes `(a) => recordStart(a.by, a.reason, code, since)`. Its `{ recorded, standing }` maps onto the first two outcomes.
- Any throw is caught inside the recorder and becomes `failed` with the message. `recordStart` itself rethrows (Fix §2.4). The recorder is where it becomes data, so neither caller needs a `try`.
- `attributeStart` loses its `control` input and its `record: false` arm (:1532-1534). `Attribution` collapses to `{ by, reason }`.

## `recordStart(by, reason, code, since, store = eventStore)`

`since` goes in before `store`, so `tsc` finds every positional caller:
- `apps/cli/src/daemon.ts:307`
- `packages/daemon/integration/shutdown.test.ts:322`
- `apps/cli/integration/service.test.ts:1509`

The body copies `requestShutdownUnlessStanding` (`packages/daemon/src/control.ts:233-244`) line for line:
- `head` first, then `readControl(store, 0, { snapshots: store === eventStore ? log.snapshots : undefined })`;
- then the `standing.version > since` test, then `append(..., at)`;
- `attempt >= 4` rethrows.

The return type is `Promise<{ recorded: true } | { recorded: false; standing: ShutdownRequest }>`. Its doc comment's last paragraph ("It does not withdraw a standing shutdown request, deliberately", :262-263) becomes the rule: a start ends a request at or below `since`, and refuses to start over one above it.

It stays an `async function`, edited in place, so the ratchet count does not move. Do not wrap it in `Effect.gen` in this ticket: that would be a second change of shape that nobody asked for.

## Wiring in `apps/cli/src/daemon.ts`

**Conducting** (`shutdown:` at :586-602). This is the first thing `drain()` asks, before `paused` (`packages/daemon/src/work-loop.ts:514`), so it is the first read the daemon acts on.

```
const start = await noteStart()
if ('failed' in start) { failedStart = start.failed; return `the start could not be recorded: ${start.failed}` }
if (!start.take) { asked = start.standing; return `asked by …` }
const control = await controlRead(since)   // unchanged; scopeControl no longer touches shutdown
asked = control.shutdown
return asked ? … : null
```

- Returning a sentence makes the loop set `stopped` and call `onShutdown` (`work-loop.ts:515-521`).
- `onShutdown` checks `failedStart` first and goes to `stopNow` rather than `drain`.
- **`stopNow` ends in `process.exit(0)` (`daemon.ts:430`)**. Give it an exit code (`stopNow(why, code = 0)`) and pass `1`. Nothing is in flight on the first check, so `stopNow` costs nothing over `drain`. The non-zero exit is what a supervisor and `service start`'s wait on `ConductorStarted` read.
- Keep `controlRead(since)` for the later reads rather than switching to `controlRead()`. With `keepShutdown` gone the shutdown half is identical either way, and `claiming` still needs `since` for the pause.

**`--no-conduct`** (`hearShutdown`, :699-708).
- The first call does `noteStart()` before the read.
  - `failed` → `stopNow(…, 1)`.
  - `standing` → `drain(...)` as today.
- Every later tick goes on as now. The `.catch(() => null)` on `controlRead()` stays for the ticks only. It must never stand in for the start decision, because "a failed read is never taken as *nothing stands*" (ticket, *Edges*).
- `since` is in scope there: `const since = started.since` (:511) is above the `if (!('no-conduct' in flags))` branch (:526).

Rewrite the comment blocks the ticket lists. The one at :592-600 currently says "`since` makes an older request invisible". After this change, an older request is *ended* by the start, not hidden.

## Tests: where they go, and which ones go red unseen

**Unit (the gate runs these):**
- `packages/domain/unit/control.test.ts`: the reducer cases from *Done when*. Also rewrite the scopeControl case at :519.
- `packages/daemon/unit/control-head.test.ts`: add the `recordStart` cases. The `racing` helper there (:14-27) hooks `readTypes`, which is what `readControl` → `readState` calls. A `ConductorShutdownRequested` raced through it covers the read-to-append window as long as `recordStart` reads `head` **before** it reduces, which is why the order in Fix §2.1 matters.
  - For "append throws something else", wrap `append` to throw a plain `Error`.
- `apps/cli/unit/start-recorder.test.ts` (new): the three `startRecorder` cases, plus "two calls await one record". `startRecorder` and `attributeStart` are pure. Their current tests sit in `apps/cli/integration/restart.test.ts:395-460`, which the gate never runs, so move them here and delete them there. The `record: false` case at :399 goes, because the branch is gone.

**Integration (not run inside the pass, and it will go red on the new rule):**
- `packages/daemon/integration/shutdown.test.ts:357-363`, *is invisible to the daemon that started after it*. `readControl(store, 1)` over a lone request now answers it. Rewrite it to the new rule: a request with a `ConductorStarted` after it is `null`, and without one it stands.
- `:374-382` still holds, because a pause below the watermark stays invisible.
- `:318-326` needs `since` and still records, because the request is at or below it.
- `service.test.ts:1503-1510` passes `v` as `since`.

Nothing can check these edits before the merge. The unit tests above are the claim that stands in for them, so keep the rewritten integration cases as direct translations of the unit ones and add nothing new there.

## Things not to do

- Don't key the decision on `since >= standing.version` against a scoped read. `recordStart` reads the **whole** stream (`since = 0`), then compares versions itself. A scoped read is exactly what the ticket removes.
- Don't touch `withdrawShutdown`, its callers, `holdsAcrossStarts`, or the pause half of `scopeControl`.
- `reducer-versions.json`: add row `"3"` only. `histories.hashes.json` moves wherever `late_everyControlEvent` is folded. Regenerate it with whatever `histories.test.ts` prints, and never by hand.
