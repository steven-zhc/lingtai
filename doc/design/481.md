# Design: #481, `finding_backlog` folds through the read model

## Only one of the backlog's five event types is retired, and it has no rounds

`backlogProjection.apply` switches on five types (`packages/projector/src/backlog.ts:127-218`):

- `RunStarted`
- `StepPassed`
- `FindingAccepted`, `FindingProposed`, `FindingDeclined`

0120's appendix retires exactly one of them. Its row reads `StepPassed, StepFailed, … → StepEnded` (`doc/decisions/0120-a-reason-is-a-type.md:634`). `RunStarted` and the three `Finding*` types appear nowhere in the appendix, and its closing line is "Unchanged: … and the rest of `EVENTS`." So those four `case`s stay exactly as they are, the same way #480 kept `RunStarted` and its kin in `task-view.ts`'s switch (`doc/design/480.md`, "`task-view.ts` keeps its `switch`…").

The ticket's "`routesOf` for rounds" has nothing to apply to here. `backlog.ts` reads no `FixRequested`, `FixApplied`, `PassRestarted` or `PassRouted`, and it writes no round. The line was carried over from #480's ticket. Do not invent a use for `routesOf`.

## The decision: a per-event function, not `stepOutcomesOf`, for the same reason #480 gave

The ticket says findings come from `stepOutcomesOf`, and it also says the rows must be byte-identical. `stepOutcomesOf` cannot give byte-identical rows. In each case below, today's fold writes a row and `stepOutcomesOf` drops it or cannot place it:

- **It needs the run's `StepsResolved`.** `recipeFor` (`read-model.ts:165-168`) finds the action's shape. Where there is no recipe entry and no `STEP_DEFAULTS` row, `shapeFor` answers `undefined` and the action is skipped (`read-model.ts:670-674`, "Skip it and keep folding"). `build`, `review` and `proposed` have no default (`read-model.ts:146-148`). So a `StepPassed` at `proposed:review` on a v1/v2 `StepsResolved` ("absent, not empty", `:145`) yields no outcome, and its minors vanish. `integration/backlog.test.ts:33-53` writes exactly that: a `StepPassed` with no `StepsResolved` at all.
- **Only a `verdict`-yield action keeps its findings.** `verdictResultFrom` carries `findings` (`read-model.ts:256-262`). `signoffResultFrom` turns a `StepPassed` into `{ _tag: 'Completed', requested: null }` (`:290-291`). Today's fold takes the minors off any `StepPassed`, whatever its action's yield (`backlog.ts:139-140`).
- **`seq` and `at` are gone.** `RunStepOutcome` carries `runId`, `step`, `round` and `actions` (`read-model.ts:80`). `raised_seq` and `raised_at` are the `StepPassed`'s own `event.seq` and `event.at` (`backlog.ts:178-179`).
- **It is a slice function** (`read-model.ts:6-14`). `apply` gets whatever batch the runner hands it, and a run's `StepsResolved` can sit in an earlier batch than its `StepPassed`.

**So byte-identity wins over the literal "`stepOutcomesOf`"**, as it did in #480 ("the ticket's Watch out and Done when both demand byte-identical rows… So byte-identity wins", `doc/design/480.md`). No ADR is contradicted. 0120 *Two phases* asks only that "at the switch only the read model and the builders change" (`0120…md:588`), and a per-event export in `read-model.ts` is what makes that true for this file.

### `findingsRaisedOf(event: Envelope)`, in `packages/domain/src/read-model.ts`

Put it in its own section after `cardFactOf` (`read-model.ts:1256`), with a header comment that says the same thing `cardFactOf`'s comment says (`:1306-1313`): it is not `stepOutcomesOf`, and why. Cite the four losses above.

- **It owns `StepPassed` and nothing else, and answers `null` for every other type.** `StepFailed` must answer `null` too. The rule "only `StepPassed`" (`backlog.ts:26-28`) is about which verdict raises a backlog entry, so it moves into the read model with its reason. At #464 the function decodes `StepEnded` and keeps that rule.
- **What it returns:** `runId` taken from **`data.runId`, not `event.streamId`**, because today's lookup and `run_id` column both use `d.runId` (`backlog.ts:144,169`). Also `step`, `action`, `onSha`, and the findings. Express the findings in 0120's vocabulary by reusing `verdictResultFrom(e)` (`read-model.ts:256-262`), which already turns a `StepPassed` into `assessment: { verdict: 'accepted', findings }`. Return that `Assessment` rather than a bare array. That keeps this function's output in the new types, which is what the ticket means by "through the read model".
- **Leave the `severity === 'minor'` filter in `backlog.ts`** (`:140`). It is 0038 §5's backlog policy, not a fact about the event.
- **`seq` and `at` are still read off the envelope in `backlog.ts`.** They are envelope fields, not an old event type, and #464 does not change them.

### `backlog.ts`

- Keep the switch for `RunStarted` and the three `Finding*` cases, byte for byte.
- `case 'StepPassed'` goes. Its body moves under `default:`, behind `const raised = findingsRaisedOf(event); if (raised === null) break`.
- **Every `ctx.query` keeps the same SQL, the same parameters and the same order** (`backlog.ts:142-182`): the `finding_backlog_run` lookup first, the `!link || !task` drop, then one insert per minor in the order the findings came.
- `PayloadOf<'StepPassed'>` leaves the file.
- The header prose names `StepPassed` three times (`:7,12,26`). Reword those lines to "a passing gate's accepted assessment" and point at `findingsRaisedOf`. Then #464 can leave this file alone entirely, comments included.
- Do not touch `create`, `reset` or the table shapes. A rebuild is the only migration, and nothing here changes a column.

## The pin: `packages/projector/unit/backlog-rebuild.test.ts`, committed before any `src` change

Use the same harness as `task-view-rebuild.test.ts:437-449`:

- `openSqliteProjections(':memory:')` and `createSqliteProjectionStore`, then `backlogProjection.create`, then `apply`.
- Compare `select * from finding_backlog order by project, key` and `select * from finding_backlog_run order by run_id`, whole, as a snapshot.
- Build the stream once at module scope (`makeStream`'s module-global seq, `task-view-rebuild.test.ts:19-21`).
- Generate the snapshot from today's `backlog.ts`, and never `-u` it after the `src` change. That file's header says why.

**Nothing in `pnpm test` folds `finding_backlog` today.** The backlog case in `test/contract.ts:691` runs only through `integration/sqlite.test.ts:44` and `integration/projection.test.ts:182`, and `integration/backlog.test.ts` is Postgres-only. So this file is the only check inside the pass. Say so in its header.

What the stream must cover, each case on its own work item and commented:

- **Raised and filtered:** a `RunStarted`, then a passing verdict carrying two minors and a major. Two rows, no major.
- **A passing verdict with no minors.** No row, and no lookup effect.
- **Two passing verdict actions in one outcome** (`aStepEnded` with two actions). Two `StepPassed`s, so the per-finding insert order and `raised_seq` of each are pinned.
- **A failing gate's minors** (`verdict: 'refused'` → `StepFailed`). No row.
- **First sighting wins:** a second run on the same item re-raises the same claim with a different line and spacing (`findingKey` normalises). The row keeps the first `run_id`, `line`, `on_sha` and `raised_seq`.
- **No `RunStarted`:** a `StepPassed` on a run nothing started is dropped (`backlog.ts:147-149`).
- **A `workItemId` that `parseWorkItemStream` refuses** is dropped. A body with no `-` returns `null` (`streams.ts:28-29`).
- **A duplicate `RunStarted`** for one run. The first `task_id` holds (`on conflict (run_id) do nothing`).
- **The decisions:**
  - `FindingDeclined`, then a re-raise. It stays declined.
  - `FindingAccepted` then `FindingProposed`.
  - `FindingAccepted` with no `FindingProposed`. `proposed_ref` stays null (`backlog.ts:39-41`).
  - A `Finding*` for a key with no row. No-op.
- **One `StepPassed` with no `StepsResolved` before it.** Every builder writes one, so the only way to make this is `makeStream` with the wire shape. The pin records today's row, and it is the case that would catch someone "fixing" this onto `stepOutcomesOf`. That is the one hand-written old-type event the ticket allows: name it as a pinned exception, the way #480 documented `aLegacyHold` (`fe8a923`'s message).
- **Folded in two batches split mid-stream gives the same rows as one batch.** The split must fall between a `RunStarted` and its run's `StepPassed`. `task_view`'s pin does not do this. Here it is cheap, and it is the property a slice-based fold would lose.

`RunStarted` and `Finding*` may use `makeStream` directly, as #480 allowed for unchanged types (`doc/design/480.md`, *Builders*). The verdicts go through `aRun(runId).aStepEnded(...)`. `contract.ts:153-170`'s `stepPassed` is the template: an `agent` action yielding `verdict`, with `assessment: { verdict: 'accepted' | 'refused', findings }`.

## Moving the existing tests

- **`test/contract.ts`'s backlog half is already on the builders.** #480 moved the shared `stepPassed` helper (`contract.ts:152-170`), and `fe8a923` fixed the backlog case's `written.at(-1)` seq. `started(task)` is `RunStarted`, which is unchanged. Check it, and do not rewrite it.
- **`integration/backlog.test.ts` is the one to move.** `attempt()` (`:33-53`) hand-writes `StepPassed`/`StepFailed`. Build those through `aRun(run(n, a)).aStepEnded(...)` at `step: 'proposed'`, an `agent` action named `review` yielding `verdict`, and map each envelope to `{ type, actor, data }` as `contract.ts:150` does. The `RunStarted` and the `Finding*` appends may stay as they are.
  - The builder adds `StepsResolved`/`StepRequested`/`StepStarted` ahead of the verdict on the same stream, so the append at version 0 still works. No assertion in that file reads a seq.
  - `onSha` is `z.string()` (`events.ts:709`), so `` `sha-${a}` `` survives the builder's validation.
- **Only `pnpm typecheck` checks that file inside the pass.** It is integration and skips without `LINGTAI_TEST_DATABASE_URL`, so the unit pin stands in for it. Do not run the integration half.
