# #838: the shape of the change

The ticket already gives the shape (the `FindingState` union, the fold's rules, the conductor mapping, the single projection case). This note covers only what the ticket leaves open or gets slightly wrong.

## 1. `applyFinding` is a `switch` on string-literal `case` labels

The `COVERS` test finds the event types by walking the AST for `case` clauses whose expression is a string literal and a key of `EVENTS` (`packages/domain/unit/histories.test.ts:35-56`). If it finds none, it throws `"yields no catalogue case labels — the check would be vacuous"` (`:54`).

- Write `case 'FindingAccepted':`, `case 'FindingProposed':` and `case 'FindingDeclined':` inside `function applyFinding`, declared at top level with the `function` keyword. A `const applyFinding = …` would not be found (`:48-49` matches only `FunctionDeclaration`).
- `default: return state` is the rule that *a type that is not a `Finding*` changes nothing*.
- Add `caseLabels('backlog.ts', 'applyFinding')` against `COVERS.finding` to the existing `it` at `:84`, and add the finding fold to its name. `COVERS.finding` already lists all three types (`packages/domain/test/histories.ts:971`).
- `applyChat` says *"never throws (D14)"* (`packages/domain/src/chat.ts:31`). `applyFinding` throws on purpose. Say so in its doc comment and cite #822, so nobody "fixes" it to match chat.

The error message names `e.streamId`, `e.seq`, the event type, and the state's `status` before the event. Both the conductor and the projector raise it, so the projector adds no message of its own.

## 2. The fixture histories: Watch out's precondition is already met

`lateHistories` already has `run`, `ticket`, `control` and `chat` (`packages/domain/test/histories.ts:893-926`). **Convert nothing.**

- Add `late_acceptedOnly` and `late_declinedThenAccepted` as module-level consts, directly after `late_twoAsksTwoAnswers` (`:883-891`), the last history built.
- Add `finding: { acceptedOnly, declinedThenAccepted }` as the last key of `lateHistories`.
- Use `makeStream(backlogStream(PROJECT, 'minor-3'))`, and `'minor-4'` for the second. `seq` is module-global (`support.ts:23`), so putting them anywhere else moves every later hash.
- **Reuse** means `histories.finding.acceptedThenProposed` and `histories.finding.declined` stay exactly as they are, including their `fnd-` prefix (`:426-437`). "Each on `backlogStream`" applies to the new ones only. Changing the old ones changes two locked hashes, and the prefix is out of scope.
- The hash test prints the entries to paste (`histories.test.ts:180-185`). It keys late histories as `${kind}.${name}` (`:169`), so they land as `finding.acceptedOnly` and `finding.declinedThenAccepted`. Only append; never edit an existing line.
- `the histories fold` (`:96-102`) gets a `finding` loop that skips `declinedThenAccepted` by name. The `shape` test (`:113-121`) still runs on that history, and it passes, because it is one stream with versions 1…2.

Calling `makeStream` inside a separate test file moves no locked hash: the histories are built when `histories.ts` is imported.

## 3. The projection case: what `findingOfRow` may and may not do

The fold runs on SQLite in `pnpm test` (`packages/projector/unit/backlog-rebuild.test.ts:12-18`) and on Postgres in production. The two drivers return `decided_at` and `decided_seq` as different JS types. So:

- `findingOfRow` converts only what a rule reads:
  - `status`, which is `open | accepted | declined` (`packages/projector/src/backlog.ts:45`);
  - for `accepted`, whether `proposed_ref` is null.
- Fill the other fields with placeholders (`new Date(0)`, `0n`, `''`, `[]`). Do not parse driver values that nothing reads.
- A `status` outside the three throws, naming the project and key. The table's default is `'open'` (`:99`), so a row the writers made is never caught by this.
- The `update` takes its values from the **event**: `event.at`, `seq`, and the payload, exactly as the three statements before this change did. It never takes them from the new state. The new state only decides *which* of the three statements runs. That keeps every column but `last_seq` identical to the old fold by construction rather than by luck; `last_seq` is the one added key, and each statement writes it and carries `last_seq is null or last_seq < $5` in its `where`, so a stale runner matches nothing.
- Comparing the old state with the new state is fine. A simpler test is enough: `old.status === 'open'` picks accept or decline, and anything else that did not throw is the proposal.

**Several events for one key in one batch.** Each event re-`select`s its row inside the same transaction, so it sees the previous event's `update`. That is the only reason "batches of 1, of 3 and all at once" agree, and it is why the row must not be cached across the loop in `apply`.

**No row means no fold** (the ticket's step 2). On that path a malformed decision stream does *not* throw in the projection. That is not a gap: a finding that was never raised has no row to be wrong about. The conductor still throws on it.

## 4. The two new projector tests

Both go in `backlog-rebuild.test.ts`'s shape. The incremental test reuses the module-scope `events` (`:20-22`) and folds it with batch sizes 1 and 3 next to the existing `foldInTwoBatches` (`:347-360`). Compare against `fold(events)` (`:332-345`), not against the snapshot. The snapshot is pinned only by the existing test. It was regenerated once, for #838, to add the `last_seq` key to each row and nothing else (`:6-10`); it is not regenerated again.

The "row equals `reduceFinding`" test does not need the fixture histories. It reads each of the three pinned findings' decision streams out of `events` by `backlogStream(PROJECT, key)` and compares:

| `reduceFinding` field | row column |
|---|---|
| `status` | `status` |
| `by` | `decided_by` |
| `seq` | `decided_seq`, compared as strings |
| `kind` / `reason` | `kind` / `reason` |
| `proposed.externalRef` / `.url` | `proposed_ref` / `proposed_url` |

Leave `labels` and `proposed.seq` out: the row does not keep them (Out of scope).

`settle`'s changed sentence is the only behaviour change, and the writers cannot reach it, so no test is owed for it.
