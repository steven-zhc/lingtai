## Design: #500, scope doctor's three schema checks to `public.events`

### The decision: query every schema, judge only `public`, in TypeScript

The ticket's **Fix** puts the scoping in the SQL (`where schemaname = 'public'`). Don't do it that way. A unit test can't run SQL, so if the filter lives in the query string, a "fake catalogue with a second `events` schema" has nothing to exercise. The test would just hand a pure function the rows the fixed query would already have returned, and it would pass whether or not the query is right. The first two **Done when** boxes would then prove nothing.

So split `schema()` (`apps/cli/src/doctor.ts:475`) the way the rest of this file splits a row from its reach (`storeRow`, `logReachable`, `postgresOnlyRows` are exported and tested without a database in `apps/cli/unit/doctor.test.ts:24`):

1. **The three queries stay inside `schema()` and return the schema name with every row.** They keep matching on `tablename = 'events'` across all schemas, which is the behaviour that causes the bug, and now they also say which schema each row came from:
   - The index query (`:494`) selects `schemaname` from `pg_indexes`.
   - The rules query (`:507`) selects `schemaname, rulename` from `pg_rules`.
   - The trigger query (`:521`) adds `join pg_namespace n on n.oid = c.relnamespace` and selects `n.nspname as schemaname`.

   Use the join, **not `'public.events'::regclass`**. A missing `public.events` makes the regclass cast throw. That would fall into the `catch` at `:551` and collapse all five schema rows into one `schema` failure, losing the `schema: tables` row (`:485`) that names the real problem.

2. **Add one exported pure function** that takes the three row sets plus the log's schema name and returns the three `CheckResult`s. It is the only place that filters to `public`, and the unit test's fake catalogue goes into it. Name the schema once, as a constant beside it. `'public'` already appears hard-coded at `:485` and `:537`, and those two can take the constant too. Keep the existing row names and `detail` strings word for word: `apps/cli/integration/doctor.test.ts:937-939` and `lingtai restart`'s gate both match on the names.

3. **Count "present", not "exactly one".** Today's checks are `uq.rowCount === 1` (`:499`), `ruleNames.length === 2` (`:512`) and `trig.rowCount === 1` (`:526`). Exact counts are what turned "found it twice" into "MISSING". After filtering:
   - The index check passes when at least one `public` row matches.
   - The append-only check passes when the set of `public` rule names is both names.
   - The trigger check passes when at least one `public` row matches.

   An exact count would still print "MISSING" for a second matching index on `public.events`, which is the same wrong emergency the ticket's **Watch out** describes.

   The append-only failure detail at `:516` lists the rule names it found. Build that list from the `public` rows only. Today the archive's copies are what printed `lingtai_events_no_delete, lingtai_events_no_delete, …`.

### The tests

Add them to `apps/cli/unit/doctor.test.ts`, which already imports `../src/doctor.ts` and is not in `ON_POSTGRES` (`packages/event-store/test/postgres.ts:33` lists only the integration file). Don't import `pg` or call `createDb(` there: `packages/event-store/unit/on-postgres.test.ts:69` fails the unit half on either. The fake catalogue is three arrays of rows, each row carrying a `schemaname`.

- **Healthy case:** both `public` and `archive_20261012` are complete, and all three checks are `ok`.
- **Failure cases:** for each check, `public` lacks its piece while the archive still has it, and that check is `fail` while the other two stay `ok`.
- **Rules detail:** when one `public` rule is missing and the archive has both, the detail names only the one rule `public` has.

### What the unit half cannot see

The column names `pg_indexes.schemaname`, `pg_rules.schemaname` and `pg_namespace.nspname` are standard Postgres catalogue columns. Inside a pass, though, only `apps/cli/integration/doctor.test.ts:937-939` runs this SQL against a real server, and that file is in the integration half, which is out of reach before the merge. Run it if a `LINGTAI_TEST_DATABASE_URL` happens to be set; don't make finishing the ticket depend on it.

Don't add a second-schema case to that integration file either. The pure function's test covers the scoping, and the person's **Done when** box (`lingtai doctor` on this machine) is the real check against `archive_20261012`.

**Nothing in this change creates, reads past the catalogue, or drops anything in a non-`public` schema.** The three queries are `select`s on `pg_indexes`, `pg_rules`, `pg_trigger`/`pg_class`/`pg_namespace`, and that should stay true of every line written here.
