## The decision the ticket does not make: "absent versus empty" is one thing today

The ticket asks the page to explain "what absent versus empty steps mean." In the code they mean **the same thing**, and the page must say so rather than invent a difference.

- **The parser treats them the same.** Every step list is `.default([])` (`packages/recipe/src/recipe.ts:2671`), and the resolved recipe always carries all ten steps (`recipe.ts:3171-3185`: *"the file may omit a step, the resolved recipe may not"*).
- **The engine treats them the same.** `const running = declared.length > 0 ? declared : defaultsAt(step)` (`packages/conductor/src/conduct.ts:3283`). The comment says it outright (`conduct.ts:3214-3220`): *"**`[]` and an omitted key are the same thing here, and 0065 §2's *`[]` runs nothing* is not built.** … an `admit: []` cuts and a `merge: []` merges."*

So the distinction worth teaching is **declared versus not declared**. An empty or omitted step runs its built-in default, which `defaultsAt` defines at `conduct.ts:3240-3273`:

| Step | Built-in default when nothing is declared |
|---|---|
| `claim` | the queue takes a ticket |
| `admit` | cuts the branch and worktree from the base |
| `implement` | one agent on `runtime.agent` |
| `merge` | lands with `strategy: merge-commit` |
| the other six | nothing |

Writing anything at a step **replaces** that default. It does not add to it (`conduct.ts:3232-3238`). That is the trap to state plainly: a reader who writes `merge: [{ run: … }]` to add a check has removed the landing.

The other half of the trap: **`merge: []` does not stop landing.** A hold is a `human:` at `proposed:`, and `human:` is legal nowhere else (`doc/plugins/index.md` table; `packages/recipe/src/answers.ts:43-49`: *"An absent or empty `merge:` still runs the default lane"*).

Because 0065 §2 says `[]` runs nothing and the code does not do that, cite `conduct.ts:3214` and say the page describes what is built. **Do not describe 0065 §2 as current behaviour**, and do not edit the ADR.
