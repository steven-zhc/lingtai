# Design note: #575, a judge/triage disagreement is the person's decision

## Where it goes

Three places. Nothing new is written to the log.

1. **`packages/domain/src/wait.ts`**: the recommendation and what the judge's reading maps to. Both are pure.
2. **`apps/board/src/app/triage-picks.tsx`**: the page state, kept in the provider that already wraps the whole page.
3. **`apps/board/src/app/standing.tsx`**: the band gets the choice control, and the resolution grid reads the choice.

## 1. Domain: one function still decides

The board's comment at `standing.tsx:540` is the rule to keep: *"The only place a recommendation is decided is `recommendedResolution` (0118 §1)"*. So the person's pick goes into that function as an argument. Do not write a second function beside it.

- Export a `Disagreement` type, which is the return type `disagreement()` writes inline at `wait.ts:868-874`.
- Add two options to `recommendedResolution` (`wait.ts:677`): `disagreement?: Disagreement | null` and `picked?: 'judge' | 'triage' | null`.
  - **Disagreement present, `picked` null or absent:** return `null`. This is the Done-when line.
  - **`picked: 'triage'`:** run today's path unchanged, including the contradiction drops at `wait.ts:694-696`.
  - **`picked: 'judge'`:** look up `judgeResolution(disagreement.judge.chose)` and pass the result through the same `allowed` filter. That filter already removes `GrantFixRound` when `savedHead: false`.
  - **No disagreement:** `picked` is ignored, and every existing call returns what it returns today.
- The caller passes the disagreement in, as the ticket's Watch-out asks. `recommendedResolution` must not call `judgeReadingOf` itself or read `why`.
- New `judgeResolution(chose: CandidateId): Resolution['_tag'] | null`, placed beside `judgeReadingOf` (`wait.ts:853`). It reads only the id. The mapping follows where `destinationOf` sends each candidate (`packages/conductor/src/proposed-route.ts:95-107`):

| `chose` | destination there | resolution here |
|---|---|---|
| `fix-lines` | `implement` | `GrantFixRound` |
| `restart` | `claim` (`Requeued{Restart}`) | `Requeue` |
| `state-assumption` | `proposal.from` | `EditBodyAndRequeue` |
| `hand-to-person` | `waiting` | `null` |
| anything else | — | `null` (`CandidateId` is `z.string()`, `route.ts:23`, so it needs a `default`) |

**This is the decision the ticket leaves open.** Picking *the judge is right* where the judge handed over (`JudgeHandedOver` always reads `hand-to-person`, `wait.ts:856-857`) draws nothing first. That is a real answer, not a gap: the judge's reading *was* "a person decides". The page has to say so in words; see §3. Only `CandidateUnavailable` (`wait.ts:858-859`) can give the judge's pick a resolution to draw first. Put a sentence in the PR noting that this is narrower than 0118 §5's *"asks which is right"* might suggest. The ticket's Evidence already flags it.

**Unit tests** go in `packages/domain/unit/wait.test.ts` beside `describe('recommendedResolution')` (`:404`):
- the disagreement case returns `null`;
- `picked: 'triage'` equals the call without a disagreement;
- `picked: 'judge'` on `CandidateUnavailable{fix-lines}` returns `GrantFixRound`, and returns `null` under `savedHead: false`;
- `picked: 'judge'` on `JudgeHandedOver` returns `null`;
- `judgeResolution` gives the table above, row by row.

## 2. Page state: extend `TriagePicks`, don't add a second provider

`Standing` is a server component (no `'use client'`; it is rendered from the page). `TriagePicks` (`triage-picks.tsx:17`) is a client context that already wraps the whole of `Standing`'s output (`standing.tsx:675`). It already forgets its state when `waitId` changes (`triage-picks.tsx:26-27`), and a reading picked for one wait must be dropped the same way.

Add `reading: 'judge' | 'triage' | null` and `pickReading(r)` to that context. Store `reading` inside the same `{ waitId, … }` record so it resets together with the answers.

**Nothing leaves the browser.** The choice only reorders cards. The resolution the person then confirms goes through the existing actions unchanged. 0118 §6 (`doc/decisions/0118-a-hold-explains-itself.md:439`): *"Which advice a resolution answered is derived, never written."* Do not add an event, a field on `WaitResolved`, a form field or a hidden input. Checking the third Done-when box means confirming the diff touches no file under `packages/domain/src/events*`, and no `actions.ts`.

## 3. The board

**The band (`standing.tsx:236-262`).** Under *"Which reading is right?"*, add a small client control that reads the context. Use radios in the style of `TriageChoices` (`triage-picks.tsx:48`), with three options: *The judge is right* / *Triage is right* / *Neither*. Neither is selected at first. Where `judgeResolution` gives `null`, the judge option's copy says that picking it draws nothing first: the judge handed the wait to you. None of the three options resolves the wait.

**Trap in the same function.** `kept` at `standing.tsx:222` calls `recommendedResolution` to decide whether the triage reading says *"Recommends X"*. Once the disagreement makes that call return `null`, the triage reading would say *"Triage advised X, which this wait does not offer"*, which is false. Inside the side-by-side, compute `kept` with `picked: 'triage'`. That is the reading being described, whether or not it has been picked.

**The grid (`standing.tsx:543-566`, `:891-1000`).** When there is a disagreement, the server cannot know the order, so the ordering moves into a client component.

- The server computes `readings = disagreement(reason, result)` once, when the status is `Done` with `TriageAdvised`.
- It computes three answers from `recommendedResolution`: picked `null`, `'judge'` and `'triage'`.
- It renders each card's content as today, keyed by tag.
- It passes `{ cards: Record<tag, ReactNode>, order: drawable, recommendedBy }` to a client `ResolutionGrid`. That component sorts the cards and sets the `sresolution--recommended` class and badge from the context.
- The values have to be JSX, not render functions: a function prop cannot cross from a server component to a client one.

Keys must stay stable. The comment at `:567` says the body editor stays mounted across refreshes, and reordering keyed children preserves that.

The badge says whose reading put the card first: *Judge's reading* or *Triage recommended*. Today it always says the second (`:914`).

The buttons' `primary` / `recommended` props (`Decide`, `Send`, `Requeue`, `ContinueFixing`) stay as the server computed them with no pick, which means none are promoted while a disagreement stands. Moving the card first and giving it the badge is enough to satisfy "draws that reading's resolution first". Promoting a button on a client pick would mean threading the context into four components, and nothing in the ticket asks for it.

With no disagreement, `recommendedBy` is the single settled tag and the render is byte-for-byte what it is today.

**Existing test that must change.** `apps/board/unit/standing.test.tsx:1471` is titled *"…without changing the resolutions"* and asserts `moves(disagreeing) === moves(agreeing)` (`:1506`). That is exactly the behaviour this ticket reverses: the agreeing render draws triage's `Close` first, and the disagreeing one must not. Rewrite the assertion so the disagreeing render has no `sresolution--recommended` and has the band's three unchecked choices.

**What the board's tests can reach.** They use `renderToStaticMarkup` (`triage-band.test.tsx:2`), and the repo has no DOM-event library. A click therefore cannot be tested at unit level, and do not add a dependency to make it testable. The pick is covered by the domain tests in §1. Add a static render of `ResolutionGrid` with each `reading` passed as a prop, or exported so it can be called directly, asserting which tag comes first for each.
