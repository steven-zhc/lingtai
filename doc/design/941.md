## Design note for #941: claim drawn as passed, and default actions shown in the plan

### Where the table goes: its own file, imported by subpath

Put the four names in a new file, `packages/recipe/src/defaults.ts`. Its only import is `import type { Step } from '@lingtai/domain'`. Export it from `packages/recipe/src/index.ts`, so `conduct.ts` can keep importing the package root. Also add a `"./defaults"` subpath to `packages/recipe/package.json`'s `exports`, which today lists only `.`, `./duration` and `./settings`.

**The board must import it from `@lingtai/recipe/defaults` and never from the root.** `apps/board/src/lib/progress.ts` is imported by two client components: `apps/board/src/app/last-event.tsx:5` and `apps/board/src/app/since.tsx:5`. `packages/recipe/src/judges.ts` explains why that matters:

> *"`settings.ts` is read by the board's wizard, which is a client component, and a value imported from `recipe.ts` drags `@lingtai/env` and its `node:fs` into"* the client graph.

`duration.ts` exists for the same reason (#164). `tsc` cannot see this mistake. The only check that does is `apps/release/integration/build.test.ts`, which is in the integration half and out of reach inside a pass (#230 is what a late catch looks like). The unit-level stand-in is the import itself: `progress.ts` and `queued.ts` import the subpath, and `defaults.ts` imports nothing but a type.

### Shape: a table and one function

- `DEFAULT_ACTION`: a readonly partial record from `Step` to a name. It has entries for `claim`, `admit`, `implement` and `merge`, and nothing else.
- `plannedAt(step, declared: readonly string[]): readonly string[]`: returns `declared` when it is non-empty, otherwise `[DEFAULT_ACTION[step]]` when there is one, otherwise `[]`.

This function is the substitution rule (0065 §2: *a default replaces what would have run*), written once. Both board readers call it, so `planOf` and `progressOf` cannot disagree. `defaultsAt` (`conduct.ts:3568-3600`) reads its four `name:` strings from `DEFAULT_ACTION` and keeps everything else. It does not call `plannedAt`, because it builds actions, not names.

### `progressOf`: test for an empty list, not a missing one

`progress.ts:387-388` is `recorded?.actions ?? (plan.get(step) ?? []).map(...)`. For every log since `StepsResolved`, `recorded.actions` is `[]` at `claim` and `admit`, not `undefined`, because `stepsResolved` writes `resolved.recipe.steps[step].map(a => a.name)` (`packages/conductor/src/steps-resolved.ts:18-21`). The `??` therefore never reaches a fallback. Keep that line as it is, and pass its result through `plannedAt(step, …)`. This covers both the recorded branch and the recipe branch, and with them the *old log with no `StepsResolved`* edge.

### Drawing `claim` as passed

Inside `progressOf`'s `STEPS.map`, when `step === 'claim'`, give every name in `planned` the verdict `'passed'` unless the stream already has a `claim:` key for it. Then pass those verdicts into `stateOf` and set the cell's state from them.

Today no `claim:` key ever reaches `state.steps`:
- `claim` runs outside the walk (`run-attempt.ts:1519-1524`).
- `nextOf` throws for it (`packages/domain/src/attempt-next.ts:117`: *"claim and end run outside runPass"*).
- The claim's own events are on the ticket stream (`packages/domain/src/events.ts:2478-2479`).

The *unless* is there so that the day #463 is undone, a recorded verdict wins over the one we make up.

Do this before `stateOf`, not as a special case inside it. With `seen` non-empty, the `onRecord … seen.length === 0` rule (`progress.ts:338`) is never asked about `claim`, and that is exactly the trap the ticket's *Watch out* names. Leave `stateOf` alone except for the comment.

### What else changes on the rail, so it does not surprise the reviewer

Running `plannedAt` over the recorded plan also fills in `admit`, `implement` and (when declared empty) `merge`. That has three effects:

- **`implement` on a running attempt that has not reached it** now reads `pending` instead of `skipped`. That is correct: it will run.
- **On a landed attempt** those steps have their own `StepEnded`. That is the ticket's evidence for `admit`, `implement` and `merge` on #937's attempt.
- **Name mismatch.** The new action cell matches the logged verdict only if the key is `${step}:${action.name}`. The ticket's run-log line `claim:take the ticket` suggests it is, but check it in the test. Use a fixture with a real `admit:cut the branch` `StepEnded`, and assert one passed cell, not a pending `cut the branch` beside an extra.

If an old log keyed these differently, a landed attempt would show a `pending` default cell next to the real one. The fix there is the test fixture, not a guard.

### `planOf`

`queued.ts:196-197` becomes `const actions = plannedAt(step, (plan.get(step) ?? []).map(a => a.name))`. Leave `skipped: actions.length === 0` as it is: after the substitution, it means exactly *empty and no default*.

### The comment

`progress.ts:64-77` says `admit`, `claim` and `implement` each record a verdict "on every run". Make that true of `admit` and `implement` only. Then say that `claim` runs before the walk and gets no step events (#463), that `progressOf` draws it passed because an attempt stream exists only after a claim passed (`conduct.ts:4359-4377`), and that the plan is no longer empty at a default-filled step, because `plannedAt` fills it.

The sentence about *"A `claim` segment reading `failed` is the take declining"* describes something this stream cannot show. Delete it. A take that declined has no attempt.

### Tests

- **`progressOf`:** add the cases from the ticket's *Done when* to the existing unit file for `progress.ts`, plus the `admit` key check above.
- **`planOf`:** cases for `claim`, `admit` and `implement` filled in, `design` skipped, and a declared `claim:` list winning over the default.
- **`defaultsAt`:** needs no new test. The conductor's existing tests still read the same names.

Rail snapshots that change from a dashed `claim` to a passed one are expected, so update them; don't treat them as regressions.
