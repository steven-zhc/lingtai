# Design: #398, the agent questions belong to the project, and `init` stops asking

## Where the questions are asked: `lingtai add`, not `init`

`init` has no project yet. It knows the store, the App and the board (`apps/cli/src/init.ts:239-325`), and nothing in it names a repository. The first-project question is #394, which is still open, and #398 is not blocked by it (#398's only blockers are #392 and #395, both closed). So a per-project question asked inside `init` today would have no recipe to write into.

The command that has a project is `lingtai add <owner>/<repo>`. `addCommand` is at `apps/cli/src/lingtai.ts:362`, and it calls `add()` at `packages/conductor/src/onboard.ts:247`, where `parseSlug` at `:248` gives `repo`, the project name. #391 decision 5 says *"`lingtai add` asks the same recipe questions for every later project, through the same code."*

**The decision:**
- The questions live in a new `apps/cli/src/agents.ts`. It returns `RecipeChange[]` and imports nothing from `init.ts`, for the same reason `question.ts` doesn't (`question.ts:8-10`).
- `addCommand` asks them **before** it calls `add()`.
- When #394 lands, `init` calls the same function for the first project.

**Ask before `add()`, not inside it.** Two reasons:
- `add()` is in `@lingtai/conductor`, which has no question seam.
- `add()` resolves the recipe at `onboard.ts:285` with `resolveLocalRecipe(repo, { signedIn: signedInHere })`. On a file with no `runtime.agent` and two runtimes signed in, that is exactly the refusal at `packages/recipe/src/local.ts:180-186`: *"… names no runtime.agent — which one should run?"* The answer has to be written before that line runs.

**An absent recipe is not created here.** `doc/design/395.md`, *"a new file is written once"*: a new file needs `repo.base`, `source.kinds` and `env` to resolve, and those are #394's and #396's answers. #395 decided not to guess them. So:
- **The file exists:** ask, then write with `setRecipe`.
- **The file is absent and no agent flag was given:** ask nothing. `add()` refuses as it does today, with `RecipeMissingError` (`local.ts:303-309`).
- **The file is absent and an agent flag was given:** refuse by name: *"--agent needs a recipe to write into; there is none at \<path\>. Nothing was written."* A flag that is silently ignored is the one outcome #391 rules out.

**Returning `RecipeChange[]` is what lets #394 batch these answers** into the single first write that #395 requires.

## What is offered

Get the runtimes the way `init` does: `askEveryRuntime(runnableEnv({}))` mapped to `RuntimeFound` (`init.ts:689-699`).
- Move that mapping and the `RuntimeFound` type (`init.ts:121-127`) into a small `apps/cli/src/runtimes.ts`, so `add` doesn't import `init.ts` and through it `board.ts`.
- Move the readline `ask` (`init.ts:671-684`) into `question.ts` as the live `QuestionWorld.ask`, so both commands share one terminal reader.

Rules for what is offered:
- **Offer only runtimes with `signedIn: true`.** For every runtime that is left out, log one line before the question saying why: `codex is installed and not signed in (<detail>) — not offered; sign in and run lingtai add again to choose it`, or `codex is not installed`. Reuse the wording at `init.ts:645-647`.
- **`--agent codex` when codex is not signed in** is refused through `validate` with that same reason. Don't use `choices` for this: `choices`' message is a bare `codex is not one of claude-code` (`question.ts:46-48`), which is the hidden reason the ticket's *Watch out* is about.
- **No runtime signed in at all:** refuse before any question, with today's `init.ts:644-652` sentence (minus *"run lingtai init again"*). Nothing is written. This is where `init`'s refusal goes when `init` stops making it.
- **The reviewer gets the same rule.** `agentRefusal` (`packages/conductor/src/conduct.ts:282`) reads every `agent:` in the file against what is signed in, so a reviewer on a signed-out runtime fails the first pass in the same way.

## The four questions and their defaults

All four go through `question()`. Every question needs a flag (#391, *Rules*), so the reviewer's model gets one too: **`--reviewer-model`** is added beside the ticket's three.

| Question | Flag | `current` (re-run) | `detected` |
|---|---|---|---|
| Which agent writes the change | `--agent` | the `agent` of the entry carrying `agent:` in `steps.implement`, else `runtime.agent`, but only if it is signed in now | the first signed-in runtime |
| On which model (empty means the runtime's own default) | `--model` | that entry's `model` | `''` |
| A cold reviewer? Which agent, or `none` | `--reviewer <agent>\|none` | the `agent` of the agent entry in `steps.review`; `none` when the file writes `review: []` | a signed-in runtime **other than the writer's**, else the writer's |
| The reviewer's model | `--reviewer-model` | that entry's `model` | see below |

Read `current` with `readRecipeKey` (`packages/recipe/src/write.ts:199`). It returns what the file says, not what resolves: that is #395's rule against writing a preset's value into the file because someone pressed enter. A written agent that is no longer signed in is not passed as `current`. Log why, and fall through to `detected`.

**"A different model from the writer" without a table of models.** Lingtai keeps no list of models. `recipe.ts:210-215` says why: *"Lingtai carries no table of what each runtime defaults to: naming one here would be a second place for it to be wrong."* So the default is a different model only where the code can know that:
- **The reviewer is on another runtime:** default `''`. That is a different model by construction.
- **Same runtime, and the writer named model X:** default `''`, the runtime's own default. Don't default to X.
- **Same runtime, and the writer took the default:** there is nothing to name. Default `''`, and log one muted line: the reviewer will read with the same model that wrote the change, and typing a model name changes that. Don't refuse that answer. It is legal, and #391 says *"if one is available"*.

**The question asks nothing when no reviewer is chosen.** When the reviewer answer is `none`, skip the reviewer-model question entirely. Like any flag, `--reviewer-model` beside `--reviewer none` is refused by name, never ignored.

## What is written

There are two `setRecipe` calls (`write.ts:172`), one after each pair of answers. #392 decision 1 lets an existing file be written as each answer arrives, so a Ctrl+C at the reviewer keeps the writer.

**After the writer and its model:**
- **`runtime.agent` = the writer, always.** This is the *Watch out*'s second line. `8a7ace8`'s refusal fires only when `runtime.agent` is absent (`local.ts:172-192`, reached from `:316-325`), so a recipe written by this code never reaches it. `steps.implement`'s `agent:` overrides `runtime.agent` (`recipe.ts:283-292`), so the two are written to the same value and `agentRefusal`'s `named !== dispatched` (`conduct.ts:287`) has no disagreement to find.
- **`steps.implement`, when it already holds an entry with `agent:`:** set `['steps','implement',i,'agent']` and `[…,i,'model']` in place, where `i` is that entry's index. Pass `value: undefined` for an empty model, which removes the key (`emit.ts:57`). This keeps the entry's `prompt:`. This repository's own recipe has one at `implement:` and `review:` (`~/.lingtai/lingtai/recipe.yml:79-86`, `:108-112`), and the review prompt is about 100 lines.
- **`steps.implement`, when absent or empty:** write `[{ name: 'write the change', agent, prompt: '', model? }]`.
  - The name and the empty prompt are `defaultsAt`'s (`conduct.ts:2325-2342`).
  - `prompt` is required (`DISPATCH.prompt`, `recipe.ts:218`).
  - `''` is the default: *"A recipe's `prompt:` is appended to that and never substituted for it — the rule the cold reviewer follows"* (`conduct.ts:2336-2339`).

**After the reviewer:**
- **`none`:** `steps.review: []`, written out rather than left absent (0064 §5). `defaultsAt` has no `review` row (`conduct.ts:2317-2352`), so `[]` means no reviewer.
- **An agent, with an existing agent entry:** change it in place, as for `implement`.
- **An agent, with no existing entry:** `[{ name: 'review', agent, prompt: '', model? }]`.
- **Other entries are not edited.** `agentPlugin` is the only plugin served at `review` (`recipe.ts:409-415`), and only the first agent entry is edited. Log that any second reviewer was left as written.
- **`none` over an entry with comments in it** gets `CommentWouldBeLostError` from `editRecipe`. Print it as the refusal. Don't catch it and go round again.

**On a file that `extends:` a preset and writes no `steps:`, the first `steps.*` write pins the preset's steps into the file for good.** `write.ts:102-125` says this, and `doc/design/395.md` says *"A caller showing this question to a person is the place to say so."* Detect it with `readRecipeKey(['extends'])` non-null and `readRecipeKey(['steps'])` null. Log one line before the writer question, naming the preset.

**A non-TTY `lingtai add` on an existing project now needs the flags.** #392 decision 3 refuses with no terminal *"even when a `current` exists"*. That is a behaviour change for anything that runs `lingtai add` unattended. The board's *Recheck* calls `add()` directly (`onboard.ts:25-33`), not `addCommand`, so it is not affected. Name the change in the commit body.

## `init`

- **Delete `checkAgent`'s signed-in half** (`init.ts:643-658`) and its call at `:278-280`.
- **Keep the refusal at `:635-641` as a pure function**, `machineRuntimeRefusal(config: Document, path: string): string | null`. Call it where `checkAgent` was, before the App step. That keeps the migration message on the path it is on today, and a pure function can be tested in `unit/`.
- **Keep the look step's per-runtime lines** (`init.ts:257-262`). They are how a person sees what `add` will offer.
- **Update the header's `agent` row (`:8`) and paragraph (`:28-32`)** to say *which runtime runs, and the reviewer, are asked by `lingtai add` per project*. The paragraph currently says the board's onboarding page asks, and that `init` checks whether anything is signed in. Both stop being true here.

`apps/cli/integration/init.test.ts:284-294`, `:308-317` and `:374` pin the old agent lines. Rewrite or delete them, and keep `:296-306`, which is the migration refusal. That file is the integration half. It needs no database, so it runs on its own within a pass:

```sh
pnpm vitest run --project integration apps/cli/integration/init.test.ts
```

## Unit tests (`apps/cli/unit/agents.test.ts`)

Use the fake world from `question.test.ts`, a `Map`-backed `RecipeFiles`, and an inline recipe string that resolves. Nothing touches the disk.

- **Only signed-in runtimes are offered:**
  - signed out, and installed but not signed in, each produce a logged reason and are not offered;
  - `--agent <that one>` is refused with that reason;
  - none signed in refuses, and `replace` is never called.
- **The reviewer's defaults:**
  - with two signed in, the reviewer defaults to the other runtime;
  - with one signed in and `--model X`, the reviewer model's default is not `X`.
- **`--reviewer none`:** writes `steps.review: []`, and the text has no `agent:` under `review`. `--reviewer-model` beside it is refused.
- **What is written resolves.** Take the `text` from `setRecipe` and pass it to `resolveLocalRecipe(project, { home, read, signedIn: async () => ['claude-code', 'codex'] })`. That function already takes `read` and `home` (`local.ts:267-281`). Two signed in is the condition under which a missing `runtime.agent` refuses, so this test fails if the write ever leaves it out. Also assert that `recipe.steps.implement[0].agent` equals the writer.
- **An existing implement prompt survives** a change of agent or model, compared as an exact string.
- **`machineRuntimeRefusal`:** `runtime:` refuses, `projects:` refuses, and a file with neither returns null.

Everything above runs in `pnpm test`. The only thing that needs the integration half is the edit to `init.test.ts`, and the single-file run above covers it.
