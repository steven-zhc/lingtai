## Shape for #735

### Where the classification lives

Two pure functions are exported from `packages/agent/src/auth.ts`, next to the probes they serve. A suggested name is `classifyCodexLogin` / `classifyClaudeAuth`. They import nothing new. Today the file imports `node:child_process`, `RuntimeId` from `@lingtai/domain` and a type from `./runtime.ts` (`auth.ts:11-15`), and the header says why that list stays short: "`lingtai init` asks before there is a log (#186)" (`auth.ts:4-9`).

Each function takes one value describing what the child did, as a discriminated union, and returns the **whole** `AuthStatus`, not just the state:

```ts
type ProbeEnd =
  | { kind: 'spawn-error'; code: string | undefined; message: string }   // child.on('error')
  | { kind: 'timeout' }                                                   // the 20s timer
  | { kind: 'exited'; code: number | null; signal: NodeJS.Signals | null; out: string; err: string }
```

The probes only gather this value and resolve with `classify…(end)`.

- **Read the spawn error's `code === 'ENOENT'`**, not `/ENOENT/` on its message. That regex is what `askRuntimes` does today (`apps/cli/src/runtimes.ts:33-34`), and it is the one heuristic this ticket removes.
- **Keep the first-settle-wins order.** The Promise may already be settled when Node fires `close` after an `error`, or after the timer's `SIGKILL` (`auth.ts:44-47, 103-107`). Today the extra resolves do nothing, and that is the behaviour that must survive. Don't restructure this into a "last event decides" handler: a timed-out Codex would then read as `exited` with `signal: 'SIGKILL'`. That still lands in `did-not-start`, but it loses the "did not answer in 20s" detail.
- **Codex.** `codexAuth` merges stdout and stderr into one buffer (`auth.ts:100-101`). Pass it as `out` with `err: ''`, or fold the two the same way inside the classifier. Either works, but there is only one place to test.

### `AuthStatus` gains `state`, and keeps `loggedIn`

`AuthStatus` is at `packages/agent/src/runtime.ts:248-254`. Add `export type AuthState = 'signed-in' | 'signed-out' | 'not-installed' | 'did-not-start'` next to it, and give the interface `state: AuthState`. **Do not remove `loggedIn`.** It has readers outside this ticket's scope:

- the conductor's signed-in list, `packages/conductor/src/projects.ts:110` (`(await r.checkAuth?.(env))?.loggedIn`), which feeds `agentRefusal`, whose behaviour the ticket keeps;
- the board, `apps/board/src/lib/recipe.ts:453, 494, 514-515`;
- `doctor`'s machine row, `doctor.ts:912`, which the ticket marks out of scope.

The two fields can never disagree because the classifier is the only place either is set: `loggedIn: state === 'signed-in'`. The other place that builds an `AuthStatus` is `codex-text.ts:32`, which gets `state: 'signed-in'`.

**`tsc` will not find every fake.** The doctor fakes are cast: `as unknown as Runtime` in `apps/cli/unit/doctor-progress.test.ts:19-22`, and `as never` in `doctor-titles-projects.test.ts:41-46`. So a fake without `state` compiles and arrives as `undefined`. The rule for every reader below is that a `state` it does not recognise, including `undefined`, is worded as `did-not-start`, never as signed out. That is the ticket's Watch out applied to the reader as well as the probe. Signed-out fakes such as `doctor-titles-projects.test.ts:44` and `:155`, and `doctor-ownerless.test.ts:94`, will go red in `pnpm test` until they carry `state: 'signed-out'`. That is the intended way to find them. Grep `loggedIn:` under `apps/cli/unit` and `packages/conductor/unit` (listed in the evidence above), and add `state` to every one.

### Claude Code: Watch out wins over Edges

The two rows disagree on one input: parsed JSON with **no** `loggedIn` key. Edges says "`loggedIn` not `true` → `signed-out`"; Watch out says "only when its JSON parsed and said `loggedIn: false`".

**Build Watch out's version:**

- `loggedIn === true` → `signed-in`
- `loggedIn === false` → `signed-out`
- any other value, including a missing key → `did-not-start`, with the output as `detail`

This is the safe side: the person sees a line instead of being told to sign in. It also matches the Codex rule's insistence on a positive sign. Keep the `{`-search that tolerates a leading warning line (`auth.ts:56-58`).

### `RuntimeFound` swaps `installed` for `state`

`RuntimeFound` is at `apps/cli/src/runtimes.ts:15-21`. Replace `installed: boolean` with `state: AuthState`, and keep `signedIn` as `state === 'signed-in'`, set inside `askRuntimes` only. `signedIn` has many filtering readers (`agents.ts:145`, and others through `first-project.ts`). `installed` has two readers in `src`: `agents.ts:34` and `init.ts:329`. Dropping it means a fixture that says `installed: true` with no `state` fails `tsc` instead of passing quietly.

The fixtures to change are the `installed:` lines in `apps/cli/unit/{agents,add,add-github,add-github-gh,first-project,init,layout-625,recipe-flow,recipe-summary}.test.ts` and `apps/cli/integration/init.test.ts:260-266`. `apps/cli/tsconfig.json:3` includes `integration`, so `pnpm typecheck` covers the integration fixture even though nobody runs that file in a pass.

### One sentence per state, written once

Put the wording in `apps/cli/src/runtimes.ts`, which `agents.ts` and `init.ts` already import. `doctor.ts` should import it from there too; `runtimes.ts` loads only `@lingtai/agent-env` and `@lingtai/agent/auth`, so it adds no weight. Two helpers:

- `firstLine(detail)`: the first non-empty line, or `printed nothing`.
- `runtimeStateSentence(id, state, detail)`:
  - `not installed`
  - `installed but does not start: <firstLine>`
  - `installed and signed out`

These replace `whyMissing` (`agents.ts:33-35`) and the expression on `init.ts:329`. That makes the Done-when line come out exactly: "codex is installed but does not start: dyld[…]: Library not loaded …".

The remedy depends on the state, so it is a second function, `remedyFor(state)`:

| state | remedy |
|---|---|
| `not-installed` | install it |
| `did-not-start` | fix what it printed |
| `signed-out` | sign in to it |

`refuseUnlessOffered` (`agents.ts:154-162`) becomes `` `${sentence} — ${remedy}, or choose one of ${choiceList}${extra}` `` for a runtime it found. For an answer that names no runtime it becomes `` `${answer} is not a runtime — choose one of ${choiceList}${extra}` ``. #727 has landed: the empty-answer line at `agents.ts:159` is already there and is left as it is.

`noRuntimesSignedInRefusal` (`agents.ts:43-48`, also called from `first-project.ts:474`):

- It joins the per-runtime sentences unchanged.
- Its fixed "Sign in to one and try again" is replaced by the distinct remedies of the states present, in a fixed order and joined with ", or ".
- It keeps the trailing "whether it is paid for is between you and its provider".

### Doctor

`dispatchedAuthRow` (`doctor.ts:2466-2500`):

- It still decides `ok` on `status.loggedIn` (`:2489`), so the `ok` fakes that never set `state` keep passing.
- On a fail it words the title by `state`:
  - `signed-out`: "is signed out", as today.
  - `did-not-start`, or anything unrecognised: "does not start".
  - `not-installed`: "is not installed".
- The detail's opening clause, `${agent} reports ${status.detail}`, stays for every state.
- The "Sign in, or name a runtime …" remedy (`:2497`) takes `remedyFor(state)` in place of "Sign in".
- The trailing "If you are signed in yourself … see runtime: signed in" belongs to the signed-out state only. Drop it for the other two: it is the sign-in advice the ticket is removing.

The steps variant's title override at `doctor.ts:2661-2663` ("which is signed out") needs the state too. The simplest route is a small `titleFor(state)` that both titles share, with the override using its phrase in place of the fixed "is signed out".
