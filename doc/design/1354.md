Records a merge back whose push landed even when the PR has been closed or merged by the time it is recorded, and stops `covers` storing guessed counts.

## Where it goes

Three files. No new event, port or reconciliation path.

- `packages/domain/src/pr.ts`: the guard in `mergedBackTransition` (`:556`), and how `BranchSynced` writes `covers` (`:271-280`).
- `packages/project/src/pr.ts`: `recordPrMergedBack` (`:253-260`) answers what happened, not nothing.
- `packages/conductor/src/pr-sync.ts`: both places that record a pushed merge back read that answer — the clean one at `:513-521` and the resolved one at `:620-627`.

## 1. The transition

Today it reads `if (state.status !== 'in-review') return null` (`pr.ts:556`). The new rule is: allowed when `status` is `in-review`, `merged` or `closed` **and** `merged.prHead === state.lastPushed`. The once-per-head line at `:558` stays as it is.

"Never reached review" needs no flag of its own:
- `requested`, `in-progress`, `waiting` and `refused` stay `null`.
- A merge back only pushes after reading `in-review` with `lastPushed === prHead`, twice: at the start of `mergePrBack` (`:323`) and again inside the lane turn (`:481`).
- So a `closed` or `merged` PR whose `lastPushed` is that head has been in review on it.
- `PrClosed` (`:323-326`) and `PrMerged` leave `lastPushed` alone, so the head comparison still means something after the PR ends.

The reducer needs no change. `case 'PrMergedBack'` (`:291-301`) never looked at `status`. For a closed PR it fills `mergedBackTickets`, which the draft reads through `pr.status === 'closed'` (`packages/project/src/pr.ts:395-396`).

**Do not change `mergeBackFailedTransition`** (`:567`, also `in-review` only). A failure recorded on an ended PR would not be read by `mergeBackOwed` (step 3) or by the draft.

## 2. The answer, read as three outcomes

`transitionPr` already passes `(state, appended)` to its `answer` callback (`packages/project/src/pr.ts:97-108`). Make `recordPrMergedBack` return one of:
- `'recorded'` when it appended;
- `'already'` when `state.mergeBack?.prHead === prHead && state.mergeBack.outcome === 'merged'`;
- `'refused'` otherwise.

Every other `record*` keeps `(_s, appended) => appended`.

Both callers in `pr-sync.ts` currently drop the success value. Change them so that:
- `'recorded'` and `'already'` are done.
- `'refused'` is logged with the ticket's wording: *"pr N merge back pushed <merge>; the PR has no record of <head> (status <s>, last pushed <lastPushed>)"*. Then it calls `failed('unknown', …)`.
  - That call appends only while the PR is `in-review`. Then `mergeBackOwed` sees `why: 'unknown'` and looks again (`:289-297`).
  - For any other status it appends nothing and the log line is the whole record. That is intended, not a gap to fill.

Splitting `'already'` from `'refused'` is what keeps the ticket's "already recorded, or no such head" log line from becoming a guess.

## 3. `mergeBackOwed` stays `in-review` only — the ticket's restart edge is narrower than it says

The ticket's *"a process restarting halfway … now whatever the PR's status"* holds for the **transition**, not for the lost-record search:
- The search runs only inside `mergePrBack`.
- `mergePrBack` runs only when `mergeBackOwed` is true (`:290`: `state.status !== 'in-review' … return false`).
- `servePendingPrs` serves an ended PR only through that same predicate (`packages/conductor/src/pr.ts:714-720`).

Widening `mergeBackOwed` to ended PRs would not just search. It would run a whole merge back, so a closed PR's head would be merged and pushed into `branch.personal` when it had never been merged back at all. That is a new path, and the Watch-out row and Out of scope forbid it.

So the case *the push landed, the process died before the append, and the PR then closed* stays unrecorded. That is the "another interleaving" which Out of scope gives up. Say so in a comment at the transition, not in new code.

## 4. `covers` holds only exact counts

Change only `BranchSynced` (`pr.ts:271-280`). Today `held` is `Math.max(heldAt(target), heldAt(lastPushed))`, and `heldAt`'s floor fallback (`:166-170`) gets written back as if it were exact. The new rule:
- Look at both candidates, `state.target` and `state.lastPushed`, whichever are non-null.
- If every one of them has an entry in `state.covers`, write `covers[d.head] = state.covers[d.head] ?? max(those entries)`.
- Otherwise leave `covers` exactly as it was. If `d.head` already had a count, it keeps it.

Requiring every candidate is a decision, chosen over "the newer one". The comment at `:270` says the sync starts from whichever is later, but the reducer cannot tell which is later. With both required, an unknown count can only cost one ancestry check per ticket in `closeMergedTickets`; it never closes a ticket without proof.

Leave `heldAt` as it is; it is the floor used when reading. The other two writers also stay:
- `PrInProgress` (`:205`) writes the count the freeze or restart names.
- `PrFixLanded` (`:227`) writes the landing's own ticket list.

Both are counts the event states, not guesses.

Trace of the ticket's reducer case:
1. The freeze sets `A=1`.
2. `PrFixLanded` sets `B=2`.
3. `PrHeadAdopted(C)` sets `lastPushed = target = C` (`:357`).
4. `PrInProgress` sets `target = A`.
5. `BranchSynced(C)`: `C` has no count, so `covers[C]` stays unset.
6. `PrMerged(C)`: `mergedExact` is false (`:309`), and `closeMergedTickets` proves ticket 2 by ancestry.

The merge back's `heldAt(prHead)` (`:295`) becomes a floor in the same way. Under-counting `mergedBackTickets` leaves a ticket out of a draft. Over-counting would put code that is not on `branch.personal` into one. The floor is the safe side.

## Edges the ticket leaves open, decided

- **Two passes at once**: unchanged. Both record points sit inside `branch.personal`'s lane turn. The stream's version check (`store.append(…, state.version, …)` at `packages/project/src/pr.ts:105`) plus `withOneRetry` means a `PrClosed` racing the append is re-read, and the widened guard accepts it.
- **The cost to later tickets**: `recordPrMergedBack`'s return type changes. Any test asserting `true`/`false` from it moves to the three strings. No baseline moves: the new code is `Effect.gen`, with no `async` and no `Effect.run*`.
