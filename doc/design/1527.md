## 2. The decision that keeps every caller and test unedited: the asker gets the question with `ctx` already bound

Today all four askers hand the descriptor's validator straight to `questionEffect` as a one-argument function:
- `validate: d.question.validate` at `apps/cli/src/claude-token.ts:216` and `apps/cli/src/github-auth.ts:66`;
- the same line in `apps/cli/src/machine-askers.ts` `storeAsker` (`:215`) and `ceilingAsker` (`:233`).

The ticket gives `validate` a `ctx` argument. If `Decided.question` stayed the raw descriptor, all four lines would fail to typecheck, because a two-parameter function is not assignable to a one-parameter slot.

So `Decided<C>` does not hand out the descriptor:

```ts
/** What an asker sees of a question: ctx already applied, so nothing here takes it. */
export interface AskedQuestion {
  id: string; name: string; flag: string
  why?: readonly string[]; show?: (value: string) => string
  validate: (answer: string) => Effect.Effect<string | null, unknown>   // = (a) => q.validate(a, ctx)
}
export interface Decided<C> {
  question: AskedQuestion; ctx: C
  default: string | null; inForce: InForce; kept: string; startOver?: string; why: readonly string[]
}
export type Asker<C = unknown> = (d: Decided<C>) => Effect.Effect<AskerAnswer, unknown>
export interface SetupInput<C = unknown> { …; askers: Readonly<Record<string, Asker<C>>> }
```

The asker still "receives `ctx`", through `d.ctx`.

**Why this works:**
- `AskedQuestion` does not mention `C`, so `C` appears in `Decided<C>` only as data.
- That makes an `Asker<unknown>` assignable to an `Asker<RunContext>`.
- So the bare `Asker` and `SetupInput` used today keep compiling unchanged:
  - `apps/cli/src/machine-askers.ts:103`, `:108`, `:197`, `:220` and `:236`;
  - `machine-list.test.ts:44`.

**Make the runner infer `C` from the list alone.** Write the parameter as `input: SetupInput<NoInfer<C>>` (TypeScript 5.9, root `package.json:43`). Otherwise the test's `SetupInput<unknown>` competes with the list's `RunContext` during inference.

**`SetupQuestion<C>` has no default.** A question always knows its context. This costs exactly two type-only edits outside `packages/setup`, both in `apps/cli/src/machine-askers.ts`: `list: readonly SetupQuestion[]` at `:102` and at `:270` becomes `SetupQuestion<RunContext>`. No other line outside `packages/setup` changes. If the build shows another site, that is a bare `SetupQuestion` this note missed. Parameterise it the same way, and do not add a default.

## 3. `ctx` stays optional, but only for a context whose fields are all optional

Several calls omit `ctx` today and must keep working:
- `apps/cli/src/init.ts:474`;
- `apps/cli/src/machine-askers.ts:290`;
- `machine-list.test.ts:55`, `:173`, `:243`, `:246`, `:255`.

The current default `ctx: RunContext = { draft: null }` (`machine-list.ts:152`) belongs to the machine list, and a generic runner cannot invent a `C`. So:

```ts
export function runSetupList<C extends object>(
  list: readonly SetupQuestion<C>[],
  input: SetupInput<NoInfer<C>>,
  ...[ctx]: {} extends C ? [ctx?: C] : [ctx: C]
): Effect.Effect<ListResult<C>, unknown>          // at runtime: ctx ?? ({} as C)
```

**`RunContext` becomes `{ draft?: Recipe | null }`.** The token's `needed` must then read `ctx.draft ?? null`.

**This one is a trap.** `machine-list.ts:571` reads `if (ctx.draft !== null)`, which is true for `undefined`. Without the `?? null` the token would warn with no draft, and would put `undefined` into `[...recipes, ctx.draft]` at `:575`. `machine-list.test.ts:175` (`none.entries` toEqual `[]`) and `:179` pin this behaviour.

**#1529's context gets the opposite treatment.** Its fields are required, so the type demands its `ctx`.

## 4. The descriptor

There is one interface. Only fields the runner reads go on it.

| field | signature | note |
|---|---|---|
| `fromFlags?` | `(flags, ctx) => string \| null \| {refused}` | absent = null |
| `inForce?` | `(ctx) => Effect<InForce>` | absent = `null` (a confirm or switch has none) |
| `systemDefault?` | `(ctx, mode) => Effect<string \| null>` | absent = null; `mode` below |
| `validate?` | `(answer, ctx) => Effect<string \| null>` | absent accepts |
| `write` | `(answer, inForce, ctx) => Effect<WriteResult \| {refused: string}>` | `ctx` goes **last**, so the machine's writers stay `(answer, inForce)` unedited |
| `needed?` | unchanged: `(ctx) => Effect<boolean>` | the token only (`machine-list.ts:80`) |
| `applies?` | `(ctx) => boolean` | pure |
| `fixed?` | `(ctx, flag: string \| null) => {answer} \| {refused} \| null` | pure; **null = not fixed this run** |
| `derive?` | `(ctx) => string` | pure |
| `confirm?` | `{ declined: string }` | not `true`: a confirmation without its refusal words cannot be written |
| `defaultsSwitch?` | `true` | |

**What each field means:**
- **`applies`, `fixed` and `derive` are pure functions of `ctx`**, and `fixed` also gets the flag. Anything they need was read by an earlier entry's `write` into `ctx`. That keeps the read failures (*a failed read is not an absent value*, `c6526de0f`) where they already are: in `inForce`, `systemDefault`, `validate` and `write`, each of which stops the walk on failure as `yield*` does today.
- **`fixed` returns null where nothing is fixed.** Local projects are fixed to `db` and GitHub projects are not, so one descriptor needs both answers. It is given the flag because 1523 §1 says *"a differing flag is refused by the descriptor's own text"*.
- **`mode` is `{ defaults: boolean; interactive: boolean }`, the runner's current view.** `defaults` includes a switch already answered `yes`. The trial's default is `no` whenever the defaults are on or there is no terminal (1523 §1, `recipe-flow.ts:621-624`, #436). Without `mode` no descriptor could know the switch had fired. The machine descriptors ignore it.

**The machine's descriptors.** `inForce: Effect.sync(…)` and `systemDefault: Effect.succeed(…)` (`machine-list.ts` `:393`, `:407`, `:466`, `:514`, `:520`, `:578`, `:586` in the file) become `() => …`. Nothing else in the four of them changes.

**`Entry` gains `applies: boolean`.** It is false only for an entry whose `applies` said no. Every machine test reads entries with `toMatchObject` or `toEqual([])` (`machine-list.test.ts:67-302`), so the extra key breaks none of them.

## 5. The walk, per entry, in this order

The order is the design. Each step either moves on or ends the entry.

1. **`needed`.** If it says no: push to `deferred`, record **no entry**, continue. This stays separate from `applies` (1523 §1). Folding the two together breaks `machine-list.test.ts:130` and `:175`, which expect `entries` to be `[]`.
2. **`fromFlags(flags, ctx)`.** A `{refused}` stops the walk. This runs **before** `applies`. The Edges line says a flag on a non-applying question is *"the descriptor's own `fromFlags`"* to refuse (`--reviewer-model` beside `--reviewer none`, `apps/cli/src/agents.ts:327-331`). That only works if the runner calls it.
3. **`applies(ctx)` false.** Record `{ applies: false, asked: false, wrote: false, after: null, before: null }`, drop any flag value without a word, and continue.
4. **`derive(ctx)`.**
   - Write the derived answer.
   - Record `asked: false`, and never call an asker.
   - A flag value is ignored. 0125 §9 says a derived entry is *"never reported as a question the person skipped"*.
5. **`fixed(ctx, flag)`.**
   - A `{refused}` stops the walk.
   - An `{answer}` is validated, then written with `asked: false`.
   - Null falls through to the ordinary path.
6. **`inForce(ctx)`.** The environment branch and the fatal-fault branch stay exactly as at `machine-list.ts:164-188`.
7. **Choose the answer.** `defaults` here is the runner's local `let defaults = input.defaults`, not `input.defaults` itself.

   | case | `defaults` on | no terminal | otherwise |
   |---|---|---|---|
   | a flag | the flag wins, as today; it is validated (`:202-205`) | same | same |
   | `confirm` | `yes` | refused, naming `--defaults` (below) | the asker asks; `no` is refused with `confirm.declined` |
   | `defaultsSwitch` | `yes` | record `{asked: false, wrote: false, after: null}` and continue without calling `write` (#433, `recipe-flow.ts:510-515`) | the asker asks |
   | ordinary | the fallback, refused naming `q.flag` where it is null (`:209-216`) | same | the asker, as today (`:217-230`) |

   The confirm refusal for want of a terminal uses the same template as `:211`, with `--defaults` where `q.flag` would be: `` `${q.name} needs an answer: pass --defaults. ${kept}` ``.

   An asker's `{refused}`, which is a Ctrl+C or a cancel, stops the walk for every kind of entry, the switch included.
8. **`write(answer, inForce, ctx)`.** A `{refused}` stops the walk and pushes no entry, because nothing was written. Otherwise push the entry as today (`:233-241`).
9. **The switch.** Where this was the switch entry and the answer is `yes`, set `defaults = true` for every later entry.

**The runner itself writes nothing to `ctx`.** Every change is a descriptor's `write`, which is what the Fix calls *"one `WriteResult` shape for both lists"*.

## 6. `packages/setup/unit/setup-list.test.ts`

Use a fake list over `type Ctx = { log: string[]; login?: string }`.
- Every `write` appends its id to `ctx.log`.
- Each asker is either a recorder or `() => Effect.die('asked')`. That die is how `machine-list.test.ts:173` already proves an asker was not called.

The Done-when list already names each case. Three are easy to under-test:
- **`applies` false.** Assert one entry with `applies: false`, no asker called, and no refusal, *with* the flag for that question passed. Also add the step 2 case: a non-applying descriptor whose `fromFlags` refuses stops the walk.
- **The switch answered `yes`.** Assert that the later entry is unasked, and that its `systemDefault` saw `mode.defaults === true`.
- **`ctx` carries an answer forward.** Entry A's `write` sets `ctx.login`. Entry B's `systemDefault(ctx)` returns `` `${ctx.login}/studio` ``. Assert B's `after`.

Also add one `fixed` case that returns null and falls through to the asker. It is the case #1529 relies on for GitHub projects.

**A field this ticket adds and no test exercises is a review finding** (the ticket's Edges), and that includes `mode`.
