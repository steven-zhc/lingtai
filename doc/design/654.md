# Design: #654, a granted round that crashes with the head unmoved puts its wait back on offer

## Where the decision is made

The `standing` field is added in **`conduct.ts`, inside `waitReasonFor`** (`packages/conductor/src/conduct.ts:4198-4205`). Do not add it in `pass-next.ts`. `interruptedAs` (`packages/domain/src/pass-next.ts:333-349`) is pure. It is handed a `run` and nothing else, so it cannot know which wait the round resumed or where the head is. `waitReasonFor` is already where the reason gets patched with things only the conductor knows. Its own comment says so: *"The `run` every `WaitReason` carries, patched on here — the one fact only `conduct.ts` holds and `nextOf`/`routeNext` cannot"* (`:4161-4168`).

Put the rule in a pure function and unit-test that function. Don't test it through a whole pass. Something like `standingFor({ reason, continuation, resumed, head, wip, notPushed })`, which returns `{ waitId, reason } | null`. It answers non-null only when all of these hold:

- `reason._tag === 'AgentCrashed'`. That reason only carries `crash | timeout | aborted` (`wait.ts:168`), so the cause filter comes with the tag.
- The round was granted: `continuation?.grant` is set (`conduct.ts:1050-1058`). An approved non-grant continuation has `resumedWaitId` too, but it is not a granted round, so it must not count.
- `wip === null`. `wip` is the WIP that work kept uncommitted becomes (`conduct.ts:1722`). Once it exists, `head` is the WIP sha (`:1996-1998`).
- `notPushed === null`, meaning `runRef.unpushed` is absent (`:4169-4174`).
- The worktree `head` equals `continuation.onSha`.

**Compare against `head`, not against `cutBase`, `headSha` or `published`.** On a continuation, `cutBase` is `continuation.diffBaseSha` (`:1970`), which is the admit base and not the granted sha. `headSha` is `headReached(pass.steps)`, which the code itself warns is *"the commit the worktree was cut at on every ending whose step moved the tree without reporting it"* (`:4126-4131`). `published` is per-claim and starts out `null` (`:1656`). The `head` that `publishWhatIsCommitted` reads with `rev-parse HEAD` (`:1990-2017`) is the only value that means "the worktree is where the person last decided". It is local to that closure, so hoist it into a `let` beside `wip`.

The resumed wait comes from `waitsOf(before).find(w => w.waitId === continuation.resumedWaitId)`, the same read `:1018` already makes.

## The schema: `standing.reason` is never itself `AgentCrashed`

`standing.reason` is a `WaitReason` nested inside a `WaitReason` variant. Don't use `z.lazy`. Declare a `StandingReason` discriminated union of the **eleven variants other than `AgentCrashed`**, and declare it before `AgentCrashed`. That means moving `SetupRefused` and `AnswerUnreadable` above it (`wait.ts:172-189`). The field is `standing: z.object({ waitId: WaitId, reason: StandingReason }).optional()`.

That leaves one case to decide: **a granted round from a standing crash wait that crashes again with the head unmoved.** With this change, `grantCriterion` answers for a standing crash wait, so that can happen. The conductor must **flatten** it: if the resumed wait is itself `AgentCrashed{standing}`, carry that wait's `standing` forward unchanged, with the original `waitId` and the original reason. It must never point at the crash wait. That keeps three things true:

- the type stays non-recursive;
- the recommendation keeps reading the triage the person actually saw;
- the waiver stays exactly the original wait's.

Unit-test this case too. Feed `standingFor` a resumed `AgentCrashed{standing}` and expect the same `standing` back.

## What delegates to `standing.reason`

`standing.reason` should answer in every one of these, and nowhere else:

- **`tableResolutions` / `allowedResolutions`** (`wait.ts:258`, `:381`). For a standing crash wait the answer is `standing.reason`'s row plus `Requeue` and `Close`, deduplicated. The `unpushed` filter still applies, and it reads `reason.run`, which is the crash wait's own run. That run is never unpushed when `standing` is set, so the result agrees anyway.
- **`grantCriterion`** (`wait.ts:327`). `conduct.ts:1050-1058` calls this to build a grant's brief, and `allowedResolutions` uses it to offer `GrantFixRound`. Delegating here covers both, and the "one function for both the offer and the brief" claim in its doc comment stays true.
- **`continuationOf`** (`wait.ts:420`). Return `continuationOf(standing.reason, runOutcomes)`. This is what makes *"an `Approve` waives exactly what the standing wait's `Approve` waived"* true by construction. `approve.ts:179` and `:251` both go through this function. So does `waivedActionsAt` (`wait.ts:490`), which filters by `reason.run.runId`, and a continuation keeps its runId (`conduct.ts:1088-1091`), so both waits are on the same run. The `CheckRefused` fallback that reads `runOutcomes` gets the same run either way.
- **`defaultResolution`** (`wait.ts:546`). Delegate here too. A standing `ReviewFindings` should prefill nothing (`null`), not `AgentCrashed`'s `Requeue`. Otherwise an untriaged standing wait would draw *throw it away* first, which is the outcome this ticket exists to prevent.

`recommendedResolution`'s signature stays the same. *Which triage it reads* is the caller's job, because callers already pass the `TriageStatus` in.

## Which triage the recommendation reads

This is where the ticket's *"#637 would have been approvable on the board"* has to be cut down to size.

- **The task page** already reads the stream: `triageFactsOf(own, waitId)` (`apps/board/src/lib/task.ts:1749`, `packages/domain/src/read-model.ts:108`). For a standing crash wait, build its status as `triageStatus(standing.reason, triageFactsOf(own, standing.waitId), …)`. Then `standing.tsx:536-538` draws the standing wait's advice, and **Approve and Grant appear on the page**. That is the real fix for #637.
- **The board card's one-click move** (`apps/board/src/lib/board.ts:584-600`) reads `card.triage`. That comes from the `task_view` projection, which stores triage only for the current wait, in SQL that exists twice (`packages/projector/src/postgres.ts:112`, `sqlite.ts:309`, `task-view.ts:376-379`, `:588-601`). Getting the standing wait's triage there means changing both store twins. Those are only exercised by the integration half (*"Neither … may go through a pooler"*; 0060), which nothing in a pass can run. **So: `moveOf` returns `null` for a wait whose reason has `standing`.** The card draws no one-click button, and the person decides on the page. Both pages offer `Approve`, because `allowedResolutions` is shared, so the page and the server action still agree (`standing.tsx:3-5`'s comment). Carrying the standing wait's triage into the projection is a follow-up ticket, not this one.
- **`grantedAdviceOf(before, approvedWaitId)`** (`conduct.ts:1046-1047`, `fix.ts:579`). When a person grants a round from a standing crash wait, the advice the round gets should be the standing wait's. Look it up under `standing.waitId` when the resumed reason has one. Otherwise #643's *"a granted round carries the standing wait's advice"* is lost after the first crash.

Triage is still dispatched for the crash wait as it is today, and still recorded, as the ticket's Edges list says. Nothing in this change reads that triage for the recommendation.

## The one sentence on the wait

The crash wait's own `detail` already reaches `describeWaitLines` / `waitWords`. Add one clause to the `AgentCrashed` line when `standing` is set. It should say the round broke nothing and the earlier offer stands at `onSha`. Keep it one line, written in `wait-words.ts` so the card, the page and `lingtai status` say the same thing. Don't add a second block.

## Old events and the ADR

`standing` is optional, and the variant is read straight off `WaitStarted.reason` (`wait.ts:3-7`: *"verbatim, with no translation layer"*). So an old event parses as today and needs no upcast. The projection stores `wait_reason` as JSON, and nothing in its fold changes, so no rebuild is needed.

`doc/decisions/0118-a-hold-explains-itself.md` is in `doc/decisions/`. That makes it a topic ADR, edited in place, not an archived one. Add the line to its resolution table.

## Unit tests that stand in

All of these run in `pnpm test`; none need `test:integration`.

- `standingFor`: head unmoved / one new commit / `wip` set / `notPushed` set / not granted / resumed wait already standing (flattened).
- `wait.test.ts`: `allowedResolutions` and `continuationOf` for `AgentCrashed{standing: ReviewFindings}`. `continuationOf` must deep-equal what the standing reason alone returns, including the `waive`. Also check `defaultResolution` through `recommendedResolution`.
- A `WaitReason.parse` of an `AgentCrashed` with no `standing`, and of one whose `standing.reason` is `AgentCrashed`. The second must be refused.
- `board.ts`'s `moveOf` returns `null` when `standing` is set.
