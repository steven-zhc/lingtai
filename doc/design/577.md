## The decisions that aren't obvious from the ticket

### 1. The wall starts at the top of `waitTriage`, not at the first runtime round

Today the only deadline is `const deadline = deps.now() + call.wallMs` (`:618`). It is computed after `gatherEvidence` and after `prepare`/`prepareCheckout`, so none of the reads count against the wall.

There is also a read before `TriageStarted`: `deps.mirror.conflictedPathsAt` (`:541`), for a `MergeConflict` proposal. Start the clock before it.

That read needs no new failure path. Its `catch` already turns a rejection into `mechanical = { _tag: 'TriageFailed', … }` (`:556-558`). That makes `by` `Mechanical`, `TriageStarted` is appended, and `WaitTriaged` follows. So a wall that fires there still produces a `TriageStarted`/`WaitTriaged` pair. Make the `why` `'timeout'` rather than the abort error's message.

Compute `deadline` from the same start, so the per-round `wallLeft` (`:686`) and the signal agree.

### 2. Make the wall from a timer you clear, not `AbortSignal.timeout`

Use `new AbortController()` with `setTimeout(() => wall.abort(), call.wallMs)`, call `.unref()` on the timer, and clear it in a `finally` around the whole body.

- `AbortSignal.timeout` is not driven by vitest's fake timers, so the unit test would need a real wait.
- An uncleared timer keeps the daemon's event loop alive past an attempt that already finished.

`parseDuration` accepts `ms` (`packages/recipe/src/duration.ts:14`), so a test can also just write `wall: '20ms'`.

Combine it with the caller's signal using `AbortSignal.any([wall.signal, request.signal].filter(Boolean))`. Keep the two separate wherever the outcome is named:

- **`'timeout'`** is the wall.
- **`'aborted'`** is `request.signal`, a person or the conductor cancelling.

The pre-append line `if (request.signal?.aborted) final = { … why: 'aborted' }` (`:885`) must keep testing **`request.signal` only**. Testing the combined signal would overwrite a real `TriageAdvised` that finished a moment before the wall with a failure.

### 3. Pass the signal *and* race the await: the race is what meets the Done-when

The Done-when asks for *"a fake read that never resolves"*, and a fake that ignores its signal never resolves however it is aborted. So every read awaited between the start and the last runtime round goes through one small helper. The helper races the promise against the combined signal and rejects when the signal fires. The reads are:

- `deps.issue`
- `deps.base`
- each `deps.mirror.*` call in `gatherEvidence` (`:427-445`)
- `conflictedPathsAt`
- `serve`'s `readAt` (`:626`)
- `deps.prepare`
- `deps.prepareCheckout`

Also add an optional `signal` to each port. Production then stops the work rather than just stopping waiting for it:

- **`git()`** (`packages/repo/src/git.ts`): `execFile` takes `signal` and kills the child, so add `signal?: AbortSignal` to `GitRunOptions` and pass it through. Each `mirror.ts` reader gets an optional `signal` that it hands to `git`. All five are listed in `TriagePorts.mirror` (`:353-359`).
- **`client.getIssue`** (`packages/github/src/client.ts:527`): there is no signal on this path today. Racing it in `waitTriage` is enough for this ticket. Threading a signal into `request` is optional, and if you skip it, say so in the commit body.

Wherever a race is lost, `gatherEvidence` already maps a rejection to `null` or `ticketProblem`. That is wrong for an abort: a wall that fired must not go on to dispatch a runtime on empty evidence.

- Check the combined signal after `gatherEvidence`, before dispatch. The round loop already checks it at `:679`, but it checks `request.signal`; switch that check to the combined signal.
- Give the timeout result the wall's `why`.

**`prepareCheckout` needs one more line.** If its race is lost, the checkout can still materialise later. Hang `.then((c) => c.cleanup())` off the losing promise so the directory isn't left behind.

### 4. Don't race the runtime round or the appends

- **The runtime round.** `runtime.run` already takes `signal`. The contract is *"Killed when this aborts, producing a `timeout` failure rather than silence"* (`packages/agent/src/runtime.ts:136`), and it resolves with turns and cost. Racing it would set `threw = true` (`:713-724`), and `spend()` would never record a call that was billed. That is the `RunSpent` the ticket's Want asks for. Give it the combined signal and nothing else.
- **The `TriageStarted`, `RunSpent` and `WaitTriaged` appends and their store reads.** These must run after the abort; that is the point of them.
- **`deps.store.read(runId)` in `gatherEvidence`** (`:420`). It's a store read, not a mirror read, so leave it unraced. If the store hangs, nothing could be recorded anyway.

## Tests (unit, `apps/cli/unit/triage.test.ts`)

- **The Done-when test:** a mirror `refSha` or `issue` returns `new Promise(() => {})`, with a short wall or fake timers. Assert three things:
  - `waitTriage` resolves with `TriageFailed`/`'timeout'`;
  - the stream reads `['TriageStarted', 'WaitTriaged']`, with no `RunSpent` because no round was dispatched;
  - the stub runtime received zero requests.
- **The queue half:** call `enqueueTriage` twice. The first job is a `waitTriage` whose read never returns, the second records that it ran. Assert that the second runs once the first job's wall fires. Without this test, nothing checks the "and the next triage starts" clause.
- **The same shape for `conflictedPathsAt`:** the stream reads `TriageStarted` with `by: Mechanical`, then `WaitTriaged`.
- **The existing test at `:1009`** asserts `requests[0]?.signal).toBe(controller.signal)`. With a combined signal that identity no longer holds. Change it to assert that the runtime's signal is aborted after `controller.abort()`, and keep the `'aborted'` assertion so the two names stay distinct.

`pnpm typecheck` and `pnpm test` cover all of this. Passing `signal` into `git()` is only exercised against a real `git` in `packages/repo/integration`, and nothing here needs that. The unit claim that stands in for it is that `waitTriage` returns at the wall when a port ignores its signal.

## What would settle it in the log

For an attempt the wall stopped, the ticket stream should carry a `TriageStarted{waitId, attempt}`, then a `WaitTriaged` with the same `attempt` and `result: { _tag: 'TriageFailed', why: 'timeout' }`. The time between their `recordedAt` values should be no more than `triage.limits.wall` plus the time the appends take. Any `RunSpent{for: {_tag: 'Triage', waitId}}` must come from a round that was actually dispatched. The next queued wait's `TriageStarted` coming after that `WaitTriaged` is what shows the queue moved on.
