# #1106 design note: following a run log as a Stream and closing one as an Effect

The prerequisites have landed in this worktree, so you start from the state the ticket describes. `closeRunLogEffect` is at `packages/agent/src/run-log.ts:246`, `openRunLogEffect` at `:168`, and #1082's finalizer at `packages/conductor/src/conduct.ts:1838-1848`. CLI-16a's lifts are at `apps/cli/src/discuss.ts:399-401` and `:471`. The baseline reads `"apps/cli": { "async": 116, "run": 1 }` and `"packages/agent": { "async": 1, "run": 0 }`. The ticket cites line numbers from before those changes landed; use the ones here.

Effect is **4.1.2** (`packages/agent/node_modules/effect/package.json`). No file in `packages/*/src` or `apps/*/src` uses `Stream.unwrap`, `Stream.paginate`, `Stream.toAsyncIterable` or `Stream.interruptWhen` yet, so there is no house pattern to copy. The v4 names exist and are below.

## 1. `followRunLogStream`: what the generator's control flow turns into

Today's body (`run-log.ts:347-411`) does four things that a Stream has to express differently:

- **The handle is a resource.** It is opened at `:351` and closed in a `finally` at `:408-410`. Write the Stream as `Stream.unwrap(Effect.gen(…))`. Inside, open with `Effect.acquireRelease`, and make the release `handle.close()` with its error swallowed. In v4, `Stream.unwrap` takes an Effect that needs `Scope` and removes `Scope` from the requirements (`Stream.d.ts:1436`: `Exclude<R, Scope.Scope>`). The handle therefore lives as long as the stream, and it closes on an ending, on interruption, and when the board's `for await` breaks. That last case is where the `finally` mattered.
- **A failed open is an ending, not an error.** A failed `open` yields `{ ended: 'removed' }` and returns (`:352-358`). In the Effect version, a failed acquire becomes `Stream.make({ ended: 'removed' })`. Do the catch before the `acquireRelease`, so that no release is registered for a handle that never opened.
- **The poll loop is a state machine.** The state is `{ pending: string, done: boolean }`; the decoder and the 64 KiB buffer are per-stream values that do not change. Each step does four things:
  1. Drain all available reads into `pending`.
  2. Split off whole lines.
  3. Emit them, stopping after the first line for which `runLogEnded` says it ended, and emit that ending.
  4. Otherwise stat the path against `own.ino`/`own.dev`, which still ends with `removed` (#132, `:384-392`), and then `Effect.sleep(pollMs)`.

  `Stream.paginate` with a chunk of outputs per step fits this. **Keep the order "read first, then ask"** (`:384-388`): the last line of a landed run is only safe because the drain comes before the stat.
- **The `signal` is interruption.** Add `Stream.interruptWhen` on an `Effect.callback` that resumes on `abort`, and resumes at once if `signal.aborted` is already true. That replaces both the `aborted` check at `:368` and `pause` (`:414+`). `Effect.sleep` is interruptible, so a reader who leaves does not wait out a poll. When there is no signal, nothing is added. **An abort ends the stream with no ending element**, which is today's contract (`:315`: *"Ends the follow without an ending, which is the truth"*). `attach` uses that to tell *detached* apart from *ended*. Delete `pause` with the generator.

**Error channel (decided).** A `read` on an open handle that fails escapes the generator today. The board's `catch` at `route.ts:91-92` turns it into `event: trouble`. Keep that error visible rather than turning it into `removed`, because `removed` claims the run landed, and that would be a lie. Do it with `Effect.tryPromise`, and give the failure a tagged error such as `RunLogFollowFailed { path, cause }`. The type is therefore `Stream<RunLogFollowed, RunLogFollowFailed>`, not the ticket's `Stream<RunLogFollowed>`. That deliberately loosens the ticket's signature: a defect (`Effect.promise`) would get past `orFailed` in `cli.ts`, which only catches failures. `Stream.toAsyncIterable` rejects with the failure, so the board's `trouble` still receives it. The `stat` keeps its own `.catch(() => null)`, which correctly means "gone."

## 2. `RunLog.close` becomes an Effect: two traps besides `await`

- **`conduct.ts:1813`, the wrapper.** It becomes `close: (fate) => Effect.suspend(() => opened?.close(fate) ?? Effect.void)`. Use `suspend`, not a direct read of `opened`. A promise read `opened` when `close` was called, and that was also when it ran. An Effect may be built before the open finishes and run after it, and then a direct read would close nothing. The finalizer at `:1846` becomes `return runLog.close(didLand ? 'delete' : 'keep')`, still inside the existing `Effect.suspend`, so the `RUN_LOG_END` note is still written before the close.
- **`packages/conductor/test/one-attempt.ts:944`.** `close: async (fate) => void did.push(\`runLog ${fate}\`)` records the fate when `close` is *called*. It must become `Effect.sync(() => did.push(…))`, which records when the close *runs*. Any test that asserts the order in `did` will then see when the close actually happened. That is the correct order, and a test whose expected order changes was asserting when the Effect was built. `:907`'s `async () => {}` becomes `() => Effect.void`.
- In `NO_RUN_LOG` (`run-log.ts:136`), `close` becomes `() => Effect.void`. In `openRunLogEffect`, `:236` becomes `close: (fate) => closeRunLogEffect(handle, tail, path, fate)`. `tail` must be read when the Effect *runs*, not when `close` is called; the comment at `:258-259` makes the same point about the promise. `tail` is a reassigned `let`, so wrap the call in `Effect.suspend` as well.

## 3. `discuss.ts`

`:399-401` currently is `Effect.promise(() => openRunLog({ path }).catch(() => NO_RUN_LOG).then((trace) => { …beat… }))`. It becomes `openRunLogEffect({ path }).pipe(Effect.catch(() => Effect.succeed(NO_RUN_LOG)), Effect.map((trace) => { …beat… }))`, still as the acquire of the same `acquireRelease`. The comment at `:397-398` depends on that: *"Acquired uninterruptibly and released on every exit"*. The release at `:471` becomes `Effect.sync(() => clearInterval(beat)).pipe(Effect.andThen(trace.close('delete')))`. Import `openRunLogEffect` from `@lingtai/agent` in place of `openRunLog` (`:45`). Rewrite the prose at `:378` and `:391` so it no longer names the deleted functions; the `rg` in *Done when* allows comments, but a comment naming a deleted export misleads the next reader.

## 4. `attach`

- Use `findRunLogEffect` and `listRunLogsEffect` (`packages/conductor/src/run-log.ts:83`, `:113`); they already exist. After this change the board's `route.ts:35` is the only `src` caller of the promise `findRunLog`, which 0101 §7 allows at the board's edge. `listRunLogs` (`:139`) loses its last `src` caller except the re-export at `packages/conductor/src/index.ts:82`. **Leave both promise forms where they are**: removing them is not in the ticket, and their face entries are another row's.
- To print the ending, use `Stream.runForEach` on the follow. Collect what ended into a local variable (or use `Stream.runFold`), and decide *ended* versus *detached* after the run finishes. That is the same test the generator's fall-through makes at `attach.ts:89`, and it works because an abort ends the stream without an ending element (§1). Keep every sentence byte for byte; `apps/cli/integration/attach.test.ts` pins them.
- In `cli.ts:500`, `lift(() => attach(…))` becomes `yield* attach(…)`. The SIGINT `AbortController` at `:495-499` stays exactly as it is. **Do not swap it for fiber interruption**: an interrupted fiber would never print *— detached*, and the integration test drives detach through `signal`.
- The unit test in *Done when* needs a "fake Stream". So that `attach` can be tested without the filesystem (0060 §1), add an optional `follow?: (o: FollowRunLogOptions) => Stream<…>` and `find?` to `AttachOptions`, and default them to the real ones. That is the seam. Otherwise the test has to write a temporary file and becomes integration.

## 5. The unit test for the Stream itself

*A file written in pieces* is the filesystem, and that makes it integration under the CLAUDE.md rule (*"A temporary directory is still the filesystem"*). To keep the split-line and split-UTF-8 claim in `pnpm test`, factor the pure part out: a function that takes `(pending, decoder output)` and returns the whole lines, the new `pending`, and an ending if there is one. Unit-test that with a `StringDecoder` fed a multi-byte character split across two `Buffer`s, and a line split across two chunks. The file-backed run goes into `packages/agent/integration/run-log.test.ts`, which runs after the merge. Say this in the PR, so nobody reads the unit test as proof of the file reads.

## 6. The integration tests nobody runs before the merge

There are about twenty `await x.close(…)` sites, listed in the ticket. All of them still typecheck after the change, and **the one check that runs in the pass is the second `rg` in *Done when*.** Run it before committing, and run `rg -n "\.close\((fate|'keep'|'delete')" packages apps -g '!**/.next/**'`, then read each hit. The ticket's regex needs `await` on the same line, so a site written as `const p = log.close('keep'); …; await p` gets past it.

`openRunLog(` call sites in those tests become `Effect.runPromise(openRunLogEffect(…))`. `followRunLog` in `packages/conductor/integration/run-log.test.ts:58`, `:175` becomes `Stream.runCollect` (or `toAsyncIterable` where the test interleaves writes with reads) over `followRunLogStream`.
