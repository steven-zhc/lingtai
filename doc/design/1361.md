## Design: #1361, the task route's unmeasured stages

### The decision: a stage outside `measure` is a `measure`, because only a `page …` span gets re-parented

The ticket asks for "an exported parent" for work outside `page /task`. Only one kind of span gets one. `OnlyScope` re-parents a board span onto Next's request span only when its name starts with `page ` (`telemetry.ts:131`, `:141`: *"`if (!span.name.startsWith('page ')) return this.inner.onEnd(span)`"*). Any other board span started in the layout keeps its parent, and that parent is a Next render span the exporter drops. The doc on `measure` says what that costs: *"A page that loads outside `measure` has no page span, and its reads export as orphans"* (`timing.ts:57-58`).

So each new layout stage goes through `measure` with a fixed label, the way `/task github` already does (`layout.tsx:255`). Don't use `traced` here, and don't write a new helper:

| Stage | Wraps | Where |
|---|---|---|
| `page /task preflight` | `knowable(taskId)` | `layout.tsx:250` |
| `page /task projects` | `readRegistered()` | `layout.tsx:258`. The existing `.catch(() => [])` stays outside the `measure`, so the stage is marked ERROR before the fallback. |
| `page /task locks` | `pauseSlot(project)` | `layout.tsx:278`, still awaited at the same point in the JSX |

Keep both `notFound()` calls (`:250`, `:259`) outside every `measure`. Otherwise Next's not-found throw would be marked as a failed stage. Don't change the order or concurrency: preflight, then `github` started, then `Promise.all([page /task, page /task projects])`, then `locks`. `measure` also prints a slow line to stderr above 1 s (`timing.ts:79-85`). That is the existing `/task github` behaviour, and the returned values don't change.

The tests have to show these three are roots in a unit run. `measure` has no request span there (`timing.ts:52-54`), so the claim to test is *"the stage is a `page ` span and the reads are its descendants"*. Re-parenting itself is already covered by `telemetry.test.ts`.

### New children are `traced`, never `timed`: the TimingMeta list is pinned

`timed` adds an entry to the `<meta>` list as well as a span. `timing-load-task.test.ts:109` and `:115` assert that list exactly (`['events.task', 'events.task', 'events.control', 'tasks.read', 'events.run', 'spend.read']`). Every span this ticket adds is `traced`/`tracedSync`: *"a span and nothing else … `timed` stays for the fixed few reads a render waits for"* (`timing.ts:143-147`). Those two assertions stay byte-for-byte unchanged, and that is the proof that the coarse spans were kept. Existing `timed` calls inside the new spans still record into the initiating `measure` scope, so nothing moves in the meta list.

### Cached reads: the operation span is inside `cache`, it belongs to whichever render calls it first, and a caller gets at most a `*.wait`

**`locks.ts:98` `readProjectLocks`.** Wrap the body in `traced('locks.read', async (span) => …)`:
- On the `catch` path, call `span.setStatus({ code: SpanStatusCode.ERROR })` with **no `message`** before returning `{ ok: false, problem }`. `traced` only marks a rejection (`timing.ts:152-156`), and this function never rejects.
- When `'problem' in control`, set `span.setAttribute('lingtai.control_failed', true)`. The problem text is never exported. `control.snapshot` is already ERROR for the same failure, because `readControlOnce` rejects inside its own `traced` (`locks.ts:56`).
- In the loop at `:110/:112`, wrap each `run(accountsFor(...))` in `traced('locks.account', …)` with no attributes, one per project in the order the projects were registered. These are sequential siblings, which is the current read order.

**`locks.ts:43` `readRegistered`.** Put `traced('projects.load', () => loadProjects())` inside the `cache`. The home page's caller-side `timed('projects.read', …)` (`page.tsx:739`) stays, with `projects.load` as its child when it initiated the read.

**Who initiates the lock read depends on the state.** For every non-queued task, the layout's `pauseSlot` is the only early caller, so `locks.read` sits under `page /task locks`. For a **queued** task, `loadTaskAnswer` also reads it (`task.ts:2679`) inside `page /task github`. That read starts only after the GitHub issue read returns (`:2660`), so it is a race. Whichever stage gets there first owns the one `locks.read`, and the other's time is a wait. Wrap `task.ts:2679` in `traced('locks.wait', () => readProjectLocks())`. Don't add a wait span in `pauseSlot`: the `page /task locks` stage already is that wait.

The banner's read (`lock-banner.tsx:33`) gets no span. On this route `project` is always set once `ticket !== null`, because `loadTicketBase` always returns it (`task.ts:1880`). So `pauseSlot` always reads before the banner renders, and the banner's call is a hit on an already-settled read.

**`task.ts:2135` `readAttempts`.** Wrap the body in `traced('attempts.read')`. Inside it:
- `tracedSync('attempts.reduce')` covers the reduction at `:2158-2165` plus the plain `standingOf`.
- `traced('attempts.base')` covers the satisfied-only `readProject` at `:2171`.

In `loadTaskAnswer`, wrap the `Promise.all([readAttempts, readConductor])` at `:2666` in `traced('attempts.wait')`. That loader always runs as the second caller beside `loadTask`. `loadTask` itself gets no wait spans.

**Tests must not hard-code the winner of a race.** Use deferred promises to force each order, then assert:
- exactly one `locks.read` (and one `projects.load`, one `control.snapshot`) per simulated render;
- it is parented under the stage that started first;
- the other stage has no copy of it.

### Concurrent Effect reads need the context carried explicitly

`readControl` is `Effect.runPromise` (`packages/daemon/src/control.ts:131`), and so is `accountsFor` through `run` (`locks.ts:40`). #1360 already recorded why `traced` inside an observer hook is wrong once two reads are in flight: *"Effect resumes fibers from one shared dispatcher, so AsyncLocalStorage alone would hand a stage whichever context scheduled the batch"* (`timing.ts:178-180`; `doc/design/1360.md`). `readControlOnce`'s hooks (`locks.ts:59-62`) were only safe because one read was in flight at a time. The Done-when's "two overlapping task renders" breaks that, and so does adding observers to `readConductor`.

- **Control observers.** Write one helper, say `controlObserve(span)` in `locks.ts`. It captures `const ctx = context.active()` synchronously and returns `read: (step, run) => context.with(ctx, () => traced(`control.${step}`, run))`, `reduce` the same way, and `served → span.setAttribute('lingtai.snapshot', …)`. This is `board.ts:1621-1629`'s pattern.
  - Use it in `readControlOnce`.
  - Use it in `readConductor` (`task.ts:2116`). That one is `timed`, which gives no span handle. Take `trace.getActiveSpan()` and `context.active()` right before calling `readControl`, after `await boardWriterOrNone()`.
  - The `.catch(() => emptyControl)` stays, and `timed` has already marked `events.control` ERROR by the time it runs.
- **Accounts.** Pipe `accountsFor(...)` through `Effect.withTracer(boardTracer)` and `Effect.provideService(ApiContext, trace.setSpan(context.active(), span))` inside each `locks.account`, as `board.ts:1065` does. That way the `events.read`/`db.acquire` seam spans (`trace-seams.ts:32-45`) land under the right render. This adds no `Effect.run*`, and the board is outside the ratchet anyway (`effect-ratchet.baseline.json` has no `apps/board` row; 0101 §7: *"The board (`apps/board`) stays `async`"*).
- **What we can't reach.** `readProject`/`loadProjects` live in `@lingtai/project` as promise faces, so the board can't give them a tracer. Parentage tests assert board-owned spans only, and should say so in their names.

### What else to measure, by file

Wrap a step only on the path where it actually runs, so a skipped branch emits no span.

- **`task.ts:1868` `loadTicketBase`:** `traced('ticket.base')`, with a child `ticket.recipe` around `currentRecipe` (`:1876`). Its `.catch(() => null)` marks the child ERROR first.
- **`task.ts:2517-2518`:** put the `traced` *inside* `inFlightFor` and `startEstimateFor`, after their `state !== 'queued'` guards (`:2265`, `:2287`). Name them `task.in-flight` and `task.start-estimate`, with children `report.read` and `spend.day`. They stay sequential, in their current order. Inside these functions, a value the existing `catch` turns into `null` or `{ failure }` marks the span ERROR without a message.
- **Other state-dependent awaits:**
  - the fix-work client build `:2393-2401` → `task.fix-work.client`;
  - the rerun client build `:2426-2434` → `task.rerun.client`;
  - the split reads `:2459-2463` → `task.split`.
  
  Each of these already has `github.ref`/`triage.read`/`mirror.ref` children, which stay as they are.
- **`prompt.ts` `outgoingFor`**, under the existing `next.outgoing` (`task.ts:2688`):
  - `prompt.template` (`:137`);
  - `prompt.project` (`:142`);
  - `prompt.filter` (`:148`), ERROR when `!filter.ok`;
  - `prompt.arms` (`:158-159`), only when `streams.length > 0`, with `prompt.client` around `githubClientFor` nested inside it;
  - `tracedSync('prompt.compose')` around `nextPrompt` through `lineDelta`.
  
  The span is placed inside each `.catch`/`try`, so it ends ERROR before the existing `refused(...)` or `null`. No span carries the path, the body or the refusal text.

### Tests, and the trap in them

React 19's `cache` does not memoize outside a server render. In this tree, react 19.2.8 gives `cache(f)() !== cache(f)()` under plain node, which is why `events.task` appears twice in `timing-load-task.test.ts:109`. A plain unit test therefore can't show "once per actual execution". Mock `react`'s `cache` with a memo kept in an `AsyncLocalStorage<Map>`, and run each simulated render inside `als.run(new Map(), …)`. Two overlapping renders are then two separate maps, which is the real behaviour.

Put the tests in a new `apps/board/unit/task-stage-spans.test.ts`, using `attempt-spans.test.ts:8-33`'s `InMemorySpanExporter` set-up. Mock `node:fs/promises`'s `readFile` for the template. A real file read is the filesystem, so it would make the test integration under 0060 §1. Assert:
- names, parentage and status;
- return values and mock call counts against a no-provider run.

Don't assert source text. `pnpm test` is the whole check. Nothing here needs `pnpm test:integration`, and the Next-build client-graph check doesn't apply: `lock-banner.tsx` is a server module that already imports `locks.ts`.
