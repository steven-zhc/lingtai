# Design note: #1328, refuse a team → solo switch while work is stranded

## Where it goes

One step in `changeRecipe` (`packages/project/src/change.ts:62`), placed after both arms have set `current` and `text` and before `if (written) yield* files.replace(path, text)` (`change.ts:129-130`). In the `{ text, expected }` arm it runs after the stale check (`change.ts:90-95`) and after the resolve (`change.ts:101-125`). So a stale or invalid text is still refused as `stale` or `invalid`, and this check only sees text that would otherwise be written.

## Reading the two modes: parse the text, not a `Recipe`

Neither arm holds a resolved `Recipe` for the *old* file. The `{ changes }` arm resolves nothing at all (`change.ts:76-83`). Do not resolve the old text just to call `modeOf`. Read both texts the way `isTeamSource` already does (`packages/project/src/pr.ts`, *"Whether a recorded recipe text says `mode: team`. Text that does not parse is not team"*):
- Export it, or move it beside the new read.
- old is team = `current !== null && isTeamSource(current)`.
- new is team = `isTeamSource(text)`.
- Only the case old team, new not team goes on to read the log. Every other save returns to the existing path with no extra read. That covers solo → team, same mode, `mode: solo` written over a file with no mode, and `current === null`.

`branch.personal` can also be read straight from the old text. A team recipe must write it out: `resolve.ts:503-504` refuses *"`mode: team` lands on a personal branch; write `branch.personal`, or use `mode: solo`"*. So the old text always names it, and no default needs reconstructing. If the old text says `team` but has no string `branch.personal`, fall back to its `branch.main`. That is the same fallback `readPrDraft` uses (`recipe.branch.personal ?? recipe.branch.main`).

## Reuse #1316's reads by splitting `readPrDraft`, not copying it

`readPrDraft(project, recipe, candidates, store)` (`packages/project/src/pr.ts`) needs a `Recipe` only for:
- `modeOf(recipe) !== 'team'`, which returns `[]`;
- the `personal` branch name.

Split it:
- `readDraftOn(project, personal, candidates, store)` takes the body from `const since = teamSince(...)` to the sort.
- `readPrDraft` keeps its signature and becomes the mode check plus `readDraftOn(project, recipe.branch.personal ?? recipe.branch.main, …)`.
- The existing `packages/project/unit/pr.test.ts` cases keep passing unchanged. That is the check that the split kept one implementation.

The draft already covers the ticket's traps, and nothing needs adding:
- `state.landed` survives `TicketClosed` (`packages/domain/src/ticket.ts:300-301`, *"kept after a `TicketClosed` replaces `lifecycle`"*; set at `:824`).
- Landings before the project last became team are cut by `teamSince` (`packages/domain/src/pr.ts:356-366`), which is the `lingtai-base` solo-history edge.
- PRs that are `refused` or `closed` hold nothing, so a closed PR's tickets come back into the draft. PRs that are `merged` still hold their tickets, so those are not in the draft.

**Open PR**: use `listPrs(project, store)` (`pr.ts`) filtered by the domain's `isOpen` (`packages/domain/src/pr.ts:173-181`). Do not write a second list of statuses. `isOpen` also counts `requested`, which the ticket's three columns leave out. That is a decision, not a question:
- a Submit that is requested and not yet frozen is about to take the draft, so it holds the switch too;
- the safe side is refusing;
- it is one definition rather than two.

Do not use `projectStreams` for the PRs. `listPrs` already walks `pr-{project}-{n}` by `head` and explains why (`pr.ts`, *"no `startsWith('pr')`, which takes `prj-` for a PR"*).

## The candidates: a port on `ChangeOptions`, never `task_view` from inside `packages/project`

`readPrDraft` takes candidates *handed in* (*"`candidates` are handed in — … **never the board's two-day default**"*). `packages/project` does not depend on `@lingtai/projector` (`packages/project/package.json`) and must not start to.

Add `candidates?: (project: string) => Effect.Effect<readonly { readonly issue: string }[], Error>` to `ChangeOptions`. This is the same shape as `PrWorld.candidates` (`apps/cli/src/pr.ts:28`) and the conductor's port (`packages/conductor/src/pr.ts:59`).

- **Board**: `saveRecipe` (`apps/board/src/app/actions.ts:1066`) passes `readTasksEffect({ project, retentionDays: … })` mapped to `{ issue }`, as `apps/cli/src/pr-ports.ts:82-86` does. The constant `EVERY_LANDED_ROW_DAYS = 36_500` is private to `apps/cli/src/pr-ports.ts:21`. Export one copy from `@lingtai/projector/task-view` beside `readTasksEffect`, and have both sites import it. Do not write a second literal.
- **Absent on a team → solo switch**: refuse `mode-switch` and write nothing. Message: *"mode: team → solo is refused here: this caller cannot read what has landed on `<personal>` — switch the mode on /recipe"*. This fails closed, the way `readProjectStateEffect`'s doc puts it (*"unknown is not unlocked"*, `state.ts:50-53`).
  - None of `applySetup`'s three callers write `mode`: `packages/setup/src` contains no `mode` key.
  - `doctor --fix` only applies spelling changes (`apps/cli/src/doctor.ts:2547-2548`).
  - So no existing caller reaches this branch, and none needs the port wired in this ticket.
- **`applySetup`** (`packages/setup/src/apply-setup.ts:92`) currently drops an `ok: false` result: it only maps errors (`:100-105`). Make it fail with `SetupWriteError(result.message)` when `!result.ok`, so any refusal (this one, `stale`, `missing`) is passed up by name rather than reported as written. This is the ticket's *"pass the refusal up by name rather than dropping it"*.

## The refusal

Add `'mode-switch'` to the `reason` union at `packages/recipe/src/write.ts:141`. Run `pnpm typecheck` to find any exhaustive `switch` it breaks.

The message builder should be a pure function next to the check, unit-tested on its own:
- PR name: the code host's number when `pr.host !== null`, otherwise Lingtai's `n`.
- At most five ticket numbers, then *and N more*.
- Both sentences when both conditions hold, PR first, as the ticket specifies.
- When every `PrState` is open but none has been read from the host, the sentence still points at the PR page. This is the *"merge not yet read"* edge.

## Order of reads, and the "reads nothing" test

Inside the team → solo branch:
1. `listPrs` (open check);
2. `options.candidates`;
3. `readDraftOn`.

Compute both conditions; do not short-circuit, because the message names both. Any failure propagates as the Effect's error. It is never mapped to "nothing open", and `files.replace` is never reached.

For the Done-when *"reads no ticket or PR stream"*, wrap the memory store so that `read` and `head` fail on any stream starting `pr-` or `ticket-`, and pass a `candidates` port that fails. A solo → team save and a `mode: solo`-over-no-mode save must both succeed against that wrapped store. The upfront `readProjectStateEffect` (`change.ts:69`) reads `prj-`, which the wrapper must let through.

## Edge the ticket's Watch out understates

`task_view` is the source of candidate ids. A ticket that landed while no conductor was folding the projection is not yet a card, so it is not a candidate, and the draft reads empty for it. This is #1316's accepted trade (the ticket's Watch out: *"#1316's draft takes only its candidate ids from `task_view`"*), and this ticket does not widen it. Say so in a comment at the port.

Whether it actually happened can be settled from the log: a `TicketLanded` with `base: <branch.personal>` on a `ticket-{project}-` stream whose issue has no `task_view` row.

## Ratchet

The new read is `Effect.gen` with no `async` and no `Effect.run*`. `saveRecipe` already has its one `Effect.runPromise` (`actions.ts:1065`), and passing the port adds none. `effect-ratchet.baseline.json` must not move.
