## Design note: #613, publishing `requirements` on the site

### The trap: adding to `PUBLIC_SLUGS` alone does nothing

`servable()` doesn't look at `doc/` directly. It filters `published()` through `PUBLIC_SLUGS`:

```ts
// apps/site/src/lib/docs.ts:73-75
export async function servable(): Promise<string[]> {
  const all = await published()
  return DOCS_PUBLIC ? all : all.filter((f) => isPublicSlug(slugOf(f)))
}
```

`published()` only returns the files named in `SECTIONS` (`docs.ts:271-275`). Today `requirements.md` is in no section. The Guides list is `['tutorial.md', 'guide.md', 'operating.md', 'reference.md', 'design.md', 'roadmap.md']` (`docs.ts:100`).

So with `'requirements'` added to `PUBLIC_SLUGS` and nothing else:
- `generateStaticParams` still builds no `/docs/requirements` route.
- `DocPage` still calls `notFound()` (`apps/site/src/app/docs/[...slug]/page.tsx:89`).
- The tutorial's link still goes to GitHub.

The ticket's link would not change, and the miss would be silent. `resolveHref` sends a `.md` link to the site only when `isPublished(rel)` is true (`docs.ts:409`). `isPublished` is `published.includes(file)` (`document.tsx:148`), and the page passes it `servable()` (`page.tsx:88`, `:113`).

### Shape

Two edits in `apps/site/src/lib/docs.ts`, plus tests.

1. **Add `'requirements.md'` to the Guides section's `files`, right after `'tutorial.md'`.** The tutorial points the reader there at its line 16 ("Everything else Lingtai needs, and when, is on [requirements](requirements.md)"), so it is the second page someone reads. It belongs in Guides, not in a new section. Moving it out of the uncovered set also takes it off the docs index's list of unpublished files. Nothing asserts that `requirements.md` is on that list: the `unpublished()` test only names `research/market-opportunities.md` and `README.md` (`apps/site/unit/docs.test.ts:62-63`).
2. **Add `'requirements'` to `PUBLIC_SLUGS`** (`docs.ts:66`), and update its doc comment (`docs.ts:54-65`). The comment explains why each published slug is there ("the tutorial, which is the way in… and `plugins`… Nothing else in `doc/` has been through that edit yet"). Add the reason for requirements in the same voice: it is the page the tutorial sends a first-time installer to.

The Guides section is pinned by `docs.test.ts:40-45`: `filesOf(guides)` must equal the declared list, so a name that isn't on disk fails. That test covers the new entry with no change.

### Where the published list is actually pinned

The ticket points at `docs.test.ts`, but the assertion is in **`apps/site/unit/page.test.ts:78`**: `expect(PUBLIC_SLUGS).toEqual(['tutorial', 'plugins'])`. Its test title (`:72`, "except the tutorial and the plugin pages") also names the set, so update the title along with the array.

Leave the same test's link check (`:79-82`) as it is. It is about the front page and the chrome. The ticket asks for no requirements link in either, and adding one is out of scope.

### The tests the Done-when needs, in `docs.test.ts`

These go in a new `it` beside "where a link inside a document goes" (`docs.test.ts:154`). That block's `isPublished` is a hand-written list (`:155-156`), so a test using it says nothing about the real publication.

The new test should take `const served = await servable()` and `const isPublished = (f) => served.includes(f)`, then assert:

- `served` contains `'requirements.md'`, and does **not** contain `'operating.md'`. `operating.md` is published (it is in Guides) but must not be served.
- `resolveHref('tutorial.md', 'requirements.md', isPublished)` is `'/docs/requirements/'`. This is the Done-when's "the tutorial's link points there", checked through the same predicate the page uses.
- `resolveHref('tutorial.md', 'operating.md', isPublished)` is `` `${GITHUB_BLOB}doc/operating.md` ``. The tutorial links `operating.md` at lines 129 and 218, and the ticket says those stay on GitHub on purpose.

### The requirements page's own links

Today `doc/requirements.md` has these links:
- `tutorial.md` (lines 4 and 36): goes to the site, `/docs/tutorial/`.
- `../README.md` (lines 47, 50, 52): `rel` starts with `../`, so it goes to `GITHUB_BLOB + 'README.md'` (`docs.ts:407`), which exists.

Its `file.ts:line` citations, such as `apps/cli/src/doctor.ts:883`, are code spans, not links, so they render as text. Nothing resolves to a 404. One assertion that `resolveHref('requirements.md', '../README.md', isPublished)` is `` `${GITHUB_BLOB}README.md` `` is enough; don't add a link walker for this. Don't edit `doc/requirements.md`. The site rewrites links when it renders and leaves the files written for the repository (`document.tsx:107-112`).

### Checks

Everything above is unit-level. Before this lands, `pnpm typecheck` and `HOME=/nonexistent pnpm test` confirm it.

The one thing they can't see is the Next build actually emitting `/docs/requirements`, which is `apps/release/integration/build.test.ts`. That runs after the merge. The `servable()` assertion stands in for it, because `generateStaticParams` builds its routes from `servable()` (`page.tsx:46`).
