# Design: #602, the split plan drawn as waves

## Where it mounts

The plan goes in the triage band, not in a resolution card.

- **Triage band.** `standing.tsx` is a server component: it has no `'use client'`, and `triage-picks.tsx` is how it embeds interactive parts. The band switches on `cause._tag` and today does nothing for this cause: `case 'TicketTooBig': … break` (`apps/board/src/app/standing.tsx:211-214`). When `cause.split !== undefined`, set `parts` to `<SplitPlan plan={cause.split} parent={…} />`, the same slot `ConflictingHunks` fills just above. With no `split`, nothing changes. The plan is not drawn as text anywhere today; it is simply not drawn.
- **Resolution cards.** Leave `const drawable = allowed.filter((tag) => tag !== 'Split')` (`standing.tsx:620`) alone. Its comment still holds: *"`Split` has no card until its editor exists (#563): a card with no action under it is worse than none."* This ticket has no action, because Create all is a separate ticket. The band's existing line, "Recommends Split into smaller tickets", is enough of a pointer.

## New files

### `apps/board/src/lib/split-waves.ts`

Pure TypeScript with no React and no dagre, so the unit test can import it. It holds the rule and nothing about pixels:

- **`waves(children, blockedBy) → Map<key, number>`.**
  - A child with no blocker is wave 1.
  - Otherwise a child is `1 + max(wave of each blocker)`.
  - Memoise it.
  - Guard against cycles, as the mockup does (`Split.dc.html:408`, `seen.includes(i) ? 1`), so a bad plan never loops. `SplitProposal` already refuses cycles through `splitPlanProblems` (`packages/domain/src/split.ts:165-179`), so the guard matters only for edits.
- **`wouldCycle(blockedBy, ticket, blocker) → boolean`.** A reachability check. The panel uses it to disable any blocked-by checkbox that would close a loop. Refuse the edit rather than draw a cycle. `findCycle` in `split.ts:128` is not exported, and exporting it is not needed for this.

### `apps/board/src/app/split-plan.tsx`

A `'use client'` component beside `standing.tsx`.

**Local state**, all seeded from the proposal:
- `children` (title and body editable)
- `off: Set<key>` (the include checkbox)
- `blockedBy`
- `selected: key | null`

Nothing goes to a server action and nothing is appended. Excluded children stay in the wave computation and are drawn faded, with the mockup's `off` state. That way unticking one does not reshuffle the plan under the person's cursor. Whether an exclusion leaves a dangling dependency is Create all's question, through `splitPlanProblems`.

**Layout.** Follow the mockup: `L = { W: 236, H: 66, dir: 'LR', nodesep: 16, ranksep: 64 }` and `smoothstep` edges (`Split.dc.html:22`). Then:
- Blocker → dependent edges get `{ minlen: 1, weight: 1 }`.
- The parent gets an invisible edge to every child with `{ minlen: wave, weight: 20 }` (`:51-54`). This edge is what gives an arrow that skips a wave its own lane.
- Children with no blocker get a visible dashed parent → child edge.
- Each wave gets one band node labelled `wave 1 · starts first`, `wave 2`, … (`:73-79`).
- A child's card label is `Child N`, because no number exists before Create all (`:491`). The card shows the kind and the title's first line, and takes its kind colour from `lib/kind-colour.ts`.

**Canvas.** Do not use `fitView`; this is the one non-obvious decision.
- **Why not `fitView`:** the mockup's `fitView` (`:95`) scales the whole graph to the container. At 390 px a five-wave plan would shrink to unreadable cards. `fitView` also needs measured dimensions, so `renderToStaticMarkup` in the unit tests would render an empty pane.
- **Instead:** use a fixed viewport `{ x: 0, y: 0, zoom: 1 }`. Size the `<ReactFlow>` box to dagre's own `graph().width/height`, and give every node an explicit `width`/`height` so React Flow 12 renders without measuring. Wrap it in a container with `overflow-x: auto`: the page scrolls, and the canvas still neither pans nor zooms.
- **Props:** `panOnDrag`, `zoomOnScroll`, `zoomOnPinch` and `zoomOnDoubleClick` all `false`, plus `nodesDraggable={false}`, `nodesConnectable={false}` and `preventScrolling={false}`.
- **Attribution:** do not pass `proOptions={{ hideAttribution: true }}`.

**Selection.**
- `onNodeClick` on a child sets `selected`, and clicking the same child again sets `null`.
- `onPaneClick` sets `null`.
- Clicks on the parent and band nodes are ignored.
- With a selection, the selected child, the parent and the selected child's direct neighbours stay lit, and everything else is faded (`:57-61`). With none, every arrow is drawn at full strength.

**Panel.** It renders below the canvas at full width only while something is selected:
- a title input
- a body textarea
- the "include this ticket" checkbox
- one checkbox per other child for blocked-by, disabled where `wouldCycle` says so

Editing blocked-by recomputes `waves` and re-runs dagre. That costs nothing at `TRIAGE_SPLIT_CHILDREN_MAX = 8` (`packages/domain/src/triage.ts:39`).

**CSS.** Import `@xyflow/react/dist/style.css` from this component, and put the board-side card, band and faded rules in `globals.css` beside the other `triage-*` rules.

## Dependencies

Run `pnpm --filter @lingtai/board add @xyflow/react @dagrejs/dagre`. Pick the 12.x line of `@xyflow/react`, which supports React 19 (the board is on `react` 19.2.8, `apps/board/package.json`), and check that `pnpm-lock.yaml` changes. Neither package goes in `transpilePackages`, which lists workspace packages only (`apps/board/next.config.ts`).

The README promises that the board fetches nothing (`README.md:40`). For fonts that is *"`next/font/local` … so building it fetches nothing from Google"*. The same holds here as long as nothing is loaded from `esm.sh`; installing the packages is the only network step. Once the build works, grep the built `.next` output for `esm.sh` to confirm.
