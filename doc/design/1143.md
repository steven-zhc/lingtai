### The one decision the ticket doesn't spell out: two consumers that `main` never exercises

The ticket flags `release.yml`'s `publish` job (`release.yml:123-126`, `path: artifacts` + `merge-multiple: true`, which runs only on `tags: ["v*"]`, `release.yml:18`). There is a second consumer with the same blind spot, and it fails more quietly:

- `integration.yml:116-120` downloads every artifact with only `path: reports`. It carries `if: needs.integration.result == 'failure'` and `continue-on-error: true`. So a green run on `main` never executes it, and a broken download does not fail the job.
- The step after it reads a fixed layout, one directory per artifact name. `integration.yml:143` has `f="reports/integration-$store/integration-$store.json"`.
- When that file is missing, the step writes `**$store** — no report; it failed before vitest finished, or passed. See the run.` (`integration.yml:158-159`). If a new `download-artifact` major changes the layout for a no-`name` download (flattening, a new subdirectory, or a different default for `merge-multiple`), nothing goes red. The red-on-main issue would just stop naming failing files.

So when you read `download-artifact`'s notes for v5 through v8, check two cases. Write the result of each in the commit body. Use the "for those inputs" wording the ticket asks for, and do not use a closing verb next to any issue number.

1. **Download all, no `name`, `path` only, no `merge-multiple`** (`integration.yml`). It must still produce `reports/<artifact-name>/<file>`. If the notes say the default changed, set the input that restores this layout explicitly (for example `merge-multiple: false`). Do not change the `jq` reader.
2. **Download all, `path` + `merge-multiple: true`** (`release.yml`). It must still put every platform's files flat into `artifacts/`, because later steps write into that directory (`cp doc/cli.json artifacts/cli.json`, and the `SHA256SUMS` step the comment at `release.yml:160` names).

If either case has changed and no input restores it, stop and say so in the commit. Do not paper over it in the shell.

The upload side pairs with these. `integration.yml:94-99` and `release.yml:100-104` keep `name`, `path` and `if-no-files-found` as they are. If an `upload-artifact` major changes a default those steps rely on (hidden files, or what `if-no-files-found` does by default), set the input explicitly.

### Other things to check while reading the notes

- **`pnpm/action-setup`**: confirm in v5 and v6 that a step with no `version:` input still reads `packageManager` (`package.json:8`, `pnpm@11.9.0`). If a new major needs an input to keep doing that, use the input that points at `package.json`. Do not use one that names a pnpm version.
- **`actions/checkout`**: `deploy-site.yml:38-39` and `release.yml:115-116` use `fetch-depth: 0`. `release.yml`'s `publish` relies on tags being present (`git tag --list 'v*'`, in the "Previous release" step). If a major changes whether tags are fetched or how credentials are kept, look again at any later step that runs `git` against the remote.
- **`actions/setup-node`**: keep `cache: pnpm` explicit everywhere. Any automatic caching a new major adds based on `packageManager` does not replace it.

### What can be checked before the merge

Nothing in the YAML can be run here. `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` prove only that nothing else moved. As a last check, `grep -rnoE "uses: [^ ]+@v[0-9]+" .github/workflows` should show the five actions only at their new majors and `oven-sh/setup-bun@v2` unchanged.

Don't push a branch or dispatch a workflow to try it. That is outward-facing and outside the ticket. After the merge, a person checks two things in addition to what the ticket lists: the next tag's `publish`, and the next red `integration` run on `main`. The second is the first real test of case 1.
