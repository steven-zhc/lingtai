## Design note: #697: a Rust detector

**Where it goes.** Add one `rustDetector: StackDetector` (`stack: 'Rust'`) to `apps/cli/src/detect-setup.ts`, after `javaDetector`, and put it fifth in `DETECTORS` (`detect-setup.ts:693`). Being last is deliberate. `detectSetup` takes "the first stack present" and only names the others in a note (`:695-700`), so a repository with both `package.json` and `Cargo.toml` (a napi crate, a Tauri app) keeps Node's suggestions and gets "Rust is also at the root; Node was used". Put a unit test on that ordering. Tests go in `apps/cli/unit/detect-setup.test.ts` with a fake `SetupReader`, as the other four detectors do.

**Shape.** Model it on Java's Maven branch (`:620-690`), not on Go:

1. `hasOrUnknown(reader, 'Cargo.toml')`. If it is `unknown`, add the note "could not tell whether a Cargo project is at the root" and return `presence: 'unknown'`. If it is `false`, return `absent`.
2. Read it inside a `try`, as Java does for `pom.xml` (`:657-661`), and parse it with `parseToml`. `smol-toml` is already imported (`:12`), so this needs no new dependency. Two failures end the same way, with `presence: 'present'` and nothing suggested:
   - a read that rejects or returns `null` gets the note "Cargo.toml could not be read";
   - a parse that throws gets "Cargo.toml does not parse".
   
   Do not look inside the parsed table. `[package]` and `[workspace]` get the same commands, and that is the whole workspace edge.
3. Check `hasOrUnknown(reader, 'Cargo.lock')`:
   - `true`: fetch and test both get `--locked`.
   - `false`: neither gets it. No note is needed, because a library without a lockfile is normal.
   - `unknown`: this is a decision the ticket leaves open. Suggest the commands **without** `--locked` and add "could not tell whether Cargo.lock is at the root; --locked was left off". Dropping the guard is the choice that cannot fail a pass on its own account, and the note keeps the guess from being silent, which is the rule in the file header (`:6-9`).
4. Commands:
   - install: `cargo fetch [--locked]`, because "Cargo.toml is at the root".
   - build, in order: `format` = `cargo fmt --check`, `lint` = `cargo clippy --all-targets -- -D warnings`, `test` = `cargo test [--locked]`.
   - The ticket puts `--locked` on fetch and test only, and that is enough. Once `cargo fetch --locked` has succeeded, the lockfile is consistent, so clippy has nothing to rewrite.
5. Always add the timeout note, worded like Java's (`:681-683`): a cold Cargo build compiles every dependency in each new worktree and can exceed a run's default timeout of 15m, so set `timeout:` on the command in the recipe if the trial runs out. The detector sets no `timeout` itself. A unit test asserts the note is among the notes.

**The PATH note is the non-obvious part.** `printFound` probes one tool per command, `c.tool ?? c.run.split(' ')[0]`, collected into a set (`apps/cli/src/setup-build.ts:250`). All four commands start with `cargo`, so left alone the only thing probed would be `cargo`. A machine with cargo but without the `clippy` or `rustfmt` rustup components would then pass the probe and fail at the trial. So:
- the `format` entry carries `tool: 'rustfmt'`;
- the `lint` entry carries `tool: 'cargo-clippy'`;
- fetch and test carry no `tool`, so `cargo` is still probed through them.

This is what the `tool` field's doc comment already allows ("what to look for on PATH when the command's first word is not it", `detect-setup.ts:47`). Widen that comment to say that the first word can also be a launcher for a separately installed component. Also add a clause about Rust to the comment above `printFound` (`setup-build.ts:241-245`), which lists by stack what is probed and why. `setup-build.ts` needs no code change. A unit test asserts the two `tool` values on the detector's output. The probe itself is already covered wherever `printFound` is tested.

**Docs.** In the README's setup paragraph (`README.md:61-70`), add Rust after the Java clause: "and Rust from `Cargo.toml` (`cargo fetch`, then `cargo fmt --check`, `cargo clippy` and `cargo test`, with `--locked` when `Cargo.lock` is at the root)".

**What checks it.** Everything above can be checked at unit level by `pnpm test`. Nothing here needs the integration half, and nothing runs `cargo`.
