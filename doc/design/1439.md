## Design note: #1439, the PR detail load starts before the bar's reads

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

This is one edit, to `apps/board/src/app/pr/[project]/[n]/page.tsx`, plus one new unit test file. No ADR changes. Nothing in `lib/` changes. Every claim below can be checked with `pnpm test`, and none depends on `pnpm test:integration`.

### The page: copy the list page's shape, not its spirit

`[project]/page.tsx:64-111` is the model, and it is the same bar. `RecipeBar` takes the same five reads on both pages. Today the detail page awaits them one after another:

- `readRegistered` at `[n]/page.tsx:78`
- `onBoardProjects` at `:83`
- `readProjectLocks`, `placeViewsOf` and `pauseSlot` inline as props at `:97`, `:99` and `:100`

Detail calls `loadPrDetail` itself at `:29`, so the load cannot start until `Page` has returned. Make these changes:

1. **Validate `n` and start the load.** Keep the existing `n` parse at `:76`. On the next line write `const load = n === null ? null : loadPrDetail(name, n)`. If `load` is not null, attach `load.catch(() => undefined)` and discard the result. Put the list page's comment beside it (`[project]/page.tsx:66-67`): *"marks the promise handled while this page is still awaiting the bar; `Board`'s own `await` still sees a rejection."* The branch is needed even though `readPrDetail` turns its own failures into `{ kind: 'failed' }` (`prs.ts:317-323`). The reason is that `measure` rethrows (`timing.ts:73`: *"Rethrown untouched and never read"*), so a fault in tracing or in `timed` still rejects `load`.
2. **Read the bar in one `Promise.all`.** Read the same five values, in the same shapes as the list page (`[project]/page.tsx:71-83`). Each listing becomes `{ value, error }` through `.then(ok, err)`, so neither listing can reject the `Promise.all`. Locks, views and pause stay bare, as they are on the list page today.
3. **Compute the listing error after both listings settle.** Use `listing.error ?? onBoardListing.error`, as `[project]/page.tsx:85` does. The current code sets the precedence with a `catch` assignment at `:79` followed by `??=` at `:84`. That only works because the two reads run one after the other, and they no longer will.
4. **Pass the load to Detail.** Change Detail's props to `{ project, n, load }`. Detail still returns the "There is no PR numbered like that." line when `n === null`. In every other branch it does `await load`, where it now calls `loadPrDetail` at `:29`. Everything from `:30` to `:70` stays as it is, including the host `Suspense` and the generated-description `Suspense`. A rejected `load` stays a throw out of Detail, so it reaches the error boundary as it does today. It must not become a `failed` read, and it must not become a `none`.

**Leave Detail in `page.tsx`.** This route file does not need it moved. Named exports from page files are already present and build: `app/page.tsx:203` `export function Card` and `recipe/[project]/page.tsx:110` `export function ModeCard`. Even so, do not export Detail. The test reaches it through the element tree (see below).

The ratchet counts no `apps/board` entry (`packages/domain/unit/effect-ratchet.baseline.json` lists only packages and `apps/cli`). Add no new `async` helper anyway: `Page` and `Detail` are already `async`.

### What overlap means for the bar's reads (#1420)

`placeViewsOf` (`prs.ts:230-246`) and `readPrDetail` (`prs.ts:317+`) both read `projectOf` and `recipeOf`. Both functions are `cache()`d by project name (`request-reads.ts:16`, `:19`: *"Each is `cache()`d by the project's **name**"*). Today `placeViewsOf` fills that cache while the bar is built, and `pr.detail` later finds it warm. After the change both callers start together and share the same in-flight promise. Expect three things:

- No extra store reads. Nothing in `request-reads.ts` or `request-store.ts` changes.
- If `projectOf` rejects, both callers see it. `placeViewsOf` turns it into `waiting: null` (`:236`), and `readPrDetail` turns it into `failed` (`:321-322`), exactly as each does today.
- **`pr.detail`'s own duration may get longer while its start offset gets shorter**, because the project and recipe reads now run inside its span. The operator's validation cohort must compare the `pr.detail` start offset and the request's total duration. It must not compare `pr.detail` duration against the 0.204 s median in the ticket. Write that sentence in the handoff.

`pauseSlot` calls `readProjectLocks()` a second time (`lock-banner.tsx:61`). In production `cache` (`locks.ts:121`) makes those two calls share one promise. Under vitest the React build that loads may not memoise `cache` outside a render. So the test must assert that `readProjectLocks` was *called*, not that it was called exactly once.

### The test: a new `apps/board/unit/pr-detail-page.test.tsx`

`apps/board/unit/home-streams.test.tsx:13-52` is the pattern. It uses `vi.hoisted` deferred mocks, `vi.mock(path, async (orig) => ({ ...(await orig()), … }))`, calls `Page(...)` directly, and walks the returned tree.

- **What to mock and what to fake:**
  - `../src/lib/locks.ts`: `readRegistered` and `readProjectLocks`.
  - `../src/lib/board.ts`: `onBoardProjects`.
  - `../src/lib/prs.ts`: `loadPrDetail` and `placeViewsOf`.
  - `../src/app/lock-banner.tsx`: `pauseSlot`, plus `LockBanner: () => null`.
  - `@lingtai/env`'s `hasGitHubAuth`, as `home-streams.test.tsx:38-44` does.
  - Give each mock its own deferred promise, so the test controls when each one settles.
- **The order assertion:**
  1. Call `Page({ params: Promise.resolve({ project: 'p', n: '7' }) })` and do not await it.
  2. Flush a few `await Promise.resolve()` turns.
  3. Assert that `loadPrDetail` was called with `('p', 7)` and that all five bar mocks were called, while all of them are still pending.
  4. Resolve the bar reads and await `Page`.
  5. Walk the tree. Find the element whose `props.load` is **the same object** `loadPrDetail` returned (`toBe`, not `toEqual`). That is the "same promise" check.
  6. Repeat with `n: 'next'`.
- **Invalid `n`:** run with `'0'`, `'-1'`, `'abc'` and `'07'`. In every case `loadPrDetail` is never called. The Detail element gets `load: null`, and calling it renders the existing sentence. The current regex `/^[1-9]\d*$/` (`:76`) rejects `07`; keep it.
- **Early rejection with a slow bar:**
  1. Make `loadPrDetail` return an already-rejected promise. Leave the bar pending.
  2. Install a `process.on('unhandledRejection', spy)` listener.
  3. Yield one `setImmediate` turn. Node reports unhandled rejections after the microtask queue drains. `setImmediate` is not the wall clock, so 0060 §1 still allows it.
  4. Assert that `spy` was not called.
  5. Resolve the bar and get the Detail element. Assert that `el.type(el.props)` rejects with the same error.
  6. Do the same with a bar that resolves successfully, so a green bar cannot hide the body's failure.
- **Listing error precedence:** reject both listings with different messages. The `pr-refusal` line shows the registered listing's message. Reject only the onboard listing, and the line shows that one.
- **What not to assert:** milliseconds, source-text order, or a snapshot of the whole page. The ticket's last edge rules these out.

Existing tests that must stay green unchanged: `trace-spans.test.ts:290` (it calls `loadPrDetail` with a fake reader, and that signature does not change), `request-reads.test.ts` and `pr-page.test.tsx`.

### What only the operator can check

Whether production improved shows up in the `lingtai-board` Jaeger traces, not in the event log. That means the `pr.detail` span's start offset within RSC GET `/pr/[project]/[n]` requests, measured after the rebuild. The unit test is the claim that stands in for it before the merge: **the detail load has started while every bar read is still pending.** The handoff must say so, and must not present the test as a latency result.
