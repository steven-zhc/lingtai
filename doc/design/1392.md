## Design: #1392, record a landing on `branch.personal` in the draft in the same transaction

### Line numbers have moved since the ticket was written
- `landTicketEffect` is at `packages/conductor/src/ticket/commands.ts:910-924` and `appendOnTicket` at `:876-885`.
- The two callers in a live pass are `packages/conductor/src/conduct.ts:3198` (`recordLanding`, `Effect.retry({ times: 2 })` at `:3202`) and `:6363` (the normal ending).
- `attemptBase` is at `:1197`.

### There is a third caller. Leave it at `null`, on purpose.
`packages/daemon/src/owed-landings.ts:89` calls `landTicketEffect(ticketId, { mergeCommit, base }, store, options.read)` for "the landings a dead conductor owed (#1397)". Its own header says it holds no recipe on purpose:

> "The reconcile holds no resolved recipe — `ProjectState.recipe` is declared text — and resolving one is a new way for a step that exists to work after a crash to fail." (`owed-landings.ts:11-12`)

The ticket's Out of scope already covers this ("Recording a landing whose process died after the push: a separate bug ticket"). So don't touch this file. It passes no `draft`, which means `null`, and it keeps writing the ticket's stream only.

State the consequence in the commit body, not only here. A landing recorded by this path has `TicketLanded` (field `base` = `branch.personal`) and no `PrDraftTicketAdded` on any `pr-{project}-{n}`. The ticket's edge "No `TicketLanded` is left without a draft entry" holds only for the live pass. The backfill ticket, or the owed-landings ticket, has to close that gap.

### `PrDraftTicketAdded.ticket` is the issue, not the stream id
The draft compares `ticket` against the issue:
- `readDraftOn` reads `store.read(ticketStream(project, issue))` and keeps `held` by `t.ticket` (`packages/project/src/pr.ts:514, 520-521`).
- `ticketStream` is `` `ticket-${project}-${ref}` `` (`packages/domain/src/streams.ts:24-26`).

`landTicketEffect` only gets `ticketId`, the stream id (`conduct.ts:1331`: `const ticketId = ticketStream(project, options.issue)`). Get the issue with `parseTicketStream(ticketId)` (`streams.ts:36`), and treat a `null` there as a defect.

If `ticket-lingtai-1392` is written into the draft, every write succeeds and every reader misses the entry. The `readDraft` test in Done-when only catches this if it asserts `.ticket === '<issue>'`, so make it assert that.

### Where the parts go
- **`draftBatchFor`** goes in `packages/project/src/pr.ts`. It returns a `StreamBatch` (`packages/event-store/src/event-store.ts:340`) built from `draftTarget` (`pr.ts:109-124`) and `addDraftTicket` (`packages/domain/src/pr.ts:614-620`).
  - `addDraftTicket` returns `null` only for a status that is not `null`, `draft` or `requested`, and `draftOf` never returns such a status (`pr.ts:117-124`). So a `null` there is a defect: die, don't skip silently.
  - Don't use `withOneRetry`, which this file's header describes ("on a lost race re-read and ask again once", `pr.ts:4-5`). This function does not append. The retry belongs to the caller and has no limit.
  - Update the header line "nothing else appends to a `pr-` stream" (`pr.ts:8`) to say that this one batch is handed to `landTicketEffect`. 0129 §5 allows exactly this: "Each stream's events still come from its own aggregate's transition, at the version read … No other decision may use `appendAll`" (`doc/decisions/0129-one-module-owns-each-aggregate.md:107-109`).
  - The owner test only counts `ticket-` appends (`packages/domain/unit/aggregate-owners.test.ts:29`), and `landTicketEffect` lives in that owner. No baseline moves.
- **Dependency direction.** `@lingtai/conductor` already depends on `@lingtai/project` (`packages/conductor/package.json:65`), and `@lingtai/project` does not depend on conductor. No new edge.
- **Callers.** Reuse the predicate already written at `conduct.ts:3517-3519`: `modeOf(recipe) === 'team' && recipe.branch.personal !== undefined && base === recipe.branch.personal`. Here `base` is `attemptBase()`. Compute it once in a small helper so both call sites use the same test. A pr-fix's `attemptBase()` is the PR branch (`:1191-1197`), so it passes `null` without a special case.

### The retry loop, which the ticket does not spell out
- **Read the ticket's version once, outside the loop.** Put only `draftBatchFor` + `appendAll` inside the loop. Re-reading the ticket's version on each try would quietly accept a write to the ticket's stream that happened in between. The ticket says a conflict on that stream is a defect.
- **Batch order matters.** Put the ticket's batch first. The memory store checks batches in order and throws on the first stream that conflicts (`packages/event-store/test/memory.ts:194-201`). The sqlite store names `current`, the batch it was inserting (`packages/event-store/src/sqlite.ts:297-301`). Either way, when both streams moved, the ticket's stream is the one named, and that is the defect.
- **Classify inside the attempt.**
  - A `ConcurrencyError` whose `streamId` (`event-store.ts:66`) is the ticket's stream: `orDie`.
  - A `ConcurrencyError` on the draft's stream: stay a typed failure, log the ticket's line, and wrap the attempt in `Effect.retry` with no `times`.
  - Compare against the `streamId` of the batch that try actually sent, not a stream fixed before the loop. After a freeze, the target becomes the next number (`pr.ts:123`).
- **Log with `Effect.logWarning`.** `landTicketEffect` has no logger parameter, and the line's text is the ticket's own.
- **The store call** is `Effect.tryPromise` around `store.appendAll`, with no new `async`. `appendAllFace` is already in `effect-ratchet.faces.json:202`.
- **A failed read of the draft target dies** (`orDie`), as `appendOnTicket` does today (`commands.ts:882`). `recordLanding` already turns defects into failures and retries them (`conduct.ts:3201-3202`).
- **Tests must not hang.** A fake store that refuses on the draft stream every time never returns. Each conflict test refuses once and then delegates.

### Freeze test
Put the PR in `requested` before the read: `draftTarget` is `{ n, version, state: 'requested' }`, as at `packages/project/unit/pr.test.ts:106`. Then inject `PrInProgress` through `freezeTransition`, which only freezes a `requested` PR (`packages/domain/src/pr.ts:628-631`).

The field to assert is `PrDraftTicketAdded.data.ticket` on `pr-{project}-{n+1}`, and its absence on `pr-{project}-{n}`.

### Verification
Everything can be checked at unit level with `createMemoryEventStore()`. It runs the same `appendAll` contract as sqlite and Postgres (`packages/event-store/test/contract.ts:247-360`), so no claim depends on `pnpm test:integration`.

The one thing no test inside a pass covers is how sqlite and Postgres actually name the conflicting stream. That is held by the contract suite in the integration half, after the merge.

No ADR contradiction: 0131 §1 (`doc/decisions/0131-a-pr-goes-from-draft-to-merged.md:44-50`) and 0129 §5 describe this shape.
