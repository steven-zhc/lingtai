## Design note for #1379: the key line at the foot of search

This is nearly what the ticket already says. One trap is not obvious from it, and the test needs two rules spelled out.

### The trap: the existing `.k-mac` / `.k-pc` rules do not reach the dialog

The ticket says to reuse the bar's Mac/PC switch. Those rules are scoped to the bar's search field:

```css
.bar .search .k-pc { display: none; }
html[data-os="pc"] .bar .search .k-pc { display: inline; }
html[data-os="pc"] .bar .search .k-mac { display: none; }
```
(`apps/board/src/app/globals.css:316-318`)

The dialog is not inside `.bar`. `<Palette />` is mounted straight under `<body>` in `RootLayout` (`apps/board/src/app/layout.tsx:79-81`). So `<kbd className="k-mac">` and `<kbd className="k-pc">` placed in the new line would match none of those rules, and both `⌘↵` and `Ctrl ↵` would show on every machine. No unit test can see that: `renderToStaticMarkup` loads no CSS.

**Decision:**
- Add three rules of your own, scoped to the line: `.palette-keys .k-pc { display: none; }` and the two `html[data-os="pc"] .palette-keys …` overrides.
- Put them in the `⌘K (#908)` block, after `.palette-detail` (`globals.css:3648-3679`).
- Do not widen the bar's selectors to a bare `.k-pc`. That changes CSS belonging to the bar, which the ticket puts out of scope.
- Keep the class names `k-mac` / `k-pc`, so one convention covers both places.
- The default stays Mac: the hiding rule is unconditional and only `data-os="pc"` reverses it. That matches the comment at `globals.css:305-306`: *"CSS picks the label once `Palette` has set `data-os` on <html>: until then the Mac one."*

Only `⌘↵` changes by platform. Every other key in the line is the same on both.

### Where the line goes in `PaletteView`

Put it as the last child of `.palette-body`, after the `<ul className="palette-list" role="listbox">` (`apps/board/src/app/palette.tsx:84-105`). Render it every time, whatever `index` is: pending, `null` or loaded. The keys work in all three states.

`.palette-body` is a grid with `gap: 6px` (`globals.css:3660`), so the line needs no margin of its own. A muted, small style like `.palette-problems` (`:3668`) fits. Don't reuse `.empty`: that class carries its own meaning (`:396`).

### The test

Add it to the `describe('PaletteView')` block in `apps/board/unit/palette.test.tsx:88-122`, written the way that file already works (`renderToStaticMarkup`, then string matches).

**"Outside the listbox":**
- Take the substring after `</ul>` closes the `role="listbox"` element, and match `class="palette-keys"` and the words there.
- Do not search the whole HTML for `#`. Option ids and hrefs in the fixture index contain `#`-like text, so a whole-page match passes for the wrong reason.

**The platform half:**
- Assert that both `k-mac` and `k-pc` are in the line's markup.
- That is the unit-level claim that stands in for the visual check. The visual check itself is the ticket's last checkbox and needs a person.

### What stays as it is

- **The import guard.** `palette.tsx is "use client" and imports only what a client may` (`unit/palette.test.tsx:128`) reads the file's value imports. A static `<p>` adds none, so the test stays as it is. If it goes red, the diff gained an import.
- **No unit test reads `globals.css`.** The three CSS rules are therefore checked by nothing before the merge except a person opening search.
