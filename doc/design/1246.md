# Design note: #1246, both continuations redo the cut-off step whole

The ticket's line numbers have drifted. All the citations below are to this worktree as it stands. There are five decisions the ticket does not make, and one place where its wording would build the wrong thing.

## 1. A continuation does not call `redoStep`. It shares the half of it that builds the context.

`redoStep` (`run-attempt.ts:1632-1694`) does four things in order:

1. It appends `StepRedone`.
2. It sleeps `waitFor(retry)`.
3. It runs `resetToHead`.
4. It builds `rerun = { reached, context: { ...handed, rerun, redo: { why, startedAt, head } } }`.

A continuation needs only the fourth:

- **The re-cut is already done.** `conduct.ts` provisions the worktree at `releasedHeadOf` (`attempts.ts:660`) before `runAttempt` starts.
- **There is no wait.** The lock has lifted, or a person clicked.
- **`StepRedone` is the spend.** `reduceAttempt` folds `stepRedos` as `Math.max(state.stepRedos ?? 0, d.rerun)` from it (`domain/src/attempt.ts:584`). Appending one would spend, or would show on the board as a redo that 0108 §12 says spends nothing.

So move the context-building lines (`run-attempt.ts:1677-1689`) into a small function. `redoStep` and the continuation's first visit both call it, which keeps it one engine. The continuation's first visit is the branch at `run-attempt.ts:2189-2204` that today builds `{ ...contextFor(), round, rerun, recorded }`. It now builds a `redo` context instead, with:

- `why`: the 0108 §12 sentence;
- `startedAt`: see §3;
- `head`: `options.context.onSha`, which is the re-cut head.

Delete line 2192 (`if (firstAccountVisit && accountRerun.askedAgain === true) askingAgain = at`). That line is the only place `askedAgain` is read in `runAttempt`.

## 2. `from.redo` carries more than `{ step, why, startedAt }`

`from.redo` replaces `from.rerun` (`run-attempt.ts:1036-1042`), and it must also carry these from the old shape:

- **`for: { name, round }`.** `run-attempt.ts:2792-2798` uses `from.rerun.for.round > 0` to hand an account-resumed `implement` an `again`. That `again` makes `conduct.ts` take the fix-round path (`fixRound`, `conduct.ts:5200` onward) rather than `firstDispatch`. Without `round`, a cut-off fix round would be dispatched again as a first implementation, with round 0's dispatch id and spend. Keep the condition and read it from `from.redo.for.round`. The `why` can be `from.redo.why`.
- **`prompt`.** This is the recorded prompt; see §4.
- **`accountReruns`.** The dispatch suffix stays `stepRedosSpent + landingRetriesSpent + accountReruns`, as the doc comment at `run-attempt.ts:1031-1035` says, so that no session id repeats.

The `BaseRed` builder (`conduct.ts:1414-1420`) writes `rerun: { for: null, prompt: null, accountReruns }` and redoes nothing: it continues at `build`. Leave its behaviour alone. When `released.rerun` is reshaped, move `accountReruns` up a level so that `BaseRed` still carries it without a fake `for: null`. Rewrite the mapping at `conduct.ts:5637-5648` to match.

## 3. `StepStarted.startedAt` is written on every `StepStarted`, and the reader takes the last one

The ticket says *"the first `StepStarted` for that step in this attempt"*. Built literally, that is wrong for a fix round. `implement` is visited again each round, at a new `onSha` (`run-attempt.ts:1567`). If an account limit cuts off round 2, the first `StepStarted` at `implement` gives round 0's start sha. A round-2 fixer that adds nothing would then read as *head moved*, and the guard at `conduct.ts:5066` (`if (head === startedAt)`, the 0057 §2 receipt) would be bypassed.

In-process, the code already measures per arrival: `agentStarts` is keyed `${onSha}:${name}` (`conduct.ts:4790-4794`), and `redoStep` takes `earlier?.startedAt ?? redo.visit.context.onSha` (`run-attempt.ts:1688`).

So the rule is:

- **Writer.** The emit at `run-attempt.ts:2253-2254` always writes `startedAt`:
  - on a fresh arrival, `visitContext.onSha`;
  - on any redo, whether in-attempt or a continuation, `visitContext.redo.startedAt`, the value being carried forward.
- **Reader.** It is a new function in `domain/src/attempt.ts` beside `cutOffPromptOf` (`:737`). It takes the **last** `StepStarted` for the step in the released run's stream that has `startedAt`. Because a redo writes the carried value, every redo of one arrival reads the same sha, across any number of processes.

The field is optional in the zod object at `domain/src/events.ts:1288-1293`, so no upcaster is needed. `StepStarted` is `{ runId, step, round }` today.

The ticket's `implementerStartedAt` does not exist under that name. The in-memory state it means is `agentStarts` and `stepFirst` (`conduct.ts:2457-2458`), and both are empty in a fresh process. To seed them, change `conduct.ts:4793` so that, when there is no `agentStarts` entry and `brief.context.redo` is set, it uses `brief.context.redo.startedAt` before `rev-parse HEAD`. Apply this only to the step's first agent dispatch in this process (`stepFirst === null`). A later agent in the same step falls back to `rev-parse` as it does today.

When a stream has no `startedAt`, because the attempt began before this change, `from.redo.startedAt` is absent. `run-attempt` then uses the re-cut head, which is today's behaviour.

## 4. The brief is the recorded prompt, then the paragraph, at all three places a recorded prompt replaces the composed one

Today the recorded prompt replaces the whole brief, paragraph included:

| Where | Step | Code |
|---|---|---|
| `conduct.ts:4883-4887` | `implement`, first dispatch | `recordedBrief !== null ? [recordedBrief] : [..., redoNote]` |
| `conduct.ts:5200-5204` | `implement`, fix round | `recordedFix`, same shape |
| `recordedOr` (`actions/src/action.ts:1302-1310`) | `design` (`agent-action.ts:1652-1658`) and review (`agent-action.ts:989`) | discards `composed` |

Make each one append. `conduct.ts` uses `[recorded, \`\n\n${redoNote}\`]` when `redoNote !== null`. `recordedOr` gains an optional tail that `design` passes. Review gets no tail: *"Never written into a `review`'s brief"* (`action.ts:1313-1316`).

`redoStep` strips `recorded` from the context (`run-attempt.ts:1677-1682`), and that is correct for an in-attempt redo. The continuation's shared context builder must **keep** `recorded`, because that is how the cut-off action finds its replay. `action.ts:1052-1057` already drops `recorded` and `rerun` after the named action. The `redo` drop at `action.ts:1060-1063` is per agent action, which is fine.

A recorded prompt may already end with a redo paragraph, if the cut-off call was itself an in-attempt redo. Strip that trailing paragraph before appending the new one, or the agent is told two different *began at / committed to* pairs. Put the stripper beside `redoParagraph` in `action.ts`, keyed on its own leading words (`This step was interrupted (`), so the wording stays in one file.

## 5. `cutOffPromptOf` and `recordedPromptOf` keep their callers

The ticket's cost edge guesses that they may lose their last callers. They do not: the brief is the cut-off call's recorded prompt, so both builders still call them (`conduct.ts:1461-1467`, `:1530-1535`). Only `askedAgainOn` loses its readers here (`:1503`, `:1564`). It stays defined until #1249, along with `domain/unit/cut-off-call.test.ts`.

The person's builder still passes `waive: waivedActionsAt(...)` (`conduct.ts:1538`). That is a person's waiver of a check, not a skip of finished actions, so keep it.

The resolution's tag is `'RedoStep'` (#1242 renamed it from `RerunStep`; `conduct.ts:1524`), and an approved wait is matched on that tag.
