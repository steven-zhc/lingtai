# #1204: how an attempt's ending gets written to the ticket

## Where it goes

All four new commands, and the change to `release`, go in `packages/conductor/src/ticket/commands.ts`. That path is the owner: `aggregate-owners.test.ts:33` exempts `packages/conductor/src/ticket/`. The owner is a set of exported `…Effect` functions, not a class (`claimTicketEffect`, `continueTicketEffect`, `releaseTicketEffect`, `releaseDeadWorkerEffect`), so the new ones should look the same:

- `refuseDispatchEffect(ticketId, { runtime, missing }, store, options)`
- `landTicketEffect(ticketId, { mergeCommit, base, endPlan }, store, options)`
- `holdTicketEffect(ticketId, { waitId, reason, endPlan }, store, options)`
- `recordEndPlanEffect(store, ticketId, actions, outcome)`
- `releaseTicketEffect(…)` gains an end plan

Each command builds its own ticket event with `parsePayload`. `conduct.ts` no longer writes a `type: 'TicketLanded'` literal.

`endPlan` is passed in as the `ToAppend[]` that the pass already resolved, through `recordEnd` (`conduct.ts:3350-3353`). `land` and `hold` must not resolve it again. The pass resolved it against the recipe before the ending, and the commands should not need the recipe.

## Two failure styles, kept as they are today

The two groups fail differently today, and the change keeps both styles.

**`refuseDispatch`, `land`, `hold` and `recordEndPlan` die on a refused read or append.**
- Use `Effect.promise` for the read and the append, as `appendAt` does (`conduct.ts:776-781`). Do not use `Effect.tryPromise`.
- Their call sites in `conduct.ts` go through `appendNow` today, and `appendNow` only records the failure because it is a defect (`Effect.tapDefect`, `:808-813`).
- Pull the tap out of `appendNow` into a local wrapper, e.g. `const remembered = <A>(e: Effect.Effect<A>) => e.pipe(Effect.tapDefect(d => Effect.sync(() => { unappended ??= d })))`. `appendNow` becomes `remembered(appendAt(…))`, because it still serves the run-stream appends. Each owner call that used to be `appendNow(ticketId, …)` becomes `remembered(landTicketEffect(…))`, and so on.
- `recordLanding` (`:2703-2712`) keeps its exact chain: `remembered(land…)` → `catchDefect(fail)` → `retry({ times: 2 })`. The command reads again on every try, which matches `appendAt` reading `store.read` each time.

**`release` keeps its typed failure (`tryPromise`, `commands.ts:279-282`).** Its one caller wraps it in `Effect.result` (`conduct.ts:1637-1639`).

**Version.** Read through `readThroughSnapshot(store, ticketReducer, ticketId, 'all', options)` and append at `state.version`, as `releaseWith` does. Pass `ticketSnapshots` from `conduct.ts`. There is no transition and no refusal: the ticket says "none of these writers checks the ticket's state today". A `ConcurrencyError` stays a defect, as it is through `appendAt`. Do not add a retry and do not catch `lost-race`.

## The release and its plan

Add `endPlan?: readonly ToAppend[]` to `releaseTicketEffect`. Add it to its `options` bag (`SnapshotReadOptions & { endPlan? }`), not as a seventh positional argument. `releaseWith` appends `[...decided.events, ...(endPlan ?? [])]` in one `store.append`.

At `conduct.ts:1636-1659`, pass `endPlan` only under the existing guard (`endedAs === 'failed' && endPlan.length > 0`). Then:
- On success, `endResolved = endPlan` when the plan was passed.
- On failure, keep the existing `log(...)` line and leave `endResolved` as `[]`.
- Delete the second `appendAt` block and its `log('end actions not recorded…')`. That outcome now has the same cause as the release failing.

A declined release cannot happen here: `releaseTransition` with `by: 'run'` always returns `ok: true` (`domain/src/ticket.ts:892-893`). Still, check `gave.success.ok` before setting `endResolved`, so a future decline cannot record a plan it never wrote.

Rewrite the comment at `conduct.ts:1534-1537`. It currently says *"Where the ending is a release the two cannot be one transaction — `releaseTicket` owns its own read and version — and there the order is what carries the rule"*, which is now false. It should say every ending carries its plan in one append. Also delete `end-step.ts:154-160`'s *"For the one caller that cannot batch…"*, together with the function it describes.

## `recordEndPlan`

Move `appendEndActionsEffect` (`end-step.ts:162-180`) into `commands.ts` as `recordEndPlanEffect` with the same signature and return value: the `ToAppend[]` written, which `tellGitHubAboutEffect` carries out. Keep its current `tryPromise` style, because `cli end` answers every failure in `matchCauseEffect` (`apps/cli/src/end.ts:128-134`), so nothing in that path relies on a defect.

`commands.ts` imports `resolveEndActions` from `../end-step.ts`. That creates no cycle: `end-step.ts` imports only domain, event-store and recipe (`:41-47`).

Update the two places that point at the old function:
- `apps/cli/src/end.ts:25,116` now import from the owner.
- `packages/conductor/src/index.ts:100` exports `recordEndPlanEffect` in place of `appendEndActionsEffect`.

## Bookkeeping and the gates

- **`aggregate-owners.baseline.json`.** Remove the `conduct.ts` (5) and `end-step.ts` (1) entries. The test is red in both directions (`aggregate-owners.test.ts:112-116`), so any stray ticket append left behind will show up there.
- **The `ELSEWHERE` anchor.** `scripts/events.ts:107-112` points at `end-step.ts`'s `type: 'EndActionsResolved',`. That line stays in `resolveEndActions` (`end-step.ts:147`), so the anchor holds. Check it with `events-json.test.ts`.
- **`STREAMS` and the generated file.** Change `STREAMS.EndActionsResolved` to `['ticket-']` and regenerate `doc/events.json` with the repository's script.
- **The Effect ratchet.** Every new command is an `Effect.gen` with no `async` and no `Effect.run*`, so `effect-ratchet.baseline.json` only stays the same or goes down.

## Tests

Put them in `packages/conductor/unit/`, beside `ticket-release.test.ts`, using `createMemoryEventStore()` with a wrapper whose `append` rejects.

- `landTicketEffect` with a plan, against a store that refuses: the run dies, and reading the stream back shows neither `TicketLanded` nor `EndActionsResolved`.
- `releaseTicketEffect` given a plan, against a store that refuses: the failure is typed, and the stream has neither `TicketReleased` nor `EndActionsResolved`.
- Success cases: one `append` call carrying both events, for `land`, `hold`, and `release` with a plan. Assert by counting `append` calls on the wrapper, which is what pins down "one append".

All of this runs in the unit half. Nothing here needs `pnpm test:integration`.
