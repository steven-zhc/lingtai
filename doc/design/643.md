## The shape

There are two inputs, and they come from different places. The ticket body needs no new read. The advice needs one, and it can be read at only one point in the code.

### The body is already current. Only `fixBrief` drops it.

- Every `conduct` call fetches the issue once, before the claim: `const issue = await tickets.getIssue(options.issue)` (`packages/conductor/src/conduct.ts:2223`). It becomes `brief.ticket` with `body: issue.body` (`conduct.ts:2301`).
- A granted round is a **continuation**, which is a separate `conduct` call (`conduct.ts:1007`, `options.continuing`). That call reaches line 2223 again.
- So a `Done when` row added before the grant is already in `brief.ticket.body` when `fixRound` runs. **Do not add a second `getIssue`.** "Re-read at the round" holds because the call is new.
- `fixRound` already receives `brief` (`conduct.ts:3632`). Pass `brief.ticket.body` to `fixBrief` as a new **required** field (`ticket: { title, body }` or just `body`).
- Make it required, not optional. The #603 failure had no triage at all, so the body has to reach every round.

### The advice: the granted continuation's own wait, read once

- Compute it inside the `continuation` block (`conduct.ts:1007-1072`), next to `grant`/`findings`. That block already has what you need:
  - `before`, the ticket's stream, read at `conduct.ts:994`. Triage has finished before anyone grants.
  - `approvedWaitId`, the wait this continuation resumes. It is stored as `resumedWaitId` (`conduct.ts:1040-1042`: *"a fresh UUID per wait, so it is what tells one continuation's judge from the next one's (#580)"*).
  - `granted`, which is `folded.lifecycle.grantRef !== undefined` (`conduct.ts:1013`).
- Read the advice with `triageFactsOf(before, approvedWaitId)` (`packages/domain/src/read-model.ts:108`). It already applies 0118 §3's latest-attempt rule. Its doc comment says: *"a `WaitTriaged` for an earlier attempt, or for a `waitId` with no `TriageStarted` at all, is never read."* Do not write a second fold.
- Keep the advice only when `result?._tag === 'TriageAdvised' && result.cause._tag === 'FixableLines' && result.cause.fixes.length > 0`. `FixableLines` is defined at `packages/domain/src/wait.ts:644`. `fixes` may be empty, and an empty list counts as no advice, so the brief stays unchanged.
- Gate it on **`granted`**, not on `grant`. `grant` is only set when `grantCriterion(reason) !== null` (`conduct.ts:1045`). A person who granted a round on advice they read has granted it whether or not the reason carried findings.
- Store the result as `advice?: readonly LineFix[]` on the continuation object. `fixRound` is a closure in the same scope and already reads `continuation?.grant` (`conduct.ts:3749`), so read `continuation?.advice` there and pass it to `fixBrief`. Do not route it through `ActionContext` or `Brief`. Nothing else consumes it, and the port interface (`packages/conductor/src/pass-steps.ts:286`) should not grow a field for one caller.

Why this placement already covers both of the ticket's "stale advice" traps:

- **An earlier wait.** The key is `approvedWaitId` and nothing else. A previous wait on the same ticket has a different `waitId`, so its `WaitTriaged` never matches.
- **An earlier attempt.** `triageFactsOf` handles it.
- **Mechanical rounds.** A first claim and a non-granted `Approve` continuation both leave `granted` false, so no advice is attached. A granted lap is one round long. The comment at `conduct.ts:3746-3748` says: *"The lap a person's grant paid for is capped at one round (`runPass`'s `roundLimit`)"*. So advice attached to a granted continuation reaches exactly the round the person paid for.

### Rendering in `fixBrief` (`packages/conductor/src/fix.ts:462`)

- Order: `${evidence}`, then the advice section if present, then the ticket section, then `## The change under review`. Leave every existing sentence as it is.
- **The advice section**, with a heading like *what the person who granted this round accepted*:
  - One line per fix: `` `path:line` — what ``. When `line === null`, print just `path`, as `findingsHalf` does with `f.line === null ? f.file : …`.
  - One sentence framing it as evidence, not the criterion: *the findings above are what the re-review asks about. This is how the person expects them to be met, so depart from it only for a reason you state in your final message.*
- **The ticket section.** Paste the body raw, as `renderPrompt` does (`packages/conductor/src/prompt.ts:231`, `.replaceAll('{{body}}', ticket.body)`).
  - Frame it with one sentence: *this is what the cold reviewer held the change against. It is context for the findings, not the job handed to you again.*
  - That sentence carries the decision that matters (next section).
- With no `advice`, the output must equal what `fixBrief` returns for the same input without the field. The ticket's "byte-for-byte what it is today" can only mean this: the body is unconditional now, so the brief does change for every round. That is the test to write for the third `Done when`.

### The ADR this changes, and the test comment that defends the old reading

0108 §5 (`doc/decisions/0108-a-refusal-buys-a-round.md:61`) says: *"The fixer gets the findings and the diff, not the reasoning … no plan, transcript or session of the implementer's."* §3 says a round is `implement` again *"with `fixBrief` … instead of the ticket prompt"*.

- The ticket is not the implementer's reasoning. It is what the cold reviewer already holds. 0038 §3 (archived) excluded reasoning because *"a fixer handed the reasoning that produced the defect inherits the reasoning that produced the defect"*. The ticket did not produce the defect.
- So this does not contradict the decision. It does change §5's list of what the fixer gets.
- **Edit 0108 §5 in place.** Since 2026-10-01 the CLAUDE.md rule is *"A decision that changes is an edit to its topic's ADR, not a new file beside it"*. Add the ticket body and the granted wait's `FixableLines` advice to the list, keep "not the reasoning", and say the findings remain the criterion. Leave §3's "instead of the ticket prompt" alone: the round still does not get `renderPrompt`.
- `packages/conductor/unit/fix.test.ts:227-230` has the comment *"The task is bounded, and the ticket is not part of it"*. Its assertion (`/Make each sequence stop producing its outcome/`) stays true. Reword the comment so it says the ticket is context and the criterion is still the scenarios. Keep the assertion.
- Every `fixBrief({...})` call in `fix.test.ts` (lines 194, 300 and 313) gains the new required field.

### Tests, all unit

- **`fix.test.ts`, at the `fixBrief` level:**
  - The brief contains the body passed in.
  - It contains every fix's `path`, `line` and `what`, and prints a `null` line as the path alone.
  - Without `advice`, the output equals the call with `advice: undefined` / `[]`.
- **The selection rules, tested without `conduct`:** latest attempt only, matching wait only, `FixableLines` only, and only when granted. The `conduct` closure cannot be unit-tested.
  - Pull the selection into a small pure function, e.g. `grantedAdviceOf(events, waitId)` in `fix.ts` or beside `triageFactsOf`, and test it there.
  - Build fixtures with the `WaitTriaged`/`TriageStarted` helpers in `packages/domain/test/events.ts:116`. Cover: earlier attempt advised and latest not; another wait's `FixableLines`; `UndecidedQuestion` on this wait; `TriageFailed`.
- **"The body as it reads at the round, not at claim"** depends on line 2223 running once per continuation. A unit test cannot reach that. The unit-level stand-in: `fixBrief` renders the body it is given, and `fixRound` passes `brief.ticket.body`. The read itself is covered by the existing continuation path in the integration half, which runs after the merge.

The log answers whether this works in production. On a granted round, check the `WaitTriaged{waitId, attempt, result.cause._tag}` on the ticket stream against the `PassRouted{next: FixRound}` and the fixer's `RunSpent{grant: <waitId>}` (`conduct.ts:3749`). `grant` should name the same `waitId` the advice was read from.
