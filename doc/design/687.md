# #687 — design note: `ticket_report`

## Where it goes

- `packages/projector/src/ticket-report.ts`. Build it the way `spend.ts` is built: `ticketReportProjectionWith(ports: { snapshot })` plus a default `ticketReportProjection` that uses `readRateSnapshot()` (`spend.ts:79`, `spend.ts:267`). Export both from `packages/projector/src/index.ts` next to `spendProjection` (`index.ts:65`).
- Put the rules in a **pure reducer** in the same file and keep the SQL out of it: `foldTicketEvent(state, event, link) → state`. `apply` does only read-modify-write around it.
  - This is the main decision here. The Done-when asks for a unit test per §2 rule, and a test against a SQLite file is integration (CLAUDE.md: *"A temporary directory is still the filesystem"*).
  - The projection tests that exist are all integration (`packages/projector/integration/spend-rebuild.test.ts`, `spend-estimate.test.ts`).
  - So every rule test calls the reducer in `packages/projector/unit/ticket-report.test.ts`. One integration test (rebuild equals live fold, on both stores, modelled on `spend-rebuild.test.ts`) covers the SQL. Nobody can run that before the merge, so the unit tests carry the claims.
- Wiring. Every list that names `spend` today gets `ticket_report`:
  - `PROJECTIONS` (`apps/cli/src/projection.ts:28`)
  - `PROJECTION_NAMES` (`apps/cli/src/commands.ts:33`). The ticket does not mention this one, and `projection rebuild ticket_report` is refused without it.
  - `withProjector`'s `followSecondary`/`releaseSecondary` pairs (`apps/cli/src/projector.ts:185,199`, and the daemon path at `:255,266`)
  - `doctor`'s shape list (`apps/cli/src/doctor.ts:668`)
  - `ESTIMATE_PROJECTIONS` (`apps/cli/src/rates.ts:59`). Its comment says *"`ticket_report` (0123) joins this list when it lands"*. This is how the ticket's edge *"unknown, until #680's rebuild"* happens.
  - `doc/operating.md:2164-2173`, which says *"there are three"* and lists the rebuild commands.
- **The live-runner hold has to cover it too.** `trackLiveSpend` only registers a runner whose name is `spendProjection.name` (`projector.ts:90-92`). `rebuildEstimates` calls `holdLiveSpend()` and then rebuilds every `ESTIMATE_PROJECTIONS` entry (`rates.ts:101-102`). If `ticket_report` is in the list but not held, its live follower runs through the rewind. The fenced advance from #680 (`24bcc3f0`) refuses the stale commit, but that makes the follower fail rather than wait.
  - Widen the name test to both estimate projections, and rename `holdLiveSpend` to `holdLiveEstimates` if that reads better.
  - Leave `day-ceiling.ts`'s spend hold alone: the ceiling reads `spend` only.

## Storage

**One row per ticket in `ticket_report`.** Scalar columns are the ones the next ticket filters and sorts on:

- `ticket` (pk), `project`, `kind`
- `outcome`, `outcome_at`
- `passes`, `fix_rounds`
- `machine_ms`, `intervals_empty`, `intervals_open`
- `unknown_claims`

The lists are `jsonb`:

- `pass_times` (the `at` of each claim)
- `reviews`: `{seq, at, round, blocking, cleared}`
- `waits`: `{waitId, at, reason, triage, resolution}`
- `cost`: keyed by purpose, each `{reportedCents, reportedRuns, estimatedUsd, estimatedRuns, unknown}`

`sqlite.ts` stores `jsonb` as text (`sqlite.ts:207-211`), so parse it when it arrives as a string, the way `task-view.ts:680` does. Do not build the lists with SQL JSON operators: `translate` only maps `|| jsonb_build_object` (`sqlite.ts:199-204`).

**Helper tables.** The fold needs state that has to survive a batch boundary. The `claimed` set kept by `claimsOf` does not survive one, which `spend.ts:153-157` says outright: *"the table decides, not the helper's `claimed` set (which a batch boundary or checkpoint would empty)"*. These are the projection's own tables and do not belong to `spend`, because 0123 §6 says *"never reads another projection's table"*:

- `ticket_report_stream (stream_id pk, ticket)`: the same three links as `spend_stream`. `RunStarted.ticketId`, `TicketClaimed`/`TicketContinued.runId` → ticket stream, and `DiscussionRequested` → `chatStream(chatId)` (`spend.ts:143-188`).
- `ticket_report_claim (ticket, run_id, has_action, pk(ticket, run_id))`: claims only. Feed `claimShapeOf(event, claimed)` (`packages/domain/src/claims.ts:23`) from `select run_id … where ticket = $1`, so an old-form continuation is recognised across batches.
- `ticket_report_round (ticket, pass, round, pk(…))`: the distinct `(pass, round)` pairs. Insert with `on conflict do nothing`, and increment `fix_rounds` only when a row was actually inserted.
- `ticket_report_interval (ticket, opened_seq, run_id, opened_at, life_seq, life_at, pk(ticket, opened_seq))`: the intervals that are still open.

`reset` drops all five tables. `create` must not read its results (`shape.ts:154-157`).

## The rules, as the fold applies them

- **Pass.**
  - A `claim` shape adds 1 to `passes`, appends to `pass_times` and inserts a `ticket_report_claim` row.
  - A `continuation` shape (either form) adds nothing.
  - Both shapes open an interval.
- **Kind.** The latest non-null `kind` on a `claim`-shaped `TicketClaimed`. This is the same as `spend_kind` (`spend.ts:169-176`).
  - 0123 §2 says both *"its last claim's `kind`"* and *"whose every claim has a null kind is unclassified"*. Those only agree if a null never clears the kind, so it never does.
  - An old-form continuation never sets the kind.
- **Outcome.**
  - `landed` if any `TicketLanded`; `outcome_at` is the last one.
  - Otherwise `closed` if the last `TicketClosed` comes after the last claim (compare `seq`s, and keep `last_claim_seq` on the row).
  - Otherwise `open`. A claim after a close sets it back to `open`.
- **Fix rounds.** Count `RunSpent` with `for._tag === 'Action'` and `round >= 1`, linked to the ticket, keyed `(event.streamId, round)`. They are summed over every pass. The #658 fixture: 4 passes producing 14 rounds folds to 14, not to the maximum for any one pass.
- **Reviews.** A `StepEnded` with `outcome.step === 'review'`, linked through `runId` (the pass stream id is the runId, per `spend.ts:165`).
  - `blocking` is the count of findings with severity `blocker`/`major` (`SEVERITIES`, `vocabulary.ts:119`) across the `Completed` assessments (`action.ts:30-33`).
  - Also store `cleared = actions.every(cleared)` (`action.ts:235`). Under 0123 §2's literal rule (*"a review with none of those passed"*), an `Interrupted` review has zero blockers and would count as passed. Storing both lets the next ticket decide the passed rule without a rebuild.
- **Waits.** `WaitStarted` on the ticket stream pushes `{waitId, at, reason: reason._tag}`.
  - `WaitTriaged` replaces `triage` only when its `attempt` is at least the one stored. The comment at `events.ts:2014-2016` says *"a reader takes only the latest attempt's result"*. Store `{tag: result._tag, cause: result.cause?._tag ?? null}`.
  - `WaitResolved` sets `resolution: resolution._tag`.
- **Machine time.**
  - A claim or continuation inserts an interval row.
  - **Sign of life:**
    - any event whose `streamId` is that interval's `run_id`, with `seq` greater than `opened_seq`;
    - any `IntegrationAttempted`/`IntegrationRefused`/`IntegrationSucceeded` whose `ticketId` names this ticket (`events.ts:1218-1236`).

    Either one sets `life_seq/life_at` on the open intervals it matches. Before matching, confirm what the `ticketId` passed at `packages/repo/src/integrate.ts:673` is. `RunStarted.ticketId` is the `ticket-…` stream id (`spend.ts:148`). If this field is something else, normalise it rather than letting the match quietly miss.
  - **Ending:** `TicketLanded`, `WaitStarted`, `TicketReleased` or `TicketClosed` on the ticket stream closes **every** open interval of that ticket. Each one adds `life_at − opened_at`, or 1 to `intervals_empty` if it had no sign of life, and its row is deleted.
  - The opening and ending events are never signs of life themselves. A triage `RunSpent` on the ticket stream is not one either, so triage time is excluded and its money is not.
  - `intervals_open` is the number of rows still open: in flight, or abandoned by a conductor that died. The report's *"passes it skipped"* reads this.
- **Cost.**
  - Purpose is `Action` round 0 → `Work`, `Action` round ≥ 1 → `Answering`, and otherwise `for._tag`. This copies `purposeOf` (`apps/board/src/lib/spend.ts:127-130`), which the projector cannot import.
  - A unit test in `apps/board` pins the copy: on the same rows, `billOf` and the fold's `cost` must agree. That direction of import is legal.
  - Reported is `Math.round(costUsd * 100)` summed, which is `billOf`'s cents rule. Otherwise use `estimateRow({at, usage}, snapshot)` exactly as `spend.ts:216-220` does, with the snapshot read at most once per batch. Otherwise `unknown += 1`.
  - Never add these three together.
- **Unknown claims.** An `Action` `RunSpent` on a pass stream sets `has_action` on its claim row. `unknown_claims` is the count of that ticket's claims with `has_action = false`, recomputed whenever either changes. A continuation has no claim row, so it adds nothing (0123 §2, `withNoSpendFallback`, `apps/board/src/lib/spend.ts:113`).
  - A `Judge` `RunSpent` alone still leaves that claim unknown, which is the board's rule.

## Edges

- **Event order across streams.**
  - The `RunSpent` of a pass stream can arrive before that stream has any link. For example, an `admit` refusal leaves no `RunStarted`, but `TicketClaimed` links it first (`spend.ts:48-54`).
  - A `RunSpent` with no link at all is dropped here, since there is no ticket row to put it on. This is unlike `spend`, which keeps such rows with `ticket` null.
- **Two passes at once (0122).** Every write is keyed by ticket, and intervals are keyed by `(ticket, opened_seq)`, so two tickets' passes never touch each other's rows.
- **Restart mid-batch.** The batch and the checkpoint commit in one transaction, which is the store's existing contract. All state lives in tables, so replaying from the checkpoint produces the same rows.
- **Rebuild.** The integration test folds a fixture live in two batches split across a claim and its old-form continuation, then rebuilds, and asserts the rows are identical. A unit test does the same split against the reducer with state carried between calls.
- **Price changes on the same day** (0123 §6, `mergeSnapshot`). Accepted as the ADR says. Nothing to build.
- **Cost to later tickets.** One more runner in every appending process, and one more table pair in doctor's shape check. A column added later is drift and is fixed by a rebuild (`shape.ts:1-33`).

## Not in this change

Do not add a `readTicketReport` store method or a board reader. The aggregation and the page are the next tickets, and a reader with nobody calling it is a shape nobody verifies.
