# #1525 design note: what `doc/design/1523.md` does not already settle

Read this beside the ticket and `doc/design/1523.md`. That note is the design. This one covers four things the ticket gets wrong or leaves open where it meets today's code, plus the order to do the work in. Line numbers are at `3d7cfbc0f`.

## 1. `runGithubBranch` does read project flags. Deleting the loop alone breaks every add that passes one

The ticket says `deferRecipeFlags` goes *"since `runGithubBranch` reads no project flag"*. That is not true today:

- **It refuses them.** `first-project.ts:1416-1422` refuses `--tickets` and `--kinds`. `:1430-1453` refuses thirteen more, with *"a GitHub project asks none of askRecipe's questions here — lingtai add asks them once its recipe exists"*. `init --project github` with no slug still needs that refusal (#431 fix round, finding 2). It reaches it through `init.ts:831`, which is #1526's.
- **It reads `--main`** as a named base for the registration (`:1500`, `:1612`, `base: { ref: baseFlag, named: true }`). Today the slug path never gets there, because `add-github.ts:606-607` has already deleted `main` (`PROJECT_FLAGS` includes it, `wizard-options.ts:52-54`).

So the only thing keeping `lingtai add owner/repo --agent codex` from being refused at `:1446` is the mutation at `add-github.ts:606-607`. Delete it without a replacement and every flagged add exits 1.

**The shape.** Write one pure helper, `withoutProjectFlags(flags)`, that returns a copy and changes nothing. Call it at the two places that hand flags to `chooseFirstProjectEffect`:

- `add.ts:407`, where `handed` is already built for `github-auth`: `handed = { ...withoutProjectFlags(flags), …github-auth }`.
- `add.ts:219`, the bare-`add` picker: `holdsBack ? withoutProjectFlags(flags) : flags`.

Then `chooseFirstProjectEffect` loses its `deferRecipeFlags` parameter (`first-project.ts:423`, `:500-502`), and `runGithubBranch` keeps its refusal for the slugless callers, word for word.

The helper omits exactly what the loop deletes today. That is the list's flags minus `defaults`, so the registration still takes its base from the recipe, never from `--main`. `runGithubBranch` reads no `defaults` (I grepped `:1404-1801` and found none), so either choice behaves the same. Omitting today's set keeps the hand-off identical.

The ticket's real objection to the loop is that it mutates the caller's object and leaks into `addCommand`. The helper removes that and nothing else. It is not a compatibility branch.

## 2. The list's flags include `defaults`, and two consumers outside this path read that list

The ticket says the union of the entries' `flags` is `recipeOptions` minus `base`, `yes` and `no-color`. That includes `defaults`, which is the *use every default?* entry's flag. Today's `PROJECT_FLAGS` also leaves out `defaults` (`wizard-options.ts:52-54`).

- **Where the list of flags lives.** Export it from `packages/setup/src/project-list.ts`, built from the descriptors' `flags`. `wizard-options.ts` imports it and keeps no copy.
- **Where the equality test lives.** It goes in `apps/cli/unit/`, not in `packages/setup/unit/`, because it needs `recipeOptions`, and `@lingtai/setup` must not import `apps/cli`.
- **`init.ts:628`'s `discardedFlag` would start refusing `init --defaults`** on a machine that has projects. It iterates `PROJECT_FLAGS` and excludes only `sandbox`, `sandbox-hosts`, `mode`, `login` and `personal`. Add `defaults` to that exclusion list. That one word keeps #1526's code doing what it does today. It is not the rework the ticket puts out of scope.
- **`ROUNDS_RETIRED`** (`wizard-options.ts:136`) moves into `@lingtai/setup`, because the `refusal-fixes` entry's `fromFlags` refuses `--rounds` with it. `wizard-options.ts` re-exports it for `init.ts:172` and `first-project.ts:118`.

## 3. Validation moves into `@lingtai/setup`, and the local path imports it back until #1526

The descriptors live in `packages/setup`. The checks they need are in `apps/cli` today:

- `refuseUnlessOffered` and `leftoverRefusal` (`agents.ts:86-135`);
- the branch-name checks in `team.ts`;
- the kinds and tickets checks in `source.ts`;
- the limit checks in `landing.ts`.

A package cannot import an app, so each check moves into `packages/setup`, with its words unchanged, next to the descriptor that uses it.

`askRecipeEffect` stays, for `runLocalBranch` (`first-project.ts:1156`), until #1526, and it calls `askAgents`, `askLanding` and the rest. So:

- **Old `ask*` functions keep their bodies.** Their inline checks become calls to the moved functions, so each check exists once.
- **New askers call the inner pieces.** `project-askers.ts` calls the `questionEffect` pieces that design §4 names (`agents.ts:254`, `:280`, `:303`, `:379` and so on). Export each one as its own function, and have the old `ask*` call those same functions.
- **The judge stays in `askAgents` for now.** Its code (`agents.ts:341-363`, `:399`) still serves the local path, so #1526 deletes it, not this ticket. The new path gets its judge only from the `findings-judge` derive entry.

This is the "split at the seams" the operator asked for. The old caller does not survive alongside the new one on the GitHub path: `add-github.ts` imports none of it.

## 4. Before the list, in the list, after it

- the auth election and the `github` entry (`:316-342`);
- the `gh` access check, or the App installation check (`:350-418`);

The *recipe unreadable* refusal also comes before the first entry. It is `add.ts:339-348` on a rerun; add the same check for a file that is there but whose project is not registered.

**The seeds become `pending`'s first entries.** Today the seeds are `branch.main`, `env.plantAt` and `steps.end` (`add-github.ts:468-480`). `env.plantAt` and `steps.end` go into `ctx.pending` before the walk, on a new recipe only. `branch.main` does not: the `branch` entry writes it.

- **Solo.** The entry's `systemDefault` is the default-branch port.
- **Team.** It writes `branch.personal`, and also `branch.main`, from `--main` or the default branch (`recipe-flow.ts:413-430`).
- **A failed read.** Today `:481-487` refuses with *"could not read … default branch — … Pass --main <branch>"*. That sentence becomes the port's refusal through `validate`. Never an absent value.

**The single set.** After the walk:

1. `draft.set(ctx.pending)` runs once.
2. `draft.changes()` is the `answers.changes` that `add.ts:363` already tests for emptiness. That test keeps working, and a rerun that takes every default gets an unchanged card with no `ProjectConfigured`.
3. Then `make`: the code at `:615-624`, unchanged.
4. Then the deferred token (`:626-631`), reading `previewSetup` over the final answers.

`kept` is `ADD_KEPT` (`recipe-flow.ts:54`) on the add and `world.project.kept` on `init`. Pass it as `input.kept`, a constant.

**The trial.** It needs `reach` and `ref` (`add-github.ts:576-593`). Where either is missing, the `trial` entry's `applies` is false. Print the line `setup-build.ts` prints today when there is no build port, so the words do not change.

**Delete these:**

- `run = Effect.runPromiseWith(…)` (`:517`), with the two promise ports it served (`:574`, `:596`);
- `RecipeAt.defaultBranch` and `history`.

The ratchet does not count `runPromiseWith`, so expect no change to the baseline. Every port is an Effect, and there is no `async`.

## 5. One gap that stays open

Today the `github` entry writes `github.auth` to `config.yml` before any project question:

- through `deps.githubAuth` (`add-github.ts:335`);
- through `add.ts:213` on the bare add.

ADR 0125 (`:133-136`) says a Ctrl+C anywhere in the list *"leaves `config.yml` and the recipe as they were"*. The ticket's Ctrl+C rule is about the project list and the draft, so this ticket does not change the machine entry's write. That entry is the machine list's own write model, and moving it is `init`'s work (#1526).

Keep the interrupt test's claims to *no recipe file, no branch, no registration*. Say in the commit body that `github.auth` can still be written before an interrupt, so a reviewer does not read the test as covering it. This does not contradict the ADR's decision; the code has not caught up with it yet. It needs a backlog entry, not a superseding ADR.

## 6. Tests, and what only integration sees

- **The end-to-end add test** is a unit test. It drives `githubProjectEffect` with the following fakes:
  - fake `githubDeps` (`ghAccess`, `defaultBranch`, `reader`, a client that records `createRef`);
  - `createMemoryEventStore()`;
  - a `ProjectFiles` port over memory.

  `apps/cli/unit/add-github-gh.test.ts` already builds most of this world.
- **The interrupt test** makes the `kinds` asker return `Effect.interrupt`. It asserts that the files port has no recipe, the client recorded no `createRef`, and the store has no `ProjectConfigured` (`events` type `ProjectConfigured`, field `project`).
- **The tests pinned to the old structure** are rewritten against the list's entries, not kept:
  - `add-github.test.ts`
  - `add-github-gh.test.ts`
  - `team.test.ts`
  - `recipe-flow.test.ts` (the parts about the GitHub path)
  - `add-from-page-equals-add.test.ts` (rerun it, and change it only where the list's order changed what it walks)
- **Integration cannot run in a pass.** `apps/cli/integration/init.test.ts` drives `init --github` through real git, and it takes 803 s, so nothing checks it before the merge. Two unit claims stand in for it:
  - the entries test for `add owner/repo`;
  - the same walk through `init --github` (`init.ts:802` calls the same `githubProjectEffect`), asserting the same `ListResult.entries.map(e => [e.id, e.asked])`.

## 7. Order of work, so nothing lands half-built

The work is too large to land in pieces, so build in this order and commit only once the last step is green:

1. **The generic runner and the machine list.** Move the runner into `setup-list.ts`, put `machineQuestions` on the generic shape, and keep its four descriptors ignoring `ctx`. `pnpm test` must be green here before anything else.
2. **The moved checks.** Move the validators into `@lingtai/setup` (§3), and have the old `ask*` call them.
3. **The new files.** Write `project-list.ts` and `project-askers.ts`.
4. **The GitHub path.** Rewire `add-github.ts`, add `withoutProjectFlags` (§1), and delete the loop and `deferRecipeFlags`.
5. **The tests.** Rewrite them, then run `pnpm typecheck` and `HOME=/nonexistent pnpm test`.

If step 4 does not fit in this pass, stop and ask at `implement`, as the ticket says. Do not commit steps 1–3 alone.
