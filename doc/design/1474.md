# #1474: how the change is laid out

## Where the refusal sits: before any branch is made, and again at the write

On a rerun the recipe is still written once, through `applySetup` → `changeRecipe` (`packages/setup/src/apply-setup.ts:91-106`, *"Write the recipe once — `changeRecipe`, the file and then the event naming `by`"*). The team-to-solo check is already on that path (`packages/project/src/change.ts:178-193`). A refusal there comes back as `SetupWriteError` before `register` runs (`apply-setup.ts:105`, *"A refusal is passed up by name, never reported as written"*). So the refusal needs no new path to the write. The draft writes inside `askRecipe` (`writeOrRefuse(draft, …)`, `recipe-flow.ts:257`, `:339`) only touch the in-memory draft: *"committing a draft is the module's `changeRecipe` over `changes()`"* (`packages/project/src/draft.ts:6`).

The problem is timing. Both callers make branches **after the questions and before `applySetup`**:

- local: `makeBranch()` at `apps/cli/src/first-project.ts:1096-1099`;
- GitHub: `recipeResult.make`, at `apps/cli/src/add-github.ts:612-622`, under the comment *"After every question and before `applySetup` writes the recipe"*.

Suppose a rerun moves team to solo, also changes the working branch, and has a draft pending. It would cut the new branch first, and `changeRecipe` would refuse afterwards. A branch is then left behind by a rerun that "wrote nothing", which breaks the `Done when`.

**Decision:** split the check out of `changeRecipe` into an exported Effect in `packages/project/src/change.ts`. For example, `modeSwitchRefusal(project, currentText, nextIsTeam, store)` returns `string | null`, built from the same `listPrs`/`isOpen`/`draftIn` read and `modeSwitchMessage`.

- `changeRecipe` calls this Effect itself, so the sentence and the read exist in one place only.
- The rerun calls it as soon as the mode answer is `solo` on a recipe whose `mode` is `team`. That is right after `askMode` in `first-project.ts:675`, and right after `askMode` in `recipe-flow.ts:262` for GitHub. A refusal there returns `{ refused }` with `world.kept` / `askKept`, before any later question is asked and before any branch is made.
- A failed read refuses too. `change.ts:181` says *"A failed read fails the change: never *nothing open*"*.

`changeRecipe`'s own check stays the authority. A Submit that lands between the early check and the write is still refused there. That is the same reason `change.ts:182` gives for one read rather than two.

This adds no way past the refusal, and it must not become one. Without it, the early check would be the only check.

`askMode` (`apps/cli/src/team.ts:49`, `fallback: 'team'`) and `askSandbox` (`apps/cli/src/sandbox-step.ts:43`, `fallback: 'on'`; `:58`, `'none'`) each take an optional `current` that replaces the fallback. `askPersonal` already takes `fallback` (`team.ts:104`). Only the value passed in changes.

A rerun's answer equal to the current value must produce no `RecipeChange`, just as #1473 requires (*"writes nothing, registers nothing"*, `first-project.ts:1102-1104`). `teamChanges` (`recipe-flow.ts:331-335`) is built unconditionally today. Filter it against the draft so that an unchanged team rerun stays `unchanged: true`. Do the same for the sandbox changes.

Database: when the settled Postgres URL does not answer, the rerun still offers it as the default. `validate` refuses it by name (*"does not answer — … Nothing was written"*, `init.ts:1036`) and asks again. An answer equal to the settled store skips `world.machine.write` entirely. Do not rewrite the same text.

## The working branch is cut from the old one

- **Local:** `validate` sets `source = mainBranch` for an absent personal branch (`first-project.ts:714` area, *"the branch to make it from"*). On a rerun, `source` is the recipe's current working branch, if that branch exists: `branch.personal` in team mode, `branch.main` in solo mode. Only a first run, or a solo-to-team change with no personal branch yet, uses `mainBranch`.
- **GitHub:** set `make = { name, from: mainBranch }` (`recipe-flow.ts:328`) to `from: <old branch.personal>` on a team rerun. The confirmation prompt (`:314`, *"Make it from origin/${mainBranch} and push it?"*) and its `flag` text then name `from`, not `mainBranch`. The helper at `add-github.ts:257` (*"read first, then made, so a failed read makes nothing"*) already takes `from`.

`trialBase` (`first-project.ts:930`) keeps cutting at the main that a deferred branch would be made from. On a rerun, that is the old working branch.

## The card: one list of lines

Add `leftBehind?: readonly string[]` to `SetupCardFacts` (`apps/cli/src/setup-card.ts:50`), rendered under the heading by `renderSetupCard` (`:205`). Both callers compute it by comparing the recipe before the rerun with `finalRecipe` (`first-project.ts:1128`), and `init.ts` adds the store's line:

- **new working branch, did not exist:** *"`<new>` was made from `<old>`; `<old>` is kept and may be deleted"*.
- **new working branch, existed:** the commits on `<old>` that are not on `<new>`. Local: `world.git(toplevel, ['log', '--oneline', `${new}..${old}`])`. GitHub: `packages/github/src/client.ts:296` has no compare call. Add one to the Effect interface (`GET /compare/{new}...{old}`) as an Effect, not an `async` (the ratchet). Read it **before** the write, as a fact rather than a precondition: if the read fails, the rerun is not refused, and the line says the commits could not be read and gives the `git log origin/<new>..origin/<old>` command.
- **team to solo, nothing pending:** one line saying `<personal>` is kept and everything on it has reached `main`. No git command.
- **another store:** *"the log at `<store>` is new and empty; nothing was copied from `<old>`"*, per ADR 0100 §9.

## Registering again

A rerun that changed anything already calls `register` with `base: final` (`first-project.ts:1165-1174`), and `register` appends `ProjectConfigured`. So a changed `branch.main` is registered on the local path as things stand. Check the GitHub path the same way. It is settled by the newest `ProjectConfigured` event's `base` field equalling the recipe's `branch.main`. That is the field `conduct.ts:134-135` compares.

## Tests (all unit)

The existing rerun tests use fakes for `git`, the store and the terminal (for example `apps/cli/unit/init.test.ts:143`). Record the prompts and the git argv through those fakes:

- **Question list:** run once on an absent file and once on a file written by that run, and compare the recorded `prompt` strings in order. Prompts that name a branch get the same names in both runs from the fixture. Do not normalise the strings.
- **Draft refusal:** seed a `ProjectPrNumbered` event and a landed draft, as `packages/project/unit/pr.test.ts` does, on `createMemoryEventStore()`. Assert:
  - the refusal sentence equals `modeSwitchMessage(…)`;
  - the event count is unchanged and the recipe file is unchanged;
  - no recorded git call whose argv is `branch`, `push` or `update-ref`. With a faked `git`, that stands in for *the personal branch's head unchanged*. A real head is `pnpm test:integration`, which cannot run inside a pass.
- **Branch cut:** "cut at the old tip" is asserted as the argv `['branch', <new>, <old>]` locally, and as `make.from === <old>` on GitHub.
