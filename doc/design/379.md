# Design note for #379: the ticket tables

## Where the drivers go: not in `packages/conductor`

The ticket's **Fix** puts a SQLite implementation and a Postgres implementation in `packages/conductor/src/db-tickets.ts`. That cannot pass, for three reasons:

- `packages/conductor/unit/one-store.test.ts` scans every file in `conductor/src`. It fails on `new pg.` or `from "pg"`, on any mention of `node:sqlite`, and on any `createSqlite…` (lines 48–72). The header says *"There is no exempt file here. … the conductor has none and should have none. It holds no store: it asks one."*
- `packages/env/unit/one-choice.test.ts:61` fails on `createPostgres…(` and `createSqlite…(` anywhere outside `IMPLEMENTATIONS` and `CHOOSERS` (lines 67–83). The ticket says not to change that test, so no new file can be added to either list.
- `packages/event-store/unit/on-postgres.test.ts:69` (`REACHES_POSTGRES = /from ["']pg["']|\bcreateDb\(|\bcreatePostgres[A-Za-z]*\(/`) also fails a file listed in `ON_POSTGRES` whose code *no longer* matches. So the Postgres integration test has to call a `createPostgres…(` factory or import `pg`.

So the change is split this way:

| Piece | File | Notes |
|---|---|---|
| `interface TicketSql` | `packages/event-store/src/ticket-sql.ts` (new) | Only types. Exported from the barrel and from a `./ticket-sql` subpath. |
| Postgres implementation | `packages/event-store/src/queries.ts` | Already in `IMPLEMENTATIONS`, already imports `pg`. Call it `createPostgresTicketSql({ url })`. |
| SQLite implementation | `packages/event-store/src/sqlite.ts` | Already in `IMPLEMENTATIONS`. Call it `createSqliteTicketSql(db: DatabaseSync)`. |
| Selection | `packages/event-store/src/choose.ts` | `processTicketSql()`, exported from `index.ts` beside `processLog`. |
| DDL and `ensureTicketTables(sql)` | `packages/conductor/src/db-tickets.ts` | No driver code: it only takes a `TicketSql`. |

## The seam

```ts
interface TicketSql {
  readonly dialect: 'sqlite' | 'postgres'
  query<T>(text: string, params?: readonly unknown[]): Promise<T[]>
  exec(text: string): Promise<void>
}
```

- **`dialect` is on the seam** because the DDL is different text for each store, and so will a few of #380's statements be. Without it, `ensureTicketTables` cannot choose which DDL to run.
- **Parameters are written Postgres-style, `$1…$n`, for both stores.** The SQLite implementation rewrites `$n` to `?n` before `prepare`. SQLite reads `?NNN` as a numbered positional parameter, so a repeated `$1` still binds once. This is what lets #380 write each statement once. Put this rewrite under a unit test (`$2` used twice, out of order) so it is not left to trust.
- **`exec` takes many statements on SQLite and one on Postgres.** On SQLite, `DatabaseSync.exec` runs several statements in one string. `pg` does too when there are no parameters, but keep `ensureTicketTables` to one `exec` per `CREATE TABLE` so neither store relies on that.
- **Rows come back as each driver gives them.** `timestamptz` comes back as a `Date` from `pg` and as ISO text from SQLite. `BIGSERIAL` comes back as a string from `pg`. Normalising these is #380's job (`parseTimestamptz` exists, `packages/event-store/src/timestamptz.ts`). This ticket only needs to say it in the interface's doc comment.

## Connection lifetime: nothing to close

- **Postgres** follows the precedent in the same file, `createPostgresLogQueries` (`queries.ts:164–186`): *"A connection per question, opened and closed around it … a pool held here would be a connection a short command has to remember to end."* Do the same: a `pg.Client` per call, connected and then `end()`ed. Read the URL per call, so building one never throws.
- **SQLite** shares the log's own handle. `choose.ts:88–89` opens `openSqliteLog(choice.path)` inside `open()`. Keep that `DatabaseSync` and wrap the same one. Never open the file a second time; that is the ticket's "one opener only". `TicketSql` therefore has no `close()`, because the handle belongs to the log.

That changes how `choose.ts` memoises. Today it memoises the `Log` alone (`opening`, line 49). Make `open()` return `{ log, tickets }` and memoise that. Then `processLog()` returns `.log`, and `processTicketSql()` returns `.tickets`. Both go through the one `chosenStore()` call at line 68, so the rule in `one-choice.test.ts:130–141` (only `choose.ts` and `env/src/index.ts` read `chosenStore()`) still holds without editing the test. On Postgres, build it as `createPostgresTicketSql({ url: choice.url })`. Use the written URL, not `postgresUrl()`, for the reason `daemon/src/choose.ts:54–59` gives.

`./sqlite.ts` is still reached only through the existing `await import`, so a Postgres machine still never loads `node:sqlite` (`choose.ts:32–38`).

## Where `ensureTicketTables` is called

**Nowhere, in this ticket.** The ticket says the tables are created "by the adapter on first use", and the adapter is #380. Here, `ensureTicketTables` is exported and tested, and nothing else calls it. Do not call it from `processTicketSql()` or `openSqliteLog`'s `SCHEMA`. Doing so would make every process that opens the log create ticket tables. It would also put them in the event store's schema, and the ticket's **Watch out** keeps them out of there (`schema.ts:17`, *"A database that has `events` is left alone"*).

## Tests

- **Unit: `packages/conductor/unit/db-tickets.test.ts`.** Import `createSqliteTicketSql` and `openSqliteLog` from `@lingtai/event-store/sqlite`, on `':memory:'`. That is the same shape as `projector/unit/drift.test.ts:40,54`. The scans read only `src/`, so a test file may name the factory.
  - Run `ensureTicketTables`, insert a ticket and a comment, run it again.
  - Assert the rows survive and the columns are unchanged (`pragma table_info`).
  - A second run that *does not throw* is not enough on its own to show "running it twice changes nothing". The surviving row is the actual evidence.
  - Also test the `$n` → `?n` rewrite here.
- **Integration: `packages/conductor/integration/db-tickets.test.ts`.**
  - Calls `createPostgresTicketSql({ url: postgresUrl() })`, which satisfies `REACHES_POSTGRES`.
  - Wrapped in `describe.skipIf(!postgresUnderTest())`.
  - Listed in `ON_POSTGRES` with a reason such as `'the Postgres DDL for tickets and ticket_comments — timestamptz and BIGSERIAL'`.
  - The test database is not reset between runs (nothing in `test-support/teardown.ts` drops tables), so the tables may already exist when it starts. Use a `project` value unique to the run, and delete the rows it wrote.
  - Run only this file: `pnpm vitest run --project integration packages/conductor/integration/db-tickets.test.ts`. **Nothing in the `build` step can check it**, because `pnpm test` is the unit half. Within a pass, the unit test above and `on-postgres.test.ts` (that the file is listed and does reach Postgres) are what stand in for it.

`pnpm test` also covers the barrel export: `one-choice.test.ts` and `one-store.test.ts` must stay green **with no edits**. If either needs an edit, something has been put in the wrong file.

## Not an ADR change

Nothing here supersedes 0055, 0056 or 0100. The tables live in whichever store the machine wrote down, opened by the one chooser. Nothing appends an event, so this is not part of the log, and a reset of `events` leaves the tables alone.
