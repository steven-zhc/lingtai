# Design note — #847

The ticket already says which sentences to fix, and it says to re-read the code before each one. This note covers one open decision and two things the re-read will run into.

## The decision: each upgrade note says which of three kinds of rebuild it is

The ticket wants each entry to "name the projection, the user-visible change, the §4.5 runbook". The existing entries (#679, #680) also say **what `lingtai doctor` says**, and the ticket asks for that shape. For #797 that line differs from ticket to ticket, because a stale projection shows up in one of three ways:

1. **Shape drift.** A column was added to or removed from the DDL. `shapeIn` (`packages/projector/src/shape.ts`) finds it, `lingtai doctor` reports the projection as drifted, and the runner refuses to start (`projection.ts:236-237`: *"Refusing here costs the same board and no orphan"*). Fill in #679's sentence pattern for these.
2. **Stored state that no longer decodes.** `ticket_report`, `spend`, `task_view` and `ticket-row.ts` store a serialized `TicketState` or `RunState`. They read it back through `decodeTicket` (`packages/domain/src/ticket-codec.ts:135-161`) or `decodeRun` (`task-view.ts:549`), and those refuse an old row by name: *"the stored ticket state is not today's shape (…); run `lingtai projection rebuild <name>`"* (`ticket-codec.ts:138-139`). `ticket-report.ts:15-17` states the rule: *"A change to what `applyTicket` returns makes stored rows stale: `decodeTicket` refuses them by name, and §4.5's runbook rebuilds this table."* The shape check does not see this, because the column is the same JSON column. The refusal comes on the first event that touches an old row. This is why #842 (`waits`) and #843 (`discussions`) need entries even though neither diff touches `packages/projector` (`git diff --stat 4abc49fc^1 4abc49fc` and `666a3366^1 666a3366` change only `packages/domain/src/ticket.ts`, the board and tests). A field added to `TicketState` changes every stored row in every projection that stores it. Before writing the #843 row, confirm it against `StoredTicket`: check whether `discussions` is required or defaulted.
3. **The reducer changed and the shape did not.** Examples are #835 (`spend` kind), #838 (`finding_backlog` decision), #833's reopen rule and #834's cells. Nothing complains. `doctor` is green, and rows written before the merge keep the old answer until the projection is rebuilt. Say exactly that in the entry: "`lingtai doctor` says nothing; the rebuild is what changes the old rows". The danger with this kind is that it is silent.

A ticket can be more than one kind. To classify one, read its merge diff (`git diff <merge>^1 <merge>`) for three things: DDL changes in the projection's `create`, changes to `StoredTicket` or the run codec schema, and reducer changes. Its merged body is a fourth source. Do not classify from the ticket table. The merges are in the log: #821 `f6ca928c`, #842 `4abc49fc`, #843 `666a3366`, #833 `cf893884`, #835 `77640289`, #838 `d7d637f8`, #834 `9c1f5307`, #844 `f77d43a8`, #845 `af6a48c5`.

**Order and dedupe.** Write the entries in that landing order, by `git log --first-parent main`, which is not the order of the table. Every entry tells someone to rebuild, and an operator upgrading past several of them only needs to rebuild each named projection once, after the last one. So put one sentence before the #797 entries: *"if you are upgrading across all of these at once, drain, merge, rebuild each of `task_view`, `ticket_report`, `spend` and `finding_backlog` once, restart, restart the board"*. Then give the per-ticket entries. This is the §4.5 runbook (`doc/design/one-fold-per-stream.md:611-625`) applied once. It is not a new procedure. Write the runbook steps in operating.md's own words and do not link to the design doc: the ticket's out-of-scope list keeps that doc for the operator, and the user docs should not send readers there.

## Two things the re-read will run into

- **`operating.md:1589-1592`** (*"Nothing on that page is maintained in a table"*). `loadTask` (`apps/board/src/lib/task.ts:1555`) imports `readTasks` from `@lingtai/projector/task-view` (`task.ts:75`), and the comments at `:417` and `:533` say the ticket part is *"folded from the item's own stream through `applyTicket`"*. Follow `loadTask` to see whether `readTasks` supplies anything the page displays, or only the card. If it supplies a displayed value, the sentence is false and should say which part comes from `task_view`. If it supplies only the card, leave the sentence alone.
- **`reference.md:1490`'s keys.** Report each reader's key the way the code builds it: `task_view` (`task-view.ts:41-48`, after #844), the board's rail (`progressOf`, `apps/board/src/lib/progress.ts`), and `reduceRun` / `stepsOn` (`packages/domain/src/run.ts`). If two of them share a key, one sentence can cover both. Do not invent a uniform rule they do not follow.

## What a reviewer checks

The changes are prose only. No unit test reads these sentences. `apps/site/unit/docs.test.ts` and `sitemap.test.ts` check only the file list, and that list does not change. So the check is the commit body. For each changed sentence it names the §6 item or ticket, and for each upgrade note it names which of the three kinds it is and the line of code that shows it. Each sentence listed as false but left unchanged gets a line saying why.
