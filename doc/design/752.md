## The decision the ticket leaves implicit: Step 1's `--base main` has to change

Step 1's `init` passes `--base main` in both shells (`doc/tutorial.md:64`, `:74`). If you only remove the bare repository and leave that flag, the project lands on **`main` in the checkout**. That is the branch checked out there, so every first pass would stop at #771's hold. Here is why:

- `first-project.ts:542` uses `LINGTAI_BASE` as the detected answer only when `flags['base'] === undefined`.
- `validate` (`:559-565`) accepts any existing branch as given.

**Write `--base lingtai-base` explicitly.** Do not just drop the flag:

- `validate` creates the branch from whatever is checked out when the answer is `lingtai-base`, whether it was given or detected (`:566-579`). So it behaves exactly like the default.
- The options table keeps a row that names where landings go.
- Part 2 tells the reader to "pass Step 1's flags; a fresh home needs `--base`" (`:262`). Its own command still says `--base main`, so Part 2 is unaffected.

The operator's measured run must use the same flag you print. If the pasted output in the ticket body was made with a different `--base`, say so on the ticket and stop. Do not reconcile the two by wording.

## What changes, place by place

1. **Setup (`:26-49`).** Keep only the clone and the `CHAPTER_GARDEN_DIR` lines, in both shells. Delete `git clone --bare` and `remote set-url`. The checkout's `origin` stays GitHub, and nothing pushes there.
2. **Before you start table (`:13`).** "let Lingtai merge into a repository on this machine" is still true. Leave it unless you need the words.
3. **Options row (`:96`).** Change `--base main` to `--base lingtai-base`, with a meaning like "Lands on a `lingtai-base` branch in your checkout, made from the branch checked out now; `main` and your working tree are never touched."
4. **Step 4 landing (`:182-186`).** This replaces "reached `main` of the bare repository. Run `git pull`…". **`git pull` has to go, not just be reworded**: the checkout's `origin` is GitHub again, so `git pull` would fetch upstream Chapter Garden and none of the landing. It should say three things:
   - the change is on `lingtai-base` in the checkout;
   - `lingtai-base` does not follow `main`, so take it onto `main` with `git merge lingtai-base` while on `main`;
   - one sentence on the hold: if `lingtai-base` is checked out, the land holds with `lingtai-base is checked out in <dir> — switch to another branch, then lingtai approve chapter-garden --issue <n>`. Quote the hold from `integrate.ts:490`, with `<project>` filled in as `chapter-garden`.
5. **Part 2 (`:275`).** One phrase only. "not the local bare repository" becomes "not `lingtai-base` in your checkout". The ticket's Watch out protects Part 2's GitHub landing, and that stays as written: "merges into `main` of your fork". What changes is the comparison it draws, which would otherwise point at something Part 1 no longer creates. Nothing else in Part 2 changes.
6. **`doc/img/waiting.svg:3` and `:21`.** Change the `<desc>` text "merges into main of the bare repository" and the detail text `main, bare repository` to `lingtai-base` wording. Nothing generates this file: `scripts/the-pass.py` does not produce it, and no test reads it. Edit it by hand and keep the detail text no longer than it is now, so it still fits the box at `x="614"`.
