## Shape for #974: `proposeSetup`, and what moves to make it possible

Most of this is a move. The design questions are three: where the line falls between a *reader* (moves) and an *asker* (stays), how `proposeSetup` can be an Effect without raising any ratchet number, and what the ticket's local-directory rule does to `lingtai add --local` (nothing).

### What moves, and what stays in `apps/cli`

**Readers move into `@lingtai/setup`. Askers stay in `apps/cli`.** An asker is a function that takes a `QuestionWorld`. `question.ts` belongs to the CLI, and the board must never reach it.

- **`apps/cli/src/runtimes.ts` moves whole.** That covers `askRuntimes` (`:32`), `firstLine`, `runtimeStateSentence` and `remedyFor` (`:63`). They are all pure or read-only. `agents.ts` and `init.ts` re-point their imports.
- **`apps/cli/src/source.ts` is split, not moved whole:**
  - These move: `liveHistory` (`:241`) and `DIFFERENT_SOURCE_CLASH` (`:77`), plus one new pure function that takes the rule `askTickets` uses to decide `current`, verbatim, out of `source.ts:114-116`. It is `rawTickets === 'db' || (rawTickets === null && history.some(h => h.startsWith('db ticket #'))) ? 'db' : 'github'`, as something like `ticketSourceFrom(raw, history)`.
  - These stay in `source.ts` and call the moved rule: `askTickets` and `askKinds`.
  - That extraction is the only line of `source.ts` logic that changes. The Proposal and `askTickets` must answer *which source holds* the same way, and the way to keep them identical is to make it one function. A copy would drift.
- **`apps/cli/src/trial-build.ts` moves whole.** It imports `TrialReport`, `TrialResult` and `AskInstallAndBuildInput['tryBuild']` from `./setup-build.ts` (`trial-build.ts:18`; the types are at `setup-build.ts:31-57`). `@lingtai/setup` cannot import `apps/cli`, so `TrialResult`, `TrialReport` and `Trial` (`setup-build.ts:31-44`) move with it. `setup-build.ts` imports them back from `@lingtai/setup`. `liveTrialBuild`'s return type becomes `Trial` rather than `NonNullable<AskInstallAndBuildInput['tryBuild']>`, which is the same type by `setup-build.ts:57`.
- **Tests move with their files, `git mv`, and only their import specifiers change:**
  - `apps/cli/unit/trial-build.test.ts`
  - the parts of `apps/cli/unit/source.test.ts` that cover `liveHistory` or the source rule, if any. Its `askTickets` and `askKinds` tests stay.
  - `git grep -l "runtimes.ts'\|trial-build.ts'" apps` lists every importer to re-point: `add.test.ts`, `agents.test.ts`, `first-project.test.ts`, `recipe-flow.test.ts` and `recipe-summary.test.ts`, as well as the `src/` files.

**`@lingtai/setup`'s new dependencies** are whatever the moved files import:

| Source | Dependencies |
|---|---|
| `runtimes.ts:1,9-11` | `@lingtai/agent`, `@lingtai/agent-env`, `@lingtai/domain` |

None of these packages depends on `@lingtai/setup`, so there is no cycle. `packages/conductor/package.json:51-60` lists none. Keep `liveHistory`'s imports **dynamic**. Its own comment (`source.ts:226-228`) says *"a caller that only wants to ask a setup question must not open a store merely by importing this module"*, and the board will import this package's entry. Run `pnpm install` so the lockfile records the new dependencies, and commit it.

### `Proposal`: three states per line, never two

The ticket's Watch out says *"a default passed off as detected"* is the failure. So each line is a tagged value, not a bare value with an optional reason:

```ts
type Line<T> =
  | { state: 'detected'; value: T; from: string }   // read off the repository, GitHub, the log or this machine
  | { state: 'default';  value: T }                 // nothing to read; this is what Lingtai offers
  | { state: 'unknown';  reason: string }           // a reader failed; `reason` says which and why
```

**`default` is not `unknown`, and kinds is the case that shows why.** There is nothing to detect, so kinds is always `default` with `SETUP_KINDS`. `unknown` is only for a reader that threw or answered something it could not read.

Line by line:

| Line | State and value |
|---|---|
| base | GitHub's default branch for a slug (`defaultBranchOf`, `add-github.ts:64`, moved or injected); `git`'s current branch for a path |
| stack, install, checks | `detectSetup` over the target's `SetupReader` |
| runtimes | the `RuntimeFound[]` from `askRuntimes` |
| reviewer | derived from the runtimes the same way `askAgents` picks it (`agents.ts:288`) |
| tickets | see the next section |
| kinds | `default`, `SETUP_KINDS` |
| held-by, end | `default`. Held-by is the recipe's default hold label. End is the two entries `add-github.ts:345-351` seeds today. |
| limits | `default`, the values `askLimits` reads its `current` from (`landing.ts:261,277,298`) |
| approve | `default`, `false`. This is `askLanding`'s `LAND` (`landing.ts:185`). |

**No runtime signed in is a `detected` line, not `unknown`.** The probe answered. Carry each `RuntimeFound`, so that a page can print `runtimeStateSentence` and `remedyFor` per runtime without probing again.

### Ticket source

- **If there is history, it wins over everything,** through the extracted rule. It is `detected`, with `from` naming the streams, exactly as `askTickets` keeps it (`source.ts:118-129`).
- **A GitHub slug** with no history gets `github`.
- **A local path** with no history: run `git remote get-url origin`. If that parses as GitHub, the line is `github` with the parsed `owner/repo` and `from: 'origin'`. The three forms are `https://github.com/o/r(.git)`, `git@github.com:o/r(.git)` and `ssh://git@github.com/o/r(.git)`. No such parser exists in the tree today, so write a small pure one and unit-test it. Otherwise the line is `db`, `detected`, with `from` saying *no origin* or *origin is not GitHub*.
  - A failed `git` call is `unknown`, not `db`.

**`lingtai add --local` does not change.** `askTickets` never asks a local project anything. It forces `db` and refuses `--tickets github` because *"a project with no owner cannot take its tickets from GitHub"* (`source.ts:131-142`). A local project is registered with `owner: null` (`first-project.ts:110`). Taking GitHub issues for one is a registration change, which is #968's write, and this ticket's Out of scope rules that out. So the Proposal *says* `github` for a local checkout whose origin is on GitHub, which is what the mock shows (*"remote origin → github.com/… — tickets still come from its issues"*, `doc/design/add-repository.html:970`), and the CLI's local branch has no ticket question to take it as a default. That is consistent, and the existing `add --local` tests stay green unedited.

### `proposeSetup` is an Effect, and no ratchet number rises

- **It is `Effect.gen` over an injected `ProposalReaders` record of Effect-returning functions.** The live record wraps each moved `async` reader in `Effect.tryPromise`. Unit tests pass a fake record, which is the ticket's *"fake readers"*.
- **Each line is read with `Effect.result` (Effect 4's `either`)** and mapped to `unknown` on failure, so one failed reader never fails the whole Proposal. Run the reads with `Effect.all(…, { concurrency: 'unbounded' })`. They are independent, and the runtime probe spawns processes.
- **New `async` in `packages/setup/src`: zero.** Only `src/` is counted (`effect-ratchet.test.ts:212`), so async fakes in `unit/` are free. The moved `async` functions raise `packages/setup` and lower `apps/cli` by the same amount. Take the exact numbers from the red's printed JSON, and check the sum is unchanged before pasting. The test fails below baseline as well as above (967's note, Trap 1).
- **New `Effect.run*` in `apps/cli`: zero.** The CLI's command handlers are `Effect.promise(async () => …)` (`cli.ts:160-175` for `add`). A bare `Effect.runPromise` inside `addFlow` would take `apps/cli`'s `run` from 6 to 7, and CLAUDE.md calls that a blocking finding. Instead:
  - Turn the `add` handler, and the `init` handler just above it (`cli.ts:~140-157`, which reaches `askRecipe` through `first-project.ts`), into `Effect.gen` that takes `const services = yield* Effect.context()`.
  - Hand `Effect.runPromiseWith(services)` down on the world as `propose: (target) => Promise<Proposal>`.
  - The ratchet does not count `runPromiseWith` (`RUN`, `effect-ratchet.test.ts:55`), and CLAUDE.md names this pattern, citing `schedule.ts`.

### How `askRecipe` takes the Proposal as its defaults

`RecipeAt` (`recipe-flow.ts:108`) gains `proposal: Proposal`. Its callers are `first-project.ts:692` and `add-github.ts:377`, and each calls `world.propose(...)` once, at the point where it now builds `runtimes`, `reader` and `defaultBranch`.

**A Proposal value replaces a `fallback` and never a `current`.** An existing recipe still wins wherever an asker reads one (`agents.ts:234-335`, `landing.ts:185,261`, `source.ts:205`). The Proposal is what Enter accepts on a file that says nothing.

- **runtimes:** pass the Proposal's runtimes as `at.runtimes`, and drop the separate `deps.runtimes()` probe (`add-github.ts:373`, `first-project.ts:1088`). One probe per run, not two. If the line is `unknown`, give `askAgents` an empty list. Its existing `noRuntimesSignedInRefusal` (`agents.ts:43`) is then the answer, and the probe's own failure is added to that refusal.
- **base:** seed the memoized `defaultBranch` (`add-github.ts:331-334`) from the Proposal's `detected` base. If the line is `unknown`, fall back to the existing request, so behaviour is unchanged.
- **kinds:** `askKinds`'s `fallback` (`source.ts:205`) is the Proposal's kinds. It is `SETUP_KINDS` either way.
- **install, checks:** `askInstallAndBuild` now runs `detectSetup` itself (`setup-build.ts:22`). If the Proposal is computed over the same reader, hand its detection in rather than detecting twice: over a GitHub ref, that would be every contents request again. If threading it in means more than one parameter, leave `askInstallAndBuild` alone and say so in the commit. The cost is requests, not correctness.
- **The trial build:** `liveTrialBuild` stays exactly where it is called (`add-github.ts:388`, `first-project.ts:700`), now imported from `@lingtai/setup`. `proposeSetup` neither takes it nor calls it.

### `SETUP_KINDS`

`packages/recipe/src/answers.ts:161` becomes `['bug', 'feature', 'tech-debt', 'documentation']`, in that order. Rewrite the comment above it (`:159-160`) if it still says three. `git grep -n "bug, feature, documentation\|'bug', 'feature', 'documentation'" apps packages` finds the tests that assert the old default, and those assertions change to four kinds and nothing else. A test that asserts kinds read from an existing file is not one of them.

### Edges

- **A reader fails** (GitHub, `git`, the filesystem, a runtime probe, or the log for `liveHistory`): that line is `unknown` with the error's message, and the other lines still read. The unit test gives each reader in turn a failing fake and asserts that only that line is `unknown`. This is the stand-in for any claim about live behaviour.
- **The log is unreachable while a slug proposes:** tickets is `unknown`, not `github`. Today `askTickets` would throw out of `deps.history`. That stays the CLI's behaviour, because the asker still calls `at.history` itself.
- **Restart, pause, two passes, retry:** nothing is written and no event is appended, so none of them apply. For the same reason no event or field can settle this ticket. The unit tests are the whole check, and none of them needs `pnpm test:integration`.
- **The cost to later tickets:** the Proposal is a type the board's children will render. Keep each line's `from` and `reason` as sentences, so the page prints them rather than re-deriving them.
- **ADRs:** this continues 0125 §1, which #967 started. It contradicts no accepted ADR.
