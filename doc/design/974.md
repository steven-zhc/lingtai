### `liveHistory` cannot go into `@lingtai/setup`

It imports `@lingtai/conductor/db-tickets` (`source.ts:244`), and `@lingtai/conductor` already depends on `@lingtai/setup` (`packages/conductor/src/pick-repository.ts:43`: `import { type Picker, same } from '@lingtai/setup'`). Moving it in would create the cycle setup → conductor → setup.

So `proposeSetup` takes history as an injected reader, the way `TicketsDeps.history` already does (`source.ts:52`). `liveHistory` moves next to `db-tickets.ts` instead: `packages/conductor/src/ticket-history.ts`, exported as `@lingtai/conductor/ticket-history`. The board already depends on conductor (`apps/board/package.json`), so it can wire that in later, and `apps/cli` imports it from there.

`source.ts:108` refers to "`liveHistory`'s own comment" — keep that comment with the function. The ticket's list says `liveHistory` moves *into the package*; this is the one place the note departs from it, and the cycle is the reason.

## The `Proposal`

Every line has the same two-sided shape. A failed reader can never be mistaken for a detected value:

```ts
type Line<T> =
  | { known: true; value: T; because: string }
  | { known: false; reason: string; default: T }
```

`default` is what `lingtai add` would offer when the read failed. The board shows it marked as not detected, and it is never moved into `value`. The fields:

| Field | Comes from |
|---|---|
| `base` | the default branch: injected reader; for a local path, the `base` the CLI already worked out |
| `stack`, `install`, `checks` | `detectSetup(reader)`. Its `notes` / `skipped` are what step 2 prints, and an `unknown` stack's notes are kept (`detect-setup.ts:768–771`) |
| `runtimes` | `RuntimeFound[]`, plus `remedyFor` per runtime that is not signed in |
| `reviewer` | the same default `askAgents` picks today, from the runtimes |
| `tickets` | see the next section |
| `kinds` | `SETUP_KINDS` |
| `heldBy` | the same default as today |
| `end` | the same default as today |
| `limits` | the same default as today |
| `personApprovesMerge` | always `false`. #964 decision 5: `proposed: []` |

For `reviewer`, `heldBy`, `end` and `limits`, find each default where today's question computes it and reuse the same value. Do not write a second copy of it.

### Make it an Effect

```ts
proposeSetup(target, readers): Effect.Effect<Proposal, never>
```

- `target` is `{ kind: 'github'; owner; repo } | { kind: 'local'; path }`.
- `readers` holds `setupReader`, `defaultBranch`, `runtimes`, `history` and `origin`. Each is wrapped in `Effect.tryPromise`, with one `Effect.either` per line, so that a failure becomes that line's `{ known: false, reason }` and every other line still proposes. The error channel is therefore `never`.

`apps/cli` runs it with the existing `runEffect` (`first-project.ts:1052`, `Effect.runPromiseWith(Context.empty())`). Its comment says why the ratchet does not count it: *"`runPromiseWith` is the run the ratchet does not count, and it starts no fiber of a caller's tracer because there is no caller here."* `add.ts:31` already imports it.

Writing `proposeSetup` as an `async` function would add one `async` to the ratchet's total. Writing it as an Effect adds none.

## The ticket source for a local directory

`readers.origin(path)` returns the output of `git remote get-url origin`. Parsing it as a GitHub slug is new: there is no shared parser today, and `parseSlug` (`packages/github/src/client.ts:775`) only reads `owner/repo`. Write a small pure `githubSlugOfRemote(url)` in setup that recognises:
- `https://github.com/o/r(.git)`
- `git@github.com:o/r(.git)`
- `ssh://git@github.com/o/r`

Anything else returns `null`. The tickets line is then:

| Case | Line |
|---|---|
| `origin` is on GitHub | `github` (`o/r` from `origin`) |
| no `origin`, or an `origin` that is not GitHub | `db` |
| the `git` call failed | `known: false`, default `db` |
| history exists (`source.ts:117–131`) | whatever `ticketSourceOf` says |

History overrides `origin` because switching source would put two sources' numbers into the same streams (`DIFFERENT_SOURCE_CLASH`, `source.ts:77`).

A history read that fails is also `known: false`. It must not count as "no history".

**This ticket does not change `lingtai add --local`'s ticket source.** That branch registers `owner: null` (`first-project.ts:771`) and calls `askRecipe` with `local: true` (`first-project.ts:716`). `askTickets` then never asks, and refuses `github` for that reason: *"a project with no owner cannot take its tickets from GitHub"* (`source.ts:134–141`).

Making a local directory take GitHub issues means registering an owner, which is writing — #968 (`applySetup`), and out of scope here. So:
- the `Proposal` carries #964 decision 6 for the board to show;
- the CLI's local branch keeps passing `local: true` and keeps writing `db`;
- a unit test pins both facts side by side, so #968 has something to turn green.

## `askRecipe` takes the `Proposal`

`RecipeAt` (`recipe-flow.ts:107`) gains `proposal: Proposal`. The `Proposal` **replaces the fallbacks only**. A value an existing file already has still wins: `askKinds` offers the file's `currentDisplay` and uses `fallback` only when it is `null` (`source.ts:198–206`).

That keeps every existing-file test as it is. `proposeSetup` reads no existing recipe: it proposes for a new project.

Pass `proposal.kinds` as `askKinds`' fallback in place of the direct `SETUP_KINDS` (`source.ts:206`). Do the same for the other questions that have a fallback.

`runtimes`, `history` and `defaultBranch` stay on `RecipeAt`. The callers (`add-github.ts:377`, `first-project.ts:714`) build the `Proposal` from readers that return what they have **already** probed, so nothing is asked twice. Today:
- `add-github.ts:332` memoizes `defaultBranch` because asking GitHub twice for one run is waste (`:329`);
- `AskedBeforeAdd.runtimes` exists so the card does not probe again (`add-github.ts:177`).

## The effect ratchet

The ratchet is per package (`effect-ratchet.test.ts:203–219`): it goes red on a package above its baseline **and** on one below it. Moving code therefore means editing two numbers in `effect-ratchet.baseline.json` by the same amount, in opposite directions. That is the one case where a number rises, and the sum must not change.

The `async` keywords being moved, counted from today's source:

| From | Count |
|---|---|
| `trial-build.ts` (`:78`, `:98`, `:114`, `:228`, `:241`, `:254`) | 6 |
| `askRuntimes` (`runtimes.ts:32`) | 1 |
| `liveHistory` (`source.ts:241`) | 1 |

The expected change:

| Package | Change | Where it goes to |
|---|---|---|
| `apps/cli.async` | −8 | 425 → 417 |
| `packages/setup.async` | +7 | 12 → 19 |
| `packages/conductor.async` | +1 | 200 → 201 |

New code adds 0. That includes `ticketSourceOf` and `githubSlugOfRemote`, which are synchronous.

Run the test and copy the `measured now:` JSON it prints rather than adding the numbers up by hand. If the sum of all `async` counts is higher afterwards, something new was written `async`, and the diff is wrong.

## Edges

- **A reader fails:** that line is `known: false` with the reason; the rest still propose.
- **History cannot be read:** `known: false`, never read as "no history".
- **No runtime signed in:** each runtime's state, with `remedyFor`.
- **The trial build:** `proposeSetup` never calls it.
- **Restart, pause, two passes:** do not apply — nothing is written.
