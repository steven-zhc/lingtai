# Design: #623. `lingtai board` moves to `@effect/cli`, and only `board status` takes `--json`

## The trap: the supervised board does not start through the entry

`lingtai service` writes the board job as `node <root>/apps/cli/src/lingtai.ts board start --no-open`. You can see it at `service.ts:299` (launchd, `const argv = [join(inputs.root, 'apps/cli/src/lingtai.ts'), ...job.argv]`), at `service.ts:397` (systemd `ExecStart`), and at `BOARD_JOB.argv` (`service.ts:163`). `keeper()` also refuses a plist that does not contain that exact path (`service.ts:740-746`: *"runs a different checkout than this one"*).

#621 moved its commands into the *"runs from the entry"* group (`lingtai.ts:1179-1189`). That case prints `lingtai ${command} runs from the entry …` and returns 2. **If `board` goes into that group, every installed board job exits 2 and launchd respawns it every thirty seconds.** That is the same failure #187 describes for `builtBoardDir`. Nothing in the unit half would notice.

Do not change the job to run `entry.ts` either. Every plist already on disk would stop matching the `service.ts:740` check, `keeper` would answer `unread`, and `board stop` would refuse to signal anything (`board.ts`'s `stop`, the `'unread' in kept` branch).

**The shape:**

- `MIGRATED_COMMANDS` (`migrated.ts:9-22`) gains `'board'`, so `pnpm lingtai board …` and the bundle reach `cli.ts`.
- **`lingtai.ts`'s `case 'board'` (`:1064-1081`) stays a real case.** Its body becomes `return (await import('./cli.ts')).runCli(['node', 'lingtai', 'board', ...rest])`. Both doors then go through one parser, and `satisfies never` (`lingtai.ts:1199`) is unaffected.
- Add a comment on that case naming `service.ts:299`/`:397` as the reason, so the next migration does not "tidy" it into the entry group.
- Add a unit test that pins it: read `lingtai.ts` as text and assert the `case 'board'` body reaches `runCli`, not the entry-group refusal. Or, if you can do it more cheaply, assert that `BOARD_JOB.argv[0]` is a command whose `lingtai.ts` case is not in the refusal group.

## The live world moves out of `lingtai.ts`

`cli.ts` cannot import `lingtai.ts`, because importing it runs `main` (`lingtai.ts:1217`). `liveBoardWorld` (`lingtai.ts:284-346`) and `boardAnswering` (`:274-282`) move into a new `apps/cli/src/board-world.ts`.

- `boardAnswering` is a copy of `boardAt` (`board.ts:37-45`), byte for byte apart from the name. Delete it and use `boardAt`.
- The new module's imports are what the world already uses: `createFileLocker` (`@lingtai/env/lock`), `keeper`/`BOARD_JOB` (`service.ts`), `boardPort`, and `configPath` (`init.ts:71` import in `lingtai.ts`).
- The `cli.ts` handler `await import()`s it, as `status` does (`cli.ts:46-49`).
- The port resolution moves into the handler: `parsed.port ?? boardPort()`, and on a throw, the message and exit 1 (`lingtai.ts:1070-1079`). So does `dir ?? builtBoardDir()`.
- The handler must not reach `entry.ts`'s `process.exit` special case (`entry.ts:41-43` is `init` only). `start` returns 0 while the server keeps the loop alive, and `process.exitCode = 0` is what `lingtai.ts:1219` does today.

## Parsing

`board` is `Command.make('board', startOptions, startHandler)` with `withSubcommands([start, stop, restart, status])`.

**The parent's own handler is `start`.** This keeps `lingtai board` and `lingtai board --port <n> --no-open` working. The second is exactly what `apps/release/integration/build.test.ts:273` spawns, and `init.ts:617` prints `next: lingtai board`.

That integration test is the only witness for the bare form through the bundle, and it is out of reach inside a pass. The unit-level claim that stands in for it is a `runCli` test asserting that `['board', '--port', '18080', '--no-open']` reaches start with `{ port: 18080, open: false }`. Write it against an exported command factory that takes the world as a parameter, as #620 and #621 suggested.

| today (`parseBoardArgs`, `board.ts:290-332`) | after |
|---|---|
| `board shutdown` → a named refusal and exit 2 | precheck in `runCli` next to `TAKES` (`cli.ts:296-299`): same sentence, exit 2, and the `usage` error document under `--json`. Without it, `@effect/cli` answers with a generic unknown subcommand. |
| `--port` not an integer in 1–65535 → `… — --port takes a port number`, exit 2 | `Options.integer('port')`, plus a range check in the handler that keeps the sentence and exit 2 |
| an unknown verb or flag → the usage line, exit 2 | `@effect/cli`'s usage error, exit 1. Say so in the PR, as #621 did. |
| `stop`/`status`/`restart` accept `--port` | they keep it (`boardLock` is per port, `board.ts:221-223`). Give `--dir`/`--no-open` to `start`, `restart` and the parent only. |

Delete `parseBoardArgs` and `BoardArgs`. Their tests become `runCli` tests that assert the same outcomes: `integration/board.test.ts:225-249`.

## Output

`boardCommand` keeps its signature, and `log`/`error` stay on the world. That signature is what every verb test drives. What changes is what those lines are made of.

- **`status`** becomes three pure functions in `board.ts`:
  - `readBoardStatus(command, world) → BoardStatus`
  - `renderBoardStatus(s) → string[]`: a heading `board on <port>` (`heading`, `output.ts:70`), then `keyValues` (`output.ts:80`) over the four rows that exist today: `serving`, `answering`, `supervisor`, `port`.
  - `boardStatusJson(s)`
  
  The ticket says three facts. The fourth row, `port … set in …`, is a fact the old output printed, so keep it (`board.ts:612`). `keyValues` pads to the widest key plus two, and `supervisor` is ten characters. So the plain text is `serving     …` at the same twelve columns as today, and the assertions at `integration/board.test.ts:506-509`, `:516-518`, `:524` hold unchanged.
- **`start`/`stop`/`restart`** get no `--json`. Their definition is `effect: 'changes'` (`commands.ts`, `board` entry) and they report no verdict object. Each terminal line gets a glyph: `symbol.pass()` on the line that says it worked (`board on …`, `stopped the board …`, `the board answers on …`) and `symbol.fail()` on the first `error` line of a refusal. Every sentence after the glyph stays **word for word**, because the tests above assert substrings of `w.out`/`w.err`. Do not add a `next:` line where the old sentence did not already name a command (0121 §5's rule, which #621 followed).

## `--json` for `board status`, and the edit to 0121 §5

0121 §5 gives `--json` to *"every command whose definition says it only reads"*, plus #621's verdict commands. `board` is one definition marked `changes`, so as written the ADR gives `board status` nothing. **Edit 0121 §5**, the topic's own ADR, which is how #621 handled its exception (`doc/design/621.md`, first section). Do not add a new file. The new sentence: *a read-only verb of a `changes` command, `board status` today, takes `--json`.* Leave `commands.ts`'s `effect` for `board` as `changes`: `help.ts:34` is about the whole command.

The document, with `command` set to `"board status"` so a future `board start --json` can never be mistaken for it:

```json
{"version":1,"command":"board status",
 "serving":{"holder":"board on 17820 pid 500 on mac","pid":500,"host":"mac"},
 "answering":{"url":"http://127.0.0.1:17820"},
 "supervisor":{"kept":true,"platform":"launchd","path":"/…/ai.nextloom.lingtai.board.plist"},
 "port":17820,"portSetIn":"board.port in ~/.lingtai/config.yml, or --port for this one run"}
```

- When nothing holds the lock: `serving: {holder: null}`. When nothing answers: `answering: {url: null}`. When nothing keeps it: `supervisor: {kept: false}`.
- **A fact that could not be read is `{ "unread": "<message>" }` inside its own key, not an `error` document.** Today `status` exits 0 with the unread fact printed in its row (`board.ts:581-584`, test `:521-536`), and three facts *"none concluded from another"* means one unreadable fact does not fail the others.
- Use the `error` document only when the handler could not run at all: a `board.port` that does not parse goes through `failed()` (`cli.ts:31-37`). A usage error becomes the `usage` document (`cli.ts:367-370`).
- Do not add a `pid` that `holdingProcess` (`board.ts:335-338`) cannot read from the holder name. Leave the key out.

## Tests: move the verb tests into the unit half

Lines `127-596` of `apps/cli/integration/board.test.ts` drive `boardCommand` against a world that *"holds no lock, signals nothing and starts no server"* (its own comment, `:128-132`). They sit in `integration/` only because the same file also tests `serveBoard` and `builtBoardDir` against tmp files.

**Move the `boardCommand`, lock and holder blocks to `apps/cli/unit/board.test.ts`.** Keep `serveBoard`, `builtBoardDir` and *"the board's port, where the board is not the subject"* (`:575`, which writes `config.yml` to a tmpdir) in `integration/`. Without the move, *"no fact the old output printed is lost"* has no witness inside a pass.

Add these:

- `renderBoardStatus` under `NO_COLOR`, one case per branch of each row.
- `boardStatusJson`, one document per branch, including each `unread` branch. Run `JSON.parse` on what `printJson` writes.
- The `runCli` cases from the parsing table.
- A `migrated.test.ts` row each for `['board']`, `['board', 'status']` and `['board', '--port', '1', '--no-open']` → `'effect'`. `:49`'s `board start --help` → `'help'` stays.
- `commands.ts`'s `board` usage line for `status` gains `[--port <n>] [--json] [--no-color]`, within the 76-column limit `help.test.ts` enforces (`commands.ts:10-12`).
