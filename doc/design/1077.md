# #1077: design note

The ticket describes the change well. This note covers the places where the obvious edit would change behaviour, or would fail the ratchet without anyone noticing.

## 1. The ratchet counts async arrow functions

`packages/domain/unit/effect-ratchet.test.ts:125-132` counts the `async` modifier on `isArrowFunction` and `isFunctionExpression` nodes, not just on declarations. So the obvious Postgres rewrite, `Effect.promise(async () => { … })`, keeps the count above 0.

Write each Postgres method like this:

```ts
Effect.acquireUseRelease(
  connect,                                   // Effect.promise(() => client.connect()).pipe(Effect.as(client))
  (client) => Effect.gen(function* () { … yield* Effect.promise(() => client.query(…)) … }),
  (client) => Effect.promise(() => client.end()),
)
```

- `create` puts its four statements (`postgres.ts:77-100`) in that order as four `yield*`s inside one use. That means one connection, as it is today.
- `connect` (`postgres.ts:64-68`) builds `new pg.Client` inside the acquire Effect, never outside it. Each run must make its own client, so an Effect that is run twice opens two connections. Sharing one client would mean a second beat calls `connect()` on a client that has already ended.
- An `end()` that rejects becomes a defect. That matches today's `finally { await client.end() }`, which rejects as well.
- `close` is `Effect.void`.

## 2. The "no table" null has to stay a value, and only for the select

`postgres.ts:142-170` turns `/does not exist/` into `null`. The `try` there wraps only the select: `connect()` runs before the `try`. So a connection error such as *database "x" does not exist* rejects today and is never read as "no daemon".

Keep that boundary:

- Lift that one query with `Effect.tryPromise({ try: () => client.query(…), catch: (e) => e })`.
- Recover to `null` when the message matches, and `Effect.orDie` everything else.
- Do this inside the use, not around the whole `acquireUseRelease`.

If you use `Effect.promise` for that query, a fresh machine's `lingtai doctor` reports a defect where it now reports *no daemon has run*.

SQLite is the same case in another form. The `try/catch` around `isMissingTable` (`sqlite.ts:183-190`) stays inside the `Effect.sync` thunk.

## 3. `streams` with an empty query opens nothing

`postgres.ts:183` and `sqlite.ts:213` return `[]` before they connect or prepare a statement. In Postgres, return `Effect.succeed([])` before the `acquireUseRelease`, not from inside its use. Otherwise every empty query opens a connection.

## 4. The callers: there are seven, and the ticket's grep finds three

`grep "Effect.promise(() => s\."` only matches a lift written exactly that way, and none of the lifts in `src` use the name `s`. These are the store-method lifts to remove:

| Where | Today | After |
|---|---|---|
| `control.ts:505` | `Effect.promise(() => it.create())` | `it.create()` |
| `control.ts:543-555` | `Effect.promise(() => store.beat({…}))` | `store.beat({…})` |
| `control.ts:720` | `Effect.promise(() => it.status())` | `it.status()` |
| `work-loop.ts:669` | `Effect.promise(() => store.head())` | `store.head()` |
| `reconcile.ts:115-118` | `withStreams`'s `fn` returns a `Promise<T>` and is lifted | `fn: (store) => Effect.Effect<T>`, passed straight to `withDaemonStore`; its one caller is `:553` |
| `converge.ts:361-369`, `:386` | `candidates` returns `Promise<Set>` via `.then` | `candidates` returns `store.streams(…).pipe(Effect.map((f) => new Set(f)))`; `:386` passes `candidates` itself |
| `choose.ts:88` | release is `Effect.promise(() => store.close())` | release is `(store) => store.close()` |

`choose.ts` is not in the ticket's list, but it is in `packages/daemon/src`, so the diff stays in scope.

These are not store-method lifts and stay as they are: `reconcile.ts:830`, `:843`; `in-flight.ts:40`; `daemon.ts:184-219`. Neither are `runner.close()` at `daemon.ts:230` and `:334`, which belong to a runner, not a store.

The check that does find all seven is reading every `Effect.promise` in `packages/daemon/src` after the change. The `s\.` grep is not.

## 5. A failed beat is still swallowed

`control.ts:635-656` runs `beatEffect` under `Effect.catchCause`. It swallows anything that is not interrupts-only, and the comment at `:628` reads: *"**A beat must never reject**, the first one included."*

A SQLite statement that throws inside `Effect.sync`, or a Postgres query that dies, becomes a defect, which is the same cause as a rejected `Effect.promise` today. The beacon needs no change.

"Fresh" is set only by a beat that landed (`:624-626`), so a failed beat still leaves the next one fresh.

What is new is interruption. If the beacon fiber is interrupted during a Postgres beat, the release now runs `client.end()`, where before the client was left to finish. That is the improvement the ticket's *Watch out* asks for. The query already sent still completes on the server.

## 6. What can be verified before the merge

- **SQLite** is verified by `unit/beacon-stopped-projections.test.ts`, a real store, and by the four integration files in *Done when*. Those all run on SQLite and are quick, unlike the 803-second half.
- **Postgres** is checked only by `pnpm typecheck` before the merge; its behaviour runs after the merge.
  - Nothing at unit level stands in for points 1–3 on Postgres.
  - Read `postgres.ts` against points 2 and 3 by hand.
  - After the merge, the evidence that nothing leaks is a steady stream of beats. A `daemon_status.last_seen_at` that keeps advancing every `HEARTBEAT_MS` on the conducting machine's beacon would show it. A leak shows up as Postgres refusing connections, not as an event.

## 7. Tests

These are the trap the ticket names. The fakes outside `packages/daemon` that look like store fakes are not:

- `head: async` in `apps/cli/unit/project-pause.test.ts:141` is an `EventStore`'s.
- `head: async` in `packages/conductor/unit/resolve-wait.test.ts:975` is also an `EventStore`'s.

Leave both alone.

For the four direct calls in `apps/cli/integration/doctor-daemon.test.ts` and the roughly 34 in `test/contract.ts`, wrap each one in `Effect.runPromise(…)`. Do not add a `run` helper to `src`: the ratchet counts it.

`integration/the-written-choice.test.ts:231` should call `readStatus(daemon)` (`control.ts:722`), as the ticket says.
