## #411 design note: `triage:` in the recipe

### Where it goes

Put it all in `packages/recipe/src/recipe.ts`, directly after `callFor` (`:2884-2890`) and before `export const Recipe` (`:2892`), so it sits beside `Discuss`. It has three parts:

- **`TRIAGE_WALL_MAX`**: a number in milliseconds, so #413 can compare it with `SUBSCRIBER_TIMEOUT_MS = 10 * 60_000` (`packages/daemon/src/work-loop.ts:135`) using `<`. Do not make it a string. Use **`8 * 60_000`**. Any value just under 10m would leave the subscriber no time for its own work after the agent returns: starting up, reading the hold, and appending the result. Put that reason in its doc comment.
- **`Triage`**: a `z.strictObject` with the same fields as `Discuss` (`:2851-2869`):
  - `agent: DiscussAgent.default('claude-code')`. Reuse `DiscussAgent`; do not add a second enum. Its doc (`:2780-2802`) already says it is "every runtime that can be held to `tools: "none"`", and `apps/cli/unit/discuss-agent.test.ts` checks it against `RUNTIMES`. A new enum would not be checked by anything. A one-line comment on `Triage.agent` saying so is enough.
  - `model: DISPATCH.model`
  - `prompt: DISPATCH.prompt.optional()`
  - `limits: z.strictObject({ turns, wall, usd }).default({ turns: 40, wall: '5m', usd: 0.5 })`
  - `usd` is `z.number().positive().default(0.5)`. `runtime.limits.usd` has no default on purpose (`:3222-3228`: *"absent means 'no dollar ceiling', said out loud, never assumed"*), and the triage default contradicts that. Say why in the comment: the whole of `triage:` is opt-in, so writing `triage:` is what turns the spend on, and the 0.50 comes from #427's measurement.
  - **The wall bound is a `.refine` on `wall` itself**, after the positive-duration check. Zod then reports the path as `triage.limits.wall`, the same way `discuss.test.ts` matches `/discuss\.agent/`. The message names the bound and the reason, with the bound computed rather than written in: ``must be under ${formatDuration(TRIAGE_WALL_MAX)} — the daemon gives a subscriber 10m`` (`formatDuration` is in `duration.ts:35`). The check is `parseDuration(text) < TRIAGE_WALL_MAX`, so a wall exactly equal to the bound is refused, as the ticket asks. Do the duration-shape check first so `parseDuration` (`duration.ts:13`) never throws inside the refine.
- **`triageCallFor(triage)`** (or a similar name): the `callFor` twin. It returns `{ model?, turns, wallMs, usd }`, which is the shape of the agent request's `limits: { turns: number; wallMs: number; usd?: number }` (`packages/agent/src/runtime.ts:122`). That is how "passed to the runtime as the per-triage ceiling" is met in this ticket. Nothing calls a triage agent yet; the subscriber that will is later work in #388. Claude Code already maps `limits.usd` to `--max-budget-usd` (`packages/agent/src/claude-code.ts:265`), so the resolver only has to carry the field through. The unit test checks the resolver's output; there is no runner to test against.

Register it in `Recipe` beside `discuss` (`:3079`) as **`triage: Triage.optional()`, with no `.default`**. This is the one way it must differ from `discuss`, which is `Discuss.default(DISCUSS_DEFAULTS)` because "a recipe that says nothing about `discuss:` has *declared the defaults*". For triage, absent means *nothing runs*. A default would also add the key to every parsed recipe, which is the `configHash` change that `repo.remote`'s comment warns against (`:2917-2921`). The doc comment should say both, in that order.

### Why the hash stays unchanged, and the test that proves it

`canonical` in `packages/recipe/src/resolve.ts:87-94` filters out `v === undefined` before sorting. An optional key that is never written therefore never reaches `hashRecipe`. The unit test should not just compare a recipe's hash with itself. It should:

1. assert that `'triage' in recipe` is false for a recipe without the key;
2. assert that `hashRecipe` of `BASE` equals the hash of `BASE` re-parsed through the schema. Better still, if any test in `packages/recipe/unit/resolve.test.ts` already pins a literal hash, that literal has to stay green unedited, and that is the strongest form of the check.

Put the triage tests in a new `packages/recipe/unit/triage.test.ts`, written like `discuss.test.ts`, using its `BASE`/`resolve` helpers. Cover these cases:

- absent → `undefined`
- `triage: { agent: claude-code }` → the defaults, including `usd: 0.5`
- `agent: codex` → refused, matching `/triage\.agent/`
- `limits.wall: 10m` and `8m` → refused, matching `/triage\.limits\.wall/` and the bound
- `7m` → accepted
- an unknown field → refused by name
- `triageCallFor` → returns `usd`

### Readers: say "absent" out loud, but only in the reading

`packages/recipe/src/local.ts:416-421`:

- When declared, write `triage.agent`, `triage.model` (`'(none)'` when absent, as `discuss.model` does), `triage.limits.turns`, `triage.limits.wall` and `triage.limits.usd` into `recipeValues`.
- When not declared, write one key, `triage`, as `'(not declared)'` with origin `default`, the way `runtime.limits.usd` reads `(none)` rather than disappearing (`:376-380`).

This is display only and does not touch the hash.

`apps/board/src/lib/recipe.ts:848-858`: add a row after `discussions`, named `triage`.

- **Declared:** say something like `claude-code, its default model, 40 turns, 5m and $0.50 per hold`, with keys set to the five `triage.*` keys.
- **Absent:** say `not declared — no hold is triaged`, with key `['triage']`.

The ticket only requires the row when declared. Showing the absent case as well is what the rail does for empty steps (`:794-796`: *"a step that is merely absent looks like one that was configured and silently did not run"*). It costs one row, and it answers *why did nothing triage this hold?* where somebody will look.

### What not to touch

- `askAgents` (`apps/cli/src/agents.ts`): as the ticket says, it gets no setup question.
- `pluginRefusedAt`: `discuss` is named there because an action could carry a `discuss` key. Leave triage out; nothing in `steps:` takes a `triage` key today.
- `doc/`: no ADR changes. 0118 §3 is the decision and this ticket only builds it.

### Rollout trap (not code)

The ticket's warning still applies after merge. `Recipe` is `z.object` (`:2892`), so a daemon started before this lands drops `triage:` without an error. Do not put `triage:` into `~/.lingtai/lingtai/recipe.yml` in this pass: this follows *code, restart, paste* (`doc/design/the-plugin-body.md`). A pass changes only the worktree, and nothing reads the conducting machine's file from here.

### Checks

Every claim above can be checked with `pnpm test` in `packages/recipe/unit/` and `apps/board/unit/`, plus `pnpm typecheck`. None of it needs `pnpm test:integration`. `pnpm typecheck` will catch any reader that treats `recipe.triage` as always present.
