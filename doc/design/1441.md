# #1441 design: where the PR pages' time goes

## Where it goes

There are three layers, each with one owner.

1. **`events.head` is measured where the physical read happens: in `promiseStore`, never in `memoStore`.** `packages/event-store/src/store-face.ts:56` already wraps `read` (and `readTypes` at `:58–59`) in `observedRead`. `head` at `:57` is still a plain `headFace(events, streamId)`. Add the twin of the read seam to `packages/event-store/src/observe.ts`:
   - `HeadInfo { kind }`, a `HeadObserver`, `setHeadObserver` on its own `Symbol.for(...)` key on `globalThis`, and `observedHead(streamId, run)`.
   - Export them from `packages/event-store/src/index.ts`, next to line 112.
   - Wire them in at `store-face.ts:57`.

   This boundary sits under both backends: `promiseStore` builds Postgres (`event-store.ts:619`), SQLite (`sqlite.ts:365`) and the process store (`index.ts:88`). So no driver code changes, and the span measures the face's round trip, not "SQL execution".

   `memoStore` sits above it (`request-store.ts:56–62`). It calls `store.head` only when `heads` has no entry for the stream. So only the caller that starts the read ever reaches the observer, and its span parents under that caller. A second waiter gets the kept promise and never sees the seam. "Measure once" therefore comes from the layering, and needs no bookkeeping.

   Copy what `observedRead` does:
   - With no observer, `run()` is returned as-is: "the same promise, no hop" (`observe.ts:33`).
   - With an observer, `report(head)` runs only after the promise resolves, so a rejection reaches the caller untouched and never reports a count.

2. **The board installs the observer** in `installTraceSeams` (`apps/board/src/lib/trace-seams.ts:17`). That function is only called from `installTracing`, so with no `telemetry.otlp_endpoint` nothing is installed (`:14–15`, "with no `telemetry.otlp_endpoint` nothing is installed and a request or a read is what it was"). Use `traced('events.head', ...)` with `{ 'lingtai.stream': info.kind }`, and set `lingtai.count` to the head inside `run`, exactly as `events.read` does at `:32–41`.
   - `head === 0` is a successful read of an absent stream: it gets `lingtai.count = 0` and OK status.
   - A failed read gets ERROR status and no count. `traced` already does that (`timing.ts:154–158`).

3. **The phases are board spans in `apps/board/src/lib/prs.ts` and nowhere else.** `packages/project` stays provider-neutral; that is the rule in `trace-seams.ts:8–12`: "**They start no spans of their own**".
   - `pr.numbers` wraps `topPrNumber` inside `readProjectPrs` (`prs.ts:72`). Both the list page and `prsOf` (`:109`, used by detail's `next`) then get it.
   - `pr.draft` wraps the `readDraftOf(project)` call in `readPrPage` (`:161`) and in detail's `next` branch (`:136`). That draft walk is `listTailPrs`' own `head` loop (`packages/project/src/pr.ts:107–112`), which the board cannot see into. On the list page it races `pr.numbers` over the same memoized heads, so each physical `events.head` lands under whichever of the two started it first, and the other phase shows only the wait. That is the evidence the ticket asks for, so the phase is worth its name.
   - `recipe.resolve` wraps the `recipeOf(project)` waits at `prs.ts:156` and `:128`. Wrap the call sites, not the `cache()`d body at `request-reads.ts:19`. The bar's `placeViewsOf` (`prs.ts:241`) asks for the same cached promise, and #1439 now starts the detail load alongside the bar. A span inside the body would parent under whichever render asked first, often the bar, and would leave the gap under `pr.board`/`pr.detail` unexplained. Each caller's wait is what the witness trace is missing.
   - `spend.read` wraps `spendByPr` at `:164–167` (list) and at `:364` in the detail block (the `own` read). `readSpendEffect` opens a store per call (`packages/projector/src/spend.ts:386–389`, `withStoreEffect({ url, max: 1 }, ...)`). So this phase covers store open, acquire and query together, and the existing `db.acquire` child (`trace-seams.ts:44`) separates out only the pool wait. Do not name it anything SQL-specific.

   **No `async` keyword and no new `Effect.run*`** (the ratchet). The phases inside `Effect.gen` use `tracedEffect` (`timing.ts:214`). The phases around a promise use `traced(...)` with a plain arrow, `() => recipeOf(project)`.

## The decision that isn't in the ticket: ancestry needs the board's tracer on these runs

`readPrPage`'s run (`prs.ts:158`), `readPrDetail`'s run (`:330`) and `prsOf` (`:109`) are bare `Effect.runPromise` calls. Effect resumes fibers from one shared dispatcher, so AsyncLocalStorage alone hands a stage whichever context scheduled the batch. That is the reason `boardTracer` exists (`timing.ts:184–188`, "AsyncLocalStorage alone would hand a stage whichever context scheduled the batch; the fiber carries its own").

The list page runs `readProjectPrs` and `readDraftOf` on two fibers (`:160–162`). An `events.head` started on the second fiber after any yield would find an arbitrary parent. That would break the ticket's "preserve request ancestry", and also "separate requests never share parentage", because the context leaked would be another request's.

So all three runs get what `board.ts` already does:
- capture `const active = context.active()` before the run (`board.ts:999–1000`, "The caller's span (`queue.project`), taken here because the run below resumes elsewhere (#1359)");
- pipe the run through `Effect.withTracer(boardTracer)` and `Effect.provideService(ApiContext, active)` (`board.ts:1079`).

For `prsOf`, take `active` inside the `cache()`d function, so the first caller owns it. `tracedEffect` reads `ApiContext` (`timing.ts:216`), so the phases nest under `pr.board`/`pr.detail`. The head span is started synchronously inside the `tryPromise` thunk, which `boardTracer` evaluates with the phase's context active, so it nests under the phase.

This is not a change to the algorithm: no read moves, and no concurrency changes.

## What stays as it is

- `memoStore` is unchanged. Invalidation still works because `forget` deletes `heads` (`request-store.ts:29`), so the next `head` after an append is a new physical read and gets a new span. A kept rejection stays a rejection (`:10–11`): its waiters get no span and no count.
- `topPrNumber` and `listTailPrs` keep their loops (out of scope).
- The daemon never installs the seam, so its heads are untouched.
- An interrupted fiber does not cancel the promise underneath. `traced` ends the `events.head` span when the promise settles, and `tracedEffect`'s `onExit` ends the phase (`timing.ts:220–224`). Nothing is kept in a map, so the "bounded cleanup" requirement is met because nothing is retained, not by a cleanup routine.
- No phase span carries a count. A probe count on `pr.numbers` would be the highest PR number plus one, and the ticket says never to export PR numbers. The walk's length is visible as the number of `events.head` children, which counts operations, not an identifier. `lingtai.stream` is the only string attribute anywhere, and `kindOf` already reduces it to the prefix (`observe.ts:27–30`).

## Tests (all unit, none needs integration)

**Event store** (`packages/event-store/unit/`): `observedHead` with no observer returns the very same promise (`toBe`), and with an observer it reports on resolve and not on reject.

**Board**, in `apps/board/unit/trace-spans.test.ts`, following the `events.read` case at `:267–285`: build a `promiseStore(fromPromiseStore(fake))` around a fake with a deferred `head`, then wrap that in `memoStore`. Cases:
- **Shared waiters:** two concurrent `head`s of one stream give one `events.head` span, one fake call, and both callers see the same value.
- **Separate requests:** two `memoStore`s over one fake give two calls and two spans, each under its own page span.
- **Absent stream:** head 0 gives `lingtai.count = 0` and OK status.
- **Failed read:** a rejection gives ERROR status, no `lingtai.count`, and the second waiter gets the same rejection with no second call.
- **Invalidation:** `append`, then `head`, gives a second call and a second span.
- **Telemetry off:** with the observer unset, the fake's call count is the same and no span is created.

**PR pages:** extend the `:287` case with a stubbed `readPrPage` path: `pr.numbers`, `pr.draft`, `recipe.resolve` and `spend.read` under `pr.board`, and the `events.head` spans under `pr.numbers` or `pr.draft`, never under the page or a root. Assert parentage and names, never total span counts. No assertion has a timing threshold.

## What only the log/trace settles

Whether the 1.256 s and 2.829 s gaps belong to `pr.numbers`, `recipe.resolve` or `spend.read` is the after-cohort's question. Read it from the new spans' durations under `pr.board` on the witness route. Do not assert it from the code.
