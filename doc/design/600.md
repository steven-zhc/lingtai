# #600: design note

## The event

Add it beside `WaitResolved` (`packages/domain/src/events.ts:308`) and register it in `EVENTS` (`:1947`). `SCHEMA_VER` is derived from `EVENTS` (`:2037`), so it starts at version 1 without being listed anywhere else.

```ts
export const SplitChild = z.strictObject({
  key: ChildTicket.shape.key,               // split.ts:24
  number: z.number().int().positive(),      // the issue number, 161
  id: z.number().int().positive(),          // GitHub's REST id, 5466453198
})
export const TicketSplit = z
  .strictObject({ waitId: WaitId, children: z.array(SplitChild).min(1), blockedBy: z.array(Dependency) })
  .superRefine(/* consistency only, see below */)
```

**Strict, for the reason `WaitStarted` gives.** Its comment (`:285–288`) says: *"zod 4 strips unknown keys from a plain `z.object`, so a payload carrying a second shape beside `reason` would parse silently."* The likely slip here is a writer that spreads `{ ...childTicket, number, id }`. That would copy the approved title, body and kind into this event, which the ticket's Watch out forbids. With `strictObject` that write fails to parse. With `z.object` it would be stripped silently. Don't reuse `ChildTicket` itself, and don't use `.extend` on it.

**`waitId` points at the plan instead of copying it.** The approved plan stays on `WaitResolved{Split}`. `waitId` names that wait, so a reader joins to the plan rather than reading a second copy of it. The ticket's field list doesn't name `waitId`; adding it is my call. It also gives `id` and `number` the same discipline #599 asked for: two different integers, never confused.

**Consistency, not the plan's rules.** The `superRefine` checks three things:
- keys are unique;
- numbers are unique;
- every `blockedBy` entry names two keys that appear in `children`.

Do **not** call `splitPlanProblems` (`split.ts`). It enforces the plan's own rules: at least two children, non-blank titles and bodies, known kinds. This event records what was written, not what was planned.

**`blockedBy` holds child-to-child links only**, in `Dependency`'s `{ ticket, blockedBy }` key form (`split.ts:28`). The parent is also held by each of its children (*"#561 blocked by each child"*, `doc/decisions/0118/Split.dc.html:447`). That hold follows from `children` and has no key, so it is not a `Dependency` row.

**Order on the parent's stream:** `TicketSplit` first, then `WaitResolved{Split}`. Two sources say so:
- `Split.dc.html:448–449`: *"record the split … end the wait: WaitResolved{Split}, then a requeue"*;
- 0118 §12 (`doc/decisions/0118-a-hold-explains-itself.md:618`): *"Create the children and their GitHub dependency links, then record `WaitResolved{Split}`."*

No writer is added here, but the fold below depends on this order.

Leave `applyTicket` (`packages/domain/src/ticket.ts`) alone. `TicketSplit` must **not** join `LIFECYCLE_EVENTS` (`:214`); its comment says *"`closed` has to absorb exactly these and nothing else"*. Folding the split into `TicketState` belongs to the close-rule ticket.

## The fold: its own column, never `note`

`WaitResolved` comes after `TicketSplit`, and its non-Approve branch writes `note = null` (`packages/projector/src/task-view.ts:665`). Later, `TicketReleased` writes `note: d.reason` (`:268`). Children folded into `note` would therefore vanish one event later.

So add a `split jsonb` column, holding `children` as written. Follow the precedent of `answer` (`:146–152`): *"Assignment, not a list, so a replay lands on the same value … Kept across a claim and a landing."* Rules for the column:
- No other case clears it.
- A second `TicketSplit` replaces the value.
- Write it with the existing `set` helper (`:806`), in the outer switch beside `TicketClosed` (`:290`). It is a plain ticket-stream event, so it does not go through `cardFactOf`.
- Pass the value as `JSON.stringify(...)`, as `wait_reason` is written (`:564`). Then `sqlite.ts`'s `jsonb → text` rewrite (`:210`) covers it with no new translation.

The fold must not move `state`. A split parent goes back to `queued` through `WaitResolved`, as today. Excluding it from the queue is GitHub's blocked-by hold, and closing it is the later close rule (`Split.dc.html`, *How #561 ends*).

## The read: both twins, through `columnOf`

- Add `split: { key: string; number: number }[] | null` to `TaskCard` (`task-view.ts:869`). Leave `id` out of the card: the board has no use for it.
- Read it in `postgres.ts` (beside `:126`) and in `sqlite.ts` (beside `:323`, through `parseJson`).
- Read it with `columnOf(row, 'task_view', 'split')`, as `wait_id` is read. Then a table built before this change raises shape drift instead of drawing a card with no split.
- Put the sentence in one exported function beside `waitOf` (`:984`), `splitLine(split) → 'split into #12, #13'`, so the board and any CLI say it in the same words.
- On the board, carry it through `boardCardOf` (`apps/board/src/lib/board.ts:614`) as its own field. Render it as its own `<p>` next to `card.note` (`apps/board/src/app/page.tsx:363`), not merged into `note`.
- Optionally, add one `FORMAT` line in `apps/board/src/lib/history.ts:141`. That map is `Partial`, so nothing fails without it.

**After the merge, the conducting machine must run `lingtai projection rebuild task_view`.** `shape.ts` reads the declared columns out of the DDL. A live table without `split` will show as drift in `lingtai doctor` and at daemon start, and `columnOf` will refuse board reads until the rebuild runs. Writes are not at risk in the meantime: nothing appends `TicketSplit` until the writer lands.
