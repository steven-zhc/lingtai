## Design: #611, an optional step where a check refuses once and one fix round lands it

All the changes go in `doc/tutorial.md` and `apps/site/unit/docs.test.ts`. Code is not touched.

### 1. The refusal is planted on purpose, and the tutorial says so

No ordinary ticket fails `npm run check` reliably. The reason is that Lingtai tells the agent to run the checks itself. `checksBrief` puts every `build:` command into the implement prompt under *"Run this before you finish:"* (`packages/conductor/src/prompt.ts:301-320`). Chapter Garden's own `AGENTS.md` says the same thing: *"Run `npm run check` and `npm run build` before submitting."* So a natural mistake, like a wrong type or a bad field, gets caught and fixed by the agent before the `build` step ever sees it. A ticket built on that would pass first time on most runs, which is the failure the ticket warns about.

So the step's ticket **asks for the mistake and says why**, and the prose around it says so too, in one sentence: *this ticket asks for a mistake on purpose, so you can watch a check catch it.* Hiding it would teach the reader something false about why work fails. The ticket body needs four parts:

- **The task.** The next chapter of a story, and it must be a *different* story from Step 2's. The reader may already have added chapter 2 to whichever story they picked, so don't hard-code one title.
- **The planted mistake.** Write the new chapter's `order` as a quoted string, e.g. `order: "2"`. Chapter Garden's schema has `order: z.number().int().positive()` (`chapter-garden/src/content.config.ts`), so a string is refused, and the refusal names the field. The fix is one character per file, so the round is cheap after an expensive first write.
- **"Do not run `npm run check` or `npm run build` yourself; Lingtai runs them."** Without this line the agent follows `checksBrief` and fixes the mistake before the gate. This line is what makes the failure reliable.
- **The tie-breaker.** *"If Lingtai reports that a check refused this change, fix what the check names. The check wins over this ticket."* The fix-round prompt still carries the ticket body (`{{body}}` and `{{failure}}` are filled into the same template, `prompt.ts:228-245`), so without this line the agent sees "write a string" and "a string was refused" together and may argue instead of fixing. The cold reviewer reads the ticket too, and could raise the unquoted `order` as a deviation, which would buy a second round. The same sentence covers that case.

**Verify the mechanism before writing prose.** In a scratch Chapter Garden clone, quote `order` in one existing chapter and run `npm ci && npm run check`. Confirm it exits non-zero and that the output names `order`. If `astro check` (astro 7.4.2) does not validate content frontmatter, `npm run build` will, and it is the recipe's second `build:` command. In that case, say "the build refused" rather than "`npm run check` refused" everywhere, and note the switch in the PR. Don't write the step against a refusal you have not seen.

### 2. Run it for real, at least twice

Use Step 1's recipe as is. It has `rounds` at its default of `2` (`packages/recipe/src/recipe.ts:3308`), and `red` is answered by the built-in `same-worktree` judge (`packages/conductor/src/judge.ts:483-484`). So one refusal buys one round and nobody is asked. Each run should show this sequence in History:

1. `build` failed.
2. A round opens (`RoundOpened`, rendered as `round 1 — …` by `apps/board/src/lib/history.ts:467-469`).
3. `implement` runs at round 1.
4. `build` passes, then `review` passes.
5. The pass holds at `proposed` (Step 1's `--land hold`).

For the PR, record per run:
- the ticket number
- whether the first `build` refused, and the first line of what it named
- how many rounds ran
- the attempt's cost figure

Any of these counts as a failure of the ticket text, not bad luck, and means changing the text and starting the count again:
- the first build passed
- the review raised a finding
- a second round opened

### 3. Where the step points on the task page

Quote what the board actually renders on your own runs. The strings below come from code, not from an observed page:

- **The refusal.** The **History** tab (the five tabs are History, Diff, Findings, Attempts, Ticket; `apps/board/src/app/task/[id]/page.tsx:37-39`). The row is clipped at 160 characters (`history.ts:93`), and opening it shows the build's output in full (`history-row.tsx`).
- **The round.** In the same History tab, the `round 1` row, followed by `implement` running again. **There is one attempt row, not two**: since #143 a refusal buys a round inside the pass, not a new run (`page.tsx:247-252`). Say this in a single clause, because a reader will look for "attempt 2".
- **The spend.** The **Attempts** tab. Each attempt row shows turns, duration, cost and diff size (`page.tsx:262-268`). `/spend` has the totals.
- **The run log.** It sits inside the attempt row (`<RunLog>`, `page.tsx:296-300`). The run id is printed under the row (`page.tsx:280`), and `lingtai attach <runId>` reads the same file. While the round is running, the page itself follows the live log at the top (`run-log.tsx:8-10`).

**Trap: the run log is deleted when the run lands.** `packages/agent/src/run-log.ts:53` says *"it is deleted when that run lands"*, and `:101-102` says *"landed → delete, did not land → keep"*. So the step must tell the reader to open the run log, or `attach`, **before** pressing Approve. Afterwards there is nothing to read. The hold at `proposed` is what makes this possible. Then the reader approves exactly as in Step 4, and "as in Step 4" is all the step needs to say.

### 4. Where it goes, and the caps

Add a new `##` section between Step 4 and Part 2, titled something like `Optional — Watch a check refuse`. Change Step 4's closing "To put work on GitHub, continue with Part 2." so the optional step is offered first.

The step's shape:
1. One sentence on the planted mistake.
2. `lingtai ticket new --project chapter-garden`, plus the `text` block to paste. Give it a `labels: bug` or `feature` line in the same form as Step 2's block.
3. The four places from §3, as a short list.
4. Approve as in Step 4.

`lingtai start` and the board are already running from Step 3, so don't repeat them.

The caps (`apps/site/unit/docs.test.ts:94-125`):
- **Part 1** is everything before `\n## Part 2`, and its prose is at **927 of 1100** today. The new section can't fit inside it.
- So give the section a slice and cap of its own, the way #596 split off Part 2 (the comment at `:104-106` gives the reason). Measure Part 1 up to the new heading, measure the new section up to `## Part 2`, and set its cap at about 350.
- Add the heading to the exact `##` list at `:117-124`.
- **The whole page** is at **1650 of 2000** words, counting code blocks. Keep the section under about 300 words in total, ticket block included, rather than raising that cap.
- Measure the slices the way the test does: prose with code fences removed, split on whitespace.
