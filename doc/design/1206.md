# Design: #1206, building the base check's question without an attempt

## Where it goes

`baseCheckQuestion` goes in `packages/conductor/src/base-check.ts`, below `createBaseCheck`. It is an `Effect`, because it reads the caller's context (see *Git* below), and it is never `async`. The effect-ratchet test counts both (`packages/domain/unit/effect-ratchet.test.ts`). It returns one of two things:

- `{ question: BaseCheckQuestion; observed: 'sandboxed' | 'degraded' | 'off by choice' | null }`
- `{ notBuilt: string }`

`observed` is what `observedKindOfDecision` returns (`sandbox-record.ts:69-74`). The pass needs it for `observeTheSandbox(observed, runId)` (`conduct.ts:3860-3863`). The builder computes it, so it is never derived twice.

What stays in `conductWork`'s `baseIsRed` (`conduct.ts:3801-3868`):
- choosing `baseSha` (`:3810-3811`). The *no base commit was cut* refusal belongs to the pass, because the builder takes a sha.
- `baseAbort` (`:3799-3800`).
- `runLog.note` of whatever `notBuilt` says.
- `observeTheSandbox`.
- mapping the answer to `{ red } | { notRed }`.

The `notBuilt` sentence for a build action that is missing or is not a `run:` is today's `'not a run: action in the recipe'` (`:3807-3808`). The run-log line stays word for word.

## The sandbox: pass the decision, not the raw service

The ticket's Watch out says *"the question carries the asking pass's own sandbox decision"*. If the builder called `decidePassSandbox` itself, the pass would decide twice. Each call runs `readHost` and builds the host's service Effect again (`sandbox-decision.ts:31-58`). A second answer could then differ from the one the pass claimed under (`conduct.ts:1051`), and the pass's `observeTheSandbox` would report one decision while the question carried another.

**So the builder takes a `PassSandbox`** (`sandbox-decision.ts:20-24`): the decision plus the service, as `decidePassSandbox(recipe.sandbox, host)` returns it.
- The pass hands in the `passSandbox` it already has (`conduct.ts:1051`).
- #1208's look calls that same `decidePassSandbox` and hands in the result. That keeps one rule and no second one.
- The unit tests can build the *refused* and *sandboxed with no service* cases without `readHost` touching the real host.

This narrows the ticket's "the host's sandbox service" to "the host's decided sandbox". The decision still comes from `decidePassSandbox`, as the Watch out requires.

The refusals mirror `conduct.ts:1055-1072`:
- `kind === 'refused'` returns `notBuilt: decision.why`.
- `kind === 'sandboxed'` with `service === undefined` returns `notBuilt` with the sentence at `:1070-1071`.

Neither branch builds an unsandboxed question. Neither can be reached from a pass, because the pass refused both before its claim.

**The builder makes its own `RunSandbox` with `makeRunSandbox`, without `appends`.** It passes the same `project`, `mirror`, `cache`, `additions` and `codexNamed` as `conduct.ts:3788-3797`. Dropping `appends` changes nothing:
- The base check calls `sandbox.wrap(argv, path, env, profile)` with no `log` and no `keys` (`base-check.ts:226`).
- `makeRunSandbox` records only *"keys === undefined || pass.appends === undefined ? service.wrap(input)"* (`sandbox-decision.ts:128-130`): *"Without keys … nothing can be recorded under them"*.

The fingerprint is `service.fingerprintOf(inputOf(...))` (`sandbox-decision.ts:104-105`). That is a function of the same service and the same inputs, so the boundary matches the pass's own wrap. That is the property the new unit test asserts.

The pass keeps its own `runSandbox` for the `run:` commands (`conduct.ts:4151`). Edit the #1153 comment at `conduct.ts:3783-3787`: "one wrap for the pass, whoever asks" stops being true of the base check. Say instead that the base check builds an identical wrap with no appends.

## The env: take the resolved env, not only its values

`envForExtension` reads `env.merged` (`conduct.ts:1174-1175`). `plant` writes `env.values` (`conduct.ts:1856`). So the builder takes the object `host.resolveEnv` returns (`env` at `conduct.ts:1159`), not a bare record, and it applies `runnableEnv(extensionEnv(env.merged, declared, productionPatterns(recipe.env.refuseHosts)).values)` itself.

`extensionEnv` throws on a denied production value. A pass has already checked that before its claim (`conduct.ts:1177-1194`); a look has not. So the builder wraps its own calls in `Result.try` and turns a throw into `notBuilt` carrying the error's message. It never throws.

## Git: the cut runs against the mirror, not the pass's worktree

Today `tree.cut` and `tree.remove` run `gitAskedEffect` → `gitHere`. Its `cwd` is the pass's own worktree (`conduct.ts:1952`, `cwd = worktreePath(home, project, runId)` at `:1403`). A look has no worktree. The builder runs:

`repo.git([...], { token, env: gitEnv, cwd: mirrorPathFor(project, home) })`

under the same `mirrorWrite(mirrorPathFor(project, home), …)`, and the submodule update keeps `cwd: path` (`:3841-3845`).
- A linked worktree and its mirror share one common git dir, and `worktreePath` is absolute (`packages/repo/src/worktree.ts:94`). So `worktree add --force --detach <path> <sha>` registers the same worktree from either place.
- That claim is only proven against real git, in the integration half, after the merge. The unit check that stands in: a fake `Repo` in the new test, asserting `cut`'s argv and that its `cwd` is the mirror.

The ticket's argument list leaves out two things the tree needs, `token` and `gitEnv` (today `options.token` / `options.gitEnv`, `:3842-3843`), so they are parameters. `Repo` comes from context (`yield* Repo`, as at `conduct.ts:764`).

**Capture `Effect.context()` inside the builder, when it runs** (`:3804-3805`). This keeps the comment *"Read before any mirror write, so a permit holder is never carried into the detached runs"*. Use `Effect.runPromiseWith(services)` for `detached`, which the ratchet does not count.

## The boundary on the answer

- `lookup` already has the boundary it matched on (`base-check.ts:135`) and puts it on `red` and `green`.
- `check` puts `ran.boundary` on them (`:290-292`).
- The unsandboxed hit at `:167` is `UNSANDBOXED`.
- The port's `red` (`run-attempt.ts:924-934`) gains a required `boundary: string`, and `baseIsRed` passes `answer.boundary` through.

**This conflicts with Done-when's *"only their imports changed, never an expected value"*.**
- `base-check.test.ts:87`, `:98` and `:108` pin the whole answer with `toEqual`, so an added field fails them.
- `a-base-that-is-red-buys-no-round.test.ts:66` and the mapping near `:136` build a `red` that tsc will reject once `boundary` is required.

The Want asks for the field, so those literals gain `boundary: 'unsandboxed'`, and no existing value changes. Name the five lines in the commit body, so a reviewer sees an addition and not an edited expectation.

## Tests

Put the new tests in a new `packages/conductor/unit/base-check-question.test.ts`. They use a fake `SandboxApi`, a fake `Repo` and `createMemoryEventStore()`, with no attempt in scope.
- **Sandboxed and unsandboxed recipes:** build the question and run it through `createBaseCheck`. Assert that `answer.boundary` equals the `boundary` of the `BaseChecked` it appended. Then build a second question the way a pass does (the pass's own `makeRunSandbox` arguments, with `appends`) and assert the same fingerprint.
- **Refusals:** a `refused` decision, and a sandboxed decision with no service, each return `notBuilt` and no question.

## Docs

`base-check.ts:4-6` says *"`conduct.ts` builds one per store and `runAttempt` asks it through `baseIsRed`"*. Add that `baseCheckQuestion` builds the question and that the pass is one caller of it. No ADR changes, and none is contradicted: the key, the boundary rule (0108 §13) and the in-flight join (`base-check.ts:332-350`) are untouched.
