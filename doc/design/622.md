# Design: #622. The daemon commands move to `@effect/cli`, show their steps, and close on one verdict

## The trap: `lingtai.ts` has two callers that do not go through the entry

Since #616, migrating a command has meant adding it to `MIGRATED_COMMANDS` (`migrated.ts:9`) and turning its `case` in `lingtai.ts` into the *"runs from the entry"* refusal (`lingtai.ts:1176-1190`). **Do not do that for `start`, `daemon` or `service`.**

- **Supervisor files.** Every installed supervisor file runs `lingtai.ts`, not `entry.ts`:
  - `launchdPlist` builds `[join(inputs.root, 'apps/cli/src/lingtai.ts'), ...job.argv]` (`service.ts:299`).
  - `systemdUnit` writes the same path into `ExecStart=` (`service.ts:397`).
  - `DAEMON_JOB.argv` is `['daemon']` (`service.ts:134`).
  - If `daemon` became a refusal, every LaunchAgent and systemd unit on disk would exit 2 and be respawned every thirty seconds. The comment at `lingtai.ts:1105-1108` explains why this matters: *"an installed LaunchAgent or systemd unit has `lingtai daemon` written into its plist, and renaming a command must not stop a supervisor that is already on disk."* `version` was kept working at `lingtai.ts:1171-1174` *"for a process started from this file, as a service's plist starts it"*. Follow that precedent.
- **An integration test.** `apps/cli/integration/service.test.ts:1185-1189` runs `lingtai.ts service status` directly.

The second half of the trap: **`lingtai.ts` runs `main(process.argv…)` on import** (`lingtai.ts:1218`). `daemonCommand` (`lingtai.ts:369-842`), `serviceOptions` (`:166`), `boardOptions` (`:214`), `boardMissing`, `boardAnswering` and `liveBoardWorld` (`:254-368`) all live there. If `cli.ts` did `await import('./lingtai.ts')` to reach them, it would run a second `main` against the same argv.

**The shape:**

1. Move lines `166-842` into a new module, `apps/cli/src/daemon.ts`, that has no side effects at import. `controlCommand` (`:865-956`) moves into it as well.
   - `lingtai.ts` imports from it: `board` still needs `liveBoardWorld`, and `restart` and `service` need `serviceOptions`.
   - `cli.ts` imports it lazily, the same way `status` loads `status.ts` (`cli.ts:46-49`).
2. `start`, `daemon`, `service`, `restart`, `shutdown`, `pause` and `resume` all join `MIGRATED_COMMANDS`, so the entry sends them to `@effect/cli`.
   - `daemon` is in the list because `lingtai daemon` typed at a terminal goes through the entry. It stays out of help, which already calls it *"the old name of start"* (`commands.ts:327-336`).
3. In `lingtai.ts`:
   - `start`, `daemon` and `service` **keep working cases** that call the moved functions. Add a comment naming the plist and `service.test.ts:1186` as the callers.
   - `restart`, `shutdown`, `pause` and `resume` move into the refusal group at `:1176`.
   - `satisfies never` still holds.
4. Do not touch `launchdPlist`, `systemdUnit` or `DAEMON_JOB.argv`. Changing what an installed file runs is a separate decision, and it would only reach a machine after `service install`.

The PR states that a supervised daemon is still started through `lingtai.ts daemon`, and that this is why those cases remain.

## `--json`: `service status` only, and 0121 gets one sentence

Every command in this group is `effect: 'changes'` (`commands.ts:314`, `:330`, `:342`, `:360`, `:379`, `:395`, `:409`). 0121 §5 gives `--json` to commands that only read, and to verdict-answering commands, but only to *"the waiting on you group and `now`"*.

- **The one read here is `service status`.** It is a subcommand of a `changes` command, and the ticket's *"each read command takes `--json`"* and *"where the command reports state"* both point at it.
- **`pause`, `resume`, `shutdown`, `restart`, `start` and the other `service` verbs get the text verdict and no `--json`.**
  - Extending §5's verdict clause to them is a decision the ticket did not ask for.
  - `start` is a foreground process that runs for hours, so "one JSON value and nothing else" (0121 §5) cannot describe it.
  - Nothing parses their output today. I searched outside `src/`, tests, `decisions-archive/`, `design/` and `experiments/` for `paused by`, `resumed by`, `shutdown asked by`, `not restarting`, `service status` and `nothing to do`:
    - The only hits are prose. `CLAUDE.md:250` quotes `another daemon holds the lock — nothing to do`, and `doc/operating.md:1288-1289` names the commands in a table.
    - `scripts/` holds `deploy-site.sh` and `the-pass.py` and nothing else.
  - So no caller moves to `--json`. Say so in the PR, because the *Watch out* asks for it.

**Edit 0121 in place.** This is one ADR per topic (`doc/README.md`, and CLAUDE.md agrees), so it is an edit, not a new file. Add one sentence to §6: *"A command that changes something but has a subcommand that only reads (`service status`) takes `--json` on that subcommand alone."* Also update the doc comment at `commands.ts:24`. Do not add a third `effect` value.

### `service status --json`

Today `status` prints two reports through `log`: `report()` (`service.ts:866-874`) and `reportBoard()` (`:1096-1117`). The exit code is `daemon !== 0 ? daemon : board` (`:1500`). Change it like this:

- Split it into a read, `readServiceStatus(…) → ServiceStatus`, and two pure functions, `renderServiceStatus(s) → string[]` and `serviceStatusJson(s)`. These are the same three parts `status.ts` exports (`readStatus`, `renderStatus`, `statusJson`; see `cli.ts:50-54`).
- `serviceCommand`'s `'status'` case calls the read and logs the rendered lines one per `log` call, so the signature and the exit codes stay as they are.

The document:

```json
{"version":1,"command":"service status","platform":"launchd",
 "conductor":{"target":"gui/501/ai.nextloom.lingtai.daemon","supervisor":{"lines":["state = running"]},"beacon":"…"},
 "board":{"target":"…","supervisor":{"unread":"launchctl print exited 112"},"url":"http://…","answers":null}}
```

- `supervisor` is `{lines}` or `{unread}`. This is `askSupervisor`'s own split (`service.ts:869`). An unread supervisor is never folded into "not loaded".
- `beacon` is the string `options.liveness()` returns (`service.ts:594`), or `{unread}` when that read throws (`:872`).
- `answers` is `boardAnswers()`'s three-way value (`:904-910`): a URL, `null`, or `{unread}`.
- `missing: {why, remedy}` appears only when `options.board.missing()` is non-null (`:1111-1115`).
- **A supervisor that could not be read is still the status document, with exit 1.** It is a fact the report carries, not a failure to run.
- **`NO_SUPERVISOR`** (`:774-776`) is the case where the command could not run. It becomes the `error` document with code `no-supervisor`, exit 1, via `printJsonError` (`output.ts:121-124`).

The text layout uses `section` and `keyValues` from `output.ts`. Two rules from `service.ts:1492-1494` (*"Two jobs, two reports, and never one summary"*) and from `service.ts:36` (*"loaded"* is not *"taking work"*):

- The two jobs get one section each.
- The supervisor's raw lines are printed verbatim, indented, under a `supervisor` key that also names the target. They are never summarised into a word.

## Parsing: `parseRestartArgs` stays the authority on restart's line

`parseRestartArgs` (`restart.ts:146-205`) exists because a boolean must never consume the next word:

> `lingtai restart --dirty picking up #88` would record `dirty: "picking"` … and the reason is what `ConductorStarted` carries.

It also refuses `--anyway` by name (`:169-175`) and refuses any flag it does not have (`:177`). The integration tests that pin it (`integration/restart.test.ts:353`, `:369`) cannot run inside a pass.

**Declare restart's options in `@effect/cli`, and also run `parseRestartArgs` as a precheck in `runCli`.** This is the same place #621 put its own prechecks (`cli.ts:347-356`).

- Strip `--no-color` from the argv first. Otherwise `parseRestartArgs` refuses it as *"lingtai restart has no --no-color"*.
- On `{ok: false}`, print `message` to stderr and exit 2. The `--anyway`, `--timeout` and *"has no --x"* sentences and their exit codes are then byte-identical.
- After parsing, the handler builds `RestartArgs` from the parsed options.
- Add a unit test that feeds the argv cases from `restart.test.ts:353-380` through both `runCli`'s parse and `parseRestartArgs` and asserts they produce the same `RestartArgs`.

The other commands:

| today | after |
|---|---|
| `pause`/`shutdown`: `flags['reason'] ?? positional.join(' ')` (`lingtai.ts:880`, `:899`) | `Args.text({name:'why'}).pipe(Args.repeated)` joined with `' '`, plus an optional `Options.text('reason')` that wins when given |
| `pause` with a blank reason prints `lingtai pause <why>  — a pause needs a reason` on stderr and exits 2 (`:881-886`) | unchanged, and refused in the handler |
| `shutdown --timeout` errors print `--timeout takes a duration like 30m or 90s, not "…"`, `--timeout takes a positive duration`, and the `--force`/`--timeout` sentence, each exiting 2 (`:903-923`) | unchanged, and refused in the handler |
| `service stop` prints two named lines and exits 2 (`service.ts:759-766`) | a `runCli` precheck, before parsing, prints the same two lines |
| `service <verb>` with an unknown verb prints `lingtai service install\|start\|…` and exits 2 (`:767-770`) | an `@effect/cli` usage error, exit 1. Name this in the PR, as #621 did |
| `restart --no-conduct`/`--no-merge` under a supervisor prints the `${kept.path} decides how…` sentence and exits 2 (`lingtai.ts:1129-1135`) | unchanged, in the handler |
| `controlCommand`'s own `--help` guard (`lingtai.ts:869-872`) | delete it. `routeOf` answers `--help` before any handler runs (`migrated.ts:31-33`) |

`service` uses `Command.withSubcommands`: `install`, `start`, `shutdown [why…]`, `restart [why…]`, `status [--json]` and `uninstall`.

- **Each handler rebuilds `[verb, ...why]` and calls `serviceCommand(args, options)` with the signature it has today.** `restartSupervised` calls `serviceCommand` with an argv internally (`lingtai.ts:1140-1149`). The integration tests call it the same way, through `command(...).go('status')` (`service.test.ts:1158`).
- Keep `prepareRestart`, `restartSupervised`, `openDaemon`, `waitForTheLock` and `pauseCommand` with their signatures unchanged, for the same reason.

## Steps: what is added, and the rule that keeps 3,000 lines of untestable assertions true

`integration/service.test.ts` is 2,038 lines and `integration/restart.test.ts` is 1,059. Neither can run inside a pass. Some of their assertions compare whole array elements:

- `expect(out).toContain('  state = spawn scheduled')` (`service.test.ts:347`, `:1159`)
- `expect(err).toEqual([NO_SUPERVISOR])` (`:286`, `:307`)
- `expect(err).toEqual([])` (`:1520`)

**The rule:** every line that `serviceCommand`, `prepareRestart`, `restartSupervised`, `openDaemon` and `waitForTheLock` write today is still written unchanged, as its own `log` or `error` call, to the same stream. The new layout only **adds** lines:

- a step line when a phase begins
- one closing verdict line from the `cli.ts` handler

**Nothing new goes to `error`.** This rule is also how *"keep every fact"* and *"`RESTART_GUARDS` and every refusal sentence stay"* are met: none of those strings changes. `RESTART_GUARDS` and `SUPERVISED_ONLY` (`restart.ts:537`, `:648`) are not touched.

**The `service status` exception.** It is restructured, as above. Change its assertions at `service.test.ts:1150-1161` and `:1679` to `out.join('\n')` containment of the same facts. Do this by reading, and list them in the PR as *checked by reading, not run*. That is how #621 handled `requeue-into-body.test.ts`.

**The `Steps` interface.** Add it in a new `apps/cli/src/steps.ts`, injected and optional. The default prints labels through `log`, so existing callers get the additive lines and nothing else:

```ts
interface Steps {
  begin(label: string): void
  progress(line: string): void
  end(): void
}
```

- `begin(label)` writes one line: the label, in `accent`. Examples: `checking`, `draining`, `checking again`, `starting`.
- `progress(line)` is the repeated *"still draining after 300s — <in flight>. ctrl-c …"* line from `waitForTheLock` (`restart.ts:1347-1355`). It is the only line that changes behaviour:
  - **On a TTY** it sets the spinner's message instead of adding a scrollback line.
  - **Off a TTY** it is written exactly as today.

  The spinner is `@clack/prompts`' `spinner`, live only when both streams are terminals. Use `prompt.ts`'s `interactivity`/`refusal` check (`prompt.ts:90-104`), because *"piped output is the same bytes either way"*. A launchd log or a test's collector is not a TTY, so it gets today's bytes. On a TTY the wait still says, every `SAY_EVERY_MS`, what it is waiting for and how long it has waited. That is the *"waiting, not hung"* promise.
- **These lines stay ordinary `log` lines in every mode:**
  - `could not ask who holds the lock — …` (`:1342`)
  - `draining … — <in flight>` and *"It is waiting, not hung"* (`restart.ts:994-1000`)
  - `waiting for the board to answer … It is waiting, not hung.` (`service.ts:915`)
- `end()` clears the spinner before the next line is written.

Where the steps begin:

| command | phases |
|---|---|
| `restart`, terminal path (`prepareRestart`, `restart.ts:894-`) | `checking` → `draining` or `waiting` → `checking again` → `starting` (`openDaemon`) |
| `restart`, supervised (`restartSupervised`, `:1100-`) | `checking` → `draining` (via `service shutdown`) → `checking again` → `starting` (via `service start`) |
| `service shutdown`, `service start`, `service restart`, `service install` | `draining`, `unloading`, `starting`, and `the board`, for whichever of these the verb does |

## Verdicts: reuse `verdict.ts`, text only

`renderVerdict(verb, v)` (`verdict.ts:31-45`) already draws `✓`/`✗`, the verb, `(<reason>)`, the subject in `muted`, and the detail indented beneath. Use it for the three small commands, whose output is all detail:

| command | accepted | detail, verbatim |
|---|---|---|
| `pause` | `✓ paused` | `paused by <by> — <reason>` and `${RUN_UNDER_A_PAUSE}.` (`pause.ts:23-25`) |
| `resume` | `✓ resumed` | `resumed by <by>` (`lingtai.ts:892`) |
| `shutdown` | `✓ shutdown asked` | `shutdown asked by <by> — <reason>`, then the `--force` sentence or the in-flight sentence (`:927-950`) |

- `pauseCommand(by, reason, {store, log})` keeps its signature and logs the rendered lines. `unit/run-pause.test.ts:30-36` asserts on `printed.join('\n')`, so indentation does not break it, and it runs in `pnpm test`.
- The `shutdown` verdict is **only that the request was appended**. The daemon finishes the pass on its own (0030), so the line must not say *stopped*.

For the long commands, the verdict is **one line the `cli.ts` handler prints after the inner function returns**, chosen by exit code:

| command | 0 | non-zero |
|---|---|---|
| `restart` | `✓ restarted <sha7>` (`Prepared.examined.sha`, `restart.ts:710`). It prints once `openDaemon` returns ok, before the daemon's own running lines | `✗ not restarted` |
| `service <verb>` | `✓ <installed/started/shut down/restarted/uninstalled>` | `✗ not <verb>`. For `SHUTDOWN_BOARD_ONLY` (3) and `START_BOARD_ONLY` (4) (`service.ts:204`, `:227`) it is `✗ <verb> — the conductor did, the board did not` |
| `start` | `✓ started` once `openDaemon` returns ok | the `stopped: <projection> failed — …` line stays (`lingtai.ts:839-841`) |

- **Exit codes do not change.** `restartSupervised` reads 3 and 4 as *did the conductor start* (`service.ts:206-221`).
- The verdict line never adds a fact that is not in the lines above it, such as *"nothing was stopped"*. A refusal after the drain is different from one before it, and only the lines above say which happened.
- **`another daemon holds the lock — nothing to do` stays a `muted` line with no `✗` and exits 0** (`restart.ts:469-472`). The comment there explains: *"Nothing is wrong — red here would be the error that teaches people to ignore errors."* That is 0121 §1's *"a command that has nothing to say says so in one line and exits 0"*. `CLAUDE.md:250` quotes it, so it stays word for word.
- `next:` appears only where an existing sentence already names a command, as in #621. Do not add new advice.

## Done when, in unit-reachable terms

- `renderServiceStatus` and `serviceStatusJson` are pure tests under `NO_COLOR`. Cover: supervisor read, supervisor unread, beacon unread, board answering/nothing/unread, and `missing`. Each fact the old lines printed is asserted, along with the shape of the document. Add the `no-supervisor` error document.
- A `Steps` test with a fake writer: off a TTY, `progress` writes the same line `waitForTheLock` writes today; on a TTY, it writes nothing to scrollback.
- `runCli` tests for:
  - restart's precheck: `--anyway`, `--timeout 0s`, an unknown flag, and `--dirty picking up #88` → `reason: "picking up #88"`
  - `service stop`'s two lines
  - pause's blank reason
  - shutdown's `--force --timeout`
- Each verdict, rendered for each command and each exit code.
- `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` are green.

**What no unit test reaches:** a real drain, a real supervisor and a real start. These are `integration/restart.test.ts`, `integration/service.test.ts` and `integration/board.test.ts`, and none of them can run inside a pass. Two things stand in for them: the unchanged signatures, and the rule that no existing line changes. The PR says so. Whether a restart behaved the same after this change is settled by the log, not the output: `ConductorStarted`'s `by`, `reason` and commit after a `lingtai restart`, and `ConductorShutdownWithdrawn` after the drain.
