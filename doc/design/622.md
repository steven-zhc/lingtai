# #622 — the daemon commands move to `@effect/cli`; their sentences stay

## The shape in one paragraph

The parsing and the layout change in **two places only**: `cli.ts`, which gets seven new commands, and a new writer, `steps.ts`, which the runners hand in as `log`. `restart.ts` and `service.ts` keep their sentences word for word and keep their signatures. Each gains one optional callback that marks where a step begins. The verdict line, the step lines, the glyphs and the spinner all sit around those functions. None of it goes inside them. `service status` is the only verb that takes `--json`.

## Why this layering and not a rewrite of the prose

The functions that speak already take their printer as an argument:
- `prepareRestart(args, log = console.log, facts)` at `restart.ts:894-897`
- `waitForTheLock(doing, giveUpAfterMs, log, how)` at `restart.ts:1297-1310`
- `serviceCommand(args, options)`, with `options.log` and `options.error`, at `service.ts:751-753`

`apps/cli/integration/service.test.ts` passes in its own `log` and pins what comes out with `toEqual([...])` 43 times. `integration/restart.test.ts` does it 9 times. Both are integration files, so nobody can run them during the pass.

If the wording changed inside these functions, those tests would go red after the merge, and nothing could catch it before. If the wording stays and only the `log` handed in changes, every line the old output printed still goes out. That is also the simplest proof of *"No fact the old output printed is lost"*.

So treat each existing string as frozen. That includes `RESTART_GUARDS` (`restart.ts:537`), every `sayRefusal` line, `lostTheLock` (`restart.ts:425`), and the `still ${doing} after Ns — … ctrl-c …` line that waitForTheLock prints every `sayEveryMs` (`restart.ts:1350-1355`). That last line is what says *waiting, not hung* in a log file and on a pipe. **CLAUDE.md quotes `another daemon holds the lock — nothing to do` verbatim** (CLAUDE.md:250; the line comes from `restart.ts:472`), so it must come out unchanged.

**Steps need boundaries that only these functions know.** Add one optional callback to each: `step?: (name: StepName) => void`, defaulting to a no-op.
- `prepareRestart` calls it at `checking` (before `checkBeforeTheDrain`, `restart.ts:900`), at `draining` / `waiting` (before `waitForTheLock`, `restart.ts:1009`), at `checking again` (before `checkAfterTheWait`), and at `starting`.
- `restartSupervised` (`restart.ts:1100`) and the `shutdown` / `restart` / `start` arms of `serviceCommand` call it the same way, at drain → wait → unload → start → board.

Integration tests that pass no callback see no change. This one parameter is the only new thing the two big files take in.

## Routing: two doors, as `board` has

Add `start`, `daemon`, `service`, `restart`, `shutdown`, `pause` and `resume` to `MIGRATED_COMMANDS` (`migrated.ts:9`). Then `migrated.test.ts:75` (`[['daemon', '--no-conduct'], 'lingtai']`) flips to `'effect'`.

**`lingtai.ts` has to keep answering `daemon`.** Every installed supervisor runs that file directly with this argv:
- `DAEMON_JOB.argv` is `['daemon']` (`service.ts:134`)
- the launchd plist builds `[join(root, 'apps/cli/src/lingtai.ts'), ...job.argv]` (`service.ts:299`)
- systemd's `ExecStart` is the same (`service.ts:397`)

`entry.ts` never sees those processes. Do it the way `board` already does at `lingtai.ts:806-814`, which says *"A refusal here would exit every installed board job 2, and launchd would respawn it every thirty seconds (#187). One parser, two doors."* The `start`, `daemon`, `service`, `restart`, `pause`, `resume` and `shutdown` cases in `main` forward to `(await import('./cli.ts')).runCli(['node', 'lingtai', <command>, ...rest])`. They must not join the list at `lingtai.ts:881-905` that refuses with *"runs from the entry"*.

**The bodies have to move out of `lingtai.ts`.** That file calls `main(process.argv.slice(2))` when it is imported (its last statement). So a live runner in `cli.ts` cannot import `daemonCommand` (`lingtai.ts:197`), `serviceOptions` (`lingtai.ts:75`), `controlCommand` (`lingtai.ts:693`) or the restart arm (`lingtai.ts:824-871`) from there.
- Move them into a new module with no top-level effect, e.g. `apps/cli/src/daemon-commands.ts`.
- `cli.ts` loads it inside the handler, as `status` and `board` do (`cli.ts:292`), so `--help` still needs no log (0121 §8).
- `daemonCommand` stays *"The one place a daemon is started"* (`lingtai.ts:193`): it moves, it is not copied.
- `parseFlags` (from `add.ts`) and the hand parsing in `controlCommand` go away.
- Follow the `Runners` and `guarded` pattern (`cli.ts:383-551`) so a unit test can drive each command with no store.

**Parsing traps that already have tests or sentences:**
- **`restart --dirty picking up #88`**: *"A boolean here never consumes anything"* (`restart.ts:138-145`). The reason must come out as `picking up #88`, with `--dirty` true. Pin it in both orders, flag first and flag last.
- **`--anyway`** still refuses with its own sentence (`restart.ts:166-172`). Make it a hidden boolean whose handler refuses with exit 2.
- **`--force` with `--timeout`**: refuse with *"--timeout is about waiting for the pass, and --force does not wait. Use one."* (`lingtai.ts:751`). Restart's `--timeout` takes the same duration and positive checks as `parseRestartArgs` (`restart.ts:178-187`).
- **`pause` with no reason** exits 2 with its sentence (`lingtai.ts:706-713`). **`service stop`** still refuses with its two lines and exits 2 (`service.ts:758-765`). It should be a `stop` subcommand whose handler refuses, not a parse error.
- **`--no-conduct` / `--no-merge`** under a supervisor are refused before anything stops (`lingtai.ts:837-843`).

## `steps.ts`: the spinner, and nothing else that touches the process

Keep the spinner out of `output.ts`. That module is *"Rendering returns strings and printing is separate, so the module is tested with no process"* (`output.ts:5`). `steps.ts` is the only place that imports `ora`.

- **`ora` is not installed.** There is no `ora@` in `node_modules/.pnpm`, and `apps/cli/package.json` does not list it. Run `pnpm add ora --filter @lingtai/cli`.
- **Create it as** `ora({ stream: process.stdout, discardStdin: false, hideCursor: false, isEnabled })`. The stream is stdout because every progress line these commands print goes there today (`console.log`, the default for `prepareRestart`). The frame and the lines have to share one stream, or they interleave.
- **`isEnabled` is our decision, not ora's.** It is `stream.isTTY === true && coloured(stream) && !json`. `coloured()` (`packages/env/src/colour.ts:57`) alone is not enough, because `FORCE_COLOR` makes it true on a pipe, and a spinner on a pipe is escape codes in a log file. A supervised daemon's stdout is `daemon.log`, so there it is always plain.
- **Never call ora's `succeed()` / `fail()` / `warn()`.** They draw `log-symbols` in colours that ora chooses for itself. 0121 §3 says plain mode *"is decided in `coloured()` … and no command decides it for itself"*. End a step with `spinner.stop()`, then print our own line through `symbol.pass()` / `symbol.fail()` (`output.ts:62-66`).
- **A line printed while the spinner runs** goes out as `spinner.clear()`, then the write, then `spinner.render()`. The `log` that `steps.ts` hands to `prepareRestart`, `waitForTheLock` and `serviceCommand` does exactly that and nothing more. With the spinner off, a step's name is printed once as a plain line when the step begins.
- **The verdict** is one line, built with `renderVerdict` from `verdict.ts:31`, which already does *"one verdict line, the sentence the command always said beneath it, and `next:` only where that sentence already named a command"*. The old closing sentence becomes `detail`, word for word.
  - `pause`: `✓ paused` over `paused by … — …` and `RUN_UNDER_A_PAUSE` (`pause.ts:22-25`; `unit/run-pause.test.ts` asserts both and must stay green).
  - `resume`: `✓ resumed`.
  - `shutdown`: `✓ shutdown asked` over the in-flight sentence.
  - A refusal from `restart` or `service`: `✗ not restarting` and so on, from the exit code.
  - **`SHUTDOWN_BOARD_ONLY` (3) and `START_BOARD_ONLY` (4)** (`service.ts:204`, `227`) mean *the conductor's part worked and the board's did not*. Their verdict has to say that, not a bare ✗. The exit codes do not change.
- **`start` and a restart run here** print their verdict once the daemon holds the lock, that is, when `openDaemon` (`restart.ts:446`) has returned. Every line after that is the daemon's own stream. That stream is not a report and takes no `--json`, for the same reason `attach` takes none (0121 §5).

## `--json`: `service status`, and only that

0121 §5 gives `--json` to commands that only read; to read-only verbs of `changes` commands (#623: `board status`, …); and to verdict-answering commands, but those are named as *"the _waiting on you_ group and `now`"*. None of `pause`, `resume`, `shutdown`, `restart` or `start` is in either list, and the ticket's own Want says *"each read command"*. So `service status --json` is the only one, with `command: "service status"`.

- **Gather the data before printing it, the way `board status` does** (`readBoardStatus` / `boardStatusJson`, `cli.ts:292-307`). Today `report()` (`service.ts:866-874`) and `reportBoard` write lines as they read. Split each into a read that returns data and a render that produces the same lines as now.
- **The shape** has one key per job, `daemon` and `board`. Each job's facts (the supervisor's answer and the beacon or the board's answer) are a value or `{ "unread": "…" }`, following §5's convention for `board status`. Never fold them into one word: *"Two jobs, two reports, and never one summary"* (`service.ts:1492-1494`).
- **Exit codes** stay as they are (`service.ts:1491-1500`). `NO_SUPERVISOR` becomes the `error` document with a non-zero exit. `askJob`'s complaints go to stderr.
- **Add `service status`** to the #623 sentence in 0121 §5. That is an edit to the topic ADR in place, per this repo's `doc/decisions/` rule (*"A decision that changes is an edit to its topic's ADR"*); it extends a list and contradicts nothing. Also add `status [--json]` to `service`'s usage in `commands.ts`.

**The Watch-out about greps:** nothing in the repository parses these commands' output. `rg` for `grep|awk|sed` against `service status`, `paused by`, `resumed by` and `shutdown asked` finds only the code that writes those strings. So nothing has to move to `--json`; say that in the PR. The prose examples that must still be literally true are CLAUDE.md:250 (above) and `doc/operating.md:1118-1124`.

## The Ctrl+C test: a unit test, and what it must import last

- Record `process.listenerCount('SIGINT')` **before** the dynamic `import('../src/steps.ts')`. A listener installed when `ora` and its dependency chain are imported would otherwise be hidden in the baseline.
- Drive the real writer with a fake TTY stream, `FORCE_COLOR=1` and `NO_COLOR` unset.
- Replace `process.stdin.setRawMode` with a spy. Under vitest it may be undefined, so define it.
- Start a step, print through its `log`, stop it, and assert the count is unchanged and the spy was never called.
- Then run `waitForTheLock('draining', null, stepsLog, { ask: async () => 'holder', pollMs: 5 })` with the spinner running, and `process.emit('SIGINT')`. It must resolve `'interrupted'`, which `prepareRestart` maps to 130 (`restart.ts:1026`). Assert that mapping at the runner, since `prepareRestart`'s own path reaches the store.
- This needs no OS process, so it stays in the unit half.

## What only runs after the merge

`ora` is ESM-only, and `lingtai.ts` is bundled to CJS for the SEA (`lingtai.ts` tail: *"`pnpm build` bundles this file to CJS"*). The only check of that bundle is `apps/release/integration/build.test.ts`, which is out of reach during the pass. The unit stand-in is that `ora` is imported only from `steps.ts`, and only lazily from a handler. A failure would then show in `lingtai restart` rather than in `--help`.
