# Design: #1147, the recipe's `sandbox` block

## Where it goes

| Piece | File | What it is |
|---|---|---|
| Schema | `packages/recipe/src/recipe.ts`, beside `Recipe` | `SandboxBlock`: a `z.strictObject` with a `superRefine`, added to `Recipe` as `.optional()` and never defaulted |
| Path rules, host answer, decision | new `packages/recipe/src/sandbox.ts` | All pure apart from the two host Effects handed in |
| Wiring | `packages/recipe/src/local.ts` (`resolveLocalRecipeEffect`) | Two new required options, run after `resolved` (around `local.ts:395`) |
| Production default | `packages/conductor/src/projects.ts:196-210` (`currentRecipeEffect`) | The only place either option gets a default |
| Host-side seams | `@lingtai/sandbox` | Two small moves, below. This is S3's package, and nothing outside it imports it today. |

## Decisions the ticket leaves open

### 1. `@lingtai/recipe` imports `@lingtai/sandbox`'s `.` entry and does not write its own path list

- `refuseProtected` and `protectedEntries` (`packages/sandbox/src/protect.ts:29-89`) already implement *is / inside / contains* segment by segment. That includes reading a glob's static prefix the way srt reads it (`:59-64`, from `93f80834`).
- Write a second copy of the deny list and the two drift apart. `.` does not load srt: `live.ts:1-3` says *the only file that imports `@anthropic-ai/sandbox-runtime`, and not re-exported from `.`*.
- The mirror path: add `mirrorDir(host, project)` beside `cacheDir` (`policy.ts:84`), equal to `<stateDir>/repos/<project>.git`.
  - Do not import `@lingtai/repo`'s `mirrorPathFor` (`mirror.ts:32-34`). `@lingtai/repo` depends on `event-store`, which the recipe must not pull in.
  - Add one conductor unit test asserting `mirrorDir` and `mirrorPathFor` agree.

### 2. `deny` is checked exactly as S3's wrap checks it, which is stricter than the ticket's deny rule

- `wrap` runs `refuseProtected` over `[...write, ...deny]` (`sandbox.ts:115-118`). If resolve checked `deny` only against the worktree and the mirror, `deny: [~/.ssh/x]` would resolve, and then every sandboxed run of that project would fail `SandboxPolicyRefused`. That breaks the ticket's own reason for checking at resolve: *red before a run* (`recipe.ts:77-80`).
- So resolve runs the same `refuseProtected` over both lists. The ticket's two `deny` cases are covered by it:
  - `<stateDir>/worktrees/<project>/` lies inside `stateDir`, which is a `state-dir` entry (`protect.ts:33`).
  - The mirror is a `mirror` entry (`:35`).
- This refuses some `deny` paths the ticket's rule alone would accept (`~/.cache/x`, for instance). Wrap would refuse them anyway. Loosening it is a change to S3's caller, not to this ticket.

### 3. Two required options, not one, because `'skip'` still needs the host's paths

The editor, `lingtai add` and onboard pass `'skip'`, yet the ticket wants `$PNPM_HOME` and the `PATH` directories refused at save. So the facts cannot live inside the `'skip'` branch.

```ts
host: HostAnswer | 'skip'                           // HostAnswer = Effect<void, SandboxUnavailable>, i.e. SandboxApi['hostCanSandbox']
hostFacts: Effect.Effect<HostFacts, SandboxUnavailable>
```

- Both are **lazy Effects**. That is what lets a counting fake prove the zero-calls claims.
- `hostFacts` runs only when the block is present with a non-empty `write` or `deny`.
- `host` runs only when `enabled && required` and it is not `'skip'`.
- If `hostFacts` fails (for example `HOME` is unset, `live.ts:61`), the problem is reported at `sandbox.write`: the paths could not be checked. A list that cannot be checked is refused, never accepted.
- Add `packages/recipe/test/sandbox-host.ts`. It exports `fakeSandboxHost({ can, home, pnpmHome?, path? })`, which returns both options plus call counters. All 83 existing `resolveLocalRecipe*` references across 18 files spread `...skipSandboxHost` (the `'skip'` form of it), so the churn is one token per call.
- `saveRecipeTextEffect`'s options (`write.ts:227`) gain `hostFacts` and pass `host: 'skip'` themselves.

### 4. The production answer must not build `SandboxLayer`

`makeSandbox` adds `srt.reset` as its scope's finalizer (`sandbox.ts:75`). If `currentRecipe` builds the layer per call, it pays an `initialize` on every call, and once S4–S6 hold the instance, closing a scope there resets the instance under a run that is wrapping.

So, in `@lingtai/sandbox`:

- **The platform check.** Factor `platformAndDeps` (`sandbox.ts:77-98`) into an exported `checkHost(srt, host)`. `makeSandbox` keeps using it through `cachedWithTTL`, so the resolver and S4–S6 cannot disagree about what *can* means.
- **The host facts.** Move `readHost` (`live.ts:58-80`) into a new srt-free `src/host.ts`, exported as `@lingtai/sandbox/host`. `live.ts` re-exports it.
- **The per-process answer.** In `live.ts`, `hostCanSandboxHere` is a per-process answer kept for `HOST_CHECK_TTL` in a module-level memo, the way `signedInProbe` keeps `kept` (`projects.ts:140-157`).
  - **Not** `Effect.runSync(Effect.cachedWithTTL(…))`: that is an `Effect.run*`, and the ratchet holds this package at 0 (`live.ts:6`).

`currentRecipeEffect` defaults:

- `hostFacts` to `@lingtai/sandbox/host`'s `readHost`.
- `host` to `Effect.tryPromise(() => import('@lingtai/sandbox/live'))` flatMapped to `hostCanSandboxHere`. The dynamic import loads srt only in a process that actually resolves a `required: true` block.
- Its `options` type widens the same way `signedIn` was made optional there (`:200`).

### 5. The decision function returns S3's input shape, not merged lists

The function is `sandboxDecision(block, answer, home)`, where `answer` is a value, `{ can: true } | { can: false; reason; sentences }`. It returns:

- `{ kind: 'sandboxed', project_additions }` — this is exactly `WrapInput.project_additions` (`sandbox.ts:34`), with `~` expanded against `home`.
- `{ kind: 'unsandboxed', reason: 'off' | 'degraded', sentences }`
- `{ kind: 'refused', … }`

*Built-ins plus the recipe's* is merged by S3's `filesystemFor`/`runDomains` (`policy.ts:107-145`). Merging here as well would make two places say what the built-ins are.

### 6. Expanding `~`

- `~` and `~/…` are expanded against `HostFacts.home`, then `posix.normalize`d. This happens only inside the comparison and the decision.
- `parsed.data` keeps the text as written, so `configHash` does not depend on the machine.
- `~user/…` is neither `~/` nor absolute, so the schema refuses it as relative. No extra rule is needed.

## The schema

- **Strict, because a silently dropped key is the failure `resolve.ts:280-281` names.** `z.strictObject` for the block and for `network`, as `recipe.ts:280`, `:883` and `:924` already do. With a plain `z.object`, `network: { alow: […] }` would be stripped and silently allow nothing.
- Inner defaults are as the ticket says: `enabled: true`, `required: false`, lists `[]`. Nothing is defaulted on the block, for the reason at `recipe.ts:3251-3258`.
- **`superRefine`, text-only, in the style of `ExtensionEnvNames` (`:90-105`).** It checks:
  - a path that is neither `~/…` nor absolute;
  - `enabled: false` together with `required: true`;
  - a domain that is not a hostname or `*.` followed by a hostname. Hostname means RFC 1123 labels, at most 253 characters, case-insensitive, with no scheme, port, path or bare `*`.

  Each sentence says why. Issue paths come out as `sandbox.write.0: …`, through `resolve.ts:252-259`.
- **Presets carry no block, and applying one leaves the key alone.** `applyPreset` passes it through in `...rest` (`presets.ts:136-139`).

## Where a refusal is raised

Everything below runs inside `resolveLocalRecipeEffect`, after `resolveSource` succeeds.

**The path rules.** Every refusal becomes one `RecipeInvalidError`, with each problem written as `sandbox.write.N: "<as written>" <relation> <kind> <protectedPath>`.

**The host check.** On `SandboxUnavailable`, on a defect, or on any non-interrupt cause (`catchCause`, the same shape as `write.ts:255-262`), the result is `RecipeInvalidError` with the problem at `sandbox.required`:

- **The text.** A fixed sentence plus S3's `reason` and `sentences`. For a defect, the fixed text is *the host check could not be read*, never the defect's message.
- **No varying digits.** S3's reasons carry none (`sandbox.ts:79-96`). srt's own sentences might; `turnTransition` strips digits (`project.ts:186-218`).
- **The prefix is fine.** `RecipeInvalidError` puts its `where` in front (`resolve.ts:56`). That names the recipe's path and so the project, but it is the same on every sweep.

## Traps the implementing agent will hit

- **The board must transpile the new package.** `@lingtai/sandbox` must be added to `apps/board/next.config.ts`'s `transpilePackages` (`:15-23`). The recipe now imports TypeScript source from it, and without the entry the Next build fails.
  - **Nothing in the unit half sees this.** Only `apps/release/integration/build.test.ts` builds Next (CLAUDE.md, *the only thing that sees a server-only import…*). This is an integration-only check, out of reach before the merge.
  - The dynamic `import('@lingtai/sandbox/live')` will also be traced into the standalone output. srt ships no `.node` file (checked under `node_modules/.pnpm/@anthropic-ai+sandbox-runtime@0.0.83`), so `build.ts`'s prune has nothing new to remove.
- **`Recipe.shape` feeds an error message.** `unknownKeys`' message lists every declared key (`resolve.ts:299-311`). Adding `sandbox` changes that sentence, so any test pinning it goes red. Keep `doc/recipe.md` resolving (`recipe-page.test.ts`).
- **Doctor builds its own recipe lookups.** `DoctorReach` gains `sandboxHost?` and `hostFacts?` beside `signedIn?` (`doctor.ts:1254`). These must be threaded into every `currentRecipeEffect` default doctor builds: `:1433`, `:2381`, `:3022` and `:3227`.
  - Defaulting only through `currentRecipeEffect` is safe for tests whose recipes have no block, because the host is never asked.
  - Pin that safety with the counter-at-zero test, not with a hope.
- **No unit test exists to extend for the daemon turn.** `apps/cli/unit` has no `ProjectRefused` test, so the two-sweeps-one-event test is new. Build it on `createMemoryEventStore()` and a fake `world.currentRecipe` that closes over a mutable `can`.
- **No new `async` function.** The dynamic import goes through `Effect.tryPromise`, and the new resolvers are `Effect.fn`. If the ratchet goes red, the change is wrong; never raise `effect-ratchet.baseline.json`.

## What settles it on the log

- **The once-only claim:** exactly one `ProjectRefused` per project whose `message` contains `sandbox.required:`, from the first sweep after the paste until a `ProjectRecovered` for the same project.
- **The `configHash` claim:** recorded attempts' hashes before and after the change. The fixture test stands in for this.
