# #1473: what a rerun of `init` does, and what it must not write

## Where it goes

The change touches four places.

1. **`apps/cli/src/first-project.ts:646-668`**: delete the `initRerun` short cut. Put a resolve-or-refuse check in the same spot (see below). After that check the rerun goes on through the code that is already there:
   - The base question already offers the recipe's base, because `current: typeof currentBase === 'string' && ports === null ? currentBase : null` (`:732`).
   - A file that exists keeps its mode: `if (fileText === null)` guards `askMode` (`:675-679`).
   - The sandbox is offered only when `existingText === null` (`:979`, and `recipe-flow.ts:359` *"an existing project is never given the block"*).
   - On a team project the personal-branch question is asked, with `fallback: currentBase` when `ports === null` (`:705`). It is out of scope: leave it as it is.
2. **`first-project.ts:1121-1170`** (`applySetup` + `register`): skip the whole write on a rerun that changed nothing. This is the trap the ticket names, and it is real (see below).
3. **`apps/cli/src/agents.ts`**: a recipe's own writer and reviewer must be accepted as an answer even when signed out. Also stop the `turns` write on an unchanged writer.
4. **The card's heading** (`setup-card.ts:274`): it needs a third state, *unchanged*.

## A rerun writes nothing until the end, and Ctrl+C keeps nothing

The ticket's Ctrl+C edge relies on `recipe-flow.ts:5-8` (*"an existing file is edited one answer at a time … so a Ctrl+C keeps what was answered"*). That header is out of date.

- Since #968 every answer goes into an in-memory draft: *"Every answer lands in this draft and nowhere else: `applySetup` (#968) is the one writer of the file, so a refusal anywhere below leaves the disk as it was"* (`recipe-flow.ts:216-218`).
- `draft.ts:5-6` says *"nothing here ever writes"*.
- `apply-setup.ts:5-10` says *"Written once … in one replace. A refusal while asking therefore leaves nothing behind"*.

**Decision:** keep #968's shape. A Ctrl+C halfway through a rerun leaves the recipe and the log exactly as they were. Do not build per-answer commits: that would undo #968/#1182, and that is a separate decision. Correct the stale sentence in `recipe-flow.ts`'s header so the next ticket is not built on it.

## "Every default changes nothing": two places would write anyway

**1. `register` always appends.** `registerProject` appends `ProjectConfigured` unconditionally (`packages/project/src/commands.ts:137-141`, no equality check). `addLocalEffect` then reports *updated* for any project that was already registered (`packages/conductor/src/onboard.ts:568`). `changeRecipe` would also append `ProjectRecipeChanged` when the file's hash differs from the one the log records (`change.ts:7-9`). That is the case for a hand edit the log has not seen yet.

**Decision:** when `found !== undefined` and `recipeResult.answers.changes` is empty, do not call `applySetup` at all.
- `draft.changes()` holds only the sets that changed the text: `if (existing !== null && text === existing) return { … written: false }` comes before `recorded.push` (`draft.ts:72-75`). So *empty* means *byte-identical*.
- Return the card with `trial: recipeResult.trial` and the new *unchanged* state.
- The daemon's next `loadProject` still records a pending hand edit as `by: 'file'` (`change.ts:7-9`), which is the right owner for it.
- What settles it in the log: **no new event on `prj-{project}`**. Neither `ProjectConfigured` nor `ProjectRecipeChanged` appears after the second run, so its version is unchanged.

When a change *was* written, register as today. The card then says *updated*: `isRegistered(before)` is true there.

**2. `askAgents` writes `turns` when the key is absent.** It pushes `unboundedTurnsChange()` whenever the writer does not enforce `turns` and `runtime.limits.run.turns` is absent (`agents.ts:357-362`). On a recipe whose `turns` was removed by hand, or that predates #547, a run that takes every default would add the key. **Decision:** on an existing file, push it only when the writer answer differs from the writer the file named (`writingAgent`, `:221-227`).

### Writes that look unconditional but are no-ops

These are covered by `draft.ts:72`'s text comparison, and the byte-for-byte test must prove it:
- `runtime.agent` is written every time (`agents.ts:342-349`, *"written to the writer every time"*).
- The seeds (`first-project.ts:944-958`: `branch.main`, `repo.remote`).
- `model: undefined` on a recipe that has no model (`agents.ts:366-367`).
- `askLanding`'s `holdRemovalChanges` (`landing.ts:184`).

`askLimits` already compares before it writes (`landing.ts:325`). `askTickets` returns no change when the answer equals the current source (`source.ts:155`).

### The test

`apps/cli/unit/init.test.ts:577` already runs `init` twice and asserts both files are byte-for-byte unchanged. Today it passes only because the second run asks nothing. Once the short cut is gone, it becomes the real proof. Add to it a count of the events on `prj-repo` before and after the second run.

## A recipe that does not resolve is refused before the first question

Without the short cut, a broken recipe would quietly fall back to the system's defaults:
- `currentBase` swallows the resolve error into `null` (`first-project.ts:621-628`).
- The base question then offers `detected`, which is `LINGTAI_BASE` (`:637`).
- A seed `branch.main: lingtai-base` could then "repair" the file once a person presses Enter.

**Decision:** where the short cut was, when `found !== undefined` and `onDisk.text() !== null`, run `resolveSource` once. On failure, refuse by name with the path and the resolver's message, before any question or any write. Two neighbouring cases:
- **A read that errors:** it already fails inside `draftRecipe`'s `files.read` (`draft.ts:58`). Make sure the message names the path.
- **A registered project whose file is absent:** nothing would be overwritten, so keep today's behaviour and fall through to the first-run questions.

## A signed-out runtime in the recipe is still the default

Today that runtime is deliberately not offered:
- The writer: `currentAgent = … signedInIds.includes(writingAgent) ? writingAgent : null` (`agents.ts:228`).
- The reviewer: `:272-283`, *"never offered … so `defaultReviewer`'s detected value is reached instead"*.
- `refuseUnlessOffered` refuses it as an answer (`:209-216`).
- Under `--defaults` a refused default ends the run, because `acceptingDefaults` returns `null` on a repeated prompt (`question.ts:134-137`).

So taking every default would either switch runtimes or fail. Both contradict the edge.

**Decision:**
- `current` is the recipe's runtime whether or not it is signed in.
- The validators accept exactly that value, and still refuse any other signed-out runtime.
- The `whyMissing` line already printed at `:200-202` is the "says it is signed out" part.

This also changes `lingtai add`'s existing-file path, which calls the same `askAgents`. That is intended: one rule. In `refusal-fixes` and the reviewer model, keep `currentModel`'s rule that a model goes with the agent it was written beside (`:243-248`).

A rerun with **no** runtime signed in is now refused by `noRuntimesSignedInRefusal` (`first-project.ts:774-777`). Today it got the card, which `:646-647` says on purpose (*"a machine whose first project is added must not fail"*). Accept the refusal, since nothing can be asked. The four `init.test.ts` rerun tests (`:374`, `:436`, `:505`, `:577`) must keep a runtime signed in.

## The card

`setup-card.ts:274` prints `updated` from `facts.updated`, which is `registration.updated` (`first-project.ts:1162`). That value is true for every rerun.
- Carry a third state, *unchanged*, from the no-write path above.
- Keep the team heading's `!facts.updated` test (`:272`) meaning *first run*.

The trial line needs no new code. `recipeResult.trial` carries the real reason:
- `declined` under every default, because the `check` flag is forced to `'no'` when `askWorld !== world` (`recipe-flow.ts:372`).
- `no checks` only when the list is really empty (`setup-build.ts:302`).

Do not add a new `TrialOutcome` variant.

## What later changes inherit

Every question in `askRecipeEffect` is now asked on both runs. A question added later that reads no `current` from the draft fails the "each question offers the recipe's value" test. Build that test as a table of question name → recipe key, so a new question fails it by name.

`pnpm test` covers all of this. Nothing here depends on `pnpm test:integration`.

When this lands, delete the `§6` bullet's first clause from ADR 0125's *Not built yet* (`doc/decisions/0125-setup-is-one-module-two-inputs.md:105-107`) and keep its second half about mode, sandbox and personal branch. That is an edit to the topic's own ADR, which is how `doc/decisions/` works.
