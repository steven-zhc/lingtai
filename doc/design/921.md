# #921: the shape of the change

## Where the write goes in `resolveWaitHolding`

Put it in one place: **after every refusal and right before the `store.append`** at `packages/conductor/src/resolve-wait.ts:345`. That placement handles three of the ticket's traps without any extra code:

- **Reschedule path.** It returns at `:236-247`, long before the write, so it never writes. Add no condition for it, only a test.
- **`EditBodyAndRequeue`.** The write is gated on `resolution._tag === 'GrantFixRound' || 'Requeue'`, so `edit-body.ts:221`'s own call never reaches it.
- **Refuse before you write.** `not-blocked`, `not-offered`, `bad-sha`, `stale` (saved head and remote ref, `:309-336`) and `no-client` all return before the body is touched. That is 0118 §6's rule, which `edit-body.ts:197` states as *"a body edited for a refusal it was always going to get is a body changed for nothing."*

The order inside that slot:

1. Read the triage with `triageFactsFromState(item, options.waitId).result` (`packages/domain/src/read-model.ts:147`). `item` is already reduced, so this costs no second read. Go on only if the result is `TriageAdvised` and its cause yields at least one question.
2. Compose the text with `triageAnswersText(cause, options.picks)`. A stale pick refuses here, with `reason: 'stale'`, before anything is written.
3. If `options.github` is undefined, refuse with `no-github`.
4. Call `writeSection` with key `` `${ticketId}/${options.waitId}` ``. If it returns `written: false`, refuse with `write-failed` and the detail it gave.
5. **Re-read `item` before you append.** This is the trap the ticket does not name.

### Why step 5 is needed

`writeSection` records its outcome **on the ticket's own stream**. `tellGitHub` → `record(store, ticketId, 'IssueUpdated', …)` appends at `store.read(ticketId).length` (`packages/conductor/src/tell.ts:369-378`), and `writeSection` itself calls `record` again on a found-on-read-back write (`edit-body.ts:123-129`).

So once anything has been written, the `item.version` read at `:225` is behind. If the append at `:346` used it, every write would end in `ConcurrencyError` → `reason: 'stale'`, with the section written and the wait never resolved, every time.

`editBodyAndRequeue` does not hit this only because it writes *before* calling `resolveWaitHolding`, which reads afterwards.

After the write, run `readState` again. Check that the ticket is still `blocked` on `options.waitId`; if not, refuse as `not-blocked`. Then append at the fresh version. We hold `deciding`, so the re-check should always pass. It exists for writers outside the lock (the daemon's own appends), and those get the usual `stale` answer.

When a refusal comes after a successful write, return `written: true` on it, the way `EditBodyAndRequeueResult.written` does (`edit-body.ts:141`):

- Add `written?: boolean` to the `ok: false` arm of `ResolveWaitResult`.
- `requeue()` (`approve.ts:421-423`) passes it through.

## Move `writeSection` out of `edit-body.ts` first

`edit-body.ts` imports `resolveWaitHolding` from `resolve-wait.ts` (`:19`). If `resolve-wait.ts` now imports `writeSection` from `edit-body.ts`, the two modules import each other.

Move `writeSection`, `sectionTextFor`, `WriteSectionResult` and `errorMessage` into a new `packages/conductor/src/write-section.ts`. It needs only `body-section.ts`, `tell.ts` and `ticket-store.ts`, none of which import `resolve-wait.ts`. Re-export everything from `edit-body.ts` so that `discuss.ts:82` and `index.ts:144` stay untouched.

Make the move its own commit. That keeps the behaviour diff readable.

## The domain functions and the `triage.ts` import

`triage.ts`'s header says it *"imports nothing from either"* `wait.ts` or `events.ts`, so that both can import it with no load-time cycle. `RootCause` lives in `wait.ts` (`:808`). Two ways to type the parameter, either is fine:

- `import type { RootCause } from './wait.ts'`. This is erased at runtime: `verbatimModuleSyntax` is on (`tsconfig.base.json:16`) and there is no lint rule against import cycles. If you take this one, edit the header sentence to say *"imports nothing from either at runtime"*.
- Or type it structurally from `triage.ts`'s own `TriageQuestion` and `Hunk`, e.g. `{ _tag: string; questions?: …; hunks?: … }`.

How the two functions behave:

- **`triageQuestionsOf(cause)`** returns `{ question: TriageQuestion; at?: { path: string; line: number | null } }[]`.
  - `UndecidedQuestion` gives its `questions` in order.
  - `ConflictingHunks` gives each `Divergent` hunk's `question`, with its `path`/`line`, in hunk order.
  - Every other cause gives `[]`.
- **`triageAnswersText(cause, picks?)`** returns `{ ok: true; text: string } | { ok: false; detail: string }`. Return the result rather than throwing, because refusing a stale pick is an expected outcome.
  - A question with no pick takes `recommended`.
  - If no question results at all, return `{ ok: true, text: '' }`. The caller treats empty text as *write nothing*, so this is the only test the caller makes.
  - Each line reads `` `path:line` — question — answer text ``, using the same backticked `at()` form as `fix.ts:625`. Only a hunk line has the location prefix.
  - Add no timestamp or `by`, so a retry writes the same section byte for byte.

## Options, and the callers

- Type `github?: IssueChannel` (`tell.ts:40`).
- Type `picks?: Readonly<Record<number, string>>`, since the key is a question's index.
- `requeue()`'s options gain `github?` and forward it to the `resolveWaitHolding` call at `approve.ts:409`.
- The callers listed in the ticket's Edges pass `github` and never `picks`.
- `requeue()` is also reached for tickets with no triage, and for withdrawn `OwnQuestion` waits (`approve.ts:395`). There the write step finds no questions and is skipped, so a caller without a client still works. `no-github` is returned only when there is something to write.
