# Design note for #1222: rerun a red `run:` check once, and let a flaky test through only on 0108 §17's three conditions

## Where it goes

There are three pieces, and each has one owner:

1. **`packages/domain/src/failure/flaky.ts`** (new; export it from `failure/index.ts` next to `tests.ts`). This file holds the pure decision `flakyVerdict` and the claim vocabulary: `FLAKY_CLAIM_PREFIX`, `flakyClaim(entry, command)`, `flakyEntryOf(claim): string | null` and `isFlakyFinding(f)`. Nothing else in the codebase builds or parses this claim. #1231 calls `isFlakyFinding`, and condition 3b calls `flakyEntryOf`.
2. **`packages/actions/src/process-action.ts`** gets the rerun and an optional `flaky` port on `ProcessActionSpec`. The port's type is declared here, because `actions` cannot import `conductor`. `from-recipe.ts` passes `deps.flaky` through only when `step` is `build`, `proposed` or `merge`. `implement`'s kept run (`from-recipe.ts:397-404`) and `prepared` never receive it.
3. **`packages/conductor/src/flaky-port.ts`** (new) has `flakyPortOf(reads)`. It takes the three reads as Effects and returns the port. `conduct.ts` only wires the real reads into it and puts the port on `stepDeps` (built before `actionsAt` at `conduct.ts:4382`). The unit test from *Done when* ("the port over a memory store") then calls `flakyPortOf` with a memory store's `read` and a backlog read built inline. It needs no Postgres and no git.

## The decisions the ticket leaves to the design

**No port means no rerun.** The rerun belongs to the port: without a port, `makeProcessAction` behaves exactly as today. That keeps `prepared`, `implement` and every existing caller unchanged, and the *never rerun an agent* claim is true by construction. The rerun lives in `makeProcessAction` and no agent action is built there, so the test only has to show that an agent action built with the same deps runs once.

**When to rerun.** Use the same condition the base check already uses (`base-check.ts:280`): `!signal.aborted && !timedOut && exitCode !== null && exitCode !== 0`, plus `!wrapFailed` and no `spec.refused`. Pull the spawn-or-wrap block (`process-action.ts:170-199`) into a local `runOnce` Effect so the rerun goes through the same wrap. `recordUnwrapped` (`:169`) stays outside `runOnce`, so it is called once per action. If the signal aborted between the two runs, do not start the second; answer `failed` with the first run's evidence.

**Red twice never reaches the port.** Red twice needs no reads, so `makeProcessAction` answers `failed` itself. The evidence is one line, ``the first run of `<run>` failed too``, then the second run's evidence. The port is called only for red then green. It receives `{ step, action, command: spec.run, first: CommandOutcome, second: CommandOutcome }` and returns `Effect<{ passed: true; evidence; findings } | { passed: false; evidence }, never>`. Its error channel is `never`: every failed read becomes a `passed: false` inside the port, so the process action has no failure path to get wrong.

**The reads are lazy and run in condition order.** `flakyVerdict` is pure, so the port does the IO before calling it. Read in this order, and stop at the first read whose condition already fails:

1. `failingTestsOf(first.evidence)` (`failure/tests.ts:12`). Null means red with *the failing tests could not be named*, and no IO is spent.
2. The diff paths.
3. The `BaseChecked` events.
4. The backlog.

Shape `flakyVerdict` so it accepts each of the three reads as `T | null`, where null means *could not be read*. The domain tests then cover every branch, and the port just runs the reads and hands their results over. Evidence for a red that the rule did not let through starts with ``red then green; not let through because <condition>``, followed by `first.evidence`.

**Read the base sha when the port is called, not when it is built.** `stepDeps` is built once per pass, but `worktree` is a `let` assigned later (`conduct.ts:1752`). So the diff read inside the closure computes `continuation?.diffBaseSha ?? worktree?.baseSha ?? null` at the moment it runs. This is the same expression `baseIsRed` uses (`conduct.ts:3881`), without `mergedOnto`, because no merge has happened when a check runs. A null sha answers null for the diff (red, *the diff could not be read*). Otherwise use `pathsBetween(`${baseSha}...HEAD`)` (`conduct.ts:3608-3612`).

**Condition 2 compares paths by suffix, not only by equality.** A vitest entry is `<file> > … > <test>`, with the file relative to vitest's root (`tests.ts:5`). `git diff --name-only` paths are relative to the repository root. If a check runs in a subdirectory, an exact comparison never matches and condition 2 passes silently. So a diff path `p` matches an entry's file `f` when `p === f || p.endsWith('/' + f)`. Any mismatch then errs toward red.

**Condition 3a** reads the project's integration stream with `store.read(integrationStream(project, base))`, the read `base-check.ts:155` already makes. It keeps only events that are `type === 'BaseChecked'` and have `command === spec.run`, on any `baseSha`. An entry counts as seen when either:
- the event is not `ok` and `failingTestsOf(evidence)` includes the entry; or
- the event's `flaky` (`events.ts:1545`) includes the entry.

The match is the whole entry string. `evidence` is `boundedEvidence` (`base-check.ts:306`), so its `failingTestsOf` may be null. That record then names nothing, and nothing else follows from it.

**Condition 3b** goes through `readBacklogEffect({ project })` (`packages/projector/src/backlog.ts:302`), with no `status`, so it reads every status (`:286`). An entry counts as seen when some row has `flakyEntryOf(row.claim) === entry`. The match does **not** require the command: a flake a person already has on the backlog stays known when the command is renamed. 3a, which follows the ticket's text, does require the command. The test only needs `{ file, claim }`, so the port's backlog read is typed as `Effect<readonly { file: string; claim: string }[], unknown>`.

**The claim.** Build it as ``flaky: <entry> failed then passed on a rerun of `<command>` ``. `flakyEntryOf` parses it back by taking the prefix and then the text up to the **last** occurrence of ` failed then passed on a rerun of `` ` ``. An entry may contain any characters, so the last occurrence is the safe boundary. `isFlakyFinding(f)` is `f.severity === 'minor' && flakyEntryOf(f.claim) !== null`.

The finding's other fields:
- `file` is the entry's file: `entry.split(' > ')[0]`, the same split `tests.ts:33` uses.
- `line` is `null`.
- `failureScenario` holds the head sha and the first run's `FAIL` lines.

The head sha has to come from somewhere, so the port's diff read also does `rev-parse HEAD` through `gitAskedEffect`. If that read fails, the sha is left out of `failureScenario`. That failure is not a reason for red, because it is not one of the three conditions.

**A passed flaky action's evidence** is `red then green`, plus one line per test naming its record. The record is either ``BaseChecked on <sha7>`` (or ``… flaky on <sha7>``) or ``backlog row <key> (<status>)``. The second run's output is dropped, because it was green.

## Verification inside the pass

Everything above is checked by the unit half:
- `flakyVerdict` gets pure tests.
- `makeProcessAction` is tested with a scripted `command` runner that answers exit 1 then 0, and counts its calls.
- `flakyPortOf` is tested over `createMemoryEventStore()` with an inline backlog read and an inline diff read.
- A `StepEnded` built from a passed action's findings is fed through `findingsRaisedOf` (`read-model.ts:179`).

The wiring in `conduct.ts` is only exercised by the integration half, which runs after the merge. So keep that wiring to a single `flakyPortOf({...})` call, with no logic of its own. The `merge` case in *Done when* is a test that `actionPortsFromRecipe('merge', [run], { …, flaky })` returns a port that reruns. It is not a conduct-level test.

The `conduct.ts` closures are new IO, so write them as `Effect.gen` with `Effect.try`/`tryPromise` around `store.read`. Add no `async` function and no `Effect.run*`. The ratchet baseline does not move.
