**Design note: #1444, the PR pages' colours become variables**

**Where the rules actually are.** The ticket's line numbers are out of date. The PR rules are two short blocks, not the range `globals.css:3411-3868`:
- `.prp-*` (a PR's page): `globals.css:3420-3490`.
- `.pr-*` (the PRs board): `globals.css:3492-3546`.
- `.obs-*`: `globals.css:3548-3559`. These are the branch sketch's own rules. `branch-sketch.tsx` uses `className="obs-ring` and `obs-sketch` next to `prp-line` and `prp-svg-t`.

The rest of 3411-3868 belongs to other pages (`.rp-*`, the ⌘K palette's `rgb(15 24 28 / 0.18)` at `:3709` and `:3711`, `.livelog`, and so on). Leave those alone. That is why the test below picks rules by selector, never by line range. No colour is set in markup: the `#NNNN` matches in `pr-*.tsx` and `branch-sketch.tsx` are issue numbers in comments. So this change is CSS plus one test.

**Scope includes `.obs-*`.** The ticket's edge says the branch sketch follows the same rule, and its ring (`.obs-ring { stroke: #c58a14 }`, `:3553`) and box (`.obs-box { stroke: #2a8a7a }`, `:3552`) are `.obs-*` rules. Convert those four rules too, and give the test `.obs-` as a third prefix. Without that, the edge is promised and nothing checks it.

**Light mode stays exactly as it is, which decides when an existing variable is used.** "Same role" is not enough: a variable replaces a literal only when its light value equals that literal. Exact matches today:

| Literal | Variable | Defined at |
|---|---|---|
| `#2c7a4c` | `--pass` | `:27` |
| `#a33029` | `--fail` | `:29` |
| `#9c5a08` | `--signal` | `:24` |
| `#fff` used as a background | `--surface` | `:13` |

Near misses get a `--pr-*` variable of their own, because swapping them in would change light mode, which is out of scope:
- `#c0392b` against `--fail`
- `#2e8b57` against `--pass`
- `#c58a14` against `--warn`'s `#b8860b`
- `#5b6485` against `--muted`'s `#5e6e74`
- the queued `#b8782f`

Two literals within 2 per channel of each other may merge into one variable, since nobody can see that difference: `#d5daea` and `#d5dbec`, and `#e3e8f5` and `#e4e8f6`. Nothing further apart merges. That gives roughly fifteen `--pr-*` names rather than "a few". That is the price of keeping light mode identical, and it is accepted.

**Names: do not declare `--pr-soft` or `--pr-ink`.** `.ltag-pr` already reads them, with a light fallback (`globals.css:806`: `background: var(--pr-soft, #e5e9f3); color: var(--pr-ink, #4a5d8a)`) and its own dark fallback (`:809-811`, `var(--pr-soft, #1f2536)`). Declaring them would quietly override both fallbacks on every page that shows the tag. Use other names, for example:
- `--pr-tint` for `#f2f4fa`
- `--pr-navy` for `#44507a`
- `--pr-navy-deep` for `#2f3d63`
- `--pr-slate` for `#5b6485`

Leave `.ltag-pr` and its fallbacks as they are.

**Filled headers and chips need a text variable of their own.** Today white text sits on navy, fail, pass or signal fills:
- `.pr-head { background: #2f3d63; color: #fff }` (`:3504`)
- `.pr-card.waiting .pr-head { background: #a33029 }` (`:3516`)
- `.prp-chip`, and `.prp-life li.current`

In dark mode `--fail`, `--pass` and `--signal` become light tones (`#e2776e`, `#61be86`, `#e0a55c`, at `:68-71`), so white text on them is unreadable. Add `--pr-on-fill`: `#fff` in light mode and a dark ink (`--ground`'s `#0c1316`) in dark mode. Give every filled navy also a light dark-mode value, so all filled headers follow one rule in dark mode: light fill, dark text. `.pr-head a` (`:3505`) uses the same variable.

**Dark values.** `--pr-tint` must stay a navy-leaning dark, not `--ground`, so the board stays tinted. It must also be darker than `--surface` (`#131e22`), so cards and panels stand off it the way `#fff` does on `#f2f4fa` today. Each text-role `--pr-*` variable needs 4.5:1 contrast against both `--pr-tint` and `--surface` in dark mode. The *Made with Lingtai* field (`.prp-textarea.generated`, `:3481`) reads `--pr-tint` and `--pr-slate`, which is what fixes it.

**Small things the test will catch:**
- Drop the fallback in `.prp-panel { background: var(--surface, #fff) }` (`:3430`). `--surface` is always declared, and the hex inside the fallback counts as a literal.
- Rewrite the comment at `:3421`, "*Colours are the board's own variables*", which only becomes true with this change. Also rewrite the `.pr-page` comment at `:3492` to name the tint variable.

**The test.** Put it in a new file, `apps/board/unit/pr-colours.test.ts`. Read the CSS the way `unit/panel-css.test.ts:24` does. Do not reuse that file's selector regex (`:27`): it only matches a rule that follows `}` or the start of the file, so it misses a rule nested in `@media (max-width: …) { .prp-grid {…} }` (`:3490`).

1. Strip `/* … */` comments first. They contain `#1320` and `#1319`, which look like hex colours.
2. Match innermost blocks with `([^{}]+)\{([^{}]*)\}`.
3. For each block whose selector contains `.pr-`, `.prp-` or `.obs-`, fail on `#[0-9a-fA-F]{3,8}\b`, `rgba?\(` or `hsla?\(` in the body.

`:root` never matches those prefixes, so the declarations are exempt without a special case. To stop the test passing by finding nothing, it must also assert two things:
- the scan found at least 100 matching rules;
- the same function flags a planted `.pr-x { color: #fff }`.

**Checks.** `pnpm typecheck` and `HOME=/nonexistent pnpm test` cover the test. Nothing here needs `pnpm test:integration`, and the release build test sees nothing different in a CSS-only change. Dark readability and the light-mode screenshot comparison are left to a person, as the ticket says. No ADR is involved.
