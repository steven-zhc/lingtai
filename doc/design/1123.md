## Design note for #1123: sticky footer

### The ticket names the wrong page for `.rfile`. Read this before the `Done when`

The ticket says the sticky panel `.rfile` is on the task page. It is not. `.rfile` is on two pages, and neither is `/task`:

- **`/recipe/[project]`** at `apps/board/src/app/recipe/[project]/recipe-text.tsx:29` (`<div className="rfile">`). This page draws the footer, so this is the page whose panel the new footer would cover.
- **`/setup/repository/read`** at `apps/board/src/app/setup/repository/read/setup-form.tsx:432`. This page has **no footer**, and the ticket says `/setup` stays unchanged.

So the `.rfile` checkbox is about `/recipe/<project>`. If you shorten `.rfile` everywhere, `/setup`'s panel ends up one footer height short of the window for no reason. Limit the change to pages that have a footer.

The task page does have a sticky element, but it is pinned at the top: the attempt band at `globals.css:2604-2606` (`position: sticky; top: 0; z-index: 2`). The footer is pinned at the bottom, so the two never compete. Leave the band alone.

### The footer rule (`globals.css:165-171`)

Add these to `.footer`:

- `position: sticky; bottom: 0;`
- `background: var(--ground)`: **there is no `--bg`**. The body's background is `--ground` (`globals.css:84`), and it has a dark-scheme value at `:51`. Use `--ground` and the dark scheme works with no extra rule.
- `z-index: 5`. Content that sets `z-index: 2` (the band at `:2606`) must paint under the footer. The bar's filter menu (`.filter .menu`, `z-index: 10`, `:262`) opens downward and must still paint over the footer on a short window. The ⌘K palette is a modal `<dialog>` (`palette.tsx:123`, `showModal()`), so it sits in the top layer and needs no number.

Leave `margin-top: 8px` as it is. It only affects the footer's place in the page's flow and has no effect while the footer is stuck.

All three markups that draw the footer use the same class: the reading (`footer.tsx:111`, `:158`) and the skeleton and failure state (`footer-fetched.tsx:40`). One rule covers all of them, and the pending footer sticks in the same place as the real one.

**Why sticky works on every page.** No ancestor clips it. The root layout puts the page directly in `<body>` with no wrapper (`layout.tsx:78-79`). Every page except home draws `<FooterFetched />` as a sibling after `</main>`, for example `task/[id]/layout.tsx:233-234`. That makes the footer's parent `<body>`, which is as tall as the document. On home the parent is `.home-frame`, which is at least the window's height (`globals.css:308-321`). Only one `overflow-x: auto` sits near the frame: `.cols` at `:335`. It is *inside* `<main>`, not an ancestor of the footer, so it does not break sticky. The ticket asks for a browser check anyway, and that check is still the proof.

### The `.rfile` height

Today's rule (`globals.css:3313`) is `max-height: calc(100dvh - 28px)`. A height has to be a number, and the footer's height varies because it wraps (`flex-wrap: wrap`). Decision:

- Declare the footer's **one-line** height **once**, as a custom property set only where a footer exists: `body:has(.footer) { --footer-h: <measured>px; }`.
- Make `.rfile` use `calc(100dvh - 28px - var(--footer-h, 0px))`, keeping the `100vh` fallback line beside it the way it is written today.
- `/setup` has no `.footer`, so the variable falls back to `0px` there and `/setup` stays unchanged without a second selector.

Measure the value in a browser; don't derive it. The arithmetic suggests about 42px: 1px border, 20px padding, and a 14px font at the body's 1.5 line height. Put a comment beside the value saying what it is the height of.

**Only one line is accounted for, on purpose.** Below 900px, `.s2` collapses to one column (`globals.css:3360`) and the panel stacks under the form. The footer wraps only at narrow widths, so the case where a wrapped footer covers a side panel does not come up. Say this in the comment, so the next reader doesn't "fix" it with a `ResizeObserver`.

**Keep the frame test green.** `home-frame.test.tsx:31-35` forbids only the string `calc(100vh - 41px)` and a `min-height` on `.cols`. Writing the footer's height as a named variable instead of a bare number in a `calc` keeps to #939's intent: the comment at `globals.css:309-312` says a fixed offset "went stale the day the footer arrived". Do not touch `.home-frame`'s `min-height` at all.
