## Shape for #684

**Both folds take the two types in one shared case, and neither one needs the helper's answer to fold.** Use `case 'TicketContinued': case 'TicketClaimed':` in `task-view.ts:243` and `spend.ts:153`. This follows `applyTicket`'s precedent at `packages/domain/src/ticket.ts:268-270`, and it rests on `claims.ts:5`: *"`TicketContinued` is a continuation by type."* (The ticket says `spend.ts:118`, but that line is the `spend_stream` DDL. The case is at 153.)

### Why the old form and the new form give identical rows

The old-form continuation is `continueTicket`'s own append:

```
parsePayload('TicketClaimed', { runId, worker, title: null, kind: null })   // packages/conductor/src/claim.ts:233
```

It always carries `title: null, kind: null`. `TicketContinued` is `{ runId, worker }` (`packages/domain/src/events.ts:226-229`). If both cases read a `TicketContinued` as a claim whose `title` and `kind` are `null`, the fold sees exactly the same values for both shapes. The equality comes from that, and no new branch is needed.

**The trap is the cast.** `ticket.ts:270` writes `event.data as PayloadOf<'TicketClaimed'>` for both types. That is safe there because `applyTicket` never reads `title` or `kind`. Both projections do read them:
- `task_view` passes `d.title` and `d.kind` into `upsert` as SQL parameters (`task-view.ts:258-260`).
- `spend` binds `d.kind` (`spend.ts:158`) and branches on `d.kind !== null` (`spend.ts:160`).

On a `TicketContinued` those reads give `undefined`. `undefined !== null` is true, so `spend` would run the `spend_kind` upsert with an undefined parameter. What a driver does with an undefined bind also differs between the SQLite and Postgres stores. Read the payload through one small local normaliser, `title`/`kind` = `null` when `event.type === 'TicketContinued'`, so the rest of each case stays as it is.

### Where the helper fits, and where it doesn't

The ticket asks both folds to "classify with the shared helper". `claimShapeOf(event, claimed)` (`claims.ts:23`) needs `claimed`, which is the set of runIds earlier `TicketClaimed` events on the same stream carried.

- **Don't keep that set in memory inside `apply`.** A projection folds in batches and from a checkpoint (`spend-rebuild.test.ts:139` `foldInTwoBatches` exists to test exactly that). A set held in `apply` would be empty after a restart or at a batch boundary, and would call a continuation a claim.
- **Neither fold needs the answer anyway.** Each one already decides from its own table:
  - **`task_view`**: the attempt count is decided in SQL: `attempts + case when $10 > 0 and task_view.run_id is distinct from excluded.run_id then 1 else 0 end` (`task-view.ts:789-790`). That is #509's fix. The comment at `task-view.ts:783-788` explains why `task_view_run` is not the "seen" test. Keep it. A continuation must still pass `attempt: true`, because that flag also clears the hold state: `wait_id`, `wait_reason`, `triage_*`, `note` (`task-view.ts:792-800`). The `upsert` doc says so: *"Set on every claim including a continuation's; the SQL decides from the row's own run_id whether the claim is a fresh attempt"* (`task-view.ts:761-765`). Swapping the SQL test for the helper would change behaviour in at least one pinned case. A claim after a release has `run_id` null on the row (`task-view.ts:277`), so the SQL counts it as an attempt. Row 28 depends on that (`task-view-rebuild.test.ts:471-475`).
  - **`spend`**: the `spend_stream` insert is idempotent per `runId` (`on conflict … coalesce(spend_stream.kind, excluded.kind)`, `spend.ts:156-157`). `spend_kind` moves only on a non-null kind. A null-kind claim of either shape changes nothing once the run is linked, and links the run if it is the first event. `spend-estimate.test.ts:78-89` already pins this for the old form.

So the helper's contribution here is the rule it states: `TicketContinued` is claim-shaped. Do not call `claimShapeOf` with a made-up `claimed` (`[]`, or one read from `task_view_run`) just so a call is there. Put a comment on each shared case that cites `claims.ts` and explains why the fold's own table, not the helper's `claimed`, decides. That covers the first "Done when" box.

Do not copy `ticket.ts:273`'s guard either (*"A continuation of a run nobody claimed continues nothing and records nothing"*). The old form has no equivalent: a `TicketClaimed` on an unknown run is a claim by definition. Copying the guard would make the two streams diverge in exactly the case the tests compare.
