# #712: init signs `gh` in from inside the question

## Where it goes

Everything is in `askGithubAuth`, in `apps/cli/src/github-auth.ts`. It changes only on its last path: no `github.auth`, no App, no `--github-auth`, and `notReady(status)` is not null (`github-auth.ts:155-166`). The flag paths and the "already elected" path stay as they are.

**The port.** Add an optional `gh?: GhRun` to `GithubAuthWorld.github` (`github-auth.ts:27-36`). This is #706's runner, used as it is: `GhRunOptions.stdio: 'inherit'` "hands the terminal over (an interactive login)" (`packages/github/src/gh.ts:36-37`). **The port being present is how the code knows there is a terminal.**
- `init`'s live world sets it to `liveGh` only when `refusal('', interactivity(false))` is null. That is the same test `liveAsk` uses to decide it may ask (`apps/cli/src/prompt.ts:74-79`). Under `--json` or off a TTY the port is left out, so the option is never offered.
- Thread it from `InitWorld` (`init.ts:199-200`, beside `ghStatus`) through the `github:` block at `init.ts:530-539`.
- `lingtai add` builds its own world (`first-project.ts:873`) and does not get the port. The ticket covers `init`. Adding it to `add` later is one line.
- Every existing #710 test uses a fake world with no `gh`, so none of them changes.

## The loop

Replace the single `question()` at `github-auth.ts:156-166` with a loop. The sign-in option is offered only when one of these is true:
- `status.ok === false` and `status.reason` is `signed-out` or `no-account`. Run `['auth','login','--hostname','github.com','--web','--scopes','workflow']`.
- `status.ok` and `ghScopeGap(status) !== null`. Run `['auth','refresh','--hostname','github.com','--scopes','repo,workflow']`.

It is not offered for `missing`, which is the ticket's edge: #710's install line stands. It is also not offered for `too-old` or `unparsed`. Signing in cannot change a status that `gh auth status --json` cannot report (`gh.ts:112-127`), so the option would loop for nothing.

**The choices when it is offered:** `['sign-in', 'app']`, with `sign-in` as the default.
- `gh` is dropped from this list. Today choosing `gh` here only refuses with "fix it and run this again" (`github-auth.ts:166`), which is exactly what this ticket replaces.
- When sign-in is not offered, the prompt, the choices and the `app` default stay #710's.
- The default is `sign-in` because #710 defaults to `gh` (`39ac9d6e`) and this is the way to get there. A failed sign-in costs nothing, because it comes back to this same choice.

**On `sign-in`:**
1. Log one line naming the exact `gh` command before handing over, so the person knows what took the screen.
2. Run `await world.github.gh(args, { stdio: 'inherit' })` inside the SIGINT guard (below).
3. Re-read `world.github.ghStatus()` whatever the outcome.
4. If the exit code was 0 and `notReady(fresh) === null`, log `github       gh, signed in as <login>` and return `write()` (`github-auth.ts:138-145`). This is "continues as if gh had been chosen". The gh/app question is not asked again.
5. Otherwise, a non-zero exit or a still-not-ready status:
   - Log what happened: `gh auth login exited N`, or the new `why`.
   - Go round again with the **fresh** status, so the prompt is right for the next attempt. A login that worked but still lacks a scope now offers `refresh`, and a status that has become ready shows #710's ready prompt (`github-auth.ts:147-153`).
   - Nothing is written on any of these paths. `writeAuth` is reached only through `write()`.
6. `{ missing: true }` from the run (gh was removed in between) is a non-zero exit like any other. The fresh status then says `missing`, so the option drops out.

The loop has no bound, and that is on purpose. Every turn is a person choosing `sign-in` again. They can choose `app` instead. Ctrl+C at the select exits 130 through `liveAsk`'s own path (`prompt.ts:89-92`).

## Handing the terminal over

**Nothing extra is needed to release the terminal.** `liveAsk` resolves only after clack's prompt has closed. On submit, `@clack/core` turns raw mode off and closes its readline, and closing readline pauses stdin (`node_modules/.pnpm/@clack+core@1.4.3/node_modules/@clack/core/dist/index.mjs:156` and `:266`). Check which `@clack/core` `apps/cli` actually resolves (1.4.0 and 1.4.3 are both in the store). If that version leaves stdin flowing, add `process.stdin.setRawMode?.(false); process.stdin.pause()` in the live port before the spawn. Do not use `waitForKeypress`: it is the precedent for undoing raw mode (`keypress.ts:47-54`), not a helper to call here.

## The SIGINT guard

Put the guard in `askGithubAuth` around the `gh` call, not inside `liveGh`. That keeps the Done-when test at the same level as the other four: a fake `gh` plus the real `process`.

```ts
const ignore = () => {}
process.on('SIGINT', ignore)
try { result = await world.github.gh(args, { stdio: 'inherit' }) } finally { process.off('SIGINT', ignore) }
```

- This is `liveTrialBuild`'s shape (`trial-build.ts:236-246`), with a no-op listener in place of an abort.
- Use `on`, not `once`. A second Ctrl+C during the same login must not kill init.
- Any listener at all stops Node's default exit-on-SIGINT. The `gh` child is in the same foreground process group, so it gets the signal itself and exits non-zero, which returns to the choice.
- Remove only your own listener and leave the others. That is what "the previous handler is restored" means here.
- 0121 §10 bars signal listeners for *output* ("a spinner, a progress line… never installs a signal listener"), not for the command: "the command owns the process". `init` is the command.

**The test:** a fake `gh` records `process.listenerCount('SIGINT')` and whether `process.listeners('SIGINT')` includes a listener that was not there before the call. Afterwards the count and the list match what they were before. Add a sentinel listener before the call and check it is still there afterwards.

## The scrubbed environment, and what makes it checkable

`GhRun` carries no `env`, on purpose. The scrub belongs to the live runner (`gh.ts:5-8`: "`scrubbedEnv` is what the live runner passes as `env`"). An `askGithubAuth` test with a fake `gh` therefore cannot see the env. Two tests meet the "scrubbed env" checkbox together:
1. In `gh.ts`, extract `ghSpawnOptions(parent, signal)`, which returns `{ env: scrubbedEnv(parent), stdio: 'inherit', signal }`. Have `liveGh`'s inherit branch (`gh.ts:50-55`) spread it. Add a case to `packages/github/unit/gh.test.ts` next to the existing one at `:13-16` ("is what the live runner hands the child"), with `GH_TOKEN` set in the parent.
2. The init-level test asserts the arguments and `{ stdio: 'inherit' }` given to the port.

Point to both in the PR so nobody looks for an env assertion in `init.test.ts`. **The scrub is load-bearing**: `gh auth login` refuses outright when `GH_TOKEN` is set.

## Decided here

- **No `--git-protocol` and no answering `gh`'s prompts.** Pass exactly the ticket's argument lists. `gh`'s own questions go to the person over the inherited terminal (0114 §1).
- **`--defaults` still shows the option at a terminal.** This question is never wrapped in `acceptingDefaults` (`github-auth.ts:10-13`).
- **Init dies while `gh` runs.** Nothing of init's has been written yet, since `writeAuth` comes after the re-check. `gh` may have saved a login, and a re-run then finds it ready and goes down #710's ready path.
- **Two inits at once.** Both write `gh`'s own hosts file, and that is `gh`'s problem. Each init re-reads the status afterwards, which is the only thing either one acts on.
- **The run log or events.** None. This is `init` at a terminal, before any conductor exists.
