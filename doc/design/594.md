## Shape

The ticket's Fix covers the prompt. The two things it leaves out are how the shas get from the route to the review action, and one fact about the review's main diff after the merge, which the section depends on (§3).

### 1. Carry it on `ActionContext`, set by the `MergeBase` route, absent otherwise

The `{ paths, fromSha, toSha }` already reaches `runPass`. The route's `offer.proposal` is the `BaseMoved` proposal (`packages/domain/src/proposal.ts:83-88`), and all three fields there are **nullable**. The context is the one way a fact about *this run of the pipeline* reaches an action. `recheck`'s docblock gives the reason: *"On the context rather than on a spec, because it is a fact about this run of the pipeline exactly as `onSha` is"* (`packages/actions/src/action.ts:480-494`).

- **Add `landedOnBase?: { paths: string[]; fromSha: string; toSha: string }` to `ActionContext`** (`action.ts:459`), as a neighbour of `recheck` and `again`.
- **Add `let landedOnBase = null` in `runPass`** beside `onSha` and `recheck` (`packages/conductor/src/pass.ts:1207-1210`). Write it in the `case 'MergeBase'` success path (`pass.ts:1308-1333`) from `offer.proposal`, but only when `paths` and `fromSha` are both non-null. Use `next.toSha` for `toSha`, because that is what was merged. If either field is null, leave it null: there is nothing to diff, and the review falls back to the ordinary prompt.
- **Spread the key in `contextFor`** (`pass.ts:1220`), and never set it to `undefined`: `...(landedOnBase === null ? {} : { landedOnBase })`. An ordinary pass's context then has no such key, so every existing `toEqual` on a context stays green.
- **Clear it in `case 'FixRound'`** (`pass.ts:1334`). The ticket says *only the review after a base-moved merge*. Any finding that review raised about the interaction travels on `recheck` from then on, so a re-review does not need the base diff again.
- **A second `MergeBase` replaces the value.** After the first merge, the fork point is the old `toSha`, so the second refusal's `fromSha` is exactly where the base's next move starts.
- **Do not seed it from `options.from`.** `baseMergesSpent` isn't seeded either (`pass.ts:1173-1178`, *"a continuation is a new pass"*). The continuation reaches `merge` again, is refused again, and goes through the same route.

### 2. The base diff is a dep, cut by a pure function

The actions package doesn't run git. `AgentActionDeps.diff` says so: *"Supplied by the caller: the actions package does not know about git, and should not learn"* (`packages/actions/src/agent-action.ts:112-114`).

- **Add an optional dep, `landed?: (moved) => Promise<{ path: string; diff: string }[]>`.** Implement it in `conduct.ts`'s `stepDeps.agent` (`conduct.ts:2878-2881`) as one `git diff <fromSha> <toSha> -- <path>` per path.
- **Use `gitAsked`, not `gitOrDie`** (`conduct.ts:1570-1571`). A diff that can't be read must not kill the review. Put the git error text into that path's `diff` instead.
- **One git call per path, not one for all of them.** Splitting a combined diff back into paths means parsing `diff --git` headers, and git C-quotes non-ASCII paths there (#593's note gives the same reason for `-z`). The paths are the overlap only, so they are few.
- **Both shas are already in the worktree.** The `mergeBase` port fetched and merged `toSha` (`conduct.ts`, the `mergeBase` closure #593 added), and `fromSha` is an ancestor of the branch.

**Build the section in a pure exported function**, e.g. `landedOnBaseBlock(per: {path, diff}[], capLines)`. That function is what *Done when 2* tests.

- **`LANDED_DIFF_LINES = 400` is a module constant in `agent-action.ts`, not a recipe knob.** The ticket fixes the number. It is separate from `runtime.budget.diff`, which caps the branch's own diff in bytes (`agent-action.ts:274-275`).
- **Walk the paths in order and add lines until the cap.** The path the cap lands in is shown cut and named as cut. Every path after it is named as left out.
- **The section always lists all the overlapping paths up front**, so the reviewer knows the overlap even where the diff was cut.
- End with the ticket's question, word for word: *does what landed on the base change the behaviour this change relies on or alters? Name the line on each side.* Answers go into the ordinary `findings`, so `CONTRACT` and `REVIEW_ANSWER_JSON_SCHEMA` don't change.

### 3. The main diff after a merge is not the branch's change, and this ticket has to fix that too

The review's diff is `git diff ${baseShaOr('HEAD')}...HEAD` (`conduct.ts:2881`). `baseShaOr` is the pass's original cut (`conduct.ts:1582`).

**The problem:** after `mergeBase`, the merge commit has `toSha` as a parent. The original cut is now an ancestor of `HEAD`, so the three-dot merge-base is still that cut. The "diff under review" now contains **everything that landed on the base**, including files that don't overlap.

- #593's note claims *"`review`'s diff is against the new base"*. That isn't what the code does.
- #593 had no section to confuse it with. Here, the base's changes would appear twice: once as the branch's change and once as what landed. The question *does what landed change what this change does* can't be answered when the two can't be told apart.

**So in this ticket, change `diff` to `diff: (from?: string) => Promise<string>`.**

- `createAgentAction` (`agent-action.ts:459`) passes `context.mergedOnto ?? context.landedOnBase.toSha`. `runPass` keeps `mergedOnto` after the first fix round drops `landedOnBase`, because the original cut stays an ancestor of `HEAD`; do not remove it as redundant. Only an ordinary pass that never merged the base passes nothing.
- A **human-granted continuation** is a fresh `runPass`, so `mergedOnto` starts null there. `conduct.ts`'s `diff` then finds the merge in the branch (`heldBaseMerge`: our `Merge <base> at … into <branch>` commit's second parent) before falling back to the original cut.
- `conduct.ts` uses `${from ?? baseShaOr('HEAD')}...HEAD`. With no argument, the command is the same as today.
- `toSha...HEAD` is exactly the branch's change against the base it was merged with.
- Leave `numstat` and `changedFilesArgs` (`conduct.ts:1591`, `:2910`) alone. They feed other consumers, and changing them is a different ticket.

### 4. The prompt, byte for byte

Add an optional last parameter to `buildReviewPrompt` (`agent-action.ts:267`), after `recheck`.

- **Insert the section between the diff's closing fence and `## How to report`** (`:296-301`). Use the same idiom as the recheck block: `${block ? `${block}\n\n` : ''}`. With nothing passed, the template's characters are exactly today's.
- **After the diff, not before it.** The question is about "this change", and the reviewer has to have read the change first.
- **Call `deps.landed` only when `context.landedOnBase` is present.** An ordinary review makes no extra call.
- Add a `context.log?.note('review', …)` suffix, e.g. `· base moved on N paths, M lines shown`, in the style of the `rechecking` suffix (`:489-492`).
- **Keep `reviewId` unchanged** (`:487`). After a merge, `onSha` is the merge commit, which already makes it a new reviewer.

### 5. Tests (all unit, in `packages/actions/unit/agent-action.test.ts`)

**For *Done when 1*:**

- A `createAgentAction` run with `landedOnBase` set and fakes for `landed`, `diff` and the runtime. Assert three things:
  - the runtime's `prompt` contains the section and the question;
  - `landed` was called with exactly the context's paths and shas;
  - `diff` was called with `toSha`.
- The same run without the key. Assert three things:
  - `landed` was never called;
  - `diff` was called with no argument;
  - the prompt equals `buildReviewPrompt(spec, issue, diff, n, recheck)` called without the new parameter.
- Also pin a literal heading: the ordinary prompt does **not** contain the section's heading.

**For *Done when 2*:** `landedOnBaseBlock` over three paths whose diffs add up to more than 400 lines. Assert three things:

- the section has at most 400 diff lines;
- the path the cap landed in is named as cut;
- the paths after it are named as left out.

**In `packages/conductor/unit/a-base-that-moved.test.ts`,** extend the existing route test:

- the `review` action's `ActionContext` after the merge carries `landedOnBase` with the proposal's `paths` and `fromSha` and the route's `toSha`;
- the first `review`, before the refusal, has no such key;
- a `review` after a later `FixRound` has no such key.

**Not reachable before the merge:** the `conduct.ts` closures (`git diff` per path, and `toSha...HEAD`) need the `git` binary, so per 0060 §1 they are integration. The unit claims that stand in for them are that the action asks `diff` for `toSha` and asks `landed` for exactly the context's paths.

### Settling it afterwards

The prompt isn't an event, so the log can only settle that the conditions were met. Look for:

- a `RouteTaken` whose decision chose `merge-base`;
- then a `StepStarted{step: 'review'}` at the same `round`;
- with that review's `StepFailed`/`StepPassed` findings citing a base-side line.

The run log note in §4 is only a trace.
