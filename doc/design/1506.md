# #1506 — shape

## Where it goes

**One new pure file, `apps/board/src/lib/pr-fixing.ts`.** It has the rule, the words and the column decision, and nothing else. It imports only types and pure helpers, under the same promise `pr-board.ts:4-6` makes: *"Pure: it imports types and the domain's pure folds, never a store, so a test reads every word the page draws without rendering."* `pr-board.ts`, `pr-page.ts` and `waitingPrs` all import it. The only `@lingtai/conductor` import it may take is `PR_FIX_LABEL` / `LANDED_LABEL` / `HOLD_LABEL` from `@lingtai/conductor/labels` (`labels.ts:26-33`). Do not pull `conduct.ts` into it: `pr-board.ts:5-6` says *"the conductor stays out of this file so a client graph may import it"*, and only the Next build (`apps/release/integration/build.test.ts`, after the merge) would catch that import. Inline the comparison the take uses at `conduct.ts:3293` (`kind.toLowerCase().replace(/\s+/g, '-') === PR_FIX_LABEL`) as a small exported `isPrFixKind`.

**The reads go in `apps/board/src/lib/prs.ts`, as Effects.** That is where `readPrPage` (`:163`), `readPrDetail` (`:337`) and `waitingPrs` (`:120`) already live. No new `async` function and no new `Effect.run*`. Wrap `readAttemptState` (a Promise, `board.ts:1650`) in `Effect.tryPromise` inside the generator each caller already runs. The ratchet (`effect-ratchet.baseline.json`) must not move up.

## The one data shape

`prBoard` and `prPage` get one new **optional** input, `fixes?: PrFixRead`, for the open PR only (`openAmong`, `pr-board.ts:309`). When it is absent the output is exactly today's, so the existing `pr-board`/`pr-page` unit tests stay green untouched.

    PrFixRead =
      | { kind: 'failed'; why: string }                       // projection, a ticket stream, or the listing
      | { kind: 'read';
          claimed: ClaimedFix[];                              // pr-fix rows of task_view, each with its stream's reduce
          listed: ListedFix[] | 'not-asked' }

    ClaimedFix = { issue, title, state: TaskState, cutFromPr: number | null | 'absent',
                   step: string | null, takenAt: Date | null }
    ListedFix  = { issue, title, labels: string[] }

`fixingOf(pr, read)` returns one of three things:
- `{ kind: 'none' }`
- `{ kind: 'unknown'; why }`
- `{ kind: 'fixing'; lines: FixLine[]; waitingOn: issue | null }`, with `FixLine = { issue, title, word, href }` sorted by issue number and `href` from `ticketPath` (`paths.ts:59`).

Next to it, `countsAsWaiting(pr, fixing)` is the **one** decider. It answers true when `pr.status === 'waiting'`, unless the wait's reason is `ci-red` and `fixing.kind === 'fixing' && fixing.waitingOn === null`. `prBoard` uses it for both the column and `waitingCount` (`pr-board.ts:467-469`). `waitingPrs` uses it for the badge. That is how the ticket's "one function decides both" is built.

Decided here, not in the ticket:
- **A claimed row whose stream has no `cutFrom` (`'absent'`) is not fixing any PR.** The claim decides whenever there is one. The field is *"Absent on every other claim, and on every claim written before this field existed"* (`events.ts:261-265`), so an absent `cutFrom` says the claim was not cut from a PR.
- **A listed ticket that has any `task_view` row, terminal or not, is dropped from `listed`.** It has been claimed, so its row and its claim decide it, not its labels.
- **The `fixOwed` + `landed` case is computed from `pr` alone** (`pr.fixOwed`, `pr.fixesLanded`, titles from `pr.tickets`, `domain/src/pr.ts:332-352`). It never needs a read, so it is drawn even when `read` is `failed`.

## How the reads are assembled (`prFixReadOf` in `prs.ts`)

1. **The reads run only for an open PR whose status is `waiting` or `in-review`.** In every other state the card does not change, so nothing extra is read.
2. **Read the projection:** `readTasksEffect({ project })` (`task-view.ts:1043`), keeping rows where `isPrFixKind(row.kind)`.
3. **Read the ticket stream** only for rows whose state is not `landed`/`satisfied`/`closed`, usually none or one. Read it as `task.ts:1237` does (`reduceTicket` over the stream `ticketStream(project, issue)`, `domain/src/streams.ts:24`). That gives `cutFrom.pr` (`TicketState.cutFrom`, set at `ticket.ts:597`, which is the latest claim) and `takenAt`, the time of the stream's first `TicketClaimed`, for History. `TaskCard` has no `cutFrom` (`task-view.ts:771`), so this read is the price of rule 3. Keep it bounded by the filter above.
4. **For rows in `running`/`verifying`/`approved` with a `runId`, read the step:** `readAttemptState` → `progressOf` → `stepOf(now.label)`, the way `board.ts:1700-1706` does. If that read fails, `step` is null and the word is `running`. Never draw it as stopped.
5. **Ask the listing only when** `fixingOf(pr, { …, listed: 'not-asked' })` is `none`, `pr.status` is `in-review` or a CI wait (`CI_WAITS`, `pr-board.ts:155`), and the call would offer the button. Get the `Tickets` the way the Queued column does: the board already builds it per project through `queueFilters` (`board.ts:1111`), whose `AskableFilter` carries `tickets` (`:956`) and resolves `db` vs GitHub through `ticketsForEffect` (`ticket-store.ts:270`). Do not build a second GitHub client. Cap it with `Effect.timeout(ISSUE_READ_BUDGET)` (`prs.ts:263`). Keep entries whose labels include `PR_FIX_LABEL` and exclude `LANDED_LABEL`. An entry with `HOLD_LABEL` gets the word `waiting on you`.
6. **Any failure in steps 2, 3 or 5** gives `{ kind: 'failed', why }`. That is never `listed: []` and never `claimed: []`. The pure function turns it into today's card plus the sub-line `could not tell whether a pr-fix is open: <why>`.

**The `waitingPrs` path stops after step 3.** It never runs step 4 or 5. Order it so the extra cost lands only where the badge can change: first `openPr`, which it already does (`prs.ts:122`). Then, only when `pr.status === 'waiting'` and `prWaitOf(pr).reason === 'ci-red'`, run steps 2 and 3. For every other PR, the badge costs exactly what it costs today. If that read fails, the badge is `null` through the existing `.catch(() => null)` (`prs.ts:266`). For a unit test, give `waitingPrs` an injectable third parameter (the fix read, defaulting to `prFixReadOf`). Use the memory event store for `openPr`. `readTasksEffect` opens a real store (`withStoreEffect`), so it must not be reached from a unit test.

The comment on `waitingPrs` must say what the ticket accepts: *an unclaimed pr-fix is not seen here, so the badge may say ❶ for up to one queue pass while the board says In progress.*

## Drawing

**`prBoard`.** When the open PR is `waiting`, compute `fixing` and branch on `countsAsWaiting`.
- **Leaves Waiting (`ci-red`, fixing, nothing waiting on you):** build the card in `progress` from the same parts `waitingCard` builds (`pr-board.ts:504-566`), with these changes:
  - head `${prName(pr)} · fixing CI`, pill `in progress`;
  - sub-line `${detail up to the first ':'} — a pr-fix is on it`;
  - the CI chip from `chipsOf` (`:252-265`) swapped for `CI ↻ fix` / `running`;
  - one `fixing:` line per ticket;
  - *Open the run ↗* kept, *New pr-fix ticket* dropped.

  Factor the button list out of `waitingCard` and pass it a `withFix: boolean`. Do not copy it.
- **Stays Waiting:** today's `waitingCard`, plus the `fixing:` lines. With a CI wait and a ticket waiting on you, the sub-line is `#N is waiting on you` and the button is still hidden. For a non-CI wait, its own buttons are unchanged (`:519-531`).
- **`in-review`:** the review card (`:470-478`) gains the `fixing:` lines.

**The `fixing:` line needs a field `CardView` does not have**, because it is a link. Add `fixing?: readonly { text: string; href: string }[]` to `CardView` and render it in `pr-columns.tsx:28-52` with the link styles `doc/design/the-board-style.md` already has. Do not use `sub`, which is plain text.

**`prPage`.**
- Replace the `addFix()` calls at `pr-page.ts:672-679` and `:687-689` with "the `fixing:` lines if `fixing.kind === 'fixing'`, else `addFix()`".
- Leave the poster and the wait panel reading `pr` as today.
- History: add `fixesTaken: { issue, at }[]`, built from `ClaimedFix.takenAt` of the tickets that are fixing the PR. Merge it by time into the `events.map(... summarise ...)` list (`:777`) as `pr-fix #N taken`.
- `readPrDetail` (`prs.ts:392`) and `readPrPage` (`:199`) each call `prFixReadOf` for the open PR and pass the result in.

## What stands in for what cannot be run

`pnpm test:integration` is not needed. Every *Done when* item is a unit test:
- `pr-fixing.ts` tested directly: the rule, each table row, two tickets, a claim naming another PR, `cutFrom` absent, `lingtai:landed`, `fixOwed`, `failed`.
- `prBoard` / `prPage` given plain `PrFixRead` values.
- `waitingPrs` with its read injected.

One thing only the Next build sees after the merge: `pr-fixing.ts` reaching the client graph with a server import. The unit-level stand-in is that `pr-fixing.ts` imports only from `@lingtai/domain`, `@lingtai/conductor/labels` and `./paths.ts`. Say so in its header comment.

What the log would settle, when someone checks #1505 on the running board: its stream's first `TicketClaimed` and that event's `cutFrom.pr` (expected `8`), and the `task_view` row's `state`. No ADR is contradicted: ADR 0131's display and `PrState` are untouched, and nothing is appended.
