# #509 — count a pass once in `task_view`

## Decision: fix the fold, not the log

`task_view`'s `TicketClaimed` case keeps folding every claim. The upsert adds one to `attempts` only when the claim names a run the row is not already on. No new event, no new payload field and no new column, so this is not a log change, and the commit body has nothing of that kind to declare.

The other option, giving the continuation its own event or field, loses for three reasons:

- **The second claim is deliberate.** The docblock on `continueWorkItem` says so: *"this is not a second kind of claim on the log — it is the ordinary one, appended again, onto a run that has already spent its first claim"* (`packages/conductor/src/claim.ts:150-152`).
- **The other fold already handles it.** `attempts.ts` de-duplicates the same event (`packages/conductor/src/attempts.ts:173-181`): *"A second claim by the same run is the same attempt claiming again, not a new one … a continuation's own claim must not count as a fresh attempt."* So the bug is that `task_view` disagrees with that fold, not that the log is ambiguous.
- **It would be a log change.** A new event or field means a domain schema change plus a change to every fold that reads `TicketClaimed`, which is exactly what the ticket's *Watch out* row warns against.

## Where the change goes

The change goes in `upsert` in `packages/projector/src/task-view.ts:708-761`, and nowhere else in that file.

### Use the row's own `run_id` as the "seen" test

The condition is `task_view.run_id is distinct from excluded.run_id`, inside the `on conflict … do update` branch. It depends only on the row and the event, so `task_view` stays a plain fold.

Do **not** use `task_view_run` to decide "seen". `linkRun` runs *before* the upsert in the same case (`task-view.ts:264`), so the run is always in that table by the time the upsert runs. Using it would mean reordering the case, and the `TicketClaimed` comment at `:271-275` explains how two-statement orderings in this case have already silently broken the counter once.

### Why the row's `run_id` is reliable

- **Releases clear it.** `TicketReleased` sets `run_id: null` (`:298`), so the first claim after any release always counts.
- **The insert path already counts.** A row created by its first claim gets `attempts = 1` from the `values (…, $10, …)` clause, which needs no change.
- **A continuation always matches.** `continueWorkItem` refuses unless `lifecycle.status === 'approved'` and `lifecycle.runId === runId` (`claim.ts:168-173`). An approved item never passed through a release, so its row's `run_id` is still that run.
- **`RunStarted` writes the same value.** It sets `run_id: event.streamId` (`:411`), the same run, so nothing in between can make the comparison wrong.
- **The `coalesce` is safe.** `coalesce(excluded.run_id, task_view.run_id)` (`:737`) only fills a missing value and never replaces a different one.

### Change `attempts` and nothing else

Only line `:738` should change:

```
attempts = task_view.attempts + case when $10::int > 0 and task_view.run_id is distinct from excluded.run_id then 1 else 0 end
```

Leave every other `$10::int > 0` branch as it is. That covers `last_attempt_at`, `note`, `awaiting_sha`, `waiting`, `asked`, `needs`, `diagnosis`, `repair_run_id` and `repair_pending`. A continuation is the run running again, and those resets are right for it:

- **The hold resets do nothing here.** `WaitResolved{Approve}` already cleared the hold and set `state: 'running'` (`:595-615`).
- **`last_attempt_at` must keep moving on every claim.** The board's backoff reads it off events and counts *any* `TicketClaimed` (`apps/board/src/lib/queued.ts:209-210`). Gating the column would open a second disagreement while closing this one.

If you rename `attempt` in `upsert`'s values type (`:720`, *"True when this event is a fresh attempt"*), keep it true for every claim. It now means "this is a claim", and the SQL decides whether the claim is a new attempt.

### No changes downstream

These all read `attempts` and become correct once the column is: `withNoSpendFallback` (`apps/board/src/lib/spend.ts:107-117`), `board.ts:1045` and `:1400`, `apps/site`'s `snapshot.ts:230`, and the `attempt N` pill at `page.tsx:305`. The spend side needs nothing: the continuation's `Action` rows already carry `pass = <same run>`, so `accounted` was right all along. Only `attempts` was over-counting.

## Test

Add the test to `packages/projector/unit/task-view-rebuild.test.ts`. That file folds a fixture through `createSqliteProjectionStore` (`:440-446`), which is the unit half and needs no Postgres.

### Fixture

Add a **new stream** rather than extending `ticket-pin-approval`. The existing approval assertions (`:472-493`) are pinned to `afterApprovalGranted`, and appending to that stream would change what they cover. The new stream runs:

1. `aClaim(stream, run)`
2. a sign-off (`StepEnded` with `Completed{requested}`, then `aWait(SignoffRequired)`)
3. `aResolution(Approve)`
4. a second `aClaim(stream, run)` with the **same** run id. This is what `continueWorkItem` appends.
5. another sign-off, then `Approve`, then a third `aClaim` on the same run

The rows from 4 and 5 are the ones #465 tests never produced. Also give the run one `Action`-purpose spend. Copy whatever `spend-rebuild.test.ts` uses to build a `RunSpent`; that event is folded into the spend projection, not `task_view`, so it only matters for the card assertion below.

### Assertions

- **Two approvals, still one attempt.** After the third claim, the row has `attempts: 1`, `run_id` equal to that run, and `state: 'running'`.
- **No unknown-cost run.** The *Done when* asks for no unknown-cost run on the card. The card's figure is `withNoSpendFallback(billOf(rows), t.attempts, rows)`. Make it a pure unit test in `apps/board/unit/`: call `withNoSpendFallback` with `attempts: 1` and `Action` rows that all carry `pass: 'pass-A'`, and assert `Work` has no unknown component. Next to it, call `withNoSpendFallback` with `attempts: 2` and the same rows, and assert it *does* add `unknownBill(1)`. That pins the arithmetic the review described, so the projection test's `1` is what keeps the card honest.
- **A new run still counts.** A claim after a `TicketReleased` with a **different** run id must still make it `attempts: 2`. Add this on the same stream or a sibling one, so the new condition cannot pass by never counting at all.

### Snapshot

The *"produces the same final rows"* test (`:453-457`) uses `toMatchSnapshot`, and a new stream adds a row to it. Update `__snapshots__/` with `-u`, then read the snapshot diff: it should be **only** the new stream's rows. A changed `attempts` on any existing row means the condition is wrong.

## After it lands (for the commit body)

- **Rebuild once.** The fold changed and the table did not, so run `lingtai projection rebuild task_view` once; no `reset` or schema migration is involved. Rows for tickets that were continued before the fix (#465 is one) currently over-count, and the replay corrects them.
- **Restart before rebuilding.** Every process that appends holds a projector on the code it started with, so do the rebuild *after* `lingtai restart`. Otherwise the old daemon's projector will add another phantom on the next approval.
- **What settles it in the log.** These are runs whose `TicketClaimed` events repeat the same `data.runId` on one ticket stream. For those, `task_view.attempts` should equal the number of distinct `runId`s among the stream's `TicketClaimed` events. An agent cannot read production `events`, so that check belongs to whoever runs the rebuild.

## Not in scope

- **`queued.ts`'s backoff.** It also counts every `TicketClaimed` (`queued.ts:210`), but only for items in the queue, and an approved item is never queued (`:608-613`). Leave it.
- **Prompt numbering.** The deferred prompt-numbering item from the #465 design doc is a separate fact, as the review says.
