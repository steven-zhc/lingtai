# Design note: #671, a review after a fix round reviews the fix and rechecks the rest

## Where it goes

There are two halves, and the boundary between them is `ActionContext`. Nothing in `conduct.ts` changes.

**`packages/conductor/src/pass.ts`** keeps two new `let`s inside `runPass`, beside `recheck`, `landedOnBase` and `mergedOnto` (`pass.ts:1211-1217`). It passes one new field, `reviewedSha`, on `contextFor()` (`pass.ts:1229-1236`). Spread it only when non-null, the same way `landedOnBase` and `mergedOnto` are spread today.

**`packages/actions/src/action.ts`** gets one new optional field on `ActionContext`, next to `mergedOnto` (`action.ts:510`): `reviewedSha?: string`. It is the head the last review in this pass actually read.

**`packages/actions/src/agent-action.ts`** does all the reading, prompting and demoting. `diff-hunks.ts` (#670) gets a second demotion function next to `demoteOutsideDiff`. Do not change `demoteOutsideDiff`.

## The pass side: when `reviewedSha` is written

There are three writes. Keep them all in `runPass`, the same way `record` (`pass.ts:1245-1249`) is the one place `onSha` is written.

1. **After a `review` visit is recorded, but only if a reviewer actually read the head.**
   - Set `reviewedSha = visitContext.onSha` only when the visit's `results` contain an action with `verdict` `passed` or `failed` and without `unreadable`.
   - `results` carries `verdict` and `unreadable` per action (`action.ts:650-660`).
   - Do not key this on `ending.ending`. A `review:` list can open with a `run:` that refuses before the agent runs. An unreadable answer is a `failed` that read nothing (`agent-action.ts:768-790`). A `did-not-finish` read nothing either.
   - Setting `reviewedSha` on any of those would make the next review delta-only over a head nobody reviewed. That is the one way this change could let a defect through rather than just cost a round.
   - Use `visitContext.onSha`, not `onSha` after `record`. They should be equal because a review commits nothing, but the context is what the reviewer was handed.

2. **In the `MergeBase` case of `routeProposal`** (`pass.ts:1343-1356`), reset `reviewedSha` to `null`. The approval exception below is the only case where it is not null.

3. **The approval exception.** Seed a second variable once, at the top of `runPass`:
   ```
   approvedAt = options.from !== undefined
     && options.from.grant === undefined
     && (options.from.step === 'proposed' || options.from.step === 'merge')
       ? options.context.onSha : null
   ```
   - On a continuation, `options.context.onSha` is the approved head: `conduct.ts:1043` sets `onSha: approvedOnSha`.
   - `proposed` and `merge` are the only steps a wait arises at after a review has read the head. A wait at `design` or `implement` was never reviewed.
   - A grant continuation goes to `implement` and is a fix round. The ticket's edge says a resumed pass has no `reviewedSha`, so it does not get one.
   - In the `MergeBase` case: if `approvedAt !== null` and `onSha === approvedAt` before the merge (no commit since the approval), set `reviewedSha = approvedAt` instead of `null`. Then set `approvedAt = null` either way.
   - It is used once. A second base move later in the same continuation was not approved by anyone, so it gets a full review as usual.
   - `landedOnBase` and `mergedOnto` are set by the same case, so the review of the merged head gets both the delta section and the #594 block.

Leave the `FixRound` case (`pass.ts:1357-1369`) alone. The fixer commits on top, `onSha` moves, and the next review sees `reviewedSha !== onSha`, so it reviews the delta.

## The action side: one rule decides when the delta applies

In `createAgentAction.run`, after the main diff is read and found non-empty (`agent-action.ts:595-601`):

- If `context.reviewedSha` is set and differs from `context.onSha`, call `deps.diff(context.reviewedSha)`. Do it inside a `try`, because `deps.diff` is `gitOrDie` (`conduct.ts:3028-3039`) and throws. Today that throw kills the review, and the delta must not.
  - The call gives `reviewedSha...HEAD`. That is `reviewedSha..HEAD` because the reviewed head is an ancestor of the current one.
  - After an approved merge it is everything the merge brought in, including every base change and not only the overlapping paths. That is a superset of what the ticket names. It errs toward not demoting, which is the safe direction.
- Build `delta = { text, hunks: hunksOf(text) }`. Fall back to today's review (no delta section, today's recheck sentence, nothing demoted) if any of these happen:
  - the call threw;
  - `text.trim()` is empty;
  - `hunksOf` returned `null`.

  On each fallback, add a `context.log?.note('review', …)` line saying why.
  - Treating unreadable hunks as a fallback is my addition to the ticket's *fails to read* edge. A prompt that says *only the delta* with no demotion behind it is a promise nothing keeps.
- Add the delta's size to the existing log note at `agent-action.ts:604-609`. For example, ` · fix delta 1234 bytes since abc1234`, so the run log shows which kind of review ran.

### The prompt

`buildReviewPrompt` gets an optional `delta` argument, placed after `landed`. Keep the positional order, since tests call it directly.

- **The delta section** goes right after `## The diff`, as `## What the fix changed` (`reviewedSha[0..7]..onSha[0..7]`). Clip it at `limitBytes` the same way the main diff is clipped.
- **The scoping instruction lives in the delta section, not in `recheckBlock`.**
  - After an approved merge, `recheck` is empty: a non-grant continuation carries no `findings` (`conduct.ts:1054-1063`), so `options.from.findings` is undefined. `recheckBlock` then never renders, but that review still has to be told to look only at the delta.
  - Put the sentence in the delta section. It should say: look for new problems only in what this section changed; the rest of the diff is context for that and for the scenarios above, and was already reviewed.
- `recheckBlock` gets a flag that drops its closing paragraph (`agent-action.ts:289-290`) when a delta is shown, and keeps it word for word when none is. That keeps the fallback byte-identical to today's prompt, which the fallback Done-when test can assert as equal to `buildReviewPrompt` called without a delta.
- Keep everything in the recheck items, including the *"`failureScenario` the same quote as above"* rule (`agent-action.ts:274-275`). The exemption depends on that rule.

### The demotion

`reviewAnswer` (`agent-action.ts:745`) gets the delta's hunks and the recheck scenarios. The order after parsing matters:

1. **Recheck exemption first.** Compare each finding's `failureScenario` against `context.recheck` scenarios with an exact string comparison. Do not trim or normalise: the prompt asks for the quote verbatim, and a reworded one is a new finding. A match is exempt from **both** demotions, #670's `pre-existing — was` and this one's.
   - This is broader than the ticket's step (4), and it is on purpose. A finding that bought the round was above the bar, so it was inside the diff or carried `reachableBecause`. If the fixer then reverted lines so that it falls outside the whole diff and the reviewer leaves `reachableBecause` empty, #670 would demote a recheck. The Watch out row says never.
   - Split the list rather than threading an exemption set through `demoteOutsideDiff`. Run both demotions over the non-matches only, then merge the matches back in their original order. Order matters because `summarise` and `evidence` read the list in order.
2. **#670 over the whole diff**, unchanged: `demoteOutsideDiff(nonMatches, hunks)`.
3. **The delta demotion**, as a new `demoteOutsideFix(findings, deltaHunks)` in `diff-hunks.ts`:
   - It skips anything already `minor`. A finding #670 just demoted is minor now, so the two prefixes never stack.
   - It demotes anything for which `isInsideHunks(f, deltaHunks)` is false, with the claim prefix `outside the fix — was <severity>: `.
   - It does **not** have `demoteOutsideDiff`'s `reachableBecause` escape (`diff-hunks.ts:140`). The ticket's edge, citing epic decision 2, says it is still demoted.
   - Give the function its own idempotence guard on the prefix, as `demoteOutsideDiff` has.
4. `verdictFor` over the result, as today.

Leave `failureScenario` untouched in every demotion. A demoted finding that ends up on a later recheck list would otherwise fail to match its own quote. `demoteOutsideDiff`'s doc already gives that reason (`diff-hunks.ts:134-136`).

## Decisions the ticket left open, and the answers

- **Which findings are "the recheck"**: `context.recheck`, which is what the round was bought on. That is `findingsIn(steps.slice(lapStart))` at `pass.ts:1360`, and it includes build findings. A build finding's scenario will not match a review finding verbatim, so including it costs nothing.
- **`reviewedSha === onSha`**: no delta call is made, so there is no section and no demotion. This comes out of the one rule above with no special case.
- **The review session id** (`agent-action.ts:576`) is unchanged (#195).
- **0038 §2** (*the recheck carries the scenarios and nothing else of the review*) is untouched: the delta is a diff, not anything from the earlier review. Nothing here contradicts an accepted ADR, so no superseding file is needed.

## What tests stand in, all unit

- **`packages/actions/unit/`**:
  - `buildReviewPrompt` with and without a delta, including the *"exactly as you would have without this section"* sentence present or absent;
  - `createAgentAction` with a fake `deps.diff` that answers per `from`, or throws for the delta's `from`. Cover the fallback, the demotion with the new prefix, the recheck exemption outside the delta, and `reachableBecause` still demoted;
  - `demoteOutsideFix` on its own, beside the existing `diff-hunks` tests.
- **`packages/conductor/unit/`**, through `runPass` with a stub review action that records the `ActionContext` it is handed:
  - the first review gets no `reviewedSha`;
  - the review after a `FixRound` gets the earlier head;
  - the review after a `MergeBase` gets none;
  - an unreadable or never-ran review does not set it;
  - a continuation with `from.step: 'proposed'` that routes `MergeBase` gets `reviewedSha` equal to the approved `context.onSha`, together with `landedOnBase`.

  That last case is the Done-when's approval case at the level where it can be checked without git. The real X..Y diff is integration-only (`deps.diff` is git), so the unit test asserts the `from` that `deps.diff` was called with, not the diff's contents.

## Docs

`scripts/the-pass.py` is the source and `doc/the-pass.html` is generated from it. Change the review step's text to say that a review after a fix round reviews what the fix changed and rechecks the earlier scenarios. Regenerate the HTML rather than editing it.

## What would settle it in the log

A review step's own `StepEnded` for a second-round review should carry findings whose `claim` starts with `outside the fix — was`, and the run log note should show `fix delta`. Comparing the count of above-bar findings per round on `StepFailed` before and after this change is the measurement #669 is after.
