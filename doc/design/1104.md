# #1104 design note: the CLI's read side becomes Effects

The ticket gives the shape correctly. This note covers six places where the plain `await` → `yield*` translation builds something wrong, and states one decision for each. The preconditions hold at `08d6b70f`:

- The baseline reads `"apps/cli": { "async": 146, "run": 1 }`.
- `grep -c async` counts 6, 5, 2, 5, 2 and 3 in the six files. `day-ceiling.ts`'s fifth match is not one of the ticket's four, so count what the ratchet counts, not what grep counts.
- `status.ts:547` is the last caller of `project-pause.ts:60`'s `runEffect`. `add.ts:40` and `add-github.ts:35` import the other `runEffect`, from `first-project.ts`.

## 1. Every runner stays detached. This is the one that fails silently.

`createProjectionRunner` is `promiseRunner(makeRunner(options, { detached: true }))` (`packages/projector/src/projection.ts:376`), and the daemon's `defaultRunnerFor` passes `{ detached: true }` too (`packages/daemon/src/daemon.ts:162`). A non-detached port behaves differently, per `projection.ts:247-249`: *"Unless the caller is a promise face, which has no fiber to outlive, the fiber that started the runner owns it: a child watcher closes it when that fiber ends"* (`:271`).

So a plain `makeRunner({ projection })` in place of `createProjectionRunner({ projection })` type-checks and then breaks things:

- `holdLiveSpend`'s resume restarts the held `spend` and `ticket_report` runners. With this change, that runs inside `rebuildEstimates`, inside `refreshOnce`'s `Effect.runPromise` (`rate-snapshot.ts:140-142`).
- When that refresh returns, its fiber ends, and the follow fibers are closed with it.
- From then on `spend` stops following after every price change. Nothing is recorded, and it is the projection the ceiling guard reads (#650).

**Decision:** every `makeRunner` call this ticket adds, in `projector.ts`, `projection.ts`'s `runnerFor` callers (`cli.ts`, `rates.ts`) and anywhere else, passes `{ detached: true }`. The release closes each runner explicitly, as today. No unit test sees this, because a fake port has no follow fiber. So add one to `unit/rates.test.ts` or a sibling: a fake port that records `start()`/`stop()` and asserts that after `rebuildEstimates` completes, the held runner was restarted and never `stop()`ped or `close()`d by the rebuild.

## 2. `RatePorts`' Effects require nothing, and a failed `rebuild` is still a line in the note

- **No requirements.** `refreshOnce` runs `refreshRatesEffect` with a bare `Effect.runPromise` (`rate-snapshot.ts:141`), so `wanted` and `rebuild` must be `Effect<…, unknown, never>`. `loadProjectsEffect` (`packages/conductor/src/projects.ts:104`) is already `Effect<ProjectState[]>`. Use it and `currentRecipeEffect` (`:201`) in `modelsSeenInSpend` instead of the promise forms. Keep the per-recipe `try { … } catch {}` (`rates.ts:46-50`) as an `Effect.catchCause` that lets interruption through; a recipe that will not resolve still "names no model".
- **The rebuild failure.** Today `rebuilt = yield* Effect.tryPromise({ try: () => rebuild(priced), … }).pipe(Effect.catch(…))` (`rate-snapshot.ts:170-173`) turns a rejection into `rebuild failed: <message>`, with `ok: true` because *"The write stood, so this is not `ok: false`"*. Once `rebuild` is an Effect, a store failure inside it is a defect (0101 §6), and `Effect.catch` does not see defects. The defect would then reach the outer `catchCause` (`:183`) and write `ok: false`. That is a changed note, and it gives the wrong answer about a snapshot that was written. **Decision:** catch the yielded `rebuild` with `Effect.catchCause`, let interruption through, and use `rebuild failed: ${(Cause.squash(cause) as Error).message}`. In `rate-snapshot.test.ts`, a fake `rebuild` that fails and one that dies must both produce `ok: true, rebuilt: 'rebuild failed: …'`.

## 3. `rebuildUnderLock`: the refusals are outside `acquireUseRelease`

`projection.ts:131-153` has three exits before anything is held:

1. `acquire` throws: *"could not take the conductor lock (…) — nothing was rebuilt"*.
2. `!held.ok`: *"… holds the conductor lock and is the only writer of …"*.
3. The lock is held: rebuild, then release.

**Decision:** in an `Effect.gen`, run the acquire seam first, as `RebuildUnderLockOptions.acquire: (o) => Effect<LockResult, unknown>`. Handle its failure with `catchCause` (letting interruption through), print exit 1's sentence, and return 1. On `!held.ok`, print exit 2's sentence and return 1. Only then call `Effect.acquireUseRelease(Effect.succeed(held), () => rebuildProjection(options), (h) => h.lock.release())`. If `lock.release` is still a promise, lift it with `Effect.promise`; it is an Effect if CLI-13/14 already lifted `acquireDaemonLock`.

The real path (`acquireDaemonLock` + `createFileLocker`, `:134-136`) is wrapped once at the default. `NO_LOCKER` (`:103`) stays. `rebuildProjection` follows the same rule: the `logPredatesHoldEffect` guard runs before `runnerFor()` builds anything (#451, `:76-79`), then `acquireUseRelease(sync(runnerFor), rebuild + lag + line, (r) => r.close())`.

## 4. `rebuildEstimates`: the hold is settled in the release, after resume

`rates.ts:100-117` sets `mine.settled = true` in the `finally`, after `resume()`. `spendRebuildHold` (`:79`) depends on that: a rebuild that failed partway still shows *"not caught up after a rebuild"* until a lag of zero clears it. **Decision:** `acquireUseRelease(holdLiveSpend(), rebuild both, (resume) => resume.pipe(Effect.ensuring(Effect.sync(() => { mine.settled = true }))))`. Set `hold = mine` and `rebuildsBegun += 1` before the acquire, as today.

The two dynamic `import()`s (`:95-96`) avoid loading `projection.ts` and the store in the daemon until a price changes. Keep them as `Effect.promise(() => import(…))`, which the ratchet does not count as `async`.

## 5. `live-spend.ts`'s coordination keeps its rules, on Effect primitives

`starting`, `closing` and `standingDown` (`:14-31`) are what let a rebuild wait for runners that are starting or closing (#680). **Decision:**

- These become `Set<Deferred<void>>` and a `Deferred | null`.
- `holdLiveSpend` keeps its loop: *"Re-read both sets after every await"* (`:44-47`) becomes "after every `yield*`".
- `startLive(projection, port): Effect<void, unknown>` registers the port before `port.start()` and removes it from `liveSpend` on failure (`:74-89`).
- `releaseLive(port): Effect<void>` deletes the port, then runs `port.close()` and swallows its failure like today's `.catch(() => {})`.

The resume's per-runner `start().catch(() => {})` becomes `Effect.ignore`, and the resume must not fail. `DaemonOptions.onRunner` (`packages/daemon/src/daemon.ts:75`) takes the `port`. The `promiseRunner` face at `:292` goes, and `:319` hands over `port`. The comment at `:290-291`, *"One face per port … a caller that keeps runners in a set looks them up by identity"*, becomes a remark about the port.

## 6. Smaller mismatches between the ticket and this tree

- **`processLogEffect` is not exported.** It is a private `const` at `packages/event-store/src/choose.ts:87`. Export it, plus from `index.ts:28` beside `processLog`. That is how `projector.ts`'s `defaultPredatesHold` becomes `Effect.flatMap(processLogEffect(), (l) => logPredatesHoldEffect(l.queries))`.
- **`Layer.scoped` does not exist in this codebase.** It appears only in comments (`projector.ts:101`, `conductor/src/live.ts:64`). `ProjectorLive` stays `Layer.effect(Projector, Effect.acquireRelease(…))`, which is scoped already. What changes is that both `Effect.promise(async …)` bodies become `Effect.gen`.
- **`ProjectorLive`'s guard catch.** The `try`/`catch` around `defaultPredatesHold` (`:115-122`) logs and carries on. Make it `catchCause` that lets interruption through, with the same two lines.
- **The dedupe stays a promise.** `startRates` (`rates.ts:131-134`) stays synchronous and keeps `refreshRates`' promise. It passes `modelsSeenInSpend` and `rebuildEstimates` as the Effect-returning ports.

## Edges this note decides

- **Interruption mid-refresh.** The daemon's drain reaches `ratesSettled()`, not the refresh's fiber, so this is not expected. If it happens anyway, decision 4's release still runs resume and settles the hold. Decision 1 is what keeps the restarted runners alive after the fiber ends.
- **What only the integration half sees.** Whether a real `spend` runner keeps following after a real price refresh sits behind the 803-second integration half. The unit-level stand-in is decision 1's start/stop/close-recording fake. The log that settles it later: after a `rates` refresh writes a note with `priced`, the `spend` projection's lag returns to zero as later `RunCompleted`-style events arrive. A daemon whose `spend` lag only grows after that note points to decision 1 being missed.
