# Design note: #726, Ctrl+C and `lingtai board stop` end a board within 2 s

## Where it goes

All of the change is in `apps/cli/src/board.ts`. Outside it, only the two callers change: they now pass `release`.

1. **A pure handler factory, exported for the unit test.** Put it beside `serveBoard`, for example `stopOnSignal({ release, exit, say })`. It returns a `(signal: 'SIGINT' | 'SIGTERM') => void`.
   - It holds a `stopping` flag in its closure.
   - **First call:** set `stopping`, `say` one line naming the board and the signal, `await release()` inside a `try`, then `exit(signal === 'SIGINT' ? 130 : 143)`.
   - **Any later call:** `exit` at once with that same code, without awaiting anything.
   - **The `release` is capped.** Race it against a timer of about 1 s, so a release that hangs cannot break the 2 s budget. The kernel drops the `fcntl` lock when the process dies anyway (`packages/env/src/lock.ts:25`: "the kernel drops it when…").
   - A `release` that throws falls through to `exit` with the same code.
   - The test drives this function and nothing else, as the ticket's *Done when* lists. No real signal, no `process`.

2. **`serveBoard(options)` gains `options.release: () => Promise<void>`** (`BoardOptions`, `board.ts:~93`).
   - The order inside it becomes:
     1. `portIsFree`
     2. set `PORT`, `HOSTNAME` and `NEXT_MANUAL_SIG_HANDLE='1'`
     3. `importFile`
     4. `await listening(...)`
     5. `delete process.env.NEXT_MANUAL_SIG_HANDLE`
     6. install the handler
   - **Install the handler after `listening` resolves, not before the import.** That is the decision the ticket does not spell out.
   - If `listening` or the import rejects, both callers already release the lock themselves: `board.ts:466-470` and `init.ts:1073-1076`. A handler installed earlier would stay on the process with a lock that is already released.
   - Between the import and `listening`, the variable means Next has no listener, and the CLI has none yet either. So Node's default applies: SIGINT or SIGTERM terminates the process, and the kernel drops the lock. That is correct for a board that is not up yet, and it needs no code.
   - Install it with `process.on('SIGINT', …)` and `process.on('SIGTERM', …)`, guarded by a module-scope `let signalsInstalled = false`, so a second `serveBoard` in one process adds nothing.
   - In the live handler, `exit` is `process.exit` and `say` writes to `process.stderr`.
   - The `serveBoard` doc comment (`board.ts:99-112`) gains one paragraph. It explains why the variable is set before the import: `start-server.js:387` reads it inside `startServer`, which `server.js` does not await. It also explains why the variable is deleted after `listening`: it would otherwise reach children such as git, agents, or a managed project's own `next`.

3. **Callers.**
   - `board start` (`board.ts:465`) passes `release: async () => { await held?.release(); held = null }` through `world.serve`. The type of `BoardWorld.serve` follows, and `board-world.ts:53` stays `serve: serveBoard`.
   - `init` (`init.ts:1072`) passes the same thing over `kept`.
   - The unit fakes (`apps/cli/unit/board.test.ts:68`, `serve: async () => {}`) only need their parameter type to accept the new field.

## Init's other SIGINT listener

`github-auth.ts:189-196` adds `process.on('SIGINT', ignore)` while it hands the terminal to `gh`. The comment there says why: "init ignores its own copy and comes back to the choice (0121 §10)".

That works only because no other SIGINT listener exits the process. Today the two do not overlap:

- The board is started only from `boardUrl()` on the App branch (`first-project.ts:684`, `init.ts:551`).
- The `gh` handoff is the other answer to the same question (`github-auth.ts:184`).

So within one run of `init`, the board is never serving while `gh` holds the terminal. Do not add code for this.

Do put one sentence in the handler's doc saying it exits the process for every SIGINT. Any later code path that serves the board and then hands the terminal to a child must deal with that, and today none does. (Before this change, Next's `cleanup` was already on SIGINT in that position, so this is not a new hazard.)

## Comment that becomes true

`board-world.ts:64-65`: "SIGTERM is the stop, and a board installs no handler that could swallow it." After this change the board does install a handler, so tighten the wording to match: it installs one, and that handler exits. Do not delete the comment.

## What can be checked where

- **Unit (`pnpm test`):** the handler's three cases from *Done when*.
- **Not checkable at unit level:** that the variable is set before the import, and that Next then installs nothing. `importFile`, `portIsFree` and `listening` all touch the real file system and network, so a unit test cannot reach them. Do not add a seam just for this.
- **What stands in:** the manual check in *Done when*. Run `curl -sN http://127.0.0.1:<port>/api/stream`, then press Ctrl+C. It must end within 2 s with exit status 130. Then run `lingtai board stop` from another terminal; it must print "stopped the board on <port>".
- **Optional extra check for the person verifying:** while the board is up, `process.listenerCount('SIGINT')` should be exactly 1.
