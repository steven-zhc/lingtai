## 1. A refused `onWait` must still release the lane

Today, when `onWait` throws, `through` still waits for `before.done` in a `finally`. The outer `finally` then releases its own tail, and the rejection propagates without `land` running (`landing-lane.ts:46-58`). The comment there says why: *"A refused append must not strand the callers queued behind us, and must not let us land beside the holder either."*

`Effect.acquireUseRelease` does not run `release` when `acquire` fails. If the new acquire is written as *register tail → `onWait` → await predecessor* and `onWait` fails, the tail stays registered forever and every later landing on that integration stream hangs. This is the same wedge the uninterruptible acquire exists to prevent, reached by a different path.

Write the acquire so it settles its own failure:
- Register the tail synchronously in `Effect.sync`. `done` is a `Deferred<void>`.
- Run `onWait` with the predecessor's await attached as `Effect.ensuring`.
- If `onWait` failed, complete your own `done`, remove the tail if it is still yours (`Effect.onError`), and only then fail.

The finalizer handles only the granted case: clear `holding` if it holds this holder, complete `done`, and drop the tail if it is still this one.

`onWait` is `appendNow` (`conduct.ts:779`, an `async` promise), lifted with `Effect.promise` as the ticket does for `take`'s reads. A refused append becomes a defect in `through`, which fails `merge:`'s action, as a rejection does now. `landing-lane.test.ts`'s existing *refused append* case (`:50-62`) keeps that guarantee, written over Effects.

## 2. Where the `take` region begins and ends

The uninterruptible region starts at the `claimTicket` / `continueTicket` call (`:2512-2525`) and ends at the assignment at `:2581`. It covers the `catch` path's `onStream = ticketId` (`:2533`) and the split-done path's `closeHolding`, `editEndedWaits` and two `tellGitHub` calls (`:2538-2575`).

It does **not** cover:
- `runnableNow` and `getIssue` before it. They hold nothing, so an interrupt there releases nothing (`release`'s `onStream === null` branch, `:1488`).
- `openTheRunLog` and `tellGitHubAbout` after it. Once `onStream` is set, an interrupt there reaches `release` through the existing `Effect.ensuring(release('the run was interrupted'))` (`:5131`), which is the guarantee the region exists to reach.

Write it as `Effect.uninterruptible(Effect.gen(…))` that returns either the claim or the early answer. Do not wrap the whole `take`.

## 3. How the two interruption tests are built

**`Fiber.interrupt` waits for the fiber to finish.** In both tests the fiber is blocked on a `Deferred` that only the test completes. Awaiting the interrupt directly would deadlock the test, which then fails only by vitest timeout, and the *Done when* rules out timers. So fork the interrupt and keep its fiber, using `Effect.forkChild(Fiber.interrupt(f))` (the house form is at `attempt-steps.test.ts:2539`). Then:

- **The claim test:** complete the gate, join the interrupter, then assert.
- **The lane's "holder interrupted during `land`" case:** assert that the third has not been granted, complete the holder's `Deferred`, join the interrupter, then assert the grant.

**The claim test** goes through `runOnce` (`conduct.ts:721`, an Effect), forked. `claimTicket` is imported, not injected, so the seam is the store:
- Wrap the memory store that `conduct-a-whole-attempt.test.ts` already uses so that the append carrying `TicketClaimed` waits on a `Deferred` before it commits.
- Fork the pass, wait until that append has been reached (a second `Deferred` it completes), fork the interrupt, then complete the gate.
- Assert that the ticket stream ends with `TicketReleased` and the reason `the run was interrupted`.
- Put it in a new file under `packages/conductor/unit/`. *Done when* allows new tests and forbids edits to existing ones outside the three it names.
