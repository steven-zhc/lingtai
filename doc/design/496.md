## Design: one `RunSpent` per discussion process (#496)

### Where it goes: `holdDiscussion`, not `discussionAsk`

The ticket's Fix row names `apps/cli/src/discuss.ts:247` (`discussionAsk`), but the append belongs in `packages/conductor/src/discuss.ts`'s `holdDiscussion`, in the round loop beside `spend(outcome)` (`:553`). Three things in the code decide this:

1. **Only the loop can tell a returned outcome from a made-up one.** At `:546` the loop calls `ports.ask(...)`, and its `.catch` fills in an `Answered` (`turns: 0, durationMs: 0, costUsd: null, failure: { kind: 'crash' }`) when the call throws. 0110 §2 says *"a process killed before it returned anything … has nothing to record, and records nothing"*. That made-up outcome must not become a `RunSpent`. Do what `conduct.ts:2301–2309` does for the judge: set `threw = true` inside the `.catch` and append only when `!threw`. Its comment explains why: *"the `.catch` above makes up a `RunOutcome` so the rest of this function can read one, and `RunSpent.turns`/`.costUsd` may never be invented numbers"*.
2. **The loop already has the stream and the store.** `stream = chatStream(options.chatId)` (`:489`) is the `chat-…` stream that 0110 §8 names: *"A discussion is on its `chat-…` stream"*. `discussionAsk` has neither.
3. **The unit test the ticket asks for drives `holdDiscussion` with a fake `ask`.** That is how `packages/conductor/unit/discuss.test.ts:244` and the others work. A `RunSpent` written inside `discussionAsk` would only be visible to a test that runs a real `Runtime`.

`discussionAsk` and `apps/cli/src/discuss.ts` change in one place only: the new option described below.

### What each one carries

- **`for`:** `{ _tag: 'Discussion' }` (`packages/domain/src/events.ts:695`). It has no round field, so the `RunSpent`s of one question are told apart by their order on the stream, which is all 0110 §9 gives a discussion.
- **`turns`, `durationMs`, `costUsd`:** copied from that round's `Answered` as they are. `costUsd` stays `null` when the runtime said nothing, never `0` (0110 §4).
- **`usage`:** `outcome.usage ?? []`. `RunSpent.usage` is required, while `Answered.usage` is optional (`discuss.ts:91`). This is the same coercion `runSpentFrom` makes at `conduct.ts:2158`.
- **`runtime`:** `RunSpent.runtime: RuntimeId` is required (`events.ts:715`), and nothing in this file knows it today. `Answered` has no runtime field, and its docstring (`:74–80`) says it deliberately keeps `@lingtai/agent` out of this module, because the board imports it.
  - **Decision: add a required `runtime: RuntimeId` to `HoldOptions`.** Import `RuntimeId` from `@lingtai/domain`, which this file already imports from (`:63`); it adds no new dependency. The CLI passes `discuss.agent` (`apps/cli/src/discuss.ts:308`, the same value given to `createRuntime`). `DiscussAgent` is a subset of `RuntimeId`, so it type-checks.
  - Make it required, not optional with a default. `HoldOptions.call`'s own comment (`:457–463`) explains why: *"an optional field with a silent default is exactly the failure this ticket exists to remove"*.
- **`actor`:** `'conductor'`, the same as the other `RunSpent` writer (`conduct.ts:2151`). It is the system recording a bill, not the assistant speaking. That is why it is not `agent:${chatId}`, the actor `DiscussionAnswered` uses.

Build the payload through `parsePayload('RunSpent', …)`, as `conduct.ts` does. Widen the private `append` helper's `type` union (`:797`) to include `'RunSpent'` and reuse it with `at = -1`. The re-read of the stream's length (`:787–791`) applies here too: minutes of agent time pass between appends.

### Order on the stream

A question that takes three processes now reads:

`DiscussionAsked`, `RunSpent`, `RunSpent`, `RunSpent`, `DiscussionAnswered`

Each `RunSpent` is appended right after its `ask` returns, before `parseReply` or any `answer(...)`. That way a failing round still records its spend before the early `return` at `:563`.

Leave `spend(outcome)` and the sums on `DiscussionAnswered` as they are. Its `turns`, `durationMs`, `costUsd` and `usage` stay the sum over every round. That includes a thrown round, which today adds zeros and still will. `DiscussionHeld` is untouched, and so are `spendOf` and `usageOf`. **Neither of them may start reading `RunSpent`.** 0110 §13 says *"every reader reads exactly one of the two … No reader adds the two, so a dollar is never counted twice."*

### Readers of `chat-…` that see a new event type

Every reader I found filters by type, so none of them changes behaviour:

- `turnsOf` (`:755`), `outstanding` (`:779`), and `answerOutstanding`'s count of answers (`apps/cli/src/discuss.ts:442`).
- The board's `foldChat` (`apps/board/src/lib/task.ts:847–860`).
- `history.ts`'s `FORMAT`, which is a `Partial<Record<…>>` (`apps/board/src/lib/history.ts:139`), so a type it has no entry for falls to its default.

**One thing does shift, and it is harmless.** The CLI's per-round run id is `` `${chatId}:${chat stream length}:${round}` `` (`apps/cli/src/discuss.ts:383–384`), so the length now grows between rounds. The ids stay unique:

- Within one question, `round` differs.
- A later question starts at a strictly greater length with `round = 0`, and every earlier question used a smaller length.

Do not "fix" this by reading the length once.

### Tests

- **Existing tests in `packages/conductor/unit/discuss.test.ts`:**
  - Line `:258` asserts `store.types()` equals `['DiscussionAsked', 'DiscussionAnswered']`. It becomes `['DiscussionAsked', 'RunSpent', 'DiscussionAnswered']`.
  - `store.appended[1]` at `:260`, `:302`, `:345`, `:366` and `:387` stops being the answer. Find the answer by type rather than moving the index to 2, so the next change does not break them again.
  - Every `holdDiscussion` call needs `runtime: 'claude-code'`.
- **Integration callers:** `packages/conductor/integration/discuss.test.ts` also calls `holdDiscussion`. It needs the new field for `pnpm typecheck`, even though that half is not run.
- **The new test:** a fake `ask` that answers `read` on rounds 0 and 1 and `answer` on round 2, with distinct `turns`, `costUsd` and `usage` per round, and one round whose `costUsd` is `null`. Assert:
  - three `RunSpent`s on the chat stream, each carrying its own round's figures, with `for: { _tag: 'Discussion' }` and the `runtime` passed in;
  - `DiscussionAnswered` still carries the sum, as today.
- **A second test for the killed process:** an `ask` that throws appends no `RunSpent`, and still appends `DiscussionAnswered` with its failure. Pair it with a returned `failure` (for example `timeout` with `costUsd: 0.42`, as in the existing test at `:237`), which *does* append one.

Everything here is checkable by `pnpm test`; nothing turns on the integration half.
