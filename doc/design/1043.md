### Where things stand in this worktree

Both blocking tickets have landed, so the pieces the ticket calls "the pipeline ticket's pattern" exist and can be used:

- `ActionPort` is at `packages/actions/src/action.ts:804`, `promiseAction` at `:828` and `fromPromiseAction` at `:845`.
- Every kind except the agent has its `make…` and its `…PortDepsFrom`: `makeProcessAction` (`process-action.ts:52`), `makeKeptRunAction(name, inner: ActionPort, deps)` (`kept-run-action.ts:87`), `makeWorkAction` (`work-action.ts:146`), `workPortDepsFrom` (`:216`), `keptRunPortDepsFrom` (`kept-run-action.ts:156`), and the others in their files.
- The baseline reads `"packages/actions": { "async": 2, "run": 0 }` (`effect-ratchet.baseline.json:8`). The two counted are `agent-action.ts:678` and `:1407`, and nothing else in `src/` is counted.

### 1. Lift with `liftPromise`, not a bare `Effect.promise`

`liftPromise` (`action.ts:818`) is the package's lift. Its doc says it *"Runs a promise-shaped thunk as an Effect whose rejection — or synchronous throw — is a defect that is the thrown value itself."*

- `agentPortDepsFrom` lifts `issue`, `diff`, `landed` and `restore` through it, the way `keptRunPortDepsFrom` does at `kept-run-action.ts:156-159`.
- Keep the defect equal to the thrown value. The review's combined messages (`agent-action.ts:823-828`) read `errorMessage(thrown.error)`, and a wrapper would change their text.
- The dispatch is the one place that needs `Effect.promise`'s own `signal`. Write it with the same body as `liftPromise`: `Effect.promise((signal) => new Promise((resolve) => resolve(runtime.run({...request, signal: combined}))))`. That way a synchronous throw from an adapter is still a defect carrying the thrown value.
- Combine the two signals with `AbortSignal.any([context.signal, signal])`, leaving out `context.signal` when it is absent (`action.ts:606` declares it `signal?: AbortSignal`). The repo requires Node ≥26 (`package.json:10`).
- Lift `runtimeVersionOf` with `liftPromise` too. It never rejects (`packages/agent/src/runtime.ts:284`, *"Never rejects; `null` when it cannot be read or asked"*).

### 2. The trap the ticket does not name: the review's fix-delta read is soft

The fix-delta read is at `agent-action.ts:744-764`:

```ts
try {
  const got = readOf(await deps.diff(context.reviewedSha))
  …
} catch (error) {
  context.log?.note('review', `the fix delta could not be read (${errorMessage(error)}); this is a full review`)
}
```

`#671` decided that *"Anything unreadable falls back to a full review."*

If `deps.diff` is an Effect whose rejection is a defect, a plain `yield*` inside a JS `try` catches nothing. A rejected delta read would then fail the whole review as `the <name> action threw: …` instead of falling back.

So:

- Wrap the delta read in `Effect.exit`. Put `readOf`, `hunksOf` and the delta construction inside it too, because their synchronous throws are inside today's `try`.
- On any non-success `Exit`, write the same note with `errorMessage(Cause.squash(cause))`.
- The `context.log?.note` text must not change.

The first `deps.diff()` at `:682` is **not** soft today: a rejection there is a thrown review. Keep it a plain `yield*`.

### 3. The review's dispatch region and the restore

**What the `Exit` covers.** Today the `try` at `:776-810` covers `composePrompt`, `context.prompted`, `runtimeVersionOf` and `deps.runtime.run`. The `Effect.exit` must cover the same four, because a throw from any of them reaches the restore today.

**Restore on success or defect.** This is today's code with `yield*`: on a defect, the thrown error is the squashed cause, and the three outcomes at `:819-834` stay word for word.

**A restore that rejects.** Today `await deps.restore` simply propagates that rejection and drops any earlier throw. Under the lift it becomes a defect with the same value, which is today's behaviour. Do not add combining here.

**Restore on interruption.** `Effect.exit` does not catch the fiber's own interruption, so the code after it never runs when the fiber is interrupted. Put an `Effect.onInterrupt` finalizer on the dispatch region. The finalizer:

- calls `deps.restore(context.onSha)` once;
- writes `restored.restored` or the `failed` sentence to the log as `:820-826` do;
- **swallows** a failed or rejected restore, because a finalizer that dies adds a second cause to an interruption nobody reads;
- then the interruption continues.

That gives exactly one `restore` per review on every path, which is what the Done-when test counts.

Do not use `acquireUseRelease` with the restore as the release. A release cannot turn a failed restore into the thrown `Error` at `:823-828`, and the ticket keeps that `Error`.

**The draft.** It has no restore and no `try`, so `makeDraftAction` is a straight `await` → `yield*`.

### 4. `from-recipe.ts`: one mapping, over ports

**Two corrections to the ticket's evidence:**

- `dispatchDeps` already carries `landed` (`from-recipe.ts:232`). The "drops `landed`" bug in Out of scope is not present at this commit. Keep exactly the keys there today.
- The `run:` branch at `implement` wraps an `Action` today: `createKeptRunAction(action.name, inner, deps.keptRun)` at `:286`. Its port form is `makeKeptRunAction(action.name, makeProcessAction({...}), deps.keptRun)`, where `deps.keptRun` is already a `KeptRunPortDeps`. It does **not** go through `fromPromiseAction`.

**`ActionPortDeps`**

- Every key of `ActionDeps` (`:40-150`) appears with the matching port deps type.
- `runtimeFor` and `env` are unchanged.
- `agent?: AgentPortDeps`.
- Each key's doc comment stays on `ActionDeps`. `ActionPortDeps` points to it rather than copying the text.

**`actionPortDepsFrom(deps)`**

- Lifts each **present** key and leaves absent ones absent. An absent key is what makes `actionPortsFromRecipe` throw `ActionUnavailableError` by name, and `step-matrix.test.ts` builds over partial deps.
- Never write `{ ...deps }`. Name each key, as `dispatchDeps` does at `:226` (*"Every key of `AgentActionDeps`, optional ones included, must be written here"*).
- Give the result a mapped type over `Required<ActionDeps>` so that adding a key fails to compile here.

**`agentPortDepsFrom(deps)`**

- Uses the same mapped-type trick over `Required<AgentActionDeps>`.
- `settingsPath` and `limits` are `get` accessors that delegate to `deps`.
- `landed` becomes `deps.landed === undefined ? undefined : (moved) => liftPromise(() => deps.landed!(moved))`. The reader at `:739` tests `deps.landed === undefined`, so an absent `landed` must stay `undefined`, not become a function.

**`dispatchDeps`**

It becomes `(deps: ActionPortDeps & { agent: AgentPortDeps }, action) => AgentPortDeps`, with the same body and the same comment (`:197-219`). The getters at `:233-243` stay getters.

**`actionsFromRecipe`**

It becomes `actionPortsFromRecipe(step, actions, actionPortDepsFrom(deps)).map(promiseAction)`, with its default `deps = {}` kept. The long comment block on it (`:170-196`) moves to `actionPortsFromRecipe`, because that is where the branches now live.

### 6. Tests

**Interruption test** (`packages/actions/unit/agent-action.test.ts`)

- Fake runtime: its `run` returns `new Promise(() => {})` and records whether `request.signal` aborted.
- Fake deps: a non-empty `diff`, and a `restore` spy.
- `Effect.runFork(makeAgentAction(spec, agentPortDepsFrom(deps)).run(context))`, then wait until the fake's `run` has been called, then `Fiber.interrupt`.
- Assert:
  - `restore` was called once, with `onSha`;
  - the signal is aborted;
  - the exit is an interruption.

**Getter test** (`from-recipe.test.ts`)

- Build over deps whose `settingsPath` getter reads a variable, and change the variable after the build.
- Run through both `actionPortsFromRecipe` and `actionsFromRecipe`.
- Assert the fake runtime received the new path.

**The unchanged suites**

`agent-action.test.ts`, `from-recipe.test.ts`, `step-matrix.test.ts` and `trace-an-attempt.test.ts` must stay green with no edits. A failure there means a lift spread a getter, or a defect changed its message.

**Fix-delta test**

Add a unit test in which the second `diff(reviewedSha)` rejects and the review still dispatches. It pins §2, which nothing currently pins under Effect.

Everything above can be checked in the unit half (`HOME=/nonexistent pnpm test`, `pnpm typecheck`). None of it depends on `pnpm test:integration`.
