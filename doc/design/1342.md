# Design: ⌘K finds PRs by number (#1342)

## Where it goes

Three files change, and one shared helper moves.

- **`apps/board/src/lib/search.ts`**: the index, the ranking and the fuzzy function. It stays type-import-only.
- **`apps/board/src/lib/prs.ts`**: one new server-side Effect that reads a project's PRs and turns them into what the index needs.
- **`apps/board/src/app/api/search/route.ts`**: it calls that Effect once per registered project, inside the existing `Promise.all`.
- **`apps/board/src/lib/pr-board.ts`**: gains `prHolding`. It is moved out of `holderOf` in `task.ts`, not written a second time.

## 1. `search.ts` cannot shape a PR, so the server hands it plain data

`search.ts` "may import types only" (`search.ts:5-8`). That rules out importing `prName` (`pr-board.ts:133`), `isOpen`, or anything else that reads a `PrState`.

The test checks this with `/^import (?!type)[^\n]*?from/` (`unit/palette.test.tsx:127`). So imports must be written **`import type { … } from`**. The inline form `import { type X } from` also fails that regex.

So `buildIndex` never sees a `PrState`. `search.ts` declares this type:

```ts
export interface SearchPr {
  project: string
  n: number               // Lingtai's id: the href, and `pr <n>` before a host number exists
  host: number | null     // the code host's number; `#<n>` names only this
  name: string            // prName(pr): `PR #88`, or `PR 7`
  title: string | null    // pr.summary?.title (#1318); null before the summary
  branch: string | null   // pr.prBranch
  status: PrStatus        // import type from @lingtai/domain
  tickets: string[]       // pr.tickets[].ticket ∪ pr.fixesLanded[].ticket: the PR's keys
  holding: string[]       // the tickets this PR holds *now*: drives the ticket's "in PR"
}
```

`buildIndex` takes a new input: `prs: ReadonlyMap<string, readonly SearchPr[] | Error>`. It is optional, so the existing tests compile unchanged.

`PR_WORD: Record<PrStatus, string>` sits beside `TICKET_WORD` (`search.ts:49`), for the same reason: a new status is a type error, never the raw enum. The words:

| status | word |
|---|---|
| `requested` | requested |
| `in-progress` | in progress |
| `waiting` | waiting on you |
| `in-review` | in review |
| `refused` | refused |
| `merged` | merged |
| `closed` | closed |

`PrStatus` is at `packages/domain/src/pr.ts:16`.

Ticket ids line up with no translation. A PR's ticket is the issue number as a string: `readDraftOf` hands cards in as `{ issue: c.issue }` (`prs.ts:104`), and `holderOf` compares `t.ticket === ticket` (`task.ts:911`). So `holding` is matched against `TaskCard.issue` per project.

## 2. "In PR" uses the store's rule, so the search and the task page agree

A PR's `tickets` is not the same as the tickets it holds. `holderOf` (`task.ts:906-928`) says *"a closed PR gives its tickets back; a merge holds what its commit held"*:

- an open PR that holds the ticket wins;
- otherwise a merged PR with the ticket in `mergedTickets`;
- otherwise a merged PR with `!mergedExact` that holds it.

A naive `pr.tickets.includes(issue)` would label a ticket *in PR #12* after #12 was closed and the ticket went back to the draft.

So: take those three cases out of `holderOf` as `prHolding(ticket, prs: PrState[]): PrState | null` in `pr-board.ts`. That file is pure and already imports `isOpen`. Then `holderOf` calls `prHolding` first.

The route fills each `SearchPr.holding` from `prHolding`. **The draft is not read.** `readDraftOf` costs a `readTasksEffect` plus `readPrDraft` per project (`prs.ts:97-110`). A ticket in the draft is in no PR, so the search says nothing about it.

## 3. The read: `readSearchPrs(project)` in `prs.ts`

It is shaped like `readOnBranch` (`prs.ts:425-440`):

1. `readProject`, then `currentRecipe`, then `modeOf(recipe) !== 'team'` → `'solo'`. Nothing is read for a solo project.
2. Otherwise `readProjectPrs(project, eventStore)`. Use no `since` option: every PR, because a merged PR must stay findable.

Failures:

- **A failed recipe read or a failed `readProjectPrs`** returns an `Error`. `buildIndex` says `PRs could not be read for <project>: <reason>`. This differs from `readOnBranch`, which swallows the failure as `none`. Here "no PRs" and "could not tell" must not look the same.
- **One unreadable stream** (`{ n, error }`, `prs.ts:66-69`) leaves the other PRs listed. It adds `PR <n> of <project> could not be read` to the list of problems. The tickets that stream may hold go without *in PR*.

The route calls `Effect.runPromise(readSearchPrs(p)).catch(asError)` for each registered name, from `loadProjects`, inside the existing `Promise.all` (`route.ts:27`). Names that appear only in the log are not read; they have no recipe.

`apps/board` is not in `effect-ratchet.baseline.json`: the ratchet counts only `packages/*` and `apps/cli`. So this run adds nothing to the baseline, and the baseline must stay unchanged.

The route still never reaches the code host (`route.ts:1-4`). `readProjectPrs` reads the log only (`prs.ts:1-7`).

## 4. Ranking: rank 0 becomes an explicit field, and the query records how it was typed

Today rank 0 is the `keys[0] === issue` convention, applied to tickets only (`search.ts:118`). Replace it with an optional field on `Entry`:

```ts
number?: { value: string; hash: boolean }
```

| Entry | `value` | `hash` |
|---|---|---|
| ticket | `issue` | `true` |
| PR with a host number | host number | `true` |
| PR before a host number | `String(n)` | `false` |

Parse the query as `/^(#|pr\s*#?)?(\d+)$/i`. That gives `kind: 'bare' | 'hash' | 'pr'` and the digits.

Rank 0 applies when `e.number.value === digits` and one of these holds:

| query kind | tickets | PRs with a host number | PRs before a host number |
|---|---|---|---|
| bare (`88`) | yes | yes | no |
| hash (`#88`) | yes | yes | no |
| pr (`pr 88`) | no | yes | yes |

For `pr <n>`, tickets fall to the ordinary rules over the whole query, which almost never match.

**Lingtai's `n` is not in a PR's `keys`.** Otherwise bare `7` would prefix-match `PR 7` at rank 1, and `#` means the code host's number (#1316). The PR's keys are:

- the host number, when there is one;
- the title;
- the branch;
- each held ticket written `#43`.

Written that way, `#43` prefix-matches the PR at rank 1, right behind ticket 43 at rank 0. Bare `43` matches it at rank 2.

`GROUPS` becomes `[…, 'Tickets', 'PRs']`, so the flat order is tickets first and then PRs. That satisfies "`pr 88` puts the PR first" only because tickets do not number-match `pr 88`. The test that holds this is "`pr 88`'s first result is the PR".

The PR entry itself:

- label: `<name> <title>`, or `<name>` alone when there is no title;
- detail: `<project> · <PR_WORD> · <k> tickets`, where k is the size of the `tickets` union;
- href: `/pr/<project>/<n>`, which is `apps/board/src/app/pr/[project]/[n]/page.tsx`.

## 5. Fuzzy is rank 3: on labels only, and never for a number

`fuzzy(q, label): { span, start } | null`, written in `search.ts`:

- remove the spaces from the query, lower-case both, and match the query as a subsequence of the label, greedily from the left;
- `start` is the first matched index, and `span` is the last matched index minus `start`.

It runs only when **the query is not a number query** (any of the three kinds) **and** has ≥ 3 characters other than spaces.

- Without the first condition, `pr88` is a subsequence of a label like `#12 prefer 88 rows`, and that ticket would show up ahead of the PR.
- Without the second, two letters would match most titles, as the ticket says.

`rank` returns `[rank, span, start]`, and ranks 0–2 carry `0, 0`. `search`'s sort (`search.ts:147`) compares rank, then span, then start, then index.

The greedy left match does not find the tightest span. A tighter window may start later, e.g. `s…shlf`. That is acceptable, and tests assert only the order of results, never a score.

## Edges this decides that the ticket left open

- **The recipe cannot be read** → the PR-read sentence above, not silence.
- **One PR stream unreadable** → that one PR's sentence. The others are listed, and tickets that PR might hold have no *in PR*.
- **A PR in the draft or already ended** → the PR entry is still listed under its state word. Its tickets get *in PR* only through `prHolding`.

## Checks that stand in for the visual

Everything above can be tested at unit level:

- `buildIndex` and `search` in `unit/palette.test.tsx`, with hand-built `SearchPr` values;
- `prHolding` beside `holderOf`'s existing tests.

`holderOf`'s behaviour must not change, so its existing tests must stay green untouched. Nothing here needs `pnpm test:integration`.
