# #317, round two: an unzoned date whose host reading has passed is read at its latest possible instant

Everything here is in `packages/conductor/src/never-started.ts` and `packages/conductor/unit/never-started.test.ts` on `agent/317` (`09f3574`). Line numbers below are that commit's. `conduct.ts:1048` keeps calling `standDown` with no `zone`. Don't make it pass one: the bug is in what the reader does when it has no zone, not in the caller.

## The decision: keep the host's reading when it is still ahead, and take the latest reading when it is not

The dated branch is `never-started.ts:188–205`. Today it reads the date in `inferredZone` (`:183`, `zoned?.[1] ?? zone ?? hostZone()`) and returns `null` once that instant has passed (`:203`, `:205`). Change it to this, applied **only when the sentence named no zone** (`zoned` undefined):

1. Read the date in `inferredZone`, exactly as now. If that instant is still ahead of `now`, return it. This keeps `America/Chicago` → `07:00Z` for the incident sentence, and it is the reading for the case the first round inferred: the Codex CLI runs on the conducting host and renders in its zone.
2. If it has passed, return **the latest instant that date and time can mean anywhere**: the naive UTC reading plus twelve hours, because −12:00 is the westernmost civil offset. Pass that through `within()` as usual. Compute it as `Date.UTC(...) + 12h` with a named constant. Don't use `wallClockOn("Etc/GMT+12", …)`: the POSIX sign is inverted (`Etc/GMT+12` *is* −12:00), and that is a mistake waiting for the next reader.
3. If even that latest reading has passed, the wall has lifted in every zone. Return `null` as today, so `readReset` gives `{ named }` and the backoff applies. That is right at that point, because nothing is left to wait for.

Run steps 1–2 inside the existing year loop (`:195`), per year, so that a yearless `Jan 2` read in December still reaches next year. A sentence that names its zone, which is every Claude form (`QUOTA` and `WEEKLY` both carry `(America/Chicago)`), never reaches step 2. That is why `#210`'s fixtures can't move.

**Why not the other option the ticket allows** (keep `null` and have the caller wait longer for *"named but unplaced"*). `{ named }` also covers `resets 25pm`, `Nowhere/Nothing` and `try again in 3 hours` (test `:281–287`). The caller would have to choose one longer wait for all of them, a duration nobody has a figure for. Step 2 produces a specific instant that is at most about a day late. The ticket's Watch out says that direction only idles.

**What this does not close, so say it in the comment.** If the host guess is wrong but its reading is *still in the future*, the pause still resumes early. Example: the host is east of whatever zone rendered the message, met well before the named time. Nothing in the sentence can detect that. It costs one pass, and the next `never-started` reads again. The bare-time branch (`:186`) is unchanged: `nextWallClock` already rolls forward and never answers `null` for a past time. No unzoned bare time has been seen from either runtime.

## The sentence must say it guessed

`standDown`'s docblock (`:286–288`) says the reason carries *"where the time came from"*. Step 2's instant is not simply *"read from the message itself"* (`:318`). Have `clockReset` report which reading it took. For example, `readReset`'s `{ at }` arm gains a flag (`Reset` type at `:104–110`). Then `standDown` gets a third phrase for `from`, along the lines of *read from the message, at the latest instant its unzoned date could mean, because this host's reading of it had already passed*. It must not contain *"it named no reset time"* or *"could not read"*. That keeps the fifth Done-when of #317 true for the new path.

## Tests

**The production-shaped test needs no `TZ`.** The first round's note was right that `process.env.TZ` is process-global and leaks across files in a worker, so don't set it. Instead, choose a `now` at which the named time has passed **in every zone a host could be in**:

- `parseResetAt(CODEX_USAGE, new Date("2026-09-30T13:00:00Z"))`, with **no third argument**, returns `2026-09-30T14:00:00.000Z`. `Sep 30 02:00` has passed by 13:00Z everywhere east of −12:00 (at −11:00 it equals `now`, and `within` refuses `<=`). So the host's reading is past on any real machine, and only step 2 can answer. Today this returns `null`: write it first and watch it fail.
- The same instant through `standDown` with no `zone`: `until` is `14:00Z`, not `13:00Z + backoff`. The reason has the new phrase and neither *"named no reset time"* nor *"could not read"*.
- The incident replayed off-host via the `zone` slot (the host stand-in): `"Asia/Tokyo"` and `"UTC"` at `CODEX_MET` both return `14:00Z`. That is the review's own reproduction, inverted. `"America/Chicago"` still returns `07:00Z` (the existing `:124` and `:252–265`).
- `[CODEX_USAGE, 2026-10-01T00:00:00Z]` in the named-but-not-read table (`:280`) stays, and it now pins step 3: past the latest reading, so the backoff applies.
- *"Still says no reset was named when none was"* (`:308–317`) already covers the no-time Done-when by name. Leave it.
