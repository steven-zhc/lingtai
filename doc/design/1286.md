## Shape: the Waiting column's empty card (#1286)

### Where it goes

Most of the code is new; the existing files change in only a few places:

1. **`apps/board/src/lib/handled-today.ts`** (new): a pure function from `Report['handled']` to the card's view-model. The rules are below.
2. **`apps/board/src/app/handled-card.tsx`** (new): `HandledCard`, a **synchronous** component that takes the view-model and renders the mock's second tab. Keep it synchronous so a unit test can render it to a string the way `apps/board/unit/visual-waiting.test.tsx:50` does.
3. **`page.tsx`**: a thin `async function HandledPart` reads the data, catches its own failure and renders either `HandledCard` or the empty note. `CardsPart`'s empty branch (`page.tsx:985-992`) calls it only for `col.id === 'waiting'`:
   ```tsx
   <Suspense key={`handled:${projectKey}`} fallback={<Skeleton shape="handled" count={1} />}>
     <div className="arrive"><HandledPart … /></div>
   </Suspense>
   ```
   Put `projectKey` in the key so a project switch remounts the card. That matches the comment at `page.tsx:1215-1217`: *"Fade on mount, never on render: the boundary is keyed by project."*
4. **`skeleton.tsx`**: add a `'handled'` shape sized like the card. It must carry no words: *"The shape is the whole placeholder: no words, for anyone (0111 §15)"* (`skeleton.tsx:21`).
5. **`globals.css`** and **`CountPart`**: the grey header (see below).

Unit tests cover only the view-model and `HandledCard`. The read goes to the database, so it is integration and out of scope.

### Reading today's figures

`report()` is not a getter; it is `report(input: ReportInput)` (`packages/conductor/src/report.ts:489`). It needs `window`, `project` and `kinds`, not just rows. Build the input the way `/report` does (`apps/board/src/app/report/page.tsx:77-91`):

- Take the window from `reportQuery({ window: 'today', project: only }, now)`. That is the parser `/report` uses (`lib/report.ts:56`: `first(params.window) === 'today' ? 'today' : '7d'`).
- Pass `currentReport(q.project, q.window.from)` (`lib/report.ts:140`), then `buildReport({ tickets, spend, window: q.window, project: q.project, kinds: null })`.

This makes "today" mean the same local day on the card, on the `+ n more kinds →` link and on `/report?window=today`. `dayKey` is local time (`report.ts:238`). Do not compute `startOfToday` by hand.

The links come from `reportHref` (`lib/report.ts:114`) plus `#handled`:
- `this week →` uses `reportHref(reportQuery({ project }, now))`. With no `window` parameter that is 7 days.
- `+ n more kinds →` uses `reportHref(todayQuery)`.

`/report` has no `handled` anchor yet; the panel is its own ticket. Link to it anyway.

**Cost:** `currentReport` reads the project's whole `ticket_report` table, because `readTicketReport` takes `project` and no `since` (`lib/report.ts:146`). That is acceptable because it runs only while the column is empty. Never start the read before the column is known to be empty.

### View-model rules

These are decided here; the ticket leaves them open.

- **solved** = Σ `handled.kinds[].system`.
- **needed you** = Σ `handled.kinds[].you`. `answeredBy` is *"`you` also while it is still open"* (`packages/domain/src/problems.ts:69`).
- **No problem today** means solved + needed you = 0. The part then returns `emptyNote(...)`, exactly as today.
  - If problems exist but solved = 0, the card still shows: *0*, *0% without you · n needed you*. The ticket falls back only when there were no problems.
- **Kinds:** those with `system > 0`, sorted by `system` descending, ties in `PROBLEM_KINDS` order. `handled.kinds` already arrives in that order (`report.ts:198`: *"Every kind of `PROBLEM_KINDS`, in its order, a zero included"*), so a stable sort is enough. Show the first four. The rest become *+ n more kinds · m problems*, where m = Σ of their `system`; omit the row when n = 0.
- **%** = round(100 · solved / (solved + you)). That gives *100% · 0 needed you* when nothing needed the person.
- **Tick strip:** draw it from the counts, never from `handled.latest`. `latest` is capped at eight (`report.ts:569`).

### When the card is not shown

The part shows `emptyNote(...)` in `p.empty` instead of the card if any of these holds:
- the read throws;
- `currency.ticketReport.error` is set;
- `currency.ticketReport.lag === null` (unknown).

A positive lag still shows the card. The table is always slightly behind while a daemon writes it, and the footer already reports currency. Never render a 0 for a failed read.

### Grey header at 0

The `<section>` and its class are rendered synchronously (`page.tsx:1193-1197`). The count arrives later in its own `Suspense` (`page.tsx:1200-1202`), so the section cannot be given a class from the count. Instead:

- `CountPart` (`page.tsx:899`) renders `<span className="ct zero">` when the length is 0.
- Add this rule after `.col.hot .col-h { color: var(--signal); }` (`globals.css:363`):
  ```css
  .col.hot:has(.col-h .ct.zero) .col-h { color: var(--muted); }
  ```
  `:has` is already used in the file, e.g. `globals.css:1352`.

Keep the `hot` class. It also sets the column's width and the count's type size (`globals.css:366-369`), and the column must not reflow at 0. While `CountPending` is showing, the header stays orange.

### Edges the ticket assumed, as the code has them

- **Pause and locks never win for this column.** `emptyNote` has no pause text for `waiting` (`lib/board.ts:588-590`), and `emptyHeld` returns false for every column but `running` (`lib/board.ts:654`: `if (column !== 'running') return false`). So the card shows whether or not the scope is paused. Do not add a pause check; the ticket's edge is already satisfied.
- **A wait opens:** the column has cards, so `CardsPart` never reaches the empty branch and the column is unchanged. That falls out of the branch structure.
- **Midnight:** the window is computed per render from `new Date()`.
- **Two conductors, retries:** nothing here writes, so they do not apply.
- **Effect ratchet:** `apps/board` is not one of the ratchet's packages (`packages/domain/unit/effect-ratchet.baseline.json`), so an `async` server component does not move the baseline.

What would settle the figures in practice is `ticket_report`'s `problems`, reduced from the routes, redos and `WaitResolved` events that `problemsOf` reads (`problems.ts:1-18`). Compare the card against `/report?window=today`; the two must agree because they share the window and `report()`.
