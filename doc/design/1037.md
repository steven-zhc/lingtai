# Design: #1037 — the home page draws a frame first, then each read streams into a boundary keyed by the project

The ticket's Fix covers the general approach. This note records what the ticket leaves open and the traps in the code as it stands. Line numbers are against `HEAD` 6d03591c.

## 1. Each read is its own promise; no part awaits a combined `view`

Today `Page` destructures `loadBoard`'s answer and builds every derived value inline. Almost every part needs several of them, but **not the same ones**. A single combined `view` promise (board + register + control + day + lags + locks) makes every part wait for the slowest read, so one slow read (the day's spend, the lags, the locks) holds the menu, the actions, the chip, the counts and the cards. That is the failure this ticket exists to remove.

Do this instead:

- `startReads(param)` starts each read once and returns them as separate promises: `board`, `registered`, `control`, `day` (after `board` and `control`), `lags` (after `board`). It runs inside `measure(…, { label: '/' })` so every `timed` lands in `/`'s timings (Fix 4); `measured` is the promise of that scope and only the timing meta awaits it.
- `locks = readProjectLocks()` is its own promise.
- The derivations are small synchronous functions of the answers they take (`shape(board, param)`, `lockShape(locks, only, registered)`). A part awaits **only** the promises it draws from: the menu rows take `board`, `registered`, `locks`; the actions take `board`, `registered`; the paused chip takes `control`; the headline takes `board`; the counts take `board`; the cards take `board`, `registered`, `control`, `locks`; the footer takes `board`, `day`, `lags`.

There is one `loadBoard(param)` call. A test that mocks `loadBoard` the way `unit/not-set-up.test.tsx:10-13` does can count it. `readProjectLocks`, `readRegistered` and `readControlOnce` are `cache()`d, but hand the parts the promise rather than relying on that.

## 2. `queue` waits for `board` and for nothing else

GitHub's half of Queued needs `board.askable` and `board.known`. Chaining it on `measured` makes it wait for the day's spend and the lags too, so the Queued count and cards stay loading while the other three columns are drawn.

So: `queue = reads.board.then((b) => measure(() => timed('board.queue', () => githubQueue(b.askable, b.known)), { label: '/ queue' })).then(([g]) => g)`.

The `.then` is registered in `Page`, outside `/`'s `AsyncLocalStorage` scope, and `measure` opens a scope of its own, so the GitHub timings land in the `/ queue` array and never in the `/` array that was serialised (the bug the old comment describes).

`<TimingMeta timings={…} />` moves into a part that awaits `measured`, under its own keyed boundary.

## 3. The boundary that will hold the switch is Live's own, not one on the page

`live.tsx:341` is an **unkeyed** `<Suspense>` around `Counted`, which reads `runnable` (`:310-321`). `runnable` comes from `queue` (`page.tsx:768-771`), so on every switch it is a new promise that waits on GitHub. Fix 3 moves `Live` outside every keyed boundary. If this inner boundary keeps no key, it is the boundary in the Watch-out row: its content is revealed, its key is unchanged, so the switch waits for GitHub.

Handle it like this:

- `Live` takes a `projectKey` prop.
- It keeps two boundaries, both with a key that contains `projectKey`:
  - **outer**, reading `code` and `near`. Fallback: the loading dot.
  - **inner**, today's `Counted`. Fallback: the dot without a count, as today.
- `useFollow()` (`live.tsx:125`) stays in `Live`'s own body, above both boundaries.

`Health` becomes a plain function that returns `<Live code={news()} near={…} runnable={…} projectKey={…} />`. It must not be `async`. An async component with no boundary above it blocks the shell.

`near` is `reads.day.then((d) => nearCeiling(d.day, d.ceilingUsd))`.

The two Queued boundaries that already exist (`page.tsx:852`, `:878`) can stay unkeyed. Each sits inside its column's new keyed boundary, which remounts on a switch.

**`Draining` (`page.tsx:787`, `draining.tsx:28`) is a read too.** It is an `async` server component with no boundary today. It goes into the rail's keyed boundary with the paused chip and the headline. Any unbounded async component left anywhere in the shell blocks the shell, keyed or not.

## 4. Keys: contain `projectKey`, but are unique among siblings

`key={projectKey}` on two `<Suspense>` siblings under the same parent is a duplicate-key warning. For example, the rail would have Live's boundary next to the chip and headline boundary. Use `key={`<part>:${projectKey}`}`, for example `rail:`, `count:`, `cards:` and `footer:`.

Put the rule in the one comment above `projectKey` that the ticket asks for: *a boundary around a read is keyed, and its key contains `projectKey`*. The key test checks for that, not for equality.

## 5. The bar: what the shell can draw, and the one-project case

**Brand and Report.** These links are `withProject(…, project)` (`bar.tsx:38`, `:60-66`), and today `project` is `only`. That depends on `filters` (`lib/board.ts:1723-1724`). The shell passes `param` instead. On a URL with no `project` and a single project, the links lose `?project=X`. They then go to `/`, which selects the same single project again (#993), so this needs no boundary.

**Recipe and Pause** (`bar.tsx:44-58`). Today both depend on `registered`, a boolean, and `pause`, a node. Give `Bar` an optional `actions?: ReactNode`. When it is given, it replaces the `project !== undefined && registered` branch. The home page passes a keyed boundary as `actions`, with no fallback. The report and recipe pages keep using `registered` and `pause` unchanged. The `.pacts` and `.vsep` markup moves into a small exported part so both paths draw the same thing.

**The filter.** `Projects` (`projects.tsx:38-110`) chooses between the *no project configured* link (`:65-71`) and `FilterMenu`. It needs `filters` to choose, and it builds `label` from `only` (`:74`). Split it like this:

- **`param` set:** the shell draws `FilterMenu` with the summary `param`. The menu's children are a keyed boundary that renders the rows. If `filters` turns out to be empty, the boundary renders the *no project configured* link as its only row.
- **No `param`:** the slot (summary and menu, `FilterSlot`) is one keyed boundary, and its fallback is a summary showing the pulse. This is the ticket's #993 edge.
- **The `+` (`AddProject`) is the shell's in both cases, outside every boundary.** It needs only `app`, so it is drawn before any read, and it stays available during loading. Never move it into `FilterSlot`.

`FilterMenu` is a client component that takes `children` (`filter-menu.tsx:14-36`). A server `<Suspense>` passed as children is fine. The `<details>` keeps its place in the tree, so the closed state from `:28-30` survives the switch.

## 6. A read that fails

There is no `error.tsx` or `loading.tsx` under `apps/board/src/app`. Today a rejection from `loadBoard` or `readControlOnce` throws out of `Page` before any byte is sent and reaches Next's error page.

After this change, the same rejection rejects the read's own promise. Every part throws inside its boundary, and with no error boundary the error still reaches Next's error page. That outcome is the same as today and is the intended one. `readControlOnce` stays uncaught on purpose (the comment at `page.tsx:639-642`, about #77).

**Do not add a `.catch` that turns a read into empty columns or an unpaused state.** The reads that already degrade keep their own degradation:

- `registered` falls back to `[]` (`:659`).
- `lags` falls back to `null` (`:665`).
- A failed locks read is the banner's row (`lock-banner.tsx:5-8`).
- A `null` day draws as unknown in the footer.

Adding `error.tsx` is not this ticket.

## 7. The ratchet does not count this app

`effect-ratchet.baseline.json` (`packages/domain/unit/effect-ratchet.baseline.json:1-11`) lists `apps/cli` and eight packages. `apps/board` is not one of them. New `async` server components here do not move it, and this change adds no IO; every read is an existing function. Make no edit to the baseline.

## 8. Testing it with what the unit half has

These are checked against `react-dom/server` 19.2.8 in this worktree:

- **`renderToStaticMarkup` draws every suspended boundary's fallback.** That includes a boundary whose promise has already resolved, and an `async` component inside a `<Suspense>`. So the shell test is `renderToStaticMarkup(await Page(…))`, the same as `not-set-up.test.tsx:54`. Every fallback, and every check that a fallback is the pulse rather than `$0`, an empty paused state or green, comes from that one render.
- **A test that asserts resolved content** cannot use `renderToStaticMarkup`. Use `prerender` from `react-dom/static`, which waits for every boundary.
- **Mock `./live.tsx` in any test that renders `Page`.** `Live` calls `useRouter` (`live.tsx:73`, `:126`) and throws outside the app router. That mock is also where the test asserting *`Live` is not inside a keyed boundary* can record its props, including `projectKey`.
- **The key test** can read `page.tsx` as source and walk each `<Suspense` opening tag. That is the same technique the closing `describe` of `not-set-up.test.tsx` uses on imports.

None of this needs the integration half.
