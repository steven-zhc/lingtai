# #1523 design note: the project list on #1522's runner

Line numbers are for this worktree at `65140870f`. Some of the ticket's `first-project.ts` lines have shifted since it was written (for example, *move the landing?* is now at `:898-908`).

## 1. #1522's runner does not fit the project list as written. Extend it; do not build a second one

`SetupQuestion` (`packages/setup/src/machine-list.ts:58-95`) was built for a file the list writes key by key:

- `inForce` is an Effect with no argument (`:68`).
- `write(answer, inForce)` writes a file itself and returns `{ wrote }` (`:47-51`, `:81`).
- `from` is `'environment' | 'file'` (`:35`, `:39`).
- The only context is `RunContext { draft: Recipe | null }` (`:53-56`).
- The only skip is `needed` → `deferred` (`:158-163`).

Project questions read earlier answers: the personal-branch default needs the login, the landing needs the mode, the judge needs the writer, and the trial needs the branch. Some project questions also have a skip rule or a forced answer. So the runner grows, in `machine-list.ts`, and the machine list moves onto the same shape. That move is mechanical: its four descriptors take a `ctx` argument they ignore.

- **`SetupQuestion<C>` and `Asker<C>` are generic over the context.** `inForce`, `systemDefault`, `fromFlags`, `validate`, `write` and the asker each receive `ctx`. The machine list's `C` is today's `RunContext`. Move the list type and the runner to a file of their own (`setup-list.ts`) that both lists import.
- **`applies?(ctx)`**: the question is not part of this run, and it is neither asked nor refused. Examples: reviewer-model after `--reviewer none`, landing in team mode, sandbox hosts with the sandbox off. This is separate from `needed`/`deferred`, which still means *run me once the recipe is final* (the token, `machine-list.ts:155-157`).
- **`fixed?(ctx)`**: an answer decided by what is already true. The question is not asked, and `write` runs with that answer. Examples: local forces `db` (`source.ts:131-140`), and a log with work items keeps its source (`source.ts:115-129`). A differing flag is refused by the descriptor's own text, as those lines do now.
- **`derive?(ctx)`**: an entry with no question. The runner calls `write` with what it returns and never calls an asker. It never appears as asked, so the ticket's order and same-questions tests see it as not asked (0125 §9: *"never reported as a question the person skipped"*).
- **`confirm: true`**: a confirmation entry, with no value in force.
  - `--defaults` makes the answer `yes`. With no terminal the entry is refused naming `--defaults`. With a terminal the asker asks.
  - A `no` is refused with the entry's own words, the ones at `recipe-flow.ts:474-479` and `first-project.ts:984-989`.
  - *Make the personal branch?* and *move the landing?* are each a confirm entry declared right after the descriptor that owns it. Their `applies` reads that descriptor's answer: the branch does not exist, or this is a move. Do not ask a confirmation from inside a `write`: the no-terminal path never calls an asker (`machine-list.ts:209-215`), so a confirmation asked inside `write` would go unasked without a terminal.
- **`write` may return `{ refused }`.** The runner stops on it as it does on a `validate` refusal. `leftoverRefusal` needs this (§5).
- **The defaults can switch on partway through the list.** *Use every default?* is an entry. When it is answered `yes`, the runner treats every later entry as if `input.defaults` were set. The mode and branch come before it, so a typed *yes* cannot answer them (#1488, `recipe-flow.ts:305-306`). When it is refused for want of a terminal, the walk goes on (#433, `recipe-flow.ts:510-515`). The trial entry's default is `no` whenever the defaults are on, including when they were switched on here (`recipe-flow.ts:621-624`, #436). It is also `no` with no terminal.

**Validation moves into the descriptors, word for word.** With no terminal the runner validates the default itself (`machine-list.ts:209-215`) and never reaches the asker. So a check that lives only in an `ask*` would be skipped headless: for example `refuseUnlessOffered` (`agents.ts:231-240`) and the GitHub branch lookups (`recipe-flow.ts:353-363`). Each asker passes `d.question.validate` to `questionEffect`, the way `machine-askers.ts:197-200` does. The prompt text stays in the asker; the refusal text moves with the check.

## 2. Both shapes collect every change and call `draft.set` once, at the end of the list

This decision is what removes `absent` (`recipe-flow.ts:293`).

- The draft cannot be set after each question. `draft.set` resolves on every call (`packages/project/src/draft.ts:72`). A recipe with `mode: team` and no `branch.personal` does not resolve, so mode and personal branch, which are separate entries, cannot be set one at a time. `recipe-flow.ts:366-367` already works around this for one pair: *"checked on its own, the new `branch.main` would be compared with the `branch.personal` that is about to be removed"*.
- `source.kinds` has no default either: `const KINDS = z.array(z.string()).min(1)` (`packages/recipe/src/recipe.ts:1036`). The ticket names only `source.tickets`, but no prefix of the list resolves until kinds is in.
- On a new recipe, `said` comments and `orderSteps` apply only to the first `set` (`draft.ts:69-70`).

So the project context holds `draft` (from `draftRecipe`, not touched mid-list) and `pending: RecipeChange[]`.

- Each `write` returns `RecipeChange[]` and the runner appends them to `pending`.
- Reads go through a **view**: `draft.text()` with `pending` applied by `widenStepsIfNeeded` and `editedText` (the two calls at `draft.ts:67-68`), without the resolve.
- `view.get(path)` is `keyIn` over that text. `view.resolved()` resolves it and answers null where it does not resolve yet.
- This replaces both hand-made overlays: `trialDraft` (`recipe-flow.ts:531-543`) and the local `tryBuild` draft (`first-project.ts:1193-1207`).

After the last entry the caller calls `draft.set(pending)` once. On a new recipe that is the creating write, so the `said` comments now cover every block. Its refusal is reported by name like any other.

Consequences:
- **Refusal text.** Every refusal inside the list is a refusal before any write, on both shapes. `kept` and `keptBeforeWrite` (`recipe-flow.ts:100-107`, `:303`) become one `kept`: what was true before the list started. On `init` that includes the machine list's writes.
- **Ctrl+C.** Nothing reaches the draft before the end, so `keepAnswered` (`first-project.ts:1093-1175`) and its `onCancelExit`/`Effect.onInterrupt` wrapper (`:1228-1243`) have nothing to write. Delete them, and delete `onDraft` (`recipe-flow.ts:67-68`). This reverses #392's *"a Ctrl+C keeps what was answered"* (`recipe-flow.ts:7-9`, `first-project.ts:1093`). The ticket's Ctrl+C edge decides it (*"so Ctrl+C also writes nothing"*). No ADR covers it, so it needs no superseding file, but name it in the commit body.
- **Equal answers write nothing.** That falls out of `draft.ts:73` (`text === existing` → `written: false`) when `draft.changes()` is read after the single set. Still make each `write` return `[]` for an equal answer. The card and #1524's old → new rows read `Entry.wrote`.

## 3. What "in force" means, per entry

Use one rule.
- **A rerun** is a recipe that existed when the run started. `inForce` is what that starting recipe resolves to, schema defaults included. Where it does not resolve, `inForce` is the raw key: keep the reads `askTickets` and `askKinds` do for that case (`source.ts:100-113`, `:183-190`).
- **A first run** has nothing in force. The default is the system's: `defaultAgents`, the proposal or detection, `kindsFallback ?? SETUP_KINDS`. It is written, which is 0125 §9's *"Taking the system's default for a key that was never written writes it"*.
- **Schema-defaulted keys** (landing, limits). Their `systemDefault` is what `view.resolved()` says, and `write` compares against the view. So Enter writes nothing on either shape (`landing.ts:182-185`, `:324`). This reconciles the ticket's *Schema defaults are not pinned* with §9. It is not a contradiction.
- **The exceptions read the view**, because they depend on answers given earlier in this run:
  - the writer's model is offered only if the writer is kept (`agents.ts:272-278`);
  - the personal branch's default comes from the login (`recipe-flow.ts:435`);
  - the trial;
  - the judge.

No entry reads the environment (ticket edge). Project `InForce.from` is always `'file'`.

## 4. The entries, in order

4. `branch`: `--main` in solo, `--personal` in team, plus `--main` in team (`recipe-flow.ts:413-430`). The detected value comes from a port: GitHub's default branch, or `lingtai-base` locally. So does the existence check: `branchExists` on GitHub, or `rev-parse` locally.
5. `make-branch` (confirm).
6. `move-landing` (confirm). It applies to a local rerun from another checkout.
7. `defaults` (*use every default?*).
8. `writer`.
9. `writer-model`.
10. `reviewer`.
11. `reviewer-model`.
12. `sandbox`. It applies where the host was read (`recipe-flow.ts:583`).
13. `sandbox-hosts`.
14. `install`.
15. `checks`. It reads `ctx.buildFlags`, because `flags['build']` holds only the last value (`recipe-flow.ts:77`). Its answer is a JSON array, so a command containing a comma survives.
16. `trial`.
17. `tickets`.
18. `kinds`.
19. `landing`. It applies in solo, or with `--land hold`. `--land <branch>` on team is refused in `fromFlags` (`recipe-flow.ts:699-704`).

Each `ask*` is split at the seams that already exist inside it:
- `askAgents`'s four `questionEffect`/`askModel` calls (`agents.ts:254`, `:280`, `:303`, `:379`);
- `askSandbox`'s two (`sandbox-step.ts:42-51`, `:70-81`);

**The trial is one entry whose `write` keeps the failure loop.** `tryTheBuild` (`setup-build.ts:296-404`) answers a red build with edit, keep or drop, and *edit* goes back to the install or the checks.
- The trial's `write` runs the trial over the view through a port the terminal input supplies. On *edit* it asks again through the `install` and `checks` askers. Its changes replace those entries' changes in `pending`.
- On a failure, the decision is asked of the world. With no terminal it is refused as it is now (`setup-build.ts:378-387`).
- The board input supplies no trial port (0125 §7), so `trial` does not apply there.

## 5. The judge

Add one function to `packages/recipe/src/answers.ts`, beside `findingsJudgeChanges` (`:83-98`). It takes the old writer, the new writer and `steps.proposed`, and returns the changes the ticket's Fix 3 lists:

- the new writer can judge, and there is no findings judge → append one;
- the first findings judge names the old writer → rewrite its `judge`, or remove that entry when `isImplementOnlyAgent(new)` holds;
- the judge names anything else → `[]`.

`findings-judge.derive` calls it. The old writer is the starting recipe's, from the view's `steps.implement` agent, which is what `agents.ts:246-250` reads.

`askAgents` loses `agents.ts:335-360` and `:402`, but `leftoverRefusal` (`agents.ts:87-135`) must still skip the judge that the derived entry will edit or remove. Otherwise G3's *"also names"* notice prints before the judge entry runs. So export a predicate from the same file, *this entry is the derived judge*: the first findings judge, naming the old writer. `reviewer.write` passes its index as `editedInPlace`. `leftoverRefusal` moves into `reviewer.write`, which knows both answers. It stays before the reviewer-model question, as at `agents.ts:367`, and uses the `{ refused }` return from §1.

## 6. Branches are made after the list, on both paths, solo `lingtai-base` included

Today the local solo base is made before `askRecipe` (`first-project.ts:994-996`, *"before `askRecipe`, whose trial build cuts from a mirror of this checkout at `base`"*, `:919-920`). Only the team branch waits (`:975`).

With the view, the trial reads the branch it will be cut from, the way the local `tryBuild` draft already handles a deferred personal branch (`first-project.ts:1199-1204`). So every branch is made after the list and before `applySetup`: the result carries `make`, as `recipe-flow.ts:481` does. Ctrl+C then leaves no branch behind either. `madeKept` (`first-project.ts:921-948`) goes away.

Team → solo keeps its split. The PR read happens before anything is made (`:954-971`). The branch made by the switch (`lateBranch`, `:957`) is still made inside the write, after `changeRecipe`'s check (0130 §1).

## 7. Callers and the deleted lists

`runLocalBranch` and `runGithubBranch` keep the non-question steps: the App step, `register`, the mirror, the labels, `alreadyOnboarded`, the in-flight check and mirror removal of a move (`first-project.ts:880-917`), and the deferred token (`runSetupList(deferred, …, { draft: final })`, `add-github.ts:665-673`). Each calls `runSetupList(projectList(ports), input, ctx)` once, then `draft.set`, then makes the branch, then registers.

- **`add-github.ts:605-627` (`delete flags[name]`).** It exists because the project path ran twice: `askBeforeGithubAdd`, then `chooseFirstProject` → `runGithubBranch`. Once the list runs only in the first and `runGithubBranch` reads no project flag, delete the list. Do not move it.
- **`RECIPE_FLAGS` (`first-project.ts:510`)** and `deferRecipeFlags` (`:423`, `:500`) go too.
- **`init.ts:626` `discardedFlag`.** That branch (a machine with projects, none named) asks no project question, but it must still refuse project flags by name (#396 finding 3, `init.ts:618-623`). It refuses any flag in the union of `projectList`'s `flags`.
- **There is a fourth copy the ticket does not name:** `unread` at `first-project.ts:824-838`, which a repair of a registered project uses to refuse questionnaire flags. The repair (`repairOnly`, `:1083`) skips the list today. Under 0125 §6 (*"a later run … asks every question the first run asks"*) it runs the whole list after *move the landing?*. So `unread`, `repairResult` and `repairOnly` are deleted. With the defaults taken, an unchanged recipe still writes nothing beyond the move's seeds.
- **`move-landing` without a terminal** is now refused naming `--defaults`. Today it goes ahead (`first-project.ts:905`: *"`null` is no terminal: the line above is the record"*). The ticket's confirmation rule decides this. Name the change in the commit.

`askMode` and `askPersonal` each end up with one caller: the `mode` and `branch` askers in `apps/cli/src/project-askers.ts`. That file is the twin of `machine-askers.ts`, with `PROJECT_ASKERS` typed over `ProjectQuestionId`, so a missing asker fails `tsc` (`machine-askers.ts:1-5`). `recipe-flow.ts` keeps `summariseRecipe`, `priceHints` and `changedLeftBehind` and loses everything else. Its `RecipeChanged` facts are computed from the starting recipe and the view after the list.

## 8. Tests, and what cannot be checked here

- **Order.** `packages/setup/unit/project-list.test.ts` reads `projectList(fakePorts)`. It asserts the ids in order, and that `findings-judge` has `derive` and no asker.
- **The two Done-when equivalence tests** compare `ListResult.entries.map(e => [e.id, e.asked])` from `init --local`/`add --local` over one fake world, and from `init --github`/`add owner/repo`. Do not compare prompts.
- **No pinning.** `draft.changes()` is empty after the second walk, and no `ProjectConfigured` is in the memory store.
- **Judge cases.** Unit tests on the new `answers.ts` function cover the codex → claude-code, no-judge and copilot-removal cases. A walk-level test asserts the *"also names"* line is absent.
- **No terminal.** `stopped-at-question.test.ts` now asserts that only `where`, the repository, `login` (when none is known) and the confirmations refuse without a terminal. Every other question takes its default.
- **`init-golden`.** It drives an interactive world with `acceptingDefaults` (`init-golden.test.ts:50-58`; `interactive` defaults to true, `init.ts:428`). The asked questions are the same, so the lines should hold. One exception: the *"the reviewer runs the writer's runtime"* log line (`agents.ts:373`) must keep its place before the reviewer-model question.
- **Integration.** `apps/cli/integration/init.test.ts` drives these paths through real git. Update it, but it cannot run inside a pass (803 s). The unit-level claim that stands in is the `init --local` ≡ `add --local` entries test over the fake `runGit` plan, which is how `init-golden.test.ts:31-35` fakes git.
- **`add-from-page-equals-add.test.ts`** compares the board's add with the CLI's. Rerun it: the order test changes what it walks.
- **Ratchet.** Every port the list takes is an Effect. `askTickets`'s `history` is a promise port today (`recipe-flow.ts:91`, `first-project.ts:1209`), and it becomes `Effect`. That removes an `Effect.runPromiseWith`, which the ratchet does not count. Write no `async`.
