# Design note for #493: implement and every fix round append `RunSpent`

## The decision the ticket leaves open: where `name` comes from

`SpentFor.Action` needs the action's `name` (`packages/domain/src/events.ts:692`), and the dispatch in `conduct.ts` never sees it. Today the name is set at two places:

- the built-in: `createWorkAction({ name: 'write the change', prompt: '' }, { work: dispatch })` (`conduct.ts:2823`);
- a recipe's `agent:` at `implement`: `createWorkAction({...agent, ...}, deps.work)` (`packages/actions/src/from-recipe.ts:323`), whose name is the recipe entry's own.

Both names stop at `createWorkAction`. `run()` builds the `WorkDispatch` from `prompt`, `model`, `agent` and `limits` only (`packages/actions/src/work-action.ts:140-147`). `WorkDispatch` has no `name` field (`work-action.ts:94-103`), and `ActionContext` has none either (its fields are `runId`, `onSha`, `cwd`, `env`, `recheck`, `round`, `design`, `again`, `log` and `signal`, in `packages/actions/src/action.ts`).

**So add `readonly name: string` to `WorkDispatch`, and have `createWorkAction` pass `name: spec.name` into the `deps.work(...)` call.** Make it required rather than optional. Every `WorkDispatch` is built in that one place, and 0110 §9 says the name is what finds the spend: *"`step`, `name` and `round` find it, which holds while an action's `name` is unique within its step"*. `actionsAt` in `recipe.ts:2425-2445` refuses a recipe that breaks that uniqueness, so whatever name arrives here is already unique. Do not hard-code `'write the change'` in `conduct.ts`. That would record the wrong name for every recipe that declares its own `agent:` at `implement`.

`packages/actions/src/work-action.ts` is a file this ticket has to touch. Commit it on its own first, so `conduct.ts` has a field to read.

## What `RunSpent` is built from

Write one small helper in `conduct.ts` beside `firstDispatch` that turns `(outcome, name, round, runtime)` into the `ToAppend`. Both dispatches call it, so the two places cannot drift apart:

- `for: { _tag: 'Action', step: 'implement', name: spec.name, round }`.
  - `round` is `0` in `firstDispatch`.
  - In `fixRound` it is the `round` the function already computes (`brief.context.round ?? 1`, `conduct.ts:3221`), the same value `FixRequested` and `FixApplied` carry.
  - `events.ts:684-685` says the same: *"implement is round 0, and only a fix round counts from 1 (0110 §10)"*.
- `runtime: dispatched.capabilities.id`. **Use `dispatched`, not `options.runtime`.**
  - Both dispatches resolve `runtimeNamed(spec.agent ?? options.runtime.capabilities.id)` (`conduct.ts:2964`, `3219`), and a recipe's `agent:` may name the second runtime.
  - The never-started branch at `conduct.ts:3127` reads `options.runtime.capabilities.id`. Do not copy that line.
  - `RunStarted` is already written from `dispatched.capabilities.id` (`conduct.ts:2999`).
- `turns`, `durationMs`, `costUsd`: copy them straight off the outcome. A `null` cost stays `null`.
- `usage: outcome.usage ?? []`. `RunSpent.usage` is required (`events.ts:703-706`: *"A runtime that reported no tokens writes `[]`"*). `RunFinished` spreads `usage` only when it is defined (`conduct.ts:3165`), and the fix round's `.catch` sets `usage: undefined` (`conduct.ts:3299`). So `[]` is the only correct spelling here, and `RunFinished`'s conditional spread must not change.
- Build it through `parsePayload('RunSpent', …)` like every other append, so the schema refuses a bad `for` at the write.

## Where it goes: inside the batch that already exists, after what is there

**Implement** has two append sites once `ran` is a `Right`:

- the failure batch, `appendFrom(runId, version, [...receipt, RunFailed])` (`conduct.ts:3113-3120`);
- the success batch, `appendFrom(runId, version, [RunFinished])` (`conduct.ts:3156-3168`).

Put `RunSpent` last in each of those arrays. Do not add a third `appendFrom`: `version` is the expected stream version for one batch, and a second call at the same `version` would conflict. Putting it last also leaves every existing event's payload unchanged. The failure batch covers `never-started`, `crash`, `timeout`, `out-of-turns` and `out-of-usd` alike: what `never-started` reported is recorded as reported, which is the ticket's *never a made-up `0`*.

**The fix round**: put it in the `appendNow(runId, [FixApplied])` batch (`conduct.ts:3313-3328`), after `FixApplied`. That batch runs on every return of `dispatched.run`, including the `.catch` stand-in (`conduct.ts:3290-3299`) and the never-started branch below it (`conduct.ts:3342`).

**What records nothing, and needs no code to make it so:**

- `Either.isLeft(ran)` at `conduct.ts:3086`: the hook socket failed, there is no outcome, and the dispatch returns before either batch.
- A `dispatched.run` that rejects inside `firstDispatch`. That is `Effect.promise`, so the rejection becomes a defect and never reaches `ran` (`conduct.ts:3041`).
- A pass killed mid-run.

These are 0110 §2's *"a process killed with no result records nothing"*.

**The fix round's `.catch` is the one place where 0110 §2 and the ticket could look like they disagree.** The process threw, and the conductor made up an outcome. The ticket settles it: *"The fix round's `.catch` today gives cost `null`: that is `costUsd: null`, not zero"*. So record it, with `turns: 0` and `durationMs: 0` exactly as the stand-in says. Do not add a branch that skips it.

## The tests, and the fixture that will go red

**`packages/conductor/unit/what-a-pass-writes-today.test.ts` will fail on every row that dispatches.** It asserts the full ordered list of event types on the run stream (e.g. `:183`, `:259`, and the list ending `'FixApplied', 'RunProducedDiff', …` at `:270-291`). Its header says what it is for: *"recorded by running the row against the fakes and copying what it actually wrote"*. Inserting `'RunSpent'` right after each `'RunFinished'`/`'RunFailed'`/`'FixApplied'` that ends a batch is the correct update, because the pass now writes one more event. Insert it only there. Changing anything else in a list means a payload or an order moved, and the third *Done when* forbids that.

`packages/conductor/unit/attempts.test.ts` also lists `'RunFinished',` / `'FixApplied',` in sequence. Check it the same way.

Put the new assertions in that file too. It drives `once()` from `test/one-pass.ts` against the fakes, so it is unit, and it already has rows for the outcomes the ticket names:

- out-of-turns at implement (`:1407`);
- out-of-turns mid-fix (`:1300`, `:1723`);
- never-started (its own test, `never-started.test.ts`);
- a fix round that crashes (`:636`).

For each, assert exactly one `RunSpent` on the run stream, with `for`, `runtime`, `costUsd` (including `null`) and `usage` (including `[]`). For a fix row, also assert `for.round` equals the `round` in `FixApplied.data`.

For *none when killed*, the reachable unit case is the hook socket not being served. If the fakes cannot make `ran` a `Left`, say so in the test file rather than reaching for a real process.

For *byte-identical*, deep-equal (`toEqual`) the `data` of `RunFinished`, `RunFailed` and `FixApplied` in one existing row against what that row asserts today. `toMatchObject` alone would not catch an added field.

The projections need nothing here. `#499` already pins that `task_view` and `finding_backlog` ignore a `RunSpent` (`packages/projector/unit/task-view-rebuild.test.ts:554`, `backlog-rebuild.test.ts:445`).

Everything above runs in `pnpm test`, so nothing here depends on the integration half. On the live log, the claim is settled by a pass stream carrying one `RunSpent` per `RunFinished`/`RunFailed`/`FixApplied` batch, with `data.for.round` matching `FixApplied.data.round`.
