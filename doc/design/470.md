Both call sites have to change, as the ticket says. The decision the ticket leaves open is how the integration test reaches the `wip:` commit. `keepUncommittedWork` is a closure inside `conductPass`, so a real `git` cannot get to it without a whole pass. The fix is to lift the staging into one exported function. Both sites call it, and the integration test drives it against a real repository.

## One helper, in `kept-run-port.ts`

The command is wrong in two places today, and they share it because one was copied from the other:

- `packages/conductor/src/kept-run-port.ts:65`: `git(['add', '-A', '--', '.', `:(exclude)${plantAt}`])`
- `packages/conductor/src/conduct.ts:1665`: the same call, with a comment saying where it came from: "the same exclusion `kept-run-port.ts`'s own `keep` applies and for the same reason".

Put the staging in one place, an exported function in `kept-run-port.ts` beside `keptRunPort`. It takes the `GitHere` that file already defines (`kept-run-port.ts:29`, "the shape `conduct.ts`'s `gitAsked` already has") and `plantAt`, and runs:

1. `add -A`
2. `reset -q -- <plantAt>`

It returns a failure that names which of the two calls refused. Each call fails only on its own `Either.left`, which means a non-zero exit. Nothing in it reads the index or the output to decide whether a call succeeded; the ticket's *Watch out* is that `git add` stages everything and still exits 1.

I checked the `reset` in a scratch repository whose `.gitignore` is `.env.*`. All three of these exit 0:
- `.env.local` ignored and never staged
- `.env.local` staged by `add -A` when it is not ignored
- a path that does not exist

So the `reset` never needs to be skipped or guarded.

Then the two callers:

- **`conduct.ts`'s `keepUncommittedWork` (1628–1720).** It already runs `git reset -- plantAt` after the add (1680). Replace both the add and that reset with the helper, and keep the `wipFailure` wording (`the dirty tree was not kept — …`), because #467's `RunRefsPublished.detail` is read in that shape. Leave the porcelain pre-check, `onlyThePlantedFile` (1648–1652), as it is. When the file is ignored, porcelain never lists it, so that check simply never fires. It still matters in a repository that does not ignore the file.
- **`keptRunPort.keep`.** Call the helper first, then `diff --cached --quiet` as now. **The `diff` must come after the reset.** Otherwise a tree whose only change is the planted file reads as *something staged*, and the commit that follows has nothing in it but the secrets.

To make the `wip:` commit itself reachable, lift the rest of the keep as well: the helper, then the `-c user.name=… -c commit.gpgsign=false commit --no-verify -m …` at 1688–1700, as one exported function taking `git`, `plantAt` and the message. `conduct.ts` keeps everything before and after it: the status check, `rev-parse` for the parent, `wipParent`, and the run-log notes. That function is what the integration test calls with a message built from `WIP_COMMIT_PREFIX`. Lift nothing beyond that. This is a staging fix, not a move of #468's keep.

## Tests

**Unit tests (`pnpm test`).** These hold the call order. They cannot see the bug, because a fake answers 0:
- `packages/conductor/unit/kept-run-port.test.ts:60–65` asserts `['add', '-A', '--', '.', `:(exclude)${PLANT}`]` literally. It becomes `['add', '-A']`, then `['reset', '-q', '--', PLANT]`, then the `diff`.
- `packages/conductor/unit/conduct-what-a-claim-leaves.test.ts:856`, *excludes the planted env file from the WIP commit's staging*, asserts the same pathspec. Change it to assert `add -A` followed by `reset -q -- .env.local`, and retitle it to match.
- Add one unit case: an `add` answering left fails the keep and nothing is committed. That is the only check of the exit code that `pnpm test` can run.

**Integration test.** Make a new `packages/conductor/integration/kept-run-port.test.ts` that runs the real `git` in an `mkdtemp` repository. It shells out the way `integration/git-refs.test.ts` does with `execFile`. Set `user.name`, `user.email` and `commit.gpgsign=false` in the repository's own config, so the machine's global config (hooks, signing) cannot decide the result; `keep`'s `commit -m` (`kept-run-port.ts:70`) sets no identity of its own. Three cases:
1. `.gitignore` covers `.env.*`, and both `a.txt` and `.env.local` are written. The lifted WIP function commits. `git show --name-only HEAD` lists `a.txt` and not `.env.local`, and the subject starts with `WIP_COMMIT_PREFIX`. This is the run from #467.
2. No ignore rule, and the agent has already run `git add .env.local a.txt`. The commit has the same contents: `a.txt` without `.env.local`.
3. `keptRunPort.keep` against case 1's repository. It commits `a.txt` alone. With `.env.local` as the only change, it answers `{ nothing: true }`.

**Nothing in the build step runs this file.** It is in the integration half, which runs after the merge (0060). Until then the evidence is the unit call-order assertions above, plus the scratch-repo transcript in the ticket. Run it once by hand with `pnpm vitest run --project integration packages/conductor/integration/kept-run-port.test.ts`. It needs no database, so it finishes in seconds, unlike the 803-second integration run. Do not run the whole integration half.

## What settles it after the merge

Settle it from the next stopped run with a dirty tree in this repository. That run needs a `RunKeptUncommitted` event, and its `RunRefsPublished.detail` must not contain `the dirty tree was not kept`. The commit at `RunKeptUncommitted.sha` on the arm must not list `.env.local`. None of this is reached until the daemon restarts onto the merge.

No ADR is touched. #468's decision, to keep a stopped run's dirty tree as a `wip:` commit on the run's own arm, is unchanged; only how it stages changes.
