## Design note for #586: the project sign-in rows cover every dispatched agent

### Where it goes

All of it is in `apps/cli/src/doctor.ts`, inside `declaredEnvironment`'s per-project loop. The change replaces the single call at `:2204`:

```ts
results.push(await dispatchedAuthRow(project.project, resolved.recipe.runtime.agent, asked, runtimes))
```

The `discuss`/`triage` loop after it (`:2205-2240`) stays as it is. It already gives each of those roles its own row, and the Codex routes (`codexRoleRow`, the `askedTriageCli` cache with `CODEX_HOME`) have different questions to ask. Do not fold them into the new grouping. The ticket's *reuse the existing per-role path* is met by leaving that loop alone.

### What counts as a dispatch

Use the predicate the conductor already uses, not a new one. `agentRefusal` in `packages/conductor/src/conduct.ts:328-338` walks `Object.entries(resolved.recipe.steps)` and counts:

- `'agent' in action` → `action.agent`
- `'judge' in action && !isBuiltInJudge(action.judge)` → `action.judge`

It carries the comment *"A built-in judge names no runtime — it is a function — so it is not a second dispatch"*. `dispatchedBy` in `packages/recipe/src/settings.ts:82-86` uses the same test, and its doc comment says *"the three places that ask *is this a paid call* have to agree"*. Doctor becomes the fourth such place, so write the same two lines, with `isBuiltInJudge` from `@lingtai/recipe` (`recipe.ts:1299`). Never compare against the string `'same-worktree'`; `recipe.ts:1320` warns against exactly that. `dispatchedBy` is not exported, so do not export it just for this. The two-line test is the contract.

### The decision: one row per distinct agent, with the runtime row as the anchor

Group the agents into a `Map<RuntimeId, string[]>` from agent to the recipe keys that need it, in this order:

1. `runtime.agent` first, under the key `runtime.agent`. It is always dispatched: an unconfigured `implement` runs on it (`conduct.ts:3113-3130`, *"an unconfigured `implement` still buys the one agent — on `runtime.agent`"*).
2. Then each step in `STEPS` order. Push `steps.<step>.agent` for an agent action, and `steps.<step>.judge (when: <when>)` for a runtime judge.

Emit one row per map entry:

- **The `runtime.agent` entry keeps its current name, `runtime: <project> signed in`.** `doctor-ownerless.test.ts:196-201` pins that exact list of names for a `steps: {}` recipe, and that test must stay green unchanged. A step or judge on the same agent adds no row. It only appears in that row's detail, e.g. `claude-code — signed in via claude.ai · needed by runtime.agent, steps.design.agent, steps.proposed.judge (when: findings)`. This satisfies *two steps on the same agent add one*.
- **Every other agent gets `steps: <project> <agent> signed in`.** The agent goes in the name because a project can have more than one of these rows, and the names must differ. The detail lists the keys in the same way.

Do not emit one row per step. The ticket asks for *once per distinct agent*, and against this repository's recipe that would be about six rows saying the same `claude-code — signed in`.

### `dispatchedAuthRow`'s signature

Today it takes `role: 'runtime' | 'discuss' | 'triage'`. That one parameter builds both the row name (`:2077`) and the failure text, `names it at ${role}.agent` (`:2091`), which is wrong for a step: there is no `review.agent`. Split it into a row label and the list of recipe keys:

- The name becomes `${label}: ${project} signed in`, where `label` is `runtime`, `discuss`, `triage`, or `steps` plus the agent.
- The failure text says `names it at ${keys.join(', ')}`.

The `discuss`/`triage` callers pass `[`${role}.agent`]`. The rest of the remedy sentence (*"Sign in, or name a runtime this machine has at … in recipePath(project)"*) stays.

Keep passing the same `asked` map, which is created once per `declaredEnvironment` call at `:2148`. Each agent is then asked at most once across all projects and all rows. `checkAuth` is the cheap status probe and starts no model call, so nothing here may build a runtime and dispatch it. The machine-wide `runtime: signed in` row (`:767-810`) is a different function and is not touched.

### Tests (unit, `apps/cli/unit/doctor-ownerless.test.ts`)

That file already drives `declaredEnvironment` with `recipe`, `agentEnv` and `runtimes` stubs (`:184-201`). Extend `runtimesStub` there with a `codex` entry that counts its `checkAuth` calls. Add:

- **Codex at `review`.** `runtime: { agent: claude-code }` plus `steps: { review: [{ agent: codex }] }` (check the step-list syntax against `recipeOf`'s fixtures) gives both `runtime: esctest signed in` and `steps: esctest codex signed in`. The codex row's detail contains `steps.review.agent`.
- **Codex signed out.** The same recipe with codex's `checkAuth` answering `loggedIn: false` gives a `fail` whose detail names `steps.review.agent`.
- **Built-in judge.** A `proposed:` with `judge: same-worktree, when: red` adds no row, and the codex stub is never asked.
- **Same agent twice.** `design` and `review` both on `claude-code` add no row beyond the runtime row, whose detail names both steps, and `claude-code`'s `checkAuth` is called once.

All of this is unit-level: the `runtimes` injection exists precisely so nothing spawns a binary (`:2069-2070`). `pnpm test` and `pnpm typecheck` cover it, and no integration file is needed.

### Not in scope

This does not touch `agentRefusal`. It already refuses a pass whose second runtime is not signed in (`conduct.ts:342`). This row is doctor telling you so before the pass does.
