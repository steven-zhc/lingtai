## 1. Domain: one `StepState` per action, so call the selector once per action

`reviewSummaryOf` reads a whole `StepOutcome`: the last completed `verdict` action of a `review` step. `stepStateOf` builds the state for **one** action, keyed `step:action` (`attempt.ts:541`). Calling the selector on the whole outcome inside `stepStateOf` would copy the reviewer's summary onto every other action at `review`.

So in the `StepEnded` case, call it with an outcome that holds only this action: `reviewSummaryOf({ ...d.outcome, actions: [action] })`. Spread the result into the state that `stepStateOf` returns. This keeps the one-selector rule, and the summary stays on the action that wrote it.

Three rules for the new keys:
- **Key order.** Add `summary?` and then `clipped?` **after** `findings`, in the TypeScript interface, in what `stepStateOf` returns, and in the zod schema. The codec's comment explains why (`run-codec.ts:59-60`): *"Keys in the order the reduce writes them, so a decoded state encodes to the same text as one that never left memory."*
- **Omit, never `undefined`.** Write each key with a conditional spread, as `action.ts:951-953` does (*"no summary is an absent key (#890)"*).
- **The schema.** Use `summary: z.string().optional()` and `clipped: z.strictObject({ read: z.number(), of: z.number() }).optional()`. Do **not** add `.nullable()`: `promptRefs` needed it (`run-codec.ts:96`), but nothing here ever writes `null`.

Old `task_view` rows decode unchanged. `firstDifference` skips a key that is absent on both sides (`packages/domain/src/ticket-codec.ts:207-209`). The decode test from the ticket's Done-when is a `StepState` fixture with no `summary` or `clipped`: decode it, re-encode it, and expect the same text.

**No projection rebuild is needed for the page.** The task page reduces each run stream itself (`readAttempts`, `task.ts:1719`: `claims.map((_, i) => reduceAttempt(streams[i] ?? []))`), so a summary written before the deploy shows up as soon as the board restarts. Rows in `task_view` pick the keys up only when something reduces them again. Nothing on this page reads those rows.

## 2. `presentAttempt`: one attempt-level field, not one per step

Add one field to `AttemptView`:

```ts
review: { summary: string; clipped: { read: number; of: number } | null } | null
```

- **Where it comes from:** the `state.steps` entry whose key starts with `review:` and that has a `summary`.
- **Several such entries:** take the last one in `Object.values` order, and say so in a comment.
- **No summary means `null`, even when the review was clipped.** The Done-when says *"no summary renders nothing"*, and the clipped line sits *under the summary*. A clipped line with no summary above it is an orphan.
- **Do not filter by `stale`.** The ticket's in-flight edge says the tab shows the latest review's summary until a re-review replaces it. A review on an older head is still the latest review.
- **Do not fall back to anything else.** Nothing is read from the implementer's account or from a commit message. The ticket's Watch-out says *"show nothing."*

Do not put the summary on `StepVerdict` (`task.ts:1162-1171`). Each step's line would then carry a paragraph.

**Update the test fixtures.** Both `apps/board/unit/attempt-tab-order.test.tsx` (`run()`, lines 8-27) and `present-attempt.test.ts` build an `AttemptView`. Give both fixtures `review: null` by default.

## 3. Rendering: a new source, with its own rendering

1. **Add `'summary'` to `DocumentSource`** (`apps/board/src/lib/markdown.ts`), and add a row to the table in that file's header.
2. **Give it its own `Rendering` value, `'inline'`.** Do not reuse `'rendered'`: the `RENDERING` record is exhaustive, so its table should say on its own line that this source is limited to four elements.
3. **In `markdown.tsx`, handle `'inline'` with the same `ReactMarkdown`**, plus `allowedElements={['p','code','em','strong']}` and `unwrapDisallowed`. Both are react-markdown's own props, so this is not a hand-rolled renderer.
   - With `unwrapDisallowed`, a heading or a list keeps its text and loses its element. That is the ticket's "shown as text".
   - **Keep `rehypeSanitize`.** The reviewer wrote this text while reading a diff that anybody's agent may have shaped. Treat it like the ticket body, as untrusted.
4. **Split the lead with a pure function in `apps/board/src/lib/`**, for example `leadOf(summary) → { lead, rest }`, so a test can check it without mounting anything.
   - The lead ends at the first `.`, `!` or `?` that is followed by whitespace or the end of the text, **and is outside a backtick span**. A summary like ``Moves `a.b` to …`` must not split at `a.`.
   - With no such boundary, the whole text is the lead.
   - The page renders `lead` and `rest` as two `'inline'` `DocumentBody` calls. The lead gets its own class, and the rest is left out when it is empty.
   - Emphasis that spans the boundary falls back to literal asterisks. That is acceptable: 0103 §3 asks for a first sentence of one clause, and *"a summary that is missing, long or malformed is shown as it is."*

## 4. The tab and the ADR

- **Placement.** In `attempt-tab.tsx`, render the summary right after `<p className="asum">` (around line 62) and **before** `<p className="ameta">`. It goes before `ameta`, not just before Steps, because the ticket says "right under its summary line".
- **The clipped line, verbatim:** `the reviewer read the first {read} of {of}`, in its own `<p>` under the summary.
  - **Do not add a unit.** `action.ts:35` calls the numbers characters, but `agent-action.ts:354` cuts the diff by `limitBytes`. A unit word on the board would be a claim nobody has checked.
- **Update the comment.** The order comment at `attempt-tab.tsx:22` gains *the reviewer's summary* after *one summary line*.
- **Edit 0118 §2 in place.** Its order list, at `doc/decisions/0118-a-hold-explains-itself.md:369-374`, gains *the reviewer's summary of the change, where there is one* after the summary line's parenthesis. 0118 is in `doc/decisions/`, where a changed decision is an edit to the file rather than a new one.

## Tests

The tab's three cases go in `attempt-tab-order.test.tsx`, using its existing `renderToStaticMarkup` pattern:
- **Order:** the summary's index is greater than the index of `asum` and less than the index of `Steps`.
- **Lead:** the lead's class wraps only the first sentence.
- **Clipped:** the text `the reviewer read the first`.
- **No summary:** `review: null` renders no summary element.

The other unit tests:
- **`leadOf`:** a backtick case and a no-boundary case.
- **The reducer:** a `StepEnded` at `review` with two verdict actions, where only one carries a summary, puts the keys on that action's `StepState` alone.
- **The codec:** the round-trip test from section 1.

Every one of these is unit-level, and `pnpm test` covers them. Nothing here needs `pnpm test:integration`.
