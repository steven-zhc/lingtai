# Design note for #576: the card, the page and the daemon read a wait's triage status from the same inputs

## The trap the ticket does not name: the beacon's `startedAt` is not the start of the daemon that is running

The ticket says to give the card "the daemon's start time from the beacon", as the page already does (`apps/board/src/lib/task.ts:1781`, `daemonStartedAt: daemon?.startedAt ?? null`). But the beacon row's `started_at` is never replaced, even when a different process writes the row.

- `packages/daemon/src/sqlite.ts:123-137` and `packages/daemon/src/postgres.ts:98-111`: the upsert's `DO UPDATE` list leaves out `started_at` (*"a beat moves `last_seen_at` and leaves the moment this row began where it is"*). Nothing ever deletes the row.
- `packages/daemon/test/contract.ts:205-222` pins this. A second store beats with `pid: 9999`, and the test asserts `status!.startedAt` still equals the first one: *"the row's beginning survives the overwriting."*

So the beacon's `startedAt` is the start of the **first daemon ever run against that store**, and that time is earlier than every `TriageStarted`. On the page today, an attempt cut off by a restart therefore reads `Running`, not `Interrupted`. If the card is only wired to the page's inputs, the card and the page will agree with each other, both will be wrong, and both will disagree with a daemon that uses its own process start. The ticket's **Want** (all three agree, and §3's retry fires) needs the beacon fixed as well.

**Decision: each process starts the beacon row afresh.** `startBeacon` (`packages/daemon/src/control.ts:511`) already means this: *"Announced before the timer, so the row is the new daemon's from the first moment it can be"* (`control.ts:538-540`). The row's `started_at` does not do what that comment says yet.

0102 §2 lists `startedAt` among the beacon's fields without defining it (`doc/decisions/0102-one-conductor-holds-the-lock.md:44`). `doc/decisions/0102-one-conductor-holds-the-lock.md` and `doc/decisions/0111-the-board-is-a-local-app.md` contain no other mention of it, and nothing in `apps/cli/src` reads it. The only readers are the board and the task page. This change gives the field the meaning 0102 implies, so no superseding ADR is needed.

### How to make the beacon fresh

- Add a `fresh: boolean` to `Beat` (`packages/daemon/src/store.ts:91`).
  - `startBeacon` sends `true` until a beat has *landed* and `false` after it: a first beat that throws leaves the next one fresh, so the previous process's start never survives. A beat that was merely asked for does not clear it.
  - It may carry `startedAt`; the daemon passes none, so the store's clock dates the row.
  - `beat()` (`control.ts:445`) passes it through `BeatOptions`.
- Both stores set `started_at = <the beat's startedAt, else the store's now>` on conflict when `fresh` is true, and keep the existing value otherwise. Fix the doc comment at `store.ts:87-90` to say "a new life per process, not per beat".
- Change `contract.ts:205-222` so that:
  - the second process's *first* beat moves `startedAt`;
  - a later non-fresh beat leaves it alone.
- That contract runs only in the integration half (`packages/daemon/integration/daemon-store.test.ts`, `sqlite.test.ts`), so the build step cannot check it before the merge. The unit-level stand-in: a test in `packages/daemon/unit/` drives `startBeacon` with `BeatOptions.store` set to a fake `DaemonStore` that records each `Beat`. It asserts that exactly the first beat has `fresh: true`, including when `say()` runs before the timer fires, and that a failed first beat leaves the next one fresh.

## The daemon: `daemonStartedAt` is a constant, taken once the lock is held

- In `apps/cli/src/lingtai.ts` (the start is read back from the beacon row once the lock is held, see Clock below):
  - Delete `let daemonStartedAt` and `let startTimeRead` (`:921-922`), and the `startAfter(since).catch(() => null)` block inside `shutdown` (`:983-986`).
  - Replace them with a `daemonStartedAt` taken right after `if (!opened.ok) return opened.code`, once the first beat has landed (below).
- **Take it after the lock, not at the top of the function.** Taken before the lock, a previous conductor could still start a triage after that instant, and this daemon would read it as `Running`. Once the lock is held, nothing else can append a `TriageStarted`.
- This also fixes a second, quieter bug: the daemon passes `daemonStartedAt` into `daemonTriagePorts(...)` by value (`:930`, `:970`). Today any `scanTriage` or `triage:` dispatch before the first `shutdown()` call sees `null`, whatever the lookup later returns.
- Narrow the type to `Date` in `TriageTriggerPorts`, `CatchUpTriagePorts` and `daemonTriagePorts` (`apps/cli/src/triage.ts:85`, `:94`, `:246`). Then *"never `null`"* is a claim `tsc` checks, not just a test.
- `triageStatus`'s own `context.daemonStartedAt` stays `Date | null` (`packages/domain/src/wait.ts:843`), because the board can genuinely have no beacon.
- **Clock.** `TriageStarted` is dated by the store, so the start is too: the daemon leaves the beacon's `startedAt` to the store's clock, waits for the first beat, and reads its own row back (`readStatus`, same pid), falling back to the host's `new Date()` where that cannot be read. A host ahead of or behind the database therefore cannot misclassify an attempt.

The unit test for the ticket's second checkbox goes over `catchUpTriage` with a memory event store:
- a `TriageStarted` attempt 1 dated before `daemonStartedAt` reads `Interrupted`, and `run` is called;
- the same attempt dated after it reads `Running`, and `run` is not called.

## The board: one context per render, built the same way as the page's

- **`declared`.** Read from `currentRecipe(p)` per registered project, the call `loadCurrentTriageStatus` (`task.ts`) makes, in `declaredTriage` beside `queuedCards` in `loadBoard`'s `Promise.all`.
  - Not collected from `queuedCards`/`filter.recipe`: `projectFilter` needs a GitHub client, which can fail for a project whose local recipe reads fine, and then the card says nothing while the page says `Queued`.
  - A recipe that cannot be read rejects and reaches the board as an error, as it reaches the page. It is never turned into "not declared".
- **`daemonStartedAt`.** Add one `readStatus()` call to `loadBoard`'s existing `Promise.all` beside `queuedCards` and `currentSpend` (`board.ts:944-954`). That is one read per render, never one per card.
- Give `toCard` (`board.ts:515`) a parameter typed `{ declared: boolean; daemonStartedAt: Date | null }` and use it at `:538` instead of the literal. Pass it from the call at `:980`.
- Build that object in one place: a small exported helper (for example `triageContextOf(declared, status)`) that both `loadBoard` and `loadCurrentTriageStatus` (`task.ts:1779-1782`) call. Then "the same inputs" is guaranteed by sharing code, not by copying it twice.
- The queued-card stub has no `wait`, so it never reaches `triageStatus`. Any default you give the new parameter only matters there, but say so in its doc comment.

For the card test (first checkbox), take one `TaskCard` with a `wait` and run it through `toCard` and `currentTriageStatus` (`task.ts:1756`) with the same context. Cover both cases:
- **queued:** `declared: true`, no facts → `Queued` from both;
- **interrupted:** facts started before `daemonStartedAt` → `Interrupted` from both.

## What this leaves alone

- When no daemon is up, the beacon still carries the last daemon's start, so an attempt that daemon started and then died during reads `Running` until the next start. The daemon will agree once it restarts, and nothing here should try to repair it.
- Whether a real interrupted attempt was retried shows in a ticket stream's `TriageStarted` events: a second one for the same `waitId` with `attempt: 2`, dated after the `ConductorStarted` that followed the first.

## Checks

`pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `pnpm test`. The store-contract edit is checked only by `pnpm test:integration`, after the merge. The `startBeacon` unit test above is what stands in for it before then.
