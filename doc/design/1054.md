## How `markFailed()` reaches an Effect span, and how it can fail to

`markFailed()` (`packages/actions/src/spans.ts`) does not read the Effect span. It reads the sink in the active **OpenTelemetry** context:

```
export function markFailed(): void {
  const sink = sinkOf()
  if (sink !== undefined) sink.errored = true
}
```

Under `Effect.withSpan` that sink is there for one reason. The bridged tracer's `context` hook wraps every primitive the fiber evaluates in `context.with(withSink(…, span.sink), …)` (`packages/conductor/src/telemetry.ts:117-123`). `BridgedSpan.end` then sends `sink.errored` up to its bridged parent (`telemetry.ts:85-88`). So the ticket's "the judge's Effect span is the fiber's current span" is true, but only for code the fiber runs **synchronously**:

- **Safe:** `held(…)` called from the `Effect.gen` body after a `yield*`, or from the `Effect.catchDefect` handler. Every `held` call site today (`:2784`, `:2919`, `:2948`) becomes one of these.
- **Silently not recorded:** a `markFailed()` inside an `Effect.promise(() => …)` thunk or a `.then` callback. Nothing fails there. `action judge` just exports as unset. Do not move a `held(...)` into a promise callback to save a `yield*`.

With no tracing layer, `markFailed` is a no-op, as `inSpan` is today with no provider. Nothing changes there.

## Where the `FAILED` annotation goes

Put it inside the span, following `run-attempt.ts:2008`:

```
askTheAgentBody(declared, on).pipe(
  Effect.onExit((exit) => (Exit.isFailure(exit) ? Effect.annotateCurrentSpan(FAILED, true) : Effect.void)),
  Effect.withSpan('action judge', { attributes: { 'lingtai.index': 0 } }, { captureStackTrace: false }),
)
```

If `onExit` sits outside `withSpan`, it annotates `step proposed` instead of the judge.

`Effect<Judged>` has no typed failure. So the failure exits are a defect that got past the dispatch (which should not happen) and an interruption. Both end the span `ERROR`, as CONDUCT-1a's step spans do. `inSpan`, being promise-bound, never saw an interruption.

`inSpan` stays imported: the `end` step's actions still use it (`spans.ts` says so). Only `askTheAgent` stops using it.

## The dispatch

- **Export:** export the existing `const dispatch` (`agent-action.ts:244`) under the name `dispatchRuntime`, with `signal: AbortSignal | undefined` in place of `context`. It only reads `context.signal` (`:261-262`). Its body, including the `Effect.suspend` that aborts and then waits, stays byte-for-byte the same. The review and the draft pass `context.signal`. Also add it to the package's `index.ts` exports.
- **Defects only:** a rejected `runtime.run` reaches `dispatchRuntime` as `Effect.die(error)` (`:268-270`). An interruption is not a defect, so `Effect.catchDefect` lets it pass and the judge stays interrupted, as the ticket requires.
- **The handler returns an Effect:** `Effect.catchDefect((err) => Effect.sync(() => { threw = true; return crashOutcome(err) }))`. It is not a bare value. `hook-socket.ts:381` and `conduct.ts:1041` already use the same form.
- **Drop the old abort:** the judge's `Effect.scoped` + `acquireRelease` abort (`:2827-2830`) goes away completely. `dispatchRuntime` now owns the abort, and keeping both would abort twice and wait on neither.

## The base check's detached runs

`baseIsRed` reads `services = yield* Effect.context()` once, at the top of the function. That is before any `mirrorWrite`, which is the ticket's point about #1040's holder marker.

Each tree callback is `(path, sha) => Effect.runPromiseWith(services)(effect)`. A callback must still **reject** with `new Error(detail)` when git fails (`:3206`), because that rejection is how `base-check.ts` answers `unknown`. So the Effect has to end in `Effect.fail` or `Effect.die` with that `Error` on a failed `Result`, not in a resolved value.

`schedule.ts:174-180` is the existing example of this pattern. Nothing in the run may add `acquireRelease` or `addFinalizer`, because `services` carries the asker's `Scope`.

## The interruption test

`runOnce` is an `Effect` (`conduct.ts:719`), so the test can `Effect.fork` it, wait on a `Deferred` that the fake `Runtime.run` completes when it is entered, and then `Fiber.interrupt`.

Base it on the setup in `conduct-continuation-judge-session.test.ts`, which already reaches a dispatched judge. The fake `run`:

1. pushes `'started'` and completes the entry `Deferred`;
2. waits on `request.signal`'s `abort` event and pushes `'aborted'`;
3. settles only after a second `Deferred` that the test completes from that abort listener, pushing `'settled'`.

After `Fiber.interrupt` returns, the test pushes `'interrupted'` and asserts the order `['started', 'aborted', 'settled', 'interrupted']`. It then asserts there is no `RunSpent`, and none of the event types `standDownAccount` appends, in the memory store's events.

The pass's `Effect.ensuring(release(…))` (`:5107`) still runs on an interruption. Its events are expected, so do not assert an empty log.

## What only the log could confirm

Nothing in production interrupts a pass today, so no event proves the new path ran. Once something does, a pass interrupted mid-judge would show `JudgeAsked`/`RunSpent` missing for that `runId`, and no account-lock event carrying the judge's crash detail. Until then, the unit test above is the only witness.
