## The fix round must serve the socket, not just point at it

The ticket says to swap the settings and the env. That alone is not enough. If the env names a socket that nothing is listening on, every tool call is refused. Today the first dispatch's server only lives inside its own scope:

- `Effect.scoped(… host.serve({ socketPath: wiring.socketPath, … }) …)` at `conduct.ts:4974-4983`.
- The run is registered with `Effect.acquireRelease(… server.register(runId, events.length) …, () => server.unregister(runId))` at `conduct.ts:5090-5093`.
- The scope closes when that dispatch returns (`conduct.ts:5122-5124`).

So by the time `fixRound` runs, there is no server and no registered run. An unregistered run is refused by design (`hook-socket.ts:207-211`): *"Fail closed on an unknown run: the conductor renders the wiring, so this means the wiring is wrong"*. A Claude Code fix round that got only the settings and env would have every tool call refused. A Copilot round would get past the ACP env check (`acp.ts:398-411`) and then be refused at its first tool call. Both are worse than today.

So the fix round's dispatch copies the whole wired block of `firstDispatch`, in this order. This is the shape to build:

1. **Wire.** `host.wire({ runId, hookBinary: options.hookBinary, home, ...(fixDecision.kind === 'sandboxed' ? { sandboxed: true } : {}) })`.
   - Pass `runId`, the stream id, and **not `fixId`**. The hook env's run id and the socket path both come from it, and it is the id the server registers.
   - This replaces `host.unhookedSettings` at `conduct.ts:5388-5398`.
2. **Smoke test.** Run `host.smokeTest(options.hookBinary, runBinary)` and use the first dispatch's three stop sentences word for word (`conduct.ts:4947-4954`).
3. **Env.** `fixEnv = runnableEnv({ ...env.values, ...wiring.env })` (`:5480`). `runtimeVersionOfEffect` and the dispatch both read it.
4. **Record the prompt, then compute the sandbox.** Keep `recordPrompt(…)` and `sandboxOf(…)` where they are, before the scope.
5. **Serve, register, run, flush.** Open `Effect.scoped` with `host.serve({ socketPath: wiring.socketPath, store, onDecision, onLifecycle })`. Use the same callbacks as `:4976-4982`, with the trace tagged `fix:${round}` as the log already is. Then:
   - Set `hookRuns = server`, so a mid-run `appendInvocation` uses the hook's version (`conduct.ts:953-966`, #1164).
   - `acquireRelease` the register and unregister. It must come **after** `recordPrompt`. The rule is #928's, stated at `conduct.ts:5017-5022`: *"`register` reads the stream's length for the hook's expected version, so this is awaited first and never after"*.
   - Call `dispatched.run({ …, settingsPath: wiring.settingsPath, env: fixEnv })`, then `server.flush(runId)` before the scope closes, as at `:5120`.
   - Keep the `Effect.catchDefect` crash mapping on the run.
   - A failure of `serve` stops the pass with `the hook socket was not served: …`, as at `:5125-5127`.
6. **After the scope.** Everything after the scope (`RunSpent` at about `:5527`, `FixApplied`, the verdict) keeps using `appendNow`. That reads the head, so the hook's `RunTouchedFile` rows, flushed inside the scope, do not conflict with it. Do not switch these to a version carried out of the scope.

The fix round runs as a separate dispatch long after the first one's scope has closed (`conduct.ts:5662`), so **each round wires and serves its own**. Do not try to build the wiring once per attempt and reuse it. `fixDecision` is decided per round and goes into the rendered settings, and the socket has to be served around each dispatch anyway. Leaving the first scope open across rounds would mean restructuring `runAttempt`, which this ticket does not ask for. The commit should say it wires per round.

Pulling steps 1, 2 and 5 into one local helper that both dispatches call is the implementer's choice, and it is the less error-prone one. If you do, the first dispatch's `RunStarted` and `StepsResolved` appends and its `register` order must stay exactly as they are. The fix round appends no `RunStarted`: it reports under the attempt's run, as the ticket says.

## Conflict rounds are in scope

A merge-conflict round goes through this same code. `fixId` branches on `from === 'merge'` at `conduct.ts:5375-5380`, and the dispatch below it is shared. So the conflict-resolution agent gets wired too, under the Out-of-scope rule *"unless it shares this exact dispatch code"*. The commit should say so.
