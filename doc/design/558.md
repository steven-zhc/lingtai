# #558 — the shape

## What it is

A `ContinueConflict` is a **conflict-flavoured `GrantFixRound`**. #539 already built most of the path: a resolution moves the lifecycle to `approved` with a ref, a continuation re-cuts at the saved head, and one `implement` visit runs on a brief that `pass.ts` hands in as `again`. After that visit the walk goes forward through `build`, `review`, `proposed` and `merge` like any fix round. Do not build a second continuation engine. Make the existing one carry this resolution, and change three things: the checks before the append, the brief, and the round accounting.

Four places change, in this order.

### 1. `resolveWaitHolding` (`packages/conductor/src/resolve-wait.ts`)

Delete the `not-built` refusal at `:232-241`. Its comment says what replaces it: *"The contract exists (#557) and the effect behind it does not (#558)."* Put a `ContinueConflict` branch in its place, after the `not-blocked` and `not-offered` checks. Every check below returns before the append. Add two optional fields to `ResolveWaitOptions`, both required for this resolution only. That follows the precedent of `kinds` for `Split` (`:141-145`): a missing one is refused by name, `no-base` / `no-conflicts`, and never skipped.

- `base: string`: the recipe's base branch name, from `baseOf(recipe)` (`packages/recipe/src/settings.ts:248`).
- `conflicts: (baseSha, headSha) => Promise<{ path: string; hunkLines: number[] }[]>`: the mirror's own count. In production this is `conflictedPathsAt` (`packages/repo/src/mirror.ts:147`), the same one triage counts with (`apps/cli/src/triage.ts:472`). It is injected because it is git, so by 0060 §1 a unit test cannot call it.

The checks, in order:

1. **`continueConflictRefusal(reason, resolution, counted)`** (`packages/domain/src/wait.ts:424`). `counted` is the port's answer flattened to `(path, line)`. Its doc already names the caller: *"`counted` is the caller's own count of the conflict's hunks (the mirror's, in the effect)."* Map `Stale` / `TooManyHunks` / `HunksMismatch` / `NotOffered` to `reason` strings with a sentence each. If the port throws, refuse with nothing resolved. Never treat a throw as zero hunks.
2. **The preserved ref.** Read the run's last `RunRefsPublished` and apply the clean-branch logic `GrantFixRound` uses at `:276-336`:
   - a WIP arm refuses;
   - `arm-only` refuses;
   - no published head refuses.

   Lift that block into one helper both branches call, so the two cannot drift. Then require all three:
   - `saved.headSha === proposal.headSha`;
   - `saved.branch === resolution.ref`;
   - `client.refSha('heads/' + ref) === headSha`.

   `client` is required here, as it is for the grant at `:328`.
3. **The base.** Require `client.refSha('heads/' + options.base) === resolution.baseSha`. 0118 §8: *"If the base or head moves before continuation, the confirmation is stale."* This check is what makes the confirmed `baseSha` the *latest* base at the moment of confirmation.
4. **The extra-round grant.** See §3 below. If rounds are exhausted, `grantExtraRound` must be `true`; refuse `grant-required` otherwise. If rounds are not exhausted, `grantExtraRound` must be `false`; refuse `grant-not-needed`, so the log never records a grant nobody needed.

Then append `WaitResolved{ContinueConflict}` with the resolution exactly as validated. Extend the two `Approve || GrantFixRound` tests to include `ContinueConflict`:

- the "way out" re-request at `:196-207`, matching on `waitId` plus `onSha === headSha` and `grantRef === ref`;
- the `requestContinuation` call at `:398`.

### 2. The fold (`packages/domain/src/ticket.ts:356-367`)

`ContinueConflict` moves the lifecycle to `approved` with `onSha: resolution.headSha` and `grantRef: resolution.ref`, exactly as `GrantFixRound` does. Do not add a lifecycle field. The continuation reads the resolution itself off `waitsOf(before)` for `approvedWaitId`.

`task_view` clears the hold only for `Approve` (`packages/projector/src/task-view.ts:598`). Add `ContinueConflict` to that condition, or the board keeps drawing a resolved wait. `packages/projector/unit/task-view-rebuild.test.ts` runs on in-memory SQLite (its `:12`), so a unit test can pin it. A deployed board needs `lingtai projection rebuild task_view`. `GrantFixRound` has the same gap at that line; it is not this ticket's, so leave it alone and say so in the commit body.

### 3. The continuation (`packages/conductor/src/conduct.ts:980-1017`)

`granted` (`:980`) is already true, because `grantRef` is set, so `next` is `implement`, `at`/`atRef` re-cut at `headSha` on `ref` (`:2324`), and `continuationRound(runEvents, true)` buys the next round.

`provisionWorktree` refuses a moved ref (`packages/repo/src/worktree.ts:159`). The `:2318-2322` comment says so: *"`provisionWorktree`'s own `at` check refuses rather than silently taking a branch that has moved since."* That is the head recheck at continuation time, and it fires before any dispatch. Cover it with a test; do not rebuild it.

Three additions:

- **`priorGrant` (`:981-986`) counts `ContinueConflict` too.** That is the line that makes *"the same grant cannot authorize a later conflict"* true. With `grant` set, `runPass` caps rounds at `roundsSpent` and restarts at `restartsSpent` (`pass.ts:1162-1166`). A second conflict on the merge lane therefore finds `fix-lines` excluded by `CeilingReached`, escalates, and becomes a new `ProposedEscalated{MergeConflict}` wait with new shas. Apply the cap in **both** cases, exhausted or not. The person authorized one round for these hunks, not the recipe's remainder.
- **The `grant` brief.** Do not route this through `grantCriterion`. It returns `null` for `MergeConflict` on purpose, and making it non-null would offer `GrantFixRound` on conflicts, which 0118 §1's table does not allow. Build the `SentBack` here instead: `{ why: 'A person confirmed the intended behavior of every conflicting hunk.', asked: null, printed: { step: 'merge', detail: paths.join('\n') } }`. `fixRound` already reads a printed `merge` as a conflict (`:3478-3483`); `grantCriterion`'s comment says the same: *"`fixRound` reads a printed `merge` as a conflict and treats the detail as its paths."* Put `conflict: { baseSha, hunks }` on the continuation object beside `grant`.
- **`fixRound` merges the confirmed sha, not the branch name.** Today it passes `base`, the recipe branch name from `:703`, into `{ on: 'conflict', base, paths }`. When `continuation?.conflict` is set and `from === 'merge'`, pass `continuation.conflict.baseSha` and the hunks. Any merge fix round on that pass is the granted one, because the cap above leaves no automatic round.

**The decision the ticket does not make: pin the merge to `baseSha`, and recheck the base at continuation.** The agent edits exactly the conflict the person read, so it merges `baseSha` and never commits nobody confirmed. 0118 §8 (*"If the base or head moves before continuation, the confirmation is stale"*) is checked twice: before the append (check 3), and again when the continuation is about to claim, because the base can move in between. A moved base there dispatches nothing and spends no round. It appends a new `WaitStarted{MergeConflict}` against the new tip (same run, same head), which moves the lifecycle from `approved` back to `blocked`; returning without a wait would strand the ticket in `approved`, which every later claim declines. A person confirms again, and the old confirmation grants nothing for the new base. If the tip cannot be read, nothing is appended and the next attempt retries. No new wait kind is needed.

### 4. The brief (`packages/conductor/src/fix.ts`)

Widen the conflict refusal (`:474`) to `{ on: 'conflict'; base; paths; confirmed?: readonly ConfirmedHunk[] }`. Add one section to `conflictHalf` (`:635`), *"What a person confirmed"*, listing every hunk by `path:line`:

- a `Divergent` hunk carries its `behavior` word for word;
- a `Mechanical` hunk is marked mechanical.

Say once that the confirmed behavior is the authority over both sides, and that a hunk git produces which is not on the list is not covered and must be reported, not guessed. Leave everything else in `conflictHalf` alone. Its *"What counts as done"* already sends the result back through the steps.

## Exhaustion is read off the log, not off the recipe

`resolveWait` holds no recipe and must decide before the append. The fact it needs is on the run's stream: the last `PassRouted` (`packages/domain/src/events.ts:1133`) whose `offer.proposal` is this `MergeConflict` (same `headSha`). Rounds are exhausted when that offer's `unavailable` (`packages/domain/src/routing.ts:57`) holds `fix-lines` with `because: CeilingReached{ceiling: 'rounds'}` (`packages/domain/src/route.ts:26`). Add this to `continueConflictRefusal` as a fourth argument, `roundsExhausted: boolean`, with the two new refusals `GrantRequired` and `GrantNotNeeded`, and compute the boolean in a small pure helper in `@lingtai/domain/wait` over `runEvents`. A prior grant on the run caps `roundLimit`, and the router records that cap as `CeilingReached`, so this one read covers both cases.

In the log, `fix-lines` excluded on that `PassRouted` should line up with `WaitResolved.resolution.grantExtraRound === true` on the ticket stream.

## Agent failure

There is nothing new to build here. The continuation is an ordinary pass from `implement`, so a crash, an empty diff, a red `build` or a `review` refusal each ends at the wait that path already produces. A refusal ends at a person because of the cap, never at another automatic round. Nothing reaches `merge` without walking `build` and `review` first. Pin that with a unit test rather than an argument.
