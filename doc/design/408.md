## Design: #408 — the conflict as fields, and a defect with a reason of its own

### 1. The new reason is `'unexpected'`, and it changes routing

The lane already calls this path by that name: the function is `unexpected` (`packages/repo/src/integrate.ts:267`), and both defect paths write the detail as `the integration failed unexpectedly: …` (`:268`, `:460`). Add `'unexpected'` to `RefusalReason` (`packages/domain/src/events.ts:133`). Give it a doc comment in the same style as `push-rejected`'s. Write it at all three places that use `'conflict'` today for something that is not a conflict:

- `:269`, the `refuse(...)` inside `unexpected`;
- `:270`, the `catchAllDefect` fallback that builds an `IntegrateResult` without an event;
- `:460`, the `RepoFailed` catch.

**This is a change in behaviour, not only a new label.** Today a defect reaches `directionOf` (`packages/conductor/src/pass-steps.ts:613-622`) as `because: 'conflict'`. `directionOf` routes that to the `conflict` judge. `conduct.ts:2766-2770` then builds a `{ on: 'conflict', base, paths: said }` fix round, so an agent is paid to resolve conflict markers that do not exist, with a "paths" string that is a stack message. After the change, `'unexpected'` falls through to `null`, so a person is next. That is the right answer: the doc above `directionOf` says the reasons that return `null` "stop the lane before the diff is what is in doubt". Do not add `'unexpected'` to `JudgeWhen` (`packages/recipe/src/recipe.ts:1286`).

**A failed merge that git reports with no unmerged paths is also `'unexpected'`.** Today, when `diff --diff-filter=U` prints nothing, `:409` falls back to `mergedIn.left.detail` and still says `conflict`. In a worktree Lingtai has just cut, a merge that fails with nothing unmerged is git failing, not the branch conflicting, and triage (0118 §8) has no path to read. So the rule is:

- **`conflict`**: the merge failed and at least one path is unmerged. The event always carries `paths`, `baseSha` and `headSha`.
- **`unexpected`**: the merge failed with no unmerged paths. It carries none of the three fields.

### 2. The fields

In the schema (`events.ts:1140-1145`):

```ts
paths: z.array(z.string()).optional(),
baseSha: z.string().optional(),
headSha: z.string().optional(),
```

- **No `SCHEMA_VER` bump and no upcaster.** An optional field added beside the existing ones has precedent: `20f44e81` added `usage: Usage.optional()` to four types without either. Events already on the log still parse, and that is the third Done-when box.
- **`paths` is an array.** It is never clipped and never joined into `detail`. The 2,000-character clip at `:232` stays on `detail` only.
- **`detail` keeps its current prose.** `apps/board/src/lib/history.ts:283` and `packages/projector/src/task-view.ts:673` print `${reason}: ${detail}` and should not change.

Where the values come from, at the conflict point (`:398-412`):

- **`baseSha`** is `localBase` (`:375`), already in scope. It is the base *this* attempt merged against. Inside the `LOST_PUSHES` loop, each attempt fetches again, and the refusal belongs to the attempt that conflicted, so a sha captured earlier would be wrong.
- **`headSha`** is `at(['rev-parse', options.branch], mirror)`. Do not use `options.headSha`. The schema's word is "the side git merged", and that is the ref `git merge` was handed after the fetch at `:333-342`. On the conductor's path the two are equal, because `land` force-pushes `on.onSha` first (`conduct.ts:1972-1999`). On `approve.ts`'s path nothing guarantees it.
- **`paths`** is the `--diff-filter=U` output split on `\n`, with empty lines dropped.

Widen `refuse` with an optional third argument holding the extra payload fields, spread into the `append` call. Do not add a second `refuse`. `IntegrateResult` (`:95`) does not change. `conduct.ts:2763` still feeds the fix prompt from `detail`, and moving it onto `paths` is #388's work, not this ticket's.

### 4. Tests, and what cannot be a unit test

**The first Done-when box cannot be a unit test as written.** `integrate()` calls `gitEffect` directly (`integrate.ts:68`), with no seam for injecting it. A conflicted merge needs the `git` binary, which makes it integration under 0060 §1 (`vitest.config.ts:7-12`). `packages/repo` has no `unit/` directory at all. Do not add a git seam just to reach the box. Split it instead:

- **Integration, verified after the merge (T11):** extend `packages/repo/integration/integrate.test.ts:127`, *refuses a conflict with the file that conflicted*. Assert `paths` equals `['README.md']`, `baseSha` equals the develop commit it pushed, and `headSha` equals `agent/2`'s tip. In the test at `:414`, the `toBe('conflict')` at `:429` becomes `'unexpected'`. Nothing inside the pass will run either test.
- **Unit, what stands in before the merge:** in `packages/domain/unit/integration.test.ts`:
  - `parsePayload('IntegrationRefused', …)` accepts a payload without the three fields.
  - It accepts a payload with them.
  - It accepts `reason: 'unexpected'`.
  - It rejects `paths` given as a string.

  If the path-splitting is pulled into a small exported helper in `integrate.ts`, it can get a `packages/repo/unit/` test too. The include glob `{apps,packages}/*/unit/**` (`vitest.config.ts:72`) picks it up without any config change.

Say this in the PR body, so a reviewer does not read the unchecked first box as forgotten.

### 5. Docs

`doc/reference.md:825-832` argues that `conflict` and `verify-failed` are "one thing at two depths". That stays true, so leave it. No ADR is contradicted: `RefusalReason`'s own comment (`events.ts:128-131`) is about making each failure name itself, and this follows it.
