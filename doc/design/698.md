# Design: Java detector (#698)

## Where it goes

The Go detector has already landed. `DETECTORS = [nodeDetector, pythonDetector, goDetector]` is at `apps/cli/src/detect-setup.ts:540`, and the ticket's `:468` predates it, so there is nothing to rebase. Add `javaDetector: StackDetector` after `goDetector` (it ends at `:538`) with `stack: 'Java'`, and put it fourth in that line. `detectSetup` (`:548`) already makes the first present stack win and names each later one (`${other.stack} is also at the root; ${first.stack} was used`), so `package.json` + `pom.xml` needs no new code. Node wins, and the note says `Java is also at the root; Node was used`.

## Presence, and which tool wins

Read the paths only through `hasOrUnknown` (`:216`, "Tri-state: `has` rejecting is 'could not tell', never absent"). Ask about Gradle first, because Gradle wins:

1. If `build.gradle` or `build.gradle.kts` is present, the stack is **Gradle**. `because` is `<file> is at the root`, naming the first one found in that order. If `pom.xml` is also present, add the note `pom.xml is also at the root; <file> was used`. That is the same wording as the lockfile note (`:129`) and the golangci note.
2. If neither Gradle file is present and either one answered `'unknown'`, Gradle might be the winner and we can't tell. When `pom.xml` is present: `presence: 'present'`, no install, no build, and the note `could not tell whether <file> is at the root`. This is the Go rule from `:509`: "An earlier file that may exist decides, so a later one cannot stand in for it". When `pom.xml` is not present: `presence: 'unknown'` with that note.
3. Otherwise `pom.xml` decides: present means **Maven**, `'unknown'` means `presence: 'unknown'` with `could not tell whether pom.xml is at the root`, and absent means `absent`.

**A Gradle script is neither read nor checked.** It is a program only Gradle can parse, so once `build.gradle` or `build.gradle.kts` is present Gradle is chosen and #436's one-time try finds a broken script (the operator's answer on #698 narrowed the ticket's "does not parse" edge this way). `pom.xml` is read and checked for **balanced tags only** (no XML parser is a dependency of `apps/cli`): a file that passes may still be invalid XML, and the try finds that too. A `pom.xml` that cannot be read gets `pom.xml could not be read`; one with unbalanced tags gets `pom.xml has unbalanced tags`; neither suggests anything.

## The wrapper

After choosing the tool, ask `hasOrUnknown` about `mvnw` or `gradlew`:

- **Present** gives `./mvnw` / `./gradlew`. Whether the file is executable is not checked (ticket edge; #436 finds it).
- **Absent** gives `mvn` / `gradle`.
- **`'unknown'`** suggests nothing (no install, no build) and adds `could not tell whether mvnw is at the root`. Falling back to `mvn` would read the unknown as absent, which is the thing `EMPTY_SETUP_READER`'s comment (`:27`) forbids.

The commands are exactly the ticket's strings:

- **Maven**: install `<mvn> -B -q dependency:go-offline`; build `[{ name: 'test', run: '<mvn> -B test' }]`.
- **Gradle**: install `null`; build `[{ name: 'test', run: '<gradle> test' }]`. Add the note `Gradle has no separate install; <gradle> test resolves dependencies itself`, so an empty install question has its reason printed.

**The timeout note.** It goes on every Java finding that suggests a build: `a cold <Maven|Gradle> build downloads its dependencies first and can exceed a run's default timeout of 15m — set timeout: on the command in the recipe if the trial runs out`. The `15m` comes from `runPlugin`'s `timeout: z.string().default('15m')` (`packages/recipe/src/recipe.ts:125`). Write it as a literal; don't import the recipe package for it.

## The PATH probe: this needs a change outside the detector

`printFound` (`apps/cli/src/setup-build.ts:235`) probes `c.tool ?? c.run.split(' ')[0]`. It hard-codes `{ tool: undefined, run: detected.install.run }` for the install (`:247`). The real probe, `toolOnPath` (`apps/cli/src/recipe-flow.ts:102`), does `existsSync(join(dir, name))` for each PATH dir. Asked about `./mvnw`, it looks for `<dir>/mvnw`, answers false, and would print `./mvnw is not on this machine's PATH`. That claim is false, and it names the wrong thing: the wrapper downloads Maven or Gradle itself and needs `java`.

So:
- Give `DetectedSetup.install` the same optional `tool?: string` that build entries already carry (`detect-setup.ts:46`). Make `printFound` use `detected.install.tool` instead of `undefined`.
- Wrapper commands set `tool: 'java'` on both the install and the build entry. Bare `mvn` / `gradle` set nothing; the first word is already right.
- Extend the comment at `setup-build.ts:241` with one clause: a wrapper's tool is `java`.

## Tests

In `apps/cli/unit/detect-setup.test.ts`, beside the Go cases, use its fake reader:

- Maven with `mvnw` and without it, with exact `install.run` and `build[0].run` strings, and `tool: 'java'` only with the wrapper.
- Gradle with `gradlew` and without it, with both `build.gradle` and `build.gradle.kts`. `install` is `null` and the no-install note is there.
- `pom.xml` + `build.gradle`: Gradle is used and a note names `pom.xml`.
- `has('build.gradle')` rejects while `pom.xml` is present: nothing is suggested and the note is there. `has('mvnw')` rejects: nothing is suggested and the note is there.
- **Never `verify` or `check`.** For each of the four tool/wrapper cases, assert that no `install.run` or `build[].run` matches `/\b(verify|check)\b/`.
- The timeout note names `15m`.

In `apps/cli/unit/setup-build.test.ts`, beside *the gofmt check probes gofmt* (`:644`): a Maven wrapper detection with `onPath` false for `java` logs the `java …` line, and no line names `./mvnw`.

All of this is unit-level. No test runs `mvn` or `gradle` (out of scope), so `pnpm test` covers it fully.

## Docs

Add a Java clause after the Go clause in the README's setup paragraph (`README.md:60-65`): `pom.xml` gives Maven (`dependency:go-offline`, then `test`), and `build.gradle(.kts)` gives Gradle (`test`, no separate install). The wrapper is used when `mvnw` / `gradlew` is at the root, and Gradle wins when both are present.
