# #1299 — the shape of the change

Three places change: `packages/agent/src/acp-session.ts` (the profile), `packages/agent/src/acp.ts` (the run), and `apps/cli/src/doctor.ts` (the new row). The conductor does not change. It already writes `usage: outcome.usage ?? []` into `RunSpent` (`packages/actions/src/agent-action.ts:101`, `packages/conductor/src/conduct.ts:3497`). `outcomeOf` already writes `costUsd: null` (`acp.ts:296`), and the test already checks it (`acp.test.ts:183`).

## 1. Usage: where it is read from

**Make sure the SDK actually passes `usage` through. Do not assume it does.** `usage` exists only in the SDK's *unstable* schema. The `PromptResponse` in v1/unstable has `usage: defaultOnError(zUsage.nullish(), …)`. The stable v1 one is `z.object({ stopReason, _meta })` (`node_modules/.pnpm/@agentclientprotocol+sdk@2.8.0_zod@4.5.4/.../dist/v1/schema/zod.gen.js:1120`), and a plain `z.object` drops keys it does not know. We import `client` from the package root (`acp-session.ts:17`), and the root export is `./dist/v1/stable/acp.js`. The stable bindings register `session/prompt` with a request validator only (`dist/v1/stable/bindings.js:553`). That suggests the client gets the response unparsed, but nobody has checked.

The unit test in `acp.test.ts` uses `fakeAgent`, which goes through the real SDK. Have the fake answer `{ stopReason: 'end_turn', usage: {…} }` and assert the mapped entry comes out:
- If `response.usage` arrives, read it from the `.then((response) => …)` at `acp.ts:518`.
- If it arrives stripped, read it from the raw message in `tap` (`acp.ts:388`, which already sees every message before the SDK). Take the JSON-RPC response whose `result` carries `stopReason`.

Either way the test makes it true. A green run without that test proves nothing.

**Store the usage as soon as the response arrives, before `settled(...)` and before any `finish`.** Add a `let usage: Usage = []` next to `calls`, and give it to `outcomeOf` the same way `turns` is passed, so that every `finish` call carries it. Then:
- A turn that stopped at the wall or at the turn limit still keeps whatever usage the agent sent with its `cancelled` answer.
- A run that ends before any answer arrives gets `[]`.

## 2. The mapping lives on the profile

`AcpProfile` gets a new field: `tokens(usage: Record<string, unknown>): { tokens: TokenCounts; note?: string }`. It is a pure function. Import `TokenCounts` with `import type` from `@lingtai/domain`, because `acp-session.ts` promises to load nothing of Lingtai (`acp-session.ts:5-8`). The Antigravity profile will supply its own function (inputs that do not include the cache) without touching this one.

Add a shared helper `count(v)`: it returns the number when `v` is a finite number ≥ 0, and `undefined` for anything else (`null`, missing, a string, NaN). `null` matters here: the unstable type declares `cachedReadTokens?: number | null` (`v1/unstable/schema/types.gen.d.ts:3217`), and a `null` must stay absent, never become `0`. That is 0110 §3, as quoted at `spend.ts:7`: *"absent means this runtime did not say."*

Copilot:
- `fresh`: absent if any of the three inputs is absent. Absent if the result is negative, and in that case return a `note` with the three numbers, which `acpRun` writes with `request.log?.note('usage', …)`.
- `cacheRead`, `cacheWrite`, `output`: each copied directly from its own field.
- No `reasoning`: `thoughtTokens` is inside `outputTokens`.
- No `model` on the entry. This holds even when `request.model` was sent through `session/set_model` (`acp.ts:490-494`): that is what we asked for, not what the agent reported, and 0.16.md:73 records a model only *"where the agent names it"*.

**When the result has no tokens at all, `usage` is `[]`, not `[{ tokens: {} }]`.** An empty entry gives the reduce nothing to price, and it would look like a line on the bill.

## 3. Turns: one stop with a reason, not a second `wallHit`

Counting goes where `calls += 1` already is (`acp.ts:413`). When `request.limits.turns !== undefined && calls > request.limits.turns`, the run stops. The stop is the same sequence `onWall` already runs: `session/cancel`, wait `cancelWaitMs`, SIGTERM the group, wait `killWaitMs`, then `finish`.

**The trap: `wallHit` is checked in six places, and every one of them finishes as `timeout`.** They are at `acp.ts:422`, `448`, `477`, `521`, `525` and `539`. If the turn limit simply set `wallHit = true`, a turn-limited run would come out as `timeout`, which the ticket's edge rules out.

Replace the boolean with `let stopping: { kind: 'timeout' | 'out-of-turns'; detail: string } | undefined`, and make `onWall` call a general `stop(reason)`:
- **The first reason wins.** A wall that arrives during a turn stop's cancel wait does not rename it, and the reverse holds too.
- Every one of the six sites finishes with `stopping.kind`.

Write the detail the way Claude Code does (`claude-code.ts:370`): ``${calls} turns, and the recipe allows ${limits.turns}``.

Two things to leave as they are:
- **The tool call that went over the limit is still recorded.** `ledger.apply` and `record` run as they do now. The ADR 0016 §6 note at the top of `acp.ts` says Lingtai refuses no tool call, so the stop is a cancel and a kill. It is never a permission answer of `cancelled`.
- `outcome.turns` is `calls`, which is limit + 1 on this path.

The `unlessWall` guard (`acp.ts:476`) only runs before the prompt, so a turn stop cannot reach it. Keep it working off `stopping !== undefined` anyway, so it has a single meaning.

Change `COPILOT_CAPABILITIES.enforces` to `['wall', 'turns']` and delete the *"Turns and usd are the next ticket's"* comment (`acp.ts:49-50`). Two things depend on this value:
- `acp.test.ts:430-437` asserts `['wall']`. Update it.
- `apps/cli/src/agents.ts:358-364` writes `turns: unbounded` for any writer whose capabilities lack `turns`. From now on copilot gets the schema's `turns` number instead. This is intended. If an `agents.test.ts` case expects `unbounded` for copilot, update that case.

`limitsRow` (`doctor.ts:2651`) handles copilot without changes. Turns show as applied. A declared `run.usd` stays `fail`, because copilot still does not enforce `usd`, and the docstring at `doctor.ts:2614-2628` explains why that red must not be softened.

## 4. The doctor row

**Put it inside the loop over `needed` (`doctor.ts:3215`).** That map already covers `runtime.agent`, each step's `agent:`, and each judge that names a runtime, de-duplicated. That is exactly *"each ACP runtime its recipe names."* After the auth row for an agent, push the unpriced row when the agent is an ACP runtime.

**Decide "is ACP" from an export, not from a name written in `doctor.ts`.** Export `ACP_PROFILES: Partial<Record<RuntimeId, AcpProfile>>` (copilot → `COPILOT_PROFILE`) from `acp-session.ts`, re-export it from `packages/agent/src/index.ts`, and have both `RUNTIMES.copilot` (`runtimes.ts:94-100`) and doctor read it. When Antigravity is added to that map, it gets the row automatically.

The row:
- **Name:** `runtime: <project> <agent> unpriced`.
- **Status: `info`.** By `doctor.ts:186-188`, `info` means *"true, and there is nothing to do … never counted, never a non-zero exit and never a restart gate."* `warn` would be yellow on every copilot project permanently, the always-on trap that `doctor.ts:179-184` describes. The only fix is a rate row plus a model the agent never reports, and that is out of scope.
- **Detail:** say that `costUsd` is not reported and no model is named, that `run.usd` and the day ceiling do not count this agent's runs, and that it is bounded by `turns <n|unbounded>` and `wall <w>` taken from `ceilingOf(recipe)`. Add `needed by …` keys the same way the auth row does.

**When the recipe cannot be read:** this code only runs after `resolved` succeeds. A recipe that fails to resolve already gets its own failing row earlier in this function. Leave that row as it is and add nothing.

## Checks that stand in for an integration run

Every item in the ticket's Done-when list can be checked with a unit test:
- **Mapping:** test the profile's `tokens` function directly, using the evidence numbers (expected `fresh` is 21) and the absent, `null` and negative cases.
- **Turns:** use `acp.test.ts`'s `fakeAgent` with `limits.turns: 2` and three `tool_call` updates. Assert `failure.kind === 'out-of-turns'` and that `signalGroup` recorded `SIGTERM` then `SIGKILL`. The existing wall test at `acp.test.ts:271` is the template.
- **Both reasons together:** a turn stop followed by the wall timer firing during `cancelWaitMs` must still finish as `out-of-turns`.
- **Doctor:** call the new row function directly with a resolved recipe that names `copilot`. No database is needed.

No `async` and no `Effect.run*` anywhere: chain the SDK's promises as the file already does (`acp.ts:18-20`).
