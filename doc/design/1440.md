# #1440: the shape of the change

## Where it goes

The new read is a method on the Effect port only. There is no promise twin and no face.

- **`ProjectionsPort`** (`packages/projector/src/store.ts:415`) gets one method, beside `tasks` at `:429`:
  - `taskStates(query: { project: string; issues: readonly string[] }): Effect.Effect<TaskState[]>`.
  - Each row is `{ issue, state, lastAttemptAt, repairPending }`. That type already satisfies `BackoffInput` (`packages/conductor/src/queue.ts:122-130`), so `heldUntil` takes it unchanged.
  - `project` is required, not optional like `TaskQuery.project` (`store.ts:243`). A read that leaves the project out would match the same issue number in every project, which is the cross-project collision the ticket's Edges rule out.
- **Do not add it to the promise `ProjectionStore` or to `store-face.ts`.** Every face in that file needs an entry in `packages/domain/unit/effect-ratchet.faces.json` (the `tasksFace` entry is at `:469-474`). `effect-ratchet.test.ts:10-13` describes a face as one "kept where a host reads through it (`0101 §7`) or under a named issue still open". Nothing would read through this face: the contract fixture already exposes the port (`packages/projector/test/contract.ts:116-117`: *"The port `store` is a face over"*), so the tests can call `f.port.taskStates(...)` directly. Adding the face would also add an exemption, and a reviewer would treat that as raising the ratchet.
- **The two store implementations:**
  - Postgres (`packages/projector/src/postgres.ts`): an explicit column list, `where project = $1 and issue = any($2::text[])`. Follow the `backlog` `taskIds` precedent at `:497-500`.
  - SQLite (`packages/projector/src/sqlite.ts`): `issue in (?, …)`, following the same precedent at `:757-760`. Parse the values with the helpers `toCard` already uses: `parseAt` and `parseBool` (`sqlite.ts:260-262`), as `repairPending` does at `:331`.
  - Neither has a retention clause or an `order by`. The selector sorts offers, not rows (`queue.ts:113-118`).
  - Neither calls `toCard` or `mapRows`. The four columns are named, so a dropped column is a driver error, not a `ProjectionShapeError`. That is why the error type is `never`.
- **Missing table: keep each store's current `tasks` behaviour.** Postgres uses `rows` (`postgres.ts:324`), which fails. SQLite uses `allOrEmpty` (`sqlite.ts:452-459`), which returns `[]`. Making the two agree is a different change from this one.
- **`readTaskStatesEffect`** goes in `packages/projector/src/task-view.ts` beside `readTasksEffect` (`:1043-1053`). It uses `Effect.fn('projector.readTaskStates')` and `withStoreEffect({ url, max: 1 }, …)`, and is exported from `packages/projector/src/index.ts` (next to `:108-109`).
  - **The empty-input check comes before `withStoreEffect`.** No issues means no store is opened and no connection acquired, not just no query. Each store implementation also returns `[]` for empty input, the way `backlog` does at `postgres.ts:498` and `sqlite.ts:758`, so the contract can check it.
  - There is no promise `readTaskStates`: it would be a new `Effect.runPromise` in a package that sits at 0/0 (`effect-ratchet.baseline.json:4`).

## `selectRunnableEffect`

- Rank kinds and filter the offers by kind **first**. Then read only the distinct refs of the offers that survive. Offers dropped by kind are thrown away at `queue.ts:101` today whatever their row says, so the output is identical. An offer with no runnable kinds then never reaches the database.
- Yield `readTaskStatesEffect` directly. Delete the `Effect.tryPromise(readTasks)` wrapper (`queue.ts:87-95`) and the `readTasks` import (`:14`). Build the `Map` the way `:96` does now.
- Duplicate offers stay duplicates in the output. Only the list of refs sent to the store is deduplicated.

## The decision the ticket doesn't make: a read failure is now a defect

Today `tryPromise` turns any rejection into a failure in the error channel (`queue.ts:94`, `catch: (error) => error`). On the port, *"A driver or SQLite error is a defect"* (`store.ts:403`, `:412`). If the read is yielded directly, a database error reaches `selectRunnableEffect` as a `Die`, not a `Fail`.

**Accept that, and don't convert it back.** Every caller treats the two the same way:

- **Board:** wraps the promise `selectRunnable` in `Effect.tryPromise` (`apps/board/src/lib/board.ts:1050-1060`). `selectRunnable` rejects with the squashed cause either way (`store-face.ts:7-9`: *"the `Fail`'s error itself, else the `Die`'s defect itself"*).
- **Conductor:** `schedule.ts:283` uses `Effect.promise`, which turns any rejection into a defect anyway.
- **`lingtai status`:** `apps/cli/src/status.ts:554` yields it inside `readStatus` (`:440`), and that file has no `catch`, `either` or `exit` anywhere.

Keep the signature `Effect.Effect<Runnable[], unknown>`. Do **not** add `catchAll`, `orElseSucceed` or `catchAllDefect` to turn the defect back into a failure, and above all not into `[]`. The failure test should assert that the run did not succeed and carries the injected error (`Exit.isFailure` is true for a `Die` too, and so is a rejection of `selectRunnable`). It should not assert that the cause is a `Fail`.

## Tests, and which of them can run in this pass

- **Selection rules: unit, in `packages/conductor/unit/`.**
  - `queue-pr-fix.test.ts:5` mocks `@lingtai/projector` as `{ readTasks: async () => [] }`. After this change `queue.ts` imports `readTaskStatesEffect`, which that mock leaves undefined, so the file goes red. Change the mock to `readTaskStatesEffect: () => Effect.succeed([])`.
  - Put the new cases in a sibling file with the same kind of mock. The mock records the refs it receives and returns fixed rows, `Effect.die(err)` or `Effect.fail(err)`.
  - Cases:
    - a missing row is eligible;
    - every non-queued state is excluded;
    - queued inside the backoff window, outside it, and exactly at it: `until > now` (`queue.ts:150`), so equality means not held;
    - repair-pending;
    - duplicate offers;
    - read failure;
    - the kind-filtered, deduplicated ref list is what the mock receives;
    - empty or all-filtered offers never call the read.
- **The read itself: unit, using in-memory SQLite.**
  - Do it the way `packages/projector/unit/backlog-task-ids.test.ts:46` does: `openSqliteProjections(':memory:')`, but call the port from `makeSqliteProjections` (`sqlite.ts:433`).
  - Cases:
    - a closed row whose `closed_at` is far beyond `DEFAULT_RETENTION_DAYS = 2` (`task-view.ts:87`) is still returned;
    - another project's row with the same issue is not;
    - `'12'` does not match `'120'` or `'012'`;
    - empty input returns `[]`;
    - each row carries exactly the four fields.
  - This is what stands in, inside the pass, for the Postgres claims.
- **The same read cases in `packages/projector/test/contract.ts`,** through `f.port`. That is the only check of the Postgres `any($2::text[])` SQL, and it runs only under `pnpm test:integration`, which takes 803 s. So the Postgres store is **unverified until after the merge**; it is checked on the `integration (postgres)` leg. Add the cases and don't run that suite.
- `packages/conductor/integration/queue.test.ts` goes on exercising the whole path with `selectRunnable` end to end, also after the merge.

## What doesn't change

- `selectRunnable`'s signature and all three callers.
- `status.ts:561`'s own `readTasksEffect` for arms.
- `heldUntil` and the sort.
- Spans: `queue.select` stays as it is. The `Effect.fn` name replaces `projector.readTasks` one for one, and there is no new `tracedEffect`. `apps/board/unit/queue-stages.test.ts:167` stubs `select`, so it isn't affected.
- No schema change and no index: `(project, state)` (`task-view.ts:219`) already narrows by project. No ADR is touched. 0101 §6 is what this change follows.
