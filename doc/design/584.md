# #584: the shape

## Which lane: the whole installation's, unfiltered

The task page's route takes only `params` (`apps/board/src/app/task/[id]/page.tsx:844`). It has no `?project=`, so it cannot know which filter the reader came from. **Use `readTasks({})`**, which is what `/` reads with no filter (`apps/board/src/lib/board.ts:992`). Do not use the `readTasks({ project })` that `loadCurrentTriageStatus` already makes (`apps/board/src/lib/task.ts:1774`).

The difference shows. The store sorts by **project first** and only then by how long a card has waited:

```
order by t.project,
  -- "Waiting on you" is oldest first ...
  case when t.state = 'waiting' then t.updated_at end asc nulls last,
```

That is `packages/projector/src/postgres.ts:305-309`, and SQLite has the same order at `packages/projector/src/sqlite.ts:672-674`. So *next* at the end of one project's waits is the first wait of the next project, exactly as the unfiltered board lists them. That is correct, and it is what "walk every wait" asks for. Do not re-sort, and do not group by project yourself. The order lives in that SQL. `toColumns` leaves Waiting alone on purpose: *"`readTasks` orders the other lanes deliberately — waiting by how long it has waited … none of that is this function's to undo"* (`board.ts:1188-1190`). This change is a second reader of the same rule and must not touch it.

That `updated_at` is the store's sort key. It is not yours. "Nothing reads an event timestamp" is a claim about the new code, and the new code never looks at `updatedAt` on a card.

## What counts as "waiting": the board's column

Filter with `COLUMN_OF[card.state] === 'waiting'` (`board.ts:493-511`), not `state === 'waiting'` written out again. `COLUMN_OF` is *"the whole mapping, said once"*. If a state is ever added to the lane, the links follow it.

**Whether this ticket is waiting is decided by the same list**, not by `task.standing.state === 'blocked'`. The ticket is waiting if and only if its `taskId` is in the filtered list. Otherwise the page can be in an impossible state: the standing fold says blocked while the projection has already moved the ticket, and you would compute neighbours of a ticket that is not in the list. Reading one list makes "someone else resolved it mid-view" fall out naturally. The next render finds the ticket missing and draws the not-waiting case.

## One pure function, in `board.ts`

Put it next to `toColumns`, because it reads `COLUMN_OF` and the board's order:

```ts
export interface WaitingNeighbour { taskId: string; issue: string; title: string }
export function waitingNeighbours(cards: readonly TaskCard[], taskId: string):
  { previous: WaitingNeighbour | null; next: WaitingNeighbour | null }
```

- Ticket is in the lane at index `i`: `previous = lane[i-1] ?? null` and `next = lane[i+1] ?? null`. Nothing wraps.
- Ticket is not in the lane: `previous = null` and `next = lane[0] ?? null`. Because the ticket is absent, `lane[0]` is already "the first other than this one".

Return only `taskId`, `issue` and `title`. The header needs nothing more, and the full card would put `TaskCard` into `TaskDetail`.

## Wiring

- **`loadTask`** (`task.ts:1783`): add `readTasks({})` to the existing `Promise.all` at `task.ts:1802-1807`, so it costs no extra round trip. Then set `waiting: waitingNeighbours(cards, taskId)` on the `TaskDetail` (`task.ts:943`). The page is a dynamic route that `<Follow>` re-renders on every append (`page.tsx:849-856`), so "compute per render" means nothing gets cached, memoised or held in a module variable.
- **An unbuilt projection** means no links, not a broken page. Copy `loadBoard`'s posture: catch `/does not exist/` and return `[]`, rethrow anything else (`emptyIfUnbuilt`, `board.ts:1124-1127`). That function is private, so export it, or catch inline the same way. Never treat a failed read as an empty lane silently for any other error.
- **Render** in `TaskBody`'s `.bar` (`page.tsx:764-777`), after `<Coords>`. Draw `← #561 title` and `#572 title →`, using `<Link href={`/task/${encodeURIComponent(n.taskId)}`}>`, the pattern at `apps/board/src/app/backlog/page.tsx:33`. A null side renders nothing at all: no disabled placeholder and no empty element. Label them in words ("previous waiting" / "next waiting") in the `title` or an `aria-label`, so the arrows are not the only meaning. Truncate a long title with CSS rather than slicing the string.
- **Test fixtures:** `apps/board/unit/task-page.test.tsx:87` builds a `TaskDetail` by hand, so the new field needs a default there, `{ previous: null, next: null }`, or every existing render breaks typecheck.
