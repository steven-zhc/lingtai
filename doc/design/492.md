## Design note for #492: turn off background tasks in every claude-code spawn

**Where it goes.** The change goes in one file, `packages/agent/src/claude-code.ts`. Today `run` passes `request.env` straight to `spawn` (`:402–407`). Its comment says: *"Filtered, not inherited. The agent gets what the recipe allows plus the hook's wiring, and nothing else — one of the three real boundaries (doc/decisions-archive/0007)."* The hook's wiring is not added here. It is merged upstream, at `conduct.ts:2963`: `runnableEnv({ ...env.values, ...wiring.env })`. `runnableEnv` lets the project's own values win (`packages/agent-env/src/index.ts:157`: *"The project's own values win: a recipe that requires `PATH` meant it."*). So if the variable were added upstream like the wiring, a recipe that set it to `0` would win. The runtime has to add it **after** the request's env, in `claude-code.ts`, so that nothing the recipe says can turn it off.

**The shape.** Add a small exported pure function beside `claudeClose` and `usageFromModelUsage`, the two existing pure halves, pulled out so a unit test can reach them (`unit/claude-code.test.ts:1–9`). Something like `spawnEnvFor(env)`, returning `{ ...env, CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: '1' }`. Name the variable once, as a module constant, with a comment that cites #492 and says why the runtime rather than the recipe sets it. `run` then spawns with `env: spawnEnvFor(request.env)`, and the 0007 comment at `:403` gets one more clause: the recipe's env, the hook's wiring, and this one variable.

**Do not put the env on `Spawned`.** `invocation()` looks like the natural thing to test through, and the `--max-budget-usd` tests already do (`unit/claude-code.test.ts:158–183`). But `Spawned` (`runtime.ts:143`) carries only `command` and `args`. Conduct builds it at `conduct.ts:2964` so the run can be described on its stream, and the env holds the recipe's secrets. Widening `Spawned` to make this testable would put those secrets on the stream. Test the pure function directly:
- it sets the variable when the request's env is empty;
- it overrides a request env that says `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS: '0'`;
- it passes every other key through unchanged;
- its key set is exactly the input's keys plus this one. This last test is the unit-level claim for *"no other new variable"*.

**What a unit test cannot check.** No unit test can show that `run` actually uses the function. That would take a `fakeClaude` that dumps its environment, and that test belongs in `integration/claude-code.test.ts` (its `fakeClaude` is at `:54`; `:266` and `:297` already dump argv the same way). Add it there for after the merge. The pure-function test is what `pnpm test` can verify before the merge, and the one-line call site is small enough for the reviewer to read.

**What not to touch.**
- `checkAuth` (`:380`) runs no agent and needs no flag.
- Codex is not affected.
- `conduct.ts` and `runnableEnv` stay as they are. All three `.run({` call sites in `conduct.ts` (`:2215`, `:3041`, `:3268`) go through `Runtime.run`, so the one place covers all of them.
- `hook-config.ts`'s `env` is Lingtai's own `LINGTAI_*` names. This variable belongs to Claude Code and must not be renamed with that prefix.

**The real `claude -p` run** is a manual check before the commit. It is not a test, and it costs about one cheap prompt. Run Claude Code 2.1.302 with the variable set, in a scratch directory and not this worktree. Ask it, in one prompt, to:
1. start an `Agent` with `run_in_background: true` that sleeps briefly and writes a file;
2. start a `Bash` command with `run_in_background: true`;
3. report what each tool call returned.

Use `--output-format stream-json` so the tool calls and their results show. Quote the lines that show:
- whether the subagent's result came back inside the turn (foreground) or as a launched-in-background acknowledgement;
- whether background Bash was refused, quietly run in the foreground, or still backgrounded.

If background Bash is still allowed, say so plainly in the commit body. The ticket asks for the fact, not a fix: the 10-minute kill is about tasks still running after the last turn, and the background-Bash case would need a ticket of its own.

**After it lands,** it does nothing on the running daemon until `lingtai restart`. To check it on a real run afterwards, look for the stderr line `Background tasks still running 10m after the last turn` in a run log. Its absence on a run whose agent tried to delegate is the evidence, not the receipt's `success · exit 0`.
