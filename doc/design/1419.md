## Design note for #1419: what to draw while the PRs board loads

### Where it goes

**The constant goes in `lib/pr-board.ts`.** Add an exported `PR_COLUMNS` next to `Tone` (`pr-board.ts:28`): five `{ id, title, tone }` entries `as const`, in the order of today's array at `pr-board.ts:568-627`. Each column literal in that array then spreads its entry, followed by its own `count`, `cards`, `older`, `empty`, `note` and `unread`. Don't map over the constant there, because each column's fields are computed separately. Importing a value from this file is safe from any graph. The header says it is pure and that "the conductor stays out of this file so a client graph may import it" (`pr-board.ts:4-6`).

- `Tone` also contains `'queued'` (`pr-board.ts:28`), which is not one of the five columns. Type each entry's `tone` as `Tone` and leave `Tone` as it is.

**`PrBoardSkeleton` goes in `app/pr-columns.tsx`, beside `PrColumns`.** Keeping them in the same file keeps the class names in one place. That file already imports only types from `pr-board.ts` (`pr-columns.tsx:8`); it now also imports `PR_COLUMNS`. The skeleton:

- copies the `section.pr-col ${tone}` + `aria-label={title}` + `h2` structure from `Column` (`pr-columns.tsx:94-101`);
- renders no submitted banner, as the ticket's Edges section says;
- loops over `PR_COLUMNS` for the titles and never writes a title out itself.

`page.tsx:98` then swaps `<Skeleton shape="card" count={5} />` for `<PrBoardSkeleton />`. If `Skeleton` is no longer used in that file, drop the import at `page.tsx:22`.

### The decision the ticket doesn't make: how the two bars sit in the text

`.sk-bar` is `display: block` and gets its width only from the `sk-id`, `sk-title` or `sk-line` class (`globals.css:3655-3666`). Two consequences:

- **The count bar.** A plain `span.sk-bar` inside `span.pr-n` in the `h2` would drop below the title. When the real count arrives the heading would shrink back, which is exactly the jump this ticket is meant to remove. Don't use `<Skeleton>` here either: it renders a `div.skeleton` (`skeleton.tsx:24`), and a `div` inside an `h2` is invalid HTML. Instead, render a bare `<span className="sk-bar sk-n" aria-hidden="true" />` inside `.pr-n`, and add a `.sk-n` rule next to `.sk-id` (`globals.css:3663`): `display: inline-block`, a width of about two digits, and `vertical-align: middle`.
- **The strip bar.** Use a bare `<span className="sk-bar sk-line" aria-hidden="true" />` inside `p.pr-strip`. Don't use `<Skeleton shape="lines">`, which would put a `div` inside a `p`. Give it a width well under 100%, because the real strip is one short line (`pr-columns.tsx:128-130`). The paragraph's margin (`globals.css:3482`) keeps its height close enough. Judge it against `doc/milestone/0.16.0/team-mode/pr-board.html`; there is no number to match.
- **Each column's card.** This stays `<Skeleton shape="card" count={1} />`. It sits directly inside the `section`, which is a block, so the `div` is valid there.

The two bare spans carry no `aria-busy`. The `div.skeleton` in each column already marks the board as busy, and 0111 §15 rules out a label (`skeleton.tsx:21-22`: "The shape is the whole placeholder: no words, for anyone").

### The test

Add a `describe` to the existing `unit/pr-board.test.tsx`, which already renders `PrColumns` with `renderToStaticMarkup` (`pr-board.test.tsx:12,16`). Reuse the `text` and `count` helpers pattern from `unit/skeleton.test.tsx:7-8`. It asserts:

- the `aria-label`s of the `section.pr-col`s, in order, equal `PR_COLUMNS.map(c => c.title)`;
- each section contains exactly one `class="sk-card"`;
- with the tags stripped, the text is the five titles joined and nothing else.

Read the expected titles from `PR_COLUMNS`, not from string literals. That keeps the test true through a rename: a rename then moves the constant and the test with it. It also adds no markup snapshot, as the Edges section asks.

There is no IO, no `async` and no Effect anywhere in this change, so the effect ratchet doesn't move. All of it is covered by `pnpm test`; none of it needs `pnpm test:integration`.
