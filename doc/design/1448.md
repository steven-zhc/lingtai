# #1448: a new recipe declares a `findings` judge

## Where it goes

Three files write a new recipe's `steps.proposed`, and all three change in this ticket:

1. **`packages/recipe/src/answers.ts`: a new `findingsJudgeChanges(writer, currentProposed)` beside `landingChanges`.**
   - Give it the same shape as `landingChanges`: it takes the list as it stands and returns `RecipeChange[]` that writes `steps.proposed` with the judge entry appended.
   - The entry is `{ name: 'send findings back to the writer', judge: <writer>, when: 'findings' }`.
   - It returns `[]` in three cases:
     - the writer is `null` (nobody is signed in);
     - the writer `isImplementOnlyAgent` (`recipe.ts:1390-1392`);
     - the list already holds a `judge:` with `when: findings`.
   - Put it here because it is the one place both inputs import (`answers.ts:4-8`: *"this is the one place both of those tests import"*).
   - 0125 §1 says *"Every setup question, default and check is in it once"*, so neither input should build the entry itself.

2. **Board: `packages/setup/src/setup-answers.ts:251-252`.**
   - Today this writes either the hold (`landingChanges({ land: 'hold' }, [])`) or `[]` on `rewrite`.
   - Turn it into one `steps.proposed` value: the hold first if `personApprovesMerge`, then `findingsJudgeChanges(form.writer, …)` applied to that list.
   - Write it on every path, new or `rewrite`. `rewrite` is *"a registration that failed after the write, now retried"* (`setup-answers.ts:180-186`), and it has to write what a first try writes. Leaving `[]` there would give a retried setup a file a first try never writes.

3. **Terminal: `apps/cli/src/recipe-flow.ts`, after the `askLanding` block (`:461-470`) and before `askLimits`.**
   - Only when `absent`, call `findingsJudgeChanges` on `draft.get(['steps','proposed'])` with the writer `askAgents` chose. That writer is the `runtime.agent` value in `agents.changes` (`agents.ts:352`).
   - Write the result with `writeOrRefuse`.
   - It has to come after `askLanding`. The absent-file batch is written at `:425-436`, before landing, and `landingChanges` appends the hold to whatever is already there (`answers.ts:64`). Adding the judge in that batch would give `[judge, hold]` from the terminal and `[hold, judge]` from the board.
   - The two inputs are held to the same text (`setup-answers.ts:23-25`: *"the page and `lingtai add` are held to writing the same text for the same answers"*). The ticket's Edges also say the hold comes first.
   - Order does not change behaviour. `judgeDeclaredAt` only looks at `judge:` entries (`judge.ts:105-110`), and a `judge:` *"never becomes an `Action`"* (`recipe.ts`, `judgePlugin.at` doc, near `:1466`). So the order only matters as text.
   - `!absent` writes nothing. That is the "an existing recipe is left as it is" case, and `lingtai init` on a home with a recipe goes through this same branch.

## Decisions the ticket leaves to the code

- **The judge is the writer as written, not the writer `defaultAgents` proposed.**
  - `--agent codex` with Claude Code signed in gives `judge: codex`.
  - The writer is already the one runtime the pass needs signed in. `agentRefusal` reads every step's `judge:` against what is signed in (`agents.ts:67-75`, quoting `conduct.ts:282`), so a judge that is not the writer could add a sign-in failure the writer does not.
  - The `--defaults` case still matches the ticket: Claude Code where it is signed in, else Codex.
- **No entry when the writer is `copilot` or `antigravity`.**
  - Defaults never propose either (`propose-setup.ts:107-108`). `askAgents` also leaves both out of the runtimes `--agent` accepts and refuses an explicit flag naming one before any recipe is made, so this case is reached only through the board form or a hand-built form.
  - A `judge:` naming one is refused when the recipe resolves (`recipe.ts:3589-3593`: *"names `judge: …`, which runs only as the `agent:` at `implement`"*). Writing it would make every ticket answer `stage: "recipe"`.
  - So with these writers the recipe stays as it is today.
- **No `model:` on the entry.** The ticket names no model. Copying the writer's `--model` would make the judge as expensive as the writer, and `judgePlugin`'s doc gives $0.42 for one judge call beside a $22.56 implement (`recipe.ts`, the `fields` comment near `:1436`). Leave it to the runtime's default.
- **`Proposal` gets no new field.** The entry follows the writer the form or `askAgents` settles on, not a value proposed ahead of time.
  - Change the comment at `propose-setup.ts:66` (*"Always false: `proposed: []` (#964 decision 5)"*). It stays false, but the reason is now that a judge is not a hold.
  - The Done-when test "the setup proposal emits that entry" is: `proposeSetup` with only Codex signed in → its `writer.value` → `setupChanges` → `steps.proposed` contains `{ judge: 'codex', when: 'findings' }`. That lives in `packages/setup/unit/`.
  - Also add a `recipe-flow.test.ts` case under `acceptingDefaults`: absent file, only Codex signed in, so the terminal is held to the same entry.

## The card

- Add one field to `CardRecipe` (`setup-card.ts:23-36`), read in `cardRecipe` (`:80-96`) from the recipe as written, the same way `approves` is: the `steps.proposed` entry with `when === 'findings'` that is not `isBuiltInJudge`, plus `recipe.runtime.limits.attempt.refusalFixes` (default 6, `recipe.ts:3444`).
- Add one row under *each attempt*, after `reviews`: findings go back to the writer up to N times, and each time is a judge call and another writer run. When N is 0, the row says there are no fix rounds and the judge can still restart the attempt or hand a finding over: `refusalFixes` bounds only the line fixes, so 0 is not a guaranteed stop for a person.
- Only show the row when a judge is declared. Because it is read from the recipe, it also shows on a hand-written recipe that has a judge, and never shows a judge that is not in the file.
- `apps/cli/unit/init-golden.fixture.json` gains this row. Its test says *"A ticket that changes `init`'s words on purpose regenerates it, and says so in its diff"* (`init-golden.test.ts:11-12`).
- `setup-card.test.ts` needs a case with a judge and one without.

## ADR

- Change 0125 §5's bullet *"`proposed:` is `[]` by default."* (`doc/decisions/0125-setup-is-one-module-two-inputs.md:57`) to say what is now true:
  - `proposed:` holds one `judge:` for `findings`, naming the writer;
  - no hold unless a person asks for one;
  - nothing when the writer cannot judge.
- This is an edit, not a new file. 0125 is in `doc/decisions/`, and CLAUDE.md says *"A decision that changes is an edit to its topic's ADR, not a new file beside it"*. The append-only rule applies to `doc/decisions-archive/`, and no archived ADR is contradicted: 0064 §5 is about writing `proposed:` out rather than leaving it absent, and it still is written out.
- Commit it as `0125: a new recipe declares a judge for findings`.

## Costs to later changes

- After a writer change, `lingtai add` on such a project keeps the old judge. `leftoverRefusal` logs it as *"left as written"* when that runtime is still signed in, and refuses when it is not (`agents.ts:103-115`). That is the existing rule for hand-written judges, and this ticket does not change it.
- The board's `rewrite` already replaced a hand-written `steps.proposed` with `[]` before this ticket. It now replaces it with the setup's list instead. That is not new behaviour and is outside this ticket.

## What settles it after the merge

Unit tests stand in for everything here: the setup test, the recipe-flow test, the card test and the regenerated golden. The routing a declared runtime judge does is #277's and is already built. Nothing here needs `pnpm test:integration`.

The behavioural claim is settled on a fresh `init --defaults` run whose reviewer raises a finding:

- `StepsResolved` should carry the new entry at `proposed`. `judge.ts:91` says both entries *"are on the log in `StepsResolved`"*.
- The run log's `route` line should read `proposed → implement` (or `claim`) as the judge's answer, not the `waiting: no judge: is declared` line from the 2026-11-25 run.
