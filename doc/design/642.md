# Design: #642, three passes landing together through `runQueue`'s slots

## Where it goes, and what it drives

Put it in a new file, `packages/conductor/unit/three-passes-at-once.test.ts`. Don't add it to `conduct-a-whole-pass.test.ts`, which is already 2230 lines about one pass. Import that file's fixtures from `../test/one-pass.ts`: `memoryStore`, `streams`, `fakePorts`, `fakeGitHub`, `runtime`, `RECIPE`, `project`, `issue`, `PROJECT`.

**Drive `runQueue` with `slots`, and let the real `runOnce` run underneath it.** The existing tests already cover each half alone:

- `unit/schedule-slots.test.ts` covers the slot logic, but it mocks `../src/conduct.ts` (`schedule-slots.test.ts:39-46`), so no pass runs in it.
- `unit/one-landing-at-a-time.test.ts` runs two real `runOnce` calls but calls `once()` itself (`:101-104`), so no scheduler is involved.

Nothing joins the two halves, and joining them is the whole of this ticket. So mock only what would reach outside the process (next section). Leave `conduct.ts`, `schedule.ts`, `slots.ts`, `same-file.ts` and `landing-lane.ts` real.

`concurrency: 3` in the ticket means `slots: { set: createSlots(), limit: 3, started }`. `runQueue` takes the limit as a number (`schedule.ts:95-100`). Turning `concurrencyOf(recipe)` into that number is `apps/cli/src/conduct.ts:310`'s job, so this test doesn't need it.

**This is a test-only change. Don't edit `src/`.** If the test fails because the code misbehaves, report that as a finding. Don't patch around it.

## What has to be faked, and the two traps

1. **The queue projection.** `selectRunnable` reads `task_view` through `readTasks` (`queue.ts:14`, `:77`), which is Postgres. Mock `../src/queue.ts` the way `schedule-slots.test.ts:31-37` does. The difference: derive "taken" from the shared memory store rather than from a hand-kept set. A ticket is taken when `ticket-${PROJECT}-${n}` holds `TicketClaimed` or `TicketLanded`. Return `taskId: ticketStream(project, ref)`, as `queue.ts:100` does. Sort by issue number.

2. **The recipe.** `runQueue` does not forward a recipe resolver to `runOnce` (`schedule.ts:254-269`, no `recipe:` key). So `runOnce` falls back to `currentRecipe` (`conduct.ts:669`), which is `resolveLocalRecipe` reading `~/.lingtai/<project>/recipe.yml` (`projects.ts:153-165`). That read is the filesystem. Under `HOME=/nonexistent` every pass would stop at `stage: 'recipe'`.
   - Fix it with `vi.mock('../src/projects.ts', async (orig) => ({ ...(await orig()), currentRecipe: () => resolveRecipe(fileAt, 'main') }))`, where `fileAt` is the fake client's.
   - Don't add a `recipe` pass-through to `ScheduleOptions` instead. That is a source change for a test ticket.

3. **The ports: one `Repo`/`AgentHost` for all three passes, so the tree has to be per run.** In slots mode, `runQueue` provides one captured context to every pass it starts (`schedule.ts:158`, `:270`). But `fakePorts` keeps one mutable `FakeTree` (`one-pass.ts:127-131`), and `wire` advances it to `b`×40 (`:806-810`). If three passes share that tree, the first pass's `wire` moves the head before the second pass reads its baseline. The second pass then finds no receipt for its implementer and refuses. You would see a red that looks like a concurrency bug, and it is a fixture bug.
   - Build one port object that keeps a `FakeTree` per `runId`.
   - `provision`, `remove` and `wire` all receive `runId`. `RenderOptions.runId` is at `packages/agent/src/hook-config.ts:80`.
   - `git` receives `cwd` = `worktreePath(home, project, runId)` (`conduct.ts:1103`, `:1619`). Pull the runId out of that path.
   - Delegate everything else to `fakePorts(did, store, true)`'s implementations.

4. **The runtime.** With `RECIPE` (`steps: {}`, `one-pass.ts:125-132`), each pass calls `runtime.run` exactly once, for the implementer. Make `run` a barrier: each call registers and waits, and the test releases them. That is how you control when things happen without a clock.

5. **The client.** Three issues, each with a `| **Fix** |` row naming a distinct file. `listOpenIssues` returns the issues still open. `getIssue(n)` returns that issue's body; `same-file.ts:readFixFiles` and the pass both read it. `closeIssue` removes the issue from the open list. Base it on `fakeGitHub(said, RECIPE)` and override those three methods, as `one-landing-at-a-time.test.ts:81-87` does.

**One shared `memoryStore()` for every pass.** `one-landing-at-a-time` uses one store per pass. Don't copy that. The ticket asks for "the memory store", and a `ConcurrencyError` on a stream the three passes share would be exactly the bug this test exists to find. If it happens, report it as a finding. Don't split the stores to make it go away.

## "About the time of one", without a clock

The Watch-out row bans the wall clock, so don't use `Date.now()` or `vi.useFakeTimers()`. Nothing on this path schedules a timer: `schedule.ts` and `claim.ts` contain no `setTimeout`, `Date.now` or `Clock`. **The store's `seq` is the clock.** `memoryStore` gives every append a single global `seq` (`one-pass.ts:87-113`). So the claim *the three ran together* can be stated as two checks, and the log settles both:

- **The barrier check.** One `runQueue` look returns `{ stopped: 'max', started: 3 }`, and `runtime.run` has been entered three times before any call is released.
- **The seq check.** Every ticket's `RunStarted` seq is lower than every ticket's `TicketLanded` seq. If the passes were awaited one after another, the second `RunStarted` would come after the first `TicketLanded`. That ordering is the "time of three" this test must rule out.

To let the background promises run, use the `tick` from `one-landing-at-a-time.test.ts:27` (`setTimeout(r, 0)`) in a bounded loop. That only yields a turn of the event loop and measures no time, so it is allowed.

## The four claims, as `it`s

1. **Three independent tickets land together.** Three tickets with disjoint Fix files and `limit: 3`. One look starts all three, and the barrier and seq checks above hold. Release the runtime, then `await Promise.all(handed)`. Every ticket stream ends with `TicketLanded`, and `slots.of(PROJECT)` is empty again (`slots.ts:38-41`).

2. **The lane lands them one at a time.** Same set-up. Wrap `integrate` with an `inFlight`/`maxInFlight` counter. Hold the first `integrate` until the other two runs have appended `MergeLaneWaited`, bounded the same way as `one-landing-at-a-time.test.ts:57-60`.
   - Then `maxInFlight === 1`.
   - There are exactly two `MergeLaneWaited` events across the run streams. Each names the holder that was inside `land` at the time (`landing-lane.ts:46-48`).
   - Don't pass `lane` to anything. `runQueue` can't (`schedule.ts:254-269`), so the process's own `landingLane` (`conduct.ts:2793`) is the lane under test. That is correct, and it is the same choice `one-landing-at-a-time.test.ts:5-7` makes.
   - Give the fake `integrate` disjoint files so it never answers `base-moved`. The #593 re-route already has its own test.

3. **A same-file pair runs in turn.** Tickets 1 and 2 both name `src/x.ts`, and ticket 3 names something else.
   - The first look starts 1 and 3, and its log says `waits for #1 in flight — both name \`src/x.ts\`` (`same-file.ts:waitsFor`).
   - Release everything, then run a second look, as the work loop's `started` wrapper would after a settle (`work-loop.ts`, #638). That look starts 2.
   - Check it in the log: ticket 2's `TicketClaimed` seq is greater than ticket 1's `TicketLanded` seq. This is not a duplicate of `schedule-slots.test.ts:132`. That test checks the call order of a mocked `runOnce`; this one checks that the real pass landed before the second was claimed.

4. **A drain waits for all of them.** Three in flight, plus a fourth ticket queued. Run a second look with `paused: async () => 'draining'`. It returns `stopped: 'paused'` (`schedule.ts:181-187`) and starts nothing. Then release the barrier. `Promise.allSettled(handed)` resolves only after all three `TicketLanded` events exist, and the fourth ticket has no `TicketClaimed`.
   - The daemon's `stop()` awaiting `passesInFlight.settled()` is `packages/daemon`'s claim, already tested in `work-loop-stop.test.ts`.
   - `@lingtai/conductor` does not depend on `@lingtai/daemon` (`packages/conductor/package.json:45-54`), so do not import the work loop here. In this package, the drain is `paused` plus the promises handed to `started`.

## Edges

- **A pass that throws.** `schedule.ts` turns a rejection into a log line and frees the slot (`pass.finally(leave)`). That is not this ticket's subject, but if a fixture mistake makes a pass refuse, show what happened. Collect the `ran` results and throw with `stage`/`detail`, as `conduct-a-whole-pass.test.ts:84-87` does, so a red doesn't just read as `false`.
- **Module-level state.** `landingLane` is a process singleton keyed by `integrationStream(project, base)`. vitest isolates each file, but the `it`s in this file share it. Await every handed promise before an `it` ends, so no lane chain carries into the next test.
- **What it costs later tickets.** Assert on event types, seq order and the `waits for` sentence, not on the whole `did` list. Another step added to `RECIPE`'s path must not turn this test red.
- **Restart, two conductors, a stale page.** These do not apply. Everything runs in memory inside one process.

## Out of scope

- The integration half, which takes 803 s and which nobody runs as part of a ticket. This test is the unit-level stand-in for "N passes land", and there is no integration counterpart to add.
- Serialising writes to the mirror (0122 §6). It is named as unbuilt in `doc/design/638.md`'s *Edges*, and the fake ports never touch a mirror.
- `apps/cli`'s choice between awaited and detached mode.
