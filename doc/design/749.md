## Design note for #749

The ticket gets the shape right. These are the three places where building it could go wrong.

**1. The seed is one change at `['steps', 'end']`, not at `['steps']`.** `setRecipe` passes every change through `widenStepsIfNeeded` (`packages/recipe/src/write.ts:128-159`). That function is skipped when any change's path has length 1: `stepChanges.some((c) => c.path.length === 1)` at `write.ts:134`. Otherwise it widens the `steps.*` changes into one `['steps']` value made of the touched keys plus the displaced ones (`write.ts:156-158`). A length-3 change is also fine. So write it as a sibling of the other two seeds:

```ts
{ path: ['steps', 'end'], value: [
  { name: 'close the ticket', when: 'landed', close: true },
  { name: 'close the ticket a person ended', when: 'closed', close: true },
] }
```

Before relying on that, check that no first-run question in `askRecipe` writes a bare `['steps']`. If one does, it would replace the seeded `end`, because `all = [...at.seeds, ...collected]` (`apps/cli/src/recipe-flow.ts:372`) puts the seeds first and the later change wins. The add-github test that resolves the file and expects both actions at `end` will catch this either way. Write that test first.

**2. Seeding only on the absent-file path is already enforced at the caller, and has to stay there.** `askRecipe` writes `at.seeds` on its own when the file exists (`recipe-flow.ts:285-288`, `if (!absent) { … writeOrRefuse(at.project, at.seeds, …) }`). The only thing keeping `repo.base`, and now `steps.end`, out of an existing file is that `askBeforeGithubAdd` builds `seeds` only inside `if (existing === null)` (`apps/cli/src/add-github.ts:326-338`). Put the new seed in that same array literal, not anywhere that runs for an existing file. Otherwise a re-run would overwrite a person's `end:`, which is the ticket's *Watch out*. Make the "already exists" test use a file whose `end:` is something other than the seed, for example `end: []`, and compare the bytes. The re-run path writes seeds through `writeOrRefuse`, so a stray seed would show up as a changed file, not a silent no-op.

**3. The comment needs no new mechanism.** `commentWritten` runs only on the creation write (`write.ts:193-195`) and labels only blocks that exist. For a block that isn't there, `commentBlocks` reaches `continue` instead of throwing (`packages/recipe/src/emit.ts:94-97`, non-strict). So adding `'steps.end'` to `SAID` (`recipe-flow.ts:88-100`) gives the GitHub file its comment, and the local file stays unchanged. The two tests that walk `SAID` behave differently:
- `apps/cli/unit/add-github.test.ts:300-311` treats a missing pair as allowed only for `steps.proposed` and `runtime.limits`. Since `end` will now be present, it checks the sentence. Leave that list alone.
- `apps/cli/unit/recipe-flow.test.ts:128-131` (the local test) gets `''` for `steps.end` and fails unless `'steps.end'` joins `['steps.proposed', 'runtime.limits']`. Also update the comment just above it (`:124-127`) to say why: `end` is decided only on the GitHub path, and #749 is not the local decision.

Keep the `SAID` sentence about the ticket's end, for example *"what happens to the ticket once it ends"*. It is the comment above `end:` in every new GitHub recipe.

Everything here is checked by `pnpm test` (unit). Nothing in this shape needs `pnpm test:integration`.
