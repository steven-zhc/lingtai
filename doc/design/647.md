# Design: #647, one triage button on a waiting card

## Where it goes

There are three pieces. The decision is made on the server, a button is drawn from it, and one anchor is added on the task page.

1. **`toCard` decides; the page does not.** In `apps/board/src/lib/board.ts`, `toCard` already computes `status` (`board.ts:596`) and uses it for `cause` (`board.ts:619-622`). Add one field to `BoardCard` from that same `status`. Call it `move`, shaped `{ resolution: Resolution['_tag']; onSha: string | null } | null`.
   - It is non-null only when `status` is `Done` with `TriageAdvised`.
   - It is also non-null only when `recommendedResolution(t.wait.reason, status, { savedHead })` (`packages/domain/src/wait.ts:580`) returns a tag.
   - Do not gate on `recommendedResolution` alone. For `Queued`, `Running`, `Interrupted` and `Done/TriageFailed` it returns the wait's *default* (`wait.ts:603-611`). The ticket says no button unless triage advised, and the task page draws the same distinction: "Badged only when triage advised it: a wait's own default orders the cards but is not called a recommendation" (`standing.tsx:583-584`).
   - Keep this pure so it can be unit-tested beside the other `toCard` claims.

2. **A client button in `decide.tsx`**, the module that already imports `approveCard`, `continueFixingCard` and `requeueCard` (`decide.tsx:22-31`). `page.tsx` is a server component and must not import a function from it. `decide.tsx:51-52` says why: "a server component calling a function from one gets a reference rather than the function". So the button takes only data props: `project`, `issue`, `waitId`, `move`, `note`, `taskId`.
   - Copy `Decide`'s pattern exactly: optimistic, then revert on refusal with the server's own `detail` (`decide.tsx:5-14`, `128-138`).
   - No `confirm()`.
   - Put the label in 0118's words from `RESOLUTION_COPY[tag].title`, as the triage band does (`standing.tsx:230`).
   - Render it in `page.tsx`'s waiting branch, under the cause line (`page.tsx:180-184`). Also update the module comment at `page.tsx:41-42`. It says "Its resolutions and the rest of the wait's detail are on the task page", and it should now say "all but triage's one".

3. **Anchors on the task page** for the open-the-page cases.
   - `ResolutionCard` spreads `...rest` onto its `<article>` (`triage-picks.tsx:186`). Add `id?: string` to its props (`triage-picks.tsx:177-184`) and pass `id={`resolution-${tag}`}` where `standing.tsx:953` renders a visible card.
   - `Split` has no resolution card ("`Split` has no card until its editor exists", `standing.tsx:575-577`). Its link anchors the triage band instead: put `id="triage"` on `<section className="triage-band triage-band--advised">` (`standing.tsx:221`).
   - The link is a plain `next/link` to `/task/<taskId>#resolution-<Tag>`. It writes nothing.

ADR 0118 §2 already says all of this (`doc/decisions/0118-a-hold-explains-itself.md:356-365`, `5f6eb51c`). No ADR edit is needed. If the implementation departs from that text, edit that bullet: 0118 is in `doc/decisions/`, where the file is edited rather than superseded.

## The decision that is not in the ticket: `GrantFixRound` needs a sha the board does not have

`continueFixingCard` refuses an empty `onSha` (`actions.ts:170`). The sha it wants is the **saved fix head**, not `awaitingSha`. The page passes `standing.fixWork.head` (`standing.tsx:985`), and `resolveWait` refuses any other value: "The saved head is ${head}, not the displayed ${resolution.onSha}" (`resolve-wait.ts:278-284`).

On the page, that head comes from two reads:
- `savedFixWork(runId, events)`, which reads `RunRefsPublished` off the run stream (`apps/board/src/lib/task.ts:918-943`).
- A GitHub `refSha` call (`task.ts:1887-1907`).

**Do not add the GitHub call to the board render.** That would mean one API round trip per waiting card on every load, which is the cost #112 and `laneProgress`'s comment are about (`board.ts:440-448`, `910-912`). Instead:

- **Take the head from the log alone, and only where the board already reads the stream.**
  - `laneProgress` reads `eventStore.read(task.runId)` for the first `WAITING_RAILS` (6) waiting cards (`board.ts:917-931`, `450`).
  - Have it also return `savedFixWork(task.runId, events)` for those cards.
  - Pass that into `toCard` as `savedHead: 'head' in saved` and `onSha: saved.head`.
- **Any other waiting card gets `savedHead: false`.** That covers cards past the cap, a stream that would not read, and a `{ refusal }`. `recommendedResolution` then drops `GrantFixRound` (`wait.ts:589`), and the card shows no button. It does not fall back to another resolution. This is the same rule the page follows: "with no saved head it does not return `GrantFixRound`, so nothing is swapped in" (`standing.tsx:579-580`).
- **The remote-ref check still happens, in the action.** `resolveWait` reads `refSha(heads/<ref>)` and refuses with "Restore that ref to the saved head or requeue for a fresh pass" (`resolve-wait.ts:293-301`). A ref that moved therefore refuses on click, with that sentence on the card. It is a refusal, not a silent continue.
- **Moving `savedFixWork`:** it lives in `lib/task.ts`. If importing it into `board.ts` pulls in a cycle or a server-only chain, move it to a small module both files import, rather than copying it.
- **Check that it is the right run.** Confirm that `task_view`'s `runId` for a waiting card is the run the wait blocks. That run is `block.runId`, the one `resolveWait` passes to `savedHead` at `resolve-wait.ts:275`. If the two can differ, the button is absent there, because a head from the wrong run is a stale click every time.

## What each click sends

Every click sends `waitId: card.waitId`. A card with a null `waitId` renders no button, as `Decide` already requires (`decide.tsx:89-94`).

| Resolution | Action | `onSha` | Note |
|---|---|---|---|
| `GrantFixRound` | `continueFixingCard` | saved head (above) | none; the action takes none |
| `Requeue` | `requeueCard` | n/a | `''` |
| `Approve` | `approveCard` | `card.awaitingSha` (no button if null) | `accepted triage's recommendation: <summary>` |
| `EditBodyAndRequeue`, `AnswerQuestion`, `Close` | link to `#resolution-<Tag>` | n/a | n/a |
| `Split` | link to `#triage` | n/a | n/a |

**Requeue sends an empty note on purpose.** The requeue note is what "every attempt at this ticket is told" (`decide.tsx:497`). Putting triage's sentence there would feed it into the next agent's prompt, and that is a decision the ticket did not make. An empty note is what a page click with nothing typed sends.

**Approve sends the note on every one-click approve, not only when a step refuses.** The card does not know whether anything refuses; `Decide`'s `refusing` is "a hint, and only that" (`decide.tsx:96-101`). `checkApprove` only *requires* a note when `refusingOn` is non-empty (`resolve-wait.ts:517-526`), so the note costs nothing when nothing refuses.

- `<summary>` is `status.result.summary`, the sentence the card already shows (`board.ts:621`).
- Write the template once, as a pure exported function beside `requeueNote` (`wait.ts:615`). For example, `acceptedTriageNote(summary)`. `toCard` (or `page.tsx`) calls it, and the unit test pins its output. A literal in the client component cannot be pinned without rendering it.

## Edges

- **Triage `Queued`, `Running`, `Interrupted`, `Unknown` or `Failed`:** `move` is null, so no button. The `TRIAGE_WORDS` line (`page.tsx:87-92`) is unchanged.
- **Advice that contradicts itself, or a resolution the wait does not allow:** `recommendedResolution` returns null (`wait.ts:597-603`), so no button.
- **Stale card** (the wait moved, a second tab, or the head moved): the existing actions refuse by `waitId` (`actions.ts:107-112`, `266-271`), and by `onSha` through `checkApprove` (`resolve-wait.ts:503`) or `resolveWait` (`resolve-wait.ts:278`). The button reverts and shows that detail.
- **Success:** the actions already call `revalidatePath('/')` (`actions.ts:145`, `190`, `280`), so the card leaves Waiting on the next render. Until then the button shows `result.detail`, as `Decide` does.
- **A retried `Approve` or `GrantFixRound` on an already-approved wait** returns ok without a second `WaitResolved` (`resolve-wait.ts:203-215`). A double click is safe.
- **Daemon paused or draining:** irrelevant. These actions resolve the wait, and the continuation belongs to whichever process holds the lock (`actions.ts:146-147`).
- **Cost to later tickets:** none beyond the extra `BoardCard` field. Queued-card stubs (`board.ts:849-860`) need `move: null`.

## Tests (unit; nothing here needs `pnpm test:integration`)

- **`toCard`:** `move` is null for each non-advised triage status, for contradicted advice, and for `GrantFixRound` with `savedHead: false`. It carries the tag and the right `onSha` for advised `GrantFixRound`, `Requeue` and `Approve`.
- **The note function:** pin its exact output.
- **Stale `waitId`:** follow `apps/board/unit/schedule-continuation-stale.test.ts`, which drives "the function `approveCard` calls underneath the lock" against an in-memory store. Do the same for the resolution under a stale `waitId` and assert `reason: 'stale'`.
- **The link cases:** a render test that `EditBodyAndRequeue`, `Split`, `AnswerQuestion` and `Close` produce an `<a href="/task/…#…">` and no button. `apps/board/unit/standing.test.tsx` already renders to markup.
- **Check:** `pnpm typecheck` and `HOME=/nonexistent pnpm test`.
