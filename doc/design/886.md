# #886: design note

## What #885 already did, so you don't redo it

- **Fix (2) is already true. Don't move anything for it.** `planFor` runs inside `readAttempts` (`apps/board/src/lib/task.ts:1641-1644`). `loadTask` starts `readAttempts` in parallel with `loadTicket` (`:1684-1690`). `recipesFor` is no longer called from `loadTask` at all; only `loadAttemptTab` calls it (`:1886`), in its own segment. The ticket's evidence comes from traces taken before #885. Fix (2) still gets its Done-when test, which pins this behaviour.
- **Two places currently await GitHub, and both must stop.** One is the layout (`app/task/[id]/layout.tsx:234`). The other is the Ticket tab: `loadTicketTab` awaits `loadTicket` (`task.ts:1905-1910`). `/task/<id>` reaches that function too, through `loadDefaultTab` (`app/tab-view.ts:28-30`). `defaultTabOf` returns `'ticket'` whenever there are no runs (`lib/tabs.ts:50-51`). So the slowest case, an untouched ticket, would still hold the whole response on GitHub through the child segment, even after the layout is fixed. **`loadTicketTab` must not await the answer.** It returns the log's part plus the pending answer, and `TicketTab` draws through the seam.
- **No GitHub read is hiding in the part that stays.** `url` and `compareUrl` stay in `loadTask`. They use `currentRecipe`, which reads a local file: *"No request is made and nothing is read from the repository"* (`packages/conductor/src/projects.ts:136-139`).

## Where the GitHub read starts, and why there

**Start it in the layout, before `loadTask` is awaited, in its own `measure`:**

```
const github = measure(() => loadTaskAnswer(id), { label: '/task github' })   // not awaited
const [task, timings] = await measure(() => loadTask(id), { label: '/task' })
```

There are two reasons to start it there and not anywhere else:

1. **`measure` scopes by AsyncLocalStorage** (`lib/timing.ts:65-67`, `scope.run`). A promise started inside `loadTask` puts its `timed` reads into the `/task` entries and under the `page /task` span. That span ends before those reads do, so Jaeger could never show "`page /task` ends before `/task github`".
2. **It must start at t=0.** Chained after `loadTask`, the page would cost the log time plus GitHub's time, where today it costs the larger of the two.

`loadTaskAnswer(taskId)` returns one `Promise<TaskAnswer>`, where `TaskAnswer = { ticket: TicketAnswer; outgoing; queued }`:

- **`ticket`**: `await loadTicketAnswer(taskId)`. This is `readProjectTicket` plus the three-way `found` logic from `task.ts:1408-1431`, wrapped in `cache()`.
- **`own`, `streams`, `standing`**: `await readAttempts(taskId)`. It is already `cache()`d (`:1601`), so in a real render it does not read twice.
- **`paused`** for `queuedFor`: from the control read. Lift that read into a `cache()`d function next to `readOwn` (`:1587`), so the layout and the deferred part share it.
- **`outgoing` and `queued`**: under exactly the conditions at `:1810-1819`, keyed on `standing.state`. The folded state is enough here: `loadTask` adds only `triageStatus`, `triageHeadLine`, `fixWork` and `split` to it, and never changes the state.

`TaskDetail.outgoing` and `TaskDetail.queued` are removed.

**`TaskAnswer` never rejects.** A rejected promise read under `<Suspense>` goes to the error boundary, which would replace the page instead of saying *what failed* in one place. So:

- `loadTicketAnswer` catches everything, including `loadProject` throwing, and turns it into `problem`.
- A throw from `outgoingFor` or `queuedFor` becomes that view's own `problem`. Both views already carry one (`standing.tsx:530-532`, `:850`).

In unit tests React's `cache()` does not memoize, because there is no RSC render, so each call reads again. That only costs mock calls.

## The split of `TicketView`

**`TaskDetail.ticket` (from the log and the register):** `project`, `ref`, the log's `title`, `kind` and `labels`, the built `url`, and `compareUrl`. The clearing of `compareUrl` on an unpushed branch stays where it is (`:1859`).

**`TicketAnswer`:** `found` (`true | false | null`), `askedGitHub`, `title`, `labels`, `url`, `body` and `problem`. Where the answer has a field, the drawn place prefers it over the log's: GitHub's `url` when `from === 'github'` (`:1418`), GitHub's title, GitHub's labels.

The *"not a registered project"* branch (`:1376-1389`) leaves the answer entirely, because the layout now 404s on it.

The layout calls it and is the only place that calls `notFound()` on it. Rewrite the comment to cite 0118 §2, whose lines 389-392 already state the rule. ## The seam

Write it once, as `apps/board/src/app/deferred.tsx`:

- `type Answered<T> = T | Promise<T>`
- `<Deferred value fallback>{(v) => …}</Deferred>`. For a value that is not a thenable, it calls the render function synchronously. For a promise, it renders `<Suspense fallback>` around a small sync component that calls React 19's `use(promise)` and renders.
- **Use `use()`, not an async component.** It suspends correctly in both RSC and `react-dom/server`. So `renderToStaticMarkup` with a promise that never resolves renders the fallback, which is how the fallback tests are written. With a resolved value it renders exactly what renders today.

**`Standing` and `Coords` each take one `answer: Answered<TaskAnswer>`.** It replaces `body`, `outgoing`, `queued`, `unknown` and the GitHub half of `subject`. `subject` keeps `ref`, the log's title and the built url, so the heading draws at once.

Each place listed in the ticket's **Watch out** row wraps itself in `<Deferred>` over that one value, with its fallback from **Edges**. They all resolve together because they share one promise.

The four test files that render `<Standing>` and the two that render `<Coords>` (`standing.test.tsx`, `queued.detail.test.tsx`, and the others `grep -l '<Standing' apps/board/unit` lists) change mechanically: a resolved `answer={{ ticket, outgoing, queued }}` replaces the separate props.

## The untouched ticket (`task.events === 0`)

This case is the one place the seam is not per-place. **In `TaskBody`, wrap the whole `Standing` in one `Deferred`.** A sibling boundary cannot hide the state line and the moves row, which is what *"state and moves are replaced"* asks for.

- **Fallback:** `Standing` with the pending answer, and with `issue={null}`. `issue={null}` already means *"states the state without offering a move"* (`layout.tsx:181-183`). So the state line reads *queued* and draws no moves until GitHub has said the issue exists. You write no new code for this.
- **Resolved, `found === false`:** the *"GitHub has no issue #N"* block. It has no queued lines and no moves.
- **Resolved, `found === null && askedGitHub`:** the current `unknown` sentence (`layout.tsx:203-205`), with moves as today.
- **Resolved, otherwise:** `Standing` with the answer.

A ticket the log has touched never takes this branch. It uses the per-place boundaries, and a 404 there is the Ticket part saying GitHub has no such issue.

## Ticket tab

`TicketTab` draws one `<Deferred>` over the whole `Ticket` block (`app/ticket-tab.tsx:19-66`):

- **Fallback:** `#ref`, the log's kind and labels, the built link and the log's title, with *asking GitHub…* where the body goes.
- **Resolved:** today's `Ticket`, unchanged.
- **Always visible:** the Events disclosure is the log's, and stays outside the boundary.

  - `loadTask` resolves with every field the log and the register give.
  - The `next.plan` read was made, using the existing `filter` mock.
  - `readProjectTicket` was **not called by `loadTask`**. Clear the mock before calling `loadTask` alone.
- **`loadTaskAnswer`** gets its own unit test in the same file:
  - answer, 404 and failure each produce the right `TicketAnswer`;
  - `outgoing` and `queued` appear only in their states;
  - a throw from `queuedFor` becomes a `problem`, not a rejection.
- **The fallback and the resolved renders** are `renderToStaticMarkup` calls with a promise that never resolves and with resolved values, as the ticket's Done-when lists.

The Jaeger check stays a person's. No unit test asserts span order.
