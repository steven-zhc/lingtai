# Design: #1221 — land again from the same head after a transient refusal

## The shape in one paragraph

`land-again` is a new **candidate**, and a new kind of move, that sits beside `MergeBase`. `offerFor` offers it. `routeProposal` picks it by rule before `replyFor` runs. Picking it records a route, waits, and sets `at = 'merge'`. On replay, `routeMove` answers it, and the attempt reducer folds it into `transientRetries`. Copy `MergeBase` at every place it appears: it is the one existing "free" move that spends a per-attempt counter. Search for `'MergeBase'` and you have the checklist.

What exists today:
- #1200 has landed: `TRANSIENT_RETRIES_LIMIT = 3` and `TRANSIENT_WAITS` are at `packages/domain/src/failure/respond.ts:547-550`.
- `AttemptState.transientRetries` is declared at `packages/domain/src/attempt.ts:249`, with the comment *"Nothing raises it yet (#1201, #1221)"*.
- `run-codec.ts:144` already parses that field.

## The move: a new `CandidateNext` variant, not a `FixRound` or a flag

- **`packages/domain/src/attempt-next.ts`**: add `LandAgain = { _tag: 'LandAgain', retry: number }`. `retry` is the count this route *makes*, the way `MergeBase.merge` is (`attempt-next.ts:85-89`). Add it to the `AttemptNext` union (`:91-99`). In `spentAfter` (`:459-470`), add `LandAgain → { ...spent, transientRetries: next.retry }`. Add `transientRetries?: number` to `Spent` (`:107`).
- **`packages/domain/src/routing.ts:46-51`**: add `LandAgain` to `CandidateNext`. `routeMove` (`:197-212`) then returns it with no change, because it returns `candidate.next`. `routeNext` passes it through, since it is not `WaitOnPerson`.
- **Exhaustive switches.** `pnpm typecheck` will list them. The ones known today:
  - `destinationOf` (`packages/conductor/src/proposed-route.ts:100-109`): `LandAgain → 'merge'`.
  - `read-model.ts:98` and `:311`.
  - `apps/board/src/lib/history.ts:740`.
  - `attempts.ts:283` only filters for `MergeBase`; leave it.
- **Why `retry` is stored on the move rather than counted in memory:** the reducer has to replay it. Without that, a continuation could not keep the count, as the ticket requires and as 0108 §8 says (*"None of these counters is reset inside an attempt"*).

## Offering it: `offerFor`'s `MergeRefused` case

The case is at `respond.ts:700-704`. Its spent argument gains `transientRetries`. Before the existing `round` and `restart` calls, push:

```
{ id: 'land-again', next: { _tag: 'LandAgain', retry: spent + 1 } }
```

Push it **only** when both of these hold:
- `proposal.reason` is `'unreachable'` or `'remote-error'`;
- `spent.transientRetries < TRANSIENT_RETRIES_LIMIT`.

**When spent, omit it entirely. Do not list it in `unavailable`.**
- Ticket: *"it is never on a card"*.
- Done-when: the other reasons route *"with no expected value changed"*.
- With the retries spent, the offer must be byte-for-byte today's offer. That is what makes a declared `when: merge-refused` judge see today's offer, and what keeps the existing `MergeRefused` tests unchanged.

It is fine that this departs from `offerFor`'s *"each candidate … carries exactly one exclusion when withheld"* (`respond.ts` doc above `:575`). Say why in the doc comment: a rule's candidate is never shown to a chooser.

## Choosing it: in `routeProposal`, before `replyFor` and before the base-red block

The base-red block (`run-attempt.ts:1546-1584`) is the precedent for answering by rule. Put the new branch right after `offerFor` (`:1537-1546`). It cannot collide with base-red, which needs `BuildRed`.

If `offer.available` contains `land-again`:
1. Build `reply = { _tag: 'Selected', candidate: 'land-again', why: <rule sentence> }`. **Use `Selected`, not `NotAsked`**: `routeMove` throws on a `Selected` decision paired with any other reply (`routing.ts:199-204`), and replay runs through it. The why can say: *"origin did not answer the land; landing again from <onSha> after <wait>, retry n of 3"*.
2. Then `decision = decideRoute(offer, reply)`, `routed = routedVisit(...)` and `next = routeNext(...)`.
3. Call `record(...)` and `routes.push(...)` exactly as the general path does (`:1636-1654`). Record **before** the sleep, so the log shows what it is waiting for.
4. Then `yield* Effect.sleep(transientWaits[next.retry - 1])`. The index is the count *before* this retry, as the ticket says.
5. Set `transientRetriesSpent = next.retry` and `at = 'merge'`, then `return true`.
6. Do **not** touch `onSha`, `reviewedSha`, `approvedAt`, `recheck`, `lapStart` or `landedOnBase`. Nothing was built or reviewed, so every value a later step reads stays as the first land left it.

Simplest code shape: a `case 'LandAgain'` in the switch at `:1656` that does steps 4–5. Then the rule only has to supply the reply in place of `yield* replyFor(...)` (`:1592`), via something like `const reply = ruleReply ?? (yield* replyFor(...))`. This keeps one `record`/`routes.push` site. It also keeps the `'neverStarted' in reply` check working, because a `Selected` reply has no `neverStarted`.

**The wait is injectable, the same way `unreachableWaits` is** (`conduct.ts:576`, threaded at `:2565`, `:3462` and `:3511`):
- Add `transientWaits?: readonly Duration.Input[]` to conduct's options and to `runAttempt`'s options, defaulting to `TRANSIENT_WAITS`.
- `land-unreachable.test.ts` passes `unreachableWaits: ['0 millis', '0 millis']` (`:55`). The new tests pass zero waits in the same way, so the first two Done-when tests stay fast.
- For the *"waits 1, 5, 15 minutes"* Done-when, run that one test under `TestContext` and drive it with `TestClock.adjust`. Nothing in `packages/conductor/unit` uses `TestClock` yet, so `once(...)` may need a variant that keeps the Effect instead of a Promise.
- If threading the clock through `once` costs more than the test is worth, inject the sleep instead: record the durations it is handed, and assert `['1 minute','5 minutes','15 minutes']`. Say in the PR which one you did.

## Counters across a continuation

- `runAttempt` gains `let transientRetriesSpent = options.from?.transientRetriesSpent ?? 0`, beside `baseMergesSpent` (`run-attempt.ts:1364`), plus the matching field on `from` (`:994-996`).
- `continuationSpent` (`conduct.ts:757-760`) returns `transientRetries: run.transientRetries ?? 0`, and the two call sites pass it on (`conduct.ts:1355`, `:5233`).
- Reducer (`attempt.ts:601-604`): `if (next._tag === 'LandAgain') return { ...state, ...settled, ...at, transientRetries: Math.max(state.transientRetries ?? 0, next.retry), route: d }`.
- **Bump `attemptReducer.version` to 7** (`run-codec.ts:201-202`) with a line like the one for 6. A version-6 snapshot was cut by a reducer that ignored `LandAgain`. Under 0124 a version change voids the old snapshot, so this needs no other step.
- Fix the comment on `attempt.ts:248`: it now says *"Nothing raises it yet"*, and the `land-again` route raises it.

## The sentence when the retries are spent

The count must survive replay. That rules out appending text to `output`:
- `MergeRefused`'s copied field is `output` (`proposal.ts:246`).
- A `ProposalRouted` stores the proposal without it, and `resolveOffer` reads it back from the `StepEnded` (`routing.ts:225+`).
- So an in-memory edit to `output` vanishes on the board.

Instead:
- Add an optional `landedAgain: { times: number, minutes: number }` to the `MergeRefused` schema (`proposal.ts:169-175`). It is not a copied field, so it is stored with the route.
- `routeProposal` sets it on the proposal it hands onward when two things hold: the offer has no `land-again` (because the retries are spent), and this pass made one or more `land-again` routes. Keep a local tally of times and summed minutes. Sum the minutes from the waits actually slept, not `3 × …`: once #1201 lands, some of the counter may already have been spent elsewhere.
- Absent means today's sentence, word for word. That is what keeps every existing expected value unchanged.
- **`times` counts this pass's re-lands only.** After a person's Approve, a continuation whose land fails again starts at zero, says nothing about landing again, and reads as today. Being honest about this pass is enough; don't reconstruct earlier passes from the stream.
- `diagnoseRefusal` (`explain.ts:459`) gains an optional `landedAgain`. `mergeRefusedColumns` (`wait-words.ts:107-113`) passes `proposal.landedAgain`, which needs the proposal, or its field, threaded to that function's callers. The `unreachable` and `remote-error` readings (`explain.ts:330-353`) insert *", landed again N times over M minutes"* after *"after N tries"*. The `move` is unchanged.

## Edges this note decides

- **The landing lane runs inside one call.** The sleep sits between two calls to `landNow` (`conduct.ts:3447`, `:3548`), so the serialiser is never held while waiting. No change is needed there.
- **`landNow`'s branch-push refusal** (`conduct.ts:3388-3398`) reaches the router through the same `MergeRefused`, so no second code path is needed. Re-entering `merge` calls `landNow` again, which pushes the branch again.
- **No events.json regeneration.** `doc/events.json` holds no payload variants (`grep MergeBase doc/events.json` finds nothing), so `LandAgain` needs no regeneration and no `ELSEWHERE` row. No new event type is added.
- **No baseline raise.** The sleep is `Effect.sleep` inside the existing `Effect.gen`, with no new `async` and no new `Effect.run*`.
