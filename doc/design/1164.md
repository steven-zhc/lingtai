# Design: #1164, recording each invocation's sandbox boundary and refused connections

## The decision the ticket gets wrong: the boundary can't be appended "when conduct hands the invocation its decision"

`SandboxBoundaryRecorded` requires a `commandId` (`packages/domain/src/events.ts`: `SandboxInvocationKeys.commandId: z.string()`), and a sandboxed boundary carries the `policy` that was enforced. Neither exists when conduct hands over the decision:

- The `commandId` is minted inside `wrap` (`packages/sandbox/src/sandbox.ts:159`).
- The policy depends on `caller_additions`, which the runtime builds just before it wraps (`packages/agent/src/claude-sandbox.ts:204-208`, `packages/agent/src/codex-sandbox.ts:155-163`).

Both exist at one point only: the moment `wrap` returns, before the runtime spawns. That moment is already in code conduct owns. Every wrap any runtime or `run:` calls is a closure the conductor built:

- the agent closure in `sandboxOf`'s `wrap`, `packages/conductor/src/conduct.ts:871-889`;
- the `run:` closure, `makeRunSandbox(...).wrap`, `packages/conductor/src/sandbox-decision.ts:66-103`.

Codex goes through the first closure too: `codexSandboxedLaunch` calls `sandbox.wrap` (`codex-sandbox.ts:164`) on the same `RunSandbox` that `sandboxOf` builds.

**So do both appends inside those two closures. Do not put a field on `RunOutcome` or on the action result.** Inside each closure:

1. Call `api.wrap(input)`. Then compute `api.policyOf(input)` from **the same `input`**, so the recorded policy is the one srt was handed (1156 §9).
2. Append `SandboxBoundaryRecorded` with `{ kind: 'sandboxed', srtVersion: policy.srtVersion, policy }` and `wrapped.commandId`.
3. Then `Effect.addFinalizer` that does two things:
   - calls `api.refusedConnections(wrapped)`;
   - appends `SandboxConnectionsRefused` only when `worthRecording(read)` is true (`packages/sandbox/src/refusals.ts`, the last export).
4. Return `wrapped` unchanged.

The runtimes, `RunOutcome` and `ProcessAction`'s result do not change. The ticket's *Before you start* covers this departure: "where a name, field or call site differs from what landed, follow the code and keep the rules". The two rules still hold:

- **The read happens inside the wrap's scope.** A finalizer added after `api.wrap` runs before `api.wrap`'s own two releases (`sandbox.ts:160-173`), because a scope runs its finalizers in reverse order.
- **The read happens after the child exits.** Each caller's `Effect.scoped` encloses the spawn:
  - Claude Code, `claude-code.ts:456-490`: `runChild` runs inside the scope, in `onSuccess`.
  - Codex, `codex.ts:1515`.
  - `run:`, `process-action.ts:135-146`. Its comment reads *"The scope encloses the command: closing it cleans srt up, which must not happen under a running child."*

**The test the ticket's *Watch out* asks for is what proves the finalizer order.**

- Use a fake `SrtPort` whose `cleanupAfterCommand` and `unregisterCommandNetworkLists` empty its store.
- Wrap through the closure inside `Effect.scoped`, then let the scope close.
- Assert that the appended `SandboxConnectionsRefused` holds the fake's entries. If the finalizer ran after the release, the event would be missing.

## Where the store append goes: the hook server holds the pass stream's version during `implement`

At the implementer site, `server.register(runId, events.length)` happens before `dispatched.run` (`conduct.ts:4455-4458`). The hook server then appends at its own in-memory `run.version` and advances it (`packages/agent/src/hook-socket.ts:186-197`). Its comment: *"The stream version the next append expects."*

If the boundary is appended mid-run through `appendAt`/`appendNow` (a read of the head; `conduct.ts:765-771`), the hook server's version is left one behind, and its next `RunTouchedFile` append is refused.

**Write one helper in conduct, `appendInvocation(events)`.** Both closures and the unsandboxed paths below use it:

- When `server.get(runId)` returns a registered run, append at `registered.version` and set `registered.version` to the written version, the same way `hook-socket.ts:194-196` does.
- Otherwise use `appendAt(runId, …)`.

`implement`'s receipts already read `server.get(runId)?.version` after the run (`conduct.ts:4482-4483`). Because the helper advances that version, those receipts land at the right one with no change.

The `runId` here is always the pass's stream: the `runId` that `conduct` built at `conduct.ts:1298-1301`. It is never the dispatch's own id.

## Failures

- **The boundary append is refused.** Let the defect travel, as `appendNow` does (`conduct.ts:773-790`). The closure fails before returning `wrapped`, so nothing is spawned, and the pass's defect handler answers, as it does for a refused `RunStarted`. An unrecorded child is the outcome to avoid.
- **The refusals append is refused** (in the finalizer). Do two things:
  - remember the defect the way `appendFrom` does (`unappended ??= defect`, `conduct.ts:815-823`);
  - then `Effect.catchDefect`.

  The child has already run, and losing its `RunFinished`/`RunSpent` receipts over the refusals row is the worse loss.
- **A read that fails.** `refusedConnections` never fails: it answers `unreadable` (`sandbox.ts:183-195`). `worthRecording` is true for `unreadable`, so the event is appended.

## The keys

`step`, `action`, `runtime` and the dispatch's `runId` are not in the closures today. `sandboxOf` gains a third argument, `{ step, action, runtime }`. Each site passes the same identity its `RunPrompt`/`RunSpent` already uses:

| Site | `step` / `action` | `runtime` | `runId` in the event |
|---|---|---|---|
| implementer (`:4479`) | `implement` / `spec.name` | `dispatched.capabilities.id` | the dispatch's run id handed to `sandboxOf` (the `runId` in `sandboxOf`'s second argument) |
| fixer (`:4760`) | the fix site's `for` | `dispatched.capabilities.id` | `fixId` |
| judge (`:3096`) | `proposed` / `judge:${on.when}` (its `SpentFor` is `{ _tag: 'Judge', when }`, `:3058`) | the judge's runtime | `judgeRunId` |
| reviewer and design agent | the action's step, and `spec.name` | `deps.runtime.capabilities.id` | `reviewId` / `draftId` |
| `run:` | the step, and `action.name` | absent | `null` |

The judge's `runId` carries the judgement count, so two judges in one pass stay distinct even before `commandId`.

**Plumbing for the reviewer and design agent.** `sandboxFor` (`agent-action.ts:178`) is called with `(runId, cwd)` only. It gains the step and action:

- `from-recipe.ts` knows the step where it builds `makeAgentAction`/`makeDraftAction` (`from-recipe.ts:400-445`); put it on the spec.
- The two call sites (`agent-action.ts:1001`, `:1645`) pass it.

**Plumbing for `run:`.** `RunSandbox.wrap` (`process-action.ts:41-49`) gains a `keys: { step, action }` argument:

- `makeProcessAction` already has `spec.name`;
- `from-recipe.ts:369` adds the step to the spec.

## Unsandboxed and refused decisions

**Unsandboxed.** No closure is called: `sandboxOf` returns `{}` (`conduct.ts:854`), and a `run:` gets no `sandbox` (`from-recipe.ts:362-376`). These paths therefore append the boundary themselves, with a `commandId` minted the same way `sandbox.ts:159` mints one. Export that minting as a function from `@lingtai/sandbox`'s root, which loads no srt. Never append a refusals event on these paths.

- **The three conduct sites** call `appendInvocation` before `dispatched.run` when the decision is `unsandboxed`.
- **Reviewer and design agent.** `sandboxFor` becomes an `Effect` returning `{ sandbox } | {}`. Its unsandboxed branch appends the boundary. Both callers are already inside `Effect.gen`.
- **`run:`.** `ActionDeps` gains an optional `recordUnwrapped: (keys) => Effect<void>`, which conduct supplies. `makeProcessAction` yields it before `spawn(base)` when `spec.sandbox` is absent.

The boundary for each `unsandboxed` decision:

| Decision | Boundary |
|---|---|
| `off by choice` | `{ kind: 'unsandboxed', reason: 'off by choice' }` |
| `degraded` | the same, plus `why` |
| `refused` | `{ kind: 'refused', why }` |

Write that mapping as one pure function. **The `refused` row is reachable only in that function's test.** A `refused` pass returns `stage: 'recipe'` before the claim (`conduct.ts:956-964`), so no `pass-` stream exists to append to. Do not invent one. For the Done-when line *"a refused decision appends its boundary"*:

- the pure mapping test covers the boundary;
- a conduct test asserts that a `refused` pass appends no `SandboxBoundaryRecorded` anywhere.

**A wrap that fails under a sandboxed decision appends no boundary.** This covers a refusal before `wrap` (no token, a profile collision; `claude-sandbox.ts:160-196`) and a failure inside it. No child was started and no `commandId` was minted. The run's own `RunFailed` (`crash`) or the action's failed evidence (`process-action.ts:102-111`) is the record. Say so in a comment, because the schema's own JSDoc reads a missing boundary as *unknown*.

## Where the code lives

Write it as a new `packages/conductor/src/sandbox-record.ts`:

- the pure decision→boundary mapping;
- `recordingWrap(api, input, keys, append)`, which wraps, appends the boundary and adds the read finalizer.

`conduct.ts`'s closure and `makeRunSandbox` both call `recordingWrap`. `conduct.ts` is already over 4,900 lines, and both closures must behave identically.

All new IO is `Effect.gen`/`Effect.promise`, with no `async` and no `Effect.run*`, so `effect-ratchet.baseline.json` does not move.

## Tests (unit only, fake `Sandbox`/`SrtPort` and the memory store)

- **The closure.** A fake `spawn` (for `run:`, `spec.command`) or a fake runtime that calls `request.sandbox.wrap` reads the store at its "spawn" and asserts the boundary is already there. After the scope closes, the refusals event is there too.
- **The scope-close test** described above.
- **The hook-version test, at `implement`.** A fake hook server is registered, then a boundary is appended through `appendInvocation`. Assert two things:
  - `server.get(runId).version` advanced;
  - a following append at that version is accepted.
- **Unsandboxed.** One boundary, no refusals, for a conduct site, for `sandboxFor`, and for `run:`.

Nothing in this shape needs `pnpm test:integration`.

**What only a real run can settle:** the first sandboxed pass after the merge should show `SandboxBoundaryRecorded` before that action's first `RunTouchedFile` on the same `pass-` stream, and no hook append refused for version.
