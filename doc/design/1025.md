# Design note for #1025: the GitHub client, the App's token cache and the App reader become Effects

## Before you start: where things are now

  - `Effect.runPromiseExit` / `Cause.squash` are at `app.ts:299-301`.
- **The two copies of `request`:**
  - `githubJson` is at `app.ts:132-156`.
  - The client's `request` is at `client.ts:401-427`.
- **`installationForRepo`** is at `app.ts:159-181`, and its 404 → `NotInstalledError` is at `:179`.
- **Who uses `ghToken`:** only `client.ts:395`, and `gh.ts:110-112` is its face.

## The face rule decides how three functions must look

`effect-ratchet.test.ts:167-260` (`face()`) checks a face's shape rather than trusting the entry in `faces.json`. Three things follow.

1. **`runGitHub`** must be `export function runGitHub<A>(effect: …, signal?: AbortSignal) { return Effect.runPromise(effect, { signal }) }`.
   - One statement and nothing else.
   - `effect` and `signal` must both be its own parameters (`:243`, `:257`). That makes it the generic form.
   - It must not inspect an `Exit` (header comment, `:14`: *"a face that inspects an `Exit` … is a caller doing work, and is counted"*). So the `Cause.squash` unwrapping at `app.ts:301` cannot move into it. It doesn't need to: `runPromise` rejects with the failure itself.

2. **`appInstallations(reader)` and `installationRepositories(reader, id)`** take no `signal` today (`app.ts:357`, `:384`). Their faces are `return Effect.runPromise(appInstallationsEffect(reader))`, with no second argument. Don't add a `signal` parameter, because the signatures must stay as they are.

3. **`createGitHubClient` and `installationForRepo`** call `runGitHub`, not `Effect.run*`. `count()` therefore sees nothing in them, and listing them in `faces.json` would be refused (`:262`, *"has no counted run in its own span"*). Their bodies are one `return runGitHub(…)`. The helper that builds the promise object (`makeGitHubClient`) is an ordinary non-exported function that returns an `Effect.map`. It contains no `async` and no run.

## The error type has a fourth member, and it is already covered

The ticket's `runGitHub` signature lists `GitHubFailed | BodyChanged | NotInstalledError`. The link calls also fail with `PermissionDenied` (`client.ts:539-548`).

`PermissionDenied` is `class PermissionDenied extends GitHubFailed` (`client.ts:52`). Its comment says *"A `GitHubFailed` still, so an `instanceof GitHubFailed` check keeps catching it."* It inherits the tag `'GitHubFailed'`. So:

- It fits the union with no new member.
- `Effect.catchTag('GitHubFailed')` catches it.
- In `asLinkCall`'s `Effect.catchIf`, fail with `new PermissionDenied(err, 'issues', level, isGh(auth) ? 'gh' : 'app')`. The `kind` argument is part of the message (`:61-66`), so keep it.

Don't add a separate tag.

## `request` and `token` are members, so the arrows must keep their exact shapes

**`request` is generic.** `GitHubClient.request<T>(method, path, body?)` is public (`client.ts:185`) and has callers outside the package: `add-github.ts:107`, `onboard.ts:328`, `:553`, `wizard.ts:224`, `add-from-page.ts:110`.

- On the Effect side, `GitHub.request` is `<T>(method, path, body?) => Effect<T, GitHubFailed>`.
- If `Effect.fn` won't carry the type parameter under `tsc`, write `request` as a plain generic function that returns `Effect.withSpan('github.request')(…)`. Don't cast the generic away.
- The promise arrow is `request: <T>(m: string, p: string, b?: unknown) => runGitHub(github.request<T>(m, p, b))`.

**Only `getIssue` takes a signal.** It is the only method with one (`client.ts:248`). Every other arrow passes `undefined`, as their signatures do today.

**`token` is handed to git and called per invocation** (`repo/src/git.ts:75`, `await options.token()`). The arrow is `token: () => runGitHub(github.token)`.

- It must be a fresh call each time, never a memoised promise.
- Memoising would hand git an expired token after an hour, which is exactly what `client.ts:357-360` says the function exists to prevent.

## `githubJson` becomes the single request path

`githubJson` becomes the one request, as an Effect. It takes `(method, path, token, body?)`.

**Header and body rules come from the client's version** (`client.ts:403-414`):

- `content-type` is set only when `body !== undefined`, and the body is `JSON.stringify(body)`.
- App-side callers send no body (the token `POST` at `app.ts:265` has none), so this changes nothing for them.

**Where the `tryPromise` boundary goes.** Wrap fetch, the status check, the text read and `json()` in **one** `tryPromise({ try: async (signal) => …, catch })`.

- An `async` arrow inside `try` is a function the ratchet counts. Check what `count()` does with an arrow passed as an argument before relying on it.
- The safer shape uses no `async` at all:
  - `Effect.tryPromise((signal) => fetch(…, { signal }))`;
  - then `Effect.flatMap` on `response.ok`;
  - then a second `tryPromise` for `response.text()` or `.json()`.
- In every `catch`, map with the rule from `app.ts:279-282`: `err instanceof GitHubFailed ? err : new GitHubFailed(0, path, (err as Error).message)`.
- Keep the `204 → undefined` rule (`client.ts:425`).

`installationForRepoEffect` is `githubJson(…).pipe(Effect.map(toInstallation), Effect.catchIf(e => e.status === 404, () => Effect.fail(new NotInstalledError(owner, repo))))`.

## Token cache: the Ref holds the state, and the test cases must construct the cache once

`installationToken(auth, id)` becomes `Effect.gen(function* () { const refreshing = yield* Semaphore.make(1); const cached = yield* Ref.make<CachedToken | null>(null); return <the read> })`.

- The read keeps today's structure (`app.ts:285-292`).
  - `fresh` becomes `Ref.get` plus the 60 s margin, still against `Date.now()`. `app.test.ts` uses the real clock, and switching to `Clock` would put `TestClock` on the tests.
  - The fast path is checked outside the permit, and checked again inside it.
- The comment at `app.ts:241-255` stays as it is.

**The tests rewritten from `createTokenSource`** (`app.test.ts:130-190`):

- Each case does `const token = await Effect.runPromise(installationToken(auth, 42))` **once**, then runs `token` repeatedly.
  - Building it inside each read is the *one cache per call* trap from the ticket. The "fetches once" case is what catches that.
- The burst case uses `Promise.all` of four `Effect.runPromise(token)` against the one constructed cache. That reproduces today's coalescing test exactly.
- **The interruption case:**
  - Stub `fetch` so it settles only when `init.signal` aborts, rejecting with an `AbortError`.
  - Start a read with an `AbortController` and abort it. It rejects.
  - Swap in the normal stub and read again. It must resolve, and `issued()` must be 1. Without the permit's release the second read would hang, so give that test a short timeout so a regression fails rather than stalls.

## `createAppReader`'s per-installation map

The `Map<number, Effect<string, GitHubFailed>>` stays a plain closure value, as at `app.ts:324`. Inside `readAsApp`, a miss does `const t = yield* installationToken(auth, as); tokens.set(as, t)`.

There is a `yield*` between the `get` and the `set`. Two concurrent first reads for the same installation could therefore each build a cache. The cost is one extra token request, once per reader. It is not a correctness problem, so accept it rather than adding a lock.

The non-`GET` guard is `Effect.die(new Error(…))` with the sentence from `app.ts:327`. `runPromise` rejects with that same `Error`.

## `ghToken` is deleted outright, including from `index.ts`

The ticket contradicts itself here. It says delete the `ghToken` face, and it also says `index.ts` keeps every name except `createTokenSource`. But `index.ts:52` exports `ghToken`.

`git grep` finds no caller outside `packages/github` other than `faces.json:130`. The only other user is `packages/github/unit/gh.test.ts:3`, `:25-47`. So the call is:

- Remove `ghToken` from `gh.ts` and from `index.ts`, along with its `faces.json` entry.
- Rewrite `gh.test.ts`'s `ghToken` block against `ghTokenEffect(run)` run with `Effect.runPromise`. The assertions on message text (`/not installed/`, `/no token/`) are unchanged.

`gh.test.ts` is inside `packages/github`, so this stays within the ticket's file boundary.

Under `{ kind: 'gh' }`, `GitHub.token` is `ghTokenEffect(run)`. It is evaluated per read and never cached (`gh.ts:85`).

## `index.ts` additions

`installationToken` is already exported (`index.ts:11`). Its type changes from `Effect<string>` to `Effect<Effect<string>>`, and that is fine: nothing outside the package imports it.

Also add `ghTokenEffect` to the exports if `makeGitHub` callers will need it. The ticket's list doesn't require it, so it is optional.

## What the tests can and cannot show

Everything above is checked by the unit half: `effect-ratchet.test.ts` (the counts and the face shapes), and `app.test.ts`, `client.test.ts` and `gh.test.ts`.

One gap: the Next build (`apps/release/integration/build.test.ts`) is the only check that a server-only import doesn't reach a `"use client"` graph. This change adds no import to `apps/board`, so nothing in it should move. If a board file stops type-checking, the face is wrong (see the ticket's Watch out).
