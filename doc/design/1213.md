# Design note for #1213: a GitHub rate limit locks `acct-github`

The prerequisite work has landed in this worktree:
- `GitHubFailed` carries `ratelimitRemaining`, `ratelimitReset` and `retryAfter` (`packages/github/src/app.ts:79-95`).
- `classify` has the GitHub `rate-limited` rows (`packages/domain/src/failure/classify.ts:127-151`).
- `reachAccountLimit` takes an `Account` (`packages/conductor/src/account.ts:65-77`).

So this ticket only reads and wires what exists. Five decisions are not obvious from the ticket.

## 1. One predicate for "rate limited", shared by two readers

`asLinkCall` already calls `classify(...)?.kind === 'rate-limited'` inline (`client.ts:572-585`). Move that into one local `isRateLimited(err: GitHubFailed): boolean` in `client.ts`, and have both `asLinkCall` and the new hook call it.

- Pass `ratelimitRemaining` and `retryAfter` straight from the error. They are already `number | null`, and null means absent (`app.ts:83`).
- So "absent is not `0`" is #1132's parsing, and this ticket must not add a `?? 0` anywhere.
- The `classify` row for 403 + `/rate limit/i` detail with no headers (`classify.ts:148-151`) also counts as a limit. That is #1194's rule, so do not narrow it here.

## 2. Where the hook sits in `makeGitHub`

Wrap the **whole** `send` (token plus call), not just `githubJson`:

```ts
const send = <T>(method, path, body?) =>
  locking(Effect.flatMap(token, (t) => githubJson<T>(method, path, t, body)))
```

`locking(eff)` is `Effect.tapError(eff, (err) => err instanceof GitHubFailed && isRateLimited(err) ? options.onRateLimited?.(err) ?? Effect.void : Effect.void)`. The installation token is refreshed inside `token`, and a mint refused for rate is the same account limit. The one-off installation lookup at construction (`client.ts:555-556`) also goes through `locking`. It is a GitHub REST answer like any other, and in the conductor it is the first call of every look (`apps/cli/src/conduct.ts:286`).

The hook must not change the error:
- Type `onRateLimited` as `(failed: GitHubFailed) => Effect.Effect<void, never>`, so the client never sees a lock failure.
- The `tapError` re-fails with the original `err`.

`createGitHubClient` passes `options` through to `makeGitHubClient` (`client.ts:826-828`), so the new field reaches it without other changes.

## 3. The port is built in `packages/conductor/src/account.ts`

Add `githubLimitPort(store, log, now = () => new Date()): (failed: GitHubFailed) => Effect<void, never>` next to `reachAccountLimit`. It does three things:

1. Folds `acct-github`.
2. Calls `githubLimitUntil({ failed, now: now(), account: state })`.
3. Calls `reachAccountLimit(store, 'github', fields)`.

On failure it uses `Effect.catch` to write one line through `log` and succeeds. The fold and the transition are **one** read: `githubLimitUntil` runs inside the version-checked transition (`transitionAccount`), so `until` and `doublings` always come from the state the append is asserted against, and a lost race re-reads and recomputes. Do not split the deadline calculation from the transition: a person's lift in between would reset `doublings` while the appended deadline kept the old count.

Pass `onRateLimited: githubLimitPort(store, options.log)` at exactly the three places where the conductor-lock holder builds a client:
- `apps/cli/src/conduct.ts:287`: the look, and the client handed to the attempt as `common.client` (`:304`). This client also does the ticket listing (`:300`).
- `apps/cli/src/conduct.ts:742`: the `wantsMany` look.
- `apps/cli/src/run.ts:383`: `lingtai run`, which holds the same lock (#93).

`createGitHubClient`'s `options` type is `CreateClientOptions` in both `World`s (`conduct.ts:131`, `run.ts:279`), so no `World` signature changes. Do **not** add it in these places, which are the board's and the CLI's (the ticket's Out of scope):
- `packages/conductor/src/filter.ts:275` (`githubClientForEffect`)
- `packages/conductor/src/onboard.ts`
- `apps/cli/src/add-github.ts`

## 4. `githubLimitUntil` and the reducer

Put it in `packages/domain/src/failure/respond.ts`, beside `standDown` (`:347`). Its return shape matches `standDown`'s: `{ until, untilFrom, said, reason }`. Every append site then carries a `reason` sentence for the run log. Import nothing from `@lingtai/github`. Type the input structurally as `{ status, detail, retryAfter, ratelimitReset }`, because `domain` must not depend on `github`.

In order:
1. `retryAfter` gives `now + s·1000`.
2. Else `ratelimitReset` gives `new Date(s·1000)`. This is epoch seconds, not ms. The test of one hour out catches this mistake.
3. Else the doubling: `min(60_000 · 2^doublings, 3_600_000)`.

Every result is then `max(until, now + 60_000)`. Treat a non-finite or negative value as absent before choosing the branch, so `retryAfter: -1` falls through to the reset. `said` is `detail.trim().replace(/\s+/g, ' ').slice(0, 200)`, the same expression as `standDown` (`respond.ts:358`). Never use the path.

`reduceAccountEvent` (`packages/domain/src/account.ts:37-58`) works as follows:

- **`AccountLimitReached` that starts a lock** (`state.limit === null`):
  - `doubling` gives `doublings + 1`.
  - `retry-after` or `ratelimit-reset` gives `0`.
  - Every other `untilFrom` (the runtimes') leaves it unchanged. Runtime streams never use it.
- **`AccountLimitReached` while a lock stands** changes nothing (`:42-43`).
- **`AccountLimitLifted`**: `by` present (a person, `lifted()` at `:66-68`) gives `0`. `by` absent (the guard) leaves it unchanged.
- **`emptyAccount`** (`:34`) gains `doublings: 0`.

The doubling is counted from the state *before* the append. The first doubling lock is therefore 1 minute (2^0), the second 2 minutes, and the Done-when's `doublings: 7` gives 128 minutes capped to 60.

## 5. Schema and wording

- Add `'retry-after' | 'ratelimit-reset' | 'doubling'` to the enum at `packages/domain/src/events.ts:2403`. This is additive, and stored events still parse.
- Correct the doc comment above it (`:2391-2394`). *"Only an attempt meeting the wall appends it"* is false after this change. It should say the conductor's GitHub call that met the limit appends it too.
- Write the three sentences in `untilFromWords` (`packages/domain/src/locks.ts:104-119`). For `'doubling'`, say that GitHub named no time, and that this is one minute doubling for each limit met since the last header or person.
- Run `pnpm events:generate` and commit what it writes.

## Checks that stand in for integration

Everything here is reachable from the unit half. The client test uses the fake `fetch` the existing `packages/github/unit` tests use, plus `createMemoryEventStore()`. It asserts the following, in this order:

1. The 403 with `x-ratelimit-remaining: 0` fails with the **same** `GitHubFailed`, not a wrapped one.
2. One `AccountLimitReached` is on `acct-github`.
3. A second call appends nothing.

A port whose store `append` rejects must still fail the call with the original `GitHubFailed`. That assertion is what pins the "a failure to lock never changes the error" edge.

What actually happened in production is settled by the `AccountLimitReached` event's `untilFrom` and `until` on `acct-github`, next to the `AccountLimitLifted` whose `by` is absent at `until`.
