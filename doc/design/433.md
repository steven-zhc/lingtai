# Design: #433, `--defaults`

## Where it goes

Everything except the two parsers goes in `apps/cli/src/recipe-flow.ts`'s `askRecipe` (`recipe-flow.ts:138`). Both callers reach that one function: `first-project.ts:449` for the local branch of `init` and `add`, and `add-github.ts:291` for the GitHub branch of `add`. So putting the question there covers every entry point at once, and neither caller changes.

**Ask "use every default?" first, before the existing-file seed write at `recipe-flow.ts:145-148`.** Doing it first means the refusal's `kept` is `at.keptBeforeWrite`. A refusal with no terminal is then true on both paths: the seeds have not been written yet. Shape, as `doc/design/400.md` §*The shape* step 1 gives it:

- `name: 'every default'`, `flag: '--defaults'`, `choices: ['yes', 'no']`, `fallback: 'yes'`, `kept: at.keptBeforeWrite`.
- `given: at.flags['defaults'] !== undefined ? 'yes' : null`. The flag is a presence, never a value (see *Parsers* below).

On `yes`, every later call in `askRecipe` gets the wrapped world instead of `world`. That covers the `askAgents`, `askInstallAndBuild`, `askTickets`, `askKinds`, `askLanding` and `askLimits` calls, and `announce`. On `no`, nothing changes. With no terminal and no flag, `question()` returns `every default needs an answer: pass --defaults. <keptBeforeWrite>` (`question.ts:99-100`). That is the third Done-when, and it needs no code of its own.

## The wrapper

Put it in `question.ts`, beside `liveAsk`, as an exported `acceptingDefaults(world: QuestionWorld): QuestionWorld`. It carries the loop rule that `question()`'s own loop forces (`question.ts:97-105`), so it lives next to that loop:

- `log` passes through unchanged.
- `ask(prompt)` returns `''` and remembers `prompt`. If the prompt is **the same as the one just answered**, it returns `null` instead.

**Why "the same prompt as last time" is a safe test.** `question()` asks the same prompt again only after `validate` refused (`question.ts:104`). The one other loop that repeats a prompt is `setup-build.ts:304-316`, *"a command that must pass before review — empty when done"*, and it stops on the first `''`. So under the wrapper it never repeats. I checked every recipe prompt, and no two different questions in a row share text. The two model prompts are *"which model …"* (`agents.ts:200`) and *"on which model …"* (`agents.ts:279`). Do not key the check on the question's `name`: `ask` never sees it.

**A default that fails validation, concretely:** two runtimes signed in, no file, and no `--agent`. `currentAgent` is null (`agents.ts:173`). `detected` is null because more than one runtime is signed in (`agents.ts:181`). So the default is `''`, and `refuseUnlessOffered` rejects it (`agents.ts:155-161`). Under the wrapper, this logs that reason once and then refuses with *`which agent writes the change needs an answer: pass --agent <claude-code, codex>`*. Use this as the fixture for the second Done-when.

**Flags still win, and that needs no code.** `question()` returns at `question.ts:86-89` before it calls `ask`. The first Done-when should prove it with something visible in the written file, for example `flags: { defaults: '', rounds: '5' }` and then checking the rounds value in the written recipe. Use an `ask` that **throws**, not one that returns `''`, so the test proves that no question reached the person's terminal. Do not wrap a throwing `ask` in `acceptingDefaults`: the throw belongs to the world passed into `askRecipe`, and the wrapper should never call it.

## Parsers

- **`init`'s `parseArgs` (`init.ts:249-287`).** Add `--defaults` to the list, and give it its own branch ahead of the `value === undefined` check: it sets `flags['defaults'] = ''` and consumes nothing. It is the only flag that does this. Leave `repeated` alone.
- **`lingtai.ts`'s `parseFlags` (`lingtai.ts:385-410`) has a trap the ticket does not mention.** Its rule is that a flag is boolean only when the next token starts with `--` or there is no next token. So `lingtai add --defaults owner/repo` parses as `defaults: 'owner/repo'`, the slug disappears from `positional`, and the command goes down the no-positional path. Name `defaults` there as a flag that never takes a value. Add a unit assertion for that ordering if `parseFlags` can be reached from a unit test. If it cannot, because `lingtai.ts` calls `main()` on import (`add-github.ts:3-5`), say so in the commit.
- **Do not add `defaults` to the refusal list in `runGithubBranch` (`first-project.ts:528-539`), and do not add it to the delete list in `add-github.ts:310-320`.** Those lists hold answers to particular questions. `--defaults` is a policy, and `install.sh` passes it without knowing which branch the person will pick. On `init`'s GitHub branch it answers nothing and stays silent, which is correct: nothing there takes a default.
- Add `--defaults` to `init`'s `USAGE` string and to `add`'s help text.

## Scope: the recipe section only

The wrapper covers what `askRecipe` asks and nothing before it. In the local branch, the directory question and **the base question** (`first-project.ts:403-417`) run before `askRecipe` and still need `--local` and `--base` when there is no terminal. The base question has a `detected` default, but `question()` refuses a `null` from `ask` whatever the default is.

This is narrower than `doc/design/400.md` §*`init`: what moves*, which describes `init --store sqlite --local <dir> --defaults` completing with no terminal. That run still needs `--base <branch>`. The ticket's *Want* only places the question at the start of the recipe section. Do not widen it here. Say in the PR that extending `--defaults` to the base question is its own ticket.

## Tests the new question shifts

- **`unit/recipe-flow.test.ts`'s `defaultsWorld`** answers `''` to everything, so step 1 takes `yes` and those tests still pass. Put the three new tests in this file.
- **`unit/first-project.test.ts` and `unit/add-github.test.ts` script answers in order.** Each script that reaches `askRecipe` needs a leading answer for the new question, either `'no'` or `'yes'`. A test that expects `null` at a *specific* recipe question will now be refused at `every default` instead. Pass `flags.defaults` where the test is not about the recipe questions, and pass a scripted `'no'` where it is (`400.md` §*The unit tests*).
- **`integration/init.test.ts`** only has to compile. Its assertions run after the merge.

All three Done-when claims are unit tests through `askRecipe` with the `Map` file seam (`recipe-flow.test.ts:23-33`), so `HOME=/nonexistent pnpm test` checks them inside the pass.
