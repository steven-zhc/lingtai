The ticket already names most of the change. What follows is the part it leaves open: how `--fix` makes the move as one edit, the call sites it misses, and the order the edits must go in.

## 1. Where the refusal happens: already in place

`oldSpellingsIn` runs on the raw recipe with the preset already applied, before the parse, at both entry points:
- `resolve.ts:283`: `const old = oldSpellingsIn(applied.recipe); if (old.length > 0) throw new OldSpellingRefusedError(…)`
- `declared.ts:56`: the same, for the board's declared reading.

`lingtai doctor` reads the same list through the filter: `oldSpellings: err.spellings` (`packages/conductor/src/filter.ts:492`), shown as a row at `apps/cli/src/doctor.ts:2473`. `fixOldSpellings` (`doctor.ts:2507`) applies `refused.flatMap((s) => s.changes)` as one recipe change (`doctor.ts:2543`).

So adding one entry to `oldSpellingsIn` covers the refusal, the doctor row and the fix. Do not add a second check anywhere else.

No preset carries an assignee: `grep assignee packages/recipe/src/presets.ts` is empty, and `applyPreset` merges only `repo` and `runtime` (`presets.ts:127-141`). So a `runtime.assignee` that `oldSpellingsIn` finds is always the file's own, and a change written at that path edits what the person wrote.

## 2. The one real decision: the move replaces the `take: both` rewrite at `runtime`, it does not sit beside it

Today `takeBoth(raw['runtime'], 'runtime', ['runtime'])` (`resolve.ts:403`) emits `{ path: ['runtime','assignee','take'], value: 'all' }`. The changes run in order (`doctor.ts:2543`). If you keep that entry and add a move after it, the move copies the **raw** value, `take: both` included, into `source.assignee`. After the fix, nothing rewrites `source.assignee.take: both`, so the next resolve fails on Zod's enum with no `--fix` to offer. If the move runs first instead, the later `take` write brings `runtime.assignee` back.

So:

- **Remove** the `takeBoth(raw['runtime'], …)` call. The `steps.claim[*].queue` one stays exactly as it is.
- **Add** one `runtime.assignee` entry, with `at: 'runtime.assignee'`. A recipe still writing `take: both` there then gets one sentence and one change. Its changes, in this order:
  1. When the file has no `source.assignee`: `{ path: ['source','assignee'], value: { ...raw.runtime.assignee, take: take === 'both' ? 'all' : take } }`. Leave `take` out when the file did not write it, so the result stays as unwritten as the original was.
  2. Always: `{ path: ['runtime','assignee'], value: undefined }`. `undefined` removes the key with its comments (`emit.ts:58`, *"`undefined` removes what is there, with its comments"*).
- **When both spellings are written**, change 1 is omitted and the sentence says `source.assignee` is kept: for example, *"`runtime.assignee`: `source.assignee` is already written and is kept; delete `runtime.assignee`, or run `lingtai doctor --fix`"*. This is the ticket's edge, made concrete.
- Leave `runtime:` in place even if it ends up `{}`. An empty `runtime` mapping parses, and the resolve defaults a missing one anyway (`resolve.ts:295-300`). Do not add a rule to delete the block.

Update the `OldSpelling.at` doc example at `resolve.ts:331` and the bullet at `resolve.ts:347`.

**Do not** make `source.assignee.take: both` an old spelling. No file has ever written it, so it is just an invalid value, and Zod refuses it.

## 3. Schema

Write it as `source: z.object({ ...SOURCE_FIELDS, assignee: AssigneeRule.optional() })` at `recipe.ts:3228`, and not inside `SOURCE_FIELDS`, which `QUEUE_FIELDS` shares (`recipe.ts:1242-1244`). Remove `assignee` from `runtime:` (`recipe.ts:3494`).

Removing the field from the type is what makes `tsc` find every reader. Let it: each red `recipe.runtime.assignee` is a site to move, not one to cast around.

Three comments currently say the new key must not exist, and each is now false. Rewrite each one rather than deleting it:
- `recipe.ts:1009-1014`, which ends *"not `source.assignee`, which no file has ever held"*;
- `recipe.ts:3225-3227`, *"deliberately not here … a `source.assignee` nothing reads would be a key accepted and dropped"*;
- `recipe.ts:3473-3492`.

The rewritten version should say that `source.assignee` is the top-level spelling, `queue.assignee` is the step one, and `runtime.assignee` is an old spelling that `oldSpellingsIn` refuses.

## 5. `assigneeChanges` on a file that still has the old spelling

`assigneeChanges` writes only `['source','assignee']` (`answers.ts:179`). It does **not** also remove `runtime.assignee`.

On a recipe still in the old spelling, the draft that `lingtai add`, the setup page or the team switch writes then resolves with both spellings, and is refused by name with `lingtai doctor --fix` in the sentence. That is the same answer every other old spelling gives a draft today.

A writer that quietly migrated the file would be a second, unannounced road to the same edit. `--fix` stays the only one.
