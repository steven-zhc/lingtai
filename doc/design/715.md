## #715: design note

### 1. `init.test.ts`: one branch in the scripted `ask`, not a flag added to 35 calls

The test world's `ask` already answers every question that isn't about the database straight from the script, and records none of them as a step (`apps/cli/integration/init.test.ts:150-167`):

> The project and App questions (#393) are answered directly from the script, never through the `answers` queue and never recorded as a step: the Ctrl+C matrix below is about the database question alone.

#710's question belongs in that list. Add it beside `/which labels are work/` and `/use every default/`, matching on `/a GitHub App of its own/`. Both prompt variants in `askGithubAuth` contain that phrase (`apps/cli/src/github-auth.ts:159-161` and `:175-177`). Return `'app'`.

- **Don't push `'ask:...'` onto `seen.asked` and don't call `step()`.** Otherwise every `seen.asked` / step-order assertion in the Ctrl+C matrix moves.
- **Why `app` is the only answer that keeps today's path.** The world's `ghStatus` always answers `{ ok: false, reason: 'missing' }` (`init.test.ts:194`). So `askGithubAuth` takes the not-ready branch with `canSignIn` false and `choices: ['app', 'gh']`. Answering `gh` there is refused (`github-auth.ts:181`). `app` returns `{ auth: 'app', pending: true }`, and `first-project.ts:612-614` then carries on to the App question these tests were written against.
- **Why not `--github-auth app` on each call.** It would touch 35 argv lists. It would also change what `initCommand` is handed in tests that assert on the exact flags, and an `ask` branch answers a question it doesn't yet ask in one place. A test that is about `--github-auth` itself (grep for `github-auth` in the file first) keeps its flag. A given `app` returns at `github-auth.ts:133` before anything is asked, so the new branch is never reached for it.
- **The `expect(question).toMatch(/Postgres/)` at `:170` stays.** It is the tripwire that found this. The next question init adds should fail there the same way.

### 2. `--store` with no value: the exit code lives in `cli.ts`, not `wizard-options.ts`, and `:1069` can't see it

The ticket points at the parse in `wizard-options.ts`. That file only finds the flag: `valuelessFlag` (`apps/cli/src/wizard-options.ts:100`) returns the name. The exit code is in `runCli`, `apps/cli/src/cli.ts:1327-1331`:

```ts
const valueless = valuelessFlag(args.slice(1))
if (valueless !== null) {
  console.error(`lingtai ${args[0]}: --${valueless} takes a value`)
  return 1
}
```

That `return 1` has been there since `bf4aaad9` (*init and add parse through @effect/cli*). Make it `return 2`, which is the code `initCommand` gives every other usage refusal (`apps/cli/src/init.ts:305-308`, `refuse(..., 2)`). This also changes `lingtai add`'s valueless flags, because the same block guards both commands. That is the intent: it is the same usage error. Say so in the commit body.

**`init.test.ts:1069`'s second line can't pass from `initCommand` alone, whatever `cli.ts` says.** It calls `initCommand(flagsFromArgv(['--store']), w)`. `flagsFromArgv` (`apps/cli/test/flags.ts:24`) reads `argv[++i]!` past the end and stores `flags.store = undefined`. `init.ts:307` then reads `flags['store'] ?? null` as "not given", so the refusal at `:308` never fires and the wizard runs on. The refusal moved out of `initCommand` into `runCli` with `bf4aaad9`, and this line was left behind. So:

- **Keep** `expect(await initCommand(flagsFromArgv(['--store', 'mysql']), w)).toBe(2)` in `init.test.ts`. That refusal is still `initCommand`'s.
- **Move** the valueless case to where the refusal lives: a **unit** test that calls `runCli(['node', 'lingtai', 'init', '--store'])` and expects `2`. Several files in `apps/cli/unit/` already call `runCli(`, for example `version-cli.test.ts` and `five-commands-cli.test.ts`; follow their setup. The check at `cli.ts:1327` returns before the Effect run, so nothing under `$HOME` is read. Confirm that under `HOME=/nonexistent pnpm test`.
- **Don't make `flagsFromArgv` refuse or invent a value.** It is a test helper standing in for `flagsOf`, and making it act like `valuelessFlag` would be a second copy of the rule.

This is the one place the change is checked inside a pass. The unit test is what stands for the ticket's "exits 2" line. The six integration files are checked by the command in **Done when**, run by hand, and by nothing in `build`.

### 3. The other five files: assertions only, but read each before changing it

The ticket names the cause of each one, so there is no design here. One rule applies to all of them, from **Watch out**: confirm each new value is the deliberate change it is said to be.

| File | Confirm before changing the assertion |
|---|---|
| `doctor.test.ts:802` | The summary is `· N failed` and N equals the number of failed checks in that report. |
| `tell.test.ts:128`, `:139` | `{ recorded }` carries what the old return value asserted. Assert on its field rather than only on its shape. |
| `injected-store.test.ts:120` | `TicketContinued` sits in the stream where #683 puts it. Assert the whole sequence, not just its length. |
| `worktree.test.ts:317` | Only the message changed, to "the continuation is stale"; the outcome is the same. |
| `requeue.test.ts:107`, `:169` | `TicketReleased` arrives with the requeue, not instead of it. |

If any of these shows an outcome changing rather than a renamed value, stop and say so in the PR, as the ticket asks. Settle it by naming the event and field: for example, the `type` sequence on the ticket's stream that the requeue test reads.
