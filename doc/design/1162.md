# #1162: the shape

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

The ticket's own design holds, apart from one point: **the read it names cannot be filtered to a project as it stands.** The rest of this note covers what follows from that, plus the decisions the ticket leaves to the implementer.

## 1. `rowsOfType` has to return the stream id

`TypeRow` is `{ seq, schemaVer, data }` (`packages/event-store/src/queries.ts:82-86`). There is no stream id and no timestamp (both are added: `streamId` and `at`). The refusal payload doesn't name a project either:
- `SandboxConnectionsRefused` is `{ step, action, runtime?, runId, commandId, read }` (`packages/domain/src/events.ts:954-960`, `:988-994`).
- `runId` is `null` for every `run:` command, the base check included (`packages/conductor/src/sandbox-record.ts:17`, `packages/conductor/src/sandbox-decision.ts:121`). Those are the refusals people will actually see, such as `pnpm install`.

So "filtered in memory to the project's own streams" needs the row's stream.

**Decision:** add `streamId: string` to `TypeRow` and select `stream_id` in all three implementations:
- Postgres: `queries.ts:312`
- SQLite: `sqlite.ts:548`
- Memory: `packages/event-store/test/memory.ts:207-210`

Then extend `packages/event-store/test/queries-contract.ts` to assert it. Only the memory store's run of that contract is in the unit half. The Postgres and SQLite runs are integration, so before the merge the stand-in claim is the memory contract plus `tsc` on the two SQL mappers. Existing callers (`apps/cli` doctor, `log-predates-hold`) only gain a field. Add no new `async`: `packages/event-store` is held by `packages/domain/unit/effect-ratchet.test.ts`.

**How a stream maps to a project.** Refusals land on `pass-<uuid>` streams (`packages/domain/src/streams.ts:64`), and that name says nothing about the project. Join the two reads in memory:

1. Read `rowsOfType('TicketClaimed')`. For each row whose `streamId` is `ticketStreamsOf(project)` followed by digits alone (`ticket-app-tools-12` also starts with `ticket-app-`, so the prefix is not enough), its `data.runId` is an attempt stream of this project, and its issue number comes from `parseTicketStream`. `readAttemptStates` reads `eventStore.read(c.runId)` (`apps/board/src/lib/task.ts:2113`), so `runId` *is* the stream id.
2. Read `rowsOfType('SandboxConnectionsRefused')` and keep the rows whose `streamId` is in that set.

That is two whole-log reads, never one read per stream, as the ticket requires. A project name may contain `-`, so match on the full `ticket-<project>-` prefix. Don't use `parseTicketStream` to choose the project.

**The 14-day window** is keyed on each entry's `firstAt` (`events.ts:978`) for hosts, and on the row's `at` for caveats, which a refusal record dates by when it was appended. Drop telemetry entries (`e.telemetry`), as `sandboxViewOf` does (`apps/board/src/lib/sandbox-view.ts:286`).

## 2. Reusing S9's component without faking an attempt

`SandboxPanel` (`apps/board/src/app/sandbox-panel.tsx:77`) takes a whole `SandboxView`. That type is per-attempt: `PolicyGroup.runs`, `RunRow`s, and a *Runs* section that says "No wrapped run was recorded for this attempt." Do not build a fake `SandboxView` to get it to render.

Instead, split the file's existing sections into exported parts and keep `SandboxPanel` composing them:
- a `Blocked` part taking `SandboxView['blocked']`
- the writable / reachable / deny lists taking `PolicyGroup`-shaped rows

`PolicyGroup.domains` already carries `source: 'built in' | 'recipe'` (`sandbox-view.ts:72`). Grey the built-in rows using the same source tag, and make sure they have no remove affordance.

**Pure function for the project view.** Add a pure `projectBlockedOf(rows, project, now)` beside `sandboxViewOf` in `sandbox-view.ts`. That file's header says "no React and no reads", and that stays true. It returns `BlockedHost[]` plus caveats:
- `from` names tickets (`#1162`), not `step · action` labels.
- `allowHref` comes from the existing `allowHrefOf` (`:122`). That function already refuses metadata hosts and anything `isNetworkEntry` rejects.
- An `unreadable` read or a `complete: false` read becomes a caveat, as at `:276-279`. Unknown is never drawn as zero.

**The loader.** Put the read (§1) in a lib module of its own, for example `apps/board/src/lib/project-sandbox.ts`, not in `sandbox-view.ts`.

The board keeps promises (0101 §7, `effect-ratchet.test.ts:454`), so a page-edge `await` is the existing pattern, as in `apps/board/src/app/setup/repository/page.tsx:35`. Run `pnpm test`, and if the board's count moves, follow what the ratchet says rather than editing the baseline.

**On the page:**
- `Recipe` stays pure. It takes the recently-blocked part as a `ReactNode` slot, as it already takes `pause` and `banner` (`apps/board/src/app/recipe/[project]/page.tsx:200-205`).
- `RecipePage` passes an async server component wrapped in `<Suspense fallback={<Skeleton shape="lines" …/>}>`, the pattern at `apps/board/src/app/task/[id]/sandbox/page.tsx:43-46`.
- A failed read renders a stated sentence, never the empty list.

**The section itself** goes in `LeftColumn` as `<section className="rcard" id="sandbox">`, headed *configured now*.

## 3. What is configured now, and what is built in

- **The project's own entries** come from `view.recipe.sandbox`. The block is optional and never defaulted, so absent means off (`packages/recipe/src/recipe.ts:3430-3433`). That absent state is the *off — no sandbox block* case.
- **The built-ins** come from `@lingtai/sandbox`'s `.` entry only:
  - `BUILT_IN_DOMAINS` (`packages/sandbox/src/policy.ts:59`)
  - `denyRead(host)` (`:89`)
  - `filesystemFor(host, input)` (`:121`), evaluated with this machine's `HostFacts` and `WORKTREE_PLACEHOLDER` (`:205`) for the worktree.

  Use the same host facts the board already hands the save (`HOST_FOR_SAVING`, `apps/board/src/app/actions.ts:67`, `:1019`). If those facts can't be read, the built-in paths say so, and the domains still render.
- **On a failed recipe** (`!view.ok`), `LeftColumn` is not rendered today (`page.tsx:268`). The section still has to appear and show the built-ins, so render it outside `LeftColumn` in that case, under the refusal.

## 4. `?allow=<host>`: a pure function, run on the editor's current draft

- `RecipePage` reads `allow` and `r` next to `edit`. It sends the editor an `AllowRequest` (`{ host, nonce }`) and never a draft: the page cannot know what is typed in the editor, and a draft built from the disk bytes would drop earlier unsaved edits.
- The pure `withAllowedHost(text, host): string | null` lives in `packages/recipe` beside `write.ts`. It uses `parseDocument(text)`, then `setIn(['sandbox','network','allow'], …)` (which creates the block when absent), then `doc.toString()`. **`RecipeForm` runs it on its own current body**, so earlier unsaved edits and earlier hosts stay; a live CodeMirror is handed the result as a `push`, applied only when its `rev` is new (a push already in the props when the chunk mounts is in `initial` and is not replayed over later typing).
- It returns `null`, meaning no change, when:
  - the host fails `isNetworkEntry` (`packages/recipe/src/sandbox-block.ts:23`) or is in the metadata list;
  - the host is already in the list (the retry edge);
  - the text does not parse.
- **The page never judges a request against the disk.** A host that is on disk but was removed from the draft must be addable again, so the request always reaches the form.
- **A click is a new command; a render is not.** The links on the page carry `?r=<stamp>`, taken when the page renders. The stamp is read back from the URL, so a revalidation after a save (same URL) repeats nothing, and the next render's links carry a new stamp. `RecipeText` acts on a changed stamp: it opens a closed editor (`open`, which covers the *Add the block* link) and hands a request on (`allow`).
- **Creating the block also turns the sandbox on**, because `enabled` defaults to `true` (`sandbox-block.ts:36`). That is what the editor should show. Save still resolves it (`write.ts:250`).
- **The stale-save trap.** `loaded` stays `initial`, the file's bytes (`apps/board/src/app/recipe/[project]/recipe-form.tsx`); only the form's body carries the added host.
- **Unsaved has to be visible:** with an added host, show a line in the `FileBar` saying it is not saved.

**Tests:**
- The draft test asserts the output of `withAllowedHost` for three cases: comment kept, block created, no duplicate. It also asserts that the page's tree performs no write (`recipe.test.tsx` already scans the segment).
- The *prefilled Save succeeds* test drives `saveRecipeTextEffect` on the memory `RecipeFiles`, with `loaded` equal to the file's bytes and `text` equal to the draft.

## What would settle it in the log

To confirm a project's *recently blocked* is complete, compare two counts:
- the `SandboxConnectionsRefused` rows on its `pass-` streams;
- the `TicketClaimed.runId` values on `ticket-<project>-*`.

A refused row whose stream no claim names is a refusal this section drops. I could not read production `events`, so I don't know whether such rows exist.
