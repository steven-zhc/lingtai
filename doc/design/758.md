# #758: shape of the change

## The base name: the trial owns it, not the caller

The trial does not cut at the base its caller hands in. `cutOf` (`trial-build.ts:98-111`) reads, in order:
1. the file's `worktree.base` at `admit`;
2. then `repo.base`;
3. and only after that, `at.base`.

On an existing recipe, `askRecipe` writes the seeds, including `repo.base`, *before* the setup questions (`recipe-flow.ts:266-269`). So a base worked out by `first-project.ts:688` or `add-github.ts:379` before `askRecipe` runs can name a different branch from the one actually cut. "From the same value the trial cuts at" therefore means asking the trial itself, at the moment it is about to run.

**Decision:** change `tryBuild` from a bare function to a small object:

```ts
interface Trial { base: () => Promise<string>; run: (install, build) => Promise<TrialReport> }
tryBuild: Trial | null
```

- `trialBuild(at, deps)` returns `{ base: async () => (await cutOf(at)).base, run }`, and `run` keeps using the same `cutOf`.
- `tryTheBuild` calls `base()` just before it asks the trial question.

This is a small departure from the ticket's wording "`AskInstallAndBuildInput` gains `base`". The base still arrives on that input, but it travels with the runner, so the two can never be paired wrong. The cost is mechanical: every `tryBuild: async () => …` in `apps/cli/unit/setup-build.test.ts` (`:491`, `:516`, `:605`, …) becomes `{ base: async () => 'main', run: async () => … }`.

## Whether the file existed

`askRecipe` already computes `absent` (`recipe-flow.ts:264`). Pass `recipeExisted: !absent` into `askInstallAndBuild` (`:301`). That boolean alone picks the last sentence of the trial question:
- `Nothing is written yet.` when the recipe was absent;
- `This list is not written yet.` when it existed.

## The loop in `askInstallAndBuild`

Today the order is install, then build, then trial, run once each (`:383-390`). Make it:

```
install ← askInstall
loop:
  build ← askBuild(previous)
  loop:                       // inner loop is drop's
    tried ← tryTheBuild(install, build)
    passed | declined | keep | no checks → leave both loops
    drop  → build ← build minus the failed checks; empty → leave; else repeat inner (no trial question)
    edit  → if the failure was install/git/env/cleanup: install ← askInstall(previous) ; then repeat outer
```

The change-building that follows (`:392` onward) runs once, on the final `install` and `build`. This is what makes "written once" true.
- On an absent recipe, nothing is written inside the loop.
- On an existing recipe, `askRecipe`'s single `writeOrRefuse(setup.changes)` (`recipe-flow.ts:321-322`) is still the only write for this group.
- The agents were written before `askInstallAndBuild` was called, and are never asked again.

`tryTheBuild` returns one of:

```ts
| { ok: true; trial: TrialOutcome }
| { again: 'edit'; at: 'install' | 'build' }
| { again: 'drop'; failed: string[] }
| { refused: string }
```

`keep` is the `ok` arm with `failed-kept`. `TrialOutcome` keeps its shape (#754/#773 read it). It always describes the **last** trial run: `passed` with that trial's `ms`, or `failed-kept` with that trial's first failed command. When a drop leaves nothing, it is `not-run: 'no checks'`, and the existing guard at `:254` already produces that.

## Defaults on a second pass round the loop

`question()` puts `current ?? detected ?? fallback` in the brackets (`question.ts:130`). After `edit`, give `askInstall` and `askBuild` a `previous` argument:

- **`askInstall`:** the command just tried becomes `current`, and the detection `why` is dropped.
- **`askBuild`:** the list just tried replaces `defaultList`, and `why` is `[]`. This is the same rule #773 set for when detection explains a default: only when the default came from detection (`doc/design/773.md:108`), since detection is not what is on offer the second time.

Answering `yes` re-tries the same list. That is a real choice, for example after fixing the base. `no` goes into the typed loop as today (`:358-372`).

## What a failure is

The trial stops at the first failure (`trial-build.ts:188-195`), so a report holds at most one failed command, plus possibly a trailing `cleanup` result (`:204-212`). Sort the failed results by their `command`:

- **A check:** its command is in `build.map(b => b.run)` and is not `install`. Only a check offers `drop`.
- **Anything else:** `env` (`:132-135`), `git` (`:178-180`), `cleanup`, or the install command. These offer `keep` and `edit` only, and `edit` goes back to `at: 'install'`.
- **A `cleanup` that fails beside a failed check:** does not block `drop`. It is printed as it is today.

`drop` removes the failed checks' `run:` entries, matched by `run` text, and keeps the order. The passed checks stay as well as the not-run ones: the ticket's Fix says "runs the trial again on what is left". The next trial runs all of the remaining list in a fresh worktree, so a pass that only re-runs the not-run checks would have to repeat the install anyway. `drop` does not ask the trial question again, because choosing it was already a "try again".

## Flags, the refusals the ticket names, and no terminal

Before `edit` loops, check whether a question it would go back to is answered by a flag:
- `at: 'build'` with `input.given.build !== null` → refuse with today's sentence at `:306-308`, which names `--build`.
- `at: 'install'` with `input.given.install !== null` → refuse with `the trial's install failed and the list was not written — rerun with --install to give a different one`.
- A git or env failure where both are flags → refuse, naming `--install`. That is the first question `edit` would reach.

The choice question is:

```ts
question(world, {
  name: 'what to do with the failed build list',
  flag: '--check-build no, or --build <command>',
  given: null,
  prompt: 'keep the list as it is, edit it, or drop the checks that failed?',
  choices: ['edit', 'keep', 'drop'],   // ['edit', 'keep'] where drop is not offered
  fallback: 'edit',
})
```

With no terminal, `question()` refuses by `flag` as it does now.

- **`keep`** logs `kept the list as tried — it is written to ${recipePath(project, home)}`. Use the path itself, not a paraphrase.
- **The build prompt** is `Each pass runs these checks before review — keep this list? (yes / no to write your own)`.
- **The trial prompt** is ``Try them once now, on `${base}`, to see that they work? ${recipeExisted ? 'This list is not written yet.' : 'Nothing is written yet.'}``.

## `acceptingDefaults` and the repeated prompt

Under `--defaults` the trial is never reached (`check: 'no'`, `recipe-flow.ts:308`), so the guard on repeated prompts (`question.ts:95-112`) never sees this loop. A scripted test world that answers `edit` and then `yes` *does* ask the same build prompt twice. That is fine with a scripted world. It is the reason not to wrap one of these tests in `acceptingDefaults`.
