## Design note for #442: the task page draws exactly the resolutions `allowedResolutions` offers

### Where `reason` comes from: the lifecycle, not the row and not `waitsOf`

`standingOf` already folds the item's whole stream through `applyTicket` (`apps/board/src/lib/task.ts:703-711`). The `blocked` lifecycle already carries the wait's reason:

> `/** The \`WaitReason\` this block is, since #502 — what the event actually carries. */ reason: WaitReason` (`packages/domain/src/ticket.ts:43-44`)

So add `reason: WaitReason | null` to `StandingView` (the type is at `task.ts:~431`, next to `awaitingSha`). Set it in `standingOf` as `blocked ? life.reason : null`, next to `waitId` (`task.ts:752`). Do not read `task_view`'s `wait` column (`packages/projector/src/task-view.ts:942`), and do not call `waitsOf(events).at(-1)` again. `waitId` already comes from this same lifecycle, and taking the reason from it means a `waitId` and a `reason` can never name two different waits. `sendAttempt`'s `waitsOf(...).at(-1)` (`apps/board/src/app/actions.ts:641`) is a server action with no fold to hand, and it stays as it is.

`state === 'blocked'` at `standing.tsx:409` stays as the test for whether there is a wait at all. Treat `reason === null` on a blocked standing like the `waitId === null` branch at `:410-420`, which is defensive and draws only the refusal sentence. Put it in that same branch (`standing.waitId === null || standing.reason === null`). Do not add a second message.

### The moves row: one list, three slots

Compute `const allowed = allowedResolutions(standing.reason)` once. Draw in this order:

1. **`Approve` ∈ allowed.**
   - If `standing.awaitingSha !== null`, draw `<Decide …onSha={standing.awaitingSha}>` unchanged.
   - Otherwise draw `<p className="refusal">` with one sentence saying there is no sha to approve yet. Use the same class as the `:418` sentence.
   - `awaitingSha` now decides only *button or sentence*, never *whether the slot exists*. Do not test `unpushed` here: `allowedResolutions` has already dropped `Approve` (`wait.ts:297-300`).
2. **`AnswerQuestion` ∈ allowed.** Draw `<Requeue … asked question=…>` in answer mode. Its *Withdraw* button is the `Requeue` resolution, so this slot uses up `Requeue` too.
   - Rename nothing in `decide.tsx`. Pass `asked={allowed.includes('AnswerQuestion')}`.
   - The question comes from `standing.reason._tag === 'OwnQuestion' ? standing.reason.question : null`, not from `askedQuestion`.
   - `asked` and `askedQuestion` then have no reader in `standing.tsx`. They still have one in the card (`page.tsx:407-408` reads `card.asked`/`card.note`, which come from `board.ts`, not from `StandingView`). If nothing else reads the `StandingView` fields after this change, delete them, and their assertions at `standing.test.tsx:575-576,1236-1237` go with them.
3. **Otherwise, `Requeue` ∈ allowed.** Draw `Send` when there is a composed prompt (`outgoing !== null && outgoing.problem === null`), else draw `Requeue`. Drop the `!standing.asked` term from `sendable` (`:206`): slot 2 now catches an `OwnQuestion` before this point. Rewrite the #147 comment above `sendable` to say so rather than delete it.
4. **`Close` ∈ allowed.** Draw `Close`. Every row of the table carries it today, but it is drawn from the list now and not unconditionally (`:471`).
5. **`EditBodyAndRequeue`.** Draw nothing (#422/#520).

Leave each control's props untouched, including `Send`'s `primary`, which still reads `awaitingSha === null` (`:443`). That expression decides emphasis, not existence, and the ticket keeps behaviour. Rewrite the header comment at `:401-408` ("a question is open exactly when there is a sha it is about, so Approve is offered there and nowhere"): it states the rule this ticket removes.

`page.tsx` is not touched.

### What will visibly change, and the event that settles it

`awaitingSha` is set from one event only: `SignoffRequested{onSha}` on the run's stream (`task.ts:1169-1170`). Every Approve-allowed wait whose run never appended one will now show the no-sha sentence where it used to show nothing. That covers `CheckRefused`, `FixerDisagrees`, `MergeRefused`, and `ProposedEscalated` over `ReviewFindings`/`ReviewEmpty`/`CheckRefused`/`FixerDisagrees`. This is the case the ticket's Watch out names, and it is probably most of them, not an edge. Do not add a fallback to `headSha` to "fix" it. Inventing an `onSha` is the thing `approveCard`'s server-side check exists to refuse (`actions.ts:132`). Whether a given wait gets a button or the sentence in production is settled by whether `SignoffRequested` precedes `WaitStarted{reason}` for that run. Say in the commit which waits gained the sentence.

### The test

Move the event fixtures out of `apps/board/unit/waiting-card.test.tsx` (the `FIXTURES`/`add(...)` list from `:85`) into a shared module, `apps/board/test/waits.ts`. `test/` is the place for shared fixtures that are not tests themselves (CLAUDE.md). Both test files import it.

- The card's `expectedPill`/`expectedQuestion`/`expectedButtons` belong to the card. Either leave them in `waiting-card.test.tsx`, keyed by fixture name, or keep them on the shared entries and have the new test ignore them. Do not change what the card test asserts.
- The new test, in `standing.test.tsx`, goes through each fixture:
  - `standingOf(fixture.events, [])`, so the `reason` plumbing is under test and not hand-written.
  - Then `{ ...that, awaitingSha: SHA }` for the button case.
  - Render with the existing `render`/`moves` helpers (`standing.test.tsx:1145-1159`).
  - Map the drawn button labels back to resolution tags and assert the set equals `allowedResolutions(reason)` minus `EditBodyAndRequeue`.
  - Labels to tags: `Decide`'s label → `Approve`; `Answer` → `AnswerQuestion` (and `Withdraw` → `Requeue`); `Back to the queue` or `Send attempt N` → `Requeue`; `Close` → `Close`.
  - Run it once with `outgoing: null` and once with `OUTGOING` for the waits that allow `Requeue`, so `Send` is checked to take `Requeue`'s slot rather than add one.
- Two more cases:
  - An `unpushed` run: add `unpushed: {branch, said}` to a `ReviewFindings` reason, with `awaitingSha` set. No `Approve` and no sentence.
  - An Approve-allowed wait with `awaitingSha: null`: the sentence, and no `Decide` button.
- `HELD` (`standing.test.tsx:563`) needs a `reason`. Give it `CheckRefused` on a run (Approve, Requeue, Close), which keeps the existing Send/Decide cases at `:1162-1220` asserting what they assert now. The `asked: true` case at `:1232` becomes `reason: { _tag: 'OwnQuestion', … }`.

All of this is unit-level: `renderToStaticMarkup` plus a pure fold, with no store. `HOME=/nonexistent pnpm test` covers it, and nothing here needs the integration half.
