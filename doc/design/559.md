Both conflict with #574 and #575, which landed since the branch was cut. Resolve those two files by keeping main's behaviour for discussion answers and triage picks, and attempt 2's conflict card.

Both reviews refused the same flaw, and this note is about that flaw: **whether a continuation is scheduled is read from the lifecycle.** The flaw is at `agent/559:apps/cli/src/continue-conflict.ts:132-148`, in the `approved` branch:

```ts
if (lifecycle.status === 'approved' && lifecycle.grantRef !== undefined) {
  …
  log(`${ticketId} was already confirmed; its continuation is requested and waits for the conductor to claim it.`)
```

`approved` is the state both when `ContinueRequested` landed and when its retried append ran out of attempts:

- `resolve-wait.ts:345-373`: *"Never rethrown even once the retries run out … a continuation this call could not schedule is a gap for something else to notice."*
- `requestContinuation` is at `resolve-wait.ts:567-591`.

So the sentence above is false whenever `unscheduled` was returned.

## Where the fact lives, and how it is matched to "this wait"

The operator's decision says to read it *"on the item's stream"*. **It is not on the item's stream.** `ContinueRequested` is appended to `CONTROL_STREAM` (`'ctl-conductor'`, `packages/domain/src/control.ts:19`) by `requestContinuation` (`resolve-wait.ts:577-584`). Its payload is `{ project, issue, runId, by }` (`packages/domain/src/events.ts:1490-1495`), with **no `waitId`**. The intent is unambiguous: read the log, don't infer. So the read takes two streams.

Matching by `(project, issue, runId)` alone is wrong, for two reasons:

1. **The rows never expire.** `apps/cli/src/conduct.ts:248-256`: *"`control.continuing` only ever grows and a row an earlier pass already continued stays on the stream forever."*
2. **A new wait can carry the same run.** When the base moves under a confirmed continuation, `conduct.ts:996-1018` reopens the conflict as a **new** `WaitStarted` with the same `reason.run`. The run is the same, but the wait is new. An old `ContinueRequested` from the first confirmation has the same `runId`, and would read as *scheduled* for a wait nobody has confirmed.

**The rule is:** a `ContinueRequested` counts for wait `W` when:

- its `project`, `issue` and `runId` equal the ticket's and `W`'s run; **and**
- its envelope `seq` is greater than the `seq` of the `WaitResolved` whose `data.waitId === W`.

`seq` is global and increasing across streams (`packages/domain/src/envelope.ts:76-77`: *"Global order, assigned by the store"*). The memory store keeps that promise in tests (`packages/event-store/test/memory.ts:43`: *"`seq` is global and increasing, across streams, in append order"*). The way-out's re-append (`resolve-wait.ts:201-224`) also lands after the `WaitResolved`, so it counts by the same rule.

Put this in `@lingtai/domain` as a pure function beside `continueConflictRefusal` in `packages/domain/src/wait.ts`. It takes the ticket envelopes and the control envelopes, and returns one state:

```ts
continuationOf(ticketEvents, controlEvents)
  → { _tag: 'Open'; waitId }                                     // blocked on a conflict wait offering ContinueConflict
  | { _tag: 'Requested'; waitId; resolution; by; at }            // approved on W, a matching ContinueRequested after W's WaitResolved
  | { _tag: 'Unscheduled'; waitId; resolution }                  // approved on W, none
  | { _tag: 'Taken'; waitId; resolution }                        // W resolved ContinueConflict, lifecycle has left `approved` for a later state
  | { _tag: 'Reopened'; waitId; voidedWaitId; oldBase; newBase } // blocked on a new conflict wait whose run is the run a ContinueConflict wait resolved
  | { _tag: 'NotAConflict' }
```

`resolution` is the recorded `WaitResolved{ContinueConflict}` for `W`. If the lifecycle is `approved` but that resolution is not a `ContinueConflict`, the answer is `NotAConflict`.

These five states are what the Done-when's *"moved base/head, missing ref, failed dispatch and completed continuation distinctly"* asks for:

| state | what it covers |
|---|---|
| `Open` + one of the reader's refusals | moved head, missing ref, moved base |
| `Unscheduled` | failed dispatch |
| `Taken` | completed continuation |
| `Reopened` | the base moved after the confirmation |

The base-moved reopen also produces `Open` for the new wait. `Reopened` is that same moment told from the person's side: it says the earlier confirmation was voided and why.

## What each state prints, and the recovery command

The operator's rule is that *"a recovery command it prints must be one that works in the state the log shows."* Check each command against `resolveWaitHolding`'s way-out at `resolve-wait.ts:212-224`. That way-out fires only when all of these hold:

- the lifecycle is `approved`;
- `lifecycle.waitId === options.waitId`;
- `grantRef === resolution.ref`;
- `onSha === resolution.headSha`.

| state | the CLI prints | exit | the board draws |
|---|---|---|---|
| `Requested` | *"confirmed by {by}; the continuation was requested at {at} and the conductor takes it on its next pass."* No resend command: one is already on the log, and a second only adds a row `conduct.ts:271` walks past. If nothing starts, the next thing to try is `lingtai doctor`: the claim can be declined at GitHub and log nothing (`conduct.ts:283-286`). | 0 | the same sentence; **no** `ScheduleContinuation` button |
| `Unscheduled` | *"confirmed, but no continuation is on the log"*, and the command that resends the **recorded** resolution. This works because exactly the four way-out conditions above hold in this state. | 1 | `ScheduleContinuation` re-submitting the recorded resolution |
| `Taken` | *"continued; this wait is closed"*, plus the current lifecycle | 0 | the existing `afterMove` section; no button |
| `Reopened` | the earlier confirmation, why it was voided (old → new base), then the `Open` reading of the new wait | 0 | the new wait's card, with a line naming the voided confirmation |
| `NotAConflict` | `not waiting on a conflict that can be continued` | 1 | the existing cards |

**`Unscheduled` exits 1 on purpose.** A pipeline that reads the exit code must not treat "nothing will happen" as success.

The CLI reads `CONTROL_STREAM` through the same `deps` injection attempt 2 already uses (`deps.events`), so `apps/cli/unit/continue-conflict.test.ts` stays in memory.

The board's task loader already reads the control stream in the same `Promise.all` as the ticket (`apps/board/src/lib/task.ts:1803-1808`). Compute `continuationOf` from those envelopes and put the answer on `StandingView`, beside `approvedSha` (`task.ts:533-539`).

## Scope of the board change

`ScheduleContinuation` is drawn today for every `approved` item (`standing.tsx:1056-1065`). It is the same lifecycle inference for `Approve` and `GrantFixRound` too.

**Change it only where `continuationOf` answers a conflict state.** Leave the `Approve` and `GrantFixRound` path as main has it. Generalising the rule to those two touches #465's and #508's pinned behaviour, which is a separate ticket. Write one sentence in the `ScheduleContinuation` comment (`decide.tsx:188-210`) saying the conflict path reads the log and the other two do not yet.

For the conflict path, `ScheduleContinuation` needs a third variant that re-submits the recorded `ContinueConflict` resolution, not a `GrantFixRound` or an `Approve`. Attempt 2's `standing.tsx` hunk already adds one; keep it.

## Tests (unit half only)

- **`packages/domain/unit/continue-conflict.test.ts`** pins `continuationOf` with hand-built envelopes and explicit `seq`s:
  - **approved, no `ContinueRequested` → `Unscheduled`.** This is the Done-when's named test.
  - approved, a `ContinueRequested` after the `WaitResolved` → `Requested`.
  - **approved on a reopened wait `W2`, where the only `ContinueRequested` with this `runId` is older than `W2`'s `WaitResolved` → `Unscheduled`, not `Requested`.** This is the trap above.
  - a `ContinueRequested` for another issue, or another run → ignored.
  - lifecycle claimed after a `ContinueConflict` resolution → `Taken`.
- **`apps/cli/unit/continue-conflict.test.ts`**:
  - Replace attempt 2's *"approved ⇒ requested"* case with the two cases above, driven through the memory store. Assert the printed line.
  - For `Unscheduled`, assert that running the printed command against the same store reaches the way-out: one more `ContinueRequested`, no second `WaitResolved`. `resolve-wait.test.ts:1137-1205` is the model.
- **Board:** a `renderToStaticMarkup` case shows no `ScheduleContinuation` button for `Requested`, and one for `Unscheduled`.

Nothing here needs the integration half. The cross-stream `seq` ordering in Postgres and SQLite is already the store's contract (`packages/event-store/test/contract.ts`), and the memory store stands in for it in the unit half.

**No ADR changes.** 0118 §8 and 0120 §6 already say the continuation is requested on the control stream. This change only stops a reader from guessing whether it was.
