# #559: the shape

## What is already built, and what is left

#557 built the contract and #558 built the effect. **This ticket draws a card and adds a verb. It changes nothing about what `resolveWait` accepts.**

- `resolveWait` already validates and runs `ContinueConflict` (`packages/conductor/src/resolve-wait.ts:247-254`, `checkContinueConflict` at `:481-559`).
- The command it takes is `{ baseSha, headSha, ref, hunks: ConfirmedHunk[], grantExtraRound }` (`packages/domain/src/wait.ts:218-223`, `ConfirmedHunk` at `packages/domain/src/triage.ts:92-102`).
- Today there is no card. `standing.tsx:557-563` maps an advised `ContinueConflict` to `null`, `:579` filters it out of `drawable`, and `RESOLUTION_COPY` at `:60-64` still says *"Not runnable yet."* Remove all three, and `moves-by-wait.test.tsx:126-128`'s exclusion with them.

## The decision the ticket doesn't make: one reader, three callers

To build the command, a caller needs five facts that triage does not hold:

1. the counted hunks, from the mirror;
2. the saved ref and head;
3. whether that ref is still at the head;
4. whether the base is still at `baseSha`;
5. whether rounds are exhausted.

`checkContinueConflict` already gathers all five, then throws them away once they have been checked. If the board and the CLI each gather the same facts their own way, they will drift from the server and draw cards the server refuses. That is what the *Watch out* row means by a stale confirmation.

**So lift the gathering out of `checkContinueConflict` into one exported function, and have all three callers use it.** Put it in `packages/conductor/src/resolve-wait.ts`, or a new `continue-conflict.ts` beside it, exported from `@lingtai/conductor`:

```ts
readConflictContinuation({ store, ticketId, block, client, base, conflicts })
  → { ok: false; reason; detail }
  | { ok: true; baseSha; headSha; ref; grantExtraRound: boolean;
      counted: { path; line: number | null; excerpt: HunkExcerpt | null }[] }
```

**Callers:**

- `checkContinueConflict` becomes this read plus `continueConflictRefusal(...)` and the `saved.ref === resolution.ref` comparison.
- The board loader calls it to decide what the card can draw.
- The CLI calls it to decide what to print.

**`grantExtraRound` is `conflictRoundsExhausted(runEvents, headSha)`** (`wait.ts:431`). The person does not choose it; it is shown to them. `resolveWait` refuses a grant in both directions: `grant-required` and `grant-not-needed` (`resolve-wait.ts:463-471`). So the form must not offer it as a checkbox. It shows it as the cost line:

- `true`: *"The automatic rounds are spent; confirming grants one extra paid round."*
- `false`: *"Uses one of the recipe's remaining rounds."*

**Make the refusals distinct by name.** Today three different facts all come back as `reason: 'stale'`, at `:533`, `:543` and `:552`. The ticket requires moved head, missing ref and moved base to be handled distinctly, so give each its own reason:

| reason | when |
|---|---|
| `head-moved` | saved head ≠ the proposal's head |
| `ref-missing` | the remote ref is null |
| `ref-moved` | the remote ref ≠ the head |
| `base-moved` | the base tip ≠ `baseSha` |
| `base-missing` | the base tip is null |

Also:

- Keep the `savedHead` reasons as they are (`wip-head`, `branch-diverged`, `no-saved-head`, `:415-460`).
- Keep `conflicts-unreadable`.
- Add `too-many-hunks` when `counted.length > MERGE_HUNKS_ONE_BY_ONE`, checked in the reader before any form is offered.
- The tests that pin `'stale'` for the `ContinueConflict` paths need updating: `packages/conductor/unit/resolve-wait.test.ts:796` and `:834`. Leave `GrantFixRound`'s `'stale'` alone.

**A moved base is the common case, not an edge case.**

- `continueConflictRefusal` requires `resolution.baseSha === proposal.baseSha` (`wait.ts:466-470`).
- `checkContinueConflict` requires the base tip to equal that sha (`resolve-wait.ts:549-557`).
- So the card can be submitted only while `main` has not moved since the conflict was recorded.
- Nothing re-records a conflict when the base moves before a person confirms.

That makes the reader's refusal a **state the page renders, not an error after a click**. The card reads *"Cannot continue the conflict"* with the sentence, the same way `fixUnavailable` does for `GrantFixRound` (`standing.tsx:916-918`, `:965-971`). It has no submit button, and Requeue and Close stay drawn beside it. The server's own check is still the authority for a race between render and click.

## Hunk excerpts: a pure splitter in `@lingtai/repo`, shared with the count

The ticket says *inspect*, but `conflictedPathsAt` throws away the merged text it reads (`packages/repo/src/mirror.ts:189-195`). It keeps only marker line numbers and whole-file blobs.

**Do not add a field to `ConflictedPath`.** Triage puts that array into the prompt as-is (`apps/cli/src/triage.ts:555`), so any new field changes what triage is sent and what it costs.

Instead:

- Add a pure `conflictHunksOf(merged: string | null): { line: number; ours: string; theirs: string }[]` that splits on `<<<<<<<` / `=======` / `>>>>>>>`, bounded per side.
- Make `conflictedPathsAt` derive `hunkLines` from it. Keep the `[1]` fallback for a path with no markers (`:194`) with `excerpt: null`.
- That way the identity `(path, line)` the excerpt is shown under is the very one `resolveWait` counts by. The count and the excerpt cannot drift.
- Add a sibling `conflictHunksAt(...)` that returns the paths plus excerpts, and pass it to the reader as the board's and CLI's port.
- Unit-test the splitter (`packages/repo/unit/`). `conflictHunksAt` is git, so it is integration-only, and nothing in this pass checks it before the merge. The splitter test is what stands in for it.
- The board already reads the mirror in `task.ts` (`:71`, `:1828-1846`), so this is not a new dependency.

## The draft: a pure builder in `@lingtai/domain/wait`

Put two functions beside `continueConflictRefusal`:

- **`conflictDraft(counted, triageStatus)`**: one row per **counted** hunk, never per triage hunk. Triage's hunks are matched by `(path, line)`.
  - A triage `Mechanical` match preselects mechanical.
  - A `Divergent` match carries its `question`.
  - No match, or triage `NotDeclared`, `Failed`, `Queued` or `Running`, or the over-20 `hunks: []` (`apps/cli/src/triage.ts:478-485`): the row is **unclassified**, with no preselection.
  - A triage hunk the mirror no longer counts is listed as *"triage named a hunk the mirror no longer counts"*. It is never submitted. This happens when triage read an older head; the `triageHeadLine` at `task.ts:1842-1847` already says so.
- **`confirmedHunks(draft, choices)`** returns `ConfirmedHunk[]` or the list of rows still unconfirmed. It produces `Divergent` rows as follows:
  - a picked triage answer gives `behavior = answer.text` verbatim, `adopted = { questionId, answerId }`;
  - text the person wrote or edited gives `behavior = text`, `adopted: null`;
  - an unclassified row needs either *Mechanical* or non-empty text.

  The ticket's *"does not fabricate choices"* is this: an unclassified row has no default, and nothing submits until every row is answered. The schema's `.trim().min(1)` (`triage.ts:98`) is the backstop, not the check.

Both functions are pure, so `packages/domain/unit/continue-conflict.test.ts` pins every triage state against the same counted list.

## The board

**Loader** (`apps/board/src/lib/task.ts`): add `standing.conflictWork` beside the `fixWork` block at `:1850-1882`, guarded by `allowedResolutions(...).includes('ContinueConflict')`.

- It holds the reader's answer.
- It uses the same client construction as `:1862-1869`, plus `baseOf(recipe)` for `base`.
- Type it in `StandingView` beside `fixWork` (`:398`).
- In `visual-waiting.ts:419`, the preview should set it from fixture data, the way it sets `fixWork`.

**The card** goes in a new `'use client'` component in `decide.tsx`, beside `ContinueFixing` (`:265`), with a `continueConflictCard` server action beside `continueFixingCard` (`actions.ts:160`).

The action:

- takes `{ project, issue, waitId, baseSha, headSha, ref, hunks, grantExtraRound }`;
- builds the `ContinueConflict` resolution;
- passes `client`, `base`, and `conflicts` (production `conflictedPathsAt`) to `resolveWait`;
- returns the refusal's `detail` untouched.

**The card is the only place a conflict choice is made.**

- `allowedResolutions` gives a `MergeConflict` no `EditBodyAndRequeue`, so the triage band's picks feed nothing on a conflict wait. The band therefore shows each divergent question and triage's recommended answer as text, with no radios.
- The card's state is `Record<path:line, ConflictChoice>`, and only an `onChange` writes it. Triage's result is read at render to badge the recommended answer and is never copied into state, so advice arriving or changing cannot touch what the person chose. No effect watches triage.
- A divergent row has no default: the recommendation is badged, not checked, and submit stays disabled (naming the unanswered `path:line`s) until the person has chosen. Only a row triage classed Mechanical is pre-shown as mechanical. Rows with no advice (NotDeclared, Failed, running, or past 20 hunks' empty list) get Mechanical / Write the behavior.

**What the card shows, in order:**

1. `baseSha` on the base branch, and `headSha` on `ref` (short shas with full ones in `title`).
2. The cost line.
3. Every counted hunk as `path:line` with its status, its excerpt in a `<details>` (ours / theirs), and its choice.
4. The submit button.

**The submit button:**

- Label: **"Confirm behavior and continue on {ref}"**.
- Never "merge" or "land". The mockup's *"Merge on the branch"* (`doc/decisions/0118/Conflict.dc.html:198`) is the generic merge button the ticket forbids.
- Consequence copy says that an agent edits `ref`, then `build` and `review` run before anything reaches `merge` (0118 §8: *"The changed branch runs through `build` and `review` before `proposed` and the merge lane. This is not an `Approve`"*).
- While rows are unconfirmed, it is `disabled` with `aria-describedby` pointing at a line that names them.

**Recommended:** `ContinueConflict` is recommended when triage advised it **and** `conflictWork.ok`. Otherwise it maps to `null`, the way `GrantFixRound` falls back at `:562`. Triage's advice already cannot name it without a concrete list (`wait.ts:775-780`), so the over-20 case recommends `Requeue` by construction.

**After the click:**

- `task.ts:804-808`'s `continued` gains `ContinueConflict`.
- `standing.tsx:1062` passes `grant` for it too. `ScheduleContinuation`'s grant path calls `continueFixingCard` (`decide.tsx:243-245`), which resolves a `GrantFixRound` and would not match a `ContinueConflict`'s way-out check (`resolve-wait.ts:215-217`).
- Give `ScheduleContinuation` a `conflict` variant that re-submits the recorded resolution, read off the wait's `WaitResolved`.
- `unscheduled` is reported as *"confirmed — the continuation was not scheduled (…); click again to schedule it"*, never as plain success.

## The CLI: `lingtai continue-conflict`

The verb is in `apps/cli/src/continue-conflict.ts`, registered in `lingtai.ts` and its usage text. It reads through the same `conflictWorkOf` the board uses and submits through `resolveWait`, the one writer. Behavior text is prose, so choices go in a `--choices` JSON file rather than repeated flags. There is no `--draft` and no `--confirm`.

- **`lingtai continue-conflict <project> --issue <n>`** only inspects and appends nothing. It prints base/head/ref, every counted hunk with its text, triage's question with its recommended answer marked, the cost line, and the exact command to confirm with. If the conflict cannot be continued it prints why, with `lingtai requeue`, and exits 1.
- **Submitting** needs `--if-base <sha> --if-head <sha>`, which tie the confirmation to what was printed, and one of:
  - `--accept-recommended`: take triage's recommendation for each row it made one for;
  - `--choices <file.json>`: an object mapping `"path:line"` to `"mechanical"`, `{"answer": "<id>"}` or `{"behavior": "<text>"}`. A key naming no counted hunk is refused.

  Both may be given; `--choices` wins per row. A row with neither a recommendation nor a choice is named and nothing is submitted, so an unclassified hunk is never defaulted. `--grant-extra-round` is added when the printed text says the automatic rounds are spent.
- **Outcomes:**
  - `--if-base`/`--if-head` differ from the current ones: *"the conflict moved since you read it"*, nothing confirmed, exit 1.
  - `resolveWait` refuses: `not confirmed (<reason>): <detail>`, exit 1, including `already-confirmed` when the wait was confirmed with a different base, head or behavior.
  - Confirmed but `unscheduled`: a separate message, exit 1; run the command again to ask for the continuation.
  - Already confirmed (`rescheduled`): *"already confirmed; asked again for the continuation"*, exit 0.
  - On an already-confirmed wait, with no submit flags, it reports from the control stream whether a `ContinueRequested` is on the log (exit 0) or not (exit 1, with the command that resends the recorded confirmation).

## Whether a continuation was requested is read from the log

`approved` is left in place both when `ContinueRequested` landed and when its
retried append ran out of attempts (`resolve-wait.ts`), so the lifecycle proves
the confirmation and nothing about the scheduling. The row is on
`CONTROL_STREAM`, not the item's stream, and since schema version 2 it **names
the wait** it was asked for (`waitId`; a v1 row upcasts to `null`).
`conflictContinuationOf` in `@lingtai/domain/wait` reads it:

| Result | Means |
|---|---|
| `Requested` | a row naming this wait is on the stream |
| `LegacyRunRequest` | only a `waitId: null` row for the run: made before requests named their wait, and the conductor may still start the run on it |
| `NotRequested` | no row for this wait |
| `Unreadable` | the control stream could not be read; never drawn as `NotRequested` |

`conductWork` also requires a named row to match the ticket's current `waitId`,
so a first wait's row no longer starts a second wait on the same run, and
*not requested* means nothing will start until the resend runs. A `null` row
keeps matching on the run alone.

The CLI exits 0 for `Requested` and `LegacyRunRequest`, 1 for `NotRequested`
(printing the resend, which the way-out in `resolveWaitHolding` accepts and
which now appends a row naming the wait) and for `Unreadable` (printing a retry
of the same inspection). It reports the continuation as taken up, and exits 0,
only when the confirmed wait's own run is claimed again after the confirmation
(`continueTicket` appends that claim under the run it continues): leaving
`approved` proves nothing, since a close does too, and a claim under another run
is a fresh start from base. The
board draws no `ScheduleContinuation` for `Requested`, and a resend button for
`NotRequested`. The `Approve` and `GrantFixRound` paths still infer it from the
lifecycle.
