# #559: the shape

## Read this first: three attempts already exist, and two design flaws sank them

`agent/559-attempt-1`, `-2` and `-3` are on the remote. `-3`'s `doc/design/559.md` is mostly right, so reuse its parts where this note agrees with them. Those parts are: the reader lifted out of `checkContinueConflict`, distinct refusal names in place of `'stale'`, the pure `conflictHunksOf` splitter in `@lingtai/repo`, `conflictDraft`/`confirmedHunks` in `@lingtai/domain/wait`, the cost line built from `conflictRoundsExhausted`, and the button copy that never says "merge". You may cherry-pick its `packages/` commits. **Do not carry over its card state or its continuation reading.** Both were refused, and the run logs (`~/.lingtai/runs/lingtai/pass-73ffcc14-….log`, `pass-e9a30e8f-….log`) show why:

1. **Two controls for one choice.** Attempt 1 gave the card its own state, and a reviewer found that it ignored the triage band's radios. Attempts 2 and 3 then spent seven rounds making the card follow the band: by index, by question id, by content, and by a "stamp" change detector. The last refusal (`continue-conflict.tsx:80`, judged `claim`) was *"arriving triage advice silently deletes the person's existing intent"*. The detector read a recommendation appearing as a person's click.
2. **Scheduling read off the lifecycle, then off a guess.** Attempt 3 stopped reading `approved` and inferred the request from the control stream: any row for project/issue/run whose `seq` came after the wait's `WaitResolved`. The reviewer's W1/W2 scenario broke that. W1 is confirmed and requested; the base moves; W2 opens on the **same run**; W2's request append fails. The inspection says *unscheduled*, but `conduct.ts:274` dispatches W2 on W1's row, because it matches on run only.

The two decisions below remove both flaws.

## Decision 1: `ContinueRequested` names the wait, and the conductor honours the name

Today `ContinueRequested` is `{ project, issue, runId, by }` (`packages/domain/src/events.ts:1490-1495`). It is appended on `CONTROL_STREAM`, **not** the ticket's stream, and it stays there. `resolve-wait.ts:347-355` gives the reason: *"on the control stream rather than the ticket's, so a store that refuses it costs this approval nothing"*. The operator's "on the item's stream" means *this item's rows on the log*. The append does not move.

"A `ContinueRequested` for the current wait" can only be a fact on the log if the row carries the wait. So:

- **Add `waitId: WaitId | null` to `ContinueRequested`.** Bump it in `BUMPED` (`events.ts:~2010-2034`, `SCHEMA_VER` is derived at `:2036`) to `2`. Add a `1 → 2` step in `UPCASTERS` (`packages/domain/src/upcast.ts`) that sets `waitId: null`. `upcast.ts:54` requires *"Add a step here in the same commit that bumps that type's `SCHEMA_VER`"*.
- `requestContinuation` (`resolve-wait.ts:568`) takes the wait id. Both call sites pass it: the way-out at `:224` passes `options.waitId`, and the first append at `:374` passes the wait it just resolved.
- `control.ts:204-211` folds `waitId` into `continuing`, and the type at `:88` gains it.
- **`conduct.ts:274` also requires `c.waitId === null || ticket.lifecycle.waitId === c.waitId`.** This one-line change is what makes the inspection true. A row names the approval it was asked for, so W1's row no longer starts W2, and *"not scheduled"* means nothing will start until the printed resend runs. A `null` row comes from a legacy v1 payload and keeps today's run-only behaviour. Pin it in the unit test that covers `conductWork`'s continuing walk, or add one beside it: a W1 row plus a W2 `approved` lifecycle claims nothing.

The reading is one pure function in `@lingtai/domain/wait`, used by the board loader and the CLI:

```ts
continuationOf({ waitId, project, issue, runId, own, control: readonly Envelope[] | 'unreadable' })
  → 'Requested' { by, at } | 'NotRequested' | 'LegacyRunRequest' | 'Unreadable'
```

- `Requested` means a row exists with `waitId === W`.
- `LegacyRunRequest` means only a `waitId: null` row for the same project/issue/run exists. Say it as it is: *a request made before requests named their wait; the conductor may still start this run on it*.
- `Unreadable` means the control stream could not be read. Attempt 3's first finding was `task.ts:1874` swallowing the read failure as `[]` and drawing *unscheduled*. A read failure is never `NotRequested`.

Done-when #1's unit test is `NotRequested` for an `approved` lifecycle on W with an empty control stream, plus one with only a W1 row.

## Decision 2: the card is the only place a conflict choice is made, and only the person's clicks are state

`allowedResolutions` gives a `MergeConflict` exactly `Requeue`, `Close` and, when continuable, `ContinueConflict` (`wait.ts:301-303`, `:411`). It gives no `EditBodyAndRequeue`. So the band's picks feed nothing on a conflict wait: `TriagePicks`' `text` only reaches the body editor and the answer box (`triage-picks.tsx:73-78`, `:103-123`). Attempts 2 and 3 synced against a state with no reader.

- **In the band's `ConflictingHunks` branch, stop rendering `TriageChoices`** (`standing.tsx:205`). Show the question and triage's recommended answer as text, and leave `UndecidedQuestion`'s radios (`:148`) alone. Also drop the `ConflictingHunks` arm of `triageQuestions` (`standing.tsx:641-646`), so the band's index space no longer contains conflict questions.
- **The card's state is `Record<HunkKey, PersonChoice>`**, where `HunkKey` is `` `${path}:${line ?? ''}` `` and never an index or a question id. That key is the `(path, line)` identity `ConfirmedHunk` is accepted by (`triage.ts:87-89`). `PersonChoice` is `'mechanical' | { answerId } | { behavior: string }`. **Only an `onChange`/`onClick` writes it.** Triage's result is read at render to *show* the recommendation and is never copied into state. An arriving or changed triage result therefore cannot change what the person chose. No `useEffect` watches triage, and no stamp is compared.
- **A divergent row needs an explicit choice.** The recommended answer is badged, not pre-checked. That is *"confirm each behavioral choice"*, and it also means a live refresh between reading and clicking cannot submit something the person never saw. A row triage classed `Mechanical` is pre-shown as mechanical, because it carries no behavior. An unclassified row has no triage match: NotDeclared, Failed, Queued, Running, or the over-20 `hunks: []` (`wait.ts:761-766`). It has no default either. Those rows render *Mechanical* / *Write the behavior* controls, and the submit stays disabled, with `aria-describedby` naming the unanswered `path:line`s. That covers done-when #3.
- Choices are scoped to the wait, the way `TriagePicks` scopes its own (`triage-picks.tsx:66-68`): state written under another `waitId` reads as empty. The pure `confirmedHunks(draft, choices)` builds the payload. A picked answer gives `behavior = answer.text` and `adopted = { questionId, answerId }`. Written text gives `adopted: null`.

Add a unit test (`renderToStaticMarkup` plus the pure builder) where triage advice arrives after a written behavior and `confirmedHunks` still returns the written text. That is the scenario that sank attempt 3.

## The card and the verb: outcomes that must stay distinct

These are `-3`'s choices with its findings fixed:

- Refusals the reader knows before a click (`head-moved`, `ref-missing`, `ref-moved`, `base-moved`, `base-missing`, `too-many-hunks`, `conflicts-unreadable`) render as *"Cannot continue the conflict"* with the sentence and no submit button. Requeue and Close stay drawn beside it: `drawable` at `standing.tsx:566` stops excluding `ContinueConflict` and keeps everything else.
- `unscheduled` is tested with `!== undefined`, never for truthiness. `requestContinuation` returns `err.message`, which can be `''` (attempt 3's blocker at `actions.ts:237`). The retry control stays drawn after a failed retry and does not swap itself for text.
- On an `approved` lifecycle whose `WaitResolved` was a `ContinueConflict`, the board shows a resend button that resubmits the **recorded** resolution only for `NotRequested`. That resend is the way-out `resolve-wait.ts:205-221` accepts, and it now appends a row naming W. `ScheduleContinuation`'s grant path calls `continueFixingCard` (`decide.tsx:243-245`) and would not match a `ContinueConflict`, so do not route the resend through it.
- `lingtai continue-conflict <project> --issue <n>` reports from `continuationOf`. It also reports a **completed** continuation distinctly: the latest `WaitResolved{ContinueConflict}` is followed by a lifecycle that has left `approved` (running, landed, or blocked on a newer wait). Attempt 3 printed *"is not waiting on a conflict that can be continued"* there and exited 1.
- Each recovery command it prints must be accepted in the state it just reported. `NotRequested` prints the resend, `Unreadable` prints a retry of the same inspection, and `Requested` prints none.

## Checks

The unit half covers all of it: `continuationOf`, the upcaster step, the `conduct.ts` wait filter, `confirmedHunks` under arriving advice, the splitter, the reader's reasons via stub ports, and static-markup tests (no submit button under a refusal, no "merge" in the card, Requeue and Close present). Real refs and the real merge-tree are integration-only. The stub-port and splitter tests stand in for them before the merge.

No ADR changes. The row naming its wait does not change 0120 §6's *what tells the next pass which issue to look at*.
