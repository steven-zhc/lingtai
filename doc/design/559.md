# Design note — #559, `ContinueConflict` on the board and the CLI

## What is already built, and what this ticket adds

The contract and the continuation are already in the code. This ticket adds the two callers and the presentation, and nothing new in the domain.

- `Resolution.ContinueConflict` carries `baseSha`, `headSha`, `ref`, `hunks` (1–20 `ConfirmedHunk`s) and `grantExtraRound`. See `packages/domain/src/wait.ts:218-226`: *"**every** counted hunk with the behavior they confirmed. A hunk left out is not "mechanical"; the command alone says what was confirmed."*
- `ConfirmedHunk` is at `packages/domain/src/triage.ts:92-101`. The authority is `behavior`. `adopted` is `null` whenever the person wrote or edited the text, *"and always `null` without a triage result."*
- The pure refusal is `continueConflictRefusal` (`wait.ts:458-486`). The rounds read is `conflictRoundsExhausted` (`wait.ts:431-445`).
- `resolveWait`'s effectful checks are `checkContinueConflict` (`packages/conductor/src/resolve-wait.ts:478-560`). `conduct.ts:997-1022` reopens the wait when the base moves after confirmation.

**Nothing in production calls `resolveWait` with `ContinueConflict` today.** Its two required ports, `base` and `conflicts` (`resolve-wait.ts:145-155`), are passed only by tests; a grep for `conflicts:` under `packages/conductor/src` finds only the doc comment. Without them every call is refused `no-base` / `no-conflicts` (`:485-499`). Wiring those two ports is half of this ticket.

The board hides the move on purpose until this ticket lands:
- `standing.tsx:552-556` nulls `ContinueConflict` as a recommendation.
- `standing.tsx:574` filters it out of `drawable`.
- The copy at `standing.tsx:57-61` says *"Not runnable yet."*

All three go.

## The one decision: the rows come from the mirror's count, and triage is laid over them

`resolveWait` checks the submitted hunks against `conflicts(baseSha, headSha)` — the mirror's count — and never against triage. `HunksMismatch` is raised when the two sets of `(path, line)` differ (`wait.ts:473-482`). *"It never takes a triage status, so the same command validates the same way whether triage was absent, failed or done"* (`wait.ts:450-451`).

So the form must be built from the same count, flattened exactly as `resolve-wait.ts:513` flattens it: `paths.flatMap(p => p.hunkLines.map(line => ({ path: p.path, line })))`. Triage's `ConflictingHunks.hunks` is matched onto those rows by `(path, line)`. It never supplies rows of its own.

This one rule answers each case the ticket's *Watch out* row names:

| Triage status | Every counted row starts as | The person must |
|---|---|---|
| `Done` / `ConflictingHunks`, row matched as `Divergent` | the question and its answers, recommended answer preselected | keep it, pick another answer, or write their own text |
| `Done` / `ConflictingHunks`, row matched as `Mechanical` | Mechanical, preselected | keep it, or change it to divergent and write the behavior ("permit correction") |
| `NotDeclared`, `Queued`, `Running`, `Interrupted`, `TriageFailed`, any other cause, or a row triage did not classify | unset | choose Mechanical or write the intended behavior; submit stays disabled until every row is set |
| counted total > `MERGE_HUNKS_ONE_BY_ONE` (with or without triage's mechanical `hunks: []`, `apps/cli/src/triage.ts:477-485`) | no rows at all | — the form is not drawn, only *"N hunks — past one-by-one; start over from the new base"*, with Requeue and Close beside it |

The >20 case is keyed on the **count**, not on triage. Triage can be absent and the conflict can still be 41 hunks. A form must not be fabricated for a set that the schema's `.max(20)` would refuse to parse anyway.

### The shared builder

Put two pure functions in `packages/domain/src/wait.ts`, next to `continueConflictRefusal`. Both the board and the CLI use them, so neither keeps a rule of its own (0118 §1: *"none keeps a rule of its own"*).

- `conflictRows(counted, triageStatus)` returns the rows above, or `{ tooMany: total }`.
- `confirmHunks(rows, choices)` returns `ConfirmedHunk[]`, or the rows still unset.

`adopted` is `{ questionId, answerId }` only when the chosen answer's text is taken unchanged, and `behavior` is that answer's text word for word. An edited text gives `adopted: null`. Unit-test both against all four rows of the table. These tests are the unit-level claim that stands in for the board, because a server component that runs git cannot be rendered in the unit half.

Import them in the client component only through `@lingtai/domain/wait`, which is already client-safe enough for `standing.tsx:3`. A server-only import that reaches a `"use client"` graph is seen only by `apps/release/integration/build.test.ts`, which runs after the merge (CLAUDE.md, #230).

### CLI — `apps/cli/src/continue-conflict.ts`
Wire it in `lingtai.ts` next to `grant-fix-round` (`:1282`). `parseFlags` is single-valued (`lingtai.ts:652`, `Record<string, string>`), so per-hunk choices go in a file:

```
lingtai continue-conflict <project> --issue <n>
    # prints base/head/ref, every counted row with triage's question and
    # recommendation (or "no advice — your intent is required"), the rounds
    # line, and the exact command to confirm. Appends nothing.
lingtai continue-conflict <project> --issue <n> --if-base <sha> --if-head <sha>
    (--accept-recommended | --choices <file.json>) [--grant-extra-round]
```

- `--choices` maps `"path:line"` to `{ "answer": "<id>" }`, `{ "behavior": "<text>" }` or `"mechanical"`, and is applied over the recommendations through `confirmHunks`.
- `--accept-recommended` with any row unset (no advice) is refused, and the refusal names the rows.
- `--if-base` and `--if-head` are required to submit. They are what tie the confirmation to what was printed.

## Distinct outcomes: one reason each

Today every staleness check in `checkContinueConflict` answers `reason: 'stale'` (`resolve-wait.ts:533-558`), with only the detail text differing. The done-when needs these told apart, so split them in place:

- `head-moved`: the saved head or ref differs (`:533`).
- `ref-missing`: the remote is `null` (`:542`, `remote === null`).
- `ref-moved`: the remote differs (`:542`).
- `base-moved`: `:551`.

`not-blocked`, `busy`, `hunks-mismatch` and `conflicts-unreadable` are already distinct. Update the assertions in `packages/conductor/unit/resolve-wait.test.ts` that expect `'stale'` for these paths.

**Failed dispatch.** `ok: true` with `unscheduled` set means `WaitResolved` committed but `ContinueRequested` did not (`resolve-wait.ts:164-171`). Never print a bare "continued" for it.
- On the board, the `ScheduleContinuation` path already works for this. A `ContinueConflict` folds to `approved` with `grantRef` set (`ticket.ts:356-372`), which is exactly what the `GrantFixRound` way-out at `resolve-wait.ts:218-220` accepts. Widen `grant=` at `standing.tsx:1057` to `GrantFixRound || ContinueConflict`.
- In the CLI, a rerun finds the lifecycle `approved`. Resend the resolution recorded on that wait, verbatim, which takes the way-out at `:216-217`. Accept that state up front, as `grant-fix-round.ts:35-38` does.

**Completed continuation.** The way-out returns the same `{ ok: true }` as a first confirmation, so the callers cannot tell a repeat from a new decision. Add `rescheduled: true` to the way-out's return (`resolve-wait.ts:225`). The CLI and the board then say *"already confirmed; asked again for the continuation"* rather than reporting a second decision.

**After the move.**
- `task.ts:804-808`'s `continued` covers only `GrantFixRound`. Add `ContinueConflict`, with the reason *"Continuing the preserved conflict with the confirmed behavior; build and review run again."*
- When the daemon reopens the conflict because the base moved after confirmation (`conduct.ts:1007-1016`), the new wait is drawn as usual. Also add one line: *"An earlier confirmation was against base `X`; the base moved, so it granted nothing."* The trigger is a `WaitResolved{ resolution._tag: 'ContinueConflict', baseSha: X }` followed by a `WaitStarted` on the same run whose `reason.proposal.baseSha` differs. Those two events, in that order, are what show that a stale confirmation was not taken as success.

## What checks it

All of the following are unit-level, and `pnpm test` reaches them:
- `conflictRows` and `confirmHunks`, across the four cases.
- The split refusal reasons and `rescheduled`, through `resolveWaitHolding` with fake ports.
- The CLI command, with injected ports and a memory store.
- The board's selection logic in `moves-by-wait.test.tsx`, which already names `ContinueConflict`: the card is drawn exactly where `conflictWork` has rows, and absent where it has `tooMany` or a refusal.

`conflictedPathsAt` and the Next build are integration-only. Nothing in this pass verifies the git extraction or the client-import boundary, so keep the extraction in the pure helper and the client imports to `@lingtai/domain/wait`.

No accepted ADR is contradicted. This implements 0118 §1's row and §8 as written.
