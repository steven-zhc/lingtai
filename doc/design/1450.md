# #1450: the shape

## Code that already does this, and why `clean` doesn't reuse it

The ticket says *"Nothing looks for what was left"*, and that is not quite true. When the daemon starts, `reconcileEffect` removes orphan worktrees and the logs of landed runs (`packages/daemon/src/reconcile.ts:799`, `:314`, `:389`). `lingtai doctor` lists the same items with `dryRun: true` (`apps/cli/src/doctor.ts:1878-1883`). So the first thing the implementer will want to do is call `findOrphansEffect` / `findOrphanLogsEffect` from a new command. **Don't.** They are built for a process that holds the conductor lock, and three of their rules are wrong for a command that runs beside a live daemon:

1. **A failed ticket read becomes backlog, so the worktree is treated as an orphan.** `ticketOf` catches every failure as `reduceTicket([])` (`reconcile.ts:136-139`), which reduces to backlog. `findOrphansEffect` then decides *not live* (`:369`) and the worktree counts as an orphan. That breaks the ticket's *"a read that fails means keep"*.
2. **A failed read of a run stream becomes "no RunStarted".** In `findOrphanLogsEffect` the error is caught as `[]` (`:416`), so the log is reported as a run with no `RunStarted`. That item would be kept anyway, but under the wrong reason. The ticket wants it listed as *could not be checked*.
3. **No age check, no status check, and unknown runs are never removed.** `findOrphansEffect` has no age or `git status` guard because, under the lock, *"no run is live then"* (`:741-742`, said of the Claude-dir sweep under the same premise). It also never removes a run with no `RunStarted`: *"deleting mysteries is how you stop being able to explain them"* (`:357-359`).

The header gives the reason a lockless process must not borrow the daemon's rule: doctor *"is a different process from the conductor and holds no lock, so it has no standing to call anyone else's claim dead"* (`:62-64`). `clean` keeps that rule. It never decides a claim is dead. A worktree whose ticket is `claimed` by its own run is kept even when the conductor that claimed it is gone. Returning that claim is still the restart's job (`releaseForeignClaimsEffect`, `:515`).

So `clean` gets its own classifier. It reuses the same reads, without the error-swallowing.

## Where the code goes

- **`apps/cli/src/clean.ts`** holds three things:
  - a **pure** `classify` that takes the facts gathered for one item and `now`, and returns `{ verdict: 'remove' | 'keep', reason }`;
  - an Effect that gathers those facts through an injected port;
  - an Effect that removes.

  Register it in `apps/cli/src/commands.ts` beside `doctor` (`:661`) with `effect: 'changes'`. Then run `pnpm docs:cli` (`scripts/cli-doc.ts`), which writes **both** `doc/cli.md` and `doc/cli.json`. `apps/cli/unit/cli-doc.test.ts` fails if the committed copies differ, so neither file is edited by hand.
- **Every filesystem and git call goes through a port.** That covers: list directories, read a directory's mtime, size, `git worktree list --porcelain`, `git status --porcelain`, `git worktree remove --force`, `rm`, `git worktree prune`, and removing a file. Shape it like `ClaudeDirFs` (`reconcile.ts:309-312`). This is not optional. Every Done-when item is a *unit* test, and under 0060 §1 *"A temporary directory is still the filesystem"* (CLAUDE.md), so a test with a real worktree is integration and belongs to the 803-second half nobody runs during a pass. The unit tests use a fake port and `createMemoryEventStore()`. The real port gets no test before the merge. The unit claims that stand in for it:
  - `classify`'s table;
  - with `--yes` off, the port's remove methods are never called.

  All IO is `Effect.gen` / `Effect.tryPromise`, with no `async` functions, so `effect-ratchet.baseline.json` does not move.

## What counts as running

The ticket says to use the board's fold. That fold is `taskStateOf` (`packages/projector/src/task-view.ts:302`), which is *"The only place a `TicketLifecycle` becomes a `TaskState`"*. The board puts `running` and `approved` in its Running column (`apps/board/src/lib/board.ts:680-687`).

`clean` reads that fold from the **stream**, not from `task_view`:

- the run's own stream gives the `ticketId`, as `reconcile.ts:345-351` reads it, with a sub-run's id cut at the first `:`;
- then `readThroughSnapshot(store, ticketReducer, ticketId, 'all', …)` is called with **no `writer`**, because the CLI is not one of a snapshot's two writers (0124).

The projection only moves while a conductor runs, so reading the stream keeps a stuck projector from making a live worktree look abandoned.

A worktree is **running** when `taskStateOf(lifecycle)` is `running` or `approved` **and** `lifecycle.runId` equals the worktree's pass id. `approved` has to count. An approved item is continued *"onto the same `runId`"* (`packages/domain/src/ticket.ts:222-229`), so its continuation is provisioned at the same `worktreePath(home, project, runId)` (`packages/repo/src/worktree.ts:97-99`).

A worktree whose run id is in **no** stream is not running. Unlike reconcile, `clean` does not keep it as a mystery: it is removable once it passes the age and status guards. The ticket's worktree rule has no *unknown* exception, while its run-log rule does. The reason line says `no run in the log names it`.

## The order of checks, per worktree

Each guard is checked in this order, and the first one that holds decides:

1. **Mirror listing fails.** If `git worktree list --porcelain` on `<home>/repos/<project>.git` fails, every entry under that project is *could not be checked*.
2. **Younger than an hour** (mtime of the directory itself): keep. The root directory's mtime barely changes while an agent edits files deeper down, so age is not a liveness test. The log is. Age only covers a worktree created before its attempt shows up in the log, which is what the ticket says it is for.
3. **Store read fails** (run stream or ticket fold): *could not be checked*, keep.
4. **Running**: keep.
5. **Registered with git and `git status --porcelain` fails**: *could not be checked*, keep. If the output is non-empty: *uncommitted changes*, keep, even with `--yes`. A killed agent's worktree usually ends up here. That is the cost of the ticket's rule, and the listing is how the operator finds out.
6. **Not registered with git**: step 5 still applies, since recovered edits may sit in a directory whose registration is missing; if status succeeds and is empty the entry is removed with `rm` (the ticket's own edge), and git removes a registered worktree's directory itself, so no second `rm` follows it. This also covers the PR sync's `base-<sha>-pr-<n>-*` worktrees once they are left behind. Those have no run stream, and `sweepPrWorktrees` already removes most of them (`packages/repo/src/pr-sync.ts:101-129`).

**Re-check just before removing.** With `--yes`, read the fold, the mtime and the status again immediately before each removal, and skip the item if the verdict changed. This shrinks the gap that a blocked→approved→claimed continuation on the same run id could otherwise fall through. With no lock it cannot close that gap completely. That is the trade the operator made on 2026-11-25.

**Removal** is `git worktree remove --force <path>` on the mirror. Use a single `--force`: a locked worktree is refused, and `clean` keeps it with reason `locked`, as `pr-sync.ts:124-126` does (*"Git refusing (a locked worktree) is the end of it"*). Then `rm` whatever is left of the directory, and run **one** `git worktree prune` per project at the end. Failures in that prune are ignored. `clean` is another process, so the in-process mirror permit does not cover it (`packages/repo/src/mirror-lock.ts:12-13`: *"Another process writing the same mirror is not covered"*). Git itself marks a worktree that is still being added as locked while it initialises, so prune skips the daemon's half-made `worktree add`. Nothing in this repo can check that git behaviour before the merge.

## Run logs

Only `runs/<project>/*.log` counts, filtered as `reconcile.ts:401-407` filters. `runs/` also holds `runs/<runId>/` directories, and those are out of scope.

A log is **stale** when its ticket's lifecycle is `landed`, `closed` or `satisfied`. `satisfied` is added here: it is terminal, and *"nothing was landed"* (`ticket.ts:214-215`), so no explanation is owed for it. The ticket's *closed* means the log's `closed` lifecycle, **not** GitHub's. An issue closed on GitHub that the log has not folded yet is kept until the daemon's converge catches up. That keeps `clean` from asking GitHub anything.

A log is kept as *unknown* when no stream names its id. That includes the chat logs `discuss.ts:403` writes under a `chatId`. A failed read is *could not be checked*.

## Smaller decisions

- **Size**: `du -sk` through the port. A failed size prints `?` and changes no verdict.
- **Exit code**: non-zero when any item could not be checked or a removal failed, so a script running `clean --yes` notices.
- **Projects**: with no argument, the directories under `worktrees/` and `runs/`. The mirror and `cache/` are never touched.

## ADR

0111 §11 says reconcile *"reports, never removes, a log with no `RunStarted` … and the same for a worktree"*, and doctor lists what is left *"until a person removes it"*. `clean` is that person's tool, so it contradicts nothing.

What it adds is a rule a person may apply that the conductor does not: closed and satisfied logs, and unknown worktrees. Under `doc/README.md`'s one-ADR-per-topic rule, that is a sentence added to 0111 §11. The prompt's superseding-file convention does not apply to 0100+ ADRs here.

## What the log would settle

The ticket does not say why the five worktrees outlived the daemon's restarts. Look at `Reconciled` on the control stream, at its `findings[].actual` / `action`:

- `worktree at …/pass-… for a run with no RunStarted` with `reported` would mean the runs' streams were gone, for example after a log reset or a store switch (0055 §3), and reconcile deliberately left them.
- No `Reconciled` naming them at all would mean no restart happened between the crash and the full disk.

Either way `clean` would have listed them. The finding belongs on the ticket, not in this change.
