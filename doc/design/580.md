## Where the change goes

There are two edits, both in `packages/conductor/src/conduct.ts`. Nothing changes in `packages/agent`, since `sessionIdFor` hashes whatever run id it is given (`claude-code.ts:91`).

1. **The `continuation` object carries the wait it resumes.** The value is already in scope inside that closure: `const { waitId: approvedWaitId, onSha: approvedOnSha } = folded.lifecycle` (`conduct.ts:968`). Today the returned object takes `onSha` from that line and drops `waitId` (`conduct.ts:997-1032`). Add `resumedWaitId: approvedWaitId` beside `onSha: approvedOnSha`.

2. **The judge's run id reads it from there** (`conduct.ts:2447`):
   `` runId: `${runId}:judge:${on.when}:${continuation?.resumedWaitId ?? 'start'}:${judgements}` ``.
   Update the comment above it and the `judgements` doc block (`conduct.ts:1388-1406`). That block says the count is "the thing that differs". That is true within one `conduct` call only, and the wait id is what differs across calls (#580).

## The decision that is not obvious: key on `continuation`, not on `options.continuing`

`options.continuing` is only a request. A stale one becomes an ordinary fresh claim with a fresh run id. The code says so at `conduct.ts:1037-1043`: *"A stale request — the item left `approved` before this pass reached it — is an ordinary fresh claim and must get an ordinary fresh id"*. In that case `continuation` is `null` (`conduct.ts:966-968`) and the run id is new. So `'start'` is correct there, and the wait id would be wrong there. Read the wait id only from the `continuation` value that `conduct.ts:1044` already uses to decide whether this is the same run.

Do not re-read `folded.lifecycle.waitId` at the judge site. `folded.lifecycle` holds that field whether or not the continuation was accepted, so reading it there would bring back the problem above.

## Effect on fresh passes

Every fresh pass's judge id gains a `:start` segment, so its session id changes. That is harmless: a fresh pass's run id is a new UUID (`conduct.ts:1046`), so no transcript is keyed on the old string. The existing tests that look at judge ids match with `includes(':judge:')` or `toContain(':judge:findings:')` (`conduct-a-whole-pass.test.ts:1621,1660`, `what-a-pass-writes-today.test.ts:372`), so they keep passing as written.

## The test

Use the two-continuation pattern from `conduct-continuation-remembers-every-waiver.test.ts:92,128`: conduct, resolve the wait, conduct with `continuing: { runId: first.runId }`, and repeat. Record `request.runId` for every request containing `:judge:`, the same way `conduct-a-whole-pass.test.ts:1621` does. Then assert:

- the first judgement of each continuation has a different run id;
- each id contains that continuation's own resumed `waitId`;
- one case is continued by `GrantFixRound` and one by `Approve`.

The `Approve` case needs a continuation whose path reaches a judge at `proposed`, for example a `findings` reached again after the approval. If no recipe in the existing fixtures gets there, say so in the commit. Do not drop the `Approve` case.

The within-one-call case (#195) stays covered by `conduct-a-whole-pass.test.ts:1657-1660`. Add an assertion there that the ids in `asked` are all distinct, if nothing already checks that.

All of this is unit-level, with nothing that needs `pnpm test:integration`.
