## Design note for #629: `doc/events.json`

### Where it goes

- **Script:** `packages/domain/scripts/events.ts`. Use this directory, not the root `scripts/`, for three reasons:
  - The root `fmt` and `fmt:check` globs cover only `packages/**` and `apps/**` (`package.json:16-17`).
  - The script needs the TypeScript compiler API, which `@lingtai/domain` already has as a devDependency (`packages/domain/package.json`).
  - `packages/event-store/scripts/` is the precedent for a `scripts/` directory beside `src/`.
- **tsconfig:** add `"scripts"` to `packages/domain/tsconfig.json`'s `include`. Today it reads `["src", "unit", "integration", "test"]`. Without it, `pnpm typecheck` checks the script only for as long as something imports it.
- **Imports:** the script imports `EVENTS`, `EVENT_AT`, `SCHEMA_VER` and `RETIRED` from `../src/index.ts`. `src/` stays import-free; the `typescript`, `node:fs` and `git` dependencies are the script's alone.
- **Shape of the script:** split it into a pure function and a thin CLI.
  - The pure function is `generate({ root, sha }) → EventsDoc`.
  - Only the CLI runs `git rev-parse HEAD`, writes the file and formats it.
  - The unit test calls `generate` with a placeholder sha, so it never spawns git. 0060 §1 puts "the `git` binary" and "any OS process" outside the unit half (`vitest.config.ts:9-11`).
- **Root script:** `"events:generate": "node packages/domain/scripts/events.ts && oxfmt doc/events.json"`.
- **Test:** `packages/domain/unit/events-json.test.ts`. Reading the repository's own source in a unit test has precedent: `packages/domain/unit/retired-names.test.ts:82,140` uses `ts.createSourceFile` on `src/`, and `packages/event-store/unit/on-postgres.test.ts` walks files from `repoRoot()`.

### Scanning

- **Files scanned:** `{apps,packages}/*/src/**/*.{ts,tsx}`, excluding `.d.ts`. Tests, fixtures and `test/` directories are not append sites.
- **How:** walk with `readdirSync` from `repoRoot()` (`packages/env/src/index.ts:1092`) and parse each file with `ts.createSourceFile`. Do not build a `Program`: there is no type information to use, and the rule is syntactic on purpose.

### The finder, exactly as the ticket states it

1. Find a `CallExpression` whose callee name is in `APPEND_CALLEES`:
   - an `Identifier` (`appendNow(...)`), or
   - the `name` of a `PropertyAccessExpression` (`store.append(...)`, `events.append(...)`).
2. Look at each argument, and at each element of an argument that is an `ArrayLiteralExpression`.
3. Take any `ObjectLiteralExpression` that has a `PropertyAssignment` named `type` whose initializer is a `StringLiteral`.
4. If that string is an `EventType`, it is a site. Any other string is ignored, not an error.

The anchor line is the line of the `type:` property, not the call. A `store.append(id, v, [` with three events in its array then gives three distinct links.

Do not unwrap `as const` or follow anything else. These are all `ELSEWHERE` by design:

- shorthand `{ type, actor, data }` (`packages/daemon/src/converge.ts:546`, `packages/conductor/src/tell.ts:349`)
- helpers that take the type as a string argument (`packages/agent/src/hook-socket.ts:230`, `packages/daemon/src/control.ts:159`)
- `appendAt(stream, events)` with a variable (`packages/conductor/src/conduct.ts:637`)

Expect the table to be long because of this. The ticket accepted that cost.

### Where `group` and `stream prefix` come from

Nothing in the code declares either one per event, so this is the decision the ticket leaves open.

- **`group` is read from the code.** `events.ts` is divided by banner comments such as `// ---- run ----` (`packages/domain/src/events.ts:176, 452, 836, 1113, 1181, 1209, 1242, 1616, 1753, 1903, 1941, 1997`). An event's group is the name in the nearest banner above its `export const`.
  - Take it from the source text you already parsed, not from a hand table.
  - `shared` (line 50) is never a group: no event is declared under it.
  - `prepare` (line 450) has nothing between it and `run` (line 452), so no event lands in it.
- **`stream` is a hand-kept table in the script, as an array per event.** Some events go to more than one kind of stream: `RunSpent` is appended to a pass stream (`conduct.ts:2582`) and to a chat stream (`discuss.ts:572`). Deriving it from the append call's first argument would mean following `ticketId`, `runId` and `stream`, which is exactly the variable-following the ticket rules out.
  - Type the table `satisfies { readonly [T in EventType]: readonly StreamPrefix[] }`, so that `tsc` refuses a missing event. `EVENT_AT` uses the same device (`events.ts:2183`): "*`satisfies` over `EventType` makes `tsc` refuse a type with no entry*".
  - `StreamPrefix` is the closed union `STREAM_ID_PATTERN` accepts: `ticket- | pass- | int- | prj- | ctl- | chat- | ext- | bkl-` (`packages/domain/src/envelope.ts:44-46`).
  - `RETIRED` types get `[]`.
  - **No unit test can check that the table is true**, only that it is total. What would settle it is the log: `events.stream_id` grouped by `type`. No agent can read the production log.
  - Fill the table in from the append sites the finder reports and from `ELSEWHERE`, and say in the commit body that it was filled in by hand.
  - Do not move it into `@lingtai/domain` beside `EVENT_AT`. That is a wider change than this ticket's, and it is a follow-up if the page needs the table to be enforced.

### Per-event record

Use these exact field names, which the page ticket will read:

```
{ name, group, stream: string[], schemaVersion, retired, at: string[],
  summary: string | null, definition: url, sites: url[], subscribers: "on: [Name]" }
```

- **`summary`:** the first non-blank line of the JSDoc on the `export const`, with `/**`, `*` and the surrounding whitespace removed. Use `ts.getJSDocCommentsAndTags`, or the leading comment ranges of the `VariableStatement`. It is `null` when there is no doc comment; never invent one.
- **`definition`:** points at the `export const Name =` line.
- **`sites`:** sorted by path and then line, so the output is deterministic.
- **Top level:** `{ sha, events: [...] }`, with events in `EVENTS` key order (`events.ts:2040`).

### `ELSEWHERE`

- **Shape:** `{ event, why, site: 'path.ts:line' }[]`, with one row per site. An event may have several rows.
- **The completeness test has three checks:**
  1. Every event that is not `RETIRED` has at least one finder site or `ELSEWHERE` row. The failure names each event that has neither.
  2. No `ELSEWHERE` row names an event the finder also finds.
  3. **Each row's `site` line contains the event's name as a quoted string.** This check is not in the ticket, and it is the cheap one that stops the table going stale: without it, the `line` in `site` drifts the first time somebody edits the file above it, and nothing goes red.

  Check 3 does not make the finder smarter; it checks only the table.

### Staleness test

- Regenerate with `sha: 'SHA'`, `JSON.parse` the committed `doc/events.json`, replace the 40-hex segment in every `/blob/<sha>/` URL (and the top-level `sha`) with `SHA`, and `toEqual` the two.
- **Compare parsed objects, never text.** That keeps the test independent of how oxfmt lays out arrays, which the generator cannot reproduce without spawning it.
- The failure message must say `run pnpm events:generate`. This test goes red on any edit that moves a line above an append site, which in `conduct.ts` is most edits, so the next agent needs the remedy in the message.

### Formatting

The ticket says *"`pnpm lint` and `fmt:check` cover the JSON"*. Today neither does:

- `fmt:check`'s globs are `.ts` and `.tsx` only (`package.json:17`).
- oxlint does not read JSON.

To make the format claim true, add `'doc/events.json'` to both the `fmt` and `fmt:check` globs. `events:generate` runs `oxfmt` on the file after writing it, so its output already passes. Run `pnpm fmt:check` once to confirm that this oxfmt version (0.71.0) accepts a `.json` path. If it refuses one, drop the glob and say so in the commit body rather than adding an ignore. `lint` gains nothing here; say that rather than claim it.

### The sha, and committing

A permalink can only name a commit that already exists. That makes the order matter:

1. Make the code change and commit it.
2. With that commit as `HEAD`, run `pnpm events:generate`.
3. Commit `doc/events.json` **on its own**.

Because the JSON commit's parent is the commit its links name, and the JSON commit touches no source file, every `#L<n>` is correct at that sha. If the JSON is generated before the code commit, the links name a parent where the new lines do not exist.

The merge lane is `git merge --no-edit` and a push (`packages/actions/src/merge-action.ts:47`, as cited in CLAUDE.md), so both commits keep their shas on `main`.

### Checks

`pnpm typecheck`, `HOME=/nonexistent pnpm test`, `pnpm lint` and `pnpm fmt:check` reach everything here. No part of this needs the integration half.
