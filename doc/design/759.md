# Design note: #759, the landing question becomes a two-way choice

## Where the change goes

All of it is in `askLanding` (`apps/cli/src/landing.ts:139-183`). Leave `question()`, `liveAsk` and `landingChanges` alone. `question()` already draws a select when it is handed `choices` (`question.ts:141` passes `choices: q.choices ?? q.offer`; `prompt.ts:79-80` draws `select(...)` when `shape.choices !== undefined`). `landingChanges` already does both writes (`answers.ts:64-93`).

## Two `question()` calls, chosen by whether the flag spoke

**The flag path (`land !== null`): keep today's call exactly as it is.** That is `given: land`, `flag: '--land <branch>|hold'`, the same `validate` and no `choices`. Today's flag behaviour, including its refusals, then stays word for word, and existing tests pin it:
- `landing.test.ts:163`: *a bare --land with no value is refused*. This holds because `validate` refuses `''` (`landing.ts:166`).
- `landing.test.ts:209`: *--land hold never calls defaultBranch*.

The answer then goes to `landingChanges` as it does now (`landing.ts:173-177`). Do not merge this into the choice call. `accept` runs `choices` before `validate` (`question.ts:95-98`), so `--land main` would be refused as "not one of …". That is the ticket's Watch out.

**The terminal path (`land === null`): a second call with `given: null`.**
- Use the two phrases themselves as `choices`: `['wait for me to approve', 'land it without asking']`. Every other choice in the CLI is a plain value with no label map: `first-project.ts:317`, `recipe-flow.ts:250`, `github-auth.ts:164`. Matching that means scripted tests answer with the words the Done-when checks for, and `offerLabels` is not needed.
- The prompt is `'when a pass is ready'`.
- `current` is `currentlyHolds ? 'wait for me to approve' : 'land it without asking'`. It is never null, so `detected` and `fallback` are never reached.
- Keep `kept: deps.kept`.
- Set `flag` so that the no-terminal refusal (`question.ts:148-149`, `` `${q.name} needs an answer: pass ${q.flag}.` ``) names both escapes, for example `'--land hold (wait for me to approve) or --land <branch> (land on that branch)'`. `landing.test.ts:308` only asserts that the refusal contains `--land`.

## The default branch is read after the answer, and only when *land* needs it

Delete the `detected` line at `landing.ts:154`. The choice always has a `current`, so asking GitHub up front would be wasted. `add-github.ts:328` notes that this round trip is memoized and shared, so paying it less often costs nothing.

When the answer is *land* and `file.base === ''`, call `deps.defaultBranch()` (typed `() => Promise<string | null>`, `landing.ts:48`). If it returns null, return `{ refused: 'no base branch to land on — pass --land <branch>' }` before any `readRecipeKey` or `setRecipe` call, so nothing is written.

## *Land* on a base the file already resolves writes only the hold removal

This is the decision the ticket does not make. The ticket says *land* goes to `landingChanges({ land: file.base })`, on the grounds that writing the same base back leaves the file unchanged. That holds only when the base is literally in the file.

`file.base` is `baseOf(resolved.recipe)` (`landing.ts:105`). That is the value after the preset has been applied, read from `steps.admit`'s `worktree.base` when one exists (`answers.ts:57-62`). Where the base comes from a preset, `landingChanges` writes `repo.base` (or rewrites `steps.admit`) into a file that never said it. That pins the base, and `setRecipe`'s no-op check (`write.ts:199`, `text === existing`) does not catch it. It breaks the Done-when line *leaves `repo.base` unchanged*.

So, on the terminal path:
- **Wait:** `landingChanges({ land: 'hold' }, …)`, as today.
- **Land with a non-blank `file.base`:** call `landingChanges({ land: file.base }, …)` and keep only the change whose path is `['steps', 'proposed']`. That is, remove the hold and write nothing else. If there was no hold, the change set is empty and `setRecipe` reports `written: false`.
- **Land with a blank base:** use the full `landingChanges({ land: <defaultBranch> }, …)`. Here the base really is being decided, and it goes where `baseWrittenAt` reads it, as today.

The flag path keeps the full `landingChanges` result. `--land feature-x` is meant to move the base (Done-when 3).

The `steps:`-pinning note at `landing.ts:179-185` keys off `changes.some(c => c.path[0] === 'steps')`. Compute it from the filtered list.

## Tests that move

- `first-project.test.ts:491` finds the question by `'land this on which branch'`. It should find `'when a pass is ready'`.
- Search `apps/cli/unit/{recipe-flow,add-github,source,first-project}.test.ts` for scripted answers that type a branch at the landing prompt. Each one becomes one of the two phrases, or moves to `--land <branch>` where the test is really about the branch.
- `RECIPE_FLOW_DEFAULTS` (`first-project.test.ts:179`) answers `''` at every prompt, so it needs no change. On a new recipe with no hold, Enter means *land it without asking*.
- New unit cases in `landing.test.ts`, covering the Done-when lines:
  - the two choices and both defaults;
  - *wait* writes one `human:`;
  - *land* removes it with no `repo.base` in the diff;
  - *land* on a preset-inherited base leaves the file byte for byte (`written: false`);
  - a blank base with `defaultBranch → null` is refused and `replace` is never called.

## Docs

Changing only the prompt words does not touch `doc/cli.md`. If `--land`'s help text in `apps/cli/src/commands.ts` is reworded, run `pnpm docs:cli`, or `cli-doc.test.ts` fails. Update the JSDoc above `askLanding` (`landing.ts:118-138`): it describes the typed branch question. Nothing here contradicts an ADR.

All of the above can be checked in the unit half: `pnpm typecheck` and `HOME=/nonexistent pnpm test`.
