# Design: #463: `runPass` returns `PassEnd`, and the claim runs before it

## What stays where

**The ending's appends stay in `conduct.ts`.** The words "its terminal is already on the log when it returns" cover what the pass writes itself: the step events through `emit` (`conduct.ts:2870`) and the lane's integration rows. They do not cover `WorkItemLanded`, `WorkItemBlocked`, `PassRestarted` or the release. 0120's *Consequences* says so: "`pass.ts` and `conduct.ts` keep the loop and the effects". There are also two mechanical reasons:
- The landing and the block must be one append with `endPlan` (`conduct.ts:3800-3812`, and the `WorkItemBlocked` append near `:4025`).
- Those endings read facts only the closure holds: `published`, `wip`, `armPublished`, `ceilingHit`, `declined`, `folded`.

So do not move those ~400 lines. Make them branch on `PassEnd` instead of on `outcomeOf`/`rested`.

## The return type

```ts
export type PassEnd = Extract<PassNext, { _tag: 'Requeued' | 'WaitOnPerson' | 'Landed' }>
export interface PassOver {
  readonly end: PassEnd
  readonly stopped: { readonly step: Step; readonly ending: StepReport } | null
  readonly unanswered: boolean
  readonly steps: readonly StepReached[]   // admit … end, no claim
  readonly routes: readonly RouteTaken[]
}
```

`PassResult`, `stoppedAt`, `rested`, `waitOn` and `pass.ts`'s `outcomeOf` (`pass.ts:1028`) are deleted. **Keep `adapters.ts`'s `outcomeOf`.** `pass.ts:118` imports it as `stepOutcomeOf`; it is about one step's actions, not this one.

**Why `stopped` survives.** "Events are unchanged" outranks a literal reading of "stoppedAt gone". `stopped` is the evidence the ending's events are worded from, and it no longer decides anything:
- `ApprovalRequested.step` and `.action` come from `stopped?.step ?? 'proposed'` and `whatRefused(stopped)` (`conduct.ts:3992-4000`).
- `judged` and `held` are read from it (`conduct.ts:3921`, `:3971`).
- The stand-down's step, `at` and detail come from it (`conduct.ts:4054-4085`).
- The release reason is built from it (`conduct.ts:4086-4089`).

Which ending branch runs is decided by `end._tag` alone. **`steps` and `routes` stay** because `conduct.ts` still appends `PassRouted` after the walk (`conduct.ts:~3505`) and reads `headReached(pass.steps)`.

Put the end→outcome mapping in `pass.ts` as a three-case switch on `PassEnd`: `Landed`→`landed`, `Requeued`→`failed`, `WaitOnPerson`→`blocked`. `end`'s `Reaching.outcome` and `conduct.ts`'s `endedAs` (`:3542`) both use it.

`pass.ts:1200-1310`. Keep a `landed: string | null` from `next._tag === 'Landed'` (its `integrated`).

**The `AgentCrashed` row needs a schema change.** The shell can stop at `admit`, `prepared` or `build` (an `actionsAt` that throws, or `nextOf` throwing). For those to type-check, widen `AgentCrashed.step` at `domain/src/wait.ts:150` to every step except `claim` and `end`. This is safe for three reasons:
- No event schema carries `WaitReason`; `events.ts` has no reference to it.
- 0120 §4's table already gives `Interrupted` at "any" step → `AgentCrashed`.
- Leave `nextOf`'s own guard at `pass-next.ts:309` alone. It limits what an *agent's* outcome may claim, and the shell's stop is not one.

**`unanswered` is what keeps `holdFor` byte-identical.** It is true exactly where `waitOn === null` today. So `holdFor`'s split (`conduct.ts:3635`) becomes:

```ts
over.unanswered ? holdOfPass(…) : holdOf(over.end.reason, …)
```

Everything after that is unchanged. `holdOfPass` keeps its ceiling-then-declined-then-`DidNotFinish` order (`hold-of.ts:153-236`), and this change does not alter it. Drop its `rested` input: `rested` was only ever non-null on router rests, which are never `unanswered`. `hold-of.ts:50`'s `StoppedAt` becomes `PassOver['stopped']`.

**The last row of the table changes behaviour for one kind of recipe.** It is reachable only by a recipe whose `merge:` declares no lane (`conduct.ts:2778-2784`: "a recipe that declares something *else* at `merge` no longer lands"). Today `end` resolves `landed` and the release then appends nothing. Now `end` resolves `failed`, and `release` appends `endPlan` (`conduct.ts:1113`). That is a change only if the recipe also declares a `when: failed` action at `end`. It is the derived outcome the ticket asks for, and `end-step.ts`'s own meaning of `failed` ("put the item back in the queue") is what that ending does. Pin it with a unit test and name it in the commit body. Every other row derives the same `TerminalOutcome` that `outcomeOf` gives today.

On the restart ending, keep `restart = folded.restarts.length + 1` (`conduct.ts:~3890`) as the number written to `PassRestarted`. Do not read it from `end.cause.restart` in this ticket.

## The claim

**The claim leaves the walk.** It starts at `admit`, and the router's `claim` *destination* (the requeue) is unchanged. Export a `claimStep(options): Promise<StepReached>` from `pass.ts` that is `runStep(SPEC.claim, options, bodies, [], { context: options.context, outcome: null })`. It runs the same `runActionPipeline`, `emit`, `endingOf` and `stepOutcomeOf`, which is how passed-over still writes `StepRequested, StepStarted, StepFailed` (`what-a-pass-writes-today.test.ts:1384`).

In `conduct.ts`:
1. Build the pass options once, and call `claimStep` **at the exact spot `runPass` is called now** (`:3431`). That way the claim's events land in the same order relative to everything above "the pass".
2. **Then run the `unappended` check (`:3478`).** A store that refuses the claim's own `emit` is an `Effect.die` today, because that check runs before the claim branch.
3. On `ending !== 'passed'`, run the existing early return (`:3780-3793`), with `stopped = { step: 'claim', ending }`.
4. Only on `passed`, call `runPass`.

`end` no longer runs on a decline, and nothing written changes because of it:
- On `passed-over` and `not-claimed`, `onStream` is null, so `end` returns at `pass-steps.ts:915`. `end` is not a pipeline step, so it emits nothing.
- On `claim-unconfirmed`, `recordEnd` only stashed the plan (`conduct.ts:2345`), and `release` appended it only when `endedAs === 'failed'` (`:1113`). Today it is `blocked`; after this change it is `null`. Either way nothing is appended.

`onPass` gets the `PassOver` with the claim's visit put back at the front, `{ ...over, steps: [claimed, ...over.steps] }`. That keeps `test/one-pass.ts:126`'s `eventOf` check whole. It is not called on a decline, because there is no `PassEnd` to hand it. `conduct.ts`'s `pass: …` log line prints the claim visit first, as it does now.
