## Design note for #1000: what stops new work

**Every blocker has landed.** All 22 issues GitHub lists as blocking #1000 are closed (#991–#999, #1001–#1013). So no part of this ticket uses the *"a #675 ticket is still open"* line. Write the locks as built and name no open ticket. The one part not built is #676, and the ticket already says how to treat it.

### Use the real command names, from the generated `doc/cli.md`

The ticket's prose paraphrases some of these. The prose documents must use the names that shipped:

- **A project's pause:** `lingtai pause [project]` and `lingtai resume [project]`. With no project, each covers every registered project. The pause takes no reason: `controlCommand` passes only `project` and `by` (`apps/cli/src/daemon.ts:786-790`).
- **The day's ceiling:** in the CLI it is `lingtai ceiling raise <usd>` (`doc/cli.md:576-592`), not "continue today".
  - *continue today to $x* is the banner's wording only.
  - The raise is refused until the ceiling has been reached, and refused while today's spend cannot be read.
  - It lasts until midnight and leaves `limits.day_usd` unchanged.
- **A runtime's usage limit:** `lingtai account lift <runtime>`, where the runtime is `claude-code` or `codex` (`doc/cli.md:594-610`).
  - It appends nothing when no limit stands.
  - Its projects take work again "at the next look".
- **Where a project's pause shows in `lingtai doctor`:** a row named `daemon: paused projects`, at level `info` (`apps/cli/src/doctor.ts:1316-1331`).
- **Where the setup's pause shows:** inside the `daemon: liveness` row, as `paused by <by> (<reason>)` (`doctor.ts:1252`).

### Bare `lingtai resume` and the chip's Resume are not the same thing

This is the decision the ticket leaves implicit.

- **Bare `lingtai resume` does two things** (`apps/cli/src/project-pause.ts:90-145`):
  - it unlocks every paused registered project (`:100-110`);
  - it then lifts the conductor-wide pause if one stands, and prints `lifted the setup's pause — <reason>` (`:112-142`).
- **The `paused` chip's Resume does one thing.** It calls `resumeWork`, which calls only `resumeConductor(by)` (`apps/board/src/app/actions.ts:523-531`), so it unlocks no project.
- **`lingtai resume <project>` never lifts the setup's pause.** The lift sits inside `if (name === undefined)` (`project-pause.ts:112`).

This shapes two passages:

1. **The setup's pause paragraph.**
   - Its remedy is: fix the recipe, then use **the chip's Resume**, or bare `lingtai resume`.
   - Say in one clause that bare `lingtai resume` also unlocks every project a person paused.
   - The conductor's own sentence says only *"run `lingtai resume` once it is"* (`packages/conductor/src/conduct.ts:1101`).
   - The line numbers have moved since the ticket was written: the setup pause is appended at `:990-1031` and the sentence is at `:1092-1104`, not `:1049-1123`. Cite the current lines.
2. **The *Upgrading* note.**
   - `lingtai doctor` reads the control stream with the checkout's own code, so it sees a legacy pause only before the checkout contains #1013. Write the steps in this order:
     1. Run `lingtai doctor` before updating the checkout. If it was already updated, do not trust a doctor with no pause; re-pause every project that should stay stopped.
     2. Note any `daemon: liveness` row that says `paused by …` for a pause that is not the setup's. Bare `lingtai resume` appends nothing for such a pause once the checkout has #1013, so it is not the remedy.
     3. With the old daemon drained and no new one started yet, run `lingtai pause <project>` for each stop that is still wanted, then start the daemon (not `lingtai restart`, which starts one at once). A pause appended after the start does not stop an attempt already begun.
   - Re-pause after resuming, never the other way round: a bare resume run after the pause would unlock that project again.
   - Why it matters: after the restart, `isSetupPause` treats only `cause: 'setup'`, or a `holdsAcrossStarts: true` pause with no `cause`, as a pause (`packages/domain/src/control.ts:173-179`). Every other old `ConductorPaused` reduces to nothing. ADR 0126 *Upgrading* says this at `:220-222`.

### The drain

`ConductorStarted` clears `shutdown` (`packages/domain/src/control.ts:198-201`): *"A drain lasts from its request to the next start (0126): the start is the unlock."*

- `resumeProjects` never touches `shutdown`.
- `ConductorShutdownWithdrawn` is still read so that old logs reduce the same, but *"Nothing writes this any more"* (`:202-208`).
- Base the drain paragraph on those lines.
- The second-Ctrl+C sentence in CLAUDE.md `:334` stays true as written: *"the next `restart` by the same person picks that request up"*. #1001 kept that behaviour (`apps/cli/src/restart.ts:1079`). Change only the clause *"`lingtai resume` lifts a request nothing acted on"*, to say the drain ends at the next start.

### Code that still says the old thing, which this ticket does not edit

`apps/cli/src/commands.ts:455-456`, the help for `resume`, still says it *"also lifts a conductor-wide pause or a shutdown request that stands"*. That text flows into the generated `doc/cli.md:563-566`.

- The *Done when* checks only the documents the ticket lists, and `doc/cli.md` is not one of them, so this does not block the ticket.

### The guard paragraph

Quote 0126 §4 (`doc/decisions/0126-a-stop-is-a-lock-and-an-unlock.md:79-86`):

- A look happens at start, after every attempt, on a control event and on the five-minute sweep.
- So a passed midnight, a passed `until` or an edited configuration is acted on at most five minutes late, whether or not the project has work: `conductProjects` calls `options.locked(name)` for every registered project (`apps/cli/src/conduct.ts:782-804`).
- A raise and a lift append at once.

Do not say the queue must have work: the sweep lifts an expired lock and clears the banner while the queue is idle.

### The glossary

- **ControlState** (`packages/domain/src/control.ts:70-75` and on) still has `paused`, `by` and `reason`, plus `shutdown`.
- The entry should say that `paused` is now only the setup's pause.
- Before you write "no `until`", read the rest of the interface. If an `until` field is still declared and always null, say *"always null"* rather than *"absent"*, so the entry stays true.
