## Design: #727, the writer's default with two runtimes signed in

The ticket's Fix is already the code shape. This note covers one decision the ticket leaves open, the rewritten #433 test, plus three details that are easy to get wrong.

### 1. The pick

Change `apps/cli/src/agents.ts:182` to:

    detected: RuntimeId.options.find((id) => signedInIds.includes(id)) ?? null,

- `RuntimeId` is already imported there (`agents.ts:25`, `import { RuntimeId } from '@lingtai/domain'`). No new dependency is needed.
- `signedInIds` is typed `string[]` (`agents.ts:146`), so `.includes(id)` type-checks without a cast.
- Don't add a comment explaining the order. `propose.ts:321-326` already makes the #313 argument ("The enum's own order, not a ternary"). One line citing #313 and `doc/design/398.md:43` is enough.
- Leave `defaultReviewer` (`agents.ts:212-213`) alone. It uses `signedInIds`' order, so with `runtimes` passed as `[codex, claude-code]` the reviewer is the first signed-in runtime other than the writer, which is still `codex`. The Done-when test for the reversed order should check both writer and reviewer. With only two runtimes there is just one other runtime, so the reviewer's order can't be wrong. Making the reviewer follow the enum is not this ticket's job.

### 2. The empty-answer sentence

In `refuseUnlessOffered` (`agents.ts:155-162`), check for `answer === ''` before the `found` lookup, and return a sentence that does not start with `${why} — sign in to it`. Signing in to nothing makes no sense. The ticket's wording is "no agent is chosen yet — choose one of ${choiceList}${extra}". Keep `${extra}` so the reviewer's version still ends with ", or none" (`agents.ts:236`).

#735 builds on this sentence. Keep the change to one branch and don't reword the other two (`whyMissing(found)`, and `is not a runtime` for a non-empty typed name); those are listed under Out of scope.

`refuseUnlessOffered` is a closure inside `askAgents`, not an export. To test it, call `askAgents` with `flags.agent: ''`. `question()` validates a flag once and returns the refusal unchanged (`question.ts:106-109`), so that one call reaches the function and nothing else. Assert that the refusal names no runtime as the chosen one, does not start with a space, and contains `claude-code, codex`. Do not export the closure for the test.

### 3. Where the #433 guard's test goes

This is the open decision. After this change, no agent question in `askRecipe` can have a default that fails `validate`:

- `currentAgent` and `currentReviewer` are filtered to signed-in ids (`agents.ts:174`, `agents.ts:222-228`).
- `detected` and `defaultReviewer` come from `signedInIds`.

So the rewritten test needs a different question. Use **`the kinds`** (`apps/cli/src/source.ts:202-214`):

- Its `current` comes from the recipe's own `source.kinds` (`source.ts:196-200`).
- Its `validate` refuses whatever `parseKinds` returns as a string (`source.ts:210-213`).

Seed a recipe whose `source.kinds` is a list `parseKinds` refuses. Then run `--defaults` with no `--kinds` and a world whose `ask` throws (the same harness as `recipe-flow.test.ts:256-286`). Assert `{ refused: 'the kinds needs an answer: pass --kinds <a,b,c>. Nothing was written' }` and `files.replaced` length 0.

Before relying on this, read `parseKinds` and find a value it really refuses. If a seeded raw value can't reach the `rawKinds` branch (`source.ts:197` reads it only when `resolved === null`), or every seedable value parses, put the guard in `apps/cli/unit/question.test.ts` instead:

- Call `question(acceptingDefaults(world), { detected: 'bad', validate: async (a) => (a === 'bad' ? 'no' : null), … })`.
- Assert the by-name refusal and that the inner world's `ask` was never called.

That file has no `acceptingDefaults` test today; its `it(` list runs from `question.test.ts:42` to `:166`. Either location is acceptable. Deleting the test is not.

Rename the test so the name says which default fails. The old name was attached to the two-runtime writer, and that is what hid this bug (see the ticket's *Why it stayed hidden*).

### 4. The two-runtime success tests

Put them in `recipe-flow.test.ts`, next to the old one, and reuse `TWO_RUNTIMES` (`recipe-flow.test.ts:214`).

For the typed `yes` case, model the world on the test that asserts `asked` equals `['use every default? [yes]: ']` (`recipe-flow.test.ts:344`). The test passes if `asked` contains nothing after that first prompt.

For the re-run test, a recipe seeded with writer `codex` must keep `codex`. This checks `current` ahead of `detected` (`question.ts:112`). Seed `runtime.agent` or the `implement` action's `agent`, whichever the existing re-run tests in `agents.test.ts` already use.

### 5. The `auth.ts` comment

`packages/agent/src/auth.ts:87-90` currently says a machine signed in to both "must be asked rather than handed the one that happened to have a probe". Rewrite it to say:

- Which runtimes are signed in decides what setup can offer as the default.
- With several signed in, the default is the first in `RuntimeId`'s order, not whichever probe finished first.

Keep the second half of the comment (the exit-code contract) as it is. Do not cite 0046 §3 as the governing rule; it is archived, and the ticket's Evidence explains why 0106 §7 is about the pass, not setup. This is a comment edit, not a decision change, so no ADR file is needed.
