# Design note: #1041, action ports and the pipeline as Effects

The ticket gives the shape and these notes don't repeat it. They cover three things it leaves conditional or unstated, all at the point where the pipeline meets OpenTelemetry and the Effect runtime.

## 1. The action span gets its parent from a captured context, never from `context.active()` inside the fiber

Making this conditional is the trap: *"If the context is not the step's by the time the first action starts…"*. Treat it as a rule instead. `runActionPipelineEffect(options)` reads `context.active()` once, synchronously, when it is called. In the face that is before `Effect.runPromise` hands anything to the scheduler. It closes over that value, and `inSpanEffect` receives it as an argument.

Why it can't be trusted in the fiber: Effect 4's scheduler flushes its queued tasks from one `setImmediate` (`effect/src/Scheduler.ts:97-117`). Each flush therefore runs in the AsyncLocalStorage context of whatever scheduled it, which is not necessarily the fiber that is resuming. Two passes at once (0122) share that scheduler. Today the parent of the action span and the sink both come from the active context:

- `startSpan(name, { attributes })` takes its parent from the active context, by default.
- `sinkOf()` reads `context.active().getValue(SINK)` (`spans.ts:37`).

The sink is the one thing that keeps two passes apart: *"The sink rides the OpenTelemetry context, which is per async chain, so two passes at once never share one (0122)"* (`spans.ts:24-26`). If it is read from whatever context happens to be active in the fiber, one pass's failed action could mark the other pass's step `ERROR`.

So `inSpanEffect(captured, name, attributes, body, failed)`:

- **Start the span from the captured context:** `trace.getTracer(SCOPE).startSpan(name, { attributes }, captured)`.
- **Find the parent sink there too:** `captured.getValue(SINK)`. It is not `sinkOf()`.
- **End the span in a finalizer.** Use `Effect.onExit`, or `acquireUseRelease` with the span as the resource. It is `ERROR` when the exit is a failure or interruption, or when `failed(value)` holds. When it is `ERROR`, set `parent.errored = true`.
- **Don't use `context.with` around the body.** Per the ticket, no dep reads the active span. `inSpan`'s `mine` sink only matters to a body that calls `markFailed()`, and none under an action does (the ticket's list of `markFailed` callers).

Export `SINK` from `spans.ts`, or add a `sinkIn(ctx)` reader beside `sinkOf`, rather than duplicating the key.

`trace-an-attempt.test.ts` tests one pass at a time, so it would stay green if this were wrong. Add a unit test for it:

- Run two `runActionPipeline` calls concurrently (`Promise.all`), each under its own `context.with(withSink(ctx, sinkN), …)`, with an in-memory span exporter like the one `trace-an-attempt.test.ts` uses.
- One pipeline has a failing action, the other only passing actions.
- Assert that only the failing pipeline's sink is `errored`.
- Assert that each `action <kind>` span's `parentSpanContext.spanId` is its own step span.

## 2. Order of the wrappers, which keeps both *Watch out* routes

Per action, from the inside out:

```
port.run(handed)                           // a dep's rejection is a Die (Effect.promise, internal/effect.ts:1139-1147)
  → inSpanEffect(captured, …)              // span ends ERROR on the Die, then the Die propagates
  → Effect.catchCause / exit-and-match     // a Die becomes `the ${action.name} action threw: ${(defect as Error).message}`
then, outside that:
  context.log?.note(...)                   // as action.ts:938
  emit(RunSpent) via Effect.promise        // a rejection here is a Die that nothing catches
```

This is today's nesting: the `catch` sits outside `inSpan` (`action.ts:907-937`), and the `emit` is after it (`:943-948`).

Match a cause that is a defect, and only that:

- **Interruption:** let it through, as the ticket's Edges say. Don't use a catch-all that would turn an interrupt into a verdict.
- **Typed failure:** impossible, since every port's error channel is `never`.

### The face must reject with the raw `Error`

`Effect.runPromise` on a `Die` rejects with what? Check it, don't assume. Whatever it is, the done-when test `rejects.toBe(theSameInstance)` decides. If `runPromise` wraps the defect, the face has to unwrap it:

- run `Effect.runPromiseExit`;
- on a failure, rethrow `Cause.squash(cause)`, or the single defect;
- keep the face one line by putting the unwrapping in a non-`async` helper.

`runPromiseExit` is an `Effect.run*` call too, so it is the face's one listed run, not a second one.

## 3. A hand-written `Action` whose `run` throws synchronously

`inSpan` turns a synchronous throw into a rejection (`spans.ts:73-77`). That is why a test fake with `run() { throw … }` gives a `failed` verdict today.

`fromPromiseAction` lifts with `Effect.promise(() => action.run(ctx))`. A synchronous throw in that thunk is raised from inside `register` (`internal/effect.ts:1142-1143`, called at `:1158`'s `callbackOptions`), not from the `.then` that dies.

Don't rely on the run loop to catch it. Write the lift as `Effect.promise(() => Promise.resolve().then(() => action.run(ctx)))`, or wrap it in `Effect.suspend`, and add a case for it to the unit test that covers the stamp:

- a hand-written action that throws synchronously gives `the <name> action threw: …`.

The same applies to every `<kind>PortDepsFrom` lift. A conductor dep such as `cut` can throw before its first `await`.

## Placement

- **`action.ts`:** `ActionPort`, `promiseAction`, `fromPromiseAction` and the `WeakMap`, `actionRunFace`, `runActionPipelineEffect`, and `runActionPipeline` as the face.
- **Each `<kind>-action.ts`:** its `<Kind>PortDeps`, `make<Kind>Action`, `<kind>PortDepsFrom`, and `create<Kind>Action` rewritten over them.
- **`spans.ts`:** `inSpanEffect`, beside `inSpan`. Rewrite the header (`:4-7`) to say that the action span is now started from an Effect body, and that `Effect.withSpan` waits for row 7's bridged tracer.

`index.ts` re-exports whatever the done-when list names. Check that `@lingtai/actions/action` is a subpath in `package.json`'s `exports` before relying on it.

### The ratchet

The two faces are named functions, and each contains the package's only `Effect.run*` calls:

- `actionRunFace`
- `runActionPipeline`

Nothing else in `packages/actions/src` may call `Effect.run*`. In particular, `promiseAction`'s `run` arrow calls `actionRunFace`; it must not inline `runPromise`, or the ratchet counts it against an anonymous function that isn't listed.

None of the new code is `async`. Build each kind's body with `Effect.gen` and keep the order of the old body.
