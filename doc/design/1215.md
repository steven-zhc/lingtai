# Design note: #1215 `whyNothingRuns`

## Where it goes

- `packages/conductor/src/why-nothing-runs.ts` holds the pure `whyNothingRuns(facts) → WhyNothingRuns | null`.
- `packages/conductor/src/blockers.ts` holds the blocker read, moved out of the board.
- Export both through a new `./why-nothing-runs` subpath in `packages/conductor/package.json`. The current subpaths are listed there, one per file.
- `apps/cli/src/status.ts` gathers the facts, calls the function and renders the result. `apps/board/src/lib/board.ts` only changes its imports.

## Decision 1: the beacon is a fact passed in, never read by conductor

`@lingtai/daemon` already depends on `@lingtai/conductor` (`packages/daemon/package.json:19`). So conductor cannot import `readStatusEffect` or `lastBeat` without a cycle.

Status does the read itself. It already imports from `@lingtai/daemon` (`status.ts:26`). It hands the function data:

```ts
type Beacon = { up: boolean; ageMs: number } | { never: true } | { unread: string }
```

- `readStatusEffect` returns `null` when *"no daemon has ever run"* (`packages/daemon/src/control.ts:701-702`). That is `{ never: true }`, and it reads as *not running*.
- `readStatusEffect`'s type has no error channel (`Effect<DaemonStatus | null>`, `:702`). A store that fails to open is therefore a defect, not a failure. Status must catch the cause (`Effect.exit` / `catchCause`) and turn it into `{ unread }`. Otherwise the gap 0122 rules out comes back: `health.ts:18` says *"A beacon that could not be read is an error, never an empty list."*
- `lastBeat(status, now)` (`packages/daemon/src/store.ts:258-261`) gives `up`. Use it unchanged.

**A `lingtai run` writes no beacon.** While it has a ticket, something is in flight, so the sentence does not show. Do not add a lock-holder read to cover it.

## Decision 2: the red base comes from the look status already makes

The ticket's table proposes reading the root from a release cause. Status already computes the same fact for this project: `lookAtBase(...)` gives `looked: BaseRedLook` (`status.ts:453-460`; type at `packages/conductor/src/base-red.ts:47-56`).

Pass `looked` in and read it as follows:

- **`held`**: the sentence uses `held.baseSha.slice(0,7)` and `held.command`. The ticket count is the skips whose reason is `base-red`. The wording should match `passOverBaseRed`'s own line (`base-red.ts:94-97`).
- **`unreadable`**: this is a root of its own. Say *the base could not be read — <reason>; N tickets wait for it*. `passOverBaseRed` skips them for this too (`base-red.ts:89-91`: *"a base that could not be read is not a green one"*), so it must not fall through to *no reason found*.
- **`clear` / `moved`**: not a root.

Do not read the integration stream a second time.

## Decision 3: status must keep the whole skip, not `{ref, reason}`

Status cuts the skips down to `{ ref, reason }` (`status.ts:461`). That drops `blockedBy`, which the blocker cache needs as part of its key (`board.ts:966`), and drops `title`. Keep the full `seen.skipped`, which is the same shape as `offered.skipped`, and narrow it only where the JSON is built.

## Decision 4: the blocker read moves as one Effect, and walking a chain makes no reads of its own

Move these into `blockers.ts`, with their comments:

- `BlockedSkip`, `BLOCKERS_READ_MOST`, `BLOCKERS_FRESH_MS`, the module-level `blockerCache` and `forgetBlockers` (`board.ts:906-939`).
- `readBlockers` (`board.ts:944-987`), as:

```ts
export const readBlockersEffect = (
  owner: { project: string; links: TicketLinks },
  skipped: Offered['skipped'],
  now: () => number,
): Effect.Effect<BlockedSkip[]>
```

The body is the existing one without its last line: return `Effect.all(reads, { concurrency: 'unbounded' }).pipe(Effect.as(out))` and drop the `await Effect.runPromise`.

After the move:

- `askProject` (`board.ts:1026`) calls `await Effect.runPromise(readBlockersEffect(filter, offered.skipped, options.now ?? Date.now))`. The board's ratchet row loses one `async` and keeps the same `Effect.run*` count. Conductor gains neither and stays at `"async": 0`.
- `board.ts` re-exports `BLOCKERS_READ_MOST`, `forgetBlockers` and `BlockedSkip` from conductor. That way `apps/board/unit/blocked-skips.test.ts:11` either keeps passing unchanged or changes only its import, as the ticket allows.
- `filter.links` is typed `TicketLinks` (`filter.ts:209`, `:214-217`), not `Pick<GitHubClient, …>`. Take that type.

**The chain is walked over what that one read returned. It never adds reads.**

- Each `blocked-by` skip in the look has already had its blockers read, up to 20 of them.
- Build a map from each `blocked-by` skip's ref to its open blockers, then walk from each skip. Keep only links with `state === 'open'` (`db-tickets.ts:129-134`).
- A blocker that is itself a `blocked-by` skip in the map is the next hop. The first open blocker that is not one is the **root**. Its state comes from the task rows status already holds:
  - a wait means *which waits on you*;
  - `queued` with `heldUntil` means *which retries at HH:MM*;
  - an `agent:hold` / excluded skip means *which is on hold*;
  - no row means *which is open and not queued here*.
- A blocker with `link.repository !== links.repository` is *a blocker that is not a ticket here*. Do not recurse into it.
- A hop that lands on a skip with `unread: true` (past the cap), or the 10-hop depth cap, ends in *a chain longer than this reads, through #a, #b, …*.
- A visited ref seen twice is a cycle, and the sentence names its tickets.

The result: at most 20 reads per project, the same budget the board already spends, and no walk can exceed it. It also reuses the board's 60-second cache, because status runs in its own process and gets a fresh cache each time, while the board shares one. The ticket's *every hop counts against the budget* holds by construction.

**Read blockers only when the sentence will show.** Status first decides everything it can from the facts it already has: nothing in flight, nothing `running` updated within the last five minutes, and unheld work queued. Only if those all hold, and no earlier root holds (daemon, drain, lock, red base), does it run `readBlockersEffect`. Read the beacon under the same guard. The function stays pure: status passes `blockers: BlockedSkip[] | null`, where `null` means not read because an earlier root answered.

To keep that ordering honest, split the function in two:

- `rootBeforeChains(facts)`, which needs no blockers;
- `whyNothingRuns(facts & { blockers })`.

Status calls the first, and only if it returns nothing does it read blockers and call the second. #1216 imports both. The stub-client test the ticket asks for is on the second step.

## Correction to the ticket's `db` edge

The ticket's *a `db` project's `links` is null* is out of date. `filter.ts:203-208` says: *"What reads a ticket's blockers (#954, #1226): the GitHub client when it is also `tickets`, or the `dbTickets` store for a `db` project … Null only for a source with no link verbs (tests' `memoryTickets`)."* `ticketLinksOf` (`filter.ts:222-228`) builds one for `db`.

So a `db` project's chains are followed like GitHub's. `links === null` with a `blocked-by` skip is a test-only case, and it still says *N tickets wait on blockers this project cannot list*. **Do not add `listBlockedBy` to `Tickets`.** That still holds: `TicketLinks` is the seam.

## Locks

Use the existing words, not new ones:

- An account lock uses `lockSentence(project, [lock], now)` from `@lingtai/domain` (`packages/domain/src/locks.ts`; the CLI uses it at `apps/cli/src/ceiling-words.ts:41`). This is #1214's sentence; append *— see above*.
- A pause uses `lockLine`'s `paused by … — lingtai resume <project>` (`ceiling-words.ts:37`). That function lives in the CLI, so the pure function returns the lock and status renders it. Have the result carry `{ root: 'lock', lock }`, so #1216 can render the same lock its own way.
- A ceiling only counts when it is today's: apply the filter `l.kind !== 'ceiling' || l.day === localDay(now)` (`status.ts:712`), or the sentence blames yesterday's ceiling.
- `{ unread }` locks (`status.ts:667`): the sentence says *what holds it could not be read* and stops. It does not drop to the next root.

## Output

- `WhyNothingRuns` is `{ roots: Root[] }`, ordered by how many tickets each root holds, most first. Each root carries `{ root, sentence, tickets }`.
- Text mode prints `roots[0].sentence`, plus *and N more for other reasons* when there is more than one root. `--all` prints every root, one line each.
- `--json` carries `whyNothingRuns: { root, sentence, tickets } | null` for the first root. Add `others: [...]` only under `--all`; do not invent a second field name for the default.
- The line goes first in the `queue` array, before `offerLine` (`status.ts:688-692`).
- It is suppressed when `offerError` is set or the recipe did not resolve, because the Queue section already says that (`status.ts:690`).

## What checks it

Every claim here is unit-level and needs no integration run:

- a fact-table test for `whyNothingRuns`;
- a stub-`TicketLinks` test for `readBlockersEffect`, covering the cap, a cache hit, and `ok: false`;
- the board's existing `blocked-skips.test.ts`, which proves the move kept behaviour;
- the ratchet test, which proves no `async` reached conductor.

`HOME=/nonexistent pnpm test` must stay green: the beacon read in status goes through `withDaemonStore` (`packages/daemon/src/choose.ts:76-83`), so a status unit test must inject the beacon fact rather than open a store.
