# #747: `lingtai run` continues approved passes before it takes the queue

## Where it goes

**One new module, `apps/cli/src/continuing.ts`, holds the only copy of the liveness rule.** It exports a check on one row, not a function that returns the list of live rows:

```ts
/** Whether this `control.continuing` row is still owed a continuation in `project`, read fresh. */
export async function stillOwed(store: EventStore, project: string, row: ControlState['continuing'][number]): Promise<boolean>
```

The body is what `conduct.ts` does today: the project test (`:381`), then the fresh read and the `lifecycle.status === 'approved' && lifecycle.runId === row.runId` test (`:388-389`). Add one guard in front of the read: return `false` when `row.runId === ''` or when `row.issue` is not a positive integer. The fold defaults both fields to `''` (`packages/domain/src/control.ts:206-209`). Without the guard, `Number('')` is `0`, so the code reads `ticketStream(name, 0)`. `ticketStream` only joins strings (`packages/domain/src/streams.ts:23-25`), so a junk row turns into a read of a stream nobody owns. The guard changes nothing for any row the daemon can match today.

**Why a per-row check and not a list.** The daemon applies its own tests before the read: `isFull()`, the slot already holding that issue, and the declined backoff (`conduct.ts:382-387`). It also stops after the first continuation that claims (`return 'looked'`, `:414`). If the shared code read every row's ticket up front, every daemon pass would read every stranded row's stream, including passes whose slots are full. Today's comment says that is exactly the cost it bounds: "Bounding it here costs one `runOnce` per pass per stranded row" (`:286-287`). With a per-row check, the daemon's loop keeps its order and its early exit. It changes only these two lines:

```ts
if (c.project !== name) continue                      // :381 — folded into stillOwed
...
const ticket = reduceTicket(...); if (...) continue    // :388-389 — becomes `if (!(await stillOwed(store, name, c))) continue`
```

Keep the `isFull`/backoff `continue`s ahead of the `stillOwed` call, as they are now, so a full look still reads nothing. `apps/cli/unit/conduct-continuing.test.ts` is the proof that this is a pure extraction. Its assertions must not change. Add a short unit test for `stillOwed` itself (an empty `runId`, a non-numeric `issue`, a `landed` ticket, a `wrong-run` ticket) beside it in `apps/cli/unit/`.

## `run()`'s side

All of it is in `apps/cli/src/run.ts`, after `common` is built (`:482-495`) and before the `if (options.issue === undefined)` branch (`:500`).

**The control read.** Use `readControl(options.store)` with no `since`, for the reason `heedThePause` gives: "This command's life starts now: scoped to its own start, it would see no pause ever" (`run.ts:137-142`). An approval made before this command started is exactly the row this ticket exists for. Wrap the read in `Effect.tryPromise` with a `refuse(...)`, as `loadProject` is wrapped at `:325-330`, so a failed read exits 1 through `Refused` (`:584-589`). A failed ticket read inside `stillOwed` is a refusal by the same route. It must never be treated as "not owed".

**The walk is a local helper, `continueApproved(limit)`.** It returns `{ ran: RunOnceResult[]; stopped: string | null }`. It goes through `control.continuing` in order. For each row:

1. Ask `stillPaused(options.store)()` (`run.ts:171-183`). If that returns a sentence, log it and return it as `stopped`.
2. Check `stillOwed`.
3. Log `continuing #n — asked for by <by>`.
4. Call `world.runOnce({ ...common, prompt, issue, continuing: { runId } })`.

A `stage: 'claim'` result is logged and is **not** added to `ran`, which matches `conduct.ts:406-409`. Every other result is added. The walk stops once `ran.length` reaches `limit`.

Order the check before the read, not after. `stillPaused` may append the ceiling's `ConductorPaused` (`packages/conductor/src/day-ceiling.ts:218-230`), and nothing should be read for a pass that will not run.

**The queue path:**

```
first  = continueApproved(max ?? ∞)
stop   = first.stopped
queue  = stop || (max !== undefined && first.ran.length >= max) ? skipped : world.runQueue({ ..., max: max - first.ran.length })
second = queue ran and stopped for neither 'max' nor 'paused' ? continueApproved(remaining) : none
tally  = world.tallyPass([...first.ran, ...queue.ran, ...second.ran])
```

- **Do not call `runQueue` with `max: 0`.** `runQueue` would return `finish('max')` (`packages/conductor/src/schedule.ts:188`), but only after its own `paused()` read and a `stopped: max — 0 run(s)` line (`:163`). The first Done-when test says it is "never called". So when the continuations used up `--max`, skip it.
- **One summary line**, as today (`run.ts:520-522`), counting every run. The text in parentheses is the queue's `StoppedBecause` when the queue ran. Otherwise it is `max` when the continuations reached the bound, or `paused` when the walk stopped on a sentence. Those are the same words `runQueue` would have used, so #766's rewording finds one vocabulary and not two.
- **`--max 0`** runs no continuation and no queue. That keeps `conductWork`'s rule that "`max: 0` means look and take nothing" (`conduct.ts:209-213`).
- **The second walk** is the Edges line "read once more after `runQueue` returns". Each walk reads `readControl` again. Do not reuse the first walk's `control`, or an approval made during the queue is missed, and catching that approval is the only reason for the second walk.

**The `--issue <n>` path.** The ceiling check stays where it is (`run.ts:531-537`). After it, read control the same way and take the first row with `row.issue === String(n)` for which `stillOwed` is true. Pass its `continuing: { runId }` to the existing `world.runOnce` call (`:537-543`). If there is no such row, the call is unchanged. The output after the call is unchanged too: the `--no-merge` line at `:555` is #766's.

## The ceiling test needs a seam, and the one the ticket implies does not exist

The third Done-when test asks for "a store whose day spend is over the ceiling". **The ceiling figure does not come from the store.** `dayCeilingStop` reads it from `(ports.ceiling ?? machineDayCeiling)()` and the spend from `ports.rows ?? readSpend` (`apps/cli/src/day-ceiling.ts:85-86`). `run()` calls it with no ports in all three places (`run.ts:151`, `:174`, `:533`). Under vitest no `config.yml` is read (CLAUDE.md: "A test reads no machine's `config.yml`"), so the ceiling is `undefined` and `dayCeilingPause` returns `null` before it reads any spend (`packages/conductor/src/day-ceiling.ts:204-207`).

**Decision:** add `dayCeiling?: DayCeilingPorts` to `RunOptions`, next to `store`, with the same comment ("The suite passes …; nothing else should set it", `run.ts:94-95`). Thread it through `heedThePause`, `stillPaused` and the nominated path's call as `dayCeilingStop(options.store, options.dayCeiling)`. Production passes nothing, so behaviour there is unchanged. `DayCeilingPorts` is already exported (`day-ceiling.ts:62`). In tests, give it `ceiling: () => 1`, `rows: async () => [...]` over 1, `lags: async () => []`, `rebuilding: () => null` and `rebuilds: () => 0`.

**A ceiling already reached at start does not test the new check.** `heedThePause` catches that case first (`run.ts:148-160`, before the lock), and the `Paused` branch prints the pause and exits 0 (`:573-579`). That test would pass with the new check deleted. So the ceiling test must be **two live rows, with a `rows` port that goes over the ceiling after the fake `runOnce`'s first call**. Assert:

- `runOnce` was called once;
- `runQueue` was never called;
- the log has the ceiling's sentence;
- `stillOwed` is still true for the second row after the run.

The start-of-run case can stay as a second assertion if you want it, but it is not the proof.

## Tests

Put them in a new `apps/cli/unit/run-continuing.test.ts`, built on the `RunWorld` fakes that `apps/cli/unit/run-ownerless.test.ts` already uses (`notReached`, `FAKE_LOCK`, `FAKE_PROJECTOR`, `FAKE_PORTS`, `:25-42`). Use an owner-less project so that no GitHub client is needed.

- Build the approved ticket and its row the way `conduct-continuing.test.ts:70-80` does: `aClaim`, `aWait`, `aResolution` with `Approve`. Then append a `ContinueRequested` to the control stream of the same memory store, passed as `options.store`.
- `world.runOnce` and `world.runQueue` are recording fakes. `world.tallyPass` returns a fixed tally.

This is unit by 0060 §1: a memory store and fakes, with no process and no filesystem. `pnpm test` covers it, so nothing in this change depends on `pnpm test:integration`.

## `--help`

Add one line under `--max` in `apps/cli/src/commands.ts:100-103`, for example `'  continues what you approved first, then takes the queue'`. If a test pins the usage block, update it in the same commit.

## Not an ADR change

This does not contradict 0120 §6 / #465 ("whoever holds the conductor lock continues the run"). It makes `run` do what that decision already allows. No ADR needs a superseding file.
