### 1. The ticket's line numbers point at an older file

`task-view.ts` is 1072 lines now. The run half is `task-view.ts:252-430`, not `:406-565`:

- `RunProducedDiff` `:273`
- `RunProposedCompletion` `:304`
- `RunFinished` `:327`
- the integration cases `:335-358`
- `cardFactOf`'s `Verdict`/`RoundOpened`/`RunEnded` `:366-427`

`linkRun` is at `:447`. The deletions the ticket lists are these:

### 2. There is no per-`apply` cache today, so this ticket builds it for both halves

The ticket says the cache holds "the ticket's (#834)" state, as if #834 left one behind. It did not. `applyTicketEvent` reads and writes SQL once per event (`task-view.ts:582-668`):

- a `select ticket` from `task_view`, then from `task_view_ticket`;
- an `update`/`insert … on conflict` whose `case when $flag` keeps the row's own `state`, `note`, `updated_at`, `run_id` and `awaiting_sha`;
- a `delete from task_view_ticket`.

All of that becomes reads and writes through the cache. Make it a small object built at the top of `apply` and flushed at its end, inside the same transaction (`projection.ts:153-165`):

```ts
interface TaskEntry {
  where: 'row' | 'staged' | 'none'   // task_view, task_view_ticket, or neither yet
  ticket: TicketState
  cols: RowColumns                    // derive(...) ∪ rowOf(...), as last computed
  note: string | null
  updatedAt: Date; updatedSeq: bigint
  dirty: boolean
}
interface RunEntry { taskId: string | null; run: RunState; dirty: boolean }
// tasks: Map<taskId, TaskEntry>, runs: Map<runId, RunEntry>; each loaded from SQL on first touch only.
```

**The per-event step.** It is the same for both halves:

1. Reduce the event into its own entry.
2. Get the ticket entry: for a run event, the one `runs.get(runId).taskId` names; for a ticket event, its own.
3. Get the run entry for `ticket.runs.at(-1)`.
4. Compute `cols = { ...derive(taskId, ticket), ...rowOf(ticket, run) }`.
5. Compare `cols` with `entry.cols`. If anything differs, set `updatedAt = event.at` and `updatedSeq = event.seq`.

`updated_at` has to be decided per event. Computing it once at the flush would stamp the batch's last `at` on every row, and the batch-of-1/3/all test would catch that.

**The flush.** Write each dirty entry once:

- `task_view`: one full-row upsert, no `case when` (every column is in memory).
- `task_view_ticket`: upsert for `staged`, delete for an entry that moved from `staged` to `row`.
- `task_view_run`: upsert `(run_id, task_id, run)`.

**Rules from #834 that survive.** Each is a property of the entry now, not a SQL flag. Keep them exactly:

- `MAKES_THE_ROW` decides whether a `staged`/`none` entry becomes a `row` (`:525-531`).
- The `releases` touch and the `DispatchRefused`-not-blocked touch (`:599-602`) move `updated_at` and write the note even when no derived column moved.
- `noteOf` (`:534-567`) is unchanged.

**`state` is now wholly derived.** The `moved` flag (`:606`) existed only to protect the `verifying` overlay from a prompt edit. Since `rowOf` computes `verifying` from the run's state, the flag goes.

**`run_id` takes the ticket's rule.** That is the `claims.findLast(…).ended?.kind === 'released'` rule from the ticket. It replaces `setsRun`/`clearsRun`. The pin's `run_id` rows staying put is the check that the two agree.

**The run-half `note` writes go through the cache too.** These are `RunAwaitingInput`, the signoff request's `question`, `RoundOpened`, `RunEnded`, and the two integration cases. They set `entry.note`. The ticket keeps `note` per-event and leaves it to #845, so these writes **keep today's timing**: a note write moves `updated_at`/`updated_seq`, as `set` does today (`:690`). A pass-stream event that writes no note moves them only when `cols` changed.

### 3. Ordering inside one event

**`TicketClaimed`/`TicketContinued`.**

1. Link first: `runs` entry created as `{ taskId, run: emptyRun }`, or `taskId` updated if the entry exists.
2. Then reduce the ticket.

That way `rowOf` already sees the new run as `runs.at(-1)` with `emptyRun`, and the card reads:

| Column | Value |
|---|---|
| `state` | `running` (`emptyRun.lifecycle` is `pending`, `run.ts:194`, so not `gating`) |
| `base_sha` | `null` |
| `head_sha` | `null` |
| `turns` | `null` |

`base_sha` is a fourth user-visible change: it is `null` from the claim until `RunStarted`, where today it keeps the previous run's base. It belongs in the pin comment's "a new run starts with no head" rule. Name it there.

**`RunStarted`.** Link from `d.ticketId` first (`on conflict` updates `task_id` and keeps `run`, as the ticket says), then `applyRun`.

**A run event with no `task_id`, or whose task is not a `row`.** Reduce and store the run, and write no task row.

**A run event for a run that is not `ticket.runs.at(-1)`.** A late event from an earlier attempt still reduces into its own run row. `rowOf` reads the latest run, so the card does not move. That is the design, not a bug.

### 4. The codec

Put it in `packages/domain/src/run-codec.ts`, beside `ticket-codec.ts`, exported where `encodeTicket` is.

**Signature.** Match `decodeTicket`'s three-argument form: `decodeRun(stored, projection, runId)`. Edges says the throw names the run, and the two-argument form in *The shape* cannot do that.

**Rules.** Same as #833's (`ticket-codec.ts:1-12`):

- `z.strictObject` everywhere;
- `Date` as ISO strings: `openedAt`, `agentStartedAt`, `askedAt`, `laneWaitedAt`, `step.since`;
- `lastSeq` as a digit string;
- absent and `null` stay apart.

**Payload copies.** For `produced`, `route`, `published` and `kept[]`, use the event schemas themselves (`RunProducedDiff`, `PassRouted`, `RunRefsPublished`, `RunKeptUncommitted` in `events.ts`). The same goes for `invocation` and `refusal.findings` (`run.ts:96-190`). A `PassRouted` payload that `parsePayload` accepts must round-trip strictly equal.

**Before writing a custom schema,** check whether the event schemas carry a zod `.transform` or default. A default would make the round trip unequal.

### 5. `verifying` holds through `RunFinished`

`applyRun` moves the lifecycle to `finished` on `RunFinished` (`run.ts:447-455`). That would break `gating ∧ roundsOpened.length === 0` if `RunFinished` came last. It doesn't: the first dispatch appends `RunFinished` (`conduct.ts:3796-3812`) and then `RunProposedCompletion` (`:3832-3838`), and the kept-run path appends no `RunFinished` (`:3149-3155`). Build `fixRoundAfterCompletion` in that order too: `RunFinished` before `RunProposedCompletion`.

### 6. `awaiting_sha`'s comparison

`run.askedAt` and `ticket.lastAttemptAt` are both `Date | null` (`run.ts:156`, `ticket.ts:288`). Compare with `getTime()`, and treat a `null` `askedAt` as "not asked".

For `staleSignoff`, `lastAttemptAt` is the continuation's `at`, set at `ticket.ts:499`/`:505`. That `at` is later than the first signoff's `askedAt`, so the final `MergeRefused` wait reads `null`. That is the rule working, not a coincidence of fixture clocks: `histories.ts` stamps `at` in evaluation order.

### 7. Where the table changes reach

- `task_id` drops `not null`, and `task_view_run` gains `run jsonb not null`. `reset` already drops the table (`task-view.ts:243-249`).
- Run `drift.test.ts` (`packages/projector/unit/`). `shape.ts` derives the expected columns from the `create` text after stripping comments (`shape.ts:65`), so a comment containing a comma in the new DDL is the trap it documents.
- `postgres.ts:88-94` and `sqlite.ts:268-274` read `verdicts` by the `${run_id}:` prefix and need no change.
