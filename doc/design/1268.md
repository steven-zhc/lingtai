# #1268 — the shape

## What "the count" is, and so which names change

`TicketState.restarts` is not a number. It is a list, `readonly RestartRecord[]` (`packages/domain/src/ticket.ts:337`), where `RestartRecord` is `{ after: string; restart: number }` (`ticket.ts:205-208`). The count is derived from it in two ways:

- **`.length`**, by the conductor: `conduct.ts:1775` (`newAttemptsSpent: reduced.restarts.length`) and `conduct.ts:6026` and `6063-6065`. Also `restart.ts:165` and `172`, and the board's `task.ts:942`.
- **The last record's ordinal**, by the projection: `task-view.ts:349` (`restarts: t.restarts.at(-1)?.restart ?? 0`).

Both readings stay as they are. The figure must not move (Out of scope).

**The rule:** an identifier changes if it holds this count, or the ceiling it is counted against. It does not change if it names the action. The domain already uses this pairing: `RoutingPolicy.newAttempts` is the bound (`packages/domain/src/routing.ts:39-40`), and the spent side is the one still waiting: *"spent as `Spent.restarts` until the log rename"*. So:

**What stays:**

- **Function and file names that are the action**: `decideRestart`, `restart.ts`, `armSuffix`, `afterArms`. The verbs are #1242's other tickets.
- **Every string a person reads**, even where it sits next to a renamed identifier. Examples: `progress.ts:525-528` (`restart left`, `no restarts left`), `describeArm`'s `restart ${n} of ${m}` (`task-view.ts:991-992`), and `fix.ts:1902` / `fix.ts:1924`. `fix.ts:1681` and `fix.ts:1755` (`restarts?: number`) are inputs to those sentences. Rename them to `newAttempts` (they are names), and leave the sentence text alone.
- **Comments that describe the behaviour**: leave them. Change a comment only where it quotes a renamed identifier in backticks, e.g. `fix.ts:1389`, `judge.ts:188-189`, `task.ts:583-594`, `board.ts:231-232`.
- **`upcast.ts:83` (`restarts: 'newAttempts'`)** stays. It is the upcaster's map *from* the retired name in old `ProposalRouted`/`PassRouted` payloads, and it has to name the old key. This is the one sanctioned exception to *Done when*'s grep. So is every hit in `apps/cli/src/service.ts`, `doctor.ts`, `rates.ts`, `subscribers.ts` and `restart.ts`: those are the daemon or a supervisor restarting, not this count.

## The reducer version, and the refusal

- Bump `ticketReducer.version` from 5 to 6 (`ticket-codec.ts:174`). Add a comment line above it in the house style, e.g. *"6: `restarts` is `newAttempts`, its records `{after, newAttempt}` (#1268); a version-5 snapshot holds the old key."* A snapshot is thrown away on a version mismatch, not decoded (0124; *"A snapshot is discarded, not rebuilt, so no remedy is named"*, `ticket-codec.ts:169`). So snapshots need nothing else.
- **No upcaster is needed.** No event carries this field. `Spent` is *"Reduced from events, never parsed"* (`attempt-next.ts:145-148`). The list is rebuilt from `TicketReleased`'s `cause.newAttempt`, which #1241 already renamed.
- **The refusal comes for free, and the test is what proves it.** `StoredTicket` is a `z.strictObject` (`ticket-codec.ts:67`). A stored row holding `restarts` and no `newAttempts` fails the parse, and `decodeTicket` throws a message naming `lingtai projection rebuild <projection>` (`ticket-codec.ts:159-166`).
- Put the test in `packages/domain/unit/ticket-codec.test.ts`:
  1. Take `encodeTicket(emptyTicket)`.
  2. Swap `newAttempts` back to `restarts: [{ after: 'r1', restart: 1 }]`.
  3. Assert that `decodeTicket(old, 'task_view')` throws `TicketCodecError` matching both `/newAttempts|restarts/` and `/lingtai projection rebuild task_view/`.

  Do not assert on zod's exact wording, which is a trap for a later zod bump.

## The task_view columns

**Decision: rename them.** The ticket's deploy already rebuilds `task_view`. The DDL comment says a table of another shape *"is refused by the shape check until rebuilt"* (`task-view.ts:216-218`). So an un-rebuilt table is refused by name and never read as zero, which is the ticket's *read that fails* edge.

Two other places pin the DDL and must follow:

- `packages/projector/unit/declared-shape.test.ts`'s `EXPECTED` list. Rename the two entries in place.
- `packages/projector/unit/__snapshots__/task-view-rebuild.test.ts.snap`. Regenerate it with `pnpm vitest run --project unit packages/projector/unit/task-view-rebuild.test.ts -u`, then **read the diff**: it should change `restarts`/`restartsOf` keys and nothing else. Any other line that moves is a behaviour change, and that is a finding.

The DDL's long comment (`task-view.ts:197-210`) mentions `TicketReleased{cause: Restart}`, which is stale since #1241. Fixing that one backticked tag to `NewAttempt` is in scope; the prose around it is not.

## Tests, and what checks it

About 60 unit files mention `restarts`. Most are fixtures building a `TicketState` (`restarts: []`) or a `TaskCard`. These follow mechanically, and `pnpm typecheck` finds every one that builds a typed object.

Fixtures written as untyped JSON or as `as` casts are only caught by `pnpm test`. In particular, check `what-an-attempt-writes-today.test.ts`, `what-an-attempt-shows-today.test.tsx`, `routing.test.ts` (39 hits, mostly `Spent`) and `rail.test.tsx`.

`apps/site/unit/*` hits are prose about the product; leave them unless they build a `TaskCard`.

Everything here can be checked at unit level: `pnpm typecheck`, `pnpm lint`, `pnpm fmt:check` and `HOME=/nonexistent pnpm test`. The SQL column rename on Postgres is exercised only by the integration half. The unit stand-ins are:

- `declared-shape.test.ts`, which reads the DDL;
- the `task-view-rebuild` snapshot, for the row the reducer writes;
- `sqlite.ts` / `postgres.ts` reading `row.new_attempts`, which is a one-line change in each, with no test inside the pass.

`effect-ratchet.baseline.json` must not change. This is a rename, and it adds no `async` and no `Effect.run*`.
