# Design note: #1108, triage attempt as an Effect

Line numbers below are this worktree's HEAD (`43c77d8a`, which already has CLI-17). The ticket's numbers are `8abc8613`, and in `triage.ts` they sit about 84 lines lower than here. Here: `gatherEvidence` is `:584`, `waitTriage` `:686`, `guard` `:723-745`, the `TriageStarted` loop `:811-854`, the checkout `:880-891`, `spend` `:927-973`, `runtimeVersionOf`/`runtimeRun` `:1029`/`:1035`, the checkout `finally` `:1149-1157`, the `WaitTriaged` loop `:1181-1213`, and `daemonTriagePorts.run` `:486-507`. In `discuss.ts`, `prepare` is `:124` and `answerDiscussion` lifts it at `:322`.

## 1. `guard` must disconnect the work, or the wall stops being a bound

`Effect.race` and its relatives wait for the losing fiber's interruption to finish. The ticket's shape is `Effect.acquireRelease(prepareCheckout(…), …)`, and an acquire is uninterruptible. A clone that hangs inside a guarded acquire therefore never stops the race, `guard` never returns, and the attempt holds the queue's one permit (CLI-17's semaphore). That is the failure the Watch out row names, by another route.

So `guard(eff)` is:

- `signal.aborted` → `Effect.fail(new WallReached())` at once (as `:724-727`).
- Otherwise, race `Effect.disconnect(eff)` against an `Effect.callback` that fails `WallReached` on `abort`. The callback removes its listener in its finalizer, as `:736-743` does by hand.

`disconnect` is what *a port that settled late is dropped* (`:721-722`) means in Effect. Every mirror read still passes `signal`, so the git child is killed as it is today (`mirror.ts:86-88`). The guard is the bound; the signal is a courtesy.

## 2. The checkout: who acquires, who releases, and when the scope closes

**No `Scope` on the port.** `TriagePorts.prepareCheckout` returns `Effect<Checkout, Error>`, where `Checkout.cleanup` is an `Effect<void, Error>`. The ticket's `Effect<Checkout, Error, Scope>` would let the port register its own finalizer, and that finalizer cannot know `toolsMayRemain` (`:895`, set at `:1061`). It would delete the directory under a live tool. The release belongs to `waitTriage`:

```
const checkout = yield* Effect.acquireRelease(
  guard(prepareCheckout(project, sha, signal).pipe(
    Effect.tap((c) => signal.aborted ? Effect.forkDaemon(c.cleanup.pipe(Effect.ignore)) : Effect.void))),
  (c) => toolsMayRemain ? log kept : c.cleanup.pipe(Effect.catch(e => log; final = cleanup failed)))
```

- **The `tap` stays on the work, inside the guard.** A checkout that lands after the wall has already lost the race, so no release was registered for it. Its own `tap` is the only thing that cleans it up (`:888`).
- **`Effect.scoped` covers the agent's part only, and closes before the `WaitTriaged` loop.** The release may overwrite `final` (`:1153-1156`). So `final` is a `let` outside the scoped block, and the append reads it after `Effect.scoped` returns. Do not scope the whole function: the checkout would then be deleted after the log says *triaged*, and a cleanup failure would never reach the result.
- `prepareTriageCheckout` becomes an `Effect.gen` over `gitEffect` (`git.ts:112`) and `Effect.tryPromise` around `mkdtemp`/`mkdir`/`writeFile`/`rm`. On failure it runs `cleanup`. If cleanup also fails it fails with the `AggregateError` (`triage-checkout.ts:63-71`); otherwise it fails with the original error. Use `Effect.onError` or `catch` + re-fail, not `ensuring`. A successful prepare must keep its directory.

## 3. The error channel is not `never`

`waitTriage` throws today when `WaitTriaged` will not land after five tries (`:1213`), and the comment at `:1181-1195` explains why that must stay a failure and not a returned result. The ticket's `Effect<{ attempt; result; started? }>` leaves out the error type. Make it `Effect<{…}, unknown>` and fail with the last error. CLI-17's port already accepts that: `run(request): Effect<{ started?: boolean } | void, unknown>` (`triage.ts:144`, `:156`). Do not `orDie` it, and do not catch it into a result.

## 4. Catching the agent's part

Today the `try` at `:863` turns *every* throw into `crashed: …`. That includes a `parsePayload` that throws synchronously inside what will become `Effect.gen`. In Effect that is a defect, not a failure. So the outer handler is `Effect.catchCause`:

- A cause that is only interruption is re-raised.
- `WallReached` becomes `abortedWhy()`.
- Anything else, failure or defect, becomes `crashed: <message>` (`:1158-1165`).

The `runtime.run` catch (`:1048-1059`) works the same way: `catchCause`, let interruption through, everything else is the `threw` outcome.

## 5. What stays a promise, and stays unguarded

`store` is lifted where it is read, not guarded. That covers `before` (`:751`), `readState` (`:620`), the start loop, `spend`, `recordPrompt` and the `WaitTriaged` loop. None of these is guarded today, and changing that changes which outcome a slow store produces. It is not this ticket. `runtime.run` is not guarded either: the wall reaches it as `request.signal`, which is what keeps `triage.test.ts:1142-1148` signal-driven (#1065).

## 7. The first Done-when test cannot pass as written

Build the two claims as two tests:

- **"A mirror read that never settles … and the fake checkout's `cleanup` ran once" is unreachable.** In `full` mode every mirror read happens in `gatherEvidence`, before the checkout (`:864` then `:880`). After the checkout nothing reads the mirror: `serve` runs only when `!full`, `:980`.
- **Test (a):** `listAt` returns `Effect.never` and the wall is 50 ms. The result is `TriageFailed('timeout')` and `prepareCheckout` was never called.
- **Test (b):** `tools: 'full'`, and `prepareCheckout` succeeds after 100 ms against a 50 ms wall. The result is `TriageFailed('timeout')` and `cleanup` ran exactly once, through the `tap`.
- **Make (b)'s fake uninterruptible** (`Effect.uninterruptible(Effect.sleep(…))`). That is what proves §1's `disconnect`: without it, (b) settles at 100 ms instead of 50 ms. Assert on elapsed time.

## 8. The `RunSpent` test

`spend` keeps its loop as an `Effect.gen` with a `for`, not `Effect.retry`. The fake store's `append` writes the row and then fails. The second iteration's read finds it (`:939-950`), and `spend` returns null with exactly one `RunSpent` in the stream.
