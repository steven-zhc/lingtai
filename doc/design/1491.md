# #1491: design note

## Where it goes

There are four places, in this order.

1. **`apps/board/src/lib/prs.ts` (the `next` branch, `:345-361`).** This branch now finds the previous PR and hands it to `prPage`.
2. **`apps/board/src/lib/pr-page.ts`.** `PrPageInput` (`:188-209`) gets a new input, and `draftPage` (`:715-760`) branches on whether the draft is empty.
3. **`apps/board/src/lib/pr-branches.ts`.** The `pr === null` path (`:101-122`) gets an empty-draft branch.
4. **`apps/board/src/app/pr-detail.tsx` and `globals.css:3325-3326`.** The legend and the `now` line change on every drawing.

`domain` and `project` do not change. No reducer field, event or ADR is added.

## The one decision the ticket does not make: where the freeze sha comes from

The ticket says to mark *the previous PR's freeze commit (`frozenSha` of its first `PrInProgress`)*. `PrState` cannot give you that.

- `PrState.frozenSha` is overwritten by every `PrInProgress` (`packages/domain/src/pr.ts:299`, `frozenSha: d.frozenSha`).
- The drawing already explains why a later value is wrong: *"The commit the personal branch was frozen at: only the first `PrInProgress`'s. A later walk's `frozenSha` is the PR branch's own head (a pr-fix lands there), which the personal branch does not hold until it is merged back."* (`pr-branches.ts:138-139`).

So for a PR that has had a pr-fix or a retry, `prs[k].frozenSha` names a commit that is not on the personal branch. Do not use it.

**Decision:** read that PR's own events in the `next` branch of `readPrDetail`, using `readPrEvents(project, n, requestStore())`. It is already imported (`prs.ts:22`) and the numbered path already uses it (`prs.ts:363`). Take the first `PrInProgress`'s `data.frozenSha`, which is the same rule as `personalFrozen` in `pr-branches.ts`.

- Make this read only when the drawing needs it: a newest non-draft PR exists, it has a number, it is not `closed` or `refused`, and no PR has `catchUp.outcome === 'caught-up'`.
- Otherwise read nothing extra. The ticket's *"no new read"* holds for the caught-up case, since `catchUp` is on every `PrState` (`pr.ts:97-105`).
- **If this read fails**, let it fail the page the same way the other `yield*`s in that `Effect.gen` do (`prs.ts:399-401`). It reads the same store `prsOf` just read, and the ticket's own rule is that the `next` page never falls back to *no earlier PR*.
- A newest PR still `requested` has no `PrInProgress`. Its freeze sha is then absent: draw no dot and no pointer, and keep the sentence. Whether a `requested` PR can have a `PrSubmitRequested` with no `PrInProgress` yet is settled by that stream's events, not by the code.

## Passing it in

Add one **optional** field to `PrPageInput`. Something like:

```
previous?: { pr: PrState; frozenSha: string | null; caughtUp: { sha: string; n: number | null } | null }
```

It has to be optional because the existing draft tests (`unit/pr-page.test.tsx:114-128`) build `PrPageInput` without it and must stay green unchanged.

- `open` stays as it is. The draft-with-tickets path still uses it for the disabled reason (`pr-page.ts:729-731`).
- `previous.pr` is the newest PR whose status is not `draft`, found with `openAmong`'s walk (`domain/src/pr.ts:621-627`) minus the open-only cut. Write it as a small local helper in `prs.ts`. Do not change `openAmong`, which other code calls for its open-only meaning.
- `caughtUp` is the newest PR in `prs` with `catchUp?.outcome === 'caught-up'`. Its sha is `catchUp.mergeCommit ?? catchUp.mainSha`, because `mergeCommit` is nullable (`pr.ts:101`).

`drawingOf` (`pr-page.ts:523-532`) passes `input.previous` through to `prBranches` as a new optional parameter. This keeps `prBranches` a pure function of its arguments, and `pr-branches.test.tsx` can build the case without a store.

## draftPage

Branch on `error === null && tickets.length === 0`. Leave the other two paths byte-for-byte as they are.

- **Sentence and link.** `poster.line` is a plain string, rendered under *Where it is* (`pr-detail.tsx:164-170`). Add a structured field to `PrPageView` rather than putting markup in a string, for example:

  ```
  previous: { lead: string; name: string; state: string; href: string | null } | null
  ```

  `pr-detail.tsx` renders it as the first sentence, with an `<a>` only when `href` is non-null (the PR's `n` is null otherwise). Set the field to `null` on every other path.
- **Small line.** It replaces `ON YOUR MACHINE` as `poster.line` on the empty path only.
- **State word.** The state word is `POSTER[status].word.toLowerCase()` (`pr-page.ts:230-238`). Do not hand-write a second table.
- **Ticket count.** While `requested`, the count is `pr.draft.length`. Otherwise it is `slipsOf(pr).length` (`pr-board.ts:186-194`). Branch on `status === 'requested'` explicitly. Do not branch on `tickets.length === 0`, which would also hit a started PR whose slips are genuinely empty.
- **Title and buttons.** The empty path uses the title `Next PR — nothing in it yet` and `buttons: []`. Write the sub line's `0 tickets` as it is today.

## The empty-draft drawing

In `prBranches`, when `pr === null`, the draft read succeeded, and the draft is empty:

- **Nodes.** There are no ticket nodes and no `submit` node, and `words: []`. Add one `done` node on `personal`: the caught-up sha labelled `<sha7> caught up with main` (the ticket leaves this label open; this is the choice made here), or else the freeze sha labelled `<sha7> frozen for PR k`. If neither exists, add a single **hidden** node (`hidden?: true`, `pr-branches.ts:28`) so that `now` has something to stand on. Point `now` at whichever node you added.
- **Pointer.** Add a new model field, `pointer: { from: nodeId; text: 'PR k' } | null`, and `pr-detail.tsx` draws it as a dashed path with that text. Set it only when a sentence names a PR and the dot exists. Do not reuse `edges`: an edge needs a target node, and the previous PR has no node in this model.
- **Two lanes.** Add a field to the model and to the laid-out `Drawing`, for example `prLane: false`. `pr-detail.tsx` then skips the PR lane's label and line, and the layout does not reserve its height. You cannot key this off `lanes.pr === null`, because the draft with tickets also has `lanes.pr === null` (`pr-branches.ts:98`) and must keep its *no PR yet* lane.
- **When the newest PR is `closed` or `refused`.** There is no sentence and no pointer. A caught-up dot from an older merged PR is still drawn, because it is true of the branch. The freeze fallback is not used.

## Legend and `now` (every PR page)

- **Legend.** In `Branches` (`pr-detail.tsx:116-125`), take `LEGEND.filter(l => d.nodes.some(n => !n.hidden && n.kind === l.cls))`. If the result is empty, render no `<p className="prp-legend">` at all.
- **The label.** The text changes from `NOW` to `now` (`pr-detail.tsx:76`).
- **The CSS.** `.prp-now` becomes `stroke: var(--muted); stroke-width: 1; stroke-dasharray: 2 3`, and `.prp-now-t` becomes `fill: var(--muted)`.
- **Placement.** Leave `d.nowX` and the line's coordinates alone. Placement belongs to #1492.

## Tests and what checks them

The tests are all unit tests. They assert on the view and on rendered text, never on coordinates (`pr-branches.ts:6`).

- **`pr-page.test.tsx`:**
  - in review → title, sentence, `href` and `buttons: []`;
  - `requested`, with `tickets: []` and `draft` of length 3 → `The 3 tickets`;
  - no previous PR, and a `closed` previous PR → only the small line.
- **`pr-branches.test.tsx`:**
  - no `submit` node, no *no PR yet* word, and `prLane` false;
  - the caught-up dot when one exists, otherwise the `frozen for PR k` label;
  - the `pointer.from` id equals the dot's id.

  Build the freeze case with a PR that has had **two** `PrInProgress` with different `frozenSha`, and assert that the first one is used. That is the case `PrState` would get wrong.
- **`pr-detail-page.test.tsx`:** the legend holds only the drawn kinds, there is no `.prp-legend` when nothing visible is drawn, and the text `now` appears.
- **Not reachable from unit tests:**
  - the extra read in `readPrDetail` would only be exercised end to end by `pnpm test:integration`, which is not run during a pass;
  - the Next build (`apps/release/integration/build.test.ts`) is not affected, because nothing new is imported into a client graph.

  The pure `prBranches`/`prPage` tests stand in for the first. The person's check in light and dark against §F15 covers the rest.
