# Design note for #572: one recommendation, decided in `@lingtai/domain`

## The decision that isn't obvious: a contradicting advice gives `null`, not a substitute

0118 §1 (`doc/decisions/0118-a-hold-explains-itself.md:298-301`) says: *"An advised resolution is recommended when `allowedResolutions` offers it, and otherwise is not, its words still shown."* It allows an advice to be dropped. It never allows the advice to be swapped for a different one. The board's two cause rules move into `recommendedResolution` in that form:

- `cause: WrongApproach` with advice `Approve` or `GrantFixRound` → `null`.
- `cause: FixableLines` with advice `Approve` → `null`.
- `WrongApproach` with advice `Requeue` stays `Requeue`, as it does today.

The board's `wrongApproachOverride` (`apps/board/src/app/standing.tsx:539-545`) recommends `Requeue` when triage advised something else. That is a resolution nobody advised, and the domain function should not take it over. Deleting it means a `WrongApproach`+`Approve` card no longer gets drawn first with "Recommended for this diagnosis" (`standing.tsx:929-931`). That loss is intended: the board and the CLI may only recommend what the function returns.

Both rules need only `status.result.cause`, and that is already on the `TriageAdvised` value `recommendedResolution` receives (`packages/domain/src/wait.ts:634-643`). So no new input is needed and the function stays pure. Put the check beside the existing `allowed.includes(advised)` in the `Done` branch. A contradicting advice gives `null`, not `toDefault()`: the comment at `wait.ts:626-628` says *"a disallowed advice returns `null`, not the default, because there was advice."* Update that docblock to name the two contradictions. Add cases to `packages/domain/unit/wait.test.ts`'s `describe('recommendedResolution')` (`:404`):

- each contradiction gives `null`;
- `WrongApproach`+`Requeue` gives `Requeue`;
- `FixableLines`+`GrantFixRound` is kept where it is allowed.

Do **not** add a cause check to the conductor's triage parse. `packages/conductor/src/triage.ts:339-340` makes a point of not checking: *"An advised kind the wait does not offer still parses; `recommendedResolution` already…"*. Keep that.

## `GrantFixRound` with no saved head: `recommendedResolution` takes the fact, `allowedResolutions` stays pure

The ticket asks whether `allowedResolutions` already drops this case. **Only partly.** `allowedResolutions` (`wait.ts:395-410`) leaves `GrantFixRound` out only when `reason.run.unpushed` is set, or when `grantCriterion` is null.

The board's `standing.fixWork` (`apps/board/src/lib/task.ts:1850-1880`) is a different fact, built from two sources:

- **The last `RunRefsPublished` on the run's stream.** `savedFixWork` (`task.ts:892-920`) refuses on `outcome: 'arm-only'`, on a WIP `armSha`, on `branchCarries === false`, and on a missing `headSha` or `branch`.
- **A live GitHub read.** `client.refSha(`heads/${saved.ref}`)` is compared with the saved head.

The second source is a network read, so it can never be an input to `allowedResolutions`. That function is the one `resolve-wait.ts:221` enforces for every caller. It cannot depend on GitHub being reachable.

So in `standing.tsx`:

- Remove the `advised === 'GrantFixRound' && !(… 'head' in standing.fixWork) ? 'Requeue'` branch (`:557-558`). Pass the fact it tested to the domain instead: `recommendedResolution(reason, status, { savedHead })`, where `savedHead` is false when `fixWork` has no `head`. With `savedHead: false` the function does not return `GrantFixRound` (advice or default), so nothing is recommended in its place; `allowedResolutions` itself stays pure.
- Leave the card itself alone. Where there is no head it already draws as "Cannot continue saved work" with `fixWork.refusal` (`:911-914`, `:926`, `:960-966`). It already withholds `<ContinueFixing>` (`:946-958`), and that refusal tells the person to start over from base.
- The card is the place to say *this cannot run*. Recommending `Requeue` instead is the board re-deciding, which is what this ticket removes.

`savedFixWork`'s first three refusals come from the log, not the network. A follow-up could put them on the `WaitReason` so `allowedResolutions` can see them. That is not this ticket. Mention it in the commit body, and do not do it here.

## What `standing.tsx` keeps: drawing, not deciding

After the change, `:535-560` reduces to this:

```
recommended = recommendedResolution(reason, triageStatus)   // or null without both
shown       = recommended !== null && drawable.includes(recommended) ? recommended : null
```

- `drawable` (`:572`) already leaves out `Split` (#563) and `ContinueConflict` (#559).
- The current `advised === 'ContinueConflict' ? null` (`:556`) is a special case of *"a card that isn't drawn can't be the one drawn first."* Write it that way once, through `drawable`, rather than naming `ContinueConflict` a second time.
- `orderedResolutions`, the `sresolution--recommended` class, and the `primary`/`recommended` props passed to `ContinueFixing`/`Decide`/`Close` all read `shown`.
- `triageRecommended` (`:561-565`) existed to tell the override apart from a real recommendation. With the override gone it is the same as `shown` whenever triage advised. Use `shown` for the class and let the badge say `Triage recommended`. Delete the `wrongApproachOverride` badge copy.

The `TriageBand` words (`:217-226`) must stop testing cause × resolution themselves. Branch on whether the domain's answer kept the advice: `recommendedResolution(reason, status) === result.resolution`. This means `TriageBand` either gets the domain's answer passed in or calls the function itself. Either is fine; don't add a third copy of the test.

- **Kept:** keep `Recommends ${title}`, with its *only your click grants the paid round* suffix for `GrantFixRound`.
- **Not kept:** the sentence may still depend on the cause, because that is copy, not a decision:
  - the `WrongApproach` sentence for a dropped `Approve`/`GrantFixRound`;
  - the `FixableLines` waiver sentence for a dropped `Approve`;
  - a generic *"Triage advised X, which this wait does not offer"* for an advice `allowedResolutions` refused.

## The close box: prefill whenever triage advised

`closePrefill` (`:566-570`) becomes `triageStatus.result.summary` whenever `triageStatus` is `Done` with `TriageAdvised`, whatever the resolution. Leave the `key={closePrefill ?? ''}` remount at `:1013` as it is. The box can still be cleared, and `close.ts:99-100` still refuses a blank reason (0118 §6, `:459-465`).

## The requeue reason: composed once, in the conductor, from the body text

Today the board sends `triage.note` (`apps/board/src/app/decide.tsx:371`). That note is built from the radio picks in `triage-picks.tsx:43`, so:

- it goes stale once the text is edited;
- it is absent when there were no questions;
- the CLI never sends one.

The text that gets written is `EditBodyAndRequeueOptions.text` (`packages/conductor/src/edit-body.ts:148`). Both the board (`actions.ts:286-305`) and the CLI's `--into-body` (`apps/cli/src/requeue.ts:72-88`) already pass through `editBodyAndRequeue`. So:

- **Add a pure `requeueNote(text: string): string` to `@lingtai/domain/wait`.** It should be a fixed prefix plus the text, e.g. `Added to the ticket body:\n…`. Don't say "Triage answers": the text may be the person's own.
- **Call it in `editBodyAndRequeue`.** Before `resolveWaitHolding` (`edit-body.ts:211-218`), use `options.note?.trim() ? options.note : requeueNote(options.text)`. The CLI always passes `note: ''` (`lingtai.ts:1330`, `requeue.ts:86`), so a bare `--into-body` composes a note, and an explicit non-blank `--note` still wins.
- **Plain `Requeue` is unchanged.** It writes no text, and 0118 §6's #424 bullet (`:449-453`) — *"a blank note is stored as empty, never invented"* — still holds for it. A composed note on `EditBodyAndRequeue` is derived from what was written, so it doesn't conflict with that bullet.
- **On the board:** stop sending `note` from `decide.tsx:371`, and drop `note` from `TriagePicks`'s context (`triage-picks.tsx:10,43`).

Tests to change or add:

- `apps/board/unit/edit-body-and-requeue.test.tsx:129-152` asserts `note: 'Triage answers:\n…'` and has to change. Assert that the board sends no note.
- In `packages/conductor/unit/edit-body.test.ts`, assert that the `WaitResolved.note` (`events.ts:313`, a plain `z.string()`) the memory store records is `requeueNote(text)`, both for a picked text and for an edited one.
- In `apps/cli/unit/requeue-into-body.test.ts`, assert the same for `--into-body` with no `--note`.

## "The CLI's recommendation" in Done when

The CLI does not compute a recommendation. No file under `apps/cli/src` calls `recommendedResolution`; the evidence's `lingtai.ts:1282-1375` is only argument parsing. Do not add a recommendation printout to the CLI to satisfy that checkbox; that is new surface area this ticket didn't ask for.

What can be checked instead is that the board draws exactly what the domain function returns. In `apps/board/unit/standing.test.tsx`, render the panel with:

- a `WrongApproach`+`Approve` triage, where no card is recommended and `Approve` is not first;
- a `FixableLines`+`Approve` triage, with the same expectation;
- a `FixableLines`+`GrantFixRound` triage with no `fixWork`, where nothing is recommended (not `Requeue`, not `GrantFixRound`), and the `GrantFixRound` card still draws "Cannot continue saved work".

Each case should compare against `recommendedResolution(reason, status)` called in the test, not against a literal. Say in the commit body that the CLI half of that checkbox does not apply, because the CLI draws no recommendation.

All of this is unit-level. `pnpm typecheck` and `pnpm test` cover it, and nothing here depends on `pnpm test:integration`.
