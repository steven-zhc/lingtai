# #1410 — design: chapter 11, solo

## The fact the chapter is built around

Solo always lands on `branch.main`. What changes between a local project and a GitHub project is the value `lingtai add` writes into `branch.main`, not where solo lands. So the "Watch out" row is one rule with two defaults, and the chapter should say it that way. Telling the reader "local lands on X, GitHub lands on Y" would read as two separate behaviours.

- **Local** (`init --local` / `add --local`). A solo answer skips `askPersonal`, so the base question is asked with `detected = LINGTAI_BASE` (`first-project.ts:635`). That value is seeded as `branch.main`: `mode === 'team' && mainBranch !== null ? mainBranch : base` (`first-project.ts:947`). The comments: "`add --local` lands on `lingtai-base` unless a flag says otherwise (0104 §15)" (`:731`), and "`lingtai-base` is made from the checked-out branch when absent" (`:632`). `--main <branch>` overrides it. `askLanding` can also move it ("can move `branch.main` on a local project", `:1054`).
- **GitHub**. The `branch.main` seed on an absent recipe is the repository's default branch: `const seedBase = base ?? (yield* defaultBranch)` (`add-github.ts:392`, doc comment at `add-github.ts:63-66`). `--main` overrides it (`--base` is refused with exit 2, `add-github.ts:247`).
- The CLI's own words: "A solo project has no PR page: it lands on branch.main itself", and `pr submit` is "Refused … in a solo project" (`commands.ts:153,156`). Solo therefore has no `lingtai pr` step. This one line is the only PR content the chapter needs.

`tutorial.md:31` ("Answer `solo` and work lands on `lingtai-base` too") is therefore correct for chapter 1's local project. Leave the sentence as it is and only add the link.

## Shape of `doc/solo.md`

Use H2 sections in the same style as the other chapters. Suggested sections:

1. **When to pick solo.** The first screen answers it: nobody else works on the repository. Quote the question and the label as `add` prints them (`team.ts:24,44`).
2. **What changes from chapters 1–3.** Every ticket with a kind label and no hold is taken, unless the recipe keeps `source.assignee.take: mine`, which solo honours (`discover.ts:321`); work lands on `branch.main`, and a landed ticket is closed. There is no PR and no `lingtai pr`.
3. **Where work lands.** The rule above, with both defaults and the flag that overrides each.
4. **Switching.** Edit the recipe only; an existing project never moves by itself. In one line each, link to [upgrading-to-0.16.md §4](upgrading-to-0.16.md#4-switching-to-team-if-you-want-it) for the YAML and to `recipe.md` for the keys (0112 §15). Do not repeat the refusal rules (`take: all`, `branch.personal`) beyond one clause.
5. Last chapter, so there is no `## Next` section.

Do not link `team.md`: it does not exist in `doc/` (`ls doc/team.md` fails). The link would resolve to GitHub and 404. Use the upgrading §4 anchor instead.

One sentence the chapter must **not** contain: "re-running `lingtai add` keeps the mode." The local path asks the mode question only when there is no recipe file (`first-project.ts:674`, "a file that already exists keeps the mode it names"). The GitHub path asks whenever the file names no `mode` (`recipe-flow.ts:261`: `at.mode === undefined && rawMode === null && !at.local`), and the default answer is team. Write only the documented "edit the recipe", and leave this mismatch out of the chapter. It is a behaviour question for a separate ticket.

Update the test: add `'Next'` to the heading list and rename the `it` so it no longer says "with no Next".
- **`neighboursOf('safety', all).next` is asserted null** (`docs.test.ts:565`). Change it to `neighboursOf('solo', all).next` being null, and assert that safety's next is `solo.md`.
- **`PUBLIC_SLUGS`**. The `BOOK` comment says "A chapter ticket adds its own row here and its slug to `PUBLIC_SLUGS`" (`docs.ts:125-126`). Without the slug, the page is not served: `neighboursOf` filters by `served` (`docs.ts:163`), and the site would link safety's Next to GitHub. Add `'solo'` in three places:
  - the `PUBLIC_SLUGS` array (`docs.ts:70-86`), with a clause for it in the prose comment above it (`docs.ts:63`);
  - the exact-equality list in `page.test.tsx:131-147`;
  - the menu exclusion list at `page.test.tsx:106-108`, like `board` and `tickets` ("reached through the book"). `DOCS_MENU`'s label list (`page.test.tsx:111-122`) then stays as it is.
- **`tutorial.md` is at 393 words, and the test requires `< 400`** (`docs.test.ts:177`). Make the link by wrapping words already in the sentence, e.g. ``[Answer `solo`](solo.md)``, so that no words are added.

Add a `describe('solo is chapter 11 …')` beside the safety one. It asserts `proseOf ≤ 800`, no `## Next`, and that the body contains both `lingtai-base` and `branch.main`. That last assertion is the unit-level stand-in for "says where work lands for each". Whether the prose matches the code is the reviewer's check, against the lines cited above.
