## Design: #1091, `runDoctor` as an Effect

### The decision the ticket leaves open: what replaces a step's `async` arrow

The ratchet counts **every** `async` function, arrows included. So if you write `Effect.promise(async () => { … })`, the `async` the ticket is meant to remove is still there and the count stays put. The ticket's single example, `Effect.promise(() => logReachable(…)).pipe(Effect.map(…))`, only fits steps whose body is one call. The steps fall into three groups, and each is written differently:

1. **One awaited check, then a push**: `the log` … `end step` in the file-backed branch, and `project recipes`, `declared environment`, `recipe bases`, `settings`, `runtimes` (`src/doctor.ts:3467-3471`). Write these as the ticket shows: `Effect.promise(() => check(…)).pipe(Effect.map((r) => void results.push(r)))`, with `...r` where the row is an array today.
2. **A body with several statements, or several awaits**: `Node` in the checkout branch (`:3268-3277`) and `GitHub` (`:3462-3466`). Make each one an `Effect.gen(function* () { … })` that keeps the same statements in the same order, with each `await x` becoming `yield* Effect.promise(() => x)`. **Do not** wrap the whole body in `Effect.promise(async () => …)`.
3. **Steps that are already non-`async` but return a promise**: `recipes` (`:3301`), `stopped projections` (`:3368`, `:3426`), `paused projects` (`:3371`, `:3431`), `account limits` (`:3372`, `:3432`), `snapshots` (`:3392`, `:3443`), `issue titles` (`:3398`, `:3448`). The ratchet does not count these, but they still have to become Effects, because `step` now takes an Effect. Write each as `Effect.promise(() => theCall(…))`, with the `.then(push)` turned into `Effect.map`. Any step whose body is purely synchronous becomes `Effect.sync`: `Node` in the SEA branch (`:3251`), `packages` (`:3280`), `the store` (`:3296`), `the environment` (`:3350`), `Postgres-only rows` (`:3404`), `Postgres` (`:3453`) and `deferred` (`:3472`).

`grep -n "step('" src/doctor.ts` finds 57 lines. Every one of them takes an Effect after this change, not only the 39 that are `async` today.

### The trap inside `Node`: a caught read must stay caught

`Node` reads `.node-version` inside a `try { … } catch { declaredNode = undefined }` (`:3270-3274`). A missing file is a normal answer there, not a throw. If that `readFile` is lifted with plain `Effect.promise`, the rejection becomes a defect. That defect ends the whole report, and `lingtai restart` would then refuse on a machine that is fine. Keep the catch:

```ts
Effect.promise(() => readFile(…).then((s) => s.trim(), () => undefined))
```

This is the only `try` among the step bodies. Every other throw should stay a defect, as the ticket says.

### Side effects between the steps

- `const choice = store()` (`:3295`) stays a plain statement inside the `Effect.gen` and runs between the same two steps as today.
- `shareFixes(results)` (`:3475`) and the final `return { results, ...tally(results) }` stay in the same places.
- `step` reads `results.length` and emits `start` inside an `Effect.sync` **before** it yields `run`. It stamps the rows and emits `end` in a second `Effect.sync` **after** `run` succeeds. If `run` dies, the second sync never runs. That is today's *"A step that throws stamps nothing and emits no `end`"* (`:3233-3234`), and it needs no `onExit`. Do not add one.

### Rejections still print the same

The handler's `orFailed` → `printedBy` (`src/exit.ts:38-47`) runs `Cause.squash`es any cause that is not a `CommandExit` and prints it through `failed()`. So a check that dies inside `doctorReportEffect` prints the same message and exits 1, exactly as a rejection from `lift(() => doctorReport(…))` does today (`src/cli.ts:99`).

The face goes through `Effect.runPromise` (effect `^4.1.2`, `apps/cli/package.json:28`). The ticket's new unit test should check the **message**, `rejects.toThrow('beacon gone')`, rather than whether it is the same error object. That message is what `world.ts:293`, `restart.ts:731` and `setup-end.ts:29` go on to print.

### The two tests that mock by name

`unit/doctor-render.test.ts:391-396` and `unit/doctor-progress.test.ts:153-162` each take a `read` returning a promise. Keep their `run` helpers' signatures, and change only the mock:

```ts
doctorReportEffect: (o) => Effect.promise(() => read(o))
```

That way no test case body changes. Using `Effect.promise` rather than `tryPromise` also means a `read` that rejects reaches `printedBy` as a defect, the same way a real check does. Check that `doctorReport` no longer appears in either mock. If it is left beside the new key, the tests stay green whether or not the handler is calling the new function.

### The handler

Today the handler is `const { doctorReport, … } = yield* lift(() => import('./doctor.ts'))`, followed by `yield* lift(() => doctorReport({ onProgress }))` (`src/cli.ts:94`, `:99`). The import stays. Only the second line becomes `yield* doctorReportEffect({ onProgress: progress.onProgress })`. The `Effect.ensuring(… progress.clear())` already around it (`:108`) is the finalizer the ticket asks for, so leave it alone.

### Checks

Everything here is checked by `pnpm test`. The ratchet (`packages/domain/unit/effect-ratchet.test.ts`) confirms the count is 314 and that the face is well-formed: its `face()` rejects any body other than one `return Effect.runPromise(…)`. `doctor-progress.test.ts`'s *starts and ends every step in turn* checks the order of `start`/`end` and the stamping. The rewritten `integration/doctor.test.ts` runs only after the merge.
