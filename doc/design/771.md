# Design note — #771, the land checks what is checked out in a local remote

## Where the check goes

The check goes in `integrateEffect` (`packages/repo/src/integrate.ts`), inside the generator and **before the lane-ref fetch at `:437-440`**. It goes through the same `at` port as every other git call (`:340-341`, "`const at = (args, cwd) => gitPort(args, { ...run, cwd })`"). Run it as `at(['worktree', 'list', '--porcelain'], remote)`, with the remote as `cwd`, rather than `-C`, so the fake `git` in a unit test sees one argv shape. A git failure is a `RepoFailed` on the typed channel, and the existing `catchTag('RepoFailed', …)` at `:634` already turns it into `unexpected` with git's detail. So the "a failed read is never nothing checked out" edge needs no code beyond not catching the error.

Put the porcelain parser in a pure exported function, for example `checkedOutAt(porcelain, base): { dir } | null | 'unreadable'`, beside `baseMovedOn` (`:131`). That function is where most unit tests can aim without an Effect harness:

- A block starts at a `worktree <path>` line.
- The hit is the exact line `branch refs/heads/<base>`, compared whole.
- A `bare` block never hits.
- Output with no `worktree ` line at all is `'unreadable'`. The caller refuses that as `unexpected` with the raw output.

## Where `remote` comes from, and which remotes are checked

`IntegrateOptions.remote?: string`. In `packages/conductor/src/conduct.ts`, hand `remote: options.remote` at the `repo.integrate({…})` call, which is at **`:2861`** (the ticket says `:2763`). `provision` already gets the same value at `:2506`.

`options.remote` is set **only for a project with no owner**. `apps/cli/src/conduct.ts:194` says: "Set only for a project with no owner — `ownerlessClient`'s own remote". `packages/conductor/src/ownerless.ts:57` reads it from `remoteOf(recipe)`. A GitHub-owned project gets `undefined`, and `undefined` means no check. That is correct, because its origin is `github.com`.

**The ticket's `isUrlOrScpLike` does not exist.** Nothing by that name is in `apps/` or `packages/`; it may arrive with #745. The nearest rule in the code today is `apps/cli/src/setup-card.ts:108-118`: `SCP_REMOTE = /^[^:@/\s]+@[^:/\s]+:(?!\/\/)\S*$/`, plus "contains `://`". Write the lane's own private predicate in `integrate.ts`, `isLocalRemote(remote)`:

- false for anything containing `://`, including `file://`, as the ticket's URL rule says;
- false for anything `SCP_REMOTE` matches;
- true otherwise.

Do not import it from `apps/cli`. `packages/repo` cannot import from there.

## How the directory, the project and the issue reach the sentence

This is the part that is not obvious from the ticket.

`REFUSAL_READING[reason].says` is handed only `{ branch, base }` (`packages/domain/src/attribution.ts:257`). `diagnoseRefusal` builds `where` from those two fields alone (`:410`). Its callers, `wait-words.ts:113` (`mergeRefusedColumns`) and `:212`, have no project and no directory. `subjectOf`'s comment (`wait-words.ts:56-65`) explains why: the card and board readers have no projection of anything beyond the event.

So **compose the sentence in `integrate.ts`, which has every slot.** It has `options.base`, `options.project`, the `dir` from the parse, and the issue number. The issue number is a new `issue: string` option. `conduct.ts` already holds it as `took.ticket.ref = String(issue.number)` (`:2414`); confirm that it is in scope at `:2861`. Do not parse it out of `ticketId`.

The refusal's `detail` is then:

    <base> is checked out in <dir> — switch to another branch, then lingtai approve <project> --issue <n>
    <the matching porcelain block, verbatim>

There is a precedent: `base-protected` puts its whole remedy into `detail` (`integrate.ts:611`, `refuse('base-protected', \`${baseProtectedRemedies(options.base)}\n${…}\`)`).

On the domain side:

- **`says` gains `detail`.** Change the signature to `(where: { branch; base; detail }) => string`, and have `diagnoseRefusal` pass `input.detail` into `where`. That is the one call site, `:410`. `'base-checked-out'.says` returns the first line of `detail`. If that line is empty, which nothing writes today, it falls back to `` `${base} is checked out in the remote's working tree — switch to another branch, then approve it.` ``, so an empty `raw` can never print `" is checked out in "`. The other twelve readings ignore the new field.
- **`move: { action: 'approve', why: … }`**, not `null`. `MergeRefused` already offers `['Approve', 'Requeue', 'Close']` (`packages/domain/src/wait.ts:344-345`) and continues at `merge` (`:501-502`), and the ticket says approve is the move. The `why` explains that approving re-runs only the land, and that a requeue would buy the work again (0108 §8).
- **`INTEGRATION_OWNER['base-checked-out'] = 'person'`**, which is `pending-migration`'s owner (`:138`). `OWNER_SAYS.person` reads "a hold somebody meant", and that is close enough. Do not add a fourth owner.

The hold's `diagnosis.what` is `reading.what + unpushedSuffix(run)` (`wait-words.ts:120`). The exact-sentence test must therefore be on `diagnoseRefusal(…).what`, or on a `waitWords` call with a run that has no `unpushed`, so that a suffix does not break the equality.

The CLI's line for the same wait comes from `waitCommand` (`apps/cli/src/wait-command.ts:37`). It spells Approve for a non-`SignoffRequired` wait as `lingtai approve <p> --issue <n> --note "<why>"`. That is a second, slightly different command shown beside the sentence. Leave it alone; it belongs to #769, and the sentence is what the ticket fixes.

## The other places that list the reasons

- `RefusalReason` gains `'base-checked-out'` (`packages/domain/src/vocabulary.ts:52-72`), with a one-line comment in the style of its neighbours.
- `packages/conductor/src/step-outcome.ts:53` keeps a hand-written `REFUSAL_REASONS` array. Check whether it is typed as complete. If nothing forces it, `tsc` will not catch a missing entry, so add the reason there by hand.
- `MergeRefused.reason` is `RefusalReason.exclude([...])` (`wait.ts:148`), so it takes the new value without an edit.

## Tests

All the tests are unit tests: a fake `git` port on `integrateEffect` and `createMemoryEventStore()`, plus pure tests on the parser and on `diagnoseRefusal`. A real non-bare checkout with a linked worktree would be integration under 0060 §1, and nothing inside the pass can run it. The parser test on a hand-written two-block porcelain string stands in for it: the main worktree on `main`, and a linked worktree on `lingtai-base`. That string is also what pins "`worktree list`, not `symbolic-ref`".

"No `push` is called" is an assertion over the fake's recorded argv. The fake should also record that no `fetch` ran either, because the check comes first.
