## Design note: #1307 `doctor` names old recipe spellings, and `doctor --fix` rewrites them

Most of the ticket stands as written. Four things in the code today change its shape. One of them changes the `Fix` list itself.

### 1. `--fix` writes one change for the base, not three

When a change writes `branch`, `editRecipe` already takes out both old spellings of the base. It also drops a `repo:` that the removal leaves empty:

- `packages/recipe/src/emit.ts:182-185`: *"`branch.main` is the base's one home: an old spelling the file still carries is the same setting written twice, so a write of the new one takes the old one out in the same edit."*
- `dropOldBase` (`emit.ts:147-163`) deletes `repo.base`, every `steps.admit[*].worktree.base`, and an emptied `repo:`.

So the base needs one change: `{ path: ['branch', 'main'], value }`. Do not write `undefined` removals for `repo.base` or `worktree.base`. They would do nothing, and they would put two paths into `editRecipe`'s error message for one setting (`emit.ts:198`).

This also settles the ticket's "removing an empty `repo:` is optional" point. `editRecipe` removes it, which is what `readOldSpellings` does at `resolve.ts:355-356`. The Done-when line that says `hashRecipe` is unchanged then holds by construction.

**Where the value comes from:** use `resolved.recipe.branch.main` (`packages/recipe/src/recipe.ts:3130-3133`). **Do not use `branchOf`**. In team mode it returns `branch.personal` (`settings.ts:265`, and the schema comment at `recipe.ts:3127-3128`: *"`branch.personal` in team mode, `branch.main` in solo"*). A recipe written before #1306 has no `personal`, so the two agree today. But that is luck, not a rule to build on.

A recipe that already writes `branch:` together with an old base never reaches `--fix`. `resolveSource` refuses it as `twoHomes` (`resolve.ts:271`, `:360-364`). It shows up in the existing `recipe: resolves for every project` row, so the new row gives it a `skip`, as the ticket says for any recipe that does not resolve.

### 2. `oldSpellings` holds display strings, not paths, so the mapping belongs in `@lingtai/recipe`

`readOldSpellings` pushes these strings:

- `steps.admit[${i}].worktree.base` (`resolve.ts:345`)
- `repo.base` (`:353`)
- `${at}.assignee.take: both` (`:371`)

The last one ends in `: both`, so it is not a path. Do not parse these strings in `doctor.ts`. Add one pure function next to `readOldSpellings` in `packages/recipe/src/resolve.ts`, exported from the package index. It takes the `ResolvedRecipe` and returns two things:

- the **lines** for the row's detail, for example `repo.base: main → branch.main: main` and `runtime.assignee.take: both → take: all`;
- the **`RecipeChange[]`**: the one `branch.main` change if any base spelling was found, plus `{ path: [...at, 'assignee', 'take'], value: 'all' }` for each `take` found.

The function maps the three string shapes `readOldSpellings` itself produces. A unit test in `packages/recipe/unit/branch.test.ts` checks the round trip. The fixtures at lines 93, 113 and 125 already produce every shape. For each fixture: apply the changes with `editRecipe`, re-resolve, and assert `oldSpellings: []` and the same `configHash`. That one test is the claim the Done-when line about `hashRecipe` needs, and it runs in the unit half.

The detail line shows the old value of the base. Take it from `branch.main` of the resolved recipe. Where admit and `repo.base` both wrote a base, the admit value wins (`resolve.ts:346`, `:354`), and the row says so by showing that one value on both lines.

### 3. The row reads the report's single resolve, so `ProjectFilter` carries `oldSpellings`

Since #389, the report resolves each project's recipe once (`doctor.ts:3790-3793`, `projectFiltersOnce`). The `ok: true` arm of `ProjectFilter` does not carry `oldSpellings` (`packages/conductor/src/filter.ts:108-130`, built at `:437`).

Add `oldSpellings: readonly string[]` to that arm, copied from `resolved.oldSpellings`, plus `branchMain`, so the row can print the value. Then build the row from `filters` in the same way `projectRecipes(filters, …)` is built at `doctor.ts:3993-3996`:

- a project in `unresolvedProblems(filters)` gets a `skip` that says its recipe does not resolve;
- `filters === null` gets the `skip` for *"the project streams could not be read"*.

Do not copy `recipeGovernsItsBase`'s second `recipeFor` call per project (`doctor.ts:3378-3392`). That is the pattern #389 removed. Any test that builds a `ProjectFilter` by hand will need the new field. `rg -n "ok: true," --glob '*.test.ts'` finds them.

The detail lines should use the function from §2. That means the filter either carries the `RecipeChange[]` as well, or the row rebuilds the change list from `oldSpellings` and `branchMain`. Pick whichever keeps `filter.ts` from importing anything new beyond `@lingtai/recipe`, which it already reads.

### 4. `--fix` resolves again, writes, and then runs the report once

`--fix` does not run the full report before writing. The whole report is slow: GitHub, the runtimes and the release check all run in it. `--fix` does not use any of those results.

Put a separate Effect in `doctor.ts`, for example `fixOldSpellings(load, reach, { by, store?, home? })`. For each project it:

1. calls `recipeLookup(reach)` (`doctor.ts:1455`) to resolve the recipe;
2. builds the changes with the function from §2;
3. if there are any, calls `changeRecipe(project, { changes }, { by })` (`packages/project/src/change.ts:62`);
4. collects one result per project: `written` with the new `sourceHash`, `nothing to fix`, or `failed` with the message.

Then `cli.ts` runs the ordinary report and prints it. The output is what the ticket asks for, and the slow work runs once.

Exit status: 1 if any project failed in step 4, otherwise the report's own `failed === 0` rule (`cli.ts:116`).

`changeRecipe` reads the file again through `draftRecipe` (`change.ts:78-84`). The changes from step 2 are therefore applied to the file as it is at write time, which is the ticket's "edited by hand between the check and the fix" case.

Use `resolved.recipe.branch.main` from this second resolve, never one carried over from the report.

A project whose `changeRecipe` fails does not stop the loop. Catch each project's failure into its result, as `recovering` already does in `doctor.ts`, and let the next project run.

**`changeRecipe` appends even when nothing was written.** `recordFileRecipe` is called on every path (`change.ts:132-138`). It is idempotent only because `recipeChange` compares hashes (`packages/domain/src/project.ts:247-251`, cited in the ticket). So skip the call when the change list is empty, as step 3 says. Do not rely on the append being a no-op. The second-run Done-when test should assert that `store` gained no event, not only that the file is unchanged.

`by` is ``human:${userInfo().username}``, as in `fix-refusal.ts:51`.

### 5. The CLI

- **`cli.ts:87-118`:** add `fix: Flag.Boolean('fix').pipe(Flag.withDefault(false))`. Check `args.fix && args.json` before `doctorProgress` starts and before anything is read. Refuse it through `orFailed('doctor', …)` with a sentence naming both flags.
- **`commands.ts:612-625`:** change the usage line to `lingtai doctor [--verbose] [--json] [--no-color] [--fix]`, and add a line saying `--fix` is the one way `doctor` writes: it rewrites a recipe's old spellings as a new recipe change, and nothing else. Leave `effect: 'reads'` alone (the ticket explains why).
- **`doc/cli.json` and `doc/cli.md`:** both are generated from the definitions by `scripts/cli-doc.ts`, and `apps/cli/unit/cli-doc.test.ts` holds them to the source. Regenerate them after editing `commands.ts`, or the unit half goes red. #1298 is a recent commit that touched both.
- **`doctor.ts:26-31`:** add `--fix` to *"It never writes"* as the second exception, after `NOTIFY`. Say that it writes only through `changeRecipe` and never appends to the log directly.

### Tests (unit half only)

- **`packages/recipe/unit/branch.test.ts`:** the round trip in §2. This is the `configHash` claim.
- **The row:** build `ProjectFilter[]` by hand with and without `oldSpellings`, plus one `ok: false` filter, and assert `warn`, `ok` and `skip` with the detail lines and `fix: lingtai doctor --fix`.
- **`fixOldSpellings`:** use `createMemoryEventStore()` and the in-memory `ProjectFiles`, as `packages/project/unit/change-recipe.test.ts:29,56-57` does with `home: HOME`. Inject `recipeFor` through `reach.recipe` (`doctor.ts:1293`). Run it on a recipe with comments written in the old spelling, and assert:
  - every comment not on a removed key survives;
  - exactly one `ProjectRecipeChanged` with `by: 'human:…'`;
  - a second run appends no event and leaves the text unchanged.

  Cover two projects where the first one's `changeRecipe` fails, and assert the second is still written.
- **Refusal of `--fix --json`:** test it where `cli.ts`'s other refusals are tested, if a unit-level seam exists for that. If none does, put the check in a small exported function, test that, and do not spawn the CLI.

`HOME=/nonexistent pnpm test` covers all of these. Nothing here depends on `pnpm test:integration`.
