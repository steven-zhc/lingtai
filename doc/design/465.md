# #465: design

## The decision the ticket asks for first: the conductor continues the run, not the command

**A `WaitResolved{Approve}` is a request. Whichever process holds the conductor lock, the daemon or `lingtai run`, is the one that calls the continuing `runPass`.** `lingtai approve` and the board's Approve button append the resolution and return. They never take the conductor lock and never merge. Put this paragraph and its four reasons in the commit body, because 0120's *Not decided here* says the answer belongs to this ticket.

1. **The lock.** Under #93 the CLI would have to take `DAEMON_LOCK_KEY` (`apps/cli/src/conductor-lock.ts`, `ConductorLockLive`). When the daemon is up, which is the normal case, the CLI is turned away with `ConductorBusy`. So "the CLI under the lock" would mean approvals fail exactly when the system is running.
2. **Duration.** A continued pass is an ordinary pass. 0118 §11 says *"a conflict after an approval routes as any conflict does"*, so a continuation can pay for a fix round and run up to `runtime.limits.wall`. A board server action cannot wait that long.
3. **The wake already exists.** `WaitResolved` is in `WAIT_EVENTS` (`events.ts:322`), which is spread into `COMPLETION_EVENTS` (`packages/daemon/src/work-loop.ts:93-96`). So the append that records the approval already starts a daemon pass.
4. **There is a precedent.** `RunRequested` is appended by a command and taken by `conductWork` ahead of the queue (`apps/cli/src/conduct.ts:221-246`). A continuation goes in the same place and is taken first.

The cost, which the CLI must tell the person: if nothing is conducting, or the conductor is paused, the approval waits. `lingtai approve` prints `approved — the conductor continues <runId> at <step>`. It no longer prints `landed …`, and its exit code no longer means the change merged.

## The pieces, in the order they depend on each other

### 1. `resolveWait`: `packages/conductor/src/resolve-wait.ts`

0118 §11's signature, `{waitId, resolution, by, note}`, plus two more inputs:

- **`with?: readonly ToAppend[]`**: events appended after `WaitResolved` in the same append. `close` needs this so it can put `TicketClosed` and its `end` plan in the same transaction (`close.ts:132-136` keeps them in one append, and that must stay true).
- **The `client`**: needed only for `Approve`'s `refSha`.

It runs under `deciding` (`approve.ts:62`, moved here) and does these checks in this order. Each refusal keeps its current wording, which is #443's *Watch out*:

1. **The wait is current.** The item is `blocked` and `lifecycle.waitId === waitId`. Otherwise refuse with `not-blocked`, using `approve.ts:200-206`'s wording. The store's version check at append time makes this atomic (464 design, choice 3).
2. **The resolution is offered.** `allowedResolutions(reason).includes(resolution._tag)`, or refuse by name, e.g. `` `Approve is not offered for ProposedEscalated{BuildRed}` ``. This is the first half of #443, for every caller at once. **Leave #443's column drop (`blocked`/`asked`/`needs`/`diagnosis`) to #443.** It is a different rebuild.
3. **For `Approve` only**, carry over `approve.ts:220-281` unchanged:
   - work out which sha is being asked about;
   - check the caller's `onSha` against it (`stale`);
   - require a note when anything still refuses (`refusingOn`, `reason-required`);
   - check `refSha(heads/<branch>) === onSha` (`stale`). This is the *refused if the branch moved* box.
4. Append `WaitResolved` and then `with`.

**This is the only file that writes `type: 'WaitResolved'`.** Today there are three writers: `approve.ts:326`, `approve.ts:563` and `ask.ts:162`. `requeueHolding`'s `OwnQuestion` withdrawal logic and its `onQuestion: 'refuse'` stay with the caller. They decide which resolution is meant, which is a separate question from whether the wait offers it.

### 2. The fold: an approved item is the conductor's, not the person's

`work-item.ts:359-366` currently leaves the lifecycle alone on `Approve`, because `approve.ts` merges synchronously. With the continuation now asynchronous, that would leave a card in *Waiting on you* that nobody is waiting on.

- **Add a lifecycle status `{ status: 'approved', runId, waitId, onSha }`**, written on `WaitResolved{Approve}`.
- **`pnpm typecheck` finds every exhaustive switch on `lifecycle.status`. Read each one, don't just silence it.**
- In `task_view`'s `WaitResolved` case (`task-view.ts:595-603`), the `Approve` branch now:
  - clears `waiting`;
  - sets `state = 'queued'`;
  - writes a note naming the step it continues at;
  - writes a new column, `continue_at` (the step), which the continuation's `TicketClaimed` clears.
- Rewrite the comment at `:597-601`, because it describes `approve.ts`'s synchronous merge, which no longer exists.
- Also add `wait_id`: set by `WaitStarted`, cleared by `WaitResolved`. **The board has no wait id today.** `task_view` has no such column, and `actions.ts:111` sends only `onSha`. 0118 §11 is explicit that the check is *by the wait, not the ticket*.
- **Both columns are a rebuild**: `lingtai projection rebuild task_view`. Say so in the commit body.

### 3. The conductor takes approved items first

In `conductWork`, before the `asked` lookup:

- Select this project's `task_view` rows where `continue_at is not null`. `task_view` is only an index here, so fold each row's ticket stream to confirm it is still `approved`.
- Run the oldest one through `world.runOnce({...common, issue, continuing})`, count it in `outcome.ran`, and return `'looked'`. Its own completion wakes the next pass.
- The check `options.paused` already guards this the same way it guards the queue.
- **`common.merge` is dropped for a continuation.** 0120 §6: *"does not re-inject `--no-merge`, which belonged to the call that was asked."* A daemon started with `--no-merge` must not ask the same question again on the approval of the question it asked.

### 4. `runOnce` with `continuing: { runId, waitId, step, onSha, waive }`

Where `continuing` is set, `runOnce` (`conduct.ts:509`) changes in four places and nowhere else. Everything after the walk is the same code path as any other pass: `PassRouted`, `WaitStarted`, `TicketLanded` with `end`'s plan, and `publishWhatIsCommitted`. This is what deletes `approve.ts:348-450`.

- **Use `continuing.runId`, not a new one** (`conduct.ts:907`). It is the same run, and its stream continues.
- **A continuation claim instead of `claimStep`** (`conduct.ts:3457`). Add a sibling of `claimWorkItem`, `continueWorkItem`, in `claim.ts`:
  - it appends `TicketClaimed{runId: continuing.runId}` only from `approved`, at the version it read;
  - `claimWorkItem` refuses anything that is not `backlog` (`claim.ts:104`), so a separate function is needed;
  - the fold already de-duplicates a re-claimed run (`work-item.ts:268`);
  - a `close` landing between the approval and this claim causes a `ConcurrencyError`, so nothing runs, which is correct.
- **`cut` provisions at `onSha`, not from base** (`conduct.ts:2025-2094`):
  - `ProvisionOptions` (`packages/repo/src/worktree.ts:22`) gains `at?: string`;
  - the cut returns `notCut` when `remoteHead` (`worktree.ts:138`) is not `onSha`, naming both shas;
  - `lease` becomes `onSha` (`:2090`), so the lane's `--force-with-lease` (`:2404`) checks the branch a second time at the moment of landing.
- **`alsoHeldAtMerge` returns `[]`** (`:2696`).

### 5. `runPass({ from })`: the tree is rebuilt, then the walk resumes

`runPass` starts at `let at: Step | null = 'admit'` (`pass.ts:1119`). Behaviour with `from: {step, approved}`:

- **Visit `admit` and `prepared`, then jump to `from.step`.** Skip `design` through `review`. For `from.step === 'merge'`, also skip `proposed`.
- **Why `admit` and `prepared` still run:** the worktree from the held pass is gone, because it is *"removed when this scope closes"* (`conduct.ts:1718`). A check declared at `merge` (for example `pnpm test`) needs an installed tree. Running these two steps again judges nothing.
- **Their refusal is the second "branch moved" refusal.** A refused cut is `admit` reporting `NotDone`, which already routes to `ProposedEscalated{SetupRefused}`. That wait offers `Requeue` and `Close`, so a moved branch becomes a new wait instead of a silent merge.
- This is my reading of 0120 §6's *"continues the run at the step its wait arose at"*, not a departure from it. Add a sentence saying so in `pass.ts`'s doc for `from`.
- **`roundsSpent` starts at what the run has already spent.** Count the `FixRound` decisions in the run's `routesOf` and pass the count in `Ceilings` beside `restartsSpent` (`pass.ts:765`). Otherwise an approval resets the round budget.
- **The waiver applies only to the first visit to `from.step`.** If a conflict after the approval sends the walk back through `merge` on a new head, the approval does not apply to that head.

### 6. The pipeline records `Waived`, and does not run the action

`PipelineOptions` (`packages/actions/src/action.ts:651`) gains `waived?: { name: string; waitId: WaitId }`:

- The first action at the step with that name is not called.
- Its result is `Waived{waitId}` (`domain/src/action.ts:97`), and `cleared` already counts that as passing (`:226`).
- Everything after it runs.
- If the current recipe no longer has an action by that name, nothing is waived and nothing asks. 0047 §1 says the current recipe wins.

### 7. Which step, which action: one pure function beside `allowedResolutions`

`continuationOf(reason, runOutcomes): { step, waive: string | null } | null` goes in `packages/domain/src/wait.ts`. It returns `null` exactly where `allowedResolutions` has no `Approve`, and a unit test holds the two functions to each other. It follows 0118 §1's table **by the proposal's kind**, as the ticket's 2026-10-14 section says:

| Wait | step | waive |
|---|---|---|
| `SignoffRequired` | `reason.step` | `reason.action` |
| `CheckRefused` | `reason.step` | `reason.action` |
| `ProposedEscalated{CheckRefused}` | `proposal.from` | read from the run (see the trap below) |
| `FixerDisagrees`, `ProposedEscalated{FixerDisagrees \| ReviewFindings \| ReviewEmpty}` | `proposed` | `null` |
| `MergeRefused`, `ProposedEscalated{MergeRefused}` | `merge` | `null`: the lane runs again, it is not waived |

**Trap:** `Proposal`'s `CheckRefused` carries `from` and `output` and **no action name** (`proposal.ts:101-105`). Since #471 that is the shape every check refusal waits in. Take the name from the run's last `StepEnded` at `from` on `onSha`: the first action there that did not clear (`stepOutcomesOf`, `read-model.ts:42`). That is the same read `refusingOn` does (`approve.ts:102`).

## Callers, and what is deleted

- **`lingtai approve`, `requeue`, `answer` and `close`, and the board's Approve, Requeue, Send and Answer actions** each read the item's current `waitId` and call `resolveWait`. The board sends the `wait_id` it rendered.
  - Send-with-edit (`actions.ts:578-608`) is `EditBodyAndRequeue` when it edited, not `Requeue`. `resolveWait` refuses it on a `MergeRefused`, as 0118's table says it should.
  - `close` passes `TicketClosed` and its `end` plan through `with` only when the item is `blocked`. A ticket closed while not waiting gets no `WaitResolved` (0118 §11).
- **Delete:** the merge-and-land path in `approveHolding` (`approve.ts:283-450`, together with its `integrate`, `resolveEndActions` and `tellGitHubAbout` imports), and the `afterApproval` exception the 464 design left in place (*"#465 removes this exception"*).
  - Update `approve.ts`'s header (`:15-33`). It calls itself a stopgap that "takes the held run's own `headSha` and merges that", and that is no longer true.
  - `ApproveResult`'s `mergeCommit` becomes the step it continues at. Update the board's `landed …` message (`actions.ts:131-133`) to match.

## Watch out

- **A continuation that dies mid-pass is released like any other dead claim** (0027's reconcile). The item goes back to the backlog, and the next pass cuts from base. The approval is spent. That is the existing rule for a crashed pass, and the continuation does not get its own.
- **Do not inject `--no-merge`, and do not read `options.merge` at all on a continuation.** A test that passes `merge: false` to a continuation and expects it to land is the guard against this. That is CLAUDE.md's #58 lesson in the other direction.
- **Find the action by step and name, never by position.** The current recipe may have reordered the step's list.

## What can be checked before the merge

All of this is unit-level, which is the half the `build` step runs:

- `resolveWait` against `createMemoryEventStore()`:
  - every disallowed tag is refused by name;
  - a stale `waitId` is refused;
  - an `Approve` whose `refSha` has moved appends nothing;
  - a grep-style test confirms no other `src` file contains `type: 'WaitResolved'`.
- `continuationOf`: the table above, plus the `null`-iff-no-`Approve` property.
- `runPass` with fake bodies:
  - `from: merge` visits `admit`, `prepared`, `merge` and nothing else;
  - a `SignoffRequired` at `merge` records `Waived{waitId}` and **still runs the checks declared at `merge` before the lane**;
  - the waiver is not applied on a second visit.
- `conduct-a-whole-pass.test.ts` gets a continuation row through `runOnce`:
  - a held `SignoffRequired` is approved and continued, ending in `TicketLanded` with `end` resolved;
  - a branch that moved after the approval ends in a new `WaitStarted`, not a merge.
- The daemon picking up the item end to end, and the `task_view` rebuild over a real store, are integration. Say in the commit body that they are proven after the merge, by the rebuild a person runs and by T11.
