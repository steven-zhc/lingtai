## 1 [blocker] A declined continuation falls through to the queue, in the same pass

**Decision: bound the row; do not consume it.** Only a continuation that actually claimed something counts as the project's work for this pass. `ContinueRequested` stays without a "consumed" event, so the control stream keeps the single-writer shape `RunRequested` has (`apps/cli/src/conduct.ts:243-247` on `749f65d2` already says why). A new event type would be a second state machine. That costs more than this finding warrants, and it is the thing the `RunRequested` comment argues against.

The shape, in `conductWork` (`apps/cli/src/conduct.ts:255-280` on `749f65d2`):

- Turn the `find`-then-dispatch into a loop over **every** live row for this project, in order, using the same `approved && runId ===` filter as today.
- For each row, call `runOnce({ …common, issue, continuing })`.
- If `result.ok === false && result.stage === 'claim'`, this is `runOnce`'s *nothing was claimed* ending.
  - That ending is the `passedOver`, `notClaimed` and `claim-unconfirmed` declines (`packages/conductor/src/conduct.ts:3584-3601`). The last one has already released what it may have held.
  - Log it as `<name>: continuation of #<n> declined at claim — <detail>`, and **do not** add to `outcome.ran`.
  - Move to the next row.
- Any other result (`true`, `'held'`, or `ok: false` at `recipe`, `env`, `dispatch`, `restart` or `unexpected`) is a pass that ran. Count it, log it as today, and `return 'looked'`.
  - A `recipe` or `env` refusal is not a reason to fall through, because the queue's own ticket would hit the same refusal.
- After the loop, fall through to `runnableNow` / `selectRunnable` unchanged.

The ticket remains `approved`, and its row will be tried again on the next pass. That is intended: removing the `agent:hold`, or the blocker closing, has to make it continue without anyone approving again. The cost is one `runnableNow({only:[issue]})` per pass per stranded row, and it is bounded by the number of approvals still in `approved`. Rewrite the comment above the loop (`:233-253`) to say this. Its sentence *"a stale row … is simply a `runOnce` that claims nothing, logged and moved past"* is what the finding showed to be false.

The board showing nothing about *why* an approved ticket is not continuing is real, but it belongs to a fifth finding, not to this ticket. Say so in the commit body.

**Test, failing first:** in `apps/cli/unit/conduct-continuing.test.ts`, set up an `approvedTicket(store, 470, 'pass-470')`. Its row's `runOnce` returns `{ ok: false, ticketId: 't-470', runId: 'pass-470', stage: 'claim', detail: '…excluded-label' }`. Assert:

On `749f65d2`, `runQueue` is never called, because of the `return 'looked'` at `:279`.

## 2 [blocker] The control append is retried as a whole, and a continuation that still cannot be scheduled says so and has a way out

**Part (a), the read inside the retry.** Move `const at = (await store.read(CONTROL_STREAM)).length` (`packages/conductor/src/resolve-wait.ts:236`) into the `try` block. The `catch` now covers both the read and the append.

**Part (b), not only `ConcurrencyError`.** Retry *any* error, with the same bound of five attempts (`attempt < 4`). A dropped connection is as transient as a lost version race; the CLAUDE.md section on the pooler is the evidence that it is routine here. After the retries are exhausted, still never throw, but stop answering a bare `ok: true`:

- Add an optional field to the success arm: `ResolveWaitResult`'s `{ ok: true; ticketId; unscheduled?: string }`. Its value is the last error's message.
- `approveHolding` passes it through on `ApproveResult`'s `ok: true` arm.
- `approveCommand` and `approveCard` (`apps/board/src/app/actions.ts:116-120`) report it. Print something like `approved — but the continuation was not scheduled (<why>); run lingtai approve again to schedule it`. The approval itself still exits 0, because `WaitResolved` is on the log and that is the record.

**The way out.** An Approve on an item that is **already `approved`** reschedules the continuation instead of refusing. Put the branch in `resolveWaitHolding`, before the `not-blocked` refusal. It applies only when all of these hold:
- the resolution is `Approve`;
- `item.lifecycle.status === 'approved'`;
- `lifecycle.waitId === options.waitId`;
- `lifecycle.onSha === resolution.onSha`.

When they do, it appends **no** `WaitResolved`, only the `ContinueRequested` row (using the same retried append, so pull that into a local function), and answers `ok: true`. `approveHolding`'s own `status !== 'blocked'` refusal (`packages/conductor/src/approve.ts:96-103`) has to let the `approved` state reach that branch too. The duplicate row this can leave behind is harmless: fix 1 dispatches only rows whose ticket is still `approved` on that run, and `continueWorkItem` refuses `lost-race` for the second claim.

This keeps `resolveWait` the only writer of `WaitResolved`, which `resolve-wait.test.ts:646` checks. A second approval of the same sha is not a second resolution, so writing one would be wrong.

**Tests, failing first,** in `packages/conductor/unit/resolve-wait.test.ts`, next to the existing retry tests at `:414` and `:490`. Use a store wrapper over `createMemoryEventStore()`.
- **(a)** `read(CONTROL_STREAM)` throws a plain `Error` the first time. The approval answers `ok: true`, and exactly one `ContinueRequested` is on the control stream. On `749f65d2`, `resolveWaitHolding` rejects.
- **(b)** `append(CONTROL_STREAM, …)` throws a non-`ConcurrencyError` once. Same expectations. On `749f65d2` it answers `ok: true` with no row.
- **The exit:** the control append always throws, so the result carries `unscheduled`. Then a second Approve with the same `waitId` and `onSha`, on a working store, writes the row and appends no second `WaitResolved`.

## 3 [minor] The board sends the wait it rendered; CLI commands read it at the moment they run

**Where the wait id comes from:** the board's own fold, not `task_view`. `standingOf` (`apps/board/src/lib/task.ts:680-715`) already folds `life = item.lifecycle` from the item's events, so `life.waitId` is there for free. Add `waitId: blocked ? life.waitId : null` to `StandingView`.

That means no new projection column, no migration and no rebuild. `doc/design/465.md:48`'s `wait_id` column on `task_view` is dropped in favour of this. Say so in the commit body, because that document is the one the reviewer compared against.

**Threading:**
- `approveCard`, `requeueCard`, `answerCard` and `closeCard` take `waitId: string` from the card that rendered them, alongside `onSha` where they have one.
- `approve`, `requeue`, `answer` and `close` (`approve.ts`, `ask.ts`, `close.ts`) take an optional `waitId?: WaitId`. When it is given, they hand **that** to `resolveWaitHolding` instead of the one they just folded:
  - `approve.ts:163`'s `block.waitId`;
  - `approve.ts:288`'s `item.lifecycle.waitId`;
  - `ask.ts:172`'s `wait.waitId`;
  - `close.ts:152`'s `item.lifecycle.waitId`.

The CLI passes nothing. Its read and its resolve happen inside one command under `deciding`, so "the wait the person was shown" really is "the wait now", and that is fine. Write that sentence where the option is declared, so the next reviewer does not file the same finding about the CLI.

## 4 [minor] A continuation pushes to the held run's own arm

**Decision: take the arm from the held run's attempt number, not from `next.attempt`.** `priorAttempts(before)` already numbers the held run: its `TicketClaimed` is on `before`, and `attempts.ts:178` de-duplicates the continuation's re-claim by run id. At `packages/conductor/src/conduct.ts:1020`:

```
const arm = armBranch(branch, continuation !== null
  ? priorAttempts(before).find((a) => a.runId === runId)!.n
  : next.attempt)
```

That is the same `n` that `attempts.ts:447-449`'s `armOf` uses to name an attempt's arm to the next prompt. So the arm a person is later told to `git fetch` is the arm this continuation pushed to, and the next genuine attempt (`n + 1`) cannot force-push over it.

Rewrite the comment at `:991-1000`. `previous: undefined` decides only that no prior-attempt brief is fetched; it says nothing about the arm. The `!` is safe because `continuation !== null` means `continueWorkItem`'s preconditions were read off this same `before`. Spell that out in a comment, or `throw` with a sentence instead of using `!`.

The prompt's own attempt number for a continuation is still `next.attempt` (2, not 1). This finding does not cover that, so leave it alone. If it matters, it is a fifth finding.

**Test:** `runOnce` cannot be unit-tested as a whole, so put the choice in a pure helper beside `armBranch` in `packages/conductor/src/branches.ts`, for example `armFor(before, branch, continuingRunId | null, nextAttempt)`. Test it in `packages/conductor/unit`: given an item with one `TicketClaimed{pass-1}`, `blocked`, then `approved`, it returns `agent/465/1` for a continuation of `pass-1`, and `agent/465/2` for a fresh claim.
