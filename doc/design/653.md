# Design: #653, a merge conflict gets its own fix-round budget

## The decision the ticket does not make: `FixRound.round` keeps meaning `rounds`

The ticket says the conflict `FixRound`'s "number comes from that counter". Taken literally, that breaks the rule in its own Watch out row. Today four places read `FixRound.round`, or the round it sets, as the pass's `rounds` counter:

- `spentAfter`, `packages/domain/src/pass-next.ts:407`: `case 'FixRound': return { ...spent, rounds: next.round }`
- `routeProposal`, `packages/conductor/src/pass.ts:1354`: `roundsSpent = next.round`
- `continuationRound`, `packages/conductor/src/conduct.ts:569-581`. It takes the last `FixRound`'s `.round` from `PassRouted`, and the largest `StepStarted.round` at `implement`, as the round count a granted continuation starts from.
- `contextFor`, `pass.ts:1227-1230` (`round: roundsSpent`). This value becomes `StepStarted.round` (`pass.ts:1397`), which `continuationRound` then folds.

Take a pass with `rounds: 4` spent. If a conflict round were offered as `FixRound{round: 1}`, `roundsSpent` would go back to 1, and a review that refused afterwards would get three rounds it never had. That is review borrowing from the conflict budget, which the ticket forbids.

**So the shape is:**

- **Schema.** `FixRound` (`pass-next.ts:50-55`) gains `conflict: z.number().int().optional()`. On a conflict round, `round` is `spent.rounds` unchanged (no `+ 1`) and `conflict` is `(spent.conflictRounds ?? 0) + 1`. Absent `conflict` means a `rounds` round, as before.
- **The offer.** In `offerFor`'s `MergeConflict` case (`packages/domain/src/routing.ts:166-168`), write the offer by hand the way `BaseMoved` does at `:169-184`, not through `round()`. It needs no criterion check, because the case passes `true` today. It checks `(spent.conflictRounds ?? 0) >= CONFLICT_ROUNDS_LIMIT` and sets `CeilingReached{ceiling: 'conflict-rounds'}` when it is reached. Otherwise it offers `{ id: 'fix-lines', next: { _tag: 'FixRound', to: 'implement', round: spent.rounds, conflict: n } }`. The id stays `fix-lines`, so the `when: conflict` judge and `destinationOf` need no change.
- **`spentAfter`.** With `conflict` set, return `{ ...spent, conflictRounds: next.conflict }` and leave `rounds` alone. Update the doc comment above it (`pass-next.ts:397-402`).
- **`pass.ts`.** Add `let conflictRoundsSpent = 0` beside `baseMergesSpent` (`:1180`). Like that counter, it is not seeded from `options.from`, which covers the ticket's "a new pass starts at 0" edge (see that comment's *the bound is per pass, and a continuation is a new pass*). Pass it in the `Spent` at `:1268-1272`. In the `FixRound` case (`:1346-1356`), assign `conflictRoundsSpent = next.conflict` when it is set, and `roundsSpent = next.round` only when it is not. The rest of that case, `recheck`, `lapStart` and `at`, stays as it is.
- **Unchanged and correct:** `continuationRound`, and `contextFor`'s `round`. The conflict lap runs `implement`, `build` and `review` at the same `round` as the lap before it. A lap after `MergeBase` already does this (`pass.ts:1344-1352` moves nothing but `baseMergesSpent`), so a repeated round on a later lap is not new.

### What this costs, and why it is accepted

- **A fixer that commits nothing reads as `NothingProduced`.** In a pass where `rounds` is still 0, the conflict round's `implement` visit has `round: 0`. So `nextOf` answers `NothingProduced` rather than `FixerDisagrees` (`pass-next.ts:134`, `outcome.round > 0 ? …`). `NothingProduced` has no criterion and reaches a person. For a conflict fixer that changed nothing, a person is the right floor.
- **The log line can read "round 0 of 4".** `conduct.ts:3647` (`brief.context.round ?? 1`) and `:3662` produce it. This is cosmetic and is not worth changing here.
- **`implement` still gets the fix brief at round 0.** The brief does not depend on the round number: `conduct.ts:3845` dispatches `fixRound` on `brief.again`, which `pass.ts:1794-1800` builds from the visit list. Its `from === 'merge'` branch gives the `on: 'conflict'` refusal (`conduct.ts:3651-3657`).

## The ceiling vocabulary is in two places

- `CeilingReached.ceiling`, `packages/domain/src/route.ts:29`. Add `'conflict-rounds'` after `'base-merges'` and rename nothing. Old `PassRouted` payloads (`events.ts:1244`) still parse, because the enum only grows.
- `Ceiling`, `packages/conductor/src/pass.ts:1002`. It is a hand-written copy, and `ceilingOf` (`proposed-route.ts:254-256`) returns the zod value as it, so `tsc` flags the missing member. Add it there, and extend that doc comment the way it describes `base-merges`.

Put `CONFLICT_ROUNDS_LIMIT = 2` beside `BASE_MERGES_LIMIT` (`routing.ts:38-44`) with its own doc comment. Its difference from that constant is the point: it **does** spend an agent, so it bounds agent rounds that `rounds` does not count.

## Left as it is, on purpose

- **`conduct.ts:4141`.** It counts `roundsSpent` as every route that is not `waiting` or `claim`. It already counts merge-base laps, and it will count conflict rounds too. It feeds only `restartReason`'s text (`:4307-4311`) and the `conductor:judge` `StepEnded.round` (`:4432`), never a budget. Correcting it is a separate ticket.
- **`passCeiling`** (`packages/conductor/src/ceiling.ts:58`). It prints `(restarts + 1) × (rounds + 1) × wall`. Conflict rounds fall outside that number, the way a `GrantFixRound` does. ADR 0070 §8 requires the string to stay "character for character", and many tests across `apps/` and `packages/` assert it. Do not touch it. Say so in the ADR instead, as below.

## Docs

- **ADR 0108 §8** (`doc/decisions/0108-a-refusal-buys-a-round.md:107-112`). The *"A third bound is free and is not a knob"* sentence is where the new one goes: a merge conflict buys its fix round from its own budget of `CONFLICT_ROUNDS_LIMIT = 2` per pass, never from `rounds`. The round runs an agent, so it is outside the ceiling printed above, and its result passes `build`, `review` and `proposed` again. This is an edit to the topic's ADR, not a new file (`doc/README.md`'s one-ADR-per-topic rule).
- **ADR 0120** (`doc/decisions/0120-a-reason-is-a-type.md:365`). It quotes the `CeilingReached` union and needs `'conflict-rounds'` added. Next to the `merge-base` bullet (`:402-415`), add one line saying that `MergeConflict`'s `fix-lines` draws from `conflict-rounds`.

## Tests

- **`packages/domain/unit/routing.test.ts`:** the ticket's three `offerFor` cases. In the first, assert `next` is exactly `{ _tag: 'FixRound', to: 'implement', round: 4, conflict: 1 }`. A `round` of 4 here is the assertion that the trap is closed.
- **`packages/domain/unit/pass-next.test.ts`:** `spentAfter({rounds: 4, restarts: 0}, conflictFixRound)` leaves `rounds: 4` and sets `conflictRounds: 1`. Also parse an old payload: `CeilingReached` with `'rounds'`, and a `FixRound` without `conflict`.
- **`packages/conductor/unit/`, through `runPass`:** the Watch out row. With `rounds` spent, the merge lane conflicts, a conflict round is taken, `review` then refuses with findings, and the route ends at a person with `CeilingReached{rounds}` on `fix-lines`. `a-base-that-moved.test.ts` drives the sibling `BaseMoved` flow and is the template. This is the only test that shows the four readers above do not reset `rounds`. The `offerFor` tests alone cannot show it.

All of this is unit-level. Nothing here needs `pnpm test:integration`.
