## Design note for #354: Queued for a project with no owner

### Where it goes

Three files change. A fourth line gets a small edit.

- **`packages/conductor/src/filter.ts`**: `projectFilter` (`:258-297`) gets a second path for `state.owner === null`. It also takes a new optional fourth parameter.
- **`apps/board/src/lib/board.ts`**: `askProject` (`:525-542`) gets an optional seam so a unit test can reach it.
- **`apps/cli/src/run.ts`**: the two refusals for a project with no owner (`:428-438`) move into `filter.ts`, and `run.ts` calls them from there.
- **`packages/conductor/package.json`**: one new entry in `exports`, so the board's unit test can use `memoryTickets()`.

`queued.ts`, `status.ts` and `runnableNow` stay as they are. They already read `filter.tickets` (`board.ts:531`, `queued.ts:272`, `status.ts:132`).

### Test for no owner with `=== null`, the same test `run.ts` uses

`run.ts:339` branches on `project.owner !== null`. `projectFilter` should use the same test so the two agree about which projects have no owner. `githubClientFor` (`filter.ts:217`) uses `!state.owner`; leave that as it is.

### The path with no owner, in order

1. Do not call `clientFor`. Call `recipeFor(state, undefined)` instead. This is safe: `currentRecipe` ignores its second argument (`projects.ts:153-155`, "`client` is unused and kept so every caller that conducts still passes through the one `RecipeFor` shape").
2. Check the resolved recipe and refuse in two cases. Throw inside the existing `try`, so the refusal comes out of the catch at `:293` as `{ ok: false, problem }`, like every other refusal there:
   - The recipe does not say `source.tickets: db`. Without that, `ticketsFor` returns its `client` argument unchanged (`ticket-store.ts:239`), and on this path there is no client.
   - `remoteOf(recipe)` is null. `lingtai run` refuses this case (`run.ts:428-432`). The filter is the module that "stops any two of them disagreeing" (`filter.ts:15-17`), so it must not say a project will take work when `lingtai run` says it will not.

   This is the rule from #389 that the ticket's **Watch out** row names: report the project as a problem row, never skip it.
3. Call `ticketsOf(state, recipe, …)`. The third argument is never read once step 2 has required `db`. Pass it the same way `run.ts:457` does: `undefined as unknown as Tickets`. If `TicketSourceConflict` is thrown here, the existing catch turns it into a problem row.
4. Return the same `ok: true` shape a GitHub project gets, with `client: tickets`. Nothing reads `filter.client` today: a search for `filter.client` and `f.client` across `apps/` and `packages/` finds nothing. Making the field nullable would spread changes through every caller for nothing. Update the doc comment at `filter.ts:175-181` to say this path carries the tickets in `client`. That comment's claim that "a `db` project's `client` still reaches GitHub for the recipe" has been wrong since #180, because the recipe is now a local file.

### Move the two refusal sentences into `filter.ts`

Export one function from `filter.ts`, for example `ownerlessRefusal(project, recipe): string | null`. `run.ts:428-438` then calls it in place of its own two `if`s. Without this, the wording is written twice and the two copies will drift. #76 is the story of what drifting wording costs.

Use this order and these sentences:

- **The `db` check first.** `ProjectState.owner` is also null for a GitHub project registered before an owner was recorded (`domain/src/project.ts:23-25`, "Null for a project registered before `ProjectConfigured` carried one — re-run `lingtai add` to record it"). For such a project, the missing `db` is the first thing it hits. That sentence must keep telling the person to re-run `lingtai add <owner>/<repo>`, as well as offering `source.tickets: db`. Until now that project got `no owner recorded — re-run lingtai add to record it` from `githubClientFor`, and it should not lose that advice.
- **The `remote` check second**, keeping `run.ts:431`'s wording.

`apps/cli/unit/run-ownerless.test.ts` does not assert either sentence. Its only `toContain` is `'no GitHub App configured'` at `:161`, so changing the wording breaks nothing there.

### The test seam: a function, not `TicketsForOptions`

Add a fourth positional parameter, `ticketsOf = ticketsFor`, with `ticketsFor`'s own signature. Thread it through `projectFilters` (`:299-305`), as `clientFor` and `recipeFor` already are.

- The GitHub path calls `ticketsOf(state, resolved.recipe, client)`. With the default, that is exactly the call made today, so the existing tests in `packages/conductor/unit/filter.test.ts` pass unchanged.
- `projectClient` uses `{ tickets?: TicketsForOptions }` (`:240`), which hands in a SQL store, not a `Tickets`. That shape cannot carry `memoryTickets()`, and the ticket asks for `memoryTickets()`.

The `projectFilter` test should have:

- a `clientFor` that fails the test if it is called;
- a `recipeFor` that resolves a recipe with `source.tickets: db` and `repo.remote` set (like `fromFile`/`client()` in `filter.test.ts:66-77`);
- a `ticketsOf` spy that returns a `memoryTickets()`.

Assert that `filter.tickets` is the same object the spy returned (`toBe`), and that the spy was called once with the state and the resolved recipe. Also add one case for each refusal, asserting `ok: false` and the sentence.

### The Queued test

`askProject(state)` cannot be unit-tested as it stands. With its defaults, `projectFilter(state)` reads `~/.lingtai/<project>/recipe.yml` (`currentRecipe`), and `selectRunnable` reads `task_view` through `readTasks` (`queue.ts:77`). Both are outside the system under 0060 §1, and both fail under `HOME=/nonexistent`.

Give `askProject` an optional second argument, `{ filterFor?, select? }`, defaulting to `projectFilter` and `selectRunnable`. `queuedCards`' existing `ask` seam (`board.ts:563`) is the precedent.

In the test:

- `filterFor` is the real `projectFilter` with the three fakes above. That makes the test exercise the real path for a project with no owner, not a pre-built filter.
- `select` passes `offered` through.
- Assert that `state === 'listed'`, that `offered.runnable` comes back in the order `runnableNow` gives over the seeded `memoryTickets()`, and that a ticket with an excluded label appears in `offered.skipped` with its reason.

The ordering in the ticket's **Want** row is `runnableNow`'s. `selectRunnable`'s sort (`queue.ts:101-106`) is unchanged and already tested.

`memoryTickets` lives in `packages/conductor/test/memory-tickets.ts`, which no package export reaches. Add `"./memory-tickets": "./test/memory-tickets.ts"` to `packages/conductor/package.json`. `@lingtai/event-store` sets the precedent with `"./memory": "./test/memory.ts"`. Put the test in `apps/board/unit/`.

### Keep the database out of the client bundle

The **Watch out** row's first trap is a server-only import reaching a `"use client"` graph. This shape adds no import that could do that:

- `filter.ts` already imports `@lingtai/github` and `ticket-store.ts`, so it is already server-only. The browser-safe piece was split out to `ceiling.ts` (`filter.ts:38-40`).
- `ticketsFor` reaches `@lingtai/event-store` only through a dynamic `import()` (`ticket-store.ts:206-212`).
- The new imports are `ticketSourceOf` and `remoteOf` from `@lingtai/recipe/settings`, which are pure.

Do not add a static import of `@lingtai/event-store` or `db-tickets.ts` to `filter.ts`. Do not import `memoryTickets` from anything under `apps/board/src`.

The only check that sees this leak is `apps/release/integration/build.test.ts`, and it runs after the merge. The unit-level stand-in is a review of the import lines: `git diff` should show no new `@lingtai/event-store` import outside a dynamic `import()`.

### Changes beyond the board

The daemon's startup block (`lingtai.ts:923`), `lingtai status` (`status.ts:106`) and `lingtai doctor` (`doctor.ts:1529`) all read `projectFilter`. With this change they will describe a project with no owner as resolved, where today they print `no owner recorded`. That is intended: it is the same answer `lingtai run` now gives.

`status.ts` passes `reading.clientFor`, and doctor passes an offline client when there is no App (`doctor.ts:1503`). Both are skipped on this path, which is correct because neither is needed.

### Not in this change

- `projectClient` (`filter.ts:238-248`) builds a GitHub client before anything else, the same way `projectFilter` does.
- The board's task page and prompt actions call `githubClientFor` directly (`task.ts:1316`, `task.ts:1405`, `prompt.ts:158`).

Both are the same gap for other surfaces. Leave them alone here; the shared refusal function will be ready for them.

### The event log

None of this appends an event, and Queued is not a fold. Only one thing in the log decides which path a project takes: the `owner` field of the project's `ProjectOnboardingStarted` (from the slug, `project.ts:78`) or of its `ProjectConfigured` (`project.ts:88`). Null means the path with no owner.
