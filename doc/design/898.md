## The decisions the ticket does not make

**1. The rail's cells get a third `Skeleton` shape. Do not write a second component.**
- Today `SkeletonShape` is `'card' | 'lines'` (`apps/board/src/app/skeleton.tsx:10`).
- The file says it is "Generic on purpose — it knows nothing of the board's data".
- 0111 §15 says "There is one placeholder component, and every waiting part uses it."

So add a shape, say `'cells'`. It draws `count` cells, each an `sk-bar`, in a grid laid out like `.segs`: `repeat(var(--steps, 10), minmax(0, 1fr))` (`globals.css:494`). A rail-shaped placeholder that stands outside the component is the "second skeleton" the Watch-out row forbids. The `.sk-*` rules sit together under the 0111 §15 comment block (`globals.css:3015–3055`), and the new cell rule goes there too, at the `.scell` bar height of 5px (`globals.css:512`).

**2. The cell count is `STEPS.length`, not the plan's length.**
- The plan comes in GitHub's answer: `plan={a.queued?.plan}` (`standing.tsx:878`). So the fallback cannot know how many steps the plan has.
- What can be known without GitHub is the ten steps: `STEPS` from `@lingtai/domain`, which `lib/progress.ts:35` already imports.
- The CSS default `--steps` is 10, so the placeholder lines up with a plan rail of ten steps.

A recipe whose plan has fewer columns will shift by those cells when it arrives. 0111 §15 accepts sizing "from the last answer seen", but nothing on the task page keeps the last plan, and keeping one is new state. That belongs to a later ticket, not this one.

Only the `standing.state === 'queued'` branch of that fallback changes. Where `progress !== null`, the fallback already draws the real `<Rail>` from the log (`standing.tsx:869`), and that stays.

**3. `arrive` has to be widened, or nothing fades.**
- The rule is `.card.arrive { animation: card-arrive … }`, and the reduced-motion override names `.card.arrive` (`globals.css:3053, 3055`).
- So `arrive` on a `div.topening` does nothing.
- Change both selectors to plain `.arrive`, which is the same keyframe. The board's cards keep working, because `page.tsx:252` puts `card … arrive` on one element.

**4. `arrive` goes on the element that takes the placeholder's place, and only on the answered render.**
- **Opening:** the fallback is `TicketContext` with `pending` (`standing.tsx:787`), and the answer is `TicketContext` without it (`:792`). Make the root `topening${pending ? '' : ' arrive'}`.
- **Ticket tab:** the `tref` line and the title are the log's and are drawn in both branches (`ticket-tab.tsx:22–43`), so they must not fade. Wrap the body `<details>` and the sentence chain under it (problem / *This issue has no body.*) in one `<div className="arrive">` when not `pending`.
- **Queued reasons:** wrap the answered fragment (`standing.tsx:1011–1025`) in a `<div className="arrive">`.
- **Rail:** the answered `<Rail>` is the arriving part. Wrap it, or pass a class through. Do not add `arrive` to `Rail` itself: `Rail` also draws the board's cards and the running rail.

The failure sentences come from the answered branch: `problem` in `TicketContext` (`standing.tsx:302–306`), `ticket.problem` in `Ticket`, and the *GitHub has no issue #N* / `refusal` paths around `standing.tsx:990`. They therefore arrive inside the `arrive` element and replace the skeleton. That is 0118 §2's "said where the answer would be", and it needs no extra code. Check the 404 path, which returns `null` from the opening (`missingOf(a)`, `standing.tsx:789`). There the placeholder disappears and the sentence elsewhere carries it. That is correct; do not draw a skeleton for it.

**5. A live refresh does not fade again, and nothing new is needed for that.**
- `live.tsx:145` calls `router.refresh()` inside a transition (`startRender`).
- React does not put an already-revealed `Suspense` boundary back on its fallback during a transition. The revealed element stays the same DOM node with the same class, so its CSS animation does not restart.

Do not give the `arrive` wrappers a `key` that changes between renders, such as one derived from the answer. A remount would replay the fade on every append.
