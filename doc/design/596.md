## Design: #596, the tutorial's GitHub part

### Where it goes

Add one new part to `doc/tutorial.md`, after `## Optional Step 5 — Open a pull request`. Title it something like `## Part 2 — Move the project to GitHub`. Steps 1–5 stay as they are, byte for byte. Outside the new part there are only two edits:

- Add a row to the **Before you start** table for a GitHub project: a repository you own or administer, and the permission to create and install a GitHub App on that account or organisation.
- Add a link from the `--local` row (`tutorial.md:117`) down to the new part.

Do not touch `doc/zh/` (it has no tutorial). Do not touch `doc/github.md`: link its `## One App, and it is not a person` and `## Where the App's credentials live` sections and do not restate them.

The new part starts from the end of the local walk-through. The store is initialised, so the GitHub part runs `lingtai add`, not `init`. The board from Step 3 is still the one in use.

### The repository is the reader's fork, not `steven-zhc/chapter-garden`

Installing an App needs admin on the repository. A reader cannot install their own App on `steven-zhc/chapter-garden`. The part therefore uses `<you>/chapter-garden`, and the fork link the tutorial already gives (`tutorial.md:22-24`) becomes required here, not optional. State this in the Before-you-start row.

### The order the code actually runs, which the part must follow

1. **A board must already be running.** `lingtai add` starts no board of its own (`first-project.ts:143`, *"A board already running, or null — `add` starts none of its own."*). Without one it refuses with `first-project.ts:587`: *"no board is running here to create the GitHub App on — start one with lingtai init --project github, or lingtai board, then run this again."* Tell the reader to keep `lingtai board` from Step 3 running.

2. **`lingtai add <you>/chapter-garden --github-app create`** asks its recipe questions first. When no App exists the questions still run and write the recipe (`add-github.ts:177-182`). The recipe flags Step 1 used (`--agent`, `--install`, `--build`, `--land`) may be passed here: `askBeforeGithubAdd` consumes them (`add-github.ts:323`, `delete flags[name]`) before `runGithubBranch`'s refusal of recipe flags at `first-project.ts:529-547` can see them. Next comes the App question: prompt `create the GitHub App now, or skip it for later`, flag `--github-app create, or --github-app skip` (`github-app.ts:63-69`). The CLI then opens `<board>/setup/github-app` and prints `waiting for the App — press Create on that page, or any key here to skip` (`github-app.ts:113-119`). The wait is ten minutes (`APP_WAIT_MS`, `github-app.ts:15`). If it times out or is skipped, it prints the come-back line from `appComeBackLine` (`github-app.ts:82-87`).

3. **The board page** (`apps/board/src/app/setup/github-app/page.tsx`). Quote its labels exactly:
   - fields `App name`, `Organisation`, `Webhook URL`
   - button `Create the App on GitHub`
   - the note that GitHub's own next screen needs a person to press **Create GitHub App**. That label is quoted on the board page, so it may be quoted in the tutorial.

   Tell the reader to leave the webhook blank. The page's own text says blank *"declares the hook inactive, and nothing degrades: discovery runs on the daemon's sweep"*, and a localhost URL is not offered.

   Describe GitHub's screens only through the strings the board quotes. Do not invent labels for them.

4. **Creating is not installing.** On success the page says *"Creating is not installing"* and gives `https://github.com/apps/<slug>/installations/new`. In the terminal, `waitForApp` prints `app          <slug>, owned by <owner> — it answered`.

   **Then this same `add` run ends in a refusal, and the tutorial must say it is expected.** After the App appears, `runGithubBranch` goes straight on to the picker (`first-project.ts:597-618`). At that point nothing is installed, so `choose` refuses with *"The App is not installed on <owner>, so it cannot see <slug>."* (`pick-repository.ts:291`, printed through `refusalLines`). Present this as the cue for the next step, not as an error.

5. **Install on the one repository, then run `lingtai add <you>/chapter-garden` again, without `--github-app`.** Once an App is configured, `--github-app create` is refused: *"--github-app create, but a GitHub App is already configured here and none is created now. Leave out --github-app, or pass --github-app skip."* (`first-project.ts:271-276`, `:285-290`, `:559-565`). The successful run prints `installation <id> on <account> (<selection>)` and `permissions: issues, contents, pull requests write; metadata read` (`onboard.ts:291`, `:301`).

### The two places the ticket's wording disagrees with the code; follow the code

- **The private key is not in `config.yml`.** `create-app.ts` writes the PEM to its own file. The default is `~/.ssh/lingtai-agent.private-key.pem` (`KEY_PATH_DEFAULT`, `create-app.ts:83`), with mode `0600` (`:88`). `config.yml`'s `github:` section receives `app_id`, `app_private_key_path` and `webhook_secret` (`create-app.ts:653-657`). The board's Created screen says exactly that split.

  Write: *the key is a file at the path the board names, and `~/.lingtai/config.yml` holds its path, the App id and the webhook secret.* Keep the ticket's real point, that GitHub hands the key over once. The board's own sentence for it is *"GitHub hands a private key over exactly once, so that one cannot be fetched again."* `doc/github.md:66` mentions an inline `app_private_key` form; leave it to that doc.

- **`lingtai doctor` checks the credentials, not the installation.** Its row is `github: app credentials` (`doctor.ts:820`). It reads `app <id> from <source>, key from <keySource> · requires issues:write, contents:write, pull_requests:write, metadata:read (verified per repository by lingtai add)` (`doctor.ts:842-846`). With no App the row is `skip`, not `fail`. The installation and its permissions are proved by the second `lingtai add`, as the deferred row `github: installation and labels` says (`doctor.ts:883-889`).

  So "how to check it worked" has two parts: `doctor`'s row is `ok`, and `add` prints the `permissions:` line. If permissions are missing, `add` prints the gap list ending *"Fix them in the App's settings, then re-run."* (`onboard.ts:297-299`).

### The permissions table

Build it from `REQUIRED_PERMISSIONS` (`packages/github/src/app.ts:178-183`). Copy each `why` string verbatim; the board's `Permissions` component draws the same list. Add the `issues` event subscription the board lists beside it. Say once that the reader does not choose these: the manifest carries them, which is the board's *"You never choose them, so they cannot be chosen wrong."*

### Smaller decisions

- The App is the reader's own. Lingtai is self-hosted and no shared App exists. Put this in the part's first paragraph, then link `doc/github.md` for why an App rather than a token.
- Use the installed `lingtai` binary, as the rest of the tutorial does. The board's own text says `pnpm lingtai add`; do not copy that prefix.
- If the dependency list #597 is producing is in the tree when you start, link it from the new Before-you-start row. If it is not, link `doc/github.md` and do not link a file that does not exist.
- After the second `add`, end the part by pointing back to Steps 2–4. A ticket on a GitHub project is a GitHub issue carrying a kind label, not `lingtai ticket new` (`tutorial.md:142`). Say so in one line; do not walk the loop a second time.
- Add no images. The ticket's Watch out rules out screenshots, and `scripts/the-pass.py` draws only the pass.
