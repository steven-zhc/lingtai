# #910: what the change looks like

The ticket gives the fields and the functions. Five things below are not obvious from it, and each one changes the code you write.

## 1. `kinds` holds the order `selectRunnable` actually sorted by

`selectRunnable` does not use `filter.kinds` exactly as it arrives. It runs `const kinds = options.kinds.length > 0 ? [...options.kinds] : ['bug']` (`packages/conductor/src/queue.ts:71`). So a recipe with no kinds is sorted as `['bug']`. Put the same fallback on `QueuedView.kinds` in `queuedFor`, so the *why first* line describes the order the queue really used. Don't export a new helper from `queue.ts` for this; one line copying that expression next to the call at `queued.ts:276-281` is enough. On `problem`, `kinds` is `[]`, and `kindOrder` returns `null` so the panel draws its placeholder. Never return an empty string from it.

## 2. Read `kind` from what GitHub offers, not from the runnable list

A ticket that is backing off is offered by GitHub but missing from `runnable` (`queued.ts:284-287`: *"An item GitHub offers and the backoff holds is missing from `runnable` and is being offered all the same"*). Its kind still explains its place once the backoff ends. So:

- Take `kind` from `offered.runnable.find((o) => o.ref === issue)?.kind ?? null`. `offered.runnable` entries carry `kind`, because `selectRunnable` filters on `o.kind` at `queue.ts:89`.
- Take `behind` from `runnable[at + 1]` only when `at >= 0`. Otherwise it is null.

Make `behind` `{ issue: string; title: string; kind: string } | null`, which is the `Runnable` shape minus `taskId` (`queue.ts:100`). The panel will want the title, and you already have it in hand.

Both places that build a view on failure need the three new fields: `refused` in `queued.ts`, and `refusedQueued`, which `loadTaskAnswer` calls in its `.catch` (`apps/board/src/lib/task.ts:1957-1959`). Without them, the throw path type-checks only because of a spread, or fails to type-check. Set `kind: null, kinds: [], behind: null` in both.

## 3. `planFor` for a queued ticket must not change `limits`

`planFor` is gated on `standing.state === 'running' || standing.state === 'blocked'` (`task.ts:1689-1691`). Its result feeds both `plan` and `limits` (`:1692-1693`), and the comment there says `limits` is `held`'s fallback ceiling *"only source for a ceiling the run's own stream never named (`#415`)"*. If you widen the gate to `queued` and leave those two lines as they are, a queued page gets a `plan` and `limits` it never had. That breaks the ticket's *no rendered page changes* requirement.

Do this instead:

- Widen only the call: `running | blocked | queued`.
- Keep `plan` and `limits` behind the old `running | blocked` condition.
- Have `planFor` also return `concurrency: concurrencyOf(filter.recipe)`. `ProjectFilter` carries `recipe` on its `ok` branch (`packages/conductor/src/filter.ts`, the `recipe: Recipe` field of the `ok: true` arm). This is the same one-read reasoning as `#415`'s comment at `task.ts:1522-1526`: *"both come off the one `projectFilter` read"*.

A queued page then reads the recipe twice, once here and once in `queuedFor` (`queued.ts:251`). That is acceptable. The two halves are separate promises by design (#886), and sharing one read between them would make the log's half wait for GitHub's.

## 4. The `inFlight` builder: one pure function, and `held` stays the only definition

`held` returns strings (`project#issue`, `packages/daemon/src/control.ts:404-406`). Don't write a second `running || verifying` filter. Call `held(rows)` and split each string at `lastIndexOf('#')`. The issue is a number, so the last `#` is always the separator. `apps/board/src/lib/health.ts:20` already imports `held` from `@lingtai/daemon/control`, so the board can reach it.

The builder:

```
inFlightOf(rows, project, concurrency: number | undefined, ceilingSet: boolean): InFlight | null
```

- Return `null` when `concurrency` is `undefined`, meaning the recipe was not read.
- With no ceiling: `slots: 1`, and `running` is every row `held` names.
- With a ceiling: `slots: concurrency`, and `running` is only this project's rows.

This mirrors `isFull` at `apps/cli/src/conduct.ts:350-351`: `slots.ceilingSet ? slots.set.of(name).length >= limit : slots.set.size >= 1`.

Compute `ceilingSet` the way the conductor does: `machineDayCeiling() !== undefined` (`conduct.ts:594`). Do it in `loadTask`, not inside the builder, so the builder stays pure and its test needs no config. `machineDayCeiling` reads `~/.lingtai/config.yml` on every call, and `readDayReading` wraps it in a `try` (`apps/board/src/lib/day-spend.ts:42-48`). Do the same here: if it throws, `inFlight` is `null`. An unreadable ceiling means unknown, and that is not the same as one slot.

Put `InFlight`, `inFlightOf`, `queuedChip`, `queuedSentence` and `kindOrder` in `queued.ts`, next to `holding` and `place`. `task.ts` imports `InFlight` from there for the `TaskDetail` field. That gives one type with one home, rather than one per page half. Set `inFlight` only when `standing.state === 'queued'`; every other state gets `null`, because nothing else draws it.

## 5. Which wording wins when there are no free slots

`queuedSentence`'s third and fourth cases describe this project's slots. Without a ceiling, `running` can hold another project's attempt, and *as soon as the running attempt finishes* is still true then. Don't name the project in this ticket; that is for the panel's markup. `running.length > slots` can happen when the limit was lowered while passes were still in flight (`conduct.ts:343-346`: *"the slot count and the same-file rule are what keep a lowered limit honest until they have drained"*). Treat it as full and use the number in `running` for N, not `slots`.

## Checks

Everything here is checkable with unit tests:

- `inFlightOf` takes rows and returns a value, so it needs no database.
- `queuedFor` is already tested with `selectRunnable` and `runnableNow` stubbed (`apps/board/unit/queued.detail.test.tsx`).
- The `loadTask` wiring has no unit test, and the ticket doesn't ask for one. The claim that stands in for it is the `inFlightOf` test plus `pnpm typecheck` on the new `TaskDetail` field.

Run `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test`.

None of this contradicts an ADR. 0118 §2 already states the split between the two halves.
