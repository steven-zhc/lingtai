### The port

The port is two git operations. It never reads the worktree's state before acting on it.

```
clean(): Promise<{ ok: true } | { failed: string }>
keep(name): Promise<{ committed: sha } | { nothing: true } | { failed: string }>
```

- **`clean`** runs `git reset --hard HEAD`, then `git clean -fd -e /<plantAt>`. Do not use `-x`.
- **`keep`** runs these in order:
  1. `git add -A -- . ':(exclude)<plantAt>'`
  2. `git diff --cached --quiet`. A zero exit means `nothing`.
  3. `git commit -m "chore(implement): <action name>"`. Name the issue as `#ref` with no verb beside it (CLAUDE.md, *Commits*).
  4. `git rev-parse HEAD`
  5. `recordCompletion(head)`

**The clean excludes the planted file with `-e`, not with `:(exclude)`.** This is the one place this design departs from the letter of the triage, and it keeps the triage's intent. With a pathspec, `git clean -fd` removes a wholly untracked directory as one unit, including a file the pathspec excluded. I checked this on this machine with a throwaway repo:

- `git clean -fd -- . ':(exclude)sub2/.env.local'` printed `Removing sub2/` and deleted the planted file.
- `git clean -fd -e /sub/.env.local -e /.env.local` kept both planted files and removed the junk beside them.

`plantAt` is usually beside a tracked `.env.example` (`packages/recipe/src/propose.ts:317`), so the directory case is rare. It is also silent, and it deletes secrets the next `pnpm install` needs. Anchor the pattern with a leading `/` so that it names exactly that one path. `git add` has no such trap, so it keeps `:(exclude)` as the triage says.

### The action, in order

The wrapper calls `clean`, then the inner process action, then `keep` or `clean`:

| Step | Outcome | Verdict | `head` | `evidence` |
|---|---|---|---|---|
| `clean` before the command | failed | **`failed`** | absent | the git refusal |
| command | exit 0, and `keep` returns `committed` | `passed` | new sha | `committed <sha>` and the tail |
| command | exit 0, and `keep` returns `nothing` | `passed` | absent | `nothing to commit` |
| command | exit 0, and `keep` returns `failed` | `passed` once `clean` has run again (or `failed` if that clean fails too) | absent | the refusal |
| command | non-zero exit or timeout | `passed` once `clean` has run again | absent | `` `pnpm fmt` exited 1, nothing committed, `build` judges the agent's commit as it stands `` and the tail |
| `clean` after the failure | failed | **`failed`** | absent | both reasons |

**What happens when git itself fails.** The triage's Q2 covers a command that fails. It does not cover the case where git cannot put the tree back, for example because of a stale `.git/index.lock`. In that case the action returns `failed`.

`endingOf` turns a `failed` at a step that may not refuse into `did-not-finish` (`pass.ts:1800`): *"a step that may not refuse has not refused"*. That stops the pass for a person. Stopping is correct here, because `build` runs in this same worktree. If the tree cannot be put back, `build` would judge files that `merge` will never land. This is a fault in the machine, not a judgement about the diff. Write it down in `runPlugin`'s comment. Do not edit `endingOf`.

**`context.onSha` is not the agent's commit.** It is *"the commit the whole pipeline is about"* (`packages/actions/src/action.ts:585`), which at `implement` means the head before the agent ran. The port works only from the worktree's `HEAD`. Never reset to `onSha`, because that would drop the agent's work.

**A `run` before the agent is legal.** `implement: [run, agent]` cleans the base and finds nothing to commit. Say so in the comment. Do not refuse it.

### How the commit reaches `build`

The commit reaches `build` only through `ActionResult.head`. `headFrom` (`pass.ts:1831`) takes the last result that has a head. So a `run` after the agent wins when it commits, and the agent's head stands when the `run` returns none.

A fix round routes back through `implement` (`pass.ts:504`). `runPass` resolves `actionsAt` again on that visit, so the `run` runs again with nothing extra to build.

### Tests

All of these go in `unit/` with the `packages/conductor/test/one-pass.ts` fakes. The port is a fake function, and the command runner is injectable, so no test spawns a process or calls `git`.

- **Commit:** the fake `keep` returns a sha. `build`'s `onSha` equals that sha, and `clean` was called before the command.
- **Nothing to commit:** the fake `keep` returns `nothing`. `build`'s `onSha` is the agent's sha.
- **Fix round:** there are two `StepPassed` events with `step: "implement"` and `action: "format"`, one per visit. The second `build` sees the second commit.
- **Command fails:** `implement` passes, `clean` is called twice, `keep` is never called, and the evidence carries the note.
- **`clean` fails:** the pass ends `did-not-finish` at `implement`.
- **Step matrix:** every `actionsFromRecipe` call in `step-matrix.test.ts` needs `keptRun` in its deps, or the new refusal fires.

The real `git` behaviour can only be tested with a `git` binary, which makes it integration and out of reach inside a pass. That covers the reset, the `-e` clean that spares the planted file, and the `:(exclude)` add that never stages it. The seam tests above stand in for it. If you write an integration test for it, assert the untracked-directory case from the table above, because it is the only part that has a trap.
