## Design: `run:` at `implement`

### Shape

Two packages change, plus the conductor's wiring:

1. **`packages/recipe/src/recipe.ts:143`**: add `implement: notBuiltYet` to `runPlugin.at`, and extend the doc comment above it. It has to say why `implement` is open, and what a failure there means (see *Failure* below).
2. **`packages/actions/src/from-recipe.ts:245`**: branch on the step, the way `agent:` already does at line 282 (`if (step === 'implement') … createWorkAction`). At `implement`, a `run:` builds a new action. It is not the plain `createProcessAction`. Call the new action `createFixUpAction` in its own `fix-up-action.ts`, and give it a new dep, `ActionDeps.commit`. If that dep is absent, refuse by name with `ActionUnavailableError`, the way `file:` without `deps.file` is refused (`from-recipe.ts:313`). At every other step `run:` stays exactly as it is.
3. **`packages/conductor/src/conduct.ts`**: supply `commit` in `stepDeps`, beside `keep` (`conduct.ts:2028`). It is a closure over `cwd` and `gitAsked`, the same as the keep.

The new action wraps `runCommand`, as `process-action.ts` does, and then calls `deps.commit`. Keep the action free of `git`. `file-action.ts:32` gives the reason: *"a filesystem and a `git` binary are things only a caller with a machine under it has"*. Under the pass fakes the dep is a function, so that is what makes the Done-when tests unit tests.

### How the commit reaches `build`

It reaches `build` through `ActionResult.head` and nothing else. `headFrom` (`pass.ts:1831`) takes *the last result that has a head*. So:

- **The command changed something:** the action returns `head: <new sha>`. That wins over the agent's `head` and moves `onSha` for `build`.
- **The command changed nothing:** the action returns no `head`. The agent's commit stays the step's head, with no special case needed.

**Trap: `context.onSha` inside the action is not the agent's commit.** `runActionPipeline` hands every entry the same `onSha`, which is *"the commit the whole pipeline is about"* (`action.ts:582-586`). At `implement` that is the head before the agent ran. The commit dep must work from the worktree's actual `HEAD`. It must never reset to, diff against or parent onto `context.onSha`, because that would drop the agent's work.

What `commit` does, following the keep's pattern at `conduct.ts:2043-2066`:

- Run `git add -A`. That respects `.gitignore`, which is correct here. The keep's `-f -- path` is wrong here: a formatter that touched an ignored file has not changed the change.
- Run `git diff --cached --quiet`. A clean result means nothing changed, so return no head.
- Otherwise run `git commit -m …` and then `git rev-parse HEAD`.
- The answer has three branches, as `KeptAnswer` does: `{ committed: sha }`, `{ nothing: true }` and `{ notCommitted: reason }`.

Commit message: `chore(implement): <action name>`, with `ran \`<run>\`` in the body. Never write a `#number` beside a closing verb (CLAUDE.md, *Commits*). The keep's message names the issue as `#${options.issue}` with no verb, and that is fine to copy.

### Failure: the decision the ticket leaves open

**The action never returns `failed` at `implement`. It returns `passed`, says why in `evidence`, and puts the worktree back at `HEAD`.**

Returning `failed` is ruled out by today's code. A `failed` at a non-refusing step does not quietly pass through. `endingOf` turns it into `did-not-finish` (`pass.ts:1795-1803`): *"it does not reach the router, because a step that may not refuse has not refused"*. That stops the pass for a person, and a broken `pnpm fmt` would park every ticket. So the translation belongs in the action, not in `endingOf`. Do not edit `endingOf`, because it handles `file-brief` and the agent at the same step correctly.

What each outcome returns:

| The command… | Verdict | `head` | Tree afterwards | `evidence` |
|---|---|---|---|---|
| exits 0 and changes files | `passed` | the new commit | clean at that commit | `committed abc1234` plus the tail |
| exits 0 and changes nothing | `passed` | absent | unchanged | `nothing to commit` |
| exits non-zero or times out | `passed` | absent | **restored to `HEAD`** | `` `pnpm fmt` exited 1 — nothing committed; `build` judges the agent's commit as it stands `` plus `runCommand`'s tail |
| succeeds, but the commit is refused | `passed` | absent | restored to `HEAD` | the `notCommitted` reason |

Restoring the tree after a failure is the second trap. `build` runs its commands in this same worktree (`ActionContext.cwd`). A formatter that died halfway leaves edits that nobody committed. `build` would then judge files that `merge` will never land, and the green result would be a claim about the wrong tree. The restore is `git reset --hard HEAD` plus `git clean -fd`. Leave out `-x`, so ignored files such as `node_modules` survive. Put the restore in the commit dep (for example a `discard()` beside `commit()`), not in the action.

The note reaches the log as the `StepPassed` evidence for this action. The `StepPassed` event with `step: "implement"` and `action: "<name>"` is what proves a failure was absorbed rather than skipped. Unit tests can assert on it directly.

### Ordering

`implement: [run, agent]` is legal, and it is not refused. A `run` written before the agent formats the base, finds nothing, and returns no head. Only a `run` written after the agent gets the agent's work. That difference belongs in `runPlugin`'s comment, not in a resolve-time refusal like `file:`'s. A `file:` first has nothing to keep and does nothing; a `run:` first still runs.

### Fix rounds

There is nothing to build for them. `runPass` resolves `actionsAt(step, …)` on every visit (`recipe.ts:128-130`), and a route back visits `implement` again (`pass.ts:504`). The test should assert two `StepPassed` events for the `run` action, one in each `implement` visit, and that the second `build` sees the second fix-up commit as its `onSha`.

### Tests (unit, with `one-pass.ts` fakes)

- **`step-matrix.test.ts`:** the `implement` × `run` cell becomes *accepted ⇒ runs*. Every `from-recipe.ts` call the matrix makes needs `commit` in its deps, or the new refusal fires.
- **Changed-file case:** a fake `commit` returns a sha, and `build`'s context has `onSha` equal to that sha.
- **Nothing-changed case:** the fake returns `nothing`, and `build`'s `onSha` is the agent's sha.
- **Fix round:** the action runs after each agent run.
- **Failure:** a command that fails gives `implement` the ending `passed`, `discard` is called, `commit` is not, and the evidence carries the note. Give the action an injectable command runner so this test spawns no process; `runCommand` spawns one, and 0060 §1 makes a spawn integration.

The real `git` behaviour of the commit dep (the clean-tree check and the restore) can only be tested with a git binary, so that test is integration. It is out of reach inside a pass. The unit tests above stand in for it at the seam.

### Not in scope

- Opening `run` at `review` (`recipe.ts:136-141`).
- The daemon restart and the recipe edit. Those are the operator's, after the merge.
