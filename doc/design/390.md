# Design: a `run` action at `implement` that commits what it changed (#390)

## The shape

There are four parts. Only the first one is in the ticket's **Fix** row.

1. **Legality.** Add `implement: notBuiltYet` to `runPlugin.at` (`packages/recipe/src/recipe.ts:143-148`), and add a paragraph to the doc comment above it.
2. **The action.** In `actionsFromRecipe`, a `run` at `implement` gets a different action from a `run` anywhere else. Its step-dependent branch goes beside the `agent:` one, which already branches on `step === 'implement'` at `packages/actions/src/from-recipe.ts:229-300`.
   - The new action wraps `createProcessAction` (`process-action.ts`) and is handed a port. Call the file `packages/actions/src/kept-run-action.ts`, or something like it.
   - The port's shape follows `FileActionDeps.keep` (`file-action.ts:131`) and `WorkActionDeps`.
   - The port is a new optional field on `ActionDeps`. When it is absent, `ActionUnavailableError` refuses the action by name, the way `work` is refused (`from-recipe.ts`, *"no dispatch was supplied to actionsFromRecipe"*). It must never quietly fall back to a plain process action, because that is a `run` that formats and commits nothing.
3. **The port.** The git work lives in a module of its own, `packages/conductor/src/…-port.ts`, which takes a `git` function. It is not a closure inside `conduct.ts`. The precedent is `file-port.ts`: the logic was lifted out *"so that a test can hold it"* (#303). `conduct.ts` builds the port from `gitAsked` and `recordDiff` and passes it in `stepDeps`.
4. **The run's head.** When the port commits, it reports the new head. Nothing in `pass.ts` changes: `headFrom` (`pass.ts:1831`) takes *the last result that carried a `head`*. So when the run committed, `onSha` advances to the run's commit, and when it committed nothing, it stays at the agent's.

A route back to `implement` reruns the whole list through `runActionPipeline` (`pass.ts:504`, `runStep`), so the `run` after the agent comes back every fix round without anything being added. If the agent asks a question or leaves no receipt, the pipeline *"stops at the first failure"* (`action.ts:572`). In that case the `run` does not run, which is correct.

## The decision the ticket leaves open: what a failure does

Right now, a `failed` verdict at a step that may not refuse becomes `did-not-finish` (`pass.ts:1793-1801`, *"no fix round is spent at a step the workflow does not let refuse … and it does not reach the router"*). That would end the pass. A red `pnpm fmt` would stand down a ticket whose agent run was already paid for. That is the trap the ticket points at, arriving by a different route.

So **the wrapper never returns `failed`**. If the command exits non-zero or times out (`runCommand` reports both as `ok: false`), or if the commit itself is refused, the wrapper:

- **puts the tracked files back to `HEAD`** (`git reset --hard HEAD`). It does not run `git clean`; the next section explains why.
- **commits nothing**, and returns no `head`.
- **returns `passed`, with the evidence leading with the failure.** For example: *"`pnpm fmt` exited 1 — nothing committed, the tree is back at `abc1234`; `build` judges the agent's commit as it stands"*, followed by the command's output tail.

The note lands on the log as `StepPassed` with `step: implement`, `action: <name>`, and the sentence in `evidence`. That event and field are what settle *did the formatter run, and did it fail* for a given pass.

**Why the reset is necessary.** The `build` step runs its commands in `context.cwd`, which is the worktree, not the commit. Suppose a formatter fails halfway and leaves its edits. `build`'s `pnpm fmt:check` would then pass on a dirty tree, while what lands is the unformatted commit. That is the exact gap this ticket closes, reopened. After the reset, `build` judges `onSha`.

## What gets staged, and the trap in it

The ticket's precedent stages one path (`conduct.ts`'s `keep`: `git add -f -- <path>`, then `commit --only`). A formatter can touch any file, so this port stages everything: `git add -A`.

That is unsafe as written. **The worktree holds the planted env file.** `provisionWorktree` writes it at `recipe.env.plantAt` with mode 0600 (`packages/repo/src/worktree.ts:181-183`), and nothing adds it to `.git/info/exclude`. In a managed repository whose `.gitignore` does not cover it, `git add -A` would commit the secrets and the merge lane would land them.

So the port must exclude it by pathspec: `git add -A -- . ':(exclude)<plantAt>'`. Write a test that names this case.

The same file is why the failure path does not run `git clean`: it would delete the planted env file whenever the env file is untracked and not ignored. Untracked files a failed command left behind therefore stay. Say so in the doc comment.

**Leftover changes the agent did not commit get committed with the formatter's.** The port cannot tell them apart from the formatter's edits. This is the right outcome: `build` already judges them, because it runs in the worktree, so committing them makes the tree that was judged and the tree that lands the same tree.

The order of the git commands is `keep`'s, for `keep`'s reason (`conduct.ts:2018-2026`): stage, then `git diff --cached --quiet`. A clean answer from that check means *nothing changed*, so the port makes no commit and returns no head. Only a non-empty diff is committed. After that comes `rev-parse HEAD`.

The commit message names the action, in the style of `docs(design): the shape for #N` (`conduct.ts:2056`). For example: `chore(implement): <action name> for #<issue>`.

## The trap the ticket does not name: the run's head has to be on the run's stream

`RunState.headSha` is set only from the agent's own events: `RunProducedDiff` and `RunProposedCompletion` (`packages/domain/src/run.ts:236-252`). Those are appended at `conduct.ts:2662-2677`, using the agent's commit. Then:

```ts
export function stepsOn(state: RunState): StepState[] {
  if (state.headSha === null) return []
  return Object.values(state.steps).filter((g) => g.onSha === state.headSha)
}
```

(`run.ts:182-185`)

If the formatter commits, every verdict at `build` and `review` is stamped with the formatter's sha. `stepsOn` then filters all of them out. This is #253's failure, which `pass.ts:1046-1049` describes: *"the board shows a change with no build and no review — while `PassResult.steps` says ten steps passed."*

So when the port commits, it also calls `recordDiff(branch, head)` and appends `RunProposedCompletion { headSha: head }`, exactly as the agent's dispatch does. The rest of the system follows that head:

- `attempts.ts:203` and `discuss.ts:156` read `RunProducedDiff`, so the counts and the next attempt's brief follow the new head.
- The receipt check is unaffected. It compares the agent's `HEAD` against `startedAt` at dispatch (`conduct.ts:2663-2668`), and in a fix round `startedAt` is the formatter's previous commit. A fix round that commits nothing is still stopped with *"the agent produced no commits"*.

The events that settle this are `RunProposedCompletion.headSha` on the run's stream, which should equal the `onSha` on the `StepPassed` event for `build`.

## Tests, and which half each one is in

A `run:` spawns a real process (`command.ts:382`). By 0060 §1, a pass that actually runs `pnpm fmt` is integration, and no unit test in `conductor/unit` spawns one today. So the unit-level claims are split across three seams, none of which spawns a process.

- **The action** (`packages/actions/unit/`): give the wrapper a fake inner action and a fake port.
  - A passing inner action plus a port that commits gives `passed`, with `head` set.
  - A passing inner action plus a port with nothing to commit gives `passed`, with no `head` key.
  - A failing inner action gives `passed`, with the failure first in the evidence, the port's restore called, and its commit not called.
- **The port** (`packages/conductor/unit/`): give it a fake `git` that records its arguments, the way `conduct-a-whole-pass.test.ts:587` fakes `ports.repo.git`. Check that:
  - the `:(exclude)` pathspec carries the `plantAt` path;
  - nothing is committed when the cached diff is clean;
  - the reset happens on failure, with no `clean`;
  - the commit message names the action.
- **The pass:** use `runPass` with `actionsAt` replaced, as `unit/a-locator-the-core-did-not-write.test.ts` does. Give `implement` a fake agent and a fake run that reports a head.
  - `build`'s context `onSha` is the run's head, not the agent's.
  - In a pass with a fix round, the run is called after each agent run.
- **The step matrix:** in `step-matrix.test.ts`, the `implement` × `run` cell moves to *accepted ⇒ runs*. Update its counts, and the *which steps `run:` serves* message text that cell asserts.

The two `RunProposedCompletion` and `RunProducedDiff` appends from `conduct.ts` are reached only by a whole pass that spawns the command, so they are verified only after the merge, by the integration half (T11). The claim that stands in for them at unit level is the port test: the port calls a `recordDiff` and an append handed to it, and it calls them with the head it committed. Have the port take both as parameters rather than closing over them.

## What not to do

- Do not open `run` at `review` (`recipe.ts:136-141`).
- Do not add `implement` to `REFUSING_STEPS`. The wrapper's `passed` is the answer to the ticket's **Watch out** row, and making the step able to refuse is not.
- Do not refuse `[run, agent]` (a `run` written before the agent). It commits before the dispatch, and the receipt is measured from the dispatch, so nothing breaks.
