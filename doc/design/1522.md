# #1522: how the machine list is built

## Where each piece goes

**`packages/setup/src/machine-list.ts` (new)** holds `SetupQuestion`, `runSetupList`, `machineQuestions` and the two file writers. `packages/setup/src/index.ts` re-exports it.

**`apps/cli/src/machine-askers.ts` (new)** holds the `Record<MachineQuestionId, Asker>` and nothing else.

The `effect-ratchet` baseline for both packages is `{ "async": 0, "run": 0 }` (`packages/domain/unit/effect-ratchet.baseline.json:2`, `:11`). So:
- every descriptor member that does IO returns an `Effect`;
- the asker type is `(q: DecidedQuestion) => Effect<AskerAnswer, unknown>`;
- nothing new is written as `async`.

### The descriptors take their IO as ports

`@lingtai/setup` has no database probe, no `gh`, and no `GET /app`. Today those are `InitWorld` seams (`init.ts:1013` `world.database`, `init.ts:441` `world.app()`, `github-auth.ts:33` `ghStatus`). So the list is a constructor over ports:

```ts
machineQuestions(ports: MachinePorts, opts: { githubRequired: boolean }): readonly SetupQuestion[]
```

`MachinePorts` holds:
- `env`;
- `machine: MachineText` (it already lives in `packages/setup/src/claude-token.ts:22`);
- `path`;
- `database(url)`, `ghStatus()` and `app()`;
- `recipes()`: every registered project's resolved recipe.

`apps/cli` builds the ports from `InitWorld`, and the board builds its own later. Calling the constructor twice is not a copy of the list. `add` calls it with `githubRequired: true` and picks entries by id.

### Every write re-reads the file

Move `writeGithubAuth` (`github-auth.ts:54-65`) into `@lingtai/setup`, widened to `'gh' | 'app' | 'none'`, and add `writeDayCeiling` beside it on the same pattern: read, `parseDocument`, refuse a non-map, `setIn`/`deleteIn`, write.

The store's write is the `config.setIn … world.machine.write` tail of `chooseStore` (`init.ts:1152-1173`). It moves into the store descriptor's `write` and re-reads the file the same way. It must stop writing through the `config` Document that was read at the start (`init.ts:392`). Today that is safe only because the store is the first write. Under a generic runner it would be stale.

## What the runner does

The order for each descriptor, and what each path writes:

1. **Read what is in force.** Call `inForce`, which returns `{ value, from: 'environment' | 'file' } | { malformed: string, from } | null`.
   - **The environment supplies a value:** nothing is asked or written, and the row says *from the environment*.
   - **A flag that differs from an environment value is refused by name.** This generalises `exportedUrlRefusal` (`init.ts:1008-1012`) to `LINGTAI_GITHUB_AUTH` and `LINGTAI_LIMITS_DAY_USD`. A flag equal to it passes and writes nothing.
2. **Decide the default.** It is the in-force value if there is one, else `systemDefault`.
3. **Get the answer.**
   - **A flag:** the flag is the answer, checked once.
   - **`--defaults`, or no terminal:** the default is the answer. The runner calls `validate(default)` itself and never calls the asker. A descriptor with no default is refused by name, naming its flag (0121 §9).
   - **Otherwise:** the asker is called with `{ default, kept, why }`.
4. **Write.** Call `write(answer, inForce)`. The runner records `{ id, before, after, wrote }`.

**The default is checked too.** The store's `validate` is what connects to Postgres (`init.ts:1135-1142`), so a Postgres URL taken as the default is still checked. That is what `acceptingDefaults` gets today, because its `''` answer goes through `validate`.

**`kept` is built by the runner from what earlier entries wrote**, and handed to each asker. It replaces the one-off `storeKept` (`init.ts:422-429`). The Ctrl+C sentence then names every value already written, not only the store.

**The terminal signal.** No terminal is `input.interactive === false`. Add `interactive` to `InitWorld`: the live value is the TTY test now inlined at `init.ts:660`, and the fake world defaults to `true`.

Do not infer "no terminal" from `ask` returning `null`. The test harness returns `null` when its answers run out (`apps/cli/unit/init.test.ts:157`). Reading that as headless would let a test that is missing an answer pass silently, which the ticket forbids.

### A malformed value in the file

The ticket decides only an *unreadable* file. Here:
- **A malformed value in a readable file** (`github.auth: foo`, `limits.day_usd: 0` written by hand): print the fault, then ask with the system default, so the answer repairs the file. This follows the store's own precedent (`init.ts:1070-1075`: *"The other two are a file being repaired, and what was wrong with it is said before asking again"*). It replaces the up-front refusal of `github.auth` at `init.ts:435-436`, which this ticket deletes anyway.
- **A malformed exported variable:** refused by name. `init` cannot repair the environment.

### The on-demand token

`needed(ctx: { draft: Recipe | null })` returning false makes the runner put the descriptor in `result.deferred`. It does not count as skipped.

`init` and `add` call `runSetupList(result.deferred, input, { draft })` once their project path has its final recipe. These are today's two call sites: `init.ts:651-663`, and `add-github.ts:665-672`, which already computes `final` from `previewSetup`. A descriptor is asked at most once per run: if it was asked at its place, it is not re-evaluated at the end.

`needed` treats a registered recipe that cannot be read as not needing the token. Refusing it is the project path's job (0125 §6).

## The four entries

### The store

The descriptor wraps `chooseStore`'s question unchanged.
- Its `inForce` is `storeChoice` plus the connection check (`init.ts:1044-1066`).
- The exported-Postgres case (`init.ts:1001-1022`) becomes `from: 'environment'`. `inForce` still connects, and refuses by name if the database does not answer, as today.
- The flag pre-checks (`init.ts:977-998`, `:1029-1034`) stay in the CLI asker as flag parsing.
- `--defaults` at `init.ts:1116` goes: the runner now decides.

**The inherited `database.url` with no `store`** (`init.ts:1084-1102`) becomes a migration step before the list, beside `machineRuntimeRefusal` (`init.ts:403-404`). It is verified and recorded once. The store is then in force and is asked about like any other run. This is one more question on that run than today, and it is what "asked from the top on every run" means.

### GitHub

Delete the `elected !== null` branch of `askGithubAuthEffect` (`github-auth.ts:93-111`). `set ?? appConfigured` becomes the default.

- **`GithubAuthAnswer` gains `{ auth: 'none' }`**, and `none` is offered in both prompt shapes (`github-auth.ts:127-160`).
- **`electGithubAuth` reads `none`.** Teach `packages/env/src/index.ts:1623-1624` to return `{ kind: null, none: source }` for it. Callers keep treating `kind: null` as no GitHub, and `githubAuth()`'s throw (`:1659`) can say *github.auth is none* rather than *names no github.auth*.
- **A written `none` beats a configured `app_id`.** `auth` is a written choice and is not part of the App election (`:1605`).
- **`inForce` makes the App check only when the elected value is not `gh`** (0114 §1). It refuses a configured App that does not answer, by today's sentence (`init.ts:442-447`). The `AppCheck` it fetched is handed to `runGithubBranch` as `knownApp` (`first-project.ts:1415`, `:1464`), so `GET /app` is still made once per run.

**`app` with no App is not written.** Its `write` returns `{ pending: true }` and writes nothing. `runSetupList`'s result for `github` carries `pending`.

`runGithubBranch` stops asking (`first-project.ts:1463-1466`) and takes `decided` from the list's result. The App step and its deferred `writeAuth('app')` stay where they are (`first-project.ts:1543-1574`), so they behave as on a first run.

A pending `app` on an `init` whose project path is local has no App step to reach. Write nothing and print one line: `github.auth stays unwritten until a GitHub App exists — run lingtai init --project github`. Do not start the board for it.

Delete `askProjectKind`'s `--github-auth` refusal (`first-project.ts:389-395`).

**`githubRequired: true` (add only):**
- `validate` refuses `none` by name.
- The entry is run only when the in-force value is `null` or `none`.
- `add-github.ts:338-366` collapses into that one call: the `authFlag` pre-reads and the `deps.interactive()` refusal go.
- Headless with no flag: the runner's default is `gh` where the login is ready, else `none`. `none` is then refused, naming `--github-auth`. `add` therefore refuses exactly where it does today, and accepts a ready `gh`.

### The daily ceiling

`systemDefault: '100'`. `validate` accepts `/^\$?\d+(\.\d+)?$/` with the value above 0, or `none`, and refuses `0` by name.

**`write` checks the value again with the same predicate as `machineDayCeiling`** (`Number.isFinite(n) && n > 0`, `packages/env/src/index.ts:1078`) and refuses to write if it fails. That second check is the Watch out row's guarantee, independent of the asker. It is written as a YAML number, never a string, because `Config.Number` reads it.

`none` deletes `limits.day_usd`, and `limits` too if that leaves it empty. On a fresh machine that writes nothing, so the next run offers 100 again and Enter writes it. That is the consequence of `none` being an absence. The ticket rules out a written `none` here, because `machineDayCeiling`'s reading does not change. Say so in the asker's `why` line, so it does not read as a bug.

### The Claude Code token

Rewrite `obtainClaudeToken`'s two bare `world.ask` calls (`claude-token.ts:142`, `:154`) as `questionEffect`.

| | choices | default |
|---|---|---|
| token set | `keep`, `run` | `keep` |
| no token | `run`, `skip` | `skip` |

The flag takes only `keep|skip`, because `run` needs a terminal and a browser.
- `--claude-token keep` with no token set is refused by name.
- `--claude-token skip` with a token set writes nothing and prints nothing (it is `keep`).
- A token the environment supplies is `from: 'environment'` (`claudeTokenState`'s `environment`).

`askClaudeTokenForRecipe` (`claude-token.ts:191`) is retired from both call sites. `claudeTokenCommand` (`:215`) stays as it is.

## Tests

Everything here is reachable at the unit level with the fake world. Nothing needs `pnpm test:integration`.

- **Every fresh-machine `init` test now writes `github.auth: none`.** The fake world's `ghStatus` defaults to `missing` (`apps/cli/unit/init.test.ts:169`), so the GitHub default is `none`, and taking a system default for a key that was never written writes it.
- **Tests that pin `config.yml` text change too.** They gain `github.auth: none` and `limits: { day_usd: 100 }`. `LOCAL_ARGS` (`init.test.ts:234`) carries `--defaults`, so it answers both without a new answer in the list. Fix any other test by adding the answer or the flag, never by skipping the question.
- **The golden.** Regenerate `init-golden.fixture.json` in this diff, and say so in the commit (`init-golden.test.ts:10-12`).
- **`runSetupList` gets its own unit test in `packages/setup/unit/`**, over an in-memory `MachineText`. Cover:
  - equal answer writes nothing;
  - default for a key never written writes it;
  - environment value: not asked, not written;
  - a differing flag refused;
  - headless takes the default;
  - `deferred` re-evaluated once.

  These are the runner's claims. The `init` tests are then about passing answers through (0125 Consequences: *"an input's test is that it passes answers through"*).
- **Docs.** `config.example.yml:101-104` gains *init asks this, default 100*.

No accepted ADR is contradicted. 0125 §9 is the decision being built. Its *Not built yet* note (*"`@lingtai/setup` does not exist"*) is already stale, and this ticket leaves it alone.
