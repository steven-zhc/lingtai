# #626: one parser, and `lingtai.ts` becomes a door rather than a dispatcher

## What is left to delete

By the time this ticket runs, every command is already `@effect/cli`'s. `MIGRATED_COMMANDS` (`apps/cli/src/migrated.ts:9-40`) names all of them, and `cli.ts:1080-1111` has a subcommand for each. What is left of the "hand parser" is three things:

1. **The switch in `apps/cli/src/lingtai.ts:17-100`.** Its cases now do only one of two things. Some forward to `runCli` (`board` at `:44-45`, and the seven daemon commands at `:52-60`). The rest refuse with *"runs from the entry"* (`:64-93`). Its header (`:5-7`) still says *"Deliberately hand-rolled argument parsing"*. 0121's Consequences say that comment *"is deleted when this is built, not edited"* (`doc/decisions/0121-the-cli-output-and-input-contract.md:159-160`).
2. **The fall-through.** `routeOf` returns `'lingtai'` for anything that is not a command and not help (`migrated.ts:54`). `entry.ts:46-47` answers that by importing `lingtai.ts`. Today the only thing that reaches it is an unknown word, plus `--version` (`unit/migrated.test.ts`: `[['--version'], 'lingtai']`), and `lingtai.ts:21-33` answers it with `unknown command "…"` and the root help, exit 2.
3. **`parseFlags` in `apps/cli/src/add.ts:48`.** It has no caller left. `rg 'parseFlags\('` finds only the definition. Delete it. Then fix the three comments that still cite it: `restart.ts:140`, `first-project.ts:160` and `setup-build.ts:275`.

**`parseRestartArgs` (`restart.ts:147`) is not a second parser, so leave it.** `runCli` calls it at `cli.ts:1254` before `@effect/cli` parses. It does that only to keep restart's refusal sentences, which #622's design froze (`doc/design/622.md`, *"Parsing traps"*). The arguments still go through `@effect/cli` afterwards. Write the new test so that it does not trip on this function.

## `lingtai.ts` stays as a file, but holds nothing

**Do not delete the file.** Every installed supervisor runs it by path:
- the launchd plist: `service.ts:308`, `[join(inputs.root, 'apps/cli/src/lingtai.ts'), ...job.argv]`
- systemd: `service.ts:406`, `ExecStart=…lingtai.ts…`
- the keeper check: `service.ts:759`, `const entry = join(root, 'apps/cli/src/lingtai.ts')`, which refuses a plist that does not name it

`integration/service.test.ts:244,257,1543,1560` pins those paths. Renaming the file would orphan every unit already on disk, with the respawn loop #187 describes.

**The decision: `lingtai.ts` becomes `import './entry.ts'` plus its header, and nothing else.** That makes it one parser behind one door, where today it is two doors. `entry.ts` reads `process.argv.slice(2)` (`entry.ts:24`), which is the same argv whichever of the two files node was started with. A supervisor's `lingtai.ts daemon` and `lingtai.ts board start --no-open` then go through `routeOf` to `runCli`, exactly as `pnpm lingtai daemon` does. The SEA bundles `entry.ts` only (`apps/release/src/build.ts:157`), so the binary does not change. The header should say why the file exists (a supervisor's unit names it), and nothing about parsing.

**Move the rejection handler into `entry.ts`.** That is `lingtai.ts:102-127`, the *"Every ending is a sentence, not a stack trace"* block, comment and all. The `.then` chain at `entry.ts:30-43` has no rejection arm. `runCli` catches whatever a handler throws (`guarded`, `cli.ts:547-553`), but an import that fails, or a throw before the parse, would surface as an unhandled rejection. Keep the CJS no-top-level-`await` reason in that comment, because it still holds for `entry.ts`.

## The unknown command keeps its sentence

`Route` becomes `'effect' | 'help' | 'unknown'`, and `'lingtai'` goes. Do not send a non-command to `@effect/cli`:
- `--version` would get `@effect/cli`'s built-in version answer.
- A bad word would get its own error format.

Both are changes nobody asked for. `migrated.ts:5-7` already warns about exactly this: *"it would add `--version`, `--help` and `--wizard` to commands that have their own answer"*.

Put an `unknownCommand(argv)` in `help.ts`, which already holds `rootHelp` and has no library imports. It writes the same sentence `lingtai.ts:32` writes, `unknown command "${asked}"\n\n${rootHelp()}`, to stderr and returns 2. `entry.ts` calls it for `'unknown'`. `helpCommand` keeps its own `!isCommand` branch (`help.ts:57-60`) for `lingtai help bogus`.

**Rename `migrated.ts`'s list into the definitions.** Now that every command is migrated, `routeOf` should ask `isCommand` (`commands.ts:544`) instead of keeping `MIGRATED_COMMANDS`. A second list of names is exactly where a new command could be defined and still not routed. Keep the file and `routeOf` where they are: `entry.ts` and two tests import them. Delete the constant, and fix the comments that name it (`cli.ts:3`, `migrated.ts:1-8`). Then:
- `unit/help.test.ts:46-56` loses its `'init'`/`'lingtai'` branches: every name routes `'effect'`.
- `unit/migrated.test.ts`'s `--version` row becomes `'unknown'`. Add a row `[['bogus'], 'unknown']`.

## The test that there is no second parser

Write a new unit file, `apps/cli/unit/one-parser.test.ts`. It replaces the two tests that read `lingtai.ts`'s `case` labels from source:
- `unit/lingtai-entry-keeps.test.ts` (the whole file)
- `unit/board-cli.test.ts:101-114`

Both break the moment the switch is gone. What they were protecting, *the supervisor's argv still reaches the parser*, becomes behaviour that a test can check:

- `routeOf(DAEMON_JOB.argv)` and `routeOf(BOARD_JOB.argv)` are `'effect'` (both are exported from `service.ts`).
- The source of `lingtai.ts`, with comments stripped, is exactly one `import './entry.ts'`. Reading the source is still the right method here, because running the file would start a daemon. The existing test says so: *"Read structurally — running it would start a daemon"*, `lingtai-entry-keeps.test.ts:4`.
- **The set of `COMMANDS` names equals the set of `@effect/cli`'s top-level subcommands.** Export `root` from `cli.ts`, or a `ROOT_NAMES` derived from it, and read it with `Command.getSubcommands`. `@effect/cli`'s `Command.d.ts:169` declares it as returning `HashMap<string, Descriptor.Command<unknown>>`; check that it yields the children's names. Combined with `routeOf` using `isCommand`, this is what *"a test fails if a command bypasses `@effect/cli`"* means. A definition with no subcommand fails, a subcommand with no definition fails, and there is no other route left to bypass through.
- No file under `apps/cli/src` except `cli.ts` and `restart.ts` reads `argv[` past the command word for dispatch. **Do not write this one as a grep.** It is noisy, and the set-equality above already carries the claim. It is listed only so that you skip it on purpose.

All of this is unit-level: no process and no filesystem beyond reading a source file, and the existing tests already do that. `HOME=/nonexistent pnpm test` covers it.

**What only the integration half sees:** `integration/service.test.ts:1187` spawns `lingtai.ts service status` for real. Under this shape it now goes through `entry.ts`. It should pass unchanged, but nothing in the pass can show that. The `routeOf(DAEMON_JOB.argv)` row above is the unit-level claim that stands in for it.
