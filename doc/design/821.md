# Design note — #821, one verdict ladder

The ticket gives the cells, the signature and the deletions. This note covers what it leaves open: where each piece goes, how `stepStateOf` keeps its evidence once the verdict comes from elsewhere, and two names that look like this change's but are not.

## Where it goes

- **`Reached` and `isReached` go in `packages/domain/src/action.ts`, beside `NotReached` (`action.ts:84-85`).** They describe actions, not verdicts, and `action.ts` is already re-exported from `index.ts`.
- **`verdictOf` goes in `packages/domain/src/run.ts`, beside `StepVerdict` (`run.ts:42-50`).** `read-model.ts` then imports `verdictOf` and `StepVerdict` from `./run.ts`.
  - This creates no import cycle: `run.ts` imports only `./action.ts`, `./envelope.ts` and `./events.ts` (`run.ts:18-20`).
  - `read-model.ts` does not import `run.ts` today (`read-model.ts:14-23`), so this is a new edge, and it points the right way.
  - Delete `read-model.ts`'s own `function verdictOf(action: Action): string` (`:158`) outright. `index.ts` does `export *` from both modules, and its typed `string` return is what let `pending` exist.
- `cardFactOf` (`read-model.ts:311`) and `StepEnded` in `applyRun` (`run.ts:393`) replace their inline `_tag !== 'NotReached'` checks with `isReached`. The type then flows into `verdictOf` with no cast. Any other reader that filters `NotReached` before reaching a ladder does the same. `boardStepEndedOf` takes `Reached`.

## `stepStateOf` after the merge

`stepStateOf` (`run.ts:197-302`) returns a whole `StepState`, not just a verdict. Each arm also chooses `evidence` and `findings`. Once the verdict comes from `verdictOf`, do not rebuild a second per-cell switch to choose evidence. That would be the second ladder again under another name. Derive evidence and findings from the result:

- **`findings`**: `assessment.findings` when `yields === 'verdict'` and the result is `Completed`. Otherwise `[]`. This matches every arm today (`run.ts:203-207`, all others `[]`).
- **`evidence`**:
  - `null` when the verdict is `waived`. Every `Waived` arm does this today.
  - Otherwise the action's question if it has one: commit `Completed.question` (`run.ts:224`), design `Asked.question` (`:242`), or signoff `Completed.requested.question` (`:260`).
  - Otherwise `action.evidence`.

  A small `questionOf(action: Reached): string | null` is fine. It maps a result to a string, not to a verdict, so it does not count against the *no other function maps an action's result to a verdict string* rule in Done when.

Check this with the existing `RunState` tests. Only the two cells the ticket moves (null-head commit, worktree `NotDone`) may change. If any evidence value moves, the derivation is wrong, not the test.

## `boardEndingOf`

Use `switch (verdictOf(action))` over the six remaining `StepVerdict` values, with `failed → 'Failed'` as its own case and no `default` (`read-model.ts:492-507`).

The `unreadable` flag in `boardStepEndedOf` (`:521`) keys on `yields === 'verdict' && AnswerUnreadable` and stays as it is. The design `AnswerUnreadable` cell moving from `DidNotFinish` to `Failed` only moves its text from `detail` to `evidence` (`:517-518`), which is the change the ticket expects.

## Two names that are not this ticket's

- **The rail's `'pending'` stays.** `apps/board/src/lib/progress.ts:78-80`'s `StepState` uses `pending` for a step nothing has reached yet (`progress.ts:348`, `:638`; `rail.tsx:59`, `:396`). Change only the literal at `progress.ts:568` to `'asked'`. Removing `pending` from that type or from the rail's tone map breaks unstarted steps.
- **`apps/board/src/lib/task.ts:119` declares its own `interface StepVerdict`**, a row shape and not the domain union. It is unrelated, and `pnpm typecheck` will not flag it. Leave it alone. At `task.ts:1397`, `setStep` takes `state: string` (`:1299`), so the type checker will not catch a wrong word there either. The board test is the only check on that literal.

## Tests

- Put the D1 cell tests in one new file in `packages/domain/unit/`, for example `verdict-ladder.test.ts`. For each history named in the ticket, fold it through `applyRun` and also through `cardFactOf` and `boardFactOf`, and assert that all three give the same word. That three-way agreement is the claim this ticket makes. One `verdictOf` call per cell would pass even with two ladders still in place.
- For the `refusingOn` test (`packages/conductor/unit/resolve-wait.test.ts`, beside `:1216`), build the `RunState` by folding `histories.run.commitCompletedNoHead`, not by writing a `steps` record by hand. A hand-written record would pass on the old ladder too.
- **Snapshot.** Run the rebuild test with `-u`, then read `git diff` on `task-view-rebuild.test.ts.snap`. Today the only `pending` verdict is line 37 (`"pass-pin-approval:merge:human":"pending"`). Any other changed line must be a design `AnswerUnreadable` row going `did-not-finish` → `failed`. If something else moves, stop: that is a cell outside D1. Put the list of changed lines in the commit body.

## What only the log would settle

Whether any production run actually has a null-head commit that a person approved, and so now refuses where it passed before, shows in `StepEnded.outcome.actions[]` where `yields === 'commit'`, `result._tag === 'Completed'`, `result.head === null`, followed by a `WaitResolved{Approve}` on the same ticket. The agent cannot read production `events`. The unit test above is the claim that stands in for it.

No accepted ADR is contradicted. D1 is a design document (`doc/design/one-fold-per-stream.md` §5), and 0120's *an action is typed by what it yields* is exactly the switch being kept.
