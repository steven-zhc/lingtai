## Design note: triage writes to the ticket only through the Ticket owner (#1234)

### Where it goes

- **Transitions:** `startTriageTransition` and `finishTriageTransition` go in `packages/domain/src/ticket.ts`, beside `askTransition` (`:1043`). Each has the same shape as the others there: `{ ok: true; events: ToAppend[] } | { ok: false; refusal }`.
- **Their tests:** `packages/domain/unit/ticket-transitions.test.ts`, which already holds `askTransition` and `resolveWaitTransition`.
- **Commands:** `startTriage`, `finishTriage` and `recordTriageRun` go in `packages/conductor/src/ticket/commands.ts`. They follow `askTicketEffect` (`:426-437`): read through the snapshot, decide, then `appendLost` at `state.version` (`:312-324`). A `ConcurrencyError` comes back as `{ ok: false, lost: true }` and is never thrown.
- **`triage.ts`:** keeps every loop and every log line it has today. Each `deps.store.append(…)` call and the `recordPrompt(…)` call becomes a call to one of these commands.

### The decisions the ticket leaves open

**1. The caller fixes `attempt`, and the transition never works it out.** `triage.ts:792-793` computes `attempt` once from the first read and keeps it through all five tries (`:839-890`).

- `startTriageTransition(state, { waitId, attempt, by })` refuses `already-started` when `state.waits.findLast(w => w.waitId === waitId)?.triage.started?.attempt >= attempt`.
- **Do not let the transition derive `attempt` as "started + 1".** On a retry that would turn the loser of the race into the starter of the *next* attempt, and it would dispatch a second paid agent. That is exactly what `:868-869` prevents.
- This matches today's slice scan (`:865-867`). The reducer only ever raises `triage.started` (`ticket.ts:103`: `d.attempt > (w.triage.started?.attempt ?? 0)`), so "a `TriageStarted` for this wait landed since" and "the reduce's started attempt ≥ mine" are the same condition.
- `triage.ts` maps the refusals onto today's results:
  - `already-started` → the `'another attempt was already starting'` result and the `lost the race … nothing dispatched` log line.
  - `wait-not-current` → `'wait no longer current'`.
  - `lost` → re-read `before` (`:856-857`) and try again.

**2. "Current" keeps today's leniency for an unknown wait, and both transitions use one predicate for it.** `triage.ts:783-784`:

```ts
!reduceTicket(events).waits.some((w) => w.waitId === request.waitId) || currentWait(events, request.waitId)
```

A `waitId` the reduce has never seen counts as current. Put this in the domain as one exported function that both transitions call (and `triage.ts`'s first check can call too).

- If the transition uses the stricter `lifecycle.status === 'blocked' && lifecycle.waitId === waitId` (the rule in `currentWait`, `:316-319`), it changes behaviour for the null/unknown case.
- That would break *the triage unit tests pass with only import changes* for any test that builds a stream without its `WaitStarted`.
- Add a transition test for the unknown-wait case beside the four that Done-when asks for.

**3. `finishTriage` takes an optional `ifVersion`, and only `finishInterrupted` passes it.**

- `finishInterrupted` (`:243-283`) decides on one reduce whether the attempt is `Interrupted` and `attempt >= 2`. It then appends at that same `reduced.version` (`:263`), so a conflict sends it back to decide again.
- If `finishTriage` read on its own, that decision would be made on one read and appended on another. Passing `ifVersion: reduced.version` makes a moved stream come back as `lost`, and the loop continues as it does today. This is the same device as `closeChecks`'s `ifVersion` (`ticket.ts:1067-1072`).
- The main path (`:1270-1300`) omits `ifVersion`. Today it appends at the head it has just read, which is what the command's own read does.
- In that loop, `lost` and a thrown error are both retried. `wait-not-current` returns at once, as at `:1273-1275`.
- The `callerSignal?.aborted` adjustment of `final` (`:1276`) stays in `triage.ts`, before the call.
- `WaitTriaged` needs no stricter refusal than "current". Its reduce already ignores a result for any attempt that is not the latest started one (`ticket.ts:116`), so a late `interrupted` from an older attempt is inert.

**4. `recordTriageRun` records two moments and takes a tagged input. It has no transition.**

- `RunPrompted` is appended *before* the call, so that "a crash or a kill still leaves the prompt on the log (#923)" (`:1059-1060`). `RunSpent` is appended after the call. One append carrying both would lose #923.
- Input type: `{ _tag: 'Prompted', promptVersion, runtimeVersion, prompt } | { _tag: 'Spent', outcome, runtime }`, with the stream and `for: { _tag: 'Triage', waitId }` supplied by the command.
- It is a fact about a run, not a decision about the stream, so no transition refuses it. That is the precedent `recordIssueUpdate` documents (`commands.ts:593-596`): "A fact … so no transition refuses it".
- **`Prompted`:** wraps `recordPrompt` unchanged. Per `record-prompt.ts:77-79`, "It never rejects … and it is not retried". Keep it that way.
- **`Spent`:** takes over the whole `spend` loop from `:961-1012`. That means the five tries, the `since` captured from the first read that succeeds, and the `alreadyLanded` check. It returns `string | null` exactly as `spend` does.
  - The duplicate check is only correct with a `since` that lasts across tries, so the loop and the check move together.
  - This is the opposite of `finishTriage`, whose loop stays in `triage.ts` because the ticket says so.
- Wrap the promise with `Effect.tryPromise` / `Effect.promise`. Add no `async` function, and do not raise `effect-ratchet.baseline.json`.

**5. Store types: the narrowest `Pick`, plus `SnapshotReadOptions`.**

- `finishInterrupted` holds `CatchUpTriagePorts.store: Pick<EventStore, 'read' | 'readTypes' | 'append'>` (`triage.ts:150`). It passes `deps` as the snapshot options (`:245`).
- `startTriage` and `finishTriage` should accept that `Pick` and `SnapshotReadOptions`. Do not require a full `EventStore` the way `askTicketEffect` does (`:428`). Requiring it would force changes to the test fakes, which the "import changes only" Done-when forbids.
- `recordTriageRun` needs `EventStore`, because `recordPrompt` does (`record-prompt.ts:82`). `triageWait`'s deps already provide it (`:524`).

**6. Reads stay where they are.** `triage.ts` keeps its raw `store.read` for `before`:

- `gatherEvidence` takes the envelopes (`:910`);
- the first `attempt` is computed from them.

Moving reads is 0129 §6 and out of scope. The commands do their own reads for their decisions, so the decision is always made on the state the append lands on.

### What checks it

All of it is checked at unit level:

- the four transition cases from Done-when, plus the unknown-wait case and an `ifVersion` mismatch;
- the triage unit tests, unchanged apart from imports;
- the owners count with `ticket-` emptied.

Nothing here needs `pnpm test:integration`. Done-when's own check for `triage.ts` (no `.append(` and no `recordPrompt(`) also covers the two writes that #1202's count does not see.
