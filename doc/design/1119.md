# Design: #1119, the conflict brief comes first

## The decision the ticket leaves open: key on the lane's reason, not on `from`

`from === 'merge'` does not mean "conflict" on the live path. Three kinds of refusal at `merge` buy a `fix-lines` round to `implement`:

- `MergeConflict` (`packages/domain/src/routing.ts:203`)
- `VerifyRed` (`routing.ts:199`)
- `MergeRefused`, which covers the lane's other seven reasons (`routing.ts:270-274`)

In a live lap, `sentBackTo` (`packages/conductor/src/run-attempt.ts:1950-1968`) sets `printed.step` to the step of the visit the round arrived from: `{ step: arrived.step, detail: arrived.ending.detail }` at `run-attempt.ts:1963-1966`. For all three kinds that step is `merge`. So today, a `verify-failed` or a `push-rejected` with no minor findings in the lap is already briefed as a conflict. Its output is printed under `## What conflicts` and the fixer is told to `git merge`. The ticket's rule, `on: 'conflict'` whenever `from === 'merge'`, would make that the answer every time.

The fact that tells them apart is already on the visit. `StepRefused.because` (`run-attempt.ts:340-345`) is the lane's own `RefusalReason`. The merge action sets it at `packages/actions/src/merge-action.ts:146`: `because: answer.notMerged.reason`. `run-attempt.ts:2306` keeps it: `because: becauseFrom(result) ?? 'action-refused'`. So:

1. **Carry the reason on `printed`.** `SentBack.printed` (`packages/actions/src/action.ts:483`) gains an optional `because?: string`. `sentBackTo` fills it when `arrived.ending.ending === 'refused'`. Leave it out on every other ending, so no other caller changes shape.
2. **Set it on the grant path too.** `grantCriterion`'s `MergeConflict` case (`packages/domain/src/wait.ts:434`) answers `printed: { step: 'merge', … }`. Its return type at `wait.ts:370` is `{ step: Step; detail: string }`. Add `because: 'conflict'` there, and widen that type the same way. `conduct.ts:1248` passes `criterion.printed` through unchanged. `VerifyRed`'s grant already prints `build` (`wait.ts:423`), so it never reaches the merge branch.
3. **Choose in `fixRound`.** Do this at `conduct.ts:4278-4286`, beside `fixId`:
   ```
   const conflict = from === 'merge' && again.printed?.because === 'conflict'
   ```
   - `conflict` gives `{ on: 'conflict', base, paths: said, findings }`.
   - Otherwise, if there are findings, use `findings` as today.
   - Otherwise use `output`. That puts `verify-failed` and the other seven merge reasons on `outputHalf`, which is where they belong.

   An absent `because` is not a conflict. Do not default it to one, because an unknown reason briefed as *run git merge* is the bug this ticket fixes.

Do not touch `fixId` (`conduct.ts:4291-4294`). It stays keyed on `from === 'merge'`, which the ticket says is unchanged. Rewrite the comment above it (`:4289-4290`, *"which makes `refusal.on` 'findings'"*), because that sentence stops being true. Say in the PR that non-conflict merge refusals moved from `conflictHalf` to `outputHalf`. It is a behaviour change, and it is the fix for this ticket's own *"A merge refusal that is not a conflict"* edge.

## The brief: where the findings render

`fixBriefParts`' `conflict` variant (`packages/conductor/src/fix.ts:484`) becomes:

```
{ on: 'conflict'; base: string; paths: string; findings: readonly ActionFinding[] }
```

Make `findings` required. Every constructor then has to decide, and `fixRound` is the only constructor outside the tests.

The parts are assembled at `fix.ts:540-560`: the header, then `evidence`, then the advice and declined sections, then the ticket. Put the new section **directly after `conflictHalf`'s evidence**, before `adviceSection`. Do not put it after the ticket, because the ticket asks for the conflict first and the findings after it.

Build the section from `findingsHalf(findings, action).evidence`'s finding list under the heading `## Also open from the last review`. Add one sentence saying these are context, not what counts as done. **Use `conflictHalf`'s criterion only.** `findingsHalf`'s criterion is never rendered on this path. When `findings` is empty, emit nothing at all: no heading and no blank section.

`findingsHalf` returns `evidence` as a string or as parts. Check its shape at `fix.ts:541` and spread it the same way the existing line does (`typeof evidence === 'string' ? [evidence] : evidence`). Do not re-render the findings by hand. That way `recordPrompt` references them the same way it does on the findings path.

The one wording change is in the criterion (`fix.ts:807`). *"Then the whole \`proposed\` step runs again on what you committed"* becomes *"Then \`build\` and then \`review\` run again on what you committed"*. Leave everything else in `conflictHalf` alone.

## The fake: `packages/conductor/test/one-attempt.ts`

Add the opt-in field, for example `conflicts?: { paths: string[]; baseSha: string; headSha: string }`. When it is set, `integrate` (`:808-813`) returns the lane's conflict refusal instead of `{ ok: true, … }`. Copy the exact shape from the `IntegrateResult` type that `integrate`'s port returns. Do not invent it: `mergeRefusalProposal` (`packages/domain/src/proposal.ts:312`) reads `reason` and `conflict.{paths,baseSha,headSha}` off it.

When the field is absent, the closure body must stay byte-for-byte what it is. Every conduct-level test uses this fake.

Refuse every time, not only the first time. The routing allows two conflict rounds (`CONFLICT_ROUNDS_LIMIT = 2`, `routing.ts:53`) and then waits, so the test terminates on its own. Assert on the **first** recorded fix prompt only.

Read the review's minor finding into the lap the way the existing *passing review with minors* tests do. Search the conduct-level unit tests for one that already does this, and copy it.

## Tests

- **`fix.test.ts`.** Pin the order with `indexOf`: `run git merge \`${base}\`` must come before `## Also open from the last review`. Also pin that the heading is absent when `findings: []`, and that the `build` and then `review` sentence is present. Do not pin any finding's text.
- **The conduct level.** Pin the same order in the recorded fix prompt. Add one more assertion: a `verify-failed` refusal arriving from `merge` is briefed with `outputHalf`'s ``## What `…` printed`` heading and not `## What conflicts`. That assertion is the unit-level proof of the choice above. If the fake can't produce a `verify-failed` without a second opt-in, write it as a direct test of `sentBackTo` plus the choice, not as a second fake field.

None of this adds IO. Expect `effect-ratchet.baseline.json` to stay unchanged. If it goes red, the change put an `async` where none belonged.

## What the log would settle

Whether a live conflict's `detail` is git's path list or the lane's prose is not decided by this change: `said` goes into `paths` as it does today. The field that settles it is `StepEnded.ending.detail` on the `merge` visit before `PassRouted{next: {_tag: 'FixRound', conflict: n}}`. #1067's l.116-117 suggests prose that names the file. Either way it still renders inside the `## What conflicts` fence.
