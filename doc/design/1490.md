## The four tests to add

All four go in `apps/cli/unit/recipe-flow.test.ts`. They use that file's existing helpers: `askAndWrite`, `mapFiles`, `BASE_AT`, and inside the `--defaults` describe, `runTwo` / `TWO_RUNTIMES` / `NO_TERMINAL`. There is no filesystem: the port is a `Map`, as 0060 §1 requires (file header, lines 3-9). Read the raw list with `parseDocument(text).getIn(['steps','proposed'])` and `.toJSON()`, as line 173 does. That checks what the file says rather than the schema-defaulted resolution.

1. **`--land hold` on a new recipe gives both entries.** Nothing in `apps/cli/unit` checks `steps.proposed` after a `land: 'hold'` run today. `recipe-summary.test.ts:91` passes the flag but asserts only the confirm text.
   - **Setup:** in the absent-file describe, call `askAndWrite` with `flags: { ...BASE_AT.flags, land: 'hold' }` and `mode: 'solo'`. That is already in `BASE_AT.flags`, so the team branch at `recipe-flow.ts:476` doesn't refuse.
   - **Assert** `toEqual([{ name: 'hold every attempt', human: SETUP_HOLD_TEXT }, { name: 'send findings back to the writer', judge: 'claude-code', when: 'findings' }])`.
   - **Import** `SETUP_HOLD_TEXT` from `@lingtai/recipe`. It is re-exported at `packages/recipe/src/answers.ts:24`; check that the package index exports it. Don't retype the sentence that `landing.test.ts:298` spells out.
   - **Why it matters:** this is the trap from #1490's Watch-out. If the judge were written before the landing, `landingChanges` would read a stale list and one of the two entries would be lost. Asserting both entries, in this order, is the whole point of the test.

2. **Writer `codex` gives `judge: codex`.** The existing test *"a recipe whose writer is codex keeps codex under --defaults (#727)"* (`recipe-flow.test.ts:375-383`) checks only `runtime.agent`. Next to it, run `runTwo(TWO_RUNTIMES, NO_TERMINAL, { defaults: '', mode: 'solo', agent: 'codex' })` and assert the raw list is `[{ name: 'send findings back to the writer', judge: 'codex', when: 'findings' }]`. The reviewer in that run is `claude-code`. Optionally assert that no entry names it as judge: the judge follows the writer, never the reviewer.

3. **An existing file gets no judge.** Extend *"is still written one answer at a time …"* (`recipe-flow.test.ts:230-262`), or add a test beside it on the same `FIXTURE`. That fixture has `steps.implement` and `review: []` and no `proposed:` key (lines 209-228). Assert that `parseDocument(text).getIn(['steps','proposed'])` is `undefined`. It stays undefined because `askLanding` on the default "land" path writes only `holdRemovalChanges`, which is empty where there is no `human:` (`answers.ts:105-107`). Add a second check in the codex test: the `again` run, which re-runs on the file the first run wrote, still holds exactly one findings judge. On that path `absent` is false, so `recipe-flow.ts:493` is never reached.

4. **`resolveSource` accepts the written file.** `resolveSource` throws `RecipeInvalidError` on a refusal (`packages/recipe/src/resolve.ts:256-266`). The absent-file test at line 139 and `runTwo` at line 336 already resolve a file that holds the judge, so this is met by implication. Make it explicit in tests 1 and 2: resolve the text and assert `resolved.steps.proposed` with `toMatchObject`. Expect `[{ judge: 'claude-code', when: 'findings' }]` in the plain case and `[{ human: … }, { judge: 'codex', when: 'findings' }]` with the hold. Use `toMatchObject`, not `toEqual`, because the resolved entries may carry fields the schema fills in.
