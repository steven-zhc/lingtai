# #1089: design note

CLI-01 has landed in this worktree. `apps/cli/src/exit.ts` exports `CommandExit`, `exitWith`, `lift`, `failed` and `orFailed`, and `status` (`cli.ts:47-58`) is the pattern to copy. Below are the decisions the ticket doesn't make, and the traps it doesn't name. Line numbers are this worktree's (`04950dbc`).

## 1. Wrap the whole handler body in `orFailed`, as `status` does. Not just the runner call.

`runCli` prints a **second**, `usage` JSON document whenever all of these hold:

- the exit is non-zero
- `--json` is on
- `handlerCode === 0`
- `!handlerExited`

The code is `cli.ts:1566`:

```ts
if (code !== 0 && json && handlerCode === 0 && !handlerExited) {
```

`handlerExited` is set only by `Effect.catchTag('CommandExit', …)` (`:1558-1561`). A defect that escapes to `Effect.catchCause(() => Effect.succeed(1))` (`:1562`) prints nothing of its own. So any path that ends non-zero without becoming a `CommandExit` breaks things under `--json`: today it is silent, and after the change it would print a stray `usage` document.

- Write each handler as `Effect.gen(function* () { …refusals…; yield* exitWith(yield* runners.x(…)) }).pipe(orFailed(command, asJson))`.
- `printedBy` already passes a `CommandExit` through untouched (`exit.ts:43-44`), so the refusals' `exitWith(2)` keep working inside the wrapper.
- An interruption is passed through rather than printed (`exit.ts:46`). That gives the ticket's *an interruption is never printed as a failure* for free.

## 2. Keep each `asJson` argument as `guarded` received it, even where it looks wrong

Today's third argument:

- **`args.json`:** `ticket list` (`:788`), `report` (`:856`), `env list` (`:947`) and `projection lag` (`:988`).
- **Default `false`:** every other call, including `backlog list` (`:870`), even though it takes `--json`.

`backlog list` works today because its runner catches its own read failure and prints with `request.json` (`:556-565`). Its handler-level `false` only matters if the import fails. Pass `orFailed('backlog', false)` at the handler and `orFailed('backlog', request.json)` inside the runner, around the read and the print only. Moving the import inside it, or "fixing" the handler to `args.json`, changes a printed line, and the ticket forbids that.

`projection lag` is the same: an inner `orFailed('projection lag', request.json)` around `projectionLagEffect()` and the print. `projectionLagEffect` has `R = never` (`packages/projector/src/projection.ts:386`, `withStoreEffect` at `choose.ts:126-129`), so a runner typed `Effect<number, unknown>` can `yield*` it directly.

A runner that fails with the inner `CommandExit` is fine: the handler's `orFailed` passes it through. `Runners`' `E` is `unknown`, so no type change is needed for that.

## 3. `envUsage` becomes an Effect, and the parent must not pass it as the handler

Make it `envUsage(json = false, command = 'env'): Effect.Effect<never, CommandExit>`. It prints exactly as now (`:935-940`), then returns `exitWith(2)`.

- **Inside a handler:** `return yield* envUsage(args.json, 'env list')`.
- **The trap:** today's parent is `Effect.sync(envUsage)` (`:979`), and `Effect.sync` calls its thunk with **no** arguments. If the parent is written as `Command.make('env', {}, envUsage)`, `@effect/cli` hands it the parsed args object as `json`. That object is truthy, so a bare `lingtai env` would print the JSON `usage` document instead of the stderr sentence. Write `() => envUsage()`.
- **What catches it:** `layout-625.test.ts:59-65` checks only `a.err` for `['env']`, and that assertion would go red.

## 4. The bare `backlog` parent exits 0 and stays a defect on a failed import

`:921-925` prints `BACKLOG_USAGE` to **stdout** with exit 0. It is not one of the ticket's bare parents that exit 2, so don't add an `exitWith(2)`. It is mostly unreachable anyway: `withBacklogVerb` (`:1464-1466`) puts `list` in front of anything that is not a verb.

Today its `Effect.promise` makes a failed import a defect, which ends 1 and prints nothing. Keep that: write `yield* lift(() => import('./backlog.ts')).pipe(Effect.orDie)`, which is CLI-01's precedent at `events` (`:68-73`, *"a failed import is a defect, which `runCli` ends as 1"*). Don't wrap it in `orFailed`, which would print where nothing prints today.

## 5. `report` has no runner

The handler is `Effect.gen`: `lift` the `import('./report.ts')`, then `lift` `runReport(…)`, then `exitWith(code)`, all piped through `orFailed('report', args.json)`. Its inner `async` callback (`:842`) disappears with `guarded`.

## 6. `attach`

`runCli` runs the program with `Effect.runPromise` (`:1552`), not `runMain`. Effect therefore installs no `SIGINT` handler of its own, so nothing races the detach listener.

Inside the live runner, put `new AbortController()` and `process.on('SIGINT', …)` in one `Effect.sync` before `lift(() => attach({ runId, signal }))`, keeping the comment at `:519-521`. Don't use `Effect.acquireRelease` or an `onInterrupt` to remove the listener. Today it is never removed, and removing it changes what a second Ctrl+C does.

## 7. The live-runner throwing test (Done when, `layout-625.test.ts:73-84`)

`layout-625.test.ts` imports `runCli` and `../src/env.ts` statically (`:6-7`), so a plain `vi.doMock` will not reach the cached module. Copy the pattern in `doctor-progress.test.ts:153-171`:

1. `vi.resetModules()`
2. `vi.doMock('../src/env.ts', async (orig) => ({ ...(await orig<typeof import('../src/env.ts')>()), envList: () => Promise.reject(new Error('unknown project "nope"')) }))`
3. A fresh `const { runCli } = await import('../src/cli.ts')`, called with **no** `env` runner.

Then:

- `capture` uses the static `runCli`. Give it an optional `runCli` parameter, or inline the spies in this one case.
- Put `vi.doUnmock('../src/env.ts')` in a `finally` or `afterEach`. `vi.restoreAllMocks()` (`:33`) does not undo a `doMock`.

## 8. Test fakes

- `recording()` in both files becomes `(request) => (seen.push(request), Effect.succeed(0))`.
- `five-commands-cli.test.ts:65` becomes `() => Effect.succeed(1)`.
- `boom` (`:113-115`) becomes `() => Effect.fail(new Error('database is down'))`.

Each file now imports `Effect` from `effect`. Nothing else in either file changes.

## What the unit half can and cannot see

Every claim here is checked by `pnpm test`, because both test files drive `runCli` in-process. One thing it cannot see: under the integration half, the real `projection lag` against a store, which `projectionLagEffect` replaces. That path stays covered by `projectionLag`'s other callers and by the contract that the promise face is `Effect.runPromise(projectionLagEffect(url))` (`projection.ts:393-395`). So the runner still calls the same function, without the face around it.
