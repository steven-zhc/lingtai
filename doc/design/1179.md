# Design note: #1179, the recipe moves back onto `StepsResolved`

Most of the change is what the ticket's Fix row says. This note covers the four places where a reasonable implementation goes wrong, and where the new test case sits. The line numbers in the ticket have drifted. Use the ones below, which are from this worktree.

## 1. Where the code is now

- **The append to delete** is `conduct.ts:4502-4510`: the `recordRecipe(store, resolved).catch(...)` block and its comment *"Before the plan that names its hash, and at version 0 (see `recordRecipe`)"*. The `StepsResolved` append right after it, `:4511-4517`, stays as it is.
- **The import to change** is `conduct.ts:288`, `import { recordRecipe, stepsResolved } from './steps-resolved.ts'`, which becomes `stepsResolved` alone.
- **`steps-resolved.ts`** loses everything below `stepsResolved` (`:25-54`). Its header says the canonical recipe *"is recorded once per hash on its own stream (0100 §14, #930)"* and must now say 0128 §4. The `recipeStream`, `ConcurrencyError` and `EventStore` imports go too, and `parsePayload` goes unless something else in the file uses it.
- **`EVENT_AT`** has `RecipeRecorded: ['claim', 'admit', 'implement']` at `events.ts:2707`, which becomes `[]`. The docstring at `:2672` says *"`RETIRED` types declare `[]`"*.
- **`RETIRED`** is at `events.ts:2794-2801`. Add `'RecipeRecorded'` to that set.

## 2. `StepsResolved.recipe` stays `.optional()` in the schema

The schema keeps `recipe: z.record(z.string(), z.unknown()).optional()` (`events.ts:1155`). The field is optional because the log holds `StepsResolved` rows written between #930 and this change that have no `recipe`. Making it required would make those rows fail to parse.

Each reader of a run's stream would then die at the first such row: the projectors stop at the first seq that fails to parse and never advance past it (`events.ts:1124-1126`). That is the same failure the v3 widening was written to avoid.

So:

- **What becomes required is the writer, not the schema.** `stepsResolved` always sets `recipe: canonicalRecipe(resolved.recipe)`.
- **There is no `schemaVer` bump and no upcaster.** The field is already in v3+ (`events.ts:1133`).
- **The field docstring changes** (`:1149-1154`). It currently says *"Absent on every event written since #930 … The body is now on `rcp-<configHash>`"*. It should say the field is present on every event written since 0128 §4. It is absent only on the rows written between #930 and this change, and for those the body is on `rcp-<configHash>`.
- **The type docstring changes too** (`:1133-1139`). It still says *"the next run's recipe is read from the base branch, as ever (0005)"*. It should say an attempt resolves from the Project's declared recipe (`loadProject`, 0128 §6), and that the record is never a source.

## 3. The `rcp-` stream mapping stays

`packages/domain/scripts/events.ts:316` maps `RecipeRecorded: ['rcp-']`. Leave that mapping alone.

The streams table marks a type `*(retired)*` using `RETIRED.has(name)` (`scripts/events.ts:404`, `:638`). So `rcp-`'s row in `doc/reference.md` keeps its one event and gains the marker, which is what the ticket's *Docs* edge asks for.

`PassRouted` is the precedent: it is retired and still maps `['pass-']` (`:328`). `OutboxDelivered: []` (`:337`) is not the model to copy here, because nothing writes those two to a stream.

Other things that stay as they are:

- the board's label at `apps/board/src/lib/history.ts:387`;
- its fixture at `apps/board/unit/history.test.ts:185`;
- `recipeStream` / `RECIPE_STREAM_PREFIX`.

`RecipeRecorded`'s docstring (`events.ts:1159-1171`) gets the retired-type shape used at `:494` and `:1850`:

- a sentence saying it was retired by 0128 §4, is still parsed and is appended never;
- a summary starting `@summary No longer written:` — for example *"the conductor recorded a recipe once under its hash; a run's `StepsResolved` carries it again."*

## 4. One commit, and check it with the conductor's own test

The ticket's Watch-out is real. An append of a retired type throws (`event-store.ts:323`), and the `.catch` at `conduct.ts:4506-4508` keeps that error as the pass's defect.

`packages/conductor/unit/what-an-event-is-written-at.test.ts` holds *appended ⊆ declared* against real passes. Once `EVENT_AT` is `[]`, that test goes red if any fixture pass still appends `RecipeRecorded`. That makes it the unit-level witness that the deletion and the retirement landed together, so run it before committing.

## 5. Rewriting `recorded-recipe.test.ts`

- **Header (`:1-14`).** Retitle it to the recipe a run ran under, carried on its own `StepsResolved` (0128 §4, after #191, 0047 and #930). It keeps three promises:
  - the recipe verifies itself;
  - it holds no secret;
  - nothing decides from a run's record, because an attempt resolves from the Project's declared recipe (0128 §4, §6).

  `projects.ts:90-95` has the same 0047-era paragraph; update it in the same change.
- **`:64-120` (verifies its hash, holds no secret).** Point these at `parsePayload('StepsResolved', stepsResolved(runId, resolved)).recipe`, and keep the `shuffled` round trip. The `recipeRecorded` import goes.
- **`:122-129`.** Invert it: `'recipe' in plan` is true. A stored plan with no `recipe` still parses (the #930-era rows). It no longer needs a "v4 event with one" case.
- **`:131-148`.** Delete the once-per-hash test. Add a case: after a `StepsResolved` append on a memory store, `store.read('rcp-…')` is empty. If something else is cheaper, appending `RecipeRecorded` to the memory store throws `RetiredEventTypeError`. Check first whether the memory store enforces `RETIRED`; the contract suite says it should.
- **`PACKAGES` (`:162`).** Add `'packages/project/src'`. The checker returns `[]` early unless the source names `StepsResolved` or `RecipeRecorded` (`:178-179`), so a package that never names them passes trivially. That is the intended answer, not a gap.

  Your own change does not trip the checker: `conduct.ts`'s `parsePayload('StepsResolved', stepsResolved(runId, resolved))` is followed by `,`, not by `.recipe`. Run the checker anyway after editing `steps-resolved.ts`.

## 6. The new case: an attempt resolves from the declared source

Drive it through `currentRecipeEffect` (`conductor/src/projects.ts:131-149`). That is the read `conduct.ts:912` makes when no `options.recipe` is given, so it is the deciding read itself. Don't call `loadProject` directly, which would only test `packages/project` again; `load-project.test.ts` already does that.

The harness already exists in `packages/conductor/unit/read-a-project-as-effects.test.ts:33-76`:

- `host: 'skip'`;
- a `Map`-backed `RecipeFiles` port, given through `Effect.provideService(ProjectFiles, files)`;
- a memory store passed as `store`.

The case:

1. **With source A at `recipePath(P, HOME)`:** `prj-` reads `['ProjectRecipeChanged']` with `by: 'file'`, and the resolved `configHash` equals `resolve(A)`'s.
2. **With an empty port:** the Effect fails with `RecipeMissingError` (from `@lingtai/recipe`), `prj-` has no events, and the port's `writes` is empty.

For the `stage: 'recipe'` half of *Done when*, don't build a full `conduct` here. The mapping from any failure of that read to `{ ok: false, stage: 'recipe' }` is `conduct.ts:908-921`, and `conduct-a-recipe-read-that-dies.test.ts` already holds it. Say so in the case's comment, citing both, rather than adding a second harness.

The behaviour this proves on production is the absence of `RecipeRecorded` on any `rcp-` stream after a post-merge daemon's first `StepsResolved`, plus that event's `data.recipe`. Neither can be read inside a pass. The unit witnesses in §4 and §5 stand in for it.
