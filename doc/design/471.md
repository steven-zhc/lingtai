# #471: the shape

## The decision the ticket leaves open: each proposal carries what its `Hold` reads

The ticket asks for two things that cannot both hold:

- the field list in **Fix**, which is ADR 0120 §2's type block (`doc/decisions/0120-a-reason-is-a-type.md:273-279`);
- the rule in **Watch out**: `holdOf(ProposedEscalated{X})` must equal today's direct `Hold` for X.

Today's direct `Hold`s read facts that the field list does not carry. All of these are in `packages/conductor/src/adapters.ts`:

| Direct `WaitReason` | What its `Hold` reads that the ADR's proposal lacks |
|---|---|
| `SetupRefused` (`:704-716`) | `step`. The `Hold` is `SetupRefused{lifts:'person'}` at `prepared` and `DidNotFinish{step}` everywhere else. |
| `CheckRefused` (`:663-670`) | `step` (`proposed` \| `merge`), carried on `CheckRed.step`. |
| `AnswerUnreadable` (`:880-899`, `answerUnreadableHold`) | `step`. It is `Routed{findings}` at `review`/`proposed`, `CheckRed` at `merge` and `DidNotFinish` at `design`. |
| `BudgetExhausted` (`:688-698`) | `detail`, because `Ceiling.detail` is a required string (`hold.ts:245`). |
| `NothingProduced` (`:647-656`) | `said: string \| null`, which feeds both `why` and `raw`. |
| `FixerDisagrees` (`:645`) | `said: string \| null`. The ADR has `said: string`. |

`fromOf` (`proposal.ts:72`) and the `offerFor` rule ("`implement` for a proposal from `implement` or any step after it") also need a step. Four of the seven can come from more than one step, according to 0120 §2's own table (`:304-310`). That contradicts the ADR's prose at `:281`: *"only `InputNeeded` can come from two, so only it carries `from`"*.

**Decision: the Watch out wins, so add the fields.** The `Hold` a person sees is the constraint the ticket calls out by name. Adding fields only extends the type, and no caller constructs these variants until #472. #472 builds each proposal from the same deciding action the direct stop reads today, so every fact is available there. Use these exact shapes:

```
SetupRefused     { from: Step; output: string }
CheckRefused     { from: 'proposed' | 'merge'; output: string }
AnswerUnreadable { from: 'design' | 'review' | 'proposed' | 'merge'; raw: string }
NothingProduced  { said: string | null }
FixerDisagrees   { said: string | null }
MergeRefused     { reason: RefusalReason.exclude(['conflict','verify-failed']); output: string }
BudgetExhausted  { from: Step; kind: CeilingKind-values; turns: number | null; costUsd: number | null; detail: string }
```

Copy the narrowed step sets from the direct `WaitReason`s in `packages/domain/src/wait.ts:115-171`. For `MergeRefused.reason`, use the same `.exclude` as `wait.ts:130`, so a `MergeRefused{conflict}` proposal cannot exist; `MergeConflict` and `VerifyRed` already cover those two. For `kind`, write out `z.enum(RUN_FAILURE_KINDS).extract(['out-of-turns','out-of-usd'])` the way `wait.ts:141` does. `proposal.ts` must not import `hold.ts`, for the same ESM-cycle reason given in `wait.ts:138-140`.

`fromOf` then answers as follows:

- `proposal.from` for the four variants that carry `from`;
- `'implement'` for `NothingProduced` and `FixerDisagrees`;
- `'merge'` for `MergeRefused`.

**Edit ADR 0120 §2 in the same change:** the type block, plus the sentence at `:281`, which should say that every variant reachable from more than one step carries `from`. CLAUDE.md says an ADR from 0100 on is edited in place, not superseded: *"A decision that changes is an edit to its topic's ADR, not a new file beside it."* Commit it as `0120: …`.

## `JudgeWhen`: seven kebab-case values

Use `setup-refused`, `check-refused`, `answer-unreadable`, `nothing-produced`, `fixer-disagrees`, `merge-refused` and `budget-exhausted`, appended to `hold.ts:58`.

Two things follow automatically:

- `Routed.when` (`hold.ts:148`) widens with the enum.
- The recipe's `when:` (`recipe.ts:1378`) starts accepting the new values. That is the intent, since it is how a recipe declares a `judge:` for these stops.

Rewrite the comment at `hold.ts:45-51`. It says a judge *"is never asked about"* `dirty-base` and the other integration reasons. ADR 0120 §2 reverses that at `:319-323`: *"a judge for `MergeRefused{dirty-base}` can rebase and retry"*.

Existing tests now run over the new values without being edited, because they iterate `JudgeWhen.options`:

- **`conductor/unit/judge.test.ts:152`** requires `stepsOnOffer` to offer `implement` for every direction except `findings` when it has non-empty evidence, and only `human` when the evidence is blank.
- **`:174`, `:481` and `:493`** iterate the enum the same way.
- **`:413`** requires `BUILT_IN_FOR`'s keys to equal the enum's options.

`stepsOnOffer` (`judge.ts:286-303`) already meets all of this with its generic non-`findings` rule. **Add no special case for the new directions there.** `offerFor` is where their candidates are decided.

## `offerFor`: one cell per variant

Use the `round()` and `restart()` helpers that already exist (`routing.ts:110-135`). `restart()` already reads `spent.restarts` against `policy.restarts`, which is the Watch out's *"counted in `restartsSpent` like any restart"* with nothing further to add. **Do not add a counter.**

Call `fix-lines` (`round('fix-lines','implement', …)`) only when the proposal's step is `implement` or later; compare `STEPS.indexOf` (`vocabulary.ts:44`). For an earlier step, leave `fix-lines` out entirely; do not exclude it. `ExcludedCandidate.because` only has `CeilingReached` and `NoCriterion`, and neither of those is true there. `BuildRed` likewise gets no restart cell today.

| Variant | Criterion (the `hasCriterion` passed to both `fix-lines` and `restart`) |
|---|---|
| `SetupRefused` | `output.trim() !== ''`; `fix-lines` only if `from` is `implement` or later |
| `CheckRefused` | `output.trim() !== ''` |
| `AnswerUnreadable` | `raw.trim() !== ''`; no `fix-lines` when `from === 'design'` |
| `NothingProduced` | `false` (the ticket says so) |
| `FixerDisagrees` | `said` is not null and is non-blank |
| `MergeRefused` | `output.trim() !== ''` |
| `BudgetExhausted` | `true`; `fix-lines` only if `from` is `implement` or later |

`hand-to-person` is already appended unconditionally (`:169`).

## `holdOf`: equal by construction

Return the direct `Hold` in `escalatedHold`, after the `InputNeeded` exception (`adapters.ts:766`) and **before** `reasonTextOf`. Factor each direct cell's literal into a small builder that takes `(run, …facts)`:

- `ceilingHold`
- `setupRefusedHold`
- `checkRedHold`
- `mergeRefusedHold`
- `declinedHold`
- `nothingProducedHold`
- the existing `answerUnreadableHold`, reshaped to take `(run, step, raw, pass)`

Then call the same builder from the direct `holdOf` case and from the escalated case. Equality then follows from the shared code, and the per-variant tests pin it.

Two consequences, both accepted:

- **`reason.because` is not folded into these seven.** None of their direct `Hold`s has a field for it, and with nothing routed, `BUILT_IN_FOR` set to `null`, and nothing declared, the only `because` that can occur is `NotAsked`, which has no text anyway (`reasonTextOf`, `:731`).
- **An escalated `BudgetExhausted` passes the proposal's own `turns`/`costUsd` through.** The direct path still writes `null` there (`:689-690`). The equality test uses `turns: null, costUsd: null` on the proposal, which is the only pair the direct path can produce.
