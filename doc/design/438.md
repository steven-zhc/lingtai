**Design: #438, the merge lane fetches into refs that only the lane uses**

## Where it goes

All of the lane's changes are in `packages/repo/src/integrate.ts`, inside `attempt`. The test is a new unit test. Nothing outside `packages/repo` needs to change. I went through every reader of the mirror's `refs/heads/<branch>` (listed below), and none of them depends on the lane writing it.

## The decision: both refs move into the lane's namespace, and the lane does not write the branch ref back

**Both refs, not only the branch.** The ticket's Want is *"the lane never fetches into a ref a worktree can hold"*. `refs/heads/<base>` is one of those too, because an agent that runs `git checkout main` trips the same refusal at `integrate.ts:346`. It is also tripped by the post-push refresh at `:474`, and that one is worse. `:474` runs after `push` has already landed on origin. A failure there reaches `Effect.catchTag('RepoFailed', …)` at `:483`, which records `IntegrationRefused: unexpected` for a merge that is in fact on `main`.

What the fetch should look like:

- **Namespace.** Use `refs/lingtai/lane/<epochMs>-<uuid8>/base` and `…/branch`. Use one id for both refs, and make it the same id as the worktree's suffix at `:332`.
- **Fetch.** Fetch `+refs/heads/<base>:<lane>/base` and `+refs/heads/<branch>:<lane>/branch` into the mirror. `--prune` does nothing with two exact refspecs, so drop it.
- **Release.** Register the deletion of both refs (`update-ref -d`, errors ignored) with `Effect.acquireRelease` **before** the fetch runs. Then a fetch that wrote one ref and failed on the second still cleans up. The scope already does the same thing for the worktree at `:368-370`.
- **Every read in the lane switches to the lane refs:**
  - `worktree add --detach cwd` at `:368` starts from `<lane>/base`
  - `rev-list base..branch` at `:386`
  - `diff base...branch` at `:389`
  - `merge` at `:410`
  - `rev-parse branch` at `:429`
- **The merge needs `-m "Merge branch '<branch>' into HEAD"`.** Without it, `git merge --no-edit refs/lingtai/lane/…/branch` writes `Merge commit 'refs/lingtai/lane/123-ab/branch'` (I checked this with git 2.50.1). That would put a uuid into every merge on `main`. `git log --merges main` currently reads `Merge branch 'agent/431' into HEAD`, and the `-m` keeps it that way.
- **`unpushed-base` at `:381-382` reads `<lane>/base` on both sides.** That check never compared anything. In a bare mirror, `rev-parse <base>` and `rev-parse refs/heads/<base>` both resolve to the same ref. Removing the reason (`RefusalReason`, `attribution.ts:120`) belongs to another ticket. Don't make the check worse here, and don't make it pretend to check something new.
- **The post-push refresh at `:474` becomes a compare-and-swap.** Replace it with `update-ref refs/heads/<base> <mergeCommit> <laneBaseSha>`, with errors ignored. Whatever happens there must never turn a landed merge into a refusal. The compare-and-swap also stops an older integration from moving the mirror's base backwards over a newer one that overlaps it. I tested it: `update-ref` succeeds on a branch that a worktree has checked out, where `fetch` refuses. The mirror's base still needs refreshing at all because `apps/cli/src/discuss.ts:199-202` reads `refSha`/`listAt` of the base from the mirror without fetching first.

**Do not write `refs/heads/<branch>` back after the merge.** The ticket offers that as an option if some reader needs it. None does:

| Reader | What it reads | Needs the lane's write? |
|---|---|---|
| `worktree.ts:138` `remoteHead` | the mirror, straight after `ensureMirror`'s own `+refs/heads/*` fetch (`:107`) | no |
| discussion: `headOf` (`apps/cli/src/discuss.ts:148`) | the log's `headSha`, read by sha (`:205`) | no |
| board `loadDiff` (`apps/board/src/app/actions.ts:633`) | by sha | no |
| publish and land (`conduct.ts:1497`, `:1975`) | pushes the worktree's `HEAD` to origin | no |
| the sweep of arms (`tell.ts:254`, `arms.ts:55`) | GitHub's `matchingRefs` | no |
| `approve.ts:248` | GitHub's `refSha` | no |

The commits stay in the mirror's object store after the lane refs are deleted, and the next `ensureMirror` fetch makes them reachable again.

## The lane's sweep has to take the refs too

`sweepAbandoned` (`:291`) deletes worktrees left behind by a killed integration. Lane refs left by the same kill would pile up without a limit. Inside the same sweep, run `for-each-ref --format=%(refname) refs/lingtai/lane/` and delete any id whose `<epochMs>` is older than `WORKTREE_IS_ABANDONED_AFTER`.

**Judge by age, not by "no worktree registered for this id".** Integrations overlap by design (#194). With the fetch first and `worktree add` later, a sweep running in another integration would see a fresh id with no worktree yet and delete refs that are still in use. That is why the epoch goes into the ref name: a ref has no mtime to judge by.

## The test

`packages/repo` has no `unit/` directory. Add one: the glob at `vitest.config.ts:72` already picks it up.

There is no git port either. Every call goes through `at` at `:279`, which closes over `gitEffect`. Add an optional `git?: (args, options) => Effect<string, RepoFailed>` to `IntegrateOptions` (`:71`), defaulting to `gitEffect`, and have `at` use it. The test passes:

- a fake that records each call and answers by subcommand: `''` for `worktree list` and `status`, a sha for `rev-parse`, `'1'` for `rev-list --count`, and success for everything else
- `createMemoryEventStore()` from `@lingtai/event-store/memory`
- a `home` string that is never touched

That stays unit-level. `sweepAbandoned`'s `stat`/`rm` only run for a listed `integrator-` path, and the fake lists none.

Assert:

- no `fetch` call has a destination `refs/heads/<branch>` or `refs/heads/<base>`
- the `merge` call names the lane's branch ref and passes `-m` with `Merge branch '<branch>'`
- `update-ref -d` is called for both lane refs on success, and on a `merge` the fake fails
- a fake that fails the post-push `update-ref` still returns `{ ok: true }`

The real-git version of the bug is `packages/repo/integration/integrate.test.ts`: a worktree of the mirror with `agent/<n>` checked out, and the lane merging anyway. Add that case there as well. It is in the 803-second half, so nothing runs it inside the pass, and the fetch-destination assertion above is what stands in for it until then.

## Watch out

**`ensureMirror` has the same bug, and its version deletes the mirror.** `worktree.ts:107` fetches `+refs/heads/*:refs/heads/*`. I tested it on git 2.50.1 with a worktree holding `agent/1`, and it answers `fatal: refusing to fetch into branch 'refs/heads/agent/1' checked out at …`. Its `catch` at `:108-113` treats every failure as a missing mirror and runs `rm(path, { recursive: true, force: true })` on the bare mirror, which pulls the git directory out from under every live worktree, and then clones again.

So the agent in #434, whose worktree outlives the pass (0039 §1), will break the **next provision** on that machine, whichever ticket it is for. Leave this out of this diff: changing that fetch changes what every provision reads (`baseSha` at `:137`, `remoteHead` at `:138`), and it needs its own ticket. Say so in the commit body, citing `worktree.ts:107-113`. Don't use the closing verbs from CLAUDE.md next to an issue number.

The event that would show it happening is a provision failure whose detail contains `refusing to fetch into branch`. Or there may be no such event, because the `catch` swallows the error and re-clones: in that case the mirror's own mtime on the conducting machine is the evidence.

## Comment to replace at `:336-340`

The new comment should say that the lane fetches only into its own namespace. No worktree can check that namespace out, so what an agent does with branches in its own tree cannot fail the merge. It should also say that the old claim, *"removes the whole class of collision"*, was wrong, because the narrowed fetch still wrote `refs/heads/<branch>` (#434).
