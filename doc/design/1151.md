# Design: #1151, sandboxing a Codex run through srt

## The seam already exists, so this mirrors Claude Code's path

#1150 landed the whole carrier this ticket needs:

- **`RunRequest.sandbox?: RunSandbox`** is at `packages/agent/src/runtime.ts:141-145`. Its comment says: *"Set only when the run's decision is *sandboxed* or *refused*; absent is an unwrapped run, as before."*
- **`CallerAdditions.denyWrite`** is at `packages/sandbox/src/policy.ts:35-36`. Its comment says: *"Not writable, still readable: on `denyWrite` only."* `filesystemFor` puts it on `denyWrite` and nowhere else (`policy.ts:138`). The ticket's fallback ("add it here in `packages/sandbox`") does not apply.

**The conductor already hands `sandbox` to Codex runs.** `sandboxOf` (`packages/conductor/src/conduct.ts:871-910`) is spread into every agent dispatch whatever the runtime:

- implement: `conduct.ts:4545`
- fix: `:4826`
- judge: `:3174`
- reviewer and design: through `sandboxFor` (`packages/actions/src/agent-action.ts:1001`, `:1645`)

`codexRun` ignores `request.sandbox` today. So on a sandboxed project, a Codex run currently goes out unwrapped under `workspace-write`. This ticket is what makes that field mean something for Codex. Nothing upstream needs plumbing except the two small conductor changes below.

Here is what that means for the ticket's wording:

- **"Unsandboxed decision" and "no decision" are one case in code: `request.sandbox === undefined`.** `RunSandboxDecision` has only `sandboxed` and `refused` (`claude-sandbox.ts:19-21`). Its comment: *"`unsandboxed` never reaches a request: `RunRequest.sandbox` is absent instead."* The two "identical to today" tests in Done-when are the same test.
- **There is no `Sandbox` service in `packages/agent`, and none is added.** `claude-sandbox.ts:13-15` says: *"`packages/agent` never imports the package's live entry (the one that loads srt): the conductor closes over the service and hands a `wrap` function."* The "fake `Sandbox`" in Done-when is a fake `RunSandbox.wrap`, as `packages/agent/unit/claude-sandbox.test.ts:47-60` builds one.

## Where it goes

Add a new `packages/agent/src/codex-sandbox.ts` as the Codex sibling of `claude-sandbox.ts`. It exports two things:

1. `codexProfileDenies(verdict: UserPermissions, at: { home: string | undefined; cwd: string })`. This is the exported function Done-when asks for, which the follow-up ticket will reuse.
   - It returns either the absolute deny paths or a `SandboxRunRefused`.
   - `none` and `kept` → `[]`.
   - `unreadable` → refused, with `verdict.why`.
   - `denies` → each key is resolved:
     - `~` or `~/…` expands against `home`. With no `home`, it refuses by name.
     - An absolute key is kept as written.
     - A relative key is resolved against `cwd`.
     - A globbed key is kept as written once its static part is anchored the same way.
     - `:special` refuses by name: *"the user's Codex permission profile denies `<key>`, which the sandbox has no path for"*.
   - It is pure; the caller does the read.
2. `codexSandboxedLaunch(sandbox, run, ports)`. This is the counterpart of `sandboxedLaunch` (`claude-sandbox.ts:136-204`) and returns `Effect<{ command, args, env }, SandboxRunRefused, Scope>`. Its steps, in order:
   1. A `refused` decision fails with the same sentence as Claude: `sandbox required and unavailable on this host: ${why}` (`claude-sandbox.ts:146-148`).
   2. It resolves the Codex home: `codexConfigPath(env, cwd)` (`codex.ts:518-522`) minus the final `config.toml`. This is the same resolution `userPermissionsAt` uses, so the home granted is the home whose config was read. Undefined (no `CODEX_HOME` and no `HOME` in the request env) refuses by name.
   3. It calls `codexProfileDenies(userPermissionsAt(env, cwd), { home: env.HOME, cwd })`.
   4. It runs the collision check, reusing `collidingDenies` from `claude-sandbox.ts:126-130`. That function already uses `staticPrefix` and `within` from `protect.ts` for *is, inside, contains*, so do not write a third relation. `needed` is:
      - `sandbox.worktree`, `sandbox.mirror`, `sandbox.cache` (new field, below) and the Codex home;
      - plus `sandbox.read` (the hook binary) and the output schema path when there is one. The run cannot work without reading those either, and a deny covering them is voided just the same.
   5. It calls `sandbox.wrap(...)` with:
      - `command: argv`;
      - `env: { ...request.env, LINGTAI_CODEX_PROCESS_MARKER: marker }`;
      - `project_additions: decision.project_additions`;
      - `caller_additions: { write: [codexHome], read: [...sandbox.read, ...(outputSchemaPath ? [outputSchemaPath] : [])], denyWrite: [codexHome/config.toml, codexHome/AGENTS.md, codexHome/rules], deny: resolvedDenies }`.

      A wrap failure maps to `SandboxRunRefused(e.message)`. The conductor's closure has already turned srt's three error tags into sentences (`conduct.ts:893-906`).

`codexRun` (`codex.ts:1427`) branches once, right after the hook-wiring check (`:1438-1455`), which stays first for both branches:

- **Absent.** Lines `:1457-1520` stay exactly as they are, including the `kept`/`unreadable` note and `denyCoveringRoot`.
- **Present.** Build the argv with `codexArgv(..., { sandbox: 'danger-full-access', writable: [], denies: [] })`, then hand it to `codexSandboxedLaunch` inside the existing `Effect.scoped` at `:1502`. A refusal becomes the same `crash` outcome shape `:1468-1477` already returns (`sessionId: ''`). Success spawns `launch.command, launch.args` with `env: launch.env`.

**`CodexSandbox` stays `'workspace-write' | 'read-only'`** (`codex.ts:267`). Do not add `danger-full-access` to the union, because that is how it would reach an unwrapped run. Instead, widen only the `sandbox` parameter of `codexArgv`/`argsFor` to `CodexSandbox | 'danger-full-access'`. The one caller that passes the third value is the sandboxed branch, plus `invocation()` when `request.sandbox?.decision.kind === 'sandboxed'`. `argsFor` already emits `--sandbox <mode>` when `denies` is empty (`:1306`), and `--add-dir` comes only from `writable` (`:1316`), so passing `writable: []` and `denies: []` produces the ticket's argv with no new branch in `argsFor`. The `lingtai_${sandbox}` profile name at `:1275` is never built in that case, because `permissionArgs` is null.

Dropping `--add-dir` loses nothing. `gitWritableRoots` (`codex.ts:1171`) returns the worktree's git directory, which lives under the mirror, and the mirror is on srt's `allowWrite` (`policy.ts:123-125`). The mirror's `config`, `hooks/` and `info/` are write-denied by the policy itself (`policy.ts:108-112`).

## The process marker moves up, and the env handed to `wrap` is the only one

Today `processMarker` is created inside `Effect.callback` (`codex.ts:1506`). Move `randomUUID()` above the branch. Both branches then use the same variable, and the stop paths at `:1650`, `:1698` and `:1714` are unchanged. In the sandboxed branch, the spawn's env is `launch.env` as returned. Do not spread the marker in again: if `wrap` dropped it, a test should see that rather than have it papered over. The unsandboxed spawn keeps its literal `{ ...request.env, LINGTAI_CODEX_PROCESS_MARKER }` byte for byte.

Keep `detached: true` and `stdio`. `child.pid` is now srt's launcher (`sandbox-exec`, or `bwrap` on Linux). `noteDescendants(child.pid, seen)` still walks down from it by `ppid`. On Linux, the marker scan over `/proc/<pid>/environ` (`:105-118`) is what finds the agent past bwrap's `--new-session`.

**What a unit test cannot show:** whether srt's bwrap passes the caller's env through untouched, so that the marker is really in the grandchild's `/proc/<pid>/environ`. The stand-in at unit level is that `wrap` received the marker and the spawn received `wrap`'s env. The real-host check is S10's canary, and that ticket is where a missing marker would show.

## Two conductor changes

1. **`RunSandbox.cache: string`** (`claude-sandbox.ts:28`). The collision check needs the project cache, and `packages/agent` has no `HostFacts` with which to call `cacheDir` (`policy.ts:71-72`, `<stateDir>/cache/<project>`). Set it in `sandboxOf` (`conduct.ts:880-889`) as `join(home, 'cache', project)`, beside the `mirrorPathFor(project, home)` it already computes. Add a one-line unit assertion that it equals `cacheDir({ stateDir: home, … }, project)`, the same way `policy.ts:74` holds `mirrorDir` to `mirrorPathFor`. Claude's launch ignores the field.
2. **A sandboxed Codex judge with no worktree must not start in `home`.** `conduct.ts:3169-3173` starts a sandboxed judge with no worktree in `claudeConfigDirFor(home, judgeRunId)`, but only when `runtime === 'claude-code'`. Every other runtime starts in `home`, the state directory, and that whole directory is on srt's `denyRead` (`policy.ts:92`). A sandboxed Codex judge there would start in a directory it cannot read. Drop the `runtime !== 'claude-code'` clause so both runtimes start in the run directory. `sandboxOf` already makes that directory the run's `worktree` (`conduct.ts:885`, `run.worktree ?? runDir`), so it is readable and writable inside srt.

   For Claude, `prepareClaudeRunDirectory` creates it. For Codex nothing does, so `codexSandboxedLaunch` creates `sandbox.worktree` when it is `sandbox.runDir` and missing. Do this as an `Effect.acquireRelease` in the run's scope that removes only what it created. Its path ends `/claude`. That is harmless, and renaming `claudeConfigDirFor` is not this ticket.

## Decisions the ticket left to the design

- **`unreadable` refuses, `kept` adds nothing.** This is as the ticket says. It falls out of `codexProfileDenies`, so the follow-up ticket inherits the same answer.
- **The output schema file is a caller `read`, not left on the temp roots' `allowWrite`.** It lives in `os.tmpdir()` (`codex.ts:1347-1349`), and `tempRoots` are writable inside srt (`policy.ts:98-105`). `codex.ts:1482-1485` says: *"An agent that could overwrite its own answer schema has no schema."* `caller_additions.read` is on `allowRead` and `denyWrite` (`policy.ts:122`, `:137`).
- **`AGENTS.md`, `config.toml` and `rules` go on `denyWrite` only, never on `deny`.** Caller `deny` lands on `denyRead` too (`policy.ts:120`), and Codex has to read its own `config.toml`. Do not stat the files: srt denies a path whether it exists or not (ticket, *Watch out*).
- **`invocation()` reads `request.sandbox` and does no I/O beyond what it does today.** It does not compute the Codex home or denies for the sandboxed shape: those are the run's and are not part of the argv.

## Tests (`packages/agent/unit/`, never srt)

- `codex-sandbox.test.ts`:
  - `codexProfileDenies`: each key form, and `none`/`kept`/`unreadable`.
  - The launch with a recording fake `wrap` and an in-memory `userPermissions` port: refused decision, Codex home missing, each collision (worktree, `<worktree>/secrets`, mirror, cache, Codex home, and a parent of the worktree), `denyWrite` contents with `config.toml` absent from `deny`, the marker in the wrap's env, and a wrap failure.

  Make the profile read a port (default `userPermissionsAt`), as `SandboxPorts.readOperatorSettings` is for Claude, so no test touches `$HOME`.
- `codex.test.ts`:
  - The existing argv expectations stay untouched; they are the "byte for byte" proof.
  - Add a test that builds an argv for every `CodexSandbox` × denies × `kept` combination without `request.sandbox` and asserts that `danger-full-access` appears in none of them.
  - Through `options.spawn`: a sandboxed run spawns the fake's `argv[0]`/rest with the fake's env and no `shell`; a refused run, or a failing wrap, calls neither `wrap` nor spawn and returns `failure.kind === 'crash'` carrying the sentence.
  - A stop test: interrupt a wrapped run and assert that `options.stopProcesses` was called with the marker the fake `wrap` received.

`effect-ratchet.baseline.json` must not rise. The directory creation and every read in the new file are Effects. `userPermissionsAt` stays sync, as it is today, and is called, not rewritten.

## What would settle it after it lands

Nothing in the log records the wrap yet; recording the boundary is S8's. Until then, the run log's `codex` note and the outcome's `failure.detail` on the run's `AgentRunFinished`-family event are where a refusal shows. Whether a real wrapped run worked is S10's canary.
