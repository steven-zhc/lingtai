# #1167: design note

> **History.** Board addresses in this note (`/task/<id>`, `/pr/…`, `/recipe/…`, `?project=`) are the ones that existed when it was written; they no longer resolve. The current forms are in [1502.md](1502.md).

## The shape

The sandbox rows are a **separate component** placed after the lock rows. They are not a new `BannerRow` kind inside `LockRows`.

- **Pure row builder.** Add `sandboxBannerRows(projects, scope)` to `apps/board/src/lib/sandbox-state.ts`. It goes beside `sandboxState`, because that file *"imports no store"* (`sandbox-state.ts:7-8`).
- **Pure markup.** Add `SandboxRows` in a new `apps/board/src/app/sandbox-banner.tsx`. Like `LockRows`, it takes its rows as props, so a test renders it without a store (`lock-banner.tsx:10-11`).
- **Streamed slot.** Add `sandboxBanner(project)` in the same file, built like `sandboxSlot` (`sandbox-slot.tsx:23-27`).

Why it is separate: the ticket's trap is that *the stopped banner is not a lock*. If `sandbox-banner.tsx` never imports `./pause-button.tsx`, the absence of Resume and Lift is structural. A test still asserts it. It also leaves `LockRows`, `bannerRows` and both of their test files (`unit/locks.test.tsx`, `unit/continue-today.test.tsx`) untouched.

## Where it renders

**Every page that already has lock rows, and only after them.**

- `LockBanner` (`lock-banner.tsx:30-33`) returns `<>{LockRows…}{sandboxBanner(project)}</>`. That covers `/backlog`, `/landed`, `/report`, both places on `/recipe/[project]` (`page.tsx:370,418`), and the task layout (`layout.tsx:285`) in one change.
- **Home** does not use `LockBanner`. Its `BannerPart` (`app/page.tsx:802-813`) draws `<LockRows>` directly. Add `sandboxBanner(only, key('sandbox-banner'))` after `<LockRows>` and before `<Pending>`. Home keys its boundaries for project switches (#1037), as `sandboxSlot` already does.

## The read

Use `readRegistered()`, the `cache()`'d read at `lib/locks.ts:42`.

- The lock rows and the bar icon already call it on these pages, so this costs no new read.
- Map each project through `sandboxFactsOf` (`sandbox-state.ts:48`).
- Never call `hostHere`, `checkSandboxBlock` or `verdictOf` from `apps/board`. #1163's note gives the reason: srt must not reach the board, and #1152's import-graph test is the unit check that stands in for the Next build here.

**A failed read draws nothing.** Catch the rejection and render `null`, not a row. The ticket says health's own failure sentence covers it. The lock rows on the same page already say *could not read which projects are paused — …* from the same failed `readRegistered` (`lock-banner.tsx:111-120`).

## The rows

`sandboxBannerRows(projects: readonly { project: string; facts: SandboxFacts }[], scope: string | undefined)` builds one row per project in scope.

- **Order:** the order `readRegistered` returns. That is the order `bannerRows` walks `held` for the paused rows, so *after the locks, in the filter's order* stays one order and not two.
- **Which states get a row:** only `stopped` and `degraded`. `off`, `sandboxed`, `unknown` and `unreadable` return no row. **Off by choice never gets a banner**, and a test pins it: a project whose recipe has no `sandbox:` block, or `enabled: false`, produces `[]`.
- **What a row carries:**
  - `{ kind: 'stopped' | 'degraded', project, reason }`.
  - The reason for **degraded** is the fixed sentence `SENTENCES.degraded` (`sandbox-state.ts:34`). `ProjectSandboxObserved` is `{ kind, runId }` and carries no *why* (1163.md §2), so there is nothing more to say.
  - The reason for **stopped** is the host's reason taken from `refused` (next section).

### The stopped reason

Add `sandboxRequiredReason(detail: string): string | undefined` to `packages/recipe/src/sandbox.ts`, beside `isSandboxRequiredRefusal` (`:39`).

- It returns the parenthesised text that follows `SANDBOX_REQUIRED_REFUSAL`. That is the `said(verdict)` part of the template at `sandbox.ts:177-179`: `` `${SANDBOX_REQUIRED_REFUSAL} (${said(verdict)}) — install what is missing, or set required: false…` ``.
- If the shape does not match, it returns `undefined`, and the row shows `SENTENCES.stopped`.
- It lives beside the template so the sentence and its reader change together. That is the reason the constant's own comment gives (`sandbox.ts:28-29`).
- Unit tests go in `packages/recipe/unit/`:
  - a detail produced by the template;
  - a detail with a ref and another problem before it (the reason `isSandboxRequiredRefusal` matches by substring, `:36-38`);
  - a detail that does not match.

### The install command

`installFor(process.platform)` comes from `@lingtai/sandbox`'s pure index (`packages/sandbox/src/index.ts:19`, `install.ts:22`). Its file says it is *"srt-free, … so a caller reads it without loading srt's module graph"* (`install.ts:4`). `@lingtai/recipe` already imports that index (`sandbox.ts:13-20`).

- Call it in the async slot and pass the result to `SandboxRows` as a prop. The markup then has no `process` access and tests can pass `undefined`.
- The board runs on the conducting machine, so its platform is the host's. That is the same assumption `lingtai doctor`'s `sandbox: host` row makes.
- On a platform `installFor` does not know (`undefined`), show the recipe fix alone. Do not invent a command.

## The markup

Draw a `<div className="pbanner sbanner">` wrapper only when there are rows. Each row is a `.pbrow` with a state class (`sbx-stopped`, red; `sbx-degraded`, amber), in this order:

1. The label: `Sandbox stopped` or `Sandbox degraded`.
2. The project as a `Link` to `withProject('/', project)`, as the paused row does (`lock-banner.tsx:139-141`).
3. The sentence: *this project is stopped: it requires a sandbox this host cannot provide*, or *this project is running without a sandbox*, followed by the reason.
4. The install command as `<code>`.
5. A link to `/recipe/<project>#sandbox` with the alternative fix: `set required: false` for stopped, `or turn it off` for degraded. This is the anchor the icon already links to (1163.md §5).

No `.grow` and no button.

**CSS:** `.pbanner` is the held colour throughout (`globals.css:3399-3404`). Add `.sbanner` overrides for the two tones beside it. Both tokens should already exist: amber is the headline's (`page.tsx:1077-1078`, *"Never amber — that is the headline's"*) and red is the fail colour. Use those tokens; add no new ones. The label text, not the colour, makes the states different.

## Loading

The slot's `Suspense` fallback is `<Skeleton shape="lines" count={lastSandboxRows(scope)} />` (`app/skeleton.tsx`).

- Keep the remembered count in a per-process `Map` keyed by scope (`''` for all projects). It is recorded when a render finishes. Follow the precedent of `lastOffered` / `skeletonCount` (`lib/board.ts:1126-1170`) and add a `forget…` function for tests.
- **Before any answer the count is 0, not 2** (`board.ts:1155` uses 2 for cards). These rows are absent in the ordinary case, so a guessed placeholder would make the page jump in the common case.

## Health

`bearing(socket, board, code, runnable)` (`lib/bearing.ts:99`) is where every sentence is chosen.

**The new parameter.** Add a fifth, **optional** parameter `sandbox: SandboxNews | null = null`, shaped like `CodeNews` (`bearing.ts:51-58`: `wrong`, `command`, `said`). It is optional so that `live.tsx:266`, `:321`, `:344` and every existing bearing test keep compiling unchanged.

**Only `stopped` counts.** *Required and not running* is exactly `stopped`. `degraded` is `required: false` by construction (`sandbox.ts:111`), so it gets no health sentence.

**Where it sits in the order.** Put a branch **immediately before `if (code?.wrong)`** (`bearing.ts:213`):

- It sits after the offline, unknown, projections-stopped, no-board, no-daemon and lag-with-no-daemon branches, because those make the board itself unbelievable.
- It sits before stale code, because `lingtai restart` does not cure a missing `bwrap`.

**What the branch returns:**

- `tone: 'warn'`.
- `label`: `<project> stopped: no sandbox`, or `N projects stopped: no sandbox`.
- `command`: the install command, or `lingtai doctor` when `installFor` is `undefined`. Doctor's `sandbox: host` row is #1159's.
- `title`: through `also(…)`, extended so `sandbox.said` is appended the way `code.said` is (`bearing.ts:110`).

**Feeding it.**

- `Health` (`health.tsx:96-106`) gets a `sandbox: Promise<SandboxNews | null>` prop, built server-side from `readRegistered()`, scoped to the filter's project, with the stopped states only. A rejection gives `null`: the failed read is said by the lock row, not twice.
- `Answered` in `live.tsx` already `use()`s `code` and `near` under its outer boundary; it `use()`s this promise the same way and passes it down to both `bearing` calls in its subtree.
- `Health` renders only on home (`page.tsx:1081`), which passes it.

**Unit tests in the existing bearing test:**

- one stopped project gives the label and the install command;
- `code.wrong` and a stopped sandbox together: the sandbox wins;
- a stale beacon or offline socket together with a stopped sandbox: those still win;
- `null`: unchanged.

## Edges this note decides

- **Paused and stopped together:** both rows show, and neither component reads the other.
- **A stale page:** as the lock rows, meaning re-read per render; nothing here subscribes.
- **Cost to later tickets:** `projects.test.tsx:175` and `bar-component.test.tsx` are untouched, because the bar's objects do not change and these are rows under it. No ADR is affected: this follows 0126 §8's rows rather than adding a lock, so no superseding file is needed.

## What settles it on a real project

The code does not settle this. Two events on `prj-<project>` do:

- **Stopped:** the last `ProjectRefused.detail` contains `SANDBOX_REQUIRED_REFUSAL`, with no `ProjectRecovered` after it.
- **Degraded:** the last `ProjectSandboxObserved.kind` is `'degraded'` and the recorded recipe's block is enabled.

Everything above is unit-level. Nothing checks the Next build before the merge.
