I've read the adapters' kill paths and Effect 4's `Effect.callback`. Here is the design note.

# #1023: the adapters' run as an interruptible Effect

The ticket already settles the shape. This note covers three things it leaves for the implementer: how the interrupt finalizer actually waits, the two Codex scans that decision 5 does not mention, and the order the scope has to unwind in.

## 1. The finalizer cannot wait on `resume`. `finish` needs a second listener.

Effect 4's `Effect.callback` ignores `resume` once the fiber is interrupted. Its doc says *"Call `resume` at most once … later calls are ignored. Return an optional cleanup effect from the registration function to run if the fiber is interrupted"* (`node_modules/.pnpm/effect@4.1.2/node_modules/effect/src/Effect.ts:1860-1864`). Today `finish` hands the outcome only to the promise's `resolve` (`claude-code.ts:517-526`, `codex.ts:1542-1563`). So the cleanup effect cannot learn that the group is gone through `resume`. It needs its own latch.

- In `finish`, replace `resolve(outcome)` with `resume(Effect.succeed(outcome))`, then call `onSettled?.()`.
- The cleanup returned from the register function is an `Effect.suspend` that does three things:
  - calls the existing `onAbort()`, which is `kill('aborted', 'the conductor aborted the run')`;
  - returns `Effect.void` if `settled` is already true;
  - otherwise returns `Effect.callback<void>((done) => { onSettled = () => done(Effect.void) })`.
- **Use `onAbort`, not a fresh `kill`.** `kill` returns at once when `killed`/`stopped` is already set or the run is `settled` (`claude-code.ts:555-556`, `codex.ts:1578-1579`). Suppose the wall timer has already started `kill('timeout', …)`. The finalizer must then wait for *that* kill to settle. It must not start a second one, and it must not return early. The latch covers both cases, because it only watches `finish`.
- Give the register function the plain `(resume)` signature, with no second parameter. If it declares `(resume, signal)`, Effect hands it an AbortSignal that it aborts on interruption (`:1860-1862`). That would be a second way to trigger `kill`, but it does no waiting, and the cleanup effect is the only route that waits.
- `request.signal`'s `onAbort` listener stays exactly as it is (ticket, decision 4).

The bound comes for free: `finish` always fires, at the latest at `5_000 + KILL_GRACE_MS` for Claude Code (`claude-code.ts:578-596`), and for Codex once `stopProcesses` settles (`codex.ts:1605-1620`). The default `stopRunProcesses` carries its own 10 s deadline (`STOP_SCAN_DEADLINE`) and fails with an Error past it, so a descendant stuck in uninterruptible I/O ends in the `process cleanup incomplete` crash rather than an endless scan. The finalizer cannot hang.

## 2. Codex has three scans, not one

`stopProcesses` is called from three places:

- `kill`'s hard timer (`codex.ts:1610`, `.then(finish, finish-with-crash)`);
- the `'exit'` handler (`:1654`, `.catch(trace.note)`);
- the `'close'` handler (`:1666`, `await`).

Decision 5 names only the third. All three become forks onto the same per-run `FiberSet` runtime, each keeping the handling it has now:

- hard timer: success → `finish(stopped!)`; failure → the `…; process cleanup incomplete: <message>` crash. That is the same sentence, byte for byte (ticket, *Watch out*).
- `'exit'`: failure → `trace.note('cleanup', 'process scan failed on exit: …')`.
- `'close'`: the `cleanupFailure` path, then the `if (stopped !== null || settled) return` re-check (`:1668-1670`).

`stopRunProcesses` throws a non-`ESRCH` error from `process.kill` (`codex.ts:152`), and `listProcesses()` can throw synchronously. So the Effect is `Effect<void, Error>`: wrap the loop body in `Effect.try`, with the error mapped to an `Error`. The forks pattern-match on that error, never on a defect. `CodexOptions.stopProcesses` (`:259`) becomes `(marker, seen) => Effect.Effect<void, Error>`. The integration double (`integration/claude-code.test.ts:927`) becomes `() => Effect.fail(new Error('ps unavailable'))`, so the message reaching the detail is unchanged.

## 3. Scope order: the finalizer finishes before the scope closes

Build it as `Effect.scoped(Effect.gen(function* () { const runFork = yield* FiberSet.makeRuntime(); return yield* Effect.callback(…) }))`.

On interruption, the callback's cleanup runs first, while the scope is still open. That is required: for Codex, the fiber that calls `finish` (and so releases the latch) is the hard-timer scan, a member of the `FiberSet`. Only after the cleanup completes does the scope close and interrupt any scans still running (for example an `'exit'` scan still looping). If the `FiberSet` were made outside the callback's scope, or closed before it, the latch would never fire.

Pass `runFork` into the callback body and call it from the Node handlers. Those handlers stay plain synchronous emitter callbacks (decision 1). `claude-code.ts` makes no scans and needs no `FiberSet` or `Effect.scoped`.

## 4. Faces and the ratchet

The face shape is fixed by `packages/domain/unit/effect-ratchet.test.ts:167-265`: exactly `export function X(…) { return Effect.runPromise(<call>) }`, with at most `{ signal }` as the second argument. The model already in the package is `openRunLog` (`packages/agent/src/run-log.ts:249-251`) together with its entry in `effect-ratchet.faces.json`. Copy its `why` style: name the callers that still await the face.

The baseline line is `packages/domain/unit/effect-ratchet.baseline.json:7`, `"async": 11`, and it goes to `2`.

The runtime objects' methods become arrows onto the faces. Codex's `'close'` handler stops being `async` because its body moves into the fork. `codex-text.ts`'s `checkAuth` becomes `() => Promise.resolve(…)`, with no face (ticket).

## 5. Tests

- **Claude Code interruption.** Use the harness at `unit/claude-code.test.ts:280`. Fork with `Effect.runFork(claudeCodeRun(options, request))` and interrupt with `Fiber.interrupt`, which gives you a promise for the interruption. Then:
  - Step `vi.advanceTimersByTimeAsync` up to the SIGKILL timer (`5_000`) and assert the interruption promise has **not** resolved.
  - Make the stand-in `sendSignal` throw `ESRCH` for signal `0`, and advance one `PROBE_MS`.
  - Assert the interruption then completes, and that the stand-in recorded `SIGTERM` and then `SIGKILL` to `-pid`.

  Never use a bare `await` (ticket, *Watch out*).
- **Codex interruption.** Inject a `stopProcesses` that stays pending until the test releases it, through a `Deferred` the test completes. Assert the interruption has not completed after `5_000` ms of fake time. Then release the `Deferred` and assert it has.
- **Spawn failure.** A spawn stand-in that emits `'error'` gives `Exit.isSuccess(exit)` with `failure: { kind: 'crash', detail: err.message }`.

None of this needs the integration half. The only integration file touched is the `stopProcesses` double, which is a type change. It runs after the merge, and the Codex unit case stands in for it before.

## Not decided here, and not open

- Whether the probes' timeouts (`auth.ts:106`, `:140`) become `Effect.timeoutTo` or stay inside the callback is the implementer's choice (ticket, *Edges*). The condition is the same either way: the child is killed, and the `ProbeEnd` is what it is today.
- No ADR is contradicted. 0101 §6 is the rule being applied, and #587's wait is the one this extends to interruption.
