# Design: #387 — 0109 states the ticket port as built, and `operating.md` documents `source.tickets: db`

This change touches documentation only, plus three stale strings in source files. No behaviour changes. `pnpm fmt:check` (oxfmt covers `.md`), `pnpm lint`, `pnpm typecheck` and `pnpm test` cover all of it. `apps/site/unit/docs.test.ts` reads `doc/`, so if 0109 is renamed, that test is what notices.

## The ticket's own plan is wrong in two places. Write what the code says.

1. **There are two interfaces, not one.** `packages/conductor/src/ticket-store.ts` defines:
   - `Tickets` (`:64-77`): eight verbs — `listOpenIssues`, `listIssuesSince`, `getIssue`, `createIssue`, `comment`, `setLabels`, `closeIssue`, `updateBody`. Every read and write the core makes against a ticket system goes through these.
   - `TicketStore` (`:105-123`): `propose` and `withdraw`, the door the findings backlog uses. It has one implementation, `githubTicketStore` (`:137`). That implementation is written only against `Tickets` verbs (`Pick<Tickets, 'createIssue' | 'listIssuesSince' | 'comment' | 'closeIssue'>`), so it works over `dbTickets` too. `apps/cli/src/backlog.ts:196-208` says so: *"`client` carries a `db` project's own ticket verbs (`projectClient`, #383), so `githubTicketStore` writes the finding wherever this project's tickets actually live."*

   0109 §2 should therefore name **`Tickets`** as the port and its two implementations. `TicketStore` should be described as the propose/withdraw layer that sits on top of any `Tickets`. Do not rename anything in code; this ticket only documents.

2. **The contract suite does not cover GitHub.** `describeTicketsContract` (`packages/conductor/test/tickets-contract.ts:37`) runs against:
   - `memoryTickets` (`unit/tickets.test.ts:42`)
   - `dbTickets` on SQLite (`unit/db-tickets.test.ts:125`)
   - `dbTickets` on Postgres (`integration/db-tickets.test.ts:160`, under `postgresUnderTest()`)

   `GitHubClient` is held to the *type* only: *"`GitHubClient` satisfies this structurally — pinned in `unit/tickets.test.ts`"* (`ticket-store.ts:45-48`). Say exactly that. Do not write "one suite holds every implementation". The Jira/Linear sentence becomes: *a new system is one `Tickets` adapter that passes `describeTicketsContract`*. That is true, and it is the rule for any adapter added from now on.

## The user-facing section: `doc/operating.md`

That file is where a person writes `source:` (§ *Onboarding a repository → 1. Write the recipe*, the YAML at `:402`). `tutorial.md` is GitHub-only by design ("one GitHub issue worked by an agent"), so leave it alone.

Add a `####` subsection after the recipe example, beside *The layers*. Call it something like *Tickets without GitHub — `source.tickets: db`*. It should cover:

- **How to set it:** `source: { tickets: db }` in `~/.lingtai/<project>/recipe.yml`, on a project with no history.
- **Version skew:** a daemon older than this field silently drops the key and keeps reading GitHub (`recipe.ts`'s *code, restart, paste* note: `source:` is `z.object`, not strict). Restart the daemon first.
- **The four commands,** exactly as `apps/cli/src/lingtai.ts:1292-1330` parses them:
  - `lingtai ticket list [--all] [--project <p>]`
  - `lingtai ticket new [--project <p>]`
  - `lingtai ticket edit <n> [--project <p>]`
  - `lingtai ticket close <n> [--project <p>]`

  `new` and `edit` open `$VISUAL`/`$EDITOR` on a form: a title, a `labels:` line, then the body. With no kind label the ticket is still created, but the queue never takes it. On a `github` project, every one of these refuses and points at `gh issue list` (`ticket.ts:153-157`).
- **`lingtai ticket close` is not `lingtai close`.** It changes a row and appends nothing (`ticket.ts:6-10`). `end` does not run, and the log does not say the work item is over.
- **What `db` does not do:**
  - No webhook. The daemon finds a new or changed ticket on its sweep, `SWEEP_MS = 5 * 60_000` (`packages/daemon/src/work-loop.ts:124`), or at the next pass completion.
  - No web page. `url` is `null`, so a board card has no link.
  - No dependencies. `blockedBy` is always `0`, so nothing is ever `blocked-by`, and a chain has to be held with `agent:hold` by hand.
  - No assignee, so `assignee: mine` matches nothing.
  - No delete, because `Tickets` has no such verb. Close a ticket instead.
  - `closeIssue`'s reason is not stored.

  All of these are listed in `db-tickets.ts`'s header comment.
- **The repository is still on GitHub.** Refs, the merge lane and the App token are untouched by `passClientOf`. `db` moves where tickets live, not where code lives.
- **Where the tables live:** on whichever store `database.store` names, so they move with that store, and `lingtai projection rebuild` does not touch them.

Check the assignee claim before writing it: grep how `assignee: mine` filters (`discover.ts`) and confirm it reads `assignees`. If it does not, drop that line.
