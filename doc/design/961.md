## Design note: #961

There are three files to change, and only the assertions in them. The ticket's Fix row covers most of it. Four things it leaves out:

**1. `discuss.test.ts`: the actor check moves by one, and the list fix alone won't catch it.**
`packages/conductor/integration/discuss.test.ts:98` reads `chat[2]?.actor`. Index 2 was `DiscussionAnswered` when the stream was `['DiscussionAsked', 'RunSpent', 'DiscussionAnswered']`. Once `RunPrompted` is in the list, index 2 is `RunSpent`. The ticket says *keep the actor check on `DiscussionAnswered`*. To do that, find the event by its type (`chat.find((e) => e.type === 'DiscussionAnswered')`) rather than changing the 2 to a 3, so the check still names the event it is about. The `RunPrompted` is appended by `recordPrompt` at `packages/conductor/src/discuss.ts:572`, and its one writer is `packages/conductor/src/record-prompt.ts:114` (`type: 'RunPrompted'`). Cite that in the commit.

I have not checked whether the `RunPrompted` actor is `agent:${chatId}` too. Don't widen the actor check to cover it. The test's comment (*"a third actor appears on the log"*) is about the answer.

**2. `recipe.test.tsx:153-165`: the row name, and the comment above it.**
The row is `name: 'an attempt'` at `apps/board/src/lib/recipe.ts:898`. Its keys are still `LIMIT_KEYS.map((key) => \`runtime.limits.${key}\`)` (`:904`), so the comment's claim (*four limits from the recipe and the schema, and says both*) still holds. Change `'a pass'` to `'an attempt'` in the two `of(...)` calls and in the comment's backticked name. Leave both `toContain` assertions as they are.

**3. `recipe.test.tsx:284`: which of the two refusals.**
This is the ticket's *reworded into two places* edge, and the answer is `stepsRefusal`. `packages/recipe/src/local.ts` has two "not configured in the machine file" sentences:
- `stepsRefusal`, at `:95`: `` `${at}: an attempt is not configured in the machine file — it is configured in the recipe, ` ``
- `runtimeRefusal`, at `:110`: `how a project's work is run is not configured in the machine file`

The test writes `steps:\n  proposed: []` into `config.yml` (`:276`), so the refusal it hits is `stepsRefusal`. The expected string becomes `'an attempt is not configured in the machine file'`. The unit test `packages/recipe/unit/local.test.ts:435` already pins this exact phrase for the same case, which is the check you can run before the merge. Don't extend the expected string into the em dash or `project's`: the board renders HTML, and the apostrophe may come out escaped. The old assertion stopped at `machine file` for the same reason.

**4. `doctor.test.ts:564`: the gate-action sentence.**
Today's sentence is at `apps/cli/src/doctor.ts:2528`, on the `inTheLoop` branch: `` `and a step's action verdict is what the loop waits for, so every attempt is refused after a worktree and an install.` `` Assert `'every attempt is refused'`. That is the same shape as the old fragment, and it is the half the test's docblock is about: a gate action is `fail` because the loop waits on it. This sentence also has an apostrophe, but `detail` is plain text, so that is not the reason to keep the fragment short. The reason is that it is the part the rule depends on.

**What can be checked before the merge.** Only the three-file command in the ticket's Watch out verifies these edits. The unit-level stand-ins are `packages/recipe/unit/local.test.ts:435` for the refusal and `pnpm typecheck` for everything. `pnpm test` covers none of the four assertions. Expect it to be green both before and after, and don't read that as proof.
