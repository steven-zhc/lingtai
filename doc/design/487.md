# Design: #487, the conductor's wait handlers stop naming `Hold` and the old events

## What the four files actually do today

**None of them calls `allowedMoves`.** `grep -rn allowedMoves packages apps --include='*.ts'` finds it in `packages/domain/src/moves.ts:21` and in comments in `action.ts` and `wait.ts`, and nowhere else in `src`. So the ticket's Problem row is wrong about that word. The handlers decide by reading the lifecycle `reduceWorkItem`/`reduceRun` give them: `approve.ts:200` (`run.lifecycle.status !== 'awaiting-approval'`), `approve.ts:215` (`item.lifecycle.status !== 'blocked' || …runId…`), `ask.ts:57`, `ask.ts:128-142` and `approve.ts:524,538`. Those reducers are domain's and are not in these four files. Leave them alone, as #486 did (`doc/design/486.md`, "Leave `reduceWorkItem`, `labelState`…").

The real work is in the Done-when: no `Hold` and no old event type in these four files. Below is each site, set against 0120's appendix (`doc/decisions/0120-a-reason-is-a-type.md:628-655`):

## Decision 1: the writers go through event-boundary adapters in `@lingtai/domain`

`approve.ts` and `ask.ts` append. 0120's *Two phases* says how a phase-1 writer appends (`0120…md:577-579`): *"a temporary event-boundary adapter turns the new value into today's payload; the adapters are the only place both shapes exist."* Put the adapters in **`packages/domain/src/adapters.ts`**, next to `holdOf` (`:361`), and update its header line *"Only `eventOf` and `holdOf` are exported"* (`:16`). Each adapter calls `parsePayload` itself, so validation stays where it is today. Each returns `{ type, data }`, the shape `eventOf` returns, and the caller adds `actor`.

- **`waitStartedOf(reason: WaitReason, pass)`** → `WorkItemBlocked{hold: holdOf(reason, pass)}`. Used by `ask()` with `{ _tag: 'OwnQuestion', question, by }`. `holdOf`'s `OwnQuestion` arm (`adapters.ts:363-364`) gives exactly today's `{ _tag: 'Question', question, by }`. `pass` stays required, as on `holdOf`. `ask.ts` passes an empty one, with a comment that `OwnQuestion` reads none of it.
- **`waitResolvedOf(reason, resolution, by, note)`**, for `Requeue` and `AnswerQuestion` → `WorkItemUnblocked`. `withdrawn: true` is set exactly when `reason._tag === 'OwnQuestion'` and the resolution is `Requeue`; the appendix says *"`withdrawn` is an `OwnQuestion` resolved by `Requeue`"*. For `AnswerQuestion`, `note` is `resolution.choice`.
- **`waiverOf({step, action, runId, onSha, by, reason})`** → `StepWaived`, and **`approvalOf({...})`** → `[...waivers, ApprovalGranted]`, in today's order (`approve.ts:309-329`). `splitStep` stays in `approve.ts`, and callers pass the parts already split. `waive()` uses `waiverOf`. Do not delete `waive()`: removing it is #464's appendix row, not a reader move.
- **`approvedMergeRefusedOf({ runId, reason: RefusalReason, raw, branch, base, paths, baseSha, headSha })`** → `{ event: WorkItemBlocked{…afterApproval: true}, question }`.

**Why the approval refusal gets its own adapter.** `holdOf` cannot produce the hold `approve.ts:394-405` writes, for two reasons:
- `mergeRefusedHold` hard-codes `afterApproval: false` (`adapters.ts:334`).
- `WaitReason`'s `MergeRefused` excludes `conflict` and `verify-failed` (`wait.ts`, `RefusalReason.exclude([...])`). An approved merge that conflicts writes `MergeRefused{reason: 'conflict'}` today. Sent through a `WaitReason`, it would come back from `holdOf` as `Routed`, a different `_tag` on the board.

The `afterApproval` bit is also load-bearing: `moves.ts:38-47` refuses `Approve` on it, and the board still reads that until #483. So the adapter builds the hold literally, computing `why` the way `mergeRefusedHold` does (`diagnoseRefusal(...).what`, `adapters.ts:328`). Its comment should say that it exists until #464, and why `holdOf` cannot stand in. `question` is `legacyColumns(hold).question`, returned beside the event because `tellGitHubAbout` needs it (`approve.ts:419-425`).

**Do not rewire the builders in `test/events.ts` onto these adapters.** Their outputs are pinned by other tickets' tests, and #464 rewrites both.

## Decision 2: `allowedResolutions` decides only where its answer is today's answer

**Today's handlers and 0118's table disagree in exactly one place: `approve`.** A red `build`, a red verify or a conflict escalated to a person is stored as `Routed{when: red|verify-failed|conflict}`. `reasonFromHold` reads that as `ProposedEscalated{BuildRed|VerifyRed|MergeConflict}` (`read-model.ts:946-962`), and `allowedResolutions` omits `Approve` for all three (`wait.ts:240-244`). Today `approve` accepts them: `conduct.ts:4007-4046` appends `ApprovalRequested{action: 'unfixed'|'judge'}` whenever `judged && onOrigin !== null`, so the run is `awaiting-approval`. `allowedMoves` agrees with today (`moves.ts:34-37`). The ticket's Watch out decides it: same answers. **`approve` must not gate on `allowedResolutions` here.** Refusing those cells is #443's change. Pin the disagreement (below) so #443 starts from evidence.

So:
- **`answer()`**: once `status === 'blocked'` is established (keep the first refusal and its message, `ask.ts:129-131`), the wait is `waitsOf(events).at(-1)`. Replace `life.runId !== null` (`:132`) with `!allowedResolutions(wait.reason).includes('AnswerQuestion')`. Only `OwnQuestion` offers it (`wait.ts:226-227`), and only a `Question` hold has a null `runId` (`work-item.ts:342`), so the two agree. The message's run id comes from `wait.reason.run.runId`, and the question check (`:138`) compares against `wait.reason.question` once narrowed to `OwnQuestion`. Keep the detail strings byte-identical.
- **`requeueHolding`**: `withdrawn = wait.reason._tag === 'OwnQuestion'` replaces `item.lifecycle.runId === null` (`approve.ts:538`). Do not add an `allowedResolutions(...).includes('Requeue')` refusal: every row offers `Requeue`, so it would be unreachable code.
- **`approveHolding`**: no gate change. Only the writes move (Decision 1).
- **`recommendedResolution`** has nothing to choose here. No handler prefills a default, so do not invent a use for it (`doc/design/481.md`'s rule).

**`waitsOf` over the item stream alone is enough for both uses.** `reasonFromHold`'s `Question → OwnQuestion` arm reads no other event (`read-model.ts:984-985`), and every other hold maps to some non-`OwnQuestion` tag whatever its lookups find. Do not add a run-stream read to `answer`/`requeue`.

## Decision 3: `attempts.ts` reads one event at a time, never `stepOutcomesOf`

`stepOutcomesOf` would lose the case `attempts.ts` was written for. It skips any action with no recipe entry and no `STEP_DEFAULTS` row (`read-model.ts:166,676-680`), and `StepsResolved` is only appended at `implement`'s dispatch (`read-model.ts:89-91`). A `prepared:install` refusal, #82's own example (`attempts.ts:8-10`), would therefore vanish. #481 refused `stepOutcomesOf` for the same reasons (`read-model.ts:1440-1461`), so follow its per-event shape:

- **`priorAttempts`'s wait** → `cardFactOf(event)` (`read-model.ts:1395-1408`, already exported, #480's). On `WaitStarted`, the run id is `'run' in fact.reason ? fact.reason.run.runId : null` and the text is `fact.card.question`, which is the same `legacyColumns(d.hold).question` read today.
- **Everything else** → a new **`attemptFactOf(event)`** in `read-model.ts`, below `findingsRaisedOf`:
  - `RepairRequested|RepairDeclined` → `{ _tag: 'RepairRefused', runId, reason, detail }`. Move the *"Retired, and still read for ever"* comment (`attempts.ts:191-196`) with it.
  - `StepStarted` → `{ _tag: 'StepStarted', key: \`${step}:${action}\` }`. The name is kept, but at #464 it becomes one per step, so it belongs where #464 will look.
  - `StepPassed|StepWaived|StepNeverRan|StepDidNotFinish|StepAsked|StepFailed` → `{ _tag: 'StepEnded', key, refused }`. `refused` is `{ evidence, findings }` for `StepFailed` (including `unreadable`) and `null` for the rest.
  - **`ApprovalRequested` answers `null`.** Today `attemptOutcome` ignores it, so an `'unfixed'` request after a red build leaves the build's evidence standing.

`attemptOutcome` keeps its loop and its `findingsAppended(...)` call. Only the `case` labels become `fact._tag`. Remove `legacyColumns` from the imports.

## The pins, committed before any `src` change

**Commit 1 adds `export` to `approveHolding` (`approve.ts:190`) and `requeueHolding` (`:517`) and changes nothing else.** `approve()`/`requeue()` take `createFileLocker()` (`approve.ts:62`), which is the filesystem, so by 0060 §1 they cannot be unit-tested. `index.ts:83` lists its names explicitly, so nothing new leaks out. **`packages/conductor/unit/wait-handlers-answer-as-today.test.ts`** uses `createMemoryEventStore()` and builders from `@lingtai/domain/test/events` only. Assert whole results with `toEqual`, `detail` strings included. Assert what was written through `waitsOf`, `reduceWorkItem(...).answers` and `cardFactOf(...).card`, **never through type names**, so #464 leaves the file alone. The header should say: a red pin means the handler changed, so fix the handler and never edit the pin.

- `ask`: empty question; not in backlog; success, with the wait reading back as `OwnQuestion` and its `card`.
- `answer`: empty; not blocked; blocked by a run (`aClaim` + `aWait` `AgentQuestion`); different question; success, with resolution `AnswerQuestion{choice}` and an `answers` entry with `runId: null`.
