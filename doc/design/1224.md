# Design: #1224 — `rerun-setup` and `ask-again` as rule-chosen transient reruns

## The precedent to copy is `land-again`, not the base-red check

The ticket points at the base-red check (`run-attempt.ts:1574-1611`). That check ends at a person. The shape these two routes need is #1221's `land-again`, which is three pieces:

- **The candidate.** `offerFor` pushes a free candidate only while retries are left (`packages/domain/src/failure/respond.ts:720-729`). When the retries are spent the candidate is *"simply absent, never `unavailable`: a rule's candidate is never shown to a chooser, and the offer is then byte for byte what it was before this existed"*.
- **The reply.** `routeProposal` answers with `{ _tag: 'Selected', candidate: 'land-again', why }` instead of calling `replyFor` (`packages/conductor/src/run-attempt.ts:1621-1636`). The comment there explains why: *"A `Selected` reply, because `routeMove` replays this route and refuses a `Selected` decision paired with anything else."*
- **The move.** `routeNext` returns a next tag, and the `switch (next._tag)` after `record` carries it out (`run-attempt.ts:1776-1785`).

Build both new routes this way. Both are proposal routes, so the offer, the reply and the decision go on the `ProposalRouted` as they do for every route. The board's history and `routeMove` already read that event.

## One next tag for both candidates

Add one `CandidateNext`/`AttemptNext` variant, `RerunStep { step, retry }`, beside `LandAgain` (`packages/domain/src/attempt-next.ts:96-111`, `routing.ts:47-53`). The two candidate ids are `rerun-setup` (step `prepared`) and `ask-again` (step `design` | `review`). Don't add one tag per id: the walk does the same thing for both, and only the wait differs.

The new tag reaches every exhaustive switch. The compiler finds them all, but check each one:

- `spentAfter` (`attempt-next.ts:486`): `transientRetries: next.retry`.
- `destinationOf` (`proposed-route.ts:98-123`): both the `next` arm and the `candidate.id` arm. The destination is `next.step`, or `prepared` / the proposal's `from` by id.
- The reducer's route case (`packages/domain/src/attempt.ts:596-633`). Fold `transientRetries` with `Math.max` exactly as `LandAgain` does. Doing that changes what the reducer folds, so bump the reducer version to 9 in `run-codec.ts:202-203`, with a comment line in the same style as the two above it.
- `routedLine` (`apps/board/src/lib/history.ts:744`). Without a case it throws *"a route formatted as a wait"*. Say `${from} → ${step} — <why>`, as `LandAgain` does.

## The count is durable before anything is spent

Use #1201's way of making it durable, not #1221's `appendRoute`. Before the wait and the redo, `routeProposal` emits `StepRerunInPlace` through `options.emit`, as the crash rerun does (`run-attempt.ts:2108-2117`). Use `rerun: retry`, set `said` to the matched row's words or the raw answer, and set `waitMs`. The route itself goes in the end-of-walk batch like any route. A daemon that dies during the 1–15 minute wait has already spent the retry, through an event the v8 reducer already folds (`attempt.ts:578-581`).

**`StepRerunInPlace`'s legal steps are `[...AGENT_STEPS]` (`events.ts:2790`), and `prepared` is not in that list.** Widen it to `['prepared', ...AGENT_STEPS]` and update the event's doc, which says *"A run an API error cut off"*. That list feeds the generated `doc/events.json`, so regenerate it. The emit goes before the `record` and the switch, so a refused emit holds for a person exactly as a refused `appendRoute` does (`run-attempt.ts:1698-1717`).

## `rerun-setup`

**Classifying the output:**
- Add `platform: 'registry'` to `Seen`, `Classified` and `FailureRow` (`packages/domain/src/failure/classify.ts:20-75`), with kind `transient` and no runtime. Add a `RegistryRow` interface.
- Add the rows after the runtime rows:
  - pnpm: `/\bERR_PNPM_FETCH_50[0234]\b/` and `/\bERR_PNPM_META_FETCH_FAIL\b/`.
  - npm: `/\bnpm (?:ERR!|error) code E50[0234]\b/`. Anchor this on npm's `code` line, not a bare `E503` that could turn up in a test name.
- Add `rerunSetup(output, spent)` in `respond.ts` beside `rerunInPlace` (`respond.ts:558-568`). It returns `{ wait }` from `TRANSIENT_WAITS[spent]`, or null.
- The table generates `doc/design/platform-errors.md`'s recognised section (`failure/doc.ts:2-13`). Run `pnpm docs:errors` and commit the regenerated file.

**In `offerFor`'s `SetupRefused` arm** (`respond.ts:686-691`): push `rerun-setup` before the existing round and restart, only when `rerunSetup(proposal.output, spent.transientRetries ?? 0) !== null`.

**`SandboxRefused` comes first.** `attempt-next.ts:317-333` turns a `SetupRefused` into a `SandboxRefused` when the sandbox refused a host. A registry the sandbox blocked is therefore never this route. That is correct, and it needs no code.

**In the walk:**
- Set `at = 'prepared'` and `rerun = null`, then sleep `TRANSIENT_WAITS[retry - 1]`.
- Pass no `resumedAfter`. The Edges say the step's commands run *"again from the first"*. A `rerun` context with `resumedAfter` would skip the install that succeeded (`packages/actions/src/action.ts:949-951`).
- `prepared` dispatches no agent, so there is no dispatch id to vary.
- Nothing moves `onSha`, `lapStart`, `recheck` or `roundsSpent`.
- Take the wait from the same `options.transientWaits ?? TRANSIENT_WAITS` that `land-again` reads (`run-attempt.ts:1627`), so a test can shorten it, and assert the 1 minute on a `TestClock` as Done-when asks.

## `ask-again`

**It needs loop state that `routeProposal` cannot see.** The crash rerun builds its `rerun` from `visitContext`, `visitedBefore` and `reached.results` (`run-attempt.ts:1912-1914`, `2090-2106`). These are locals of the loop body, while `routeProposal` is a closure defined above the loop (`run-attempt.ts:1545`).

- Pass them in. Add a fifth argument to `routing(...)` at the two call sites (`run-attempt.ts:2030`, `2071`): `{ reached: visitedBefore, context: visitContext, results: reached.results }`.
- When `ask-again` is taken, set the outer `rerun` to the same object the crash path builds, including `briefedWith`'s design and `resumedAfter: results.slice(0, -1)`. Then set `at = proposal.from`, wait nothing, and `continue`.
- The walk's existing `{ ...rerun.context, rerun: transientRetriesSpent }` (`run-attempt.ts:1913`) then gives the agent `rerunId`'s `:rerun:<n>` (`action.ts:1292-1295`). That is the fresh session the Watch out row asks for, and it needs no code of its own.
- Pull the crash path's `rerun` construction into one local function and call it from both places. Don't keep two copies.

**Only `design` and `review`.** `AnswerUnreadable.from` also admits `proposed` and `merge` (`packages/domain/src/proposal.ts:140-144`). But `StepRerunInPlace` is legal only at agent steps, and the walk has no agent to re-dispatch at those two. Offer `ask-again` only when `from` is `design` or `review`; elsewhere today's offer stands.

**"Once per arrival" is walk state, not attempt state.**
- Add `askedAgain?: boolean` to the third argument of `offerFor`. Make it a field on the argument `routeProposal` builds (`run-attempt.ts:1566-1572`), not on `Spent`: the reducer has no use for it, and absent reads as false.
- In `run-attempt.ts`, keep `let askingAgain: Step | null`. Set it when `ask-again` is taken.
- When the next visit consumes `rerun`, give that visit `arrivedAskedAgain = askingAgain === at` and clear `askingAgain`. Clearing it there means a later arrival at the same step, in another round, is asked again once more, as the Watch out row requires.
- The crash rerun sets nothing here. An answer that is unreadable after a crash rerun is still asked again once.

## Edges this decides

- **A continuation from a person's decision** starts with `askingAgain` null. A person's `Requeue`/`Approve` after a second unreadable answer is a new arrival, and that is intended.
- **The judge's own unreadable reply** never reaches here: it is `UnreadableReply` on the judge path, not a `Propose`.
- **Ratchet:** every new piece of IO is inside the existing `Effect.gen`. Add no `async` and no `Effect.run*`.

## Tests

- `packages/domain/unit/routing.test.ts`: the new candidate for each arm. It is present with retries left, absent (not `unavailable`) when they are spent, and absent at `proposed`/`merge` and with `askedAgain: true`.
- `packages/domain/unit/` classify tests: one per registry row, fed the tool's own line, plus a non-match such as `ERR_PNPM_FETCH_404`.
- `packages/conductor/unit/land-again.test.ts` and `run-attempt.test.ts` already drive a rule route through `runAttempt` with a `TestClock`. Put the Done-when walks in a new `rerun-setup.test.ts` beside them, built the same way:
  - Count reviewer dispatches by the dispatch id the stub runtime is handed, and assert the second one ends `:rerun:1`.
  - Assert that `options.judge` is never called.
- `apps/board/unit/history.test.ts`: one line for the new move.

All of this is unit-level. Nothing here needs `pnpm test:integration`.
