# Design note — #635, `doc/from-symphony.md`

## Where it goes and what it touches

This is a docs change that touches four files, and two of them are tests that pin the current list of public pages exactly.

1. **`doc/from-symphony.md`**, the page itself.
2. **`apps/site/src/lib/docs.ts`**, in two places:
   - **`PUBLIC_SLUGS`** (`:67`): add `'from-symphony'` to `['tutorial', 'requirements', 'plugins']`.
   - **`SECTIONS`, the `guides` entry** (`:105`): add `'from-symphony.md'` to its `files`. The ticket leaves this out, and it is required. `servable()` (`:73`) filters `published()`, and `published()` returns only files that some section names (`:271-275`). The comment at `:93` says *"What is published, named rather than swept up … the list is explicit."* If the slug is public but no section names the file, nothing serves it. The index then lists it under `unpublished()` with a GitHub link. Put it after `'requirements.md'`, so the public guides read tutorial → requirements → from-symphony.
3. **`apps/site/unit/page.test.ts:78`**, which asserts `expect(PUBLIC_SLUGS).toEqual(['tutorial', 'requirements', 'plugins'])`. Update the array. Also rename the `it(...)` title at `:72`, which lists the public pages in prose.
4. **`apps/site/unit/docs.test.ts`**: add a case beside `:183` (*publishes the requirements beside the tutorial…*). It should check that `servable()` contains `'from-symphony.md'` and that `resolveHref('tutorial.md', 'from-symphony.md', served$)` gives `'/docs/from-symphony/'`. This unit-level test stands in for "is public and linked".

## Where the link goes

Link from **`doc/requirements.md`**, not from the site chrome or the home page. `page.test.ts:80` asserts that every `/docs/` href in `chrome.tsx` and on the home page is `/docs/tutorial/` or `/docs/plugins/`, so a link there turns the suite red.

Add one sentence to the intro paragraph of `requirements.md` (around `:4`). It is the page for "what does Lingtai need outside itself", and a Symphony user's first question ("does it take Linear?") belongs there. A relative `[…](from-symphony.md)` link is rewritten by `resolveHref` to `/docs/from-symphony/` once the slug is public. Leave the tutorial's ending alone: it is a running walkthrough, and its last section is about GitHub App setup.

## Corrections to the ticket's concept map

Fix these before writing them on a public page. Each is checked against this tree.

- **There is no single recipe `prompt:`.** `prompt:` sits beside an `agent:` at a step. `doc/plugins/agent.md:7`: *"Needs `agent` (`claude-code` or `codex`) and `prompt`."* `:53`: *"Appended to the fixed brief. **Interpolated raw**: `{{issue}}` is not expanded."*
  - The map row and moving-step 2 must say *the `prompt:` beside the `agent:` at `implement:`* (where the implementer is declared), and link `plugins/agent.md`.
  - Don't write "Liquid is not rendered" as a Lingtai-specific gap. Say it the way `doc/reference.md:528` does: *"A recipe's `prompt:` — `{{issue}}` written there reaches the model as five literal characters, and nothing refuses or warns."* That is the trap a person pasting a `WORKFLOW.md` body falls into, so put it in the page's "watch out" spot. Link `reference.md#prompt-placeholder--6`.
  - The ticket and the checks are already in the brief: `reference.md:534-538` (`{{body}}`, `{{checks}}`, `{{failure}}` filled into `prompts/ticket.md`). That is why the Symphony body's `{{ issue.* }}` is redundant, not just unsupported.
- **`agent.max_turns` → `runtime.limits.turns`** is real: `reference.md:313`, default `300`, *"per run"*. Say where the counts differ, and only as far as SPEC.md supports it. Don't assert a Symphony turn count from memory.
- **`codex.command` → `runtime.agent: codex`.** `agent.md:7` names `codex` as a runtime, which supports the row. The row also says "and the tier". Before keeping that, check that "tier" is a word a public reader can follow (`doc/the-pass.html` uses it). If it isn't, cut it.
- **`lingtai now`** exists: `apps/cli/src/commands.ts:113`, usage `lingtai now <project> --issue <n>`, *"ask for one ticket ahead of the queue"*.
  - I found nothing in `packages/conductor/src/` for **"retries after 1h"**. Either find it (its event and constant) or drop the figure and say only that a refused ticket comes back on a later pass and `lingtai now` takes it ahead of the queue.
  - The same applies to **"the recipe is read again on every pass"** and **"`lingtai init` detects the install command"**: cite where each is true, or cut it.
  - The rule from CLAUDE.md ("Name nothing Lingtai lacks as if it shipped") holds just as much for Lingtai's own behaviour.
- **"the daemon's poll, machine-wide"**: if no interval key exists in the recipe or in `config.example.yml`, say *not configurable per project*. Don't imply a setting that doesn't exist.

## The Symphony side

Every Symphony claim gets a link to `https://github.com/openai/symphony/blob/main/SPEC.md`, with a section anchor where SPEC.md has one. Read SPEC.md before writing rather than relying on the ticket's wording. The ticket's states list (Todo → In Progress → Human Review → Merging → Done) and the field names (`tracker.required_labels`, `polling.interval_ms`, `max_retry_backoff_ms`, `hooks.after_create`, `agent.max_concurrent_agents`) are the ticket author's summary.

- **A field SPEC.md doesn't name gets no row.**
- **A behaviour SPEC.md describes differently is written SPEC.md's way.** For example, Symphony's in-memory state and its re-poll on restart.

Write the difference as a tradeoff. Symphony puts the pipeline in the prompt, which keeps it flexible and editable in one file. Lingtai keeps it outside the agent, so the agent can't skip it. Don't call it a defect in Symphony. The page should state what Lingtai gives up: Linear, concurrency, and a pipeline you can edit in prose.

## The page's own shape

Follow `doc/requirements.md`'s register: written for a stranger, with no ADR history and no "since #NNN". Gaps name their ticket: Linear as a source is #340, concurrency is #341. Cite gaps by issue number, never by seq.

Name the no-importer decision in one sentence: the tracker mismatch, and that most of a `WORKFLOW.md` body is pipeline instruction that must not reach the brief. Then give the three manual steps. In step 2, "what to leave out" is the list from the ticket: states, PRs, review comments, landing, and every `{{ }}` / `{% %}`.
