## Design note for #632: an `events.json` release asset and an *Events changed* section

### Where it goes

- **The diff is a new script: `packages/domain/scripts/events-diff.ts`.** It sits beside the generator and imports `type EventsDoc` from `./events.ts` (`packages/domain/scripts/events.ts:243`).
  - It has two pure exports: `diffEvents(old: EventsDoc, next: EventsDoc) → EventChanges` and `renderEventsChanged(...) → string`, which returns markdown.
  - It also has an `import.meta.main` CLI, the same pattern as `events.ts:470`. The CLI reads two paths, the old one possibly absent, and prints the section.
  - `scripts` is already in `packages/domain/tsconfig.json`'s `include`, so `pnpm typecheck`, `fmt:check` and `lint` already reach it.
- **The test is `packages/domain/unit/events-diff.test.ts`.** It uses small hand-built `EventsDoc` fixtures and never reads the real `doc/events.json`. A test built on the real manifest would go red every time an event is added. The real file is `events-json.test.ts`'s concern.
- **The generator gets a `--ref <ref>` flag in `packages/domain/scripts/events.ts`.**
- **The workflow is `.github/workflows/release.yml`, `publish` job only.** The `binary` job does not change.

### `--ref`: the link names the tag, but the lines still come from one commit

Today the CLI takes `sha = git rev-parse HEAD` (`events.ts:478`). That sha is used for two things: every permalink, through `permalink(sha, …)` at `events.ts:419`, and the top-level `sha` field. The `--emit` child receives it as argv (`events.ts:474`).

- **Add `ref?: string` to `generate`.** Links use `ref ?? sha`, and the top-level `sha` stays the commit hash.
  - The top-level `sha` field keeps its meaning: *the commit these lines are true at*.
  - `EventsDoc` gains no field, so the committed `doc/events.json` and the staleness test in `events-json.test.ts` do not change. That test already ignores `definition`, `sites` and the top-level `sha` (`events-json.test.ts:41-44`).
  - Thread `ref` through as an extra argv to the `--emit` child.
- **Refuse a ref that is not HEAD.** With `--ref`, the parent resolves `git rev-parse <ref>^{commit}`. If that is not `HEAD`, it refuses by name, the same way it refuses a dirty tree (`events.ts:484-490`).
  - The links name `<ref>`, but the line numbers are read from `HEAD`. A mismatch would publish links pointing at the wrong lines, and nobody would notice.
  - Use `^{commit}` because a tag may be annotated.
- **The trap: `pnpm events:generate --ref …` does not reach the script.** The root script is `"node packages/domain/scripts/events.ts && oxfmt doc/events.json"` (`package.json:31`), and pnpm appends extra arguments to the end of that line, which here means to `oxfmt`. So the workflow calls `node packages/domain/scripts/events.ts --ref "$GITHUB_REF_NAME"` directly.
  - Do not reshape the pnpm script to make the ticket's wording literally true.
  - The asset does not need oxfmt.

### What the diff reports

Match events by `name`. The categories:

- **added**: in `next`, and either absent from `old` or `retired` in `old`.
  - The second case is an event that can be appended again, which is what a subscriber needs to know. There is no separate *unretired* line.
- **retired**: `retired: false` in `old` and `retired: true` in `next`, **or** present in `old` and absent from `next`.
  - Nothing should delete an event. `RETIRED`'s comment says retiring is *"stop writing them, and keep reading them for ever"* (`packages/domain/src/events.ts:2236-2243`).
  - A deleted event still has to show up here, because it is the worst break of all for a subscriber.
- **schema bumped**: present and not retired in both, with a different `schemaVersion`. Report it as `old → new`.
  - `SCHEMA_VER` is `BUMPED[k] ?? 1` (`events.ts:2232`). A bump is the payload change, and an upcaster comes with it (`events.ts:15`).
- **There is no *renamed* category.** The registry has nothing that says one event became another. `RETIRED` is a plain set (`events.ts:2244`), and nothing pairs an old name with a new one.
  - A rename therefore comes out as one *retired* plus one *added*, and a test pins that.
  - The ticket's *Want* lists "renamed". This is the ticket's own **Watch out** winning: *"A rename is a retire plus an add unless the registry says otherwise."*
  - Do not add a rename map to `@lingtai/domain` in this ticket. If one is wanted, it is its own ticket, and `diffEvents` would then read it from the manifest.
- **Everything else is ignored:** `group`, `stream`, `at`, `summary`, `sites` and `definition`. Links change on every release, and the ticket asks only for what breaks a subscriber.
- **Order is deterministic:** `next`'s order (which is `EVENTS` key order) for added and bumped, then `old`'s order for events removed outright.

### What the notes say

`renderEventsChanged({ previousTag, previous: EventsDoc | null, next })` produces a `## Events changed` heading followed by one of three bodies:

- **`previous === null`**: *"First release with an events manifest."* If `previousTag` is set, add *"(\<tag\> has none)"*.
  - **Every release hits this branch until one has published an `events.json`**, including the first one after this lands. No release asset exists today, because the current `publish` step uploads only `artifacts/*` (`release.yml:155`).
- **The diff is empty**: *"No event changed since \<tag\>."*
- **Otherwise**: one list per non-empty category, with each name in backticks and bumps written as `` `X` 2 → 3 ``.

The unit tests cover these cases:

- added
- retired by flag
- removed outright
- schema bumped
- rename-shaped (retire plus add)
- un-retired, which reads as added
- no previous manifest
- previous tag with no asset
- nothing changed

### The `publish` job

Today the job is checkout, download artifacts, the CLI contract step, checksums, then `gh release create … artifacts/* --notes-file cli-contract.md` (`release.yml:107-155`). It has no Node and no `pnpm install`.

1. **Add the toolchain.** Use `pnpm/action-setup`, `actions/setup-node` with `node-version-file: .node-version`, and `pnpm install --frozen-lockfile`, as the `binary` job does (`release.yml:36-45`).
   - The generator imports `typescript` and symlinks `packages/domain/node_modules` into its snapshot (`events.ts:497-500`).
   - It also runs `.ts` with `import.meta.main`, which needs this Node.
2. **Add an events step after `CLI contract diff` and before `checksums`:**
   - Generate with `--ref`, then copy `doc/events.json` to `artifacts/events.json`.
     - It must go into `artifacts/` before `checksums` so that it lands in `SHA256SUMS`. "Beside" should mean "covered by".
     - The dirty check looks only at `apps` and `packages` (`events.ts:484`), so the downloaded `artifacts/` does not trip it.
   - Find `prev` with the same `git describe … "${{ github.ref_name }}^"` the CLI step uses (`release.yml:122`).
   - Download its asset only if `gh release view "$prev" --json assets --jq '.assets[].name'` lists `events.json`.
     - Do not treat any `gh release download` failure as "no asset". A network error would then publish *first release* on a release that has a predecessor.
     - "Not listed", or "no release for that tag", passes no old path. "Listed but the download failed" fails the step.
   - Run `node packages/domain/scripts/events-diff.ts [old] artifacts/events.json "$prev"` and capture its output to `events-changed.md`.
   - If the old file does not parse as an `EventsDoc` (an object with an `events` array of named entries), fail loudly. It is our own asset.
3. **Assemble the notes from sections.** `--notes-file` takes one file, so the notes become `cat cli-contract.md events-changed.md > release-notes.md`.
   - This is the seam the CLI-manifest ticket uses: each manifest has its own pure diff and renderer, writes its own section file, and joins the `cat`.
   - Do not build a generic multi-manifest abstraction now. `doc/cli.json`'s shape is not `EventsDoc`'s, and the existing CLI step is a plain `git diff` (`release.yml:116-117`, *"doc/cli.json is generated and carries no stamp (#545), so a plain diff … is the change"*).

Keep the shell to the calls listed in step 2. Every decision belongs in `events-diff.ts`, where a unit test can see it.

### What nothing can check before a tag

The workflow runs `publish` only on `refs/tags/v*` (`release.yml:101`). Neither `pnpm test` nor `check.yml` reaches these parts:

- the shell glue
- the `--ref` refusal (it spawns `git`, and 0060 §1 keeps that out of the unit half)
- the `gh release view` probe

What stands in for them at unit level:

- `diffEvents` and `renderEventsChanged`, covering every branch above.
- One assertion in `events-json.test.ts` (or the new file) that `generate({ root, sha, ref: 'v0.0.0' })` writes `/blob/v0.0.0/` in every `definition` and `sites` link and keeps `sha` as given.

The first tagged release is the integration test. Say so in the commit body.

### Edges

- **No previous tag:** `prev` is empty, and the section reads *first release with an events manifest*.
- **Previous tag with no release** (a failed `publish`): same as no asset, and the tag is named.
- **A tag on a commit whose `package.json` was not bumped:** this never reaches `publish`. The `binary` job already refuses it (`release.yml:66-71`).
- **A re-run of a failed `publish`:** `gh release create` fails on the existing release, exactly as it does today. Nothing in this change makes that worse.
- **Pause, drain, two passes at once, or the board:** none of these apply. This is CI only and touches no event and no process.
- **The committed `doc/events.json` is not regenerated by this ticket.** `--ref` is opt-in, and with no flag the output is unchanged.

### Checks

`pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test` reach everything that can be checked. No part of this needs the integration half.
