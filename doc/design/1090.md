# Design note: #1090, the daemon handlers as Effects

The ticket describes the change itself. This note covers the one helper it should reuse, where the helper attaches, and the line in `runCli` where the edit can go wrong.

## Build `daemonHandler` from what `exit.ts` already has

`exit.ts` already does what daemonHandler's try/catch does. `printedBy` (`exit.ts:37-48`, not exported) catches a cause and does three things:
- It passes a `CommandExit` through untouched.
- It passes an interruption through unprinted: *"An interruption is not a failure: nothing is printed for it."*
- It prints anything else with the printer it was given, and fails with `CommandExit(print(err))`.

`orWizardFailed()` (`:53`) is `printedBy(wizardFailed)`. That is the edge rule from the ticket's Shape section, already built and already used by `init` (`cli.ts:129`, `:143`). **Do not write a second `catchCause`.** Export `printedBy`, or a narrow wrapper over it such as `orPrinted(print)`, and then:

- **`daemonHandler(args, run, jsonCommand?)`**: `Effect.sync(applyNoColor-if-asked)`, then `run()`, then `Effect.flatMap(exitWith)`, all piped through one printer:
  - `wizardFailed` when `jsonCommand` is undefined;
  - `(err) => printJsonError(jsonCommand, 'failed', err instanceof Error ? err.message : String(err))` otherwise.
  
  These are the two branches of `cli.ts:1040-1043`, unchanged. Put `exitWith` inside the printed pipe or outside it; it makes no difference, because the printer lets `CommandExit` through. A code of 4 from `START_BOARD_ONLY` becomes `CommandExit` 4 and is never printed.
- **`account lift`**: its body is `lift(() => import('./account-lift.ts'))` and then `yield* liftAccount(…)`, mapped through `exitWith`. Wrap the whole body in `printedBy((err) => { console.error(err instanceof Error ? err.message : String(err)); return 1 })`. That is `.catch`'s text at `cli.ts:1149-1152`, and like `.catch` it also covers a failed import. Pass it to `daemonHandler` as a `run` that already ends in `CommandExit`, or skip `daemonHandler` for this command and apply `--no-color` yourself. Either way, `wizardFailed` must never see this error: it would add the stack under `LINGTAI_DEBUG`.
- **`ceiling raise`**: `ceilingRaise` is `Effect<0 | 1>` with no error channel, so `run` returns `yield* raise.ceilingRaise({…})`. The `parseUsd` refusal returns `2` from `run`, and `exitWith` makes that `CommandExit` 2. Only `ceiling-raise.ts` needs importing now; the `project-pause.ts` import goes with `runEffect`.

`run` has the type `() => Effect.Effect<number, unknown>`. Every `await import(...)` and every `daemon.ts`/`service.ts` call becomes `yield* lift(() => …)`. That is `exit.ts:16`'s `lift`, whose comment explains why bare `tryPromise` is wrong here. (The ticket's Fix row names both; `lift` is the one to use.)

## `withDaemonWriter`

Change its signature (`cli.ts:1059`) to `run: (writer) => Effect.Effect<void, CommandExit>` and its return to `Effect.Effect<void, CommandExit>`. Nothing else changes. `Effect.scoped` closes the writer on failure as well as on success, so a `restart` that exits 3 still releases it. `restartArgs!` is read inside the gen when the command runs, the same as now; `runCli` sets it at `:1513-1522`, before `run(...)` starts.

## `service` verbs

The `let unconfirmed`, `let boardHad` and `let code` locals stay as closure state inside the `Effect.gen`. The `serviceCommand` call becomes `yield* lift(() => serviceCommand(…)).pipe(Effect.ensuring(Effect.sync(() => steps.end())))`, with `ensuring` on that call only, not on the whole body. That keeps today's order: the spinner ends before the closing line is chosen and printed (`:1250-1264`), and on a throw it ends before `wizardFailed` prints. If `ensuring` wraps the whole body, `steps.end()` runs after the closing line. That changes the output that `daemon-cli.test.ts:116-158` pins.

## `runCli`: the one line that can double or drop the `usage` document

Today's condition (`cli.ts:1550`) is `code !== 0 && json && handlerCode === 0 && !handlerExited`. The `handlerCode === 0` part existed only for `daemonHandler` and the bare `ceiling`/`account`, which reported failure by setting `handlerCode` and then succeeding. After this change, all of them fail with `CommandExit`, so `handlerExited` is set. The rule becomes:

```
code !== 0 && json && !handlerExited
```

Delete `handlerCode = 0` (`:1534`) and `Effect.map(() => handlerCode)` (`:1541`). The success value becomes `Effect.as(0)`. Keep the `catchTag('CommandExit')` → `catchCause(→ 1)` order as it is.

Check the result against these:
- `service status --json` that fails: the `failed` document comes from the printer, then `CommandExit` 1, so `handlerExited` is set and no `usage` document is added (`daemon-cli.test.ts:213-214`).
- `board stop --json` (`board-cli.test.ts:95`) never reaches a handler, so `usage` is still printed.

An interrupted handler reaches `catchCause` → 1 with `handlerExited` false. Under `--json` it would get a `usage` document, exactly as it does today. Leave that alone; it is not this ticket's.

## What checks it

Everything here is unit-level and runs in `pnpm test`; nothing depends on the integration half. The two new tests the ticket asks for go through `runCli` with `vi.mock('./ceiling-raise.ts')` and `vi.mock('./account-lift.ts')`, following the pattern of `daemon-cli.test.ts:14-40`.

When `runLiftAccount` is gone, `account-lift.ts`'s `import { …, runEffect }` from `project-pause.ts` (`account-lift.ts:11`) loses its only use. Drop `runEffect` from that import and keep `type Outcome` if something still uses it, or `pnpm lint` goes red.

Lower the baseline in the same commit: 364 → 356 for `async`, with `run` staying at 6. The only `async` left in `cli.ts` should be `runCli`'s own (`:1453`).
