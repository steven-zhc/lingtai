# #1252: how the satisfied ending is built

## What #1251 already did, and what is left

Several of the ticket's own Evidence lines are out of date. #1251 got there first in five places:

- `StandingState` already has `satisfied`, and `STATE_WORD.satisfied` is `'already satisfied'` (`apps/board/src/lib/task.ts:428`, `:442`). `standingOf` already passes `life.status` through (`task.ts:891`).
- `RESOLUTION_COPY.ConfirmSatisfied` exists (`apps/board/src/lib/resolution-copy.ts:21`).
- `allowedResolutions(SatisfiedUnconfirmed)` returns the four moves (`packages/domain/src/wait.ts:352-353`).
- `triageStatus` returns `NotNeeded` for this wait (`wait.ts:1167-1168`).
- `ticket_report` already writes `outcome = 'satisfied'` (`packages/projector/src/ticket-report.ts:313-314`).

What is left is the reading side: deciding what to draw from those facts. Seven gaps remain:

1. **The board cannot tell a satisfied ticket from a landed one.** `taskStateOf` maps `satisfied → 'landed'`, and says so: *"Beside `landed` until the board draws its own ending (#1252)"* (`packages/projector/src/task-view.ts:299-301`).
2. **The home rail draws the bug the mock rules out.** `RailCandidate.over` is `t.state === 'landed'` (`apps/board/src/lib/board.ts:1603`). So today a satisfied ticket is `over`. Every planned step after `review` recorded nothing, so `stateOf` returns `never-ran`, the red hatch (`apps/board/src/lib/progress.ts:340`).
3. **The task page draws those same steps as `pending`.** It passes `landed = standing.state === 'landed'` (`task.ts:1811`), which is false for a satisfied ticket.
4. **`/landed` reads landed rows only:** `where = [\`outcome = 'landed'\`]` (`packages/projector/src/postgres.ts:541`, `sqlite.ts:809`).
5. **`whoWaits` has no `satisfied` branch.** It falls to `default` and prints `'queued'` (`task.ts:809-830`).
6. **The confirm wait recommends nothing.** `defaultResolution` returns `null` for `SatisfiedUnconfirmed` (`wait.ts:770-777`). `recommendedResolution`'s `NotNeeded` branch is `toDefault()` (`wait.ts:861-866`).
7. **The badge text is hard-coded.** `ResolutionCard` prints the literal `Triage recommended` (`apps/board/src/app/triage-picks.tsx:223`).

## Decisions

### 1. `satisfied` becomes a `TaskState`; `task_view` gets no new column

Add `'satisfied'` to `LABEL_STATES` (`packages/domain/src/streams.ts:167`), and make `taskStateOf` return it. The other reading was to keep the state `landed` and add a column to `task_view`. That is a schema change, and it lets a caller who checks `state === 'landed'` go on being wrong without a type error. With a new state, `tsc` finds every exhaustive site. These are the ones known now:

- **`COLUMN_OF`** (`board.ts:657`): `satisfied: 'landed'`. Give it a comment like `closed`'s: the row says which ending it was.
- **`labelsFor`** (`packages/conductor/src/labels.ts:33`): the `default` arm already returns `[]`, which is right.
- **`stateInk`** (`packages/env/src/colour.ts:142`): spells `LABEL_STATES` out by hand, and its test asserts the two lists agree. Use `landed`'s ink, with no new colour token.
- **`apps/cli/src/status.ts:403`**: a record over the state, so it needs the key and the word `satisfied`. Do nothing else in the CLI; that is out of scope.
- **`BoardCard`** (`board.ts:266`, `:857`): add `satisfied: t.state === 'satisfied'` beside `closed`.

`converge.ts:243` reads `TicketStatus`, not `TaskState`, so it is untouched.

**Rows already projected stay `landed` until somebody runs `lingtai projection rebuild task_view`.** That is a replay, not a repair, and the PR should say so. Nothing breaks in between: such a row draws as `landed`, exactly as it does today.

### 2. The rail is told the ending, not a boolean

`progressOf`'s `over` (`progress.ts:377`) and `RailCandidate.over` become `ending: 'landed' | 'satisfied' | null`.

- **`landed`** keeps today's rule (`progress.ts:340`).
- **`satisfied`**: a non-`end` step with nothing recorded returns `skipped`. The dashed outline already exists (`rail.tsx:60`). The cell fallback at `progress.ts:420` must pass `skipped` through too, not `pending`.
- **The callers** are `board.ts:1603` (it reads `t.state`, so `satisfied` gives `ending: 'satisfied'`) and `task.ts:1811-1814`.

`review` did run on this path (the check, `run-attempt.ts:2482-2496`), so it draws from its record like any step.

### 3. Items and the ender are read off the ticket stream, not the lifecycle

The satisfied lifecycle carries only `baseSha` and `bodyVersion` (`packages/domain/src/ticket.ts:177`, `:760-767`). Read `items` and the event's `actor` from the last `TicketSatisfied` in the events `loadTask` already holds; `history.ts:292` already formats that event.

**Do not widen `TicketLifecycle`.** It is the snapshot's reducer shape (0124), and `ticket_report` decodes the stored `ticket_state` (`ticket-report.ts:213`).

**Who ended it is decided by the event's `actor`:**

- **`'conductor'`** (`ticket.ts:1312`) is the split parent. It reads *ended by the system — a split parent*.
- **Anything else** is a person's `ConfirmSatisfied` (`ticket.ts:1344`). It reads *confirmed by `<by>` … on `<sha>`*. Take `by` and `onSha` from the resolved wait, worded as `/landed`'s `ld-decision` already words them (`apps/board/src/app/landed/view.tsx:109-116`, #1231).

### 4. The base name comes from the project's registered base

`TicketSatisfied` carries no base branch name, only a sha, so `whoWaits` takes the base name as a parameter.

- **Where it comes from:** the project's configured base (`ProjectConfigured.base`, `packages/domain/src/events.ts:2376`, which is nullable), read wherever `loadTask` already reads the project.
- **What it says:** *found already done on `<base>` at `<sha7>`*.
- **If the base is null or unreadable:** *found already done at `<sha7>`*. Never write `main` as a guess.

### 5. The evidence list is one component, used twice

Build one list, used by the task page's ending and by the confirm wait's third block, as the mock says ("列表组件是一个"). Each row has four parts:

- **The item text.**
- **A `met` mark.** It is always `met`: a `TicketSatisfied` or a `SatisfiedUnconfirmed` exists only when every item cleared.
- **A source tag.** It is the first `#N` in the evidence that is one of `TicketState.split.children`'s numbers. Otherwise it is the base name. Make it a pure function with its own unit test. That is how the mock's `#1313` / `main` are derived without inventing a field.
- **The evidence.** Empty evidence draws `.sevidence.snone` *no evidence recorded* (the class exists, `standing.tsx:2044`), and is never hidden.

### 6. The confirm wait shows `reading` once, not per item

`SatisfiedUnconfirmed.reading` is one string, the reviewer's summary (`wait.ts:110`; it is filled at `run-attempt.ts:2493-2495`). The mock draws a per-item *review: met — …* sentence, and that data does not exist. Recording it would change the wait's shape, which is #1251's and out of scope.

So the third block is:

- `reading`, as one paragraph;
- then the shared list from decision 5.

Name this difference in the PR's screenshot comparison. Do not fill the per-item sentences in.

### 7. Recommendation and copy

- **The recommendation:** `defaultResolution(SatisfiedUnconfirmed)` returns `'ConfirmSatisfied'` (`wait.ts:770`). Because triage is `NotNeeded`, `recommendedResolution` then picks it, and the home card's recommended move (`board.ts:779`) follows. Pin it with a domain unit test.
- **The badge:** `ResolutionCard`'s `recommended: boolean` becomes a badge string or `null`. Triage callers pass `Triage recommended`; this wait passes `Review found every item met`.
- **The mock's titles** (*Confirm it is already done*, *Start over from base*, *Add to the ticket and start over*) go in through `resolutionCopyFor`'s per-reason override (`resolution-copy.ts:51-60` is the pattern), keyed on `SatisfiedUnconfirmed`. **Do not edit the shared `RESOLUTION_COPY` titles**, because every other wait reads them.
- **The consequence sentences stay what the code makes true.** The mock's *"the issue is closed with each item's evidence"* goes in only if the agent finds the end action that does it.
- **Card order** follows the mock (Confirm first). `allowedResolutions`' order in the domain stays as it is.

### 8. Where the satisfied ending appears

**Landed row** (`apps/board/src/app/page.tsx:522`):

- `card.satisfied ? 'satisfied' : card.closed ? 'closed' : null`, in closed's position.
- `landedCount` (`footer.tsx:19`, `!c.closed`) already counts a satisfied card. The work is a test that proves it, not a code change.

**Attempt row's landing line:**

- Add a satisfied variant beside `landingLineOf`: *satisfied at `<sha7>` · build skipped · review ✓ · nothing to land*.
- Pick it at `task.ts:1824-1827` when `life.status === 'satisfied'`.

**`/landed`:**

- The filter becomes `outcome in ('landed','satisfied')` in both stores.
- `TicketReportRow` gains `satisfiedAt`, read as `state.lifecycle.status === 'satisfied' ? state.lifecycle.baseSha : null`, mirroring `mergeCommit` (`ticket-report.ts:231`). That needs no new column and no `ticket_report` rebuild.
- The card shows:
  - the headline *Found already done on … at …*;
  - the facts line *satisfied at `<sha7>`*;
  - the checked sha as the link;
  - grey `.ld-sq` squares with *nothing changed*.
- `Notes` draws the system-ended `ld-decision` line when the ticket was split. Today it draws only waits with a resolution (`view.tsx:104`).

**Leave `queued-estimate.ts:34`'s `outcome === 'landed'` alone.** A satisfied ticket has no diff to estimate from.

## Edges this decides

- **A stale wait page** that resolves after the ending is refused by its `waitId`. That refusal is `confirmSatisfiedTransition`'s (`ticket.ts:1317-1344`), so the page builds nothing new for it.
- **Running daemons and boards hold old code.** A board that has not restarted keeps drawing `landed`. A daemon that has not restarted keeps projecting `landed` until it restarts and `task_view` is rebuilt (see decision 1).
