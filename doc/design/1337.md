Ticket #1337's work divides into four seams in code that already exists. Each section below names a seam, where it is and the decision to make there. The ticket's Fix list is not repeated.

## 1. How a step records its own event: one append, not two

`walkPr` records every `done` as a generic `PrStepDone { step, headSha }` (`packages/conductor/src/pr.ts:205`). The PR state's `steps` is built only from `PrStepDone` (`packages/domain/src/pr.ts:102-106`). The ticket adds `PrPushed`, `PrDraftOpened` and `PrOpened` as events of their own.

**Do not append `PrStepDone` and then the specific event.** If the process dies between the two appends, the step is recorded as done but the fact that proves it is missing. A pr-fix pass would then read `lastPushed` as stale.

- **Shape:** `StepAnswer`'s `done` variant (`pr.ts:57-65`) gains an optional `record: ToAppend<…>`. When `record` is present, `walkPr` appends it in place of `PrStepDone`.
- **Reducer:** `reducePrEvent` folds `PrPushed` into `steps` as `{ step: 'push', headSha }`, and `PrDraftOpened` as `{ step: 'open', headSha: state.target }`. These follow the same rule as the `PrStepDone` case: no duplicate, `waiting` goes back to `in-progress`, and `wait` is cleared.
- **Then `steps` stays the one source** for `prStepRows` (`pr.ts:215-220`) and for `lingtai pr`'s `stepLines` (`apps/cli/src/pr.ts:58-62`).

Two new fields **must not be reset by `PrInProgress`**. That case lists the fields it resets (`domain/src/pr.ts:86-99`). Keep both new fields off that list.

- **`lastPushed`** is set from `PrPushed.headSha`.
- **`host: { number, nodeId, url } | null`** is set from `PrDraftOpened`.

The reason is the pr-fix pass. Its `PrInProgress` starts `steps` again from empty (`pr.ts:40`, *"a later pass through In progress starts empty"*). Without these two fields, `push` would lose the head it has to fast-forward from, and `open` would lose the PR it must not open a second time. On that pass, `open` answers from `state.host`: it makes no `GET` and no `POST` and returns `PrDraftOpened { found: 'existing' }`.

`PrOpened { host: 'none' }` sets `status: 'in-review'`. `walkPr` already stops on any status other than `in-progress` (`pr.ts:179`), so on a non-GitHub remote the later steps (`ci`, `summary`, `ready`) never run. That is what *unfollowed* means, and nothing else is needed to get it.

## 2. What the steps are given: today's ports cannot push, and cannot reach a non-GitHub remote

`livePrPorts` (`apps/cli/src/pr-ports.ts`) has three gaps.

- **`git` runs with no token.** It calls `gitEffect([...args], { cwd: mirrorPathFor(project) })` (`pr-ports.ts:57`). `fetch` passes `token: () => client.token()` only to `ensureMirrorEffect` (`:49`). An `ls-remote` or `push` on a private GitHub repository through `ports.git` therefore fails to authenticate.
  - **Fix:** add a `remote(project, args)` port that runs `git` in the mirror with the same token source as `fetch`.
  - Keep `git` for reads that stay local (`merge-base`, `cat-file -e`).
  - With no owner, the token is absent and `git` plants nothing. That is `ownerless.ts:43`'s rule: *"`remote` with no token — `git()` plants no `GIT_CONFIG_*`"*.
- **`fetch` refuses every project with no owner.** It reads *"has no GitHub owner on record: the mirror cannot be fetched"* (`pr-ports.ts:41-43`). It also never passes `remote`, so the mirror always clones `https://github.com/<owner>/<repo>.git` (`worktree.ts:120`).
  - **Fix:** resolve the recipe and pass `remote: remoteOf(recipe)` whenever the recipe names one, as `live.ts:50` does for a pass. Refuse only when there is neither an owner nor a `repo.remote`.
  - **Without this, the local-remote checkbox in Done when cannot be reached:** a local-remote PR is never frozen in the first place.
- **The host is a recipe fact.** It is `'github'` exactly when `remoteOf(recipe) === null` (`packages/recipe/src/settings.ts:378`) and the project has an owner. Anything else is `'none'`, including a `github.com` URL written into `repo.remote`; the ticket's Out of scope says so.
  - Compute it once, in a small pure helper in `packages/conductor/src/pr.ts`, so that `open` and `lingtai pr` agree.
- **Two more ports, both Effects:**
  - `github(project): Effect<GitHub, Error>` — the Effect face, `client.ts:201`.
  - `facts(project, tickets)` — each ticket's open-or-closed state and its spend, used by the description.

  Unit tests hand in fakes of both, so no unit test reaches the network.

## 3. The lane must be the same object as the conductor's

`landingLane` is a module singleton (`landing-lane.ts:102`). `conduct.ts:3967` uses `options.lane ?? landingLane`. The lane orders only callers inside one process (`landing-lane.ts:10`, *"In process, because a conductor is one process holding the lock"*).

- **Add `lane?: LandingLane` to `PrPorts`, defaulting to the same `landingLane` import.** Never call `createLandingLane()` in `pr-ports.ts`. A second instance would give the push its own lane, and it would no longer be ordered against #1341's pr-fix landing.
- **Unit tests** pass one `createLandingLane()` to both the PR step and a fake pass. That is how the `MergeLaneWaited { behind: { pr } }` checkbox is tested.
- **Every `servePr` caller holds the conductor lock already:** the daemon (`apps/cli/src/daemon.ts:679`) and `lingtai run` (`run.ts:340`). `lingtai pr` only appends a request and waits (`apps/cli/src/pr.ts:35-44`). Keep it that way. A push from the CLI process would happen outside the lane.

**The union reaches one reader that throws.** `apps/board/src/lib/history.ts:465-467` does `if (!behind?.issue) throw new Error('no behind')`. A stored `{ pr }` holder would break the task page's history at that row.

- Branch on `'pr' in behind` and render *behind PR `<n>`*, with `n` parsed from the stream id via `parsePrStream`.
- `packages/domain/src/attempt.ts:733` reads only the event's `at`, so it needs no change.
- Add a `{ pr }` fixture to `packages/domain/test/histories.ts` so the board's catalogue test covers the new form.
- `onWait` for a PR holder appends nothing, as the ticket says. It is a no-op hook, not a missing one.

## 4. The description: compute the facts once, render purely, store nothing

- **`prDescription` in `packages/domain/src/pr-description.ts` stays pure.** It takes `{ title, summary, tickets: [{ ticket, title, mergeCommit, open: boolean | null, spend: number | null }] }`.
  - The sections are a `readonly` array of `(pr, facts) => string | null`, joined in order. Section order matters for the *Evidence* groundwork, so this is the shape.
  - `open: null` (unread) renders `Closes #n`. `spend: null` renders as unknown; never `$0`.
  - A ticket is a GitHub ticket by the same id test the rest of the PR code uses for `tickets[].ticket`. Reuse it; do not write a second parser.
- **One Effect, `describePr(ports, project, n)`, in `packages/conductor/src/pr.ts`,** reads the state and `ports.facts` and calls `prDescription`.
  - `open` calls it right before the `POST`.
  - `lingtai pr` calls it when `host` is `'none'`. Extend `PrWorld` (`apps/cli/src/pr.ts:25-33`) with what `describePr` needs, rather than building the description a second way in the CLI.
- **Nothing stores the body.** #1318 owns pushing an edited one.

## Decisions the ticket leaves to the implementation

- **Match the exact ref in our own parser, not in git.** Pass `refs/heads/<prBranch>` to `ls-remote`, then keep only the line whose second tab-separated field equals that ref exactly.
  - The `-pr-10` test feeds the fake both lines.
  - On GitHub's side, `findOpenPull` filters the `head.ref` of each returned pull to `=== prBranch`. `?head=` is GitHub's filter, and the ticket's Watch out row already distrusts its string matching (`client.ts:230-234`).
- **"A failure that is not the person's"** is `GitHubFailed` with status 0 or ≥ 500, or a rate limit. Read `GitHubFailed`'s own fields; do not parse message text.
  - A `422` is `draft-unsupported` only when GitHub's error text names drafts. Any other `422` fails the effect and records nothing, so it is served again. It is never a silent `opened`.
  - **What settles which `422` GitHub sends:** the first live run's `PrWaiting.detail`. Quote the response body into `detail`.
- **A lost push uses `integrate.ts`'s rule, not its code.** That code is `integrate`'s own push to `base` (`integrate.ts:615-650`). For the PR branch, after a failed push:
  1. `ls-remote` again.
  2. Branch at `target` → `PrPushed { found: 'pushed' }`.
  3. Anything else → fail and record nothing, so it is served again.

  Never push blind a second time (#1125).
- **Never push `branch.main` (0130 §7).** The push's refspec is built from `state.prBranch` alone. The test asserts that every `push` argv the fake git saw ends in `:refs/heads/<prBranch>`. That is stronger than "no push names main", and the ticket's checkbox follows from it.

## Checks

Every checkbox is unit-level: a memory store, a fake git port, a fake `GitHub` face and a shared `createLandingLane()`. None of them needs `pnpm test:integration`. The real `git push` and the real `POST /pulls` are first exercised after the merge, and the log settles them.

- `PrPushed.found` and `PrDraftOpened.found` say whether the look took the place of the act.
- `PrWaiting.reason` and `detail` carry GitHub's own answer.

`doc/events.json` and `doc/reference.md` are generated: regenerate them, never edit them by hand.

None of this contradicts an accepted ADR: 0122 §3 already names the `{ pr }` holder, and 0130 §5 and §7 are what this ticket builds.
