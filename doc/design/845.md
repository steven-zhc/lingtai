# Design note: #845, `note` comes from the transition, not the event

## Where it starts from

The line numbers in the ticket are older than the tree. #834 and #844 already moved every `note` write into three places in `packages/projector/src/task-view.ts`:

- **Ticket half:** `noteOf(event, after, lifecycleMoved)` (`:365-397`). It is a `switch (event.type)` and it is called from `applyTicketEvent` (`:702`). It sits beside two special cases in `touched` (`:713-717`): `releases`, and `DispatchRefused && status !== 'blocked'`.
- **Run half:** `runNoteOf(event)` (`:636-651`). Its comment says *"The note stays per event until #845"*. It reads `RunAwaitingInput` directly and the rest through `cardFactOf`. It is called from `applyRunEvent` (`:676`).
- **Integration stream:** the branch in `apply` (`:257-264`).

So the change is mostly local. Replace those two functions with state comparisons, and delete the integration branch.

## Shape

**Two exported functions in `task-view.ts`:**

- `ticketNoteOf(before: TicketState, after: TicketState)`
- `runNoteOf(before: RunState, after: RunState)`

Neither takes an `Envelope`. That is the property the ticket's *"no event `case` writes `note`"* is really asking for.

The ticket's names are taken: `noteOf` and `runNoteOf` already exist with event signatures. Delete both, and do not overload them.

**The return type is `{ value: string | null } | null`, the wrapper `noteOf` returns today.** The ticket says these functions return "the sentence, or `null` for no transition". But two rows of its table write `null` on purpose: a claim, and a resolution back to `backlog`. A bare `string | null` cannot say *write null* and *leave it* apart. `null` means no transition. `{ value: null }` means clear it.

**Ticket order.** The first match wins. The order matters because one reduce can make several changes at once.

1. **A claim was released.** Some index `i` has `after.claims[i].ended?.kind === 'released'`, and `after.claims[i].ended` differs by value from `before.claims[i]?.ended`. Write that claim's `reason`.
   - This goes first because `TicketReleased` also moves the lifecycle to `backlog` (`packages/domain/src/ticket.ts:561-567`), and the release must not read as rule 3's `null`.
   - It also covers the Requeue pair. `WaitStarted` set the claim to `{kind:'asked'}` (`ticket.ts:578-581`). The release then moves `asked → released` on a `backlog → backlog` lifecycle.
2. **The lifecycle changed by value** (`JSON.stringify`, as `:701` does now). Switch on `after.lifecycle.status`:
   - `blocked`: `waitWords(l.reason, { branch: agentBranchOf(after.externalRef ?? ''), base: '', findings: [] }).line`.
     - Use `''` when `externalRef` is null. That matches `waitBranchOf` (`read-model.ts:36-39`) and the `answers` line in `ticket.ts:699-703`.
     - `blocked → blocked` on a new `waitId` falls here, because the lifecycle is compared by value.
   - `closed`: `l.reason`.
   - `landed`: `l.mergeCommit`.
   - `approved`: if `l.grantRef !== undefined`, *"fix round granted — continues once a conductor is free"*; otherwise *"approved — continues once a conductor is free"*.
   - `claimed`: `{ value: null }`.
   - `backlog`: `{ value: null }`. Rule 1 has already ruled out a release, so this is a `WaitResolved`. It includes the `block === null` fallthrough at `ticket.ts:688-707`, which today's `lifecycleMoved` also clears.
3. **`after.dispatchRefusals.length > before.dispatchRefusals.length`, and `after.lifecycle.status !== 'blocked'`.** Write `needs <tier>; <runtime> is missing <…>` from `after.dispatchRefusals.at(-1)`.
   - This keeps today's behaviour on a `closed` or `landed` ticket: `:714-717` touches there too, and the ticket asks for no change.
4. Otherwise, `null`.

`Close` needs no rule. `WaitResolved{Close}` leaves the lifecycle as it was (`ticket.ts:684-686`), so it is simply not a transition. A `closed` ticket absorbs every lifecycle event (`:449-451`), so no transition happens after close except rule 3.

**Run order:**

1. **The lifecycle changed by value**:
   - to `awaiting-input`: `l.prompt`.
   - to `awaiting-approval`: `l.question`.
   - A second `RunAwaitingInput` with a new prompt, or a re-request on a new `onSha`, is a change by value.
2. **`after.roundsOpened.length` grew.** Write `fixing round n` or `fixing round n: k finding(s)`, where:
   - `n = after.roundsOpened.at(-1)`;
   - `k` is `after.route.offer.proposal.findings.length` when `proposal._tag === 'ReviewFindings'`, else 0.
   - `applyRun` sets `route` in the same reduce (`run.ts:486-496`). These are the words from `read-model.ts:182-184`, moved here before that file loses them.
3. **`after.failure` set or changed by value.** Write `` `${kind}: ${detail}` ``.
   - Read `failure`, not the lifecycle: `prepare-failed` is a lifecycle with no `RunFailed`, and it writes nothing today (`run.ts:75-81`).
   - `RunFailed` sets the lifecycle as well (`run.ts:457-464`). That is why the lifecycle switch in rule 1 must return `null` for `failed`, so evaluation reaches this rule.

No reduce sets both `awaiting-*` and a round, so the order between them is moot. Keep it anyway, so the function is total.

**The callers.**

- **`applyTicketEvent`.** Compute `ticketNoteOf(before, after)`.
  - When the row is created (`:703-710`), keep `entry.note = note?.value ?? null`.
  - Otherwise `touched` becomes `JSON.stringify(was) !== JSON.stringify(now) || note !== null`. The `releases` and `DispatchRefused` special cases go: the transition is now what makes them touch.
  - Drop `lifecycleMoved`.
- **`applyRunEvent`.** Keep `const before = entry.run` before `applyRun`, then call `runNoteOf(before, entry.run)`.
  - Write the note only when `task.ticket.runs.at(-1) === runId`. Today it writes for any run linked to the task (`:676`), and the ticket narrows that.
  - Touch on `note !== null` or a change in the columns, as now.
- **`apply`.** Delete the `IntegrationRefused`/`IntegrationSucceeded` branch. Those events then fall through and touch nothing.

## Decisions the ticket left open

- **Releasing the same claim twice with the same reason now writes nothing.** Today `:289` writes it again. A claim's `ended` only becomes `released` again after a `WaitStarted` set it to `asked` (`ticket.ts:578`). A continuation does not add a claim (`ticket.ts:504`), and only `approved` leads to one. So a second identical `TicketReleased` with nothing in between is the only case, and it writes the same value again. I accept that and do not add a rule for it.
- **A `TicketReleased` whose `runId` has no claim writes nothing.** `endClaim` maps no entry. Today it writes the reason. This needs a release for a run that was never claimed, which no appender I found writes. The pin will show whether any fixture has one. If it does, name the row in the pin's comment rather than adding a rule.
- **A second identical `RunAwaitingInput`, signoff request or `RunFailed` writes nothing and no longer moves `updated_seq`.** The value is the same, so the only visible effect is the card's age.
- **The `updated_seq` changes go in the pin's comment.** Expect them on any row whose last event was an `Integration*`, or one of the identical repeats above. The comment already does this for #834's single `28 -> 27` (`task-view-rebuild.test.ts:6-12`).
