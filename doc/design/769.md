# Design note: #769, a command for every wait

Two of the ticket's assumptions are out of date in this tree. #763 and #766 have both landed, so the ticket is not blocked; it replaces code that already exists. And the start line cannot call `waitMoves`, because the pass hands it the reason's name and not the reason.

## What is already here

- **`waitCommand` exists, and its name is taken.** `apps/cli/src/status.ts:627-631` exports `waitCommand(project, ref, reason: string)`. It returns `approve` for `SignoffRequired`, `answer` for `OwnQuestion`, and `'decide on the board'` for everything else (`:630`). There are two callers: `renderStatus` (`status.ts:610`) and #766's `endingLine` (`apps/cli/src/conduct.ts:641`, which imports it at `:57`).
  - Move it to the new `apps/cli/src/wait-command.ts` with the ticket's signature.
  - Delete it from `status.ts`.
  - Point the import in `conduct.ts:57` at the new file.
  - No test calls it directly: `git grep waitCommand -- '*.test.ts'` finds nothing.
- **#744's `BaseRed` is already ranked.** `defaultResolution` returns `Requeue` when `reason.because._tag === 'BaseRed'` (`packages/domain/src/wait.ts:630`). `waitMoves` gets it through `recommendedResolution` with no extra code. Its test row is a plain fixture.

## The decision the ticket misses: the start line has only a tag

`endingLine` passes `summary?.wait ?? ''` (`conduct.ts:641`). `PassSummary.wait` is declared `wait?: string` (`packages/conductor/src/conduct.ts:533-534`) and filled with `summaryOf(reason._tag)` (`:4735`).

`waitMoves` needs the whole `WaitReason`, and a tag is not enough:
- `allowedResolutions` reads `reason.run.unpushed` (`wait.ts:457`).
- `grantCriterion` reads the proposal's `output`, `findings` and `said` (`wait.ts:366-397`).
- Which table row applies depends on `ProposedEscalated.proposal._tag` (`wait.ts:297-331`).

So `endingLine(held('BuildRed'))` cannot know whether to offer `grant-fix-round`, and it cannot tell an escalated `BuildRed` from an escalated `MergeRefused`.

**Decision:**
- Widen `PassSummary.wait` from `string` to `WaitReason` (from `@lingtai/domain/wait`).
- Call `summaryOf(reason)` at `conduct.ts:4735`.
- In `endingLine`, call `waitCommand(waitMoves(summary.wait, { triage: null }), { project, issue: ref, reason: summary.wait })`.

This is safe because the type's own comment says *"Built from facts the pass already holds; nothing here is written to the log"* (`conduct.ts:524`). `summary.wait` has no other reader in `apps/` or `packages/`: `git grep` finds only `conduct.ts:641`.

When `summary` is absent on a held result (the `summary?` is optional at `conduct.ts:544`), print `waiting for you: the board`. Do not guess a command from nothing.

**Tests to change:**
- `apps/cli/unit/start-one-line.test.ts:22-29` builds `held(wait: string)`. Change it to take a `WaitReason` fixture.
- Its two existing assertions (`approve chapter-garden-a --issue 1` and `answer p --issue 1`) should stay green as they are.
- Add the non-signoff case the ticket's *Done when* asks for.

## Status: the command is computed in `rowOf`, not in `renderStatus`

`renderStatus` reads only `StatusReport`. By the time it runs, the wait is `StatusWait.reason: string` (`status.ts:245`), so it has the same tag-only problem.

**Decision:**
- Compute the line in `rowOf` (`status.ts:470-484`), beside `recommendation`, where `t.wait.reason`, `t.triage` and `t.savedHead` are all in hand.
- Store it on `StatusWait` as `command: string`, documented like `short` as *not in `--json`*.
- `renderStatus` prints `w.command` at `:610`.
- `statusJson` (`:687-699`) is not touched, which keeps the ticket's *no new `--json` field*.

**Saved head:**
- Widen the `conflict` condition at `status.ts:500-504`. Read the saved head when `t.triage.result` is `TriageAdvised` and either `cause._tag === 'ConflictingHunks'` or `resolution === 'GrantFixRound'`.
- Pass the `SavedHead` to `waitMoves` exactly as `conflictRecommendation` already does (`status.ts:46`): `typeof savedHead === 'object' ? false : savedHead`. That puts an unreadable head and an absent one on the same side.
- `conflictLines` still returns null for anything that is not a conflict (`:63`), so the wider read changes no detail line.

## `waitMoves` and the requeue pair

`waitMoves` takes `(reason, { triage: TriageResult | null, savedHead?: boolean })`. `TriageResult` is the type of `TaskCard['triage']['result']`. Keep the function in `wait.ts` and do not import `wait-words.ts`, which imports `wait.ts` (`wait-words.ts:24`).

**`rest` order.** `allowedResolutions` keeps `tableResolutions`' order, and that order is not the same across rows: `EditBodyAndRequeue` comes before `Requeue` for `NothingProduced`, `BudgetExhausted` and `AgentCrashed` (`wait.ts:327-329`, `:337-341`), and after it for `SignoffRequired` (`:303`). Leave `waitMoves` returning both tags in table order. It is a fact about the wait.

**`waitCommand` merges the pair:**
- The merged entry goes where the first of the two appears. The second is dropped.
- If either tag is `first`, the merged entry is `first`.
- Spelling:
  - Brackets, `[--into-body "<text>"]`, by default.
  - No brackets, `--into-body "<answer>"`, for `AgentQuestion` and escalated `InputNeeded`, as the ticket says.
  - No brackets, `--into-body "<text>"`, when `EditBodyAndRequeue` itself is `first`. That happens only when triage advised a body edit, and then writing the body is the move.
  - `requeue` alone, with no `--into-body`, when the wait allows `Requeue` but not `EditBodyAndRequeue` (`MergeConflict`, `MergeRefused`, `BaseMoved`, `SetupRefused`).

**Signature:** `waitCommand(moves, { project, issue, reason: WaitReason })`. It needs the reason, not just the tag, for two choices:
- the `--note` waiver on `approve`, which is dropped only for `SignoffRequired`;
- the `<answer>` spelling, which depends on `reason.proposal._tag === 'InputNeeded'`.

**Empty line.** If `first` is null and `rest` is empty after removing `Split` and `Close`, print `the board`. This cannot happen with today's table (every row keeps a `Requeue`), but the guard costs one line, and `one of: ` with nothing after it would be worse.

## Checks

Everything here can be checked with `pnpm test`; nothing depends on the integration half.

- `packages/domain/unit/` holds `waitMoves` against fixture `WaitReason`s. Assert the ticket's "first is `recommendedResolution` or `AnswerQuestion` or null" as one loop over every fixture.
- `apps/cli/unit/` holds `waitCommand`.
- `renderStatus` gets a hand-built `StatusReport` whose rows carry `command`. The `status.ts` change has its own test through `readStatus` with the `savedHeadOf` seam (`status.ts:185`).
- `endingLine` is tested from `start-one-line.test.ts` with a `WaitReason` fixture.

No ADR changes. 0118 §1 still decides the ranking in `recommendedResolution`, and `waitMoves` only reads it.
