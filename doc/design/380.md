# #380: design note for `dbTickets`

## The decision: number allocation is one statement, not a `BEGIN … COMMIT`

The ticket says to allocate `MAX(number)+1` "inside one transaction". **`TicketSql` cannot hold a multi-statement transaction on Postgres, so do not try to issue `BEGIN` through it.** `createPostgresTicketSql` opens a new client for every call. Its comment says *"A connection per question, opened and closed around it"* (`packages/event-store/src/queries.ts:306-323`). A `BEGIN` sent through `sql.query` would commit on a connection that has already been closed. The seam's only verbs are `query` and `exec` (`packages/event-store/src/ticket-sql.ts:33-38`). Widening it to add a transaction verb is a change to `@lingtai/event-store`, and this ticket does not ask for one.

The transaction is therefore the statement itself. Use `VALUES` with a scalar subquery, which runs on both dialects:

```sql
INSERT INTO tickets (project, number, title, body, labels, state, created_at, updated_at)
VALUES ($1, (SELECT COALESCE(MAX(number), 0) + 1 FROM tickets WHERE project = $1), $2, $3, $4, 'open', $5, $5)
RETURNING number, title, body, labels, state
```

- **Use `VALUES`, not `INSERT … SELECT $1, …`.** In a `VALUES` list, Postgres types each `$n` from its target column. In a `SELECT` list a bare parameter resolves to `text`, and then the `timestamptz` column refuses it. Casting it to fix that is not portable: `::` is not SQLite, and SQLite reads `CAST(x AS TIMESTAMPTZ)` as NUMERIC affinity, which turns an ISO string into `2026`.
- I checked on this machine's `node:sqlite` that the subquery-in-`VALUES` form with `RETURNING` runs and returns `1` for an empty project.
- **SQLite cannot race.** One statement runs under the write lock (`busy_timeout`, `packages/event-store/src/sqlite.ts:125`).
- **Postgres can.** Under READ COMMITTED, two statements can both read the same `MAX`, and `PRIMARY KEY (project, number)` then refuses one of them. That refusal is the retry the ticket asks for: catch it, run the same statement again, and give up and rethrow after a small bound (5 is enough). Retry only on a duplicate, never on any other error.
  - **Postgres** duplicate: `code === '23505'`. `event-store.ts:160-175` shows how this codebase already reads it.
  - **SQLite** duplicate: `code: 'ERR_SQLITE_ERROR'`, `errcode: 1555`, message `UNIQUE constraint failed: tickets.project, tickets.number`. I observed this from `node:sqlite` here. Match on `errcode === 1555`.

`isPostgresCreateRace` already treats `23505` as a race (`db-tickets.ts:75`), but it is about the DDL and also accepts `42710`/`42P07`. Write a separate predicate rather than reusing that one.

## The rest of the shape

- **Signature:** `dbTickets(sql: TicketSql, project: string, options: { now?: () => Date } = {}): DbTickets`, in `packages/conductor/src/db-tickets.ts` below `ensureTicketTables`. Like `memoryTickets` (`test/memory-tickets.ts:14-17, 46`), the clock is injectable because 0060 §1 counts the wall clock as outside the system. Production defaults to `() => new Date()`. Unit tests pass a counter.
- **First use:** keep one `let ready: Promise<void> | undefined` in the closure, and have every verb `await` it before running. If it rejects, clear it so the next call tries again instead of reusing a failed promise forever. `ensureTicketTables`'s own header already says *"The tables are created by the adapter on first use (#380)"* (`db-tickets.ts:104-107`). Edit that paragraph so it no longer says "called from nowhere".
- **Times:** write `now().toISOString()` and pass `since.toISOString()` to `listIssuesSince`. On SQLite the column is `TEXT`, so `created_at >= $1` compares strings. That is correct only because every value written has the same `toISOString` shape. Postgres accepts the same text for a `timestamptz` parameter. `Ticket` has no time field (`TicketDetail` is `TicketListing & { body }`, `discover.ts:63-65`), so nothing has to be parsed on the way back.
- **Ordering:** `listOpenIssues` uses `ORDER BY number`. `listIssuesSince` uses `ORDER BY created_at, number`: *"oldest first"* (`ticket-store.ts`, the `listIssuesSince` doc). `number` breaks ties when a clock stamps two tickets with the same time.
- **Rows come back unnormalised** (`ticket-sql.ts:27-31`):
  - `labels` is JSON text: `JSON.parse` it, then map each entry to `{ name, color: null }`.
  - `ticket_comments.id` comes back as a string from `pg` (BIGSERIAL) and a number from SQLite: wrap it in `Number(...)`.
  - SQLite rows have a null prototype. Build fresh objects instead of spreading rows.
- **An unknown number rejects on every verb, not only `getIssue`.** `memoryTickets` throws `no ticket #n` from `setLabels`, `closeIssue`, `updateBody` and `comment` (`memory-tickets.ts:51-55`).
  - For the `UPDATE`s, use `… RETURNING number`. Zero rows means the number does not exist: throw an error that names the project and the number.
  - For `comment`, check that the ticket exists first, then insert into `ticket_comments` with `VALUES`. The tables have no foreign key, and nothing deletes a ticket, so check-then-insert has no race to lose.
- **Inspection seam:** like `MemoryTickets` (`memory-tickets.ts:40-42`), return `DbTickets extends Tickets` with `commentBodies(issue): Promise<readonly string[]>`, using `ORDER BY id`.
  - **`describeTicketsContract`'s `commentBodies` option is synchronous** (`test/tickets-contract.ts:35, 88`), and a database cannot answer synchronously.
  - Widen that option's return to `readonly string[] | Promise<readonly string[]>`, and `await` it at line 88. `memoryTickets` still passes, since `await` of an array is the array.
  - Update the header's `commentBodies` paragraph to say that a database-backed seam is async.
- **Not exported from `index.ts` in this ticket.** Nothing calls it yet, and choosing it over GitHub per project belongs to the epic (#376).

## Tests

- **`unit/db-tickets.test.ts`** (extend it; do not add a new file):
  - Call `describeTicketsContract('dbTickets on SQLite', () => dbTickets(createSqliteTicketSql(openSqliteLog(':memory:')), 'p', { now }), { commentBodies: (t, n) => t.commentBodies(n) })`. A fresh `:memory:` database per case also proves that `ensureTicketTables` runs on first use: none of those databases has the tables.
  - Add the ticket's numbering case: two `createIssue` calls on one project give distinct numbers, and two projects on one `sql` each start at `1`.
  - **The retry branch cannot be reached at unit level with a real race**, because SQLite serialises the statement. Reach it with a `TicketSql` wrapper that rethrows a **real** SQLite refusal once on the first `INSERT INTO tickets`, then delegates to the real store.
    - To get the real refusal, insert a duplicate row with `sql.query` against a scratch `:memory:` database (the existing *"refuses a second ticket"* case at `:55-69` shows how) and capture the thrown error.
    - Assert that `createIssue` resolves.
    - A second wrapper that always throws a non-duplicate error must reject on the first try. That pins "retry only on a duplicate".
- **`integration/db-tickets.test.ts`** (the same file; it is already listed in `ON_POSTGRES`, `packages/event-store/test/postgres.ts:37-38`):
  - Add `describeTicketsContract` inside a `describe.skipIf(!postgresUnderTest())` block. Have `make` use a fresh `project` per case, collected into a list for `afterAll` to delete. This is the same pattern as the file's existing `esctest…` project, which is unique to each run.
  - Add one concurrency case: for example, eight parallel `createIssue` calls on one project produce eight distinct numbers, `1..8`. **This is the only test that can trigger a real Postgres duplicate.** It runs only after the merge (803s integration half; see CLAUDE.md). Inside the pass, the unit retry test above stands in for it.
  - The file's existing case drops both tables first. Keep it ahead of the new `describe` blocks so that it runs first; vitest runs a file's `describe` blocks in order.
  - Extend the `ON_POSTGRES` reason string to mention the adapter. `unit/on-postgres.test.ts` holds that list to the code.
  - Run the file alone: `pnpm vitest run --project integration packages/conductor/integration/db-tickets.test.ts`. This needs `LINGTAI_TEST_DATABASE_URL`; without it the file is skipped, not failed.
- **`githubTicketStore` needs no test of its own here.** It takes `Pick<Tickets, …>` (`ticket-store.ts:87`), so `dbTickets` satisfies it by type, and `pnpm typecheck` is what checks that.

## Header

The file header already says that nothing here appends an event, and that a reset of `events` leaves these tables alone (`db-tickets.ts:5-9`). Add:

- The columns and what each one holds: `labels` is a JSON array of names, and `state` is `'open' | 'closed'`.
- That `url`, label `color` and `assignees` have no column, and answer `null`, `null` and `[]`.
- That `dependencies` is `{ blockedBy: 0 }`, never `null`. Cite `discover.ts:46-53` *"Null is not zero"*, and `ticket-store.ts`'s note that this is a rule on one implementation, not on every `Tickets`.
- That `closeIssue`'s `reason` is accepted and not stored.
- That a comment is an appended row and is never rewritten.
