# #707: design note

## Already built (child 1 and #706): this ticket only connects it

- The client already takes `gh` auth. `CreateClientOptions.auth` is `AppAuth | { kind: 'gh' }` (`packages/github/src/client.ts:357`). Under `gh`, `createGitHubClient` skips the installation lookup: *"No installation: the saved login is a person's, and each call asks `gh` afresh"* (`client.ts:377-380`). Its `gh?: GhRun` option (`:361`) is the seam the `githubClientFor` test uses. Don't write a second `gh` path.
- `githubAuth()` returns `{ kind: 'app' } | { kind: 'gh' }` and **carries no credentials**. Its comment says *"`{ kind: 'app' }` carries no credentials: `githubApp()` reads them when a client is built"* (`packages/env/src/index.ts:1391-1395`). So you can't simply replace `auth: githubApp()` with `auth: githubAuth()` (`filter.ts:222`, `converge.ts:154`). On `app` you still need `githubApp()`.

## Decision 1: one function decides what `auth:` is

Add one exported helper next to `githubClientFor` in `packages/conductor/src/filter.ts`. It returns `{ kind: 'gh' }` when `githubAuth().kind === 'gh'`, and `githubApp()` otherwise. Every project-client builder calls it, never `githubApp()` directly:

- `filter.ts:222`
- `converge.ts:154`, the default `clientFor`
- `conduct.ts:245`, `:595`
- `run.ts:356`

Under `gh` it must not call `githubApp()`. That rule is the "no installation under `gh`" guarantee. It also matters on a machine that has a full App **and** `github.auth: gh`: `electGithubAuth` lets a written `auth` beat any `app_id` (`index.ts:1354-1359`), so that machine is a `gh` machine. Testing `hasGitHubApp()` first would quietly build App clients there. Pin this in the `githubClientFor` test: a full App plus `auth: gh` gives a client built through the injected `gh` runner, and no `/installation` fetch happens.

## Decision 2: `hasGitHubAuth` must stay false where `hasGitHubApp` was false on an App machine

Today `hasGitHubAuth` is `!refused && kind !== null` (`index.ts:1408-1411`). A file that says `github.auth: app` but has no key, or only half a key, elects `kind: 'app'` (`:1360-1362`), so it answers **true**. `hasGitHubApp` answers false there (`:1340-1343`).

If the guards switch over unchanged, that machine stops getting the `no GitHub App configured` refusal (`conduct.ts:516`, `run.ts:350`). It gets past the filter and fails later with `githubApp()`'s throw, inside each project's client build. That breaks "nothing changes on an App machine".

Change `hasGitHubAuth` in `packages/env` so that elected `app` also requires `hasGitHubApp(from)`. Elected `gh` stays true without checking the login: that is the new doctor row's job. Add the two cases to `packages/env/unit/github-auth.test.ts`. They test `hasGitHubAuth` through `from`, which needs a `LINGTAI_HOME`; if that pulls in the filesystem, test it through the pure election instead.

## Where each switch goes

- **`projectsForPass`** (`conduct.ts:509`): rename the `hasApp` parameter to `canReach` and leave the body alone. The call at `:555` passes `hasGitHubAuth()`. The refusal stays `detail: 'no GitHub App configured'` word for word, as the ticket requires.
- **The sweep** (`converge.ts:151`, `:158`, `:176`): replace the `hasApp` default with `hasGitHubAuth`. Renaming the option is fine; update its tests in the same change.
- **`run`'s world** (`run.ts:252`, `:271`, `:348`): rename the seam to `hasGitHubAuth`. Keep the sentence at `:350` byte for byte and update `run-ownerless.test.ts:100`, `:143`.
- **`githubClientFor`'s guard** (`filter.ts:219`): use `hasGitHubAuth()` and keep the message.
- **Board** (`actions.ts:125`, `:177`, `:351`; `task.ts:1909`): switch them. Both files build their client through `githubClientFor`, so the auth change follows. `actions.ts:466` is `recheckProject` and stays, as the ticket says.
- **CLI guards** (`approve`, `backlog`, `close`, `end`, `grant-fix-round`): only the predicate changes.
- **Doctor** (`doctor.ts:1703`, `recipeClientFor`): switch to `hasGitHubAuth(env)`. Also change the proxy message at `:1692`. It says "no GitHub App configured", which was always a lie inside a bug message, and it's not one of the pinned sentences.

## Doctor

**`github: app credentials`** (`doctor.ts:826`): on a machine where `githubAuth` elects `gh`, return `skip` with a detail like *"github.auth is gh — the App is not used for projects"*. The current skip text at `:837` tells a `gh` user to configure an App. Leave App and unconfigured machines exactly as they are today.

**`github: gh login`** (new row): push it right after `githubCredentials` (`:2764`), and only when the election says `gh`. On other machines it is absent, so the existing doctor tests are untouched.

- It is async because `ghStatus` is (`packages/github/src/gh.ts:102`).
- Inject `ghStatus`'s runner through `DoctorReach` (`doctor.ts:910`) as an optional `gh?: GhRun`, the way `spend?` already is (`:924`). The unit test then fakes the spawn, as `packages/github/unit/gh.test.ts` does.
- `ok` needs `ghStatus` to be ok, **and** `scopes` to include both `repo` and `workflow`.
- Signed out, `no-account`, `missing`, `too-old` and `unparsed` each fail with `ghStatus`'s own `detail` plus `gh auth login`.
- Signed in but missing `workflow` fails naming `gh auth refresh --hostname github.com --scopes workflow`.
- Missing `repo` fails naming the same refresh command with `--scopes repo,workflow`.
- Never print a token. `ghStatus` doesn't read one, so don't call `ghToken` here.

## Edges the ticket leaves open, decided here

- **The `gh` login fails mid-pass** (signed out, scopes revoked). `ghToken` throws per request (`gh.ts:81-91`), and each caller already turns a client failure into its own outcome: the sweep's `catch { continue }` (`converge.ts:178-182`) and the filter's "never throws". Nothing new to build; the doctor row is where it gets named.
- **A refused `github.auth`** (`auth: foo`): `hasGitHubAuth` is false, so callers get the same `no GitHub App configured` refusal an unconfigured machine gets. `githubAuth()`'s throw names the bad value, and the client helper lets it propagate.
- **Restart**: the daemon and the board hold the code they started with. The PR says a `gh` machine needs `pnpm lingtai restart` and a board restart. An App machine needs nothing.
- **Cost to later tickets**: tests that stubbed `hasGitHubApp` now stub `hasGitHubAuth` through the renamed seams. Every test listed here is unit-level, so `pnpm test` covers this change without the integration half.
