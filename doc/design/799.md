## Design note: #799

**Everything stays in `apps/site/src/app/site.css`. The one possible exception is `events-filter.tsx` (see §2).** The stacking half is what the ticket already describes. The width half has a cause the ticket does not name: **a third flex child that is only there while a step is selected.**

### 1. Stacking

- Delete the two rules that set `opacity` on the node: `site.css:619` (`.ev-drawing.filtering .ev-node[aria-pressed="false"] { opacity: .6; }`) and `site.css:622` (`.ev-node:disabled { opacity: .55; }`). Put the dimming on `.ev-dot` (border colour, text colour) and `.ev-step` (colour).
- **Do not move the opacity down onto `.ev-dot`.** Opacity on the dot would let the line show through its `--surface` background in both themes. That is the opaque-background edge in the ticket, broken a second way. Change colours only; the background stays opaque.
- `:621` already dims the disabled state through its parts: `border-color: var(--rule-2); color: var(--muted)`. The filtered-and-not-pressed state can use the same two tokens on the dot, plus `color: var(--muted)` on `.ev-step`. A disabled node then needs one more thing so it still reads as disabled: muted label text is enough.
- Give `.ev-spine li::before` (`:608`) `z-index: 0` and keep the dot at `z-index: 1` (`:614`). With the opacity gone, nothing between the dot and `.ev-drawing` creates a stacking context. `.ev-node` is `position: relative` with no `z-index` (`:610`), and so is the `li` (`:607`). Both z-indices then resolve in the same context, the one `.ev-drawing` creates with `position: sticky; z-index: 2` (`:603`). **Do not add a `z-index` to `.ev-node` or the `li`.** Doing that recreates the bug by another route.
- Hover (`:616`) sets `background: var(--accent-soft)`. Make sure that token is opaque in the site's palette, in both themes. The board's copy is opaque (`apps/board/src/app/globals.css:22`, `:60`), but I did not find where the site defines it. If it turns out to be translucent, the line shows through on hover.

### 2. Width: the decision the ticket leaves implicit

Arithmetic at 1440px, from the code:
- `.wrap` has 24px padding on each side (`:68`), so the content box is 1392px.
- `.doc-layout` is `11rem minmax(0, 60rem) 10rem` with 24px gaps (`:312`), so the article column is **960px**.
- The drawing needs at least:
  - the spine, `min-width: 760px` (`:605`);
  - the lane, about 149px: 14 margin + 14 padding + 2 border (`:606`), two nodes at `3.4rem` (`:612`), and a 10px gap;
  - **the `show all` button**, which is a third flex child of `.ev-drawing` (`events-filter.tsx:125`) and is `hidden` only while `filter === null`.

Unfiltered, that is about 909px and it fits. With a step selected, it is about 909px plus the button, which is more than 960px. **That is why the overflow only shows on `?step=admit`**, the same reason the stacking bug hid. In the design, `show all` is not in the spine's row. It sits in a separate `.state` line under it (`doc/design/events-page.html:1210`).

So:
- **Take `.ev-clear` out of the row and keep it inside the sticky box.** Use `flex-wrap: wrap` on `.ev-drawing` and `flex-basis: 100%` on `.ev-clear`. The button's existing `margin-top: 8px` (`:623`) already reads as a row below.
  - Keep it inside `.ev-drawing`: it has to stay reachable while the list scrolls.
  - Keep it after the lane in the DOM: `apps/site/unit/events.test.tsx:36` slices the HTML from `class="ev-spine"` to `class="ev-clear"` to find the lane's nodes.
  - The taller box is handled already. `--ev-spine` is measured by a `ResizeObserver` on the drawing (`events-filter.tsx:46-56`, *"changes with width and with the show-all control"*), so anchors keep clearing it.
  - A JSX change is fine if CSS cannot do this cleanly, as long as those two constraints hold.
- **Replace `.ev-spine { min-width: 760px }` with `min-width: 0`.** The spine then takes whatever the lane leaves (`flex: 1`), which is about 811px at 1440, roughly 81px per step. The widest labels (`implement`, `prepared`, `proposed`; nine characters of 11px mono, `:624`) are about 60px. Without a floor, though, the spine squeezes until the `nowrap` labels collide instead of scrolling. So put a floor back **only below 1240px**, in a `@media (max-width: 1240px)` rule beside the existing breakpoints (`:359`, `:364`). That gives the ticket's edge: "may scroll ≤1080px and at 700px, never at ≥1240px". The floor can be the old 760px. At ≤760px the labels are already hidden (`:628`), so the floor only keeps the dots apart there.
- The lane keeps its own width (`flex: none` is implicit for the `ul`). Do not let it shrink. `outside` and `no step` are the nodes that went missing.

### 3. Checking it

None of this reaches a unit test: no test reads the `.ev-*` rules. `page.test.ts:25` reads `site.css` only for the chrome. The check is the ticket's person-check, and it is the only one that can see either bug. In a browser at 1440×900:
- unfiltered;
- `?step=admit`;
- a step whose selection leaves some node at count 0, if one exists, to check disabled plus filtering together;
- hovering an undimmed node;
- each of those in dark mode;
- then 1240, 1080 and 700.

`pnpm typecheck`, `pnpm lint`, `pnpm fmt:check` and `HOME=/nonexistent pnpm test` only show the change broke nothing. They do not show it works. `apps/release/integration/build.test.ts` (the Next build) does not matter here, because a stylesheet change crosses no server/client boundary.
