# Design note for #1130: why the lifted-day triage test fails sometimes

## The likely cause, and how to check it

This is the ticket's hypothesis, now with the mechanism traced through the code. Confirm it by reproducing the failure. Do not assume it.

1. **Effect runs a forked fiber later, on `setImmediate`. It does not start it straight away.**
   - `forkUnsafe` only evaluates the child immediately when `startImmediately` is set. Otherwise it schedules it (`node_modules/.pnpm/effect@4.1.2/node_modules/effect/dist/internal/effect.js:2463-2468`: `parentRuntime.currentDispatcher.scheduleTask(() => child.evaluate(effect), 0)`).
   - The dispatcher behind that call is `MixedScheduler`, whose default is `setImmediate` (`dist/Scheduler.js:121`, `:44-46`).
   - `afterScheduled` clears `running` before it calls `runTasks` (`Scheduler.js:169-172`). So when a task forks again from inside that batch, the new fork gets a **new** `setImmediate`, and that one runs on the event loop's *next* check phase.
2. **The lifted-day path forks twice, so it needs two of those turns.**
   - `triage.ts:348` forks the fiber that lists the projects.
   - `triage.ts:353` then forks one fiber per project.
   - Everything in the test is `Effect.succeed`, so `b`'s fiber reaches `readTasks` (`triage.ts:190`) on its first evaluation. That makes two check phases before `scanned` holds `'b'`.
3. **The test waits on a timer.** `drained()` is `setTimeout(resolve, 0)` (`triage-catch-up.test.ts:96-98`), and Node treats that as 1 ms.
   - Node's timers phase runs between those two check phases.
   - On an idle machine, less than 1 ms passes between arming the timer and that timers phase, so the timer has not expired and the second hop wins.
   - Under the conductor's parallel workers, more than 1 ms passes, the timer fires first, and the assertion at `:248` sees `[]`.

**A deterministic way to reproduce it (do not commit this).** Busy-wait about 3 ms inside the test's `projects:` port, so the first forked fiber holds the loop past the 1 ms timer:

```ts
Effect.sync(() => { const t = Date.now(); while (Date.now() - t < 3) {}; return ['a', 'b'] })
```

The hypothesis predicts this fails on every run. Report it in the commit body next to the `{ repeats: 200 }` counts, alone and under load, as the Done-when asks. If the busy-wait does **not** make it fail, the cause is something else: stop and find it before using the shape below.

## Where the fix goes: the test, not `triage.ts`

**The code is not wrong.** `triage.ts:336-337` says the forks are *"Forked and never awaited"*, and #1107 asked that a stalled project not hold back the others. A later check phase still reaches `b`, so no project is lost.

Adding `{ startImmediately: true }` to the forks would make this test pass by changing production scheduling to suit a test. Do not do it: the fork is detached so that the subscriber handler returns at once, and that should stay.

## The shape of the fix: wait for a signal the code gives

Replace `drained()` everywhere in `apps/cli/unit/triage-catch-up.test.ts` (it is used 23 times) and delete the helper. Each call falls into one of three kinds.

**1. The call already waited, so delete `drained()` with nothing in its place.**
- `catchUpTriage` / `catchUpChangedTriage` only resolve after their worker has settled: `yield* Deferred.await(first.done)` (`triage.ts:239`).
- So `await catchUpTriage(...)` is already the wait. That covers `:117, :139, :163, :186`, every catch-up case in `:296`–`:510`, and the `holds…` / `appends…` / `skips…` / `scans…` cases.
- The same goes for *"queues nothing live while the start time is unread"* (`:178`): `onWaitStarted` returns at `triage.ts:380` before anything is forked.
- Check each deletion by reading the call it follows. If the call forks anything it does not await, it belongs in kind 2.

**2. Work is forked and not awaited: give the port a signal and await that.**
Add one small helper at the top of the file that returns `{ fire, fired }`. Build it on a `Deferred` (`Deferred.makeUnsafe` + `Effect.runPromise(Deferred.await(d))`) or on a plain promise. Do not build it on a timer. The cases that need it:

| Case | What to change |
|---|---|
| Lifted day (`:226-252`) | `readTasks` fires `bScanned` when called with `'b'` and `aScanned` when called with `'a'`. Await `bScanned`, assert `['b']`, release `hold`, await `aScanned`, assert `['b','a']`. Keep both assertions exactly as they are: the code promises one fiber per project, and `a` cannot reach `readTasks` while `hold` is open, so the order the test pins is the order the code guarantees. |
| *"returns from onWaitStarted while the worker still waits"* (`:203-224`) | `run` fires `entered` before it awaits `hold` and fires `finished` after it. Await `entered`, assert `finished === false`, release, then await `finished`. |
| *"frees the permit and the key when a worker dies"* (`:190-201`) | `next` fires a signal; await it before asserting `next` and `log`. The `log` spy is called in worker 1's `flatMap` (`triage.ts:114-119`), which runs before the semaphore wakes worker 2, so by the time `next` has run the log call has happened. The cleanup `enqueueTriage(key(1), Effect.void)` gets the same treatment: pass an effect that fires a signal, and await it. |
| *"shares the queue with live delivery"* (`:405-410`) and *"does not pin the recipe…"* (`:433-437`) | The `worker` mock fires `called` inside its `new Promise`. Await that in place of `drained()`. It is what makes `onWaitStarted` join the existing key rather than add its own. |

**3. A negative assertion with no positive event to wait for.** If such a case exists, that is a sign it belongs in kind 1. Find the call that already settles the work. Do not invent a wait.

## Done when, read against this shape

- "No case waits on a bare `setTimeout`" means `drained` is gone and nothing replaces it.
- The `fired` promises hang rather than fail if the code never signals. That is acceptable: vitest's own test timeout turns a hang into a red with the case's name, and that is not a wait chosen to be long enough. Do **not** add a `Promise.race` against a timer.
- `apps/cli/unit/` is outside what `effect-ratchet.test.ts` counts (it counts `${pkg}/src/` only, `packages/domain/unit/effect-ratchet.test.ts:307`), so test helpers cost the baseline nothing.
- The integration half is not involved; `pnpm test` is the whole check.

## Commit body

- Say the cause in two sentences: two `setImmediate` hops (`triage.ts:348`, `:353`, via effect's `forkUnsafe`) raced one 1 ms `setTimeout` (`triage-catch-up.test.ts:97`), and the timer wins when the loop is busy.
- Say that the code was not at fault.
- Give the failure counts, with how each was produced: alone, beside the full `pnpm test` running in parallel, and under the busy-wait reproduction.
