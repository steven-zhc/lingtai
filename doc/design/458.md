# #458: the shape

## The trap: three of the new names already exist at the package root

`packages/domain/src/index.ts` is a list of `export *` lines, and the 0118 §1 names collide with names already exported there:

| 0118 §1 name | already exported by |
|---|---|
| `RunRef` | `hold.ts:75` (with `repairOf`, which 0118's does not have) |
| `TriageResult` | `triage.ts:154` (`Failed`/`Advised`, not `TriageFailed`/`TriageAdvised`) |
| `TriageStatus` | `triage.ts:164` (its `Done` carries the *old* `TriageResult`) |
| variant schemas `MergeRefused`, `SetupRefused` | `hold.ts:214`, `hold.ts:266` |
| variant schema `AnswerUnreadable`, `Interrupted` | `action.ts:86`, `action.ts:79` |
| `Approve`, `Requeue`, `Close` | `triage.ts:124-126` |

When two `export *` sources export the same name, tsc reports TS2308 and the name is exported by neither. So "beside today's `Hold`" cannot mean "also exported from `.`", and renaming the new types (`WaitRunRef`, `TriageResult2`) would break the ticket's *match 0118 §1*.

**Decision: the wait model is a subpath, `@lingtai/domain/wait`.** Add `"./wait": "./src/wait.ts"` to `packages/domain/package.json`'s `exports`, next to `"."`. `@lingtai/event-store` already does this (`"./memory"`, `"./store"`). **Do not add `wait.ts` to `index.ts`.** #464 deletes `Hold`/`Move`/`Cause` and the old `TriageResult`/`TriageStatus`; at that point it folds `wait.ts` into `index.ts` and drops the subpath. Say this in `wait.ts`'s header, next to the two-names-for-one-idea note the ticket asks for. Name `WorkItemBlocked.hold` and `HoldTriaged` as the reasons the old names stay.

The variant schemas inside `wait.ts` stay **unexported**. Export only the unions, their inferred types and the two functions, so nothing new can collide when #464 merges the two.

## `allowedResolutions`

It returns `Resolution['_tag'][]`, the tags and not values as `allowedMoves` returns (0118 §1's signature). Write it as a `switch` with no `default`, for the reason `moves.ts:16-19` gives. Return arrays **in the 0118 table's column order** and test with `toEqual`, so a reordering is a visible change.

`ProposedEscalated` switches on `reason.proposal._tag`. `Approve` goes first only for `ReviewFindings`/`ReviewEmpty`.

**`unpushed`, decided:** apply it as **one rule after the table, to every variant**: if `run.unpushed` is set, drop `Approve`. Today it applies only to `Routed`/`CheckRed`/`MergeRefused` (`moves.ts:34-47`), not to `Human` or `Declined`. Applying it uniformly is deliberate. `hold.ts:63-66` says that with `unpushed` *"the branch did not reach origin, and the worktree that held it is gone when the pass ends"*, so `Approve{onSha}` names a sha that exists nowhere, whatever the variant. 0118 §1 also puts `unpushed` on `RunRef` *"so it can sit beside any wait with a run"*.

The comment should cite `moves.ts:34-47` and say 0118's table is silent on it. The commit body should say two things:
- this extends the refusal to `SignoffRequired` and `FixerDisagrees`;
- `afterApproval` is dropped (`hold.ts:205-213`; `moves.ts:40-47`), because `WaitReason.MergeRefused` has no field for it.

Whether a `Human`/`Declined` hold ever actually carried `unpushed` is settled by `WorkItemBlocked.hold.run.unpushed` on the log. I have not read the log; nothing here depends on the answer.

## `recommendedResolution(reason, status)`

Read 0118 §1 literally: *"An advised resolution is recommended when `allowedResolutions` offers it, and otherwise is not, its words still shown. With no advice (not declared, running or failed) the wait's own default stands."*

- **`Done{TriageAdvised}` whose advice is allowed** returns the advice.
- **`Done{TriageAdvised}` whose advice is disallowed** returns **`null`**, not the default. There was advice; it just isn't drawn.
- **Every other status** (`NotDeclared`, `Queued`, `Running`, `Interrupted`, `Done{TriageFailed}`) returns the default: `Approve` for `SignoffRequired`, `Requeue` for `BudgetExhausted`/`AgentCrashed`, `null` elsewhere.
- **The default also goes through `allowedResolutions`**: a `SignoffRequired` with `unpushed` set returns `null`, not a disallowed `Approve`.

Test the disallowed-advice case on `SignoffRequired`, where the default is non-null, so the test tells "null" apart from "fell through to the default".
