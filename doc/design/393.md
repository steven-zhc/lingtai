# Design: #393, the GitHub App step waits with a deadline, can be skipped, and is asked only for a GitHub project

## The decision the ticket leaves open: #394 is not built, so #393 adds the smallest version of its question

The ticket says the App step is something "the GitHub branch of #394 calls". But #394 is open and not built. Its own Fix says *"The GitHub branch calls #393's App step"*, so #393 lands first. The first Done-when line also needs a "*local* project choice" to exist. Today nothing in `apps/cli/src` asks it: `init.ts` has no project question, and `lingtai add` only takes `<owner>/<repo>` (`lingtai.ts:364`, quoted in #394).

**So #393 adds the kind of project as one question, and nothing past it:**

- The question is `github` or `local`.
- It is asked through `question()` (`apps/cli/src/question.ts`) with `choices: ['github', 'local']`.
- Its flag is `--project github|local`.
- `local` does nothing in this ticket except *not* ask for the App. Registering the directory, `owner: null` and `repo.remote` all belong to #394, and #394's `--github <owner>/<repo>` / `--local <dir>` can each imply `--project` when it lands.
- Say so in the line `local` prints: the board is at `<url>`, and registering a directory on this machine comes with `lingtai add`.

**Ask the kind only when no App is configured.** When `world.app()` answered `configured: true, ok: true`, the GitHub path is already chosen in practice. Keep today's behaviour there: open `/setup/repository` (`init.ts:297`) and ask nothing. This keeps a re-run of a finished `init` asking nothing, and `integration/init.test.ts:352` (*re-running a finished init reports the state and changes nothing*) and `:155` keep passing as written.

## Where things go

**Create `apps/cli/src/github-app.ts`.** It declares the narrow world it needs, the way `question.ts` does (*"it declares the slice of the world it needs rather than depending on `InitWorld`"*, `question.ts:8-10`), so `lingtai add` can call it under #394. It exports two things:

1. **`askFirstProject(world, flags, app)`**. It runs at most two seam questions and writes nothing:
   - The kind question above.
   - For `github`, a second question: name `the GitHub App`, `choices: ['create', 'skip']`, `fallback: 'create'`, flag `--github-app create|skip`.
   - It returns `{ project: 'local' } | { project: 'github', app: 'create' | 'skip' } | { refused }`.
   - With no terminal and no flag, the seam refuses by name (`question.ts:72`). That is #392's rule, and it replaces today's behaviour, where a run with no TTY reached `appeared()` and waited forever.
2. **`waitForApp(world, wizardUrl, { waitMs })`**. It returns `{ made: {slug, owner} } | { skipped } | { timedOut }` and always lets `init` go on. It:
   - opens the browser;
   - prints the URL whether or not `open` worked (keep `init.ts:298-301`'s two lines);
   - races three things: `world.appeared(signal)`, `world.pressed(signal)` and a timer of `waitMs`;
   - aborts the losers;
   - for a skip or a timeout, logs the one come-back line.

**Changes in `init.ts`:**

- **The refusal stays exactly where it is.** `world.app()` and the configured-but-silent refusal (`init.ts:269-276`, *"A second App is not created beside it"*) still run at the top level, before any new question. A broken App refuses whatever the project choice. That is what keeps `integration/init.test.ts:330` passing unchanged: that test passes no `--project`, so a question asked ahead of the refusal would turn its exit 1 into a seam refusal with a different sentence.
- **Then `askFirstProject`, before the board starts.** Every refusal comes before a server is up, and a refusal leaves nothing serving.
- **Then the board**, unchanged (`init.ts:283-295`).
- **Then the branch:**
  - `create`: `waitForApp` on `/setup/github-app`.
  - `skip`: the come-back line, with no browser opened.
  - `local`: no browser opened, because #391 says *the browser is the only reason to leave the terminal*.
- **Delete the unconditional block at `init.ts:303-307`.**
- **Add `--project` and `--github-app` to `parseArgs`'s list (`init.ts:226`) and to `USAGE` (`init.ts:160`).**
- **Update the header's `App` line (`init.ts:9`).**
- **Answer a seam refusal with the same exit code `chooseStore` uses for its own seam refusal.**

## The wait

- **`appeared` takes an `AbortSignal`.** The live one (`init.ts:295-300`) is a `for (;;)` that polls `liveApp()` every 2 s. A timeout that only stops *awaiting* it leaves that loop running for as long as the board serves, which is the rest of the process. Check `signal.aborted` each time round and clear the `setTimeout` on abort.
- **`pressed(signal)` is a new `InitWorld` member.** It resolves on any key at a TTY. When `!process.stdin.isTTY`, it never resolves until aborted. This is the trap: raw mode has to be undone. Call `setRawMode(false)` and `stdin.pause()` in a `finally`. If you don't, the board's own *"ctrl-c stops it"* (`init.ts:311`) stops working for the rest of the session. In raw mode, Ctrl+C also arrives as the byte `\x03` and not as SIGINT. Treat it as stop: print the same message and exit 130, as `ask`'s SIGINT handler does (`init.ts:256-259`). It must never count as a skip.
- **The deadline is a named constant, `APP_WAIT_MS = 10 * 60_000`.** It is passed in as `waitMs` so the unit test can pass a few milliseconds with real timers rather than mocking the clock. Ten minutes covers a person reading GitHub's page and pressing Create.
- **The come-back line.** Nothing is lost at a timeout: the App's key is written by the board's own page (`@lingtai/conductor/create-app`, cited at `init.ts:20-21`), not by `init`, and the board is still serving. The line should say both ways back, for example:

  `app          not created (skipped | no answer in 10 minutes) — create it at <board>/setup/github-app while this board runs, or run lingtai init again`

  A re-run reaches the same question, because `app()` still answers `configured: false`.

## Tests

- **`apps/cli/unit/github-app.test.ts` is where the Done-when's unit claims go.** `initCommand` reads and writes `config.yml` under `LINGTAI_HOME`, which is the filesystem, so by 0060 §1 it is integration. That is why every `init` test lives in `apps/cli/integration/init.test.ts`. The unit claims are made against the two functions with injected worlds:
  - `--project local` returns `local`, and a caller following it never calls `appeared` or `pressed`.
  - `waitForApp` with an `appeared` that never resolves returns `timedOut` after `waitMs`, logs the come-back line once, and aborts `appeared`'s signal.
  - A `pressed` that resolves at once returns `skipped` with the same line.
  - With no TTY and no flag, both questions refuse by naming their flag.
- **`apps/cli/integration/init.test.ts` has to change, and the build step will not run it.**
  - Its `world().ask` asserts every prompt matches `/Postgres/` (`:76`). Route by prompt instead, answering the kind question from a new `script.project` (default `github`) and the App question with `create`.
  - Give its `appeared` the signal parameter and add a `pressed` that never resolves.
  - Add the integration form of the first Done-when line: `--project local` with no App never calls `appeared`, opens nothing, and exits 0.
  - `:330` must pass with no edit to its body.
  - Run that one file: `pnpm vitest run --project integration apps/cli/integration/init.test.ts`. It needs no Postgres; it is the store-free world above. Do not run `pnpm test:integration`.
- **Nothing to read in `events`.** `init` runs before the log exists (`init.ts:81-82`, *"none of this needs the log to exist"*) and appends nothing, so no seq settles this one. The tests are the evidence.

ADR 0114 is kept as it is: the App is still only a manifest App, and it is asked for only on the GitHub branch.
