## Design note: #1442, showing whether a response finished or closed early

### Where it goes

All of it lives in `apps/board/src/lib/`. One new module, `response-lifecycle.ts`, holds the observer, and `OnlyScope` gets one more case in `telemetry.ts`. No Next file, no `serve.ts` and no `server.js` change.

**The seam is Node's own `http.server.request.start` diagnostics channel. It is not a Next method.** In this repo's Node (v26.5.0, `engines.node: ">=26"`), `_http_server` publishes `{ request, response, socket, server }` inside `parserOnIncoming`, before the `'request'` emit. I read that in the built-in source, `process.binding('natives')._http_server`:

```js
if (onRequestStartChannel.hasSubscribers) {
  onRequestStartChannel.publish({ request: req, response: res, socket, server, });
}
```

The production board runs in the process that serves it. `apps/cli/src/board.ts:17-29` says "*The built board, served from this process (#183)*", and the CLI loads `server.js` with `import()`. Next's `start-server.js:247` calls plain `_http.default.createServer(requestListener)`. So a process-wide channel subscription sees the standalone server's real `ServerResponse` with no Next code involved. The source path (`next start`/`dev` through `serve.ts`) reaches the same channel.

**Subscribe inside `installTracing`, after the provider is set (`telemetry.ts:328-330`, beside `installTraceSeams()`).** The function already returns `undefined` before that point when no endpoint is configured (`telemetry.ts:318`: `if (url === undefined) return undefined`). So with telemetry off there is no subscriber, and the channel's `hasSubscribers` guard means Node does no work either.

### How a response is tied to its request span

This is the non-obvious part. You cannot match by trace id, URL or time, so match by async context:

1. In the channel subscriber, make a small record `{ startedAt, finishedAt?, request?: Context, done: false }`. Put it in a module-private `AsyncLocalStorage` with `enterWith(record)`. Then attach `response.once('finish', …)` and `response.once('close', …)`. The subscriber runs synchronously just before `server.emit('request')`, so Next's handler and everything it awaits inherit that store.
2. Next starts `BaseServer.handleRequest` inside that chain. `base-server.js:487-505`: `handleRequest(req, res)` → `tracer.withPropagatedContext(req.headers, …)` → `tracer.trace(BaseServerSpan.handleRequest, …)`. Next replaces only OTel's own context there, not a separate ALS instance. So in `OnlyScope.onStart`, in the existing `isRequest(span)` branch (`telemetry.ts:228`), read the store and bind `record.request = bare(context)`.
   - Bind once: the first request span under a store wins, and later ones are ignored.
   - A record already `done` is not bound.
   - Pass the store's getter into `OnlyScope`'s constructor, so `telemetry-phases.test.ts`-style rigs can inject a fake store.
3. **The record holds no `res`.** Only the listeners reference the record, and they belong to `res`, so a response that never ends takes its record with it when it is garbage-collected. No map holds a live response, so nothing needs eviction on the Node side.

There are no timers anywhere, so nothing can keep a CLI process alive.

### What one terminal event means

Use the rule Next already uses, `next-request.js:47-53`:

> *If `finish` fires first, then `res.end()` has been called and the close is just us finishing the stream on our side. If `close` fires first, then we know the client disconnected before we finished.*

- **On `finish`:** record `finishedAt`, mark `done`, and emit `finished`.
- **On `close`:** if not `done`, mark `done` and emit `closed-before-finish`, ending at the close time. Either way, remove the other listener.
- **A normal finish followed by a close is one `finished` record.** The `done` flag is the only guard against reporting it twice.
- **A request or socket error** shows up as `close` without `finish`, so it is `closed-before-finish`.
- **Never add an `'error'` listener to `req` or `res`.** A listener turns an unhandled error into a handled one, which changes error propagation, and the ticket forbids that.
- **Never wrap `write`.** First write is the existing `next.start-response` instant. `pipe-readable.js:75` and `:167` fire it right after `res.flushHeaders()` on the first chunk. "First write when available" means that phase is present, nothing more.

### What gets exported

The response is one span per physical response, named **`node.response`**:

- **Clock:** it starts at `startedAt` and ends at the terminal time. Capture both with `performance.now()` so they share the request span's clock.
- **Tracer and parent:** it is created by a tracer whose scope is **`lingtai-board.response`**, with the bound request context as its parent. It must not use `SCOPE`, because `telemetry.ts:253` forwards every `SCOPE` span except `page …` unconditionally, which would skip the route and export gates.
- **Attributes:** only two, both fixed values.
  - `lingtai.response.outcome` is `finished` or `closed-before-finish`.
  - `lingtai.response.headers_sent` is a boolean, `res.headersSent` read at the terminal event.
- **Nothing else:** no status message, no URL, no route id.
- **Unbound record:** if the record has no `request` at its terminal event, nothing is created.

In `OnlyScope`, a `lingtai-board.response` span is handled in a new branch, and it can arrive in either order:

- **The response ends while its request is in `#live`:** buffer it in `#phases` under that request. Give it its own slot, so `PHASES_PER_REQUEST` (`:72`) cannot crowd it out. It leaves with the phases at `:271-275`, under the same `#pages`/`request?.spanId` check (`:267`) and the same `MEASURED_ROUTES` check (`:270`).
- **The request ended first:** at the request's `onEnd`, after the route check passes, put its span id into a new bounded `#awaiting` set (FIFO, `limit` entries). When the response span arrives and its parent is in `#awaiting`, forward it parented to that id and delete the entry.
- **Otherwise:** the parent was not exported, not measured, or was evicted, so drop it. Missing stays missing, never a zero or a success.

Add `#awaiting` to `phasesRemembered` (`:214-216`), so the existing "0 once every span has ended" style of test covers it.

This is also the answer to the 2026-11-26 question, and it is what the validation reads. Compare `node.response` against `BaseServer.handleRequest`:

- `outcome = closed-before-finish` with its end at or before the request span's end means an **interrupted navigation**. Next aborts the pipe on that close (`next-request.js:50-53` → `pipe-readable.js:126`), and the request span can end while render children carry on.
- `outcome = finished` ending after the request span means the **span ended early** while the response was still being delivered.
- No `node.response` under the request means **unknown**.

Don't write either explanation into code or docs as a fact. These three fields settle it per trace.

### Route admission

Add `'/p/[project]/pr'` and `'/p/[project]/pr/[n]'` to `MEASURED_ROUTES` (`telemetry.ts:64-71`). Both pages already run inside `measure`, so their request copy leaves:

- `prs.ts:530`: `measure(… { label: '/pr' })`
- `prs.ts:537`: `{ label: '/pr detail' }`

Nothing else changes for them. RSC requests still have no `next.render-body`; the header comment says "Absent for RSC requests" at `:27`.

Rewrite the comment's "Unmeasured" paragraph (`:33-36`), which ends "*The next seam would be a Node `res` `finish` versus `close` timestamp*". It should say what `node.response` measures:

- the server handed the last bytes to its transport, or the connection closed first;
- it is not proof the browser received the page;
- RSC Flight render and backpressure stay unmeasured.

### Tests

**Unit, `pnpm test`:** extend `apps/board/unit/telemetry-phases.test.ts`'s `rig`, and add `response-lifecycle.test.ts`. Keep the cases in the unit half, with no socket:

- Drive the observer by publishing on `diagnostics_channel.channel('http.server.request.start')` with an `EventEmitter` standing in for `response` (`headersSent` set by hand).
- Start the Next request span inside the store it set.

Cases:

- finish then close → one `finished`;
- close only → one `closed-before-finish`;
- response ends before the request span, and after it;
- two overlapping requests in the same trace, each getting its own response;
- a response that never ends → nothing exported, and the record is not held;
- request evicted past `limit` → dropped;
- unmeasured route, or a request without a `page` span → dropped;
- `installTracing` with no endpoint → `hasSubscribers` stays false;
- `listenerCount('finish'/'close')` is 0 after the terminal event;
- the exported attribute keys are exactly the two.

**What only a real server shows:** that `enterWith` in the subscriber reaches Next's `handleRequest` span in Node 26, and that one physical request starts exactly one `BaseServer.handleRequest`. I could not open a socket in this pass, so neither is verified here. The opt-in validation below is what checks them, by looking for a `node.response` under every measured root. A missing one on a completed navigation means the binding failed.
