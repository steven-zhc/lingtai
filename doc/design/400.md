# Design: #400, `init` and `add` run as one flow

## The shape

The recipe questions run in **one function with two callers**, the same pattern as `chooseFirstProject`. Put it in a new module, `apps/cli/src/recipe-flow.ts`, as `askRecipe(world, at)`. It replaces the question blocks that exist today:

- the local branch's tickets/kinds block in `runLocalBranch` (`first-project.ts:397-432`);
- the agents/tickets/kinds/landing/limits block in `askBeforeGithubAdd` (`add-github.ts:166-262`).

`init` reaches it only through `chooseFirstProject`'s local branch. `add` reaches it through both branches.

Order inside `askRecipe`:

1. **"Use every default?"** — a `question()` (`question.ts:85`) named `every default`, with flag `--defaults`, choices `yes`/`no` and fallback `yes`. Enter on a TTY accepts.
2. `askAgents` (`agents.ts:125`).
3. `askInstallAndBuild` (`setup-build.ts:305`). Nothing calls it today: its header says *"#400, not here"*.
4. `askTickets` and `askKinds` (`source.ts:75`, `:160`).
5. **If the file is absent**, write it now, once (see *A new file* below).
6. `askLanding` and `askLimits` (`landing.ts:132`, `:208`). These write for themselves through `setRecipe`, and they need a file that resolves, so they always run after step 5.

After it returns, the caller **registers**, then prints the recipe, then runs doctor:

- **Register after the recipe is final, not before.** `runLocalBranch` currently calls `world.register` with the `configHash` resolved right after its single write (`first-project.ts:432-453`). If landing/limits then edit the file, the recorded hash is stale. Move `register` below `askRecipe` and take the hash from a `resolveLocalRecipe` call made after the last write.
- **For a local project, the land question can move `repo.base`**, because `askLanding` sets `repo.base` to the branch it is given (doc/design/399.md). So register with the base the resolved file ends with. If that differs from the base question's answer, `rev-parse --verify <base>^{commit}` again for `fromSha`, and refuse by name if it is not a branch.
- **The agent pre-check in the local branch must move.** `first-project.ts:387-395` calls `resolveAgent` before any question, and that throws `AgentUnresolvedError` on an absent file once two runtimes are signed in. Before this change no question answered it; now `askAgents` does. Drop the pre-check, or run it after `askRecipe`.

## A new file is created once, with `said`; an existing one is edited per answer

- **An existing file:** each section's `RecipeChange[]` is written as soon as it is answered. That is today's behaviour in `add-github.ts`, and it keeps *"a Ctrl+C keeps what was answered"* (doc/design/399.md:82).
- **An absent file:** steps 2–4 return changes that are collected, together with the caller's seeds, and written in one `setRecipe` call.
  - Local seeds: `repo.base`, `repo.remote`, `env.plantAt` (`first-project.ts:424-430`).
  - GitHub seeds: `repo.base` from `--base`, else `defaultBranchOf` (`add-github.ts:42`). If both are null, refuse by name: *pass --base*.
  - This is #395's rule (`setup-build.ts:7`: *"a new file is written once, by whoever collects every first-run answer — #400"*).
- **Give `setRecipe` an optional `said`, used only when it creates the file.** Today creation is `editRecipe` over a `version:` seed (`write.ts:82`). With `said`, build that same text, parse it the way `editRecipe` checks it (`Recipe.parse({ runtime: {}, ...})`, `emit.ts:119`), and hand the result to `emitRecipe(recipe, said)` (`emit.ts:73`). Then run `resolveSource` as today.
  - When the file exists, `said` is ignored. Later answers go through `editRecipe`, and 0104 §14 governs: *"a key or an item that a change removes or replaces goes with its comments."* Add no check that protects a comment.
  - `emitRecipe` writes every schema default, including all ten steps and `runtime.limits` (`packages/recipe/unit/emit.test.ts`: *"states every limit key, defaults included"*). That is wanted here: the printed file shows every setting.
- **`said` is the sentences the flow shows.** Prompts are questions, not block descriptions. So each section prints one heading line before its questions, and that same constant is its `said` value. Keep them in one `SAID` map in `recipe-flow.ts`, keyed by dotted path: `runtime`, `steps.implement`, `steps.review`, `steps.prepared`, `steps.build`, `source.tickets`, `source.kinds`, `repo`, `steps.proposed`, `runtime.limits`. `env` has no question, so print its sentence when the seed is written. `emitRecipe` **throws** on a key the recipe does not have (`emit.ts:83`); every key above exists once `Recipe.parse` has filled the defaults.
- **The GitHub branch no longer requires an existing recipe.** `askBeforeGithubAdd` currently asks only `if (existing !== null)` and refuses agent flags on an absent file (`add-github.ts:175-180`). Both go: an absent file is now created by the flow, so `add()`'s `RecipeMissingError` is no longer reached from `lingtai add`.

## `--defaults`

- **Flags always win.** `question()` never calls `ask` when `given` is set (`question.ts:80-83`), so `--defaults` fills only what no flag answered.
- **Implement it as a `QuestionWorld` wrapper whose `ask` returns `''`** (empty means take the default). **Guard the loop.** If a default fails `validate`, `question()` logs and calls `ask` again (`question.ts:97-104`), so a wrapper that always returns `''` spins forever. A real case is an agent default that is not signed in. Answer `''` once per prompt and `null` on an immediate repeat of the same prompt. That turns a bad default into the by-name refusal `<name> needs an answer: pass <flag>`.
- **With no TTY and no `--defaults`**, step 1 refuses by name, naming `--defaults`. That is #392's rule, and the refusal names the one flag that completes the run.
- **The trial run:** pass `tryBuild: null` in both callers. `setup-build.ts:210-215` already logs that it was not run. The real `tryBuild` (#397's design: worktree, install, build) takes minutes and is a ticket of its own; open one. With `null`, `--check-build` is never asked.

## Flags

- **`init`'s `parseArgs` requires a value for every flag** (`init.ts:262`). Make `--defaults` the one boolean there.
- Both parsers also accept the recipe flags the questions already name: `--agent`, `--model`, `--reviewer`, `--reviewer-model`, `--install`, `--build`, `--land`, `--rounds`, `--wall`, `--budget`.
- **`--build` is repeatable, and both parsers are last-wins** (`init.ts:243`, `lingtai.ts:376`). Collect every `--build` into `string[]`; `--build none` becomes `[]` (#397's design, §*Do not add*).

## `init`: what moves

- **Start the board lazily.** Today it starts unconditionally before the project question (`init.ts:408`), and a serving board keeps the process alive (`entry.ts:33-42`). A non-TTY `init --store sqlite --local <dir> --defaults` would therefore never exit, and the ticket says that run must complete.
  - Start the board inside `github.boardUrl()` on its first call.
  - Also start it at the end for the paths that open the wizard: an App already configured (`init.ts:478-488`).
  - A local project never starts one. Print a line saying `lingtai board` starts it.
- **The end of the run is:** the recipe path, the file's bytes as read back through `world.files.read`, printed verbatim and unpainted, then doctor's report, then the board line.
  - The GitHub branch in `init` never has a slug (`init.ts:448-458`), so it has no recipe to print. Say that the recipe is written when a repository is picked, and that `lingtai add <owner>/<repo>` asks its questions at the terminal. Then still run doctor.
- **Doctor's verdict is printed and does not set the exit code.** On a fresh machine it is likely to warn about a daemon that has never run, and the Done-when expects exit 0.
  - Add a seam to `InitWorld`, `doctor: () => Promise<string>`. The live one is a **dynamic** `import('./doctor.ts')` that calls `doctorReport()` then `formatReport()`. The import must be dynamic because `init.ts`'s header warns that an eager log read breaks a fresh machine (`init.ts:84-98`).
  - Do **not** call `releaseCheck`. It is the outbound request that `doctor` and `upgrade` alone make (`lingtai.ts:345-348`).
- **Nothing here spends money (#391).** No agent is dispatched. `askRuntimes` only probes whether runtimes are signed in. `tryBuild` is null.

## `add`: move it where a test can reach it

`lingtai.ts` calls `main()` on import, which is why `add-github.ts` exists at all (`add-github.ts:3-5`). Move `addCommand`'s body (`lingtai.ts:408-445`) into `apps/cli/src/add.ts` as `addFlow(args, world)`. `world` is `FirstProjectWorld` plus `doctor` plus `askBeforeGithubAdd`'s deps. `lingtai.ts` keeps a three-line wrapper.

`askBeforeGithubAdd` still reads `hasGitHubApp()`, `askRuntimes()` and `console` directly. Thread `runtimes` and `log` through its deps. The unit test drives the **local** branch of `add`, which reaches none of the App code.

## Re-runs: what "asks every question again" covers

- **Two settled decisions stand.**
  - A store that already answers is reported, not re-asked: *"re-asking would make every run of a finished `init` a chance to answer the wrong way"* (`init.ts:52-62`).
  - A bare `init` on a machine that already has projects lists them rather than re-asking (`init.ts:343-399`, #394 finding 3).
- **So a re-run re-asks every recipe question** for the project the run names: `init --local <dir>`, `add --local <dir>`, or `add <slug>`. Each question takes the file's current value as its default (`question.ts:89`).
- **Unchanged answers write nothing.** `setRecipe` returns `written: false` (`write.ts:187`), and `editRecipe` returns the input when nothing renders differently (`emit.ts:121`). That is what makes *byte-for-byte unchanged* hold. The test checks it rather than assuming it.

## The unit tests, and the seam they need

The full-flow `init` tests are in `apps/cli/integration/init.test.ts` because `config.yml` is a real file. `readConfig`/`writeConfig`/`describeHome` call `node:fs` (`init.ts:209-230`, `:498`), and `storeChoice`/`boardPort` read the file inside `@lingtai/env` (`machineFile`, `packages/env/src/index.ts:126-143`). Under vitest, with no `LINGTAI_HOME`, they read **no** file at all (`index.ts:94-108`), so the `confirm()` read-back after a write would refuse.

Done-when 1 is a `unit/` test, and a temp directory is integration under 0060 §1. Therefore:

- **In `InitWorld`:** add `machine: { read(path): string | null; write(path, text): void; describeHome(home, path): string }`. The live implementation is today's `fs` code.
- **In `@lingtai/env`:**
  - split `machineFile` into a read and an exported `machineFileFrom(path, text)`;
  - give `storeChoice(from, file?)` and `boardPort(from, file?)` an optional second argument that defaults to `machineFile(from)`, so every existing caller is unchanged.
- **`init` passes `machineFileFrom(path, world.machine.read(path))`** everywhere it calls those two.
- **`integration/init.test.ts` builds `InitWorld` objects,** so add the new fields (`machine`, `doctor`) to its fixture. Its order assertions will move with the lazy board. `pnpm typecheck` checks that it compiles. Its assertions run only after the merge, because the integration half (803s) is out of reach in a pass. The four unit tests are the claims that stand in for it.
- **`unit/first-project.test.ts`, `unit/add-github.test.ts` and `unit/setup-build.test.ts` script answers in order.** The new defaults question and the agent questions shift every script. Pass `--defaults` where a test is not about the recipe questions.

`HOME=/nonexistent pnpm test` is the claim to run: every path in this flow reaches for `stateDir()` or `diskFiles` unless the world is threaded all the way through.
