I've read `subscribe.ts`, ES3-2's `WakerPort` and `promiseWaker`, the ratchet's rules for a face, and Effect 4.1.2's racing API. Here is the design note.

# Design: #1049 — `follow` as an Effect, `subscribe` as a face over it

The ticket gives the shape. This note covers three things it leaves open. Two of them are traps that would compile, pass most tests and then hang. The third is where the code goes.

## 1. The race is `Effect.raceFirst`, never `Effect.race`

The ticket says the session "races the session's `lost` against a loop that takes from a `Queue.sliding(1)` of nudges and drains". In effect 4.1.2, `Effect.race` *"Races two effects and returns the first successful result"* (`node_modules/.pnpm/effect@4.1.2/node_modules/effect/dist/Effect.d.ts:8725`). A side that **fails** does not end that race. So a `HandlerFailed` from the nudge loop would sit waiting behind `lost`, which never ends on a healthy connection. The subscription would never stop, `onError(_, 'handler')` would never be called, and `close()` would be the only way out.

`Effect.raceFirst` (`Effect.d.ts:8868`, whose example is `raceFirst(fastFail, Effect.never)` → `"failed: fast-fail"`) ends on the first side to finish, whether it succeeds, fails or dies, and interrupts the other. Use it.

The test that catches this is the ticket's own "a handler that rejects with `e` stops the subscription", **as long as the rejecting event comes from a nudge after catch-up and not from the catch-up drain**. The catch-up drain runs before the race, so it would pass either way. Write the test against the nudge.

How each ending of the race is read:

- **`lost` succeeds** (a clean end; ES3-2's `listener.lost()` with no error, `store-face.ts:234-236`): reconnect after backoff with no `onError`. This matches `subscribe.ts:213-217` today, where `lost` with `err === undefined` reports nothing.
- **`lost` dies:** a defect, reported as `'connection'` by `catchDefect`.
- **The loop fails with `HandlerFailed`:** reported as `'handler'` by `catchTag`, and the subscription stops.

`EventsPort.readAll` has no error channel (`Effect.Effect<Envelope[]>`, `event-store.ts:401`), so a failed read can only reach the session as a defect. It is `'connection'` with nothing extra.

## 2. `fromPromiseWaker` never waits for `ready` inside an acquire

`fromPromiseWaker(waker: Waker): WakerPort` sits beside `promiseWaker` in `store-face.ts`. It is the inverse of `promiseWaker` (`store-face.ts:249-275`). The rule is the one ES3-2 wrote for Postgres: *"Only the client's construction is in the acquire, never the connect. An acquire is uninterruptible, so a connect inside it would make closing the scope wait for a connect that may never answer."* (`wake.ts`, above `makePostgresWaker`).

So `open(nudge)`:

1. makes a `Deferred<void>` for `lost`;
2. `Effect.acquireRelease(Effect.sync(() => waker.open({ nudge, lost: (err) => err === undefined ? succeed : die(err) })), (s) => Effect.sync(() => s.close()))`. Construction only; the release never waits (`subscribe.ts:251-257`);
3. **outside the acquire**, `yield* Effect.promise(() => s.ready)`. This is interruptible, so a scope closed mid-connect abandons it. A rejected `ready` is a defect, reported as `'connection'`;
4. returns `{ lost: Deferred.await(lost) }`.

If `ready` sits inside the acquire, `test/wake-contract.ts:133-145` (close during connect) hangs instead of failing. This was the bug the `closing` deferred existed for (`subscribe.ts:150-157`, `:226-231`: *"`subscribe()` followed immediately by `close()` hung indefinitely, and the daemon inherited it"*).

The production waker goes port → `promiseWaker` → `fromPromiseWaker` → port: `log.waker(…)` returns `promiseWaker(port)` (`sqlite.ts:406`, `choose.ts`), and ES3-2 puts unwrapping it out of scope. That round trip costs one extra root fiber per session. It is correct, because `promiseWaker`'s `close()` aborts its own fiber and never reports `lost` for a close (`store-face.ts:244-248`).

## 3. Where the code goes, and the state cell

**`subscribe.ts`** holds `follow`, the `HandlerFailed` tagged error, `backoffMs`, the cell type and `subscribe`. It has no `async`, so the deferred helper (`:103-140`) goes. `follow(ports, cell)` takes:

```
{ events: EventsPort; waker: WakerPort; fromSeq; batchSize?; backoff?;
  onError?: (error, phase) => void;            // stays a plain callback
  onEvent?: (e) => Effect<void, unknown> | onBatch?: (es) => Effect<void, unknown> }
```

`onError` stays a synchronous callback called through `Effect.sync`. Making it an Effect gains nothing, and every caller's `onError` is synchronous today. If an `onError` throws, that is a defect of `follow` itself and is not classified: the subscription ends, `stopped` becomes true, and the face's promise rejects, which is already caught (below).

**The cell** is a plain object that `subscribe` makes and `follow` writes: `{ lastSeq: bigint, stopped: boolean, caughtUp: { resolve, reject } }`. `caughtUp` is built from one `new Promise` with its executor's functions and a `.catch(() => {})` attached, keeping the reason `subscribe.ts:136-138` gives for that line. `follow` sets `stopped = true` and calls `caughtUp.reject(new Error('subscription stopped before it caught up'))` in **one `Effect.ensuring` around the whole loop**, so a handler stop, an interruption and a defect all reach it. Today only `run`'s normal exit reaches it (`:292-293`). Resolving or rejecting it twice does nothing, so no `settled` flag is needed.

**Lifting promise handlers.** Write `Effect.tryPromise({ try: () => Promise.resolve(options.onEvent(event)), catch: (e) => e })`. Do not write an `async` wrapper, because the ratchet counts every `async`. A handler that throws synchronously throws inside `try`, and `tryPromise` catches that too. `lift` uses `fromPromiseStore(options.store)` for `events`, which already exists and is exported (`store-face.ts:72`, `index.ts:110`).

**`store-face.ts`** gains `followFace(options, cell, signal)` = `return Effect.runPromise(follow(lift(options), cell), { signal })`. The ratchet allows it: its first argument is a call, and `signal` is one of the face's own parameters (`packages/domain/unit/effect-ratchet.test.ts:232-258`). `lift` is a plain function and can sit in either file. `store-face.ts` imports `follow` as a value, and `subscribe.ts` imports `followFace` as a value. That cycle is safe because neither module calls the other at load time. `wake.ts` ↔ `store-face.ts` already has the same cycle (`wake.ts:29`).

**`index.ts`** adds `follow` (and its options type) next to `subscribe` (`index.ts:117`).

**`close()` is idempotent with no flag.** A second `abort()` does nothing, and both calls return the same caught promise. Starting the face with `.then(undefined, () => {})` in `subscribe` is what keeps an abort, or the `onError` defect above, from going unhandled.

## The order inside one session, for the record

1. `nudges = yield* Queue.sliding<void>(1)`. This is **outside** `Effect.scoped`, once per session. A queue left over from a lost session is simply dropped.
2. `Effect.scoped`: open the waker with `() => Queue.offerUnsafe(nudges, undefined)`.
3. Run the catch-up drain, then mark this session as having served, then `caughtUp.resolve()`.
4. `raceFirst(lost, forever(take ≫ drain))`.

A drain repeats until a short batch. Each batch is `Effect.uninterruptible(handler ≫ advance lastSeq)`. `readAll` stays outside the uninterruptible region, so a close waiting on a slow read does not wait for it. Both span names, `Subscription.session` and `Subscription.drain`, go on with `Effect.withSpan`.

Backoff `attempt` lives in `follow`'s loop: it resets after a session that served (`:289`), otherwise it goes up by one. The sleep is `Effect.sleep`, and interruption cuts it short, which replaces the `sleeping` deferred (`:268-282`).
