# Design: discovery's read port (#347)

## Where it goes

Declare the port in `packages/conductor/src/discover.ts`, next to `RunnableNowOptions` (`discover.ts:303`), and not in `tell.ts`. `tell.ts:20-24` says a port is "the shape this needs", declared by the caller that needs it. The caller here is discovery, and `discover.ts` is already exported as `@lingtai/conductor/discover` (`packages/conductor/package.json:14`), which the board imports (`apps/board/src/lib/queued.ts:35`).

Give it its own name. Do not call it `TicketStore`: `ticket-store.ts:5-8` keeps `list`/`get`/`save` for an extraction that "has not happened". A name like `TicketSource` or `TicketReader` makes it clear this is the narrow read half.

## The decision the ticket leaves open: what the two calls return

The method names must stay `listOpenIssues` and `getIssue`. That is the only way `GitHubClient` satisfies the port structurally (`packages/github/src/client.ts:160`, `:177`). What changes is the **return type**. Discovery's helpers are all typed by `@lingtai/github`'s `Issue` (`kindOf` `:53`, `kindLabelOf` `:65-66`, `Considered.issue` `:130`, `considerIssue` `:141`, `assigneeSkip` `:195`). If the port returned `Issue`, the import would stay and the test's "plain object of two functions" would have to build `url` and `body` for every listing.

So declare a listing type in `discover.ts` that has only the fields discovery reads:

- `number`
- `title`
- `state: "open" | "closed"`
- `labels: readonly { name: string; color: string | null }[]`
  - `color` is read for `kindColors` at `:347`, and `kindLabelOf` returns the label.
- `assignees: readonly string[]`
- `dependencies: { blockedBy: number } | null`
  - Only `blockedBy` is read, at `considerIssue`'s `?.blockedBy` check and in the `=== null` unread count at `:343`.

Then retype `kindOf`, `kindLabelOf`, `considerIssue`, `assigneeSkip` and `Considered.issue` to that listing type, and drop `Issue`, `Label` and `GitHubClient` from the import at `:30`. Every current caller passes a full `Issue`, which is a supertype, so those callers and `unit/discover.test.ts` typecheck without being touched.

**`dependencies` is a required key whose value may be `null`. It is never `dependencies?:`.** If it were optional, a second source could leave it out, and `issue.dependencies === null` at `:343` would read `undefined` as *read, and nothing blocks it*. Every ticket would then go silently clear, which is the exact failure `client.ts:91-94` documents ("Null is not 'nothing blocks it'"). A required nullable key makes a source *say* that it did not read dependencies.

**`getIssue` returns the listing plus `body: string`.** [0109](doc/decisions/0109-the-core-takes-a-ticket.md) §1 says: "The listing the queue reads is cheap and holds no body; the body is fetched once, for the ticket that was claimed." So the list call has no body and the by-number call has one. That one call then serves both reads in a pass: `only:` at `:337`, and the body fetch at `conduct.ts:1588`. Line 1588 reads `number`, `title` and `body` and nothing else (`conduct.ts:1621`). The ticket says `:1582`, but the call it means is at `:1588`. Because of this, the port does not contradict 0109; it is what §1 already describes.

## conduct.ts

Do **not** add a field to `ConductOptions`. `options.client` stays `GitHubClient` (`conduct.ts:338`), because the same function also uses it for `owner`/`repo`, `armsOnOrigin`, `currentRecipe` and the `github:` channels (`:565`, `:579`, `:827`, `:1016`, `:1628`, …).

The change is to route the pass's two ticket reads, `runnableNow` at `:1577` and `getIssue` at `:1588`, through one local value typed by the port. For example: `const tickets: TicketSource = options.client`. Then `:1588` reads `tickets.getIssue(…)`, and its result is typed by the port, not by `Issue`. Swapping the source then becomes a one-line change for #330's next ticket, which should be the one that adds an option. Doing it here would create a field with only one possible value.

## What must not move

- Other callers keep passing their `GitHubClient`, unchanged: `schedule.ts:181`, `wizard.ts:89`, `apps/cli/src/status.ts:107`, `apps/cli/src/conduct.ts:181`, `apps/board/src/lib/queued.ts:280` and `board.ts:524`. Structural typing makes this work, and `pnpm typecheck` is the check.
- `board.ts:506` types a value as `Awaited<ReturnType<typeof runnableNow>>`. `Offered` does not change, so this is unaffected.
- `conduct-before-the-claim.test.ts:330` casts a spread of `fakeGitHub` to `GitHubClient`. It still typechecks, so leave it alone. The "unchanged" criterion covers it.

## The new test

Put it in `packages/conductor/unit/discover.test.ts`. Run one set of listings through `runnableNow` twice:

1. With a literal `{ listOpenIssues, getIssue }` annotated by the port, with no `as`.
2. With the existing `fakeClient` at `:381`.

Assert that both return equal `Offered` values. Include one listing with `dependencies: null` so the test also covers `dependenciesUnread`. That makes the unit test check the nullable key, not just the type. This is all unit-level; nothing here needs the integration half.
