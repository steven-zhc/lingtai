## Design note for #837: one chat fold

The ticket already gives the shape. This note covers only what the ticket leaves implicit and the test harness enforces anyway.

### 1. `applyChat` must be a `function` declaration with a string-`case` `switch`

The new `COVERS` check runs `caseLabels('chat.ts', 'applyChat')` (`packages/domain/unit/histories.test.ts:27-49`). That helper has two requirements:

- It only searches top-level `ts.isFunctionDeclaration` nodes whose name is `applyChat`. Anything else throws `applyChat not found in chat.ts`.
- It only collects `case 'X':` string labels that are catalogue event types. With none, it throws *"yields no catalogue case labels — the check would be vacuous"*.

So `export const applyChat = (…) => …` fails, and so does an `if (e.type === …)` chain. Copy `applyControl`'s form (`packages/domain/src/control.ts:161-164`):

```ts
const d = e.data …
switch (e.type) {
  case 'DiscussionAsked': …
  case 'DiscussionAnswered': …
  default: return state
}
```

Those two labels are the only `src/` mentions the Done-when grep allows outside the conductor and the scripts, so writing them in `chat.ts` is fine.

Write `reduceChat` as `events.reduce(applyChat, emptyChat)`, so the fold has one rule. Don't give it a `now` argument: no case reads a clock.

### 2. Where the new histories go

**`lateHistories` already has `run`, `ticket` and `control`** (`packages/domain/test/histories.ts:876-906`). So the ticket's clause about converting a `run`-only `lateHistories` doesn't apply. Leave every existing entry alone.

- **Placement.** Put the two new consts after `late_ceilingLapsedThenResumed` (`:871-874`) and before `export const lateHistories`. Then add a `chat:` key that lists them.
  - `stamp` takes `nextSeq` and `slot` from module-level counters (`:56-63`), so this placement is what leaves every earlier hash unchanged.
- **Stream ids.** Give each new history a stream id no other history uses, such as `chatStream('9001-3')` and `chatStream('9001-4')`. The shape test only checks that each history is on one stream with versions 1…n (`histories.test.ts:105-111`). The hash lock is keyed by `chat.<name>`, so a shared id would not fail a test, but it would make the fixtures harder to read.
- **Reuse the fixtures.** Use the existing `ASK` and `ANSWER` (`:400-409`). The retried request is `[ASK, ASK, ANSWER]`. D14's cell is `[ASK, {...ASK, question: 'second'}, ANSWER, {...ANSWER, text: 'second answer'}]`. The questions and texts must differ, or the test that the second ask takes the first answer cannot tell the turns apart.
- **The `singles` cast.** `singles` casts `kind` to `keyof typeof histories` (`histories.test.ts:51-57`). `chat` is already a key there, so a `chat` key in `lateHistories` typechecks without changes.
- **The fold test.** Add `for (const h of singles.filter((s) => s.kind === 'chat')) it(\`chat.${h.name}\`, () => void reduceChat(h.events))` beside the three loops at `:88-93`.
- **The `COVERS` test.** Add the chat line to the test at `:76-81` and retitle it to name `applyChat`.
- **Recording the hashes.** Run the hash-lock test and copy the two new hashes from its failure output into `histories.hashes.json`. Don't compute them some other way.

### 3. The answer's type changes, so each reader maps fields explicitly

`ChatTurn.answer` becomes `PayloadOf<'DiscussionAnswered'>`. That type also carries `turns` and `durationMs` (`packages/domain/src/events.ts:1829-1841`).

- **The board.** `DiscussionTurnView['answer']` (`apps/board/src/lib/task.ts:1061-1071`) keeps exactly `text`, `read`, `cannot`, `proposal` and `failure`, minus `costUsd`. `foldChat` builds that object field by field rather than spreading the payload, because the view is serialised to the client.
  - Drop the defensive `String(...)` and `Array.isArray` normalising in today's `foldChat` (`:1103-1131`). The store parses every payload before handing it out.
  - The board unit test's hand-built envelopes (`apps/board/unit/discussion.test.ts:20-44`) carry complete payloads, so they still fold.
- **The conductor.** `buildBrief`'s render at `packages/conductor/src/discuss.ts:316` changes from `t.answer ?? '(no answer was recorded)'` to `t.answer === null ? '(no answer was recorded)' : t.answer.text`. Nothing else reads `ChatTurn` outside that file and its unit test:
  - `packages/conductor/unit/discuss.test.ts` passes `history: []` five times, at `:82`, `:111`, `:133`, `:146` and `:178`. That still typechecks.
  - `apps/board/unit/task-page.test.tsx:103` also has `history: []`, but it belongs to a different object.

### 4. The CLI loop

Two lines in `answerOutstanding` change:

- The `outstanding(...)` check at `apps/cli/src/discuss.ts:446`.
- The `asks[...]` index at `:450`.

Both become one `nextRequest(asks, reduceChat(events))`, and the loop ends when it returns `null`. The existing `if (!next) break` is replaced by that check, not kept beside it.

Keep the comment above the loop (*"Until the chat has caught up, not once…"*). Rewrite the comment at `:448-449` (*"Answers land in order, so the nth request is outstanding exactly when there are fewer than n answers"*) to state D14: answered turns are counted against requests, and an answer with no open ask counts for nothing.

`DiscussionRequest` is already imported (`:65`). Import `reduceChat` and `ChatState` from `@lingtai/domain`, the package `reduceControl` already comes from.

### 5. Two `costUsd` reads that stay

`apps/board/src/lib/history.ts:346-357` reads `d['costUsd']` on `DiscussionAnswered` and `DiscussionHeld` to label timeline rows. The ticket doesn't cover that file, so leave both reads alone.

- The `DiscussionAnswered` read is just as dead as the `foldChat` one.
- Changing it changes a timeline row, which a later ticket can do.
- The board's lookup table uses object keys there, not string literals, so it doesn't trip the Done-when grep.

### Edges

The ticket decides every edge on the checklist, and this note adds none.

The only claim that depends on the log is that no real stream holds two asks followed by two answers. The way to check it is the order of `DiscussionAsked` and `DiscussionAnswered` seqs per `chat-` stream. That can't be read from inside a pass, and nothing in this change depends on the answer, because D14's cell is exercised by its own history.
