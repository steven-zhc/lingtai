## Shape for #371: the ceiling is the recipe's, and the first wizard save moves it there

### The decision the ticket left open: option 1, and option 3 is false on this machine

The ticket asks whether **(3) narrow-only makes the window harmless**. It does not, and this machine's own file shows why. The live `~/.lingtai/config.yml` holds no machine-wide limits. It writes them **per project**:

```yaml
runtime:
  agent: claude-code
projects:
  lingtai:
    runtime:
      limits: { turns: 250, wall: 1h, rounds: 3, restarts: 2 }   # (block form in the file)
  nextloom-ai-admin:
    runtime:
      limits: { turns: 300, wall: 2h, … }
```

`rounds: 3` and `restarts: 2` are **above** `LIMIT_DEFAULTS` (2 and 0, `recipe.ts:3227`). Suppose the machine's value could only narrow. On landing, before anyone saved anything, `lingtai` would silently drop from 3 rounds to 2 and from 2 restarts to 0. Option 3 assumed "nothing means `LIMIT_DEFAULTS`, which is lower", and that is untrue for two of the four keys. A dial moved **up** would also be narrowed straight back down, which is attempt 1's *applied-nowhere* refusal under another name.

So the two scopes of the machine file mean different things after this change. **Say so in `local.ts`'s header, which is the file that has to carry it:**

| Where in `config.yml` | What it is | How the resolve reads it |
|---|---|---|
| `projects.<p>.runtime.limits` | The **old home of this project's ceiling**. `machineFiles` wrote it there since #180 (`local.ts:525-535`). It is the misplaced recipe value, not a fact about the machine. | **A fallback, per key, only where the recipe is silent.** Ignored for a key the recipe states. The first wizard save deletes it. |
| `runtime.limits` (machine-wide) | *What I will spend on this machine*: the one argument the ticket says survives. | **Narrows only**, per key: `min(recipe-or-fallback-or-default, machine)`. |

So the window between landing and the first save resolves to **exactly today's numbers**: the recipe is silent and the per-project block fills in. Nothing refuses anything, so no hand-edit is needed first. The first save writes the whole ceiling into the recipe and removes the per-project block. From then on the recipe decides, and only a machine-wide cap can lower it. The machine-wide cap is absent on this machine, so narrowing never fires here today.

This departs from the Done-when's literal wording that *"the machine file's value applies only where it is smaller"*. The narrowing rule holds for the machine-wide scope. The per-project scope is a migration source rather than a narrowing. Without that difference the landing itself changes `lingtai`'s ceiling, which is the thing the ticket says must not happen.

The ADR authority is already in place: [0104](doc/decisions/0104-the-recipe-is-the-pipeline.md)'s *Not built yet* accepts the move. **Edit 0104; do not add a file.** Update §7 (around line 97: *"`runtime.agent` and `runtime.limits`, either machine-wide or under…"*) and drop the ceiling from *Not built yet* (lines 191-197). In both places state the two-scope rule above.

### The reader: `resolveLocalRecipe` (`local.ts:331-458`)

**Delete the machine merge at `local.ts:377-394`.** Move the whole limits computation into the `shape` callback at `local.ts:408`. That callback runs on the raw YAML **before** the preset and before `Recipe.safeParse` (`resolve.ts:212-237`), so the resolved recipe and its `configHash` already include the narrowing. Narrowing after the resolve would desynchronise the hash.

- **Remove `"limits"` from the refusal loop** at `local.ts:413`, leaving `["agent"]`.
- **Do not rebuild `own.limits` from a key list.** That was attempt 1's finding 3 (`local.ts:515` there). Spread it instead: `limits: { ...ownLimits, ...filled }`. Here `filled` holds only the keys that fallback or narrowing changed. Any `round:`, `restart:` or `dollars:` key survives into the parse that way.
- **Make the schema refuse the unknown key.** Change `limits: z.object({…})` in `Recipe.shape.runtime` (`recipe.ts:2969`) to `z.strictObject`. Nothing can be relying on extra keys there today, because a recipe writing `runtime.limits` at all was refused (`local.ts:413`). The refusal then arrives as a `RecipeInvalidError` against the recipe's path, under `runtime.limits`, by name. Check that `LIMIT_DEFAULTS = …limits.parse(undefined)` (`recipe.ts:3227`) still yields the same object after the change.
- **Per key, in the callback:**
  - `effective = own[key] ?? scoped[key] ?? LIMIT_DEFAULTS[key]`.
  - Then `min(effective, shared[key])` when the machine-wide scope states the key.
  - `wall` compares through `parseDuration`.
  - **If `own[key]` is malformed**, for example `turns: "150"`, write nothing for that key and let the schema refuse it. Comparing an invalid value would hide the refusal.
- **`usd`** has no default. Fallback works the same way. A machine-wide `usd` caps an absent one, since any number is smaller than no ceiling.
- **If `own.limits` is present but not a mapping**, leave it alone; the schema refuses it.
- **Provenance**, one row per key, `runtime.limits.<key>`. The value is the applied number and the source is one of:
  - the recipe path,
  - `default`,
  - `${machineFile} (projects.<p>) — not yet in the recipe; the next wizard save moves it`,
  - `${machineFile} — narrowing <recipe-or-default>'s <n>`.

  Keep the row keys exactly as they are. `apps/cli/src/doctor.ts:1469` `provenanceLines` and `apps/board/src/lib/recipe.ts` read them by name, so the doctor prints the ceiling with its source and names any narrowing **without a change to `doctor.ts`**. If a per-project key exists and the recipe overrides it, add the row `machine: projects.<p>.runtime.limits.<key>`, value `<n> ← not applied: the recipe states <m>`. Without it, a stale block reads as live to anyone who opens `config.yml`.

`MachineLimits` stays a `strictObject` (`local.ts:48`), so the machine file already refuses a misspelled key. Leave it.

### The writer: `machineFiles` (`local.ts:462-560`) carries only the agent

- **Stop deleting `runtime.limits` from the recipe text** (`local.ts:521`). `emitRecipe` already writes every limits key, default-valued or not: `new Document(Recipe.parse(recipe))` at `emit.ts:90`, and `Recipe.parse` fills every default. `saidFor` already attaches the page's sentence to `runtime.limits` (`wizard-page.ts:841`). **Today's onboarding loses both because `machineFiles` strips the block.** Removing that one `deleteIn` is the whole of *"emitRecipe keeps every key the operator was asked about"*.
  - **Do not add a default filter to `emitRecipe`, and do not add a `SCHEMA_LIMIT_DEFAULTS`.** Neither exists on `main`. Both were attempt 1's, and they caused findings 2 and 5. With no filter there is no copy to diverge.
  - The Done-when about one declaration is met by `LIMIT_DEFAULTS` staying the only one. Add a test that `emitRecipe(Recipe.parse({…}), saidFor(state))` for an untouched state carries all four keys at `LIMIT_DEFAULTS`, plus the comment. That fails if anyone reintroduces the filter.
- **`choose()` returns `{ agent }` only** (`local.ts:530-535`). The `isDeepStrictEqual` comparison and the refusal (`local.ts:547-556`) compare **`agent` alone**. Otherwise onboarding a project whose section still holds legacy limits is refused for a difference in a field this function no longer owns.
- **`machineFiles` performs the migration.** Whenever `projects.<p>.runtime.limits` exists in the machine text, delete it. If `projects.<p>.runtime` or `projects.<p>` is then empty, delete that too. In that case `machine` is never `null`. This runs on both callers, so onboarding and editing migrate the same way. Rewrite its docstring and the `MachineFiles` field comment (`local.ts:476-483`): the recipe keeps its limits now.
- **Ordering inside `editExisting`:** the recipe text must carry the full ceiling in the same result that deletes the legacy block. The next section enforces that.

### The board's save: `editExisting` (`apps/board/src/app/setup/wizard/finish.ts:110-162`)

- **`after`** (`finish.ts:118-121`) stops forcing `limits: ceilingOf(recipe)`, where `recipe` is the file resolved alone, i.e. defaults. It keeps `drafted`'s ceiling: `limits: ceilingOf(drafted)`. **Keep `ceilingOf`, not `limitsFor`.** The #314 reason in `settings.ts:107-111` is unchanged.
- **Write the whole block when migrating.** Write `{ path: ["runtime","limits"], value: ceilingOf(drafted) }` in place of the per-key changes when either:
  - the machine text holds `projects.<p>.runtime.limits`, or
  - a limits dial moved and the file does not state all of the ceiling's keys.

  This mirrors how `wholeSteps` (`wizard-page.ts:851`) writes a block whole. Per-key changes come from `PATHS` (`wizard-page.ts:806-809`), which only emits keys that differ from the file-alone resolve, i.e. from the defaults. They would leave `wall: 2h` unwritten on `nextloom-ai-admin`. That reads the same today, but a later schema default change would move it, and the page showed it. The `describes` read-back (`finish.ts:122-123`) then proves the file alone carries the ceiling. That read-back is what makes deleting the legacy block safe: if the recipe would not say the same numbers on its own, nothing is offered.
- **The machine half** (`finish.ts:141-153`): call `machineFiles` when the agent changed **or** the legacy block exists. Drop the `runtime` filter's limits from `changed`. A limits change is now in `changes` and is reported as `runtime.limits…`.
- **No refusal on a machine-wide cap.** If a dial is raised above a machine-wide `runtime.limits`, the save writes the recipe and the cap still narrows. That is the narrowing rule working, and the page says it in one sentence rather than refusing. The scoped provenance row already has the words. **Nothing in this path may compare the applied ceiling with the dial and refuse.** That comparison is attempt 1's dead board.
- `wizard.tsx:183-190`'s note *"The agent and the limits are this machine's"* becomes a statement about the agent, plus a line saying the limits moved into the recipe when the machine text is shown because of the migration.

### Onboarding: `startOnboarding` (`packages/conductor/src/wizard.ts:313-381`)

Almost nothing changes here: it goes through `machineFiles` and `resolveLocalRecipe` with an in-memory `read` (`wizard.ts:365-371`). The recipe now carries the page's ceiling, every key explicit, so a wider `config.yml` value has nothing silent to fill. **Do not add attempt 1's per-key guard** (`wizard.ts:405` there). The read-back resolve is the check, and it cannot disagree with the page unless a machine-wide cap narrows. In that case the cap's provenance row says so, and the onboarding is not refused.
