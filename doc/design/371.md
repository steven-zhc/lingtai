## Design: #371, the ceiling moves into the recipe

### Where the change goes

Most of the change is in `packages/recipe/src/local.ts`. The schema already accepts the ceiling: `Recipe.runtime.limits` in `packages/recipe/src/recipe.ts:2970-3065` declares all five keys with their defaults, and only `local.ts` refuses it. So the first Done-when box needs no schema change. You get it by deleting `"limits"` from the refusal list at `local.ts:415` (`for (const key of ["agent", "limits", "assignee"])`).

The merge moves out of the loop at `local.ts:360-375` and into the `resolveSource` callback at `local.ts:407-426`. That is the only place that can still see what the recipe *wrote*. After `Recipe.safeParse`, a missing `turns` and a written `turns: 300` look the same, because of `.default({ turns: 300, wall: "2h", rounds: 2, restarts: 0 })` at `recipe.ts:3065`. The callback already keeps `wrote = structuredClone(raw)` for this reason (comment at `local.ts:397-401`). Resolve each key there from `own.limits?.[key]` (the recipe's) and `scoped?.limits?.[key] ?? shared?.limits?.[key]` (the machine's, with the same scoped-over-shared order as today). Then write the result into `raw["runtime"]`, as `local.ts:424` does now.

### Per key, in this order

| recipe wrote it? | machine wrote it? | applied value | provenance `where` |
|---|---|---|---|
| no | no | `LIMIT_DEFAULTS[key]`; `usd` stays absent | `default` |
| no | yes | the machine's | the machine file, as today |
| yes | no | the recipe's | the recipe path |
| yes | yes, smaller | the machine's | the machine file, plus `narrowing <recipe path>'s <n>` |
| yes | yes, equal | the recipe's | the recipe path |
| yes | yes, larger | **refused** | — |

**Decision 1: a key the recipe does not write sets no ceiling, so the machine's value applies unchecked.** If a silent key were compared against `LIMIT_DEFAULTS` instead, this machine's `rounds: 3` would exceed the default `rounds: 2` and be refused on the day this lands. `conduct.ts` would then answer `stage: "recipe"` for every ticket and the daemon would take nothing. With this rule, landing the change is a no-op on both live machines: today no recipe can contain `runtime.limits` (it is refused), so every key resolves through row 2, exactly as it does now. The `configHash` of every live project does not move. A unit test can check that claim: with a recipe that writes no limits, the resolved hash is identical before and after.

**Decision 2: equal is not narrowing, and it applies the recipe's value.** This is the same rule as `recipe.ts:3147` (*"**Equal is not wider.**"*). It makes the person's migration step safe to do halfway. They copy the values into `recipe.yml` and leave `config.yml` alone, every key resolves through row 5, nothing changes, and deleting the machine's copy afterwards changes nothing either.

**Decision 3: a larger machine value throws `MachineConfigInvalidError`, not `RecipeInvalidError`.** Throw it from inside the callback. `resolveSource` calls the callback outside any `try` (`resolve.ts:220-223`), so the throw reaches the caller intact. The remedy is usually in the machine file, so that is the file the error names first. The message must also name the key, both numbers and both files: `projects.lingtai.runtime.limits.rounds is 3 in <config.yml>, above <recipe.yml>'s 2 — the recipe states the ceiling and this file may only lower it. Nothing was applied`. The ticket's Done-when outranks its own Watch out here. The Watch out says the machine "will silently get the lower one", but the Done-when asks for a refusal, and a refusal is what makes the change loud rather than discovered later.

**Comparing values.** Compare only values that pass their own schema checks: `positiveDuration` for `wall` (`recipe.ts:3234`), and a number for the others. A malformed recipe value, for example `wall: "90"`, is applied as written so that `Recipe.safeParse` refuses it by key name, as #218 requires. Do not call `parseDuration` on an unchecked string; `recipe.ts:3153-3173` explains why that throws past the named refusal. Compare `wall` through `parseDuration`, never as strings: `90m` is smaller than `2h`. `usd` compares numerically, and a recipe with no `usd` means row 2.

### The doctor box is mostly provenance

`recipeRow` already prints every provenance entry through `provenanceLines` (`apps/cli/src/doctor.ts:1469`, `:1573`, `:1586`). So "prints the resolved ceiling with its source" is already true once the `where` is right. "Names any key where the machine is narrowing" is the `narrowing … 's <n>` suffix in row 4.

Keep the arrow format `value ← where`. The board splits on `PROVENANCE_ARROW` (`local.ts:225`, `provenanceSource` at `:235`) and prints `where` in its own column (`apps/board/src/lib/recipe.ts:710-717`, `:752-760`). A longer `where` renders fine there. A second arrow would not, so don't add one.

Update the comment at `doctor.ts:1663-1665` (*"this row is about what `~/.lingtai/config.yml` says"*). After this change it is about the recipe's ceiling as narrowed.

### The trap: the wizard and the board still write limits to the machine file

`machineFiles` (`local.ts:490-526`) removes `runtime.limits` from the recipe text (`:512`) and writes `ceilingOf(recipe)` under `projects.<p>.runtime` (`:524`). It has two callers: onboarding in `packages/conductor/src/wizard.ts:342` and the board's edit in `apps/board/src/app/setup/wizard/finish.ts:143`.

Left alone, this keeps writing new ceilings into the file this ticket is moving them out of. Worse, once a person has moved the values into `recipe.yml`, a board edit that *raises* `turns` writes the higher number to `config.yml`. That machine value is then larger than the recipe's and refused (row 6), so the next pass of that project is refused.

So `machineFiles` stops moving limits:

- `runtime.limits` stays in the recipe text.
- `choose` writes `agent` and the kept `assignee` only.
- On `replace`, it keeps whatever `limits` the project section already had, the same way it keeps `assignee` at `:525`. A narrowing a person wrote by hand is not removed by a board save they did not read as touching it.

Update the docstrings at `local.ts:462-489` and `wizard.ts:288-293`. The `#314` comment at `local.ts:520-523` is about writing the ceiling into `config.yml` and goes with that line.

What to watch: `finish.ts:121-123`'s `describes` compares a `resolveRecipe` of the file text (no machine merge) against `after`. Check that the board's unit tests still read back once limits are in the file text, and run the `apps/board` and `packages/conductor` unit tests specifically.

### Known and left alone

The step-narrowing check in `Recipe.superRefine` (`recipe.ts:3151-3212`) compares a step's `limits:` against the *applied* ceiling, which is now possibly machine-lowered. A machine `turns: 150` beside a step's `turns: 200` under a recipe's `300` is refused with *"runtime.limits.turns is 150"*. This already happens today, and the machine is still allowed to narrow, so keep it. The provenance row says where the 150 came from.

### The migration paragraph

Put this in `doc/operating.md`, beside the machine-file section around line 448. Say it there so a person reads it before they meet it:

- Landing this changes nothing on its own.
- The person's step afterwards is to move each project's `runtime.limits`, comments included, into `~/.lingtai/<project>/recipe.yml` under `runtime:`.
- A value left in `config.yml` that is **equal** to the recipe's is harmless. One that is **larger** stops that project at `stage: "recipe"` until it is lowered or deleted.
- `lingtai doctor` shows which file every number came from.

### Checks

Everything here is unit-level: `packages/recipe/unit/local.test.ts` with its `files({...})` reader, and no Postgres or `HOME` involved.

- **Replace** the test at `local.test.ts:402-411`, which asserts `/runtime\.limits: moved to this machine/`. Keep one that still refuses `runtime.agent`.
- **One case per table row,** asserting both the applied value and its provenance entry.
- **Scoped over shared, under narrowing:** shared `turns: 100` and scoped `turns: 200` against a recipe's `150` is refused, because the scoped value is the machine's value.
- **Malformed wall:** a recipe `wall: "90"` beside a machine `wall` is refused by `RecipeInvalidError` naming `runtime.limits.wall`, not thrown out of the comparison.
- **The landing-day claim:** with a recipe that writes no limits, the `configHash` is unchanged.
- **`machineFiles`:** the output recipe text keeps `runtime.limits`, and on `replace` an existing project-level `limits` survives.

Then run `pnpm typecheck` and `HOME=/nonexistent pnpm test`.

What a unit test cannot show is the two live machines resolving the same hash after the merge. The thing that would settle it is the next `ConductorStarted` and the `configHash` on the first pass event after it, compared with the one before. That needs a log an agent cannot read, so leave it to the person doing the migration.
