# Design note: #1022, the hook server's scope and the face it leaves

The ticket covers most of the shape. This note settles four points it leaves open, each of which could be built two ways.

## 1. Use one `FiberSet`, made with `FiberSet.make()`, and not two `makeRuntime` calls

The ticket says to use `FiberSet.makeRuntime` for requests and `FiberSet.makeRuntimePromise` for `flush`. In `effect@4.1.2`, each of those makes **its own** set (`node_modules/.pnpm/effect@4.1.2/node_modules/effect/dist/FiberSet.d.ts:138, :179`). The release must interrupt one set by name (step 1, "`FiberSet.clear` on the set below"), so build it like this:

- `const set = yield* FiberSet.make()` (`FiberSet.d.ts:106`), inside `serveHookServer`, before the `acquireRelease`.
- `const fork = yield* FiberSet.runtime(set)()` (`:558`) for the socket's line handler.
- `const runPromise = yield* FiberSet.runtimePromise(set)()` (`:600`) for `flush`.
- The release calls `FiberSet.clear(set)` explicitly as its first step. The set's own finalizer is not enough. It was added to the scope **before** the server's release, so it runs **after** it, and by then the sockets would already be gone and `server.close` would already have waited. `clear` is `Fiber.interruptAllAs(...)` and does nothing on a closed set (`FiberSet.js:306-311`).

Hand `fork` and `runPromise` to the private `createHookServer`, or make it an `Effect.gen` that yields them. Do not make it a public option, because `createHookServer` stops being exported.

The ratchet does not count either function. It counts `Effect.run*` property accesses and `run*` names *imported* from `effect` (`packages/domain/unit/effect-ratchet.test.ts:89-110, :130-145`). A local `const fork` or `const runPromise` is neither. Do not import `runFork` or `runPromise` as bare names from `effect`, because that does count.

## 2. The request fiber catches defects, not interruption

Today a throw anywhere in the IIFE gets a fail-closed reply (`hook-socket.ts:333-338`). The Effect version must keep that and must **not** reply when it is interrupted. The release's step 2 depends on that: the hook sees the socket close with no answer.

Build it this way:

```
Effect.sync(() => JSON.parse(line) as Request)   // a bad line is a defect
  .pipe(Effect.flatMap(decide),
        Effect.catchDefect((err) => Effect.succeed({ allow: false, reason: `lingtai-hook: ${redact(String(err))}` })),
        Effect.flatMap((reply) => Effect.sync(() => socket.write(`${JSON.stringify(reply)}\n`))))
```

- `catchDefect` (`Effect.d.ts:5362`) leaves an interruption alone, so an interrupted fiber writes nothing.
- `catchCause` (`:5218`) would see the interruption too and write a reply. That is the wrong choice.
- `decide`'s own `append(...).catch(() => {})` sites (`:229`, `:237`) become `append(...).pipe(Effect.catchDefect(() => Effect.void))`. They swallow the store's rejection and keep going, as they do today.

`append` is `Effect.promise((signal) => store.append(...))` (`Effect.d.ts:1217`). When it is interrupted, the fiber ends without waiting for the store's promise to settle. The integration test depends on that: a store whose `append` never settles must not hold the scope's close.

`decide` stays synchronous for every hook except `PreCompact` and `Notification`. Write it as a plain `Effect.gen`, not an `Effect.fn`, so it gets no span (decision 7).

## 3. `flush` after the scope closed

`flush` becomes `(runId) => runPromise(flushEffect(runId))`. It is a method, so the ratchet sees no `async` and no run.

- Called while the set is still open: it resolves, or it rejects with the store's own error. The promise runtime squashes the cause, so the error comes out unwrapped.
- Called after the set has closed: the fiber is interrupted at once, and the promise rejects.

Its one caller swallows both rejections. That caller is now at `packages/conductor/src/conduct.ts:3904` (the ticket says `:3896`; the line has drifted): `Effect.promise(() => server.flush(runId).catch(() => {}))`. Nothing changes for it.

`flushEffect` keeps `run.touched.splice(0)` *before* the first append (`hook-socket.ts:313`), so a flush that is interrupted halfway does not re-append on a later call.

## 4. The socket set lives inside the server

- In the `createServer` connection listener, add each socket to a `Set<Socket>` and remove it on `'close'`.
- The `'data'` handler stays Node's callback and calls `fork(...)` for each whole line.
- Keep the empty `'error'` listener (`:342-345`). A destroyed socket still emits `'error'` for a write in flight, and an unhandled one would crash the conductor.

Release steps 2 to 4 are each `Effect.sync`, `Effect.callback` or `Effect.promise`, each followed by `.pipe(Effect.ignore)` or an equivalent, so one failed step does not skip the next. Run them in one `Effect.gen` and do not chain them with `andThen` on a failing effect.

Listening is `Effect.callback` (`Effect.d.ts:1724`):

- It resumes with `Effect.void` on the listen callback, and with `Effect.fail(new AgentHostFailed({ operation: 'serve', detail }))` on `'error'`.
- It removes the `'error'` listener on success. Today's `once('error', reject)` (`:348`) is left attached after a successful listen.

## Tests

- **Integration (`packages/agent/integration/hook.test.ts`).** This is the only place the per-request fiber can be seen, and the ticket puts that case there. That half does not run in the `build` step, so the agent must run this one file by name before committing: `pnpm exec vitest run --project integration packages/agent/integration/hook.test.ts`. It uses the memory store and needs no database.
- **Unit (what `build` sees).**
  - `writeHookWiringEffect`'s `SUN_PATH_MAX` refusal.
  - The ratchet itself, with `packages/agent` at `{ "async": 11, "run": 0 }` and the `openRunLog` face entry. The entry's shape is like the `packages/repo` entries already in `effect-ratchet.faces.json`: `"until": "#790"`, `"why": "apps/cli/src/discuss.ts:377 awaits it"`.
  - The face's body must be exactly one `return Effect.runPromise(openRunLogEffect(options))` with one argument, or `face()` refuses it (`effect-ratchet.test.ts:197-265`).

## Nothing here contradicts an ADR

- Keeping the swallow at `:229` and `:237` is 0101 §6 as the ticket reads it.
- The scope owning the close is what 0026 asked of `serveHookServer` (`hook-socket.ts:366-374`).
- Update that doc comment in place. Its last paragraph, about the release swallowing its own failure, still holds. Add one sentence saying the release also interrupts in-flight requests and destroys their sockets first.
