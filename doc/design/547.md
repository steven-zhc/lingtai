# Design: an explicit `turns: unbounded` for runtimes that cannot hold a turn ceiling (#547)

## The decision: one string literal, `unbounded`, and the default stays 300

`runtime.limits.turns` becomes `z.union([z.number().int().positive(), z.literal('unbounded')]).default(300)` at `packages/recipe/src/recipe.ts:3267`. Leave the `.default({ turns: 300, … })` at `recipe.ts:3361` and `LIMIT_DEFAULTS` (`recipe.ts:3522`) unchanged.

The other spellings that look obvious each fail somewhere:

- **Absent meaning unbounded, or a default that depends on `runtime.agent`.** `configHash` is the hash of the *resolved* recipe (`recipe.ts:233`: *"a `.default({})` on `limits` would change the hash of every project's recipe — including the one stored on every `RunStarted`"*). Either change would rewrite the hash of every recipe nobody edited. It would also quietly remove Claude Code's `--max-turns 300` from every project that never wrote a number. The ticket asks for an *explicit* choice, and absent is not explicit.
- **`null`.** YAML reads a bare `turns:` as `null`. A person who deletes the number and leaves the key would get an unbounded agent without having chosen one. Refuse `null` by name.
- **`0`.** The field is `.positive()` today, and `rounds: 0` already means something else in the same block (`recipe.ts:3292`). Keep refusing it.

`unbounded` also prints as itself in every surface that interpolates the value: provenance in `local.ts:374`, the doctor row, and the ceiling sentence.

**`wall` gets no unbounded spelling.** Every runtime enforces `wall`, so nothing is unavoidably red there. **`DISPATCH.limits.turns` (`recipe.ts:266`) stays number-only.** Under an `unbounded` ceiling, leaving it absent already means unbounded, and under a numeric ceiling `unbounded` would be a widening. The narrowing refusal at `recipe.ts:3491` (`turns > ceiling.turns`) must treat an `unbounded` ceiling as one that every number narrows.

## Translate at the edge, as `usd` is translated

`usd` has already done this shape (#370): optional on the request and on the event, and absent means no ceiling. Copy it:

- **Request.** `RunRequest.limits` (`packages/agent/src/runtime.ts:122`) becomes `{ turns?: number; wallMs: number; usd?: number }`. Do the same for `agent-action.ts:132`'s `limits`. `spendFor` (`conduct.ts:717`) and the review limits (`conduct.ts:2839`) map `'unbounded'` to absent. `from-recipe.ts:234` keeps `action.limits?.turns ?? base.limits.turns` unchanged.
- **Event.** In `Invocation.limits` (`packages/domain/src/events.ts:397`), `turns` becomes `.optional()`. This is additive, as `usd` was: every event already on the log carries a number and still parses. Extend the docstring above it the way #370's was extended. The board reads only `wallMs` from it (`apps/board/src/lib/progress.ts:426`). To settle whether a run was actually unbounded, look at `RunStarted.invocation.limits.turns`, which is absent.
- **Claude Code.** When `turns` is absent, omit `'--max-turns', String(request.limits.turns)` (`packages/agent/src/claude-code.ts:283`). Choosing unbounded on Claude Code is legal: it is a choice, and doctor checks promises, not choices. `codex-text.ts:51` (`request.limits.turns < 1`) must guard for absent.
- **`limitsFor` (`packages/recipe/src/settings.ts:131`)** takes a `Math.max` over numbers. It needs a comparison in which `unbounded` is the largest value. `StepBound.turns` (`settings.ts:163`) becomes `number | 'unbounded'`.

Leave `discuss.limits` and `triage.limits` alone. They have their own defaults and run outside any pass (`recipe.ts:2863`).

## One phrase for display, so no surface invents a 300

Add a single formatter in `packages/recipe` beside `formatDuration`, and route every `${…turns} turns` that can see a ceiling through it:

- `passCeiling` (`packages/conductor/src/ceiling.ts:71,79,80,83`)
- `apps/board/src/app/plan.tsx:50` and `apps/board/src/lib/queued.ts:187`
- `apps/board/src/lib/recipe.ts:780`'s dial
- the wizard's `limitsSentence` (`packages/conductor/src/wizard-page.ts:568`), which today refuses anything that is not an integer of 1 or more and has to accept `'unbounded'`

For a numeric ceiling the output must be **byte-identical** to today's (`ceiling.ts:72`: *"Byte-identical to the pre-#370 text when `usd` is absent (0070 §8's rule"*). The existing `passCeiling` tests pin this; do not edit their expected strings. For `unbounded`, write something like `2h and no turn limit each`. Per-run counts such as `RunFinished.turns` and card pills are spend, not ceilings, so they are untouched.

## Doctor: what counts as a promise

In `limitsRow` (`apps/cli/src/doctor.ts:1802`), a `turns` value of `'unbounded'` is handled like an absent `usd`: it is excluded from `ignored`, and the detail reads `turns — unbounded`. That makes Codex with `turns: unbounded` and no `usd` green: `wall` is applied and nothing else is promised.

A numeric `turns` on a runtime that does not enforce it **stays `fail`**. The status does not change; the lever does. `doctor.ts:1834` (*"no edit to the recipe clears them: `turns` is always present and has no spelling for *unbounded*"*) is now false for `turns`. The lever should name both ways out: write `runtime.limits.turns: unbounded` to accept no turn ceiling, or name a runtime that applies `turns`. Rewrite the docstring paragraph at `doctor.ts:1788–1792` so it says that the spelling exists, and stop calling `--despite-doctor` the waiver for this case.

**A gap this change opens:** a dispatch's own `limits.turns` on Codex. `limitsRow` reads only the ceiling (`doctor.ts:1810`: *"a step's reduction is neither"*). Until now the numeric ceiling kept every Codex project red, so a step's `limits: { turns: 50 }` was never the only red. Once the ceiling can be unbounded, that step would read green while promising 50 turns that nothing holds. That is #89's exact shape.

So in this change, also count `turns` as declared whenever a dispatching step's own `limits.turns` is set and that step dispatches the runtime whose capabilities were passed in. That is `implement` with no `agent:`, plus any action whose `agent:` equals `capabilities.id`. Steps that name a *different* runtime than the one `limitsRow` is handed belong to #207's role-aware doctor and are out of scope.

## First run: init writes the choice

`askAgents` (`apps/cli/src/agents.ts:296`) is where `runtime.agent` is written, and both `init` and `add` go through it. When the chosen writer's `capabilities.enforces` omits `'turns'`, push `{ path: ['runtime','limits','turns'], value: 'unbounded' }`. Build it with a helper in `packages/recipe/src/answers.ts` next to `wallChange` and `budgetChange` (`answers.ts:99,111`).

- Decide from **capabilities, not the string `codex`**, so the next runtime that cannot hold turns gets the same behaviour.
- Write it **only when the recipe file does not already declare `runtime.limits.turns`**. Check the source text, as `originIn` does in `local.ts`, not the resolved value, which is always 300. An explicit 150 somebody wrote must stay, and stay red. Overwriting it would be exactly the silent downgrade the Watch out forbids.

Apply the same rule to the board wizard's `applyDraft` (`wizard-page.ts`) when the draft's agent becomes such a runtime. `fromRecipe` (`wizard-page.ts:387`) must round-trip `unbounded` rather than coercing it to a number.

## Docs that state the old behaviour

- **`doc/decisions/0106-a-role-keeps-its-powers-across-runtimes.md` §9 and §10.** §9 says `runtime.limits` holds *"`turns` (default 300)"* and that a defaulted `turns` *"already does"* read Codex red forever. §10 says the limits row *"fails for a Codex project"*. The project's CLAUDE.md says a decision that changes is an **edit to its topic's ADR**, not a new file, and 0106 is a `doc/decisions/` topic ADR. So edit §9 and §10 to state the `unbounded` choice and when the row is red; no superseding file is needed. The archived 0070 is not contradicted: the ceiling is still stated once and a dispatch still only narrows it.
- **`doc/tutorial.md:126–128`.** Replace *"Codex may also cause `doctor` to report that its default turn limit is not enforced"*. After `--agent codex`, the recipe carries `turns: unbounded` and doctor is green on limits.
- **Code comments.** `codex.ts:107–109` and `recipe.ts:3349` both say *"permanently"* or *"red forever"*. Correct them.

## Watch out

- Do not change `status` in `limitsRow` for a numeric `turns`. `gatingFailures` in `restart.ts` counts only `fail` (`doctor.ts:1781`).
- Before reading a red `pnpm test` as a claim about the diff, check the `.default({ turns: 300 …})` literal and every test fixture that builds `limits: { turns: 300, … }` by hand. The `turns` field's TypeScript type widens, and `pnpm typecheck` will list each site that does arithmetic on it.

## Checks a unit test can make (all in `pnpm test`; none needs the integration half)

- The recipe parses `turns: unbounded`. It refuses `turns: null`, `turns: 0` and `turns: none` with a message that names `unbounded`. A step's `limits.turns: 50` under an `unbounded` ceiling resolves.
- `limitsRow`:
  - Codex, `unbounded`, no `usd` → `ok`.
  - Codex, `300` → `fail`, and the lever names `unbounded`.
  - Codex, `unbounded`, with `implement` declaring `limits.turns: 50` → `fail`.
  - Claude Code, `300` → `ok`.
  - Codex with `usd` declared → `fail`, as today.
- `passCeiling`: the existing numeric strings are unchanged, and a new `unbounded` case prints no number.
- The Claude Code argument list has no `--max-turns` when `turns` is absent.
- `askAgents` with a writer that does not enforce turns writes `unbounded` once. It writes nothing when the file already declares `turns`, and nothing for `claude-code`.
