Put dependency reconciliation as the first `run:` action in the active `~/.lingtai/lingtai/recipe.yml` **`build:` list**, with its own name, `CI=true pnpm install --frozen-lockfile`, a finite timeout, and `env: []`. Keep the existing checks after it. This uses the existing step rather than adding a lifecycle step: ADR 0104 says, “A step’s plugins run in the order written” (`doc/decisions/0104-the-recipe-is-the-pipeline.md` §3), and the pipeline stops at the first action that does not pass (`packages/actions/src/action.ts:866-887`). Thus an install failure retains the install action’s name and captured output; the process action makes the exit code its verdict and the command log its evidence (`packages/actions/src/process-action.ts:1-13`, `:70-91`).

The operational edit must be applied to the machine recipe after the worktree change is reviewed, then verified there. ADR 0104 says the file is “outside every worktree” and “read on every resolve” (`doc/decisions/0104-the-recipe-is-the-pipeline.md` §1); a repository edit cannot activate it. Leave a reviewable record with the intended stanza and, once applied, the resolved recipe and a headless reproduction’s result. The reproduction should establish that a dependency change made after `prepared` reaches the checks on the next `build` visit, including a fix round, and that a deliberately failing install is attributed to the install action. The unit-level claim is action ordering and failure attribution; the 803-second integration suite is outside this pass’s verification budget, as ADR 0115 says, “Nobody runs the integration half while doing a ticket” (`doc/decisions/0115-unit-gates-integration-follows.md` §5).
