## Design note: #365 (`check.yml`)

`lock.yml` is the template for this, and copying it settles most of the shape. These are the decisions it doesn't settle.

**One job, one runner, one Node: `ubuntu-24.04`, `node-version: 22.13.0`.** `lock.yml`'s matrix is there for a reason specific to the lock: *"the lock written against the second threw on the first"* (`.github/workflows/lock.yml:9-11`). The unit half has no such per-platform claim, so a matrix would double the cost and prove nothing new. Use the `engines` floor (`package.json:9`, `">=22.13"`) and not a current Node. The floor is the version a feature is most likely to be missing on, and the ticket's 22.22 measurement already covers a newer one. If a Mac or Node 26 run turns out to matter, add it as a matrix row later. It does not belong in this ticket.

**Copy the setup steps exactly:** `actions/checkout@v4`, then `pnpm/action-setup@v4` with no `version:`, then `actions/setup-node@v4` with `cache: pnpm`, then `pnpm install --frozen-lockfile`. `pnpm/action-setup` picks the version up from `packageManager: "pnpm@11.9.0"` (`package.json:7`). Pinning a version in the workflow as well gives two sources of truth, and the action fails when they disagree.

**Two named steps, not one `&&`.** One step runs `pnpm typecheck`, the next runs `pnpm test` with `env: HOME: /nonexistent`. Two steps let the PR's check page show which half went red. The recipe's `build:` joins them with `&&` because it only reports a single exit code; a workflow doesn't have that limit. Set `HOME` through the step's `env:` and not as a prefix inside `run:`, so the claim is visible in the YAML. Do not add a `--project` flag: the `test` script is already `vitest run --project unit` (`package.json:15`), and repeating it would hide a later change to that script.

**Name the workflow and job `check`.** The ticket says lint and format steps will be added to this workflow later, so a name like `unit` would be wrong after the next ticket. Start the file with a header comment in the same style as `lock.yml:1-15`. It should say three things:
- It is the unit half only, and why not integration (803s, T11).
- No `LINGTAI_*` secrets are used.
- It is deliberately not a required check, because the merge lane is `git merge --no-edit` plus a push and never a PR (`packages/actions/src/merge-action.ts:47`).

The same reason goes into CLAUDE.md, next to the `pnpm test` / `pnpm test:integration` block at `CLAUDE.md:317` onward. Put it in the paragraph that already explains that the `build` gate runs `pnpm test`, and say that this check is the second witness for PRs that the conductor did not make.

**Nothing in the conductor, the recipe or `.lingtai/config.yaml` changes.** This ticket adds no code and no tests, so `pnpm test` cannot show that the workflow works. The only evidence is the check going green on the PR that adds it, which is the ticket's third *Done when*.
