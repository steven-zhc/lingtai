# #557 design: the `ContinueConflict` contract

## Scope: the contract only. Nothing in this ticket can append it.

This ticket is one of three, and the split decides the shape:

- **#557 (this one)** adds the types, the eligibility rule, triage's right to advise the move, and a pure check.
- **#558** adds the effect behind `resolveWait`: it rechecks the remote ref, dispatches the agent and folds the result.
- **#559** adds the board card and the CLI command.

So when this lands, no person and no daemon can write `WaitResolved{ContinueConflict}`:

- `resolveWaitHolding` (`packages/conductor/src/resolve-wait.ts:169`) needs a refusal by name, placed right after the `not-offered` check at `:210-218`. Use something like `reason: 'not-built'`, with a detail that says no continuation runs yet. It must refuse before any append.
- **Why a refusal is needed:** the `WaitResolved` fold in `packages/domain/src/ticket.ts:373-379` sends every resolution that is neither a requeue nor `Approve`/`GrantFixRound` to `return { ...state, ...at }`. The lifecycle would stay `blocked` on a wait that has been resolved, and nothing in `conduct.ts:964-1000` would ever pick it up. Leave the fold alone; deciding where `ContinueConflict` folds is #558's job.
- A unit test in `packages/conductor/unit/resolve-wait.test.ts` should pin it: an eligible wait plus a well-formed `ContinueConflict` returns `ok: false` and the stream length does not change.
- **The board:** `RESOLUTION_COPY` in `apps/board/src/app/standing.tsx:47` is a `Record<Resolution['_tag'], …>`, so `typecheck` will force an entry. Give it copy, then drop `ContinueConflict` from `resolutionCards` (`:561`). Until #559 there must be no clickable card that the server refuses. Also, `recommended` (`:543-544`) must not point at a card that isn't drawn, so map an advised `ContinueConflict` to `null` there, the same way `:544` handles `GrantFixRound` when there's no work.

## The stored command

Put this in `packages/domain/src/wait.ts`, next to `GrantFixRound` (`:206`):

```ts
ContinueConflict {
  baseSha: string, headSha: string, ref: string,
  hunks: ConfirmedHunk[],        // 1..MERGE_HUNKS_ONE_BY_ONE
  grantExtraRound: boolean,
}
```

Define `ConfirmedHunk` in `packages/domain/src/triage.ts`, next to `Hunk` (`:56-77`). `wait.ts` only imports leaf modules (`wait.ts:20-21`: *"Imports leaves only, never `events.ts`"*), and `triage.ts` is the leaf both files already share:

```ts
| { _tag: 'Mechanical', path, line }
| { _tag: 'Divergent', path, line, behavior: string /* trimmed, non-empty */,
    adopted: { questionId: string, answerId: string } | null }
```

**The non-obvious decisions:**

1. **Every counted hunk is listed. A hunk left out does not mean "mechanical".**
   - With no triage, nothing has classified the hunks, so the person classifies each one.
   - Requiring the full set means the command alone answers "what did the person confirm for hunk X". It never depends on a triage result that a later attempt could replace.
   - Identity is `(path, line)`. That is the same identity `apps/cli/src/triage.ts:741-755` uses to accept triage's own classification, built from the mirror's `hunkLines` (`packages/repo/src/mirror.ts:196-206`).
   - Use the same identity, not a new index.

2. **`behavior` is the authority. `adopted` is only where it came from.**
   - The person's confirmed text is stored word for word, and #558 dispatches from that text.
   - `adopted` records that the person took triage's answer unchanged. It is `null` when they wrote or edited the text, and always `null` when triage is `NotDeclared` or `Failed`.
   - Nothing may resolve `adopted` back into a triage answer to get the behavior. That would turn a recommendation into authorization, which is what the ticket's Watch out row forbids.

3. **`ref` is added**, even though 0118 §1's illustrative type (`0118-a-hold-explains-itself.md:227`) doesn't show it.
   - A sha with no ref is ambiguous about which branch is the preserved one.
   - `GrantFixRound` already carries `ref` for the same reason, filled in by `resolveWait` at `resolve-wait.ts:291`.
   - Keep the ADR's own name `grantExtraRound`.
   - Do not edit 0118 for these extra fields. #564 is the documentation ticket that brings 0118 up to date with what was built.

Also update the comments that enumerate the resolutions, since they become false:

- `events.ts:305-307`: *"`Approve`, `Requeue`, `EditBodyAndRequeue`, `AnswerQuestion` or `Close`"*
- `wait.ts:227-234`: *"the only field one ever carries beyond its tag is `Approve`'s `onSha`"*

## Eligibility: `allowedResolutions`

`ContinueConflict` is appended (it does not replace the existing row at `wait.ts:267-269`) only when all of these hold:

- the reason is `ProposedEscalated`
- `proposal._tag === 'MergeConflict'`
- `baseSha !== null` and `headSha !== null`
- the run is not `unpushed`

Build it the way `fixable` is built at `wait.ts:311-320`.

**Why the nulls matter:** `MergeConflict`'s shas are nullable (`proposal.ts:66-76`: *"`null` where the action's result carried none"*). The CLI triage path already uses the same test before it counts any hunk (`apps/cli/src/triage.ts:466`).

**`MergeRefused` never qualifies, whether as a direct wait or as `ProposedEscalated{MergeRefused}`.** Its `reason` is `RefusalReason.exclude(['conflict', 'verify-failed'])` (`wait.ts:131`), so a wait like that is not a conflict, even when it carries `baseSha`/`headSha` (`:134-135`).

Write a test that builds one *with* both shas and asserts `ContinueConflict` is absent. That is the trap the ticket's Watch out row names.

**What stays out of the pure function:** the domain cannot see whether the remote ref still exists. That check belongs to #558's `resolveWait` effect, following `GrantFixRound`'s `refSha` check at `resolve-wait.ts:275-290`.

## The pure check (the "stale" and "missing-proposal" cases)

Add one exported function to `wait.ts`:

```ts
continueConflictRefusal(reason, resolution, counted: readonly { path; line }[])
```

It returns `null` or a tagged refusal:

| Refusal | When |
|---|---|
| `NotOffered` | `allowedResolutions` doesn't offer it |
| `Stale` | the shas differ from the proposal's |
| `TooManyHunks` | `counted.length > MERGE_HUNKS_ONE_BY_ONE` |
| `HunksMismatch` | `(path, line)` sets differ, or there are duplicates |

- `counted` comes from the caller (the mirror's count in #558). That keeps the function pure and gives this ticket's tests a target.
- It never takes a `TriageStatus`. That is how "truthful without triage" holds: the same command validates the same way whether triage was `NotDeclared`, `Failed` or `Done`.
- `TooManyHunks` is the over-20 rule: no list of individual hunks is accepted past the bound, so 0118 §8's *"recommending starting over from the new base"* still holds.

## Triage

**`TriageAdvice` gains `'ContinueConflict'`.** You have no choice here: `_triageAdviceCoversResolution` (`wait.ts:240-243`) makes `typecheck` red until you add it.

**Where to enforce "only with a concrete proposal": a `.refine` on `TriageAdvised` (`wait.ts:594-600`), not in `parseTriage`.** The rule:

```
resolution !== 'ContinueConflict' ||
  (cause._tag === 'ConflictingHunks' && cause.hunks.length > 0)
```

- On the schema, the rule also covers a `WaitTriaged` read back off the log, not just a fresh reply.
- `parseTriage` (`packages/conductor/src/triage.ts:394-397`) already turns a safeParse failure into a `refused` reply with the issue path. No new code is needed there beyond a test.
- `ConflictingHunks`'s own refine (`wait.ts:564`) already forces `hunks: []` past 20. So advice past 20 cannot name `ContinueConflict` either.

**Other triage changes:**

- Add `ContinueConflict` to the `resolution` line in `ANSWER_SHAPE` (`conductor/src/triage.ts:130-132`), with the condition stated, and *"the tag alone"* still true.
- **The mechanical over-20 advice at `apps/cli/src/triage.ts:478-485` stays `Requeue`.** Add a test that it never says `ContinueConflict`.
- Triage advice never builds a `Resolution` value. It carries no shas, no `behavior` and no grant, as 0118 §1 says: *"it never supplies an `onSha` or a conflict's base and head"*. `recommendedResolution` (`wait.ts:507-527`) needs no change: the advice is drawn only where `allowedResolutions` offers it.
