# #768: design note

**Where #763 stands.** #763 has landed in this worktree, so there is nothing to rebase onto. The filter the ticket says to remove is `apps/cli/src/status.ts:614`:

```ts
if (d === 'your judgement is needed' || d === 'a failure needs acknowledging') continue
```

Delete that line in the same commit that removes the `needs` part from `describeWaitLines`. Once the source stops emitting the phrase, the filter can never match, and leaving it in would make the `git grep` in Done when fail. Check `status.test.ts` as it reads now, after #763's rewrite, rather than relying on the ticket's line numbers.

**How `soWhat` tests "blocked".** Test `standing.state === 'blocked'`. Do not test `standing.needs !== null`, which is what the current code keys on (`apps/board/src/app/standing.tsx:1113`). The reasons:

- `state` comes from the lifecycle status (`apps/board/src/lib/task.ts:878`).
- `needs` is null on every block written before #83 (`task.ts:488`: *"null on every block written before #83"*).
- `needs` is also null on an `OwnQuestion` block (`packages/domain/src/wait-words.ts:305`).

Keying on `needs` would let those blocks keep falling through to `standing.who`. The ticket's rule is *rank 3 is the recommendation or nothing, for a blocked item*, and that rule is about the state, not about the field.

**A loss the ticket accepts.** A blocked item with no recommendation shows nothing at rank 3. That includes an `OwnQuestion`, which shows `waiting for your answer` today, through `whoWaits` (`task.ts:772`). It is fine to lose because #764 put that wording in the state word. Pin it in `standing.test.tsx`: an `OwnQuestion` block makes `soWhat` return `null`, and `whoWaits`' `waiting for your answer` still reaches the chip and state word unchanged. Leave `whoWaits` alone. It still speaks for every non-blocked state, as the ticket asks.

**Recommendations outside `blocked`.** Today any state with a recommendation gets ` — recommends …` appended (`standing.tsx:1115-1117`). Since `diagnosis` comes only from a wait's words (`task.ts:918`), a non-blocked item has `diagnosis: null` in practice. Return `standing.who` for every non-blocked state, with no recommendation added, so the two branches cannot both apply.

**The render.** Keep the existing `quiet` guard (`standing.tsx:865`), and add the null check inside it: `quiet || said === null ? null : <p …>`. The comment at `:861-864` says *"`soWhat` returns a string, so there is no path by which a second paragraph lands here"*. Change it to say `string | null`. The guarantee it describes still holds.

**The docs that would go stale.** `describeWait`'s doc and its inline comment (`packages/projector/src/task-view.ts:1086` and `:1114-1115`) say an acknowledgement *"stays what `describeWaitLines` says it is"* and *"is `describeWaitLines`'s to word"*. After this change, an acknowledgement is worded only by its diagnosis, and by nothing at all when there is no diagnosis. Say that in both places.

**Checks.** Every claim this ticket makes can be checked at unit level:

- `soWhat` in `standing.test.tsx`;
- `describeWaitLines` in a new projector unit test;
- `renderStatus` in `status.test.ts`;
- the snapshot.

The one exception is the two `task-view.test.ts` integration assertions (`:934`, `:949`). The reviewer has to check those by reading. The new projector unit test stands in for them, because it asserts the same part list (`['what', 'did', 'rec']` and `['what', 'rec']`) on a diagnosis built by hand.
