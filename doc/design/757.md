**Design note: #757, doctor's `NEXT`**

The ticket's line numbers have moved by about 40. The constant `NEXT` is at `apps/cli/src/doctor.ts:3376-3378`, `todo` is at `:3350`, `toFix` is at `:3440-3466` and `formatReport` is at `:3469-3471`. Everything else in the ticket's evidence still holds.

**Where it goes.** Put `export function nextOf(results: readonly CheckResult[]): string | undefined` beside `toFixSummary` (`:3433-3437`). It is built on `toFix` the same way, so the order is the one the blocks are drawn in, and nothing sorts the rows a second time:

- It returns `undefined` when `toFix(results)` is empty, meaning nothing to fix and so no `NEXT` line.
- Otherwise it returns the first line of the first entry whose `fix?.trim()` is non-empty, trimmed.
- Otherwise it returns `'lingtai doctor --verbose'`.

Merging rows in `toFix` (`:3450-3454`) cannot change the answer: it keeps the first row with a given fix and drops only the later ones.

**Why `undefined` and not always a string.** Today the guard is `next && report.warned + report.failed > 0` (`:3376`). Since deferred rows are always `skip` (`:3191`: `status: 'skip', deferred: true`), and `tally` counts `warned` and `failed` only from `warn` and `fail` (`:3256`, `:3260`), that guard is true exactly when `todo` is non-empty. So `renderDoctor` can become `const nextLine = nextOf(report.results); if (next && nextLine !== undefined) …` without changing when the line appears.

This return type is also what #756 needs. `init.ts:672` and `:676` currently push the literal `'lingtai doctor --verbose'` when `doctorFailed`. That caller decides "did anything fail" itself and only needs the command. Leave `init.ts` alone here; the ticket puts that change out of scope.

**What to leave alone.** Don't change the `FIX` rendering above the `NEXT` line. It still prints every line of a fix, and it still prints an empty-string fix as a `FIX` badge with nothing after it (`:3360-3368`). The whitespace rule applies to `nextOf` only.

**Tests.** They go in `apps/cli/unit/doctor-render.test.ts` as the ticket lists. Three checks need little extra:

- Test `nextOf` directly on bare `CheckResult[]` arrays as well as through `renderDoctor`. #756 will rely on it without the rendering.
- In plain mode the badge is `[next]` (the `labelled(badge('next', 'next'), 'next')` path), so assert on the line with the badge and not just that the command appears somewhere. The command also appears in the `FIX` row above it.
- Include a block whose fix is only whitespace, sitting before a block with a real fix; `nextOf` must pick the second.

Everything here is pure rendering, so `pnpm test` and `pnpm typecheck` check all of it; nothing waits on the integration half.
