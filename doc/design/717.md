## Where each piece goes

**1. Fixes are copied onto rows before rendering; rows are merged during rendering.**
- **Copying** happens in `runDoctor`, after the `deferred` step and before `return { results, ...tally(results) }` (`:2855`). Make it a small exported pure function so a unit test can reach it without a store.
- **Merging** happens only in `renderDoctor`, over `report.results`. Group the rows by an exact match on `fix`. A row with no `fix` is never merged.
- `cli.ts:111-113` appends the release row after `runDoctor` returns and runs `tally` again. That row has no `fix`, so neither step is affected by it.

**2. `runDoctor` needs to know which extensions a row is short of, as data.** Don't recover it by parsing the `fix` text.
- Split `extensionRow` into an internal function that returns `{ result, short: { step: string[]; subscriber: string[] } }`, where the arrays hold the names of the short extensions.
- Keep `extensionRow` (exported, used by `integration/doctor.test.ts`) as a wrapper that returns `.result`.
- At `:2352`, the loop keeps the `short` value next to the `project.project` it already has.

**3. When the subscriber row gets the env row's fix.** Copy only when both of these are true:
- the subscriber row's recent failures name exactly one subscriber;
- exactly one env row's short extensions are that one subscriber and nothing else.

In every other case nothing is copied. That covers a mixed row that is also short of a step extension (a `fail`), a row short of two subscribers, and two projects that both declare `telegram`. The last case matters because `subscriberFailures` groups by `data->>'name'` only, not by project (`packages/event-store/src/queries.ts:314-327`). Under this rule a copied fix is always between two `warn` rows, so the merged row is always a `warn`.

**4. Export a pure `subscriberRow(rows)` out of `subscribers`.** `subscribers` keeps the `.catch` and the query. With the row built by a pure function, the title and detail can be unit tested. `runDoctor` keeps the list of recent subscriber names for decision 3.

## Row text

**`env: <project> extensions`, when names are missing:**
- **Title:** the names of the short extensions joined with `and`, then `is missing environment variables` (`are missing` for more than one).
- **Detail:** line 1 is the existing `name ← layer` listing. Line 2 is the explanation without `(0037 §1)`, without `(0015)`, and without the trailing `lingtai env set … — it reads the value from stdin`. That command now lives in `fix`.
- **Fix:** one `lingtai env set ${project} ${NAME}` per name in `absent`. Then one `or remove the <name> subscriber` line per short subscriber, but only if no step extension is short. If any step is short, the row is a `fail` and offers no removal, even for subscribers that are also short.
- **The production-tripwire `fail` (`:2161-2163`)** gets no `title` and no `fix`.

**`subscribers: failures`, when it is a `warn`:**
- **Title:** `${name} notifications are failing`. With several subscribers, join the names with `and`.
- **Detail, one subscriber:** `${recent} in the last day · ${reason}`.
- **Detail, several subscribers:** `telegram ×31, notify ×2 in the last day · ${reason}`.
- `reason` is the first line of `lastReason`, cut at its first ` — `.
- **Why cut at ` — `:** the reason telegram records today is one line that ends with the placeholder `` `lingtai env set <project> …` `` (`packages/telegram/src/cli.ts:62-63`). That placeholder is the second way of writing the fix that the ticket's Problem row complains about. Cutting at ` — ` leaves `TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID not set`.
- **Don't change telegram's message:** `packages/telegram/integration/telegram.test.ts:167` and `:247` pin it, and events already in the log keep the old text anyway. The ticket's `are not set` comes from the fixture the operator chose, so the unit test's fixed report can use that wording.
- The `ok` branches stay as they are.

## Rendering

**Short view.** `renderDoctor`'s `!verbose` branch is replaced as follows:
- **Which rows:** `fail` and `warn` rows only. Order them by status, then by today's area order (`AREA_OF`, then `Other`), then by `report.results` order.
- **Merging:** group by `fix` as in decision 1. A group takes its title and detail from its first row in that order. Its status is the worst status in the group. Its tag is the group's areas in the same order, with duplicates removed, lower-cased, and drawn with `paint.muted`.
- **One row:**
  - title line: `  ${fail ? symbol.fail() + ' ' : ''}${title ?? name}  ${muted('· ' + areas)}`;
  - detail line: `  ${detail.split('\n')[0]}`;
  - fix lines: `  fix  ${line1}`, then each later line of `fix` indented 7 spaces so it lines up under the first.
- **Between and after rows:** one blank line between rows. Then #718's `note` block as it is now. Then `next:` with its existing condition and `next` flag.
- **Counts line, with something to fix:** `${groups} to fix · ${ok} passed · ${notChecked} not checked here · ${deferred} not implemented yet`. Paint `to fix` with `paint.fail` when any group is a `fail`.
- **Counts line, with nothing to fix:** `all ${ok} passed · …`, with `all … passed` in `paint.pass`.
- **What the counts line leaves out:** `info` gets no count, following 718.md decision 3, because every `info` row is already drawn as a `note` line.
- **What goes away:** `section()`, `marker()` and `!` are no longer used in the short view.

**Verbose view.** It stays as it is (`:3043-3064`). Each row with a `fix` gets the same `fix  …` block, indented 6 spaces, under its detail lines.

## `--json`

In `doctorJson`, add `title` and `fix` the same way `ms` is added: present only when set. `failed`, `warned` and `JSON_VERSION` don't change.
