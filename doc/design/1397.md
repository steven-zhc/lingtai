# #1397 — recording a landing owed by a conductor that died

## Where it goes

- A new file, `packages/daemon/src/owed-landings.ts`, which exports `recordOwedLandingsEffect(options: ReconcileOptions)`.
- `reconcileEffect` calls it once, as its first line, before `releaseForeignClaimsEffect(options)` (`packages/daemon/src/reconcile.ts:808`).
- Import `landTicketEffect` from the subpath `@lingtai/conductor/ticket`. The conductor's `package.json:8` maps that subpath to `src/ticket/commands.ts`, which is where the function lives (`:881`). `reconcile.ts` already imports `releaseDeadWorkerEffect` from that subpath and gives the reason for not using the barrel:

  > A subpath, never the barrel … `@lingtai/conductor`'s index pulls in the gate pipeline … and the board imports this package.

  `@lingtai/conductor` is already a dependency of `@lingtai/daemon`, so no new package edge is needed.

## The decision the ticket leaves open: find the lanes from the log, not from the recipe

The ticket's Fix takes `bases` from `branchOf(recipe)` plus the open PR's branch. Do not build it that way.

**Why the recipe route does not work here:**
- The reconcile has no resolved `Recipe`. `ProjectState.recipe` is the declared recipe text, `PayloadOf<'ProjectRecipeChanged'>` (`packages/domain/src/project.ts:56`).
- `branchOf` takes a resolved `Recipe` (`packages/recipe/src/settings.ts:316`).
- Resolving one is `clientsForProjectsEffect`'s job in `apps/cli/src/daemon.ts:515`, and it drops a project whose recipe does not resolve.
- Getting a recipe into reconcile would mean adding a `@lingtai/recipe` dependency and a resolve step. Both are new failure surfaces in a step whose whole point is to work after a crash.

**What to do instead:**
1. List the lanes. For each name in `options.projects`, ask the daemon store, inside `withStreams(options, …)` as `releaseForeignClaimsEffect` does at `:522`, for `{ prefixes: ['int-<project>-%'], types: ['IntegrationSucceeded'] }`.
2. Read each lane and reduce it with `landingsStarted`.
3. For an entry whose `mergeCommit` is non-null, read the base from that `IntegrationSucceeded` event's own payload. The event already carries `base` (`packages/domain/src/events.ts:1617-1622`), and `integrate` writes the same `options.base` there (`packages/repo/src/integrate.ts:303-307`) that the live pass hands `landTicketEffect`. Both are `attemptBase()`: `conduct.ts:4064` and `:4643` name the lane with it, and `conduct.ts:6310` passes it to `landTicketEffect`.
   - Add `base: string | null` to `landingsStarted`'s result (`packages/domain/src/pr.ts:970-1020`): the event's `base` on a success, `null` otherwise. `landingsInFlight` ignores the new field.
   - Do not re-scan the lane for the event.

**What this buys:**
- It covers a lane on a PR branch of a PR that has since closed.
- It covers a recipe whose `branch.personal` changed between the crash and the start.
- The ticket's edge *"a project with no recipe on the log is skipped"* stops applying, because nothing reads the recipe.

**Two guards, because a `like` prefix match is loose:**
- **The lane:** keep it only if `integrationStream(project, base) === laneId` (`packages/domain/src/streams.ts:181`). This rules out project `foo` matching `int-foo-bar-main`, and `_` acting as a `like` wildcard.
- **The ticket:** keep it only if `ticketId` starts with `ticketStreamsOf(project)`.

Drop and log anything that fails a guard; never land it.

**Cost:** each start reads one lane per base that ever had a success, and PR branches add one lane each. That is dozens of small reads, plus one ticket read per succeeded entry. State this in the doc comment.

## The comparison must be `landingsInFlight`'s, exactly

Owed means `ticket.landed?.mergeCommit !== started.mergeCommit`, which is the test at `packages/project/src/pr.ts:398-399`. Use that test word for word, so that Done-when 5 holds by construction. Do not also compare `base`.

Read the ticket the way `ticketOf` does: `readThroughSnapshot` with `readOf(options)` (`reconcile.ts:135`). Pass the same `SnapshotReadOptions` as the fourth argument to `landTicketEffect(ticketId, { mergeCommit, base }, store, readOf(options))`, with no `endPlan`. That keeps the daemon's ticket snapshots current.

`landTicketEffect` checks no state (`commands.ts:843-847`: *"None checks the ticket's state"*). The reducer makes the ticket `landed` from any status (`packages/domain/src/ticket.ts:825-833`), so a claimed, queued or closed ticket all end up `landed`. That is the result the ticket's edge asks for.

## It writes before the reconcile reads, and the comment there must say so

`reconcileEffect` opens with *"Read all four before acting on any"* (`reconcile.ts:801-806`). This step breaks that rule on purpose:

- The claim scan has to see the landing, or it reports the ticket as `released` (`:544`, `if (life.status !== 'claimed') continue`).
- The worktree scan has to see it too, so the dead pass's worktree is treated as belonging to a finished ticket.

Add a sentence to that comment saying the owed landings are written first because the reads that follow must see them.

## What it reports

**Not a `Finding`.** `Action` is `'removed' | 'released' | 'converged' | 'reported'` (`reconcile.ts:174`), and it feeds the `Reconciled` payload's schema. Adding a value means a schema change this ticket does not need. The `TicketLanded` (actor `conductor`) is the record, and one `log` line per landing says why it is there, in the ticket's wording.

**`options.dryRun`:** when it is true, append nothing and log `would record …`. No caller passes it to `reconcileEffect` today; doctor calls the separate find steps with it (`apps/cli/src/doctor.ts:1881-1883`). The option exists on the shared `ReconcileOptions`, though, and a step that wrote under it would break what that option promises.

## Failures never fail the start

- Wrap each project's lane listing and reads in `Effect.catchCause`. Re-raise an interrupt-only cause, as `:532-536` does, and log everything else.
- Wrap each landing on its own. `appendOnTicket` treats a refused append as a defect (`commands.ts:856`, `Effect.orDie` and a bare `Effect.promise`), so catch the cause, log it, and move on to the next landing.
- The step returns `void`. Whatever it could not record is still pending in `landingsInFlight`, and the next start tries again.

- **The fake's `streams()` must filter by `query.prefixes`.** The existing fake answers every query with every stream (`reconcile-release.test.ts:41`).
- For Done-when 4, assert that the landed ticket gets no `TicketReleased`, and that the release is still reported for another ticket that really is claimed by a dead worker.
- For Done-when 5, call `landingsInFlight(project, base, store)` after the step. It is unit-safe on the memory store.
- Add a case for the lane guard: a lane named `int-foo-bar-main` under project `foo` lands nothing.

Everything here is covered by `pnpm test`. Nothing needs the integration half.
