# #772: the shape of the change

All of it is in `runLocalBranch` (`apps/cli/src/first-project.ts:385`), plus two ports on `FirstProjectWorld` (`:129`). Below are the four things the ticket does not settle on its own.

## 1. The name guard needs `resolveRemote` back, because #745 deleted it

The ticket says the old remote is matched by "`resolveRemote` (`first-project.ts:364-366`)". That function no longer exists. `6b1e79ae` (#745) removed both helpers. Copy them back exactly as they were in `6b1e79ae^:apps/cli/src/first-project.ts:375-383`:

```ts
/** Git recognises a URL (`scheme://…`) and scp-style (`[user@]host:path`) — everything else is a path. */
function isUrlOrScpLike(remote: string): boolean { … }
/** `origin` as git stores it, resolved to an absolute path when it is a relative one. */
function resolveRemote(remote: string, top: string): string { … }
```

The old `add` wrote `resolveRemote(origin, toplevel)` into `repo.remote`, so this exact function is the only reliable way to match that string. Do not reuse `packages/repo/src/integrate.ts`'s check, even though `dfc972ee` made it treat a single-letter ssh alias as scp-like. If the rule changes, a recipe the old `add` wrote stops matching and gets refused. Comment the copy as *what the old `add` wrote*, not as a general-purpose classifier.

Today the guard is `existingRemote !== remote` (`:433-455`). The new rule: an existing remote is the same project when it equals `toplevel`, or equals `resolveRemote(origin, toplevel)` where `world.git(toplevel, ['remote', 'get-url', 'origin'])` succeeds. If that call fails, only `toplevel` is accepted. Any other value is refused with today's wording. The `owner !== null` refusal (`:421-427`) stays as it is.

## 2. The base question must not offer the old base as its default

`question()` uses `current ?? detected` as its default (`apps/cli/src/question.ts:131`). Today `runLocalBranch` passes `current: currentBase` (`:480`). Over an old recipe that means `main`, so pressing enter, or `--defaults`, would keep `main`. The ticket says the re-run lands on `lingtai-base`.

**Decision:** when the existing `repo.remote` is not `toplevel` (the old-recipe case), pass `current: null`. The question then defaults to `detected`, which is `LINGTAI_BASE`, or `--land`'s branch as now. When the existing remote is already `toplevel`, keep passing `current` as today, so a project added after #745 with `--base dev` keeps `dev` on a re-run.

This also settles how the "`ask` answers `null`" Done-when has to be tested. With no terminal, the base question refuses before the confirm is ever reached (`question.ts:143-144`). That is the same for a brand-new project and is not something this ticket changes. So the test passes `--base lingtai-base` (or `--defaults`, or has `ask` answer the base prompt) and returns `null` only for the confirm prompt.

## 3. Where the migration goes, and in what order

The `lands:` comparison needs the answered base, so it cannot run any earlier than straight after `baseAnswer` (`:510`). It also has to come before the first write. The first write is `git branch lingtai-base` (`:524-530`), not the recipe. So the order is:

1. **After `baseAnswer`:** if the existing `repo.remote` differs from `toplevel`, or the existing `repo.base` differs from `base`, this is a migration. When both match, do nothing here: no line, no question.
2. **In-flight check:** call `world.inFlight(name)`. A throw refuses with `the board could not be read — <error>. ${world.kept}`. A non-empty answer refuses, names the tickets through `describeInFlight` (`packages/daemon/src/control.ts:390`), and says to re-run once they finish or after `lingtai shutdown`.
3. **Log the line:** `lands: <old remote> <old base> → this checkout, <base>`. If the old base is absent, print it as `(none)`.
4. **Confirm:** `world.ask`. `null` carries on. Any answer other than `y`/`yes` refuses with `world.kept`. Use `paint.signal` like every other prompt.
5. **Runtimes probe, then the branch** (`:515-538`), unchanged. The runtimes refusal still truthfully says nothing was written.
6. **Remove the mirror** (`world.removeMirror(name)`) immediately before `askRecipe` (`:563`), only in the migration case. A throw refuses: `could not remove the mirror — <error>`, followed by `madeKept` if a branch was made.
7. **After removal**, append `; the mirror at <path> was removed, and the next pass clones it from this checkout` to `seededKept`. Any refusal from `askRecipe` onward then reports what was left behind (#431's rule, `:557-561`).

The seeds (`:548-552`) already write both keys over an existing file. Nothing else changes.

## 4. The two ports

On `FirstProjectWorld`:

```ts
/** `project#issue` for each of this project's cards in `running`/`verifying`. Throws when the board cannot be read — never `[]`. */
inFlight: (project: string) => Promise<readonly string[]>
/** Removes `<home>/repos/<project>.git`; absent is not an error. */
removeMirror: (project: string) => Promise<void>
```

- **Live `inFlight`:** `held(await readTasks({ project }))`, with no `.catch`. This is why `control.ts:384`'s `inFlight()` cannot be reused: it swallows a read failure into `[]`.
- **Live `removeMirror`:** `rm(mirrorPathFor(project, home), { recursive: true, force: true })`, using `@lingtai/repo`'s `mirrorPathFor`.

Make both ports **required** rather than optional. A missing port would quietly turn into "nothing in flight". Requiring them means wiring them in three places:

- `liveFirstProjectWorld` (`:915`)
- `init.ts:518`'s `firstProjectWorld`, because `init` reaches `runLocalBranch` too. Thread them through `InitWorld` the same way `projects` and `exists` are, not from live defaults (#394 finding 6).
- every unit fake of either world. `tsc` will list them.

## What can be checked inside the pass

Everything above runs through `world.git`, `world.files` and the two ports, so all of the Done-when items are unit tests over fakes.

The one claim the unit half cannot see is that the trial build re-clones the mirror from the checkout once `removeMirror` has run. That rests on `ensureMirror` cloning from `options.remote` when no mirror is present (`packages/repo/src/worktree.ts:124-129`). On a live run, the next cut's `git clone --bare <checkout>` settles it. Nothing in `pnpm test` exercises it, and it needs no new test here.
