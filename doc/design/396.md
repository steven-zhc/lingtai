## Design: #396, the setup asks where tickets come from and which labels are work

### Where it goes

**A new `apps/cli/src/source.ts`** holds `askTickets` and `askKinds`, both asked through `question()` (`apps/cli/src/question.ts`). The pure halves go into `packages/recipe/src/answers.ts` next to `landingChanges`. Its header gives the reason: *"Pure — no terminal, no file — so `@lingtai/conductor`'s own test can apply a change set with `setRecipe`"*.

**The two asks write nothing. Each returns `{ changes: RecipeChange[] } | { refused }`**, the way `setup-build.ts` does (*"**This writes nothing.** … What this returns is handed to `setRecipe` by the caller"*). `landing.ts` writes inside its ask, but that will not work here, because the two callers write differently:

- **The GitHub path** is `askBeforeGithubAdd` (`apps/cli/src/lingtai.ts:416`). Ask both inside its `if (existsSync(path))` block, **before** `askLanding` (`lingtai.ts:491`). Write each answer with `setRecipe` as soon as it is given, using `landing.ts`'s `setRecipeOrRefuse` pattern (move that helper somewhere both files can import it). This keeps #392's *"a Ctrl+C keeps what was answered"*.
- **The local path** is `runLocalBranch` in `apps/cli/src/first-project.ts`. It writes everything in **one** `setRecipe` once every check has passed. The header says *"The local branch writes nothing until everything has been checked"*, and the single write is at `first-project.ts:400-416`. Ask both questions after the base question (`first-project.ts:367`) and add their changes to that one `changes` array. `init` and `add` both reach this branch through `chooseFirstProject`, so one edit covers both.

A GitHub project picked on the board, or one with no recipe yet, still reaches neither question. That matches #399's scope: *"A local project, and a GitHub one picked on the board, reach none of this yet"* (`lingtai.ts:413`).

Add `--tickets <github|db>` and `--kinds <a,b,c>` to the `add` help block (`lingtai.ts:118-147`), and to `init`'s block if it lists the local flags. `parseFlags` is generic, so nothing else is needed to parse them.

### The local branch doesn't have this setting at all today, and that is a bug this ticket fixes

`runLocalBranch` registers `owner: null` (`first-project.ts:427`) but never writes `source.tickets`. On a new file its change set is `repo.base`, `repo.remote`, `source.kinds` and `env.plantAt` (`first-project.ts:400-410`). Every run then refuses that project:

- `ownerlessRefusal` (`packages/conductor/src/filter.ts:241`) says *"has no owner and its recipe does not say source.tickets: db — write source.tickets: db …"*.
- `ownerlessClient` calls `ownerlessRefusal` first (`packages/conductor/src/ownerless.ts:53-54`).

So a local project created with `lingtai add --local` cannot run until somebody edits the file by hand. Once this lands, the local branch **always** writes `source.tickets: db`, and it writes it again on a re-run when the file is missing it (subject to the history rule below).

**For a local project there is no prompt at all.** There is one legal answer, so asking would just be a press of Enter. Log `tickets       db — a local project has no GitHub issues to read`. With a flag:

- `--tickets db` is accepted.
- `--tickets github` is refused by name. Pass `validate` to `question()`: with `given` set, `validate` is the whole answer and is never re-asked (`question.ts:85-90`). Suggested wording: *"a project with no owner cannot take its tickets from GitHub — there is no repository to read issues from. Pass --tickets db, or leave it out."* Append `world.kept` like every other refusal in that branch.

### The history rule: read the log, and keep the current source when it has history

Switching is unsupported because `wi-<project>-<n>` (`packages/domain/src/streams.ts:14`) would collide. `ticketsFor` refuses only one direction of that switch, and only when a pass runs: it throws `TicketSourceConflict` when the recipe says `db`, the db table is empty, and `log.projectStreams('wi-<project>-')` is non-empty (`packages/conductor/src/ticket-store.ts:243-251`). Nothing guards db → github. The setup has to stop both directions, and earlier.

- **A project has history when `projectStreams('wi-<project>-')`, filtered by `parseWorkItemStream(id)?.project === project`, is non-empty.** That is the same query and filter as `ticket-store.ts:247-249`. The prefix match alone is not enough: project `foo` would match `wi-foo-bar-3`, and that is what the filter is for.
- **Make it a world function, `history: (project) => Promise<readonly string[]>`, on both callers' worlds.** The live implementation does a dynamic `import('@lingtai/event-store')` and calls `log.queries.projectStreams`, like `ticket-store.ts:210`. `FirstProjectWorld` (`first-project.ts:~88`) gets the field, and so does whatever world `askBeforeGithubAdd` builds. Unit tests pass a fake: `HOME=/nonexistent pnpm test` cannot open a store, which is the reason `ownerless.ts:42` gives for its own `ticketsOf` seam.
- **What counts as the current source: `ticketSourceOf(resolved)`** (`packages/recipe/src/settings.ts:338`), so an absent key reads as `github`.
- **With history and no flag:** don't prompt. Log the source being kept and why: *"tickets       github — kept: the log already has work items for this project (wi-x-1, …), and a different source would number its tickets into those same streams (#381)"*. Write nothing.
- **With history and a flag that differs from the current source:** refuse by name, with the same reason. A flag equal to the current source is accepted, and nothing is written.
- **A local project with history whose source is not `db`:** this is #352's `unrecorded` case, a project registered before owners were recorded. Keep the source and say so, even though the project still won't run. Don't write `db` over it: writing `db` is exactly the collision, and `ticketsFor` would refuse every pass anyway.

### The GitHub question

The prompt names both choices, for example *"where this project's tickets come from — github (this repository's issues) or db (Lingtai's own table)"*.

- `choices: ['github', 'db']`.
- `current: ticketSourceOf(resolved)`.
- Write `{ path: ['source', 'tickets'], value }` **only when the answer differs from `ticketSourceOf`.** Pressing Enter on `github` must not pin `tickets: github` into a file that never wrote it. `askLimits` already follows that rule (*"pressing enter on an inherited default must not pin it into the file"*, `landing.ts:220-224`), and #381 has an extra reason: a key that is written changes `configHash` (`doc/design/381.md`, *"default in the accessor, not in the schema"*).

### Kinds: write them where `kindsOf` reads them

`kindsOf` reads the `queue:` declared at `claim` **first** and `source.kinds` second: `takeAt(recipe)?.kinds ?? recipe.source.kinds` (`settings.ts:283-285`). A recipe that declares its queue at the step would take a `source.kinds` write and keep running on the old list without a word. `landingChanges` hit the same trap with the base and solved it the same way (*"writes the base where `baseWrittenAt` says it is read, not always `repo.base`"*, `answers.ts:50-56`).

So `kindsChanges(kinds, rawClaim)` in `answers.ts` works like this:

- **When a `claim` action carries `queue:`:** return `steps.claim` with that entry's `queue.kinds` replaced. Every other entry and field stays as written.
- **Otherwise:** return `source.kinds`.

The caller passes `readRecipeKey(project, ['steps', 'claim'])` when the file writes that key itself, and the resolved list when it doesn't. That is `askLanding`'s raw-or-resolved choice (`landing.ts:192-199`).

The question:

- **The prompt says the order is priority.** For example: *"which labels are work, comma-separated, first = taken first"*.
- `current: kindsOf(resolved).join(', ')`. Pass `fallback` only for a local file that doesn't exist yet.
- **Parsing:** split on `,`, trim, drop empties. Refuse an empty list through `validate`, because the schema says `z.array(z.string()).min(1)` (`packages/recipe/src/recipe.ts:989`).
- **Keep the order given** and don't dedupe silently. Refuse a repeated label by name instead.
- **Write only when the parsed list differs from `kindsOf` in order or content.**

**The default is a new constant, `SETUP_KINDS = ['bug', 'feature', 'documentation']`, in `answers.ts`.** Do **not** edit `PROPOSED_KINDS` (`packages/recipe/src/propose.ts:74`, `['bug', 'feature', 'tech-debt']`). That constant answers a different question: which of a GitHub repository's existing labels to *propose*. `propose.ts:182-190` matches it against that repository's labels, and its refusal text says *"the proposal names all three"*. The local branch's new-file seed (`first-project.ts:407`) stops using `PROPOSED_KINDS` and uses the answer to the kinds question instead.

### Tests (all `unit/`, all through fakes)

- **`packages/recipe/unit/answers.test.ts`** (or wherever `landingChanges` is tested):
  - `kindsChanges` writes `source.kinds` when there is no claim `queue:`.
  - It rewrites `queue.kinds` in place when there is one, and other claim entries are untouched.
  - The order comes out as given.
- **`apps/cli/unit/source.test.ts`**, using a `Map`-backed `RecipeFiles` and a scripted `ask`, as `landing.test.ts` does:
  - A GitHub project with no flags offers `github`, and Enter writes nothing.
  - A local project is never prompted and gets `db`.
  - `--tickets github` on a local project is refused, and the refusal names the reason.
  - With history, a GitHub project is not prompted, is not switched by a different `--tickets`, and the log line says why. With history, a `db` project keeps `db`.
  - `--kinds feature,bug` is written as `['feature', 'bug']`.
  - The default with no file is `bug, feature, documentation`.
- **`apps/cli/unit/first-project.test.ts`**: the local branch's single write now contains `source.tickets: db`, and the resolved recipe passes `ownerlessRefusal` (returns null). That last check stands in, at unit level, for *a local project created by the setup can run*.

Nothing here needs `pnpm test:integration`. The live `history` query is the one piece no unit test touches. What settles it in the log is whether any `wi-<project>-*` stream exists for the project, which `lingtai status` shows as that project's items.
