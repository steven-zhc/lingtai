## 1. Where the keep runs, and what makes it run only once

`keepUncommittedWork` (`packages/conductor/src/conduct.ts:2503`) keeps its job: commit a dirty tree while `stoppedBy` names a stop. What changes is its guard and who calls it.

- **Guard.** Today the guard is `stoppedBy === null || wip !== null || wipParent !== null` (`:2505`). The new guard is:
  - `stoppedBy` is `null`, or `'no-commits'` → nothing is kept;
  - the dispatch was a conflict round → nothing is kept (see §3);
  - otherwise, `git status --porcelain` decides, as it already does at `:2534-2547`.

  The clean tree is what stops a second call. The `wip !== null` test is deleted, because it is the thing the ticket's *Watch out* names.
- **A successful keep consumes the stop.** Set `stoppedBy = null` in the same `Effect.uninterruptible` region that commits (`:2560-2574`). A keep that failed leaves `stoppedBy` set, so the finalizer's call still retries it. That retry path is what `wipFailure`'s clearing at `:2528-2532` was written for.
- **Callers.**
  1. `firstDispatch`'s abnormal end, right after `stoppedBy = outcome.failure.kind` (`:5022`), before the `return { stopped: … }`.
  2. `fixRound`'s two places that set `stoppedBy` from `fixed.failure`. One is the stopped branch (`:5333`). The other is **the committed-then-cut-off branch (`:5358`), which goes on to `build`**. The comment there says *"a fixer that committed half the fix and then hit `out-of-turns` left the rest in the worktree"*.
  3. `publishWhatIsCommitted` (`:2656`) keeps its call. That is where `'interrupted'` (set at `:4944` / `:5196`, before the run) is still kept, because an interrupted dispatch never reaches lines 1 or 2.

**The decision that is not in the ticket: caller 2b changes what `build` and `review` see.** Today the half-fix's leftover edits sit uncommitted while `build` runs, and the WIP is made only after `runAttempt` returns (doc at `:2490-2496`: *"No step of this pass ever sees this commit"*). After this change the WIP is on `HEAD` before `build`. So `build` and `review` check it, and #1209's *what lands is the head build and review checked* covers it. This is intended, and it is the reason the lane refusal can go. Delete the `:2490-2496` paragraph rather than reword it. Add a unit test for this path: a fix round that committed, then ended `out-of-turns` with a dirty tree, reaches `build` with `HEAD` at the WIP.

## 2. `wip` and `wipParent` become one list

Replace both variables (`:2367`, `:2379`) with:

```
let wips: Array<{ parent: string; stoppedBy: string; sha: string | null }> = []
```

- An entry is pushed the moment `git commit` succeeds, with `sha: null`. This keeps #468's rule that the commit's existence is recorded before its sha is read (`:2370-2378`).
- Read the sha in the keep itself, with the `rev-parse HEAD` at `:2585` that today only feeds the run log. If that read succeeds, fill `sha`.
- If it fails, `publishWhatIsCommitted` resolves every entry still `sha: null` before it pushes. Use `git rev-list --reverse --ancestry-path <parent>..HEAD` and take the first line: the WIP was committed directly on `parent`, so that line is the WIP even if a later rerun committed on top of it. Do **not** carry over today's *"fill from the publish's own `rev-parse HEAD`"* (`:2680-2688`). With two WIPs in a claim, `HEAD` is only the last one.
- An entry whose sha still cannot be resolved goes into `wipFailure`'s detail (as at `:2376-2383`). It gets no `RunKeptUncommitted` row, because a row must name a fetchable sha.

`notedKept` (`:2600`) becomes a `Set<string>` of shas whose row landed. `noteKept` runs once per resolved entry, in list order, from each of the three places that call it today (`:2769`, `:2848`, `:2896`). Each row still counts `parent..sha` (`:2613`), which is exactly that one WIP.

Other readers of `wip`:

- `standingFor` (`:5828`, `packages/domain/src/wait.ts:486-491`) only asks whether anything was kept. Pass `wips.length > 0`, or narrow its input to a boolean.
- The restart check (`:5951-5954`) allows `armPublished === wipNow.sha && wipNow.parent === headSha`. That case cannot happen for new rows (see §4). Delete the WIP disjunct along with the `as` cast and its comment (`:5944-5951`).

## 3. Conflict rounds keep nothing

Delete the whole `conflictMergeStood` block in the keep (`:2507-2527`) and replace it with an early return.

Leave a standing merge alone. `mergeForConflict` already aborts a merge left standing before the next round merges again (`:4015-4025`: *"An earlier uncommitted resolution was never built or reviewed"*). The worktree is removed at scope close. The publish pushes `HEAD`, which a merge that was never committed does not move.

`conflictMergeStood` stays, because `mergeForConflict` (`:4025`, `:4082`) and `fixRound` (`:5122`) still use it. Only the keep stops reading it, which leaves nothing in the keep that can produce a `MERGE_HEAD could not be read` failure.
