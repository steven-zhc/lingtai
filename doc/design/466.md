# Design: #466 — `yields` on every action, `interrupted` on the result, and `adapters.ts`

## Where the `StepOutcome` is built: in `runStep`, not in `runActionPipeline`

The ticket says "have the pipeline build the `StepOutcome`". It also says `adapters.ts` "is the only place both shapes meet". Both cannot be true inside `packages/actions`: `@lingtai/actions` depends on `domain`, `recipe` and `agent` only (`packages/actions/package.json:13-17`), so `runActionPipeline` cannot call `actionOf` in `@lingtai/conductor`. **Resolve it like this:**

- **`runActionPipeline` builds nothing new.** It carries the new `ActionResult` fields onto `results` the way it carries the others: the spread block at `packages/actions/src/action.ts:666-700`, one spread per field, and an absent key stays absent.
- **`runStep` builds the outcome.** It is the conductor's wrapper of the pipeline (`packages/conductor/src/pass.ts:1621-1661`). It calls `outcomeOf(step, round, onSha, actions, result)` from `adapters.ts`, then puts the result on `StepReached` as a new optional field `outcome?: StepOutcome`. `StepReached` is at `pass.ts:525-529`.
  - Hoist `options.actionsAt(spec.step, actions)` into a `const` so the same list goes to the pipeline and to `outcomeOf`.
  - `results[i]` belongs to `actions[i]`, because the pipeline pushes in order and stops (`action.ts:609`, `:742`). Every action past `results.length` is `NotReached`, with `evidence: ""`.
  - `outcome` is set on the three returns that have a pipeline result: `:1660`, `:1686` and the `catch` at `:1692`. Hold it in a `let` beside `results`.
  - It is absent where no pipeline ran: a routing arrival (`reaching.arriving !== null`, `:1621`) and `end` (`plugins: 'effects'`, `pass.ts:183`).

That change is data only. No branch in `pass.ts` reads `outcome`.

**`outcomeOf`, `actionOf`, `eventOf` and `holdOf` never throw.** In this ticket the outcome is built beside the real ending and nothing reads it yet. A throw from `outcomeOf` would be caught at `pass.ts:1691` and turn into `did-not-finish: threw`, which is a control-flow change through the back door. Where 0120's union has no arm for something today's code produces, map it to the nearest arm and put a comment on that cell, as the ticket asks for `holdOf`. Do not use `ImpossibleOutcomeError` (`pass-next.ts:32`) here; that one is `nextOf`'s, and it belongs to #467.

`round` is `reaching.context.round ?? 0`. `onSha` is the context's `onSha`, the same value the pipeline stamps on every event (`action.ts:613`). `call` is `null` everywhere: #455 owns `CallId` (`packages/domain/src/action.ts:21-27`) and nothing mints one yet. `plugin` is `Action.kind`.

## The result has to say three things it cannot say today

A round trip through 0120's types needs more than `interrupted?`. Each of these fields is spread through `results` like the others.

1. **`interrupted?: Interrupted['cause']`**, as the ticket asks. Three places set it:
   - The work action, threaded through `Stopped` (`pass-steps.ts:242-244`). Widen `Stopped` with optional fields rather than adding a fifth arm to `Worked` (`pass-steps.ts:276-278`), so that no `'stopped' in` branch changes.
   - `conduct.ts:2783`, where `outcome.failure.kind` is one of the five causes.
   - `conduct.ts:2965-2971`, where `fixed.failure.kind` is one of the five causes.
   
   The reviewer at `agent-action.ts:518-522` and the drafter at `agent-action.ts:949-955` set it the same way. Every other `failure.kind` in `RUN_FAILURE_KINDS` (`vocabulary.ts:72-81`) — `no-commits`, `never-started`, `no-structured-answer` — leaves it absent.

2. **`committedNothing?: true`**, set on the work action's `did-not-finish` when the agent ran and left no commit: `conduct.ts:2808`, `conduct.ts:2965-2971` with no failure, and `failure.kind === 'no-commits'`. This one is not optional for the design.
   - 0120 calls that outcome `commit Completed{head: null, question: null}`. That cleared result is what makes `nextOf` answer `NothingProduced` or `FixerDisagrees` (`pass-next.ts`, the `changedNothing` branch).
   - Today it is the same `{ stopped }` string as "the hook was not wired" (`conduct.ts:2603-2610`, `:2733`, `:2876`), and in 0120 that case is `NotDone`.
   - Without a token, `actionOf` would have to read the sentence, which 0031 §1 forbids. The other way out — mapping both cases to `NotDone` — makes #467 hold row 7 as `DidNotFinish` instead of `Declined`.

3. **`merged?: string`** on the merge action's pass. The sha appears today only in `evidence` (`merge-action.ts:100-105`), and `Integrated` needs `mergeSha`. **Do not reuse `head`:** `headFrom` (`pass.ts:1826`) would move `onSha` for `end`.

## `actionOf` and `eventOf`: two vocabularies, and the adapter reads `plugin`

Today's events are a per-verdict vocabulary; 0120's results are per-yield. The two do not line up cell for cell. Three cases split on plugin rather than on result:

- **`commit Completed{head: null}`** was `StepDidNotFinish` from the work action (fixture rows 6 and 7) but `StepPassed` from a kept `run:` that found nothing to commit (`kept-run-action.ts:97-100`).
- **`NotDone` on `commit`** was `StepFailed` from a kept `run:` (`:80`) but `StepDidNotFinish` from the work action.
- **A throw becomes `failed` for every kind** (`action.ts:653-663`). So every yield needs a `failed` cell, including `signoff` and `merge`, whose unions have no arm for it. Map `signoff` and `merge` throws to the nearest arm and comment it.

**So `eventOf` may switch on `plugin`. `nextOf` never does.** Put that sentence in the module header; reading the plugin is the adapter's whole job. Inside each yield, write the switches exhaustively with no `default`, like `cleared` in `domain/src/action.ts`.

`eventOf(outcome, runId)` returns `ActionEvent[]`:
- `StepRequested` and `StepStarted` for every action that is not `NotReached`, then the terminal event.
- Nothing for a `NotReached` action.

Known losses, to name in the header rather than paper over:
- `about` (`action.ts:192`) has no field on the domain `Action`.
- `ApprovalRequested.artifacts` is always `[]` today (`action.ts:801`), so rebuild it as `[]`.

Cells to get right, each checked against code:
- **Reviewer `no-structured-answer`** is `failed, unreadable` (`agent-action.ts:507-515`). It becomes `verdict AnswerUnreadable{raw: evidence}`, which maps back to `StepFailed` with `unreadable: true`.
- **Any agent `did-not-finish` with no `interrupted`** becomes `Interrupted{cause: 'crash'}` on `verdict` and `design`, and `NotDone` on `commit`. Comment each one.
- **`because === NEEDS_INPUT`**:
  - from the drafter, it becomes `design Asked{question: evidence, draft: null}`;
  - from the work action, it becomes `commit Completed{head: null, question: evidence}`;
  - both map back to `StepAsked`.
- **Worktree `asked`** becomes `NotDone`, with a comment: `worktree-action.ts:33-35` says that arm never happens today, and the `worktree` union has no `Asked`.
- **`never-ran`** becomes `NeverStarted{scope: 'conductor'}`. A `work-item` scope never comes out of an action.

## `holdOf(reason, pass)` takes a second argument

`holdOfPass` builds part of each hold from facts that live on the pass, not on the wait:
- `Routed.why` opens with `${branch} into ${base} is waiting on you.` (`hold-of.ts:121`).
- `Human` and `Routed` carry `review`'s `findings` (`hold-of.ts:124`, `:197`).
- `legacyColumns`' recommendation at `merge` vetoes `approve` on a live finding (`hold.ts`, the `Human` docblock).

A `holdOf` that only takes a `WaitReason` would quietly change the card text and that recommendation once #467 moves the call site. So the signature is `holdOf(reason: WaitReason, pass: { branch: string; base: string; findings: readonly Finding[] }): Hold`.

## The proof against #461 lives in the harness, so the fixture stays untouched

#461's rows are separate `it`s inside `what-a-pass-writes-today.test.ts`, and none of them is exported. A separate adapter test would have to copy about 1000 lines of setup, and the ticket forbids editing that file. Put the check where every row already passes through, **`once()` in `packages/conductor/test/one-pass.ts:50`:**

1. Add an optional `onPass?: (pass: PassResult) => void` to `RunOnceOptions` (`conduct.ts:341`). Call it right after `runPass` returns (`conduct.ts:3040`). It is an observer that branches on nothing.
2. In `once()`:
   - record the `run-*` stream ids before the call;
   - pass an `onPass` that keeps the `PassResult`;
   - after `runOnce` resolves, find the one new run stream (rows 4 and 5 call `once()` twice on one store);
   - filter that stream to the eight `ActionEvent` types (`action.ts:469-488`);
   - `expect` that `{type, step, action, onSha}` equals the same fields of `pass.steps.flatMap(s => s.outcome ? eventOf(s.outcome, runId) : [])`.
   
   `conduct.ts:2536-2544` appends every emitted event unchanged apart from `parsePayload`, so the two lists should be the same.

That covers every #461 row, and every other suite that drives `once()`. A mismatch there is an adapter bug by the ticket's own rule. If one surfaces outside #461's file, it is the same bug found earlier. Where `runPass` never ran (refusals before the claim), `onPass` never fires and nothing is asserted.

Next to it, add `packages/conductor/unit/adapters.test.ts`. Its cases:
- one per factory × verdict cell above, as `eventOf(actionOf(...))` → today's event type;
- every `WaitReason` variant through `holdOf`, parsed with `Hold.parse`;
- a `wellFormed` check (`domain/src/action.ts`, the last function) on each outcome `outcomeOf` builds.

All of this is unit-level and needs nothing from `pnpm test:integration`.

## The module header

It says what the ticket asks: the module exists until phase 2, #464, which puts `StepOutcome` on the log as `StepEnded` and deletes `Hold`. It also says three more things:
- `eventOf` reads `plugin`, and why;
- the cells that map to the nearest arm, listed;
- `about` is not carried.

No ADR changes. These are adapters onto 0120's types as accepted, and the three new result fields are legacy-side tokens of the kind `because` and `unreadable` already are.
