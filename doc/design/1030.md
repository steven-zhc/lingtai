# Design note for #1030: fill the blank base in refusal sentences, and name the base in `lingtai status`

## Where the substitute goes, and where it must not

Put it inside `diagnoseRefusal` (`packages/domain/src/attribution.ts:413-433`), when `where` is built at `:421`. The ticket asks for exactly this. Do not apply it anywhere upstream:

- **Not in `waitWords` or `mergeRefusedColumns`** (`packages/domain/src/wait-words.ts`). They pass the same `base` to `subjectOf` (`:69-71`), and that rule drops an empty base on purpose: *"dropping `base` rather than printing it blank is the difference between "agent/473 is waiting on you" and "agent/473 into  is waiting on you""*. If `'the base'` were substituted before `subjectOf` runs, the card would read *"agent/473 into the base is waiting on you"*. The two rules handle the same empty string differently: the subject leaves the base out, and the refusal sentence says *the base*. So each rule belongs to the function that prints its own text.
- **Not in `REFUSAL_READING` and not in `baseProtectedRemedies`.** `base-protected`'s `says` (`attribution.ts:342-344`) already passes its `base` argument into `baseProtectedRemedies(base)`, so that function receives the substitute without being touched. `baseProtectedRemedies` is also the warning `add` prints (*"for the warning at `add` and the refusal at merge to say the same thing (#662)"*, `:106-107`), and `add` always has a real base. Changing the function itself would only risk that caller.

The fallback for an unknown reason (`:424`) uses only `branch` and `reason`, so it stays as it is. `raw` and `recommendation` also stay as they are, as the ticket says.

All the sentences read correctly with *the base* in place of a branch name: *"Lingtai's own checkout of the base was not clean"* and *"the base moved on files agent/1 also changed … not merged into the base unreviewed"*. Sentences that start with `${base}` already start lower-case when the base is `main`. No rewording.

## `status.ts`: the change also adds "into main" to the row's subject

`rowOf` is a closure inside `readStatus`'s `for (const project of projects)` loop (`apps/cli/src/status.ts:384`). So `project` is in scope at `:489`, and `:537` already reads `base: project.base ?? null`. Pass `project.base ?? ''` at `:489`.

This also changes text the ticket does not mention. Because `subjectOf` now receives a real base, every wait row's `line` and `short` in `lingtai status` go from *"agent/1024 is waiting on you"* to *"agent/1024 into main is waiting on you"*. That is intended: it is what the GitHub comment from `conduct.ts` already says (`wait-words.ts:64`). Say it in the commit body so nobody files it as a regression. A project with no `base` recorded passes `''` and keeps today's wording, with *the base* in the refusal sentence.

## The status test has to reach a pure function, because `rowOf` does not

`apps/cli/unit/status.test.ts:7-10` says why: *"`status()` itself calls `selectRunnable` and `readTasks`, which reach the log, so it is not unit-reachable — `offerLine` and `offerFailedLine` are pulled out of it for exactly that reason"*. `rowOf` is in the same position.

So follow that precedent:

- Pull out a small exported pure function that builds the `waitWords` argument from the issue and the project, e.g. `waitPassOf(issue, base)` returning `{ branch: agentBranchOf(issue), base: base ?? '', findings: [] }`.
- Call it at `:489`.
- In the unit test, feed its result through `waitWords` and `waitDetail` (`status.ts:118`) for a `push-rejected` merge refusal. The test asserts that the first detail line starts with `main moved while agent/…`, and that with `base: null` it starts with `the base moved while`.

That is the unit-level stand-in for "status names its base". Do not add an integration test for it: no integration test is run inside a pass.

The existing `status.test.ts` cases at `:643`, `:657` and `:676` pass `base: ''` directly to `waitWords`, so their assertions are unaffected unless one of them matches a refusal sentence's leading text.

## Tests in `packages/domain/unit/attribution.test.ts`

The list of reasons already exists in that file (`:53`, `:102`, `:168`); loop over it rather than writing out a new list. With `base: 'main'`, check each sentence word for word against today's output. Use a literal `'main'`, not a snapshot of the new code, so the test proves nothing changed for a known base.

The ticket's own edges cover everything else. Nothing here adds IO, so `effect-ratchet.baseline.json` stays as it is.
