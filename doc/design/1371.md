# #1371: the catch-up's shape

## Where it runs: serve and resume, never the sweep

`PrMerged` is appended inside the sweep, in `learnOnePr` (`packages/conductor/src/pr.ts:1183-1194`). Do not add the catch-up there, even though the ticket's Fix 3 suggests it. The sweep is the one PR path that must not push. `makePrHandlers` says it runs *"**paused or not** — learning that a PR merged records a fact and takes no work … It pushes nothing, so it can be interrupted; the walks owed are `resume`'s"* (`pr.ts:1376-1379`). The loop does not track it for the drain either: *"Not waited for by `stop()`, which interrupts it"* (`packages/daemon/src/work-loop.ts:319-323`, `:480-497`). A push started from there would break the ticket's drain edge.

So the catch-up is a walk:

- **In `servePr`** (`pr.ts:991-1011`), a merged PR goes to `catchUpPersonal` and returns. It returns before freeze, back, retry and walk, because `serveRetry` and `walkPr` are written for an open PR. It still runs under `permitOf(project)` (`pr.ts:232`).
- **In `servePendingPrs`** (`pr.ts:1024-1033`), add the `catchUpOwed` clause.
- **Add `'PrMerged'` to `PR_EVENTS`** (`work-loop.ts:119-129`). The append then reaches `serve` at once through `trackWalk` (`work-loop.ts:453-461`, `:664-669`), and the drain waits for it. Without this the catch-up waits for the next tick's `resumePrs`, up to `SWEEP_MS = 5 * 60_000` (`work-loop.ts:184`). That tick still covers a missed event and a restart.

## Every merged PR is owed a catch-up, once

`servePendingPrs` iterates over `listPrs`, which is every PR in the project, and `catchUpOwed` is true for any merged PR with no record. No PR merged before this change has one, so on the first start after deploy each of them is owed. There is no "latest only" rule, and a newer PR does not cancel an older one's obligation.

- `catchUpOwed(state)` is pure in the domain and the conductor picks every PR for which it holds. Each is served under the project's lane, one at a time.
- Historic merged PRs cost little. The first one's catch-up merges `main`'s tip into the personal branch. Each later one finds that tip already in the branch with no merge of ours to show for it, and records `PrCaughtUp` with no merge commit (`pr-sync.ts`, the `nothing` outcome). That is the fix the evidence asks for: e4c4ae6 is in neither branch until the first one runs.
- A PR whose catch-up waits on a person keeps waiting after a newer PR is submitted. A newer PR's freeze and sync bring `main` into its own branch (0130 §6), but that does not discharge the older PR's catch-up: it stays owed, and `lingtai pr` names it by number (`apps/cli/src/pr.ts`, the `older` loop in the status lines).
- `lingtai pr retry`, `rounds` and `--pr <n>` can address it: with no `--pr` the request goes to the open PR, else the latest merged PR waiting on its catch-up, and `--pr <n>` names an older one.

## Pause

Today nothing pauses the PR walks: `resumePrs` has no pause check (`work-loop.ts:467-479`). The only lock a PR consults is the resolver's `locked`, *"the sentence for a lock that stops new work on the project (0126 §6)"* (`pr.ts:184-185`), which is asked before a round (`pr-resolve.ts:430`, `:597`).

The ticket decides that a paused project does not start a catch-up:

- At the start of the lane turn, ask `ports.resolver?.locked(project)`.
- If it returns a sentence, record `PrCatchUpFailed { why: 'locked', detail: sentence }` and do nothing else. It stays owed, and the *once per answer* rule keeps it from appending every tick.
- With no resolver there is no lock port, and it proceeds as the merge back does.

## One body, parameterised

Turn `mergePrBack`'s body (`pr-sync.ts:335-722`) into a function that takes a small record. These are the places that name the PR head today and must take a parameter:

| What | Merge back today | Catch-up |
|---|---|---|
| owed, re-read in the turn and in `pushResolution` | `mergeBackOwed(state) && state.lastPushed === prHead` (`:510`, `:583`) | `catchUpOwed(state)`, still the same `mainSha` |
| theirs | `prHead` (`:461`, `:616`) | the tip of `fetchedRef(n, 'main')` |
| the commit's name in the merge's other side | `prBranch` (`:598`, `:684`) | `branch.main` |
| subject | `Merge ${prBranch} into ${branch}` (`:340`) | `Merge <main> at <sha7> into <personal> after PR <n>` |
| the lost-record match | `second === prHead` (`:433`) | see below |
| record ok / failed | `recordPrMergedBack` / `recordPrMergeBackFailed` | `recordPrCaughtUp` / `recordPrCatchUpFailed` |
| `checkId` | `pr-${n}-back` (`:475`, `:604`, `:689`) | `pr-${n}-catch-up` |
| the round's `commit` | `prHead` (`:678`) | `mainSha`, with `merging: 'back'` as the ticket says |

Details:

- **Fetch both refs in the one `fetchInto`** at the top of `attempt` (`:413`): personal into `fetchedRef(n, 'personal')`, `branch.main` into `fetchedRef(n, 'main')`. The `'main'` kind already exists (`pr-git.ts:10`). Read the tip in that same attempt, so `lost` → `attempt(1)` re-reads both.
- **Keep the parts that vary as parameters, and leave `pushIt` unchanged.** It builds its refspec from `branch` alone (`:379-381`). The `branch === main` refusal at `:371-374` comes before any push and serves both.
- **Keep `base: prBranch` for the build.** The comment at `:471-473` says why the base must not be the personal branch: *"`branch.personal`'s own stream's newest `BaseChecked` is read as the state of that branch, and a commit that was never on it must not stand there."* `branch.main`'s stream is wrong for the same reason. The merged PR's branch stream is the one nobody reads as a branch's state.
- **`backRef(n)` and `fetchedRef(n, 'personal')` can be shared.** The merge back is owed only `in-review` (`pr-sync.ts:306`), the catch-up only `merged`. Both run under the same project permit, so they never overlap on one PR. A merge back's resolution still running when the PR merges stops itself: `pushResolution` re-reads at `:583`.
- **`refusedRecord`** (`:353-366`) exists for #1354, a PR that ended after the push. A catch-up's record can only be refused as `already`, so log it and append nothing.

### Finding a lost push

The ticket says the catch-up runs **once per PR**. Suppose a catch-up of `main` at X landed, its record was lost, and `main` moved on to Y. Searching for "second parent is Y" finds nothing and merges a second time. Search for this PR's subject instead, and hold what it finds to the claim it would record:

- Ask for `--format=%H %P%x09%s`.
- Accept a line only when it has a subject, its second parent P2 gives exactly the subject `Merge <main> at <short(P2)> into <personal> after PR <n>`, and P2 is an ancestor of `main`'s tip read in this attempt. A merge that names another branch, another PR or a commit that is not `main`'s says nothing about this catch-up.
- Record that line as `PrCaughtUp { mainSha: P2, mergeCommit: %H }`.

Compare the whole subject, not only `--fixed-strings --grep`, because `after PR 1` is a substring of `after PR 12`. Keep `--grep` as the pre-filter.

## The domain

`catchUpOwed` moves into `packages/domain/src/pr.ts`, because `conflictOpen` (`pr.ts:1062`) needs it. The new `conflictOpen` is `walking(state) || state.status === 'in-review' || (state.status === 'merged' && catchUpOwed(state))`. Otherwise `syncRoundTransition` (`:1048-1056`) refuses every catch-up round, and the comment at `:1059-1060` calls that *"a refusal that will never lift"*.

Grants and retries are **new for this wait**, not copied from the merge back:

- Today's merge-back failures at In review cannot be granted or retried. `grantTransition` requires `status === 'waiting'` (`pr.ts:1143-1144`), `retryRequestTransition` requires the same (`:1197`), and `notAskable` refuses any PR that is not open (`:1098`).
- So: `catchUp: { mainSha, outcome: 'caught-up' | 'failed', mergeCommit, why, conflict, grantedThen } | null`. `grantedThen` is `grantedFor(state, 'back', mainSha)` (`:1109`) at the moment the failure is reduced.
- `catchUpOwed` is true when the state is merged and one of these holds:
  - `catchUp === null`;
  - the last failure was `unknown` or `locked`;
  - the last failure was `conflict`, `red` or `lost-push`, and a retry is pending or `grantedFor(...) > grantedThen`.
- `PrRetryRequested` already sets `pending` whatever the status (`pr.ts:470-472`). Make `PrCaughtUp` and `PrCatchUpFailed` clear a pending retry, so the one pending slot (#1314) is freed by the answer.
- `PrRoundsGranted` on a merged PR already just appends to `grants` (`pr.ts:458-468`, `walks` false).
- `grantTransition` and `retryRequestTransition` get one branch. If the PR is merged and its `catchUp` failed with `conflict`, `red` or `lost-push`, accept it: grants only with `merging: 'back'` and `commit === catchUp.mainSha`. Every other merged PR is refused as today. `notAskable` needs the same exception.
- Main can move after a failure. The retried catch-up merges the tip as found, so its rounds may be keyed on a newer sha with a fresh budget. That follows the ticket's *"the tip is read and merged as found"*.

Rounds can collide. If `main`'s tip equals the PR's `lastPushed` (a `how: 'git'` merge), the catch-up's `('back', mainSha)` rounds are the merge back's `('back', prHead)` rounds. That is the same commit merged into the same branch, so sharing one budget is correct. Leave it.

Register both events in the step map beside `PrMergeBackFailed: ['outside']` (`events.ts:3383`), and in the union at `:3244`. `apps/board/unit/history.test.ts` reads PR events; check it for an exhaustive list.

## The CLI

- **`prRequestVerdict`** (`apps/cli/src/pr.ts:343-398`):
  - The `!isOpen(latest)` refusal at `:355` lets through a latest merged PR that is waiting on its catch-up.
  - The conflict comes from `latest.catchUp.conflict`, with `commit = catchUp.mainSha`, instead of `latest.wait?.conflict` (`:360`).
  - The wait loop (`:389-398`) answers on a merged PR when `catchUp` changes or `pending` clears.
- **The catch-up line** goes in the `ended` block (`:182-187`), for `status === 'merged'` only.

## The ADRs

0130 is **proposed** (`0130-a-project-is-solo-or-team.md:3`), so it is edited, not superseded. Three places need changing:

- **§6** says *"`main` is brought in when a PR is submitted or reworked, and only then"* (`:138-140`). The "and only then" is what this ticket changes, so §6 changes with it, not only the *Left for later* bullet (`:166-169`).
- **0131** owns the PR's events. Its list at `0131-a-pr-goes-from-draft-to-merged.md:305-309` names `PrMergedBack, PrMergeBackFailed`; add the two new events there.
- **0131 §9's merge-back rules** (`:222-233`) are the rules the catch-up shares. Add a sentence there pointing to it.

## Checks

Every *Done when* item can be checked at unit level with the fakes in `packages/conductor/unit/pr-sync.test.ts` and `pr-resolve.test.ts`. Nothing depends on `pnpm test:integration`. Add these to the ticket's list:

- (a) A merged PR that is not the latest is served too, once, and a second serve of it appends nothing.
- (b) A `locked` answer records `why: 'locked'` and pushes nothing.
- (c) A lost push for `main` at X is found after `main` moved to Y and recorded with `mainSha: X`, with no second merge.
- (d) `PrMerged` is in `PR_EVENTS`.

A behaviour question after deploy is settled on the merged PR's stream: `PrCaughtUp.mainSha` and `.mergeCommit`, or `PrCatchUpFailed.why` and `.detail`. It is not settled by a log line.
