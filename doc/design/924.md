# #924: the shape of the change

#921 has landed (`40a7707a`), and it moved code since the ticket was written. The ticket says `edit-body.ts:210-224`, but the write and the resolve are now in `editBodyAndRequeueHolding`, at `packages/conductor/src/edit-body.ts:106-125`. The triage write is in `resolveWaitHolding`, at `packages/conductor/src/resolve-wait.ts:362-411`. `WaitResolved` is at `packages/domain/src/events.ts:352-357`.

## 1. The schema

Add `answers` to `WaitResolved` (`events.ts:352`) as the ticket gives it. Use `index: z.number().int().nonnegative()` and `answerId: z.string()`. Give it a short comment saying it is the copy of what went into the body: absent means nothing was written, and it is never empty. `WaitResolved` is a plain `z.object`, not strict, so the change is purely additive. Export the inner shape only if a test needs it. Then run `pnpm events:generate`.

## 2. The picks come out of `triageAnswersText`

`resolveWaitHolding` gets the text, not the picks. Line 372 calls `triageAnswersText(triage.cause, options.picks)`, and that function works out the effective id inside its loop: `const id = picks[i] ?? question.recommended` (`packages/domain/src/triage.ts:138`). It returns only `{ ok, text }`.

If the conductor rebuilt the defaults itself, that would be a second copy of the rule, and the log could disagree with the body. So add `picks: { index: number; answerId: string }[]` to the `ok: true` branch of `triageAnswersText`'s result. Fill it in the same loop, one entry per `asks` entry, in order. That way the ids recorded are the same ones that built `text`. The field is additive, so existing callers still compile. Extend `packages/domain/unit/triage-answers.test.ts` to check that defaults show up in `picks`.

## 3. `resolveWaitHolding` sets `answers` exactly where `written = true`

- Declare `let answers: PayloadOf<'WaitResolved'>['answers']` beside `written` (`resolve-wait.ts:367`).
- Set it to `{ picks: answers.picks, section: answers.text }` on the line where `written = true` (`:395`). That point is after `writeSection` returned `written: true`.
  - `section` must be the same `answers.text` string passed as `text:` to `writeSection` at `:393`. Do not use a value re-read from the body.
- Rename the local `answers` (`:372`) to something like `composed`, so it doesn't clash with the new local.
- Spread it into the payload at `:417-422` only when it is defined: `...(answers ? { answers } : {})`.

This leaves `answers` absent in every case the ticket rules out, with no extra conditions:
- Approve, Split and Close never enter that block.
- A wait with no triage, or with no questions (`answers.text === ''`), never sets `written`.
- The continuation-retry path returns at `:262`, before anything is appended.

## 4. `EditBodyAndRequeue` passes the text in

Add one optional field to `ResolveWaitOptions` (`resolve-wait.ts:118`): `writtenSection?: string`. Its doc comment should say: *"the exact text `editBodyAndRequeue` handed `writeSection`; read only for `EditBodyAndRequeue`"*.

In `resolveWaitHolding`, when `resolution._tag === 'EditBodyAndRequeue'` and `options.writtenSection !== undefined`, set `answers = { picks: [], section: options.writtenSection }`.

`editBodyAndRequeueHolding` passes `writtenSection: options.text`. That is the same value it gave `writeSection` at `edit-body.ts:106`: untrimmed, with nothing normalised.

Two alternatives were rejected:
- **A general `answers` option.** It would let any caller attach answers to an Approve. Under this design, `answers` can only come from a write the function made itself, or from the one resolution whose caller made the write.
- **Making `EditBodyAndRequeue` carry the text in the `Resolution` union.** That changes 0118 §1's `Resolution` and every reader of it.

## Edges the ticket leaves to the design

- **Retry after `stale` or `write-failed`.**
  - A second call rewrites the same section key and records `answers` from that second composition.
  - The first call appended no `WaitResolved`, so only one copy exists.
  - In the `not-blocked`-after-write branch (`:400-409`), nothing is appended and `answers` is dropped, as the ticket accepts.
- **The section on the log vs the section in the body.** `writeSection` trims and turns CRLF into LF when it writes (`write-section.ts:21-28`). The log keeps the string as it was handed over, before that. This is "what was written" in the ticket's sense: the input to the write, not a re-read of the body.
