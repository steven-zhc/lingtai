## Design: #573 — the granted round tagged on its `RunSpent`, folded onto the rail line

### 1. Where the tag goes: `SpentFor.Action.grant`, optional

Put the field on the `Action` variant of `SpentFor` (`packages/domain/src/events.ts:707-712`), not at the top level of `RunSpent`. `SpentFor` is documented as *"What a paid run was for"* (`:697`), and a granted round is one of those things. The new shape is `{ _tag: 'Action', step, name, round, grant?: WaitId }`. It is optional, so every stored payload still parses. Update the doc comment above `SpentFor`, which says `step`, `name` and `round` find one action's spend: `grant` names the person's decision that paid for it, and it is absent on every automatic round.

**`spend` (`packages/projector/src/spend.ts:152-172`) needs no column and no migration.** It reads `d.for.step`, `.name` and `.round` by name, so an extra key is ignored. Nothing in this ticket reads the grant through `spend`, because the rail line is folded off the run stream (§3). Don't add a `grant` column just for symmetry. The PR still says to run `lingtai projection rebuild spend` and `lingtai projection rebuild task_view` after the merge, as the ticket asks. Both should be no-ops, and the PR should say that too.

### 2. Who writes it: `fixRound` in `conduct.ts`, from `continuation.resumedWaitId`

Only one writer changes: the `RunSpent` that `fixRound` appends, `{ _tag: 'Action', step: 'implement', name: spec.name, round }` at `packages/conductor/src/conduct.ts:3637-3641`. Add `grant: continuation.resumedWaitId` when `continuation?.grant !== undefined`.

Why that id is the grant's `waitId`, and why no round numbers are matched:

- `resumedWaitId` is `approvedWaitId` (`conduct.ts:1050`), and that is `folded.lifecycle.waitId` (`:982`).
- `reduceTicket` sets that `waitId` to the `block.waitId` the `WaitResolved{GrantFixRound}` resolved (`packages/domain/src/ticket.ts:357-375`).
- So the id comes through the lifecycle the claim already read. It is not inferred.

Why every `fixRound` in a granted continuation is the granted round:

- `continuation.grant` is set only when `granted` is true (`conduct.ts:1073-1081`) or a `ContinueConflict` was confirmed (`:1056-1070`).
- For such a pass, `runPass` caps it with `roundLimit = roundsSpent` and `restartLimit = ceilings.restartsSpent` (`packages/conductor/src/pass.ts:1161-1166`, *"the lap that spends a human grant ends at a person"*). The lap can open no second round and no restart.
- So no extra condition is needed.

**Tag `ContinueConflict` too.** `ticket.ts:356` calls it *"a conflict-flavoured `GrantFixRound` (#558)"*. It gives the lifecycle a `grantRef` (`:372-374`) and is held to the same cap. If it were left untagged, its paid round would print as an automatic one, which is the inference this ticket removes. The line words both the same way: a round a person granted.

**Leave the other `RunSpent` writers alone:**
- `firstDispatch`'s writers (`conduct.ts:3431`, `:3476`) always write round 0.
- The judge dispatch's (`:2562`).
- `runActions`' writer in `packages/actions/src/action.ts:798-802`. This is the cold reviewer during the granted lap: it is paid inside that lap but is not the round the grant bought.

0118 §7 defines the grant as *"one paid `implement` round"*, so the bill printed is the fixer's. Say so in the `describeHeld` doc so nobody reads it as the whole lap's cost.

**Unit test.** `packages/conductor/unit/conduct-continuation-judge-session.test.ts` already drives a `GrantFixRound` continuation through `runOnce` with fakes (`:48-53`). Extend it, or add a sibling file, to assert both halves of the first Done-when:
- the granted lap's implement `RunSpent` carries `for.grant === <the wait's id>`;
- the first pass's round-1 `RunSpent` has no `grant` key at all. Use `'grant' in for`, not `=== undefined`, so the test pins that the field is absent rather than set to `undefined`.

### 3. The read model: `RunProgress.granted`, folded in `foldProgress`

The run stream is one stream throughout. A continuation reuses `options.continuing.runId` (`conduct.ts:1109-1111`), and `fixRound` appends to `runId` (`:3636`). So `foldProgress` (`apps/board/src/lib/progress.ts:349`) can see every grant from the events it already receives.

- Add a `case 'RunSpent'` to the raw `switch (event.type)` (`:420`). It reads `data.for`; when `for._tag === 'Action'` and `for.grant` is a string, it pushes `{ round, waitId, costUsd }`.
- Add `granted: readonly { round: number; waitId: string; costUsd: number | null }[]` to `RunProgress` (`:186-210`).
- Read the raw payload, as the `RunStarted` and `StepsResolved` cases already do. Don't add a `BoardFact`: `boardFactOf` lives in `@lingtai/domain`, and widening it is a second change with other readers.

**Automatic rounds must exclude granted ones.** Today `spent` is the highest `RoundOpened.round` (`:555-557`). `continuationRound` gives a granted lap the round after every round already recorded (`conduct.ts:540-552`). So `spent` changes in this ticket: it becomes the highest `RoundOpened` round whose number no `RunSpent{grant}` on this same stream names.

This is a comparison between two facts on one stream, where the `RunSpent` names its own round. It is not a match against `WaitResolved`, which is what Watch out forbids.

I could not read the log. Whether a granted lap writes a `RoundOpened` at all (that is, a `PassRouted{next: FixRound}`) settles whether `spent` was already wrong, and it is not settled. The fold is correct either way; the unit test should cover both histories.

### 4. The sentence: `describeHeld` takes `granted`

`describeHeld` (`progress.ts:636-659`) gets a `granted` argument, and both callers pass `progress.granted`:
- `apps/board/src/lib/board.ts:569`
- `apps/board/src/lib/task.ts:1944`

The function's own doc gives the reason there is one function: *"so the card and the task page cannot word one hold's budget two ways"*. Keep it that way: no wording in the callers.

**Shape:** `2 of 2 rounds · round 3 granted, $1.42 · 1 restart left`. Each granted round is its own clause, in round order. The rail already supplies *what refused* as a prefix (`apps/board/src/app/rail.tsx:269,289`), so `describeHeld` does not repeat it.

**Money must not go through `lib/spend.ts`.** That file imports `@lingtai/projector`'s runner (`apps/board/src/lib/spend.ts:27`). `progress.ts` is imported by `rail.tsx`, and pulling a server-only import into that graph is the #230 failure that only the integration-half Next build catches. Format inside `progress.ts` by `billText`'s rule (`spend.ts:177-191`): cents rounded once per row, and a `null` `costUsd` reads `cost unknown`, never `$0.00` (0110 §4/§7). That is a few lines.

**Unit tests** go in `apps/board/unit/progress.test.ts`, which already has `describe('describeHeld')` at `:315`:
- one test folds a history with two automatic rounds and one `RunSpent{grant}` round, and asserts the exact line;
- one test has a granted round whose `costUsd` is `null`;
- the existing no-grant cases stay byte-identical.

### 5. The requeue sentence

Edit the cost-line text for both `RESOLUTION_COPY.Requeue` and `RESOLUTION_COPY.EditBodyAndRequeue` (`apps/board/src/app/standing.tsx:67-74`). Both release with `cause: ByPerson` (`packages/domain/src/events.ts:227`), and 0118 §7 says *"Every cost line on the page says so."*

Use one shared sentence, for example *"This neither spends nor refunds an automatic restart."*, defined once and appended to both.

`standing.test.tsx` and `visual-waiting.test.tsx` may assert on this copy, so update them rather than loosening them.

### Checks

Everything here is unit-level: the conductor fake run (§2), the fold and the sentence (§3–4), and the copy (§5). None of it needs `pnpm test:integration`. The one check this ticket cannot reach is the Next build seeing a server import inside `rail.tsx`'s graph. The rule in §4 against importing `lib/spend.ts` from `progress.ts` is what stands in for that check.
