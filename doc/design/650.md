# Design note: #650 — the daily ceiling refuses a stalled `spend` projection

## Where the check goes

The check belongs in `apps/cli/src/day-ceiling.ts`, and nothing changes in `packages/conductor`. `dayCeilingPause` (`packages/conductor/src/day-ceiling.ts:137`) appends a pause when the ceiling is reached and lifts its own pause when spend is under it (`:140-146`). A stalled read has to return before either can happen. If it got as far as `dayCeilingPause`, stale totals that happen to be under the figure would lift a ceiling pause that is really in force. So the order inside `dayCeilingStop` is:

1. Read the ceiling. If it is `undefined`, call `dayCeilingPause` exactly as today and do not read the lag. That is the ticket's "no `day_usd`, nothing changes".
2. Read the lag. If the read throws, the existing `catch` (`:24-26`) already gives the *could not check the daily ceiling* sentence.
3. If `spend` is stalled, return the stall sentence. Nothing is appended and nothing is lifted.
4. Otherwise call `dayCeilingPause` as today.

A stall also stops work when a person has waived the ceiling for today (`resumedPast`, `:152`). That is intended. `lingtai resume` does not lift it; what lifts it is the projector moving again. The stall check appends nothing, so it has nothing to resume.

## A pure rule and a seam

`dayCeilingStop` calls `machineDayCeiling()` and `readSpend` directly (`:18-21`), and it has no unit test today. The only test that mentions it is the source-text test `apps/cli/unit/daemon-day-ceiling.test.ts`. The four *Done when* tests need two changes:

- **`spendStall(lags: readonly ProjectionLag[], now: Date): string | null`**: a pure function exported from `day-ceiling.ts`. It returns the sentence or null, and both `dayCeilingStop` and `daySpendLine` use it. The 60 s threshold is a module constant, not configurable (out of scope). Write `lag` as `N events behind`. Write the age in whole seconds or minutes; when `updatedAt` is null, write *has never moved*.
- **An optional second argument to `dayCeilingStop`**: `{ ceiling?, lags?, rows?, now? }`, with defaults `machineDayCeiling`, `() => projectionLag()`, `(since) => readSpend({ since })` and `new Date()`. The tests pass fakes and `createMemoryEventStore()`. A test for "no ceiling → lag never read" passes a `lags` that throws or counts its calls. No test may fall through to the defaults, because `HOME=/nonexistent pnpm test` has to stay green.

## The missing-row edge differs from the ticket

The ticket says a missing `spend` row should count as stalled when the log has any `RunSpent` today. **Do not build that scan.** A missing row cannot happen once a projector has started. `start()` registers the checkpoint before it follows (`packages/projector/src/projection.ts:202-205`, `store.register(ctx, projection.name)`). Both `withProjector` and `ProjectorLive` start `spendProjection` (`apps/cli/src/projector.ts:162`, `:232`), and every process that appends holds a projector (CLAUDE.md, 0022). The one exception is `controlCommand` (`apps/cli/src/daemon.ts:683`), which appends only to the control stream. Answering "any `RunSpent` today" would also mean scanning the log by type, and `EventStore` reads by stream.

So: **no `spend` row means not stalled**, and the check falls through to `readSpend`, which reports what it finds. This keeps "a fresh install with no spend is not stopped" without a log read. `lags()` returns `[]` when there are no checkpoints at all (`packages/projector/src/sqlite.ts:642`). Put a one-line comment beside the `find` that says why.

## Why the threshold works

The runner folds every event, not only `RunSpent`: `commitBatch` advances the checkpoint to the batch's last `seq` (`projection.ts:150-157`). So on a quiet system `lag` is 0, and on a busy one `updatedAt` moves with each batch. That is the premise that makes `lag > 0 && updatedAt older than 60 s` mean stopped. If it were false, every quiet minute would read as a stall.

One case does read as stalled. `lingtai pause` or `lingtai shutdown` appends without a projector. If no daemon is running, `lingtai status` afterwards shows lag 1 with an old `updatedAt`. That is true (nothing is following), so let `status` say it. When a daemon is running, its projector catches the event up. The daemon's first check comes after its projector has started and caught up, because `runner.start()` resolves only once the runner is current (`projector.ts:150-156`).

## `daySpendLine`

Apply the same rule as the ceiling: read lags only when `ceilingUsd !== undefined`, and when stalled return the `spendStall` sentence in place of `daySpendText`. Without a ceiling, the line stays a plain reading, like the board's `/spend` page (out of scope). A failed lag read goes to the existing `catch` (`:43-45`). This changes `readDaySpend`'s callers, so check `git grep readDaySpend` before you change its signature. Adding the lag read inside `daySpendLine` alone is enough.

## The daemon's outer `paused` callback

`createWorkLoop`'s `paused` is `() => Promise<boolean>` (`packages/daemon/src/work-loop.ts:180`), and the loop logs a fixed `'paused — taking no work'` (`:501`). The inner callback (`daemon.ts:563-572`) already has the right shape: ceiling first, then control, and it returns a sentence, with a `catch` that refuses. The outer one (`:515-519`) collapses the sentence to `true` and has no `catch`.

- Move the inner callback's body into one exported function, `pausedSentence(since, ports?)` in `day-ceiling.ts` or beside `readControl`'s caller. Its ports are `ceiling` and `control`, so a unit test can hand both in. Use it for **both** callbacks.
- Widen the work loop's `paused` to `() => Promise<boolean | string | null>`. A string is logged as given; `true` keeps today's line. Keep boolean accepted, because `packages/daemon/integration/work-loop.test.ts:450` passes `async () => !lifted`, and the integration half cannot be run inside a pass to catch it if that breaks.
- `apps/cli/unit/daemon-day-ceiling.test.ts` splits the source on `paused: async () => {` and expects two bodies (`:12-13`). After this change it fails by construction. Rewrite it to assert that both callbacks call the shared function, and make the *Done when* test a unit test of `pausedSentence` with a ceiling port that returns a sentence.

## Not a gap: `heedThePause` discards the sentence

`apps/cli/src/run.ts:149` does `(await dayCeilingStop(store), readControl(store))`, so a stall sentence is dropped there. That is safe, and you do not need to change it. On the queue path, `runQueue` asks `stillPaused` before **each** item, the first included (`packages/conductor/src/schedule.ts:80-88`, `:160`), and `stillPaused` returns the sentence (`run.ts:172-175`). The single-issue path checks the sentence itself (`run.ts:530-535`).

Say that, and say that a stalled `spend` is answered here as *could not check*.
