# Design note for #516: refuse the pair *work + item* in `src/`

## The ticket's premise is false today, and that decides the shape

The three renames have landed: `0cac0f19` merges #515, and #513 and #514 are closed. The renamed `src/` still does not pass a pair rule. I ran the test's own reading over `{apps,packages}/*/src/`: identifiers plus string, template and JSX text, parsed by `typescript` as `scannable` does at `retired-names.test.ts:126`. It still finds the pair about 35 times in about 22 files:

- **Copy a person reads.** For example: `"this id is not a work item"` (`apps/board/src/app/actions.ts`, ×3), `" already has work items in the log ("` (`apps/cli/src/source.ts`), the `discuss.ts` prompt, `github/src/app.ts`'s permission line, `recipe.ts`'s step descriptions, `doctor.ts`, `attach.ts`, `lingtai.ts`'s help text, `envelope.ts`'s refusal and `apps/site/src/app/snapshot-board.tsx`.
- **Two code-only identifiers:** `WorkItemLink` (`packages/domain/src/ticket.ts`) and `NotifiedWorkItem` (`packages/extension/src/index.ts`).
- **A SQL alias inside a string:** `work_item` in `packages/event-store/src/queries.ts:235,247` and `sqlite.ts:399,412`.
- **A stored value:** `'work-item'`, the `scope` of `ReleaseCause`'s `NeverStarted` (`packages/domain/src/events.ts:226`). It is written into `TicketReleased.cause` (`events.ts:231`). It is mirrored in `action.ts:70` and `pass-next.ts:61,340`, and written at `conductor/src/pass.ts:1438`.

The stored value cannot be renamed here. #450's *Watch out* says *"A stored name is a log change … plan those renames to ride a reset, never alone"*, and #489 said the same: *"if one is still `WorkItem…` that is #464's miss, so name it in the commit body rather than renaming a stored name alone."* Whether a stored `TicketReleased` with `cause.scope: "work-item"` exists is a question about `events` that this pass cannot read.

**Decision: this ticket renames nothing. It records what is left in the allowlist, with counts.** This is #232's precedent (`retired-names.test.ts:39`: *"This ticket renames nothing. It records what is still wrong and makes it countable"*). Two reasons:

- At least one row, the stored literal, has to exist whatever else is done.
- Sweeping copy across 20 files is the kind of wide diff #489 was split to avoid.

So *"passes on main once the three renames have landed"* is met by a ledger that is exactly what `src/` says. Say in the commit body that `'work-item'` is #464's miss, and that the copy is a follow-up ticket.

## Where the rule goes

**A new subsection, `### the pair`, in `doc/reference.md`'s *retired name* section. Not new rows in `### the words`.** `parse` (`retired-names.test.ts:307`) sorts every `the words` row that is not `/^[a-z]+$/` into `named`. The case at line 39 pins `named` to `['GatePoint', 'GateAction', 'Gate']`, so a `work item` row there would be misread and red.

- Use `| retired | current | decided by |` as the table header. `rows()` drops a header only when its first cell is `retired`, `token` or `file` (line 255).
- Two rows: `work item` → `ticket` and `work items` → `tickets`, decided by #450 (2026-10-18).
- Include the plural. The copy says `work items` eight times, and `item` alone stays unretired.
- `parse` returns `pairs` as `[first, second]` word pairs. A new case pins them, the way line 42 pins the four words. Taking a pair out is a door like taking a word out.
- `written()` (line 947) builds the fixture section and must gain an empty `### the pair` block. Otherwise `rows('the pair')` fails every ledger case.

## How a pair is matched, which is the decision the ticket leaves open

`tokens()` (line 164) flattens everything the test reads into identifier-shaped tokens. `"work item"` and `'work-item'` become two tokens, `work` and `item`, and no rule applied token by token can see them. The flattened sequence also loses node boundaries: `work.item`, or `const work = …; item`, would look adjacent.

So **match the pair on each read entry before the join**. In `scannable`, each entry is one `read.push` (lines 136–137): one identifier, or one string, template chunk or JSX text. Inside one entry, a hit is a word `work` followed directly by a word `item` or `items`, where *directly* means either:

- within one token's `words()` (line 88), which covers `WorkItem`, `workItem`, `work_item` and `WORK_ITEM`; or
- across two tokens separated only by whitespace or `-`, which covers `work item`, `Work items` and `work-item`.

Template holes stay apart because a hole is a different entry, as line 878's case already requires.

**The ledger key.** `counts()` reads a key as `\S+` (line 268), so the key cannot contain a space:

- A hit inside one token is keyed by that token: `WorkItemLink`, `NotifiedWorkItem`, `work_item`.
- A hit across tokens is keyed by the lowercased words joined with `-`: `work-item` or `work-items`.

This works because the exemption and allowlist machinery is keyed `file · token` throughout (`count`, line 388), and the pair hits feed the same `hit` map. A hit counts once: do not also count its `work` and `item` through the word rule, which never matches them anyway.

Neither `item` nor `items` goes into `retired`. `lineItem`, `items` and `itemWork` must stay unflagged. Add them as negatives in the same case as the positives.

Narrow it to that: no ledger row and no `found` token whose `words()` hit the four words. Pair rows are then the only debt the allowlist may carry. Keep its name and its failure messages, so the day `gate` comes back it still fails by name. Do not delete it.

## Proving it fails on `workItem`

Since the renames have already landed, *"run it against main before"* has no commit to run against cleanly. Two unit claims stand in for it:

1. **Scanner-level cases.** Feed `tokens`/`scannable` literal sources: `const workItem = 1`, `'work item'`, `'Work items'`, `WORK_ITEM`, `work_item`, `type X = 'work-item'`, `<p>a work item</p>` in a `.tsx`. Assert each is a hit with the key above. Assert the negatives are not hits: `items`, `lineItem`, `` `work${n}item` ``, and `work; item` as two statements.
2. **The ledger itself.** With the pair rows deleted from the document, *is exactly what src/ says today* reds with every one of them as `unrecorded`. This is the same claim *reds a retired name that no row records* (line 1026) already makes. One more `workItem` added to any `src/` file is likewise one more `unrecorded`.

## The document's *why*

It goes in `### the pair`, in the section's own voice:

- **Why a pair and not `item`:** `item` is ordinary vocabulary (`items`, `lineItem`) and never meant a ticket on its own. The whole-word rule exists so that a list of words never becomes a substring ban, and retiring `item` would be that ban with a different word.
- **Why it is read per entry and not over the flattened tokens.**
- **Why the stored `'work-item'` is a ledger row and not an exemption:** an exemption is a `continue` that grows nothing (*"This table is a second door into the debt"*). The row comes out in the reset that renames the stored value.
