# Design: #405, attempt 2. The pause has to outlive a restart

Start from `agent/405-attempt-1` (`9fb5b514`, `05132757`) and keep almost all of it. `pauseConductorOnce`, the shared `detail`/`reason`, the `queued` fold, the board comment and both test files are the right shape. The judge's comment on #405 says the second major finding argued that a per-repository mismatch should not pause every project. The ticket's *Watch out* already settled that: the pause is installation-wide, on purpose. Do not reopen it. What is left is the restart finding, plus one Done-when item the attempt missed. Add both to the branch's `doc/design/405.md` as a new section. Do not write a second note.

## 1. Why the pause attempt 1 wrote does not hold across a restart

A daemon reads the control stream only from its own watermark onward. In `apps/cli/src/lingtai.ts`, the loop's check (`:944`), the per-ticket check inside the pass (`:989`) and the startup line (`:1020`) all call `readControl(undefined, since)`. `readControl` drops everything at or below `since` (`packages/daemon/src/control.ts:103-105`). [0102](doc/decisions/0102-one-conductor-holds-the-lock.md) §3 decides this: *"a `shutdown` or a `pause` stops the daemon it was aimed at and never the next one"*. The integration-only contract test pins it: *hides what was said before the watermark from the daemon that read it* (`packages/daemon/test/contract.ts:301-322`).

So after `lingtai restart`, the new daemon does not see the refusal's `ConductorPaused`. It takes the top queued ticket and refuses it again. `pauseConductorOnce` folds the **whole** stream, finds the pause standing, appends nothing and returns `already-paused`. The daemon then repeats this every pass. The fold change keeps the ticket in Queued, so the queue no longer drains. But there is now a `DispatchRefused` on every sweep, and the ticket says *"a restart must not … let the daemon take work while it holds"*.

## 2. The shape: this pause is marked, and the scoped read obeys it

**Schema.** Add a field to `ConductorPaused` in `packages/domain/src/events.ts:1470-1488`: `holdsAcrossStarts: z.boolean().default(false)`. It is defaulted for the same reason `until` is. Every pause written before this field existed must still parse as the pause it was.

**Fold.** Add `holdsAcrossStarts: boolean` to `ControlState` (`packages/domain/src/control.ts:44`) and to `emptyControl`. In `reduceControl`:
- `ConductorPaused` sets it with `state.holdsAcrossStarts ||= d.holdsAcrossStarts === true`. It is **sticky**: a person pausing on top of a setup pause does not make the setup pause forgettable, because the setup is still wrong.
- `ConductorResumed` clears it, together with everything else (`:163-172`). That is what makes `lingtai resume` the only thing that lifts it.
- The expiry clause at `:199` cannot apply, because this pause's `until` is null.

**The scoped read.** In `readControl` (`packages/daemon/src/control.ts:103`), fold the scoped events as now. If that fold is not paused, but the whole stream's fold is paused and has `holdsAcrossStarts`, return the scoped state with the whole fold's `paused`, `by`, `reason` and `until`. Do the merge here and not in `reduceControl`: `since` belongs to this function, and `reduceControl` does not know about it.

What this changes and what it leaves alone:
- Every `since` caller in `lingtai.ts` gets this for free. That includes the startup line at `:1020`, which will then print the pause the daemon is obeying.
- A **person's** pause written before the watermark is still ignored. 0102 §3 stands for everything except this one pause.
- The whole-stream readers already see the pause and need nothing: `doctor` (`apps/cli/src/doctor.ts:916`), `status`, the board, and `lingtai run`'s `heedThePause` (`apps/cli/src/run.ts:144-155`).

**The writer.** Give `pauseConductorOnce` a `holdsAcrossStarts` input:
- The refusal branch passes `true`.
- `standDownConductor` passes `false`. Its pause has an expiry, and a restart ignoring it is today's behaviour. Do not change that here.
- Keep the *already paused?* check on the **whole** stream, as attempt 1 does. That check is what leaves a person's pause alone.

**The remaining edge, accepted and named.** A person pauses, the daemon restarts (and ignores that pause under 0102 §3), and the setup is wrong. The refusal finds the person's pause standing and appends nothing. So that daemon refuses the top ticket once per pass until the person resumes. The next refusal after the resume pauses with the marker, and it holds from then on. That costs one event per pass and no money. Not overwriting a person's pause is the rule this trade protects. Put this edge in a comment beside the check.

In the log, this edge looks like:
- `DispatchRefused` repeating on one `wi-…` stream,
- after a `ConductorStarted`,
- while a `ConductorPaused` with `holdsAcrossStarts: false` or absent is standing below that start's watermark.

Any repetition of `DispatchRefused` while a `holdsAcrossStarts: true` pause stands means the scoped read is not merging.

## 3. The ADR

This narrows 0102 §3, which is accepted. Under this repository's rule, an ADR in `doc/decisions/` is edited in place (one ADR per topic, `doc/README.md`), so **edit 0102 §3**. Do not add a file. Add one sentence: a pause the conductor itself appends because the setup cannot provide what a recipe needs carries `holdsAcrossStarts`, and a daemon obeys it whatever its watermark, until `ConductorResumed`. Leave `doc/decisions-archive/0048-…` unchanged; the archive is never edited.

## 4. The minor the attempt left: the project is not in the reason

The reason attempt 1 builds names the runtime, the tier and what is missing, but **not the project**. The Done-when requires the project, because the pause stops every project and a person may have several recipes. The project is available as `project` (`packages/conductor/src/conduct.ts:489`). Put it first, for example `lingtai: claude-code cannot provide sandboxed …`, and assert it in the unit test with `expect(d.reason).toContain(PROJECT)`.
