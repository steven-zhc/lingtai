# #1078: design note

The ticket decides almost everything. This note covers three things the ticket gets wrong or leaves out.

## 1. Keep `readState`'s `why` as it is

The ticket asks for `approve` to be dropped from `readState`'s `why`. Don't drop it. That `why` names **apps/cli's** approve, not `packages/conductor/src/approve.ts`:

- `effect-ratchet.faces.json:168` says *"apps/cli (requeue, continuing, subscribers, status, grant-fix-round, triage, approve) and apps/board read a reducer's state as a promise"*.
- `apps/cli/src/approve.ts:101` still calls `readState(world.store, ticketReducer, stream, 'all', …)`, and this ticket does not touch it.

So moving `approveHolding` (`approve.ts:138`) onto `readThroughSnapshot` leaves that `why` true as written. Editing it would make it false. Treat that `Done when` box as satisfied with no edit, and say so in the PR.

The read move itself goes ahead. Every `readState(...)` call in the six files becomes `yield* readThroughSnapshot(...)` with the same arguments:

- `approve.ts:138`, `:386`
- `resolve-wait.ts:240`, `:406`, `:498`, `:586`
- `ask.ts:65`, `:170`
- `edit-body.ts:84`, `:127`

`readThroughSnapshot` fails in the error channel with `unknown` (`packages/event-store/src/snapshot-read.ts:38,46`), not as a defect. The face's `Effect.runPromise` rejects with that same value. `snapshot-state.ts:6` says *"Since Effect 4, `runPromise` rejects with the store's own error (`causeSquash`)"*. So a read failure reaches a caller as it does today. Leave it uncaught. Do not wrap it in `Effect.orDie`.

## 2. A `try/catch` that exists today becomes a typed failure, not a defect

The ticket lists three catches (`refSha` at `resolve-wait.ts:348` and `:659`, and `tellGitHubAbout` in `close.ts`). The files have more:

- `resolve-wait.ts:313`, `:441`, `:553`
- `ask.ts:88`
- `close.ts:177`, `:235`
- `write-section.ts:59`, `:69`, `:76`, `:85`

The rule for all of them: **if a promise call sits inside a `try` today, lift it with `Effect.tryPromise({ try, catch: asFailure })` (`port-face.ts:18`). Then answer with `Effect.catch` / `Effect.catchIf`, with the same predicate (`instanceof ConcurrencyError`, `BodyChanged`, …) and the same return.**

If it is lifted with `Effect.promise` instead, the call becomes a defect. `Effect.catch` never sees a defect, so the refusal turns into a crash. The unit tests that pin those sentences are the only thing that would notice.

`Effect.promise` is only for calls that no `try` covers today.

The `catch (err) { if (!(err instanceof X)) throw err; … }` shape (`resolve-wait.ts:441-442`, `close.ts:238`) becomes `Effect.catchIf((e) => e instanceof X, …)`. Anything else stays a failure and rejects the face exactly as the rethrow does now.

## 3. The faces must fit the ratchet's face check

`effect-ratchet.test.ts:206-240` accepts a face only when its body is exactly one statement, `return Effect.runPromise(<call>)`. The argument must be a **call** or one of the function's own parameters, plus at most `{ signal }`.

So the face is `return Effect.runPromise(approveEffect(options))`. A face that builds options, catches, or awaits anything first is refused by name.

For `deciding`, the ticket's `Effect.runPromise(decidingEffect(ticketId, busy, Effect.promise(act)))` passes: the argument is a call. `Effect.promise(act)` keeps today's behaviour, because a rejection from `act` dies, and `causeSquash` hands the original error back to `split-ticket.ts`.

The baseline goes from **105** (`effect-ratchet.baseline.json:9`, today) to 86, which is 105 − 19. If the count comes out above 86, something has not been converted. Never raise the baseline to make it pass.

## `decidingEffect`

- The `Locker` is a parameter, not a service. That fits the ticket's signature, keeps it simple to unit-test, and adds nothing to `R`.
- Shape:
  ```
  Effect.acquireUseRelease(
    tryLock lifted with Effect.promise,
    got => got.ok ? act : Effect.sync(busy),
    got => got.ok ? Effect.promise(() => got.lock.release()) : Effect.void,
  )
  ```
  A `tryLock` that rejects is a defect, which matches today: an `await` with no `try` around it (`approve.ts:38`).
- `busy` runs inside `use`, so the release step still runs on that path. It must branch on `got.ok` itself, or a not-`ok` answer would call `release` on nothing.
- The interruption test interrupts the fiber with `Fiber.interrupt` after `act` has reached `Deferred.await`. To know `act` got there, have `act` complete a second `Deferred` as its first step and await that from the test. No timer.

## Edges the ticket leaves open

- **Interrupted mid-append:** the lock is released, but an append that already reached the store is not rolled back. That is the same as a process dying there today, and the version check (`ConcurrencyError`) still holds the next decider. Nothing new to build.
- **`close.ts`'s `recipe` seam** (`close.ts:176`, with its catch at `:177`): lift it with `tryPromise` under the same answer. The `async () => resolved` at `conduct.ts:2677` stays as it is.
- **What settles a regression in the log:** a wrong resolution shows up as a `WaitResolved` whose `waitId` is not the card's. Two decisions slipping past each other show up as two `WaitResolved` on one `waitId`. The unit tests in `resolve-wait.test.ts` stand in for both, because the integration half cannot run inside a pass.
