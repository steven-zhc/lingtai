# #210 — design note

## Where the code is now

The ticket's `run-once.ts:1276` and `:1555` no longer exist, because #256 deleted that engine. `standDown` has one caller: `standDownConductor` at `packages/conductor/src/conduct.ts:1026`, invoked at `:3507`. It appends `ConductorPaused { by: "lingtai", reason, until }` to `ctl-conductor`. Both surfaces the ticket names print `reason` as written:

- the board: `apps/cli/src/lingtai.ts:408` returns `c.reason`
- `lingtai doctor`: `apps/cli/src/doctor.ts:876` prints `paused by ${control.by} (${control.reason})`

So **the third branch is a change to `standDown`'s sentence only.** Do not touch the board or doctor. The "board and doctor both carry it" checkbox is satisfied by the append, and a `standDown` unit test is the proof.

The whole change is in `packages/conductor/src/never-started.ts`, `packages/conductor/unit/never-started.test.ts`, and the pause-between-claims fix in §4.

## 1. Parsing the dated form

Today the clock regex is `/\bresets?\b(?:\s+at)?\s+(\d{1,2})(?::(\d{2}))?\s*(am|pm)?/i` (`never-started.ts:58`). Add an **optional** month-and-day group between `resets` and the optional `at`: an English month name or its abbreviation, a day number, and optionally a `, 2026` year. English only, from a fixed table. 0031 already treats the runtime's prose as English (`0031:56-61` quotes the prefix table), and `Intl` has no parser for it.

When a date is present, resolve **that calendar date** in the zone. Do not use `nextWallClock`, which only picks today or tomorrow (`never-started.ts:265-267`).

- Pull `nextWallClock`'s inner `at(day)` out into something like `wallClockOn(zone, year, month, day, hour, minute)`. Keep the two-pass offset trick and its comment (`:252-256`), and have `nextWallClock` call it.
- For the year, use the zone's current year. If that instant is already past, try the next year (a Dec → Jan message). `within` (`:200-206`) still enforces the week ceiling, and that ceiling is what rejects a date that was really something else.
- A dated reset that is already past is **not** rolled forward to "the next one". That rollover is right for a time with no date and wrong for a date.

The undated path must behave exactly as it does now. The regression risk is next to the change: the optional group must not let `resets 11pm` start matching `11` as a day.

## 2. The third case: a time was named but not read

`parseResetAt` returns `Date | null`, and `null` stands for two different facts. Split them internally:

- Add a private `readReset(detail, now)` returning one of:
  - `{ at: Date }`
  - `{ named: string }` — the fragment it found, clipped
  - `null`
- Keep `parseResetAt` exported with the same signature as a wrapper. It is re-exported from `packages/conductor/src/index.ts:66` and the existing tests use it.

`named` means the message contains a reset marker and no time came out of it. The marker is `\bresets?\b`, `resets_at`, or `try again in`. Include the last one: Codex's wall is `"You have hit your usage limit. Try again in 3 hours."` (`packages/agent/unit/codex.test.ts:100`), and today that message also gets the false *"it named no reset time"*. **Do not parse relative durations in this ticket.** Just stop lying about them.

`standDown`'s `from` (`never-started.ts:181-184`) gets three branches:

- **read**: unchanged, `read from the message itself`
- **named, unreadable**: new, and it has to read as a fault in Lingtai. For example: *"it named a reset time (`resets Sep 19 at 9am`) this build could not read, so this is the recipe's backoff — that is a bug in `parseResetAt`, not the account"*. Quote the fragment, so the reader is pointed at the string rather than away from it.
- **nothing named**: unchanged, `it named no reset time…`

Existing inputs will move categories. Some cases in `never-started.test.ts:64-77` will change from "no reset" to "named, unreadable": `resets 25pm`, `resets 11:74pm`, `resets 11pm (Nowhere/Nothing)`, and the beyond-a-week ISO at `:85`. **That is correct.** Each of them named something. `parseResetAt` still returns `null` for all of them, so those assertions stay green. Add `standDown` assertions that pick the branch, and make each one assert `not.toContain("it named no reset time")`.

## 3. The header

Rewrite the argument at `never-started.ts:18-24` and its restatement at `never-started.test.ts:6-8`. A miss means a *longer* wait only while the true reset is sooner than the backoff. When the reset is further away than the backoff, a miss means resuming early, hitting the wall again, and pausing again, once per backoff until the reset: 45 times for a 45-hour wall. Correctness still holds; the cost runs the other way, and that is why this went unnoticed.

Also fix the `parseResetAt` doc (`:36-39`). Add the dated form to the list, and note that the week ceiling exists *for* this form.

**0031 needs no edit and no superseding file.** Its decision still stands: read the message for a time, fall back to the backoff, never classify on the text. §4's sentence is about correctness and is still true. The mistake was in the file's gloss on it.

## 4. Is the pause in force before the next claim?

Read, not assumed:

- **`lingtai run`:** `runQueue` is handed `paused: stillPaused(options.store)` (`apps/cli/src/run.ts:277`) and asks it before every ticket (`packages/conductor/src/schedule.ts:162-168`). This path is covered.
- **Daemon, one project:** `work-loop.ts:491` asks `paused` before each pass, via `readControl(undefined, since)` (`apps/cli/src/lingtai.ts:874`). The daemon's `runQueue` takes one ticket (`max: options.max ?? 1`, `apps/cli/src/conduct.ts:203`), so the next claim comes after that check. Covered, but by `max` being 1 rather than by anything stated, because that `runQueue` is **not** handed `paused`.
- **Daemon, several projects: not covered.** `conductorPass` reads control once for the whole pass (`apps/cli/src/conduct.ts:100`). `conductProjects` then loops over every project (`:252`) without asking again. A project after the one that stood down is claimed in the same pass, straight into an account-wide wall.

**The fix:**

1. Add `paused?: () => Promise<boolean>` to `ConductOptions`.
2. Pass in the same `since`-scoped read that `lingtai.ts:874` builds. It must be scoped, not the whole stream: #159's rule is that a daemon obeys only signals appended while it runs.
3. In `work`, check it before `currentRecipe` and return `"looked-away"` if paused.
4. Also pass it into the daemon's `runQueue` as `paused` (a string-or-null adapter, as `stillPaused` is), so a `max > 1` cannot walk into the wall either.

`conductProjects` has no unit test; `apps/cli/integration/conduct.test.ts` is out of reach inside a pass. It takes `work` and `store` as parameters, so write a unit test under `apps/cli/unit/` with a memory store: two projects, the first project's `work` appends a `ConductorPaused`, and the second `work` is never entered. That test stands in for the integration half.

**The 41-second pair on 09-17 is not settled by this.** Three facts settle it:

- the `RunFailed.kind` of wi-lingtai-197's run
- the `seq` and `until` of the `ConductorPaused` on `ctl-conductor` around 12:35:13
- the `seq` of wi-lingtai-187's claim

If the pause's seq is lower than the claim's and `until` was later than 12:35:28, then a pause that was in force was ignored, and that is a separate bug. If this repository was the only registered project, the multi-project gap does not explain it. State that in the PR rather than implying it does.
