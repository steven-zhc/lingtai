## Design note: #1071, `startDaemonEffect`

The ticket fixes the overall shape. This note adds the five decisions it leaves open. Each one would build different code, and three of them would fail `stopped-projections.test.ts` or the timeout test if read the wrong way. Line numbers are this worktree's `HEAD`, which matches the ticket's `8abc8613` for `daemon.ts`. The baseline currently reads `"packages/daemon": { "async": 50, "run": 0 }` (`effect-ratchet.baseline.json:10`), so 47 means exactly the three `async` the ticket names.

### 1. `recordStopped` is half plain code, half forked read

Today the entry is pushed and `tell` is called before anything waits. The comment says so: *"Listed at once and undated: the checkpoint is a store read that can stall, and a failure is not to wait on a diagnostic"* (`daemon.ts:216-218`). `stopped-projections.test.ts` depends on this. In *"a projection that throws live stops alone"*, the test calls `fail()` and gives it one `setTimeout(0)` before it reads `stoppedProjections`.

So keep these steps synchronous, as plain code: the memo check on `recording`, the `stoppedList.push`, and the `tell`. Only the checkpoint read becomes an Effect, and it is forked. Do not make the whole of `recordStopped` an Effect that `onError` runs. If you do, the push depends on when the forked fiber is first scheduled, which is not a guarantee.

### 2. Fork the read detached, and memoise the fiber

`recording` becomes `Map<string, Fiber<void>>`. There are two callers:
- `onError`, which `follow` calls synchronously;
- the start-time path at `:268-271`.

Both go through the same `Effect.runForkWith(services)(read)`, with `services` taken once by `yield* Effect.context()` at the top of `startDaemonEffect`. `runForkWith` is not counted by the ratchet (`RUN = /^run[A-Z](?!\w*With$)/`, `effect-ratchet.test.ts:70`, pinned at `:366`). Do **not** use `Effect.forkChild` on the start path. A child of the start fiber is interrupted when the face's `runPromise` ends, so a read that outlived `CHECKPOINT_WAIT_MS` would be killed and the entry would stay undated for good. That is exactly what the ticket's timeout test catches.

`dated(fiber)` is `Fiber.await(fiber).pipe(Effect.timeout(CHECKPOINT_WAIT_MS), Effect.ignore)`. Interrupting an `await` leaves the awaited fiber running. The fiber itself must fill the entry on either outcome: `lag()` → `lastSeq`, or a failure → `null` (today's `:220-223`).

Through the face, the test's `TestClock` reaches the forked read only because it carries the start's `services`. The repository has no `TestClock` use yet and no `@effect/vitest`. Run `startDaemonEffect` directly with `TestClock` from `effect/testing` provided, and call `TestClock.adjust` past 2000 ms. Do not call the face from that test.

### 3. Catching a failed `start()`: match today's catch-all, minus interruption

Today `catch (err)` (`:256`) sees every rejection, and only two things continue: an `err instanceof ProjectionShapeError`, or `runner.failure !== null`.

A port's `start()` fails in the error channel (`projection.ts:169-170`, `:316`). A test fake may use `Effect.die`. So use `Effect.catchCause`:
- If the cause contains an interruption, re-fail with the cause unchanged. An interrupted start must reach the `onExit` in §4; it must never be recorded as a stopped projection.
- Otherwise run today's predicate against `Cause.squash(cause)` and `port.failure`.
- If neither matches, `Effect.failCause(cause)`.

Under that rule, the ticket's "dies with a non-shape defect" case has `failure === null`, so it propagates.

### 4. Release the lock with `onExit` on the post-lock segment only

Wrap everything after `held.ok` up to building the port, meaning the runner loop, in `Effect.onExit`, and act only when the exit is not a success:
- `close()` every runner pushed so far, each with its errors ignored;
- then lift `lock.release()`.

Finalizers in `onExit` already run uninterruptibly. Do not put the predates check, the watermark or the acquire inside it, because there is no lock to release yet. Today's `catch` at `:286-292` does `close()` and never `stop()`. Since the port's `close()` is `stop` then `close` (`projection.ts:352`), calling `close()` alone is enough here. For `stop`, keep the ticket's `stop()` then `close()`.

### 5. Build one promise face per port, and reuse it

`onRunner` is called on both paths: success at `:255`, and the stopped-projection path at `:272`. Build `promiseRunner(port)` once, right after `runnerFor`, and pass that same object both times. `trackLiveSpend` keeps runners in a `Set` (`apps/cli/src/live-spend.ts:11`, `:65`), and `releaseLive` looks them up by identity (`:24`). A fresh face per call would put two entries in the set for one runner.

### Smaller decisions

- **`stopped`**: a `Deferred<StopReason>` from `Deferred.make` inside the Effect. `stop` completes it last, inside `Effect.uninterruptible`. The `stopping` flag stays a plain `let`: a second `stop` is `Effect.void`, and its `stopped` resolves once the first finishes.
- **`stop` face**: `stop: () => void daemonStopFace(port)`. `start.test.ts:41-43` calls `stop()` without awaiting, then awaits `stopped` and checks that `'lock released'` came first. That holds because the `Deferred` completes after `release`.
- **The lag line** at `:278-281` becomes `yield* port.lag()`.
- **Errors**: a rejected `acquire`, `watermark` or `predatesHold` lifted with `Effect.promise` is a defect. Effect 4's `runPromise` rejects with the squashed cause, so `startDaemon` still rejects with the original error.
- **Types**: `runnerFor`'s `onError` parameter can stay `(error, phase: string) => void`. `ProjectionRunnerOptions.onError` takes the narrower `'connection' | 'handler'` (`projection.ts:140`). A function that accepts `string` is assignable there, so `defaultRunnerFor` type-checks as written in the ticket.

### What only the log could settle

Nothing in this shape depends on recorded behaviour. If a restart onto this build ever looks wrong, compare the daemon's `ConductorStarted` for that commit with the beacon's `stoppedProjections`. A `stoppedProjections` entry with `checkpoint: null` that lasts past the first beat would mean the read in §2 was interrupted.

### Verification

Everything here is covered by `pnpm test`: `start.test.ts`, `stopped-projections.test.ts` and the three new tests. Nothing in the shape needs the integration half. The daemon's real start against a store, the `the-written-choice` integration test, is checked only after the merge.
