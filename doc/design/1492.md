## Design note for #1492

### Where the fold goes: a pass after the event loop, never inside `add`

The event loop patches nodes in place by position, so merging nodes as they are added would break it. It does this four ways:
- `nodes[nodes.indexOf(s.main)] = …` at `pr-branches.ts:274`, `:350`, `:373`, `:378-379`.
- `lastMergedBack = { node, index: nodes.length - 1 }` at `:436`, written back at `:522-523`.
- `w.sync.node`, kept and looked up again at `:381`.

So add one pure function, `foldCommits(nodes, edges)`. Call it after the owed nodes (`:539-558`) and before the walk cap (`:560`: *"Only the last walks are kept"*). The rules:

- **The key** is `lane + '/' + sha`. Only nodes with `sha !== null`, no `hidden`, and `kind !== 'ticket'` take part.
- **The survivor** is the first member. It keeps its `id` and its place in the array, which is what seeds its x. It takes `kind`, `tone` and `title` from the last member.
- **`BranchNode` gets `lines: readonly { text, tone?, walk }[]`.** Every node has it, and an unfolded node has one line.
  - A line's text is that member's `label`. Drop identical consecutive lines: two walks syncing the same `mainCommit` give the same main-lane text twice.
  - The short sha appears once: if no line contains it, append ` · <sha>` to the first line. That is what `shownLabel` (`:637-643`) does today for one node, so keep `shownLabel` exported as the one-line case. `pr-branches.test.tsx:13` and `:481` import it.
- **Edges:** point every `from`/`to` naming an absorbed id at the survivor, drop any edge whose ends are now the same node, and dedupe on `from-to`. The page keys edges by `` `${e.from}-${e.to}` `` (`pr-detail.tsx:96`), so a duplicate is a React key warning as well as a wrong drawing.
- **Walks:** a line carries its own `walk`, and the survivor's `walk` is the last member's. The cap at `:563` then filters lines as well as nodes. A node with no lines left goes. A survivor's lines can span walks: a second walk's `already` sync is `sha: d.head` (`:369`), which can be the first walk's pushed head. This is how the ticket's *"a dropped walk takes all its lines with it"* holds even then. The survivor's kind is always that of a kept line, because the cap drops only the earliest walks.

`label` stays the first member's, so `<title>` tests like `pr-branches.test.tsx:518` don't move. The page builds the tooltip from the lines.

### The merge dot: decided in the event loop, not by the fold

The fold must not decide this. A `merged` node and a `main` node with the same sha would fold to the later kind, `main`, and the dot would lose its green. So decide it in `case 'PrCaughtUp'` (`:458-468`):

- Scan `nodes` backwards for the last node with `lane === 'main'`.
- If that node is `kind: 'merged'` and its `sha` is `null` or equals `d.mainSha`, add no `main` node. Draw the `catch-up` edge from that node.
- Never write `mainSha` onto it. The label stays as `:504` makes it: `merged`, or `<sha> merged`.

Apply the same rule in `case 'PrCatchUpFailed'` (`:470-488`). It is the same catch-up attempt from the same merge. Then a failed catch-up and its retry both leave the one green dot. Without the rule, the failure would bring the two-dot drawing back.

A failed catch-up and a later successful one name the same `mainSha` only when this rule did not attach them. The generic fold then joins their two `main` dots, which is correct.

### Layout: one solve, every mark a rectangle, *now* placed last

`layoutBranches` (`:658`) changes in five places:

1. **Remove the shrink, don't tune it.** Delete `:703-708` (the `step *= 0.85` loop) and the `ok` field it reads. Call `solve` once with a constant seed step of `36`: x starts at `GUTTER + 24 + i * 36`, in log order. The lane chain rule at `:684` becomes `xs[prev] + 36`, not `Math.min(GAP, step)`. The `width` argument (`pr-page.ts:585`, `DRAWING_WIDTH = 1000`) becomes a minimum width only, as `:710` already treats it.
2. **The label box is geometry `layoutBranches` owns.** Today the page writes text at `n.x - 6`, `n.y - 13` above or `n.y + 21` below (`pr-detail.tsx:117-126`). The box keeps those positions:
   - `x = n.x - 6`
   - `width = max(line length) * CHAR`
   - line pitch 12, for `--fs-2xs` at 10px
   - a box above the lane grows upward from the baseline at `y - 13`, so its first line is on top; a box below the lane grows downward from the baseline at `y + 21`.

   `LaidNode` gets `box: { x, y, width, height } | null` and the baselines of its lines. `pr-detail.tsx` writes each line at its given baseline and computes no offset of its own.
3. **One collision rule replaces `sides`.** Delete `:666-672` and `:686-687`. In its place: for every pair `i < j` in model order, take each mark of `i` (the dot as a square of radius 7, then its box) and each mark of `j`. Where their y ranges overlap, raise `x_j` until `j`'s mark starts at or after `i`'s mark ends, plus `LABEL_GAP`. This is O(n²) per pass, with n under 60.
   - It keeps the fixed point's only-moves-right property, so the 45° raises (`:688-692`) stay correct.
   - A label above the lane does not overlap a dot on the lane vertically, so a dot can still sit under the previous label. That matches the mock's density. The dot spacing comes from the 36px chain rule, not from this rule.
4. **`nowX` no longer reads a node.** `:748` becomes `max(every visible dot x + 7, every box's right edge) + 16`. The final width is `max(width, nowX + 'now'.length * CHAR + 4 + 8)`. `model.now` stays: it decides whether a line is drawn at all (null only when there is no `PrInProgress`, `:188-189`). The builder tests at `pr-branches.test.tsx:394` and `:411` assert it. Its x no longer matters.
5. **Header:** change *"time left to right"* at `pr-branches.ts:5` to *"event order left to right"*. Change the `solve` comment at `:655` (*"the spacing shrinks until everything fits `width`"*) to say the drawing widens instead.

### The page: a 1:1 scroll box

`.prp-drawing { width: 100%; height: auto; }` (`globals.css:3334`) scales a wide viewBox down and shrinks the text below 10px. `doc/design/the-board-style.md:40` says *"nothing under 10px"*. Make these changes:

- Give the SVG `width={d.width}` and `height={d.height}`.
- Change the CSS to `display: block; min-width: 100%; height: auto`. A drawing narrower than the card still fills it. A wider one keeps its natural size.
- Wrap the SVG in a `.prp-drawing-scroll { overflow-x: auto }` box. The box is a small new `'use client'` component, with a `useLayoutEffect` that sets `scrollLeft = scrollWidth`. `pr-buttons.tsx` is the existing pattern for a client component inside this server-rendered page. `renderToStaticMarkup` in the page tests does not run effects, so those tests are unaffected.

In `globals.css:3348`, change `.prp-nd.todo, .prp-nd.main { fill: var(--surface); }` to `.prp-nd.todo`. A `main` dot then takes the default `.prp-nd` fill, `var(--pr-navy)` (`:3347`). That adds no colour.

**Do not touch** `globals.css:3340-3341` or the `<line>`/`<text>now</text>` at `pr-detail.tsx:74-81` except their `x`. #1491 has already landed in this tree (`4fe87d4f4`, *"every PR graph draws now in grey"*), so that styling is final.

### Tests: what changes, and what is the claim

- **Builder tests that change on purpose.** Frames whose fixtures put build and push on the sync's sha now expect one node with several `lines`. That includes `inReview` (`pr-branches.test.tsx:52-66`, `0ab635bffff`) and the frames at `:104` and `:126` that use it. This is the fix, not a regression: rewrite those expectations as lines. Frame 12 (`:268`) uses host merge `1234567aaaa` and catch-up `m2m2m2m`, two different shas, so it must still show two main dots.
- **A collision helper beside `:431`, run over every `frames` entry and the new PR 1 fixture.** It asserts:
  - 36px between dots on the same lane;
  - no two dots at the same (x, y);
  - all boxes pairwise disjoint;
  - no box contains a dot centre;
  - `nowX` greater than every box's right edge and every dot's x;
  - `nowX + text <= width`.

  Assert distances and disjointness only, never coordinates.
- **The PR 1 fixture needs real `headSha`s.** The build and push rows' `headSha` come from `prStepRows` (`:248`, `:250-258`) and must be `fea9eb1…`. A null `headSha` never folds, and the `pr` lane would show three dots.
- **The 45° and order test (`:454-467`) and the main-lane spacing test (`:470-483`) stay unchanged.** Neither should need its expectations edited.
- **The fit test's comment at `:466` must change.** It says *"the SVG scales to the card"*, which is no longer true: it now sits in a 1:1 scroll box.

`pnpm typecheck` and `HOME=/nonexistent pnpm test` cover all of this. Nothing here needs `pnpm test:integration`.

There is one check no unit test can stand in for: the scroll to the right end on load. It runs only in a browser, so it belongs to the person's check on a `pnpm build && pnpm start` page at 1440px, in light and in dark.

No ADR is affected. The split into two pure functions and the 45° rule (#1373) are kept.
