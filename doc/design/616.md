# Design: #616: `@effect/cli` as the entry, with a fall-through, plus the shared output module

## Where the router goes: `entry.ts`, not `lingtai.ts`

The ticket names `lingtai.ts`, but `version` never gets there. `entry.ts` answers it before `lingtai.ts` is imported. It is the first branch in `INSTALL_COMMANDS` (`install.ts:56`: `['version', 'upgrade', 'rollback', 'uninstall']`), dispatched at `entry.ts:50`, and `installCommand` prints `versionLine()` at `install.ts:432-434`. So the place where "a migrated command goes to `@effect/cli`, everything else falls through" is decided is `entry.ts`, ahead of its three existing branches. Those branches are `init`, the install commands, and `void import('./lingtai.ts')`.

**`@effect/cli` decides nothing about a command it does not own.** The router checks `argv[0]` against a list of migrated commands. Only a match is handed to `@effect/cli`. Everything else goes down the existing `if`/`else if`/`else` with `argv` untouched. Do not build a root `Command` and let unknown subcommands fail over from inside it. If you do, `@effect/cli` parses first and adds its built-in options (`--version`, `--help`, `--wizard`, `--completions`, `--log-level`). Then `lingtai` with no arguments, `lingtai --help` and `lingtai --version` would all change.

Today those three go to `lingtai.ts`:
- No arguments and `--help` print `USAGE`. No arguments exits 2 and `--help` exits 0 (`lingtai.ts:1549-1554`).
- `--version` gets `unknown command` and exits 2 (`lingtai.ts:1555-1557`).

They must keep doing exactly that. Moving `--help` onto definitions is ADR 0121 §8, and that belongs to a later ticket.

Concretely:

- **`apps/cli/src/migrated.ts`**: no library imports. It holds `MIGRATED_COMMANDS = ['version'] as const` and a pure `routeOf(argv): 'effect' | 'init' | 'install' | 'lingtai'`. `entry.ts` imports it statically. It is the unit-testable half of the router, because `entry.ts` runs on import and a test cannot load it.
- **`apps/cli/src/cli.ts`**: the `@effect/cli` side. It holds the root command, the `version` subcommand, and `runCli(argv): Promise<number>`. `entry.ts` loads it with a **dynamic `import()`**, as it already does for `init.ts` and `lingtai.ts`. The reason `entry.ts:18-19` gives applies here: a static import is evaluated before a line of the file runs. With a static import, every `lingtai daemon` and `lingtai status` would load Effect's CLI stack for nothing.
- Take `'version'` out of `INSTALL_COMMANDS` and remove the `case 'version'` at `install.ts:432`. Otherwise the list claims a command that the router never sends there. `INSTALL_COMMANDS` is read only at `entry.ts:21,50`.
- Leave `lingtai.ts:1539-1541`'s own `version` case as it is. It serves a process started from that file directly ("here for a process started from this file, as a service's plist starts it"), and this ticket changes nothing in `lingtai.ts`. Also leave the `lingtai.ts:5` "hand-rolled" comment and `USAGE`. 0121's Consequences delete them when the whole contract is built, not on the first command.

Hand `runCli` the full `process.argv` shape. `Command.run`'s handler drops the first two elements.

## `lingtai version`'s text must not change by a byte

This is the trap the ticket doesn't name. **`upgrade` parses this line from a *different* binary.** `versionRuns` (`install.ts:307-312`) spawns the newly downloaded `lingtai version`. It accepts the binary only if the exit is 0, the first word is `lingtai`, and the second word is the version: *"`lingtai 1.0.1 macos-arm64 (binary, node v26.5.0)`, whose second word is it"*. `apps/release/integration/build.test.ts:116-119` asserts the same shape.

So under `@effect/cli` and the output module, plain `lingtai version` still prints `versionLine()` and a newline to stdout, exits 0, and adds no heading, section or colour. That is consistent with 0121 §1: *"A command that has nothing to say says so in one line"*. A layout that wraps it in a heading would break every upgrade *into* this release.

Restructure `version.ts` so the line and the JSON cannot drift apart. Add `versionFacts()`, which returns `{ lingtai, platform, form, node }`, and rebuild `versionLine()` from it. `platformName()` stays exported for the build test.

**`--json`** prints `{ "version": 1, "command": "version", "lingtai": "<workspace version>", "platform": "macos-arm64", "form": "binary" | "script", "node": "v26.…" }` on one line to stdout, and nothing else. The top-level `version` key is 0121 §5's schema version. That is why the program's own version goes under `lingtai` and not `version`.

## The output module: `apps/cli/src/output.ts`

**Rendering returns strings; printing is separate.** That keeps the module unit-testable with no process and no real stdout, which is the 0060 §1 line. It needs:

- **Glyphs:** ✓ in `paint.pass`, ✗ in `paint.fail`, ● in `paint.signal`, per 0121 §2's table. Import `paint` and `coloured` from `@lingtai/env/colour` (`packages/env/package.json:8`). This module defines no colour of its own. `colour.ts:9` calls the palette *"the board's vocabulary, not a second one"*, and ● is the only thing that may be amber (`colour.ts:101-104`).
- **`heading`, `section(title, lines)`, `keyValues(pairs)`, `table(header, rows, { columns })`.**
  - When `columns` is narrower than the table, `table` falls back to one key/value block per row (0121 §4).
  - `columns === undefined` means a redirected stream and is never truncated.
- **Alignment measures visible width, not `.length`.** When colour is on, `paint.muted('#612')` is several bytes longer than `#612`. Pad the plain text first and paint afterwards, or measure after stripping SGR sequences. A test under `FORCE_COLOR=1` should show the columns still line up.
- **Plain mode is not decided here.** `ink` calls `coloured()` on every call (`colour.ts:59-68`), checking `NO_COLOR`, then `TERM=dumb`, then `FORCE_COLOR`, then `isTTY`. 0121 §3 says plain mode *"is decided in `coloured()` … and no command decides it for itself"*. `--no-color` is *"`NO_COLOR` for that process"*: when the option is parsed, set `process.env.NO_COLOR = '1'` before anything renders. In this ticket, define `--no-color` and `--json` as options on the migrated command only. The router never removes them from a fall-through `argv`.
- **`printJson(command, body)` / `printJsonError(command, code, message)`** write `JSON.stringify({ version: 1, command, ...body })` and a newline through `process.stdout.write`. They never go through `paint`. The error form returns the non-zero code for the caller to exit with.

**A *parse* error under `--json`** (`lingtai version --json --bogus`, or `--json=true --bogus`) is reported by `@effect/cli` itself, in prose. `runCli` holds that text back and prints the one error document (`code: "usage"`) instead, with stdout the only stream written. `--json` is recognised in every spelling `@effect/cli` accepts for true.

## `@clack/prompts`: `apps/cli/src/prompt.ts`

Write a thin wrapper that nothing calls yet. Each question takes the flag that would answer it. It refuses by name, naming that flag, when stdin or stdout is not a TTY or when `--json` is in force (0121 §9). Pass `isTTY` in as a parameter so the refusal is unit-tested. `env.ts:63` is the existing `!stdin.isTTY` branch to read alongside it.

The lockfile already resolves `@clack/prompts@1.7.0`. Pin `^1.7.0` so no second copy is added.

## Dependencies and the bundle

- **Effect major:** every workspace package pins `effect: ^3.22.1`. The lockfile also carries `effect@4.0.0-rc.111` for the `@effect/sql-*` v4 packages, and Effect 4 moved the CLI into `effect/unstable/cli`. Choose the 3.x-line versions of `@effect/cli` and its peers, `@effect/platform`, `@effect/printer`, `@effect/printer-ansi` and `@effect/platform-node`, whose `effect` peer range includes 3.22.1. Afterwards, `pnpm why effect --filter @lingtai/cli` must show only `3.22.1`.
- **The environment `Command.run` needs** is FileSystem, Path and Terminal, from `@effect/platform-node`'s `NodeContext`. Import the subpath (`@effect/platform-node/NodeContext`), not the barrel, so esbuild doesn't pull in the HTTP, socket or cluster modules. If pnpm warns about missing optional peers of `platform-node`, that is acceptable as long as they are not in the bundle.
- **Check the bundle by running it.** `bundleCli` (`apps/release/src/build.ts:155-184`) is `bundle: true, format: 'cjs', platform: 'node'`, and nothing is external.
  - Run `pnpm build`, then `node dist/lingtai.cjs version` and `node dist/lingtai.cjs version --json`. The first must still match `lingtai <version> <platform> (script, node …)`.
  - `apps/release/integration/build.test.ts` is integration and cannot run in a pass. The `pnpm build` run is what stands in for it.
  - `prompt.ts` is not reachable from `entry.ts`, so the release bundle won't include clack. Check it once by hand with `esbuild apps/cli/src/prompt.ts --bundle --platform=node --format=cjs --outfile=/tmp/…`, and record in the PR that this was done.

## Tests (all in `apps/cli/unit/`)

- **`migrated.test.ts`:** `routeOf` sends `version`, `version --json` and `version --help` to `effect`. It sends `[]`, `--help`, `--version`, `status`, `init`, `upgrade` and `uninstall` to the branch each takes today, with the `argv` it was given. This is the unit claim behind *"every other command behaves byte-for-byte as before"*. A spawn-the-binary comparison is a process, so it is integration and cannot run before the merge. Say that in the PR.
- **`version` through `runCli`:** with stdout captured, the text output equals `versionLine() + '\n'`. The `--json` output parses to the document above and is a single line. Stderr is empty in both cases.
- **`output.test.ts`:** sections; table alignment with and without `FORCE_COLOR=1`; no `\u001b` under `NO_COLOR=1`, and none with a non-TTY stream and no `FORCE_COLOR`; the narrow-`columns` fallback; JSON written to stdout only. Restore `process.env` after each test, because `coloured()` reads it on every call.

Finish with `pnpm fmt:check`, `pnpm lint`, `pnpm typecheck` and `HOME=/nonexistent pnpm test`.
