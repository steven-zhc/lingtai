## Design note — #1226, links between local tickets

The ticket's Fix is right as written. This note covers the decisions it leaves open: how `filter.ts` gets the store's `listBlockedBy` without a second store, and the details that make that work.

### 1. How `filter.ts` gets the store's `listBlockedBy`

`ticketsForEffect` is typed `Effect<Tickets, Error>` (`packages/conductor/src/ticket-store.ts:267-272`). Its `db` branch really returns `promiseDbTickets(tickets)` (`:290`), but its type hides the store's extra methods. The `ticketsOf` seam in `projectFilterEffect` has the same type (`filter.ts:382`). `filter.test.ts:262-263` fills that seam with `memoryTickets()`.

**Decision: do not change `ticketsForEffect`'s or `TicketsFor`'s signature.** Five call sites use it: `conduct.ts:304`, `run.ts:533`, `read-ticket.ts:86`, `ownerless.ts:52` and `filter.ts:342`. Instead, `filter.ts` gets one helper, used by both branches of `projectFilterEffect`:

```
ticketLinksOf(project, tickets, gh: GitHubClient | null): TicketLinks
```

It checks three cases, in this order:

1. **`tickets === gh`** → `{ repository: \`${gh.owner}/${gh.repo}\`, listBlockedBy: (n) => gh.listBlockedBy(n) }`. This is the same identity test as today's `links = tickets === ghClient ? ghClient : null` (`filter.ts:405`).
2. **`'listBlockedBy' in tickets`** → `{ repository: project, listBlockedBy: (n) => tickets.listBlockedBy(n) }`. This is the `DbTickets` that `ticketsForEffect` already built, so it is the same store and the same table memo (*"One store, one memo"*, `ticket-store.ts:280-281`).
3. **Anything else** → `null`. This is `memoryTickets` in tests.

**The order matters.** `GitHubClient` also has `listBlockedBy`, so the identity check must come first. In the owner branch, reaching case 2 means `tickets !== ghClient`, which means `db`. The ownerless branch passes `gh = null`.

Put a type guard such as `hasTicketLinks(t): t is Tickets & Pick<DbTickets, 'listBlockedBy'>` beside `DbTickets` in `db-tickets.ts`. Do not use a cast in `filter.ts`.

**Do not build a second `makeDbTickets` in `filter.ts`.** It would ensure the tables again and break the memo.

**`filter.ts:200-204` and `:389` must be rewritten.** That comment currently says the reverse of the new behaviour: *"A `db` project gets null even with an owner"*.

### 2. The count is one shared subquery

Every read in `makeDbTickets` takes `project` as `$1`: `listOpenIssues` at `db-tickets.ts:304-307`, `listIssuesSince` at `:314-319`, and `getIssue` at `:326-329`. Write one constant, aliasing the outer table `t` in all three reads:

```sql
(SELECT COUNT(*) FROM ticket_links l
   JOIN tickets b ON b.project = l.project AND b.number = l.blocked_by
  WHERE l.project = t.project AND l.number = t.number AND b.state = 'open') AS blocked_by
```

- `TicketRow` (`db-tickets.ts:136`) gains `blocked_by: number | string`.
- The `Pick<…>` that `toListing` takes (`:175`) gains `blocked_by`.
- `toListing` writes `blockedBy: Number(row.blocked_by)`.
- Replace the comment at `:182-183`. The new count is still never `null`; the reason is now *"this source always reads its links"*.

Because of the inner join, an orphan link row (one with no blocker row) counts as nothing. The ticket already puts that case out of scope.

### 3. The verbs

Add `addBlockedBy`, `removeBlockedBy` and `listBlockedBy` to `DbTicketsEffects` (`:204-220`) and to `DbTickets` (`:121`). In `promiseDbTickets` (`:448-462`), each one is a single `runPort(...)` line. `runPort` (`port-face.ts:10-12`) is the one existing `Effect.runPromise` call site, so this adds no `Effect.run*` and no `async`.

**`addBlockedBy(issue, blocker)` does its work in this order, each step writing nothing if it refuses:**

1. If `issue === blocker`, refuse with `#5 cannot block itself`.
2. Read existing rows with `SELECT number FROM tickets WHERE project = $1 AND number IN ($2, $3)`. Name the first missing number with `noSuchTicket(project, n)` (`:167-169`), so the message matches every other verb.
3. Read `SELECT number, blocked_by FROM ticket_links WHERE project = $1` once, and build an adjacency map in memory.
4. Run a DFS from `blocker` looking for `issue`. If it finds a path, refuse with `#3 blocked by #5 would close a cycle: #3 → #5 → … → #3`. The path is `issue`, then the DFS path from `blocker` back to `issue`. Ignore state: closed tickets can still be on a cycle.
5. `INSERT INTO ticket_links (project, number, blocked_by) VALUES ($1,$2,$3) ON CONFLICT DO NOTHING`.

Adding a link that already exists passes step 4. Its edge `issue → blocker` cannot form a path from `blocker` back to `issue` unless a cycle is already there.

**`listBlockedBy(issue)`** first fails with `noSuchTicket` if `issue` has no row. Then it runs `SELECT b.number, b.title, b.state FROM ticket_links l JOIN tickets b … WHERE l.project = $1 AND l.number = $2 ORDER BY b.number` and maps each row to `{ repository: project, number, title, state }`.

**`TicketLink`** lives in `db-tickets.ts` and is exported through `packages/conductor/src/index.ts` beside the other `db-tickets` exports. Put `TicketLinks` (the board's face) beside `ProjectFilter` in `filter.ts`.

### 4. The board

- `BlockedSkip.blockers` (`apps/board/src/lib/board.ts:918`) becomes `{ ok: true; issues: readonly TicketLink[] }`. Every `readBlockers` reader (`:941-`) only reads `number`, `state` and `repository`, so nothing else changes. Use `import type` from `@lingtai/conductor`: `BlockedSkip` crosses into a client component (`:910`, *"this crosses into a client component"*), and a type import adds no server-side code to that graph.
- `blockerChip` (`apps/board/src/lib/blocker-state.ts:44-45`) takes `TicketLink`.
- `page.tsx:691-693` becomes `[f.project, f.links.repository]`.
- `board.ts:1341` becomes `links.repository.toLowerCase()`.

For a db project, `repository` is the project name. That makes `mine` true at `blocker-state.ts:55`, and the label `#n`. A db ticket has no sub-issue parents, so `adopt` never matches for it, which is harmless.

### 5. Tests, and what each check proves

- **`test/ticket-links-contract.ts`** takes a factory `() => DbTickets`. It runs on `createSqliteTicketSql(openSqliteLog(':memory:'))` in `unit/db-tickets.test.ts`, the same `freshStore` already at `:15-16`. That is unit-level: it is in memory, with no filesystem.
- **The Postgres run** goes inside the existing `describe.skipIf(!postgresUnderTest())` at `integration/db-tickets.test.ts:144`. That is the only check of the `COUNT`-as-string case, and nothing runs it before the merge. **The unit stand-in:** in the contract, assert `typeof listing.dependencies.blockedBy === 'number'` and use `toBe(1)`, not `toEqual`. On Postgres, a missing `Number()` then fails there by name rather than passing through a loose comparison.
- **The column assertions** at `unit/db-tickets.test.ts:39-61` and `integration/db-tickets.test.ts:84` gain `ticket_links`.
- **`filter.test.ts`** needs two cases:
  - An ownerless project whose `ticketsOf` returns `memoryTickets()` plus a stub `listBlockedBy`. Assert `filter.links?.repository === 'name'` and that the stub is what gets called.
  - The existing memory case (`:261-277`) keeps `links === null`.

  Stub the store rather than using a real one, so the case stays free of `@lingtai/event-store`.
- **Board unit test:** `blockerChip({ repository: 'proj', number: 3, title: '', state: 'open' }, 'proj', { repositories: new Map([['proj', 'proj']]), … })` gives `#3`.

### Edges this note decides

- **A memory-backed filter** (tests only) has `links === null`, as today. The board reads that as *"blockers could not be read"* (`queued-stream.tsx:146-147`). No production path gives a `db` project memory tickets.
- **A failure while reading the cycle walk** is a defect, like every other read here (`db-tickets.ts:199-203`). It is never treated as *no cycle*.
- **What the log says.** `projectFilterEffect` and the store append nothing. Whether a db ticket was passed over shows only as the `blocked-by` skip that `runnableNow` returns (`discover.ts:461`), which the board's queued column and `lingtai status` read. No event or field settles it.
