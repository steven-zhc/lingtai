## Design note: #1302, `antigravity` as a second ACP profile

### Where it goes

The change is mostly a second `AcpProfile`. The rest is one choice of sandbox per invocation, made in the one place every agent dispatch goes through.

**1. The profile carries its own identity, and today the runtime does not ask it for that.** `createAcpRuntime` hard-codes two Copilot facts whatever profile it is given:

- `capabilities: COPILOT_CAPABILITIES` (`packages/agent/src/acp.ts:281`), whose `id: 'copilot'` is at `acp.ts:45`.
- `checkAuth: (env) => copilotAuth(binary, env)` (`acp.ts:283`).

`capabilities.id` is what the pass records as the invocation's runtime: `runtime: dispatched.capabilities.id` at `packages/conductor/src/conduct.ts:3671`, fed into `SandboxBoundaryRecorded`'s keys. If the profile does not supply it, an Antigravity run is recorded as `copilot`, and the per-runtime sandbox choice below never sees `antigravity`. So `AcpProfile` (`packages/agent/src/acp-session.ts:25`) gains:

- `id: RuntimeId`, replacing `name: string`; `name` survives only as the label in messages;
- what `capabilities` is built from (`id` from the profile, the rest as Copilot's);
- how a model is chosen;
- the signed-out sentence.

`copilotAuth` / `copilotAuthEffect` (`packages/agent/src/auth.ts:323-330`) become one `acpAuth(profile, binary, env)`. `AUTH_PROBES` (`auth.ts:353`) gains an `antigravity` row on it with binary `agy`. `ACP_PROFILES` (`acp-session.ts:89`) gains `antigravity`.

**2. Three exhaustive lists must each get a row.** `RuntimeId` (`packages/domain/src/events.ts:144`) gains `antigravity`. `tsc` then fails at `RUNTIMES` (`packages/agent/src/runtimes.ts:93`) and at `AUTH_PROBES`, which is the intended effect (`runtimes.ts:8`: *"A `RuntimeId` is dispatchable now because it has a row here and for no other reason"*). The `RUNTIMES.antigravity` row is the same shape as `copilot`'s (`runtimes.ts:94-101`), including `ToolsCannotBeDenied` for `tools: 'none'`: E2 shows Antigravity has no tool-free mode either.

`Account` derives from `RuntimeId` (`events.ts:151`), so `antigravity` becomes an account. `ACCOUNT_NAMES` (`apps/cli/src/commands.ts:36`) is written out by hand and *"`account-lift.test.ts` holds this to `Account`"*. Add `antigravity` there, or that test goes red.

**3. Antigravity is an implement-only agent.** Add it to `IMPLEMENT_ONLY_AGENTS` (`packages/recipe/src/recipe.ts:1390`). The reason is the one that comment gives for Copilot: an ACP agent takes no output schema. That one entry also keeps it out of `runtime.agent`, judges and review (`recipe.ts:3567`, `:3589`), and out of the setup wizard (`packages/setup/src/propose-setup.ts:105`, `apps/cli/src/agents.ts:199`). So the only sandbox choice that can reach it is at `implement`.

### The decision the ticket leaves to the implementer

**Where "cannot be sandboxed" lives.** It is needed in three packages:

- `@lingtai/recipe`, to refuse at resolve;
- `@lingtai/conductor`, to choose per invocation;
- `apps/cli`, for `doctor`.

`@lingtai/recipe` does not depend on `@lingtai/agent` (`packages/recipe/package.json:18-20`: domain, env, sandbox only). A `sandboxable: false` on the profile would therefore have to be repeated as a list in recipe, and the two would drift apart. **Put it beside `RuntimeId` in `@lingtai/domain`** as `UNSANDBOXABLE_RUNTIMES: readonly RuntimeId[] = ['antigravity']` with an `isUnsandboxableRuntime(id: string)` helper, and give the profile no flag. The ticket's *"cannot be sandboxed"* is a fact about the agent at this release, not about how it speaks ACP.

**At resolve.** Use the per-agent branch that already exists at `recipe.ts:3586-3600`. That branch refuses Copilot when `recipe.sandbox?.enabled`, and **that stays exactly as it is**: #1301 is the ticket that changes Copilot. Antigravity takes a sibling branch:

- condition: `recipe.sandbox?.enabled && recipe.sandbox.required`;
- message: the ticket's sentence, *"antigravity cannot run sandboxed in this release — set `sandbox.required: false`, or name another agent"*, prefixed with `steps.${step}'s "${action.name}" names \`agent: antigravity\`` as its neighbours are.

It is a schema refinement, so it refuses on every host, including one that cannot sandboxed at all. That is right: the sentence is about the agent, not the host. `enabled: false` with `required: true` is already refused separately (`packages/recipe/src/sandbox-block.ts:46`).

**Per invocation.** The pass makes one decision, before the claim (`packages/conductor/src/sandbox-decision.ts:3`: *"Decided once per pass, before the claim, so every action of the pass sees one answer"*). Leave that alone. Narrow it per runtime in `sandboxOf` (`conduct.ts:1059`): every agent dispatch goes through it (`:3668`, `:4571`, `:5130`, `:5492`), and it already has `record.runtime` in hand.

Write the rule as a pure function in `packages/recipe/src/sandbox.ts`, beside `sandboxDecision`: `invocationDecision(pass: SandboxDecision, runtime: string): SandboxDecision`.

- A pass decision of `sandboxed` with an unsandboxable runtime becomes `{ kind: 'unsandboxed', reason: 'runtime cannot' }`.
- Every other decision is returned unchanged.
  - `degraded` stays `degraded`. The host's reason is also true, and that banner is the operator's to see.
  - `off by choice` stays `off by choice`.
  - `refused` stays `refused`. It stops every invocation already, and with `required: true` this agent was refused at resolve.

`SandboxDecision` (`sandbox.ts:79`) gains that variant. `sandboxDecision` itself never returns it. `sandboxOf`'s existing `decision.kind === 'unsandboxed'` branch (`conduct.ts:1068`) then records it through `recordUnwrapped` with no further change.

**The record and its readers:**

- **Schema.** `SandboxBoundary.unsandboxed.reason` (`events.ts:1032`) gains `'runtime cannot'`.
- **`boundaryOfDecision`** (`packages/conductor/src/sandbox-record.ts:46`) maps it through.
- **`observedKindOf`** (`sandbox-record.ts:54`) gets an explicit `'runtime cannot'` case that returns **`null`**. It does not get a new `ProjectSandboxObserved` kind, and the `events.ts:2432` enum is not touched. That event is appended *"on the transition"* of a project's state. Inside one pass, the Antigravity implement and a Claude Code review would alternate the project between two states, appending one event per run. Write the reason into the case as a comment.
- **The board's `markOf`** (`apps/board/src/lib/sandbox-view.ts:136-139`) currently draws every non-`off by choice` reason as `degraded` in the signal tone, which is wrong for this one. Add a `'runtime cannot'` state in the muted tone, with a fixed `why` that names the agent. `MarkState` (`:25`) gains the value.

### The profile's ACP details

- **Mode.** Read `modes.currentModeId` from the `session/new` response. If it is not `default`, send `session/set_mode` with `default` before the prompt. If `default` is not among the offered modes, end the run `crash` naming the mode and the modes that were offered. Experiment 019 never measured the mode Antigravity starts in, and its own config could start it in `auto`; 0.16.md rules auto out. Copilot keeps sending nothing (`acp-session.ts:33`).
- **Model.** `openSession` (`acp-session.ts:131`) returns only the session id. Have it return the `session/new` response as well (the probe at `:189` ignores it). The profile's model strategy is one of:
  - `'set_model'`: Copilot, as at `acp.ts:510-513` today;
  - `'config-option'`: Antigravity. Send `session/set_config_option {sessionId, configId: 'model', value}` and take the current model from the `configOptions` in the reply. When no change was asked for, take it from `session/new`'s `configOptions`.

  `usageOf` (`acp.ts:291`) puts that value on the `UsageEntry` as `model`, reported, so with no `modelFrom` (`packages/domain/src/spend.ts:33-36`).
  - If `RunRequest.model` is set and no `model` option is offered, the run ends `crash` before the prompt rather than running some other model.
  - A refused `set_config_option` rejects, and the existing error branch (`acp.ts:570`) ends the run `crash`. Make sure its detail names the requested model.
  - The SDK has the method (`@agentclientprotocol/sdk@2.8.0`'s `dist/v1/stable/methods.d.ts`).
- **Tokens.** `fresh = inputTokens`; `cacheRead`, `cacheWrite` and `output` map one to one; there is no `reasoning`. Unlike `copilotTokens` (`acp-session.ts:65`), `fresh` here does not depend on the cache fields being present.
- **Failed turn.** `/^⚠ failed to construct executor/`. `acpFailure` already trims the start (`acp.ts:191`).
- **Signed out.** One profile sentence, used by both `classifyAcpSession`'s `auth-required` case (`auth.ts:311`) and the run's `never-started` detail (`acp.ts:567`). A run started over ssh then says the same thing `doctor` says: *not signed in, or Lingtai is not running in your GUI login session (started over ssh?) — sign in with `agy acp --login` in Terminal*.

### `lingtai doctor`

The per-project loop at `apps/cli/src/doctor.ts:3252` already adds `unpricedRow` for each ACP agent the project's steps name. Add an `unsandboxedRow` there under `isUnsandboxableRuntime(agent)`. It is an info row whose why depends on the sandbox block:

- **Sandbox enabled:** *"antigravity runs unsandboxed: it cannot run inside srt in this release (it binds a local port and reads the keychain); where the host can sandbox, this project's other agents stay sandboxed; where it cannot, the pass is degraded and they run unsandboxed too"*.
- **Sandbox off:** *"off by choice, like every run here"*.

`unpricedRow`'s *"and names no model"* (`doctor.ts:2665`) is false for Antigravity. Phrase it per profile: Antigravity names its model, and where a fetched rate row prices that model the day ceiling counts its spend afterwards. `run.usd` does not apply: an ACP run is bounded by turns and wall only (`packages/agent/src/acp.ts:53–54`).

### What settles it, and what checks it

- **On the log:**
  - `SandboxBoundaryRecorded` with `runtime: 'antigravity'` and `boundary.reason: 'runtime cannot'` on the attempt's `pass-` stream;
  - no `ProjectSandboxObserved` appended for that invocation;
  - the run's usage entry carrying `model`.
- **No unit test reaches `sandboxOf`.** It is a closure inside `conduct`. The unit-level checks that stand in for it:
  - `invocationDecision` across the four pass decisions × an unsandboxable and a sandboxable runtime;
  - `boundaryOfDecision` and `observedKindOf` on the new reason;
  - `parsePayload('SandboxBoundaryRecorded', …)` accepting it, and still accepting a stored `off by choice` payload.
- **The resolve refusal** is a unit test on `Recipe` parsing: `required: true` names the sentence; `required: false` with `enabled: true` resolves; Copilot with `enabled: true` is still refused with its own sentence.
- **ACP tests** take the injected `spawn` that `AcpOptions.spawn` exists for (`acp.ts:266`), so they spawn no process:
  - the token mapping;
  - `set_config_option` being the method sent;
  - the model read back from the reply;
  - the failed-turn sentence;
  - the mode switch.

### Edges this decides

- **Two passes at once:** `invocationDecision` is pure and runs per invocation. Nothing is shared.
- **Restart:** a daemon runs the `RuntimeId` enum it loaded. A recipe naming `antigravity` on an older daemon is refused at resolve, and every pass answers `stage: 'recipe'`. *Code, restart, paste*, as for any new plugin name.
- **Cost to later changes:**
  - the four exhaustive tables gain a row;
  - every test that enumerates `SandboxBoundary` reasons or `MarkState` gains one;
  - #1301 deletes Copilot's `enabled` branch and does not touch Antigravity's.
