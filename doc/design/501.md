## Design note for #501: always make a merge commit in the merge lane

This is a one-flag change, plus two test assertions and a stale comment. The ticket gives the shape. This note pins down where each piece goes and what is already safe.

### Where it goes

- **The flag.** Add `--no-ff` to the lane's merge at `packages/repo/src/integrate.ts:473`. Put it right after `'merge'`, so the call becomes `['merge', '--no-ff', '-m', …, laneBranch]`.
  - Update the comment above it (`integrate.ts:467-471`). It currently explains only why `-m` names the branch. Add one sentence: `--no-ff` is why `git log --first-parent <base>` reads one line per landing, whether or not the base moved.
- **The push needs no change.** It is still `push origin HEAD:refs/heads/<base>` (`integrate.ts:535`). It is still a fast-forward of the remote, because the merge commit's first parent is the base the lane fetched. A rejection is still answered by `LOST_PUSHES`.
- **The unit test.** The existing test is `packages/repo/unit/integrate.test.ts:90`, *merges the lane branch ref with -m naming the branch, not the ref*. Either extend it or add a test beside it that asserts `merge!.args` contains `--no-ff`.
  - The fake finds the merge call with `c.args[0] === 'merge' && c.args[1] !== '--abort'` (lines 43, 95, 155). `--no-ff` at `args[1]` passes that filter. Do not put it anywhere that makes `args[1]` equal `--abort`.
  - This unit test is the claim the `build` gate can check. Everything below it is integration.
- **The integration test.** This is `packages/repo/integration/integrate.test.ts:109`. After the existing assertions, run `git rev-list --parents -n1 <mergeCommit>` in `originPath`. Assert two parents: the base sha from before the integrate, then the `agent/1` head.
  - Run that file alone. It cannot gate the merge.
- **The stale comment.** `packages/recipe/src/recipe.ts:900-904` says `strategy` is *"`git merge --no-edit` of the branch into the base, then a push that is a fast-forward where it can be one."* Rewrite it to say the merge is `--no-ff`, so it always makes a merge commit, and the push is always a fast-forward of the remote base.
  - The enum stays `['merge-commit']`. After this change it is simply accurate.

### Readers of `mergeCommit` are already safe; name them in the commit body

- **Already assumes a merge commit:** `packages/actions/src/action.ts:272-280` says *"Never `head`… a merge commit is not where the worktree the pass is still holding stands."* That was false on a fast-forward and becomes true with this change. The end step reads `head` via `onSha`, not `merged`, so it is unaffected.

The only `--is-ancestor` outside tests is `apps/cli/src/doctor.ts:1148`. It is about the daemon's own commit, not a landing.

### What is not a risk

An "already up to date" no-op merge cannot happen. `integrate.ts:435-437` refuses `no-commits` before the merge whenever `laneBase..laneBranch` is empty, so `--no-ff` always has something to merge.

### What settles it after the merge

On the log, `IntegrationSucceeded.mergeCommit` is the sha. `git cat-file -p <sha>` showing two `parent` lines on a landing whose base did not move is the proof. That proof only appears after `lingtai restart`, because the daemon running now still has the old `integrate.ts` loaded.
