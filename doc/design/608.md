## Design note for #608: split progress as events on the parent's stream

### Where it goes

- **`packages/domain/src/events.ts`**: the four schemas go next to `TicketSplit` (`:343`) and are added to `EVENTS` (`:2003`). All of them start at schema version 1, so `BUMPED` does not change. `TicketSplit`'s docblock has to drop *"It records what **was** done, after the fact — there is no `SplitStarted`."* (`:331`). It should say instead that `TicketSplit` is the terminal record and the progress events lead up to it.
- **The fold goes in `packages/domain/src/split.ts`.** It is 0118 §12's module and it already holds `ChildTicket` and `Dependency`. Its header says it imports `zod` and `triage.ts` only, under *"the leaf-only rule of `wait.ts`'s header"*. If importing `PayloadOf` from `events.ts` would break that rule, put `splitProgressOf` in a new `packages/domain/src/split-progress.ts` and export it from the domain index.
- **`packages/conductor/src/split-ticket.ts`** does the appending. The module header's *"nothing on the log until all of them were. A partial split leaves no event"* (`:4-6`) is no longer true and needs rewriting in the same commit.
- **Neither projection changes.** `reduceTicket` (`ticket.ts:443`) and `task-view.ts` both have a `default:`, so new types fall through untouched. #603's page will read `splitProgressOf` straight off the ticket's stream, which it already reads. `projection rebuild task_view` therefore has nothing new to replay; say so in the PR rather than leaving the Done-when box unexplained.
- **`apps/board/unit/history.test.ts:55`** iterates over `EVENTS` and requires `summarise` to print something non-empty for every type, even with a `{}` payload. The payload fallback already covers that. A short formatter per type is welcome but not required.
- **`packages/domain/test/events.ts`** should get builders for the four events, in the same style as the `TicketSplit` builder at `:82`.

### The payloads

Every progress event carries **`waitId`**. A parent can be split, come back and wait again (`claim.ts:83` handles "every child it recorded is closed"), so plan keys can repeat across waits. The fold has to scope by wait, not by stream.

- **`SplitStarted { waitId, plan, instance }`**
  - `plan` is `{ children: ChildTicket[], blockedBy: Dependency[] }`: the person's edited plan, as `Resolution.Split` will carry it.
  - `instance` is a non-empty string.
- **`SplitChildWritten { waitId, key, number, id }`**
  - Make it strict, and give the child fields the same shape as `SplitChild` (`events.ts:322`), for the reason that type's docblock gives.
  - **It is appended after `attach <key>` reads the child back as a sub-issue, not after `create <key>`.** The create call does not return GitHub's REST `id`; `record the split` says so (*"no create call returns one"*, `split-ticket.ts:303`). A child adopted by its marker has no `id` either (`:178`). The `id` only exists on the `LinkedIssue` that `listSubIssues` returns (`client.ts:71`).
  - So "written" means the child has the approved body and kind **and** hangs under the parent. `ensure` already reads that list; have it return the matched `LinkedIssue`, or re-find it in the list it read last.
- **`SplitLinkWritten { waitId, ticket, blockedBy }`**
  - Uses `Dependency`'s key form.
  - It is appended after a `chain` step's read-back, and only for the plan's child-to-child links.
  - The parent's own `hold parent ← x` rows and `done when` get no event. `TicketSplit`'s docblock already says the parent's holds follow from `children` and *"is not a row"*. Keep the progress record the same shape as the final one.
- **`SplitFailed { waitId, step, detail }`**
  - `step` is the name from `stepNames` (`:105`), e.g. `create a`, `chain b←a`, `end the wait`. For failures in the GitHub reads before the first step, use `read GitHub`.
  - `detail` is the text that already goes into `SplitTicketResult.detail`.

### The writer

1. **The refusals still append nothing.** These are:
   - lock contention in `splitTicket`;
   - not waiting on `waitId`;
   - `Split` not offered for this wait;
   - plan problems;
   - duplicate titles.

   All of them are checks against the log and the plan, done before any GitHub call (`:130-148`). Nothing has started yet, so a `SplitStarted` there would be a lie.

   `SplitStarted` is appended immediately after these checks, before `listSubIssues`. If one of the reads after that fails (`:166`, `:185`), the writer appends `SplitFailed{step: 'read GitHub'}`.
2. **`instance` becomes a required field on `SplitTicketOptions`.** The writer does not make it. The board does not call `splitTicket` yet (nothing under `apps/` imports it; #604 does that wiring), so creating the id is the caller's job.

   For #604's sake, one line in the option's doc: make it once per process and cache it on `globalThis`. A module-level `randomUUID()` gets re-evaluated by Next's dev HMR, and a running write would then read as *interrupted* to its own page.
3. **Appending is unconditional against the stream's current version.**
   - `append(streamId, expectedVersion, events)` (`event-store.ts:346`) takes a version.
   - Triage and other writers append to the same ticket stream outside this lock, so pinning to the version read at `:130` would throw `ConcurrencyError` for no reason.
   - Re-read the stream's version before each progress append, and retry once on `ConcurrencyError`. Progress events are facts about GitHub, not decisions that depend on what the stream says.
   - `resolveWaitHolding` reads the stream itself (`resolve-wait.ts:307` appends against `item.version`), so the earlier appends don't affect it.
4. **"A retry appends only what it newly writes" means: what this wait's fold does not already have.** Before the first step, compute `splitProgressOf(events, …)` from the events already read at `:130`, and skip any `SplitChildWritten`/`SplitLinkWritten` whose key or link it already lists. If a previous call wrote a child to GitHub and died before appending, the retry adopts that child and *does* append it. That is how the log catches up to GitHub.
5. **Reconciliation still reads GitHub, never the log.** `:150` says *"What GitHub already has, never what the log says"*, and that rule stays. The progress events are a record for the page. A retry must not trust them to skip a write: a person can edit sub-issues after the fact, which is the same reason `ticket.ts:130` gives for `TicketSplit` being the only list a close rule may read.
6. **Every non-ok outcome after `SplitStarted` appends `SplitFailed`.** That includes:
   - the `{ detail }` branch from `end the wait` (`:351`);
   - the catch (`:362`).

   This is the one thing the fold cannot recover from. If a failure leaves no terminal event and the instance still matches, the fold says *writing* until the board restarts. Put the append in one place on the way out, not in each branch. If the `SplitFailed` append itself throws, let it propagate; the page reading *writing* until restart is the accepted cost.
7. **`TicketSplit` stays inside `resolveWaitHolding`'s transaction with `WaitResolved`** (`resolve-wait.ts:309-313`). It is the "done" terminal, and nothing about it changes.

### The fold

`splitProgressOf(events, { waitId, instance })` returns either:

- `{ state: 'idle' }`, or
- `{ state: 'writing' | 'interrupted' | 'failed' | 'done', plan, children: SplitChild[], links: Dependency[], failed?: { step, detail } }`.

**It takes `waitId` as well as the `instance` the ticket names.** Without it, a parent whose earlier split finished and which is now waiting again would read *done* for the new wait. #603's page always knows which wait it is drawing.

How the state is chosen, looking only at events with this `waitId`:

- **idle**: there is no `SplitStarted`.
- **done**: there is a `TicketSplit`. Check this first, whatever else is on the stream.
- **For the rest, take the latest `SplitStarted`:**
  - **failed**: a `SplitFailed` comes after it.
  - **writing**: no `SplitFailed` comes after it and its `instance === options.instance`.
  - **interrupted**: no `SplitFailed` comes after it and its `instance` is different.

**Interrupted is never written**, as the ticket says. It is the same reading triage makes of an unfinished attempt (`read-model.ts:101-120`).

What the fold returns alongside the state:

- `children` and `links` are the union over **every** attempt for this wait, de-duplicated by key and by link. A failed first attempt's children are still on GitHub, and the page has to show them.
- `plan` comes from the latest `SplitStarted`.

Order by stream position, never by `at`.

### Tests (unit half only)

- **`packages/domain/unit/`**:
  - schema accept/reject for the four events;
  - the five states;
  - a two-attempt stream where the first attempt failed after one child, the second is interrupted, and the union holds both attempts' writes;
  - a different `waitId`'s events being ignored.
- **`packages/conductor/unit/split-ticket.test.ts`** already drives the writer against a memory store. Add:
  - a full run appends, in order: `SplitStarted`, children, links, `TicketSplit`, `WaitResolved`;
  - a failure on `chain` appends `SplitFailed{step:'chain …'}`;
  - a retry after that appends a fresh `SplitStarted` and only the missing link, not the children again;
  - a refusal before writing appends nothing;
  - a child adopted with no prior event gets its `SplitChildWritten`.
