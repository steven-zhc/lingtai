The Loop and the Log

Four names get used as if they were four programs. They are not. This page draws what actually runs, what writes to the log, and who finds out when it changes. Everything on it is drawn from code that exists.

Conductor is not a process. It is the code for one pass of the loop — discover, claim, worktree, agent, gates, integrate. It runs inside whatever process calls it.

Daemon and CLI are processes, and since 0022 they differ by less than they used to. Both call the conductor, and both hold a projector for as long as they run. What the daemon adds is a lock, a heartbeat, a repair at startup and a loop that keeps taking work.

Thirteen packages, and the arrow that points left

The left column decides things. The right column touches something outside the process. No package on the left names one on the right.

The two names that get confused, kept apart on purpose

@lingtai/env holds the machine's environment: the two connection strings, the App key, the state directory. @lingtai/agent-env holds the agent's: the layers, the filter, the file that gets planted in a worktree. They lived in one file until 0024, and that adjacency is the shape by which a machine credential reaches a subprocess. The names now say whose environment each one is, which is the distinction that matters and the one that was invisible while they shared a file.

Two hosts, one rule

Every process that appends holds a projector for as long as it runs. That rule is what removed the difference people kept being surprised by.

What each of the daemon's standing jobs is for

The useful half of each definition is the second one: what you see when it is not running.

  • conductor pass Ask GitHub what is runnable for each registered project, take one item, and run it to a verdict. One pass handles one item, or none. Without it: nothing is worked. This is the one job lingtai run also does.
  • projector Reads events as they land and advances task_view — the one projection, and the table the board renders. It is a reader; it never writes to the log. Without it: the log is perfectly correct and every screen is frozen at whatever it last saw. Held by every process that appends, which is why this is no longer a difference between the two hosts.
  • work loop Wakes on an append rather than on a timer, asks the log whether it is paused, and runs a pass. Pause is an event, so a pause issued while the daemon is down is waiting when it comes back. Without it — --no-conduct — you get a daemon that keeps the board current and takes no work, which is what to run beside a pass already in flight.
  • heartbeat Writes daemon_status every few seconds; anything older than fifteen reads as stale. Deliberately outside the log, and the only mutable operational state in the system. Because the log cannot answer “is anything alive?”. A dead daemon appends nothing — and so does an idle one. Absence of events is not absence of a daemon, so liveness needs a store that gets written even when nothing happens.
  • reconcile, at startup Four comparisons between what the log says and what the world has: the projection is caught up, no worktree is orphaned, no claim is held by a conductor that no longer exists, and GitHub says what the log says. Each one no-ops without its own input rather than guessing at a global scan. It appends the repair rather than quietly tidying, because a system that silently cleans up after itself cannot tell you it has been crashing — the disk gets cleaner, the symptom disappears, and something kills the daemon nightly for six weeks before it surfaces as something else. Only the daemon runs it: the pass releases claims other runs hold, and a one-shot command somebody is watching should not have that effect on work it was not asked about.
  • the lock A session-level Postgres advisory lock, lingtai:daemon. A second daemon does not start; it says who holds it and exits 0. Without it: two daemons take the same work. The claim would catch most of it, but the merge lane and the worktree directory would not.

Who changes state

Four writers, one table, one projection — and GitHub on both sides of the loop, as an input and as an output, never as a store of what Lingtai did.

  • Only the conductor writes about work. Claims, gate verdicts, integrations, landings. Nothing else may.
  • The board writes too. Approve, reject and waive are appends. The board is not read-only — it is where a person's decision enters the log.
  • The agent writes through the hook. A thin binary on a unix socket; the conductor appends on its behalf, with the run id as the actor.
  • Projections never write to the log. They read it and maintain their own table. A projection that appended would be a second author of history.
  • There is one projection. task_view. A list of one was a list whose only job was to let a projection be written and silently left out of it — no table, no checkpoint, no failing check. A second one is added in the open, by name, or it does not exist.

Who tells whom

There is exactly one notification channel, and it is fired by the database, not by any of the processes.

One work item, end to end

The five gate points are fixed and closed. What runs at each is the managed repository's recipe; what gets appended is Lingtai's.

Found 2026-09-03 · the shape this system names as its own bug

Lingtai's own recipe puts a human: action at merge — every merge was supposed to wait for a person. It never ran. Two changes to main merged with no approval, five seconds after their build gate passed.

The point was declared, printed by lingtai add, recorded in GatesResolved and rendered on the board. All of that reads as evidence that it works. Configured and did not run is the failure this system names as its own bug, and this is the most expensive instance of it so far.

The point builds a pipeline like every other now (run-once.ts, step 11), and gate-audit.ts makes the same comparison for every gating point: an item that landed, whose GatesResolved planned actions at a point, and whose run recorded no verdict there. That check is the part that generalises — the fix closes one instance, the comparison closes the class. The landings from before the fix are still on the log, so lingtai doctor still names them, which is the correct behaviour for a record that cannot be edited.

The same shape has now been found six times: a check present, reported, and not looking at the thing you think it is. It is worth reading this page for that pattern rather than for the individual bugs.

Telling GitHub: convergence, not replay

The outbox is gone — a table, a projection, a worker, a backoff and a dead-letter standing behind three calls. What replaced it is smaller and stronger, and the difference is that it computes the target instead of remembering the attempt.

What the agent is given

Two files, merged, filtered by the recipe, planted in the worktree at 0600. The shell the conductor happens to be running in is not a layer.

LayerWhereHoldsReaches the agent
machine file~/.lingtai/env/<project>.envwhat this machine can supply to that projectyes — unless it is Lingtai's own
project filethe workspace .env.local, then .envwhat the repository itself declaresyes
the conductor's shellprocess.envwhatever you happened to exportno — not a layer, by decision
  • The recipe decides; the machine only holds. env.allow and env.deny are the filters and env.required is a check — a declared name with no value refuses the whole project before anything is claimed, which is to say before the money.
  • A LINGTAI_ name never crosses, from the machine file. That prefix is the machine's own namespace. No managed application asks for such a name, so a project whose file is missing a line gets an absent value — which required refuses loudly — instead of silently inheriting Lingtai's.
  • A project keeps its own names. DATABASE_URL in a project's file is that project's database and passes through untouched. LINGTAI_DATABASE_URL is this system's own log, and an agent is never given it.
  • The list is not hardcoded any more. A RESERVED constant used to decide this. It was deleted with #60: a guard nobody could see from the recipe is a guard nobody can audit from the repository it protects.

The rule that explains the rest

Two questions look alike and are not: what work exists and what Lingtai did about it. GitHub answers the first and is the authority on it — that is why discovery reads labels and stores nothing, and why an issue GitHub stops offering simply stops being runnable. The log answers the second, and nothing else may.

Every bug this page records is a place where that boundary was crossed without saying so: a queue written into a projection with no event behind it, a command that skipped the refresh its long-running twin performed, a gate point declared in one repository and executed in neither, an outbox that remembered attempts because nobody had noticed the target was computable.

And the reading rule that follows from it: behavioural claims are settled by reading events, not by reasoning about the code. A finding that cites a seq number is worth more than one that argues.

What is still open

Marked in indigo, which on this page means true today and not yet fixed — as against red, which marks something that was found by running the system.

Named, so that it is a fact rather than a discovery

Two interfaces are still promises, on purpose. 0025 took runOnce, the ports and the adapters to Effect: the worktree, the hook socket and the agent process are each a Scope, and the catch-all that held “every exit appends” is a named defect handler with a test behind it. What it did not convert is Runtime, because actions consumes it and 0023 keeps that package plain, and GitHubClient, because the board, the daemon and four commands use it. Each is its own ticket, and worth doing only if something asks for it.

admit runs nothing. It is one of the five points, resolved into GatesResolved and drawn on the board, and no pipeline is built for it. That is the same sentence as #58's, which is why gate-audit includes it rather than excepting it.

seq is not gapless. A Postgres sequence claims a value when the INSERT runs and publishes it when the transaction commits, so under concurrent writers a subscriber can see seq 6 while 5 is still in flight, and a checkpoint advanced to 6 skips 5 forever. It cannot bite while the conductor is the single writer. #4 has to solve it rather than assume it away.

Forward compatibility stops at the store. The reducers ignore an event type they do not know, so an older projection survives a newer conductor. The store does not — it throws on read, so in practice it refuses the event first. Deliberate for now, but it means the tolerance is only real once the two agree.

tier: sandboxed is not built. Containerising the whole toolchain is its own piece of work; guarded is what the first project runs at.
