The Loop and the Log

Four names get used as if they were four programs. They are not. This page draws what actually runs, what writes to the log, and who finds out when it changes. The last section is a proposal, and says so.

Conductor is not a process. It is the code for one pass of the loop — discover, claim, worktree, agent, gates, integrate. It runs inside whatever process calls it.

Daemon and CLI are processes. Both call the conductor. The daemon does four more things around it, and every difference in behaviour anyone has been surprised by today lives in that gap.

One library, two hosts

The daemon is not “the conductor running”. It is the conductor plus the four standing jobs that keep the rest of the system current.

What each of those jobs is for

The useful half of each definition is the second one: what you see when it is not running. Most of them have been missing at some point today.

  • conductor pass Ask GitHub what is runnable for each registered project, take one item, and run it to a verdict. One pass handles one item, or none. Without it: nothing is worked. This is the only one of the five that lingtai run also does.
  • projection follower Reads events as they land and advances task_view and outbox — the tables the board renders and the GitHub deliveries are built from. It is a reader; it never writes to the log. Without it: the log is perfectly correct and every screen is frozen at whatever it last saw. This is what left the board blank through nine runs — the fix at the time was starting a second process, lingtai daemon --no-conduct.
  • outbox deliverer Takes the rows the outbox projection wrote and actually calls GitHub: set the labels, post the comment, close the issue. Retries with backoff; after six attempts a row is dead and doctor fails on it by name. Without it: decisions never leave the machine. The merge happens, the log is right, and on GitHub the issue sits open and unlabelled as though nothing touched it.
  • heartbeat Writes daemon_status every five seconds; anything older than fifteen reads as stale. Deliberately outside the log. Because the log cannot answer “is anything alive?”. A dead daemon appends nothing — and so does an idle one. Absence of events is not absence of a daemon, so liveness needs a store that gets written even when nothing happens.
  • reconcile At startup, compares the machine against the log and records what diverged. A daemon killed mid-run leaves a worktree behind holding a branch checked out, which stops git updating that ref on the next attempt. The claim expires on its own; the directory does not. It appends the removal rather than quietly tidying, because a system that silently cleans up after itself cannot tell you it has been crashing — the disk gets cleaner, the symptom disappears, and something kills the daemon nightly for six weeks before it surfaces as something else.
  • the lock A session-level Postgres advisory lock, lingtai:daemon. A second daemon does not start; it says who holds it. Without it: two daemons take the same work. The claim would catch most of it, but the merge lane and the worktree directory would not.

Who changes state

Four writers, one table, and one exception that explains a whole class of surprises.

  • Only the conductor writes about work. Claims, gate verdicts, integrations, landings. Nothing else may.
  • The board writes too. Approve, reject and waive are appends. The board is not read-only — it is where a person's decision enters the log.
  • The agent writes through the hook. A thin binary on a unix socket; the conductor appends on its behalf, with the run id as the actor.
  • Projections never write to the log. They read it and maintain their own tables. A projection that appended would be a second author of history.

Who tells whom

There is exactly one notification channel, and it is fired by the database, not by any of the processes.

One work item, end to end

The five gate points are fixed and closed. What runs at each is the managed repository's recipe; what gets appended is Lingtai's.

Found 2026-09-03 · fixed 2026-09-04 (#58)

Lingtai's own recipe puts a human: action at merge — every merge was supposed to wait for a person. It never ran. Two changes to main merged with no approval, five seconds after their build gate passed.

The point was declared, printed by lingtai add, recorded in GatesResolved and rendered on the board. All of that reads as evidence that it works. Configured and did not run is the failure this system names as its own bug, and this is the most expensive instance of it so far.

The point now builds a pipeline like every other, and lingtai doctor makes the same comparison for every gating point that #55 asked for at end: an item that landed, whose GatesResolved planned actions at a point, and whose run recorded no verdict there. That check is the part that generalises — the fix closes one instance, the comparison closes the class.

The rule that explains the rest

Two questions look alike and are not: what work exists and what Lingtai did about it. GitHub answers the first and is the authority on it — that is why the queue is a cache and not a stream of events, and why a queued row that GitHub stops listing is simply dropped. The log answers the second, and nothing else may.

Every confusion on this page is a place where that boundary is crossed without saying so: a queue write that reaches no one, a command that skips the refresh its long-running twin performs, a gate point that is declared in one repository and executed in neither.

Proposed — eleven packages, and four deletions

Everything above is drawn from code that exists. This is not: a proposal, dated 2026-09-04 and under review. Nothing in it is built.

A proposal · not the system

The module names below came from outside the code, as a guess at what Lingtai ought to be made of. Most of them already exist under other names — but the boundaries are wrong in four places, and four whole mechanisms turn out not to be needed at all. The deletions are the larger half of this proposal.

An earlier draft of this section invented two names of its own, effects and ports, and kept the outbox. Both inventions are gone. A proposal that has to teach you its own vocabulary before it can be read has already failed at the thing it is arguing for.

The diagnosis: the last piece always lives in an application

What it already cost

The board runs git. apps/board/src/app/actions.ts imports git and stateDir from @lingtai/conductor/worktree — a page reaching into the orchestrator for a shell helper, because that is the only place one lives.

Two gaps stack on one another. #58 merged this morning. Its close has not been computed yet, because nothing advanced the projection after approve — and even once it is, nothing would deliver it, because the deliverer is reachable from two entry points out of five.

Which projections exist is decided in the CLI. The daemon is handed them — startDaemon({ projections: Object.values(PROJECTIONS) }) — so “why is the board stale” has a different answer depending on which entry point you came through (#64). Worse: a projection written and never added to that list has no table, no checkpoint, and no failing check. It is indistinguishable from one that does not exist.

What goes away

Four deletions

All four have landed, and so has the renaming — the outbox on 2026-09-03 (442f513), the queue cache, the catch-up-on-exit and the projection list on 2026-09-04, and the four renames and the store split on 2026-09-07. Sections 1–6 above describe the system as it stood before all of that, and still draw the outbox, the queue and the old package names. The extraction landed on 2026-09-07 too, so the whole of 0022 is now built and these figures are the last thing owing to it.

conductor calls github and appends the outcome. What did not land, reconcile converges.

Every host that appends holds a projector while it runs. One behaviour, not two.

the projection list — PROJECTIONS
One projection is left. A list of one is not a list.

The outbox deletion is the one with loose ends, so here they are. Two things inside it are not scaffolding and have to land somewhere. The first is labelsFor — twenty lines that turn a work item’s state into the labels its issue should carry: lingtai:working while the machine has it, lingtai:waiting while you do, nothing otherwise. That is the whole definition of what GitHub ought to look like, which is exactly what reconcile needs to converge against, and it is pure. It belongs in conductor, beside the other judgements about a work item. The impure half stays on the right: taking the union with whatever labels somebody else put on the issue needs GitHub’s current state, so it lives in github. The second is the pair of events that replaces OutboxDelivered and OutboxFailed: IssueUpdated { project, issue, change, detail } and IssueUpdateFailed { project, issue, change, error }, with change one of comment, labels, closed. The noun is the issue rather than the queue, because the queue is about to stop existing and an event name should not carry an implementation detail. The failure event survives the deletion of every retry — the old loop called gh inline and a failed call left nothing at all, so afterwards you could not tell “we never commented” from “we commented and it did not help”. Keep the record; drop the machine.

The queue deletion is the one worth arguing about, so here is the argument. conductorPass already asks GitHub for the runnable set at the top of every pass and then reads it straight back out of the table — the cache is a holding place inside one pass. The only consumer that benefits from its persistence is the board's Queued column, which renders on the server anyway. And because it is stored, two entry points came to disagree about whether to refresh it first: that is #57. Take the cache away and there is nothing left to disagree about. If a rate limit ever makes this hurt, a cache can come back — with a reason, and with someone watching it.

The proposal

Eleven packages, one boundary. Decisions above the line, everything that touches the world below it. Eight of the eleven names already exist in some form; three are new or extracted, and each of the three is what is left over when something stopped being a decision. Two of today’s packages are not in the table: @lingtai/runtime folds into agent, which is the whole of “start it, hear it”; and @lingtai/hook stays exactly as it is — a compiled binary planted in the worktree, not a library, with agent as the end that talks to it.

The wiring is not hand-rolled. A package declaring an interface and a host handing it an implementation is dependency injection, and passing objects as parameters is how it works today — runOnce already takes client, runtime, token and store. That works for values and it does not work for lifetimes: something has to guarantee that a projector opened for a run is closed when the run ends, on every path including the early refusals. Nothing does today, which is why a leaked follower would hold a session connection and keep the process alive forever. Effect — the TypeScript library — is proposed for exactly that seam: Context.Tag names a port, Layer provides one, and Scope ties an acquired resource to a lifetime, so release is structural rather than remembered. The test at the bottom of this page is what a Layer is for: swap the live one for a fake and the same conductor runs with no database. The cost is real, and it is specific to this project. design.md §8 refuses ceremony until a failure demands it, and a framework adopted up front is the shape that list guards against; Effect is also viral, in that once conductor returns an Effect so does everything calling it. And this repository is written by an agent, so a steep idiom is paid for again on every run. So: at the seam, not everywhere. domain, recipe and actions stay plain functions that Effect code calls; the ports and conductor are Effect; the hosts call runPromise at the edge. That is a decision that deserves its own ADR rather than a line in a proposal.

The order

  • Delete the outbox. The largest net subtraction in the proposal, and it is subtraction rather than a move. It also leaves projector with exactly one target table.
  • Delete the queue cache. #56 and #57 are both cache-invalidation bugs. They go with the cache.
  • One behaviour, both hosts. Every process that appends holds a projector for as long as it runs — the daemon already does, and lingtai run starts to. This deletes the catch-up-on-exit special case rather than adding a second mechanism beside it, and it is what closes #64: an event drives the projector, whichever process is holding it. Two projectors on one log is now the normal case, and it is safe by construction — apply is idempotent and the checkpoint advances inside the same transaction as its writes, so the second one finds nothing left to do. That was already true; it stops being an edge case and becomes the design. The board is the one host this rule does not reach — its writes are request-scoped, so it appends and then depends on a daemon. That is acceptable only if it says so, and today it does not: the live chip reports whether the SSE socket is open, which is precisely this morning's lie — chip live, board frozen. It should report the projection's lag and the heartbeat instead: behind 7, or no daemon. Latency is fine once it is visible.
  • Rename and split. store → event-store + projector; env → agent-env + secrets; config → recipe; gates → actions; core → domain. Mechanical, and cheapest while nothing else is moving.
  • Extract repo and agent. The big one. conductor declares the interfaces it needs and the two packages implement them. By injection, not by moving files.
  • Widen reconcile. Startup brings four things into agreement: the projection caught up, worktrees cleaned, expired claims returned, GitHub converged on what the log says.

The test that decides whether this happened

Can conductor run a whole pass with a fake repo, a fake agent, a fake event-store and no database — producing the events it wants appended and the calls it wants made, for a test to assert?

Today it cannot, and the recipe says so out loud: the suite refuses to start without TEST_DATABASE_URL because every test appends real events. There are 23 appends across six files in that one package. If the answer is still no when the move is finished, the move did not happen — whatever the directory listing says.
