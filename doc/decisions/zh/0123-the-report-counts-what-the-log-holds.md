# 0123 — 报表：每张票统计什么、平均什么、来回最多的票怎么解释

> 中文版，供阅读。以英文原文 [0123](../0123-the-report-counts-what-the-log-holds.md) 为准，两者不一致时按英文。

**状态** 已采纳 · 2026-10-28

报表针对一个时间窗口和一个项目，说明流水线解决了多少张票。对每张已合并的票，它说明这张票跑了几遍、几轮修复、等了几次人、机器干了多久、花了多少钱。它还列出来回最多的几张票，以及每张票的钱花在了哪里。每个数字都来自日志里已有的事件，由一个 projection（`ticket_report`）折叠成每张票一行，报表页面只做聚合。不为报表写任何新事件。等人的时间不计入。这些票怎么解释，由已记录的事实拼出来，不花钱。至于从一张票里总结出什么教训，是另一个可选的步骤：`end:` 上的一个 agent plugin，在它自己的 ADR 里决定。

**用词。**
- **票**：一条 `ticket-<project>-<n>` 事件流。
- **一遍（pass）**：对它的一次领取，不管是谁触发的：队列、重启、requeue，还是批给的一轮修复。
- **继续执行**：人 approve 之后，被挂起的运行接着跑。它不是一次领取（0109 §5）：写的是 `TicketContinued`；在那之前写入的日志里，是同一条流上 runId 已经被领取过的 `TicketClaimed`。
- **一轮修复（fix round）**：为回应一次拒绝而付费跑的一次。
- **一次等待（wait）**：票的事件流上的一个 `WaitStarted`。
- **窗口**：报表覆盖的时间段。

## 背景

`/spend` 只汇总看板上正显示的卡片（`apps/board/src/app/spend/page.tsx` 写着它是 *"the same window as the board"*）。它没有按票的视图，没有时间，也不统计跑了几遍、几轮。无人值守跑了一夜之后，操作者想问的几个问题都没有地方回答：做完了多少，一张票合并要花多少，为什么某张票比另一张贵十倍。而这些事实都已经记录下来了：

- 票的事件流上有 `TicketClaimed`、`TicketLanded`、`TicketClosed`、`TicketReleased`、`WaitStarted`、`WaitResolved` 和 `WaitTriaged`；
- `RunSpent` 带着用途（`SpentFor`，0110 §9）和轮次，由 `spend` 投影（`packages/projector/src/spend.ts`）关联到票。

这里的输入是操作者在 epic #648 里做的决定。

## 决定

1. **统计单位是票，用结果决定它落在哪个窗口。** 票的**结果**有三种：
   - *已合并*：它最后一个 `TicketLanded`；
   - *已关闭*：有 `TicketClosed`，且最后一次领取之后没有合并；
   - *未完成*。

   已合并或已关闭的票，结果事件落在哪个窗口，就属于哪个窗口。未完成的票，只要有任何一遍落在某个窗口里，就属于那个窗口，并且不进平均数，单独列出。窗口有三种：**今天**、**最近 7 天**、读者自选的**日期段**（选最早到最晚，就是「库里的全部」）。任何窗口都可以再按项目、按**票的类型**过滤（recipe 的 `source.kinds`：`bug`、`tech-debt`、`feature`、`documentation`）。报表按日志现状来读；被重置过的库，内容自然就少一些。

2. **每张票统计以下几项，而且只从这些事件里读：**

   | 事实 | 从哪里读 |
   | --- | --- |
   | 遍数 | 票的事件流上的领取，按 0109 §5 的规则排除继续执行 |
   | 修复轮数 | 这张票的 `RunSpent` 事件中，`for` 为 `Action` 且 `round ≥ 1` 的不同 `(pass, round)` 组合数（0110 §10），**这张票所有遍加在一起** |
   | review | 这张票各个 pass 流上每次 review 的 `StepEnded`（`outcome.step` 为 `review`），带上它的 `round`、时间，以及严重程度为 `blocker` 或 `major` 的意见条数；一条都没有的 review 算通过 |
   | 等待 | 票的事件流上的 `WaitStarted`，每次带上原因标签、最近一次 `WaitTriaged` 给出的原因（如果有），以及 `WaitResolved` 的处理方式 |
   | 机器时间 | 每次领取、每次继续执行各算一段：从它开始，到「它之后第一个 `TicketLanded`、`WaitStarted`、`TicketReleased` 或 `TicketClosed`」和「它最后一次有动静的时候」（见下）两者中较早的那个为止，各段相加。approve 本身不开始计时；之后的继续执行单独开一段 |
   | 花费 | 这张票的 `RunSpent` 事件，按用途拆开：Work、Answering、Judge、Triage、Discussion（`apps/board/src/lib/spend.ts:30`） |
   | 未知 | 这张票的 `RunSpent` 事件里，既没有上报金额也无法按价格估算的条数；再加上每一次领取，如果一条 `Action` 的 `RunSpent` 都没有，就算一条。一次领取就是一个 `runId`（0109 §5），所以这就是看板的规则（`withNoSpendFallback`，`apps/board/src/lib/spend.ts:113`），继续执行不会多算 |

   **机器时间不包括等人的时间。** triage 或 discussion 是在票等待期间跑的，所以它们的钱要算，时间不算。只有领取、没有结束事件的一遍（正在跑的，或者 conductor 在追加结束事件之前就死掉的）不计时间，报表会说明跳过了几遍，以及有几段因为区间内没有自己的事件而计为 0。

   **票的类型取最后一次领取的 `kind`。** 继续执行不带类型（0109 §5），所以不会把类型清空。两遍之间改了标签，这张票就算作最新的类型。所有领取的类型都为空的票，归为「未分类」，在类型筛选和按类型的表里单独作为一项，不丢弃。

   **每一段都只计到它最后一次有动静的时候，所以崩溃不会多算几个小时。** conductor 死掉后，领取还挂着，要等下一个 conductor 启动时才补写 `TicketReleased`（`packages/conductor/src/claim.ts:20-23`、`packages/daemon/src/reconcile.ts:664`），夜里崩溃的话就是几个小时之后。这种释放和普通的释放区分不开：两者都是 `actor: conductor`、`cause: null`，只有原因的文字不同，而 0120 禁止解析原因文字。所以不单独识别哪种释放。一段的「最后一次有动静」，是指按日志顺序（`seq`），在它的开始事件和结束事件之间，这一遍自己 `pass-…` 流上的事件，或者集成通道上点名这张票的事件（`IntegrationAttempted` 及其结果都带 `ticketId`）里，最后的那一个，这样合并本身的耗时也算在内。崩溃时，这就是死掉的进程最后做的事；正常的一遍里，它只比结束事件早几秒。区间里没有这样的事件，这一段就计 0，并算作不完整的区间。这是日志能验证的下限，也不需要识别任何事件。

   **修复轮数按票累加，跨所有遍。** 一张票跑了三遍、每遍四轮，就是十二轮，不是四轮。只按单遍计，恰好会把最贵的那些票藏起来（#658：4 遍共 14 轮）。

   **修复轮数从 `RunSpent` 数，不从路由事件数，而且是下限。** `PassRouted` 里 `fix-lines` 的决定，会漏掉人批给的轮、base 合并之后的轮，以及 build 红了时系统自动安排的轮：2026-10-28 时，日志里按 `RunSpent` 数有 347 轮，按 `fix-lines` 数只有 288 轮。进程在返回之前就被杀掉的那一轮，没有 `RunSpent`（0110 §2），所以不计入，它的花费也同样不计入；修复轮数和花费合计一样，都是「至少」。

3. **总览只对已合并的票求平均。** 对所选的窗口和项目，它显示：
   - 已合并、已关闭、未完成的数量；
   - 对已合并的票，遍数、修复轮数、等待次数、机器时间和花费的平均数**和**中位数；
   - 对已合并的票，**0 或 1 轮修复**就合并的占比，以及需要 **5 轮或以上**的占比。后者是收敛的衡量指标（#669）：2026-10-27 时，167 张已合并的票里这个比例是 10%，而中位数已经是 1；
   - **经过 k 次 review 之后，还没通过的票占比**：对第一次 review 落在窗口里的票，算出经过 1、2、3……次 review 之后还没通过的比例。一张票的所有 review 按时间顺序计数，跨所有遍。没有通过就停下的票（靠人 approve 合并的、关闭的、还没完成的），在它最后一次 review 之后退出计数，既不算通过也不算失败（Kaplan-Meier 估计）。收敛的 review，曲线降得快，最后接近 0；曲线停在高处变平，就是不收敛。2026-10-28 时，174 张票里：1 次 review 后 54% 没过，2 次后 33%，3 次后 27%，4 次后 19%，5 次后 12%，7 次后 9%，也就是大约十张票里有一张，在它得到的 review 里始终没有通过；
   - **窗口内的花费：运行时间落在窗口里的每一次运行**，不管它的票结果如何，按运行日期从 `spend` 读，和每天花费图同一口径，所以这张卡片的数字等于图上各天之和。类型筛选按 `spend` 折叠每次运行时记下的类型来筛（0110 §11）：两遍之间改过标签的票，它的花费会分到前后两个类型里，这种情况很少，接受。花在最终没合并的工作上的钱也在里面，这是操作者最需要知道的数字，而只对合并的票求平均会把它藏起来。一张票自己的花费（平均值、第 4 条里的那一行）是另一个数字：这张票全部的花费，不管落在哪几天。两者都用各自的标签说明；
   - **按类型**：合并张数、中位修复轮数、0–1 轮占比、≥5 轮占比、每张已合并票的平均花费，来自 `ticket_report`；以及窗口内的花费，来自 `spend`，按它给每次运行记下的类型。不同类型收敛得不一样：2026-10-27 时，已合并的 `feature` 有 15% 需要 5 轮以上，`tech-debt` 是 0%；
   - 每个金额旁边都标出未知行数，绝不把未知当成零算进去（0110 §5，0122 §5）。有价格表时（#645），没有上报金额的行按价格估算，并标为估算，不当作上报金额。

4. **来回最多的票用机械的方式解释。** 窗口内修复轮数最多的八张票（任何结果都算），轮数相同时按花费排；读者也可以把同一份列表改成按花费排。每张列出：
   - 花费，以及各用途所占的比例；
   - 遍数、修复轮数和等待次数；
   - 每次等待的原因、triage 判断的原因，以及最后怎么处理的；
   - 一句用这些事实拼出来的话，从占比最大的一项说起：*72% 花在回应拒绝上，共 6 轮修复 · 3 遍 · 等待 3 次（FixableLines ×2，ConflictingHunks）。*

   这句话是用上面那张表填出来的模板。不经过模型，里面没有一句话是旁边的事实核对不了的。

5. **总结教训不归报表管。** 数字是对日志的折叠；判断能从一张票学到什么，是要花钱的工作。这件工作是 `end:` 上一个可选的 agent plugin（*retro*，复盘），recipe 不声明就不启用。它读一张已合并票的记录，写下观察。它的设计（写什么、写到哪里、多张票的观察怎么汇总）另写一份 ADR，和长期盯路线图的 agent 一起讨论。报表本身不花钱，也从不启动 agent。

6. **一个 projection，两个界面。** `ticket_report` 是和 `task_view`、`finding_backlog`、`spend` 并列的一个 projection：每张票一行，存放第 2 条的事实（结果及其时间、遍数、修复轮数、各次 review 的轮次、时间和阻断意见数、各次等待的原因和处理方式、机器时间、按用途拆分的花费、未知行数，以及每一遍的时间，好让窗口能把未完成的票放对位置）。它只是一个折叠，由每个写日志的进程本来就带着的 projector 保持最新（0022），修正它的唯一方式是 `lingtai projection rebuild ticket_report`。**它自己从日志折叠，从不读别的 projection 的表**，理由和 `spend` 一样（`spend.ts:22-24`）：每个 projection 停在自己的 checkpoint 上。所以它直接折叠 `RunSpent`，用和 `spend` 相同的规则关联到票（pass 流的领取、票自己的流、discussion 的请求），两者可以分别重建。**按 0110 §5 的允许，钱存进表里**：每张票、每种用途存三列：上报的 `costUsd` 合计、估算合计（在这个折叠里按每次运行当天的价格估）、两者都没有的运行条数，三列绝不相加成一列。**「哪天花了多少」归 `spend`，「每张票花了多少」归这张表**：窗口花费卡片和每天花费图按每次运行的时间和它记下的类型读 `spend`；平均值、按类型的每张票数字和第 4 条读这张表。某个模型第一次有了价格时（#678 会用这第一个价格估之前的运行），两个 projection 都重建，按 0110 §5 的规定。**同一天第二次抓取可能替换当天的价格**（`mergeSnapshot`，`packages/domain/src/rate-card.ts:231`），这只会在「上游当天调价、conductor 又在同一天重启」时发生。已经折叠的行保留之前的估价，重建则会用后来的价格。这一点接受：估算不是账单，为它全部重建不值得。看板的 `/report` 页面和 `lingtai report` 对所选窗口和项目的行做聚合（「哪天花了多少」聚合的是 `spend` 的行）；聚合、第 3 条的数字和第 4 条的那句话，是两者都调用的同一个纯函数。CLI 命令只读，所以支持 `--json`（0121 §5）、`--window today|7d`、`--from <date> --to <date>`、`--kind <k>` 和 `--project <p>`，放在 *everyday* 帮助分组里（0121 §7）。`--window` 和 `--from`/`--to` 互斥：同时给出时拒绝执行，并点明这两个参数（0121）。

7. **页面。** 看板的 `/report` 用看板自己的外框和配色：顶栏、冷灰、青绿是唯一的强调色，不用琥珀色，因为琥珀色表示「有人在等你」。图表的系列色不用看板的任何状态色（琥珀、红、绿）。从上到下：
   - 筛选：窗口、日期、类型；
   - 指标卡片：合并（附关闭和未完成）、中位修复轮数、≥5 轮占比、0–1 轮占比、窗口内的花费（按运行日期，附未知条数）、中位机器时间；
   - 五个面板：修复轮数分布（0、1、2、3、4、5+，按类型叠加）；**reviews to pass**：经过 k 次 review 之后仍未通过的票占比，一条从 100% 往下走的阶梯线，分 1 到 6 级，再加一个 7+ 级，收纳所有 review 满 7 次及以上的票，还在计数中的票数显示在每一级的悬停里；每天合并（按类型叠加）；每天花费（按用途叠加，从 `spend` 按每次运行的日期算）；**为什么停下等人：每次等待的原因 × triage 的判断交叉表**（没有 triage 单独一列）；
   - 第 3 条的按类型表；
   - 第 4 条的列表，每张票链接到它的任务页。

   每张图都有悬停显示精确数字和图例；不用双纵轴的图。

## 后果

- 只对合并的票求平均，看不到没合并的票。所以窗口内的花费覆盖每一次运行，不管它的票结果如何，已关闭的票也和合并的票并列计数。
- requeue 和批给的一轮修复都会多出一遍；approve 之后的继续执行不算。*遍数*衡量的是流水线有多少次不得不重来或需要人帮忙，而不是它主动选择重启了多少次。
- 多一个 projection，就要在两种存储（Postgres 和 SQLite）上各多一张表、一个检查点和一个重建命令，而且折叠逻辑要和它读的事件保持同步。这是换来「报表页面不用每次都读整个日志」的代价。
- 改变某项事实的统计口径，就是改代码加一次重建，绝不手工迁移数据。
- 0121 §7 的 *everyday* 一行加上 `report`。

## 这里不决定的

- 两个窗口并排对比。
- 按模型拆分数字。
- 在轮数旁边加回滚次数作为护栏。Lingtai 目前不记录任何回滚，没有东西可数；以后有了再加。
- 第 5 条的 retro plugin：读什么、写什么、多张票的观察怎么变成一张共性问题表。

## 原型

[`0123/`](../0123/index.html) 里放着这份决定参照的页面原型，可以直接在浏览器里打开，唯一从外部加载的是字体。里面的数字是这台机器 2026-10-28 时的真实日志。原型只是示意，不扩展决定：原型和正文不一致时，以正文为准。特别是：原型把「第一次抓到价格之前」的运行按第一次的价格估价，这是 #678，还没实现；原型把一张票的全部花费算在它合并的那天，而 §6 规定每天花费按每次运行的日期从 `spend` 算；原型把 approve 之后的继续执行也算成了一遍；原型还把 Triage 和 Discussion 两种用途合成一个系列，好让图表只用四种颜色。
