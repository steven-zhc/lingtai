The Pass and the Worktree

A pass is what one claim buys: a branch, an agent, five gate points and a merge lane. This page draws where a refusal goes — and what 0039 changed about that. Everything on it is drawn from code that exists.

The worktree is the whole of a pass. Everything a refusal could be answered by — the branch, the build, the diff — is on disk while the pass runs. Effect.scoped moves out to enclose the merge lane, so that stays true until the pass ends, and a new run stops being the answer to anything except a run that ended.

Any refusal returns to the agent, carrying its own evidence. Findings, the build's output, the conflicting paths: three prompts differing in one argument, not three flows. A person is asked when runtime.limits.rounds is spent — and only then.

What one pass may spend

Three numbers in one block, because two of them already had to agree with a third kept somewhere else.

runtime:
  limits:
    turns: 150   # inside one agent run
    wall:  1h    # inside one agent run
    rounds: 2    # how many times a pass sends the agent back

round is the word the code already speaks — FixRequested.round, roundsSpent, round 1 of 2. It is not attempts, which already means two other things: budget.attempts is how much history a prompt carries, and an attempt on the board is a claim. Putting it beside turns and wall is the point rather than tidiness: what one pass may spend is then one block, (rounds + 1) × wall. On 2026-09-10 the drain told an operator it would wait at most one wall, which the fix loop had already made false — a sentence chasing a number kept elsewhere. Three numbers in one place cannot drift apart like that. repair.maxAttempts and repair.fix are what rounds now counts, and repair.on is rounds: 0.

What this replaced, and the constraint it had to solve first

What it was until 2026-09-11

Only a refused review returned to the agent. A red build walked on to the merge lane carrying a gate-failed verdict, and a conflict aborted the lane; both then reached decideRepair, which bought an agent for a new run — because the worktree was released before the integrator ran.

Which is to say the expensive path was never a decision about failures. It was an ordering between two scopes, and undoing that ordering is the whole of it. A pass is one loop in the code now, because it always was one in the drawing.

The constraint §1 had to solve first

run-once.ts:53 says the worktree is gone before the integrator runs, because the integrator is outside its scope, which is circular. The reason is 690 lines further down, at :736: the worktree holds agent/<n> checked out against the same mirror, and git refuses to update a ref some worktree has checked out. Keeping it alive through the merge is what made the first end-to-end run fail.

So §1 was never a boundary to move — it was that constraint to solve. The run's worktree is a detached checkout now, so no worktree holds the ref the lane must update, and worktree.test.ts pins the lane's own fetch against a live worktree rather than pinning the checkout. Nothing needed the branch to be checked out there: the push has always been HEAD:refs/heads/<branch>.
