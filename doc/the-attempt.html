How one ticket gets built

Lingtai takes one ticket at a time and walks it through ten steps. This page is what each step is, what you decide about it, and where a ticket goes when a step will not let it past.

The pipeline is fixed; what each step does is yours. The ten steps and their order never change — that is what makes the board, the log and this page describe one thing. What runs at each step is a plugin, and your recipe names it. Say nothing and you get the set Lingtai ships, which is a working pipeline.

One worktree is the whole of an attempt. A ticket gets a branch cut from your base, and everything after that — the install, the agent, the build, the review, the merge — happens in it. Nothing is thrown away and restarted because a step said no.

The ten steps

Read it downward. The four in brass are the steps that may say no; most of what does not simply pass arrives at proposed, which is the only step that decides what happens next — a prepared refusal and a check before the merge lane visit it too, same as the rest, though with no judge declared for either direction, nothing there is chosen and they still rest with you.

What you write

One file, on your machine, at ~/.lingtai/<project>/recipe.yml. Nothing is committed to the repository Lingtai works on.

steps:
  claim:
    - queue: { kinds: [bug, feature], backoff: 1h }
  admit:
    - worktree: { base: main }
  prepared:
    - run: pnpm install
      timeout: 10m
  implement:
    - agent: claude-code
      turns: 150            # inside one agent run
      wall:  1h             # inside one agent run
  build:
    - run: pnpm typecheck && pnpm test
  review:
    - agent: claude-code
runtime:
  limits:
    attempt: { refusalFixes: 3 }  # fix the refusal: how many times a refusal sends the agent back
    ticket:  { newAttempts: 1 }   # new attempt: how many times this ticket may be started over

A step is a list of plugins, and they run in the order you write them. What the step does with the results is the step's own business: at claim the first plugin that finds a ticket wins; at prepared every one of them has to pass. A step you leave out of the file simply has nothing at it — and is still drawn, so that nothing configured and silently skipped never look alike.

Some keys are not the plugin's — they are the bounds Lingtai puts on it. A run: plugin cannot ignore its timeout, because the runner enforces it rather than the plugin honouring it. refusalFixes and newAttempts work the same way: the system counts them, under runtime.limits, and no plugin can raise them. implement's brief asks the agent to commit each piece that works, so an interruption loses little, and a ticket too big for one run is split by the system once — its ## Done when is what the parent is checked against when the children close.

What an attempt can cost you

Each automatic path has a bound of its own, and the arithmetic is the implement runs they add up to.

Read it as arithmetic: an attempt is up to 1 + refusalFixes + conflictResolutions + stepRedos implement runs, and a ticket buys (newAttempts + 1) attempts and up to personAsks answers to a person — each run bounded by turns and wall. With the defaults that is (2 + 1) × 16 + 5 = 53 runs. lingtai add prints the whole sum, and the other steps' bounds beside it rather than added in.

What you are asked is bounded too: personAsks. A step that did not finish buys no fix — a rule redoes it whole from the head, up to stepRedos. Nor does a review finding on a line your diff never touched: it is recorded as a pre-existing minor, unless the reviewer says how the diff makes that code reachable. A review after a fix reviews what the fix changed and rechecks the earlier findings: a new finding outside the fix is recorded as a minor, and a recheck never is. implement ends in one of five outcomes — Implemented, AgentFailed, Disputed, AlreadyDone or Unclear — and an AlreadyDone that review checks ends the ticket satisfied.

A base that moved on your branch's files buys no fix either — if it merges in cleanly. Lingtai merges it in itself and runs build and review again, with the base's new changes in front of the reviewer — up to baseBranchMerges an attempt, then it waits for you. A base that changed the same lines incompatibly is a conflict instead, and is answered as one. A base that moved anywhere else lands after merge's verify. A red base is not the ticket's: it is passed over as base-red and continues from its saved head when the base is green.

A person's FixRefusal and RedoStep spend nothing automatic: one more agent run on saved work, with its own turns and wall limits (and a dollar limit where declared), and it raises none of the bounds above. A ticket too big for one run is split by the system, once — it is not a move offered to you.

When it stops and waits for you

One place to look, however it got there.

What puts a ticket there

A failure is answered in three layers, and you are the last. A rule answers what is mechanical or transient, free. A judge (within the bounds) or triage (where a wait would open) names a cause, and the system chooses the action and carries it out. A person is asked only for a limit (a bound is spent), an unclear requirement or a broken environment.

Mostly proposed decides to send a ticket to you. A prepared refusal and a check before the merge lane are no exception — both visit it too, and it is only because no judge is declared for either that they rest with you just the same — which is still what makes is this worth interrupting somebody over one decision rather than a habit scattered through the pipeline. A wait the system resolved itself is a line on the card, not a wait.

What it carries with it

What refused it and why, in the words the step used — the findings, the build's output, the paths that conflicted. You should never have to open a log to learn why a ticket is waiting.

And end still runs. Closing the ticket yourself is an outcome like any other, and the step that tidies up runs on every outcome rather than only on the happy one.

The ways forward

Fix the refusal (FixRefusal) is offered when there is a fixable refusal and the saved branch is still at its recorded commit: one more implement on the saved work, and the result runs through build, review and proposed again before merge. It waives no refusal and spends no automatic bound. A merge conflict is answered this way too: the run merges the new base in and resolves it, and the agent asks if the two sides contradict. Redo the step (RedoStep) runs the step that stopped again, whole, on the saved head. Start a new attempt requeues the ticket from the base; add to the ticket and start a new attempt writes into the body first. Both leave the saved work behind and neither spends nor refunds an automatic newAttempts. A missing or moved saved branch cannot continue the first two. Every move, by who makes it and what it spends, is in the glossary.
