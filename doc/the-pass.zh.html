一趟 pass 与工作树

一趟 pass 就是一次 claim 买到的东西：一个分支、一个 agent、五个 gate 点，外加一条合并道。这张图画的是一次拒绝去哪里，以及 0039 把它改成了什么。图上的一切都来自已经存在的代码。

工作树就是一趟 pass 的全部现场。回答一次拒绝所需要的一切 —— 分支、构建产物、那份 diff —— 在这趟 pass 跑着的时候都还在磁盘上。Effect.scoped 外扩到把合并道也包进去，于是这句话到这趟 pass 结束都成立，而开新的一趟 run 不再是任何问题的答案 —— 除了一趟真的结束了的 run。

任何拒绝都带着自己的证据回到 agent。findings、build 的输出、冲突的路径：三个 prompt 只差一个参数，不是三条流程。只有 runtime.limits.rounds 用尽，才去问人。

一趟 pass 最多花多少

三个数放在同一个块里，因为其中两个本来就得和另一个放在别处的数保持一致。

runtime:
  limits:
    turns: 150   # 一次 agent run 之内
    wall:  1h    # 一次 agent run 之内
    rounds: 2    # 一趟 pass 把 agent 打回去几次

round 是代码里已经在说的词 —— FixRequested.round、roundsSpent、round 1 of 2。不是 attempts，那个词已经有两个别的意思了：budget.attempts 是一个 prompt 带多少历史，看板上的一次 attempt 是一次 claim。把它摆在 turns 和 wall 旁边是目的本身，不是为了整齐：一趟 pass 最多花多少，从此就是一个块，(rounds + 1) × wall。2026-09-10 那天，排空提示告诉操作者最多等一个 wall —— 而修复循环早就让这句话不成立了，一句话在追一个存在别处的数。三个数在同一处，就没法这样各自漂移。repair.maxAttempts 和 repair.fix 就是 rounds 现在数的东西，repair.on 就是 rounds: 0。

它替换掉了什么，以及必须先解决的那个约束

2026-09-11 之前是这样

只有被拒的 review 会回到 agent。红的 build 会带着 gate-failed 的裁决继续走到合并道；冲突则让合并道 abort。两者随后都走到 decideRepair，由它买一个 agent 开新的一趟 run —— 因为工作树在 integrator 跑起来之前就被释放了。

也就是说，那条昂贵的路径从来不是一个关于失败的决定。它是两个作用域之间的一个次序，撤掉这个次序就是全部。现在代码里的一趟 pass 是一个循环 —— 它在图上本来就一直是。

§1 当初必须先解决的那个约束

run-once.ts:53 说：工作树在 integrator 跑起来之前就没了，因为 integrator 在它的作用域之外 —— 这是循环的。真正的理由在 690 行之后的 :736：这个工作树把 agent/<n> 检出在同一个 mirror 上，而 git 拒绝更新任何一个被某个工作树检出的 ref。让它活过合并这一步，正是第一次端到端运行失败的原因。

所以 §1 从来不是搬一条边界，而是解决那个约束。现在 run 的工作树是 detached 检出，没有任何工作树占着合并道要更新的那个 ref；worktree.test.ts 钉的是合并道自己那句 fetch 对着一个活着的工作树，而不是钉检出方式。本来也没有谁需要那个分支被检出在这里：push 一直都是 HEAD:refs/heads/<branch>。

2026-09-11 在 cb66466 绘制，依据的是 ADR 而不是代码。想知道这些各自跑在哪个进程里，看 循环与日志；想看论证，看 0039。
