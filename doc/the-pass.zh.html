一张票是怎么被做出来的

灵台一次只拿一张票，让它走完十步。这一页讲的是：每一步是什么、关于它你能决定什么、以及当某一步不放行时这张票去哪里。

流水线是固定的；每一步做什么是你的。十步和它们的顺序永远不变 —— 正是这一点让看板、日志和这一页说的是同一件事。每一步跑什么，是一个插件，由你的 recipe 指定。什么都不写，你得到灵台自带的那一套，而那本身就是一条能用的流水线。

一棵工作树就是一趟 pass 的全部。一张票拿到一个从你的 base 切出来的分支，之后的一切 —— install、agent、build、review、合并 —— 都发生在里面。不会因为某一步说了不，就把它扔掉重来。

你要写的东西

一个文件，在你自己的机器上：~/.lingtai/<项目>/recipe.yml。灵台工作的那个仓库里，什么都不用提交。

steps:
  claim:
    - queue: { kinds: [bug, feature], backoff: 1h }
      restarts: 1        # 这张票最多被认领几次
  admit:
    - worktree: { base: main }
  prepared:
    - run: pnpm install
      timeout: 10m
  implement:
    - agent: claude-code
      turns: 150            # 一次 agent run 之内
      wall:  1h             # 一次 agent run 之内
      rounds: 3            # 一次拒绝把 agent 打回去几次
  build:
    - run: pnpm typecheck && pnpm test
  review:
    - agent: claude-code

一步是一串插件，按你写下的顺序跑。结果怎么归并，是那一步自己的事：在 claim，第一个找到票的插件赢；在 prepared，每一个都得过。文件里没写的步，就是那一步上什么都没有 —— 而它仍然会被画出来，好让没配置和被悄悄跳过永远不长得一样。

有些键不属于插件 —— 它们是灵台加在插件上的界限。一个 run: 插件没法忽略自己的 timeout，因为执行它的是 runner，不是插件在自觉遵守。rounds 和 restarts 是同一类，而且各自写在被它约束的那一步上。

一趟 pass 最多花你多少

四个数，前三个会被第四个乘一遍。

把它当算术读：一趟 pass 最多 rounds + 1 次 agent run，每次由 turns 和 wall 封顶 —— 而 restarts 是一张票最多买几趟 pass。lingtai add 会在任何东西跑起来之前把这笔总账打印给你。

这里没有任何一个数在限制「你被问几次」。一个没跑完的步 —— agent 停下来问、reviewer 崩了 —— 不买任何一轮，因为它对你的改动没有做出任何裁决。

它什么时候停下来等你

一个入口，一个去处。

什么会把一张票放到那里

所有上限都花完了 —— 先是 rounds，然后是 restarts —— 而这次改动仍然被拒。或者回来了一个只有你能回答的问题：需求不清、一个设计决定、两处改动把同一个意图改成了不同的样子。

只有 proposed 能把票送到你面前。没有任何一步能自己走到你这里 —— 正是这一点，让这值不值得打扰一个人成为一个地方的一个决定，而不是散落在整条流水线里的习惯。

它会带着什么过来

是什么拒的、为什么，用那一步自己的话 —— findings、build 的输出、冲突的那些路径。你不该为了搞清一张票为什么在等而去翻日志。

而且 end 照样会跑。你自己把票关掉，也是一种结局；那个负责收尾的步对每一种结局都跑，而不是只对顺利的那一种。
